<BigIdea>
<Tr>
<En>
A **proxy** is a middleman server that forwards requests. A **forward proxy** works for **clients** going out (a company web filter). A **reverse proxy** works for **servers**: users talk to it, and it passes requests to your app (nginx, Caddy, Cloudflare). A **load balancer** is a reverse proxy that spreads requests across several servers and skips broken ones using **health checks**. Behind a proxy, the real user's IP arrives in **`X-Forwarded-For`**.
</En>
<Ur>
**Proxy** beech ka server hai jo requests aage bhejta hai. **Forward proxy** bahar jane wale **clients** ke liye kaam karta hai (company ka web filter). **Reverse proxy** **servers** ke liye kaam karta hai: users us se baat karte hain, aur wo requests aap ki app ko deta hai (nginx, Caddy, Cloudflare). **Load balancer** aisa reverse proxy hai jo requests kai servers me baant deta hai aur **health checks** se tootay hue servers chhor deta hai. Proxy ke peeche asli user ka IP **`X-Forwarded-For`** me aata hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Your Node.js app listens on port 3000. You could expose it directly, but then who handles HTTPS, compression, static files, rate limits, many app copies, zero-downtime deploys and attacks? A specialised server in front does all that, and your app just answers requests.

```text
Forward proxy (for clients):          Reverse proxy / load balancer (for servers):

 employee ─┐                                           ┌─► app server 1 :3000
 employee ─┼─► proxy ─► internet       user ─► nginx ──┼─► app server 2 :3000
 employee ─┘   (filters, logs)                (TLS,     └─► app server 3 :3000
                                               cache,       (health-checked)
                                               routing)
```

| | Forward proxy | Reverse proxy |
| --- | --- | --- |
| Works for | Clients | Servers |
| Hides | Who the client is | What the servers are |
| Set up by | Client / company IT | Site owner |
| Typical uses | Web filtering, egress control, privacy | TLS, routing, caching, load balancing, WAF |

</En>
<Ur>

Aap ki Node.js app port 3000 par sunti hai. Ise seedha bahar khol sakte hain, lekin phir HTTPS, compression, static files, rate limits, app ki kai copies, bina rukawat deploys aur hamle kaun sambhalega? Saamne ka khaas server ye sab karta hai, aur aap ki app bas requests ka jawab deti hai.

```text
Forward proxy (for clients):          Reverse proxy / load balancer (for servers):

 employee ─┐                                           ┌─► app server 1 :3000
 employee ─┼─► proxy ─► internet       user ─► nginx ──┼─► app server 2 :3000
 employee ─┘   (filters, logs)                (TLS,     └─► app server 3 :3000
                                               cache,       (health-checked)
                                               routing)
```

| | Forward proxy | Reverse proxy |
| --- | --- | --- |
| Kis ke liye | Clients | Servers |
| Kya chhupata hai | Client kaun hai | Servers kya hain |
| Kaun lagata hai | Client / company IT | Site ka malik |
| Aam istemal | Web filtering, bahar jane par qaboo, raazdari | TLS, routing, caching, load balancing, WAF |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Almost every production web app** sits behind nginx, Caddy, Traefik, an ingress controller, a cloud load balancer or a CDN, often several layers.
- **Scale and uptime:** run many copies, survive one crashing, deploy without downtime.
- **Security:** one hardened front door for TLS, rate limits and WAF rules, hiding internal servers.
- **Debugging:** 502/504 errors, wrong client IPs in logs, redirect loops: all proxy problems.

</En>
<Ur>

- **Taqreeban har production web app** nginx, Caddy, Traefik, ingress controller, cloud load balancer ya CDN ke peeche hoti hai, aksar kai tehon me.
- **Barhna aur chalte rehna:** kai copies chalao, ek ke crash par bhi chalte raho, bina rukawat deploy.
- **Security:** TLS, rate limits aur WAF rules ke liye ek mazboot saamne ka darwaza, andaroni servers chhupe hue.
- **Debugging:** 502/504 errors, logs me ghalat client IPs, redirect loops: sab proxy ke masle.

</Ur>
</Tr>
</Why>

<Tr>
<En>

The proxy opens its **own** connection to the backend and copies the request across, adding headers about the original client. In nginx it's one line: `proxy_pass http://127.0.0.1:3000;`.

</En>
<Ur>

Proxy backend se **apna** connection kholta hai aur request wahan copy karta hai, asal client ke baare me headers jor kar. nginx me ye ek line hai: `proxy_pass http://127.0.0.1:3000;`.

</Ur>

## Picture it

<Tr>
<En>

A **hotel reception**. Guests never walk straight into the kitchen. They talk to reception (the **reverse proxy**), which checks them, answers simple questions itself (static files, cached answers), and passes real requests to the right department (**routing**). When several staff can do the same job, reception spreads the work evenly and skips anyone who is sick today (**load balancing + health checks**).

A **forward proxy** is the opposite: a **company travel desk** that books trips **for employees**, so the outside world only sees the travel desk, not the employee.

</En>
<Ur>

**Hotel ki reception**. Mehman seedha kitchen me nahi jate. Wo reception (**reverse proxy**) se baat karte hain, jo unhe check karti hai, aasaan sawalon ke jawab khud deti hai (static files, cached jawab), aur asli requests sahi shoabe tak pohanchati hai (**routing**). Jab kai mulazim ek hi kaam kar sakte hon, reception kaam barabar baantti hai aur aaj beemar mulazim ko chhor deti hai (**load balancing + health checks**).

**Forward proxy** ulta hai: **company ka travel desk** jo **mulazimon ke liye** safar book karta hai, isliye bahar ki duniya sirf travel desk dekhti hai, mulazim ko nahi.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="A reverse proxy in a few lines">

<Tr>
<En>

The proxy receives the request, sends it to the backend over its **own** connection, and returns the answer. Building one shows exactly why nginx behaves as it does: the backend talks to the **proxy**, not the user.

</En>
<Ur>

Proxy request leta hai, use **apne** connection par backend ko bhejta hai, aur jawab lautata hai. Ek bana kar saaf samajh aata hai ke nginx aisa kyun karta hai: backend **proxy** se baat karta hai, user se nahi.

</Ur>
</Tr>

```bash
cat > backend.mjs <<'EOF'
import http from "node:http";
const name = process.argv[2], port = Number(process.argv[3]);
http.createServer((req, res) => {
  if (req.url === "/health") return res.end("ok");
  res.end(`${name} answered ${req.url} | socket IP: ${req.socket.remoteAddress} | X-Forwarded-For: ${req.headers["x-forwarded-for"] ?? "-"}\n`);
}).listen(port, "127.0.0.1");
EOF
cat > proxy.mjs <<'EOF'
import http from "node:http";
http.createServer((req, res) => {
  const up = http.request({ host: "127.0.0.1", port: 4001, path: req.url, method: req.method,
    headers: { ...req.headers, "x-forwarded-for": "203.0.113.5", "x-forwarded-proto": "https" } },   // pretend the user was 203.0.113.5
    (r) => { res.writeHead(r.statusCode, r.headers); r.pipe(res); });
  up.on("error", () => { res.writeHead(502); res.end("502 Bad Gateway: upstream not reachable\n"); });
  req.pipe(up);
}).listen(4000, "127.0.0.1");
EOF
node backend.mjs app-1 4001 & b1=$!
node proxy.mjs & px=$!
sleep 0.5
curl -s http://127.0.0.1:4000/products
kill $b1; sleep 0.3
curl -s http://127.0.0.1:4000/products
kill $px
```

```text output
app-1 answered /products | socket IP: 127.0.0.1 | X-Forwarded-For: 203.0.113.5
502 Bad Gateway: upstream not reachable
```

<Happened>
<Tr>
<En>The backend's **socket** saw the proxy's IP (`127.0.0.1`); the real client was only known from `X-Forwarded-For`. When the backend died, the proxy itself answered **502**: exactly what nginx shows when your app is down.</En>
<Ur>Backend ke **socket** ne proxy ka IP (`127.0.0.1`) dekha; asal client sirf `X-Forwarded-For` se maloom hua. Backend marne par proxy ne khud **502** diya: bilkul wahi jo nginx aap ki app band hone par dikhata hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Load balancing algorithms">

<Tr>
<En>

How the load balancer picks a backend for each request:

- **Round robin:** each in turn.
- **Least connections:** the least busy one.
- **Weighted:** bigger servers get more.
- **IP hash:** the same client IP always goes to the same server.

</En>
<Ur>

Load balancer har request ke liye backend kaise chunta hai:

- **Round robin:** baari baari.
- **Least connections:** sab se kam masroof.
- **Weighted:** bare servers ko zyada.
- **IP hash:** ek client IP hamesha ek hi server par.

</Ur>
</Tr>

```python
import itertools, hashlib
servers = ["app-1", "app-2", "app-3"]
rr = itertools.cycle(servers)
print("round robin:      ", [next(rr) for _ in range(6)])
active = {"app-1": 12, "app-2": 3, "app-3": 7}
print("least connections:", min(active, key=active.get), "(fewest active:", active, ")")
weights = {"app-1": 3, "app-2": 1}
print("weighted 3:1:     ", [s for s, w in weights.items() for _ in range(w)])
for ip in ["203.0.113.5", "198.51.100.7", "203.0.113.5"]:
    h = int(hashlib.md5(ip.encode()).hexdigest(), 16)
    print(f"ip hash {ip:<13} →", servers[h % len(servers)])
```

```text output
round robin:       ['app-1', 'app-2', 'app-3', 'app-1', 'app-2', 'app-3']
least connections: app-2 (fewest active: {'app-1': 12, 'app-2': 3, 'app-3': 7} )
weighted 3:1:      ['app-1', 'app-1', 'app-1', 'app-2']
ip hash 203.0.113.5   → app-3
ip hash 198.51.100.7  → app-1
ip hash 203.0.113.5   → app-3
```

</Step>

<Step title="Health checks">

<Tr>
<En>

The load balancer calls each backend regularly (e.g. `GET /health` every 10 s) and stops sending traffic to one that fails several times in a row. Crashed or frozen instances disappear for users automatically. A good `/health` is fast and checks what the app really needs (can it reach the database?). Kubernetes splits it into **liveness** ("am I alive?") and **readiness** ("can I take traffic now?").

</En>
<Ur>

Load balancer har backend ko baqaida call karta hai (maslan har 10 s `GET /health`) aur jo musalsal kai dafa fail ho use traffic bhejna band kar deta hai. Crash ya atke instances users ke liye khud gayab ho jate hain. Achha `/health` tez hota hai aur wo check karta hai jo app ko waqai chahiye (database tak pohanch?). Kubernetes ise **liveness** ("kya main zinda hoon?") aur **readiness** ("kya main abhi traffic le sakta hoon?") me baant deta hai.

</Ur>
</Tr>

```bash
cat > lb.mjs <<'EOF'
import http from "node:http";
const backends = [{ port: 4011, healthy: true }, { port: 4012, healthy: true }];
let i = 0;
const check = () => backends.forEach((b) => {
  http.get({ host: "127.0.0.1", port: b.port, path: "/health", timeout: 500 }, (r) => { b.healthy = r.statusCode === 200; r.resume(); })
      .on("error", () => (b.healthy = false));
});
setInterval(check, 200); check();
http.createServer((req, res) => {
  const pool = backends.filter((b) => b.healthy);
  if (!pool.length) { res.writeHead(503); return res.end("503: no healthy backend\n"); }
  const b = pool[i++ % pool.length];
  http.get({ host: "127.0.0.1", port: b.port, path: req.url }, (r) => r.pipe(res)).on("error", () => { res.writeHead(502); res.end("502\n"); });
}).listen(4010, "127.0.0.1");
EOF
node backend.mjs app-1 4011 & a=$!
node backend.mjs app-2 4012 & b=$!
node lb.mjs & lb=$!
sleep 0.8
for n in 1 2 3 4; do curl -s http://127.0.0.1:4010/x | cut -d'|' -f1; done
echo "--- app-2 crashes ---"; kill $b; sleep 0.6
for n in 1 2 3; do curl -s http://127.0.0.1:4010/x | cut -d'|' -f1; done
echo "--- app-1 crashes too ---"; kill $a; sleep 0.6
curl -s http://127.0.0.1:4010/x
kill $lb
```

```text output
app-1 answered /x 
app-2 answered /x 
app-1 answered /x 
app-2 answered /x 
--- app-2 crashes ---
app-1 answered /x 
app-1 answered /x 
app-1 answered /x 
--- app-1 crashes too ---
503: no healthy backend
```

<Happened>
<Tr>
<En>Requests alternated (round robin). After app-2 crashed, health checks removed it and users kept getting answers. With no healthy backend at all, the balancer returned **503**.</En>
<Ur>Requests baari baari gayin (round robin). app-2 crash hone ke baad health checks ne use hata diya aur users ko jawab milte rahe. Koi sehatmand backend na bacha to balancer ne **503** diya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="The real client IP: X-Forwarded-For">

<Tr>
<En>

Behind a proxy, every request seems to come from the proxy's IP, which breaks logs, rate limits, geo-blocking and fraud checks. Proxies add the client's IP to `X-Forwarded-For` (plus `X-Forwarded-Proto` for http/https). In Express/NestJS: `app.set("trust proxy", 1)`. But the header is **just text** that clients can fake, so **trust only the entries your own proxies added**.

</En>
<Ur>

Proxy ke peeche har request proxy ke IP se aati lagti hai, jo logs, rate limits, mulk ke hisaab se rok aur fraud checks tor deta hai. Proxies client ka IP `X-Forwarded-For` me jorte hain (aur http/https ke liye `X-Forwarded-Proto`). Express/NestJS me: `app.set("trust proxy", 1)`. Lekin header **sirf text** hai jo clients naqli bana sakte hain, isliye **sirf wo entries maanein jo aap ke apne proxies ne jori hon**.

</Ur>
</Tr>

```text
user 203.0.113.5 ─► Cloudflare 172.68.1.9 ─► ALB 10.0.1.20 ─► app

header received by the app:
X-Forwarded-For: 203.0.113.5, 172.68.1.9
                 └ client     └ CDN edge                (ALB's own address = the socket peer)
```

```javascript
// The header is just text — a client can fake it. Only the RIGHT-most entries added by YOUR proxies are trustworthy.
const header = "6.6.6.6, 203.0.113.5, 172.68.1.9";        // first value forged by the client
const trustedProxyHops = 2;                                  // CDN + load balancer
const parts = header.split(",").map((s) => s.trim());
console.log("naive (left-most):  ", parts[0], "← attacker-controlled!");
console.log("correct (trust 2):  ", parts[parts.length - trustedProxyHops]);
```

```text output
naive (left-most):   6.6.6.6 ← attacker-controlled!
correct (trust 2):   203.0.113.5
```

</Step>

<Step title="Sticky sessions">

<Tr>
<En>

Sending all of one user's requests to the same backend, usually with a load-balancer cookie. It's needed when an app keeps sessions **in memory**; otherwise the next request lands on a server that doesn't know the user. Prefer **stateless** apps (sessions in Redis/DB, or signed tokens) so any server can serve any request; stickiness makes scaling and deploys uneven.

</En>
<Ur>

Ek user ki saari requests ek hi backend par bhejna, aam tor par load balancer ki cookie se. Ye tab zaroori hai jab app sessions **memory me** rakhti ho; warna agli request aise server par jati hai jo user ko nahi jaanta. **Stateless** apps behtar hain (sessions Redis/DB me, ya signed tokens) taa ke koi bhi server koi bhi request sambhal sake; stickiness barhne aur deploys ko be-tawazun banati hai.

</Ur>
</Tr>

</Step>

<Step title="L4 vs L7 load balancers">

<Tr>
<En>

An **L4** balancer forwards TCP/UDP connections by IP and port without reading them: fast, any protocol. An **L7** balancer understands HTTP: it can route by host and path, end TLS, run HTTP health checks and a WAF. Websites and APIs → L7. Non-HTTP traffic, extreme performance, static IPs → L4.

| | L4 (AWS NLB) | L7 (AWS ALB) |
| --- | --- | --- |
| Understands | IP, port | HTTP host, path, headers, cookies |
| Route `/api` vs `/` | No | Yes |
| TLS termination | Optional (passthrough or TLS listener) | Yes |
| WAF | No | Yes (AWS WAF) |
| Protocols | Any TCP/UDP | HTTP, HTTPS, gRPC, WebSocket |
| Client IP | Kept | In X-Forwarded-For |

</En>
<Ur>

**L4** balancer TCP/UDP connections ko IP aur port se parhe baghair aage bhejta hai: tez, har protocol. **L7** balancer HTTP samajhta hai: host aur path se route, TLS khatam, HTTP health checks aur WAF chala sakta hai. Websites aur APIs → L7. Ghair-HTTP traffic, bohot zyada raftar, pakke IPs → L4.

| | L4 (AWS NLB) | L7 (AWS ALB) |
| --- | --- | --- |
| Samajhta hai | IP, port | HTTP host, path, headers, cookies |
| `/api` bamuqabla `/` route | Nahi | Haan |
| TLS termination | Ikhtiyari (passthrough ya TLS listener) | Haan |
| WAF | Nahi | Haan (AWS WAF) |
| Protocols | Koi bhi TCP/UDP | HTTP, HTTPS, gRPC, WebSocket |
| Client IP | Bacha rehta hai | X-Forwarded-For me |

</Ur>
</Tr>

</Step>

<Step title="An nginx reverse proxy config">

<Tr>
<En>

The most common real setup: nginx in front of app processes on one server. You'll write or read this on almost every VPS deployment. It lives in `/etc/nginx/sites-available/shop` (linked into `sites-enabled`). Test with `sudo nginx -t`, apply with `sudo systemctl reload nginx`.

</En>
<Ur>

Sab se aam asli setup: ek server par app processes ke saamne nginx. Taqreeban har VPS deployment par aap ise likhenge ya parhenge. Ye `/etc/nginx/sites-available/shop` me hota hai (`sites-enabled` me link). `sudo nginx -t` se test karein, `sudo systemctl reload nginx` se lagayen.

</Ur>
</Tr>

```text
upstream shop_app {
    least_conn;
    server 127.0.0.1:3000 max_fails=3 fail_timeout=10s;
    server 127.0.0.1:3001 max_fails=3 fail_timeout=10s;
    keepalive 32;                                   # reuse connections to the app
}

server {
    listen 80;
    server_name shop.example.com;
    return 301 https://$host$request_uri;           # force HTTPS
}

server {
    listen 443 ssl;
    http2 on;
    server_name shop.example.com;
    ssl_certificate     /etc/letsencrypt/live/shop.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/shop.example.com/privkey.pem;

    client_max_body_size 10m;                       # upload limit
    location /assets/ {                             # static files served by nginx itself
        root /var/www/shop/current/public;
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
    location / {
        proxy_pass http://shop_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;
    }
}
```

</Step>

<Step title="CDNs: reverse proxies all over the world">

<Tr>
<En>

A **Content Delivery Network** is a global set of caching reverse proxies (edge servers) close to users: a user in Houston is served from a nearby edge. Lower latency, less load on your **origin**, and DDoS protection. Point DNS at the CDN; it fetches from the origin on a cache miss. Control caching with `Cache-Control`, and lock the origin so it only accepts traffic from the CDN.

</En>
<Ur>

**Content Delivery Network** users ke qareeb caching reverse proxies (edge servers) ka duniya bhar ka majmua hai: Houston ke user ko qareebi edge se diya jata hai. Kam der, aap ke **origin** par kam bojh, aur DDoS se bachao. DNS ko CDN ki taraf karein; cache miss par ye origin se laata hai. `Cache-Control` se caching sambhalein, aur origin ko band karein taa ke sirf CDN se traffic le.

</Ur>
</Tr>

</Step>

<Step title="Forward proxies and egress control">

<Tr>
<En>

Clients can be set to send outgoing requests through a proxy: `HTTPS_PROXY`, `HTTP_PROXY`, browser settings. Companies filter and log web access this way, and secure environments only let servers reach approved destinations through an **egress proxy** (Squid, Zscaler, cloud egress firewalls). `NO_PROXY=localhost,127.0.0.1,.internal` skips the proxy for internal addresses. "Works on my laptop, fails on the company server" is often a proxy setting.

</En>
<Ur>

Clients ko bahar jane wali requests proxy se bhejne par set kiya ja sakta hai: `HTTPS_PROXY`, `HTTP_PROXY`, browser settings. Companies isi tarah web ka istemal filter aur log karti hain, aur mehfooz mahol servers ko sirf **egress proxy** (Squid, Zscaler, cloud egress firewalls) ke zariye manzoor jagahon tak jane dete hain. `NO_PROXY=localhost,127.0.0.1,.internal` andaroni addresses ke liye proxy chhor deta hai. "Mere laptop par chalta hai, company server par nahi" aksar proxy ki setting hoti hai.

</Ur>
</Tr>

```bash

env HTTPS_PROXY=http://127.0.0.1:9 NO_PROXY=127.0.0.1 curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:9; echo " ← NO_PROXY: connects directly (here nothing listens, so also 000)"
```

## Common mistakes

<Compare>
<Bad title="Trusting X-Forwarded-For from anyone">

```text
const ip = req.headers["x-forwarded-for"].split(",")[0];   // attacker sends 6.6.6.6
```

</Bad>
<Good title="Trust only your own proxy hops">

```text
app.set("trust proxy", 1);      // exactly one proxy (the load balancer)
const ip = req.ip;
```

</Good>
</Compare>

<Compare>
<Bad title="Health check that lies">

```text
app.get("/health", (req, res) => res.send("ok"));   // 200 even if the database is down
```

</Bad>
<Good title="Check what really matters">

```text
app.get("/health", async (req, res) => {
  try { await db.query("SELECT 1"); res.send("ok"); }
  catch { res.status(503).send("db down"); }
});
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Not trusting the header at all**: every user looks like the proxy.
- **Timeouts that don't line up** (proxy 30 s, app 60 s) → 504s.
- **Sessions in memory** with several backends and no stickiness.
- **Backends reachable directly**, skipping the proxy's TLS and WAF.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Header par bilkul bharosa na karna**: har user proxy jaisa dikhta hai.
- **Mel na khaate timeouts** (proxy 30 s, app 60 s) → 504.
- **Kai backends ke saath memory me sessions** aur stickiness nahi.
- **Backends seedhe pohanch me**, proxy ka TLS aur WAF chhor kar.

</Ur>
</Tr>

<Challenge title="Path-based routing">

<Tr>
<En>
Build what an L7 balancer does: one public address, two internal services, chosen by **path**. That's how one domain can serve a Next.js front-end at `/` and a NestJS API at `/api`.
</En>
<Ur>
Wo banayen jo L7 balancer karta hai: ek public address, do andaroni services, **path** ke hisaab se chuni hui. Isi tarah ek domain `/` par Next.js front-end aur `/api` par NestJS API chala sakta hai.
</Ur>

```bash
# Path-based routing (what an L7 balancer does)
cat > router.mjs <<'EOF'
import http from "node:http";
const routes = [["/api/", 4021], ["/", 4022]];
http.createServer((req, res) => {
  const [, port] = routes.find(([prefix]) => req.url.startsWith(prefix));
  http.get({ host: "127.0.0.1", port, path: req.url }, (r) => r.pipe(res));
}).listen(4020, "127.0.0.1");
EOF
node backend.mjs api-service 4021 & a=$!
node backend.mjs web-frontend 4022 & w=$!
node router.mjs & r=$!
sleep 0.6
curl -s http://127.0.0.1:4020/api/orders | cut -d'|' -f1
curl -s http://127.0.0.1:4020/about | cut -d'|' -f1
kill $a $w $r
```

```text output
web-frontend answered /about 
```

<DeepDive title="Real world: three things broke behind an ALB">

After moving an Express app behind an AWS ALB, three things broke at once:

```text
1. Logs and rate limiting: every request came from 10.0.1.x (the ALB) → all users shared one rate limit.
   Fix: app.set("trust proxy", 1) so req.ip uses X-Forwarded-For from the ALB only.

2. Redirect loop on login: the app saw http:// (TLS ends at the ALB) and kept redirecting to https://.
   Fix: trust X-Forwarded-Proto (same setting) so req.secure is true.

3. Random 502s during deploys: instances were killed while still in the target group.
   Fix: a /health endpoint, target-group health checks, deregistration delay of 30 s,
        and graceful shutdown on SIGTERM so in-flight requests finish.
```

</DeepDive>

<DeepDive title="Security lens">

The reverse proxy is your front door. Harden it, and make sure it's the **only** door.

- **Lock backends:** security groups allow app ports only from the load balancer; CDN origins only from the CDN's IP ranges.
- **Rate limits and request limits** (body size, header size, timeouts) at the proxy stop brute force and slow-loris attacks.
- **WAF** on the L7 balancer or CDN blocks common attacks (SQL injection patterns, known bad bots).
- **Request smuggling:** proxy and backend reading requests differently can let attackers sneak requests through; keep proxies updated and use HTTP/1.1 keep-alive consistently or HTTP/2 end to end.
- **SSRF via open proxies:** never expose a proxy that fetches arbitrary URLs for anyone (it can reach your internal network and cloud metadata).
- **Proxy logs** are the best single source for spotting attacks: keep them centrally.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a forward proxy and a reverse proxy?">
A forward proxy sits in front of clients and makes requests on their behalf to the outside world, used for filtering, logging and egress control; servers see the proxy instead of the client. A reverse proxy sits in front of servers and receives requests on their behalf, used for TLS termination, routing, caching, load balancing and protection; clients see the proxy instead of the backend servers.
</QA>

<QA q="How does a load balancer know a server is unhealthy?">
It runs health checks, regularly sending a request such as GET /health to each backend and expecting a successful status within a timeout. After a configured number of consecutive failures it marks the backend unhealthy and stops routing traffic to it, and after enough successes it adds it back. Passive checks also mark backends unhealthy when real requests fail.
</QA>

<QA q="How does an application behind a proxy get the real client IP, and what is the risk?">
The proxy adds the client's address to the X-Forwarded-For header (or a similar header), and the application is configured to read it, for example with trust proxy in Express. The risk is that clients can send their own forged X-Forwarded-For values, so the application must only trust entries added by its own known proxies.
</QA>

<QA q="When would you choose a layer 4 load balancer over a layer 7 one?">
For non-HTTP protocols, when you need very high throughput and low latency, static IP addresses, or TLS passthrough to the backends. A layer 7 load balancer is preferred for web applications and APIs that need routing by host or path, TLS termination, HTTP health checks and WAF integration.
</QA>

</DeepDive>
