<BigIdea>
<Tr>
<En>
A **tunnel** carries one network's packets **inside** another connection, like a sealed pipe through the internet. A **VPN** is an encrypted tunnel that makes a far-away laptop, or a whole far-away network, behave as if it were on the private network. **Remote-access VPNs** connect people; **site-to-site VPNs** connect networks. Modern teams increasingly replace "VPN = access to the whole network" with **zero-trust** tools that grant access one app at a time.
</En>
<Ur>
**Tunnel** ek network ke packets doosre connection ke **andar** le jata hai, internet me se guzarti band pipe ki tarah. **VPN** ek encrypted tunnel hai jo door ke laptop, ya poore door ke network, ko aisa bana deta hai jaise wo private network par ho. **Remote-access VPNs** logon ko jorte hain; **site-to-site VPNs** networks ko. Jadeed teams barhte tor par "VPN = poore network tak pohanch" ki jagah **zero-trust** tools istemal karti hain jo ek waqt me ek app ki ijazat dete hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Your database lives in a private subnet with no internet access: good for security. But you're at home and need to reach it. Or your office network and an AWS VPC must talk privately. A **tunnel** builds a private, encrypted path across the public internet.

```text
Without VPN:   laptop 192.168.1.20 ──internet──► ✗ 10.0.21.5 (private DB: unreachable)

With VPN:      laptop gets a VPN address 10.100.0.7
               inner packet: 10.100.0.7 → 10.0.21.5:5432          (private addresses)
               outer packet: 39.40.41.42:51820 → 203.0.113.50:51820 (public, encrypted UDP)
                                         │
               VPN gateway in the VPC unwraps, decrypts, forwards → 10.0.21.5:5432 ✓
```

| | Remote-access VPN | Site-to-site VPN |
| --- | --- | --- |
| Connects | A person's device to a network | Two networks |
| Who starts it | User clicks "connect" | Always on, between gateways |
| Typical tech | WireGuard, OpenVPN, AWS Client VPN, Tailscale | IPsec (AWS/Azure/GCP VPN), WireGuard |
| Example | Developer at home → staging VPC | Office in Chicago ↔ AWS VPC in Frankfurt |

</En>
<Ur>

Aap ka database bina internet wale private subnet me hai: hifazat ke liye achha. Lekin aap ghar par hain aur us tak pohanchna hai. Ya aap ke office ka network aur AWS VPC private tareeqe se baat karein. **Tunnel** public internet ke paar private, encrypted raasta banata hai.

```text
Without VPN:   laptop 192.168.1.20 ──internet──► ✗ 10.0.21.5 (private DB: unreachable)

With VPN:      laptop gets a VPN address 10.100.0.7
               inner packet: 10.100.0.7 → 10.0.21.5:5432          (private addresses)
               outer packet: 39.40.41.42:51820 → 203.0.113.50:51820 (public, encrypted UDP)
                                         │
               VPN gateway in the VPC unwraps, decrypts, forwards → 10.0.21.5:5432 ✓
```

| | Remote-access VPN | Site-to-site VPN |
| --- | --- | --- |
| Kis ko jorta hai | Insaan ka device network se | Do networks |
| Kaun shuru karta hai | User "connect" dabata hai | Hamesha on, gateways ke darmiyan |
| Aam tech | WireGuard, OpenVPN, AWS Client VPN, Tailscale | IPsec (AWS/Azure/GCP VPN), WireGuard |
| Misaal | Ghar se developer → staging VPC | Chicago ka office ↔ Frankfurt ka AWS VPC |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Private infrastructure stays private:** databases, admin panels and internal tools need no public exposure.
- **Hybrid cloud:** offices and data centres connect to cloud VPCs.
- **Remote work:** employees reach internal systems safely.
- **Security:** VPN gateways are top attack targets (many critical bugs each year), and "VPN = access to everything" is a big risk.

</En>
<Ur>

- **Private infrastructure private rehta hai:** databases, admin panels aur andaroni tools ko bahar khulne ki zaroorat nahi.
- **Hybrid cloud:** offices aur data centres cloud VPCs se jurte hain.
- **Ghar se kaam:** mulazim andaroni systems tak mehfooz pohanchte hain.
- **Security:** VPN gateways hamlon ka sab se bara nishana hain (har saal kai sangeen bugs), aur "VPN = har cheez tak pohanch" bara khatra hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Need | Option |
| --- | --- |
| A developer needs a private DB for a few minutes | SSH tunnel through a bastion, or SSM port forwarding |
| Small team needs private network access | WireGuard / Tailscale |
| Office ↔ cloud permanently | Site-to-site IPsec (AWS Site-to-Site VPN) |
| Very high bandwidth, stable link | AWS Direct Connect / Azure ExpressRoute (private lines) |
| Employees reach internal web apps | Zero-trust access proxy (Cloudflare Access, Google IAP) |
| Privacy on public Wi-Fi | Full-tunnel VPN (personal use) |

</En>
<Ur>

| Zaroorat | Option |
| --- | --- |
| Developer ko chand minute private DB chahiye | Bastion ke zariye SSH tunnel, ya SSM port forwarding |
| Chhoti team ko private network chahiye | WireGuard / Tailscale |
| Office ↔ cloud hamesha | Site-to-site IPsec (AWS Site-to-Site VPN) |
| Bohot zyada bandwidth, mustaqil link | AWS Direct Connect / Azure ExpressRoute (private lines) |
| Mulazim andaroni web apps tak | Zero-trust access proxy (Cloudflare Access, Google IAP) |
| Public Wi-Fi par raazdari | Full-tunnel VPN (zaati istemal) |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Two ideas do all the work: **encapsulation** (wrap the private packet inside a public one) and **encryption** (so nobody in between can read or change it). Which traffic enters the tunnel is just **routing**.

</En>
<Ur>

Do khayal saara kaam karte hain: **encapsulation** (private packet ko public packet me lapetna) aur **encryption** (taa ke beech me koi parh ya badal na sake). Kaunsa traffic tunnel me jaye ye bas **routing** hai.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

A **diplomatic pouch**. A letter for someone inside an embassy is put in a sealed pouch, and the pouch travels through the normal post to the embassy. Postal workers only see "pouch for the embassy", not the letter or its real recipient. At the embassy the pouch is opened and the letter delivered inside. The **outer** address is the public internet; the **inner** letter is your private traffic. That's **encapsulation + encryption**.

</En>
<Ur>

**Sifarati thaila** (diplomatic pouch). Sifarat khane ke andar kisi ke liye khat ek band thaile me rakha jata hai, aur thaila aam daak se sifarat khane jata hai. Daak wale sirf "sifarat khane ka thaila" dekhte hain, khat ya us ka asli paane wala nahi. Sifarat khane me thaila khol kar khat andar pohancha diya jata hai. **Bahar** ka pata public internet hai; **andar** ka khat aap ka private traffic. Yahi **encapsulation + encryption** hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Tunnels: a packet inside a packet">

<Tr>
<En>

A tunnel wraps complete packets from one network in new outer packets, sends them across another network, and unwraps them at the far end. The internet only delivers the outer packet; it never has to understand the private addresses inside. Used by VPNs, container overlay networks and SSH port forwarding. Wrapping adds bytes, so tunnels lower the **MTU** (WireGuard uses 1420 instead of 1500).

</En>
<Ur>

Tunnel ek network ke poore packets ko naye bahari packets me lapet kar doosre network ke paar bhejta hai, aur door ke sire par kholta hai. Internet sirf bahar wala packet pohanchata hai; use andar ke private addresses samajhne ki zaroorat nahi. VPNs, container overlay networks aur SSH port forwarding isi par chalte hain. Lapetne se bytes barhte hain, isliye tunnels **MTU** kam karte hain (WireGuard 1500 ki jagah 1420).

</Ur>
</Tr>

```python
inner = {"src": "10.100.0.7", "dst": "10.0.21.5", "dport": 5432, "data": "SELECT 1"}
outer = {"src": "39.40.41.42", "dst": "203.0.113.50", "proto": "UDP", "dport": 51820,
         "payload": "<encrypted inner packet: %d bytes>" % (len(str(inner)) + 32)}
print("what the internet sees:", {k: v for k, v in outer.items()})
print("what the VPN gateway delivers inside:", inner)
mtu, overhead = 1500, 80
print(f"room left for inner packets: {mtu - overhead} bytes (WireGuard's default MTU is 1420)")
```

```text output
what the internet sees: {'src': '39.40.41.42', 'dst': '203.0.113.50', 'proto': 'UDP', 'dport': 51820, 'payload': '<encrypted inner packet: 108 bytes>'}
what the VPN gateway delivers inside: {'src': '10.100.0.7', 'dst': '10.0.21.5', 'dport': 5432, 'data': 'SELECT 1'}
room left for inner packets: 1420 bytes (WireGuard's default MTU is 1420)
```

</Step>

<Step title="A working port tunnel">

<Tr>
<En>

The simplest tunnel listens on a local port and, for each connection, connects to the target and copies bytes both ways. That's exactly what `ssh -L` and `kubectl port-forward` do.

</En>
<Ur>

Sab se saada tunnel local port par sunta hai aur har connection ke liye target se jur kar dono taraf bytes copy karta hai. Bilkul yahi `ssh -L` aur `kubectl port-forward` karte hain.

</Ur>
</Tr>

```bash
cat > private-db.mjs <<'EOF'
import net from "node:net";
net.createServer((s) => s.end("hello from the PRIVATE database on port 4105\n")).listen(4105, "127.0.0.1");
EOF
cat > tunnel.mjs <<'EOF'
import net from "node:net";
net.createServer((client) => {
  const target = net.connect(4105, "127.0.0.1");   // in real life: the private IP, reached via SSH/VPN
  client.pipe(target); target.pipe(client);
}).listen(15432, "127.0.0.1");
EOF
node private-db.mjs & db=$!
node tunnel.mjs & tn=$!
sleep 0.5
echo "connecting to localhost:15432 (my end of the tunnel):"
nc -w1 127.0.0.1 15432
kill $db $tn
```

```text output
connecting to localhost:15432 (my end of the tunnel):
hello from the PRIVATE database on port 4105
```

<Happened>
<Tr>
<En>The client only talked to `localhost:15432`, yet reached the private service. An SSH tunnel adds **login and encryption** to the same idea.</En>
<Ur>Client ne sirf `localhost:15432` se baat ki, phir bhi private service tak pohanch gaya. SSH tunnel isi khayal me **login aur encryption** jorta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="SSH tunnels and bastion hosts">

<Tr>
<En>

SSH can forward ports through its encrypted connection:

- **Local** (`-L`): a local port reaches something behind the server.
- **Remote** (`-R`): something on the server reaches your machine.
- **Dynamic** (`-D`): a SOCKS proxy.

A **bastion** (jump host) is the single hardened SSH entry into a private network. AWS SSM Session Manager does the same **without** opening port 22.

</En>
<Ur>

SSH apne encrypted connection se ports forward kar sakta hai:

- **Local** (`-L`): local port server ke peeche ki cheez tak pohanchta hai.
- **Remote** (`-R`): server ki koi cheez aap ki machine tak pohanchti hai.
- **Dynamic** (`-D`): SOCKS proxy.

**Bastion** (jump host) private network ka wahid mazboot SSH darwaza hai. AWS SSM Session Manager yahi kaam port 22 khole **baghair** karta hai.

</Ur>
</Tr>

```text
your laptop                bastion (public subnet)            database (private subnet)
localhost:15432 ══SSH═════► sshd ─────────────────────────────► 10.0.21.5:5432
   ▲ DBeaver/psql here

$ ssh -N -L 15432:10.0.21.5:5432 admin@bastion.example.com
$ psql "host=localhost port=15432 user=app dbname=shop"

# Same without an open port 22 (AWS Systems Manager):
$ aws ssm start-session --target i-0abc123 \
    --document-name AWS-StartPortForwardingSessionToRemoteHost \
    --parameters host=shop-db.xxxx.rds.amazonaws.com,portNumber=5432,localPortNumber=15432
```

</Step>

<Step title="WireGuard: a modern VPN">

<Tr>
<En>

A small, fast VPN built into the Linux kernel, running over UDP (default port 51820). Each peer has a key pair and is configured with the other side's **public key**, address, and **AllowedIPs** (the ranges routed through the tunnel). It's simple, modern, fast and easy to audit; Tailscale and many commercial VPNs are built on it. Generate keys with `wg genkey | tee priv | wg pubkey > pub`, start with `sudo wg-quick up wg0`.

</En>
<Ur>

Linux kernel me shamil chhota, tez VPN jo UDP par chalta hai (default port 51820). Har peer ka key pair hota hai aur use doosri taraf ki **public key**, pata, aur **AllowedIPs** (tunnel se jane wali ranges) di jati hain. Ye saada, jadeed, tez aur jaanchne me aasaan hai; Tailscale aur kai commercial VPNs isi par bane hain. Keys `wg genkey | tee priv | wg pubkey > pub` se banayen, `sudo wg-quick up wg0` se shuru karein.

</Ur>
</Tr>

```text
# Server (VPN gateway in the VPC): /etc/wireguard/wg0.conf
[Interface]
Address    = 10.100.0.1/24
ListenPort = 51820
PrivateKey = <server private key>

[Peer]                                   # Alex's laptop
PublicKey  = <laptop public key>
AllowedIPs = 10.100.0.7/32               # only this address may come from this key

# Laptop: wg0.conf
[Interface]
Address    = 10.100.0.7/32
PrivateKey = <laptop private key>
DNS        = 10.0.0.2

[Peer]                                   # the gateway
PublicKey  = <server public key>
Endpoint   = 203.0.113.50:51820
AllowedIPs = 10.0.0.0/16, 10.100.0.0/24  # split tunnel: only private ranges go through the VPN
PersistentKeepalive = 25
```

</Step>

<Step title="IPsec and cloud site-to-site VPNs">

<Tr>
<En>

IPsec is the long-standing standard for encrypted network-to-network tunnels. Almost every enterprise router supports it, so offices connect to clouds without special software. AWS Site-to-Site VPN, Azure VPN Gateway and GCP Cloud VPN all speak IPsec. AWS gives you **two tunnels** for redundancy. Both sides agree on keys (IKE), settings and the address ranges exchanged; routes are static or learned via BGP. CIDRs must not overlap.

</En>
<Ur>

IPsec network-se-network encrypted tunnels ka purana mayar hai. Taqreeban har company router ise samajhta hai, isliye offices bina khaas software ke cloud se jur jate hain. AWS Site-to-Site VPN, Azure VPN Gateway aur GCP Cloud VPN sab IPsec bolte hain. AWS bharose ke liye **do tunnels** deta hai. Dono taraf keys (IKE), settings aur badli jane wali ranges par mutafiq hoti hain; routes pakke hote hain ya BGP se seekhe jate hain. CIDRs takrane nahi chahiye.

</Ur>
</Tr>

```text
Office LAN 192.168.0.0/16                                     AWS VPC 10.0.0.0/16
 ┌──────────────┐   IPsec tunnel 1 (active)    ┌──────────────────────────┐
 │ office       │══════════════════════════════│ AWS Site-to-Site VPN     │
 │ firewall     │══════════════════════════════│ (Virtual Private Gateway │
 └──────────────┘   IPsec tunnel 2 (standby)   │  or Transit Gateway)     │
                                               └──────────────────────────┘
 office routes 10.0.0.0/16 → tunnel          VPC route table: 192.168.0.0/16 → vgw
```

</Step>

<Step title="Split tunnel vs full tunnel">

<Tr>
<En>

- **Split tunnel:** only private ranges go through the VPN; everything else goes straight to the internet. Saves bandwidth, keeps video calls fast.
- **Full tunnel:** all traffic (`0.0.0.0/0`) goes through the VPN. The company can filter everything, and users on untrusted Wi-Fi are protected.

It's just routing: which destinations point at the tunnel.

</En>
<Ur>

- **Split tunnel:** sirf private ranges VPN se; baqi sab seedha internet. Bandwidth bachta hai, video calls tez rehti hain.
- **Full tunnel:** saara traffic (`0.0.0.0/0`) VPN se. Company sab kuch filter kar sakti hai, aur be-bharosa Wi-Fi par users mehfooz rehte hain.

Ye bas routing hai: kaunsi manzilen tunnel ki taraf ishara karti hain.

</Ur>
</Tr>

```python
import ipaddress
def via(dst, tunnel_ranges):
    return "VPN tunnel" if any(ipaddress.ip_address(dst) in ipaddress.ip_network(r) for r in tunnel_ranges) else "direct to internet"
for mode, ranges in [("split", ["10.0.0.0/16", "10.100.0.0/24"]), ("full", ["0.0.0.0/0"])]:
    print(f"{mode} tunnel:")
    for dst in ["10.0.21.5", "142.250.181.14"]:
        print(f"   {dst:<15} → {via(dst, ranges)}")
```

```text output
split tunnel:
   10.0.21.5       → VPN tunnel
   142.250.181.14  → direct to internet
full tunnel:
   10.0.21.5       → VPN tunnel
   142.250.181.14  → VPN tunnel
```

</Step>

<Step title="Overlay networks in containers">

<Tr>
<En>

Kubernetes and Docker Swarm build one flat virtual network across many machines by tunnelling container traffic between nodes (VXLAN, WireGuard, IP-in-IP), so pods on different hosts talk as if on one LAN. CNI plugins do it: Flannel (VXLAN), Calico, Cilium (optional WireGuard encryption). It's mostly automatic, but MTU problems and blocked UDP ports (VXLAN uses 4789/UDP) are classic cluster bugs.

</En>
<Ur>

Kubernetes aur Docker Swarm nodes ke darmiyan container traffic ko tunnel kar ke (VXLAN, WireGuard, IP-in-IP) kai machines par ek chapta virtual network banate hain, taa ke alag hosts ke pods aise baat karein jaise ek LAN par hon. CNI plugins ye karte hain: Flannel (VXLAN), Calico, Cilium (ikhtiyari WireGuard encryption). Ye zyada tar khud hota hai, lekin MTU masle aur band UDP ports (VXLAN 4789/UDP istemal karta hai) mashhoor cluster bugs hain.

</Ur>
</Tr>

</Step>

<Step title="Zero-trust access instead of a network VPN">

<Tr>
<En>

Classic VPNs put a user **on the network**: one stolen VPN login or infected laptop can reach everything. Zero-trust tools grant access to **specific apps** after checking identity (SSO + MFA), device health and policy, for **every** request. Examples: Cloudflare Access, Google IAP, Tailscale (WireGuard mesh with ACLs and SSO), Teleport, AWS Verified Access.

| | Traditional VPN | Zero-trust access |
| --- | --- | --- |
| Grants | Network access (IP ranges) | Access to specific apps |
| Trust decision | Once, at connect | Every request |
| Identity | VPN account / certificate | SSO + MFA + device checks |
| Lateral movement risk | High | Low |
| Exposure | A public VPN gateway | Often no inbound ports at all |

</En>
<Ur>

Purane VPNs user ko **network par** daal dete hain: ek chori VPN login ya infected laptop har cheez tak pohanch sakta hai. Zero-trust tools pehchan (SSO + MFA), device ki sehat aur policy check kar ke **khaas apps** ki ijazat dete hain, **har** request par. Misaalen: Cloudflare Access, Google IAP, Tailscale (ACLs aur SSO wala WireGuard mesh), Teleport, AWS Verified Access.

| | Purana VPN | Zero-trust access |
| --- | --- | --- |
| Kya deta hai | Network tak pohanch (IP ranges) | Khaas apps tak pohanch |
| Bharose ka faisla | Ek dafa, connect par | Har request par |
| Pehchan | VPN account / certificate | SSO + MFA + device checks |
| Andar phailne ka khatra | Zyada | Kam |
| Bahar khulapan | Public VPN gateway | Aksar koi inbound port nahi |

</Ur>
</Tr>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="One shared VPN profile for everyone">

```text
team.ovpn  → same key for 12 people, access to the whole production VPC
```

</Bad>
<Good title="Personal identity, per-app access">

```text
SSO + MFA per person
developers → staging apps; on-call → production SSH via SSM, logged
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Unpatched VPN appliances**: among the most exploited devices on the internet.
- **Overlapping CIDRs** between home/office networks and the VPC (`192.168.1.0/24` everywhere).
- **MTU problems**: tunnels that work for small requests but hang on large ones (SSH connects, file transfer stalls).
- **Leaving SSH tunnels or port-forwards open** forever on shared machines.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bina patch VPN appliances**: internet par sab se zyada hack hone wale devices me se.
- **Ghar/office networks aur VPC ke takrate CIDRs** (har jagah `192.168.1.0/24`).
- **MTU masle**: tunnels jo chhoti requests par chalte lekin bari par atak jate hain (SSH jurta hai, file transfer ruk jata hai).
- **Mushtarka machines par SSH tunnels ya port-forwards hamesha khule chhorna.**

</Ur>
</Tr>

## Try it yourself

<Challenge title="VPN keys and AllowedIPs">

<Tr>
<En>
Make a key pair like WireGuard's, protect the private key, and see how `AllowedIPs` acts as both routing and access control: a peer can't send packets with someone else's source address. With WireGuard installed, the real commands are `wg genkey | tee priv | wg pubkey > pub`, `sudo wg-quick up wg0` and `sudo wg show`.
</En>
<Ur>
WireGuard jaisa key pair banayen, private key ko bachayen, aur dekhein ke `AllowedIPs` routing aur access control dono kaise hai: koi peer kisi aur ke source address wale packets nahi bhej sakta. WireGuard install ho to asli commands `wg genkey | tee priv | wg pubkey > pub`, `sudo wg-quick up wg0` aur `sudo wg show` hain.
</Ur>
</Tr>

```bash
# A key pair like WireGuard's — public key derived from the private key (here with OpenSSL's X25519)
openssl genpkey -algorithm x25519 -out wg-priv.pem 2>/dev/null
openssl pkey -in wg-priv.pem -pubout -outform DER 2>/dev/null | tail -c 32 | base64 > wg-pub.txt
echo "public key length: $(tr -d '\n' < wg-pub.txt | wc -c) base64 characters (same format as 'wg pubkey')"
chmod 600 wg-priv.pem && stat -c 'private key permissions: %a' wg-priv.pem

# AllowedIPs = routing + access control: which inner source addresses are accepted from a peer?
python3 - <<'EOF'
import ipaddress
allowed = {"laptop-alex": "10.100.0.7/32", "office-gw": "192.168.0.0/16"}
for peer, src in [("laptop-alex", "10.100.0.7"), ("laptop-alex", "10.100.0.9"), ("office-gw", "192.168.4.20")]:
    ok = ipaddress.ip_address(src) in ipaddress.ip_network(allowed[peer])
    print(f"packet from {peer:<11} with inner source {src:<13} → {'accept' if ok else 'DROP (spoofed source)'}")
EOF
```

```text output
public key length: 44 base64 characters (same format as 'wg pubkey')
private key permissions: 600
packet from laptop-alex with inner source 10.100.0.7    → accept
packet from laptop-alex with inner source 10.100.0.9    → DROP (spoofed source)
packet from office-gw   with inner source 192.168.4.20  → accept
```

<Hint>

<DeepDive title="Real world: one infected laptop, one shared VPN">

A 12-person startup gave every developer the same OpenVPN profile with access to the whole production VPC. When one laptop was infected, the attacker used the VPN to scan the VPC and log in to an internal admin panel with default credentials.

The new setup:

```text
1. Remove the shared VPN. Each person signs in with SSO + MFA (Tailscale/Cloudflare Access).
2. Per-application rules:
     developers  → staging apps, staging DB (read/write)
     developers  → production Grafana (read-only)
     on-call     → production SSH via SSM, time-limited and logged
3. No inbound ports on production at all: connectors make outbound connections.
4. Device posture: only company-managed laptops with disk encryption and updates.
5. Logs of every access shipped to the SIEM.
```

</DeepDive>

<DeepDive title="Security lens">

A VPN moves a user **inside** the network. Make sure "inside" still requires authentication and authorisation for everything.

- **MFA on every remote access** method, and short-lived credentials/certificates.
- **Patch VPN gateways quickly:** critical bugs in Fortinet, Pulse/Ivanti, Citrix and Palo Alto VPNs have caused major breaches.
- **Least privilege:** per-group access to specific subnets/apps, not the whole network.
- **Log and monitor** VPN logins (impossible travel, unusual hours, new devices).
- **Revoke quickly:** removing a peer's public key (WireGuard) or user (SSO) must cut access immediately.
- **Bastions and SSM** over public SSH; prefer zero-trust tools for new designs.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a remote-access VPN and a site-to-site VPN?">
A remote-access VPN connects an individual user's device to a private network, started by the user with a VPN client. A site-to-site VPN connects two networks, such as an office and a cloud VPC, through permanently running gateways, so all hosts on both sides can reach each other according to routing and firewall rules.
</QA>

<QA q="What is a tunnel and what is encapsulation?">
A tunnel carries packets of one network inside packets of another. Encapsulation wraps the original, inner packet, often with private addresses, inside a new outer packet addressed between the tunnel endpoints; the transit network only routes the outer packet, and the far endpoint removes the outer header and forwards the inner packet. VPNs also encrypt the inner packet.
</QA>

<QA q="What is split tunnelling and what are its trade-offs?">
With split tunnelling only traffic destined for the private networks is routed through the VPN, while other traffic goes directly to the internet. It saves VPN bandwidth and improves performance, but the company cannot inspect or filter the user's general internet traffic. Full tunnelling routes everything through the VPN, adding control and protection on untrusted networks at the cost of performance.
</QA>

<QA q="How would you give a developer access to a private RDS database without exposing it to the internet?">
Keep the database in a private subnet and use a controlled path: an SSH local port forward through a hardened bastion, or better, AWS Systems Manager port forwarding without any open inbound port, or a zero-trust access tool with SSO and MFA. Restrict the database security group to that path, use individual credentials and log the access.
</QA>

</DeepDive>
