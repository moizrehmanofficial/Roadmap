<BigIdea>
<Tr>
<En>
**HTTP** is a plain-text language of **requests** and **responses**. A request says **what to do** (the method: `GET`, `POST`…), **to what** (the path), with **extra details** (headers) and sometimes **data** (the body). A response comes back with a **status code** (2xx good, 4xx your mistake, 5xx server's mistake), headers and a body. **HTTPS** is the exact same thing inside an encrypted, tamper-proof connection.
</En>
<Ur>
**HTTP** **requests** aur **responses** ki saada text wali zabaan hai. Request batati hai **kya karna hai** (method: `GET`, `POST`…), **kis cheez ke saath** (path), **izafi tafseel** (headers) ke saath, aur kabhi **data** (body). Response **status code** (2xx achha, 4xx aap ki ghalti, 5xx server ki ghalti), headers aur body ke saath wapas aata hai. **HTTPS** bilkul yahi cheez hai, encrypted aur cherh chhaar se mehfooz connection ke andar.
</Ur>
</Tr>
</BigIdea>

## Learn it step by step

<Walkthrough>

<Step title="A test server for this lesson">

<Tr>
<En>Every example below talks to this small Node.js API. Start it once; we stop it at the end.</En>
<Ur>Neeche ki har misaal is chhoti Node.js API se baat karti hai. Ise ek dafa chalayen; hum aakhir me band karenge.</Ur>
</Tr>

```bash
cat > api.mjs <<'EOF'
import http from "node:http";
const products = [{ id: 1, name: "Kettle", price: 3500 }, { id: 2, name: "Iron", price: 4200 }];
http.createServer((req, res) => {
  const url = new URL(req.url, "http://localhost");
  const send = (status, data, headers = {}) => {
    res.writeHead(status, { "Content-Type": "application/json", ...headers });
    res.end(data === undefined ? "" : JSON.stringify(data));
  };
  if (url.pathname === "/api/products" && req.method === "GET") return send(200, products, { "Cache-Control": "public, max-age=60" });
  if (url.pathname === "/api/products" && req.method === "POST") {
    let body = "";
    req.on("data", (c) => (body += c));
    return req.on("end", () => {
      try {
        const p = JSON.parse(body);
        if (!p.name) return send(400, { error: "name is required" });
        send(201, { id: 3, ...p }, { Location: "/api/products/3" });
      } catch { send(400, { error: "invalid JSON" }); }
    });
  }
  if (url.pathname === "/api/me") {
    return req.headers.authorization === "Bearer secret-token" ? send(200, { user: "alex" }) : send(401, { error: "login required" });
  }
  if (url.pathname === "/old-page") return send(301, undefined, { Location: "/api/products" });
  if (url.pathname === "/boom") return send(500, { error: "something broke" });
  send(404, { error: "not found" });
}).listen(3490, "127.0.0.1");
EOF
node api.mjs > /dev/null 2>&1 &
sleep 0.5
curl -s http://127.0.0.1:3490/api/products; echo
```

```text output
[{"id":1,"name":"Kettle","price":3500},{"id":2,"name":"Iron","price":4200}]
```

</Step>

<Step title="Methods">

<Tr>
<En>

The method says what to do with the resource at the path. Clear APIs (REST) and correct caching depend on picking the right one. `GET` must **never** change data, and `PUT`/`DELETE` should be **idempotent** (doing it twice = same result).

| Method | Meaning | Body? | Safe (no changes) | Idempotent |
| --- | --- | --- | --- | --- |
| `GET` | Read | No | Yes | Yes |
| `POST` | Create / perform an action | Yes | No | No |
| `PUT` | Replace completely | Yes | No | Yes |
| `PATCH` | Change part | Yes | No | Not necessarily |
| `DELETE` | Remove | Usually no | No | Yes |
| `HEAD` | Like GET, headers only | No | Yes | Yes |
| `OPTIONS` | Which methods are allowed (CORS preflight) | No | Yes | Yes |

</En>
<Ur>

Method batata hai ke path wali cheez ke saath kya karna hai. Saaf APIs (REST) aur sahi caching sahi method chunne par munhasir hai. `GET` ko data **kabhi** nahi badalna chahiye, aur `PUT`/`DELETE` **idempotent** hone chahiye (do dafa karna = wahi nateeja).

| Method | Matlab | Body? | Mehfooz (koi tabdeeli nahi) | Idempotent |
| --- | --- | --- | --- | --- |
| `GET` | Parhna | Nahi | Haan | Haan |
| `POST` | Banana / koi kaam karna | Haan | Nahi | Nahi |
| `PUT` | Poora badalna | Haan | Nahi | Haan |
| `PATCH` | Hissa badalna | Haan | Nahi | Zaroori nahi |
| `DELETE` | Hatana | Aam tor par nahi | Nahi | Haan |
| `HEAD` | GET jaisa, sirf headers | Nahi | Haan | Haan |
| `OPTIONS` | Kaunse methods jaiz (CORS preflight) | Nahi | Haan | Haan |

</Ur>
</Tr>

```bash
curl -s -X POST http://127.0.0.1:3490/api/products -H 'Content-Type: application/json' -d '{"name":"Fan","price":8000}'; echo
curl -s -o /dev/null -w 'POST without name → %{http_code}\n' -X POST http://127.0.0.1:3490/api/products -H 'Content-Type: application/json' -d '{"price":1}'
curl -s -o /dev/null -w 'POST with broken JSON → %{http_code}\n' -X POST http://127.0.0.1:3490/api/products -d '{oops'
```

```text output
{"id":3,"name":"Fan","price":8000}
POST without name → 400
POST with broken JSON → 400
```

</Step>

<Step title="Status codes">

<Tr>
<En>

A three-digit summary of the result; the first digit is the class. Clients, monitoring and caches react to it automatically. Return the **most accurate** code from your API, not `200` with `{"error": …}` inside.

| Code | Meaning | Typical cause |
| --- | --- | --- |
| **200** OK | Success | |
| **201** Created | New resource created | POST |
| **204** No Content | Success, nothing to return | DELETE |
| **301 / 308** | Moved permanently | Old URL, http → https |
| **302 / 307** | Temporary redirect | After login |
| **304** Not Modified | Use your cached copy | ETag / If-None-Match |
| **400** Bad Request | Invalid input | Validation failed |
| **401** Unauthorized | Not logged in / bad token | Missing or expired token |
| **403** Forbidden | Logged in, but not allowed | Wrong role |
| **404** Not Found | No such resource | Wrong path or ID |
| **409** Conflict | Clashes with current state | Duplicate email |
| **422** Unprocessable | Valid format, invalid meaning | Some APIs use it for validation |
| **429** Too Many Requests | Rate limited | Too many calls |
| **500** Internal Server Error | Unhandled exception | Bug |
| **502** Bad Gateway | Proxy got no/invalid answer from the app | App crashed / wrong port |
| **503** Service Unavailable | Overloaded or maintenance | |
| **504** Gateway Timeout | App too slow for the proxy | Slow query |

</En>
<Ur>

Nateeje ka teen hindson ka khulasa; pehla hindsa qism batata hai. Clients, monitoring aur caches is par khud react karte hain. Apni API se **sab se durust** code lautayen, andar `{"error": …}` ke saath `200` nahi.

| Code | Matlab | Aam wajah |
| --- | --- | --- |
| **200** OK | Kamyabi | |
| **201** Created | Nayi cheez bani | POST |
| **204** No Content | Kamyabi, lautane ko kuch nahi | DELETE |
| **301 / 308** | Hamesha ke liye muntaqil | Purana URL, http → https |
| **302 / 307** | Waqti redirect | Login ke baad |
| **304** Not Modified | Apni cached copy istemal karo | ETag / If-None-Match |
| **400** Bad Request | Ghalat input | Validation fail |
| **401** Unauthorized | Login nahi / ghalat token | Token ghayab ya expire |
| **403** Forbidden | Login hai, lekin ijazat nahi | Ghalat role |
| **404** Not Found | Aisi koi cheez nahi | Ghalat path ya ID |
| **409** Conflict | Mojooda haalat se takraao | Duplicate email |
| **422** Unprocessable | Format sahi, maani ghalat | Kuch APIs validation ke liye |
| **429** Too Many Requests | Had se zyada | Bohot zyada calls |
| **500** Internal Server Error | Na-sambhala exception | Bug |
| **502** Bad Gateway | Proxy ko app se jawab nahi/ghalat mila | App crash / ghalat port |
| **503** Service Unavailable | Bojh ya maintenance | |
| **504** Gateway Timeout | App proxy ke liye bohot dheemi | Dheemi query |

</Ur>
</Tr>

<Step title="Headers">

<Tr>
<En>

`Name: value` lines of extra information. Login, content type, caching, compression, cookies, security policies and CORS all live in headers. Names aren't case-sensitive, and custom ones are fine (`X-Request-Id`).

| Header | Direction | Purpose |
| --- | --- | --- |
| `Host` | Request | Which site (many sites share one IP) |
| `Authorization` | Request | Credentials, e.g. `Bearer <token>` |
| `Content-Type` | Both | Format of the body (`application/json`) |
| `Accept` | Request | Formats the client wants |
| `Cookie` / `Set-Cookie` | Request / Response | Send / store cookies |
| `Cache-Control` | Response | How long it may be cached |
| `Location` | Response | Redirect target / new resource URL |
| `User-Agent` | Request | Client software |
| `X-Forwarded-For` | Request (via proxy) | Original client IP |

</En>
<Ur>

Izafi maloomat ki `Name: value` lines. Login, content type, caching, compression, cookies, security policies aur CORS sab headers me rehte hain. Naam chhote bare huroof ki parwah nahi karte, aur apne bhi chalte hain (`X-Request-Id`).

| Header | Simt | Maqsad |
| --- | --- | --- |
| `Host` | Request | Kaunsi site (kai sites ek IP share karti hain) |
| `Authorization` | Request | Credentials, maslan `Bearer <token>` |
| `Content-Type` | Dono | Body ka format (`application/json`) |
| `Accept` | Request | Client ko kaunse formats chahiye |
| `Cookie` / `Set-Cookie` | Request / Response | Cookies bhejna / rakhna |
| `Cache-Control` | Response | Kitni der cache ho sakta hai |
| `Location` | Response | Redirect ki manzil / nayi cheez ka URL |
| `User-Agent` | Request | Client ka software |
| `X-Forwarded-For` | Request (proxy ke zariye) | Asal client ka IP |

</Ur>
</Tr>

```bash
curl -s -w '  → %{http_code}\n' http://127.0.0.1:3490/api/me
curl -s -w '  → %{http_code}\n' -H 'Authorization: Bearer secret-token' http://127.0.0.1:3490/api/me
```

```text output
{"error":"login required"}  → 401
{"user":"alex"}  → 200
```

</Step>

<Step title="Bodies and content types">

<Tr>
<En>

The body carries the data; `Content-Type` tells the server how to read it. Express and NestJS body parsers look at this header, so a wrong one gives you an empty `req.body`.

| Content-Type | Looks like | Used for |
| --- | --- | --- |
| `application/json` | `{"name":"Fan"}` | APIs |
| `application/x-www-form-urlencoded` | `name=Fan&price=8000` | Classic HTML forms |
| `multipart/form-data` | parts with boundaries | File uploads |
| `text/html; charset=utf-8` | `<html>…` | Web pages |
| `application/octet-stream` | raw bytes | Downloads |

</En>
<Ur>

Body data le jati hai; `Content-Type` server ko batata hai use kaise parhna hai. Express aur NestJS ke body parsers yahi header dekhte hain, isliye ghalat header khaali `req.body` deta hai.

| Content-Type | Shakal | Istemal |
| --- | --- | --- |
| `application/json` | `{"name":"Fan"}` | APIs |
| `application/x-www-form-urlencoded` | `name=Fan&price=8000` | Purane HTML forms |
| `multipart/form-data` | boundaries wale hisse | File uploads |
| `text/html; charset=utf-8` | `<html>…` | Web pages |
| `application/octet-stream` | kachche bytes | Downloads |

</Ur>
</Tr>

</Step>

<Step title="Statelessness, cookies and sessions">

<Tr>
<En>

HTTP forgets every request. **Cookies** fix that: the server stores a small value in the browser, and the browser sends it back automatically with every request to that site. That's how "logged in" works. Secure flags matter:

- `HttpOnly`: JavaScript can't read it (limits XSS damage).
- `Secure`: sent over HTTPS only.
- `SameSite=Lax/Strict`: limits CSRF.

APIs often use an `Authorization: Bearer` token instead.

</En>
<Ur>

HTTP har request bhool jata hai. **Cookies** ye theek karti hain: server browser me ek chhoti value rakhta hai, aur browser us site ki har request ke saath ise khud wapas bhejta hai. "Logged in" isi tarah kaam karta hai. Hifazati flags ahem hain:

- `HttpOnly`: JavaScript ise nahi parh sakti (XSS ka nuqsan kam).
- `Secure`: sirf HTTPS par bheji jati hai.
- `SameSite=Lax/Strict`: CSRF ko mehdood karta hai.

APIs aksar is ki jagah `Authorization: Bearer` token istemal karti hain.

</Ur>
</Tr>

```text
After login:
< Set-Cookie: session=7f3a9c…; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400

Every later request from that browser:
> Cookie: session=7f3a9c…
```

```bash
cat > cookie.mjs <<'EOF'
import http from "node:http";
http.createServer((req, res) => {
  if (req.url === "/login") { res.writeHead(200, { "Set-Cookie": "session=abc123; HttpOnly; SameSite=Lax; Path=/" }); return res.end("logged in\n"); }
  const loggedIn = (req.headers.cookie || "").includes("session=abc123");
  res.end(loggedIn ? "welcome back (cookie received)\n" : "who are you? (no cookie)\n");
}).listen(3491, "127.0.0.1");
EOF
node cookie.mjs & c=$!; sleep 0.5
curl -s http://127.0.0.1:3491/profile
curl -s -c jar.txt http://127.0.0.1:3491/login
curl -s -b jar.txt http://127.0.0.1:3491/profile
kill $c
```

```text output
who are you? (no cookie)
logged in
welcome back (cookie received)
```

<Happened>
<Tr>
<En>`-c jar.txt` saved the cookie like a browser does; `-b jar.txt` sent it back, so the server recognised us.</En>
<Ur>`-c jar.txt` ne browser ki tarah cookie rakhi; `-b jar.txt` ne use wapas bheja, isliye server ne hamein pehchana.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Caching">

<Tr>
<En>

Storing responses so they can be reused without asking the server again, in the browser, a CDN or a proxy. Faster pages, less load, lower bills.

| Cache-Control | Meaning |
| --- | --- |
| `public, max-age=60` | Anyone (browser, CDN) may cache for 60 s |
| `private, max-age=60` | Only the user's browser may cache |
| `no-cache` | Store, but check with the server before each use (ETag) |
| `no-store` | Never store (sensitive data) |
| `immutable` | Will never change; don't even recheck |

Hashed static files: `public, max-age=31536000, immutable`. HTML/API: short or `no-cache`. Private data: `private` or `no-store`.

</En>
<Ur>

| Cache-Control | Matlab |
| --- | --- |
| `public, max-age=60` | Koi bhi (browser, CDN) 60 s cache kar sakta hai |

| `no-cache` | Rakho, lekin har istemal se pehle server se check (ETag) |
| `no-store` | Kabhi na rakho (hassas data) |

Hash wali static files: `public, max-age=31536000, immutable`. HTML/API: chhota ya `no-cache`. Private data: `private` ya `no-store`.

<Step title="CORS">

<Tr>
<En>

**Cross-Origin Resource Sharing** is a set of **browser** rules: JavaScript on one origin (`https://app.example.com`) can't read responses from another origin (`https://api.example.com`) unless the API allows it in its response headers. It protects users: a bad site can't use your logged-in browser to read your bank's API. `curl` and servers ignore CORS completely. Allow **specific** origins; never reflect any origin together with credentials.

</En>
<Ur>

**Cross-Origin Resource Sharing** **browser** ke usool hain: ek origin (`https://app.example.com`) ki JavaScript doosre origin (`https://api.example.com`) ke responses nahi parh sakti jab tak API apne response headers me ijazat na de. Ye users ki hifazat karta hai: buri site aap ke logged-in browser se aap ke bank ki API nahi parh sakti. `curl` aur servers CORS ko bilkul nahi dekhte. **Khaas** origins ki ijazat dein; credentials ke saath kabhi har origin wapas na lautayen.

</Ur>
</Tr>

```text

API response must include:
  Access-Control-Allow-Origin: https://app.example.com      ← exact origin, not *
  Access-Control-Allow-Credentials: true

Otherwise DevTools shows:
  "blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present"
```

<Step title="HTTPS: HTTP inside TLS">

<Tr>
<En>

Without HTTPS, anyone on the path (Wi-Fi, ISP, a hacked router) can read and change everything: passwords, cookies, pages. HTTPS sends HTTP through a **TLS**-encrypted connection (port **443**) and gives you **privacy**, **integrity** and **proof of the server** (the certificate shows you reached the real `shop.example.com`). Use it **always**, even internally. Free certificates come from Let's Encrypt, or are managed by Vercel, Cloudflare or AWS ACM. Redirect HTTP → HTTPS and add **HSTS**. Details in **TLS and Certificates**.

</En>
<Ur>

HTTPS ke baghair raaste me koi bhi (Wi-Fi, ISP, hack shuda router) sab kuch parh aur badal sakta hai: passwords, cookies, pages. HTTPS HTTP ko **TLS**-encrypted connection (port **443**) se bhejta hai aur aap ko **raazdari**, **sahi salamat data** aur **server ka saboot** deta hai (certificate dikhata hai ke aap asli `shop.example.com` tak pohanche). Ise **hamesha** istemal karein, andar bhi. Muft certificates Let's Encrypt se milte hain, ya Vercel, Cloudflare ya AWS ACM sambhalte hain. HTTP → HTTPS redirect karein aur **HSTS** lagayen. ## Common mistakes

<Compare>
<Bad title="200 with an error inside">

```text
HTTP/1.1 200 OK
{"error": "user not found"}       # monitoring thinks everything is fine
```

</Bad>
<Good title="The right status code">

```text
HTTP/1.1 404 Not Found
{"error": "user not found"}
```

</Good>
</Compare>

<Compare>
<Bad title="GET that changes data">

```text
GET /api/orders/58/delete         # crawlers and link previews will trigger it
```

</Bad>
<Good title="The right method">

```text
DELETE /api/orders/58
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Wrong `Content-Type`**: the server can't parse the body (empty `req.body`).
- **Confusing 401 and 403**: 401 = not logged in, 403 = logged in but not allowed.
- **`Access-Control-Allow-Origin: *` with credentials**: browsers reject it, and reflecting any origin is a vulnerability.
- **Caching private data publicly**: one user's page served to others from a CDN.
- **Mixed content**: an HTTPS page loading HTTP scripts or APIs (browsers block it).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ghalat `Content-Type`**: server body parh nahi sakta (khaali `req.body`).
- **401 aur 403 me ulajhna**: 401 = login nahi, 403 = login hai lekin ijazat nahi.
- **Credentials ke saath `Access-Control-Allow-Origin: *`**: browsers inkaar karte hain, aur har origin lautana kamzori hai.
- **Private data ko public cache karna**: ek user ka page CDN se doosron ko.
- **Mixed content**: HTTPS page ka HTTP scripts ya APIs load karna (browsers rok dete hain).

</Ur>
</Tr>

<Tr>

```bash
cat > mini.mjs <<'EOF'
import http from "node:http";
const notes = [];
http.createServer((req, res) => {
  if (req.method === "POST" && req.url === "/notes") {
    let b = ""; req.on("data", (c) => (b += c));
    return req.on("end", () => { notes.push(JSON.parse(b).text); res.writeHead(201, { "Content-Type": "application/json" }); res.end(JSON.stringify({ id: notes.length })); });
  }
  if (req.method === "GET" && req.url === "/notes") { res.writeHead(200, { "Content-Type": "application/json" }); return res.end(JSON.stringify(notes)); }
  if (req.method === "DELETE" && req.url === "/notes") { notes.length = 0; res.writeHead(204); return res.end(); }
  res.writeHead(405, { Allow: "GET, POST, DELETE" }); res.end();
}).listen(3492, "127.0.0.1");
EOF
```

<DeepDive title="Real world: 'Network Error' only in the browser">

A React app on `https://app.example.com` shows "Network Error" when calling `https://api.example.com/orders`. DevTools → Network:

```text
OPTIONS /orders   (preflight)   204   ← API answers, but…
  Response headers: (no Access-Control-Allow-Origin)
Console: blocked by CORS policy
```

Meanwhile `curl https://api.example.com/orders -H "Authorization: Bearer …"` works fine, because **curl ignores CORS**. The API had CORS enabled only for `http://localhost:3000` from development. Fix in NestJS:

```text
app.enableCors({
  origin: ["https://app.example.com"],      // exact production origin
  credentials: true,
  methods: ["GET", "POST", "PATCH", "DELETE"],
});
```

Lesson: when the browser fails but curl works, think **CORS**, cookies (`SameSite`), or mixed content (HTTPS page calling an HTTP API).

</DeepDive>

<DeepDive title="Security lens">

HTTP is where most web attacks happen. Never trust anything in a request: method, path, headers, cookies or body can all be forged with one curl command.

- **Validate every input on the server**; client-side checks are only for convenience.
- **Cookies:** `HttpOnly; Secure; SameSite=Lax` (or `Strict`) for session cookies.
- **Security headers:** `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `frame-ancestors` (clickjacking).
- **Don't put secrets in URLs** (query strings land in logs, history and `Referer` headers).
- **Rate limiting (429)** on login and expensive endpoints against brute force and abuse.
- **Error responses must not leak stack traces** or internal details in production.
- **HTTPS everywhere**, including internal APIs, with HSTS on public sites.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between GET, POST, PUT and PATCH?">
GET retrieves a resource and must not change server state. POST creates a resource or triggers an action and is not idempotent. PUT replaces a resource completely and is idempotent, so repeating it gives the same result. PATCH applies a partial update to a resource.
</QA>

<QA q="What is the difference between 401 and 403?">
401 Unauthorized means the request lacks valid authentication, for example no token or an expired one, and the client should authenticate. 403 Forbidden means the client is authenticated but does not have permission for the resource, so authenticating again will not help.
</QA>

<QA q="What do 502 and 504 errors usually indicate?">
They come from a gateway or proxy in front of the application. 502 Bad Gateway means the proxy got no valid response from the upstream application, for example because it crashed or is listening on a different port. 504 Gateway Timeout means the upstream application took too long to respond.
</QA>

<QA q="What is CORS and why does it exist?">
CORS is a browser mechanism that blocks JavaScript from reading responses from a different origin unless the server allows it with Access-Control-Allow-Origin and related headers. It protects users from malicious sites using their logged-in browser to read data from other sites. Servers and tools like curl are not restricted by it.
</QA>

<QA q="How do cookies make a stateless protocol stateful, and how should session cookies be secured?">
The server sends a Set-Cookie header, the browser stores the cookie and sends it back with every subsequent request to that site, so the server can recognise the session. Session cookies should be HttpOnly so scripts cannot read them, Secure so they are sent only over HTTPS, and SameSite=Lax or Strict to limit cross-site request forgery, with sensible expiry.
</QA>

</DeepDive>
