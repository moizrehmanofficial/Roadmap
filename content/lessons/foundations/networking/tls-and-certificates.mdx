<BigIdea>
<Tr>
<En>
**TLS** (the successor of SSL) wraps a connection in encryption so nobody in between can **read** it, **change** it unnoticed, or **pretend** to be the server. The server proves who it is with a **certificate**: its public key and domain name, **signed** by a **Certificate Authority (CA)** that browsers trust. Use TLS 1.2+ (ideally 1.3), get free certificates from **Let's Encrypt**, and let them renew automatically.
</En>
<Ur>
**TLS** (SSL ka jaanasheen) connection ko encryption me lapet deta hai taa ke beech me koi use **parh** na sake, chupke se **badal** na sake, ya server **ban kar** dhoka na de sake. Server **certificate** se saabit karta hai ke wo kaun hai: us ki public key aur domain ka naam, jis par browsers ke bharose wali **Certificate Authority (CA)** ke **dastakhat** hote hain. TLS 1.2+ (behtar 1.3) istemal karein, **Let's Encrypt** se muft certificates lein, aur unhe khud renew hone dein.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

When you log in over public Wi-Fi, your data passes through routers you don't control. Three things could go wrong:

1. Someone **reads** your password (no confidentiality).
2. Someone **changes** the page or the account number in a transfer (no integrity).
3. You're talking to a **fake** site that looks real (no authentication).

TLS solves all three. The handshake:

```text
Client                                                 Server (shop.example.com)
  │ ClientHello: TLS 1.3, ciphers, key share, SNI=shop…  │
  │─────────────────────────────────────────────────────►│
  │ ServerHello + key share, Certificate (chain),        │
  │ CertificateVerify (signed with private key), Finished│
  │◄─────────────────────────────────────────────────────│
  │ client checks: chain → trusted root? name matches?   │
  │ not expired? signature valid?                        │
  │ Finished                                             │
  │─────────────────────────────────────────────────────►│
  │  ═════ encrypted HTTP with shared symmetric keys ═════│
```

TLS 1.3 needs **one round trip** for the handshake (TLS 1.2 needed two).

</En>
<Ur>

Public Wi-Fi par login karte waqt aap ka data un routers se guzarta hai jo aap ke qaboo me nahi. Teen cheezen ghalat ho sakti hain:

1. Koi aap ka password **parh** le (raazdari nahi).
2. Koi page ya transfer me account number **badal** de (sahi salamati nahi).
3. Aap asli jaisi dikhne wali **naqli** site se baat kar rahe hon (pehchan nahi).

TLS teeno hal karta hai. Handshake:

```text
Client                                                 Server (shop.example.com)
  │ ClientHello: TLS 1.3, ciphers, key share, SNI=shop…  │
  │─────────────────────────────────────────────────────►│
  │ ServerHello + key share, Certificate (chain),        │
  │ CertificateVerify (signed with private key), Finished│
  │◄─────────────────────────────────────────────────────│
  │ client checks: chain → trusted root? name matches?   │
  │ not expired? signature valid?                        │
  │ Finished                                             │
  │─────────────────────────────────────────────────────►│
  │  ═════ encrypted HTTP with shared symmetric keys ═════│
```

TLS 1.3 handshake ke liye **ek round trip** leta hai (TLS 1.2 ko do chahiye the).

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Every site and API must use HTTPS:** browsers warn on HTTP, and HTTP/2 and secure cookies need it.
- **Expired or wrong certificates** cause real outages: sites down, mobile apps failing, APIs rejecting calls.
- **Internal traffic** (service to service, app to database) should be encrypted too: zero-trust networking.
- **Security careers:** TLS settings, certificate management (PKI) and mTLS are core DevSecOps and cloud security topics.

</En>
<Ur>

- **Har site aur API ko HTTPS chahiye:** browsers HTTP par warning dete hain, aur HTTP/2 aur secure cookies ko ye chahiye.
- **Expire ya ghalat certificates** asli outages laate hain: sites band, mobile apps fail, APIs calls radd karti hain.
- **Andaroni traffic** (service se service, app se database) bhi encrypted hona chahiye: zero-trust networking.
- **Security career:** TLS settings, certificate management (PKI) aur mTLS DevSecOps aur cloud security ke bunyadi mauzoo hain.

</Ur>

## Picture it

<Tr>
<En>

**A sealed envelope plus an ID card.** Encryption is the **sealed, tamper-evident envelope**: nobody can read the letter, and if someone opens it, you notice. But how do you know the person you hand it to is really the bank? They show an **ID card** (the certificate) issued by the **government** (the Certificate Authority). You trust the ID because you trust the government that issued it: that's the **chain of trust**.

</En>
<Ur>

**Band lifafa aur shanakhti card.** Encryption **band, cherh chhaar dikhane wala lifafa** hai: koi khat nahi parh sakta, aur koi khole to pata chal jata hai. Lekin kaise pata chale ke jise lifafa de rahe hain wo waqai bank hai? Wo **shanakhti card** (certificate) dikhate hain jo **hukumat** (Certificate Authority) ne jaari kiya. Aap card par bharosa karte hain kyun ke jaari karne wali hukumat par bharosa hai: yahi **chain of trust** hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Symmetric and asymmetric encryption">

<Tr>
<En>

- **Symmetric:** one key locks and unlocks. Fast.
- **Asymmetric:** a public key anyone may have and a private key only the owner has; what one does, only the other can undo. Slow.

TLS uses asymmetric crypto to **agree on a secret and prove identity** without ever sending the secret, then switches to symmetric crypto to encrypt the data quickly (key exchange: ECDHE; signatures: RSA/ECDSA; data: AES-GCM or ChaCha20-Poly1305). You don't implement any of this, but you choose key types, versions and where private keys live.

</En>
<Ur>

- **Symmetric:** ek key band bhi karti hai aur kholti bhi. Tez.
- **Asymmetric:** public key jo kisi ke paas bhi ho sakti hai aur private key jo sirf malik ke paas; jo ek kare, sirf doosri ulat sakti hai. Dheemi.

TLS asymmetric crypto se **raaz par mutafiq hota aur pehchan saabit karta** hai bina raaz bheje, phir data jaldi encrypt karne ke liye symmetric par chala jata hai (key exchange: ECDHE; dastakhat: RSA/ECDSA; data: AES-GCM ya ChaCha20-Poly1305). Ye sab aap khud nahi banate, lekin key ki qism, versions aur private keys ki jagah aap chunte hain.

</Ur>
</Tr>

```bash
echo -n "secret order #58" > msg.txt
openssl rand -hex 32 > sym.key
openssl enc -aes-256-cbc -pbkdf2 -pass file:sym.key -in msg.txt -out msg.enc
echo "encrypted bytes look like: $(head -c 12 msg.enc | od -An -tx1 | tr -d ' \n')…" | sed -E 's/: [0-9a-f]+…/: <random-looking bytes>…/'
openssl enc -d -aes-256-cbc -pbkdf2 -pass file:sym.key -in msg.enc
echo
openssl genpkey -algorithm ed25519 -out priv.pem 2>/dev/null
openssl pkey -in priv.pem -pubout -out pub.pem
openssl pkeyutl -sign -inkey priv.pem -rawin -in msg.txt -out msg.sig
openssl pkeyutl -verify -pubin -inkey pub.pem -rawin -in msg.txt -sigfile msg.sig
echo -n "secret order #59" > tampered.txt
openssl pkeyutl -verify -pubin -inkey pub.pem -rawin -in tampered.txt -sigfile msg.sig > /dev/null 2>&1 || echo "Signature check FAILED for the changed message"
```

```text output
encrypted bytes look like: <random-looking bytes>…
secret order #58
Signature Verified Successfully
Signature check FAILED for the changed message
```

<Happened>
<Tr>
<En>First part: **symmetric**, the same key encrypted and decrypted. Second part: an **asymmetric signature**, signed with the private key and checked with the public key; changing one character broke it. Certificates and the TLS handshake rely on exactly this.</En>
<Ur>Pehla hissa: **symmetric**, ek hi key ne encrypt aur decrypt kiya. Doosra hissa: **asymmetric dastakhat**, private key se sign aur public key se check; ek harf badalne se toot gaya. Certificates aur TLS handshake bilkul isi par chalte hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="What's inside a certificate">

<Tr>
<En>

An X.509 certificate holds: **subject** (who), **Subject Alternative Names** (the domains it's valid for), the **public key**, the **issuer** (which CA signed it), **validity dates**, and the CA's **signature**. The client checks all of them. Let's build a realistic setup: our own root CA, and a server certificate it signs.

</En>
<Ur>

X.509 certificate me hota hai: **subject** (kaun), **Subject Alternative Names** (kin domains ke liye jaiz), **public key**, **issuer** (kis CA ne sign kiya), **muddat ki tareekhen**, aur CA ke **dastakhat**. Client in sab ko check karta hai. Chaliye ek asli jaisa setup banayen: apni root CA, aur us ka sign kiya hua server certificate.

</Ur>
</Tr>

```bash
# A private Certificate Authority (in real life: Let's Encrypt or your company's CA)
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 3650 \
  -subj "/CN=DevGuide Demo Root CA" -keyout ca.key -out ca.pem 2>/dev/null

# The server's own key + a certificate request, then the CA signs it
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -subj "/CN=shop.test" -keyout server.key -out server.csr 2>/dev/null
printf 'subjectAltName=DNS:shop.test,DNS:www.shop.test,IP:127.0.0.1\nextendedKeyUsage=serverAuth\n' > ext.cnf
openssl x509 -req -in server.csr -CA ca.pem -CAkey ca.key -CAcreateserial -days 90 \
  -extfile ext.cnf -out server.pem 2>/dev/null

openssl x509 -in server.pem -noout -subject -issuer -ext subjectAltName | sed 's/^ *//'
openssl x509 -in server.pem -noout -checkend $((89*86400)) > /dev/null && echo "valid for at least 89 more days"
```

```text output
subject=CN = shop.test
issuer=CN = DevGuide Demo Root CA
X509v3 Subject Alternative Name: 
DNS:shop.test, DNS:www.shop.test, IP Address:127.0.0.1
valid for at least 89 more days
```

<Tr>
<En>

| Field | Meaning |
| --- | --- |
| Subject / CN | Name of the owner (legacy for domains) |
| **SAN** | The domains/IPs it's valid for: **this is what browsers check** |
| Issuer | The CA that signed it |
| Not Before / Not After | Validity period (public certs: at most ~398 days; Let's Encrypt: 90) |
| Public key | The server's public key |
| Signature | The CA's signature over all of the above |

</En>
<Ur>

| Field | Matlab |
| --- | --- |
| Subject / CN | Malik ka naam (domains ke liye purana tareeqa) |
| **SAN** | Jin domains/IPs ke liye jaiz: **browsers yahi check karte hain** |
| Issuer | Sign karne wali CA |
| Not Before / Not After | Muddat (public certs: zyada se zyada ~398 din; Let's Encrypt: 90) |
| Public key | Server ki public key |
| Signature | Upar ki har cheez par CA ke dastakhat |

</Ur>
</Tr>

<Step title="The chain of trust">

<Tr>
<En>

Nobody can check every website personally, so your OS and browser ship a list of trusted **root CAs** (the **trust store**). Roots sign **intermediate** CAs, which sign server certificates. A certificate is trusted if it chains up to a trusted root. Servers must send their certificate **plus intermediates** (the "full chain"): a missing intermediate is a classic error that works in some browsers but fails in curl and mobile apps.

</En>
<Ur>

Koi har website ko khud check nahi kar sakta, isliye aap ka OS aur browser bharose wali **root CAs** ki list saath laate hain (**trust store**). Roots **intermediate** CAs ko sign karti hain, jo server certificates sign karti hain. Certificate tab bharosemand hai jab wo ooper bharose wali root tak jure. Servers ko apna certificate **aur intermediates** ("full chain") bhejne chahiye: ghayab intermediate mashhoor ghalti hai jo kuch browsers me chalti hai lekin curl aur mobile apps me fail hoti hai.

</Ur>
</Tr>

```bash
openssl verify -CAfile ca.pem server.pem
openssl verify server.pem 2>&1 | grep -o 'unable to get local issuer certificate'
```

```text output
server.pem: OK
unable to get local issuer certificate
```

<Happened>
<Tr>
<En>With our CA it verified. Against the system trust store, which doesn't know our demo CA, it failed: exactly what a browser shows as "certificate not trusted".</En>
<Ur>Hamari CA ke saath ye verify hua. System trust store ke khilaf, jo hamari demo CA nahi jaanta, fail hua: bilkul wahi jo browser "certificate not trusted" ki shakal me dikhata hai.</Ur>
</Tr>
</Happened>

```text
Root CA  (self-signed, in your trust store)          e.g. ISRG Root X1
   └── Intermediate CA  (signed by the root)         e.g. Let's Encrypt R11
          └── Server certificate (signed by the intermediate)   shop.example.com
```

</Step>

<Step title="A real HTTPS server and client">

<Tr>
<En>

Serve HTTPS with the certificate and private key, then connect with a client that checks it. The client must trust the issuing CA **and** the hostname must match a SAN. In nginx that's `ssl_certificate` (full chain) and `ssl_certificate_key`; in Node.js, `https.createServer({ key, cert })`.

</En>
<Ur>

Certificate aur private key se HTTPS chalayen, phir aise client se jurein jo ise check kare. Client ko jaari karne wali CA par bharosa **aur** hostname ka SAN se milna zaroori hai. nginx me ye `ssl_certificate` (full chain) aur `ssl_certificate_key` hai; Node.js me `https.createServer({ key, cert })`.

</Ur>
</Tr>

```bash
cat > https.mjs <<'EOF'
import https from "node:https";
import fs from "node:fs";
https.createServer({ key: fs.readFileSync("server.key"), cert: fs.readFileSync("server.pem") },
  (req, res) => res.end("hello over TLS\n")).listen(3493, "127.0.0.1");
EOF
node https.mjs & srv=$!; sleep 0.5

echo "1) trusting our CA, correct name:"
curl -s --cacert ca.pem --resolve shop.test:3493:127.0.0.1 https://shop.test:3493/
echo "2) not trusting the CA:"
curl -s https://127.0.0.1:3493/ -o /dev/null -w '%{http_code}\n' 2>&1; echo "   curl exit code: $(curl -s https://127.0.0.1:3493/ > /dev/null 2>&1; echo $?) (60 = certificate problem)"
echo "3) trusted CA, but a name the certificate does not cover:"
curl -s --cacert ca.pem --resolve evil.test:3493:127.0.0.1 https://evil.test:3493/ > /dev/null 2>&1; echo "   curl exit code: $? (60 = certificate problem)"
echo "4) TLS version negotiated:"
echo | openssl s_client -connect 127.0.0.1:3493 -servername shop.test -CAfile ca.pem 2>/dev/null | grep -oE 'TLSv1\.[0-9]' | head -1
kill $srv
```

```text output
1) trusting our CA, correct name:
hello over TLS
2) not trusting the CA:
000
   curl exit code: 60 (60 = certificate problem)
3) trusted CA, but a name the certificate does not cover:
   curl exit code: 60 (60 = certificate problem)
4) TLS version negotiated:
TLSv1.3
```

<Happened>
<Tr>
<En>`--resolve shop.test:3493:127.0.0.1` made curl use our IP for that name, like a hosts entry, so the **name** check could be tested. Case 2 was an untrusted issuer; case 3 a name mismatch. Both were refused: that's TLS protecting you from impostors.</En>
<Ur>`--resolve shop.test:3493:127.0.0.1` ne curl ko us naam ke liye hamara IP istemal karwaya, hosts entry ki tarah, taa ke **naam** ka check test ho sake. Case 2 be-bharosa jaari karne wala tha; case 3 naam ka mel na hona. Dono radd hue: yahi TLS ka aap ko dhokebazon se bachana hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Let's Encrypt and automatic renewal">

<Tr>
<En>

A free, automated public CA. You prove you control the domain (HTTP-01 challenge on port 80, or DNS-01 with a TXT record), and it issues a 90-day certificate. Short lifetimes force **automation**, which removes the most common outage: someone forgetting to renew. Use `certbot` (nginx/Apache), Caddy (automatic HTTPS built in), or cert-manager (Kubernetes). Vercel, Cloudflare and AWS ACM do all of it for you.

</En>
<Ur>

Muft, khud kaar public CA. Aap saabit karte hain ke domain aap ke qaboo me hai (port 80 par HTTP-01 challenge, ya TXT record ke saath DNS-01), aur ye 90 din ka certificate jaari karti hai. Chhoti muddat **automation** par majboor karti hai, jo sab se aam outage khatam karti hai: kisi ka renew karna bhool jana. `certbot` (nginx/Apache), Caddy (khud kaar HTTPS shamil), ya cert-manager (Kubernetes) istemal karein. Vercel, Cloudflare aur AWS ACM ye sab aap ke liye karte hain.

</Ur>
</Tr>

```text
$ sudo certbot --nginx -d shop.example.com -d www.shop.example.com

Certificate is saved at: /etc/letsencrypt/live/shop.example.com/fullchain.pem

Certbot has set up a scheduled task to automatically renew this certificate in the background.

```

<En>Test renewal anytime with `sudo certbot renew --dry-run`.</En>
<Ur>Renewal kabhi bhi `sudo certbot renew --dry-run` se test karein.</Ur>

<Step title="Check certificates and expiry">

<Tr>
<En>

Expired certificates take sites, APIs and mobile apps down instantly, so watching expiry is a basic ops task. For a remote server: `echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -dates -issuer -ext subjectAltName`. Most uptime monitors check expiry too.

</En>
<Ur>

Expire certificates sites, APIs aur mobile apps ko foran gira dete hain, isliye muddat par nazar rakhna bunyadi ops kaam hai. Door ke server ke liye: `echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -dates -issuer -ext subjectAltName`. Zyada tar uptime monitors bhi muddat check karte hain.

</Ur>
</Tr>

```bash
days_left() { local end; end=$(openssl x509 -in "$1" -noout -enddate | cut -d= -f2); echo $(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 )); }
d=$(days_left server.pem)
if (( d < 14 )); then echo "RENEW NOW: $d days left"; else echo "OK: expires in about $(( d / 10 * 10 ))+ days"; fi
```

```text output
OK: expires in about 80+ days
```

<Step title="Common certificate errors">

<Tr>
<En>

| Error (browser / curl) | Meaning | Usual fix |
| --- | --- | --- |
| `NET::ERR_CERT_DATE_INVALID` / "certificate has expired" | Expired (or wrong system clock) | Renew; automate; check NTP |
| `ERR_CERT_COMMON_NAME_INVALID` / "no alternative certificate subject name matches" | Name not in SAN | Include every hostname (apex **and** `www`) |
| `ERR_CERT_AUTHORITY_INVALID` / "unable to get local issuer certificate" | Untrusted issuer or **missing intermediate** | Serve `fullchain.pem`, not just `cert.pem` |
| "self signed certificate" | Not issued by a trusted CA | Use a real CA; for internal use, give clients your CA |
| `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` | No shared protocol/cipher | Enable TLS 1.2/1.3 with modern ciphers |
| Mixed content warnings | HTTPS page loads HTTP resources | Load everything over HTTPS |

</En>
<Ur>

| Error (browser / curl) | Matlab | Aam hal |
| --- | --- | --- |
| `NET::ERR_CERT_DATE_INVALID` / "certificate has expired" | Muddat khatam (ya system ki ghari ghalat) | Renew; automate; NTP check |
| `ERR_CERT_COMMON_NAME_INVALID` / "no alternative certificate subject name matches" | Naam SAN me nahi | Har hostname shamil (apex **aur** `www`) |
| `ERR_CERT_AUTHORITY_INVALID` / "unable to get local issuer certificate" | Be-bharosa issuer ya **ghayab intermediate** | Sirf `cert.pem` nahi, `fullchain.pem` dein |
| "self signed certificate" | Bharose wali CA ka jaari nahi | Asli CA; andaroni ke liye clients ko apni CA dein |
| `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` | Koi mushtarka protocol/cipher nahi | Jadeed ciphers ke saath TLS 1.2/1.3 |
| Mixed content warnings | HTTPS page HTTP cheezen load karta hai | Sab kuch HTTPS par load karein |

</Ur>

<Step title="TLS termination">

<Tr>
<En>

TLS is often decrypted at the load balancer or reverse proxy, which then talks to the app over plain HTTP, or encrypts again. That centralises certificates, offloads crypto work, and lets L7 proxies route by path and host. Inside a trusted private network, HTTP to the app is common; for sensitive systems, re-encrypt (end-to-end TLS). Pass `X-Forwarded-Proto: https` so the app builds correct URLs and secure cookies.

</En>
<Ur>

TLS aksar load balancer ya reverse proxy par decrypt hota hai, jo phir app se saada HTTP par baat karta hai, ya dobara encrypt karta hai. Is se certificates ek jagah rehte hain, crypto ka kaam hat jata hai, aur L7 proxies path aur host se route kar sakte hain. Bharose wale private network ke andar app tak HTTP aam hai; hassas systems ke liye dobara encrypt karein (end-to-end TLS). `X-Forwarded-Proto: https` bhejein taa ke app sahi URLs aur secure cookies banaye.

</Ur>
</Tr>

```text
user ══HTTPS══► ALB (cert from ACM, TLS ends here) ──HTTP or HTTPS──► app servers
                 └ adds X-Forwarded-For, X-Forwarded-Proto: https
```

</Step>

<Step title="Mutual TLS (mTLS)">

<Tr>
<En>

In mTLS **both** sides present certificates: the server proves who it is, and the client does too. It's strong machine-to-machine login without passwords or API keys, a building block of zero-trust networks. Used between microservices (Istio and Linkerd do it automatically), for B2B APIs, IoT devices and database clients. Client certificates come from a private CA that the server trusts.

</En>
<Ur>

mTLS me **dono** taraf certificates dikhati hain: server saabit karta hai wo kaun hai, aur client bhi. Ye passwords ya API keys ke baghair mazboot machine-se-machine login hai, zero-trust networks ka ek bunyadi pathar. Microservices ke darmiyan (Istio aur Linkerd khud karte hain), B2B APIs, IoT devices aur database clients me istemal hota hai. Client certificates ek private CA se aate hain jis par server bharosa karta hai.

</Ur>
</Tr>

</Step>

## Common mistakes

<Compare>
<Bad title="Turning verification off">

```text
curl -k https://api.example.com          # accepts ANY certificate
new https.Agent({ rejectUnauthorized: false })
requests.get(url, verify=False)
```

</Bad>
<Good title="Trust the right CA instead">

```text
curl --cacert company-ca.pem https://api.internal
new https.Agent({ ca: fs.readFileSync("company-ca.pem") })
requests.get(url, verify="company-ca.pem")
```

</Good>
</Compare>

<Compare>
<Bad title="Only the leaf certificate">

```text
ssl_certificate /etc/letsencrypt/live/api.example.com/cert.pem;
```

</Bad>
<Good title="The full chain">

```text
ssl_certificate /etc/letsencrypt/live/api.example.com/fullchain.pem;
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting `www`** (or the apex) in the certificate.
- **Manual renewal**: certificates expire on weekends.
- **Private keys in Git**, in Docker images or in world-readable files.
- **Allowing TLS 1.0/1.1** for "compatibility".
- **Plain HTTP between proxy and app across untrusted networks.**

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Certificate me `www` (ya apex) bhoolna.**
- **Haath se renewal**: certificates weekend par expire hote hain.
- **Private keys Git me**, Docker images me ya sab ke parhne layaq files me.
- **"Compatibility" ke liye TLS 1.0/1.1 ki ijazat.**
- **Be-bharosa networks par proxy aur app ke darmiyan saada HTTP.**

</Ur>
</Tr>

<Challenge title="TLS lab: a self-signed certificate">

<Tr>
<En>
Create a self-signed certificate and check four things. Check 3 is a real-world lifesaver: "nginx won't start after renewing" is often a key that doesn't match the certificate. With internet, also inspect a real site: `echo | openssl s_client -connect github.com:443 -servername github.com 2>/dev/null | openssl x509 -noout -subject -issuer -dates`.
</En>
<Ur>
Self-signed certificate banayen aur chaar cheezen check karein. Check 3 asal zindagi me jaan bachata hai: "renew ke baad nginx shuru nahi hota" aksar aisi key hoti hai jo certificate se nahi milti. Internet ho to asli site bhi dekhein: `echo | openssl s_client -connect github.com:443 -servername github.com 2>/dev/null | openssl x509 -noout -subject -issuer -dates`.
</Ur>
</Tr>

```bash
mkdir -p tls-lab && cd tls-lab
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 1 \
  -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost" -keyout k.pem -out c.pem 2>/dev/null
echo "1) self-signed certificate created for: $(openssl x509 -in c.pem -noout -ext subjectAltName | tail -1 | tr -d ' ')"
echo "2) issuer equals subject (self-signed): $([[ $(openssl x509 -in c.pem -noout -issuer | cut -d= -f2-) == $(openssl x509 -in c.pem -noout -subject | cut -d= -f2-) ]] && echo yes)"
echo "3) key and certificate belong together: $([[ $(openssl x509 -in c.pem -noout -pubkey | sha256sum) == $(openssl pkey -in k.pem -pubout | sha256sum) ]] && echo yes)"
echo "4) private key permissions should be 600: $(chmod 600 k.pem; stat -c %a k.pem)"
cd .. && rm -rf tls-lab
```

<DeepDive title="Real world: the missing intermediate">

On a Monday morning the mobile app stops loading data, while the website works in Chrome. The API's certificate had been renewed on Friday by a script that copied only `cert.pem` into nginx instead of `fullchain.pem`:

```text
$ openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null 2>/dev/null | grep -A3 'Certificate chain'
Certificate chain
 0 s:CN = api.example.com
   i:C = US, O = Let's Encrypt, CN = R11          ← only 1 certificate sent; intermediate missing
Verify return code: 20 (unable to get local issuer certificate)
```

Chrome had the intermediate cached from other sites and silently filled the gap; the Android app and curl didn't. Fix: `ssl_certificate /etc/letsencrypt/live/api.example.com/fullchain.pem;`, `nginx -t && systemctl reload nginx`, and add a monitoring check that verifies the chain from a **clean** client (curl in CI), not just a browser.

</DeepDive>

<DeepDive title="Security lens">

The private key **is** the server's identity. Anyone who steals it can impersonate your site to every user.

- **Protect private keys:** mode `600`, owned by root or the service user, never committed, ideally in a managed service (ACM, Key Vault, KMS/HSM) where they can't be exported.
- **Never disable certificate verification** in code: it silently removes all protection against man-in-the-middle attacks.
- **HSTS** prevents SSL-stripping attacks that downgrade users to HTTP.
- **Certificate Transparency logs** publish every issued certificate: attackers use them to discover your subdomains; you can monitor them to spot unauthorised certificates. Add **CAA** records to limit which CAs may issue.
- **Revocation:** if a key leaks, revoke the certificate and issue a new one with a **new** key.
- **TLS doesn't make a site honest:** phishing sites use HTTPS too.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does TLS provide?">
Confidentiality, because traffic is encrypted; integrity, because tampering is detected through message authentication; and authentication of the server (and optionally the client), because the server proves possession of the private key matching a certificate signed by a trusted certificate authority.
</QA>

<QA q="Why does TLS use both asymmetric and symmetric cryptography?">
Asymmetric cryptography allows two parties to agree on shared secrets and to authenticate each other without having exchanged a secret beforehand, but it is slow. Once the handshake has established shared keys, TLS switches to fast symmetric encryption such as AES-GCM or ChaCha20-Poly1305 for the actual data.
</QA>

<QA q="How does a browser decide whether to trust a certificate?">
It builds a chain from the server certificate through any intermediate certificates to a root certificate in its trust store, verifies each signature, checks that the certificates are within their validity dates and not revoked, and checks that the requested hostname matches one of the certificate's Subject Alternative Names.
</QA>

<QA q="What is mutual TLS and when would you use it?">
In mutual TLS both the server and the client present certificates and verify each other. It is used for strong machine-to-machine authentication, for example between microservices in a service mesh, for business-to-business APIs and for devices, replacing shared secrets such as API keys.
</QA>

<QA q="What is TLS termination?">
It is decrypting TLS at a load balancer or reverse proxy rather than at the application. The proxy holds the certificate, inspects and routes HTTP, and forwards requests to backends either in plain HTTP inside a trusted network or re-encrypted with TLS. Headers such as X-Forwarded-Proto tell the application the original scheme.
</QA>

</DeepDive>
