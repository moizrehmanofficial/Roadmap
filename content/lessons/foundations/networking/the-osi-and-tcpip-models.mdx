<Callout type="tip" title="In one minute">
Sending data across a network involves many jobs: turning bits into signals, delivering to the right machine, delivering to the right program, and making sense of the content. Network **models** split these jobs into **layers**, each with its own rules (**protocols**). The **OSI model** has 7 layers (Physical, Data Link, Network, Transport, Session, Presentation, Application) — used to **talk about** networks. The **TCP/IP model** has 4 (Link, Internet, Transport, Application) — what the internet **actually uses**. On the way out, each layer wraps the data in its own **header** (**encapsulation**); on the way in, each layer unwraps its part.
</Callout>

## Start from zero

### What is a network?

A **network** is two or more devices connected so they can exchange data: your phone and Wi-Fi router, a server and its database, millions of networks joined together as the **internet**.

To get a web page from a server in another country to your screen, many separate problems must be solved: electrical or radio signals, finding the right machine among billions, choosing a path, recovering lost pieces, finding the right program on that machine, and understanding the content. One giant program solving all of it would be impossible to build and fix. So the work is split into **layers**.

<Callout type="analogy">
**Sending a parcel with a courier (TCS / Leopards / DHL):**

- You write a **letter** in Urdu (the content — Application).
- You put it in an **envelope** with the recipient's **name and flat number** (which person/program — Transport, ports).
- The courier puts it in a **package with the city and street address** (which building/computer — Network, IP address).
- At each depot, the package gets a **local routing label** for the next truck (next hop — Data Link, MAC address).
- The **trucks and roads** physically move it (Physical).

Each worker only cares about **their** label. The truck driver never opens your letter; the sorting depot never reads your Urdu. That independence is exactly what layers give networks.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Network** | Connected devices that exchange data | home Wi-Fi, the internet |
| **Protocol** | Agreed rules for communication | HTTP, TCP, IP |
| **Layer** | One level of the job, with its own protocols | Transport layer |
| **Header** | Extra information a layer adds in front of the data | IP header with addresses |
| **Encapsulation** | Wrapping data in headers, layer by layer | data → segment → packet → frame |
| **Packet** | A chunk of data with an IP header | ~1500 bytes |
| **Frame** | A chunk with a link-layer (e.g. Ethernet) header | |
| **MAC address** | Hardware address of a network card (local network only) | `02:42:ac:11:00:02` |
| **IP address** | Logical address of a machine on a network | `203.0.113.10` |
| **Port** | Number identifying a program on a machine | 443 |

## What is it?

### The OSI model (7 layers)

| # | Layer | Job | Unit | Examples |
| --- | --- | --- | --- | --- |
| 7 | **Application** | What the user/app wants | data | HTTP, DNS, SSH, SMTP |
| 6 | **Presentation** | Format, encoding, encryption | data | TLS, JSON, UTF-8, JPEG |
| 5 | **Session** | Opening, keeping, closing conversations | data | sessions, TLS sessions |
| 4 | **Transport** | Process-to-process delivery, reliability | segment / datagram | TCP, UDP (ports) |
| 3 | **Network** | Machine-to-machine across networks, routing | packet | IP, ICMP, routers |
| 2 | **Data Link** | Delivery on the **local** network | frame | Ethernet, Wi-Fi, MAC, switches |
| 1 | **Physical** | Bits as signals | bits | cables, fibre, radio |

Memory trick (top to bottom): **A**ll **P**eople **S**eem **T**o **N**eed **D**ata **P**rocessing.

### The TCP/IP model (4 layers) — what the internet really uses

```text
        OSI                         TCP/IP
 7  Application   ┐
 6  Presentation  ├──────────►  Application   HTTP, DNS, TLS, SSH
 5  Session       ┘
 4  Transport     ───────────►  Transport     TCP, UDP
 3  Network       ───────────►  Internet      IP, ICMP
 2  Data Link     ┐
 1  Physical      ┘───────────►  Link          Ethernet, Wi-Fi
```

People say "layer 4 load balancer" or "layer 7 firewall" using **OSI numbers**, even though the protocols are TCP/IP. Learn both.

## Why does it matter?

- **Troubleshooting:** "Is the cable/Wi-Fi up (L1–2)? Can I reach the IP (L3)? Is the port open (L4)? Does the app answer correctly (L7)?" — going layer by layer finds problems fast.
- **Cloud and DevOps vocabulary:** L4 vs L7 load balancers (AWS NLB vs ALB), security groups (L3/L4) vs WAF (L7).
- **Security:** attacks and defences are described by layer: ARP spoofing (L2), IP spoofing (L3), SYN floods (L4), SQL injection and XSS (L7).
- **Interviews:** "explain the OSI model" and "what happens when you type a URL" are classic questions.

## When and where do you use it?

| Situation | Layer thinking |
| --- | --- |
| "Site is down" | Ping (L3) works? Port 443 open (L4)? HTTP status (L7)? |
| Choosing a load balancer | L4 (TCP, fast) or L7 (HTTP routing by path/host) |
| Firewall rules | Security group (IP/port, L3–4), WAF (HTTP content, L7) |
| Reading Wireshark/tcpdump | Each packet shows Ethernet → IP → TCP → HTTP |

## Concepts one by one

### 1. Layers and protocols

<Explain>
<What>
Each layer solves one part of communication and **only talks to the layer directly above and below** it. A **protocol** is the set of rules at one layer.
</What>
<Why>
You can change one layer without touching the others: the same HTTP works over Wi-Fi, fibre or 5G; the same Wi-Fi carries HTTP, SSH or video calls.
</Why>
<When>
Always — every network message passes through all the layers.
</When>
<Where>
Every device: your laptop, routers, servers, phones.
</Where>
<How>
Think of each layer as a service: "Transport, please deliver these bytes to port 443 on that machine — reliably."
</How>
</Explain>

### 2. Encapsulation: headers wrapped around data

<Explain>
<What>
On the way **out**, each layer adds its own header (and the link layer also a trailer) around the data from the layer above. On the way **in**, each layer removes and reads its header, then passes the rest up.
</What>
<Why>
Each layer gets the information it needs (addresses, ports, checks) without understanding the rest.
</Why>
<When>
Every message, every time.
</When>
<Where>
Visible in packet captures (tcpdump, Wireshark).
</Where>
<How>
Data → **segment** (+TCP header) → **packet** (+IP header) → **frame** (+Ethernet header) → bits on the wire.
</How>
</Explain>

```text
Application    [ GET / HTTP/1.1 … ]                                     data
Transport      [TCP hdr: ports 51522→443, seq…][ data ]                 segment
Internet       [IP hdr: 192.168.1.20→203.0.113.10][TCP][ data ]         packet
Link           [Eth hdr: MACs][IP][TCP][ data ][checksum]               frame
Physical       0101100101010…                                           bits
```

```python
data = b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n"
tcp_header, ip_header, eth_header = 20, 20, 14 + 4   # typical sizes in bytes
total = len(data) + tcp_header + ip_header + eth_header
print(f"application data: {len(data)} bytes")
print(f"on the wire:      {total} bytes ({total - len(data)} bytes of headers)")
```

```text output
application data: 37 bytes
on the wire:      95 bytes (58 bytes of headers)
```

Small requests carry a lot of header overhead — one reason HTTP/2 and HTTP/3 combine many requests.

### 3. Layer 1 — Physical

<Explain>
<What>
Turning bits into signals: electricity in copper cables, light in fibre, radio waves in Wi-Fi and 4G/5G.
</What>
<Why>
Nothing works if the signal does not arrive.
</Why>
<When>
"Is it plugged in?", bad cables, weak Wi-Fi, data-centre fibre.
</When>
<Where>
Cables, connectors, network cards, radios, repeaters.
</Where>
<How>
In the cloud you never see this layer — the provider manages it.
</How>
</Explain>

### 4. Layer 2 — Data Link (the local network)

<Explain>
<What>
Delivers frames between devices on the **same local network** using **MAC addresses**.
</What>
<Why>
Before data can travel across the internet, it must get from your laptop to your router.
</Why>
<When>
Every hop: your laptop → router; router → next router.
</When>
<Where>
Ethernet, Wi-Fi, **switches**, ARP (finds the MAC for an IP), VLANs.
</Where>
<How>
`ip link` shows your interfaces and MAC addresses. MACs are only meaningful **inside** one local network — routers replace the frame at every hop.
</How>
</Explain>

```bash
ip -br link | awk '{print $1, "state:", $2}' | head -2
```

Example output:

```text
lo state: UNKNOWN
eth0 state: UP
```

(`lo` is the loopback interface — the machine talking to itself; names like `eth0`, `ens5`, `wlan0` vary by system.)

### 5. Layer 3 — Network (IP)

<Explain>
<What>
Moves **packets** from the source machine to the destination machine, possibly across many networks, using **IP addresses**. **Routers** decide the next hop.
</What>
<Why>
This is what makes an inter-**net**: networks joined together.
</Why>
<When>
Every connection beyond your local network.
</When>
<Where>
IPv4, IPv6, ICMP (`ping`, `traceroute`), routers, cloud route tables, VPCs.
</Where>
<How>
IP is "best effort": packets can be lost, duplicated or arrive out of order. Fixing that is the job of layer 4.
</How>
</Explain>

### 6. Layer 4 — Transport (TCP and UDP)

<Explain>
<What>
Delivers data to the right **program** (using **ports**) and, with TCP, makes delivery reliable and ordered.
</What>
<Why>
A server runs many programs; an IP address alone does not say which one should get the data.
</Why>
<When>
Every connection: TCP for web, SSH, databases; UDP for DNS, video calls, games, QUIC.
</When>
<Where>
TCP, UDP; L4 load balancers; firewall rules on ports.
</Where>
<How>
TCP: connection, acknowledgements, retransmission, ordering. UDP: just send, no guarantees, very fast. (Details in **Ports, TCP and UDP**.)
</How>
</Explain>

### 7. Layers 5–7 — Session, Presentation, Application

<Explain>
<What>
Everything the applications themselves care about: the conversation (session), the format and encryption (presentation), and the meaning (application).
</What>
<Why>
This is where your code lives: URLs, headers, JSON, cookies, authentication.
</Why>
<When>
Every request your app sends or receives.
</When>
<Where>
HTTP, DNS, SSH, SMTP, TLS (encryption), JSON/UTF-8 (format). In TCP/IP all three are simply "Application".
</Where>
<How>
L7 tools understand content: reverse proxies (nginx), API gateways, WAFs, L7 load balancers.
</How>
</Explain>

```bash
cat > l7.mjs <<'EOF'
import http from "node:http";
http.createServer((req, res) => res.end(`layer 7 sees: ${req.method} ${req.url} (Host: ${req.headers.host})\n`)).listen(3460, "127.0.0.1");
EOF
node l7.mjs & pid=$!; sleep 0.5
curl -s http://127.0.0.1:3460/api/orders?id=7
kill $pid
```

```text output
layer 7 sees: GET /api/orders?id=7 (Host: 127.0.0.1:3460)
```

A **layer 4** device would only have seen "TCP to 127.0.0.1 port 3460" — not the method, path or host name. That is why path-based routing (`/api` → API servers, `/` → web servers) needs a **layer 7** load balancer.

### 8. Which device works at which layer?

<Explain>
<What>
Network devices and services are often named by the highest layer they understand.
</What>
<Why>
It tells you what they can see and decide on.
</Why>
<When>
Designing networks, choosing cloud services.
</When>
<Where>
Data centres, offices, every cloud.
</Where>
<How>
See the table.
</How>
</Explain>

| Device / service | Layer | Decides using |
| --- | --- | --- |
| Hub, repeater | 1 | Nothing — just repeats signals |
| Switch | 2 | MAC addresses |
| Router | 3 | IP addresses |
| Firewall / security group | 3–4 | IPs, ports, protocols |
| L4 load balancer (AWS NLB) | 4 | IP + port |
| L7 load balancer (AWS ALB), reverse proxy (nginx) | 7 | Host, path, headers, cookies |
| WAF (web application firewall) | 7 | Request content (SQL injection, XSS patterns) |

### 9. Troubleshooting bottom-up (or top-down)

<Explain>
<What>
Checking each layer in order until you find the broken one.
</What>
<Why>
Random guessing wastes time; layers give a checklist.
</Why>
<When>
"I can't reach the server / the site is down."
</When>
<Where>
Your laptop, servers, cloud networks.
</Where>
<How>
L1–2: interface up? (`ip link`). L3: IP and route? reachable? (`ip addr`, `ping`, `traceroute`). L4: port open? (`nc -zv host 443`, `ss -ltn`). L7: correct answer? (`curl -v`). DNS sits in between: does the name resolve? (`dig`).
</How>
</Explain>

```bash
python3 -m http.server 3461 --bind 127.0.0.1 > /dev/null 2>&1 & pid=$!; sleep 1
echo "L3 (IP reachable):  $(ping -c1 -W1 127.0.0.1 > /dev/null 2>&1 && echo OK || echo 'no ICMP here (try L4)')" | sed -E 's/:  (OK|no ICMP.*)$/:  OK or blocked/'
echo "L4 (port open):     $(nc -z 127.0.0.1 3461 2>/dev/null && echo OK)"
echo "L4 (closed port):   $(nc -z 127.0.0.1 3999 2>/dev/null || echo 'refused — nothing listening')"
echo "L7 (HTTP answer):   $(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3461/)"
kill $pid
```

```text output
L3 (IP reachable):  OK or blocked
L4 (port open):     OK
L4 (closed port):   refused — nothing listening
L7 (HTTP answer):   200
```

(Many networks and cloud firewalls block `ping`, so a failed ping does not prove a server is down — always also test the actual port.)

## Hands-on

```bash
# 1. Your interfaces and addresses (layers 2 and 3)
ip -br addr | awk '{print $1, $3}' | head -3

# 2. Who is listening on this machine (layer 4)
ss -ltn | awk 'NR==1 || /LISTEN/' | head -5 | awk '{print $1, $4}'

# 3. Layer 7: see the request and response headers of a local server
python3 -m http.server 3462 --bind 127.0.0.1 > /dev/null 2>&1 & pid=$!; sleep 1
curl -sv http://127.0.0.1:3462/ -o /dev/null 2>&1 | grep -E '^(> GET|< HTTP)' | tr -d '\r'
kill $pid
```

Example output:

```text
lo 127.0.0.1/8
eth0 <your IP>/<prefix>
State Local
LISTEN <address:port of a listening service>
> GET / HTTP/1.1
< HTTP/1.0 200 OK
```

Your interface names, IPs and listening services will differ. In the `curl -v` output, `>` lines are what you **sent** and `<` lines are what you **received** — layer 7 in plain text.

## Real-world example

A user reports: "The shop website is down." The on-call engineer works up the layers:

```text
$ dig +short shop.example.com            # name resolution
203.0.113.10                             ✓ DNS fine

$ ping -c 2 203.0.113.10                 # L3
2 packets transmitted, 2 received        ✓ server reachable

$ nc -zv 203.0.113.10 443                # L4
Connection to 203.0.113.10 443 port [tcp/https] succeeded!   ✓ port open (nginx is up)

$ curl -sI https://shop.example.com      # L7
HTTP/2 502                               ✗ Bad Gateway
```

Layers 3 and 4 are fine; layer 7 returns **502**, which means nginx is running but **the app behind it** is not answering. Next step: `systemctl status shop` and `journalctl -u shop` on the server — the Node.js process had crashed. Ten minutes instead of an hour of guessing.

## Common mistakes

- **Memorising layer names without meaning** — know what each layer does and which problems belong to it.
- **"Ping fails, so the server is down"** — ICMP is often blocked; test the real port.
- **Confusing MAC and IP** — MAC is local (layer 2, changes every hop), IP is end-to-end (layer 3).
- **Thinking a firewall on ports can block SQL injection** — that is layer 7 content; you need input validation and/or a WAF.
- **Mixing up L4 and L7 load balancers** — only L7 can route by URL path or host name, or terminate HTTPS and inspect headers.

## Security lens

<Callout type="security">
Attackers and defenders think in layers too. Each layer needs its own protection — "defence in depth".
</Callout>

| Layer | Example attack | Example defence |
| --- | --- | --- |
| 1 Physical | Cable tapping, stolen hardware | Locked data centres, encryption |
| 2 Data Link | ARP spoofing, rogue Wi-Fi | Switch security, WPA3, 802.1X |
| 3 Network | IP spoofing, ICMP floods | Firewalls, anti-spoofing filters |
| 4 Transport | SYN floods, port scanning | SYN cookies, rate limits, closing ports |
| 6 Presentation | Weak TLS, downgrade attacks | TLS 1.2+/1.3 only, HSTS |
| 7 Application | SQL injection, XSS, credential stuffing | Input validation, WAF, MFA, rate limiting |

DDoS attacks are also classified by layer: **volumetric / L3–4** (flooding bandwidth or connections) vs **L7** (expensive HTTP requests that look legitimate).

## Interview questions

<QA q="What are the layers of the OSI model?">
From bottom to top: 1 Physical (signals on cables or radio), 2 Data Link (frames and MAC addresses on the local network), 3 Network (IP addressing and routing between networks), 4 Transport (TCP and UDP, ports, reliability), 5 Session (managing conversations), 6 Presentation (formats, encoding and encryption such as TLS), 7 Application (protocols like HTTP, DNS and SSH).
</QA>

<QA q="What is the difference between the OSI and TCP/IP models?">
OSI is a 7-layer reference model used to describe and discuss networking. TCP/IP is the 4-layer model the internet actually implements: Link (OSI 1–2), Internet (OSI 3), Transport (OSI 4) and Application (OSI 5–7). People still use OSI layer numbers, such as L4 or L7, to describe devices and services.
</QA>

<QA q="What is encapsulation?">
As data goes down the stack, each layer adds its own header around the data from the layer above: the transport layer adds a TCP or UDP header to make a segment, the internet layer adds an IP header to make a packet, and the link layer adds an Ethernet or Wi-Fi header and trailer to make a frame. The receiver removes the headers in reverse order.
</QA>

<QA q="What is the difference between a layer 4 and a layer 7 load balancer?">
A layer 4 load balancer forwards TCP or UDP connections based on IP addresses and ports without looking at the content, which makes it fast and protocol-agnostic. A layer 7 load balancer understands the application protocol, usually HTTP, so it can route by host name, path, headers or cookies, terminate TLS and modify requests.
</QA>
