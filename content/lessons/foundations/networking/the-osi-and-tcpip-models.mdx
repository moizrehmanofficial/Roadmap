<BigIdea>
<Tr>
<En>
Getting a web page from a server in another country to your screen needs many separate jobs: turning bits into signals, finding the right machine, finding the right program, and understanding the content. Network **models** split these jobs into **layers**, each with its own rules (**protocols**). **OSI** has 7 layers and is used to **talk about** networks. **TCP/IP** has 4 and is what the internet **actually uses**.
</En>
<Ur>
Doosre mulk ke server se web page aap ki screen tak laane ke liye kai alag kaam chahiye: bits ko signals banana, sahi machine dhoondna, sahi program dhoondna, aur mawad samajhna. Network **models** in kaamon ko **layers** me baant dete hain, har ek ke apne usool (**protocols**). **OSI** ki 7 layers hain aur ye networks ke **baare me baat** karne ke liye hai. **TCP/IP** ki 4 hain aur internet **asal me** yahi istemal karta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

A **network** is two or more devices connected so they can exchange data: your phone and Wi-Fi router, a server and its database, and millions of networks joined together as the **internet**.

| # | OSI layer | Job | Unit | Examples |
| --- | --- | --- | --- | --- |
| 7 | **Application** | What the user/app wants | data | HTTP, DNS, SSH, SMTP |
| 6 | **Presentation** | Format, encoding, encryption | data | TLS, JSON, UTF-8, JPEG |
| 5 | **Session** | Opening, keeping, closing conversations | data | sessions, TLS sessions |
| 4 | **Transport** | Program-to-program delivery, reliability | segment | TCP, UDP (ports) |
| 3 | **Network** | Machine-to-machine across networks | packet | IP, ICMP, routers |
| 2 | **Data Link** | Delivery on the **local** network | frame | Ethernet, Wi-Fi, MAC, switches |
| 1 | **Physical** | Bits as signals | bits | cables, fibre, radio |

Memory trick, top to bottom: **A**ll **P**eople **S**eem **T**o **N**eed **D**ata **P**rocessing.

</En>
<Ur>

**Network** do ya zyada devices hain jo data badalne ke liye jure hon: aap ka phone aur Wi-Fi router, server aur us ka database, aur lakhon networks jo mil kar **internet** bante hain.

| # | OSI layer | Kaam | Ikai | Misaalen |
| --- | --- | --- | --- | --- |
| 7 | **Application** | User/app kya chahta hai | data | HTTP, DNS, SSH, SMTP |
| 6 | **Presentation** | Format, encoding, encryption | data | TLS, JSON, UTF-8, JPEG |
| 5 | **Session** | Guftagu kholna, chalana, band karna | data | sessions, TLS sessions |
| 4 | **Transport** | Program se program tak, bharose se | segment | TCP, UDP (ports) |
| 3 | **Network** | Networks ke paar machine se machine | packet | IP, ICMP, routers |
| 2 | **Data Link** | **Local** network par pohanchana | frame | Ethernet, Wi-Fi, MAC, switches |
| 1 | **Physical** | Bits ko signals banana | bits | cables, fibre, radio |

Yaad rakhne ka tareeqa, ooper se neeche: **A**ll **P**eople **S**eem **T**o **N**eed **D**ata **P**rocessing.

</Ur>

</What>
<Why>
<Tr>
<En>

- **Troubleshooting:** "Is the Wi-Fi up (L1–2)? Can I reach the IP (L3)? Is the port open (L4)? Does the app answer correctly (L7)?" Going layer by layer finds problems fast.
- **Cloud and DevOps words:** L4 vs L7 load balancers (AWS NLB vs ALB), security groups (L3/L4) vs WAF (L7).
- **Security:** attacks and defences are described by layer: ARP spoofing (L2), SYN floods (L4), SQL injection (L7).
- **Interviews:** "explain the OSI model" and "what happens when you type a URL" are classics.

</En>
<Ur>

- **Masle hal karna:** "Wi-Fi chal raha hai (L1–2)? IP tak pohanch sakte hain (L3)? Port khula hai (L4)? App sahi jawab deti hai (L7)?" Layer ba layer chalna masle jaldi dhoondta hai.
- **Cloud aur DevOps ke alfaz:** L4 bamuqabla L7 load balancers (AWS NLB bamuqabla ALB), security groups (L3/L4) bamuqabla WAF (L7).
- **Security:** hamle aur hifazat layer ke hisaab se bayan hote hain: ARP spoofing (L2), SYN floods (L4), SQL injection (L7).
- **Interviews:** "OSI model samjhao" aur "URL type karne par kya hota hai" mashhoor sawal hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Layer thinking |
| --- | --- |
| "Site is down" | Ping (L3) works? Port 443 open (L4)? HTTP status (L7)? |
| Choosing a load balancer | L4 (TCP, fast) or L7 (HTTP routing by path/host) |
| Firewall rules | Security group (IP/port, L3–4), WAF (HTTP content, L7) |

</En>

| Soorat | Layer ke hisaab se sochna |
| --- | --- |
| "Site band hai" | Ping (L3) chalta hai? Port 443 khula (L4)? HTTP status (L7)? |
| Load balancer chunna | L4 (TCP, tez) ya L7 (path/host se HTTP routing) |
| Firewall rules | Security group (IP/port, L3–4), WAF (HTTP mawad, L7) |
| Wireshark/tcpdump parhna | Har packet Ethernet → IP → TCP → HTTP dikhata hai |

</Ur>
</Tr>

<How>
<Tr>
<En>

The TCP/IP model joins some OSI layers together:

```text
        OSI                         TCP/IP
 7  Application   ┐
 6  Presentation  ├──────────►  Application   HTTP, DNS, TLS, SSH
 5  Session       ┘
 4  Transport     ───────────►  Transport     TCP, UDP
 3  Network       ───────────►  Internet      IP, ICMP
 2  Data Link     ┐
 1  Physical      ┘───────────►  Link          Ethernet, Wi-Fi
```

People say "layer 4 load balancer" or "layer 7 firewall" using **OSI numbers**, even though the protocols are TCP/IP. Learn both.

</En>
<Ur>

TCP/IP model kuch OSI layers ko jor deta hai:

```text
        OSI                         TCP/IP
 7  Application   ┐
 6  Presentation  ├──────────►  Application   HTTP, DNS, TLS, SSH
 5  Session       ┘
 4  Transport     ───────────►  Transport     TCP, UDP
 3  Network       ───────────►  Internet      IP, ICMP
 2  Data Link     ┐
 1  Physical      ┘───────────►  Link          Ethernet, Wi-Fi
```

Log "layer 4 load balancer" ya "layer 7 firewall" **OSI numbers** se kehte hain, halanke protocols TCP/IP ke hain. Dono seekhein.

</Ur>

## Picture it

<Tr>
<En>

**Sending a parcel with a courier (UPS / FedEx / DHL):**

- You write a **letter** (the content: Application).
- You put it in an **envelope** with the recipient's **name and flat number** (which person/program: Transport, ports).
- The courier puts it in a **package with the city and street address** (which building/computer: Network, IP address).
- At each depot the package gets a **local label** for the next truck (next hop: Data Link, MAC address).
- The **trucks and roads** physically move it (Physical).

Each worker cares only about **their** label. The truck driver never opens your letter; the sorting depot never reads it. That independence is exactly what layers give networks.

</En>
<Ur>

**Courier (UPS / FedEx / DHL) se parcel bhejna:**

- Aap **khat** likhte hain (mawad: Application).
- Use **lifafe** me daalte hain jis par paane wale ka **naam aur flat number** ho (kaunsa shakhs/program: Transport, ports).
- Courier use **shehar aur gali ke pate wale package** me daalta hai (kaunsi imarat/computer: Network, IP address).
- Har depot par package ko agle truck ke liye **local label** milta hai (agla hop: Data Link, MAC address).
- **Truck aur sarkein** use asal me le jati hain (Physical).

Har kaarkun sirf **apne** label ki parwah karta hai. Truck driver kabhi khat nahi kholta; sorting depot use kabhi nahi parhta. Yahi aazadi layers networks ko deti hain.

</Ur>
</Tr>

<Tr>
<En>

| --- | --- | --- |

| **Packet** | A chunk of data with an IP header | ~1500 bytes |
| **Frame** | A chunk with a link-layer (e.g. Ethernet) header | |

## Learn it step by step

<Walkthrough>

<Step title="Layers and protocols">

<Tr>
<En>

Each layer solves one part of communication and **only talks to the layer directly above and below**. So you can change one layer without touching the others: the same HTTP works over Wi-Fi, fibre or 5G, and the same Wi-Fi carries HTTP, SSH or video calls. Think of each layer as a service: "Transport, please deliver these bytes to port 443 on that machine, reliably."

</En>
<Ur>

Har layer guftagu ka ek hissa hal karti hai aur **sirf apne bilkul ooper aur neeche wali layer** se baat karti hai. Isliye aap ek layer doosri ko chhoye baghair badal sakte hain: wahi HTTP Wi-Fi, fibre ya 5G par chalta hai, aur wahi Wi-Fi HTTP, SSH ya video calls le jata hai. Har layer ko ek service samjhein: "Transport, ye bytes us machine ke port 443 par bharose se pohancha do."

</Ur>
</Tr>

</Step>

<Step title="Encapsulation: headers wrapped around data">

<Tr>
<En>

On the way **out**, each layer wraps the data from above in its own header (the link layer also adds a trailer). On the way **in**, each layer removes and reads its header, then passes the rest up. Each layer gets the information it needs (addresses, ports, checks) without understanding the rest. You can see this in packet captures (tcpdump, Wireshark).

</En>
<Ur>

**Bahar** jate waqt har layer ooper se aaye data ko apne header me lapetti hai (link layer trailer bhi jorti hai). **Andar** aate waqt har layer apna header hata kar parhti hai, phir baqi ooper bhejti hai. Har layer ko zaroori maloomat (addresses, ports, checks) milti hai baqi samjhe baghair. Ye packet captures (tcpdump, Wireshark) me nazar aata hai.

</Ur>
</Tr>

```text
Application    [ GET / HTTP/1.1 … ]                                     data
Transport      [TCP hdr: ports 51522→443, seq…][ data ]                 segment
Internet       [IP hdr: 192.168.1.20→203.0.113.10][TCP][ data ]         packet
Link           [Eth hdr: MACs][IP][TCP][ data ][checksum]               frame
Physical       0101100101010…                                           bits
```

```python
data = b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n"
tcp_header, ip_header, eth_header = 20, 20, 14 + 4   # typical sizes in bytes
total = len(data) + tcp_header + ip_header + eth_header
print(f"application data: {len(data)} bytes")
print(f"on the wire:      {total} bytes ({total - len(data)} bytes of headers)")
```

```text output
application data: 37 bytes
on the wire:      95 bytes (58 bytes of headers)
```

<Happened>
<Tr>
<En>A 37-byte request became 95 bytes on the wire: 58 bytes were headers. Small requests carry a lot of header overhead, which is one reason HTTP/2 and HTTP/3 combine many requests.</En>
<Ur>37 byte ki request taar par 95 byte ban gayi: 58 byte headers the. Chhoti requests par headers ka bohot bojh hota hai, aur ye ek wajah hai ke HTTP/2 aur HTTP/3 kai requests ko jor dete hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Layer 1: Physical">

<Tr>
<En>

Turning bits into signals: electricity in copper, light in fibre, radio waves in Wi-Fi and 4G/5G. Nothing works if the signal doesn't arrive: "Is it plugged in?", bad cables, weak Wi-Fi. In the cloud you never see this layer; the provider manages it.

</En>
<Ur>

Bits ko signals banana: tanbe me bijli, fibre me roshni, Wi-Fi aur 4G/5G me radio lehrein. Signal na pohanche to kuch nahi chalta: "Plug laga hai?", kharab cables, kamzor Wi-Fi. Cloud me ye layer kabhi nazar nahi aati; provider sambhalta hai.

</Ur>
</Tr>

</Step>

<Step title="Layer 2: Data Link (the local network)">

<Tr>
<En>

Delivers frames between devices on the **same local network** using **MAC addresses**: your laptop → your router, then router → next router. Switches, ARP (finds the MAC for an IP) and VLANs live here. MACs only mean something **inside** one local network; routers build a new frame at every hop. `ip link` shows your interfaces.

</En>
<Ur>

**Ek hi local network** par devices ke darmiyan **MAC addresses** se frames pohanchati hai: aap ka laptop → router, phir router → agla router. Switches, ARP (IP ka MAC dhoondta hai) aur VLANs yahin hain. MAC sirf **ek** local network ke **andar** maani rakhte hain; routers har hop par naya frame banate hain. `ip link` aap ke interfaces dikhata hai.

</Ur>
</Tr>

```bash
ip -br link | awk '{print $1, "state:", $2}' | head -2
```

<Tr>
<En>Example output:</En>
<Ur>Misaali output:</Ur>
</Tr>

```text
lo state: UNKNOWN
eth0 state: UP
```

<Tr>
<En>`lo` is the loopback interface (the machine talking to itself); names like `eth0`, `ens5`, `wlan0` vary by system.</En>
<Ur>`lo` loopback interface hai (machine ka khud se baat karna); `eth0`, `ens5`, `wlan0` jaise naam har system par alag hote hain.</Ur>
</Tr>

</Step>

<Step title="Layer 3: Network (IP)">

<Tr>
<En>

Moves **packets** from the source machine to the destination machine, maybe across many networks, using **IP addresses**. **Routers** pick the next hop. This is what makes an inter-**net**: networks joined together. IP is "best effort": packets can be lost, duplicated or arrive out of order. Fixing that is layer 4's job. Tools: `ping`, `traceroute`; in the cloud: route tables and VPCs.

</En>
<Ur>

**IP addresses** se **packets** ko shuru wali machine se manzil wali machine tak le jati hai, shayad kai networks ke paar. **Routers** agla hop chunte hain. Yahi inter-**net** banata hai: networks ka jor. IP "best effort" hai: packets kho sakte hain, do dafa aa sakte hain ya be-tarteeb pohanch sakte hain. Ise theek karna layer 4 ka kaam hai. Tools: `ping`, `traceroute`; cloud me: route tables aur VPCs.

</Ur>
</Tr>

</Step>

<Step title="Layer 4: Transport (TCP and UDP)">

<Tr>
<En>

A server runs many programs; an IP address alone doesn't say which one should get the data. Layer 4 delivers to the right **program** using **ports**.

- **TCP:** connection, acknowledgements, resending, ordering. For web, SSH, databases.
- **UDP:** just send, no guarantees, very fast. For DNS, video calls, games, QUIC.

Details in **Ports, TCP and UDP**.

</En>
<Ur>

Server bohot se programs chalata hai; sirf IP address nahi batata ke data kis ko mile. Layer 4 **ports** se sahi **program** tak pohanchati hai.

- **TCP:** connection, tasdeeq, dobara bhejna, tarteeb. Web, SSH, databases ke liye.
- **UDP:** bas bhej do, koi zamanat nahi, bohot tez. DNS, video calls, games, QUIC ke liye.

Tafseel **Ports, TCP and UDP** me.

</Ur>
</Tr>

</Step>

<Step title="Layers 5–7: Session, Presentation, Application">

<Tr>
<En>

Everything apps themselves care about: the conversation (session), format and encryption (presentation), and meaning (application). This is where your code lives: URLs, headers, JSON, cookies, login. In TCP/IP all three are simply "Application". L7 tools understand **content**: nginx, API gateways, WAFs, L7 load balancers.

</En>
<Ur>

Wo sab jis ki apps ko khud parwah hai: guftagu (session), format aur encryption (presentation), aur maani (application). Aap ka code yahin rehta hai: URLs, headers, JSON, cookies, login. TCP/IP me teeno bas "Application" hain. L7 tools **mawad** samajhte hain: nginx, API gateways, WAFs, L7 load balancers.

</Ur>
</Tr>

```bash
cat > l7.mjs <<'EOF'
import http from "node:http";
http.createServer((req, res) => res.end(`layer 7 sees: ${req.method} ${req.url} (Host: ${req.headers.host})\n`)).listen(3460, "127.0.0.1");
EOF
node l7.mjs & pid=$!; sleep 0.5
curl -s http://127.0.0.1:3460/api/orders?id=7
kill $pid
```

```text output
layer 7 sees: GET /api/orders?id=7 (Host: 127.0.0.1:3460)
```

<Happened>
<Tr>
<En>A **layer 4** device would only have seen "TCP to 127.0.0.1 port 3460", not the method, path or host name. That's why path-based routing (`/api` → API servers, `/` → web servers) needs a **layer 7** load balancer.</En>
<Ur>**Layer 4** device sirf "TCP to 127.0.0.1 port 3460" dekhta, method, path ya host ka naam nahi. Isi liye path ke hisaab se routing (`/api` → API servers, `/` → web servers) ko **layer 7** load balancer chahiye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Which device works at which layer?">

<Tr>
<En>

Devices are often named by the highest layer they understand, which tells you what they can see and decide on.

| Device / service | Layer | Decides using |
| --- | --- | --- |
| Hub, repeater | 1 | Nothing, just repeats signals |
| Switch | 2 | MAC addresses |
| Router | 3 | IP addresses |
| Firewall / security group | 3–4 | IPs, ports, protocols |
| L4 load balancer (AWS NLB) | 4 | IP + port |
| L7 load balancer (AWS ALB), reverse proxy (nginx) | 7 | Host, path, headers, cookies |
| WAF (web application firewall) | 7 | Request content (SQL injection, XSS patterns) |

</En>
<Ur>

Devices ka naam aksar us sab se oonchi layer par hota hai jo wo samajhte hain, jo batata hai ke wo kya dekh aur tay kar sakte hain.

| Device / service | Layer | Kis bunyad par faisla |
| --- | --- | --- |
| Hub, repeater | 1 | Kuch nahi, bas signals dohrata hai |
| Switch | 2 | MAC addresses |
| Router | 3 | IP addresses |
| Firewall / security group | 3–4 | IPs, ports, protocols |
| L4 load balancer (AWS NLB) | 4 | IP + port |
| L7 load balancer (AWS ALB), reverse proxy (nginx) | 7 | Host, path, headers, cookies |
| WAF (web application firewall) | 7 | Request ka mawad (SQL injection, XSS patterns) |

</Ur>
</Tr>

</Step>

<Step title="Troubleshoot layer by layer">

<Tr>
<En>

Random guessing wastes time; layers give you a checklist:

- **L1–2:** interface up? `ip link`
- **L3:** IP and route? reachable? `ip addr`, `ping`, `traceroute`
- **L4:** port open? `nc -zv host 443`, `ss -ltn`
- **L7:** correct answer? `curl -v`
- **DNS** sits in between: does the name resolve? `dig`

</En>
<Ur>

Andaze waqt zaya karte hain; layers checklist deti hain:

- **L1–2:** interface chal raha? `ip link`
- **L3:** IP aur raasta? pohanch hai? `ip addr`, `ping`, `traceroute`
- **L4:** port khula? `nc -zv host 443`, `ss -ltn`
- **L7:** sahi jawab? `curl -v`
- **DNS** beech me hai: naam resolve hota hai? `dig`

</Ur>
</Tr>

```bash
python3 -m http.server 3461 --bind 127.0.0.1 > /dev/null 2>&1 & pid=$!; sleep 1
echo "L3 (IP reachable):  $(ping -c1 -W1 127.0.0.1 > /dev/null 2>&1 && echo OK || echo 'no ICMP here (try L4)')" | sed -E 's/:  (OK|no ICMP.*)$/:  OK or blocked/'
echo "L4 (port open):     $(nc -z 127.0.0.1 3461 2>/dev/null && echo OK)"
echo "L4 (closed port):   $(nc -z 127.0.0.1 3999 2>/dev/null || echo 'refused — nothing listening')"
echo "L7 (HTTP answer):   $(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3461/)"
kill $pid
```

```text output
L3 (IP reachable):  OK or blocked
L4 (port open):     OK
L4 (closed port):   refused — nothing listening
L7 (HTTP answer):   200
```

<Happened>
<Tr>
<En>Many networks and cloud firewalls block `ping`, so a failed ping doesn't prove a server is down. Always also test the actual port.</En>
<Ur>Kai networks aur cloud firewalls `ping` band rakhte hain, isliye fail ping saabit nahi karta ke server band hai. Hamesha asal port bhi test karein.</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Ping fails, so the server is down">

```text
$ ping shop.example.com
100% packet loss          → "the server is dead!"
```

</Bad>
<Good title="Test the real port and the app">

```text
$ nc -zv shop.example.com 443     → port open
$ curl -sI https://shop.example.com   → HTTP/2 200 (ICMP was just blocked)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Memorising layer names without meaning**: know what each layer does and which problems belong to it.
- **Confusing MAC and IP**: MAC is local (layer 2, changes every hop); IP is end-to-end (layer 3).
- **Thinking a port firewall can block SQL injection**: that's layer 7 content; you need input validation and/or a WAF.
- **Mixing up L4 and L7 load balancers**: only L7 can route by URL path or host name, or look inside HTTP headers.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Maani ke baghair layers ke naam ratna**: jaanein har layer kya karti hai aur kaunse masle us ke hain.
- **MAC aur IP me ulajhna**: MAC local hai (layer 2, har hop par badalta hai); IP shuru se aakhir tak (layer 3).
- **Samajhna ke port firewall SQL injection rok sakta hai**: ye layer 7 ka mawad hai; input validation aur/ya WAF chahiye.
- **L4 aur L7 load balancers me ulajhna**: sirf L7 URL path ya host ke naam se route kar sakta hai, ya HTTP headers ke andar dekh sakta hai.

</Ur>
</Tr>

## Try it yourself

<Challenge title="See the layers on your own machine">

<Tr>
<En>
Look at layers 2–3 (your interfaces and IPs), layer 4 (who is listening), and layer 7 (real request and response lines). Your names, IPs and services will differ. In `curl -v`, `>` lines are what you **sent** and `<` lines are what you **received**.
</En>
<Ur>
Layer 2–3 (aap ke interfaces aur IPs), layer 4 (kaun sun raha hai), aur layer 7 (asli request aur response lines) dekhein. Aap ke naam, IPs aur services alag honge. `curl -v` me `>` lines wo hain jo aap ne **bheja** aur `<` lines wo jo aap ko **mila**.
</Ur>
</Tr>

```bash
# 1. Your interfaces and addresses (layers 2 and 3)
ip -br addr | awk '{print $1, $3}' | head -3

# 2. Who is listening on this machine (layer 4)
ss -ltn | awk 'NR==1 || /LISTEN/' | head -5 | awk '{print $1, $4}'

# 3. Layer 7: see the request and response headers of a local server
python3 -m http.server 3462 --bind 127.0.0.1 > /dev/null 2>&1 & pid=$!; sleep 1
curl -sv http://127.0.0.1:3462/ -o /dev/null 2>&1 | grep -E '^(> GET|< HTTP)' | tr -d '\r'
kill $pid
```

<En>Example output:</En>
<Ur>Misaali output:</Ur>

eth0 <your IP>/<prefix>
State Local
LISTEN <address:port of a listening service>
> GET / HTTP/1.1
< HTTP/1.0 200 OK

<DeepDive title="Real world: 'the shop website is down'">

The on-call engineer works up the layers:

```text
$ dig +short shop.example.com            # name resolution
203.0.113.10                             ✓ DNS fine

$ ping -c 2 203.0.113.10                 # L3
2 packets transmitted, 2 received        ✓ server reachable

$ nc -zv 203.0.113.10 443                # L4
Connection to 203.0.113.10 443 port [tcp/https] succeeded!   ✓ port open (nginx is up)

$ curl -sI https://shop.example.com      # L7
HTTP/2 502                               ✗ Bad Gateway
```

Layers 3 and 4 are fine; layer 7 returns **502**, which means nginx is running but **the app behind it** isn't answering. Next step: `systemctl status shop` and `journalctl -u shop` on the server: the Node.js process had crashed. Ten minutes instead of an hour of guessing.

</DeepDive>

<DeepDive title="Security lens">

Attackers and defenders think in layers too. Each layer needs its own protection: "defence in depth".

| Layer | Example attack | Example defence |
| --- | --- | --- |
| 1 Physical | Cable tapping, stolen hardware | Locked data centres, encryption |
| 2 Data Link | ARP spoofing, rogue Wi-Fi | Switch security, WPA3, 802.1X |
| 3 Network | IP spoofing, ICMP floods | Firewalls, anti-spoofing filters |
| 4 Transport | SYN floods, port scanning | SYN cookies, rate limits, closing ports |
| 6 Presentation | Weak TLS, downgrade attacks | TLS 1.2+/1.3 only, HSTS |
| 7 Application | SQL injection, XSS, credential stuffing | Input validation, WAF, MFA, rate limiting |

DDoS attacks are also classified by layer: **volumetric / L3–4** (flooding bandwidth or connections) vs **L7** (expensive HTTP requests that look legitimate).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the layers of the OSI model?">
From bottom to top: 1 Physical (signals on cables or radio), 2 Data Link (frames and MAC addresses on the local network), 3 Network (IP addressing and routing between networks), 4 Transport (TCP and UDP, ports, reliability), 5 Session (managing conversations), 6 Presentation (formats, encoding and encryption such as TLS), 7 Application (protocols like HTTP, DNS and SSH).
</QA>

<QA q="What is the difference between the OSI and TCP/IP models?">
OSI is a 7-layer reference model used to describe and discuss networking. TCP/IP is the 4-layer model the internet actually implements: Link (OSI 1–2), Internet (OSI 3), Transport (OSI 4) and Application (OSI 5–7). People still use OSI layer numbers, such as L4 or L7, to describe devices and services.
</QA>

<QA q="What is encapsulation?">
As data goes down the stack, each layer adds its own header around the data from the layer above: the transport layer adds a TCP or UDP header to make a segment, the internet layer adds an IP header to make a packet, and the link layer adds an Ethernet or Wi-Fi header and trailer to make a frame. The receiver removes the headers in reverse order.
</QA>

<QA q="What is the difference between a layer 4 and a layer 7 load balancer?">
A layer 4 load balancer forwards TCP or UDP connections based on IP addresses and ports without looking at the content, which makes it fast and protocol-agnostic. A layer 7 load balancer understands the application protocol, usually HTTP, so it can route by host name, path, headers or cookies, terminate TLS and modify requests.
</QA>

</DeepDive>
