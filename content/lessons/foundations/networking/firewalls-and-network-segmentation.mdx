<Callout type="tip" title="In one minute">
A **firewall** decides which network traffic is allowed, using **rules**: *from* (source IP/range), *to* (destination), *protocol/port*, and *action* (allow/deny). Good firewalls **deny everything by default** and allow only what is needed. **Stateful** firewalls remember connections, so replies to allowed traffic are let back in automatically. Control both **inbound** and **outbound (egress)** traffic. On servers use **ufw/nftables**; in the cloud use **security groups** (stateful, per resource) and **network ACLs** (stateless, per subnet). **Segmentation** splits the network into zones (public, app, data, admin) with strict rules between them — limiting how far an attacker can move.
</Callout>

## Start from zero

### Deciding who gets in

Every server answers on some ports. A firewall sits on the path and checks every connection against a list of rules before it reaches the service — the network's security guard.

<Callout type="analogy">
A **gated housing society**. The **guard at the gate** (perimeter firewall) checks every car: residents allowed, delivery vans only to the market area, unknown cars refused. Inside, each **house has its own locked door** (host firewall), and the **server room** of the society office has a separate, stricter door (segmentation). A thief who sneaks past the main gate still faces locked doors everywhere — that is **defence in depth**.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Firewall** | Filters network traffic by rules | ufw, AWS security group |
| **Rule** | Match conditions + action | allow TCP 443 from anywhere |
| **Default policy** | What happens if no rule matches | deny |
| **Inbound / ingress** | Traffic coming in | users → web server |
| **Outbound / egress** | Traffic going out | server → internet |
| **Stateful** | Remembers connections, allows replies automatically | security groups |
| **Stateless** | Checks every packet alone, replies need their own rules | network ACLs |
| **Segmentation** | Splitting a network into isolated parts | public / app / data subnets |
| **WAF** | Web Application Firewall — inspects HTTP content | AWS WAF, Cloudflare WAF |
| **Zero trust** | Never trust by network location; verify every request | |

## What is it?

| Type | Where | Looks at | Examples |
| --- | --- | --- | --- |
| Host firewall | On each server | IP, port, protocol | ufw, firewalld, nftables/iptables, Windows Firewall |
| Network firewall | Between networks | IP, port, protocol, state (some: apps) | pfSense, FortiGate, AWS Network Firewall |
| Cloud security group | Attached to an instance/ENI | IP/port, other security groups | AWS SG, Azure NSG |
| Cloud network ACL | On a subnet | IP/port, stateless | AWS NACL |
| WAF | In front of web apps (L7) | HTTP requests and content | AWS WAF, Cloudflare, ModSecurity |
| Kubernetes NetworkPolicy | Between pods | Pod labels, namespaces, ports | Calico, Cilium |

## Why does it matter?

- **Exposed services are the #1 entry point:** databases, Redis, Elasticsearch, admin panels and RDP open to the internet are found by scanners within hours.
- **Containment:** if one web server is hacked, segmentation stops the attacker from reaching the database or other systems (lateral movement).
- **Compliance:** PCI DSS, ISO 27001 and SOC 2 require documented firewall rules and segmentation.
- **Cloud jobs:** writing and reviewing security groups is daily work for DevOps and cloud security engineers.

## When and where do you use it?

| Layer | Rule example |
| --- | --- |
| Cloud SG for the load balancer | Allow TCP 443 (and 80) from `0.0.0.0/0` |
| Cloud SG for app servers | Allow TCP 3000 **from the load balancer's SG** only |
| Cloud SG for the database | Allow TCP 5432 **from the app SG** only |
| Host firewall (ufw) | Default deny incoming; allow 22 from office IP, 80/443 |
| Egress | App servers may reach `api.stripe.com:443` and package mirrors only |
| WAF | Block SQL-injection patterns, rate-limit `/login` |

## Concepts one by one

### 1. Rules and first-match evaluation

<Explain>
<What>
A rule matches packets by fields (source, destination, protocol, port) and applies an action. Many firewalls check rules **in order** and use the **first** match; if nothing matches, the **default policy** applies.
</What>
<Why>
Rule order and the default policy decide what really happens — a broad "allow" above a specific "deny" makes the deny useless.
</Why>
<When>
Writing and reviewing any firewall.
</When>
<Where>
iptables/nftables chains, network ACLs (numbered rules), most network firewalls. (Security groups are different: they only contain **allow** rules, all evaluated together.)
</Where>
<How>
Put specific rules first, broad rules later, and **deny by default**.
</How>
</Explain>

```python
import ipaddress
rules = [  # (action, protocol, port, source)
    ("deny",  "tcp", 22,   "198.51.100.0/24"),   # known bad range
    ("allow", "tcp", 22,   "203.0.113.5/32"),    # admin's office IP
    ("allow", "tcp", 443,  "0.0.0.0/0"),         # website for everyone
    ("allow", "tcp", 5432, "10.0.11.0/24"),      # DB only from the app subnet
]
DEFAULT = "deny"
def decide(proto, port, src):
    for i, (action, p, prt, net) in enumerate(rules, 1):
        if p == proto and prt == port and ipaddress.ip_address(src) in ipaddress.ip_network(net):
            return f"{action.upper():5} (rule {i})"
    return f"{DEFAULT.upper():5} (default policy)"
tests = [("tcp", 443, "8.8.4.4"), ("tcp", 22, "203.0.113.5"), ("tcp", 22, "8.8.4.4"),
         ("tcp", 22, "198.51.100.7"), ("tcp", 5432, "10.0.11.20"), ("tcp", 5432, "8.8.4.4"), ("udp", 53, "8.8.4.4")]
for t in tests:
    print(f"{t[0]}/{t[1]:<5} from {t[2]:<13} → {decide(*t)}")
```

```text output
tcp/443   from 8.8.4.4       → ALLOW (rule 3)
tcp/22    from 203.0.113.5   → ALLOW (rule 2)
tcp/22    from 8.8.4.4       → DENY  (default policy)
tcp/22    from 198.51.100.7  → DENY  (rule 1)
tcp/5432  from 10.0.11.20    → ALLOW (rule 4)
tcp/5432  from 8.8.4.4       → DENY  (default policy)
udp/53    from 8.8.4.4       → DENY  (default policy)
```

Everything not explicitly allowed was denied — that is **default deny**.

### 2. Default deny (allow-list)

<Explain>
<What>
Block all traffic unless a rule specifically allows it.
</What>
<Why>
New services, forgotten test servers and mistakes are closed automatically. "Default allow + block the bad stuff" always misses something.
</Why>
<When>
Every firewall, both directions where possible.
</When>
<Where>
ufw (`default deny incoming`), security groups (deny is implicit), Kubernetes (a default-deny NetworkPolicy per namespace).
</Where>
<How>
Start from nothing; add one rule per real need, with the narrowest source and port. Document why each rule exists.
</How>
</Explain>

### 3. Stateful vs stateless

<Explain>
<What>
A **stateful** firewall tracks connections: if an outgoing request was allowed, the reply is automatically allowed back. A **stateless** one judges every packet alone, so replies need their own rules (often for the ephemeral port range 1024–65535).
</What>
<Why>
Stateful rules are simpler and safer. Stateless filters are fast and useful as a coarse extra layer.
</Why>
<When>
Choosing and writing cloud rules.
</When>
<Where>
Security groups, ufw, nftables with `ct state` = stateful. AWS **network ACLs** = stateless.
</Where>
<How>
With NACLs, remember to allow return traffic to ephemeral ports in the opposite direction, or connections hang.
</How>
</Explain>

```python
state_table = set()
def outbound(src, sport, dst, dport):
    state_table.add((dst, dport, src, sport))         # remember the expected reply
    print(f"OUT {src}:{sport} → {dst}:{dport}  allowed, connection remembered")
def inbound_stateful(src, sport, dst, dport):
    ok = (src, sport, dst, dport) in state_table
    print(f"IN  {src}:{sport} → {dst}:{dport}  stateful: {'ALLOW (reply to known connection)' if ok else 'DENY (unsolicited)'}")
outbound("10.0.11.20", 51522, "93.184.216.34", 443)
inbound_stateful("93.184.216.34", 443, "10.0.11.20", 51522)
inbound_stateful("198.51.100.9", 443, "10.0.11.20", 51522)
```

```text output
OUT 10.0.11.20:51522 → 93.184.216.34:443  allowed, connection remembered
IN  93.184.216.34:443 → 10.0.11.20:51522  stateful: ALLOW (reply to known connection)
IN  198.51.100.9:443 → 10.0.11.20:51522  stateful: DENY (unsolicited)
```

### 4. Host firewalls: ufw and nftables

<Explain>
<What>
Firewalls running on the server itself. On Linux, the kernel's **netfilter** does the filtering; **nftables** (newer) or **iptables** (older) configure it; **ufw** (Ubuntu) and **firewalld** (RHEL) are friendlier front-ends.
</What>
<Why>
A last line of defence on each machine, even inside a "trusted" network or if the cloud rules are misconfigured.
</Why>
<When>
Every server, especially VPS hosts without cloud security groups.
</When>
<Where>
`ufw status`, `firewall-cmd --list-all`, `nft list ruleset`.
</Where>
<How>
Allow SSH **before** enabling the firewall. Remember Docker's published ports can bypass ufw.
</How>
</Explain>

```text
$ sudo ufw default deny incoming
$ sudo ufw default allow outgoing
$ sudo ufw allow from 203.0.113.5 to any port 22 proto tcp
$ sudo ufw allow 443/tcp
$ sudo ufw enable
$ sudo ufw status numbered
     To                         Action      From
[ 1] 22/tcp                     ALLOW IN    203.0.113.5
[ 2] 443/tcp                    ALLOW IN    Anywhere

# The same idea in nftables:
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;          # default deny
    ct state established,related accept                      # stateful: replies
    iif "lo" accept
    ip saddr 203.0.113.5 tcp dport 22 accept
    tcp dport 443 accept
  }
}
```

### 5. Cloud security groups

<Explain>
<What>
Virtual, stateful firewalls attached to cloud resources (EC2 instances, load balancers, RDS, Lambda in a VPC). They contain only **allow** rules; everything else is denied.
</What>
<Why>
The main network control in AWS (Azure: NSGs, GCP: firewall rules). Fine-grained and easy to automate with Terraform.
</Why>
<When>
Every cloud resource with a network interface.
</When>
<Where>
AWS console / Terraform `aws_security_group`.
</Where>
<How>
Reference **other security groups** as sources instead of IP ranges: "allow 5432 from `sg-app`" keeps working as app servers scale and change IPs.
</How>
</Explain>

```text
sg-alb      inbound:  443 from 0.0.0.0/0, 80 from 0.0.0.0/0
            outbound: 3000 to sg-app
sg-app      inbound:  3000 from sg-alb                  ← only the load balancer can reach the app
            outbound: 5432 to sg-db, 443 to 0.0.0.0/0 (external APIs, via NAT)
sg-db       inbound:  5432 from sg-app                  ← only app servers can reach the database
            outbound: none needed (stateful replies are automatic)
```

### 6. Network ACLs: a second, coarse layer

<Explain>
<What>
Stateless, numbered allow **and** deny rules on a whole **subnet**, evaluated in order.
</What>
<Why>
A safety net at subnet level and a way to block specific IP ranges quickly (security groups cannot deny).
</Why>
<When>
Blocking a known bad range, extra isolation for data subnets, compliance.
</When>
<Where>
AWS NACLs (Azure NSGs can sit on subnets too).
</Where>
<How>
Because they are stateless, allow **return traffic** on ephemeral ports (1024–65535). Most teams keep NACLs simple and do fine-grained work in security groups.
</How>
</Explain>

| | Security group | Network ACL |
| --- | --- | --- |
| Applies to | A resource (network interface) | A subnet |
| State | Stateful | Stateless |
| Rules | Allow only | Allow and deny |
| Evaluation | All rules together | In number order, first match |
| Typical use | Main access control | Coarse guard rails, quick blocks |

### 7. Egress (outbound) filtering

<Explain>
<What>
Rules limiting where your servers may connect **out** to.
</What>
<Why>
After a break-in, malware calls home, downloads tools and sends stolen data out. Strict egress makes all of that harder and noisier. Many teams forget egress entirely ("allow all outbound").
</Why>
<When>
Production servers, especially those holding sensitive data.
</When>
<Where>
Security group outbound rules, egress proxies, AWS Network Firewall (domain allow-lists), Kubernetes egress policies.
</Where>
<How>
Allow only required destinations (payment API, package mirrors, monitoring) and DNS; log and alert on denied outbound attempts.
</How>
</Explain>

### 8. Network segmentation and zones

<Explain>
<What>
Splitting a network into zones by trust and function, with firewalls deciding what may cross between them.
</What>
<Why>
**Blast radius**: one compromised machine should not give access to everything. Flat networks let attackers move from a printer to the domain controller.
</Why>
<When>
Designing any network: office, data centre, cloud, Kubernetes.
</When>
<Where>
VLANs (office), subnets + security groups (cloud), namespaces + NetworkPolicies (Kubernetes), separate cloud accounts per environment.
</Where>
<How>
Group by sensitivity (public, application, data, management), allow only the specific flows between them, and keep production separate from development.
</How>
</Explain>

```text
           Internet
               │ 443
     ┌─────────▼─────────┐  PUBLIC ZONE (DMZ)
     │ load balancer/WAF │
     └─────────┬─────────┘
               │ 3000 (only from LB)
     ┌─────────▼─────────┐  APP ZONE
     │    app servers    │──► egress: payment API 443 only
     └─────────┬─────────┘
               │ 5432 (only from app)
     ┌─────────▼─────────┐  DATA ZONE (no internet route)
     │     database      │
     └───────────────────┘
     ┌───────────────────┐  MANAGEMENT ZONE
     │ bastion / SSM, CI │──► SSH/admin to the others, from VPN only
     └───────────────────┘
```

### 9. WAF: a firewall for HTTP

<Explain>
<What>
A Web Application Firewall inspects HTTP requests (paths, headers, bodies) and blocks malicious patterns: SQL injection, XSS, path traversal, bad bots, and floods.
</What>
<Why>
Network firewalls allow port 443 for everyone — they cannot see attacks **inside** allowed HTTPS traffic.
</Why>
<When>
Public web apps and APIs, especially with legacy code or compliance needs.
</When>
<Where>
AWS WAF on ALB/CloudFront, Cloudflare WAF, Azure Front Door, ModSecurity/Coraza with nginx.
</Where>
<How>
Start with managed rule sets (OWASP Core Rule Set) in **count/log** mode, tune false positives, then block. A WAF **adds** protection; it does not replace secure code.
</How>
</Explain>

```python
import re
patterns = {"SQL injection": r"('|%27)\s*(or|union|--)", "path traversal": r"\.\./", "XSS": r"<script"}
for req in ["/products?id=7", "/products?id=7' OR 1=1--", "/download?file=../../etc/passwd", "/search?q=<script>alert(1)</script>"]:
    hit = next((name for name, p in patterns.items() if re.search(p, req, re.I)), None)
    print(f"{'BLOCK' if hit else 'allow'}  {req:<40} {('(' + hit + ')') if hit else ''}")
```

```text output
allow  /products?id=7                           
BLOCK  /products?id=7' OR 1=1--                 (SQL injection)
BLOCK  /download?file=../../etc/passwd          (path traversal)
BLOCK  /search?q=<script>alert(1)</script>      (XSS)
```

Real WAF rules are far more sophisticated — and attackers constantly find encodings that slip past them, which is why the application itself must still use parameterised queries and output encoding.

### 10. Zero trust

<Explain>
<What>
A security model that does not trust any request just because it comes from "inside" the network. Every request is authenticated, authorised and encrypted.
</What>
<Why>
Perimeters leak (VPNs, cloud, remote work, compromised laptops). Segmentation plus identity checks everywhere limits damage.
</Why>
<When>
Modern architectures, remote-first companies, microservices.
</When>
<Where>
Identity-aware proxies (Cloudflare Access, Google IAP, Tailscale), mTLS between services, short-lived credentials.
</Where>
<How>
Combine strong identity (SSO + MFA), device checks, least-privilege access per application, and encryption — firewalls remain one layer among several.
</How>
</Explain>

## Hands-on

```bash
# Audit a list of cloud rules for dangerous exposure
cat > rules.csv <<'EOF'
sg-web,tcp,443,0.0.0.0/0
sg-web,tcp,80,0.0.0.0/0
sg-admin,tcp,22,0.0.0.0/0
sg-db,tcp,5432,10.0.11.0/24
sg-cache,tcp,6379,0.0.0.0/0
sg-legacy,tcp,0-65535,0.0.0.0/0
EOF
while IFS=, read -r sg proto port src; do
  if [[ $src == 0.0.0.0/0 && ! $port =~ ^(80|443)$ ]]; then
    echo "RISK  $sg: $proto/$port open to the whole internet"
  fi
done < rules.csv
```

```text output
RISK  sg-admin: tcp/22 open to the whole internet
RISK  sg-cache: tcp/6379 open to the whole internet
RISK  sg-legacy: tcp/0-65535 open to the whole internet
```

This tiny check is the heart of real tools (AWS Config rules, Security Hub, Prowler, ScoutSuite) that flag world-open security groups.

## Real-world example

**The flat network breach.** A company ran its web server, database and file shares in one subnet with "allow all traffic within the VPC". An outdated WordPress plugin gave an attacker a shell on the web server; from there they connected straight to the database (5432 open to the whole VPC) and exported customer data.

The redesign:

```text
1. Subnets per tier: public (ALB), app, data (no internet route), management.
2. Security groups referencing each other: ALB → app:3000 → db:5432. Nothing else.
3. SSH removed from all instances; admin access via SSM Session Manager with MFA.
4. Egress: app servers may reach only the payment API, OS mirrors and the monitoring service.
5. WAF with managed rules in front of the ALB; plugin patching automated.
6. VPC Flow Logs + alerts on rejected traffic from the app tier to unexpected ports.
```

Now a compromised web server can reach almost nothing — and any attempt shows up in the logs.

## Common mistakes

- **`0.0.0.0/0` on SSH, RDP, databases or caches** — "temporarily".
- **Allow-all inside the network** ("it's internal, it's safe").
- **No egress rules** — compromised servers can talk to anything.
- **Rule sprawl** — hundreds of old rules nobody understands. Review and remove regularly.
- **Locking yourself out** — enabling a host firewall before allowing SSH.
- **Forgetting stateless return traffic** on network ACLs.
- **Thinking a WAF fixes vulnerable code.**

## Security lens

<Callout type="security">
Firewalls are not a wall around a castle; they are many doors inside the building. Assume something will get in, and make sure it cannot go far.
</Callout>

- **Least privilege for networks:** narrowest source, narrowest port, per tier.
- **Log what is denied:** VPC Flow Logs, firewall logs and WAF logs reveal scans, misconfigurations and lateral-movement attempts.
- **Infrastructure as code** (Terraform) for firewall rules: reviewed in pull requests, scanned automatically (Checkov, tfsec) before deployment.
- **Continuous auditing:** tools like Prowler, AWS Config and Security Hub flag world-open ports and unused rules.
- **Microsegmentation** (Kubernetes NetworkPolicies, service meshes) brings the same idea down to individual services.

## Interview questions

<QA q="What is the difference between a stateful and a stateless firewall?">
A stateful firewall tracks connections, so once an outbound or inbound connection is allowed, its return traffic is automatically permitted. A stateless firewall evaluates every packet independently, so return traffic must be explicitly allowed, typically on the ephemeral port range. AWS security groups are stateful; network ACLs are stateless.
</QA>

<QA q="What is the difference between a security group and a network ACL in AWS?">
A security group is attached to individual resources, is stateful and contains only allow rules that are evaluated together. A network ACL is attached to a subnet, is stateless and has numbered allow and deny rules evaluated in order. Security groups are the primary access control; NACLs act as a coarse, subnet-level safety net.
</QA>

<QA q="Why is network segmentation important?">
It limits the blast radius of a compromise. By separating systems into zones such as public, application, data and management, and allowing only specific flows between them, an attacker who compromises one system cannot freely reach databases or other sensitive systems, and lateral movement attempts become visible in logs.
</QA>

<QA q="Why should you control outbound traffic?">
Compromised systems use outbound connections to download tools, contact command-and-control servers and exfiltrate data. Restricting egress to known required destinations makes these steps harder and generates alerts, and it also prevents accidental data leaks to unapproved services.
</QA>

<QA q="What does a WAF protect against that a network firewall does not?">
A network firewall filters by IP, port and protocol, so it allows all traffic to an open web port. A web application firewall inspects HTTP requests themselves and can block malicious content such as SQL injection, cross-site scripting and path traversal patterns, abusive bots and request floods. It complements, but does not replace, secure application code.
</QA>
