<BigIdea>
<Tr>
<En>
A **firewall** decides which traffic is allowed using **rules**: *from where*, *to where*, *which port*, and *allow or deny*. Good firewalls **deny everything by default** and allow only what's needed, in **both** directions. **Segmentation** splits a network into zones (public, app, data, admin) with strict rules between them, so if one machine is hacked, the attacker can't reach everything else.
</En>
<Ur>
**Firewall** **rules** ke zariye tay karta hai kaunsa traffic jaiz hai: *kahan se*, *kahan tak*, *kaunsa port*, aur *ijazat ya inkaar*. Achhe firewalls **pehle se sab kuch band** rakhte hain aur sirf zaroori cheez kholte hain, **dono** simton me. **Segmentation** network ko zones (public, app, data, admin) me baant deti hai jin ke darmiyan sakht rules hon, taa ke ek machine hack ho jaye to hamla awar baqi sab tak na pohanch sake.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Every server answers on some ports. A firewall sits on the path and checks every connection against its rules before it reaches the service: the network's security guard.

| Type | Where | Looks at | Examples |
| --- | --- | --- | --- |
| Host firewall | On each server | IP, port, protocol | ufw, firewalld, nftables/iptables, Windows Firewall |
| Network firewall | Between networks | IP, port, protocol, state | pfSense, FortiGate, AWS Network Firewall |
| Cloud security group | On an instance/interface | IP/port, other security groups | AWS SG, Azure NSG |
| Cloud network ACL | On a subnet | IP/port, stateless | AWS NACL |
| WAF | In front of web apps (L7) | HTTP requests and content | AWS WAF, Cloudflare, ModSecurity |
| Kubernetes NetworkPolicy | Between pods | Labels, namespaces, ports | Calico, Cilium |

</En>
<Ur>

Har server kuch ports par jawab deta hai. Firewall raaste me baith kar har connection ko service tak pohanchne se pehle apne rules se check karta hai: network ka chowkidaar.

| Qism | Kahan | Kya dekhta hai | Misaalen |
| --- | --- | --- | --- |
| Host firewall | Har server par | IP, port, protocol | ufw, firewalld, nftables/iptables, Windows Firewall |
| Network firewall | Networks ke darmiyan | IP, port, protocol, state | pfSense, FortiGate, AWS Network Firewall |
| Cloud security group | Instance/interface par | IP/port, doosre security groups | AWS SG, Azure NSG |
| Cloud network ACL | Subnet par | IP/port, stateless | AWS NACL |
| WAF | Web apps ke saamne (L7) | HTTP requests aur mawad | AWS WAF, Cloudflare, ModSecurity |
| Kubernetes NetworkPolicy | Pods ke darmiyan | Labels, namespaces, ports | Calico, Cilium |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Exposed services are the #1 way in:** databases, Redis, Elasticsearch, admin panels and RDP open to the internet are found by scanners within hours.
- **Containment:** if one web server is hacked, segmentation stops the attacker moving to the database (lateral movement).
- **Compliance:** PCI DSS, ISO 27001 and SOC 2 require documented rules and segmentation.
- **Cloud jobs:** writing and reviewing security groups is daily work for DevOps and cloud security engineers.

</En>
<Ur>

- **Khuli services andar aane ka sab se bara raasta:** internet par khule databases, Redis, Elasticsearch, admin panels aur RDP scanners ghanton me dhoond lete hain.
- **Rok thaam:** ek web server hack ho to segmentation hamla awar ko database tak jane se rokti hai (lateral movement).
- **Qawaneen:** PCI DSS, ISO 27001 aur SOC 2 likhe hue rules aur segmentation maangte hain.
- **Cloud naukriyan:** security groups likhna aur review karna DevOps aur cloud security engineers ka rozana kaam hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Layer | Rule example |
| --- | --- |
| Cloud SG for the load balancer | Allow TCP 443 (and 80) from `0.0.0.0/0` |
| Cloud SG for app servers | Allow TCP 3000 **from the load balancer's SG** only |
| Cloud SG for the database | Allow TCP 5432 **from the app SG** only |
| Host firewall (ufw) | Default deny incoming; allow 22 from office IP, 80/443 |
| Egress | App servers may reach `api.stripe.com:443` and package mirrors only |
| WAF | Block SQL-injection patterns, rate-limit `/login` |

</En>

| Teh | Rule ki misaal |
| --- | --- |
| Load balancer ka cloud SG | `0.0.0.0/0` se TCP 443 (aur 80) |
| App servers ka cloud SG | Sirf **load balancer ke SG** se TCP 3000 |
| Database ka cloud SG | Sirf **app SG** se TCP 5432 |
| Host firewall (ufw) | Andar aana pehle se band; office IP se 22, aur 80/443 |
| Egress | App servers sirf `api.stripe.com:443` aur package mirrors tak |
| WAF | SQL-injection patterns band, `/login` par had |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Start from **nothing allowed**, then add one rule per real need with the narrowest source and port, and write down why each rule exists.

**Kuch bhi allow nahi** se shuru karein, phir har asli zaroorat ke liye sab se tang source aur port ke saath ek rule jorein, aur likhein ke har rule kyun hai.

## Picture it

<Tr>
<En>

A **gated community**. The **guard at the gate** (perimeter firewall) checks every car: residents allowed, delivery vans only to the shops, unknown cars refused. Inside, each **house has its own locked door** (host firewall), and the office's **server room** has a separate, stricter door (segmentation). A thief who sneaks past the main gate still faces locked doors everywhere: that's **defence in depth**.

</En>
<Ur>

Ek **gated community**. **Gate ka chowkidaar** (perimeter firewall) har gaari check karta hai: rehne walon ko ijazat, delivery vans sirf dukaanon tak, anjaan gaariyan wapas. Andar har **ghar ka apna band darwaza** (host firewall) hai, aur office ke **server room** ka alag, zyada sakht darwaza (segmentation). Bara gate paar karne wale chor ke saamne bhi har jagah band darwaze hain: yahi **defence in depth** hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Rules and first-match evaluation">

<Tr>
<En>

A rule matches packets by fields (source, destination, protocol, port) and applies an action. Many firewalls check rules **in order** and use the **first** match; if nothing matches, the **default policy** applies. So a broad "allow" above a specific "deny" makes the deny useless: put specific rules first. (Security groups differ: allow-only rules, all checked together.)

</En>
<Ur>

Rule packets ko fields (source, destination, protocol, port) se milata hai aur kaam karta hai. Kai firewalls rules **tarteeb se** check karte hain aur **pehla** milne wala istemal karte hain; koi na mile to **default policy** lagti hai. Isliye khaas "deny" se ooper aam "allow" deny ko bekaar kar deta hai: khaas rules pehle rakhein. (Security groups alag hain: sirf allow rules, sab ek saath check.)

</Ur>
</Tr>

```python
import ipaddress
rules = [  # (action, protocol, port, source)
    ("deny",  "tcp", 22,   "198.51.100.0/24"),   # known bad range
    ("allow", "tcp", 22,   "203.0.113.5/32"),    # admin's office IP
    ("allow", "tcp", 443,  "0.0.0.0/0"),         # website for everyone
    ("allow", "tcp", 5432, "10.0.11.0/24"),      # DB only from the app subnet
]
DEFAULT = "deny"
def decide(proto, port, src):
    for i, (action, p, prt, net) in enumerate(rules, 1):
        if p == proto and prt == port and ipaddress.ip_address(src) in ipaddress.ip_network(net):
            return f"{action.upper():5} (rule {i})"
    return f"{DEFAULT.upper():5} (default policy)"
tests = [("tcp", 443, "8.8.4.4"), ("tcp", 22, "203.0.113.5"), ("tcp", 22, "8.8.4.4"),
         ("tcp", 22, "198.51.100.7"), ("tcp", 5432, "10.0.11.20"), ("tcp", 5432, "8.8.4.4"), ("udp", 53, "8.8.4.4")]
for t in tests:
    print(f"{t[0]}/{t[1]:<5} from {t[2]:<13} → {decide(*t)}")
```

```text output
tcp/443   from 8.8.4.4       → ALLOW (rule 3)
tcp/22    from 203.0.113.5   → ALLOW (rule 2)
tcp/22    from 8.8.4.4       → DENY  (default policy)
tcp/22    from 198.51.100.7  → DENY  (rule 1)
tcp/5432  from 10.0.11.20    → ALLOW (rule 4)
tcp/5432  from 8.8.4.4       → DENY  (default policy)
udp/53    from 8.8.4.4       → DENY  (default policy)
```

<Happened>
<Tr>
<En>Everything not explicitly allowed was denied: that's **default deny**.</En>
<Ur>Jo saaf allow nahi tha wo sab deny hua: yahi **default deny** hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Default deny (allow-list)">

<Tr>
<En>

Block everything unless a rule allows it. New services, forgotten test servers and mistakes stay closed automatically. "Default allow, then block the bad stuff" always misses something. In ufw: `default deny incoming`; security groups deny automatically; Kubernetes needs a default-deny NetworkPolicy per namespace.

</En>
<Ur>

Sab kuch band rakhein jab tak koi rule ijazat na de. Naye services, bhoole hue test servers aur ghaltiyan khud band rehti hain. "Pehle sab allow, phir buri cheezen band" hamesha kuch na kuch chhor deta hai. ufw me: `default deny incoming`; security groups khud deny karte hain; Kubernetes ko har namespace me default-deny NetworkPolicy chahiye.

</Ur>
</Tr>

</Step>

<Step title="Stateful vs stateless">

<Tr>
<En>

A **stateful** firewall remembers connections: if a request went out, its reply is allowed back in automatically. A **stateless** one judges every packet alone, so replies need their own rules (often for ports 1024–65535). Stateful is simpler and safer; stateless is a fast, coarse extra layer. Security groups and ufw are stateful; AWS **network ACLs** are stateless.

</En>
<Ur>

**Stateful** firewall connections yaad rakhta hai: request bahar gayi to us ka jawab khud andar aane diya jata hai. **Stateless** har packet alag parakhta hai, isliye jawabon ko apne rules chahiye (aksar ports 1024–65535 ke liye). Stateful aasaan aur mehfooz hai; stateless tez, mota izafi parda hai. Security groups aur ufw stateful hain; AWS **network ACLs** stateless.

</Ur>
</Tr>

```python
state_table = set()
def outbound(src, sport, dst, dport):
    state_table.add((dst, dport, src, sport))         # remember the expected reply
    print(f"OUT {src}:{sport} → {dst}:{dport}  allowed, connection remembered")
def inbound_stateful(src, sport, dst, dport):
    ok = (src, sport, dst, dport) in state_table
    print(f"IN  {src}:{sport} → {dst}:{dport}  stateful: {'ALLOW (reply to known connection)' if ok else 'DENY (unsolicited)'}")
outbound("10.0.11.20", 51522, "93.184.216.34", 443)
inbound_stateful("93.184.216.34", 443, "10.0.11.20", 51522)
inbound_stateful("198.51.100.9", 443, "10.0.11.20", 51522)
```

```text output
OUT 10.0.11.20:51522 → 93.184.216.34:443  allowed, connection remembered
IN  93.184.216.34:443 → 10.0.11.20:51522  stateful: ALLOW (reply to known connection)
IN  198.51.100.9:443 → 10.0.11.20:51522  stateful: DENY (unsolicited)
```

</Step>

<Step title="Host firewalls: ufw and nftables">

<Tr>
<En>

Firewalls on the server itself: a last line of defence even if cloud rules are wrong. On Linux the kernel's **netfilter** filters; **nftables** (newer) or **iptables** (older) configure it; **ufw** (Ubuntu) and **firewalld** (RHEL) are friendlier front-ends. **Allow SSH before enabling** the firewall, and remember Docker's published ports can bypass ufw.

</En>
<Ur>

Server par hi chalne wale firewalls: cloud rules ghalat hon tab bhi aakhri hifazati deewar. Linux par kernel ka **netfilter** filter karta hai; **nftables** (naya) ya **iptables** (purana) use set karte hain; **ufw** (Ubuntu) aur **firewalld** (RHEL) aasaan front-ends hain. Firewall **on karne se pehle SSH allow** karein, aur yaad rakhein ke Docker ke publish ports ufw bypass kar sakte hain.

</Ur>
</Tr>

```text
$ sudo ufw default deny incoming
$ sudo ufw default allow outgoing
$ sudo ufw allow from 203.0.113.5 to any port 22 proto tcp
$ sudo ufw allow 443/tcp
$ sudo ufw enable
$ sudo ufw status numbered
     To                         Action      From
[ 1] 22/tcp                     ALLOW IN    203.0.113.5
[ 2] 443/tcp                    ALLOW IN    Anywhere

# The same idea in nftables:
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;          # default deny
    ct state established,related accept                      # stateful: replies
    iif "lo" accept
    ip saddr 203.0.113.5 tcp dport 22 accept
    tcp dport 443 accept
  }
}
```

</Step>

<Step title="Cloud security groups">

<Tr>
<En>

Virtual, stateful firewalls on cloud resources (EC2, load balancers, RDS, Lambda in a VPC), with **allow** rules only. They're the main network control in AWS (Azure: NSGs, GCP: firewall rules). Best habit: use **other security groups** as sources instead of IP ranges: "allow 5432 from `sg-app`" keeps working as app servers scale and change IPs.

</En>
<Ur>

Cloud resources (EC2, load balancers, RDS, VPC me Lambda) par virtual, stateful firewalls, sirf **allow** rules ke saath. AWS me ye asal network control hain (Azure: NSGs, GCP: firewall rules). Behtareen aadat: IP ranges ke bajaye **doosre security groups** ko source banayen: "`sg-app` se 5432 allow" app servers ke barhne aur IP badalne par bhi chalta rehta hai.

</Ur>
</Tr>

```text
sg-alb      inbound:  443 from 0.0.0.0/0, 80 from 0.0.0.0/0
            outbound: 3000 to sg-app
sg-app      inbound:  3000 from sg-alb                  ← only the load balancer can reach the app
            outbound: 5432 to sg-db, 443 to 0.0.0.0/0 (external APIs, via NAT)
sg-db       inbound:  5432 from sg-app                  ← only app servers can reach the database
            outbound: none needed (stateful replies are automatic)
```

</Step>

<Step title="Network ACLs: a second, coarse layer">

<Tr>
<En>

Stateless, numbered allow **and** deny rules on a whole **subnet**, checked in order. Useful as a subnet-level safety net and for quickly blocking a bad IP range (security groups can't deny). Because they're stateless, allow **return traffic** on ports 1024–65535, or connections hang. Most teams keep NACLs simple.

| | Security group | Network ACL |
| --- | --- | --- |
| Applies to | A resource (network interface) | A subnet |
| State | Stateful | Stateless |
| Rules | Allow only | Allow and deny |
| Evaluation | All rules together | In number order, first match |
| Typical use | Main access control | Coarse guard rails, quick blocks |

</En>
<Ur>

Poore **subnet** par stateless, numbered allow **aur** deny rules, tarteeb se check hote hain. Subnet ki satah par hifazati jaal aur kisi bure IP range ko jaldi band karne ke kaam aate hain (security groups deny nahi kar sakte). Stateless hone ki wajah se ports 1024–65535 par **wapsi ka traffic** allow karein, warna connections atak jate hain. Zyada tar teams NACLs saada rakhti hain.

| | Security group | Network ACL |
| --- | --- | --- |
| Kis par lagta hai | Ek resource (network interface) | Ek subnet |
| State | Stateful | Stateless |
| Rules | Sirf allow | Allow aur deny |
| Jaanch | Saare rules ek saath | Number ki tarteeb se, pehla milne wala |
| Aam istemal | Asal access control | Mote hifazati jangle, jaldi rok |

</Ur>
</Tr>

</Step>

<Step title="Egress (outbound) filtering">

<Tr>
<En>

After a break-in, malware calls home, downloads tools and sends stolen data **out**. Strict outbound rules make all of that harder and noisier, yet many teams leave "allow all outbound". Allow only required destinations (payment API, package mirrors, monitoring) plus DNS, and alert on denied outbound attempts. Tools: security group outbound rules, egress proxies, AWS Network Firewall domain allow-lists, Kubernetes egress policies.

</En>
<Ur>

Hack ke baad malware ghar call karta hai, tools download karta hai aur chori ka data **bahar** bhejta hai. Sakht outbound rules ye sab mushkil aur shor wala bana dete hain, phir bhi kai teams "sab outbound allow" chhor deti hain. Sirf zaroori manzilen (payment API, package mirrors, monitoring) aur DNS allow karein, aur roki gayi outbound koshishon par alert lagayen. Tools: security group outbound rules, egress proxies, AWS Network Firewall domain allow-lists, Kubernetes egress policies.

</Ur>
</Tr>

</Step>

<Step title="Network segmentation and zones">

<Tr>
<En>

Split the network into zones by trust and function, and let firewalls decide what may cross between them. The goal is a small **blast radius**: one compromised machine shouldn't reach everything (in flat networks attackers hop from a printer to the domain controller). Group by sensitivity (public, application, data, management), allow only specific flows, and keep production apart from development.

</En>
<Ur>

Network ko bharose aur kaam ke hisaab se zones me baantein, aur firewalls ko tay karne dein ke un ke darmiyan kya guzre. Maqsad chhota **blast radius** hai: ek hack machine har cheez tak na pohanche (chapte networks me hamla awar printer se domain controller tak kood jate hain). Hassasiyat ke hisaab se group karein (public, application, data, management), sirf khaas raaste kholein, aur production ko development se alag rakhein.

</Ur>
</Tr>

```text
           Internet
               │ 443
     ┌─────────▼─────────┐  PUBLIC ZONE (DMZ)
     │ load balancer/WAF │
     └─────────┬─────────┘
               │ 3000 (only from LB)
     ┌─────────▼─────────┐  APP ZONE
     │    app servers    │──► egress: payment API 443 only
     └─────────┬─────────┘
               │ 5432 (only from app)
     ┌─────────▼─────────┐  DATA ZONE (no internet route)
     │     database      │
     └───────────────────┘
     ┌───────────────────┐  MANAGEMENT ZONE
     │ bastion / SSM, CI │──► SSH/admin to the others, from VPN only
     └───────────────────┘
```

</Step>

<Step title="WAF: a firewall for HTTP">

<Tr>
<En>

Network firewalls allow port 443 for everyone, so they can't see attacks **inside** allowed HTTPS traffic. A **WAF** inspects HTTP requests (paths, headers, bodies) and blocks bad patterns: SQL injection, XSS, path traversal, bad bots, floods. Start with managed rule sets (OWASP Core Rule Set) in **count/log** mode, tune false alarms, then block. A WAF **adds** protection; it doesn't replace secure code.

</En>
<Ur>

Network firewalls port 443 sab ke liye kholte hain, isliye jaiz HTTPS traffic ke **andar** ke hamle nahi dekh sakte. **WAF** HTTP requests (paths, headers, bodies) ko parakhta hai aur bure patterns band karta hai: SQL injection, XSS, path traversal, bure bots, sailaab. Managed rule sets (OWASP Core Rule Set) se **count/log** mode me shuru karein, ghalat alarms theek karein, phir block. WAF hifazat **barhata** hai; mehfooz code ki jagah nahi leta.

</Ur>
</Tr>

```python
import re
patterns = {"SQL injection": r"('|%27)\s*(or|union|--)", "path traversal": r"\.\./", "XSS": r"<script"}
for req in ["/products?id=7", "/products?id=7' OR 1=1--", "/download?file=../../etc/passwd", "/search?q=<script>alert(1)</script>"]:
    hit = next((name for name, p in patterns.items() if re.search(p, req, re.I)), None)
    print(f"{'BLOCK' if hit else 'allow'}  {req:<40} {('(' + hit + ')') if hit else ''}")
```

```text output
allow  /products?id=7                           
BLOCK  /products?id=7' OR 1=1--                 (SQL injection)
BLOCK  /download?file=../../etc/passwd          (path traversal)
BLOCK  /search?q=<script>alert(1)</script>      (XSS)
```

<Happened>
<Tr>
<En>Real WAF rules are far more sophisticated, and attackers keep finding encodings that slip past them. That's why the app itself must still use parameterised queries and output encoding.</En>
<Ur>Asli WAF rules kahin zyada pecheeda hain, aur hamla awar aisi encodings dhoondte rehte hain jo un se nikal jayen. Isi liye app ko khud bhi parameterised queries aur output encoding istemal karni chahiye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Zero trust">

<Tr>
<En>

Don't trust any request just because it comes from "inside" the network: authenticate, authorise and encrypt **every** request. Perimeters leak (VPNs, cloud, remote work, hacked laptops). Combine strong identity (SSO + MFA), device checks, least-privilege access per app, and encryption. Tools: identity-aware proxies (Cloudflare Access, Google IAP, Tailscale), mTLS between services, short-lived credentials. Firewalls stay one layer among several.

</En>
<Ur>

Sirf is liye kisi request par bharosa na karein ke wo network ke "andar" se aayi: **har** request ki pehchan, ijazat aur encryption karein. Hadein leak hoti hain (VPNs, cloud, ghar se kaam, hack laptops). Mazboot pehchan (SSO + MFA), device checks, har app ke liye kam se kam ijazat, aur encryption jorein. Tools: identity-aware proxies (Cloudflare Access, Google IAP, Tailscale), services ke darmiyan mTLS, kam umar credentials. Firewalls kai tehon me se ek teh rehte hain.

</Ur>
</Tr>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Allow-all inside the network">

```text
sg-internal: all traffic from 10.0.0.0/16      # "it's internal, it's safe"
```

</Bad>
<Good title="Only the flows you need">

```text
sg-app:  3000 from sg-alb
sg-db:   5432 from sg-app
```

</Good>
</Compare>

<Compare>
<Bad title="Locking yourself out">

```text
sudo ufw default deny incoming
sudo ufw enable                  # SSH not allowed yet → you're cut off
```

</Bad>
<Good title="Allow SSH first">

```text
sudo ufw allow from 203.0.113.5 to any port 22 proto tcp
sudo ufw default deny incoming
sudo ufw enable
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`0.0.0.0/0` on SSH, RDP, databases or caches**, "temporarily".
- **No egress rules**: compromised servers can talk to anything.
- **Rule sprawl**: hundreds of old rules nobody understands. Review and remove regularly.
- **Forgetting return traffic** on stateless network ACLs.
- **Thinking a WAF fixes vulnerable code.**

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **SSH, RDP, databases ya caches par `0.0.0.0/0`**, "thori der ke liye".
- **Egress rules na hona**: hack servers kisi se bhi baat kar sakte hain.
- **Rules ka dher**: sainkron purane rules jo koi nahi samajhta. Baqaida review aur safai karein.
- **Stateless network ACLs par wapsi ka traffic bhoolna.**
- **Samajhna ke WAF kamzor code theek kar deta hai.**

</Ur>
</Tr>

<DeepDive title="Real world: the flat network breach">

A company ran its web server, database and file shares in one subnet with "allow all traffic within the VPC". An outdated WordPress plugin gave an attacker a shell on the web server; from there they connected straight to the database (5432 open to the whole VPC) and exported customer data.

The redesign:

```text
1. Subnets per tier: public (ALB), app, data (no internet route), management.
2. Security groups referencing each other: ALB → app:3000 → db:5432. Nothing else.
3. SSH removed from all instances; admin access via SSM Session Manager with MFA.
4. Egress: app servers may reach only the payment API, OS mirrors and the monitoring service.
5. WAF with managed rules in front of the ALB; plugin patching automated.
6. VPC Flow Logs + alerts on rejected traffic from the app tier to unexpected ports.
```

Now a compromised web server can reach almost nothing, and any attempt shows up in the logs.

</DeepDive>

<DeepDive title="Security lens">

Firewalls aren't a wall around a castle; they're many doors inside the building. Assume something will get in, and make sure it can't go far.

- **Least privilege for networks:** narrowest source, narrowest port, per tier.
- **Log what's denied:** VPC Flow Logs, firewall logs and WAF logs reveal scans, misconfigurations and lateral-movement attempts.
- **Infrastructure as code** (Terraform) for firewall rules: reviewed in pull requests and scanned automatically (Checkov, tfsec) before deployment.
- **Continuous auditing:** Prowler, AWS Config and Security Hub flag world-open ports and unused rules.
- **Microsegmentation** (Kubernetes NetworkPolicies, service meshes) brings the same idea down to individual services.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a stateful and a stateless firewall?">
A stateful firewall tracks connections, so once an outbound or inbound connection is allowed, its return traffic is automatically permitted. A stateless firewall evaluates every packet independently, so return traffic must be explicitly allowed, typically on the ephemeral port range. AWS security groups are stateful; network ACLs are stateless.
</QA>

<QA q="What is the difference between a security group and a network ACL in AWS?">
A security group is attached to individual resources, is stateful and contains only allow rules that are evaluated together. A network ACL is attached to a subnet, is stateless and has numbered allow and deny rules evaluated in order. Security groups are the primary access control; NACLs act as a coarse, subnet-level safety net.
</QA>

<QA q="Why is network segmentation important?">
It limits the blast radius of a compromise. By separating systems into zones such as public, application, data and management, and allowing only specific flows between them, an attacker who compromises one system cannot freely reach databases or other sensitive systems, and lateral movement attempts become visible in logs.
</QA>

<QA q="Why should you control outbound traffic?">
Compromised systems use outbound connections to download tools, contact command-and-control servers and exfiltrate data. Restricting egress to known required destinations makes these steps harder and generates alerts, and it also prevents accidental data leaks to unapproved services.
</QA>

<QA q="What does a WAF protect against that a network firewall does not?">
A network firewall filters by IP, port and protocol, so it allows all traffic to an open web port. A web application firewall inspects HTTP requests themselves and can block malicious content such as SQL injection, cross-site scripting and path traversal patterns, abusive bots and request floods. It complements, but does not replace, secure application code.
</QA>

</DeepDive>
