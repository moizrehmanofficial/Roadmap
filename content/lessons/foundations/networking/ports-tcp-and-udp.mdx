<BigIdea>
<Tr>
<En>
An IP address finds the **machine**; a **port** (0–65535) finds the **program** on it: 22 SSH, 443 HTTPS, 5432 PostgreSQL. A server **listens** on a fixed port; the client uses a random temporary one. **TCP** is reliable: it connects first, numbers the data, resends lost pieces and keeps order (web, SSH, databases). **UDP** just sends, with no guarantees, but it's fast (DNS, video calls, games, HTTP/3).
</En>
<Ur>
IP address **machine** dhoondta hai; **port** (0–65535) us par **program** dhoondta hai: 22 SSH, 443 HTTPS, 5432 PostgreSQL. Server ek pakke port par **sunta** hai; client ek ittefaqi waqti port istemal karta hai. **TCP** bharosemand hai: pehle judta hai, data ko number deta hai, khoye tukre dobara bhejta hai aur tarteeb rakhta hai (web, SSH, databases). **UDP** bas bhej deta hai, koi zamanat nahi, lekin tez hai (DNS, video calls, games, HTTP/3).
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

A server at `203.0.113.10` may run a web server, SSH, a database and a cache at once. When a packet arrives, the operating system must know **which program** gets it: that's what ports are for.

| | TCP | UDP |
| --- | --- | --- |
| Connection | Yes, handshake before data | No, just send |
| Reliability | Lost data is resent | Lost data stays lost |
| Order | Delivered in order | May arrive out of order |
| Speed / overhead | More overhead, more delay | Minimal overhead |
| Unit | Byte stream | Separate messages (datagrams) |
| Used by | HTTP/1.1, HTTP/2, HTTPS, SSH, SMTP, databases | DNS, DHCP, NTP, VoIP, video, games, QUIC (HTTP/3), WireGuard |

</En>
<Ur>

`203.0.113.10` wala server ek waqt me web server, SSH, database aur cache chala sakta hai. Packet aaye to operating system ko pata hona chahiye ke **kis program** ko mile: ports isi liye hain.

| | TCP | UDP |
| --- | --- | --- |
| Connection | Haan, data se pehle handshake | Nahi, bas bhejo |
| Bharosa | Khoya data dobara bheja jata hai | Khoya data khoya rehta hai |
| Tarteeb | Tarteeb se pohanchta hai | Be-tarteeb aa sakta hai |
| Raftar / bojh | Zyada bojh, zyada der | Kam se kam bojh |
| Ikai | Bytes ki dhaara | Alag alag paighaam (datagrams) |
| Kaun istemal karta hai | HTTP/1.1, HTTP/2, HTTPS, SSH, SMTP, databases | DNS, DHCP, NTP, VoIP, video, games, QUIC (HTTP/3), WireGuard |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Every connection string, firewall rule, Docker mapping and load balancer** names a port and a protocol.
- **"Connection refused" vs "timed out"** tells you whether a port is closed or blocked: the core of network debugging.
- **Security:** open ports are the doors into your servers. Port scanning is step one of every attack and every audit.
- **Performance:** knowing why video calls use UDP explains modern protocol design.

</En>
<Ur>

- **Har connection string, firewall rule, Docker mapping aur load balancer** port aur protocol ka naam leta hai.
- **"Connection refused" bamuqabla "timed out"** batata hai ke port band hai ya roka gaya: network debugging ki jaan.
- **Security:** khule ports aap ke servers ke darwaze hain. Port scanning har hamle aur har audit ka pehla qadam hai.
- **Raftar:** ye jaanna ke video calls UDP kyun istemal karti hain, jadeed protocols ka design samjhata hai.

## Picture it

<Tr>
<En>

An **apartment building**: the IP address is the **building's street address**; the port is the **flat number**. A letter addressed only to the building can't be delivered; it needs "Flat 443".

**TCP vs UDP** is a **phone call vs a text message**. A phone call (TCP) connects first ("hello? can you hear me?"), both sides confirm, and if something is unclear you say "say that again". A text message (UDP) is just sent: quick and cheap, but if it's lost, nobody automatically resends it.

</En>
<Ur>

Ek **apartment building**: IP address **building ka gali ka pata** hai; port **flat number** hai. Sirf building ke naam ka khat pohanch nahi sakta; use "Flat 443" chahiye.

**TCP bamuqabla UDP** **phone call bamuqabla text message** hai. Phone call (TCP) pehle judti hai ("hello? awaaz aa rahi hai?"), dono taraf tasdeeq hoti hai, aur kuch samajh na aaye to "dobara kehna" kehte hain. Text message (UDP) bas bhej diya jata hai: tez aur sasta, lekin kho jaye to koi khud dobara nahi bhejta.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Ports identify programs">

<Tr>
<En>

Every TCP and UDP packet carries a 16-bit source port and destination port. The OS uses the destination port to hand data to the right program.

| Range | Name | Who uses it |
| --- | --- | --- |
| 0–1023 | Well-known (system) | Standard services; binding needs root on Linux |
| 1024–49151 | Registered | Databases, app servers (3306, 5432, 8080) |
| 49152–65535 | Dynamic / ephemeral | Client side of connections (Linux uses 32768–60999) |

| Port | Protocol | Service |
| --- | --- | --- |
| 22 | TCP | SSH |
| 25 / 587 | TCP | SMTP (sending email) |
| 53 | UDP + TCP | DNS |
| 80 / 443 | TCP (443 also UDP for HTTP/3) | HTTP / HTTPS |
| 123 | UDP | NTP (time) |
| 3306 | TCP | MySQL / MariaDB |
| 3389 | TCP | RDP (Windows remote desktop) |
| 5432 | TCP | PostgreSQL |
| 6379 | TCP | Redis |
| 27017 | TCP | MongoDB |

</En>
<Ur>

Har TCP aur UDP packet 16-bit source port aur destination port le jata hai. OS destination port dekh kar data sahi program ko deta hai.

| Range | Naam | Kaun istemal karta hai |
| --- | --- | --- |
| 0–1023 | Well-known (system) | Mayari services; Linux par bind ke liye root chahiye |
| 1024–49151 | Registered | Databases, app servers (3306, 5432, 8080) |
| 49152–65535 | Dynamic / ephemeral | Connections ki client taraf (Linux 32768–60999 istemal karta hai) |

| Port | Protocol | Service |
| --- | --- | --- |
| 22 | TCP | SSH |
| 25 / 587 | TCP | SMTP (email bhejna) |
| 53 | UDP + TCP | DNS |
| 80 / 443 | TCP (443 HTTP/3 ke liye UDP bhi) | HTTP / HTTPS |
| 123 | UDP | NTP (waqt) |
| 3306 | TCP | MySQL / MariaDB |
| 3389 | TCP | RDP (Windows remote desktop) |
| 5432 | TCP | PostgreSQL |
| 6379 | TCP | Redis |
| 27017 | TCP | MongoDB |

</Ur>
</Tr>

<Step title="A connection is four numbers">

<Tr>
<En>

Every TCP connection is identified by **client IP, client port, server IP, server port** (plus the protocol). That's how one server port (443) serves thousands of clients at once: each connection differs in client IP or client port. The client OS picks a free **ephemeral** port automatically.

</En>
<Ur>

Har TCP connection **client IP, client port, server IP, server port** (aur protocol) se pehchana jata hai. Isi tarah ek server port (443) ek saath hazaron clients ko sambhalta hai: har connection client IP ya client port me alag hota hai. Client ka OS khud ek khali **ephemeral** port chunta hai.

</Ur>
</Tr>

```bash
python3 -m http.server 3470 --bind 127.0.0.1 > /dev/null 2>&1 & srv=$!; sleep 1
for i in 1 2 3; do
  python3 - <<'EOF'
import socket
s = socket.create_connection(("127.0.0.1", 3470))
cip, cport = s.getsockname(); sip, sport = s.getpeername()
print(f"client {cip}:{'EPHEMERAL' if cport >= 1024 else cport} → server {sip}:{sport}")
s.close()
EOF
done
kill $srv
```

```text output
client 127.0.0.1:EPHEMERAL → server 127.0.0.1:3470
client 127.0.0.1:EPHEMERAL → server 127.0.0.1:3470
client 127.0.0.1:EPHEMERAL → server 127.0.0.1:3470
```

<Happened>
<Tr>
<En>Each run got a **different** random client port (shown as `EPHEMERAL` because it changes every time), all talking to the same server port 3470.</En>
<Ur>Har run ko **alag** ittefaqi client port mila (`EPHEMERAL` dikhaya kyun ke ye har dafa badalta hai), sab ek hi server port 3470 se baat kar rahe the.</Ur>
</Tr>
</Happened>

<Step title="Listening vs connecting">

<Tr>
<En>

A **server** binds to an address and port and **listens**; a **client** connects to it. Most "can't connect" problems are: nothing listening, listening on the wrong address, or a firewall in between.

- Listening on `127.0.0.1` = only this machine can connect.
- Listening on `0.0.0.0` (or `::`) = every network interface.

</En>
<Ur>

**Server** kisi address aur port se bind ho kar **sunta** hai; **client** us se judta hai. Zyada tar "connect nahi hota" masle ye hain: koi sun nahi raha, ghalat address par sun raha hai, ya beech me firewall.

- `127.0.0.1` par sunna = sirf yahi machine jur sakti hai.
- `0.0.0.0` (ya `::`) par sunna = har network interface.

</Ur>
</Tr>

```bash
python3 -m http.server 3471 --bind 127.0.0.1 > /dev/null 2>&1 & a=$!
python3 -m http.server 3472 --bind 0.0.0.0   > /dev/null 2>&1 & b=$!
sleep 1
ss -ltn | awk '$4 ~ /:347[12]$/ {print "listening on", $4}' | sort
kill $a $b
```

```text output
listening on 0.0.0.0:3472
listening on 127.0.0.1:3471
```

<Happened>
<Tr>
<En>Port 3471 is reachable only from this machine; 3472 from any network the machine is on, unless a firewall blocks it.</En>
<Ur>Port 3471 sirf isi machine se pohanch me hai; 3472 har us network se jis par machine hai, jab tak firewall na roke.</Ur>
</Tr>
</Happened>

</Step>

<Step title='"Connection refused" vs "timed out"'>

<Tr>
<En>

- **Refused:** the packet reached the machine, but nothing listens on that port; the OS answers with a reset. Look at the **service**.
- **Timed out:** no answer at all, usually a firewall silently dropping packets or a wrong IP. Look at the **network**.

In Node.js these show up as `ECONNREFUSED` and `ETIMEDOUT`.

</En>
<Ur>

- **Refused:** packet machine tak pohancha, lekin us port par koi nahi sun raha; OS reset ke saath jawab deta hai. **Service** dekhein.
- **Timed out:** koi jawab hi nahi, aam tor par firewall chupke se packets phaink raha hai ya IP ghalat hai. **Network** dekhein.

Node.js me ye `ECONNREFUSED` aur `ETIMEDOUT` ki shakal me aate hain.

</Ur>
</Tr>

```bash
python3 - <<'EOF'
import socket
s = socket.socket(); s.settimeout(2)
try:
    s.connect(("127.0.0.1", 3999))
except ConnectionRefusedError:
    print("127.0.0.1:3999 → connection REFUSED: machine reachable, no program listening")
EOF
```

```text output
127.0.0.1:3999 → connection REFUSED: machine reachable, no program listening
```

<Tr>
<En>

| Error | Meaning | Check |
| --- | --- | --- |
| Connection refused | Nothing listening (or on another address) | Is the service running? `ss -ltnp` |
| Timed out | Packets dropped / no route | Firewall, security group, wrong IP, routing |
| No route to host | Network unreachable | IP, routes, VPN |
| Name or service not known | DNS failed | `dig` the hostname |

</En>
<Ur>

| Error | Matlab | Kya check karein |
| --- | --- | --- |
| Connection refused | Koi nahi sun raha (ya doosre address par) | Service chal rahi hai? `ss -ltnp` |
| Timed out | Packets phenke gaye / raasta nahi | Firewall, security group, ghalat IP, routing |
| No route to host | Network pohanch se bahar | IP, routes, VPN |
| Name or service not known | DNS fail | Hostname par `dig` |

</Ur>
</Tr>

<Step title="TCP: reliable and ordered">

<Tr>
<En>

A web page, a file or a database query must arrive **complete and exact**. TCP turns unreliable IP packets into a reliable stream: it numbers every byte, the receiver acknowledges what arrived, missing data is resent, and data comes out in order. It starts with the **three-way handshake** (next lesson) and adjusts speed to the receiver and the network.

</En>
<Ur>

Web page, file ya database query **poori aur bilkul sahi** pohanchni chahiye. TCP be-bharosa IP packets ko bharosemand dhaara banata hai: har byte ko number deta hai, paane wala tasdeeq karta hai ke kya aaya, ghayab data dobara bheja jata hai, aur data tarteeb se nikalta hai. Ye **three-way handshake** se shuru hota hai (agla sabaq) aur raftar ko paane wale aur network ke mutabiq rakhta hai.

</Ur>
</Tr>

```bash
python3 - <<'EOF'
import socket, threading
srv = socket.socket(); srv.bind(("127.0.0.1", 3473)); srv.listen()
def serve():
    conn, _ = srv.accept()
    data = b""
    while chunk := conn.recv(4096):
        data += chunk
    print(f"server received {len(data):,} bytes, in order: {data == bytes(range(256)) * 4000}")
    conn.close()
t = threading.Thread(target=serve); t.start()
c = socket.create_connection(("127.0.0.1", 3473))
c.sendall(bytes(range(256)) * 4000)      # ~1 MB as a stream
c.close(); t.join(); srv.close()
EOF
```

```text output
server received 1,024,000 bytes, in order: True
```

<Happened>
<Tr>
<En>The data went in many packets, but TCP delivered every byte, in the right order, as one stream.</En>
<Ur>Data kai packets me gaya, lekin TCP ne har byte sahi tarteeb me ek dhaara ki shakal me pohanchaya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="UDP: fast, no guarantees">

<Tr>
<En>

For real-time data a late packet is useless anyway (a video frame from 1 second ago), and for tiny request/response protocols like DNS a handshake would double the time. UDP sends independent **datagrams**: no connection, no acknowledgement, no resending, no ordering. The app handles loss itself (DNS retries; video hides lost frames).

</En>
<Ur>

Real-time data me der se aaya packet waise bhi bekaar hai (1 second purana video frame), aur DNS jaise chhote sawal/jawab protocols me handshake waqt dugna kar deta. UDP alag alag **datagrams** bhejta hai: na connection, na tasdeeq, na dobara bhejna, na tarteeb. App nuqsan khud sambhalti hai (DNS dobara koshish karta hai; video khoye frames chhupa deta hai).

</Ur>
</Tr>

```bash
python3 - <<'EOF'
import socket
srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); srv.bind(("127.0.0.1", 3474))
cli = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
for msg in [b"frame-1", b"frame-2", b"frame-3"]:
    cli.sendto(msg, ("127.0.0.1", 3474))          # no connect, no handshake
for _ in range(3):
    data, addr = srv.recvfrom(1024)
    print("received datagram:", data.decode())
cli.sendto(b"hello?", ("127.0.0.1", 3998))         # nobody listening: no error at send time
print("sent to a closed UDP port without any error — UDP does not know if anyone received it")
EOF
```

```text output
received datagram: frame-1
received datagram: frame-2
received datagram: frame-3
sent to a closed UDP port without any error — UDP does not know if anyone received it
```

</Step>

<Step title="Port mapping in Docker">

<Tr>
<En>

Containers have their own network; nothing inside is reachable from outside unless published. `-p HOST:CONTAINER` forwards a host port into the container: `-p 8080:3000` = host 8080 → container 3000. `-p 127.0.0.1:5432:5432` publishes only on localhost: use that for databases.

</En>
<Ur>

Containers ka apna network hota hai; andar ki koi cheez bahar se pohanch me nahi jab tak publish na ho. `-p HOST:CONTAINER` host ka port container me bhejta hai: `-p 8080:3000` = host 8080 → container 3000. `-p 127.0.0.1:5432:5432` sirf localhost par publish karta hai: databases ke liye yahi istemal karein.

</Ur>
</Tr>

```text
# compose.yaml
services:
  api:
    image: shop-api
    ports:
      - "8080:3000"              # http://server:8080 → container 3000
  db:
    image: postgres:16
    ports:
      - "127.0.0.1:5432:5432"    # reachable only from the host itself, not the internet
```

<Callout type="warning" title="Docker can bypass your firewall">
<Tr>
<En>On Linux, ports published with `-p 5432:5432` are opened through Docker's own iptables rules, often **bypassing ufw**. A database "protected by ufw" can still be on the internet. Publish on `127.0.0.1`, or don't publish internal services at all (containers on the same Docker network reach each other by name).</En>
<Ur>Linux par `-p 5432:5432` se publish ports Docker ke apne iptables rules se khulte hain, aksar **ufw ko bypass** kar ke. "ufw se mehfooz" database phir bhi internet par ho sakta hai. `127.0.0.1` par publish karein, ya andaroni services bilkul publish na karein (ek hi Docker network ke containers ek doosre tak naam se pohanchte hain).</Ur>
</Tr>
</Callout>

</Step>

<Step title="Ports in firewalls and security groups">

<Tr>
<En>

Firewall rules combine **protocol + port + source range**: "allow TCP 443 from 0.0.0.0/0". Start by allowing nothing, then open only what must be reachable.

| Port | Public? | Typical rule |
| --- | --- | --- |
| 443 (and 80 for redirects) | Yes | `0.0.0.0/0` |
| 22 SSH | No | Office/VPN IP `/32`, or none (use SSM) |
| 5432 / 3306 databases | Never | App subnets / app security group only |
| 6379 Redis, 27017 MongoDB, 9200 Elasticsearch | Never | Private only: the most commonly exposed by mistake |

</En>
<Ur>

Firewall rules **protocol + port + source range** jorte hain: "0.0.0.0/0 se TCP 443 ki ijazat". Shuru me kuch bhi allow na karein, phir sirf wahi kholein jo pohanch me hona zaroori hai.

| Port | Public? | Aam rule |
| --- | --- | --- |
| 443 (aur redirects ke liye 80) | Haan | `0.0.0.0/0` |
| 22 SSH | Nahi | Office/VPN IP `/32`, ya bilkul nahi (SSM istemal karein) |
| 5432 / 3306 databases | Kabhi nahi | Sirf app subnets / app security group |
| 6379 Redis, 27017 MongoDB, 9200 Elasticsearch | Kabhi nahi | Sirf private: ghalti se sab se zyada khule rehne wale |

</Ur>
</Tr>

</Step>

<Step title="Port scanning">

<Tr>
<En>

Checking which ports on a host are open, by trying to connect to many of them. Attackers do it to find doors; defenders do it to confirm only intended doors are open. The standard tool is `nmap`. **Only scan systems you own or are allowed to test.**

</En>
<Ur>

Kisi host ke kaunse ports khule hain, bohot se ports se judne ki koshish kar ke check karna. Hamla awar darwaze dhoondne ke liye karte hain; hifazat karne wale ye tasdeeq karne ke liye ke sirf matloob darwaze khule hain. Mayari tool `nmap` hai. **Sirf wo systems scan karein jo aap ke hain ya jin ki ijazat hai.**

</Ur>
</Tr>

```bash
python3 -m http.server 3475 --bind 127.0.0.1 > /dev/null 2>&1 & srv=$!; sleep 1
for port in 3474 3475 3476; do
  if nc -z -w1 127.0.0.1 "$port" 2>/dev/null; then echo "$port open"; else echo "$port closed"; fi
done
kill $srv
```

```text output
3475 open
3476 closed
```

## Common mistakes

<Compare>
<Bad title="Database published on all interfaces">

```text
docker run -p 5432:5432 postgres:16      # may be reachable from the internet
```

</Bad>
<Good title="Localhost only, or not published">

```text
docker run -p 127.0.0.1:5432:5432 postgres:16
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Binding services to `0.0.0.0`** when only local or private access is needed.
- **Opening a port in the app but not the firewall** (or the reverse) and blaming the other side.
- **Assuming UDP works like TCP**: no error on send doesn't mean it arrived.
- **Forgetting DNS needs UDP and TCP 53** in strict outgoing rules.
- **Confusing host and container ports** in `-p 8080:3000`.
- **Using ports below 1024 for non-root apps**: permission denied; use 3000/8080 behind a reverse proxy.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Services ko `0.0.0.0` par bind karna** jab sirf local ya private pohanch chahiye.
- **App me port kholna lekin firewall me nahi** (ya ulta) aur doosri taraf ko qasoorwar thehrana.
- **UDP ko TCP jaisa samajhna**: bhejte waqt error na aana matlab pohanch jana nahi.
- **Sakht outgoing rules me bhoolna ke DNS ko UDP aur TCP 53 dono chahiye.**
- **`-p 8080:3000` me host aur container ports me ulajhna.**
- **Non-root apps ke liye 1024 se neeche ke ports**: permission denied; reverse proxy ke peeche 3000/8080 istemal karein.

</Ur>

<DeepDive title="Real world: the exposed MongoDB ransom">

A startup's MongoDB server was found by an automated scanner: port **27017** was open to `0.0.0.0/0` with no authentication. Within hours the data was copied and deleted, and a ransom note was left in a new collection: one of the most common real-world breaches of the last decade (also seen with Elasticsearch on 9200 and Redis on 6379).

The fix, layer by layer:

```text
1. Bind:       mongod --bind_ip 127.0.0.1,10.0.21.15         (not 0.0.0.0)
2. Firewall:   security group allows 27017 only from sg-app  (not 0.0.0.0/0)
3. Docker:     ports: ["127.0.0.1:27017:27017"]  — or no published port at all
4. Auth:       enable authentication, strong passwords, TLS
5. Verify:     nmap from outside → 27017 filtered
6. Monitor:    alert on any security group rule with 0.0.0.0/0 on non-web ports
```

</DeepDive>

<DeepDive title="Security lens">

Every open port is a door. The fewer doors, and the fewer people allowed through each, the smaller your attack surface.

- **Inventory your open ports** regularly (`ss -ltnup` on hosts, `nmap` from outside, cloud security-group audits).
- **Never expose databases, caches or admin interfaces** (5432, 3306, 6379, 27017, 9200, 2375 Docker API) to the internet.
- **Moving SSH to port 2222** reduces log noise but is **not** security: keys, no passwords and source restrictions are.
- **UDP amplification attacks** abuse open UDP services (DNS, NTP, memcached) to flood victims; don't run open resolvers.
- **Egress filtering** (limiting outgoing ports) makes it harder for malware to call home or exfiltrate data.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between TCP and UDP?">
TCP is connection-oriented: it performs a handshake, numbers and acknowledges data, retransmits lost segments and delivers bytes in order, which makes it reliable but adds latency and overhead. UDP is connectionless: it sends independent datagrams with no handshake, acknowledgements, retransmission or ordering, which makes it fast and lightweight. TCP is used for the web, SSH and databases; UDP for DNS, real-time media, games and QUIC.
</QA>

<QA q="What uniquely identifies a TCP connection?">
The combination of source IP, source port, destination IP and destination port, together with the protocol. This is why a server listening on one port can handle many simultaneous clients: each connection has a different client IP or client ephemeral port.
</QA>

<QA q="What does connection refused mean compared to a timeout?">
Connection refused means the target host was reached but no process is listening on that port, so the host replied with a TCP reset. A timeout means no reply came back at all, which usually indicates a firewall dropping the packets, a wrong or unreachable address, or a routing problem.
</QA>

<QA q="Why does DNS use UDP, and when does it use TCP?">
Most DNS queries and answers fit in one small message, so UDP avoids the round trip of a TCP handshake and keeps lookups fast. DNS falls back to TCP when a response is too large for UDP (it is truncated), for zone transfers, and increasingly for encrypted DNS such as DNS over TLS.
</QA>

</DeepDive>
