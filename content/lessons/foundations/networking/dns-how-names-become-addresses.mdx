<Callout type="tip" title="In one minute">
**DNS** (Domain Name System) is the internet's phone book: it turns names like `shop.example.com` into IP addresses like `203.0.113.10`. Your device asks a **recursive resolver** (from your ISP, or 1.1.1.1 / 8.8.8.8), which asks the **root** servers, then the **TLD** servers (`.com`), then the domain's **authoritative** servers, and caches the answer for its **TTL**. Records you will use: **A** (name → IPv4), **AAAA** (→ IPv6), **CNAME** (alias to another name), **MX** (mail servers), **TXT** (verification, SPF/DKIM/DMARC), **NS** (who is authoritative). Check them with `dig`.
</Callout>

## Start from zero

### Humans remember names, computers need numbers

Computers connect using IP addresses, but nobody wants to type `142.250.181.14` to reach Google. And IPs change: when you move your site to a new server, its IP changes but the name stays. DNS keeps the mapping.

<Callout type="analogy">
Your **phone's contact list**: you tap "Ammi", the phone dials the number stored for that name. If Ammi changes her number, you update **one contact** and everyone who calls "Ammi" reaches the new number. DNS is a giant, shared contact list for the whole internet — split across millions of servers, each responsible for its own part.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Domain name** | A human-readable name | `example.com` |
| **Subdomain** | A name under a domain | `api.example.com` |
| **TLD** | Top-level domain, the last part | `.com`, `.pk`, `.io` |
| **Record** | One entry in DNS | `A shop.example.com 203.0.113.10` |
| **Resolver** | The server that finds answers for you | 1.1.1.1, 8.8.8.8, your router |
| **Authoritative server** | The server that holds the official records of a domain | Cloudflare / Route 53 name servers |
| **Zone** | All records of one domain, managed together | the `example.com` zone |
| **TTL** | How long an answer may be cached (seconds) | `300` |
| **Registrar** | Where you buy/renew a domain | Namecheap, GoDaddy, PKNIC |

## What is it?

```text
 You type shop.example.com
   │
   ▼
 Browser / OS cache ── hit? → done
   │ miss
   ▼
 Recursive resolver (1.1.1.1)  ── cache hit? → answer
   │ miss: it walks the tree
   ├──► Root server:        "ask the .com servers at a.gtld-servers.net"
   ├──► .com TLD server:    "example.com is handled by ns1.dns-host.net"
   └──► Authoritative NS:   "shop.example.com A 203.0.113.10, TTL 300"
   │
   ▼
 Resolver caches it for 300 s and answers you → browser connects to 203.0.113.10:443
```

DNS mostly uses **UDP port 53** (TCP 53 for large answers), and increasingly encrypted DNS: DNS-over-HTTPS (DoH) and DNS-over-TLS (DoT, port 853).

## Why does it matter?

- **Every connection starts with DNS.** If DNS breaks, "the internet is down" for users even when servers are fine.
- **Deploying sites:** pointing a domain to Vercel, Netlify, a VPS or a load balancer is DNS work.
- **Email deliverability:** without correct MX, SPF, DKIM and DMARC records, your emails land in spam (or can be spoofed).
- **Migrations:** TTLs decide how fast a change reaches users.
- **Security:** domain hijacking, DNS spoofing, subdomain takeover and phishing look-alike domains are major attack types.

## When and where do you use it?

| Task | Record / tool |
| --- | --- |
| Point `example.com` to a server | `A` (and `AAAA` for IPv6) |
| Point `www` or `app` to Vercel / a load balancer name | `CNAME` |
| Receive email (Google Workspace, Zoho) | `MX` |
| Prove domain ownership (Google, AWS, Let's Encrypt DNS challenge) | `TXT` |
| Protect email from spoofing | `TXT` for SPF, DKIM, DMARC |
| Move DNS to Cloudflare / Route 53 | `NS` at the registrar |
| Debug | `dig`, `nslookup`, `getent hosts` |

## Concepts one by one

### 1. Domain names are a tree

<Explain>
<What>
Names are read **right to left**, from general to specific: root (`.`) → TLD (`com`) → domain (`example`) → subdomain (`shop`).
</What>
<Why>
The tree lets responsibility be **delegated**: the root knows who runs `.com`, `.com` knows who runs `example.com`, and the owner of `example.com` controls everything below it.
</Why>
<When>
Every lookup walks this tree (unless cached).
</When>
<Where>
Every domain on the internet.
</Where>
<How>
The full name actually ends with a dot: `shop.example.com.` — the root.
</How>
</Explain>

```python
name = "api.shop.example.com"
parts = name.split(".")
print("read right to left:")
for i in range(len(parts) - 1, -1, -1):
    print("  " + ".".join(parts[i:]))
```

```text output
read right to left:
  com
  example.com
  shop.example.com
  api.shop.example.com
```

### 2. Resolvers and authoritative servers

<Explain>
<What>
A **recursive resolver** does the work of finding answers for clients and caches them. **Authoritative servers** hold the real records for a zone and only answer about their own zones.
</What>
<Why>
Clients stay simple (one question, one answer); caching at resolvers keeps DNS fast and reduces load.
</Why>
<When>
Every lookup.
</When>
<Where>
Resolvers: your router, ISP, `1.1.1.1` (Cloudflare), `8.8.8.8` (Google), AWS VPC resolver (`169.254.169.253` / VPC base + 2). Authoritative: Cloudflare DNS, Route 53, your registrar's DNS.
</Where>
<How>
Your machine's resolver is configured in `/etc/resolv.conf` (often `127.0.0.53`, the local systemd-resolved cache).
</How>
</Explain>

```bash
grep -E '^nameserver' /etc/resolv.conf | head -1 | sed -E 's/[0-9.]+$/<resolver IP>/'
```

```text output
nameserver <resolver IP>
```

### 3. Record types

<Explain>
<What>
Each DNS record has a **name**, a **type**, a **TTL** and a **value**.
</What>
<Why>
Different types answer different questions: where is the website, where should email go, who is authoritative.
</Why>
<When>
Setting up domains, email, verification, migrations.
</When>
<Where>
Your DNS provider's dashboard or API (Terraform, Cloudflare API).
</Where>
<How>
Learn the common ones below.
</How>
</Explain>

| Type | Maps a name to… | Example value | Typical use |
| --- | --- | --- | --- |
| `A` | IPv4 address | `203.0.113.10` | Website on a server |
| `AAAA` | IPv6 address | `2001:db8::10` | IPv6 |
| `CNAME` | Another name (alias) | `cname.vercel-dns.com` | Subdomain on Vercel, a load balancer, a CDN |
| `MX` | Mail server (with priority) | `10 mx1.mail.example.net` | Receiving email |
| `TXT` | Any text | `v=spf1 include:_spf.google.com ~all` | Verification, SPF, DKIM, DMARC |
| `NS` | Authoritative name servers | `ns1.cloudflare.com` | Delegation |
| `SOA` | Zone metadata | serial, refresh… | Zone management |
| `CAA` | Which CAs may issue certificates | `0 issue "letsencrypt.org"` | Certificate security |
| `SRV` | Service host and port | `_sip._tcp …` | Some protocols |
| `PTR` | IP → name (reverse DNS) | `mail.example.com` | Mail servers, logs |

A typical zone for a small business site:

```text
example.com.        300   A      76.76.21.21                       ; apex → Vercel
www.example.com.    300   CNAME  cname.vercel-dns.com.
api.example.com.    300   A      203.0.113.10                      ; NestJS on a VPS
example.com.        3600  MX     1 smtp.google.com.                ; Google Workspace mail
example.com.        3600  TXT    "v=spf1 include:_spf.google.com ~all"
_dmarc.example.com. 3600  TXT    "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"
example.com.        3600  CAA    0 issue "letsencrypt.org"
```

### 4. CNAME: an alias

<Explain>
<What>
A CNAME says "this name is another name — look that one up instead".
</What>
<Why>
Platforms (Vercel, Netlify, AWS load balancers, CDNs) change their IPs; pointing to their **name** keeps your record valid automatically.
</Why>
<When>
Subdomains on hosting platforms, CDNs, load balancers.
</When>
<Where>
`www`, `app`, `docs` subdomains.
</Where>
<How>
A CNAME cannot be used at the **apex** (`example.com` itself) and cannot coexist with other records on the same name. For the apex, providers offer `ALIAS`/`ANAME`/"CNAME flattening" (Cloudflare) or Route 53 **alias** records.
</How>
</Explain>

```text
$ dig +short www.example.com
cname.vercel-dns.com.        ← the CNAME
76.76.21.21                  ← the A record it finally resolved to
```

### 5. TTL and caching

<Explain>
<What>
TTL (time to live) tells resolvers how many seconds they may reuse an answer before asking again.
</What>
<Why>
Caching makes DNS fast, but it also delays changes: with TTL 86400 (1 day), some users may see the old IP for a day after you change it.
</Why>
<When>
Before migrations, failovers, launches.
</When>
<Where>
Every record; also browser and OS caches.
</Where>
<How>
Before changing a record, **lower its TTL** (e.g. to 60–300) and wait at least the **old** TTL. Change the record. Raise the TTL again later. "DNS propagation" is mostly caches expiring.
</How>
</Explain>

```python
old_ttl, new_ttl = 86400, 300
print(f"1) lower TTL from {old_ttl}s to {new_ttl}s")
print(f"2) wait {old_ttl // 3600} hours so every cache has picked up the short TTL")
print(f"3) change the IP — users switch within ~{new_ttl // 60} minutes")
print("4) raise the TTL again once the migration is stable")
```

```text output
1) lower TTL from 86400s to 300s
2) wait 24 hours so every cache has picked up the short TTL
3) change the IP — users switch within ~5 minutes
4) raise the TTL again once the migration is stable
```

### 6. Looking up records with `dig`

<Explain>
<What>
`dig` (from the `dnsutils`/`bind-utils` package) queries DNS and shows the full answer.
</What>
<Why>
The standard tool to verify records, check TTLs, query specific servers and debug.
</Why>
<When>
Every DNS change and every "site not reachable" investigation.
</When>
<Where>
Linux, macOS; Windows has `nslookup` and `Resolve-DnsName`.
</Where>
<How>
`dig example.com` (A), `dig example.com MX`, `dig +short name`, `dig @1.1.1.1 name` (ask a specific resolver), `dig +trace name` (walk from the root), `dig -x 8.8.8.8` (reverse).
</How>
</Explain>

```text
$ dig shop.example.com

;; QUESTION SECTION:
;shop.example.com.          IN  A

;; ANSWER SECTION:
shop.example.com.   287     IN  A   203.0.113.10
                    └ TTL left in the resolver's cache (it started at 300)

;; Query time: 21 msec
;; SERVER: 127.0.0.53#53(127.0.0.53) (UDP)
```

| Command | Answers |
| --- | --- |
| `dig +short example.com` | Just the IP(s) |
| `dig example.com AAAA` | IPv6 addresses |
| `dig example.com MX +short` | Mail servers |
| `dig example.com TXT +short` | SPF, verification strings |
| `dig example.com NS +short` | Who is authoritative |
| `dig @ns1.cloudflare.com example.com` | Ask the authoritative server directly (bypasses caches) |
| `dig +trace example.com` | The full root → TLD → authoritative walk |

### 7. `/etc/hosts` — local overrides

<Explain>
<What>
A local file mapping names to IPs, checked **before** DNS on most systems.
</What>
<Why>
Test a new server before changing public DNS, give names to local services, or block domains.
</Why>
<When>
Migrations, local development, quick tests.
</When>
<Where>
`/etc/hosts` (Linux/macOS), `C:\Windows\System32\drivers\etc\hosts` (Windows).
</Where>
<How>
Add `IP name` lines. `getent hosts name` shows what the system resolves (hosts file + DNS). Remove test entries afterwards!
</How>
</Explain>

```bash
cp /etc/hosts /tmp/hosts.backup
echo "127.0.0.1 shop.test" >> /etc/hosts
getent hosts shop.test
python3 -c 'import socket; print("Python resolves shop.test to", socket.gethostbyname("shop.test"))'
cp /tmp/hosts.backup /etc/hosts
getent hosts shop.test || echo "after removing the line: shop.test no longer resolves"
```

```text output
127.0.0.1       shop.test
Python resolves shop.test to 127.0.0.1
after removing the line: shop.test no longer resolves
```

(Editing `/etc/hosts` needs root; on your machine use `sudo`.)

### 8. Pointing a domain to your site

<Explain>
<What>
The steps to make a bought domain show your website.
</What>
<Why>
Every project you deploy needs it.
</Why>
<When>
Launching a site, moving hosts.
</When>
<Where>
Registrar (where the domain is bought) and DNS provider (where records live — often the same, or Cloudflare).
</Where>
<How>
Either keep DNS at the registrar, or change the domain's **NS** records to your DNS provider. Then add records the host tells you (A for the apex, CNAME for `www`), wait for the TTL, verify with `dig`, and let the host issue an HTTPS certificate.
</How>
</Explain>

```text
Domain bought at Namecheap, site on Vercel, API on a VPS:

At Namecheap:   Nameservers → Custom: ns1.cloudflare.com, ns2.cloudflare.com   (optional: move DNS to Cloudflare)
At Cloudflare:  example.com      A      76.76.21.21              (Vercel's apex IP)
                www              CNAME  cname.vercel-dns.com
                api              A      203.0.113.10             (VPS; nginx + Let's Encrypt there)
Verify:         dig +short example.com     → 76.76.21.21
                dig +short api.example.com → 203.0.113.10
```

### 9. Email records: SPF, DKIM, DMARC

<Explain>
<What>
Three TXT-based records that let receiving mail servers check that an email claiming to be from your domain really is.
</What>
<Why>
Without them, anyone can send email "from" your domain (phishing), and your real emails go to spam.
</Why>
<When>
As soon as a domain sends any email (including app emails via SendGrid, SES, Resend).
</When>
<Where>
TXT records on the domain.
</Where>
<How>
**SPF**: which servers may send for the domain. **DKIM**: a public key to verify email signatures. **DMARC**: what receivers should do on failure (`none` → `quarantine` → `reject`) and where to send reports.
</How>
</Explain>

```text
example.com.                      TXT  "v=spf1 include:_spf.google.com include:amazonses.com -all"
google._domainkey.example.com.    TXT  "v=DKIM1; k=rsa; p=MIIBIjANBgkqh…"
_dmarc.example.com.               TXT  "v=DMARC1; p=reject; rua=mailto:dmarc@example.com"
```

### 10. DNS in clouds and containers

<Explain>
<What>
Internal DNS that gives names to services inside private networks.
</What>
<Why>
Services find each other by name (`db`, `redis`, `api.internal`) instead of hard-coded IPs that change.
</Why>
<When>
Docker Compose, Kubernetes, VPCs.
</When>
<Where>
Docker's embedded DNS (`127.0.0.11`) resolves service names; Kubernetes CoreDNS resolves `service.namespace.svc.cluster.local`; AWS Route 53 private hosted zones.
</Where>
<How>
In Compose, the service name **is** the hostname: `DATABASE_URL=postgres://shop@db:5432/shop`.
</How>
</Explain>

```bash
python3 -c 'import socket; ips={a[4][0] for a in socket.getaddrinfo("localhost", None)}; print("localhost resolves to 127.0.0.1:", "127.0.0.1" in ips)'
```

```text output
localhost resolves to 127.0.0.1: True
```

`getaddrinfo` is the function every program (Node.js, Python, curl) uses to resolve names. On many systems it also returns `::1`, the IPv6 loopback.

## Hands-on

```bash
# 1. How does this machine resolve names?
grep -E '^hosts:' /etc/nsswitch.conf

# 2. A lookup table like a tiny DNS zone
declare -A zone=([shop.example.com]=203.0.113.10 [www.example.com]="CNAME shop.example.com" [api.example.com]=203.0.113.20)
resolve() {
  local v=${zone[$1]:-}
  if [[ $v == CNAME* ]]; then echo "$1 is an alias for ${v#CNAME }"; resolve "${v#CNAME }"
  elif [[ -n $v ]]; then echo "$1 → $v"
  else echo "$1 → NXDOMAIN (does not exist)"; fi
}
resolve www.example.com
resolve api.example.com
resolve old.example.com
```

```text output
hosts:          files dns
www.example.com is an alias for shop.example.com
shop.example.com → 203.0.113.10
api.example.com → 203.0.113.20
old.example.com → NXDOMAIN (does not exist)
```

`hosts: files dns` means "check `/etc/hosts` first, then DNS". **NXDOMAIN** is DNS's "no such name" answer.

On your own computer with internet, try: `dig +short google.com`, `dig google.com MX +short`, `dig +trace example.com`, `dig @1.1.1.1 github.com AAAA +short`.

## Real-world example

**Moving a live site to a new server with zero downtime:**

```text
Day 1   dig example.com → TTL 3600. Lower it: A example.com 203.0.113.10, TTL 300.
Day 2   (old TTL has expired everywhere) Deploy the site on the new server 198.51.100.20.
        Test it WITHOUT touching public DNS:  echo "198.51.100.20 example.com" | sudo tee -a /etc/hosts
        → browse, test login and payments, then remove the hosts line.
        Switch: A example.com 198.51.100.20 (TTL 300).
        Verify from outside: dig @1.1.1.1 +short example.com ; dig @8.8.8.8 +short example.com
        Keep the old server running for a day — some clients cache longer than the TTL.
Day 4   Raise TTL back to 3600. Shut down the old server.
```

## Common mistakes

- **Changing a record with a long TTL** and expecting the change to be instant.
- **A CNAME at the apex**, or a CNAME next to other records on the same name.
- **Forgetting `www`** (or the apex) — only one of them works.
- **Testing only from your own machine** (cached) — check public resolvers and authoritative servers too.
- **Leaving test entries in `/etc/hosts`** and wondering later why the site "never changes".
- **Missing SPF/DKIM/DMARC** — emails to customers go to spam.
- **Dangling records** pointing to deleted cloud resources (see Security lens).

## Security lens

<Callout type="security">
Whoever controls your DNS controls where your users and your email go. Protect it like a production password.
</Callout>

- **Registrar and DNS accounts:** strong passwords, **MFA**, registrar lock, auto-renew. Expired domains get bought by attackers.
- **Subdomain takeover:** a CNAME like `shop.example.com → myshop.herokuapp.com` stays after the app is deleted; an attacker claims `myshop` on that platform and serves content on **your** subdomain. Remove records when you delete resources.
- **DNS spoofing / cache poisoning:** fake answers redirect users; **DNSSEC** signs records, and HTTPS certificates stop most impersonation.
- **Email spoofing:** SPF + DKIM + DMARC with `p=reject` stops attackers from sending as your domain.
- **CAA records** limit which certificate authorities can issue certificates for your domain.
- **Reconnaissance:** attackers enumerate subdomains (certificate transparency logs, brute force) to find forgotten, unpatched systems — keep an inventory.
- **DNS tunnelling/exfiltration:** malware can hide data in DNS queries; monitoring DNS logs is a standard detection technique.

## Interview questions

<QA q="What happens when you type a domain name into the browser, from a DNS point of view?">
The browser and operating system check their caches and the hosts file. If there is no answer, the OS asks its configured recursive resolver. The resolver, if it has no cached answer, asks a root server, which refers it to the TLD servers for .com; those refer it to the domain's authoritative name servers, which return the record. The resolver caches the answer for its TTL and returns it, and the browser connects to that IP.
</QA>

<QA q="What is the difference between an A record and a CNAME?">
An A record maps a name directly to an IPv4 address. A CNAME maps a name to another name, which is then resolved further. CNAMEs are used for aliases to platform or load balancer host names that may change IPs; they cannot be used at the zone apex or alongside other records on the same name.
</QA>

<QA q="What is TTL and how does it affect a migration?">
TTL is how long, in seconds, resolvers and clients may cache a record. A long TTL means changes take that long to reach everyone. Before a migration, lower the TTL and wait for the old TTL to expire, then change the record so clients switch quickly, and raise the TTL again afterwards.
</QA>

<QA q="What are SPF, DKIM and DMARC?">
They are DNS TXT records for email authentication. SPF lists which servers may send mail for the domain, DKIM publishes a public key used to verify a cryptographic signature on each message, and DMARC tells receivers how to handle messages that fail SPF and DKIM alignment, such as quarantine or reject, and where to send reports.
</QA>

<QA q="What is a subdomain takeover?">
It happens when a DNS record, usually a CNAME, still points to a resource on an external platform that has been deleted. An attacker registers that resource name on the platform and then controls content served on the victim's subdomain, which can be used for phishing or cookie theft. Removing records when resources are deleted prevents it.
</QA>
