<BigIdea>
<Tr>
<En>
**DNS** (Domain Name System) is the internet's phone book: it turns names like `shop.example.com` into IP addresses like `203.0.113.10`. Your device asks a **resolver**, which walks a tree of servers (root → `.com` → the domain's own servers) and remembers the answer for a while (its **TTL**). Every website visit, every API call and every email starts with DNS.
</En>
<Ur>
**DNS** (Domain Name System) internet ki phone book hai: ye `shop.example.com` jaise naamon ko `203.0.113.10` jaise IP addresses me badalta hai. Aap ka device ek **resolver** se poochta hai, jo servers ke ek darakht par chalta hai (root → `.com` → domain ke apne servers) aur jawab kuch der yaad rakhta hai (us ka **TTL**). Har website visit, har API call aur har email DNS se shuru hoti hai.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

Computers connect with IP addresses, but nobody wants to type `142.250.181.14`. And IPs change: move your site to a new server and its IP changes, but the name stays. DNS keeps the mapping.

```text
 You type shop.example.com
   │
   ▼
 Browser / OS cache ── hit? → done
   │ miss
   ▼
 Recursive resolver (1.1.1.1)  ── cache hit? → answer
   │ miss: it walks the tree
   ├──► Root server:        "ask the .com servers at a.gtld-servers.net"
   ├──► .com TLD server:    "example.com is handled by ns1.dns-host.net"
   └──► Authoritative NS:   "shop.example.com A 203.0.113.10, TTL 300"
   │
   ▼
 Resolver caches it for 300 s and answers you → browser connects to 203.0.113.10:443
```

DNS mostly uses **UDP port 53** (TCP 53 for big answers), and more and more encrypted DNS: DNS-over-HTTPS (DoH) and DNS-over-TLS (DoT, port 853).

</En>
<Ur>

Computers IP addresses se jurte hain, lekin koi `142.250.181.14` type nahi karna chahta. Aur IPs badalte hain: site naye server par le jayen to IP badal jata hai, naam wahi rehta hai. DNS ye rabta yaad rakhta hai.

```text
 You type shop.example.com
   │
   ▼
 Browser / OS cache ── hit? → done
   │ miss
   ▼
 Recursive resolver (1.1.1.1)  ── cache hit? → answer
   │ miss: it walks the tree
```

DNS zyada tar **UDP port 53** istemal karta hai (bare jawabon ke liye TCP 53), aur barhte tor par encrypted DNS: DNS-over-HTTPS (DoH) aur DNS-over-TLS (DoT, port 853).

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Every connection starts with DNS.** If DNS breaks, "the internet is down" for users even when servers are fine.
- **Deploying sites:** pointing a domain to Vercel, Netlify, a VPS or a load balancer is DNS work.
- **Email:** without correct MX, SPF, DKIM and DMARC records, your emails land in spam, or others can fake them.
- **Migrations:** TTLs decide how fast a change reaches users.
- **Security:** domain hijacking, spoofing, subdomain takeover and look-alike phishing domains are major attacks.

</En>
<Ur>

- **Har connection DNS se shuru hota hai.** DNS toote to users ke liye "internet band" hai chahe servers theek hon.
- **Sites deploy karna:** domain ko Vercel, Netlify, VPS ya load balancer ki taraf karna DNS ka kaam hai.
- **Email:** sahi MX, SPF, DKIM aur DMARC records ke baghair aap ki emails spam me jati hain, ya doosre unhe naqli bana sakte hain.
- **Migrations:** TTL tay karte hain ke tabdeeli users tak kitni jaldi pohanche.
- **Security:** domain hijacking, spoofing, subdomain takeover aur milte julte phishing domains bare hamle hain.

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Domain names are a tree">

<Tr>
<En>

Read names **right to left**, from general to specific: root (`.`) → TLD (`com`) → domain (`example`) → subdomain (`shop`). The tree lets responsibility be **handed down**: the root knows who runs `.com`, `.com` knows who runs `example.com`, and the owner of `example.com` controls everything below it. The full name really ends with a dot: `shop.example.com.`

</En>
<Ur>

Naam **daayen se baayen** parhein, aam se khaas tak: root (`.`) → TLD (`com`) → domain (`example`) → subdomain (`shop`). Darakht zimmedari **neeche saunpne** deta hai: root jaanta hai `.com` kaun chalata hai, `.com` jaanta hai `example.com` kaun chalata hai, aur `example.com` ka malik us ke neeche sab sambhalta hai. Poora naam asal me dot par khatam hota hai: `shop.example.com.`

</Ur>
</Tr>

```python
name = "api.shop.example.com"
parts = name.split(".")
print("read right to left:")
for i in range(len(parts) - 1, -1, -1):
    print("  " + ".".join(parts[i:]))
```

```text output
read right to left:
  com
  example.com
  shop.example.com
  api.shop.example.com
```

</Step>

<Step title="Resolvers and authoritative servers">

<Tr>
<En>

A **recursive resolver** does the searching for clients and caches answers. **Authoritative servers** hold the real records for a zone and only answer about their own zones. Clients stay simple, and caching keeps DNS fast. Resolvers: your router, your ISP, `1.1.1.1` (Cloudflare), `8.8.8.8` (Google), the AWS VPC resolver. Your machine's resolver is set in `/etc/resolv.conf` (often `127.0.0.53`, a local cache).

</En>
<Ur>

**Recursive resolver** clients ke liye talaash karta hai aur jawab cache karta hai. **Authoritative servers** zone ke asli records rakhte hain aur sirf apne zones ke baare me jawab dete hain. Clients saada rehte hain, aur cache DNS ko tez rakhta hai. Resolvers: aap ka router, ISP, `1.1.1.1` (Cloudflare), `8.8.8.8` (Google), AWS VPC resolver. Aap ki machine ka resolver `/etc/resolv.conf` me hai (aksar `127.0.0.53`, ek local cache).

</Ur>
</Tr>

```bash
grep -E '^nameserver' /etc/resolv.conf | head -1 | sed -E 's/[0-9.]+$/<resolver IP>/'
```

```text output
nameserver <resolver IP>
```

</Step>

<Step title="Record types">

<Tr>
<En>

Each record has a **name**, a **type**, a **TTL** and a **value**. Different types answer different questions.

| Type | Maps a name to… | Example value | Typical use |
| --- | --- | --- | --- |
| `A` | IPv4 address | `203.0.113.10` | Website on a server |
| `AAAA` | IPv6 address | `2001:db8::10` | IPv6 |
| `CNAME` | Another name (alias) | `cname.vercel-dns.com` | Subdomain on Vercel, a load balancer, a CDN |
| `MX` | Mail server (with priority) | `10 mx1.mail.example.net` | Receiving email |
| `TXT` | Any text | `v=spf1 include:_spf.google.com ~all` | Verification, SPF, DKIM, DMARC |
| `NS` | Authoritative name servers | `ns1.cloudflare.com` | Delegation |
| `SOA` | Zone details | serial, refresh… | Zone management |
| `CAA` | Which CAs may issue certificates | `0 issue "letsencrypt.org"` | Certificate security |
| `SRV` | Service host and port | `_sip._tcp …` | Some protocols |
| `PTR` | IP → name (reverse DNS) | `mail.example.com` | Mail servers, logs |

</En>
<Ur>

Har record ka **naam**, **type**, **TTL** aur **value** hoti hai. Mukhtalif types mukhtalif sawalon ke jawab dete hain.

| Type | Naam ko kis se jorta hai… | Misaali value | Aam istemal |
| --- | --- | --- | --- |
| `A` | IPv4 address | `203.0.113.10` | Server par website |
| `AAAA` | IPv6 address | `2001:db8::10` | IPv6 |
| `CNAME` | Doosra naam (alias) | `cname.vercel-dns.com` | Vercel, load balancer, CDN par subdomain |
| `MX` | Mail server (tarjeeh ke saath) | `10 mx1.mail.example.net` | Email lena |
| `TXT` | Koi bhi text | `v=spf1 include:_spf.google.com ~all` | Tasdeeq, SPF, DKIM, DMARC |
| `NS` | Authoritative name servers | `ns1.cloudflare.com` | Zimmedari saunpna |
| `SOA` | Zone ki tafseel | serial, refresh… | Zone ka intezam |
| `CAA` | Kaunse CAs certificates de sakte hain | `0 issue "letsencrypt.org"` | Certificate security |
| `SRV` | Service ka host aur port | `_sip._tcp …` | Kuch protocols |
| `PTR` | IP → naam (reverse DNS) | `mail.example.com` | Mail servers, logs |

</Ur>
</Tr>

<Tr>
<En>A typical zone for a small business site:</En>
<Ur>Chhote karobar ki site ka aam zone:</Ur>
</Tr>

```text
example.com.        300   A      76.76.21.21                       ; apex → Vercel
www.example.com.    300   CNAME  cname.vercel-dns.com.
api.example.com.    300   A      203.0.113.10                      ; NestJS on a VPS
example.com.        3600  MX     1 smtp.google.com.                ; Google Workspace mail
example.com.        3600  TXT    "v=spf1 include:_spf.google.com ~all"
_dmarc.example.com. 3600  TXT    "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com"
example.com.        3600  CAA    0 issue "letsencrypt.org"
```

</Step>

<Step title="CNAME: an alias">

<Tr>
<En>

A CNAME says "this name is really that other name; look that one up". Platforms (Vercel, Netlify, AWS load balancers, CDNs) change their IPs, so pointing at their **name** keeps your record valid automatically.

Two rules: a CNAME **can't** be at the **apex** (`example.com` itself), and it can't share a name with other records. For the apex, providers offer `ALIAS`/`ANAME`, "CNAME flattening" (Cloudflare) or Route 53 **alias** records.

</En>
<Ur>

CNAME kehta hai "ye naam asal me wo doosra naam hai; use dhoondo". Platforms (Vercel, Netlify, AWS load balancers, CDNs) apne IPs badalte hain, isliye un ke **naam** ki taraf ishara aap ka record khud sahi rakhta hai.

Do usool: CNAME **apex** (`example.com` khud) par **nahi** ho sakta, aur doosre records ke saath ek naam share nahi kar sakta. Apex ke liye providers `ALIAS`/`ANAME`, "CNAME flattening" (Cloudflare) ya Route 53 **alias** records dete hain.

</Ur>
</Tr>

```text
$ dig +short www.example.com
cname.vercel-dns.com.        ← the CNAME
76.76.21.21                  ← the A record it finally resolved to
```

</Step>

<Step title="TTL and caching">

<Tr>
<En>

TTL tells resolvers how many seconds they may reuse an answer. Caching makes DNS fast, but also **delays changes**: with TTL 86400 (1 day), some users may see the old IP for a day. Before changing a record, **lower its TTL**, wait at least the **old** TTL, change it, and raise the TTL later. "DNS propagation" is mostly caches expiring.

</En>
<Ur>

TTL resolvers ko batata hai ke jawab kitne second dobara istemal kar sakte hain. Cache DNS ko tez banata hai, lekin **tabdeeli me der** bhi karta hai: TTL 86400 (1 din) ke saath kuch users ek din tak purana IP dekh sakte hain. Record badalne se pehle **TTL kam karein**, kam az kam **purane** TTL jitna intezar karein, badlein, aur baad me TTL wapas barhayen. "DNS propagation" zyada tar caches ka khatam hona hai.

</Ur>
</Tr>

```python
old_ttl, new_ttl = 86400, 300
print(f"1) lower TTL from {old_ttl}s to {new_ttl}s")
print(f"2) wait {old_ttl // 3600} hours so every cache has picked up the short TTL")
print(f"3) change the IP — users switch within ~{new_ttl // 60} minutes")
print("4) raise the TTL again once the migration is stable")
```

```text output
1) lower TTL from 86400s to 300s
2) wait 24 hours so every cache has picked up the short TTL
3) change the IP — users switch within ~5 minutes
4) raise the TTL again once the migration is stable
```

</Step>

<Step title="/etc/hosts: local overrides">

<Tr>
<En>

A local file mapping names to IPs, checked **before** DNS on most systems. Use it to test a new server before changing public DNS, name local services, or block domains. `getent hosts name` shows what the system resolves. Editing it needs `sudo`, and **remove test entries afterwards**. On Windows it's `C:\Windows\System32\drivers\etc\hosts`.

</En>
<Ur>

Local file jo naamon ko IPs se jorti hai, aur zyada tar systems par DNS se **pehle** dekhi jati hai. Public DNS badalne se pehle naya server test karne, local services ko naam dene, ya domains band karne ke liye istemal karein. `getent hosts name` dikhata hai system kya resolve karta hai. Ise badalne ke liye `sudo` chahiye, aur **test entries baad me hata dein**. Windows par ye `C:\Windows\System32\drivers\etc\hosts` hai.

</Ur>
</Tr>

```bash
cp /etc/hosts /tmp/hosts.backup
echo "127.0.0.1 shop.test" >> /etc/hosts
getent hosts shop.test
python3 -c 'import socket; print("Python resolves shop.test to", socket.gethostbyname("shop.test"))'
cp /tmp/hosts.backup /etc/hosts
getent hosts shop.test || echo "after removing the line: shop.test no longer resolves"
```

```text output
127.0.0.1       shop.test
Python resolves shop.test to 127.0.0.1
after removing the line: shop.test no longer resolves
```

<Step title="Email records: SPF, DKIM, DMARC">

<Tr>
<En>

Three TXT-based records that let receiving mail servers check that an email "from" your domain really is. Without them, anyone can send as your domain (phishing), and your real emails go to spam. Set them up as soon as the domain sends **any** email, including app emails via SendGrid, SES or Resend.

- **SPF:** which servers may send for the domain.
- **DKIM:** a public key to verify email signatures.
- **DMARC:** what receivers should do on failure (`none` → `quarantine` → `reject`) and where to send reports.

</En>
<Ur>

Teen TXT records jo email lene wale servers ko check karne dete hain ke aap ke domain "se" aayi email waqai aap ki hai. In ke baghair koi bhi aap ke domain ke naam se bhej sakta hai (phishing), aur aap ki asli emails spam me jati hain. Domain jaise hi **koi bhi** email bheje, inhe lagayen, SendGrid, SES ya Resend se app emails samet.

- **SPF:** kaunse servers domain ki taraf se bhej sakte hain.
- **DKIM:** email ke signatures check karne ki public key.
- **DMARC:** nakami par lene wale kya karein (`none` → `quarantine` → `reject`) aur reports kahan bhejein.

</Ur>
</Tr>

```text
example.com.                      TXT  "v=spf1 include:_spf.google.com include:amazonses.com -all"
google._domainkey.example.com.    TXT  "v=DKIM1; k=rsa; p=MIIBIjANBgkqh…"
_dmarc.example.com.               TXT  "v=DMARC1; p=reject; rua=mailto:dmarc@example.com"
```

</Step>

<Step title="DNS in clouds and containers">

<Tr>
<En>

Internal DNS gives names to services inside private networks, so they find each other by name (`db`, `redis`) instead of hard-coded IPs that change. Docker's built-in DNS (`127.0.0.11`) resolves Compose service names; Kubernetes CoreDNS resolves `service.namespace.svc.cluster.local`; AWS has Route 53 private zones. In Compose, the service name **is** the hostname: `DATABASE_URL=postgres://shop@db:5432/shop`.

</En>
<Ur>

Andaroni DNS private networks ke andar services ko naam deta hai, taa ke wo badalne wale pakke IPs ke bajaye ek doosre ko naam (`db`, `redis`) se dhoondein. Docker ka built-in DNS (`127.0.0.11`) Compose service naam resolve karta hai; Kubernetes ka CoreDNS `service.namespace.svc.cluster.local`; AWS me Route 53 private zones hain. Compose me service ka naam **hi** hostname hai: `DATABASE_URL=postgres://shop@db:5432/shop`.

</Ur>
</Tr>

```bash
python3 -c 'import socket; ips={a[4][0] for a in socket.getaddrinfo("localhost", None)}; print("localhost resolves to 127.0.0.1:", "127.0.0.1" in ips)'
```

```text output
localhost resolves to 127.0.0.1: True
```

```bash
  if [[ $v == CNAME* ]]; then echo "$1 is an alias for ${v#CNAME }"; resolve "${v#CNAME }"
```

<DeepDive title="Real world: moving a live site with zero downtime">

```text
Day 1   dig example.com → TTL 3600. Lower it: A example.com 203.0.113.10, TTL 300.
Day 2   (old TTL has expired everywhere) Deploy the site on the new server 198.51.100.20.

        Switch: A example.com 198.51.100.20 (TTL 300).

Day 4   Raise TTL back to 3600. Shut down the old server.
```

<DeepDive title="Security lens">

Whoever controls your DNS controls where your users and your email go. Protect it like a production password.

- **Registrar and DNS accounts:** strong passwords, **MFA**, registrar lock, auto-renew. Expired domains get bought by attackers.
- **Subdomain takeover:** a CNAME like `shop.example.com → myshop.herokuapp.com` stays after the app is deleted; an attacker claims `myshop` on that platform and serves content on **your** subdomain. Remove records when you delete resources.
- **DNS spoofing / cache poisoning:** fake answers redirect users; **DNSSEC** signs records, and HTTPS certificates stop most impersonation.
- **Email spoofing:** SPF + DKIM + DMARC with `p=reject` stops attackers sending as your domain.
- **CAA records** limit which certificate authorities can issue certificates for your domain.
- **Reconnaissance:** attackers list subdomains (certificate transparency logs, brute force) to find forgotten, unpatched systems; keep an inventory.
- **DNS tunnelling:** malware can hide data in DNS queries; watching DNS logs is a standard detection technique.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What happens when you type a domain name into the browser, from a DNS point of view?">
The browser and operating system check their caches and the hosts file. If there is no answer, the OS asks its configured recursive resolver. The resolver, if it has no cached answer, asks a root server, which refers it to the TLD servers for .com; those refer it to the domain's authoritative name servers, which return the record. The resolver caches the answer for its TTL and returns it, and the browser connects to that IP.
</QA>

<QA q="What is the difference between an A record and a CNAME?">
An A record maps a name directly to an IPv4 address. A CNAME maps a name to another name, which is then resolved further. CNAMEs are used for aliases to platform or load balancer host names that may change IPs; they cannot be used at the zone apex or alongside other records on the same name.
</QA>

<QA q="What is TTL and how does it affect a migration?">
TTL is how long, in seconds, resolvers and clients may cache a record. A long TTL means changes take that long to reach everyone. Before a migration, lower the TTL and wait for the old TTL to expire, then change the record so clients switch quickly, and raise the TTL again afterwards.
</QA>

<QA q="What are SPF, DKIM and DMARC?">
They are DNS TXT records for email authentication. SPF lists which servers may send mail for the domain, DKIM publishes a public key used to verify a cryptographic signature on each message, and DMARC tells receivers how to handle messages that fail SPF and DKIM alignment, such as quarantine or reject, and where to send reports.
</QA>

<QA q="What is a subdomain takeover?">
It happens when a DNS record, usually a CNAME, still points to a resource on an external platform that has been deleted. An attacker registers that resource name on the platform and then controls content served on the victim's subdomain, which can be used for phishing or cookie theft. Removing records when resources are deleted prevents it.
</QA>

</DeepDive>
