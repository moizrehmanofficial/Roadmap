<BigIdea>
<Tr>
<En>
Before TCP sends any data, both sides do a **three-way handshake**: the client sends **SYN** ("can we talk?"), the server answers **SYN-ACK** ("yes, can you hear me?"), the client sends **ACK** ("yes"). Now the connection is **ESTABLISHED**. Every byte is numbered and acknowledged, so losses get resent. Connections end politely with **FIN** or abruptly with **RST**. Each new connection costs a round trip, which is why reusing connections matters.
</En>
<Ur>
TCP koi data bhejne se pehle dono taraf **three-way handshake** karti hain: client **SYN** bhejta hai ("baat kar sakte hain?"), server **SYN-ACK** se jawab deta hai ("haan, meri awaaz aa rahi hai?"), client **ACK** bhejta hai ("haan"). Ab connection **ESTABLISHED** hai. Har byte ko number aur tasdeeq milti hai, isliye khoya data dobara bheja jata hai. Connections tameez se **FIN** ya achanak **RST** se khatam hote hain. Har naya connection ek round trip ka kharcha hai, isi liye connections dobara istemal karna ahem hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

TCP promises reliable, ordered delivery. To keep that promise, both sides first confirm they can reach each other and agree on the numbers they'll use to count bytes.

```text
 client                                          server (LISTEN on :443)
   │                                                 │
   │ ── SYN, seq=1000 ─────────────────────────────► │   "let's talk; I'll start counting at 1000"
   │ ◄──────────────────── SYN-ACK, seq=5000, ack=1001│   "OK; I start at 5000; next I expect 1001"
   │ ── ACK, ack=5001 ─────────────────────────────► │   "got it"
   │              ESTABLISHED (1 round trip spent)   │
   │ ── data: GET / … (seq=1001) ──────────────────► │
   │ ◄────────────────────────── data: 200 OK … (ack) │
   │ ── FIN ───────────────────────────────────────► │   "I'm done sending"
   │ ◄─────────────────────────────────────── ACK, FIN│   "OK, me too"
   │ ── ACK ───────────────────────────────────────► │
   │ TIME_WAIT (waits a little before forgetting)    │ CLOSED
```

</En>
<Ur>

TCP bharosemand, tarteeb wali delivery ka wada karta hai. Ye wada nibhane ke liye dono taraf pehle tasdeeq karti hain ke ek doosre tak pohanch sakti hain aur bytes ginne ke numbers par mutafiq hoti hain.


</What>
<Why>
<Tr>
<En>

- **Latency:** every new TCP connection costs one round trip before any data, and HTTPS adds TLS on top. To a server 150 ms away that's 300+ ms before the first byte.
- **Debugging:** states in `ss` reveal leaks (`CLOSE_WAIT` piling up), overload (many `SYN_RECV`), or blocked ports (SYN with no answer).
- **Scaling:** thousands of `TIME_WAIT` sockets and exhausted ports are real problems behind proxies.
- **Security:** SYN floods, port scans and resets all happen at the handshake level.

</En>
<Ur>

- **Der:** har naya TCP connection kisi bhi data se pehle ek round trip leta hai, aur HTTPS ooper se TLS jorta hai. 150 ms door server ke liye pehle byte se pehle 300+ ms.
- **Debugging:** `ss` me states leaks (`CLOSE_WAIT` ka dher), bojh (bohot se `SYN_RECV`), ya band ports (SYN ka jawab nahi) dikhati hain.
- **Barhana:** hazaron `TIME_WAIT` sockets aur khatam hote ports proxies ke peeche asli masle hain.
- **Security:** SYN floods, port scans aur resets sab handshake ki satah par hote hain.

</Ur>
</Tr>
</Why>

## Picture it

<Tr>
<En>

A **phone call on a bad line**:

- You: "Hello, can you hear me?" (**SYN**)
- Friend: "Yes, I hear you. Can you hear me?" (**SYN-ACK**)
- You: "Yes, I hear you." (**ACK**). Now you start talking.

During the call your friend says "got it" after each sentence (**ACK**). If they say "sorry, I missed that", you repeat it (**retransmission**). At the end: "I'm done, bye" / "OK, bye" (**FIN**). Slamming the phone down is **RST**.

</En>
<Ur>

**Kharab line par phone call**:

- Aap: "Hello, meri awaaz aa rahi hai?" (**SYN**)
- Dost: "Haan, sun raha hoon. Meri awaaz aa rahi hai?" (**SYN-ACK**)
- Aap: "Haan, sun raha hoon." (**ACK**). Ab baat shuru.

Call ke dauran dost har jumle ke baad "samajh gaya" kehta hai (**ACK**). Agar kahe "maaf karna, wo reh gaya", to aap dohrate hain (**retransmission**). Aakhir me: "Bas, Allah Hafiz" / "Theek, Allah Hafiz" (**FIN**). Phone patakh dena **RST** hai.

</Ur>
</Tr>

<Step title="The three-way handshake">

<Tr>
<En>

SYN, SYN-ACK, ACK: both sides confirm they can send **and** receive, and agree on starting sequence numbers (random, for security). A real capture to a local server:

</En>
<Ur>

SYN, SYN-ACK, ACK: dono taraf tasdeeq karti hain ke bhej **aur** le sakti hain, aur shuru ke sequence numbers par mutafiq hoti hain (hifazat ke liye ittefaqi). Local server ka asli capture:

</Ur>
</Tr>

```text
$ sudo tcpdump -i lo -n 'tcp port 3480'
IP 127.0.0.1.51522 > 127.0.0.1.3480: Flags [S],  seq 3051962283, win 65495, length 0
IP 127.0.0.1.3480 > 127.0.0.1.51522: Flags [S.], seq 1281893570, ack 3051962284, win 65483, length 0
IP 127.0.0.1.51522 > 127.0.0.1.3480: Flags [.],  ack 1, win 512, length 0
```

<Tr>
<En>In tcpdump: `[S]` = SYN, `[S.]` = SYN-ACK (the dot means ACK), `[.]` = ACK, `[P.]` = data, `[F.]` = FIN, `[R]` = reset. The handshake costs **one round trip**, and you can measure it:</En>
<Ur>tcpdump me: `[S]` = SYN, `[S.]` = SYN-ACK (dot ka matlab ACK), `[.]` = ACK, `[P.]` = data, `[F.]` = FIN, `[R]` = reset. Handshake **ek round trip** leta hai, aur aap ise naap sakte hain:</Ur>
</Tr>

```bash

curl -s -o /dev/null -w 'connect (handshake) done after: %{time_connect}s\nfirst byte after:              %{time_starttransfer}s\n' http://127.0.0.1:3480/ \
  | sed -E 's/[0-9]+\.[0-9]+s/Xs/'
kill $srv
```

```text output
connect (handshake) done after: Xs
first byte after:              Xs
```

<Happened>
<Tr>
<En>On localhost both are tiny (so we masked them). Against a real server, `time_connect` ≈ one RTT. Try `curl -w '%{time_connect}\n' -o /dev/null -s https://example.com` from your machine.</En>
<Ur>Localhost par dono bohot chhote hain (isliye chhupaye). Asli server ke saath `time_connect` ≈ ek RTT. Apni machine se `curl -w '%{time_connect}\n' -o /dev/null -s https://example.com` aazmayen.</Ur>
</Tr>
</Happened>

<Step title="Sequence numbers and acknowledgements">

<Tr>
<En>

Every byte sent is numbered, and the receiver replies with the number of the **next byte it expects**. This detects lost and duplicate data and reorders out-of-order packets. If no ACK arrives in time, the sender **resends**. Starting numbers are random so attackers can't guess them and inject data.

</En>
<Ur>

Har bheja gaya byte number paata hai, aur paane wala **agle mutawaqqa byte** ka number lautata hai. Is se khoya aur do dafa aaya data pakra jata hai aur be-tarteeb packets sahi kiye jate hain. Waqt par ACK na aaye to bhejne wala **dobara bhejta** hai. Shuru ke numbers ittefaqi hote hain taa ke hamla awar andaza laga kar data na ghusa sakein.

</Ur>
</Tr>

```python
data = "GET /products HTTP/1.1\r\n\r\n".encode()
seq = 1001                                  # first data byte (after the SYN used 1000)
segments = [data[i:i + 10] for i in range(0, len(data), 10)]
for s in segments:
    print(f"send seq={seq:<5} {len(s):>2} bytes → receiver replies ack={seq + len(s)}")
    seq += len(s)
```

```text output
send seq=1001  10 bytes → receiver replies ack=1011
send seq=1011  10 bytes → receiver replies ack=1021
send seq=1021   6 bytes → receiver replies ack=1027
```

<Happened>
<Tr>
<En>"ack=1021" means "I have everything **before** byte 1021; send 1021 next". If the second segment were lost, the receiver would keep saying `ack=1011`, and the sender would resend it.</En>
<Ur>"ack=1021" ka matlab "byte 1021 se **pehle** sab mil gaya; ab 1021 bhejo". Agar doosra segment kho jata, to paane wala `ack=1011` kehta rehta, aur bhejne wala use dobara bhejta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Closing: FIN and TIME_WAIT">

<Tr>
<En>

Each side sends **FIN** when it's done sending, and the other acknowledges. The side that closes first enters **TIME_WAIT** (about 60 s on Linux) so late packets from the old connection aren't mistaken for a new one using the same ports. This is normal. Thousands of them mean connections aren't **reused**: fix that with keep-alive, not kernel tweaks.

</En>
<Ur>

Har taraf bhejna khatam karne par **FIN** bhejti hai, aur doosri tasdeeq karti hai. Pehle band karne wali taraf **TIME_WAIT** me jati hai (Linux par taqreeban 60 s) taa ke purane connection ke der se aaye packets usi ports wale naye connection ke na samjhe jayen. Ye aam baat hai. Hazaron ka matlab hai connections **dobara istemal** nahi ho rahe: ise keep-alive se theek karein, kernel chherne se nahi.

</Ur>
</Tr>

```bash
port=$((20000 + RANDOM % 20000))      # a random port, so old runs don't interfere
python3 -m http.server $port --bind 127.0.0.1 > /dev/null 2>&1 & srv=$!; sleep 1
for i in 1 2 3; do curl -s -o /dev/null http://127.0.0.1:$port/; done
ss -tan state time-wait | grep -c ":$port" | sed 's/$/ connection(s) in TIME_WAIT after 3 short requests/'
kill $srv
```

```text output
3 connection(s) in TIME_WAIT after 3 short requests
```

</Step>

<Step title="RST: aborting a connection">

<Tr>
<En>

A **reset** kills a connection immediately, with no goodbye. It's sent when a SYN reaches a closed port ("connection refused"), when a program crashes, or by firewalls and load balancers cutting connections. `ECONNRESET` ("connection reset by peer") in your logs means the **other side** aborted: check its logs, timeouts and limits.

</En>
<Ur>

**Reset** connection ko foran, bina alvida, khatam karta hai. Ye tab bheja jata hai jab SYN band port tak pohanche ("connection refused"), jab program crash ho, ya firewalls aur load balancers connections kaatein. Logs me `ECONNRESET` ("connection reset by peer") ka matlab hai **doosri taraf** ne khatam kiya: us ke logs, timeouts aur hadein dekhein.

</Ur>
</Tr>

```text
$ sudo tcpdump -i lo -n 'tcp port 3999'
IP 127.0.0.1.40112 > 127.0.0.1.3999: Flags [S], seq 991827364, length 0
IP 127.0.0.1.3999 > 127.0.0.1.40112: Flags [R.], seq 0, ack 991827365, length 0   ← nothing listens: reset = "refused"
```

</Step>

<Step title="Connection states (what ss shows)">

<Tr>
<En>

A quick look at state counts tells you if a server is healthy, overloaded or leaking. Count them with `ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c`.

| State | Meaning | Worry if… |
| --- | --- | --- |
| `LISTEN` | Server waiting for connections | A port you didn't expect |
| `SYN-SENT` | Client sent SYN, waiting | Many: target unreachable / filtered |
| `SYN-RECV` | Server got SYN, sent SYN-ACK, waiting | Thousands: possible **SYN flood** |
| `ESTABLISHED` | Open, data can flow | Far more than expected: leak or attack |
| `FIN-WAIT-1/2` | We closed, waiting for the other side | |
| `CLOSE-WAIT` | **Other side closed; our app hasn't yet** | Growing = **bug in your app** |
| `TIME-WAIT` | Closed by us, waiting before forgetting | Huge numbers = no reuse |
| `LAST-ACK` | Closing, waiting for the final ACK | |

</En>
<Ur>

States ki ginti par ek nazar batati hai ke server theek hai, bojh me hai ya leak kar raha hai. Inhe `ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c` se ginein.

| State | Matlab | Fikr karein agar… |
| --- | --- | --- |
| `LISTEN` | Server connections ka intezar kar raha | Aisa port jis ki umeed na thi |
| `SYN-SENT` | Client ne SYN bheja, intezar | Bohot se: target pohanch se bahar / filtered |
| `SYN-RECV` | Server ko SYN mila, SYN-ACK bheja, intezar | Hazaron: mumkina **SYN flood** |
| `ESTABLISHED` | Khula, data chal sakta hai | Umeed se kahin zyada: leak ya hamla |
| `FIN-WAIT-1/2` | Hum ne band kiya, doosri taraf ka intezar | |
| `CLOSE-WAIT` | **Doosri taraf ne band kiya; hamari app ne abhi nahi** | Barhte hue = **aap ki app me bug** |
| `TIME-WAIT` | Hum ne band kiya, bhoolne se pehle intezar | Bohot zyada = dobara istemal nahi |
| `LAST-ACK` | Band ho raha, aakhri ACK ka intezar | |

</Ur>
</Tr>

```bash
python3 - <<'EOF'
import socket, subprocess, time
srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 0)); srv.listen()          # port 0 = let the OS pick a free port
port = srv.getsockname()[1]
cli = socket.create_connection(("127.0.0.1", port)); conn, _ = srv.accept()
def states():
    out = subprocess.run(["ss", "-tan"], capture_output=True, text=True).stdout
    return sorted({l.split()[0] for l in out.splitlines() if f":{port}" in l})
print("after connect:         ", states())
cli.close(); time.sleep(0.2)          # the client closes; the server code "forgets" to close conn
print("client closed, server didn't:", states())
conn.close(); srv.close()
EOF
```

```text output
after connect:          ['ESTAB', 'LISTEN']
client closed, server didn't: ['CLOSE-WAIT', 'FIN-WAIT-2', 'LISTEN']
```

<Happened>
<Tr>
<En>The server side sat in **CLOSE-WAIT** because our "app" never called `close()`. In a real server, each forgotten socket stays like this until the process runs out of file descriptors and crashes.</En>
<Ur>Server ki taraf **CLOSE-WAIT** me rahi kyun ke hamari "app" ne kabhi `close()` nahi chalaya. Asli server me har bhoola hua socket aise hi rehta hai jab tak process ke file descriptors khatam ho kar wo crash na ho jaye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Keep-alive and connection reuse">

<Tr>
<En>

Keep a connection open after one request so the next ones skip the handshake. It saves one round trip (plus TLS) per request: often the biggest speed win for API calls between services. Reuse **one** HTTP client object instead of creating one per request, and make sure the **load balancer's idle timeout** is longer than the client's, or you get random `ECONNRESET`.

</En>
<Ur>

Ek request ke baad connection khula rakhein taa ke agli requests handshake chhor dein. Ye har request par ek round trip (aur TLS) bachata hai: services ke darmiyan API calls me aksar sab se bari raftar ki jeet. Har request par naya banane ke bajaye **ek** HTTP client object dobara istemal karein, aur yaqeeni banayen ke **load balancer ka idle timeout** client se lamba ho, warna ittefaqi `ECONNRESET` milte hain.

</Ur>
</Tr>

```bash
cat > keepalive.mjs <<'EOF'
import http from "node:http";
http.createServer((req, res) => res.end("ok")).listen(3483, "127.0.0.1");   // Node keeps connections alive by default
EOF
node keepalive.mjs & srv=$!; sleep 0.5
echo "3 separate curl runs (3 new handshakes):"
for i in 1 2 3; do curl -s -o /dev/null -w '  new connections: %{num_connects}\n' http://127.0.0.1:3483/; done
echo "1 curl run, 3 requests on one kept-alive connection:"
curl -s -o /dev/null -o /dev/null -o /dev/null -w '  new connections: %{num_connects}\n' \
  http://127.0.0.1:3483/a http://127.0.0.1:3483/b http://127.0.0.1:3483/c
kill $srv
```

```text output
3 separate curl runs (3 new handshakes):
  new connections: 1
  new connections: 1
  new connections: 1
1 curl run, 3 requests on one kept-alive connection:
  new connections: 1
  new connections: 0
  new connections: 0
```

<Happened>
<Tr>
<En>In the second case only the first request paid for a handshake; requests two and three reused the open connection.</En>
<Ur>Doosri soorat me sirf pehli request ne handshake ki qeemat di; doosri aur teesri ne khula connection dobara istemal kiya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Connection pools for databases">

<Tr>
<En>

A database connection costs a handshake, often TLS, login, and server memory (PostgreSQL starts a process per connection). A **pool** keeps connections open; the app borrows and returns them. Keep `pool size × app instances` below the database's `max_connections`. Serverless functions need a pooler (PgBouncer, RDS Proxy).

</En>
<Ur>

Database connection handshake, aksar TLS, login, aur server ki memory leta hai (PostgreSQL har connection par ek process chalata hai). **Pool** connections khule rakhta hai; app inhe udhaar le kar wapas karti hai. `pool size × app instances` ko database ke `max_connections` se kam rakhein. Serverless functions ko pooler (PgBouncer, RDS Proxy) chahiye.

</Ur>
</Tr>

```python
app_instances, pool_size, db_max = 12, 20, 200
total = app_instances * pool_size
print(f"{app_instances} app instances × pool {pool_size} = {total} connections vs database limit {db_max}")
print("→ OK" if total <= db_max else f"→ TOO MANY: reduce pool to {db_max // app_instances} or add PgBouncer")
```

```text output
12 app instances × pool 20 = 240 connections vs database limit 200
→ TOO MANY: reduce pool to 16 or add PgBouncer
```

</Step>

<Step title="Timeouts">

<Tr>
<En>

Without timeouts, one slow dependency makes every request hang, connections pile up, and the whole service falls over. Set a short **connect timeout** (a few seconds) and a sensible **request timeout** on every outgoing call: `curl --connect-timeout 3 --max-time 10`, or `fetch(url, { signal: AbortSignal.timeout(5000) })`.

</En>
<Ur>

Timeouts ke baghair ek dheemi dependency har request ko latka deti hai, connections ka dher lag jata hai, aur poori service gir jati hai. Har bahar jane wali call par chhota **connect timeout** (chand second) aur maqool **request timeout** lagayen: `curl --connect-timeout 3 --max-time 10`, ya `fetch(url, { signal: AbortSignal.timeout(5000) })`.

</Ur>
</Tr>

```text
$ time curl -s --connect-timeout 3 http://10.255.255.1/
real    0m3.004s          ← gave up after 3 s instead of hanging for minutes
$ echo $?
28                        ← curl's exit code for "timeout"
```

</Step>

<Step title="SYN floods">

<Tr>
<En>

An attacker sends huge numbers of SYNs (often from fake IPs) and never finishes the handshake, filling the server's queue of half-open connections, so real users' SYNs get dropped. You see it as thousands of `SYN-RECV`. Defences: **SYN cookies** (on by default in Linux), cloud DDoS protection (AWS Shield, Cloudflare), and load balancers that absorb handshakes.

</En>
<Ur>

Hamla awar bohot zyada SYNs bhejta hai (aksar naqli IPs se) aur handshake kabhi poora nahi karta, jis se server ki aadhe khule connections ki qataar bhar jati hai, aur asli users ke SYNs phenk diye jate hain. Ye hazaron `SYN-RECV` ki shakal me nazar aata hai. Hifazat: **SYN cookies** (Linux me pehle se on), cloud DDoS protection (AWS Shield, Cloudflare), aur load balancers jo handshakes khud sambhalte hain.

</Ur>
</Tr>

```text
$ ss -tan state syn-recv | wc -l
48211                                  ← normal is a handful; this is a SYN flood
$ sysctl net.ipv4.tcp_syncookies
net.ipv4.tcp_syncookies = 1            ← kernel answers with cookies, keeping no state per SYN
```

</Step>

## Common mistakes

<Compare>
<Bad title="New client per request">

```text
app.get("/pay", async () => {
  const client = new HttpClient();     // new connection + handshake every time
  return client.post(providerUrl, …);
});
```

</Bad>
<Good title="One shared client with keep-alive and a timeout">

```text
const client = new HttpClient({ keepAlive: true, timeoutMs: 5000 });
app.get("/pay", async () => client.post(providerUrl, …));
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Ignoring CLOSE-WAIT**: it's always a bug on **your** side (the app didn't close sockets).
- **Panicking about TIME-WAIT**: usually normal; fix it with reuse, not risky kernel tweaks.
- **No timeouts** on outgoing calls.
- **Mismatched idle timeouts** (load balancer 60 s, app keep-alive 120 s) → random `ECONNRESET` and 502s.
- **Database pools too large** across many instances, exhausting `max_connections`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **CLOSE-WAIT nazar andaz karna**: ye hamesha **aap ki** taraf ka bug hai (app ne sockets band nahi kiye).
- **TIME-WAIT se ghabrana**: aam tor par normal; ise dobara istemal se theek karein, khatarnak kernel tabdeeliyon se nahi.
- **Bahar jane wali calls par timeouts na hona.**
- **Idle timeouts ka mel na hona** (load balancer 60 s, app keep-alive 120 s) → ittefaqi `ECONNRESET` aur 502.
- **Kai instances par bohot bare database pools**, jo `max_connections` khatam kar dete hain.

</Ur>

<DeepDive title="Real world: EMFILE every afternoon">

A Node.js API started failing every afternoon with `EMFILE: too many open files`. Investigation:

```text
$ ss -tanp | awk 'NR>1 {print $1}' | sort | uniq -c
  31  ESTAB
 9874 CLOSE-WAIT        ← growing all day
$ ss -tanp state close-wait | head -2
CLOSE-WAIT 0 0 10.0.11.20:44310 10.0.30.5:443 users:(("node",pid=2314,fd=8123))
```

Thousands of sockets in `CLOSE-WAIT` towards `10.0.30.5:443` (a payment provider). The code created a new HTTP client for every request and, on errors, never read or destroyed the response, so sockets were never closed. The fix: one shared HTTP client with keep-alive and a timeout, and always reading or destroying response bodies. `CLOSE-WAIT` dropped to zero and the crashes stopped.

</DeepDive>

<DeepDive title="Security lens">

The handshake is the first thing every attacker and scanner touches. Understanding it explains scans, floods and resets.

- **Port scanners** send SYNs: SYN-ACK = open, RST = closed, nothing = filtered. Your firewall decides which of these an attacker sees.
- **SYN floods:** keep SYN cookies on and put public services behind DDoS-protected load balancers or CDNs.
- **Random initial sequence numbers** prevent TCP session hijacking by guessing.
- **Slowloris-style attacks** hold many connections open slowly (layer 7): set header/body timeouts in your reverse proxy.
- **Connection limits per IP** (nginx `limit_conn`, load balancer settings) limit abuse.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Explain the TCP three-way handshake.">
The client sends a SYN with a random initial sequence number. The server replies with SYN-ACK, acknowledging the client's sequence number plus one and sending its own random initial sequence number. The client replies with ACK, acknowledging the server's number. Both sides have now confirmed they can send and receive and agreed on sequence numbers, so the connection is established. It costs one round trip before data can flow.
</QA>

<QA q="What does a large number of CLOSE_WAIT connections indicate?">
The remote side has closed its half of the connection, but the local application has not called close on the socket. A growing CLOSE_WAIT count means the application is leaking sockets, for example not closing connections or not consuming responses on error paths, and will eventually run out of file descriptors.
</QA>

<QA q="What is TIME_WAIT and is it a problem?">
TIME_WAIT is the state of the side that closed the connection first; it keeps the connection details for a short period so delayed packets from the old connection are not confused with a new one using the same ports. It is normal. Very large numbers indicate many short-lived connections, which is better fixed with keep-alive and connection pooling than with kernel tweaks.
</QA>

<QA q="What is a SYN flood and how is it mitigated?">
An attacker sends many SYN packets, often with spoofed source addresses, and never completes the handshake, filling the server's queue of half-open connections so legitimate clients cannot connect. Mitigations include SYN cookies, larger backlogs, rate limiting, and DDoS protection at the network edge such as cloud load balancers or CDNs.
</QA>

</DeepDive>
