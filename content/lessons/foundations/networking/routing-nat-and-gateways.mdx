<BigIdea>
<Tr>
<En>
A **router** connects networks and moves each packet one **hop** closer to its destination using a **routing table**: a list of destination ranges and where to send them. The most specific match wins, and `0.0.0.0/0` means "everything else". **NAT** lets many devices with **private** IPs share one **public** IP: your home router does it, and so do cloud **NAT gateways**.
</En>
<Ur>
**Router** networks ko jorta hai aur har packet ko **routing table** ki madad se manzil ki taraf ek **hop** aage barhata hai: manzil ki ranges aur unhe kahan bhejna hai, ki list. Sab se khaas milta hua rule jeetta hai, aur `0.0.0.0/0` ka matlab "baqi sab". **NAT** **private** IPs wale bohot se devices ko ek **public** IP share karne deta hai: aap ka ghar ka router ye karta hai, aur cloud ke **NAT gateways** bhi.
</Ur>

## At a glance

<Glance>
<What>
<Tr>
<En>

Your laptop only knows its own little network. A Google server is many networks away: through your router, your ISP, internet backbones and Google's network. No single device knows the whole path; each router only decides the **next step**.

```text
laptop 192.168.1.20 ──► home router (NAT) ──► ISP routers ──► internet backbone ──► Google routers ──► server
           │                    │
   route: default via    replaces source 192.168.1.20 with the home's public IP 39.x.x.x
   192.168.1.1
```

Each router: 1) reads the **destination IP**, 2) finds the best route, 3) lowers the packet's TTL by 1, 4) sends it to the next hop.

</En>
<Ur>

Aap ka laptop sirf apna chhota network jaanta hai. Google ka server kai networks door hai: aap ka router, ISP, internet ki bari lines aur Google ka network. Koi ek device poora raasta nahi jaanta; har router sirf **agla qadam** tay karta hai.

```text
laptop 192.168.1.20 ──► home router (NAT) ──► ISP routers ──► internet backbone ──► Google routers ──► server
           │                    │
   route: default via    replaces source 192.168.1.20 with the home's public IP 39.x.x.x
   192.168.1.1
```

Har router: 1) **manzil ka IP** parhta hai, 2) behtareen raasta dhoondta hai, 3) packet ka TTL 1 kam karta hai, 4) agle hop ko bhejta hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Cloud networking is routing:** every subnet's route table decides if it's public, private or isolated.
- **"Private servers can't download updates"**: they need a NAT gateway route.
- **VPNs, VPC peering, Docker and Kubernetes** all add routes.
- **"Works from here, not from there"** is mostly routing and NAT.
- **Security:** NAT hides internal addresses and drops unsolicited inbound connections; routes decide what can reach what.

</En>
<Ur>

- **Cloud networking routing hi hai:** har subnet ki route table tay karti hai ke wo public, private ya alag thalag hai.
- **"Private servers updates download nahi kar sakte"**: unhe NAT gateway ka raasta chahiye.
- **VPNs, VPC peering, Docker aur Kubernetes** sab routes jorte hain.
- **"Yahan se chalta hai, wahan se nahi"** zyada tar routing aur NAT hai.
- **Security:** NAT andaroni addresses chhupata hai aur bin bulaye aane wale connections phaink deta hai; routes tay karte hain kya kahan pohanch sakta hai.

</Ur>

## Picture it

<Tr>
<En>

**Road signs at every junction.** Driving from Austin to Houston, you don't need the whole map at each junction: the sign says "Dallas → left, San Antonio → right, **all other cities → highway**". Each junction is a **router**, the signs are its **routing table**, and "all other cities" is the **default route**.

**NAT** is an **office reception with one phone number**: 50 employees share one public number. When an employee calls out, reception notes who called so the reply goes to the right desk. Outsiders can't call an employee directly unless reception has a rule ("calls for extension 20 → Alex's desk"): that's **port forwarding**.

</En>
<Ur>

**Har chauraahe par sarak ke nishan.** Austin se Houston jate hue har chauraahe par poora naqsha nahi chahiye: nishan kehta hai "Dallas → baayen, San Antonio → daayen, **baqi saare shehar → highway**". Har chauraha ek **router** hai, nishan us ki **routing table** hain, aur "baqi saare shehar" **default route** hai.

**NAT** **ek phone number wala office reception** hai: 50 mulazim ek public number share karte hain. Jab koi mulazim bahar call karta hai, reception note karti hai ke kis ne kiya taa ke jawab sahi desk tak jaye. Bahar wale kisi mulazim ko seedha call nahi kar sakte jab tak reception ka rule na ho ("extension 20 ki calls → Alex ki desk"): ye **port forwarding** hai.

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="The routing table">

<Tr>
<En>

Every device that sends IP packets (laptop, server, router) has a list of rules: "packets to **this range** go **out this interface**, **via this next hop**". Routes without `via` are directly connected networks (deliver on the LAN); routes with `via` go to a router.

</En>
<Ur>

IP packets bhejne wale har device (laptop, server, router) ke paas rules ki list hoti hai: "**is range** ke packets **is interface** se, **is agle hop** ke zariye". Bina `via` wale routes seedhe jure networks hain (LAN par pohanchao); `via` wale router ko jate hain.

</Ur>
</Tr>

```bash
ip route | head -3 | sed -E 's/[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+/<ip>/g; s/<ip>\/[0-9]+/<network>/g' | awk '{print $1, $2, $3}'
```

```text output
default via <ip>
<network> dev eth0
```

<Tr>
<En>A typical laptop table:</En>
<Ur>Aam laptop ki table:</Ur>
</Tr>

```text
$ ip route
default via 192.168.1.1 dev wlan0             ← everything else → the router
192.168.1.0/24 dev wlan0 src 192.168.1.20     ← my LAN: deliver directly
172.17.0.0/16 dev docker0 src 172.17.0.1      ← Docker's bridge network
10.100.0.0/16 dev wg0                         ← office VPN tunnel
```

</Step>

<Step title="Longest prefix match">

<Tr>
<En>

When several routes match, the one with the **longest prefix** (most specific, biggest `/N`) wins. That lets you add exceptions on top of general rules: "everything to the internet, **except** 10.100.0.0/16 to the VPN". Cloud route tables use the same rule.

</En>
<Ur>

Jab kai routes milte hon, to **sab se lamba prefix** (sab se khaas, sab se bara `/N`) jeetta hai. Is se aam rules ke ooper istisna jore ja sakte hain: "sab internet ko, **siwaye** 10.100.0.0/16 ke jo VPN ko". Cloud route tables bhi yahi usool istemal karti hain.

</Ur>
</Tr>

```python
import ipaddress
routes = {
    "0.0.0.0/0": "default → home router 192.168.1.1",
    "10.100.0.0/16": "office VPN (wg0)",
    "10.100.5.0/24": "office VPN, server subnet (more specific)",
    "192.168.1.0/24": "local LAN, deliver directly",
}
def lookup(dst):
    ip = ipaddress.ip_address(dst)
    matches = [n for n in routes if ip in ipaddress.ip_network(n)]
    best = max(matches, key=lambda n: ipaddress.ip_network(n).prefixlen)
    return f"{dst:<13} matches {len(matches)} route(s) → best {best:<15} = {routes[best]}"
for d in ["8.8.8.8", "10.100.2.9", "10.100.5.40", "192.168.1.7"]:
    print(lookup(d))
```

```text output
8.8.8.8       matches 1 route(s) → best 0.0.0.0/0       = default → home router 192.168.1.1
10.100.2.9    matches 2 route(s) → best 10.100.0.0/16   = office VPN (wg0)
10.100.5.40   matches 3 route(s) → best 10.100.5.0/24   = office VPN, server subnet (more specific)
192.168.1.7   matches 2 route(s) → best 192.168.1.0/24  = local LAN, deliver directly
```

<En>`ip route get <ip>` shows which route your system would use:</En>
<Ur>`ip route get <ip>` dikhata hai ke aap ka system kaunsa raasta istemal karega:</Ur>


<Step title="Hops, IP TTL and traceroute">

<Tr>
<En>

Each router a packet passes is a **hop**. Every packet carries a **TTL** counter that each router lowers by 1; at 0 the packet is dropped and the router sends back "time exceeded". TTL stops packets looping forever, and `traceroute` uses it on purpose: it sends packets with TTL 1, 2, 3… so each hop reports itself in turn. `* * *` means that hop didn't answer, which is often just a firewall.

</En>
<Ur>

Packet jis router se guzre wo ek **hop** hai. Har packet ek **TTL** counter le jata hai jise har router 1 kam karta hai; 0 par packet phaink diya jata hai aur router "time exceeded" wapas bhejta hai. TTL packets ko hamesha ghoomne se rokta hai, aur `traceroute` ise jaan boojh kar istemal karta hai: TTL 1, 2, 3… wale packets bhejta hai taa ke har hop baari baari apna pata de. `* * *` ka matlab us hop ne jawab nahi diya, jo aksar sirf firewall hota hai.

</Ur>
</Tr>

```text
$ traceroute -n 1.1.1.1
 1  192.168.1.1     1.2 ms     ← home router
 2  10.200.0.1      6.8 ms     ← ISP (private range inside the ISP)
 3  119.63.x.x      9.1 ms     ← ISP core
 4  * * *                      ← does not answer traceroute (common)
 5  162.158.x.x    24.7 ms     ← Cloudflare edge
 6  1.1.1.1        25.0 ms     ← destination
```

<Tr>
<En>Different starting TTLs even hint at the OS: Linux uses 64, Windows 128.</En>
<Ur>Shuru ke mukhtalif TTL OS ka andaza bhi dete hain: Linux 64 istemal karta hai, Windows 128.</Ur>
</Tr>

</Step>

<Step title="NAT: many private devices, one public IP">

<Tr>
<En>

There are far too few IPv4 addresses for every device. **Source NAT** (SNAT, "masquerade") fixes that: when a packet leaves the private network, the router swaps the private source IP (and often port) for its own public IP, and remembers the swap in a **NAT table** to translate replies back. The mapping is created by **outgoing** traffic, so unsolicited **incoming** packets have no mapping and are dropped.

</En>
<Ur>

Har device ke liye IPv4 addresses bohot kam hain. **Source NAT** (SNAT, "masquerade") ye theek karta hai: jab packet private network se nikle, router private source IP (aur aksar port) ko apne public IP se badalta hai, aur jawab wapas badalne ke liye ye tabdeeli **NAT table** me yaad rakhta hai. Rabta **bahar jane wale** traffic se banta hai, isliye bin bulaye **andar aane wale** packets ka koi rabta nahi hota aur wo phenk diye jate hain.

</Ur>
</Tr>

```python
public_ip, next_port, nat = "39.40.41.42", 40001, {}
def outgoing(src_ip, src_port, dst):
    global next_port
    key = (src_ip, src_port, dst)
    if key not in nat:
        nat[key] = next_port; next_port += 1
    print(f"OUT  {src_ip}:{src_port} → {dst}   becomes   {public_ip}:{nat[key]} → {dst}")
def incoming(dst_port, src):
    for (ip, port, d), p in nat.items():
        if p == dst_port and d == src:
            return print(f"IN   {src} → {public_ip}:{dst_port}   becomes   {src} → {ip}:{port}")
    print(f"IN   {src} → {public_ip}:{dst_port}   no NAT mapping → DROPPED")
outgoing("192.168.1.20", 51522, "142.250.181.14:443")
outgoing("192.168.1.31", 51522, "142.250.181.14:443")      # same port, different laptop
incoming(40002, "142.250.181.14:443")                       # reply to the second laptop
incoming(40999, "198.51.100.9:4444")                        # random scanner
```

```text output
OUT  192.168.1.20:51522 → 142.250.181.14:443   becomes   39.40.41.42:40001 → 142.250.181.14:443
OUT  192.168.1.31:51522 → 142.250.181.14:443   becomes   39.40.41.42:40002 → 142.250.181.14:443
IN   142.250.181.14:443 → 39.40.41.42:40002   becomes   142.250.181.14:443 → 192.168.1.31:51522
IN   198.51.100.9:4444 → 39.40.41.42:40999   no NAT mapping → DROPPED
```

<Happened>
<Tr>
<En>Google only ever saw `39.40.41.42` and couldn't tell the two laptops apart. The reply reached the right laptop through the table, and the scanner's unsolicited packet was dropped.</En>
<Ur>Google ne sirf `39.40.41.42` dekha aur dono laptops me farq na kar saka. Jawab table ke zariye sahi laptop tak pohancha, aur scanner ka bin bulaya packet phaink diya gaya.</Ur>
</Tr>
</Happened>

<Step title="Port forwarding (DNAT)">

<Tr>
<En>

**Destination NAT** makes a service behind NAT reachable: a router rule sends incoming traffic for one public port to a private IP and port. `docker -p` is exactly this. Every forwarded port is a hole in your perimeter, so expose as little as possible.

</En>
<Ur>

**Destination NAT** NAT ke peeche ki service ko pohanch me laata hai: router ka rule ek public port ka andar aane wala traffic kisi private IP aur port ko bhejta hai. `docker -p` bilkul yahi hai. Har forward kiya port aap ki deewar me ek surakh hai, isliye kam se kam kholein.

</Ur>
</Tr>

```text
Router rule:   TCP  39.40.41.42:8443  →  192.168.1.50:443   (NAS web interface)
Docker:        docker run -p 8080:3000 …   =  host:8080 → container 172.17.0.2:3000 (DNAT in iptables)
```

</Step>

<Step title="Internet gateway and NAT gateway in the cloud">

<Tr>
<En>

The usual secure design: load balancers in public subnets, app servers and databases in private subnets. But app servers still need to download packages and call external APIs. In AWS (similar in Azure/GCP):

- An **Internet Gateway (IGW)** connects the VPC to the internet for resources with public IPs.
- A **NAT Gateway**, placed in a public subnet, lets **private** subnets make outgoing connections without being reachable.

Each subnet's **route table** picks one.

</En>
<Ur>

Aam mehfooz design: load balancers public subnets me, app servers aur databases private subnets me. Lekin app servers ko phir bhi packages download aur bahar ki APIs call karni hoti hain. AWS me (Azure/GCP me bhi milta julta):

- **Internet Gateway (IGW)** public IPs wale resources ke liye VPC ko internet se jorta hai.
- **NAT Gateway**, jo public subnet me rakha jata hai, **private** subnets ko bahar connections banane deta hai bina un tak pohanch diye.

Har subnet ki **route table** ek chunti hai.

</Ur>
</Tr>

```text
VPC 10.0.0.0/16
                         Internet
                            │
                     ┌──────▼──────┐
                     │  Internet   │
                     │  Gateway    │
                     └──────┬──────┘
 public subnet 10.0.1.0/24  │      route table: 10.0.0.0/16 → local,  0.0.0.0/0 → igw
   ┌─────────┐       ┌──────┴──────┐
   │   ALB   │       │ NAT gateway │ (has an Elastic IP)
   └────┬────┘       └──────▲──────┘
 private subnet 10.0.11.0/24│      route table: 10.0.0.0/16 → local,  0.0.0.0/0 → nat
   ┌────▼────┐              │
   │ app EC2 │──────────────┘  outbound only (apt update, payment API)
   └────┬────┘
 data subnet 10.0.21.0/24          route table: 10.0.0.0/16 → local   (no internet at all)
   ┌────▼────┐
   │   RDS   │
   └─────────┘
```

<Tr>
<En>

| Subnet type | Default route | Reachable from internet? | Can reach internet? |
| --- | --- | --- | --- |
| Public | Internet gateway | Yes, with a public IP and an allowing security group | Yes |
| Private | NAT gateway | No | Outbound only |
| Isolated | None | No | No |

NAT gateways cost money per hour **and** per GB; VPC **endpoints** (S3, ECR…) keep that traffic off the NAT.

</En>
<Ur>

| Subnet ki qism | Default route | Internet se pohanch? | Internet tak pohanch? |
| --- | --- | --- | --- |
| Public | Internet gateway | Haan, public IP aur ijazat dene wale security group ke saath | Haan |
| Private | NAT gateway | Nahi | Sirf bahar |
| Isolated | Koi nahi | Nahi | Nahi |

NAT gateways ka kharcha ghante ke hisaab se **aur** har GB par hota hai; VPC **endpoints** (S3, ECR…) wo traffic NAT se bahar rakhte hain.

</Ur>
</Tr>

</Step>

<Step title="Routing between private networks">

<Tr>
<En>

VPC peering, VPNs, Transit Gateway and Kubernetes overlays all connect private networks by adding routes. **Both sides** need a route to the other's CIDR (plus security rules allowing it), and overlapping CIDRs can't be routed at all.

</En>
<Ur>

VPC peering, VPNs, Transit Gateway aur Kubernetes overlays sab routes jor kar private networks ko milate hain. **Dono taraf** ko doosre ke CIDR ka raasta chahiye (aur ijazat dene wale security rules), aur takrate CIDRs route ho hi nahi sakte.

</Ur>
</Tr>

```text
VPC A 10.0.0.0/16  ◄── peering ──►  VPC B 10.1.0.0/16
route table A: 10.1.0.0/16 → pcx-123
route table B: 10.0.0.0/16 → pcx-123        ← forgetting this side = one-way silence
```

</Step>

<Step title="IP forwarding on Linux">

<Tr>
<En>

A kernel setting that lets a Linux machine pass packets between its interfaces, so it acts as a router. Docker, Kubernetes nodes, VPN servers and self-made NAT instances all need it. Check with `sysctl net.ipv4.ip_forward` (1 = on); NAT itself is set up with nftables/iptables (`MASQUERADE`).

</En>
<Ur>

Kernel ki setting jo Linux machine ko apne interfaces ke darmiyan packets guzarne deti hai, yaani wo router ban jati hai. Docker, Kubernetes nodes, VPN servers aur khud banaye NAT instances sab ko ye chahiye. `sysctl net.ipv4.ip_forward` se check karein (1 = on); NAT khud nftables/iptables (`MASQUERADE`) se set hota hai.

</Ur>
</Tr>

```bash
echo "IP forwarding on this machine: $(cat /proc/sys/net/ipv4/ip_forward)" | sed -E 's/: [01]$/: 0 or 1/'
```


## Common mistakes

<Compare>
<Bad title="NAT gateway in a private subnet">

```text
NAT gateway → private subnet 10.0.11.0/24   # it has no route to the internet itself
```

</Bad>
<Good title="NAT gateway in a public subnet">

```text
NAT gateway → public subnet 10.0.1.0/24 (route 0.0.0.0/0 → igw)
private route table: 0.0.0.0/0 → nat-…
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Routes on only one side** of a peering or VPN.
- **Overlapping CIDRs** between networks you need to connect.
- **Thinking NAT is a firewall**: it drops unsolicited inbound by accident, not by policy; still use security groups and firewalls.
- **Panicking at traceroute `* * *`**: it's often normal filtering, not an outage.
- **Expensive NAT traffic** to AWS services that could use VPC endpoints.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Peering ya VPN me sirf ek taraf routes.**
- **Jorne wale networks ke takrate CIDRs.**
- **NAT ko firewall samajhna**: ye bin bulaye inbound ko ittefaqan rokta hai, policy se nahi; security groups aur firewalls phir bhi lagayen.
- **traceroute ke `* * *` se ghabrana**: aksar ye aam filtering hai, outage nahi.
- **AWS services ka mehnga NAT traffic** jo VPC endpoints se ja sakta tha.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Routers forward packets hop by hop using routing tables.
- Longest prefix match wins; `0.0.0.0/0` is the default route.
- IP TTL drops at every hop; traceroute uses it to map the path.
- SNAT: many private devices share one public IP; unsolicited inbound is dropped.
- DNAT / port forwarding exposes a private service; open as few as possible.
- Cloud: public subnet → IGW, private → NAT gateway (in a public subnet), isolated → no default route.
- Peering/VPN needs routes on **both** sides and no overlapping CIDRs.

<DeepDive title="Real world: private instances can't run apt update">

The engineer checks the subnet's route table:

```text
Route table rtb-private-a (associated with 10.0.11.0/24):
  10.0.0.0/16   local
  (no 0.0.0.0/0 route)                ← nothing for internet traffic
```

The instances were in a private subnet with no NAT route, so packets to Ubuntu's mirrors had nowhere to go (timeouts). Fix: create a NAT gateway in a **public** subnet with an Elastic IP, and add `0.0.0.0/0 → nat-0abc…` to the **private** route table. To save NAT costs, the team also added a **gateway VPC endpoint** for S3, so backups to S3 no longer go through the NAT gateway.

</DeepDive>

<DeepDive title="Security lens">

Routes decide what **can** reach what. Combined with firewalls (what is **allowed**), they define your network's attack surface.

- **Private by default:** databases and internal services in subnets with **no** internet route.
- **Egress control:** NAT gateways plus firewalls/proxies limit and log where servers can connect, making malware command-and-control and data theft harder.
- **Port forwarding is exposure:** every forwarded port must be justified, patched and monitored.
- **Route hijacking (BGP):** on the internet, wrong or malicious route announcements can redirect traffic for whole IP ranges, one reason TLS certificates and RPKI matter.
- **Asymmetric routing** can make stateful firewalls drop legitimate traffic: design paths deliberately.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does a router decide where to send a packet?">
It looks up the destination IP in its routing table, finds all routes whose prefix contains that address and chooses the most specific one (longest prefix match). The default route 0.0.0.0/0 matches everything and is used only when nothing more specific matches. The router decreases the packet's TTL and forwards it to the chosen next hop or interface.
</QA>

<QA q="What is NAT and why is it used?">
Network Address Translation rewrites addresses in packets as they pass through a router. Source NAT replaces private source addresses with a public address and tracks the mapping so replies can be translated back, allowing many private devices to share one public IP and saving IPv4 addresses. Destination NAT, or port forwarding, maps a public address and port to a private host for inbound access.
</QA>

<QA q="What is the difference between an internet gateway and a NAT gateway in AWS?">
An internet gateway connects a VPC to the internet and allows two-way traffic for resources that have public IP addresses in public subnets. A NAT gateway sits in a public subnet and lets resources in private subnets initiate outbound connections to the internet while preventing unsolicited inbound connections to them. Private subnets route 0.0.0.0/0 to the NAT gateway; public subnets route it to the internet gateway.
</QA>

<QA q="How does traceroute work?">
It sends packets with increasing IP TTL values, starting at 1. Each router that decreases the TTL to zero drops the packet and returns an ICMP time-exceeded message, revealing its address and the round-trip time. Increasing the TTL one hop at a time maps the path to the destination; hops that do not reply appear as asterisks.
</QA>

</DeepDive>
