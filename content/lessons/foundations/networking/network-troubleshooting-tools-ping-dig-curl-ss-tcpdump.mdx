<BigIdea>
<Tr>
<En>
A connection can fail in a dozen places: Wi-Fi, DNS, a route, a firewall, the service, TLS, the app. Guessing wastes hours. Check **layer by layer, from your side outwards**: my own network → DNS → reachability → **port** → **application** → (on the server) is it **listening**? → and only then **packets**. "Refused" points to the service; "timeout" points to a firewall or route.
</En>
<Ur>
Connection darjan jagahon par fail ho sakta hai: Wi-Fi, DNS, raasta, firewall, service, TLS, app. Andaze ghante zaya karte hain. **Layer ba layer, apni taraf se bahar ki taraf** check karein: mera apna network → DNS → pohanch → **port** → **application** → (server par) kya wo **sun** raha hai? → aur sirf tab **packets**. "Refused" service ki taraf ishara hai; "timeout" firewall ya raaste ki taraf.
</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="My own network: ip">

<Tr>
<En>

If your own machine has no IP, no default route or broken DNS, nothing else will work, so check it first. Look for an interface that's UP with an address, a `default via` route, and DNS servers. (`ifconfig`/`route` are the old tools; `ipconfig` on Windows.)

</En>
<Ur>

Agar aap ki apni machine ka IP nahi, default route nahi, ya DNS toota hai, to kuch aur nahi chalega, isliye ise pehle check karein. Address wala UP interface, `default via` route, aur DNS servers dhoondein. (`ifconfig`/`route` purane tools hain; Windows par `ipconfig`.)

</Ur>
</Tr>

```bash
ip -br addr show lo | awk '{print $1, $2, $3}'
ip route show default | grep -q 'default via' && echo "default route: present" || echo "default route: MISSING"
grep -c '^nameserver' /etc/resolv.conf | sed 's/^/DNS servers configured: /' | sed -E 's/: [1-9][0-9]*$/: yes/'
```

```text output
lo UNKNOWN 127.0.0.1/8
default route: present
DNS servers configured: yes
```

</Step>

<Step title="DNS: dig and getent">

<Tr>
<En>

Wrong or stale DNS sends traffic to the wrong place and looks like a network failure. `getent hosts` resolves the way **applications** do (hosts file + DNS); `dig` asks DNS servers directly. Compare your resolver, a public one and the authoritative server: `dig +short host`, `dig @1.1.1.1 +short host`, `dig @ns1.provider.com host`.

</En>
<Ur>

Ghalat ya purana DNS traffic ghalat jagah bhejta hai aur network ki nakami jaisa lagta hai. `getent hosts` **applications** ki tarah resolve karta hai (hosts file + DNS); `dig` seedha DNS servers se poochta hai. Apne resolver, ek public resolver aur authoritative server ka muqabla karein: `dig +short host`, `dig @1.1.1.1 +short host`, `dig @ns1.provider.com host`.

</Ur>
</Tr>

```bash
getent hosts localhost | awk '{print "applications resolve localhost to", $1}'
getent hosts no-such-name.invalid > /dev/null || echo "no-such-name.invalid → not found (exit code $?)"
```

```text output
applications resolve localhost to 127.0.0.1
no-such-name.invalid → not found (exit code 2)
```

```text
$ dig +short api.example.com              # what my resolver says
203.0.113.10
$ dig @1.1.1.1 +short api.example.com     # what the world sees
198.51.100.20                              ← different! my resolver (or /etc/hosts) is stale
```

</Step>

<Step title="Reachability: ping, traceroute, mtr">

<Tr>
<En>

`ping` measures round-trip time and loss; `traceroute` lists the routers on the path; `mtr` does both continuously. But many servers and clouds **block ICMP**, so silence doesn't prove a host is down. Read **received vs transmitted** (loss) and **avg** (latency).

</En>
<Ur>

`ping` aane jane ka waqt aur nuqsan naapta hai; `traceroute` raaste ke routers dikhata hai; `mtr` dono musalsal karta hai. Lekin kai servers aur clouds **ICMP band** rakhte hain, isliye khamoshi host ke band hone ka saboot nahi. **received bamuqabla transmitted** (nuqsan) aur **avg** (der) parhein.

</Ur>
</Tr>

```bash
ping -c 3 -i 0.2 127.0.0.1 | tail -2 | sed -E 's/= [0-9.\/]+ ms/= <min\/avg\/max\/mdev> ms/; s/time [0-9]+ms/time Xms/'
```

```text output
3 packets transmitted, 3 received, 0% packet loss, time Xms
rtt min/avg/max/mdev = <min/avg/max/mdev> ms
```

```text
$ mtr -rwc 50 -n api.example.com
HOST                    Loss%   Avg
1. 192.168.1.1           0.0%   1.2
2. 10.200.0.1            0.0%   6.9
3. 119.63.x.x           18.0%  88.4      ← loss and latency start here (ISP) and continue…
4. 162.158.x.x          17.5%  91.0
5. 203.0.113.10         18.2%  92.3      ← …to the end: a real problem at hop 3
```

<Happened>
<Tr>
<En>Loss that appears at one hop but **not** at later hops is usually just that router giving ICMP low priority, not a real problem. Here it continues to the end, so it's real.</En>
<Ur>Jo nuqsan ek hop par dikhe lekin baad ke hops par **na** dikhe, wo aam tor par sirf us router ka ICMP ko kam tarjeeh dena hai, asli masla nahi. Yahan ye aakhir tak jata hai, isliye asli hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Is the port open? nc">

<Tr>
<En>

`nc -zv host port` tries a TCP connection and reports success, refusal or timeout, without sending data. It splits "network/firewall problem" from "app problem" in one second. Always add a timeout (`-w 3`). Alternatives: `curl -v telnet://host:port`, Bash's `/dev/tcp`, PowerShell `Test-NetConnection host -Port 443`.

</En>
<Ur>

`nc -zv host port` TCP connection ki koshish karta hai aur kamyabi, inkaar ya timeout batata hai, data bheje baghair. Ek second me "network/firewall masla" ko "app masla" se alag karta hai. Hamesha timeout lagayen (`-w 3`). Mutabadil: `curl -v telnet://host:port`, Bash ka `/dev/tcp`, PowerShell `Test-NetConnection host -Port 443`.

</Ur>
</Tr>

```bash
python3 -m http.server 4200 --bind 127.0.0.1 > /dev/null 2>&1 & srv=$!; sleep 1
check() { if nc -z -w 2 "$1" "$2" 2>/dev/null; then echo "$1:$2 → OPEN"; else echo "$1:$2 → CLOSED or BLOCKED"; fi; }
check 127.0.0.1 4200
check 127.0.0.1 4201
timeout 1 bash -c 'echo > /dev/tcp/127.0.0.1/4200' 2>/dev/null && echo "bash /dev/tcp test: 4200 open too"
kill $srv
```

```text output
127.0.0.1:4200 → OPEN
127.0.0.1:4201 → CLOSED or BLOCKED
bash /dev/tcp test: 4200 open too
```

<Happened>
<Tr>
<En>The `/dev/tcp` trick works in Bash even in tiny containers that have no `nc` or `curl`.</En>
<Ur>`/dev/tcp` wala tareeqa Bash me un chhote containers me bhi chalta hai jin me `nc` ya `curl` nahi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="The application: curl -v and timings">

<Tr>
<En>

`curl -v` shows the whole conversation: DNS, TCP connect, TLS and certificate, request and response headers. `-w` prints timings for each phase, so you see **where** time goes. If DNS, connect and TLS are fast but the first byte is slow, the **app or its database** is the slow part. Browser DevTools → Network → Timing shows the same phases.

</En>
<Ur>

`curl -v` poori guftagu dikhata hai: DNS, TCP connect, TLS aur certificate, request aur response headers. `-w` har marhale ka waqt chhaapta hai, taa ke aap dekhein waqt **kahan** ja raha hai. Agar DNS, connect aur TLS tez hon lekin pehla byte dheema, to **app ya us ka database** dheema hissa hai. Browser DevTools → Network → Timing yahi marhale dikhata hai.

</Ur>
</Tr>

```bash
cat > slow.mjs <<'EOF'
import http from "node:http";
http.createServer((req, res) => setTimeout(() => res.end("done\n"), 300)).listen(4202, "127.0.0.1");   // app takes 300 ms
EOF
node slow.mjs & s=$!; sleep 0.5
curl -s -o /dev/null -w 'dns %{time_namelookup}s | connect %{time_connect}s | first byte %{time_starttransfer}s | total %{time_total}s\n' http://127.0.0.1:4202/ \
 | awk -F'[ |]+' '{ server = $7 - $4; printf "network part: %s, server processing: %s\n", ($4 < 0.05 ? "fast" : "slow"), (server >= 0.29 ? "~300 ms (the app is the slow part)" : "fast") }'
kill $s
```

```text output
network part: fast, server processing: ~300 ms (the app is the slow part)
```

<Tr>
<En>A reusable timing command for real sites:</En>
<Ur>Asli sites ke liye dobara istemal hone wali timing command:</Ur>
</Tr>

```text
$ curl -s -o /dev/null -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} code=%{http_code}\n' https://shop.example.com
dns=0.004 connect=0.041 tls=0.093 ttfb=1.874 total=1.902 code=200
                                            └ 1.8 s waiting for the server → app/database problem, not network
```

</Step>

<Step title="TLS problems: openssl s_client">

<Tr>
<En>

Certificate errors are invisible to `nc` and often vague in apps. `openssl s_client` opens a raw TLS connection and shows the chain, protocol and verification result: `echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -subject -issuer -dates`, and look for `Verify return code: 0 (ok)`. See **TLS and Certificates**.

</En>
<Ur>

Certificate errors `nc` ko nazar nahi aate aur apps me aksar mubham hote hain. `openssl s_client` kachcha TLS connection khol kar chain, protocol aur verification ka nateeja dikhata hai: `echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -subject -issuer -dates`, aur `Verify return code: 0 (ok)` dhoondein. **TLS and Certificates** dekhein.

</Ur>
</Tr>

</Step>

<Step title="Server side: who is listening? ss">

<Tr>
<En>

The service may be running but listening on `127.0.0.1` instead of `0.0.0.0`, on the wrong port, or not at all. On the **server** (or inside the container): `ss -ltnp` lists listening sockets with their process; `lsof -i :PORT` shows who uses a port. Check the **local address**: `127.0.0.1:3000` = local only; `0.0.0.0:3000` / `*:3000` = all interfaces.

</En>
<Ur>

Service chal rahi ho sakti hai lekin `0.0.0.0` ki jagah `127.0.0.1` par, ghalat port par, ya bilkul nahi sun rahi. **Server** par (ya container ke andar): `ss -ltnp` sunne wale sockets un ke process ke saath dikhata hai; `lsof -i :PORT` batata hai port kaun istemal kar raha hai. **Local address** dekhein: `127.0.0.1:3000` = sirf local; `0.0.0.0:3000` / `*:3000` = saare interfaces.

</Ur>
</Tr>

```bash
python3 -m http.server 4203 --bind 127.0.0.1 > /dev/null 2>&1 & a=$!
sleep 1
ss -ltn | awk '$4 ~ /:4203$/ {print "listening on", $4, "→", ($4 ~ /^127\./ ? "ONLY reachable from this machine" : "reachable from the network")}'
kill $a
```

```text output
listening on 127.0.0.1:4203 → ONLY reachable from this machine
```

<Happened>
<Tr>
<En>The classic container bug: an app inside Docker listens on `127.0.0.1:3000`, so `-p 3000:3000` publishes nothing useful. It must listen on `0.0.0.0` inside the container.</En>
<Ur>Mashhoor container bug: Docker ke andar app `127.0.0.1:3000` par sunti hai, isliye `-p 3000:3000` kuch kaam ka publish nahi karta. Container ke andar use `0.0.0.0` par sunna chahiye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Looking at packets: tcpdump">

<Tr>
<En>

The final truth: did the SYN leave? Did a SYN-ACK come back? Was there a reset? Is DNS answered? `tcpdump` captures packets on an interface (needs root). **Always filter**: `sudo tcpdump -i any -nn 'tcp port 5432'`, `'host 10.0.21.5'`, `'udp port 53'`. Save with `-w file.pcap` for Wireshark, and limit with `-c 100`.

</En>
<Ur>

Aakhri sach: kya SYN gaya? Kya SYN-ACK wapas aaya? Kya reset hua? Kya DNS ka jawab aaya? `tcpdump` interface ke packets capture karta hai (root chahiye). **Hamesha filter lagayen**: `sudo tcpdump -i any -nn 'tcp port 5432'`, `'host 10.0.21.5'`, `'udp port 53'`. Wireshark ke liye `-w file.pcap` se save karein, aur `-c 100` se had lagayen.

</Ur>
</Tr>

```bash
port=$((30000 + RANDOM % 20000))
timeout 4 tcpdump -i lo -nn -c 4 "tcp port $port" 2>/dev/null > capture.txt &
sleep 0.5
python3 -m http.server $port --bind 127.0.0.1 > /dev/null 2>&1 & srv=$!; sleep 0.8
curl -s -o /dev/null http://127.0.0.1:$port/
sleep 1; kill $srv; wait 2>/dev/null
grep -oE 'Flags \[[^]]+\]' capture.txt | head -3 | awk '{n++; d = (n == 2) ? "server → client" : "client → server"; print n ". " d ": " $0}'
```

```text output
1. client → server: Flags [S]
2. server → client: Flags [S.]
3. client → server: Flags [.]
```

<Happened>
<Tr>
<En>The three-way handshake captured live: SYN, SYN-ACK, ACK.</En>
<Ur>Three-way handshake live capture hua: SYN, SYN-ACK, ACK.</Ur>
</Tr>
</Happened>

<Tr>
<En>

| Pattern in tcpdump | Meaning |
| --- | --- |
| `[S]` repeated, no reply | Packets dropped (firewall, security group, route) |
| `[S]` then `[R.]` | Port closed (nothing listening) |
| Handshake OK, then `[R]` later | App or proxy aborted (timeout, crash) |
| DNS query, no response | DNS server unreachable / UDP 53 blocked |

</En>
<Ur>

| tcpdump me pattern | Matlab |
| --- | --- |
| `[S]` baar baar, jawab nahi | Packets phenke ja rahe (firewall, security group, raasta) |
| `[S]` phir `[R.]` | Port band (koi nahi sun raha) |
| Handshake theek, phir baad me `[R]` | App ya proxy ne khatam kiya (timeout, crash) |
| DNS query, jawab nahi | DNS server pohanch se bahar / UDP 53 band |

</Ur>
</Tr>

</Step>

<Step title="The checklist in one script">

<Tr>
<En>

A small script that runs DNS → port → HTTP in order, each with a short timeout and a clear verdict. Keep it in your ops tools repo; anyone on the team can run it as the first response to "can't connect".

</En>
<Ur>

Chhota script jo DNS → port → HTTP tarteeb se chalata hai, har ek chhote timeout aur saaf faisle ke saath. Ise apne ops tools repo me rakhein; team ka koi bhi "connect nahi hota" par pehle jawab ke tor par chala sakta hai.

</Ur>
</Tr>

```bash
cat > netcheck.sh <<'EOF'
#!/usr/bin/env bash
host=$1 port=$2
ip=$(getent hosts "$host" | awk '{print $1; exit}')
[[ -n $ip ]] && echo "DNS   OK    $host → $ip" || { echo "DNS   FAIL  $host does not resolve"; exit 1; }
if nc -z -w 3 "$host" "$port" 2>/dev/null; then echo "PORT  OK    $port is open"
else echo "PORT  FAIL  $port refused or filtered (service down? firewall?)"; exit 2; fi
code=$(curl -s -o /dev/null -m 5 -w '%{http_code}' "http://$host:$port/")
[[ $code =~ ^[23] ]] && echo "HTTP  OK    status $code" || echo "HTTP  WARN  status $code (application problem)"
EOF
chmod +x netcheck.sh
python3 -m http.server 4204 --bind 127.0.0.1 > /dev/null 2>&1 & s=$!; sleep 1
./netcheck.sh localhost 4204; echo "---"
./netcheck.sh localhost 4205; echo "---"
./netcheck.sh no-such-host.invalid 80
kill $s
```

```text output
DNS   OK    localhost → 127.0.0.1
PORT  OK    4204 is open
HTTP  OK    status 200
---
DNS   OK    localhost → 127.0.0.1
PORT  FAIL  4205 refused or filtered (service down? firewall?)
---
DNS   FAIL  no-such-host.invalid does not resolve
```

</Step>

## Common mistakes

<Compare>
<Bad title="Testing from the wrong machine">

```text
laptop$ nc -zv db.internal 5432     # works from your laptop over the VPN…
```

</Bad>
<Good title="Test where the problem is">

```text
$ docker exec -it api sh -c 'nc -zv db.internal 5432'   # …but does the app container reach it?
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Concluding "server down" from a failed ping.**
- **Ignoring the difference between refused and timeout.**
- **Forgetting DNS caches** (`/etc/hosts`, browser, resolver) when "nothing changed".
- **Capturing without a filter**: tcpdump floods the screen and can expose sensitive data.
- **Changing many things at once**: you never learn which change fixed it.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Fail ping se "server band" ka nateeja nikalna.**
- **Refused aur timeout ke farq ko nazar andaz karna.**
- **"Kuch nahi badla" par DNS caches bhoolna** (`/etc/hosts`, browser, resolver).
- **Bina filter capture**: tcpdump screen bhar deta hai aur hassas data dikha sakta hai.
- **Ek saath kai cheezen badalna**: kabhi pata nahi chalta kis tabdeeli ne theek kiya.

</Ur>
</Tr>

```bash
python3 -m http.server 4206 --bind 127.0.0.1 > /dev/null 2>&1 & bad=$!
python3 -m http.server 4207 --bind 0.0.0.0   > /dev/null 2>&1 & good=$!
sleep 1
for p in 4206 4207; do
  addr=$(ss -ltn | awk -v p=":$p" '$4 ~ p"$" {print $4}')
  case $addr in
    127.0.0.1:*) echo "port $p: listens on $addr → outside clients will get 'connection refused'" ;;
    0.0.0.0:*|\*:*) echo "port $p: listens on $addr → reachable from other machines (if firewalls allow)" ;;
  esac
done
kill $bad $good
```

<DeepDive title="Real world: the new API server can't reach the database">

Working through the checklist **on the API server**:

```text
1. $ ip route | head -1          → default via 10.0.11.1          ✓ network config fine
2. $ dig +short db.internal      → 10.0.21.5                      ✓ DNS fine
3. $ ping -c2 10.0.21.5          → 100% packet loss               ? (ICMP may be blocked — not conclusive)
4. $ nc -zv -w3 10.0.21.5 5432   → timed out                      ✗ TIMEOUT, not refused → something drops packets
5. $ sudo tcpdump -nn host 10.0.21.5 and port 5432
      10.0.11.40.50122 > 10.0.21.5.5432: Flags [S] …
      10.0.11.40.50122 > 10.0.21.5.5432: Flags [S] …   (retries, no SYN-ACK)
   → the SYN leaves; nothing comes back: a firewall on the way or at the DB.
6. Database security group: inbound 5432 from sg-app-old  ← the new server uses sg-app-v2!
   Fix: allow 5432 from sg-app-v2.  nc → succeeded.  App connects.
```

Total time: about 6 minutes, because each step ruled out one layer.

</DeepDive>

<DeepDive title="Security lens">

These are dual-use tools: the same commands map networks for attackers and defenders. Use them only on systems you own or are allowed to test.

- **Packet captures contain secrets** (cookies, tokens, unencrypted passwords, personal data). Store `.pcap` files securely, delete them after use, and capture only what you need.
- **`ss -tnp` and `lsof -i`** during incident response reveal unexpected outbound connections (reverse shells, miners, data theft).
- **DNS logs and `dig`** help spot phishing look-alike domains and DNS tunnelling.
- **Keep diagnostic tools minimal in production images**: they help attackers too; use temporary debug containers (`kubectl debug`) instead.
- **Port scanning** (`nmap`) of other people's systems without permission is illegal in many countries.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="A user says a website is down. How do you troubleshoot it?">
Work layer by layer: confirm the user's own connectivity, then resolve the name with dig and compare with public resolvers, test reachability and the path with ping or traceroute while remembering ICMP may be blocked, test the TCP port with nc or curl, then check the HTTP response and timings with curl -v and -w, including TLS. On the server, check that the service is running and listening on the right address with ss, check logs, and if needed capture packets with tcpdump to see whether SYNs arrive and replies leave.
</QA>

<QA q="What does it mean if nc reports a timeout instead of connection refused?">
A refusal means the host was reached and actively rejected the connection because nothing is listening on that port. A timeout means no reply came back at all, which usually points to a firewall or security group dropping the packets, a routing problem, or a wrong or unreachable IP address.
</QA>

<QA q="How do you find out whether slowness is caused by the network or the application?">
Use curl's timing variables: time_namelookup for DNS, time_connect for the TCP handshake, time_appconnect for TLS, and time_starttransfer for the first byte. If DNS, connect and TLS are fast but the time to first byte is long, the server or its database is slow; if the connect time is high, the network path or distance is the issue.
</QA>

<QA q="Why might a service be reachable from the server itself but not from outside?">
It may be listening only on 127.0.0.1, a firewall on the host or a cloud security group may block the port, or in Docker the application listens on localhost inside the container so the published port does not reach it. ss -ltn shows the listening address, and firewall and security group rules show what is allowed.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="ping">Tests reachability and latency with ICMP.</Term>
  <Term name="traceroute / mtr">Shows the router path and per-hop latency/loss.</Term>
  <Term name="dig">Queries DNS servers.</Term>
  <Term name="nc">Netcat; tests TCP/UDP ports.</Term>
  <Term name="curl -v / -w">Shows HTTP details and phase timings.</Term>
  <Term name="ss">Lists sockets: listening and connected.</Term>
  <Term name="tcpdump">Captures and prints packets.</Term>
  <Term name="Refused vs timeout">Nothing listening vs packets dropped.</Term>
  <Term name="TTFB">Time to first byte: mostly server processing time.</Term>
</Terms>
