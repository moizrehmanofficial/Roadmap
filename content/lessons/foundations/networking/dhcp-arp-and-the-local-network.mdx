<BigIdea>
<Tr>
<En>
When a device joins a network it needs an IP address, a mask, a **default gateway** (the router) and DNS servers. **DHCP** hands these out automatically in four steps (Discover, Offer, Request, Acknowledge) as a time-limited **lease**. To actually send to the router, the device also needs its **MAC address**, and **ARP** finds it by asking the whole network "who has 192.168.1.1?". Two small protocols, quietly working every time you join Wi-Fi.
</En>
<Ur>
Jab koi device network se jurta hai to use IP address, mask, **default gateway** (router) aur DNS servers chahiye. **DHCP** ye sab chaar qadmon (Discover, Offer, Request, Acknowledge) me khud de deta hai, ek waqti **lease** ki shakal me. Router ko asal me bhejne ke liye device ko us ka **MAC address** bhi chahiye, aur **ARP** poore network se "192.168.1.1 kis ke paas hai?" pooch kar ise dhoondta hai. Do chhote protocols, jo har dafa Wi-Fi se jurne par chupke se kaam karte hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

When your laptop connects to Wi-Fi, within a second it has an IP and can reach the internet, without you typing anything:

```text
New laptop joins Wi-Fi
  │
  ├─ DHCP (UDP 67/68):  Discover → Offer → Request → Ack
  │      gets: IP 192.168.1.20/24, gateway 192.168.1.1, DNS 192.168.1.1, lease 24h
  │
  ├─ wants to reach 8.8.8.8 → not in 192.168.1.0/24 → send via gateway 192.168.1.1
  │
  ├─ ARP broadcast: "Who has 192.168.1.1? Tell 192.168.1.20"
  │  ARP reply:     "192.168.1.1 is at 9c:53:22:aa:10:01"      (cached in the ARP table)
  │
  └─ Ethernet frame to MAC 9c:53:22:aa:10:01, containing an IP packet to 8.8.8.8
```

</En>
<Ur>

Jab aap ka laptop Wi-Fi se jurta hai, ek second me us ke paas IP hota hai aur wo internet tak pohanch jata hai, bina aap ke kuch type kiye:


</Ur>

<Why>
<Tr>
<En>

- **"Connected, no internet"** problems are often DHCP (a `169.254.x.x` address) or gateway issues.
- **Servers and cloud:** VPCs use DHCP to give instances IPs and DNS settings; static IPs vs reservations is a common design choice.
- **Docker and Kubernetes** create virtual switches, MACs and ARP entries for containers.
- **Security:** anyone on the same LAN (café Wi-Fi, a hacked office PC) can try ARP spoofing or a fake DHCP server to intercept traffic.

</En>
<Ur>

- **"Connected, no internet"** masle aksar DHCP (`169.254.x.x` address) ya gateway ke hote hain.
- **Servers aur cloud:** VPCs instances ko IPs aur DNS settings dene ke liye DHCP istemal karte hain; static IP bamuqabla reservation aam design faisla hai.
- **Docker aur Kubernetes** containers ke liye virtual switches, MACs aur ARP entries banate hain.
- **Security:** ek hi LAN par koi bhi (café Wi-Fi, hack shuda office PC) ARP spoofing ya naqli DHCP server se traffic pakarne ki koshish kar sakta hai.

</Ur>

## Picture it

<Tr>
<En>

Arriving at a **hotel**:

- **DHCP** is the **reception desk**: you say "I'm new here" (Discover), reception offers "room 20 is free" (Offer), you say "I'll take room 20" (Request), and they hand you a key card valid for 2 nights (Acknowledge + lease). They also tell you where the exit (gateway) and the information desk (DNS) are.
- **ARP** is **calling down the corridor**: "Who's in room 1? Please wave!" The person in room 1 waves, and you remember their face (MAC) so you don't have to call again.

## Learn it step by step

<Walkthrough>

<Step title="MAC addresses">

<Tr>
<En>

A 48-bit address written as six hex bytes; the first three identify the manufacturer (OUI). On a local network, frames are delivered by MAC (layer 2), not by IP. MACs only matter **inside** one LAN; routers replace them at every hop. Phones randomise their MAC per Wi-Fi network for privacy.

</En>
<Ur>

Chhe hex bytes me likha 48-bit pata; pehle teen banane wali company batate hain (OUI). Local network par frames MAC (layer 2) se pohanchte hain, IP se nahi. MAC sirf ek LAN ke **andar** maani rakhte hain; routers har hop par inhe badalte hain. Phones privacy ke liye har Wi-Fi network par apna MAC ittefaqi bana lete hain.

</Ur>
</Tr>

```bash
ip -br link show lo | awk '{print $1, "MAC:", $3}'
python3 -c 'm="3c:22:fb:1a:9e:07"; b=m.split(":"); print("MAC", m, "→ vendor part (OUI):", ":".join(b[:3]), "| device part:", ":".join(b[3:]))'
```

```text output
lo MAC: 00:00:00:00:00:00
MAC 3c:22:fb:1a:9e:07 → vendor part (OUI): 3c:22:fb | device part: 1a:9e:07
```

<Happened>
<Tr>
<En>The loopback interface has an all-zero MAC because it never sends real frames.</En>
<Ur>Loopback interface ka MAC saara zero hai kyun ke ye kabhi asli frames nahi bhejta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="DHCP: settings automatically (DORA)">

<Tr>
<En>

Nobody configures IPs by hand on hundreds of phones, and DHCP makes sure two devices never get the same IP. It uses UDP ports 67/68. The client starts with **no IP**, so Discover is a **broadcast**; the server offers an IP from its **pool**, the client requests it, and the server confirms. Leases renew at about half their time.

</En>
<Ur>

Sainkron phones par koi haath se IPs set nahi karta, aur DHCP yaqeeni banata hai ke do devices ko kabhi ek IP na mile. Ye UDP ports 67/68 istemal karta hai. Client ke paas shuru me **koi IP nahi** hota, isliye Discover **broadcast** hai; server apne **pool** se IP pesh karta hai, client use maangta hai, aur server tasdeeq karta hai. Leases aadhe waqt par renew hoti hain.

</Ur>
</Tr>

```python
pool = [f"192.168.1.{i}" for i in range(100, 105)]
leases = {}
def dora(mac):
    print(f"[{mac}] DISCOVER (broadcast: 'any DHCP server?')")
    ip = next(ip for ip in pool if ip not in leases.values())
    print(f"[server] OFFER {ip}, mask 255.255.255.0, gateway 192.168.1.1, DNS 192.168.1.1, lease 24h")
    print(f"[{mac}] REQUEST {ip}")
    leases[mac] = ip
    print(f"[server] ACK — {ip} is yours for 24h")
dora("aa:aa:aa:00:00:01")
dora("aa:aa:aa:00:00:02")
print("lease table:", leases)
```

```text output
[aa:aa:aa:00:00:01] DISCOVER (broadcast: 'any DHCP server?')
[server] OFFER 192.168.1.100, mask 255.255.255.0, gateway 192.168.1.1, DNS 192.168.1.1, lease 24h
[aa:aa:aa:00:00:01] REQUEST 192.168.1.100
[server] ACK — 192.168.1.100 is yours for 24h
[aa:aa:aa:00:00:02] DISCOVER (broadcast: 'any DHCP server?')
[server] OFFER 192.168.1.101, mask 255.255.255.0, gateway 192.168.1.1, DNS 192.168.1.1, lease 24h
[aa:aa:aa:00:00:02] REQUEST 192.168.1.101
[server] ACK — 192.168.1.101 is yours for 24h
lease table: {'aa:aa:aa:00:00:01': '192.168.1.100', 'aa:aa:aa:00:00:02': '192.168.1.101'}
```

<Tr>
<En>

| DHCP gives | Example |
| --- | --- |
| IP address + mask | `192.168.1.100/24` |
| Default gateway | `192.168.1.1` |
| DNS servers | `192.168.1.1`, `1.1.1.1` |
| Lease time | `86400` s |
| Search domain (optional) | `office.local` |

If no DHCP server answers, many systems give themselves a **link-local** address in `169.254.0.0/16`: a clear sign DHCP failed.

</En>
<Ur>

| DHCP deta hai | Misaal |
| --- | --- |
| IP address + mask | `192.168.1.100/24` |

| DNS servers | `192.168.1.1`, `1.1.1.1` |
| Lease ka waqt | `86400` s |
| Search domain (ikhtiyari) | `office.local` |

Agar koi DHCP server jawab na de, to kai systems khud ko `169.254.0.0/16` me **link-local** address de dete hain: DHCP fail hone ki saaf nishani.

</Ur>
</Tr>

</Step>

<Step title="Static IPs and DHCP reservations">

<Tr>
<En>

Servers, printers and routers need stable addresses so others can find them. A **static IP** is set by hand on the device; a **reservation** tells the DHCP server to always give the same IP to one MAC. Static IPs must be **outside** the DHCP pool, or two devices will eventually clash. In the cloud, instances keep their private IP for life; use **Elastic IPs** when you need a fixed public address.

</En>
<Ur>

Servers, printers aur routers ko pakke addresses chahiye taa ke doosre unhe dhoond sakein. **Static IP** device par haath se set hota hai; **reservation** DHCP server ko kehti hai ke ek MAC ko hamesha wahi IP de. Static IPs DHCP pool se **bahar** hone chahiye, warna aakhir kaar do devices takrayenge. Cloud me instances apna private IP poori umar rakhte hain; pakka public address chahiye to **Elastic IPs** istemal karein.

</Ur>
</Tr>

</Step>

<Step title="The default gateway">

<Tr>
<En>

Your device only knows its own subnet. For everything else ("the internet"), it hands packets to the **gateway**: the home router (`192.168.1.1`), or the VPC router (`.1` of each AWS subnet). `ip route` shows it as `default via …`.

</En>
<Ur>

Aap ka device sirf apna subnet jaanta hai. Baqi sab ("internet") ke liye wo packets **gateway** ko deta hai: ghar ka router (`192.168.1.1`), ya VPC router (har AWS subnet ka `.1`). `ip route` ise `default via …` ki shakal me dikhata hai.

</Ur>
</Tr>

```text
$ ip route
default via 192.168.1.1 dev wlan0 proto dhcp metric 600      ← everything else → the router
192.168.1.0/24 dev wlan0 proto kernel scope link src 192.168.1.20   ← my own subnet: deliver directly
```

```python
import ipaddress
my_net, gateway = ipaddress.ip_network("192.168.1.0/24"), "192.168.1.1"
for dst in ["192.168.1.55", "10.0.0.5", "142.250.181.14"]:
    nxt = "directly (same LAN)" if ipaddress.ip_address(dst) in my_net else f"via gateway {gateway}"
    print(f"to {dst:<15} → send {nxt}")
```

```text output
to 192.168.1.55    → send directly (same LAN)
to 10.0.0.5        → send via gateway 192.168.1.1
to 142.250.181.14  → send via gateway 192.168.1.1
```

</Step>

<Step title="ARP: from IP to MAC">

<Tr>
<En>

Frames need a destination MAC, but the sender only knows the IP. ARP broadcasts "Who has IP X?" and the owner answers "X is at MAC Y"; answers are cached in the **ARP table**. For internet destinations, the MAC you need is the **gateway's**, never the remote server's. IPv6 uses **NDP** (Neighbor Discovery) instead. `ip neigh` shows the table.

</En>
<Ur>

Frames ko manzil ka MAC chahiye, lekin bhejne wala sirf IP jaanta hai. ARP broadcast karta hai "IP X kis ke paas hai?" aur malik jawab deta hai "X MAC Y par hai"; jawab **ARP table** me cache hote hain. Internet ki manzilon ke liye aap ko **gateway ka** MAC chahiye, door ke server ka kabhi nahi. IPv6 is ki jagah **NDP** (Neighbor Discovery) istemal karta hai. `ip neigh` table dikhata hai.

</Ur>
</Tr>

```text
$ ip neigh
192.168.1.1   dev wlan0 lladdr 9c:53:22:aa:10:01 REACHABLE    ← the router
192.168.1.42  dev wlan0 lladdr 3c:22:fb:1a:9e:07 STALE        ← a phone, not used recently
```

```text
ARP request  (broadcast to ff:ff:ff:ff:ff:ff):  Who has 192.168.1.1? Tell 192.168.1.20
ARP reply    (unicast back):                    192.168.1.1 is-at 9c:53:22:aa:10:01
```

</Step>

<Step title="Switches and MAC tables">

<Tr>
<En>

A **switch** connects LAN devices and learns which MAC is on which port, by looking at the **source** MAC of every frame. Then it forwards frames only to the right port, keeping traffic private between the two devices talking. Unknown destinations and broadcasts are sent to all ports. In Linux, software bridges (`docker0`, `br0`) work the same way.

</En>
<Ur>

**Switch** LAN devices jorta hai aur har frame ka **source** MAC dekh kar seekhta hai ke kaunsa MAC kis port par hai. Phir wo frames sirf sahi port par bhejta hai, baat karne wale do devices ke darmiyan traffic private rakhte hue. Anjaan manzilen aur broadcasts saare ports par jate hain. Linux me software bridges (`docker0`, `br0`) isi tarah kaam karte hain.

</Ur>
</Tr>

```python
mac_table = {}
frames = [("aa:01", "bb:02", 1), ("bb:02", "aa:01", 2), ("aa:01", "bb:02", 1), ("cc:03", "ff:ff", 3)]
for src, dst, port in frames:
    mac_table[src] = port                                # learn: src lives on this port
    out = "flood to all ports" if dst == "ff:ff" or dst not in mac_table else f"forward to port {mac_table[dst]}"
    print(f"frame {src}→{dst} arrived on port {port}: {out}")
print("learned:", mac_table)
```

```text output
frame aa:01→bb:02 arrived on port 1: flood to all ports
frame bb:02→aa:01 arrived on port 2: forward to port 1
frame aa:01→bb:02 arrived on port 1: forward to port 2
frame cc:03→ff:ff arrived on port 3: flood to all ports
learned: {'aa:01': 1, 'bb:02': 2, 'cc:03': 3}
```

<Happened>
<Tr>
<En>The first frame was flooded because the switch didn't know `bb:02` yet. Once `bb:02` replied, the switch learned its port, so the third frame went straight there.</En>
<Ur>Pehla frame sab ports par gaya kyun ke switch abhi `bb:02` nahi jaanta tha. `bb:02` ke jawab dete hi switch ne us ka port seekh liya, isliye teesra frame seedha wahan gaya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Broadcast domains and VLANs">

<Tr>
<En>

A **broadcast domain** is the set of devices that hear each other's broadcasts (ARP, DHCP). A **VLAN** splits one physical network into several isolated ones, so guests, staff, servers, cameras and payment terminals don't share one flat network (PCI DSS even requires separating payment systems). Traffic between VLANs must pass a router/firewall, where rules apply. In the cloud, **subnets and security groups** play this role.

</En>
<Ur>

**Broadcast domain** un devices ka majmua hai jo ek doosre ke broadcasts (ARP, DHCP) sunte hain. **VLAN** ek physical network ko kai alag thalag networks me baant deta hai, taa ke mehman, staff, servers, cameras aur payment terminals ek hi chapte network par na hon (PCI DSS to payment systems ko alag karna laazmi karta hai). VLANs ke darmiyan traffic ko router/firewall se guzarna parta hai, jahan rules lagte hain. Cloud me **subnets aur security groups** yahi kaam karte hain.

</Ur>
</Tr>

```text
One office switch, three VLANs:

VLAN 10 Staff     10.10.10.0/24  laptops
VLAN 20 Servers   10.10.20.0/24  file server, internal apps
VLAN 30 Guests    10.10.30.0/24  visitors' phones   → internet only, blocked from VLAN 10 and 20
                     │
              router/firewall decides what may cross between VLANs
```

</Step>

<Step title="The local network inside Docker">

<Tr>
<En>

Docker creates a virtual switch (a Linux **bridge**, `docker0`), gives each container a virtual interface with its own MAC and IP, and acts as their IP allocator and gateway. That explains container IPs like `172.17.0.2`. The bridge's IP (`172.17.0.1`) is the containers' gateway; NAT then takes traffic out to the internet.

</En>
<Ur>

Docker ek virtual switch (Linux **bridge**, `docker0`) banata hai, har container ko apne MAC aur IP wala virtual interface deta hai, aur un ka IP baantne wala aur gateway banta hai. Isi se `172.17.0.2` jaise container IPs samajh aate hain. Bridge ka IP (`172.17.0.1`) containers ka gateway hai; phir NAT traffic ko internet tak le jata hai.

</Ur>
</Tr>

```text
$ ip -br addr show docker0
docker0   UP   172.17.0.1/16                       ← the containers' gateway
$ docker run --rm alpine ip route
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 scope link src 172.17.0.2   ← this container's IP
```

</Step>

## Common mistakes

<Compare>
<Bad title="Static IP inside the DHCP pool">

```text
DHCP pool:   192.168.1.100 – 192.168.1.150
Printer:     static 192.168.1.120          # one day DHCP gives .120 to a laptop → conflict
```

</Bad>
<Good title="Outside the pool, or a reservation">

```text
DHCP pool:   192.168.1.100 – 192.168.1.150
Printer:     static 192.168.1.20           # or a DHCP reservation for its MAC
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **DHCP pools too small** for all devices (phones, IoT, guests).
- **Wrong gateway or DNS** handed out by DHCP → "connected, no internet".
- **Flat networks** where guests, staff and servers share one LAN.
- **Treating a MAC address as a security identity**: MACs are trivial to change.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bohot chhote DHCP pools** saare devices (phones, IoT, mehman) ke liye.
- **DHCP ka ghalat gateway ya DNS dena** → "connected, no internet".
- **Chapte networks** jahan mehman, staff aur servers ek hi LAN par.
- **MAC address ko security pehchan samajhna**: MAC badalna bohot aasaan hai.

</Ur>
</Tr>

<DeepDive title="Real world: Wi-Fi works for some people only">

The admin checks an affected laptop:

```text
$ ip -br addr show wlan0
wlan0   UP   169.254.88.14/16              ← link-local: no DHCP answer
```

The DHCP pool was `192.168.1.100–192.168.1.150` (51 addresses) with 24-hour leases. The office had grown to 40 laptops plus 30 phones: the pool was **exhausted**, so new devices got no lease. Fix: enlarge the pool (`192.168.1.50–192.168.1.250`), shorten leases to 8 hours, and move phones to a separate guest VLAN with its own pool.

</DeepDive>

<DeepDive title="Security lens">

Anyone on the same local network can attack it at layer 2. Treat café, hotel and shared-office Wi-Fi as hostile.

- **ARP spoofing / poisoning:** an attacker sends fake ARP replies ("192.168.1.1 is at **my** MAC") and sits in the middle of the victim's traffic. Defences: HTTPS/TLS everywhere, Dynamic ARP Inspection on managed switches, client isolation on Wi-Fi.
- **Rogue DHCP:** a fake DHCP server hands out the attacker's IP as gateway or DNS. Defence: **DHCP snooping** on switches.
- **DHCP starvation:** exhausting the pool with fake MACs so real users get no IP.
- **MAC filtering isn't security:** MACs can be spoofed in one command.
- **Segmentation (VLANs, subnets, security groups)** limits how far an attacker can move after compromising one device.
- **802.1X / WPA3-Enterprise** requires authentication before a device even joins the network.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Describe the DHCP process.">
DHCP uses four messages known as DORA. The client broadcasts a Discover because it has no IP yet, a server replies with an Offer containing an IP address and settings such as mask, gateway and DNS, the client sends a Request for that offer, and the server confirms with an Acknowledge. The address is leased for a period and the client renews it before it expires.
</QA>

<QA q="What does ARP do and why is it needed?">
ARP maps an IPv4 address to a MAC address on the local network. Frames on Ethernet or Wi-Fi are delivered by MAC address, so before sending to a local IP or to the default gateway, a host broadcasts an ARP request asking who has that IP; the owner replies with its MAC, which is cached in the ARP table.
</QA>

<QA q="What does a 169.254.x.x address on a host indicate?">
It is a link-local address the host assigned itself because no DHCP server answered. It usually means DHCP failed, for example the server is down, unreachable, or its pool is exhausted, and the host cannot reach other networks.
</QA>

<QA q="What is ARP spoofing and how can it be mitigated?">
An attacker on the local network sends forged ARP replies claiming that an IP, often the gateway's, belongs to the attacker's MAC address, so victims send their traffic through the attacker. Mitigations include encryption such as TLS so intercepted traffic is unreadable, Dynamic ARP Inspection and port security on switches, Wi-Fi client isolation and network segmentation.
</QA>

</DeepDive>
