<BigIdea>
<Tr>
<En>
**JSON** (JavaScript Object Notation) is a **text format for structured data**. It has two structures, **objects** `{ "key": value }` (named fields) and **arrays** `[ value, value ]` (ordered lists), plus four simple types: **strings**, **numbers**, **booleans** and **`null`**, nested as deep as you like. The rules are strict: **double quotes**, **no trailing commas**, **no comments**. Every language can **parse** JSON (text → data) and **serialize** it (data → text). It's the default language of APIs, `package.json`, logs and cloud tools. Treat incoming JSON as **untrusted input**: parse it safely and validate it.
</En>
<Ur>
**JSON** (JavaScript Object Notation) **structured data ke liye text format** hai. Is ke do dhaanche hain, **objects** `{ "key": value }` (naam wale khane) aur **arrays** `[ value, value ]` (tarteeb wali fehristen), aur chaar saadi qisamen: **strings**, **numbers**, **booleans** aur **`null`**, jitna chahen andar andar. Qawaid sakht hain: **double quotes**, **aakhri comma nahi**, **comments nahi**. Har zubaan JSON ko **parse** (text → data) aur **serialize** (data → text) kar sakti hai. Ye APIs, `package.json`, logs aur cloud tools ki default zubaan hai. Bahar se aane wale JSON ko **na-bharose wala input** samjhein: mehfooz parse karein aur validate karein.
</Ur>

<Tr>
<En>

```json

  "orderId": 1042,
  "customer": {
    "name": "Olivia Brown",

    "vip": true

    { "sku": "MUG-01", "price": 800, "qty": 1 }
  ],
  "couponCode": null,
  "notes": "Leave at the gate"
}
```

## Learn it step by step

<Walkthrough>

<Step title="Objects: named fields">

<Tr>
<En>

An object is a collection of **key–value pairs** inside curly braces. Each key is a **string in double quotes**, then a colon `:` and a value; pairs are separated by commas. It describes **one thing** with named properties: a user, an order, a setting. Keys should be unique inside one object, and their order has **no meaning**: `{"a":1,"b":2}` and `{"b":2,"a":1}` are the same data.

</En>
<Ur>

Object curly braces ke andar **key–value joron** ka majmua hai. Har key **double quotes me string** hai, phir colon `:` aur value; jore commas se alag hote hain. Ye naam wali khasoosiyaat ke saath **ek cheez** bayan karta hai: user, order, setting. Ek object me keys alag alag hon, aur un ki tarteeb ka **koi matlab nahi**: `{"a":1,"b":2}` aur `{"b":2,"a":1}` ek hi data hain.

</Ur>
</Tr>

```bash
cat > user.json <<'EOF'
{"name": "Sam Lee", "age": 27, "city": "Chicago", "isStudent": false}
EOF
python3 -m json.tool user.json
```

```text output
{
    "name": "Sam Lee",
    "age": 27,
    "city": "Chicago",
    "isStudent": false
}
```

<Happened>
<Tr>
<En>`python3 -m json.tool` uses Python's built-in JSON module to **parse** the file and print it indented. If the JSON were invalid it would print an error instead, so it's also a quick validator with nothing to install. Whitespace between elements doesn't matter in JSON; it's only for humans.</En>
<Ur>`python3 -m json.tool` Python ka andar bana JSON module istemal kar ke file **parse** karta hai aur indent kar ke chhaapta hai. JSON ghalat hoti to error chhaapta, isliye ye kuch install kiye baghair jaldi ka validator bhi hai. JSON me elements ke beech khaali jagah ka koi farq nahi; ye sirf insaanon ke liye hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="The six value types">

<Tr>
<En>

A JSON value is one of exactly six types. There are **no** others: no dates, no binary data, no comments, no `undefined`. Dates are usually sent as **ISO 8601 strings** (`"2026-11-10T13:05:00Z"`), and binary data as Base64 strings.

| Type | Example | Notes |
| --- | --- | --- |
| string | `"Chicago"`, `"07700900123"` | Always **double** quotes |
| number | `27`, `-3.5`, `1.2e6` | No quotes; no `NaN`, `Infinity`, leading zeros or hex |
| boolean | `true`, `false` | Lowercase, no quotes |
| null | `null` | "No value / unknown", lowercase |
| object | `{"a": 1}` | Named fields |
| array | `[1, "two", null]` | Ordered list; items may have different types |

</En>
<Ur>

JSON value bilkul chhe qisamon me se ek hoti hai. Koi aur **nahi**: dates nahi, binary data nahi, comments nahi, `undefined` nahi. Dates aam tor par **ISO 8601 strings** (`"2026-11-10T13:05:00Z"`) ki shakal me bheji jati hain, aur binary data Base64 strings me.

| Qisam | Misaal | Note |
| --- | --- | --- |
| string | `"Chicago"`, `"07700900123"` | Hamesha **double** quotes |
| number | `27`, `-3.5`, `1.2e6` | Quotes nahi; `NaN`, `Infinity`, shuru ke zero ya hex nahi |
| boolean | `true`, `false` | Chhote huroof, quotes nahi |
| null | `null` | "Koi value nahi / na-maloom", chhote huroof |
| object | `{"a": 1}` | Naam wale khane |
| array | `[1, "two", null]` | Tarteeb wali fehrist; items alag qisam ke ho sakte hain |

</Ur>
</Tr>

```bash
node -e '
const data = JSON.parse(`{"s": "hi", "n": 42, "b": true, "z": null, "o": {"k": 1}, "a": [1, 2]}`);
for (const [key, value] of Object.entries(data)) {
  const type = value === null ? "null" : Array.isArray(value) ? "array" : typeof value;
  console.log(key.padEnd(2), "→", type);
}'
```

```text output
s  → string
n  → number
b  → boolean
z  → null
o  → object
a  → array
```

<Happened>
<Tr>
<En>

`JSON.parse` turned the text into a JavaScript object, and the loop printed each value's type. JavaScript's `typeof null` and `typeof []` are both `"object"` (an old quirk), so we check `null` and `Array.isArray` first to print the real JSON type.

A phone number like `"07700900123"` should be a **string**: as a number it loses the leading `0`, and you never do maths with it. Same for national ID numbers, ZIP codes and IDs with leading zeros.

</En>
<Ur>

`JSON.parse` ne text ko JavaScript object banaya, aur loop ne har value ki qisam chhaapi. JavaScript me `typeof null` aur `typeof []` dono `"object"` hain (purani ajeeb baat), isliye asli JSON qisam chhaapne ke liye pehle `null` aur `Array.isArray` check karte hain.

`"07700900123"` jaisa phone number **string** hona chahiye: number ban kar shuru ka `0` kho deta hai, aur us par hisaab kabhi nahi hota. Yahi qomi shanakhti numbers, ZIP codes aur shuru me zero wali IDs ke saath hai.

</Ur>
</Tr>
</Happened>

<Step title="Arrays and nesting">

<Tr>
<En>

An array is an ordered list inside `[ ]`, and objects and arrays can contain each other to any depth, because real data is hierarchical: an order **has** a customer and **has** a list of items. Reading nested values uses a **path**: `order.items[0].sku` means "field `items`, element 0 (the first), its field `sku`". Arrays count from **0**. Keep nesting to about 3–4 levels so it stays readable.

</En>
<Ur>

Array `[ ]` ke andar tarteeb wali fehrist hai, aur objects aur arrays ek doosre ko kisi bhi gehrai tak rakh sakte hain, kyun ke asli data darja ba darja hota hai: order ka ek customer **hota hai** aur items ki fehrist **hoti hai**. Andar ki values ek **path** se parhte hain: `order.items[0].sku` ka matlab "khana `items`, element 0 (pehla), us ka khana `sku`". Arrays **0** se ginte hain. Parhne laayiq rakhne ke liye 3–4 darjon tak rakhein.

</Ur>
</Tr>

```bash
cat > order.json <<'EOF'
{
  "orderId": 1042,
  "customer": { "name": "Olivia Brown", "vip": true },
  "items": [
    { "sku": "TSHIRT-M", "price": 1500, "qty": 2 },
    { "sku": "MUG-01", "price": 800, "qty": 1 }
  ],
  "couponCode": null
}
EOF
node -e '
const order = JSON.parse(require("fs").readFileSync("order.json", "utf8"));
console.log("customer name:", order.customer.name);
console.log("first item:   ", order.items[0].sku);
console.log("item count:   ", order.items.length);
const total = order.items.reduce((sum, item) => sum + item.price * item.qty, 0);
console.log("order total:  ", total);
console.log("has coupon:   ", order.couponCode !== null);'
```

```text output
customer name: Olivia Brown
first item:    TSHIRT-M
item count:    2
order total:   3800
has coupon:    false
```

<Tr>
<En>

- `readFileSync` read the file as text; `JSON.parse` turned it into an object.
- `order.customer.name` went into the nested object; `order.items[0].sku` took the first array element.
- `reduce` added up `price * qty`: 1500×2 + 800×1 = 3800.
- `couponCode` is `null` ("no coupon"), so `!== null` is `false`.

</En>
<Ur>

- `readFileSync` ne file text ki tarah parhi; `JSON.parse` ne use object banaya.
- `order.customer.name` andar wale object me gaya; `order.items[0].sku` ne array ka pehla element liya.
- `reduce` ne `price * qty` jora: 1500×2 + 800×1 = 3800.
- `couponCode` `null` hai ("koi coupon nahi"), isliye `!== null` `false` hai.

<Step title="The strict rules, and the errors you'll see">

<Tr>
<En>

JSON is **much stricter** than JavaScript object syntax: one wrong character makes the whole document invalid. That strictness is why every parser in every language agrees on what a document means. Parsers report the **line and column** of the first problem. The five most common mistakes: **trailing comma**, **single quotes**, **unquoted keys**, **comments**, **missing commas**.

</En>
<Ur>

JSON JavaScript object syntax se **kahin zyada sakht** hai: ek ghalat harf poori document ko ghalat bana deta hai. Isi sakhti ki wajah se har zubaan ka har parser document ke matlab par muttafiq hai. Parsers pehle masle ki **line aur column** batate hain. Paanch sab se aam ghaltiyan: **aakhri comma**, **single quotes**, **baghair quotes ki keys**, **comments**, **ghayab commas**.

</Ur>
</Tr>

```bash
check() { printf '%s' "$2" | python3 -m json.tool >/dev/null 2>err.txt && echo "$1: valid" || echo "$1: $(cat err.txt)"; }
check "correct        " '{"name": "Sam", "tags": ["a", "b"]}'
check "trailing comma " '{"name": "Sam", "age": 30,}'
check "single quotes  " "{'name': 'Sam'}"
check "unquoted key   " '{name: "Sam"}'
check "comment        " '{"port": 8080 // web port
}'
check "missing comma  " '{"a": 1 "b": 2}'
```

```text output
correct        : valid
trailing comma : Illegal trailing comma before end of object: line 1 column 26 (char 25)
single quotes  : Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
unquoted key   : Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
comment        : Expecting ',' delimiter: line 1 column 15 (char 14)
missing comma  : Expecting ',' delimiter: line 1 column 9 (char 8)
```

<Happened>
<Tr>
<En>

- `check` pipes the text into `python3 -m json.tool`, hides normal output, and prints "valid" or the saved error.
- A **trailing comma** (`30,}`) is fine in JavaScript but **not** JSON. **Single quotes** and **unquoted keys** aren't allowed. **Comments** don't exist in JSON (`tsconfig.json` and VS Code settings accept a non-standard variant called JSONC). The last one is a **missing comma**.
- "line 1 column 26 (char 25)" is where the parser got confused (columns from 1, characters from 0). Wording depends on the Python version; Node and browsers word it differently but point to the same spot.

</En>
<Ur>

- `check` text ko `python3 -m json.tool` me bhejta hai, aam output chhupata hai, aur "valid" ya save kiya error chhaapta hai.
- **Aakhri comma** (`30,}`) JavaScript me theek hai lekin JSON me **nahi**. **Single quotes** aur **baghair quotes keys** mana hain. JSON me **comments** hote hi nahi (`tsconfig.json` aur VS Code settings JSONC naam ka ghair mayaari roop maante hain). Aakhri wala **ghayab comma** hai.
- "line 1 column 26 (char 25)" wo jagah hai jahan parser uljha (columns 1 se, characters 0 se). Alfaaz Python version par munhasir hain; Node aur browsers alag alfaaz me lekin wahi jagah batate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Strings and escaping">

<Tr>
<En>

Inside a string, some characters must be **escaped** with a backslash: `\"` (quote), `\\` (backslash), `\n` (new line), `\t` (tab), `\uXXXX` (any Unicode character). Otherwise a quote inside the text would end the string early. JSON text is **UTF-8**, so accented letters, other alphabets and emoji can appear directly. Let your language's library do the escaping; never build JSON by gluing strings together.

</En>
<Ur>

String ke andar kuch huroof backslash se **escape** karne padte hain: `\"` (quote), `\\` (backslash), `\n` (nayi line), `\t` (tab), `\uXXXX` (koi bhi Unicode harf). Warna text ke andar ka quote string ko jaldi khatam kar deta. JSON text **UTF-8** hai, isliye accent wale huroof, doosri zubaanon ke huroof aur emoji seedhe aa sakte hain. Escaping apni zubaan ki library ko karne dein; strings jor kar JSON kabhi na banayen.

</Ur>
</Tr>

```bash
node -e '
const message = {
  quote: "He said \"hello\"",
  path: "C:\\Users\\Alex",
  multiline: "line one\nline two",
  greeting: "Grüße"
};
const text = JSON.stringify(message);
console.log(text);
console.log("round trip equal:", JSON.parse(text).greeting === "Grüße");'
```

```text output
{"quote":"He said \"hello\"","path":"C:\\Users\\Alex","multiline":"line one\nline two","greeting":"Grüße"}
round trip equal: true
```

<Happened>
<Tr>
<En>

- In the JavaScript source the real values are `He said "hello"`, `C:\Users\Alex`, and a real line break.
- `JSON.stringify` **added the JSON escapes** automatically: quotes became `\"`, each backslash `\\`, and the line break `\n`.
- The German word `Grüße` stayed as-is, because JSON is UTF-8, and `JSON.parse` gave back exactly the same value.

**Never** build JSON like `'{"name": "' + name + '"}'`: if `name` contains a quote, you get broken (or malicious) JSON.

</En>
<Ur>

- JavaScript source me asli values `He said "hello"`, `C:\Users\Alex`, aur asli nayi line hain.
- `JSON.stringify` ne JSON escapes **khud jore**: quotes `\"` bane, har backslash `\\`, aur nayi line `\n`.
- German lafz `Grüße` waisa hi raha, kyun ke JSON UTF-8 hai, aur `JSON.parse` ne bilkul wahi value wapas di.

JSON **kabhi** `'{"name": "' + name + '"}'` ki tarah na banayen: `name` me quote ho to tooti (ya bad-niyat) JSON banti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Numbers and their pitfalls">

<Tr>
<En>

JSON numbers are decimals with an optional exponent (`1.5e3`). The standard doesn't limit their size, but **parsers do**. JavaScript stores every number as a 64-bit float, exact for integers only up to **2^53 − 1 = 9007199254740991**, so bigger IDs silently change. APIs therefore send big IDs **as strings** (`"id_str"`). For money, use integers of the smallest unit (cents) or decimal strings, never floats. `NaN`, `Infinity`, leading zeros (`007`) and a leading `+` aren't valid JSON.

</En>
<Ur>

JSON numbers ikhtiyari exponent (`1.5e3`) wale ashariya hain. Standard un ka size mehdood nahi karta, lekin **parsers karte hain**. </Ur>

<Step title="Validate data with JSON Schema">

<Tr>
<En>

Valid **syntax** isn't enough: `{"qty": -5}` is perfectly valid JSON but nonsense data. **JSON Schema** is a JSON document describing what valid data looks like: required fields, types, allowed values, string patterns, number ranges. Check every incoming document against it and reject bad or malicious data before your code touches it. Libraries: `ajv` (JavaScript), `jsonschema` (Python), and Zod or Pydantic for schemas in code. OpenAPI uses JSON Schema to describe API bodies.

</En>
<Ur>

Durust **syntax** kaafi nahi: `{"qty": -5}` bilkul durust JSON hai lekin be-maani data. **JSON Schema** ek JSON document hai jo batata hai durust data kaisa dikhe: lazmi khane, qisamen, ijazat wali values, string ke patterns, numbers ki hadden. Har aane wali document is se check karein aur kharab ya bad-niyat data code tak pahunchne se pehle radd karein. Libraries: `ajv` (JavaScript), `jsonschema` (Python), aur code me schemas ke liye Zod ya Pydantic. OpenAPI API bodies bayan karne ke liye JSON Schema istemal karta hai.

</Ur>
</Tr>

```bash
cat > order.schema.json <<'EOF'
{
  "type": "object",
  "required": ["orderId", "items"],
  "properties": {
    "orderId": { "type": "integer", "minimum": 1 },
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["sku", "qty"],
        "properties": {
          "sku": { "type": "string", "pattern": "^[A-Z0-9-]+$" },
          "qty": { "type": "integer", "minimum": 1, "maximum": 100 }
        },
        "additionalProperties": false
      }
    }
  }
}
EOF
cat > validate.py <<'EOF'
import json, sys
from jsonschema import Draft202012Validator

schema = json.load(open("order.schema.json"))
validator = Draft202012Validator(schema)
for text in sys.argv[1:]:
    errors = sorted(validator.iter_errors(json.loads(text)), key=lambda e: list(e.path))
    if not errors:
        print("VALID  ", text)
    for e in errors:
        path = "/".join(str(p) for p in e.path) or "(root)"
        print("INVALID", path, "→", e.message)
EOF
python3 validate.py \
  '{"orderId": 7, "items": [{"sku": "MUG-01", "qty": 2}]}' \
  '{"orderId": 7, "items": [{"sku": "mug 01", "qty": -5, "price": 0}]}' \
  '{"items": []}'
```

```text output

INVALID items/0 → Additional properties are not allowed ('price' was unexpected)
INVALID items/0/qty → -5 is less than the minimum of 1
INVALID items/0/sku → 'mug 01' does not match '^[A-Z0-9-]+$'
INVALID (root) → 'orderId' is a required property
INVALID items → [] should be non-empty
```

<Happened>
<Tr>
<En>

- The schema requires `orderId` (integer ≥ 1) and a non-empty `items` array; each item needs `sku` (uppercase letters, digits, dashes) and `qty` (1–100), and `additionalProperties: false` forbids other fields.
- `iter_errors` returns **all** problems, not just the first, with the path to each bad value.
- The second document had three problems. `"price": 0` was rejected as unexpected: a client should never choose the price; the server looks it up.
- The third was missing `orderId` and had an empty `items` list.

</En>
<Ur>

- Schema `orderId` (integer ≥ 1) aur khaali na hone wala `items` array lazmi karta hai; har item ko `sku` (bare huroof, hindse, dash) aur `qty` (1–100) chahiye, aur `additionalProperties: false` doosre khane mana karta hai.
- `iter_errors` sirf pehla nahi, **saare** masle har kharab value ke path ke saath deta hai.
- Doosri document me teen masle the. `"price": 0` ghair mutawaqqa keh kar radd hua: client ko kabhi qeemat chunne na dein; server khud dekhta hai.
- Teesri me `orderId` ghayab tha aur `items` khaali.

</Ur>

<Step title="Security: parse safely">

<Tr>
<En>

JSON from users, services or files is **untrusted input**. Attackers send crafted JSON to change prices, become admin, crash servers or run code. Use only real parsers (`JSON.parse`, `json.loads`), **never** `eval()`. Validate with a schema, limit the body size (e.g. `express.json({ limit: "100kb" })`), and copy only the fields you expect. The demo shows two surprises: duplicate keys and **prototype pollution**.

</En>
<Ur>

Users, services ya files se aane wala JSON **na-bharose wala input** hai. Hamla awar banayi hui JSON bhej kar qeematen badalte, admin bante, servers girate ya code chalate hain. Sirf asli parsers (`JSON.parse`, `json.loads`), `eval()` **kabhi nahi**. Schema se validate karein, body ka size mehdood karein (maslan `express.json({ limit: "100kb" })`), aur sirf mutawaqqa khane copy karein. Demo do hairaniyan dikhata hai: dohri keys aur **prototype pollution**.

</Ur>
</Tr>

```bash
node -e '
const dup = JSON.parse(`{"role": "user", "role": "admin"}`);
console.log("duplicate keys, last one wins:", dup.role);

function naiveMerge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object" && source[key] !== null) {
      target[key] = target[key] || {};
      naiveMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}
const attackerBody = JSON.parse(`{"theme": "dark", "__proto__": {"isAdmin": true}}`);
naiveMerge({}, attackerBody);
const freshUser = {};
console.log("brand-new object isAdmin:", freshUser.isAdmin);'
```

```text output
duplicate keys, last one wins: admin
brand-new object isAdmin: true
```

<Happened>
<Tr>
<En>

- **Duplicate keys:** the standard says keys *should* be unique but doesn't forbid duplicates, and most parsers keep the **last**. If a security check reads the first `role` and your app reads the last, an attacker slips `"admin"` past the check.
- **Prototype pollution:** `naiveMerge` copies every key from the user's settings, a very common "update my settings" pattern. On the key `__proto__`, it reached the shared prototype of **all** objects and wrote `isAdmin = true` there.
- Now **every** object, even a brand-new `{}`, has `isAdmin === true`. If the app checks `if (user.isAdmin)`, the attacker is admin everywhere.
- Defences: skip `__proto__`, `constructor` and `prototype` when merging; use `Object.create(null)` or `Map`; keep libraries updated; validate with `additionalProperties: false`.

</En>
<Ur>

- **Dohri keys:** standard kehta hai keys alag *honi chahiyen* lekin dohri ko mana nahi karta, aur zyada tar parsers **aakhri** rakhte hain. Agar security check pehla `role` parhe aur app aakhri, to hamla awar `"admin"` check se guzar leta hai.
- **Prototype pollution:** `naiveMerge` user ki settings ki har key copy karta hai, "meri settings update karo" ka bohot aam andaaz. `__proto__` key par wo **saare** objects ke saanjhe prototype tak pahuncha aur wahan `isAdmin = true` likh diya.
- Ab **har** object, bilkul naya `{}` bhi, `isAdmin === true` rakhta hai. App `if (user.isAdmin)` check kare to hamla awar har jagah admin hai.
- Bachao: merge karte waqt `__proto__`, `constructor` aur `prototype` chhorein; `Object.create(null)` ya `Map` istemal karein; libraries update rakhein; `additionalProperties: false` se validate karein.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Hand-built JSON, numbers for IDs, trust the client">

```text
const body = '{"name": "' + name + '", "phone": 07700900123}';
User.update(JSON.parse(body));        // role, isAdmin, price... all accepted
```

</Bad>
<Good title="Library-built JSON, strings for IDs, pick fields">

```text
const body = JSON.stringify({ name, phone: "07700900123" });
const { name: n, phone } = JSON.parse(body);
User.update({ name: n, phone });      // only the fields we expect
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Trailing commas, single quotes, comments** in `.json` files, which break builds and deployments.
- **Floats for money:** `0.1 + 0.2 !== 0.3`. Use integers of the smallest unit or decimal strings.
- **Forgetting `Content-Type: application/json`** when sending JSON to an API.
- **Not handling `JSON.parse` errors**, so one bad request crashes the server.
- **Expecting `Date`s back after parsing:** they come back as strings.
- **Assuming key order matters:** objects are unordered; use an array if order matters.
- **Pretty-printing JSON Lines**, which breaks one-object-per-line.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- `.json` files me **aakhri commas, single quotes, comments**, jo builds aur deployments torte hain.
- **Paison ke liye floats:** `0.1 + 0.2 !== 0.3`. Sab se chhoti ikai ke integers ya decimal strings.

<DeepDive title="Real world: payment webhooks">

A trading platform receives webhooks from a payment provider: JSON bodies like `{"event": "payment.succeeded", "orderId": "1042", "amount": 150000, "currency": "USD"}`. The backend:

1. checks the request's **signature header** so only the real provider can send events (see **Digital Signatures**),
2. limits the body to 100 KB and parses it with `JSON.parse` inside `try/catch`,
3. validates it against a JSON Schema: `amount` is an integer in cents (150000 = $1,500.00), `orderId` is a **string** so big IDs stay exact, and unknown fields are rejected,
4. looks up the order and compares the amount with the stored price, never trusting the amount alone,
5. logs the event as one JSON line (`{"level":"info","msg":"payment.succeeded","orderId":"1042"}`) for searching.

When a bug report says "order 1042 was marked paid twice", an engineer runs `jq 'select(.orderId == "1042")'` over the logs, sees two identical webhook deliveries, and the team makes the handler **idempotent** (it ignores an event ID it has already processed).

</DeepDive>

<DeepDive title="Security lens">

Valid JSON is not safe JSON. Parse with a real parser, validate against a schema, and only use the fields you expect.

- **Never `eval()` JSON.** `JSON.parse` only reads data; `eval` runs code.
- **Mass assignment:** don't do `User.update(req.body)`. Pick allowed fields explicitly, or attackers add `"role": "admin"`.
- **Prototype pollution:** block `__proto__`, `constructor` and `prototype` keys; keep libraries like lodash updated.
- **Denial of service:** limit body size and nesting depth.
- **Duplicate keys and parser differences:** reject duplicates where security depends on them.
- **Big numbers:** precision loss can make checks compare the wrong IDs or amounts.
- **Don't leak data in responses:** no password hashes, internal IDs or stack traces in error JSON.
- **Escape JSON inside HTML:** in a `<script>` tag, write `<` as `\u003c`, or a string containing `</script>` can break out and run code (XSS).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What data types does JSON support?">
JSON supports six types: strings in double quotes, numbers, the booleans true and false, null, objects as unordered collections of string keys and values, and arrays as ordered lists of values. There are no native types for dates, binary data, undefined, NaN or Infinity, so dates are typically ISO 8601 strings and binary data Base64-encoded strings.
</QA>

<QA q="What is the difference between JSON and a JavaScript object?">
JSON is a text format, while a JavaScript object is an in-memory data structure. JSON requires double-quoted keys and strings, does not allow trailing commas, comments, functions, undefined or special numbers, and must be parsed with JSON.parse to become an object or produced with JSON.stringify from one.
</QA>

<QA q="Why might a large numeric ID change after being parsed in JavaScript, and how do you avoid it?">
JavaScript represents numbers as 64-bit floating point values, which can only represent integers exactly up to 2 to the power 53 minus 1. Larger integers are rounded silently during parsing. APIs avoid this by sending such IDs as strings, or clients can use BigInt-aware parsers.
</QA>

<QA q="What is JSON Lines and when would you use it?">
JSON Lines is a format where each line of a file is a separate, complete JSON value, usually an object. It allows appending records and streaming or processing very large files line by line, which suits structured logs, event streams and data exports.
</QA>

<QA q="How do you safely handle JSON received from clients?">
Limit the request size, parse it with a real JSON parser inside error handling, validate it against a schema that defines required fields, types and ranges and disallows unexpected properties, copy only expected fields instead of mass-assigning the body, protect against prototype pollution in JavaScript, and never trust security-relevant values such as prices or roles from the client.
</QA>

</DeepDive>
