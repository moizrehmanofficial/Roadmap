<Callout type="tip" title="In one minute">
**JSON** (JavaScript Object Notation) is a **text format for structured data**. It has just two structures: **objects** `{ "key": value }` (named fields) and **arrays** `[ value, value ]` (ordered lists), plus four simple types: **strings** `"text"`, **numbers** `42`, **booleans** `true`/`false` and **`null`**. These can be nested as deep as you like. The rules are strict: keys in **double quotes**, **no trailing commas**, **no comments**, no single quotes. Every language can **parse** JSON (text → data) and **serialize** it (data → text): `JSON.parse` / `JSON.stringify` in JavaScript, `json.loads` / `json.dumps` in Python, `jq` in the terminal. It's the default language of REST APIs, `package.json`, logs and cloud configs. Treat incoming JSON as **untrusted input**: parse it safely and validate it.
</Callout>

## Start from zero

<Callout type="analogy">
Think of JSON as a **standard form** that every computer agrees on. Imagine a school admission form: it has **labelled boxes** ("Name: ___", "Age: ___") and **lists** ("Subjects: 1. ___ 2. ___ 3. ___"). Any school in the world can read the form because the layout is standard. A JSON **object** is the set of labelled boxes, and a JSON **array** is a numbered list. Because the format is so strict and simple, a program written in JavaScript in Karachi can send a form to a program written in Python in Berlin, and both understand it perfectly.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Data format** | An agreed way to write data as text or bytes | JSON, YAML, CSV, XML |
| **Object** | A set of `"key": value` pairs inside `{ }` | `{"name": "Ali"}` |
| **Key** | The label of a value in an object (always a string) | `"name"` |
| **Array** | An ordered list of values inside `[ ]` | `[1, 2, 3]` |
| **Nesting** | Putting objects/arrays inside other objects/arrays | `{"user": {"tags": ["a"]}}` |
| **Parse** | Turn JSON **text** into data your program can use | `JSON.parse(text)` |
| **Serialize / stringify** | Turn data into JSON **text** | `JSON.stringify(obj)` |
| **API** | A way for programs to talk to each other, often sending JSON over HTTP | `GET /api/users/7` |
| **Schema** | A description of what valid data must look like | "age must be a number ≥ 0" |

## What is it?

JSON is a plain-text format defined in a tiny standard (RFC 8259 / ECMA-404). It started as a subset of JavaScript syntax, but today it's **language-independent**. Here is a complete JSON document describing one order:

```json
{
  "orderId": 1042,
  "customer": {
    "name": "Ayesha Khan",
    "email": "ayesha@example.com",
    "vip": true
  },
  "items": [
    { "sku": "TSHIRT-M", "price": 1500, "qty": 2 },
    { "sku": "MUG-01", "price": 800, "qty": 1 }
  ],
  "couponCode": null,
  "notes": "Leave at the gate"
}
```

```text
object { }
├── "orderId"    → number   1042
├── "customer"   → object { }
│     ├── "name"  → string  "Ayesha Khan"
│     ├── "email" → string  "ayesha@example.com"
│     └── "vip"   → boolean true
├── "items"      → array [ ]
│     ├── [0] → object { "sku", "price", "qty" }
│     └── [1] → object { "sku", "price", "qty" }
├── "couponCode" → null
└── "notes"      → string  "Leave at the gate"
```

## Why does it matter?

- **APIs:** almost every web and mobile app talks to its backend in JSON. Your React front end, a Stripe payment, a weather API: all JSON.
- **Configuration:** `package.json`, `tsconfig.json`, VS Code `settings.json`, AWS IAM policies, Terraform state, Docker `daemon.json`.
- **Logs and monitoring:** modern apps write **structured logs** as one JSON object per line, which tools like Elasticsearch, Loki and CloudWatch can search.
- **Databases:** MongoDB stores JSON-like documents; PostgreSQL has `jsonb` columns.
- **DevOps and security:** `kubectl get pods -o json`, `aws ... --output json`, and security tools (gitleaks, Trivy) all output JSON for automation.

## When and where do you use it?

- **Use JSON** for data exchanged between programs (APIs, messages, logs), and for configs that programs write or read.
- **Prefer YAML or TOML** for configs that **humans** edit a lot and that need comments (Kubernetes, GitHub Actions, `pyproject.toml`). These are the next lessons.
- **Prefer CSV** for big flat tables (spreadsheets, exports).
- You'll read and write JSON in: the browser DevTools Network tab, Postman/Insomnia, the terminal with `jq`, and every backend language.

## Concepts one by one

### 1. Objects: named fields

<Explain>
<What>
An object is a collection of **key–value pairs** inside curly braces. Each key is a **string in double quotes**, followed by a colon `:` and a value. Pairs are separated by commas.
</What>
<Why>
It describes **one thing** with named properties: a user, an order, a setting.
</Why>
<When>
Whenever data has named fields.
</When>
<Where>
API responses (`{"id": 7, "name": "Ali"}`), config files, database documents.
</Where>
<How>
Keys should be unique inside one object. The order of keys has **no meaning**: `{"a":1,"b":2}` and `{"b":2,"a":1}` are the same data.
</How>
</Explain>

```bash
cat > user.json <<'EOF'
{"name": "Ali Raza", "age": 27, "city": "Lahore", "isStudent": false}
EOF
python3 -m json.tool user.json
```

```text output
{
    "name": "Ali Raza",
    "age": 27,
    "city": "Lahore",
    "isStudent": false
}
```

Line by line:

- `cat > user.json <<'EOF'` writes one line of JSON into a file.
- `python3 -m json.tool user.json` uses Python's built-in JSON module to **parse** the file and print it nicely indented (4 spaces). If the JSON were invalid, it would print an error instead, so it's also a quick validator. No installation needed.
- The output has the same four pairs, one per line. Whitespace (spaces, new lines) between elements doesn't matter in JSON; it's only for humans.

### 2. The six value types

<Explain>
<What>
A JSON value is one of exactly six types: **string**, **number**, **boolean**, **null**, **object**, **array**.
</What>
<Why>
Knowing the type tells you what you can do with a value: add numbers, loop over arrays, read fields of objects.
</Why>
<When>
Every time you design or read an API.
</When>
<Where>
Everywhere. There are **no** other types: no dates, no binary data, no comments, no `undefined`.
</Where>
<How>
Dates are usually sent as **strings** in ISO 8601 format (`"2026-11-10T13:05:00Z"`), and binary data as Base64 strings.
</How>
</Explain>

| Type | Example | Notes |
| --- | --- | --- |
| string | `"Lahore"`, `"03001234567"` | Always **double** quotes |
| number | `27`, `-3.5`, `1.2e6` | No quotes; no `NaN`, `Infinity`, leading zeros or hex |
| boolean | `true`, `false` | Lowercase, no quotes |
| null | `null` | "No value / unknown", lowercase |
| object | `{"a": 1}` | Named fields |
| array | `[1, "two", null]` | Ordered list; items may have different types |

```bash
node -e '
const data = JSON.parse(`{"s": "hi", "n": 42, "b": true, "z": null, "o": {"k": 1}, "a": [1, 2]}`);
for (const [key, value] of Object.entries(data)) {
  const type = value === null ? "null" : Array.isArray(value) ? "array" : typeof value;
  console.log(key.padEnd(2), "→", type);
}'
```

```text output
s  → string
n  → number
b  → boolean
z  → null
o  → object
a  → array
```

Line by line:

- `node -e '...'` runs a small JavaScript program directly from the terminal.
- `JSON.parse(...)` turns the JSON text into a JavaScript object.
- `Object.entries(data)` gives each `[key, value]` pair, and the loop prints the type of every value.
- JavaScript's `typeof null` is `"object"` (a famous old quirk) and `typeof []` is also `"object"`, so we check `null` and `Array.isArray` first to print the real JSON type.

A phone number like `"03001234567"` should be a **string**, not a number: as a number it would lose the leading `0`, and you never do maths with it. The same goes for CNICs, ZIP codes and IDs with leading zeros.

### 3. Arrays and nesting

<Explain>
<What>
An array is an ordered list of values inside `[ ]`. Objects and arrays can contain each other to any depth.
</What>
<Why>
Real data is hierarchical: an order **has** a customer and **has** a list of items, and each item has fields.
</Why>
<When>
Lists of things (users, products, log entries) and grouped details.
</When>
<Where>
Reading nested values uses a **path**: `order.items[0].sku` means "the field `items`, element 0 (the first), its field `sku`". Arrays count from **0**.
</Where>
<How>
Keep nesting reasonable (3–4 levels). Very deep JSON is hard to read and to query.
</How>
</Explain>

```bash
cat > order.json <<'EOF'
{
  "orderId": 1042,
  "customer": { "name": "Ayesha Khan", "vip": true },
  "items": [
    { "sku": "TSHIRT-M", "price": 1500, "qty": 2 },
    { "sku": "MUG-01", "price": 800, "qty": 1 }
  ],
  "couponCode": null
}
EOF
node -e '
const order = JSON.parse(require("fs").readFileSync("order.json", "utf8"));
console.log("customer name:", order.customer.name);
console.log("first item:   ", order.items[0].sku);
console.log("item count:   ", order.items.length);
const total = order.items.reduce((sum, item) => sum + item.price * item.qty, 0);
console.log("order total:  ", total);
console.log("has coupon:   ", order.couponCode !== null);'
```

```text output
customer name: Ayesha Khan
first item:    TSHIRT-M
item count:    2
order total:   3800
has coupon:    false
```

Line by line:

- `require("fs").readFileSync("order.json", "utf8")` reads the file as text; `JSON.parse` turns it into an object.
- `order.customer.name` goes into the nested `customer` object.
- `order.items[0].sku` takes the first element of the `items` array (index 0) and reads its `sku`.
- `order.items.length` is the number of elements in the array.
- `reduce` loops over the items and adds up `price * qty`: 1500×2 + 800×1 = 3800.
- `couponCode` is `null`, meaning "no coupon". Checking `!== null` tells us whether one exists.

### 4. The strict rules, and the errors you'll see

<Explain>
<What>
JSON is **much stricter** than JavaScript object syntax. One wrong character makes the whole document invalid.
</What>
<Why>
Strictness is why every parser in every language agrees on what a JSON document means.
</Why>
<When>
Every time you write JSON by hand, e.g. editing `package.json` or an API request body in Postman.
</When>
<Where>
Your editor highlights errors; parsers report the **line and column** (or character position) of the first problem.
</Where>
<How>
The five most common mistakes: **trailing comma**, **single quotes**, **unquoted keys**, **comments**, and **missing commas** between items.
</How>
</Explain>

```bash
check() { printf '%s' "$2" | python3 -m json.tool >/dev/null 2>err.txt && echo "$1: valid" || echo "$1: $(cat err.txt)"; }
check "correct        " '{"name": "Ali", "tags": ["a", "b"]}'
check "trailing comma " '{"name": "Ali", "age": 30,}'
check "single quotes  " "{'name': 'Ali'}"
check "unquoted key   " '{name: "Ali"}'
check "comment        " '{"port": 8080 // web port
}'
check "missing comma  " '{"a": 1 "b": 2}'
```

```text output
correct        : valid
trailing comma : Illegal trailing comma before end of object: line 1 column 26 (char 25)
single quotes  : Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
unquoted key   : Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
comment        : Expecting ',' delimiter: line 1 column 15 (char 14)
missing comma  : Expecting ',' delimiter: line 1 column 9 (char 8)
```

Line by line:

- `check` is a small function: it pipes the JSON text (`$2`) into `python3 -m json.tool`, throws away the normal output, and saves error messages in `err.txt`. If parsing succeeds it prints "valid", otherwise the error.
- **Trailing comma** after the last item (`30,}`) is allowed in JavaScript but **not** in JSON.
- **Single quotes** are not allowed: strings and keys need **double** quotes.
- **Unquoted keys** like `name:` are fine in JavaScript, but not in JSON.
- **Comments** (`//` or `/* */`) do not exist in JSON. (Some tools accept "JSON with comments", e.g. `tsconfig.json` and VS Code settings, but that's a non-standard extension called JSONC.)
- **Missing comma** between `"a": 1` and `"b": 2`.
- "line 1 column 26 (char 25)" points to where the parser got confused. Columns count from 1 and characters from 0. The exact wording depends on your Python version; Node and browsers word errors differently but point to the same spots.

### 5. Strings and escaping

<Explain>
<What>
Inside a string, some characters must be **escaped** with a backslash: `\"` (quote), `\\` (backslash), `\n` (new line), `\t` (tab), and `\uXXXX` for any Unicode character.
</What>
<Why>
Otherwise a quote inside the text would end the string early and break the document.
</Why>
<When>
Text containing quotes, Windows paths (`C:\Users`), multi-line messages, emojis or Urdu text.
</When>
<Where>
Let your language's JSON library do the escaping (`JSON.stringify`, `json.dumps`). Never build JSON by gluing strings together.
</Where>
<How>
JSON text is **UTF-8**, so Urdu, Arabic and emoji can appear directly; `\u` escapes are just an alternative.
</How>
</Explain>

```bash
node -e '
const message = {
  quote: "He said \"hello\"",
  path: "C:\\Users\\Moiz",
  multiline: "line one\nline two",
  urdu: "شکریہ"
};
const text = JSON.stringify(message);
console.log(text);
console.log("round trip equal:", JSON.parse(text).urdu === "شکریہ");'
```

```text output
{"quote":"He said \"hello\"","path":"C:\\Users\\Moiz","multiline":"line one\nline two","urdu":"شکریہ"}
round trip equal: true
```

Line by line:

- In the JavaScript source, `\"` and `\\` are JavaScript escapes. The real values are `He said "hello"` and `C:\Users\Moiz`, and `\n` is a real line break.
- `JSON.stringify` converts the object to JSON text and **adds the JSON escapes** automatically: the quotes become `\"`, each backslash becomes `\\`, and the line break becomes `\n`.
- The Urdu word is written as-is, because JSON is UTF-8.
- `JSON.parse(text)` reads it back, and the Urdu value is exactly the same: a perfect round trip.

**Never** build JSON like `'{"name": "' + name + '"}'`. If `name` contains a quote, you get broken (or malicious) JSON. Always use the library.

### 6. Numbers and their pitfalls

<Explain>
<What>
JSON numbers are decimal: integers or fractions, with an optional exponent (`1.5e3`). The standard doesn't limit their size, but **parsers do**.
</What>
<Why>
JavaScript stores every number as a 64-bit float, which can represent integers exactly only up to **2^53 − 1 = 9007199254740991**. Bigger IDs silently change.
</Why>
<When>
Large IDs (Twitter/X IDs, database `bigint`s, blockchain amounts), money, and scientific values.
</When>
<Where>
APIs commonly send big IDs **as strings** (`"id_str"`) for this reason. For money, use integers of the smallest unit (paisa, cents) or decimal strings, never floats.
</Where>
<How>
`NaN` and `Infinity` are **not** valid JSON. Leading zeros (`007`) and a leading `+` are not allowed either.
</How>
</Explain>

```bash
node -e '
const parsed = JSON.parse(`{"id": 9007199254740993, "price": 0.1}`);
console.log("id after parse:  ", parsed.id);
console.log("max safe integer:", Number.MAX_SAFE_INTEGER);
console.log("0.1 + 0.2 =      ", 0.1 + 0.2);
console.log("NaN becomes:     ", JSON.stringify({ x: NaN, y: Infinity }));'
python3 -c 'import json; print("python keeps id: ", json.loads("{\"id\": 9007199254740993}")["id"])'
```

```text output
id after parse:   9007199254740992
max safe integer: 9007199254740991
0.1 + 0.2 =       0.30000000000000004
NaN becomes:      {"x":null,"y":null}
python keeps id:  9007199254740993
```

Line by line:

- The JSON contains the ID `9007199254740993`. After `JSON.parse` in JavaScript it becomes `...992`: **the ID changed** without any error. Your app would load the wrong record.
- `Number.MAX_SAFE_INTEGER` shows the largest integer JavaScript stores exactly.
- `0.1 + 0.2` is not exactly `0.3` in floating point. That's why money is stored as whole paisa or cents (`1500` = Rs 15.00) or as decimal strings.
- `JSON.stringify` turns `NaN` and `Infinity` into `null`, because JSON has no way to write them. Data is silently lost.
- Python's `json` module uses arbitrary-size integers, so it keeps the exact ID. The **same JSON** can produce different values in different languages, which is why big IDs are safest as strings.

### 7. JSON in JavaScript: `parse` and `stringify`

<Explain>
<What>
`JSON.parse(text)` turns text into values; `JSON.stringify(value, null, 2)` turns values into text, optionally pretty-printed.
</What>
<Why>
Every front-end and Node.js program uses these to talk to APIs, store data in `localStorage`, and read config files.
</Why>
<When>
Receiving and sending API data, saving and loading files.
</When>
<Where>
`fetch(...).then(r => r.json())` calls `JSON.parse` for you; `fetch(url, { body: JSON.stringify(data) })` sends JSON.
</Where>
<How>
Know what `stringify` changes: `Date` objects become ISO strings, `undefined` and functions are **dropped**, and `Map`/`Set` become `{}`. `JSON.parse` throws an exception on invalid text, so wrap it in `try/catch`.
</How>
</Explain>

```bash
node -e '
const profile = {
  name: "Moiz",
  joined: new Date("2026-01-15T09:30:00Z"),
  nickname: undefined,
  greet() { return "hi"; },
  skills: new Set(["git", "linux"])
};
console.log(JSON.stringify(profile, null, 2));
try {
  JSON.parse("{bad json}");
} catch (err) {
  console.log("parse failed:", err.name);
}'
```

```text output
{
  "name": "Moiz",
  "joined": "2026-01-15T09:30:00.000Z",
  "skills": {}
}
parse failed: SyntaxError
```

Line by line:

- `JSON.stringify(profile, null, 2)`: the second argument (`null`) means "no filter", and `2` means "indent with 2 spaces".
- `joined` was a `Date` object and became an ISO 8601 **string**. When you parse it back, you get a string, not a Date. You must convert it yourself (`new Date(value)`).
- `nickname` (undefined) and `greet` (a function) **disappeared** completely.
- `skills` was a `Set` and became `{}`, so the data was lost. Convert it first: `[...profile.skills]`.
- `JSON.parse("{bad json}")` throws a `SyntaxError`. The `try/catch` handles it instead of crashing the program. Always do this with data from outside your program.

### 8. JSON in Python

<Explain>
<What>
Python's built-in `json` module: `json.loads(text)` / `json.dumps(obj)` for strings, `json.load(file)` / `json.dump(obj, file)` for files.
</What>
<Why>
Python is everywhere in DevOps, data and security scripts, and nearly all of them read or write JSON.
</Why>
<When>
Calling APIs (`requests` has `response.json()`), processing tool output, writing reports.
</When>
<Where>
JSON maps to Python like this: object ↔ `dict`, array ↔ `list`, string ↔ `str`, number ↔ `int`/`float`, `true`/`false` ↔ `True`/`False`, `null` ↔ `None`.
</Where>
<How>
Use `ensure_ascii=False` to keep Urdu and other non-English text readable, `indent=2` for pretty output, and `sort_keys=True` for stable output.
</How>
</Explain>

```bash
cat > report.py <<'EOF'
import json

with open("order.json", encoding="utf-8") as f:
    order = json.load(f)

print(type(order).__name__, type(order["items"]).__name__, order["couponCode"])

summary = {
    "order": order["orderId"],
    "customer": order["customer"]["name"],
    "total": sum(i["price"] * i["qty"] for i in order["items"]),
    "status": "تیار",
    "paid": True,
}
print(json.dumps(summary, ensure_ascii=False, sort_keys=True))
print(json.dumps({"status": "تیار"}))
EOF
python3 report.py
```

```text output
dict list None
{"customer": "Ayesha Khan", "order": 1042, "paid": true, "status": "تیار", "total": 3800}
{"status": "\u062a\u06cc\u0627\u0631"}
```

Line by line:

- `json.load(f)` parses the file from concept 3 into Python data.
- The top-level object became a `dict`, the `items` array a `list`, and `null` became `None`.
- We build a new `dict` with a computed total, an Urdu status ("ready") and a Python `True`.
- `json.dumps(..., ensure_ascii=False, sort_keys=True)` gives JSON text with keys in alphabetical order, the Urdu text readable, and `True` written as JSON `true`.
- Without `ensure_ascii=False` (last line), Python escapes every non-ASCII character as `\uXXXX`. It's still valid JSON with the same meaning, just unreadable for humans.

### 9. JSON over HTTP: APIs

<Explain>
<What>
REST APIs send JSON in HTTP request and response **bodies**, labelled with the header `Content-Type: application/json`.
</What>
<Why>
The header tells the other side how to parse the body. Servers often reject a JSON body sent without it.
</Why>
<When>
Every time a front end, mobile app or script calls a backend.
</When>
<Where>
Browser DevTools → Network tab → a request → **Response** / **Payload**; or `curl` in the terminal (see **HTTP and HTTPS in Depth**).
</Where>
<How>
To send: set `Content-Type: application/json` and a JSON body. To receive: check the status code first, then parse the body.
</How>
</Explain>

A typical exchange (shown, not run, because it needs a live server):

```text
POST /api/orders HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Authorization: Bearer <token>

{"items": [{"sku": "MUG-01", "qty": 1}], "couponCode": null}

HTTP/1.1 201 Created
Content-Type: application/json

{"orderId": 1043, "status": "pending", "total": 800}
```

```text
curl -s -X POST https://shop.example.com/api/orders \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"items": [{"sku": "MUG-01", "qty": 1}]}'
```

And from JavaScript:

```js
const res = await fetch("/api/orders", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ items: [{ sku: "MUG-01", qty: 1 }] }),
});
if (!res.ok) throw new Error(`Request failed: ${res.status}`);
const order = await res.json();   // parses the JSON body
console.log(order.orderId);
```

Errors are usually JSON too, often in a standard shape (RFC 9457 "problem details"): `{"type": "...", "title": "Invalid coupon", "status": 400, "detail": "Coupon EID50 has expired"}`.

### 10. JSON in the terminal with `jq`

<Explain>
<What>
`jq` is a command-line tool to pretty-print, filter and transform JSON.
</What>
<Why>
DevOps and security work involves a lot of JSON output (cloud CLIs, `kubectl`, scanners), and `jq` turns it into exactly the answer you need.
</Why>
<When>
Reading API responses, scripting with cloud CLIs, processing logs.
</When>
<Where>
Covered in depth in **Working with JSON Using jq** (Shell Scripting module). Here is a quick taste.
</Where>
<How>
`jq '.path'` selects, `[]` loops over arrays, `select()` filters, and `-r` prints raw strings without quotes.
</How>
</Explain>

```bash
jq -r '.customer.name' order.json
jq -r '.items[] | "\(.sku): \(.price * .qty)"' order.json
jq '[.items[] | select(.price > 1000) | .sku]' order.json
jq -c '{id: .orderId, items: (.items | length)}' order.json
```

```text output
Ayesha Khan
TSHIRT-M: 3000
MUG-01: 800
[
  "TSHIRT-M"
]
{"id":1042,"items":2}
```

Line by line:

- `.customer.name` follows the path; `-r` prints `Ayesha Khan` without quotes.
- `.items[]` outputs each item separately, and the string `"\(.sku): \(.price * .qty)"` builds a line per item (`\( )` inserts a value).
- `select(.price > 1000)` keeps only expensive items, and wrapping it in `[ ]` collects the results into an array.
- `{id: .orderId, items: (.items | length)}` builds a new object; `-c` prints it compactly on one line.

### 11. JSON Lines: one JSON object per line

<Explain>
<What>
**JSON Lines** (also called NDJSON, `.jsonl`) is a file where **each line is a complete JSON object**. The file as a whole is not one JSON document.
</What>
<Why>
You can append a line at any time and read huge files line by line, without loading everything into memory. That's perfect for logs and data streams.
</Why>
<When>
Application logs, event streams, big data exports, machine-learning datasets.
</When>
<Where>
Structured logging libraries (pino for Node, structlog for Python), Docker's JSON log driver, cloud log exports, `jq` (which reads line by line naturally).
</Where>
<How>
Never pretty-print JSON Lines: one object must stay on one line.
</How>
</Explain>

```bash
cat > app.log.jsonl <<'EOF'
{"time": "2026-11-10T10:00:01Z", "level": "info", "msg": "server started", "port": 3000}
{"time": "2026-11-10T10:02:13Z", "level": "error", "msg": "payment failed", "orderId": 1042, "code": "CARD_DECLINED"}
{"time": "2026-11-10T10:02:40Z", "level": "info", "msg": "order created", "orderId": 1043}
{"time": "2026-11-10T10:05:09Z", "level": "error", "msg": "payment failed", "orderId": 1044, "code": "TIMEOUT"}
EOF
echo "errors:"; jq -r 'select(.level == "error") | "  \(.time)  order \(.orderId)  \(.code)"' app.log.jsonl
echo "count by level:"; jq -s -r 'group_by(.level)[] | "  \(.[0].level): \(length)"' app.log.jsonl
```

```text output
errors:
  2026-11-10T10:02:13Z  order 1042  CARD_DECLINED
  2026-11-10T10:05:09Z  order 1044  TIMEOUT
count by level:
  error: 2
  info: 2
```

Line by line:

- Each line of `app.log.jsonl` is a separate log event with fields like `level` and `orderId`. Compare that with a plain text log like `ERROR payment failed for 1042`, where you'd need fragile `grep`/`awk` to extract the order number.
- `select(.level == "error")` keeps only error events, and the template prints the fields we care about.
- `-s` ("slurp") reads **all** lines into one array first, `group_by(.level)` groups them, and `length` counts each group.

### 12. Validating JSON with JSON Schema

<Explain>
<What>
**JSON Schema** is a JSON document that describes what valid data looks like: required fields, types, allowed values, string formats, number ranges.
</What>
<Why>
Valid **syntax** isn't enough. `{"qty": -5}` is perfectly valid JSON but nonsense data. Checking input against a schema rejects bad or malicious data before your code touches it.
</Why>
<When>
API request bodies, config files, messages between services.
</When>
<Where>
Libraries: `ajv` (JavaScript), `jsonschema` (Python), and Zod or Pydantic for schemas written in code. OpenAPI specifications use JSON Schema to describe API bodies. VS Code uses schemas to autocomplete `package.json`.
</Where>
<How>
Write the schema once, validate every incoming document, and return a clear 400 error listing what's wrong.
</How>
</Explain>

```bash
cat > order.schema.json <<'EOF'
{
  "type": "object",
  "required": ["orderId", "items"],
  "properties": {
    "orderId": { "type": "integer", "minimum": 1 },
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["sku", "qty"],
        "properties": {
          "sku": { "type": "string", "pattern": "^[A-Z0-9-]+$" },
          "qty": { "type": "integer", "minimum": 1, "maximum": 100 }
        },
        "additionalProperties": false
      }
    }
  }
}
EOF
cat > validate.py <<'EOF'
import json, sys
from jsonschema import Draft202012Validator

schema = json.load(open("order.schema.json"))
validator = Draft202012Validator(schema)
for text in sys.argv[1:]:
    errors = sorted(validator.iter_errors(json.loads(text)), key=lambda e: list(e.path))
    if not errors:
        print("VALID  ", text)
    for e in errors:
        path = "/".join(str(p) for p in e.path) or "(root)"
        print("INVALID", path, "→", e.message)
EOF
python3 validate.py \
  '{"orderId": 7, "items": [{"sku": "MUG-01", "qty": 2}]}' \
  '{"orderId": 7, "items": [{"sku": "mug 01", "qty": -5, "price": 0}]}' \
  '{"items": []}'
```

```text output
VALID   {"orderId": 7, "items": [{"sku": "MUG-01", "qty": 2}]}
INVALID items/0 → Additional properties are not allowed ('price' was unexpected)
INVALID items/0/qty → -5 is less than the minimum of 1
INVALID items/0/sku → 'mug 01' does not match '^[A-Z0-9-]+$'
INVALID (root) → 'orderId' is a required property
INVALID items → [] should be non-empty
```

Line by line:

- The schema says: the document is an object; `orderId` and `items` are **required**; `orderId` is an integer ≥ 1; `items` is a non-empty array; each item needs `sku` (uppercase letters, digits and dashes only) and `qty` (integer 1–100); and `additionalProperties: false` forbids any other fields in an item.
- `validate.py` uses the `jsonschema` library (`pip install jsonschema`). `iter_errors` returns **all** problems, not just the first, and we print the path to each bad value.
- The first document is valid.
- The second has three problems in item 0. Notice `"price": 0` is rejected as an unexpected field: a client should never get to choose the price. The server looks it up.
- The third is missing `orderId` and has an empty `items` list. Within each document, errors are sorted by their path.

### 13. Security: parse safely

<Explain>
<What>
JSON from users, other services or files is **untrusted input**. The main dangers: unsafe parsing, unexpected fields or types, duplicate keys, very large or deeply nested documents, and **prototype pollution** in JavaScript.
</What>
<Why>
Attackers send crafted JSON to change prices, become admin, crash servers or run code.
</Why>
<When>
Every API endpoint, webhook and file upload that accepts JSON.
</When>
<Where>
Use only real JSON parsers (`JSON.parse`, `json.loads`). **Never** use `eval()`. Validate with a schema, limit the body size (e.g. Express `express.json({ limit: "100kb" })`), and copy only the fields you expect.
</Where>
<How>
The demo below shows two surprises: duplicate keys and prototype pollution through a naive "merge" function.
</How>
</Explain>

```bash
node -e '
const dup = JSON.parse(`{"role": "user", "role": "admin"}`);
console.log("duplicate keys, last one wins:", dup.role);

function naiveMerge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object" && source[key] !== null) {
      target[key] = target[key] || {};
      naiveMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}
const attackerBody = JSON.parse(`{"theme": "dark", "__proto__": {"isAdmin": true}}`);
naiveMerge({}, attackerBody);
const freshUser = {};
console.log("brand-new object isAdmin:", freshUser.isAdmin);'
```

```text output
duplicate keys, last one wins: admin
brand-new object isAdmin: true
```

Line by line:

- **Duplicate keys:** the JSON standard says keys *should* be unique but doesn't forbid duplicates. Most parsers keep the **last** value. If a security check (e.g. a WAF or a validation library) reads the **first** `role` and your app reads the last, an attacker can slip `"admin"` past the check.
- **Prototype pollution:** `naiveMerge` copies every key from the user's settings into an object, a very common pattern for "update my settings". The attacker includes the key `__proto__`.
- When `naiveMerge` reaches `target["__proto__"]`, it gets the shared **prototype of all objects** (`Object.prototype`) and writes `isAdmin = true` onto it.
- Now **every** object in the program, including a brand-new empty `{}`, has `isAdmin === true`. If the app checks `if (user.isAdmin)`, the attacker is now an admin everywhere.
- Defences: skip the keys `__proto__`, `constructor` and `prototype` when merging; use `Object.create(null)` or `Map`; use well-maintained libraries; validate input with a schema that has `additionalProperties: false`; or freeze the prototype with `Object.freeze(Object.prototype)`.

## Hands-on

Turn raw API data into a clean report, validating it first, in one pipeline of small steps:

```bash
cat > users.json <<'EOF'
[
  {"id": 1, "name": "Ali Raza", "city": "Lahore", "active": true, "orders": [1500, 800]},
  {"id": 2, "name": "Sara Ahmed", "city": "Karachi", "active": false, "orders": []},
  {"id": 3, "name": "Bilal Khan", "city": "Lahore", "active": true, "orders": [3200]},
  {"id": 4, "name": "Hina Malik", "city": "Islamabad", "active": true, "orders": [600, 900, 450]}
]
EOF
python3 -m json.tool users.json >/dev/null && echo "1) users.json is valid JSON"
echo "2) active users and total spend:"
jq -r '.[] | select(.active) | "   \(.name) (\(.city)): Rs \(.orders | add // 0)"' users.json
echo "3) users per city:"
jq -r 'group_by(.city)[] | "   \(.[0].city): \(length)"' users.json
node -e '
const users = JSON.parse(require("fs").readFileSync("users.json", "utf8"));
const report = {
  generatedAt: "2026-11-10",
  activeUsers: users.filter(u => u.active).length,
  revenue: users.flatMap(u => u.orders).reduce((a, b) => a + b, 0),
  topCustomer: users.map(u => ({ name: u.name, spent: u.orders.reduce((a, b) => a + b, 0) }))
                    .sort((a, b) => b.spent - a.spent)[0].name
};
require("fs").writeFileSync("report.json", JSON.stringify(report, null, 2) + "\n");'
echo "4) report.json:"; cat report.json
```

```text output
1) users.json is valid JSON
2) active users and total spend:
   Ali Raza (Lahore): Rs 2300
   Bilal Khan (Lahore): Rs 3200
   Hina Malik (Islamabad): Rs 1950
3) users per city:
   Islamabad: 1
   Karachi: 1
   Lahore: 2
4) report.json:
{
  "generatedAt": "2026-11-10",
  "activeUsers": 3,
  "revenue": 7450,
  "topCustomer": "Bilal Khan"
}
```

Line by line:

- `users.json` is an **array** of user objects, each with a nested `orders` array of amounts.
- Step 1 validates the syntax before anything else.
- Step 2: `.[]` loops over users, `select(.active)` keeps active ones, and `.orders | add // 0` sums the orders (`add` of an empty array is `null`, and `// 0` replaces it with 0).
- Step 3: `group_by(.city)` makes one group per city (sorted alphabetically), and `length` counts each group.
- Step 4 (Node): reads the file, counts active users, flattens all orders into one list to get total revenue, finds the top customer by sorting by amount spent, and writes `report.json` pretty-printed with 2-space indentation and a final newline (good practice for files in Git).

## Real-world example

Moiz's trading platform receives webhooks from a payment provider: JSON bodies like `{"event": "payment.succeeded", "orderId": "1042", "amount": 150000, "currency": "PKR"}`. The backend:

1. checks the request's **signature header** so only the real provider can send events (see **Digital Signatures** in Cryptography Basics),
2. limits the body to 100 KB and parses it with `JSON.parse` inside `try/catch`,
3. validates it against a JSON Schema: `amount` is an integer in paisa (150000 = Rs 1,500.00), `orderId` is a **string** (so big IDs stay exact), and unknown fields are rejected,
4. looks up the order and compares the amount with the stored price, never trusting the amount alone,
5. logs the event as one JSON line (`{"level":"info","msg":"payment.succeeded","orderId":"1042"}`) so it can be searched in the log system.

When a bug report says "order 1042 was marked paid twice", an engineer runs `jq 'select(.orderId == "1042")'` over the JSON logs and sees two identical webhook deliveries, so the team makes the handler **idempotent** (it ignores an event ID it has already processed).

## Common mistakes

- **Trailing commas, single quotes, comments** in `.json` files, which break builds and deployments.
- **Building JSON with string concatenation** instead of `JSON.stringify` / `json.dumps`.
- **Numbers for IDs and phone numbers:** leading zeros lost, big IDs corrupted in JavaScript.
- **Floats for money:** `0.1 + 0.2 !== 0.3`. Use integers of the smallest unit or decimal strings.
- **Forgetting `Content-Type: application/json`** when sending JSON to an API.
- **Not handling `JSON.parse` errors,** so one bad request crashes the server.
- **Expecting `Date`s back after parsing:** they come back as strings.
- **Assuming key order matters:** objects are unordered; use an array if order matters.
- **Pretty-printing JSON Lines,** which breaks the one-object-per-line rule.
- **Trusting fields from the client** such as `price`, `role` or `isAdmin`.

## Security lens

<Callout type="security">
Valid JSON is not safe JSON. Parse with a real parser, validate against a schema, and only use the fields you expect.
</Callout>

- **Never `eval()` JSON.** `JSON.parse` only reads data; `eval` runs code.
- **Mass assignment:** don't do `User.update(req.body)`. Pick allowed fields explicitly, or attackers add `"role": "admin"`.
- **Prototype pollution** (JavaScript): block `__proto__`, `constructor` and `prototype` keys; keep libraries like lodash updated.
- **Denial of service:** limit request body size and nesting depth. Huge or deeply nested JSON can exhaust memory or CPU.
- **Duplicate keys and parser differences:** reject documents with duplicate keys where security depends on them.
- **Big numbers:** precision loss can make security checks compare the wrong IDs or amounts.
- **Don't leak data in responses:** return only the fields the client needs (no password hashes, internal IDs or stack traces in error JSON).
- **Escape JSON inside HTML:** putting JSON into a `<script>` tag needs proper escaping (`<` as `\u003c`), or an attacker's string containing `</script>` can break out and run code (XSS).

## Interview questions

<QA q="What data types does JSON support?">
JSON supports six types: strings in double quotes, numbers, the booleans true and false, null, objects as unordered collections of string keys and values, and arrays as ordered lists of values. There are no native types for dates, binary data, undefined, NaN or Infinity, so dates are typically ISO 8601 strings and binary data Base64-encoded strings.
</QA>

<QA q="What is the difference between JSON and a JavaScript object?">
JSON is a text format, while a JavaScript object is an in-memory data structure. JSON requires double-quoted keys and strings, does not allow trailing commas, comments, functions, undefined or special numbers, and must be parsed with JSON.parse to become an object or produced with JSON.stringify from one.
</QA>

<QA q="Why might a large numeric ID change after being parsed in JavaScript, and how do you avoid it?">
JavaScript represents numbers as 64-bit floating point values, which can only represent integers exactly up to 2 to the power 53 minus 1. Larger integers are rounded silently during parsing. APIs avoid this by sending such IDs as strings, or clients can use BigInt-aware parsers.
</QA>

<QA q="What is JSON Lines and when would you use it?">
JSON Lines is a format where each line of a file is a separate, complete JSON value, usually an object. It allows appending records and streaming or processing very large files line by line, which makes it well suited to structured logs, event streams and data exports.
</QA>

<QA q="How do you safely handle JSON received from clients?">
Limit the request size, parse it with a real JSON parser inside error handling, validate it against a schema that defines required fields, types, ranges and disallows unexpected properties, copy only expected fields instead of mass-assigning the body, protect against prototype pollution in JavaScript, and never trust security-relevant values such as prices or roles from the client.
</QA>
