<Callout type="tip" title="In one minute">
**XML** (eXtensible Markup Language) stores structured data as a **tree of elements** written with **tags**: `<price currency="PKR">1500</price>`. An element has a **start tag**, an **end tag**, optional **attributes** (`currency="PKR"`), and content: text, other elements, or both. Every document has exactly **one root element**, tags must be **properly nested and closed**, and names are **case-sensitive**. A document following these rules is **well-formed**; one that also matches a **schema (XSD)** is **valid**. Special characters are escaped as `&lt;` `&gt;` `&amp;` `&quot;` `&apos;`. XML is older and wordier than JSON, but it's still everywhere in enterprise, finance, government, documents and identity systems (SAML). Its biggest risk is **XXE**: a parser that resolves external entities can be tricked into reading server files. Use safe parsers.
</Callout>

## Start from zero

<Callout type="analogy">
Think of XML as a set of **labelled boxes inside labelled boxes**, like moving house. A big box says **"Kitchen"**. Inside it are smaller boxes: **"Plates"**, **"Cups"**. Each box has a label on top (the start tag) and you seal it at the end (the end tag). A sticker on the box can add extra facts: "fragile = yes" (an **attribute**). Anyone can open the outer box and find exactly what's inside, at any depth. JSON packs the same things more compactly; XML writes the label on **both** ends of every box, which is wordier but very explicit.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Markup** | Tags added around text to describe it | `<b>bold</b>` |
| **Element** | A start tag, its content, and the end tag | `<city>Lahore</city>` |
| **Tag** | The label in angle brackets | `<city>`, `</city>` |
| **Attribute** | A `name="value"` pair inside a start tag | `<price currency="PKR">` |
| **Root element** | The single outermost element | `<order>` |
| **Well-formed** | Follows XML's syntax rules | every tag closed and nested |
| **Valid** | Well-formed **and** matches a schema | checked with an XSD |
| **Entity** | A named shortcut like `&amp;` for `&` | `&lt;`, `&amp;` |
| **Namespace** | A URI that makes element names unique | `xmlns="http://..."` |
| **XPath** | A query language for selecting parts of an XML tree | `//item[@sku="MUG-01"]` |

## What is it?

XML is a W3C standard (1998) for representing structured data as text. It's a cousin of HTML (both come from SGML), but in XML **you define your own tags**, and the rules are much stricter. Here is the same order we used in the JSON lesson, as XML:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<order id="1042">
  <customer vip="true">
    <name>Ayesha Khan</name>
    <email>ayesha@example.com</email>
  </customer>
  <items>
    <item sku="TSHIRT-M" qty="2"><price currency="PKR">1500</price></item>
    <item sku="MUG-01" qty="1"><price currency="PKR">800</price></item>
  </items>
  <notes>Leave at the gate</notes>
</order>
```

```text
order (id=1042)                       ← root element
├── customer (vip=true)
│   ├── name   → "Ayesha Khan"
│   └── email  → "ayesha@example.com"
├── items
│   ├── item (sku=TSHIRT-M, qty=2)
│   │   └── price (currency=PKR) → "1500"
│   └── item (sku=MUG-01, qty=1)
│       └── price (currency=PKR) → "800"
└── notes  → "Leave at the gate"
```

The first line, `<?xml version="1.0" encoding="UTF-8"?>`, is the **XML declaration** (optional, but recommended). It says which version and character encoding the file uses.

## Why does it matter?

You may never **choose** XML for a new API, but you will **meet** it constantly:

- **Enterprise and finance:** SOAP web services, bank and payment-gateway integrations, ISO 20022 payment messages, many government e-invoicing and tax systems.
- **Identity:** **SAML** single sign-on (log in with your company account) sends signed XML between the identity provider and the app.
- **Web:** RSS/Atom feeds, `sitemap.xml` for search engines, **SVG** images, XHTML.
- **Build tools and apps:** Maven `pom.xml`, Android `AndroidManifest.xml` and layouts, .NET `.csproj` and `web.config`, Spring configuration.
- **Documents:** `.docx`, `.xlsx` and `.pptx` files are ZIP archives full of XML.
- **Security:** XXE is one of the classic web vulnerabilities (it had its own place in the OWASP Top 10), and many security tools exchange reports as XML (Nmap `-oX`, JUnit test reports, SARIF's predecessors).

## When and where do you use it?

- **When a system requires it:** a SOAP API, a SAML identity provider, a sitemap, Maven, an Office document.
- **Documents mixing text and markup:** XML handles "text with tags inside" (`<p>Hello <b>world</b></p>`) far better than JSON.
- **Strict contracts:** XSD schemas with types, required elements and namespaces are common in regulated industries.
- **Prefer JSON** for new web APIs and simple data exchange. It's smaller, simpler, and native to JavaScript.

## Concepts one by one

### 1. Elements and the tree

<Explain>
<What>
An **element** is a start tag `<name>`, content, and an end tag `</name>`. Elements nest inside each other to form a **tree** with exactly one **root**.
</What>
<Why>
The tree structure lets you represent any hierarchical data, like JSON objects inside objects.
</Why>
<When>
Every XML document.
</When>
<Where>
Empty elements can be written as `<br></br>` or the short **self-closing** form `<br/>`.
</Where>
<How>
Tag names are **case-sensitive** (`<Name>` ≠ `<name>`), can't start with a digit, and can't contain spaces.
</How>
</Explain>

```bash
cat > order.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<order id="1042">
  <customer vip="true">
    <name>Ayesha Khan</name>
    <email>ayesha@example.com</email>
  </customer>
  <items>
    <item sku="TSHIRT-M" qty="2"><price currency="PKR">1500</price></item>
    <item sku="MUG-01" qty="1"><price currency="PKR">800</price></item>
  </items>
  <giftWrap/>
  <notes>Leave at the gate</notes>
</order>
EOF
python3 - <<'PY'
import xml.etree.ElementTree as ET
root = ET.parse("order.xml").getroot()
print("root element:", root.tag, root.attrib)
def show(element, depth=0):
    text = (element.text or "").strip()
    print("  " * depth + element.tag + (f' = "{text}"' if text else ""))
    for child in element:
        show(child, depth + 1)
show(root)
PY
```

```text output
root element: order {'id': '1042'}
order
  customer
    name = "Ayesha Khan"
    email = "ayesha@example.com"
  items
    item
      price = "1500"
    item
      price = "800"
  giftWrap
  notes = "Leave at the gate"
```

Line by line:

- `xml.etree.ElementTree` (usually imported as `ET`) is Python's built-in XML library. `ET.parse` reads the file, and `getroot()` returns the root element, `order`.
- `root.tag` is the element name; `root.attrib` is a dictionary of its attributes. Attribute values are always **strings**: `'1042'`, not `1042`.
- `show()` walks the tree recursively: it prints the element's name and text, then calls itself for each child with more indentation.
- `element.text` is the text directly inside the element. For containers like `customer` it's only whitespace (new lines and spaces), which `.strip()` removes.
- `<giftWrap/>` is an empty, self-closing element. Its presence can itself carry meaning ("gift wrap requested").

### 2. Attributes vs child elements

<Explain>
<What>
Data can go in **attributes** (`<item sku="MUG-01">`) or in **child elements** (`<item><sku>MUG-01</sku></item>`).
</What>
<Why>
Both work. Conventions help readers and schemas stay consistent.
</Why>
<When>
Common rule of thumb: **attributes for metadata** (IDs, units, types, flags), **elements for the actual data**, especially anything long, structured or repeating.
</When>
<Where>
Attributes can't contain child elements and can't repeat on the same element; elements can.
</Where>
<How>
Attribute values must be **quoted** (single or double quotes) and are always strings. Attribute order has no meaning.
</How>
</Explain>

```bash
python3 - <<'PY'
import xml.etree.ElementTree as ET
root = ET.parse("order.xml").getroot()
total = 0
for item in root.iter("item"):
    sku = item.get("sku")
    qty = int(item.get("qty"))
    price = item.find("price")
    amount = int(price.text) * qty
    total += amount
    print(f"{sku:9} qty={qty}  {price.get('currency')} {amount}")
print("total:", total, "| vip:", root.find("customer").get("vip") == "true")
print("missing attribute:", root.get("discount"), "| with default:", root.get("discount", "0"))
PY
```

```text output
TSHIRT-M  qty=2  PKR 3000
MUG-01    qty=1  PKR 800
total: 3800 | vip: True
missing attribute: None | with default: 0
```

Line by line:

- `root.iter("item")` finds every `<item>` element anywhere below the root.
- `item.get("sku")` reads an attribute; `int(item.get("qty"))` converts the string to a number, because XML has no number type.
- `item.find("price")` finds the first `<price>` **child**, and `.text` is its content (`"1500"`).
- `vip` is the **string** `"true"`, so we compare it with `"true"` to get a real boolean.
- `root.get("discount")` returns `None` if the attribute doesn't exist, and `get(name, default)` provides a fallback.

### 3. Well-formed: the strict rules

<Explain>
<What>
A document is **well-formed** if it follows XML's syntax rules. If not, a conforming parser must **stop with an error**: it may not guess like a web browser does with HTML.
</What>
<Why>
That strictness makes XML predictable across every language and tool.
</Why>
<When>
Editing XML by hand (`pom.xml`, `web.config`, Android layouts).
</When>
<Where>
Check with `xmllint --noout file.xml` (from libxml2; on Ubuntu, `sudo apt install libxml2-utils`) or your editor.
</Where>
<How>
The rules: exactly one root element; every element closed; tags properly **nested** (no overlapping); matching case in start and end tags; attribute values quoted; no duplicate attributes on one element; `<` and `&` escaped in text.
</How>
</Explain>

```bash
check() { printf '%s' "$2" | xmllint --noout - 2>err.txt && echo "$1: well-formed" || echo "$1: $(head -1 err.txt | sed 's/^-:[0-9]*: parser error : //')"; }
check "good            " '<order><id>1</id></order>'
check "not closed      " '<order><id>1</id>'
check "bad nesting     " '<b><i>text</b></i>'
check "case mismatch   " '<Name>Ali</name>'
check "unquoted attr   " '<item qty=2/>'
check "two roots       " '<a/><b/>'
check "raw ampersand   " '<company>Smith & Sons</company>'
```

```text output
good            : well-formed
not closed      : Premature end of data in tag order line 1
bad nesting     : Opening and ending tag mismatch: i line 1 and b
case mismatch   : Opening and ending tag mismatch: Name line 1 and name
unquoted attr   : AttValue: " or ' expected
two roots       : Extra content at the end of the document
raw ampersand   : xmlParseEntityRef: no name
```

Line by line:

- `check` sends the XML text to `xmllint --noout -` (`-` means "read from standard input", `--noout` means "don't print the document, only errors") and prints the first error line without the `-:1: parser error :` prefix.
- **not closed:** `<order>` never gets `</order>`.
- **bad nesting:** `<i>` opens inside `<b>`, so it must close before `</b>`. Overlapping tags are not allowed.
- **case mismatch:** `<Name>` and `</name>` are different names.
- **unquoted attr:** `qty=2` needs quotes: `qty="2"`.
- **two roots:** a document must have one single root element.
- **raw ampersand:** `&` starts an entity reference, so a plain `&` must be written `&amp;`.

### 4. Escaping and CDATA

<Explain>
<What>
Five characters have special meaning and are written as **entities**: `&lt;` (`<`), `&gt;` (`>`), `&amp;` (`&`), `&quot;` (`"`) and `&apos;` (`'`). A **CDATA section** `<![CDATA[ ... ]]>` holds text that isn't parsed at all.
</What>
<Why>
Otherwise text like `a < b` or `Smith & Sons` would break the document.
</Why>
<When>
Any text containing those characters; CDATA for code snippets or HTML inside XML.
</When>
<Where>
`&lt;` and `&amp;` are **always** required in text; `&quot;`/`&apos;` only inside attribute values using that quote. Characters can also be written as numeric references: `&#169;` or `&#xA9;` for ©.
</Where>
<How>
Let the library escape for you when **writing** XML (concept 8). When **reading**, the parser turns entities back into characters automatically.
</How>
</Explain>

```bash
cat > escaped.xml <<'EOF'
<rules>
  <rule>price &lt; 1000 &amp;&amp; qty &gt; 0</rule>
  <company name="Smith &amp; Sons &quot;Ltd&quot;"/>
  <script><![CDATA[ if (a < b && c > d) { alert("hi"); } ]]></script>
  <copyright>&#169; 2026</copyright>
</rules>
EOF
python3 - <<'PY'
import xml.etree.ElementTree as ET
root = ET.parse("escaped.xml").getroot()
print("rule:     ", root.find("rule").text)
print("company:  ", root.find("company").get("name"))
print("script:   ", root.find("script").text.strip())
print("copyright:", root.find("copyright").text)
PY
```

```text output
rule:      price < 1000 && qty > 0
company:   Smith & Sons "Ltd"
script:    if (a < b && c > d) { alert("hi"); }
copyright: © 2026
```

Line by line:

- In the file, the rule is written with `&lt;`, `&amp;&amp;` and `&gt;`; the parser gives back the real characters `<`, `&&` and `>`.
- In the attribute, `&amp;` and `&quot;` become `&` and `"`. Escaping `"` is needed because the attribute value itself is in double quotes.
- Inside `<![CDATA[ ... ]]>`, the code is taken **literally**, with no escaping needed. The only thing CDATA can't contain is `]]>`.
- `&#169;` is a numeric character reference for ©.

### 5. Namespaces

<Explain>
<What>
A **namespace** is a URI (usually a URL that's never actually fetched) attached to element names with `xmlns` or a prefix like `xmlns:pay="..."`. It makes names unique when documents mix vocabularies.
</What>
<Why>
Two standards might both have an element called `<id>` or `<amount>`. Namespaces tell them apart: `pay:amount` vs `tax:amount`.
</Why>
<When>
SOAP, SAML, SVG, Maven, sitemaps, RSS extensions, Office files: almost every real-world XML format.
</When>
<Where>
`xmlns="URI"` sets a **default namespace** for an element and its children; `xmlns:prefix="URI"` defines a prefix used as `prefix:element`.
</Where>
<How>
The **URI** identifies the namespace, not the prefix. Parsers like ElementTree write names as `{URI}localname`, and a search for plain `"url"` finds **nothing**. This is the number-one XML beginner confusion.
</How>
</Explain>

```bash
cat > sitemap.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url><loc>https://devguide.example/</loc><priority>1.0</priority></url>
  <url><loc>https://devguide.example/learn/json</loc><priority>0.8</priority></url>
  <url><loc>https://devguide.example/learn/yaml</loc><priority>0.8</priority></url>
</urlset>
EOF
python3 - <<'PY'
import xml.etree.ElementTree as ET
root = ET.parse("sitemap.xml").getroot()
print("root tag as Python sees it:", root.tag)
print("findall('url') without namespace:", len(root.findall("url")))
ns = {"sm": "http://www.sitemaps.org/schemas/sitemap/0.9"}
urls = root.findall("sm:url", ns)
print("findall('sm:url', ns):", len(urls))
for u in urls:
    print(" ", u.findtext("sm:priority", namespaces=ns), u.findtext("sm:loc", namespaces=ns))
PY
```

```text output
root tag as Python sees it: {http://www.sitemaps.org/schemas/sitemap/0.9}urlset
findall('url') without namespace: 0
findall('sm:url', ns): 3
  1.0 https://devguide.example/
  0.8 https://devguide.example/learn/json
  0.8 https://devguide.example/learn/yaml
```

Line by line:

- The sitemap has a **default namespace** (`xmlns="http://www.sitemaps.org/..."`), so **every** element in it, `urlset`, `url`, `loc` and `priority`, belongs to that namespace even though no prefix is visible.
- Python shows the full name as `{namespace-URI}urlset`.
- `root.findall("url")` returns **0** results: it searches for `url` with **no** namespace, which doesn't exist in this document.
- We define a prefix mapping `ns = {"sm": "..."}` (the prefix `sm` is our own choice; only the URI must match) and search for `sm:url`: all 3 are found.
- `findtext(..., namespaces=ns)` reads child text the same way.

### 6. XPath: querying the tree

<Explain>
<What>
**XPath** is a small query language for selecting nodes in an XML tree, like `jq` for JSON or CSS selectors for HTML.
</What>
<Why>
One line instead of nested loops: "the price of the item whose SKU is MUG-01".
</Why>
<When>
Extracting data, writing tests (Selenium uses XPath for HTML too), XSLT transformations, configuring security tools.
</When>
<Where>
`xmllint --xpath`, Python `lxml` (full XPath 1.0) and, in a limited form, `ElementTree`'s `findall`. Browsers have `document.evaluate`.
</Where>
<How>
`/` = child, `//` = any depth, `@name` = attribute, `[...]` = condition, `text()` = text content, `count()`, `sum()` = functions.
</How>
</Explain>

```bash
xmllint --xpath 'string(/order/customer/name)' order.xml
xmllint --xpath '//item[@sku="MUG-01"]/price/text()' order.xml
xmllint --xpath 'count(//item)' order.xml
xmllint --xpath 'sum(//item/price)' order.xml
xmllint --xpath '//item[price > 1000]/@sku' order.xml
```

```text output
Ayesha Khan
800
2
2300
 sku="TSHIRT-M"
```

Line by line:

- `string(/order/customer/name)`: start at the root `order`, go to child `customer`, then `name`, and return its text.
- `//item[@sku="MUG-01"]/price/text()`: any `item` (at any depth) whose `sku` **attribute** equals `MUG-01`, then its `price` child's text.
- `count(//item)` counts all `item` elements.
- `sum(//item/price)` adds up the price values: 1500 + 800 = 2300. (It sums prices, not price × quantity.)
- `//item[price > 1000]/@sku` selects the `sku` attribute of items whose price is over 1000. xmllint prints the attribute as `sku="..."`.

### 7. Creating XML safely

<Explain>
<What>
Build XML with a library (ElementTree, lxml, `xmlbuilder2` in Node), never by concatenating strings.
</What>
<Why>
The library escapes `<`, `&` and quotes automatically. String concatenation lets user input **change the structure** of the document: **XML injection**.
</Why>
<When>
Generating sitemaps, SOAP requests, feeds, reports and config files.
</When>
<Where>
`ET.Element`, `ET.SubElement`, `element.set(name, value)`, `ET.indent` (pretty print, Python 3.9+), `ET.tostring`.
</Where>
<How>
Below, a customer enters a name designed to inject an extra `<role>` element. The string-built XML is corrupted; the library-built XML stays correct.
</How>
</Explain>

```bash
python3 - <<'PY'
import xml.etree.ElementTree as ET
user_input = 'Ali</name><role>admin</role><name>x'

unsafe = "<user><name>" + user_input + "</name><role>customer</role></user>"
roles = [r.text for r in ET.fromstring(unsafe).iter("role")]
print("string concatenation -> roles:", roles)

user = ET.Element("user")
ET.SubElement(user, "name").text = user_input
ET.SubElement(user, "role").text = "customer"
safe = ET.tostring(user, encoding="unicode")
print("library-built XML:  ", safe)
print("library -> roles:   ", [r.text for r in ET.fromstring(safe).iter("role")])
PY
```

```text output
string concatenation -> roles: ['admin', 'customer']
library-built XML:   <user><name>Ali&lt;/name&gt;&lt;role&gt;admin&lt;/role&gt;&lt;name&gt;x</name><role>customer</role></user>
library -> roles:    ['customer']
```

Line by line:

- `user_input` is what an attacker types in the "name" field. It closes `</name>`, adds `<role>admin</role>`, and opens a new `<name>` so the rest still fits.
- **String concatenation:** the resulting XML is well-formed but has **two** roles, and the first one is `admin`. A system that reads "the first role" now treats this user as an admin.
- **Library-built:** `ET.SubElement(user, "name").text = user_input` stores the input as **text**. `tostring` escapes every `<` and `>`, so the input stays inside `<name>` as harmless characters.
- Parsing the safe XML finds only one role: `customer`.

### 8. Pretty printing and converting to JSON

<Explain>
<What>
XML can be formatted (indented) for reading, and converted to JSON for tools like `jq` or JavaScript front ends.
</What>
<Why>
Machine-generated XML is often one huge line; JSON is easier to work with in modern code.
</Why>
<When>
Debugging SOAP responses, migrating legacy data, building APIs on top of XML systems.
</When>
<Where>
`xmllint --format`, `ET.indent`, and libraries like `xmltodict` (Python) or `fast-xml-parser` (Node) for conversion.
</Where>
<How>
There's **no single standard mapping** from XML to JSON: attributes vs elements, repeated elements (one item or a list?), mixed text and namespaces all need decisions. Write the conversion yourself when the structure matters.
</How>
</Explain>

```bash
echo '<order id="1042"><item sku="MUG-01" qty="1"/><item sku="CAP-02" qty="3"/></order>' > compact.xml
xmllint --format compact.xml
python3 - <<'PY'
import json, xml.etree.ElementTree as ET
root = ET.parse("compact.xml").getroot()
data = {
    "orderId": int(root.get("id")),
    "items": [{"sku": i.get("sku"), "qty": int(i.get("qty"))} for i in root.findall("item")],
}
print(json.dumps(data))
PY
```

```text output
<?xml version="1.0"?>
<order id="1042">
  <item sku="MUG-01" qty="1"/>
  <item sku="CAP-02" qty="3"/>
</order>
{"orderId": 1042, "items": [{"sku": "MUG-01", "qty": 1}, {"sku": "CAP-02", "qty": 3}]}
```

Line by line:

- `xmllint --format` adds the XML declaration and indents the one-line document.
- The Python code builds a JSON structure **explicitly**: `id` becomes an integer `orderId`, and every `<item>` becomes an object in an `items` list with a numeric `qty`.
- Writing the mapping by hand avoids a classic generic-converter bug: an order with **one** item becoming an object instead of a one-element list, which breaks code expecting an array.

### 9. Validation with XSD

<Explain>
<What>
An **XML Schema (XSD)** describes which elements and attributes are allowed, their order, how many times they can appear, and their **types** (integer, decimal, date, patterns). A document that matches is **valid**.
</What>
<Why>
Well-formed only means "correct syntax". A schema catches wrong data: missing fields, text where a number belongs, a negative quantity.
</Why>
<When>
Contracts between organisations: banks, governments, SOAP services (WSDL files contain XSDs), e-invoicing.
</When>
<Where>
`xmllint --schema schema.xsd file.xml`, `lxml.etree.XMLSchema`, Java and .NET built-in validators. Older documents may use a **DTD** instead.
</Where>
<How>
XSD files are themselves XML, in the namespace `http://www.w3.org/2001/XMLSchema` (prefix `xs:`).
</How>
</Explain>

```bash
cat > order.xsd <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="order">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="item" maxOccurs="unbounded">
          <xs:complexType>
            <xs:attribute name="sku" use="required">
              <xs:simpleType>
                <xs:restriction base="xs:string"><xs:pattern value="[A-Z0-9\-]+"/></xs:restriction>
              </xs:simpleType>
            </xs:attribute>
            <xs:attribute name="qty" type="xs:positiveInteger" use="required"/>
          </xs:complexType>
        </xs:element>
      </xs:sequence>
      <xs:attribute name="id" type="xs:positiveInteger" use="required"/>
    </xs:complexType>
  </xs:element>
</xs:schema>
EOF
echo '<order id="7"><item sku="MUG-01" qty="2"/></order>' > good-order.xml
echo '<order id="7"><item sku="mug 01" qty="-2"/><item qty="1"/></order>' > bad-order.xml
xmllint --noout --schema order.xsd good-order.xml
xmllint --noout --schema order.xsd bad-order.xml 2>&1 | sed -E "s/^bad-order.xml:1: element item: Schemas validity error : //"
```

```text output
good-order.xml validates
Element 'item', attribute 'sku': [facet 'pattern'] The value 'mug 01' is not accepted by the pattern '[A-Z0-9\-]+'.
Element 'item', attribute 'qty': '-2' is not a valid value of the atomic type 'xs:positiveInteger'.
Element 'item': The attribute 'sku' is required but missing.
bad-order.xml fails to validate
```

Line by line:

- The schema says: the root is `order` with a required positive-integer `id`; it contains one or more (`maxOccurs="unbounded"`) `item` elements; each item **requires** a `sku` matching the pattern (uppercase letters, digits, dashes) and a positive-integer `qty`.
- `good-order.xml validates`: correct.
- The bad file has three problems, and the validator reports all of them: `mug 01` breaks the pattern, `-2` is not a positive integer, and the second item has no `sku`. (The `sed` only shortens the long message prefix.)
- Note that `bad-order.xml` is perfectly **well-formed**. Only the schema catches that the data is wrong.

### 10. XML vs JSON

| | XML | JSON |
| --- | --- | --- |
| Structure | Tree of elements + attributes | Objects + arrays |
| Types | Everything is text (types only via schema) | string, number, boolean, null built in |
| Size | Larger (every tag written twice) | Smaller |
| Comments | Yes, written as `<!-- comment -->` | No |
| Mixed content (text with tags inside) | Excellent | Awkward |
| Namespaces | Yes | No |
| Schema | XSD, DTD, RELAX NG (mature) | JSON Schema |
| Signatures/encryption standards | XML Signature, XML Encryption (used by SAML) | JWS/JWE (used by JWT) |
| Typical use today | Enterprise, finance, SAML, documents, SVG, sitemaps, build files | Web/mobile APIs, configs, logs |

### 11. Security: XXE, billion laughs, and friends

<Explain>
<What>
XML allows a **DOCTYPE** that defines **entities**. An **external entity** (`SYSTEM "file:///etc/passwd"`) tells the parser to **load a file or URL** and insert its content. If an app parses attacker-supplied XML with entity resolution enabled, the attacker can read server files or make the server call internal URLs (SSRF). This is **XXE (XML External Entity)** injection.
</What>
<Why>
XXE has leaked passwords, cloud credentials and source code from many real companies. Nested internal entities ("billion laughs") can also exhaust memory and crash the server.
</Why>
<When>
Any feature that accepts XML from outside: SOAP endpoints, file uploads (`.docx`, `.svg`, `.xlsx`, which are XML inside), SAML responses, RSS imports, sitemap processors.
</When>
<Where>
Use safe defaults: Python's `defusedxml`, modern `lxml` (no external entities by default), and in Java/.NET **disable DTDs** explicitly (`disallow-doctype-decl`), because older defaults were unsafe.
</Where>
<How>
Below, the same malicious upload is parsed three ways. Only a parser configured to resolve entities leaks the secret.
</How>
</Explain>

```bash
echo "DB_PASSWORD=topsecret" > secret.txt
cat > upload.xml <<EOF
<?xml version="1.0"?>
<!DOCTYPE order [ <!ENTITY xxe SYSTEM "file://$PWD/secret.txt"> ]>
<order><note>&xxe;</note></order>
EOF
python3 - <<'PY'
from lxml import etree
vulnerable = etree.XMLParser(resolve_entities=True, no_network=True)
leaked = etree.parse("upload.xml", vulnerable).getroot().findtext("note")
print("VULNERABLE parser returned:", repr(leaked))

try:
    etree.parse("upload.xml")
except etree.XMLSyntaxError as err:
    print("lxml default:", str(err).split(",")[0])

import defusedxml.ElementTree as SafeET
try:
    SafeET.parse("upload.xml")
except Exception as err:
    print("defusedxml:  ", type(err).__name__, "- refused entity", repr(err.name))
PY
```

```text output
VULNERABLE parser returned: 'DB_PASSWORD=topsecret\n'
lxml default: Entity 'xxe' not defined
defusedxml:   EntitiesForbidden - refused entity 'xxe'
```

Line by line:

- `secret.txt` stands in for a sensitive server file such as `/etc/passwd`, an `.env` file, or cloud credentials.
- The uploaded XML defines an entity `xxe` whose value is **the content of that file**, then uses `&xxe;` inside `<note>`. (The here-document is unquoted, so `$PWD` becomes the real folder path.)
- **Vulnerable parser** (`resolve_entities=True`): it reads the file and puts the secret into `note`. If the app then shows or returns the note ("Your order note: …"), the attacker sees the secret.
- **lxml's default** (version 5 and newer) doesn't load external entities, so `&xxe;` stays undefined and parsing fails safely.
- **defusedxml** detects the entity declaration and refuses the document with a clear `EntitiesForbidden` error. It's the recommended choice for parsing untrusted XML in Python.

The "billion laughs" attack (don't run it on a shared machine):

```xml
<!DOCTYPE lolz [
  <!ENTITY lol "lol">
  <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
  <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
  <!-- ... up to lol9 ... -->
]>
<lolz>&lol9;</lolz>
```

Each level repeats the previous one ten times, so a file under 1 KB expands to 10⁹ copies of "lol", about 3 GB in memory. Modern parsers limit entity expansion; defusedxml refuses it outright.

## Hands-on

Read an RSS feed (the format behind blog and podcast subscriptions), list the newest posts, and export them as JSON, using a safe parser:

```bash
cat > feed.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<rss version="2.0" xmlns:dc="http://purl.org/dc/elements/1.1/">
  <channel>
    <title>DevGuide Blog</title>
    <link>https://devguide.example/blog</link>
    <item>
      <title>JSON vs YAML: which one when?</title>
      <link>https://devguide.example/blog/json-vs-yaml</link>
      <pubDate>Mon, 09 Nov 2026 10:00:00 +0500</pubDate>
      <dc:creator>Moiz Rehman</dc:creator>
      <category>Data Formats</category>
    </item>
    <item>
      <title>Signing your Git commits</title>
      <link>https://devguide.example/blog/signing-commits</link>
      <pubDate>Fri, 06 Nov 2026 09:00:00 +0500</pubDate>
      <dc:creator>Sara Ahmed</dc:creator>
      <category>Git &amp; GitHub</category>
    </item>
  </channel>
</rss>
EOF
xmllint --noout feed.xml && echo "1) feed.xml is well-formed"
echo "2) feed title: $(xmllint --xpath 'string(/rss/channel/title)' feed.xml)"
python3 - <<'PY'
import json
from email.utils import parsedate_to_datetime
import defusedxml.ElementTree as ET

NS = {"dc": "http://purl.org/dc/elements/1.1/"}
channel = ET.parse("feed.xml").getroot().find("channel")
posts = []
for item in channel.findall("item"):
    posts.append({
        "title": item.findtext("title"),
        "url": item.findtext("link"),
        "author": item.findtext("dc:creator", namespaces=NS),
        "category": item.findtext("category"),
        "published": parsedate_to_datetime(item.findtext("pubDate")).date().isoformat(),
    })
print("3) posts:")
for p in posts:
    print(f"   {p['published']}  {p['title']}  ({p['author']}, {p['category']})")
with open("posts.json", "w") as f:
    json.dump(posts, f, indent=2)
print("4) wrote posts.json with", len(posts), "posts")
PY
```

```text output
1) feed.xml is well-formed
2) feed title: DevGuide Blog
3) posts:
   2026-11-09  JSON vs YAML: which one when?  (Moiz Rehman, Data Formats)
   2026-11-06  Signing your Git commits  (Sara Ahmed, Git & GitHub)
4) wrote posts.json with 2 posts
```

Line by line:

- The RSS file has the standard structure: `rss` → `channel` → several `item`s. It also uses the Dublin Core namespace (`dc:creator`) for the author, which is very common in real feeds.
- Step 1 checks well-formedness with `xmllint`. Step 2 reads the channel title with XPath.
- The Python part uses **`defusedxml.ElementTree`** (the same API as `ElementTree`, but safe against XXE and entity bombs), which is right for feeds fetched from the internet.
- `findtext("dc:creator", namespaces=NS)` needs the namespace mapping, because `creator` is in the `dc` namespace. The other elements have no namespace, so plain names work.
- `Git &amp; GitHub` comes out as `Git & GitHub`: the parser un-escapes automatically.
- RSS dates use the email date format (`Mon, 09 Nov 2026 10:00:00 +0500`); `parsedate_to_datetime` parses it, and `.date().isoformat()` gives `2026-11-09`.
- Finally, the posts are saved as JSON, ready for a front end or for `jq`.

## Real-world example

A company's HR portal lets employees upload their CV as a `.docx` file and extracts their name and skills. A security tester creates a `.docx` (a ZIP of XML files), edits `word/document.xml` to add a DOCTYPE with an external entity pointing to `file:///etc/hostname`, and then to the cloud metadata URL `http://169.254.169.254/latest/meta-data/iam/security-credentials/`. Because the backend used an old Java XML parser with default settings, the extracted "name" field showed the server's hostname, and then **temporary cloud credentials**. The fix: disable DTDs in the parser (`factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)`), upgrade the library, block the metadata endpoint for that service (IMDSv2 on AWS), add XXE test cases to the security test suite, and rotate the exposed credentials.

## Common mistakes

- **Unescaped `&` or `<`** in text (`Smith & Sons`, `a < b`).
- **Forgetting namespaces** when searching: `findall("url")` returns nothing in a namespaced document.
- **Treating attribute values as numbers or booleans** without converting them (`"false"` is a non-empty string, so it's truthy).
- **Building XML by string concatenation:** broken documents and XML injection.
- **Using generic XML→JSON converters** and getting an object instead of a list when there's only one item.
- **Parsing untrusted XML with entity resolution or DTDs enabled** (XXE, billion laughs).
- **Confusing well-formed with valid:** syntax checks don't catch wrong data.
- **Ignoring encoding:** declaring `UTF-8` while saving the file in another encoding, which corrupts non-English text.

## Security lens

<Callout type="security">
Any XML from outside your system, including files that don't look like XML (.docx, .xlsx, .svg), must be parsed with DTDs and external entities disabled.
</Callout>

- **XXE:** disable DTD processing and external entities; use defusedxml (Python), and set secure features explicitly in Java (`DocumentBuilderFactory`, `SAXParserFactory`) and .NET (`DtdProcessing.Prohibit`). OWASP's XXE Prevention Cheat Sheet lists the settings per language.
- **SSRF through XXE:** external entities can make the server request internal URLs (cloud metadata, admin panels). Network egress controls limit the damage.
- **Denial of service:** entity expansion (billion laughs), huge or deeply nested documents. Limit size and depth.
- **XML injection:** build documents with libraries, never by concatenation; validate against a schema.
- **XPath injection:** never put user input directly into XPath queries (`//user[name='` + input + `']`). Use parameterised XPath (lxml supports variables) or strict validation.
- **SAML:** signed XML assertions are complex, and bugs like **XML Signature Wrapping** have allowed attackers to log in as other users. Use well-maintained SAML libraries and keep them updated.
- **SVG uploads** can contain JavaScript (`<script>`) and cause stored XSS. Sanitise them, or serve them from a separate domain with a strict Content-Security-Policy.

## Interview questions

<QA q="What is the difference between well-formed and valid XML?">
A well-formed document follows XML's syntax rules: a single root element, properly nested and closed tags, quoted attribute values, matching case and escaped special characters. A valid document is well-formed and also conforms to a schema such as an XSD or DTD, which defines allowed elements, attributes, order, cardinality and data types.
</QA>

<QA q="What is an XXE attack and how do you prevent it?">
XML External Entity injection happens when an application parses attacker-controlled XML with DTD or external entity processing enabled. The attacker defines an entity that refers to a local file or URL, and the parser inserts its content, leaking files or making server-side requests. Prevent it by disabling DTDs and external entity resolution in the parser, using safe libraries such as defusedxml, keeping parsers updated and validating input.
</QA>

<QA q="Why do namespaces matter when parsing XML?">
Namespaces qualify element names with a URI so that vocabularies from different standards do not clash. Parsers treat the namespace as part of the element name, so a query for an element without the correct namespace will not match, which is a common reason searches return no results. You must use a namespace mapping in queries, where the URI and not the prefix identifies the namespace.
</QA>

<QA q="When would you choose XML over JSON?">
When integrating with systems that require it such as SOAP, SAML or e-invoicing standards, for documents with mixed content where text contains markup, when mature schema validation, namespaces or XML signature and encryption standards are needed, and for formats built on XML such as SVG, RSS, sitemaps or Office documents. For new web APIs JSON is usually simpler and smaller.
</QA>
