<BigIdea>
<Tr>
<En>
**XML** (eXtensible Markup Language) stores structured data as a **tree of elements** written with **tags**: `<price currency="USD">25</price>`. An element has a **start tag**, an **end tag**, optional **attributes**, and content (text, other elements, or both). Every document has exactly **one root**, tags must be **properly nested and closed**, and names are **case-sensitive**: a document following these rules is **well-formed**, and one that also matches a **schema (XSD)** is **valid**. XML is wordier than JSON but still everywhere in enterprise, finance, documents and SAML login. Its biggest risk is **XXE**: a careless parser can be tricked into reading server files.
</En>
<Ur>
**XML** (eXtensible Markup Language) structured data ko **tags** se likhe **elements ke darakht** ki shakal me rakhta hai: `<price currency="USD">25</price>`. Element ka **start tag**, **end tag**, ikhtiyari **attributes**, aur mawad (text, doosre elements, ya dono) hota hai. Har document me bilkul **ek root** hota hai, tags **theek tarah andar aur band** hone chahiyen, aur naam **case-sensitive** hain: in qawaid wala document **well-formed** hai, aur jo **schema (XSD)** se bhi mile wo **valid**. XML JSON se lamba hai lekin enterprise, finance, documents aur SAML login me ab bhi har jagah hai. Is ka sab se bara khatra **XXE** hai: laparwah parser ko server ki files parhne par dhoka diya ja sakta hai.
</Ur>

## At a glance

<Glance>
<What>
<Tr>
<En>

XML is a W3C standard (1998) for representing structured data as text, a cousin of HTML (both come from SGML). In XML **you define your own tags**, and the rules are much stricter. Here's the order from the JSON lesson, as XML and as a tree:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<order id="1042">
  <customer vip="true">
    <name>Olivia Brown</name>
    <email>olivia@example.com</email>
  </customer>
  <items>
    <item sku="TSHIRT-M" qty="2"><price currency="USD">25</price></item>
    <item sku="MUG-01" qty="1"><price currency="USD">8</price></item>
  </items>
  <notes>Leave at the gate</notes>
</order>
```

```text
order (id=1042)                       ← root element
├── customer (vip=true)
│   ├── name   → "Olivia Brown"
│   └── email  → "olivia@example.com"
├── items
│   ├── item (sku=TSHIRT-M, qty=2)
│   │   └── price (currency=USD) → "25"
│   └── item (sku=MUG-01, qty=1)
│       └── price (currency=USD) → "8"
└── notes  → "Leave at the gate"
```

The first line, `<?xml version="1.0" encoding="UTF-8"?>`, is the optional but recommended **XML declaration**: which version and character encoding the file uses.

</En>

## Picture it

<Tr>
<En>

XML is **labelled boxes inside labelled boxes**, like moving house. A big box says **"Kitchen"**; inside are smaller boxes, **"Plates"** and **"Cups"**. Each box has a label on top (the start tag) and you seal it at the end (the end tag). A sticker adds extra facts: "fragile = yes" (an **attribute**). Anyone can open the outer box and find exactly what's inside, at any depth. JSON packs the same things more compactly; XML writes the label on **both** ends of every box, which is wordier but very explicit.

</En>
<Ur>

XML **label lage dabbon ke andar label lage dabbe** hai, jaise ghar shift karna. Bare dabbe par likha hai **"Kitchen"**; andar chhote dabbe, **"Plates"** aur **"Cups"**. Har dabbe ke upar label hai (start tag) aur aakhir me aap use seal karte hain (end tag). Sticker izafi baat batata hai: "fragile = yes" (**attribute**). Koi bhi bahar ka dabba khol kar har gehrai par bilkul andar ki cheez dhoondh sakta hai. JSON wahi cheezen zyada mukhtasar bandhta hai; XML har dabbe ke **dono** siron par label likhta hai, jo lamba lekin bohot wazeh hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Elements and the tree">

<Tr>
<En>

An **element** is a start tag `<name>`, content, and an end tag `</name>`. Elements nest to form a **tree** with exactly one **root**, so XML can represent any hierarchy, like JSON objects inside objects. Empty elements can be `<br></br>` or the **self-closing** `<br/>`. Tag names are **case-sensitive** (`<Name>` ≠ `<name>`), can't start with a digit, and can't contain spaces.

</En>
<Ur>

**Element** start tag `<name>`, mawad, aur end tag `</name>` hai. Elements ek doosre ke andar ja kar ek **root** wala **darakht** banate hain, isliye XML koi bhi darja bandi dikha sakta hai, JSON objects ke andar objects ki tarah. Khaali elements `<br></br>` ya **khud band** `<br/>` ho sakte hain. Tag names **case-sensitive** hain (`<Name>` ≠ `<name>`), hindse se shuru nahi ho sakte, aur un me space nahi ho sakta.

</Ur>
</Tr>

```bash
cat > order.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<order id="1042">
  <customer vip="true">
    <name>Olivia Brown</name>
    <email>olivia@example.com</email>
  </customer>
  <items>
    <item sku="TSHIRT-M" qty="2"><price currency="USD">25</price></item>
    <item sku="MUG-01" qty="1"><price currency="USD">8</price></item>
  </items>
  <giftWrap/>
  <notes>Leave at the gate</notes>
</order>
EOF
python3 - <<'PY'
import xml.etree.ElementTree as ET
root = ET.parse("order.xml").getroot()
print("root element:", root.tag, root.attrib)
def show(element, depth=0):
    text = (element.text or "").strip()
    print("  " * depth + element.tag + (f' = "{text}"' if text else ""))
    for child in element:
        show(child, depth + 1)
show(root)
PY
```

```text output
root element: order {'id': '1042'}
order
  customer
    name = "Olivia Brown"
    email = "olivia@example.com"
  items
    item
      price = "25"
    item
      price = "8"
  giftWrap
  notes = "Leave at the gate"
```

<Happened>
<Tr>
<En>

- `xml.etree.ElementTree` (`ET`) is Python's built-in XML library; `ET.parse` read the file and `getroot()` returned `order`.
- `root.tag` is the name and `root.attrib` a dictionary of attributes. Attribute values are always **strings**: `'1042'`, not `1042`.
- `show()` walked the tree recursively, printing each name and text, then calling itself for every child with more indentation.
- For containers like `customer`, `element.text` is only whitespace, which `.strip()` removed.
- `<giftWrap/>` is an empty, self-closing element; its presence alone can carry meaning ("gift wrap requested").

</En>
<Ur>

- `xml.etree.ElementTree` (`ET`) Python ki andar bani XML library hai; `ET.parse` ne file parhi aur `getroot()` ne `order` diya.
- `root.tag` naam hai aur `root.attrib` attributes ki dictionary. Attribute values hamesha **strings** hain: `'1042'`, `1042` nahi.
- `show()` ne darakht ko recursively chala, har naam aur text chhaap kar, phir har bachche ke liye zyada indentation ke saath khud ko bulaya.
- `customer` jaise dabbon me `element.text` sirf khaali jagah hai, jo `.strip()` ne hata di.
- `<giftWrap/>` khaali, khud band element hai; is ka sirf hona bhi matlab rakh sakta hai ("gift wrap chahiye").

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Attributes vs child elements">

<Tr>
<En>

Data can go in **attributes** (`<item sku="MUG-01">`) or **child elements** (`<item><sku>MUG-01</sku></item>`). Both work; a common rule is **attributes for metadata** (IDs, units, types, flags) and **elements for the actual data**, especially anything long, structured or repeating. Attributes can't contain child elements or repeat on one element. Values must be **quoted** and are always strings; attribute order has no meaning.

</En>
<Ur>

Data **attributes** (`<item sku="MUG-01">`) ya **child elements** (`<item><sku>MUG-01</sku></item>`) me ja sakta hai. Dono chalte hain; aam qaida: **metadata ke liye attributes** (IDs, units, qisam, flags) aur **asal data ke liye elements**, khaas tor par lamba, structured ya dohrane wala. Attributes me child elements nahi ho sakte aur ek element par dohra nahi sakte. Values **quotes** me hon aur hamesha strings hain; attributes ki tarteeb ka koi matlab nahi.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import xml.etree.ElementTree as ET
root = ET.parse("order.xml").getroot()
total = 0
for item in root.iter("item"):
    sku = item.get("sku")
    qty = int(item.get("qty"))
    price = item.find("price")
    amount = int(price.text) * qty
    total += amount
    print(f"{sku:9} qty={qty}  {price.get('currency')} {amount}")
print("total:", total, "| vip:", root.find("customer").get("vip") == "true")
print("missing attribute:", root.get("discount"), "| with default:", root.get("discount", "0"))
PY
```

```text output
TSHIRT-M  qty=2  USD 50
MUG-01    qty=1  USD 8
total: 58 | vip: True
missing attribute: None | with default: 0
```

<Happened>
<Tr>
<En>

- `root.iter("item")` found every `<item>` anywhere below the root.
- `item.get("sku")` read an attribute; `int(item.get("qty"))` converted it, because XML has no number type.
- `item.find("price")` found the first `<price>` child, and `.text` is `"25"`.
- `vip` is the **string** `"true"`, so we compared it with `"true"` to get a real boolean.
- `root.get("discount")` returned `None` for a missing attribute; `get(name, default)` gives a fallback.

</En>
<Ur>

- `root.iter("item")` ne root ke neeche kahin bhi har `<item>` dhoondha.
- `item.get("sku")` ne attribute parha; `int(item.get("qty"))` ne badla, kyun ke XML me number ki qisam nahi.
- `item.find("price")` ne pehla `<price>` bachcha dhoondha, aur `.text` `"25"` hai.
- `vip` **string** `"true"` hai, isliye asli boolean ke liye `"true"` se milaya.
- `root.get("discount")` ne ghayab attribute par `None` diya; `get(name, default)` mutabadil deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Well-formed: the strict rules">

<Tr>
<En>

A conforming parser must **stop with an error** on a document that isn't well-formed; unlike a browser with HTML, it may not guess. That strictness makes XML predictable everywhere. The rules: exactly one root; every element closed; tags properly **nested** (no overlapping); matching case; attribute values quoted; no duplicate attributes; `<` and `&` escaped in text. Check with `xmllint --noout file.xml` (from libxml2; on Ubuntu, `sudo apt install libxml2-utils`) or your editor.

</En>
<Ur>

Jo document well-formed na ho us par sahi parser ko **error de kar rukna** padta hai; HTML wale browser ki tarah andaza nahi laga sakta. Yahi sakhti XML ko har jagah qabil-e-paishgoi banati hai. Qawaid: bilkul ek root; har element band; tags theek **andar** (ek doosre par chadhe nahi); ek jaisa case; attribute values quotes me; dohre attributes nahi; text me `<` aur `&` escape. `xmllint --noout file.xml` (libxml2 se; Ubuntu par `sudo apt install libxml2-utils`) ya editor se check karein.

</Ur>
</Tr>

```bash
check() { printf '%s' "$2" | xmllint --noout - 2>err.txt && echo "$1: well-formed" || echo "$1: $(head -1 err.txt | sed 's/^-:[0-9]*: parser error : //')"; }
check "good            " '<order><id>1</id></order>'
check "not closed      " '<order><id>1</id>'
check "bad nesting     " '<b><i>text</b></i>'
check "case mismatch   " '<Name>Sam</name>'
check "unquoted attr   " '<item qty=2/>'
check "two roots       " '<a/><b/>'
check "raw ampersand   " '<company>Smith & Sons</company>'
```

```text output
good            : well-formed
not closed      : Premature end of data in tag order line 1
bad nesting     : Opening and ending tag mismatch: i line 1 and b
case mismatch   : Opening and ending tag mismatch: Name line 1 and name
unquoted attr   : AttValue: " or ' expected
two roots       : Extra content at the end of the document
raw ampersand   : xmlParseEntityRef: no name
```

<Happened>
<Tr>
<En>`check` sent each text to `xmllint --noout -` (`-` = read from standard input) and printed the first error without its prefix. `<order>` never closed; `<i>` opened inside `<b>` but closed after it; `<Name>` and `</name>` differ; `qty=2` needs quotes; a document can't have two roots; and a plain `&` starts an entity reference, so it must be `&amp;`.</En>
<Ur>`check` ne har text `xmllint --noout -` ko diya (`-` = standard input se parho) aur pehla error us ki shuruat ke baghair chhaapa. `<order>` kabhi band nahi hua; `<i>` `<b>` ke andar khula lekin us ke baad band hua; `<Name>` aur `</name>` alag hain; `qty=2` ko quotes chahiyen; document ke do root nahi ho sakte; aur akela `&` entity shuru karta hai, isliye `&amp;` hona chahiye.</Ur>
</Tr>
</Happened>

<Step title="Escaping and CDATA">

<Tr>
<En>

Five characters are written as **entities**: `&lt;` (`<`), `&gt;` (`>`), `&amp;` (`&`), `&quot;` (`"`) and `&apos;` (`'`); otherwise `a < b` or `Smith & Sons` would break the document. `&lt;` and `&amp;` are **always** required in text; `&quot;`/`&apos;` only inside attributes using that quote. Numeric references also work: `&#169;` = ©. A **CDATA section** `<![CDATA[ ... ]]>` holds text that isn't parsed at all, useful for code snippets. When writing, let the library escape for you; when reading, the parser un-escapes automatically.

</En>
<Ur>

Paanch huroof **entities** ki shakal me likhe jate hain: `&lt;` (`<`), `&gt;` (`>`), `&amp;` (`&`), `&quot;` (`"`) aur `&apos;` (`'`); warna `a < b` ya `Smith & Sons` document tor dete. Text me `&lt;` aur `&amp;` **hamesha** lazmi; `&quot;`/`&apos;` sirf us quote wale attributes ke andar. Numeric references bhi chalte hain: `&#169;` = ©. **CDATA section** `<![CDATA[ ... ]]>` aisa text rakhta hai jo bilkul parse nahi hota, code ke tukron ke liye kaam ka. Likhte waqt library ko escape karne dein; parhte waqt parser khud wapas badalta hai.

</Ur>
</Tr>

```bash
cat > escaped.xml <<'EOF'
<rules>
  <rule>price &lt; 1000 &amp;&amp; qty &gt; 0</rule>
  <company name="Smith &amp; Sons &quot;Ltd&quot;"/>
  <script><![CDATA[ if (a < b && c > d) { alert("hi"); } ]]></script>
  <copyright>&#169; 2026</copyright>
</rules>
EOF
python3 - <<'PY'
import xml.etree.ElementTree as ET
root = ET.parse("escaped.xml").getroot()
print("rule:     ", root.find("rule").text)
print("company:  ", root.find("company").get("name"))
print("script:   ", root.find("script").text.strip())
print("copyright:", root.find("copyright").text)
PY
```

```text output
rule:      price < 1000 && qty > 0
company:   Smith & Sons "Ltd"
script:    if (a < b && c > d) { alert("hi"); }
copyright: © 2026
```

<Happened>
<Tr>
<En>The parser turned `&lt;`, `&amp;&amp;` and `&gt;` back into `<`, `&&` and `>`; in the attribute, `&amp;` and `&quot;` became `&` and `"` (escaping `"` was needed because the value itself is in double quotes). Inside CDATA the code was taken literally; the only thing CDATA can't contain is `]]>`. `&#169;` became ©.</En>
<Ur>Parser ne `&lt;`, `&amp;&amp;` aur `&gt;` ko wapas `<`, `&&` aur `>` banaya; attribute me `&amp;` aur `&quot;` `&` aur `"` bane (`"` escape karna zaroori tha kyun ke value khud double quotes me hai). CDATA ke andar code lafzi taur par liya gaya; CDATA me sirf `]]>` nahi aa sakta. `&#169;` © bana.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Namespaces">

<Tr>
<En>

A **namespace** is a URI (usually a URL that's never fetched) attached to element names with `xmlns` or a prefix like `xmlns:pay="..."`. Two standards might both have `<amount>`; namespaces tell them apart (`pay:amount` vs `tax:amount`). `xmlns="URI"` sets a **default namespace** for an element and its children. The **URI** identifies the namespace, not the prefix. Parsers like ElementTree write names as `{URI}localname`, so a search for plain `"url"` finds **nothing**: the number-one XML beginner confusion.

</En>
<Ur>

**Namespace** ek URI hai (aam tor par URL jo kabhi khola nahi jata) jo `xmlns` ya `xmlns:pay="..."` jaise prefix se element names par lagta hai. Do standards me dono ka `<amount>` ho sakta hai; namespaces unhe alag karte hain (`pay:amount` bamuqabla `tax:amount`). `xmlns="URI"` element aur us ke bachchon ka **default namespace** set karta hai. Namespace ki pehchan **URI** se hai, prefix se nahi. ElementTree jaise parsers naam `{URI}localname` likhte hain, isliye saada `"url"` ki search **kuch nahi** dhoondhti: XML ke naye logon ki number ek uljhan.

</Ur>
</Tr>

```bash
cat > sitemap.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
```

<Step title="XPath: querying the tree">

<Tr>
<En>

**XPath** selects nodes in an XML tree, like `jq` for JSON or CSS selectors for HTML: one line instead of nested loops. <Step title="Create XML safely">

<Tr>
<En>

Build XML with a library (ElementTree, lxml, `xmlbuilder2` in Node), never by concatenating strings. The library escapes `<`, `&` and quotes automatically; concatenation lets user input **change the document's structure**: **XML injection**. Below, a customer enters a name designed to inject an extra `<role>` element.

</En>
<Ur>

XML library (ElementTree, lxml, Node me `xmlbuilder2`) se banayen, strings jor kar kabhi nahi. Library `<`, `&` aur quotes khud escape karti hai; jorna user ke input ko **document ka dhancha badalne** deta hai: **XML injection**. Neeche ek customer naam me aisa text daalta hai jo izafi `<role>` element ghusa de.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import xml.etree.ElementTree as ET
user_input = 'Sam</name><role>admin</role><name>x'

unsafe = "<user><name>" + user_input + "</name><role>customer</role></user>"
roles = [r.text for r in ET.fromstring(unsafe).iter("role")]
print("string concatenation -> roles:", roles)

user = ET.Element("user")
ET.SubElement(user, "name").text = user_input
ET.SubElement(user, "role").text = "customer"
safe = ET.tostring(user, encoding="unicode")
print("library-built XML:  ", safe)
print("library -> roles:   ", [r.text for r in ET.fromstring(safe).iter("role")])
PY
```

```text output
string concatenation -> roles: ['admin', 'customer']
library-built XML:   <user><name>Sam&lt;/name&gt;&lt;role&gt;admin&lt;/role&gt;&lt;name&gt;x</name><role>customer</role></user>
library -> roles:    ['customer']
```

<Happened>
<Tr>
<En>The input closes `</name>`, adds `<role>admin</role>`, and opens a new `<name>` so the rest still fits. With concatenation, the XML is well-formed but has **two** roles, the first `admin`; a system reading "the first role" now treats this user as an admin. The library stored the input as **text** and escaped every `<` and `>`, so only `customer` came back.</En>
<Ur>Input `</name>` band karta hai, `<role>admin</role>` jorta hai, aur naya `<name>` kholta hai taa ke baqi fit ho jaye. Jorne se XML well-formed hai lekin **do** roles hain, pehla `admin`; "pehla role" parhne wala system ab is user ko admin samjhega. Library ne input ko **text** ki tarah rakha aur har `<` aur `>` escape kiya, isliye sirf `customer` wapas aaya.</Ur>
</Tr>
</Happened>

<Step title="Pretty printing and converting to JSON">

<Tr>
<En>

Machine-generated XML is often one huge line, and JSON is easier in modern code. `xmllint --format` or `ET.indent` pretty-print; `xmltodict` (Python) or `fast-xml-parser` (Node) convert. But there's **no single standard mapping** from XML to JSON: attributes vs elements, repeated elements (one item or a list?), mixed text and namespaces all need decisions. Write the conversion yourself when the structure matters.

</En>
<Ur>

Machine ka banaya XML aksar ek lambi line hota hai, aur jadeed code me JSON aasaan hai. `xmllint --format` ya `ET.indent` khoobsurat chhaapte hain; `xmltodict` (Python) ya `fast-xml-parser` (Node) badalte hain. Lekin XML se JSON ki **koi ek standard tabdeeli nahi**: attributes bamuqabla elements, dohraye elements (ek item ya list?), mila hua text aur namespaces sab faisle maangte hain. Jab dhancha ahem ho, tabdeeli khud likhein.

</Ur>
</Tr>

```bash
PY
```

<Step title="Validation with XSD">

<Tr>
<En>

Well-formed only means correct syntax. An **XML Schema (XSD)** describes which elements and attributes are allowed, their order, how often they appear, and their **types** (integer, decimal, date, patterns); a matching document is **valid**. Schemas are contracts between organisations (banks, governments, SOAP WSDLs, e-invoicing). Validate with `xmllint --schema`, `lxml.etree.XMLSchema`, or Java/.NET validators; older documents may use a **DTD**. XSD files are themselves XML in the `http://www.w3.org/2001/XMLSchema` namespace (prefix `xs:`).

</En>
<Ur>

Well-formed ka matlab sirf durust syntax. **XML Schema (XSD)** batata hai kaunse elements aur attributes jaiz hain, un ki tarteeb, kitni dafa aate hain, aur un ki **qisam** (integer, decimal, tareekh, patterns); milne wala document **valid** hai. Schemas idaron ke beech muahide hain (banks, hukoomaten, SOAP WSDLs, e-invoicing). `xmllint --schema`, `lxml.etree.XMLSchema`, ya Java/.NET validators se jaanchein; purane documents **DTD** istemal kar sakte hain. XSD files khud `http://www.w3.org/2001/XMLSchema` namespace (prefix `xs:`) wala XML hain.

</Ur>
</Tr>

```bash
cat > order.xsd <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="order">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="item" maxOccurs="unbounded">
          <xs:complexType>
            <xs:attribute name="sku" use="required">
              <xs:simpleType>
                <xs:restriction base="xs:string"><xs:pattern value="[A-Z0-9\-]+"/></xs:restriction>
              </xs:simpleType>
            </xs:attribute>
            <xs:attribute name="qty" type="xs:positiveInteger" use="required"/>
          </xs:complexType>
        </xs:element>
      </xs:sequence>
      <xs:attribute name="id" type="xs:positiveInteger" use="required"/>
    </xs:complexType>
  </xs:element>
</xs:schema>
EOF
echo '<order id="7"><item sku="MUG-01" qty="2"/></order>' > good-order.xml
echo '<order id="7"><item sku="mug 01" qty="-2"/><item qty="1"/></order>' > bad-order.xml
xmllint --noout --schema order.xsd good-order.xml
xmllint --noout --schema order.xsd bad-order.xml 2>&1 | sed -E "s/^bad-order.xml:1: element item: Schemas validity error : //"
```

<Step title="Security: XXE, billion laughs and friends">

<Tr>
<En>

XML allows a **DOCTYPE** that defines **entities**. An **external entity** (`SYSTEM "file:///etc/passwd"`) tells the parser to **load a file or URL** and insert it. If an app parses attacker-supplied XML with entity resolution on, the attacker can read server files or make the server call internal URLs (SSRF): **XXE (XML External Entity)** injection. It has leaked passwords, cloud credentials and source code from real companies. Watch every feature that accepts XML from outside: SOAP endpoints, uploads (`.docx`, `.svg`, `.xlsx` are XML inside), SAML, RSS imports. Use safe defaults: Python's `defusedxml`, modern `lxml`, and in Java/.NET **disable DTDs** explicitly.

</En>
<Ur>

XML **DOCTYPE** ki ijazat deta hai jo **entities** banata hai. **External entity** (`SYSTEM "file:///etc/passwd"`) parser se kehta hai **file ya URL load karo** aur andar daalo. Agar app hamla awar ka bheja XML entity resolution on rakh kar parse kare, to hamla awar server ki files parh sakta hai ya server se andaruni URLs bulwa sakta hai (SSRF): **XXE (XML External Entity)** injection. Is ne asli companies se passwords, cloud credentials aur source code leak kiye hain. Har us feature par nazar rakhein jo bahar se XML le: SOAP endpoints, uploads (`.docx`, `.svg`, `.xlsx` andar se XML hain), SAML, RSS imports. Mehfooz defaults: Python ka `defusedxml`, jadeed `lxml`, aur Java/.NET me DTDs khud **band karein**.

</Ur>
</Tr>

```bash
echo "DB_PASSWORD=topsecret" > secret.txt
cat > upload.xml <<EOF
<?xml version="1.0"?>
<!DOCTYPE order [ <!ENTITY xxe SYSTEM "file://$PWD/secret.txt"> ]>
<order><note>&xxe;</note></order>
EOF
python3 - <<'PY'
from lxml import etree
vulnerable = etree.XMLParser(resolve_entities=True, no_network=True)
leaked = etree.parse("upload.xml", vulnerable).getroot().findtext("note")
print("VULNERABLE parser returned:", repr(leaked))

try:
    etree.parse("upload.xml")
except etree.XMLSyntaxError as err:
    print("lxml default:", str(err).split(",")[0])

import defusedxml.ElementTree as SafeET
try:
    SafeET.parse("upload.xml")
except Exception as err:
    print("defusedxml:  ", type(err).__name__, "- refused entity", repr(err.name))
PY
```

```text output
VULNERABLE parser returned: 'DB_PASSWORD=topsecret\n'
lxml default: Entity 'xxe' not defined
defusedxml:   EntitiesForbidden - refused entity 'xxe'
```

<Happened>
<Tr>
<En>

- `secret.txt` stands in for a sensitive server file. The upload defines entity `xxe` as **the file's content** and uses `&xxe;` in `<note>` (the here-document is unquoted so `$PWD` becomes the real path).
- The **vulnerable parser** (`resolve_entities=True`) put the secret into `note`. If the app shows the note ("Your order note: …"), the attacker sees it.
- **lxml's default** (version 5+) doesn't load external entities, so parsing failed safely.
- **defusedxml** refused the document with `EntitiesForbidden`: the recommended choice for untrusted XML in Python.

</En>
<Ur>

- `secret.txt` server ki hassas file ki jagah hai. Upload `xxe` entity ko **file ka mawad** banata hai aur `<note>` me `&xxe;` istemal karta hai (here-document bina quotes hai isliye `$PWD` asli path banta hai).
- **Kamzor parser** (`resolve_entities=True`) ne raaz `note` me daal diya. Agar app note dikhaye ("Your order note: …"), hamla awar use dekh leta hai.
- **lxml ka default** (version 5+) external entities load nahi karta, isliye parsing mehfooz tareeqe se fail hui.
- **defusedxml** ne `EntitiesForbidden` ke saath document radd kiya: Python me na-bharose wale XML ke liye tajweez shuda.

</Ur>
</Tr>
</Happened>

<Tr>
<En>

The "billion laughs" attack (don't run it on a shared machine):

```xml
<!DOCTYPE lolz [
  <!ENTITY lol "lol">
  <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
```

## Common mistakes

<Compare>
<Bad title="String-built XML, default old parser">

```text
xml = "<user><name>" + name + "</name></user>"     # XML injection
DocumentBuilderFactory.newInstance().newDocumentBuilder().parse(upload)   # XXE risk
```

</Bad>
<Good title="Library-built XML, hardened parser">

```text
ET.SubElement(user, "name").text = name            # escaped automatically
factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)
defusedxml.ElementTree.parse(upload)               # Python: safe by design
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Unescaped `&` or `<`** in text (`Smith & Sons`, `a < b`).
- **Forgetting namespaces** when searching: `findall("url")` returns nothing in a namespaced document.
- **Treating attribute values as numbers or booleans** without converting (`"false"` is a non-empty string, so it's truthy).
- **Generic XML→JSON converters** giving an object instead of a list when there's one item.
- **Confusing well-formed with valid:** syntax checks don't catch wrong data.
- **Ignoring encoding:** declaring `UTF-8` but saving in another encoding corrupts non-English text.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Text me **bina escape `&` ya `<`** (`Smith & Sons`, `a < b`).
- Search karte hue **namespaces bhoolna**: namespaced document me `findall("url")` kuch nahi deta.
- **Attribute values ko numbers ya booleans samajhna** baghair badle (`"false"` khaali string nahi, isliye sach mana jata hai).
- **Aam XML→JSON converters** ek item par list ke bajaye object dete hain.
- **Well-formed aur valid me uljhan:** syntax check ghalat data nahi pakarta.
- **Encoding nazar andaz:** `UTF-8` likh kar file kisi aur encoding me save karna ghair English text bigar deta hai.

</Ur>
</Tr>

<DeepDive title="Real world: a CV upload that leaked cloud credentials">

A company's HR portal lets employees upload a `.docx` CV and extracts their name and skills. A security tester creates a `.docx` (a ZIP of XML files), edits `word/document.xml` to add a DOCTYPE with an external entity pointing to `file:///etc/hostname`, and then to the cloud metadata URL `http://169.254.169.254/latest/meta-data/iam/security-credentials/`. Because the backend used an old Java XML parser with default settings, the extracted "name" showed the server's hostname, and then **temporary cloud credentials**. The fix: disable DTDs (`disallow-doctype-decl`), upgrade the library, block the metadata endpoint for that service (IMDSv2 on AWS), add XXE cases to the security tests, and rotate the exposed credentials.

</DeepDive>

<DeepDive title="Security lens">

Any XML from outside your system, including files that don't look like XML (.docx, .xlsx, .svg), must be parsed with DTDs and external entities disabled.

- **XXE:** disable DTD processing and external entities; use defusedxml (Python), and set secure features explicitly in Java (`DocumentBuilderFactory`, `SAXParserFactory`) and .NET (`DtdProcessing.Prohibit`). OWASP's XXE Prevention Cheat Sheet lists the settings per language.
- **SSRF through XXE:** external entities can make the server request internal URLs (cloud metadata, admin panels); egress controls limit the damage.
- **Denial of service:** entity expansion, huge or deeply nested documents. Limit size and depth.
- **XML injection:** build documents with libraries; validate against a schema.
- **XPath injection:** never put user input directly into XPath queries; use parameterised XPath (lxml supports variables) or strict validation.
- **SAML:** bugs like **XML Signature Wrapping** have let attackers log in as other users. Use well-maintained SAML libraries and keep them updated.
- **SVG uploads** can contain `<script>` and cause stored XSS. Sanitise them, or serve them from a separate domain with a strict CSP.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between well-formed and valid XML?">
A well-formed document follows XML's syntax rules: a single root element, properly nested and closed tags, quoted attribute values, matching case and escaped special characters. A valid document is well-formed and also conforms to a schema such as an XSD or DTD, which defines allowed elements, attributes, order, cardinality and data types.
</QA>

<QA q="What is an XXE attack and how do you prevent it?">
XML External Entity injection happens when an application parses attacker-controlled XML with DTD or external entity processing enabled. The attacker defines an entity that refers to a local file or URL, and the parser inserts its content, leaking files or making server-side requests. Prevent it by disabling DTDs and external entity resolution in the parser, using safe libraries such as defusedxml, keeping parsers updated and validating input.
</QA>

<QA q="Why do namespaces matter when parsing XML?">
Namespaces qualify element names with a URI so that vocabularies from different standards do not clash. Parsers treat the namespace as part of the element name, so a query without the correct namespace will not match, a common reason searches return no results. You must use a namespace mapping in queries, where the URI and not the prefix identifies the namespace.
</QA>

<QA q="When would you choose XML over JSON?">
When integrating with systems that require it such as SOAP, SAML or e-invoicing standards, for documents with mixed content where text contains markup, when mature schema validation, namespaces or XML signature and encryption standards are needed, and for formats built on XML such as SVG, RSS, sitemaps or Office documents. For new web APIs JSON is usually simpler and smaller.
</QA>

</DeepDive>
