<BigIdea>
<Tr>
<En>
**YAML** ("YAML Ain't Markup Language") is a **human-friendly data format**, used mostly for **configuration**. It stores the same data as JSON (objects called **mappings**, arrays called **sequences**, plus strings, numbers, booleans and null) but uses **indentation** instead of braces, `key: value` lines, `- ` for list items, and **`# comments`**. You meet it in Kubernetes, Docker Compose, GitHub Actions and Ansible. The traps: indent with **spaces, never tabs**, and YAML **guesses types**, so `NO`, `on`, `1.10` or a phone number starting with `0` may not stay what you typed. **Quote when in doubt**, and load YAML only with **safe loaders**.
</En>
<Ur>
**YAML** ("YAML Ain't Markup Language") **insaanon ke liye aasaan data format** hai, zyada tar **configuration** ke liye. Ye JSON jaisa hi data rakhta hai (objects jinhe **mappings** kehte hain, arrays jinhe **sequences**, plus strings, numbers, booleans aur null) lekin braces ke bajaye **indentation**, `key: value` lines, list items ke liye `- `, aur **`# comments`** istemal karta hai. Ye Kubernetes, Docker Compose, GitHub Actions aur Ansible me milta hai. Jaal: indentation **spaces se, tabs kabhi nahi**, aur YAML **qisam ka andaza lagata** hai, isliye `NO`, `on`, `1.10` ya `0` se shuru phone number shayad waisa na rahe jaisa likha. **Shak ho to quotes lagayen**, aur YAML sirf **safe loaders** se load karein.
</Ur>

## At a glance

<Glance>
<What>
<Tr>
<En>

YAML is designed to be **easy for humans** to read and edit. Every JSON document is also valid YAML (YAML 1.2 is a superset of JSON), but YAML adds a cleaner, indentation-based syntax and comments. The same data in both formats:

```yaml
# YAML
app: shop
replicas: 3
ports:
  - 80
  - 443
database:
  host: db.internal
  port: 5432
  ssl: true
```

```json
{
  "app": "shop",
  "replicas": 3,
  "ports": [80, 443],
  "database": { "host": "db.internal", "port": 5432, "ssl": true }
}
```

<Why>
<Tr>
<En>

- **DevOps runs on YAML:** Kubernetes (every Deployment, Service, Ingress), Helm, Docker Compose, GitHub Actions, GitLab CI, Ansible, CloudFormation, OpenAPI specs, Prometheus rules.
- **Readable reviews:** config changes in pull requests are easy to read in YAML diffs.

- **Security:** unsafe YAML loading is a known remote-code-execution class, and misconfigured manifests are a top cloud-security finding.

## Picture it

<Tr>
<En>

If JSON is a **printed government form** (strict boxes, brackets and quotes everywhere), YAML is a **neat handwritten outline** in a notebook. You show that something belongs under a heading just by **indenting** it, you make lists with dashes, and you can scribble **notes in the margin** (comments). It's much easier to read and write. But like handwriting, it can be misread: if your indentation slips by one space, or you write something that "looks like" a number or a yes/no, the reader may understand it differently from what you meant.

</En>
<Ur>

Agar JSON **chhapa hua sarkari form** hai (sakht khane, har jagah brackets aur quotes), to YAML notebook me **saaf haath se likha khaka** hai. Kisi cheez ko heading ke neeche dikhane ke liye bas use **andar khiskate** hain, dashes se fehristen banate hain, aur **haashiye me notes** (comments) likh sakte hain. Parhna aur likhna kahin aasaan. Lekin haath ki likhai ki tarah ye ghalat parha ja sakta hai: indentation ek space khisak jaye, ya aap kuch aisa likhen jo number ya haan/nahi "lage", to parhne wala aap ke matlab se alag samajh sakta hai.

</Ur>
</Tr>

## Learn it step by step

<Tr>
<En>
To see exactly how a program reads our YAML, we use a tiny helper that loads YAML and prints it as JSON:
</En>
<Ur>
Program hamari YAML bilkul kaise parhta hai, ye dekhne ke liye ek chhota madadgar istemal karte hain jo YAML load kar ke JSON ki shakal me chhaapta hai:
</Ur>
</Tr>

```bash
cat > y2j.py <<'EOF'
import sys, json, yaml
for doc in yaml.safe_load_all(sys.stdin):
    print(json.dumps(doc, default=str, ensure_ascii=False))
EOF
echo 'hello: world' | python3 y2j.py
```

```text output
{"hello": "world"}
```

<Tr>
<En>`yaml.safe_load_all` (PyYAML, `pip install pyyaml`) reads one or more YAML documents, and `json.dumps` prints each as JSON so we can see real types: quotes mean a string, no quotes a number or boolean. `default=str` lets it print dates.</En>
<Ur>`yaml.safe_load_all` (PyYAML, `pip install pyyaml`) ek ya zyada YAML documents parhta hai, aur `json.dumps` har ek ko JSON me chhaapta hai taa ke asli qisamen dikhen: quotes ka matlab string, quotes nahi to number ya boolean. `default=str` dates chhaapne deta hai.</Ur>
</Tr>

<Walkthrough>

<Step title="Mappings: key: value">

<Tr>
<En>

A mapping is a set of `key: value` lines: the main building block of every config file. A **colon followed by a space** separates the key from the value, and that space is **required**: `port:8080` is a single string, not a key and value. Keys must be unique inside one mapping.

</En>
<Ur>

Mapping `key: value` lines ka set hai: har config file ka bunyadi patthar. **Colon ke baad space** key ko value se alag karta hai, aur wo space **lazmi** hai: `port:8080` ek akeli string hai, key aur value nahi. Ek mapping me keys alag alag hon.

</Ur>
</Tr>

```bash
cat > app.yaml <<'EOF'
name: shop-api
replicas: 3
debug: false
port: 8080
owner: Alex Carter
EOF
python3 y2j.py < app.yaml
echo 'port:8080' | python3 y2j.py
```

```text output
{"name": "shop-api", "replicas": 3, "debug": false, "port": 8080, "owner": "Alex Carter"}
"port:8080"
```

<Happened>
<Tr>
<En>Strings like `shop-api` and `Alex Carter` needed no quotes. YAML **guessed** types: `3` and `8080` became numbers, `false` a boolean. `port:8080` (no space) was read as the single string `"port:8080"`: a silent mistake a program may only notice later, if at all.</En>
<Ur>`shop-api` aur `Alex Carter` jaisi strings ko quotes nahi chahiye the. YAML ne qisam ka **andaza lagaya**: `3` aur `8080` numbers bane, `false` boolean. `port:8080` (space nahi) akeli string `"port:8080"` parhi gayi: chupi ghalti jo program shayad baad me, ya kabhi nahi, pakre.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Indentation and nesting">

<Tr>
<En>

Leading **spaces** show that a value belongs **inside** the key above it, replacing JSON's braces. Use **2 spaces** per level (the convention in Kubernetes, Compose and Actions), and items at the same level must line up **exactly**. **Tabs are forbidden**; set your editor to insert spaces in `.yaml` files.

</En>
<Ur>

Shuru ke **spaces** dikhate hain ke value upar wali key ke **andar** hai, JSON ke braces ki jagah. Har darje ke liye **2 spaces** (Kubernetes, Compose aur Actions ka riwaj), aur ek darje ke items **bilkul** seedh me hon. **Tabs mana hain**; editor ko `.yaml` files me spaces daalne par set karein.

</Ur>
</Tr>

```bash
cat > db.yaml <<'EOF'
database:
  host: db.internal
  port: 5432
  credentials:
    user: shop
    passwordFile: /run/secrets/db_password
cache:
  host: redis.internal
EOF
python3 y2j.py < db.yaml
python3 -c 'import yaml; c = yaml.safe_load(open("db.yaml")); print("db user:", c["database"]["credentials"]["user"])'
```

```text output
{"database": {"host": "db.internal", "port": 5432, "credentials": {"user": "shop", "passwordFile": "/run/secrets/db_password"}}, "cache": {"host": "redis.internal"}}
db user: shop
```

<Happened>
<Tr>
<En>

- `database:` has no value on its line; the indented lines below become its value (a nested mapping).
- `credentials:` is one level deeper (4 spaces), so it's inside `database`; `cache:` at column 0 is a new top-level sibling.
- Python reads nested data key by key: `c["database"]["credentials"]["user"]`.
- `passwordFile` points to a file instead of holding the password: config files end up in Git, secrets must not.

</En>
<Ur>

- `database:` ki line par value nahi; neeche ki indent shuda lines us ki value (andar wali mapping) ban jati hain.
- `credentials:` ek darja aur andar (4 spaces) hai, isliye `database` ke andar; column 0 par `cache:` naya upar ka bhai hai.
- Python andar ka data key ba key parhta hai: `c["database"]["credentials"]["user"]`.
- `passwordFile` password rakhne ke bajaye file ki taraf ishara karta hai: config files Git me jati hain, raaz nahi jane chahiyen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Sequences (lists)">

<Tr>
<En>

A list is lines starting with `- ` (dash and space) at the same indentation, for ports, hosts, steps, containers. A short list can also be inline in **flow style**: `[a, b, c]` (handy for `branches: [main]`). The dash can sit at the same indentation as the parent key (Kubernetes style) or further in; both work, but be consistent.

</En>
<Ur>

Fehrist ek hi indentation par `- ` (dash aur space) se shuru hone wali lines hain, ports, hosts, steps, containers ke liye. Chhoti fehrist **flow style** me ek line me bhi: `[a, b, c]` (`branches: [main]` ke liye kaam ka). Dash parent key ki indentation par (Kubernetes andaaz) ya aage ho sakta hai; dono chalte hain, lekin ek jaisa rakhein.

</Ur>
</Tr>

```bash
cat > lists.yaml <<'EOF'
ports:
  - 80
  - 443
allowedCountries: [US, AE, GB]
admins:
- alex
- emma
EOF
python3 y2j.py < lists.yaml
```

```text output
{"ports": [80, 443], "allowedCountries": ["US", "AE", "GB"], "admins": ["alex", "emma"]}
```

<Happened>
<Tr>
<En>`ports` used block style with indented dashes, `allowedCountries` flow style (a JSON array without quotes), and `admins` put dashes at the **same** indentation as the key, also valid and very common in Kubernetes.</En>
<Ur>`ports` ne andar khiske dashes wala block style, `allowedCountries` ne flow style (quotes ke baghair JSON array), aur `admins` ne dashes key ki **usi** indentation par rakhe, ye bhi durust aur Kubernetes me bohot aam.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Lists of mappings: the shape of real config">

<Tr>
<En>

A list item can be a mapping: the first key goes after the dash, and the remaining keys line up **under the first key**, not under the dash. This is the most common DevOps shape (Kubernetes `containers:`, Actions `steps:`, Ansible `tasks:`): every `- name: ...` starts a new item. Misaligning the second key is the number-one YAML bug.

</En>
<Ur>

Fehrist ka item mapping ho sakta hai: pehli key dash ke baad, aur baqi keys **pehli key ke neeche** seedh me, dash ke neeche nahi. Ye DevOps ki sab se aam shakal hai (Kubernetes `containers:`, Actions `steps:`, Ansible `tasks:`): har `- name: ...` naya item shuru karta hai. Doosri key ka seedh se hatna YAML ka number ek bug hai.

</Ur>
</Tr>

```bash
cat > deploy.yaml <<'EOF'
containers:
  - name: web
    image: nginx:1.27
    ports:
      - containerPort: 80
  - name: api
    image: ghcr.io/acme/shop-api:2.4.1
    env:
      - name: NODE_ENV
        value: production
EOF
python3 -c '
import yaml
spec = yaml.safe_load(open("deploy.yaml"))
for c in spec["containers"]:
    print(f"{c["name"]:4} -> {c["image"]}  keys: {sorted(c)}")'
```

```text output
web  -> nginx:1.27  keys: ['image', 'name', 'ports']
api  -> ghcr.io/acme/shop-api:2.4.1  keys: ['env', 'image', 'name']
```

```text
containers:            ← key with a list value
  - name: web          ← "- " starts item 1 (a mapping); first key: name
    image: nginx:1.27  ← lines up with "name" → same item
  - name: api          ← "- " starts item 2
```

<Happened>
<Tr>
<En>`image:` and `ports:` line up with `name`, so all three belong to one container. `ports` is itself a list of mappings and `env` a list of `name`/`value` mappings: lists inside mappings inside lists, normal in Kubernetes. The loop confirmed the structure was read as intended.</En>
<Ur>`image:` aur `ports:` `name` ki seedh me hain, isliye teeno ek container ke hain. `ports` khud mappings ki fehrist hai aur `env` `name`/`value` mappings ki: fehriston ke andar mappings ke andar fehristen, Kubernetes me aam. Loop ne tasdeeq ki dhancha sahi parha gaya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Type guessing and its traps">

<Tr>
<En>

Unquoted values are **interpreted**: YAML decides if they're numbers, booleans, null, dates or strings. The older YAML 1.1 rules (PyYAML and many tools) recognise many "booleans" and number formats, the source of the most famous YAML bugs. Watch country codes, yes/no-like words, versions, phone numbers, leading zeros and times. YAML 1.2 parsers fixed some of this, but you can't rely on every tool using 1.2. **Quote any value that must stay a string.**

</En>
<Ur>

Baghair quotes values ki **tashreeh hoti hai**: YAML tay karta hai ye numbers, booleans, null, dates ya strings hain. Purane YAML 1.1 qawaid (PyYAML aur bohot se tools) bohot se "booleans" aur number formats pehchante hain, jo YAML ke mashhoor tareen bugs ki jar hai. Country codes, haan/nahi jaise alfaaz, versions, phone numbers, shuru ke zero aur waqt par nazar rakhein. YAML 1.2 parsers ne kuch theek kiya, lekin har tool ke 1.2 istemal karne par bharosa nahi kar sakte. **Jo value string rehni chahiye use quote karein.**

</Ur>
</Tr>

```bash
cat > traps.yaml <<'EOF'
country: NO
quotedCountry: "NO"
feature: on
version: 1.10
quotedVersion: "1.10"
fileMode: 0755
phone: 01234567654
quotedPhone: "01234567654"
meetingTime: 12:30
releaseDate: 2026-11-10
nothing: ~
emptyValue:
EOF
python3 -c '
import yaml
for key, value in yaml.safe_load(open("traps.yaml")).items():
    print(f"{key:14} = {value!r:14} ({type(value).__name__})")'
```

```text output
country        = False          (bool)
quotedCountry  = 'NO'           (str)
feature        = True           (bool)
version        = 1.1            (float)
quotedVersion  = '1.10'         (str)
fileMode       = 493            (int)
phone          = 175304620      (int)
quotedPhone    = '01234567654'  (str)
meetingTime    = 750            (int)
releaseDate    = datetime.date(2026, 11, 10) (date)
nothing        = None           (NoneType)
emptyValue     = None           (NoneType)
```

<Happened>
<Tr>
<En>

- **The "Norway problem":** `NO` (Norway's country code) became `False`; in YAML 1.1 `yes/no/on/off/y/n` are booleans. Quoted, it stays `'NO'`.
- `feature: on` became `True` (GitHub Actions' `on:` key works only because Actions handles it specially).
- `version: 1.10` became the float `1.1`: a different version! Quote versions.
- `0755` is **octal** (base 8) = 493: right for file permissions, surprising otherwise.
- `phone: 01234567654` starts with `0` and has only digits 0–7, so it's octal too: 175304620, a completely different number. Quoted, it's correct.
- `12:30` is base-60 time: 12×60 + 30 = **750**. `2026-11-10` became a `date` object. `~` and an empty value are both **null**.

**Rule:** if a value isn't clearly a number or `true`/`false` you **want** as such, quote it.

</En>
<Ur>

- **"Norway problem":** `NO` (Norway ka country code) `False` ban gaya; YAML 1.1 me `yes/no/on/off/y/n` booleans hain. Quotes ke saath `'NO'` rehta hai.
- `feature: on` `True` bana (GitHub Actions ki `on:` key sirf is liye chalti hai ke Actions use khaas tor par sambhalta hai).
- `version: 1.10` float `1.1` ban gaya: doosra version! Versions quote karein.
- `0755` **octal** (base 8) = 493: file permissions ke liye theek, warna hairan kun.
- `phone: 01234567654` `0` se shuru aur sirf 0–7 hindse, isliye ye bhi octal: 175304620, bilkul alag number. Quotes ke saath durust.
- `12:30` base-60 waqt hai: 12×60 + 30 = **750**. `2026-11-10` `date` object bana. `~` aur khaali value dono **null**.

**Qaida:** agar value saaf tor par wo number ya `true`/`false` nahi jo aap **chahte** hain, to quote karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Strings and quoting">

<Tr>
<En>

Strings can be **plain** (no quotes), **single-quoted** or **double-quoted**. Plain is convenient, but some characters are special (`: `, ` #`, `{`, `[`, `*`, `&`, `!`, `%`, `@`, a leading `-`, `?`). In single quotes everything is literal (write `''` for one `'`); in double quotes backslash escapes work (`\n`, `\t`, `\"`). A `#` after a space starts a **comment**, so `password: abc #123` loses `#123`.

</En>
<Ur>

Strings **plain** (quotes nahi), **single-quoted** ya **double-quoted** ho sakti hain. Plain aasaan hai, lekin kuch huroof khaas hain (`: `, ` #`, `{`, `[`, `*`, `&`, `!`, `%`, `@`, shuru ka `-`, `?`). Single quotes me sab lafzi hai (ek `'` ke liye `''`); double quotes me backslash escapes chalte hain (`\n`, `\t`, `\"`). Space ke baad `#` **comment** shuru karta hai, isliye `password: abc #123` `#123` kho deta hai.

</Ur>
</Tr>

```bash
cat > strings.yaml <<'EOF'
plain: Hello World
withColon: "time: 10:30"
withHash: "abc #123"
brokenHash: abc #123
single: 'It''s literal: \n stays'
double: "Tab\there, newline\nhere"
url: https://example.com:8443/path
star: "*.example.com"
EOF
python3 y2j.py < strings.yaml
```

```text output
{"plain": "Hello World", "withColon": "time: 10:30", "withHash": "abc #123", "brokenHash": "abc", "single": "It's literal: \\n stays", "double": "Tab\there, newline\nhere", "url": "https://example.com:8443/path", "star": "*.example.com"}
```

<Happened>
<Tr>
<En>

- `withColon` needs quotes because `: ` in a plain string starts a new key.
- `withHash` keeps `#123`; `brokenHash` lost it as a comment. Imagine that happening to a password.
- In single quotes `''` is one `'` and `\n` stays two literal characters (shown as `\\n` in JSON); in double quotes `\t` and `\n` became a real tab and newline.
- `url` works unquoted because no colon is followed by a space; quoting it anyway is a good habit. `star` **must** be quoted, or a leading `*` is read as an alias.

</En>
<Ur>

- `withColon` ko quotes chahiyen kyun ke plain string me `: ` nayi key shuru karta hai.
- `withHash` ne `#123` rakha; `brokenHash` ne use comment samajh kar kho diya. Socho password ke saath ye ho.
- Single quotes me `''` ek `'` hai aur `\n` do lafzi huroof rehta hai (JSON me `\\n`); double quotes me `\t` aur `\n` asli tab aur nayi line bane.
- `url` baghair quotes chalta hai kyun ke kisi colon ke baad space nahi; phir bhi quote karna achhi aadat hai. `star` ko quote karna **lazmi** hai, warna shuru ka `*` alias samjha jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Multi-line strings: | and >">

<Tr>
<En>

**Block scalars** write long text over several lines. `|` (**literal**) keeps line breaks exactly: scripts (`run: |` in Actions), embedded configs, PEM certificates. `>` (**folded**) joins lines with spaces into one paragraph: long descriptions. YAML removes the indentation under the key. **Chomping indicators** control the final newline: `|` keeps one, `|-` removes it, `|+` keeps all.

</En>
<Ur>

**Block scalars** lamba text kai lines me likhte hain. `|` (**literal**) nayi lines bilkul qaim rakhta hai: scripts (Actions me `run: |`), andar rakhi configs, PEM certificates. `>` (**folded**) lines ko spaces se jor kar ek paragraph banata hai: lambi tafseelat. YAML key ke neeche ki indentation hata deta hai. **Chomping indicators** aakhri nayi line control karte hain: `|` ek rakhta, `|-` hatata, `|+` sab rakhta.

</Ur>
</Tr>

```bash
cat > blocks.yaml <<'EOF'
script: |
  echo "step 1"
  echo "step 2"
summary: >
  This deployment runs the shop API
  with three replicas behind a load balancer.
noTrailingNewline: |-
  last line
EOF
python3 y2j.py < blocks.yaml
python3 -c 'import yaml; print(yaml.safe_load(open("blocks.yaml"))["script"], end="")' | bash
```

```text output
{"script": "echo \"step 1\"\necho \"step 2\"\n", "summary": "This deployment runs the shop API with three replicas behind a load balancer.\n", "noTrailingNewline": "last line"}
step 1
step 2
```

<Happened>
<Tr>
<En>`script: |` kept each line separate plus one final newline, exactly what a shell script needs. `summary: >` folded two lines into one sentence. `|-` removed the final newline. The last command piped `script` into `bash`, which ran both lines: what GitHub Actions does with `run: |`.</En>
<Ur>`script: |` ne har line alag aur aakhir me ek nayi line rakhi, bilkul jo shell script ko chahiye. `summary: >` ne do lines ek jumle me jor din. `|-` ne aakhri nayi line hata di. Aakhri command ne `script` ko `bash` me bheja, jis ne dono lines chalayin: yahi GitHub Actions `run: |` ke saath karta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Comments and indentation errors">

<Tr>
<En>

`#` starts a comment to the end of the line (at line start or after a space). Comments explain **why** a setting has a value ("# 3 replicas: one per availability zone"), one of the main reasons to choose YAML. Indentation errors are the most common parse failures; errors include the **line and column**. Common causes: a tab, a key indented one space too much or too little, or a missing space after `:` or `-`. Check with `yaml.safe_load` or the **yamllint** tool.

</En>
<Ur>

`#` line ke aakhir tak comment shuru karta hai (line ke shuru me ya space ke baad). Comments batate hain setting ki value **kyun** hai ("# 3 replicas: har availability zone me ek"), YAML chunne ki bari wajah. Indentation ki ghaltiyan sab se aam parse nakaamiyan hain; errors **line aur column** batate hain. Aam wajahen: tab, key ka ek space zyada ya kam khiska hona, ya `:` ya `-` ke baad space ghayab. `yaml.safe_load` ya **yamllint** tool se check karein.

</Ur>
</Tr>

```bash
check() {
  printf '%b' "$2" | python3 -c '
import sys, yaml
try:
    yaml.safe_load(sys.stdin)
    print("valid")
except yaml.YAMLError as e:
    m = e.problem_mark
    print(f"{e.problem} (line {m.line + 1}, column {m.column + 1})")' | sed "s/^/$1: /"
}
check "good          " 'server:\n  port: 80   # HTTP\n  host: web\n'
check "tab indent    " 'server:\n\tport: 80\n'
check "extra indent  " 'server:\n  port: 80\n   host: web\n'
check "no space dash " 'items:\n  -a\n  - b\n'
printf 'items:\n  -a\n  - b\n' | python3 y2j.py
```

```text output
good          : valid
tab indent    : found character '\t' that cannot start any token (line 2, column 1)
extra indent  : mapping values are not allowed here (line 3, column 8)
no space dash : valid
{"items": "-a - b"}
```

<Happened>
<Tr>
<En>

- `check` expands `\n` and `\t` with `printf '%b'`, loads the YAML, and prints "valid" or the problem with its position (`problem_mark` counts from 0, so we add 1).
- **good:** the comment `# HTTP` was ignored. **tab indent:** YAML refuses tabs. **extra indent:** `host` had 3 spaces, so YAML read it as a continuation of `port`'s value and failed at the second colon.
- **no space dash** is **valid**, which is worse: `-a` isn't a list item but the start of a plain string, so `items` became the single string `"-a - b"`. No error, just wrong data.
- Errors sometimes point to the **next** line, so check the line above too.

</En>
<Ur>

- `check` `printf '%b'` se `\n` aur `\t` phailata hai, YAML load karta hai, aur "valid" ya masla us ki jagah ke saath chhaapta hai (`problem_mark` 0 se ginta hai, isliye 1 jorte hain).
- **good:** comment `# HTTP` nazar andaz hua. **tab indent:** YAML tabs nahi maanta. **extra indent:** `host` ke 3 spaces the, to YAML ne use `port` ki value ka hissa samjha aur doosre colon par fail hua.
- **no space dash** **durust** hai, jo aur bura hai: `-a` list item nahi balke plain string ki shuruat hai, isliye `items` akeli string `"-a - b"` ban gaya. Koi error nahi, bas ghalat data.
- Errors kabhi **agli** line batate hain, isliye upar wali line bhi dekhein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Anchors, aliases and merge keys">

<Tr>
<En>

`&name` puts an **anchor** on a value, `*name` reuses it (an **alias**), and `<<: *name` **merges** an anchored mapping into another, where later keys override. Don't repeat yourself: shared defaults for several services (Docker Compose, GitLab CI). Merge keys are a YAML 1.1 feature supported by most tools, but Kubernetes manifests usually rely on Helm or Kustomize for reuse instead.

</En>
<Ur>

`&name` value par **anchor** lagata hai, `*name` use dobara istemal karta hai (**alias**), aur `<<: *name` anchor wali mapping ko doosri me **milata** hai, jahan baad ki keys upar likhti hain. Dohrao mat: kai services ke saanjhe defaults (Docker Compose, GitLab CI). Merge keys YAML 1.1 ka feature hain jo zyada tar tools maante hain, lekin Kubernetes manifests aam tor par dobara istemal ke liye Helm ya Kustomize par chalte hain.

</Ur>
</Tr>

```bash
cat > compose-like.yaml <<'EOF'
x-defaults: &defaults
  restart: always
  logging: json-file
  memory: 512m

services:
  web:
    <<: *defaults
    image: nginx:1.27
  worker:
    <<: *defaults
    image: ghcr.io/acme/worker:1.0
    memory: 1g
EOF
python3 -c '
import yaml, json
services = yaml.safe_load(open("compose-like.yaml"))["services"]
print(json.dumps(services, indent=2))'
```

```text output
{
  "web": {
    "restart": "always",
    "logging": "json-file",
    "memory": "512m",
    "image": "nginx:1.27"
  },
  "worker": {
    "restart": "always",
    "logging": "json-file",
    "memory": "1g",
    "image": "ghcr.io/acme/worker:1.0"
  }
}
```

<Happened>
<Tr>
<En>`x-defaults: &defaults` named a mapping (Compose ignores top-level `x-` keys, a handy place for shared blocks). `<<: *defaults` copied `restart`, `logging` and `memory` into both services, and `worker`'s `memory: 1g` **overrode** `512m`. Changing a default now means editing one place.</En>
<Ur>`x-defaults: &defaults` ne mapping ko naam diya (Compose upar ki `x-` keys nazar andaz karta hai, saanjhe hisson ki achhi jagah). `<<: *defaults` ne `restart`, `logging` aur `memory` dono services me copy kiye, aur `worker` ke `memory: 1g` ne `512m` ko **badal** diya. Ab default badalna ek jagah ka kaam hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Multiple documents with ---">

<Tr>
<En>

One file can contain several YAML documents separated by `---` lines. Kubernetes users often keep related objects (Deployment + Service + ConfigMap) in one file, and `kubectl apply -f app.yaml` applies them all. Load them with `safe_load_all`; `safe_load` (singular) fails if there's more than one.

</En>
<Ur>

Ek file me `---` lines se alag kai YAML documents ho sakte hain. Kubernetes users aksar mutaliq objects (Deployment + Service + ConfigMap) ek file me rakhte hain, aur `kubectl apply -f app.yaml` sab lagata hai. Inhe `safe_load_all` se load karein; ek se zyada hon to `safe_load` (wahid) fail hota hai.

</Ur>
</Tr>

```bash
cat > k8s.yaml <<'EOF'
apiVersion: apps/v1

  name: shop-api
---
apiVersion: v1

  name: shop-api
```


<Happened>
<Tr>
<En>`safe_load_all` returned the three documents one by one, and the loop printed each kind and name.</En>
<Ur>`safe_load_all` ne teeno documents ek ek kar ke diye, aur loop ne har ek ki kind aur naam chhaapa.</Ur>

<Step title="YAML ⇄ JSON">

<Tr>
<En>

YAML can represent everything JSON can, so you can convert between them. APIs speak JSON while humans edit YAML, `kubectl` accepts both, and `jq` reads only JSON. Tools: Python (`yaml` + `json`), the Go **yq** (`yq -o=json file.yaml`), `kubectl get deploy x -o json`. JSON → YAML **loses nothing**; YAML → JSON loses comments and anchors (aliases are expanded), and dates become strings.

</En>
<Ur>

YAML wo sab dikha sakta hai jo JSON, isliye dono me badal sakte hain. APIs JSON bolti hain jab ke insaan YAML badalte hain, `kubectl` dono maanta hai, aur `jq` sirf JSON parhta hai. Tools: Python (`yaml` + `json`), Go ka **yq** (`yq -o=json file.yaml`), `kubectl get deploy x -o json`. JSON → YAML me **kuch nahi khota**; YAML → JSON me comments aur anchors khote hain (aliases phail jate hain), aur dates strings banti hain.

</Ur>
</Tr>

```bash
python3 -c 'import yaml, json, sys; print(json.dumps(yaml.safe_load(open("db.yaml"))))' | jq -r '.database | "\(.host):\(.port)"'
echo '{"name": "shop", "ports": [80, 443], "tls": {"enabled": true}}' > from-api.json
python3 -c 'import yaml, json; print(yaml.safe_dump(json.load(open("from-api.json")), sort_keys=False), end="")'
```

```text output
db.internal:5432
name: shop
ports:
- 80
- 443
tls:
  enabled: true
```

<Happened>
<Tr>
<En>The first line turned `db.yaml` into JSON and piped it into `jq` to build `host:port`. The next two turned a JSON file into YAML with `yaml.safe_dump`; `sort_keys=False` kept the key order, and PyYAML put list dashes at the parent key's indentation, one of the two valid styles.</En>
<Ur>Pehli line ne `db.yaml` ko JSON banaya aur `host:port` banane ke liye `jq` me bheja. Agli do lines ne `yaml.safe_dump` se JSON file ko YAML banaya; `sort_keys=False` ne keys ki tarteeb rakhi, aur PyYAML ne list ke dashes parent key ki indentation par rakhe, do durust andaazon me se ek.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Security: unsafe loading and alias bombs">

<Tr>
<En>

Some YAML libraries can create **any object** of the language from special tags such as `!!python/object/apply:`, so loading untrusted YAML with them lets an attacker **run commands**. YAML often comes from users: uploaded configs, CI files in PRs, Helm values. In Python use `yaml.safe_load`, **never** `yaml.unsafe_load` / `full_load` on untrusted input; similar risks hit Ruby, Java (SnakeYAML before 2.0) and old Node js-yaml. Safe loaders only build basic types and reject other tags.

</En>
<Ur>

Kuch YAML libraries khaas tags jaise `!!python/object/apply:` se zubaan ka **koi bhi object** bana sakti hain, isliye un se na-bharose YAML load karna hamla awar ko **commands chalane** deta hai. YAML aksar users se aata hai: upload configs, PRs me CI files, Helm values. Python me `yaml.safe_load`, na-bharose input par `yaml.unsafe_load` / `full_load` **kabhi nahi**; aise khatre Ruby, Java (2.0 se pehle SnakeYAML) aur purane Node js-yaml me bhi the. Safe loaders sirf bunyadi qisamen banate hain aur doosre tags radd karte hain.

</Ur>
</Tr>

```bash
cat > evil.yaml <<'EOF'
name: harmless-looking-config
run: !!python/object/apply:os.system ["echo PWNED: attacker command ran > pwned.txt"]
EOF
python3 -c 'import yaml; yaml.safe_load(open("evil.yaml"))' 2>&1 | grep -o 'could not determine a constructor.*os.system' | sed 's/^/safe_load:   rejected: /'
ls pwned.txt 2>/dev/null || echo "safe_load:   no file created"
python3 -c 'import yaml; yaml.unsafe_load(open("evil.yaml"))'
echo "unsafe_load: $(cat pwned.txt)"
```

```text output
safe_load:   rejected: could not determine a constructor for the tag 'tag:yaml.org,2002:python/object/apply:os.system
safe_load:   no file created
unsafe_load: PWNED: attacker command ran
```

<Happened>
<Tr>
<En>

The `!!python/object/apply:os.system` tag asks the loader to **call** `os.system` with a shell command. `safe_load` refused the tag and nothing ran. `unsafe_load` obeyed and wrote `pwned.txt`; a real attacker would download malware or steal credentials instead. That's **remote code execution** from loading a "config file".

**Alias bombs:** a few lines where each level references the previous one nine times expand to 9⁹ (about 387 million) values in memory. Limit file size and alias expansion, or use parsers with built-in limits.

</En>
<Ur>

`!!python/object/apply:os.system` tag loader se shell command ke saath `os.system` **chalwata** hai. `safe_load` ne tag radd kiya aur kuch nahi chala. `unsafe_load` ne maana aur `pwned.txt` likh di; asli hamla awar malware download karta ya credentials churata. Ye "config file" load karne se **remote code execution** hai.

**Alias bombs:** chand lines jahan har darja pichhle ko nau dafa dohrata hai, memory me 9⁹ (takreeban 38.7 crore) values tak phail jati hain. File ka size aur alias phailao mehdood karein, ya andar se hadd wale parsers istemal karein.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Unquoted values YAML will reinterpret">

```text
image_tag: 1.10          # becomes 1.1
country: NO              # becomes false
support_phone: 0123456   # becomes an octal number
colour: #fff             # becomes null (a comment)
```

</Bad>
<Good title="Quote anything that must stay a string">

```text
image_tag: "1.10"
country: "NO"
support_phone: "0123456"
colour: "#fff"
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Tabs** for indentation, or mixing 2 and 4 spaces.
- **Second key of a list item not aligned** with the first key after the dash.
- **Missing space after `:` or `-`.**
- **Values starting with `*`, `&`, `!`, `@`, `{` or `[`** without quotes.
- **Using unsafe loaders** on files you didn't write.
- **Secrets in committed YAML:** Kubernetes `Secret` manifests are only Base64, not encrypted.
- **Expecting comments to survive** a YAML → JSON → YAML round trip.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Indentation ke liye **tabs**, ya 2 aur 4 spaces milana.
- **List item ki doosri key** dash ke baad pehli key ki seedh me na hona.
- **`:` ya `-` ke baad space ghayab.**
- **`*`, `&`, `!`, `@`, `{` ya `[` se shuru values** baghair quotes.
- Apni na likhi files par **ghair mehfooz loaders**.
- **Commit hone wali YAML me raaz:** Kubernetes `Secret` manifests sirf Base64 hain, encrypted nahi.
- YAML → JSON → YAML ke chakkar me **comments bachne ki umeed**.

</Ur>
</Tr>

<DeepDive title="Real world: version 1.10 that deployed 1.1">

A platform team at a fintech company manages 40 microservices on Kubernetes with Helm. One Friday, a developer changes `values.yaml` to roll out version `1.10` of the payment service: `tag: 1.10`. The parser reads it as the number `1.1`, Helm renders `image: payments:1.1`, and Kubernetes happily deploys the **old** version 1.1, re-introducing a fixed bug. Afterwards the team quotes every `tag:` value (`tag: "1.10"`), adds **yamllint** and **kubeconform** (validates manifests against Kubernetes schemas) to CI, adds a policy check (Kyverno / OPA) that rejects images without an exact tag, and enables the Red Hat YAML extension with Kubernetes schemas in everyone's VS Code.

</DeepDive>

<DeepDive title="Security lens">

YAML is where infrastructure security settings live. A misread value or an unsafe loader can turn a config file into an attack path.

- **Always use safe loaders** for untrusted YAML (`yaml.safe_load`, SnakeYAML `SafeConstructor`, js-yaml 4 `load`, safe by default).
- **Limit size and aliases** to prevent alias-bomb denial of service.
- **Kubernetes Secrets in YAML are Base64, not encryption.** Use SOPS, Sealed Secrets or an external secret manager.
- **Scan manifests in CI:** Checkov, kube-score, kubescape and Trivy find risky settings (`privileged: true`, `runAsUser: 0`, `hostNetwork: true`, missing resource limits).
- **Type confusion can disable security:** `enabled: off` meant as a string may silently become a boolean.
- **CI YAML from pull requests is code:** protect workflow and `.gitlab-ci.yml` paths with CODEOWNERS.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between YAML and JSON?">
Both represent the same basic data model of mappings, sequences and scalars. JSON uses braces, brackets and mandatory quotes and has no comments, which makes it strict and ideal for data exchange between programs. YAML uses indentation, allows unquoted strings, comments, multi-line strings, anchors and multiple documents, which makes it more readable for human-edited configuration. YAML 1.2 is a superset of JSON.
</QA>

<QA q="What is the Norway problem in YAML?">
In YAML 1.1, unquoted words such as yes, no, on and off are interpreted as booleans, so the country code NO for Norway is parsed as false. Similar implicit typing turns 1.10 into 1.1 and leading-zero numbers into octal. The fix is to quote values that must remain strings.
</QA>

<QA q="What is the difference between the literal and folded block styles in YAML?">
Both start a multi-line block scalar. The literal style, written with a pipe, preserves line breaks exactly, which suits scripts and certificates. The folded style, written with a greater-than sign, joins lines with spaces into a single paragraph. Chomping indicators control whether the final newline is removed or all trailing newlines are kept.
</QA>

<QA q="Why is yaml.load dangerous in Python?">
With a full or unsafe loader, YAML tags can instruct the parser to construct arbitrary Python objects or call functions such as os.system, so loading attacker-controlled YAML can lead to remote code execution. yaml.safe_load only constructs basic data types and rejects such tags, so it should be used for any untrusted input.
</QA>

<QA q="What are YAML anchors and aliases used for?">
An anchor names a node and an alias references it again, avoiding repetition. The merge key can merge an anchored mapping into another mapping, where additional keys override the merged defaults. They are common in Docker Compose and GitLab CI files to share default settings.
</QA>
