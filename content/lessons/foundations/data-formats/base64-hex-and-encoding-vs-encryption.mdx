<BigIdea>
<Tr>
<En>
**Encoding** changes how data is **written**, not who can read it. **Hex** writes each byte as two characters (`Hi!` → `486921`); **Base64** packs every 3 bytes into 4 safe characters (`Hi!` → `SGkh`), about **33% bigger**; **Base64url** swaps `+/` for `-_` for URLs and JWTs; **URL encoding** (`%20`) and **HTML escaping** (`&lt;`) make text safe in one context. Anyone can **decode** all of these without a key. **Encryption** needs a **key**; **hashing** can't be reversed at all. So a Base64 "password", a Kubernetes Secret or a JWT payload is **not secret**.
</En>
<Ur>
**Encoding** data ke **likhne ka tareeqa** badalti hai, ye nahi ke kaun parh sakta hai. **Hex** har byte ko do huroof me likhta hai (`Hi!` → `486921`); **Base64** har 3 bytes ko 4 mehfooz huroof me bandh karta hai (`Hi!` → `SGkh`), takreeban **33% bara**; **Base64url** URLs aur JWTs ke liye `+/` ki jagah `-_` likhta hai; **URL encoding** (`%20`) aur **HTML escaping** (`&lt;`) text ko ek khaas jagah ke liye mehfooz banate hain. Ye sab koi bhi bina key ke **decode** kar sakta hai. **Encryption** ko **key** chahiye; **hashing** ulti ho hi nahi sakti. Isliye Base64 wala "password", Kubernetes Secret ya JWT payload **raaz nahi** hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Computers store everything as **bytes**, but many systems can only safely carry **text**: JSON, email, URLs, HTTP headers, YAML, HTML, terminals. A raw byte might look like a quote, a newline or an invisible control character and break things. Encodings **re-write bytes using only safe characters**.

<Why>
<Tr>
<En>

- **You see it everywhere:** SHA-256 hashes and Git commit IDs (hex), colours `#ff5733` (hex), JWT login tokens (Base64url), email attachments and `data:` URLs (Base64), Kubernetes Secrets, Basic auth headers, query strings (URL encoding).
- **Debugging:** a "garbled" value in a log or API response is often just encoded. Recognising it saves hours.
- **The number-one security misunderstanding:** "the password is in Base64, so it's safe" is wrong, and it shows up constantly in code reviews and audits.
- **Attack and defence:** malware, phishing and web attacks hide payloads in Base64, hex and double URL encoding; analysts and WAFs must decode to see the real content.

</En>

- **Har jagah nazar aata hai:** SHA-256 hashes aur Git commit IDs (hex), rang `#ff5733` (hex), JWT login tokens (Base64url), email attachments aur `data:` URLs (Base64), Kubernetes Secrets, Basic auth headers, query strings (URL encoding).

## Picture it

<Tr>
<En>

**Encoding** is like writing a message in **Roman Urdu instead of Urdu script**: the words are the same, only written with different letters so another system (an English keyboard) can carry it, and anyone who knows the rule can read it back. **Encryption** is putting the message in a **locked box**: without the key nobody can read it, even if they know exactly what kind of box it is. **Hashing** is a **fingerprint**: it identifies the message, but you can't rebuild a person from their fingerprint.

</En>
<Ur>

**Encoding** aisa hai jaise paigham **Urdu rasm-ul-khat ke bajaye Roman Urdu** me likhna: alfaaz wahi, sirf alag huroof me taa ke doosra system (English keyboard) use le ja sake, aur qaida jaanne wala koi bhi wapas parh le. **Encryption** paigham ko **taale wale sandooq** me rakhna hai: key ke baghair koi nahi parh sakta, chahe use bilkul pata ho sandooq kis qisam ka hai. **Hashing** **fingerprint** hai: paigham ki pehchan karta hai, lekin fingerprint se insaan dobara nahi banaya ja sakta.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Everything is bytes">

<Tr>
<En>

Text is stored as numbers. In UTF-8, English letters take 1 byte each; most other scripts (Urdu, Arabic, Chinese, Japanese) take 2–4 bytes per character. Every encoding works on **bytes**, not "letters", which is why non-English text produces longer Base64 or URL-encoded output. `od` (on every Linux system) shows the bytes: `-tx1` as hex, `-tu1` as decimal 0–255.

</En>
<Ur>

Text numbers ki shakal me save hota hai. UTF-8 me English huroof 1 byte lete hain; zyada tar doosre rasm-ul-khat (Urdu, Arabic, Chinese, Japanese) har harf ke 2–4 bytes. Har encoding **bytes** par kaam karti hai, "huroof" par nahi, isi liye ghair English text ka Base64 ya URL-encoded output lamba hota hai. `od` (har Linux system par) bytes dikhata hai: `-tx1` hex me, `-tu1` 0–255 decimal me.

</Ur>
</Tr>

```bash
printf 'Hi!' | od -An -tx1
printf 'Hi!' | od -An -tu1
printf 'ありがとう' | od -An -tx1
printf 'ありがとう' | wc -c | sed 's/$/ bytes for 5 Japanese letters/'
```

```text output
 48 69 21
  72 105  33
 e3 81 82 e3 82 8a e3 81 8c e3 81 a8 e3 81 86
15 bytes for 5 Japanese letters
```

<Happened>
<Tr>
<En>`printf 'Hi!'` output three characters (no newline); `od -An -tx1` showed each byte in hex, `48 69 21`, and `-tu1` the same bytes in decimal: `72 105 33`, the ASCII codes of `H`, `i`, `!`. The Japanese word "arigatou" (5 letters, "thank you") became **15 bytes**: three per letter.</En>
<Ur>`printf 'Hi!'` ne teen huroof diye (nayi line nahi); `od -An -tx1` ne har byte hex me dikhaya, `48 69 21`, aur `-tu1` ne wahi bytes decimal me: `72 105 33`, `H`, `i`, `!` ke ASCII codes. Japanese lafz "arigatou" (5 huroof, "shukriya") **15 bytes** ban gaya: har harf ke teen.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Hexadecimal">

<Tr>
<En>

Hex writes each byte as **two** characters from `0–9 a–f` (one per 4 bits): `00` = 0, `0f` = 15, `ff` = 255. It's compact, exact and fixed-width, so you can count bytes by counting pairs. You'll see it in hashes and commit IDs, keys, MAC addresses (`3c:22:fb:...`), colours (`#1e90ff` = red 30, green 144, blue 255), dumps and escapes like `\x41`. Hex doubles the size (32 bytes → 64 characters) and is case-insensitive.

</En>
<Ur>

Hex har byte ko `0–9 a–f` ke **do** huroof me likhta hai (har 4 bits ka ek): `00` = 0, `0f` = 15, `ff` = 255. Ye mukhtasar, durust aur barabar chaurai wala hai, isliye jore gin kar bytes gin sakte hain. Ye hashes aur commit IDs, keys, MAC addresses (`3c:22:fb:...`), rang (`#1e90ff` = laal 30, hara 144, neela 255), dumps aur `\x41` jaise escapes me milta hai. Hex size dugna karta hai (32 bytes → 64 huroof) aur chhote bare huroof ka farq nahi.

</Ur>
</Tr>

```bash
printf 'Hi!' | od -An -tx1 | tr -d ' \n'; echo
python3 -c 'print(b"Hi!".hex(), bytes.fromhex("486921").decode())'
printf 'password123' | sha256sum | cut -c1-64
printf 'password123' | sha256sum | cut -d' ' -f1 | awk '{print length($0), "hex characters =", length($0)/2, "bytes"}'
```

```text output
486921
486921 Hi!
ef92b778bafe771e89245b89ecbc08a44a4e166c06659911881f383d4473e94f
64 hex characters = 32 bytes
```

<Happened>
<Tr>
<En>`tr -d ' \n'` removed `od`'s spaces, giving the usual compact `486921`. Python's `.hex()` encodes and `bytes.fromhex(...).decode()` decodes. A SHA-256 hash is 32 bytes, shown as 64 hex characters. (The hash itself isn't encoding: you can't get `password123` back from it. Only its **display** is hex.)</En>
<Ur>`tr -d ' \n'` ne `od` ke spaces hata kar aam mukhtasar `486921` diya. Python ka `.hex()` encode aur `bytes.fromhex(...).decode()` decode karta hai. SHA-256 hash 32 bytes ka hai, jo 64 hex huroof me dikhta hai. (Hash khud encoding nahi: is se `password123` wapas nahi milta. Sirf us ka **dikhawa** hex hai.)</Ur>
</Tr>
</Happened>

</Step>

<Step title="Base64: how it works">

<Tr>
<En>

Base64 takes 3 bytes (24 bits), splits them into four 6-bit groups, and writes each group (a number 0–63) as one character from `A–Z a–z 0–9 + /`. It uses only characters that survive every text system and is denser than hex: 4 characters per 3 bytes instead of 6. If the data isn't a multiple of 3 bytes, the last block gets `=` padding: 1 leftover byte → `==`, 2 → `=`. You'll never do this by hand, but seeing it once removes the mystery.

</En>
<Ur>

Base64 3 bytes (24 bits) le kar unhe chaar 6-bit groups me baant-ta hai, aur har group (0–63 ka number) ko `A–Z a–z 0–9 + /` ke ek harf se likhta hai. Ye sirf wo huroof istemal karta hai jo har text system me bach jate hain aur hex se ghana hai: 3 bytes ke 6 ke bajaye 4 huroof. Data 3 bytes ka multiple na ho to aakhri block me `=` padding lagti hai: 1 bacha byte → `==`, 2 → `=`. Ye kabhi haath se nahi karenge, lekin ek dafa dekhne se raaz khul jata hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import base64
data = b"Hi!"
bits = "".join(f"{b:08b}" for b in data)
print("bytes :", " ".join(f"{b:08b}" for b in data))
groups = [bits[i:i+6] for i in range(0, len(bits), 6)]
print("6-bit :", " ".join(groups))
alphabet = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/"
print("values:", " ".join(str(int(g, 2)) for g in groups))
print("chars :", "".join(alphabet[int(g, 2)] for g in groups))
for text in [b"Hi!", b"Hi", b"H"]:
    print(text, "->", base64.b64encode(text).decode())
PY
```

```text output
bytes : 01001000 01101001 00100001
6-bit : 010010 000110 100100 100001
values: 18 6 36 33
chars : SGkh
b'Hi!' -> SGkh
b'Hi' -> SGk=
b'H' -> SA==
```

<Happened>
<Tr>
<En>

- `f"{b:08b}"` wrote each byte as 8 binary digits: `H` = `01001000`, `i` = `01101001`, `!` = `00100001`.
- The 24 bits were cut into four 6-bit pieces: 18, 6, 36, 33.
- Looking those up in the alphabet gave `S` (18), `G` (6), `k` (36), `h` (33): **`SGkh`**, exactly what the library produces.
- `Hi` (2 bytes) ended with one `=`, and `H` (1 byte) with `==`. Padding tells the decoder how many real bytes the last block had.

</En>
<Ur>

- `f"{b:08b}"` ne har byte 8 binary hindson me likha: `H` = `01001000`, `i` = `01101001`, `!` = `00100001`.
- 24 bits chaar 6-bit tukron me kate: 18, 6, 36, 33.
- Inhe huroof ki fehrist me dekhne se `S` (18), `G` (6), `k` (36), `h` (33) mile: **`SGkh`**, bilkul wahi jo library deti hai.
- `Hi` (2 bytes) ek `=` par khatam hua, aur `H` (1 byte) `==` par. Padding decoder ko batati hai aakhri block me kitne asli bytes the.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Base64 on the command line, and its size cost">

<Tr>
<En>

`base64` encodes and `base64 -d` decodes; every language has the same functions (Python `base64`, Node `Buffer.from(x, "base64")`, browser `atob`/`btoa` for ASCII). You'll constantly decode values from configs, tokens, logs and API responses. Output is about **4/3 the size** of the input, which is why embedding big images as Base64 in HTML or JSON is usually a bad idea.

</En>
<Ur>

`base64` encode aur `base64 -d` decode karta hai; har zubaan me yahi functions hain (Python `base64`, Node `Buffer.from(x, "base64")`, browser me ASCII ke liye `atob`/`btoa`). Aap configs, tokens, logs aur API jawabon se values baar baar decode karenge. Output input ka takreeban **4/3** hota hai, isi liye bari tasveeren HTML ya JSON me Base64 bana kar daalna aam tor par bura khayal hai.

</Ur>
</Tr>

```bash
printf 'Hello, DevGuide' | base64
echo 'SGVsbG8sIERldkd1aWRl' | base64 -d; echo
head -c 3000 /dev/zero > image.bin
echo "3000 bytes become $(base64 -w0 image.bin | wc -c) Base64 characters"
```

```text output
SGVsbG8sIERldkd1aWRl
Hello, DevGuide
3000 bytes become 4000 Base64 characters
```

<Happened>
<Tr>
<En>The text encoded and decoded back (the trailing `echo` only adds a newline). `head -c 3000 /dev/zero` made a 3000-byte binary file as a stand-in for an image; `base64 -w0` encoded it on one line (`-w0` disables wrapping at 76 characters), and `wc -c` counted **4000** characters: 3000 × 4/3.</En>
<Ur>Text encode ho kar wapas decode hua (aakhri `echo` sirf nayi line jorta hai). `head -c 3000 /dev/zero` ne tasveer ki jagah 3000 byte ki binary file banayi; `base64 -w0` ne use ek line me encode kiya (`-w0` 76 huroof par line torna band karta hai), aur `wc -c` ne **4000** huroof gine: 3000 × 4/3.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Base64url: the URL-safe variant">

<Tr>
<En>

Standard Base64 uses `+`, `/` and `=`, which mean something in URLs and file names (`+` can become a space, `/` a path separator). **Base64url** writes `-` instead of `+` and `_` instead of `/`, and usually drops the `=` padding, so values fit into URLs, cookies and file names. Every part of a JWT is Base64url. A standard decoder often fails on `-`, `_` or missing padding, a common bug when hand-decoding tokens.

</En>
<Ur>

Aam Base64 `+`, `/` aur `=` istemal karta hai, jin ka URLs aur file names me matlab hota hai (`+` space ban sakta hai, `/` path ka hissa). **Base64url** `+` ki jagah `-` aur `/` ki jagah `_` likhta hai, aur aam tor par `=` padding hata deta hai, taa ke values URLs, cookies aur file names me fit hon. JWT ka har hissa Base64url hai. Aam decoder aksar `-`, `_` ya ghayab padding par fail hota hai, tokens haath se decode karte hue aam bug.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import base64
data = bytes([251, 255, 191, 62])
print("standard :", base64.b64encode(data).decode())
print("url-safe :", base64.urlsafe_b64encode(data).decode())
print("no '='   :", base64.urlsafe_b64encode(data).decode().rstrip("="))
PY
```

```text output
standard : +/+/Pg==
url-safe : -_-_Pg==
no '='   : -_-_Pg
```

<Happened>
<Tr>
<En>These four bytes were chosen so the standard alphabet produces `+` and `/`, which would break in a URL. Base64url wrote `-` and `_` instead, and JWT-style strings also strip the `=`.</En>
<Ur>Ye chaar bytes is liye chune gaye ke aam alphabet `+` aur `/` de, jo URL me toot jate. Base64url ne in ki jagah `-` aur `_` likhe, aur JWT andaaz ki strings `=` bhi hata deti hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="URL encoding and HTML escaping">

<Tr>
<En>

Each format has characters with special meaning, so you encode for the **right context** to keep data as data. **URL (percent) encoding** writes unsafe characters as `%` + two hex digits (`space` → `%20`, `<` → `%3C`, `&` → `%26`): a `&` in a search term must not start a new parameter. **HTML escaping** writes `< > & " '` as entities (`&lt;`…) so text is shown, not run. Use the library function for the exact context (Python `urllib.parse`, JavaScript `encodeURIComponent`, template engines like React and Jinja); never a home-made `replace()` chain.

</En>
<Ur>

Har format ke kuch huroof ka khaas matlab hota hai, isliye data ko data rakhne ke liye **sahi jagah ke mutabiq** encode karein. **URL (percent) encoding** na-mehfooz huroof ko `%` + do hex hindson me likhti hai (`space` → `%20`, `<` → `%3C`, `&` → `%26`): search term ka `&` naya parameter shuru na kare. **HTML escaping** `< > & " '` ko entities (`&lt;`…) me likhti hai taa ke text dikhe, chale nahi. Bilkul us jagah ke liye library function istemal karein (Python `urllib.parse`, JavaScript `encodeURIComponent`, React aur Jinja jaise template engines); ghar ka bana `replace()` silsila kabhi nahi.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from urllib.parse import quote, unquote, urlencode
import html
print(quote("price < 500 & city = Chicago/Houston"))
print(urlencode({"q": "café & chai", "page": 2}))
print(unquote("%E3%81%82%E3%82%8A%E3%81%8C%E3%81%A8%E3%81%86"))
print(html.escape('<script>alert("hi")</script>'))
PY
```

```text output
price%20%3C%20500%20%26%20city%20%3D%20Chicago/Houston
q=caf%C3%A9+%26+chai&page=2
ありがとう
&lt;script&gt;alert(&quot;hi&quot;)&lt;/script&gt;
```

<Happened>
<Tr>
<En>

- `quote` turned spaces into `%20`, `<` into `%3C`, `&` into `%26`, `=` into `%3D`, and left `/` alone because it's usually part of a path (`quote(x, safe="")` encodes it too).
- `urlencode` built a full query string: `é` became its two UTF-8 bytes `%C3%A9`, the form-value space became `+`, and the `&` inside the value was encoded so it doesn't split parameters.
- `unquote` decoded the UTF-8 bytes of the Japanese word from step 1.
- `html.escape` turned a script tag into harmless text the browser **shows** instead of running: the core of preventing XSS.

</En>
<Ur>

- `quote` ne spaces ko `%20`, `<` ko `%3C`, `&` ko `%26`, `=` ko `%3D` kiya, aur `/` ko chhor diya kyun ke wo aam tor par path ka hissa hota hai (`quote(x, safe="")` use bhi encode karta hai).
- `urlencode` ne poori query string banayi: `é` apne do UTF-8 bytes `%C3%A9` bana, form value ka space `+` bana, aur value ke andar ka `&` encode hua taa ke parameters na toot-ain.
- `unquote` ne qadam 1 ke Japanese lafz ke UTF-8 bytes decode kiye.
- `html.escape` ne script tag ko be-zarar text bana diya jo browser chalane ke bajaye **dikhata** hai: XSS se bachao ki jar.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A JWT is readable by anyone">

<Tr>
<En>

A **JWT** (JSON Web Token) has three Base64url parts separated by dots: `header.payload.signature`. The header and payload are just encoded JSON. JWTs are **signed**, not encrypted: the signature proves nobody changed the payload, but anyone holding the token can **read** it. So never put secrets or sensitive personal data in a JWT payload; if content must be hidden, use an encrypted token (JWE) or keep the data on the server.

</En>
<Ur>

**JWT** (JSON Web Token) ke teen Base64url hisse dots se alag hote hain: `header.payload.signature`. Header aur payload bas encoded JSON hain. JWTs **signed** hote hain, encrypted nahi: signature sabit karta hai payload kisi ne nahi badla, lekin token rakhne wala koi bhi use **parh** sakta hai. Isliye JWT payload me kabhi raaz ya hassas zaati data na daalein; mawad chhupana zaroori ho to encrypted token (JWE) istemal karein ya data server par rakhein.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import base64, hmac, hashlib, json

payload = b64url(json.dumps({"sub": "1042", "name": "Olivia", "role": "user", "exp": 1794326400}, separators=(",", ":")).encode())
signature = b64url(hmac.new(b"server-secret", f"{header}.{payload}".encode(), hashlib.sha256).digest())
token = f"{header}.{payload}.{signature}"
open("token.txt", "w").write(token)
print(token[:60] + "...")
PY
echo "--- decode the payload without any key:"
cut -d. -f2 token.txt | tr '_-' '/+' | base64 -d 2>/dev/null; echo
python3 - <<'PY'
import base64, json
part = open("token.txt").read().split(".")[1]
part += "=" * (-len(part) % 4)
print(json.loads(base64.urlsafe_b64decode(part)))
PY
```

<Step title="Kubernetes Secrets are only Base64">

<Tr>
<En>

Kubernetes `Secret` objects store values in Base64 under `data:`. Real protection: RBAC (who may read them), encryption at rest in etcd, and Sealed Secrets, SOPS or External Secrets so plaintext never lands in Git.

</En>
<Ur>

Kubernetes `Secret` objects values ko `data:` ke neeche Base64 me rakhte hain. <Step title="Encoding vs encryption vs hashing">

<Tr>
<En>

Three different jobs. **Encoding** changes the representation, reversible by anyone. **Encryption** hides the content, reversible only **with the key**. **Hashing** makes a fixed-size fingerprint that **can't** be reversed. Mixing them up causes real vulnerabilities: "encrypting" passwords with Base64, "hashing" data you need to read back, or storing passwords with reversible encryption. Ask: "Does reading this need a secret?" If not, it's encoding, not protection.

</En>
<Ur>

Teen alag kaam. **Encoding** shakal badalti hai, koi bhi ulat sakta hai. **Encryption** mawad chhupati hai, sirf **key ke saath** ulti hoti hai. **Hashing** barabar size ka fingerprint banati hai jo ulta **nahi** ho sakta. Inhe milana asli kamzoriyan paida karta hai: Base64 se passwords "encrypt" karna, wo data "hash" karna jo wapas parhna ho, ya passwords ulti ho sakne wali encryption se rakhna. Poochein: "kya isay parhne ke liye raaz chahiye?" Nahi, to ye encoding hai, hifazat nahi.

</Ur>
</Tr>

```bash
printf 'Transfer $500 to Sam' > message.txt
echo "encoded  : $(base64 message.txt)"
echo "decoded  : $(base64 message.txt | base64 -d)"
openssl enc -aes-256-cbc -pbkdf2 -S 0102030405060708 -pass pass:CorrectHorse -in message.txt -out message.enc
echo "encrypted: $(base64 -w0 message.enc)"
echo "wrong key: $(openssl enc -d -aes-256-cbc -pbkdf2 -S 0102030405060708 -pass pass:WrongGuess -in message.enc 2>&1 | head -1)"
echo "right key: $(openssl enc -d -aes-256-cbc -pbkdf2 -S 0102030405060708 -pass pass:CorrectHorse -in message.enc)"
echo "hashed   : $(sha256sum message.txt | cut -c1-16)... (one-way: there is no 'decrypt')"
```

wrong key: bad decrypt
right key: Transfer $500 to Sam
hashed   : 151f70c6b02ac4f6... (one-way: there is no 'decrypt')

<Happened>
<Tr>
<En>

- **Encoding:** `base64` changed the look and `base64 -d` got the message back. No secret involved.
- **Encryption:** `openssl enc -aes-256-cbc` encrypted with AES-256; `-pbkdf2` turned the password into a key properly, and `-S` fixed the salt only so the output repeats (normally it's random). The ciphertext is binary, so we **Base64 it to display it**: encryption protects, encoding transports.
- With the wrong password, decryption failed (`bad decrypt`); with the right one, the message came back.
- **Hashing:** SHA-256 made a fingerprint, and there's no command to turn it back into the message.

| | Encoding | Encryption | Hashing |
| --- | --- | --- | --- |
| Purpose | Represent data safely in another format | Keep data secret | Fingerprint / verify data |
| Reversible? | Yes, by anyone | Yes, only with the key | No |
| Needs a key? | No | Yes | No (HMAC uses a key for authenticity) |
| Output size | Grows (hex ×2, Base64 ×4/3) | About the input size | Fixed (SHA-256: 32 bytes) |
| Examples | Base64, hex, URL, HTML entities | AES-GCM, ChaCha20, RSA | SHA-256, bcrypt, Argon2 |
| Wrong use | "Securing" passwords with Base64 | Storing user passwords encrypted | MD5/SHA-256 alone for passwords |

</En>
<Ur>

- **Encoding:** `base64` ne shakal badli aur `base64 -d` ne paigham wapas diya. Koi raaz shamil nahi.
- **Encryption:** `openssl enc -aes-256-cbc` ne AES-256 se encrypt kiya; `-pbkdf2` ne password ko durust tareeqe se key banaya, aur `-S` ne salt sirf is liye qaim kiya ke output dohraye (aam tor par random hota hai). Ciphertext binary hai, isliye **dikhane ke liye Base64** kiya: encryption hifazat karti hai, encoding le jati hai.
- Ghalat password se decryption fail hui (`bad decrypt`); sahi se paigham wapas aaya.
- **Hashing:** SHA-256 ne fingerprint banaya, aur use wapas paigham banane wali koi command nahi.

| | Encoding | Encryption | Hashing |
| --- | --- | --- | --- |
| Maqsad | Data ko doosre format me mehfooz dikhana | Data raaz rakhna | Fingerprint / tasdeeq |
| Ulta ho sakta? | Haan, koi bhi | Haan, sirf key se | Nahi |
| Key chahiye? | Nahi | Haan | Nahi (HMAC asliyat ke liye key leta hai) |
| Output size | Barhta hai (hex ×2, Base64 ×4/3) | Input jitna | Muqarrar (SHA-256: 32 bytes) |
| Misaalen | Base64, hex, URL, HTML entities | AES-GCM, ChaCha20, RSA | SHA-256, bcrypt, Argon2 |
| Ghalat istemal | Base64 se passwords "mehfooz" | User passwords encrypted rakhna | Passwords ke liye akela MD5/SHA-256 |

</Ur>

<Step title="Encoding as camouflage: how attackers use it">

<Tr>
<En>

Attackers encode payloads so simple filters and human reviewers miss them: Base64-wrapped shell commands, PowerShell's `-EncodedCommand` (Base64 of UTF-16LE text), hex strings, and **double URL encoding** (`%252e` → `%2e` → `.`). A filter that blocks `../` but checks input **before** the app decodes it can be bypassed. Defenders decode in SIEM rules, use CyberChef for manual analysis, and **canonicalise** input (decode fully, once, in one place) before validating. Below: a PowerShell-style encoded command, created and decoded. In UTF-16LE every English character is followed by a zero byte, which is why such strings contain many `A`s.

</En>
<Ur>

Hamla awar payloads encode karte hain taa ke saade filters aur insaani reviewers chook jayen: Base64 me lipti shell commands, PowerShell ka `-EncodedCommand` (UTF-16LE text ka Base64), hex strings, aur **double URL encoding** (`%252e` → `%2e` → `.`). Jo filter `../` rokta hai lekin app ke decode karne se **pehle** input check karta hai, use chhora ja sakta hai. Difa karne wale SIEM rules me decode karte hain, haath ke tajziye ke liye CyberChef istemal karte hain, aur validate karne se pehle input **canonicalise** karte hain (poora, ek dafa, ek jagah decode). Neeche: PowerShell andaaz ki encoded command, banayi aur decode ki gayi. UTF-16LE me har English harf ke baad zero byte hota hai, isi liye aisi strings me bohot se `A` hote hain.

</Ur>
</Tr>

<Compare>
<Bad title="'Encrypting' a key with Base64">

```text

```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Putting sensitive data in JWT payloads**, assuming nobody can read them.
- **Decoding Base64url with a standard decoder** and getting errors because of `-`, `_` or missing padding.
- **Forgetting the text encoding:** Base64 gives **bytes**; decoding them with the wrong character set (UTF-8 vs UTF-16LE) gives garbage.
- **Embedding large files as Base64** in JSON or HTML: 33% bigger, slower, and not cached separately.
- **Writing your own URL or HTML escaping** with `replace()` instead of the library function for that context.
- **Validating input before decoding it** (or decoding it twice in different places), which opens double-encoding bypasses.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **JWT payloads me hassas data**, ye samajh kar ke koi nahi parh sakta.
- **Base64url ko aam decoder se decode karna** aur `-`, `_` ya ghayab padding ki wajah se errors.
- **Text encoding bhoolna:** Base64 **bytes** deta hai; ghalat character set (UTF-8 bamuqabla UTF-16LE) se decode karne par kachra milta hai.
- **Bari files Base64 bana kar** JSON ya HTML me: 33% bari, sust, aur alag cache nahi hotin.
- **Apni URL ya HTML escaping** `replace()` se likhna, us jagah ke library function ke bajaye.
- **Decode se pehle input validate karna** (ya do jagah decode karna), jis se double-encoding bypass khulte hain.

</Ur>
</Tr>

import base64, binascii, re
from urllib.parse import unquote

def try_decode(value):
    steps = []
    for _ in range(5):                                   # at most 5 layers
        if "%" in value and unquote(value) != value:
            value = unquote(value); steps.append(("url", value)); continue
        if re.fullmatch(r"(?:[0-9a-fA-F]{2}){4,}", value):
            try:
                value = bytes.fromhex(value).decode(); steps.append(("hex", value)); continue
            except UnicodeDecodeError:
                pass
        if re.fullmatch(r"[A-Za-z0-9+/]{8,}={0,2}", value) and len(value) % 4 == 0:
            try:
                value = base64.b64decode(value, validate=True).decode(); steps.append(("base64", value)); continue
            except (binascii.Error, UnicodeDecodeError):
                pass
        break
    return steps

for line in open("suspicious.log"):
    ip, method, target = line.split()
    raw = target.split("=", 1)[1]
    print(f"{ip}  {method:4} {raw[:40]}")
    for kind, text in try_decode(raw):
        print(f"      {kind:6} -> {text}")

<DeepDive title="Real world: the 'encrypted' key and the encoded PowerShell">

During a code review at a payments startup, a security engineer finds `const API_KEY = atob("c2tfbGl2ZV81MWg...")` in a mobile app. The developer says the key is "encrypted". It's Base64: decoding it gives a **live payment-provider secret key**, and anyone who downloads the app can extract it in seconds. The team rotates the key immediately, moves every call that needs the secret to their backend (the app only gets short-lived, limited tokens), and adds a gitleaks rule plus a CI check that flags `atob(` or `base64` near words like `key` or `secret`.

A month later the SOC sees `powershell.exe -nop -w hidden -enc JABjAD0A...` on an employee laptop. Decoding the UTF-16LE Base64 in CyberChef reveals a command downloading malware from a lookalike domain, delivered through a phishing Excel file. The encoded string itself becomes an indicator the team searches for across all machines.

</DeepDive>

<DeepDive title="Security lens">

If it can be decoded without a key, it isn't protected. Encode for transport, encrypt for secrecy, hash for verification.

- **Secrets:** treat any Base64-encoded secret as plaintext; store secrets in secret managers and encrypt them at rest.
- **Tokens:** JWT payloads are public. Verify the signature and algorithm on the server, keep payloads minimal, avoid sensitive personal data.
- **Canonicalisation:** decode input fully into its canonical form **once**, then validate. Inconsistent decoding between a WAF, a proxy and the app is a classic bypass.
- **Output encoding:** encode for the exact output context (HTML body, attribute, JavaScript, URL, SQL via parameters). Context-aware output encoding is the main defence against XSS.
- **Detection:** decode Base64, hex and UTF-16LE in logs and scripts; look for encoded blobs in command lines (`-enc`, `base64 -d | bash`, `FromBase64String`, `eval(atob(...))`).
- **Data exposure:** Base64 in URLs and logs (Basic auth headers, tokens) is still sensitive data. Mask it in logs.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between encoding, encryption and hashing?">
Encoding transforms data into another representation for compatibility, such as Base64 or URL encoding, and anyone can reverse it without a key. Encryption transforms data so that only someone with the right key can recover it, providing confidentiality. Hashing produces a fixed-size fingerprint that cannot be reversed and is used for integrity checks and, with slow salted algorithms, for password storage.
</QA>

<QA q="How does Base64 work and why is the output larger than the input?">
Base64 splits the input into groups of three bytes, or 24 bits, divides them into four 6-bit values and maps each value to one of 64 printable characters, adding equals-sign padding when the last group is incomplete. Because every three bytes become four characters, the output is about 33 percent larger.
</QA>

<QA q="Is a JWT encrypted?">
A standard JWT is signed, not encrypted. Its header and payload are Base64url-encoded JSON that anyone holding the token can decode and read. The signature only ensures the token was issued by someone with the key and has not been modified. Sensitive data should not be put in the payload, or an encrypted JWE should be used.
</QA>

<QA q="Are Kubernetes Secrets secure because their values are Base64-encoded?">
No. Base64 is only an encoding and can be decoded by anyone who can read the Secret. Protection comes from RBAC restricting who can read Secrets, encryption at rest in etcd, and keeping plaintext Secrets out of Git with tools such as Sealed Secrets, SOPS or an external secret manager.
</QA>

<QA q="What is double encoding and why does it matter for security?">
Double encoding encodes already encoded data again, for example a percent sign encoded as %25 so that %252e becomes %2e and then a dot. If a security filter decodes input once but the application decodes it again later, attackers can slip payloads such as path traversal sequences past the filter. Input should be canonicalised fully once before validation.
</QA>

</DeepDive>

  <Term name="Encoding">Reversible change of representation, without a key.</Term>

  <Term name="Hashing">One-way fixed-size fingerprint of data.</Term>
  <Term name="Double encoding">Encoding data twice to evade filters.</Term>
  <Term name="Canonicalisation">Decoding input into a single standard form before validation.</Term>
