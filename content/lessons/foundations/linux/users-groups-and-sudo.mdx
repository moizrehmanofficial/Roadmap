<BigIdea>
<Tr>
<En>
On Linux, **every person and every program is a user**, and users only get the access they need. **root** is the all-powerful admin. Instead of working as root, you borrow its power for one command at a time with **sudo**, and every borrow is written down.
</En>
<Ur>
Linux par **har insaan aur har program ek user hai**, aur users ko sirf utni hi ijazat milti hai jitni zaroorat ho. **root** sab se taqatwar admin hai. Root ban kar kaam karne ke bajaye aap **sudo** se ek waqt me ek command ke liye us ki taqat udhaar lete hain, aur har udhaar likha jata hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **User**: an account that owns files and runs programs (`alex`, `www-data`). Linux really knows it by a number, the **UID**.
- **Group**: a team of users who share the same access (`sudo`, `docker`, `developers`).
- **root** (UID 0): the admin who can do **anything**.
- **sudo**: "run **this one command** as root", if you're allowed.

</En>
<Ur>

- **User**: ek account jo files ka maalik hota hai aur programs chalata hai (`alex`, `www-data`). Linux ise asal me ek number se pehchanta hai, **UID**.
- **Group**: users ki team jo ek jaisi ijazat share karti hai (`sudo`, `docker`, `developers`).
- **root** (UID 0): wo admin jo **kuch bhi** kar sakta hai.
- **sudo**: "**ye ek command** root ban kar chalao", agar aap ko ijazat ho.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Damage control**: if the web server gets hacked, the attacker is stuck as `www-data`, not root.
- **Who did what**: personal accounts + sudo logs show exactly who ran what.
- **"Permission denied"** errors are almost always about which user a program runs as.

</En>
<Ur>

- **Nuqsan ki had**: agar web server hack ho jaye, to hacker `www-data` me phansa rehta hai, root nahi banta.
- **Kis ne kya kiya**: zaati accounts + sudo logs bilkul dikhate hain kis ne kya chalaya.
- **"Permission denied"** errors taqreeban hamesha is baare me hote hain ke program kis user ke taur par chal raha hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- a new teammate needs access to a server
- giving someone admin rights
- creating an account for your app
- removing someone who left the team

</En>
<Ur>

- naye saathi ko server ki access chahiye
- kisi ko admin ki ijazat dena
- apni app ke liye account banana
- team chhorne wale ko hatana

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

- `id`: who am I and which groups am I in?
- `sudo adduser sam`: create a user
- `sudo usermod -aG sudo sam`: add to a group (**never forget `-a`**)
- `sudo command`: run one command as root

</En>
<Ur>

- `id`: main kaun hoon aur kin groups me hoon?
- `sudo adduser sam`: user banao
- `sudo usermod -aG sudo sam`: group me shamil karo (**`-a` kabhi na bhoolein**)
- `sudo command`: ek command root ban kar chalao

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of an **office building with key cards**:

- Each employee has a card (a **user**) that opens only certain doors.
- Departments (**groups**) share access: everyone in Accounts can open the Accounts room.
- The **building owner** (**root**) has a **master key** that opens every door.
- Wise managers don't carry the master key all day. They **borrow** it for one job, and the security desk **writes down** who borrowed it and when. That borrowing is **sudo**.

</En>
<Ur>

**Key cards wali office building** ka socho:

- Har mulazim ke paas card hai (**user**) jo sirf kuch darwaze kholta hai.
- Shobay (**groups**) access share karte hain: Accounts ka har banda Accounts room khol sakta hai.
- **Building ka maalik** (**root**) ke paas **master key** hai jo har darwaza kholti hai.
- Samajhdar managers saara din master key le kar nahi ghoomte. Wo ek kaam ke liye **udhaar** lete hain, aur security desk **likh leti** hai ke kis ne kab li. Yahi udhaar **sudo** hai.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **UID / GID** | The numbers Linux really uses for a user / group | `0` = root, `1000` = first normal user |
| **Primary group** | The group your new files get by default | usually the same name as you |
| **Supplementary groups** | Extra groups you belong to | `docker`, `sudo` |
| **Service account** | A user for a program, not a person; can't log in | `www-data`, `postgres` |
| **Password hash** | A scrambled form of a password, not the password itself | stored in `/etc/shadow` |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **UID / GID** | Wo numbers jo Linux asal me user / group ke liye istemal karta hai | `0` = root, `1000` = pehla aam user |
| **Primary group** | Wo group jo aap ki nayi files ko khud ba khud milta hai | aam taur par aap ke naam jaisa |
| **Supplementary groups** | Izafi groups jin me aap hain | `docker`, `sudo` |
| **Service account** | Program ke liye user, insaan ke liye nahi; login nahi kar sakta | `www-data`, `postgres` |
| **Password hash** | Password ki ulti pulti shakal, asal password nahi | `/etc/shadow` me rakha jata hai |

</Ur>
</Tr>

## Where accounts live

<Tr>
<En>

| File | What's in it | Who can read it |
| --- | --- | --- |
| `/etc/passwd` | One line per user: name, UID, GID, home, shell | Everyone |
| `/etc/group` | One line per group, with its members | Everyone |
| `/etc/shadow` | Password hashes | **root only** |
| `/etc/sudoers` (+ `/etc/sudoers.d/`) | Who may use sudo, for what | **root only** |

</En>
<Ur>

| File | Is me kya hai | Kaun parh sakta hai |
| --- | --- | --- |
| `/etc/passwd` | Har user ki ek line: naam, UID, GID, home, shell | Har koi |
| `/etc/group` | Har group ki ek line, members ke saath | Har koi |
| `/etc/shadow` | Password hashes | **Sirf root** |
| `/etc/sudoers` (+ `/etc/sudoers.d/`) | Kaun sudo istemal kar sakta hai, kis liye | **Sirf root** |

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Who am I? whoami and id">

<Tr>
<En>

`whoami` prints your user name. `id` prints your UID, your main group and **all** your groups. When you see "Permission denied", start here.

</En>
<Ur>

`whoami` aap ka user naam print karta hai. `id` aap ka UID, main group aur aap ke **saare** groups print karta hai. "Permission denied" dikhe to yahin se shuru karein.

</Ur>
</Tr>

```bash
id root
whoami
```

```text output
uid=0(root) gid=0(root) groups=0(root)
root
```

<Happened>
<Tr>
<En>This example ran as root, so it says `uid=0(root)`. On your own machine you'd see something like `uid=1000(alex) gid=1000(alex) groups=1000(alex),27(sudo)`: Alex is user 1000, and also in the `sudo` group (an admin).</En>
<Ur>Ye misaal root ke taur par chali, isliye `uid=0(root)` likha. Aap ki apni machine par kuch aisa dikhega: `uid=1000(alex) gid=1000(alex) groups=1000(alex),27(sudo)`: Alex user 1000 hai, aur `sudo` group me bhi (yani admin).</Ur>
</Tr>
</Happened>

</Step>

<Step title="Reading /etc/passwd">

<Tr>
<En>

`/etc/passwd` has one line per account, with **seven** parts separated by `:`. Here's how to read one:

</En>
<Ur>

`/etc/passwd` me har account ki ek line hai, **saat** hisson ke saath jo `:` se alag hain. Ise aise parhein:

</Ur>
</Tr>

```text
alex:x:1000:1000:Alex Carter:/home/alex:/bin/bash
 │   │  │    │      │            │          └ login shell
 │   │  │    │      │            └ home folder
 │   │  │    │      └ comment (full name)
 │   │  │    └ primary GID
 │   │  └ UID
 │   └ x = password is stored in /etc/shadow
 └ user name
```

```bash
awk -F: '$3 == 0 {print "UID 0 accounts:", $1}' /etc/passwd
awk -F: '$7 ~ /nologin|false/ {n++} END {print (n > 0 ? "some accounts cannot log in (service accounts)" : "none")}' /etc/passwd
```

```text output
UID 0 accounts: root
some accounts cannot log in (service accounts)
```

<Happened>
<Tr>
<En>

- The first command lists every account with UID 0. Only **root** should ever be there. Another UID-0 account is a classic sign that a server was **hacked**.
- The second counts accounts whose shell is `nologin` or `false`: these are **service accounts** for programs, and they can't log in.

</En>
<Ur>

- Pehli command har UID 0 wala account dikhati hai. Wahan sirf **root** hona chahiye. Koi aur UID-0 account is baat ki mashhoor nishani hai ke server **hack** hua.
- Doosri un accounts ko ginti hai jin ka shell `nologin` ya `false` hai: ye programs ke **service accounts** hain, aur login nahi kar sakte.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Creating a user">

<Tr>
<En>

Every **person** gets their **own** account. Never share logins.

`useradd -m -s /bin/bash -c "Full Name" name`:

- `-m` = make a home folder
- `-s` = which shell
- `-c` = a comment (full name)

On Ubuntu, `adduser name` is a friendlier version that asks questions. On a real server, put `sudo` in front.

</En>
<Ur>

Har **insaan** ka **apna** account ho. Kabhi login share na karein.

`useradd -m -s /bin/bash -c "Poora Naam" naam`:

- `-m` = home folder banao
- `-s` = kaun sa shell
- `-c` = tabsira (poora naam)

Ubuntu par `adduser naam` zyada dostana version hai jo sawal poochta hai. Asli server par aage `sudo` lagayen.

</Ur>
</Tr>

```bash
useradd -m -s /bin/bash -c "Sam Brown" sam
getent passwd sam | cut -d: -f1,5,6,7
ls -ld /home/sam | awk '{print $1, $3, $4, $9}'
```

```text output
sam:Sam Brown:/home/sam:/bin/bash
drwxr-x--- sam sam /home/sam
```

<Happened>
<Tr>
<En>

- Sam's account exists with his name, home folder `/home/sam` and the Bash shell.
- `/home/sam` is owned by user `sam` and group `sam`. A **group with the same name** was created automatically.
- `drwxr-x---`: only Sam (and his group) can look inside.

</En>
<Ur>

- Sam ka account us ke naam, home folder `/home/sam` aur Bash shell ke saath ban gaya.
- `/home/sam` ka maalik user `sam` aur group `sam` hai. **Usi naam ka group** khud ba khud ban gaya.
- `drwxr-x---`: sirf Sam (aur us ka group) andar dekh sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Groups: access for a whole team">

<Tr>
<En>

Giving access to a **group** ("developers can deploy") is easier than giving it to each person.

- `groupadd developers`: create a group
- `usermod -aG developers sam`: add Sam to it
- New groups take effect at the user's **next login**.

</En>
<Ur>

**Group** ko ijazat dena ("developers deploy kar sakte hain") har shakhs ko alag dene se aasaan hai.

- `groupadd developers`: group banao
- `usermod -aG developers sam`: Sam ko shamil karo
- Naye groups user ke **agle login** par lagu hote hain.

</Ur>
</Tr>

```bash
groupadd developers
usermod -aG developers sam
id -nG sam
getent group developers | sed 's/:[0-9]*:/:<GID>:/'
```

```text output
sam developers
developers:x:<GID>:sam
```

<Callout type="danger" title="Never forget the -a">
<Tr>
<En>`-a` means **append** (add to the list). `usermod -G developers sam` **without** `-a` **removes** Sam from every other extra group, such as `sudo`. Always type `usermod -aG`.</En>
<Ur>`-a` ka matlab **append** (list me shamil karo). `-a` ke **baghair** `usermod -G developers sam` Sam ko har doosre izafi group se **nikal deta hai**, jaise `sudo`. Hamesha `usermod -aG` likhein.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Passwords and /etc/shadow">

<Tr>
<En>

Linux never stores your actual password. It stores a **hash**: a one-way scrambled version. Those hashes live in `/etc/shadow`, which only root can read, so normal users can't copy them and try to crack them.

- `passwd user`: set a password
- `passwd -l user`: lock it
- On servers, prefer **SSH keys** and turn password login off.

</En>
<Ur>

Linux kabhi aap ka asal password save nahi karta. Ye ek **hash** rakhta hai: ek tarfa ulti pulti shakal. Ye hashes `/etc/shadow` me hain, jise sirf root parh sakta hai, taa ke aam users inhe copy kar ke torne ki koshish na kar sakein.

- `passwd user`: password set karo
- `passwd -l user`: lock karo
- Servers par **SSH keys** ko tarjeeh dein aur password login band karein.

</Ur>
</Tr>

```bash
stat -c '%A %U %n' /etc/passwd /etc/shadow
passwd -S sam | awk '{print $1, ($2 == "L" ? "password locked/not set" : $2)}'
```

```text output
-rw-r--r-- root /etc/passwd
-rw-r----- root /etc/shadow
sam password locked/not set
```

<Happened>
<Tr>
<En>

- `/etc/passwd` is `rw-r--r--`: **everyone** can read it (it has no passwords).
- `/etc/shadow` is `rw-r-----`: others can't read it at all.
- Sam has no password yet, so he can't log in with one. That's fine when SSH keys are used.

</En>
<Ur>

- `/etc/passwd` `rw-r--r--` hai: **har koi** parh sakta hai (is me passwords nahi).
- `/etc/shadow` `rw-r-----` hai: doosre bilkul nahi parh sakte.
- Sam ka abhi password nahi, isliye wo password se login nahi kar sakta. SSH keys istemal hon to ye theek hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Why not just be root?">

<Tr>
<En>

root skips almost every permission check. That means:

- **one typo** as root can delete the whole system
- **one hacked program** running as root gives the attacker everything
- a **shared root login** hides **who** did what

So: turn off direct root login over SSH (`PermitRootLogin no`), give each person their own account, and use **sudo**.

</En>
<Ur>

root taqreeban har permission check chhor deta hai. Is ka matlab:

- root ke taur par **ek typo** poora system mita sakta hai
- root ke taur par chalne wala **ek hack shuda program** hacker ko sab kuch de deta hai
- **share shuda root login** chhupa deta hai ke **kis ne** kya kiya

To: SSH par seedha root login band karein (`PermitRootLogin no`), har shakhs ko apna account dein, aur **sudo** istemal karein.

</Ur>
</Tr>

</Step>

<Step title="sudo: one command, with permission, written down">

<Tr>
<En>

`sudo` = "**s**ubstitute **u**ser **do**". It runs **one** command as root (or another user), after checking you're allowed and asking **your own** password. Every use is **logged**.

- `sudo command`: as root
- `sudo -u postgres psql`: as another user
- `sudo -l`: "what am I allowed to run?"
- `sudo -i`: a full root shell (use rarely)

Members of the `sudo` group (Ubuntu) or `wheel` group (Red Hat) can use it.

</En>
<Ur>

`sudo` = "**s**ubstitute **u**ser **do**". Ye **ek** command root (ya kisi aur user) ke taur par chalata hai, check kar ke ke aap ko ijazat hai aur **aap ka apna** password pooch kar. Har istemal **likha** jata hai.

- `sudo command`: root ke taur par
- `sudo -u postgres psql`: kisi aur user ke taur par
- `sudo -l`: "mujhe kya chalane ki ijazat hai?"
- `sudo -i`: poora root shell (kam istemal karein)

`sudo` group (Ubuntu) ya `wheel` group (Red Hat) ke members ise istemal kar sakte hain.

</Ur>
</Tr>

```bash
sudo -u sam whoami
sudo -u sam id -nG
sudo -u sam touch /root/test 2>&1 | sed 's/^touch: //'
```

```text output
sam
sam developers
cannot touch '/root/test': Permission denied
```

<Happened>
<Tr>
<En>

- `sudo -u sam` ran each command **as Sam**.
- As Sam, the command has only **Sam's** permissions: it can't write into root's home folder.

</En>
<Ur>

- `sudo -u sam` ne har command **Sam ke taur par** chalayi.
- Sam ke taur par command ke paas sirf **Sam ki** ijazat hai: wo root ke home folder me likh nahi sakti.

</Ur>
</Tr>
</Happened>

<Tr>
<En>

**su vs sudo:**

| | `su - user` | `sudo command` |
| --- | --- | --- |
| Password asked | The **target** user's | **Your own** |
| Scope | A whole shell | One command |
| Control | All or nothing | Fine-grained rules |
| Logging | Little | Every command logged |
| Recommended | Rarely | Yes |

</En>
<Ur>

**su bamuqabla sudo:**

| | `su - user` | `sudo command` |
| --- | --- | --- |
| Kis ka password | **Target** user ka | **Aap ka apna** |
| Daira | Poora shell | Ek command |
| Control | Sab ya kuch nahi | Bareek qaide |
| Record | Thora | Har command likhi jati hai |
| Mashwara | Kabhi kabhar | Haan |

</Ur>
</Tr>

</Step>

<Step title="The sudoers file and visudo">

<Tr>
<En>

The **sudoers** rules say **who** may run **which** commands as **whom**. You can give exactly the power needed: for example, a deploy account that may **only** restart the app.

**Always** edit with `sudo visudo`. It checks for mistakes before saving. A broken sudoers file can lock **everyone** out of sudo.

</En>
<Ur>

**sudoers** ke qaide batate hain ke **kaun** **kaun si** commands **kis** ke taur par chala sakta hai. Aap bilkul utni hi taqat de sakte hain jitni chahiye: misaal ke taur par deploy account jo **sirf** app restart kar sake.

**Hamesha** `sudo visudo` se edit karein. Ye save se pehle ghaltiyan check karta hai. Toota hua sudoers file **sab ko** sudo se bahar kar sakta hai.

</Ur>
</Tr>

```text
# who   where=(as whom)  commands
%sudo   ALL=(ALL:ALL)    ALL                                   ← members of group sudo: everything
deploy  ALL=(root)       NOPASSWD: /usr/bin/systemctl restart shop.service
                          ↑ deploy may run exactly this one command as root, without a password
```

```bash
echo 'deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart shop.service' > deploy.sudoers
visudo -cf deploy.sudoers | sed 's/^deploy.sudoers: //'
echo 'deploy ALL=(root) NOPASSWD /usr/bin/systemctl' > broken.sudoers
visudo -cf broken.sudoers > /dev/null 2>&1 || echo "broken.sudoers: syntax error caught before installing"
```

```text output
parsed OK
broken.sudoers: syntax error caught before installing
```

<Happened>
<Tr>
<En>

- `visudo -cf file` **checks** a sudoers file without installing it.
- The first rule is correct: "parsed OK".
- The second is missing the `:` after `NOPASSWD`, and `visudo` catches it **before** it could lock anyone out.

</En>
<Ur>

- `visudo -cf file` sudoers file ko install kiye baghair **check** karta hai.
- Pehla qaida sahi hai: "parsed OK".
- Doosre me `NOPASSWD` ke baad `:` nahi, aur `visudo` ise **pehle hi** pakar leta hai, is se pehle ke koi bahar ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Service accounts: users for programs">

<Tr>
<En>

Every app on a server should run as its **own** user, with **no password**, **no login shell** and often **no home folder**. If the app is hacked, the damage stays inside that one account.

Examples: `www-data` (nginx), `postgres`, `redis`, or your own `shopapp`. System accounts get UIDs below 1000.

</En>
<Ur>

Server ki har app ko **apne** user ke taur par chalna chahiye, **baghair password**, **baghair login shell** aur aksar **baghair home folder**. Agar app hack ho, to nuqsan usi ek account tak rehta hai.

Misalein: `www-data` (nginx), `postgres`, `redis`, ya aap ka apna `shopapp`. System accounts ko 1000 se kam UIDs milte hain.

</Ur>
</Tr>

```bash
useradd --system --no-create-home --shell /usr/sbin/nologin shopapp
getent passwd shopapp | awk -F: '{print "user:", $1, "| system UID below 1000:", ($3 < 1000 ? "yes" : "no"), "| shell:", $7}'
su -s /bin/sh -c 'echo hi' shopapp > /dev/null 2>&1 && echo "commands can run as shopapp (for services)"
su - shopapp 2>&1 | grep -qi 'not available' && echo "but interactive login is refused"
```

```text output
user: shopapp | system UID below 1000: yes | shell: /usr/sbin/nologin
commands can run as shopapp (for services)
but interactive login is refused
```

<Happened>
<Tr>
<En>

- `shopapp` is a system user with shell `nologin`.
- A service can still **run commands** as `shopapp`.
- But nobody can **log in** as it: the login is refused.

</En>
<Ur>

- `shopapp` `nologin` shell wala system user hai.
- Service phir bhi `shopapp` ke taur par **commands chala** sakti hai.
- Lekin koi us ke taur par **login** nahi kar sakta: login rad ho jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Removing and locking users">

<Tr>
<En>

Old accounts with working SSH keys are a common way in for attackers. When someone leaves:

1. **Lock** first: `usermod -L user`, set the shell to `nologin`, remove `~/.ssh/authorized_keys`.
2. **Delete** later: `userdel -r user` (also removes the home folder).

</En>
<Ur>

Chalti SSH keys wale purane accounts hackers ke andar aane ka aam raasta hain. Jab koi chala jaye:

1. Pehle **lock**: `usermod -L user`, shell `nologin` karein, `~/.ssh/authorized_keys` hata dein.
2. Baad me **delete**: `userdel -r user` (home folder bhi hata deta hai).

</Ur>
</Tr>

```bash
userdel -r sam 2>/dev/null; userdel shopapp; groupdel developers
for u in sam shopapp; do getent passwd "$u" > /dev/null && echo "$u still exists" || echo "$u removed"; done
```

```text output
sam removed
shopapp removed
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="usermod -G without -a">

```text
sudo usermod -G docker sam     # Sam just lost his sudo access!
```

</Bad>
<Good title="Always -aG">

```text
sudo usermod -aG docker sam
```

</Good>
</Compare>

<Compare>
<Bad title="Running apps as root">

<Tr>
<En>`sudo npm start`, `sudo node server.js`, or containers with no `USER` line. One bug and the attacker owns the server.</En>
<Ur>`sudo npm start`, `sudo node server.js`, ya baghair `USER` line ke containers. Ek bug aur hacker server ka maalik.</Ur>
</Tr>

</Bad>
<Good title="A user per app">

<Tr>
<En>Create a service account (`useradd --system ... shopapp`) and run the app as that user.</En>
<Ur>Service account banayen (`useradd --system ... shopapp`) aur app usi user ke taur par chalayen.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="One shared login for everyone">

<Tr>
<En>Everyone logs in as `ubuntu`. No one knows who did what, and when someone leaves you must change access for everybody.</En>
<Ur>Har koi `ubuntu` ke taur par login karta hai. Kisi ko nahi pata kis ne kya kiya, aur jab koi jaye to sab ki access badalni parti hai.</Ur>
</Tr>

</Bad>

<DeepDive title="Real world: setting up a fresh Ubuntu server">

```bash
# As root on first login
adduser alex && usermod -aG sudo alex
mkdir -p /home/alex/.ssh && cp ~/.ssh/authorized_keys /home/alex/.ssh/
chown -R alex:alex /home/alex/.ssh && chmod 700 /home/alex/.ssh && chmod 600 /home/alex/.ssh/authorized_keys

# A service user that owns the app and runs it
useradd --system --no-create-home --shell /usr/sbin/nologin app
chown -R app:app /srv/app

# A deploy account for CI that may only restart the service
adduser --disabled-password --gecos "" deploy
echo 'deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart app.service' > /etc/sudoers.d/deploy
chmod 440 /etc/sudoers.d/deploy && visudo -c

# Then in /etc/ssh/sshd_config: PermitRootLogin no, PasswordAuthentication no
```

Result: nobody logs in as root, each human has a named account (actions are traceable), the app can't change the system, and a leaked CI key can only restart one service.

</DeepDive>

<DeepDive title="Security lens">

Most Linux privilege escalation isn't a clever exploit. It's a user or group with more power than anyone realised.

- **The `docker` group is root.** Anyone in it can run `docker run -v /:/host -it alpine chroot /host` and get a root shell on the host. Treat membership like sudo. The same applies to the `lxd` and `disk` groups.
- **Dangerous sudo rules:** letting a user run editors, interpreters or tools with shell escapes (`vim`, `less`, `find`, `python`, `tar`, `awk`…) as root lets them open a root shell. The GTFOBins project lists hundreds of these. Allow specific commands with fixed arguments only.
- **Wildcards in sudoers** (`/bin/systemctl * app`) can often be abused with extra arguments.
- **Broad `NOPASSWD: ALL`** for automation accounts turns one leaked key into full root.
- **`sudo -l` is an attacker's first command** after getting a shell. Check it on your own servers first.
- **Least privilege for services:** each service its own user, owning only its own files.
- **Audit and offboarding:** review login shells in `/etc/passwd`, `getent group sudo`, every `~/.ssh/authorized_keys`, and sudo logs.
- **Containers:** run as non-root (`USER 10001`); in Kubernetes set `runAsNonRoot: true` and `allowPrivilegeEscalation: false`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between su and sudo?">
su switches to another user (root by default) and requires that user's password, giving a full session as them. sudo runs a single command as another user after checking the caller's own password and the rules in /etc/sudoers, and logs each command. sudo allows fine-grained, auditable privilege without sharing the root password.
</QA>

<QA q="How do you give a user permission to restart only one service?">
Create a file in /etc/sudoers.d/ with visudo, for example `deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart app.service`, using the full path and exact arguments. Set the file mode to 440 and validate with visudo -c. The user can then run only that command as root.
</QA>

<QA q="Why is adding a user to the docker group a security concern?">
The Docker daemon runs as root, and members of the docker group can control it without sudo. They can start a container that mounts the host's root file system and get a root shell on the host. So docker group membership is equivalent to root access and should be restricted like sudo; rootless Docker or Podman reduce this risk.
</QA>

<QA q="Where are user accounts and password hashes stored on Linux?">
Accounts are in /etc/passwd (username, UID, GID, home directory, shell), readable by everyone. Password hashes and ageing data are in /etc/shadow, readable only by root. Groups and their members are in /etc/group. In enterprises, accounts may also come from LDAP or Active Directory via SSSD.
</QA>

<QA q="What is a service account and how should it be configured?">
A non-human account that a service runs as, such as www-data or postgres. It should have a system UID, no password, a non-login shell like /usr/sbin/nologin, no sudo rights, and own only the files the service needs. This limits the damage if the service is compromised.
</QA>

</DeepDive>

<Terms>
  <Term name="UID / GID">Numeric user and group identifiers used by the kernel.</Term>
  <Term name="root">The superuser, UID 0, with unrestricted access.</Term>
  <Term name="Primary group">The default group of a user, assigned to files they create.</Term>
  <Term name="Supplementary groups">Additional groups a user belongs to.</Term>
  <Term name="sudo">Runs a command as another user (usually root) according to sudoers rules.</Term>
  <Term name="sudoers">The rules file /etc/sudoers and /etc/sudoers.d/, edited with visudo.</Term>
  <Term name="Service account">A non-human account a daemon runs as.</Term>
  <Term name="nologin">A shell that refuses interactive logins.</Term>
  <Term name="Least privilege">Granting only the access needed for a task, nothing more.</Term>
  <Term name="Privilege escalation">Gaining higher privileges than intended, typically becoming root.</Term>
