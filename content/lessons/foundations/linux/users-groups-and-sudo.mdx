<Callout type="tip" title="In one minute">
Every user has a numeric **UID**; every group a **GID**. **root** is UID 0 and can do anything. Accounts live in `/etc/passwd`, password hashes in `/etc/shadow`, groups in `/etc/group`. Humans log in as normal users and use **sudo** to run individual commands as root; the rules are in `/etc/sudoers` (edit with `visudo`). Services run as dedicated **system users** with no login shell. Adding someone to the `sudo`/`wheel` or `docker` group is effectively giving them root.
</Callout>

## What is it?

### Users

A **user account** is an identity the kernel uses for permission checks. It is really just a number; the name is for humans.

| Kind | UID range (typical) | Examples | Purpose |
| --- | --- | --- | --- |
| **root** | 0 | `root` | Unlimited power over the system |
| **System / service users** | 1–999 | `www-data`, `postgres`, `nobody`, `systemd-network` | Run services with limited rights; usually cannot log in |
| **Regular users** | 1000+ | `moiz`, `deploy`, `ubuntu`, `ec2-user` | Humans and automation accounts |

### Groups

A **group** is a named set of users. Permissions can be granted to a group instead of to each user.

- Each user has one **primary group** (usually with the same name as the user) and any number of **supplementary groups**.
- Common groups with special meaning: `sudo` (Debian/Ubuntu) or `wheel` (RHEL family) — may use sudo; `adm` — may read logs; `docker` — may control the Docker daemon.

### Where accounts are stored

```text
/etc/passwd   moiz:x:1000:1000:Moiz Rehman:/home/moiz:/bin/bash
              │    │ │    │    │           │          └ login shell
              │    │ │    │    │           └ home directory
              │    │ │    │    └ comment (full name)
              │    │ │    └ primary GID
              │    │ └ UID
              │    └ "x" = password hash is in /etc/shadow
              └ username

/etc/shadow   moiz:$y$j9T$...hash...:20000:0:99999:7:::     (root-only)
/etc/group    sudo:x:27:moiz,deploy                          (group members)
```

### sudo

**sudo** ("superuser do") lets an allowed user run a single command as root (or as another user), after entering **their own** password. It records what was run in the logs, and its rules can be narrow ("deploy may only restart the app service").

Older alternative: `su` switches to another user entirely and needs **that user's** password — sharing root's password is exactly what sudo avoids.

## Why does it matter?

- **Full-stack:** your app should run as its own user (`app` or `node`), not root, so a bug in it cannot take over the server.
- **DevOps:** Dockerfiles use `USER node`; Kubernetes uses `runAsUser` and `runAsNonRoot`; CI runners and deploy scripts need exactly the sudo rights they use, no more.
- **Cloud:** EC2 gives you `ubuntu` or `ec2-user` with passwordless sudo; teams create named accounts per person so actions are traceable.
- **Security:** most Linux privilege escalation is about misconfigured sudo rules, dangerous group memberships or services running as root. "Least privilege" starts here.

## When and where do you use it?

- First setup of a VPS: create your own user, add SSH keys, give it sudo, disable root login.
- Creating a service user for an app and making it own the app directory.
- Giving a CI deploy account permission to restart only one service.
- Auditing a server: who has sudo, who is in `docker`, which accounts have a login shell.
- Offboarding someone: lock the account, remove keys, remove sudo.

## How does it work?

### Every process carries an identity

When you log in, your shell runs with your UID and groups. Every program you start inherits them. When that program opens a file, the kernel compares **those numbers** against the file's owner, group and mode (next lesson). Change the user a process runs as, and you change what it can do.

```bash
id
# uid=1000(moiz) gid=1000(moiz) groups=1000(moiz),4(adm),27(sudo),999(docker)
```

### What happens when you run `sudo systemctl restart nginx`

```text
1. sudo (a setuid-root program) starts
2. reads /etc/sudoers and /etc/sudoers.d/*: is "moiz" allowed to run this?
3. asks for moiz's password (cached for ~15 minutes) unless NOPASSWD
4. logs the command (to /var/log/auth.log or the journal)
5. runs systemctl as root with a cleaned environment
```

### sudoers rules

Always edit with `sudo visudo` (or `visudo -f /etc/sudoers.d/name`) — it checks syntax before saving. A broken sudoers file can lock everyone out of root.

```text
# Format:  who   where=(as_whom)   what
%sudo     ALL=(ALL:ALL) ALL                         # members of group sudo: anything
moiz      ALL=(ALL) ALL                             # user moiz: anything
deploy    ALL=(root) NOPASSWD: /usr/bin/systemctl restart app.service
backup    ALL=(postgres) NOPASSWD: /usr/bin/pg_dump
```

The `deploy` line is what least privilege looks like: one exact command, nothing else.

### Login shells and service users

A service account should not be usable for logging in:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin app
```

`nologin` refuses interactive logins, but processes can still run as that user (via systemd's `User=app`, for example).

## Hands-on

```bash
# Who am I and what groups am I in?
whoami
id
groups

# All accounts, and only those that can log in
cut -d: -f1,3,7 /etc/passwd | column -t -s:
grep -vE "nologin|false$" /etc/passwd

# Who is in the sudo / wheel / docker groups?
getent group sudo wheel docker

# What may I run with sudo?
sudo -l

# Create a regular user with a home directory and bash
sudo adduser alice                     # Debian/Ubuntu interactive
# or: sudo useradd -m -s /bin/bash alice && sudo passwd alice

# Give alice sudo (Ubuntu) — careful: this is full root
sudo usermod -aG sudo alice            # -a = append; without it, other groups are removed!

# Create a service user for an app
sudo useradd --system --no-create-home --shell /usr/sbin/nologin app
sudo mkdir -p /srv/app && sudo chown app:app /srv/app

# Run a command as another user
sudo -u app whoami                     # app
sudo -u postgres psql -c "select 1"    # common for database admin

# Become root interactively (use sparingly, exit when done)
sudo -i
exit

# Lock, then remove, an account
sudo usermod -L alice                  # lock password
sudo deluser --remove-home alice       # or: sudo userdel -r alice

# Who has logged in recently? Failed attempts?
last -n 10
sudo lastb -n 10 2>/dev/null
sudo grep "sudo:" /var/log/auth.log | tail -n 5
```

Group changes apply to **new** logins. After `usermod -aG docker moiz`, log out and in again (or run `newgrp docker`).

## Real-world example

Hardening a fresh Ubuntu VPS for a production app:

```bash
# As root on first login
adduser moiz && usermod -aG sudo moiz
mkdir -p /home/moiz/.ssh && cp ~/.ssh/authorized_keys /home/moiz/.ssh/
chown -R moiz:moiz /home/moiz/.ssh && chmod 700 /home/moiz/.ssh && chmod 600 /home/moiz/.ssh/authorized_keys

# A service user that owns the app and runs it
useradd --system --no-create-home --shell /usr/sbin/nologin app
chown -R app:app /srv/app

# A deploy account for CI that may only restart the service
adduser --disabled-password --gecos "" deploy
echo 'deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart app.service' > /etc/sudoers.d/deploy
chmod 440 /etc/sudoers.d/deploy && visudo -c

# Then in /etc/ssh/sshd_config: PermitRootLogin no, PasswordAuthentication no
```

Result: nobody logs in as root, each human has a named account (actions are traceable), the app cannot modify the system, and a leaked CI key can only restart one service.

## Common mistakes

- **Running everything as root** — `sudo npm start`, `sudo node server.js`, containers with no `USER`.
- **`usermod -G` without `-a`** — replaces all supplementary groups and can remove someone's sudo access.
- **Editing `/etc/sudoers` with a normal editor** and saving a syntax error. Use `visudo`.
- **Shared accounts** (everyone logs in as `ubuntu`) — no accountability, and offboarding means rotating everyone's access.
- **Broad `NOPASSWD: ALL`** for automation accounts.
- **Adding users to `docker`** "to avoid typing sudo", not realising it grants root.

## Security lens

<Callout type="security">
Most Linux privilege escalation is not a clever exploit — it is a user or group that has more power than anyone realised.
</Callout>

- **The `docker` group is root.** Anyone in it can run `docker run -v /:/host -it alpine chroot /host` and get a root shell on the host. Treat membership like sudo. The same applies to `lxd` and `disk` groups.
- **Dangerous sudo rules:** allowing a user to run editors, interpreters or tools with shell escapes (`vim`, `less`, `find`, `python`, `tar`, `awk`…) as root lets them spawn a root shell. The GTFOBins project catalogues hundreds of these. Allow specific commands with fixed arguments only.
- **Wildcards in sudoers** (`/bin/systemctl * app`) can often be abused with extra arguments.
- **`sudo -l` is an attacker's first command** after getting a shell; check it on your own servers before they do.
- **Least privilege for services:** each service its own user, owning only its own files. A compromised `www-data` should not be able to read the database's files.
- **Audit and offboarding:** review `/etc/passwd` login shells, `getent group sudo`, every `~/.ssh/authorized_keys`, and sudo logs. Remove access the same day someone leaves.
- **Containers:** run as non-root (`USER 10001`), and in Kubernetes set `runAsNonRoot: true` and `allowPrivilegeEscalation: false`.

## Interview questions

<QA q="What is the difference between su and sudo?">
su switches to another user (root by default) and requires that user's password, giving a full session as them. sudo runs a single command as another user after checking the caller's own password and the rules in /etc/sudoers, and logs each command. sudo allows fine-grained, auditable privilege without sharing the root password.
</QA>

<QA q="How do you give a user permission to restart only one service?">
Create a file in /etc/sudoers.d/ with visudo, for example `deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart app.service`, using the full path and exact arguments. Set the file mode to 440 and validate with visudo -c. The user can then run only that command as root.
</QA>

<QA q="Why is adding a user to the docker group a security concern?">
The Docker daemon runs as root, and members of the docker group can control it without sudo. They can start a container that mounts the host's root file system and get a root shell on the host. So docker group membership is equivalent to root access and should be restricted like sudo; rootless Docker or Podman reduce this risk.
</QA>

<QA q="Where are user accounts and password hashes stored on Linux?">
Accounts are in /etc/passwd (username, UID, GID, home directory, shell), readable by everyone. Password hashes and ageing data are in /etc/shadow, readable only by root. Groups and their members are in /etc/group. In enterprises, accounts may also come from LDAP or Active Directory via SSSD.
</QA>

<QA q="What is a service account and how should it be configured?">
A non-human account that a service runs as, such as www-data or postgres. It should have a system UID, no password, a non-login shell like /usr/sbin/nologin, no sudo rights, and own only the files the service needs. This limits the damage if the service is compromised.
</QA>

## Key terms

<Terms>
  <Term name="UID / GID">Numeric user and group identifiers used by the kernel.</Term>
  <Term name="root">The superuser, UID 0, with unrestricted access.</Term>
  <Term name="Primary group">The default group of a user, assigned to files they create.</Term>
  <Term name="Supplementary groups">Additional groups a user belongs to.</Term>
  <Term name="sudo">Runs a command as another user (usually root) according to sudoers rules.</Term>
  <Term name="sudoers">The rules file /etc/sudoers and /etc/sudoers.d/, edited with visudo.</Term>
  <Term name="Service account">A non-human account a daemon runs as.</Term>
  <Term name="nologin">A shell that refuses interactive logins.</Term>
  <Term name="Least privilege">Granting only the access needed for a task, nothing more.</Term>
  <Term name="Privilege escalation">Gaining higher privileges than intended, typically becoming root.</Term>
</Terms>
