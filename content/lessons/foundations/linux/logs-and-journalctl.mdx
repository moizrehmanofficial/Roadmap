<Callout type="tip" title="In one minute">
A **log** is a time-stamped record of what a program did. Linux keeps logs in two places: **text files** in `/var/log` (e.g. `auth.log`, `syslog`, `nginx/access.log`) and the **systemd journal**, read with `journalctl`. The most useful forms: `journalctl -u nginx` (one service), `-f` (follow live), `--since "1 hour ago"`, `-p err` (errors only), `-b` (this boot), `-k` (kernel). **logrotate** compresses and deletes old log files so they do not fill the disk. In every incident, logs answer **what happened, when, and who did it**.
</Callout>

## Start from zero

### Why logs?

When something breaks at 3 a.m., nobody was watching. The only witness is the **log**: every program writes down what it did and what went wrong.

<Callout type="analogy">
A **ship's logbook**: every event is written with the time — "08:00 left port", "11:30 engine overheated", "11:32 engine restarted". If something goes wrong, investigators read the logbook to reconstruct exactly what happened, in order. Server logs are that logbook — written automatically by every program.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Log** | A record of events with timestamps | `Nov 10 14:30:01 sshd: Accepted publickey for alex` |
| **Log file** | A text file of log lines | `/var/log/auth.log` |
| **journal** | systemd's binary log store | read with `journalctl` |
| **syslog** | The classic Unix logging system and format | `/var/log/syslog` |
| **Log level / priority** | How serious an event is | `err`, `warning`, `info`, `debug` |
| **Log rotation** | Renaming, compressing and deleting old logs | `syslog.1`, `syslog.2.gz` |
| **Tail / follow** | Watching new lines as they arrive | `tail -f`, `journalctl -f` |

## What is it?

| Source | Where | Read with |
| --- | --- | --- |
| systemd journal (all services, kernel, boot) | `/var/log/journal/` (binary) | `journalctl` |
| System messages | `/var/log/syslog` (Debian/Ubuntu), `/var/log/messages` (RHEL) | `less`, `tail`, `grep` |
| Logins, sudo, SSH | `/var/log/auth.log` (Debian/Ubuntu), `/var/log/secure` (RHEL) | same |
| Kernel | `dmesg`, `journalctl -k` | |
| Web server | `/var/log/nginx/access.log`, `error.log` | |
| Package installs | `/var/log/apt/history.log`, `/var/log/dnf.log` | |
| Your app | journal (stdout/stderr of the service) or `/var/log/<app>/` | |

## Why does it matter?

- **Debugging:** "why did the service fail to start?" — the error is in the log.
- **Security:** failed logins, sudo use, new users and suspicious commands are all logged. Investigations and compliance (PCI, ISO 27001) depend on logs.
- **Monitoring:** log-based alerts ("more than 50 errors per minute") catch problems early.
- **Disk space:** unrotated logs are a classic cause of full disks.

## When and where do you use it?

| Question | Command |
| --- | --- |
| Why did my service fail? | `journalctl -u shop -n 50 --no-pager` |
| Watch errors live while I test | `journalctl -u shop -f` |
| What happened last night? | `journalctl --since "yesterday 22:00" --until "today 06:00"` |
| Who logged in / used sudo? | `grep -E 'Accepted|sudo' /var/log/auth.log` |
| Why did the server reboot / app get killed? | `journalctl -b -1 -p err`, `journalctl -k \| grep -i oom` |
| Web errors | `tail -f /var/log/nginx/error.log` |

## Concepts one by one

### 1. Anatomy of a log line

<Explain>
<What>
A typical line has a **timestamp**, the **host**, the **program** (and its PID), and the **message**.
</What>
<Why>
Knowing the structure lets you filter by time, program or content.
</Why>
<When>
Reading any log.
</When>
<Where>
syslog-style files and `journalctl` output.
</Where>
<How>
Split it into parts with `awk`, filter with `grep`.
</How>
</Explain>

```text
Nov 10 14:30:01  web-1  sshd[2391]:  Accepted publickey for alex from 203.0.113.5 port 51522 ssh2
└─ timestamp ─┘  host   program[PID]  message
```

```bash
line='Nov 10 14:30:01 web-1 sshd[2391]: Accepted publickey for alex from 203.0.113.5 port 51522 ssh2'
echo "$line" | awk '{print "time:", $1, $2, $3; print "host:", $4; print "program:", $5; print "user:", $9, "| from:", $11}'
```

```text output
time: Nov 10 14:30:01
host: web-1
program: sshd[2391]:
user: alex | from: 203.0.113.5
```

### 2. `/var/log` — the classic log folder

<Explain>
<What>
The folder where programs and the syslog daemon (rsyslog) write text log files.
</What>
<Why>
Plain text: readable with `less`, `grep`, `awk`, and by every log shipping tool.
</Why>
<When>
Web server logs, auth logs, app logs written to files.
</When>
<Where>
`/var/log/*`. Many files need `sudo` to read (or membership in the `adm` group).
</Where>
<How>
`ls -lt /var/log | head` shows the most recently written logs.
</How>
</Explain>

```bash
[[ -d /var/log ]] && echo "/var/log exists"
ls /var/log | grep -cE '\.log$|syslog|messages|journal' | sed 's/^/log files or folders found: /' | sed -E 's/: [0-9]+$/: several/'
```

```text output
/var/log exists
log files or folders found: several
```

| File (Ubuntu / RHEL) | Contains |
| --- | --- |
| `syslog` / `messages` | General system messages |
| `auth.log` / `secure` | Logins, SSH, sudo, user changes |
| `kern.log` | Kernel messages |
| `dpkg.log`, `apt/history.log` / `dnf.log` | Package installs and upgrades |
| `nginx/access.log`, `nginx/error.log` | Web requests and web errors |
| `fail2ban.log` | IPs banned for brute force |

### 3. journalctl — reading the systemd journal

<Explain>
<What>
The tool to query the journal, where systemd stores logs from **all** services, the kernel and the boot process.
</What>
<Why>
Powerful filtering by service, time, priority and boot, with one command — and your service's stdout/stderr land here automatically.
</Why>
<When>
Any systemd service problem; any "what happened at time X".
</When>
<Where>
Every systemd-based Linux.
</Where>
<How>
Combine filters freely. `--no-pager` prints directly (good for scripts and copying).
</How>
</Explain>

| Command | Shows |
| --- | --- |
| `journalctl -u nginx` | Logs of one unit |
| `journalctl -u nginx -f` | Follow live |
| `journalctl -u nginx -n 100` | Last 100 lines |
| `journalctl --since "2026-11-10 14:00" --until "14:30"` | Time range |
| `journalctl --since "1 hour ago"` | Relative time |
| `journalctl -p err` | Priority error and worse |
| `journalctl -b` / `-b -1` | This boot / previous boot |
| `journalctl -k` | Kernel messages |
| `journalctl _UID=1000` | By user ID |
| `journalctl -o json-pretty -n 1` | Full structured entry |
| `journalctl --disk-usage` | How much space the journal uses |

```text
$ journalctl -u shop --since "10 min ago" -p warning --no-pager
Nov 10 14:31:44 web-1 node[2314]: WARN slow query took 2300ms: SELECT * FROM orders …
Nov 10 14:33:10 web-1 systemd[1]: shop.service: Main process exited, code=exited, status=1/FAILURE
Nov 10 14:33:10 web-1 systemd[1]: shop.service: Failed with result 'exit-code'.
Nov 10 14:33:15 web-1 systemd[1]: shop.service: Scheduled restart job, restart counter is at 1.
```

### 4. Log levels (priorities)

<Explain>
<What>
A severity on every message, from `emerg` (0, system unusable) to `debug` (7).
</What>
<Why>
Filtering by level turns thousands of lines into the dozen that matter.
</Why>
<When>
Incidents ("errors only"), tuning how much your app logs.
</When>
<Where>
syslog, journald, and most app logging libraries (pino, winston, Python logging).
</Where>
<How>
`journalctl -p err` shows `err` and everything more severe. In apps, log `info` in production and `debug` only while debugging.
</How>
</Explain>

| Level | No. | Use for |
| --- | --- | --- |
| emerg | 0 | System unusable |
| alert | 1 | Act immediately |
| crit | 2 | Critical failure |
| err | 3 | Errors |
| warning | 4 | Something unusual, not yet an error |
| notice | 5 | Normal but significant |
| info | 6 | Normal operation |
| debug | 7 | Detailed debugging |

```bash
logger_demo() {   # simulate an app writing levelled logs
  printf '%s\n' "INFO server started" "DEBUG cache miss user:42" "WARN slow query 2300ms" "ERROR payment API timeout" "INFO request ok"
}
echo "warnings and worse:"
logger_demo | grep -E '^(WARN|ERROR|CRIT)'
```

```text output
warnings and worse:
WARN slow query 2300ms
ERROR payment API timeout
```

### 5. Writing to the logs yourself: `logger`

<Explain>
<What>
`logger` sends a message to the system log from the shell.
</What>
<Why>
Your scripts and cron jobs can log to the same place as everything else, with a tag and a level.
</Why>
<When>
Backup scripts, deploy scripts, health checks.
</When>
<Where>
Shows up in the journal and `/var/log/syslog`.
</Where>
<How>
`logger -t backup -p user.err "backup failed"`, then `journalctl -t backup`.
</How>
</Explain>

```text
$ logger -t backup "nightly backup finished: shop-2026-11-10.tar.gz (212M)"
$ journalctl -t backup -n 1 --no-pager
Nov 10 02:04:13 web-1 backup[3311]: nightly backup finished: shop-2026-11-10.tar.gz (212M)
```

### 6. Security logs: who logged in, who used sudo

<Explain>
<What>
Authentication events: SSH logins (successful and failed), sudo commands, user and group changes.
</What>
<Why>
The first evidence in any security investigation, and the source of brute-force alerts.
</Why>
<When>
Daily review, alerts, incident response.
</When>
<Where>
`/var/log/auth.log` (Ubuntu), `/var/log/secure` (RHEL), or `journalctl -u ssh`; `last` (successful logins), `lastb` (failed, root only).
</Where>
<How>
grep for the key phrases and count by IP or user.
</How>
</Explain>

```bash
cat > auth.log <<'EOF'
Nov 10 02:11:01 web-1 sshd[901]: Failed password for root from 198.51.100.7 port 40112 ssh2
Nov 10 02:11:03 web-1 sshd[903]: Failed password for root from 198.51.100.7 port 40118 ssh2
Nov 10 02:11:06 web-1 sshd[905]: Failed password for invalid user admin from 198.51.100.7 port 40124 ssh2
Nov 10 09:02:44 web-1 sshd[1201]: Accepted publickey for alex from 203.0.113.5 port 51522 ssh2
Nov 10 09:05:10 web-1 sudo:     alex : TTY=pts/0 ; PWD=/home/alex ; USER=root ; COMMAND=/usr/bin/systemctl restart nginx
Nov 10 23:40:02 web-1 sshd[2210]: Failed password for invalid user test from 192.0.2.44 port 5512 ssh2
EOF
echo "failed logins per IP:"
grep 'Failed password' auth.log | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn
echo "successful logins:"
grep 'Accepted' auth.log | awk '{print "  " $9, "from", $11, "at", $3}'
echo "sudo commands:"
grep 'sudo:' auth.log | sed -E 's/.*sudo: +([a-z]+) .*COMMAND=(.*)/  \1 ran: \2/'
```

```text output
failed logins per IP:
      3 from 198.51.100.7
      1 from 192.0.2.44
successful logins:
  alex from 203.0.113.5 at 09:02:44
sudo commands:
  alex ran: /usr/bin/systemctl restart nginx
```

### 7. Log rotation with logrotate

<Explain>
<What>
**logrotate** renames the current log (`app.log` → `app.log.1`), compresses older ones (`.2.gz`), and deletes the oldest — usually daily via a timer or cron.
</What>
<Why>
Logs grow forever otherwise and fill the disk. Rotation keeps a fixed amount of history.
</Why>
<When>
Every log file your apps write themselves (the journal has its own limits).
</When>
<Where>
Rules in `/etc/logrotate.conf` and `/etc/logrotate.d/<app>`.
</Where>
<How>
Write a small rule file; test with `logrotate -d` (dry run, shows what it would do).
</How>
</Explain>

```bash
mkdir -p logs && seq 1 1000 > logs/app.log
cat > app.logrotate <<EOF
$PWD/logs/app.log {
    daily
    rotate 7
    compress
    missingok
    notifempty
    copytruncate
}
EOF
logrotate -f -s state.txt app.logrotate
ls logs | sort
wc -l < logs/app.log | sed 's/$/ lines left in the current app.log/'
```

```text output
app.log
app.log.1.gz
0 lines left in the current app.log
```

| Option | Meaning |
| --- | --- |
| `daily` / `weekly` | How often |
| `rotate 7` | Keep 7 old files |
| `compress` | gzip old files |
| `missingok` / `notifempty` | No error if missing; skip empty files |
| `copytruncate` | Copy then empty the file (for apps that keep it open) |
| `postrotate … endscript` | Run a command after rotating (e.g. tell nginx to reopen logs) |

### 8. Journal size and persistence

<Explain>
<What>
Settings that control how much space the journal uses and whether it survives reboots.
</What>
<Why>
On small servers the journal can use gigabytes; on some systems it is lost at reboot, losing evidence.
</Why>
<When>
Server setup, disk-space incidents.
</When>
<Where>
`/etc/systemd/journald.conf` (`Storage=persistent`, `SystemMaxUse=1G`).
</Where>
<How>
Check: `journalctl --disk-usage`. Clean: `sudo journalctl --vacuum-size=500M` or `--vacuum-time=14d`.
</How>
</Explain>

```text
$ journalctl --disk-usage
Archived and active journals take up 3.8G in the file system.
$ sudo journalctl --vacuum-size=1G
Vacuuming done, freed 2.8G of archived journals from /var/log/journal/…
```

### 9. Kernel messages and OOM kills

<Explain>
<What>
Messages from the kernel itself: hardware errors, disk problems, network driver issues, and the **OOM killer** stopping processes.
</What>
<Why>
"My app disappeared" is often the kernel killing it for memory — only the kernel log says so.
</Why>
<When>
Unexplained crashes and restarts, disk or hardware errors.
</When>
<Where>
`dmesg -T`, `journalctl -k`.
</Where>
<How>
Search for `oom`, `killed process`, `I/O error`, `segfault`.
</How>
</Explain>

```text
$ journalctl -k --since today | grep -iE 'oom|killed process|i/o error'
Nov 10 03:14:07 web-1 kernel: Out of memory: Killed process 2314 (node) total-vm:4161028kB, anon-rss:1953212kB
```

### 10. Central logging

<Explain>
<What>
Sending logs from all servers to one central system.
</What>
<Why>
With 10 servers you cannot SSH into each one to grep. And an attacker on a server can delete local logs — central copies are safe evidence.
</Why>
<When>
More than one server, any production system, any compliance requirement.
</When>
<Where>
ELK/OpenSearch, Grafana Loki, Datadog, AWS CloudWatch Logs, a SIEM (Wazuh, Splunk, Microsoft Sentinel).
</Where>
<How>
An agent (Fluent Bit, Vector, the CloudWatch agent, Promtail) reads the journal and files and ships them. Prefer **structured (JSON) logs** in your apps so fields can be searched.
</How>
</Explain>

```javascript
// Structured log line (what pino/winston produce): easy to search by field centrally
const entry = { time: "2026-11-10T14:31:44Z", level: "warn", msg: "slow query", ms: 2300, route: "/api/orders", userId: 42 };
console.log(JSON.stringify(entry));
```

```text output
{"time":"2026-11-10T14:31:44Z","level":"warn","msg":"slow query","ms":2300,"route":"/api/orders","userId":42}
```

## Hands-on

On your Linux machine (with sudo):

```text
journalctl -b -p err --no-pager | tail -20        # errors since boot
journalctl -u ssh --since today --no-pager         # SSH service today (sshd on RHEL)
sudo tail -n 20 /var/log/auth.log                  # recent logins / sudo
last -n 5                                          # last 5 successful logins
journalctl --disk-usage                            # journal size
ls -lh /var/log | sort -k5 -rh | head              # biggest log files
cat /etc/logrotate.d/apt                           # an example rotation rule
```

And a small incident drill with a sample log:

```bash
printf '%s\n' \
  '2026-11-10T14:30:01Z INFO  GET /api/products 200' \
  '2026-11-10T14:31:44Z WARN  slow query 2300ms' \
  '2026-11-10T14:33:10Z ERROR db connection refused' \
  '2026-11-10T14:33:11Z ERROR db connection refused' \
  '2026-11-10T14:35:00Z INFO  db reconnected' > app.log
echo "first error at: $(grep -m1 ERROR app.log | cut -c12-19)"
echo "errors: $(grep -c ERROR app.log), most common: $(grep ERROR app.log | cut -d' ' -f3- | sort | uniq -c | sort -rn | head -1 | sed 's/^ *//')"
echo "recovered at: $(grep -m1 reconnected app.log | cut -c12-19)"
```

```text output
first error at: 14:33:10
errors: 2, most common: 2 db connection refused
recovered at: 14:35:00
```

The three answers every incident report needs: **when did it start, what was it, when did it end**.

## Real-world example

At 09:00 users report they cannot log in. The investigation, using only logs:

```bash
journalctl -u api --since "08:00" -p warning --no-pager | tail -n 30
# 08:52:13 api[4410]: error: connect ECONNREFUSED 127.0.0.1:6379  (Redis)

journalctl -u redis-server --since "08:00" --no-pager | tail
# 08:51:58 systemd[1]: redis-server.service: Main process exited, code=killed, status=9/KILL

journalctl -k --since "08:45" --no-pager | grep -i oom
# 08:51:58 kernel: Out of memory: Killed process 1203 (redis-server) total-vm:3.1GB

journalctl -u api --since "07:00" --no-pager | grep -c "session created"
# a bot created 2 million sessions overnight → Redis grew until the OOM killer stopped it
```

Root cause in ten minutes: a bot hammering signup filled Redis, the kernel killed Redis, and the API lost its session store. Fixes: rate limiting on signup, a `maxmemory` limit with an eviction policy in Redis, session TTLs, an alert on memory usage — and shipping logs centrally so this is visible on a dashboard next time.

## Common mistakes

- **Not looking at logs first** and guessing instead.
- **Non-persistent journal** — all evidence lost at reboot. Check with `journalctl --list-boots`.
- **No log rotation** for app-written files, until the disk is full.
- **Logging secrets and personal data**: passwords, tokens, full card numbers, request bodies.
- **Logging too little** (no request ID, no user ID) so events cannot be connected; or **too much** (`debug` in production) so cost and noise explode.
- **Inconsistent time zones** between servers. Use UTC on servers and in logs.
- **Only keeping logs on the server** that might be compromised or terminated (auto-scaling instances disappear with their disks).

## Security lens

<Callout type="security">
Logs are both your alarm system and your evidence. Attackers know it — the first thing many do after getting root is delete or edit them.
</Callout>

- **What to watch in `auth.log`/`secure`:** repeated `Failed password` (brute force), `Accepted` logins from new IPs or at odd hours, `sudo` use, `useradd`/`usermod`, changes to SSH keys.
- **Ship logs off the host in real time** (rsyslog forwarding, Fluent Bit, Vector, CloudWatch agent) to a system the server cannot modify. Local logs on a compromised server cannot be trusted.
- **Integrity:** the journal can sign entries (`journalctl --setup-keys`, Forward Secure Sealing) so tampering is detectable.
- **Retention:** keep enough history to investigate (many standards expect 90 days to a year); attackers are often discovered weeks after they arrive.
- **Do not log secrets or sensitive personal data**; logs are copied widely and kept long. Mask tokens and card numbers.
- **Logs are attack surface too:** log injection (newlines in user input forging extra log lines), and vulnerable log libraries — Log4Shell (2021) let attackers execute code just by getting a string logged.
- **Alert on silence:** a server that suddenly stops sending logs may have been tampered with.

## Interview questions

<QA q="How do you view the logs of a systemd service, including live output?">
Use journalctl with the unit: `journalctl -u name` for all entries, `-n 100` for the last lines, `-f` to follow live, `--since` and `--until` for a time window, and `-p err` to filter by priority. `systemctl status name` also shows the last few lines.
</QA>

<QA q="What is log rotation and why is it needed?">
Log rotation periodically renames the current log file, starts a new one, compresses old files and deletes those beyond a retention limit. Without it, log files grow until the disk is full, which can crash databases and services. On Linux it is handled by logrotate (configured in /etc/logrotate.d) or, for journal and stdout logging, by journald's size limits.
</QA>

<QA q="Where are SSH login attempts logged, and how would you detect a brute-force attack?">
In /var/log/auth.log on Debian/Ubuntu or /var/log/secure on RHEL-family systems (and in the journal for the ssh unit). A brute-force attack appears as many "Failed password" or "Invalid user" lines from one or a few IPs in a short time; count them by IP with grep and awk, and use tools like fail2ban or SIEM alerts with thresholds. Disabling password authentication removes the risk.
</QA>

<QA q="Why should logs be shipped to a central system?">
Central logging lets you search across many servers and services in one place, correlate events, build dashboards and alerts, and keep logs after instances are terminated. It also protects evidence: an attacker who gains root on a server can delete local logs, but not copies already shipped to a separate, access-controlled system.
</QA>

<QA q="What is structured logging and why use it?">
Structured logging writes each event as machine-readable fields, usually JSON, instead of free text — for example level, time, message, request ID, user ID and duration. It makes logs easy to filter, aggregate and alert on in systems like ELK, Loki or CloudWatch, and lets you follow one request across services by its ID.
</QA>
