<Tr>
<En>
When something breaks at 3 a.m., nobody was watching. The only witness is the **log**: every program writes down, with the time, what it did and what went wrong. Reading logs well answers the three big questions: **what happened, when, and who did it**.
</En>
<Ur>

## At a glance

<Glance>
<What>
<Tr>
<En>

A **log** is a time-stamped record of what a program did. Linux keeps logs in two places:

- **Text files** in `/var/log`, like `auth.log` (logins), `syslog` and `nginx/access.log`.
- The **systemd journal**, read with the `journalctl` command.

</En>
<Ur>

**Log** waqt ke nishan ke saath record hai ke program ne kya kiya. Linux logs do jagah rakhta hai:

- `/var/log` me **text files**, jaise `auth.log` (logins), `syslog` aur `nginx/access.log`.
- **systemd journal**, jo `journalctl` command se parha jata hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Debugging**: "why did my service fail?" The exact error is in the log.
- **Security**: failed logins, sudo use and new users are all written down.
- **Warnings early**: alerts like "more than 50 errors a minute" catch problems before users do.
- **Disk space**: logs that are never cleaned up fill disks.

</En>
<Ur>

- **Debugging**: "meri service fail kyun hui?" Asal error log me hai.
- **Security**: nakam logins, sudo ka istemal aur naye users sab likhe jate hain.
- **Jaldi khabardar**: "minute me 50 se zyada errors" jaise alerts users se pehle masle pakar lete hain.
- **Disk ki jagah**: jo logs kabhi saaf na hon wo disk bhar dete hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- a service won't start
- the site went down last night
- you suspect someone tried to break in
- an app "disappeared" for no reason

</En>
<Ur>

- service start na ho
- kal raat site band ho gayi
- shak ho ke kisi ne andar ghusne ki koshish ki
- koi app baghair wajah "ghayab" ho gayi

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

The commands you'll use most:

- `journalctl -u nginx`: one service's logs
- `-f`: follow new lines live
- `--since "1 hour ago"`: a time range
- `-p err`: errors only
- `tail -f /var/log/nginx/error.log`: follow a log file

</En>
<Ur>

Sab se zyada istemal hone wali commands:

- `journalctl -u nginx`: ek service ke logs
- `-f`: nayi lines live dekho
- `--since "1 hour ago"`: waqt ka daira
- `-p err`: sirf errors
- `tail -f /var/log/nginx/error.log`: log file live dekho

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **ship's logbook**. Every event is written with the time: "08:00 left port", "11:30 engine overheated", "11:32 engine restarted". If something goes wrong, investigators read the logbook to see **exactly what happened, in order**.

Server logs are that logbook, written automatically by every program.

</En>
<Ur>

Ek **jahaz ki logbook** ka socho. Har waqia waqt ke saath likha jata hai: "08:00 bandargah chhori", "11:30 engine garam hua", "11:32 engine dobara chalaya". Kuch ghalat ho, to tafteesh karne wale logbook parh kar dekhte hain ke **bilkul kya hua, kis tarteeb se**.

Server logs wahi logbook hain, jo har program khud ba khud likhta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="The parts of a log line">

<Tr>
<En>

A typical line has four parts: **when** (timestamp), **which machine** (host), **which program** (and its PID), and **what happened** (the message).

</En>
<Ur>

Aam line ke chaar hisse hain: **kab** (waqt), **kaun si machine** (host), **kaun sa program** (aur us ka PID), aur **kya hua** (paigham).

</Ur>
</Tr>

```text
Nov 10 14:30:01  web-1  sshd[2391]:  Accepted publickey for alex from 203.0.113.5 port 51522 ssh2
└─ timestamp ─┘  host   program[PID]  message
```

```bash
line='Nov 10 14:30:01 web-1 sshd[2391]: Accepted publickey for alex from 203.0.113.5 port 51522 ssh2'
echo "$line" | awk '{print "time:", $1, $2, $3; print "host:", $4; print "program:", $5; print "user:", $9, "| from:", $11}'
```

```text output
time: Nov 10 14:30:01
host: web-1
program: sshd[2391]:
user: alex | from: 203.0.113.5
```

<Happened>
<Tr>
<En>`awk` splits the line into words by spaces and prints the ones we want: the time, the machine, the program, the user (word 9) and the IP address (word 11). Once you know the shape of a line, you can pull any part out of thousands of lines.</En>
<Ur>`awk` line ko spaces se alfaz me torta hai aur jo chahiye wo print karta hai: waqt, machine, program, user (lafz 9) aur IP address (lafz 11). Line ki shakal pata ho, to aap hazaron lines me se koi bhi hissa nikal sakte hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="/var/log: the classic log folder">

<Tr>
<En>

Many programs write plain **text** logs into `/var/log`. Text means you can read them with `less`, `grep` and `tail`. Many need `sudo` to read (or membership in the `adm` group). `ls -lt /var/log | head` shows the most recently written ones.

</En>
<Ur>

Bohot se programs `/var/log` me saada **text** logs likhte hain. Text ka matlab aap unhe `less`, `grep` aur `tail` se parh sakte hain. Bohot se parhne ke liye `sudo` chahiye (ya `adm` group ki membership). `ls -lt /var/log | head` sab se taaza likhe gaye dikhata hai.

</Ur>
</Tr>

```bash
[[ -d /var/log ]] && echo "/var/log exists"
ls /var/log | grep -cE '\.log$|syslog|messages|journal' | sed 's/^/log files or folders found: /' | sed -E 's/: [0-9]+$/: several/'
```

```text output
/var/log exists
log files or folders found: several
```

<Tr>
<En>

| File (Ubuntu / Red Hat) | What's in it |
| --- | --- |
| `syslog` / `messages` | General system messages |
| `auth.log` / `secure` | Logins, SSH, sudo, user changes |
| `kern.log` | Kernel messages |
| `apt/history.log` / `dnf.log` | Software installs and upgrades |
| `nginx/access.log`, `nginx/error.log` | Web requests and web errors |
| `fail2ban.log` | IPs blocked for too many failed logins |

</En>
<Ur>

| File (Ubuntu / Red Hat) | Is me kya hai |
| --- | --- |
| `syslog` / `messages` | System ke aam paigham |
| `auth.log` / `secure` | Logins, SSH, sudo, users ki tabdeeliyan |
| `kern.log` | Kernel ke paigham |
| `apt/history.log` / `dnf.log` | Software install aur upgrade |
| `nginx/access.log`, `nginx/error.log` | Web requests aur web errors |
| `fail2ban.log` | Bohot nakam logins par block hue IPs |

</Ur>
</Tr>

</Step>

<Step title="journalctl: one tool for every service">

<Tr>
<En>

systemd stores logs from **all** services, the kernel and the boot process in its **journal**. Anything your app prints (with `console.log`) lands here automatically. `journalctl` reads it, and you can combine filters freely:

</En>
<Ur>

systemd **saari** services, kernel aur boot ke logs apne **journal** me rakhta hai. Aap ki app jo kuch print kare (`console.log` se) wo khud ba khud yahan aata hai. `journalctl` ise parhta hai, aur aap filters azadi se jor sakte hain:

</Ur>
</Tr>

| Command | Shows |
| --- | --- |
| `journalctl -u nginx` | Logs of one service |
| `journalctl -u nginx -f` | Follow live |
| `journalctl -u nginx -n 100` | Last 100 lines |
| `journalctl --since "2026-11-10 14:00" --until "14:30"` | Time range |
| `journalctl --since "1 hour ago"` | Relative time |
| `journalctl -p err` | Errors and worse |
| `journalctl -b` / `-b -1` | This boot / previous boot |
| `journalctl -k` | Kernel messages |
| `journalctl -o json-pretty -n 1` | Full structured entry |
| `journalctl --disk-usage` | How much space the journal uses |

```text
$ journalctl -u shop --since "10 min ago" -p warning --no-pager
Nov 10 14:31:44 web-1 node[2314]: WARN slow query took 2300ms: SELECT * FROM orders …
Nov 10 14:33:10 web-1 systemd[1]: shop.service: Main process exited, code=exited, status=1/FAILURE
Nov 10 14:33:10 web-1 systemd[1]: shop.service: Failed with result 'exit-code'.
Nov 10 14:33:15 web-1 systemd[1]: shop.service: Scheduled restart job, restart counter is at 1.
```

<Happened>
<Tr>
<En>

- We asked for **warnings and worse** from the `shop` service in the **last 10 minutes**.
- 14:31: a slow database query. 14:33: the app crashed. 5 seconds later systemd restarted it (`Restart=on-failure` at work).
- `--no-pager` prints straight to the screen, which is handy for copying.

</En>
<Ur>

- Hum ne `shop` service se **pichle 10 minute** ki **warnings aur un se bura** maanga.
- 14:31: database ki sust query. 14:33: app crash hui. 5 second baad systemd ne dobara chalayi (`Restart=on-failure` kaam kar raha hai).
- `--no-pager` seedha screen par print karta hai, jo copy ke liye aasaan hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Log levels: how serious is it?">

<Tr>
<En>

Every message has a **level**, from `emerg` (0, system unusable) to `debug` (7, lots of detail). Filtering by level turns thousands of lines into the dozen that matter. In production, apps usually log `info` and above; `debug` only while hunting a bug.

</En>
<Ur>

Har paigham ka ek **level** hai, `emerg` (0, system bekaar) se `debug` (7, bohot tafseel) tak. Level se filter karna hazaron lines ko un darjan lines me badal deta hai jo ahem hain. Production me apps aam taur par `info` aur upar log karti hain; `debug` sirf bug dhoondte waqt.

</Ur>
</Tr>

| Level | No. | Use for |
| --- | --- | --- |
| emerg | 0 | System unusable |
| alert | 1 | Act immediately |
| crit | 2 | Critical failure |
| err | 3 | Errors |
| warning | 4 | Something unusual, not yet an error |
| notice | 5 | Normal but significant |
| info | 6 | Normal operation |
| debug | 7 | Detailed debugging |

```bash
logger_demo() {   # simulate an app writing levelled logs
  printf '%s\n' "INFO server started" "DEBUG cache miss user:42" "WARN slow query 2300ms" "ERROR payment API timeout" "INFO request ok"
}
echo "warnings and worse:"
logger_demo | grep -E '^(WARN|ERROR|CRIT)'
```

```text output
warnings and worse:
WARN slow query 2300ms
ERROR payment API timeout
```

</Step>

<Step title="Write to the logs yourself: logger">

<Tr>
<En>

Your own scripts (backups, deploys) can write to the same place as everything else with `logger`. Add a **tag** with `-t` so you can find them later.

</En>
<Ur>

Aap ki apni scripts (backups, deploys) `logger` se usi jagah likh sakti hain jahan baaqi sab. `-t` se **tag** lagayen taa ke baad me dhoond sakein.

</Ur>
</Tr>

```text
$ logger -t backup "nightly backup finished: shop-2026-11-10.tar.gz (212M)"
$ journalctl -t backup -n 1 --no-pager
Nov 10 02:04:13 web-1 backup[3311]: nightly backup finished: shop-2026-11-10.tar.gz (212M)
```

</Step>

<Step title="Security logs: who logged in, who used sudo">

<Tr>
<En>

Every SSH login (successful or failed), every `sudo` command and every user change is written to `/var/log/auth.log` (Ubuntu) or `/var/log/secure` (Red Hat). This is the **first evidence** in any security investigation. Let's read a sample one:

</En>
<Ur>

Har SSH login (kamyab ya nakam), har `sudo` command aur users ki har tabdeeli `/var/log/auth.log` (Ubuntu) ya `/var/log/secure` (Red Hat) me likhi jati hai. Ye kisi bhi security tafteesh ka **pehla saboot** hai. Chalo ek namoona parhte hain:

</Ur>
</Tr>

```bash
cat > auth.log <<'EOF'
Nov 10 02:11:01 web-1 sshd[901]: Failed password for root from 198.51.100.7 port 40112 ssh2
Nov 10 02:11:03 web-1 sshd[903]: Failed password for root from 198.51.100.7 port 40118 ssh2
Nov 10 02:11:06 web-1 sshd[905]: Failed password for invalid user admin from 198.51.100.7 port 40124 ssh2
Nov 10 09:02:44 web-1 sshd[1201]: Accepted publickey for alex from 203.0.113.5 port 51522 ssh2
Nov 10 09:05:10 web-1 sudo:     alex : TTY=pts/0 ; PWD=/home/alex ; USER=root ; COMMAND=/usr/bin/systemctl restart nginx
Nov 10 23:40:02 web-1 sshd[2210]: Failed password for invalid user test from 192.0.2.44 port 5512 ssh2
EOF
echo "failed logins per IP:"
grep 'Failed password' auth.log | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn
echo "successful logins:"
grep 'Accepted' auth.log | awk '{print "  " $9, "from", $11, "at", $3}'
echo "sudo commands:"
grep 'sudo:' auth.log | sed -E 's/.*sudo: +([a-z]+) .*COMMAND=(.*)/  \1 ran: \2/'
```

```text output
failed logins per IP:
      3 from 198.51.100.7
      1 from 192.0.2.44
successful logins:
  alex from 203.0.113.5 at 09:02:44
sudo commands:
  alex ran: /usr/bin/systemctl restart nginx
```

<Happened>
<Tr>
<En>

- **198.51.100.7** tried 3 times in 5 seconds, guessing `root` and `admin`: a **brute-force** attempt (a robot guessing passwords).
- **Alex** logged in normally with an SSH key at 09:02, then used `sudo` to restart nginx. That's normal admin work.
- `uniq -c` counts repeats, and `sort -rn` puts the biggest number first.

</En>
<Ur>

- **198.51.100.7** ne 5 second me 3 dafa koshish ki, `root` aur `admin` ka andaza laga kar: ye **brute-force** koshish hai (robot jo passwords ka andaza lagata hai).
- **Alex** ne 09:02 par SSH key se aam tareeqe se login kiya, phir `sudo` se nginx restart kiya. Ye aam admin kaam hai.
- `uniq -c` dohraav ginta hai, aur `sort -rn` sab se bara number pehle rakhta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Log rotation: stop logs from filling the disk">

<Tr>
<En>

Log files grow forever unless something cleans them up. **logrotate** does it, usually once a day:

1. renames `app.log` → `app.log.1`
2. compresses older ones (`app.log.2.gz`)
3. deletes the oldest

Rules live in `/etc/logrotate.d/<app>`. Test with `logrotate -d` (a dry run that shows what it **would** do).

</En>
<Ur>

Log files hamesha barhti rehti hain jab tak koi saaf na kare. **logrotate** ye karta hai, aam taur par din me ek dafa:

1. `app.log` → `app.log.1` naam badalta hai
2. purani files compress karta hai (`app.log.2.gz`)
3. sab se purani delete karta hai

Qaide `/etc/logrotate.d/<app>` me hote hain. `logrotate -d` se test karein (dry run jo dikhata hai ke wo kya **karega**).

</Ur>
</Tr>

```bash
mkdir -p logs && seq 1 1000 > logs/app.log
cat > app.logrotate <<EOF
$PWD/logs/app.log {
    daily
    rotate 7
    compress
    missingok
    notifempty
    copytruncate
}
EOF
logrotate -f -s state.txt app.logrotate
ls logs | sort
wc -l < logs/app.log | sed 's/$/ lines left in the current app.log/'
```

```text output
app.log
app.log.1.gz
0 lines left in the current app.log
```

<Happened>
<Tr>
<En>

- The old 1000 lines were saved and compressed into `app.log.1.gz`.
- `app.log` is now empty and ready for new lines.
- With `rotate 7`, only the last 7 files are kept; older ones are deleted.

</En>
<Ur>

- Purani 1000 lines save ho kar `app.log.1.gz` me compress ho gayin.
- `app.log` ab khaali hai aur nayi lines ke liye tayyar.
- `rotate 7` ke saath sirf aakhri 7 files rakhi jati hain; purani delete.

</Ur>
</Tr>
</Happened>

| Option | Meaning |
| --- | --- |
| `daily` / `weekly` | How often |
| `rotate 7` | Keep 7 old files |
| `compress` | gzip old files |
| `missingok` / `notifempty` | No error if missing; skip empty files |
| `copytruncate` | Copy then empty the file (for apps that keep it open) |
| `postrotate … endscript` | Run a command after rotating (e.g. tell nginx to reopen logs) |

</Step>

<Step title="Journal size, and keeping logs after reboot">

<Tr>
<En>

The journal can grow to gigabytes on small servers, and on some systems it's **lost at every reboot** (losing evidence). Settings live in `/etc/systemd/journald.conf`: `Storage=persistent` keeps it, `SystemMaxUse=1G` limits it.

</En>
<Ur>

Chhote servers par journal gigabytes tak barh sakta hai, aur kuch systems par **har reboot par mit jata hai** (saboot zaya). Settings `/etc/systemd/journald.conf` me hain: `Storage=persistent` ise bachata hai, `SystemMaxUse=1G` had lagata hai.

</Ur>
</Tr>

```text
$ journalctl --disk-usage
Archived and active journals take up 3.8G in the file system.
$ sudo journalctl --vacuum-size=1G
Vacuuming done, freed 2.8G of archived journals from /var/log/journal/…
```

</Step>

<Step title="Kernel messages: why did my app disappear?">

<Tr>
<En>

Sometimes an app just **vanishes**. Often the kernel killed it because the server ran **out of memory** (the "OOM killer"). Only the kernel log tells you. Search for `oom`, `killed process`, `I/O error` or `segfault`:

</En>
<Ur>

Kabhi kabhi app bas **ghayab** ho jati hai. Aksar kernel ne use maar diya hota hai kyun ke server ki **memory khatam** ho gayi ("OOM killer"). Ye sirf kernel log batata hai. `oom`, `killed process`, `I/O error` ya `segfault` dhoondein:

</Ur>
</Tr>

```text
$ journalctl -k --since today | grep -iE 'oom|killed process|i/o error'
Nov 10 03:14:07 web-1 kernel: Out of memory: Killed process 2314 (node) total-vm:4161028kB, anon-rss:1953212kB
```

</Step>

<Step title="Send logs to one central place">

<Tr>
<En>

With 10 servers you can't SSH into each one to search. And a hacker on a server can **delete** local logs. So production systems send logs to **one central place**: ELK/OpenSearch, Grafana Loki, Datadog, AWS CloudWatch, or a security system (SIEM).

Write **structured (JSON) logs** in your apps, so each field can be searched:

</En>
<Ur>

10 servers ho to har ek me SSH kar ke dhoondna mumkin nahi. Aur server par hacker local logs **delete** kar sakta hai. Isliye production systems logs **ek markazi jagah** bhejte hain: ELK/OpenSearch, Grafana Loki, Datadog, AWS CloudWatch, ya security system (SIEM).

Apni apps me **structured (JSON) logs** likhein, taa ke har field dhoondi ja sake:

</Ur>
</Tr>

```javascript
// Structured log line (what pino/winston produce): easy to search by field centrally
const entry = { time: "2026-11-10T14:31:44Z", level: "warn", msg: "slow query", ms: 2300, route: "/api/orders", userId: 42 };
console.log(JSON.stringify(entry));
```

```text output
{"time":"2026-11-10T14:31:44Z","level":"warn","msg":"slow query","ms":2300,"route":"/api/orders","userId":42}
```

<Happened>
<Tr>
<En>Instead of a sentence, the log is a set of named fields. A central system can now answer questions like "show every `warn` on `/api/orders` slower than 2000 ms" in seconds.</En>
<Ur>Jumle ke bajaye log naam wali fields ka majmua hai. Ab markazi system "`/api/orders` par 2000 ms se sust har `warn` dikhao" jaise sawalon ka jawab seconds me de sakta hai.</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Guessing instead of reading logs">

<Tr>
<En>Restarting things at random and hoping the problem goes away.</En>
<Ur>Andaze se cheezen restart karna aur umeed karna ke masla chala jaye.</Ur>
</Tr>

</Bad>
<Good title="Logs first">

```text
systemctl status app
journalctl -u app -n 50 --no-pager
```

</Good>
</Compare>

<Compare>
<Bad title="Logging secrets">

```text
INFO login ok user=alex password=Hunter2 token=eyJhbGci...
```

<Tr>
<En>Logs are copied everywhere and kept for months. Anyone who can read them gets the secrets.</En>
<Ur>Logs har jagah copy hote hain aur mahinon rakhe jate hain. Jo bhi inhe parh sake use secrets mil jate hain.</Ur>
</Tr>

</Bad>
<Good title="Log the event, not the secret">

```text
INFO login ok user=alex request_id=7f3a
```

</Good>
</Compare>

<Compare>
<Bad title="Logs only on the server">

<Tr>
<En>The server is hacked or auto-deleted, and all the evidence goes with it.</En>
<Ur>Server hack ho ya khud delete ho jaye, aur saara saboot saath chala jata hai.</Ur>
</Tr>

</Bad>
<Good title="Ship them off the server">

<Tr>
<En>An agent (Fluent Bit, Vector, CloudWatch agent) copies logs to a central system in real time.</En>
<Ur>Ek agent (Fluent Bit, Vector, CloudWatch agent) logs ko usi waqt markazi system me copy karta hai.</Ur>
</Tr>

</Good>
</Compare>

echo "first error at: $(grep -m1 ERROR app.log | cut -c12-19)"
echo "errors: $(grep -c ERROR app.log), most common: $(grep ERROR app.log | cut -d' ' -f3- | sort | uniq -c | sort -rn | head -1 | sed 's/^ *//')"
echo "recovered at: $(grep -m1 reconnected app.log | cut -c12-19)"
```

```

<DeepDive title="Where every log lives, and quick answers">

| Source | Where | Read with |
| --- | --- | --- |
| systemd journal (all services, kernel, boot) | `/var/log/journal/` (binary) | `journalctl` |
| System messages | `/var/log/syslog` (Debian/Ubuntu), `/var/log/messages` (RHEL) | `less`, `tail`, `grep` |
| Logins, sudo, SSH | `/var/log/auth.log` (Debian/Ubuntu), `/var/log/secure` (RHEL) | same |
| Kernel | `dmesg`, `journalctl -k` | |
| Web server | `/var/log/nginx/access.log`, `error.log` | |
| Package installs | `/var/log/apt/history.log`, `/var/log/dnf.log` | |
| Your app | journal (stdout/stderr of the service) or `/var/log/<app>/` | |

| Question | Command |
| --- | --- |
| Why did my service fail? | `journalctl -u shop -n 50 --no-pager` |
| Watch errors live while I test | `journalctl -u shop -f` |
| What happened last night? | `journalctl --since "yesterday 22:00" --until "today 06:00"` |
| Who logged in / used sudo? | `grep -E 'Accepted|sudo' /var/log/auth.log` |
| Why did the server reboot / app get killed? | `journalctl -b -1 -p err`, `journalctl -k \| grep -i oom` |
| Web errors | `tail -f /var/log/nginx/error.log` |

More mistakes: a non-persistent journal loses all evidence at reboot (check with `journalctl --list-boots`); logging too little (no request ID, no user ID) means events can't be connected; logging too much (`debug` in production) means cost and noise explode; and mixed time zones between servers make timelines confusing.

</DeepDive>

<DeepDive title="Real world: users can't log in">

At 09:00 users report they can't log in. The investigation, using only logs:

```bash
journalctl -u api --since "08:00" -p warning --no-pager | tail -n 30
# 08:52:13 api[4410]: error: connect ECONNREFUSED 127.0.0.1:6379  (Redis)

journalctl -u redis-server --since "08:00" --no-pager | tail
# 08:51:58 systemd[1]: redis-server.service: Main process exited, code=killed, status=9/KILL

journalctl -k --since "08:45" --no-pager | grep -i oom
# 08:51:58 kernel: Out of memory: Killed process 1203 (redis-server) total-vm:3.1GB

journalctl -u api --since "07:00" --no-pager | grep -c "session created"
# a bot created 2 million sessions overnight → Redis grew until the OOM killer stopped it
```

Root cause in ten minutes: a bot hammering signup filled Redis, the kernel killed Redis, and the API lost its session store. Fixes: rate limiting on signup, a `maxmemory` limit with an eviction policy in Redis, session TTLs, a memory alert, and central logs so this shows on a dashboard next time.

</DeepDive>

<DeepDive title="Security lens">

Logs are both your alarm system and your evidence. Attackers know it: the first thing many do after getting root is delete or edit them.

- **What to watch in `auth.log`/`secure`:** repeated `Failed password` (brute force), `Accepted` logins from new IPs or at odd hours, `sudo` use, `useradd`/`usermod`, changes to SSH keys.
- **Ship logs off the host in real time** (rsyslog forwarding, Fluent Bit, Vector, CloudWatch agent) to a system the server can't modify.
- **Integrity:** the journal can sign entries (`journalctl --setup-keys`, Forward Secure Sealing) so tampering is detectable.
- **Retention:** keep enough history to investigate (many standards expect 90 days to a year); attackers are often found weeks after they arrive.
- **Don't log secrets or sensitive personal data.** Mask tokens and card numbers.
- **Logs are attack surface too:** log injection (newlines in user input forging extra lines), and vulnerable log libraries. Log4Shell (2021) let attackers run code just by getting a string logged.
- **Alert on silence:** a server that suddenly stops sending logs may have been tampered with.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you view the logs of a systemd service, including live output?">
Use journalctl with the unit: `journalctl -u name` for all entries, `-n 100` for the last lines, `-f` to follow live, `--since` and `--until` for a time window, and `-p err` to filter by priority. `systemctl status name` also shows the last few lines.
</QA>

<QA q="What is log rotation and why is it needed?">
Log rotation periodically renames the current log file, starts a new one, compresses old files and deletes those beyond a retention limit. Without it, log files grow until the disk is full, which can crash databases and services. On Linux it is handled by logrotate (configured in /etc/logrotate.d) or, for journal and stdout logging, by journald's size limits.
</QA>

<QA q="Where are SSH login attempts logged, and how would you detect a brute-force attack?">
In /var/log/auth.log on Debian/Ubuntu or /var/log/secure on RHEL-family systems (and in the journal for the ssh unit). A brute-force attack appears as many "Failed password" or "Invalid user" lines from one or a few IPs in a short time; count them by IP with grep and awk, and use tools like fail2ban or SIEM alerts with thresholds. Disabling password authentication removes the risk.
</QA>

<QA q="Why should logs be shipped to a central system?">
Central logging lets you search across many servers and services in one place, correlate events, build dashboards and alerts, and keep logs after instances are terminated. It also protects evidence: an attacker who gains root on a server can delete local logs, but not copies already shipped to a separate, access-controlled system.
</QA>

<QA q="What is structured logging and why use it?">
Structured logging writes each event as machine-readable fields, usually JSON, instead of free text: for example level, time, message, request ID, user ID and duration. It makes logs easy to filter, aggregate and alert on in systems like ELK, Loki or CloudWatch, and lets you follow one request across services by its ID.
</QA>

</DeepDive>
