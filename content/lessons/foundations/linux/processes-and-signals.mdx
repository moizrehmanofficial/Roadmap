<Callout type="tip" title="In one minute">
Every running program is a **process** with a **PID**. See them with `ps aux` (snapshot), `top`/`htop` (live), `pgrep name` (find PIDs). Run a command in the background with `&`, list jobs with `jobs`, bring one back with `fg`. Stop a process with a **signal**: `kill PID` sends **SIGTERM** (please stop), `kill -9 PID` sends **SIGKILL** (stop now, no cleanup — last resort). `pkill name` signals by name. `nohup cmd &` keeps it running after you log out. `ss -ltnp` or `lsof -i :3000` shows which process uses a port.
</Callout>

## Start from zero

### What is running on this machine?

When a server is slow or a port is "already in use", the question is always: **which process** is doing it, and what should I do with it?

<Callout type="analogy">
A **task manager** at a factory: every worker (process) wears a numbered badge (**PID**). The manager can see who is busy (`top`), call a worker by name (`pgrep`), politely ask one to finish and go home (**SIGTERM**), or have security remove them immediately (**SIGKILL**). A polite request lets the worker tidy up first; forced removal leaves a mess.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Process** | A running program | `nginx`, `node server.js` |
| **PID** | Process ID number | `2314` |
| **PPID** | Parent process ID — who started it | your shell's PID |
| **Foreground** | Runs attached to your terminal; you wait for it | `npm run dev` |
| **Background** | Runs while you keep using the terminal | `sleep 60 &` |
| **Job** | A process started from your current shell | `[1] 2314` |
| **Signal** | A message sent to a process | SIGTERM, SIGKILL, SIGHUP |
| **Daemon** | A background service process | `sshd`, `nginx` |

## What is it?

| Tool | Shows / does |
| --- | --- |
| `ps aux` / `ps -ef` | Snapshot of all processes |
| `top` / `htop` | Live, sorted view of CPU and memory use |
| `pgrep`, `pidof` | Find PIDs by name |
| `kill`, `pkill`, `killall` | Send signals |
| `jobs`, `fg`, `bg`, `&`, Ctrl+Z | Manage your shell's jobs |
| `nohup`, `disown` | Keep running after logout |
| `nice`, `renice` | Lower or raise priority |
| `ss -ltnp`, `lsof` | Which process uses a port / file |

## Why does it matter?

- **"Port 3000 already in use"** — find and stop the old process.
- **100% CPU or memory** — find the culprit in seconds.
- **Graceful restarts** — SIGTERM vs SIGKILL decides whether requests and data are lost.
- **Security** — unknown processes, crypto miners and reverse shells are found with these tools.

## When and where do you use it?

| Problem | Command |
| --- | --- |
| Server slow | `top` (press `P` for CPU, `M` for memory) |
| Is my app running? | `pgrep -af node` |
| Who listens on 80/443/3000? | `sudo ss -ltnp` |
| Stop a stuck process | `kill PID`, then `kill -9 PID` if needed |
| Keep a job running after SSH disconnects | `nohup ./job.sh &` (better: systemd, tmux) |

## Concepts one by one

### 1. Listing processes with `ps`

<Explain>
<What>
`ps` prints a snapshot of processes. `ps aux` shows **all** processes of all users with CPU, memory and the full command.
</What>
<Why>
The first look at "what is running?".
</Why>
<When>
Any investigation.
</When>
<Where>
Every Linux system.
</Where>
<How>
`ps aux | head`, `ps aux --sort=-%mem | head` (biggest memory users), `ps -o pid,ppid,stat,cmd -p PID` (chosen columns).
</How>
</Explain>

```bash
sleep 100 & pid=$!
ps -o pid=,stat=,cmd= -p "$pid" | awk '{print "PID <N>, state", $2, "→", $3, $4}'
ps aux | head -1 | tr -s ' '
kill "$pid"
```

```text output
PID <N>, state S → sleep 100
USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND
```

| Column | Meaning |
| --- | --- |
| `USER` | Which user runs it |
| `PID` | Process ID |
| `%CPU`, `%MEM` | Share of CPU and RAM |
| `RSS` | Real memory used, in KB |
| `STAT` | State: `R` running, `S` sleeping, `D` waiting on disk, `Z` zombie, `T` stopped |
| `COMMAND` | The command line |

### 2. Finding processes by name: `pgrep`

<Explain>
<What>
Prints the PIDs of processes whose name (or full command with `-f`) matches a pattern.
</What>
<Why>
Easier and more reliable than `ps aux | grep …` (which also finds the grep itself).
</Why>
<When>
Checking whether something runs, getting a PID for `kill`.
</When>
<Where>
Scripts and the terminal.
</Where>
<How>
`pgrep nginx`, `pgrep -a node` (with command line), `pgrep -f "server.js"` (match the full command), `pgrep -u www-data` (by user), `-x` (exact name). Careful with `-f` in scripts: the pattern can also match the script's own command line.
</How>
</Explain>

```bash
sleep 201 & sleep 202 &
pgrep -a -x sleep | grep -E 'sleep 20[12]$' | awk '{print "found:", $2, $3}'
echo "count: $(pgrep -a -x sleep | grep -cE 'sleep 20[12]$')"
pkill -x -f "sleep 20[12]"
sleep 0.2
pgrep -a -x sleep | grep -qE 'sleep 20[12]$' || echo "both stopped"
```

```text output
found: sleep 201
found: sleep 202
count: 2
both stopped
```

### 3. Live view: `top` and `htop`

<Explain>
<What>
A continuously updating table of the busiest processes plus system totals (load, CPU, memory).
</What>
<Why>
Shows **right now** who is using the CPU and memory.
</Why>
<When>
"The server is slow", during load tests and incidents.
</When>
<Where>
`top` is always installed; `htop` is friendlier (install it).
</Where>
<How>
In `top`: `P` sort by CPU, `M` by memory, `k` kill, `1` show each CPU core, `q` quit. `top -b -n 1 | head -15` prints one snapshot (for scripts).
</How>
</Explain>

```text
top - 14:31:02 up 12 days,  3:04,  1 user,  load average: 3.92, 2.10, 1.40
Tasks: 142 total,   2 running, 140 sleeping
%Cpu(s): 96.3 us,  2.1 sy,  0.0 ni,  1.2 id,  0.4 wa
MiB Mem :   3911.0 total,    210.4 free,   2804.1 used,    896.5 buff/cache

    PID USER      %CPU  %MEM  COMMAND
   2314 shopapp   188.0  41.2  node          ← the culprit: 1.9 cores busy, 41% RAM
    812 www-data    2.3   0.4  nginx
```

Reading it: load 3.92 on a 2-core machine = overloaded; `96.3 us` = CPU busy in user programs; `wa` near 0 = not waiting on disk. Conclusion: the Node.js app is CPU-bound.

### 4. Foreground and background jobs

<Explain>
<What>
A **foreground** process holds your terminal until it ends. Adding `&` starts it in the **background** so you can keep typing. Ctrl+Z pauses a foreground process; `bg` resumes it in the background; `fg` brings a job back.
</What>
<Why>
Run something long while doing other things in the same terminal.
</Why>
<When>
Interactive work: a dev server, a long copy, a download.
</When>
<Where>
Your shell session.
</Where>
<How>
`command &`, `jobs`, `fg %1`, `bg %1`, `kill %1`. Background jobs still die when you close the terminal — see `nohup` below.
</How>
</Explain>

```bash
sleep 300 &
sleep 301 &
jobs | sed 's/  */ /g'
kill %1
wait %1 2>/dev/null
jobs | sed 's/  */ /g'
kill %2
```

```text output
[1]- Running sleep 300 &
[2]+ Running sleep 301 &
[2]+ Running sleep 301 &
```

`%1` refers to job number 1 of **this** shell (not a PID).

### 5. Signals: asking processes to stop (or reload)

<Explain>
<What>
Signals are short messages the kernel delivers to a process. Each has a name and number.
</What>
<Why>
They are the standard way to stop, pause, resume or reload programs.
</Why>
<When>
Stopping stuck programs, graceful restarts, reloading configs.
</When>
<Where>
`kill`, Ctrl+C, Ctrl+Z, `systemctl stop`, `docker stop`.
</Where>
<How>
`kill PID` = SIGTERM. `kill -SIGNAL PID` for others. `kill -l` lists all.
</How>
</Explain>

| Signal | No. | Sent by | Meaning |
| --- | --- | --- | --- |
| SIGTERM | 15 | `kill PID`, `systemctl stop`, `docker stop` | Please terminate (cleanup allowed) |
| SIGINT | 2 | Ctrl+C | Interrupt |
| SIGKILL | 9 | `kill -9 PID` | Kill immediately — cannot be caught |
| SIGHUP | 1 | Terminal closed; `kill -HUP` | Hang up — many daemons **reload config** on it |
| SIGSTOP / SIGCONT | 19 / 18 | Ctrl+Z / `fg`, `bg` | Pause / continue |
| SIGUSR1 / SIGUSR2 | 10 / 12 | `kill -USR1` | App-defined (e.g. reopen log files) |

```bash
sleep 300 & p=$!
kill -STOP "$p"; ps -o stat= -p "$p" | sed 's/^/after STOP: state /'
kill -CONT "$p"; ps -o stat= -p "$p" | sed 's/^/after CONT: state /'
kill -TERM "$p"; wait "$p"; echo "after TERM: exit code $? (128 + 15)"
```

```text output
after STOP: state T
after CONT: state S
after TERM: exit code 143 (128 + 15)
```

### 6. SIGTERM first, SIGKILL last

<Explain>
<What>
The safe order for stopping a process: polite SIGTERM, wait a few seconds, then SIGKILL only if it is still running.
</What>
<Why>
SIGKILL gives the program **no chance** to finish writes, close connections or delete temp files. Databases can be left needing recovery; half-written files can be corrupted.
</Why>
<When>
Every manual stop.
</When>
<Where>
Servers, containers (Docker does exactly this: TERM, wait 10 s, KILL).
</Where>
<How>
`kill PID; sleep 5; kill -0 PID 2>/dev/null && kill -9 PID`. `kill -0` only **checks** whether the process exists.
</How>
</Explain>

```bash
stop_gracefully() {
  local pid=$1
  kill "$pid" 2>/dev/null || return 0
  for _ in 1 2 3 4 5; do kill -0 "$pid" 2>/dev/null || { echo "stopped with SIGTERM"; return 0; }; sleep 0.2; done
  kill -9 "$pid"; echo "had to use SIGKILL"
}
sleep 300 & stop_gracefully $!
bash -c 'trap "" TERM; sleep 300' & sleep 0.2; stop_gracefully $!
wait 2>/dev/null; true
```

```text output
stopped with SIGTERM
had to use SIGKILL
```

The second process **ignored** SIGTERM (`trap "" TERM`), so after waiting, SIGKILL was needed.

### 7. Keeping processes alive after logout: `nohup`

<Explain>
<What>
`nohup` runs a command immune to SIGHUP — the signal sent when your terminal or SSH session closes.
</What>
<Why>
Background jobs normally die when you disconnect.
</Why>
<When>
Quick one-off long tasks on a server.
</When>
<Where>
SSH sessions.
</Where>
<How>
`nohup ./long-job.sh > job.log 2>&1 &`. For anything permanent, use a **systemd service** (next lesson); for interactive sessions you want to return to, use **tmux** or **screen**.
</How>
</Explain>

```bash
nohup bash -c 'sleep 1; echo "finished even if the terminal had closed"' > job.log 2>&1 &
wait
cat job.log
```

```text output
finished even if the terminal had closed
```

### 8. Priorities: `nice` and `renice`

<Explain>
<What>
The **niceness** value (−20 to 19) tells the scheduler how "nice" a process is to others. Higher = lower priority.
</What>
<Why>
Run heavy background work (backups, compression, reports) without slowing down the live website.
</Why>
<When>
Batch jobs on production servers.
</When>
<Where>
Cron jobs, backup scripts.
</Where>
<How>
`nice -n 10 command` starts with lower priority; `renice -n 15 -p PID` changes a running process. Only root can raise priority (negative values). For disk-heavy work, also `ionice -c3 command`.
</How>
</Explain>

```bash
nice -n 10 sleep 30 & p=$!
ps -o ni= -p "$p" | sed 's/^ */niceness of the background job: /'
kill "$p"
```

```text output
niceness of the background job: 10
```

### 9. Which process uses this port or file?

<Explain>
<What>
Tools that map network ports and open files back to processes.
</What>
<Why>
"Address already in use", "device is busy", and "disk full but I deleted the file" are all answered this way.
</Why>
<When>
Port conflicts, unmount failures, mysterious disk usage, security checks.
</When>
<Where>
`ss -ltnp` (listening TCP ports with process), `lsof -i :PORT`, `lsof +L1` (deleted files still open), `fuser`.
</Where>
<How>
Use `sudo` to see processes of other users.
</How>
</Explain>

```bash
python3 -m http.server 8799 --bind 127.0.0.1 > /dev/null 2>&1 & p=$!
sleep 1
lsof -nP -iTCP:8799 -sTCP:LISTEN | awk 'NR>1 {print "port 8799 is used by:", $1, "(PID <N>)"}'
kill "$p"
```

```text output
port 8799 is used by: python3 (PID <N>)
```

A typical `ss` output on a server:

```text
$ sudo ss -ltnp
State   Local Address:Port   Process
LISTEN  0.0.0.0:22           users:(("sshd",pid=701,fd=3))
LISTEN  0.0.0.0:80           users:(("nginx",pid=812,fd=6))
LISTEN  127.0.0.1:3000       users:(("node",pid=2314,fd=19))   ← app only reachable locally (good)
LISTEN  0.0.0.0:5432         users:(("postgres",pid=990,fd=5)) ← database open to the network (check firewall!)
```

### 10. Investigating a suspicious process

<Explain>
<What>
Looking behind a process's name to see what it really is and what it is doing.
</What>
<Why>
Malware renames itself to look harmless (`kworker`, `systemd-helper`). `/proc/PID/` does not lie.
</Why>
<When>
Unknown high-CPU processes (crypto miners), unexpected network connections, incident response.
</When>
<Where>
`/proc/PID/exe`, `/proc/PID/cmdline`, `/proc/PID/cwd`, `lsof -p PID`, `ss -tnp`.
</Where>
<How>
Check the real binary path, its command line, its working folder, its user, its parent, and its network connections — **before** killing it (killing destroys evidence).
</How>
</Explain>

```bash
cp /usr/bin/sleep /tmp/kworker-fake
/tmp/kworker-fake 300 & p=$!
echo "name it shows:   $(cat /proc/$p/comm)"
echo "real binary:     $(readlink /proc/$p/exe)"
echo "started from:    $(readlink /proc/$p/cwd | sed "s|$PWD|<current folder>|")"
echo "parent process:  $(ps -o comm= -p "$(ps -o ppid= -p $p | tr -d ' ')")"
kill "$p"; rm /tmp/kworker-fake
```

```text output
name it shows:   kworker-fake
real binary:     /tmp/kworker-fake
started from:    <current folder>
parent process:  bash
```

A process named like a kernel worker but running a binary from `/tmp` is a big red flag. Real kernel threads have no `exe` link at all.

## Hands-on

```bash
# 1. Start, find, inspect, stop
sleep 500 & pid=$!
pgrep -x sleep > /dev/null && echo "sleep is running"
echo "state: $(ps -o stat= -p $pid), parent is this shell: $([[ $(ps -o ppid= -p $pid | tr -d ' ') == $$ ]] && echo yes)"
kill $pid; wait $pid 2>/dev/null; echo "exit code after kill: $?"

# 2. Top 3 memory users (names only)
ps -eo comm --sort=-rss | sed -n '2,4p' | wc -l | sed 's/$/ processes listed/'

# 3. Signal numbers
for s in TERM KILL HUP INT; do printf '%s=%s ' "$s" "$(kill -l "$s")"; done; echo
```

```text output
sleep is running
state: S, parent is this shell: yes
exit code after kill: 143
3 processes listed
TERM=15 KILL=9 HUP=1 INT=2 
```

On a real server also try: `top` (then `M`, `P`, `q`), `htop`, `sudo ss -ltnp`, `ps aux --sort=-%cpu | head`.

## Real-world example

An alert fires: CPU on `web-02` has been at 100% for 20 minutes.

```bash
uptime                       # load average: 7.9, 7.6, 6.2 on a 2-core box — heavily overloaded
ps -eo pid,ppid,user,%cpu,etime,cmd --sort=-%cpu | head -n 5
#  PID  PPID USER     %CPU  ELAPSED CMD
# 9183     1 www-data 196.0 00:21:44 /tmp/.x/kworkerd -o pool.example:3333
```

Red flags in one line:

- running as `www-data` (the web server user),
- binary in a hidden folder under `/tmp`,
- a name pretending to be a kernel thread (`kworkerd`),
- a `-o pool…:3333` argument — a cryptocurrency mining pool.

Next steps are incident response, not just `kill -9`:

```bash
ls -l /proc/9183/exe                          # where the binary really is
sudo ss -tnp | grep 9183                      # its network connections
sudo cp /proc/9183/exe /root/evidence.bin     # preserve evidence before killing
sudo crontab -u www-data -l                   # how does it come back? (persistence)
sudo grep -rn "/tmp/.x" /etc/cron* /etc/systemd /var/spool/cron 2>/dev/null
```

Then contain (isolate the server), kill the process, remove persistence, find the entry point (often a vulnerable web app or plugin), patch, and rotate any credentials the server held. The full process is in the Incident Response module.

## Common mistakes

- **Going straight to `kill -9`** — no cleanup, corrupted files, lost requests. Try SIGTERM first.
- **`killall node` on a shared server** — kills everyone's Node processes.
- **Running production services with `nohup` or in a `screen` session** — no restart on crash or reboot, no logs management. Use systemd or containers.
- **Ignoring high `wa`** in `top` and adding CPUs, when the bottleneck is disk.
- **Reading load average without knowing the core count.**
- **Killing zombies** — you cannot; deal with the parent.

## Security lens

<Callout type="security">
On a compromised host, the process list is the crime scene. Know what normal looks like so abnormal stands out.
</Callout>

- **Signals of compromise:** binaries running from `/tmp`, `/dev/shm` or hidden directories; processes whose `/proc/PID/exe` points to a **deleted** file; web servers or databases with `sh`/`bash`/`python` children; unexpected outbound connections; kernel-thread look-alike names; sustained CPU from unknown processes.
- **Preserve before you kill:** copy `/proc/PID/exe`, note the command line, open files and connections. Killing first destroys evidence.
- **Persistence:** attackers re-launch through cron, systemd units, `~/.bashrc`, `authorized_keys` and container restart policies. Killing the process is not cleaning the system.
- **Process visibility:** on shared machines, mount `/proc` with `hidepid=2` so users cannot see others' command lines (which may contain secrets).
- **Least privilege again:** if the web server had run as an unprivileged user with read-only code and no writable executable locations, the attacker's options shrink dramatically.
- **Graceful shutdown is also an availability control:** apps that ignore SIGTERM drop requests on every deploy and every autoscaling event.

## Interview questions

<QA q="How do you find which process is listening on a port?">
`sudo ss -ltnp | grep :PORT` shows the listening socket with the process name and PID; `sudo lsof -i :PORT` gives the same plus details. Then inspect the process with ps or /proc/PID to see its user, binary and command line.
</QA>

<QA q="What is the difference between kill, kill -9 and kill -HUP?">
kill sends SIGTERM, asking the process to terminate; it can clean up or ignore it. kill -9 sends SIGKILL, which the kernel enforces immediately without any cleanup — a last resort. kill -HUP sends SIGHUP; many daemons such as Nginx and sshd interpret it as "reload configuration" without stopping.
</QA>

<QA q="What does load average mean?">
It is the average number of processes that were running or waiting to run (including those in uninterruptible I/O wait) over the last 1, 5 and 15 minutes. It must be compared with the number of CPU cores: a load equal to the core count means fully utilised; much higher means work is queuing, either for CPU or for I/O.
</QA>

<QA q="What is a zombie process and how do you get rid of it?">
A zombie is a process that has exited but whose parent has not yet collected its exit status with wait(). It holds only a PID entry. You cannot kill a zombie; you fix or restart the parent process, after which PID 1 reaps the zombies. In containers, use an init such as tini so PID 1 reaps children.
</QA>

<QA q="You find a suspicious process using 100% CPU. What do you do?">
Do not just kill it. Record its details: user, PID, parent, command line, binary path (/proc/PID/exe), open files and network connections, and preserve a copy of the binary. Look for persistence mechanisms (cron, systemd, startup files, SSH keys). Then contain the host, stop the process, remove persistence, identify and patch the entry point, rotate credentials and review logs — following the incident response process.
</QA>

## Key terms

<Terms>
  <Term name="ps">Lists processes and their attributes.</Term>
  <Term name="top / htop">Live view of processes and resource usage.</Term>
  <Term name="Load average">Average number of runnable or I/O-waiting processes over 1, 5 and 15 minutes.</Term>
  <Term name="SIGTERM / SIGKILL">Polite vs forced termination signals.</Term>
  <Term name="SIGHUP">Hang-up signal; commonly used to reload configuration.</Term>
  <Term name="Job control">Managing shell jobs with &, jobs, fg, bg and Ctrl+Z.</Term>
  <Term name="nice value">Scheduling priority hint; higher is lower priority.</Term>
  <Term name="Zombie">An exited process whose status has not been collected by its parent.</Term>
  <Term name="lsof">Lists open files, sockets and the processes holding them.</Term>
</Terms>
