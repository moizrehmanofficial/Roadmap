<BigIdea>
<Tr>
<En>
Every running program is a **process** with a number (its **PID**). You can **see** them (`ps`, `top`), **find** them (`pgrep`), and **talk** to them with **signals**: "please stop" (SIGTERM) or "stop right now" (SIGKILL). Always ask politely first.
</En>
<Ur>
Har chalta program ek **process** hai jis ka ek number hota hai (us ka **PID**). Aap unhe **dekh** sakte hain (`ps`, `top`), **dhoond** sakte hain (`pgrep`), aur **signals** se un se **baat** kar sakte hain: "please ruk jao" (SIGTERM) ya "abhi ruko" (SIGKILL). Hamesha pehle tameez se kahein.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Process**: a running program, with a **PID** (process ID number).
- `ps aux`: a snapshot of everything running. `top`: a live view.
- `pgrep name`: find a process's number by its name.
- `kill PID`: send **SIGTERM** ("please stop"). `kill -9 PID`: send **SIGKILL** ("stop now", no cleanup).
- `command &`: run in the **background** so you can keep typing.

</En>
<Ur>

- **Process**: chalta hua program, ek **PID** (process ID number) ke saath.
- `ps aux`: jo kuch chal raha hai us ki tasveer. `top`: live manzar.
- `pgrep naam`: naam se process ka number dhoondo.
- `kill PID`: **SIGTERM** bhejo ("please ruk jao"). `kill -9 PID`: **SIGKILL** bhejo ("abhi ruko", safai ke baghair).
- `command &`: **background** me chalao taa ke aap likhte reh sakein.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **"Port 3000 already in use"**: find the old process and stop it.
- **Server slow, 100% CPU**: find the culprit in seconds.
- **Safe restarts**: SIGTERM vs SIGKILL decides whether requests and data get lost.
- **Security**: hidden crypto miners and backdoors are found with these same tools.

</En>
<Ur>

- **"Port 3000 already in use"**: purana process dhoond kar roko.
- **Server sust, 100% CPU**: mujrim chand seconds me dhoondo.
- **Mehfooz restarts**: SIGTERM ya SIGKILL tay karta hai ke requests aur data zaya hon ya nahi.
- **Security**: chhupe crypto miners aur backdoors inhi tools se milte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- the server feels slow
- your app won't start because a port is busy
- a program is stuck and won't close
- you want a long job to keep running after you disconnect

</En>
<Ur>

- server sust lag raha ho
- port masroof hone ki wajah se app start na ho
- koi program phans gaya ho aur band na ho
- aap chahte hon ke disconnect hone ke baad bhi lamba kaam chalta rahe

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

The safe way to stop something:

1. Find it: `pgrep -a node`
2. Ask politely: `kill PID`
3. Wait a few seconds.
4. Only if it's still running: `kill -9 PID`

</En>
<Ur>

Kisi cheez ko rokne ka mehfooz tareeqa:

1. Dhoondo: `pgrep -a node`
2. Tameez se kaho: `kill PID`
3. Chand second intezar karo.
4. Sirf agar abhi bhi chal raha ho: `kill -9 PID`

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **factory manager**:

- Every worker (**process**) wears a numbered badge (**PID**).
- The manager can see who is busy (`top`) and call a worker by name (`pgrep`).
- They can **politely ask** a worker to finish up and go home (**SIGTERM**). The worker tidies the desk first.
- Or they can have **security remove** the worker immediately (**SIGKILL**). The desk is left in a mess.

</En>
<Ur>

Ek **factory manager** ka socho:

- Har mazdoor (**process**) number wala badge pehenta hai (**PID**).
- Manager dekh sakta hai kaun masroof hai (`top`) aur naam se mazdoor ko bula sakta hai (`pgrep`).
- Wo mazdoor se **tameez se keh** sakta hai ke kaam samet kar ghar jao (**SIGTERM**). Mazdoor pehle apni mez saaf karta hai.
- Ya wo **security se** mazdoor ko foran **nikalwa** sakta hai (**SIGKILL**). Mez bikhri reh jati hai.

</Ur>
</Tr>

<Compare>
<Bad title="SIGKILL (kill -9)">

<Tr>
<En>Stops **instantly**. No saving, no closing connections, no cleanup. Files can be left half-written.</En>
<Ur>**Foran** rukta hai. Na save, na connections band, na safai. Files aadhi likhi reh sakti hain.</Ur>
</Tr>

</Bad>
<Good title="SIGTERM (kill)">

<Tr>
<En>The program **finishes its current work**, saves, closes connections, then exits.</En>
<Ur>Program **apna mojooda kaam khatam** karta hai, save karta hai, connections band karta hai, phir band hota hai.</Ur>
</Tr>

</Good>
</Compare>

## Learn it step by step

<Walkthrough>

<Step title="ps: a snapshot of what's running">

<Tr>
<En>

`ps aux` lists **all** processes of all users, with how much CPU and memory each uses. Useful variations:

- `ps aux --sort=-%mem | head`: biggest memory users first
- `ps -o pid,stat,cmd -p PID`: only the columns you choose, for one process

</En>
<Ur>

`ps aux` saare users ke **saare** processes dikhata hai, saath har ek kitna CPU aur memory le raha hai. Kaam ki shakalen:

- `ps aux --sort=-%mem | head`: sab se zyada memory wale pehle
- `ps -o pid,stat,cmd -p PID`: ek process ke liye sirf aap ke chune columns

</Ur>
</Tr>

```bash
sleep 100 & pid=$!
ps -o pid=,stat=,cmd= -p "$pid" | awk '{print "PID <N>, state", $2, "→", $3, $4}'
ps aux | head -1 | tr -s ' '
kill "$pid"
```

```text output
PID <N>, state S → sleep 100
USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND
```

<Happened>
<Tr>
<En>

- `sleep 100 &` started a process that waits 100 seconds. `$!` holds its PID (we show it as `<N>` because it changes every time).
- Its state is **`S`** = sleeping (waiting). The second line shows the column names of `ps aux`.

</En>
<Ur>

- `sleep 100 &` ne aisa process shuru kiya jo 100 second intezar karta hai. `$!` me us ka PID hai (hum ise `<N>` dikhate hain kyun ke ye har dafa badalta hai).
- Is ki halat **`S`** = so raha (intezar). Doosri line `ps aux` ke columns ke naam dikhati hai.

</Ur>
</Tr>
</Happened>

<Tr>
<En>

| Column | Meaning |
| --- | --- |
| `USER` | Which user runs it |
| `PID` | Process ID |
| `%CPU`, `%MEM` | Share of CPU and RAM |
| `RSS` | Real memory used, in KB |
| `STAT` | State: `R` running, `S` sleeping, `D` waiting on disk, `Z` zombie, `T` stopped |
| `COMMAND` | The command line |

</En>
<Ur>

| Column | Matlab |
| --- | --- |
| `USER` | Kaun sa user chala raha hai |
| `PID` | Process ID |
| `%CPU`, `%MEM` | CPU aur RAM ka hissa |
| `RSS` | Asal istemal shuda memory, KB me |
| `STAT` | Halat: `R` chal raha, `S` so raha, `D` disk ka intezar, `Z` zombie, `T` ruka hua |
| `COMMAND` | Command line |

</Ur>
</Tr>

</Step>

<Step title="pgrep and pkill: find and signal by name">

<Tr>
<En>

`pgrep` prints the PIDs of processes that match a name. It's cleaner than `ps aux | grep` (which also finds the `grep` itself).

- `pgrep -a node`: show the full command too
- `pgrep -f "server.js"`: match the whole command line
- `pgrep -u www-data`: only one user's processes
- `pkill name`: send a signal to every match

</En>
<Ur>

`pgrep` naam se milte processes ke PIDs print karta hai. Ye `ps aux | grep` se saaf hai (jo khud `grep` ko bhi pakar leta hai).

- `pgrep -a node`: poori command bhi dikhao
- `pgrep -f "server.js"`: poori command line se milao
- `pgrep -u www-data`: sirf ek user ke processes
- `pkill naam`: har milne wale ko signal bhejo

</Ur>
</Tr>

```bash
sleep 201 & sleep 202 &
pgrep -a -x sleep | grep -E 'sleep 20[12]$' | awk '{print "found:", $2, $3}'
echo "count: $(pgrep -a -x sleep | grep -cE 'sleep 20[12]$')"
pkill -x -f "sleep 20[12]"
sleep 0.2
pgrep -a -x sleep | grep -qE 'sleep 20[12]$' || echo "both stopped"
```

```text output
found: sleep 201
found: sleep 202
count: 2
both stopped
```

<Happened>
<Tr>
<En>We started two `sleep` processes, found both by name, then `pkill` stopped both with one command.</En>
<Ur>Hum ne do `sleep` processes shuru kiye, dono naam se dhoonde, phir `pkill` ne ek command se dono rok diye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="top: the live view">

<Tr>
<En>

`top` shows a **live** table of the busiest processes plus totals for the whole system. Inside `top`:

- `P` sort by CPU, `M` by memory
- `1` show each CPU core
- `q` quit

`htop` is a friendlier version you can install.

</En>
<Ur>

`top` sab se masroof processes ki **live** table dikhata hai, saath poore system ke totals. `top` ke andar:

- `P` CPU se tarteeb, `M` memory se
- `1` har CPU core alag dikhao
- `q` bahar niklo

`htop` zyada dostana version hai jo aap install kar sakte hain.

</Ur>
</Tr>

```text
top - 14:31:02 up 12 days,  3:04,  1 user,  load average: 3.92, 2.10, 1.40
Tasks: 142 total,   2 running, 140 sleeping
%Cpu(s): 96.3 us,  2.1 sy,  0.0 ni,  1.2 id,  0.4 wa
MiB Mem :   3911.0 total,    210.4 free,   2804.1 used,    896.5 buff/cache

    PID USER      %CPU  %MEM  COMMAND
   2314 shopapp   188.0  41.2  node          ← the culprit: 1.9 cores busy, 41% RAM
    812 www-data    2.3   0.4  nginx
```

<Happened>
<Tr>
<En>

- **Load average 3.92** on a machine with **2 cores** = more work than it can handle (load should be around the number of cores or less).
- **96.3 us** = the CPU is busy running programs; **wa** near 0 = it's **not** waiting for the disk.
- The `node` app uses 188% CPU (almost 2 full cores). Conclusion: the Node.js app is the bottleneck.

</En>
<Ur>

- **2 cores** wali machine par **load average 3.92** = jitna sambhal sakti hai us se zyada kaam (load cores ki ginti ke qareeb ya kam hona chahiye).
- **96.3 us** = CPU programs chalane me masroof hai; **wa** taqreeban 0 = disk ka intezar **nahi** kar raha.
- `node` app 188% CPU le rahi hai (taqreeban 2 poore cores). Nateeja: Node.js app hi rukawat hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Foreground and background jobs">

<Tr>
<En>

A **foreground** program holds your terminal until it ends. Add **`&`** at the end to run it in the **background** and keep typing.

- `jobs`: list background jobs in this shell
- `fg %1`: bring job 1 back to the front
- **Ctrl+Z**: pause the foreground program; `bg` resumes it in the background
- `kill %1`: stop job 1

`%1` means "**job** number 1 of this shell", not a PID.

</En>
<Ur>

**Foreground** program khatam hone tak aap ka terminal pakre rakhta hai. Aakhir me **`&`** lagayen to wo **background** me chalta hai aur aap likhte reh sakte hain.

- `jobs`: is shell ke background jobs ki list
- `fg %1`: job 1 ko wapas saamne lao
- **Ctrl+Z**: foreground program ko roko (pause); `bg` use background me chala deta hai
- `kill %1`: job 1 band karo

`%1` ka matlab "is shell ka **job** number 1", PID nahi.

</Ur>
</Tr>

```bash
sleep 300 &
sleep 301 &
jobs | sed 's/  */ /g'
kill %1
wait %1 2>/dev/null
jobs | sed 's/  */ /g'
kill %2
```

```text output
[1]- Running sleep 300 &
[2]+ Running sleep 301 &
[2]+ Running sleep 301 &
```

<Happened>
<Tr>
<En>Two jobs were running. After `kill %1`, only job 2 is left. Background jobs still die when you close the terminal; see `nohup` below.</En>
<Ur>Do jobs chal rahe the. `kill %1` ke baad sirf job 2 bacha. Background jobs terminal band karne par phir bhi mar jate hain; neeche `nohup` dekhein.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Signals: messages to a process">

<Tr>
<En>

A **signal** is a short message the system delivers to a process. Each has a name and a number. You've already used some: **Ctrl+C** sends SIGINT; `kill PID` sends SIGTERM.

</En>
<Ur>

**Signal** ek chhota paigham hai jo system process tak pohanchata hai. Har ek ka naam aur number hai. Aap kuch pehle hi istemal kar chuke hain: **Ctrl+C** SIGINT bhejta hai; `kill PID` SIGTERM bhejta hai.

</Ur>
</Tr>

| Signal | No. | Sent by | Meaning |
| --- | --- | --- | --- |
| SIGTERM | 15 | `kill PID`, `systemctl stop`, `docker stop` | Please terminate (cleanup allowed) |
| SIGINT | 2 | Ctrl+C | Interrupt |
| SIGKILL | 9 | `kill -9 PID` | Kill immediately: can't be caught |
| SIGHUP | 1 | Terminal closed; `kill -HUP` | Hang up: many services **reload their settings** on it |
| SIGSTOP / SIGCONT | 19 / 18 | Ctrl+Z / `fg`, `bg` | Pause / continue |
| SIGUSR1 / SIGUSR2 | 10 / 12 | `kill -USR1` | App-defined (e.g. reopen log files) |

```bash
sleep 300 & p=$!
kill -STOP "$p"; ps -o stat= -p "$p" | sed 's/^/after STOP: state /'
kill -CONT "$p"; ps -o stat= -p "$p" | sed 's/^/after CONT: state /'
kill -TERM "$p"; wait "$p"; echo "after TERM: exit code $? (128 + 15)"
```

```text output
after STOP: state T
after CONT: state S
after TERM: exit code 143 (128 + 15)
```

<Happened>
<Tr>
<En>

- `STOP` **paused** it: state `T` (stopped).
- `CONT` let it **continue**: back to `S` (sleeping).
- `TERM` ended it. The exit code **143** = 128 + 15, which tells you "it was stopped by signal 15 (SIGTERM)".

</En>
<Ur>

- `STOP` ne use **rok** diya: halat `T` (ruka hua).
- `CONT` ne **chalne** diya: wapas `S` (so raha).
- `TERM` ne khatam kar diya. Exit code **143** = 128 + 15, jo batata hai "ise signal 15 (SIGTERM) ne roka".

</Ur>
</Tr>
</Happened>

</Step>

<Step title="SIGTERM first, SIGKILL last">

<Tr>
<En>

The safe order: send **SIGTERM**, wait a few seconds, and only if it's **still running**, send **SIGKILL**. Docker does exactly this: TERM, wait 10 seconds, then KILL.

`kill -0 PID` sends nothing; it only **checks** whether the process still exists.

</En>
<Ur>

Mehfooz tarteeb: **SIGTERM** bhejein, chand second intezar karein, aur sirf agar **abhi bhi chal raha ho**, to **SIGKILL** bhejein. Docker bilkul yahi karta hai: TERM, 10 second intezar, phir KILL.

`kill -0 PID` kuch nahi bhejta; sirf **check** karta hai ke process abhi mojood hai ya nahi.

</Ur>
</Tr>

```bash
stop_gracefully() {
  local pid=$1
  kill "$pid" 2>/dev/null || return 0
  for _ in 1 2 3 4 5; do kill -0 "$pid" 2>/dev/null || { echo "stopped with SIGTERM"; return 0; }; sleep 0.2; done
  kill -9 "$pid"; echo "had to use SIGKILL"
}
sleep 300 & stop_gracefully $!
bash -c 'trap "" TERM; sleep 300' & sleep 0.2; stop_gracefully $!
wait 2>/dev/null; true
```

```text output
stopped with SIGTERM
had to use SIGKILL
```

<Happened>
<Tr>
<En>

- The first process stopped politely with SIGTERM.
- The second one was set up to **ignore** SIGTERM (`trap "" TERM`). After waiting, our function had to use SIGKILL.

</En>
<Ur>

- Pehla process SIGTERM se tameez se ruk gaya.
- Doosre ko SIGTERM **nazar andaz** karne ke liye tayyar kiya gaya tha (`trap "" TERM`). Intezar ke baad hamare function ko SIGKILL istemal karna para.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="nohup: keep running after you log out">

<Tr>
<En>

When your terminal or SSH session closes, background jobs get SIGHUP and usually die. `nohup` makes a command **ignore** that signal:

`nohup ./long-job.sh > job.log 2>&1 &`

Good for quick one-off jobs. For anything permanent, use a **systemd service** (next lesson). For sessions you want to come back to, use **tmux**.

</En>
<Ur>

Jab aap ka terminal ya SSH session band hota hai, background jobs ko SIGHUP milta hai aur wo aam taur par mar jate hain. `nohup` command ko wo signal **nazar andaz** karwata hai:

`nohup ./long-job.sh > job.log 2>&1 &`

Jaldi ke ek waqti kaam ke liye achha. Kisi bhi mustaqil cheez ke liye **systemd service** istemal karein (agla lesson). Jin sessions par wapas aana ho un ke liye **tmux**.

</Ur>
</Tr>

```bash
nohup bash -c 'sleep 1; echo "finished even if the terminal had closed"' > job.log 2>&1 &
wait
cat job.log
```

```text output
finished even if the terminal had closed
```

</Step>

<Step title="nice: be nice to other programs">

<Tr>
<En>

The **niceness** value (−20 to 19) tells the system how "nice" a process is to others. **Higher = lower priority**. Use it to run heavy background work (backups, compression) without slowing down the live website.

- `nice -n 10 command`: start with lower priority
- `renice -n 15 -p PID`: change a running process
- For disk-heavy work, also `ionice -c3 command`

</En>
<Ur>

**Niceness** value (−20 se 19) system ko batati hai ke process doosron ke saath kitna "acha" hai. **Zyada = kam tarjeeh**. Bhari background kaam (backups, compression) live website ko sust kiye baghair chalane ke liye istemal karein.

- `nice -n 10 command`: kam tarjeeh se shuru karo
- `renice -n 15 -p PID`: chalte process ki badlo
- Disk ke bhari kaam ke liye `ionice -c3 command` bhi

</Ur>
</Tr>

```bash
nice -n 10 sleep 30 & p=$!
ps -o ni= -p "$p" | sed 's/^ */niceness of the background job: /'
kill "$p"
```

```text output
niceness of the background job: 10
```

</Step>

<Step title="Which program is using this port?">

<Tr>
<En>

"Address already in use" means another program already holds the port. Find it:

- `sudo ss -ltnp`: every listening port, with its program
- `lsof -i :3000`: who uses port 3000
- `lsof +L1`: deleted files still held open (the "disk full but I deleted it" mystery)

</En>
<Ur>

"Address already in use" ka matlab koi aur program pehle se port pakre hue hai. Use dhoondein:

- `sudo ss -ltnp`: har sunne wala port, us ke program ke saath
- `lsof -i :3000`: port 3000 kaun istemal kar raha hai
- `lsof +L1`: delete ki hui files jo abhi bhi khuli hain ("disk full lekin main ne delete kar di" wali paheli)

</Ur>
</Tr>

```bash
python3 -m http.server 8799 --bind 127.0.0.1 > /dev/null 2>&1 & p=$!
sleep 1
lsof -nP -iTCP:8799 -sTCP:LISTEN | awk 'NR>1 {print "port 8799 is used by:", $1, "(PID <N>)"}'
kill "$p"
```

```text output
port 8799 is used by: python3 (PID <N>)
```

<Tr>
<En>A typical `ss` output on a server, and how to read it:</En>
<Ur>Server par aam `ss` output, aur ise kaise parhein:</Ur>
</Tr>

```text
$ sudo ss -ltnp
State   Local Address:Port   Process
LISTEN  0.0.0.0:22           users:(("sshd",pid=701,fd=3))
LISTEN  0.0.0.0:80           users:(("nginx",pid=812,fd=6))
LISTEN  127.0.0.1:3000       users:(("node",pid=2314,fd=19))   ← app only reachable locally (good)
LISTEN  0.0.0.0:5432         users:(("postgres",pid=990,fd=5)) ← database open to the network (check firewall!)
```

</Step>

<Step title="Look behind a suspicious process">

<Tr>
<En>

Malware often gives itself a harmless-looking name. But `/proc/PID/` tells the truth:

- `/proc/PID/exe`: the **real** program file
- `/proc/PID/cwd`: the folder it runs in
- the parent process: who started it

Check these **before** killing it: killing destroys the evidence.

</En>
<Ur>

Malware aksar khud ko masoom sa naam deta hai. Lekin `/proc/PID/` sach batata hai:

- `/proc/PID/exe`: **asal** program file
- `/proc/PID/cwd`: jis folder me chal raha hai
- parent process: kis ne shuru kiya

Ye sab use maarne se **pehle** check karein: maarna saboot mita deta hai.

</Ur>
</Tr>

```bash
cp /usr/bin/sleep /tmp/kworker-fake
/tmp/kworker-fake 300 & p=$!
echo "name it shows:   $(cat /proc/$p/comm)"
echo "real binary:     $(readlink /proc/$p/exe)"
echo "started from:    $(readlink /proc/$p/cwd | sed "s|$PWD|<current folder>|")"
echo "parent process:  $(ps -o comm= -p "$(ps -o ppid= -p $p | tr -d ' ')")"
kill "$p"; rm /tmp/kworker-fake
```

```text output
name it shows:   kworker-fake
real binary:     /tmp/kworker-fake
started from:    <current folder>
parent process:  bash
```

<Happened>
<Tr>
<En>We disguised `sleep` as `kworker-fake` (pretending to be a kernel worker). But its real file is in **`/tmp`**, which is a big red flag. Real kernel workers have **no** `exe` file at all.</En>
<Ur>Hum ne `sleep` ko `kworker-fake` ka bhes diya (kernel worker hone ka dikhawa). Lekin is ki asal file **`/tmp`** me hai, jo bari khatre ki nishani hai. Asli kernel workers ki koi `exe` file **hoti hi nahi**.</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Going straight to kill -9">

<Tr>
<En>No cleanup: half-written files, lost requests, a database that needs recovery.</En>
<Ur>Koi safai nahi: aadhi likhi files, zaya requests, database jise recovery chahiye.</Ur>

<DeepDive title="All the tools in one table">

| Tool | Shows / does |
| --- | --- |
| `ps aux` / `ps -ef` | Snapshot of all processes |
| `top` / `htop` | Live, sorted view of CPU and memory use |
| `pgrep`, `pidof` | Find PIDs by name |
| `kill`, `pkill`, `killall` | Send signals |
| `jobs`, `fg`, `bg`, `&`, Ctrl+Z | Manage your shell's jobs |
| `nohup`, `disown` | Keep running after logout |
| `nice`, `renice` | Lower or raise priority |
| `ss -ltnp`, `lsof` | Which process uses a port / file |

Other gotchas: ignoring a high `wa` in `top` and adding CPUs when the real bottleneck is the disk; reading load average without knowing the core count; and trying to kill **zombies** (you can't; fix or restart the parent).

</DeepDive>

<DeepDive title="Real world: 100% CPU and a hidden miner">

An alert fires: CPU on `web-02` has been at 100% for 20 minutes.

```bash
uptime                       # load average: 7.9, 7.6, 6.2 on a 2-core box — heavily overloaded
ps -eo pid,ppid,user,%cpu,etime,cmd --sort=-%cpu | head -n 5
#  PID  PPID USER     %CPU  ELAPSED CMD
# 9183     1 www-data 196.0 00:21:44 /tmp/.x/kworkerd -o pool.example:3333
```

Red flags in one line:

- running as `www-data` (the web server user),
- binary in a hidden folder under `/tmp`,
- a name pretending to be a kernel thread (`kworkerd`),
- a `-o pool…:3333` argument: a cryptocurrency mining pool.

Next steps are incident response, not just `kill -9`:

```bash
ls -l /proc/9183/exe                          # where the binary really is
sudo ss -tnp | grep 9183                      # its network connections
sudo cp /proc/9183/exe /root/evidence.bin     # preserve evidence before killing
sudo crontab -u www-data -l                   # how does it come back? (persistence)
sudo grep -rn "/tmp/.x" /etc/cron* /etc/systemd /var/spool/cron 2>/dev/null
```

Then contain (isolate the server), kill the process, remove persistence, find the entry point (often a vulnerable web app or plugin), patch, and rotate any credentials the server held.

</DeepDive>

<DeepDive title="Security lens">

On a hacked host, the process list is the crime scene. Know what normal looks like so abnormal stands out.

- **Signs of compromise:** programs running from `/tmp`, `/dev/shm` or hidden folders; processes whose `/proc/PID/exe` points to a **deleted** file; web servers or databases with `sh`/`bash`/`python` children; unexpected outbound connections; kernel-thread look-alike names; sustained CPU from unknown processes.
- **Preserve before you kill:** copy `/proc/PID/exe`, note the command line, open files and connections.
- **Persistence:** attackers re-launch through cron, systemd units, `~/.bashrc`, `authorized_keys` and container restart policies. Killing the process isn't cleaning the system.
- **Process visibility:** on shared machines, mount `/proc` with `hidepid=2` so users can't see others' command lines (which may contain secrets).
- **Least privilege:** if the web server runs as an unprivileged user with read-only code and no writable executable locations, the attacker's options shrink a lot.
- **Graceful shutdown is an availability control too:** apps that ignore SIGTERM drop requests on every deploy and every autoscaling event.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you find which process is listening on a port?">
`sudo ss -ltnp | grep :PORT` shows the listening socket with the process name and PID; `sudo lsof -i :PORT` gives the same plus details. Then inspect the process with ps or /proc/PID to see its user, binary and command line.
</QA>

<QA q="What is the difference between kill, kill -9 and kill -HUP?">
kill sends SIGTERM, asking the process to terminate; it can clean up or ignore it. kill -9 sends SIGKILL, which the kernel enforces immediately without any cleanup: a last resort. kill -HUP sends SIGHUP; many daemons such as Nginx and sshd interpret it as "reload configuration" without stopping.
</QA>

<QA q="What does load average mean?">
It is the average number of processes that were running or waiting to run (including those in uninterruptible I/O wait) over the last 1, 5 and 15 minutes. It must be compared with the number of CPU cores: a load equal to the core count means fully utilised; much higher means work is queuing, either for CPU or for I/O.
</QA>

<QA q="What is a zombie process and how do you get rid of it?">
A zombie is a process that has exited but whose parent has not yet collected its exit status with wait(). It holds only a PID entry. You cannot kill a zombie; you fix or restart the parent process, after which PID 1 reaps the zombies. In containers, use an init such as tini so PID 1 reaps children.
</QA>

<QA q="You find a suspicious process using 100% CPU. What do you do?">
Do not just kill it. Record its details: user, PID, parent, command line, binary path (/proc/PID/exe), open files and network connections, and preserve a copy of the binary. Look for persistence mechanisms (cron, systemd, startup files, SSH keys). Then contain the host, stop the process, remove persistence, identify and patch the entry point, rotate credentials and review logs, following the incident response process.
</QA>

</DeepDive>
