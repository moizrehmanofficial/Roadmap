<BigIdea>
<Tr>
<En>
Your app must run **all the time**: after a reboot, after a crash at 3 a.m., while nobody is logged in. **systemd** is the manager that makes this happen. You give it a short instruction card (a **unit file**), and it starts your app at boot, restarts it when it crashes, and keeps its logs.
</En>
<Ur>
Aap ki app ko **har waqt** chalna chahiye: reboot ke baad, raat 3 baje crash ke baad, jab koi login na ho tab bhi. **systemd** wo manager hai jo ye mumkin banata hai. Aap use ek chhota hidayat nama (**unit file**) dete hain, aur wo boot par app shuru karta hai, crash par dobara chalata hai, aur us ke logs rakhta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- A **service** (or **daemon**) is a program that keeps running in the background: nginx, sshd, PostgreSQL, your API.
- **systemd** is the **first program** that starts on most Linux systems (PID 1). It starts services, restarts them on crash, and collects logs.
- `systemctl` is the command you use to control it.

</En>
<Ur>

- **Service** (ya **daemon**) wo program hai jo background me chalta rehta hai: nginx, sshd, PostgreSQL, aap ki API.
- **systemd** zyada tar Linux systems par shuru hone wala **pehla program** hai (PID 1). Ye services shuru karta, crash par dobara chalata, aur logs jama karta hai.
- `systemctl` wo command hai jis se aap ise chalate hain.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Reliability**: your app starts at boot and comes back by itself after a crash.
- **Logs**: everything your app prints is saved automatically.
- **Safety**: a few lines can run your app as a limited user in a locked box.
- For a Node.js app on one server, systemd does the job of PM2 without extra tools.

</En>
<Ur>

- **Bharosa**: aap ki app boot par shuru hoti hai aur crash ke baad khud wapas aati hai.
- **Logs**: app jo kuch print karti hai wo khud ba khud save hota hai.
- **Hifazat**: chand lines se app ek mehdood user ke taur par band dabbe me chal sakti hai.
- Ek server par Node.js app ke liye systemd baghair izafi tools ke PM2 ka kaam karta hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- deploying an app directly on a Linux server
- restarting nginx after a settings change
- checking why a service stopped
- running a job every night (timers)

</En>
<Ur>

- app ko seedha Linux server par deploy karte waqt
- settings badalne ke baad nginx restart karte waqt
- check karte waqt ke service kyun ruki
- har raat koi kaam chalate waqt (timers)

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

- `systemctl status nginx`: is it running?
- `sudo systemctl restart nginx`: restart it
- `sudo systemctl enable --now shop`: start now **and** at every boot
- `journalctl -u shop`: read its logs

</En>
<Ur>

- `systemctl status nginx`: chal raha hai?
- `sudo systemctl restart nginx`: restart karo
- `sudo systemctl enable --now shop`: abhi **aur** har boot par shuru karo
- `journalctl -u shop`: is ke logs parho

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **building manager** who arrives **first** every morning (that's PID 1):

- switches on the lifts, lights and air conditioning **in the right order** (the lift needs electricity first)
- keeps a list of every machine and its condition
- **restarts** any machine that breaks down
- writes everything in a **logbook**

You give the manager an **instruction card** for each machine. That card is a **unit file**.

</En>
<Ur>

Ek **building manager** ka socho jo har subah **sab se pehle** aata hai (yahi PID 1 hai):

- lifts, bijli aur AC **sahi tarteeb** se on karta hai (lift ko pehle bijli chahiye)
- har machine aur us ki halat ki list rakhta hai
- jo machine kharab ho use **dobara chalata** hai
- sab kuch **logbook** me likhta hai

Aap manager ko har machine ke liye ek **hidayat card** dete hain. Wo card **unit file** hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="systemctl: the remote control">

<Tr>
<En>

`sudo systemctl ACTION name`. The `.service` at the end is optional.

</En>
<Ur>

`sudo systemctl ACTION naam`. Aakhir ka `.service` ikhtiyari hai.

</Ur>
</Tr>

| Command | Effect |
| --- | --- |
| `systemctl start nginx` | Start now |
| `systemctl stop nginx` | Stop now (SIGTERM, then SIGKILL after a timeout) |
| `systemctl restart nginx` | Stop + start (short downtime) |
| `systemctl reload nginx` | Re-read settings **without stopping** (if supported) |
| `systemctl enable nginx` | Start automatically at boot |
| `systemctl disable nginx` | Don't start at boot |
| `systemctl enable --now nginx` | Enable **and** start now |
| `systemctl is-active nginx` | Prints `active`/`inactive`: good for scripts |
| `systemctl is-enabled nginx` | Prints `enabled`/`disabled` |
| `systemctl list-units --type=service` | All loaded services |
| `systemctl --failed` | Units that failed |

<Tr>
<En>**reload vs restart**: reload is changing the menu while the restaurant **stays open**. Restart is closing the doors for a minute, then reopening. Prefer reload when the service supports it (nginx, sshd).</En>
<Ur>**reload bamuqabla restart**: reload aisa hai jaise restaurant **khula rakhte hue** menu badalna. Restart ek minute ke liye darwaze band kar ke phir kholna hai. Jab service support kare (nginx, sshd) to reload ko tarjeeh dein.</Ur>
</Tr>

</Step>

<Tr>
<En>

`systemctl status` answers "**is it running, and if not, why?**" on one screen. Read the `Loaded:` and `Active:` lines first, then the log lines at the bottom.

</En>
<Ur>

`systemctl status` ek screen par jawab deta hai "**chal raha hai, aur agar nahi to kyun?**". Pehle `Loaded:` aur `Active:` lines parhein, phir neeche ki log lines.

</Ur>
</Tr>

     Loaded: loaded (/etc/systemd/system/shop.service; enabled; preset: enabled)
                     └ where the unit file is ┘           └ starts at boot

   Main PID: 2314 (node)
      Tasks: 11 (limit: 4557)

Nov 10 14:30:01 web-1 node[2314]: GET /api/products 200 12ms
Nov 10 14:30:05 web-1 node[2314]: POST /api/orders 201 48ms

- **Active: active (running)** since 09:12, about 5 hours.
- **Main PID 2314** is the `node` process, using 186 MB of memory.
- The last lines are the app's own output (two API requests).

</En>
<Ur>

- **Loaded**: unit file kahan hai, aur `enabled` = boot par shuru hoti hai.
- **Active: active (running)** 09:12 se, taqreeban 5 ghante.
- **Main PID 2314** `node` process hai, 186 MB memory le raha hai.
- Aakhri lines app ka apna output hain (do API requests).

</Ur>
</Tr>

</Tr>

<Step title="Write your own unit file">

<Tr>
<En>

A unit file is a short text file with **three sections**:

- `[Unit]`: a description, and what must start **before** it
- `[Service]`: **how** to run it
- `[Install]`: **when** to start it (at boot)

Your own units go in `/etc/systemd/system/NAME.service`.

</En>
<Ur>

Unit file ek chhoti text file hai jis ke **teen hisse** hain:

- `[Unit]`: tafseel, aur is se **pehle** kya shuru hona chahiye
- `[Service]`: **kaise** chalana hai
- `[Install]`: **kab** shuru karna hai (boot par)

Aap ke apne units `/etc/systemd/system/NAAM.service` me jate hain.

</Ur>
</Tr>

```bash
cat > shop.service <<'EOF'
[Unit]
Description=Shop API (Node.js)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=shopapp
Group=shopapp
WorkingDirectory=/var/www/shop/current
EnvironmentFile=/etc/shop/shop.env
ExecStart=/usr/bin/node server.js
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
grep -E '^\[' shop.service
grep -c '=' shop.service | sed 's/$/ settings/'
```

```text output
[Unit]
[Service]
[Install]
12 settings
```

<Tr>
<En>

Line by line:

| Setting | Meaning |
| --- | --- |
| `Description` | The name shown in `status` |
| `After=` / `Wants=network-online.target` | Start after the network is up |
| `Type=simple` | The command itself is the main process (normal for Node.js, Python) |
| `User=` / `Group=` | Run as this limited service account, **never root** |
| `WorkingDirectory=` | The folder the app starts in |
| `EnvironmentFile=` | Load `KEY=value` settings (secrets, config) from this file |
| `ExecStart=` | The command, with a **full path** |
| `Restart=on-failure` | Restart automatically if it crashes |
| `RestartSec=5` | Wait 5 seconds between restarts |
| `WantedBy=multi-user.target` | `enable` adds it to normal boot |

</En>
<Ur>

Line ba line:

| Setting | Matlab |
| --- | --- |
| `Description` | `status` me dikhne wala naam |
| `After=` / `Wants=network-online.target` | Network chalne ke baad shuru karo |
| `Type=simple` | Command khud main process hai (Node.js, Python ke liye aam) |
| `User=` / `Group=` | Is mehdood service account ke taur par chalao, **kabhi root nahi** |
| `WorkingDirectory=` | Wo folder jahan app shuru hoti hai |
| `EnvironmentFile=` | Is file se `KEY=value` settings (secrets, config) load karo |
| `ExecStart=` | Command, **poore path** ke saath |
| `Restart=on-failure` | Crash ho to khud restart |
| `RestartSec=5` | Restarts ke darmiyan 5 second intezar |
| `WantedBy=multi-user.target` | `enable` ise aam boot me shamil karta hai |

</Ur>
</Tr>

</Step>

<Step title="Install and start it">

<Tr>
<En>

Four commands: copy the file, tell systemd to **re-read** its files (`daemon-reload`), enable + start, and check. systemd only notices new or changed files after `daemon-reload`.

</En>
<Ur>

Chaar commands: file copy karo, systemd ko apni files **dobara parhne** ko kaho (`daemon-reload`), enable + start, aur check. systemd nayi ya badli hui files ko sirf `daemon-reload` ke baad dekhta hai.

</Ur>
</Tr>

```text
$ sudo cp shop.service /etc/systemd/system/shop.service
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now shop
Created symlink /etc/systemd/system/multi-user.target.wants/shop.service → /etc/systemd/system/shop.service.
$ systemctl is-active shop
active
```

<Happened>
<Tr>
<En>`enable` simply created a **symlink** (shortcut) in a "boot list" folder. That's all "enabled" means: a shortcut in the right folder.</En>
<Ur>`enable` ne sirf ek "boot list" folder me **symlink** (shortcut) banaya. "Enabled" ka bas yahi matlab hai: sahi folder me ek shortcut.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Keep secrets in an environment file">

<Tr>
<En>

An **environment file** is a list of `KEY=value` lines loaded into your app. It keeps settings and secrets **out of the unit file** and **out of Git**.

Rules: no `export`, no spaces around `=`, mode `600`, and restart the service after changing it.

</En>
<Ur>

**Environment file** `KEY=value` lines ki list hai jo aap ki app me load hoti hai. Ye settings aur secrets ko **unit file se bahar** aur **Git se bahar** rakhti hai.

Qaide: `export` nahi, `=` ke gird spaces nahi, mode `600`, aur badalne ke baad service restart karein.

</Ur>
</Tr>

```bash
mkdir -p etc-shop
cat > etc-shop/shop.env <<'EOF'
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://shop:CHANGE_ME@127.0.0.1:5432/shop
EOF
chmod 600 etc-shop/shop.env
stat -c '%a %n' etc-shop/shop.env
grep -c '^[A-Z_]*=' etc-shop/shop.env | sed 's/$/ variables/'
```

```text output
600 etc-shop/shop.env
3 variables
```

</Step>

<Step title="Restart policies">

<Tr>
<En>

A crashed app should come back **without a human**. But an app that crashes instantly shouldn't restart thousands of times a minute.

| `Restart=` | Restarts when |
| --- | --- |
| `no` (default) | Never |
| `on-failure` | It crashes, exits with an error, or times out |
| `always` | Any exit, even a clean one |

`RestartSec=5` waits between tries. `StartLimitBurst=5` with `StartLimitIntervalSec=60` (in `[Unit]`) gives up after 5 failures in 60 seconds and marks the unit `failed`.

</En>
<Ur>

Crash hui app ko **insaan ke baghair** wapas aana chahiye. Lekin jo app foran crash ho, use minute me hazaron dafa restart nahi hona chahiye.

| `Restart=` | Kab restart |
| --- | --- |
| `no` (default) | Kabhi nahi |
| `on-failure` | Crash ho, error ke saath band ho, ya time out ho |
| `always` | Kisi bhi tarah band ho, saaf tareeqe se bhi |

`RestartSec=5` koshishon ke darmiyan intezar karta hai. `StartLimitBurst=5` saath `StartLimitIntervalSec=60` (`[Unit]` me) 60 second me 5 nakamiyon ke baad haar maan kar unit ko `failed` kar deta hai.

</Ur>
</Tr>

</Step>

<Step title="Change a package's service safely: systemctl edit">

<Tr>
<En>

Never edit unit files that came with a package (in `/usr/lib/systemd/system/`): the next update overwrites them. Instead, create a small **override** that changes only what you need:

</En>
<Ur>

Package ke saath aane wali unit files (`/usr/lib/systemd/system/` me) kabhi edit na karein: agla update unhe mita deta hai. Is ke bajaye ek chhota **override** banayen jo sirf zaroori cheez badle:

</Ur>
</Tr>

```text
$ sudo systemctl edit nginx
### Editing /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65535
```

<Tr>
<En>`systemctl cat nginx` shows the final result: the original plus your override.</En>
<Ur>`systemctl cat nginx` aakhri nateeja dikhata hai: asal file + aap ka override.</Ur>
</Tr>

</Step>

<Step title="Timers: scheduled jobs">

<Tr>
<En>

A `.timer` starts a `.service` on a schedule, like an alarm clock. Compared with cron: logs go to the journal, missed runs can catch up (`Persistent=true`), and the job gets all systemd's safety features.

`OnCalendar=*-*-* 02:00:00` = every day at 02:00. **Enable the timer**, not the service.

</En>
<Ur>

`.timer` ek `.service` ko schedule par shuru karta hai, alarm ghari ki tarah. Cron ke muqable me: logs journal me jate hain, chhoote hue runs baad me chal sakte hain (`Persistent=true`), aur kaam ko systemd ki saari hifazati khoobiyan milti hain.

`OnCalendar=*-*-* 02:00:00` = har roz 02:00 baje. **Timer ko enable** karein, service ko nahi.

</Ur>
</Tr>

```text
# /etc/systemd/system/backup.service
[Unit]
Description=Nightly backup
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh /var/www/shop /mnt/backups 14

# /etc/systemd/system/backup.timer
[Unit]
Description=Run backup every night
[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true
[Install]
WantedBy=timers.target

$ sudo systemctl enable --now backup.timer
$ systemctl list-timers backup.timer
NEXT                         LEFT      LAST  PASSED  UNIT          ACTIVATES
Tue 2026-11-11 02:00:00 UTC  11h left  -     -       backup.timer  backup.service
```

</Step>

<Step title="Lock the service in a box (hardening)">

<Tr>
<En>

A few lines can trap your app in a tiny box. If it gets hacked, the attacker **can't** become root, **can't** write outside allowed folders, and **can't** see home folders.

</En>
<Ur>

Chand lines aap ki app ko ek chhote dabbe me band kar sakti hain. Agar hack ho jaye, to hacker root **nahi** ban sakta, ijazat wale folders ke bahar **nahi** likh sakta, aur home folders **nahi** dekh sakta.

</Ur>
</Tr>

```text
[Service]
User=shopapp
NoNewPrivileges=true          # cannot gain more privileges (e.g. via setuid binaries)
ProtectSystem=strict          # the whole file system is read-only…
ReadWritePaths=/var/www/shop/storage /var/log/shop   # …except these folders
ProtectHome=true              # /home, /root invisible
PrivateTmp=true               # its own private /tmp
PrivateDevices=true           # no access to hardware devices
CapabilityBoundingSet=        # no special kernel capabilities
MemoryMax=512M                # hard memory limit
```

<Tr>
<En>Test that the app still works after adding them. `systemd-analyze security shop` gives an exposure score: **lower is better**.</En>
<Ur>Inhe shamil karne ke baad test karein ke app abhi bhi chalti hai. `systemd-analyze security shop` exposure score deta hai: **kam behtar hai**.</Ur>
</Tr>

</Step>

<Step title="Boot and PID 1">

<Tr>
<En>

At boot, the kernel starts systemd as **PID 1**. systemd then starts units until it reaches a **target**, usually `multi-user.target` on servers. Use `After=postgresql.service` to make your app start after the database it needs.

</En>
<Ur>

Boot par kernel systemd ko **PID 1** ke taur par shuru karta hai. Phir systemd units chalata jata hai yahan tak ke ek **target** tak pohanche, servers par aam taur par `multi-user.target`. `After=postgresql.service` se apni app ko us database ke baad shuru karwayen jis ki use zaroorat hai.

</Ur>
</Tr>

```bash
echo "PID 1 on this system is: $(ps -o comm= -p 1)" | sed -E 's/is: .+/is: <init process>/'
```

```text output
PID 1 on this system is: <init process>
```

<Happened>
<Tr>
<En>On a normal server or VM this prints `systemd`. Inside a Docker container, PID 1 is usually your app itself (or a tiny helper like `tini`). That's why `systemctl` doesn't work in most containers.</En>
<Ur>Aam server ya VM par ye `systemd` print karta hai. Docker container ke andar PID 1 aam taur par aap ki app khud hoti hai (ya `tini` jaisa chhota madadgar). Isi liye zyada tar containers me `systemctl` kaam nahi karta.</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Started, but not enabled">

```text
sudo systemctl start shop     # gone after the next reboot
```

</Bad>
<Good title="Enable and start">

```text
sudo systemctl enable --now shop
```

</Good>
</Compare>

<Compare>
<Bad title="Edited the file, forgot to reload">

<Tr>
<En>systemd keeps using the **old** version of your unit file.</En>
<Ur>systemd aap ki unit file ka **purana** version hi istemal karta rehta hai.</Ur>
</Tr>

</Bad>
<Good title="daemon-reload after every edit">

```text
sudo systemctl daemon-reload && sudo systemctl restart shop
```

</Good>
</Compare>

<Compare>
<Bad title="Secrets inside the unit file">

```text
Environment=DB_PASSWORD=Secret123
```

<Tr>
<En>Unit files can be read by every user, and `systemctl show` reveals these values.</En>
<Ur>Unit files har user parh sakta hai, aur `systemctl show` ye values dikha deta hai.</Ur>
</Tr>

</Bad>
<Good title="A protected environment file">

```text
EnvironmentFile=/etc/shop/shop.env    # mode 600
```

</Good>

## Try it yourself

<Challenge title="Your first service">

<Tr>
<En>
On a Linux VM or server (not inside Docker), create a tiny service, watch it, **crash it on purpose**, and see systemd bring it back.
</En>
<Ur>
Linux VM ya server par (Docker ke andar nahi) ek chhoti service banayen, use dekhein, **jaan boojh kar crash karein**, aur dekhein systemd use wapas lata hai.
</Ur>
</Tr>

```text
# 1. A tiny app
sudo mkdir -p /opt/hello
echo 'while true; do echo "hello at $(date +%T)"; sleep 10; done' | sudo tee /opt/hello/run.sh
sudo chmod 755 /opt/hello/run.sh

# 2. Its unit file
sudo tee /etc/systemd/system/hello.service > /dev/null <<'EOF'
[Unit]
Description=Hello demo service
[Service]
ExecStart=/bin/bash /opt/hello/run.sh
Restart=on-failure
DynamicUser=yes
[Install]
WantedBy=multi-user.target
EOF

# 3. Start it and watch it
sudo systemctl daemon-reload
sudo systemctl enable --now hello
systemctl status hello --no-pager
journalctl -u hello -f            # Ctrl+C to stop watching

# 4. Crash it and see systemd bring it back
sudo systemctl kill -s KILL hello
sleep 6; systemctl is-active hello      # → active again (Restart=on-failure)

# 5. Clean up
sudo systemctl disable --now hello
sudo rm /etc/systemd/system/hello.service /opt/hello -r
sudo systemctl daemon-reload
```

<Hint>
<Tr>
<En>`DynamicUser=yes` makes systemd create a temporary, limited user just for this service, so you don't have to create one.</En>
<Ur>`DynamicUser=yes` se systemd sirf is service ke liye aarzi, mehdood user bana deta hai, taa ke aap ko khud na banana pare.</Ur>
</Tr>
</Hint>

</Challenge>

<Challenge title="Why did it disappear?">

<Tr>
<En>
Your API worked yesterday. This morning, after the server rebooted, it's not running, and `systemctl status api` says `inactive (dead)` and `disabled`. What happened, and what's the fix?

<DeepDive title="Unit types and quick reference">

| Unit type | Describes | Example |
| --- | --- | --- |
| `.service` | A program / daemon | `nginx.service` |
| `.timer` | A schedule that starts a service | `certbot.timer` |
| `.socket` | A socket that starts a service on demand | `docker.socket` |
| `.target` | A group / boot stage | `multi-user.target` |
| `.mount` | A mounted file system | `data.mount` |

| Task | Command |
| --- | --- |
| Is nginx running? | `systemctl status nginx` |
| Apply new config without downtime | `sudo systemctl reload nginx` |
| Restart after changes | `sudo systemctl restart shop` |
| Start at boot (and now) | `sudo systemctl enable --now shop` |
| See failed services | `systemctl --failed` |
| Logs of a service | `journalctl -u shop -f` |
| After editing a unit file | `sudo systemctl daemon-reload` |
| Slowest units at boot | `systemd-analyze blame` |

More gotchas: a comment after a value (`User=app # app user`) becomes part of the value, so put comments on their own line; relative paths in `ExecStart` fail because `PATH` is minimal; and `Restart=always` on a crash loop hides the real problem.

</DeepDive>

<DeepDive title="Real world: a NestJS API done properly">

```ini
# /etc/systemd/system/api.service
[Unit]
Description=Orders API (NestJS)
After=network-online.target
Wants=network-online.target

[Service]
User=api
Group=api
WorkingDirectory=/srv/api/current
EnvironmentFile=/etc/api/api.env
ExecStart=/usr/bin/node dist/main.js
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
LimitNOFILE=65535
MemoryMax=1G

# Sandboxing
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/srv/api/uploads /var/log/api
CapabilityBoundingSet=
RestrictSUIDSGID=true

[Install]
WantedBy=multi-user.target
```

Deployment becomes:

```bash
rsync -a --delete build/ deploy@server:/srv/api/releases/2026-11-10/
ssh deploy@server 'ln -sfn /srv/api/releases/2026-11-10 /srv/api/current && sudo systemctl restart api'
```

Nginx in front listens on 443 and passes requests to `127.0.0.1:3000`. If the API crashes at 3 a.m., systemd restarts it within 5 seconds; after a reboot it starts by itself; and even if an attacker finds a code-execution bug, the process can't write outside its two folders, can't read `/home`, and can't become root.

</DeepDive>

<DeepDive title="Security lens">

systemd can sandbox a service more tightly than most people bother to, and attackers love it as a place to hide.

- **Least privilege:** always set `User=`/`Group=`. For services that need no persistent user, `DynamicUser=yes` creates a throwaway one.
- **Sandboxing options** worth knowing: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `ReadWritePaths`, `RestrictAddressFamilies`, `CapabilityBoundingSet`, `SystemCallFilter`. Check exposure with `systemd-analyze security app.service`.
- **Persistence:** a new `.service` or `.timer` in `/etc/systemd/system/` or `~/.config/systemd/user/` is a classic attacker trick. Monitor these folders and review `systemctl list-unit-files --state=enabled` regularly.
- **Secrets:** `systemctl show app` reveals `Environment=` values to any user. Use protected files or `LoadCredential=`.
- **Writable unit files or scripts:** if a non-root user can edit a unit file or the script it runs as root, that user can become root.
- **Resource limits** (`MemoryMax`, `CPUQuota`, `TasksMax`) contain runaway or abused services so they can't take down the host.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is systemd?">
systemd is the init system and service manager used by most modern Linux distributions. It runs as PID 1, starts and orders services at boot, supervises and restarts them, manages scheduled timers, mounts and sockets, collects logs through journald, and applies resource limits and sandboxing through cgroups and namespaces. It is controlled with systemctl.
</QA>

<QA q="What is the difference between systemctl restart and systemctl reload?">
restart stops the service and starts it again, which briefly interrupts it and loads new code and configuration. reload asks the running process to re-read its configuration without stopping, usually by sending SIGHUP; it only works if the service supports it (Nginx does). Use reload for config changes where possible to avoid dropped connections.
</QA>

<QA q="A service is running now but disappears after a reboot. Why?">
It was started but never enabled. Enabling creates links so the service is pulled in by a boot target such as multi-user.target. Fix it with `systemctl enable --now service-name` and confirm with `systemctl is-enabled`.
</QA>

<QA q="How would you run a Node.js app as a production service without Docker?">
Create a dedicated unprivileged user, put the app in a directory it owns, and write a unit file in /etc/systemd/system with User, WorkingDirectory, an EnvironmentFile for secrets, a full-path ExecStart, Restart=on-failure and sandboxing options. Run daemon-reload and enable --now, put Nginx in front as a reverse proxy, and make the app handle SIGTERM for graceful restarts. Read logs with journalctl -u.
</QA>

<QA q="How can attackers abuse systemd, and how do you detect it?">
They create or modify service or timer units to run their code at boot or on a schedule, often with names that mimic legitimate services, or edit scripts that existing root services execute. Detect it by monitoring /etc/systemd/system and user unit directories for changes, reviewing enabled units and timers, checking ExecStart paths for unusual locations such as /tmp, and alerting on file integrity changes.
</QA>

</DeepDive>
