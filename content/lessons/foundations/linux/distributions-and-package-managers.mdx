<Callout type="tip" title="In one minute">
A **distribution** packages the Linux kernel with tools and defaults. The big families: **Debian/Ubuntu** (package manager **apt**, `.deb` files), **Red Hat / Rocky / Alma / Amazon Linux / Fedora** (**dnf**, `.rpm`), and **Alpine** (**apk**, tiny — popular for Docker). A **package manager** installs software from trusted **repositories**, resolves **dependencies** automatically, verifies **signatures**, and updates everything with one command. Always `apt update` before `apt install`, and keep servers patched.
</Callout>

## Start from zero

### Why so many Linux versions?

The Linux kernel is just the core. Different groups combine it with different tools, update schedules and goals — one wants stability for banks, another wants the newest software, another wants the smallest possible size for containers. Each combination is a **distribution**.

<Callout type="analogy">
The **engine** is the same, but car companies build different cars around it: a reliable family sedan (Debian), a popular all-rounder (Ubuntu), a corporate fleet car with a service contract (Red Hat), a tiny city car (Alpine). And a **package manager** is the official **app store** of each car brand: you pick an app, it downloads the right version for your car, checks it is genuine, and installs everything it needs.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Distribution** | A complete Linux OS | Ubuntu 24.04 |
| **Package** | A bundle of a program's files plus information about it | `nginx_1.24.0.deb` |
| **Package manager** | The tool that installs, updates and removes packages | apt, dnf, apk |
| **Repository (repo)** | A server hosting packages | `archive.ubuntu.com` |
| **Dependency** | Another package a program needs | `curl` needs `libcurl` |
| **LTS** | Long-Term Support: years of security updates | Ubuntu 24.04 LTS (5 years) |
| **Signing key (GPG)** | Proves a package came from the real publisher | Ubuntu archive key |

## What is it?

| Family | Distros | Package manager | Package format | Typical use |
| --- | --- | --- | --- | --- |
| Debian | Debian, **Ubuntu**, Linux Mint, Kali | `apt` (`dpkg` underneath) | `.deb` | Servers, cloud, desktops, WSL |
| Red Hat | **RHEL**, Rocky, AlmaLinux, Fedora, **Amazon Linux**, CentOS Stream | `dnf` (`yum` on old ones, `rpm` underneath) | `.rpm` | Enterprise, AWS |
| Alpine | Alpine | `apk` | `.apk` | Docker images (~5 MB) |
| Arch | Arch, Manjaro | `pacman` | `.pkg.tar.zst` | Enthusiast desktops |
| SUSE | openSUSE, SLES | `zypper` | `.rpm` | Enterprise (Europe) |

## Why does it matter?

- **Commands differ:** a tutorial for Ubuntu (`apt install`) will not work on Amazon Linux (`dnf install`).
- **Security:** most server breaches exploit **known, already-patched** vulnerabilities. Package managers are how you patch.
- **Docker:** your base image (`node:22`, `node:22-slim`, `node:22-alpine`) decides the package manager, image size and libraries.
- **Support lifetime:** running an end-of-life release means no more security updates.

## When and where do you use it?

| Task | Debian/Ubuntu | RHEL/Amazon Linux | Alpine |
| --- | --- | --- | --- |
| Refresh package lists | `sudo apt update` | (automatic) | `apk update` |
| Install | `sudo apt install nginx` | `sudo dnf install nginx` | `apk add nginx` |
| Remove | `sudo apt remove nginx` | `sudo dnf remove nginx` | `apk del nginx` |
| Upgrade everything | `sudo apt upgrade` | `sudo dnf upgrade` | `apk upgrade` |
| Search | `apt search redis` | `dnf search redis` | `apk search redis` |
| Show info | `apt show nginx` | `dnf info nginx` | `apk info nginx` |
| List installed | `apt list --installed` | `dnf list installed` | `apk info` |
| Which package owns a file | `dpkg -S /usr/bin/curl` | `rpm -qf /usr/bin/curl` | `apk info --who-owns /usr/bin/curl` |

## Concepts one by one

### 1. Which distribution am I on?

<Explain>
<What>
Every modern distro describes itself in `/etc/os-release`.
</What>
<Why>
Scripts and you need to know which commands and package names to use.
</Why>
<When>
First thing on any new server or container.
</When>
<Where>
Servers, containers, CI runners.
</Where>
<How>
`cat /etc/os-release`, or source it in scripts and read `$ID` and `$VERSION_ID`.
</How>
</Explain>

```bash
. /etc/os-release
case "$ID" in
  ubuntu|debian)                    family="Debian family → use apt" ;;
  rhel|rocky|almalinux|fedora|amzn) family="Red Hat family → use dnf" ;;
  alpine)                           family="Alpine → use apk" ;;
  *)                                family="other: $ID" ;;
esac
echo "$family"
```

```text output
Debian family → use apt
```

(On a Red Hat or Alpine system you would see the matching line instead.)

### 2. Release types: LTS, stable and rolling

<Explain>
<What>
How often a distro releases new versions and how long each is supported.
</What>
<Why>
Servers need predictability and long security support; developers sometimes want the newest software.
</Why>
<When>
Choosing an OS for a server or a base image.
</When>
<Where>
Ubuntu LTS (every 2 years, April of even years: 22.04, 24.04), Debian stable (~2 years), RHEL (10 years of support), Arch and Fedora (fast-moving).
</Where>
<How>
For servers, pick an **LTS** release and upgrade before it reaches end of life.
</How>
</Explain>

| Type | Example | Good for |
| --- | --- | --- |
| LTS / stable | Ubuntu 24.04 LTS, Debian 12, RHEL 9 | Production servers |
| Regular | Ubuntu 25.10, Fedora | Desktops, trying new features |
| Rolling | Arch | Enthusiasts — always newest, more change |

### 3. Packages and repositories

<Explain>
<What>
A **package** is a program's files plus metadata (version, description, dependencies, install scripts). **Repositories** are servers that host thousands of packages.
</What>
<Why>
Instead of downloading installers from random websites, you install tested, signed software from trusted sources.
</Why>
<When>
Installing any software on a server.
</When>
<Where>
Repos are listed in `/etc/apt/sources.list.d/` (Debian/Ubuntu) and `/etc/yum.repos.d/` (Red Hat).
</Where>
<How>
`apt show package` displays a package's metadata; `dpkg -s` shows an installed package's status.
</How>
</Explain>

```bash
dpkg -s bash | grep -E '^(Package|Status|Priority):'
dpkg -S "$(readlink -f /bin/bash)" | cut -d: -f1 | sed 's/^/the file \/bin\/bash belongs to package: /'
```

```text output
Package: bash
Status: install ok installed
Priority: required
the file /bin/bash belongs to package: bash
```

### 4. `apt update` vs `apt upgrade`

<Explain>
<What>
`apt update` downloads the **latest list** of available packages and versions. `apt upgrade` actually **installs** newer versions of installed packages.
</What>
<Why>
Confusing them is the most common beginner mistake: `update` alone installs nothing; `install` without a recent `update` may fail with "404 Not Found" or install an old version.
</Why>
<When>
Before every install, and regularly for security patches.
</When>
<Where>
Every Debian/Ubuntu machine and Dockerfile.
</Where>
<How>
`sudo apt update && sudo apt upgrade -y`. `full-upgrade` also allows removing packages to complete an upgrade. `apt list --upgradable` shows what is waiting.
</How>
</Explain>

<Callout type="analogy">
`apt update` is **refreshing the shop's catalogue**. `apt upgrade` is **actually buying** the new versions. Refreshing the catalogue does not put anything new in your bag.
</Callout>

```text
$ sudo apt update
Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease
Get:2 http://security.ubuntu.com/ubuntu noble-security InRelease [126 kB]
...
23 packages can be upgraded. Run 'apt list --upgradable' to see them.

$ sudo apt upgrade -y
The following packages will be upgraded:
  libssl3 openssl openssh-server ...
```

### 5. Installing and removing software

<Explain>
<What>
Installing downloads a package and all its dependencies, unpacks them, and runs setup scripts. Removing deletes the program; **purge** also deletes its config files.
</What>
<Why>
One command replaces manual downloads, unpacking and dependency hunting.
</Why>
<When>
Setting up servers, Docker images, CI runners.
</When>
<Where>
Terminal, setup scripts, Dockerfiles.
</Where>
<How>
`apt install -y pkg` (yes to prompts), `apt remove pkg`, `apt purge pkg`, `apt autoremove` (remove dependencies nobody needs any more).
</How>
</Explain>

```text
$ sudo apt install -y nginx
The following additional packages will be installed:
  nginx-common libnginx-mod-http-...       ← dependencies pulled in automatically
Setting up nginx (1.24.0-2ubuntu7) ...

$ nginx -v
nginx version: nginx/1.24.0 (Ubuntu)

$ sudo apt purge -y nginx && sudo apt autoremove -y
```

### 6. Dependencies

<Explain>
<What>
Most programs rely on shared libraries and other programs. The package manager reads each package's dependency list and installs what is missing.
</What>
<Why>
Installing by hand leads to "dependency hell": missing or conflicting libraries.
</Why>
<When>
Every install and upgrade.
</When>
<Where>
`apt show pkg` (the Depends line), `apt-cache depends pkg`.
</Where>
<How>
Shared libraries are installed once and used by many programs — which is also why one security update to `openssl` fixes every program that uses it.
</How>
</Explain>

```bash
apt-cache depends curl 2>/dev/null | grep -m3 'Depends' | sed 's/^ *//'
```

```text output
Depends: libc6
Depends: libcurl4t64
Depends: zlib1g
```

(Exact names vary between releases.)

### 7. Trust: signed repositories

<Explain>
<What>
Repositories sign their package lists with a **GPG key**. The package manager verifies the signature before installing anything.
</What>
<Why>
It prevents attackers from tampering with packages in transit or on a mirror — a supply-chain protection.
</Why>
<When>
Every `apt update`; and when adding third-party repos (Docker, Node.js, PostgreSQL).
</When>
<Where>
Keys in `/usr/share/keyrings/` or `/etc/apt/keyrings/`, referenced with `signed-by=` in the repo file.
</Where>
<How>
Add third-party repos only from the vendor's official instructions, with a key scoped to that repo.
</How>
</Explain>

```text
# Official Docker repository on Ubuntu (from Docker's documentation)
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
echo "deb [signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update && sudo apt install -y docker-ce
```

### 8. Packages in Dockerfiles

<Explain>
<What>
Installing packages while building a container image.
</What>
<Why>
Images should be small, reproducible and free of leftover caches.
</Why>
<When>
Every Dockerfile that needs system tools.
</When>
<Where>
`RUN` lines in Dockerfiles.
</Where>
<How>
Combine update and install in **one** `RUN`, skip recommended extras, and delete the package lists afterwards. On Alpine, `apk add --no-cache`.
</How>
</Explain>

```text
# Debian/Ubuntu-based image
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*

# Alpine-based image
RUN apk add --no-cache curl
```

In scripts and Dockerfiles use `apt-get` (stable output for machines); `apt` is the friendlier version for humans.

### 9. Other ways software is installed

| Method | Example | Notes |
| --- | --- | --- |
| Language package managers | `npm`, `pip`, `cargo` | For libraries of one language, not system software |
| Snap / Flatpak | `snap install code` | Self-contained apps with their own dependencies |
| Official binaries | Download a Go binary and put it in `/usr/local/bin` | Verify the checksum |
| Version managers | `nvm`, `pyenv` | Several versions of Node.js / Python side by side |
| From source | `./configure && make && make install` | Last resort; no automatic updates |

## Hands-on

```bash
# 1. Identify the system
. /etc/os-release && echo "ID=$ID"

# 2. Is a package installed?
for p in bash coreutils this-package-does-not-exist; do
  if dpkg -s "$p" > /dev/null 2>&1; then echo "$p: installed"; else echo "$p: not installed"; fi
done

# 3. Which package provides a command?
dpkg -S "$(readlink -f "$(command -v ls)")" | cut -d: -f1 | sed 's/^/ls comes from: /'

# 4. How many packages are installed? (a number)
n=$(dpkg-query -f '.\n' -W | wc -l); (( n > 50 )) && echo "more than 50 packages installed"
```

```text output
ID=ubuntu
bash: installed
coreutils: installed
this-package-does-not-exist: not installed
ls comes from: coreutils
more than 50 packages installed
```

On your own Ubuntu machine, also try: `apt list --upgradable`, `apt show nginx`, `apt search jq`, `apt-cache policy openssl`.

## Real-world example

A company runs a Node.js API in Docker. A weekly Trivy scan in CI reports 140 vulnerabilities in the image, 6 of them critical.

1. Most findings are in OS packages from the `node:20` base image (full Debian with compilers, `git`, `imagemagick`…), which the app never uses.
2. They switch to `node:22-bookworm-slim` with `--no-install-recommends`, and later to a **distroless** Node image for the final stage. Findings drop to a handful.
3. They rebuild images **weekly**, not only when code changes, so base-image security patches get picked up.
4. On the remaining VMs, they enable `unattended-upgrades` for security updates and schedule reboots when a kernel update requires one.
5. A developer had added a random PPA to get a newer `ffmpeg`. Security review removes it: one unknown maintainer could push a root-level update to every server.

## Common mistakes

- **Running `apt install` without `apt update`** — old versions, or "Unable to locate package".
- **`curl https://… | sudo bash`** from a blog post. You are running unreviewed code as root.
- **Mixing package sources** (system `nodejs` plus a NodeSource repo plus `nvm`) and not knowing which `node` runs.
- **Never upgrading** "because it works", until a known vulnerability is exploited.
- **Fat container images** with compilers, editors and debug tools in production.
- **Using `apt` in Dockerfiles and scripts**; it warns that its CLI is not stable — use `apt-get`.
- **Assuming Alpine works the same as Debian.** musl differs from glibc; some prebuilt binaries and Python wheels break.

## Security lens

<Callout type="security">
Every installed package is code running on your machine, often as root. The package manager is part of your supply chain — treat repositories, keys and versions as security decisions.
</Callout>

- **Patch management:** a large share of real-world breaches use vulnerabilities that already had a patch. Automate security updates, track reboots, and rebuild container images regularly.
- **Minimal installs:** fewer packages means fewer vulnerabilities and fewer tools for an attacker who gets in (no `curl`, `wget` or compilers in production images).
- **Trusted repositories only:** each added repo and key can deliver root-level code to your servers. Prefer official distribution repos and well-known vendors; document every third-party repo.
- **Signature verification:** never disable it (`--allow-unauthenticated`, `gpgcheck=0`, `[trusted=yes]`). It is what stops a tampered mirror.
- **Pin and verify** in CI: pin versions or image digests (`node:22-alpine@sha256:…`) so builds cannot change silently.
- **Know what you run:** an inventory of installed packages (an SBOM) lets you answer "are we affected?" within minutes when the next big vulnerability (like Log4Shell or the 2024 `xz` backdoor) is announced.

## Interview questions

<QA q="What is the difference between apt update and apt upgrade?">
`apt update` downloads the latest package indexes from the configured repositories; it installs nothing. `apt upgrade` installs newer versions of already-installed packages based on those indexes. You run update first so upgrade and install see current versions.
</QA>

<QA q="What is the difference between dpkg and apt (or rpm and dnf)?">
dpkg and rpm are low-level tools that install, remove and query individual package files; they do not download packages or resolve dependencies from repositories. apt and dnf are high-level tools built on top of them that use repositories, resolve and download dependencies, verify signatures and manage upgrades.
</QA>

<QA q="How does a package manager know a package was not tampered with?">
Repositories publish a signed index. The client verifies that signature with the repository's public key that was installed beforehand, and the index contains checksums for every package. Downloaded packages are checked against those checksums, so tampered indexes or packages are rejected.
</QA>

<QA q="How do you keep a container image's OS packages patched?">
Use a minimal, regularly updated base image (slim, Alpine or distroless), install only what is needed with no recommended extras, rebuild and redeploy images on a schedule rather than only on code changes, scan images in CI with a tool like Trivy, and pin base images by digest while updating them deliberately.
</QA>

<QA q="Why is piping curl into sudo bash considered risky?">
It downloads and immediately executes a script as root without any review, signature check or record of what changed. If the site, the network path or the script is compromised, the attacker gets root. Safer: download the script, read it, verify a checksum or signature, or use the vendor's signed package repository instead.
</QA>

## Key terms

<Terms>
  <Term name="Package">Software plus metadata, packaged for installation (.deb, .rpm, .apk).</Term>
  <Term name="Repository">A server hosting packages and a signed index of them.</Term>
  <Term name="Dependency">A package another package requires to work.</Term>
  <Term name="apt / dnf / apk">High-level package managers for Debian/Ubuntu, RHEL/Amazon Linux and Alpine.</Term>
  <Term name="dpkg / rpm">Low-level tools that handle individual package files.</Term>
  <Term name="Signing key">Public key used to verify repository indexes and packages.</Term>
  <Term name="Backporting">Applying a security fix to an older version line without upgrading to a new release.</Term>
  <Term name="LTS">Long-term support release with years of security updates.</Term>
  <Term name="musl / glibc">Alternative C standard libraries; Alpine uses musl, most distributions glibc.</Term>
</Terms>

## Practice

1. Run `apt list --installed | wc -l` (or `dnf list installed | wc -l`). How many packages are on your system?
2. Find which package owns `/bin/ls` on your system.
3. Install and fully remove a small package (`cowsay` or `tree`) with update, install, purge and autoremove.
4. Write a two-line Dockerfile `RUN` instruction that installs `curl` on Debian in the image-size-friendly way.
5. Check whether your system needs a reboot after updates.
