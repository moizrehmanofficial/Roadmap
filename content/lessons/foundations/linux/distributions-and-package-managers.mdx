<BigIdea>
<Tr>
<En>
On Linux you don't download installers from websites. You ask the **package manager** (`apt`, `dnf` or `apk`), which is like an **official app store**: it downloads trusted software, installs everything it needs, and updates it all with one command.
</En>
<Ur>
Linux par aap websites se installers download nahi karte. Aap **package manager** (`apt`, `dnf` ya `apk`) se kehte hain, jo ek **official app store** jaisa hai: ye bharosemand software download karta hai, us ki har zaroori cheez install karta hai, aur ek command se sab update karta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Distribution**: a complete Linux system. There are three big **families**:
  - **Debian / Ubuntu** → package manager **apt**
  - **Red Hat / Rocky / Amazon Linux** → **dnf**
  - **Alpine** (tiny, used in Docker) → **apk**
- **Package**: a program bundled with information about it (version, what else it needs).
- **Package manager**: the tool that installs, updates and removes packages.

</En>
<Ur>

- **Distribution**: mukammal Linux system. Teen bare **khandan** hain:
  - **Debian / Ubuntu** → package manager **apt**
  - **Red Hat / Rocky / Amazon Linux** → **dnf**
  - **Alpine** (bohot chhoti, Docker me) → **apk**
- **Package**: program, us ki maloomat ke saath bandha hua (version, aur kya kya chahiye).
- **Package manager**: wo tool jo packages install, update aur remove karta hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Commands differ** between families: an Ubuntu tutorial (`apt install`) won't work on Amazon Linux (`dnf install`).
- **Security**: most server hacks use problems that **already have a fix**. The package manager is how you install those fixes.
- **Docker**: your base image decides which package manager and how big your image is.

</En>
<Ur>

- Khandanon me **commands alag** hain: Ubuntu ka tutorial (`apt install`) Amazon Linux (`dnf install`) par nahi chalega.
- **Security**: zyada tar server hacks un masail se hote hain jin ka **hal pehle se mojood** hota hai. Package manager hi wo hal install karne ka tareeqa hai.
- **Docker**: aap ki base image tay karti hai ke kaun sa package manager hoga aur image kitni bari hogi.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- setting up a new server
- installing a tool like `nginx`, `git` or `curl`
- writing a Dockerfile
- applying security updates (every week)

</En>
<Ur>

- naya server tayyar karte waqt
- `nginx`, `git` ya `curl` jaisa tool install karte waqt
- Dockerfile likhte waqt
- security updates lagate waqt (har hafte)

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

On Ubuntu, almost always these two steps:

1. `sudo apt update`: refresh the list of available software.
2. `sudo apt install nginx`: install it.

Keep the server patched with `sudo apt upgrade`.

</En>
<Ur>

Ubuntu par taqreeban hamesha ye do qadam:

1. `sudo apt update`: dastiyab software ki list taaza karein.
2. `sudo apt install nginx`: install karein.

Server ko `sudo apt upgrade` se updated rakhein.

</Ur>
</Tr>
</How>
</Glance>

<Step title="Which distribution am I on?">

<Tr>
<En>

Before you follow any guide, check which family you're on. Every modern distro describes itself in `/etc/os-release`. A script can read the `ID` from it and choose the right command:

</En>
<Ur>

Kisi bhi guide par amal karne se pehle check karein ke aap kis khandan par hain. Har jadeed distro `/etc/os-release` me apna taaruf likhti hai. Script us me se `ID` parh kar sahi command chun sakti hai:

</Ur>
</Tr>

```bash
. /etc/os-release
case "$ID" in
  ubuntu|debian)                    family="Debian family → use apt" ;;
  rhel|rocky|almalinux|fedora|amzn) family="Red Hat family → use dnf" ;;
  alpine)                           family="Alpine → use apk" ;;
  *)                                family="other: $ID" ;;
esac
echo "$family"
```

```text output
Debian family → use apt
```

<Happened>
<Tr>
<En>

- `. /etc/os-release` loads values like `ID=ubuntu` into the shell.
- `case` compares `$ID` with each list, like a chain of "if" checks.
- This machine is Ubuntu, so it prints the Debian line. On Red Hat or Alpine you'd see their lines instead.

</En>
<Ur>

- `. /etc/os-release` `ID=ubuntu` jaisi values shell me load karta hai.
- `case` `$ID` ko har list se milata hai, "agar" checks ki ek zanjeer ki tarah.
- Ye machine Ubuntu hai, isliye Debian wali line print hui. Red Hat ya Alpine par un ki lines dikhengi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Release types: LTS vs rolling">

<Tr>
<En>

Distros release new versions on different schedules:

- **LTS / stable** (Ubuntu 24.04 LTS, Debian 12, RHEL 9): changes slowly, gets security fixes for **years**. Best for **servers**.
- **Regular** (Ubuntu 25.10, Fedora): newer features, shorter support.
- **Rolling** (Arch): always the newest software, but more things change.

Ubuntu LTS comes out every 2 years in April (22.04, 24.04). Rule for servers: pick an **LTS** and upgrade before it reaches **end of life**, when security updates stop.

</En>
<Ur>

Distros naye versions alag alag schedule par nikalti hain:

- **LTS / stable** (Ubuntu 24.04 LTS, Debian 12, RHEL 9): aahista badalti hai, **saalon** tak security fixes milte hain. **Servers** ke liye behtareen.
- **Regular** (Ubuntu 25.10, Fedora): naye features, kam support.
- **Rolling** (Arch): hamesha naya software, lekin zyada cheezen badalti hain.

Ubuntu LTS har 2 saal baad April me aata hai (22.04, 24.04). Servers ka qaida: **LTS** chunein aur **end of life** (jab security updates band hon) se pehle upgrade karein.

</Ur>
</Tr>

</Step>

<Step title="Packages and repositories">

<Tr>
<En>

A **package** is a program's files plus a label: name, version, description, and what other packages it needs. **Repositories** are servers that host thousands of tested, signed packages, so you never have to download installers from random websites.

`dpkg` can tell you about installed packages, and which package a file came from:

</En>
<Ur>

**Package** program ki files + ek label hai: naam, version, tafseel, aur use kaun se doosre packages chahiyen. **Repositories** wo servers hain jahan hazaron test shuda, signed packages hote hain, taa ke aap ko kabhi idhar udhar ki websites se installers download na karne parein.

`dpkg` installed packages ke baare me bata sakta hai, aur ye bhi ke koi file kis package se aayi:

</Ur>
</Tr>

```bash
dpkg -s bash | grep -E '^(Package|Status|Priority):'
dpkg -S "$(readlink -f /bin/bash)" | cut -d: -f1 | sed 's/^/the file \/bin\/bash belongs to package: /'
```

```text output
Package: bash
Status: install ok installed
Priority: required
the file /bin/bash belongs to package: bash
```

<Happened>
<Tr>
<En>

- `dpkg -s bash` shows the label of the installed `bash` package: it's installed, and its priority is **required** (the system needs it).
- `dpkg -S <file>` answers "which package put this file here?". The `/bin/bash` program belongs to the `bash` package.
- The list of repositories lives in `/etc/apt/sources.list.d/` (Ubuntu) or `/etc/yum.repos.d/` (Red Hat).

</En>
<Ur>

- `dpkg -s bash` installed `bash` package ka label dikhata hai: ye install hai, aur is ki priority **required** hai (system ko is ki zaroorat hai).
- `dpkg -S <file>` jawab deta hai "ye file kis package ne yahan rakhi?". `/bin/bash` program `bash` package ka hai.
- Repositories ki list `/etc/apt/sources.list.d/` (Ubuntu) ya `/etc/yum.repos.d/` (Red Hat) me hoti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="apt update vs apt upgrade (the #1 confusion)">

<Tr>
<En>

- `apt update` = **refresh the shop's catalogue**. It downloads the latest list of what's available. It installs **nothing**.
- `apt upgrade` = **actually buy** the newer versions of what you already have.

If you `apt install` without a recent `apt update`, you may get an old version or "Unable to locate package".

</En>
<Ur>

- `apt update` = **dukaan ka catalogue taaza karna**. Ye dastiyab cheezon ki naye list download karta hai. Ye **kuch bhi** install nahi karta.
- `apt upgrade` = jo pehle se hai us ke naye versions **waqai khareedna**.

Agar aap taaza `apt update` ke baghair `apt install` karein, to purana version mil sakta hai ya "Unable to locate package" aa sakta hai.

</Ur>
</Tr>

```text
$ sudo apt update
Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease
Get:2 http://security.ubuntu.com/ubuntu noble-security InRelease [126 kB]
...
23 packages can be upgraded. Run 'apt list --upgradable' to see them.

$ sudo apt upgrade -y
The following packages will be upgraded:
  libssl3 openssl openssh-server ...
```

<Happened>
<Tr>
<En>

- `update` checked the repositories and found **23** packages with newer versions.
- `upgrade -y` installed them (`-y` = answer "yes" automatically). Notice `openssl` and `openssh-server`: security-critical software.
- `apt list --upgradable` shows what's waiting. `full-upgrade` is allowed to remove packages if needed to finish an upgrade.

</En>
<Ur>

- `update` ne repositories check kin aur **23** packages ke naye versions paye.
- `upgrade -y` ne unhe install kar diya (`-y` = khud ba khud "haan" kehna). `openssl` aur `openssh-server` dekhein: security ke liye bohot ahem software.
- `apt list --upgradable` dikhata hai ke kya intezar me hai. `full-upgrade` ko zaroorat par packages hatane ki bhi ijazat hai taa ke upgrade mukammal ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Install and remove software">

<Tr>
<En>

Installing downloads the package **and everything it needs**, unpacks it, and runs its setup. Removing has levels:

- `apt remove pkg`: delete the program, **keep** its settings files.
- `apt purge pkg`: delete the program **and** its settings.
- `apt autoremove`: delete helper packages nobody needs any more.

</En>
<Ur>

Install karna package **aur us ki har zaroorat** download karta hai, kholta hai, aur us ka setup chalata hai. Hatane ke darje hain:

- `apt remove pkg`: program hatao, us ki settings files **rehne do**.
- `apt purge pkg`: program **aur** us ki settings dono hatao.
- `apt autoremove`: wo madadgar packages hatao jin ki ab kisi ko zaroorat nahi.

</Ur>
</Tr>

```text
$ sudo apt install -y nginx
The following additional packages will be installed:
  nginx-common libnginx-mod-http-...       ← dependencies pulled in automatically
Setting up nginx (1.24.0-2ubuntu7) ...

$ nginx -v
nginx version: nginx/1.24.0 (Ubuntu)

$ sudo apt purge -y nginx && sudo apt autoremove -y
```

</Step>

<Step title="Dependencies: programs need other programs">

<Tr>
<En>

Most programs rely on shared **libraries** (ready-made code) and other programs. The package manager reads each package's "needs" list and installs what's missing. Doing this by hand leads to "dependency hell": missing or clashing libraries.

A nice side effect: a shared library like `openssl` is installed **once** and used by many programs, so **one** security update fixes all of them.

</En>
<Ur>

Zyada tar programs share shuda **libraries** (bana banaya code) aur doosre programs par chalte hain. Package manager har package ki "zarooraton" ki list parhta hai aur jo kam ho wo install karta hai. Ye haath se karna "dependency hell" banata hai: gum ya takrati libraries.

Ek achha faida: `openssl` jaisi share shuda library **ek dafa** install hoti hai aur kai programs istemal karte hain, isliye **ek** security update sab ko theek kar deti hai.

</Ur>
</Tr>

```bash
apt-cache depends curl 2>/dev/null | grep -m3 'Depends' | sed 's/^ *//'
```

```text output
Depends: libc6
Depends: libcurl4t64
Depends: zlib1g
```

<Happened>
<Tr>
<En>

- `apt-cache depends curl` lists what `curl` needs. The first three: the basic C library (`libc6`), the curl library (`libcurl…`) and a compression library (`zlib1g`).
- The exact names change a little between releases.

</En>
<Ur>

- `apt-cache depends curl` batata hai `curl` ko kya chahiye. Pehli teen: bunyadi C library (`libc6`), curl library (`libcurl…`) aur compression library (`zlib1g`).
- Asal naam releases ke darmiyan thore badalte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Trust: signed repositories">

<Tr>
<En>

How do you know a package wasn't changed by a hacker on the way? Repositories **sign** their package lists with a secret key. Your computer has the matching **public key** and checks the signature before installing anything. A changed package fails the check and is rejected.

When you add a third-party repository (Docker, Node.js, PostgreSQL), add its key **only** from the vendor's official instructions, and link the key to that one repo with `signed-by=`:

</En>
<Ur>

Aap ko kaise pata ke raste me kisi hacker ne package badla nahi? Repositories apni package lists ko ek khufiya key se **sign** karti hain. Aap ke computer par us ki **public key** hoti hai jo install se pehle signature check karti hai. Badla hua package check me fail hota hai aur rad ho jata hai.

Jab aap koi third-party repository (Docker, Node.js, PostgreSQL) shamil karein, to us ki key **sirf** vendor ki official hidayat se shamil karein, aur `signed-by=` se key ko sirf usi repo se jorein:

</Ur>
</Tr>

```text
# Official Docker repository on Ubuntu (from Docker's documentation)
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
echo "deb [signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update && sudo apt install -y docker-ce
```

<Happened>
<Tr>
<En>

- Line 2 downloads Docker's **public key** into `/etc/apt/keyrings/`.
- Line 3 adds Docker's repository, saying "only trust packages signed by **that** key".
- Then the normal `update` + `install`.

</En>
<Ur>

- Line 2 Docker ki **public key** `/etc/apt/keyrings/` me download karti hai.
- Line 3 Docker ki repository shamil karti hai, ye keh kar ke "sirf **us** key se signed packages par bharosa karo".
- Phir aam `update` + `install`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Packages inside Dockerfiles">

<Tr>
<En>

When you build a Docker image, you want it **small** and with no leftover junk:

- do `update` and `install` in **one** `RUN` line
- skip "recommended" extras
- delete the downloaded lists at the end
- on Alpine, `apk add --no-cache` does all this

In scripts and Dockerfiles use `apt-get` (stable for machines); `apt` is the friendlier version for humans.

</En>
<Ur>

Jab aap Docker image banate hain, to aap use **chhota** aur bacha kucha kachra ke baghair chahte hain:

- `update` aur `install` **ek** `RUN` line me karein
- "recommended" izafi cheezen chhor dein
- aakhir me download ki hui lists delete kar dein
- Alpine par `apk add --no-cache` ye sab khud karta hai

Scripts aur Dockerfiles me `apt-get` istemal karein (machines ke liye stable); `apt` insanon ke liye zyada dostana version hai.

</Ur>
</Tr>

```text
# Debian/Ubuntu-based image
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*

# Alpine-based image
RUN apk add --no-cache curl
```

</Step>

## Common mistakes

<Compare>
<Bad title="Install without update">

```text
sudo apt install nginx
E: Unable to locate package nginx
```

</Bad>
<Good title="Update first">

```text
sudo apt update && sudo apt install -y nginx
```

</Good>
</Compare>

<Compare>
<Bad title="Never upgrading">

<Tr>
<En>"It works, don't touch it." Until a known, already-fixed security hole is used to break in.</En>
<Ur>"Chal raha hai, haath na lagao." Jab tak koi mashhoor, pehle se theek shuda security surakh istemal kar ke andar na ghus jaye.</Ur>
</Tr>

</Bad>
<Good title="Patch regularly">

<Tr>
<En>`sudo apt update && sudo apt upgrade -y` every week, or turn on `unattended-upgrades` for automatic security updates.</En>
<Ur>Har hafte `sudo apt update && sudo apt upgrade -y`, ya khud kaar security updates ke liye `unattended-upgrades` on karein.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Many sources for the same tool">

<Tr>
<En>System `nodejs` + a NodeSource repo + `nvm`, and nobody knows which `node` actually runs.</En>
<Ur>System ka `nodejs` + NodeSource repo + `nvm`, aur kisi ko nahi pata ke asal me kaun sa `node` chal raha hai.</Ur>
</Tr>

</Bad>

<Tr>
<En>Pick one way to install each tool, and check with `command -v node` and `node -v`.</En>

## Try it yourself

<Challenge title="Explore your packages">

<Tr>
<En>
On an Ubuntu or Debian terminal, run this lab. It checks whether packages are installed, finds where `ls` comes from, and counts your packages. Your output should match ours.
</En>
<Ur>
Ubuntu ya Debian terminal par ye lab chalayen. Ye check karta hai ke packages install hain ya nahi, `ls` kahan se aaya, aur aap ke packages ginta hai. Aap ka output hamare jaisa hona chahiye.
</Ur>
</Tr>

```bash
# 1. Identify the system
. /etc/os-release && echo "ID=$ID"

# 2. Is a package installed?
for p in bash coreutils this-package-does-not-exist; do
  if dpkg -s "$p" > /dev/null 2>&1; then echo "$p: installed"; else echo "$p: not installed"; fi
done

# 3. Which package provides a command?
dpkg -S "$(readlink -f "$(command -v ls)")" | cut -d: -f1 | sed 's/^/ls comes from: /'

# 4. How many packages are installed? (a number)
n=$(dpkg-query -f '.\n' -W | wc -l); (( n > 50 )) && echo "more than 50 packages installed"
```

```text output
ID=ubuntu
bash: installed
coreutils: installed
this-package-does-not-exist: not installed
ls comes from: coreutils
more than 50 packages installed
```

<DeepDive title="Other ways software gets installed">

| Method | Example | Notes |
| --- | --- | --- |
| Language package managers | `npm`, `pip`, `cargo` | For libraries of one language, not system software |
| Snap / Flatpak | `snap install code` | Self-contained apps with their own dependencies |
| Official binaries | Download a Go binary and put it in `/usr/local/bin` | Verify the checksum |
| Version managers | `nvm`, `pyenv` | Several versions of Node.js / Python side by side |
| From source | `./configure && make && make install` | Last resort; no automatic updates |

`dpkg` and `rpm` are the low-level tools that handle single package files. `apt` and `dnf` sit on top and add repositories, dependency solving, signature checks and upgrades.

Alpine uses **musl** instead of **glibc** (the C library most distros use). Some prebuilt binaries and Python wheels break on Alpine because of this.

</DeepDive>

<DeepDive title="Real world: 140 vulnerabilities in one image">

A company runs a Node.js API in Docker. A weekly Trivy scan in CI reports 140 vulnerabilities in the image, 6 of them critical.

1. Most findings are in OS packages from the `node:20` base image (full Debian with compilers, `git`, `imagemagick`…), which the app never uses.
2. They switch to `node:22-bookworm-slim` with `--no-install-recommends`, and later to a **distroless** Node image for the final stage. Findings drop to a handful.
3. They rebuild images **weekly**, not only when code changes, so base-image security patches get picked up.
4. On the remaining VMs, they enable `unattended-upgrades` for security updates and schedule reboots when a kernel update needs one.
5. A developer had added a random PPA to get a newer `ffmpeg`. Security review removes it: one unknown maintainer could push a root-level update to every server.

</DeepDive>

<DeepDive title="Security lens">

Every installed package is code running on your machine, often as root. The package manager is part of your **supply chain**.

- **Patch management:** a large share of real breaches use vulnerabilities that already had a patch. Automate security updates, track reboots, rebuild container images regularly.
- **Minimal installs:** fewer packages = fewer vulnerabilities and fewer tools for an attacker (no `curl`, `wget` or compilers in production images).
- **Trusted repositories only:** each added repo and key can deliver root-level code to your servers. Document every third-party repo.
- **Signature verification:** never disable it (`--allow-unauthenticated`, `gpgcheck=0`, `[trusted=yes]`).
- **Pin and verify** in CI: pin versions or image digests (`node:22-alpine@sha256:…`) so builds can't change silently.
- **Know what you run:** a package inventory (an SBOM) lets you answer "are we affected?" in minutes when the next big vulnerability (like Log4Shell or the 2024 `xz` backdoor) is announced.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between apt update and apt upgrade?">
`apt update` downloads the latest package indexes from the configured repositories; it installs nothing. `apt upgrade` installs newer versions of already-installed packages based on those indexes. You run update first so upgrade and install see current versions.
</QA>

<QA q="What is the difference between dpkg and apt (or rpm and dnf)?">
dpkg and rpm are low-level tools that install, remove and query individual package files; they do not download packages or resolve dependencies from repositories. apt and dnf are high-level tools built on top of them that use repositories, resolve and download dependencies, verify signatures and manage upgrades.
</QA>

<QA q="How does a package manager know a package was not tampered with?">
Repositories publish a signed index. The client verifies that signature with the repository's public key that was installed beforehand, and the index contains checksums for every package. Downloaded packages are checked against those checksums, so tampered indexes or packages are rejected.
</QA>

<QA q="How do you keep a container image's OS packages patched?">
Use a minimal, regularly updated base image (slim, Alpine or distroless), install only what is needed with no recommended extras, rebuild and redeploy images on a schedule rather than only on code changes, scan images in CI with a tool like Trivy, and pin base images by digest while updating them deliberately.
</QA>

<QA q="Why is piping curl into sudo bash considered risky?">
It downloads and immediately executes a script as root without any review, signature check or record of what changed. If the site, the network path or the script is compromised, the attacker gets root. Safer: download the script, read it, verify a checksum or signature, or use the vendor's signed package repository instead.
</QA>

</DeepDive>
