<Callout type="tip" title="In one minute">
A **disk** (e.g. `/dev/nvme1n1`) is split into **partitions**, each formatted with a **file system** (ext4, XFS) and **mounted** at a folder so it appears in the one Linux tree. `df -h` shows how full each mounted file system is; `du -sh *` shows what uses the space; `lsblk` lists disks. To add a new disk: find it with `lsblk`, format with `mkfs.ext4`, `mount` it, and add it to `/etc/fstab` using its **UUID** so it mounts at boot. A full disk breaks databases, logs and deploys — monitor it.
</Callout>

## Start from zero

### From a raw disk to a folder you can use

A new disk is like an empty plot of land. Before anyone can live there you must divide it (partitions), build a structure (a file system), and connect it to the town's road network (mount it at a folder).

<Callout type="analogy">
A **new cupboard** delivered to your house: first you decide the **shelves** (partitions), then you add **labelled boxes and dividers** so things can be found (formatting with a file system), and finally you **put it in a room** and write "Documents cupboard — bedroom" on the house plan (mounting at `/data` and adding it to `/etc/fstab`). Until it is placed in a room, nobody can use it.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Block device** | A disk-like device Linux reads in blocks | `/dev/sda`, `/dev/nvme0n1` |
| **Partition** | A section of a disk | `/dev/sda1`, `/dev/nvme0n1p1` |
| **File system** | The structure that stores files on a partition | ext4, XFS |
| **Format (mkfs)** | Create a new, empty file system (erases data!) | `mkfs.ext4 /dev/sdb1` |
| **Mount** | Attach a file system at a folder | `mount /dev/sdb1 /data` |
| **Mount point** | The folder where it appears | `/data` |
| **fstab** | The list of file systems to mount at boot | `/etc/fstab` |
| **UUID** | A unique ID of a file system that never changes | `3f2a…-…` |

## What is it?

```text
Physical / cloud disk      /dev/nvme1n1  (100 GiB EBS volume)
   └─ partition            /dev/nvme1n1p1
        └─ file system     ext4
             └─ mounted at /data   ← you use it as a normal folder
```

| Command | Shows / does |
| --- | --- |
| `lsblk` | Disks, partitions, sizes, mount points |
| `df -h` | Used / free space per mounted file system |
| `du -sh path` | Space used by files and folders |
| `findmnt` | What is mounted where, with options |
| `blkid` | File system types and UUIDs |
| `mkfs.ext4`, `mkfs.xfs` | Create a file system |
| `mount`, `umount` | Attach / detach |
| `/etc/fstab` | Mount at boot |

## Why does it matter?

- **"No space left on device"** stops databases, logging, uploads, Docker builds and deploys. It is one of the most common production incidents.
- **Cloud servers** come with a small root disk; data belongs on separate **volumes** (AWS EBS, Azure Managed Disks) that can be resized, snapshotted and moved.
- **A wrong fstab line** can stop a server from booting.
- **Security:** mount options like `noexec` on `/tmp`; encrypting disks (LUKS, cloud encryption) protects data at rest.

## When and where do you use it?

| Situation | Commands |
| --- | --- |
| Disk full alert | `df -h`, `du -xh --max-depth=1 / \| sort -rh \| head` |
| Attached a new cloud volume | `lsblk`, `mkfs`, `mount`, `fstab` |
| Volume resized in the cloud console | `growpart`, `resize2fs` / `xfs_growfs` |
| "Device is busy" when unmounting | `lsof +f -- /data`, `fuser -vm /data` |
| Space not freed after deleting logs | `lsof +L1` |

## Concepts one by one

### 1. Disks and partitions: `lsblk`

<Explain>
<What>
`lsblk` lists block devices (disks), their partitions, sizes and where they are mounted.
</What>
<Why>
First step to understand the storage of any machine, and to find a newly attached disk.
</Why>
<When>
New servers, new volumes, disk problems.
</When>
<Where>
Disks appear as `/dev/sdX` (SATA/SCSI, many VMs), `/dev/nvmeXnY` (NVMe, AWS Nitro), `/dev/vdX` (KVM VMs).
</Where>
<How>
`lsblk -f` adds file system types and UUIDs.
</How>
</Explain>

```text
$ lsblk
NAME         MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
nvme0n1      259:0    0   20G  0 disk
├─nvme0n1p1  259:1    0 19.9G  0 part /             ← root file system
└─nvme0n1p15 259:2    0  106M  0 part /boot/efi
nvme1n1      259:3    0  100G  0 disk               ← new volume: no partitions, not mounted
```

### 2. How full is it? `df`

<Explain>
<What>
**d**isk **f**ree: size, used, available and use% of every mounted file system.
</What>
<Why>
Answers "which disk is full?" instantly.
</Why>
<When>
Alerts, before big uploads or backups, daily checks.
</When>
<Where>
Every system.
</Where>
<How>
`df -h` (human sizes), `df -h /var` (the file system that holds `/var`), `df -i` (inodes), `df -hT` (with types).
</How>
</Explain>

```bash
df -h / | awk 'NR==1 {print $1, $2, $3, $4, $5, $6} NR==2 {print "<device>", "<size>", "<used>", "<avail>", "<use%>", $6}'
used=$(df --output=pcent / | tail -1 | tr -dc '0-9')
(( used < 100 )) && echo "root file system is below 100% — OK for now"
```

```text output
Filesystem Size Used Avail Use% Mounted
<device> <size> <used> <avail> <use%> /
root file system is below 100% — OK for now
```

Real output:

```text
$ df -h
Filesystem       Size  Used Avail Use% Mounted on
/dev/nvme0n1p1    20G   18G  1.6G  92% /          ← almost full!
/dev/nvme1n1     100G   12G   83G  13% /data
tmpfs            1.9G     0  1.9G   0% /dev/shm
```

### 3. What uses the space? `du`

<Explain>
<What>
**d**isk **u**sage: adds up the size of files and folders.
</What>
<Why>
`df` says a disk is full; `du` finds **what** filled it.
</Why>
<When>
Every disk-full incident.
</When>
<Where>
Usually `/var/log`, `/var/lib/docker`, `/var/lib/mysql`, `/home`, `/tmp`, `node_modules`, old backups.
</Where>
<How>
Drill down: `sudo du -xh --max-depth=1 / | sort -rh | head`, then repeat inside the biggest folder. `-x` stays on one file system.
</How>
</Explain>

```bash
mkdir -p disk/{logs,uploads,cache}
head -c 5000000 /dev/zero > disk/logs/app.log
head -c 1500000 /dev/zero > disk/uploads/photo.jpg
head -c 100000  /dev/zero > disk/cache/x.bin
du -h --apparent-size --max-depth=1 disk | sort -rh
```

```text output
6.3M	disk
4.8M	disk/logs
1.5M	disk/uploads
98K	disk/cache
```

A real drill-down usually looks like `/` → `/var` (18G) → `/var/lib` → `/var/lib/docker` (15G) — then `docker system df` and `docker system prune` (carefully).

### 4. Formatting: creating a file system

<Explain>
<What>
`mkfs` writes an empty file system onto a partition or disk.
</What>
<Why>
A new disk has no structure for files.
</Why>
<When>
Only on **new, empty** disks.
</When>
<Where>
New cloud volumes, new physical disks.
</Where>
<How>
`sudo mkfs.ext4 /dev/nvme1n1` (or `mkfs.xfs`). **This erases everything on that device** — double-check the name with `lsblk` first.
</How>
</Explain>

```bash
truncate -s 64M disk.img              # a 64 MB file pretending to be a disk
mkfs.ext4 -q -F -L practice disk.img  # format it (safe: it is just a file)
blkid -o value -s TYPE disk.img
blkid -o value -s LABEL disk.img
```

```text output
ext4
practice
```

| File system | Typical use |
| --- | --- |
| ext4 | Default on Ubuntu/Debian; safe general choice |
| XFS | Default on RHEL/Amazon Linux; great for large files and databases |
| Btrfs / ZFS | Snapshots, checksums, advanced features |
| vfat / exFAT | USB sticks, EFI boot partition |
| tmpfs | In-memory, e.g. `/dev/shm`, `/run` |

### 5. Mounting and unmounting

<Explain>
<What>
Attaching a file system to a folder (`mount`) and detaching it (`umount`).
</What>
<Why>
Linux has one tree; a disk is only usable once mounted somewhere in it.
</Why>
<When>
After formatting a new disk; when moving or checking disks.
</When>
<Where>
Mount points like `/data`, `/mnt/backup`, `/var/lib/postgresql`.
</Where>
<How>
`sudo mkdir -p /data && sudo mount /dev/nvme1n1 /data`. `findmnt /data` confirms. `sudo umount /data` (note: **umount**, no "n"). "target is busy" means a process is using it — find it with `lsof +f -- /data`.
</How>
</Explain>

```text
$ sudo mkdir -p /data
$ sudo mount /dev/nvme1n1 /data
$ findmnt /data
TARGET SOURCE       FSTYPE OPTIONS
/data  /dev/nvme1n1 ext4   rw,relatime
$ df -h /data
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme1n1     98G   24K   93G   1% /data
```

### 6. Mounting at boot: `/etc/fstab` and UUIDs

<Explain>
<What>
`/etc/fstab` lists file systems that should be mounted automatically at boot.
</What>
<Why>
A manual `mount` disappears at reboot — the app would then write to the root disk instead of `/data`.
</Why>
<When>
After mounting any permanent disk.
</When>
<Where>
`/etc/fstab`.
</Where>
<How>
Use the **UUID** (from `blkid`), not `/dev/nvme1n1` — device names can change between reboots. Add `nofail` for cloud volumes so a missing volume does not stop booting. **Test with `sudo mount -a`** before rebooting.
</How>
</Explain>

```text
# /etc/fstab
# <what>                                    <where>  <type> <options>         <dump> <check>
UUID=3f2a9c1e-7b4d-4f0a-9e3a-1c2d3e4f5a6b    /data    ext4   defaults,nofail   0      2

$ sudo blkid /dev/nvme1n1
/dev/nvme1n1: UUID="3f2a9c1e-7b4d-4f0a-9e3a-1c2d3e4f5a6b" TYPE="ext4"
$ sudo umount /data && sudo mount -a && findmnt /data     ← proves the fstab line works
```

<Callout type="danger" title="A broken fstab can stop the server from booting">
A typo in `/etc/fstab` can drop the server into emergency mode — and on a cloud VM you may have no console. Always run `sudo mount -a` (and `findmnt --verify`) after editing, before rebooting.
</Callout>

### 7. Mount options

<Explain>
<What>
Settings that change how a file system behaves once mounted.
</What>
<Why>
Security and reliability: stop programs from running from `/tmp`, make backups read-only, avoid boot failures.
</Why>
<When>
Hardening servers, special-purpose mounts.
</When>
<Where>
The 4th column of `/etc/fstab`, or `mount -o`.
</Where>
<How>
Common options in the table. `findmnt -o TARGET,OPTIONS` shows the current ones.
</How>
</Explain>

| Option | Effect |
| --- | --- |
| `defaults` | Normal settings (rw, …) |
| `ro` | Read-only |
| `noexec` | Programs cannot be executed from here |
| `nosuid` | setuid bits are ignored |
| `nodev` | Device files are ignored |
| `nofail` | Do not fail boot if the device is missing |
| `noatime` | Do not update access times (less disk writing) |

### 8. Inodes: full without being full

<Explain>
<What>
Each file uses one **inode**. A file system has a fixed number of them. Millions of tiny files can use up all inodes while bytes are still free.
</What>
<Why>
"No space left on device" while `df -h` shows free space = inode exhaustion.
</Why>
<When>
Mail queues, session files, cache folders with millions of small files.
</When>
<Where>
ext4 (fixed at format time); XFS allocates inodes dynamically.
</Where>
<How>
`df -i` shows inode use. Find the folder with the most files: `sudo find / -xdev -type f | cut -d/ -f2-3 | sort | uniq -c | sort -rn | head`.
</How>
</Explain>

```bash
df -i / | awk 'NR==1 {print $1, $2, $3, $4, $5} NR==2 {print "<device>", "<inodes>", "<used>", "<free>", ($5 ~ /%$/ ? "<use%>" : $5)}'
```

```text output
Filesystem Inodes IUsed IFree IUse%
<device> <inodes> <used> <free> <use%>
```

### 9. Deleted but still using space

<Explain>
<What>
If you delete a file that a running process still has open (typically a log), the space is **not** freed until the process closes it.
</What>
<Why>
Classic incident: "I deleted the 20 GB log, but the disk is still full."
</Why>
<When>
Deleting active log files by hand.
</When>
<Where>
Long-running services writing logs.
</Where>
<How>
Find them with `sudo lsof +L1`. Fix by restarting the process, or truncate instead of deleting: `: > file` or `truncate -s 0 file`. Better: use logrotate.
</How>
</Explain>

```bash
head -c 3000000 /dev/zero > big.log
sleep 300 < big.log & holder=$!          # a process keeps the file open
rm big.log
lsof -nP -a +L1 -p "$holder" 2>/dev/null | awk 'NR>1 {print "still open after delete:", $NF, $(NF-1)}' | sed 's|/.*/big.log|.../big.log|'
kill "$holder"
```

```text output
still open after delete: (deleted) .../big.log
```

### 10. Swap

<Explain>
<What>
Disk space used as overflow memory when RAM is full.
</What>
<Why>
Prevents immediate out-of-memory kills on small servers — but swap is thousands of times slower than RAM.
</Why>
<When>
Small VPS/VMs (1–2 GB RAM). Kubernetes nodes usually run without swap.
</When>
<Where>
A swap file (`/swapfile`) or swap partition.
</Where>
<How>
`free -h` and `swapon --show` show it. Creating a 2 GB swap file is a common first step on tiny servers.
</How>
</Explain>

```text
$ sudo fallocate -l 2G /swapfile
$ sudo chmod 600 /swapfile
$ sudo mkswap /swapfile && sudo swapon /swapfile
$ echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
$ swapon --show
NAME      TYPE SIZE USED PRIO
/swapfile file   2G   0B   -2
```

### 11. Growing a cloud disk

<Explain>
<What>
Making a disk bigger after resizing the volume in the cloud console.
</What>
<Why>
Cloud volumes can grow without downtime — but Linux must be told to use the new space.
</Why>
<When>
Disk getting full on a cloud VM.
</When>
<Where>
AWS EBS, Azure disks, GCP persistent disks.
</Where>
<How>
1) Resize the volume in the console/CLI. 2) Grow the partition: `sudo growpart /dev/nvme0n1 1`. 3) Grow the file system: `sudo resize2fs /dev/nvme0n1p1` (ext4) or `sudo xfs_growfs /` (XFS). 4) Check `df -h`. Take a **snapshot** first.
</How>
</Explain>

### 12. LVM in one paragraph

<Explain>
<What>
**Logical Volume Manager** adds a flexible layer between disks and file systems: several disks become one pool (volume group) that is split into resizable logical volumes.
</What>
<Why>
Grow a volume by adding a disk, take snapshots, move data between disks online.
</Why>
<When>
On-premise servers and some cloud images (RHEL defaults to LVM).
</When>
<Where>
Devices like `/dev/mapper/vg0-data`.
</Where>
<How>
Main commands: `pvs`, `vgs`, `lvs` (show), `lvextend -r -L +10G /dev/vg0/data` (grow volume and file system together).
</How>
</Explain>

## Hands-on

Practise the whole new-disk workflow safely with a **file** instead of a real disk:

```bash
truncate -s 100M practice.img
mkfs.ext4 -q -F practice.img
uuid=$(blkid -o value -s UUID practice.img)
echo "UUID looks like: ${uuid:0:8}-…" | sed -E 's/: [0-9a-f]{8}/: XXXXXXXX/'
echo "fstab line would be: UUID=<uuid> /mnt/practice ext4 defaults,nofail 0 2" 
ls -lh practice.img | awk '{print "image file size:", $5}'
rm practice.img
```

```text output
UUID looks like: XXXXXXXX-…
fstab line would be: UUID=<uuid> /mnt/practice ext4 defaults,nofail 0 2
image file size: 100M
```

On a VM where you have root, you can go further: `sudo mkdir /mnt/practice && sudo mount -o loop practice.img /mnt/practice && df -h /mnt/practice`, then `sudo umount /mnt/practice`.

## Real-world example

A PostgreSQL server on EC2 is designed for safety and easy growth:

1. **Root volume** (30 GB, gp3) holds only the OS and packages.
2. **Data volume** (200 GB, gp3, **encrypted with KMS**) mounted at `/var/lib/postgresql` via its UUID with `defaults,nofail,noatime`.
3. **Daily EBS snapshots** via AWS Backup with 30-day retention, plus `pg_dump` to S3 (another account, versioned, Object Lock) for point-in-time recovery and ransomware resilience.
4. **CloudWatch alarm** when disk usage passes 80% — growing the volume online takes two commands and no downtime.
5. **Restore drill** each quarter: create a volume from a snapshot, attach it to a test instance, start PostgreSQL, check the data.

When a developer runs a wrong migration that drops a table, the team restores the snapshot to a new volume, extracts the table and loads it back — because backups existed and had been tested.

## Common mistakes

- **Running `mkfs` on the wrong device** — it erases it instantly. Always check `lsblk -f` first and look for an empty FSTYPE.
- **Using `/dev/sdb` names in fstab** — device names can change; use UUIDs.
- **Forgetting `nofail`** on extra volumes; if the volume is missing, the instance may not boot.
- **Not testing fstab** with `mount -a` before rebooting.
- **Storing data on instance store or the container's writable layer** and losing it on stop/restart.
- **Ignoring inodes**, only checking `df -h`.
- **Treating snapshots or RAID as the whole backup strategy** without off-account copies and restore tests.
- **Letting Docker fill the root disk** — prune regularly or move `/var/lib/docker` to its own volume.

## Security lens

<Callout type="security">
Data at rest is a target: stolen snapshots, readable old disks, ransomware that encrypts everything reachable. Storage choices are security choices.
</Callout>

- **Encrypt at rest:** enable EBS encryption by default in every AWS region you use; use LUKS (`cryptsetup`) for disks you manage yourself. Encrypted snapshots stay encrypted.
- **Snapshot exposure:** public or wrongly shared EBS snapshots and AMIs have leaked databases and credentials. Audit sharing settings.
- **Ransomware-resistant backups:** keep copies in a separate account, with versioning and Object Lock / immutability, so an attacker with production credentials cannot delete them.
- **Mount hardening:** `/tmp`, `/var/tmp` and `/dev/shm` with `noexec,nosuid,nodev` blocks many "download a tool to /tmp and run it" attacks (not all — scripts can still be run via an interpreter).
- **Data remanence:** deleting files or terminating a self-managed disk may leave readable data. Encryption makes old data useless without the key; destroy keys or use provider guarantees for disposal.
- **Disk exhaustion is a DoS:** uploads, logs and temp files without limits let an attacker fill the disk and crash the service. Enforce upload size limits, quotas and log rotation.

## Interview questions

<QA q="How do you add a new disk to a Linux server and make it available at /data permanently?">
Identify it with lsblk -f, create a file system with mkfs.ext4 or mkfs.xfs (after confirming it is empty), create /data and mount it, then add an /etc/fstab entry using the UUID from blkid with options like defaults,nofail. Test with umount and mount -a before rebooting.
</QA>

<QA q="df shows free space but writes fail with 'No space left on device'. Why?">
The file system has probably run out of inodes, typically because of a huge number of small files; check with df -i and find the directories with the most files. Other causes are a full quota, reserved blocks for root on ext4, or writing to a different file system than the one you checked.
</QA>

<QA q="How do you grow an EBS volume without downtime?">
Increase the volume size in AWS (console or CLI), then on the instance grow the partition with growpart (for example `growpart /dev/nvme0n1 1`) and grow the file system: resize2fs for ext4, or xfs_growfs on the mount point for XFS. Verify with df -h. No reboot is needed on modern instances.
</QA>

<QA q="What is the difference between EBS, instance store, EFS and S3?">
EBS is persistent block storage attached to one instance, like a network disk. Instance store is physically attached, very fast storage that is lost when the instance stops. EFS is a managed NFS file system that many instances can mount at once. S3 is object storage accessed over HTTP, not mounted as a normal disk, highly durable and suited for backups, static files and data lakes.
</QA>

<QA q="Why is RAID or replication not a substitute for backups?">
RAID and replication protect against hardware failure by keeping copies in sync, but they also instantly replicate mistakes, corruption, deletions and ransomware encryption. Backups are separate, point-in-time copies with retention, ideally isolated in another account or location and immutable, and they must be tested by restoring.
</QA>

## Key terms

<Terms>
  <Term name="Block device">A disk or disk-like device exposed under /dev.</Term>
  <Term name="Partition">A region of a disk with its own file system.</Term>
  <Term name="GPT / MBR">Modern and legacy partition table formats.</Term>
  <Term name="ext4 / XFS">The most common Linux file systems.</Term>
  <Term name="Mount point">The directory where a file system is attached.</Term>
  <Term name="fstab">/etc/fstab: the list of file systems mounted at boot.</Term>
  <Term name="UUID">A unique ID of a file system, stable across reboots.</Term>
  <Term name="Inode">The per-file record in a file system; there is a fixed number of them.</Term>
