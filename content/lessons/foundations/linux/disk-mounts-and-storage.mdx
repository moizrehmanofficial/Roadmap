<BigIdea>
<Tr>
<En>
A new disk is useless until you **format** it (give it a file system) and **mount** it (attach it to a folder like `/data`). And the most common storage problem of all is simple: **the disk is full**. `df -h` tells you which disk; `du` tells you what filled it.
</En>
<Ur>
Nayi disk tab tak bekaar hai jab tak aap use **format** (file system dena) aur **mount** (`/data` jaise folder se jorna) na karein. Aur storage ka sab se aam masla saada hai: **disk bhar gayi**. `df -h` batata hai kaun si disk; `du` batata hai kis cheez ne bhari.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- A **disk** (like `/dev/nvme1n1`) can be split into **partitions**.
- Each partition is **formatted** with a **file system** (ext4, XFS).
- Then it's **mounted** at a folder so it shows up in the one Linux tree.
- `/etc/fstab` is the list of disks to mount automatically at **boot**.

</En>
<Ur>

- **Disk** (jaise `/dev/nvme1n1`) ko **partitions** me baanta ja sakta hai.
- Har partition ko **file system** (ext4, XFS) ke saath **format** kiya jata hai.
- Phir use kisi folder par **mount** kiya jata hai taa ke wo Linux ke ek tree me nazar aaye.
- `/etc/fstab` un disks ki list hai jo **boot** par khud ba khud mount hon.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **"No space left on device"** stops databases, logs, uploads and deploys. It's one of the most common production problems.
- Cloud servers come with a **small** main disk; data belongs on separate **volumes** you can grow and back up.
- A **wrong line in `/etc/fstab`** can stop a server from booting.

</En>
<Ur>

- **"No space left on device"** databases, logs, uploads aur deploys rok deta hai. Ye production ke sab se aam masail me se ek hai.
- Cloud servers ke saath **chhoti** main disk aati hai; data alag **volumes** par hona chahiye jinhe barhaya aur backup kiya ja sake.
- `/etc/fstab` me **ek ghalat line** server ko boot hone se rok sakti hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- a "disk full" alert
- you attached a new disk to a cloud server
- you made a disk bigger in the cloud console
- you deleted a big file but the space didn't come back

</En>
<Ur>

- "disk full" ka alert
- aap ne cloud server se nayi disk jori
- aap ne cloud console me disk bari ki
- aap ne bari file delete ki lekin jagah wapas nahi aayi

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

- `lsblk`: list disks
- `df -h`: how full each disk is
- `du -sh *`: what uses the space
- `mkfs.ext4` → `mount` → `/etc/fstab` (with the **UUID**): add a new disk

</En>
<Ur>

- `lsblk`: disks ki list
- `df -h`: har disk kitni bhari
- `du -sh *`: jagah kaun le raha hai
- `mkfs.ext4` → `mount` → `/etc/fstab` (**UUID** ke saath): nayi disk jorna

</Ur>
</Tr>
</How>
</Glance>

## Learn it step by step

<Walkthrough>

<Step title="lsblk: what disks do I have?">

<Tr>
<En>

`lsblk` lists every disk, its partitions, sizes and where they're mounted. It's how you find a **newly attached** disk. Names depend on the hardware: `/dev/sdX` (many VMs), `/dev/nvmeXnY` (AWS), `/dev/vdX` (KVM).

</En>
<Ur>

`lsblk` har disk, us ke partitions, size aur mount ki jagah dikhata hai. Isi se aap **nayi jori gayi** disk dhoondte hain. Naam hardware par munhasir hain: `/dev/sdX` (bohot se VMs), `/dev/nvmeXnY` (AWS), `/dev/vdX` (KVM).

</Ur>
</Tr>

```text
$ lsblk
NAME         MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
nvme0n1      259:0    0   20G  0 disk
├─nvme0n1p1  259:1    0 19.9G  0 part /             ← root file system
└─nvme0n1p15 259:2    0  106M  0 part /boot/efi
nvme1n1      259:3    0  100G  0 disk               ← new volume: no partitions, not mounted
```

<Happened>
<Tr>
<En>

- `nvme0n1` (20 GB) is the main disk; its partition `p1` is mounted at `/`.
- `nvme1n1` (100 GB) has **no** mount point: that's the new disk waiting to be set up.

</En>
<Ur>

- `nvme0n1` (20 GB) main disk hai; is ka partition `p1` `/` par mounted hai.
- `nvme1n1` (100 GB) ka **koi** mount point nahi: yahi nayi disk hai jo tayyar hone ka intezar kar rahi hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="df: how full is each disk?">

<Tr>
<En>

`df -h` ("**d**isk **f**ree") shows size, used, available and **Use%** for every mounted disk. It answers "**which** disk is full?" instantly.

</En>
<Ur>

`df -h` ("**d**isk **f**ree") har mounted disk ka size, istemal shuda, baaqi aur **Use%** dikhata hai. Ye foran jawab deta hai "**kaun si** disk bhari hai?".

</Ur>
</Tr>

```bash
df -h / | awk 'NR==1 {print $1, $2, $3, $4, $5, $6} NR==2 {print "<device>", "<size>", "<used>", "<avail>", "<use%>", $6}'
used=$(df --output=pcent / | tail -1 | tr -dc '0-9')
(( used < 100 )) && echo "root file system is below 100% — OK for now"
```

```text output
Filesystem Size Used Avail Use% Mounted
<device> <size> <used> <avail> <use%> /
root file system is below 100% — OK for now
```

<Tr>
<En>(We hid the numbers so the page matches every machine.) A real output on a server:</En>
<Ur>(Hum ne numbers chhupa diye taa ke page har machine se mel khaye.) Server par asli output:</Ur>
</Tr>

```text
$ df -h
Filesystem       Size  Used Avail Use% Mounted on
/dev/nvme0n1p1    20G   18G  1.6G  92% /          ← almost full!
/dev/nvme1n1     100G   12G   83G  13% /data
tmpfs            1.9G     0  1.9G   0% /dev/shm
```

<Happened>
<Tr>
<En>The main disk `/` is **92%** full with only 1.6 GB left: act now. The `/data` disk is fine at 13%.</En>
<Ur>Main disk `/` **92%** bhari hai aur sirf 1.6 GB bacha hai: abhi kuch karein. `/data` disk 13% par theek hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="du: what's using the space?">

<Tr>
<En>

`df` says a disk is full; `du` ("**d**isk **u**sage") finds **what** filled it. Drill down one level at a time, biggest first:

`sudo du -xh --max-depth=1 / | sort -rh | head`

Then repeat inside the biggest folder. `-x` means "stay on this one disk". The usual suspects: `/var/log`, `/var/lib/docker`, databases, old backups, `node_modules`.

</En>
<Ur>

`df` batata hai disk bhari hai; `du` ("**d**isk **u**sage") dhoondta hai **kis cheez** ne bhari. Ek ek level neeche jayen, bara pehle:

`sudo du -xh --max-depth=1 / | sort -rh | head`

Phir sab se bare folder ke andar yahi dohrayen. `-x` ka matlab "isi ek disk par raho". Aam mujrim: `/var/log`, `/var/lib/docker`, databases, purane backups, `node_modules`.

</Ur>
</Tr>

```bash
mkdir -p disk/{logs,uploads,cache}
head -c 5000000 /dev/zero > disk/logs/app.log
head -c 1500000 /dev/zero > disk/uploads/photo.jpg
head -c 100000  /dev/zero > disk/cache/x.bin
du -h --apparent-size --max-depth=1 disk | sort -rh
```

```text output
6.3M	disk
4.8M	disk/logs
1.5M	disk/uploads
98K	disk/cache
```

<Happened>
<Tr>
<En>The `disk` folder uses 6.3 MB in total, and `logs` is the biggest part (4.8 MB). On a real server you'd now look inside `logs`. A typical real path: `/` → `/var` → `/var/lib` → `/var/lib/docker` (15 GB), then clean with `docker system prune` (carefully).</En>
<Ur>`disk` folder kul 6.3 MB le raha hai, aur `logs` sab se bara hissa hai (4.8 MB). Asli server par ab aap `logs` ke andar dekhte. Aam asli raasta: `/` → `/var` → `/var/lib` → `/var/lib/docker` (15 GB), phir `docker system prune` se safai (ehtiyat se).</Ur>
</Tr>
</Happened>

</Step>

<Step title="Format: give the disk a file system">

<Tr>
<En>

A brand-new disk has no structure for files. `mkfs` writes an empty file system onto it.

**Warning: this erases everything on that device.** Double-check the name with `lsblk -f` first (a new disk shows an **empty** FSTYPE).

Below we practise safely on a **file** that pretends to be a disk:

</En>
<Ur>

Bilkul nayi disk me files ke liye koi dhancha nahi hota. `mkfs` us par khaali file system likhta hai.

**Khabardar: ye us device ki har cheez mita deta hai.** Pehle `lsblk -f` se naam dobara check karein (nayi disk ka FSTYPE **khaali** hota hai).

Neeche hum ek aisi **file** par mehfooz practice karte hain jo disk hone ka dikhawa karti hai:

</Ur>
</Tr>

```bash
truncate -s 64M disk.img              # a 64 MB file pretending to be a disk
mkfs.ext4 -q -F -L practice disk.img  # format it (safe: it is just a file)
blkid -o value -s TYPE disk.img
blkid -o value -s LABEL disk.img
```

```text output
ext4
practice
```

<Happened>
<Tr>
<En>`truncate` made a 64 MB file, `mkfs.ext4` formatted it as **ext4** with the label "practice", and `blkid` confirms both.</En>
<Ur>`truncate` ne 64 MB ki file banayi, `mkfs.ext4` ne use **ext4** ke taur par "practice" label ke saath format kiya, aur `blkid` dono ki tasdeeq karta hai.</Ur>
</Tr>
</Happened>

<Tr>
<En>

| File system | Typical use |
| --- | --- |
| ext4 | Default on Ubuntu/Debian; a safe general choice |
| XFS | Default on Red Hat/Amazon Linux; great for large files and databases |
| Btrfs / ZFS | Snapshots, checksums, advanced features |
| vfat / exFAT | USB sticks, the EFI boot partition |
| tmpfs | Lives in memory, e.g. `/dev/shm`, `/run` |

</En>
<Ur>

| File system | Aam istemal |
| --- | --- |
| ext4 | Ubuntu/Debian ka default; mehfooz aam intekhab |
| XFS | Red Hat/Amazon Linux ka default; bari files aur databases ke liye behtareen |
| Btrfs / ZFS | Snapshots, checksums, advanced khoobiyan |
| vfat / exFAT | USB sticks, EFI boot partition |
| tmpfs | Memory me rehta hai, jaise `/dev/shm`, `/run` |

</Ur>
</Tr>

</Step>

<Step title="Mount: attach it to a folder">

<Tr>
<En>

Linux has **one** tree, so a disk is usable only once it's **mounted** somewhere in it:

`sudo mkdir -p /data && sudo mount /dev/nvme1n1 /data`

To detach: `sudo umount /data` (note: **umount**, no "n"). If it says "target is busy", a program is still using it: find it with `lsof +f -- /data`.

</En>
<Ur>

Linux ka **ek** tree hai, isliye disk tabhi kaam aati hai jab is me kahin **mount** ho:

`sudo mkdir -p /data && sudo mount /dev/nvme1n1 /data`

Alag karne ke liye: `sudo umount /data` (dhyan dein: **umount**, "n" nahi). Agar "target is busy" kahe, to koi program abhi bhi istemal kar raha hai: `lsof +f -- /data` se dhoondein.

</Ur>
</Tr>

```text
$ sudo mkdir -p /data
$ sudo mount /dev/nvme1n1 /data
$ findmnt /data
TARGET SOURCE       FSTYPE OPTIONS
/data  /dev/nvme1n1 ext4   rw,relatime
$ df -h /data
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme1n1     98G   24K   93G   1% /data
```

</Step>

<Step title="/etc/fstab: mount it at every boot">

<Tr>
<En>

A manual `mount` **disappears at reboot**. Then your app would silently write to the small main disk instead of `/data`. To make it permanent, add a line to `/etc/fstab`:

- Use the **UUID** (from `blkid`), not `/dev/nvme1n1`: device names can change between reboots.
- Add **`nofail`** for cloud volumes, so a missing disk doesn't stop the server from booting.
- **Test with `sudo mount -a`** before you reboot.

</En>
<Ur>

Haath se kiya `mount` **reboot par ghayab** ho jata hai. Phir aap ki app chupke se `/data` ke bajaye chhoti main disk par likhti. Mustaqil banane ke liye `/etc/fstab` me line shamil karein:

- **UUID** (`blkid` se) istemal karein, `/dev/nvme1n1` nahi: device ke naam reboots ke darmiyan badal sakte hain.
- Cloud volumes ke liye **`nofail`** lagayen, taa ke gumshuda disk server ko boot hone se na roke.
- Reboot se pehle **`sudo mount -a` se test** karein.

</Ur>
</Tr>

```text
# /etc/fstab
# <what>                                    <where>  <type> <options>         <dump> <check>
UUID=3f2a9c1e-7b4d-4f0a-9e3a-1c2d3e4f5a6b    /data    ext4   defaults,nofail   0      2

$ sudo blkid /dev/nvme1n1
/dev/nvme1n1: UUID="3f2a9c1e-7b4d-4f0a-9e3a-1c2d3e4f5a6b" TYPE="ext4"
$ sudo umount /data && sudo mount -a && findmnt /data     ← proves the fstab line works
```

<Callout type="danger" title="A broken fstab can stop the server from booting">
<Tr>
<En>One typo in `/etc/fstab` can drop the server into emergency mode, and on a cloud VM you may have no screen to fix it. Always run `sudo mount -a` (and `findmnt --verify`) after editing, **before** rebooting.</En>
<Ur>`/etc/fstab` me ek typo server ko emergency mode me daal sakta hai, aur cloud VM par theek karne ke liye shayad screen bhi na ho. Edit ke baad, reboot se **pehle**, hamesha `sudo mount -a` (aur `findmnt --verify`) chalayen.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Mount options">

<Tr>
<En>

The 4th column of an fstab line holds **options** that change how the disk behaves. Some are important for security, like `noexec` on `/tmp` so downloaded programs can't run from there.

</En>
<Ur>

fstab line ka chautha column **options** rakhta hai jo disk ka andaz badalte hain. Kuch security ke liye ahem hain, jaise `/tmp` par `noexec` taa ke download kiye programs wahan se na chal sakein.

</Ur>
</Tr>

| Option | Effect |
| --- | --- |
| `defaults` | Normal settings |
| `ro` | Read-only |
| `noexec` | Programs can't be run from here |
| `nosuid` | setuid bits are ignored |
| `nodev` | Device files are ignored |
| `nofail` | Don't fail boot if the device is missing |
| `noatime` | Don't update "last read" times (less disk writing) |

</Step>

<Step title="Inodes: full without being full">

<Tr>
<En>

Every file uses one **inode** (its record card), and an ext4 disk has a **fixed** number of them. Millions of tiny files (sessions, cache, mail) can use up **all the inodes** while bytes are still free. Then you get "No space left on device" even though `df -h` shows space. Check with `df -i`.

</En>
<Ur>

Har file ek **inode** (us ka record card) istemal karti hai, aur ext4 disk me in ki **tay** ginti hoti hai. Laakhon chhoti files (sessions, cache, mail) **saare inodes** khatam kar sakti hain jab ke bytes abhi baaqi hon. Phir "No space left on device" aata hai halanke `df -h` jagah dikhata hai. `df -i` se check karein.

</Ur>
</Tr>

```bash
df -i / | awk 'NR==1 {print $1, $2, $3, $4, $5} NR==2 {print "<device>", "<inodes>", "<used>", "<free>", ($5 ~ /%$/ ? "<use%>" : $5)}'
```

```text output
Filesystem Inodes IUsed IFree IUse%
<device> <inodes> <used> <free> <use%>
```

</Step>

<Step title="Deleted, but the disk is still full">

<Tr>
<En>

A classic trap: you delete a 20 GB log, but the disk is **still** full. Why? A running program still has the file **open**, so the space isn't freed until that program closes it.

- Find such files: `sudo lsof +L1`
- Fix: restart that program, or **empty** the file instead of deleting it: `truncate -s 0 file`
- Prevent it: use **logrotate**

</En>
<Ur>

Mashhoor jaal: aap 20 GB ka log delete karte hain, lekin disk **abhi bhi** bhari hai. Kyun? Koi chalta program abhi bhi file **khole** hue hai, isliye jagah tab tak wapas nahi aati jab tak wo program use band na kare.

- Aisi files dhoondo: `sudo lsof +L1`
- Hal: wo program restart karo, ya file delete karne ke bajaye **khaali** karo: `truncate -s 0 file`
- Bachao: **logrotate** istemal karo

</Ur>
</Tr>

```bash
head -c 3000000 /dev/zero > big.log
sleep 300 < big.log & holder=$!          # a process keeps the file open
rm big.log
lsof -nP -a +L1 -p "$holder" 2>/dev/null | awk 'NR>1 {print "still open after delete:", $NF, $(NF-1)}' | sed 's|/.*/big.log|.../big.log|'
kill "$holder"
```

```text output
still open after delete: (deleted) .../big.log
```

<Happened>
<Tr>
<En>We deleted `big.log`, but a running process still held it open. `lsof +L1` shows it as `(deleted)`: the name is gone, but the data (and the space) is still there until the process stops.</En>
<Ur>Hum ne `big.log` delete ki, lekin ek chalta process abhi bhi use khole hue tha. `lsof +L1` ise `(deleted)` dikhata hai: naam chala gaya, lekin data (aur jagah) process rukne tak mojood hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Swap: emergency memory on disk">

<Tr>
<En>

**Swap** is disk space used as overflow memory when RAM is full. It stops small servers (1–2 GB RAM) from killing apps immediately, but it's **thousands of times slower** than RAM. Adding a 2 GB swap file is a common first step on tiny servers:

</En>
<Ur>

**Swap** disk ki jagah hai jo RAM bharne par izafi memory ke taur par istemal hoti hai. Ye chhote servers (1–2 GB RAM) ko foran apps maarne se rokti hai, lekin ye RAM se **hazaron guna sust** hai. Chhote servers par 2 GB ki swap file banana aam pehla qadam hai:

</Ur>
</Tr>

```text
$ sudo fallocate -l 2G /swapfile
$ sudo chmod 600 /swapfile
$ sudo mkswap /swapfile && sudo swapon /swapfile
$ echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
$ swapon --show
NAME      TYPE SIZE USED PRIO
/swapfile file   2G   0B   -2
```

</Step>

<Step title="Making a cloud disk bigger">

<Tr>
<En>

Cloud disks can grow **without downtime**, but Linux must be told to use the new space:

1. Take a **snapshot** first (a safety copy).
2. Resize the volume in the cloud console.
3. Grow the partition: `sudo growpart /dev/nvme0n1 1`
4. Grow the file system: `sudo resize2fs /dev/nvme0n1p1` (ext4) or `sudo xfs_growfs /` (XFS)
5. Check with `df -h`.

</En>
<Ur>

Cloud disks **baghair downtime** ke barh sakti hain, lekin Linux ko batana parta hai ke nayi jagah istemal kare:

1. Pehle **snapshot** lein (hifazati copy).
2. Cloud console me volume ka size barhayen.
3. Partition barhayen: `sudo growpart /dev/nvme0n1 1`
4. File system barhayen: `sudo resize2fs /dev/nvme0n1p1` (ext4) ya `sudo xfs_growfs /` (XFS)
5. `df -h` se check karein.

</Ur>
</Tr>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="mkfs on the wrong disk">

```text
sudo mkfs.ext4 /dev/nvme0n1     # that's the main disk: everything is gone
```

</Bad>
<Good title="Check first">

```text
lsblk -f          # the new disk has an empty FSTYPE and no mount point
sudo mkfs.ext4 /dev/nvme1n1
```

</Good>
</Compare>

<Compare>
<Bad title="Device names in fstab">

```text
/dev/nvme1n1  /data  ext4  defaults  0 2
```

<Tr>
<En>After a reboot the name can change, and the wrong disk (or none) gets mounted.</En>
<Ur>Reboot ke baad naam badal sakta hai, aur ghalat disk (ya koi bhi nahi) mount hoti hai.</Ur>
</Tr>

</Bad>
<Good title="UUID + nofail, then test">

```text
UUID=3f2a9c1e-...  /data  ext4  defaults,nofail  0 2
sudo mount -a
```

</Good>
</Compare>

<DeepDive title="LVM in one paragraph">

**Logical Volume Manager** adds a flexible layer between disks and file systems: several disks become one pool (a volume group) that's split into resizable logical volumes. You can grow a volume by adding a disk, take snapshots, and move data between disks online. It's common on on-premise servers and some cloud images (RHEL defaults to it). Devices look like `/dev/mapper/vg0-data`. Main commands: `pvs`, `vgs`, `lvs` (show), and `lvextend -r -L +10G /dev/vg0/data` (grow the volume and its file system together).

</DeepDive>

<DeepDive title="Real world: a PostgreSQL server built for safety">

1. **Root volume** (30 GB, gp3) holds only the OS and packages.
2. **Data volume** (200 GB, gp3, **encrypted with KMS**) mounted at `/var/lib/postgresql` via its UUID with `defaults,nofail,noatime`.
3. **Daily EBS snapshots** via AWS Backup with 30-day retention, plus `pg_dump` to S3 (another account, versioned, Object Lock) for recovery and ransomware resilience.
4. **CloudWatch alarm** when disk usage passes 80%; growing the volume online takes two commands and no downtime.
5. **Restore drill** every quarter: create a volume from a snapshot, attach it to a test instance, start PostgreSQL, check the data.

When a developer runs a wrong migration that drops a table, the team restores the snapshot to a new volume, extracts the table and loads it back, because backups existed **and had been tested**.

Other mistakes to avoid: storing data on instance store or a container's writable layer (lost on stop), and treating snapshots or RAID as the whole backup plan.

</DeepDive>

<DeepDive title="Security lens">

Data at rest is a target: stolen snapshots, readable old disks, ransomware that encrypts everything reachable.

- **Encrypt at rest:** turn on EBS encryption by default in every AWS region you use; use LUKS (`cryptsetup`) for disks you manage yourself.
- **Snapshot exposure:** public or wrongly shared EBS snapshots and AMIs have leaked databases and credentials. Audit sharing settings.
- **Ransomware-resistant backups:** copies in a separate account, with versioning and Object Lock, so an attacker with production credentials can't delete them.
- **Mount hardening:** `/tmp`, `/var/tmp` and `/dev/shm` with `noexec,nosuid,nodev` blocks many "download a tool to /tmp and run it" attacks (not all: scripts can still run through an interpreter).
- **Data remanence:** deleting files may leave readable data on disk. Encryption makes old data useless without the key.
- **Disk exhaustion is a denial of service:** uploads, logs and temp files without limits let an attacker fill the disk. Enforce upload size limits, quotas and log rotation.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you add a new disk to a Linux server and make it available at /data permanently?">
Identify it with lsblk -f, create a file system with mkfs.ext4 or mkfs.xfs (after confirming it is empty), create /data and mount it, then add an /etc/fstab entry using the UUID from blkid with options like defaults,nofail. Test with umount and mount -a before rebooting.
</QA>

<QA q="df shows free space but writes fail with 'No space left on device'. Why?">
The file system has probably run out of inodes, typically because of a huge number of small files; check with df -i and find the directories with the most files. Other causes are a full quota, reserved blocks for root on ext4, or writing to a different file system than the one you checked.
</QA>

<QA q="How do you grow an EBS volume without downtime?">
Increase the volume size in AWS (console or CLI), then on the instance grow the partition with growpart (for example `growpart /dev/nvme0n1 1`) and grow the file system: resize2fs for ext4, or xfs_growfs on the mount point for XFS. Verify with df -h. No reboot is needed on modern instances.
</QA>

<QA q="What is the difference between EBS, instance store, EFS and S3?">
EBS is persistent block storage attached to one instance, like a network disk. Instance store is physically attached, very fast storage that is lost when the instance stops. EFS is a managed NFS file system that many instances can mount at once. S3 is object storage accessed over HTTP, not mounted as a normal disk, highly durable and suited for backups, static files and data lakes.
</QA>

<QA q="Why is RAID or replication not a substitute for backups?">
RAID and replication protect against hardware failure by keeping copies in sync, but they also instantly replicate mistakes, corruption, deletions and ransomware encryption. Backups are separate, point-in-time copies with retention, ideally isolated in another account or location and immutable, and they must be tested by restoring.
</QA>

</DeepDive>
