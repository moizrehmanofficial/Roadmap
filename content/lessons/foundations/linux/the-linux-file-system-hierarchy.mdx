<Callout type="tip" title="In one minute">
Linux has **one tree** starting at `/`. Disks, USB drives and network shares are **mounted** into it as folders. The layout follows the **Filesystem Hierarchy Standard (FHS)**: configs in `/etc`, logs and changing data in `/var`, programs in `/usr/bin`, users' files in `/home`, root's in `/root`, temporary files in `/tmp`, and live kernel/process information in `/proc` and `/sys`. Learn ten directories and you can navigate any Linux server.
</Callout>

## What is it?

Windows gives each drive its own letter (`C:\`, `D:\`). Linux has a single tree. Everything — every disk, every device, even running processes — appears somewhere under `/` (called "root", not to be confused with the root *user*).

The **Filesystem Hierarchy Standard** defines what each top-level directory is for. Distributions follow it closely, so the same knowledge works on Ubuntu, Amazon Linux, Alpine and inside containers.

| Directory | Contains | Examples you will use |
| --- | --- | --- |
| `/` | The top of the tree | — |
| `/etc` | System-wide **configuration** (text files) | `/etc/nginx/`, `/etc/ssh/sshd_config`, `/etc/hosts`, `/etc/passwd` |
| `/var` | **Variable** data that changes while the system runs | `/var/log/`, `/var/lib/postgresql/`, `/var/lib/docker/`, `/var/www/` |
| `/var/log` | Log files | `syslog`, `auth.log`, `nginx/access.log` |
| `/usr` | Installed software (read-mostly) | `/usr/bin/node`, `/usr/lib/`, `/usr/share/doc/` |
| `/usr/local` | Software you installed **manually**, outside the package manager | `/usr/local/bin/terraform` |
| `/bin`, `/sbin` | Essential commands (on modern distros, links to `/usr/bin`, `/usr/sbin`) | `ls`, `cp`, `ip` |
| `/home` | Regular users' home directories | `/home/moiz/` |
| `/root` | The root user's home directory | `/root/.ssh/` |
| `/tmp` | Temporary files, often cleared on reboot; writable by everyone | build scratch files |
| `/opt` | Self-contained third-party applications | `/opt/google/chrome/` |
| `/srv` | Data served by this system (a common place for app code) | `/srv/app/` |
| `/boot` | Kernel and bootloader files | `vmlinuz-6.8.0-45-generic` |
| `/dev` | **Device** files | `/dev/sda`, `/dev/nvme0n1`, `/dev/null`, `/dev/random` |
| `/proc` | Virtual: **processes** and kernel information, generated live | `/proc/cpuinfo`, `/proc/1234/` |
| `/sys` | Virtual: devices and kernel settings | `/sys/class/net/` |
| `/run` | Runtime data since last boot (PID files, sockets) | `/run/docker.sock` |
| `/mnt`, `/media` | Mount points for temporary/removable file systems | `/mnt/data` |
| `/lib`, `/lib64` | Shared libraries needed by essential programs | `libc.so.6` |

### Per-user locations

| Path | Meaning |
| --- | --- |
| `~` or `$HOME` | Your home directory |
| `~/.bashrc`, `~/.profile` | Your shell configuration |
| `~/.ssh/` | Your SSH keys and `authorized_keys` |
| `~/.config/` | Per-user application settings |
| `~/.aws/`, `~/.kube/` | Cloud and Kubernetes credentials |
| Files starting with `.` | "Hidden" (just not shown by plain `ls`) |

## Why does it matter?

- **Full-stack:** you deploy your app to `/srv/app` or `/var/www`, configure Nginx in `/etc/nginx`, and debug with `/var/log/nginx/error.log`.
- **DevOps:** Dockerfiles copy into `/app` or `/usr/src/app`; volumes mount databases at `/var/lib/postgresql/data`; Kubernetes mounts secrets under paths you choose; `/var/lib/docker` fills disks.
- **Cloud:** EBS volumes are mounted under `/mnt` or `/data`; cloud-init writes its logs to `/var/log/cloud-init-output.log`.
- **Security:** attackers and auditors both go straight to `/etc/passwd`, `/etc/shadow`, `/etc/sudoers`, `~/.ssh/`, `/var/log/auth.log`, `/tmp` and `/proc`. Knowing what *should* be there is how you notice what should *not*.

## When and where do you use it?

- "Where is the Nginx config?" → `/etc/nginx/sites-available/`.
- "Why did the service fail?" → `/var/log/` or `journalctl`.
- "Disk is full!" → usually `/var/log`, `/var/lib/docker` or `/tmp`.
- "Where did `npm i -g` install that tool?" → `/usr/local/lib/node_modules` and `/usr/local/bin`.
- "How many CPUs does this container see?" → `/proc/cpuinfo`, `/sys/fs/cgroup/`.
- Incident response: "who logged in?" → `/var/log/auth.log`; "what keys can log in as this user?" → `~/.ssh/authorized_keys`.

## How does it work?

### Mounting

A file system on a disk partition is attached ("mounted") to a directory in the tree. Before mounting, `/data` is an empty folder; after mounting, it shows the disk's contents.

```text
/ ──────────────── root file system on /dev/nvme0n1p1
├── etc
├── var
├── home
└── data  ◄──────── second EBS volume /dev/nvme1n1 mounted here
```

Permanent mounts are listed in `/etc/fstab`. In the lesson "Disk, Mounts and Storage" you will mount and format a volume yourself.

### Virtual file systems: `/proc`, `/sys`, `/dev`

These directories are not on any disk. The kernel generates their content when you read them:

- `/proc/<pid>/` has one folder per running process: its command line, environment, open files, memory maps.
- `/proc/cpuinfo`, `/proc/meminfo`, `/proc/loadavg` show hardware and load.
- `/dev/null` discards anything written to it; `/dev/urandom` returns random bytes; `/dev/sda` is a whole disk.

This is "everything is a file" in practice: tools like `top`, `ps` and `free` mostly just read `/proc`.

### Why `/usr/local` exists

The package manager owns `/usr/bin` and `/usr/lib`. If you put files there by hand, the next package upgrade may overwrite them. Software you install manually goes into `/usr/local/` (or `/opt/`), which package managers never touch.

### Inside a container

A container image has its own small tree. It usually contains `/etc`, `/usr`, `/lib` and your app (e.g. `/app`) — but no `/boot`, no running systemd, and often no shell at all in distroless images. `/proc` and `/sys` are provided by the host kernel, restricted to the container's view.

## Hands-on

```bash
# The top of the tree
ls /

# Where are you, and where is home?
pwd
echo $HOME
ls -la ~                         # -a shows hidden "dot" files

# Configuration lives in /etc
ls /etc | head -n 20
cat /etc/hostname
cat /etc/hosts
head -n 5 /etc/passwd            # user accounts (no passwords here)
sudo head -n 3 /etc/shadow       # password hashes — root only

# Logs live in /var/log
ls /var/log
sudo tail -n 20 /var/log/auth.log 2>/dev/null || sudo tail -n 20 /var/log/secure

# Which disk is mounted where, and how full?
df -h
findmnt --real

# Virtual files generated by the kernel
cat /proc/loadavg
grep -c processor /proc/cpuinfo
grep MemAvailable /proc/meminfo
ls /proc/$$/                     # your shell's own process folder

# Where does a command live?
which node python3 ls
type cd                          # "cd is a shell builtin" — not a file at all

# The biggest directories under /var (find what fills a disk)
sudo du -xh /var --max-depth=1 2>/dev/null | sort -h | tail
```

## Real-world example

A typical VPS running a Node.js app behind Nginx:

```text
/etc/nginx/sites-available/app.conf    Nginx site config
/etc/systemd/system/app.service        systemd unit that runs the app
/etc/letsencrypt/live/example.com/     TLS certificates (private key here!)
/srv/app/                              application code (owned by user "app")
/srv/app/.env                          secrets (mode 600, owner app)
/var/log/nginx/access.log              every HTTP request
/var/log/nginx/error.log               proxy errors
/var/lib/postgresql/16/main/           database files
/home/deploy/.ssh/authorized_keys      who may SSH in as "deploy"
/var/backups/ or an S3 bucket          backups
```

When the site goes down at 2 a.m., you do not search randomly: `systemctl status app`, then `/var/log/nginx/error.log`, then `df -h` for a full `/var`. That speed comes from knowing the map.

## Common mistakes

- **Editing files in `/usr/bin` or `/usr/lib` by hand** — the next package upgrade overwrites them. Use `/usr/local` or `/etc`.
- **Putting app code or uploads in `/tmp`** — it is cleared on reboot and writable by every user.
- **Letting `/var` fill up**: unrotated logs and old Docker images (`docker system prune`) are the usual causes, and a full disk can crash databases.
- **Confusing `/` (root directory) with `/root` (root user's home).**
- **Committing or copying `~/.ssh`, `~/.aws` or `.env` files** into repositories or Docker images.

## Security lens

<Callout type="security">
Attackers follow the same map you do. These are the paths they read first — and the ones you should protect and monitor.
</Callout>

| Path | Why attackers want it | Protection |
| --- | --- | --- |
| `/etc/shadow` | Password hashes to crack offline | Root-only (mode 640/600); strong passwords; prefer SSH keys |
| `/etc/sudoers`, `/etc/sudoers.d/` | Who can become root | Minimal entries; edit with `visudo`; monitor changes |
| `~/.ssh/authorized_keys` | Adding a key = permanent backdoor | File integrity monitoring; review regularly |
| `~/.ssh/id_*`, `~/.aws/credentials`, `~/.kube/config` | Credentials to pivot to other systems and clouds | Mode 600; short-lived credentials; never on shared servers |
| `/etc/cron*`, `/etc/systemd/system/` | Persistence: run code at boot or on a schedule | Monitor for new files |
| `/tmp`, `/dev/shm` | World-writable: attackers drop and run tools here | Mount with `noexec` where possible |
| `/var/log/` | Evidence — attackers try to delete it | Ship logs off-host in real time |
| `/proc/<pid>/environ` | Environment variables, often containing secrets | Do not keep long-lived secrets in env where avoidable; restrict access |
| `/run/docker.sock` | Access to it is equivalent to root on the host | Never mount it into untrusted containers |

`/etc/passwd` being world-readable is normal: it lists accounts but holds no password hashes since those moved to `/etc/shadow`.

## Interview questions

<QA q="Where would you look for a service's configuration and logs on Linux?">
Configuration is normally under /etc (for example /etc/nginx/ or /etc/ssh/sshd_config), and systemd units under /etc/systemd/system. Logs are in /var/log (for example /var/log/nginx/error.log) or in the systemd journal via journalctl -u service-name.
</QA>

<QA q="What is /proc?">
A virtual file system the kernel generates on the fly. It exposes information about every running process (/proc/PID/ with its command line, environment, open files and memory) and about the system (cpuinfo, meminfo, loadavg). Tools such as ps, top and free read it. Nothing in it is stored on disk.
</QA>

<QA q="What is the difference between /etc/passwd and /etc/shadow?">
/etc/passwd lists user accounts (username, UID, GID, home directory, shell) and is readable by everyone. /etc/shadow stores the password hashes and ageing information and is readable only by root, so hashes cannot be copied and cracked by ordinary users.
</QA>

<QA q="Why should manually installed software go in /usr/local or /opt?">
The package manager owns /usr/bin, /usr/lib and similar directories; files placed there by hand can be overwritten or conflict during package upgrades and are invisible to package queries. /usr/local and /opt are reserved for locally installed software, so the two never clash.
</QA>

<QA q="A server's disk is full. Where do you look first?">
Run df -h to see which file system is full, then du -xh --max-depth=1 on it, starting with /var: /var/log (unrotated logs), /var/lib/docker (images, containers, volumes), database directories under /var/lib, and /tmp. Also check for deleted-but-open files with lsof +L1.
</QA>

## Key terms

<Terms>
  <Term name="/ (root directory)">The top of the single Linux file tree.</Term>
  <Term name="FHS">Filesystem Hierarchy Standard; defines the purpose of each directory.</Term>
  <Term name="/etc">System configuration files.</Term>
  <Term name="/var">Variable data: logs, databases, caches, spools.</Term>
  <Term name="/usr/local">Location for software installed outside the package manager.</Term>
  <Term name="/proc, /sys">Virtual file systems exposing processes and kernel information.</Term>
  <Term name="Mount point">A directory where a file system is attached to the tree.</Term>
  <Term name="Home directory">A user's personal directory, such as /home/moiz; shortcut ~.</Term>
  <Term name="Dotfile">A file whose name starts with a dot; hidden by default.</Term>
</Terms>
