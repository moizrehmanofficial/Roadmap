<BigIdea>
<Tr>
<En>
Linux has **one big folder tree** that starts at `/`, and **every main folder has one job**: settings go in `/etc`, logs in `/var/log`, programs in `/usr/bin`, your files in `/home`. Learn this map once, and you can find your way around **any** Linux server.
</En>
<Ur>
Linux ka **ek bara folder tree** hai jo `/` se shuru hota hai, aur **har bare folder ka ek kaam** hai: settings `/etc` me, logs `/var/log` me, programs `/usr/bin` me, aap ki files `/home` me. Ye naqsha ek dafa seekh lein, to aap **kisi bhi** Linux server par raasta dhoond sakte hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

The most important folders:

- `/etc`: **settings** (configuration files)
- `/var`: data that **changes**, like **logs** (`/var/log`) and websites (`/var/www`)
- `/home`: each user's **personal folder** (`/home/alex`)
- `/root`: the admin user's home
- `/usr/bin`: **programs**
- `/tmp`: **temporary** files, often cleared on restart
- `/proc`, `/sys`: **live information** from the kernel
- `/dev`: **devices** (disks, `/dev/null`)

</En>
<Ur>

Sab se ahem folders:

- `/etc`: **settings** (configuration files)
- `/var`: wo data jo **badalta** rehta hai, jaise **logs** (`/var/log`) aur websites (`/var/www`)
- `/home`: har user ka **zaati folder** (`/home/alex`)
- `/root`: admin user ka home
- `/usr/bin`: **programs**
- `/tmp`: **aarzi** files, aksar restart par saaf
- `/proc`, `/sys`: kernel se **live maloomat**
- `/dev`: **devices** (disks, `/dev/null`)

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Fix problems fast**: "where are nginx's logs?" → `/var/log/nginx`. You know before searching.
- **Backups**: you know what to save (`/etc`, `/home`, `/var/www`) and what to skip (`/proc`, `/tmp`).
- **"Disk full"** is almost always `/var/log` or `/var/lib/docker`.
- **Security**: attackers know this map too, so you must know what to protect.

</En>
<Ur>

- **Masle jaldi hal**: "nginx ke logs kahan hain?" → `/var/log/nginx`. Dhoondne se pehle hi pata hota hai.
- **Backups**: pata hota hai kya bachana hai (`/etc`, `/home`, `/var/www`) aur kya chhorna (`/proc`, `/tmp`).
- **"Disk full"** taqreeban hamesha `/var/log` ya `/var/lib/docker` hota hai.
- **Security**: hackers bhi ye naqsha jaante hain, isliye aap ko pata hona chahiye kya bachana hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- every time you log in to a server
- looking for a program's settings or logs
- deploying an app (where should the code live?)
- cleaning up a full disk

</En>
<Ur>

- har dafa server me login karte waqt
- kisi program ki settings ya logs dhoondte waqt
- app deploy karte waqt (code kahan rakhein?)
- bhari hui disk saaf karte waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

`ls /` shows the top of the tree. Then use the rule of thumb:

- **settings** → `/etc/<program>`
- **logs** → `/var/log/<program>`
- **data** → `/var/lib/<program>`

</En>
<Ur>

`ls /` tree ka upar wala hissa dikhata hai. Phir ye aam qaida:

- **settings** → `/etc/<program>`
- **logs** → `/var/log/<program>`
- **data** → `/var/lib/<program>`

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

On Windows you have `C:\`, `D:\`: each drive is a separate tree. Linux has **one** tree. Extra disks and USB sticks are attached (**mounted**) as folders inside it.

Think of a **well-organised office building** where every room has a fixed purpose:

- the **records room** for rules and settings (`/etc`)
- the **logbook room** where every day's activity is written down (`/var/log`)
- a **personal office** for each employee (`/home/sam`, `/home/emma`)
- the **manager's office** (`/root`)
- the **tool store** (`/usr/bin`)
- a **scratch room** cleaned every night (`/tmp`)
- a **control room** with live screens about the building (`/proc`, `/sys`)

Move to another branch of the company, and you find the same rooms in the same places.

</En>
<Ur>

Windows par `C:\`, `D:\` hote hain: har drive ka alag tree. Linux ka **ek** tree hai. Izafi disks aur USB sticks is ke andar folders ki shakal me jore (**mount**) jate hain.

Ek **munazzam office building** ka socho jahan har kamre ka ek tay kaam hai:

- qaidon aur settings ka **record room** (`/etc`)
- **logbook room** jahan har din ki sargarmi likhi jati hai (`/var/log`)
- har mulazim ka **zaati office** (`/home/sam`, `/home/emma`)
- **manager ka office** (`/root`)
- **auzaar ka store** (`/usr/bin`)
- **kachcha kaam ka kamra** jo har raat saaf hota hai (`/tmp`)
- **control room** jahan building ki live screens hain (`/proc`, `/sys`)

Company ki kisi doosri branch me jayen, to wahi kamre wahi jagah milte hain.

</Ur>
</Tr>

## The whole map

```text
/
├── bin  → usr/bin      essential programs (ls, cp, bash)
├── boot                kernel and boot loader files
├── dev                 device files (disks, /dev/null, terminals)
├── etc                 system configuration (text files)
├── home                users' personal folders (/home/alex)
├── lib  → usr/lib      shared libraries
├── media, mnt          mount points for removable / extra disks
├── opt                 optional third-party software
├── proc                live process and kernel info (virtual)
├── root                home folder of the root user
├── run                 runtime data since boot (PID files, sockets)
├── sbin → usr/sbin     system administration programs
├── srv                 data served by this machine (sometimes)
├── sys                 live hardware and driver info (virtual)
├── tmp                 temporary files (often cleared on reboot)
├── usr                 installed software: bin, lib, share, local
└── var                 variable data: log, lib, cache, www, spool
```

<Tr>
<En>The arrows (`→`) mean "is a shortcut to". On modern systems `/bin`, `/sbin` and `/lib` just point into `/usr`. This standard map is called the **FHS** (Filesystem Hierarchy Standard).</En>
<Ur>Teer (`→`) ka matlab hai "shortcut hai". Jadeed systems par `/bin`, `/sbin` aur `/lib` sirf `/usr` ki taraf ishara karte hain. Is standard naqshe ko **FHS** (Filesystem Hierarchy Standard) kehte hain.</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="/ : the root of everything">

<Tr>
<En>

Every file on the system lives somewhere below `/`, even on other disks. So every **full path** starts with `/`. `ls /` lists the top level; `cd /` takes you there.

</En>
<Ur>

System ki har file `/` ke neeche kahin hai, chahe doosri disk par ho. Isliye har **poora path** `/` se shuru hota hai. `ls /` upar wala hissa dikhata hai; `cd /` aap ko wahan le jata hai.

</Ur>
</Tr>

```bash
for d in etc var home usr tmp proc dev; do [[ -d /$d ]] && printf '/%s ' "$d"; done; echo
readlink /bin 2>/dev/null | sed 's/^/\/bin is a link to: /'
```

```text output
/etc /var /home /usr /tmp /proc /dev 
/bin is a link to: usr/bin
```

<Happened>
<Tr>
<En>

- The loop checks that the main folders exist: they do on every Linux system.
- `readlink /bin` shows that `/bin` is just a **shortcut** to `usr/bin`.

</En>
<Ur>

- Loop check karta hai ke bare folders mojood hain: har Linux system par hote hain.
- `readlink /bin` dikhata hai ke `/bin` sirf `usr/bin` ka **shortcut** hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="/etc : settings">

<Tr>
<En>

`/etc` holds the **settings** for the whole system, and they're almost all **plain text** files you can read. Users, network, SSH, web server: their settings are all here.

Golden rule: **make a backup before you edit** (`sudo cp file file.bak`).

</En>
<Ur>

`/etc` me poore system ki **settings** hain, aur ye taqreeban sab **saada text** files hain jo aap parh sakte hain. Users, network, SSH, web server: sab ki settings yahin hain.

Sunehra qaida: **edit karne se pehle backup banayen** (`sudo cp file file.bak`).

</Ur>
</Tr>

```bash
head -1 /etc/passwd
grep -c '' /etc/passwd > /dev/null && echo "/etc/passwd lists one user account per line"
grep -E '^127\.0\.0\.1' /etc/hosts | head -1 | awk '{print "/etc/hosts maps", $2, "to", $1}'
```

```text output
root:x:0:0:root:/root:/bin/bash
/etc/passwd lists one user account per line
/etc/hosts maps localhost to 127.0.0.1
```

<Happened>
<Tr>
<En>

- The first line of `/etc/passwd` describes the **root** user. The parts are split by `:`: name `root`, user number `0`, home folder `/root`, shell `/bin/bash`. The `x` means "the password is stored elsewhere" (in `/etc/shadow`).
- `/etc/hosts` is a tiny local phone book: it says `localhost` means `127.0.0.1`.

</En>
<Ur>

- `/etc/passwd` ki pehli line **root** user ke baare me hai. Hisse `:` se alag hain: naam `root`, user number `0`, home folder `/root`, shell `/bin/bash`. `x` ka matlab "password kahin aur rakha hai" (`/etc/shadow` me).
- `/etc/hosts` ek chhoti si local phone book hai: kehti hai ke `localhost` ka matlab `127.0.0.1` hai.

</Ur>
</Tr>
</Happened>

<Tr>
<En>

| File | What it's for |
| --- | --- |
| `/etc/passwd`, `/etc/group` | Users and groups (no passwords) |
| `/etc/shadow` | Password hashes, readable only by root |
| `/etc/hosts` | Local name → IP address list |
| `/etc/resolv.conf` | Which DNS servers to use |
| `/etc/fstab` | Disks to attach at startup |
| `/etc/ssh/sshd_config` | SSH server settings |
| `/etc/sudoers` | Who may use sudo |
| `/etc/os-release` | Distro name and version |

</En>
<Ur>

| File | Kis liye |
| --- | --- |
| `/etc/passwd`, `/etc/group` | Users aur groups (passwords nahi) |
| `/etc/shadow` | Password hashes, sirf root parh sakta hai |
| `/etc/hosts` | Local naam → IP address list |
| `/etc/resolv.conf` | Kaun se DNS servers istemal hon |
| `/etc/fstab` | Startup par kaun si disks jori jayen |
| `/etc/ssh/sshd_config` | SSH server ki settings |
| `/etc/sudoers` | Kaun sudo istemal kar sakta hai |
| `/etc/os-release` | Distro ka naam aur version |

</Ur>
</Tr>

</Step>

<Step title="/var : data that changes (and fills disks)">

<Tr>
<En>

"var" means **variable**: data that grows and changes while the system runs.

- `/var/log`: **logs** (the system's diary)
- `/var/lib`: programs' saved data (databases, Docker)
- `/var/www`: websites
- `/var/cache`: downloaded stuff that can be re-downloaded

This is where disks **fill up**.

</En>
<Ur>

"var" ka matlab **variable**: wo data jo system chalte waqt barhta aur badalta hai.

- `/var/log`: **logs** (system ki diary)
- `/var/lib`: programs ka mehfooz data (databases, Docker)
- `/var/www`: websites
- `/var/cache`: download ki hui cheezen jo dobara download ho sakti hain

Disks yahin **bharti** hain.

</Ur>
</Tr>

```bash
for d in log lib cache; do [[ -d /var/$d ]] && echo "/var/$d exists"; done
```

```text output
/var/log exists
/var/lib exists
/var/cache exists
```

<Tr>
<En>A typical "disk full" investigation. `du` shows how much space each folder uses, biggest first:</En>
<Ur>"Disk full" ki ek aam tafteesh. `du` dikhata hai ke har folder kitni jagah le raha hai, sab se bara pehle:</Ur>
</Tr>

```text
$ sudo du -xh --max-depth=1 /var | sort -rh | head -4
21G   /var
18G   /var/lib          ← drill down: /var/lib/docker? /var/lib/mysql?
2.6G  /var/log          ← old logs not rotated?
310M  /var/cache
```

</Step>

<Step title="/home and /root : personal folders">

<Tr>
<En>

Each normal user gets `/home/<name>`. The admin (**root**) user's home is `/root`.

- `~` is a shortcut for **your** home folder.
- Files whose names **start with a dot** (like `.bashrc`) are **hidden**. `ls -a` shows them.
- Your SSH keys (`~/.ssh`) and personal settings live here.

</En>
<Ur>

Har aam user ko `/home/<naam>` milta hai. Admin (**root**) user ka home `/root` hai.

- `~` **aap ke** home folder ka shortcut hai.
- Jin files ke naam **dot se shuru** hote hain (jaise `.bashrc`) wo **chhupi** hoti hain. `ls -a` unhe dikhata hai.
- Aap ki SSH keys (`~/.ssh`) aur zaati settings yahin hoti hain.

</Ur>
</Tr>

```bash
echo "my home folder is: $(eval echo ~root)  (for the root user)"
cd ~ && touch .hidden-settings visible.txt
echo "ls shows:    $(ls)"
echo "ls -a shows: $(ls -a | grep -v '^\.\.\?$' | tr '\n' ' ')"
```

```text output
my home folder is: /root  (for the root user)
ls shows:    visible.txt
ls -a shows: .hidden-settings visible.txt 
```

<Happened>
<Tr>
<En>

- We created two files: `.hidden-settings` and `visible.txt`.
- Plain `ls` shows only `visible.txt`. `ls -a` ("all") also shows the dot file.

</En>
<Ur>

- Hum ne do files banayin: `.hidden-settings` aur `visible.txt`.
- Saada `ls` sirf `visible.txt` dikhata hai. `ls -a` ("all") dot wali file bhi dikhata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="/usr and /opt : installed software">

<Tr>
<En>

- `/usr/bin`: programs installed by the **package manager** (`ls`, `git`, `node`).
- `/usr/local/bin`: programs **you** install by hand.
- `/opt`: big third-party apps that come as one folder.

Never edit files in `/usr/bin` by hand: the next update overwrites them. `command -v name` tells you where a command lives.

</En>
<Ur>

- `/usr/bin`: **package manager** ke install kiye programs (`ls`, `git`, `node`).
- `/usr/local/bin`: wo programs jo **aap** haath se install karte hain.
- `/opt`: bari third-party apps jo ek folder ki shakal me aati hain.

`/usr/bin` ki files kabhi haath se edit na karein: agla update unhe mita deta hai. `command -v naam` batata hai ke command kahan rehti hai.

</Ur>
</Tr>

```bash
for cmd in ls bash grep; do echo "$cmd → $(readlink -f "$(command -v "$cmd")")"; done
```

```text output
ls → /usr/bin/ls
bash → /usr/bin/bash
grep → /usr/bin/grep
```

</Step>

<Step title="/tmp : the scratch room">

<Tr>
<En>

`/tmp` is for **temporary** files. **Everyone** can write there, and it's often emptied when the computer restarts. A special **sticky bit** stops users from deleting each other's files.

Never keep anything important or secret in `/tmp`.

</En>
<Ur>

`/tmp` **aarzi** files ke liye hai. Yahan **har koi** likh sakta hai, aur computer restart hone par aksar khaali ho jata hai. Ek khaas **sticky bit** users ko ek doosre ki files delete karne se rokta hai.

`/tmp` me kabhi koi ahem ya khufiya cheez na rakhein.

</Ur>
</Tr>

```bash
stat -c '%A %n' /tmp
```

```text output
drwxrwxrwt /tmp
```

<Happened>
<Tr>
<En>`rwxrwxrwx` would mean everyone can do everything. The last letter is `t` instead of `x`: that's the **sticky bit**.</En>
<Ur>`rwxrwxrwx` ka matlab hota har koi sab kuch kar sakta hai. Aakhri letter `x` ki jagah `t` hai: yahi **sticky bit** hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="/proc and /sys : live screens from the kernel">

<Tr>
<En>

These folders are **not stored on disk**. The kernel writes their content the moment you read them, like a live dashboard. `/proc` shows running programs and system state; `/sys` shows hardware.

Every running program has a folder `/proc/<its number>`. `$$` is the number of your own shell:

</En>
<Ur>

Ye folders **disk par save nahi**. Kernel inka content usi waqt likhta hai jab aap parhte hain, jaise live dashboard. `/proc` chalte programs aur system ki halat dikhata hai; `/sys` hardware.

Har chalte program ka ek folder hota hai `/proc/<us ka number>`. `$$` aap ke apne shell ka number hai:

</Ur>
</Tr>

```bash
echo "my shell's process folder: /proc/\$\$ = /proc/$$" | sed 's/= \/proc\/[0-9]*/= \/proc\/<PID>/'
cat /proc/$$/comm
tr '\0' ' ' < /proc/$$/cmdline | grep -q bash && echo "cmdline shows how it was started"
ls /proc/$$ | grep -E '^(cwd|environ|exe|fd)$' | tr '\n' ' '; echo
```

```text output
my shell's process folder: /proc/$$ = /proc/<PID>
bash
cmdline shows how it was started
cwd environ exe fd 
```

<Happened>
<Tr>
<En>

- `comm` = the program's name: `bash`.
- `cmdline` = the exact command used to start it.
- `cwd` = the folder it's working in, `exe` = the real program file, `fd` = the files it has open, `environ` = its settings (environment variables).
- During a security incident, `/proc/<PID>/exe` reveals what a suspicious program **really** is, even if it gave itself a fake name.

</En>
<Ur>

- `comm` = program ka naam: `bash`.
- `cmdline` = bilkul wo command jis se ye shuru hua.
- `cwd` = jis folder me ye kaam kar raha hai, `exe` = asal program file, `fd` = jo files is ne khol rakhi hain, `environ` = is ki settings (environment variables).
- Security incident ke dauran `/proc/<PID>/exe` batata hai ke shakki program **asal me** kya hai, chahe us ne apna jaali naam rakh liya ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="/dev : devices as files">

<Tr>
<En>

Hardware and special devices show up as files, so programs can use them like normal files:

- `/dev/sda`, `/dev/nvme0n1`: disks
- `/dev/null`: a **bin**: anything written here disappears
- `/dev/zero`: endless zero bytes
- `/dev/urandom`: endless random bytes

</En>
<Ur>

Hardware aur khaas devices files ki shakal me nazar aate hain, taa ke programs unhe aam files ki tarah istemal kar sakein:

- `/dev/sda`, `/dev/nvme0n1`: disks
- `/dev/null`: ek **kooradaan**: jo yahan likha jaye ghayab ho jata hai
- `/dev/zero`: zero bytes ki na khatam hone wali qataar
- `/dev/urandom`: random bytes ki na khatam hone wali qataar

</Ur>
</Tr>

```bash
echo "thrown away" > /dev/null && echo "/dev/null swallowed the text"
head -c 8 /dev/zero | od -An -tx1 | tr -s ' '
head -c 16 /dev/urandom | wc -c | sed 's/$/ random bytes read from \/dev\/urandom/'
```

```text output
/dev/null swallowed the text
 00 00 00 00 00 00 00 00
16 random bytes read from /dev/urandom
```

</Step>

<Step title="/mnt, /media : where extra disks appear">

<Tr>
<En>

Because there's only one tree, every extra disk must appear **as a folder** somewhere inside it. That folder is called a **mount point**: `/mnt` (manual), `/media` (USB sticks) or any folder like `/data`. `findmnt` and `df -h` show what is attached where. The **Disk, Mounts and Storage** lesson covers this in depth.

</En>
<Ur>

Chun ke tree sirf ek hai, har izafi disk ko is ke andar kahin **folder ki shakal me** nazar aana hota hai. Us folder ko **mount point** kehte hain: `/mnt` (haath se), `/media` (USB sticks) ya koi bhi folder jaise `/data`. `findmnt` aur `df -h` dikhate hain ke kya kahan jora hai. **Disk, Mounts and Storage** lesson ise tafseel se samjhata hai.

</Ur>
</Tr>

```bash
findmnt -no TARGET / | sed 's/^/the root file system is mounted at: /'
findmnt -no FSTYPE /proc | sed 's/^/\/proc is a file system of type: /'
```

```text output
the root file system is mounted at: /
/proc is a file system of type: proc
```

</Step>

## Common mistakes

<Compare>
<Bad title="Keeping app files in /tmp">

<Tr>
<En>Code or uploads in `/tmp` disappear on restart, and every user on the server can write there.</En>
<Ur>`/tmp` me code ya uploads restart par ghayab ho jate hain, aur server ka har user wahan likh sakta hai.</Ur>
</Tr>

</Bad>
<Good title="Use the right folder">

<Tr>
<En>App code in `/srv/<app>` or `/var/www/<app>`, data in `/var/lib/<app>`, owned by the app's own user.</En>
<Ur>App ka code `/srv/<app>` ya `/var/www/<app>` me, data `/var/lib/<app>` me, app ke apne user ki milkiyat.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Editing /usr/bin by hand">

<Tr>
<En>The next package update overwrites your changes without warning.</En>
<Ur>Agla package update baghair bataye aap ki tabdeeliyan mita deta hai.</Ur>
</Tr>

</Bad>
<Good title="/usr/local or /etc">

<Tr>
<En>Your own programs in `/usr/local/bin`; settings changes in `/etc`.</En>
<Ur>Apne programs `/usr/local/bin` me; settings ki tabdeeliyan `/etc` me.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Letting /var fill up">

<Tr>
<En>Old logs and Docker images pile up until the disk is 100% full and the database crashes.</En>
<Ur>Purane logs aur Docker images jama hote rehte hain, yahan tak ke disk 100% bhar jaye aur database crash ho jaye.</Ur>
</Tr>

</Bad>
<Good title="Watch and rotate">

<Tr>
<En>Check `df -h` regularly, rotate logs, and clean old images with `docker system prune`.</En>
<Ur>Baqaidagi se `df -h` check karein, logs rotate karein, aur purani images `docker system prune` se saaf karein.</Ur>
</Tr>

</Good>
</Compare>

<DeepDive title="Quick lookup: where is it?">

| Question | Look in |
| --- | --- |
| Where is the config of X? | `/etc/X/` or `/etc/X.conf` |

</DeepDive>

<DeepDive title="Real world: a VPS running a Node.js app">

```text
/etc/nginx/sites-available/app.conf    Nginx site config
/etc/systemd/system/app.service        systemd unit that runs the app
/etc/letsencrypt/live/example.com/     TLS certificates (private key here!)
/srv/app/                              application code (owned by user "app")
/srv/app/.env                          secrets (mode 600, owner app)
/var/log/nginx/access.log              every HTTP request
/var/log/nginx/error.log               proxy errors
/var/lib/postgresql/16/main/           database files
/home/deploy/.ssh/authorized_keys      who may SSH in as "deploy"
/var/backups/ or an S3 bucket          backups
```

When the site goes down at 2 a.m., you don't search randomly: `systemctl status app`, then `/var/log/nginx/error.log`, then `df -h` for a full `/var`. That speed comes from knowing the map.

</DeepDive>

<DeepDive title="Security lens">

Attackers follow the same map you do. These are the paths they read first, and the ones you should protect and monitor.

| Path | Why attackers want it | Protection |
| --- | --- | --- |
| `/etc/shadow` | Password hashes to crack offline | Root-only (mode 640/600); strong passwords; prefer SSH keys |
| `/etc/sudoers`, `/etc/sudoers.d/` | Who can become root | Minimal entries; edit with `visudo`; monitor changes |
| `~/.ssh/authorized_keys` | Adding a key = permanent backdoor | File integrity monitoring; review regularly |
| `~/.ssh/id_*`, `~/.aws/credentials`, `~/.kube/config` | Credentials to pivot to other systems and clouds | Mode 600; short-lived credentials; never on shared servers |
| `/etc/cron*`, `/etc/systemd/system/` | Persistence: run code at boot or on a schedule | Monitor for new files |
| `/tmp`, `/dev/shm` | World-writable: attackers drop and run tools here | Mount with `noexec` where possible |
| `/var/log/` | Evidence: attackers try to delete it | Ship logs off-host in real time |
| `/proc/<pid>/environ` | Environment variables, often containing secrets | Avoid long-lived secrets in env; restrict access |
| `/run/docker.sock` | Access to it is equivalent to root on the host | Never mount it into untrusted containers |

`/etc/passwd` being readable by everyone is normal: it lists accounts but holds no password hashes since those moved to `/etc/shadow`. Never commit or copy `~/.ssh`, `~/.aws` or `.env` files into repositories or Docker images.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Where would you look for a service's configuration and logs on Linux?">
Configuration is normally under /etc (for example /etc/nginx/ or /etc/ssh/sshd_config), and systemd units under /etc/systemd/system. Logs are in /var/log (for example /var/log/nginx/error.log) or in the systemd journal via journalctl -u service-name.
</QA>

<QA q="What is /proc?">
A virtual file system the kernel generates on the fly. It exposes information about every running process (/proc/PID/ with its command line, environment, open files and memory) and about the system (cpuinfo, meminfo, loadavg). Tools such as ps, top and free read it. Nothing in it is stored on disk.
</QA>

<QA q="What is the difference between /etc/passwd and /etc/shadow?">
/etc/passwd lists user accounts (username, UID, GID, home directory, shell) and is readable by everyone. /etc/shadow stores the password hashes and ageing information and is readable only by root, so hashes cannot be copied and cracked by ordinary users.
</QA>

<QA q="Why should manually installed software go in /usr/local or /opt?">
The package manager owns /usr/bin, /usr/lib and similar directories; files placed there by hand can be overwritten or conflict during package upgrades and are invisible to package queries. /usr/local and /opt are reserved for locally installed software, so the two never clash.
</QA>

<QA q="A server's disk is full. Where do you look first?">
Run df -h to see which file system is full, then du -xh --max-depth=1 on it, starting with /var: /var/log (unrotated logs), /var/lib/docker (images, containers, volumes), database directories under /var/lib, and /tmp. Also check for deleted-but-open files with lsof +L1.
</QA>

</DeepDive>
