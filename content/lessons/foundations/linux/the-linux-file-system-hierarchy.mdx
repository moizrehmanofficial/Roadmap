<Callout type="tip" title="In one minute">
Linux has **one** directory tree starting at the **root** `/` — no `C:` or `D:` drives. Each top-level folder has a job defined by the **Filesystem Hierarchy Standard (FHS)**: `/etc` = configuration, `/var` = changing data like **logs** (`/var/log`) and websites (`/var/www`), `/home` = users' files, `/root` = root's home, `/usr/bin` = programs, `/tmp` = temporary files, `/opt` = third-party software, `/proc` and `/sys` = live kernel information, `/dev` = devices, `/mnt` and `/media` = mounted disks. Knowing this map tells you where to look on any Linux server.
</Callout>

## Start from zero

### One tree, not drives

On Windows you have `C:\`, `D:\`, each a separate tree. Linux has **one** tree. Extra disks, USB sticks and network shares are attached (**mounted**) as folders somewhere inside it.

<Callout type="analogy">
A **well-organised office building** where every floor has a fixed purpose: the **records room** for rules and settings (`/etc`), the **logbook room** where daily activity is written down (`/var/log`), **personal offices** for each employee (`/home/sam`, `/home/emma`), the **manager's office** (`/root`), the **tool store** (`/usr/bin`), a **scratch room** cleaned every night (`/tmp`), and a **control room** with live dashboards of the building (`/proc`, `/sys`). Any employee moving to another branch of the company finds the same rooms on the same floors.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Root directory** | The top of the tree, written `/` | `/` |
| **Directory** | A folder | `/etc` |
| **Path** | Folders separated by `/` | `/var/log/nginx/access.log` |
| **FHS** | The standard describing what goes where | "configs go in /etc" |
| **Mount** | Attaching a disk's file system at a folder | a data disk at `/data` |
| **Virtual file system** | Files generated live by the kernel, not stored on disk | `/proc/cpuinfo` |
| **root** (user) vs `/` (folder) vs `/root` | The admin user; the top folder; the admin's home folder | three different things! |

## What is it?

```text
/
├── bin  → usr/bin      essential programs (ls, cp, bash)
├── boot                kernel and boot loader files
├── dev                 device files (disks, /dev/null, terminals)
├── etc                 system configuration (text files)
├── home                users' personal folders (/home/alex)
├── lib  → usr/lib      shared libraries
├── media, mnt          mount points for removable / extra disks
├── opt                 optional third-party software
├── proc                live process and kernel info (virtual)
├── root                home folder of the root user
├── run                 runtime data since boot (PID files, sockets)
├── sbin → usr/sbin     system administration programs
├── srv                 data served by this machine (sometimes)
├── sys                 live hardware and driver info (virtual)
├── tmp                 temporary files (often cleared on reboot)
├── usr                 installed software: bin, lib, share, local
└── var                 variable data: log, lib, cache, www, spool
```

On modern distros `/bin`, `/sbin` and `/lib` are just **symlinks** into `/usr` ("usr-merge").

## Why does it matter?

- **Troubleshooting speed:** "where are nginx's logs?" — `/var/log/nginx`. "Where is its config?" — `/etc/nginx`. You know before searching.
- **Backups:** what to back up (`/etc`, `/home`, `/var/www`, `/var/lib/postgresql`) and what to skip (`/proc`, `/tmp`, `/usr`).
- **Disk-full incidents:** almost always `/var/log`, `/var/lib/docker` or `/tmp`.
- **Security:** attackers hide in `/tmp` and `/dev/shm`; sensitive files live in `/etc` (`shadow`, SSH keys); audits check permissions there.
- **Docker:** you choose where volumes mount and where apps live in images (`/app`, `/usr/src/app`).

## When and where do you use it?

| Question | Look in |
| --- | --- |
| Where is the config of X? | `/etc/X/` or `/etc/X.conf` |
| Where are the logs? | `/var/log/` (or `journalctl`) |
| Where is the website? | `/var/www/` (or `/srv/`, `/opt/app`) |
| Where does the database keep data? | `/var/lib/postgresql`, `/var/lib/mysql` |
| Where does Docker keep images/volumes? | `/var/lib/docker` |
| Where do I put my own scripts/tools? | `/usr/local/bin` (system-wide) or `~/bin` |
| What hardware/process info exists? | `/proc`, `/sys` |

## Concepts one by one

### 1. `/` — the root of everything

<Explain>
<What>
The top-level directory. Every file and folder on the system is somewhere below it.
</What>
<Why>
One tree means one consistent way to address any file, on any disk.
</Why>
<When>
Every absolute path starts here.
</When>
<Where>
Every Linux and macOS system.
</Where>
<How>
`ls /` lists the top level. `cd /` goes there.
</How>
</Explain>

```bash
for d in etc var home usr tmp proc dev; do [[ -d /$d ]] && printf '/%s ' "$d"; done; echo
readlink /bin 2>/dev/null | sed 's/^/\/bin is a link to: /'
```

```text output
/etc /var /home /usr /tmp /proc /dev 
/bin is a link to: usr/bin
```

### 2. `/etc` — configuration

<Explain>
<What>
System-wide configuration files, almost all plain text.
</What>
<Why>
Configuration in one place makes servers easy to inspect, back up and manage with tools like Ansible.
</Why>
<When>
Configuring services, users, networking, hostnames, DNS.
</When>
<Where>
`/etc/nginx/`, `/etc/ssh/sshd_config`, `/etc/hosts`, `/etc/passwd`, `/etc/fstab`, `/etc/systemd/system/`.
</Where>
<How>
Read with `cat`/`less`, edit with `sudo nano`, and **back up before editing**: `sudo cp file file.bak`.
</How>
</Explain>

```bash
head -1 /etc/passwd
grep -c '' /etc/passwd > /dev/null && echo "/etc/passwd lists one user account per line"
grep -E '^127\.0\.0\.1' /etc/hosts | head -1 | awk '{print "/etc/hosts maps", $2, "to", $1}'
```

```text output
root:x:0:0:root:/root:/bin/bash
/etc/passwd lists one user account per line
/etc/hosts maps localhost to 127.0.0.1
```

| File | Purpose |
| --- | --- |
| `/etc/passwd`, `/etc/group` | Users and groups (no passwords) |
| `/etc/shadow` | Password hashes — readable only by root |
| `/etc/hosts` | Local name → IP overrides |
| `/etc/resolv.conf` | Which DNS servers to use |
| `/etc/fstab` | Disks mounted at boot |
| `/etc/ssh/sshd_config` | SSH server settings |
| `/etc/sudoers` | Who may use sudo |
| `/etc/os-release` | Distro name and version |

### 3. `/var` — data that changes

<Explain>
<What>
"Variable" data that grows and changes while the system runs.
</What>
<Why>
Separating changing data from programs makes backups and disk sizing easier. It is also where disks fill up.
</Why>
<When>
Reading logs, finding database files, checking disk usage.
</When>
<Where>
`/var/log` (logs), `/var/lib` (application state: databases, Docker), `/var/www` (websites), `/var/cache`, `/var/spool` (mail and print queues).
</Where>
<How>
`du -sh /var/*` shows what uses space.
</How>
</Explain>

```bash
for d in log lib cache; do [[ -d /var/$d ]] && echo "/var/$d exists"; done
```

```text output
/var/log exists
/var/lib exists
/var/cache exists
```

A typical disk-full investigation:

```text
$ sudo du -xh --max-depth=1 /var | sort -rh | head -4
21G   /var
18G   /var/lib          ← drill down: /var/lib/docker? /var/lib/mysql?
2.6G  /var/log          ← old logs not rotated?
310M  /var/cache
```

### 4. `/home` and `/root` — personal folders

<Explain>
<What>
Each normal user gets `/home/username`. The **root** user's home is `/root` (kept separate in case `/home` is on another disk).
</What>
<Why>
Users' files, SSH keys and personal settings stay separate and private.
</Why>
<When>
Working as a user, setting up SSH keys, per-user config.
</When>
<Where>
`~/.ssh/authorized_keys`, `~/.bashrc`, `~/.config/`.
</Where>
<How>
`~` is a shortcut for your home folder; `$HOME` holds its path. Files starting with `.` are **hidden** — show them with `ls -a`.
</How>
</Explain>

```bash
echo "my home folder is: $(eval echo ~root)  (for the root user)"
cd ~ && touch .hidden-settings visible.txt
echo "ls shows:    $(ls)"
echo "ls -a shows: $(ls -a | grep -v '^\.\.\?$' | tr '\n' ' ')"
```

```text output
my home folder is: /root  (for the root user)
ls shows:    visible.txt
ls -a shows: .hidden-settings visible.txt 
```

### 5. `/usr` and `/opt` — installed software

<Explain>
<What>
`/usr` holds software installed by the package manager: programs (`/usr/bin`), libraries (`/usr/lib`), shared data and docs (`/usr/share`). `/usr/local` is for software **you** install manually. `/opt` is for big self-contained third-party packages.
</What>
<Why>
Keeping manual installs out of package-managed folders prevents conflicts during upgrades.
</Why>
<When>
Installing tools by hand, finding where a program lives.
</When>
<Where>
`/usr/bin/git`, `/usr/local/bin/terraform`, `/opt/google/chrome`.
</Where>
<How>
`command -v name` or `which name` shows where a command lives.
</How>
</Explain>

```bash
for cmd in ls bash grep; do echo "$cmd → $(readlink -f "$(command -v "$cmd")")"; done
```

```text output
ls → /usr/bin/ls
bash → /usr/bin/bash
grep → /usr/bin/grep
```

### 6. `/tmp` — temporary files

<Explain>
<What>
A world-writable folder for temporary files, protected by the **sticky bit** so users cannot delete each other's files. Often cleared at reboot.
</What>
<Why>
Programs need scratch space.
</Why>
<When>
Downloads during installs, temporary processing.
</When>
<Where>
`/tmp` (and `/var/tmp`, which survives reboots).
</Where>
<How>
Use `mktemp` for unique names. Never store anything important or secret there long-term.
</How>
</Explain>

```bash
stat -c '%A %n' /tmp
```

```text output
drwxrwxrwt /tmp
```

The final `t` is the sticky bit.

### 7. `/proc` and `/sys` — live information from the kernel

<Explain>
<What>
**Virtual** file systems: their "files" do not exist on disk; the kernel creates their content when you read them. `/proc` describes processes and kernel state; `/sys` describes hardware and drivers.
</What>
<Why>
Tools like `ps`, `top`, `free` and `uptime` read these files. You can too — in scripts and investigations.
</Why>
<When>
Monitoring, troubleshooting, incident response.
</When>
<Where>
`/proc/cpuinfo`, `/proc/meminfo`, `/proc/loadavg`, `/proc/<PID>/` (one folder per process), `/sys/class/net/` (network interfaces).
</Where>
<How>
`cat /proc/loadavg`; `ls /proc/$$` for your own shell's process.
</How>
</Explain>

```bash
echo "my shell's process folder: /proc/\$\$ = /proc/$$" | sed 's/= \/proc\/[0-9]*/= \/proc\/<PID>/'
cat /proc/$$/comm
tr '\0' ' ' < /proc/$$/cmdline | grep -q bash && echo "cmdline shows how it was started"
ls /proc/$$ | grep -E '^(cwd|environ|exe|fd)$' | tr '\n' ' '; echo
```

```text output
my shell's process folder: /proc/$$ = /proc/<PID>
bash
cmdline shows how it was started
cwd environ exe fd 
```

During an incident, `/proc/<PID>/exe` (the real program file), `cmdline` and `cwd` reveal what a suspicious process really is — even if it renamed itself.

### 8. `/dev` — devices as files

<Explain>
<What>
Special files representing hardware and virtual devices.
</What>
<Why>
Programs read and write devices with the same file operations they use for normal files.
</Why>
<When>
Working with disks, redirecting output, generating random data.
</When>
<Where>
`/dev/sda`, `/dev/nvme0n1` (disks), `/dev/null` (bin), `/dev/zero`, `/dev/urandom` (random bytes), `/dev/tty` (your terminal).
</Where>
<How>
Treat them like files: `> /dev/null`, `head -c 16 /dev/urandom`.
</How>
</Explain>

```bash
echo "thrown away" > /dev/null && echo "/dev/null swallowed the text"
head -c 8 /dev/zero | od -An -tx1 | tr -s ' '
head -c 16 /dev/urandom | wc -c | sed 's/$/ random bytes read from \/dev\/urandom/'
```

```text output
/dev/null swallowed the text
 00 00 00 00 00 00 00 00
16 random bytes read from /dev/urandom
```

### 9. `/mnt`, `/media` and mount points

<Explain>
<What>
Folders where extra file systems are attached: data disks, USB drives, network shares.
</What>
<Why>
Because Linux has one tree, every additional disk must appear somewhere inside it.
</Why>
<When>
Adding a cloud data volume, mounting backups, USB drives.
</When>
<Where>
`/mnt` (temporary, manual mounts), `/media` (automatic removable media), or any folder like `/data`.
</Where>
<How>
`findmnt` or `df -h` shows what is mounted where. Covered in **Disk, Mounts and Storage**.
</How>
</Explain>

```bash
findmnt -no TARGET / | sed 's/^/the root file system is mounted at: /'
findmnt -no FSTYPE /proc | sed 's/^/\/proc is a file system of type: /'
```

```text output
the root file system is mounted at: /
/proc is a file system of type: proc
```

### 10. Where to put your own things

<Explain>
<What>
Conventions for placing your apps, scripts and data so others (and future you) can find them.
</What>
<Why>
Servers where apps live in random folders are hard to maintain and back up.
</Why>
<When>
Deploying apps, adding scripts and cron jobs.
</When>
<Where>
See the table.
</Where>
<How>
Follow the convention your team uses, and write it down in the README.
</How>
</Explain>

| What | Common place |
| --- | --- |
| Web app code | `/var/www/<app>` or `/opt/<app>` or `/srv/<app>` |
| Your admin scripts | `/usr/local/bin` (or `/opt/scripts`) |
| App configuration | `/etc/<app>/` |
| App data | `/var/lib/<app>/` |
| App logs | `/var/log/<app>/` (or the journal) |
| systemd services you write | `/etc/systemd/system/<app>.service` |
| In Docker images | `/app` or `/usr/src/app` |

## Hands-on

```bash
# 1. A tour of the top level with a one-line description
declare -A role=([etc]=config [var]="changing data" [home]="user folders" [usr]=software [tmp]=temporary [proc]="live kernel info" [dev]=devices)
for d in etc var home usr tmp proc dev; do printf '%-6s %s\n' "/$d" "${role[$d]}"; done


# 2. Virtual vs real: /proc files show size 0 but have content
echo "size on disk of /proc/version: $(stat -c %s /proc/version), but it contains: $(cut -c1-13 /proc/version)"
```

```text output
/etc   config
/var   changing data
/home  user folders
/usr   software
/tmp   temporary
/proc  live kernel info
/dev   devices
size on disk of /proc/version: 0, but it contains: Linux version
```

On your own machine, also run `ls -l /`, `ls /etc | head -30`, `ls /var/log`, and `man hier` (the manual page describing the hierarchy).

## Real-world example

A typical VPS running a Node.js app behind Nginx:

```text
/etc/nginx/sites-available/app.conf    Nginx site config
/etc/systemd/system/app.service        systemd unit that runs the app
/etc/letsencrypt/live/example.com/     TLS certificates (private key here!)
/srv/app/                              application code (owned by user "app")
/srv/app/.env                          secrets (mode 600, owner app)
/var/log/nginx/access.log              every HTTP request
/var/log/nginx/error.log               proxy errors
/var/lib/postgresql/16/main/           database files
/home/deploy/.ssh/authorized_keys      who may SSH in as "deploy"
/var/backups/ or an S3 bucket          backups
```

When the site goes down at 2 a.m., you do not search randomly: `systemctl status app`, then `/var/log/nginx/error.log`, then `df -h` for a full `/var`. That speed comes from knowing the map.

## Common mistakes

- **Editing files in `/usr/bin` or `/usr/lib` by hand** — the next package upgrade overwrites them. Use `/usr/local` or `/etc`.
- **Putting app code or uploads in `/tmp`** — it is cleared on reboot and writable by every user.
- **Letting `/var` fill up**: unrotated logs and old Docker images (`docker system prune`) are the usual causes, and a full disk can crash databases.
- **Confusing `/` (root directory) with `/root` (root user's home).**
- **Committing or copying `~/.ssh`, `~/.aws` or `.env` files** into repositories or Docker images.

## Security lens

<Callout type="security">
Attackers follow the same map you do. These are the paths they read first — and the ones you should protect and monitor.
</Callout>

| Path | Why attackers want it | Protection |
| --- | --- | --- |
| `/etc/shadow` | Password hashes to crack offline | Root-only (mode 640/600); strong passwords; prefer SSH keys |
| `/etc/sudoers`, `/etc/sudoers.d/` | Who can become root | Minimal entries; edit with `visudo`; monitor changes |
| `~/.ssh/authorized_keys` | Adding a key = permanent backdoor | File integrity monitoring; review regularly |
| `~/.ssh/id_*`, `~/.aws/credentials`, `~/.kube/config` | Credentials to pivot to other systems and clouds | Mode 600; short-lived credentials; never on shared servers |
| `/etc/cron*`, `/etc/systemd/system/` | Persistence: run code at boot or on a schedule | Monitor for new files |
| `/tmp`, `/dev/shm` | World-writable: attackers drop and run tools here | Mount with `noexec` where possible |
| `/var/log/` | Evidence — attackers try to delete it | Ship logs off-host in real time |
| `/proc/<pid>/environ` | Environment variables, often containing secrets | Do not keep long-lived secrets in env where avoidable; restrict access |
| `/run/docker.sock` | Access to it is equivalent to root on the host | Never mount it into untrusted containers |

`/etc/passwd` being world-readable is normal: it lists accounts but holds no password hashes since those moved to `/etc/shadow`.

## Interview questions

<QA q="Where would you look for a service's configuration and logs on Linux?">
Configuration is normally under /etc (for example /etc/nginx/ or /etc/ssh/sshd_config), and systemd units under /etc/systemd/system. Logs are in /var/log (for example /var/log/nginx/error.log) or in the systemd journal via journalctl -u service-name.
</QA>

<QA q="What is /proc?">
A virtual file system the kernel generates on the fly. It exposes information about every running process (/proc/PID/ with its command line, environment, open files and memory) and about the system (cpuinfo, meminfo, loadavg). Tools such as ps, top and free read it. Nothing in it is stored on disk.
</QA>

<QA q="What is the difference between /etc/passwd and /etc/shadow?">
/etc/passwd lists user accounts (username, UID, GID, home directory, shell) and is readable by everyone. /etc/shadow stores the password hashes and ageing information and is readable only by root, so hashes cannot be copied and cracked by ordinary users.
</QA>

<QA q="Why should manually installed software go in /usr/local or /opt?">
The package manager owns /usr/bin, /usr/lib and similar directories; files placed there by hand can be overwritten or conflict during package upgrades and are invisible to package queries. /usr/local and /opt are reserved for locally installed software, so the two never clash.
</QA>

<QA q="A server's disk is full. Where do you look first?">
Run df -h to see which file system is full, then du -xh --max-depth=1 on it, starting with /var: /var/log (unrotated logs), /var/lib/docker (images, containers, volumes), database directories under /var/lib, and /tmp. Also check for deleted-but-open files with lsof +L1.
</QA>
