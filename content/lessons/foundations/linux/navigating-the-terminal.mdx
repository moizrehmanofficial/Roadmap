<Callout type="tip" title="In one minute">
The **prompt** (`moiz@web-1:~$`) shows who you are, which machine, and which folder. A command is `command -options arguments`, like `ls -la /etc`. `pwd` shows where you are, `cd folder` moves, `ls` lists. `~` is home, `.` is here, `..` is the parent, `cd -` goes back. Press **Tab** to complete names, **↑** for previous commands, **Ctrl+R** to search history, **Ctrl+C** to stop a command. Get help with `command --help` or `man command`. Read files with `cat` (short), `less` (long, press `q` to quit), `head` and `tail -f` (watch a log live).
</Callout>

## Start from zero

### What is the terminal?

A terminal is a text window where you type commands and the computer answers in text. On servers there is usually **no** graphical desktop — the terminal is the only way to work.

<Callout type="analogy">
Using a **file explorer** is like walking around a building and pointing at things. The **terminal** is like phoning a very fast assistant who is standing inside the building: you say "go to the 3rd floor", "tell me what is in this room", "copy that file to the store room" — and the assistant does it instantly and reports back. You have to know the **words**, but once you do, you are much faster — and you can write the instructions down as scripts.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Prompt** | The text before your cursor, waiting for a command | `moiz@web-1:~$` |
| **Command** | The program to run | `ls` |
| **Option / flag** | Changes how the command behaves; starts with `-` or `--` | `-l`, `--all` |
| **Argument** | What the command should work on | `/etc` |
| **Working directory** | The folder you are "in" right now | `/home/moiz` |
| **Absolute path** | Full path from `/` | `/var/log/syslog` |
| **Relative path** | Path from the working directory | `logs/app.log` |
| **Home** | Your personal folder, written `~` | `/home/moiz` |

## What is it?

Navigating the terminal means knowing **where you are**, **moving** between folders, **seeing** what is there, **reading** files, and **finding help** — the basic moves you will make thousands of times.

```text
moiz@web-1:~/projects$ ls -la src
└┬─┘ └─┬─┘ └────┬────┘ │ └┬┘ └┬┘ └┬┘
 │     │        │      │  │   │   └ argument (what to work on)
 │     │        │      │  │   └ options (how)
 │     │        │      │  └ command
 │     │        │      └ $ = normal user   (# = root — be careful!)
 │     │        └ current folder (~ = home)
 │     └ machine name (host name)
 └ your user name
```

## Why does it matter?

- **Every server task starts here:** checking logs, editing configs, restarting services, deploying.
- **Speed:** experienced engineers do in seconds what takes minutes with a mouse.
- **Automation:** every command you type can go into a script.
- **Interviews and on-call:** you will be asked to "SSH in and find out why it's down" — navigation must be automatic.

## When and where do you use it?

| Goal | Command |
| --- | --- |
| Where am I? | `pwd` |
| What's here? | `ls`, `ls -la` |
| Go somewhere | `cd /var/log` |
| Go home / back / up | `cd`, `cd -`, `cd ..` |
| Read a file | `cat`, `less`, `head`, `tail` |
| Watch a log live | `tail -f /var/log/syslog` |
| Get help | `ls --help`, `man ls` |

## Concepts one by one

### 1. The structure of a command

<Explain>
<What>
A command line is: the **command**, then **options** that change its behaviour, then **arguments** it works on, separated by spaces.
</What>
<Why>
Once you know the pattern, you can read and write any command.
</Why>
<When>
Every command you type.
</When>
<Where>
Every shell.
</Where>
<How>
Short options use one dash and can be combined (`-l -a` = `-la`); long options use two dashes (`--all`). Some options take a value (`-n 5` or `--lines=5`).
</How>
</Explain>

```bash
mkdir -p demo && touch demo/a.txt demo/.hidden
ls demo
ls -a demo
ls --all demo
```

```text output
a.txt
.
..
.hidden
a.txt
.
..
.hidden
a.txt
```

`-a` and `--all` mean the same thing: "show hidden entries too" (names starting with `.`, plus `.` and `..`).

### 2. `pwd` — where am I?

<Explain>
<What>
**P**rint **W**orking **D**irectory: shows the full path of the folder you are in.
</What>
<Why>
Relative paths, `rm` and many commands act on the current folder. Running a command in the wrong folder is a classic mistake.
</Why>
<When>
Whenever you are unsure, and before any delete.
</When>
<Where>
Everywhere.
</Where>
<How>
Type `pwd`. Many prompts also show the folder.
</How>
</Explain>

```bash
cd /etc && pwd
cd /var/log && pwd
```

```text output
/etc
/var/log
```

### 3. `cd` — moving around

<Explain>
<What>
**C**hange **D**irectory: moves you to another folder.
</What>
<Why>
Working inside the right folder makes commands shorter and safer.
</Why>
<When>
Constantly.
</When>
<Where>
Everywhere.
</Where>
<How>
`cd /absolute/path`, `cd relative/path`, `cd ..` (up one), `cd ~` or just `cd` (home), `cd -` (previous folder).
</How>
</Explain>

```bash
cd /usr/share
echo "1: $PWD"
cd ..
echo "2: $PWD (went up one level)"
cd -  > /dev/null
echo "3: $PWD (cd - went back)"
cd
echo "4: home → $([[ $PWD == "$HOME" ]] && echo yes)"
```

```text output
1: /usr/share
2: /usr (went up one level)
3: /usr/share (cd - went back)
4: home → yes
```

### 4. Absolute vs relative paths

<Explain>
<What>
An **absolute** path starts with `/` and works from anywhere. A **relative** path starts from the current folder.
</What>
<Why>
Relative paths are shorter; absolute paths are reliable (especially in scripts and cron jobs).
</Why>
<When>
Relative while working interactively; absolute in scripts, configs and cron.
</When>
<Where>
Every command that takes a path.
</Where>
<How>
Special names: `.` = this folder, `..` = parent folder, `~` = your home, `~user` = another user's home.
</How>
</Explain>

```bash
mkdir -p ~/shop/src/components ~/shop/config
cd ~/shop/src/components
echo "here:                  $(pwd | sed "s|$HOME|~|")"
echo "../../config resolves: $(cd ../../config && pwd | sed "s|$HOME|~|")"
echo "./ is the same folder: $(cd . && pwd | sed "s|$HOME|~|")"
```

```text output
here:                  ~/shop/src/components
../../config resolves: ~/shop/config
./ is the same folder: ~/shop/src/components
```

<Callout type="analogy">
An absolute path is a **full postal address** — it works for anyone, anywhere. A relative path is "**two doors down, turn left**" — it only works if you know where the person is standing.
</Callout>

### 5. `ls` — what is here?

<Explain>
<What>
**L**i**s**t: shows the contents of a folder.
</What>
<Why>
You constantly need to see files, their sizes, owners, permissions and dates.
</Why>
<When>
Every time you enter a folder or check a result.
</When>
<Where>
Everywhere.
</Where>
<How>
Most-used options: `-l` (long details), `-a` (hidden too), `-h` (human sizes), `-t` (newest first), `-r` (reverse), `-S` (by size), `-R` (recursive). Combine: `ls -lah`, `ls -lt`.
</How>
</Explain>

```bash
mkdir -p lsdemo && cd lsdemo
printf '%.0s.' {1..2048} > big.log
echo hi > small.txt
touch -d '2026-01-01' old.txt
touch -d '2026-11-09' big.log
touch -d '2026-11-10' small.txt
ls -l --time-style=+%F | awk 'NR>1 {print $1, $5, $6, $7}'
echo "--- newest first:"; ls -t
echo "--- biggest first:"; ls -S
```

```text output
-rw-r--r-- 2048 2026-11-09 big.log
-rw-r--r-- 0 2026-01-01 old.txt
-rw-r--r-- 3 2026-11-10 small.txt
--- newest first:
small.txt
big.log
old.txt
--- biggest first:
big.log
small.txt
old.txt
```

(`touch -d` set fixed dates so the order is predictable.) The columns of `ls -l`: permissions, link count, owner, group, size, date, name.

### 6. Tab completion and wildcards

<Explain>
<What>
Pressing **Tab** completes command names, file names and paths. **Wildcards** (`*`, `?`) match many names at once.
</What>
<Why>
Less typing and **no typos** — Tab only completes names that really exist.
</Why>
<When>
Always. Press Tab after the first few letters; press it twice to see all options.
</When>
<Where>
Every interactive shell.
</Where>
<How>
`cd /var/lo` + Tab → `cd /var/log/`. `ls *.log` lists all `.log` files; `ls file?.txt` matches `file1.txt`, `fileA.txt`.
</How>
</Explain>

```bash
mkdir -p wild && cd wild && touch app.log error.log notes.txt file1.txt file2.txt
echo "*.log    → $(echo *.log)"
echo "file?.txt → $(echo file?.txt)"
echo "*        → $(echo *)"
```

```text output
*.log    → app.log error.log
file?.txt → file1.txt file2.txt
*        → app.log error.log file1.txt file2.txt notes.txt
```

### 7. Reading files: cat, less, head, tail

<Explain>
<What>
Commands to show a file's content: `cat` prints all of it, `less` lets you scroll, `head` shows the start, `tail` shows the end.
</What>
<Why>
Config files are short (cat), logs are huge (less, tail).
</Why>
<When>
Reading configs, checking logs, inspecting output.
</When>
<Where>
`/etc/*`, `/var/log/*`.
</Where>
<How>
`head -n 5 file`, `tail -n 20 file`. In `less`: arrow keys / Space to scroll, `/word` to search, `n` for next match, `G` to jump to the end, `q` to quit. `tail -f file` keeps showing new lines as they are written (Ctrl+C to stop).
</How>
</Explain>

```bash
seq 1 100 | sed 's/^/log line /' > app.log
echo "--- head -n 3:"; head -n 3 app.log
echo "--- tail -n 2:"; tail -n 2 app.log
echo "--- lines containing '5' at the end, counted: $(grep -c '5$' app.log)"
```

```text output
--- head -n 3:
log line 1
log line 2
log line 3
--- tail -n 2:
log line 99
log line 100
--- lines containing '5' at the end, counted: 10
```

Watching a log live while you reproduce a problem is one of the most useful habits in operations:

```text
$ sudo tail -f /var/log/nginx/error.log
2026/11/10 14:31:02 [error] 812#812: *41 connect() failed (111: Connection refused) while connecting to upstream ...
                ↑ new lines appear here as they happen — press Ctrl+C to stop
```

### 8. History and keyboard shortcuts

<Explain>
<What>
The shell remembers your previous commands, and has shortcuts for editing the command line.
</What>
<Why>
Re-running and fixing commands quickly saves enormous time.
</Why>
<When>
All day.
</When>
<Where>
Bash, zsh.
</Where>
<How>
See the table. `history` lists past commands; `!!` repeats the last one (`sudo !!` = "the last command, with sudo").
</How>
</Explain>

| Keys | Action |
| --- | --- |
| **↑ / ↓** | Previous / next command |
| **Ctrl+R** | Search history (type part of a command; Ctrl+R again for older) |
| **Tab** | Complete |
| **Ctrl+C** | Stop the running command |
| **Ctrl+L** | Clear the screen (same as `clear`) |
| **Ctrl+A / Ctrl+E** | Jump to start / end of the line |
| **Ctrl+U / Ctrl+K** | Delete to start / end of the line |
| **Ctrl+W** | Delete the previous word |
| **Ctrl+D** | Exit the shell (logout) |

### 9. Getting help

<Explain>
<What>
Built-in documentation: `--help` (quick summary), `man` (full manual), `type`/`which` (what a command is), `tldr` (short examples, optional install).
</What>
<Why>
Nobody remembers every option. Knowing how to look things up is more important than memorising.
</Why>
<When>
Whenever you meet a new command or forget an option.
</When>
<Where>
Every Linux system (minimal containers may not include man pages).
</Where>
<How>
`ls --help | less`, `man ls` (q to quit, `/word` to search), `type cd` (shows `cd` is a shell builtin).
</How>
</Explain>

```bash
type cd | sed 's/ is a shell builtin/: built into the shell itself/'
type ls | grep -q 'aliased\|/usr/bin/ls\|/bin/ls' && echo "ls: a separate program (or an alias for it)"
ls --help | head -1
```

```text output
cd: built into the shell itself
ls: a separate program (or an alias for it)
Usage: ls [OPTION]... [FILE]...
```

In the usage line, `[ ]` means optional and `...` means "can be repeated" — the same notation as in the usage messages you write for your own scripts.

### 10. Being careful: root and the `#` prompt

<Explain>
<What>
When the prompt ends with `#`, you are **root** — the all-powerful admin user.
</What>
<Why>
As root, a typo can delete the system. There is no recycle bin in the terminal.
</Why>
<When>
Every time you see `#`.
</When>
<Where>
After `sudo -i`, `su -`, or logging in as root.
</Where>
<How>
Work as a normal user and use `sudo` only for single commands that need it. Before `rm -r`, run `pwd` and `ls` first.
</How>
</Explain>

## Hands-on

```bash
cd ~
mkdir -p tour/{docs,logs,src/app}
touch tour/docs/readme.md tour/logs/{app,error}.log tour/src/app/main.js
cd tour

echo "1) where am I: $(pwd | sed "s|$HOME|~|")"
echo "2) folders here: $(ls -d */ | tr '\n' ' ')"
cd src/app && echo "3) moved to: $(pwd | sed "s|$HOME|~|")"
cd ../../logs && echo "4) relative jump to: $(basename "$PWD")"
echo "5) log files: $(ls *.log | tr '\n' ' ')"
cd - > /dev/null && echo "6) cd - took me back to: $(basename "$PWD")"
cd ~ && rm -rf tour && echo "7) cleaned up"
```

```text output
1) where am I: ~/tour
2) folders here: docs/ logs/ src/ 
3) moved to: ~/tour/src/app
4) relative jump to: logs
5) log files: app.log error.log 
6) cd - took me back to: app
7) cleaned up
```

`{docs,logs,src/app}` is **brace expansion**: Bash turns it into three separate arguments, so one `mkdir` creates three folders.

## Real-world example

It is 2 a.m. and the API returns 502 errors. An engineer who knows the terminal:

```bash
ssh deploy@api-01                               # check the prompt: right server?
systemctl status app --no-pager                 # is the service running?
journalctl -u app -n 50 --no-pager              # last 50 log lines
# → "Error: connect ECONNREFUSED 127.0.0.1:5432"
systemctl status postgresql --no-pager          # database stopped?
df -h /var                                      # → 100% — disk full, Postgres crashed
sudo du -xh /var --max-depth=2 | sort -h | tail # → /var/log/app grew to 30G
```

Six commands, five minutes, root cause found. The same investigation through a cloud console and SFTP client would take far longer — and on many servers is simply not possible.

## Common mistakes

- **Not checking the prompt** and running a command on production instead of staging, or as root instead of your user.
- **Typing paths instead of using Tab** — slow and error-prone.
- **Spaces in filenames without quotes**, especially in scripts.
- **Copy-pasting multi-line commands from the web** without reading them; a hidden newline can run a command before you meant to.
- **Pressing Ctrl+S** in some terminals freezes output; **Ctrl+Q** unfreezes it.
- **Using `;` instead of `&&`** in deploy commands, so later steps run even after a failure.

## Security lens

<Callout type="security">
Your shell history and your prompt are both security tools — and both can leak secrets.
</Callout>

- **History stores secrets:** `mysql -p'Secret123'`, `export AWS_SECRET_ACCESS_KEY=...` or `curl -H "Authorization: Bearer ..."` end up in `~/.bash_history`. Attackers read it first. Prefer prompts, files with tight permissions or environment files; in bash, a command starting with a **space** is not saved when `HISTCONTROL=ignorespace` (Ubuntu default is `ignoreboth`, which includes it).
- **History is also evidence:** in incident response, `~/.bash_history` of compromised accounts often shows exactly what an attacker ran (unless they cleared it — which is itself a signal).
- **Command-line arguments are visible** to other users through `ps`. Never pass passwords as arguments.
- **Paste-jacking:** web pages can show one command and put another on your clipboard. Paste into an editor first if in doubt.
- **Know who you are:** `id` and a `#` prompt tell you that you are root. Use a normal account and `sudo` for individual commands.

## Interview questions

<QA q="What is the difference between a terminal and a shell?">
The terminal (emulator) is the program that displays text and captures keyboard input. The shell is the command interpreter running inside it — bash, zsh, sh — which parses what you type, expands variables and wildcards, and starts programs. You can run different shells in the same terminal.
</QA>

<QA q="What is the difference between && and ; when chaining commands?">
With a semicolon, the next command runs regardless of whether the previous one succeeded. With &&, the next command runs only if the previous one exited with status 0. Deployment and build steps should use && so they stop at the first failure.
</QA>

<QA q="Why do single and double quotes behave differently in bash?">
Inside double quotes, the shell still expands variables, command substitution and escapes, but keeps spaces together as one argument. Inside single quotes, nothing is expanded; the text is passed literally. Use double quotes around variables in scripts to avoid word splitting, and single quotes for literal strings.
</QA>

<QA q="A command says 'command not found' but you know it is installed. What do you check?">
Check whether its directory is in $PATH (echo $PATH, and which or command -v to locate it), whether you are in the right shell or environment (for example nvm, a virtualenv or a different user with sudo), and whether the shell needs reloading after installation (hash -r or a new shell).
</QA>

<QA q="How can shell history become a security problem?">
Commands containing passwords, tokens or keys are saved to ~/.bash_history in plain text, where attackers or other administrators can read them. Avoid putting secrets on the command line, use prompts or protected files, configure HISTCONTROL/HISTIGNORE, and treat history files as sensitive.
</QA>

## Key terms

<Terms>
  <Term name="Terminal">The window that displays text and takes keyboard input.</Term>
  <Term name="Shell">The command interpreter, such as bash or zsh.</Term>
  <Term name="Prompt">The text showing the shell is ready, including user, host and directory.</Term>
  <Term name="Builtin">A command implemented inside the shell itself, such as cd.</Term>
  <Term name="PATH">The list of directories the shell searches for commands.</Term>
  <Term name="Tab completion">Pressing Tab to complete commands and paths.</Term>
  <Term name="Exit code">A number a command returns; 0 means success. Read it with $?.</Term>
  <Term name="Alias">A shortcut name for a longer command.</Term>
  <Term name="Globbing">The shell expanding wildcards like *.txt into matching filenames.</Term>
</Terms>
