<BigIdea>
<Tr>
<En>
Every file answers two questions: **who are you** to this file (its owner, its group, or anyone else), and **what may you do** (read it, change it, run it). `chmod` changes the "what", `chown` changes the "who".
</En>
<Ur>
Har file do sawalon ka jawab deti hai: is file ke liye **aap kaun hain** (maalik, us ka group, ya koi aur), aur **aap kya kar sakte hain** (parhna, badalna, chalana). `chmod` "kya" badalta hai, `chown` "kaun" badalta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- `ls -l` shows permissions like `-rwxr-x---`.
- After the first character, there are **three sets** of `r` (read), `w` (write), `x` (execute): for the **owner**, the **group**, and **others**.
- Each letter has a number: **r = 4, w = 2, x = 1**. So `rwx` = 7, `rw-` = 6, `r-x` = 5, `r--` = 4.
- `chmod 640 file` sets them; `chown user:group file` changes the owner.

</En>
<Ur>

- `ls -l` `-rwxr-x---` jaisi permissions dikhata hai.
- Pehle character ke baad `r` (parhna), `w` (likhna), `x` (chalana) ke **teen set** hain: **maalik**, **group**, aur **others** ke liye.
- Har letter ka number hai: **r = 4, w = 2, x = 1**. To `rwx` = 7, `rw-` = 6, `r-x` = 5, `r--` = 4.
- `chmod 640 file` inhe set karta hai; `chown user:group file` maalik badalta hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **"Permission denied"** is one of the most common errors when deploying, in Docker and in CI.
- **Secrets** readable by everyone (`.env`, keys, backups) are among the most common security findings.
- **SSH refuses** to use keys whose permissions are too open.

</En>
<Ur>

- **"Permission denied"** deploy karte waqt, Docker me aur CI me sab se aam errors me se ek hai.
- Har kisi ke parhne layak **secrets** (`.env`, keys, backups) sab se aam security masail me se hain.
- Bohot khuli permissions wali keys istemal karne se **SSH inkaar** kar deta hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- making a script runnable
- protecting secrets and SSH keys
- setting up a website folder
- fixing "Permission denied"

</En>
<Ur>

- script ko chalne layak banate waqt
- secrets aur SSH keys ki hifazat
- website ka folder tayyar karte waqt
- "Permission denied" theek karte waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

The numbers you'll use 90% of the time:

- `755`: programs and folders
- `644`: normal files
- `600`: secrets and private keys
- `700`: private folders like `~/.ssh`

And **never** `chmod 777`.

</En>
<Ur>

Wo numbers jo 90% waqt istemal honge:

- `755`: programs aur folders
- `644`: aam files
- `600`: secrets aur private keys
- `700`: private folders jaise `~/.ssh`

Aur **kabhi** `chmod 777` nahi.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **notebook** in an office. On its cover are three rules:

- the **owner** may read and write in it
- **teammates** (the group) may read it but not write
- **visitors** (others) may not even open it

Written on the cover: `rw- r-- ---`. `chmod` **rewrites the rules** on the cover; `chown` **hands the notebook** to a new owner.

</En>
<Ur>

Office me ek **notebook** ka socho. Us ke cover par teen qaide likhe hain:

- **maalik** is me parh aur likh sakta hai
- **saathi** (group) parh sakte hain lekin likh nahi sakte
- **mehman** (others) khol bhi nahi sakte

Cover par likha hai: `rw- r-- ---`. `chmod` cover ke **qaide dobara likhta** hai; `chown` notebook naye maalik ko **de deta** hai.

</Ur>
</Tr>

## Reading a permission string

```text
-rwxr-x---  1  alex  developers  4096  Nov 10 14:30  deploy.sh
│└┬┘└┬┘└┬┘     └┬─┘  └───┬────┘
│ │  │  │       │        └ group
│ │  │  │       └ owner
│ │  │  └ others:  ---  nothing
│ │  └ group:     r-x  read, execute
│ └ owner:        rwx  read, write, execute
└ type: - file, d directory, l link
```

<Tr>
<En>

Each set of three becomes one digit by adding: **read = 4, write = 2, execute = 1**.

| Number | Letters | Meaning |
| --- | --- | --- |
| 7 | `rwx` | read + write + execute |
| 6 | `rw-` | read + write |
| 5 | `r-x` | read + execute |
| 4 | `r--` | read only |
| 0 | `---` | nothing |

Think of it as a **price list**: read costs 4, write costs 2, execute costs 1. The owner wants read + write = 4 + 2 = **6**. The group wants read = **4**. Others get nothing = **0**. Total: **640**.

</En>
<Ur>

Teen ka har set jama kar ke ek digit banta hai: **read = 4, write = 2, execute = 1**.

| Number | Letters | Matlab |
| --- | --- | --- |
| 7 | `rwx` | parhna + likhna + chalana |
| 6 | `rw-` | parhna + likhna |
| 5 | `r-x` | parhna + chalana |
| 4 | `r--` | sirf parhna |
| 0 | `---` | kuch nahi |

Ise ek **qeemat ki list** samjhein: parhna 4 ka, likhna 2 ka, chalana 1 ka. Maalik ko parhna + likhna chahiye = 4 + 2 = **6**. Group ko parhna = **4**. Others ko kuch nahi = **0**. Kul: **640**.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Read permissions as letters and numbers">

<Tr>
<En>

`ls -l` shows letters; `stat -c %a` shows the number. Skip the first character (the type), then read three groups of three.

</En>
<Ur>

`ls -l` letters dikhata hai; `stat -c %a` number. Pehla character (type) chhor dein, phir teen teen ke teen group parhein.

</Ur>
</Tr>

```bash
touch report.txt && chmod 640 report.txt
mkdir -p private && chmod 700 private
stat -c '%A  %a  %n' report.txt private
```

```text output
-rw-r-----  640  report.txt
drwx------  700  private
```

<Happened>
<Tr>
<En>

- `report.txt` = `640`: owner reads and writes (6), group only reads (4), others nothing (0).
- `private` (a folder, `d`) = `700`: only the owner can do anything.

</En>
<Ur>

- `report.txt` = `640`: maalik parhta aur likhta hai (6), group sirf parhta hai (4), others kuch nahi (0).
- `private` (folder, `d`) = `700`: sirf maalik kuch kar sakta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="chmod with letters: small, clear changes">

<Tr>
<En>

Write **who** + **add/remove/set** + **what**:

- who: `u` owner, `g` group, `o` others, `a` all
- `+` add, `-` remove, `=` set exactly
- what: `r`, `w`, `x`

So `chmod u+x` = "owner, add execute"; `chmod go-r` = "group and others, remove read".

</En>
<Ur>

Likhein **kaun** + **shamil/hatao/set** + **kya**:

- kaun: `u` maalik, `g` group, `o` others, `a` sab
- `+` shamil, `-` hatao, `=` bilkul yahi set karo
- kya: `r`, `w`, `x`

To `chmod u+x` = "maalik, chalana shamil karo"; `chmod go-r` = "group aur others, parhna hatao".

</Ur>
</Tr>

```bash
touch script.sh && chmod 644 script.sh
stat -c '%A  start' script.sh
chmod u+x script.sh;        stat -c '%A  after u+x' script.sh
chmod go-r script.sh;       stat -c '%A  after go-r' script.sh
chmod u=rwx,g=rx,o= script.sh; stat -c '%A  after u=rwx,g=rx,o=' script.sh
```

```text output
-rw-r--r--  start
-rwxr--r--  after u+x
-rwx------  after go-r
-rwxr-x---  after u=rwx,g=rx,o=
```

<Happened>
<Tr>
<En>

- `u+x`: the owner got an `x`, so now the owner can run the script.
- `go-r`: group and others lost their `r`.
- `u=rwx,g=rx,o=`: set everything exactly in one go. `o=` with nothing after it means "others get nothing".

</En>
<Ur>

- `u+x`: maalik ko `x` mila, ab maalik script chala sakta hai.
- `go-r`: group aur others se `r` chhin gaya.
- `u=rwx,g=rx,o=`: ek hi baar me sab bilkul set. `o=` ke baad kuch na ho to matlab "others ko kuch nahi".

</Ur>
</Tr>
</Happened>

</Step>

<Step title="chmod with numbers: the whole setting at once">

<Tr>
<En>

Three digits set **everything** in one go: owner, group, others. This is the form you'll see in guides, scripts and Dockerfiles.

</En>
<Ur>

Teen digits **sab kuch** ek saath set karte hain: maalik, group, others. Guides, scripts aur Dockerfiles me yahi shakal nazar aayegi.

</Ur>
</Tr>

```bash
touch f
for m in 777 755 750 700 644 640 600 400; do chmod "$m" f; printf '%s = %s\n' "$m" "$(stat -c %A f | cut -c2-)"; done
```

```text output
777 = rwxrwxrwx
755 = rwxr-xr-x
750 = rwxr-x---
700 = rwx------
644 = rw-r--r--
640 = rw-r-----
600 = rw-------
400 = r--------
```

<Happened>
<Tr>
<En>This table is worth memorising. `777` (everyone can do everything) is at the top only so you can **recognise** it: you should almost never use it.</En>
<Ur>Ye table yaad karne layak hai. `777` (har koi sab kuch kar sakta hai) sab se upar sirf is liye hai taa ke aap ise **pehchan** sakein: ise taqreeban kabhi istemal nahi karna.</Ur>
</Tr>
</Happened>

</Step>

<Step title="See permissions in action">

<Tr>
<En>

Let's watch what really happens when a normal user (`demo`) tries to read a secret file and run a script without permission. (We use a normal user because **root ignores most permissions**.)

</En>
<Ur>

Dekhte hain jab aam user (`demo`) baghair ijazat khufiya file parhne aur script chalane ki koshish kare to asal me kya hota hai. (Hum aam user istemal kar rahe hain kyun ke **root zyada tar permissions nazar andaz karta hai**.)

</Ur>
</Tr>

```bash
useradd -m demo 2>/dev/null
mkdir -p /srv/permtest && cd /srv/permtest
echo "secret=42" > secret.txt && chmod 600 secret.txt
printf '#!/bin/sh\necho "script ran"\n' > run.sh && chmod 644 run.sh

sudo -u demo cat secret.txt 2>&1 | sed 's/^cat: //'
sudo -u demo bash -c ./run.sh 2>&1 | sed "s/^.*: //"
chmod 755 run.sh && sudo -u demo bash -c ./run.sh
chmod 644 secret.txt && sudo -u demo cat secret.txt

cd / && rm -rf /srv/permtest && userdel -r demo 2>/dev/null
```

```text output
secret.txt: Permission denied
Permission denied
script ran
secret=42
```

<Happened>
<Tr>
<En>

- `secret.txt` is `600`: `demo` is "others", so reading it fails.
- `run.sh` is `644`: nobody has `x`, so running it fails.
- After `chmod 755 run.sh`, others have `x`, and the script runs.
- After `chmod 644 secret.txt`, others have `r`, and `demo` can read the secret. (That's exactly what you **don't** want for real secrets.)

</En>
<Ur>

- `secret.txt` `600` hai: `demo` "others" hai, isliye parhna fail.
- `run.sh` `644` hai: kisi ke paas `x` nahi, isliye chalana fail.
- `chmod 755 run.sh` ke baad others ke paas `x` hai, aur script chal jati hai.
- `chmod 644 secret.txt` ke baad others ke paas `r` hai, aur `demo` secret parh leta hai. (Asli secrets ke liye bilkul yahi **nahi** chahiye.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Folders: r, w and x mean something different">

<Tr>
<En>

On a **folder**:

- **r** = see the list of names inside
- **w** = create, delete or rename things inside
- **x** = **go in** and reach things inside

To open `/var/www/shop/index.html`, you need `x` on **every folder along the way**: `/var`, `/var/www`, `/var/www/shop`. "I can read the file but still get Permission denied" almost always means a folder up the path is missing `x`. `namei -l` shows the whole path at once:

</En>
<Ur>

**Folder** par:

- **r** = andar ke naamon ki list dekhna
- **w** = andar cheezen banana, delete ya rename karna
- **x** = **andar jana** aur andar ki cheezon tak pohanchna

`/var/www/shop/index.html` kholne ke liye **raste ke har folder** par `x` chahiye: `/var`, `/var/www`, `/var/www/shop`. "File parh sakta hoon phir bhi Permission denied" ka matlab taqreeban hamesha ye hai ke raste me kisi folder par `x` nahi. `namei -l` poora raasta ek saath dikhata hai:

</Ur>
</Tr>

```bash
namei -l /etc/hostname | tail -n +2
```

```text output
drwxr-xr-x root root /
drwxr-xr-x root root etc
-rw-r--r-- root root hostname
```

<Tr>
<En>

| Folder mode | Can list (`ls`) | Can go in / open files | Can create/delete files |
| --- | --- | --- | --- |
| `r-x` (5) | Yes | Yes | No |
| `--x` (1) | No | Yes, if you know the name | No |
| `r--` (4) | Names only | No | No |
| `rwx` (7) | Yes | Yes | Yes |

</En>
<Ur>

| Folder mode | List (`ls`) | Andar jana / files kholna | Files banana/delete |
| --- | --- | --- | --- |
| `r-x` (5) | Haan | Haan | Nahi |
| `--x` (1) | Nahi | Haan, agar naam pata ho | Nahi |
| `r--` (4) | Sirf naam | Nahi | Nahi |
| `rwx` (7) | Haan | Haan | Haan |

</Ur>
</Tr>

</Step>

<Step title="chown: hand files to the right owner">

<Tr>
<En>

Files must belong to the user that needs them: the app's service account, the web server, a deploy user.

- `chown user file`: new owner
- `chown user:group file`: new owner **and** group
- `chown -R user:group folder/`: everything inside too

Only root can give files away, so on a server it's usually `sudo chown`.

</En>
<Ur>

Files us user ki honi chahiyen jise un ki zaroorat hai: app ka service account, web server, deploy user.

- `chown user file`: naya maalik
- `chown user:group file`: naya maalik **aur** group
- `chown -R user:group folder/`: andar ki har cheez bhi

Sirf root files kisi ko de sakta hai, isliye server par aam taur par `sudo chown`.

</Ur>
</Tr>

```bash
groupadd -f webteam
useradd -M -s /usr/sbin/nologin webapp 2>/dev/null
mkdir -p site/css && touch site/index.html site/css/style.css
chown -R webapp:webteam site
find site -printf '%u:%g %p\n' | sort -k2
userdel webapp; groupdel webteam
```

```text output
webapp:webteam site
webapp:webteam site/css
webapp:webteam site/css/style.css
webapp:webteam site/index.html
```

<Happened>
<Tr>
<En>One `chown -R` gave the whole `site` folder, and everything inside it, to user `webapp` and group `webteam`.</En>
<Ur>Ek `chown -R` ne poora `site` folder, aur us ke andar ki har cheez, user `webapp` aur group `webteam` ko de di.</Ur>
</Tr>
</Happened>

</Step>

<Step title="umask: the default for new files">

<Tr>
<En>

When a program creates a new file, who can read it? The **umask** decides. It **removes** permissions from the starting point (666 for files, 777 for folders):

- `022` → files `644`, folders `755` (others can read)
- `027` → files `640`, folders `750` (others get nothing)
- `077` → files `600`, folders `700` (only you)

Services that handle secrets should use `077`.

</En>
<Ur>

Jab koi program nayi file banata hai, use kaun parh sakta hai? **umask** tay karta hai. Ye shuruati nuqte (files ke liye 666, folders ke liye 777) se permissions **hata deta** hai:

- `022` → files `644`, folders `755` (others parh sakte hain)
- `027` → files `640`, folders `750` (others ko kuch nahi)
- `077` → files `600`, folders `700` (sirf aap)

Secrets sambhalne wali services ko `077` istemal karna chahiye.

</Ur>
</Tr>

```bash
for m in 022 027 077; do
  ( umask $m; touch "f$m"; mkdir "d$m"; printf 'umask %s → file %s, dir %s\n' "$m" "$(stat -c %a "f$m")" "$(stat -c %a "d$m")" )
done
```

```text output
umask 022 → file 644, dir 755
umask 027 → file 640, dir 750
umask 077 → file 600, dir 700
```

</Step>

<Step title="Special bits: setuid, setgid, sticky">

<Tr>
<En>

Three extra switches, written as a **fourth digit in front**:

- **setuid (4)**: the program runs as its **owner** (often root). `passwd` uses it to change the password file.
- **setgid (2)**: on a folder, new files automatically get the **folder's group**. Great for team folders.
- **sticky (1)**: in a shared folder, only a file's owner can delete it. `/tmp` uses it.

They show up as `s` or `t` where `x` would be.

</En>
<Ur>

Teen izafi switch, **aage chautha digit** likh kar:

- **setuid (4)**: program apne **maalik** (aksar root) ke taur par chalta hai. `passwd` ise password file badalne ke liye istemal karta hai.
- **setgid (2)**: folder par, nayi files ko khud ba khud **folder ka group** milta hai. Team folders ke liye behtareen.
- **sticky (1)**: share shuda folder me sirf file ka maalik use delete kar sakta hai. `/tmp` ise istemal karta hai.

Ye `x` ki jagah `s` ya `t` ki shakal me dikhte hain.

</Ur>
</Tr>

```bash
groupadd -f team
mkdir -p shared && chgrp team shared && chmod 2775 shared
touch shared/new-file
stat -c '%A %G %n' shared shared/new-file
groupdel team 2>/dev/null; true
```

```text output
drwxrwsr-x team shared
-rw-r--r-- team shared/new-file
```

<Happened>
<Tr>
<En>

- `2775`: the `2` in front turns on setgid. See the `s` in the group part: `rws`.
- The new file automatically belongs to group `team`, even though we didn't say so. Every teammate's new files land in the right group.

</En>
<Ur>

- `2775`: aage ka `2` setgid on karta hai. Group wale hisse me `s` dekhein: `rws`.
- Nayi file khud ba khud group `team` ki ho gayi, halanke hum ne nahi kaha tha. Har saathi ki nayi files sahi group me jati hain.

</Ur>
</Tr>
</Happened>

<Tr>
<En>Listing setuid programs is a standard security audit step. Anything unexpected deserves a closer look:</En>
<Ur>setuid programs ki list banana security audit ka aam qadam hai. Koi bhi ghair mutawaqqa cheez ghaur se dekhne layak hai:</Ur>
</Tr>

```text
$ sudo find / -perm -4000 -type f 2>/dev/null
/usr/bin/passwd
/usr/bin/sudo
/usr/bin/su
...                     ← anything unexpected here deserves investigation
```

</Step>

<Step title="Recipes for real servers">

<Tr>
<En>

Most permission problems come from guessing, or from "fixing" with `chmod 777`. Copy these instead:

</En>
<Ur>

Zyada tar permission masail andaze se aate hain, ya `chmod 777` se "theek" karne se. In ki jagah ye copy karein:

</Ur>
</Tr>

```text
# SSH (on your laptop and on servers)
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519 ~/.ssh/authorized_keys
chmod 644 ~/.ssh/id_ed25519.pub

# A web app run by the user "shopapp", served by nginx (group www-data)
sudo chown -R shopapp:www-data /var/www/shop
sudo find /var/www/shop -type d -exec chmod 750 {} +    # folders: owner rwx, group r-x
sudo find /var/www/shop -type f -exec chmod 640 {} +    # files:   owner rw,  group r
sudo chmod 600 /var/www/shop/.env                      # secrets: owner only
sudo chmod 770 /var/www/shop/storage                   # a folder the app must write to
```

<Happened>
<Tr>
<En>

- SSH keys: private key `600`, the `.ssh` folder `700`. The public key (`.pub`) can be `644`.
- For the web app, we treat **folders** and **files** separately with `find -type d` / `-type f`. A plain `chmod -R 755` would make every file executable, which is wrong.
- Only the `storage` folder is writable by the group; the code itself isn't.

</En>
<Ur>

- SSH keys: private key `600`, `.ssh` folder `700`. Public key (`.pub`) `644` ho sakti hai.
- Web app ke liye hum `find -type d` / `-type f` se **folders** aur **files** ko alag sambhalte hain. Saada `chmod -R 755` har file ko chalne layak bana deta, jo ghalat hai.
- Sirf `storage` folder group ke liye likhne layak hai; code khud nahi.

</Ur>
</Tr>
</Happened>

| Thing | Typical mode | Owner |
| --- | --- | --- |
| Scripts you run | `755` or `750` | you |
| Normal files, web content | `644` | owner of the app |
| Secrets: `.env`, private keys, `credentials` | `600` | the app's user |
| `~/.ssh` folder | `700` | you |
| `~/.ssh/authorized_keys` | `600` | you |
| Normal directories | `755` | |
| Private directories | `700` or `750` | |
| `/tmp`-like shared folders | `1777` (sticky) | root |

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="chmod -R 777 to fix anything">

<Tr>
<En>It gives **every user and every hacked program** the power to change your files. It hides the real problem.</En>
<Ur>Ye **har user aur har hack shuda program** ko aap ki files badalne ki taqat de deta hai. Asal masla chhup jata hai.</Ur>
</Tr>

</Bad>
<Good title="Find who needs access, give only that">

<Tr>

<Takeaways>
<Tr>
<En>

- Permissions = three sets of `rwx` for **owner, group, others**.
- **r = 4, w = 2, x = 1**. Add them up per set: `rwx` = 7, `rw-` = 6, `r-x` = 5, `r--` = 4.

<DeepDive title="ACLs: extra permissions for one more user">

**Access Control Lists** add permissions for additional named users or groups, beyond the single owner and group. Useful when one extra account (backups, CI) needs read access without changing the owner. A `+` at the end of the `ls -l` permissions means an ACL exists. Tools: `setfacl`, `getfacl` (package `acl`).

```text
$ setfacl -m u:backup:r-- /var/www/shop/.env
$ ls -l /var/www/shop/.env
-rw-r-----+ 1 shopapp shopapp 220 Nov 10 14:30 .env      ← the + means "has an ACL"
$ getfacl /var/www/shop/.env
user::rw-
user:backup:r--
group::r--
other::---
```

`setfacl -b file` removes all ACL entries.

</DeepDive>

<DeepDive title="Real world: 403 Forbidden after deploying">

After deploying a Next.js static export behind Nginx, the site returns **403 Forbidden**.

```bash
sudo tail -n 5 /var/log/nginx/error.log
# open() "/home/deploy/site/index.html" failed (13: Permission denied)

namei -l /home/deploy/site/index.html
# drwxr-xr-x root   root   /
# drwxr-xr-x root   root   home
# drwxr-x--- deploy deploy deploy        ← www-data has no x here
# drwxr-xr-x deploy deploy site
# -rw-r--r-- deploy deploy index.html
```

Nginx runs as `www-data`, which is "others" for `/home/deploy`, and others have no `x`. Wrong fixes: `chmod 777 /home/deploy`, or running Nginx as root. Right fixes:

- Deploy static files to `/var/www/site` owned by `deploy` with `755`/`644` permissions, or
- Grant only what's needed: `sudo setfacl -m u:www-data:x /home/deploy`.

Also watch out for Docker `COPY` without `--chown`, which leaves files owned by root so the non-root app user can't write where it needs to.

</DeepDive>

<DeepDive title="Security lens">

Permissions are the last line of defence once an attacker has a foothold. Check them the way an attacker would.

- **World-writable + run by root = root for everyone.** A cron script, systemd unit or script in root's `PATH` that others can edit is an instant privilege escalation. Find them with `find / -xdev -perm -0002 -type f`.
- **setuid binaries** run as root. Unusual ones (or `cp`, `find`, `vim`, `python` with setuid) are escalation paths. Keep a baseline list and alert on changes.
- **Secrets readable by others:** `.env`, `config/database.yml`, backups and private keys must be `600`/`640`. SSH refuses keys that are too open; your app won't.
- **Web roots:** the web server should be able to *read* the site but not *write* it (except an upload folder, which must never execute code). Writable code folders turn file-upload bugs into remote code execution.
- **Containers:** run as a non-root UID; mount the root file system read-only (`readOnlyRootFilesystem: true` in Kubernetes) and give write access only to specific volumes.
- **Default umask** for services handling secrets should be `077`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does chmod 755 mean, and when would you use it?">
7 for the owner is read, write and execute; 5 for group and others is read and execute. It is the standard mode for directories and executable scripts: the owner can modify, everyone can read and run or enter, but only the owner can change it.
</QA>

<QA q="A web server returns 403 for a static file that exists. How do you debug it?">
Check the web server error log for "Permission denied", identify the user the server runs as (for example www-data), and inspect every directory in the path with `namei -l /full/path`. The user needs execute on every directory and read on the file. Fix ownership, group membership or an ACL, not chmod 777 or running the server as root. Also check SELinux/AppArmor where enabled.
</QA>

<QA q="What is the setuid bit and why is it a security risk?">
When set on an executable, the program runs with the privileges of the file's owner rather than the user who started it; passwd uses it to modify /etc/shadow as root. If a setuid-root program has a bug or can spawn a shell or write arbitrary files, any user can escalate to root, so setuid binaries should be minimal, audited and monitored.
</QA>

<QA q="What permissions should an SSH private key have, and why?">
600 (read and write for the owner only), inside a ~/.ssh directory with 700. The SSH client refuses to use private keys readable by other users, because anyone who can read the key can impersonate you.
</QA>

<QA q="What is umask?">
umask is a mask of permission bits removed from newly created files and directories. Files start from 666 and directories from 777; with umask 022 they become 644 and 755, and with 077 they become 600 and 700. It is set per process, for example in shell profiles or a systemd unit's UMask setting.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Mode">A file's permission bits, such as 644 or -rw-r--r--.</Term>
  <Term name="chmod">Changes permission bits.</Term>
  <Term name="chown / chgrp">Changes a file's owner and/or group.</Term>
  <Term name="umask">Bits removed from default permissions of new files.</Term>
  <Term name="setuid / setgid">Special bits that run a program as its owner or group; setgid on directories passes the group to new files.</Term>
  <Term name="Sticky bit">On shared directories, only a file's owner may delete it.</Term>
  <Term name="ACL">Access control list granting permissions to extra users or groups.</Term>
  <Term name="namei">A tool that shows permissions along every component of a path.</Term>
</Terms>

</DeepDive>
