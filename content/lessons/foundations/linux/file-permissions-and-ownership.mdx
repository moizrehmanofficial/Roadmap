<Callout type="tip" title="In one minute">
`ls -l` shows permissions like `-rwxr-x---`: the first character is the type, then three sets of **r**ead/**w**rite/e**x**ecute for the **owner**, the **group**, and **others**. Change them with `chmod`: letters (`chmod u+x script.sh`, `chmod go-w file`) or numbers (`chmod 755` = rwxr-xr-x, `644` = rw-r--r--, `600` = rw-------). Change the owner with `chown user:group file` (`-R` for folders). Secrets: `600`. SSH: `~/.ssh` = `700`, private key = `600`. Never `chmod 777`.
</Callout>

## Start from zero

### Who may do what with a file?

Every file answers three questions for three kinds of people. **Who** are you to this file — its owner, a member of its group, or anyone else? And **what** may you do — read it, change it, run it?

<Callout type="analogy">
A **notebook** in an office: the **owner** may read and write in it; **teammates** (the group) may read it but not write; **visitors** (others) may not even open it. Written on the cover: `rw- r-- ---`. `chmod` rewrites the rules on the cover; `chown` hands the notebook to a new owner.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Owner (u)** | The user the file belongs to | `alex` |
| **Group (g)** | The group the file belongs to | `www-data` |
| **Others (o)** | Everyone else | any other user |
| **r / w / x** | Read / write / execute | `rwx` |
| **Mode** | The full permission setting | `755` or `rwxr-xr-x` |
| **chmod** | Change mode (permissions) | `chmod 600 key` |
| **chown** | Change owner (and group) | `chown www-data:www-data site/` |
| **Octal** | Writing permissions as numbers 0–7 | `6` = rw- |

## What is it?

```text
-rwxr-x---  1  alex  developers  4096  Nov 10 14:30  deploy.sh
│└┬┘└┬┘└┬┘     └┬─┘  └───┬────┘
│ │  │  │       │        └ group
│ │  │  │       └ owner
│ │  │  └ others:  ---  nothing
│ │  └ group:     r-x  read, execute
│ └ owner:        rwx  read, write, execute
└ type: - file, d directory, l link
```

| Number | Letters | Meaning |
| --- | --- | --- |
| 7 | `rwx` | read + write + execute |
| 6 | `rw-` | read + write |
| 5 | `r-x` | read + execute |
| 4 | `r--` | read only |
| 0 | `---` | nothing |

Each digit is the sum: **r = 4, w = 2, x = 1**. Three digits = owner, group, others.

## Why does it matter?

- **"Permission denied"** is one of the most common errors in deployments, Docker volumes and CI.
- **Security:** world-readable secrets (`.env`, private keys, backups) and world-writable scripts are among the most common real findings in audits and pentests.
- **SSH refuses keys** with permissions that are too open.
- **Web servers** need to read files but should not be able to change the code.

## When and where do you use it?

| Thing | Typical mode | Owner |
| --- | --- | --- |
| Scripts you run | `755` or `750` | you |
| Normal files, web content | `644` | owner of the app |
| Secrets: `.env`, private keys, `credentials` | `600` | the app's user |
| `~/.ssh` folder | `700` | you |
| `~/.ssh/authorized_keys` | `600` | you |
| Normal directories | `755` | |
| Private directories | `700` or `750` | |
| `/tmp`-like shared folders | `1777` (sticky) | root |

## Concepts one by one

### 1. Reading permissions

<Explain>
<What>
The 10-character string in `ls -l`, or the number from `stat -c %a`.
</What>
<Why>
You cannot fix a permission problem you cannot read.
</Why>
<When>
Every "Permission denied", every security check.
</When>
<Where>
`ls -l`, `stat`, `namei -l` (permissions along a whole path).
</Where>
<How>
Skip the first character (type), then read three groups of three.
</How>
</Explain>

```bash
touch report.txt && chmod 640 report.txt
mkdir -p private && chmod 700 private
stat -c '%A  %a  %n' report.txt private
```

```text output
-rw-r-----  640  report.txt
drwx------  700  private
```

### 2. chmod with letters

<Explain>
<What>
Change specific permissions using **who** (`u`, `g`, `o`, `a` = all), an **operator** (`+` add, `-` remove, `=` set exactly) and **what** (`r`, `w`, `x`).
</What>
<Why>
Precise, readable changes: "add execute for the owner", "remove write for others".
</Why>
<When>
Small adjustments without thinking about numbers.
</When>
<Where>
Making scripts executable, removing group/other access.
</Where>
<How>
`chmod u+x file`, `chmod go-rwx file`, `chmod a=r file`, `chmod u=rw,g=r,o= file`.
</How>
</Explain>

```bash
touch script.sh && chmod 644 script.sh
stat -c '%A  start' script.sh
chmod u+x script.sh;        stat -c '%A  after u+x' script.sh
chmod go-r script.sh;       stat -c '%A  after go-r' script.sh
chmod u=rwx,g=rx,o= script.sh; stat -c '%A  after u=rwx,g=rx,o=' script.sh
```

```text output
-rw-r--r--  start
-rwxr--r--  after u+x
-rwx------  after go-r
-rwxr-x---  after u=rwx,g=rx,o=
```

### 3. chmod with numbers

<Explain>
<What>
Set the whole mode at once with three octal digits.
</What>
<Why>
Short and exact; the form used in docs, scripts and Dockerfiles.
</Why>
<When>
Setting a known, complete permission.
</When>
<Where>
`chmod 600 ~/.ssh/id_ed25519`, `chmod 755 deploy.sh`.
</Where>
<How>
Add r=4, w=2, x=1 for each of owner, group, others.
</How>
</Explain>

```bash
touch f
for m in 777 755 750 700 644 640 600 400; do chmod "$m" f; printf '%s = %s\n' "$m" "$(stat -c %A f | cut -c2-)"; done
```

```text output
777 = rwxrwxrwx
755 = rwxr-xr-x
750 = rwxr-x---
700 = rwx------
644 = rw-r--r--
640 = rw-r-----
600 = rw-------
400 = r--------
```

<Callout type="analogy">
Think of the digits as a price list: **read costs 4, write costs 2, execute costs 1**. Owner wants read + write = 4 + 2 = **6**. Group wants read = **4**. Others want nothing = **0**. Total: `640`.
</Callout>

### 4. Permissions in action

<Explain>
<What>
What actually happens when a user without permission tries to read, write or run a file.
</What>
<Why>
Seeing the errors makes them easy to recognise on real servers.
</Why>
<When>
Debugging access problems.
</When>
<Where>
Any multi-user system, Docker volumes, web servers.
</Where>
<How>
Root ignores most permissions, so the test below uses a normal user (`demo`).
</How>
</Explain>

```bash
useradd -m demo 2>/dev/null
mkdir -p /srv/permtest && cd /srv/permtest
echo "secret=42" > secret.txt && chmod 600 secret.txt
printf '#!/bin/sh\necho "script ran"\n' > run.sh && chmod 644 run.sh

sudo -u demo cat secret.txt 2>&1 | sed 's/^cat: //'
sudo -u demo bash -c ./run.sh 2>&1 | sed "s/^.*: //"
chmod 755 run.sh && sudo -u demo bash -c ./run.sh
chmod 644 secret.txt && sudo -u demo cat secret.txt

cd / && rm -rf /srv/permtest && userdel -r demo 2>/dev/null
```

```text output
secret.txt: Permission denied
Permission denied
script ran
secret=42
```

### 5. Directories: r, w and x mean something else

<Explain>
<What>
On a directory, **r** = list names, **w** = create/delete/rename entries, **x** = enter it and access things inside.
</What>
<Why>
"I have read permission on the file but still get Permission denied" usually means a parent directory lacks `x`.
</Why>
<When>
Web roots, shared folders, home directories.
</When>
<Where>
Every directory on the path matters: to read `/var/www/shop/index.html`, you need `x` on `/var`, `/var/www`, `/var/www/shop`.
</Where>
<How>
`namei -l /full/path` shows permissions of every folder along the way.
</How>
</Explain>

```bash
namei -l /etc/hostname | tail -n +2
```

```text output
drwxr-xr-x root root /
drwxr-xr-x root root etc
-rw-r--r-- root root hostname
```

| Directory mode | Can list (`ls`) | Can enter / open files inside | Can create/delete files |
| --- | --- | --- | --- |
| `r-x` (5) | Yes | Yes | No |
| `--x` (1) | No | Yes, if you know the name | No |
| `r--` (4) | Names only | No | No |
| `rwx` (7) | Yes | Yes | Yes |

### 6. Changing owner and group: chown and chgrp

<Explain>
<What>
`chown` changes the owner (and optionally the group); `chgrp` changes only the group.
</What>
<Why>
Files must belong to the user that needs them — the app's service account, the web server, a deploy user.
</Why>
<When>
After copying files as root, after `git clone` with sudo, when setting up Docker volumes.
</When>
<Where>
Web roots, app folders, data folders.
</Where>
<How>
`chown user file`, `chown user:group file`, `chown -R user:group folder/` (recursive). Only root can give files away, so normally `sudo chown`.
</How>
</Explain>

```bash
groupadd -f webteam
useradd -M -s /usr/sbin/nologin webapp 2>/dev/null
mkdir -p site/css && touch site/index.html site/css/style.css
chown -R webapp:webteam site
find site -printf '%u:%g %p\n' | sort -k2
userdel webapp; groupdel webteam
```

```text output
webapp:webteam site
webapp:webteam site/css
webapp:webteam site/css/style.css
webapp:webteam site/index.html
```

### 7. Default permissions: umask

<Explain>
<What>
The **umask** removes permissions from every new file and directory.
</What>
<Why>
It decides whether new files are private or readable by everyone — important for logs, backups and generated secrets.
</Why>
<When>
Every file creation by shells, scripts and services.
</When>
<Where>
Shell (`umask`), systemd services (`UMask=0077`), scripts (`umask 077` at the top).
</Where>
<How>
Files start from 666, directories from 777, minus the umask. `022` → 644/755; `027` → 640/750; `077` → 600/700.
</How>
</Explain>

```bash
for m in 022 027 077; do
  ( umask $m; touch "f$m"; mkdir "d$m"; printf 'umask %s → file %s, dir %s\n' "$m" "$(stat -c %a "f$m")" "$(stat -c %a "d$m")" )
done
```

```text output
umask 022 → file 644, dir 755
umask 027 → file 640, dir 750
umask 077 → file 600, dir 700
```

### 8. Special bits: setuid, setgid, sticky

<Explain>
<What>
**setuid (4)**: a program runs as its **owner** (e.g. root). **setgid (2)**: runs as its group; on a directory, new files inherit the directory's group. **sticky (1)**: in a shared directory, only a file's owner can delete it.
</What>
<Why>
`passwd` needs setuid to update `/etc/shadow`; team folders need setgid; `/tmp` needs sticky. Misplaced setuid binaries are a top privilege-escalation path.
</Why>
<When>
Team shared folders, security audits.
</When>
<Where>
`/usr/bin/passwd`, `/usr/bin/sudo`, `/tmp`.
</Where>
<How>
A fourth digit in front: `chmod 2775 shared/`, `chmod 1777 /shared-tmp`. Shown as `s`/`t` in place of `x`.
</How>
</Explain>

```bash
groupadd -f team
mkdir -p shared && chgrp team shared && chmod 2775 shared
touch shared/new-file
stat -c '%A %G %n' shared shared/new-file
groupdel team 2>/dev/null; true
```

```text output
drwxrwsr-x team shared
-rw-r--r-- team shared/new-file
```

Because of the setgid `s`, the new file automatically belongs to group `team` — perfect for team project folders.

Finding setuid programs (an audit step):

```text
$ sudo find / -perm -4000 -type f 2>/dev/null
/usr/bin/passwd
/usr/bin/sudo
/usr/bin/su
...                     ← anything unexpected here deserves investigation
```

### 9. ACLs: permissions for specific extra users

<Explain>
<What>
**Access Control Lists** add permissions for additional named users or groups, beyond the single owner and group.
</What>
<Why>
Sometimes one extra user (a backup account, a CI user) needs read access without changing the owner or group.
</Why>
<When>
Rare, special cases.
</When>
<Where>
`setfacl`, `getfacl` (package `acl`). A `+` at the end of `ls -l` permissions means an ACL exists.
</Where>
<How>
`setfacl -m u:backup:r file`, `getfacl file`, `setfacl -b file` (remove all).
</How>
</Explain>

```text
$ setfacl -m u:backup:r-- /var/www/shop/.env
$ ls -l /var/www/shop/.env
-rw-r-----+ 1 shopapp shopapp 220 Nov 10 14:30 .env      ← the + means "has an ACL"
$ getfacl /var/www/shop/.env
user::rw-
user:backup:r--
group::r--
other::---
```

### 10. Recipes for real servers

<Explain>
<What>
Correct, safe permissions for the things you set up most often.
</What>
<Why>
Most permission problems come from guessing — or from "fixing" with `chmod 777`.
</Why>
<When>
Every deployment and server setup.
</When>
<Where>
SSH, web apps, secrets.
</Where>
<How>
Copy these patterns.
</How>
</Explain>

```text
# SSH (on your laptop and on servers)
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519 ~/.ssh/authorized_keys
chmod 644 ~/.ssh/id_ed25519.pub

# A web app run by the user "shopapp", served by nginx (group www-data)
sudo chown -R shopapp:www-data /var/www/shop
sudo find /var/www/shop -type d -exec chmod 750 {} +    # folders: owner rwx, group r-x
sudo find /var/www/shop -type f -exec chmod 640 {} +    # files:   owner rw,  group r
sudo chmod 600 /var/www/shop/.env                      # secrets: owner only
sudo chmod 770 /var/www/shop/storage                   # a folder the app must write to
```

Using `find -type d` / `-type f` separately avoids making every file executable (which `chmod -R 755` would do).

## Hands-on

```bash
mkdir -p ~/perm-lab && cd ~/perm-lab

# 1. numbers ↔ letters
touch a && chmod 750 a && echo "750 → $(stat -c %A a)"
chmod u=rw,g=r,o= a && echo "u=rw,g=r,o= → $(stat -c %a a)"

# 2. find dangerous permissions in a folder
touch ok.txt open.txt && chmod 644 ok.txt && chmod 666 open.txt
find . -type f -perm -o+w -printf 'world-writable: %p\n'

# 3. fix SSH-style permissions
mkdir -p dotssh && touch dotssh/id_key && chmod 755 dotssh && chmod 644 dotssh/id_key
chmod 700 dotssh && chmod 600 dotssh/id_key
stat -c '%a %n' dotssh dotssh/id_key

cd ~ && rm -rf ~/perm-lab
```

```text output
750 → -rwxr-x---
u=rw,g=r,o= → 640
world-writable: ./open.txt
700 dotssh
600 dotssh/id_key
```

## Real-world example

After deploying a Next.js static export behind Nginx, the site returns **403 Forbidden**.

```bash
sudo tail -n 5 /var/log/nginx/error.log
# open() "/home/deploy/site/index.html" failed (13: Permission denied)

namei -l /home/deploy/site/index.html
# drwxr-xr-x root   root   /
# drwxr-xr-x root   root   home
# drwxr-x--- deploy deploy deploy        ← www-data has no x here
# drwxr-xr-x deploy deploy site
# -rw-r--r-- deploy deploy index.html
```

`namei -l` shows every directory in the path. Nginx runs as `www-data`, which is "others" for `/home/deploy`, and others have no `x`. Wrong fixes: `chmod 777 /home/deploy`, or running Nginx as root. Right fixes:

- Deploy static files to `/var/www/site` owned by `deploy` with `755`/`644` permissions, or
- Grant only what is needed: `sudo setfacl -m u:www-data:x /home/deploy`.

## Common mistakes

- **`chmod -R 777`** as a fix for anything. It hides the real problem and lets any user (or compromised process) modify the files.
- **`chmod -R 755` on a whole tree**, making every file executable. Treat files and directories separately.
- **Running the app as root** to avoid permission errors.
- **Forgetting directory `x`** somewhere up the path (use `namei -l`).
- **`sudo` creating root-owned files** in your project (`sudo npm install`), which later break normal commands. Fix with `chown -R`.
- **Docker `COPY` without `--chown`**, so the non-root app user cannot write where it needs to.

## Security lens

<Callout type="security">
Permissions are the last line of defence once an attacker has a foothold. Check them the way an attacker would.
</Callout>

- **World-writable + run by root = root for everyone.** A cron script, systemd unit or script in root's `PATH` that others can edit is an instant privilege escalation. Find them with `find / -xdev -perm -0002 -type f`.
- **setuid binaries** run as root. Unusual ones (or `cp`, `find`, `vim`, `python` with setuid) are escalation paths. Keep a baseline list and alert on changes.
- **Secrets readable by others:** `.env`, `config/database.yml`, backups and private keys must be `600`/`640`. SSH refuses keys that are too open; your app will not.
- **Web roots:** the web server user should be able to *read* the site but not *write* it (except an upload directory, which must never execute code). Writable code directories turn file-upload bugs into remote code execution.
- **Containers:** run as a non-root UID; mount the root file system read-only (`readOnlyRootFilesystem: true` in Kubernetes) and give write access only to specific volumes.
- **Default umask** for services handling secrets should be `077`.

## Interview questions

<QA q="What does chmod 755 mean, and when would you use it?">
7 for the owner is read, write and execute; 5 for group and others is read and execute. It is the standard mode for directories and executable scripts: the owner can modify, everyone can read and run or enter, but only the owner can change it.
</QA>

<QA q="A web server returns 403 for a static file that exists. How do you debug it?">
Check the web server error log for "Permission denied", identify the user the server runs as (for example www-data), and inspect every directory in the path with `namei -l /full/path`. The user needs execute on every directory and read on the file. Fix ownership, group membership or an ACL — not chmod 777 or running the server as root. Also check SELinux/AppArmor where enabled.
</QA>

<QA q="What is the setuid bit and why is it a security risk?">
When set on an executable, the program runs with the privileges of the file's owner rather than the user who started it; passwd uses it to modify /etc/shadow as root. If a setuid-root program has a bug or can spawn a shell or write arbitrary files, any user can escalate to root, so setuid binaries should be minimal, audited and monitored.
</QA>

<QA q="What permissions should an SSH private key have, and why?">
600 (read and write for the owner only), inside a ~/.ssh directory with 700. The SSH client refuses to use private keys readable by other users, because anyone who can read the key can impersonate you.
</QA>

<QA q="What is umask?">
umask is a mask of permission bits removed from newly created files and directories. Files start from 666 and directories from 777; with umask 022 they become 644 and 755, and with 077 they become 600 and 700. It is set per process, for example in shell profiles or a systemd unit's UMask setting.
</QA>

## Key terms

<Terms>
  <Term name="Mode">A file's permission bits, such as 644 or -rw-r--r--.</Term>
  <Term name="chmod">Changes permission bits.</Term>
  <Term name="chown / chgrp">Changes a file's owner and/or group.</Term>
  <Term name="umask">Bits removed from default permissions of new files.</Term>
  <Term name="setuid / setgid">Special bits that run a program as its owner or group; setgid on directories passes the group to new files.</Term>
  <Term name="Sticky bit">On shared directories, only a file's owner may delete it.</Term>
  <Term name="ACL">Access control list granting permissions to extra users or groups.</Term>
  <Term name="namei">A tool that shows permissions along every component of a path.</Term>
</Terms>
