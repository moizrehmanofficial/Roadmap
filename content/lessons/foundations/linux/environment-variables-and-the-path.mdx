<Callout type="tip" title="In one minute">
An **environment variable** is a `NAME=value` setting that every process inherits from the process that started it: `HOME`, `USER`, `PATH`, `LANG`, and app settings like `NODE_ENV`, `PORT`, `DATABASE_URL`. See them with `env` or `printenv NAME`. Set one for a single command (`PORT=4000 node server.js`), for the session (`export PORT=4000`), or permanently (`~/.bashrc`, `/etc/environment`, systemd `EnvironmentFile=`). **PATH** is a colon-separated list of folders the shell searches when you type a command; `command -v name` shows which file will run. Apps read secrets from environment variables, so never commit `.env` files.
</Callout>

## Start from zero

### Settings that travel with every program

The same app code runs on your laptop, on staging and in production — but with different database addresses, ports and API keys. The code should not change; only the **settings around it** should. Environment variables are those settings.

<Callout type="analogy">
A **name badge and instruction card** given to every new worker when they start a shift: "Your floor: 3. Your manager: Emma. Emergency number: 1122." Each worker (process) gets a **copy** of the card from whoever sent them (the parent process), and passes a copy on to anyone they send out. Changing your own card later does not change the cards others already have.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Environment variable** | A `NAME=value` setting passed to processes | `NODE_ENV=production` |
| **Environment** | The full set of these a process has | shown by `env` |
| **Shell variable** | Exists only in the current shell, not passed on | `count=5` |
| **export** | Turns a shell variable into an environment variable | `export PORT=3000` |
| **PATH** | List of folders to search for commands | `/usr/local/bin:/usr/bin:/bin` |
| **`.bashrc` / `.profile`** | Files the shell runs at start-up | `~/.bashrc` |
| **`.env` file** | A file of `NAME=value` lines loaded by apps/tools | `DATABASE_URL=…` |

## What is it?

Every process has its own **environment** — a list of `NAME=value` strings. When a process starts another one, the child receives a **copy**. Programs read it to configure themselves:

| Variable | Meaning |
| --- | --- |
| `HOME` | Your home folder |
| `USER` | Your user name |
| `PATH` | Where to find commands |
| `SHELL` | Your login shell |
| `PWD` | Current folder |
| `LANG` | Language and encoding (e.g. `en_US.UTF-8`) |
| `TZ` | Time zone (e.g. `Asia/Tashkent`) |
| `EDITOR` | Default text editor |
| `NODE_ENV`, `PORT`, `DATABASE_URL` | Common app settings |

## Why does it matter?

- **Twelve-factor apps:** modern apps (Node.js, NestJS, Next.js, Django, FastAPI) read configuration from the environment. Docker, Kubernetes, CI systems and cloud platforms (Vercel, Heroku, ECS) all inject settings this way.
- **"Command not found"** errors are PATH problems.
- **Cron and systemd** start with a minimal environment — a classic reason scripts work by hand but fail there.
- **Security:** secrets in environment variables are convenient but can leak through logs, error pages, `/proc`, child processes and committed `.env` files.

## When and where do you use it?

| Need | How |
| --- | --- |
| Read a value | `echo "$HOME"`, `printenv PATH` |
| Set for one command | `NODE_ENV=production node server.js` |
| Set for this terminal session | `export AWS_PROFILE=dev` |
| Set permanently for you | add `export …` to `~/.bashrc` |
| Set for a service | systemd `Environment=` / `EnvironmentFile=` |
| Set in Docker | `docker run -e PORT=3000`, `env_file:` in compose |
| Set in CI | Repository secrets / variables |

## Concepts one by one

### 1. Reading environment variables

<Explain>
<What>
Showing the variables your shell (or any process) has.
</What>
<Why>
Debugging configuration: "is `NODE_ENV` really `production`?"
</Why>
<When>
Before running an app, while debugging, inside containers.
</When>
<Where>
Shell, `/proc/PID/environ` for other processes.
</Where>
<How>
`env` (all), `printenv NAME` (one), `echo "$NAME"`. Inside Node.js: `process.env.NAME`; Python: `os.environ["NAME"]`.
</How>
</Explain>

```bash
export APP_COLOR=blue
printenv APP_COLOR
echo "HOME is set: $([[ -n $HOME ]] && echo yes)"
env | grep -c '=' | awk '{print ($1 > 3 ? "env lists several variables" : "few variables")}'
node -e 'console.log("Node.js sees APP_COLOR =", process.env.APP_COLOR)'
python3 -c 'import os; print("Python sees APP_COLOR =", os.environ["APP_COLOR"])'
```

```text output
blue
HOME is set: yes
env lists several variables
Node.js sees APP_COLOR = blue
Python sees APP_COLOR = blue
```

### 2. Shell variables vs exported (environment) variables

<Explain>
<What>
A plain assignment (`name=value`) creates a **shell variable** visible only in this shell. `export` puts it into the environment so **child processes** receive it.
</What>
<Why>
"I set `PORT=4000` but my app still uses 3000" — because it was not exported.
</Why>
<When>
Whenever a program you start needs the value.
</When>
<Where>
Scripts and terminals.
</Where>
<How>
`export NAME=value`, or `export NAME` for an existing variable. `unset NAME` removes it.
</How>
</Explain>

```bash
PORT=4000
node -e 'console.log("without export, child sees PORT =", process.env.PORT)'
export PORT
node -e 'console.log("after export,  child sees PORT =", process.env.PORT)'
unset PORT
node -e 'console.log("after unset,   child sees PORT =", process.env.PORT)'
```

```text output
without export, child sees PORT = undefined
after export,  child sees PORT = 4000
after unset,   child sees PORT = undefined
```

### 3. Setting a variable for one command only

<Explain>
<What>
Writing `NAME=value command` sets the variable **only for that command**.
</What>
<Why>
Try a different setting without changing your session.
</Why>
<When>
Testing, one-off runs, scripts.
</When>
<Where>
`NODE_ENV=production npm run build`, `TZ=UTC date`, `DEBUG=* node app.js`.
</Where>
<How>
Put the assignments directly before the command, no `export`, no semicolon.
</How>
</Explain>

```bash
TZ=UTC date -d '2026-11-10 12:00 UTC' +'UTC:     %H:%M'
TZ=Asia/Tashkent date -d '2026-11-10 12:00 UTC' +'Tashkent: %H:%M'
GREETING=salaam bash -c 'echo "child got: $GREETING"'
echo "this shell has: [${GREETING:-}]"
```

```text output
UTC:     12:00
Tashkent: 17:00
child got: salaam
this shell has: []
```

### 4. Children get a copy — changes never flow back

<Explain>
<What>
A child process receives a **copy** of its parent's environment. Changing it in the child does not change the parent.
</What>
<Why>
Explains why `./set-env.sh` does not change your terminal's variables, while `source set-env.sh` does.
</Why>
<When>
Writing scripts that "set up" an environment.
</When>
<Where>
All processes.
</Where>
<How>
Use `source file` (or `. file`) to run a file in the current shell.
</How>
</Explain>

```bash
printf 'export STAGE=staging\n' > set-env.sh
bash set-env.sh;   echo "after running it:  STAGE=[${STAGE:-}]"
source set-env.sh; echo "after sourcing it: STAGE=[${STAGE:-}]"
```

```text output
after running it:  STAGE=[]
after sourcing it: STAGE=[staging]
```

### 5. Making variables permanent

<Explain>
<What>
Files the shell or system reads at start-up, where you can put `export` lines.
</What>
<Why>
`export` in a terminal is forgotten when the terminal closes.
</Why>
<When>
Personal settings (editor, PATH additions), system-wide settings.
</When>
<Where>
See the table. For **services**, do not rely on these files — use the service's own config (systemd, Docker).
</Where>
<How>
Add `export NAME=value` to the right file, then open a new terminal or `source ~/.bashrc`.
</How>
</Explain>

| File | Applies to | Use for |
| --- | --- | --- |
| `~/.bashrc` | Your interactive Bash shells | Aliases, prompt, PATH additions |
| `~/.profile` / `~/.bash_profile` | Your login shells (SSH logins) | Login-time variables |
| `/etc/environment` | All users (simple `NAME=value`, no `export`) | System-wide simple values |
| `/etc/profile.d/*.sh` | All users' login shells | System-wide scripts |
| systemd `Environment=` / `EnvironmentFile=` | One service | App configuration and secrets |

### 6. `.env` files

<Explain>
<What>
A file of `NAME=value` lines that tools load into the environment: Docker Compose, Next.js, Vite, `dotenv` in Node.js, systemd's `EnvironmentFile`.
</What>
<Why>
Keeps per-machine settings and secrets out of the code.
</Why>
<When>
Local development, simple deployments.
</When>
<Where>
Project root (`.env`, `.env.local`) — **always in `.gitignore`**. Commit a `.env.example` with fake values instead.
</Where>
<How>
In Bash: `set -a; source .env; set +a` exports every variable in the file.
</How>
</Explain>

```bash
cat > .env <<'EOF'
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://shop:secret@127.0.0.1:5432/shop
EOF
set -a; source .env; set +a
node -e 'const { NODE_ENV, PORT } = process.env; console.log(`app sees NODE_ENV=${NODE_ENV}, PORT=${PORT}`)'
printf '.env\n.env.*\n!.env.example\n' > .gitignore
cat .gitignore
```

```text output
app sees NODE_ENV=production, PORT=3000
.env
.env.*
!.env.example
```

`set -a` means "export every variable assigned from now on"; `set +a` turns it off again.

### 7. PATH — how the shell finds commands

<Explain>
<What>
`PATH` is a list of folders separated by `:`. When you type `node`, the shell looks in each folder, **left to right**, and runs the first `node` it finds.
</What>
<Why>
Explains "command not found", and why the wrong version of a tool runs (an old `node` earlier in PATH).
</Why>
<When>
Installing tools, using version managers (nvm, pyenv), debugging cron jobs.
</When>
<Where>
Every shell and every process (cron, systemd, Docker all have their own PATH).
</Where>
<How>
`echo "$PATH" | tr ':' '\n'` shows the folders. `command -v name` (or `which`) shows which file will run; `type -a name` shows all matches.
</How>
</Explain>

```bash
echo "$PATH" | tr ':' '\n' | grep -E '^/usr/(local/)?bin$' | sort -u
command -v ls
type -t cd
```

```text output
/usr/bin
/usr/local/bin
/usr/bin/ls
builtin
```

<Callout type="analogy">
PATH is a **list of shops to visit, in order**, when you ask for "bread". You go to the first shop; if it has bread, you buy it there and stop. If a dodgy shop is put at the **front** of the list, you will buy its bread — even if a better shop is further down.
</Callout>

### 8. Adding a folder to PATH

<Explain>
<What>
Putting a new folder (where your own scripts or a tool live) into PATH.
</What>
<Why>
So you can run `deploy` instead of `/home/alex/bin/deploy`.
</Why>
<When>
After installing tools by hand, or for your personal script folder.
</When>
<Where>
`~/.bashrc` for yourself; `/usr/local/bin` is already in PATH for system-wide tools.
</Where>
<How>
`export PATH="$HOME/bin:$PATH"` (front = takes priority) or `export PATH="$PATH:$HOME/bin"` (end = fallback). Never replace PATH entirely (`PATH=~/bin`) — every normal command would disappear.
</How>
</Explain>

```bash
mkdir -p ~/bin
printf '#!/usr/bin/env bash\necho "hello from my own tool"\n' > ~/bin/hello-tool
chmod +x ~/bin/hello-tool
hello-tool 2>&1 | sed 's/.*: //'
export PATH="$HOME/bin:$PATH"
hello-tool
command -v hello-tool | sed "s|$HOME|~|"
```

```text output
command not found
hello from my own tool
~/bin/hello-tool
```

### 9. The minimal environment of cron and systemd

<Explain>
<What>
Services and cron jobs do **not** read your `~/.bashrc`. They start with a small, fixed environment and a short PATH.
</What>
<Why>
The number-one reason scripts "work in my terminal but not in cron".
</Why>
<When>
Writing cron jobs, systemd services, CI steps.
</When>
<Where>
cron (`PATH=/usr/bin:/bin` by default), systemd (a minimal environment), Docker (`ENV` in the image).
</Where>
<How>
Use absolute paths, set PATH at the top of scripts, and pass variables explicitly (`Environment=` in systemd, `-e` in Docker).
</How>
</Explain>

```bash
export MY_SETTING=from-my-terminal
env -i /bin/bash -c 'echo "minimal env: MY_SETTING=[${MY_SETTING:-}], number of variables: $(env | wc -l)"' | sed -E 's/variables: [0-9]+/variables: very few/'
```

```text output
minimal env: MY_SETTING=[], number of variables: very few
```

### 10. Secrets in environment variables

<Explain>
<What>
API keys, database passwords and tokens are commonly passed as environment variables.
</What>
<Why>
Better than hard-coding them — but environment variables leak in surprising ways.
</Why>
<When>
Every app that uses secrets.
</When>
<Where>
Process listings, `/proc/PID/environ` (readable by the same user and root), crash reports, debug pages, logs that print `process.env`, child processes, front-end builds.
</Where>
<How>
Restrict `.env` files to mode `600`, never log the environment, never commit `.env`, use a secrets manager in production (AWS Secrets Manager, Vault, Kubernetes Secrets), and remember that **front-end** variables (`NEXT_PUBLIC_*`, `VITE_*`) are shipped to every visitor's browser.
</How>
</Explain>

```bash
export API_KEY=sk-live-123456
bash -c 'sleep 30' & pid=$!
sleep 0.3
tr '\0' '\n' < /proc/$pid/environ | grep -c '^API_KEY=' | sed 's/^1$/the child process received API_KEY — anyone who can read its \/proc entry can see it/'
kill $pid
```

```text output
the child process received API_KEY — anyone who can read its /proc entry can see it
```

## Hands-on

```bash
# 1. Inspect
echo "user=$(id -un | sed 's/.*/<you>/') shell-is-bash=$([[ $BASH ]] && echo yes)"
printenv | cut -d= -f1 | grep -qx PATH && echo "PATH is in the environment"

# 2. One-command vs exported
X=1 bash -c 'echo "one-command: X=$X"'; echo "after: X=[${X:-}]"
export Y=2; bash -c 'echo "exported: Y=$Y"'

# 3. PATH order decides which command runs
mkdir -p fakebin && printf '#!/bin/sh\necho "fake ls!"\n' > fakebin/ls && chmod +x fakebin/ls
PATH="$PWD/fakebin:$PATH" ls
PATH="$PATH:$PWD/fakebin" ls fakebin
```

```text output
user=<you> shell-is-bash=yes
PATH is in the environment
one-command: X=1
after: X=[]
exported: Y=2
fake ls!
ls
```

Step 3 is also a **security lesson**: whoever controls a folder early in your PATH controls what your commands really run. Never put `.` or world-writable folders in PATH.

## Real-world example

A team deploys a Next.js + NestJS app to three environments. Configuration is handled like this:

| Value | Development | Staging | Production | Where it lives |
| --- | --- | --- | --- | --- |
| `DATABASE_URL` | local Docker Postgres | staging RDS | production RDS | `.env` (dev) / AWS Secrets Manager → ECS task |
| `JWT_SECRET` | random dev value | secret | secret | Secrets Manager |
| `NEXT_PUBLIC_API_URL` | `http://localhost:4000` | staging URL | `https://api.example.com` | Vercel project settings (public, fine) |
| `LOG_LEVEL` | `debug` | `info` | `info` | Task definition (not secret) |
| `STRIPE_SECRET_KEY` | test key | test key | live key | Secrets Manager, server only |

The NestJS app validates every variable at startup with a schema and refuses to boot if something is missing — so a bad deploy fails in seconds in CI instead of at 2 a.m. in production. A pre-commit hook and CI step run **gitleaks** to stop `.env` files and keys from being committed.

## Common mistakes

- **Committing `.env`** to Git (even once — it stays in history). Rotate the secrets if it happens.
- **Putting secrets in `NEXT_PUBLIC_`/`VITE_` variables** — they are public.
- **`ENV SECRET=...` or `COPY .env` in a Dockerfile** — secrets baked into image layers forever.
- **Treating `"false"` as false** — environment values are strings.
- **Editing `~/.bashrc` and expecting a running service to see it** — services get their environment from systemd/Docker/Kubernetes, not your shell.
- **Forgetting to restart** the app or open a new terminal after changing variables.
- **Breaking `PATH`** with `export PATH=/my/dir` (forgot `:$PATH`) — suddenly no command works. Fix with full paths: `/usr/bin/vim ~/.bashrc`.

## Security lens

<Callout type="security">
Environment variables are the most common place secrets live — and one of the most common ways they leak.
</Callout>

- **Where env secrets leak:** Git history, CI logs (`echo $TOKEN`, `set -x`), error pages and debug endpoints that dump `process.env`, crash reports and APM tools, `docker inspect`, image layers, `/proc/PID/environ` (readable by the same user and root), child processes that inherit everything.
- **Prefer a secrets manager** (AWS Secrets Manager, SSM Parameter Store, Vault, Kubernetes Secrets with encryption) and short-lived credentials (IAM roles, OIDC from CI) over long-lived keys in variables.
- **Mask secrets in CI** and never print them; GitHub Actions masks `secrets.*` but not values you derive from them.
- **PATH hijacking:** if a writable directory (like `.` or `/tmp`) appears in `PATH` before system directories, an attacker can drop a fake `ls` or `sudo` there. Never put `.` in `PATH`; scripts run by root should use absolute paths or set a safe `PATH`.
- **Library injection:** variables like `LD_PRELOAD` and `NODE_OPTIONS=--require ...` can load attacker code into a process. That is why sudo and setuid programs strip them.
- **Scan for leaks** with gitleaks or trufflehog in pre-commit hooks and CI (covered in DevSecOps → Code Security).

## Interview questions

<QA q="What is the difference between a shell variable and an environment variable?">
A shell variable exists only in the current shell. An environment variable has been exported, so it is copied into the environment of every child process the shell starts. Programs read environment variables (for example process.env in Node.js), not shell variables.
</QA>

<QA q="Why does a variable I exported in a script not exist in my terminal afterwards?">
Running a script starts a child process with a copy of the environment; changes made in the child disappear when it exits and never flow back to the parent. To apply a script's exports to the current shell, source it (`source script.sh` or `. script.sh`).
</QA>

<QA q="How does the shell find a command, and how do you fix 'command not found'?">
Unless the command is an alias, function or builtin, the shell searches each directory listed in PATH, in order, and runs the first matching executable. To fix 'command not found', locate the binary, then add its directory to PATH in ~/.profile or ~/.bashrc, reload the shell, and confirm with command -v. Also remember that sudo uses its own secure_path.
</QA>

<QA q="Are environment variables a safe place for secrets?">
They are better than hard-coding secrets in source code, and they are standard for twelve-factor apps, but they leak easily: through logs, debug output, child processes, /proc, docker inspect, image layers and committed .env files. For production, inject them at runtime from a secrets manager, restrict who can read them, avoid printing them, rotate them, and prefer short-lived credentials such as IAM roles where possible.
</QA>

<QA q="What happens to NEXT_PUBLIC_ variables in a Next.js app?">
They are inlined into the client-side JavaScript at build time, so their values are visible to anyone who loads the site. They must only contain public configuration such as a public API URL or a publishable key. Server-only secrets must use variables without the prefix and be used only in server code.
</QA>

## Key terms

<Terms>
  <Term name="Environment variable">A NAME=value pair passed from a process to its children.</Term>
  <Term name="export">Shell builtin that adds a variable to the environment.</Term>
  <Term name="PATH">Colon-separated list of directories searched for commands.</Term>
