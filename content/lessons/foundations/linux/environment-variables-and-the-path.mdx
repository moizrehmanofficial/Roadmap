<BigIdea>
<Tr>
<En>
The same code runs on your laptop, on staging and in production, but with different databases, ports and keys. The code doesn't change; only the **settings around it** do. Those settings are **environment variables**. And one special variable, **PATH**, tells the shell where to find every command you type.
</En>
<Ur>
Wahi code aap ke laptop, staging aur production par chalta hai, lekin alag databases, ports aur keys ke saath. Code nahi badalta; sirf **us ke gird ki settings** badalti hain. Wahi settings **environment variables** hain. Aur ek khaas variable, **PATH**, shell ko batata hai ke aap ki likhi har command kahan dhoondni hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- An **environment variable** is a `NAME=value` setting, like `NODE_ENV=production` or `PORT=3000`.
- Every program gets a **copy** of these settings from the program that started it.
- **PATH** is a list of folders, separated by `:`, where the shell looks for commands.

</En>
<Ur>

- **Environment variable** `NAME=value` setting hai, jaise `NODE_ENV=production` ya `PORT=3000`.
- Har program ko ye settings us program se **copy** me milti hain jis ne use shuru kiya.
- **PATH** folders ki list hai, `:` se alag, jahan shell commands dhoondta hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- Modern apps (Node.js, Next.js, NestJS, Django) read their settings from the environment. Docker, CI and cloud platforms all set them this way.
- **"Command not found"** is almost always a PATH problem.
- Scripts that "work in my terminal but fail in cron" usually miss a variable.
- Secrets in variables can **leak** if you're not careful.

</En>
<Ur>

- Jadeed apps (Node.js, Next.js, NestJS, Django) apni settings environment se parhti hain. Docker, CI aur cloud platforms sab isi tarah set karte hain.
- **"Command not found"** taqreeban hamesha PATH ka masla hai.
- Jo scripts "mere terminal me chalti hain lekin cron me fail" hoti hain, un me aam taur par koi variable gum hota hai.
- Variables me rakhe secrets ehtiyat na ho to **leak** ho sakte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- configuring an app for dev, staging and production
- installing a tool and getting "command not found"
- writing a `.env` file
- setting up a service, a Docker container or CI

</En>
<Ur>

- app ko dev, staging aur production ke liye set karte waqt
- tool install kar ke "command not found" milne par
- `.env` file likhte waqt
- service, Docker container ya CI tayyar karte waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

- Read: `echo "$HOME"`, `printenv PORT`
- One command only: `PORT=4000 node server.js`
- This terminal: `export PORT=4000`
- Forever (for you): add `export ...` to `~/.bashrc`
- Which program runs? `command -v node`

</En>
<Ur>

- Parhna: `echo "$HOME"`, `printenv PORT`
- Sirf ek command: `PORT=4000 node server.js`
- Is terminal ke liye: `export PORT=4000`
- Hamesha (aap ke liye): `~/.bashrc` me `export ...` likhein
- Kaun sa program chalega? `command -v node`

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Every new worker starting a shift gets an **instruction card**: "Your floor: 3. Your manager: Emma. Emergency number: 911."

- Each worker (process) gets a **copy** of the card from whoever sent them (the parent process).
- They pass a copy on to anyone **they** send out.
- Changing your own card later **doesn't** change the cards others already have.

</En>
<Ur>

Shift shuru karne wale har naye mazdoor ko ek **hidayat card** milta hai: "Aap ki manzil: 3. Aap ki manager: Emma. Emergency number: 911."

- Har mazdoor (process) ko card ki **copy** us se milti hai jis ne use bheja (parent process).
- Wo aage jise **khud** bhejta hai use bhi copy deta hai.
- Baad me apna card badalne se doosron ke paas mojood cards **nahi** badalte.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Reading variables (from the shell, Node.js and Python)">

<Tr>
<En>

`env` shows all variables; `printenv NAME` or `echo "$NAME"` shows one. Inside your code: `process.env.NAME` in Node.js, `os.environ["NAME"]` in Python.

</En>
<Ur>

`env` saare variables dikhata hai; `printenv NAAM` ya `echo "$NAAM"` ek. Code ke andar: Node.js me `process.env.NAAM`, Python me `os.environ["NAAM"]`.

</Ur>
</Tr>

```bash
export APP_COLOR=blue
printenv APP_COLOR
echo "HOME is set: $([[ -n $HOME ]] && echo yes)"
env | grep -c '=' | awk '{print ($1 > 3 ? "env lists several variables" : "few variables")}'
node -e 'console.log("Node.js sees APP_COLOR =", process.env.APP_COLOR)'
python3 -c 'import os; print("Python sees APP_COLOR =", os.environ["APP_COLOR"])'
```

```text output
blue
HOME is set: yes
env lists several variables
Node.js sees APP_COLOR = blue
Python sees APP_COLOR = blue
```

<Happened>
<Tr>
<En>We set `APP_COLOR=blue` once in the shell. Both Node.js and Python, started from that shell, received a copy and could read it.</En>
<Ur>Hum ne shell me ek dafa `APP_COLOR=blue` set kiya. Us shell se shuru hone wale Node.js aur Python dono ko copy mili aur dono ne parh liya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Why export matters">

<Tr>
<En>

`PORT=4000` on its own creates a **shell variable**: only this shell knows it. **`export`** puts it into the environment so programs you start **receive** it. This explains the classic "I set `PORT=4000` but my app still uses 3000".

</En>
<Ur>

Akela `PORT=4000` **shell variable** banata hai: sirf ye shell jaanta hai. **`export`** ise environment me daalta hai taa ke aap ke shuru kiye programs ko **mile**. Isi se wo mashhoor masla samajh aata hai: "main ne `PORT=4000` set kiya lekin app abhi bhi 3000 istemal kar rahi hai".

</Ur>
</Tr>

```bash
PORT=4000
node -e 'console.log("without export, child sees PORT =", process.env.PORT)'
export PORT
node -e 'console.log("after export,  child sees PORT =", process.env.PORT)'
unset PORT
node -e 'console.log("after unset,   child sees PORT =", process.env.PORT)'
```

```text output
without export, child sees PORT = undefined
after export,  child sees PORT = 4000
after unset,   child sees PORT = undefined
```

</Step>

<Step title="A variable for one command only">

<Tr>
<En>

Write `NAME=value command` and the variable exists **only for that one command**. Great for quick tests: `NODE_ENV=production npm run build`, `TZ=UTC date`.

</En>
<Ur>

`NAAM=value command` likhein aur variable **sirf us ek command ke liye** hota hai. Jaldi ke tests ke liye behtareen: `NODE_ENV=production npm run build`, `TZ=UTC date`.

</Ur>
</Tr>

```bash
TZ=UTC date -d '2026-11-10 12:00 UTC' +'UTC:     %H:%M'
TZ=Asia/Tashkent date -d '2026-11-10 12:00 UTC' +'Tashkent: %H:%M'
GREETING=hello bash -c 'echo "child got: $GREETING"'
echo "this shell has: [${GREETING:-}]"
```

```text output
UTC:     12:00
Tashkent: 17:00
child got: hello
this shell has: []
```

<Happened>
<Tr>
<En>

- The same moment shows as 12:00 with `TZ=UTC` and 17:00 with `TZ=Asia/Tashkent`.
- The child got `GREETING=hello`, but our own shell still has nothing: the variable lived only for that one command.

</En>
<Ur>

- Ek hi lamha `TZ=UTC` ke saath 12:00 aur `TZ=Asia/Tashkent` ke saath 17:00 dikhta hai.
- Bache ko `GREETING=hello` mila, lekin hamare apne shell me ab bhi kuch nahi: variable sirf us ek command ke liye tha.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Copies never flow back: run vs source">

<Tr>
<En>

A child gets a **copy**. Changes in the child **never flow back** to the parent. That's why running `./set-env.sh` doesn't change your terminal, but `source set-env.sh` does (it runs the file **inside** your current shell).

</En>
<Ur>

Bache ko **copy** milti hai. Bache me tabdeeliyan parent tak **kabhi wapas nahi** jatin. Isi liye `./set-env.sh` chalana aap ka terminal nahi badalta, lekin `source set-env.sh` badal deta hai (ye file ko aap ke mojooda shell ke **andar** chalata hai).

</Ur>
</Tr>

```bash
printf 'export STAGE=staging\n' > set-env.sh
bash set-env.sh;   echo "after running it:  STAGE=[${STAGE:-}]"
source set-env.sh; echo "after sourcing it: STAGE=[${STAGE:-}]"
```

```text output
after running it:  STAGE=[]
after sourcing it: STAGE=[staging]
```

</Step>

<Step title="Making variables permanent">

<Tr>
<En>

`export` in a terminal is forgotten when you close it. To keep it, put the `export` line in a start-up file, then open a new terminal or run `source ~/.bashrc`.

**Services don't read these files.** For a service, use its own settings (systemd `EnvironmentFile=`, Docker `-e`).

</En>
<Ur>

Terminal me `export` band karte hi bhool jata hai. Rakhne ke liye `export` line kisi start-up file me likhein, phir naya terminal kholein ya `source ~/.bashrc` chalayen.

**Services ye files nahi parhtin.** Service ke liye us ki apni settings istemal karein (systemd `EnvironmentFile=`, Docker `-e`).

</Ur>
</Tr>

| File | Applies to | Use for |
| --- | --- | --- |
| `~/.bashrc` | Your interactive Bash shells | Aliases, prompt, PATH additions |
| `~/.profile` / `~/.bash_profile` | Your login shells (SSH logins) | Login-time variables |
| `/etc/environment` | All users (simple `NAME=value`, no `export`) | System-wide simple values |
| `/etc/profile.d/*.sh` | All users' login shells | System-wide scripts |
| systemd `Environment=` / `EnvironmentFile=` | One service | App configuration and secrets |

</Step>

<Step title=".env files">

<Tr>
<En>

A `.env` file is a list of `NAME=value` lines. Docker Compose, Next.js, Vite and `dotenv` load it automatically. Two rules:

- **Always** put `.env` in `.gitignore`.
- Commit a `.env.example` with **fake** values so teammates know what's needed.

In Bash, `set -a; source .env; set +a` exports every variable in the file.

</En>
<Ur>

`.env` file `NAME=value` lines ki list hai. Docker Compose, Next.js, Vite aur `dotenv` ise khud load karte hain. Do qaide:

- `.env` ko **hamesha** `.gitignore` me rakhein.
- **Jaali** values wali `.env.example` commit karein taa ke saathiyon ko pata ho kya chahiye.

Bash me `set -a; source .env; set +a` file ke har variable ko export kar deta hai.

</Ur>
</Tr>

```bash
cat > .env <<'EOF'
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://shop:secret@127.0.0.1:5432/shop
EOF
set -a; source .env; set +a
node -e 'const { NODE_ENV, PORT } = process.env; console.log(`app sees NODE_ENV=${NODE_ENV}, PORT=${PORT}`)'
printf '.env\n.env.*\n!.env.example\n' > .gitignore
cat .gitignore
```

```text output
app sees NODE_ENV=production, PORT=3000
.env
.env.*
!.env.example
```

<Happened>
<Tr>
<En>

- `set -a` = "export everything assigned from now on"; `set +a` turns it off. So all three lines became environment variables, and Node.js read them.
- The `.gitignore` hides `.env` and `.env.anything`, but the `!` **allows** `.env.example` to be committed.

</En>
<Ur>

- `set -a` = "ab se jo bhi assign ho sab export karo"; `set +a` band karta hai. Isliye teeno lines environment variables ban gayin, aur Node.js ne parh lin.
- `.gitignore` `.env` aur `.env.kuchbhi` chhupata hai, lekin `!` `.env.example` ko commit hone ki **ijazat** deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="PATH: how the shell finds commands">

<Tr>
<En>

When you type `node`, the shell looks in each folder in `PATH`, **left to right**, and runs the **first** `node` it finds.

Think of PATH as a **list of shops to visit, in order**, when you want bread. You buy from the first shop that has it. If a dodgy shop is put at the **front** of the list, you'll buy its bread, even if a better shop is further down.

- `echo "$PATH" | tr ':' '\n'`: see the folders
- `command -v name`: which file will run
- `type -a name`: every match

</En>
<Ur>

Jab aap `node` likhte hain, shell `PATH` ke har folder me **baayen se daayen** dekhta hai, aur jo **pehla** `node` mile use chalata hai.

PATH ko **dukanon ki list** samjhein jahan roti lene **tarteeb se** jana hai. Jis pehli dukaan me mile wahan se khareed lete hain. Agar koi mashkook dukaan list ke **shuru** me rakh di jaye, to aap usi ki roti khareedenge, chahe behtar dukaan aage ho.

- `echo "$PATH" | tr ':' '\n'`: folders dekho
- `command -v naam`: kaun si file chalegi
- `type -a naam`: saare milne wale

</Ur>
</Tr>

```bash
echo "$PATH" | tr ':' '\n' | grep -E '^/usr/(local/)?bin$' | sort -u
command -v ls
type -t cd
```

```text output
/usr/bin
/usr/local/bin
/usr/bin/ls
builtin
```

<Happened>
<Tr>
<En>`/usr/bin` and `/usr/local/bin` are in PATH. Typing `ls` runs `/usr/bin/ls`. `cd` is a **builtin**: part of the shell itself, so PATH isn't searched for it.</En>
<Ur>`/usr/bin` aur `/usr/local/bin` PATH me hain. `ls` likhne se `/usr/bin/ls` chalta hai. `cd` **builtin** hai: shell ka apna hissa, isliye us ke liye PATH nahi dhoonda jata.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Add your own folder to PATH">

<Tr>
<En>

To run `deploy` instead of `/home/alex/bin/deploy`, add its folder to PATH:

- `export PATH="$HOME/bin:$PATH"`: at the **front** (takes priority)
- `export PATH="$PATH:$HOME/bin"`: at the **end** (fallback)

**Never** replace PATH completely (`PATH=~/bin`): every normal command would disappear.

</En>
<Ur>

`/home/alex/bin/deploy` ki jagah `deploy` chalane ke liye us ka folder PATH me shamil karein:

- `export PATH="$HOME/bin:$PATH"`: **shuru** me (tarjeeh milti hai)
- `export PATH="$PATH:$HOME/bin"`: **aakhir** me (baad ka sahara)

PATH ko **kabhi** poora na badlein (`PATH=~/bin`): har aam command ghayab ho jayegi.

</Ur>
</Tr>

```bash
mkdir -p ~/bin
printf '#!/usr/bin/env bash\necho "hello from my own tool"\n' > ~/bin/hello-tool
chmod +x ~/bin/hello-tool
hello-tool 2>&1 | sed 's/.*: //'
export PATH="$HOME/bin:$PATH"
hello-tool
command -v hello-tool | sed "s|$HOME|~|"
```

```text output
command not found
hello from my own tool
~/bin/hello-tool
```

<Happened>
<Tr>
<En>Before adding `~/bin` to PATH, the shell couldn't find `hello-tool`. After adding it, the same command works from anywhere.</En>
<Ur>`~/bin` ko PATH me shamil karne se pehle shell `hello-tool` dhoond nahi saka. Shamil karne ke baad wahi command kahin se bhi chalti hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Cron and services start almost empty">

<Tr>
<En>

Cron jobs and systemd services **don't** read your `~/.bashrc`. They start with a tiny environment and a short PATH. This is the #1 reason a script "works in my terminal but not in cron".

Fix: use **full paths**, set `PATH` at the top of the script, and pass variables **explicitly** (`Environment=` in systemd, `-e` in Docker).

</En>
<Ur>

Cron jobs aur systemd services aap ka `~/.bashrc` **nahi** parhte. Wo bohot chhote environment aur chhote PATH se shuru hote hain. Script ke "mere terminal me chalti hai lekin cron me nahi" ki ye sab se bari wajah hai.

Hal: **poore paths** istemal karein, script ke shuru me `PATH` set karein, aur variables **khud** dein (systemd me `Environment=`, Docker me `-e`).

</Ur>
</Tr>

```bash
export MY_SETTING=from-my-terminal
env -i /bin/bash -c 'echo "minimal env: MY_SETTING=[${MY_SETTING:-}], number of variables: $(env | wc -l)"' | sed -E 's/variables: [0-9]+/variables: very few/'
```

```text output
minimal env: MY_SETTING=[], number of variables: very few
```

<Happened>
<Tr>
<En>`env -i` starts a program with an **empty** environment, like cron does. Our `MY_SETTING` is gone, and only a handful of variables exist.</En>
<Ur>`env -i` program ko **khaali** environment ke saath shuru karta hai, jaise cron karta hai. Hamara `MY_SETTING` ghayab hai, aur sirf chand variables mojood hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Secrets in variables can leak">

<Tr>
<En>

API keys and passwords often live in environment variables. That's better than writing them in code, but they **leak** in surprising ways: every child process gets them, and anyone who can read `/proc/PID/environ` (the same user, or root) can see them.

</En>
<Ur>

API keys aur passwords aksar environment variables me rehte hain. Ye code me likhne se behtar hai, lekin ye hairat angez tareeqon se **leak** hote hain: har bache process ko milte hain, aur jo bhi `/proc/PID/environ` parh sake (wahi user, ya root) wo dekh sakta hai.

</Ur>
</Tr>

```bash
export API_KEY=sk-live-123456
bash -c 'sleep 30' & pid=$!
sleep 0.3
tr '\0' '\n' < /proc/$pid/environ | grep -c '^API_KEY=' | sed 's/^1$/the child process received API_KEY — anyone who can read its \/proc entry can see it/'
kill $pid
```

```text output
the child process received API_KEY — anyone who can read its /proc entry can see it
```

<Tr>
<En>

So: `.env` files get mode `600`, never print or log `process.env`, never commit `.env`, use a **secrets manager** in production, and remember that front-end variables (`NEXT_PUBLIC_*`, `VITE_*`) are shipped to **every visitor's browser**.

</En>
<Ur>

To: `.env` files ka mode `600` rakhein, kabhi `process.env` print ya log na karein, kabhi `.env` commit na karein, production me **secrets manager** istemal karein, aur yaad rakhein ke front-end variables (`NEXT_PUBLIC_*`, `VITE_*`) **har visitor ke browser** tak jate hain.

</Ur>
</Tr>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Breaking PATH">

```text
export PATH=/home/alex/bin      # forgot :$PATH, now ls, git, node... all "not found"
```

</Bad>
<Good title="Add, don't replace">

```text
export PATH="$HOME/bin:$PATH"
```

<Tr>
<En>If you already broke it, fix it with full paths: `/usr/bin/nano ~/.bashrc`.</En>
<Ur>Agar pehle hi tor diya, to poore paths se theek karein: `/usr/bin/nano ~/.bashrc`.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Secrets in public variables">

```text
NEXT_PUBLIC_STRIPE_SECRET_KEY=sk_live_...
```

<Tr>
<En>Anything with `NEXT_PUBLIC_` or `VITE_` ends up in the browser, readable by everyone.</En>
<Ur>`NEXT_PUBLIC_` ya `VITE_` wali har cheez browser me pohanchti hai, har koi parh sakta hai.</Ur>
</Tr>

</Bad>
<Good title="Server-only names">

```text
STRIPE_SECRET_KEY=sk_live_...          # used only in server code
NEXT_PUBLIC_API_URL=https://api.example.com
```

</Good>
</Compare>

<Compare>
<Bad title="Treating 'false' as false">

```javascript
if (process.env.DEBUG) enableDebug();   // DEBUG=false → the string "false" is truthy!
```

</Bad>
<Good title="Compare the text">

```javascript
if (process.env.DEBUG === "true") enableDebug();
```

</Good>
</Compare>

## Try it yourself

<Challenge title="Variables and PATH lab">

<Tr>
<En>
Run this lab. Part 3 shows something important: a fake `ls` placed **first** in PATH wins.
</En>
<Ur>
Ye lab chalayen. Hissa 3 ek ahem cheez dikhata hai: PATH me **pehle** rakha jaali `ls` jeet jata hai.
</Ur>
</Tr>

```bash
# 1. Inspect
echo "user=$(id -un | sed 's/.*/<you>/') shell-is-bash=$([[ $BASH ]] && echo yes)"
printenv | cut -d= -f1 | grep -qx PATH && echo "PATH is in the environment"

# 2. One-command vs exported
X=1 bash -c 'echo "one-command: X=$X"'; echo "after: X=[${X:-}]"
export Y=2; bash -c 'echo "exported: Y=$Y"'

# 3. PATH order decides which command runs
mkdir -p fakebin && printf '#!/bin/sh\necho "fake ls!"\n' > fakebin/ls && chmod +x fakebin/ls
PATH="$PWD/fakebin:$PATH" ls
PATH="$PATH:$PWD/fakebin" ls fakebin
```

```text output
user=<you> shell-is-bash=yes
PATH is in the environment
one-command: X=1
after: X=[]
exported: Y=2
fake ls!
ls
```

<Hint>
<Tr>
<En>With `fakebin` at the **front**, our fake `ls` ran. At the **end**, the real `ls` ran (and listed the folder). Whoever controls a folder early in your PATH controls what your commands really run, so never put `.` or world-writable folders in PATH.</En>

<DeepDive title="Where to set what">

| Need | How |
| --- | --- |
| Read a value | `echo "$HOME"`, `printenv PATH` |
| Set for one command | `NODE_ENV=production node server.js` |
| Set for this terminal session | `export AWS_PROFILE=dev` |
| Set permanently for you | add `export …` to `~/.bashrc` |
| Set for a service | systemd `Environment=` / `EnvironmentFile=` |
| Set in Docker | `docker run -e PORT=3000`, `env_file:` in compose |
| Set in CI | Repository secrets / variables |

More mistakes: `ENV SECRET=...` or `COPY .env` in a Dockerfile bakes secrets into image layers forever; editing `~/.bashrc` and expecting a running service to see it; and forgetting to restart the app or open a new terminal after a change.

</DeepDive>

<DeepDive title="Real world: three environments, one codebase">

| Value | Development | Staging | Production | Where it lives |
| --- | --- | --- | --- | --- |
| `DATABASE_URL` | local Docker Postgres | staging RDS | production RDS | `.env` (dev) / AWS Secrets Manager → ECS task |
| `JWT_SECRET` | random dev value | secret | secret | Secrets Manager |
| `NEXT_PUBLIC_API_URL` | `http://localhost:4000` | staging URL | `https://api.example.com` | Vercel project settings (public, fine) |
| `LOG_LEVEL` | `debug` | `info` | `info` | Task definition (not secret) |
| `STRIPE_SECRET_KEY` | test key | test key | live key | Secrets Manager, server only |

The NestJS app checks every variable at startup with a schema and refuses to boot if something is missing, so a bad deploy fails in seconds in CI instead of at 2 a.m. in production. A pre-commit hook and a CI step run **gitleaks** to stop `.env` files and keys from being committed.

</DeepDive>

<DeepDive title="Security lens">

Environment variables are the most common place secrets live, and one of the most common ways they leak.

- **Where they leak:** Git history, CI logs (`echo $TOKEN`, `set -x`), error pages and debug endpoints that dump `process.env`, crash reports and APM tools, `docker inspect`, image layers, `/proc/PID/environ`, and child processes that inherit everything.
- **Prefer a secrets manager** (AWS Secrets Manager, SSM Parameter Store, Vault, Kubernetes Secrets with encryption) and short-lived credentials (IAM roles, OIDC from CI) over long-lived keys.
- **Mask secrets in CI** and never print them; GitHub Actions masks `secrets.*` but not values you derive from them.
- **PATH hijacking:** if a writable folder (like `.` or `/tmp`) appears in `PATH` before system folders, an attacker can drop a fake `ls` or `sudo` there. Scripts run by root should use full paths or set a safe `PATH`.
- **Library injection:** variables like `LD_PRELOAD` and `NODE_OPTIONS=--require ...` can load attacker code into a process. That's why sudo and setuid programs strip them.
- **Scan for leaks** with gitleaks or trufflehog in pre-commit hooks and CI (covered in DevSecOps → Code Security). If a `.env` was ever committed, **rotate** every secret in it: it stays in Git history.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a shell variable and an environment variable?">
A shell variable exists only in the current shell. An environment variable has been exported, so it is copied into the environment of every child process the shell starts. Programs read environment variables (for example process.env in Node.js), not shell variables.
</QA>

<QA q="Why does a variable I exported in a script not exist in my terminal afterwards?">
Running a script starts a child process with a copy of the environment; changes made in the child disappear when it exits and never flow back to the parent. To apply a script's exports to the current shell, source it (`source script.sh` or `. script.sh`).
</QA>

<QA q="How does the shell find a command, and how do you fix 'command not found'?">
Unless the command is an alias, function or builtin, the shell searches each directory listed in PATH, in order, and runs the first matching executable. To fix 'command not found', locate the binary, then add its directory to PATH in ~/.profile or ~/.bashrc, reload the shell, and confirm with command -v. Also remember that sudo uses its own secure_path.
</QA>

<QA q="Are environment variables a safe place for secrets?">
They are better than hard-coding secrets in source code, and they are standard for twelve-factor apps, but they leak easily: through logs, debug output, child processes, /proc, docker inspect, image layers and committed .env files. For production, inject them at runtime from a secrets manager, restrict who can read them, avoid printing them, rotate them, and prefer short-lived credentials such as IAM roles where possible.
</QA>

<QA q="What happens to NEXT_PUBLIC_ variables in a Next.js app?">
They are inlined into the client-side JavaScript at build time, so their values are visible to anyone who loads the site. They must only contain public configuration such as a public API URL or a publishable key. Server-only secrets must use variables without the prefix and be used only in server code.
</QA>

</DeepDive>
