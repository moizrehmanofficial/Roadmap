<Callout type="tip" title="In one minute">
**SSH** (Secure Shell) gives you an encrypted terminal on a remote machine: `ssh user@server`. Instead of passwords, use **key pairs**: a **private key** (secret, stays on your laptop, `~/.ssh/id_ed25519`) and a **public key** (safe to share, `.pub`) placed in the server's `~/.ssh/authorized_keys`. Create one with `ssh-keygen -t ed25519`, install it with `ssh-copy-id user@server`. The first connection asks you to confirm the server's **fingerprint** (stored in `known_hosts`). Save shortcuts in `~/.ssh/config`. On servers, disable password and root login.
</Callout>

## Start from zero

### Working on a computer far away

Your server is in a data centre in Frankfurt or Mumbai. You need to type commands on it as if you were sitting in front of it — and nobody on the network between you should be able to read your commands or steal your login.

<Callout type="analogy">
A **padlock and key**. You give copies of an **open padlock** (your **public key**) to every server you want to enter; anyone may see the padlock — it is useless without the key. Only you keep the **key** (your **private key**). When you connect, the server snaps your padlock onto a challenge box; only someone holding the matching key can open it. No password ever travels over the network.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **SSH** | Encrypted protocol for remote terminals and file copies | `ssh alex@203.0.113.10` |
| **Client / server** | `ssh` on your machine / `sshd` on the server | port 22 |
| **Key pair** | A matching private + public key | `id_ed25519`, `id_ed25519.pub` |
| **Private key** | Secret half; never share, never copy to servers | `~/.ssh/id_ed25519` |
| **Public key** | Shareable half, installed on servers | `ssh-ed25519 AAAA… alex@laptop` |
| **authorized_keys** | Server-side list of public keys allowed to log in | `~/.ssh/authorized_keys` |
| **Host key / fingerprint** | The server's own identity, so you know it is the real server | `SHA256:x9F…` |
| **known_hosts** | Your list of servers you have trusted before | `~/.ssh/known_hosts` |
| **Passphrase** | A password protecting your private key file | |

## What is it?

SSH (port **22**) provides:

| Feature | Command |
| --- | --- |
| Remote terminal | `ssh user@host` |
| Run one remote command | `ssh user@host 'df -h'` |
| Copy files | `scp`, `rsync -e ssh`, `sftp` |
| Tunnels / port forwarding | `ssh -L 5432:localhost:5432 user@host` |
| Git over SSH | `git@github.com:user/repo.git` |

Everything is **encrypted**, and the server proves its identity with a **host key**, so man-in-the-middle attacks are detected.

## Why does it matter?

- **How you reach every Linux server**: VPS, cloud VMs, Raspberry Pis.
- **Deployments**: CI pipelines deploy over SSH; Ansible uses SSH.
- **GitHub/GitLab**: push and pull with SSH keys.
- **Security**: exposed SSH with password login is attacked by bots within minutes of a server going online. Key-only login + no root login stops almost all of it.

## When and where do you use it?

| Situation | What you do |
| --- | --- |
| New laptop | `ssh-keygen -t ed25519 -C "alex@laptop"` |
| New server | Add your public key (cloud console, `ssh-copy-id`) |
| Daily work | `ssh web-1` (with `~/.ssh/config`) |
| Copy a file | `scp file web-1:/tmp/`, `rsync -az dir/ web-1:/srv/app/` |
| Reach a private database | `ssh -L 5432:db.internal:5432 bastion` |
| GitHub | Add your `.pub` key in GitHub → Settings → SSH keys |

## Concepts one by one

### 1. Connecting: `ssh user@host`

<Explain>
<What>
Opens an encrypted shell on the remote machine as the given user.
</What>
<Why>
It is the standard way to administer Linux servers.
</Why>
<When>
Any time you work on a server.
</When>
<Where>
From Linux, macOS and Windows (OpenSSH is built into Windows 10/11 terminals).
</Where>
<How>
`ssh user@host` (default port 22), `ssh -p 2222 user@host` (other port), `ssh -i ~/.ssh/key user@host` (specific key), `exit` or Ctrl+D to leave.
</How>
</Explain>

```text
$ ssh alex@203.0.113.10
Welcome to Ubuntu 24.04.1 LTS (GNU/Linux 6.8.0-45-generic x86_64)
alex@web-1:~$ hostname
web-1
alex@web-1:~$ exit
logout
Connection to 203.0.113.10 closed.
```

Notice the prompt changes: you are now typing on `web-1`.

### 2. Public and private keys

<Explain>
<What>
A pair of mathematically linked keys. What the private key signs, the public key can verify — but the public key cannot be used to recreate the private one.
</What>
<Why>
Much stronger than passwords: nothing secret is ever sent, keys cannot be guessed by bots, and one key can be revoked without affecting others.
</Why>
<When>
Every SSH login, every Git push over SSH, every CI deploy.
</When>
<Where>
`~/.ssh/id_ed25519` (private) and `~/.ssh/id_ed25519.pub` (public) on your machine; the `.pub` content goes into servers' `authorized_keys`.
</Where>
<How>
Prefer **ed25519** keys (short, fast, secure). RSA keys should be at least 3072 bits.
</How>
</Explain>

```text
Login with a key, simplified:

  your laptop (private key)                         server (your public key in authorized_keys)
  ─────────────────────────                         ────────────────────────────────────────────
  "I'm alex, here is my public key"   ───────────►  "Is that key in authorized_keys? Yes."
                                      ◄───────────  "Prove it: sign this random challenge"
  signs it with the private key       ───────────►  checks the signature with the public key ✓
                                                    → logged in. No password was sent.
```

### 3. Creating a key: `ssh-keygen`

<Explain>
<What>
Generates a new key pair.
</What>
<Why>
You need your own key before any server can trust you.
</Why>
<When>
Once per device (laptop, CI system). Not per server.
</When>
<Where>
Saved in `~/.ssh/`.
</Where>
<How>
`ssh-keygen -t ed25519 -C "alex@laptop"`. Choose a **passphrase** for keys on laptops (protects you if the laptop is stolen). `-N ""` creates a key without passphrase (only for automation).
</How>
</Explain>

```bash
mkdir -p demo-ssh && chmod 700 demo-ssh
ssh-keygen -q -t ed25519 -C "alex@laptop" -N "" -f demo-ssh/id_ed25519
ls demo-ssh
stat -c '%a %n' demo-ssh/id_ed25519 demo-ssh/id_ed25519.pub
cut -d' ' -f1,3 demo-ssh/id_ed25519.pub
ssh-keygen -lf demo-ssh/id_ed25519.pub | awk '{print "fingerprint type:", $NF, "| starts with:", substr($2,1,7)}'
```

```text output
id_ed25519
id_ed25519.pub
600 demo-ssh/id_ed25519
644 demo-ssh/id_ed25519.pub
ssh-ed25519 alex@laptop
fingerprint type: (ED25519) | starts with: SHA256:
```

- The **private** key is created with `600` (only you can read it) — SSH refuses keys with looser permissions.
- The **public** key is one line: type, the key itself (long base64 text), and the comment.

### 4. Installing your public key on a server

<Explain>
<What>
Adding your public key to `~/.ssh/authorized_keys` of the user on the server.
</What>
<Why>
That file is the server's list of "padlocks it accepts".
</Why>
<When>
Once per server and user.
</When>
<Where>
Cloud consoles do it when creating a VM (you choose a key pair). Otherwise `ssh-copy-id`, or append it by hand.
</Where>
<How>
`ssh-copy-id -i ~/.ssh/id_ed25519.pub alex@server` (uses your password once). Permissions on the server must be strict: `~/.ssh` = 700, `authorized_keys` = 600.
</How>
</Explain>

```bash
mkdir -p server-home/.ssh
cat demo-ssh/id_ed25519.pub >> server-home/.ssh/authorized_keys
chmod 700 server-home/.ssh && chmod 600 server-home/.ssh/authorized_keys
stat -c '%a %n' server-home/.ssh server-home/.ssh/authorized_keys
wc -l < server-home/.ssh/authorized_keys | sed 's/$/ key(s) allowed/'
```

```text output
700 server-home/.ssh
600 server-home/.ssh/authorized_keys
1 key(s) allowed
```

(Here `server-home` stands in for `/home/alex` on a real server.) Each line in `authorized_keys` is one allowed key; delete a line to revoke that device's access.

### 5. Host keys and `known_hosts`

<Explain>
<What>
Each server has its own **host key**. On the first connection, SSH shows its fingerprint and asks if you trust it; then it remembers it in `~/.ssh/known_hosts`.
</What>
<Why>
If an attacker pretends to be your server (man-in-the-middle), the host key will not match and SSH **refuses** with a loud warning.
</Why>
<When>
First connection to a server; after a server is rebuilt (its key changes).
</When>
<Where>
`~/.ssh/known_hosts` on your machine; `/etc/ssh/ssh_host_*_key.pub` on the server.
</Where>
<How>
Compare the fingerprint with the one shown in the cloud console / by the admin. If a rebuilt server changes key legitimately, remove the old entry: `ssh-keygen -R hostname`.
</How>
</Explain>

```text
$ ssh alex@203.0.113.10
The authenticity of host '203.0.113.10' can't be established.
ED25519 key fingerprint is SHA256:x9Fq3k0n7Qk2v4Jd8mYlW1sB6tPzQe0rKcA5h2uV7nE.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added '203.0.113.10' (ED25519) to the list of known hosts.

… and if it ever changes unexpectedly:
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
```

Never just delete `known_hosts` to make that warning go away — first find out **why** the key changed.

### 6. `~/.ssh/config` — shortcuts

<Explain>
<What>
A personal config file where you name your servers and their settings.
</What>
<Why>
`ssh web-1` instead of `ssh -i ~/.ssh/work_key -p 2222 deploy@203.0.113.10`. Also used automatically by `scp`, `rsync` and `git`.
</Why>
<When>
As soon as you have more than one server.
</When>
<Where>
`~/.ssh/config`, mode `600`.
</Where>
<How>
One `Host` block per server. Comments go on their own lines.
</How>
</Explain>

```bash
cat > demo-ssh/config <<'EOF'
Host web-1
    HostName 203.0.113.10
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519

# Reach private servers through a bastion (jump host)
Host db-1
    HostName 10.0.2.15
    User admin
    ProxyJump web-1
EOF
ssh -G -F demo-ssh/config web-1 2>/dev/null | grep -E '^(hostname|user|port) '
ssh -G -F demo-ssh/config db-1 2>/dev/null | grep -E '^(hostname|proxyjump) '
```

```text output
user deploy
hostname 203.0.113.10
port 22
hostname 10.0.2.15
proxyjump web-1
```

`ssh -G` prints the settings SSH would use for a host — a safe way to check your config without connecting.

### 7. Running remote commands and copying files

<Explain>
<What>
Executing commands remotely without an interactive shell, and copying files over SSH.
</What>
<Why>
Scripts and CI pipelines do this all the time.
</Why>
<When>
Deploys, backups, quick checks.
</When>
<Where>
`ssh host 'command'`, `scp`, `rsync`.
</Where>
<How>
`rsync -avz --delete src/ host:/dest/` is the best choice for folders: it only sends what changed and can resume. Note the trailing `/` on the source = "the contents of src".
</How>
</Explain>

```text
$ ssh web-1 'uptime; df -h / | tail -1'
 14:30:01 up 12 days,  3:04,  1 user,  load average: 0.21, 0.30, 0.28
/dev/nvme0n1p1   20G  9.1G  11G  47% /

$ scp backup.sql.gz web-1:/tmp/
backup.sql.gz                         100%   48MB  11.2MB/s   00:04

$ rsync -avz --delete ./dist/ web-1:/var/www/shop/releases/20261110-1430/
sending incremental file list
index.html
assets/app.3f2a1b.js
sent 412,331 bytes  received 1,204 bytes  165,414.00 bytes/sec
```

### 8. Port forwarding (tunnels)

<Explain>
<What>
Sending a local port through the encrypted SSH connection to a port on (or behind) the server.
</What>
<Why>
Reach services that are deliberately **not** exposed to the internet — a database, an admin panel — securely.
</Why>
<When>
Connecting a database GUI (DBeaver, pgAdmin) to a production database in a private network.
</When>
<Where>
`ssh -L localport:target:targetport host`.
</Where>
<How>
`ssh -N -L 5433:localhost:5432 web-1` then connect your DB tool to `localhost:5433`. `-N` = no remote shell, just the tunnel.
</How>
</Explain>

```text
 your laptop                   web-1 (SSH)                 PostgreSQL
 localhost:5433  ══ SSH tunnel (encrypted) ══►  ───────►   localhost:5432
 (DBeaver connects here)                       the database never opens to the internet
```

### 9. ssh-agent: type the passphrase once

<Explain>
<What>
A background helper that keeps your **unlocked** private keys in memory for the session.
</What>
<Why>
Use a passphrase-protected key without typing the passphrase for every connection.
</Why>
<When>
Daily work on your laptop.
</When>
<Where>
Built into macOS Keychain, Windows (OpenSSH Authentication Agent service), Linux desktops.
</Where>
<How>
`eval "$(ssh-agent -s)"` then `ssh-add ~/.ssh/id_ed25519`; `ssh-add -l` lists loaded keys. Avoid **agent forwarding** (`-A`) to servers you do not fully trust — use `ProxyJump` instead.
</How>
</Explain>

```bash
eval "$(ssh-agent -s)" > /dev/null
ssh-add -q demo-ssh/id_ed25519
ssh-add -l | awk '{print "agent holds a key of type", $NF, "with comment", $3}'
ssh-agent -k > /dev/null
```

```text output
agent holds a key of type (ED25519) with comment alex@laptop
```

### 10. Hardening the SSH server

<Explain>
<What>
Server settings in `/etc/ssh/sshd_config` (or a drop-in in `/etc/ssh/sshd_config.d/`) that reduce the attack surface.
</What>
<Why>
Internet-facing SSH is scanned and brute-forced constantly.
</Why>
<When>
On every new server, **after** confirming your key login works.
</When>
<Where>
`/etc/ssh/sshd_config.d/50-hardening.conf`.
</Where>
<How>
Disable passwords and root login, limit users, then `sudo sshd -t && sudo systemctl reload ssh`. Keep your current session open and test a **new** login before disconnecting. Add fail2ban and, in the cloud, allow port 22 only from your IP (security group).
</How>
</Explain>

```text
# /etc/ssh/sshd_config.d/50-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowUsers alex deploy
```

```bash
printf 'PermitRootLogin no\nPasswordAuthentication no\nMaxAuthTries 3\n' > hardening.conf
grep -E '^(PermitRootLogin|PasswordAuthentication) no$' hardening.conf | wc -l | sed 's/^2$/both critical settings present/'
```

```text output
both critical settings present
```

## Hands-on

On your own computer:

```text
ssh-keygen -t ed25519 -C "you@laptop"        # 1. create a key (choose a passphrase)
cat ~/.ssh/id_ed25519.pub                    # 2. this line is what you give to servers/GitHub
ls -l ~/.ssh                                 # 3. private key must be -rw------- (600)
ssh -T git@github.com                        # 4. after adding the key to GitHub: "Hi <user>! You've successfully authenticated"
ssh-copy-id you@your-server                  # 5. install on a server (if you have one)
ssh you@your-server 'hostname; whoami'       # 6. remote command
```

A quick self-check of key permissions you can run anywhere:

```bash
check_key() {
  local mode; mode=$(stat -c %a "$1")
  if [[ $mode == 600 || $mode == 400 ]]; then echo "$1: OK ($mode)"; else echo "$1: TOO OPEN ($mode) — run chmod 600"; fi
}
cp demo-ssh/id_ed25519 bad_key && chmod 644 bad_key
check_key demo-ssh/id_ed25519
check_key bad_key
```

```text output
demo-ssh/id_ed25519: OK (600)
bad_key: TOO OPEN (644) — run chmod 600
```

SSH itself refuses a private key that others can read, with the message `UNPROTECTED PRIVATE KEY FILE!`.

## Real-world example

A small company with three VPS servers and a CI pipeline sets up SSH properly:

1. **Personal keys per person**, with passphrases, never shared. Each person has their own Linux account (no shared `ubuntu` login), so `auth.log` shows who did what.
2. **Password login and root login disabled** on every server; `AllowUsers` lists real accounts. Internet-wide password brute force becomes irrelevant.
3. **A bastion host** is the only server with port 22 open to the internet (and only from the office/VPN IPs); app and database servers accept SSH only from the bastion's private IP. Developers use `ProxyJump`.
4. **A dedicated deploy key** for CI, restricted in `authorized_keys`:

   ```text
   from="203.0.113.50",command="/usr/local/bin/deploy.sh",no-port-forwarding,no-pty ssh-ed25519 AAAA... ci-deploy
   ```

   The CI runner has a fixed outbound IP (a self-hosted runner or a NAT gateway). Even if the CI secret leaks, the key only runs the deploy script, and only from that IP.
5. **Offboarding** is one step: remove the person's key and lock their account on every server (automated with Ansible).
6. Later they move to **AWS Session Manager** for EC2: no inbound port 22 at all, access controlled by IAM and fully logged.

## Common mistakes

- **Leaving password authentication on** for internet-facing servers.
- **Sharing one private key** among a team, or copying private keys onto servers.
- **No passphrase** on a personal key — anyone who copies the file is you.
- **Wrong permissions** on `~/.ssh` (must be 700) or `authorized_keys` (600) — sshd silently ignores the key.
- **Blindly typing "yes"** to a changed host key warning, or deleting `known_hosts` to make the warning go away.
- **Restarting sshd with a broken config** and locking yourself out. Run `sshd -t` and keep a session open.
- **Committing private keys** (`id_rsa`, `.pem` files from AWS) to Git.

## Security lens

<Callout type="security">
SSH is the front door of every Linux server. Treat keys like passwords that never expire — because by default, they don't.
</Callout>

- **Brute force is constant:** any server with port 22 open sees login attempts within minutes. Keys-only authentication, `fail2ban`, limiting source IPs (security groups/firewalls) and not exposing 22 at all (bastion, VPN, Session Manager) are layered defences.
- **Host key verification prevents MITM.** A "REMOTE HOST IDENTIFICATION HAS CHANGED" warning means stop and verify (rebuilt server? or attack?). Distribute known host keys or use SSH certificates in larger fleets.
- **`authorized_keys` is a persistence target:** attackers add their own key to keep access. Monitor these files, review them, and manage them centrally (configuration management).
- **Private keys on laptops and CI** are high-value targets for infostealer malware and supply-chain attacks. Use passphrases, hardware-backed keys (FIDO2 `ed25519-sk`, YubiKey) for admins, and short-lived SSH certificates for scale.
- **Agent forwarding (`ssh -A`) is risky:** root on the remote host can use your agent to log in elsewhere as you. Prefer `ProxyJump`.
- **Key rotation and offboarding:** keys do not expire on their own. Keep an inventory; remove keys of people and systems that no longer need access.

## Interview questions

<QA q="How does SSH key-based authentication work?">
The user generates a key pair and places the public key in the server's authorized_keys for their account. During login, after the encrypted channel is established and the server has proven its identity with its host key, the server asks the client to prove possession of a private key matching one of the authorized public keys. The client signs a challenge with the private key; the server verifies the signature with the public key. The private key never leaves the client.
</QA>

<QA q="What is the purpose of the known_hosts file?">
It stores the host keys of servers you have connected to before. On each connection, SSH compares the server's presented host key with the stored one. If it differs, SSH warns that the remote host identification has changed, which could indicate a man-in-the-middle attack or a rebuilt server, and refuses to connect by default.
</QA>

<QA q="What would you change in sshd_config to harden a server?">
Disable root login (PermitRootLogin no), disable password and keyboard-interactive authentication so only keys work, restrict which users can log in (AllowUsers/AllowGroups), lower MaxAuthTries and LoginGraceTime, disable X11 and unnecessary forwarding, and keep OpenSSH patched. Combine this with firewall rules limiting port 22 to trusted IPs or a bastion, and test with sshd -t before reloading.
</QA>

<QA q="How do you securely access a database that is not exposed to the internet?">
Through an SSH tunnel from a host that can reach it: `ssh -L 5433:db-host:5432 bastion`, then connect your client to localhost:5433. In AWS, Session Manager port forwarding achieves the same without opening port 22. The database stays on a private network with no public port.
</QA>

<QA q="Why is SSH agent forwarding considered risky, and what is the alternative?">
With agent forwarding, the remote server can ask your local agent to sign authentication requests. Anyone with root on that server can use your forwarded agent socket to log in to other systems as you while you are connected. ProxyJump (ssh -J) reaches internal hosts through a bastion without exposing the agent to it.
</QA>

## Key terms

<Terms>
  <Term name="SSH">Secure Shell: encrypted remote login and command execution protocol.</Term>
  <Term name="sshd">The SSH server daemon.</Term>
  <Term name="Key pair">A private key you keep secret and a public key you share.</Term>
  <Term name="authorized_keys">Server-side list of public keys allowed to log in as a user.</Term>
  <Term name="Host key">The server's key pair, proving its identity to clients.</Term>
  <Term name="known_hosts">Client-side record of trusted server host keys.</Term>
  <Term name="ssh-agent">Holds decrypted private keys in memory for reuse.</Term>
  <Term name="Ed25519">Modern elliptic-curve signature algorithm recommended for SSH keys.</Term>
  <Term name="Port forwarding">Tunnelling other TCP traffic through an SSH connection.</Term>
  <Term name="Bastion / jump host">A hardened server used as the only entry point to private machines.</Term>
</Terms>
