<BigIdea>
<Tr>
<En>
**SSH** gives you a **secret, encrypted terminal** on a computer far away. Instead of a password, you use a **key pair**: a **private key** that never leaves your laptop, and a **public key** you give to servers. Nothing secret ever travels over the network.
</En>
<Ur>
**SSH** aap ko door ke computer par ek **khufiya, encrypted terminal** deta hai. Password ke bajaye aap ek **key pair** istemal karte hain: **private key** jo kabhi aap ka laptop nahi chhorti, aur **public key** jo aap servers ko dete hain. Network par kabhi koi khufiya cheez safar nahi karti.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **SSH** (Secure Shell): `ssh user@server` opens a terminal on another computer, encrypted end to end. It uses port **22**.
- **Private key** (`~/.ssh/id_ed25519`): your secret. Never share it.
- **Public key** (`~/.ssh/id_ed25519.pub`): safe to share. Servers keep it in `~/.ssh/authorized_keys`.
- **known_hosts**: your list of servers you've already checked and trusted.

</En>
<Ur>

- **SSH** (Secure Shell): `ssh user@server` doosre computer par terminal kholta hai, shuru se aakhir tak encrypted. Ye port **22** istemal karta hai.
- **Private key** (`~/.ssh/id_ed25519`): aap ka raaz. Kabhi share na karein.
- **Public key** (`~/.ssh/id_ed25519.pub`): share karna mehfooz hai. Servers ise `~/.ssh/authorized_keys` me rakhte hain.
- **known_hosts**: un servers ki list jinhe aap pehle check kar ke bharosa kar chuke hain.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- It's **how you reach every Linux server**: VPS, cloud machines, Raspberry Pis.
- **GitHub** and **CI deployments** use SSH keys too.
- A server with password login open to the internet gets attacked by bots **within minutes**. Keys stop almost all of it.

</En>
<Ur>

- Ye **har Linux server tak pohanchne ka tareeqa** hai: VPS, cloud machines, Raspberry Pi.
- **GitHub** aur **CI deployments** bhi SSH keys istemal karte hain.
- Internet par password login wala server **chand minute me** bots ke hamle ka shikar hota hai. Keys taqreeban sab rok deti hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- logging in to a server
- pushing code to GitHub
- copying files to a server
- reaching a private database safely

</En>
<Ur>

- server me login karte waqt
- GitHub par code bhejte waqt
- server par files copy karte waqt
- private database tak mehfooz tareeqe se pohanchte waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Three steps, once per laptop:

1. Create a key: `ssh-keygen -t ed25519`
2. Put it on the server: `ssh-copy-id user@server`
3. Log in: `ssh user@server` (no password)

Then switch password login **off** on the server.

</En>
<Ur>

Teen qadam, har laptop par ek dafa:

1. Key banao: `ssh-keygen -t ed25519`
2. Server par rakho: `ssh-copy-id user@server`
3. Login karo: `ssh user@server` (password ke baghair)

Phir server par password login **band** kar dein.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **padlock and its key**:

- You give **open padlocks** (your **public key**) to every server you want to enter. Anyone can see a padlock: it's useless without the key.
- You keep the only **key** (your **private key**).
- When you connect, the server locks a challenge box with your padlock. Only the person holding the matching key can open it.

So you prove who you are **without ever sending a password**.

</En>
<Ur>

Ek **taala aur us ki chaabi** ka socho:

- Aap har us server ko **khule taale** (aap ki **public key**) dete hain jahan andar jana hai. Taala koi bhi dekh sakta hai: chaabi ke baghair bekaar hai.
- Wahid **chaabi** aap ke paas rehti hai (aap ki **private key**).
- Jab aap connect karte hain, server ek sawal ka dabba aap ke taale se band karta hai. Sirf milti chaabi wala hi use khol sakta hai.

Yani aap **kabhi password bheje baghair** sabit karte hain ke aap kaun hain.

</Ur>
</Tr>

```text
Login with a key, simplified:

  your laptop (private key)                         server (your public key in authorized_keys)
  ─────────────────────────                         ────────────────────────────────────────────
  "I'm alex, here is my public key"   ───────────►  "Is that key in authorized_keys? Yes."
                                      ◄───────────  "Prove it: sign this random challenge"
  signs it with the private key       ───────────►  checks the signature with the public key ✓
                                                    → logged in. No password was sent.
```

## Learn it step by step

<Walkthrough>

<Step title="Connecting: ssh user@host">

<Tr>
<En>

`ssh user@host` opens a shell on the other machine as that user. It works from Linux, macOS and Windows 10/11 (OpenSSH is built in).

- `ssh -p 2222 user@host`: a different port
- `ssh -i ~/.ssh/key user@host`: a specific key
- `exit` or Ctrl+D: leave

</En>
<Ur>

`ssh user@host` doosri machine par us user ke taur par shell kholta hai. Ye Linux, macOS aur Windows 10/11 se chalta hai (OpenSSH pehle se mojood hai).

- `ssh -p 2222 user@host`: doosra port
- `ssh -i ~/.ssh/key user@host`: khaas key
- `exit` ya Ctrl+D: bahar niklo

</Ur>
</Tr>

```text
$ ssh alex@203.0.113.10
Welcome to Ubuntu 24.04.1 LTS (GNU/Linux 6.8.0-45-generic x86_64)
alex@web-1:~$ hostname
web-1
alex@web-1:~$ exit
logout
Connection to 203.0.113.10 closed.
```

<Happened>
<Tr>
<En>Look at the **prompt**: after logging in it says `alex@web-1`. Everything you type now runs on `web-1`, not your laptop. `exit` brings you back.</En>
<Ur>**Prompt** dekhein: login ke baad `alex@web-1` likha hai. Ab jo kuch aap likhenge wo `web-1` par chalega, laptop par nahi. `exit` wapas le aata hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Create your key: ssh-keygen">

<Tr>
<En>

You make a key **once per device** (laptop, CI system), not once per server.

`ssh-keygen -t ed25519 -C "alex@laptop"`:

- `-t ed25519`: the modern, short, secure key type
- `-C`: a comment so you know which device it is
- Choose a **passphrase** on laptops: if the laptop is stolen, the key is still locked.

</En>
<Ur>

Key **har device par ek dafa** banti hai (laptop, CI system), har server ke liye nahi.

`ssh-keygen -t ed25519 -C "alex@laptop"`:

- `-t ed25519`: jadeed, chhoti, mehfooz key ki qism
- `-C`: tabsira taa ke pata ho ye kaun sa device hai
- Laptops par **passphrase** rakhein: laptop chori ho to bhi key band rehti hai.

</Ur>
</Tr>

```bash
mkdir -p demo-ssh && chmod 700 demo-ssh
ssh-keygen -q -t ed25519 -C "alex@laptop" -N "" -f demo-ssh/id_ed25519
ls demo-ssh
stat -c '%a %n' demo-ssh/id_ed25519 demo-ssh/id_ed25519.pub
cut -d' ' -f1,3 demo-ssh/id_ed25519.pub
ssh-keygen -lf demo-ssh/id_ed25519.pub | awk '{print "fingerprint type:", $NF, "| starts with:", substr($2,1,7)}'
```

```text output
id_ed25519
id_ed25519.pub
600 demo-ssh/id_ed25519
644 demo-ssh/id_ed25519.pub
ssh-ed25519 alex@laptop
fingerprint type: (ED25519) | starts with: SHA256:
```

<Happened>
<Tr>
<En>

- Two files were made: the **private** key `id_ed25519` and the **public** key `id_ed25519.pub`.
- The private key is `600` (only you can read it). SSH **refuses** keys with looser permissions.
- The public key is one line: the type, a long code (the key itself), and your comment.
- The **fingerprint** is a short summary of the key, used to compare keys quickly.
- (We used `-N ""` for no passphrase because this is a demo. Only do that for automation.)

</En>
<Ur>

- Do files banin: **private** key `id_ed25519` aur **public** key `id_ed25519.pub`.
- Private key `600` hai (sirf aap parh sakte hain). Is se dheeli permissions wali keys SSH **rad** kar deta hai.
- Public key ek line hai: qism, ek lamba code (khud key), aur aap ka tabsira.
- **Fingerprint** key ka chhota khulasa hai, keys ko jaldi milane ke liye.
- (Hum ne `-N ""` se passphrase nahi rakha kyun ke ye demo hai. Aisa sirf automation ke liye karein.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Put your public key on the server">

<Tr>
<En>

The server keeps a list of padlocks it accepts: `~/.ssh/authorized_keys`, **one key per line**. Add yours there:

- Cloud consoles do it when you create a machine (you pick a key).
- Otherwise: `ssh-copy-id -i ~/.ssh/id_ed25519.pub alex@server` (uses your password once).

Permissions on the server must be strict: `~/.ssh` = `700`, `authorized_keys` = `600`. If they're too open, the server **silently ignores** your key.

</En>
<Ur>

Server un taalon ki list rakhta hai jinhe wo qubool karta hai: `~/.ssh/authorized_keys`, **har line me ek key**. Apni wahan shamil karein:

- Cloud consoles machine banate waqt ye kar dete hain (aap key chunte hain).
- Warna: `ssh-copy-id -i ~/.ssh/id_ed25519.pub alex@server` (ek dafa password istemal karta hai).

Server par permissions sakht honi chahiyen: `~/.ssh` = `700`, `authorized_keys` = `600`. Zyada khuli hon to server aap ki key **chupke se nazar andaz** kar deta hai.

</Ur>
</Tr>

```bash
mkdir -p server-home/.ssh
cat demo-ssh/id_ed25519.pub >> server-home/.ssh/authorized_keys
chmod 700 server-home/.ssh && chmod 600 server-home/.ssh/authorized_keys
stat -c '%a %n' server-home/.ssh server-home/.ssh/authorized_keys
wc -l < server-home/.ssh/authorized_keys | sed 's/$/ key(s) allowed/'
```

```text output
700 server-home/.ssh
600 server-home/.ssh/authorized_keys
1 key(s) allowed
```

<Happened>
<Tr>
<En>Here `server-home` stands in for `/home/alex` on a real server. We **appended** (`>>`) the public key, set strict permissions, and now 1 key is allowed. To remove a device's access later, just delete its line.</En>
<Ur>Yahan `server-home` asli server ke `/home/alex` ki jagah hai. Hum ne public key **aakhir me jori** (`>>`), sakht permissions lagayin, aur ab 1 key ki ijazat hai. Baad me kisi device ki access khatam karni ho to bas us ki line mita dein.</Ur>
</Tr>
</Happened>

</Step>

<Step title="'Are you sure?' Host keys and known_hosts">

<Tr>
<En>

You prove who **you** are with your key. But how do you know the **server** is the real one, and not an attacker in the middle? Every server has its own **host key**.

- On the **first** connection, SSH shows the server's fingerprint and asks if you trust it. Compare it with the one in your cloud console.
- After that, SSH remembers it in `~/.ssh/known_hosts`.
- If it ever **changes**, SSH refuses with a loud warning.

</En>
<Ur>

Aap apni key se sabit karte hain ke **aap** kaun hain. Lekin aap ko kaise pata ke **server** asli hai, beech me koi hacker nahi? Har server ki apni **host key** hoti hai.

- **Pehle** connection par SSH server ka fingerprint dikha kar poochta hai ke bharosa hai. Ise apne cloud console wale se milayen.
- Us ke baad SSH ise `~/.ssh/known_hosts` me yaad rakhta hai.
- Agar ye kabhi **badal** jaye, to SSH zor dar warning ke saath inkaar kar deta hai.

</Ur>
</Tr>

```text
$ ssh alex@203.0.113.10
The authenticity of host '203.0.113.10' can't be established.
ED25519 key fingerprint is SHA256:x9Fq3k0n7Qk2v4Jd8mYlW1sB6tPzQe0rKcA5h2uV7nE.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added '203.0.113.10' (ED25519) to the list of known hosts.

… and if it ever changes unexpectedly:
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
```

<Callout type="warning" title="Don't just delete known_hosts">
<Tr>
<En>First find out **why** the key changed. Was the server rebuilt? Then remove only that old entry with `ssh-keygen -R hostname`. If nobody rebuilt it, treat it as a possible attack.</En>
<Ur>Pehle pata karein key **kyun** badli. Kya server dobara bana? To sirf wo purani entry `ssh-keygen -R hostname` se hatayen. Agar kisi ne dobara nahi banaya, to ise mumkina hamla samjhein.</Ur>
</Tr>
</Callout>

</Step>

<Step title="~/.ssh/config: short names for servers">

<Tr>
<En>

Instead of typing `ssh -i ~/.ssh/work_key -p 2222 deploy@203.0.113.10` every time, give the server a **nickname** in `~/.ssh/config`, then just type `ssh web-1`. `scp`, `rsync` and `git` use it automatically too.

`ProxyJump` lets you reach a **private** server through a bastion in one step.

</En>
<Ur>

Har dafa `ssh -i ~/.ssh/work_key -p 2222 deploy@203.0.113.10` likhne ke bajaye, `~/.ssh/config` me server ka **chhota naam** rakhein, phir bas `ssh web-1` likhein. `scp`, `rsync` aur `git` bhi ise khud istemal karte hain.

`ProxyJump` aap ko ek qadam me bastion ke zariye **private** server tak le jata hai.

</Ur>
</Tr>

```bash
cat > demo-ssh/config <<'EOF'
Host web-1
    HostName 203.0.113.10
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519

# Reach private servers through a bastion (jump host)
Host db-1
    HostName 10.0.2.15
    User admin
    ProxyJump web-1
EOF
ssh -G -F demo-ssh/config web-1 2>/dev/null | grep -E '^(hostname|user|port) '
ssh -G -F demo-ssh/config db-1 2>/dev/null | grep -E '^(hostname|proxyjump) '
```

```text output
user deploy
hostname 203.0.113.10
port 22
hostname 10.0.2.15
proxyjump web-1
```

<Happened>
<Tr>
<En>`ssh -G` prints the settings SSH **would** use for a nickname, without connecting. `web-1` means user `deploy` at `203.0.113.10`; `db-1` is reached by jumping through `web-1` first.</En>
<Ur>`ssh -G` connect kiye baghair wo settings print karta hai jo SSH kisi chhote naam ke liye **istemal karega**. `web-1` ka matlab `203.0.113.10` par user `deploy`; `db-1` tak pehle `web-1` se guzar kar pohanchte hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Run remote commands and copy files">

<Tr>
<En>

- `ssh web-1 'command'`: run one command on the server and come back
- `scp file web-1:/tmp/`: copy a file
- `rsync -avz --delete src/ web-1:/dest/`: copy a **folder**, sending only what changed. The best choice for deploys. The trailing `/` on `src/` means "the **contents** of src".

</En>
<Ur>

- `ssh web-1 'command'`: server par ek command chala kar wapas aao
- `scp file web-1:/tmp/`: file copy karo
- `rsync -avz --delete src/ web-1:/dest/`: **folder** copy karo, sirf badli hui cheezen bhej kar. Deploys ke liye behtareen. `src/` ke aakhir ka `/` matlab "src ke **andar ka saman**".

</Ur>
</Tr>

```text
$ ssh web-1 'uptime; df -h / | tail -1'
 14:30:01 up 12 days,  3:04,  1 user,  load average: 0.21, 0.30, 0.28
/dev/nvme0n1p1   20G  9.1G  11G  47% /

$ scp backup.sql.gz web-1:/tmp/
backup.sql.gz                         100%   48MB  11.2MB/s   00:04

$ rsync -avz --delete ./dist/ web-1:/var/www/shop/releases/20261110-1430/
sending incremental file list
index.html
assets/app.3f2a1b.js
sent 412,331 bytes  received 1,204 bytes  165,414.00 bytes/sec
```

</Step>

<Step title="Tunnels: reach a private database safely">

<Tr>
<En>

Your database should **not** be open to the internet. But how do you connect your database app (DBeaver, pgAdmin) to it? Through an **SSH tunnel**: a local port on your laptop is sent through the encrypted SSH connection to the database.

`ssh -N -L 5433:localhost:5432 web-1`, then connect your app to `localhost:5433`. (`-N` = just the tunnel, no shell.)

</En>
<Ur>

Aap ka database internet ke liye **khula nahi** hona chahiye. To apni database app (DBeaver, pgAdmin) us se kaise jorein? **SSH tunnel** ke zariye: laptop ka ek local port encrypted SSH connection se database tak bheja jata hai.

`ssh -N -L 5433:localhost:5432 web-1`, phir apni app ko `localhost:5433` se jorein. (`-N` = sirf tunnel, shell nahi.)

</Ur>
</Tr>

```text
 your laptop                   web-1 (SSH)                 PostgreSQL
 localhost:5433  ══ SSH tunnel (encrypted) ══►  ───────►   localhost:5432
 (DBeaver connects here)                       the database never opens to the internet
```

</Step>

<Step title="ssh-agent: type the passphrase once">

<Tr>
<En>

A passphrase protects your key, but typing it for every connection is annoying. **ssh-agent** keeps your **unlocked** key in memory for your session, so you type it once.

- `eval "$(ssh-agent -s)"` then `ssh-add ~/.ssh/id_ed25519`
- `ssh-add -l` lists loaded keys
- macOS Keychain and Windows' "OpenSSH Authentication Agent" do this for you.

</En>
<Ur>

Passphrase aap ki key ki hifazat karta hai, lekin har connection par likhna tang karta hai. **ssh-agent** aap ki **khuli hui** key session ke liye memory me rakhta hai, taa ke aap ek dafa likhein.

- `eval "$(ssh-agent -s)"` phir `ssh-add ~/.ssh/id_ed25519`
- `ssh-add -l` load shuda keys dikhata hai
- macOS Keychain aur Windows ka "OpenSSH Authentication Agent" ye aap ke liye karte hain.

</Ur>
</Tr>

```bash
eval "$(ssh-agent -s)" > /dev/null
ssh-add -q demo-ssh/id_ed25519
ssh-add -l | awk '{print "agent holds a key of type", $NF, "with comment", $3}'
ssh-agent -k > /dev/null
```

```text output
agent holds a key of type (ED25519) with comment alex@laptop
```

<Tr>
<En>Avoid **agent forwarding** (`ssh -A`) to servers you don't fully trust: root on that server could use your agent to log in elsewhere as you. Use `ProxyJump` instead.</En>
<Ur>Jin servers par poora bharosa na ho un par **agent forwarding** (`ssh -A`) se bachein: us server ka root aap ka agent istemal kar ke aap ban kar kahin aur login kar sakta hai. Is ki jagah `ProxyJump` istemal karein.</Ur>
</Tr>

</Step>

<Step title="Lock down the SSH server">

<Tr>
<En>

On every new server, **after** you've confirmed key login works, change these settings:

- no root login
- no password login (keys only)
- only certain users allowed

Then check and reload: `sudo sshd -t && sudo systemctl reload ssh`. **Keep your current session open** and test a **new** login before disconnecting, so a mistake can't lock you out.

</En>
<Ur>

Har naye server par, key login chalne ki **tasdeeq ke baad**, ye settings badlein:

- root login nahi
- password login nahi (sirf keys)
- sirf chand users ki ijazat

Phir check aur reload: `sudo sshd -t && sudo systemctl reload ssh`. Disconnect se pehle **mojooda session khula rakhein** aur **naya** login test karein, taa ke koi ghalti aap ko bahar band na kar de.

</Ur>
</Tr>

```text
# /etc/ssh/sshd_config.d/50-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowUsers alex deploy
```

```bash
printf 'PermitRootLogin no\nPasswordAuthentication no\nMaxAuthTries 3\n' > hardening.conf
grep -E '^(PermitRootLogin|PasswordAuthentication) no$' hardening.conf | wc -l | sed 's/^2$/both critical settings present/'
```

```text output
both critical settings present
```

<Tr>
<En>Add **fail2ban** (blocks IPs that keep failing), and in the cloud allow port 22 only from your own IP (security group).</En>
<Ur>**fail2ban** shamil karein (baar baar fail hone wale IPs block karta hai), aur cloud me port 22 sirf apne IP ke liye kholein (security group).</Ur>
</Tr>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="One shared key for the whole team">

<Tr>
<En>When someone leaves, you can't remove only their access, and logs can't tell who did what.</En>
<Ur>Jab koi jaye, to sirf us ki access khatam nahi kar sakte, aur logs nahi bata sakte kis ne kya kiya.</Ur>
</Tr>

</Bad>
<Good title="One key per person, per device">

<Tr>
<En>Each person creates their own key, with a passphrase. Remove one line from `authorized_keys` to revoke one device.</En>
<Ur>Har shakhs apni key banaye, passphrase ke saath. Ek device ki access khatam karne ke liye `authorized_keys` se ek line hatayen.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Restarting sshd with a broken config">

<Tr>
<En>One typo in `sshd_config`, restart, and nobody can log in any more.</En>
<Ur>`sshd_config` me ek typo, restart, aur ab koi login nahi kar sakta.</Ur>
</Tr>

</Bad>
<Good title="Test first, keep a session open">

```text
sudo sshd -t && sudo systemctl reload ssh
# then open a NEW terminal and log in before closing the old one
```

</Good>
</Compare>

<Compare>
<Bad title="Private keys in Git">

<Tr>
<En>Committing `id_rsa` or an AWS `.pem` file. Bots scan GitHub for these all day.</En>
<Ur>`id_rsa` ya AWS ki `.pem` file commit karna. Bots saara din GitHub par yahi dhoondte hain.</Ur>
</Tr>

</Bad>
<Good title="Keys stay in ~/.ssh">

<DeepDive title="Real world: SSH done right for a small company">

A small company with three VPS servers and a CI pipeline sets up SSH properly:

1. **Personal keys per person**, with passphrases, never shared. Each person has their own Linux account (no shared `ubuntu` login), so `auth.log` shows who did what.
2. **Password login and root login disabled** on every server; `AllowUsers` lists real accounts. Internet-wide password brute force becomes irrelevant.
3. **A bastion host** is the only server with port 22 open to the internet (and only from office/VPN IPs); app and database servers accept SSH only from the bastion's private IP. Developers use `ProxyJump`.
4. **A dedicated deploy key** for CI, restricted in `authorized_keys`:

   ```text
   from="203.0.113.50",command="/usr/local/bin/deploy.sh",no-port-forwarding,no-pty ssh-ed25519 AAAA... ci-deploy
   ```

   The CI runner has a fixed outbound IP. Even if the CI secret leaks, the key only runs the deploy script, and only from that IP.
5. **Offboarding** is one step: remove the person's key and lock their account on every server (automated with Ansible).
6. Later they move to **AWS Session Manager** for EC2: no inbound port 22 at all, access controlled by IAM and fully logged.

</DeepDive>

<DeepDive title="Security lens">

SSH is the front door of every Linux server. Treat keys like passwords that never expire, because by default they don't.

- **Brute force is constant:** any server with port 22 open sees login attempts within minutes. Keys-only authentication, `fail2ban`, limiting source IPs (security groups/firewalls) and not exposing 22 at all (bastion, VPN, Session Manager) are layered defences.
- **Host key verification prevents man-in-the-middle attacks.** A "REMOTE HOST IDENTIFICATION HAS CHANGED" warning means stop and verify. Distribute known host keys or use SSH certificates in larger fleets.
- **`authorized_keys` is a persistence target:** attackers add their own key to keep access. Monitor these files, review them, and manage them centrally.
- **Private keys on laptops and CI** are high-value targets for infostealer malware and supply-chain attacks. Use passphrases, hardware-backed keys (FIDO2 `ed25519-sk`, YubiKey) for admins, and short-lived SSH certificates at scale.
- **Agent forwarding (`ssh -A`) is risky:** root on the remote host can use your agent to log in elsewhere as you. Prefer `ProxyJump`.
- **Key rotation and offboarding:** keys don't expire on their own. Keep an inventory; remove keys of people and systems that no longer need access.
- Also: don't leave password authentication on, don't skip passphrases on personal keys, and don't blindly type "yes" to a changed host key.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does SSH key-based authentication work?">
The user generates a key pair and places the public key in the server's authorized_keys for their account. During login, after the encrypted channel is established and the server has proven its identity with its host key, the server asks the client to prove possession of a private key matching one of the authorized public keys. The client signs a challenge with the private key; the server verifies the signature with the public key. The private key never leaves the client.
</QA>

<QA q="What is the purpose of the known_hosts file?">
It stores the host keys of servers you have connected to before. On each connection, SSH compares the server's presented host key with the stored one. If it differs, SSH warns that the remote host identification has changed, which could indicate a man-in-the-middle attack or a rebuilt server, and refuses to connect by default.
</QA>

<QA q="What would you change in sshd_config to harden a server?">
Disable root login (PermitRootLogin no), disable password and keyboard-interactive authentication so only keys work, restrict which users can log in (AllowUsers/AllowGroups), lower MaxAuthTries and LoginGraceTime, disable X11 and unnecessary forwarding, and keep OpenSSH patched. Combine this with firewall rules limiting port 22 to trusted IPs or a bastion, and test with sshd -t before reloading.
</QA>

<QA q="How do you securely access a database that is not exposed to the internet?">
Through an SSH tunnel from a host that can reach it: `ssh -L 5433:db-host:5432 bastion`, then connect your client to localhost:5433. In AWS, Session Manager port forwarding achieves the same without opening port 22. The database stays on a private network with no public port.
</QA>

<QA q="Why is SSH agent forwarding considered risky, and what is the alternative?">
With agent forwarding, the remote server can ask your local agent to sign authentication requests. Anyone with root on that server can use your forwarded agent socket to log in to other systems as you while you are connected. ProxyJump (ssh -J) reaches internal hosts through a bastion without exposing the agent to it.
</QA>

</DeepDive>
