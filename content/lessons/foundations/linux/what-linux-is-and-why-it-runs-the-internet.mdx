<Callout type="tip" title="In one minute">
An **operating system (OS)** is the software that manages the hardware and lets programs run. **Linux** is strictly the **kernel** — the core of the OS that talks to CPU, memory, disks and network. A **distribution** (Ubuntu, Debian, Red Hat, Alpine) packages the kernel with tools, a package manager and defaults. Linux runs the vast majority of web servers, nearly every cloud VM and container, all the top supercomputers, and Android. It is free, open source, stable, scriptable and runs without a graphical desktop — perfect for servers. On Windows, use **WSL** to get a real Linux terminal.
</Callout>

## Start from zero

### What does an operating system do?

Programs like Chrome or Node.js do not talk to the hardware directly. They ask the operating system: "open this file", "give me memory", "send this over the network", "run this other program". The OS does the hard work and keeps programs from interfering with each other.

<Callout type="analogy">
A **hotel**:

- The **building, rooms, kitchen and electricity** are the hardware.
- The **hotel management** is the **kernel**: it assigns rooms (memory), decides who uses the kitchen when (CPU time), keeps guests out of each other's rooms (security), and handles deliveries (network, disk).
- The **reception desk** is the **shell**: guests (you) make requests there in a language the management understands.
- The **guests** are the **programs**.
</Callout>

## What is it?

Linux was started in **1991** by **Linus Torvalds**, a Finnish student, as a free kernel. Combined with the free **GNU** tools (Bash, `ls`, `cp`, compilers) it became a complete, free operating system. Today it is developed by thousands of companies and volunteers.

```text
┌───────────────────────────────────────────────┐
│  Your programs: nginx, Node.js, PostgreSQL     │   user space
│  Shell (Bash) and tools (ls, grep, systemctl)  │
├───────────────────────────────────────────────┤
│  System calls: open(), read(), fork(), …       │   the door between them
├───────────────────────────────────────────────┤
│  Linux kernel: processes, memory, files,       │   kernel space
│  network, drivers, security                    │
├───────────────────────────────────────────────┤
│  Hardware: CPU, RAM, disk, network card        │
└───────────────────────────────────────────────┘
```

## Why does it matter?

- **Servers:** most of the world's websites and APIs run on Linux.
- **Cloud:** AWS, Azure and Google Cloud VMs are overwhelmingly Linux; AWS's own Amazon Linux is a distro.
- **Containers:** Docker containers are Linux processes using Linux kernel features (namespaces, cgroups). Kubernetes nodes run Linux.
- **DevOps and CI/CD:** GitHub Actions, GitLab runners and build servers are mostly Linux.
- **Security:** pentesting distros (Kali), most security tools, and most attack targets on servers are Linux.
- **Your career:** every role in this guide — full-stack, DevOps, cloud, security — uses Linux daily.

## Concepts one by one

### 1. The kernel

<Explain>
<What>
The core program of the OS. It starts first when the computer boots, stays in memory, and controls all hardware.
</What>
<Why>
Programs need a safe, shared way to use hardware. The kernel enforces rules: memory isolation between processes, file permissions, CPU scheduling.
</Why>
<When>
Always running; every file open, network packet and new process goes through it.
</When>
<Where>
`/boot/vmlinuz-*` on disk; in memory while running.
</Where>
<How>
`uname -r` shows the kernel version; `uname -s` shows the kernel name.
</How>
</Explain>

```bash
echo "kernel name: $(uname -s)"
uname -r | grep -qE '^[0-9]+\.[0-9]+' && echo "kernel version looks like: X.Y.Z-… (e.g. 6.8.0-45-generic)"
echo "architecture: $(uname -m | sed 's/x86_64/x86_64 (Intel\/AMD 64-bit)/; s/aarch64/aarch64 (ARM 64-bit)/')"
```

```text output
kernel name: Linux
kernel version looks like: X.Y.Z-… (e.g. 6.8.0-45-generic)
architecture: x86_64 (Intel/AMD 64-bit)
```

On an ARM machine (Apple Silicon VM, AWS Graviton, Raspberry Pi) the last line shows `aarch64`.

### 2. System calls — how programs ask the kernel

<Explain>
<What>
A **system call** is a request from a program to the kernel: open a file, read bytes, create a process, open a network socket.
</What>
<Why>
Programs are not allowed to touch hardware directly. System calls are the only door, and the kernel checks permissions at that door.
</Why>
<When>
Constantly — even `echo hi` makes several.
</When>
<Where>
Every program. Security tools and container sandboxes (seccomp) watch or restrict system calls.
</Where>
<How>
`strace command` shows a program's system calls (install it with your package manager).
</How>
</Explain>

```text
$ strace -e trace=openat,write cat /etc/hostname
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3     ← "kernel, please open this file"
write(1, "web-1\n", 6)                              ← "kernel, write these 6 bytes to the screen"
web-1
```

### 3. Distributions

<Explain>
<What>
A distribution is a complete, installable OS built around the Linux kernel: tools, libraries, a package manager, default settings, and a release/update policy.
</What>
<Why>
Nobody assembles an OS from thousands of separate projects by hand. Distros do it, test it, and ship security updates.
</Why>
<When>
Choosing a server image, a Docker base image, or a laptop OS.
</When>
<Where>
Ubuntu (most popular for servers and beginners), Debian (stable), RHEL/Rocky/Alma (enterprise), Amazon Linux (AWS), Alpine (tiny, for containers), Kali (security), Arch (do-it-yourself).
</Where>
<How>
`/etc/os-release` tells you which distro you are on. The next lesson covers distros and package managers in depth.
</How>
</Explain>

```bash
. /etc/os-release
echo "This system says it is: ${NAME:-unknown}" | sed -E 's/: .+/: <distribution name>/'
grep -c '^ID=' /etc/os-release
```

```text output
This system says it is: <distribution name>
1
```

On Ubuntu you would see `NAME="Ubuntu"` and `VERSION_ID="24.04"`.

### 4. The shell and the terminal

<Explain>
<What>
The **terminal** is the window; the **shell** is the program inside it that reads your commands, runs them and shows output.
</What>
<Why>
Servers usually have no graphical desktop. Everything — installing, configuring, debugging, deploying — happens through the shell, often over SSH.
</Why>
<When>
Every interaction with a server.
</When>
<Where>
Bash (default on most servers), zsh (macOS default), sh/ash (minimal, in Alpine containers).
</Where>
<How>
`echo $SHELL` shows your login shell; `$0` shows the shell running right now.
</How>
</Explain>

```bash
echo "this command is being run by: $(basename "$BASH")"
command -v bash sh | sed 's|/usr||' | sort -u
```

```text output
this command is being run by: bash
/bin/bash
/bin/sh
```

### 5. "Everything is a file"

<Explain>
<What>
Linux represents almost everything — documents, devices, processes, kernel settings — as files in one directory tree.
</What>
<Why>
The same tools (`cat`, `grep`, `echo`, permissions) work on all of them, which makes Linux very scriptable.
</Why>
<When>
Reading system information, talking to devices, tuning the kernel.
</When>
<Where>
`/proc` (processes and kernel info), `/sys` (hardware and drivers), `/dev` (devices).
</Where>
<How>
Read them with `cat` like normal files.
</How>
</Explain>

```bash
grep -m1 'MemTotal' /proc/meminfo | awk '{print "RAM according to /proc/meminfo:", ($2 > 0 ? "a number in kB" : "?")}'
echo "uptime file has $(awk '{print NF}' /proc/uptime) numbers (seconds up, seconds idle)"
ls -l /dev/null | cut -c1 | sed 's/c/\/dev\/null is a character device (c), not a normal file/'
```

```text output
RAM according to /proc/meminfo: a number in kB
uptime file has 2 numbers (seconds up, seconds idle)
/dev/null is a character device (c), not a normal file
```

### 7. Getting Linux on your computer

<Explain>
<What>
Ways to practise Linux without buying a server.
</What>
<Why>
You learn Linux by typing commands every day.
</Why>
<When>
Right now.
</When>
<Where>
Windows, macOS, or the cloud.
</Where>
<How>
**Windows:** open PowerShell as admin and run `wsl --install` (installs Ubuntu). **macOS:** the Terminal is Unix-like; for real Linux use a VM (UTM, Multipass) or Docker. **Cloud:** a small VPS or a free-tier VM. **Quick sandbox:** `docker run -it --rm ubuntu bash`.
</How>
</Explain>

```text
PS C:\> wsl --install          # Windows: installs WSL 2 + Ubuntu, then reboot
PS C:\> wsl                    # opens your Ubuntu shell

$ docker run -it --rm ubuntu bash    # any OS with Docker: a throwaway Ubuntu shell
root@3f2a1b:/# cat /etc/os-release | head -2
```

## Hands-on

Open a Linux terminal (WSL, a VM, a cloud server or a container) and run:

```bash
uname -a                 # kernel, host name, architecture
cat /etc/os-release      # which distribution and version
whoami                   # your user name
echo $SHELL              # your login shell
uptime                   # how long the system has been running
nproc; free -h; df -h /  # CPUs, memory, disk
ls /                     # the top of the file system tree (next lessons)
```

A safe check you can compare with this page:

```bash
for cmd in uname cat ls grep; do
  command -v "$cmd" > /dev/null && echo "$cmd is installed"
done
[[ -d /proc && -d /etc && -d /home ]] && echo "standard Linux folders exist"
```

```text output
uname is installed
cat is installed
ls is installed
grep is installed
standard Linux folders exist
```

## Real-world example

A typical small production setup you might build for a client:

1. An **Ubuntu 24.04** VPS or EC2 instance.
2. **Nginx** in front, terminating HTTPS and proxying to the app.
3. The **Node.js API** running in a Docker container based on `node:22-alpine`.
4. **PostgreSQL** in another container or a managed service.
5. **systemd** (or Docker's restart policy) keeping things running after a reboot.
6. **SSH with keys only** for admin access; the firewall allows only ports 22, 80 and 443.

Every item in that list is a Linux skill: package installation, services, file permissions, networking, SSH and logs. The rest of this module walks through each one.

At larger companies the picture is the same, just automated: thousands of Linux machines created by Terraform, configured by Ansible or baked into images, running Kubernetes, and watched by monitoring and security agents that read Linux logs and syscalls.

## Common mistakes

- **Working as root all the time.** One mistyped `rm -rf` or one compromised app then owns the whole machine. Use a normal user and `sudo` only when needed.
- **Copy-pasting commands you don't understand**, especially `curl ... | sudo bash`. You are running a stranger's script with full privileges.
- **Assuming every distribution is the same.** `apt` does not exist on Alpine (`apk`) or Amazon Linux (`dnf`). Check `/etc/os-release` first.
- **Using `chmod 777` to "fix" permission errors.** It works by giving everyone write access, which is a security hole. Fix ownership instead. (See "File Permissions and Ownership".)
- **Never updating.** Unpatched packages are one of the most common ways servers get compromised.

## Security lens

<Callout type="security">
Linux security is mostly about **who can do what** — users, groups, permissions and capabilities — and about **keeping the attack surface small**: fewer packages, fewer open ports, fewer services and fewer privileges.
</Callout>

What attackers look for on a Linux server, and what defends against it:

| Attacker goal | Typical weakness | Defence |
| --- | --- | --- |
| Get in | Password SSH login, exposed admin panels, vulnerable web app | SSH keys only, firewall, patch the app |
| Become root (privilege escalation) | Misconfigured `sudo`, world-writable scripts run by root, outdated kernel | Least privilege, correct permissions, kernel updates |
| Stay in (persistence) | New SSH key in `~/.ssh/authorized_keys`, cron jobs, new systemd services | File integrity monitoring, audit logs, alerts |
| Hide | Clearing `/var/log` | Ship logs off the machine to a central log store |
| Escape a container | Containers share the **host kernel**; privileged containers, mounted Docker socket | Non-root containers, no `--privileged`, runtime security tools |

The last row matters for DevSecOps: a container is **not** a virtual machine. All containers on a host share one Linux kernel, so a kernel vulnerability or a badly configured container can affect the host and every other container on it.

## Interview questions

<QA q="What is the difference between Linux and a Linux distribution?">
Linux is the kernel — the core that manages hardware, processes, memory, file systems and the network. A distribution packages the kernel with system libraries, an init system, a shell, utilities and a package manager, plus defaults and an update policy. Ubuntu, Debian, RHEL and Alpine are distributions; they all use the Linux kernel.
</QA>

<QA q="What are kernel space and user space, and why are they separated?">
Kernel space is where the kernel runs with full hardware access. User space is where applications run without direct hardware access; they ask the kernel for resources through system calls. The separation means a crashing or compromised application cannot directly control hardware or other processes' memory — the kernel enforces permissions on every request.
</QA>

<QA q="What is PID 1, and why does it matter in containers?">
PID 1 is the first user-space process the kernel starts, usually systemd on a full system. It starts and supervises services and adopts orphaned processes. In a container, your application often becomes PID 1, so it must handle signals such as SIGTERM correctly and reap child processes; otherwise containers stop slowly or leak zombie processes. Tools like `tini`, or Docker's `--init` flag, exist for this.
</QA>

<QA q="Why do containers depend on Linux, and what is the security implication?">
Containers are ordinary Linux processes isolated using kernel features: namespaces (what a process can see) and cgroups (how much it can use). There is no separate kernel per container, so all containers on a host share the host kernel. A kernel exploit or a privileged, misconfigured container can therefore lead to a container escape that affects the host and its other workloads.
</QA>

<QA q="A deployment fails with 'permission denied'. How do you start investigating?">
Find out which user the process runs as (`ps -o user,pid,cmd`, or the `User=` line in the systemd unit), then which file or port it tried to use (the error message, or `strace`). Check that file's owner and mode with `ls -l` and compare. Fix it by changing ownership or group membership, or by running the service as the right user — not with `chmod 777` or by running as root. Remember that ports below 1024 need extra privileges.
</QA>

## Key terms

<Terms>
  <Term name="Kernel">The core of the operating system; controls hardware, memory, processes and permissions.</Term>
  <Term name="Distribution">The kernel plus libraries, tools, a package manager and defaults, released as one product.</Term>
  <Term name="User space">Where normal programs run, without direct hardware access.</Term>
  <Term name="System call">A request from a program to the kernel, such as open, read, write or connect.</Term>
  <Term name="PID 1 / init">The first process the kernel starts; on most systems systemd.</Term>
  <Term name="Shell">A program that reads your commands and runs them, such as bash or zsh.</Term>
  <Term name="Package manager">Installs, updates and removes software: apt, dnf, apk.</Term>
  <Term name="Root">The superuser account (UID 0) with unrestricted access.</Term>
</Terms>
