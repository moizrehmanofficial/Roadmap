<BigIdea>
<Tr>
<En>
An **operating system** is the manager that sits between your programs and the hardware. **Linux** is a free operating system core (the **kernel**), and it runs most of the internet: servers, cloud machines, containers and even Android phones.
</En>
<Ur>
**Operating system** wo manager hai jo aap ke programs aur hardware ke darmiyan baitha hai. **Linux** ek muft operating system ka markaz (**kernel**) hai, aur internet ka zyada tar hissa isi par chalta hai: servers, cloud machines, containers, yahan tak ke Android phones bhi.
</Ur>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Operating system (OS)**: the software that manages the hardware and lets programs run. Windows, macOS and Linux are all operating systems.
- **Linux** is, strictly, the **kernel**: the core part that talks to the CPU, memory, disk and network.
- A **distribution** (distro) like **Ubuntu**, Debian or Alpine is the kernel + tools + an app installer, ready to use.

</En>
<Ur>

- **Operating system (OS)**: wo software jo hardware sambhalta hai aur programs chalne deta hai. Windows, macOS aur Linux sab operating systems hain.
- **Linux** asal me **kernel** hai: wo bunyadi hissa jo CPU, memory, disk aur network se baat karta hai.
- **Distribution** (distro) jaise **Ubuntu**, Debian ya Alpine: kernel + tools + apps install karne wala system, istemal ke liye tayyar.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- Most websites and APIs in the world run on Linux servers.
- Almost every cloud machine, Docker container and Kubernetes node is Linux.
- Every career in this guide (full-stack, DevOps, cloud, security) uses Linux every day.

</En>
<Ur>

- Duniya ki zyada tar websites aur APIs Linux servers par chalti hain.
- Taqreeban har cloud machine, Docker container aur Kubernetes node Linux hai.
- Is guide ka har career (full-stack, DevOps, cloud, security) roz Linux istemal karta hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- renting a server (VPS) or cloud machine
- building a Docker image
- running CI/CD pipelines (GitHub Actions runs on Linux)
- doing security work (Kali Linux and most security tools)

</En>
<Ur>

- server (VPS) ya cloud machine kiraye par lete waqt
- Docker image banate waqt
- CI/CD pipelines chalate waqt (GitHub Actions Linux par chalta hai)
- security ka kaam karte waqt (Kali Linux aur zyada tar security tools)

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

You talk to Linux mostly by **typing commands** in a **terminal**. Servers usually have **no screen or mouse**: everything is done with commands, often from far away over SSH.

On Windows you can get a real Linux terminal today with **WSL** (`wsl --install`).

</En>
<Ur>

Aap Linux se zyada tar **terminal** me **commands likh kar** baat karte hain. Servers ke paas aam taur par **screen ya mouse nahi hota**: sab kuch commands se hota hai, aksar door se SSH ke zariye.

Windows par aap aaj hi **WSL** (`wsl --install`) se asli Linux terminal le sakte hain.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of a **hotel**:

- The **building, rooms, kitchen and electricity** are the **hardware**.
- The **hotel management** is the **kernel**. It gives out rooms (memory), decides who uses the kitchen and when (CPU time), keeps guests out of each other's rooms (security), and handles deliveries (disk and network).
- The **reception desk** is the **shell**: you make requests there, in words the management understands.
- The **guests** are the **programs** (Chrome, Node.js, a database).

Guests never walk into the power room themselves. They **ask reception**, and management does it safely.

</En>
<Ur>

Ek **hotel** ka socho:

- **Building, kamre, kitchen aur bijli** **hardware** hain.
- **Hotel ki management** **kernel** hai. Ye kamre deti hai (memory), tay karti hai ke kitchen kaun aur kab istemal kare (CPU ka waqt), mehmanon ko ek doosre ke kamron se door rakhti hai (security), aur deliveries sambhalti hai (disk aur network).
- **Reception desk** **shell** hai: aap wahan apni farmaish karte hain, aise alfaz me jo management samajhti hai.
- **Mehman** **programs** hain (Chrome, Node.js, database).

Mehman kabhi khud bijli ke kamre me nahi jate. Wo **reception se kehte hain**, aur management ye kaam mehfooz tareeqe se karti hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="A short history, and the layers">

<Tr>
<En>

Linux was started in **1991** by **Linus Torvalds**, a student in Finland, as a free kernel. Together with free **GNU** tools (Bash, `ls`, `cp`, compilers) it became a complete, free operating system. Today thousands of companies and volunteers build it together.

A Linux system is made of **layers**. Your programs sit on top; the kernel sits under them; the hardware is at the bottom. Programs can only reach the kernel through a special door called **system calls**.

</En>
<Ur>

Linux **1991** me Finland ke ek student **Linus Torvalds** ne ek muft kernel ke taur par shuru kiya. Muft **GNU** tools (Bash, `ls`, `cp`, compilers) ke saath mil kar ye ek mukammal, muft operating system ban gaya. Aaj hazaron companies aur volunteers mil kar ise banate hain.

Linux system **tehon (layers)** se bana hai. Aap ke programs upar hain; kernel un ke neeche; hardware sab se neeche. Programs kernel tak sirf ek khaas darwaze se pohanch sakte hain jise **system calls** kehte hain.

</Ur>
</Tr>

```text
┌───────────────────────────────────────────────┐
│  Your programs: nginx, Node.js, PostgreSQL     │   user space
│  Shell (Bash) and tools (ls, grep, systemctl)  │
├───────────────────────────────────────────────┤
│  System calls: open(), read(), fork(), …       │   the door between them
├───────────────────────────────────────────────┤
│  Linux kernel: processes, memory, files,       │   kernel space
│  network, drivers, security                    │
├───────────────────────────────────────────────┤
│  Hardware: CPU, RAM, disk, network card        │
└───────────────────────────────────────────────┘
```

</Step>

<Step title="The kernel: the manager that's always running">

<Tr>
<En>

The kernel is the **first program** that starts when the computer turns on, and it keeps running until it shuts down. It controls all the hardware and enforces the rules: programs can't read each other's memory, files have owners, and every program gets a fair share of the CPU.

The `uname` command asks the kernel about itself.

</En>
<Ur>

Kernel wo **pehla program** hai jo computer on hote hi shuru hota hai, aur band hone tak chalta rehta hai. Ye saara hardware chalata hai aur qaide lagata hai: programs ek doosre ki memory nahi parh sakte, files ke maalik hote hain, aur har program ko CPU ka munasib hissa milta hai.

`uname` command kernel se us ke baare me poochti hai.

</Ur>
</Tr>

```bash
echo "kernel name: $(uname -s)"
uname -r | grep -qE '^[0-9]+\.[0-9]+' && echo "kernel version looks like: X.Y.Z-… (e.g. 6.8.0-45-generic)"
echo "architecture: $(uname -m | sed 's/x86_64/x86_64 (Intel\/AMD 64-bit)/; s/aarch64/aarch64 (ARM 64-bit)/')"
```

```text output
kernel name: Linux
kernel version looks like: X.Y.Z-… (e.g. 6.8.0-45-generic)
architecture: x86_64 (Intel/AMD 64-bit)
```

<Happened>
<Tr>
<En>

- `uname -s` = the kernel's **name**: Linux.
- `uname -r` = the kernel's **version**, something like `6.8.0-45-generic`.
- `uname -m` = the **type of CPU**. `x86_64` is a normal Intel/AMD computer. On ARM machines (Apple Silicon, AWS Graviton, Raspberry Pi) you'd see `aarch64`.

</En>
<Ur>

- `uname -s` = kernel ka **naam**: Linux.
- `uname -r` = kernel ka **version**, kuch `6.8.0-45-generic` jaisa.
- `uname -m` = **CPU ki qism**. `x86_64` aam Intel/AMD computer hai. ARM machines (Apple Silicon, AWS Graviton, Raspberry Pi) par `aarch64` dikhega.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="System calls: how programs ask the kernel">

<Tr>
<En>

A **system call** is a program's request to the kernel: "open this file", "read these bytes", "start a new program", "connect to the network". Programs are **not allowed** to touch the hardware themselves; system calls are the only door, and the kernel checks permissions at that door.

Even a tiny command like `cat` (which shows a file) makes several system calls. The `strace` tool lets you watch them:

</En>
<Ur>

**System call** program ki kernel se darkhwast hai: "ye file kholo", "ye bytes parho", "naya program chalao", "network se jodo". Programs ko khud hardware chhoone ki **ijazat nahi**; system calls hi wahid darwaza hain, aur kernel us darwaze par permissions check karta hai.

`cat` jaisi chhoti command (jo file dikhati hai) bhi kai system calls karti hai. `strace` tool se aap inhe dekh sakte hain:

</Ur>
</Tr>

```text
$ strace -e trace=openat,write cat /etc/hostname
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3     ← "kernel, please open this file"
write(1, "web-1\n", 6)                              ← "kernel, write these 6 bytes to the screen"
web-1
```

<Happened>
<Tr>
<En>

- `openat(...)`: `cat` asks the kernel to open `/etc/hostname`. The kernel checks permissions and says "OK, it's number 3".
- `write(1, ...)`: `cat` asks the kernel to write 6 bytes to the screen (number 1 means "the screen").
- Security tools and container sandboxes watch or block system calls, because that's where every action happens.

</En>
<Ur>

- `openat(...)`: `cat` kernel se `/etc/hostname` kholne ko kehta hai. Kernel permissions check kar ke kehta hai "theek hai, ye number 3 hai".
- `write(1, ...)`: `cat` kernel se screen par 6 bytes likhne ko kehta hai (number 1 ka matlab "screen").
- Security tools aur container sandboxes system calls par nazar rakhte hain ya unhe rokte hain, kyun ke har kaam yahin hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Distributions: Linux, ready to use">

<Tr>
<En>

Nobody builds an operating system from thousands of separate projects by hand. A **distribution** does that for you: it bundles the kernel with tools, libraries, an app installer (**package manager**) and sensible settings, tests it all, and sends security updates.

Popular ones:

- **Ubuntu**: the most popular for servers and beginners
- **Debian**: very stable
- **Red Hat / Rocky / Alma**: big companies
- **Amazon Linux**: AWS
- **Alpine**: tiny, used in containers
- **Kali**: security testing

The file `/etc/os-release` tells you which one you're on.

</En>
<Ur>

Koi bhi hazaron alag projects se haath se operating system nahi banata. **Distribution** ye kaam aap ke liye karti hai: kernel ko tools, libraries, apps install karne wale system (**package manager**) aur munasib settings ke saath jorti hai, sab test karti hai, aur security updates bhejti hai.

Mashhoor distros:

- **Ubuntu**: servers aur beginners me sab se mashhoor
- **Debian**: bohot stable
- **Red Hat / Rocky / Alma**: bari companies
- **Amazon Linux**: AWS
- **Alpine**: bohot chhoti, containers me istemal hoti hai
- **Kali**: security testing

`/etc/os-release` file batati hai ke aap kaun si distro par hain.

</Ur>
</Tr>

```bash
. /etc/os-release
echo "This system says it is: ${NAME:-unknown}" | sed -E 's/: .+/: <distribution name>/'
grep -c '^ID=' /etc/os-release
```

```text output
This system says it is: <distribution name>
1
```

<Happened>
<Tr>
<En>

- `. /etc/os-release` loads the settings from that file, including `NAME`.
- We hid the real name here so the page matches every machine. On Ubuntu you'd see `NAME="Ubuntu"` and `VERSION_ID="24.04"` in the file.
- The next lesson covers distributions and package managers in depth.

</En>
<Ur>

- `. /etc/os-release` us file se settings load karta hai, jin me `NAME` bhi hai.
- Hum ne yahan asal naam chhupa diya taa ke page har machine se mel khaye. Ubuntu par file me `NAME="Ubuntu"` aur `VERSION_ID="24.04"` dikhega.
- Agla lesson distributions aur package managers ko gehrai se samjhata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The shell and the terminal">

<Tr>
<En>

- The **terminal** is the **window**.
- The **shell** is the **program inside it** that reads what you type, runs it, and shows the result.

Servers usually have **no desktop**. Installing, configuring, fixing and deploying all happen through the shell, often over SSH. The most common shell is **Bash**; macOS uses zsh; tiny Alpine containers use `sh`.

</En>
<Ur>

- **Terminal** **window** hai.
- **Shell** us **window ke andar ka program** hai jo aap ka likha parhta hai, chalata hai, aur nateeja dikhata hai.

Servers ke paas aam taur par **desktop nahi hota**. Install karna, settings karna, theek karna aur deploy karna sab shell se hota hai, aksar SSH ke zariye. Sab se aam shell **Bash** hai; macOS zsh istemal karta hai; chhote Alpine containers `sh`.

</Ur>
</Tr>

```bash
echo "this command is being run by: $(basename "$BASH")"
command -v bash sh | sed 's|/usr||' | sort -u
```

```text output
this command is being run by: bash
/bin/bash
/bin/sh
```

<Happened>
<Tr>
<En>

- `$BASH` holds the path of the Bash program running this command.
- `command -v bash sh` shows **where** each shell program lives on disk: `/bin/bash` and `/bin/sh`.

</En>
<Ur>

- `$BASH` me us Bash program ka path hai jo ye command chala raha hai.
- `command -v bash sh` dikhata hai ke har shell program disk par **kahan** hai: `/bin/bash` aur `/bin/sh`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title='"Everything is a file"'>

<Tr>
<En>

Linux shows almost **everything** as a file in one big folder tree: your documents, but also devices, running programs and kernel settings. That means the same simple tools (`cat`, `grep`) work on all of them.

- `/proc`: information about running programs and the system
- `/sys`: hardware and drivers
- `/dev`: devices

</En>
<Ur>

Linux taqreeban **har cheez** ko ek bare folder tree me file ki tarah dikhata hai: aap ke documents, lekin devices, chalte programs aur kernel ki settings bhi. Is ka matlab ye hai ke wahi saade tools (`cat`, `grep`) sab par kaam karte hain.

- `/proc`: chalte programs aur system ki maloomat
- `/sys`: hardware aur drivers
- `/dev`: devices

</Ur>
</Tr>

```bash
grep -m1 'MemTotal' /proc/meminfo | awk '{print "RAM according to /proc/meminfo:", ($2 > 0 ? "a number in kB" : "?")}'
echo "uptime file has $(awk '{print NF}' /proc/uptime) numbers (seconds up, seconds idle)"
ls -l /dev/null | cut -c1 | sed 's/c/\/dev\/null is a character device (c), not a normal file/'
```

```text output
RAM according to /proc/meminfo: a number in kB
uptime file has 2 numbers (seconds up, seconds idle)
/dev/null is a character device (c), not a normal file
```

<Happened>
<Tr>
<En>

- `/proc/meminfo` isn't a real file on disk; the kernel creates it on the fly. Reading it tells you how much RAM there is.
- `/proc/uptime` holds how long the system has been running.
- `/dev/null` is a special "device": anything written to it disappears. Scripts use it to throw away output you don't want.

</En>
<Ur>

- `/proc/meminfo` disk par asli file nahi; kernel ise usi waqt banata hai. Ise parhne se pata chalta hai kitni RAM hai.
- `/proc/uptime` me hai ke system kab se chal raha hai.
- `/dev/null` ek khaas "device" hai: jo kuch is me likha jaye wo ghayab ho jata hai. Scripts isay faltu output phainkne ke liye istemal karti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Get Linux on your own computer today">

<Tr>
<En>

You learn Linux by **typing commands every day**. You don't need to buy a server:

- **Windows:** open PowerShell **as administrator** and run `wsl --install`. Restart, and you have Ubuntu.
- **macOS:** the Terminal is already very similar. For real Linux, use a virtual machine (UTM, Multipass) or Docker.
- **Any computer with Docker:** `docker run -it --rm ubuntu bash` gives a throwaway Ubuntu shell.
- **Cloud:** a small VPS or a free-tier cloud machine.

</En>
<Ur>

Linux **roz commands likh kar** seekha jata hai. Server khareedne ki zaroorat nahi:

- **Windows:** PowerShell **administrator ke taur par** kholein aur `wsl --install` chalayen. Restart karein, aur Ubuntu aap ke paas hai.
- **macOS:** Terminal pehle hi kaafi milta julta hai. Asli Linux ke liye virtual machine (UTM, Multipass) ya Docker istemal karein.
- **Docker wala koi bhi computer:** `docker run -it --rm ubuntu bash` ek waqti Ubuntu shell deta hai.
- **Cloud:** chhota VPS ya free-tier cloud machine.

</Ur>
</Tr>

```text
PS C:\> wsl --install          # Windows: installs WSL 2 + Ubuntu, then reboot
PS C:\> wsl                    # opens your Ubuntu shell

$ docker run -it --rm ubuntu bash    # any OS with Docker: a throwaway Ubuntu shell
root@3f2a1b:/# cat /etc/os-release | head -2
```

## Common mistakes

<Compare>
<Bad title="Working as root all the time">

<Tr>
<En>One typo like `rm -rf` in the wrong place, or one hacked app, and the **whole machine** is gone.</En>
<Ur>Ghalat jagah `rm -rf` jaisi ek ghalti, ya ek hack shuda app, aur **poori machine** khatam.</Ur>
</Tr>

</Bad>
<Good title="Normal user + sudo">

<Tr>
<En>Log in as a normal user and put `sudo` in front only of commands that really need admin power.</En>
<Ur>Aam user ke taur par login karein aur `sudo` sirf un commands se pehle lagayen jinhe waqai admin taqat chahiye.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Pasting commands you don't understand">

<Tr>
<En>`curl https://some-site/install.sh | sudo bash` runs a stranger's script with **full** power.</En>
<Ur>`curl https://some-site/install.sh | sudo bash` kisi ajnabi ki script **poori** taqat ke saath chalata hai.</Ur>
</Tr>

</Bad>
<Good title="Read first">

<Tr>
<En>Download the script, read it, and only then run it. Prefer the official package manager.</En>
<Ur>Script download karein, parhein, aur phir chalayen. Official package manager ko tarjeeh dein.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Assuming all distros are the same">

<Tr>
<En>`apt install` fails on Alpine (it uses `apk`) and Amazon Linux (it uses `dnf`).</En>
<Ur>`apt install` Alpine (jo `apk` istemal karti hai) aur Amazon Linux (jo `dnf` istemal karti hai) par fail hota hai.</Ur>
</Tr>

</Bad>
<Good title="Check first">

<Tr>
<En>Run `cat /etc/os-release` to see which distro you're on before following a guide.</En>
<Ur>Kisi guide par amal karne se pehle `cat /etc/os-release` chala kar dekhein ke aap kaun si distro par hain.</Ur>
</Tr>

</Good>
</Compare>

<DeepDive title="Real world: a small production setup">

A typical small setup you might build for a client:

1. An **Ubuntu 24.04** VPS or EC2 instance.
2. **Nginx** in front, handling HTTPS and passing requests to the app.
3. The **Node.js API** in a Docker container based on `node:22-alpine`.
4. **PostgreSQL** in another container or a managed service.
5. **systemd** (or Docker's restart policy) keeping things running after a reboot.
6. **SSH with keys only** for admin access; the firewall allows only ports 22, 80 and 443.

Every item is a Linux skill: installing packages, services, file permissions, networking, SSH and logs. The rest of this module walks through each one.

At large companies the picture is the same, just automated: thousands of Linux machines created by Terraform, configured by Ansible or baked into images, running Kubernetes, and watched by monitoring and security agents that read Linux logs and system calls.

</DeepDive>

<DeepDive title="Security lens">

Linux security is mostly about **who can do what** (users, groups, permissions, capabilities) and about **keeping the attack surface small**: fewer packages, open ports, services and privileges.

| Attacker goal | Typical weakness | Defence |
| --- | --- | --- |
| Get in | Password SSH login, exposed admin panels, vulnerable web app | SSH keys only, firewall, patch the app |
| Become root (privilege escalation) | Misconfigured `sudo`, world-writable scripts run by root, outdated kernel | Least privilege, correct permissions, kernel updates |
| Stay in (persistence) | New SSH key in `~/.ssh/authorized_keys`, cron jobs, new systemd services | File integrity monitoring, audit logs, alerts |
| Hide | Clearing `/var/log` | Ship logs off the machine to a central log store |
| Escape a container | Containers share the **host kernel**; privileged containers, mounted Docker socket | Non-root containers, no `--privileged`, runtime security tools |

The last row matters for DevSecOps: a container is **not** a virtual machine. All containers on a host share one Linux kernel, so a kernel bug or a badly configured container can affect the host and every other container on it.

Also: **never updating** is one of the most common ways servers get hacked, and `chmod 777` "fixes" permission errors by giving everyone write access. Fix ownership instead (see "File Permissions and Ownership").

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between Linux and a Linux distribution?">
Linux is the kernel: the core that manages hardware, processes, memory, file systems and the network. A distribution packages the kernel with system libraries, an init system, a shell, utilities and a package manager, plus defaults and an update policy. Ubuntu, Debian, RHEL and Alpine are distributions; they all use the Linux kernel.
</QA>

<QA q="What are kernel space and user space, and why are they separated?">
Kernel space is where the kernel runs with full hardware access. User space is where applications run without direct hardware access; they ask the kernel for resources through system calls. The separation means a crashing or compromised application cannot directly control hardware or other processes' memory: the kernel enforces permissions on every request.
</QA>

<QA q="What is PID 1, and why does it matter in containers?">
PID 1 is the first user-space process the kernel starts, usually systemd on a full system. It starts and supervises services and adopts orphaned processes. In a container, your application often becomes PID 1, so it must handle signals such as SIGTERM correctly and reap child processes; otherwise containers stop slowly or leak zombie processes. Tools like `tini`, or Docker's `--init` flag, exist for this.
</QA>

<QA q="Why do containers depend on Linux, and what is the security implication?">
Containers are ordinary Linux processes isolated using kernel features: namespaces (what a process can see) and cgroups (how much it can use). There is no separate kernel per container, so all containers on a host share the host kernel. A kernel exploit or a privileged, misconfigured container can therefore lead to a container escape that affects the host and its other workloads.
</QA>

<QA q="A deployment fails with 'permission denied'. How do you start investigating?">
Find out which user the process runs as (`ps -o user,pid,cmd`, or the `User=` line in the systemd unit), then which file or port it tried to use (the error message, or `strace`). Check that file's owner and mode with `ls -l` and compare. Fix it by changing ownership or group membership, or by running the service as the right user, not with `chmod 777` or by running as root. Ports below 1024 need extra privileges.
</QA>

</DeepDive>
