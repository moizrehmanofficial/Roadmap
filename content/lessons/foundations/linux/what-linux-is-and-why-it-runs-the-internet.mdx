<Callout type="tip" title="In one minute">
Linux is a **kernel**: the core program that controls the CPU, memory, disks and network for every other program. A **distribution** (Ubuntu, Debian, Alpine, Amazon Linux…) packages that kernel with tools, a package manager and defaults. Almost every server, container and cloud VM you will deploy to or defend runs Linux, so the terminal skills in this module are the base for DevOps, cloud and security work.
</Callout>

## What is it?

An **operating system** is the software layer between hardware and your programs. When your Node.js API reads a file, opens a network socket or allocates memory, it does not touch the hardware directly. It asks the operating system, and the operating system decides whether and how that happens.

**Linux** is, strictly speaking, the **kernel** of an operating system: the part that runs with full control of the machine. Linus Torvalds released it in 1991 as a free, open-source kernel, and it has been developed in public ever since.

What people casually call "Linux" is usually a **Linux distribution** — the kernel plus everything you need to use it:

| Layer | What it is | Examples |
| --- | --- | --- |
| Kernel | Manages CPU, memory, devices, files, network, processes, permissions | Linux 6.x |
| System libraries | Code programs call to talk to the kernel | glibc, musl |
| Init system | First process; starts and supervises services | systemd, OpenRC |
| Shell & utilities | The commands you type | bash, ls, grep, ssh |
| Package manager | Installs and updates software | apt, dnf, apk |
| Distribution | A curated, tested bundle of all of the above | Ubuntu, Debian, RHEL, Alpine, Amazon Linux |

So when someone says "the server runs Ubuntu", they mean: Linux kernel, plus Ubuntu's choice of libraries, tools, defaults and update policy.

## Why does it matter?

You cannot avoid Linux in the careers this guide covers:

- **Full-stack:** your Next.js or NestJS app is built and served on Linux — on Vercel, Render, a VPS or a Docker container.
- **DevOps:** Docker containers are Linux processes. Kubernetes nodes are Linux machines. CI runners (GitHub Actions `ubuntu-latest`) are Linux.
- **Cloud:** the default and most common choice for EC2 instances, Azure VMs and GCP Compute Engine is a Linux image.
- **Security:** attackers target Linux servers; incident responders read Linux logs; pentesters escalate privileges on Linux; detection tools watch Linux system calls.

Without Linux knowledge you can follow tutorials, but you cannot debug them. When a deployment fails with `permission denied`, `address already in use` or `No space left on device`, those are Linux problems, and you fix them in a Linux terminal.

Why Linux won the server world:

1. **Free and open source.** No licence fee per server, so running thousands of machines costs nothing extra. Anyone can read and audit the code.
2. **Stable and lightweight.** A minimal server install uses very little memory and can run for long periods between reboots.
3. **Built for automation.** Everything is a text file or a command, so it scripts well — exactly what DevOps needs.
4. **The features containers need.** Docker and Kubernetes are built on Linux kernel features (namespaces and cgroups).

## When and where do you use it?

You meet Linux whenever you:

- `ssh` into a VPS or EC2 instance to deploy or debug.
- Write a `Dockerfile` — `FROM node:22-alpine` means "start from Alpine Linux with Node installed".
- Write a CI pipeline — every `run:` step in GitHub Actions is a Linux shell command by default.
- Read server logs during an outage or a security incident.
- Harden a server: close ports, set permissions, configure SSH.
- Use Android — its kernel is Linux.

Where it physically lives: cloud data centres, Kubernetes clusters, your CI runners, routers and IoT devices, and — through WSL on Windows or a VM — on your own laptop.

## How does it work?

### Kernel space and user space

Memory and CPU time are split into two worlds:

- **Kernel space**: the kernel runs here with full access to hardware.
- **User space**: every normal program — bash, Node.js, Nginx, PostgreSQL — runs here with **no direct hardware access**.

When a program needs something only the kernel can do (open a file, send a packet, start a process), it makes a **system call** (syscall). The kernel checks permissions, does the work, and returns the result.

```text
  Your program (user space)        Kernel (kernel space)          Hardware
  ─────────────────────────        ─────────────────────          ────────
  fs.readFile("config.json")  ──►  open() / read() syscalls  ──►  disk
                              ◄──  checks permissions, returns data
```

This split is the foundation of Linux security: a bug in your app should not be able to take over the whole machine, because the app never runs with kernel privileges.

### What happens when a Linux machine boots

1. **Firmware** (BIOS/UEFI) checks hardware and finds a bootloader.
2. The **bootloader** (usually GRUB) loads the kernel into memory.
3. The **kernel** starts, detects hardware and mounts the root file system.
4. The kernel starts the first user-space process, **PID 1** — on most distributions this is **systemd**.
5. systemd starts services: networking, SSH, your web server, your database.
6. You get a login prompt, or an SSH connection.

You will meet steps 4 and 5 again in "systemd and Services".

### "Everything is a file"

Linux exposes almost everything through the file system:

- Your app's config: `/etc/nginx/nginx.conf`
- Running process information: `/proc/<pid>/`
- Devices: `/dev/sda` (a disk), `/dev/null` (a black hole)
- Logs: `/var/log/`

That means one small toolset — `cat`, `less`, `grep`, `ls` — lets you inspect almost anything on the system.

### Distributions you will actually meet

| Distribution | Where you see it | Package manager |
| --- | --- | --- |
| Ubuntu | VPS servers, GitHub Actions runners, most tutorials | `apt` |
| Debian | Servers; base of many Docker images (`node:22`, `python:3.12`) | `apt` |
| Alpine | Small Docker images (`node:22-alpine`) | `apk` |
| Amazon Linux | AWS EC2 default image | `dnf` |
| RHEL / Rocky / Alma | Enterprises, banks, government | `dnf` |
| Kali | Penetration testing (a toolbox, not a server OS) | `apt` |

The kernel is the same idea everywhere; distributions differ mainly in package manager, default tools and release cycle.

## Hands-on

You need a Linux shell. Any one of these works:

- **Windows:** install WSL — open PowerShell as administrator and run `wsl --install`, then open "Ubuntu" from the Start menu.
- **macOS:** the Terminal is Unix-like, but not Linux. For identical results run `docker run -it --rm ubuntu bash`.
- **Phone or no install:** use a cloud shell (AWS CloudShell, Google Cloud Shell) or a free VPS.

Run these and read what each one tells you.

```bash
# Which kernel is running? (-r = release, -m = CPU architecture)
uname -rm
# 6.8.0-45-generic x86_64

# Which distribution is this?
cat /etc/os-release
# PRETTY_NAME="Ubuntu 24.04.1 LTS"
# ID=ubuntu
# ...

# Who am I, and which groups am I in?
whoami
id

# What is PID 1? (the first process the kernel started)
ps -p 1 -o pid,comm
#   PID COMMAND
#     1 systemd

# How much memory and disk is there?
free -h
df -h /

# The kernel's view of a running process — "everything is a file"
ls /proc/self/
cat /proc/self/status | head -n 8
```

<Callout type="note">
Inside a Docker container, `ps -p 1` shows **your app or shell**, not systemd. A container is just a process tree with its own view of the system — it has no boot process of its own. That one detail explains a lot of container behaviour you will meet in the DevOps track.
</Callout>

Now watch a system call happen. `strace` shows every syscall a program makes:

```bash
sudo apt-get update && sudo apt-get install -y strace
strace -e trace=openat cat /etc/hostname
# openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3
# my-machine
```

`cat` did not read the disk itself. It asked the kernel to `openat` the file, received file descriptor `3`, then read from it. Every program on the system works this way.

## Real-world example

A typical small production setup you might build for a client:

1. An **Ubuntu 24.04** VPS or EC2 instance.
2. **Nginx** in front, terminating HTTPS and proxying to the app.
3. The **Node.js API** running in a Docker container based on `node:22-alpine`.
4. **PostgreSQL** in another container or a managed service.
5. **systemd** (or Docker's restart policy) keeping things running after a reboot.
6. **SSH with keys only** for admin access; the firewall allows only ports 22, 80 and 443.

Every item in that list is a Linux skill: package installation, services, file permissions, networking, SSH and logs. The rest of this module walks through each one.

At larger companies the picture is the same, just automated: thousands of Linux machines created by Terraform, configured by Ansible or baked into images, running Kubernetes, and watched by monitoring and security agents that read Linux logs and syscalls.

## Common mistakes

- **Working as root all the time.** One mistyped `rm -rf` or one compromised app then owns the whole machine. Use a normal user and `sudo` only when needed.
- **Copy-pasting commands you don't understand**, especially `curl ... | sudo bash`. You are running a stranger's script with full privileges.
- **Assuming every distribution is the same.** `apt` does not exist on Alpine (`apk`) or Amazon Linux (`dnf`). Check `/etc/os-release` first.
- **Using `chmod 777` to "fix" permission errors.** It works by giving everyone write access, which is a security hole. Fix ownership instead. (See "File Permissions and Ownership".)
- **Never updating.** Unpatched packages are one of the most common ways servers get compromised.

## Security lens

<Callout type="security">
Linux security is mostly about **who can do what** — users, groups, permissions and capabilities — and about **keeping the attack surface small**: fewer packages, fewer open ports, fewer services and fewer privileges.
</Callout>

What attackers look for on a Linux server, and what defends against it:

| Attacker goal | Typical weakness | Defence |
| --- | --- | --- |
| Get in | Password SSH login, exposed admin panels, vulnerable web app | SSH keys only, firewall, patch the app |
| Become root (privilege escalation) | Misconfigured `sudo`, world-writable scripts run by root, outdated kernel | Least privilege, correct permissions, kernel updates |
| Stay in (persistence) | New SSH key in `~/.ssh/authorized_keys`, cron jobs, new systemd services | File integrity monitoring, audit logs, alerts |
| Hide | Clearing `/var/log` | Ship logs off the machine to a central log store |
| Escape a container | Containers share the **host kernel**; privileged containers, mounted Docker socket | Non-root containers, no `--privileged`, runtime security tools |

The last row matters for DevSecOps: a container is **not** a virtual machine. All containers on a host share one Linux kernel, so a kernel vulnerability or a badly configured container can affect the host and every other container on it.

## Interview questions

<QA q="What is the difference between Linux and a Linux distribution?">
Linux is the kernel — the core that manages hardware, processes, memory, file systems and the network. A distribution packages the kernel with system libraries, an init system, a shell, utilities and a package manager, plus defaults and an update policy. Ubuntu, Debian, RHEL and Alpine are distributions; they all use the Linux kernel.
</QA>

<QA q="What are kernel space and user space, and why are they separated?">
Kernel space is where the kernel runs with full hardware access. User space is where applications run without direct hardware access; they ask the kernel for resources through system calls. The separation means a crashing or compromised application cannot directly control hardware or other processes' memory — the kernel enforces permissions on every request.
</QA>

<QA q="What is PID 1, and why does it matter in containers?">
PID 1 is the first user-space process the kernel starts, usually systemd on a full system. It starts and supervises services and adopts orphaned processes. In a container, your application often becomes PID 1, so it must handle signals such as SIGTERM correctly and reap child processes; otherwise containers stop slowly or leak zombie processes. Tools like `tini`, or Docker's `--init` flag, exist for this.
</QA>

<QA q="Why do containers depend on Linux, and what is the security implication?">
Containers are ordinary Linux processes isolated using kernel features: namespaces (what a process can see) and cgroups (how much it can use). There is no separate kernel per container, so all containers on a host share the host kernel. A kernel exploit or a privileged, misconfigured container can therefore lead to a container escape that affects the host and its other workloads.
</QA>

<QA q="A deployment fails with 'permission denied'. How do you start investigating?">
Find out which user the process runs as (`ps -o user,pid,cmd`, or the `User=` line in the systemd unit), then which file or port it tried to use (the error message, or `strace`). Check that file's owner and mode with `ls -l` and compare. Fix it by changing ownership or group membership, or by running the service as the right user — not with `chmod 777` or by running as root. Remember that ports below 1024 need extra privileges.
</QA>

## Key terms

<Terms>
  <Term name="Kernel">The core of the operating system; controls hardware, memory, processes and permissions.</Term>
  <Term name="Distribution">The kernel plus libraries, tools, a package manager and defaults, released as one product.</Term>
  <Term name="User space">Where normal programs run, without direct hardware access.</Term>
  <Term name="System call">A request from a program to the kernel, such as open, read, write or connect.</Term>
  <Term name="PID 1 / init">The first process the kernel starts; on most systems systemd.</Term>
  <Term name="Shell">A program that reads your commands and runs them, such as bash or zsh.</Term>
  <Term name="Package manager">Installs, updates and removes software: apt, dnf, apk.</Term>
  <Term name="Root">The superuser account (UID 0) with unrestricted access.</Term>
</Terms>
