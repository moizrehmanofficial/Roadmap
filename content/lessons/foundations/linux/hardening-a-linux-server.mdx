<Callout type="tip" title="In one minute">
**Hardening** means reducing a server's **attack surface**: fewer ways in, fewer privileges, more visibility. The essentials, in order: **patch** everything and enable automatic security updates; use **personal accounts + sudo**, never shared root; **SSH keys only**, no root login; a **default-deny firewall** that allows only needed ports; **fail2ban** against brute force; **remove** unused services and close unused ports; strict **permissions** on secrets; **central logs** and auditing; and **verify** with a scanner like Lynis. Do it with a script so every server is the same.
</Callout>

## Start from zero

### Why a fresh server is already in danger

The moment a server gets a public IP, automated bots start scanning it — trying SSH passwords, probing for open databases and known vulnerabilities. They do not target **you**; they target **everyone**, all the time.

<Callout type="analogy">
Moving into a new house in a busy city: before you unpack, you **change the locks** (SSH keys), **close windows you never use** (unused ports), install an **alarm** (fail2ban, logging), give **keys only to people who need them** (users, sudo), keep **valuables in a safe** (permissions on secrets), and arrange **regular maintenance** (updates). None of these alone makes the house safe; together they make it a hard target, and burglars move on.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Hardening** | Making a system harder to attack | disabling password SSH |
| **Attack surface** | All the ways an attacker could get in | open ports, users, services |
| **Least privilege** | Give only the access that is needed | app runs as `shopapp`, not root |
| **Defence in depth** | Several layers of protection | firewall + keys + fail2ban + updates |
| **Patch** | An update that fixes a bug or vulnerability | `openssl` security update |
| **CVE** | A public ID for a known vulnerability | CVE-2024-6387 (OpenSSH "regreSSHion") |
| **Firewall** | Rules deciding which network traffic is allowed | `ufw`, `firewalld`, cloud security groups |
| **Baseline / benchmark** | A standard list of secure settings | CIS Benchmarks |

## What is it?

Hardening is not one setting — it is a **checklist** applied to every server, ideally by a script or a tool like Ansible:

| Layer | Goal | Main tools |
| --- | --- | --- |
| Updates | No known vulnerabilities | `apt`, `unattended-upgrades`, `dnf-automatic` |
| Identity | Only the right people, minimal power | users, groups, sudo |
| Remote access | Strong, key-based login | sshd config, keys |
| Network | Only needed ports reachable | `ufw`/`firewalld`, security groups |
| Brute-force protection | Block repeated failures | fail2ban |
| Services | Run only what is needed | `systemctl disable`, `ss -ltnp` |
| Files | Secrets and system files protected | permissions, `find` audits |
| Visibility | Know what happens | journald, auditd, central logging |
| Kernel | Safer network and memory settings | `sysctl` |
| Verification | Measure and repeat | Lynis, CIS benchmarks |

## Why does it matter?

- Most real-world server compromises use **known** weaknesses: unpatched software, weak or reused passwords, exposed admin panels and databases, leaked keys.
- **Cloud bills and reputation:** a hacked server mines crypto on your bill, sends spam, or attacks others from your IP.
- **Compliance and jobs:** hardening is the daily work of DevSecOps and cloud security engineers, and a standard interview topic.

## When and where do you use it?

- **Immediately** after creating any server (as part of the setup script or cloud-init).
- **Continuously:** patching, reviewing users and keys, checking open ports.
- **After incidents:** verify nothing was changed (users, keys, cron, services).

## Concepts one by one

### 1. Update everything, then patch automatically

<Explain>
<What>
Installing all available updates, and enabling automatic installation of **security** updates.
</What>
<Why>
Unpatched software is the most common way in. Critical CVEs (like OpenSSH or OpenSSL bugs) get exploited within days of disclosure.
</Why>
<When>
First thing on a new server; then automatically every day.
</When>
<Where>
Ubuntu/Debian: `unattended-upgrades`. RHEL/Amazon Linux: `dnf-automatic`.
</Where>
<How>
Update, enable automatic security updates, and reboot when the kernel was updated (`/var/run/reboot-required` exists on Ubuntu).
</How>
</Explain>

```text
sudo apt update && sudo apt full-upgrade -y
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades       # answer "Yes"
[ -f /var/run/reboot-required ] && echo "reboot needed: $(cat /var/run/reboot-required.pkgs)"
```

### 2. Personal accounts, sudo, and no shared root

<Explain>
<What>
Each admin gets their own account with sudo; nobody logs in as root; unused accounts are removed.
</What>
<Why>
Accountability (logs show **who** did what), revocation (remove one person without changing everyone's access), and less damage from mistakes.
</Why>
<When>
Server setup; whenever people join or leave.
</When>
<Where>
`useradd`, `usermod -aG sudo`, `/etc/sudoers.d/`.
</Where>
<How>
Audit regularly: only `root` should have UID 0, and every account with a login shell should be expected.
</How>
</Explain>

```bash
echo "UID 0 accounts: $(awk -F: '$3 == 0 {print $1}' /etc/passwd | tr '\n' ' ')"
echo "accounts with empty password field in shadow: $(awk -F: '$2 == ""' /etc/shadow | wc -l)"
```

```text output
UID 0 accounts: root 
accounts with empty password field in shadow: 0
```

### 3. SSH: keys only, no root, limited users

<Explain>
<What>
Configuring the SSH server so only key-based logins of named users are possible.
</What>
<Why>
Password guessing against SSH is the most common attack on any public server.
</Why>
<When>
Right after you have confirmed your own key login works.
</When>
<Where>
`/etc/ssh/sshd_config.d/50-hardening.conf`.
</Where>
<How>
Write the drop-in, test with `sshd -t`, reload, and test a **new** session before closing the old one.
</How>
</Explain>

```text
# /etc/ssh/sshd_config.d/50-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
AllowUsers alex deploy
X11Forwarding no

$ sudo sshd -t && sudo systemctl reload ssh
$ sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication'
permitrootlogin no
passwordauthentication no
```

`sshd -T` prints the **effective** settings — the real proof that your changes are active.

### 4. Firewall: deny by default

<Explain>
<What>
Rules that block all incoming connections except the ones you explicitly allow.
</What>
<Why>
Services sometimes listen on all interfaces by accident (a database on `0.0.0.0:5432`, Redis on `6379`). A default-deny firewall protects you from your own mistakes.
</Why>
<When>
Every server; in the cloud **in addition** to security groups.
</When>
<Where>
`ufw` (Ubuntu), `firewalld` (RHEL), cloud **security groups / NSGs**.
</Where>
<How>
Allow SSH **first** (or you lock yourself out), then web ports, then enable.
</How>
</Explain>

```text
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH                       # 22 — before enabling!
sudo ufw allow 80,443/tcp                    # web
sudo ufw allow from 203.0.113.5 to any port 5432 proto tcp   # DB only from one admin IP
sudo ufw enable
sudo ufw status verbose
Status: active
Default: deny (incoming), allow (outgoing)
To                         Action      From
22/tcp (OpenSSH)           ALLOW IN    Anywhere
80,443/tcp                 ALLOW IN    Anywhere
5432/tcp                   ALLOW IN    203.0.113.5
```

In the cloud, the best practice is stricter still: allow SSH only from your office/VPN IP in the **security group**, or use AWS SSM Session Manager and close port 22 entirely.

### 5. fail2ban: ban repeated failures

<Explain>
<What>
A service that watches logs for repeated failures (SSH logins, web logins) and temporarily blocks the offending IPs in the firewall.
</What>
<Why>
Stops brute force, reduces log noise, and slows down scanners.
</Why>
<When>
Every server with SSH or login pages exposed.
</When>
<Where>
`/etc/fail2ban/jail.local`.
</Where>
<How>
Install, enable the `sshd` jail, check with `fail2ban-client status sshd`.
</How>
</Explain>

```text
# /etc/fail2ban/jail.local
[sshd]
enabled  = true
maxretry = 5
findtime = 10m
bantime  = 1h

$ sudo systemctl enable --now fail2ban
$ sudo fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed: 3
|  `- Total failed:     1842
`- Actions
   |- Currently banned: 12
   `- Banned IP list:   198.51.100.7 192.0.2.44 …
```

The idea, in a few lines of Bash:

```bash
printf '%s\n' 198.51.100.7 198.51.100.7 198.51.100.7 198.51.100.7 198.51.100.7 192.0.2.44 203.0.113.5 > failed-ips.txt
echo "would ban (5 or more failures):"
sort failed-ips.txt | uniq -c | awk '$1 >= 5 {print "  " $2, "(" $1 " failures)"}'
```

```text output
would ban (5 or more failures):
  198.51.100.7 (5 failures)
```

### 6. Remove what you do not need

<Explain>
<What>
Finding and disabling services, packages and open ports that are not required.
</What>
<Why>
Every running service is code that can have vulnerabilities. Software that is not running cannot be exploited.
</Why>
<When>
Setup, and after installing anything new.
</When>
<Where>
`ss -ltnp` (listening ports), `systemctl list-unit-files --state=enabled`, `apt list --installed`.
</Where>
<How>
For each listening port ask: "who needs this, and from where?" Bind internal services to `127.0.0.1`, disable the rest: `sudo systemctl disable --now SERVICE`.
</How>
</Explain>

```text
$ sudo ss -ltnp
LISTEN 0.0.0.0:22     sshd          ← needed (restricted by firewall/SG)
LISTEN 0.0.0.0:80     nginx         ← needed
LISTEN 0.0.0.0:443    nginx         ← needed
LISTEN 0.0.0.0:6379   redis-server  ← DANGER: Redis open to the world → bind 127.0.0.1
LISTEN 0.0.0.0:111    rpcbind       ← not needed → sudo systemctl disable --now rpcbind
LISTEN 127.0.0.1:3000 node          ← fine: only local, nginx proxies to it
```

### 7. Protect secrets and system files

<Explain>
<What>
Correct ownership and permissions for sensitive files, and regular audits for dangerous ones.
</What>
<Why>
World-readable `.env` files, backups and keys leak credentials; world-writable scripts run by root are an instant privilege escalation.
</Why>
<When>
Deploys, audits, incident response.
</When>
<Where>
App folders, `/etc`, `/root`, backup folders, cron scripts.
</Where>
<How>
Secrets `600` owned by the service user; audit with `find` for world-writable files and unexpected setuid binaries.
</How>
</Explain>

```bash
mkdir -p app && echo "DB_PASS=x" > app/.env && chmod 644 app/.env
echo "echo backup" > app/run-as-root.sh && chmod 777 app/run-as-root.sh
echo "findings:"
find app -type f -perm -o+r -name '.env*' -printf '  readable by everyone: %p\n'
find app -type f -perm -o+w -printf '  writable by everyone: %p\n'
chmod 600 app/.env && chmod 750 app/run-as-root.sh
echo "after fixing: $(find app -type f \( -perm -o+w -o \( -name '.env*' -perm -o+r \) \) | wc -l) findings"
```

```text output
findings:
  readable by everyone: app/.env
  writable by everyone: app/run-as-root.sh
after fixing: 0 findings
```

### 8. Logging, auditing and time

<Explain>
<What>
Making sure security-relevant events are recorded, kept, and timestamped correctly.
</What>
<Why>
Without logs you cannot detect or investigate an attack. Without correct time, logs from different systems cannot be correlated.
</Why>
<When>
Setup; always on.
</When>
<Where>
Persistent journald, `auth.log`, **auditd** (detailed audit trail of file access and commands), time sync with `systemd-timesyncd` or `chrony`, central log shipping.
</Where>
<How>
Enable persistent journal storage, install auditd with rules for sensitive files, ship logs off the server.
</How>
</Explain>

```text
# Watch changes to identity and SSH config with auditd
sudo apt install -y auditd
sudo auditctl -w /etc/passwd -p wa -k identity
sudo auditctl -w /etc/ssh/sshd_config -p wa -k sshd
sudo ausearch -k identity --start today          # who changed /etc/passwd today?

timedatectl | grep -E 'synchronized|Time zone'
System clock synchronized: yes
                Time zone: Etc/UTC (UTC, +0000)
```

### 9. Kernel and network settings (sysctl)

<Explain>
<What>
Kernel parameters that make the network stack and memory handling safer.
</What>
<Why>
Defaults favour compatibility; servers can be stricter (ignore redirects, protect against SYN floods, hide kernel pointers).
</Why>
<When>
Server setup (many cloud images already set some).
</When>
<Where>
`/etc/sysctl.d/99-hardening.conf`, applied with `sudo sysctl --system`.
</Where>
<How>
Add settings, apply, and verify with `sysctl name`.
</How>
</Explain>

```text
# /etc/sysctl.d/99-hardening.conf
net.ipv4.tcp_syncookies = 1                 # resist SYN flood attacks
net.ipv4.conf.all.accept_redirects = 0      # ignore ICMP redirects
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.all.rp_filter = 1             # drop spoofed packets
kernel.kptr_restrict = 2                    # hide kernel addresses
kernel.dmesg_restrict = 1                   # only root reads the kernel log
fs.protected_symlinks = 1                   # block symlink tricks in /tmp
fs.protected_hardlinks = 1
```

```bash
for k in net.ipv4.tcp_syncookies; do
  v=$(sysctl -n "$k" 2>/dev/null || cat "/proc/sys/${k//.//}")
  echo "$k = $v"
done
```

```text output
net.ipv4.tcp_syncookies = 1
```

Check any other key the same way, e.g. `sysctl fs.protected_symlinks` (Ubuntu sets it to `1` by default).

### 10. Verify: Lynis and benchmarks

<Explain>
<What>
Tools and standards that check a server against hundreds of hardening rules.
</What>
<Why>
You cannot remember everything; a scanner finds what you missed and gives a score to track over time.
</Why>
<When>
After setup, after changes, regularly (monthly) and before audits.
</When>
<Where>
**Lynis** (free, `sudo apt install lynis`), **CIS Benchmarks** (detailed guides per OS), OpenSCAP, cloud tools (AWS Inspector, Defender for Cloud).
</Where>
<How>
`sudo lynis audit system`, read the **Warnings** and **Suggestions**, fix, run again.
</How>
</Explain>

```text
$ sudo lynis audit system
…
  Hardening index : 64 [############        ]
  Tests performed : 262

  Warnings (2):
  ! Found one or more vulnerable packages. [PKGS-7392]
  ! Couldn't find 2 responsive nameservers [NETW-2705]

  Suggestions (31):
  * Consider hardening SSH configuration [SSH-7408]
      - Details  : MaxAuthTries (6 --> 3)
  …
```

### 11. Automate the baseline

<Explain>
<What>
Putting all hardening steps in a script (or Ansible role / cloud-init) that runs on every new server.
</What>
<Why>
Manual hardening is forgotten, inconsistent and undocumented. A script is repeatable, reviewable and version-controlled.
</Why>
<When>
Every server, from day one.
</When>
<Where>
The setup script from **Practical Scripts: Deployment and Server Setup**, Ansible, cloud-init user data, golden images (Packer).
</Where>
<How>
Make every step idempotent, run it, then verify with Lynis.
</How>
</Explain>

```bash
cat > harden-check.sh <<'EOF'
#!/usr/bin/env bash
# Quick, read-only hardening report (safe to run anywhere)
pass=0; fail=0
check() { if eval "$2" > /dev/null 2>&1; then echo "PASS  $1"; ((pass++)); else echo "FAIL  $1"; ((fail++)); fi; }
check "only root has UID 0"            '[[ $(awk -F: "\$3==0" /etc/passwd | wc -l) == 1 ]]'
check "/etc/shadow not world-readable" '[[ $(stat -c %a /etc/shadow) != *[4-7] ]]'
check "SYN cookies enabled"            '[[ $(cat /proc/sys/net/ipv4/tcp_syncookies) == 1 ]]'
check "/tmp has the sticky bit"        '[[ -k /tmp ]]'
echo "score: $pass passed, $fail failed"
EOF
bash harden-check.sh
```

```text output
PASS  only root has UID 0
PASS  /etc/shadow not world-readable
PASS  SYN cookies enabled
PASS  /tmp has the sticky bit
score: 4 passed, 0 failed
```

Extend this script with your own checks (SSH settings via `sshd -T`, firewall status, pending updates) and run it from cron or CI against every server.

## Hands-on

A hardening checklist to work through on a fresh VM (Ubuntu), in this order:

```text
1.  sudo apt update && sudo apt full-upgrade -y && sudo apt install -y unattended-upgrades ufw fail2ban lynis
2.  sudo adduser alex && sudo usermod -aG sudo alex            # personal admin account
3.  Put your public key in /home/alex/.ssh/authorized_keys (700/600), test: ssh alex@server
4.  SSH drop-in: no root, no passwords, AllowUsers → sudo sshd -t && sudo systemctl reload ssh
5.  sudo ufw allow OpenSSH && sudo ufw allow 80,443/tcp && sudo ufw enable
6.  sudo systemctl enable --now fail2ban unattended-upgrades
7.  sudo ss -ltnp → disable or bind-to-localhost anything unexpected
8.  Secrets: chmod 600, owned by the service user; find world-writable files
9.  sysctl hardening file → sudo sysctl --system
10. sudo lynis audit system → fix warnings → run again and compare the score
```

## Real-world example

A team turns this lesson into an **Ansible role** called `baseline`, applied to every server, and a **golden AMI** built weekly with Packer:

```text
roles/baseline/
  tasks/
    updates.yml          # unattended-upgrades, reboot window
    users.yml            # admin users from a list, SSH keys, locked root
    ssh.yml              # sshd_config.d/10-hardening.conf + validate + reload
    firewall.yml         # ufw rules per server role (web, db, worker)
    sysctl.yml           # /etc/sysctl.d/90-hardening.conf
    services.yml         # disable unneeded services
    logging.yml          # journald persistent, Fluent Bit shipping, auditd rules
    lynis.yml            # weekly Lynis run, report to central storage
```

Results after a quarter: every server has the same configuration; a new server is production-ready in minutes; auditors get a Lynis/CIS report per host; and when a developer's laptop was compromised, the attacker found SSH keys that only worked through the bastion, from the VPN, for one non-root account with narrow sudo — and the login alert fired within a minute.

## Common mistakes

- **Locking yourself out** — changing SSH or firewall rules without a second session or console access.
- **Hardening by hand** on each server, so servers drift apart. Use scripts or configuration management.
- **Host firewall but wide-open security group** (or the reverse), or forgetting that Docker bypasses UFW.
- **Disabling SELinux/AppArmor** to make an error go away.
- **Chasing a perfect Lynis score** with risky changes you do not understand; prioritise high-impact controls.
- **Hardening once** and never patching, re-auditing or reviewing access again.
- **Ignoring the application:** a perfectly hardened OS running a vulnerable web app with admin credentials in `.env` is still compromised through the app.

## Security lens

<Callout type="security">
Hardening does not make a server unbreakable. It makes attacks more expensive, more visible and less damaging — and it removes the easy wins that most real attackers rely on.
</Callout>

How the baseline maps to attacker steps (MITRE ATT&CK, simplified):

| Attacker step | Typical technique | Controls from this lesson |
| --- | --- | --- |
| Initial access | SSH brute force, exploit an exposed service | Keys only, restricted port 22, firewall, minimal services, patching |
| Execution | Run a downloaded tool from `/tmp` | `noexec` mounts, AppArmor/SELinux, non-root services |
| Persistence | Cron job, systemd unit, SSH key | File integrity monitoring, auditd rules, regular reviews |
| Privilege escalation | sudo misconfig, setuid binary, kernel exploit | Narrow sudo, setuid baseline, kernel updates, sysctl |
| Defense evasion | Delete logs | Log shipping, alerts on silence |
| Impact | Encrypt or delete data | Off-account immutable backups, tested restores |

## Interview questions

<QA q="How would you secure a newly created Linux server?">
Patch it and enable automatic security updates; create named admin accounts with sudo and lock root; configure SSH for keys only with root login disabled and restricted users; apply a default-deny firewall on the host and in the cloud security group; remove or disable unneeded services and bind internal ones to localhost; run apps as unprivileged users with systemd sandboxing; check file permissions and setuid binaries; apply kernel sysctl hardening; keep AppArmor or SELinux enforcing; ship logs centrally with alerts and auditd; set up tested off-host backups; and audit with Lynis or the CIS Benchmark. Automate all of it with configuration management.
</QA>

<QA q="What is the difference between discretionary and mandatory access control?">
In discretionary access control (standard Linux permissions), the owner of a resource decides who may access it, and root bypasses checks. In mandatory access control (SELinux, AppArmor), a system-wide policy defines what each program or label may access, and even the owner or a compromised process cannot override it. MAC limits damage from compromised services.
</QA>

<QA q="Why might UFW rules not protect a Docker container's published port?">
Docker manipulates iptables directly and inserts its own rules for published ports in chains that are evaluated before UFW's rules, so a port published with -p is reachable even if UFW denies it. Fix it by binding published ports to 127.0.0.1 or a private interface, not publishing internal services at all, using cloud security groups, or configuring the DOCKER-USER chain.
</QA>

<QA q="What is a CIS Benchmark?">
A consensus-based, freely available set of configuration recommendations for securing a specific operating system, cloud platform or application, published by the Center for Internet Security. Controls are grouped into levels (Level 1 practical, Level 2 stricter), each with rationale, audit and remediation steps. Tools like OpenSCAP and cloud security posture tools check systems against them.
</QA>

<QA q="If a server is compromised, should you clean it or rebuild it?">
Rebuild it. After preserving evidence (disk snapshot, memory, logs) for investigation, you cannot fully trust any binary or configuration on a compromised host, since attackers may have installed rootkits or persistence you have not found. Provision a fresh server from trusted images and code, restore data from clean backups, rotate all credentials the server had, and fix the original entry point.
</QA>

## Key terms

<Terms>
  <Term name="Hardening">Reducing attack surface and limiting impact through secure configuration.</Term>
  <Term name="Attack surface">All the ways an attacker could interact with a system.</Term>
  <Term name="Defense in depth">Layering several independent security controls.</Term>
  <Term name="UFW / firewalld / nftables">Host firewall tools on Linux.</Term>
  <Term name="Security group">A cloud provider's virtual firewall around instances.</Term>
  <Term name="sysctl">Interface for setting kernel parameters at runtime.</Term>
  <Term name="AppArmor / SELinux">Mandatory access control systems that confine programs.</Term>
  <Term name="auditd">Linux auditing daemon that records security-relevant events.</Term>
  <Term name="File integrity monitoring">Detecting unexpected changes to files.</Term>
  <Term name="CIS Benchmark">Published secure configuration baseline for a platform.</Term>
  <Term name="Lynis">Open-source security auditing tool for Unix-like systems.</Term>
  <Term name="Golden image">A pre-hardened base image used to create servers.</Term>
</Terms>
