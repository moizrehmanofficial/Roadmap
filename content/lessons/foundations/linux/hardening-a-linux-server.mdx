<BigIdea>
<Tr>
<En>
**Hardening** means making a server a **hard target**: fewer ways in, less power for each user and program, and more visibility. No single setting does it. A **checklist** of layers does, applied the same way to every server.
</En>
<Ur>
**Hardening** ka matlab server ko **mushkil nishana** banana: andar aane ke kam raaste, har user aur program ke paas kam taqat, aur zyada nigrani. Koi ek setting ye kaam nahi karti. Tehon (layers) ki ek **checklist** karti hai, jo har server par ek hi tarah lagayi jaye.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

The essentials, in order:

1. **Update** everything, and turn on automatic security updates.
2. **Personal accounts + sudo**, never a shared root login.
3. **SSH keys only**, no root login.
4. A **firewall** that blocks everything except the ports you need.
5. **fail2ban** to block password guessers.
6. **Turn off** services you don't use.
7. **Lock down** secrets (`600`).
8. Keep **logs**, and send them off the server.
9. **Check** with a scanner like Lynis.

</En>
<Ur>

Zaroori qadam, tarteeb se:

1. Sab kuch **update** karein, aur khud kaar security updates on karein.
2. **Zaati accounts + sudo**, kabhi share shuda root login nahi.
3. **Sirf SSH keys**, root login nahi.
4. **Firewall** jo zaroori ports ke ilawa sab rok de.
5. Password andaza lagane walon ko rokne ke liye **fail2ban**.
6. Jo services istemal nahi hotin unhe **band** karein.
7. Secrets **mehfooz** karein (`600`).
8. **Logs** rakhein, aur server se bahar bhejein.
9. Lynis jaise scanner se **check** karein.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- The moment a server gets a public IP, **bots start attacking it**. They don't target you personally; they attack **everyone**, all the time.
- Most real break-ins use **known, easy** weaknesses: old software, weak passwords, open databases, leaked keys.
- A hacked server mines crypto **on your bill**, sends spam, or attacks others from your IP.

</En>
<Ur>

- Jaise hi server ko public IP milta hai, **bots hamla shuru kar dete hain**. Wo aap ko zaati taur par nishana nahi banate; wo **sab par**, har waqt hamla karte hain.
- Zyada tar asli hamle **mashhoor, aasaan** kamzoriyon se hote hain: purana software, kamzor passwords, khule databases, leak shuda keys.
- Hack shuda server **aap ke bill par** crypto mine karta hai, spam bhejta hai, ya aap ke IP se doosron par hamla karta hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **immediately** after creating any server
- **continuously**: patching, reviewing users and keys, checking open ports
- **after an incident**: check nothing was changed

</En>
<Ur>

- koi bhi server banane ke **foran baad**
- **musalsal**: patching, users aur keys ka jaiza, khule ports check karna
- **kisi waqiye ke baad**: check karein ke kuch badla to nahi

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Put every step in a **script** (or Ansible), so every server ends up the same. Then run a scanner to measure the result, fix what it finds, and run it again.

</En>
<Ur>

Har qadam ek **script** (ya Ansible) me daalein, taa ke har server ek jaisa bane. Phir nateeja naapne ke liye scanner chalayen, jo mile use theek karein, aur dobara chalayen.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

You move into a new house in a busy city. Before you even unpack:

- you **change the locks** (SSH keys)
- you **close windows you never use** (unused ports)
- you install an **alarm** (fail2ban, logging)
- you give **keys only to people who need them** (users, sudo)
- you keep **valuables in a safe** (permissions on secrets)
- you arrange **regular maintenance** (updates)

None of these alone makes the house safe. Together they make it a hard target, and burglars move on to an easier house.

</En>
<Ur>

Aap ek masroof shehar me naye ghar me jate hain. Saman kholne se bhi pehle:

- aap **taale badalte** hain (SSH keys)
- **wo khirkiyan band** karte hain jo kabhi istemal nahi hotin (faltu ports)
- **alarm** lagate hain (fail2ban, logging)
- **chaabiyan sirf zaroorat walon** ko dete hain (users, sudo)
- **qeemti cheezen tijori** me rakhte hain (secrets par permissions)
- **baqaida dekh bhaal** ka intezam karte hain (updates)

In me se koi ek akeli ghar ko mehfooz nahi banati. Sab mil kar use mushkil nishana banati hain, aur chor kisi aasaan ghar ki taraf chale jate hain.

</Ur>
</Tr>

## The layers at a glance

| Layer | Goal | Main tools |
| --- | --- | --- |
| Updates | No known vulnerabilities | `apt`, `unattended-upgrades`, `dnf-automatic` |
| Identity | Only the right people, minimal power | users, groups, sudo |
| Remote access | Strong, key-based login | sshd config, keys |
| Network | Only needed ports reachable | `ufw`/`firewalld`, security groups |
| Brute-force protection | Block repeated failures | fail2ban |
| Services | Run only what is needed | `systemctl disable`, `ss -ltnp` |
| Files | Secrets and system files protected | permissions, `find` audits |
| Visibility | Know what happens | journald, auditd, central logging |
| Kernel | Safer network and memory settings | `sysctl` |
| Verification | Measure and repeat | Lynis, CIS benchmarks |

## Learn it step by step

<Walkthrough>

<Step title="1. Update everything, then patch automatically">

<Tr>
<En>

Old, unpatched software is the **most common** way in. Serious bugs in OpenSSH or OpenSSL get attacked within **days** of being announced.

So: install all updates first, then turn on **automatic security updates** (`unattended-upgrades` on Ubuntu, `dnf-automatic` on Red Hat), and reboot when the kernel was updated.

</En>
<Ur>

Purana, bina patch ka software andar aane ka **sab se aam** raasta hai. OpenSSH ya OpenSSL ke sangeen bugs elaan ke **chand din** ke andar hamle ka shikar hote hain.

To: pehle saare updates install karein, phir **khud kaar security updates** on karein (Ubuntu par `unattended-upgrades`, Red Hat par `dnf-automatic`), aur kernel update ho to reboot karein.

</Ur>
</Tr>

```text
sudo apt update && sudo apt full-upgrade -y
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades       # answer "Yes"
[ -f /var/run/reboot-required ] && echo "reboot needed: $(cat /var/run/reboot-required.pkgs)"
```

<Happened>
<Tr>
<En>The last line checks for the file Ubuntu creates when a reboot is needed, and lists which packages asked for it.</En>
<Ur>Aakhri line us file ko check karti hai jo Ubuntu reboot ki zaroorat par banata hai, aur batati hai kin packages ne reboot maanga.</Ur>
</Tr>
</Happened>

</Step>

<Step title="2. Personal accounts and sudo, no shared root">

<Tr>
<En>

Each admin gets **their own** account with sudo. Nobody logs in as root. Unused accounts are removed. This gives you:

- **accountability**: logs show who did what
- **easy removal**: take away one person without changing everyone's access

Check it regularly: only `root` should have UID 0, and no account should have an empty password.

</En>
<Ur>

Har admin ka **apna** account ho, sudo ke saath. Koi root ke taur par login nahi karta. Faltu accounts hata diye jate hain. Is se milta hai:

- **jawabdehi**: logs dikhate hain kis ne kya kiya
- **aasaan hataana**: sab ki access badle baghair ek shakhs ko hata dein

Baqaidagi se check karein: UID 0 sirf `root` ka ho, aur kisi account ka password khaali na ho.

</Ur>
</Tr>

```bash
echo "UID 0 accounts: $(awk -F: '$3 == 0 {print $1}' /etc/passwd | tr '\n' ' ')"
echo "accounts with empty password field in shadow: $(awk -F: '$2 == ""' /etc/shadow | wc -l)"
```

```text output
UID 0 accounts: root 
accounts with empty password field in shadow: 0
```

<Happened>
<Tr>
<En>Both checks pass: only `root` has UID 0, and no account can log in with an empty password.</En>
<Ur>Dono checks paas: UID 0 sirf `root` ka hai, aur koi account khaali password se login nahi kar sakta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="3. SSH: keys only, no root, named users">

<Tr>
<En>

Password guessing against SSH is the most common attack on any public server. After you've confirmed **your own key login works**, write these settings, test, reload, and **test a new login before closing your current session**:

</En>
<Ur>

SSH par password ka andaza lagana kisi bhi public server par sab se aam hamla hai. **Apna key login chalne** ki tasdeeq ke baad ye settings likhein, test karein, reload karein, aur **mojooda session band karne se pehle naya login test karein**:

</Ur>
</Tr>

```text
# /etc/ssh/sshd_config.d/50-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
AllowUsers alex deploy
X11Forwarding no

$ sudo sshd -t && sudo systemctl reload ssh
$ sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication'
permitrootlogin no
passwordauthentication no
```

<Happened>
<Tr>
<En>`sshd -t` tests the file for mistakes. `sshd -T` prints the settings SSH is **really** using now: the proof that your changes are active.</En>
<Ur>`sshd -t` file me ghaltiyan test karta hai. `sshd -T` wo settings print karta hai jo SSH ab **waqai** istemal kar raha hai: saboot ke aap ki tabdeeliyan lagu hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="4. Firewall: block everything, then allow what you need">

<Tr>
<En>

A **default-deny** firewall blocks every incoming connection **except** the ones you allow. It protects you from your own mistakes, like a database that accidentally listens to the whole internet.

**Allow SSH first**, or you'll lock yourself out. Then web ports, then turn it on.

</En>
<Ur>

**Default-deny** firewall har aane wala connection rokta hai **siwaye** un ke jinhe aap ijazat dein. Ye aap ko apni ghaltiyon se bachata hai, jaise database jo ghalti se poore internet ki sun raha ho.

**Pehle SSH ki ijazat dein**, warna aap khud bahar band ho jayenge. Phir web ports, phir on karein.

</Ur>
</Tr>

```text
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH                       # 22 — before enabling!
sudo ufw allow 80,443/tcp                    # web
sudo ufw allow from 203.0.113.5 to any port 5432 proto tcp   # DB only from one admin IP
sudo ufw enable
sudo ufw status verbose
Status: active
Default: deny (incoming), allow (outgoing)
To                         Action      From
22/tcp (OpenSSH)           ALLOW IN    Anywhere
80,443/tcp                 ALLOW IN    Anywhere
5432/tcp                   ALLOW IN    203.0.113.5
```

<Happened>
<Tr>
<En>

- Everything incoming is blocked by default.
- SSH and web (80, 443) are open.
- The database port 5432 is open **only** to one admin IP.
- In the cloud, also lock the **security group**: SSH only from your office/VPN IP, or close port 22 completely and use AWS Session Manager.

</En>
<Ur>

- Har aane wali cheez pehle se band hai.
- SSH aur web (80, 443) khule hain.
- Database port 5432 **sirf** ek admin IP ke liye khula hai.
- Cloud me **security group** bhi band karein: SSH sirf office/VPN IP se, ya port 22 bilkul band kar ke AWS Session Manager istemal karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="5. fail2ban: block repeated failures">

<Tr>
<En>

**fail2ban** watches the logs. When one IP fails to log in too many times, it **blocks that IP** in the firewall for a while. It stops brute force and slows down scanners.

</En>
<Ur>

**fail2ban** logs par nazar rakhta hai. Jab koi IP bohot dafa login me fail ho, to wo firewall me us **IP ko kuch der ke liye block** kar deta hai. Ye andhadhund koshishen rokta hai aur scanners ko sust karta hai.

</Ur>
</Tr>

```text
# /etc/fail2ban/jail.local
[sshd]
enabled  = true
maxretry = 5
findtime = 10m
bantime  = 1h

$ sudo systemctl enable --now fail2ban
$ sudo fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed: 3
|  `- Total failed:     1842
`- Actions
   |- Currently banned: 12
   `- Banned IP list:   198.51.100.7 192.0.2.44 …
```

<Tr>
<En>The settings mean: **5 failures within 10 minutes** = banned for **1 hour**. Here's the same idea in a few lines of Bash:</En>
<Ur>Settings ka matlab: **10 minute me 5 failures** = **1 ghante** ke liye ban. Yahi khayal Bash ki chand lines me:</Ur>
</Tr>

```bash
printf '%s\n' 198.51.100.7 198.51.100.7 198.51.100.7 198.51.100.7 198.51.100.7 192.0.2.44 203.0.113.5 > failed-ips.txt
echo "would ban (5 or more failures):"
sort failed-ips.txt | uniq -c | awk '$1 >= 5 {print "  " $2, "(" $1 " failures)"}'
```

```text output
would ban (5 or more failures):
  198.51.100.7 (5 failures)
```

<Happened>
<Tr>
<En>`sort | uniq -c` counts how many times each IP failed. Only `198.51.100.7` reached 5, so only it would be banned.</En>
<Ur>`sort | uniq -c` ginta hai har IP kitni dafa fail hua. Sirf `198.51.100.7` 5 tak pohancha, isliye sirf wahi ban hoga.</Ur>
</Tr>
</Happened>

</Step>

<Step title="6. Turn off what you don't need">

<Tr>
<En>

Every running service is code that might have a security hole. Software that **isn't running can't be attacked**.

List what's listening with `sudo ss -ltnp`, and for each port ask: **"Who needs this, and from where?"**

- Internal services (Redis, the app) → listen on `127.0.0.1` only.
- Not needed at all → `sudo systemctl disable --now SERVICE`.

</En>
<Ur>

Har chalti service aisa code hai jis me security surakh ho sakta hai. Jo software **chal hi nahi raha us par hamla nahi ho sakta**.

`sudo ss -ltnp` se dekhein kya sun raha hai, aur har port ke liye poochein: **"Is ki kise zaroorat hai, aur kahan se?"**

- Andaruni services (Redis, app) → sirf `127.0.0.1` par sunein.
- Bilkul zaroorat nahi → `sudo systemctl disable --now SERVICE`.

</Ur>
</Tr>

```text
$ sudo ss -ltnp
LISTEN 0.0.0.0:22     sshd          ← needed (restricted by firewall/SG)
LISTEN 0.0.0.0:80     nginx         ← needed
LISTEN 0.0.0.0:443    nginx         ← needed
LISTEN 0.0.0.0:6379   redis-server  ← DANGER: Redis open to the world → bind 127.0.0.1
LISTEN 0.0.0.0:111    rpcbind       ← not needed → sudo systemctl disable --now rpcbind
LISTEN 127.0.0.1:3000 node          ← fine: only local, nginx proxies to it
```

</Step>

<Step title="7. Protect secrets and system files">

<Tr>
<En>

Two kinds of dangerous files:

- **secrets readable by everyone** (`.env`, backups, keys) leak passwords
- **scripts writable by everyone** that root runs = anyone can become root

Secrets should be `600`, owned by the app's user. Find problems with `find`:

</En>
<Ur>

Do qism ki khatarnak files:

- **har kisi ke parhne layak secrets** (`.env`, backups, keys) passwords leak karte hain
- **har kisi ke likhne layak scripts** jo root chalata hai = koi bhi root ban sakta hai

Secrets `600` hon, app ke user ki milkiyat. Masail `find` se dhoondein:

</Ur>
</Tr>

```bash
mkdir -p app && echo "DB_PASS=x" > app/.env && chmod 644 app/.env
echo "echo backup" > app/run-as-root.sh && chmod 777 app/run-as-root.sh
echo "findings:"
find app -type f -perm -o+r -name '.env*' -printf '  readable by everyone: %p\n'
find app -type f -perm -o+w -printf '  writable by everyone: %p\n'
chmod 600 app/.env && chmod 750 app/run-as-root.sh
echo "after fixing: $(find app -type f \( -perm -o+w -o \( -name '.env*' -perm -o+r \) \) | wc -l) findings"
```

```text output
findings:
  readable by everyone: app/.env
  writable by everyone: app/run-as-root.sh
after fixing: 0 findings
```

<Happened>
<Tr>
<En>We made both mistakes on purpose, `find` caught both, and after `chmod 600` / `chmod 750` the same check finds **nothing**.</En>
<Ur>Hum ne dono ghaltiyan jaan boojh kar kin, `find` ne dono pakar lin, aur `chmod 600` / `chmod 750` ke baad wahi check **kuch nahi** paata.</Ur>
</Tr>
</Happened>

</Step>

<Step title="8. Logs, auditing and correct time">

<Tr>
<En>

Without logs you can't **notice** an attack or **investigate** one. Without the correct time, you can't match logs from different servers.

- Keep the journal **persistent** (it survives reboots).
- **auditd** records detailed events, like who changed `/etc/passwd`.
- Keep the clock synced (`timedatectl`).
- **Ship logs off the server**, because attackers delete local logs.

</En>
<Ur>

Logs ke baghair aap hamla na **dekh** sakte hain na us ki **tafteesh** kar sakte hain. Sahi waqt ke baghair mukhtalif servers ke logs mila nahi sakte.

- Journal **mustaqil** rakhein (reboot ke baad bhi rahe).
- **auditd** tafseeli waqiat likhta hai, jaise kis ne `/etc/passwd` badli.
- Ghari sync rakhein (`timedatectl`).
- **Logs server se bahar bhejein**, kyun ke hackers local logs mita dete hain.

</Ur>
</Tr>

```text
# Watch changes to identity and SSH config with auditd
sudo apt install -y auditd
sudo auditctl -w /etc/passwd -p wa -k identity
sudo auditctl -w /etc/ssh/sshd_config -p wa -k sshd
sudo ausearch -k identity --start today          # who changed /etc/passwd today?

timedatectl | grep -E 'synchronized|Time zone'
System clock synchronized: yes
                Time zone: Etc/UTC (UTC, +0000)
```

</Step>

<Step title="9. Safer kernel settings (sysctl)">

<Tr>
<En>

The kernel's default settings favour compatibility. Servers can be stricter: resist flood attacks, ignore fake network redirects, hide internal memory addresses. Put the settings in a file and apply with `sudo sysctl --system`.

</En>
<Ur>

Kernel ki default settings mutabiqat ko tarjeeh deti hain. Servers zyada sakht ho sakte hain: sailabi hamlon ka muqabla, jaali network redirects nazar andaz, andaruni memory ke pate chhupana. Settings ek file me daal kar `sudo sysctl --system` se lagayen.

</Ur>
</Tr>

```text
# /etc/sysctl.d/99-hardening.conf
net.ipv4.tcp_syncookies = 1                 # resist SYN flood attacks
net.ipv4.conf.all.accept_redirects = 0      # ignore ICMP redirects
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.all.rp_filter = 1             # drop spoofed packets
kernel.kptr_restrict = 2                    # hide kernel addresses
kernel.dmesg_restrict = 1                   # only root reads the kernel log
fs.protected_symlinks = 1                   # block symlink tricks in /tmp
fs.protected_hardlinks = 1
```

```bash
for k in net.ipv4.tcp_syncookies; do
  v=$(sysctl -n "$k" 2>/dev/null || cat "/proc/sys/${k//.//}")
  echo "$k = $v"
done
```

```text output
net.ipv4.tcp_syncookies = 1
```

<Happened>
<Tr>
<En>SYN cookies are already on (`1`) on this machine. Check any other setting the same way, e.g. `sysctl fs.protected_symlinks` (Ubuntu sets it to `1` by default).</En>
<Ur>Is machine par SYN cookies pehle se on (`1`) hain. Koi bhi doosri setting isi tarah check karein, jaise `sysctl fs.protected_symlinks` (Ubuntu ise default `1` rakhta hai).</Ur>
</Tr>
</Happened>

</Step>

<Step title="10. Check your work: Lynis">

<Tr>
<En>

You can't remember everything. A scanner checks **hundreds** of rules and gives you a score to improve over time.

- **Lynis** is free: `sudo apt install lynis`, then `sudo lynis audit system`.
- Read the **Warnings** first, then the **Suggestions**. Fix, and run again.
- **CIS Benchmarks** are detailed official guides per operating system.

</En>
<Ur>

Aap sab kuch yaad nahi rakh sakte. Scanner **saikron** qaide check karta hai aur score deta hai jise waqt ke saath behtar kar sakte hain.

- **Lynis** muft hai: `sudo apt install lynis`, phir `sudo lynis audit system`.
- Pehle **Warnings** parhein, phir **Suggestions**. Theek karein, aur dobara chalayen.
- **CIS Benchmarks** har operating system ke liye tafseeli official guides hain.

</Ur>
</Tr>

```text
$ sudo lynis audit system
…
  Hardening index : 64 [############        ]
  Tests performed : 262

  Warnings (2):
  ! Found one or more vulnerable packages. [PKGS-7392]
  ! Couldn't find 2 responsive nameservers [NETW-2705]

  Suggestions (31):
  * Consider hardening SSH configuration [SSH-7408]
      - Details  : MaxAuthTries (6 --> 3)
  …
```

</Step>

<Step title="11. Automate the whole baseline">

<Tr>
<En>

Hardening by hand gets **forgotten**, done **differently** on each server, and never written down. Put it in a **script** (or Ansible, or cloud-init) that runs on every new server. Here's a small, **read-only** checker you can grow:

</En>
<Ur>

Haath se hardening **bhool** jati hai, har server par **alag** hoti hai, aur kabhi likhi nahi jati. Ise ek **script** (ya Ansible, ya cloud-init) me daalein jo har naye server par chale. Ye ek chhota, **sirf parhne wala** checker hai jise aap barha sakte hain:

</Ur>
</Tr>

```bash
cat > harden-check.sh <<'EOF'
#!/usr/bin/env bash
# Quick, read-only hardening report (safe to run anywhere)
pass=0; fail=0
check() { if eval "$2" > /dev/null 2>&1; then echo "PASS  $1"; ((pass++)); else echo "FAIL  $1"; ((fail++)); fi; }
check "only root has UID 0"            '[[ $(awk -F: "\$3==0" /etc/passwd | wc -l) == 1 ]]'
check "/etc/shadow not world-readable" '[[ $(stat -c %a /etc/shadow) != *[4-7] ]]'
check "SYN cookies enabled"            '[[ $(cat /proc/sys/net/ipv4/tcp_syncookies) == 1 ]]'
check "/tmp has the sticky bit"        '[[ -k /tmp ]]'
echo "score: $pass passed, $fail failed"
EOF
bash harden-check.sh
```


## Common mistakes

<Compare>
<Bad title="Locking yourself out">

<Tr>
<En>Changing SSH or firewall settings with only one session open. One mistake and you can't get back in.</En>
<Ur>Sirf ek session khol kar SSH ya firewall settings badalna. Ek ghalti aur aap wapas andar nahi aa sakte.</Ur>
</Tr>

</Bad>
<Good title="A second session, and test first">

<Tr>
<En>Keep one session open, `sshd -t` before reload, allow SSH **before** `ufw enable`, and test a new login before disconnecting.</En>
<Ur>Ek session khula rakhein, reload se pehle `sshd -t`, `ufw enable` se **pehle** SSH ki ijazat, aur disconnect se pehle naya login test karein.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Hardening by hand, once">

<Tr>
<En>Each server is a little different, nobody remembers what was done, and patching stops after month one.</En>
<Ur>Har server thora alag, kisi ko yaad nahi kya kiya, aur pehle mahine ke baad patching band.</Ur>
</Tr>

</Bad>
<Good title="A script, run on every server, re-checked">

<Tr>
<En>One baseline in Git (script or Ansible), automatic updates, and a monthly Lynis run.</En>
<Ur>Git me ek baseline (script ya Ansible), khud kaar updates, aur har mahine Lynis.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Trusting UFW with Docker">

<Tr>
<En>`docker run -p 6379:6379 redis`: Docker writes its own firewall rules **before** UFW's, so Redis is open to the world even though UFW "denies" it.</En>
<Ur>`docker run -p 6379:6379 redis`: Docker apne firewall qaide UFW se **pehle** likhta hai, isliye UFW ke "inkaar" ke bawajood Redis duniya ke liye khula hai.</Ur>
</Tr>

</Bad>
<Good title="Bind to localhost">

```text
docker run -p 127.0.0.1:6379:6379 redis
```

</Good>
</Compare>

<DeepDive title="Real world: a baseline role and a golden image">

A team turns this lesson into an **Ansible role** called `baseline`, applied to every server, and a **golden AMI** built weekly with Packer:

```text
roles/baseline/
  tasks/
    updates.yml          # unattended-upgrades, reboot window
    users.yml            # admin users from a list, SSH keys, locked root
    ssh.yml              # sshd_config.d/10-hardening.conf + validate + reload
    firewall.yml         # ufw rules per server role (web, db, worker)
    sysctl.yml           # /etc/sysctl.d/90-hardening.conf
    services.yml         # disable unneeded services
    logging.yml          # journald persistent, Fluent Bit shipping, auditd rules
    lynis.yml            # weekly Lynis run, report to central storage
```

Results after a quarter: every server has the same configuration; a new server is production-ready in minutes; auditors get a Lynis/CIS report per host; and when a developer's laptop was compromised, the attacker found SSH keys that only worked through the bastion, from the VPN, for one non-root account with narrow sudo, and the login alert fired within a minute.

More pitfalls: disabling SELinux/AppArmor to make an error go away; chasing a perfect Lynis score with risky changes you don't understand; and ignoring the **application**: a perfectly hardened OS running a vulnerable web app with admin credentials in `.env` is still compromised through the app.

</DeepDive>

<DeepDive title="Security lens: how the baseline maps to attacker steps">

Hardening doesn't make a server unbreakable. It makes attacks more expensive, more visible and less damaging, and it removes the easy wins most real attackers rely on.

| Attacker step | Typical technique | Controls from this lesson |
| --- | --- | --- |
| Initial access | SSH brute force, exploit an exposed service | Keys only, restricted port 22, firewall, minimal services, patching |
| Execution | Run a downloaded tool from `/tmp` | `noexec` mounts, AppArmor/SELinux, non-root services |
| Persistence | Cron job, systemd unit, SSH key | File integrity monitoring, auditd rules, regular reviews |
| Privilege escalation | sudo misconfig, setuid binary, kernel exploit | Narrow sudo, setuid baseline, kernel updates, sysctl |
| Defense evasion | Delete logs | Log shipping, alerts on silence |
| Impact | Encrypt or delete data | Off-account immutable backups, tested restores |

(Simplified from MITRE ATT&CK.)

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How would you secure a newly created Linux server?">
Patch it and enable automatic security updates; create named admin accounts with sudo and lock root; configure SSH for keys only with root login disabled and restricted users; apply a default-deny firewall on the host and in the cloud security group; remove or disable unneeded services and bind internal ones to localhost; run apps as unprivileged users with systemd sandboxing; check file permissions and setuid binaries; apply kernel sysctl hardening; keep AppArmor or SELinux enforcing; ship logs centrally with alerts and auditd; set up tested off-host backups; and audit with Lynis or the CIS Benchmark. Automate all of it with configuration management.
</QA>

<QA q="What is the difference between discretionary and mandatory access control?">
In discretionary access control (standard Linux permissions), the owner of a resource decides who may access it, and root bypasses checks. In mandatory access control (SELinux, AppArmor), a system-wide policy defines what each program or label may access, and even the owner or a compromised process cannot override it. MAC limits damage from compromised services.
</QA>

<QA q="Why might UFW rules not protect a Docker container's published port?">
Docker manipulates iptables directly and inserts its own rules for published ports in chains that are evaluated before UFW's rules, so a port published with -p is reachable even if UFW denies it. Fix it by binding published ports to 127.0.0.1 or a private interface, not publishing internal services at all, using cloud security groups, or configuring the DOCKER-USER chain.
</QA>

<QA q="What is a CIS Benchmark?">
A consensus-based, freely available set of configuration recommendations for securing a specific operating system, cloud platform or application, published by the Center for Internet Security. Controls are grouped into levels (Level 1 practical, Level 2 stricter), each with rationale, audit and remediation steps. Tools like OpenSCAP and cloud security posture tools check systems against them.
</QA>

<QA q="If a server is compromised, should you clean it or rebuild it?">
Rebuild it. After preserving evidence (disk snapshot, memory, logs) for investigation, you cannot fully trust any binary or configuration on a compromised host, since attackers may have installed rootkits or persistence you have not found. Provision a fresh server from trusted images and code, restore data from clean backups, rotate all credentials the server had, and fix the original entry point.
</QA>

</DeepDive>

<Terms>
  <Term name="Hardening">Reducing attack surface and limiting impact through secure configuration.</Term>
  <Term name="Attack surface">All the ways an attacker could interact with a system.</Term>

  <Term name="UFW / firewalld / nftables">Host firewall tools on Linux.</Term>
  <Term name="Security group">A cloud provider's virtual firewall around instances.</Term>
  <Term name="sysctl">Interface for setting kernel parameters at runtime.</Term>
  <Term name="AppArmor / SELinux">Mandatory access control systems that confine programs.</Term>
  <Term name="auditd">Linux auditing daemon that records security-relevant events.</Term>
  <Term name="File integrity monitoring">Detecting unexpected changes to files.</Term>
  <Term name="CIS Benchmark">Published secure configuration baseline for a platform.</Term>
  <Term name="Lynis">Open-source security auditing tool for Unix-like systems.</Term>
