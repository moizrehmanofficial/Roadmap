<Callout type="tip" title="In one minute">
The **CPU** (processor) executes instructions — it does the calculating. **RAM** (memory) is fast, temporary workspace holding the programs and data in use right now; it is wiped when the power goes off. **Storage** (SSD/HDD) keeps files permanently but is much slower. Each layer is roughly 100–1000× slower than the one above it, which explains most performance problems: a program is slow because it waits for the CPU (**CPU-bound**), for memory, or for disk/network (**I/O-bound**). When RAM runs out, Linux uses **swap** (slow) or kills a process (**OOM killer**).
</Callout>

## Start from zero

### The three parts every computer has

Your phone, your laptop, a cloud server and a Raspberry Pi all have the same three core parts.

<Callout type="analogy">
A **kitchen**:

- The **CPU** is the **chef** — the one who actually does the work (chopping, mixing, cooking). A chef with more hands (cores) can do several things at once.
- **RAM** is the **counter top** — the ingredients the chef is using right now are laid out here, within easy reach. A bigger counter means more dishes can be prepared at the same time. At closing time the counter is cleared.
- **Storage** is the **storeroom / fridge** — everything is kept there permanently, but fetching something takes much longer than grabbing it from the counter.
</Callout>

When you open an app, it is copied **from storage to RAM**, and the **CPU** runs it from RAM. When you save a file, it goes **from RAM back to storage**.

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **CPU** | Central Processing Unit — the chip that executes instructions | Intel Core i7, AMD EPYC, Apple M3 |
| **Core** | One independent processing unit inside a CPU | "8-core CPU" |
| **Clock speed** | How many steps a core does per second | 3.5 GHz = 3.5 billion per second |
| **RAM** | Fast temporary memory for running programs | 16 GB RAM |
| **Storage** | Permanent memory for files | 512 GB SSD |
| **Volatile** | Loses its content when power is off | RAM is volatile |
| **Latency** | How long one access takes | RAM ≈ 100 ns |
| **Throughput** | How much data per second | SSD ≈ 3 GB/s |

## What is it?

| Part | Job | Speed | Size (typical) | Keeps data without power? |
| --- | --- | --- | --- | --- |
| CPU (and its cache) | Executes instructions | Fastest | KB–MB of cache | No |
| RAM | Holds running programs and their data | Very fast | 8–512 GB | No |
| SSD / NVMe | Stores files permanently | Fast for storage | 256 GB–8 TB | Yes |
| HDD | Stores files permanently | Slow | 1–20 TB | Yes |

## Why does it matter?

- **Choosing servers:** cloud instance types differ by vCPUs and RAM ("t3.small = 2 vCPU, 2 GiB"). Picking wrong wastes money or makes apps slow.
- **Performance problems:** "the server is slow" means one of these resources is exhausted. Knowing which one tells you the fix.
- **Containers:** Docker and Kubernetes set CPU and memory **limits**; a container over its memory limit is killed (exit code 137).
- **Databases:** they are fast when the working data fits in RAM and slow when they must read disk.
- **Security:** secrets live in RAM while in use; some attacks read memory, and some exploit how CPUs work (Spectre, Meltdown).

## When and where do you use it?

| Situation | Resource to look at | Command |
| --- | --- | --- |
| Server feels slow | CPU load | `top`, `uptime` |
| App crashes randomly / exit 137 | RAM | `free -h`, `dmesg` |
| "No space left on device" | Storage | `df -h` |
| Database slow under load | RAM and disk I/O | `iostat`, `vmstat` |
| Choosing a cloud instance | All three | provider pricing pages |

## Concepts one by one

### 1. The CPU and its cores

<Explain>
<What>
The CPU is the chip that executes program instructions: add numbers, compare values, move data, jump to another instruction. Modern CPUs contain several **cores**, each able to run its own stream of instructions.
</What>
<Why>
More cores mean more work at the same time — many web requests, many containers, parallel builds.
</Why>
<When>
Any time software runs.
</When>
<Where>
Laptops (4–16 cores), servers (16–192 cores), cloud instances (measured in **vCPUs**, usually one hardware thread each).
</Where>
<How>
See your cores with `nproc` (Linux) or `lscpu` for details.
</How>
</Explain>

```bash
cores=$(nproc)
(( cores >= 1 )) && echo "This machine has at least 1 CPU core available"
lscpu | grep -E '^(Architecture|CPU\(s\)):' | sed 's/:.*/: …/'
```

```text output
This machine has at least 1 CPU core available
Architecture: …
CPU(s): …
```

On your machine you will see real values, for example `Architecture: x86_64` and `CPU(s): 8`. (`x86_64` is Intel/AMD; `aarch64` is ARM, such as Apple Silicon or AWS Graviton.)

### 2. How the CPU runs instructions

<Explain>
<What>
The CPU repeats a simple loop billions of times per second: **fetch** the next instruction from memory, **decode** what it means, **execute** it.
</What>
<Why>
It explains why everything a program does — even showing one letter — is broken into many tiny steps.
</Why>
<When>
Constantly, while anything runs.
</When>
<Where>
Every processor.
</Where>
<How>
Clock speed (GHz) is how many cycles per second. A 3 GHz core does about 3 billion cycles per second; one simple instruction often takes about one cycle.
</How>
</Explain>

<Callout type="analogy">
A chef following a recipe: **read** the next line (fetch), **understand** it — "chop 2 onions" (decode), **do** it (execute), then read the next line. A faster chef (higher GHz) gets through more lines per minute.
</Callout>

### 3. RAM — the working space

<Explain>
<What>
Random Access Memory: fast memory where running programs and their data are kept. Any byte can be read in about the same short time.
</What>
<Why>
The CPU cannot work directly on files in storage — they are far too slow. Everything being used is first loaded into RAM.
</Why>
<When>
From the moment a program starts until it ends.
</When>
<Where>
Browser tabs, Node.js servers, databases, Docker containers — all use RAM.
</Where>
<How>
`free -h` shows total, used and **available** memory. "available" is what new programs can still use (Linux uses free RAM as disk cache and gives it back when needed).
</How>
</Explain>

```bash
free -h | awk 'NR==1 {print "      " $1, $2, $6} NR==2 {print $1, "(values in your machine)"}'
```

```text output
      total used available
Mem: (values in your machine)
```

A real example output looks like:

```text
               total        used        free      shared  buff/cache   available
Mem:            15Gi       6.1Gi       1.2Gi       410Mi       8.3Gi       8.9Gi
Swap:          2.0Gi          0B       2.0Gi
```

Do not panic about low "free": the 8.3 GiB "buff/cache" is reused automatically. **"available" (8.9 GiB)** is the number that matters.

### 4. Storage — keeping data permanently

<Explain>
<What>
Devices that keep data without power: **HDDs** (spinning magnetic disks), **SATA SSDs** and **NVMe SSDs** (flash chips, much faster).
</What>
<Why>
Your OS, apps, databases and files must survive restarts.
</Why>
<When>
Saving, loading, booting, logging, database writes.
</When>
<Where>
Laptops, servers; in the cloud as **block storage** (AWS EBS, Azure Managed Disks) attached to servers.
</Where>
<How>
`df -h` shows how full each filesystem is; `lsblk` lists disks.
</How>
</Explain>

```bash
df -h / | awk 'NR==1 {print $1, $2, $3, $4, $5} NR==2 {print "/ is mounted from a device with", ($5 ~ /%$/ ? "a usage percentage" : "?")}'
```

```text output
Filesystem Size Used Avail Use%
/ is mounted from a device with a usage percentage
```

| Type | Random reads per second (roughly) | Typical use |
| --- | --- | --- |
| HDD | ~100–200 | Cheap bulk storage, backups |
| SATA SSD | ~50,000–100,000 | Laptops, general servers |
| NVMe SSD | ~500,000+ | Databases, high-performance servers |

### 5. The memory hierarchy

<Explain>
<What>
A ladder of storage layers: CPU registers → CPU cache (L1/L2/L3) → RAM → SSD → HDD → network. Each step down is bigger and cheaper but much slower.
</What>
<Why>
It explains why caching works and why reading from disk or the network is "slow" for a computer.
</Why>
<When>
Every performance discussion: caching, database tuning, choosing instance types.
</When>
<Where>
CPU design, Redis caches, CDNs, database buffer pools — all are "keep the hot data in a faster layer".
</Where>
<How>
Learn the rough numbers below. Scale them to human time to feel the difference.
</How>
</Explain>

| Layer | Typical latency | If 1 CPU cycle were 1 second… |
| --- | --- | --- |
| CPU register | ~0.3 ns | 1 second |
| L1 cache | ~1 ns | 3 seconds |
| L3 cache | ~10 ns | 30 seconds |
| RAM | ~100 ns | 5 minutes |
| NVMe SSD read | ~20–100 µs | 1–4 days |
| HDD seek | ~5–10 ms | 6–12 months |
| Network round trip across the world | ~150 ms | about 15 years |

<Callout type="analogy">
Getting something from the CPU cache is like picking up a pen from your desk. RAM is walking to the next room. An SSD is driving to another city. An HDD is a trip to another country. A request to a server on another continent is like sending a letter by ship and waiting for the reply.
</Callout>

### 6. What happens when you run a program

<Explain>
<What>
The sequence of events from double-click (or typing a command) to the program running.
</What>
<Why>
It ties the three parts together and explains "slow startup" (disk) vs "slow while running" (CPU or RAM).
</Why>
<When>
Every program start: `node server.js`, opening a browser, starting a container.
</When>
<Where>
Every operating system.
</Where>
<How>
1) The OS reads the program file from **storage**. 2) It loads the code and data into **RAM** and creates a **process**. 3) The **CPU** executes the instructions from RAM, keeping the hottest parts in its **cache**. 4) Files the program opens are read from storage into RAM as needed. 5) When the process ends, its RAM is freed.
</How>
</Explain>

### 7. When RAM runs out: swap and the OOM killer

<Explain>
<What>
If programs need more RAM than exists, Linux first moves rarely used memory to **swap** (a part of the disk). If that is not enough, the **OOM (Out Of Memory) killer** terminates a process to save the system.
</What>
<Why>
Swap on disk is thousands of times slower than RAM — the server becomes extremely slow ("thrashing"). An OOM kill makes an app or database disappear suddenly.
</Why>
<When>
Memory leaks, too many workers, a big query, a container with a low memory limit.
</When>
<Where>
Servers, Docker containers (`OOMKilled`, exit code 137), Kubernetes pods.
</Where>
<How>
Check `free -h` for swap use, and the kernel log for kills: `dmesg -T | grep -i "killed process"` or `journalctl -k | grep -i oom`.
</How>
</Explain>

```text
$ journalctl -k | grep -i "killed process"
Nov 10 03:14:07 web-1 kernel: Out of memory: Killed process 2314 (node) total-vm:4.1GB, anon-rss:1.9GB
```

That single line explains "my Node.js app restarted at 3 a.m. for no reason".

### 8. CPU-bound vs I/O-bound

<Explain>
<What>
A task is **CPU-bound** if its speed is limited by calculation (image resizing, encryption, compiling). It is **I/O-bound** if it mostly **waits** for disk, database or network (most web apps).
</What>
<Why>
The fix depends on the type. Adding CPUs does not help an app waiting for a slow database; caching does not help an app busy hashing passwords.
</Why>
<When>
Diagnosing slowness and choosing architecture.
</When>
<Where>
Web servers (mostly I/O-bound), video processing (CPU-bound), Node.js (great for I/O-bound, careful with CPU-bound work).
</Where>
<How>
In `top`: high `%us`/`%sy` CPU = CPU-bound; high `%wa` (I/O wait) = waiting for disk. `time command` shows "real" (wall clock) vs "user+sys" (CPU actually used).
</How>
</Explain>

```bash
cpu_task() { local i s=0; for ((i = 0; i < 200000; i++)); do ((s += i)); done; }
io_task()  { sleep 1; }

start=$SECONDS; cpu_task; echo "CPU task kept the CPU busy the whole time"
TIMEFORMAT='real=%R user=%U'
{ time io_task; } 2>&1 | awk -F'[= ]' '{ printf "I/O-like task: real %.0fs, CPU used ~%.0fs (it was waiting)\n", $2, $4 }'
```

```text output
CPU task kept the CPU busy the whole time
I/O-like task: real 1s, CPU used ~0s (it was waiting)
```

The waiting task took 1 second of wall-clock time but used almost **no** CPU — the shape of an I/O-bound program.

## Hands-on

Run these on any Linux machine (or a cloud VM, or WSL on Windows) and look at your own numbers:

```bash
nproc                               # number of CPU cores
lscpu | head -15                    # CPU model, architecture, cache sizes
free -h                             # RAM and swap
df -h                               # disk usage per filesystem
lsblk                               # disks and partitions
uptime                              # load average over 1, 5, 15 minutes
top -b -n 1 | head -15              # busiest processes (press q to quit interactive top)
cat /proc/meminfo | head -5         # the raw memory numbers the tools read
```

**Load average** in `uptime` (e.g. `0.52, 0.71, 0.66`) is the average number of processes running or waiting for CPU. Compare it with `nproc`: on a 4-core machine, a load of 4 means fully busy; 8 means work is queueing.

## Real-world example

An Express API on a 2 vCPU / 2 GiB VPS starts timing out every afternoon. A structured investigation:

1. **CPU:** `top` shows Node at 100% of one core. Profiling finds a PDF report being generated synchronously inside the request — CPU-bound work blocking the event loop. Fix: move it to a background job queue (BullMQ) handled by a separate worker.
2. **Memory:** `free -h` shows available memory falling all day until the process restarts. A cache stored in a plain object grows forever. Fix: bound it (LRU) or move it to Redis.
3. **Disk:** `df -h` shows `/` at 97%. Logs were never rotated. Fix: log rotation, and ship logs to a central system.
4. **Database:** PostgreSQL reads from disk for every request because a missing index forces a full table scan. Fix: add the index so the working set fits in RAM.

None of these needed a bigger server. They needed someone who knew which resource was the bottleneck.

## Common mistakes

- **"Linux is using all my RAM!"** It is using free RAM as file cache, and it gives it back instantly. Look at the `available` column.
- **Scaling up before measuring.** A bigger instance rarely fixes a memory leak or a missing index; it only delays it.
- **No memory limits on containers.** One leaking container can starve every other workload on the node.
- **Ignoring CPU architecture.** An image built only for `amd64` fails on ARM (`exec format error`). Use multi-platform builds.
- **Storing important data on ephemeral storage** (container filesystem, instance store). It disappears on restart.

## Security lens

<Callout type="security">
CPU, RAM and disk are where attacks become visible — and where secrets leak if you are careless.
</Callout>

- **Resource exhaustion is a denial-of-service attack.** An attacker sends requests that are cheap to send but expensive to process: huge JSON bodies (RAM), regex that backtracks forever (CPU — "ReDoS"), or uploads that fill the disk. Defences: request size limits, timeouts, rate limiting, resource limits per container.
- **Cryptojacking:** compromised servers and containers are often used to mine cryptocurrency. The first symptom is sustained 100% CPU. Unexplained CPU on a node is a security signal, not just a performance one.
- **Secrets in memory:** passwords and keys sit in RAM while in use. Memory dumps, core dumps and swap files can contain them. Restrict access to dumps and avoid logging objects that contain secrets.
- **Deleted is not erased:** deleting a file removes its directory entry; the data may remain on disk until overwritten. Cloud volumes and old disks must be encrypted or securely wiped.
- **Hardware side channels:** Spectre and Meltdown (2018) showed that CPU speed optimisations such as speculative execution can leak memory between processes. This is why cloud providers patched hypervisors and why kernel updates matter.

## Interview questions

<QA q="What is the difference between RAM and storage?">
RAM is fast, volatile memory that holds running programs and their data; its contents vanish when power is lost. Storage (SSD/HDD) is slower but persistent, holding files, the operating system and databases. Programs are loaded from storage into RAM to run, and only what is written back to storage survives a restart.
</QA>

<QA q="What is a vCPU in AWS?">
On most EC2 instance types a vCPU is one hardware thread of a physical core, because hyper-threading exposes two threads per core. So 2 vCPUs is usually one physical core with two threads. Burstable instances such as t3 additionally limit sustained CPU use through CPU credits.
</QA>

<QA q="A container keeps restarting with exit code 137. What does that mean?">
Exit code 137 means the process was killed with SIGKILL (128 + 9). In containers this is most often the OOM killer, because the container exceeded its memory limit; `kubectl describe pod` shows `OOMKilled`. Check memory usage and leaks, then fix the leak or raise the limit with evidence.
</QA>

<QA q="Why is caching so effective?">
Each layer of the memory hierarchy is orders of magnitude faster than the one below it. Programs tend to reuse the same data (locality), so keeping frequently used data in a faster layer — CPU cache, RAM, Redis, a CDN — avoids slow trips to disk or across the network for most requests.
</QA>

<QA q="What is the difference between CPU-bound and I/O-bound work?">
CPU-bound work is limited by computation (hashing, image processing, compression); adding cores or optimising the algorithm helps. I/O-bound work spends most of its time waiting for disk or network (database queries, API calls); concurrency, caching and faster I/O help. Most web APIs are I/O-bound, which is why a single-threaded event loop like Node.js scales well — until CPU-bound work blocks it.
</QA>

## Key terms

<Terms>
  <Term name="CPU">The processor; executes instructions.</Term>
  <Term name="Core">An independent processing unit inside a CPU.</Term>
  <Term name="vCPU">A virtual CPU sold by cloud providers; usually one hardware thread.</Term>
  <Term name="Register">Tiny, fastest storage inside the CPU.</Term>
  <Term name="Cache (CPU)">Small fast memory (L1/L2/L3) holding recently used data close to the CPU.</Term>
  <Term name="RAM">Volatile main memory for running programs.</Term>
  <Term name="Swap">Disk space used as overflow memory when RAM is full.</Term>
  <Term name="OOM killer">The Linux mechanism that kills a process when memory runs out.</Term>
  <Term name="SSD / NVMe">Flash storage; NVMe connects over PCIe and is the fastest common type.</Term>
  <Term name="Architecture">The instruction set a CPU understands, e.g. x86-64 or ARM64.</Term>
</Terms>
