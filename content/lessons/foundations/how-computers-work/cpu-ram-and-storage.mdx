<BigIdea>
<Tr>
<En>
Every computer has three main parts: the **CPU** does the work, **RAM** holds what's being used **right now**, and **storage** keeps everything **permanently**, even when the power is off.
</En>
<Ur>
Har computer ke teen ahem hisse hote hain: **CPU** kaam karta hai, **RAM** wo cheezen rakhti hai jo **abhi** istemal ho rahi hain, aur **storage** sab kuch **hamesha ke liye** rakhti hai, bijli band hone par bhi.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **CPU** (processor): the "brain" that follows instructions: add numbers, compare things, move data. Billions of tiny steps every second.
- **RAM** (memory): fast, temporary space for the apps and files you have **open right now**. It's **wiped** when the computer turns off.
- **Storage** (SSD or hard disk): where files, apps and the operating system are **kept forever**. Much slower than RAM.

</En>
<Ur>

- **CPU** (processor): wo "dimagh" jo hidayaat par chalta hai: numbers jorna, cheezon ka mawazna, data idhar udhar karna. Har second arbon chhote qadam.
- **RAM** (memory): tez, aarzi (temporary) jagah un apps aur files ke liye jo **abhi khuli** hain. Computer band hote hi ye **saaf** ho jati hai.
- **Storage** (SSD ya hard disk): jahan files, apps aur operating system **hamesha ke liye** rakhe jate hain. RAM se kaafi slow.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

When a computer or server is **slow**, one of these three is usually the reason: the CPU is too busy, RAM is full, or the disk is slow or full.

Knowing which one helps you fix the real problem, instead of just buying a bigger (and more expensive) server.

</En>
<Ur>

Jab computer ya server **slow** ho, to aam tor par in teeno me se koi ek wajah hoti hai: CPU bohot masroof hai, RAM bhar gayi hai, ya disk slow ya full hai.

Ye pata ho ke kaun sa hai, to aap asal masla theek kar sakte hain, bajaye seedha bara (aur mehanga) server khareedne ke.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- buying a laptop or choosing a cloud server ("2 vCPU, 4 GB RAM")
- an app is slow or keeps crashing
- you see "No space left on device"
- setting limits for Docker containers

</En>
<Ur>

- laptop khareedte ya cloud server chunte waqt ("2 vCPU, 4 GB RAM")
- jab app slow ho ya baar baar crash ho
- jab "No space left on device" aaye
- Docker containers ki limits set karte waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

When you open an app:

1. it's copied **from storage into RAM**,
2. the **CPU** runs it from RAM,
3. when you save, your work goes **from RAM back to storage**.

Anything you didn't save is lost when the power goes off, because RAM forgets everything.

</En>
<Ur>

Jab aap koi app kholte hain:

1. wo **storage se RAM me** copy hoti hai,
2. **CPU** use RAM se chalata hai,
3. jab aap save karte hain, kaam **RAM se wapas storage me** jata hai.

Jo save nahi kiya, wo bijli jaate hi chala jata hai, kyunke RAM sab kuch bhool jati hai.

</Ur>
</Tr>
</How>
</Glance>

<Walkthrough>

<Step title="The CPU: the worker">

<Tr>
<En>

The **CPU** follows instructions one tiny step at a time: "add these two numbers", "is this bigger than that?", "move this data there". It does **billions** of these steps every second.

Modern CPUs have several **cores**. Each core is like a separate worker, so an 8-core CPU can work on 8 things at the same time: many website visitors, many apps, many containers.

</En>
<Ur>

**CPU** hidayaat ko ek ek chhote qadam me chalata hai: "ye do numbers jor do", "kya ye us se bara hai?", "ye data wahan le jao". Ye har second **arbon** aise qadam uthata hai.

Aaj kal ke CPUs me kai **cores** hote hain. Har core ek alag kaam karne wale jaisa hai, to 8-core CPU ek waqt me 8 kaam kar sakta hai: website ke kai visitors, kai apps, kai containers.

</Ur>
</Tr>

```bash
cores=$(nproc)
(( cores >= 1 )) && echo "This machine has at least 1 CPU core available"
lscpu | grep -E '^(Architecture|CPU\(s\)):' | sed 's/:.*/: …/'
```

```text output
This machine has at least 1 CPU core available
Architecture: …
CPU(s): …
```

<Happened>
<Tr>
<En>

- `nproc` counts the CPU cores. `lscpu` shows details about the CPU.
- The real values are hidden with `…` here because they're different on every machine. On yours you'll see something like `Architecture: x86_64` and `CPU(s): 8`.
- `x86_64` means an Intel or AMD chip. `aarch64` means an ARM chip, like Apple Silicon Macs or AWS Graviton servers.

</En>
<Ur>

- `nproc` CPU cores ginta hai. `lscpu` CPU ki tafseelat dikhata hai.
- Asal values yahan `…` se chhupa di gayi hain kyunke har machine par alag hoti hain. Aap ki machine par kuch aisa aayega: `Architecture: x86_64` aur `CPU(s): 8`.
- `x86_64` ka matlab Intel ya AMD chip. `aarch64` ka matlab ARM chip, jaise Apple Silicon Macs ya AWS Graviton servers.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="RAM: the working space">

<Tr>
<En>

The CPU **can't** work directly with files on the disk; the disk is far too slow. So everything being used is first loaded into **RAM**: your open browser tabs, a running server, a database's busiest data.

RAM is **fast but temporary**. Turn the power off and it's empty again.

</En>
<Ur>

CPU disk par rakhi files ke saath **seedha** kaam **nahi** kar sakta; disk bohot slow hai. Isliye jo cheez istemal ho rahi ho, pehle **RAM** me load hoti hai: aap ke khule browser tabs, chalta hua server, database ka sab se zyada istemal hone wala data.

RAM **tez lekin aarzi** hai. Bijli band karein, to wo phir se khaali ho jati hai.

</Ur>
</Tr>

```bash
free -h | awk 'NR==1 {print "      " $1, $2, $6} NR==2 {print $1, "(values in your machine)"}'
```

```text output
      total used available
Mem: (values in your machine)
```

<Tr>
<En>
On a real machine, `free -h` shows something like this:
</En>
<Ur>
Asal machine par `free -h` kuch aisa dikhata hai:
</Ur>
</Tr>

```text
               total        used        free      shared  buff/cache   available
Mem:            15Gi       6.1Gi       1.2Gi       410Mi       8.3Gi       8.9Gi
Swap:          2.0Gi          0B       2.0Gi
```

<Happened>
<Tr>
<En>

- **total**: all the RAM in the machine (15 GiB).
- **free** looks low (1.2 GiB), but don't panic. Linux uses spare RAM to remember recently used files (**buff/cache**, 8.3 GiB) and gives it back the moment an app needs it.
- **available** (8.9 GiB) is the number that matters: how much RAM new programs can still use.

</En>
<Ur>

- **total**: machine ki poori RAM (15 GiB).
- **free** kam lagta hai (1.2 GiB), lekin ghabrayen nahi. Linux faltu RAM ko haal hi me istemal hui files yaad rakhne ke liye istemal karta hai (**buff/cache**, 8.3 GiB) aur app ko zaroorat parte hi wapas de deta hai.
- **available** (8.9 GiB) asal number hai: naye programs abhi kitni RAM istemal kar sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Storage: keeping things forever">

<Tr>
<En>

**Storage** keeps your data when the power is off: the operating system, apps, photos, databases. There are two common kinds:

- **HDD** (hard disk drive): a spinning metal disk with a moving arm. Cheap and big, but slow.
- **SSD** (solid-state drive): memory chips with no moving parts. Much faster. **NVMe** SSDs are the fastest kind.

</En>
<Ur>

**Storage** aap ka data bijli band hone par bhi rakhti hai: operating system, apps, photos, databases. Do aam qisme hain:

- **HDD** (hard disk drive): ghoomti hui dhaat ki disk aur hilne wala baazu. Sasti aur bari, lekin slow.
- **SSD** (solid-state drive): memory chips, koi hilne wala hissa nahi. Kaafi tez. **NVMe** SSDs sab se tez qisam hain.

</Ur>
</Tr>

```bash
df -h / | awk 'NR==1 {print $1, $2, $3, $4, $5} NR==2 {print "/ is mounted from a device with", ($5 ~ /%$/ ? "a usage percentage" : "?")}'
```

```text output
Filesystem Size Used Avail Use%
/ is mounted from a device with a usage percentage
```

<Happened>
<Tr>
<En>

- `df -h` shows each disk's **Size**, how much is **Used**, how much is **Avail**able, and the **Use%**.
- If `Use%` reaches 100%, apps start failing with "No space left on device". Old log files are a very common cause.

</En>
<Ur>

- `df -h` har disk ka **Size**, kitna **Used** hai, kitna **Avail**able hai, aur **Use%** dikhata hai.
- Agar `Use%` 100% tak pohanch jaye, to apps "No space left on device" ke saath fail hona shuru ho jati hain. Purani log files is ki bohot aam wajah hain.

</Ur>
</Tr>
</Happened>

| Type | How many random reads per second (roughly) | Used for |
| --- | --- | --- |
| HDD | ~100–200 | Cheap bulk storage, backups |
| SATA SSD | ~50,000–100,000 | Laptops, normal servers |
| NVMe SSD | ~500,000+ | Databases, fast servers |

</Step>

<Step title="The speed ladder: why some things feel slow">

<Tr>
<En>

Every place data can live is on a **ladder**. Each step down is **bigger and cheaper, but much slower**.

Computer times are tiny (nanoseconds), so let's pretend one CPU step takes **1 second** and see how long everything else would feel:

</En>
<Ur>

Data jahan jahan reh sakta hai, wo sab ek **seerhi (ladder)** par hain. Har neeche wala qadam **bara aur sasta, lekin kaafi slow** hota hai.

Computer ke waqt bohot chhote hote hain (nanoseconds), to farz karein CPU ka ek qadam **1 second** leta hai, aur dekhein baqi sab kitna lagega:

</Ur>
</Tr>

| Place | Real time | If 1 CPU step were 1 second… |
| --- | --- | --- |
| Inside the CPU (register) | ~0.3 ns | 1 second |
| CPU cache (L1) | ~1 ns | 3 seconds |
| CPU cache (L3) | ~10 ns | 30 seconds |
| RAM | ~100 ns | 5 minutes |
| NVMe SSD | ~20–100 µs | 1–4 days |
| Hard disk (HDD) | ~5–10 ms | 6–12 months |
| A server on another continent | ~150 ms | about 15 years |

<Callout type="analogy">
<Tr>
<En>
The CPU cache is a pen **on your desk**. RAM is **the next room**. An SSD is **another city**. A hard disk is **another country**. A server on another continent is like **sending a letter by ship** and waiting for the reply.
</En>
<Ur>
CPU cache **aap ki mez par rakha pen** hai. RAM **agla kamra** hai. SSD **doosra shehar** hai. Hard disk **doosra mulk** hai. Doosre continent ka server aisa hai jaise **jahaz se khat bhejna** aur jawab ka intezar karna.
</Ur>
</Tr>
</Callout>

<Tr>
<En>
This is why **caching** works so well: keep the data you use most in a **faster** place (RAM, Redis, a CDN) so you rarely make the slow trip.
</En>
<Ur>
Isi liye **caching** itni kaam aati hai: jo data sab se zyada istemal hota hai use **tez** jagah (RAM, Redis, CDN) par rakho, taake slow safar kam se kam karna pare.
</Ur>
</Tr>

</Step>

<Step title="When RAM runs out">

<Tr>
<En>

If programs need **more RAM than the machine has**, Linux does two things:

1. **Swap:** it moves rarely used memory onto the disk. But the disk is thousands of times slower, so everything becomes **painfully slow**.
2. **OOM killer:** if that's still not enough, Linux **kills** a program to save the rest. ("OOM" = Out Of Memory.)

That's why an app can suddenly "restart for no reason" at 3 a.m.

</En>
<Ur>

Agar programs ko machine se **zyada RAM** chahiye ho, to Linux do kaam karta hai:

1. **Swap:** kam istemal hone wali memory ko disk par daal deta hai. Lekin disk hazaron guna slow hai, isliye sab kuch **bohot slow** ho jata hai.
2. **OOM killer:** phir bhi kaafi na ho, to Linux baqi sab ko bachane ke liye ek program **band (kill)** kar deta hai. ("OOM" = Out Of Memory.)

Isi wajah se koi app raat 3 baje achanak "bina wajah restart" ho sakti hai.

</Ur>
</Tr>

```text
$ journalctl -k | grep -i "killed process"
Nov 10 03:14:07 web-1 kernel: Out of memory: Killed process 2314 (node) total-vm:4.1GB, anon-rss:1.9GB
```

<Happened>
<Tr>
<En>

- This line in the system log says: at 03:14, memory ran out and Linux **killed** the `node` program, which was using about 1.9 GB.
- In Docker and Kubernetes the same thing shows as **`OOMKilled`** or **exit code 137**.
- Fix: find what's using too much memory (often a memory leak), then fix it, or give the app more memory based on real measurements.

</En>
<Ur>

- System log ki ye line kehti hai: 03:14 par memory khatam ho gayi aur Linux ne `node` program ko **band (kill)** kar diya, jo taqreeban 1.9 GB istemal kar raha tha.
- Docker aur Kubernetes me yahi cheez **`OOMKilled`** ya **exit code 137** ki shakal me dikhti hai.
- Hal: dhoondein ke zyada memory kaun kha raha hai (aksar memory leak), use theek karein, ya asal naap tol ki buniyad par app ko zyada memory dein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Busy working, or busy waiting?">

<Tr>
<En>

A slow program is usually slow for one of two reasons:

- **CPU-bound:** it's busy **calculating** (resizing images, encrypting, compressing). A faster or bigger CPU helps.
- **I/O-bound:** it's mostly **waiting** for something else: the disk, a database, another website. Most web apps are like this. A faster CPU won't help; caching or a faster database will.

"I/O" means Input/Output: reading and writing to disks and networks.

</En>
<Ur>

Slow program aam tor par do me se ek wajah se slow hota hai:

- **CPU-bound:** wo **hisaab kitaab** me masroof hai (images chhoti bari karna, encrypt karna, compress karna). Tez ya bara CPU madad karta hai.
- **I/O-bound:** wo zyada tar kisi aur cheez ka **intezar** kar raha hai: disk, database, koi aur website. Zyada tar web apps aisi hoti hain. Tez CPU se faida nahi; caching ya tez database se hoga.

"I/O" ka matlab Input/Output: disks aur networks se parhna likhna.

</Ur>
</Tr>

```bash
cpu_task() { local i s=0; for ((i = 0; i < 200000; i++)); do ((s += i)); done; }
io_task()  { sleep 1; }

start=$SECONDS; cpu_task; echo "CPU task kept the CPU busy the whole time"
TIMEFORMAT='real=%R user=%U'
{ time io_task; } 2>&1 | awk -F'[= ]' '{ printf "I/O-like task: real %.0fs, CPU used ~%.0fs (it was waiting)\n", $2, $4 }'
```

```text output
CPU task kept the CPU busy the whole time
I/O-like task: real 1s, CPU used ~0s (it was waiting)
```

<Happened>
<Tr>
<En>

- `cpu_task` adds numbers 200,000 times: pure calculating.
- `io_task` just **waits** 1 second, like waiting for a slow database.
- `time` shows the waiting task took **1 second** on the clock, but used almost **no** CPU. That's what an I/O-bound program looks like.

</En>
<Ur>

- `cpu_task` 200,000 dafa numbers jorta hai: sirf hisaab.
- `io_task` bas 1 second **intezar** karta hai, jaise slow database ka intezar.
- `time` dikhata hai ke intezar wale kaam ne ghari par **1 second** liya, lekin CPU taqreeban **bilkul** istemal nahi kiya. I/O-bound program aisa hi dikhta hai.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="'Linux is using all my RAM!'">

<Tr>
<En>Looking at the **free** column and panicking because it's low.</En>
<Ur>**free** column dekh kar ghabra jana ke wo kam hai.</Ur>
</Tr>

</Bad>
<Good title="Look at 'available'">

<Tr>
<En>Linux uses spare RAM as a file cache and hands it back instantly. **available** is the real number.</En>
<Ur>Linux faltu RAM ko file cache ke liye istemal karta hai aur foran wapas de deta hai. **available** asal number hai.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Buying a bigger server first">

<Tr>
<En>A bigger server rarely fixes a memory leak, a full disk or a slow database query. It only delays the problem and costs more.</En>
<Ur>Bara server memory leak, bhari hui disk ya slow database query ko kam hi theek karta hai. Ye sirf masle ko aage karta hai aur mehanga parta hai.</Ur>
</Tr>

</Bad>
<Good title="Measure first">

<Tr>
<En>Check CPU (`top`), memory (`free -h`) and disk (`df -h`) to find the real bottleneck, then fix that.</En>
<Ur>Pehle CPU (`top`), memory (`free -h`) aur disk (`df -h`) check karein, asal rukawat dhoondein, phir use theek karein.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Containers with no memory limit">

<Tr>
<En>One leaking container can eat all the RAM and crash everything else on the server.</En>
<Ur>Ek leak karne wala container sari RAM kha kar server par baqi sab ko crash kar sakta hai.</Ur>
</Tr>

</Bad>
<Good title="Set limits">

<Tr>
<En>Give every container a memory limit, so a problem stays inside one container.</En>
<Ur>Har container ki memory limit set karein, taake masla ek hi container tak rahe.</Ur>
</Tr>

</Good>
</Compare>

<Tr>
<En>

</En>
<Ur>

1. **RAM**: exit code 137 ka aam matlab hai memory khatam hone par OOM killer ne use band kar diya.
2. **Storage**: disk bhar gayi hai.
3. **CPU**: PDF banana bhaari hisaab hai (CPU-bound). Isay background worker me bhej dein.

</Ur>

<DeepDive title="How the CPU runs instructions: fetch, decode, execute">

The CPU repeats a simple loop billions of times per second: **fetch** the next instruction from memory, **decode** what it means, **execute** it. Clock speed (GHz) is how many cycles per second: a 3 GHz core does about 3 billion cycles per second, and one simple instruction often takes about one cycle.

Think of a chef following a recipe: **read** the next line (fetch), **understand** it, "chop 2 onions" (decode), **do** it (execute), then read the next line. A faster chef (higher GHz) gets through more lines per minute.

</DeepDive>

<DeepDive title="What happens when you start a program">

1. The OS reads the program file from **storage**.
2. It loads the code and data into **RAM** and creates a **process**.
3. The **CPU** executes the instructions from RAM, keeping the hottest parts in its **cache**.
4. Files the program opens are read from storage into RAM as needed.
5. When the process ends, its RAM is freed.

This explains "slow startup" (reading from disk) vs "slow while running" (CPU or RAM).

</DeepDive>

<DeepDive title="More commands for your own machine">

```bash
nproc                               # number of CPU cores
lscpu | head -15                    # CPU model, architecture, cache sizes
free -h                             # RAM and swap
df -h                               # disk usage per filesystem
lsblk                               # disks and partitions
uptime                              # load average over 1, 5, 15 minutes
top -b -n 1 | head -15              # busiest processes (press q to quit interactive top)
cat /proc/meminfo | head -5         # the raw memory numbers the tools read
```

**Load average** in `uptime` (e.g. `0.52, 0.71, 0.66`) is the average number of processes running or waiting for CPU. Compare it with `nproc`: on a 4-core machine, a load of 4 means fully busy; 8 means work is queueing.

</DeepDive>

<DeepDive title="Real world: a slow API that didn't need a bigger server">

An Express API on a 2 vCPU / 2 GiB server starts timing out every afternoon. A structured investigation:

1. **CPU:** `top` shows Node at 100% of one core. A PDF report is being generated inside the request: CPU-bound work blocking the event loop. Fix: move it to a background job queue (BullMQ) handled by a separate worker.
2. **Memory:** `free -h` shows available memory falling all day until the process restarts. A cache stored in a plain object grows forever. Fix: limit it (LRU) or move it to Redis.
3. **Disk:** `df -h` shows `/` at 97%. Logs were never rotated. Fix: log rotation, and ship logs to a central system.
4. **Database:** PostgreSQL reads from disk for every request because a missing index forces a full table scan. Fix: add the index so the working data fits in RAM.

None of these needed a bigger server. They needed someone who knew which resource was the bottleneck.

</DeepDive>

<DeepDive title="Security lens">

- **Resource exhaustion is a denial-of-service attack.** An attacker sends requests that are cheap to send but expensive to handle: huge JSON bodies (RAM), regex that backtracks forever (CPU, "ReDoS"), or uploads that fill the disk. Defences: request size limits, timeouts, rate limiting, resource limits per container.
- **Cryptojacking:** hacked servers and containers are often used to mine cryptocurrency. The first symptom is constant 100% CPU. Unexplained CPU use is a security signal, not just a performance one.
- **Secrets in memory:** passwords and keys sit in RAM while in use. Memory dumps, core dumps and swap files can contain them. Restrict access to dumps and never log objects containing secrets.
- **Deleted is not erased:** deleting a file removes its directory entry; the data may stay on disk until overwritten. Encrypt disks and wipe old ones properly.
- **Hardware side channels:** Spectre and Meltdown (2018) showed that CPU speed tricks like speculative execution can leak memory between processes. That's why cloud providers patched their systems and why kernel updates matter.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between RAM and storage?">
RAM is fast, volatile memory that holds running programs and their data; its contents vanish when power is lost. Storage (SSD/HDD) is slower but persistent, holding files, the operating system and databases. Programs are loaded from storage into RAM to run, and only what is written back to storage survives a restart.
</QA>

<QA q="What is a vCPU in AWS?">
On most EC2 instance types a vCPU is one hardware thread of a physical core, because hyper-threading exposes two threads per core. So 2 vCPUs is usually one physical core with two threads. Burstable instances such as t3 also limit sustained CPU use through CPU credits.
</QA>

<QA q="A container keeps restarting with exit code 137. What does that mean?">
Exit code 137 means the process was killed with SIGKILL (128 + 9). In containers this is most often the OOM killer, because the container went over its memory limit; kubectl describe pod shows OOMKilled. Check memory usage and leaks, then fix the leak or raise the limit with evidence.
</QA>

<QA q="Why is caching so effective?">
Each layer of the memory hierarchy is orders of magnitude faster than the one below it. Programs tend to reuse the same data (locality), so keeping frequently used data in a faster layer (CPU cache, RAM, Redis, a CDN) avoids slow trips to disk or across the network for most requests.
</QA>

<QA q="What is the difference between CPU-bound and I/O-bound work?">
CPU-bound work is limited by computation (hashing, image processing, compression); more cores or a better algorithm help. I/O-bound work spends most of its time waiting for disk or network (database queries, API calls); concurrency, caching and faster I/O help. Most web APIs are I/O-bound, which is why a single-threaded event loop like Node.js scales well, until CPU-bound work blocks it.
</QA>
