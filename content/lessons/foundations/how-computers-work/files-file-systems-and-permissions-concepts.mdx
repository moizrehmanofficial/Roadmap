<BigIdea>
<Tr>
<En>
A **file** is just bytes plus a label of information about them. **Folders** organise files into a tree, a **path** is the address of a file in that tree, and **permissions** are the rules that decide who may read it, change it or run it.
</En>
<Ur>
**File** sirf bytes hain, saath un ke baare me maloomat ka ek label. **Folders** files ko ek darakht (tree) me tarteeb dete hain, **path** us tree me file ka pata hai, aur **permissions** wo qaide hain jo tay karte hain ke kaun use parh, badal ya chala sakta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **File**: content (bytes) + **metadata** (size, owner, permissions, dates).
- **Folder** (directory): a list of names that point to files.
- **Path**: the address of a file, folder by folder, like `/home/alex/notes.txt`.
- **File system**: the system that organises files on a disk (ext4 on Linux, NTFS on Windows, APFS on Mac).
- **Permissions**: who can **read**, **write** (change) or **execute** (run) a file.

</En>
<Ur>

- **File**: content (bytes) + **metadata** (size, maalik, permissions, tareekhen).
- **Folder** (directory): naamon ki list jo files ki taraf ishara karti hai.
- **Path**: file ka pata, folder dar folder, jaise `/home/alex/notes.txt`.
- **File system**: wo nizaam jo disk par files tarteeb deta hai (Linux par ext4, Windows par NTFS, Mac par APFS).
- **Permissions**: kaun file ko **read** (parh), **write** (badal) ya **execute** (chala) sakta hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

The most common errors when you put an app on a server are about files:

- `No such file or directory` (wrong path)
- `Permission denied` (wrong owner or permissions)
- "disk full"

Wrong permissions are also one of the most common ways servers get hacked.

</En>
<Ur>

Jab aap app server par lagate hain to sab se aam errors files ke baare me hote hain:

- `No such file or directory` (ghalat path)
- `Permission denied` (ghalat maalik ya permissions)
- "disk full"

Ghalat permissions servers hack hone ke sab se aam tareeqon me se bhi ek hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- running commands in a Linux terminal
- deploying a website to a server
- fixing "Permission denied" errors
- saving user uploads
- working with Docker or cloud storage

</En>
<Ur>

- Linux terminal me commands chalate waqt
- website server par deploy karte waqt
- "Permission denied" errors theek karte waqt
- users ki uploads save karte waqt
- Docker ya cloud storage ke saath kaam karte waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Every time a program opens a file, the operating system:

1. follows the **path** to find the file
2. checks **who** is asking
3. checks the **permissions**
4. allows or blocks it

</En>
<Ur>

Jab bhi koi program file kholta hai, operating system:

1. **path** follow kar ke file dhoondta hai
2. check karta hai ke **kaun** maang raha hai
3. **permissions** check karta hai
4. ijazat deta hai ya rok deta hai

</Ur>
</Tr>
</How>
</Glance>

## Learn it step by step

<Walkthrough>

<Step title="A file is content plus metadata">

<Tr>
<En>

The content of a file is just bytes. Besides that, the operating system keeps a "label" for it: size, type, owner, permissions and dates. The `stat` command shows that label.

Funny detail: the file's **name** is not stored inside the file. It's stored in the **folder** that contains it.

</En>
<Ur>

File ka content sirf bytes hai. Is ke ilawa operating system us ka ek "label" rakhta hai: size, type, maalik, permissions aur tareekhen. `stat` command wo label dikhati hai.

Dilchasp baat: file ka **naam** file ke andar save nahi hota. Wo us **folder** me save hota hai jis me file hai.

</Ur>
</Tr>

```bash
printf 'hello\n' > note.txt
stat -c 'name=%n size=%s bytes type=%F permissions=%A owner-uid=%u' note.txt | sed 's/owner-uid=[0-9]*/owner-uid=N/'
```

```text output
name=note.txt size=6 bytes type=regular file permissions=-rw-r--r-- owner-uid=N
```

<Happened>
<Tr>
<En>

- `printf 'hello\n' > note.txt` creates a file with 6 bytes: five letters plus one "new line".
- `stat` shows the label: name, size (6 bytes), type (a normal file), permissions (`-rw-r--r--`, explained below) and the owner's user number.

</En>
<Ur>

- `printf 'hello\n' > note.txt` 6 bytes ki file banata hai: paanch letters aur ek "nayi line".
- `stat` label dikhata hai: naam, size (6 bytes), type (aam file), permissions (`-rw-r--r--`, neeche samjhaya hai) aur maalik ka user number.

</Ur>
</Tr>
</Happened>

<Def tip="Linux keeps three times: when the content changed (mtime), when the label changed (ctime), when it was last read (atime).">Linux also stores three dates</Def> for every file. `ls -l` shows the "content changed" date.

</Step>

<Step title="Folders and paths: the address of a file">

<Tr>
<En>

Folders sit inside folders, forming a **tree**. On Linux the tree starts at `/` (called "root"). Windows has one tree per drive (`C:\`, `D:\`).

Shortcuts you'll use every day:

- `.` = this folder
- `..` = the folder above (the parent)
- `~` = your home folder
- `pwd` = "print working directory": shows where you are

</En>
<Ur>

Folders folders ke andar hote hain, aur ek **tree** banate hain. Linux par tree `/` se shuru hota hai (jise "root" kehte hain). Windows me har drive ka apna tree hota hai (`C:\`, `D:\`).

Shortcuts jo aap roz istemal karenge:

- `.` = yahi folder
- `..` = upar wala folder (parent)
- `~` = aap ka home folder
- `pwd` = "print working directory": batata hai aap kahan hain

</Ur>
</Tr>

```bash
mkdir -p project/src project/config
cd project/src
echo "now in: $(basename "$PWD")"
echo "parent of here: $(cd .. && basename "$PWD")"
touch ../config/app.env
ls ../config
realpath --relative-to="$HOME" ../config/app.env
```

```text output
now in: src
parent of here: project
app.env
project/config/app.env
```

<Happened>
<Tr>
<En>

- `mkdir -p` creates `project/src` and `project/config` (and `project` itself).
- After `cd project/src`, we're inside `src`; its parent `..` is `project`.
- `../config/app.env` means "go up one folder, then into `config`, file `app.env`". `touch` creates that empty file.
- `realpath` prints the full route from the home folder.

</En>
<Ur>

- `mkdir -p` `project/src` aur `project/config` banata hai (aur khud `project` bhi).
- `cd project/src` ke baad hum `src` ke andar hain; us ka parent `..` `project` hai.
- `../config/app.env` ka matlab: "ek folder upar jao, phir `config` me, file `app.env`". `touch` wo khaali file banata hai.
- `realpath` home folder se poora raasta print karta hai.

</Ur>
</Tr>
</Happened>

<Callout type="warning" title="Relative paths depend on where you are">
<Tr>
<En>A script that opens `config/app.env` works when started from the project folder and fails from anywhere else. Scripts and scheduled jobs should use full paths, or build them from the script's own location.</En>
<Ur>Jo script `config/app.env` kholti hai wo project folder se chalane par chalegi aur kahin aur se fail hogi. Scripts aur scheduled jobs ko poore paths istemal karne chahiyen, ya script ki apni jagah se path banana chahiye.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Names and files are separate: links">

<Tr>
<En>

On Linux, each file has a record card called an **inode** (size, owner, where the bytes are on disk). A file **name** is just a pointer to that card. So:

- A **hard link** is a second name pointing to the **same** card. Both names are equal.
- A **symbolic link** (symlink, shortcut) is a tiny file that stores a **name** to follow.

</En>
<Ur>

Linux par har file ka ek record card hota hai jise **inode** kehte hain (size, maalik, disk par bytes kahan hain). File ka **naam** sirf us card ki taraf ishara hai. To:

- **Hard link** doosra naam hai jo **usi** card ki taraf ishara karta hai. Dono naam barabar hain.
- **Symbolic link** (symlink, shortcut) ek chhoti si file hai jo ek **naam** rakhti hai jis ke peeche jana hai.

</Ur>
</Tr>

```bash
echo "version 1" > original.txt
ln original.txt hardlink.txt           # second name, same inode
ln -s original.txt symlink.txt         # a small file that points to a NAME

[[ $(stat -c %i original.txt) == $(stat -c %i hardlink.txt) ]] && echo "hard link: same inode as the original"
echo "version 2" > original.txt
echo "hard link now reads: $(cat hardlink.txt)"
echo "symlink points to: $(readlink symlink.txt)"

rm original.txt
echo "after deleting original.txt:"
echo "  hard link still works: $(cat hardlink.txt)"
cat symlink.txt 2>/dev/null || echo "  symlink is broken (its target name is gone)"
```

```text output
hard link: same inode as the original
hard link now reads: version 2
symlink points to: original.txt
after deleting original.txt:
  hard link still works: version 2
  symlink is broken (its target name is gone)
```

<Happened>
<Tr>
<En>

- Changing `original.txt` also changes what `hardlink.txt` shows: they're the **same file** with two names.
- After deleting `original.txt`, the hard link still works, because the data is only removed when its **last** name is gone.
- The symlink breaks, because the name it pointed to no longer exists.
- Symlinks are very common: e.g. a `current` link pointing to the latest release folder.

</En>
<Ur>

- `original.txt` badalne se `hardlink.txt` bhi badal jata hai: ye **ek hi file** ke do naam hain.
- `original.txt` delete karne ke baad bhi hard link chalta hai, kyun ke data tab hi hat-ta hai jab us ka **aakhri** naam bhi chala jaye.
- Symlink toot jata hai, kyun ke jis naam ki taraf wo ishara karta tha wo ab mojood nahi.
- Symlinks bohot aam hain: misaal ke taur par `current` naam ka link jo latest release folder ki taraf ishara kare.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Owner, group and everyone else">

<Tr>
<En>

Every file belongs to one **user** (the owner) and one **group**. Permissions are set separately for three kinds of people:

- **u** = the owner (user)
- **g** = members of the group
- **o** = others (everyone else)

`ls -l` shows this as 10 characters. Here's how to read them:

</En>
<Ur>

Har file ek **user** (maalik) aur ek **group** ki hoti hai. Permissions teen qism ke logon ke liye alag alag set hoti hain:

- **u** = maalik (user)
- **g** = group ke members
- **o** = others (baaqi sab)

`ls -l` ye 10 characters me dikhata hai. Inhe aise parhein:

</Ur>
</Tr>

```text
-rw-r-----  1 alex  www-data  2048 Nov 10 14:30 app.env
│└┬┘└┬┘└┬┘     │     │
│ │  │  │      │     └ group
│ │  │  │      └ owner
│ │  │  └ others: ---  (no access)
│ │  └ group:   r--  (read only)
│ └ owner:      rw-  (read and write)
└ type: - = regular file
```

<Happened>
<Tr>
<En>

- The first character is the type: `-` file, `d` folder, `l` link.
- Then three sets of three: owner `rw-`, group `r--`, others `---`.
- So **Alex** can read and change `app.env`, the **www-data** group can only read it, and **nobody else** can touch it.

</En>
<Ur>

- Pehla character type hai: `-` file, `d` folder, `l` link.
- Phir teen teen ke teen set: maalik `rw-`, group `r--`, others `---`.
- Yani **Alex** `app.env` parh aur badal sakta hai, **www-data** group sirf parh sakta hai, aur **koi aur** use chhoo bhi nahi sakta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What read, write and run mean (and the numbers)">

<Tr>
<En>

Each letter also has a number: **r = 4**, **w = 2**, **x = 1**. Add them up for each group of people. So `rw-` = 4+2 = **6**, `r--` = **4**, `rwx` = **7**. That's why you'll see commands like `chmod 644`.

The letters mean slightly different things for files and folders:

| | On a file | On a folder |
| --- | --- | --- |
| **r** (4) | Read the content | See the list of names inside |
| **w** (2) | Change the content | Add, delete or rename things inside |
| **x** (1) | Run it as a program | Go inside it (`cd`) |

</En>
<Ur>

Har letter ka ek number bhi hai: **r = 4**, **w = 2**, **x = 1**. Har qism ke logon ke liye inhe jama karein. To `rw-` = 4+2 = **6**, `r--` = **4**, `rwx` = **7**. Isi liye aap `chmod 644` jaisi commands dekhenge.

Files aur folders ke liye letters ka matlab thora alag hai:

| | File par | Folder par |
| --- | --- | --- |
| **r** (4) | Content parhna | Andar ke naamon ki list dekhna |
| **w** (2) | Content badalna | Andar cheezen banana, delete ya rename karna |
| **x** (1) | Program ki tarah chalana | Andar jana (`cd`) |

</Ur>
</Tr>

```bash
mkdir -p vault && echo "secret" > vault/data.txt
chmod 600 vault/data.txt
chmod 700 vault
stat -c '%A %n' vault vault/data.txt
chmod 644 vault/data.txt
stat -c '%A %n' vault/data.txt
```

```text output
drwx------ vault
-rw------- vault/data.txt
-rw-r--r-- vault/data.txt
```

<Happened>
<Tr>
<En>

- `chmod 600` = owner 6 (`rw-`), group 0, others 0: **only the owner** can read or change it. Good for secrets.
- `chmod 700` on the folder = only the owner can open it.
- `chmod 644` = owner can read and write, everyone else can only read. Normal for public files like web pages.
- Surprise rule: if you can **write to a folder**, you can **delete** files inside it, even ones you can't write to. Deleting changes the folder's list, not the file.

</En>
<Ur>

- `chmod 600` = maalik 6 (`rw-`), group 0, others 0: **sirf maalik** parh ya badal sakta hai. Secrets ke liye achha.
- Folder par `chmod 700` = sirf maalik use khol sakta hai.
- `chmod 644` = maalik parh aur likh sakta hai, baaqi sab sirf parh sakte hain. Web pages jaisi public files ke liye aam.
- Hairat wala qaida: agar aap **folder me likh** sakte hain, to aap us ke andar ki files **delete** kar sakte hain, chahe un files me likh na sakein. Delete karna folder ki list badalta hai, file nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="How the system decides: only one rule applies">

<Tr>
<En>

When a program opens a file, Linux checks **who** the program is running as, in this order, and stops at the first match:

1. Is it **root**? → allowed (almost always).
2. Is it the **owner**? → use the owner's letters only.
3. Is it in the file's **group**? → use the group's letters only.
4. Otherwise → use the "others" letters.

Important: **apps run as their own user** (like `www-data` or `node`), not as you. Files they need must be readable by **that** user.

</En>
<Ur>

Jab koi program file kholta hai, Linux check karta hai ke program **kis user** ke taur par chal raha hai, is tarteeb se, aur pehle match par ruk jata hai:

1. Kya ye **root** hai? → ijazat (taqreeban hamesha).
2. Kya ye **maalik** hai? → sirf maalik ke letters istemal hon.
3. Kya ye file ke **group** me hai? → sirf group ke letters.
4. Warna → "others" ke letters.

Ahem: **apps apne user ke taur par chalti hain** (jaise `www-data` ya `node`), aap ke taur par nahi. Jo files unhe chahiyen wo **us** user ke liye parhne ke qabil honi chahiyen.

</Ur>
</Tr>

```text
process user = deploy, groups = deploy, www-data
file: -rw-r----- root www-data /var/www/shop/.env

is deploy root?                 no
is deploy the owner (root)?     no
is deploy in group www-data?    yes → use group bits r-- → READ allowed, WRITE denied
```

</Step>

<Step title="Default permissions for new files (umask)">

<Tr>
<En>

When a program creates a new file, who can read it? The **umask** decides. It's a "remove these permissions" setting.

- umask `022` (common) → new files `644`, folders `755` (others can read)
- umask `077` (private) → new files `600`, folders `700` (only you)

</En>
<Ur>

Jab koi program nayi file banata hai, to use kaun parh sakta hai? Ye **umask** tay karta hai. Ye "ye permissions hata do" wali setting hai.

- umask `022` (aam) → nayi files `644`, folders `755` (doosre parh sakte hain)
- umask `077` (private) → nayi files `600`, folders `700` (sirf aap)

</Ur>
</Tr>

```bash
umask 022; touch normal.txt; mkdir normal-dir
umask 077; touch private.txt; mkdir private-dir
stat -c '%a %n' normal.txt normal-dir private.txt private-dir
```

```text output
644 normal.txt
755 normal-dir
600 private.txt
700 private-dir
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="chmod -R 777 to fix any error">

<Tr>
<En>It gives **everyone** permission to change everything. It hides the real problem and opens a security hole.</En>
<Ur>Ye **sab ko** har cheez badalne ki ijazat de deta hai. Asal masla chhup jata hai aur security ka surakh khul jata hai.</Ur>
</Tr>

</Bad>
<Good title="Fix the owner">

<Tr>
<En>Find the user the app runs as and give **that user** ownership: `chown -R app:app /srv/app/uploads`.</En>
<Ur>Pata karein app kis user ke taur par chalti hai aur **usi user** ko maalik banayen: `chown -R app:app /srv/app/uploads`.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Case doesn't matter (on Windows)">

<Tr>
<En>`import Header from "./Components/Header"` works on Windows even if the folder is `components`.</En>
<Ur>`import Header from "./Components/Header"` Windows par chal jata hai chahe folder ka naam `components` ho.</Ur>
</Tr>

</Bad>
<Good title="Match exact names (for Linux)">

<Tr>
<En>Linux servers and Docker treat `Components` and `components` as **different** folders. Always match the real name exactly.</En>
<Ur>Linux servers aur Docker `Components` aur `components` ko **alag** folders samajhte hain. Hamesha asal naam bilkul theek likhein.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Secrets readable by everyone">

<Tr>
<En>`.env` with mode `644`: any user or hacked program on the server can read your database password.</En>
<Ur>`.env` mode `644` ke saath: server ka koi bhi user ya hack shuda program aap ka database password parh sakta hai.</Ur>
</Tr>

</Bad>
<Good title="Owner-only secrets">

<Tr>
<En>`.env` and SSH keys: owned by the app's user, mode `600`.</En>
<Ur>`.env` aur SSH keys: app ke user ki milkiyat, mode `600`.</Ur>
</Tr>

</Good>
</Compare>

```bash
echo "size: $(stat -c %s a.txt) bytes, permissions: $(stat -c %A a.txt)"

# 2. Paths
mkdir -p one/two && cd one/two && echo "relative ../.. is $(cd ../.. && basename "$PWD")" && cd ../..

# 3. Permissions in numbers and letters
for m in 600 640 644 700 755; do chmod "$m" a.txt; echo "$m = $(stat -c %A a.txt)"; done

# 4. Links
ln -s a.txt link-to-a && echo "link-to-a → $(readlink link-to-a)"

# 5. Directory permission controls deleting
mkdir shared && touch shared/locked.txt && chmod 444 shared/locked.txt
rm -f shared/locked.txt && echo "deleted a read-only file, because the directory was writable"

cd ~ && rm -rf ~/fs-lab
```

```text output
644 = -rw-r--r--
```

<DeepDive title="File systems you'll meet">

**ext4** and **XFS** (Linux servers), **NTFS** (Windows), **APFS** (macOS), **FAT32/exFAT** (USB sticks), plus special ones like **tmpfs** (lives in RAM) and **overlayfs** (Docker layers).

The three timestamps:

| Timestamp | Changes when | Shown by |
| --- | --- | --- |
| **mtime** (modify) | The content changes | `ls -l` |
| **ctime** (change) | The metadata changes (permissions, owner, rename) | `ls -lc` |
| **atime** (access) | The file is read (often updated lazily) | `ls -lu` |

| | Hard link | Symbolic (soft) link |
| --- | --- | --- |
| Points to | The inode (the data) | A path (a name) |
| Survives deleting the original name | Yes | No, it becomes broken |
| Across file systems / to folders | No | Yes |
| Typical use | Rare (backup tools) | Very common: `current → releases/v2`, `/etc/nginx/sites-enabled/…` |

`ls -i` shows inode numbers; `df -i` shows inode usage. A disk can be "full" of inodes (millions of tiny files) while space remains.

</DeepDive>

<DeepDive title="Special permission bits: setuid, setgid, sticky">

- **setuid**: the program runs as its **owner**, not as you. `passwd` uses it to update the password file as root.
- **setgid**: runs as the file's group; on a folder, new files inherit the folder's group (good for team folders).
- **sticky bit**: in a shared folder, only a file's owner can delete it. `/tmp` uses it so users can't delete each other's files.

```bash
stat -c '%A %n' /tmp /usr/bin/passwd 2>/dev/null
```

```text output
drwxrwxrwt /tmp
-rwsr-xr-x /usr/bin/passwd
```

- `t` at the end of `/tmp`: sticky bit.
- `s` in the owner position of `passwd`: setuid, so anyone who runs it runs it **as root**.

Find setuid programs with `find / -perm -4000 -type f 2>/dev/null`. They're a favourite target in privilege escalation.

</DeepDive>

<DeepDive title="Containers: layered file systems">

A Docker image is a stack of **read-only layers** (one per Dockerfile instruction). A running container adds a thin **writable layer** on top, and **overlayfs** merges them into one view. Files written inside a container vanish when it's removed, so databases and uploads go into **volumes**.

```text
┌────────────────────────────┐  writable container layer (lost when the container is removed)
├────────────────────────────┤  COPY . /app          ← your code
├────────────────────────────┤  RUN npm ci            ← node_modules
├────────────────────────────┤  FROM node:22-alpine   ← base OS + Node.js
└────────────────────────────┘
         + volume mounted at /app/uploads  ← survives restarts and redeploys
```

</DeepDive>

<DeepDive title="Object storage (S3) is not a file system">

Object storage (AWS S3, Azure Blob, Cloudflare R2) stores whole **objects** under a **key** in a **bucket**, over HTTP. Keys like `uploads/2026/photo.jpg` look like paths, but there are no real folders. You `PUT` and `GET` whole objects; permissions come from IAM and bucket policies, not `chmod`.

| | Block storage (EBS, disk) | File storage (NFS, EFS) | Object storage (S3) |
| --- | --- | --- | --- |
| Looks like | A raw disk you format | A shared network folder | Buckets of objects over HTTP |
| Used by | One server at a time | Many servers at once | Any app, anywhere |
| Edit part of a file | Yes | Yes | No, replace the whole object |
| Permissions | Linux permissions | Linux permissions | IAM / bucket policies |
| Typical use | OS, databases | Shared uploads, legacy apps | Uploads, backups, static sites |

</DeepDive>

<DeepDive title="Real world: deploying to a Linux server">

A Next.js + Express app is deployed to an Ubuntu server.

1. The build fails: `Module not found: ./Components/Header`. It worked on Windows because Windows paths ignore upper/lower case; Linux doesn't. Fix the import.
2. The API crashes with `EACCES: permission denied, open '/srv/app/uploads/...'`. The service runs as user `app`, but `uploads/` is owned by `root` because it was created with `sudo`. Fix: `chown -R app:app /srv/app/uploads`, not `chmod 777`.
3. The `.env` file is `-rw-r--r--` (644): any user on the box can read the database password. Fix: owned by `app`, mode `600`.
4. Disk is "full" but `du` shows little usage: a deleted 20 GB log is still held open by the running process. Restarting the service frees it; log rotation prevents it.
5. Uploaded files are served from the same folder as the app code. Fix: store uploads outside the web root (or in S3), with random names, and never execute them.

</DeepDive>

<DeepDive title="Security lens">

On a hacked server, file permissions decide how far the attacker gets.

- **Path traversal:** user input like `../../etc/passwd` used in a file path lets attackers read files outside the intended folder. Never use user input as a path; map IDs to stored names, or resolve the final path and check it stays inside the allowed folder.
- **Secrets on disk:** `.env` files, SSH private keys (`~/.ssh/id_ed25519` must be `600`), cloud credentials and kubeconfigs are prime targets. Restrict them to the owner and keep them out of Git and Docker images.
- **World-writable files run by root** (cron scripts, systemd units) let any user become root by editing them.
- **setuid binaries** are classic escalation targets; keep the list minimal and patched.
- **Unrestricted file upload:** an uploaded `shell.php` in a web-served folder becomes remote code execution. Check the real type, rename files, store outside the web root.
- **Secrets in image layers:** `COPY .env .` then `RUN rm .env` still leaves the secret in an earlier layer. Use build secrets and `.dockerignore`.
- **Public cloud storage:** misconfigured public S3 buckets have leaked huge amounts of data. Keep Block Public Access on.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What do the permissions -rwxr-x--- mean?">
The first character `-` means a regular file. Then three triplets: owner `rwx` can read, write and execute; group `r-x` can read and execute; others `---` have no access. In octal that is 750.
</QA>

<QA q="What is the difference between a hard link and a symbolic link?">
A hard link is another directory entry pointing to the same inode; all names are equal, and the data survives until every link is deleted. It cannot cross file systems or point to directories. A symbolic link is a separate small file containing a path to the target; it can cross file systems and point to directories, but breaks if the target is moved or deleted.
</QA>

<QA q="The disk is full, you deleted a large log file, but df still shows it full. Why?">
A process still has the deleted file open. Deleting removed the name, but the inode and its data blocks are freed only when the last open file handle closes. Find it with `lsof +L1` and restart or signal the process to reopen its logs; use log rotation to prevent it.
</QA>

<QA q="What is path traversal and how do you prevent it?">
Path traversal is when user input such as `../../etc/passwd` is used to build a file path, letting an attacker escape the intended directory. Prevent it by not using user input as paths (map IDs to stored filenames), or by resolving the full path, verifying it still starts with the allowed base directory, and running the service with minimal file permissions.
</QA>

<QA q="Why is S3 not a file system?">
S3 is an object store: data is stored as whole objects under keys in a flat namespace and accessed through an HTTP API. There are no real directories, no in-place partial writes, no POSIX permissions and no file locking; access is controlled by IAM and bucket policies.
</QA>

</DeepDive>
