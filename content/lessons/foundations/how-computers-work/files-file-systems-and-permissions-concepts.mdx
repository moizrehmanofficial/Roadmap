<Callout type="tip" title="In one minute">
A **file** is a sequence of bytes plus **metadata** (size, owner, permissions, timestamps). A **directory** (folder) is a list of names pointing to files. A **path** like `/var/www/index.html` is the route to a file. A **file system** (ext4, NTFS, APFS) is the system that organises files on a disk. On Linux each file has an **inode** holding its metadata; names are just labels pointing at inodes. **Permissions** decide who can **read**, **write** or **execute** a file: the **owner**, the **group**, and **everyone else**. Object storage like S3 stores objects by key — it looks like folders but is not a file system.
</Callout>

## Start from zero

### Where does your data actually go?

A disk is just a huge row of numbered blocks of bytes. Without organisation, nobody could find "the photo from last week" in billions of bytes.

<Callout type="analogy">
A **library**:

- The **books** are files — the actual content.
- The **catalogue card** of each book is its **metadata**: title, size, which shelf, who may borrow it.
- **Sections and shelves** are **directories**.
- The **path** is the directions: "Building A → Floor 2 → Shelf 7 → Book 'Linux Basics'".
- The **library system** that keeps the catalogue correct and finds shelves is the **file system**.
- **Library rules** — "staff only", "reference books cannot leave" — are **permissions**.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **File** | Named content: a sequence of bytes | `notes.txt` |
| **Metadata** | Information *about* a file | size, owner, modified time |
| **Directory / folder** | A container of file names | `/home/moiz` |
| **Path** | The location of a file, folder by folder | `/etc/nginx/nginx.conf` |
| **Absolute path** | Starts at the root `/` | `/var/log/syslog` |
| **Relative path** | Starts from the current folder | `logs/app.log`, `../config` |
| **File system** | The way files are organised on a disk | ext4, XFS, NTFS, APFS |
| **Inode** | Linux's record of a file's metadata and data location | inode number 131074 |
| **Permission** | A rule about who may read, write or execute | `rw-r--r--` |

## What is it?

| Concept | What it is |
| --- | --- |
| File | Bytes + metadata |
| Directory | A special file: a table of names → inodes |
| Path | A chain of directory names ending in a file |
| File system | The on-disk structure and rules for storing files |
| Permissions | Access rules checked by the OS on every open/run |

Common file systems: **ext4** and **XFS** (Linux servers), **NTFS** (Windows), **APFS** (macOS), **FAT32/exFAT** (USB sticks), plus special ones like **tmpfs** (in RAM) and **overlayfs** (Docker layers).

## Why does it matter?

- **Deployments break on files:** wrong paths, missing permissions ("Permission denied"), a full disk.
- **Security:** most Linux privilege-escalation tricks abuse wrong permissions; leaked `.env` files and world-readable SSH keys are classic findings.
- **Docker and Kubernetes:** images are layered file systems, volumes are mounted file systems, and containers run as users with permissions.
- **Cloud:** knowing the difference between block storage (a disk), file storage (NFS/EFS) and object storage (S3) is a common interview topic.

## When and where do you use it?

| Situation | Concept |
| --- | --- |
| "No such file or directory" | Paths (absolute vs relative, current folder) |
| "Permission denied" | Owner, group, permissions |
| Disk full but files deleted | Inodes, open files |
| Script will not run | Execute permission |
| Uploading user files | Object storage vs local disk |

## Concepts one by one

### 1. A file = content + metadata

<Explain>
<What>
The content is just bytes. The metadata is everything the OS records about those bytes: size, type, owner, group, permissions, and three timestamps.
</What>
<Why>
Tools, backups, deploys and security checks all rely on metadata: "changed since yesterday?", "owned by root?", "executable?".
</Why>
<When>
Every time a file is created, read, changed or listed.
</When>
<Where>
`ls -l`, `stat`, file explorers' "Properties".
</Where>
<How>
`stat file` shows the full metadata. The file **name** is not part of the file itself — it lives in the directory.
</How>
</Explain>

```bash
printf 'hello\n' > note.txt
stat -c 'name=%n size=%s bytes type=%F permissions=%A owner-uid=%u' note.txt | sed 's/owner-uid=[0-9]*/owner-uid=N/'
```

```text output
name=note.txt size=6 bytes type=regular file permissions=-rw-r--r-- owner-uid=N
```

The three timestamps Linux keeps:

| Timestamp | Changes when | Shown by |
| --- | --- | --- |
| **mtime** (modify) | The content changes | `ls -l` |
| **ctime** (change) | The metadata changes (permissions, owner, rename) | `ls -lc` |
| **atime** (access) | The file is read (often updated lazily) | `ls -lu` |

### 2. Directories and paths

<Explain>
<What>
A directory is a list of entries, each a name plus a pointer to a file or another directory. Directories nest into a **tree** starting at the root `/`.
</What>
<Why>
Paths are how every program, script and config file finds things.
</Why>
<When>
Every file operation.
</When>
<Where>
Linux has one tree starting at `/`; Windows has one tree per drive (`C:\`, `D:\`).
</Where>
<How>
Absolute paths start with `/`. Relative paths start from the **current working directory** (`pwd`). `.` means "this folder", `..` means "the parent folder", `~` means your home folder.
</How>
</Explain>

```bash
mkdir -p project/src project/config
cd project/src
echo "now in: $(basename "$PWD")"
echo "parent of here: $(cd .. && basename "$PWD")"
touch ../config/app.env
ls ../config
realpath --relative-to="$HOME" ../config/app.env
```

```text output
now in: src
parent of here: project
app.env
project/config/app.env
```

<Callout type="warning" title="Relative paths depend on where you are">
A script that uses `config/app.env` works when started from the project folder and fails from anywhere else. Scripts and cron jobs should use absolute paths or build them from the script's own location.
</Callout>

### 3. Inodes: names are separate from files

<Explain>
<What>
On Linux, every file has an **inode**: a record with its metadata and where its bytes are on disk. The **name** is just a directory entry pointing to the inode. One inode can have several names (**hard links**).
</What>
<Why>
It explains strange situations: deleting a file that a process still has open does not free space; a disk can be "full" of inodes while space remains; a hard link changes when the "other" file changes.
</Why>
<When>
Disk-space puzzles, links, backups.
</When>
<Where>
ext4, XFS and other Unix file systems.
</Where>
<How>
`ls -i` shows inode numbers; `df -i` shows inode usage.
</How>
</Explain>

```bash
echo "version 1" > original.txt
ln original.txt hardlink.txt           # second name, same inode
ln -s original.txt symlink.txt         # a small file that points to a NAME

[[ $(stat -c %i original.txt) == $(stat -c %i hardlink.txt) ]] && echo "hard link: same inode as the original"
echo "version 2" > original.txt
echo "hard link now reads: $(cat hardlink.txt)"
echo "symlink points to: $(readlink symlink.txt)"

rm original.txt
echo "after deleting original.txt:"
echo "  hard link still works: $(cat hardlink.txt)"
cat symlink.txt 2>/dev/null || echo "  symlink is broken (its target name is gone)"
```

```text output
hard link: same inode as the original
hard link now reads: version 2
symlink points to: original.txt
after deleting original.txt:
  hard link still works: version 2
  symlink is broken (its target name is gone)
```

| | Hard link | Symbolic (soft) link |
| --- | --- | --- |
| Points to | The inode (the data) | A path (a name) |
| Survives deleting the original name | Yes | No — becomes broken |
| Across file systems / to folders | No | Yes |
| Typical use | Rare (backup tools) | Very common: `current → releases/v2`, `/etc/nginx/sites-enabled/…` |

### 4. Users, groups and the three permission classes

<Explain>
<What>
Every file has one **owner** (a user) and one **group**. Permissions are set separately for three classes: the **owner** (u), members of the **group** (g), and **others** (o) — everyone else.
</What>
<Why>
On a shared server many users and services exist; each should access only what it needs.
</Why>
<When>
Creating files, deploying apps, configuring services.
</When>
<Where>
Every Linux/Unix system; similar ideas (ACLs) on Windows and in cloud IAM.
</Where>
<How>
`ls -l` shows them as 10 characters: the type (`-` file, `d` directory, `l` link), then `rwx` for owner, group and others.
</How>
</Explain>

```text
-rw-r-----  1 moiz  www-data  2048 Nov 10 14:30 app.env
│└┬┘└┬┘└┬┘     │     │
│ │  │  │      │     └ group
│ │  │  │      └ owner
│ │  │  └ others: ---  (no access)
│ │  └ group:   r--  (read only)
│ └ owner:      rw-  (read and write)
└ type: - = regular file
```

### 5. What read, write and execute mean

<Explain>
<What>
**r**, **w**, **x** mean different things for files and for directories.
</What>
<Why>
Many "Permission denied" puzzles come from directory permissions, not file permissions.
</Why>
<When>
Debugging access problems, securing folders.
</When>
<Where>
Web roots, home folders, upload folders.
</Where>
<How>
See the table. To open `/a/b/file`, you need `x` on `/a` and `/a/b` **and** the right permission on `file`.
</How>
</Explain>

| | On a file | On a directory |
| --- | --- | --- |
| **r** (4) | Read the content | List the names inside (`ls`) |
| **w** (2) | Change the content | Create, delete, rename entries inside |
| **x** (1) | Run it as a program | Enter it (`cd`) and reach files inside |

```bash
mkdir -p vault && echo "secret" > vault/data.txt
chmod 600 vault/data.txt
chmod 700 vault
stat -c '%A %n' vault vault/data.txt
chmod 644 vault/data.txt
stat -c '%A %n' vault/data.txt
```

```text output
drwx------ vault
-rw------- vault/data.txt
-rw-r--r-- vault/data.txt
```

Note a surprising rule: with **write** permission on a **directory**, a user can delete a file inside it — even a file they cannot write to. Deleting is an operation on the directory's list of names.

### 6. How the OS checks a permission

<Explain>
<What>
On every open or run, the kernel checks the process's **user** and **groups** against the file, in a fixed order.
</What>
<Why>
Knowing the order explains every "but I'm in the group!" surprise.
</Why>
<When>
Every file access.
</When>
<Where>
The Linux kernel.
</Where>
<How>
1) If the user is **root** → allowed (almost always). 2) If the user is the **owner** → use the owner bits only. 3) Else if the user is in the file's **group** → use the group bits only. 4) Else → use the others bits. Only **one** class applies — an owner with `---` is denied even if "others" have `rwx`.
</How>
</Explain>

```text
process user = deploy, groups = deploy, www-data
file: -rw-r----- root www-data /var/www/shop/.env

is deploy root?                 no
is deploy the owner (root)?     no
is deploy in group www-data?    yes → use group bits r-- → READ allowed, WRITE denied
```

A service runs as a specific user (`www-data`, `node`, `postgres`). Files it must read need permissions for **that** user, not for you.

### 7. Special permission bits

<Explain>
<What>
Three extra bits: **setuid** (run the program as its owner), **setgid** (run as its group / new files inherit the folder's group), and the **sticky bit** (in a shared folder, only a file's owner can delete it).
</What>
<Why>
`passwd` needs setuid root to update the password file; `/tmp` needs the sticky bit so users cannot delete each other's files. They are also a favourite target in privilege escalation.
</Why>
<When>
Security audits, shared folders.
</When>
<Where>
`/usr/bin/passwd` (setuid), `/tmp` (sticky), team project folders (setgid).
</Where>
<How>
Shown as `s` or `t` in the `x` positions. Find setuid programs with `find / -perm -4000 -type f 2>/dev/null`.
</How>
</Explain>

```bash
stat -c '%A %n' /tmp /usr/bin/passwd 2>/dev/null
```

```text output
drwxrwxrwt /tmp
-rwsr-xr-x /usr/bin/passwd
```

- `t` at the end of `/tmp` — sticky bit.
- `s` in the owner position of `passwd` — setuid: anyone who runs it runs it **as root**.

### 8. Default permissions: umask

<Explain>
<What>
The **umask** removes permissions from newly created files and folders.
</What>
<Why>
It decides whether new files are readable by other users — important for secrets, keys and backups.
</Why>
<When>
Every time a program creates a file.
</When>
<Where>
Shell sessions, scripts, services (systemd `UMask=`).
</Where>
<How>
New files start from `666`, folders from `777`, minus the umask. Common umask `022` → files `644`, folders `755`. With `077` → files `600`, folders `700` (private).
</How>
</Explain>

```bash
umask 022; touch normal.txt; mkdir normal-dir
umask 077; touch private.txt; mkdir private-dir
stat -c '%a %n' normal.txt normal-dir private.txt private-dir
```

```text output
644 normal.txt
755 normal-dir
600 private.txt
700 private-dir
```

### 9. Containers: layered file systems

<Explain>
<What>
A Docker image is a stack of **read-only layers** (one per Dockerfile instruction). A running container adds a thin **writable layer** on top. **overlayfs** merges them into one view.
</What>
<Why>
Explains why images share layers (fast pulls), why files written inside a container disappear when it is removed, and why data must go to **volumes**.
</Why>
<When>
Building images, debugging "my uploaded files vanished after redeploy".
</When>
<Where>
Docker, Kubernetes, Podman.
</Where>
<How>
Persistent data (databases, uploads) goes into **volumes** or bind mounts — separate file systems mounted into the container.
</How>
</Explain>

```text
┌────────────────────────────┐  writable container layer (lost when the container is removed)
├────────────────────────────┤  COPY . /app          ← your code
├────────────────────────────┤  RUN npm ci            ← node_modules
├────────────────────────────┤  FROM node:22-alpine   ← base OS + Node.js
└────────────────────────────┘
         + volume mounted at /app/uploads  ← survives restarts and redeploys
```

### 10. Object storage is not a file system

<Explain>
<What>
Object storage (AWS S3, Azure Blob, Cloudflare R2) stores **objects** — bytes plus metadata — under a **key** in a **bucket**, accessed over HTTP. Keys like `uploads/2026/photo.jpg` look like paths, but there are no real folders.
</What>
<Why>
It is cheap, durable and nearly unlimited — ideal for uploads, backups and static sites — but it cannot be edited in place or locked like a normal file.
</Why>
<When>
User uploads, backups, logs archives, static hosting, data lakes.
</When>
<Where>
Every cloud.
</Where>
<How>
You `PUT` and `GET` whole objects through an API or CLI (`aws s3 cp`). Permissions are set by bucket policies and IAM, not `chmod`.
</How>
</Explain>

| | Block storage (EBS, disk) | File storage (NFS, EFS) | Object storage (S3) |
| --- | --- | --- | --- |
| Looks like | A raw disk you format | A shared network folder | Buckets of objects over HTTP |
| Used by | One server at a time | Many servers at once | Any app, anywhere |
| Edit part of a file | Yes | Yes | No — replace the whole object |
| Permissions | Linux permissions | Linux permissions | IAM / bucket policies |
| Typical use | OS, databases | Shared uploads, legacy apps | Uploads, backups, static sites |

## Hands-on

```bash
mkdir -p ~/fs-lab && cd ~/fs-lab

# 1. Content vs metadata
echo "data" > a.txt
echo "size: $(stat -c %s a.txt) bytes, permissions: $(stat -c %A a.txt)"

# 2. Paths
mkdir -p one/two && cd one/two && echo "relative ../.. is $(cd ../.. && basename "$PWD")" && cd ../..

# 3. Permissions in numbers and letters
for m in 600 640 644 700 755; do chmod "$m" a.txt; echo "$m = $(stat -c %A a.txt)"; done

# 4. Links
ln -s a.txt link-to-a && echo "link-to-a → $(readlink link-to-a)"

# 5. Directory permission controls deleting
mkdir shared && touch shared/locked.txt && chmod 444 shared/locked.txt
rm -f shared/locked.txt && echo "deleted a read-only file, because the directory was writable"

cd ~ && rm -rf ~/fs-lab
```

```text output
size: 5 bytes, permissions: -rw-r--r--
relative ../.. is fs-lab
600 = -rw-------
640 = -rw-r-----
644 = -rw-r--r--
700 = -rwx------
755 = -rwxr-xr-x
link-to-a → a.txt
deleted a read-only file, because the directory was writable
```

## Real-world example

A Next.js + Express app is deployed to an Ubuntu VPS.

1. The build fails: `Module not found: ./Components/Header`. It worked on Windows because Windows paths are case-insensitive; Linux is not. Fix the import to match the real folder name.
2. The API crashes with `EACCES: permission denied, open '/srv/app/uploads/...'`. The service runs as user `app`, but `uploads/` is owned by `root` because it was created with `sudo`. Fix: `chown -R app:app /srv/app/uploads` — not `chmod 777`.
3. The `.env` file is `-rw-r--r--` (644): any user on the box, including a compromised process running as another user, can read the database password. Fix: owned by `app`, mode `600`.
4. Disk is "full" but `du` shows little usage: a deleted 20 GB log is still held open by the running process. Restarting the service frees it; log rotation prevents it.
5. Uploaded files are served from the same directory as the app code. Fix: store uploads outside the web root (or in S3), with random names, and never execute them.

## Common mistakes

- **`chmod -R 777` to fix any permission error.** It gives everyone write access and often "fixes" the wrong problem. Fix the **owner** or the user the service runs as.
- **Relying on the current working directory** (`fs.readFile("config.json")`). It changes depending on where the process was started; resolve from a known base directory.
- **Case-insensitive assumptions** from Windows/macOS that break on Linux servers and in Docker.
- **Writing important data inside a container's filesystem** instead of a volume.
- **Treating S3 like a disk** — expecting folders, renames and file permissions.
- **Trusting file extensions** for uploaded files.

## Security lens

<Callout type="security">
On a compromised server, file permissions decide how far an attacker gets. Many privilege-escalation paths and data leaks are nothing more than one wrong owner or mode bit.
</Callout>

- **Path traversal:** user input like `../../etc/passwd` used in a file path lets attackers read or overwrite files outside the intended folder. Resolve the final path and verify it stays inside the allowed base directory; better, never use user input as a path — map IDs to stored names.
- **Secrets on disk:** `.env` files, SSH private keys (`~/.ssh/id_ed25519` must be `600`), cloud credentials (`~/.aws/credentials`) and kubeconfigs are prime targets. Restrict them to the owner and keep them out of Git and Docker images.
- **World-writable files executed by root** (cron scripts, systemd units, scripts in `PATH`) let any user become root by editing them. Auditing tools such as LinPEAS look for exactly this.
- **setuid binaries** are classic escalation targets; keep the list minimal and patched.
- **Unrestricted file upload:** an uploaded `shell.php` or `.jsp` in a web-served directory becomes remote code execution. Validate type by content, rename files, store outside the web root, and serve with safe headers.
- **Secrets in image layers:** `COPY .env .` followed by `RUN rm .env` still leaves the secret in an earlier layer. Use build secrets and `.dockerignore`.
- **Public cloud storage:** misconfigured public S3 buckets have exposed huge amounts of private data. Block Public Access should be on by default.

## Interview questions

<QA q="What do the permissions -rwxr-x--- mean?">
The first character `-` means a regular file. Then three triplets: owner `rwx` can read, write and execute; group `r-x` can read and execute; others `---` have no access. In octal that is 750.
</QA>

<QA q="What is the difference between a hard link and a symbolic link?">
A hard link is another directory entry pointing to the same inode; all names are equal, and the data survives until every link is deleted. It cannot cross file systems or point to directories. A symbolic link is a separate small file containing a path to the target; it can cross file systems and point to directories, but breaks if the target is moved or deleted.
</QA>

<QA q="The disk is full, you deleted a large log file, but df still shows it full. Why?">
A process still has the deleted file open. Deleting removed the name, but the inode and its data blocks are freed only when the last open file handle closes. Find it with `lsof +L1` (or `lsof | grep deleted`) and restart or signal the process to reopen its logs; use log rotation to prevent it.
</QA>

<QA q="What is path traversal and how do you prevent it?">
Path traversal is when user input such as `../../etc/passwd` is used to build a file path, letting an attacker escape the intended directory. Prevent it by not using user input as paths (map IDs to stored filenames), or by resolving the full path with `path.resolve`, verifying it still starts with the allowed base directory, and running the service with minimal file permissions.
</QA>

<QA q="Why is S3 not a file system?">
S3 is an object store: data is stored as whole objects under keys in a flat namespace and accessed through an HTTP API. There are no real directories, no in-place partial writes, no POSIX permissions and no file locking; access is controlled by IAM and bucket policies. Tools can make it look like a file system, but its semantics, performance and security model are different.
</QA>

## Key terms

<Terms>
  <Term name="File">Named bytes plus metadata.</Term>
  <Term name="Metadata">Data about a file: owner, permissions, size, timestamps.</Term>
  <Term name="Inode">The Linux record holding a file's metadata and data location.</Term>
  <Term name="Absolute path">A path starting from the root, such as /etc/hosts.</Term>
  <Term name="Relative path">A path starting from the current working directory, such as ./src.</Term>
  <Term name="File system">How files and directories are organised on a storage device, such as ext4 or NTFS.</Term>
  <Term name="Permission bits">Read, write and execute for owner, group and others.</Term>
  <Term name="setuid">A bit that makes a program run with its owner's privileges.</Term>
  <Term name="Magic number">The first bytes of a file that identify its real type.</Term>
  <Term name="Object storage">Storage of whole objects by key over an API, such as S3.</Term>
  <Term name="Path traversal">An attack using ../ sequences to access files outside an allowed directory.</Term>
</Terms>
