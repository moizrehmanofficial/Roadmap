<Callout type="tip" title="In one minute">
A **program** is a file; a **process** is that program **running**, with its own memory and a **PID** (process ID). A **thread** is a worker inside a process; threads of the same process **share** its memory. **Concurrency** means handling many tasks by switching between them; **parallelism** means really doing several at the same instant on several cores. The OS **scheduler** gives each thread tiny time slices. Node.js runs your JavaScript on **one** thread and uses an **event loop** to handle thousands of waiting requests. When several workers change shared data at the same time without coordination, you get **race conditions**.
</Callout>

## Start from zero

### One computer, thousands of tasks

Right now your computer runs a browser, a music player, an antivirus, background updates and dozens of system services — but it may have only 4–8 CPU cores. How does everything seem to run at once?

<Callout type="analogy">
A **restaurant**:

- Each **restaurant branch** is a **process** — it has its own kitchen, its own fridge (memory) and its own staff. Branches do not share fridges.
- The **cooks** inside one branch are **threads** — they share the same kitchen and fridge. That makes cooperation easy but means they can bump into each other ("who took the last tomato?").
- A single **waiter** serving 20 tables is **concurrency** — he takes an order, and while the kitchen cooks it he takes the next order, instead of standing and waiting.
- **Four** waiters each serving at the same moment is **parallelism**.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Program** | A file containing code | `/usr/bin/node` |
| **Process** | A running instance of a program, with its own memory | `node server.js` running as PID 2314 |
| **PID** | Process ID — a unique number for each process | `2314` |
| **Thread** | A sequence of execution inside a process; shares the process's memory | worker threads |
| **Scheduler** | The part of the OS that decides which thread runs on which core, when | Linux CFS/EEVDF |
| **Context switch** | Pausing one thread and resuming another on a core | happens thousands of times per second |
| **Concurrency** | Making progress on many tasks by interleaving them | one waiter, many tables |
| **Parallelism** | Several tasks executing at the same instant | four cores busy |
| **Race condition** | A bug where the result depends on timing between workers | two withdrawals from one balance |

## What is it?

| Concept | Has own memory? | Created by | Cost to create |
| --- | --- | --- | --- |
| Process | Yes (isolated) | Starting a program, `fork()` | Higher |
| Thread | No — shares the process's memory | The program itself | Lower |
| Async task (event loop) | Shares everything, runs on one thread | `async` functions, callbacks | Very low |

## Why does it matter?

- **Servers handle many users at once.** How they do it (processes, threads or an event loop) decides how they scale and how they fail.
- **Node.js:** one slow, CPU-heavy function blocks **every** user, because all JavaScript runs on one thread.
- **Operations:** `ps`, `top`, `kill`, systemd and Docker all manage processes. A container is basically an isolated process.
- **Bugs:** race conditions cause double payments, oversold stock and corrupted files — and they appear only under load.
- **Security:** each process runs as a **user**; process isolation is a key security boundary.

## When and where do you use it?

| Situation | Concept |
| --- | --- |
| A service won't stop / uses 100% CPU | Processes, PIDs, signals |
| Choosing PM2 cluster mode or multiple containers | Processes for parallelism |
| `async/await` in Node.js and the browser | Event loop concurrency |
| Image processing, crypto, big JSON in Node.js | Worker threads / separate processes |
| Two requests update the same record | Race conditions, locks, transactions |

## Concepts one by one

### 1. Program vs process

<Explain>
<What>
A **program** is a file on disk. A **process** is that program loaded into memory and running. One program can run as many processes at the same time.
</What>
<Why>
Everything you monitor, restart or kill on a server is a process, identified by its PID.
</Why>
<When>
Every time you start a command, a service, or a container.
</When>
<Where>
`ps`, `top`, `htop`, `systemctl status`, `docker ps` (each container's main process).
</Where>
<How>
`$$` is the PID of the current shell; `$!` is the PID of the last background process. `ps -o pid,ppid,cmd` shows processes with their **parent** PID.
</How>
</Explain>

```bash
sleep 30 &
child=$!
echo "shell PID is a number: $([[ $$ =~ ^[0-9]+$ ]] && echo yes)"
echo "parent of the sleep process is this shell: $([[ $(ps -o ppid= -p "$child" | tr -d ' ') == "$$" ]] && echo yes)"
ps -o cmd= -p "$child"
kill "$child"
```

```text output
shell PID is a number: yes
parent of the sleep process is this shell: yes
sleep 30
```

Every process (except the very first, PID 1) has a **parent** that started it. Your shell is the parent of the commands you run.

### 2. Each process has its own memory

<Explain>
<What>
The OS gives each process a private memory space. One process cannot read or change another's memory directly.
</What>
<Why>
Isolation: a crashing browser tab does not crash your editor; a hacked web process cannot simply read your SSH agent's memory.
</Why>
<When>
Always.
</When>
<Where>
Every OS; containers add even stronger isolation on top.
</Where>
<How>
A child process gets a **copy** of its parent's variables; changing the copy does not affect the parent.
</How>
</Explain>

```bash
balance=100
( balance=0; echo "inside the child process: balance=$balance" )
echo "back in the parent process: balance=$balance"
```

```text output
inside the child process: balance=0
back in the parent process: balance=100
```

`( … )` runs the commands in a **subshell** — a separate child process with a copy of the variables.

### 3. Threads share memory

<Explain>
<What>
Threads are several flows of execution inside **one** process, all sharing the same memory.
</What>
<Why>
Sharing makes cooperation cheap (no copying data between processes) — but also dangerous, because two threads can change the same data at the same time.
</Why>
<When>
Java and C# web servers (a thread per request), databases, browsers, Node.js worker threads.
</When>
<Where>
Inside almost every large program.
</Where>
<How>
`ps -o nlwp -p PID` (number of light-weight processes) shows how many threads a process has.
</How>
</Explain>

```bash
node -e 'setTimeout(() => {}, 2000)' &
pid=$!
sleep 0.5
threads=$(ps -o nlwp= -p "$pid" | tr -d ' ')
(( threads > 1 )) && echo "Node.js runs JavaScript on one thread, but the process has several helper threads"
kill "$pid"
```

```text output
Node.js runs JavaScript on one thread, but the process has several helper threads
```

Even "single-threaded" Node.js has extra threads for garbage collection and for the **libuv** thread pool (file system, DNS, crypto). Only **your JavaScript** runs on one thread.

### 4. Concurrency vs parallelism

<Explain>
<What>
**Concurrency** is dealing with many tasks at once by switching between them. **Parallelism** is executing several tasks at the very same moment on different cores.
</What>
<Why>
Most web servers mainly need concurrency (users spend most time waiting for databases and networks). CPU-heavy work needs parallelism (more cores).
</Why>
<When>
Designing or scaling any service.
</When>
<Where>
Node.js (concurrency on one thread), Go goroutines and Java threads (both), PM2 cluster / multiple containers (parallelism with processes).
</Where>
<How>
Concurrency needs only one core; parallelism needs several. You can have both.
</How>
</Explain>

```text
Concurrency (1 core):    A A B B A C C B A C      ← tasks interleaved
Parallelism (3 cores):   core 1: A A A A A
                         core 2: B B B B B        ← tasks truly simultaneous
                         core 3: C C C C C
```

```bash
start=$SECONDS
sleep 1 & sleep 1 & sleep 1 &
wait
echo "3 one-second waits, run concurrently, took about $((SECONDS - start)) second(s)"
```

```text output
3 one-second waits, run concurrently, took about 1 second(s)
```

Run one after another they would take 3 seconds. Started together with `&` and collected with `wait`, they overlap.

### 5. The scheduler and context switching

<Explain>
<What>
The OS **scheduler** decides which thread runs on each core and for how long (a few milliseconds), then switches to another. Saving one thread's state and loading another's is a **context switch**.
</What>
<Why>
It is what makes hundreds of programs appear to run simultaneously on a few cores — and it costs a little time on every switch.
</Why>
<When>
Constantly, thousands of times per second.
</When>
<Where>
Every multitasking OS.
</Where>
<How>
Priorities influence it: `nice -n 10 command` runs a command with lower priority so it does not slow down important services. `vmstat 1` shows context switches per second (column `cs`).
</How>
</Explain>

### 6. Two ways servers handle many requests

<Explain>
<What>
**Thread-per-request**: each incoming request gets its own thread, which can block while waiting. **Event loop**: one thread handles all requests, never waiting — it starts an operation and moves on, coming back when the result is ready.
</What>
<Why>
Threads are simple to program but each costs memory (often ~1 MB stack). An event loop handles tens of thousands of idle connections cheaply but must never be blocked.
</Why>
<When>
Choosing frameworks, debugging slowdowns.
</When>
<Where>
Thread-per-request: classic Java (Spring), PHP-FPM workers. Event loop: Node.js, NGINX, Python asyncio.
</Where>
<How>
In Node.js, every `await db.query()` gives the thread back to the event loop while the database works.
</How>
</Explain>

<Callout type="analogy">
**Thread-per-request** is a restaurant with one waiter per table: simple, but 500 tables need 500 waiters standing around while food cooks. An **event loop** is one fast waiter who never waits at a table: takes an order, hands it to the kitchen, serves another table, and returns when a dish is ready.
</Callout>

### 7. The Node.js event loop in action

<Explain>
<What>
The mechanism Node.js (and browsers) use to run callbacks: synchronous code first, then **microtasks** (resolved promises), then **macrotasks** (timers, I/O callbacks).
</What>
<Why>
Explains the order in which things print, and why a long synchronous loop freezes the whole server.
</Why>
<When>
Every `async`/`await`, `setTimeout`, `fetch`, file read.
</When>
<Where>
Node.js, browsers, Deno, Bun.
</Where>
<How>
Synchronous code runs to the end without interruption. Only then does the event loop pick the next queued job.
</How>
</Explain>

```javascript
console.log("1. synchronous: start");
setTimeout(() => console.log("4. timer callback (macrotask)"), 0);
Promise.resolve().then(() => console.log("3. promise callback (microtask)"));
console.log("2. synchronous: end");
```

```text output
1. synchronous: start
2. synchronous: end
3. promise callback (microtask)
4. timer callback (macrotask)
```

Even with a delay of 0 ms, the timer runs **after** all synchronous code and after promises.

**Blocking the event loop** — why CPU-heavy code hurts every user:

```javascript
const start = Date.now();
setTimeout(() => console.log(`timer wanted 10 ms, ran after ${Date.now() - start >= 200 ? "200+" : "<200"} ms`), 10);

const until = Date.now() + 200;
while (Date.now() < until) {}           // 200 ms of pure CPU work blocks the only JS thread
console.log("heavy work finished");
```

```text output
heavy work finished
timer wanted 10 ms, ran after 200+ ms
```

In a server, that timer could be **another user's request**. Move heavy work to **worker threads**, a separate process, or a job queue.

### 8. Race conditions

<Explain>
<What>
A bug where the result depends on the **timing** of two or more workers that read and update the same data.
</What>
<Why>
Each worker reads the old value, changes it, and writes it back — and one write overwrites the other. This causes lost updates, double spending and overselling.
</Why>
<When>
Any shared data updated concurrently: counters, balances, stock, files.
</When>
<Where>
Web APIs (two requests at once), threads, multiple servers sharing a database.
</Where>
<How>
Make the "read-change-write" step **atomic**: database transactions with row locks, atomic SQL (`UPDATE … SET stock = stock - 1 WHERE stock > 0`), Redis `INCR`, file locks, or a mutex.
</How>
</Explain>

```javascript
let stock = 1;                                   // only ONE item left
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function buy(user) {
  const current = stock;                         // 1. read
  await sleep(10);                               // 2. e.g. waiting for the payment API
  if (current > 0) {
    stock = current - 1;                         // 3. write back
    console.log(`${user}: order confirmed`);
  } else {
    console.log(`${user}: sold out`);
  }
}

await Promise.all([buy("Sam"), buy("Emma")]);    // two requests arrive at the same time
console.log("stock now:", stock, "— but two people were sold the last item!");
```

```text output
Sam: order confirmed
Emma: order confirmed
stock now: 0 — but two people were sold the last item!
```

Both requests read `stock = 1` before either wrote. Even single-threaded Node.js has races whenever an `await` sits between reading and writing.

The fix — check and update in **one atomic step**:

```javascript
let stock = 1;
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function buy(user) {
  if (stock > 0) { stock -= 1; }                 // atomic: no await between check and update
  else { console.log(`${user}: sold out`); return; }
  await sleep(10);                               // slow work after reserving
  console.log(`${user}: order confirmed`);
}

await Promise.all([buy("Sam"), buy("Emma")]);
console.log("stock now:", stock);
```

```text output
Emma: sold out
Sam: order confirmed
stock now: 0
```

In a real app the "atomic step" is a database operation such as `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0`, which the database performs safely even with many servers.

### 9. Process states and signals

<Explain>
<What>
A process is always in a state — running, sleeping (waiting), stopped or zombie (finished but not yet collected by its parent). **Signals** are messages to processes, like "please stop" (SIGTERM) or "stop now" (SIGKILL).
</What>
<Why>
Reading states and sending signals is how you manage stuck or misbehaving processes.
</Why>
<When>
Restarting services, stopping runaway processes, container shutdown.
</When>
<Where>
`ps` (column STAT), `top`, `kill`, `docker stop`, systemd.
</Where>
<How>
`kill PID` sends SIGTERM (polite); `kill -9 PID` sends SIGKILL (cannot be refused — last resort). See **Processes and Signals** in the Linux module for details.
</How>
</Explain>

| STAT | Meaning |
| --- | --- |
| `R` | Running or ready to run |
| `S` | Sleeping — waiting for something (most processes, most of the time) |
| `D` | Uninterruptible sleep — usually waiting for disk; cannot be killed until it returns |
| `T` | Stopped (Ctrl+Z) |
| `Z` | Zombie — finished, waiting for its parent to collect the exit code |

## Hands-on

```bash
# 1. Every command is a process with a parent
bash -c 'echo "child PID differs from parent: $([[ $$ != $PPID ]] && echo yes)"'

# 2. Run three jobs in parallel and wait for all of them
for n in 1 2 3; do (sleep 0.$n; echo "job $n done") & done
wait
echo "all jobs finished"

# 3. Processes do not share variables
x=1; (x=2); echo "x is still $x"

# 4. A race condition between processes writing one counter file
echo 0 > counter
for i in $(seq 1 50); do ( n=$(cat counter); echo $((n + 1)) > counter ) & done
wait
echo "expected 50, got $(cat counter) (often less: lost updates)" | sed -E 's/got [0-9]+/got N/'

# 5. The same with a lock: always correct
echo 0 > counter
for i in $(seq 1 50); do ( flock 9; n=$(cat counter); echo $((n + 1)) > counter ) 9> counter.lock & done
wait
echo "with flock: $(cat counter)"
```

```text output
child PID differs from parent: yes
job 1 done
job 2 done
job 3 done
all jobs finished
x is still 1
expected 50, got N (often less: lost updates)
with flock: 50
```

Run step 4 a few times: the number changes from run to run — the classic sign of a race condition. `flock` makes each read-and-write a protected, one-at-a-time step.

## Real-world example

An e-commerce API built with Express runs in Docker on a 4-core server.

1. **One process, one core:** Node uses one thread for JavaScript, so 3 of the 4 cores sit idle. The team runs **4 container replicas** (or PM2 cluster mode with 4 processes) behind Nginx.
2. **Blocking:** invoice PDFs are generated inside the request handler and freeze the event loop for 800 ms each. They move PDF generation to a **BullMQ queue** with separate worker processes.
3. **Race condition:** during a flash sale, stock goes negative because two requests read "1 left" at the same time. They replace read-then-write with an atomic `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0` and check the affected row count.
4. **Deploys drop requests:** the app ignored `SIGTERM`, so every deploy killed in-flight checkouts. They add graceful shutdown and a readiness probe.

## Common mistakes

- **CPU-heavy work on the Node.js main thread** (big `JSON.parse`, image resizing, bcrypt with high cost, giant loops). Move it off the request path.
- **`await` inside a loop when the calls are independent.** Use `Promise.all` — but limit how many run at once so you do not overwhelm the database.
- **Read-modify-write without atomicity** on balances, stock or counters.
- **Ignoring `SIGTERM`** and losing requests on every deploy.
- **Running services as root** "because the port didn't work". Use a reverse proxy or capabilities instead.
- **Zombie processes in containers:** if your app spawns children and is PID 1, nobody reaps them. Use `docker run --init` or `tini`.

## Security lens

<Callout type="security">
Every process runs with some identity and some privileges. Attackers want to run their own process — preferably as root — and defenders watch process activity to catch them.
</Callout>

- **Least privilege:** run each service as its own unprivileged user. In Dockerfiles use `USER node`; in Kubernetes set `runAsNonRoot: true`.
- **Suspicious process trees are a top detection signal.** `node` or `nginx` spawning `sh`, `bash`, `curl` or `wget` usually means command injection or remote code execution. EDR tools and Falco alert on exactly this.
- **Command injection:** `exec("convert " + userFilename)` lets an attacker add `; rm -rf /`. Use `execFile`/`spawn` with an argument array, never a shell string.
- **Secrets in process listings and environments:** command-line arguments are visible to every user via `ps`, and `/proc/<pid>/environ` exposes environment variables to the same user and root. Never pass passwords as CLI arguments.
- **Race conditions are vulnerabilities**, known as **TOCTOU** (time-of-check to time-of-use): redeeming one coupon twice, withdrawing more than the balance, bypassing rate limits with parallel requests. Security testers send dozens of parallel requests specifically to find these.
- **Resource limits** (`ulimit`, cgroups, container limits) stop one compromised or runaway process — such as a fork bomb — from taking down the host.

## Interview questions

<QA q="What is the difference between a process and a thread?">
A process is a running program with its own isolated memory space, PID, user identity and file descriptors. A thread is an execution path inside a process; threads share the process's memory and resources. Processes are isolated, safer and heavier; threads are lighter and communicate through shared memory, which requires synchronisation to avoid race conditions.
</QA>

<QA q="Node.js is single-threaded. How does it handle thousands of concurrent requests?">
JavaScript runs on one thread, but I/O is non-blocking: network and file operations are delegated to the operating system or libuv's thread pool, and their callbacks are queued. The event loop runs those callbacks when the thread is free. Since most web requests spend their time waiting on I/O, one thread can serve many requests concurrently — as long as no handler does long CPU-bound work, which would block all others.
</QA>

<QA q="What is a race condition? Give an example and a fix.">
A race condition is a bug where the result depends on the timing of concurrent operations on shared data. Example: two withdrawals both read a balance of 100 and both write their own result, losing one update. Fixes: atomic database updates (`SET balance = balance - 30 WHERE balance >= 30`), transactions with appropriate isolation or row locks, or locks/mutexes in threaded code.
</QA>

<QA q="What is the difference between SIGTERM and SIGKILL?">
SIGTERM (15) asks a process to terminate; the process can catch it and shut down gracefully — finish requests, close connections, flush logs. SIGKILL (9) cannot be caught; the kernel ends the process immediately. Docker and Kubernetes send SIGTERM first and SIGKILL after a grace period, so apps must handle SIGTERM to avoid dropped requests.
</QA>

<QA q="What is the difference between concurrency and parallelism?">
Concurrency is structuring a program to make progress on multiple tasks by interleaving them, which works even on one core. Parallelism is executing multiple tasks at the same instant on multiple cores. Node.js's event loop gives concurrency; worker threads, multiple processes or multiple replicas give parallelism.
</QA>

## Key terms

<Terms>
  <Term name="Process">A running instance of a program with its own memory and PID.</Term>
  <Term name="PID / PPID">Process ID / parent process ID.</Term>
  <Term name="Thread">An execution path inside a process; shares the process's memory.</Term>
  <Term name="Scheduler">The kernel component that decides which thread runs on which CPU core.</Term>
  <Term name="Context switch">Saving one thread's state and loading another's.</Term>
  <Term name="Event loop">A loop that runs queued callbacks when the main thread is free.</Term>
  <Term name="Race condition">A bug where the outcome depends on the timing of concurrent operations.</Term>
  <Term name="Deadlock">Two or more tasks each waiting for a lock the other holds, forever.</Term>
  <Term name="Signal">A notification sent to a process, such as SIGTERM or SIGKILL.</Term>
  <Term name="TOCTOU">Time-of-check to time-of-use; a race condition exploited as a vulnerability.</Term>
</Terms>
