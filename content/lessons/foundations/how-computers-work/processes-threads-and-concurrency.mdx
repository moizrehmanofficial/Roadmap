<BigIdea>
<Tr>
<En>
A **process** is a program that's **running right now**. A **thread** is a worker inside it. The computer switches between them so fast that everything seems to happen at the same time.
</En>
<Ur>
**Process** wo program hai jo **is waqt chal raha** hai. **Thread** us ke andar ek kaam karne wala hai. Computer in ke darmiyan itni tezi se badalta hai ke sab kuch ek saath hota lagta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- A **program** is a file sitting on the disk, like a recipe book on a shelf.
- A **process** is that program **running**, with its own memory and its own ID number (**PID**). Open the same app twice and you get two processes.
- A **thread** is a worker inside a process. Threads of the same process **share** its memory.

</En>
<Ur>

- **Program** disk par rakhi ek file hai, jaise shelf par recipe ki kitaab.
- **Process** wahi program **chalta hua**, apni memory aur apne ID number (**PID**) ke saath. Ek app do dafa kholein to do processes bante hain.
- **Thread** process ke andar ek kaam karne wala hai. Ek process ke threads us ki memory **share** karte hain.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Your computer runs a browser, music, updates and dozens of background services, but it might have only 4 or 8 CPU cores. Understanding processes explains:

- how a server serves **thousands of users** at once
- why one slow piece of code can freeze a whole Node.js app
- how bugs like "**two people bought the last item**" happen

</En>
<Ur>

Aap ka computer browser, music, updates aur darjanon background services chalata hai, lekin us me shayad sirf 4 ya 8 CPU cores hon. Processes samajhne se samajh aata hai:

- server ek saath **hazaron users** ko kaise sambhalta hai
- code ka ek slow hissa poori Node.js app ko kaise jama (freeze) kar deta hai
- "**do logon ne aakhri item khareed liya**" jaise bugs kaise hote hain

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- when a server or app **won't stop**, or uses 100% CPU
- when you write `async`/`await` in JavaScript
- when two users change the **same data** at the same time (stock, bank balance)
- when you restart services or stop Docker containers

</En>
<Ur>

- jab server ya app **band na ho**, ya 100% CPU istemal kare
- jab JavaScript me `async`/`await` likhein
- jab do users ek hi **data** ek saath badlein (stock, bank balance)
- jab services restart karein ya Docker containers rokein

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

The operating system has a **scheduler**. It gives each thread a tiny turn on a CPU core (a few milliseconds), then pauses it and gives the next one a turn. It does this **thousands of times per second**, so to us it looks like everything runs at once.

</En>
<Ur>

Operating system me ek **scheduler** hota hai. Wo har thread ko CPU core par ek chhoti si baari deta hai (kuch milliseconds), phir use rok kar agle ko baari deta hai. Ye **har second hazaron dafa** hota hai, isliye hamein lagta hai sab kuch ek saath chal raha hai.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **restaurant chain**:

- Each **branch** is a **process**. It has its own kitchen and its own fridge (memory). Branches don't share fridges.
- The **cooks** inside one branch are **threads**. They share the same kitchen and fridge. Easy to work together, but they can bump into each other ("who took the last tomato?").
- **One waiter serving 20 tables** is **concurrency**: he takes an order, and while the kitchen cooks it, he takes the next order instead of standing and waiting.
- **Four waiters** serving four tables at the same moment is **parallelism**.

</En>
<Ur>

Ek **restaurant chain** sochein:

- Har **branch** ek **process** hai. Us ka apna kitchen aur apna fridge (memory) hai. Branches fridge share nahi karti.
- Ek branch ke andar ke **cooks** **threads** hain. Wo ek hi kitchen aur fridge share karte hain. Mil kar kaam aasaan, lekin ek doosre se takra bhi sakte hain ("aakhri tamatar kis ne uthaya?").
- **Ek waiter jo 20 tables sambhale** **concurrency** hai: wo order leta hai, aur jab tak kitchen pakata hai, wo khara intezar karne ke bajaye agla order le leta hai.
- **Chaar waiters** jo ek hi waqt me chaar tables sambhalein, ye **parallelism** hai.

</Ur>
</Tr>

```text
Concurrency (1 core):    A A B B A C C B A C      ← tasks take turns
Parallelism (3 cores):   core 1: A A A A A
                         core 2: B B B B B        ← tasks truly at the same time
                         core 3: C C C C C
```

## Learn it step by step

<Walkthrough>

<Step title="Every running program is a process with a number">

<Tr>
<En>

When you run a command, the system creates a **process** and gives it a **PID**. Every process (except the very first one) also has a **parent**: the process that started it. Your terminal is the parent of the commands you type.

</En>
<Ur>

Jab aap koi command chalate hain, system ek **process** banata hai aur use **PID** deta hai. Har process (sab se pehle wale ke ilawa) ka ek **parent** bhi hota hai: wo process jis ne use shuru kiya. Aap ka terminal un commands ka parent hai jo aap type karte hain.

</Ur>
</Tr>

```bash
sleep 30 &
child=$!
echo "shell PID is a number: $([[ $$ =~ ^[0-9]+$ ]] && echo yes)"
echo "parent of the sleep process is this shell: $([[ $(ps -o ppid= -p "$child" | tr -d ' ') == "$$" ]] && echo yes)"
ps -o cmd= -p "$child"
kill "$child"
```

```text output
shell PID is a number: yes
parent of the sleep process is this shell: yes
sleep 30
```

<Happened>
<Tr>
<En>

- `sleep 30 &` starts a process that just waits 30 seconds. The `&` runs it **in the background**, so we can keep typing.
- `$$` is the terminal's own PID; `$!` is the PID of the process we just started.
- `ps` confirms the `sleep` process's parent is our terminal.
- `kill` stops it.

</En>
<Ur>

- `sleep 30 &` ek process shuru karta hai jo bas 30 second intezar karta hai. `&` use **background** me chalata hai, taake hum type karte rahein.
- `$$` terminal ka apna PID hai; `$!` us process ka PID hai jo abhi shuru kiya.
- `ps` tasdeeq karta hai ke `sleep` process ka parent hamara terminal hai.
- `kill` use rok deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Each process has its own private memory">

<Tr>
<En>

The operating system gives each process a **private** memory space. One process can't read or change another one's memory. That's why a crashing browser tab doesn't crash your editor.

When a process starts a child, the child gets a **copy** of the parent's variables. Changing the copy doesn't change the original.

</En>
<Ur>

Operating system har process ko **apni niji** memory deta hai. Ek process doosre ki memory na parh sakta hai na badal sakta hai. Isi liye browser ka ek tab crash hone se aap ka editor crash nahi hota.

Jab process ek bacha (child) shuru karta hai, to bache ko parent ke variables ki **copy** milti hai. Copy badalne se asal nahi badalta.

</Ur>
</Tr>

```bash
balance=100
( balance=0; echo "inside the child process: balance=$balance" )
echo "back in the parent process: balance=$balance"
```

```text output
inside the child process: balance=0
back in the parent process: balance=100
```

<Happened>
<Tr>
<En>

- `( … )` runs the commands in a separate **child** process.
- The child set its copy of `balance` to 0.
- The parent's `balance` is still **100**: processes don't share memory.

</En>
<Ur>

- `( … )` commands ko ek alag **child** process me chalata hai.
- Child ne apni copy me `balance` ko 0 kar diya.
- Parent ka `balance` ab bhi **100** hai: processes memory share nahi karte.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Taking turns vs at the same time">

<Tr>
<En>

Most of a web server's time is spent **waiting**: for a database, for another website, for a file. While one task waits, the computer can work on another. This is **concurrency**.

Let's start three tasks that each wait 1 second. Done one after another, that would take 3 seconds. Started together:

</En>
<Ur>

Web server ka zyada tar waqt **intezar** me guzarta hai: database ka, kisi aur website ka, file ka. Jab ek kaam intezar karta hai, computer doosre par kaam kar sakta hai. Isay **concurrency** kehte hain.

Teen kaam shuru karte hain jo har ek 1 second intezar karta hai. Ek ke baad ek karein to 3 second lagenge. Ek saath shuru karein:

</Ur>
</Tr>

```bash
start=$SECONDS
sleep 1 & sleep 1 & sleep 1 &
wait
echo "3 one-second waits, run concurrently, took about $((SECONDS - start)) second(s)"
```

```text output
3 one-second waits, run concurrently, took about 1 second(s)
```

<Happened>
<Tr>
<En>

- `&` starts each `sleep` in the background without waiting for it.
- `wait` waits until **all** of them are finished.
- All three waits **overlapped**, so the total was about 1 second, not 3.

</En>
<Ur>

- `&` har `sleep` ko background me shuru karta hai, us ka intezar kiye baghair.
- `wait` tab tak rukta hai jab tak **sab** khatam na ho jayen.
- Teeno intezar **ek doosre ke upar** chale, isliye kul waqt 3 nahi, taqreeban 1 second laga.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Node.js: one worker, never standing still">

<Tr>
<En>

Node.js runs your JavaScript on **one thread**. It still serves thousands of users, because it **never waits**: it starts a slow job (like a database query), moves on to the next user, and comes back when the result is ready. The part that manages this is called the **event loop**.

There's an order to it: normal code runs **first**, then quick promise callbacks, then timers.

</En>
<Ur>

Node.js aap ka JavaScript **ek thread** par chalata hai. Phir bhi hazaron users sambhalta hai, kyunke ye **kabhi intezar nahi karta**: slow kaam (jaise database query) shuru karke agle user ki taraf chala jata hai, aur jab nateeja tayyar ho to wapas aata hai. Jo hissa ye sambhalta hai use **event loop** kehte hain.

Is ki ek tarteeb hai: aam code **pehle** chalta hai, phir promise ke chhote callbacks, phir timers.

</Ur>
</Tr>

```javascript
console.log("1. synchronous: start");
setTimeout(() => console.log("4. timer callback (macrotask)"), 0);
Promise.resolve().then(() => console.log("3. promise callback (microtask)"));
console.log("2. synchronous: end");
```

```text output
1. synchronous: start
2. synchronous: end
3. promise callback (microtask)
4. timer callback (macrotask)
```

<Happened>
<Tr>
<En>

- The two normal `console.log` lines run first (1 and 2).
- The promise callback runs next (3).
- The timer runs last (4), even though its delay is **0**. A timer always waits until the current code has finished.

</En>
<Ur>

- Do aam `console.log` lines pehle chalti hain (1 aur 2).
- Phir promise ka callback chalta hai (3).
- Timer sab se aakhir me chalta hai (4), halanke us ki deri **0** hai. Timer hamesha mojooda code khatam hone ka intezar karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="One slow calculation freezes everyone">

<Tr>
<En>

Because Node.js has only **one** thread for your code, a long **calculation** (not waiting, but busy working) blocks **everything else**. Every other user has to wait until it finishes.

</En>
<Ur>

Kyunke Node.js me aap ke code ke liye sirf **ek** thread hai, ek lamba **hisaab** (intezar nahi, balke masroof kaam) **baqi sab kuch** rok deta hai. Har doosre user ko us ke khatam hone tak intezar karna parta hai.

</Ur>
</Tr>

```javascript
const start = Date.now();
setTimeout(() => console.log(`timer wanted 10 ms, ran after ${Date.now() - start >= 200 ? "200+" : "<200"} ms`), 10);

const until = Date.now() + 200;
while (Date.now() < until) {}           // 200 ms of pure CPU work blocks the only JS thread
console.log("heavy work finished");
```

```text output
heavy work finished
timer wanted 10 ms, ran after 200+ ms
```

<Happened>
<Tr>
<En>

- The timer asked to run after **10 ms**.
- But a loop kept the only thread busy for **200 ms**, so the timer had to wait.
- On a server, that timer could be **another user's request**. Heavy work (image resizing, big PDFs) should go to a **separate worker** or a **job queue**.

</En>
<Ur>

- Timer ne **10 ms** baad chalne ka kaha tha.
- Lekin ek loop ne akele thread ko **200 ms** masroof rakha, isliye timer ko intezar karna para.
- Server par wo timer **kisi doosre user ki request** ho sakti hai. Bhaari kaam (images chhoti bari karna, bari PDFs) **alag worker** ya **job queue** me jana chahiye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Race conditions: two people buy the last item">

<Tr>
<En>

A **race condition** happens when two tasks **read** the same data, both **change** it, and both **write** it back. One write overwrites the other, and the result depends on timing.

Here, only **one** item is left in stock, and two customers click "Buy" at the same moment:

</En>
<Ur>

**Race condition** tab hoti hai jab do kaam ek hi data **parhte** hain, dono use **badalte** hain, aur dono wapas **likhte** hain. Ek ki likhai doosre ko mita deti hai, aur nateeja waqt par munhasir hota hai.

Yahan stock me sirf **ek** item bacha hai, aur do customers ek hi waqt me "Buy" dabate hain:

</Ur>
</Tr>

```javascript
let stock = 1;                                   // only ONE item left
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function buy(user) {
  const current = stock;                         // 1. read
  await sleep(10);                               // 2. e.g. waiting for the payment API
  if (current > 0) {
    stock = current - 1;                         // 3. write back
    console.log(`${user}: order confirmed`);
  } else {
    console.log(`${user}: sold out`);
  }
}

await Promise.all([buy("Sam"), buy("Emma")]);    // two requests arrive at the same time
console.log("stock now:", stock, "— but two people were sold the last item!");
```

```text output
Sam: order confirmed
Emma: order confirmed
stock now: 0 — but two people were sold the last item!
```

<Happened>
<Tr>
<En>

- Both Sam and Emma **read** `stock = 1` before either one updated it.
- Both thought "1 left, that's mine!", so **both** got a confirmed order for **one** item.
- This happens in real shops during flash sales, and with coupons and bank balances.

</En>
<Ur>

- Sam aur Emma dono ne `stock = 1` **parha**, is se pehle ke koi bhi update karta.
- Dono ne socha "1 bacha hai, mera hai!", isliye **ek** item ke liye **dono** ka order confirm ho gaya.
- Ye asal dukaanon me flash sales ke dauran hota hai, aur coupons aur bank balance ke saath bhi.

</Ur>
</Tr>
</Happened>

<Tr>
<En>
The fix: **check and update in one step**, with no waiting in between:
</En>
<Ur>
Hal: **check aur update ek hi qadam me** karein, beech me koi intezar na ho:
</Ur>
</Tr>

```javascript
let stock = 1;
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function buy(user) {
  if (stock > 0) { stock -= 1; }                 // atomic: no await between check and update
  else { console.log(`${user}: sold out`); return; }
  await sleep(10);                               // slow work after reserving
  console.log(`${user}: order confirmed`);
}

await Promise.all([buy("Sam"), buy("Emma")]);
console.log("stock now:", stock);
```

```text output
Emma: sold out
Sam: order confirmed
stock now: 0
```

<Happened>
<Tr>
<En>

- Sam checks and takes the item **in one step**. When Emma checks, it's already 0, so she sees "sold out".
- In a real app this one step is done by the **database**, for example: `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0`. That stays safe even with many servers.

</En>
<Ur>

- Sam check aur item lena **ek hi qadam me** karta hai. Jab Emma check karti hai, stock pehle hi 0 hota hai, to use "sold out" dikhta hai.
- Asal app me ye ek qadam **database** karta hai, misaal ke taur par: `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0`. Ye kai servers ke saath bhi mehfooz rehta hai.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Heavy work on the Node.js thread">

<Tr>
<En>Resizing images or making big PDFs inside a request freezes every other user.</En>
<Ur>Request ke andar images chhoti bari karna ya bari PDFs banana baqi har user ko rok deta hai.</Ur>
</Tr>

</Bad>
<Good title="Move it to a worker">

<Tr>
<En>Put heavy jobs in a **job queue** (like BullMQ) handled by a separate worker process.</En>
<Ur>Bhaari kaam **job queue** (jaise BullMQ) me daalein jise alag worker process sambhale.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Read, wait, then write">

```javascript
const current = stock;
await payment();
stock = current - 1;
```

</Bad>
<Good title="Check and update in one step">

```javascript
if (stock > 0) stock -= 1;
await payment();
```

<Tr>
<En>In a real app, let the database do it in one `UPDATE`.</En>
<Ur>Asal app me database ko ek `UPDATE` me ye karne dein.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Running everything as root">

<Tr>
<En>If an attacker breaks into a process running as root, they control the whole server.</En>
<Ur>Agar attacker root ki tarah chalte process me ghus jaye, to poora server us ke qabze me.</Ur>
</Tr>

</Bad>
<Good title="One limited user per service">

<Tr>
<En>Run each service as its own normal user (in Docker: `USER node`).</En>
<Ur>Har service ko apne aam user ki tarah chalayen (Docker me: `USER node`).</Ur>
</Tr>

</Good>
</Compare>

<Challenge title="Fix the bank account">

<Tr>
<En>
Two withdrawals of 80 happen at the same time from a balance of 100. Right now **both** succeed and the balance goes **negative**. Press **Edit**, fix `withdraw` so only one succeeds, and **Run** it. The balance should end at **20**.
</En>
<Ur>
100 ke balance se ek hi waqt me 80 ki do withdrawals hoti hain. Abhi **dono** kamyab hoti hain aur balance **manfi** ho jata hai. **Edit** dabayen, `withdraw` theek karein taake sirf ek kamyab ho, aur **Run** karein. Aakhir me balance **20** hona chahiye.
</Ur>
</Tr>

```javascript
let balance = 100;
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function withdraw(amount) {
  const current = balance;
  await sleep(10);
  if (current >= amount) {
    balance = current - amount;
    console.log("withdrew", amount);
  } else {
    console.log("refused", amount);
  }
}

await Promise.all([withdraw(80), withdraw(80)]);
console.log("balance:", balance);
```

```text output
withdrew 80
withdrew 80
balance: 20
```

<Hint>
<Tr>
<En>Notice the output says balance 20, but **160** was paid out from 100! Check `balance >= amount` and subtract **before** the `await`.</En>
<Ur>Dhyan dein: output balance 20 dikhata hai, lekin 100 me se **160** de diye gaye! `balance >= amount` check karein aur `await` se **pehle** minus karein.</Ur>
</Tr>
</Hint>

<Solution>

```javascript
let balance = 100;
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function withdraw(amount) {
  if (balance < amount) { console.log("refused", amount); return; }
  balance -= amount;                // check and update in one step
  await sleep(10);                  // slow work afterwards
  console.log("withdrew", amount);
}

await Promise.all([withdraw(80), withdraw(80)]);
console.log("balance:", balance);
```

```text output
refused 80
withdrew 80
balance: 20
```

</Solution>

## Remember

<Takeaways>
<Tr>
<En>

- A **program** is a file; a **process** is it running, with a **PID** and private memory.
- **Threads** are workers inside a process and **share** its memory.
- **Concurrency** = taking turns; **parallelism** = truly at the same time on several cores.
- The **scheduler** switches between threads thousands of times per second.
- **Node.js** runs your JavaScript on one thread with an **event loop**: great at waiting, bad at long calculations.
- Order in JavaScript: normal code → promise callbacks → timers.
- **Race conditions** happen when you read, wait, then write. **Check and update in one step.**

<DeepDive title="Threads share memory: even Node.js has several">

Threads are several flows of execution inside **one** process, all sharing the same memory. That makes cooperation cheap but dangerous: two threads can change the same data at the same time.

```bash
node -e 'setTimeout(() => {}, 2000)' &
pid=$!
sleep 0.5
threads=$(ps -o nlwp= -p "$pid" | tr -d ' ')
(( threads > 1 )) && echo "Node.js runs JavaScript on one thread, but the process has several helper threads"
kill "$pid"
```

```text output
Node.js runs JavaScript on one thread, but the process has several helper threads
```

Even "single-threaded" Node.js has extra threads for garbage collection and the **libuv** thread pool (file system, DNS, crypto). Only **your JavaScript** runs on one thread.

</DeepDive>

<DeepDive title="Thread-per-request vs event loop servers">

- **Thread-per-request:** each request gets its own thread, which can block while waiting. Simple to program, but each thread costs memory (often ~1 MB). Classic Java (Spring), PHP-FPM.
- **Event loop:** one thread handles all requests and never waits. Handles tens of thousands of idle connections cheaply, but must never be blocked by heavy work. Node.js, NGINX, Python asyncio.

A thread-per-request restaurant has one waiter per table: 500 tables need 500 waiters standing around while food cooks. An event loop is one fast waiter who never waits at a table.

</DeepDive>

<DeepDive title="The scheduler, context switches and priorities">

The scheduler gives each thread a time slice of a few milliseconds, then saves its state and loads another's: a **context switch**. This costs a little time on every switch. `nice -n 10 command` runs a command with lower priority so it doesn't slow down important services. `vmstat 1` shows context switches per second (column `cs`).

</DeepDive>

<DeepDive title="Process states and signals">

A process is always in a state:

| STAT | Meaning |
| --- | --- |
| `R` | Running or ready to run |
| `S` | Sleeping: waiting for something (most processes, most of the time) |
| `D` | Uninterruptible sleep: usually waiting for disk; can't be killed until it returns |
| `T` | Stopped (Ctrl+Z) |
| `Z` | Zombie: finished, waiting for its parent to collect the exit code |

**Signals** are messages to processes: `kill PID` sends **SIGTERM** ("please stop", can be handled gracefully); `kill -9 PID` sends **SIGKILL** ("stop now", can't be refused). Docker and Kubernetes send SIGTERM first and SIGKILL after a grace period, so apps should handle SIGTERM to avoid dropping requests. See **Processes and Signals** in the Linux topic.

</DeepDive>

<DeepDive title="Hands-on: parallel jobs and a race between processes">

```bash
# 1. Every command is a process with a parent
bash -c 'echo "child PID differs from parent: $([[ $$ != $PPID ]] && echo yes)"'

# 2. Run three jobs in parallel and wait for all of them
for n in 1 2 3; do (sleep 0.$n; echo "job $n done") & done
wait
echo "all jobs finished"

# 3. Processes do not share variables
x=1; (x=2); echo "x is still $x"

# 4. A race condition between processes writing one counter file
echo 0 > counter
for i in $(seq 1 50); do ( n=$(cat counter); echo $((n + 1)) > counter ) & done
wait
echo "expected 50, got $(cat counter) (often less: lost updates)" | sed -E 's/got [0-9]+/got N/'

# 5. The same with a lock: always correct
echo 0 > counter
for i in $(seq 1 50); do ( flock 9; n=$(cat counter); echo $((n + 1)) > counter ) 9> counter.lock & done
wait
echo "with flock: $(cat counter)"
```

```text output
child PID differs from parent: yes
job 1 done
job 2 done
job 3 done
all jobs finished
x is still 1
expected 50, got N (often less: lost updates)
with flock: 50
```

Run step 4 a few times: the number changes from run to run, the classic sign of a race condition. `flock` makes each read-and-write a protected, one-at-a-time step.

</DeepDive>

<DeepDive title="Real world: scaling an Express API on a 4-core server">

1. **One process, one core:** Node uses one thread for JavaScript, so 3 of the 4 cores sit idle. The team runs **4 container replicas** (or PM2 cluster mode) behind Nginx.
2. **Blocking:** invoice PDFs generated inside the request freeze the event loop for 800 ms each. They move PDF generation to a **BullMQ queue** with separate workers.
3. **Race condition:** during a flash sale, stock goes negative. They switch to an atomic `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0` and check the affected row count.
4. **Deploys drop requests:** the app ignored `SIGTERM`, so every deploy killed in-flight checkouts. They add graceful shutdown and a readiness probe.

</DeepDive>

<DeepDive title="Security lens">

- **Least privilege:** run each service as its own unprivileged user. In Dockerfiles use `USER node`; in Kubernetes set `runAsNonRoot: true`.
- **Suspicious process trees are a top detection signal.** `node` or `nginx` starting `sh`, `bash`, `curl` or `wget` usually means command injection. Security tools like Falco alert on exactly this.
- **Command injection:** `exec("convert " + userFilename)` lets an attacker add `; rm -rf /`. Use `execFile`/`spawn` with an argument array, never a shell string.
- **Secrets in process listings:** command-line arguments are visible to every user via `ps`. Never pass passwords as CLI arguments.
- **Race conditions are vulnerabilities**, called **TOCTOU** (time-of-check to time-of-use): redeeming one coupon twice, withdrawing more than the balance, bypassing rate limits with parallel requests.
- **Resource limits** (`ulimit`, cgroups, container limits) stop one runaway process, like a fork bomb, from taking down the server.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a process and a thread?">
A process is a running program with its own isolated memory space, PID, user identity and file descriptors. A thread is an execution path inside a process; threads share the process's memory and resources. Processes are isolated, safer and heavier; threads are lighter and communicate through shared memory, which requires synchronisation to avoid race conditions.
</QA>

<QA q="Node.js is single-threaded. How does it handle thousands of concurrent requests?">
JavaScript runs on one thread, but I/O is non-blocking: network and file operations are delegated to the operating system or libuv's thread pool, and their callbacks are queued. The event loop runs those callbacks when the thread is free. Since most web requests spend their time waiting on I/O, one thread can serve many requests concurrently, as long as no handler does long CPU-bound work.
</QA>

<QA q="What is a race condition? Give an example and a fix.">
A race condition is a bug where the result depends on the timing of concurrent operations on shared data. Example: two withdrawals both read a balance of 100 and both write their own result, losing one update. Fixes: atomic database updates (SET balance = balance - 30 WHERE balance >= 30), transactions with row locks, or mutexes in threaded code.
</QA>

<QA q="What is the difference between SIGTERM and SIGKILL?">
SIGTERM (15) asks a process to terminate; it can catch it and shut down gracefully. SIGKILL (9) cannot be caught; the kernel ends the process immediately. Docker and Kubernetes send SIGTERM first and SIGKILL after a grace period.
</QA>

<QA q="What is the difference between concurrency and parallelism?">
Concurrency is making progress on multiple tasks by interleaving them, which works even on one core. Parallelism is executing multiple tasks at the same instant on multiple cores. Node.js's event loop gives concurrency; worker threads, multiple processes or replicas give parallelism.
</QA>

</DeepDive>
