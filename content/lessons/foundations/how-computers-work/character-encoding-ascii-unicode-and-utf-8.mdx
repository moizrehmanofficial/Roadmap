<Tr>
<En>
A computer can't store letters, only **numbers**. So everyone agrees on a **codebook**: which number means which letter. Today that codebook is **Unicode**, and the way we save it as bytes is **UTF-8**. Use UTF-8 everywhere.
</En>
<Ur>
Computer letters nahi rakh sakta, sirf **numbers**. Isliye sab ek **codebook** par mutafiq hote hain: kaun sa number kis letter ka hai. Aaj wo codebook **Unicode** hai, aur use bytes me save karne ka tareeqa **UTF-8** hai. Har jagah UTF-8 istemal karein.

## At a glance

<Glance>
<What>
<Tr>
<En>

**Character encoding** is the rule for turning letters into numbers (and bytes) and back again.

- **ASCII** (1963): numbers for 128 English characters. `A` = 65.
- **Unicode**: a number for **every** character in **every** language, plus emoji. `م` = 1605, `😀` = 128512.
- **UTF-8**: the most common way to store Unicode numbers as bytes. English letters take 1 byte; Arabic or Urdu letters take 2; emoji take 4.

</En>
<Ur>

**Character encoding** wo qaida hai jo letters ko numbers (aur bytes) me badalta hai aur wapas bhi.

- **ASCII** (1963): 128 English characters ke numbers. `A` = 65.
- **Unicode**: **har** zabaan ke **har** character, aur emoji, ka number. `م` = 1605, `😀` = 128512.
- **UTF-8**: Unicode numbers ko bytes me rakhne ka sab se aam tareeqa. English letter 1 byte leta hai; Arabic ya Urdu letter 2; emoji 4.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

When encoding goes wrong, users see:

- `????` instead of their name
- garbage like `Ø¢Ù¾` instead of `آپ`
- messages with emoji that **fail to save**
- a "max 20 characters" check that counts wrong

These bugs are very common, and once you understand encoding, they're easy to fix.

</En>
<Ur>

Jab encoding ghalat ho jaye, users ko ye dikhta hai:

- apne naam ki jagah `????`
- `آپ` ki jagah `Ø¢Ù¾` jaisa kachra
- emoji wale messages jo **save hi nahi hote**
- "zyada se zyada 20 characters" wala check jo ghalat ginta hai

Ye bugs bohot aam hain, aur encoding samajh aa jaye to inhe theek karna aasaan hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- building any website or app that accepts text
- creating a database or table
- importing or exporting CSV files
- writing scripts on Windows that run on Linux servers

</En>
<Ur>

- koi bhi website ya app banate waqt jo text leti ho
- database ya table banate waqt
- CSV files import ya export karte waqt
- Windows par scripts likhte waqt jo Linux servers par chalengi

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Writing text: **letter → number (Unicode) → bytes (UTF-8)**.
Reading text: **bytes → number → letter**.

Both sides must use the **same** codebook. If one side writes UTF-8 and the other reads something else, you get garbage.

</En>
<Ur>

Text likhna: **letter → number (Unicode) → bytes (UTF-8)**.
Text parhna: **bytes → number → letter**.

Dono taraf **ek hi** codebook honi chahiye. Agar ek taraf UTF-8 likhe aur doosri kuch aur parhe, to kachra aata hai.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Two friends write secret messages with a **codebook**: "1 = A, 2 = B, 3 = C…". The message `8 9` means **HI**, but only if both use the **same codebook**. If your friend uses a different one, the same numbers turn into nonsense.

Character encodings are exactly these codebooks. Almost every text bug happens because **two systems used different codebooks**.

</En>
<Ur>

Do dost ek **codebook** se khufiya paigham likhte hain: "1 = A, 2 = B, 3 = C…". Paigham `8 9` ka matlab **HI** hai, lekin sirf tab jab dono **ek hi codebook** istemal karein. Agar dost doosri istemal kare, to wahi numbers bekaar ban jate hain.

Character encodings bilkul aisi hi codebooks hain. Taqreeban har text bug is liye hota hai ke **do systems ne alag alag codebooks istemal kin**.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Letters are really numbers (ASCII)">

<Tr>
<En>

The first widely used codebook was **ASCII**. It gave numbers to 128 characters: English letters, digits, punctuation and a few special codes (like "new line" = 10). JavaScript can show you these numbers.

</En>
<Ur>

Pehli aam codebook **ASCII** thi. Is ne 128 characters ko numbers diye: English letters, digits, nishanat aur kuch khaas codes (jaise "nayi line" = 10). JavaScript aap ko ye numbers dikha sakta hai.

</Ur>
</Tr>

```javascript
for (const ch of ["A", "a", "0", " "]) {
  console.log(JSON.stringify(ch), "=", ch.charCodeAt(0));
}
console.log("Newline is", "\n".charCodeAt(0), "| 72, 105 →", String.fromCharCode(72, 105));
```

```text output
"A" = 65
"a" = 97
"0" = 48
" " = 32
Newline is 10 | 72, 105 → Hi
```

<Happened>
<Tr>
<En>

- `charCodeAt(0)` gives the number of the first character: `A` is 65, `a` is 97.
- The **character** `"0"` is 48, not the number 0. That's why `"5" + "5"` is `"55"`: it's joining text, not adding numbers.
- `String.fromCharCode(72, 105)` goes the other way: numbers 72 and 105 become **Hi**.

</En>
<Ur>

- `charCodeAt(0)` pehle character ka number deta hai: `A` 65 hai, `a` 97.
- **Character** `"0"` ka number 48 hai, 0 nahi. Isi liye `"5" + "5"` ka jawab `"55"` hai: ye text jor raha hai, numbers jama nahi kar raha.
- `String.fromCharCode(72, 105)` ulta kaam karta hai: numbers 72 aur 105 **Hi** ban jate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Unicode: one number for every character in the world">

<Tr>
<En>

ASCII only had English. Before Unicode, every region made its **own** codebook for numbers 128–255, so the same byte meant a different letter on different computers. Text moved between them became garbage.

**Unicode** fixed this with **one** worldwide list: every character in every language (and emoji) gets its own number, called a **code point**, written like `U+0645`.

</En>
<Ur>

ASCII me sirf English thi. Unicode se pehle har ilaqe ne numbers 128–255 ke liye **apni** codebook bana li, isliye ek hi byte alag computers par alag letter ban jata. Ek se doosre par jane wala text kachra ban jata.

**Unicode** ne ye **ek** aalmi list se theek kiya: har zabaan ke har character (aur emoji) ko apna number milta hai, jise **code point** kehte hain, aur aise likhte hain: `U+0645`.

</Ur>
</Tr>

```javascript
for (const ch of ["A", "é", "م", "آ", "😀"]) {
  const cp = ch.codePointAt(0);
  console.log(ch, "→ U+" + cp.toString(16).toUpperCase().padStart(4, "0"), `(${cp})`);
}
```

```text output
A → U+0041 (65)
é → U+00E9 (233)
م → U+0645 (1605)
آ → U+0622 (1570)
😀 → U+1F600 (128512)
```

<Happened>
<Tr>
<En>

- `A` keeps its old ASCII number, 65 (`U+0041` in hex).
- `é` (French), `م` and `آ` (Arabic script) and `😀` (emoji) all have their **own** numbers.
- There are about **150,000** characters in Unicode today.

</En>
<Ur>

- `A` apna purana ASCII number 65 hi rakhta hai (hex me `U+0041`).
- `é` (French), `م` aur `آ` (Arabic script) aur `😀` (emoji) sab ke **apne** numbers hain.
- Aaj Unicode me taqreeban **150,000** characters hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="UTF-8: how those numbers become bytes">

<Tr>
<En>

Unicode gives each character a number. **UTF-8** decides how to store that number in **bytes**:

- small numbers (English) → **1 byte**, exactly like ASCII
- bigger numbers (Arabic, Urdu, most of Europe) → **2 bytes**
- other scripts and symbols like € → **3 bytes**
- emoji → **4 bytes**

About 98% of websites use UTF-8.

</En>
<Ur>

Unicode har character ko number deta hai. **UTF-8** tay karta hai ke us number ko **bytes** me kaise rakha jaye:

- chhote numbers (English) → **1 byte**, bilkul ASCII ki tarah
- bare numbers (Arabic, Urdu, zyada tar Europe) → **2 bytes**
- doosre scripts aur € jaise nishan → **3 bytes**
- emoji → **4 bytes**

Taqreeban 98% websites UTF-8 istemal karti hain.

</Ur>
</Tr>

```javascript
const enc = new TextEncoder();
for (const ch of ["A", "é", "م", "€", "😀"]) {
  const bytes = [...enc.encode(ch)].map((b) => b.toString(16).padStart(2, "0"));
  console.log(ch, "→", bytes.length, "byte(s):", bytes.join(" "));
}
```

```text output
A → 1 byte(s): 41
é → 2 byte(s): c3 a9
م → 2 byte(s): d9 85
€ → 3 byte(s): e2 82 ac
😀 → 4 byte(s): f0 9f 98 80
```

<Happened>
<Tr>
<En>

- `TextEncoder` turns text into UTF-8 bytes (shown in hex).
- `A` is one byte, `41`, the same as in ASCII. So old English text is already valid UTF-8.
- `😀` needs four bytes. Remember this; it causes bugs in the next steps.

</En>
<Ur>

- `TextEncoder` text ko UTF-8 bytes me badalta hai (hex me dikhaye gaye).
- `A` ek byte hai, `41`, bilkul ASCII jaisa. Isliye purana English text pehle se hi theek UTF-8 hai.
- `😀` ko chaar bytes chahiyen. Ye yaad rakhein; agle qadmon me ye bugs ki wajah banta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Mojibake: reading with the wrong codebook">

<Tr>
<En>

If text was saved as UTF-8 but someone **reads** those bytes with an old codebook (like Windows-1252), every multi-byte letter turns into strange symbols. This garbage has a name: **mojibake**.

</En>
<Ur>

Agar text UTF-8 me save hua ho lekin koi un bytes ko purani codebook (jaise Windows-1252) se **parhe**, to har kai-byte wala letter ajeeb nishanon me badal jata hai. Is kachre ka naam hai: **mojibake**.

</Ur>
</Tr>

```javascript
const original = "آپ کیسے ہیں؟ café €";
const utf8Bytes = new TextEncoder().encode(original);
const wrong = new TextDecoder("windows-1252").decode(utf8Bytes);   // read with the wrong codebook
const right = new TextDecoder("utf-8").decode(utf8Bytes);
console.log("wrong:", wrong);
console.log("right:", right);
```

```text output
wrong: Ø¢Ù¾ Ú©ÛŒØ³Û’ ÛÛŒÚºØŸ cafÃ© â‚¬
right: آپ کیسے ہیں؟ café €
```

<Happened>
<Tr>
<En>

- The **bytes are exactly the same** in both lines. Only the codebook used to **read** them is different.
- Read as Windows-1252, the Urdu sentence becomes `Ø¢Ù¾ Ú©ÛŒØ³Û’…`, `café` becomes `cafÃ©`, and `€` becomes `â‚¬`.
- Tip: when you see lots of `Ø`, `Ù` or `Ã`, think **"UTF-8 text read with the wrong codebook"**. The fix is to make every part use UTF-8, not to "find and replace" the garbage.

</En>
<Ur>

- Dono lines me **bytes bilkul ek jaise** hain. Sirf unhe **parhne** wali codebook alag hai.
- Windows-1252 se parhne par Urdu jumla `Ø¢Ù¾ Ú©ÛŒØ³Û’…` ban jata hai, `café` `cafÃ©` ban jata hai, aur `€` `â‚¬`.
- Nuskha: jab bohot saare `Ø`, `Ù` ya `Ã` dikhein, to samjhein **"UTF-8 text ghalat codebook se parha gaya"**. Hal ye hai ke har hissa UTF-8 istemal kare, kachre ko "find and replace" karna nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="One text, three different 'lengths'">

<Tr>
<En>

How long is a piece of text? It depends on what you count:

- **bytes**: how much space it takes when saved
- **`.length`**: what JavaScript counts (a special unit called "UTF-16 code units")
- **characters**: what a **person** sees and counts

For English these are all the same. For other languages and emoji, they're **not**.

</En>
<Ur>

Text kitna lamba hai? Ye is par munhasir hai ke aap kya gin rahe hain:

- **bytes**: save karne par kitni jagah leta hai
- **`.length`**: jo JavaScript ginta hai (ek khaas unit jise "UTF-16 code units" kehte hain)
- **characters**: jo ek **insaan** dekhta aur ginta hai

English ke liye ye sab barabar hain. Doosri zabanon aur emoji ke liye **nahi**.

</Ur>
</Tr>

```javascript
const words = ["hello", "آپ", "😀", "👍🏽", "👨‍👩‍👧"];
const seg = new Intl.Segmenter("en", { granularity: "grapheme" });
for (const s of words) {
  console.log(
    s.padEnd(6),
    "bytes:", new TextEncoder().encode(s).length,
    "| .length:", s.length,
    "| code points:", [...s].length,
    "| characters:", [...seg.segment(s)].length
  );
}
```

```text output
hello  bytes: 5 | .length: 5 | code points: 5 | characters: 5
آپ     bytes: 4 | .length: 2 | code points: 2 | characters: 2
😀     bytes: 4 | .length: 2 | code points: 1 | characters: 1
👍🏽   bytes: 8 | .length: 4 | code points: 2 | characters: 1
👨‍👩‍👧 bytes: 18 | .length: 8 | code points: 5 | characters: 1
```

<Happened>
<Tr>
<En>

- `hello`: every count is 5. English is easy.
- `آپ`: 2 characters, but **4 bytes**.
- `😀`: 1 character, but JavaScript's `.length` says **2**.
- `👍🏽` (thumbs up with a skin tone) is really 2 code points shown as 1 character.
- The family emoji is 5 code points joined together, **18 bytes**, but one character on screen.
- So decide which length your rule means: **characters** for what users see ("max 20 characters"), **bytes** for storage limits.

</En>
<Ur>

- `hello`: har ginti 5 hai. English aasaan hai.
- `آپ`: 2 characters, lekin **4 bytes**.
- `😀`: 1 character, lekin JavaScript ka `.length` **2** kehta hai.
- `👍🏽` (skin tone wala thumbs up) asal me 2 code points hai jo 1 character dikhta hai.
- Family wala emoji 5 code points ka jora hua hai, **18 bytes**, lekin screen par ek character.
- To tay karein ke aap ka qaida kaun si lambai ki baat karta hai: users jo dekhte hain us ke liye **characters** ("max 20 characters"), storage ki had ke liye **bytes**.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Same look, different letters: normalisation">

<Tr>
<En>

Some characters can be written in **two ways** that look identical. `é` can be one code point, or `e` plus a separate accent mark. They look the same but the computer says they're **different**. This breaks logins and searches.

The fix: **normalise** text before comparing or saving it.

</En>
<Ur>

Kuch characters **do tareeqon** se likhe ja sakte hain jo bilkul ek jaise dikhte hain. `é` ek code point bhi ho sakta hai, ya `e` aur alag accent ka nishan. Dikhne me ek jaise, lekin computer kehta hai ye **alag** hain. Is se login aur search kharab hote hain.

Hal: compare ya save karne se pehle text ko **normalise** karein.

</Ur>
</Tr>

```javascript
const a = "café";            // é as one code point
const b = "cafe\u0301";     // e + a separate accent mark (U+0301)
console.log(a, b, "equal?", a === b, "| lengths:", a.length, b.length);
console.log("after NFC normalisation equal?", a.normalize("NFC") === b.normalize("NFC"));
```

```text output
café café equal? false | lengths: 4 5
after NFC normalisation equal? true
```

<Happened>
<Tr>
<En>

- Both words look like `café`, but one is 4 units long and the other 5, so `===` says `false`.
- `.normalize("NFC")` turns both into the same standard form, and now they're equal.

</En>
<Ur>

- Dono lafz `café` dikhte hain, lekin ek 4 units ka hai aur doosra 5 ka, isliye `===` `false` kehta hai.
- `.normalize("NFC")` dono ko ek hi standard shakal me badal deta hai, aur ab dono barabar hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Windows line endings break Linux scripts">

<Tr>
<En>

Another invisible difference: at the end of each line, **Linux and Mac** save one hidden character (LF, `\n`), but **Windows** saves two (CR + LF, `\r\n`). A script written on Windows can fail on a Linux server with a strange error like `$'\r': command not found`.

Some Windows tools also add an invisible **BOM** marker at the very start of UTF-8 files.

</En>
<Ur>

Ek aur nazar na aane wala farq: har line ke aakhir me **Linux aur Mac** ek chhupa hua character save karte hain (LF, `\n`), lekin **Windows** do (CR + LF, `\r\n`). Windows par likhi script Linux server par ajeeb error ke saath fail ho sakti hai, jaise `$'\r': command not found`.

Kuch Windows tools UTF-8 files ke bilkul shuru me ek nazar na aane wala **BOM** nishan bhi daal dete hain.

</Ur>
</Tr>

```bash
printf 'echo hello\r\n' > win.sh
printf '\xef\xbb\xbfname,city\n' > excel.csv
file win.sh excel.csv | sed 's/,  *with/ with/'
cat -A win.sh
sed -i 's/\r$//' win.sh && bash win.sh
```

```text output
win.sh:    ASCII text with CRLF line terminators
excel.csv: Unicode text, UTF-8 (with BOM) text
echo hello^M$
hello
```

<Happened>
<Tr>
<En>

- `file` detects the Windows line endings (**CRLF**) and the **BOM**.
- `cat -A` shows hidden characters: `^M` is the extra Windows character, `$` is the end of the line.
- `sed -i 's/\r$//'` removes the extra character, and the script runs correctly.
- Prevent it: set your editor to **UTF-8, LF**. VS Code shows both in the bottom-right corner.

</En>
<Ur>

- `file` Windows wali line endings (**CRLF**) aur **BOM** pehchan leta hai.
- `cat -A` chhupe characters dikhata hai: `^M` Windows ka extra character hai, `$` line ka aakhir.
- `sed -i 's/\r$//'` extra character hata deta hai, aur script theek chal jati hai.
- Bachao: apne editor ko **UTF-8, LF** par set karein. VS Code dono cheezen neeche dayen kone me dikhata hai.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Not saying UTF-8 anywhere">

<Tr>
<En>Leaving the encoding unset in HTML, the database and the connection, and hoping for the best.</En>
<Ur>HTML, database aur connection me encoding set na karna, aur umeed rakhna ke sab theek hoga.</Ur>
</Tr>

</Bad>
<Good title="UTF-8 in every layer">

<Tr>
<En>`<meta charset="utf-8">` in HTML, `charset=utf-8` in HTTP headers, UTF-8 (`utf8mb4` in MySQL) for the database **and** the connection.</En>
<Ur>HTML me `<meta charset="utf-8">`, HTTP headers me `charset=utf-8`, database **aur** connection dono me UTF-8 (MySQL me `utf8mb4`).</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="MySQL's old 'utf8'">

<Tr>
<En>MySQL's `utf8` only stores up to 3 bytes per character, so emoji (4 bytes) fail to save.</En>
<Ur>MySQL ka `utf8` har character ke zyada se zyada 3 bytes rakhta hai, isliye emoji (4 bytes) save nahi hote.</Ur>
</Tr>

</Bad>
<Good title="utf8mb4">

<Tr>
<En>`utf8mb4` is MySQL's real, complete UTF-8.</En>
<Ur>`utf8mb4` MySQL ka asli, mukammal UTF-8 hai.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Counting characters with .length">

```javascript
if (name.length > 20) reject();   // an emoji counts as 2
```

</Bad>
<Good title="Count what users see">

```javascript
const count = [...new Intl.Segmenter().segment(name)].length;
```

</Good>
</Compare>

<DeepDive title="The code page mess before Unicode">

Before Unicode, each region extended ASCII to 256 characters differently: numbers 128–255 meant Western European letters in one **code page**, Arabic letters in another, Cyrillic in another. Byte `0xC7` is `Ç` in Windows-1252 but `ا` (alef) in Windows-1256. Without knowing which code page was used, the bytes can't be read correctly. You still meet this in old Excel/CSV files and legacy databases.

| Standard | Year | Characters | Bytes per character |
| --- | --- | --- | --- |
| ASCII | 1963 | 128 | 1 |
| Code pages (Windows-1252, -1256…) | 1980s | 256, different per language | 1 |
| Unicode | 1991– | ~150,000 | (it's the list) |
| UTF-8 | 1993 | All of Unicode | 1–4 |
| UTF-16 | | All of Unicode | 2 or 4 |

</DeepDive>

<DeepDive title="Byte counts in the terminal">

```bash
for w in "A" "آپ" "😀"; do
  printf '%-4s %s byte(s): %s\n' "$w" "$(printf '%s' "$w" | wc -c)" "$(printf '%s' "$w" | od -An -tx1 | tr -s ' ')"
done
```

```text output
A    1 byte(s):  41
آپ 4 byte(s):  d8 a2 d9 be
😀 4 byte(s):  f0 9f 98 80
```

`wc -c` counts **bytes**. The columns don't line up because Bash's `%-4s` padding also counts bytes, so the 4-byte `آپ` and `😀` get no extra spaces: the same "which length?" problem.

```bash
# 1. Byte counts for different scripts
for w in hello سلام 你好 😀; do printf '%s → %s bytes\n' "$w" "$(printf '%s' "$w" | wc -c)"; done

# 2. Code point of a character (Python)
python3 -c 'for ch in "Aمé😀": print(ch, hex(ord(ch)))'

# 3. Create mojibake and repair it
printf 'آپ' | iconv -f windows-1252 -t utf-8 > broken.txt 2>/dev/null || true
cat broken.txt; echo
iconv -f utf-8 -t windows-1252 broken.txt | cat; echo

# 4. Your terminal locale
locale 2>/dev/null | grep -q 'UTF-8' && echo "locale uses UTF-8" || echo "check your locale (LANG)"
```

```text output
hello → 5 bytes
سلام → 8 bytes
你好 → 6 bytes
😀 → 4 bytes
A 0x41
م 0x645
é 0xe9
😀 0x1f600
Ø¢Ù¾
آپ
locale uses UTF-8
```

`iconv` converts between encodings. Step 3 first creates the classic mojibake (UTF-8 bytes read as Windows-1252), then reverses that mistake.

</DeepDive>

<DeepDive title="Encodings in databases">

```text
-- MySQL / MariaDB
CREATE DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
-- Connection string (Node.js mysql2):  charset: "utf8mb4"

-- PostgreSQL
CREATE DATABASE shop ENCODING 'UTF8';
```

Set the encoding on the database, the tables **and** the connection: all three must match. With the wrong setting, inserts fail ("Incorrect string value: '\xF0\x9F\x98\x80'") or text is silently replaced by `?`.

</DeepDive>

<DeepDive title="Real world: names showing as ????">

An international shop stores customer names in MySQL. Orders with Arabic-script names show as `????`, and orders with emoji in delivery notes fail entirely.

1. The table was created with `latin1`, so those characters can't be stored at all and become `?`. Converting the table to `utf8mb4` fixes new data; old rows have permanently lost their text.
2. Emoji fail because MySQL's legacy `utf8` (an alias for `utf8mb3`) allows at most 3 bytes; emoji need 4.
3. The connection also needs `charset=utf8mb4`; otherwise the driver converts text on the way in.
4. The CSV export opens garbled in Excel; adding a UTF-8 BOM fixes it.
5. "Max 30 characters" on names is enforced with `.length`, rejecting valid names with emoji. They switch to counting graphemes in the UI and a byte limit in the database.

</DeepDive>

<DeepDive title="Security lens">

Encodings let the same text be written in many ways. If a security check looks at one form and the app uses another, the check is bypassed.

- **Filter evasion:** filters have been bypassed with URL encoding, double encoding (`%252e%252e%252f` for `../`), overlong UTF-8 and look-alike characters. Decode and normalise **first**, then validate, and prefer allow-lists over block-lists.
- **Homograph attacks:** Cyrillic "а" (U+0430) looks like Latin "a" (U+0061). `pаypal.com` with a Cyrillic letter is a different domain. Browsers show such domains as Punycode (`xn--...`); your app should prevent look-alike usernames too.
- **Invisible characters:** zero-width spaces and bidirectional control characters can hide text or make code display differently from how it runs ("Trojan Source", 2021).
- **Encoding is not encryption:** Base64 in a JWT payload or a hex "hidden" key is readable by anyone.
- **Length bugs:** byte vs character mismatches have caused buffer overflows in C and validation bypasses in web apps.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between Unicode and UTF-8?">
Unicode is a character set: it assigns a unique number (code point) to every character, such as U+0645. UTF-8 is an encoding: a rule for turning those code points into bytes, using 1 to 4 bytes per character. UTF-16 and UTF-32 are other encodings of the same code points.
</QA>

<QA q="Why is UTF-8 the dominant encoding on the web?">
It is backward compatible with ASCII, compact for English and markup, able to represent every Unicode character, free of byte-order issues, and self-synchronising, so decoders can recover from errors.
</QA>

<QA q="Why does '😀'.length return 2 in JavaScript?">
JavaScript strings are sequences of UTF-16 code units. Characters outside the Basic Multilingual Plane, such as most emoji, need two code units (a surrogate pair). Count code points with [...str].length and user-perceived characters with Intl.Segmenter.
</QA>

<QA q="Users report names showing as 'Ã©' instead of 'é'. What is happening?">
Mojibake: text encoded as UTF-8 (é is the bytes C3 A9) is being decoded as Latin-1 or Windows-1252, where those bytes are "Ã" and "©". Some layer (database connection, column charset, HTTP header, file import) isn't using UTF-8. Trace the data path and make every layer explicitly UTF-8.
</QA>

<QA q="How can character encoding be used to bypass security controls?">
If validation happens on raw input but the application later decodes or normalises it, an attacker can encode a forbidden payload so the check doesn't recognise it, for example double-URL-encoded path traversal or look-alike characters. Canonicalise input once, before validation, and use allow-lists.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="ASCII">7-bit encoding of 128 English characters.</Term>
  <Term name="Unicode">The universal character set covering all writing systems.</Term>
  <Term name="Code point">The number Unicode gives a character, written U+XXXX.</Term>
  <Term name="UTF-8">Variable-length (1–4 byte) encoding of Unicode; the web's default.</Term>
  <Term name="UTF-16">2- or 4-byte encoding used inside JavaScript, Java and Windows.</Term>
  <Term name="Grapheme">What a user sees as one character, possibly several code points.</Term>

  <Term name="Normalisation">Converting equivalent Unicode sequences to one standard form (NFC/NFD).</Term>
  <Term name="BOM">Byte order mark; an optional marker at the start of a text file.</Term>
