<Callout type="tip" title="In one minute">
**ASCII** maps 128 characters (English letters, digits, punctuation) to the numbers 0–127. **Unicode** gives every character in every writing system a number called a **code point** (`A` = U+0041, `م` = U+0645, 😀 = U+1F600). **UTF-8** is the way those code points are stored as bytes: 1 byte for ASCII, 2–4 bytes for everything else. Use UTF-8 everywhere — files, HTML, APIs, databases — and remember that "string length" depends on whether you count bytes, code units or visible characters.
</Callout>

## What is it?

A file, a network packet or a database column only holds bytes. To store text, everyone has to agree on which number means which character. That agreement is a **character encoding**.

| Term | Meaning | Example |
| --- | --- | --- |
| **Character** | An abstract symbol | the letter "A", the Urdu letter "م", "😀" |
| **Character set** | The list of characters that exist and their numbers | Unicode |
| **Code point** | The number assigned to a character | U+0041, U+0645, U+1F600 |
| **Encoding** | How code points are turned into bytes | UTF-8, UTF-16, ASCII |
| **Glyph** | What a character looks like in a font | the shape you see on screen |

### ASCII (1963)

ASCII uses 7 bits: 128 characters. `A` is 65, `a` is 97, `0` is 48, space is 32, newline is 10. Enough for English, nothing else.

### The code page mess

To support other languages, vendors used the 8th bit for 128 extra characters — each in a different way (Latin-1, Windows-1252, Windows-1256 for Arabic script…). The same byte meant different letters on different machines. Text moved between systems turned into nonsense.

### Unicode

Unicode solved this with one universal list: every character from every script — Latin, Arabic, Urdu, Chinese, emoji, maths symbols — gets a unique code point. There is room for over a million code points (U+0000 to U+10FFFF); around 150,000 are assigned.

### UTF-8

Unicode says *which number*; UTF-8 says *which bytes*. It is a **variable-length** encoding:

| Code point range | Bytes | Covers |
| --- | --- | --- |
| U+0000 – U+007F | 1 | ASCII — identical to ASCII bytes |
| U+0080 – U+07FF | 2 | Latin accents, Arabic, Urdu, Hebrew, Greek, Cyrillic |
| U+0800 – U+FFFF | 3 | Most Chinese/Japanese/Korean, Devanagari, many symbols |
| U+10000 – U+10FFFF | 4 | Emoji, rare scripts |

Because ASCII text is valid UTF-8 unchanged, UTF-8 became the default of the web, Linux, JSON, Git and almost every modern API. Well over 95% of websites use it.

**UTF-16** (2 or 4 bytes per character) is used internally by JavaScript, Java and Windows. That detail explains several JavaScript surprises below.

## Why does it matter?

- **Full-stack:** Urdu names, emoji in chat messages and accented characters must survive the round trip: browser → API → database → back. One wrong setting and "معیز" becomes "Ù…Ø¹ÛŒØ²".
- **Databases:** MySQL's old `utf8` stores at most 3 bytes per character and **rejects emoji**; you need `utf8mb4`. Column limits like `VARCHAR(255)` count characters in PostgreSQL but byte limits apply in other places.
- **APIs and files:** CSV exports open garbled in Excel without a BOM; `Content-Type` headers need `charset=utf-8`.
- **DevOps:** log files, shell scripts with Windows line endings (`\r\n`), and container locale settings (`LANG=C.UTF-8`) all cause hard-to-find bugs.
- **Security:** filters that check one representation of a string can be bypassed with another — encodings are a classic evasion tool.

## When and where do you use it?

- The `<meta charset="utf-8">` tag in every HTML page.
- `Content-Type: application/json; charset=utf-8` in API responses.
- Creating databases: PostgreSQL `ENCODING 'UTF8'`, MySQL `utf8mb4`.
- Validating input length: "max 20 characters" for a username containing emoji.
- URL encoding (`%20`, `%D9%85`) and Base64 — both build on top of bytes.
- Reading a hex dump during debugging or forensics.

## How does it work?

### Encoding "Aم😀" as UTF-8

```text
Character   Code point   UTF-8 bytes (hex)     Byte count
A           U+0041       41                    1
م           U+0645       D9 85                 2
😀          U+1F600      F0 9F 98 80           4
                                               ── 7 bytes total
```

UTF-8 is self-synchronising: the first bits of every byte say whether it starts a character (`0xxxxxxx`, `110xxxxx`, `1110xxxx`, `11110xxx`) or continues one (`10xxxxxx`). A program can always find where characters begin, even in the middle of a stream.

### Mojibake: how text gets garbled

Garbled text ("mojibake") almost always means **bytes written in one encoding were read as another**:

```text
"é" written as UTF-8  →  bytes C3 A9
read as Windows-1252  →  C3 = "Ã", A9 = "©"   →  "Ã©"
```

If you see `Ã©`, `â€™` or `Ù…`, some step in your pipeline is decoding UTF-8 as Latin-1/Windows-1252.

### Three different "lengths"

In JavaScript, `"😀".length` is **2**, because JS strings are UTF-16 and this emoji needs two 16-bit units (a "surrogate pair"). And what users see as one character may be several code points: 👍🏽 is a thumb plus a skin-tone modifier; 👨‍👩‍👧 is several people joined by invisible "zero-width joiner" characters.

| Question | How to measure in JS |
| --- | --- |
| Bytes on the wire / in storage | `new TextEncoder().encode(s).length` |
| Code points | `[...s].length` |
| Visible characters (graphemes) | `Intl.Segmenter` |

### Normalisation

Some characters can be written two ways: "é" as one code point (U+00E9) or as "e" + a combining accent (U+0065 U+0301). They look identical but are different strings, so equality checks and database uniqueness fail. **Normalise** (`str.normalize("NFC")`) before comparing or storing identifiers such as usernames.

### Line endings and the BOM

- **Line endings:** Linux/macOS use `\n` (LF); Windows uses `\r\n` (CRLF). A shell script saved with CRLF fails on Linux with `bad interpreter: /bin/bash^M`.
- **BOM:** an optional marker (`EF BB BF`) at the start of a UTF-8 file. Excel uses it to detect UTF-8 in CSVs; many Unix tools and JSON parsers dislike it.

## Hands-on

```javascript
const s = "Aم😀";

// Code points
for (const ch of s) {
  console.log(ch, "U+" + ch.codePointAt(0).toString(16).toUpperCase().padStart(4, "0"));
}

// UTF-8 bytes
const bytes = new TextEncoder().encode(s);
console.log("UTF-8 bytes:", [...bytes].map((b) => b.toString(16).padStart(2, "0")).join(" "));
console.log("byte length:", bytes.length);              // 7

// Three different lengths
const family = "👨‍👩‍👧";
console.log(".length:", family.length);                  // UTF-16 units
console.log("code points:", [...family].length);
console.log("graphemes:", [...new Intl.Segmenter().segment(family)].length); // 1

// Mojibake: decode UTF-8 bytes as the wrong encoding
const utf8 = new TextEncoder().encode("é");
console.log("as latin1:", new TextDecoder("windows-1252").decode(utf8)); // Ã©

// Normalisation: same look, different strings
const a = "café", b = "café";
console.log(a === b, a.normalize("NFC") === b.normalize("NFC"));         // false true

// URL encoding and Base64 operate on UTF-8 bytes
console.log(encodeURIComponent("م"));                    // %D9%85
console.log(btoa(String.fromCharCode(...new TextEncoder().encode("م")))); // 2YU=
```

## Real-world example

A Pakistani e-commerce site stores customer names in MySQL. Orders with Urdu names show as `????`, and orders with emoji in delivery notes fail entirely.

1. The table was created with `latin1`, so Urdu characters cannot be stored at all: they are replaced with `?`. Converting the table to `utf8mb4` fixes new data; old rows have permanently lost their text.
2. Emoji fail because MySQL's legacy `utf8` (an alias for `utf8mb3`) allows at most 3 bytes; emoji need 4. `utf8mb4` fixes this too.
3. The connection itself also needs `charset=utf8mb4`; otherwise the driver converts text on the way in.
4. The CSV export for the accounts team opens garbled in Excel; adding a UTF-8 BOM fixes it.
5. "Max 30 characters" on names is enforced with `.length`, rejecting a valid name with emoji early. They switch to counting graphemes for the UI and enforcing a byte limit in the database.

## Common mistakes

- **Not declaring UTF-8** in HTML, HTTP headers, database creation and DB connection strings.
- **Using MySQL `utf8` instead of `utf8mb4`.**
- **Using `.length` to validate user-visible length**, or `substring` to truncate text — it can cut an emoji in half and leave an invalid character.
- **Comparing usernames without normalising**, allowing two accounts that look identical.
- **Committing scripts with CRLF line endings** to a repo that deploys to Linux. Configure `.gitattributes`.
- **Thinking Base64 or URL encoding is security.** They are reversible encodings.

## Security lens

<Callout type="security">
Encodings let the same text be represented in many ways. If a security check looks at one representation and the application uses another, the check is bypassed.
</Callout>

- **Filter evasion:** WAFs and input filters have been bypassed with URL encoding, double encoding (`%252e%252e%252f` for `../`), overlong UTF-8 sequences and Unicode look-alikes. Decode and normalise **first**, then validate — and prefer allow-lists over block-lists.
- **Homograph attacks:** Cyrillic "а" (U+0430) looks like Latin "a" (U+0061). `pаypal.com` with a Cyrillic letter is a different domain. Browsers display such domains as Punycode (`xn--...`); your app should too for user-supplied links, and should prevent look-alike usernames.
- **Invisible characters:** zero-width spaces and bidirectional control characters can hide text or make code display differently from how it runs ("Trojan Source", 2021). Code review tools now warn about them.
- **Encoding is not encryption:** Base64 in a JWT payload, a hex "obfuscated" API key or a URL-encoded password are all readable by anyone.
- **Truncation and length bugs:** byte vs character length mismatches have caused buffer overflows in C code and validation bypasses in web apps.

## Interview questions

<QA q="What is the difference between Unicode and UTF-8?">
Unicode is a character set: it assigns a unique number (code point) to every character, such as U+0645 for "م". UTF-8 is an encoding: a rule for turning those code points into bytes, using 1 to 4 bytes per character. UTF-16 and UTF-32 are other encodings of the same Unicode code points.
</QA>

<QA q="Why is UTF-8 the dominant encoding on the web?">
It is backward compatible with ASCII (ASCII text is already valid UTF-8), compact for English and markup-heavy content, able to represent every Unicode character, free of byte-order issues, and self-synchronising, so decoders can recover from errors. That made it the natural default for HTML, JSON, Linux and most protocols.
</QA>

<QA q="Why does '😀'.length return 2 in JavaScript?">
JavaScript strings are sequences of UTF-16 code units. Characters outside the Basic Multilingual Plane, such as most emoji, need two code units (a surrogate pair), so `.length` reports 2. To count code points use `[...str].length`; to count user-perceived characters use `Intl.Segmenter`.
</QA>

<QA q="Users report names showing as 'Ã©' instead of 'é'. What is happening?">
That is mojibake: text encoded as UTF-8 (é is the two bytes C3 A9) is being decoded as Latin-1 or Windows-1252, where those bytes are "Ã" and "©". Some layer — the database connection, the column charset, an HTTP header, or a file import — is not using UTF-8. Trace the data path and make every layer explicitly UTF-8.
</QA>

<QA q="How can character encoding be used to bypass security controls?">
If validation happens on the raw input but the application later decodes or normalises it, an attacker can encode a forbidden payload so the check does not recognise it — for example double-URL-encoded path traversal or Unicode look-alike characters. The defence is to canonicalise (decode and normalise) input once, before validation, and to use allow-lists.
</QA>

## Key terms

<Terms>
  <Term name="ASCII">7-bit encoding of 128 English characters.</Term>
  <Term name="Unicode">The universal character set covering all writing systems.</Term>
  <Term name="Code point">The number Unicode assigns to a character, written U+XXXX.</Term>
  <Term name="UTF-8">Variable-length (1–4 byte) encoding of Unicode; the web's default.</Term>
  <Term name="UTF-16">2- or 4-byte encoding used inside JavaScript, Java and Windows.</Term>
  <Term name="Grapheme">What a user sees as one character, possibly several code points.</Term>
  <Term name="Mojibake">Garbled text caused by decoding bytes with the wrong encoding.</Term>
  <Term name="Normalisation">Converting equivalent Unicode sequences to one standard form (NFC/NFD).</Term>
  <Term name="BOM">Byte order mark; an optional marker at the start of a text file.</Term>
  <Term name="utf8mb4">MySQL's real UTF-8 charset that supports 4-byte characters.</Term>
</Terms>
