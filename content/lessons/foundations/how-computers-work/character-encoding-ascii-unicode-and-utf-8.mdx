<Callout type="tip" title="In one minute">
Computers store only numbers, so every character needs an agreed number. **ASCII** (1963) numbered 128 English characters: `A` = 65. **Unicode** gives every character in every language a number called a **code point**: `م` = U+0645, `😀` = U+1F600. **UTF-8** is the way to store those numbers as bytes: English letters take 1 byte, Urdu/Arabic letters 2, most emoji 4. If text is saved in one encoding and read in another, you get garbage like `Ù…` — **mojibake**. Rule: use **UTF-8 everywhere** — files, databases (`utf8mb4` in MySQL), HTTP headers and HTML.
</Callout>

## Start from zero

### Letters are really numbers

From the first lesson you know a computer only stores bits. A letter is not "a shape" for the computer — it is a **number**, and everyone must agree which number means which letter.

<Callout type="analogy">
A **secret code** between two friends: "1 = A, 2 = B, 3 = C…". The message `8 9` means "HI" — but only if both use the **same codebook**. If your friend uses a different codebook, the same numbers produce nonsense. Character encodings are those codebooks, and most text bugs happen when two systems use different ones.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Character** | One letter, digit, symbol or emoji | `A`, `م`, `7`, `😀` |
| **Character set** | The list of characters and their numbers | ASCII, Unicode |
| **Code point** | Unicode's number for a character, written `U+` hex | `U+0041` = A |
| **Encoding** | The rule for turning code points into bytes | UTF-8, UTF-16 |
| **Decoding** | Turning bytes back into characters | reading a file |
| **Mojibake** | Garbled text from decoding with the wrong encoding | `Ø¢Ù¾` instead of `آپ` |
| **Byte** | 8 bits | `0x41` |

## What is it?

| Standard | Year | Characters | Bytes per character |
| --- | --- | --- | --- |
| ASCII | 1963 | 128 (English letters, digits, symbols, control codes) | 1 |
| "Code pages" (Windows-1252, Windows-1256 …) | 1980s | 256, different per language | 1 |
| Unicode | 1991– | ~150,000 (all scripts, symbols, emoji) | — (it is the list) |
| UTF-8 | 1993 | All of Unicode | 1–4 |
| UTF-16 | — | All of Unicode | 2 or 4 |

**Unicode is the codebook; UTF-8 is the way of writing its numbers as bytes.**

## Why does it matter?

- **Urdu, Arabic, Chinese, emoji:** your users type them. Wrong settings turn names into `???` or `Ø§Ø±Ø¯Ùˆ`.
- **Databases:** MySQL's old `utf8` cannot store emoji; a user's message with 😀 can fail to save.
- **String length:** `"😀".length` in JavaScript is 2, not 1 — breaking validation and truncation.
- **APIs and files:** CSV exports open garbled in Excel; JSON must be UTF-8.
- **Security:** look-alike characters (Cyrillic `а` vs Latin `a`) enable phishing domains; invisible characters can hide malicious code.

## When and where do you use it?

| Place | What to set |
| --- | --- |
| HTML | `<meta charset="utf-8">` |
| HTTP responses | `Content-Type: text/html; charset=utf-8` |
| MySQL / MariaDB | `utf8mb4` character set, `utf8mb4_unicode_ci` collation |
| PostgreSQL | `UTF8` database encoding (the default) |
| Source files, editors | UTF-8, LF line endings |
| Linux locale | `LANG=en_US.UTF-8` (or `C.UTF-8`) |

## Concepts one by one

### 1. ASCII — the first common codebook

<Explain>
<What>
A table of 128 characters numbered 0–127: control codes (0–31, like newline = 10), space (32), digits (48–57), uppercase letters (65–90), lowercase (97–122) and symbols.
</What>
<Why>
It made English text exchangeable between all computers — and it is still the first part of Unicode and UTF-8.
</Why>
<When>
Every time you type English text, code or commands.
</When>
<Where>
Source code, HTTP headers, URLs, email headers, log files.
</Where>
<How>
In JavaScript, `"A".charCodeAt(0)` gives 65 and `String.fromCharCode(65)` gives "A".
</How>
</Explain>

```javascript
for (const ch of ["A", "a", "0", " "]) {
  console.log(JSON.stringify(ch), "=", ch.charCodeAt(0));
}
console.log("Newline is", "\n".charCodeAt(0), "| 72, 105 →", String.fromCharCode(72, 105));
```

```text output
"A" = 65
"a" = 97
"0" = 48
" " = 32
Newline is 10 | 72, 105 → Hi
```

Notice `"0"` (the character) is 48 — not the number 0. That is why `"5" + "5"` is `"55"` in JavaScript.

### 2. The code page mess

<Explain>
<What>
Before Unicode, each region extended ASCII to 256 characters differently: the numbers 128–255 meant Western European letters in one code page, Arabic/Urdu letters in another, Cyrillic in another.
</What>
<Why>
The same byte meant different letters on different computers, so text moved between them became garbage. This is the origin of most "encoding problems" you still meet in old files and systems.
</Why>
<When>
Old Excel/CSV files, legacy databases, old Windows software.
</When>
<Where>
Windows-1252 (Western), Windows-1256 (Arabic/Urdu), ISO-8859-1 (Latin-1).
</Where>
<How>
Byte `0xC7` is `Ç` in Windows-1252 but `ا` (alef) in Windows-1256. Without knowing which code page was used, the bytes cannot be read correctly.
</How>
</Explain>

### 3. Unicode — one number for every character

<Explain>
<What>
A single, worldwide list giving every character a unique number, its **code point**, written as `U+` followed by hex.
</What>
<Why>
One codebook for every language and symbol ended the code-page confusion.
</Why>
<When>
Whenever modern software handles text.
</When>
<Where>
Every modern OS, language and browser.
</Where>
<How>
`"م".codePointAt(0).toString(16)` gives `645`, so it is U+0645. Unicode also includes emoji, maths symbols and invisible control characters.
</How>
</Explain>

```javascript
for (const ch of ["A", "é", "م", "آ", "😀"]) {
  const cp = ch.codePointAt(0);
  console.log(ch, "→ U+" + cp.toString(16).toUpperCase().padStart(4, "0"), `(${cp})`);
}
```

```text output
A → U+0041 (65)
é → U+00E9 (233)
م → U+0645 (1605)
آ → U+0622 (1570)
😀 → U+1F600 (128512)
```

### 4. UTF-8 — storing code points as bytes

<Explain>
<What>
An encoding that stores each code point in 1 to 4 bytes. ASCII characters stay exactly one byte with the same value.
</What>
<Why>
It is compact for English and code, supports every language, and old ASCII text is already valid UTF-8. That is why ~98% of websites use it.
</Why>
<When>
By default, for everything.
</When>
<Where>
Web pages, JSON, Linux, Git, source code, modern databases.
</Where>
<How>
Bigger code points need more bytes: U+0000–007F → 1 byte, up to U+07FF → 2 bytes (Arabic/Urdu), up to U+FFFF → 3 bytes (most other scripts, many symbols), above → 4 bytes (emoji).
</How>
</Explain>

```javascript
const enc = new TextEncoder();
for (const ch of ["A", "é", "م", "€", "😀"]) {
  const bytes = [...enc.encode(ch)].map((b) => b.toString(16).padStart(2, "0"));
  console.log(ch, "→", bytes.length, "byte(s):", bytes.join(" "));
}
```

```text output
A → 1 byte(s): 41
é → 2 byte(s): c3 a9
م → 2 byte(s): d9 85
€ → 3 byte(s): e2 82 ac
😀 → 4 byte(s): f0 9f 98 80
```

The same in the terminal:

```bash
for w in "A" "آپ" "😀"; do
  printf '%-4s %s byte(s): %s\n' "$w" "$(printf '%s' "$w" | wc -c)" "$(printf '%s' "$w" | od -An -tx1 | tr -s ' ')"
done
```

```text output
A    1 byte(s):  41
آپ 4 byte(s):  d8 a2 d9 be
😀 4 byte(s):  f0 9f 98 80
```

`wc -c` counts **bytes**. Notice also that the columns do not line up: Bash's `%-4s` padding counts bytes too, so the 4-byte `آپ` and `😀` get no extra spaces — a first taste of the "which length?" problem in the next section.

### 5. Three different "lengths" of a string

<Explain>
<What>
A piece of text has several lengths: the number of **bytes** (storage), the number of **code units** (what JavaScript's `.length` counts — UTF-16 units), and the number of **user-perceived characters** (what a human counts).
</What>
<Why>
Validation ("max 20 characters"), database column sizes and truncation all break when the wrong length is used. Cutting a string in the middle of an emoji produces a broken character `�`.
</Why>
<When>
Limiting names, tweets, SMS messages; sizing database columns; slicing text.
</When>
<Where>
JavaScript, databases (VARCHAR limits), APIs.
</Where>
<How>
Bytes: `new TextEncoder().encode(s).length`. Code points: `[...s].length`. Human characters: `Intl.Segmenter`.
</How>
</Explain>

```javascript
const words = ["hello", "آپ", "😀", "👍🏽", "👨‍👩‍👧"];
const seg = new Intl.Segmenter("en", { granularity: "grapheme" });
for (const s of words) {
  console.log(
    s.padEnd(6),
    "bytes:", new TextEncoder().encode(s).length,
    "| .length:", s.length,
    "| code points:", [...s].length,
    "| characters:", [...seg.segment(s)].length
  );
}
```

```text output
hello  bytes: 5 | .length: 5 | code points: 5 | characters: 5
آپ     bytes: 4 | .length: 2 | code points: 2 | characters: 2
😀     bytes: 4 | .length: 2 | code points: 1 | characters: 1
👍🏽   bytes: 8 | .length: 4 | code points: 2 | characters: 1
👨‍👩‍👧 bytes: 18 | .length: 8 | code points: 5 | characters: 1
```

- `آپ` is 2 characters, 2 code points — but **4 bytes**. A database column limited to 4 bytes would fit only two Urdu letters, but four English ones.
- `😀` is 1 character but `.length` says **2**: JavaScript counts UTF-16 units, and emoji need two.
- `👍🏽` (thumbs up + skin tone) is 2 code points shown as 1 character.

So **decide which length your rule means** — bytes for storage limits, characters (graphemes) for what users see — and test with real Urdu text and emoji. (The columns are not aligned for the same reason: `padEnd` counts UTF-16 units, not visible characters.)

- The family emoji is 5 code points (three people joined by invisible "zero-width joiners"), 8 UTF-16 units, 18 bytes — but one character on screen.

### 6. Mojibake — how text gets garbled

<Explain>
<What>
Garbage text produced when bytes written in one encoding are read as another.
</What>
<Why>
It is the most common encoding bug: UTF-8 bytes interpreted as Windows-1252 or Latin-1.
</Why>
<When>
Importing CSVs, old databases, wrong `Content-Type` headers, terminals with the wrong locale.
</When>
<Where>
`Ø¢Ù¾` instead of `آپ`, `Ã©` instead of `é`, `â‚¬` instead of `€`.
</Where>
<How>
The fix is never "find and replace the garbage" — it is making the writer and reader use the **same** encoding (UTF-8). If text was double-encoded, decode it back once.
</How>
</Explain>

```javascript
const original = "آپ کیسے ہیں؟ café €";
const utf8Bytes = new TextEncoder().encode(original);
const wrong = new TextDecoder("windows-1252").decode(utf8Bytes);   // read with the wrong codebook
const right = new TextDecoder("utf-8").decode(utf8Bytes);
console.log("wrong:", wrong);
console.log("right:", right);
```

```text output
wrong: Ø¢Ù¾ Ú©ÛŒØ³Û’ ÛÛŒÚºØŸ cafÃ© â‚¬
right: آپ کیسے ہیں؟ café €
```

The bytes are identical — only the codebook used to **read** them differs. Once you see `Ø` and `Ù` everywhere, think "UTF-8 Urdu/Arabic read as Windows-1252".

### 7. Encodings in databases

<Explain>
<What>
Databases store text in a configured character set. MySQL's old `utf8` stores at most 3 bytes per character and **cannot store emoji**; `utf8mb4` stores all of Unicode.
</What>
<Why>
With the wrong setting, inserts fail ("Incorrect string value: '\xF0\x9F\x98\x80'") or text is silently replaced by `?`.
</Why>
<When>
Creating databases and tables, connecting from apps.
</When>
<Where>
MySQL/MariaDB (`utf8mb4`), PostgreSQL (`UTF8`), connection strings (`charset=utf8mb4`).
</Where>
<How>
Set the encoding on the database, the tables **and** the connection — all three must match.
</How>
</Explain>

```text
-- MySQL / MariaDB
CREATE DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
-- Connection string (Node.js mysql2):  charset: "utf8mb4"

-- PostgreSQL
CREATE DATABASE shop ENCODING 'UTF8';
```

### 8. Normalisation — same look, different bytes

<Explain>
<What>
Some characters can be written in more than one way: `é` as one code point (U+00E9) or as `e` + a combining accent (U+0065 U+0301). They look identical but compare as different.
</What>
<Why>
Logins, searches and duplicate checks fail ("user already exists" — or worse, two accounts that look identical).
</Why>
<When>
Comparing or storing user-supplied text, usernames, search.
</When>
<Where>
Input from different keyboards, macOS file names, copy-pasted text.
</Where>
<How>
Normalise before comparing or storing: `s.normalize("NFC")`.
</How>
</Explain>

```javascript
const a = "café";            // é as one code point
const b = "café";           // e + combining accent
console.log(a, b, "equal?", a === b, "| lengths:", a.length, b.length);
console.log("after NFC normalisation equal?", a.normalize("NFC") === b.normalize("NFC"));
```

```text output
café café equal? false | lengths: 4 5
after NFC normalisation equal? true
```

### 9. Line endings and the BOM

<Explain>
<What>
**Line endings**: Linux/macOS end lines with LF (`\n`); Windows uses CRLF (`\r\n`). The **BOM** is an optional invisible marker (`EF BB BF`) some Windows tools put at the start of UTF-8 files.
</What>
<Why>
CRLF breaks Bash scripts (`$'\r': command not found`), and a BOM can break shebangs, JSON parsers and CSV headers.
</Why>
<When>
Files edited on Windows and used on Linux servers or in Docker.
</When>
<Where>
Shell scripts, `.env` files, CSV exports, config files.
</Where>
<How>
Set your editor to UTF-8 without BOM and LF. Check with `file name` or `cat -A`; fix with `dos2unix` or `sed -i 's/\r$//'`. In Git, `.gitattributes` with `* text=auto eol=lf` keeps line endings consistent.
</How>
</Explain>

```bash
printf 'echo hello\r\n' > win.sh
printf '\xef\xbb\xbfname,city\n' > excel.csv
file win.sh excel.csv | sed 's/,  *with/ with/'
cat -A win.sh
sed -i 's/\r$//' win.sh && bash win.sh
```

```text output
win.sh:    ASCII text with CRLF line terminators
excel.csv: Unicode text, UTF-8 (with BOM) text
echo hello^M$
hello
```

`^M` is the hidden carriage return (`\r`); `$` marks the end of the line.

## Hands-on

```bash
# 1. Byte counts for different scripts
for w in hello سلام 你好 😀; do printf '%s → %s bytes\n' "$w" "$(printf '%s' "$w" | wc -c)"; done

# 2. Code point of a character (Python)
python3 -c 'for ch in "Aمé😀": print(ch, hex(ord(ch)))'

# 3. Create mojibake and repair it
printf 'آپ' | iconv -f windows-1252 -t utf-8 > broken.txt 2>/dev/null || true
cat broken.txt; echo
iconv -f utf-8 -t windows-1252 broken.txt | cat; echo

# 4. Your terminal locale
locale 2>/dev/null | grep -q 'UTF-8' && echo "locale uses UTF-8" || echo "check your locale (LANG)"
```

```text output
hello → 5 bytes
سلام → 8 bytes
你好 → 6 bytes
😀 → 4 bytes
A 0x41
م 0x645
é 0xe9
😀 0x1f600
Ø¢Ù¾
آپ
locale uses UTF-8
```

`iconv` converts between encodings. Step 3 first creates the classic mojibake (UTF-8 bytes read as Windows-1252), then reverses that mistake.

## Real-world example

A Pakistani e-commerce site stores customer names in MySQL. Orders with Urdu names show as `????`, and orders with emoji in delivery notes fail entirely.

1. The table was created with `latin1`, so Urdu characters cannot be stored at all: they are replaced with `?`. Converting the table to `utf8mb4` fixes new data; old rows have permanently lost their text.
2. Emoji fail because MySQL's legacy `utf8` (an alias for `utf8mb3`) allows at most 3 bytes; emoji need 4. `utf8mb4` fixes this too.
3. The connection itself also needs `charset=utf8mb4`; otherwise the driver converts text on the way in.
4. The CSV export for the accounts team opens garbled in Excel; adding a UTF-8 BOM fixes it.
5. "Max 30 characters" on names is enforced with `.length`, rejecting a valid name with emoji early. They switch to counting graphemes for the UI and enforcing a byte limit in the database.

## Common mistakes

- **Not declaring UTF-8** in HTML, HTTP headers, database creation and DB connection strings.
- **Using MySQL `utf8` instead of `utf8mb4`.**
- **Using `.length` to validate user-visible length**, or `substring` to truncate text — it can cut an emoji in half and leave an invalid character.
- **Comparing usernames without normalising**, allowing two accounts that look identical.
- **Committing scripts with CRLF line endings** to a repo that deploys to Linux. Configure `.gitattributes`.
- **Thinking Base64 or URL encoding is security.** They are reversible encodings.

## Security lens

<Callout type="security">
Encodings let the same text be represented in many ways. If a security check looks at one representation and the application uses another, the check is bypassed.
</Callout>

- **Filter evasion:** WAFs and input filters have been bypassed with URL encoding, double encoding (`%252e%252e%252f` for `../`), overlong UTF-8 sequences and Unicode look-alikes. Decode and normalise **first**, then validate — and prefer allow-lists over block-lists.
- **Homograph attacks:** Cyrillic "а" (U+0430) looks like Latin "a" (U+0061). `pаypal.com` with a Cyrillic letter is a different domain. Browsers display such domains as Punycode (`xn--...`); your app should too for user-supplied links, and should prevent look-alike usernames.
- **Invisible characters:** zero-width spaces and bidirectional control characters can hide text or make code display differently from how it runs ("Trojan Source", 2021). Code review tools now warn about them.
- **Encoding is not encryption:** Base64 in a JWT payload, a hex "obfuscated" API key or a URL-encoded password are all readable by anyone.
- **Truncation and length bugs:** byte vs character length mismatches have caused buffer overflows in C code and validation bypasses in web apps.

## Interview questions

<QA q="What is the difference between Unicode and UTF-8?">
Unicode is a character set: it assigns a unique number (code point) to every character, such as U+0645 for "م". UTF-8 is an encoding: a rule for turning those code points into bytes, using 1 to 4 bytes per character. UTF-16 and UTF-32 are other encodings of the same Unicode code points.
</QA>

<QA q="Why is UTF-8 the dominant encoding on the web?">
It is backward compatible with ASCII (ASCII text is already valid UTF-8), compact for English and markup-heavy content, able to represent every Unicode character, free of byte-order issues, and self-synchronising, so decoders can recover from errors. That made it the natural default for HTML, JSON, Linux and most protocols.
</QA>

<QA q="Why does '😀'.length return 2 in JavaScript?">
JavaScript strings are sequences of UTF-16 code units. Characters outside the Basic Multilingual Plane, such as most emoji, need two code units (a surrogate pair), so `.length` reports 2. To count code points use `[...str].length`; to count user-perceived characters use `Intl.Segmenter`.
</QA>

<QA q="Users report names showing as 'Ã©' instead of 'é'. What is happening?">
That is mojibake: text encoded as UTF-8 (é is the two bytes C3 A9) is being decoded as Latin-1 or Windows-1252, where those bytes are "Ã" and "©". Some layer — the database connection, the column charset, an HTTP header, or a file import — is not using UTF-8. Trace the data path and make every layer explicitly UTF-8.
</QA>

<QA q="How can character encoding be used to bypass security controls?">
If validation happens on the raw input but the application later decodes or normalises it, an attacker can encode a forbidden payload so the check does not recognise it — for example double-URL-encoded path traversal or Unicode look-alike characters. The defence is to canonicalise (decode and normalise) input once, before validation, and to use allow-lists.
</QA>

## Key terms

<Terms>
  <Term name="ASCII">7-bit encoding of 128 English characters.</Term>
  <Term name="Unicode">The universal character set covering all writing systems.</Term>
  <Term name="Code point">The number Unicode assigns to a character, written U+XXXX.</Term>
  <Term name="UTF-8">Variable-length (1–4 byte) encoding of Unicode; the web's default.</Term>
  <Term name="UTF-16">2- or 4-byte encoding used inside JavaScript, Java and Windows.</Term>
  <Term name="Grapheme">What a user sees as one character, possibly several code points.</Term>
  <Term name="Mojibake">Garbled text caused by decoding bytes with the wrong encoding.</Term>
  <Term name="Normalisation">Converting equivalent Unicode sequences to one standard form (NFC/NFD).</Term>
  <Term name="BOM">Byte order mark; an optional marker at the start of a text file.</Term>
  <Term name="utf8mb4">MySQL's real UTF-8 charset that supports 4-byte characters.</Term>
</Terms>
