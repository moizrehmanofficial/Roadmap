<BigIdea>
<Tr>
<En>
Almost everything online is one program **asking** and another program **answering**. The asker is the **client** (your browser, an app). The answerer is the **server**. The question is a **request**; the answer is a **response**.
</En>
<Ur>
Online taqreeban har cheez ek program ka **poochna** aur doosre program ka **jawab dena** hai. Poochne wala **client** hai (aap ka browser, koi app). Jawab dene wala **server** hai. Sawal **request** hai; jawab **response**.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Client**: the program that asks. Your browser, a phone app, the `curl` command.
- **Server**: a program that waits for questions and answers them. A website, an API, a database.
- **Request**: the question, like "give me the product with ID 7".
- **Response**: the answer, with a **status** (`200 OK` = success, `404` = not found) and the data.

</En>
<Ur>

- **Client**: wo program jo poochta hai. Aap ka browser, phone app, `curl` command.
- **Server**: wo program jo sawalon ka intezar karta hai aur jawab deta hai. Website, API, database.
- **Request**: sawal, jaise "mujhe ID 7 wala product do".
- **Response**: jawab, ek **status** ke saath (`200 OK` = kamyabi, `404` = nahi mila) aur data.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- Almost every app you build has this shape: a website (client) + an API (server) + a database (another server).
- When something breaks, the first question is always: **is it the client, the network, or the server?**
- Every server is a door into your system, so security starts here.

</En>
<Ur>

- Taqreeban har app jo aap banayenge us ki yahi shakal hai: website (client) + API (server) + database (ek aur server).
- Jab kuch toote, to pehla sawal hamesha ye hota hai: **masla client me hai, network me, ya server me?**
- Har server aap ke system ka ek darwaza hai, isliye security yahin se shuru hoti hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- opening any website
- an app loading data with `fetch()`
- your API reading from a database
- logging in to a server with `ssh`
- pushing code to GitHub with `git push`

</En>
<Ur>

- koi bhi website kholte waqt
- app jab `fetch()` se data load kare
- aap ki API jab database se parhe
- `ssh` se server me login karte waqt
- `git push` se GitHub par code bhejte waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. The client finds the server's address (**IP address**) and the right door (**port**).
2. It sends a request.
3. The server program listening on that port does the work.
4. It sends back a response.

</En>
<Ur>

1. Client server ka pata (**IP address**) aur sahi darwaza (**port**) dhoondta hai.
2. Request bhejta hai.
3. Us port par sunne wala server program kaam karta hai.
4. Response wapas bhejta hai.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **restaurant**:

- You (the **client**) tell the waiter: "One burger, please." That's a **request**.
- The kitchen (the **server**) makes it, and the waiter brings the burger, or says "Sorry, we're out." That's the **response**, with a result (**status**).
- The restaurant's street address is the **IP address**. The counter you go to (takeaway, dine-in, delivery) is the **port**.
- The kitchen doesn't remember you between visits unless you show your **loyalty card**. On the web that card is a **cookie** or **token**.

</En>
<Ur>

Ek **restaurant** ka socho:

- Aap (**client**) waiter se kehte hain: "Ek burger, please." Ye **request** hai.
- Kitchen (**server**) banati hai, aur waiter burger le aata hai, ya kehta hai "Maaf kijiye, khatam ho gaya." Ye **response** hai, ek nateeje (**status**) ke saath.
- Restaurant ka gali ka pata **IP address** hai. Jis counter par aap jate hain (takeaway, dine-in, delivery) wo **port** hai.
- Kitchen aap ko agli dafa yaad nahi rakhti jab tak aap apna **loyalty card** na dikhayen. Web par wo card **cookie** ya **token** hai.

</Ur>
</Tr>

<FlowStep>Travels over the **network**</FlowStep>
<FlowStep>**Server** does the work</FlowStep>
<FlowStep>**Response** comes back: 200 OK + data</FlowStep>
</Flow>

## Learn it step by step

<Walkthrough>

<Step title="A request and its response">

<Tr>
<En>

Here's what a real request and response look like. The request says **what** you want (`GET` = "give me") and **where** (`/api/products/7`). The response starts with a **status** and then the data.

</En>
<Ur>

Asli request aur response aise dikhte hain. Request batati hai aap **kya** chahte hain (`GET` = "mujhe do") aur **kahan se** (`/api/products/7`). Response ek **status** se shuru hota hai aur phir data.

</Ur>
</Tr>

```text
REQUEST (client → server)                RESPONSE (server → client)
──────────────────────────────           ─────────────────────────────────
GET /api/products/7 HTTP/1.1             HTTP/1.1 200 OK
Host: shop.example.com                   Content-Type: application/json
Accept: application/json                 Content-Length: 35
Authorization: Bearer eyJhbGci…
                                         {"id":7,"name":"Kettle","price":35}
```

<Tr>
<En>

Status codes are grouped by their first digit. **4xx means the request was wrong; 5xx means the server failed.** This one rule tells you where to look when something breaks.

| Status | Meaning | Whose problem? |
| --- | --- | --- |
| 2xx (200, 201) | Success | Nobody's |
| 3xx (301, 304) | Go somewhere else / nothing changed | Nobody's |
| 4xx (400, 401, 403, 404) | The **request** was wrong | Client |
| 5xx (500, 502, 503) | The **server** failed | Server |

</En>
<Ur>

Status codes pehle digit se group hote hain. **4xx ka matlab request ghalat thi; 5xx ka matlab server fail hua.** Ye ek qaida batata hai ke kuch toote to kahan dekhna hai.

| Status | Matlab | Kis ka masla? |
| --- | --- | --- |
| 2xx (200, 201) | Kamyabi | Kisi ka nahi |
| 3xx (301, 304) | Kahin aur jao / kuch nahi badla | Kisi ka nahi |
| 4xx (400, 401, 403, 404) | **Request** ghalat thi | Client |
| 5xx (500, 502, 503) | **Server** fail hua | Server |

</Ur>
</Tr>

</Step>

<Step title="Run your own server and call it">

<Tr>
<En>

Let's make both sides on one computer. A tiny Node.js **server** waits on port 3456. Then `curl` acts as the **client** and sends requests.

</En>
<Ur>

Chalo ek hi computer par dono taraf banate hain. Ek chhota Node.js **server** port 3456 par intezar karta hai. Phir `curl` **client** ban kar requests bhejta hai.

</Ur>
</Tr>

```bash
cat > server.mjs <<'EOF'
import http from "node:http";
const server = http.createServer((req, res) => {
  const url = new URL(req.url, "http://localhost");
  if (url.pathname === "/hello") {
    const name = (url.searchParams.get("name") ?? "world").slice(0, 50);
    res.writeHead(200, { "Content-Type": "application/json" });
    return res.end(JSON.stringify({ message: `Hello, ${name}` }));
  }
  res.writeHead(404, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ error: "Not found" }));
});
server.listen(3456, "127.0.0.1");
EOF
node server.mjs &
server_pid=$!
sleep 0.5

curl -s "http://127.0.0.1:3456/hello?name=Alex"; echo
curl -s -o /dev/null -w "status for /nope: %{http_code}\n" http://127.0.0.1:3456/nope
curl -s -i http://127.0.0.1:3456/hello | head -2 | tr -d '\r'

kill "$server_pid"
```

```text output
{"message":"Hello, Alex"}
status for /nope: 404
HTTP/1.1 200 OK
Content-Type: application/json
```

<Happened>
<Tr>
<En>

- `server.listen(3456, "127.0.0.1")`: the server starts **listening** on port 3456 of this computer.
- `node server.mjs &` runs it in the background, so it keeps waiting.
- `curl …/hello?name=Alex`: the client asks; the server answers `{"message":"Hello, Alex"}`.
- `/nope` doesn't exist, so the server answers status **404**.
- `-i` shows the top of the response: `200 OK` and the content type.
- `kill` stops the server.

</En>
<Ur>

- `server.listen(3456, "127.0.0.1")`: server is computer ke port 3456 par **sunna** shuru karta hai.
- `node server.mjs &` use background me chalata hai, taa ke wo intezar karta rahe.
- `curl …/hello?name=Alex`: client poochta hai; server jawab deta hai `{"message":"Hello, Alex"}`.
- `/nope` mojood nahi, isliye server status **404** deta hai.
- `-i` response ka upar wala hissa dikhata hai: `200 OK` aur content ki type.
- `kill` server band kar deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="IP addresses and ports: building and flat number">

<Tr>
<En>

An **IP address** finds the **computer**. A **port** (a number from 0 to 65535) finds the **program** on that computer. Like a letter that needs the **building address** and the **flat number**.

Two addresses you'll see all the time:

- `127.0.0.1` (localhost): only **this computer** can connect.
- `0.0.0.0` (when a server listens): **any** computer on the network can connect, if the firewall allows.

</En>
<Ur>

**IP address** **computer** dhoondta hai. **Port** (0 se 65535 tak ka number) us computer par **program** dhoondta hai. Jaise khat ko **building ka pata** aur **flat number** dono chahiyen.

Do addresses jo aap har waqt dekhenge:

- `127.0.0.1` (localhost): sirf **yahi computer** connect kar sakta hai.
- `0.0.0.0` (jab server sun raha ho): network ka **koi bhi** computer connect kar sakta hai, agar firewall ijazat de.

</Ur>
</Tr>

<En>

| --- | --- |
| 22 | SSH (remote login) |
| 53 | DNS |
| 80 | HTTP (websites) |
| 443 | HTTPS (secure websites) |
| 3000 / 8080 | Apps during development |
| 3306 | MySQL |
| 5432 | PostgreSQL |
| 6379 | Redis |
| 27017 | MongoDB |

</En>
<Ur>

| Port | Service |
| --- | --- |
| 22 | SSH (door se login) |
| 53 | DNS |
| 80 | HTTP (websites) |
| 443 | HTTPS (mehfooz websites) |

<Step title="What happens when you open a website">

<Tr>
<En>

You type `https://shop.example.com` and press Enter. Behind the scenes:

1. **DNS**: the browser asks "what's the IP address of `shop.example.com`?"
2. **Connect**: it opens a connection to that IP on port 443.
3. **Encrypt (TLS)**: both sides agree on encryption, and the server proves who it is with a certificate.
4. **Request**: the browser sends `GET /`.
5. **Server work**: the web server passes the request to the app, which may ask the database.
6. **Response**: `200 OK` + the HTML page.
7. **More requests**: the browser asks for CSS, JavaScript, images and fonts (often dozens).
8. **Show**: the page appears.

Each step can fail, and knowing the order tells you where to look. Later lessons (DNS, TCP/IP, HTTP, TLS) go deep into each one.

</En>
<Ur>

Aap `https://shop.example.com` likh kar Enter dabate hain. Parde ke peeche:

1. **DNS**: browser poochta hai "`shop.example.com` ka IP address kya hai?"
2. **Connect**: us IP ke port 443 par connection kholta hai.
3. **Encrypt (TLS)**: dono taraf encryption par mutafiq hoti hain, aur server certificate se sabit karta hai ke wo kaun hai.
4. **Request**: browser `GET /` bhejta hai.
5. **Server ka kaam**: web server request app ko deta hai, jo database se pooch sakti hai.
6. **Response**: `200 OK` + HTML page.
7. **Mazeed requests**: browser CSS, JavaScript, images aur fonts maangta hai (aksar darjanon).
8. **Dikhana**: page nazar aata hai.

Har qadam fail ho sakta hai, aur tarteeb jaanne se pata chalta hai ke kahan dekhna hai. Agle lessons (DNS, TCP/IP, HTTP, TLS) har ek ko gehrai se samjhate hain.

</Ur>
</Tr>

```bash
getent hosts localhost | awk '{print "DNS-style lookup: localhost →", $1}'
```

```text output
DNS-style lookup: localhost → 127.0.0.1
```

<Happened>
<Tr>
<En>

- `getent hosts` does a name lookup like DNS: the name `localhost` becomes the address `127.0.0.1`.
- Some systems show `::1` instead: the newer (IPv6) way to write "this computer".

</En>
<Ur>

- `getent hosts` DNS ki tarah naam dhoondta hai: naam `localhost` address `127.0.0.1` ban jata hai.
- Kuch systems `::1` dikhate hain: "yahi computer" likhne ka naya (IPv6) tareeqa.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Two errors every developer meets">

<Tr>
<En>

Only **one** program can listen on a port at a time. And if **nothing** is listening, the client can't connect. These give two very common errors:

- `EADDRINUSE` ("address already in use"): you tried to start a server on a port that's already taken.
- **Connection refused**: you tried to connect to a port where nothing is listening (maybe the server isn't running).

</En>
<Ur>

Ek port par ek waqt me **sirf ek** program sun sakta hai. Aur agar wahan **koi** na sun raha ho, to client connect nahi kar sakta. Is se do bohot aam errors aate hain:

- `EADDRINUSE` ("address pehle se istemal me hai"): aap ne aise port par server chalana chaha jo pehle se le liya gaya hai.
- **Connection refused**: aap ne aise port se connect karna chaha jahan koi nahi sun raha (shayad server chal hi nahi raha).

</Ur>
</Tr>

```bash
node -e 'require("http").createServer(()=>{}).listen(3457,"127.0.0.1")' &
first=$!
sleep 0.5
node -e 'require("http").createServer(()=>{}).listen(3457,"127.0.0.1").on("error",e=>{console.log("second server:",e.code);process.exit(1)})'
curl -s -o /dev/null -w "nothing on port 3999 → curl exit code %{exitcode}\n" http://127.0.0.1:3999/ || true
kill "$first"
```

```text output
second server: EADDRINUSE
nothing on port 3999 → curl exit code 7
```

<Happened>
<Tr>
<En>

- The first server takes port 3457. The second one tries the same port and gets `EADDRINUSE`.
- `curl` to port 3999, where nothing is running, fails with exit code `7`: "failed to connect" (connection refused).
- Fix for the first: stop the old server or use another port. Fix for the second: start the server, or check the port number.

</En>
<Ur>

- Pehla server port 3457 le leta hai. Doosra wahi port try karta hai aur `EADDRINUSE` milta hai.
- Port 3999 par, jahan kuch nahi chal raha, `curl` exit code `7` ke saath fail hota hai: "connect nahi ho saka" (connection refused).
- Pehle ka hal: purana server band karein ya doosra port istemal karein. Doosre ka hal: server chalayen, ya port number check karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Servers forget you: stateless and sessions">

<Tr>
<En>

Web servers treat every request as **new**; they don't automatically remember the last one. This is called **stateless**. So how do you stay logged in? Your browser sends a "loyalty card" with **every** request: a **cookie** or a **token**.

Why design it this way? Because then you can run **many copies** of the server, and any copy can answer any request. A **load balancer** spreads requests across them.

The rule: don't keep user data in one server's memory. Keep it in a **shared** place (a database or Redis) or inside the token.

</En>
<Ur>

Web servers har request ko **naya** samajhte hain; pichli request khud ba khud yaad nahi rakhte. Ise **stateless** kehte hain. To aap logged in kaise rehte hain? Aap ka browser **har** request ke saath ek "loyalty card" bhejta hai: **cookie** ya **token**.

Aisa design kyun? Kyun ke phir aap server ki **kai copies** chala sakte hain, aur koi bhi copy kisi bhi request ka jawab de sakti hai. **Load balancer** requests un me baant-ta hai.

Qaida: user ka data ek server ki memory me na rakhein. Use **share shuda** jagah (database ya Redis) me rakhein ya token ke andar.

</Ur>
</Tr>

```text
Bad (state in server memory):              Good (state shared or in a token):

 user ─► LB ─► server A  (remembers user)    user ─► LB ─► server A ─┐
          │                                           │               ├─► Redis / DB (sessions)
          └──► server B  ("who are you?")             └──► server B ──┘
```

</Step>

<Step title="Real systems are chains of clients and servers">

<Tr>
<En>

A real app is split into layers (**tiers**): the browser, the API servers, and the database. Each arrow is a client talking to a server. Your API is a **server** to the browser and a **client** of the database at the same time.

The database sits in a **private** network: the internet can't reach it at all.

</En>
<Ur>

Asli app tehon (**tiers**) me banti hai: browser, API servers, aur database. Har teer (arrow) ek client hai jo server se baat kar raha hai. Aap ki API ek hi waqt me browser ke liye **server** aur database ke liye **client** hai.

Database ek **private** network me hota hai: internet us tak pohanch hi nahi sakta.

</Ur>
</Tr>

```text
 Internet
    │ HTTPS 443
    ▼
┌──────────────┐   public subnet
│ Load balancer│
└──────┬───────┘
       │ HTTP 3000
┌──────▼───────┐   private subnet
│  API servers │──► Redis 6379 (sessions, cache)
│  (NestJS ×3) │
└──────┬───────┘
       │ 5432
┌──────▼───────┐   private subnet, no internet access
│  PostgreSQL  │
└──────────────┘
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Trusting the client">

<Tr>
<En>Hiding the admin button, checking input only in the browser, or sending the price from the front-end. Anyone can call your API directly with `curl` and skip all of that.</En>
<Ur>Admin button chhupana, input sirf browser me check karna, ya price front-end se bhejna. Koi bhi `curl` se seedha aap ki API call kar ke ye sab chhor sakta hai.</Ur>
</Tr>

</Bad>
<Good title="Check everything on the server">

<Tr>
<En>The server validates every input and checks every permission ("does **this** user own **this** order?"). Browser checks are only for a nicer experience.</En>
<Ur>Server har input check karta hai aur har ijazat dekhta hai ("kya **ye** user **is** order ka maalik hai?"). Browser wale checks sirf behtar tajurbe ke liye hain.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Database open to the internet">

<Tr>
<En>A database or admin panel listening on `0.0.0.0` with the port open to the world.</En>
<Ur>Database ya admin panel `0.0.0.0` par sun raha ho aur port poori duniya ke liye khula ho.</Ur>
</Tr>

</Bad>
<Good title="Private by default">

<Tr>
<En>Listen on `127.0.0.1` or a private network, and use a firewall so only the app can connect.</En>
<Ur>`127.0.0.1` ya private network par sunein, aur firewall lagayen taa ke sirf app connect kar sake.</Ur>
</Tr>

</Good>
</Compare>

<Compare>
<Bad title="Login stored in one server's memory">

<Tr>
<En>Users get logged out whenever a request reaches a different server copy, or the server restarts.</En>
<Ur>Jab bhi request kisi doosri server copy par jaye, ya server restart ho, users logout ho jate hain.</Ur>
</Tr>

</Bad>
<Good title="Shared sessions">

<Tr>
<En>Sessions in Redis or the database, or a signed token: every copy of the server can answer.</En>
<Ur>Sessions Redis ya database me, ya signed token: server ki har copy jawab de sakti hai.</Ur>
</Tr>

</Good>
</Compare>

<Challenge title="Be several clients at once">

<Tr>
<En>
If you have a terminal with Node.js, run this lab. A tiny server counts its requests, and you call it a few times. Notice the counter lives in the **server's memory**: restart the server and it starts again from 0.
</En>
<Ur>
Agar aap ke paas Node.js wala terminal hai, to ye lab chalayen. Ek chhota server apni requests ginta hai, aur aap use kuch dafa call karte hain. Dekhein ke counter **server ki memory** me hai: server restart karein to wo phir 0 se shuru hota hai.
</Ur>
</Tr>

```bash
mkdir -p ~/cs-lab && cd ~/cs-lab

# 1. Start a tiny server and act as several clients
cat > api.mjs <<'EOF'
import http from "node:http";
let hits = 0;
http.createServer((req, res) => {
  hits++;
  const status = req.url === "/admin" ? 403 : req.url === "/" ? 200 : 404;
  res.writeHead(status, { "Content-Type": "text/plain" });
  res.end(`request #${hits}: ${req.method} ${req.url} → ${status}\n`);
}).listen(3458, "127.0.0.1");
EOF
node api.mjs & pid=$!; sleep 0.5

curl -s http://127.0.0.1:3458/
curl -s http://127.0.0.1:3458/admin
curl -s -X POST http://127.0.0.1:3458/orders
for code in $(for p in / /admin /x; do curl -s -o /dev/null -w '%{http_code} ' "http://127.0.0.1:3458$p"; done); do printf '%s ' "$code"; done; echo

kill $pid
cd ~ && rm -rf ~/cs-lab
```

```text output
request #1: GET / → 200
request #2: GET /admin → 403
request #3: POST /orders → 404
200 403 404 
```

<DeepDive title="Other models, and thin vs thick clients">

| Model | How it works | Examples |
| --- | --- | --- |
| Client–server | Central servers, many clients | Websites, APIs, email, databases |
| Peer-to-peer (P2P) | Every computer is both client and server | BitTorrent, some video calls, blockchains |
| Pub/sub, message queues | Senders publish messages; receivers subscribe | Kafka, RabbitMQ, WebSocket notifications |

A **thin client** shows what the server prepares (server-rendered HTML). A **thick client** does a lot itself and calls the server only for data (React single-page apps, mobile apps). Either way, security checks must happen on the server.

Each network connection is a **socket**: client-IP:client-port ↔ server-IP:server-port. The client side uses a random high port (an **ephemeral port**). `ss -ltnp` lists listening sockets on Linux.

</DeepDive>

<DeepDive title="Real world: an e-commerce app on AWS">

| Client | Server | Port | Who may connect |
| --- | --- | --- | --- |
| Customer's browser | CloudFront (CDN) | 443 | Everyone |
| CloudFront | Application Load Balancer | 443 | Only CloudFront |
| Load balancer | Next.js containers (ECS) | 3000 | Only the load balancer's security group |
| Next.js | RDS PostgreSQL | 5432 | Only the app's security group |
| Next.js | Stripe API | 443 | Outbound only |
| You (admin) | Servers | 22 or Session Manager | Only your IP / IAM users |

Every row is a client–server relationship, and every row is a security decision. Drawing this table for any system is the first step of both architecture and threat modelling.

</DeepDive>

<DeepDive title="Security lens">

The server is the only place you control. Treat every request as if it came from an attacker's custom client, because sometimes it does.

- **Never trust client input:** validate type, length and format on the server; authorise every request. Broken access control is the #1 category in the OWASP Top 10 (2021).
- **Minimise exposed ports:** every port reachable from the internet is attack surface. Scan your own servers (`nmap`) and compare with what you expect.
- **Authentication on every service:** many breaches started with an internet-exposed database, Redis, Elasticsearch or Docker API with no password.
- **Encrypt in transit:** HTTPS/TLS between client and server, and between internal services on shared networks.
- **Rate limiting and timeouts:** protect servers from brute force; protect clients from hanging on slow servers.
- **SSRF:** when your server fetches a URL the user supplies, attackers can make it call internal services or the cloud metadata endpoint (`169.254.169.254`). Covered in Web App Security and Cloud Security.
- **CORS is not security:** it's a browser rule about which sites' JavaScript may read responses. It doesn't stop `curl` or other servers.
- **Logging:** log client IP, method, path, status and user on the server: the raw material of incident response.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Explain the client–server model.">
It is an architecture where clients initiate requests and servers wait for them, process them and return responses. Servers listen on a network address and port and typically serve many clients; clients can be browsers, mobile apps or other servers. One component can be a server to some parts of the system and a client to others, like a web app that serves browsers and calls a database.
</QA>

<QA q="What happens when you type a URL into a browser and press Enter?">
The browser parses the URL, resolves the hostname to an IP address via DNS, opens a TCP connection to the server's port (443 for HTTPS), performs a TLS handshake and verifies the certificate, then sends an HTTP request. The request may pass through a CDN, load balancer and reverse proxy to the application, which may query databases and other services. The server returns an HTTP response; the browser parses and renders it and makes further requests for CSS, JavaScript, images and API data.
</QA>

<QA q="Why should application servers be stateless?">
If servers keep no client-specific state in memory, any instance can handle any request. That allows horizontal scaling behind a load balancer, rolling deployments, auto-scaling and replacing failed instances without logging users out. State lives in shared stores (databases, Redis, object storage) or in tokens carried by the client.
</QA>

<QA q="What is the difference between binding a server to 127.0.0.1 and 0.0.0.0?">
127.0.0.1 is the loopback interface, so only processes on the same machine can connect. 0.0.0.0 means all network interfaces, so the service is reachable from other machines if firewalls allow it. Databases and internal admin tools should bind to localhost or a private interface.
</QA>

<QA q="Why is client-side validation not enough?">
The client runs on a device the user controls. Anyone can modify the JavaScript, use browser dev tools, or skip the UI entirely and send requests with curl or Burp Suite. Client-side validation is for user experience; all validation, authentication and authorisation must also happen on the server.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Client">A program that initiates requests.</Term>
  <Term name="Server">A program that listens for and responds to requests; also the machine running it.</Term>
  <Term name="Port">A number (0–65535) identifying a service on a host.</Term>
  <Term name="Socket">An OS endpoint for network communication, bound to an address and port.</Term>
  <Term name="Request / response">The basic exchange: the client asks, the server answers.</Term>
  <Term name="Stateless">Each request carries everything needed; the server keeps no per-client memory between requests.</Term>
  <Term name="Reverse proxy">A server that receives client requests and forwards them to backend servers, such as Nginx.</Term>
  <Term name="Load balancer">Distributes requests across multiple servers.</Term>
  <Term name="Trust boundary">The point where data from an untrusted source enters a system you control.</Term>
