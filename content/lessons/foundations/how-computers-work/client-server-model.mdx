<Callout type="tip" title="In one minute">
A **server** is a process that waits for requests on a network **address and port**. A **client** is a process that sends a request and waits for a **response**. Your browser is a client of your Next.js server; your Next.js server is a client of PostgreSQL and of the Stripe API. Between them sit DNS, load balancers, reverse proxies and CDNs. Servers must treat every request as untrusted, because anyone can write a client.
</Callout>

## What is it?

The **client–server model** splits a system into two roles:

| Role | What it does | Examples |
| --- | --- | --- |
| **Client** | Starts the conversation, sends a request, uses the response | Browser, mobile app, `curl`, Postman, your backend calling another API |
| **Server** | Listens on an address and port, processes requests, sends responses | Nginx, a Next.js/Express app, PostgreSQL, Redis, an SSH daemon |

"Server" means two things, and people use both:

- **Server software** — a process listening on a port (`node server.js` on port 3000).
- **Server machine** — the computer (physical or virtual) that runs such processes.

One machine usually runs several server processes, each on its own **port**:

| Port | Typical service |
| --- | --- |
| 22 | SSH |
| 53 | DNS |
| 80 | HTTP |
| 443 | HTTPS |
| 3000 / 8080 | Development web servers |
| 5432 | PostgreSQL |
| 6379 | Redis |
| 27017 | MongoDB |

A **request/response** exchange always has the same shape: the client says *what it wants* (method, path, data, credentials), and the server answers with *a result* (status, data, errors).

### Other models, for comparison

- **Peer-to-peer (P2P):** every node is both client and server (BitTorrent, some video calls, blockchains).
- **Publish/subscribe:** producers send messages to a broker; consumers receive them without talking directly (Kafka, Redis pub/sub, SNS). Still built on client–server connections underneath.
- **Server push:** WebSockets and Server-Sent Events let the server send data whenever it wants — but the **client** still opens the connection first.

## Why does it matter?

- **Full-stack:** every `fetch`, every API route, every database query is a client talking to a server. Knowing which side code runs on is the core of Next.js (Server vs Client Components).
- **DevOps:** you deploy servers, expose ports, configure reverse proxies and load balancers, and set health checks that act as clients.
- **Cloud:** security groups, load balancers, API gateways and managed databases are all about who may act as a client to which server on which port.
- **Security:** the server is the trust boundary. Client-side checks can always be bypassed; authorisation, validation and rate limiting must happen on the server. Every open port is attack surface.

## When and where do you use it?

- Writing a Next.js route handler (server) and calling it with `fetch` from a component (client).
- Opening port 443 but not 5432 in a firewall or AWS security group.
- Pointing a domain at a server with DNS.
- Putting Nginx in front of a Node.js app.
- Debugging "it works in Postman but not in the browser" (usually CORS — a browser rule, not a server one).
- Testing an API directly with `curl` to bypass the front-end entirely — which is exactly what attackers do.

## How does it work?

### What happens when you open a website

```text
You type https://shop.example.com/products
   │
 1 │ DNS: browser asks a resolver "what IP is shop.example.com?"  →  203.0.113.10
 2 │ TCP: browser connects to 203.0.113.10 port 443 (three-way handshake)
 3 │ TLS: they agree on encryption; the server proves its identity with a certificate
 4 │ HTTP request:   GET /products   Host: shop.example.com   Cookie: session=…
   ▼
 CDN / load balancer ──► Nginx (reverse proxy) ──► Next.js process :3000
                                                         │ is a CLIENT of ▼
                                                   PostgreSQL :5432, Redis :6379, Stripe API
   ▲
 5 │ HTTP response:  200 OK   Content-Type: text/html   …page…
 6 │ Browser renders, then makes more requests for CSS, JS, images, API data
```

Each of these steps has its own lesson in the Networking module. The point here: **one page load is a chain of clients and servers**, and a request is often "client" and "server" several times over.

### Sockets: how a process listens

A server process asks the OS for a **socket**, **binds** it to an address and port, and **listens**. The OS queues incoming connections; the process **accepts** them. A connection is identified by four values: client IP, client port, server IP, server port.

```text
Server:  0.0.0.0:443  (listening)
Conn 1:  198.51.100.7:52114  ⇄  203.0.113.10:443
Conn 2:  198.51.100.7:52115  ⇄  203.0.113.10:443   ← same client, new random source port
Conn 3:  192.0.2.44:61002    ⇄  203.0.113.10:443
```

The **bind address** matters for security:

- `127.0.0.1` (localhost): only processes on the same machine can connect.
- `0.0.0.0`: every network interface — reachable from outside if the firewall allows.

### Stateless servers, stateful sessions

HTTP is **stateless**: each request stands alone, and the server does not automatically remember previous ones. Login "state" is carried by the client on every request — a **session cookie** pointing to data on the server, or a **token** (such as a JWT).

Designing your app servers to be stateless (sessions in Redis or the database, files in S3) is what allows you to run many copies behind a load balancer and replace any of them at any time — the basis of horizontal scaling, containers and Kubernetes.

### Thin client vs thick client

- **Server-rendered** (classic PHP, Next.js Server Components): the server builds HTML; the client mostly displays it.
- **Client-rendered** (single-page apps): the server sends JavaScript and JSON; the browser builds the UI.
- **Native/mobile apps:** the client is a compiled app; the server is usually a JSON API.

In all cases the **server is the authority**. The client is just a user interface the user fully controls.

### Tiers

```text
2-tier:  client ──► database                                   (old desktop apps; risky)
3-tier:  client ──► application server ──► database             (standard web app)
n-tier:  client ──► CDN ──► load balancer ──► app servers ──► cache / queue / database / other APIs
```

## Hands-on

Be a client by hand:

```bash
# Ask a server for a page and show the request and response headers
curl -v https://example.com/ -o /dev/null

# Just the response headers
curl -I https://example.com/

# Call a JSON API
curl -s https://jsonplaceholder.typicode.com/users/1

# Which servers are listening on this machine, on which address and port?
sudo ss -ltnp
```

Be a server: a minimal HTTP server in Node.js. Save it as `server.mjs` and run `node server.mjs`, then open `http://localhost:3000/hello?name=Moiz`.

```javascript
// server.mjs — a tiny HTTP server (run with Node.js, not the playground)
import http from "node:http";

const server = http.createServer((req, res) => {
  const url = new URL(req.url, "http://localhost");
  console.log(new Date().toISOString(), req.socket.remoteAddress, req.method, url.pathname);

  if (url.pathname === "/hello") {
    const name = (url.searchParams.get("name") ?? "world").slice(0, 50);
    res.writeHead(200, { "Content-Type": "application/json; charset=utf-8" });
    return res.end(JSON.stringify({ message: `Hello, ${name}` }));
  }
  res.writeHead(404, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ error: "Not found" }));
});

// 127.0.0.1 = only this machine can connect. 0.0.0.0 would expose it to the network.
server.listen(3000, "127.0.0.1", () => console.log("listening on http://127.0.0.1:3000"));
```

And be a client in the playground — a real request to a real server:

```javascript
const t = Date.now();
const res = await fetch("https://jsonplaceholder.typicode.com/posts/1");
console.log("status:", res.status, res.statusText);
console.log("content-type:", res.headers.get("content-type"));
const body = await res.json();
console.log("title:", body.title);
console.log("round trip:", Date.now() - t, "ms");

// A request for something that does not exist
const missing = await fetch("https://jsonplaceholder.typicode.com/posts/999999");
console.log("missing →", missing.status);
```

## Real-world example

Your Next.js e-commerce app on AWS:

| Client | Server | Port | Who may connect |
| --- | --- | --- | --- |
| Customer's browser | CloudFront (CDN) | 443 | Everyone |
| CloudFront | Application Load Balancer | 443 | Only CloudFront |
| Load balancer | Next.js containers (ECS) | 3000 | Only the load balancer's security group |
| Next.js | RDS PostgreSQL | 5432 | Only the app's security group |
| Next.js | Stripe API | 443 | Outbound only |
| You (admin) | Servers | 22 or Session Manager | Only your IP / IAM users |

Every row is a client–server relationship, and every row is a security decision. The database is never reachable from the internet; it is a server **only** to the application. Drawing this table for any system is the first step of both architecture and threat modelling.

## Common mistakes

- **Trusting the client:** hiding an admin button, validating only in the browser, or sending the price from the front-end. Anyone can call the API directly with `curl`.
- **Binding databases and admin panels to `0.0.0.0`** and exposing them to the internet. Bind to localhost or a private network and use firewalls.
- **Storing session state in server memory**, so users are logged out whenever a request hits a different instance or the server restarts.
- **Confusing CORS with security.** CORS is a browser rule about which sites' JavaScript may read responses. It does not stop `curl`, scripts or other servers from calling your API.
- **No timeouts on outgoing requests**, so one slow third-party server ties up all your resources.

## Security lens

<Callout type="security">
The server is the only place you control. Treat every request as if it came from an attacker's custom client — because sometimes it does.
</Callout>

- **Never trust client input:** validate type, length and format on the server; authorise every request (does *this* user own *this* order?). Broken access control is the #1 category in the OWASP Top 10 (2021).
- **Minimise exposed ports:** every listening port reachable from the internet is attack surface. Scan your own servers (`nmap`) and compare with what you expect.
- **Authentication on every service:** many breaches started with an internet-exposed database, Redis, Elasticsearch or Docker API with no password.
- **Encrypt in transit:** use HTTPS/TLS between client and server — and between internal services when the network is shared.
- **Rate limiting and timeouts:** protect servers from brute force and denial of service; protect clients from hanging on slow servers.
- **Server-side request forgery (SSRF):** when your server acts as a client to a URL the user supplies, attackers can make it call internal services or the cloud metadata endpoint (`169.254.169.254`) to steal credentials. Covered in depth in Web App Security and Cloud Security.
- **Logging:** log client IP, method, path, status and user on the server — this is the raw material of detection and incident response.

## Interview questions

<QA q="Explain the client–server model.">
It is an architecture where clients initiate requests and servers wait for them, process them and return responses. Servers listen on a network address and port and typically serve many clients; clients can be browsers, mobile apps or other servers. One component can be a server to some parts of the system and a client to others, like a web app that serves browsers and calls a database.
</QA>

<QA q="What happens when you type a URL into a browser and press Enter?">
The browser parses the URL, resolves the hostname to an IP address via DNS, opens a TCP connection to the server's port (443 for HTTPS), performs a TLS handshake and verifies the certificate, then sends an HTTP request. The request may pass through a CDN, load balancer and reverse proxy to the application, which may query databases and other services. The server returns an HTTP response; the browser parses and renders it and makes further requests for CSS, JavaScript, images and API data.
</QA>

<QA q="Why should application servers be stateless?">
If servers keep no client-specific state in memory, any instance can handle any request. That allows horizontal scaling behind a load balancer, rolling deployments, auto-scaling and replacing failed instances without logging users out. State lives in shared stores — databases, Redis, object storage — or in tokens carried by the client.
</QA>

<QA q="What is the difference between binding a server to 127.0.0.1 and 0.0.0.0?">
127.0.0.1 is the loopback interface, so only processes on the same machine can connect. 0.0.0.0 means all network interfaces, so the service is reachable from other machines if firewalls allow it. Databases and internal admin tools should bind to localhost or a private interface, never be exposed publicly.
</QA>

<QA q="Why is client-side validation not enough?">
The client runs on a device the user controls. Anyone can modify the JavaScript, use browser dev tools, or skip the UI entirely and send requests with curl or Burp Suite. Client-side validation is for user experience; all validation, authentication and authorisation must also happen on the server.
</QA>

## Key terms

<Terms>
  <Term name="Client">A program that initiates requests.</Term>
  <Term name="Server">A program that listens for and responds to requests; also the machine running it.</Term>
  <Term name="Port">A number (0–65535) identifying a service on a host.</Term>
  <Term name="Socket">An OS endpoint for network communication, bound to an address and port.</Term>
  <Term name="Request / response">The basic exchange: the client asks, the server answers.</Term>
  <Term name="Stateless">Each request carries everything needed; the server keeps no per-client memory between requests.</Term>
  <Term name="Reverse proxy">A server that receives client requests and forwards them to backend servers, such as Nginx.</Term>
  <Term name="Load balancer">Distributes requests across multiple servers.</Term>
  <Term name="Trust boundary">The point where data from an untrusted source enters a system you control.</Term>
</Terms>
