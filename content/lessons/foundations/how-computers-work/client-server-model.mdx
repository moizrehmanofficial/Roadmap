<Callout type="tip" title="In one minute">
A **client** asks; a **server** answers. Your browser (client) sends a **request** — "GET /products" — to a server's **IP address** and **port** (443 for HTTPS); the server program listening there sends back a **response** — status `200 OK` plus data. The same pattern is used by mobile apps calling APIs, your API calling a database, and `git push` talking to GitHub. Web servers are usually **stateless**: each request carries everything needed (like a cookie or token) so any server can answer it. Real systems have **tiers**: client → web/API server → database.
</Callout>

## Start from zero

### Asking and answering

When you open Amazon, check WhatsApp or deploy with `git push`, two programs are talking: one **asks**, the other **answers**.

<Callout type="analogy">
A **restaurant**:

- You (the **client**) look at the menu and tell the waiter: "One chicken karahi, please." That is a **request**.
- The kitchen (the **server**) prepares it and the waiter brings the dish — or says "Sorry, we're out of chicken". That is the **response**, with a result (**status**).
- The restaurant's **address** is the IP address; the specific **counter** you go to (takeaway, dine-in, delivery) is the **port**.
- The kitchen does not remember you between visits unless you show your **loyalty card** — that is a session cookie or token.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Client** | The program that starts the conversation and asks | browser, mobile app, `curl`, your API calling a DB |
| **Server** | A program that waits for requests and answers | nginx, a Node.js API, PostgreSQL |
| **Request** | The question sent by the client | `GET /api/users/7` |
| **Response** | The answer sent back | `200 OK` + JSON |
| **IP address** | The network address of a machine | `142.250.181.14`, `127.0.0.1` |
| **Port** | A number identifying one program on that machine | 443 (HTTPS), 5432 (PostgreSQL) |
| **Protocol** | The agreed language of the conversation | HTTP, SSH, SMTP, PostgreSQL protocol |
| **DNS** | Turns names like `google.com` into IP addresses | |
| **Socket** | One end of a network connection inside a program | |

## What is it?

The **client–server model** is a way of organising software where **servers** provide a service (web pages, data, files, email) and **clients** use it by sending requests over a network.

- A **server** is a **program** (and, loosely, the machine running it). One machine can run many server programs, each on its own port.
- A program can be **both**: your Node.js API is a server for browsers and a **client** of the database.

| Model | How it works | Examples |
| --- | --- | --- |
| Client–server | Central servers, many clients | Websites, APIs, email, databases |
| Peer-to-peer (P2P) | Every computer is both client and server | BitTorrent, some video calls, blockchains |
| Pub/sub, message queues | Senders publish messages; receivers subscribe | Kafka, RabbitMQ, WebSocket notifications |

## Why does it matter?

- **It is the shape of almost everything you build:** React front-end (client) + NestJS API (server) + PostgreSQL (server for the API).
- **Debugging:** "is the problem in the client, the network, or the server?" is the first question in every incident.
- **Scaling:** stateless servers can be copied behind a load balancer; understanding why requires this model.
- **Security:** every server port is an entry point; the client can never be trusted; data travels across networks you do not control.

## When and where do you use it?

| You are… | Client | Server |
| --- | --- | --- |
| Opening a website | Browser | nginx / Next.js on port 443 |
| Calling an API from React | `fetch()` in the browser | Express / NestJS |
| Querying a database | Your API (Prisma, pg) | PostgreSQL on 5432 |
| Logging in to a server | `ssh` | `sshd` on 22 |
| Pushing code | `git` | GitHub over HTTPS/SSH |

## Concepts one by one

### 1. Request and response

<Explain>
<What>
Every interaction is a pair: the client sends a **request**; the server sends one **response**.
</What>
<Why>
It is the basic unit of all web and API traffic — and the unit you read in logs and DevTools.
</Why>
<When>
Every page load, API call, image, font, and form submit.
</When>
<Where>
Browser DevTools → Network tab, server access logs, `curl -v`.
</Where>
<How>
An HTTP request has a **method** (GET, POST, PUT, DELETE), a **path**, **headers** and sometimes a **body**. A response has a **status code**, headers and a body.
</How>
</Explain>

```text
REQUEST (client → server)                RESPONSE (server → client)
──────────────────────────────           ─────────────────────────────────
GET /api/products/7 HTTP/1.1             HTTP/1.1 200 OK
Host: shop.example.com                   Content-Type: application/json
Accept: application/json                 Content-Length: 46
Authorization: Bearer eyJhbGci…
                                         {"id":7,"name":"Kettle","price":3500}
```

| Status | Meaning | Whose problem? |
| --- | --- | --- |
| 2xx (200, 201, 204) | Success | — |
| 3xx (301, 302, 304) | Redirect / not modified | — |
| 4xx (400, 401, 403, 404, 429) | The **request** was wrong | Client |
| 5xx (500, 502, 503, 504) | The **server** failed | Server |

### 2. A server you can run and call

<Explain>
<What>
A small program that **listens** on a port and answers requests, and a client (`curl`) that calls it.
</What>
<Why>
Seeing both sides on your own machine makes the model concrete.
</Why>
<When>
Learning, local development, testing.
</When>
<Where>
Your laptop: `localhost` / `127.0.0.1` means "this same machine".
</Where>
<How>
Node.js's `http` module creates a server; `curl` sends requests and shows responses.
</How>
</Explain>

```bash
cat > server.mjs <<'EOF'
import http from "node:http";
const server = http.createServer((req, res) => {
  const url = new URL(req.url, "http://localhost");
  if (url.pathname === "/hello") {
    const name = (url.searchParams.get("name") ?? "world").slice(0, 50);
    res.writeHead(200, { "Content-Type": "application/json" });
    return res.end(JSON.stringify({ message: `Hello, ${name}` }));
  }
  res.writeHead(404, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ error: "Not found" }));
});
server.listen(3456, "127.0.0.1");
EOF
node server.mjs &
server_pid=$!
sleep 0.5

curl -s "http://127.0.0.1:3456/hello?name=Alex"; echo
curl -s -o /dev/null -w "status for /nope: %{http_code}\n" http://127.0.0.1:3456/nope
curl -s -i http://127.0.0.1:3456/hello | head -2 | tr -d '\r'

kill "$server_pid"
```

```text output
{"message":"Hello, Alex"}
status for /nope: 404
HTTP/1.1 200 OK
Content-Type: application/json
```

- `node server.mjs &` — start the **server** in the background; it waits for requests.
- `curl …/hello?name=Alex` — the **client** sends a GET request; the server answers with JSON.
- `-w "%{http_code}"` — show only the status code.
- `-i` — include the response headers.

### 3. IP addresses and ports

<Explain>
<What>
An **IP address** identifies a machine on a network; a **port** (0–65535) identifies one program on that machine. Together, `IP:port` is the full address of a service.
</What>
<Why>
One server machine runs many services. The port tells the operating system which program should receive the data.
</Why>
<When>
Configuring apps (`PORT=3000`), firewalls, Docker port mappings (`-p 8080:3000`), connection strings.
</When>
<Where>
Everywhere in DevOps and security.
</Where>
<How>
Learn the well-known ports. `127.0.0.1` (localhost) = only this machine; `0.0.0.0` when listening = all network interfaces (reachable from outside if the firewall allows).
</How>
</Explain>

<Callout type="analogy">
The IP address is the **building address**; the port is the **flat number**. A letter needs both to reach the right person.
</Callout>

| Port | Service |
| --- | --- |
| 22 | SSH |
| 53 | DNS |
| 80 | HTTP |
| 443 | HTTPS |
| 3000 / 8080 | Common for development apps |
| 3306 | MySQL / MariaDB |
| 5432 | PostgreSQL |
| 6379 | Redis |
| 27017 | MongoDB |

### 4. What happens when you open a website

<Explain>
<What>
The chain of steps between typing `https://shop.example.com` and seeing the page.
</What>
<Why>
Each step can fail — DNS, connection, TLS, the server, the database — and knowing the chain tells you where to look.
</Why>
<When>
Every page visit; every debugging session for "the site is down".
</When>
<Where>
Browser, OS, network, CDN, load balancer, servers.
</Where>
<How>
Follow the numbered steps below. Later lessons (DNS, TCP/IP, HTTP, TLS) go deep into each one.
</How>
</Explain>

```text
1. DNS        browser asks: "IP of shop.example.com?"     → 203.0.113.10
2. TCP        browser connects to 203.0.113.10:443         (three-way handshake)
3. TLS        both sides agree on encryption; the server proves its identity with a certificate
4. HTTP       browser sends:  GET / HTTP/2  Host: shop.example.com
5. Server     nginx → forwards to the Node.js app → app queries PostgreSQL
6. Response   200 OK + HTML
7. More       browser parses HTML, requests CSS, JS, images, fonts (dozens of requests)
8. Render     the page appears; JavaScript calls APIs for more data
```

```bash
getent hosts localhost | awk '{print "DNS-style lookup: localhost →", $1}'
```

```text output
DNS-style lookup: localhost → 127.0.0.1
```

(Some systems show `::1` instead — the IPv6 form of "this machine".)

### 5. How a server listens: sockets

<Explain>
<What>
A server program asks the OS to **listen** on a port. The OS then passes incoming connections to it. Each connection is a **socket**: the pair client-IP:client-port ↔ server-IP:server-port.
</What>
<Why>
Explains errors like "address already in use" (another program has the port) and "connection refused" (nothing is listening).
</Why>
<When>
Starting servers, debugging connections, firewall rules.
</When>
<Where>
`ss -ltnp` (or `netstat -ltnp`) lists listening sockets on Linux.
</Where>
<How>
Only **one** program can listen on a given IP:port. The client side uses a random high port (**ephemeral port**) for its end.
</How>
</Explain>

```bash
node -e 'require("http").createServer(()=>{}).listen(3457,"127.0.0.1")' &
first=$!
sleep 0.5
node -e 'require("http").createServer(()=>{}).listen(3457,"127.0.0.1").on("error",e=>{console.log("second server:",e.code);process.exit(1)})'
curl -s -o /dev/null -w "nothing on port 3999 → curl exit code %{exitcode}\n" http://127.0.0.1:3999/ || true
kill "$first"
```

```text output
second server: EADDRINUSE
nothing on port 3999 → curl exit code 7
```

- `EADDRINUSE` — the port is already taken by the first server.
- curl exit code `7` — "failed to connect": **connection refused**, nobody is listening.

### 6. Stateless servers and sessions

<Explain>
<What>
HTTP is **stateless**: each request is independent, and the server does not automatically remember the previous one. To keep a user "logged in", the client sends proof with **every** request — a **cookie** with a session ID, or a **token** (often a JWT).
</What>
<Why>
Stateless servers are easy to scale: any copy of the server can answer any request, so you can run many copies behind a **load balancer**.
</Why>
<When>
Login systems, carts, any "remember me" behaviour.
</When>
<Where>
Express sessions with Redis, NextAuth, JWT in an `Authorization` header.
</Where>
<How>
Keep state in a shared place (database, Redis) or in a signed token — **not** in the memory of one server process.
</How>
</Explain>

```text
Bad (state in server memory):              Good (state shared or in a token):

 user ─► LB ─► server A  (remembers user)    user ─► LB ─► server A ─┐
          │                                           │               ├─► Redis / DB (sessions)
          └──► server B  ("who are you?")             └──► server B ──┘
```

### 7. Thin and thick clients

<Explain>
<What>
A **thin client** shows what the server prepares (classic server-rendered HTML). A **thick client** does a lot itself and calls the server only for data (React single-page apps, mobile apps).
</What>
<Why>
It affects performance, SEO, security and where logic lives.
</Why>
<When>
Choosing an architecture: Next.js server components vs a React SPA calling an API.
</When>
<Where>
Web apps, mobile apps, desktop apps.
</Where>
<How>
Whatever the client does, **security checks must happen on the server** — anyone can change client-side code in DevTools.
</How>
</Explain>

### 8. Tiers: real systems are chains of clients and servers

<Explain>
<What>
A production system splits responsibilities into **tiers**: presentation (browser/app), application (API servers), and data (databases, caches, storage).
</What>
<Why>
Each tier can be scaled, secured and deployed separately. Databases should never be directly reachable from the internet.
</Why>
<When>
Designing any non-trivial app; reading architecture diagrams.
</When>
<Where>
Every company's architecture; cloud networks (public and private subnets).
</Where>
<How>
Each arrow in the diagram is a client–server relationship with its own port and protocol.
</How>
</Explain>

```text
 Internet
    │ HTTPS 443
    ▼
┌──────────────┐   public subnet
│ Load balancer│
└──────┬───────┘
       │ HTTP 3000
┌──────▼───────┐   private subnet
│  API servers │──► Redis 6379 (sessions, cache)
│  (NestJS ×3) │
└──────┬───────┘
       │ 5432
┌──────▼───────┐   private subnet, no internet access
│  PostgreSQL  │
└──────────────┘
```

## Hands-on

```bash
mkdir -p ~/cs-lab && cd ~/cs-lab

# 1. Start a tiny server and act as several clients
cat > api.mjs <<'EOF'
import http from "node:http";
let hits = 0;
http.createServer((req, res) => {
  hits++;
  const status = req.url === "/admin" ? 403 : req.url === "/" ? 200 : 404;
  res.writeHead(status, { "Content-Type": "text/plain" });
  res.end(`request #${hits}: ${req.method} ${req.url} → ${status}\n`);
}).listen(3458, "127.0.0.1");
EOF
node api.mjs & pid=$!; sleep 0.5

curl -s http://127.0.0.1:3458/
curl -s http://127.0.0.1:3458/admin
curl -s -X POST http://127.0.0.1:3458/orders
for code in $(for p in / /admin /x; do curl -s -o /dev/null -w '%{http_code} ' "http://127.0.0.1:3458$p"; done); do printf '%s ' "$code"; done; echo

kill $pid
cd ~ && rm -rf ~/cs-lab
```

```text output
request #1: GET / → 200
request #2: GET /admin → 403
request #3: POST /orders → 404
200 403 404 
```

The server counted 6 requests in total but the last 3 only printed their status codes. Note that `hits` lives in the **memory of this one process** — restart it and the count is lost, and a second copy of the server would have its own count. That is exactly why shared state belongs in a database or Redis.

## Real-world example

Your Next.js e-commerce app on AWS:

| Client | Server | Port | Who may connect |
| --- | --- | --- | --- |
| Customer's browser | CloudFront (CDN) | 443 | Everyone |
| CloudFront | Application Load Balancer | 443 | Only CloudFront |
| Load balancer | Next.js containers (ECS) | 3000 | Only the load balancer's security group |
| Next.js | RDS PostgreSQL | 5432 | Only the app's security group |
| Next.js | Stripe API | 443 | Outbound only |
| You (admin) | Servers | 22 or Session Manager | Only your IP / IAM users |

Every row is a client–server relationship, and every row is a security decision. The database is never reachable from the internet; it is a server **only** to the application. Drawing this table for any system is the first step of both architecture and threat modelling.

## Common mistakes

- **Trusting the client:** hiding an admin button, validating only in the browser, or sending the price from the front-end. Anyone can call the API directly with `curl`.
- **Binding databases and admin panels to `0.0.0.0`** and exposing them to the internet. Bind to localhost or a private network and use firewalls.
- **Storing session state in server memory**, so users are logged out whenever a request hits a different instance or the server restarts.
- **Confusing CORS with security.** CORS is a browser rule about which sites' JavaScript may read responses. It does not stop `curl`, scripts or other servers from calling your API.
- **No timeouts on outgoing requests**, so one slow third-party server ties up all your resources.

## Security lens

<Callout type="security">
The server is the only place you control. Treat every request as if it came from an attacker's custom client — because sometimes it does.
</Callout>

- **Never trust client input:** validate type, length and format on the server; authorise every request (does *this* user own *this* order?). Broken access control is the #1 category in the OWASP Top 10 (2021).
- **Minimise exposed ports:** every listening port reachable from the internet is attack surface. Scan your own servers (`nmap`) and compare with what you expect.
- **Authentication on every service:** many breaches started with an internet-exposed database, Redis, Elasticsearch or Docker API with no password.
- **Encrypt in transit:** use HTTPS/TLS between client and server — and between internal services when the network is shared.
- **Rate limiting and timeouts:** protect servers from brute force and denial of service; protect clients from hanging on slow servers.
- **Server-side request forgery (SSRF):** when your server acts as a client to a URL the user supplies, attackers can make it call internal services or the cloud metadata endpoint (`169.254.169.254`) to steal credentials. Covered in depth in Web App Security and Cloud Security.
- **Logging:** log client IP, method, path, status and user on the server — this is the raw material of detection and incident response.

## Interview questions

<QA q="Explain the client–server model.">
It is an architecture where clients initiate requests and servers wait for them, process them and return responses. Servers listen on a network address and port and typically serve many clients; clients can be browsers, mobile apps or other servers. One component can be a server to some parts of the system and a client to others, like a web app that serves browsers and calls a database.
</QA>

<QA q="What happens when you type a URL into a browser and press Enter?">
The browser parses the URL, resolves the hostname to an IP address via DNS, opens a TCP connection to the server's port (443 for HTTPS), performs a TLS handshake and verifies the certificate, then sends an HTTP request. The request may pass through a CDN, load balancer and reverse proxy to the application, which may query databases and other services. The server returns an HTTP response; the browser parses and renders it and makes further requests for CSS, JavaScript, images and API data.
</QA>

<QA q="Why should application servers be stateless?">
If servers keep no client-specific state in memory, any instance can handle any request. That allows horizontal scaling behind a load balancer, rolling deployments, auto-scaling and replacing failed instances without logging users out. State lives in shared stores — databases, Redis, object storage — or in tokens carried by the client.
</QA>

<QA q="What is the difference between binding a server to 127.0.0.1 and 0.0.0.0?">
127.0.0.1 is the loopback interface, so only processes on the same machine can connect. 0.0.0.0 means all network interfaces, so the service is reachable from other machines if firewalls allow it. Databases and internal admin tools should bind to localhost or a private interface, never be exposed publicly.
</QA>

<QA q="Why is client-side validation not enough?">
The client runs on a device the user controls. Anyone can modify the JavaScript, use browser dev tools, or skip the UI entirely and send requests with curl or Burp Suite. Client-side validation is for user experience; all validation, authentication and authorisation must also happen on the server.
</QA>

## Key terms

<Terms>
  <Term name="Client">A program that initiates requests.</Term>
  <Term name="Server">A program that listens for and responds to requests; also the machine running it.</Term>
  <Term name="Port">A number (0–65535) identifying a service on a host.</Term>
  <Term name="Socket">An OS endpoint for network communication, bound to an address and port.</Term>
  <Term name="Request / response">The basic exchange: the client asks, the server answers.</Term>
  <Term name="Stateless">Each request carries everything needed; the server keeps no per-client memory between requests.</Term>
  <Term name="Reverse proxy">A server that receives client requests and forwards them to backend servers, such as Nginx.</Term>
  <Term name="Load balancer">Distributes requests across multiple servers.</Term>
  <Term name="Trust boundary">The point where data from an untrusted source enters a system you control.</Term>
</Terms>
