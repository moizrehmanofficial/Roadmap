<BigIdea>
<Tr>
<En>
You write code as **text**. The CPU only understands **machine code** (numbers in binary). So something must **translate** your text before or while it runs: a **compiler**, an **interpreter**, or a mix of both.
</En>
<Ur>
Aap code **text** ki shakal me likhte hain. CPU sirf **machine code** (binary numbers) samajhta hai. Isliye kisi cheez ko aap ka text chalne se pehle ya chalte waqt **tarjuma (translate)** karna parta hai: **compiler**, **interpreter**, ya dono ka milan.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

The **translators** that turn your code into something the CPU can run:

- **Compiler:** translates the **whole program first**, then you run the result (Go, C, Rust).
- **Interpreter:** translates and runs **one line at a time** while the program runs (Bash).
- **JIT engine:** starts like an interpreter, then **speeds up** the parts that run a lot (JavaScript in Chrome and Node.js).
- **Runtime:** the "home" your program lives in while it runs, like **Node.js**.

</En>
<Ur>

Wo **tarjuma karne wale (translators)** jo aap ke code ko CPU ke chalane ke qabil banate hain:

- **Compiler:** **poora program pehle** tarjuma karta hai, phir aap nateeja chalate hain (Go, C, Rust).
- **Interpreter:** program chalte waqt **ek line ek waqt** tarjuma karke chalata hai (Bash).
- **JIT engine:** interpreter ki tarah shuru hota hai, phir baar baar chalne wale hisson ko **tez** kar deta hai (Chrome aur Node.js me JavaScript).
- **Runtime:** wo "ghar" jahan aap ka program chalte waqt rehta hai, jaise **Node.js**.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

This explains a lot of everyday things:

- why a **Go** app is one file you copy to a server, but a **Node.js** app needs Node.js installed
- why some errors appear **before** running and others only **while** running
- why **TypeScript** types don't protect you from bad data coming from users
- why some apps slowly use more and more memory

</En>
<Ur>

Is se roz ki kai cheezen samajh aati hain:

- **Go** app ek file kyun hoti hai jo server par copy kar do, jabke **Node.js** app ke liye Node.js install hona zaroori hai
- kuch errors chalane se **pehle** kyun aate hain aur kuch sirf **chalte waqt**
- **TypeScript** ki types users se aane wale ghalat data se kyun nahi bachatin
- kuch apps dheere dheere zyada memory kyun khane lagti hain

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Every time you:

- run `npm run build` in a React or Next.js project
- start a server with `node server.js`
- run a Bash script
- build a Docker image for your app

</En>
<Ur>

Har dafa jab aap:

- React ya Next.js project me `npm run build` chalate hain
- `node server.js` se server shuru karte hain
- Bash script chalate hain
- apni app ki Docker image banate hain

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Most translators work in steps:

1. **Read** your text and check the grammar (spelling mistakes in code become **syntax errors** here).
2. **Turn** it into simpler instructions.
3. **Run** those instructions, or save them in a file to run later.

</En>
<Ur>

Zyada tar translators qadam ba qadam kaam karte hain:

1. Aap ka text **parhte** hain aur grammar check karte hain (code ki ghaltiyan yahan **syntax errors** ban kar aati hain).
2. Use aasaan hidayaat me **badalte** hain.
3. Un hidayaat ko **chalate** hain, ya baad me chalane ke liye file me save kar dete hain.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

You wrote a speech in **English** for an audience that only understands **Japanese**.

- **Compiler:** a translator translates the **whole speech in advance** and hands you a printed Japanese copy. Reading it out is fast, but every change means translating again.
- **Interpreter:** a translator stands next to you and translates **sentence by sentence while you speak**. Easy to change things on the fly, but every sentence takes extra time.
- **JIT:** the live translator notices you repeat some paragraphs, so he writes those down in Japanese once and just reads them out after that.

</En>
<Ur>

Aap ne **English** me taqreer likhi hai, aur sunne wale sirf **Japanese** samajhte hain.

- **Compiler:** tarjuma karne wala **poori taqreer pehle hi** tarjuma karke aap ko Japanese ki chhapi hui copy de deta hai. Parhna tez hai, lekin har tabdeeli par dobara tarjuma.
- **Interpreter:** tarjuma karne wala aap ke saath khara ho kar **aap ke bolte waqt jumla jumla** tarjuma karta hai. Beech me tabdeeli aasaan, lekin har jumle par extra waqt.
- **JIT:** live tarjuma karne wala dekhta hai ke aap kuch paragraph baar baar dohrate hain, to wo unhe ek dafa Japanese me likh leta hai aur us ke baad seedha parh deta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Code is checked for 'grammar' first">

<Tr>
<En>

Before any code can run, the translator **reads** it and checks the grammar, just like a teacher checking a sentence. If something is in the wrong place, you get a **syntax error** and **nothing runs at all**.

</En>
<Ur>

Koi bhi code chalne se pehle translator use **parhta** hai aur grammar check karta hai, bilkul jaise teacher jumla check karta hai. Agar kuch ghalat jagah ho, to **syntax error** aata hai aur **kuch bhi nahi chalta**.

</Ur>
</Tr>

```javascript
try {
  new Function("let total = price * ;");
} catch (error) {
  console.log(error.name + ":", error.message);
}
```

```text output
SyntaxError: Unexpected token ';'
```

<Happened>
<Tr>
<En>

- `price * ;` is like the sentence "I want to buy and." Something is missing after `*`.
- The translator stopped at `;` and said **"Unexpected token ';'"**: "I didn't expect a `;` here."
- `new Function(...)` and `try/catch` are only used here so we can see the error message without stopping the page.

</En>
<Ur>

- `price * ;` aisa hai jaise jumla "Main khareedna chahta hoon aur." `*` ke baad kuch ghaib hai.
- Translator `;` par ruk gaya aur bola **"Unexpected token ';'"**: "Mujhe yahan `;` ki tawaqqo nahi thi."
- `new Function(...)` aur `try/catch` sirf isliye hain taake page roke baghair error ka message dekh sakein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Compiled programs: translated once, ahead of time">

<Tr>
<En>

A **compiler** translates the **whole** program into machine code and saves it as a file (an **executable**). Then you can run that file again and again with no translation needed, so it starts fast.

The catch: the file only works on **one kind of computer** (for example Linux on Intel). For Windows or for an ARM chip, you compile again.

Tools you'll use every day, like **Docker**, **Kubernetes** and **Terraform**, are compiled programs.

</En>
<Ur>

**Compiler** **poore** program ko machine code me tarjuma karke ek file me save kar deta hai (**executable**). Phir aap wo file baar baar chala sakte hain, tarjume ki zaroorat nahi, isliye ye tez shuru hoti hai.

Shart ye hai: wo file sirf **ek qisam ke computer** par chalti hai (misaal ke taur par Intel par Linux). Windows ya ARM chip ke liye dobara compile karna parta hai.

Jo tools aap roz istemal karenge, jaise **Docker**, **Kubernetes** aur **Terraform**, sab compiled programs hain.

</Ur>
</Tr>

```bash
file /bin/ls | grep -o 'ELF [0-9]*-bit [A-Z]*' | sed 's/$/ executable (machine code)/'
head -c 4 /bin/ls | od -An -c | tr -s ' '
```

```text output
ELF 64-bit LSB executable (machine code)
 177 E L F
```

<Happened>
<Tr>
<En>

- `ls` (the command that lists files) is a compiled program.
- Every Linux executable starts with the bytes `177 E L F`. That's the **ELF** format, which Linux knows how to load and run.
- Windows programs use a different format (`.exe`), so a Linux program can't run on Windows as-is.

</En>
<Ur>

- `ls` (files ki list dikhane wali command) ek compiled program hai.
- Har Linux executable `177 E L F` bytes se shuru hota hai. Ye **ELF** format hai, jise Linux load karke chalana jaanta hai.
- Windows programs ka format alag hai (`.exe`), isliye Linux ka program Windows par waise hi nahi chalta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Interpreted programs: translated line by line">

<Tr>
<En>

An **interpreter** reads your file and runs it **one line at a time**. There's no build step: you edit and run immediately. Bash scripts work like this.

The downside: a mistake on a line is only found **when that line is reached**.

</En>
<Ur>

**Interpreter** aap ki file parh kar use **ek line ek waqt** chalata hai. Build ka koi qadam nahi: edit karo aur foran chalao. Bash scripts aise hi chalti hain.

Nuqsan: kisi line ki ghalti sirf **tab pata chalti hai jab wo line aati hai**.

</Ur>
</Tr>

```bash
cat > demo.sh <<'EOF'
echo "line 1 runs"
echo "line 2 runs"
this-command-does-not-exist
echo "line 4 still runs (the interpreter just continues)"
EOF
bash demo.sh 2>&1 | sed 's/.*: line 3: /ERROR line 3: /'
```

```text output
line 1 runs
line 2 runs
ERROR line 3: this-command-does-not-exist: command not found
line 4 still runs (the interpreter just continues)
```

<Happened>
<Tr>
<En>

- Lines 1 and 2 ran fine.
- Line 3 has a command that doesn't exist. Bash only noticed when it **got there**.
- Bash printed an error and **kept going** to line 4. (In real scripts we usually tell Bash to stop on errors; you'll learn that in the Bash topic.)

</En>
<Ur>

- Line 1 aur 2 theek chal gayin.
- Line 3 me aisi command hai jo mojood hi nahi. Bash ko tab pata chala jab wo **wahan pohancha**.
- Bash ne error dikhaya aur line 4 tak **chalta raha**. (Asal scripts me hum aam tor par Bash ko error par rukne ka kehte hain; ye Bash topic me seekhenge.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="JavaScript: starts fast, then speeds up (JIT)">

<Tr>
<En>

JavaScript in Chrome and Node.js is run by an engine called **V8**. It uses a smart mix called **JIT** (Just-In-Time):

1. It starts running your code quickly, like an interpreter.
2. It watches which functions run **a lot** ("hot" code).
3. It compiles those hot functions into fast machine code **while the program is running**.

So the same function often gets **faster after it has run a few times**.

</En>
<Ur>

Chrome aur Node.js me JavaScript **V8** naam ka engine chalata hai. Ye **JIT** (Just-In-Time) naam ka samajhdaar milan istemal karta hai:

1. Aap ka code interpreter ki tarah jaldi chalana shuru karta hai.
2. Dekhta hai ke kaun se functions **bohot zyada** chalte hain ("hot" code).
3. Program **chalte waqt hi** un hot functions ko tez machine code me compile kar deta hai.

Isliye ek hi function aksar **kuch dafa chalne ke baad tez** ho jata hai.

</Ur>
</Tr>

```javascript
function sum(n) { let s = 0; for (let i = 0; i < n; i++) s += i; return s; }

let t = performance.now(); sum(1e6); const first = performance.now() - t;
for (let k = 0; k < 50; k++) sum(1e6);      // warm up: the function becomes "hot"
t = performance.now(); sum(1e6); const later = performance.now() - t;

console.log(later < first ? "after warm-up the same call is faster (JIT at work)" : "timings vary — run it again");
```

```text output
after warm-up the same call is faster (JIT at work)
```

<Happened>
<Tr>
<En>

- We time `sum(1e6)` once (cold), run it 50 more times to "warm it up", then time it again.
- The second time is faster, because V8 has turned it into optimised machine code.
- Press **Run** a few times: exact timings change, but the warm call is almost always faster.

</En>
<Ur>

- Hum `sum(1e6)` ka waqt ek dafa naapte hain (thanda), phir 50 dafa chala kar use "garam" karte hain, phir dobara waqt naapte hain.
- Doosri dafa tez hota hai, kyunke V8 use behtar machine code me badal chuka hota hai.
- **Run** kai dafa dabayen: waqt badalta rehta hai, lekin garam call taqreeban hamesha tez hoti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Node.js is a runtime: JavaScript plus extra powers">

<Tr>
<En>

JavaScript by itself can't read files or start a web server. A **runtime** gives it those powers.

- In the **browser**, JavaScript gets `window`, `document` (the web page) and `fetch`.
- In **Node.js**, JavaScript gets files (`fs`), web servers (`http`) and `process`, but **no** web page.

Same language, different "home", different tools.

</En>
<Ur>

JavaScript khud files nahi parh sakta aur web server shuru nahi kar sakta. **Runtime** use ye taqat deta hai.

- **Browser** me JavaScript ko `window`, `document` (web page) aur `fetch` milte hain.
- **Node.js** me JavaScript ko files (`fs`), web servers (`http`) aur `process` milte hain, lekin web page **nahi**.

Zabaan ek, "ghar" alag, tools alag.

</Ur>
</Tr>

```bash
node -e 'console.log("window in Node:", typeof window); console.log("process in Node:", typeof process); console.log("Node uses V8:", typeof process.versions.v8 === "string")'
```

```text output
window in Node: undefined
process in Node: object
Node uses V8: true
```

<Happened>
<Tr>
<En>

- `window` doesn't exist in Node.js (`undefined`): there's no browser window on a server.
- `process` exists (`object`): Node.js gives you information about the running program.
- Node.js runs on the same **V8** engine as Chrome.

</En>
<Ur>

- Node.js me `window` mojood nahi (`undefined`): server par browser ki window nahi hoti.
- `process` mojood hai (`object`): Node.js chalte program ki maloomat deta hai.
- Node.js wahi **V8** engine istemal karta hai jo Chrome karta hai.

</Ur>
</Tr>
</Happened>

| Feature | Browser | Node.js |
| --- | --- | --- |
| Web page (`document`, `window`) | Yes | No |
| Files (`fs`) | No | Yes |
| Start a web server | No | Yes |
| `fetch`, timers, `console` | Yes | Yes |

</Step>

<Step title="TypeScript: the types disappear before running">

<Tr>
<En>

**TypeScript** is JavaScript with **types**: labels that say "this must be a number". They catch mistakes while you're writing code.

But browsers and Node.js can't run TypeScript. It's first **translated to plain JavaScript**, and **all the types are removed**. So while the app is running, nothing checks them anymore.

</En>
<Ur>

**TypeScript** JavaScript hai **types** ke saath: aise label jo kehte hain "ye number hona chahiye". Ye code likhte waqt ghaltiyan pakar lete hain.

Lekin browsers aur Node.js TypeScript nahi chala sakte. Pehle use **saada JavaScript me tarjuma** kiya jata hai, aur **sari types hata di jati hain**. To app chalte waqt koi unhe check nahi karta.

</Ur>
</Tr>

```text
TypeScript you write                    JavaScript that actually runs
─────────────────────────────           ──────────────────────────────
function price(qty: number,             function price(qty, rate) {
               rate: number): number {    return qty * rate;
  return qty * rate;                    }
}
```

```javascript
// What happens at runtime when an API sends a string instead of a number?
function price(qty, rate) { return qty * rate; }   // the "typed" function after transpiling
console.log(price(3, 500));
console.log(price("3", "500"));
console.log(price("three", 500));
```

```text output
1500
1500
NaN
```

<Happened>
<Tr>
<En>

- With real numbers, the answer is 1500.
- If a user sends `"three"` (text), the types are already gone, so nothing stops it, and the answer is `NaN` ("Not a Number").
- Lesson: always **check data that comes from outside** (forms, APIs) while the app runs, using a validation library like **Zod**.

</En>
<Ur>

- Asal numbers ke saath jawab 1500 hai.
- Agar user `"three"` (text) bhej de, to types pehle hi ja chuki hain, koi nahi rokta, aur jawab `NaN` ("Not a Number") aata hai.
- Sabaq: bahar se aane wala data (forms, APIs) app chalte waqt **zaroor check karein**, **Zod** jaisi validation library se.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Who cleans up the memory?">

<Tr>
<En>

Programs keep creating values in RAM. When they're no longer needed, someone must **free** that memory.

In JavaScript, Python, Java and Go, a **garbage collector** does it automatically: when **nothing points to a value anymore**, it's thrown away.

A **memory leak** happens when something long-lived keeps pointing to data you don't need, so it's never thrown away and memory keeps growing.

</En>
<Ur>

Programs RAM me baar baar values banate rehte hain. Jab un ki zaroorat na rahe, kisi ko wo memory **khaali** karni hoti hai.

JavaScript, Python, Java aur Go me **garbage collector** ye kaam khud karta hai: jab **koi cheez us value ki taraf ishara na kare**, wo phenk di jati hai.

**Memory leak** tab hota hai jab koi lambi umar wali cheez faltu data ki taraf ishara karti rahe, to wo kabhi nahi phenka jata aur memory barhti rehti hai.

</Ur>
</Tr>

```javascript
const cache = [];                                  // lives as long as the program
function handleRequest(i) {
  const big = new Array(10000).fill(i);            // freed after the function… unless kept
  cache.push(big);                                 // LEAK: every request keeps 10,000 values forever
}
for (let i = 0; i < 100; i++) handleRequest(i);
console.log("arrays kept in memory:", cache.length);
```

```text output
arrays kept in memory: 100
```

<Happened>
<Tr>
<En>

- Each "request" creates a big list. Normally it would be thrown away when the function ends.
- But `cache.push(big)` keeps a pointer to it **forever**, so all 100 lists stay in memory.
- On a real server with millions of requests, memory grows until the app is killed (the OOM killer from the last lesson).

</En>
<Ur>

- Har "request" ek bari list banati hai. Aam tor par function khatam hote hi wo phenk di jati.
- Lekin `cache.push(big)` us ki taraf **hamesha** ishara rakhta hai, isliye sari 100 lists memory me reh jati hain.
- Asal server par lakhon requests ke saath memory barhti rehti hai, yahan tak ke app band kar di jati hai (pichle lesson wala OOM killer).

</Ur>
</Tr>
</Happened>

</Step>

<Challenge title="Stop the memory leak">

<Tr>
<En>
Change the leaking example so the cache never holds more than **10** lists. Press **Edit**, change it, and press **Run**. It should print `arrays kept in memory: 10`.
</En>
<Ur>
Leak wale example ko aise badlein ke cache me kabhi **10** se zyada lists na hon. **Edit** dabayen, tabdeeli karein, aur **Run** dabayen. `arrays kept in memory: 10` print hona chahiye.
</Ur>
</Tr>

```javascript
const cache = [];
function handleRequest(i) {
  const big = new Array(10000).fill(i);
  cache.push(big);
}
for (let i = 0; i < 100; i++) handleRequest(i);
console.log("arrays kept in memory:", cache.length);
```

```text output
arrays kept in memory: 100
```

<Hint>
<Tr>
<En>After `push`, if the cache is longer than 10, remove the oldest item with `cache.shift()`.</En>
<Ur>`push` ke baad agar cache 10 se lamba ho, to sab se purana item `cache.shift()` se nikaal dein.</Ur>
</Tr>
</Hint>

<Solution>

```javascript
const cache = [];
function handleRequest(i) {
  const big = new Array(10000).fill(i);
  cache.push(big);
  if (cache.length > 10) cache.shift();   // keep only the newest 10
}
for (let i = 0; i < 100; i++) handleRequest(i);
console.log("arrays kept in memory:", cache.length);
```

```text output
arrays kept in memory: 10
```

</Solution>

<DeepDive title="Parsing: tokens and the syntax tree (AST)">

Most translators first **parse** the text: split it into tokens (keywords, names, numbers), check the grammar, and build a tree structure called an **AST** (abstract syntax tree). Syntax errors are found here. Then the tree is turned into bytecode or machine code.

```text
source:   let total = price * 2;

tokens:   [let] [total] [=] [price] [*] [2] [;]

tree:          VariableDeclaration (total)
                        │
                 BinaryExpression (*)
                  ┌─────┴─────┐
              price            2
```

Linters (ESLint), formatters (Prettier) and bundlers all work on this tree.

</DeepDive>

<DeepDive title="Bytecode and virtual machines (Java, Python, C#)">

Many languages first compile to **bytecode**: compact instructions for an imaginary "virtual machine", not for a real CPU. The VM (a program) then runs the bytecode. Bytecode is portable: the same `.class` or `.pyc` file runs on any OS that has the VM.

Python does this automatically (cached in `__pycache__/*.pyc`). You can look at it:

```python
import dis
def add(a, b):
    return a + b
for ins in dis.get_instructions(add):
    if ins.opname not in ("RESUME",):
        print(ins.opname, ins.argrepr)
```

Output on Python 3.12:

```text
LOAD_FAST a
LOAD_FAST b
BINARY_OP +
RETURN_VALUE
```

These are the steps Python really runs for `return a + b`. Bytecode changes between versions; on Python 3.13 the two loads are merged into `LOAD_FAST_LOAD_FAST a, b`.

</DeepDive>

<DeepDive title="Inside V8: Ignition, TurboFan and de-optimisation">

```text
app.js ──parse──► AST ──► bytecode ──run by Ignition (interpreter)──►
                                         │ function called very often ("hot")
                                         ▼
                           TurboFan compiles optimised machine code ──► runs fast
                                         │ assumptions broken (types changed)
                                         ▼
                                    de-optimise, back to bytecode
```

TurboFan optimises using assumptions, such as "this function always gets numbers". If it suddenly receives strings, V8 **de-optimises** and falls back to slower bytecode. Keeping data shapes consistent helps performance.

</DeepDive>

<DeepDive title="Bundlers and build tools">

Front-end tools (Vite, webpack, esbuild, Turbopack in Next.js) take many source files (TS, JSX, CSS, images, npm packages), transform them, and output a few optimised files. They remove unused code (**tree shaking**) and shorten names (**minification**). The output folder (`dist/`, `.next/`) is what you deploy, not `src/`.

</DeepDive>

<DeepDive title="Hands-on: binaries, scripts and bytecode on your machine">

```bash
# 1. Is this command a compiled binary or a script?
for cmd in ls bash; do
  printf '%-6s → %s\n' "$cmd" "$(file -L "$(command -v "$cmd")" | grep -o 'ELF[^,]*' | head -1)"
done

# 2. A script is just text for an interpreter
printf '#!/usr/bin/env bash\necho "I am interpreted"\n' > s.sh && chmod +x s.sh
head -1 s.sh; ./s.sh

# 3. Python makes bytecode automatically
printf 'def hello():\n    return "hi"\n' > mod.py
python3 -c 'import mod; print(mod.hello())'
ls __pycache__ | sed 's/cpython-[0-9]*/cpython-XY/'

# 4. Which engine is your Node.js using?
node -e 'console.log("V8 engine present:", Boolean(process.versions.v8))'
```

```text output
ls     → ELF 64-bit LSB pie executable
bash   → ELF 64-bit LSB pie executable
#!/usr/bin/env bash
I am interpreted
hi
mod.cpython-XY.pyc

```

</DeepDive>

<DeepDive title="Real world: Node.js vs Go container images">

| | Node.js (TypeScript) | Go |
| --- | --- | --- |
| Build output | `dist/*.js` + `node_modules` | One static binary |
| Runtime needed in image | Node.js | None |
| Typical image | `node:22-alpine`, roughly 150–250 MB with dependencies | `distroless/static`, roughly 10–25 MB |
| Cold start | Slower (load and parse JS, JIT warm-up) | Fast |
| Packages to patch and scan | OS packages + Node + every npm dependency | Mostly the Go dependencies compiled in |

Neither is "better": Node.js gives faster development and a huge ecosystem; Go gives small images and fast startup. A DevOps or security engineer must know **what's inside the image**, because everything inside is attack surface to scan and patch.

</DeepDive>

<DeepDive title="Security lens">

Any time a program turns **data into code**, an attacker can try to supply the data.

- **Code injection:** `eval()`, `new Function()`, `child_process.exec()` with string concatenation and Python's `eval` can run attacker-controlled input. Never build code or shell commands from user input.
- **Supply chain:** your build runs code you didn't write: npm `postinstall` scripts, plugins, GitHub Actions. A compromised package can steal secrets from the build machine.
- **Memory safety:** Microsoft and Google have each reported that roughly 70% of their serious security bugs are memory-safety bugs (buffer overflows, use-after-free) in C and C++ code. Memory-safe languages (Go, Rust, Java, C#, JavaScript) prevent most of this class.
- **Source maps and debug builds** in production can reveal source code, internal paths and comments.
- **Prototype pollution** (JavaScript): merging untrusted JSON into objects can modify `Object.prototype` and change the behaviour of the whole app.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a compiler and an interpreter?">
A compiler translates the whole program into another form (usually machine code) before it runs, producing an executable; errors are caught early and execution is fast. An interpreter executes the source directly, statement by statement, so it starts immediately and is flexible but generally slower. Most modern runtimes combine both, for example bytecode plus a JIT compiler.
</QA>

<QA q="Is JavaScript compiled or interpreted?">
Both. Engines like V8 parse JavaScript into bytecode and interpret it (Ignition), then JIT-compile frequently executed functions into optimised machine code (TurboFan), de-optimising if their type assumptions break. It is best described as a JIT-compiled language.
</QA>

<QA q="What is the difference between Node.js and V8?">
V8 is the JavaScript engine: it parses, compiles and executes JavaScript and manages memory. Node.js is a runtime built around V8 that adds the event loop and asynchronous I/O (via libuv) and APIs for files, networking, processes and crypto. The browser is a different runtime around a JS engine, with the DOM and Web APIs instead.
</QA>

<QA q="Does TypeScript make your app type-safe at runtime?">
No. TypeScript checks types at build time and then removes them; the output is plain JavaScript. Data entering at runtime (HTTP requests, API responses, database rows, environment variables) is not checked. Use runtime validation such as Zod at those boundaries.
</QA>

<QA q="Why are Go container images often much smaller than Node.js images?">
Go compiles to a single static binary that includes its own runtime, so the image can contain little more than that binary. A Node.js app needs the Node runtime plus node_modules at runtime. Smaller images also mean fewer packages to patch and a smaller attack surface.
</QA>

</DeepDive>
