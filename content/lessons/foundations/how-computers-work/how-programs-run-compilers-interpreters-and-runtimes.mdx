<Callout type="tip" title="In one minute">
You write **source code** (text). The CPU only understands **machine code** (binary instructions). Something must translate. A **compiler** translates the whole program **before** it runs into an executable file (C, Go, Rust). An **interpreter** reads and runs the code **line by line** while it runs (Bash, classic Python). Modern **JIT** engines (V8 in Chrome and Node.js, the JVM) do both: start interpreting, then compile the hot parts while running. A **runtime** is everything a program needs around it while running — Node.js is V8 plus file, network and timer features. **TypeScript** is translated to JavaScript first and its types are then thrown away.
</Callout>

## Start from zero

### The language problem

The CPU only understands very simple numbered instructions in binary, like "add register 1 and register 2". Humans cannot productively write programs that way. So we write in **programming languages** — readable text like `if (total > 1000) applyDiscount()` — and a tool translates it.

<Callout type="analogy">
You wrote a speech in Urdu for an audience that only understands Chinese.

- **Compiler:** a translator translates the **whole speech in advance** and hands you a printed Chinese copy. Reading it out is fast; but every change means translating again.
- **Interpreter:** a translator stands next to you and translates **sentence by sentence while you speak**. Easy to change things on the fly, but every sentence takes extra time.
- **JIT:** the live translator notices you repeat certain paragraphs, so he writes those down in Chinese once and just reads them out after that.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Source code** | The text humans write | `app.js`, `main.go` |
| **Machine code** | Binary instructions the CPU executes | `48 89 e5` |
| **Compiler** | Translates source to machine code before running | `gcc`, `go build`, `rustc` |
| **Interpreter** | Runs source code directly, statement by statement | `bash`, `python` |
| **Executable / binary** | A file of machine code the OS can run | `/usr/bin/ls` |
| **Bytecode** | An in-between format, simpler than source, not yet machine code | Python `.pyc`, Java `.class` |
| **JIT** | Just-In-Time compiler: compiles while the program runs | V8, the JVM |
| **Runtime** | The environment a program needs while running | Node.js, the JVM, Python |
| **Transpiler** | Translates one source language into another | TypeScript → JavaScript |

## What is it?

Every language uses one (or a mix) of these strategies:

| Strategy | When translation happens | Examples | Strength | Weakness |
| --- | --- | --- | --- | --- |
| Ahead-of-time (AOT) compiled | Before running, once | C, C++, Go, Rust | Fast, single binary | Must rebuild for each OS/CPU |
| Interpreted | While running, every time | Bash, early Python | Easy, flexible | Slower |
| Bytecode + VM / JIT | Partly before, partly while running | Java, C#, JavaScript (V8), Python | Portable, fast after warm-up | Startup time, needs a runtime |
| Transpiled | Before running, into another language | TypeScript, JSX, Sass | Better language features | Extra build step |

## Why does it matter?

- **Deployment:** a Go binary can be copied to a server and run. A Node.js app needs Node.js installed (or a Docker image with it).
- **Docker image sizes:** compiled languages can use tiny images; runtime languages need the runtime inside.
- **Performance:** knowing where time goes (startup, warm-up, garbage collection) explains benchmark results.
- **Errors:** compile-time errors (caught before running) vs runtime errors (found only when that line runs).
- **Security:** compiled binaries can be reverse-engineered; interpreted code ships as readable source; supply-chain attacks target build tools and dependencies.

## When and where do you use it?

| You are… | You meet |
| --- | --- |
| Writing a React / Next.js app | Transpiling (TS/JSX), bundling, V8 JIT in the browser |
| Running a Node.js / NestJS API | The Node.js runtime, V8 JIT, garbage collection |

## Concepts one by one

### 1. Source code to machine code

<Explain>
<What>
The journey from text you type to instructions the CPU can execute.
</What>
<Why>
The CPU cannot read text. Every programming language needs a translation step somewhere.
</Why>
<When>
Every time a program is built or run.
</When>
<Where>
Every language and platform.
</Where>
<How>
Most translators first **parse** the text: split it into tokens (keywords, names, numbers), check the grammar, and build a tree structure (an **AST — abstract syntax tree**). Syntax errors are found here. Then the tree is turned into bytecode or machine code.
</How>
</Explain>

```text
source:   let total = price * 2;

tokens:   [let] [total] [=] [price] [*] [2] [;]

tree:          VariableDeclaration (total)
                        │
                 BinaryExpression (*)
                  ┌─────┴─────┐
              price            2
```

A syntax error means the parser could not build this tree:

```javascript
try {
  new Function("let total = price * ;");
} catch (error) {
  console.log(error.name + ":", error.message);
}
```

```text output
SyntaxError: Unexpected token ';'
```

### 2. Compiled languages (ahead of time)

<Explain>
<What>
A **compiler** translates the whole program into a machine-code **executable** before it runs.
</What>
<Why>
The work of translating is done once, so the program starts instantly and runs fast. The result is a single file that needs no extra tools on the server.
</Why>
<When>
CLI tools, system software, high-performance services.
</When>
<Where>
Docker, Kubernetes, Terraform and most cloud CLIs are compiled Go programs.
</Where>
<How>
`go build` / `gcc` / `cargo build` produce a binary **for one OS and CPU type**. A Linux x86_64 binary does not run on Windows or on ARM without rebuilding.
</How>
</Explain>

```bash
file /bin/ls | grep -o 'ELF [0-9]*-bit [A-Z]*' | sed 's/$/ executable (machine code)/'
head -c 4 /bin/ls | od -An -c | tr -s ' '
```

```text output
ELF 64-bit LSB executable (machine code)
 177 E L F
```

Every Linux executable starts with the bytes `\177 E L F` — the **ELF** format the Linux kernel knows how to load. Windows uses `.exe` (PE format); macOS uses Mach-O.

### 3. Interpreted languages

<Explain>
<What>
An **interpreter** reads the source code and performs each statement directly, while the program runs.
</What>
<Why>
No build step: edit and run immediately. Great for scripts and quick changes.
</Why>
<When>
Shell scripts, automation, quick tasks.
</When>
<Where>
Bash, sh, and — partly — Python, Ruby, PHP.
</Where>
<How>
Run the file through the interpreter: `bash script.sh`. Errors in a line are found only when that line is reached.
</How>
</Explain>

```bash
cat > demo.sh <<'EOF'
echo "line 1 runs"
echo "line 2 runs"
this-command-does-not-exist
echo "line 4 still runs (the interpreter just continues)"
EOF
bash demo.sh 2>&1 | sed 's/.*: line 3: /ERROR line 3: /'
```

```text output
line 1 runs
line 2 runs
ERROR line 3: this-command-does-not-exist: command not found
line 4 still runs (the interpreter just continues)
```

A compiler would have refused to build such a program at all (for typos it can detect); the interpreter only found the problem when it **reached** line 3.

### 4. Bytecode and virtual machines

<Explain>
<What>
Many languages first compile to **bytecode**: compact instructions for an imaginary "virtual machine" (VM), not for a real CPU. The VM (a program) then runs the bytecode.
</What>
<Why>
Bytecode is portable: the same `.class` or `.pyc` file runs on any OS and CPU that has the VM.
</Why>
<When>
Java, Kotlin, C#, Python.
</When>
<Where>
The JVM (Java), .NET CLR (C#), CPython (Python).
</Where>
<How>
Python compiles your file to bytecode automatically (cached in `__pycache__/*.pyc`) and then interprets the bytecode.
</How>
</Explain>

```python
import dis
def add(a, b):
    return a + b
for ins in dis.get_instructions(add):
    if ins.opname not in ("RESUME",):
        print(ins.opname, ins.argrepr)
```

Output on Python 3.12:

```text
LOAD_FAST a
LOAD_FAST b
BINARY_OP +
RETURN_VALUE
```

These instructions are what Python actually runs for `return a + b`: load `a`, load `b`, add, return. Bytecode changes between Python versions — on Python 3.13 the two loads are merged into one instruction, `LOAD_FAST_LOAD_FAST a, b`.

### 5. JIT compilation: how JavaScript runs (V8)

<Explain>
<What>
A **JIT (Just-In-Time) compiler** compiles code **while the program runs**, focusing on the parts that run most often ("hot" code).
</What>
<Why>
It combines quick startup (start interpreting immediately) with high speed (hot code becomes optimised machine code).
</Why>
<When>
Every time JavaScript runs in Chrome, Edge, Node.js or Deno.
</When>
<Where>
V8 (Chrome, Node.js), SpiderMonkey (Firefox), JavaScriptCore (Safari), the JVM.
</Where>
<How>
V8 parses your code, its **Ignition** interpreter runs bytecode, and its **TurboFan** compiler turns hot functions into optimised machine code. If assumptions break (for example a function suddenly receives strings instead of numbers), V8 **de-optimises** and falls back.
</How>
</Explain>

```text
app.js ──parse──► AST ──► bytecode ──run by Ignition (interpreter)──►
                                         │ function called very often ("hot")
                                         ▼
                           TurboFan compiles optimised machine code ──► runs fast
                                         │ assumptions broken (types changed)
                                         ▼
                                    de-optimise, back to bytecode
```

```javascript
function sum(n) { let s = 0; for (let i = 0; i < n; i++) s += i; return s; }

let t = performance.now(); sum(1e6); const first = performance.now() - t;
for (let k = 0; k < 50; k++) sum(1e6);      // warm up: the function becomes "hot"
t = performance.now(); sum(1e6); const later = performance.now() - t;

console.log(later < first ? "after warm-up the same call is faster (JIT at work)" : "timings vary — run it again");
```

```text output
after warm-up the same call is faster (JIT at work)
```

### 6. Runtimes: what Node.js actually is

<Explain>
<What>
A **runtime** is the environment around your code while it runs: the engine plus built-in libraries and services.
</What>
<Why>
JavaScript itself has no way to read files or open network ports. A runtime adds those abilities. The same language behaves differently in different runtimes.
</Why>
<When>
Running JavaScript in the browser vs on a server.
</When>
<Where>
Browser runtime = V8 + DOM, `fetch`, `localStorage`. **Node.js** = V8 + `fs`, `http`, `process`, the event loop (libuv). Deno and Bun are alternative runtimes.
</Where>
<How>
Check what exists: in Node.js, `typeof window` is "undefined"; in a browser, `typeof require` is "undefined".
</How>
</Explain>

```bash
node -e 'console.log("window in Node:", typeof window); console.log("process in Node:", typeof process); console.log("Node uses V8:", typeof process.versions.v8 === "string")'
```

```text output
window in Node: undefined
process in Node: object
Node uses V8: true
```

| Feature | Browser runtime | Node.js runtime |
| --- | --- | --- |
| Engine | V8 / SpiderMonkey / JavaScriptCore | V8 |
| DOM (`document`, `window`) | Yes | No |
| Files (`fs`) | No | Yes |
| Start a web server | No | Yes (`http`) |
| `fetch`, timers, `console` | Yes | Yes |

### 7. TypeScript: transpiled, then the types disappear

<Explain>
<What>
TypeScript is JavaScript plus **types**. Browsers and Node.js do not run TypeScript directly — it is first **transpiled** to plain JavaScript, and all types are removed.
</What>
<Why>
Types catch mistakes before running (wrong argument types, typos in property names) and make editors smarter. But they do **not** exist at runtime.
</Why>
<When>
Every TypeScript project: React, Next.js, NestJS.
</When>
<Where>
`tsc`, or faster tools like esbuild, SWC and Babel inside Next.js and Vite.
</Where>
<How>
`tsc` checks types and emits `.js`. Because types vanish, data from outside (API requests, JSON, forms) must still be **validated at runtime** (for example with Zod or class-validator).
</How>
</Explain>

```text
TypeScript you write                    JavaScript that actually runs
─────────────────────────────           ──────────────────────────────
function price(qty: number,             function price(qty, rate) {
               rate: number): number {    return qty * rate;
  return qty * rate;                    }
}
```

```javascript
// What happens at runtime when an API sends a string instead of a number?
function price(qty, rate) { return qty * rate; }   // the "typed" function after transpiling
console.log(price(3, 500));
console.log(price("3", "500"));
console.log(price("three", 500));
```

```text output
1500
1500
NaN
```

TypeScript's types could not stop `"three"` arriving from an HTTP request — only runtime validation can.

### 8. Bundlers and build tools

<Explain>
<What>
Tools that take many source files (TS, JSX, CSS, images, npm packages), transform them, and output a few optimised files ready to ship.
</What>
<Why>
Browsers load fewer, smaller files much faster. Bundlers also remove unused code (**tree shaking**) and shorten names (**minification**).
</Why>
<When>
Every front-end build: `npm run build`.
</When>
<Where>
Vite, webpack, esbuild, Turbopack (Next.js), Rollup.
</Where>
<How>
The output goes to a folder like `dist/` or `.next/` — that is what you deploy, not your `src/` folder.
</How>
</Explain>

### 9. Memory management and garbage collection

<Explain>
<What>
Programs create values in RAM all the time. Someone must free that memory when it is no longer needed: either the programmer (C, C++), the compiler's rules (Rust), or a **garbage collector (GC)** that finds unreachable values and frees them automatically (JavaScript, Python, Java, Go, C#).
</What>
<Why>
Forgetting to free memory causes **leaks**; freeing too early causes crashes and security holes (use-after-free).
</Why>
<When>
Constantly, while programs run.
</When>
<Where>
Node.js servers that slowly grow in memory, Java apps with GC pauses.
</Where>
<How>
With a GC, a value is freed when **nothing refers to it any more**. Leaks happen when something long-lived (a global array, a cache, an event listener) keeps a reference.
</How>
</Explain>

```javascript
const cache = [];                                  // lives as long as the program
function handleRequest(i) {
  const big = new Array(10000).fill(i);            // freed after the function… unless kept
  cache.push(big);                                 // LEAK: every request keeps 10,000 values forever
}
for (let i = 0; i < 100; i++) handleRequest(i);
console.log("arrays kept in memory:", cache.length);
```

```text output
arrays kept in memory: 100
```

In a real server, this pattern grows until the process is killed for using too much memory.

## Real-world example

Two teams deploy the same API to Kubernetes:

| | Node.js (TypeScript) | Go |
| --- | --- | --- |
| Build output | `dist/*.js` + `node_modules` | One static binary |
| Runtime needed in image | Node.js | None |
| Typical image | `node:22-alpine`, roughly 150–250 MB with dependencies | `distroless/static`, roughly 10–25 MB |
| Cold start | Slower (load and parse JS, JIT warm-up) | Fast |
| Packages to patch and scan | OS packages + Node + every npm dependency | Mostly just the Go dependencies compiled in |

Neither is "better" — Node.js gives faster development and a huge ecosystem; Go gives small images and fast startup. But a DevOps or security engineer must know **what is inside the image** and why, because everything inside it is attack surface that has to be scanned and patched.

## Common mistakes

- **Trusting TypeScript types for runtime data.** API responses and form input are unchecked at runtime. Validate them.
- **Shipping the TypeScript compiler, dev dependencies and source into production images.** Use multi-stage Docker builds and `npm ci --omit=dev`.
- **Debugging minified code without source maps** — or the opposite: publishing source maps publicly and exposing your source.
- **Assuming "it compiled" means "it works".** Compilers catch syntax and type errors, not logic errors.
- **Expecting browser APIs in Node.js** (`window`, `document`) or Node APIs in the browser (`fs`). They are different runtimes.

## Security lens

<Callout type="security">
Any time a program turns **data into code**, an attacker can try to supply the data.
</Callout>

- **Code injection:** `eval()`, `new Function()`, `child_process.exec()` with string concatenation, Python's `eval`, and template engines that execute expressions can all run attacker-controlled input. Never build code or shell commands from user input.
- **Supply chain:** your build runs code you did not write — npm `postinstall` scripts, Babel/ESLint plugins, GitHub Actions. A compromised package can steal secrets from the build machine. (Covered deeply in DevSecOps → Software Supply Chain Security.)
- **Memory safety:** Microsoft and Google have each reported that roughly 70% of their serious security bugs are memory-safety bugs (buffer overflows, use-after-free) in C and C++ code. Memory-safe languages such as Go, Rust, Java, C# and JavaScript prevent most of this class — which is why governments and large vendors now recommend them for new code.
- **Source maps and debug builds:** shipping them to production can reveal source code, internal paths and comments.
- **Prototype pollution** (JavaScript): because objects are dynamic at runtime, merging untrusted JSON into objects can modify `Object.prototype` and change the behaviour of the whole app.

## Interview questions

<QA q="What is the difference between a compiler and an interpreter?">
A compiler translates the whole program into another form (usually machine code) before it runs, producing an executable; errors are caught early and execution is fast. An interpreter executes the source directly, statement by statement, so it starts immediately and is flexible but generally slower. Most modern runtimes combine both, for example bytecode plus a JIT compiler.
</QA>

<QA q="Is JavaScript compiled or interpreted?">
Both. Engines like V8 parse JavaScript into bytecode and interpret it (Ignition), then JIT-compile frequently executed functions into optimised machine code (TurboFan), de-optimising if their type assumptions break. So it is best described as a JIT-compiled language.
</QA>

<QA q="What is the difference between Node.js and V8?">
V8 is the JavaScript engine: it parses, compiles and executes JavaScript and manages memory. Node.js is a runtime built around V8 that adds the event loop and asynchronous I/O (via libuv) and APIs for files, networking, processes and crypto. The browser is a different runtime around a JS engine, with DOM and Web APIs instead.
</QA>

<QA q="Does TypeScript make your app type-safe at runtime?">
No. TypeScript checks types at build time and then removes them; the output is plain JavaScript. Data entering at runtime — HTTP requests, API responses, database rows, environment variables — is not checked. Use runtime validation (for example zod) at those boundaries.
</QA>

<QA q="Why are Go container images often much smaller than Node.js images?">
Go compiles to a single static binary that includes its own runtime, so the image can contain little more than that binary (scratch or distroless base). A Node.js app needs the Node runtime plus `node_modules` at runtime. Smaller images also mean fewer packages to patch and a smaller attack surface.
</QA>

## Key terms

<Terms>
  <Term name="Machine code">Binary instructions a specific CPU architecture executes directly.</Term>
  <Term name="Compiler">Translates a whole program ahead of time into another form, usually machine code.</Term>
  <Term name="Interpreter">Executes code directly, statement by statement.</Term>
  <Term name="Bytecode">A compact intermediate instruction format executed by a virtual machine.</Term>
  <Term name="JIT">Just-in-time compilation: compiling hot code to machine code while the program runs.</Term>
  <Term name="Transpiler">Translates between high-level languages, such as TypeScript to JavaScript.</Term>
  <Term name="Runtime">The engine and libraries a program needs while it runs, such as Node.js.</Term>
  <Term name="AST">Abstract syntax tree; the parsed structure of source code.</Term>
  <Term name="Garbage collection">Automatic freeing of memory that is no longer reachable.</Term>
  <Term name="Source map">A file that maps compiled output back to the original source for debugging.</Term>
</Terms>
