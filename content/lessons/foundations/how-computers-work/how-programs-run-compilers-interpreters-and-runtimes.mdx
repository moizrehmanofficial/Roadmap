<Callout type="tip" title="In one minute">
A **compiler** translates the whole program into machine code before it runs (C, Go, Rust). An **interpreter** reads and executes code as it goes (classic Python, Bash). Modern languages mix both: JavaScript engines like **V8** interpret first, then **JIT-compile** hot code to machine code. A **runtime** is everything a program needs while running — Node.js is V8 plus libraries for files, network and timers. TypeScript is **transpiled** to JavaScript; the CPU never sees TypeScript.
</Callout>

## What is it?

The CPU understands only **machine code**: binary instructions specific to its architecture (x86-64 or ARM64). Nobody writes machine code by hand. We write in a **programming language**, and something has to translate it.

| Approach | What happens | Examples | Output |
| --- | --- | --- | --- |
| **Ahead-of-time (AOT) compilation** | Translate the whole program to machine code before running | C, C++, Go, Rust | A native executable (binary) |
| **Interpretation** | Read the source and execute it statement by statement | Bash, classic Python (CPython), Ruby | Nothing saved; runs directly |
| **Bytecode + virtual machine** | Compile to an intermediate bytecode, then run it on a VM | Java (JVM), C# (.NET), Python (`.pyc`) | `.class`, `.dll`, `.pyc` files |
| **JIT compilation** | Interpret/bytecode first, then compile hot code to machine code while running | JavaScript (V8), Java (HotSpot), C# | Machine code in memory |
| **Transpilation** | Translate one high-level language into another | TypeScript → JavaScript, JSX → JS, Sass → CSS | Source code in the target language |

A **runtime** (or runtime environment) is the software that must be present while the program runs: the engine plus its standard library and services such as memory management (garbage collection), file and network access, and the event loop.

- **Node.js** = V8 JavaScript engine + libuv (event loop, I/O) + Node's APIs (`fs`, `http`, `crypto`).
- **The browser** = a JS engine (V8, SpiderMonkey, JavaScriptCore) + Web APIs (DOM, `fetch`, `localStorage`).
- **Bun** and **Deno** are alternative JavaScript runtimes.
- **The JVM** is Java's runtime; **.NET** is C#'s.

## Why does it matter?

- **Full-stack:** you need to know why `tsc` errors do not stop JavaScript from running, why the browser and Node.js have different APIs, and what `npm run build` actually produces.
- **DevOps:** a Go app ships as one static binary in a tiny container image; a Node.js app needs the Node runtime and `node_modules` inside the image. That decides image size, startup time and what gets scanned.
- **Cloud:** serverless functions pay for **cold start** time; compiled languages start faster than large interpreted apps.
- **Security:** interpreters can run code from strings (`eval`), which is the root of code-injection vulnerabilities. Compiled binaries in C/C++ can have memory-safety bugs that interpreted and garbage-collected languages largely prevent.

## When and where do you use it?

- Running `npm run build` (Next.js compiles and bundles your TS/JSX into optimised JavaScript).
- Choosing a base image: `node:22-alpine` vs `gcr.io/distroless/static` for a Go binary.
- Debugging `SyntaxError` (caught while parsing) vs `TypeError` (thrown while running).
- Setting `"target"` in `tsconfig.json` to decide which JavaScript version gets emitted.
- Reading a stack trace that points to compiled output — and using **source maps** to map it back to your TypeScript.

## How does it work?

### Step 1: from text to structure

Every approach starts the same way:

```text
source code ──► Lexer ──► tokens ──► Parser ──► AST (abstract syntax tree)
"let x = 2 + 3"     [let][x][=][2][+][3]        VariableDeclaration
                                                  └─ x = BinaryExpression(+, 2, 3)
```

If the code cannot be parsed, you get a **syntax error** before a single line runs. That is why a missing bracket anywhere in a JavaScript file stops the whole file.

### Ahead-of-time compilation (Go, C, Rust)

```text
main.go ──► compiler ──► machine code for linux/amd64 ──► ./app (single binary)
```

- Fast startup and execution; no runtime needs to be installed (Go even bundles its own runtime into the binary).
- One binary per OS and architecture: building for ARM needs `GOARCH=arm64`.
- Many errors (types, missing functions) are caught at compile time.

### Interpretation (Bash)

The interpreter reads a line, executes it, reads the next. If line 40 has a typo, lines 1–39 have already run — which is why a half-finished deployment script is dangerous, and why `set -euo pipefail` exists (covered in "Writing Safe Scripts").

### How JavaScript actually runs: V8

```text
JavaScript ─► parse ─► AST ─► Ignition (bytecode interpreter) ──runs──►
                                    │
                         "this function is hot"
                                    ▼
                         TurboFan (optimising JIT compiler) ─► fast machine code
                                    │
                    assumption broken (types changed)
                                    ▼
                               "deoptimise" back to bytecode
```

V8 starts quickly by interpreting bytecode, watches which functions run often, and compiles those to optimised machine code based on the types it has seen. If a function always gets numbers and suddenly gets a string, V8 throws away the optimised code. This is why consistent types make JavaScript faster.

### TypeScript: transpiled, then thrown away

```text
app.ts ──tsc / esbuild / SWC──► app.js ──► Node.js / browser runs it
           (types checked & removed)
```

Type annotations exist only at build time. At runtime there are no types — so data from an API, a form or a database is **not** checked by TypeScript. That is why runtime validators such as **zod** exist.

### Bundlers and build tools

Front-end builds go further: a bundler (Webpack, Turbopack, Vite/Rollup, esbuild) follows your imports, transpiles TS/JSX, removes unused code (tree-shaking), minifies, and emits a few optimised files. Next.js `next build` does all of this and also pre-renders pages.

### Memory management

- **Manual** (C, C++): the programmer allocates and frees memory. Mistakes cause leaks, crashes and security holes.
- **Garbage collected** (JavaScript, Java, Go, Python, C#): the runtime finds unreachable objects and frees them. Safer, at the cost of occasional GC pauses. You can still leak memory by keeping references you no longer need.
- **Ownership** (Rust): the compiler proves memory safety at compile time, with no garbage collector.

## Hands-on

See parse errors vs runtime errors, and that JS can be compiled from a string at runtime:

```javascript
// 1. A syntax error is caught while PARSING — nothing in the code runs.
try {
  new Function("console.log('line 1'); let = ;");
} catch (e) {
  console.log("Parse failed:", e.name);           // SyntaxError
}

// 2. A runtime error happens only when that line EXECUTES.
const fn = new Function("console.log('line 1 ran'); undefinedThing.call();");
try { fn(); } catch (e) { console.log("Runtime failed:", e.name); } // ReferenceError

// 3. The JIT likes consistent types. Same work, mixed types:
function add(a, b) { return a + b; }
let t = performance.now();
for (let i = 0; i < 3e6; i++) add(i, 1);
console.log("numbers only:", Math.round(performance.now() - t), "ms");

t = performance.now();
for (let i = 0; i < 3e6; i++) add(i % 2 ? i : String(i), 1);
console.log("mixed types: ", Math.round(performance.now() - t), "ms");
```

Switch the playground to **TS** and run this. Then notice: the type error is not caught, because types are removed before running.

```typescript
function double(n: number): number {
  return n * 2;
}
// Your editor would underline this. At runtime, there are no types:
const fromApi: any = "21";
console.log(double(fromApi));   // 42 — JavaScript coerced the string, silently
console.log(double(fromApi as any) === 42);
```

On a terminal, compare what different languages produce:

```bash
# What kind of file is each one?
file "$(which node)"   # ELF 64-bit LSB executable, x86-64 ...  (native binary — the runtime)
file "$(which npm)"    # a symlink to a JavaScript file run BY node
head -n 1 "$(which npm)"   # #!/usr/bin/env node  ← the "shebang": which interpreter runs this

# Transpile TypeScript and look at the output
echo 'const n: number = 1; export {}' > demo.ts
npx -y -p typescript@5 tsc demo.ts && cat demo.js
```

## Real-world example

Two teams deploy the same API to Kubernetes:

| | Node.js (TypeScript) | Go |
| --- | --- | --- |
| Build output | `dist/*.js` + `node_modules` | One static binary |
| Runtime needed in image | Node.js | None |
| Typical image | `node:22-alpine`, roughly 150–250 MB with dependencies | `distroless/static`, roughly 10–25 MB |
| Cold start | Slower (load and parse JS, JIT warm-up) | Fast |
| Packages to patch and scan | OS packages + Node + every npm dependency | Mostly just the Go dependencies compiled in |

Neither is "better" — Node.js gives faster development and a huge ecosystem; Go gives small images and fast startup. But a DevOps or security engineer must know **what is inside the image** and why, because everything inside it is attack surface that has to be scanned and patched.

## Common mistakes

- **Trusting TypeScript types for runtime data.** API responses and form input are unchecked at runtime. Validate them.
- **Shipping the TypeScript compiler, dev dependencies and source into production images.** Use multi-stage Docker builds and `npm ci --omit=dev`.
- **Debugging minified code without source maps** — or the opposite: publishing source maps publicly and exposing your source.
- **Assuming "it compiled" means "it works".** Compilers catch syntax and type errors, not logic errors.
- **Expecting browser APIs in Node.js** (`window`, `document`) or Node APIs in the browser (`fs`). They are different runtimes.

## Security lens

<Callout type="security">
Any time a program turns **data into code**, an attacker can try to supply the data.
</Callout>

- **Code injection:** `eval()`, `new Function()`, `child_process.exec()` with string concatenation, Python's `eval`, and template engines that execute expressions can all run attacker-controlled input. Never build code or shell commands from user input.
- **Supply chain:** your build runs code you did not write — npm `postinstall` scripts, Babel/ESLint plugins, GitHub Actions. A compromised package can steal secrets from the build machine. (Covered deeply in DevSecOps → Software Supply Chain Security.)
- **Memory safety:** Microsoft and Google have each reported that roughly 70% of their serious security bugs are memory-safety bugs (buffer overflows, use-after-free) in C and C++ code. Memory-safe languages such as Go, Rust, Java, C# and JavaScript prevent most of this class — which is why governments and large vendors now recommend them for new code.
- **Source maps and debug builds:** shipping them to production can reveal source code, internal paths and comments.
- **Prototype pollution** (JavaScript): because objects are dynamic at runtime, merging untrusted JSON into objects can modify `Object.prototype` and change the behaviour of the whole app.

## Interview questions

<QA q="What is the difference between a compiler and an interpreter?">
A compiler translates the whole program into another form (usually machine code) before it runs, producing an executable; errors are caught early and execution is fast. An interpreter executes the source directly, statement by statement, so it starts immediately and is flexible but generally slower. Most modern runtimes combine both, for example bytecode plus a JIT compiler.
</QA>

<QA q="Is JavaScript compiled or interpreted?">
Both. Engines like V8 parse JavaScript into bytecode and interpret it (Ignition), then JIT-compile frequently executed functions into optimised machine code (TurboFan), de-optimising if their type assumptions break. So it is best described as a JIT-compiled language.
</QA>

<QA q="What is the difference between Node.js and V8?">
V8 is the JavaScript engine: it parses, compiles and executes JavaScript and manages memory. Node.js is a runtime built around V8 that adds the event loop and asynchronous I/O (via libuv) and APIs for files, networking, processes and crypto. The browser is a different runtime around a JS engine, with DOM and Web APIs instead.
</QA>

<QA q="Does TypeScript make your app type-safe at runtime?">
No. TypeScript checks types at build time and then removes them; the output is plain JavaScript. Data entering at runtime — HTTP requests, API responses, database rows, environment variables — is not checked. Use runtime validation (for example zod) at those boundaries.
</QA>

<QA q="Why are Go container images often much smaller than Node.js images?">
Go compiles to a single static binary that includes its own runtime, so the image can contain little more than that binary (scratch or distroless base). A Node.js app needs the Node runtime plus `node_modules` at runtime. Smaller images also mean fewer packages to patch and a smaller attack surface.
</QA>

## Key terms

<Terms>
  <Term name="Machine code">Binary instructions a specific CPU architecture executes directly.</Term>
  <Term name="Compiler">Translates a whole program ahead of time into another form, usually machine code.</Term>
  <Term name="Interpreter">Executes code directly, statement by statement.</Term>
  <Term name="Bytecode">A compact intermediate instruction format executed by a virtual machine.</Term>
  <Term name="JIT">Just-in-time compilation: compiling hot code to machine code while the program runs.</Term>
  <Term name="Transpiler">Translates between high-level languages, such as TypeScript to JavaScript.</Term>
  <Term name="Runtime">The engine and libraries a program needs while it runs, such as Node.js.</Term>
  <Term name="AST">Abstract syntax tree; the parsed structure of source code.</Term>
  <Term name="Garbage collection">Automatic freeing of memory that is no longer reachable.</Term>
  <Term name="Source map">A file that maps compiled output back to the original source for debugging.</Term>
</Terms>
