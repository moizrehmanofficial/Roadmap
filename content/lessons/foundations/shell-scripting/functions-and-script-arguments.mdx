<Callout type="tip" title="In one minute">
A **function** is a set of commands with a name, so you can run them many times by typing just the name: `greet() { echo "hi $1"; }` then `greet Ali`. Values you pass in are called **arguments** and arrive as `$1`, `$2`… (`$@` = all of them, `$#` = how many). Use `local` for variables inside functions. A function gives data back by **printing** it (`result=$(myfunc)`) and reports success/failure with `return 0` or `return 1`. Scripts receive arguments the same way: `./deploy.sh prod` → `$1` is `prod`.
</Callout>

## Start from zero

### Giving a name to a set of steps

<Callout type="analogy">
A recipe card called **"Make tea"**: boil water, add tea leaves, add milk, add sugar, strain. Once the card exists, you do not repeat all five steps every time you explain it — you just say "make tea". And you can say "make tea **for 3 people**, **less sugar**" — those extra details are the **arguments**.

A function is that recipe card. Its name is "make tea", its steps are the commands, and the details you pass in are the arguments.
</Callout>

Scripts grow quickly. A 200-line script where the same 10 lines appear four times is hard to read and easy to break: you fix a bug in one copy and forget the other three. Functions let you write those 10 lines **once**, give them a clear name, and use them everywhere.

**Arguments** solve a second problem: instead of editing the script each time ("change the folder on line 12"), you pass the value when you run it: `./backup.sh /var/www`.

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Function** | A named group of commands you can run by its name | `greet() { echo "hi"; }` |
| **Define** | Create the function (write its steps) | the `greet() { … }` part |
| **Call** | Run the function by writing its name | `greet` |
| **Argument** | A value you pass in when calling a function or running a script | `Ali` in `greet Ali` |
| **Parameter** | The variable that receives an argument | `$1` |
| **Return value / exit status** | The success (0) or failure number a function ends with | `return 1` |
| **Output** | Text the function prints, which the caller can capture | `echo 42` |
| **Scope** | Where a variable can be seen | `local` = only inside the function |

## What is it?

Two related ideas:

1. **Functions** — named, reusable blocks of commands inside a script. They behave exactly like normal commands: they take arguments, print output and finish with an exit status.
2. **Script arguments** — the words written after a script's name when you run it. `./deploy.sh prod v2.1` passes `prod` and `v2.1` into the script.

Both receive their inputs in the same special variables: `$1`, `$2`, …, `$@`, `$#`.

## Why does it matter?

- **Readability:** a script made of `check_disk`, `backup_database`, `send_alert` reads like a to-do list.
- **No repetition:** fix a bug once, and every place that uses the function gets the fix.
- **Reusable tools:** arguments turn a one-off script into a tool your whole team can use with different values.
- **Professional scripts look like this:** install scripts, Docker entrypoints, CI helpers — all are built from small functions plus argument handling.

## When and where do you use it?

| Situation | What to use |
| --- | --- |
| The same few lines appear twice or more | A function |
| A job has a clear name (log, backup, check, notify) | A function with that name |
| A value changes between runs (folder, environment, version) | A script argument |
| Helpers shared by many scripts | A library file loaded with `source` |

## Concepts one by one

### 1. Defining and calling a function

<Explain>
<What>
Writing a name, `()`, and the commands inside curly braces. After that, typing the name runs those commands.
</What>
<Why>
To write a set of steps once and reuse them by name.
</Why>
<When>
Whenever a block of commands has a clear job or will be used more than once.
</When>
<Where>
Near the top of the script, before the code that uses it.
</Where>
<How>
`name() { commands; }`. Bash reads a script from top to bottom, so the function must be **defined before it is called**.
</How>
</Explain>

```bash
say_hello() {
  echo "Hello!"
  echo "Welcome to DevGuide."
}

say_hello
echo "---"
say_hello
```

```text output
Hello!
Welcome to DevGuide.
---
Hello!
Welcome to DevGuide.
```

Line by line:

- `say_hello() {` — start defining a function named `say_hello`. Nothing runs yet.
- The two `echo` lines — the steps inside the function.
- `}` — end of the definition.
- `say_hello` — **call** it: both lines print. Calling it again prints them again.

### 2. Passing arguments to a function

<Explain>
<What>
Extra words written after the function name when calling it. Inside the function they are available as `$1` (first), `$2` (second), and so on.
</What>
<Why>
So one function can work with different values — greet different people, back up different folders.
</Why>
<When>
Whenever the function's job depends on some input.
</When>
<Where>
Almost every real function: `create_user alice`, `backup /var/www`, `log "message"`.
</Where>
<How>
Call: `greet Ali Lahore`. Inside: `$1` is `Ali`, `$2` is `Lahore`, `$#` is `2`. Give them readable names at the top: `local name="$1"`.
</How>
</Explain>

```bash
greet() {
  local name="$1"
  local city="$2"
  echo "Hello $name from $city"
}

greet Ali Lahore
greet Sara Karachi
greet "Usman Khan" Islamabad
```

```text output
Hello Ali from Lahore
Hello Sara from Karachi
Hello Usman Khan from Islamabad
```

- `greet Ali Lahore` — two arguments: `$1` = `Ali`, `$2` = `Lahore`.
- `"Usman Khan"` — quotes keep the two words together as **one** argument.
- `local name="$1"` — copy `$1` into a variable with a meaningful name.

### 3. Default values for missing arguments

<Explain>
<What>
A fallback value used when an argument was not given.
</What>
<Why>
So the function still works when the caller skips an optional value.
</Why>
<When>
For optional settings: a port, a group, a retry count.
</When>
<Where>
Any function or script with optional inputs.
</Where>
<How>
`${1:-default}` means "use `$1`, or `default` if `$1` is empty or missing".
</How>
</Explain>

```bash
create_user() {
  local name="$1"
  local group="${2:-users}"
  echo "Creating $name in group $group"
}

create_user alice admin
create_user bob
```

```text output
Creating alice in group admin
Creating bob in group users
```

### 4. `local` — keeping variables inside the function

<Explain>
<What>
A keyword that makes a variable exist **only inside** the function.
</What>
<Why>
In Bash, variables are **global by default** — even ones created inside a function. Without `local`, a function can silently overwrite a variable the rest of the script relies on.
</Why>
<When>
For every variable you create inside a function, unless you deliberately want to change a global one.
</When>
<Where>
All functions. Loop counters like `i` are the most common victims.
</Where>
<How>
`local name="value"` instead of `name="value"`.
</How>
</Explain>

<Callout type="analogy">
Writing on the **classroom whiteboard** (global) versus in **your own notebook** (local). If you write on the whiteboard, you might erase something another student needed. Your notebook affects nobody else.
</Callout>

```bash
counter=10

change_global() { counter=99; }
change_local()  { local counter=99; }

change_local
echo "After change_local:  counter = $counter"
change_global
echo "After change_global: counter = $counter"
```

```text output
After change_local:  counter = 10
After change_global: counter = 99
```

- `change_local` creates its **own** `counter`; the outer one stays 10.
- `change_global` changes the outer `counter` — usually a bug.

### 5. Getting results back: print the data, return the status

<Explain>
<What>
A function has two ways to give something back: the **text it prints** (data), and its **exit status** (0 = success, 1–255 = failure).
</What>
<Why>
Bash's `return` can only give a small number (0–255) — it is meant for success/failure, not for data like text or big numbers.
</Why>
<When>
Print when the caller needs a value (an IP, a total, a filename). Use the status when the caller only needs a yes/no.
</When>
<Where>
Helpers like `get_ip`, `latest_backup`, and checks like `is_running`, `file_is_valid`.
</Where>
<How>
Data: `echo` the result inside the function and capture it with `result=$(my_function)`. Yes/no: `return 0` or `return 1` (or just let the last command's status be the result) and use the function in `if`.
</How>
</Explain>

```bash
square() {
  echo $(( $1 * $1 ))         # print the result
}

is_even() {
  (( $1 % 2 == 0 ))            # status 0 if even, 1 if odd
}

result=$(square 12)
echo "12 squared is $result"

for n in 7 10; do
  if is_even "$n"; then
    echo "$n is even"
  else
    echo "$n is odd"
  fi
done
```

```text output
12 squared is 144
7 is odd
10 is even
```

- `$(square 12)` — runs the function and captures what it printed (`144`) into `result`.
- `is_even` prints nothing; its last command's exit status is the answer, so it works directly with `if`.

<Callout type="warning" title="Messages inside value-returning functions go to stderr">
If a function prints a progress message **and** its result, both get captured: `result` becomes `"working… 42"`. Send messages to the error stream with `>&2` so only the real result is captured: `echo "working…" >&2`.
</Callout>

### 6. Arguments of the script itself

<Explain>
<What>
When you run `./deploy.sh prod v2.1`, Bash stores the words after the script name in `$1`, `$2`, … for the whole script. `$0` is the script's own name.
</What>
<Why>
So one script can be used in many situations without editing its code.
</Why>
<When>
For anything that differs between runs: environment, folder, version, username.
</When>
<Where>
Deploy scripts, backup scripts, tools you share with your team.
</Where>
<How>
Read them like function arguments. Inside a function, `$1` means the **function's** first argument — pass the script's arguments in with `main "$@"`.
</How>
</Explain>

| Variable | Meaning | For `./deploy.sh prod v2.1 --dry-run` |
| --- | --- | --- |
| `$0` | How the script was called | `./deploy.sh` |
| `$1` | First argument | `prod` |
| `$2` | Second argument | `v2.1` |
| `$3` | Third argument | `--dry-run` |
| `$#` | How many arguments | `3` |
| `"$@"` | All arguments, each kept separate | `"prod" "v2.1" "--dry-run"` |
| `"$*"` | All arguments joined into one text | `"prod v2.1 --dry-run"` |

```bash
cat > show-args.sh <<'EOF'
#!/usr/bin/env bash
echo "Script name: $0"
echo "Number of arguments: $#"
echo "First: $1"
echo "Second: $2"
echo "All: $*"
EOF
chmod +x show-args.sh
./show-args.sh prod v2.1 --dry-run
```

```text output
Script name: ./show-args.sh
Number of arguments: 3
First: prod
Second: v2.1
All: prod v2.1 --dry-run
```

- `cat > show-args.sh <<'EOF' … EOF` — writes the lines between into a new file (a "here document", covered in the next lessons).
- `chmod +x` — make it runnable.
- `./show-args.sh prod v2.1 --dry-run` — run it with three arguments.

For arguments 10 and above, use braces: `${10}`.

### 7. `"$@"` — passing all arguments along unchanged

<Explain>
<What>
`"$@"` (with the quotes) expands to every argument, each one kept exactly as it was given — spaces included.
</What>
<Why>
When a function or script forwards its arguments to another command, they must arrive unchanged. Unquoted `$@` or `"$*"` break arguments that contain spaces.
</Why>
<When>
Calling `main "$@"`, writing wrapper functions, looping over all arguments.
</When>
<Where>
Almost every professional script ends with `main "$@"`.
</Where>
<How>
Always write it with double quotes: `"$@"`.
</How>
</Explain>

```bash
count_args() { echo "received $# argument(s): $(printf '<%s> ' "$@")"; }

with_quoted_at()   { count_args "$@"; }
with_unquoted_at() { count_args $@; }
with_star()        { count_args "$*"; }

with_quoted_at   "my file.txt" other
with_unquoted_at "my file.txt" other
with_star        "my file.txt" other
```

```text output
received 2 argument(s): <my file.txt> <other> 
received 3 argument(s): <my> <file.txt> <other> 
received 1 argument(s): <my file.txt other> 
```

Only `"$@"` keeps the two original arguments exactly.

### 8. `shift` — taking arguments one at a time

<Explain>
<What>
A command that removes the first argument and moves all the others one place to the left: `$2` becomes `$1`, `$3` becomes `$2`, and `$#` goes down by one.
</What>
<Why>
To handle arguments one by one, especially when processing options like `--dry-run` in a loop.
</Why>
<When>
After you have used `$1` and want to move on to the next argument.
</When>
<Where>
Option-parsing loops, scripts that take a fixed first argument followed by a list.
</Where>
<How>
`shift` removes one; `shift 2` removes two.
</How>
</Explain>

<Callout type="analogy">
A queue at a bank counter. When the first person is served, they leave (`shift`), and everyone moves one place forward — the second person is now first.
</Callout>

```bash
demo() {
  echo "Start:  \$1=$1  (count $#)"
  shift
  echo "After shift: \$1=$1  (count $#)"
  shift
  echo "After shift: \$1=$1  (count $#)"
}
demo apple banana cherry
```

```text output
Start:  $1=apple  (count 3)
After shift: $1=banana  (count 2)
After shift: $1=cherry  (count 1)
```

### 9. Checking arguments and showing a usage message

<Explain>
<What>
Checks at the top of a script that make sure the right number and kind of arguments were given, with a short **usage** message explaining how to run the script correctly.
</What>
<Why>
Without checks, a missing argument turns into an empty variable — and commands like `rm -rf "$dir/"*` with an empty `dir` can be disastrous.
</Why>
<When>
In every script that takes arguments.
</When>
<Where>
The first lines of the script, before any real work.
</Where>
<How>
Count with `(( $# == 2 ))`, validate values with patterns, and on failure print the usage to stderr and `exit 2` (the usual code for "wrong usage").
</How>
</Explain>

```bash
cat > deploy.sh <<'EOF'
#!/usr/bin/env bash
usage() {
  echo "Usage: $(basename "$0") <dev|staging|prod> <version>" >&2
  exit 2
}

(( $# == 2 )) || usage
env="$1"
version="$2"
[[ $env =~ ^(dev|staging|prod)$ ]] || { echo "Unknown environment: $env" >&2; usage; }

echo "Deploying version $version to $env"
EOF
chmod +x deploy.sh

./deploy.sh staging v1.4.0
./deploy.sh production v1.4.0; echo "exit code: $?"
./deploy.sh; echo "exit code: $?"
```

```text output
Deploying version v1.4.0 to staging
Unknown environment: production
Usage: deploy.sh <dev|staging|prod> <version>
exit code: 2
Usage: deploy.sh <dev|staging|prod> <version>
exit code: 2
```

- `usage()` — a small function that prints how to use the script and stops it.
- `(( $# == 2 )) || usage` — "exactly two arguments, otherwise show usage".
- `basename "$0"` — the script's file name without the folder part.

A shorter way for one required argument: `name="${1:?Usage: $0 <name>}"` stops the script with that message when `$1` is missing.

### 10. The `main` function pattern

<Explain>
<What>
Putting the script's main steps inside a function called `main`, and calling `main "$@"` on the very last line.
</What>
<Why>
All helper functions are defined before anything runs, the flow is easy to read top to bottom, and the script's arguments are passed in cleanly.
</Why>
<When>
For any script longer than about 20 lines.
</When>
<Where>
Most professional Bash scripts and tools.
</Where>
<How>
Helpers first, `main()` next, `main "$@"` last.
</How>
</Explain>

```bash
#!/usr/bin/env bash
set -euo pipefail

log() { echo "[$(date +%T)] $*" >&2; }
die() { log "ERROR: $*"; exit 1; }

backup() {
  local source_dir="$1" destination="$2"
  [[ -d $source_dir ]] || die "folder $source_dir not found"
  tar -czf "$destination" -C "$source_dir" .
  log "saved $destination"
}

main() {
  local source_dir="${1:?usage: $0 <folder>}"
  backup "$source_dir" "/tmp/backup-$(date +%F).tgz"
}

main "$@"
```

- `log` and `die` — tiny helpers used everywhere (print a timestamped message; print an error and stop).
- `backup` — one job, two arguments.
- `main "$@"` — start the script, giving `main` all the script's arguments.

### 11. Sharing functions between scripts: `source`

<Explain>
<What>
`source file` (or `. file`) runs another file **inside the current shell**, so the functions and variables it defines become available.
</What>
<Why>
To keep common helpers (logging, error handling, colours) in one library file used by many scripts.
</Why>
<When>
When two or more scripts need the same functions.
</When>
<Where>
A `lib/` folder in a repository of scripts; also how `~/.bashrc` and `.env` files are loaded.
</Where>
<How>
`source "$(dirname "$0")/lib/common.sh"`. Running the library with `./lib/common.sh` would not work — it would run in a separate process and its functions would vanish.
</How>
</Explain>

```bash
mkdir -p lib
echo 'log() { echo "[LOG] $*"; }' > lib/common.sh

source lib/common.sh
log "This function came from lib/common.sh"
```

```text output
[LOG] This function came from lib/common.sh
```

## Hands-on

```bash
mkdir -p ~/func-lab && cd ~/func-lab

# define and call
greet() { echo "hello, ${1:-stranger}"; }
greet Ali; greet

# globals vs local
counter=10; bump() { counter=99; }; bump; echo "after bump: $counter"
counter=10; safe() { local counter=99; }; safe; echo "after safe: $counter"

# return status vs printed data
is_even() { (( $1 % 2 == 0 )); }
for n in 3 8; do if is_even "$n"; then echo "$n even"; else echo "$n odd"; fi; done
square() { echo $(( $1 * $1 )); }
result="$(square 12)"; echo "12² = $result"

# logs must go to stderr when you capture output
bad()  { echo "working…"; echo 42; }
good() { echo "working…" >&2; echo 42; }
echo "bad captured:  [$(bad)]"
echo "good captured: [$(good 2>/dev/null)]"

# required argument shortcut
need() { local name="${1:?name is required}"; echo "ok $name"; }
need Moiz
( need ) 2>&1 | sed 's/.*: //'; echo "exit of need with no argument: ${PIPESTATUS[0]}"

cd ~ && rm -rf ~/func-lab
```

```text output
hello, Ali
hello, stranger
after bump: 99
after safe: 10
3 odd
8 even
12² = 144
bad captured:  [working…
42]
good captured: [42]
ok Moiz
name is required
exit of need with no argument: 1
```

## Real-world example

A server bootstrap helper that many teams keep in a repo — small functions, a `main`, and arguments:

```bash
#!/usr/bin/env bash
# bootstrap.sh <username> [ssh-public-key-file]
set -euo pipefail

log() { printf '\e[32m[+]\e[0m %s\n' "$*" >&2; }
die() { printf '\e[31m[x]\e[0m %s\n' "$*" >&2; exit 1; }

require_root() { (( EUID == 0 )) || die "run as root (sudo $0 …)"; }

install_packages() {
  log "installing base packages"
  apt-get update -qq
  apt-get install -y -qq "$@" > /dev/null
}

create_admin() {
  local user="$1" keyfile="$2"
  if id "$user" &> /dev/null; then
    log "user $user already exists"
  else
    useradd -m -s /bin/bash -G sudo "$user"
    log "created $user"
  fi
  install -d -m 700 -o "$user" -g "$user" "/home/$user/.ssh"
  install -m 600 -o "$user" -g "$user" "$keyfile" "/home/$user/.ssh/authorized_keys"
}

main() {
  local user="${1:?usage: $0 <username> [pubkey-file]}"
  local key="${2:-/root/.ssh/authorized_keys}"
  [[ -r $key ]] || die "cannot read key file $key"
  require_root
  install_packages curl git ufw fail2ban
  create_admin "$user" "$key"
  log "done — log in as $user with your SSH key"
}

main "$@"
```

Each function does one job and can be re-run safely (`id` check before `useradd`). That property — **idempotency** — is what tools like Ansible formalise later.

## Common mistakes

- **Calling a function before defining it** → `command not found`.
- **Forgetting `local`** — a helper silently overwrites a variable the caller relies on (`i` in nested loops is the classic).
- **Using `return` for data** (`return "$total"`) — limited to 0–255 and not text. Print instead.
- **Logging to stdout inside a function whose output is captured** — the log text ends up in the variable.
- **`$@` without quotes** — arguments with spaces split apart.
- **Expecting `$1` inside a function to be the script's first argument** — it is the function's. Pass it in: `main "$@"`.
- **Running a library with `./lib.sh` instead of `source lib.sh`.**
- **No usage message** — users (including future you) guess and get it wrong.

## Security lens

<Callout type="security">
Arguments are user input. Every value that reaches `rm`, `ssh`, a SQL query, a URL or a file path must be validated first.
</Callout>

- **Allow-list arguments** with `case` or anchored regex. Reject everything else with a non-zero exit.
- **Option injection:** a "filename" like `--checkpoint-action=exec=sh` passed to `tar` becomes an option. Put `--` before user-supplied paths: `tar -czf out.tgz -- "$path"`.
- **Never pass arguments through `eval`** or build commands as strings — use arrays and `"$@"`.
- **`source` executes code:** only source files you control, with safe permissions; sourcing a world-writable file is code execution for anyone who can edit it.
- **Secrets as arguments are visible** to every user via `ps` and end up in shell history. Pass secrets through environment variables, files with mode 600, or stdin.

## Interview questions

<QA q="What is the difference between $@, $* and their quoted forms?">
Unquoted, both expand to all arguments and are then re-split on whitespace. Quoted, "$@" expands to every argument as a separate word, preserving spaces inside each one, while "$*" joins all arguments into a single word separated by the first character of IFS. "$@" is the right choice for passing arguments on to another command.
</QA>

<QA q="How do you return a value from a Bash function?">
return only sets the exit status, a number from 0 to 255, used for success or failure. To return data, the function prints it to stdout and the caller captures it with command substitution, such as result=$(myfunc). Diagnostic messages should go to stderr so they are not captured.
</QA>

<QA q="Why use local in functions?">
Bash variables are global by default, even when assigned inside a function, so a helper can accidentally overwrite a caller's variable. local limits a variable to the function (and functions it calls), which avoids these hidden side effects.
</QA>

<QA q="What does shift do?">
shift removes the first positional parameter and moves the rest down, so $2 becomes $1 and $# decreases by one; shift n removes n parameters. It is used to consume arguments in a loop when parsing options manually.
</QA>

<QA q="What is the difference between running a script and sourcing it?">
Running ./script.sh starts a new child process; variables, functions and directory changes it makes disappear when it exits. source script.sh (or . script.sh) runs the commands in the current shell, so its functions and variables remain available. Libraries of functions and environment files are sourced.
</QA>
