<BigIdea>
<Tr>
<En>
A **function** is a set of commands with a **name**: write the steps once, then run them anywhere by typing the name. Values you pass in (**arguments**) arrive as `$1`, `$2`… Scripts receive their arguments the **same way**: in `./deploy.sh prod`, `$1` is `prod`. Functions keep scripts short and readable; arguments make one script useful in many situations.
</En>
<Ur>
**Function** commands ka ek majmua hai jis ka **naam** hota hai: steps ek dafa likho, phir naam likh kar kahin bhi chalao. Jo values aap andar bhejte hain (**arguments**), wo `$1`, `$2`… me aati hain. Scripts bhi apne arguments **isi tarah** lete hain: `./deploy.sh prod` me `$1` `prod` hai. Functions scripts ko chhota aur parhne layaq rakhte hain; arguments ek script ko kai halaat me kaam ka bana dete hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Two related ideas:

1. **Functions**: named, reusable blocks of commands inside a script. They act exactly like normal commands: take arguments, print output, finish with an exit status.
2. **Script arguments**: the words after the script's name when you run it. `./deploy.sh prod v2.1` passes `prod` and `v2.1` in.

Both receive input in the same special variables: `$1`, `$2`, `$@`, `$#`.

</En>
<Ur>

Do mile julay khayal:

1. **Functions**: script ke andar naam wale, dobara istemal hone wale commands ke blocks. Ye bilkul aam commands jaise kaam karte hain: arguments lete hain, output chhaapte hain, exit status ke saath khatam hote hain.
2. **Script arguments**: script chalate waqt us ke naam ke baad wale alfaz. `./deploy.sh prod v2.1` `prod` aur `v2.1` andar bhejta hai.

Dono ek hi khaas variables me input lete hain: `$1`, `$2`, `$@`, `$#`.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Readable:** a script made of `check_disk`, `backup_database`, `send_alert` reads like a to-do list.
- **No repetition:** fix a bug once, and every place using the function gets the fix.
- **Reusable tools:** arguments turn a one-off script into a tool your whole team runs with different values.
- **Professional scripts look like this:** install scripts, Docker entrypoints and CI helpers are all small functions plus argument handling.

</En>
<Ur>

- **Parhne me aasaan:** `check_disk`, `backup_database`, `send_alert` se bana script kaamon ki list jaisa parhta hai.
- **Takraar nahi:** bug ek dafa theek karo, aur function istemal karne wali har jagah theek ho jati hai.
- **Dobara kaam aane wale tools:** arguments ek dafa ke script ko aisa tool bana dete hain jo poori team mukhtalif values ke saath chalaye.
- **Professional scripts aise hi hote hain:** install scripts, Docker entrypoints aur CI helpers sab chhote functions aur arguments ka kaam hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Use |
| --- | --- |
| The same few lines appear twice or more | A function |
| A job has a clear name (log, backup, check, notify) | A function with that name |
| A value changes between runs (folder, environment, version) | A script argument |
| Helpers shared by many scripts | A library file loaded with `source` |

</En>
<Ur>

| Soorat-e-haal | Istemal |
| --- | --- |
| Wahi chand lines do ya zyada dafa aati hain | Function |
| Kaam ka wazeh naam hai (log, backup, check, notify) | Usi naam ka function |
| Koi value har dafa badalti hai (folder, environment, version) | Script argument |
| Kai scripts me istemal hone wale helpers | `source` se load hone wali library file |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
name() { commands; }     # define
name arg1 arg2           # call: $1=arg1, $2=arg2
result=$(name)           # capture what it prints
```

</En>
<Ur>

```text
name() { commands; }     # banana
name arg1 arg2           # chalana: $1=arg1, $2=arg2
result=$(name)           # jo chhaape wo pakarna
```

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

A recipe card called **"Make tea"**: boil water, add tea leaves, add milk, add sugar, strain. Once the card exists, you don't repeat all five steps every time; you just say "make tea". And you can say "make tea **for 3 people**, **less sugar**". Those extra details are the **arguments**.

A function is that recipe card: its name is "make tea", its steps are the commands, and the details you pass in are the arguments.

</En>
<Ur>

**"Chai banao"** naam ka recipe card: paani ubalo, patti daalo, doodh daalo, cheeni daalo, chhaano. Card ban jaye to har dafa paancho steps nahi dohrane; bas "chai banao" kehna hai. Aur aap keh sakte hain "chai banao **3 logon ke liye**, **kam cheeni**". Ye izafi tafseelat **arguments** hain.

Function wahi recipe card hai: naam "chai banao", steps commands, aur jo tafseelat aap dete hain wo arguments.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Function** | A named group of commands you run by its name | `greet() { echo "hi"; }` |
| **Define** | Create the function (write its steps) | the `greet() { … }` part |
| **Call** | Run the function by writing its name | `greet` |
| **Argument** | A value passed in when calling a function or running a script | `Sam` in `greet Sam` |
| **Parameter** | The variable that receives an argument | `$1` |
| **Exit status** | The success (0) or failure number a function ends with | `return 1` |
| **Output** | Text the function prints, which the caller can capture | `echo 42` |
| **Scope** | Where a variable can be seen | `local` = only inside the function |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Function** | Commands ka naam wala group jo naam se chalta hai | `greet() { echo "hi"; }` |
| **Define** | Function banana (us ke steps likhna) | `greet() { … }` wala hissa |
| **Call** | Naam likh kar function chalana | `greet` |
| **Argument** | Function call ya script chalate waqt di gayi value | `greet Sam` me `Sam` |
| **Parameter** | Wo variable jo argument leta hai | `$1` |
| **Exit status** | Kamyabi (0) ya nakami ka number jis par function khatam hota hai | `return 1` |
| **Output** | Function ka chhapa hua text, jo bulane wala pakar sakta hai | `echo 42` |
| **Scope** | Variable kahan nazar aata hai | `local` = sirf function ke andar |

## Learn it step by step

<Walkthrough>

<Step title="Define a function, then call it">

<Tr>
<En>

`name() { commands; }`. Nothing runs when you define it; typing the name runs it. Bash reads a script top to bottom, so a function must be **defined before it is called**.

</En>
<Ur>

`name() { commands; }`. Banate waqt kuch nahi chalta; naam likhne se chalta hai. Bash script ooper se neeche parhta hai, isliye function **call se pehle bana hona** chahiye.

</Ur>
</Tr>

```bash
say_hello() {
  echo "Hello!"
  echo "Welcome to DevGuide."
}

say_hello
echo "---"
say_hello
```

```text output
Hello!
Welcome to DevGuide.
---
Hello!
Welcome to DevGuide.
```

<Happened>
<Tr>
<En>The first four lines only **created** `say_hello`. Each `say_hello` line then **ran** both `echo`s. Two calls, so the two lines printed twice.</En>
<Ur>Pehli chaar lines ne sirf `say_hello` **banaya**. Phir har `say_hello` line ne dono `echo` **chalaye**. Do calls, isliye do lines do dafa chhapi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Pass arguments: $1, $2">

<Tr>
<En>

Call `greet Sam Chicago`, and inside the function `$1` is `Sam`, `$2` is `Chicago` and `$#` is 2. Give them readable names at the top with `local name="$1"`. Quotes keep words together as **one** argument: `"Daniel Brown"`.

</En>
<Ur>

`greet Sam Chicago` call karein, to function ke andar `$1` `Sam`, `$2` `Chicago` aur `$#` 2 hai. Ooper `local name="$1"` se inhe parhne layaq naam dein. Quotes alfaz ko **ek** argument rakhte hain: `"Daniel Brown"`.

</Ur>
</Tr>

```bash
greet() {
  local name="$1"
  local city="$2"
  echo "Hello $name from $city"
}

greet Sam Chicago
greet Emma Houston
greet "Daniel Brown" Seattle
```

```text output
Hello Sam from Chicago
Hello Emma from Houston
Hello Daniel Brown from Seattle
```

</Step>

<Step title="Default values for missing arguments">

<Tr>
<En>

`${2:-users}` means "use `$2`, or `users` if it's empty or missing". Perfect for optional settings like a group, a port or a retry count.

</En>
<Ur>

`${2:-users}` ka matlab "`$2` lo, ya agar khaali ya ghayab ho to `users`". Group, port ya retry count jaisi ikhtiyari settings ke liye behtareen.

</Ur>
</Tr>

```bash
create_user() {
  local name="$1"
  local group="${2:-users}"
  echo "Creating $name in group $group"
}

create_user alice admin
create_user bob
```

```text output
Creating alice in group admin
Creating bob in group users
```

</Step>

<Step title="local: keep variables inside the function">

<Tr>
<En>

In Bash, variables are **global by default**, even ones created inside a function. Without `local`, a function can silently overwrite a variable the rest of the script needs.

Think of the **classroom whiteboard** (global) versus **your own notebook** (local). Writing on the whiteboard might erase something another student needed; your notebook affects nobody.

</En>
<Ur>

Bash me variables **pehle se global** hote hain, function ke andar bane hue bhi. `local` ke baghair function chupke se aisa variable badal sakta hai jo baqi script ko chahiye.

**Class ka whiteboard** (global) bamuqabla **apni notebook** (local) sochein. Whiteboard par likhna kisi aur student ki zaroori cheez mita sakta hai; aap ki notebook kisi ko mutasir nahi karti.

</Ur>
</Tr>

```bash
counter=10

change_global() { counter=99; }
change_local()  { local counter=99; }

change_local
echo "After change_local:  counter = $counter"
change_global
echo "After change_global: counter = $counter"
```

```text output
After change_local:  counter = 10
After change_global: counter = 99
```

<Happened>
<Tr>
<En>`change_local` made its **own** `counter`, so the outer one stayed 10. `change_global` changed the outer one to 99, which is usually a bug.</En>
<Ur>`change_local` ne apna **alag** `counter` banaya, isliye bahar wala 10 raha. `change_global` ne bahar wala 99 kar diya, jo aam tor par bug hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Getting results back: print data, return status">

<Tr>
<En>

A function gives back two things:

- **Data**: whatever it prints. Capture it with `result=$(my_function)`.
- **Yes/no**: its exit status. `return 0` (yes) or `return 1` (no), or just the last command's status. Use it directly in `if`.

`return` can only give a number 0–255, so **never** use it for text or totals.

</En>
<Ur>

Function do cheezen wapas deta hai:

- **Data**: jo kuch wo chhaapta hai. `result=$(my_function)` se pakrein.
- **Haan/nahi**: us ka exit status. `return 0` (haan) ya `return 1` (nahi), ya bas aakhri command ka status. Ise seedha `if` me istemal karein.

`return` sirf 0–255 ka number de sakta hai, isliye ise text ya totals ke liye **kabhi** istemal na karein.

</Ur>
</Tr>

```bash
square() {
  echo $(( $1 * $1 ))         # print the result
}

is_even() {
  (( $1 % 2 == 0 ))            # status 0 if even, 1 if odd
}

result=$(square 12)
echo "12 squared is $result"

for n in 7 10; do
  if is_even "$n"; then
    echo "$n is even"
  else
    echo "$n is odd"
  fi
done
```

```text output
12 squared is 144
7 is odd
10 is even
```

<Callout type="warning" title="Messages inside value functions go to stderr">
<Tr>
<En>If a function prints a progress message **and** its result, both get captured: `result` becomes "working… 42". Send messages to the error stream with `>&2` so only the real result is captured.</En>
<Ur>Agar function progress message **aur** apna result dono chhaape, to dono pakre jate hain: `result` "working… 42" ban jata hai. Messages `>&2` se error stream me bhejein taa ke sirf asli result pakra jaye.</Ur>
</Tr>
</Callout>

</Step>

<Step title="The script's own arguments">

<Tr>
<En>

Run `./deploy.sh prod v2.1 --dry-run` and Bash fills these for the whole script:

| Variable | Meaning | Value here |
| --- | --- | --- |
| `$0` | How the script was called | `./deploy.sh` |
| `$1` `$2` `$3` | 1st, 2nd, 3rd argument | `prod`, `v2.1`, `--dry-run` |
| `$#` | How many arguments | `3` |
| `"$@"` | All arguments, each kept separate | `"prod" "v2.1" "--dry-run"` |
| `"$*"` | All arguments joined into one text | `"prod v2.1 --dry-run"` |

For argument 10 and above, use braces: `${10}`.

</En>
<Ur>

`./deploy.sh prod v2.1 --dry-run` chalayen to Bash poore script ke liye ye bharta hai:

| Variable | Matlab | Yahan value |
| --- | --- | --- |
| `$0` | Script kaise bulaya gaya | `./deploy.sh` |
| `$1` `$2` `$3` | 1st, 2nd, 3rd argument | `prod`, `v2.1`, `--dry-run` |
| `$#` | Kitne arguments | `3` |
| `"$@"` | Saare arguments, har ek alag | `"prod" "v2.1" "--dry-run"` |
| `"$*"` | Saare arguments ek text me jure | `"prod v2.1 --dry-run"` |

10 aur us se ooper ke argument ke liye braces: `${10}`.

</Ur>
</Tr>

```bash
cat > show-args.sh <<'EOF'
#!/usr/bin/env bash
echo "Script name: $0"
echo "Number of arguments: $#"
echo "First: $1"
echo "Second: $2"
echo "All: $*"
EOF
chmod +x show-args.sh
./show-args.sh prod v2.1 --dry-run
```

```text output
Script name: ./show-args.sh
Number of arguments: 3
First: prod
Second: v2.1
All: prod v2.1 --dry-run
```

<Happened>
<Tr>
<En>`cat > show-args.sh <<'EOF' … EOF` wrote the lines in between into a new file (a "here document", covered soon). `chmod +x` made it runnable, and we ran it with three arguments.</En>
<Ur>`cat > show-args.sh <<'EOF' … EOF` ne darmiyani lines nayi file me likh di ("here document", jald parhenge). `chmod +x` ne use chalne layaq banaya, aur hum ne teen arguments ke saath chalaya.</Ur>
</Tr>
</Happened>

</Step>

<Step title='"$@": pass every argument along unchanged'>

<Tr>
<En>

When a function or script forwards its arguments to another command, they must arrive **exactly** as given. Only `"$@"` (with the quotes) does that. Unquoted `$@` splits at spaces; `"$*"` glues everything into one.

</En>
<Ur>

Jab function ya script apne arguments kisi aur command ko aage bhejta hai, to unhe **bilkul waise hi** pohanchna chahiye. Sirf `"$@"` (quotes ke saath) ye karta hai. Bina quotes `$@` spaces par torta hai; `"$*"` sab ko ek me jor deta hai.

</Ur>
</Tr>

```bash
count_args() { echo "received $# argument(s): $(printf '<%s> ' "$@")"; }

with_quoted_at()   { count_args "$@"; }
with_unquoted_at() { count_args $@; }
with_star()        { count_args "$*"; }

with_quoted_at   "my file.txt" other
with_unquoted_at "my file.txt" other
with_star        "my file.txt" other
```

```text output
received 2 argument(s): <my file.txt> <other> 
received 3 argument(s): <my> <file.txt> <other> 
received 1 argument(s): <my file.txt other> 
```

</Step>

<Step title="shift: take arguments one at a time">

<Tr>
<En>

`shift` removes the first argument and moves the rest left: `$2` becomes `$1`, and `$#` goes down by one. Like a **queue at a bank counter**: the first person is served and leaves, and everyone moves forward one place.

</En>
<Ur>

`shift` pehla argument hatata hai aur baqi ko baayen khiskata hai: `$2` `$1` ban jata hai, aur `$#` ek kam. Jaise **bank counter ki qataar**: pehle shakhs ka kaam ho gaya aur wo chala gaya, sab ek jagah aage aa gaye.

</Ur>
</Tr>

```bash
demo() {
  echo "Start:  \$1=$1  (count $#)"
  shift
  echo "After shift: \$1=$1  (count $#)"
  shift
  echo "After shift: \$1=$1  (count $#)"
}
demo apple banana cherry
```

```text output
Start:  $1=apple  (count 3)
After shift: $1=banana  (count 2)
After shift: $1=cherry  (count 1)
```

</Step>

<Step title="Check arguments and show a usage message">

<Tr>
<En>

Without checks, a missing argument becomes an **empty variable**, and `rm -rf "$dir/"*` with an empty `dir` is a disaster. At the top of every script: count the arguments, validate the values, and on failure print a **usage** message to stderr and `exit 2` (the usual code for "wrong usage").

</En>
<Ur>

Checks ke baghair ghayab argument **khaali variable** ban jata hai, aur khaali `dir` ke saath `rm -rf "$dir/"*` tabahi hai. Har script ke shuru me: arguments gino, values check karo, aur nakami par stderr me **usage** message chhaapo aur `exit 2` (ghalat istemal ka aam code).

</Ur>
</Tr>

```bash
cat > deploy.sh <<'EOF'
#!/usr/bin/env bash
usage() {
  echo "Usage: $(basename "$0") <dev|staging|prod> <version>" >&2
  exit 2
}

(( $# == 2 )) || usage
env="$1"
version="$2"
[[ $env =~ ^(dev|staging|prod)$ ]] || { echo "Unknown environment: $env" >&2; usage; }

echo "Deploying version $version to $env"
EOF
chmod +x deploy.sh

./deploy.sh staging v1.4.0
./deploy.sh production v1.4.0; echo "exit code: $?"
./deploy.sh; echo "exit code: $?"
```

```text output
Deploying version v1.4.0 to staging
Unknown environment: production
Usage: deploy.sh <dev|staging|prod> <version>
exit code: 2
Usage: deploy.sh <dev|staging|prod> <version>
exit code: 2
```

<Happened>
<Tr>
<En>

- `(( $# == 2 )) || usage`: "exactly two arguments, otherwise show usage".
- The regex allowed only `dev`, `staging` or `prod`, so `production` was rejected.
- `basename "$0"` gave the file name without the folder.

Shortcut for one required argument: `name="${1:?Usage: $0 <name>}"` stops with that message when `$1` is missing.

</En>
<Ur>

- `(( $# == 2 )) || usage`: "bilkul do arguments, warna usage dikhao".
- Regex ne sirf `dev`, `staging` ya `prod` ki ijazat di, isliye `production` radd hua.
- `basename "$0"` ne folder ke baghair file ka naam diya.

Ek zaroori argument ka shortcut: `name="${1:?Usage: $0 <name>}"` `$1` ghayab ho to us message ke saath rok deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The main function pattern">

<Tr>
<En>

Put the main steps in a function called `main`, and call `main "$@"` on the **last line**. All helpers get defined before anything runs, the flow reads top to bottom, and the script's arguments go in cleanly. Inside a function, `$1` means the **function's** first argument, which is why we pass `"$@"`.

</En>
<Ur>

Asal steps `main` naam ke function me rakhein, aur **aakhri line** par `main "$@"` call karein. Kuch chalne se pehle saare helpers ban jate hain, flow ooper se neeche parha jata hai, aur script ke arguments saaf andar jate hain. Function ke andar `$1` ka matlab **function ka** pehla argument hai, isi liye hum `"$@"` bhejte hain.

</Ur>
</Tr>

```bash
#!/usr/bin/env bash
set -euo pipefail

log() { echo "[$(date +%T)] $*" >&2; }
die() { log "ERROR: $*"; exit 1; }

backup() {
  local source_dir="$1" destination="$2"
  [[ -d $source_dir ]] || die "folder $source_dir not found"
  tar -czf "$destination" -C "$source_dir" .
  log "saved $destination"
}

main() {
  local source_dir="${1:?usage: $0 <folder>}"
  backup "$source_dir" "/tmp/backup-$(date +%F).tgz"
}

main "$@"
```

<Tr>
<En>`log` prints a timestamped message, `die` prints an error and stops, `backup` does one job with two arguments, and `main "$@"` starts everything.</En>
<Ur>`log` waqt ke saath message chhaapta hai, `die` error chhaap kar rokta hai, `backup` do arguments ke saath ek kaam karta hai, aur `main "$@"` sab shuru karta hai.</Ur>
</Tr>

</Step>

<Step title="Share functions between scripts: source">

<Tr>
<En>

`source file` (or `. file`) runs another file **inside the current shell**, so its functions become available. Keep common helpers (logging, errors, colours) in one library file. Running it with `./lib/common.sh` would **not** work: it would run in a separate process and its functions would vanish.

</En>
<Ur>

`source file` (ya `. file`) doosri file ko **mojooda shell ke andar** chalata hai, isliye us ke functions dastyab ho jate hain. Aam helpers (logging, errors, rang) ek library file me rakhein. Ise `./lib/common.sh` se chalana kaam **nahi** karega: ye alag process me chalegi aur us ke functions gayab ho jayenge.

</Ur>
</Tr>

```bash
mkdir -p lib
echo 'log() { echo "[LOG] $*"; }' > lib/common.sh

source lib/common.sh
log "This function came from lib/common.sh"
```

```text output
[LOG] This function came from lib/common.sh
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="return for data">

```text
total() { return $(( $1 + $2 )); }   # 200 + 100 → 44 (wraps at 256)
```

</Bad>
<Good title="Print the data">

```text
total() { echo $(( $1 + $2 )); }
sum=$(total 200 100)                  # 300
```

</Good>
</Compare>

<Compare>
<Bad title="Forgetting local">

```text
helper() { for i in 1 2; do :; done; }   # overwrites the caller's i
```

</Bad>
<Good title="local everything">

```text
helper() { local i; for i in 1 2; do :; done; }
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- Calling a function **before** defining it, which gives `command not found`.
- Logging to stdout inside a function whose output is captured.
- `$@` without quotes, so arguments with spaces split apart.
- Expecting `$1` inside a function to be the script's first argument. Pass it in: `main "$@"`.
- Running a library with `./lib.sh` instead of `source lib.sh`.
- No usage message, so users (including future you) guess and get it wrong.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Function banane se **pehle** call karna, jis se `command not found` aata hai.
- Aise function ke andar stdout par log karna jis ka output pakra ja raha ho.
- Bina quotes `$@`, jis se spaces wale arguments toot jate hain.
- Function ke andar `$1` ko script ka pehla argument samajhna. Use andar bhejein: `main "$@"`.
- Library ko `source lib.sh` ki jagah `./lib.sh` se chalana.
- Usage message na hona, isliye users (aainda aap bhi) andaza lagate aur ghalti karte hain.

</Ur>
</Tr>

<DeepDive title="Real world: a server bootstrap script">

A helper many teams keep in a repo: small functions, a `main`, and arguments.

```bash
#!/usr/bin/env bash
# bootstrap.sh <username> [ssh-public-key-file]
set -euo pipefail

log() { printf '\e[32m[+]\e[0m %s\n' "$*" >&2; }
die() { printf '\e[31m[x]\e[0m %s\n' "$*" >&2; exit 1; }

require_root() { (( EUID == 0 )) || die "run as root (sudo $0 …)"; }

install_packages() {
  log "installing base packages"
  apt-get update -qq
  apt-get install -y -qq "$@" > /dev/null
}

create_admin() {
  local user="$1" keyfile="$2"
  if id "$user" &> /dev/null; then
    log "user $user already exists"
  else
    useradd -m -s /bin/bash -G sudo "$user"
    log "created $user"
  fi
  install -d -m 700 -o "$user" -g "$user" "/home/$user/.ssh"
  install -m 600 -o "$user" -g "$user" "$keyfile" "/home/$user/.ssh/authorized_keys"
}

main() {
  local user="${1:?usage: $0 <username> [pubkey-file]}"
  local key="${2:-/root/.ssh/authorized_keys}"
  [[ -r $key ]] || die "cannot read key file $key"
  require_root
  install_packages curl git ufw fail2ban
  create_admin "$user" "$key"
  log "done — log in as $user with your SSH key"
}

main "$@"
```

Each function does one job and can be re-run safely (the `id` check before `useradd`). That property, **idempotency**, is what tools like Ansible formalise later.

</DeepDive>

<DeepDive title="Security lens">

Arguments are user input. Every value that reaches `rm`, `ssh`, a SQL query, a URL or a file path must be validated first.

- **Allow-list arguments** with `case` or an anchored regex; reject everything else with a non-zero exit.
- **Option injection:** a "filename" like `--checkpoint-action=exec=sh` passed to `tar` becomes an option. Put `--` before user-supplied paths: `tar -czf out.tgz -- "$path"`.
- **Never pass arguments through `eval`** or build commands as strings; use arrays and `"$@"`.
- **`source` executes code:** only source files you control, with safe permissions. Sourcing a world-writable file is code execution for anyone who can edit it.
- **Secrets as arguments are visible** to every user via `ps` and end up in shell history. Pass secrets through environment variables, files with mode 600, or stdin.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between $@, $* and their quoted forms?">
Unquoted, both expand to all arguments and are then re-split on whitespace. Quoted, "$@" expands to every argument as a separate word, preserving spaces inside each one, while "$*" joins all arguments into a single word separated by the first character of IFS. "$@" is the right choice for passing arguments on to another command.
</QA>

<QA q="How do you return a value from a Bash function?">
return only sets the exit status, a number from 0 to 255, used for success or failure. To return data, the function prints it to stdout and the caller captures it with command substitution, such as result=$(myfunc). Diagnostic messages should go to stderr so they are not captured.
</QA>

<QA q="Why use local in functions?">
Bash variables are global by default, even when assigned inside a function, so a helper can accidentally overwrite a caller's variable. local limits a variable to the function (and functions it calls), which avoids these hidden side effects.
</QA>

<QA q="What does shift do?">
shift removes the first positional parameter and moves the rest down, so $2 becomes $1 and $# decreases by one; shift n removes n parameters. It is used to consume arguments in a loop when parsing options manually.
</QA>

<QA q="What is the difference between running a script and sourcing it?">
Running ./script.sh starts a new child process; variables, functions and directory changes it makes disappear when it exits. source script.sh (or . script.sh) runs the commands in the current shell, so its functions and variables remain available. Libraries of functions and environment files are sourced.
</QA>

</DeepDive>
