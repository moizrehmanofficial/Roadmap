<BigIdea>
<Tr>
<En>
**Debugging** is detective work: finding the exact line and the exact reason a script misbehaves. Bash changes your command **before** running it (filling variables, splitting words, expanding `*`), so the command you **wrote** isn't always the command that **ran**. `bash -x` shows what really ran, `bash -n` checks syntax without running anything, and **ShellCheck** finds bugs before you even run the script.
</En>
<Ur>
**Debugging** jasoosi ka kaam hai: wo asal line aur asal wajah dhoondna jis se script ghalat chalta hai. Bash aap ki command chalane se **pehle** badal deta hai (variables bharna, alfaz torna, `*` phailana), isliye jo command aap ne **likhi** wo hamesha wahi nahi hoti jo **chali**. `bash -x` dikhata hai asal me kya chala, `bash -n` kuch chalaye baghair syntax check karta hai, aur **ShellCheck** script chalane se pehle hi bugs dhoond leta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

| Tool | What it does | When |
| --- | --- | --- |
| `bash -n` | Checks syntax without running | Before running a new or edited script |
| `set -x` / `bash -x` | Prints every command as it really runs | The script runs but does the wrong thing |
| `PS4` | Adds line numbers to the trace | Long scripts |
| `declare -p`, `printf '%q'` | Shows a value's exact contents | A value "looks right" but isn't |
| ShellCheck | Finds bugs without running | Always, and in CI |

</En>
<Ur>

| Tool | Kya karta hai | Kab |
| --- | --- | --- |
| `bash -n` | Chalaye baghair syntax check | Naya ya badla script chalane se pehle |
| `set -x` / `bash -x` | Har command asal me jaise chali chhaapta hai | Script chalta hai lekin ghalat kaam karta hai |
| `PS4` | Trace me line numbers jorta hai | Lambe scripts |
| `declare -p`, `printf '%q'` | Value ka bilkul asal mawad dikhata hai | Value "sahi lagti" hai lekin hai nahi |
| ShellCheck | Chalaye baghair bugs dhoondta hai | Hamesha, aur CI me |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Saves hours:** instead of guessing and sprinkling random `echo` lines, you see exactly what happened.
- **Finds hidden problems:** quoting bugs are invisible in the source but obvious in the trace.
- **Prevents incidents:** ShellCheck catches dangerous patterns (unquoted `rm`, unchecked `cd`) before they reach a server.
- **Team standard:** many teams fail CI if ShellCheck reports problems.

</En>
<Ur>

- **Ghante bachata hai:** andaze lagane aur idhar udhar `echo` daalne ke bajaye aap bilkul dekhte hain ke kya hua.
- **Chhupe masle dhoondta hai:** quoting bugs code me nazar nahi aate lekin trace me saaf hote hain.
- **Hadsat rokta hai:** ShellCheck khatarnak patterns (bina quotes `rm`, bina check `cd`) server tak pohanchne se pehle pakarta hai.
- **Team ka mayaar:** kai teams ShellCheck ke masle batane par CI fail karti hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **Before running** a script you just wrote or changed: `bash -n` and `shellcheck`.
- **When it misbehaves:** `bash -x`.
- **In CI pipelines:** ShellCheck on every pull request.
- **On servers:** tracing a cron job or entrypoint that fails only there.

</En>
<Ur>

- Naya likha ya badla script **chalane se pehle**: `bash -n` aur `shellcheck`.
- **Jab ghalat chale:** `bash -x`.
- **CI pipelines me:** har pull request par ShellCheck.
- **Servers par:** sirf wahan fail hone wale cron job ya entrypoint ka trace.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

A method that works for any bug:

1. **Read the error message** fully; it often names the line.
2. **Reproduce** the bug reliably.
3. **Check syntax** (`bash -n`) and **lint** (ShellCheck).
4. **Trace** (`bash -x`) to see what really ran.
5. **Shrink** the problem until the smallest failing piece remains.
6. **Fix one thing**, then test again.

</En>
<Ur>

Har bug ke liye chalne wala tareeqa:

1. **Error message poora parhein**; aksar line ka naam hota hai.
2. Bug ko bharose se **dobara paida** karein.
3. **Syntax** (`bash -n`) aur **lint** (ShellCheck) check karein.
4. **Trace** (`bash -x`) se dekhein asal me kya chala.
5. Masle ko **chhota** karein jab tak sab se chhota fail hone wala hissa bache.
6. **Ek cheez theek** karein, phir dobara test.

</Ur>
</Tr>
</How>
</Glance>

## Learn it step by step

<Walkthrough>

<Step title="bash -n: syntax check without running">

<Tr>
<En>

A script with a missing `fi` might run half its commands before Bash reaches the broken part. `bash -n script.sh` reads everything and runs **nothing**. No output and exit 0 means no syntax errors.

</En>
<Ur>

Ghayab `fi` wala script tooti jagah tak pohanchne se pehle aadhi commands chala sakta hai. `bash -n script.sh` sab parhta hai aur **kuch nahi** chalata. Koi output na ho aur exit 0 ho to syntax errors nahi.

</Ur>
</Tr>

```bash
cat > broken.sh <<'EOF'
#!/usr/bin/env bash
echo "start"
if [[ -d /etc ]]; then
  echo "etc exists"
echo "end"
EOF
bash -n broken.sh; echo "exit: $?"
```

```text output
broken.sh: line 6: syntax error: unexpected end of file
exit: 2
```

<Happened>
<Tr>
<En>"Unexpected end of file" almost always means something was **opened but not closed**: a missing `fi`, `done`, `esac`, `}` or quote. Here the `if` had no `fi`.</En>
<Ur>"Unexpected end of file" ka matlab taqreeban hamesha ye hai ke kuch **khola gaya lekin band nahi hua**: ghayab `fi`, `done`, `esac`, `}` ya quote. Yahan `if` ka `fi` nahi tha.</Ur>
</Tr>
</Happened>

</Step>

<Step title="set -x: see every command as it really runs">

<Tr>
<En>

In tracing mode, Bash prints each command **after** expansion, with `+` in front, before running it. Commands inside `$(…)` get `++`. Run a whole script traced with `bash -x script.sh`, or put `set -x` inside it.

</En>
<Ur>

Tracing mode me Bash har command ko expansion ke **baad**, aage `+` laga kar, chalane se pehle chhaapta hai. `$(…)` ke andar ki commands ko `++` milta hai. Poora script `bash -x script.sh` se trace karein, ya andar `set -x` lagayen.

</Ur>
</Tr>

```bash
cat > greet.sh <<'EOF'
name="Alex Carter"
file="report $(date +%Y).txt"
echo "Hello $name"
touch $file
EOF
bash -x greet.sh 2>&1 | sed 's/[0-9]\{4\}/YYYY/g'
ls report 20*.txt | sed 's/[0-9]\{4\}/YYYY/g'
```

```text output
+ name='Alex Carter'
++ date +%Y
+ file='report YYYY.txt'
+ echo 'Hello Alex Carter'
Hello Alex Carter
+ touch report YYYY.txt
YYYY.txt
report
```

<Happened>
<Tr>
<En>The trace line `+ touch report YYYY.txt` reveals the bug instantly: `touch` got **two** arguments because `$file` wasn't quoted, so two files were made, `report` and `YYYY.txt`. The fix is `touch "$file"`. (`sed` swaps the year for `YYYY` so the output stays the same every year.)</En>
<Ur>Trace line `+ touch report YYYY.txt` bug foran dikha deti hai: `touch` ko **do** arguments mile kyun ke `$file` par quotes nahi the, isliye do files banin, `report` aur `YYYY.txt`. Hal `touch "$file"` hai. (`sed` saal ko `YYYY` se badalta hai taa ke output har saal ek jaisa rahe.)</Ur>
</Tr>
</Happened>

</Step>

<Step title="Line numbers in the trace: PS4">

<Tr>
<En>

`PS4` is the prefix before each traced line (by default just `+ `). Put the file, line and function in it, so "which line printed this?" answers itself. Use single quotes so it's evaluated for each line, and set it **inside** the script (as root, Bash ignores a `PS4` from the environment for security).

</En>
<Ur>

`PS4` har trace line se pehle ka prefix hai (pehle se sirf `+ `). Is me file, line aur function daalein, taa ke "ye kis line ne chhaapa?" ka jawab khud mil jaye. Single quotes lagayen taa ke har line ke liye hisaab ho, aur ise script ke **andar** set karein (root ke tor par Bash hifazat ke liye environment wala `PS4` nazar andaz karta hai).

</Ur>
</Tr>

```bash
cat > calc.sh <<'EOF'
PS4='+ ${BASH_SOURCE##*/}:${LINENO}:${FUNCNAME[0]:-main}: '
set -x
total=0
add() {
  total=$((total + $1))
}
add 5
add 10
echo "total=$total"
EOF
bash calc.sh
```

```text output
+ calc.sh:3:main: total=0
+ calc.sh:7:main: add 5
+ calc.sh:5:add: total=5
+ calc.sh:8:main: add 10
+ calc.sh:5:add: total=15
+ calc.sh:9:main: echo total=15
total=15
```

</Step>

<Step title="Trace only part of a script">

<Tr>
<En>

Tracing a 500-line script is too noisy. Put `set -x` just before the suspicious part and `set +x` after it. `{ set +x; } 2>/dev/null` hides the `set +x` line itself from the trace.

</En>
<Ur>

500 lines ka script trace karna bohot shor wala hai. Shak wale hisse se pehle `set -x` aur baad me `set +x` lagayen. `{ set +x; } 2>/dev/null` khud `set +x` wali line ko trace se chhupa deta hai.

</Ur>
</Tr>

```bash
cat > partial.sh <<'EOF'
echo "step 1 (not traced)"
set -x
count=$(( 2 * 21 ))
{ set +x; } 2> /dev/null
echo "step 3 (not traced), count=$count"
EOF
bash partial.sh 2>&1
```

```text output
step 1 (not traced)
+ count=42
step 3 (not traced), count=42
```

</Step>

<Step title="Send the trace to a file">

<Tr>
<En>

Traces are noisy. Keep them in a separate file so normal output stays readable, and so you can trace cron jobs where there's no screen: `exec 5> trace.log; BASH_XTRACEFD=5; set -x`.

</En>
<Ur>

Traces shor wale hote hain. Inhe alag file me rakhein taa ke aam output parhne layaq rahe, aur aap un cron jobs ko bhi trace kar sakein jahan screen nahi: `exec 5> trace.log; BASH_XTRACEFD=5; set -x`.

</Ur>
</Tr>

```bash
cat > quiet.sh <<'EOF'
exec 5> trace.log
BASH_XTRACEFD=5
set -x
x=7
echo "result: $((x * 6))"
EOF
bash quiet.sh
echo "--- trace.log:"
cat trace.log
```

```text output
result: 42
--- trace.log:
+ x=7
+ echo 'result: 42'
```

</Step>

<Step title="See a value's hidden characters">

<Tr>
<En>

`echo "$x"` hides trailing spaces and `\r` characters, a very common cause of "this comparison should be true but isn't". Make them visible:

- `declare -p var` shows the variable with quoting.
- `printf '%q\n' "$var"` shows special characters escaped.
- `cat -A file` (or `cat -v`) shows line endings: `^M` = Windows.

</En>
<Ur>

`echo "$x"` aakhri spaces aur `\r` huroof chhupa deta hai, jo "ye muqabla sach hona chahiye tha lekin nahi" ki bohot aam wajah hai. Inhe nazar laayen:

- `declare -p var` variable quoting ke saath dikhata hai.
- `printf '%q\n' "$var"` khaas huroof escape kar ke dikhata hai.
- `cat -A file` (ya `cat -v`) line endings dikhata hai: `^M` = Windows.

</Ur>
</Tr>

```bash
printf 'production\r\n' > env.txt     # a file saved with Windows line endings
read -r env < env.txt
echo "echo shows: [$env]" | cat -v
[[ $env == production ]] && echo "match" || echo "NO match — why?"
printf 'printf %%q shows: %q\n' "$env"
declare -p env | cat -v
env="${env%$'\r'}"
[[ $env == production ]] && echo "after removing \\r: match"
```

```text output
echo shows: [production^M]
NO match — why?
printf %q shows: $'production\r'
declare -- env=$'production\r'
after removing \r: match
```

<Happened>
<Tr>
<En>The value had an invisible carriage return (`\r`) from Windows. `printf %q` made it visible, and `${env%$'\r'}` removed it. Converting files with `dos2unix` fixes the source of the problem.</En>
<Ur>Value me Windows ka ek nazar na aane wala carriage return (`\r`) tha. `printf %q` ne use dikhaya, aur `${env%$'\r'}` ne hataya. Files ko `dos2unix` se badalna masle ki jar theek karta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="ShellCheck: find bugs before running">

<Tr>
<En>

ShellCheck is a free **linter**: it reads the script without running it and reports likely bugs, each with a code like `SC2086` and an explanation. Install with `sudo apt install shellcheck` or `brew install shellcheck`, then run `shellcheck script.sh`. Look up any code at `https://www.shellcheck.net/wiki/SC2086`.

</En>
<Ur>

ShellCheck muft **linter** hai: ye script chalaye baghair parhta hai aur mumkina bugs batata hai, har ek ke saath `SC2086` jaisa code aur wazahat. `sudo apt install shellcheck` ya `brew install shellcheck` se install karein, phir `shellcheck script.sh` chalayen. Koi bhi code `https://www.shellcheck.net/wiki/SC2086` par dekhein.

</Ur>
</Tr>

```bash
cat > cleanup.sh <<'EOF'
#!/usr/bin/env bash
dir=$1
cd $dir
rm -rf $dir/*
EOF
shellcheck -f gcc cleanup.sh
```

```text output
cleanup.sh:3:1: warning: Use 'cd ... || exit' or 'cd ... || return' in case cd fails. [SC2164]
cleanup.sh:3:4: note: Double quote to prevent globbing and word splitting. [SC2086]
cleanup.sh:4:8: warning: Use "${var:?}" to ensure this never expands to /* . [SC2115]
cleanup.sh:4:8: note: Double quote to prevent globbing and word splitting. [SC2086]
```

<Happened>
<Tr>
<En>Four lines of code, four real problems, including the "delete everything" bug from the safe-scripts lesson (`SC2115`). `-f gcc` gives a compact one-line format; without it ShellCheck prints a friendlier view with arrows.</En>
<Ur>Code ki chaar lines, chaar asli masle, jin me mehfooz-scripts sabaq ka "sab kuch mita do" bug (`SC2115`) bhi hai. `-f gcc` chhota ek-line format deta hai; is ke baghair ShellCheck teeron ke saath zyada dostana nazar chhaapta hai.</Ur>
</Tr>
</Happened>

<Tr>
<En>The fixed version passes cleanly:</En>
<Ur>Theek kiya hua version saaf paas hota hai:</Ur>
</Tr>

```bash
cat > cleanup.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
dir="${1:?usage: cleanup.sh <dir>}"
cd "$dir"
rm -rf "${dir:?}"/*
EOF
shellcheck cleanup.sh && echo "ShellCheck: no problems found"
```

```text output
ShellCheck: no problems found
```

</Step>

<Step title="The most common ShellCheck warnings">

<Tr>
<En>

| Code | Meaning | Fix |
| --- | --- | --- |
| SC2086 | Unquoted variable may split or glob | `"$var"` |
| SC2164 | `cd` without handling failure | `cd dir \|\| exit 1` or `set -e` |
| SC2115 | `rm -rf $var/` might become `rm -rf /` | `"${var:?}"/` |
| SC2155 | `local x=$(cmd)` hides cmd's exit code | `local x; x=$(cmd)` |
| SC2034 | Variable assigned but never used (often a typo) | Check the name |
| SC2045 | Looping over `ls` output | `for f in *` |
| SC2002 | Useless use of cat | `grep x file` |
| SC2035 | `*.txt` could match a file named like an option | `./*.txt` |
| SC1091 | Can't follow a sourced file | `# shellcheck source=path` |

If a warning is truly wrong for your case, disable it for **one line** with a reason: `# shellcheck disable=SC2086  # splitting wanted here`.

</En>
<Ur>

| Code | Matlab | Hal |
| --- | --- | --- |
| SC2086 | Bina quotes variable toot ya phail sakta hai | `"$var"` |
| SC2164 | Nakami sambhale baghair `cd` | `cd dir \|\| exit 1` ya `set -e` |
| SC2115 | `rm -rf $var/` `rm -rf /` ban sakta hai | `"${var:?}"/` |
| SC2155 | `local x=$(cmd)` cmd ka exit code chhupata hai | `local x; x=$(cmd)` |
| SC2034 | Variable diya lekin kabhi istemal nahi (aksar typo) | Naam check karein |
| SC2045 | `ls` ke output par loop | `for f in *` |
| SC2002 | Bekaar `cat` | `grep x file` |
| SC2035 | `*.txt` option jaise naam wali file se mil sakta hai | `./*.txt` |
| SC1091 | Source ki gayi file follow nahi kar sakta | `# shellcheck source=path` |

Agar koi warning aap ke case me waqai ghalat ho, to use **ek line** ke liye wajah ke saath band karein: `# shellcheck disable=SC2086  # splitting wanted here`.

</Ur>
</Tr>

</Step>

<Step title="Bugs that only happen elsewhere">

<Tr>
<En>

"It works on my machine" but not in cron, CI or Docker? Those places differ: a smaller PATH, no terminal, another user, maybe `sh` instead of `bash`, another working folder, missing variables. Log the environment at the start (`env`, `pwd`, `id`, `$PATH`), use absolute paths, set PATH yourself, and reproduce with `env -i`.

</En>
<Ur>

"Mere computer par chalta hai" lekin cron, CI ya Docker me nahi? Wo jagahen mukhtalif hain: chhota PATH, terminal nahi, doosra user, shayad `bash` ki jagah `sh`, doosra working folder, ghayab variables. Shuru me environment log karein (`env`, `pwd`, `id`, `$PATH`), poore paths istemal karein, PATH khud set karein, aur `env -i` se masla dobara paida karein.

</Ur>
</Tr>

```bash
env -i /bin/bash -c 'echo "HOME=[${HOME:-}] USER=[${USER:-}] LANG=[${LANG:-}]"'
```

```text output
HOME=[] USER=[] LANG=[]
```

<Happened>
<Tr>
<En>`env -i` started Bash with an **empty** environment (no `HOME`, no `USER`, no language, only a basic PATH), similar to what cron gives you. Running your script like this reproduces many "only in cron" bugs on your own machine.</En>
<Ur>`env -i` ne Bash ko **khaali** environment ke saath shuru kiya (na `HOME`, na `USER`, na zabaan, sirf bunyadi PATH), jaisa cron deta hai. Script ko aise chalana bohot se "sirf cron me" bugs aap ki apni machine par dobara paida kar deta hai.</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Tracing around a secret">

```text
set -x
curl -H "Authorization: Bearer $TOKEN" "$api"    # the token is printed in the log
```

</Bad>
<Good title="Turn tracing off around secrets">

```text
{ set +x; } 2>/dev/null
curl -H "Authorization: Bearer $TOKEN" "$api"
set -x
```

</Good>
</Compare>

<Compare>
<Bad title="Running a Bash script with sh">

```text
sh deploy.sh        # [[ ]], arrays, ${var,,} fail with confusing errors
```

</Bad>
<Good title="Run it with bash">

```text
bash deploy.sh      # or ./deploy.sh with a #!/usr/bin/env bash shebang
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Guessing instead of tracing**: adding random `echo` lines everywhere.
- **Leaving `set -x` in production scripts**: noisy logs and leaked values. Make it opt-in with `DEBUG=1`.
- **Ignoring ShellCheck warnings** because "it works": most are real bugs waiting for an unusual input.
- **Editing scripts on Windows**: `\r` line endings give errors like `$'\r': command not found`. Fix with `dos2unix` or set your editor to LF.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Trace ke bajaye andaze**: har jagah ittefaqi `echo` lines daalna.
- **Production scripts me `set -x` chhor dena**: shor wale logs aur leak hoti values. Ise `DEBUG=1` se ikhtiyari banayen.
- **ShellCheck warnings nazar andaz karna** kyun ke "chal to raha hai": zyada tar asli bugs hain jo kisi ajeeb input ka intezar kar rahe hain.
- **Windows par scripts edit karna**: `\r` line endings `$'\r': command not found` jaise errors deti hain. `dos2unix` se theek karein ya editor ko LF par rakhein.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Debug lab">

<Tr>
<En>
A syntax check that finds a missing `done`, a trace that reveals an unquoted variable, hidden characters made visible, and ShellCheck listing three warnings.
</En>
<Ur>
Syntax check jo ghayab `done` pakarta hai, trace jo bina quotes variable dikhata hai, chhupe huroof nazar aate hue, aur ShellCheck teen warnings batata hai.
</Ur>
</Tr>

```bash
mkdir -p ~/debug-lab && cd ~/debug-lab

# 1. syntax check
printf 'for i in 1 2; do\n  echo $i\n' > s.sh
bash -n s.sh 2>&1 | sed 's/^s.sh: //'

# 2. trace shows the real command
printf 'f="a b.txt"\ntouch $f\n' > t.sh
bash -x t.sh 2>&1 | grep touch
ls

# 3. hidden characters
v=$'value \t'
printf '%q\n' "$v"

# 4. ShellCheck
printf '#!/bin/bash\nfor f in $(ls *.txt); do cat $f; done\n' > lint.sh
shellcheck -f gcc lint.sh | sed 's/.*\[\(SC[0-9]*\)\]/\1/' | sort -u

cd ~ && rm -rf ~/debug-lab
```

```text output
line 3: syntax error: unexpected end of file
+ touch a b.txt
a
b.txt
s.sh
t.sh
$'value \t'
SC2035
SC2045
SC2086
```

<Hint>
<Tr>
<En>`ls` showed files `a` and `b.txt`: the trace already told us why (`touch a b.txt`).</En>
<Ur>`ls` ne `a` aur `b.txt` files dikhayin: trace ne pehle hi wajah bata di thi (`touch a b.txt`).</Ur>
</Tr>
</Hint>

</Challenge>

<Challenge title="Fix the lint.sh script">

<DeepDive title="Real world: the cron backup that 'sometimes doesn't run'">

Debugging a nightly backup step by step:

```bash
# 1. Make the cron job log everything, including a trace with line numbers
# crontab:  0 2 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1

#!/usr/bin/env bash
set -Eeuo pipefail
export PS4='+ [$(date +%T)] ${BASH_SOURCE##*/}:${LINENO}: '
if [[ ${DEBUG:-0} == 1 ]]; then set -x; fi
trap 'echo "FAILED at line $LINENO: $BASH_COMMAND (exit $?)" >&2' ERR

echo "=== backup started $(date '+%F %T') as $(id -un), PATH=$PATH"
PATH=/usr/local/bin:/usr/bin:/bin           # 2. don't depend on cron's PATH
cd /var/backups                              # 3. absolute paths only
pg_dump shop | gzip > "shop-$(date +%F).sql.gz"
echo "=== backup finished"
```

The log then showed `FAILED at line 12: pg_dump shop (exit 127)`: command not found, because `pg_dump` lives in `/usr/lib/postgresql/16/bin`, which isn't in cron's PATH. Adding that folder to PATH fixed a bug that "never happens when I run it by hand".

`DEBUG=1 ./backup.sh` turns on the full trace when needed, without editing the script.

</DeepDive>

<DeepDive title="Security lens">

Debug output is data leakage waiting to happen: traces print every expanded value, including secrets.

- **Never enable `set -x` around secrets.** Wrap them: `{ set +x; } 2>/dev/null; …secret work…; set -x`.
- **CI logs are often visible to many people** (sometimes public for open-source projects). GitHub Actions masks registered secrets, but values derived from them may still leak.
- **Run ShellCheck in CI**: it flags injection-prone patterns like unquoted variables in commands and `eval`.
- **Remove debug flags before release**, and make debugging opt-in (`DEBUG=1`).
- **Log files with traces** must have restrictive permissions (`chmod 600`).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you debug a Bash script that runs but gives wrong results?">
Run it with bash -x (or add set -x) to print each command after expansion, which shows the actual arguments every command received. Set PS4 to include the file, line number and function to locate problems, trace only the suspicious section with set -x and set +x, and inspect suspicious values with declare -p or printf %q to reveal hidden characters.
</QA>

<QA q="What does bash -n do?">
It reads the script and checks for syntax errors without executing any commands. It is a safe first check after editing a script, but it does not find logic errors or problems that only appear at run time.
</QA>

<QA q="What is ShellCheck and why use it?">
ShellCheck is a static analysis tool for shell scripts. It detects common bugs and risky patterns without running the script, such as unquoted variables, unchecked cd, rm -rf with possibly empty variables, and hidden exit codes. Running it in the editor and in CI catches problems before they reach production.
</QA>

<QA q="A script works when run manually but fails in cron. What do you check?">
Cron runs with a minimal environment: a short PATH, often no HOME, no terminal, possibly a different user and working directory, and sometimes sh instead of bash. Check the logs (redirect output to a file), use absolute paths, set PATH explicitly, verify the shebang and permissions, and reproduce locally with env -i.
</QA>

</DeepDive>
