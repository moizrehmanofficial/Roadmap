<BigIdea>
<Tr>
<En>
**Options** are the dash-words that change how a command behaves: `ls -l`, `curl -o page.html`. `getopts` is a built-in Bash command that reads options for **your own** script, one at a time, in a `while` loop. You list the allowed letters in an **option string** like `"vn:o:h"`; a letter followed by `:` needs a value, which arrives in `$OPTARG`. After the loop, `shift $((OPTIND - 1))` removes the options so only the real arguments remain.
</En>
<Ur>
**Options** wo dash wale alfaz hain jo command ka rawaiya badalte hain: `ls -l`, `curl -o page.html`. `getopts` Bash ki built-in command hai jo **aap ke apne** script ke options ek ek kar ke `while` loop me parhti hai. Jaiz letters aap **option string** me likhte hain, jaise `"vn:o:h"`; jis letter ke baad `:` ho use value chahiye, jo `$OPTARG` me aati hai. Loop ke baad `shift $((OPTIND - 1))` options hata deta hai taa ke sirf asal arguments bachen.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

You already use options all the time:

```text
ls -l -a /etc
tar -czf backup.tgz /var/www
curl -s -o page.html https://example.com
```

- `-l` is an on/off switch, called a **flag**.
- `-o page.html` needs a **value**.
- `/etc` and the URL, the things the command works on, are **operands**.
- Flags can be combined: `-la` means `-l -a`.

`getopts` reads these for your script. Don't confuse it with `getopt` (no "s"), a separate program that behaves differently on different systems.

</En>
<Ur>

Aap options hamesha istemal karte hain:

```text
ls -l -a /etc
tar -czf backup.tgz /var/www
curl -s -o page.html https://example.com
```

- `-l` on/off switch hai, jise **flag** kehte hain.
- `-o page.html` ko **value** chahiye.
- `/etc` aur URL, jin par command kaam karti hai, **operands** hain.
- Flags jore ja sakte hain: `-la` ka matlab `-l -a`.

`getopts` ye aap ke script ke liye parhta hai. Ise `getopt` ("s" ke baghair) se na milayen, jo alag program hai aur mukhtalif systems par mukhtalif chalta hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Compare:

```text
./backup.sh /var/www 14 yes /mnt/backups
./backup.sh -k 14 -v -d /mnt/backups /var/www
```

In the first, you must remember "the second argument is days to keep, the third is verbose". In the second, every value **explains itself**, the order doesn't matter, and new options can be added without breaking anyone. Clear options with a `-h` help screen make team tools usable.

</En>
<Ur>

Muqabla karein:

```text
./backup.sh /var/www 14 yes /mnt/backups
./backup.sh -k 14 -v -d /mnt/backups /var/www
```

Pehle me yaad rakhna parta hai "doosra argument rakhne ke din hain, teesra verbose". Doosre me har value **khud bataati hai**, tarteeb se farq nahi parta, aur naye options kisi ko tore baghair jore ja sakte hain. `-h` help ke saath saaf options team tools ko qabil-e-istemal banate hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- The script has **more than one or two optional settings**.
- You want flags in **any order** and combinable (`-vf`).
- Teammates, cron jobs or CI pipelines run it with different settings.
- For one or two required values only, plain `$1` and `$2` are still fine.

</En>
<Ur>

- Script me **ek do se zyada ikhtiyari settings** hain.
- Aap flags **kisi bhi tarteeb** me aur jore hue (`-vf`) chahte hain.
- Team, cron jobs ya CI pipelines ise mukhtalif settings se chalate hain.
- Sirf ek do zaroori values ke liye saada `$1` aur `$2` ab bhi theek hain.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
while getopts ":vn:" opt; do
  case "$opt" in
    v) verbose=true ;;
    n) count="$OPTARG" ;;
  esac
done
shift $((OPTIND - 1))
```

</En>
<Ur>

```text

  case "$opt" in
```

## Learn it step by step

<Walkthrough>

<Step title="The option string: what to accept">

<Tr>
<En>

The option string lists every letter your script accepts. A **colon after a letter** means "needs a value". Start the string with `:` so you can print your own friendly errors.

| Part | Meaning |
| --- | --- |
| `:` at the very start | "I'll handle errors myself" (recommended) |
| `v` | `-v` is a flag (no value) |
| `n:` | `-n` needs a value, e.g. `-n 5` |
| `o:` | `-o` needs a value, e.g. `-o out.txt` |
| `h` | `-h` is a flag (help) |

So `":vn:o:h"` means: accept `-v`, `-n VALUE`, `-o VALUE` and `-h`, and let me handle errors.

</En>
<Ur>

Option string har wo letter likhti hai jo aap ka script maanta hai. **Letter ke baad colon** ka matlab "value chahiye". String `:` se shuru karein taa ke aap apne dostana errors chhaap sakein.

| Hissa | Matlab |
| --- | --- |
| Bilkul shuru me `:` | "Errors main khud sambhalunga" (tajweez kiya gaya) |
| `v` | `-v` flag hai (value nahi) |
| `n:` | `-n` ko value chahiye, jaise `-n 5` |
| `o:` | `-o` ko value chahiye, jaise `-o out.txt` |
| `h` | `-h` flag hai (madad) |

To `":vn:o:h"` ka matlab: `-v`, `-n VALUE`, `-o VALUE` aur `-h` maano, aur errors mujhe sambhalne do.

</Ur>
</Tr>

</Step>

<Step title="The getopts loop">

<Tr>
<En>

Each call to `getopts` puts the **next option letter** into `opt`. When no options are left, it fails and the `while` loop ends. A `case` decides what each letter does. Set **defaults first**, so they're used when no option is given.

</En>
<Ur>

`getopts` ki har call **agla option letter** `opt` me rakhti hai. Jab options khatam ho jayen to ye fail hoti hai aur `while` loop khatam. `case` tay karta hai ke har letter kya kare. **Pehle defaults** rakhein, taa ke option na diya jaye to wo istemal hon.

</Ur>
</Tr>

```bash
cat > opts-demo.sh <<'EOF'
#!/usr/bin/env bash
verbose=false
count=1

while getopts ":vn:" opt; do
  echo "getopts found: -$opt"
  case "$opt" in
    v) verbose=true ;;
    n) count="$OPTARG" ;;
  esac
done

echo "verbose=$verbose count=$count"
EOF
chmod +x opts-demo.sh

./opts-demo.sh
echo "---"
./opts-demo.sh -v -n 5
echo "---"
./opts-demo.sh -n3 -v
```

```text output
verbose=false count=1
---
getopts found: -v
getopts found: -n
verbose=true count=5
---
getopts found: -n
getopts found: -v
verbose=true count=3
```

<Happened>
<Tr>
<En>Run 1 had no options, so the defaults were used. Run 2 had two options. Run 3 used a different order and `-n3` with no space, and it still worked. The value of `-n` arrived in `OPTARG`.</En>
<Ur>Run 1 me koi option nahi tha, isliye defaults istemal hue. Run 2 me do options the. Run 3 me tarteeb alag thi aur `-n3` bina space ke, phir bhi kaam kiya. `-n` ki value `OPTARG` me aayi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="OPTARG: check the value">

<Tr>
<En>

getopts only makes sure a value **exists**, not that it makes sense. `-n abc` gives `OPTARG=abc`. Copy it into a named variable and **validate** it. `^[1-9][0-9]*$` means "a digit 1–9, then only digits, nothing else": a positive whole number.

</En>
<Ur>

getopts sirf ye yaqeeni banata hai ke value **mojood** ho, ye nahi ke wo maqool ho. `-n abc` `OPTARG=abc` deta hai. Ise naam wale variable me copy karein aur **check** karein. `^[1-9][0-9]*$` ka matlab "1–9 ka hindsa, phir sirf hindse, aur kuch nahi": musbat poora number.

</Ur>
</Tr>

```bash
check_number() {
  local value="$1"
  if [[ $value =~ ^[1-9][0-9]*$ ]]; then
    echo "'$value' is a valid count"
  else
    echo "'$value' is NOT a valid count"
  fi
}
check_number 5
check_number abc
check_number -3
```

```text output
'5' is a valid count
'abc' is NOT a valid count
'-3' is NOT a valid count
```

</Step>

<Step title="OPTIND and shift: options out, operands left">

<Tr>
<En>

`OPTIND` is the position of the next argument getopts would read. After the loop, `shift $((OPTIND - 1))` removes all the options, so `"$@"` holds only the operands (files, URLs, names). **Forgetting it is the most common getopts bug.**

</En>
<Ur>

`OPTIND` us agle argument ki jagah hai jo getopts parhta. Loop ke baad `shift $((OPTIND - 1))` saare options hata deta hai, isliye `"$@"` me sirf operands (files, URLs, naam) rehte hain. **Ise bhoolna getopts ka sab se aam bug hai.**

</Ur>
</Tr>

```bash
cat > operands.sh <<'EOF'
#!/usr/bin/env bash
while getopts ":vn:" opt; do :; done
echo "Before shift: $# args → $*   (OPTIND=$OPTIND)"
shift $((OPTIND - 1))
echo "After shift:  $# args → $*"
EOF
chmod +x operands.sh
./operands.sh -v -n 3 site1.com site2.com
```

```text output
Before shift: 5 args → -v -n 3 site1.com site2.com   (OPTIND=4)
After shift:  2 args → site1.com site2.com
```

<Happened>
<Tr>
<En>getopts read `-v`, `-n` and `3` (positions 1–3), so `OPTIND` became 4, and `shift 3` removed them. The `:` in the loop is a do-nothing command, just to keep the example short.</En>
<Ur>getopts ne `-v`, `-n` aur `3` (jagah 1–3) parhe, isliye `OPTIND` 4 hua, aur `shift 3` ne unhe hata diya. Loop me `:` kuch na karne wali command hai, sirf misaal chhoti rakhne ke liye.</Ur>
</Tr>
</Happened>

<Callout type="warning" title="Options must come first">
<Tr>
<En>getopts stops at the first argument that isn't an option. In `./script.sh site.com -v`, the `-v` is treated as an operand. Write options first, or use `--` to mark the end of options.</En>
<Ur>getopts pehle ghair-option argument par ruk jata hai. `./script.sh site.com -v` me `-v` operand samjha jata hai. Options pehle likhein, ya options ka khatma batane ke liye `--` istemal karein.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Handle mistakes: unknown option, missing value">

<Tr>
<En>

With a leading `:` in the option string, getopts reports two mistakes through `opt`:

- `?` = unknown option
- `:` = an option is missing its value

In both cases `OPTARG` holds the problem letter. A typo like `-x` must **stop** the script: ignoring it could run a real action when the user meant a test. Write `\?)` with a backslash, because a plain `?` in `case` means "any one character".

</En>
<Ur>

Option string ke shuru me `:` ho to getopts `opt` ke zariye do ghaltiyan batata hai:

- `?` = anjaan option
- `:` = option ki value ghayab

Dono soorton me `OPTARG` me masle wala letter hota hai. `-x` jaisi typo ko script **rokna** chahiye: ise nazar andaz karna asli kaam chala sakta hai jab user test chahta tha. `\?)` backslash ke saath likhein, kyun ke `case` me saada `?` ka matlab "koi bhi ek harf".

</Ur>
</Tr>

```bash
cat > strict.sh <<'EOF'
#!/usr/bin/env bash
while getopts ":vn:" opt; do
  case "$opt" in
    v)  echo "verbose on" ;;
    n)  echo "count = $OPTARG" ;;
    :)  echo "Error: -$OPTARG needs a value" >&2; exit 2 ;;
    \?) echo "Error: unknown option -$OPTARG" >&2; exit 2 ;;
  esac
done
echo "All options OK"
EOF
chmod +x strict.sh

./strict.sh -v -n 4
./strict.sh -x; echo "exit code: $?"
./strict.sh -n; echo "exit code: $?"
```

```text output
verbose on
count = 4
All options OK
Error: unknown option -x
exit code: 2
Error: -n needs a value
exit code: 2
```

</Step>

<Step title="A help screen with -h">

<Tr>
<En>

A `usage` function explains every option. Show it with `-h` (to normal output, exit 0) and after a mistake (to stderr, exit 2). In a usage line, `[ ]` means optional, `< >` means required, and `...` means one or more.

</En>
<Ur>

`usage` function har option samjhata hai. Ise `-h` par dikhayen (aam output me, exit 0) aur ghalti ke baad (stderr me, exit 2). Usage line me `[ ]` ka matlab ikhtiyari, `< >` ka matlab zaroori, aur `...` ka matlab ek ya zyada.

</Ur>
</Tr>

```bash
usage() {
  cat <<EOF
Usage: fetch.sh [-v] [-n count] [-o file] <url>...

Options:
  -n count   number of requests per URL (default: 1)
  -o file    write results to a file instead of the screen
  -v         show more details
  -h         show this help
EOF
}
usage
```

```text output
Usage: fetch.sh [-v] [-n count] [-o file] <url>...

Options:
  -n count   number of requests per URL (default: 1)
  -o file    write results to a file instead of the screen
  -v         show more details
  -h         show this help
```

</Step>

<Step title="Repeatable options">

<Tr>
<En>

Some options make sense more than once: `-e a -e b` (a list of patterns) or `-vvv` (more and more detail). Add each value to an array with `excludes+=("$OPTARG")`, and count a repeated flag with `((++verbosity))`.

</En>
<Ur>

Kuch options ek se zyada dafa maqool hain: `-e a -e b` (patterns ki list) ya `-vvv` (ziyada se ziyada tafseel). Har value `excludes+=("$OPTARG")` se array me daalein, aur dohraye flag ko `((++verbosity))` se ginein.

</Ur>
</Tr>

```bash
cat > repeat.sh <<'EOF'
#!/usr/bin/env bash
verbosity=0
excludes=()
while getopts ":ve:" opt; do
  case "$opt" in
    v) ((++verbosity)) ;;
    e) excludes+=("$OPTARG") ;;
  esac
done
echo "verbosity level: $verbosity"
echo "exclude ${#excludes[@]} pattern(s): ${excludes[*]}"
EOF
chmod +x repeat.sh
./repeat.sh -vvv -e '*.tmp' -e node_modules
```

```text output
verbosity level: 3
exclude 2 pattern(s): *.tmp node_modules
```

</Step>

<Step title="Long options (--verbose) with a manual loop">

<Tr>
<En>

getopts **can't** read `--verbose`. For long options, loop yourself:

- Loop while arguments remain: `(( $# > 0 ))`.
- Match `$1` in a `case`.
- For a value in the **next** argument, use `$2` and `shift` once extra.
- `shift` once at the end of every round.
- `--` ends the options; the first non-option also ends them.

</En>
<Ur>

getopts `--verbose` **nahi** parh sakta. Lambe options ke liye khud loop chalayen:

- Jab tak arguments bachen loop: `(( $# > 0 ))`.
- `case` me `$1` milayen.
- **Agle** argument me value ho to `$2` lein aur ek dafa izafi `shift`.
- Har round ke aakhir me ek `shift`.
- `--` options khatam karta hai; pehla ghair-option bhi.

</Ur>
</Tr>

```bash
cat > long.sh <<'EOF'
#!/usr/bin/env bash
verbose=false
count=1
while (( $# > 0 )); do
  case "$1" in
    -v|--verbose) verbose=true ;;
    -n|--count)   count="$2"; shift ;;
    --count=*)    count="${1#*=}" ;;
    --)           shift; break ;;
    -*)           echo "Unknown option: $1" >&2; exit 2 ;;
    *)            break ;;
  esac
  shift
done
echo "verbose=$verbose count=$count operands=$*"
EOF
chmod +x long.sh

./long.sh --verbose --count 4 one two
./long.sh --count=9 -v three
./long.sh --nope; echo "exit code: $?"
```

```text output
verbose=true count=4 operands=one two
verbose=true count=9 operands=three
Unknown option: --nope
exit code: 2
```

<Happened>
<Tr>
<En>For `--count=9`, `${1#*=}` removed everything up to and including `=`, leaving `9`. For `--count 4`, the value was the next argument, so the extra `shift` skipped over it. `one two` stopped the loop at `*) break` and stayed as operands.</En>
<Ur>`--count=9` ke liye `${1#*=}` ne `=` tak sab hata diya, `9` bacha. `--count 4` me value agla argument thi, isliye izafi `shift` ne use paar kiya. `one two` ne `*) break` par loop roka aur operands rahe.</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="?) in case">

```text
case "$opt" in
  ?) echo "unknown" ;;     # ? matches ANY one letter, so it catches every option
```

</Bad>
<Good title="\?) escaped">

```text
case "$opt" in
  \?) echo "unknown -$OPTARG" >&2; exit 2 ;;
```

</Good>
</Compare>

<Compare>
<Bad title="No shift after the loop">

```text
done
for f in "$@"; do …   # still sees -v, -n, 3 as "files"
```

</Bad>
<Good title="Shift the options away">

```text
done
shift $((OPTIND - 1))
for f in "$@"; do …
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Missing `:`** after a letter that needs a value: `-n 5` then treats `5` as an operand.
- **No leading `:`**: getopts prints its own cryptic errors.
- **Options after operands**: getopts stops at the first operand.
- **Calling getopts twice in one shell** (a function used twice) without resetting `OPTIND=1`.
- **Trusting `OPTARG`**: it's user input; validate it.
- **Expecting getopts to handle `--long`**: it can't.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Value wale letter ke baad **`:` bhoolna**: phir `-n 5` me `5` operand ban jata hai.
- **Shuru me `:` na hona**: getopts apne mushkil errors chhaapta hai.
- **Operands ke baad options**: getopts pehle operand par ruk jata hai.
- **Ek shell me getopts do dafa chalana** (do dafa istemal hone wala function) `OPTIND=1` reset kiye baghair.
- **`OPTARG` par bharosa**: ye user ka input hai; check karein.
- **getopts se `--long` ki umeed**: ye nahi kar sakta.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Options lab: a complete tool">

<Tr>
<En>
A full tool with every piece from this lesson: defaults, validation, repeatable options, help, errors, `shift`, and `--`. Look at the last two runs: `site.com -v` treats `-v` as a target, and `--` lets a target start with a dash.
</En>
<Ur>
Is sabaq ke har hisse ke saath poora tool: defaults, validation, dohraye options, help, errors, `shift`, aur `--`. Aakhri do runs dekhein: `site.com -v` me `-v` target samjha gaya, aur `--` target ko dash se shuru hone deta hai.
</Ur>
</Tr>

```bash
mkdir -p ~/opts-lab && cd ~/opts-lab

cat > fetch.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

usage() {
  cat <<USAGE
Usage: $(basename "$0") [-v] [-n count] [-o file] [-e pattern]... <target>...
  -n count    repeat count (default 1)
  -o file     output file (default: stdout)
  -e pattern  exclude pattern (repeatable)
  -v          verbose (repeat for more: -vv)
  -h          help
USAGE
}

verbosity=0; count=1; output=""; excludes=()

while getopts ":vn:o:e:h" opt; do
  case "$opt" in
    v) ((++verbosity)) ;;
    n) [[ $OPTARG =~ ^[1-9][0-9]*$ ]] || { echo "error: -n needs a positive number, got '$OPTARG'" >&2; exit 2; }
       count="$OPTARG" ;;
    o) output="$OPTARG" ;;
    e) excludes+=("$OPTARG") ;;
    h) usage; exit 0 ;;
    :)  echo "error: -$OPTARG needs a value" >&2; exit 2 ;;
    \?) echo "error: unknown option -$OPTARG" >&2; exit 2 ;;
  esac
done
shift $((OPTIND - 1))

(( $# > 0 )) || { echo "error: at least one target required" >&2; exit 2; }

echo "verbosity=$verbosity count=$count output=${output:-stdout} excludes=(${excludes[*]})"
for t in "$@"; do echo "  target: $t"; done
EOF
chmod +x fetch.sh

./fetch.sh example.com
./fetch.sh -vv -n 3 -o out.txt a.com "b site.com"
./fetch.sh -vn5 -e '*.tmp' -e node_modules site.com
./fetch.sh -n; echo "exit: $?"
./fetch.sh -x site.com; echo "exit: $?"
./fetch.sh -n abc site.com; echo "exit: $?"
./fetch.sh -v; echo "exit: $?"
./fetch.sh site.com -v
./fetch.sh -v -- -weird-name

cd ~ && rm -rf ~/opts-lab
```

```text output
verbosity=0 count=1 output=stdout excludes=()
  target: example.com
verbosity=2 count=3 output=out.txt excludes=()
  target: a.com
  target: b site.com
verbosity=1 count=5 output=stdout excludes=(*.tmp node_modules)
  target: site.com
error: -n needs a value
exit: 2
error: unknown option -x
exit: 2
error: -n needs a positive number, got 'abc'
```

<DeepDive title="Real world: an incident log collector">

A tool an on-call engineer runs during an incident:

```bash
#!/usr/bin/env bash
# collect-logs.sh — bundle recent logs for a service into a tarball
set -euo pipefail

usage() {
  cat <<EOF
Usage: $(basename "$0") [-s since] [-o dir] [-z] <service>...
  -s since   journalctl time, e.g. "2 hours ago" (default: "1 hour ago")
  -o dir     output directory (default: /tmp)
  -z         gzip the bundle
  -h         help
Example: $(basename "$0") -s "30 min ago" -z nginx app
EOF
}

since="1 hour ago"; outdir="/tmp"; compress=false

while getopts ":s:o:zh" opt; do
  case "$opt" in
    s) since="$OPTARG" ;;
    o) outdir="$OPTARG" ;;
    z) compress=true ;;
    h) usage; exit 0 ;;
    :)  echo "-$OPTARG needs a value" >&2; exit 2 ;;
    \?) echo "unknown option -$OPTARG" >&2; usage >&2; exit 2 ;;
  esac
done
shift $((OPTIND - 1))
(( $# > 0 )) || { usage >&2; exit 2; }
[[ -d $outdir && -w $outdir ]] || { echo "cannot write to $outdir" >&2; exit 1; }

work="$(mktemp -d)"
for svc in "$@"; do
  [[ $svc =~ ^[a-zA-Z0-9@._-]+$ ]] || { echo "skipping invalid name: $svc" >&2; continue; }
  journalctl -u "$svc" --since "$since" --no-pager > "$work/$svc.log" || true
done

bundle="$outdir/logs-$(hostname)-$(date +%Y%m%d-%H%M%S).tar"
tar_flags=(-c)
if $compress; then bundle+=".gz"; tar_flags+=(-z); fi
tar -C "$work" "${tar_flags[@]}" -f "$bundle" .
rm -rf "$work"
echo "$bundle"
```

Service names are validated with an allow-list regex before reaching `journalctl`, and the only thing printed to stdout is the bundle path, so another script can do `bundle=$(./collect-logs.sh -z nginx)`.

</DeepDive>

<DeepDive title="Security lens">

Options are user input with extra structure. Parse them strictly and fail closed.

- **Unknown option → exit non-zero.** Silently ignoring a typo like `-dryrun` can turn a dry run into a real deletion.
- **Validate every `OPTARG`** with an allow-list or anchored regex before it reaches a path, a command or a URL.
- **Support `--`** so filenames beginning with `-` aren't parsed as options; pass `--` on to the commands you call (`rm -- "$f"`).
- **Dangerous defaults are a design bug:** make destructive behaviour opt-in (`-f`/`--force`), and the safe path the default.
- **Don't accept secrets as options** (`-p password`): they show up in `ps`, logs and shell history. Read them from an environment variable, a file, or a prompt with `read -s`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does getopts work?">
getopts is a shell built-in called in a while loop. Each call reads the next option from the arguments according to an option string, stores the option letter in a variable and, for options declared with a trailing colon, stores the value in OPTARG. OPTIND tracks the next argument index. When options run out it returns non-zero, and the script runs shift $((OPTIND - 1)) to leave only the operands.
</QA>

<QA q="What does the leading colon in the getopts option string do?">
It enables silent error reporting. getopts no longer prints its own messages; instead an unknown option sets the variable to ? and a missing value sets it to :, with the offending option letter in OPTARG, so the script can print its own clear errors and usage.
</QA>

<QA q="What is the difference between getopts and getopt?">
getopts is a POSIX shell built-in, portable and consistent, but only supports single-letter options. getopt is an external program (the util-linux version) that also supports long options and option reordering, but its behaviour differs between systems such as Linux and macOS. For long options in portable scripts, a manual while/case/shift loop is common.
</QA>

<QA q="Why should unknown options cause the script to fail?">
Because a mistyped option would otherwise be ignored and the script would run with default behaviour the user did not intend, for example running for real when the user meant a dry run. Failing with a usage message and a non-zero exit code makes the mistake visible and safe.
</QA>

</DeepDive>
