<Callout type="tip" title="In one minute">
**Options** are the dash-words you give a command to change how it behaves: `ls -l`, `curl -o page.html`. `getopts` is a built-in Bash command that reads such options for your own script, one at a time, in a `while` loop. You list the accepted letters in an **option string** like `"vn:o:h"`; a letter followed by `:` needs a value, which arrives in `$OPTARG`. After the loop, `shift $((OPTIND - 1))` removes the options, leaving the remaining arguments in `"$@"`. `getopts` handles only short options (`-v`); for `--verbose`, use a `while`/`case`/`shift` loop.
</Callout>

## Start from zero

### What are options?

You already use options all the time:

```
ls -l -a /etc
tar -czf backup.tgz /var/www
curl -s -o page.html https://example.com
```

<Callout type="analogy">
Ordering food: "One burger" is the basic order. "**Extra cheese**, **no onions**, **size: large**" are options — they change **how** the burger is made. Some are just on/off (extra cheese). Some need a value (size: **large**). And the order of options does not matter: "no onions, extra cheese" is the same burger.
</Callout>

Command-line options work exactly like that:

- `-l` is an on/off switch (a **flag**): "show the long format".
- `-o page.html` needs a **value**: "save the output to page.html".
- `/etc`, the URL — the main things the command works on — are called **operands**.
- Flags can be combined: `-la` means `-l -a`; `-czf` means `-c -z -f`.

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Option** | A dash-word that changes how a command behaves | `-v`, `-o file` |
| **Flag** | An option that is simply on or off | `-v` (verbose) |
| **Option value** | The value an option needs | `5` in `-n 5` |
| **Operand** | A normal argument the command works on | `/etc`, a URL, a filename |
| **Parse** | Read the arguments and work out what each one means | "`-n 5` means count = 5" |
| **Option string** | The list of letters your script accepts, given to getopts | `"vn:o:h"` |

## What is it?

`getopts` is a **built-in Bash command** that reads your script's options for you. You call it in a `while` loop; each time, it gives you the next option letter (and its value, if it has one). It understands combined flags (`-vf`), values written with or without a space (`-n 5` or `-n5`), and tells you when an option is unknown or missing its value.

Do not confuse it with `getopt` (without the "s") — a separate program that behaves differently on different systems. `getopts` is built into every shell and is the safe default.

## Why does it matter?

Compare:

```
./backup.sh /var/www 14 yes /mnt/backups
./backup.sh -k 14 -v -d /mnt/backups /var/www
```

In the first one, you must remember that "the second argument is how many days to keep" and "the third is verbose". In the second, every value explains itself, the order does not matter, and new options can be added later without breaking anyone.

Teams build many small internal tools in Bash: deploy helpers, log collectors, cleanup jobs. Clear options with a `-h` help screen are what make them usable by others.

## When and where do you use it?

- When a script has **more than one or two optional settings**.
- When you want flags in **any order** and combinable (`-vf`).
- When teammates, cron jobs or CI pipelines run the script with different settings.
- For one or two required values only, plain `$1` and `$2` are still fine.

## Concepts one by one

### 1. The option string — telling getopts what to accept

<Explain>
<What>
A short text listing every option letter your script accepts. A colon after a letter means "this option needs a value".
</What>
<Why>
getopts needs to know which letters are valid and which ones take a value, so it can read `-n 5` correctly and reject `-x`.
</Why>
<When>
Every time you use getopts — it is the first thing you write.
</When>
<Where>
In the `while getopts "…" opt` line.
</Where>
<How>
Write the letters in any order. `v` = flag, `n:` = needs a value. Start the string with `:` (for example `":vn:h"`) so you can print your own friendly error messages.
</How>
</Explain>

| Option string part | Meaning |
| --- | --- |
| `:` at the very start | "I will handle errors myself" (recommended) |
| `v` | `-v` is a flag (no value) |
| `n:` | `-n` needs a value, e.g. `-n 5` |
| `o:` | `-o` needs a value, e.g. `-o out.txt` |
| `h` | `-h` is a flag (help) |

So `":vn:o:h"` means: accept `-v`, `-n VALUE`, `-o VALUE` and `-h`, and let me handle errors.

### 2. The getopts loop

<Explain>
<What>
A `while` loop that calls getopts again and again. Each call puts the **next option letter** into a variable (usually `opt`). When there are no options left, getopts fails and the loop ends.
</What>
<Why>
Options can come in any order and any number, so you need to look at them one at a time.
</Why>
<When>
At the start of the script, before the real work.
</When>
<Where>
Usually combined with a `case` that decides what each letter does.
</Where>
<How>
`while getopts ":vn:" opt; do case "$opt" in v) …;; n) …;; esac; done`.
</How>
</Explain>

```bash
cat > opts-demo.sh <<'EOF'
#!/usr/bin/env bash
verbose=false
count=1

while getopts ":vn:" opt; do
  echo "getopts found: -$opt"
  case "$opt" in
    v) verbose=true ;;
    n) count="$OPTARG" ;;
  esac
done

echo "verbose=$verbose count=$count"
EOF
chmod +x opts-demo.sh

./opts-demo.sh
echo "---"
./opts-demo.sh -v -n 5
echo "---"
./opts-demo.sh -n3 -v
```

```text output
verbose=false count=1
---
getopts found: -v
getopts found: -n
verbose=true count=5
---
getopts found: -n
getopts found: -v
verbose=true count=3
```

Line by line:

- `verbose=false` and `count=1` — **default values**, used when no option is given.
- `while getopts ":vn:" opt; do` — read the next option into `opt`.
- `v) verbose=true ;;` — if the letter was `v`, switch verbose on.
- `n) count="$OPTARG" ;;` — `-n` takes a value; getopts puts it in `OPTARG`.
- Run 1: no options, so defaults are used. Run 2: two options. Run 3: different order and `-n3` written without a space — still works.

### 3. `OPTARG` — the value of an option

<Explain>
<What>
A variable that getopts fills with the value of the current option, for every letter followed by `:` in the option string.
</What>
<Why>
So you can store the value: a count, a filename, a time.
</Why>
<When>
Inside the `case` branch of an option that takes a value.
</When>
<Where>
`-o file`, `-n number`, `-u username`, `-s "2 hours ago"`.
</Where>
<How>
Copy it right away into a named variable: `o) output="$OPTARG" ;;`. Then **check** it — getopts only makes sure a value exists, not that it is sensible.
</How>
</Explain>

```bash
check_number() {
  local value="$1"
  if [[ $value =~ ^[1-9][0-9]*$ ]]; then
    echo "'$value' is a valid count"
  else
    echo "'$value' is NOT a valid count"
  fi
}
check_number 5
check_number abc
check_number -3
```

```text output
'5' is a valid count
'abc' is NOT a valid count
'-3' is NOT a valid count
```

`^[1-9][0-9]*$` means "starts with a digit 1–9, followed only by digits, and nothing else" — a positive whole number.

### 4. `OPTIND` and `shift` — separating options from operands

<Explain>
<What>
`OPTIND` is a number getopts keeps: the position of the next argument it would read. After the loop, `shift $((OPTIND - 1))` removes all the options, so `"$@"` holds only the operands (files, URLs, names).
</What>
<Why>
Your script usually needs the remaining arguments ("the files to process") without the options mixed in.
</Why>
<When>
Directly after every getopts loop.
</When>
<Where>
Every script that takes both options and operands, like `./fetch.sh -v -n 3 site1.com site2.com`.
</Where>
<How>
`shift $((OPTIND - 1))` right after `done`. Forgetting it is the most common getopts bug.
</How>
</Explain>

```bash
cat > operands.sh <<'EOF'
#!/usr/bin/env bash
while getopts ":vn:" opt; do :; done
echo "Before shift: $# args → $*   (OPTIND=$OPTIND)"
shift $((OPTIND - 1))
echo "After shift:  $# args → $*"
EOF
chmod +x operands.sh
./operands.sh -v -n 3 site1.com site2.com
```

```text output
Before shift: 5 args → -v -n 3 site1.com site2.com   (OPTIND=4)
After shift:  2 args → site1.com site2.com
```

- getopts read `-v`, `-n` and `3` (positions 1–3), so `OPTIND` is 4.
- `shift $((4 - 1))` removes the first three arguments.
- `:` inside the loop is a command that does nothing — used here only to keep the example short.

<Callout type="warning" title="Options must come first">
getopts stops at the first argument that is not an option. In `./script.sh site.com -v`, the `-v` is treated as an operand. Write options before operands, or use `--` to mark the end of options.
</Callout>

### 5. Handling mistakes: unknown options and missing values

<Explain>
<What>
With a leading `:` in the option string, getopts reports two kinds of mistakes through `opt`: `?` for an unknown option, and `:` for an option whose value is missing. In both cases `OPTARG` holds the problem letter.
</What>
<Why>
A typo like `-x` should stop the script with a clear message, not be silently ignored — ignoring it could run a "real" action when the user meant a test.
</Why>
<When>
In every getopts loop.
</When>
<Where>
As the last two branches of the `case`.
</Where>
<How>
Add `:) …` and `\?) …` branches. The backslash in `\?` is needed because a plain `?` in `case` means "any single character".
</How>
</Explain>

```bash
cat > strict.sh <<'EOF'
#!/usr/bin/env bash
while getopts ":vn:" opt; do
  case "$opt" in
    v)  echo "verbose on" ;;
    n)  echo "count = $OPTARG" ;;
    :)  echo "Error: -$OPTARG needs a value" >&2; exit 2 ;;
    \?) echo "Error: unknown option -$OPTARG" >&2; exit 2 ;;
  esac
done
echo "All options OK"
EOF
chmod +x strict.sh

./strict.sh -v -n 4
./strict.sh -x; echo "exit code: $?"
./strict.sh -n; echo "exit code: $?"
```

```text output
verbose on
count = 4
All options OK
Error: unknown option -x
exit code: 2
Error: -n needs a value
exit code: 2
```

### 6. A help screen with `-h`

<Explain>
<What>
A `usage` function that explains every option, shown with `-h` and whenever the user makes a mistake.
</What>
<Why>
Nobody remembers every option — including you, six months later.
</Why>
<When>
In every script that has options.
</When>
<Where>
The top of the script, as a function.
</Where>
<How>
Print it to normal output with exit code 0 when the user asks with `-h`; print it to stderr with exit code 2 after a mistake.
</How>
</Explain>

```bash
usage() {
  cat <<EOF
Usage: fetch.sh [-v] [-n count] [-o file] <url>...

Options:
  -n count   number of requests per URL (default: 1)
  -o file    write results to a file instead of the screen
  -v         show more details
  -h         show this help
EOF
}
usage
```

```text output
Usage: fetch.sh [-v] [-n count] [-o file] <url>...

Options:
  -n count   number of requests per URL (default: 1)
  -o file    write results to a file instead of the screen
  -v         show more details
  -h         show this help
```

The square brackets `[ ]` in a usage line mean "optional"; angle brackets `< >` mean "required"; `...` means "one or more".

### 7. Repeatable options

<Explain>
<What>
Options the user can give several times: `-e a -e b`, or `-vvv` for more and more detail.
</What>
<Why>
Some settings are naturally lists (patterns to exclude, headers to add) or levels (verbosity).
</Why>
<When>
When one value is not enough.
</When>
<Where>
Exclude patterns in backup tools, multiple tags, debug levels.
</Where>
<How>
Add each value to an array: `e) excludes+=("$OPTARG") ;;`. Count a repeated flag: `v) ((++verbosity)) ;;`.
</How>
</Explain>

```bash
cat > repeat.sh <<'EOF'
#!/usr/bin/env bash
verbosity=0
excludes=()
while getopts ":ve:" opt; do
  case "$opt" in
    v) ((++verbosity)) ;;
    e) excludes+=("$OPTARG") ;;
  esac
done
echo "verbosity level: $verbosity"
echo "exclude ${#excludes[@]} pattern(s): ${excludes[*]}"
EOF
chmod +x repeat.sh
./repeat.sh -vvv -e '*.tmp' -e node_modules
```

```text output
verbosity level: 3
exclude 2 pattern(s): *.tmp node_modules
```

### 8. Long options (`--verbose`, `--count=5`) with a manual loop

<Explain>
<What>
A `while` + `case` + `shift` loop that reads arguments one by one and understands both short (`-v`) and long (`--verbose`) options.
</What>
<Why>
getopts does not support long options, but many people prefer them because they are self-explaining.
</Why>
<When>
When readable long options matter more than combined short flags like `-vf`.
</When>
<Where>
Team tools, installers, deploy scripts.
</Where>
<How>
Loop while arguments remain (`(( $# > 0 ))`), match `$1` in a `case`, use `$2` for a value and `shift` an extra time, and `shift` once at the end of every round. `--` ends the options.
</How>
</Explain>

```bash
cat > long.sh <<'EOF'
#!/usr/bin/env bash
verbose=false
count=1
while (( $# > 0 )); do
  case "$1" in
    -v|--verbose) verbose=true ;;
    -n|--count)   count="$2"; shift ;;
    --count=*)    count="${1#*=}" ;;
    --)           shift; break ;;
    -*)           echo "Unknown option: $1" >&2; exit 2 ;;
    *)            break ;;
  esac
  shift
done
echo "verbose=$verbose count=$count operands=$*"
EOF
chmod +x long.sh

./long.sh --verbose --count 4 one two
./long.sh --count=9 -v three
./long.sh --nope; echo "exit code: $?"
```

```text output
verbose=true count=4 operands=one two
verbose=true count=9 operands=three
Unknown option: --nope
exit code: 2
```

- `-n|--count) count="$2"; shift ;;` — the value is the **next** argument, so we shift once extra to skip over it.
- `--count=*) count="${1#*=}"` — for `--count=9`, `${1#*=}` removes everything up to and including `=`, leaving `9`.
- `*) break` — the first non-option argument ends option parsing; everything left is an operand.

## Hands-on

A complete tool with every piece from this lesson. Paste it into a terminal:

```bash
mkdir -p ~/opts-lab && cd ~/opts-lab

cat > fetch.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

usage() {
  cat <<USAGE
Usage: $(basename "$0") [-v] [-n count] [-o file] [-e pattern]... <target>...
  -n count    repeat count (default 1)
  -o file     output file (default: stdout)
  -e pattern  exclude pattern (repeatable)
  -v          verbose (repeat for more: -vv)
  -h          help
USAGE
}

verbosity=0; count=1; output=""; excludes=()

while getopts ":vn:o:e:h" opt; do
  case "$opt" in
    v) ((++verbosity)) ;;
    n) [[ $OPTARG =~ ^[1-9][0-9]*$ ]] || { echo "error: -n needs a positive number, got '$OPTARG'" >&2; exit 2; }
       count="$OPTARG" ;;
    o) output="$OPTARG" ;;
    e) excludes+=("$OPTARG") ;;
    h) usage; exit 0 ;;
    :)  echo "error: -$OPTARG needs a value" >&2; exit 2 ;;
    \?) echo "error: unknown option -$OPTARG" >&2; exit 2 ;;
  esac
done
shift $((OPTIND - 1))

(( $# > 0 )) || { echo "error: at least one target required" >&2; exit 2; }

echo "verbosity=$verbosity count=$count output=${output:-stdout} excludes=(${excludes[*]})"
for t in "$@"; do echo "  target: $t"; done
EOF
chmod +x fetch.sh

./fetch.sh example.com
./fetch.sh -vv -n 3 -o out.txt a.com "b site.com"
./fetch.sh -vn5 -e '*.tmp' -e node_modules site.com
./fetch.sh -n; echo "exit: $?"
./fetch.sh -x site.com; echo "exit: $?"
./fetch.sh -n abc site.com; echo "exit: $?"
./fetch.sh -v; echo "exit: $?"
./fetch.sh site.com -v
./fetch.sh -v -- -weird-name

cd ~ && rm -rf ~/opts-lab
```

```text output
verbosity=0 count=1 output=stdout excludes=()
  target: example.com
verbosity=2 count=3 output=out.txt excludes=()
  target: a.com
  target: b site.com
verbosity=1 count=5 output=stdout excludes=(*.tmp node_modules)
  target: site.com
error: -n needs a value
exit: 2
error: unknown option -x
exit: 2
error: -n needs a positive number, got 'abc'
exit: 2
error: at least one target required
exit: 2
verbosity=0 count=1 output=stdout excludes=()
  target: site.com
  target: -v
verbosity=1 count=1 output=stdout excludes=()
  target: -weird-name
```

Look at the last two runs: `site.com -v` treats `-v` as a target (options must come first), and `--` lets a target start with a dash.

## Real-world example

A log-collection tool an on-call engineer runs during an incident:

```bash
#!/usr/bin/env bash
# collect-logs.sh — bundle recent logs for a service into a tarball
set -euo pipefail

usage() {
  cat <<EOF
Usage: $(basename "$0") [-s since] [-o dir] [-z] <service>...
  -s since   journalctl time, e.g. "2 hours ago" (default: "1 hour ago")
  -o dir     output directory (default: /tmp)
  -z         gzip the bundle
  -h         help
Example: $(basename "$0") -s "30 min ago" -z nginx app
EOF
}

since="1 hour ago"; outdir="/tmp"; compress=false

while getopts ":s:o:zh" opt; do
  case "$opt" in
    s) since="$OPTARG" ;;
    o) outdir="$OPTARG" ;;
    z) compress=true ;;
    h) usage; exit 0 ;;
    :)  echo "-$OPTARG needs a value" >&2; exit 2 ;;
    \?) echo "unknown option -$OPTARG" >&2; usage >&2; exit 2 ;;
  esac
done
shift $((OPTIND - 1))
(( $# > 0 )) || { usage >&2; exit 2; }
[[ -d $outdir && -w $outdir ]] || { echo "cannot write to $outdir" >&2; exit 1; }

work="$(mktemp -d)"
for svc in "$@"; do
  [[ $svc =~ ^[a-zA-Z0-9@._-]+$ ]] || { echo "skipping invalid name: $svc" >&2; continue; }
  journalctl -u "$svc" --since "$since" --no-pager > "$work/$svc.log" || true
done

bundle="$outdir/logs-$(hostname)-$(date +%Y%m%d-%H%M%S).tar"
tar_flags=(-c)
if $compress; then bundle+=".gz"; tar_flags+=(-z); fi
tar -C "$work" "${tar_flags[@]}" -f "$bundle" .
rm -rf "$work"
echo "$bundle"
```

The service names are validated with an allow-list regex before they reach `journalctl`, and the only thing printed to stdout is the bundle path — so another script can do `bundle=$(./collect-logs.sh -z nginx)`.

## Common mistakes

- **Forgetting `shift $((OPTIND - 1))`** — options are still in `"$@"` and get treated as operands.
- **Missing `:` after a letter** that needs a value — `-n 5` then treats `5` as an operand.
- **Writing `?)` instead of `\?)`** in `case` — `?` matches any single character, so it catches every option.
- **No leading `:`** — getopts prints its own cryptic errors and sets `opt` to `?` for both error kinds.
- **Putting options after operands** — getopts stops at the first operand.
- **Calling getopts twice in one shell** (e.g. in a function used twice) without resetting `OPTIND=1` first.
- **Trusting `OPTARG`** — it is just user input; validate numbers, paths and names.
- **Expecting getopts to handle `--long`** — it cannot.

## Security lens

<Callout type="security">
Options are user input with extra structure. Parse them strictly and fail closed.
</Callout>

- **Unknown option → exit non-zero.** Silently ignoring a typo like `-dryrun` can turn a dry run into a real deletion.
- **Validate every `OPTARG`** with an allow-list or anchored regex before it reaches a path, a command or a URL.
- **Support `--`** so filenames beginning with `-` are not parsed as options; pass `--` on to the commands you call (`rm -- "$f"`).
- **Dangerous defaults are a design bug:** make destructive behaviour opt-in (`-f`/`--force`), and the safe path the default.
- **Do not accept secrets as options** (`-p password`) — they show up in `ps`, logs and shell history. Read them from an environment variable, a file, or a prompt with `read -s`.

## Interview questions

<QA q="How does getopts work?">
getopts is a shell built-in called in a while loop. Each call reads the next option from the arguments according to an option string, stores the option letter in a variable and, for options declared with a trailing colon, stores the value in OPTARG. OPTIND tracks the next argument index. When options run out it returns non-zero, and the script runs shift $((OPTIND - 1)) to leave only the operands.
</QA>

<QA q="What does the leading colon in the getopts option string do?">
It enables silent error reporting. getopts no longer prints its own messages; instead an unknown option sets the variable to ? and a missing value sets it to :, with the offending option letter in OPTARG, so the script can print its own clear errors and usage.
</QA>

<QA q="What is the difference between getopts and getopt?">
getopts is a POSIX shell built-in, portable and consistent, but only supports single-letter options. getopt is an external program (the util-linux version) that also supports long options and option reordering, but its behaviour differs between systems such as Linux and macOS. For long options in portable scripts, a manual while/case/shift loop is common.
</QA>

<QA q="Why should unknown options cause the script to fail?">
Because a mistyped option would otherwise be ignored and the script would run with default behaviour the user did not intend, for example running for real when the user meant a dry run. Failing with a usage message and a non-zero exit code makes the mistake visible and safe.
</QA>
