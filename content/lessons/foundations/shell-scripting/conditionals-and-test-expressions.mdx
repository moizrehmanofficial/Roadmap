<Callout type="tip" title="In one minute">
A **conditional** lets a script choose what to do. In Bash, `if` runs a command and looks at its **exit status** — a number every command returns when it finishes. `0` means success (treated as **true**); any other number means failure (**false**). To check things like "does this file exist?" or "is this number bigger than 80?", you use small checking commands called **tests**: `[[ … ]]` for files and text, `(( … ))` for numbers. Use `case` when one value can match many options.
</Callout>

## Start from zero

### What is a "decision" in a program?

You make decisions all day without thinking about it:

<Callout type="analogy">
**If** it is raining, take an umbrella. **Otherwise**, wear sunglasses.

**If** the phone battery is below 20%, plug it in.

**If** the shop is open, buy bread. **Else if** the other shop is open, go there. **Else**, go home.
</Callout>

Each sentence has two parts:

1. A **condition** — a question whose answer is yes or no ("is it raining?").
2. An **action** — what to do depending on the answer ("take an umbrella").

A script without conditions is like a person who takes an umbrella every day, even in summer. It does the same steps every time, no matter what is happening. Conditions make a script **react** to the situation: a missing file, a full disk, a stopped service, a wrong argument.

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Command** | Any instruction you type in the terminal | `ls`, `mkdir logs`, `grep error app.log` |
| **Condition** | A yes/no question the script asks | "Does the file `app.log` exist?" |
| **True / false** | The answer to the condition | yes = true, no = false |
| **Exit status** | A number a command gives back when it finishes, to say whether it worked | `0` = worked, `1` (or more) = did not work |
| **Test** | A small command whose only job is to answer a yes/no question | `[[ -f app.log ]]` asks "is `app.log` a file?" |
| **Branch** | One of the possible paths the script can take | the "then" part or the "else" part |

Keep this table in mind; every section below uses these words.

## What is it?

A **conditional** is a piece of code that says: "check something; if the answer is yes, run these commands; if no, run those commands (or nothing)."

In Bash, conditionals are written with `if`, `elif`, `else` and `case`. The "something" you check is always a **command**, and Bash decides yes/no from that command's **exit status**.

## Why does it matter?

- **Without conditions, scripts are dangerous.** A backup script that does not check whether the backup folder exists will happily write to the wrong place or fail halfway.
- **With conditions, scripts become smart and safe.** They can stop early with a clear message ("config file missing"), skip work that is already done, and choose different behaviour for development and production.
- **Every job role uses them:** a DevOps engineer checks "is the service running?", a cloud engineer checks "does this bucket already exist?", a security analyst checks "are there more than 20 failed logins?".

## When and where do you use it?

- **At the top of a script** — to check that the input is correct before doing anything.
- **Before using a file or folder** — to check it exists.
- **Before running a tool** — to check it is installed.
- **For monitoring** — "if disk usage is over 90%, send an alert".
- **For choices** — "if the environment is prod, ask for confirmation".

You will find conditionals in deploy scripts, CI/CD pipelines, Docker entrypoint scripts, cron jobs, install scripts and security audit scripts.

## Concepts one by one

### 1. Exit status — every command reports success or failure

<Explain>
<What>
A number between 0 and 255 that every command gives back when it finishes. `0` means "I succeeded". Any other number means "something went wrong" — different numbers can mean different problems.
</What>
<Why>
The script needs a way to know whether the previous step worked. A human reads the screen; a script reads the exit status.
</Why>
<When>
Every time a command runs. You check it whenever the next step depends on the previous one.
</When>
<Where>
It is stored automatically in the special variable `$?` right after each command. `if`, `&&` and `||` all read it for you.
</Where>
<How>
Run a command, then print `$?` immediately. Each new command overwrites `$?`, so read it straight away.
</How>
</Explain>

<Callout type="analogy">
Think of a delivery rider. When he comes back, he says either "delivered" (0) or a problem code: "address not found" (1), "customer not home" (2). The shop owner decides what to do next from that code. The exit status is the command's "delivered / not delivered" report.
</Callout>

```bash
ls /etc > /dev/null
echo "ls /etc finished with: $?"

ls /folder-that-does-not-exist 2> /dev/null
echo "ls on a missing folder finished with: $?"
```

```text output
ls /etc finished with: 0
ls on a missing folder finished with: 2
```

Line by line:

- `ls /etc > /dev/null` — list the `/etc` folder. `> /dev/null` throws the listing away, because we only care whether it worked.
- `echo "… $?"` — print the exit status of the previous command. `/etc` exists, so it is `0`.
- `2> /dev/null` — hide the error message of the second `ls`.
- The second `$?` is `2`, which is how `ls` says "serious trouble, e.g. the folder does not exist".

### 2. `if … then … fi` — do something only when a condition is true

<Explain>
<What>
The basic decision block. "If this command succeeds, run the commands between `then` and `fi`. If it fails, skip them."
</What>
<Why>
So that some steps only happen when they make sense — for example, only print "errors found" when there really are errors.
</Why>
<When>
Whenever one or more commands should run only in a certain situation.
</When>
<Where>
Anywhere in a script or even directly in the terminal.
</Where>
<How>
Write `if`, then the command to check, then `; then`, the commands to run, and finally `fi` (it is "if" written backwards and means "end of if").
</How>
</Explain>

```bash
if CONDITION_COMMAND; then
  COMMANDS_TO_RUN_WHEN_TRUE
fi
```

A real example. `grep -q` searches for text quietly: it prints nothing, it only returns exit status 0 (found) or 1 (not found) — perfect for `if`.

```bash
printf 'started\nERROR disk full\nstopped\n' > app.log

if grep -q "ERROR" app.log; then
  echo "Errors found in app.log"
fi
echo "Script finished"
```

```text output
Errors found in app.log
Script finished
```

Line by line:

- `printf … > app.log` — create a small sample log file with three lines.
- `if grep -q "ERROR" app.log; then` — run `grep`. It finds "ERROR", so its exit status is 0 → true.
- `echo "Errors found in app.log"` — runs because the condition was true. It is indented with two spaces only to make it easy to read; Bash does not require it.
- `fi` — end of the `if` block.
- `echo "Script finished"` — outside the `if`, so it always runs.

If `app.log` did not contain "ERROR", only `Script finished` would be printed.

### 3. `else` — what to do when the condition is false

<Explain>
<What>
A second branch that runs only when the condition is false.
</What>
<Why>
Often you want to do one thing **or** the other — never nothing. For example, print "running" or "stopped".
</Why>
<When>
When there are exactly two outcomes.
</When>
<Where>
Between the `then` commands and `fi`.
</Where>
<How>
Add `else` on its own line, followed by the commands for the "no" case.
</How>
</Explain>

```bash
if ping -c 1 -W 1 127.0.0.1 > /dev/null; then
  echo "Network is working"
else
  echo "Network is NOT working"
fi
```

```text output
Network is working
```

`ping -c 1` sends one test packet. `127.0.0.1` is your own computer, so it always answers and the first branch runs. Change it to an address that does not exist (e.g. `10.255.255.1`) and you will see the `else` branch.

### 4. `elif` — more than two possibilities

<Explain>
<What>
"else if". Lets you check a second (third, fourth…) condition when the first one is false.
</What>
<Why>
Real situations often have more than two answers: OK / warning / critical.
</Why>
<When>
When you have several conditions to check in order, and only the first true one should run.
</When>
<Where>
After the first `then` block and before `else`.
</Where>
<How>
Bash checks the conditions from top to bottom. The first one that is true runs its block, and all the others are skipped. If none is true, `else` runs.
</How>
</Explain>

```bash
battery=15

if (( battery < 10 )); then
  echo "Critical: plug in now"
elif (( battery < 20 )); then
  echo "Low battery"
else
  echo "Battery OK"
fi
```

```text output
Low battery
```

- `battery=15` — store 15 in a variable.
- `(( battery < 10 ))` — is 15 less than 10? No → skip.
- `(( battery < 20 ))` — is 15 less than 20? Yes → print "Low battery" and **stop checking**.
- `else` is skipped because a branch already ran.

(`(( … ))` is the number test, explained in section 8.)

### 5. Tests — commands that answer a yes/no question

<Explain>
<What>
A test is a special command whose only job is to check something and return 0 (yes) or 1 (no). In Bash the main test is written `[[ … ]]` — two square brackets with the question inside.
</What>
<Why>
Commands like `grep` and `ping` already answer a question. But for questions such as "is this a folder?" or "is this text empty?" there is no ordinary command — so we use a test.
</Why>
<When>
Whenever you need to check a file, a folder, some text, or a pattern.
</When>
<Where>
Mostly right after `if`, `elif` or `while`, and before `&&` / `||`.
</Where>
<How>
Write `[[`, a space, the question, a space, `]]`. The spaces are required: `[[` is a word just like `ls`, and words must be separated by spaces.
</How>
</Explain>

```bash
[[ 5 == 5 ]]; echo "5 == 5 gives: $?"
[[ 5 == 6 ]]; echo "5 == 6 gives: $?"
```

```text output
5 == 5 gives: 0
5 == 6 gives: 1
```

This proves a test is "just a command" with an exit status — exactly what `if` needs.

There are three test styles you will see:

| Style | Where it works | Use it for |
| --- | --- | --- |
| `[[ … ]]` | Bash (and zsh) | Files, text, patterns — **use this in Bash scripts** |
| `[ … ]` (or `test …`) | Every shell, including `sh` | The same checks, but older and easier to break with spaces |
| `(( … ))` | Bash | Numbers |

Prefer `[[ … ]]` because it does not break when a variable is empty or contains spaces, and it allows `&&` and `||` inside it.

### 6. Checking files and folders

<Explain>
<What>
Special test options (called **operators**) that ask questions about a path: does it exist, is it a file, is it a folder, can I read it?
</What>
<Why>
Scripts constantly work with files: configs, logs, backups. Using a file that is missing gives confusing errors halfway through. Checking first gives a clear message.
</Why>
<When>
Before reading, writing, deleting or running a file, or before creating a folder.
</When>
<Where>
Inside `[[ … ]]`, for example `[[ -f "$config" ]]`.
</Where>
<How>
Write the operator (a dash and a letter), a space, then the path. Put `!` before it to ask the opposite ("does NOT exist").
</How>
</Explain>

| Operator | Question it asks |
| --- | --- |
| `-e path` | Does it **exist** (file, folder, anything)? |
| `-f path` | Is it a regular **file**? |
| `-d path` | Is it a **directory** (folder)? |
| `-s path` | Does it exist and is it **not empty** (size > 0)? |
| `-r path` | Can I **read** it? |
| `-w path` | Can I **write** to it? |
| `-x path` | Can I **execute** (run) it? |
| `-L path` | Is it a symbolic **link**? |

```bash
mkdir -p demo-folder
touch empty.txt
echo "hello" > notes.txt

for path in notes.txt empty.txt demo-folder missing.txt; do
  if [[ -d $path ]]; then
    echo "$path → is a folder"
  elif [[ -s $path ]]; then
    echo "$path → is a file with content"
  elif [[ -f $path ]]; then
    echo "$path → is an empty file"
  else
    echo "$path → does not exist"
  fi
done
```

```text output
notes.txt → is a file with content
empty.txt → is an empty file
demo-folder → is a folder
missing.txt → does not exist
```

- `mkdir -p`, `touch`, `echo … >` — create a folder, an empty file, and a file with text.
- `for path in …; do … done` — repeat the check for each name (loops are the next lesson; here it just saves typing).
- The `if / elif / elif / else` chain asks the questions in order: folder? non-empty? file? — and the first "yes" wins.

A very common pattern — stop the script if a file is missing:

```bash
config="settings.conf"
if [[ ! -f $config ]]; then
  echo "Error: $config not found" >&2
  exit 1
fi
```

```text output
Error: settings.conf not found
```

`!` means "not". `>&2` sends the message to the error stream (stderr), and `exit 1` stops the script with a failure status so whoever ran it knows it failed.

### 7. Comparing text (strings)

<Explain>
<What>
Tests that compare pieces of text: are they equal, different, empty, or do they match a pattern?
</What>
<Why>
Scripts receive text all the time: a username, an environment name like "prod", a filename, a command's output. You decide what to do based on it.
</Why>
<When>
Checking user input, environment names, filenames, versions and command output.
</When>
<Where>
Inside `[[ … ]]`.
</Where>
<How>
Use `==` for equal, `!=` for not equal, `-z` for "empty", `-n` for "not empty", a `*` pattern for "matches", and `=~` for a regular-expression match.
</How>
</Explain>

| Test | True when |
| --- | --- |
| `[[ $a == $b ]]` | `a` and `b` are the same text |
| `[[ $a != $b ]]` | they are different |
| `[[ -z $a ]]` | `a` is empty (zero length) |
| `[[ -n $a ]]` | `a` is not empty |
| `[[ $file == *.log ]]` | `file` ends with `.log` (wildcard pattern) |
| `[[ $ver =~ ^v[0-9]+ ]]` | `ver` matches the regular expression |

```bash
env="prod"
name=""
file="error.log"

if [[ $env == "prod" ]]; then echo "1) This is production"; fi
if [[ $env != "dev" ]]; then echo "2) This is not dev"; fi
if [[ -z $name ]]; then echo "3) name is empty"; fi
if [[ $file == *.log ]]; then echo "4) $file is a log file"; fi
```

```text output
1) This is production
2) This is not dev
3) name is empty
4) error.log is a log file
```

- `env="prod"` — no spaces around `=` when you create a variable.
- `[[ $env == "prod" ]]` — spaces **around** `==` are required inside the test.
- `-z $name` — `name` holds nothing, so "is empty" is true.
- `*.log` — `*` means "any characters", so it matches anything ending in `.log`.

### 8. Comparing numbers with `(( … ))`

<Explain>
<What>
Double round brackets: Bash's maths area. Inside them you can compare numbers with normal symbols: `<`, `>`, `<=`, `>=`, `==`, `!=`.
</What>
<Why>
Many decisions are about amounts: disk usage, number of errors, CPU load, retry count, battery level.
</Why>
<When>
Any time you compare whole numbers.
</When>
<Where>
After `if`, `elif`, `while`, or with `&&` / `||`.
</Where>
<How>
Write the comparison like in maths: `(( disk > 80 ))`. You do not need `$` in front of variable names inside `(( … ))`.
</How>
</Explain>

```bash
disk=85

if (( disk >= 90 )); then
  echo "CRITICAL: disk ${disk}% full"
elif (( disk >= 80 )); then
  echo "WARNING: disk ${disk}% full"
else
  echo "OK: disk ${disk}% full"
fi
```

```text output
WARNING: disk 85% full
```

<Callout type="warning" title="Do not compare numbers with [[ … ]] and < >">
Inside `[[ … ]]`, `<` and `>` compare text **alphabetically**, like words in a dictionary. "10" comes before "9" in the dictionary (because "1" comes before "9"), so the result is wrong:

```bash
[[ 10 < 9 ]] && echo "text compare: 10 < 9 is TRUE (wrong for numbers!)"
(( 10 < 9 )) || echo "number compare: 10 < 9 is false (correct)"
```

```text output
text compare: 10 < 9 is TRUE (wrong for numbers!)
number compare: 10 < 9 is false (correct)
```

For numbers, always use `(( … ))`.
</Callout>

You may also see the older number operators inside `[[ … ]]` or `[ … ]`: `-eq` (equal), `-ne` (not equal), `-lt` (less than), `-le` (less or equal), `-gt` (greater than), `-ge` (greater or equal). For example `[ "$disk" -gt 80 ]` is the same as `(( disk > 80 ))`.

### 9. Combining conditions: and, or, not

<Explain>
<What>
Ways to join several questions into one: **and** (`&&`) — both must be true; **or** (`||`) — at least one must be true; **not** (`!`) — flip the answer.
</What>
<Why>
Real rules are often combined: "if the file exists **and** is not empty", "if the environment is dev **or** test".
</Why>
<When>
When one condition is not enough.
</When>
<Where>
Inside `[[ … ]]` and `(( … ))`, or between whole commands.
</Where>
<How>
`[[ A && B ]]`, `[[ A || B ]]`, `[[ ! A ]]`, `(( x > 0 && x < 100 ))`.
</How>
</Explain>

```bash
age=25
country="US"

if (( age >= 18 && age <= 60 )); then echo "Age is between 18 and 60"; fi
if [[ $country == "US" || $country == "AE" ]]; then echo "Country is US or AE"; fi
if [[ ! -d /this/folder/does/not/exist ]]; then echo "Folder is missing"; fi
```

```text output
Age is between 18 and 60
Country is US or AE
Folder is missing
```

### 10. Short decisions without `if`: `&&` and `||`

<Explain>
<What>
A one-line way to write simple decisions. `A && B` means "run B only if A succeeded". `A || B` means "run B only if A failed".
</What>
<Why>
Small checks become short and readable, like "create the folder if it does not exist".
</Why>
<When>
For one simple action. For anything bigger, use a full `if`.
</When>
<Where>
Very common at the top of scripts and in one-liners in the terminal.
</Where>
<How>
Put the check first, then `&&` or `||`, then the action. Use curly braces `{ …; }` to group more than one action.
</How>
</Explain>

```bash
[[ -d backups ]] || mkdir backups && echo "backups folder is ready"
command -v git > /dev/null && echo "git is installed"
command -v nonexistent-tool > /dev/null || echo "nonexistent-tool is NOT installed"
```

```text output
backups folder is ready
git is installed
nonexistent-tool is NOT installed
```

- `[[ -d backups ]] || mkdir backups` — "is there a backups folder? If not, create it."
- `command -v git` — prints where `git` is installed, and succeeds only if it exists. `> /dev/null` hides the path.

<Callout type="warning" title="A && B || C is not the same as if/else">
If `B` fails, `C` runs too. Example: `true && false || echo "surprise"` prints "surprise", even though the first command succeeded. When the middle command can fail, write a real `if … else … fi`.
</Callout>

### 11. `case` — choosing from many options

<Explain>
<What>
A clean way to compare **one value** with many possible patterns and run the matching block.
</What>
<Why>
A long `if / elif / elif / elif` chain checking the same variable is hard to read. `case` lists the options like a menu.
</Why>
<When>
Menu-style choices: subcommands (`start`, `stop`, `restart`), file types, yes/no answers, environment names.
</When>
<Where>
Very common in service scripts, installers and tools that take a command as the first argument.
</Where>
<How>
`case "$value" in`, then each option as `pattern) commands ;;`, then `esac` ("case" backwards). `*)` at the end catches everything else.
</How>
</Explain>

<Callout type="analogy">
A lift (elevator) panel: you press one button, and the lift goes to that floor. Button "G" → ground floor, "1" → first floor, any other button → "invalid floor". `case` is that panel.
</Callout>

```bash
for file in report.pdf backup.tar.gz photo.JPG notes.txt; do
  case "$file" in
    *.pdf)               echo "$file → PDF document" ;;
    *.tar.gz|*.zip)      echo "$file → archive" ;;
    *.jpg|*.JPG|*.png)   echo "$file → image" ;;
    *)                   echo "$file → unknown type" ;;
  esac
done
```

```text output
report.pdf → PDF document
backup.tar.gz → archive
photo.JPG → image
notes.txt → unknown type
```

- `case "$file" in` — start comparing the value of `file`.
- `*.pdf)` — a pattern; `*` means "anything".
- `*.tar.gz|*.zip)` — `|` means "or" between patterns.
- `;;` — ends each option (like a full stop).
- `*)` — the default option when nothing else matched.
- `esac` — end of the `case` block.

### 12. Putting it together: guard clauses

A **guard clause** is a check at the top of a script that stops it immediately if something is wrong — like a security guard checking your ID before you enter the building. The rest of the script can then assume everything is fine.

```bash
#!/usr/bin/env bash
set -euo pipefail

(( $# == 1 )) || { echo "usage: $0 <file>" >&2; exit 2; }
file="$1"
[[ -e $file ]] || { echo "✖ $file does not exist" >&2; exit 1; }
[[ -r $file ]] || { echo "✖ $file is not readable" >&2; exit 1; }

size=$(stat -c %s "$file")
if (( size == 0 )); then
  echo "⚠ $file is empty"
else
  echo "✓ $file ($size bytes)"
fi
```

- `$#` — the number of arguments given to the script. We require exactly 1.
- `{ …; exit 2; }` — run the message and the exit together.
- `stat -c %s` — prints a file's size in bytes.

## Hands-on

Copy this whole block into a terminal. It creates a practice folder, tries everything from this lesson, and cleans up.

```bash
mkdir -p ~/cond-lab && cd ~/cond-lab && touch app.log && echo "x" > data.txt

# 1. Exit status is the condition
grep -q x data.txt; echo "grep status: $?"

# 2. File tests
for p in data.txt app.log missing.txt ~/cond-lab; do
  if [[ -d $p ]]; then echo "$p: directory"
  elif [[ -s $p ]]; then echo "$p: file with content"
  elif [[ -f $p ]]; then echo "$p: empty file"
  else echo "$p: does not exist"; fi
done

# 3. Text vs number comparison — the classic trap
[[ 10 < 9 ]] && echo "text: 10 < 9 is TRUE (alphabetical)"
(( 10 < 9 )) || echo "numbers: 10 < 9 is false"

# 4. case and regex
for f in report.pdf backup.tar.gz notes.txt; do
  case "$f" in
    *.tar.gz|*.tgz) echo "$f → archive" ;;

ver="v2.14.3"; [[ $ver =~ ^v([0-9]+)\. ]] && echo "major version ${BASH_REMATCH[1]}"

# 5. The a && b || c trap
true && false || echo "this prints even though the first command succeeded"

# 6. A checker script with guard clauses
cat > check.sh <<'EOF'

chmod +x check.sh
```

## Real-world example

A check that runs in a CI pipeline before anything is deployed to production. Each `if` is a rule the team learned the hard way:

```bash
#!/usr/bin/env bash
# predeploy-check.sh — refuse unsafe deployments
set -euo pipefail

env="${1:-}"
branch="$(git rev-parse --abbrev-ref HEAD)"

case "$env" in
  staging) ;;
  prod)
    if [[ $branch != main ]]; then
      echo "✖ Production deploys only from main (current: $branch)" >&2; exit 1
    fi
    if [[ -n $(git status --porcelain) ]]; then
      echo "✖ Working tree has uncommitted changes" >&2; exit 1
    fi
    hour=$((10#$(date +%H)))
    if (( hour < 9 || hour >= 18 )) && [[ ${FORCE:-} != yes ]]; then
      echo "✖ Outside deploy window (09:00–18:00). Set FORCE=yes to override." >&2; exit 1
    fi
    ;;
  *) echo "usage: $0 {staging|prod}" >&2; exit 2 ;;
esac

[[ -f dist/index.js ]] || { echo "✖ Build output missing — run the build first" >&2; exit 1; }
echo "✓ Checks passed for $env"
```

What each rule protects against:

- **Only from `main`** — nobody ships half-finished code from a feature branch.
- **No uncommitted changes** — what is deployed is exactly what is in Git.
- **Deploy window** — no risky releases at night when nobody is around to fix problems (`10#` makes `08` and `09` count as normal numbers).
- **Build output exists** — the deploy does not upload an empty folder.

## Common mistakes

- **Missing spaces inside brackets.** `[[-f $f]]` fails. Write `[[ -f $f ]]` — brackets are separate words.
- **Spaces around `=` when creating a variable.** `env = prod` runs a command called `env`. Write `env=prod`.
- **Comparing numbers with `<` / `>` inside `[[ … ]]`** — compares alphabetically. Use `(( … ))`.
- **Wrapping a command in brackets.** `if [ grep -q x file ]` is wrong. Just write `if grep -q x file`.
- **Forgetting `fi`, `esac` or `;;`.**
- **Using `[ … ]` with unquoted variables.** `[ $name == admin ]` breaks when `name` is empty. Use `[[ … ]]` or quote `"$name"`.
- **Treating `a && b || c` as if/else.**

## Security lens

<Callout type="security">
Conditions are where scripts enforce rules. A careless check is a rule that someone can get around.
</Callout>

- **Allow-list, do not block-list.** `[[ $env =~ ^(dev|staging|prod)$ ]]` accepts exactly three values. Checking "is not prod" accepts every typo and every strange input.
- **Anchor regular expressions** with `^` (start) and `$` (end). `[[ $input =~ [0-9]+ ]]` also matches `abc1; rm -rf /`. Use `^[0-9]+$`.
- **Quote the right side of `==`** when it comes from a user: in `[[ $a == $b ]]` an unquoted `$b` is a pattern, so a user typing `*` matches everything. Write `[[ $a == "$b" ]]`.
- **Fail closed.** When a check fails, stop with a non-zero exit code. Do not continue "just in case".
- **Refuse dangerous situations on purpose**, for example: `(( EUID == 0 )) && { echo "do not run as root" >&2; exit 1; }`.

## Interview questions

<QA q="How does if decide true or false in Bash?">
It runs a command and checks its exit status. Exit status 0 means success and counts as true, so the then-branch runs. Any other value counts as false, so the elif/else branch runs. Tests like `[[ ]]`, `[ ]` and `(( ))` are themselves commands that return 0 or 1, which is why they work with if.
</QA>

<QA q="What is the difference between [ ] and [[ ]]?">
`[ ]` is the old POSIX test command that works in every shell; variables inside it must be quoted or they break when empty or containing spaces. `[[ ]]` is a Bash keyword: it does not split variables, allows && and || inside, supports wildcard patterns with == and regular expressions with =~. Use `[[ ]]` in Bash scripts and `[ ]` only when the script must run under plain sh.
</QA>

<QA q="How do you compare numbers, and why not use < inside [[ ]]?">
Use `(( a < b ))` or the operators -lt, -gt, -eq and so on. Inside `[[ ]]`, < and > compare text alphabetically, so "10" < "9" is true, which is wrong for numbers.
</QA>

<QA q="When would you use case instead of if/elif?">
When one value is compared against several possible values or patterns, such as a subcommand (start/stop/restart), a file extension or an environment name. case is shorter and easier to read, supports patterns and alternatives with |, and has a default branch.
</QA>

<QA q="Why is a && b || c not the same as if/else?">
In a && b || c, c runs if a fails or if b fails. In an if/else, the else part runs only when a fails. If b can fail, a real if/else must be used.
</QA>

## Key terms

<Terms>
  <Term name="Condition">A yes/no question the script asks before deciding what to do.</Term>
  <Term name="Exit status">The number a command returns when it finishes; 0 means success. Stored in `$?`.</Term>
  <Term name="Test">A small command that checks something and returns 0 (yes) or 1 (no), such as `[[ -f file ]]`.</Term>
  <Term name="Branch">One of the paths the script can take: then, elif or else.</Term>
  <Term name="Operator">A symbol or option inside a test, such as `-f`, `==`, `>=`.</Term>
  <Term name="(( ))">Bash's maths area, used to compare numbers.</Term>
  <Term name="case">Compares one value with many patterns, like a menu.</Term>
  <Term name="Guard clause">A check at the top of a script that stops it early when something is wrong.</Term>
</Terms>
