<BigIdea>
<Tr>
<En>
A **conditional** lets a script **choose**: "**if** the disk is over 90% full, send an alert, **otherwise** do nothing". In Bash, `if` runs a command and looks at its **exit status**: `0` means success (**true**), anything else means failure (**false**).
</En>
<Ur>
**Conditional** script ko **faisla** karne deta hai: "**agar** disk 90% se zyada bhari ho to alert bhejo, **warna** kuch na karo". Bash me `if` ek command chala kar us ka **exit status** dekhta hai: `0` matlab kamyabi (**sach**), kuch aur matlab nakami (**jhoot**).
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- `if … then … fi`: run something only when a condition is true.
- `else`, `elif`: what to do otherwise, or check more conditions.
- **Tests**: small commands that answer yes/no:
  - `[[ … ]]` for **files** and **text**: `[[ -f app.log ]]`, `[[ $env == prod ]]`
  - `(( … ))` for **numbers**: `(( disk > 80 ))`
- `case`: pick one option from many, like a menu.

</En>
<Ur>

- `if … then … fi`: kuch sirf tab chalao jab shart sach ho.
- `else`, `elif`: warna kya karna hai, ya mazeed sharten check karna.
- **Tests**: chhoti commands jo haan/nahi jawab deti hain:
  - **files** aur **text** ke liye `[[ … ]]`: `[[ -f app.log ]]`, `[[ $env == prod ]]`
  - **numbers** ke liye `(( … ))`: `(( disk > 80 ))`
- `case`: kai ikhtiyarat me se ek chunna, menu ki tarah.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Without conditions, scripts are dangerous**: a backup script that doesn't check the folder exists writes to the wrong place or fails halfway.
- **With conditions, scripts are smart and safe**: they stop early with a clear message, skip work already done, and behave differently in development and production.
- Every role uses them: "is the service running?", "does this bucket exist?", "more than 20 failed logins?".

</En>
<Ur>

- **Sharton ke baghair scripts khatarnak hain**: jo backup script folder ka hona check na kare wo ghalat jagah likhti hai ya aadhe me fail hoti hai.
- **Sharton ke saath scripts samajhdar aur mehfooz**: saaf paigham ke saath jaldi ruk jati hain, ho chuka kaam chhor deti hain, aur development aur production me alag rawayya rakhti hain.
- Har kirdaar inhe istemal karta hai: "service chal rahi hai?", "ye bucket mojood hai?", "20 se zyada fail logins?".

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- at the **top of a script**, to check the input before doing anything
- **before using a file** or folder
- **before running a tool**, to check it's installed
- for **monitoring**: "if disk is over 90%, alert"
- for **choices**: "if the environment is prod, ask for confirmation"

</En>
<Ur>

- **script ke shuru** me, kuch karne se pehle input check karne ke liye
- kisi **file ya folder ko istemal karne se pehle**
- **tool chalane se pehle**, check karne ke liye ke install hai
- **nigrani** ke liye: "disk 90% se zyada ho to alert"
- **intekhab** ke liye: "environment prod ho to tasdeeq maango"

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
if CONDITION_COMMAND; then
  COMMANDS_WHEN_TRUE
else
  COMMANDS_WHEN_FALSE
fi
```

`fi` is "if" backwards: it means "end of if".

</En>
<Ur>

```text
if CONDITION_COMMAND; then
  COMMANDS_WHEN_TRUE
else
  COMMANDS_WHEN_FALSE
fi
```

`fi` "if" ulta likha hai: matlab "if ka aakhir".

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

You make decisions all day:

- **If** it's raining, take an umbrella. **Otherwise**, wear sunglasses.
- **If** the phone battery is below 20%, plug it in.
- **If** the shop is open, buy bread. **Else if** the other shop is open, go there. **Else**, go home.

Each sentence has a **condition** (a yes/no question) and an **action**. A script without conditions is like someone who takes an umbrella every day, even in summer.

</En>
<Ur>

Aap saara din faisle karte hain:

- **Agar** baarish ho rahi hai, chhatri lo. **Warna** dhoop ka chashma pehno.
- **Agar** phone ki battery 20% se kam hai, charge par lagao.
- **Agar** dukaan khuli hai, double roti lo. **Warna agar** doosri dukaan khuli hai, wahan jao. **Warna** ghar jao.

Har jumle me ek **shart** (haan/nahi sawal) aur ek **kaam** hai. Sharton ke baghair script us shakhs jaisi hai jo garmi me bhi roz chhatri le kar nikle.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Condition** | A yes/no question the script asks | "Does `app.log` exist?" |
| **Exit status** | A number a command returns: did it work? | `0` = worked, `1`+ = didn't |
| **Test** | A small command whose only job is to answer yes/no | `[[ -f app.log ]]` |
| **Branch** | One of the paths the script can take | the `then` part or the `else` part |
| **Operator** | A symbol or option inside a test | `-f`, `==`, `>=` |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Condition** | Script ka poocha haan/nahi sawal | "Kya `app.log` mojood hai?" |
| **Exit status** | Command ka lautaya number: kaam hua? | `0` = hua, `1`+ = nahi |
| **Test** | Chhoti command jis ka kaam sirf haan/nahi batana hai | `[[ -f app.log ]]` |
| **Branch** | Script ke mumkina raaston me se ek | `then` wala hissa ya `else` wala |
| **Operator** | Test ke andar nishan ya option | `-f`, `==`, `>=` |

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Exit status: every command reports success or failure">

<Tr>
<En>

Every command returns a number when it finishes: `0` = "I succeeded", anything else = "something went wrong". It's stored in `$?` right after each command (read it immediately; the next command overwrites it).

Think of a **delivery rider** coming back: "delivered" (0), or a problem code like "address not found" (1). The shop decides what to do next from that code.

</En>
<Ur>

Har command khatam ho kar ek number lautati hai: `0` = "main kamyab hui", kuch aur = "kuch ghalat hua". Ye har command ke foran baad `$?` me rakha jata hai (foran parhein; agli command ise mita deti hai).

Wapas aane wale **delivery rider** ka socho: "pohancha diya" (0), ya masle ka code jaise "pata nahi mila" (1). Dukaan us code se tay karti hai aage kya karna hai.

</Ur>
</Tr>

```bash
ls /etc > /dev/null
echo "ls /etc finished with: $?"

ls /folder-that-does-not-exist 2> /dev/null
echo "ls on a missing folder finished with: $?"
```

```text output
ls /etc finished with: 0
ls on a missing folder finished with: 2
```

<Happened>
<Tr>
<En>`/etc` exists, so `ls` returned 0. The missing folder made `ls` return 2 ("serious trouble"). The `/dev/null` parts just hide the listing and the error message.</En>
<Ur>`/etc` mojood hai, isliye `ls` ne 0 lautaya. Gum folder par `ls` ne 2 lautaya ("sangeen masla"). `/dev/null` wale hisse sirf list aur error ka paigham chhupate hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="if … then … fi">

<Tr>
<En>

"If this command succeeds, run the commands between `then` and `fi`." `grep -q` is perfect here: it prints nothing and only answers 0 (found) or 1 (not found).

</En>
<Ur>

"Agar ye command kamyab ho, to `then` aur `fi` ke darmiyan wali commands chalao." Yahan `grep -q` behtareen hai: kuch print nahi karta, sirf 0 (mila) ya 1 (nahi mila) batata hai.

</Ur>
</Tr>

```bash
printf 'started\nERROR disk full\nstopped\n' > app.log

if grep -q "ERROR" app.log; then
  echo "Errors found in app.log"
fi
echo "Script finished"
```

```text output
Errors found in app.log
Script finished
```

<Happened>
<Tr>
<En>

- `grep` found "ERROR", so it returned 0 → **true** → the `echo` inside ran.
- `fi` ended the block. The last `echo` is outside the `if`, so it **always** runs.
- If `app.log` had no "ERROR", you'd only see `Script finished`. (The indent is just for readability.)

</En>
<Ur>

- `grep` ko "ERROR" mila, isliye 0 lautaya → **sach** → andar wala `echo` chala.
- `fi` ne block khatam kiya. Aakhri `echo` `if` ke bahar hai, isliye **hamesha** chalta hai.
- Agar `app.log` me "ERROR" na hota to sirf `Script finished` dikhta. (Andar ki jagah sirf parhne ki asani ke liye hai.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="else: the other path">

<Tr>
<En>

`else` gives a second path that runs only when the condition is **false**: one thing **or** the other.

</En>
<Ur>

`else` doosra raasta deta hai jo sirf tab chalta hai jab shart **jhoot** ho: ek cheez **ya** doosri.

</Ur>
</Tr>

```bash
if ping -c 1 -W 1 127.0.0.1 > /dev/null; then
  echo "Network is working"
else
  echo "Network is NOT working"
fi
```

```text output
Network is working
```

<Happened>
<Tr>
<En>`ping -c 1` sends one test packet. `127.0.0.1` is your own computer, which always answers, so the first branch ran. Try an address that doesn't exist (like `10.255.255.1`) to see the `else` branch.</En>
<Ur>`ping -c 1` ek test packet bhejta hai. `127.0.0.1` aap ka apna computer hai, jo hamesha jawab deta hai, isliye pehla raasta chala. `else` dekhne ke liye na mojood pata (jaise `10.255.255.1`) aazmayen.</Ur>
</Tr>
</Happened>

</Step>

<Step title="elif: more than two possibilities">

<Tr>
<En>

`elif` = "else if". Bash checks conditions **top to bottom**; the **first** true one runs and the rest are skipped. If none is true, `else` runs. Perfect for OK / warning / critical.

</En>
<Ur>

`elif` = "warna agar". Bash sharten **upar se neeche** check karta hai; **pehli** sach wali chalti hai aur baaqi chhor di jati hain. Koi sach na ho to `else` chalta hai. OK / warning / critical ke liye behtareen.

</Ur>
</Tr>

```bash
battery=15

if (( battery < 10 )); then
  echo "Critical: plug in now"
elif (( battery < 20 )); then
  echo "Low battery"
else
  echo "Battery OK"
fi
```

```text output
Low battery
```

<Happened>
<Tr>
<En>Is 15 less than 10? No → skip. Is 15 less than 20? Yes → print "Low battery" and **stop checking**. `else` is skipped.</En>
<Ur>Kya 15, 10 se kam hai? Nahi → chhoro. Kya 15, 20 se kam hai? Haan → "Low battery" print karo aur **check karna band**. `else` chhor diya gaya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Tests: [[ … ]] answers yes or no">

<Tr>
<En>

For questions like "is this a folder?" there's no ordinary command, so we use a **test**: `[[ … ]]`. It's just a command that returns 0 (yes) or 1 (no).

**The spaces are required**: `[[` is a word like `ls`, so write `[[ -f file ]]`, not `[[-f file]]`.

</En>
<Ur>

"Kya ye folder hai?" jaise sawalon ke liye koi aam command nahi, isliye hum **test** istemal karte hain: `[[ … ]]`. Ye bas ek command hai jo 0 (haan) ya 1 (nahi) lautati hai.

**Spaces zaroori hain**: `[[` `ls` ki tarah ek lafz hai, isliye `[[ -f file ]]` likhein, `[[-f file]]` nahi.

</Ur>
</Tr>

```bash
[[ 5 == 5 ]]; echo "5 == 5 gives: $?"
[[ 5 == 6 ]]; echo "5 == 6 gives: $?"
```

```text output
5 == 5 gives: 0
5 == 6 gives: 1
```

| Style | Works in | Use it for |
| --- | --- | --- |
| `[[ … ]]` | Bash (and zsh) | Files, text, patterns: **use this in Bash scripts** |
| `[ … ]` (or `test …`) | Every shell, including `sh` | Same checks, older, easier to break with spaces |
| `(( … ))` | Bash | Numbers |

<Tr>
<En>Prefer `[[ … ]]`: it doesn't break when a variable is empty or has spaces, and it allows `&&` and `||` inside.</En>
<Ur>`[[ … ]]` ko tarjeeh dein: variable khaali ho ya spaces wala ho to bhi nahi toot-ta, aur andar `&&` aur `||` chal jate hain.</Ur>
</Tr>

</Step>

<Step title="Checking files and folders">

<Tr>
<En>

A dash and a letter asks a question about a path. Put `!` in front for the opposite ("does **not** exist").

</En>
<Ur>

Dash aur ek letter kisi path ke baare me sawal poochta hai. Ulta poochna ho ("mojood **nahi**") to aage `!` lagayen.

</Ur>
</Tr>

| Operator | Question |
| --- | --- |
| `-e path` | Does it **exist** (anything)? |
| `-f path` | Is it a regular **file**? |
| `-d path` | Is it a **directory** (folder)? |
| `-s path` | Does it exist and is it **not empty**? |
| `-r` / `-w` / `-x path` | Can I **read** / **write** / **run** it? |
| `-L path` | Is it a symbolic **link**? |

```bash
mkdir -p demo-folder
touch empty.txt
echo "hello" > notes.txt

for path in notes.txt empty.txt demo-folder missing.txt; do
  if [[ -d $path ]]; then
    echo "$path → is a folder"
  elif [[ -s $path ]]; then
    echo "$path → is a file with content"
  elif [[ -f $path ]]; then
    echo "$path → is an empty file"
  else
    echo "$path → does not exist"
  fi
done
```

```text output
notes.txt → is a file with content
empty.txt → is an empty file
demo-folder → is a folder
missing.txt → does not exist
```

<Happened>
<Tr>
<En>For each name, the chain asks in order: folder? non-empty? file? The **first "yes"** wins. (The `for` loop just saves typing; loops are the next lesson.)</En>
<Ur>Har naam ke liye zanjeer tarteeb se poochti hai: folder? khaali nahi? file? **Pehla "haan"** jeet-ta hai. (`for` loop sirf likhne ki mehnat bachata hai; loops agla lesson hain.)</Ur>
</Tr>
</Happened>

<Tr>
<En>A very common pattern: **stop** the script if a file is missing. `>&2` sends the message to the error stream; `exit 1` stops with a failure code so whoever ran it knows.</En>
<Ur>Bohot aam tareeqa: file gum ho to script **rok do**. `>&2` paigham error stream me bhejta hai; `exit 1` nakami ke code ke saath rokta hai taa ke chalane wale ko pata chale.</Ur>
</Tr>

```bash
config="settings.conf"
if [[ ! -f $config ]]; then
  echo "Error: $config not found" >&2
  exit 1
fi
```

```text output
Error: settings.conf not found
```

</Step>

<Step title="Comparing text">

| Test | True when |
| --- | --- |
| `[[ $a == $b ]]` | `a` and `b` are the same text |
| `[[ $a != $b ]]` | they're different |
| `[[ -z $a ]]` | `a` is **empty** (zero length) |
| `[[ -n $a ]]` | `a` is **not** empty |
| `[[ $file == *.log ]]` | `file` ends with `.log` (wildcard) |
| `[[ $ver =~ ^v[0-9]+ ]]` | `ver` matches the regex |

```bash
env="prod"
name=""
file="error.log"

if [[ $env == "prod" ]]; then echo "1) This is production"; fi
if [[ $env != "dev" ]]; then echo "2) This is not dev"; fi
if [[ -z $name ]]; then echo "3) name is empty"; fi
if [[ $file == *.log ]]; then echo "4) $file is a log file"; fi
```

```text output
1) This is production
2) This is not dev
3) name is empty
4) error.log is a log file
```

<Happened>
<Tr>
<En>Note: **no** spaces around `=` when creating a variable (`env="prod"`), but spaces **are** required around `==` inside a test. `*` in `*.log` means "any characters".</En>
<Ur>Dhyan dein: variable banate waqt `=` ke gird space **nahi** (`env="prod"`), lekin test ke andar `==` ke gird spaces **zaroori** hain. `*.log` me `*` ka matlab "koi bhi characters".</Ur>
</Tr>
</Happened>

</Step>

<Step title="Comparing numbers with (( ))">

<Tr>
<En>

Inside `(( … ))`, compare numbers like in maths: `<`, `>`, `<=`, `>=`, `==`, `!=`. No `$` needed in front of variable names.

</En>
<Ur>

`(( … ))` ke andar numbers ko hisaab ki tarah milayen: `<`, `>`, `<=`, `>=`, `==`, `!=`. Variable naamon ke aage `$` ki zaroorat nahi.

</Ur>
</Tr>

```bash
disk=85

if (( disk >= 90 )); then
  echo "CRITICAL: disk ${disk}% full"
elif (( disk >= 80 )); then
  echo "WARNING: disk ${disk}% full"
else
  echo "OK: disk ${disk}% full"
fi
```

```text output
WARNING: disk 85% full
```

<Tr>
<En>**The classic trap:** inside `[[ … ]]`, `<` and `>` compare **text alphabetically**, like words in a dictionary. "10" comes before "9" (because "1" comes before "9"), so the answer is wrong for numbers:</En>
<Ur>**Mashhoor jaal:** `[[ … ]]` ke andar `<` aur `>` **text ko huroof ki tarteeb** se milate hain, jaise lughat me alfaz. "10", "9" se pehle aata hai (kyun ke "1", "9" se pehle hai), isliye numbers ke liye jawab ghalat hota hai:</Ur>
</Tr>

```bash
[[ 10 < 9 ]] && echo "text compare: 10 < 9 is TRUE (wrong for numbers!)"
(( 10 < 9 )) || echo "number compare: 10 < 9 is false (correct)"
```

```text output
text compare: 10 < 9 is TRUE (wrong for numbers!)
number compare: 10 < 9 is false (correct)
```

<Tr>
<En>For numbers, always use `(( … ))`. You'll also see older operators: `-eq`, `-ne`, `-lt`, `-le`, `-gt`, `-ge`. `[ "$disk" -gt 80 ]` = `(( disk > 80 ))`.</En>
<Ur>Numbers ke liye hamesha `(( … ))` istemal karein. Purane operators bhi nazar aayenge: `-eq`, `-ne`, `-lt`, `-le`, `-gt`, `-ge`. `[ "$disk" -gt 80 ]` = `(( disk > 80 ))`.</Ur>
</Tr>

</Step>

<Step title="And, or, not">

<Tr>
<En>

- **and** `&&`: both must be true
- **or** `||`: at least one must be true
- **not** `!`: flip the answer

They work inside `[[ … ]]` and `(( … ))`.

</En>
<Ur>

- **aur** `&&`: dono sach hone chahiyen
- **ya** `||`: kam se kam ek sach ho
- **nahi** `!`: jawab ulta karo

Ye `[[ … ]]` aur `(( … ))` ke andar kaam karte hain.

</Ur>
</Tr>

```bash
age=25
country="US"

if (( age >= 18 && age <= 60 )); then echo "Age is between 18 and 60"; fi
if [[ $country == "US" || $country == "AE" ]]; then echo "Country is US or AE"; fi
if [[ ! -d /this/folder/does/not/exist ]]; then echo "Folder is missing"; fi
```

```text output
Age is between 18 and 60
Country is US or AE
Folder is missing
```

</Step>

<Step title="Short decisions with && and ||">

<Tr>
<En>

For **one simple action**, you can skip `if`:

- `A && B`: run B only if A **succeeded**
- `A || B`: run B only if A **failed**

</En>
<Ur>

**Ek saade kaam** ke liye `if` chhor sakte hain:

- `A && B`: B sirf tab chalao jab A **kamyab** ho
- `A || B`: B sirf tab chalao jab A **nakam** ho

</Ur>
</Tr>

```bash
[[ -d backups ]] || mkdir backups && echo "backups folder is ready"
command -v git > /dev/null && echo "git is installed"
command -v nonexistent-tool > /dev/null || echo "nonexistent-tool is NOT installed"
```

```text output
backups folder is ready
git is installed
nonexistent-tool is NOT installed
```

<Happened>
<Tr>
<En>`[[ -d backups ]] || mkdir backups` = "no backups folder? create it". `command -v git` succeeds only if git is installed.</En>
<Ur>`[[ -d backups ]] || mkdir backups` = "backups folder nahi? bana do". `command -v git` sirf tab kamyab hoti hai jab git install ho.</Ur>
</Tr>
</Happened>

<Callout type="warning" title="A && B || C is not if/else">
<Tr>
<En>If `B` fails, `C` runs too. `true && false || echo "surprise"` prints "surprise" even though the first command succeeded. When the middle command can fail, write a real `if … else … fi`.</En>
<Ur>Agar `B` fail ho to `C` bhi chal jata hai. `true && false || echo "surprise"` "surprise" print karta hai, halanke pehli command kamyab thi. Jab beech wali command fail ho sakti ho, asli `if … else … fi` likhein.</Ur>
</Tr>
</Callout>

</Step>

<Step title="case: choose from a menu">

<Tr>
<En>

When you compare **one value** with many options, `case` is cleaner than a long `elif` chain. It's like a **lift panel**: press "G" → ground floor, "1" → first floor, anything else → "invalid floor".

- `case "$value" in` … `esac` ("case" backwards)
- each option: `pattern) commands ;;`
- `|` = "or" between patterns; `*)` = everything else

</En>
<Ur>

Jab **ek value** ko kai ikhtiyarat se milana ho, `case` lambi `elif` zanjeer se saaf hai. Ye **lift ke panel** jaisa hai: "G" dabao → zameeni manzil, "1" → pehli manzil, kuch aur → "ghalat manzil".

- `case "$value" in` … `esac` ("case" ulta)
- har ikhtiyar: `pattern) commands ;;`
- patterns ke darmiyan `|` = "ya"; `*)` = baaqi sab

</Ur>
</Tr>

```bash
for file in report.pdf backup.tar.gz photo.JPG notes.txt; do
  case "$file" in
    *.pdf)               echo "$file → PDF document" ;;
    *.tar.gz|*.zip)      echo "$file → archive" ;;
    *.jpg|*.JPG|*.png)   echo "$file → image" ;;
    *)                   echo "$file → unknown type" ;;
  esac
done
```

```text output
report.pdf → PDF document
backup.tar.gz → archive
photo.JPG → image
notes.txt → unknown type
```

</Step>

<Step title="Guard clauses: check first, then work">

<Tr>
<En>

A **guard clause** is a check at the **top** of a script that stops it immediately if something is wrong, like a security guard checking your ID at the door. The rest of the script can then assume everything is fine.

- `$#` = number of arguments (we require exactly 1)
- `{ …; exit 2; }` = print the message **and** exit, together

</En>
<Ur>

**Guard clause** script ke **shuru** me ek check hai jo kuch ghalat hone par foran rok deta hai, jaise darwaze par security guard aap ki ID check kare. Phir baaqi script maan sakti hai ke sab theek hai.

- `$#` = arguments ki ginti (hum bilkul 1 maangte hain)
- `{ …; exit 2; }` = paigham print karo **aur** bahar niklo, saath saath

</Ur>
</Tr>

```text
#!/usr/bin/env bash
set -euo pipefail

(( $# == 1 )) || { echo "usage: $0 <file>" >&2; exit 2; }
file="$1"
[[ -e $file ]] || { echo "✖ $file does not exist" >&2; exit 1; }
[[ -r $file ]] || { echo "✖ $file is not readable" >&2; exit 1; }

size=$(stat -c %s "$file")
if (( size == 0 )); then
  echo "⚠ $file is empty"
else
  echo "✓ $file ($size bytes)"
fi
```

<Takeaways>
<Tr>

<DeepDive title="Real world: a pre-deploy safety check">

A check that runs in a CI pipeline before anything is deployed to production. Each `if` is a rule the team learned the hard way:

```bash
#!/usr/bin/env bash
# predeploy-check.sh — refuse unsafe deployments
set -euo pipefail

env="${1:-}"
branch="$(git rev-parse --abbrev-ref HEAD)"

case "$env" in
  staging) ;;
  prod)
    if [[ $branch != main ]]; then
      echo "✖ Production deploys only from main (current: $branch)" >&2; exit 1
    fi
    if [[ -n $(git status --porcelain) ]]; then
      echo "✖ Working tree has uncommitted changes" >&2; exit 1
    fi
    hour=$((10#$(date +%H)))
    if (( hour < 9 || hour >= 18 )) && [[ ${FORCE:-} != yes ]]; then
      echo "✖ Outside deploy window (09:00–18:00). Set FORCE=yes to override." >&2; exit 1
    fi
    ;;
  *) echo "usage: $0 {staging|prod}" >&2; exit 2 ;;
esac

[[ -f dist/index.js ]] || { echo "✖ Build output missing — run the build first" >&2; exit 1; }
echo "✓ Checks passed for $env"
```

What each rule protects against:

- **Only from `main`**: nobody ships half-finished code from a feature branch.
- **No uncommitted changes**: what's deployed is exactly what's in Git.
- **Deploy window**: no risky releases at night when nobody is around to fix problems (`10#` makes `08` and `09` count as normal numbers).
- **Build output exists**: the deploy doesn't upload an empty folder.

Other mistakes: spaces around `=` when creating a variable (`env = prod` runs a command called `env`), and forgetting `fi`, `esac` or `;;`.

</DeepDive>

<DeepDive title="Security lens">

Conditions are where scripts enforce rules. A careless check is a rule someone can get around.

- **Allow-list, don't block-list.** `[[ $env =~ ^(dev|staging|prod)$ ]]` accepts exactly three values. Checking "is not prod" accepts every typo and every strange input.
- **Anchor regular expressions** with `^` (start) and `$` (end). `[[ $input =~ [0-9]+ ]]` also matches `abc1; rm -rf /`. Use `^[0-9]+$`.
- **Quote the right side of `==`** when it comes from a user: in `[[ $a == $b ]]` an unquoted `$b` is a pattern, so a user typing `*` matches everything. Write `[[ $a == "$b" ]]`.
- **Fail closed.** When a check fails, stop with a non-zero exit code. Don't continue "just in case".
- **Refuse dangerous situations on purpose**, for example: `(( EUID == 0 )) && { echo "do not run as root" >&2; exit 1; }`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does if decide true or false in Bash?">
It runs a command and checks its exit status. Exit status 0 means success and counts as true, so the then-branch runs. Any other value counts as false, so the elif/else branch runs. Tests like `[[ ]]`, `[ ]` and `(( ))` are themselves commands that return 0 or 1, which is why they work with if.
</QA>

<QA q="What is the difference between [ ] and [[ ]]?">
`[ ]` is the old POSIX test command that works in every shell; variables inside it must be quoted or they break when empty or containing spaces. `[[ ]]` is a Bash keyword: it does not split variables, allows && and || inside, supports wildcard patterns with == and regular expressions with =~. Use `[[ ]]` in Bash scripts and `[ ]` only when the script must run under plain sh.
</QA>

<QA q="How do you compare numbers, and why not use < inside [[ ]]?">
Use `(( a < b ))` or the operators -lt, -gt, -eq and so on. Inside `[[ ]]`, < and > compare text alphabetically, so "10" < "9" is true, which is wrong for numbers.
</QA>

<QA q="When would you use case instead of if/elif?">
When one value is compared against several possible values or patterns, such as a subcommand (start/stop/restart), a file extension or an environment name. case is shorter and easier to read, supports patterns and alternatives with |, and has a default branch.
</QA>

<QA q="Why is a && b || c not the same as if/else?">
In a && b || c, c runs if a fails or if b fails. In an if/else, the else part runs only when a fails. If b can fail, a real if/else must be used.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Condition">A yes/no question the script asks before deciding what to do.</Term>
  <Term name="Exit status">The number a command returns when it finishes; 0 means success. Stored in `$?`.</Term>
  <Term name="Test">A small command that checks something and returns 0 (yes) or 1 (no), such as `[[ -f file ]]`.</Term>
  <Term name="Branch">One of the paths the script can take: then, elif or else.</Term>
  <Term name="Operator">A symbol or option inside a test, such as `-f`, `==`, `>=`.</Term>
  <Term name="(( ))">Bash's maths area, used to compare numbers.</Term>
  <Term name="case">Compares one value with many patterns, like a menu.</Term>
  <Term name="Guard clause">A check at the top of a script that stops it early when something is wrong.</Term>
</Terms>
