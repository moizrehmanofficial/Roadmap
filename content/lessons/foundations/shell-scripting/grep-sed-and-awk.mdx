## At a glance

<Glance>
<What>
<Tr>
<En>

- **grep**: prints the lines that match: `grep ERROR app.log`
- **sed**: edits text as it flows past, mostly find-and-replace: `sed 's/old/new/g'`
- **awk**: splits each line into columns (`$1`, `$2`, …), filters and calculates: `awk '{print $1}'`
- All three understand **regular expressions**: patterns like `^ERROR` ("line starts with ERROR") or `[0-9]+` ("one or more digits").

</En>
<Ur>

- **grep**: milti hui lines print karta hai: `grep ERROR app.log`
- **sed**: guzarte text ko edit karta hai, zyada tar dhoondo-aur-badlo: `sed 's/old/new/g'`
- **awk**: har line ko columns (`$1`, `$2`, …) me torta, filter aur hisaab karta hai: `awk '{print $1}'`
- Teeno **regular expressions** samajhte hain: patterns jaise `^ERROR` ("line ERROR se shuru") ya `[0-9]+` ("ek ya zyada digits").

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Log analysis**: the first step of any incident. Find errors, count them, find who caused them.
- **Config changes** in scripts: change a setting on 50 servers without opening an editor.
- **Security**: failed logins, suspicious IPs, secrets accidentally committed to code.
- **Interviews**: "find the top 10 IPs in an access log" is a classic task.

</En>
<Ur>

- **Log analysis**: har incident ka pehla qadam. Errors dhoondo, gino, pata karo kis ne kiye.
- Scripts me **config ki tabdeeli**: editor khole baghair 50 servers par setting badlo.
- **Security**: fail logins, shakki IPs, code me ghalti se commit hue secrets.
- **Interviews**: "access log me top 10 IPs dhoondo" mashhoor sawal hai.

</Ur>
</Tr>
</Why>

## Learn it step by step

<Walkthrough>

<Step title="Regular expressions: the shared pattern language">

<Tr>
<En>

Real searches are rarely exact. You want "lines starting with ERROR", "any number", "status 401 **or** 500". A **regular expression** describes such patterns with special symbols. Use `grep -E` (extended) so `+`, `?`, `|` and `()` work without backslashes.

</En>
<Ur>

Asli talash kam hi bilkul theek alfaz ki hoti hai. Aap chahte hain "ERROR se shuru hone wali lines", "koi bhi number", "status 401 **ya** 500". **Regular expression** khaas nishanon se aise patterns batata hai. `grep -E` (extended) istemal karein taa ke `+`, `?`, `|` aur `()` baghair backslash ke kaam karein.

</Ur>
</Tr>

| Symbol | Means | Example | Matches |
| --- | --- | --- | --- |
| `.` | Any single character | `h.t` | hat, hot, h9t |
| `^` | Start of the line | `^ERROR` | lines starting with ERROR |
| `$` | End of the line | `ms$` | lines ending with ms |
| `*` | The previous thing 0 or more times | `ab*c` | ac, abc, abbbc |
| `+` | The previous thing 1 or more times (`-E`) | `[0-9]+` | 5, 42, 2026 |
| `?` | The previous thing 0 or 1 time (`-E`) | `colou?r` | color, colour |
| `[abc]` | One of these characters | `[aeiou]` | any vowel |
| `[0-9]` | One character in this range | `[A-Z]` | any capital letter |
| `[^0-9]` | One character **not** in this set | `[^ ]` | anything except a space |
| `a\|b` | a or b (`-E`) | `ERROR\|WARN` | either word |
| `( )` | Group (`-E`) | `(ab)+` | ab, abab |
| `\.` | A real dot (escaped) | `1\.2` | only "1.2" |

```bash
grep -E '^2026-11-10 08:02' app.log
echo "---"
grep -E ' (401|500) ' app.log
echo "---"
grep -E '[0-9]{4}ms$' app.log
```

```text output
2026-11-10 08:02:01 WARN  web-1 GET /login 401 80ms
2026-11-10 08:02:44 ERROR web-1 POST /api/orders 500 1900ms
---
2026-11-10 08:01:15 ERROR web-2 GET /api/users 500 2300ms
2026-11-10 08:02:01 WARN  web-1 GET /login 401 80ms
2026-11-10 08:02:44 ERROR web-1 POST /api/orders 500 1900ms
---
2026-11-10 08:01:15 ERROR web-2 GET /api/users 500 2300ms
2026-11-10 08:02:44 ERROR web-1 POST /api/orders 500 1900ms
```

<Happened>
<Tr>
<En>

- `^2026-11-10 08:02`: lines that **start** with that minute.
- ` (401|500) `: a space, then 401 **or** 500, then a space (the spaces stop it matching inside other numbers).
- `[0-9]{4}ms$`: exactly **four digits** then `ms` at the **end**: requests that took 1000 ms or more (slow ones).

</En>
<Ur>

- `^2026-11-10 08:02`: wo lines jo us minute se **shuru** hoti hain.
- ` (401|500) `: space, phir 401 **ya** 500, phir space (spaces doosre numbers ke andar milne se rokti hain).
- `[0-9]{4}ms$`: bilkul **chaar digits** phir **aakhir** me `ms`: wo requests jin me 1000 ms ya zyada laga (sust wali).

</Ur>
</Tr>
</Happened>

</Step>

```bash
echo "1) count of ERROR lines: $(grep -c ERROR app.log)"
echo "2) case-insensitive 'info' lines: $(grep -ci info app.log)"

grep -vi info app.log
echo "4) with line numbers:"
grep -n WARN app.log
echo "5) only the matching part (status codes):"
grep -oE ' [0-9]{3} ' app.log | sort | uniq -c
grep -q "POST" app.log && echo "6) there is at least one POST request"
```

5. `-o` ne sirf status codes print kiye, jo phir hum ne gine.

</Tr>

<Step title="sed: find and replace">

<Tr>
<En>

**sed** = **s**tream **ed**itor. It reads text line by line, edits it, and prints the result. Its most-used command is **`s/old/new/`** (substitute):

- `s/cat/dog/`: replace the **first** `cat` on each line
- `s/cat/dog/g`: replace **all** of them (**g**lobal)
- `s/cat/dog/gI`: all, ignoring case

</En>
<Ur>

**sed** = **s**tream **ed**itor. Ye text line ba line parhta, edit karta aur nateeja print karta hai. Is ki sab se zyada istemal hone wali command **`s/old/new/`** (substitute) hai:

- `s/cat/dog/`: har line ka **pehla** `cat` badlo
- `s/cat/dog/g`: **saare** badlo (**g**lobal)
- `s/cat/dog/gI`: saare, case nazar andaz kar ke

</Ur>
</Tr>

```bash
echo "cat cat cat" | sed 's/cat/dog/'
echo "cat cat cat" | sed 's/cat/dog/g'
echo "Error error ERROR" | sed 's/error/issue/gI'
```

```text output
dog cat cat
dog dog dog
issue issue issue
```

<Tr>
<En>On our log (the file itself isn't changed; sed just prints the result):</En>
<Ur>Hamare log par (file khud nahi badalti; sed sirf nateeja print karta hai):</Ur>
</Tr>

```bash
sed 's/web-/server-/g' app.log | head -2
```

```text output
2026-11-10 08:01:12 INFO  server-1 GET /home 200 120ms
2026-11-10 08:01:15 ERROR server-2 GET /api/users 500 2300ms
```

</Step>

<Step title="sed -i: edit files in place">

<Tr>
<En>

`-i` makes sed write the changes **back into the file**. Safer: `-i.bak` also keeps the original as `file.bak`. (On macOS write `sed -i '' 's/…/…/' file`.)

Golden rule: run **without** `-i` first, check the output, **then** add `-i`.

</En>
<Ur>

`-i` sed se tabdeeliyan **wapas file me** likhwata hai. Zyada mehfooz: `-i.bak` asal ko `file.bak` ki shakal me bhi rakhta hai. (macOS par `sed -i '' 's/…/…/' file` likhein.)

Sunehra qaida: pehle `-i` ke **baghair** chalayen, output check karein, **phir** `-i` lagayen.

</Ur>
</Tr>

```bash
printf 'port=8080\nhost=localhost\ndebug=true\n' > app.conf
sed -i.bak 's/^port=.*/port=9090/; s/^debug=true/debug=false/' app.conf
echo "--- app.conf now:"; cat app.conf
echo "--- backup app.conf.bak:"; cat app.conf.bak
```

```text output
--- app.conf now:
port=9090
host=localhost
debug=false
--- backup app.conf.bak:
port=8080
host=localhost
debug=true
```

<Happened>
<Tr>
<En>

- `^port=.*`: a line **starting** with `port=` followed by anything (`.*` = any characters).
- `;` separates two sed commands in one call.
- The file changed, and the original was kept as `app.conf.bak`.

</En>
<Ur>

- `^port=.*`: line jo `port=` se **shuru** ho aur phir kuch bhi (`.*` = koi bhi characters).
- `;` ek hi call me do sed commands alag karta hai.
- File badal gayi, aur asal `app.conf.bak` ki shakal me bach gayi.

</Ur>
</Tr>
</Happened>

<Tr>
<En>When the text contains `/`, use another separator like `|` so you don't have to escape every slash:</En>
<Ur>Jab text me `/` ho, to `|` jaisa doosra separator istemal karein taa ke har slash ke aage backslash na lagana pare:</Ur>
</Tr>

```bash

```


<Step title="sed: delete and print lines">

<Tr>
<En>

- `sed '/pattern/d'`: **d**elete matching lines (e.g. comments)
- `sed -n '2,4p'`: **p**rint only lines 2 to 4 (`-n` stops sed printing everything else)

</En>
<Ur>

- `sed '/pattern/d'`: milti lines **d**elete karo (jaise comments)
- `sed -n '2,4p'`: sirf lines 2 se 4 **p**rint karo (`-n` sed ko baaqi sab print karne se rokta hai)

</Ur>
</Tr>

```bash
printf '# database settings\nhost=db\n\n# port\nport=5432\n' > db.conf
echo "--- without comments and blank lines:"
sed '/^#/d; /^$/d' db.conf
echo "--- only lines 2 to 3 of app.log:"
sed -n '2,3p' app.log
```

```text output

```

<Happened>
<Tr>
<En>`/^#/d` deleted lines starting with `#`; `/^$/d` deleted empty lines (start immediately followed by end). What's left is just the real settings.</En>
<Ur>`/^#/d` ne `#` se shuru hone wali lines mitayin; `/^$/d` ne khaali lines (shuru ke foran baad aakhir). Bacha sirf asli settings.</Ur>
</Tr>
</Happened>

<Step title="awk: work with columns">

<Tr>
<En>

**awk** splits every line into **fields**: `$1` is the first column, `$2` the second, … `$0` is the whole line, and `NF` is how many fields there are. grep sees whole lines; awk understands their **structure**.

Always put the awk program in **single quotes**, so the shell doesn't touch the `$`.

</En>
<Ur>

**awk** har line ko **fields** me torta hai: `$1` pehla column, `$2` doosra, … `$0` poori line, aur `NF` kitne fields hain. grep poori lines dekhta hai; awk un ka **dhancha** samajhta hai.

awk program hamesha **single quotes** me rakhein, taa ke shell `$` ko na chhoye.

</Ur>
</Tr>

```bash
awk '{ print $3, $6 }' app.log
```

```text output
INFO /home
ERROR /api/users
WARN /login
ERROR /api/orders
INFO /about
info /health
```

<Happened>
<Tr>
<En>We printed column 3 (level) and column 6 (path) of every line. Columns are split on any number of spaces, so the double space after `INFO` causes no problem.</En>
<Ur>Hum ne har line ka column 3 (level) aur column 6 (path) print kiya. Columns kitni bhi spaces par tootte hain, isliye `INFO` ke baad do spaces se koi masla nahi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="awk: filter by a column">

<Tr>
<En>

Put a **condition** before the `{ … }` and the block runs only on lines where it's true:

- numbers: `$7 >= 500`
- text: `$4 == "web-1"`
- regex: `$3 ~ /ERR/`

This answers questions grep can't do reliably, like "status 500" (not just "500 appears somewhere on the line").

</En>
<Ur>

`{ … }` se pehle ek **shart** rakhein aur block sirf un lines par chalega jahan wo sach ho:

- numbers: `$7 >= 500`
- text: `$4 == "web-1"`
- regex: `$3 ~ /ERR/`

Ye wo sawal hal karta hai jo grep bharose se nahi kar sakta, jaise "status 500" (sirf "line me kahin 500 hai" nahi).

</Ur>
</Tr>

```bash
echo "Status 500 on which server and path:"
awk '$7 == 500 { print $4, $6 }' app.log
echo "Requests on web-1:"
awk '$4 == "web-1" { print $2, $6 }' app.log
```

```text output
Status 500 on which server and path:
web-2 /api/users
web-1 /api/orders
Requests on web-1:
08:01:12 /home
08:02:01 /login
08:02:44 /api/orders
```

</Step>

<Step title="awk: totals, averages and counts per group">

<Tr>
<En>

awk can keep **variables**, add numbers, and run code **after the last line** (`END`) or **before the first** (`BEGIN`). That gives you totals, averages and per-group counts without a spreadsheet.

</En>
<Ur>

awk **variables** rakh sakta hai, numbers jama kar sakta hai, aur **aakhri line ke baad** (`END`) ya **pehli se pehle** (`BEGIN`) code chala sakta hai. Is se spreadsheet ke baghair totals, average aur har group ki ginti milti hai.

</Ur>
</Tr>

```bash
awk '{ total += $8; n++ } END { print "requests:", n, "| average time:", total / n, "ms" }' app.log

awk '{ hits[$4]++ } END { for (s in hits) print s, hits[s] }' app.log | sort
```

```text output

web-1 3
web-2 3
```

<Step title="Which tool for which job?">

| Question | Best tool | Example |
| --- | --- | --- |
| Which lines contain X? | grep | `grep -i timeout app.log` |
| Does X exist at all? | grep -q | `grep -q '^port=' app.conf` |
| Change X to Y | sed | `sed -i 's/8080/9090/' app.conf` |
| Remove comments / blank lines | sed | `sed '/^#/d; /^$/d'` |
| Show column N | awk | `awk '{print $1}'` |
| Filter by a column's value | awk | `awk '$7 >= 500'` |
| Sum / average / count per group | awk | `awk '{s+=$8} END {print s}'` |

</Step>

## Common mistakes

<Compare>
<Bad title="Dots in IPs">

```text
grep 1.2.3.4 access.log      # also matches 1x2y3z4
```

</Bad>
<Good title="Fixed string or escaped dots">

```text
grep -F 1.2.3.4 access.log
grep '1\.2\.3\.4' access.log
```

</Good>
</Compare>

<Compare>
<Bad title="Greedy match">

```text
sed 's/".*"/X/'     # replaces from the FIRST quote to the LAST quote on the line
```

</Bad>
<Good title="Stop at the next quote">

```text
sed 's/"[^"]*"/X/'  # [^"]* = anything except a quote
```

</Good>
</Compare>

<Compare>
<Bad title="Double quotes around awk">

```text
awk "{print $1}" file     # the shell turns $1 into something else first
```

</Bad>
<Good title="Single quotes">

```text
awk '{print $1}' file
```

</Good>
</Compare>

<DeepDive title="Real world: a CI gate and a nightly report">

A DevSecOps engineer adds a quick **"no secrets, no debug in production config"** gate to a CI pipeline, plus a nightly report, using only these tools:

```bash
#!/usr/bin/env bash
set -euo pipefail

# 1. Fail the build if a production env file enables debug or uses http://
if grep -nE '^(DEBUG=true|NODE_ENV=development)|http://' deploy/production.env; then
  echo "✖ Production config contains debug settings or plain HTTP URLs" >&2
  exit 1
fi

# 2. Fail if anything looks like a private key or AWS key was committed
if grep -rnE 'BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY|AKIA[0-9A-Z]{16}' --exclude-dir=node_modules .; then
  echo "✖ Possible secret committed" >&2
  exit 1
fi

# 3. Stamp the build version into the config
sed -i "s/^APP_VERSION=.*/APP_VERSION=${GITHUB_SHA:0:7}/" deploy/production.env

# 4. Nightly: top scanners and error rate from yesterday's logs
zcat -f /var/log/nginx/access.log.1* \
  | awk '$9 ~ /^5/ {e++} {t++} $7 ~ /\.(env|git|php)/ {probe[$1]++}
         END {printf "error rate: %.2f%%\n", 100*e/t;
              for (ip in probe) print probe[ip], ip}' \
  | sort -rn | head
```

(Dedicated tools like gitleaks do secret scanning far better, covered in DevSecOps, but this shows how far three classic tools go.)

Other pitfalls: forgetting `-E` and wondering why `+` or `{3}` don't work; and parsing CSV or JSON with awk, where quoted commas and nested data break simple splitting.

</DeepDive>

<DeepDive title="Security lens">

These three tools are the fastest way to answer "what happened?" on any Linux system, and the fastest way to find secrets before attackers do.

- **Threat hunting basics:** probes for `/.env`, `/.git/config`, `/wp-login.php`, `/phpmyadmin`; spikes of 401/403; long or encoded URLs (`%2e%2e%2f`); unusual user agents (`sqlmap`, `nikto`, `curl`, `python-requests`). All findable with grep and awk.
- **IOC sweeps:** given indicators (IPs, domains, file hashes) from a threat report, `grep -rFf iocs.txt /var/log` checks a server in seconds.
- **Secret discovery:** `grep -rnE "(api[_-]?key|secret|passw(or)?d|token)\s*[:=]"` across repos and servers finds hard-coded credentials. Run it on your own code before an attacker or a public GitHub scan does.
- **Regex denial of service (ReDoS):** badly written regexes with nested quantifiers (`(a+)+$`) can take exponential time on crafted input. In apps that apply regex to user input, prefer simple patterns, length limits and safe regex engines.
- **Command injection via sed/awk:** building a `sed` expression from user input (`sed "s/$input/x/"`) lets an attacker inject sed commands; GNU sed's `e` flag can even run shell commands. Never put untrusted input into sed or awk programs; pass data with `awk -v var="$input"` instead.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How would you find the 10 IP addresses with the most requests in an Nginx access log?">
`awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -n 10`. awk prints the first field (client IP), sort groups identical IPs, uniq -c counts each group, sort -rn orders by count descending, and head keeps the top ten. An awk-only version is `awk '{c[$1]++} END {for (i in c) print c[i], i}' access.log | sort -rn | head`.
</QA>

<QA q="How do you replace a value in a config file from a script, safely?">
Use sed with in-place editing and a backup, anchoring the pattern to the start of the line: `sed -i.bak 's/^PasswordAuthentication .*/PasswordAuthentication no/' /etc/ssh/sshd_config`. Test the expression without -i first, validate the resulting file (for example sshd -t), and use a different delimiter like | when the values contain slashes.
</QA>

<QA q="What is the difference between grep, grep -E and grep -F?">
grep uses basic regular expressions, where characters such as +, ?, |, () and {} need backslashes to have special meaning. grep -E uses extended regular expressions, where they work directly. grep -F treats the pattern as a fixed string with no regex meaning at all, which is fastest and correct for literal text containing dots or brackets, like IP addresses.
</QA>

<QA q="When would you use awk instead of grep or sed?">
When the data has columns or you need logic or arithmetic: selecting specific fields, filtering on a field's value (status code over 499), summing or averaging a column, counting by group with associative arrays, or reformatting output. grep is for finding matching lines and sed for line-oriented edits such as substitutions.
</QA>

<QA q="Why is it dangerous to build a sed command from user input?">
The input becomes part of the sed program, so special characters can change its meaning: an attacker could add commands, break out of the substitution or, with GNU sed's e flag, execute shell commands. Validate input against an allow-list, escape it properly, or use tools that take data as data, such as awk -v or a real programming language.
</QA>

</DeepDive>
