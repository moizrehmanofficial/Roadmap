<BigIdea>
<Tr>
<En>
A **signal** is a short message the system sends to a running program: Ctrl+C sends **SIGINT**, `kill` sends **SIGTERM**, and `kill -9` sends **SIGKILL** (which can't be caught). `trap 'commands' SIGNAL` tells Bash what to do when one arrives. The most useful trap is `trap cleanup EXIT`: it runs when the script ends **for any reason**, so temporary files are always deleted and locks always released.
</En>
<Ur>
**Signal** ek chhota paighaam hai jo system chalte program ko bhejta hai: Ctrl+C **SIGINT** bhejta hai, `kill` **SIGTERM**, aur `kill -9` **SIGKILL** (jise pakra nahi ja sakta). `trap 'commands' SIGNAL` Bash ko batata hai ke signal aane par kya karna hai. Sab se kaam ka trap `trap cleanup EXIT` hai: ye script **kisi bhi wajah** se khatam ho, chalta hai, isliye temporary files hamesha mitti hain aur locks hamesha chhoot jate hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Signals** are notifications sent to processes. Each has a name and a number.
- **`trap`** registers commands to run when a signal arrives, or on special Bash events: `EXIT` (script ends), `ERR` (a command fails).

| Signal | Number | Sent by | Can be trapped? |
| --- | --- | --- | --- |
| `SIGINT` (INT) | 2 | Ctrl+C in the terminal | Yes |
| `SIGTERM` (TERM) | 15 | `kill PID`, `docker stop`, systemd stop, shutdown | Yes |
| `SIGHUP` (HUP) | 1 | Terminal closed; "reload config" for many daemons | Yes |
| `SIGKILL` (KILL) | 9 | `kill -9 PID`, the out-of-memory killer | **No** |
| `SIGQUIT` (QUIT) | 3 | Ctrl+\ | Yes |

</En>
<Ur>

- **Signals** processes ko bheji jane wali itlaat hain. Har ek ka naam aur number hai.
- **`trap`** signal aane par, ya Bash ke khaas waqiyat par chalne wali commands darj karta hai: `EXIT` (script khatam), `ERR` (command fail).

| Signal | Number | Kaun bhejta hai | Pakra ja sakta hai? |
| --- | --- | --- | --- |
| `SIGINT` (INT) | 2 | Terminal me Ctrl+C | Haan |
| `SIGTERM` (TERM) | 15 | `kill PID`, `docker stop`, systemd stop, shutdown | Haan |
| `SIGHUP` (HUP) | 1 | Terminal band; kai daemons ke liye "config reload" | Haan |
| `SIGKILL` (KILL) | 9 | `kill -9 PID`, out-of-memory killer | **Nahi** |
| `SIGQUIT` (QUIT) | 3 | Ctrl+\ | Haan |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

A script doesn't always finish normally: it can **fail** halfway, be **interrupted** with Ctrl+C, or be **stopped** by the system (`docker stop`, shutdown, a CI timeout). Without traps, leftovers stay behind:

- **Temporary files** fill the disk or leak secrets.
- **Lock files** block every future run.
- **Background helpers** keep running, orphaned.

Docker and Kubernetes send SIGTERM and wait (10 s / 30 s) before SIGKILL; a script that handles SIGTERM can finish cleanly.

</En>
<Ur>

Script hamesha aam tareeqe se khatam nahi hota: ye beech me **fail** ho sakta hai, Ctrl+C se **rok** diya ja sakta hai, ya system **band** kar sakta hai (`docker stop`, shutdown, CI timeout). Traps ke baghair bachi khuchi cheezen reh jati hain:

- **Temporary files** disk bharti hain ya raaz leak karti hain.
- **Lock files** har agla run rok deti hain.
- **Background helpers** lawaris chalte rehte hain.

Docker aur Kubernetes SIGTERM bhej kar SIGKILL se pehle intezar karte hain (10 s / 30 s); SIGTERM sambhalne wala script saaf tareeqe se khatam ho sakta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Signals in practice">

<Tr>
<En>

`kill PID` (same as `kill -TERM PID`) politely asks a process to stop. `kill -9 PID` forces it, as a last resort. `kill -l` lists all signals. An exit code of **128 + N** means "killed by signal N".

</En>
<Ur>

`kill PID` (jo `kill -TERM PID` jaisa hai) process se tameez se rukne ko kehta hai. `kill -9 PID` zabardasti rokta hai, aakhri chara ke tor par. `kill -l` saare signals dikhata hai. **128 + N** exit code ka matlab "signal N se maara gaya".

</Ur>
</Tr>

```bash
sleep 30 &
pid=$!
kill -TERM "$pid"
wait "$pid"
code=$?
echo "sleep ended with code $code = 128 + $((code - 128)) (signal $(kill -l $((code - 128))))"
```

```text output
sleep ended with code 143 = 128 + 15 (signal TERM)
```

<Happened>
<Tr>
<En>`sleep 30 &` started a background process, and `$!` gave its PID. After `kill -TERM`, `wait` reported 143: 128 + 15, and 15 is TERM.</En>
<Ur>`sleep 30 &` ne background process shuru kiya, aur `$!` ne us ka PID diya. `kill -TERM` ke baad `wait` ne 143 bataya: 128 + 15, aur 15 TERM hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="trap … EXIT: always run cleanup">

<Tr>
<En>

The `EXIT` trap runs when the script ends: normally, through `exit`, because of `set -e`, or after a trapped signal. It's the **one reliable place** for cleanup: write it once, right after creating the temporary thing, and it runs on every way out.

</En>
<Ur>

`EXIT` trap tab chalta hai jab script khatam ho: aam tareeqe se, `exit` se, `set -e` ki wajah se, ya pakre gaye signal ke baad. Safai ke liye ye **wahid bharosemand jagah** hai: temporary cheez banane ke foran baad ek dafa likho, aur ye har raaste par chalta hai.

</Ur>
</Tr>

```bash
cat > job.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
workdir=$(mktemp -d)
cleanup() {
  rm -rf "$workdir"
  echo "cleanup: removed temporary folder"
}
trap cleanup EXIT

echo "working in a temporary folder"
touch "$workdir/data.part"
[[ ${1:-} == fail ]] && false
echo "job finished"
EOF
chmod +x job.sh

./job.sh; echo "exit: $?"
echo "---"
./job.sh fail; echo "exit: $?"
```

```text output
working in a temporary folder
job finished
cleanup: removed temporary folder
exit: 0
---
working in a temporary folder
cleanup: removed temporary folder
exit: 1
```

<Happened>
<Tr>
<En>In **both** runs, success and failure, the cleanup ran, and the original exit code (0 or 1) was kept.</En>
<Ur>**Dono** runs me, kamyabi aur nakami, safai chali, aur asal exit code (0 ya 1) bacha raha.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Handle Ctrl+C (SIGINT)">

<Tr>
<En>

A trap on `INT` runs when the user presses Ctrl+C: print a friendly message, save progress, then exit with **130** (128 + 2) so callers know it was interrupted. The EXIT trap still runs afterwards.

</En>
<Ur>

`INT` par trap tab chalta hai jab user Ctrl+C dabaye: dostana message chhaapo, progress save karo, phir **130** (128 + 2) par niklo taa ke bulane walon ko pata chale ke roka gaya. EXIT trap phir bhi baad me chalta hai.

</Ur>
</Tr>

```bash
cat > long.sh <<'EOF'
#!/usr/bin/env bash
trap 'echo "cleanup on exit"' EXIT
trap 'echo "Interrupted by user"; exit 130' INT
echo "starting long job"
sleep 10 &
wait $!
echo "job done"
EOF
chmod +x long.sh

set -m          # job control: lets a background script receive Ctrl+C like a foreground one
./long.sh &
script_pid=$!
sleep 0.5
kill -INT "$script_pid"
wait "$script_pid" 2> /dev/null; echo "exit: $?"
set +m
```

```text output
starting long job
Interrupted by user
cleanup on exit
exit: 130
```

<Happened>
<Tr>
<En>

- `kill -INT` played the role of your Ctrl+C.
- `sleep 10 & wait $!` is used because Bash runs traps only **between** commands; `wait` lets the trap fire immediately.
- `set -m` is only needed because this demo starts the script in the background. Scripts started from a terminal get Ctrl+C normally.

</En>
<Ur>

- `kill -INT` ne aap ke Ctrl+C ka kirdar ada kiya.
- `sleep 10 & wait $!` is liye hai ke Bash traps sirf commands ke **darmiyan** chalata hai; `wait` trap ko foran chalne deta hai.
- `set -m` sirf is liye zaroori hai ke ye demo script background me shuru karta hai. Terminal se shuru hone wale scripts ko Ctrl+C aam tor par milta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Graceful shutdown on SIGTERM">

<Tr>
<En>

Docker, Kubernetes and systemd stop programs by sending **SIGTERM first**. Scripts that ignore it get SIGKILL after a timeout: stopped mid-write, with no cleanup. Better: in the TERM trap, set a **flag**, and let the loop check it so the current job finishes before stopping.

</En>
<Ur>

Docker, Kubernetes aur systemd programs ko **pehle SIGTERM** bhej kar rokte hain. Ise nazar andaz karne wale scripts ko timeout ke baad SIGKILL milta hai: likhte likhte ruk jate hain, safai ke baghair. Behtar: TERM trap me ek **flag** set karein, aur loop use check kare taa ke mojooda kaam rukne se pehle khatam ho.

</Ur>
</Tr>

```bash
cat > worker.sh <<'EOF'
#!/usr/bin/env bash
stop=false
trap 'echo "SIGTERM received, finishing current job…"; stop=true' TERM
n=0
while ! $stop; do
  ((n++))
  echo "processing job $n"
  sleep 0.3 & wait $!
done
echo "worker stopped cleanly after $n jobs"
EOF
chmod +x worker.sh

./worker.sh > worker.out &
pid=$!
sleep 1
kill -TERM "$pid"; wait "$pid"
grep -E "received|stopped" worker.out | sed 's/after [0-9]* jobs/after N jobs/'
```

```text output
SIGTERM received, finishing current job…
worker stopped cleanly after N jobs
```

</Step>

<Step title="trap … ERR: report failures with line numbers">

<Tr>
<En>

The `ERR` trap runs when a command fails (where `set -e` would stop). It can print **where** it failed, which is gold in CI logs:

- `$LINENO`: the line number.
- `$BASH_COMMAND`: the command that was running.
- `set -E` (capital E) makes the ERR trap work **inside functions** too.

</En>
<Ur>

`ERR` trap tab chalta hai jab command fail ho (jahan `set -e` rokta). Ye chhaap sakta hai ke **kahan** fail hua, jo CI logs me sona hai:

- `$LINENO`: line ka number.
- `$BASH_COMMAND`: chalti hui command.
- `set -E` (bara E) ERR trap ko **functions ke andar** bhi chalata hai.

</Ur>
</Tr>

```bash
cat > deploy.sh <<'EOF'
#!/usr/bin/env bash
set -Eeuo pipefail
trap 'echo "ERROR: line $LINENO: \"$BASH_COMMAND\" failed with code $?" >&2' ERR

echo "step 1: build"
echo "step 2: upload"
ls /no/such/release 2> /dev/null
echo "step 3: never reached"
EOF
bash deploy.sh; echo "exit: $?"
```

```text output
step 1: build
step 2: upload
ERROR: line 7: "ls /no/such/release 2> /dev/null" failed with code 2
exit: 2
```

</Step>

<Step title="Lock files: only one copy at a time">

<Tr>
<En>

Cron may start a backup every hour. If one run takes 90 minutes, two copies would fight over the same files. `flock` fixes this:

- `exec 9> file` opens the lock file as file descriptor 9 for the whole script.
- `flock -n 9` tries to lock it; `-n` means "don't wait, fail immediately if locked".
- When the script exits, descriptor 9 closes and the lock disappears, even after a crash: **no stale locks**.

</En>
<Ur>

Cron har ghante backup shuru kar sakta hai. Agar ek run 90 minute le, to do copies ek hi files par larengi. `flock` ye theek karta hai:

- `exec 9> file` lock file ko poore script ke liye file descriptor 9 ke tor par kholta hai.
- `flock -n 9` lock karne ki koshish karta hai; `-n` ka matlab "intezar mat karo, lock ho to foran fail".
- Script nikle to descriptor 9 band hota hai aur lock gayab, crash ke baad bhi: **koi purana lock nahi**.

</Ur>
</Tr>

```bash
cat > backup.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
exec 9> /tmp/demo-backup.lock
if ! flock -n 9; then
  echo "Another backup is already running — exiting"
  exit 1
fi
echo "Backup started (pid $$)" | sed 's/pid [0-9]*/pid N/'
sleep 1
echo "Backup finished"
EOF
chmod +x backup.sh

./backup.sh &
sleep 0.2
./backup.sh; echo "second copy exit: $?"
wait
```

```text output
Backup started (pid N)
Another backup is already running — exiting
second copy exit: 1
Backup finished
```

</Step>

<Step title="Clean up background processes">

<Tr>
<En>

Helpers your script starts in the background (`ssh -L` tunnels, `kubectl port-forward`, test servers) keep running after the script is gone unless you stop them. Save the PID with `$!` and kill it in the EXIT trap.

</En>
<Ur>

Script jo helpers background me shuru karta hai (`ssh -L` tunnels, `kubectl port-forward`, test servers) wo script ke jaane ke baad bhi chalte rehte hain jab tak aap unhe na rokein. `$!` se PID mehfooz karein aur EXIT trap me use band karein.

</Ur>
</Tr>

```bash
cat > with-helper.sh <<'EOF'
#!/usr/bin/env bash
sleep 60 &
helper=$!
trap 'kill "$helper" 2> /dev/null; echo "stopped helper"' EXIT
echo "using the helper"
EOF
bash with-helper.sh
```

```text output
using the helper
stopped helper
```

</Step>

<Step title="List, ignore and reset traps">

<Tr>
<En>

- `trap -p` lists active traps.
- `trap - SIGNAL` restores the default.
- `trap '' SIGNAL` **ignores** a signal, for example around a tiny critical step.

A better way to protect writes is the **atomic write**: write to a temporary file, then `mv` it into place in one step (a `mv` within one file system is all-or-nothing).

</En>
<Ur>

- `trap -p` chalte traps dikhata hai.
- `trap - SIGNAL` pehle wala rawaiya wapas laata hai.
- `trap '' SIGNAL` signal **nazar andaz** karta hai, maslan kisi chhote ahem step ke gird.

Likhne ko bachane ka behtar tareeqa **atomic write** hai: temporary file me likho, phir ek qadam me `mv` se jagah par rakho (ek file system ke andar `mv` ya to poora hota hai ya bilkul nahi).

</Ur>
</Tr>

```bash
trap 'echo bye' EXIT
trap -p EXIT
trap - EXIT
trap -p EXIT
echo "EXIT trap removed"
```

```text output
trap -- 'echo bye' EXIT
EXIT trap removed
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Cleanup at the end of the script">

```text
tmp=$(mktemp -d)
do_work                 # fails → set -e stops here
rm -rf "$tmp"           # never runs
```

</Bad>
<Good title="Cleanup in an EXIT trap">

```text
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT
do_work                 # fails → trap still cleans up
```

</Good>
</Compare>

<Compare>
<Bad title="Double quotes in trap">

```text
trap "rm -rf $dir" EXIT      # $dir is expanded NOW (maybe still empty)
```

</Bad>
<Good title="Single quotes in trap">

```text
trap 'rm -rf "$dir"' EXIT    # $dir is expanded when the trap runs
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Expecting to trap SIGKILL** (`kill -9`): impossible; nothing runs. Only SIGTERM gives you a chance.
- **Forgetting `set -E`**: ERR traps silently don't fire inside functions.
- **Lock files made with `touch` and deleted at the end**: a crash leaves a stale lock forever. Use `flock`.
- **Container scripts that ignore SIGTERM**: slow, unclean shutdowns.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **SIGKILL (`kill -9`) pakarne ki umeed**: na-mumkin; kuch nahi chalta. Sirf SIGTERM mauqa deta hai.
- **`set -E` bhoolna**: ERR traps functions ke andar khamoshi se nahi chalte.
- **`touch` se bani aur aakhir me mitne wali lock files**: crash hamesha ke liye purana lock chhor deta hai. `flock` istemal karein.
- **SIGTERM nazar andaz karne wale container scripts**: dheema, ganda band hona.

</Ur>
</Tr>

mkdir -p ~/trap-lab && cd ~/trap-lab

set -e

[[ -d $(cat lastdir.txt) ]] && echo "leftover!" || echo "temporary folder was cleaned up"

## Remember

<Takeaways>
<Tr>
<En>

- Signals: INT (Ctrl+C, 2), TERM (stop, 15), HUP (1), KILL (9, can't be trapped).
- Exit code 128 + N = killed by signal N (130, 137, 143).
- `trap cleanup EXIT` right after `mktemp`; it runs on every way out.

<DeepDive title="Real world: a Docker entrypoint that stops fast">

An entrypoint that starts the app in the background, forwards SIGTERM to it, and always cleans up, so `docker stop` shuts down in seconds instead of waiting for the 10-second kill:

```bash
#!/usr/bin/env bash
# entrypoint.sh
set -Eeuo pipefail

tmp=$(mktemp -d)
log() { echo "[entrypoint] $*"; }

cleanup() {
  log "cleaning up"
  rm -rf "$tmp"
}
trap cleanup EXIT
trap 'log "error on line $LINENO"' ERR

shutdown() {
  log "SIGTERM received, stopping app (pid $app_pid)"
  kill -TERM "$app_pid" 2> /dev/null || true
  wait "$app_pid" || true
  exit 0
}
trap shutdown TERM INT

log "rendering config"
envsubst < /app/config.template > "$tmp/config.yml"

log "starting app"
/app/server --config "$tmp/config.yml" &
app_pid=$!
wait "$app_pid"
```

- Without the TERM trap, Bash as PID 1 in a container **ignores** SIGTERM, and Docker has to kill everything with SIGKILL after the timeout, losing in-flight requests.
- `exec /app/server …` is simpler when no cleanup is needed: the app replaces the shell and gets signals directly.

</DeepDive>

<DeepDive title="Security lens">

Leftovers are a security problem: temporary files often contain secrets, database dumps or rendered configs with passwords.

- **Always pair `mktemp` with `trap … EXIT`** so secrets in temporary files never outlive the script.
- **`umask 077`** before creating temporary files keeps them private while they exist.
- **Lock files in shared folders** like `/tmp` can be pre-created by other users; prefer `flock` on a file in a directory only your user can write (`/run/user/$UID`, or `/var/lock` for root services).
- **Forensics tip:** during an incident, don't `kill -9` a suspicious process first; it destroys its memory. Investigate (`ls -l /proc/PID/exe`, `cat /proc/PID/cmdline`) before stopping it.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between SIGTERM and SIGKILL?">
SIGTERM (15) asks a process to terminate; the process can catch it, clean up and exit gracefully. SIGKILL (9) is handled by the kernel and cannot be caught, blocked or ignored, so the process is stopped immediately with no cleanup. Tools like Docker and systemd send SIGTERM first and SIGKILL only after a timeout.
</QA>

<QA q="How do you make sure a script always deletes its temporary files?">
Create them with mktemp and register a cleanup function with trap cleanup EXIT right after creation. The EXIT trap runs when the script ends normally, through exit, because of set -e, or after a handled signal such as SIGINT or SIGTERM.
</QA>

<QA q="What does trap ... ERR do and why use set -E with it?">
The ERR trap runs whenever a command returns a non-zero status in a context where set -e would apply, which makes it useful for logging the failing line ($LINENO) and command ($BASH_COMMAND). set -E (errtrace) makes the ERR trap inherited by functions, command substitutions and subshells; without it the trap does not fire inside functions.
</QA>

<QA q="Why might docker stop take 10 seconds for a container started with a Bash script?">
The script runs as PID 1, and PID 1 ignores signals it has no handler for, so SIGTERM is ignored. Docker waits for the grace period, 10 seconds by default, and then sends SIGKILL. The fix is to trap SIGTERM and forward it to the child process, or to exec the main program so it becomes PID 1 and receives signals directly.
</QA>

<QA q="How do you prevent two copies of a cron script running at the same time?">
Use flock on a lock file, for example exec 9>/var/lock/job.lock and flock -n 9 || exit 1. The kernel releases the lock automatically when the process exits, even if it crashes, so there are no stale lock files.
</QA>
