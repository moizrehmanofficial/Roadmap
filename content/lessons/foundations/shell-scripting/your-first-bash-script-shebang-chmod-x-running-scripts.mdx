<BigIdea>
<Tr>
<En>
A **Bash script** is just a text file full of terminal commands. Bash runs them **from the top line to the bottom**, exactly as if you typed them yourself. Write the commands once, and run them again any time with one word.
</En>
<Ur>
**Bash script** sirf ek text file hai jo terminal commands se bhari hai. Bash unhe **upar ki line se neeche tak** chalata hai, bilkul jaise aap khud likhte. Commands ek dafa likhein, aur jab chahein ek lafz se dobara chalayen.

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Script**: a file of commands, usually ending in `.sh`.
- **Shebang**: the first line, `#!/usr/bin/env bash`. It says **which program** should run the file.
- **`chmod +x script.sh`**: gives the file permission to run.
- **`./script.sh`**: runs it.
- **`set -euo pipefail`**: a safety line that makes the script **stop** when something fails.

</En>
<Ur>

- **Script**: commands ki file, aam taur par `.sh` par khatam.
- **Shebang**: pehli line, `#!/usr/bin/env bash`. Ye batati hai file **kaun sa program** chalaye.
- **`chmod +x script.sh`**: file ko chalne ki ijazat deta hai.
- **`./script.sh`**: use chalata hai.
- **`set -euo pipefail`**: hifazati line jo kuch fail hone par script ko **rok** deti hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Saves time**: a 20-minute manual task becomes a 2-second command.
- **No forgotten steps**: the script does everything the same way every time.
- **Automation**: cron, CI/CD pipelines and Docker containers run scripts with no human present.
- **Career**: DevOps, cloud and security jobs all expect you to read and write Bash.

</En>
<Ur>

- **Waqt bachata hai**: 20 minute ka haath ka kaam 2 second ki command ban jata hai.
- **Koi qadam nahi bhoolta**: script har dafa sab kuch ek hi tarah karti hai.
- **Automation**: cron, CI/CD pipelines aur Docker containers insaan ke baghair scripts chalate hain.
- **Career**: DevOps, cloud aur security ki har naukri Bash parhna aur likhna maangti hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- any time you type the same terminal steps **more than twice**
- whenever something must happen **automatically** (backups at 2 a.m., deploys on every push)

</En>
<Ur>

- jab bhi aap wahi terminal qadam **do se zyada dafa** likhein
- jab bhi kuch **khud ba khud** hona ho (raat 2 baje backups, har push par deploy)

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Four steps:

1. Write the commands in a file, with `#!/usr/bin/env bash` on line 1.
2. Add `set -euo pipefail` on line 2.
3. `chmod +x file.sh`
4. `./file.sh`

</En>
<Ur>

Chaar qadam:

1. Commands file me likhein, line 1 par `#!/usr/bin/env bash`.
2. Line 2 par `set -euo pipefail`.
3. `chmod +x file.sh`
4. `./file.sh`

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Every morning you type the same five commands on a server: check disk space, check memory, check the website is up, look at recent errors, back up a folder. It takes five minutes, and some days you forget one.

A **script** is like a **written checklist** for a very fast, very obedient assistant. Instead of saying each step out loud every morning, you write the steps down **once** and say "follow the list". The assistant never skips a step and never gets bored.

</En>
<Ur>

Har subah aap server par wahi paanch commands likhte hain: disk ki jagah check, memory check, website chal rahi hai ya nahi, haal ke errors dekhna, ek folder ka backup. Paanch minute lagte hain, aur kisi din ek bhool jate hain.

**Script** ek bohot tez, bohot farmanbardar madadgar ke liye **likhi hui checklist** jaisi hai. Har subah har qadam bol kar batane ke bajaye, aap qadam **ek dafa** likh dete hain aur kehte hain "list par chalo". Madadgar kabhi koi qadam nahi chhorta aur kabhi bore nahi hota.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Create the script file">

<Tr>
<En>

A script is a normal text file. Make it with any editor (`nano hello.sh`, VS Code), or straight from the terminal like below. `cat > file <<'EOF' … EOF` means "write everything up to the line `EOF` into this file" (a **here document**; you'll learn it properly later).

</En>
<Ur>

Script ek aam text file hai. Ise kisi bhi editor se banayen (`nano hello.sh`, VS Code), ya neeche ki tarah seedha terminal se. `cat > file <<'EOF' … EOF` ka matlab "`EOF` wali line tak sab kuch is file me likh do" (ye **here document** hai; baad me achi tarah seekhenge).

</Ur>
</Tr>

```bash
cat > hello.sh <<'EOF'
#!/usr/bin/env bash
# My first script: greets the user and shows some information
echo "Hello from my first script!"
echo "Today is $(date +%A)"
echo "You are logged in as: $(whoami)"
EOF

cat hello.sh
```

```text output
#!/usr/bin/env bash
# My first script: greets the user and shows some information
echo "Hello from my first script!"
echo "Today is $(date +%A)"
echo "You are logged in as: $(whoami)"
```

<Happened>
<Tr>
<En>

- The file `hello.sh` now holds five lines: the shebang, a comment, and three `echo` commands.
- `cat hello.sh` shows the file so we can check it.
- `$(date +%A)` will run the `date` command and put the **day name** into the sentence when the script runs.

</En>
<Ur>

- File `hello.sh` me ab paanch lines hain: shebang, ek comment, aur teen `echo` commands.
- `cat hello.sh` file dikhata hai taa ke hum check kar sakein.
- Script chalne par `$(date +%A)` `date` command chala kar **din ka naam** jumle me daal dega.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The shebang: which program runs this file?">

<Tr>
<En>

When you run `./hello.sh`, Linux looks at the **first two characters**. If they're `#!`, it starts the program named after them and hands it the file.

It's like a language label on a letter: "**This letter is in French. Give it to someone who reads French.**"

Rules: always on **line 1**, with nothing before it (not even a blank line or a space). Use `#!/usr/bin/env bash`: it finds Bash wherever it's installed.

</En>
<Ur>

Jab aap `./hello.sh` chalate hain, Linux **pehle do characters** dekhta hai. Agar wo `#!` hon, to un ke baad likha program shuru kar ke file use de deta hai.

Ye khat par zabaan ke label jaisa hai: "**Ye khat French me hai. Kisi French parhne wale ko do.**"

Qaide: hamesha **line 1** par, us se pehle kuch nahi (khaali line ya space bhi nahi). `#!/usr/bin/env bash` istemal karein: ye Bash ko dhoond leta hai jahan bhi install ho.

</Ur>
</Tr>

| Shebang | Meaning |
| --- | --- |
| `#!/usr/bin/env bash` | Find `bash` in the PATH and run it (recommended) |
| `#!/bin/bash` | Use the Bash at this exact location |
| `#!/bin/sh` | Use the minimal shell: Bash-only features may fail |
| `#!/usr/bin/env python3` | A Python script |

<Tr>
<En>

**bash, sh, zsh?** `bash` is the default on most Linux servers (and what this course teaches). `sh` is a minimal shell (often in Alpine Docker images) with fewer features, like no `[[ ]]` and no arrays. `zsh` is macOS's default and very similar for everyday use. The shebang makes sure your script always runs in Bash.

</En>
<Ur>

**bash, sh, zsh?** Zyada tar Linux servers par `bash` default hai (aur yahi ye course sikhata hai). `sh` ek chhota shell hai (aksar Alpine Docker images me) jis me kam features hain, jaise `[[ ]]` aur arrays nahi. `zsh` macOS ka default hai aur roz ke kaam me kaafi milta julta. Shebang yaqeeni banata hai ke script hamesha Bash me chale.

</Ur>
</Tr>

</Step>

<Step title="Comments: notes for humans">

<Tr>
<En>

Bash ignores everything from `#` to the end of the line (except the shebang on line 1). Use comments to explain **why** something is done, not what is already obvious. `# keep 7 days to fit the 20 GB disk` is useful; `# delete files` above `rm` is not.

</En>
<Ur>

Bash `#` se line ke aakhir tak sab nazar andaz karta hai (siwaye line 1 ke shebang ke). Comments se batayen kuch **kyun** kiya gaya, jo wazeh hai wo nahi. `# 20 GB disk me fit karne ke liye 7 din rakho` kaam ka hai; `rm` ke upar `# files delete karo` nahi.

</Ur>
</Tr>

```bash
# This whole line is a comment
echo "Comments are ignored"   # this part is a comment too
# echo "This line is switched off"
```

```text output
Comments are ignored
```

<Happened>
<Tr>
<En>Only the `echo` without `#` in front ran. Putting `#` in front of a line is also a quick way to **switch it off** for a moment.</En>
<Ur>Sirf wo `echo` chala jis ke aage `#` nahi tha. Line ke aage `#` lagana use thori der ke liye **band karne** ka aasaan tareeqa bhi hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="chmod +x: permission to run">

<Tr>
<En>

New files are **not** allowed to run as programs, so a random text file can't be executed by accident. Give your script permission **once** with `chmod +x`.

</En>
<Ur>

Nayi files ko program ki tarah chalne ki ijazat **nahi** hoti, taa ke koi bhi text file ghalti se na chal jaye. Apni script ko **ek dafa** `chmod +x` se ijazat dein.

</Ur>
</Tr>

```bash
printf '#!/usr/bin/env bash\necho "It works!"\n' > hello.sh

./hello.sh 2>&1 | sed 's/.*: //'
echo "exit code: ${PIPESTATUS[0]}"

chmod +x hello.sh
./hello.sh
```

```text output
Permission denied
exit code: 126
It works!
```

<Happened>
<Tr>
<En>

- First run: not executable yet, so "Permission denied" with exit code **126** ("found it, but can't run it").
- `chmod +x hello.sh` added the permission.
- Second run: "It works!".
- `ls -l` shows the change: `-rw-r--r--` before, `-rwxr-xr-x` after. The `x` letters mean "executable". (The `sed` only shortens the error so it looks the same on every computer.)

</En>
<Ur>

- Pehla run: abhi chalne layak nahi, isliye "Permission denied" aur exit code **126** ("mil gayi, lekin chala nahi sakta").
- `chmod +x hello.sh` ne ijazat de di.
- Doosra run: "It works!".
- `ls -l` farq dikhata hai: pehle `-rw-r--r--`, baad me `-rwxr-xr-x`. `x` letters ka matlab "chalne layak". (`sed` sirf error chhota karta hai taa ke har computer par ek jaisa dikhe.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Different ways to run a script">

<Tr>
<En>

| Command | Needs `chmod +x`? | Uses the shebang? | Runs in |
| --- | --- | --- | --- |
| `./script.sh` | Yes | Yes | A **new** shell |
| `bash script.sh` | No | No (you chose Bash) | A **new** shell |
| `script.sh` (no `./`) | Yes | Yes | New shell, only if its folder is in PATH |
| `source script.sh` or `. script.sh` | No | No | **Your current** shell |

Why `./`? For safety, Linux doesn't look for commands in the folder you're in. `./` means "the file in **this** folder".

</En>
<Ur>

| Command | `chmod +x` chahiye? | Shebang istemal? | Kahan chalti hai |
| --- | --- | --- | --- |
| `./script.sh` | Haan | Haan | **Naye** shell me |
| `bash script.sh` | Nahi | Nahi (Bash aap ne chuna) | **Naye** shell me |
| `script.sh` (baghair `./`) | Haan | Haan | Naya shell, sirf agar folder PATH me ho |
| `source script.sh` ya `. script.sh` | Nahi | Nahi | **Aap ke mojooda** shell me |

`./` kyun? Hifazat ke liye Linux us folder me commands nahi dhoondta jis me aap hain. `./` ka matlab "**isi** folder wali file".

</Ur>
</Tr>

<Tr>
<En>The difference between a **new** shell and **your** shell matters:</En>
<Ur>**Naye** shell aur **aap ke** shell ka farq ahem hai:</Ur>
</Tr>

```bash
mkdir -p projects
printf 'cd projects\nmy_var="set by the script"\n' > goto.sh

bash goto.sh
echo "After bash:   folder=$(basename "$PWD")  my_var=[${my_var:-}]"

source goto.sh
echo "After source: folder=$(basename "$PWD")  my_var=[${my_var:-}]"
```

```text output
After bash:   folder=lab  my_var=[]
After source: folder=projects  my_var=[set by the script]
```

<Happened>
<Tr>
<En>

- `bash goto.sh` ran in a **child** shell. It changed folder and set a variable **inside the child**, then the child ended. Your terminal didn't change.
- `source goto.sh` ran the lines in **your** shell, so the folder change and the variable stayed.
- (`lab` is just the folder this example started in.) This is why "a `cd` inside my script doesn't work": it worked, in the child.

</En>
<Ur>

- `bash goto.sh` **child** shell me chala. Is ne folder badla aur variable set kiya **child ke andar**, phir child khatam ho gaya. Aap ka terminal nahi badla.
- `source goto.sh` ne lines **aap ke** shell me chalayin, isliye folder ki tabdeeli aur variable reh gaye.
- (`lab` sirf wo folder hai jahan se ye misaal shuru hui.) Isi liye "meri script me `cd` kaam nahi karta": kaam kiya tha, child me.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Scripts give back an exit code">

<Tr>
<En>

When a script ends, it returns a number to whoever ran it: `0` = success, anything else = a problem. CI pipelines, cron and other scripts read this number to know if your script **worked**.

Use `exit 1` (or another non-zero number) when your script detects a problem. `echo $?` shows the last exit code.

</En>
<Ur>

Script khatam hone par chalane wale ko ek number lautati hai: `0` = kamyabi, kuch aur = masla. CI pipelines, cron aur doosri scripts ye number parh kar jaante hain ke aap ki script **kamyab** hui ya nahi.

Jab script ko masla mile to `exit 1` (ya koi aur ghair-zero number) istemal karein. `echo $?` pichla exit code dikhata hai.

</Ur>
</Tr>

```bash
printf '#!/usr/bin/env bash\necho "Checking config..."\nexit 3\n' > check.sh
chmod +x check.sh

./check.sh
echo "The script returned: $?"
```

```text output
Checking config...
The script returned: 3
```

</Step>

<Step title="Arguments: give the script some input">

<Tr>
<En>

Words written **after** the script's name are available inside as `$1`, `$2`, … and `$#` holds **how many** there are. So the same script can work with different values without editing it. (Covered fully in **Functions and Script Arguments**.)

</En>
<Ur>

Script ke naam ke **baad** likhe alfaz andar `$1`, `$2`, … ki shakal me milte hain, aur `$#` me hai ke **kitne** hain. Is tarah ek hi script baghair edit kiye alag values ke saath chal sakti hai. (Poori tafseel **Functions and Script Arguments** me.)

</Ur>
</Tr>

```bash
printf '#!/usr/bin/env bash\necho "Hello, $1! You gave me $# argument(s)."\n' > greet.sh
chmod +x greet.sh
./greet.sh Alex
./greet.sh Sam Emma
```

```text output
Hello, Alex! You gave me 1 argument(s).
Hello, Sam! You gave me 2 argument(s).
```

</Step>

<Step title="Safe mode: set -euo pipefail">

<Tr>
<En>

By default, Bash **keeps going** after a command fails. Imagine a backup script whose `cd` failed and which then deletes files... in the wrong folder.

`set -euo pipefail` switches on three safety settings:

- `-e`: **stop** when a command fails
- `-u`: stop if you use a variable that was never set (catches typos)
- `-o pipefail`: notice failures inside pipes (`a | b`)

Put it on **line 2** of every script.

</En>
<Ur>

Default me Bash command fail hone ke baad bhi **chalta rehta** hai. Socho ek backup script jis ka `cd` fail ho gaya aur phir wo files delete karti hai... ghalat folder me.

`set -euo pipefail` teen hifazati settings on karta hai:

- `-e`: command fail ho to **ruk jao**
- `-u`: aisa variable istemal ho jo kabhi set nahi hua to ruk jao (typos pakarta hai)
- `-o pipefail`: pipes (`a | b`) ke andar ki failures bhi pakro

Ise har script ki **line 2** par rakhein.

</Ur>
</Tr>

```bash
printf 'echo "step 1"\nls /no/such/folder 2>/dev/null\necho "step 2 runs even though step 1 failed!"\n' > unsafe.sh
printf 'set -euo pipefail\necho "step 1"\nls /no/such/folder 2>/dev/null\necho "step 2 never runs"\n' > safe.sh

echo "--- without set -e:"; bash unsafe.sh; echo "exit: $?"
echo "--- with set -euo pipefail:"; bash safe.sh; echo "exit: $?"
```

```text output
--- without set -e:
step 1
step 2 runs even though step 1 failed!
exit: 0
--- with set -euo pipefail:
step 1
exit: 2
```

<Happened>
<Tr>
<En>

- Without safe mode, step 2 ran **after** the failure, and the script reported **success** (exit 0). That's the worst outcome for automation: nobody notices.
- With safe mode, the script **stopped** at the failing `ls` and returned exit code 2, so a pipeline would turn red.

</En>
<Ur>

- Safe mode ke baghair failure ke **baad** bhi step 2 chala, aur script ne **kamyabi** batayi (exit 0). Automation ke liye ye sab se bura nateeja hai: kisi ko pata nahi chalta.
- Safe mode ke saath script fail hone wale `ls` par **ruk gayi** aur exit code 2 lautaya, yani pipeline laal ho jati.

</Ur>
</Tr>
</Happened>

</Step>

Install it (`sudo apt install shellcheck`), run `shellcheck yourscript.sh`, and look up each warning code (like `SC2086`). There's also a VS Code extension, and many teams run it in CI.

</En>
<Ur>

**ShellCheck** ek muft tool hai jo aap ki script parh kar bugs ki warning deta hai: gum quotes, ghalat likhe variable naam, aisi commands jo wo nahi kartin jo aap samajhte hain. Install karein (`sudo apt install shellcheck`), `shellcheck yourscript.sh` chalayen, aur har warning code (jaise `SC2086`) dekhein. VS Code extension bhi hai, aur kai teams ise CI me chalati hain.

</Ur>
</Tr>

</Step>

<Tr>

Apna folder PATH me shamil karein (`~/.bashrc` me `export PATH="$HOME/bin:$PATH"`) aur aap apni scripts kahin se bhi naam se chala sakenge.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Windows line endings">

```text
/usr/bin/env: 'bash\r': No such file or directory
```

<Tr>
<En>The script was saved on Windows with CRLF line endings.</En>
<Ur>Script Windows par CRLF line endings ke saath save hui.</Ur>
</Tr>

</Bad>
<Good title="Save with LF">

```text
dos2unix script.sh
# and in .gitattributes:  *.sh text eol=lf
```

</Good>
</Compare>

<Compare>
<Bad title="sh script.sh for a Bash script">

```text
script.sh: 3: [[: not found
```

</Bad>
<Good title="Run it with Bash">

```text
./script.sh          # uses the shebang
bash script.sh       # or choose bash yourself
```

</Good>
</Compare>

<Compare>
<Bad title="No safe mode, secrets inside">

<Tr>
<En>The script keeps going after failures, and a password is written right in the file that's committed to Git.</En>

</Tr>

</Bad>

<Tr>
<En>Stop on errors, and read secrets from a protected file, CI secrets or a secrets manager.</En>

</Good>

## Try it yourself

<Challenge title="Build a system-info script">

<Tr>
<En>
Run this lab. It writes a script, shows the permissions **before and after** `chmod +x`, runs it two ways, and cleans up. The `sed` on the fifth command hides your real host name so the result matches ours.
</En>
<Ur>
Ye lab chalayen. Ye ek script likhta hai, `chmod +x` se **pehle aur baad** ki permissions dikhata hai, use do tareeqon se chalata hai, aur safai karta hai. Paanchvi command ka `sed` aap ka asal host naam chhupa deta hai taa ke nateeja hamare jaisa ho.
</Ur>
</Tr>

```bash
mkdir -p ~/script-lab && cd ~/script-lab

cat > sysinfo.sh <<'EOF'
#!/usr/bin/env bash
# sysinfo.sh — print a short summary of this machine
set -euo pipefail

echo "=== System summary ==="
echo "Host:    $(hostname)"
echo "User:    $(whoami)"
echo "Kernel:  $(uname -r)"
echo "Shell:   $BASH_VERSION"
echo "Folder:  $PWD"
echo "Files here: $(ls | wc -l)"
EOF

ls -l sysinfo.sh | cut -c1-10
chmod +x sysinfo.sh
ls -l sysinfo.sh | cut -c1-10
./sysinfo.sh | head -2 | sed -E 's/(Host: +).*/\1<your host name>/'
bash sysinfo.sh | grep -c ":"
echo "exit code: $?"

cd ~ && rm -rf ~/script-lab
```

```text output
-rw-r--r--
-rwxr-xr-x
=== System summary ===
Host:    <your host name>
6
exit code: 0
```

</Challenge>

<Challenge title="Which way should I run it?">

<Tr>

<DeepDive title="Real world: a deploy script">

A developer deploys a Next.js app to a VPS by typing the same eight commands every time, and once forgot the database migration, taking the site down. They turn it into `scripts/deploy.sh`:

```bash
#!/usr/bin/env bash
# Deploy the current main branch to production.
# Usage: ./scripts/deploy.sh
set -euo pipefail

SERVER="deploy@203.0.113.10"
APP_DIR="/srv/app"

echo "▶ Running tests locally"
npm ci
npm test

echo "▶ Building"
npm run build

echo "▶ Uploading build"
rsync -az --delete .next/ package.json package-lock.json public/ "$SERVER:$APP_DIR/"

echo "▶ Installing, migrating and restarting on the server"
ssh "$SERVER" "cd $APP_DIR && npm ci --omit=dev && npx prisma migrate deploy && sudo systemctl restart app"

echo "▶ Health check"
curl -fsS https://example.com/api/health > /dev/null
echo "✓ Deployed"
```

Now every deploy is identical, the tests always run first, a failed step stops everything (`set -e`, `curl -f`), and the same script later moves unchanged into a GitHub Actions workflow.

</DeepDive>

<DeepDive title="Security lens">

A script runs with all the permissions of whoever runs it: often root, often unattended. Treat scripts like code: reviewed, linted, version-controlled and least-privileged.

- **Never pipe unknown scripts into a shell** (`curl … | bash`, especially with `sudo`). Download, read, verify, then run.
- **Who can edit a script matters as much as what it does.** A root-run script (cron, systemd, sudo rule) that a normal user can modify is a privilege-escalation path. Keep such scripts owned by root, mode `755` or stricter, in root-owned folders.
- **No secrets in scripts or on their command lines.** Read them from a protected file, CI-injected environment, or a secrets manager.
- **Quote every variable** (`"$file"`, not `$file`): unquoted variables enable injection and break on spaces. ShellCheck catches most of these.
- **Use absolute paths or a fixed `PATH`** in scripts run by root or cron, to prevent PATH hijacking.
- **Read malicious scripts safely:** during incident response, open dropped scripts with `less` or `cat`, never run them. Many attacks are a single Bash one-liner; being fluent in Bash lets you understand them.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does the shebang line do?">
It is the first line of a script, starting with #!, that tells the kernel which interpreter to run the file with when it is executed directly. For example `#!/usr/bin/env bash` runs the script with the first bash found in PATH. Without it, the script runs in whatever shell invoked it, which may not support the syntax used.
</QA>

<QA q="What is the difference between ./script.sh, bash script.sh and source script.sh?">
./script.sh executes the file as a program: it needs execute permission and uses its shebang, running in a new child process. bash script.sh runs it with bash in a new process regardless of permissions or shebang. source (or .) runs the commands in the current shell, so variables, directory changes and exports persist after it finishes.
</QA>

<QA q="Why do you need ./ to run a script in the current directory?">
The shell only searches directories listed in PATH for commands, and the current directory is deliberately not in PATH. ./ gives an explicit relative path. Keeping . out of PATH prevents an attacker from planting a program named like a common command (ls, sudo) in a directory you happen to be in.
</QA>

<QA q="What does set -euo pipefail do and why use it?">
-e exits the script when a command fails, -u treats use of unset variables as an error, and -o pipefail makes a pipeline fail if any command in it fails rather than only the last. Together they stop scripts from continuing in a broken state, for example running rm after a failed cd, which is a common cause of destructive script bugs.
</QA>

<QA q="When would you choose Python over Bash for automation?">
Bash is ideal for gluing commands together: running programs, moving files, short sequential tasks. Python is better once a script needs non-trivial logic, data structures, JSON or API handling, error handling with retries, testing, or exceeds roughly a hundred lines, because it is easier to read, test and maintain and has rich libraries such as boto3 and requests.
</QA>

</DeepDive>
