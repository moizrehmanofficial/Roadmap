<Callout type="tip" title="In one minute">
A **Bash script** is a plain text file full of terminal commands. Bash runs them from the top line to the bottom, exactly as if you typed them. The first line, `#!/usr/bin/env bash`, is the **shebang** — it says which program should run the file. Give the file **execute permission** with `chmod +x script.sh`, then run it with `./script.sh`. Start real scripts with `set -euo pipefail` so they stop on errors.
</Callout>

## Start from zero

### Why write a script at all?

Every morning you type the same five commands on a server: check disk space, check memory, check whether the website is up, look at the last errors in the log, and back up a folder. It takes five minutes, and some days you forget one.

<Callout type="analogy">
A **script** is like a written checklist that a very fast, very obedient assistant follows. Instead of telling the assistant each step out loud every morning, you write the steps on paper once and say "follow the list". The assistant never skips a step and never gets bored.
</Callout>

Write those five commands into a file once, and from then on one command — `./morning-check.sh` — does everything in a second, the same way every time. That is all a script is: **commands saved in a file so you can run them again**.

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Shell** | The program that reads what you type in the terminal and runs it | Bash, zsh, sh |
| **Bash** | The most common shell on Linux servers | `bash --version` |
| **Script** | A text file containing shell commands | `backup.sh` |
| **Shebang** | The first line of a script, starting with `#!`, that names the program to run it | `#!/usr/bin/env bash` |
| **Comment** | A line (or end of a line) starting with `#` that Bash ignores — notes for humans | `# backup the database` |
| **Permission** | Whether a user may read, write or **execute** (run) a file | `chmod +x` |
| **Path** | The location of a file | `./hello.sh` means "hello.sh in this folder" |
| **Exit code** | The number a program returns when it finishes; 0 = success | `echo $?` |

## What is it?

A **Bash script** is a text file whose lines are commands. When you run it, Bash reads the file and executes the commands **one after another, top to bottom**. Anything you can type in the terminal can go in a script: `ls`, `mkdir`, `cp`, `curl`, `docker`, `git`, `systemctl`…

Scripts usually end in `.sh`. The ending is only a hint for humans — Linux does not need it — but it makes files easy to recognise.

### Bash, sh, zsh — which one?

| Shell | Where you meet it | Notes |
| --- | --- | --- |
| **bash** | Default on most Linux servers, Git Bash on Windows | What this course teaches |
| **sh** | The minimal shell every Unix has (often `dash` on Ubuntu, `ash` in Alpine Docker images) | Fewer features: no `[[ ]]`, no arrays |
| **zsh** | Default terminal on macOS | Very similar to Bash for everyday use |

Write `#!/usr/bin/env bash` at the top so your script always runs in Bash, whatever the user's terminal is.

## Why does it matter?

- **Saves time:** a 20-minute manual task becomes a 2-second command.
- **No mistakes:** the script does the steps the same way every time.
- **Shareable:** a teammate runs your script instead of following a long document.
- **Automation:** scripts can be run by cron at 2 a.m., by CI/CD pipelines on every push, and by Docker containers at startup — with no human present.
- **Career:** DevOps, cloud, and security roles all expect you to read and write Bash scripts; it is the glue between every other tool.

## When and where do you use it?

**When:** any time you do the same terminal steps more than twice, or need something to happen automatically.

**Where:**

| Place | Example |
| --- | --- |
| Servers | Backup scripts, cleanup jobs, health checks |
| CI/CD (GitHub Actions, GitLab CI) | Build, test and deploy steps |
| Docker | `entrypoint.sh` that prepares a container before the app starts |
| Cloud | Setup scripts that run when a new virtual machine boots |
| Security | Collecting logs during an incident, checking server settings |
| Your own laptop | Setting up a new project, renaming many files |

## Concepts one by one

### 1. Creating the script file

<Explain>
<What>
A normal text file that you create with any editor (`nano`, `vim`, VS Code) or straight from the terminal.
</What>
<Why>
The commands must be saved somewhere so they can be run again.
</Why>
<When>
At the start of every new script.
</When>
<Where>
In a project folder, or a personal `~/bin` folder for your own tools.
</Where>
<How>
`nano hello.sh` opens an editor; type the lines, save with Ctrl+O, exit with Ctrl+X. Or write the file in one go with `cat > file <<'EOF' … EOF` as below.
</How>
</Explain>

```bash
cat > hello.sh <<'EOF'
#!/usr/bin/env bash
# My first script: greets the user and shows some information
echo "Hello from my first script!"
echo "Today is $(date +%A)"
echo "You are logged in as: $(whoami)"
EOF

cat hello.sh
```

```text output
#!/usr/bin/env bash
# My first script: greets the user and shows some information
echo "Hello from my first script!"
echo "Today is $(date +%A)"
echo "You are logged in as: $(whoami)"
```

- `cat > hello.sh <<'EOF'` — "write everything up to the line `EOF` into `hello.sh`". This is a **here document**; you will learn it properly later. In real life you would usually type the lines in an editor.
- `cat hello.sh` — show the file's contents to check them.
- `$(date +%A)` — runs the `date` command and puts its output (the day name) into the sentence.

### 2. The shebang line

<Explain>
<What>
The very first line of a script, starting with `#!` followed by the path of the program that should run the file.
</What>
<Why>
When you run `./hello.sh`, Linux reads the first two characters. If they are `#!`, it starts the named program and gives it the file. Without a shebang, the file might be run by a different shell (like `sh`) where some Bash features do not work.
</Why>
<When>
In every script, always on line 1, with nothing before it — not even a blank line or a space.
</When>
<Where>
Bash scripts, Python scripts (`#!/usr/bin/env python3`), Node scripts (`#!/usr/bin/env node`).
</Where>
<How>
Write `#!/usr/bin/env bash`. `env` searches your PATH for `bash`, so it works on Linux, macOS and systems where Bash is not in `/bin`. `#!/bin/bash` also works on almost every Linux server.
</How>
</Explain>

<Callout type="analogy">
The shebang is like the language label on a letter: "**This letter is in Urdu — give it to someone who reads Urdu.**" The operating system reads the label and hands the file to the right reader.
</Callout>

| Shebang | Meaning |
| --- | --- |
| `#!/usr/bin/env bash` | Find `bash` in the PATH and run it (recommended) |
| `#!/bin/bash` | Use the Bash at this exact location |
| `#!/bin/sh` | Use the minimal shell — Bash-only features may fail |
| `#!/usr/bin/env python3` | A Python script |

### 3. Comments

<Explain>
<What>
Text that starts with `#`. Bash ignores everything from `#` to the end of the line (except the shebang on line 1).
</What>
<Why>
To explain **why** the code does something, for teammates and for your future self.
</Why>
<When>
At the top of the script (what it does, how to run it) and above any line that is not obvious.
</When>
<Where>
Any line of the script, or at the end of a command line.
</Where>
<How>
`# your note`. Explain the reason, not what is already obvious: `# keep 7 days to fit the 20 GB disk` is useful; `# delete files` above `rm` is not.
</How>
</Explain>

```bash
# This whole line is a comment
echo "Comments are ignored"   # this part is a comment too
# echo "This line is switched off"
```

```text output
Comments are ignored
```

### 4. Execute permission: `chmod +x`

<Explain>
<What>
A permission flag that allows a file to be run as a program. New files do not have it.
</What>
<Why>
Linux will not run a file as a program unless it is marked executable. This prevents random text files from being executed by accident.
</Why>
<When>
Once, after creating the script.
</When>
<Where>
Any script you want to run with `./name.sh`.
</Where>
<How>
`chmod +x hello.sh` adds execute permission. `ls -l` shows it as `x` in the permissions column.
</How>
</Explain>

```bash
printf '#!/usr/bin/env bash\necho "It works!"\n' > hello.sh

./hello.sh 2>&1 | sed 's/.*: //'
echo "exit code: ${PIPESTATUS[0]}"

chmod +x hello.sh
./hello.sh
```

```text output
Permission denied
exit code: 126
It works!
```

- First run: the file is not executable yet, so Bash refuses with "Permission denied" and exit code `126` ("found but cannot run").
- `chmod +x hello.sh` — add the execute permission.
- Second run: it works.
- (`sed` only shortens the error message so it looks the same on every computer.)

You can see the change with `ls -l hello.sh`: before, the permissions look like `-rw-r--r--`; after, like `-rwxr-xr-x` — the `x` letters mean "executable".

### 5. Ways to run a script

<Explain>
<What>
Several ways to start a script, which differ in whether they need the shebang/permission and in **where** the commands run.
</What>
<Why>
Choosing the wrong one causes confusing problems, for example a `cd` inside a script that "does not work".
</Why>
<When>
Every time you run a script.
</When>
<Where>
In the terminal, in cron jobs, in CI pipelines.
</Where>
<How>
Use `./script.sh` normally. Use `bash script.sh` to run a file without execute permission. Use `source script.sh` only when you **want** the script to change your current terminal (load variables or functions).
</How>
</Explain>

| Command | Needs `chmod +x`? | Uses shebang? | Runs in |
| --- | --- | --- | --- |
| `./script.sh` | Yes | Yes | A **new** shell process |
| `bash script.sh` | No | No (Bash is chosen by you) | A **new** shell process |
| `script.sh` (no `./`) | Yes | Yes | New process — only works if the folder is in your PATH |
| `source script.sh` or `. script.sh` | No | No | **Your current** shell |

Why `./`? For safety, Linux does not look for commands in the current folder. `./` means "the file in **this** folder".

The difference between a new shell and your current shell:

```bash
mkdir -p projects
printf 'cd projects\nmy_var="set by the script"\n' > goto.sh

bash goto.sh
echo "After bash:   folder=$(basename "$PWD")  my_var=[${my_var:-}]"

source goto.sh
echo "After source: folder=$(basename "$PWD")  my_var=[${my_var:-}]"
```

```text output
After bash:   folder=lab  my_var=[]
After source: folder=projects  my_var=[set by the script]
```

- `bash goto.sh` runs in a **child** process. It changes folder and sets a variable — in the child — and then the child exits. Your terminal is unchanged.
- `source goto.sh` runs the lines in **your** shell, so the folder change and the variable stay.
- (In this output, `lab` is the name of the folder the example was started in.)

### 6. Scripts give back an exit code

<Explain>
<What>
When a script finishes, it returns a number to whoever ran it: by default the exit code of its **last** command, or whatever you give to `exit`.
</What>
<Why>
Other programs (CI pipelines, cron, other scripts) use it to know whether your script succeeded. A failing step must make the pipeline red.
</Why>
<When>
Use `exit 1` (or another non-zero number) whenever the script detects a problem.
</When>
<Where>
Guard checks at the top of scripts, error handling.
</Where>
<How>
`exit 0` = success, `exit 1` = general failure. Check the last exit code with `echo $?`.
</How>
</Explain>

```bash
printf '#!/usr/bin/env bash\necho "Checking config..."\nexit 3\n' > check.sh
chmod +x check.sh

./check.sh
echo "The script returned: $?"
```

```text output
Checking config...
The script returned: 3
```

### 7. Taking input: arguments (a first look)

<Explain>
<What>
Words written after the script name, available inside as `$1`, `$2`, … and `$#` (how many).
</What>
<Why>
So the same script can work with different values without editing it.
</Why>
<When>
Whenever something changes between runs: a name, a folder, an environment.
</When>
<Where>
Almost all useful scripts.
</Where>
<How>
`./greet.sh Moiz` → inside, `$1` is `Moiz`. (Covered fully in **Functions and Script Arguments**.)
</How>
</Explain>

```bash
printf '#!/usr/bin/env bash\necho "Hello, $1! You gave me $# argument(s)."\n' > greet.sh
chmod +x greet.sh
./greet.sh Moiz
./greet.sh Ali Sara
```

```text output
Hello, Moiz! You gave me 1 argument(s).
Hello, Ali! You gave me 2 argument(s).
```

### 8. Safe mode: `set -euo pipefail`

<Explain>
<What>
A line near the top of a script that switches on three safety settings: stop on errors (`-e`), stop on unset variables (`-u`), and notice failures inside pipes (`-o pipefail`).
</What>
<Why>
By default Bash **keeps going** after a command fails. A backup script whose `cd` failed might then delete files in the wrong folder.
</Why>
<When>
In every script you write, on the line after the shebang.
</When>
<Where>
All professional scripts start like this.
</Where>
<How>
`set -euo pipefail`. Details and edge cases are in the lesson **Writing Safe Scripts**.
</How>
</Explain>

```bash
printf 'echo "step 1"\nls /no/such/folder 2>/dev/null\necho "step 2 runs even though step 1 failed!"\n' > unsafe.sh
printf 'set -euo pipefail\necho "step 1"\nls /no/such/folder 2>/dev/null\necho "step 2 never runs"\n' > safe.sh

echo "--- without set -e:"; bash unsafe.sh; echo "exit: $?"
echo "--- with set -euo pipefail:"; bash safe.sh; echo "exit: $?"
```

```text output
--- without set -e:
step 1
step 2 runs even though step 1 failed!
exit: 0
--- with set -euo pipefail:
step 1
exit: 2
```

Without safe mode, the script reports **success** (exit 0) even though a command failed — the worst possible outcome for automation.

### 9. Checking scripts with ShellCheck

<Explain>
<What>
A free tool that reads your script and warns about bugs: missing quotes, typos in variable names, commands that behave differently than you expect.
</What>
<Why>
It catches mistakes before they run on a real server.
</Why>
<When>
Every time you write or change a script. Many teams run it automatically in CI.
</When>
<Where>
Terminal (`shellcheck script.sh`), VS Code extension, GitHub Actions.
</Where>
<How>
Install with `sudo apt install shellcheck` (or `brew install shellcheck`), then run `shellcheck yourscript.sh`. Each warning has a code like `SC2086` you can look up.
</How>
</Explain>

### 10. Where to keep your scripts

<Explain>
<What>
A place on disk for scripts, chosen so they are easy to find and run.
</What>
<Why>
Scripts scattered across random folders get lost and duplicated.
</Why>
<When>
As soon as you have more than a couple of scripts.
</When>
<Where>
Project scripts: a `scripts/` folder **inside the project's Git repository**. Personal tools: `~/bin` or `~/.local/bin`. System-wide tools: `/usr/local/bin`.
</Where>
<How>
Put the folder in your PATH (`export PATH="$HOME/bin:$PATH"` in `~/.bashrc`) so you can run the script by name from anywhere.
</How>
</Explain>

## Hands-on

```bash
mkdir -p ~/script-lab && cd ~/script-lab

cat > sysinfo.sh <<'EOF'
#!/usr/bin/env bash
# sysinfo.sh — print a short summary of this machine
set -euo pipefail

echo "=== System summary ==="
echo "Host:    $(hostname)"
echo "User:    $(whoami)"
echo "Kernel:  $(uname -r)"
echo "Shell:   $BASH_VERSION"
echo "Folder:  $PWD"
echo "Files here: $(ls | wc -l)"
EOF

ls -l sysinfo.sh | cut -c1-10
chmod +x sysinfo.sh
ls -l sysinfo.sh | cut -c1-10
./sysinfo.sh | head -2
bash sysinfo.sh | grep -c ":"
echo "exit code: $?"

cd ~ && rm -rf ~/script-lab
```

```text output
-rw-r--r--
-rwxr-xr-x
=== System summary ===
Host:    your-hostname
6
exit code: 0
```

Your host name, kernel and other values will be different — that is expected.

## Real-world example

A developer deploys a Next.js app to a VPS by typing the same eight commands every time — and once forgot the database migration, taking the site down. They turn it into `scripts/deploy.sh`:

```bash
#!/usr/bin/env bash
# Deploy the current main branch to production.
# Usage: ./scripts/deploy.sh
set -euo pipefail

SERVER="deploy@203.0.113.10"
APP_DIR="/srv/app"

echo "▶ Running tests locally"
npm ci
npm test

echo "▶ Building"
npm run build

echo "▶ Uploading build"
rsync -az --delete .next/ package.json package-lock.json public/ "$SERVER:$APP_DIR/"

echo "▶ Installing, migrating and restarting on the server"
ssh "$SERVER" "cd $APP_DIR && npm ci --omit=dev && npx prisma migrate deploy && sudo systemctl restart app"

echo "▶ Health check"
curl -fsS https://example.com/api/health > /dev/null
echo "✓ Deployed"
```

Now every deploy is identical, the tests always run first, a failed step stops everything (`set -e`, `curl -f`), and the same script later moves unchanged into a GitHub Actions workflow.

## Common mistakes

- **No shebang**, so the script runs in a different shell than you tested with.
- **Windows line endings (CRLF)** after editing on Windows: `/usr/bin/env: 'bash\r': No such file or directory`. Fix with `dos2unix script.sh` and a `.gitattributes` rule (`*.sh text eol=lf`).
- **Forgetting `chmod +x`**, or the executable bit not committed to Git.
- **Running with `sh script.sh`** when it uses bash features — errors like `[[: not found`.
- **No `set -euo pipefail`**, so the script continues after failures.
- **Hard-coding secrets** in scripts that get committed.
- **Writing a 600-line Bash program** that should have been Python.

## Security lens

<Callout type="security">
A script runs with all the permissions of whoever runs it — often root, often unattended. Treat scripts like code: reviewed, linted, version-controlled and least-privileged.
</Callout>

- **Never pipe unknown scripts into a shell** (`curl … | bash`, especially with `sudo`). Download, read, verify, then run.
- **Who can edit a script matters as much as what it does.** A root-run script (cron, systemd, sudo rule) that a normal user can modify is a privilege-escalation path. Keep such scripts owned by root, mode `755` or stricter, in root-owned directories.
- **No secrets in scripts or in their command lines** — read them from a protected file, environment injected by CI, or a secrets manager.
- **Quote every variable** (`"$file"`, not `$file`) — unquoted variables enable injection and break on spaces. ShellCheck catches most of these.
- **Use absolute paths or a fixed `PATH`** in scripts run by root or cron, to prevent PATH hijacking.
- **Read malicious scripts safely:** during incident response, open dropped scripts with `less` or `cat`, never run them. Many attacks are a single Bash one-liner — being fluent in Bash lets you understand them.

## Interview questions

<QA q="What does the shebang line do?">
It is the first line of a script, starting with #!, that tells the kernel which interpreter to run the file with when it is executed directly. For example `#!/usr/bin/env bash` runs the script with the first bash found in PATH. Without it, the script runs in whatever shell invoked it, which may not support the syntax used.
</QA>

<QA q="What is the difference between ./script.sh, bash script.sh and source script.sh?">
./script.sh executes the file as a program: it needs execute permission and uses its shebang, running in a new child process. bash script.sh runs it with bash in a new process regardless of permissions or shebang. source (or .) runs the commands in the current shell, so variables, directory changes and exports persist after it finishes.
</QA>

<QA q="Why do you need ./ to run a script in the current directory?">
The shell only searches directories listed in PATH for commands, and the current directory is deliberately not in PATH. ./ gives an explicit relative path. Keeping . out of PATH prevents an attacker from planting a program named like a common command (ls, sudo) in a directory you happen to be in.
</QA>

<QA q="What does set -euo pipefail do and why use it?">
-e exits the script when a command fails, -u treats use of unset variables as an error, and -o pipefail makes a pipeline fail if any command in it fails rather than only the last. Together they stop scripts from continuing in a broken state, for example running rm after a failed cd, which is a common cause of destructive script bugs.
</QA>

<QA q="When would you choose Python over Bash for automation?">
Bash is ideal for gluing commands together: running programs, moving files, short sequential tasks. Python is better once a script needs non-trivial logic, data structures, JSON or API handling, error handling with retries, testing, or exceeds roughly a hundred lines, because it is easier to read, test and maintain and has rich libraries such as boto3 and requests.
</QA>

## Key terms

<Terms>
  <Term name="Shell script">A text file of shell commands executed in order.</Term>
  <Term name="Shebang">The first line starting with #! that names the interpreter.</Term>
  <Term name="Interpreter">The program that reads and runs a script, such as bash or python3.</Term>
  <Term name="Execute permission">The x permission bit required to run a file directly.</Term>
  <Term name="source">Runs a script in the current shell instead of a new process.</Term>
  <Term name="Exit code">A number a script returns: 0 for success, non-zero for failure.</Term>
  <Term name="set -euo pipefail">Bash options that stop a script on errors, unset variables and pipe failures.</Term>
  <Term name="POSIX sh">The standard minimal shell language supported by all Unix shells.</Term>
  <Term name="ShellCheck">A static analysis tool that finds bugs in shell scripts.</Term>
</Terms>
