<Callout type="tip" title="In one minute">
`read -r -p "Your name: " name` shows a question and stores the typed answer in `name`. Add `-s` to hide typing (passwords), `-t 10` for a 10-second time limit, `-n 1` to read one key. A **here document** feeds several lines of text into a command: `cat > app.conf <<EOF … EOF` writes a file. With `<<EOF`, variables inside are replaced; with `<<'EOF'` (quoted), the text is kept exactly as written. `<<-EOF` allows indenting with tabs; `<<< "text"` (a here **string**) feeds a single line.
</Callout>

## Start from zero

### Two kinds of input

So far, scripts got their information from **arguments** (`./deploy.sh prod`). But sometimes a script needs to **ask** while it runs:

- "Are you sure you want to delete 300 files? (y/n)"
- "Enter the database password:"
- "Which environment? 1) dev 2) staging 3) prod"

And sometimes a script needs to **produce** a block of text — a config file, an email, a SQL script — with many lines.

<Callout type="analogy">
`read` is a **receptionist with a form**: she asks a question, waits for your answer, and writes it in the right box. A **here document** is a **pre-written letter** you hand over in one go instead of dictating it word by word: everything between "Dear…" and "Regards" is delivered together.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Input** | Information given to a program | the name you type |
| **stdin** | The input stream (keyboard by default) | where `read` reads from |
| **Prompt** | The question shown before waiting for input | `Your name: ` |
| **Interactive** | A script a person sits in front of and answers | an installer |
| **Here document (heredoc)** | Several lines of text written inside the script and fed to a command | `cat <<EOF … EOF` |
| **Delimiter** | The word that marks the end of a heredoc | `EOF` |
| **Here string** | One string fed to a command as input | `grep x <<< "$text"` |

## What is it?

- **`read`** is a Bash built-in that reads **one line** from input (the keyboard, a file or a pipe) and stores it in one or more variables.
- A **here document** (`<<WORD … WORD`) is a way to give a command multi-line input written directly in the script.
- A **here string** (`<<< "text"`) gives a command a single string as input.

## Why does it matter?

- **Safety:** confirmations ("type the environment name to continue") stop people from destroying production by accident.
- **Secrets:** passwords should be typed (hidden) or read from files — never written in the script or passed as arguments.
- **Generating files:** setup scripts write nginx configs, systemd services, `.env` files and SQL using heredocs.
- **Processing data:** `while read` reads files line by line (you saw this with loops).

## When and where do you use it?

| Need | Tool |
| --- | --- |
| Ask a question | `read -r -p "…" var` |
| Ask for a password | `read -r -s -p "…" var` |
| Yes/no confirmation | `read -r -p "Continue? [y/N] " ans` + `case` |
| A numbered menu | `select` |
| Write a multi-line file | `cat > file <<EOF` |
| Give one line to a command | `<<< "$text"` |

## Concepts one by one

### 1. `read` — asking a question

<Explain>
<What>
A command that waits for one line of input and stores it in a variable.
</What>
<Why>
So the script can get information from the person running it.
</Why>
<When>
Interactive scripts: installers, setup wizards, confirmations.
</When>
<Where>
Server setup scripts, tools your teammates run by hand.
</Where>
<How>
`read -r -p "Question: " variable`. `-p` shows the prompt; `-r` keeps backslashes as typed (always use it).
</How>
</Explain>

```bash
printf 'Moiz\n' | {
  read -r -p "What is your name? " name
  echo "Nice to meet you, $name!"
}
```

```text output
Nice to meet you, Moiz!
```

- `printf 'Moiz\n' |` — types the answer automatically so this example runs by itself. In a real terminal, **you** type it, and you also see the prompt.
- `read -r -p "What is your name? " name` — show the question, wait for a line, store it in `name`.
- The `{ … }` groups the commands so they all read from the same input.

### 2. Reading several values at once

<Explain>
<What>
`read` can split one line into several variables, at spaces (or at the characters in `IFS`).
</What>
<Why>
To ask for related values in one go, or to split structured lines.
</Why>
<When>
"Enter first and last name", reading `key value` lines, splitting CSV.
</When>
<Where>
Parsing lines inside loops.
</Where>
<How>
`read -r first last`. The **last** variable gets everything that is left. `IFS=, read -r a b c` splits at commas.
</How>
</Explain>

```bash
read -r first last <<< "Moiz Rehman Khan"
echo "first=[$first] last=[$last]"

IFS=, read -r user role city <<< "ali,admin,Lahore"
echo "user=$user role=$role city=$city"
```

```text output
first=[Moiz] last=[Rehman Khan]
user=ali role=admin city=Lahore
```

`<<< "…"` is a here string (section 9) — a quick way to feed one line to `read`.

### 3. Hidden input for passwords: `-s`

<Explain>
<What>
The `-s` (silent) option stops the typed characters from appearing on screen.
</What>
<Why>
So nobody looking at the screen (or a screen recording) sees the password.
</Why>
<When>
Asking for passwords, tokens, passphrases.
</When>
<Where>
Database setup, creating admin users, unlocking keys.
</Where>
<How>
`read -r -s -p "Password: " pass; echo` — the extra `echo` moves to a new line, because Enter is not shown either. Never `echo "$pass"` afterwards.
</How>
</Explain>

```bash
printf 'S3cure!pass\n' | {
  read -r -s -p "Database password: " db_pass
  echo
  echo "Password received (${#db_pass} characters)"
}
```

```text output

Password received (11 characters)
```

Notice the script only prints the **length** — never the password itself.

### 4. Time limits and defaults: `-t`

<Explain>
<What>
`-t SECONDS` makes `read` give up if nothing is typed in time. It then fails, so you can fall back to a default.
</What>
<Why>
A script waiting forever for an answer blocks automation — for example when it runs in CI with nobody there.
</Why>
<When>
Optional questions with sensible defaults.
</When>
<Where>
Installers ("Press Enter within 10 s to change settings").
</Where>
<How>
`read -r -t 10 -p "Port [8080]: " port || true` then `port="${port:-8080}"`.
</How>
</Explain>

```bash
read -r -t 1 -p "Port [8080]: " port < <(sleep 3) || echo "(no answer in 1 second)"
port="${port:-8080}"
echo "Using port $port"
```

```text output
(no answer in 1 second)
Using port 8080
```

`< <(sleep 3)` simulates a person who does not answer: the input stays empty for 3 seconds, so the 1-second limit runs out.

### 5. Yes/no confirmations

<Explain>
<What>
A question whose answer decides whether the script continues.
</What>
<Why>
Dangerous actions (deleting data, deploying to production) should require a clear "yes".
</Why>
<When>
Before anything destructive or expensive.
</When>
<Where>
Cleanup scripts, database migrations, production deploys.
</Where>
<How>
Read the answer, normalise it to lower case, and use `case`. Make **No** the default (`[y/N]` — capital letter = default), so pressing Enter by mistake does nothing.
</How>
</Explain>

```bash
confirm() {
  local answer
  read -r -p "$1 [y/N] " answer
  case "${answer,,}" in
    y|yes) return 0 ;;
    *)     return 1 ;;
  esac
}

for typed in "yes" "" "Y" "nope"; do
  if printf '%s\n' "$typed" | confirm "Delete old backups?"; then
    echo "[$typed] → deleting"
  else
    echo "[$typed] → cancelled"
  fi
done
```

```text output
[yes] → deleting
[] → cancelled
[Y] → deleting
[nope] → cancelled
```

- `${answer,,}` — lower case, so `Y`, `YES` and `yes` all work.
- Empty answer (just Enter) → `*)` → cancelled. Safe default.

For production, a stronger version asks the person to **type the environment name**: `[[ $typed == prod ]]`.

### 6. Menus with `select`

<Explain>
<What>
A built-in that prints a numbered menu, reads a number and gives you the chosen item.
</What>
<Why>
Choosing from a list by number is quicker and less error-prone than typing names.
</Why>
<When>
Interactive tools with a fixed set of choices.
</When>
<Where>
Choosing an environment, a server, a backup to restore.
</Where>
<How>
`select item in a b c; do …; break; done`. `$REPLY` holds the typed number; `item` holds the chosen text (empty if the number was invalid).
</How>
</Explain>

```bash
PS3="Choose an environment: "
printf '2\n' | {
  select env in dev staging prod; do
    echo "You chose #$REPLY: $env"
    break
  done
} 2>&1
```

```text output
1) dev
2) staging
3) prod
Choose an environment: You chose #2: staging
```

- `PS3` — the prompt `select` shows.
- The menu is printed to stderr; `2>&1` only makes it visible in this example's output.
- `break` — leave the menu after one valid choice.

### 7. Here documents: writing multi-line text

<Explain>
<What>
`<<WORD` followed by lines of text and a final line containing only `WORD`. Everything in between is given to the command as input.
</What>
<Why>
Writing many `echo` lines is ugly and error-prone. A heredoc lets you write the text exactly as it should look.
</Why>
<When>
Creating config files, printing long help messages, sending SQL to a database, writing scripts from scripts.
</When>
<Where>
Server setup scripts, Docker entrypoints, CI jobs.
</Where>
<How>
`cat > file <<EOF` … `EOF`. The closing `EOF` must be **alone on its line**, with no spaces before or after. `EOF` is just a convention — any word works.
</How>
</Explain>

```bash
app="shop"
port=3000
cat > app.env <<EOF
APP_NAME=$app
PORT=$port
CREATED=$(date +%Y)
EOF
cat app.env
```

```text output
APP_NAME=shop
PORT=3000
CREATED=2026
```

- `cat > app.env` — `cat` copies its input to `app.env`.
- `<<EOF` — the input is the following lines, up to `EOF`.
- `$app`, `$port` and `$(date +%Y)` were **replaced** with their values.

### 8. Quoted heredoc `<<'EOF'` — keep text exactly

<Explain>
<What>
Putting quotes around the delimiter (`<<'EOF'`) switches off all replacement: `$` and backticks are kept as typed.
</What>
<Why>
When the text itself is a script or a template that contains `$` signs meant for **later** — for example a Bash script, an nginx config (`$host`), or a Makefile.
</Why>
<When>
Writing scripts or configs that contain their own variables.
</When>
<Where>
Generating `entrypoint.sh`, nginx configs, systemd units with `$MAINPID`.
</Where>
<How>
`cat > file <<'EOF'`. Rule of thumb: unquoted when you **want** your variables filled in, quoted when the text must stay literal.
</How>
</Explain>

```bash
cat > nginx-snippet.conf <<'EOF'
location / {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
EOF
cat nginx-snippet.conf
```

```text output
location / {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

With an unquoted `<<EOF`, Bash would have replaced `$host` and `$remote_addr` with empty values — a broken config.

You can also mix: in an unquoted heredoc, escape single dollars that must stay: `\$host`.

### 9. Here strings `<<<`

<Explain>
<What>
`command <<< "text"` gives one string (plus a newline) to a command's input.
</What>
<Why>
A short, clear alternative to `echo "text" | command` — and unlike a pipe, the command runs in the current shell, so `read` keeps its variables.
</Why>
<When>
Feeding a variable's value to `read`, `grep`, `bc`, `jq`.
</When>
<Where>
Splitting strings, quick checks.
</Where>
<How>
`grep -q "admin" <<< "$roles"`, `read -r a b <<< "$line"`.
</How>
</Explain>

```bash
roles="user editor admin"
grep -q "admin" <<< "$roles" && echo "has admin role"
read -r major minor patch <<< "$(tr . ' ' <<< "2.14.3")"
echo "major=$major minor=$minor patch=$patch"
```

```text output
has admin role
major=2 minor=14 patch=3
```

### 10. Indented heredocs `<<-`

<Explain>
<What>
`<<-EOF` removes leading **tab** characters from every line (including the closing `EOF`).
</What>
<Why>
So heredocs inside functions and `if` blocks can be indented to match the code.
</Why>
<When>
Heredocs inside indented code.
</When>
<Where>
Functions that print help or write files.
</Where>
<How>
Indent with **tabs**, not spaces — spaces are not removed. Many editors convert tabs to spaces, so check your editor settings, or simply keep heredoc lines un-indented.
</How>
</Explain>

```bash
show_help() {
	cat <<-EOF
	Usage: tool [options]
	  -h  help
	EOF
}
show_help
```

```text output
Usage: tool [options]
  -h  help
```

### 11. Reading a file and checking input safely

<Explain>
<What>
Validating what was typed before using it.
</What>
<Why>
People make typos, and anything typed is **untrusted input**. A username with `; rm -rf ~` in it must not reach a command.
</Why>
<When>
Every time you use typed input.
</When>
<Where>
Usernames, ports, file names, environment names.
</Where>
<How>
Loop until the answer matches an allow-list pattern, for example a port must be digits only and between 1 and 65535.
</How>
</Explain>

```bash
ask_port() {
  local p
  while true; do
    read -r -p "Port (1-65535): " p || return 1
    if [[ $p =~ ^[0-9]+$ ]] && (( p >= 1 && p <= 65535 )); then
      echo "$p"; return 0
    fi
    echo "Invalid port: '$p' — try again" >&2
  done
}
printf 'abc\n99999\n8080\n' | ask_port 2> errors.txt > port.txt
cat errors.txt
echo "Accepted: $(cat port.txt)"
```

```text output
Invalid port: 'abc' — try again
Invalid port: '99999' — try again
Accepted: 8080
```

The function keeps asking until the input is valid; error messages go to stderr (`>&2`) so only the good value is returned on stdout.

## Hands-on

A tiny interactive setup script, answered automatically by `printf`:

```bash
mkdir -p ~/input-lab && cd ~/input-lab

cat > setup.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
read -r -p "App name: " app
read -r -p "Port [3000]: " port
port="${port:-3000}"
read -r -s -p "Admin password: " pass; echo
read -r -p "Write config for $app? [y/N] " ok
[[ ${ok,,} == y* ]] || { echo "Cancelled"; exit 1; }
cat > "$app.env" <<CONF
APP=$app
PORT=$port
ADMIN_PASSWORD_LENGTH=${#pass}
CONF
echo "Wrote $app.env"
EOF
chmod +x setup.sh

printf 'shop\n\nhunter22\ny\n' | ./setup.sh
cat shop.env
printf 'blog\n8080\nx\nn\n' | ./setup.sh; echo "exit code: $?"

cd ~ && rm -rf ~/input-lab
```

```text output

Wrote shop.env
APP=shop
PORT=3000
ADMIN_PASSWORD_LENGTH=8

Cancelled
exit code: 1
```

(The empty lines come from the `echo` after the hidden password.) The heredoc inside `setup.sh` uses a different delimiter (`CONF`) because the outer heredoc already uses `EOF`.

## Real-world example

A safe production database restore script — the kind of tool where a wrong answer costs data:

```bash
#!/usr/bin/env bash
# restore-db.sh <backup-file>
set -euo pipefail

backup="${1:?usage: $0 <backup.sql.gz>}"
[[ -r $backup ]] || { echo "Cannot read $backup" >&2; exit 1; }

echo "This will REPLACE the production database with:"
echo "  $backup ($(du -h "$backup" | cut -f1))"
read -r -p "Type the word 'production' to continue: " answer
[[ $answer == production ]] || { echo "Aborted."; exit 1; }

read -r -s -p "Database password: " PGPASSWORD; echo
export PGPASSWORD

gunzip -c "$backup" | psql -h db.internal -U admin shop
unset PGPASSWORD

cat <<EOF
Restore finished at $(date '+%F %T').
Remember to:
  1. Restart the app servers
  2. Check the error dashboard
EOF
```

- **Typing a word**, not just `y`, makes it hard to confirm by reflex.
- **The password is hidden**, never in the script, never an argument, and removed from the environment after use.
- **The heredoc** prints a clear, multi-line checklist at the end.

## Common mistakes

- **Forgetting `-r`** — backslashes in input disappear (`C:\new` → `C:new`).
- **Spaces after the closing `EOF`** or indenting it with spaces — Bash never finds the end and reads the rest of the script as text.
- **Unquoted heredoc for configs containing `$`** — nginx, systemd and shell snippets get their variables wiped out. Use `<<'EOF'`.
- **`echo "text" | read var`** — `read` runs in a subshell and the variable is lost. Use `read var <<< "text"`.
- **No default for empty answers**, so pressing Enter crashes the script with `set -u`.
- **Interactive prompts in automation** — a script run by cron or CI hangs forever. Support arguments or environment variables as well, and use `-t`.
- **Printing or logging passwords** after reading them.

## Security lens

<Callout type="security">
Anything a person types is untrusted input, and anything secret must never be visible, stored or passed as an argument.
</Callout>

- **Validate with allow-lists**: anchored patterns like `^[a-z0-9_-]{3,32}$` for names, numeric ranges for ports.
- **Secrets:** `read -s`, a file with mode `600`, or a secrets manager. Not arguments (visible in `ps`), not the script (visible in Git), not `set -x` output (it prints values!).
- **Unquoted heredocs run commands:** `$(…)` inside an unquoted heredoc is executed. Never put untrusted data into a heredoc that generates a script.
- **Temporary files with secrets** should be created with `mktemp` and `umask 077`, and deleted with a trap (see **Traps, Signals and Cleanup**).
- **Confirmation by typing the target** ("type prod") is a cheap control that prevents a whole class of incidents.

## Interview questions

<QA q="What do the -r, -s, -p and -t options of read do?">
-r stops read from treating backslashes as escape characters, so input is kept exactly. -s hides the typed characters, for passwords. -p shows a prompt before reading. -t sets a time limit in seconds; if nothing is entered in time, read fails with a non-zero status, so the script can fall back to a default.
</QA>

<QA q="What is the difference between an unquoted heredoc delimiter (EOF) and a quoted one ('EOF')?">
With an unquoted delimiter, Bash performs variable expansion, command substitution and arithmetic inside the here document, so `$var` is replaced with its value. With a quoted delimiter, the text is passed exactly as written. Quoted heredocs are used when the content contains dollar signs meant for another program, such as nginx variables or a generated shell script.
</QA>

<QA q="Why does echo text | read var not set var?">
Each part of a pipeline runs in a subshell, so read sets var in a child process that ends when the pipeline finishes. Use a here string, `read var <<< "text"`, or process substitution so read runs in the current shell.
</QA>

<QA q="How should a script ask for a password?">
Use read -s so the input is not shown, never echo or log the value, and avoid passing it as a command-line argument because arguments are visible to other users in the process list. Better still, for automation, read it from a protected file or a secrets manager and support an environment variable.
</QA>
