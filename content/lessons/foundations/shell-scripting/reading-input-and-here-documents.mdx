<BigIdea>
<Tr>
<En>
Sometimes a script must **ask** while it runs ("Are you sure? y/n", "Enter the password"), and sometimes it must **write** a block of many lines (a config file). `read -r -p "Your name: " name` asks and stores the answer. A **here document**, `cat > app.conf <<EOF … EOF`, writes many lines at once. With `<<EOF` variables inside are filled in; with `<<'EOF'` the text stays exactly as written.
</En>
<Ur>
Kabhi script ko chalte hue **poochna** parta hai ("Pakka? y/n", "Password likhein"), aur kabhi kai lines ka block **likhna** parta hai (config file). `read -r -p "Your name: " name` poochta hai aur jawab rakhta hai. **Here document**, `cat > app.conf <<EOF … EOF`, ek saath kai lines likhta hai. `<<EOF` me andar ke variables bhar diye jate hain; `<<'EOF'` me text bilkul waisa hi rehta hai jaisa likha.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **`read`**: a built-in that reads **one line** of input (keyboard, file or pipe) into one or more variables.
- **Here document** (`<<WORD … WORD`): multi-line input written right inside the script.
- **Here string** (`<<< "text"`): one string given to a command as input.

</En>
<Ur>

- **`read`**: built-in jo input (keyboard, file ya pipe) ki **ek line** ek ya zyada variables me parhti hai.
- **Here document** (`<<WORD … WORD`): script ke andar hi likha hua kai lines ka input.
- **Here string** (`<<< "text"`): command ko input ke tor par di gayi ek string.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Safety:** confirmations ("type the environment name to continue") stop people destroying production by accident.
- **Secrets:** passwords should be typed (hidden) or read from files, never written in the script or passed as arguments.
- **Generating files:** setup scripts write nginx configs, systemd services, `.env` files and SQL with heredocs.

</En>
<Ur>

- **Hifazat:** tasdeeq ("aage barhne ke liye environment ka naam likhein") logon ko ghalti se production tabah karne se rokti hai.
- **Raaz:** passwords type kiye jayen (chhupe hue) ya files se parhe jayen, kabhi script me likhe ya arguments me na diye jayen.
- **Files banana:** setup scripts heredocs se nginx configs, systemd services, `.env` files aur SQL likhte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Need | Tool |
| --- | --- |
| Ask a question | `read -r -p "…" var` |
| Ask for a password | `read -r -s -p "…" var` |
| Yes/no confirmation | `read` + `case` |
| A numbered menu | `select` |
| Write a multi-line file | `cat > file <<EOF` |
| Give one line to a command | `<<< "$text"` |

</En>
<Ur>

| Zaroorat | Tool |
| --- | --- |
| Sawal poochna | `read -r -p "…" var` |
| Password maangna | `read -r -s -p "…" var` |
| Haan/nahi tasdeeq | `read` + `case` |
| Numbered menu | `select` |
| Kai lines ki file likhna | `cat > file <<EOF` |
| Command ko ek line dena | `<<< "$text"` |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Most useful `read` options: `-r` (keep backslashes; always use it), `-p` (prompt), `-s` (hide typing), `-t 10` (time limit), `-n 1` (read one key).

</En>
<Ur>

`read` ke sab se kaam ke options: `-r` (backslashes rakho; hamesha lagayen), `-p` (sawal), `-s` (typing chhupao), `-t 10` (waqt ki had), `-n 1` (ek key parho).

</Ur>
</Tr>
</How>
</Glance>

</Tr>

## Learn it step by step

<Walkthrough>

<Step title="read: ask a question">

<Tr>
<En>

`read -r -p "Question: " variable` shows the question, waits for a line, and stores it. In these examples `printf` **types the answer automatically** so the code runs by itself; in a real terminal **you** type it and also see the prompt.

</En>
<Ur>

`read -r -p "Question: " variable` sawal dikhata hai, ek line ka intezar karta hai, aur use rakh leta hai. In misaalon me `printf` **jawab khud type karta hai** taa ke code khud chale; asli terminal me **aap** type karte hain aur sawal bhi dekhte hain.

</Ur>
</Tr>

```bash
printf 'Alex\n' | {
  read -r -p "What is your name? " name
  echo "Nice to meet you, $name!"
}
```

```text output
Nice to meet you, Alex!
```

<Happened>
<Tr>
<En>`printf` sent "Alex" into the input. `read` stored it in `name`. The `{ … }` groups the commands so they all read from the same input. (The prompt isn't shown when input isn't a keyboard.)</En>
<Ur>`printf` ne "Alex" input me bheja. `read` ne use `name` me rakha. `{ … }` commands ko ikattha karta hai taa ke sab ek hi input se parhen. (Jab input keyboard na ho to sawal nazar nahi aata.)</Ur>
</Tr>
</Happened>

</Step>

<Step title="Read several values at once">

<Tr>
<En>

`read -r first last` splits a line at spaces. The **last** variable gets everything left over. `IFS=, read -r a b c` splits at commas. `<<< "…"` is a here string, a quick way to feed one line.

</En>
<Ur>

`read -r first last` line ko spaces par torta hai. **Aakhri** variable ko baqi sab milta hai. `IFS=, read -r a b c` commas par torta hai. `<<< "…"` here string hai, ek line dene ka jaldi wala tareeqa.

</Ur>
</Tr>

```bash
read -r first last <<< "Alex James Carter"
echo "first=[$first] last=[$last]"

IFS=, read -r user role city <<< "sam,admin,Chicago"
echo "user=$user role=$role city=$city"
```

```text output
first=[Alex] last=[James Carter]
user=sam role=admin city=Chicago
```

</Step>

<Step title="Hidden passwords: -s">

<Tr>
<En>

`-s` stops typed characters appearing on screen, so nobody watching (or a screen recording) sees the password. Add an `echo` afterwards to move to a new line, because Enter isn't shown either. **Never** print the password afterwards.

</En>
<Ur>

`-s` type kiye huroof screen par aane se rokta hai, taa ke dekhne wala (ya screen recording) password na dekhe. Baad me nayi line ke liye `echo` lagayen, kyun ke Enter bhi nazar nahi aata. Baad me password **kabhi** na chhaapein.

</Ur>
</Tr>

```bash
printf 'S3cure!pass\n' | {
  read -r -s -p "Database password: " db_pass
  echo
  echo "Password received (${#db_pass} characters)"
}
```

```text output

Password received (11 characters)
```

<Happened>
<Tr>
<En>The script printed only the **length** (`${#db_pass}`), never the password itself. The empty first line came from the `echo`.</En>
<Ur>Script ne sirf **lambai** (`${#db_pass}`) chhaapi, password kabhi nahi. Pehli khaali line `echo` se aayi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Time limits and defaults: -t">

<Tr>
<En>

A script waiting forever blocks automation (in CI nobody is there to answer). `-t SECONDS` makes `read` give up and **fail**, so you can fall back to a default with `${port:-8080}`.

</En>
<Ur>

Hamesha intezar karta script automation rok deta hai (CI me jawab dene wala koi nahi). `-t SECONDS` `read` ko haar maanne aur **fail** hone deta hai, taa ke aap `${port:-8080}` se default par aa sakein.

</Ur>
</Tr>

```bash
read -r -t 1 -p "Port [8080]: " port < <(sleep 3) || echo "(no answer in 1 second)"
port="${port:-8080}"
echo "Using port $port"
```

```text output
(no answer in 1 second)
Using port 8080
```

<Happened>
<Tr>
<En>`< <(sleep 3)` pretended to be a person who doesn't answer: input stayed empty for 3 seconds, so the 1-second limit ran out, `read` failed, and the default 8080 was used.</En>
<Ur>`< <(sleep 3)` ne aisa shakhs ban kar dikhaya jo jawab nahi deta: input 3 second khaali raha, isliye 1 second ki had khatam hui, `read` fail hua, aur default 8080 istemal hua.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Yes/no confirmations">

<Tr>
<En>

Dangerous actions should need a clear "yes". Lower-case the answer with `${answer,,}` so `Y`, `YES` and `yes` all work, and make **No the default** (`[y/N]`: the capital letter is the default), so pressing Enter by mistake does nothing.

</En>
<Ur>

Khatarnak kaamon ke liye saaf "haan" chahiye. `${answer,,}` se jawab chhote huroof me karein taa ke `Y`, `YES` aur `yes` sab chalen, aur **No ko default** banayen (`[y/N]`: bara harf default hai), taa ke ghalti se Enter dabane par kuch na ho.

</Ur>
</Tr>

```bash
confirm() {
  local answer
  read -r -p "$1 [y/N] " answer
  case "${answer,,}" in
    y|yes) return 0 ;;
    *)     return 1 ;;
  esac
}

for typed in "yes" "" "Y" "nope"; do
  if printf '%s\n' "$typed" | confirm "Delete old backups?"; then
    echo "[$typed] → deleting"
  else
    echo "[$typed] → cancelled"
  fi
done
```

```text output
[yes] → deleting
[] → cancelled
[Y] → deleting
[nope] → cancelled
```

<Tr>
<En>For production, a stronger version asks the person to **type the environment name**: `[[ $typed == prod ]]`.</En>
<Ur>Production ke liye mazboot tareeqa shakhs se **environment ka naam type** karwata hai: `[[ $typed == prod ]]`.</Ur>
</Tr>

</Step>

<Step title="Menus with select">

<Tr>
<En>

`select` prints a numbered menu, reads a number and gives you the chosen item. `$REPLY` holds the typed number; the variable holds the chosen text (empty if the number was invalid). `PS3` is the menu's prompt, and `break` leaves after one choice.

</En>
<Ur>

`select` numbered menu chhaapta hai, number parhta hai aur chuni hui cheez deta hai. `$REPLY` me type kiya number hota hai; variable me chuna hua text (number ghalat ho to khaali). `PS3` menu ka sawal hai, aur `break` ek choice ke baad bahar le jata hai.

</Ur>
</Tr>

```bash
PS3="Choose an environment: "
printf '2\n' | {
  select env in dev staging prod; do
    echo "You chose #$REPLY: $env"
    break
  done
} 2>&1
```

```text output
1) dev
2) staging
3) prod
Choose an environment: You chose #2: staging
```

<Happened>
<Tr>
<En>The menu goes to stderr; `2>&1` only makes it visible in this example. We "typed" 2, so `env` became `staging`.</En>
<Ur>Menu stderr me jata hai; `2>&1` sirf is misaal me use dikhata hai. Hum ne 2 "type" kiya, isliye `env` `staging` bana.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Here documents: write many lines">

<Tr>
<En>

Many `echo` lines are ugly and easy to get wrong. A heredoc lets you write the text **exactly as it should look**:

- `cat > file <<EOF` starts it; the lines follow; a line with only `EOF` ends it.
- The closing `EOF` must be **alone on its line**: no spaces before or after.
- `EOF` is just a habit; any word works.

</En>
<Ur>

Bohot si `echo` lines bhaddi hoti hain aur ghalti asaan. Heredoc text **bilkul waise likhne** deta hai jaisa hona chahiye:

- `cat > file <<EOF` shuru karta hai; lines aati hain; sirf `EOF` wali line khatam karti hai.
- Band karne wala `EOF` apni line par **akela** ho: pehle ya baad me koi space nahi.
- `EOF` bas aadat hai; koi bhi lafz chalta hai.

</Ur>
</Tr>

```bash
app="shop"
port=3000
cat > app.env <<EOF
APP_NAME=$app
PORT=$port
CREATED=$(date +%Y)
EOF
cat app.env
```

```text output
APP_NAME=shop
PORT=3000
CREATED=2026
```

<Happened>
<Tr>
<En>`cat > app.env` copied its input into the file, and the input was the lines up to `EOF`. `$app`, `$port` and `$(date +%Y)` were **replaced** with their values.</En>
<Ur>`cat > app.env` ne apna input file me copy kiya, aur input `EOF` tak ki lines thin. `$app`, `$port` aur `$(date +%Y)` apni values se **badal** gaye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Quoted heredoc <<'EOF': keep the text exactly">

<Tr>
<En>

Quotes around the delimiter switch off **all** replacement: `$` and backticks stay as typed. Use it when the text contains `$` signs meant for **another program**: an nginx config (`$host`), a generated Bash script, a systemd unit.

Rule of thumb: unquoted when you **want** your variables filled in; quoted when the text must stay literal.

</En>
<Ur>

Delimiter ke gird quotes **har** tabdeeli band kar dete hain: `$` aur backticks waise hi rehte hain. Tab istemal karein jab text me **kisi aur program** ke liye `$` hon: nginx config (`$host`), banaya gaya Bash script, systemd unit.

Aasaan usool: jab aap variables **bharwana chahein** to bina quotes; jab text jaisa ka taisa rehna chahiye to quotes.

</Ur>
</Tr>

```bash
cat > nginx-snippet.conf <<'EOF'
location / {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
EOF
cat nginx-snippet.conf
```

```text output
location / {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

<Happened>
<Tr>
<En>With an unquoted `<<EOF`, Bash would have replaced `$host` and `$remote_addr` with **empty** values: a broken config. You can also mix: in an unquoted heredoc, write `\$host` for a dollar that must stay.</En>
<Ur>Bina quotes `<<EOF` hota to Bash `$host` aur `$remote_addr` ko **khaali** values se badal deta: tooti hui config. Aap mila bhi sakte hain: bina quotes heredoc me rehne wale dollar ke liye `\$host` likhein.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Here strings <<<">

<Tr>
<En>

`command <<< "text"` gives one string to a command's input. It's a short alternative to `echo "text" | command`, and unlike a pipe the command runs in the **current** shell, so `read` keeps its variables.

</En>
<Ur>

`command <<< "text"` command ke input ko ek string deta hai. Ye `echo "text" | command` ka chhota mutabadil hai, aur pipe ke baraks command **mojooda** shell me chalti hai, isliye `read` apne variables rakhta hai.

</Ur>
</Tr>

```bash
roles="user editor admin"
grep -q "admin" <<< "$roles" && echo "has admin role"
read -r major minor patch <<< "$(tr . ' ' <<< "2.14.3")"
echo "major=$major minor=$minor patch=$patch"
```

```text output
has admin role
major=2 minor=14 patch=3
```

</Step>

<Step title="Indented heredocs <<-">

<Tr>
<En>

`<<-EOF` removes leading **tab** characters from every line (including the closing `EOF`), so heredocs inside functions can be indented like the code. It must be **tabs**, not spaces; many editors turn tabs into spaces, so check your settings or keep heredoc lines un-indented.

</En>
<Ur>

`<<-EOF` har line (band karne wale `EOF` samet) ke shuru ke **tab** huroof hata deta hai, taa ke functions ke andar heredocs code ki tarah indent ho sakein. Ye **tabs** hone chahiye, spaces nahi; kai editors tabs ko spaces bana dete hain, isliye settings check karein ya heredoc lines bina indent rakhein.

</Ur>
</Tr>

```bash
show_help() {
	cat <<-EOF
	Usage: tool [options]
	  -h  help
	EOF
}
show_help
```

```text output
Usage: tool [options]
  -h  help
```

</Step>

<Step title="Check typed input before using it">

<Tr>
<En>

People make typos, and anything typed is **untrusted input**: a username containing `; rm -rf ~` must never reach a command. Keep asking until the answer matches an allow-list pattern. Error messages go to stderr (`>&2`) so only the good value comes out on stdout.

</En>
<Ur>

Log typo karte hain, aur type ki gayi har cheez **na-qabil-e-aitbaar input** hai: `; rm -rf ~` wala username kabhi command tak na pohanche. Tab tak poochte rahein jab tak jawab allow-list pattern se na mile. Error messages stderr (`>&2`) me jate hain taa ke stdout par sirf sahi value aaye.

</Ur>
</Tr>

```bash
ask_port() {
  local p
  while true; do
    read -r -p "Port (1-65535): " p || return 1
    if [[ $p =~ ^[0-9]+$ ]] && (( p >= 1 && p <= 65535 )); then
      echo "$p"; return 0
    fi
    echo "Invalid port: '$p' — try again" >&2
  done
}
printf 'abc\n99999\n8080\n' | ask_port 2> errors.txt > port.txt
cat errors.txt
echo "Accepted: $(cat port.txt)"
```

```text output
Invalid port: 'abc' — try again
Invalid port: '99999' — try again
Accepted: 8080
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Unquoted heredoc for an nginx config">

```text
cat > site.conf <<EOF
proxy_set_header Host $host;     # becomes "Host ;"
EOF
```

</Bad>
<Good title="Quoted delimiter">

```text
cat > site.conf <<'EOF'
proxy_set_header Host $host;
EOF
```

</Good>
</Compare>

<Compare>
<Bad title="echo | read">

```text
echo "a b" | read -r x y; echo "$x"    # empty: read ran in a subshell
```

</Bad>
<Good title="Here string">

```text
read -r x y <<< "a b"; echo "$x"       # a
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting `-r`**: backslashes disappear (`C:\new` becomes `C:new`).
- **Spaces after the closing `EOF`**: Bash never finds the end and reads the rest of the script as text.
- **No default for empty answers**, so pressing Enter crashes a `set -u` script.
- **Prompts in automation**: a cron or CI script hangs forever. Also accept arguments or environment variables, and use `-t`.
- **Printing or logging passwords** after reading them.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`-r` bhoolna**: backslashes gayab (`C:\new` `C:new` ban jata hai).
- **Band karne wale `EOF` ke baad spaces**: Bash ko khatma nahi milta aur baqi script text samajh kar parhta hai.
- **Khaali jawab ka default na hona**, isliye Enter dabane se `set -u` wala script crash.
- **Automation me sawal**: cron ya CI script hamesha ruka rehta hai. Arguments ya environment variables bhi qabool karein, aur `-t` lagayen.
- **Passwords parhne ke baad chhaapna ya log karna.**

</Ur>
</Tr>

## Try it yourself

<Challenge title="Input lab: a tiny setup wizard">

<Tr>
<En>
A small interactive setup script, answered automatically by `printf`. The inner heredoc uses a different delimiter (`CONF`) because the outer one already uses `EOF`. The empty lines come from the `echo` after the hidden password.
</En>
<Ur>
Ek chhota interactive setup script, jis ke jawab `printf` khud deta hai. Andar wala heredoc alag delimiter (`CONF`) istemal karta hai kyun ke bahar wala pehle se `EOF` istemal kar raha hai. Khaali lines chhupe password ke baad wale `echo` se hain.
</Ur>
</Tr>

```bash
mkdir -p ~/input-lab && cd ~/input-lab

cat > setup.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
read -r -p "App name: " app
read -r -p "Port [3000]: " port
port="${port:-3000}"
read -r -s -p "Admin password: " pass; echo
read -r -p "Write config for $app? [y/N] " ok
[[ ${ok,,} == y* ]] || { echo "Cancelled"; exit 1; }
cat > "$app.env" <<CONF
APP=$app
PORT=$port
ADMIN_PASSWORD_LENGTH=${#pass}
CONF
echo "Wrote $app.env"
EOF
chmod +x setup.sh

printf 'shop\n\nhunter22\ny\n' | ./setup.sh
cat shop.env
printf 'blog\n8080\nx\nn\n' | ./setup.sh; echo "exit code: $?"

cd ~ && rm -rf ~/input-lab
```

```text output

Wrote shop.env
APP=shop
PORT=3000
ADMIN_PASSWORD_LENGTH=8

Cancelled
exit code: 1
```

<Hint>
<Tr>
<En>The second answer in the first run was an empty line, so the port fell back to 3000.</En>
<Ur>Pehle run me doosra jawab khaali line tha, isliye port 3000 par aa gaya.</Ur>
</Tr>
</Hint>

</Challenge>

<En>

```text
domain="shop.example.com"
```

</Ur>

<DeepDive title="Real world: a safe production database restore">

The kind of tool where a wrong answer costs data:

```bash
#!/usr/bin/env bash
# restore-db.sh <backup-file>
set -euo pipefail

backup="${1:?usage: $0 <backup.sql.gz>}"
[[ -r $backup ]] || { echo "Cannot read $backup" >&2; exit 1; }

echo "This will REPLACE the production database with:"
echo "  $backup ($(du -h "$backup" | cut -f1))"
read -r -p "Type the word 'production' to continue: " answer
[[ $answer == production ]] || { echo "Aborted."; exit 1; }

read -r -s -p "Database password: " PGPASSWORD; echo
export PGPASSWORD

gunzip -c "$backup" | psql -h db.internal -U admin shop
unset PGPASSWORD

cat <<EOF
Restore finished at $(date '+%F %T').
Remember to:
  1. Restart the app servers
  2. Check the error dashboard
EOF
```

- **Typing a word**, not just `y`, makes it hard to confirm by reflex.
- **The password is hidden**, never in the script, never an argument, and removed from the environment after use.
- **The heredoc** prints a clear multi-line checklist at the end.

</DeepDive>

<DeepDive title="Security lens">

Anything a person types is untrusted input, and anything secret must never be visible, stored or passed as an argument.

- **Validate with allow-lists:** anchored patterns like `^[a-z0-9_-]{3,32}$` for names, numeric ranges for ports.
- **Secrets:** `read -s`, a file with mode `600`, or a secrets manager. Not arguments (visible in `ps`), not the script (visible in Git), not `set -x` output (it prints values).
- **Unquoted heredocs run commands:** `$(…)` inside an unquoted heredoc is executed. Never put untrusted data into a heredoc that generates a script.
- **Temporary files with secrets** should be created with `mktemp` and `umask 077`, and deleted with a trap (see **Traps, Signals and Cleanup**).
- **Confirmation by typing the target** ("type prod") is a cheap control that prevents a whole class of incidents.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What do the -r, -s, -p and -t options of read do?">
-r stops read from treating backslashes as escape characters, so input is kept exactly. -s hides the typed characters, for passwords. -p shows a prompt before reading. -t sets a time limit in seconds; if nothing is entered in time, read fails with a non-zero status, so the script can fall back to a default.
</QA>

<QA q="What is the difference between an unquoted heredoc delimiter (EOF) and a quoted one ('EOF')?">
With an unquoted delimiter, Bash performs variable expansion, command substitution and arithmetic inside the here document, so `$var` is replaced with its value. With a quoted delimiter, the text is passed exactly as written. Quoted heredocs are used when the content contains dollar signs meant for another program, such as nginx variables or a generated shell script.
</QA>

<QA q="Why does echo text | read var not set var?">
Each part of a pipeline runs in a subshell, so read sets var in a child process that ends when the pipeline finishes. Use a here string, `read var <<< "text"`, or process substitution so read runs in the current shell.
</QA>

<QA q="How should a script ask for a password?">
Use read -s so the input is not shown, never echo or log the value, and avoid passing it as a command-line argument because arguments are visible to other users in the process list. Better still, for automation, read it from a protected file or a secrets manager and support an environment variable.
</QA>

</DeepDive>
