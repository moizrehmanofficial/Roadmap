<BigIdea>
<Tr>
<En>
A **setup script** prepares a fresh server: packages, users, SSH hardening, firewall, config files. It must be **idempotent**: safe to run again and again, changing only what isn't correct yet. A **deploy script** puts a new version live: build it in a new `releases/<time>` folder, switch a `current` **symlink** to it in one atomic step, check health, and **roll back** to the previous release if the check fails.
</En>
<Ur>
**Setup script** naya server tayyar karta hai: packages, users, SSH ki hifazat, firewall, config files. Ise **idempotent** hona chahiye: baar baar chalana mehfooz, sirf wahi badle jo abhi sahi nahi. **Deploy script** naya version live karta hai: nayi `releases/<time>` folder me banao, ek atomic qadam me `current` **symlink** us par switch karo, health check karo, aur check fail ho to pichhle release par **wapas** jao.
</Ur>
</Tr>

<En>

Two jobs every developer meets:

1. **A new server.** You rent a VPS (DigitalOcean, Hetzner, AWS EC2). It arrives empty: no Node.js, no nginx, root login allowed, no firewall. Doing it by hand takes an hour and is never the same twice.

## Part 1: server setup

<Walkthrough>

<Step title="Idempotency: safe to run again">

<Tr>
<En>

Setup scripts get re-run: after adding a step, after a failure halfway, on an existing server. A non-idempotent script creates duplicate users or config lines, or fails on "already exists". Make every step **check first** and act only if needed.

</En>
<Ur>

Setup scripts dobara chalte hain: naya qadam jorne ke baad, aadhe raaste nakami ke baad, mojooda server par. Ghair-idempotent script duplicate users ya config lines banata hai, ya "already exists" par fail hota hai. Har qadam **pehle check** kare aur sirf zaroorat par kaam kare.

</Ur>
</Tr>

```bash
add_line_once() {   # add a line to a file only if it is not already there
  local line="$1" file="$2"
  grep -qxF -- "$line" "$file" 2> /dev/null || echo "$line" >> "$file"
}

for run in 1 2 3; do
  mkdir -p app/logs
  add_line_once "export NODE_ENV=production" profile.sh
done
echo "folders: $(find app -type d | wc -l), lines in profile.sh: $(wc -l < profile.sh)"
cat profile.sh
```

```text output
folders: 2, lines in profile.sh: 1
export NODE_ENV=production
```

<Happened>
<Tr>
<En>Three runs, same result as one: idempotent. Without the `grep` check, the file would have the line three times.</En>
<Ur>Teen runs, ek jaisa nateeja: idempotent. `grep` check ke baghair file me line teen dafa hoti.</Ur>
</Tr>
</Happened>

<Tr>
<En>

| Not idempotent | Idempotent |
| --- | --- |
| `mkdir app` | `mkdir -p app` |
| `echo "x" >> file` | `grep -qxF "x" file \|\| echo "x" >> file` |
| `useradd deploy` | `id deploy &>/dev/null \|\| useradd deploy` |
| `ln -s target link` | `ln -sfn target link` |
| `cp new.conf /etc/app.conf` | `cmp -s new.conf /etc/app.conf \|\| cp …` |

</En>
<Ur>

| Ghair-idempotent | Idempotent |
| --- | --- |
| `mkdir app` | `mkdir -p app` |

<Step title="Root and OS checks">

<Tr>
<En>

Installing packages and editing `/etc` needs root, and package commands differ between Ubuntu (`apt`) and RHEL/Amazon Linux (`dnf`). Failing clearly at line 1 beats failing confusingly at line 40. `(( EUID == 0 ))` checks root; `/etc/os-release` holds the OS name in `$ID`.

</En>
<Ur>

Packages install karna aur `/etc` badalna root maangta hai, aur package commands Ubuntu (`apt`) aur RHEL/Amazon Linux (`dnf`) me alag hain. Line 1 par saaf fail hona line 40 par uljha hua fail hone se behtar hai. `(( EUID == 0 ))` root check karta hai; `/etc/os-release` `$ID` me OS ka naam rakhta hai.

</Ur>
</Tr>

```bash
. /etc/os-release
echo "OS id: ${ID:-unknown}" | sed 's/: .*/: <your OS id, e.g. ubuntu>/'
case "${ID:-}" in
  ubuntu|debian) pkg="apt-get install -y" ;;
  rhel|centos|rocky|almalinux|amzn|fedora) pkg="dnf install -y" ;;
  *) pkg="" ;;
esac
echo "package command chosen: ${pkg:+yes}"
(( EUID == 0 )) && echo "running as root" || echo "not root: would stop with 'run with sudo'"
```

```text output
OS id: <your OS id, e.g. ubuntu>
package command chosen: yes
running as root
```

<Step title="Config files from templates">

<Tr>
<En>

Every server needs the same nginx or systemd config with a few different values (domain, port, user). Use an **unquoted** heredoc for your variables and escape the dollars that belong to the target program (`\$host`). On a server, also **test** the config before reloading (`nginx -t`).

</En>
<Ur>

Har server ko wahi nginx ya systemd config chahiye, chand mukhtalif values ke saath (domain, port, user). Apne variables ke liye **bina quotes** heredoc istemal karein aur target program ke dollars escape karein (`\$host`). Server par reload se pehle config ko **test** bhi karein (`nginx -t`).

</Ur>
</Tr>

```bash
domain="shop.example.com"
port=3000
cat > shop.nginx.conf <<EOF
server {
    listen 80;
    server_name ${domain};

    location / {
        proxy_pass http://127.0.0.1:${port};
        proxy_set_header Host \$host;
        proxy_set_header X-Real-IP \$remote_addr;
    }
}
EOF
cat shop.nginx.conf
```

<Step title="Harden SSH safely">

<Tr>
<En>

Every public server is attacked by password-guessing bots within minutes. Allow key-only login and no root login, in a small drop-in file. Then **test** with `sshd -t` and reload only if it passes. Keep your current session open until a **new** login works; one mistake otherwise locks you out.

</En>
<Ur>

Har public server par minto me password andaza lagane wale bots hamla karte hain. Sirf key se login aur root login band, ek chhoti drop-in file me. Phir `sshd -t` se **test** karein aur paas ho tab hi reload. Apna mojooda session tab tak khula rakhein jab tak **naya** login na chal jaye; warna ek ghalti aap ko bahar band kar deti hai.

</Ur>
</Tr>

```bash
cat > 50-hardening.conf <<'EOF'
# Managed by setup-server.sh — do not edit by hand
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
MaxAuthTries 3
EOF
grep -v '^#' 50-hardening.conf
```

```text output
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
MaxAuthTries 3
```

<Tr>
<En>On the server, the script would then run:</En>

</Tr>

```bash
install -m 644 50-hardening.conf /etc/ssh/sshd_config.d/50-hardening.conf
sshd -t && systemctl reload ssh
```

<Step title="The complete setup script">

<Tr>
<En>

One idempotent script that turns a fresh Ubuntu server into a host for a Node.js app behind nginx. Run it with `sudo bash setup-server.sh deploy "ssh-ed25519 AAAA…"`, or paste it as cloud **user data**. Every step uses something from an earlier lesson.

</En>
<Ur>

Ek idempotent script jo naye Ubuntu server ko nginx ke peeche Node.js app ka host bana deta hai. Ise `sudo bash setup-server.sh deploy "ssh-ed25519 AAAA…"` se chalayen, ya cloud **user data** ke tor par chipkayen. Har qadam kisi pichhle sabaq ki cheez istemal karta hai.

</Ur>
</Tr>

```bash
#!/usr/bin/env bash
# setup-server.sh <deploy-user> <ssh-public-key>
set -euo pipefail

log() { printf '\e[32m[setup]\e[0m %s\n' "$*"; }
die() { printf '\e[31m[setup]\e[0m %s\n' "$*" >&2; exit 1; }

(( EUID == 0 )) || die "run as root: sudo $0 …"
user="${1:?usage: $0 <deploy-user> <ssh-public-key>}"
pubkey="${2:?usage: $0 <deploy-user> <ssh-public-key>}"
[[ $user =~ ^[a-z_][a-z0-9_-]{1,31}$ ]] || die "invalid user name: $user"
[[ $pubkey == ssh-* ]] || die "that does not look like an SSH public key"

install_packages() {
  log "installing packages"
  export DEBIAN_FRONTEND=noninteractive
  apt-get update -qq
  apt-get install -y -qq nginx ufw fail2ban git curl unattended-upgrades > /dev/null
}

create_user() {
  if id "$user" &> /dev/null; then
    log "user $user already exists"
  else
    useradd --create-home --shell /bin/bash "$user"
    log "created user $user"
  fi
  install -d -m 700 -o "$user" -g "$user" "/home/$user/.ssh"
  local keys="/home/$user/.ssh/authorized_keys"
  touch "$keys"
  grep -qxF "$pubkey" "$keys" || echo "$pubkey" >> "$keys"
  chown "$user:$user" "$keys"; chmod 600 "$keys"
}

harden_ssh() {
  cat > /etc/ssh/sshd_config.d/50-hardening.conf <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
MaxAuthTries 3
EOF
  sshd -t && systemctl reload ssh
  log "SSH hardened (root login and passwords disabled)"
}

setup_firewall() {
  ufw default deny incoming > /dev/null
  ufw default allow outgoing > /dev/null
  ufw allow OpenSSH > /dev/null
  ufw allow 'Nginx Full' > /dev/null
  ufw --force enable > /dev/null
  log "firewall: only SSH, HTTP and HTTPS allowed in"
}

prepare_app_dirs() {
  install -d -o "$user" -g "$user" /var/www/shop/{releases,shared}
  log "app folders ready in /var/www/shop"
}

main() {
  install_packages
  create_user
  harden_ssh
  setup_firewall
  prepare_app_dirs
  systemctl enable --now fail2ban unattended-upgrades > /dev/null
  log "done — test a NEW ssh login as $user before closing this session"
}
main "$@"
```

<Tr>
<En>

What each step protects:

- **Input validation** stops a typo or malicious value becoming a system user.
- **`install -d -m 700`** makes folders with the right owner and permissions in one idempotent command.
- **`ufw`** blocks every port except SSH and web.
- **fail2ban** bans IPs that keep failing SSH logins; **unattended-upgrades** installs security patches automatically.

</En>
<Ur>

Har qadam kis cheez se bachata hai:

- **Input validation** typo ya bad-niyat value ko system user banne se rokti hai.
- **`install -d -m 700`** ek idempotent command me sahi malik aur permissions ke saath folders banata hai.
- **`ufw`** SSH aur web ke ilawa har port band karta hai.
- **fail2ban** baar baar SSH login me fail hone wale IPs ko ban karta hai; **unattended-upgrades** security patches khud install karta hai.

</Ur>
</Tr>

</Step>

## Part 2: zero-downtime deploys

<Walkthrough>

<Step title="Release folders and the current symlink">

<Tr>
<En>

Each deploy goes into a **new** folder under `releases/`, and a symlink called `current` points to the live one. The web server always serves `current`. The live version is never changed while users use it, and old versions stay ready for rollback. Files that must survive deploys (uploads, `.env`) live in `shared/` and are linked into each release. Capistrano and Deployer use exactly this layout.

</En>
<Ur>

Har deploy `releases/` ke neeche **naye** folder me jata hai, aur `current` naam ka symlink live wale ki taraf ishara karta hai. Web server hamesha `current` dikhata hai. Users ke istemal ke dauran live version kabhi nahi badalta, aur purane versions rollback ke liye tayyar rehte hain. Jo files deploys ke baad bhi rehni chahiye (uploads, `.env`) wo `shared/` me rehti hain aur har release me link hoti hain. Capistrano aur Deployer bilkul yahi tarteeb istemal karte hain.

</Ur>
</Tr>

```text
/var/www/shop/
├── current -> releases/20261111-091500      ← nginx / systemd use this path
├── releases/
│   ├── 20261110-143000/                    ← previous (rollback target)
│   └── 20261111-091500/                    ← live
└── shared/
    ├── .env                                ← linked into every release
    └── uploads/
```

</Step>

<Step title="The atomic switch">

<Tr>
<En>

Deleting `current` and then making a new one leaves a moment where `current` doesn't exist, and requests fail. Instead, create the new link under a **temporary name** and rename it over the old one: a rename within one filesystem is atomic, all-or-nothing.

</En>
<Ur>

`current` mita kar phir naya banana aisa lamha chhorta hai jab `current` mojood hi nahi, aur requests fail hoti hain. Is ke bajaye naya link **temporary naam** se banayen aur purane par rename karein: ek filesystem ke andar rename atomic hai, ya poora ya kuch nahi.

</Ur>
</Tr>

```bash
mkdir -p www/releases/v1 www/releases/v2
echo "version 1" > www/releases/v1/index.html
echo "version 2" > www/releases/v2/index.html

switch_to() {
  ln -sfn "releases/$1" www/current.tmp
  mv -T www/current.tmp www/current
}

switch_to v1
echo "live: $(cat www/current/index.html)  (current -> $(readlink www/current))"
switch_to v2
echo "live: $(cat www/current/index.html)  (current -> $(readlink www/current))"
```

```text output
live: version 1  (current -> releases/v1)
live: version 2  (current -> releases/v2)
```

<Happened>
<Tr>
<En>After the switch, reload the app (`systemctl reload shop` or `pm2 reload shop`) so it uses the new files.</En>
<Ur>Switch ke baad app reload karein (`systemctl reload shop` ya `pm2 reload shop`) taa ke wo nayi files istemal kare.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Health check and automatic rollback">

<Tr>
<En>

Some bugs only show up in production (a missing environment variable, a bad migration). Remember the previous target with `readlink`, switch, test, and if the test fails, switch **back** and exit non-zero. The damage lasts seconds.

</En>
<Ur>

Kuch bugs sirf production me nazar aate hain (ghayab environment variable, buri migration). `readlink` se pichhla target yaad rakhein, switch karein, test karein, aur test fail ho to **wapas** switch kar ke non-zero par niklein. Nuqsan seconds tak rehta hai.

</Ur>
</Tr>

```bash
switch_to() { ln -sfn "releases/$1" www/current.tmp && mv -T www/current.tmp www/current; }   # from section 7
healthy() { grep -q "version" www/current/index.html && ! grep -q "BROKEN" www/current/index.html; }

deploy() {
  local new="$1" previous
  previous=$(basename "$(readlink www/current)")
  switch_to "$new"
  if healthy; then
    echo "deployed $new"
  else
    switch_to "$previous"
    echo "health check FAILED for $new — rolled back to $previous"
    return 1
  fi
}

mkdir -p www/releases/v3 && echo "BROKEN build" > www/releases/v3/index.html
deploy v3 || true
echo "live now: $(cat www/current/index.html)"
```

```text output
health check FAILED for v3 — rolled back to v2
live now: version 2
```

</Step>

<Step title="Keep only the last N releases">

<Tr>
<En>

Each release can hold hundreds of MB (`node_modules`), so the disk fills up without cleanup. Release names sort by time: list them newest first, skip the newest N, and delete the rest (never the one `current` points to). `tail -n +4` prints from the 4th line on, so everything after the 3 newest.

</En>
<Ur>

Har release sainkron MB (`node_modules`) rakh sakta hai, isliye safai ke baghair disk bhar jati hai. Release ke naam waqt se tarteeb me aate hain: naye pehle list karein, sab se naye N chhorein, aur baqi mitayen (kabhi wo nahi jis par `current` ishara karta ho). `tail -n +4` chauthi line se chhaapta hai, yaani 3 sab se naye ke baad sab.

</Ur>
</Tr>

```bash
mkdir -p rel && for r in 20261101 20261103 20261105 20261107 20261109; do mkdir -p "rel/$r"; done
keep=3
ls -1 rel | sort -r | tail -n +$((keep + 1)) | while read -r old; do
  echo "removing old release $old"
  rm -rf -- "rel/${old:?}"
done
echo "kept: $(ls rel | tr '\n' ' ')"
```

```text output
removing old release 20261103
removing old release 20261101
kept: 20261105 20261107 20261109 
```

</Step>

<Step title="Run commands on a server over SSH">

<Tr>
<En>

Deploys usually start on your laptop or in CI, but the work happens on the server. Use SSH keys (not passwords), strict mode in the remote script, and **single quotes** around remote commands so your local shell doesn't expand variables meant for the server. `rsync` sends only changed files.

</En>
<Ur>

Deploys aam tor par laptop ya CI se shuru hote hain, lekin kaam server par hota hai. SSH keys istemal karein (passwords nahi), remote script me strict mode, aur remote commands ke gird **single quotes** taa ke aap ka local shell server ke liye bane variables na phailaye. `rsync` sirf badli hui files bhejta hai.

</Ur>
</Tr>

```bash
# Run one command
ssh deploy@shop.example.com 'df -h / && uptime'

# Run a local script on the server, passing arguments
ssh deploy@shop.example.com 'bash -s' -- v2.4.0 < deploy.sh

# Copy the built app to a new release folder (only changed files are sent)
release=$(date +%Y%m%d-%H%M%S)
rsync -az --delete --exclude node_modules ./dist/ "deploy@shop.example.com:/var/www/shop/releases/$release/"
```

<Step title="Dry runs">

<Tr>
<En>

Before touching a production server, see what the script **would** do. Wrap every changing command in a `run` function that only prints when `DRY_RUN=1`.

</En>
<Ur>

Production server chhoone se pehle dekhein ke script **kya karega**. Har badalne wali command ko `run` function me lapetein jo `DRY_RUN=1` hone par sirf chhaape.

</Ur>
</Tr>

```bash
run() {
  if [[ ${DRY_RUN:-0} == 1 ]]; then
    printf '[dry-run] %s\n' "$*"
  else
    "$@"
  fi
}
DRY_RUN=1
run mkdir -p /var/www/shop/releases/new
run systemctl reload nginx
DRY_RUN=0
run echo "really running now"
```

```text output
[dry-run] systemctl reload nginx
really running now
```

## Common mistakes

<Compare>
<Bad title="Remove then create the link">

```text
rm current && ln -s releases/v2 current    # a moment with no current at all
```

</Bad>
<Good title="Atomic rename">

```text
ln -sfn releases/v2 current.tmp && mv -T current.tmp current
```

</Good>
</Compare>

<Compare>
<Bad title="Restart SSH without testing">

```text
echo "PasswordAuthentication no" >> /etc/ssh/sshd_config
systemctl restart ssh          # one typo and you're locked out
```

</Bad>
<Good title="Test first, then reload">

```text
install -m 644 50-hardening.conf /etc/ssh/sshd_config.d/
sshd -t && systemctl reload ssh
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Non-idempotent setup steps**: duplicate lines and "already exists" failures on the second run.
- **Copying files over the live version**: users hit half-updated code.
- **No health check after deploy**: a broken release stays live until a user complains.
- **Secrets in the script or repository**: put them in `shared/.env` with mode 600, or in a secrets manager / CI secrets.
- **Running everything as root**: deploy as a normal `deploy` user.
- **Never deleting old releases**: the disk fills up.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ghair-idempotent setup qadam**: doosre run par duplicate lines aur "already exists" nakamiyan.
- **Live version par files copy karna**: users aadhe badle code se takrate hain.
- **Deploy ke baad health check na hona**: toota release tab tak live rehta hai jab tak koi user shikayat na kare.
- **Script ya repository me raaz**: inhe mode 600 ke saath `shared/.env` me, ya secrets manager / CI secrets me rakhein.
- **Sab kuch root se chalana**: aam `deploy` user ke tor par deploy karein.
- **Purane releases kabhi na mitana**: disk bhar jati hai.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Deploy lab: releases, switch, rollback, cleanup">

<Tr>
<En>
A complete local deploy simulation: release folders, a shared `.env` linked in, an atomic switch, a health check that rolls back a broken `v3`, and cleanup that keeps 2 releases.
</En>
<Ur>
Mukammal local deploy ki naqal: release folders, andar link hui shared `.env`, atomic switch, toote `v3` ko wapas karne wala health check, aur 2 releases rakhne wali safai.
</Ur>
</Tr>

```bash
mkdir -p ~/deploy-lab && cd ~/deploy-lab
mkdir -p app/releases app/shared && echo "API_KEY=local" > app/shared/.env

cat > deploy.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
root="app"; keep=2
version="${1:?usage: deploy.sh <version> [broken]}"
release="$root/releases/$version"

mkdir -p "$release"
echo "shop $version" > "$release/index.html"
[[ ${2:-} == broken ]] && echo "BROKEN" >> "$release/index.html"
ln -sfn ../../shared/.env "$release/.env"

previous=$(readlink "$root/current" 2> /dev/null || true)
ln -sfn "releases/$version" "$root/current.tmp" && mv -T "$root/current.tmp" "$root/current"

if grep -q BROKEN "$root/current/index.html"; then
  [[ -n $previous ]] && ln -sfn "$previous" "$root/current.tmp" && mv -T "$root/current.tmp" "$root/current"
  echo "✖ $version failed health check — rolled back to ${previous#releases/}"
  exit 1
fi
ls -1 "$root/releases" | sort -r | tail -n +$((keep + 1)) | while read -r old; do rm -rf -- "$root/releases/${old:?}"; done
echo "✓ live: $(head -1 "$root/current/index.html")  (.env → $(readlink "$root/current/.env"))"
EOF
chmod +x deploy.sh

./deploy.sh v1
./deploy.sh v2
./deploy.sh v3 broken || true
./deploy.sh v4
echo "releases kept: $(ls app/releases | tr '\n' ' ')"

cd ~ && rm -rf ~/deploy-lab
```

```text output
✓ live: shop v2  (.env → ../../shared/.env)
✖ v3 failed health check — rolled back to v2
✓ live: shop v4  (.env → ../../shared/.env)
releases kept: v3 v4 
```

<Challenge title="A rollback command">

<Tr>
<En>
Write a `rollback` function that switches `current` to the release just before the live one.
</En>
<Ur>
Aisa `rollback` function likhein jo `current` ko live se bilkul pehle wale release par switch kare.
</Ur>
</Tr>

<Solution>
<Tr>
<En>

```text
rollback() {
  local live prev
  live=$(basename "$(readlink app/current)")
  prev=$(ls -1 app/releases | sort | grep -B1 -x -- "$live" | head -1)
  [[ -n $prev && $prev != "$live" ]] || { echo "no older release" >&2; return 1; }
  ln -sfn "releases/$prev" app/current.tmp && mv -T app/current.tmp app/current
  echo "rolled back to $prev"
}
```

`grep -B1 -x` prints the line before the exact match, which is the previous release name.

<DeepDive title="Real world: deploying from GitHub Actions">

A workflow that runs tests, then deploys over SSH using the release-folder idea: the bridge from Bash to CI/CD.

```yaml
# .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci && npm test && npm run build
      - name: Upload and switch release
        env:
          SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          set -euo pipefail
          install -m 600 /dev/null key && printf '%s\n' "$SSH_KEY" > key
          release=$(date +%Y%m%d-%H%M%S)
          rsync -az -e "ssh -i key -o StrictHostKeyChecking=accept-new" dist/ \
            "deploy@shop.example.com:/var/www/shop/releases/$release/"
          ssh -i key deploy@shop.example.com "bash /var/www/shop/bin/activate.sh $release"
```

`activate.sh` on the server does the symlink switch, reload, health check, rollback and cleanup: exactly the steps from this lesson. Later, the same flow is usually replaced by **building a Docker image** and letting Docker Compose, ECS or Kubernetes do the switch and rollback.

</DeepDive>

<DeepDive title="Security lens">

Setup scripts define your server's security baseline, and deploy pipelines hold the keys to production. Treat both as security-critical code.

- **Baseline hardening:** key-only SSH, no root login, firewall default-deny, fail2ban, automatic security updates, on **every** server, by script.
- **Least privilege:** a dedicated `deploy` user that owns only `/var/www/shop`; if it must reload a service, allow exactly that with a narrow `sudoers` rule.
- **Protect deploy keys:** store them as CI secrets, restrict them to the deploy user, and rotate them. Pin the server's host key instead of blindly accepting it.
- **Never pipe the internet into a root shell:** `curl https://… | sudo bash` runs code you haven't read. Download, verify the checksum, review, then run.
- **Audit trail:** log who deployed what and when (`echo "$(date) $USER $version" >> deploys.log`), and keep scripts in Git so every change is reviewed.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does idempotent mean, and why is it important for setup scripts?">
An idempotent operation produces the same result whether it runs once or many times. Setup scripts are re-run after failures, changes or on existing servers, so every step must check the current state and change only what is missing, for example mkdir -p, creating a user only if id fails, and appending a config line only if grep does not find it. Tools like Ansible are built around this idea.
</QA>

<QA q="How can you deploy a new version with zero downtime and fast rollback without containers?">
Put each release in its own timestamped folder, prepare it fully (dependencies, build, shared files linked in), then atomically switch a current symlink to it by creating a temporary link and renaming it over the old one. Reload the app, run a health check, and if it fails point current back to the previous release. Keep the last few releases and delete older ones.
</QA>

<QA q="Why test sshd configuration before reloading, and what else prevents lockouts?">
A syntax error or wrong setting in sshd_config can stop SSH from accepting connections, cutting off remote access. Running sshd -t validates the configuration first, and the reload should happen only if the test passes. Keep the current session open and verify a new login works before disconnecting, and make sure your key-based login works before disabling passwords.
</QA>

<QA q="When would you replace Bash deploy scripts with other tools?">
When the number of servers or services grows, or you need inventory, drift detection and reviewable configuration, configuration management such as Ansible replaces setup scripts, infrastructure as code such as Terraform creates the servers, and container images with an orchestrator (Docker Compose, ECS, Kubernetes) plus a CI/CD pipeline replace symlink deploys. Bash remains the glue inside those pipelines.
</QA>

</DeepDive>
