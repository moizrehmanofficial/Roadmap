<BigIdea>
<Tr>
<En>
Every command ends with an **exit code**: `0` means success, `1` to `255` mean some kind of failure. `$?` holds the last one. React to it with `if command; then`, `command && next`, or `command || handle_error`. When something is wrong, print an error to stderr and stop with `exit 1`. A script must **always** end non-zero when it failed; otherwise CI, cron and other scripts think it worked.
</En>
<Ur>
Har command ek **exit code** par khatam hoti hai: `0` ka matlab kamyabi, `1` se `255` ka matlab kisi qism ki nakami. `$?` me aakhri code hota hai. Is par `if command; then`, `command && next`, ya `command || handle_error` se react karein. Kuch ghalat ho to stderr me error chhaapein aur `exit 1` se rukein. Nakam script ko **hamesha** non-zero par khatam hona chahiye; warna CI, cron aur doosre scripts samajhte hain ke ye chal gaya.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Exit codes** are how programs tell each other whether they succeeded. The number isn't shown on screen, but every program that runs commands looks at it.
- **Error handling** is the part of your script that **checks** these codes and decides: continue, retry, clean up, or stop with a clear message and a non-zero code.

</En>
<Ur>

- **Exit codes** wo tareeqa hain jis se programs ek doosre ko batate hain ke kamyab hue ya nahi. Number screen par nazar nahi aata, lekin commands chalane wala har program use dekhta hai.
- **Error handling** script ka wo hissa hai jo in codes ko **check** karta hai aur tay karta hai: aage barho, dobara koshish, safai, ya saaf message aur non-zero code ke saath ruko.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Bash ignores errors by default.** If step 2 fails, step 3 still runs, maybe deleting or deploying the wrong thing.
- **Automation depends on it.** GitHub Actions, GitLab CI, Jenkins, cron, systemd, Docker and Kubernetes all decide "success" or "failure" from your exit code. A broken deploy that exits 0 shows a **green tick**.
- **Debugging:** "config file /etc/app.env not found" saves hours compared to a mystery failure 30 lines later.

</En>
<Ur>

- **Bash pehle se errors nazar andaz karta hai.** Step 2 fail ho to bhi step 3 chalta hai, shayad ghalat cheez mitata ya deploy karta hai.
- **Automation is par chalti hai.** GitHub Actions, GitLab CI, Jenkins, cron, systemd, Docker aur Kubernetes sab aap ke exit code se "kamyabi" ya "nakami" tay karte hain. 0 par khatam hone wala toota deploy **hara nishan** dikhata hai.
- **Debugging:** "config file /etc/app.env not found" 30 lines baad ki pur-asrar nakami ke muqable ghante bachata hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- After any command whose failure matters: `cd`, `cp`, `curl`, `docker`, `git`, database commands.
- At the top of scripts: checking arguments, files and tools.
- Around flaky network calls: retries.
- At the end: making sure the script's own exit code is right.

</En>
<Ur>

- Har us command ke baad jis ki nakami ahem ho: `cd`, `cp`, `curl`, `docker`, `git`, database commands.
- Script ke shuru me: arguments, files aur tools check karna.
- Kabhi kabhi fail hone wali network calls ke gird: retries.
- Aakhir me: yaqeeni banana ke script ka apna exit code sahi ho.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
command; echo $?            # see the code
if command; then …; fi      # react
cd /app || exit 1           # stop on failure
die() { echo "ERROR: $*" >&2; exit 1; }
```

</En>
<Ur>

```text
command; echo $?            # code dekho
if command; then …; fi      # react karo
cd /app || exit 1           # nakami par ruko
die() { echo "ERROR: $*" >&2; exit 1; }
```

</Ur>
</Tr>
</How>
</Glance>

## Learn it step by step

<Walkthrough>

<Step title="Read an exit code with $?">

<Tr>
<En>

`$?` holds the code of the **most recent** command. Read it right away, because the next command overwrites it.

</En>
<Ur>

`$?` **sab se taaza** command ka code rakhta hai. Ise foran parhein, kyun ke agli command ise badal deti hai.

</Ur>
</Tr>

```bash
ls /etc > /dev/null;      echo "ls /etc → $?"
ls /missing 2> /dev/null; echo "ls /missing → $?"
grep -q root /etc/passwd; echo "grep found → $?"
grep -q zzzz /etc/passwd; echo "grep not found → $?"
nosuchcommand 2> /dev/null; echo "unknown command → $?"
```

```text output
ls /etc → 0
ls /missing → 2
grep found → 0
grep not found → 1
unknown command → 127
```

<Callout type="warning" title="$? changes after every command">
<Tr>
<En>In `ls /missing; echo "failed"; echo $?`, the `$?` belongs to the **echo** (0), not to `ls`. Save it straight away: `ls /missing; code=$?`.</En>
<Ur>`ls /missing; echo "failed"; echo $?` me `$?` **echo** ka hai (0), `ls` ka nahi. Ise foran mehfooz karein: `ls /missing; code=$?`.</Ur>
</Tr>
</Callout>

</Step>

<Step title="What the common codes mean">

<Tr>
<En>

| Code | Meaning | Typical cause |
| --- | --- | --- |
| `0` | Success | Everything worked |
| `1` | General error | Most programs' "something failed" |
| `2` | Misuse / serious trouble | Wrong options, missing file (`ls`, `grep`) |
| `126` | Found but can't be run | Missing `chmod +x` |
| `127` | Command not found | Typo, not installed, not in PATH |
| `128 + N` | Killed by signal N | `130` = Ctrl+C, `137` = killed (9), `143` = terminated (15) |
| `255` | Out of range / SSH errors | `exit -1`, SSH connection failure |

Remember **137**: in Docker and Kubernetes it very often means the container was **killed for using too much memory** (OOMKilled). A program's man page lists its own codes (`man grep` → "EXIT STATUS").

</En>
<Ur>

| Code | Matlab | Aam wajah |
| --- | --- | --- |
| `0` | Kamyabi | Sab chal gaya |
| `1` | Aam error | Zyada tar programs ka "kuch fail hua" |
| `2` | Ghalat istemal / sangeen masla | Ghalat options, ghayab file (`ls`, `grep`) |
| `126` | Mili lekin chal nahi sakti | `chmod +x` ghayab |
| `127` | Command nahi mili | Typo, install nahi, PATH me nahi |
| `128 + N` | Signal N se maari gayi | `130` = Ctrl+C, `137` = maari gayi (9), `143` = band ki gayi (15) |
| `255` | Had se bahar / SSH errors | `exit -1`, SSH connection nakam |

**137** yaad rakhein: Docker aur Kubernetes me aksar iska matlab hai container **zyada memory lene par maara gaya** (OOMKilled). Program ka man page apne codes batata hai (`man grep` → "EXIT STATUS").

</Ur>
</Tr>

</Step>

<Step title="Check success with if">

<Tr>
<En>

Use the command **itself** as the condition: `if command; then … else … fi`. No `$?` needed. `if ! command` means "if it failed".

</En>
<Ur>

Command ko **khud** shart banayen: `if command; then … else … fi`. `$?` ki zaroorat nahi. `if ! command` ka matlab "agar fail hui".

</Ur>
</Tr>

```bash
if mkdir demo-folder; then
  echo "Created demo-folder"
fi

if ! mkdir demo-folder 2> /dev/null; then
  echo "Could not create demo-folder (it already exists)"
fi
```

```text output
Created demo-folder
Could not create demo-folder (it already exists)
```

</Step>

<Step title="Short forms: && and ||">

<Tr>
<En>

- `A && B`: run B only if A **succeeded**. `make && make install` installs only if the build worked.
- `A || B`: run B only if A **failed**. `cd /app || exit 1` means "go to /app, or stop".
- Group several reactions with `{ …; }`.

`true` always succeeds and `false` always fails, which is handy for demos.

</En>
<Ur>

- `A && B`: B tab chalao jab A **kamyab** ho. `make && make install` tab install karta hai jab build chal jaye.
- `A || B`: B tab chalao jab A **fail** ho. `cd /app || exit 1` matlab "/app par jao, warna ruko".
- Kai reactions ko `{ …; }` se ikattha karein.

`true` hamesha kamyab aur `false` hamesha nakam hoti hai, jo misaalon ke liye kaam ki hai.

</Ur>
</Tr>

```bash
cd /no/such/dir 2> /dev/null || echo "cd failed — stopping here would be wise"
true && echo "first succeeded, so this runs"
false || { echo "first failed, so this block runs"; echo "(two commands grouped)"; }
```

```text output
cd failed — stopping here would be wise
first succeeded, so this runs
first failed, so this block runs
(two commands grouped)
```

</Step>

<Step title="exit: stop the script with a code">

<Tr>
<En>

`exit N` ends the **whole script** immediately and hands code N to whoever started it. `exit 0` = success, `exit 1` = general failure, `exit 2` = wrong usage. Without `exit`, a script's code is the code of its **last** command.

</En>
<Ur>

`exit N` **poora script** foran khatam karta hai aur code N chalane wale ko deta hai. `exit 0` = kamyabi, `exit 1` = aam nakami, `exit 2` = ghalat istemal. `exit` ke baghair script ka code us ki **aakhri** command ka code hota hai.

</Ur>
</Tr>

```bash
cat > check-config.sh <<'EOF'
#!/usr/bin/env bash
config="${1:-app.env}"
if [[ ! -f $config ]]; then
  echo "Error: $config not found" >&2
  exit 1
fi
echo "Config $config looks fine"
EOF
chmod +x check-config.sh

./check-config.sh missing.env; echo "exit code: $?"
touch app.env
./check-config.sh; echo "exit code: $?"
```

```text output
Error: missing.env not found
exit code: 1
Config app.env looks fine
exit code: 0
```

</Step>

<Step title="return inside functions">

<Tr>
<En>

`return N` ends only the **function**, so it can report yes/no to its caller like any command. `exit` inside a function would stop the **entire** script, so use `return` unless that's really what you want.

</En>
<Ur>

`return N` sirf **function** khatam karta hai, taa ke ye kisi bhi command ki tarah bulane wale ko haan/nahi bata sake. Function ke andar `exit` **poora** script rok dega, isliye `return` istemal karein jab tak wahi na chahiye.

</Ur>
</Tr>

```bash
is_port_number() {
  [[ $1 =~ ^[0-9]+$ ]] || return 1
  (( $1 >= 1 && $1 <= 65535 )) || return 1
  return 0
}
for v in 80 abc 70000; do
  if is_port_number "$v"; then echo "$v → valid"; else echo "$v → invalid (code $?)"; fi
done
```

```text output
80 → valid
abc → invalid (code 1)
70000 → invalid (code 1)
```

</Step>

<Step title="Clear error messages: die() and stderr">

<Tr>
<En>

A small `die()` helper prints an error to **stderr** and exits non-zero. Errors become consistent and written in one place, and stderr keeps them apart from normal output. A good message says **what** failed, **which** thing (path, host), and ideally **what to do**.

</En>
<Ur>

Chhota `die()` helper error **stderr** me chhaapta hai aur non-zero par nikalta hai. Errors ek jaise aur ek jagah likhe hote hain, aur stderr unhe aam output se alag rakhta hai. Achha message batata hai **kya** fail hua, **kaunsi** cheez (path, host), aur behtar ho to **kya karna hai**.

</Ur>
</Tr>

```bash
cat > backup.sh <<'EOF'
#!/usr/bin/env bash
log() { echo "[INFO] $*"; }
die() { echo "[ERROR] $1" >&2; exit "${2:-1}"; }

src="${1:-}"
[[ -n $src ]] || die "usage: backup.sh <folder>" 2
[[ -d $src ]] || die "folder '$src' does not exist"
log "backing up $src"
EOF
chmod +x backup.sh

./backup.sh; echo "exit: $?"
./backup.sh /nope; echo "exit: $?"
./backup.sh /etc; echo "exit: $?"
```

```text output
[ERROR] usage: backup.sh <folder>
exit: 2
[ERROR] folder '/nope' does not exist
exit: 1
[INFO] backing up /etc
exit: 0
```

<Happened>
<Tr>
<En>`die` takes a message and an optional code (`${2:-1}`): usage errors used 2, a missing folder used 1, and success ended with 0.</En>
<Ur>`die` message aur ikhtiyari code (`${2:-1}`) leta hai: usage error ne 2 diya, ghayab folder ne 1, aur kamyabi 0 par khatam hui.</Ur>
</Tr>
</Happened>

</Step>

<Step title="React differently to different codes">

<Tr>
<En>

Not all failures are equal: for `grep`, `1` means "not found" (often fine), but `2` means a real error. Save the code with `command || code=$?` (this form also works with `set -e`), then use `case`.

</En>
<Ur>

Har nakami barabar nahi: `grep` ke liye `1` ka matlab "nahi mila" (aksar theek), lekin `2` asli error. Code `command || code=$?` se mehfooz karein (ye `set -e` ke saath bhi chalta hai), phir `case` lagayen.

</Ur>
</Tr>

```bash
search() {
  local code=0
  grep -q "$1" "$2" 2> /dev/null || code=$?
  case $code in
    0) echo "'$1' found in $2" ;;
    1) echo "'$1' not found in $2 (that's OK)" ;;
    *) echo "grep failed with code $code — is $2 readable?" >&2 ;;
  esac
}
search root /etc/passwd
search nobody-here /etc/passwd
search root /no/such/file 2>&1
```

```text output
'root' found in /etc/passwd
'nobody-here' not found in /etc/passwd (that's OK)
grep failed with code 2 — is /no/such/file readable?
```

</Step>

<Step title="Retry flaky commands">

<Tr>
<En>

Networks, APIs and package mirrors fail **for a moment**. Failing a whole deploy for a 1-second hiccup is wasteful. Retry a few times with a **growing pause** (1 s, 2 s, 4 s…, called **exponential backoff**), and return failure if every attempt fails.

Like calling a friend whose line is busy: you wait a bit and try again, waiting a little longer each time, and give up after a few tries.

</En>
<Ur>

Networks, APIs aur package mirrors **thori der ke liye** fail hote hain. 1 second ki rukawat par poora deploy fail karna zaya hai. Chand dafa dobara koshish karein **barhte waqfe** ke saath (1 s, 2 s, 4 s…, jise **exponential backoff** kehte hain), aur sab koshishen fail hon to nakami lautayen.

Jaise kisi dost ko call karna jis ki line busy ho: thora ruk kar dobara milate hain, har dafa zara zyada intezar, aur chand koshishon ke baad chhor dete hain.

</Ur>
</Tr>

```bash
retry() {
  local max=$1; shift
  local attempt=1 delay=1
  until "$@"; do
    if (( attempt >= max )); then
      echo "Failed after $attempt attempts: $*" >&2
      return 1
    fi
    echo "Attempt $attempt failed, retrying in ${delay}s…" >&2
    sleep "$delay"
    ((attempt++)); ((delay *= 2))
  done
}

rm -f counter
flaky() { echo x >> counter; (( $(wc -l < counter) >= 3 )); }   # succeeds on the 3rd call

retry 5 flaky 2>&1 && echo "flaky succeeded"
retry 2 false 2>&1 || echo "false never succeeds"
```

```text output
Attempt 1 failed, retrying in 1s…
Attempt 2 failed, retrying in 2s…
flaky succeeded
Attempt 1 failed, retrying in 1s…
Failed after 2 attempts: false
false never succeeds
```

<Happened>
<Tr>
<En>`retry 5 flaky` means "try `flaky` up to 5 times". `shift` removed the number, so `"$@"` was just the command. `flaky` failed twice and worked on the 3rd try; `false` never works, so it gave up after 2.</En>
<Ur>`retry 5 flaky` ka matlab "`flaky` ko 5 dafa tak aazmao". `shift` ne number hataya, isliye `"$@"` sirf command thi. `flaky` do dafa fail hui aur teesri koshish par chali; `false` kabhi nahi chalti, isliye 2 ke baad haar maan li.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Errors hidden inside pipelines">

<Tr>
<En>

A pipeline's exit code is normally that of its **last** command only, so failures earlier in the pipe are **hidden**. `set -o pipefail` makes the pipeline fail if **any** part fails. `${PIPESTATUS[@]}` shows every part's code.

</En>
<Ur>

Pipeline ka exit code aam tor par sirf us ki **aakhri** command ka hota hai, isliye pipe me pehle ki nakamiyan **chhup** jati hain. `set -o pipefail` pipeline ko fail karta hai agar **koi bhi** hissa fail ho. `${PIPESTATUS[@]}` har hisse ka code dikhata hai.

</Ur>
</Tr>

```bash
false | gzip > out.gz
echo "without pipefail: $?   parts: ${PIPESTATUS[*]}"

set -o pipefail
false | gzip > out.gz
echo "with pipefail:    $?"
```

```text output
without pipefail: 0   parts: 1 0
with pipefail:    1
```

<Happened>
<Tr>
<En>Imagine `false` is `mysqldump` failing. Without `pipefail`, the backup script reports success while saving an **empty** backup, and you only find out on the day you need to restore.</En>
<Ur>Sochein `false` dar asal `mysqldump` ka fail hona hai. `pipefail` ke baghair backup script kamyabi batata hai jabke **khaali** backup save hota hai, aur pata us din chalta hai jab restore karna ho.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Set the script's final exit code">

<Tr>
<En>

Batch jobs (checking many hosts or files) often keep going after one item fails, but the **final** code must still report it. Count failures, and make the last line `(( failed == 0 ))`, so the result is success only if nothing failed.

</En>
<Ur>

Batch jobs (kai hosts ya files check karna) aksar ek cheez fail hone ke baad bhi chalte rehte hain, lekin **aakhri** code ko phir bhi ye batana chahiye. Nakamiyan ginein, aur aakhri line `(( failed == 0 ))` rakhein, taa ke nateeja tab hi kamyab ho jab kuch fail na hua ho.

</Ur>
</Tr>

```bash
check_all() {
  local failed=0
  for path in /etc /tmp /no/such/dir /var; do
    if [[ -d $path ]]; then
      echo "OK      $path"
    else
      echo "MISSING $path"
      ((failed++))
    fi
  done
  echo "$failed problem(s) found"
  (( failed == 0 ))
}
check_all; echo "final exit code: $?"
```

```text output
OK      /etc
OK      /tmp
MISSING /no/such/dir
OK      /var
1 problem(s) found
final exit code: 1
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Batch job always 'succeeds'">

```text
for h in $hosts; do ping -c1 "$h" || echo "$h down"; done
echo "done"          # exit code 0, even if every host was down
```

</Bad>
<Good title="Track failures">

```text
failed=0
for h in $hosts; do ping -c1 "$h" > /dev/null || { echo "$h down"; ((failed++)); }; done
(( failed == 0 ))
```

</Good>
</Compare>

<Compare>
<Bad title="Error on stdout">

```text
echo "Error: file missing"        # ends up in output files and captured variables
```

</Bad>
<Good title="Error on stderr">

```text
echo "Error: file missing" >&2
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Ignoring failures**: no checks, so the script continues after a failed `cd` or download.
- **Reading `$?` too late**: after an `echo` or `if`, it's no longer the code you care about.
- **`exit` inside a function meant to return**: kills the whole script.
- **Retrying everything**: retrying a step that isn't safe to repeat (payments, migrations) can do it twice.
- **`exit -1` or `exit 300`**: codes are 0–255 (`-1` becomes 255, `300` becomes 44).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Nakamiyan nazar andaz karna**: koi check nahi, isliye fail `cd` ya download ke baad bhi script chalta rehta hai.
- **`$?` der se parhna**: `echo` ya `if` ke baad ye wo code nahi rehta jo aap chahte hain.
- **Return ke liye bane function me `exit`**: poora script maar deta hai.
- **Har cheez dobara aazmana**: jo step dohrane ke liye mehfooz nahi (payments, migrations), wo do dafa ho sakta hai.
- **`exit -1` ya `exit 300`**: codes 0–255 hain (`-1` 255 ban jata hai, `300` 44).

</Ur>
</Tr>

## Try it yourself

<Challenge title="Error lab">

<Tr>
<En>
This lab shows the codes 0, 2, a custom 42, and 126 (not executable), `&&`/`||` chains, `die` inside a subshell, and `pipefail` catching a failure.
</En>
<Ur>
Ye lab codes 0, 2, apna 42, aur 126 (chalne layaq nahi), `&&`/`||` zanjeeren, subshell me `die`, aur `pipefail` ka nakami pakarna dikhata hai.
</Ur>

```bash
mkdir -p ~/err-lab && cd ~/err-lab

# 1. codes
ls /etc > /dev/null; echo "ok: $?"
ls /nope 2> /dev/null; echo "missing: $?"
bash -c 'exit 42'; echo "custom: $?"
printf 'echo hi' > noexec.sh; ./noexec.sh 2> /dev/null; echo "not executable: $?"

# 2. && || chains
mkdir -p build && echo "build folder ready"
cp /nope/file . 2> /dev/null || echo "copy failed, handled"

# 3. die helper
die() { echo "ERROR: $*" >&2; exit 1; }
( [[ -f settings.ini ]] || die "settings.ini missing" ) 2>&1; echo "subshell exit: $?"

# 4. pipefail
set -o pipefail
if ! cat /nope 2> /dev/null | wc -l > /dev/null; then echo "pipeline failure detected"; fi

cd ~ && rm -rf ~/err-lab
```

```text output
missing: 2
custom: 42
not executable: 126
build folder ready
copy failed, handled
ERROR: settings.ini missing
subshell exit: 1
pipeline failure detected
```

<DeepDive title="Real world: a CI deploy step">

Proper error handling at every stage:

```bash
#!/usr/bin/env bash
# deploy.sh <image-tag>
set -euo pipefail

log() { echo "[$(date +%T)] $*"; }
die() { echo "[$(date +%T)] ERROR: $*" >&2; exit 1; }

retry() {
  local n=1 max=4 delay=2
  until "$@"; do
    (( n >= max )) && return 1
    log "attempt $n failed: $* — retrying in ${delay}s"
    sleep "$delay"; ((n++)); ((delay *= 2))
  done
}

tag="${1:?usage: deploy.sh <image-tag>}"
command -v docker > /dev/null || die "docker is not installed"

log "pulling image $tag"
retry docker pull "registry.example.com/shop:$tag" || die "could not pull image after retries"

log "running database migrations"
docker run --rm "registry.example.com/shop:$tag" npm run migrate || die "migrations failed — NOT deploying"

log "restarting service"
docker compose up -d shop || die "restart failed"

log "checking health"
retry curl -fsS http://localhost:3000/health > /dev/null || die "new version is unhealthy — roll back!"

log "deploy of $tag finished"
```

- **Retries** only for things that can fail temporarily (pulling, health checks), never for migrations.
- **Every failure exits non-zero** with a message saying what failed and what to do, so the CI job turns red and the log is clear.

</DeepDive>

<DeepDive title="Security lens">

A script that fails silently can leave systems half-configured, with security controls missing and nobody aware.

- **Fail closed:** if a security step fails (a firewall rule, rotating a key, verifying a checksum), stop with a non-zero code. Never "continue anyway".
- **Verify downloads:** `sha256sum -c` returns non-zero on mismatch; check it before running anything you downloaded.
- **Error messages must not leak secrets:** don't print full connection strings, tokens or passwords in errors or logs.
- **Exit codes feed monitoring:** security checks run by cron should exit non-zero on findings so alerts fire.
- **Code 127 in production** often means a tool is missing or PATH is different under cron: a security scan that "ran" may never have run.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is an exit code and what does 0 mean?">
An exit code is a number from 0 to 255 that every process returns when it finishes. 0 means success; any non-zero value means some kind of failure, with the specific number indicating the type of problem. Shells, CI systems, cron and orchestrators use it to decide whether a step succeeded.
</QA>

<QA q="What do exit codes 126, 127 and 137 mean?">
126 means the command was found but could not be executed, usually because of missing execute permission. 127 means the command was not found, often a typo or a missing tool or PATH. Codes above 128 mean the process was killed by a signal: 137 is 128 plus signal 9 (SIGKILL), commonly seen when a container is killed for exceeding its memory limit.
</QA>

<QA q="What is the difference between exit and return?">
exit ends the entire script (or shell) with the given code. return ends only the current function and gives its caller an exit status. Using exit inside a function stops the whole script.
</QA>

<QA q="Why use set -o pipefail?">
By default, a pipeline's exit status is that of its last command, so failures earlier in the pipeline are hidden. With pipefail, the pipeline returns the status of the last command that failed, so errors such as a failing database dump piped into gzip are detected.
</QA>

<QA q="How would you handle a command that sometimes fails because of the network?">
Wrap it in a retry function that runs the command up to a maximum number of attempts with an increasing delay between them (exponential backoff), and returns a non-zero status if every attempt fails. Only retry operations that are safe to repeat.
</QA>

</DeepDive>
