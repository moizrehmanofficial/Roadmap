## Part 1: the backup script

<Walkthrough>

<Step title="Create an archive with tar">

<Tr>
<En>

`tar -czf archive.tar.gz -C /parent folder`: `c` = create, `z` = gzip, `f` = file name, and `-C` moves into the parent first so the archive holds relative paths. List contents with `tar -tzf`; restore with `tar -xzf`.

</En>
<Ur>

`tar -czf archive.tar.gz -C /parent folder`: `c` = banao, `z` = gzip, `f` = file ka naam, aur `-C` pehle parent me jata hai taa ke archive me relative paths hon. Mawad `tar -tzf` se dekhein; `tar -xzf` se wapas nikalein.

</Ur>
</Tr>

```bash
mkdir -p site/uploads
echo "<h1>Shop</h1>" > site/index.html
echo "photo" > site/uploads/1.jpg

tar -czf site-backup.tar.gz -C . site
echo "Archive contents:"
tar -tzf site-backup.tar.gz | sort
```

```text output
Archive contents:
site/
site/index.html
site/uploads/
site/uploads/1.jpg
```

</Step>

<Step title="Dated file names">

<Tr>
<En>

Put the date and time in each name so every run makes a **new** file instead of overwriting yesterday's, and you see each backup's age at a glance. `date +%F_%H%M` gives `2026-11-10_0200`, which also sorts correctly by name.

</En>
<Ur>

Har naam me tareekh aur waqt daalein taa ke har run kal wali file par likhne ke bajaye **nayi** file banaye, aur aap ek nazar me har backup ki umar dekh sakein. `date +%F_%H%M` `2026-11-10_0200` deta hai, jo naam se sahi tarteeb me bhi aata hai.

</Ur>
</Tr>

```bash
stamp=$(date -d "2026-11-10 02:00" +%F_%H%M)
name="site-${stamp}.tar.gz"
echo "$name"
```

```text output
site-2026-11-10_0200.tar.gz
```

<Happened>
<Tr>
<En>In a real script, plain `date +%F_%H%M` uses the current time; here a fixed date keeps the output the same.</En>
<Ur>Asli script me saada `date +%F_%H%M` mojooda waqt leta hai; yahan pakki tareekh output ko ek jaisa rakhti hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Check the backup is really OK">

<Tr>
<En>

Disks fill up, processes get killed, files get corrupted. Many teams found out their backups were broken only on the day they needed them. Right after creating one:

- `tar -tzf archive > /dev/null` reads the whole archive and fails if it's damaged.
- `[[ -s file ]]` checks it isn't empty.
- `sha256sum` stores a fingerprint you can re-check later.

</En>
<Ur>

Disks bhar jati hain, processes maare jate hain, files kharab hoti hain. Kai teams ko pata tab chala ke un ke backups toote hue the jab un ki zaroorat thi. Banane ke foran baad:

- `tar -tzf archive > /dev/null` poora archive parhta hai aur kharab ho to fail hota hai.
- `[[ -s file ]]` check karta hai ke khaali na ho.
- `sha256sum` ek fingerprint rakhta hai jo baad me dobara check ho sakta hai.

</Ur>
</Tr>

```bash
if tar -tzf site-backup.tar.gz > /dev/null && [[ -s site-backup.tar.gz ]]; then
  echo "backup OK"
fi
head -c 100 site-backup.tar.gz > broken.tar.gz
tar -tzf broken.tar.gz > /dev/null 2>&1 || echo "broken backup detected"
sha256sum site-backup.tar.gz > site-backup.tar.gz.sha256
sha256sum -c site-backup.tar.gz.sha256
```

```text output
backup OK
broken backup detected
site-backup.tar.gz: OK
```

</Step>

<Step title="Retention: delete old backups">

<Tr>
<En>

Without retention, backups slowly fill the disk, and a full disk breaks the server **and** the next backup. `find "$dest" -name 'site-*.tar.gz' -mtime +7 -delete` removes backups older than 7 days. The name pattern makes sure only backup files are touched. Run it **only after** the new backup was verified.

</En>
<Ur>

Retention ke baghair backups aahista aahista disk bhar dete hain, aur bhari disk server **aur** agla backup dono tor deti hai. `find "$dest" -name 'site-*.tar.gz' -mtime +7 -delete` 7 din se purane backups mitata hai. Naam ka pattern yaqeeni banata hai ke sirf backup files chhui jayen. Ise naya backup check hone ke **baad hi** chalayen.

</Ur>
</Tr>

```bash
mkdir -p backups
for d in 1 3 6 8 15 30; do
  f="backups/site-day$d.tar.gz"; touch "$f"; touch -d "$d days ago" "$f"
done
echo "before: $(ls backups | wc -l) backups"
find backups -name 'site-*.tar.gz' -mtime +7 -print -delete | sort
echo "after: $(ls backups | wc -l) backups"
```

```text output
before: 6 backups
backups/site-day15.tar.gz
backups/site-day30.tar.gz
backups/site-day8.tar.gz
after: 3 backups
```

</Step>

<Step title="The complete backup script">

<Tr>
<En>

All the pieces together: strict mode, arguments with defaults, logging, validation, a temporary file cleaned up by a trap, verification and retention. It writes to a **temporary file first** and renames it only after verification, so a broken archive never looks like a valid backup.

</En>
<Ur>

Saare tukre ek saath: strict mode, defaults wale arguments, logging, validation, trap se saaf hone wali temporary file, verification aur retention. Ye **pehle temporary file** me likhta hai aur verification ke baad hi naam badalta hai, taa ke toota archive kabhi sahi backup jaisa na lage.

</Ur>
</Tr>

```bash
cat > backup.sh <<'EOF'
#!/usr/bin/env bash
# backup.sh <source-dir> [dest-dir] [keep-days]
set -euo pipefail

src="${1:?usage: backup.sh <source-dir> [dest-dir] [keep-days]}"
dest="${2:-./backups}"
keep="${3:-7}"
log() { echo "[backup] $*"; }
die() { echo "[backup] ERROR: $*" >&2; exit 1; }

[[ -d $src ]] || die "source $src does not exist"
[[ $keep =~ ^[0-9]+$ ]] || die "keep-days must be a number"
mkdir -p "$dest"

name="$(basename "$src")-$(date +%F_%H%M%S).tar.gz"
tmp="$(mktemp "$dest/.partial.XXXXXX")"
trap 'rm -f "$tmp"' EXIT

log "archiving $src"
tar -czf "$tmp" -C "$(dirname "$src")" "$(basename "$src")"
tar -tzf "$tmp" > /dev/null || die "verification failed"
mv "$tmp" "$dest/$name"
log "saved $name ($(du -h "$dest/$name" | cut -f1))"

deleted=$(find "$dest" -name "$(basename "$src")-*.tar.gz" -mtime +"$keep" -print -delete | wc -l)
log "removed $deleted backup(s) older than $keep days"
EOF
chmod +x backup.sh

./backup.sh site ./backups 7 | sed -E 's/[0-9]{4}-[0-9]{2}-[0-9]{2}_[0-9]{6}/DATE/; s/\(([0-9.]+K)\)/(SIZE)/'
./backup.sh missing-folder; echo "exit: $?"
```

```text output
[backup] archiving site
[backup] saved site-DATE.tar.gz (SIZE)
[backup] removed 0 backup(s) older than 7 days
[backup] ERROR: source missing-folder does not exist
exit: 1
```

<Happened>
<Tr>
<En>The `sed` only masks the date and size, which change every run. Restoring is the reverse: `tar -xzf backups/site-….tar.gz -C /restore/here`. **Practise restoring regularly**: that's the only real proof a backup works.</En>
<Ur>`sed` sirf tareekh aur size chhupata hai, jo har run badalte hain. Wapas laana ulta hai: `tar -xzf backups/site-….tar.gz -C /restore/here`. **Restore karne ki baqaida mashq karein**: backup ke chalne ka yahi asli saboot hai.</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Part 2: log analysis

<Walkthrough>

<Step title="The sample access log">

<Tr>
<En>

A web server access log has one line per request: who (IP), when, what (method and path), the result (status code), size, and often the time taken. Know which column holds what, then use `awk` on those columns.

Columns here: `$1` IP, `$4` time (with `[`), `$6` method (with a quote), `$7` path, `$9` status, `$10` bytes, `$11` seconds taken.

</En>
<Ur>

Web server access log me har request ki ek line hoti hai: kaun (IP), kab, kya (method aur path), nateeja (status code), size, aur aksar lagne wala waqt. Jaanein kaunsa column kya rakhta hai, phir un columns par `awk` chalayen.

Yahan columns: `$1` IP, `$4` waqt (`[` ke saath), `$6` method (quote ke saath), `$7` path, `$9` status, `$10` bytes, `$11` lagne wale seconds.

</Ur>
</Tr>

```bash
cat > access.log <<'EOF'
203.0.113.5 - - [10/Nov/2026:10:00:01 +0000] "GET / HTTP/1.1" 200 5120 0.012
203.0.113.5 - - [10/Nov/2026:10:00:02 +0000] "GET /shop HTTP/1.1" 200 8100 0.240
198.51.100.7 - - [10/Nov/2026:10:00:03 +0000] "POST /login HTTP/1.1" 401 210 0.030
198.51.100.7 - - [10/Nov/2026:10:00:04 +0000] "POST /login HTTP/1.1" 401 210 0.031
198.51.100.7 - - [10/Nov/2026:10:00:05 +0000] "POST /login HTTP/1.1" 401 210 0.029
192.0.2.44 - - [10/Nov/2026:10:01:10 +0000] "GET /api/orders HTTP/1.1" 500 90 2.950
192.0.2.44 - - [10/Nov/2026:10:01:12 +0000] "GET /wp-login.php HTTP/1.1" 404 150 0.004
203.0.113.5 - - [10/Nov/2026:10:02:00 +0000] "GET /api/orders HTTP/1.1" 200 4300 1.820
EOF
awk '{print "IP=" $1, "path=" $7, "status=" $9, "seconds=" $11}' access.log | head -2
```

```text output
IP=203.0.113.5 path=/ status=200 seconds=0.012
IP=203.0.113.5 path=/shop status=200 seconds=0.240
```

</Step>

<Step title="Count by status code and by IP">

<Tr>
<En>

"How many errors?" and "who sends the most requests?" are the first two questions in any web incident. The recipe: pull out the column with `awk`, then `sort | uniq -c | sort -rn | head`.

</En>
<Ur>

"Kitne errors?" aur "sab se zyada requests kaun bhej raha hai?" har web hadse ke pehle do sawal hain. Nuskha: `awk` se column nikalo, phir `sort | uniq -c | sort -rn | head`.

</Ur>
</Tr>

```bash
echo "Requests per status code:"
awk '{print $9}' access.log | sort | uniq -c | sort -rn
echo "Top IPs:"
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -3
```

```text output
Requests per status code:
      3 401
      3 200
      1 500
      1 404
Top IPs:
      3 203.0.113.5
      3 198.51.100.7
      2 192.0.2.44
```

</Step>

<Step title="Find errors, brute force and slow requests">

<Tr>
<En>

- **5xx** server errors mean something is broken: `awk '$9 >= 500'`.
- **Many 401s** from one IP mean someone is guessing passwords: count per IP, keep those above a limit.
- **Slow requests** mean unhappy users: `awk '$11 > 1.0'`.
- **Probes** for `/wp-login.php` on a non-WordPress site are scanner noise.

</En>
<Ur>

- **5xx** server errors ka matlab kuch toota hai: `awk '$9 >= 500'`.
- Ek IP se **bohot se 401** ka matlab koi password andaza laga raha hai: har IP ke liye gino, had se ooper wale rakho.
- **Dheeme requests** ka matlab naraz users: `awk '$11 > 1.0'`.
- Ghair-WordPress site par `/wp-login.php` ki **talaash** scanner ka shor hai.

</Ur>
</Tr>

```bash
echo "Server errors (5xx):"
awk '$9 >= 500 {print $4, $7, $9}' access.log | tr -d '['
echo "Possible brute force (3+ failed logins):"
awk '$9 == 401 && $7 == "/login" {print $1}' access.log | sort | uniq -c | awk '$1 >= 3 {print $2, "(" $1 " attempts)"}'
echo "Slow requests (> 1 second):"
awk '$11 > 1.0 {printf "%.2fs %s\n", $11, $7}' access.log | sort -rn
echo "Scanner noise (WordPress probes on a non-WordPress site):"
grep -c 'wp-login' access.log
```

```text output
Server errors (5xx):
10/Nov/2026:10:01:10 /api/orders 500
Possible brute force (3+ failed logins):
198.51.100.7 (3 attempts)
Slow requests (> 1 second):
2.95s /api/orders
1.82s /api/orders
Scanner noise (WordPress probes on a non-WordPress site):
1
```

</Step>

</Walkthrough>

## Part 3: the health check

<Walkthrough>

<Step title="Disk usage">

<Tr>
<En>

A full disk is one of the most common causes of outages: databases stop writing, logs stop, deploys fail. `df --output=pcent /` prints the usage percentage; strip the `%` and compare with `(( ))`.

</En>
<Ur>

Bhari disk outages ki sab se aam wajahon me se hai: databases likhna band, logs band, deploys fail. `df --output=pcent /` istemal ka percentage chhaapta hai; `%` hata kar `(( ))` se muqabla karein.

</Ur>
</Tr>

```bash
check_disk() {
  local mount="$1" warn="$2" used
  used=$(df --output=pcent "$mount" | tail -1 | tr -dc '0-9')
  if (( used >= warn )); then
    echo "WARN disk $mount at ${used}% (limit ${warn}%)"; return 1
  fi
  echo "OK   disk $mount below ${warn}%"
}
check_disk / 100
if ! result=$(check_disk / 0); then
  echo "$result" | sed "s/at [0-9]*%/at XX%/"
  echo "(that warning was forced with a 0% limit, to show the failure path)"
fi
```

```text output
OK   disk / below 100%
WARN disk / at XX% (limit 0%)
(that warning was forced with a 0% limit, to show the failure path)
```

<Happened>
<Tr>
<En>Your real percentage appears instead of `XX`. The 0% limit forced a warning just to show what failure looks like.</En>
<Ur>`XX` ki jagah aap ka asli percentage aata hai. 0% had ne sirf ye dikhane ke liye warning zabardasti karwayi ke nakami kaisi lagti hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Memory, services and websites">

<Tr>
<En>

A server can be "up" but broken in different ways:

- **Memory:** `free -m`, column "available".
- **Service:** `systemctl is-active --quiet nginx`.
- **Website:** `curl -s -o /dev/null -w '%{http_code}' --max-time 5 URL` gives the HTTP code.

</En>
<Ur>

Server "chal raha" ho sakta hai lekin mukhtalif tareeqon se toota hua:

- **Memory:** `free -m`, "available" column.
- **Service:** `systemctl is-active --quiet nginx`.
- **Website:** `curl -s -o /dev/null -w '%{http_code}' --max-time 5 URL` HTTP code deta hai.

</Ur>
</Tr>

```bash
check_url() {
  local url="$1" code
  code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 "$url" || true)
  if [[ $code == 200 ]]; then echo "OK   $url (HTTP $code)"; else echo "FAIL $url (HTTP $code)"; return 1; fi
}

python3 -m http.server 8765 --bind 127.0.0.1 > /dev/null 2>&1 &
server=$!
sleep 1
check_url http://127.0.0.1:8765/
check_url http://127.0.0.1:8765/no-such-page || true
kill "$server"

avail=$(free -m | awk '/^Mem:/ {print $7}')
(( avail > 0 )) && echo "OK   memory: some MB available"
```

```text output
OK   http://127.0.0.1:8765/ (HTTP 200)
FAIL http://127.0.0.1:8765/no-such-page (HTTP 404)
OK   memory: some MB available
```

<Happened>
<Tr>
<En>`python3 -m http.server` started a tiny local web server just for this example. On a real server you check your real site and services, for example `systemctl is-active --quiet nginx || echo "FAIL nginx"`.</En>
<Ur>`python3 -m http.server` ne sirf is misaal ke liye chhota local web server chalaya. Asli server par aap apni asli site aur services check karte hain, maslan `systemctl is-active --quiet nginx || echo "FAIL nginx"`.</Ur>
</Tr>
</Happened>

</Step>

<Step title="The complete health check script">

<Tr>
<En>

One script that runs **every** check (so no `-e`), prints one clear line per check, and exits non-zero if **any** failed. Monitoring systems and cron react to the exit code, and one line per check is easy to read on a phone at 3 a.m. Settings come from environment variables with defaults, so the same script works on every server.

</En>
<Ur>

Ek script jo **har** check chalaye (isliye `-e` nahi), har check ki ek saaf line chhaape, aur **koi bhi** fail ho to non-zero par nikle. Monitoring systems aur cron exit code par react karte hain, aur har check ki ek line raat 3 baje phone par parhna aasaan hai. Settings defaults ke saath environment variables se aati hain, isliye wahi script har server par chalta hai.

</Ur>
</Tr>

```bash
cat > healthcheck.sh <<'EOF'
#!/usr/bin/env bash
set -uo pipefail          # no -e: we want every check to run
DISK_LIMIT="${DISK_LIMIT:-90}"
MEM_MIN_MB="${MEM_MIN_MB:-200}"
failures=0
ok()   { echo "OK   $*"; }
fail() { echo "FAIL $*"; ((failures++)); }

used=$(df --output=pcent / | tail -1 | tr -dc '0-9')
(( used < DISK_LIMIT )) && ok "disk below ${DISK_LIMIT}%" || fail "disk / at ${used}%"

avail=$(free -m | awk '/^Mem:/ {print $7}')
(( avail >= MEM_MIN_MB )) && ok "memory available >= ${MEM_MIN_MB} MB" || fail "only ${avail} MB memory available"

for svc in ${SERVICES:-}; do
  systemctl is-active --quiet "$svc" && ok "service $svc" || fail "service $svc is not running"
done

echo "---"
if (( failures > 0 )); then echo "$failures check(s) failed"; exit 1; fi
echo "all checks passed"
EOF
chmod +x healthcheck.sh
MEM_MIN_MB=1 ./healthcheck.sh; echo "exit: $?"
DISK_LIMIT=1 MEM_MIN_MB=1 ./healthcheck.sh | grep -E "FAIL|failed" | sed 's/at [0-9]*%/at XX%/'; echo "exit: ${PIPESTATUS[0]}"
```


## Common mistakes

<Compare>
<Bad title="Retention before verification">

```text
tar -czf "$dest/$name" "$src"
find "$dest" -mtime +7 -delete       # old good backups gone…
tar -tzf "$dest/$name"                # …and the new one is broken
```

</Bad>
<Good title="Verify first, then clean up">

```text
tar -czf "$tmp" "$src"
tar -tzf "$tmp" > /dev/null && mv "$tmp" "$dest/$name"
find "$dest" -name 'site-*.tar.gz' -mtime +7 -delete
```

</Good>
</Compare>

<Compare>
<Bad title="Health check that always exits 0">

```text
df -h /; free -m; systemctl status nginx    # prints, never fails → no alerts
```

</Bad>
<Good title="Count failures, exit non-zero">

```text
(( used < 90 )) || { echo "FAIL disk"; ((failures++)); }
(( failures == 0 ))
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Never testing restores**: a backup is only proven when you've restored it.
- **Backups on the same disk** as the data: one disk failure loses both.
- **Relative paths and no logs in cron jobs**: they fail silently.
- **Fixed column numbers without checking the log format**: formats differ between servers.
- **Copying a live database's files**: use its dump tool (`pg_dump`, `mysqldump`) instead.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Restore kabhi test na karna**: backup tab hi saabit hota hai jab aap ne use restore kiya ho.
- **Data wali disk par hi backups**: ek disk kharab, dono gaye.
- **Cron jobs me relative paths aur logs na hona**: ye khamoshi se fail hote hain.
- **Log format check kiye baghair pakke column numbers**: formats har server par alag hote hain.
- **Chalte database ki files copy karna**: is ki jagah us ka dump tool (`pg_dump`, `mysqldump`) istemal karein.

</Ur>
</Tr>

<DeepDive title="Real world: the 3-2-1 backup rule">

- **3** copies of the data (the original + 2 backups),
- on **2** different kinds of storage (local disk + object storage),
- **1** copy off-site (another region or provider).

```bash
#!/usr/bin/env bash
# nightly-backup.sh — run by cron at 02:00
set -euo pipefail

/usr/local/bin/backup.sh /var/www/shop /mnt/backups 7          # copy 2: local disk, 7 days

latest=$(ls -1t /mnt/backups/shop-*.tar.gz | head -1)
sha256sum "$latest" > "$latest.sha256"

aws s3 cp "$latest"        "s3://acme-backups/shop/" --storage-class STANDARD_IA   # copy 3: off-site
aws s3 cp "$latest.sha256" "s3://acme-backups/shop/"

/usr/local/bin/healthcheck.sh > /dev/null || echo "health check failed after backup" >&2
echo "nightly backup done: $(basename "$latest")"
```

Add an S3 **lifecycle rule** to delete off-site copies after 30 days, and enable **object lock / versioning** so ransomware on the server can't delete the off-site backups.

</DeepDive>

<DeepDive title="Security lens">

Backups and logs contain your most sensitive data. Protect them as carefully as the production system.

- **Encrypt backups** that leave the server (`gpg --symmetric`, or server-side encryption in S3) and restrict permissions (`chmod 600`, `umask 077`).
- **Immutable / off-site copies** (S3 Object Lock, versioning) protect against ransomware that deletes local backups.
- **Logs are evidence:** ship them to a central system (ELK, Loki, CloudWatch, a SIEM) so an attacker on the server can't erase them.
- **Log analysis is detection:** many 401s from one IP (brute force), requests for `/wp-login.php`, `/.env` or `/.git/config` (scanners), and sudden 5xx spikes are classic signals. Turn them into alerts.
- **Don't log secrets:** tokens in URLs and query strings end up in access logs.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How would you design a backup script for a web server?">
Use strict mode, validate the source and destination, create a timestamped tar.gz archive into a temporary file, verify it with tar -t and store a checksum, then move it into place. Delete old backups with find -mtime only after the new one is verified, log every step, run it from cron with output redirected to a log, keep an off-site copy, and regularly test restores.
</QA>

<QA q="How do you find the top 10 IP addresses in an nginx access log?">
`awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10`. awk extracts the first column, sort groups identical IPs, uniq -c counts them, sort -rn orders by count descending and head keeps the first ten.
</QA>

<QA q="What should a server health check script do and how should it report failures?">
It should check key resources and services, such as disk usage, available memory, required services and HTTP endpoints, against configurable thresholds. It should run every check even if one fails, print a clear line per check, and exit with a non-zero status if any check failed, so cron, CI or a monitoring system can alert on it.
</QA>

<QA q="What is the 3-2-1 backup rule?">
Keep three copies of data, on two different types of storage, with one copy off-site. It protects against single-disk failure, site-wide incidents and ransomware, especially when the off-site copy is immutable or versioned.
</QA>

</DeepDive>
