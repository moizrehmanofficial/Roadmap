<Callout type="tip" title="In one minute">
Three scripts almost every server needs. A **backup script** archives a folder with `tar`, names it with the date, verifies it, and deletes copies older than N days. A **log analyser** uses `grep`, `awk`, `sort` and `uniq -c` to count errors, top IPs and slow requests. A **health check** compares disk, memory, service and website status against thresholds and exits non-zero when something is wrong. **cron** runs them automatically on a schedule.
</Callout>

## Start from zero

### From lessons to tools

Up to now you learned separate pieces: variables, conditions, loops, functions, error handling, traps, text tools. Real scripts **combine** them. This lesson builds three tools you will actually use on servers, one small piece at a time, so you can see how each earlier lesson fits in.

<Callout type="analogy">
Learning Bash commands is like learning to use a hammer, a saw and a drill. This lesson is **building the first piece of furniture**: you will see why the measuring tape (validation), the safety goggles (strict mode, traps) and the order of steps matter.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Backup** | A copy of data kept so it can be restored after loss | `site-2026-11-10.tar.gz` |
| **Archive** | Many files packed into one file | made with `tar` |
| **Retention** | How long backups are kept | "keep 7 days" |
| **Restore** | Putting backed-up data back | `tar -xzf backup.tar.gz` |
| **Log** | A file where programs write what happened | `/var/log/nginx/access.log` |
| **Health check** | An automatic test of whether a system is OK | "disk below 90%?" |
| **Threshold** | The limit at which something becomes a warning | 80% disk |
| **cron** | The Linux scheduler that runs commands at set times | every night at 02:00 |

## What is it?

Three complete, safe, reusable scripts:

| Script | Answers the question | Main tools |
| --- | --- | --- |
| `backup.sh` | "If this folder is lost, can I get it back?" | `tar`, `date`, `find`, `trap` |
| `analyze-log.sh` | "What happened on my web server?" | `grep`, `awk`, `sort`, `uniq` |
| `healthcheck.sh` | "Is this server OK right now?" | `df`, `free`, `systemctl`, `curl` |

## Why does it matter?

- **Backups** are the last line of defence against mistakes, disk failures and **ransomware**. A backup that was never verified is not a backup.
- **Log analysis** is the first step of every incident: errors, attacks and slow pages all show up in logs.
- **Health checks** catch problems (a full disk is the classic one) **before** users notice.
- These are exactly the kinds of scripts asked for in DevOps take-home tasks and interviews.

## When and where do you use it?

- **Backups:** nightly on every server with important data (uploads, databases, configs).
- **Log analysis:** during incidents, in daily reports, during security investigations.
- **Health checks:** every few minutes from cron, or as the check command for a monitoring system.

## Concepts one by one

### 1. Creating an archive with `tar`

<Explain>
<What>
`tar` packs a folder into one file; with `-z` it also compresses it with gzip (`.tar.gz`).
</What>
<Why>
One compressed file is easy to copy, store and restore.
</Why>
<When>
The core step of every file backup.
</When>
<Where>
Web roots, upload folders, config folders like `/etc/nginx`.
</Where>
<How>
`tar -czf archive.tar.gz -C /parent folder` — `c` create, `z` gzip, `f` file name, `-C` change into the parent first so the archive contains relative paths. List contents with `tar -tzf`, restore with `tar -xzf`.
</How>
</Explain>

```bash
mkdir -p site/uploads
echo "<h1>Shop</h1>" > site/index.html
echo "photo" > site/uploads/1.jpg

tar -czf site-backup.tar.gz -C . site
echo "Archive contents:"
tar -tzf site-backup.tar.gz | sort
```

```text output
Archive contents:
site/
site/index.html
site/uploads/
site/uploads/1.jpg
```

### 2. Dated file names

<Explain>
<What>
Putting the date and time into each backup's name.
</What>
<Why>
So each run creates a **new** file instead of overwriting yesterday's, and you can see at a glance how old each backup is.
</Why>
<When>
Every backup and report.
</When>
<Where>
`site-2026-11-10_0200.tar.gz`.
</Where>
<How>
`stamp=$(date +%F_%H%M)` → `2026-11-10_0200`. This format also sorts correctly by name.
</How>
</Explain>

```bash
stamp=$(date -d "2026-11-10 02:00" +%F_%H%M)
name="site-${stamp}.tar.gz"
echo "$name"
```

```text output
site-2026-11-10_0200.tar.gz
```

(In the real script, plain `date +%F_%H%M` uses the current time; here a fixed date keeps the output the same.)

### 3. Verifying the backup

<Explain>
<What>
Checking that the archive is complete and readable right after creating it.
</What>
<Why>
Disks fill up, processes get killed, files get corrupted. Many teams discovered their backups were broken only on the day they needed them.
</Why>
<When>
Immediately after every backup.
</When>
<Where>
In the backup script, before deleting old backups.
</Where>
<How>
`tar -tzf archive > /dev/null` reads the whole archive and fails if it is damaged. Also check it is not empty (`-s`). For extra safety, store a checksum: `sha256sum archive > archive.sha256`.
</How>
</Explain>

```bash
if tar -tzf site-backup.tar.gz > /dev/null && [[ -s site-backup.tar.gz ]]; then
  echo "backup OK"
fi
head -c 100 site-backup.tar.gz > broken.tar.gz
tar -tzf broken.tar.gz > /dev/null 2>&1 || echo "broken backup detected"
sha256sum site-backup.tar.gz > site-backup.tar.gz.sha256
sha256sum -c site-backup.tar.gz.sha256
```

```text output
backup OK
broken backup detected
site-backup.tar.gz: OK
```

### 4. Retention: deleting old backups

<Explain>
<What>
Automatically removing backups older than a number of days.
</What>
<Why>
Without it, backups slowly fill the disk — and a full disk breaks the server **and** the next backup.
</Why>
<When>
At the end of every backup run, only after the new backup was verified.
</When>
<Where>
The backup folder.
</Where>
<How>
`find "$dest" -name 'site-*.tar.gz' -mtime +7 -delete`. The name pattern makes sure only backup files are touched.
</How>
</Explain>

```bash
mkdir -p backups
for d in 1 3 6 8 15 30; do
  f="backups/site-day$d.tar.gz"; touch "$f"; touch -d "$d days ago" "$f"
done
echo "before: $(ls backups | wc -l) backups"
find backups -name 'site-*.tar.gz' -mtime +7 -print -delete | sort
echo "after: $(ls backups | wc -l) backups"
```

```text output
before: 6 backups
backups/site-day15.tar.gz
backups/site-day30.tar.gz
backups/site-day8.tar.gz
after: 3 backups
```

### 5. The complete backup script

<Explain>
<What>
All the pieces combined: strict mode, arguments with defaults, logging, a temporary file that is cleaned up by a trap, verification and retention.
</What>
<Why>
Each piece guards against a real failure: a missing folder, a half-written archive, a full disk.
</Why>
<When>
Nightly from cron.
</When>
<Where>
`/usr/local/bin/backup.sh` on the server.
</Where>
<How>
Write to a temporary file first and rename it only after verification, so a broken archive never looks like a valid backup.
</How>
</Explain>

```bash
cat > backup.sh <<'EOF'
#!/usr/bin/env bash
# backup.sh <source-dir> [dest-dir] [keep-days]
set -euo pipefail

src="${1:?usage: backup.sh <source-dir> [dest-dir] [keep-days]}"
dest="${2:-./backups}"
keep="${3:-7}"
log() { echo "[backup] $*"; }
die() { echo "[backup] ERROR: $*" >&2; exit 1; }

[[ -d $src ]] || die "source $src does not exist"
[[ $keep =~ ^[0-9]+$ ]] || die "keep-days must be a number"
mkdir -p "$dest"

name="$(basename "$src")-$(date +%F_%H%M%S).tar.gz"
tmp="$(mktemp "$dest/.partial.XXXXXX")"
trap 'rm -f "$tmp"' EXIT

log "archiving $src"
tar -czf "$tmp" -C "$(dirname "$src")" "$(basename "$src")"
tar -tzf "$tmp" > /dev/null || die "verification failed"
mv "$tmp" "$dest/$name"
log "saved $name ($(du -h "$dest/$name" | cut -f1))"

deleted=$(find "$dest" -name "$(basename "$src")-*.tar.gz" -mtime +"$keep" -print -delete | wc -l)
log "removed $deleted backup(s) older than $keep days"
EOF
chmod +x backup.sh

./backup.sh site ./backups 7 | sed -E 's/[0-9]{4}-[0-9]{2}-[0-9]{2}_[0-9]{6}/DATE/; s/\(([0-9.]+K)\)/(SIZE)/'
./backup.sh missing-folder; echo "exit: $?"
```

```text output
[backup] archiving site
[backup] saved site-DATE.tar.gz (SIZE)
[backup] removed 0 backup(s) older than 7 days
[backup] ERROR: source missing-folder does not exist
exit: 1
```

(The `sed` only replaces the date and size, which change every run.) Restoring is the reverse: `tar -xzf backups/site-….tar.gz -C /restore/here`. **Practise restoring regularly** — that is the only real proof a backup works.

### 6. Log analysis: the sample access log

<Explain>
<What>
A web server access log records one line per request: who (IP), when, what (method and path), the result (status code), size, and often the time taken.
</What>
<Why>
It is the most important file during incidents: errors, attacks, traffic spikes and slow pages all appear here.
</Why>
<When>
Incidents, daily reports, security reviews.
</When>
<Where>
`/var/log/nginx/access.log`, `/var/log/apache2/access.log`.
</Where>
<How>
Know which column holds what, then use `awk` on those columns.
</How>
</Explain>

```bash
cat > access.log <<'EOF'
203.0.113.5 - - [10/Nov/2026:10:00:01 +0000] "GET / HTTP/1.1" 200 5120 0.012
203.0.113.5 - - [10/Nov/2026:10:00:02 +0000] "GET /shop HTTP/1.1" 200 8100 0.240
198.51.100.7 - - [10/Nov/2026:10:00:03 +0000] "POST /login HTTP/1.1" 401 210 0.030
198.51.100.7 - - [10/Nov/2026:10:00:04 +0000] "POST /login HTTP/1.1" 401 210 0.031
198.51.100.7 - - [10/Nov/2026:10:00:05 +0000] "POST /login HTTP/1.1" 401 210 0.029
192.0.2.44 - - [10/Nov/2026:10:01:10 +0000] "GET /api/orders HTTP/1.1" 500 90 2.950
192.0.2.44 - - [10/Nov/2026:10:01:12 +0000] "GET /wp-login.php HTTP/1.1" 404 150 0.004
203.0.113.5 - - [10/Nov/2026:10:02:00 +0000] "GET /api/orders HTTP/1.1" 200 4300 1.820
EOF
awk '{print "IP=" $1, "path=" $7, "status=" $9, "seconds=" $11}' access.log | head -2
```

```text output
IP=203.0.113.5 path=/ status=200 seconds=0.012
IP=203.0.113.5 path=/shop status=200 seconds=0.240
```

Columns: `$1` IP, `$4` time (with `[`), `$5` time zone, `$6` method (with a quote), `$7` path, `$9` status, `$10` bytes, `$11` request time in seconds.

### 7. Counting by status code and by IP

<Explain>
<What>
Grouping lines by one column and counting how many fall into each group.
</What>
<Why>
"How many errors?" and "who is sending the most requests?" are the first two questions in any web incident.
</Why>
<When>
Traffic spikes, error spikes, suspected attacks.
</When>
<Where>
Any column-based log.
</Where>
<How>
Extract the column with `awk`, then `sort | uniq -c | sort -rn | head`.
</How>
</Explain>

```bash
echo "Requests per status code:"
awk '{print $9}' access.log | sort | uniq -c | sort -rn
echo "Top IPs:"
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -3
```

```text output
Requests per status code:
      3 401
      3 200
      1 500
      1 404
Top IPs:
      3 203.0.113.5
      3 198.51.100.7
      2 192.0.2.44
```

### 8. Finding errors, brute force and slow requests

<Explain>
<What>
Filtering with conditions on columns: status codes 500+, many 401s from one IP, request time above a limit.
</What>
<Why>
Server errors (5xx) mean something is broken; many failed logins (401) from one IP mean someone is guessing passwords; slow requests mean unhappy users.
</Why>
<When>
Daily reports, alerts, incident investigations.
</When>
<Where>
Web and API logs.
</Where>
<How>
`awk '$9 >= 500'` for server errors, count 401s per IP and keep those above a limit, `awk '$11 > 1.0'` for slow requests.
</How>
</Explain>

```bash
echo "Server errors (5xx):"
awk '$9 >= 500 {print $4, $7, $9}' access.log | tr -d '['
echo "Possible brute force (3+ failed logins):"
awk '$9 == 401 && $7 == "/login" {print $1}' access.log | sort | uniq -c | awk '$1 >= 3 {print $2, "(" $1 " attempts)"}'
echo "Slow requests (> 1 second):"
awk '$11 > 1.0 {printf "%.2fs %s\n", $11, $7}' access.log | sort -rn
echo "Scanner noise (WordPress probes on a non-WordPress site):"
grep -c 'wp-login' access.log
```

```text output
Server errors (5xx):
10/Nov/2026:10:01:10 /api/orders 500
Possible brute force (3+ failed logins):
198.51.100.7 (3 attempts)
Slow requests (> 1 second):
2.95s /api/orders
1.82s /api/orders
Scanner noise (WordPress probes on a non-WordPress site):
1
```

### 9. Health check: disk usage

<Explain>
<What>
Reading how full each filesystem is and comparing it with a threshold.
</What>
<Why>
A full disk is one of the most common causes of outages: databases stop writing, logs stop, deploys fail.
</Why>
<When>
Every few minutes from cron or a monitoring system.
</When>
<Where>
`/`, `/var`, data volumes.
</Where>
<How>
`df --output=pcent /` prints the usage percentage; strip the `%` and compare with `(( ))`.
</How>
</Explain>

```bash
check_disk() {
  local mount="$1" warn="$2" used
  used=$(df --output=pcent "$mount" | tail -1 | tr -dc '0-9')
  if (( used >= warn )); then
    echo "WARN disk $mount at ${used}% (limit ${warn}%)"; return 1
  fi
  echo "OK   disk $mount below ${warn}%"
}
check_disk / 100
if ! result=$(check_disk / 0); then
  echo "$result" | sed "s/at [0-9]*%/at XX%/"
  echo "(that warning was forced with a 0% limit, to show the failure path)"
fi
```

```text output
OK   disk / below 100%
WARN disk / at XX% (limit 0%)
(that warning was forced with a 0% limit, to show the failure path)
```

Your real percentage appears instead of `XX`.

### 10. Health check: memory, services and websites

<Explain>
<What>
Checking available memory, whether important services are running, and whether a website answers with HTTP 200.
</What>
<Why>
Each covers a different way a server can be "up" but broken.
</Why>
<When>
In the same health check run.
</When>
<Where>
Any web or API server.
</Where>
<How>
Memory: `free -m` (column "available"). Service: `systemctl is-active --quiet nginx`. Website: `curl -fsS -o /dev/null -w '%{http_code}' --max-time 5 URL`.
</How>
</Explain>

```bash
check_url() {
  local url="$1" code
  code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 "$url" || true)
  if [[ $code == 200 ]]; then echo "OK   $url (HTTP $code)"; else echo "FAIL $url (HTTP $code)"; return 1; fi
}

python3 -m http.server 8765 --bind 127.0.0.1 > /dev/null 2>&1 &
server=$!
sleep 1
check_url http://127.0.0.1:8765/
check_url http://127.0.0.1:8765/no-such-page || true
kill "$server"

avail=$(free -m | awk '/^Mem:/ {print $7}')
(( avail > 0 )) && echo "OK   memory: some MB available"
```

```text output
OK   http://127.0.0.1:8765/ (HTTP 200)
FAIL http://127.0.0.1:8765/no-such-page (HTTP 404)
OK   memory: some MB available
```

`python3 -m http.server` starts a tiny local web server just for this example. On a real server you check your real site and services, for example `systemctl is-active --quiet nginx || echo "FAIL nginx"`.

### 11. The complete health check script

<Explain>
<What>
One script that runs every check, prints a summary, and exits non-zero if **any** check failed.
</What>
<Why>
Monitoring systems and cron emails react to the exit code. One clear summary line per check is easy to read on a phone at 3 a.m.
</Why>
<When>
Every 5 minutes from cron, or as a monitoring "check command".
</When>
<Where>
Every server.
</Where>
<How>
Count failures, run all checks even if one fails, exit with 1 if the count is above 0.
</How>
</Explain>

```bash
cat > healthcheck.sh <<'EOF'
#!/usr/bin/env bash
set -uo pipefail          # no -e: we want every check to run
DISK_LIMIT="${DISK_LIMIT:-90}"
MEM_MIN_MB="${MEM_MIN_MB:-200}"
failures=0
ok()   { echo "OK   $*"; }
fail() { echo "FAIL $*"; ((failures++)); }

used=$(df --output=pcent / | tail -1 | tr -dc '0-9')
(( used < DISK_LIMIT )) && ok "disk below ${DISK_LIMIT}%" || fail "disk / at ${used}%"

avail=$(free -m | awk '/^Mem:/ {print $7}')
(( avail >= MEM_MIN_MB )) && ok "memory available >= ${MEM_MIN_MB} MB" || fail "only ${avail} MB memory available"

for svc in ${SERVICES:-}; do
  systemctl is-active --quiet "$svc" && ok "service $svc" || fail "service $svc is not running"
done

echo "---"
if (( failures > 0 )); then echo "$failures check(s) failed"; exit 1; fi
echo "all checks passed"
EOF
chmod +x healthcheck.sh
MEM_MIN_MB=1 ./healthcheck.sh; echo "exit: $?"
DISK_LIMIT=1 MEM_MIN_MB=1 ./healthcheck.sh | grep -E "FAIL|failed" | sed 's/at [0-9]*%/at XX%/'; echo "exit: ${PIPESTATUS[0]}"
```

```text output
OK   disk below 90%
OK   memory available >= 1 MB
---
all checks passed
exit: 0
FAIL disk / at XX%
1 check(s) failed
exit: 1
```

Settings come from environment variables with defaults, so the same script works on every server: `SERVICES="nginx postgresql" DISK_LIMIT=85 ./healthcheck.sh`.

### 12. Scheduling with cron

<Explain>
<What>
cron runs commands automatically at fixed times. Each line in a **crontab** is a schedule plus a command.
</What>
<Why>
Backups and checks are useless if someone has to remember to run them.
</Why>
<When>
Any recurring job.
</When>
<Where>
`crontab -e` for your user; `/etc/cron.d/` for system jobs.
</Where>
<How>
Five time fields — minute, hour, day of month, month, day of week — then the command. Use **absolute paths** and **redirect output to a log**, because cron has a minimal environment and no screen.
</How>
</Explain>

```text
# ┌ minute (0-59)
# │ ┌ hour (0-23)
# │ │ ┌ day of month (1-31)
# │ │ │ ┌ month (1-12)
# │ │ │ │ ┌ day of week (0-6, Sunday = 0)
# │ │ │ │ │
  0 2 * * *   /usr/local/bin/backup.sh /var/www/shop /mnt/backups 14 >> /var/log/backup.log 2>&1
*/5 * * * *   SERVICES="nginx" /usr/local/bin/healthcheck.sh >> /var/log/health.log 2>&1
  0 7 * * 1   /usr/local/bin/analyze-log.sh /var/log/nginx/access.log | mail -s "Weekly web report" ops@example.com
```

- Line 1: every day at 02:00, back up the shop, keep 14 days.
- Line 2: every 5 minutes, health check.
- Line 3: every Monday at 07:00, email a log report.

Use a tool like crontab.guru to double-check a schedule. Many modern systems use **systemd timers** instead of cron; the idea is the same.

## Hands-on

Build the log analyser as a reusable script:

```bash
mkdir -p ~/practical-lab && cd ~/practical-lab
printf '%s\n' \
  '10.0.0.1 - - [10/Nov/2026:09:00:00 +0000] "GET / HTTP/1.1" 200 100 0.01' \
  '10.0.0.2 - - [10/Nov/2026:09:00:01 +0000] "GET /api HTTP/1.1" 500 10 3.20' \
  '10.0.0.2 - - [10/Nov/2026:09:00:02 +0000] "POST /login HTTP/1.1" 401 10 0.02' \
  '10.0.0.2 - - [10/Nov/2026:09:00:03 +0000] "POST /login HTTP/1.1" 401 10 0.02' \
  '10.0.0.1 - - [10/Nov/2026:09:00:04 +0000] "GET /about HTTP/1.1" 200 100 0.05' > access.log

cat > analyze-log.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
log="${1:?usage: analyze-log.sh <access.log>}"
[[ -r $log ]] || { echo "cannot read $log" >&2; exit 1; }
total=$(wc -l < "$log")
errors=$(awk '$9 >= 500' "$log" | wc -l)
echo "Report for $(basename "$log")"
echo "  requests:      $total"
echo "  server errors: $errors ($(( errors * 100 / total ))%)"
echo "  top IP:        $(awk '{print $1}' "$log" | sort | uniq -c | sort -rn | head -1 | awk '{print $2 " (" $1 " requests)"}')"
echo "  slowest:       $(sort -k11 -rn "$log" | head -1 | awk '{print $7 " in " $11 "s"}')"
echo "  failed logins: $(awk '$9 == 401' "$log" | wc -l)"
EOF
chmod +x analyze-log.sh
./analyze-log.sh access.log

cd ~ && rm -rf ~/practical-lab
```

```text output
Report for access.log
  requests:      5
  server errors: 1 (20%)
  top IP:        10.0.0.2 (3 requests)
  slowest:       /api in 3.20s
  failed logins: 2
```

## Real-world example

The **3-2-1 backup rule**, implemented with the script from this lesson:

- **3** copies of the data (the original + 2 backups),
- on **2** different kinds of storage (local disk + object storage),
- **1** copy off-site (another region or provider).

```bash
#!/usr/bin/env bash
# nightly-backup.sh — run by cron at 02:00
set -euo pipefail

/usr/local/bin/backup.sh /var/www/shop /mnt/backups 7          # copy 2: local disk, 7 days

latest=$(ls -1t /mnt/backups/shop-*.tar.gz | head -1)
sha256sum "$latest" > "$latest.sha256"

aws s3 cp "$latest"        "s3://acme-backups/shop/" --storage-class STANDARD_IA   # copy 3: off-site
aws s3 cp "$latest.sha256" "s3://acme-backups/shop/"

/usr/local/bin/healthcheck.sh > /dev/null || echo "health check failed after backup" >&2
echo "nightly backup done: $(basename "$latest")"
```

Add an S3 **lifecycle rule** to delete off-site copies after 30 days, and enable **object lock / versioning** so ransomware on the server cannot delete the off-site backups.

## Common mistakes

- **Never testing restores** — a backup is only proven when you have restored it.
- **Backups on the same disk** as the data — one disk failure loses both.
- **Retention before verification** — deleting old good backups after creating a broken new one.
- **Relative paths and no logs in cron jobs** — they fail silently.
- **Health checks that exit 0 on failure** — monitoring never alerts.
- **Parsing logs with fixed column numbers** without checking the format — log formats differ between servers and change after config updates.
- **Backing up a live database by copying its files** — use the database's dump tool (`pg_dump`, `mysqldump`) instead.

## Security lens

<Callout type="security">
Backups and logs contain your most sensitive data. Protect them as carefully as the production system.
</Callout>

- **Encrypt backups** that leave the server (`gpg --symmetric`, or server-side encryption in S3) and restrict permissions (`chmod 600`, `umask 077`).
- **Immutable / off-site copies** (S3 Object Lock, versioning) protect against ransomware that deletes local backups.
- **Logs are evidence:** ship them to a central system (ELK, Loki, CloudWatch, a SIEM) so an attacker on the server cannot erase them.
- **Log analysis is detection:** many 401s from one IP (brute force), requests for `/wp-login.php`, `/.env` or `/.git/config` (scanners), and sudden 5xx spikes are classic signals. Turn them into alerts.
- **Do not log secrets:** tokens in URLs and query strings end up in access logs.

## Interview questions

<QA q="How would you design a backup script for a web server?">
Use strict mode, validate the source and destination, create a timestamped tar.gz archive into a temporary file, verify it with tar -t and store a checksum, then move it into place. Delete old backups with find -mtime only after the new one is verified, log every step, run it from cron with output redirected to a log, keep an off-site copy, and regularly test restores.
</QA>

<QA q="How do you find the top 10 IP addresses in an nginx access log?">
`awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10`. awk extracts the first column, sort groups identical IPs, uniq -c counts them, sort -rn orders by count descending and head keeps the first ten.
</QA>

<QA q="What should a server health check script do and how should it report failures?">
It should check key resources and services, such as disk usage, available memory, required services and HTTP endpoints, against configurable thresholds. It should run every check even if one fails, print a clear line per check, and exit with a non-zero status if any check failed, so cron, CI or a monitoring system can alert on it.
</QA>

<QA q="What is the 3-2-1 backup rule?">
Keep three copies of data, on two different types of storage, with one copy off-site. It protects against single-disk failure, site-wide incidents and ransomware, especially when the off-site copy is immutable or versioned.
</QA>
