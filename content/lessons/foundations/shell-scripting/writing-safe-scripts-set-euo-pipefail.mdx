<BigIdea>
<Tr>
<En>
By default Bash **keeps going** after an error. Put `set -euo pipefail` right after the shebang and it stops at the first problem instead. **`-e`** stops when a command fails, **`-u`** stops when you use a variable that was never set (usually a typo), and **`-o pipefail`** makes a pipeline fail if **any** part fails. Silent, dangerous failures become loud, early stops.
</En>
<Ur>
Bash pehle se error ke baad bhi **chalta rehta hai**. Shebang ke foran baad `set -euo pipefail` lagayen to ye pehle masle par ruk jata hai. **`-e`** command fail hone par rokta hai, **`-u`** aisa variable istemal karne par rokta hai jo kabhi set nahi hua (aksar typo), aur **`-o pipefail`** pipeline ko fail karta hai agar **koi bhi** hissa fail ho. Khamosh, khatarnak nakamiyan buland aur jaldi rukawat ban jati hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

`set -euo pipefail` is one line that switches on three safety options, often called **Bash strict mode**. It changes Bash from "ignore problems and continue" to "stop at the first problem". On top of it, safe scripts follow a few habits: quote variables, check inputs, use safe temporary files, and guard destructive commands.

</En>
<Ur>

`set -euo pipefail` ek line hai jo teen hifazati options on karti hai, jise aksar **Bash strict mode** kehte hain. Ye Bash ko "masle nazar andaz karo aur chalte raho" se "pehle masle par ruko" bana deti hai. Is ke ooper mehfooz scripts chand aadaten rakhte hain: variables par quotes, inputs check, mehfooz temporary files, aur tabahkun commands ki hifazat.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Look at this innocent cleanup script:

```text
cd /var/www/app/cache
rm -rf *
```

If the folder doesn't exist (typo, wrong server, not mounted), `cd` fails, and Bash happily runs `rm -rf *` in **whatever folder it's in**. Real outages and wiped servers started exactly like this. Strict mode also gives **honest exit codes** for CI and cron, and stops at the actually broken line.

</En>
<Ur>

Ye masoom sa cleanup script dekhein:

```text
cd /var/www/app/cache
rm -rf *
```

Agar folder mojood na ho (typo, ghalat server, mount nahi), to `cd` fail hota hai, aur Bash khushi se `rm -rf *` **jis folder me bhi ho** wahan chala deta hai. Asli outages aur saaf hue servers bilkul aise shuru hue. Strict mode CI aur cron ke liye **sachche exit codes** bhi deta hai, aur asal tooti line par rukta hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

**In every script**: repository scripts, CI steps, Docker entrypoints, cron jobs, setup scripts. The one exception is your **interactive terminal**: don't put `set -e` in `~/.bashrc`, or one failed command closes your terminal.

</En>
<Ur>

**Har script me**: repository scripts, CI steps, Docker entrypoints, cron jobs, setup scripts. Sirf ek istisna aap ka **interactive terminal** hai: `~/.bashrc` me `set -e` na daalein, warna ek fail command terminal band kar degi.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
#!/usr/bin/env bash
set -euo pipefail
```

Line 2 of every script. Check what's on with `echo $-` or `set -o`.

</En>
<Ur>

```text
#!/usr/bin/env bash
set -euo pipefail
```

Har script ki line 2. Kya on hai ye `echo $-` ya `set -o` se dekhein.

</Ur>
</Tr>
</How>
</Glance>

</En>
<Ur>

**Bina brakes aur warning lights wali gaari** kuch bhi ho chalti rehti hai: punctured tyre, tel khatam, ghalat sarak. `set -euo pipefail` **brakes** (error par ruko), **fuel light** (kuch ghayab ho to ruko), aur andar chhupe maslon (pipelines) ke liye **check-engine light** lagata hai.

## Learn it step by step

<Walkthrough>

<Step title="set -e: stop when a command fails">

<Tr>
<En>

With `-e`, Bash exits **immediately** when a command returns non-zero, so later steps never run on top of a failed step. The script ends with the failing command's code.

</En>
<Ur>

`-e` ke saath Bash **foran** nikal jata hai jab command non-zero de, isliye baad ke steps fail step ke ooper kabhi nahi chalte. Script fail command ke code par khatam hota hai.

</Ur>
</Tr>

```bash
cat > without-e.sh <<'EOF'
cd /no/such/folder 2> /dev/null
echo "Still running in: $PWD — a following rm would hit the WRONG folder"
EOF
cat > with-e.sh <<'EOF'
set -e
cd /no/such/folder 2> /dev/null
echo "This line never runs"
EOF
bash without-e.sh | sed "s|$PWD|<current folder>|"; echo "exit: ${PIPESTATUS[0]}"
bash with-e.sh; echo "exit: $?"
```

```text output
Still running in: <current folder> — a following rm would hit the WRONG folder
exit: 0
exit: 1
```

<Happened>
<Tr>
<En>Without `-e`, the failed `cd` was ignored, the script kept going in the wrong folder, and even reported success (0). With `-e`, it stopped at the `cd` and exited 1.</En>
<Ur>`-e` ke baghair fail `cd` nazar andaz hua, script ghalat folder me chalta raha, aur kamyabi (0) bhi batayi. `-e` ke saath ye `cd` par ruka aur 1 par nikla.</Ur>
</Tr>
</Happened>

</Step>

<Step title="set -u: stop on unset variables">

<Tr>
<En>

A typo like `$bakup_dir` instead of `$backup_dir` normally becomes **empty text silently**, and `rm -rf "$bakup_dir/"*` becomes `rm -rf /*`. With `-u`, using an unset variable stops the script.

For variables that are **allowed** to be missing, give a default: `${VAR:-}` (empty) or `${VAR:-default}`. Arguments too: `${1:-}`.

</En>
<Ur>

`$backup_dir` ki jagah `$bakup_dir` jaisi typo aam tor par **khamoshi se khaali text** ban jati hai, aur `rm -rf "$bakup_dir/"*` `rm -rf /*` ban jata hai. `-u` ke saath unset variable istemal karna script rok deta hai.

Jin variables ka ghayab hona **jaiz** ho unhe default dein: `${VAR:-}` (khaali) ya `${VAR:-default}`. Arguments bhi: `${1:-}`.

</Ur>
</Tr>

```bash
cat > typo.sh <<'EOF'
set -u
backup_dir="/tmp/backups"
echo "Cleaning: $bakup_dir/*"
EOF
bash typo.sh 2>&1 | sed 's/.*: line/line/'

cat > optional.sh <<'EOF'
set -u
echo "Region: ${AWS_REGION:-us-east-1}"
echo "First argument: [${1:-}]"
EOF
bash optional.sh
```

```text output
line 3: bakup_dir: unbound variable
Region: us-east-1
First argument: []
```

<Happened>
<Tr>
<En>`-u` caught the typo **before** anything was deleted. In the second script, the defaults let optional values be missing on purpose.</En>
<Ur>`-u` ne kuch mitne se **pehle** typo pakar li. Doosre script me defaults ne ikhtiyari values ko jaan boojh kar ghayab hone diya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="set -o pipefail: catch failures inside pipelines">

<Tr>
<En>

`-e` only sees a pipeline's **final** code. Without pipefail, `failing-command | gzip > file` looks successful because `gzip` worked. With pipefail, the pipeline's code is that of the last part that **failed**.

</En>
<Ur>

`-e` pipeline ka sirf **aakhri** code dekhta hai. pipefail ke baghair `failing-command | gzip > file` kamyab lagta hai kyun ke `gzip` chal gaya. pipefail ke saath pipeline ka code us aakhri hisse ka hota hai jo **fail** hua.

</Ur>
</Tr>

```bash
cat > dump.sh <<'EOF'
set -e
fake_dump() { echo "partial data"; return 1; }
fake_dump | gzip > backup.gz
echo "Backup reported as successful!"
EOF
cat > dump-safe.sh <<'EOF'
set -eo pipefail
fake_dump() { echo "partial data"; return 1; }
fake_dump | gzip > backup.gz
echo "never printed"
EOF
bash dump.sh; echo "exit: $?"
bash dump-safe.sh; echo "exit: $?"
```

```text output
Backup reported as successful!
exit: 0
exit: 1
```

</Step>

<Step title="When set -e does NOT stop the script">

<Tr>
<En>

By design, `-e` ignores failures it thinks you're **already handling**:

| Situation | Does `-e` stop? | Why |
| --- | --- | --- |
| `if cmd; then` | No | You're already checking it |
| `cmd \|\| echo "failed"` | No | Failure is handled |
| `cmd1 && cmd2` (cmd1 fails) | No | The list handles it |
| `! cmd` | No | You asked to invert it |
| `local var=$(cmd)` | **No** | `local` succeeds and hides cmd's code |
| A function called inside `if` | No (in the whole function!) | `-e` is switched off there |

Rule: **declare and assign separately** (`local x; x=$(cmd)`). For critical steps, check explicitly with `|| die "…"`.

</En>
<Ur>

Jaan boojh kar `-e` un nakamiyon ko nazar andaz karta hai jinhe wo samajhta hai aap **pehle se sambhal rahe** hain:

| Soorat | Kya `-e` rokta hai? | Kyun |
| --- | --- | --- |
| `if cmd; then` | Nahi | Aap pehle se check kar rahe hain |
| `cmd \|\| echo "failed"` | Nahi | Nakami sambhal li gayi |
| `cmd1 && cmd2` (cmd1 fail) | Nahi | List sambhalti hai |
| `! cmd` | Nahi | Aap ne ulta karne ko kaha |
| `local var=$(cmd)` | **Nahi** | `local` kamyab hota hai aur cmd ka code chhupa deta hai |
| `if` ke andar bulaya function | Nahi (poore function me!) | Wahan `-e` band hota hai |

Usool: **declare aur assign alag karein** (`local x; x=$(cmd)`). Ahem steps ko `|| die "…"` se khud check karein.

</Ur>
</Tr>

```bash
cat > surprise.sh <<'EOF'
set -euo pipefail
get_value() { echo "value"; false; }   # prints a value, then fails

check() {
  local result=$(get_value)
  echo "local hid the failure, result=[$result]"
}
check

check2() {
  local result
  result=$(get_value)
  echo "never printed"
}
check2
EOF
bash surprise.sh; echo "exit: $?"
```

```text output
local hid the failure, result=[value]
exit: 1
```

<Happened>
<Tr>
<En>In `check`, `local result=$(…)` succeeded as a whole, so the failure was **hidden** and the script carried on. In `check2`, the assignment was on its own line, so `-e` saw the failure and stopped.</En>
<Ur>`check` me `local result=$(…)` poora kamyab hua, isliye nakami **chhup** gayi aur script chalta raha. `check2` me assignment alag line par tha, isliye `-e` ne nakami dekhi aur roka.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Allow expected failures">

<Tr>
<En>

Some commands "fail" in normal situations: `grep` finds nothing, `diff` finds differences. Tell strict mode it's fine:

- `count=$(grep -c x file || true)` accepts the failure.
- `if grep -q …; then` handles it.
- Use `rm -f` and `mkdir -p`, which don't fail when there's nothing to do.

</En>
<Ur>

Kuch commands aam halaat me "fail" hoti hain: `grep` ko kuch nahi milta, `diff` ko farq milta hai. Strict mode ko batayen ke theek hai:

- `count=$(grep -c x file || true)` nakami qabool karta hai.
- `if grep -q …; then` use sambhalta hai.
- `rm -f` aur `mkdir -p` istemal karein, jo karne ko kuch na ho to fail nahi hote.

</Ur>
</Tr>

```bash
cat > expected.sh <<'EOF'
set -euo pipefail
printf 'INFO ok\nINFO ok\n' > app.log
errors=$(grep -c ERROR app.log || true)
echo "Errors found: $errors"
rm -f does-not-exist.tmp
mkdir -p cache cache
echo "Script finished normally"
EOF
bash expected.sh; echo "exit: $?"
```

```text output
Errors found: 0
Script finished normally
exit: 0
```

<Happened>
<Tr>
<En>Without `|| true`, `grep -c` finding 0 matches returns code 1 and `-e` would stop the script.</En>
<Ur>`|| true` ke baghair 0 matches par `grep -c` code 1 deta aur `-e` script rok deta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Safe temporary files with mktemp">

<Tr>
<En>

Fixed names like `/tmp/backup.tmp` clash between two runs, and other users can predict and abuse them. `mktemp` makes a file (or folder with `-d`) with a **random** name that only you can read. Delete it at the end; the next lesson does that automatically with `trap`.

</En>
<Ur>

`/tmp/backup.tmp` jaise pakke naam do runs me takra jate hain, aur doosre users unka andaza laga kar ghalat istemal kar sakte hain. `mktemp` **ittefaqi** naam ki file (ya `-d` se folder) banata hai jo sirf aap parh sakte hain. Aakhir me mita dein; agla sabaq ye `trap` se khud karta hai.

</Ur>
</Tr>

```bash
tmp=$(mktemp)
echo "Temporary file: ${tmp%.*}.XXXXXXXXXX (random name)"
ls -l "$tmp" | cut -c1-10
rm -f "$tmp"
```

```text output
Temporary file: /tmp/tmp.XXXXXXXXXX (random name)
-rw-------
```

<Happened>
<Tr>
<En>`-rw-------` means only the owner can read or write it. (We masked the random part of the name so the output is the same every time.)</En>
<Ur>`-rw-------` ka matlab sirf malik parh ya likh sakta hai. (Hum ne naam ka ittefaqi hissa chhupaya taa ke output har dafa ek jaisa ho.)</Ur>
</Tr>
</Happened>

</Step>

<Step title="Guard dangerous commands">

<Tr>
<En>

`rm -rf`, `chmod -R` and `chown -R` are fast and **can't be undone**. One empty variable is enough. Guard them:

- `${var:?message}` stops the script if `var` is empty.
- Quote everything.
- `--` makes sure a name starting with `-` is never read as an option.

</En>
<Ur>

`rm -rf`, `chmod -R` aur `chown -R` tez hain aur **wapas nahi ho sakte**. Ek khaali variable kaafi hai. Inki hifazat karein:

- `${var:?message}` script rokta hai agar `var` khaali ho.
- Har cheez par quotes.
- `--` yaqeeni banata hai ke `-` se shuru hone wala naam kabhi option na samjha jaye.

</Ur>
</Tr>

```bash
cat > clean.sh <<'EOF'
set -euo pipefail
target="${1:-}"
rm -rf -- "${target:?target folder is required}/cache"
EOF
bash clean.sh 2>&1 | sed 's/.*: //'; echo "exit: ${PIPESTATUS[0]}"
mkdir -p mysite/cache && touch mysite/cache/x
bash clean.sh mysite && echo "cleaned: $(ls mysite | wc -l) items left in mysite"
```

```text output
target folder is required
exit: 1
cleaned: 0 items left in mysite
```

<Happened>
<Tr>
<En>With no argument, `${target:?…}` stopped the script **before** `rm` ran, so `rm -rf /cache` could never happen. With `mysite`, it removed only `mysite/cache`.</En>
<Ur>Argument ke baghair `${target:?…}` ne `rm` chalne se **pehle** script roka, isliye `rm -rf /cache` kabhi nahi ho sakta tha. `mysite` ke saath sirf `mysite/cache` mita.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Check that required tools exist">

<Tr>
<En>

Failing at step 1 with "jq is not installed" is far better than failing at step 7, halfway through a deployment. Check every tool at the start with `command -v`.

</En>
<Ur>

Step 1 par "jq is not installed" ke saath fail hona deployment ke beech step 7 par fail hone se kahin behtar hai. Shuru me har tool `command -v` se check karein.

</Ur>
</Tr>

```bash
require() {
  local missing=0
  for tool in "$@"; do
    command -v "$tool" > /dev/null || { echo "missing tool: $tool" >&2; missing=1; }
  done
  return "$missing"
}
require bash grep awk && echo "all tools present"
require bash definitely-not-installed 2>&1 || echo "cannot continue"
```

```text output
all tools present
missing tool: definitely-not-installed
cannot continue
```

</Step>

<Step title="A safe script template">

<Tr>
<En>

Start every new script from a skeleton that's safe by default: strict mode, helpers, argument and tool checks, and a `main`. Keep it as a snippet in your editor.

Some people also add `IFS=$'\n\t'` to stop word splitting at spaces. It reduces quoting bugs but changes how unquoted variables behave; quoting correctly is the more important habit.

</En>
<Ur>

Har naya script aise dhaanche se shuru karein jo pehle se mehfooz ho: strict mode, helpers, argument aur tool checks, aur `main`. Ise editor me snippet bana kar rakhein.

Kuch log `IFS=$'\n\t'` bhi lagate hain taa ke spaces par alfaz na tooten. Ye quoting bugs kam karta hai lekin bina quotes variables ka rawaiya badal deta hai; sahi quotes lagana zyada ahem aadat hai.

</Ur>
</Tr>

```bash
#!/usr/bin/env bash
# name.sh — one line saying what this script does
# Usage: name.sh <argument>
set -euo pipefail

log() { printf '[%s] %s\n' "$(date +%T)" "$*" >&2; }
die() { log "ERROR: $*"; exit 1; }

require() { for t in "$@"; do command -v "$t" > /dev/null || die "missing tool: $t"; done; }

main() {
  local arg="${1:?usage: $(basename "$0") <argument>}"
  require curl
  log "starting with $arg"
  # … real work here …
  log "done"
}

main "$@"
```

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="local hides the failure">

```text
local data=$(curl -fsS "$url")    # curl fails, script keeps going
```

</Bad>
<Good title="Split declare and assign">

```text
local data
data=$(curl -fsS "$url")          # -e now stops on failure
```

</Good>
</Compare>

<Compare>
<Bad title="|| true everywhere">

```text
cp config.yml /etc/app/ || true    # "make the error go away"
```

</Bad>
<Good title="Allow only expected failures">

```text
cp config.yml /etc/app/            # must work, so let -e stop us
n=$(grep -c ERROR app.log || true) # 0 matches is a normal result
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **No strict mode at all**: the most common and most expensive mistake.
- **`set -e` in `~/.bashrc`**: your terminal closes on the first failed command.
- **Relying only on `-e` for critical steps**: it's switched off inside `if` conditions and functions called from them.
- **Unquoted variables**: strict mode doesn't protect against word splitting.
- **Fixed temp file names in `/tmp`**: use `mktemp`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Strict mode bilkul na hona**: sab se aam aur sab se mehngi ghalti.
- **`~/.bashrc` me `set -e`**: pehli fail command par terminal band.
- **Ahem steps ke liye sirf `-e` par bharosa**: ye `if` shart aur un se bulaye functions me band hota hai.
- **Bina quotes variables**: strict mode alfaz tootne se nahi bachata.
- **`/tmp` me pakke temp naam**: `mktemp` istemal karein.

</Ur>
</Tr>

<Challenge title="Safety lab">

<Tr>
<En>
Five quick experiments: `-e` stopping, `-u` catching a typo, pipefail off vs on, an expected failure, and a guarded `rm`.
</En>
<Ur>
Paanch jaldi tajurbe: `-e` ka rokna, `-u` ka typo pakarna, pipefail off bamuqabla on, mutawaqqa nakami, aur hifazat wala `rm`.

```bash
mkdir -p ~/safe-lab && cd ~/safe-lab

# 1. -e stops at the first failure
bash -c 'set -e; echo one; false; echo two'; echo "exit: $?"

# 2. -u catches typos
bash -c 'set -u; name=Sam; echo "$nmae"' 2>&1 | sed 's/.*line [0-9]*: //'

bash -c 'set -euo pipefail; n=$(grep -c x /dev/null || true); echo "matches: $n"'

```

```text output
exit: 1
nmae: unbound variable
no pipefail: continued
with pipefail exit: 1

empty!
```

<Challenge title="Refuse dangerous targets">

<Tr>
<En>
Write a cleanup guard that refuses to run when the target is empty, `/`, or your home folder.
</En>
<Ur>

<Solution>
<Tr>
<En>

```text
target="${1:?usage: clean.sh <folder>}"

  /|"$HOME") echo "refusing to clean '$target'" >&2; exit 1 ;;
esac
rm -rf -- "$target"/cache
```

`realpath -m` turns `~/../..` style paths into their real form before checking.

</En>
<Ur>

```text
target="${1:?usage: clean.sh <folder>}"
case "$(realpath -m -- "$target")" in
  /|"$HOME") echo "refusing to clean '$target'" >&2; exit 1 ;;
esac

```

`realpath -m` `~/../..` jaise paths ko check se pehle un ki asli shakal me badalta hai.

<DeepDive title="Real world: the empty-variable uninstall bug">

A popular open-source project once shipped an uninstall script containing something like:

```bash
rm -rf "$STEAMROOT/"*
```

When `STEAMROOT` came out **empty** in some situations, this became `rm -rf "/"*` and deleted users' entire home folders and mounted drives. Strict mode plus one guard would have prevented it:

```bash
#!/usr/bin/env bash
set -euo pipefail

STEAMROOT="$(cd "${0%/*}" && pwd)"            # fails loudly if cd fails
[[ -n $STEAMROOT && $STEAMROOT != / ]] || { echo "refusing to delete '$STEAMROOT'" >&2; exit 1; }
rm -rf -- "${STEAMROOT:?}/"*
```

- `set -e` stops if the `cd` fails.
- The explicit check refuses empty or `/` paths.
- `${STEAMROOT:?}` is a last line of defence.

</DeepDive>

<DeepDive title="Security lens">

Most "Bash disasters" aren't attacks: they're scripts doing exactly what they were told after something unexpected happened. Strict mode is your first security control.

- **Fail closed:** a security step that fails (checksum, firewall rule, permission fix) must stop the script.
- **`mktemp` + restrictive permissions** stop other users reading or replacing your temporary files (classic `/tmp` race and symlink attacks).
- **`umask 077`** at the top of scripts that create sensitive files makes new files private by default.
- **Never `curl … | bash` blindly** in your own automation: download, verify the checksum or signature, then run.
- **Guard destructive paths** with `${var:?}`, explicit allow-lists and `--` before user-supplied paths.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does set -euo pipefail do?">
-e exits the script when a command fails, -u treats use of unset variables as an error and exits, and -o pipefail makes a pipeline return the status of the last failing command instead of only the last command. Together they make scripts stop at the first error instead of continuing in a broken state.
</QA>

<QA q="When does set -e not stop a script?">
It does not trigger for commands tested in if, while or until conditions, commands in a && or || list except the last, commands negated with !, and inside functions called from such conditions. It is also defeated by local var=$(cmd), because the exit status of local hides the status of cmd.
</QA>

<QA q="How do you allow a command to fail under set -e?">
Handle the failure explicitly: use the command as an if condition, append || true when failure is acceptable, or capture the status with cmd || status=$?. Prefer commands that are idempotent, such as rm -f and mkdir -p.
</QA>

<QA q="Why should temporary files be created with mktemp?">
mktemp creates a file with an unpredictable name and owner-only permissions, avoiding name clashes between concurrent runs and preventing other users from pre-creating or symlinking a predictable path in /tmp to read or overwrite data.
</QA>

</DeepDive>
