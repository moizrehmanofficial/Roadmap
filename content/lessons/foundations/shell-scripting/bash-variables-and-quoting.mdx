<Callout type="tip" title="In one minute">
A Bash **variable** is a name that stores text: `name="Alex"` (no spaces around `=`). Read it with a dollar sign: `echo "$name"`. **Double quotes** `"…"` keep the text together but still replace `$variables`; **single quotes** `'…'` keep everything exactly as written. Always write `"$variable"` (in double quotes) — unquoted variables get split at spaces and wildcards get expanded, which causes most Bash bugs. `export NAME=value` makes a variable visible to programs the script starts.
</Callout>

## Start from zero

### What is a variable in Bash?

<Callout type="analogy">
A **sticky note with a name on top**. You write "`server`" at the top and "`web-1.example.com`" underneath. Whenever a command needs the server's address, you point at the note instead of writing the address again. If the server changes, you rewrite one note, and every command that uses it gets the new value.
</Callout>

Without variables, a backup script might write `/var/www/myapp` in ten places. When the folder moves, you must find and change all ten — and you will miss one. With `app_dir="/var/www/myapp"` at the top, you change **one line**.

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Variable** | A name that holds a value | `name` |
| **Value** | The text stored in it (in Bash, everything is text) | `"Alex"` |
| **Assignment** | Storing a value in a variable | `name="Alex"` |
| **Expansion** | Bash replacing `$name` with its value before running the command | `echo $name` → `echo Alex` |
| **Quotes** | `"…"` or `'…'` around text, controlling what Bash changes inside | `"Hello $name"` |
| **Word splitting** | Bash cutting unquoted text into separate words at spaces | `my file` → `my` + `file` |
| **Glob** | A wildcard like `*` that Bash turns into matching file names | `*.txt` |
| **Environment variable** | A variable passed on to programs you start | `PATH`, `HOME` |

## What is it?

A Bash variable is a **named piece of text** stored in the running shell. You create it with `name=value` and use it by writing `$name` (or `${name}`). Before running any command line, Bash first **expands** every `$name` into its value. **Quoting** controls how that expansion behaves — whether the result stays one piece, gets split into words, or is left exactly as typed.

## Why does it matter?

- **Reusable, changeable scripts:** folder paths, server names, versions and limits live in one place.
- **Most Bash bugs are quoting bugs:** a filename with a space, an empty variable, or a `*` in a value can make a script delete the wrong files.
- **Configuration:** Docker, CI pipelines and cloud servers pass settings to programs through environment variables (`DATABASE_URL`, `AWS_REGION`, `NODE_ENV`).
- **Security:** unquoted variables are a classic source of command injection.

## When and where do you use it?

| Situation | Example |
| --- | --- |
| A value used more than once | `backup_dir="/mnt/backups"` |
| A value that changes between runs | `env="$1"` (from an argument) |
| Saving a command's result | `today="$(date +%F)"` |
| Settings passed to programs | `export NODE_ENV=production` |
| Reading system information | `$HOME`, `$USER`, `$PWD`, `$PATH` |

## Concepts one by one

### 1. Creating and reading a variable

<Explain>
<What>
`name=value` stores a value; `$name` (or `${name}`) reads it.
</What>
<Why>
To store information once and reuse it.
</Why>
<When>
Any time a value is used more than once or may change.
</When>
<Where>
At the top of scripts (settings), and wherever you capture results.
</Where>
<How>
Write the name, `=`, and the value, with **no spaces**. Use quotes if the value contains spaces. Read it with `$` in front, inside double quotes: `"$name"`.
</How>
</Explain>

```bash
name="Alex"
city="Austin"
greeting="Hello $name from $city"
echo "$greeting"
echo "Name has ${#name} letters"
```

```text output
Hello Alex from Austin
Name has 4 letters
```

- `name="Alex"` — create the variable `name`.
- `"Hello $name from $city"` — inside double quotes, `$name` and `$city` are replaced by their values.
- `${#name}` — the **length** of the value (4 characters).

### 2. The no-spaces rule

<Explain>
<What>
There must be **no space** on either side of `=` when assigning.
</What>
<Why>
Bash splits command lines at spaces. `name = Alex` is read as "run a command called `name` with the arguments `=` and `Alex`".
</Why>
<When>
Every assignment.
</When>
<Where>
Scripts and the terminal.
</Where>
<How>
`name=Alex` ✓, `name = Alex` ✗, `name= Alex` ✗ (that runs `Alex` with an empty `name`).
</How>
</Explain>

```bash
name = Alex 2>&1 | sed 's/.*: //'
name="Alex"
echo "Correct: $name"
```

```text output
command not found
Correct: Alex
```

### 3. `${name}` — braces when the name touches other text

<Explain>
<What>
Curly braces mark exactly where the variable name ends.
</What>
<Why>
In `"$file_backup"`, Bash looks for a variable called `file_backup`, not `file` followed by `_backup`.
</Why>
<When>
When a letter, digit or `_` comes straight after the variable.
</When>
<Where>
Building file names: `"${name}_2026.log"`, `"${count}th"`.
</Where>
<How>
Write `${name}`. It is never wrong to use braces, so many people use them always.
</How>
</Explain>

```bash
file="report"
echo "Without braces: [$file_2026.txt]"
echo "With braces:    [${file}_2026.txt]"
```

```text output
Without braces: [.txt]
With braces:    [report_2026.txt]
```

`$file_2026` is a variable that does not exist, so it became empty.

### 4. Three kinds of quoting

<Explain>
<What>
**Double quotes** `"…"` keep text as one piece and still expand `$variables` and `$(commands)`. **Single quotes** `'…'` keep everything exactly as typed — nothing is expanded. **No quotes** let Bash split the text into words and expand wildcards.
</What>
<Why>
You need to control what Bash changes. Sometimes you want the value (`"$name"`); sometimes you need a literal dollar sign (`'$5 coffee'`).
</Why>
<When>
Every time you write text that contains spaces, `$`, `*` or other special characters.
</When>
<Where>
Echo messages, file paths, arguments to commands like `grep`, `awk`, `sed`.
</Where>
<How>
Default to double quotes around variables. Use single quotes for fixed text with special characters (awk programs, regex, passwords containing `$`). A backslash `\` protects a single character: `\$`.
</How>
</Explain>

```bash
name="Alex"
echo "Double: Hello $name, today is $(date +%Y)" | sed 's/[0-9]\{4\}/YYYY/'
echo 'Single: Hello $name, today is $(date +%Y)'
echo "Backslash: the price is \$5"
```

```text output
Double: Hello Alex, today is YYYY
Single: Hello $name, today is $(date +%Y)
Backslash: the price is $5
```

(`sed` only replaces the year with `YYYY` so the output is the same every year.)

| Quotes | `$var` expanded? | `$(cmd)` run? | Split at spaces? | `*` expanded? |
| --- | --- | --- | --- | --- |
| None: `$var` | Yes | Yes | **Yes** | **Yes** |
| Double: `"$var"` | Yes | Yes | No | No |
| Single: `'$var'` | No | No | No | No |

### 5. Why unquoted variables break: word splitting and globbing

<Explain>
<What>
When a variable is **not** in double quotes, Bash does two more things to its value: it **splits** it into separate words at spaces, and it treats `*`, `?` and `[ ]` as **wildcards** matching file names.
</What>
<Why>
This is the source of most Bash bugs. A file called `my report.txt` becomes two files, `my` and `report.txt`. A value `*` turns into every file in the folder.
</Why>
<When>
Every time you write `$var` without quotes.
</When>
<Where>
`rm $file`, `cp $src $dest`, `[ $name == admin ]`, loops.
</Where>
<How>
Always write `"$var"`. ShellCheck warns about this as `SC2086`.
</How>
</Explain>

```bash
touch "my report.txt" a.txt b.txt
file="my report.txt"
pattern="*.txt"

echo "--- unquoted \$file gives these arguments:"
printf '[%s]\n' $file
echo "--- quoted \"\$file\":"
printf '[%s]\n' "$file"
echo "--- unquoted \$pattern:"
printf '[%s]\n' $pattern
echo "--- quoted \"\$pattern\":"
printf '[%s]\n' "$pattern"
```

```text output
--- unquoted $file gives these arguments:
[my]
[report.txt]
--- quoted "$file":
[my report.txt]
--- unquoted $pattern:
[a.txt]
[b.txt]
[my report.txt]
--- quoted "$pattern":
[*.txt]
```

`printf '[%s]\n'` prints each argument it receives inside brackets, so you can see exactly how many arguments Bash created.

<Callout type="danger" title="A real disaster">
`rm -rf $dir/*` with `dir` empty (because of a typo or a failed command) becomes `rm -rf /*` — delete everything. Quote it (`"$dir"/*`), and protect it with `${dir:?}` which stops the script when `dir` is empty.
</Callout>

### 6. Empty vs unset variables, and defaults

<Explain>
<What>
An **unset** variable was never created. An **empty** variable exists but holds no text (`name=""`). Reading either gives empty text. Bash can supply a **default** in both cases.
</What>
<Why>
Optional settings need sensible defaults, and required settings need a clear error instead of silently being empty.
</Why>
<When>
Reading arguments and environment variables that may not be set.
</When>
<Where>
Config at the top of scripts: `port="${PORT:-8080}"`.
</Where>
<How>
`${var:-default}` — use default if empty/unset. `${var:=default}` — also save the default into var. `${var:?message}` — stop the script with the message if empty/unset.
</How>
</Explain>

```bash
unset port
echo "Port: ${port:-8080}"
port=3000
echo "Port: ${port:-8080}"

empty=""
echo "Empty with default: [${empty:-fallback}]"

check() { local db="${1:?database name is required}"; echo "using $db"; }
check shopdb
( check ) 2>&1 | sed 's/.*: //'
```

```text output
Port: 8080
Port: 3000
Empty with default: [fallback]
using shopdb
database name is required
```

### 7. Special variables Bash sets for you

<Explain>
<What>
Variables with short symbol names that Bash fills automatically.
</What>
<Why>
They give information you need constantly: did the last command succeed, what arguments were given, what is my process ID.
</Why>
<When>
Error checking, argument handling, creating temporary files.
</When>
<Where>
Almost every real script.
</Where>
<How>
Read them like any variable. See the table.
</How>
</Explain>

| Variable | Holds |
| --- | --- |
| `$?` | Exit code of the last command (0 = success) |
| `$0` | Name of the script |
| `$1`, `$2`, … | Arguments |
| `$#` | Number of arguments |
| `"$@"` | All arguments, each kept separate |
| `$$` | Process ID of the current shell |
| `$!` | Process ID of the last background command |
| `$RANDOM` | A random number 0–32767 |
| `$SECONDS` | Seconds since the script started |
| `$LINENO` | The current line number |

```bash
ls /etc > /dev/null; echo "ls /etc exit code: $?"
ls /nope 2> /dev/null; echo "ls /nope exit code: $?"
set -- apple banana cherry
echo "Arguments: $#, first: $1, all: $*"
```

```text output
ls /etc exit code: 0
ls /nope exit code: 2
Arguments: 3, first: apple, all: apple banana cherry
```

`set -- apple banana cherry` sets the arguments by hand, to show how `$#`, `$1` and `$*` behave.

### 8. Shell variables vs environment variables (`export`)

<Explain>
<What>
A normal variable exists only in the current shell. An **environment variable** (created with `export`) is also copied to every program started from that shell.
</What>
<Why>
Programs like Node.js, Python, Docker and the AWS CLI read their settings from environment variables.
</Why>
<When>
When a program or child script you start needs the value.
</When>
<Where>
`export NODE_ENV=production`, `export AWS_PROFILE=dev`, `.env` files, Dockerfiles (`ENV`), CI settings.
</Where>
<How>
`export NAME=value`, or set it just for one command: `NAME=value command`. `env` or `printenv` lists all environment variables.
</How>
</Explain>

```bash
local_only="only here"
export shared="visible to children"

bash -c 'echo "child sees local_only: [${local_only:-}]"'
bash -c 'echo "child sees shared:     [${shared:-}]"'

GREETING="one-time value" bash -c 'echo "child sees GREETING:   [$GREETING]"'
echo "after that command, GREETING here: [${GREETING:-}]"
```

```text output
child sees local_only: []
child sees shared:     [visible to children]
child sees GREETING:   [one-time value]
after that command, GREETING here: []
```

- `bash -c '…'` starts a **child** Bash — a separate program.
- The child only receives exported variables.
- `GREETING=… command` passes a value to **that one command** without keeping it.

### 9. Naming conventions

<Explain>
<What>
Rules and habits for variable names.
</What>
<Why>
Clear names make scripts readable, and the right case avoids accidentally overwriting system variables like `PATH`.
</Why>
<When>
Every variable you create.
</When>
<Where>
All scripts.
</Where>
<How>
Letters, digits and `_`; cannot start with a digit; case-sensitive. Use **lower_case** for your script's own variables, **UPPER_CASE** for environment variables and constants.
</How>
</Explain>

| Good | Why | Avoid | Why |
| --- | --- | --- | --- |
| `backup_dir` | Clear, lower case | `d` | Meaningless |
| `max_retries` | Says what it is | `2nd_server` | Starts with a digit — invalid |
| `export AWS_REGION` | Environment → upper case | `PATH=./bin` | Overwrites the real PATH! |

### 10. Everything is text

<Explain>
<What>
Bash variables always hold text (strings). `count=5` stores the character "5", not a number.
</What>
<Why>
Explains why `count + 1` does not add, and why you need special syntax for maths.
</Why>
<When>
Whenever you do arithmetic.
</When>
<Where>
Counters, sizes, percentages.
</Where>
<How>
Use `$(( … ))` for maths (next lesson: **Command Substitution and Arithmetic**).
</How>
</Explain>

```bash
count=5
echo "Text joining: $count+1"
echo "Real maths:   $((count + 1))"
```

```text output
Text joining: 5+1
Real maths:   6
```

### 11. Reading input into a variable

<Explain>
<What>
`read` waits for a line of input and stores it in a variable.
</What>
<Why>
For interactive scripts that ask the user something.
</Why>
<When>
Asking for confirmation, a name, a choice.
</When>
<Where>
Setup and install scripts.
</Where>
<How>
`read -r -p "Question: " answer`. `-p` shows a prompt; `-r` keeps backslashes; `-s` hides typing (for passwords).
</How>
</Explain>

```bash
echo "production" | {
  read -r -p "Environment? " env
  echo "You chose: $env"
}
```

```text output
You chose: production
```

(Here `echo "production" |` types the answer automatically so the example runs on its own. In a real terminal you would type it.)

```bash
mkdir -p ~/var-lab && cd ~/var-lab
```


## Real-world example

A backup script worked for a year — until someone created a database named with a space and another user ran it with `BACKUP_DIR` unset. The original:

```bash
#!/bin/bash
for db in $(psql -Atc "select datname from pg_database where not datistemplate"); do
  pg_dump $db > $BACKUP_DIR/$db.sql
done
rm -rf $BACKUP_DIR/old/*
```

What went wrong: `$(…)` output was split on spaces (one database became two names), `$BACKUP_DIR` was empty so dumps went to `/` and the last line became `rm -rf /old/*`. The fixed version:

```bash
#!/usr/bin/env bash
set -euo pipefail

: "${BACKUP_DIR:?BACKUP_DIR must be set}"
readonly BACKUP_DIR
stamp="$(date +%F)"

while IFS= read -r db; do
  pg_dump --format=custom "$db" > "$BACKUP_DIR/${db}_${stamp}.dump"
done < <(psql -Atc "select datname from pg_database where not datistemplate")

find "$BACKUP_DIR/old" -mindepth 1 -mtime +14 -delete
```

Every expansion quoted, the required variable checked, input read line by line instead of word-split, and deletion done by age with `find` instead of a glob.

## Common mistakes

- **Spaces around `=`.**
- **Unquoted `$var`** — breaks on spaces and wildcards. Quote every expansion unless you deliberately want splitting.
- **`$var_suffix`** when you meant `${var}_suffix`.
- **Using `$*` or unquoted `$@`** to pass arguments on.
- **Forgetting `local`** in functions.
- **Uppercase variable names** that collide with `PATH`, `HOME`, `USER`.
- **Expecting `'$var'` to expand** inside single quotes.
- **`for x in $(cat file)`** to read lines — splits on spaces too. Use `while IFS= read -r line; do …; done < file`.

## Security lens

<Callout type="security">
In shell scripts, quoting is input validation's first line of defence. Unquoted variables let data become arguments, options or file patterns.
</Callout>

- **Argument injection:** an unquoted or unchecked value starting with `-` can be read as an option (`rm $file` with `file="-rf /"`). Quote, and use `--` to end options: `rm -- "$file"`.
- **Glob injection:** a value like `*` in an unquoted variable expands to every file in the directory.
- **Command injection via eval or `sh -c`:** never build command strings from variables (`eval "process $input"`, `ssh host "rm $path"`). If a remote command needs a value, quote it for the remote side with `printf '%q'`.
- **Secrets in variables:** `set -x` debugging prints every expanded variable — including tokens — into CI logs. Disable tracing around secrets, and never `echo` them.
- **`$RANDOM` is not secure** — use `openssl rand -hex 16` or `/dev/urandom` for tokens and temp names.
- **readonly** for security-relevant settings (allowed paths, target hosts) prevents later code from changing them by accident.

## Interview questions

<QA q="Why can't you put spaces around = in a Bash assignment?">
The shell splits each line into words before deciding what it means. `name=value` is one word that matches the assignment syntax. With spaces, `name = value` becomes three words, so Bash runs a command called name with the arguments = and value, which usually fails with 'command not found'.
</QA>

<QA q="What is the difference between single and double quotes in Bash?">
Single quotes preserve every character literally: no variable expansion, no command substitution, no escapes. Double quotes keep the text as one word and prevent word splitting and globbing, but still expand $variables, $(commands) and arithmetic, and honour backslash escapes for $, `, " and \. Use double quotes around variables and single quotes for literal text such as regexes and awk programs.
</QA>

<QA q="Why should you quote variables, for example rm “$file” instead of rm $file?">
Unquoted expansions undergo word splitting on IFS characters and pathname expansion of wildcards. A value with spaces becomes several arguments, a value with * expands to many files, and an empty value disappears entirely, so the command receives different arguments than intended — which can delete the wrong files or allow injection. Quoting passes the value as exactly one argument.
</QA>

<QA q="What is the difference between “$@” and “$*”?">
"$@" expands to all positional parameters as separate words, preserving each argument exactly, including ones with spaces. "$*" joins them into a single word separated by the first character of IFS. To forward arguments to another command unchanged, use "$@".
</QA>

<QA q="How do you make a script fail if a required variable is not set?">
Use `set -u` so that referencing any unset variable is an error, and for specific variables use the parameter expansion `${VAR:?message}`, often as `: "${VAR:?VAR must be set}"` near the top of the script. Both stop the script before an empty value can cause damage, such as an rm on the wrong path.
</QA>

## Key terms

<Terms>
  <Term name="Variable">A named value in the shell; always a string unless declared otherwise.</Term>
  <Term name="Expansion">Replacing $name, $(cmd) or $((expr)) with its value.</Term>
  <Term name="Word splitting">Splitting an unquoted expansion into separate arguments on IFS characters.</Term>
  <Term name="Globbing">Replacing *, ? and [] patterns with matching file names.</Term>
  <Term name="IFS">Internal Field Separator; characters used for word splitting.</Term>
  <Term name="Positional parameters">Script or function arguments: $1, $2 … and "$@".</Term>
  <Term name="local">Declares a variable scoped to a function.</Term>
  <Term name="export">Makes a variable part of the environment for child processes.</Term>
  <Term name="readonly">Prevents a variable from being changed.</Term>
</Terms>
