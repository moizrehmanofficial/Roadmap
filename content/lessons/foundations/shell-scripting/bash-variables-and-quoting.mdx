<BigIdea>
<Tr>
<En>
A variable is a **name that stores text**: `name="Alex"`. Read it with a dollar sign: `"$name"`. And remember **one rule** that prevents most Bash bugs: **always put variables in double quotes**, like `"$file"`.
</En>
<Ur>
Variable ek **naam hai jo text rakhta hai**: `name="Alex"`. Ise dollar ke nishan se parhein: `"$name"`. Aur **ek qaida** yaad rakhein jo Bash ke zyada tar bugs rokta hai: **variables hamesha double quotes me rakhein**, jaise `"$file"`.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

- **Create**: `name="Alex"`, with **no spaces** around `=`.
- **Read**: `"$name"` or `"${name}"`.
- **Double quotes** `"…"`: keep the text as one piece, but still replace `$variables`.
- **Single quotes** `'…'`: keep everything **exactly** as written.
- **export** `NAME=value`: share the variable with programs the script starts.

</En>
<Ur>

- **Banana**: `name="Alex"`, `=` ke dono taraf **koi space nahi**.
- **Parhna**: `"$name"` ya `"${name}"`.
- **Double quotes** `"…"`: text ko ek tukra rakhte hain, lekin `$variables` badal dete hain.
- **Single quotes** `'…'`: sab kuch **bilkul waisa** rakhte hain jaisa likha.
- **export** `NAME=value`: variable un programs ke saath share karo jo script chalati hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Change one line, not ten**: paths, server names and versions live in one place.
- **Most Bash bugs are quoting bugs**: a space in a file name or an empty variable can make a script delete the wrong files.
- **Configuration**: Docker, CI and cloud servers pass settings to apps through environment variables (`DATABASE_URL`, `NODE_ENV`).

</En>
<Ur>

- **Das lines nahi, ek line badlo**: paths, server naam aur versions ek jagah rehte hain.
- **Bash ke zyada tar bugs quotes ke bugs hain**: file naam me space ya khaali variable script se ghalat files delete karwa sakta hai.
- **Configuration**: Docker, CI aur cloud servers apps ko settings environment variables (`DATABASE_URL`, `NODE_ENV`) se dete hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Example |
| --- | --- |
| A value used more than once | `backup_dir="/mnt/backups"` |
| A value that changes between runs | `env="$1"` (from an argument) |
| Saving a command's result | `today="$(date +%F)"` |
| Settings passed to programs | `export NODE_ENV=production` |
| Reading system information | `$HOME`, `$USER`, `$PWD`, `$PATH` |

</En>
<Ur>

| Halat | Misaal |
| --- | --- |
| Ek value jo ek se zyada dafa istemal ho | `backup_dir="/mnt/backups"` |
| Value jo har run me badle | `env="$1"` (argument se) |
| Command ka nateeja save karna | `today="$(date +%F)"` |
| Programs ko settings dena | `export NODE_ENV=production` |
| System ki maloomat parhna | `$HOME`, `$USER`, `$PWD`, `$PATH` |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

Before running any line, Bash first **replaces** every `$name` with its value (this is called **expansion**). Quotes control **how** that happens: whether the value stays one piece, gets split into words, or is left exactly as typed.

</En>
<Ur>

Koi bhi line chalane se pehle Bash har `$name` ko us ki value se **badal** deta hai (ise **expansion** kehte hain). Quotes tay karte hain ye **kaise** ho: value ek tukra rahe, alfaz me toot jaye, ya bilkul waisi rahe jaisi likhi.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

A variable is a **sticky note with a name on top**. You write "`server`" at the top and "`web-1.example.com`" underneath. Whenever a command needs the server's address, you point at the note instead of writing the address again.

If the server changes, you rewrite **one note**, and every command that uses it gets the new value. Without variables, a backup script might have `/var/www/myapp` in ten places, and when the folder moves you'll miss one.

</En>
<Ur>

Variable ek **chipakne wali parchi** hai jis ke upar naam likha ho. Upar "`server`" likhein aur neeche "`web-1.example.com`". Jab bhi kisi command ko server ka pata chahiye, aap pata dobara likhne ke bajaye parchi ki taraf ishara karte hain.

Server badle to aap **ek parchi** dobara likhte hain, aur use istemal karne wali har command ko nayi value mil jati hai. Variables ke baghair backup script me `/var/www/myapp` das jagah ho sakta hai, aur folder badalne par ek reh jayega.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Value** | The text stored (in Bash, **everything is text**) | `"Alex"` |
| **Assignment** | Storing a value | `name="Alex"` |
| **Expansion** | Bash replacing `$name` with its value | `echo $name` → `echo Alex` |
| **Word splitting** | Bash cutting unquoted text into words at spaces | `my file` → `my` + `file` |
| **Glob** | A wildcard like `*` that Bash turns into file names | `*.txt` |
| **Environment variable** | A variable passed on to programs you start | `PATH`, `HOME` |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Value** | Rakha hua text (Bash me **har cheez text hai**) | `"Alex"` |
| **Assignment** | Value rakhna | `name="Alex"` |
| **Expansion** | Bash ka `$name` ko us ki value se badalna | `echo $name` → `echo Alex` |
| **Word splitting** | Bash ka baghair quotes ke text ko spaces par alfaz me torna | `my file` → `my` + `file` |
| **Glob** | `*` jaisa wildcard jise Bash file naamon me badalta hai | `*.txt` |
| **Environment variable** | Variable jo aap ke chalaye programs tak pohanchta hai | `PATH`, `HOME` |

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Create and read a variable">

<Tr>
<En>

`name=value` stores a value; `$name` reads it. Put quotes around values with spaces. `${#name}` gives the **length** of the value.

</En>
<Ur>

`name=value` value rakhta hai; `$name` use parhta hai. Spaces wali values ke gird quotes lagayen. `${#name}` value ki **lambai** deta hai.

</Ur>
</Tr>

```bash
name="Alex"
city="Austin"
greeting="Hello $name from $city"
echo "$greeting"
echo "Name has ${#name} letters"
```

```text output
Hello Alex from Austin
Name has 4 letters
```

<Happened>
<Tr>
<En>Inside double quotes, `$name` and `$city` were replaced by their values. `${#name}` counted the letters in "Alex": 4.</En>
<Ur>Double quotes ke andar `$name` aur `$city` apni values se badal gaye. `${#name}` ne "Alex" ke huroof gine: 4.</Ur>
</Tr>
</Happened>

</Step>

<Step title="The no-spaces rule">

<Tr>
<En>

Bash splits command lines at spaces. So `name = Alex` means "run a command called `name` with the words `=` and `Alex`", which fails.

- `name=Alex` ✓
- `name = Alex` ✗
- `name= Alex` ✗ (runs `Alex` with an empty `name`)

</En>
<Ur>

Bash command lines ko spaces par torta hai. Isliye `name = Alex` ka matlab "`name` naam ki command chalao, alfaz `=` aur `Alex` ke saath", jo fail hoti hai.

- `name=Alex` ✓
- `name = Alex` ✗
- `name= Alex` ✗ (khaali `name` ke saath `Alex` chalata hai)

</Ur>
</Tr>

```bash
name = Alex 2>&1 | sed 's/.*: //'
name="Alex"
echo "Correct: $name"
```

```text output
command not found
Correct: Alex
```

</Step>

<Step title="${name}: braces when the name touches other text">

<Tr>
<En>

In `"$file_2026"`, Bash looks for a variable called `file_2026`, not `file` followed by `_2026`. Braces show exactly where the name ends: `"${file}_2026"`. Using braces is never wrong.

</En>
<Ur>

`"$file_2026"` me Bash `file_2026` naam ka variable dhoondta hai, `file` ke baad `_2026` nahi. Braces bilkul dikhate hain naam kahan khatam hota hai: `"${file}_2026"`. Braces lagana kabhi ghalat nahi.

</Ur>
</Tr>

```bash
file="report"
echo "Without braces: [$file_2026.txt]"
echo "With braces:    [${file}_2026.txt]"
```

```text output
Without braces: [.txt]
With braces:    [report_2026.txt]
```

<Happened>
<Tr>
<En>`$file_2026` doesn't exist, so it became **empty**, leaving just `.txt`. With braces we got `report_2026.txt`.</En>
<Ur>`$file_2026` mojood nahi, isliye wo **khaali** ho gaya aur sirf `.txt` bacha. Braces ke saath `report_2026.txt` mila.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Three kinds of quoting">

<Tr>
<En>

- **Double quotes** `"…"`: keep the text as one piece, **still** replace `$variables` and run `$(commands)`.
- **Single quotes** `'…'`: nothing changes; text stays **exactly** as typed.
- **Backslash** `\`: protects one character, e.g. `\$`.

Default to double quotes around variables. Use single quotes for fixed text with special characters (awk programs, regex).

</En>
<Ur>

- **Double quotes** `"…"`: text ek tukra rakhte hain, **phir bhi** `$variables` badalte aur `$(commands)` chalate hain.
- **Single quotes** `'…'`: kuch nahi badalta; text **bilkul waisa** rehta hai.
- **Backslash** `\`: ek character ki hifazat, jaise `\$`.

Variables ke gird default me double quotes. Khaas characters wale tay text (awk programs, regex) ke liye single quotes.

</Ur>
</Tr>

```bash
name="Alex"
echo "Double: Hello $name, today is $(date +%Y)" | sed 's/[0-9]\{4\}/YYYY/'
echo 'Single: Hello $name, today is $(date +%Y)'
echo "Backslash: the price is \$5"
```

```text output
Double: Hello Alex, today is YYYY
Single: Hello $name, today is $(date +%Y)
Backslash: the price is $5
```

<Happened>
<Tr>
<En>

- Double quotes: `$name` became Alex and `$(date +%Y)` ran (the `sed` turns the year into `YYYY` so the page never goes out of date).
- Single quotes: everything printed exactly as typed.
- `\$5`: the backslash stopped `$5` from being treated as a variable.

</En>
<Ur>

- Double quotes: `$name` Alex bana aur `$(date +%Y)` chala (`sed` saal ko `YYYY` kar deta hai taa ke page kabhi purana na ho).
- Single quotes: sab bilkul waisa print hua jaisa likha.
- `\$5`: backslash ne `$5` ko variable samjhe jane se roka.

</Ur>
</Tr>
</Happened>

| Quotes | `$var` replaced? | `$(cmd)` run? | Split at spaces? | `*` expanded? |
| --- | --- | --- | --- | --- |
| None: `$var` | Yes | Yes | **Yes** | **Yes** |
| Double: `"$var"` | Yes | Yes | No | No |
| Single: `'$var'` | No | No | No | No |

</Step>

<Step title="Why unquoted variables break">

<Tr>
<En>

When a variable is **not** in double quotes, Bash does two extra things to its value:

1. **splits** it into separate words at spaces
2. treats `*`, `?` and `[ ]` as **wildcards** that match file names

So a file called `my report.txt` becomes **two** files, and a value `*.txt` becomes **every** `.txt` file. `printf '[%s]\n'` below prints each argument in brackets, so you can see exactly what Bash created.

</En>
<Ur>

Jab variable double quotes me **na** ho, to Bash us ki value ke saath do izafi kaam karta hai:

1. spaces par use alag alfaz me **torta** hai
2. `*`, `?` aur `[ ]` ko file naamon se milne wale **wildcards** samajhta hai

Isliye `my report.txt` naam ki file **do** files ban jati hai, aur value `*.txt` **har** `.txt` file ban jati hai. Neeche `printf '[%s]\n'` har argument ko brackets me print karta hai, taa ke aap dekh sakein Bash ne bilkul kya banaya.

</Ur>
</Tr>

```bash
touch "my report.txt" a.txt b.txt
file="my report.txt"
pattern="*.txt"

echo "--- unquoted \$file gives these arguments:"
printf '[%s]\n' $file
echo "--- quoted \"\$file\":"
printf '[%s]\n' "$file"
echo "--- unquoted \$pattern:"
printf '[%s]\n' $pattern
echo "--- quoted \"\$pattern\":"
printf '[%s]\n' "$pattern"
```

```text output
--- unquoted $file gives these arguments:
[my]
[report.txt]
--- quoted "$file":
[my report.txt]
--- unquoted $pattern:
[a.txt]
[b.txt]
[my report.txt]
--- quoted "$pattern":
[*.txt]
```

<Happened>
<Tr>
<En>

- Unquoted `$file` → **two** wrong arguments. Quoted → **one** correct argument.
- Unquoted `$pattern` → turned into **three file names**. Quoted → stayed `*.txt`.
- ShellCheck warns about this as `SC2086`.

</En>
<Ur>

- Baghair quotes `$file` → **do** ghalat arguments. Quotes ke saath → **ek** sahi argument.
- Baghair quotes `$pattern` → **teen file naamon** me badal gaya. Quotes ke saath → `*.txt` hi raha.
- ShellCheck is ki warning `SC2086` ke naam se deta hai.

</Ur>
</Tr>
</Happened>

<Callout type="danger" title="A real disaster">
<Tr>
<En>`rm -rf $dir/*` with `dir` empty (a typo, or a failed command) becomes `rm -rf /*`: delete everything. Quote it (`"$dir"/*`), and protect it with `${dir:?}`, which stops the script when `dir` is empty.</En>
<Ur>`rm -rf $dir/*` jab `dir` khaali ho (typo, ya fail hui command) to `rm -rf /*` ban jata hai: sab kuch mita do. Quotes lagayen (`"$dir"/*`), aur `${dir:?}` se bachayen, jo `dir` khaali hone par script rok deta hai.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Empty, unset, and defaults">

<Tr>
<En>

An **unset** variable was never created; an **empty** one exists but holds no text. Bash can fill in a **default**:

- `${var:-default}`: use the default if empty or unset
- `${var:=default}`: same, and also save it into `var`
- `${var:?message}`: **stop the script** with that message if empty or unset

Great for settings at the top of scripts: `port="${PORT:-8080}"`.

</En>
<Ur>

**Unset** variable kabhi bana hi nahi; **khaali** mojood hai lekin us me text nahi. Bash **default** bhar sakta hai:

- `${var:-default}`: khaali ya unset ho to default lo
- `${var:=default}`: wahi, aur `var` me save bhi karo
- `${var:?message}`: khaali ya unset ho to us paigham ke saath **script rok do**

Script ke upar settings ke liye behtareen: `port="${PORT:-8080}"`.

</Ur>
</Tr>

```bash
unset port
echo "Port: ${port:-8080}"
port=3000
echo "Port: ${port:-8080}"

empty=""
echo "Empty with default: [${empty:-fallback}]"

check() { local db="${1:?database name is required}"; echo "using $db"; }
check shopdb
( check ) 2>&1 | sed 's/.*: //'
```

```text output
Port: 8080
Port: 3000
Empty with default: [fallback]
using shopdb
database name is required
```

<Happened>
<Tr>
<En>

- With `port` unset, the default 8080 was used; after `port=3000`, the real value won.
- `check` without an argument **stopped** with "database name is required" instead of silently using an empty name.

</En>
<Ur>

- `port` unset tha to default 8080 istemal hua; `port=3000` ke baad asal value jeet gayi.
- Baghair argument ke `check` chupke se khaali naam istemal karne ke bajaye "database name is required" ke saath **ruk gaya**.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Special variables Bash fills for you">

| Variable | Holds |
| --- | --- |
| `$?` | Exit code of the last command (0 = success) |
| `$0` | Name of the script |
| `$1`, `$2`, … | Arguments |
| `$#` | Number of arguments |
| `"$@"` | All arguments, each kept separate |
| `$$` | Process ID of the current shell |
| `$!` | Process ID of the last background command |
| `$RANDOM` | A random number 0–32767 |
| `$SECONDS` | Seconds since the script started |
| `$LINENO` | The current line number |

```bash
ls /etc > /dev/null; echo "ls /etc exit code: $?"
ls /nope 2> /dev/null; echo "ls /nope exit code: $?"
set -- apple banana cherry
echo "Arguments: $#, first: $1, all: $*"
```

```text output
ls /etc exit code: 0
ls /nope exit code: 2
Arguments: 3, first: apple, all: apple banana cherry
```

<Happened>
<Tr>
<En>`$?` was 0 after a success and 2 after a failure. `set -- apple banana cherry` set the arguments by hand, so `$#` = 3 and `$1` = apple.</En>
<Ur>Kamyabi ke baad `$?` 0 tha aur failure ke baad 2. `set -- apple banana cherry` ne arguments haath se set kiye, isliye `$#` = 3 aur `$1` = apple.</Ur>
</Tr>
</Happened>

</Step>

<Step title="export: share a variable with programs you start">

<Tr>
<En>

A normal variable lives only in the **current** shell. `export` copies it to **every program** started from that shell. Node.js, Python, Docker and the AWS CLI read their settings this way.

`NAME=value command` passes a value to **just that one command**, without keeping it.

</En>
<Ur>

Aam variable sirf **mojooda** shell me rehta hai. `export` use us shell se chalne wale **har program** me copy kar deta hai. Node.js, Python, Docker aur AWS CLI apni settings isi tarah parhte hain.

`NAME=value command` value **sirf us ek command** ko deta hai, rakhta nahi.

</Ur>
</Tr>

```bash
local_only="only here"
export shared="visible to children"

bash -c 'echo "child sees local_only: [${local_only:-}]"'
bash -c 'echo "child sees shared:     [${shared:-}]"'

GREETING="one-time value" bash -c 'echo "child sees GREETING:   [$GREETING]"'
echo "after that command, GREETING here: [${GREETING:-}]"
```

```text output
child sees local_only: []
child sees shared:     [visible to children]
child sees GREETING:   [one-time value]
after that command, GREETING here: []
```

<Happened>
<Tr>
<En>

- `bash -c '…'` starts a **child** program. It only received the **exported** variable.
- `GREETING=… bash -c …` gave the value to that one command; afterwards it's gone.

</En>
<Ur>

- `bash -c '…'` ek **child** program shuru karta hai. Use sirf **export** kiya hua variable mila.
- `GREETING=… bash -c …` ne value us ek command ko di; baad me wo ghayab.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Good names">

<Tr>
<En>

Names use letters, digits and `_`, can't start with a digit, and are case-sensitive. Use **lower_case** for your script's own variables and **UPPER_CASE** for environment variables, so you never overwrite system ones like `PATH`.

</En>
<Ur>

Naamon me letters, digits aur `_` hote hain, digit se shuru nahi ho sakte, aur case-sensitive hain. Script ke apne variables ke liye **lower_case** aur environment variables ke liye **UPPER_CASE** istemal karein, taa ke `PATH` jaise system wale kabhi na mitein.

</Ur>
</Tr>

| Good | Why | Avoid | Why |
| --- | --- | --- | --- |
| `backup_dir` | Clear, lower case | `d` | Meaningless |
| `max_retries` | Says what it is | `2nd_server` | Starts with a digit: invalid |
| `export AWS_REGION` | Environment → upper case | `PATH=./bin` | Overwrites the real PATH! |

</Step>

<Step title="Everything is text">

<Tr>
<En>

`count=5` stores the **character** "5", not a number. So `$count+1` just joins text. For real maths, use `$(( … ))` (next lesson).

</En>
<Ur>

`count=5` **character** "5" rakhta hai, number nahi. Isliye `$count+1` sirf text jorta hai. Asli hisaab ke liye `$(( … ))` istemal karein (agla lesson).

</Ur>
</Tr>

```bash
count=5
echo "Text joining: $count+1"
echo "Real maths:   $((count + 1))"
```

```text output
Text joining: 5+1
Real maths:   6
```

</Step>

<Step title="read: ask the user for a value">

<Tr>
<En>

`read -r -p "Question: " answer` waits for a line and stores it. `-p` shows a prompt, `-r` keeps backslashes as typed, `-s` hides typing (for passwords).

</En>
<Ur>

`read -r -p "Sawal: " answer` ek line ka intezar kar ke use rakhta hai. `-p` prompt dikhata hai, `-r` backslashes waise hi rakhta hai, `-s` likhna chhupata hai (passwords ke liye).

</Ur>
</Tr>

```bash
echo "production" | {
  read -r -p "Environment? " env
  echo "You chose: $env"
}
```

```text output
You chose: production
```

<Happened>
<Tr>
<En>`echo "production" |` types the answer automatically so the example runs by itself. In a real terminal you'd type it.</En>
<Ur>`echo "production" |` jawab khud likh deta hai taa ke misaal khud chal jaye. Asli terminal me aap khud likhenge.</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Unquoted variables">

```text
cp $src $dest
rm -rf $dir/*
```

</Bad>
<Good title="Quote every expansion">

```text
cp -- "$src" "$dest"
rm -rf -- "${dir:?}"/*
```

</Good>
</Compare>

<Compare>
<Bad title="Reading lines with for">

```text
for line in $(cat hosts.txt); do …; done     # also splits at spaces
```

</Bad>
<Good title="while read">

```text
while IFS= read -r line; do …; done < hosts.txt
```

</Good>
</Compare>

<Compare>
<Bad title="Expecting single quotes to expand">

```text
echo 'Hello $name'      # prints: Hello $name
```

</Bad>
<Good title="Double quotes for values">

```text
echo "Hello $name"      # prints: Hello Alex
```

</Good>
</Compare>

<Challenge title="Make it safe">

<Tr>
<En>
A script starts with `rm -rf $BACKUP_DIR/old/*`. Rewrite that line so it can **never** delete the wrong folder if `BACKUP_DIR` is empty or has spaces.

<DeepDive title="Real world: a backup script that broke after a year">

A backup script worked for a year, until someone created a database with a space in its name and another user ran it with `BACKUP_DIR` unset. The original:

```bash
#!/bin/bash
for db in $(psql -Atc "select datname from pg_database where not datistemplate"); do
  pg_dump $db > $BACKUP_DIR/$db.sql
done
rm -rf $BACKUP_DIR/old/*
```

What went wrong: `$(…)` output was split on spaces (one database became two names), `$BACKUP_DIR` was empty so dumps went to `/`, and the last line became `rm -rf /old/*`. The fixed version:

```bash
#!/usr/bin/env bash
set -euo pipefail

: "${BACKUP_DIR:?BACKUP_DIR must be set}"
readonly BACKUP_DIR
stamp="$(date +%F)"

while IFS= read -r db; do
  pg_dump --format=custom "$db" > "$BACKUP_DIR/${db}_${stamp}.dump"
done < <(psql -Atc "select datname from pg_database where not datistemplate")

find "$BACKUP_DIR/old" -mindepth 1 -mtime +14 -delete
```

Every expansion quoted, the required variable checked, input read line by line instead of word-split, and deletion done by age with `find` instead of a glob.

Other mistakes: using `$*` or unquoted `$@` to pass arguments on; forgetting `local` in functions; and upper-case names that collide with `PATH`, `HOME` or `USER`.

</DeepDive>

<DeepDive title="Security lens">

In shell scripts, quoting is the first line of defence for input validation. Unquoted variables let data become arguments, options or file patterns.

- **Argument injection:** an unchecked value starting with `-` can be read as an option (`rm $file` with `file="-rf /"`). Quote, and use `--` to end options: `rm -- "$file"`.
- **Glob injection:** a value like `*` in an unquoted variable expands to every file in the folder.
- **Command injection via eval or `sh -c`:** never build command strings from variables (`eval "process $input"`, `ssh host "rm $path"`). If a remote command needs a value, quote it for the remote side with `printf '%q'`.
- **Secrets in variables:** `set -x` debugging prints every expanded variable, including tokens, into CI logs. Disable tracing around secrets, and never `echo` them.
- **`$RANDOM` is not secure:** use `openssl rand -hex 16` or `/dev/urandom` for tokens and temp names.
- **readonly** for security-relevant settings (allowed paths, target hosts) prevents later code from changing them by accident.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why can't you put spaces around = in a Bash assignment?">
The shell splits each line into words before deciding what it means. `name=value` is one word that matches the assignment syntax. With spaces, `name = value` becomes three words, so Bash runs a command called name with the arguments = and value, which usually fails with 'command not found'.
</QA>

<QA q="What is the difference between single and double quotes in Bash?">
Single quotes preserve every character literally: no variable expansion, no command substitution, no escapes. Double quotes keep the text as one word and prevent word splitting and globbing, but still expand $variables, $(commands) and arithmetic, and honour backslash escapes for $, `, " and \. Use double quotes around variables and single quotes for literal text such as regexes and awk programs.
</QA>

<QA q="Why should you quote variables, for example rm “$file” instead of rm $file?">
Unquoted expansions undergo word splitting on IFS characters and pathname expansion of wildcards. A value with spaces becomes several arguments, a value with * expands to many files, and an empty value disappears entirely, so the command receives different arguments than intended, which can delete the wrong files or allow injection. Quoting passes the value as exactly one argument.
</QA>

<QA q="What is the difference between “$@” and “$*”?">
"$@" expands to all positional parameters as separate words, preserving each argument exactly, including ones with spaces. "$*" joins them into a single word separated by the first character of IFS. To forward arguments to another command unchanged, use "$@".
</QA>

<QA q="How do you make a script fail if a required variable is not set?">
Use `set -u` so that referencing any unset variable is an error, and for specific variables use the parameter expansion `${VAR:?message}`, often as `: "${VAR:?VAR must be set}"` near the top of the script. Both stop the script before an empty value can cause damage, such as an rm on the wrong path.
</QA>

</DeepDive>
