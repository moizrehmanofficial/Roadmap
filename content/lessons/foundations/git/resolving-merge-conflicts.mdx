<BigIdea>
<Tr>
<En>
A **conflict** happens when two branches changed the **same lines** (or one edited a file the other deleted), so Git can't choose automatically. Git stops, marks the file with **`<<<<<<<`**, **`=======`** and **`>>>>>>>`**, and waits for you. You **edit the file into the correct final version**, delete the markers, **`git add`** it, and finish with **`git commit`** (merge) or **`git rebase --continue`** (rebase). Changed your mind? **`git merge --abort`** puts everything back. Conflicts are normal, not errors.
</En>
<Ur>
**Conflict** tab hota hai jab do branches ne **wahi lines** badlin (ya ek ne wo file badli jo doosri ne mita di), aur Git khud nahi chun sakta. Git ruk jata hai, file par **`<<<<<<<`**, **`=======`** aur **`>>>>>>>`** ke nishan lagata hai, aur aap ka intezar karta hai. Aap **file ko durust aakhri shakal me** badalte hain, nishan mitate hain, **`git add`** karte hain, aur **`git commit`** (merge) ya **`git rebase --continue`** (rebase) se khatam karte hain. Iraada badal gaya? **`git merge --abort`** sab wapas kar deta hai. Conflicts aam baat hain, ghalti nahi.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

During a merge, Git compares each file in three versions: the **common ancestor (base)**, **ours** and **theirs**. Changes to different parts combine automatically. If both sides changed the same region differently, that region becomes a **conflict hunk** and the file is marked **unmerged**.

```text
<<<<<<< HEAD           ← start: our version (current branch)
Meeting at 3 pm
=======                ← separator
Meeting at 4 pm
>>>>>>> feature        ← end: their version (branch being merged)
```

</En>
<Ur>

Merge ke doran Git har file ke teen version milata hai: **mushtarka aabaa (base)**, **ours** aur **theirs**. Alag hisson ki tabdeeliyan khud jur jati hain. Agar dono taraf ne ek hi hissa alag alag badla, to wo hissa **conflict hunk** ban jata hai aur file **unmerged** kehlati hai.

```text
<<<<<<< HEAD           ← start: our version (current branch)
Meeting at 3 pm
=======                ← separator
Meeting at 4 pm
>>>>>>> feature        ← end: their version (branch being merged)
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Many beginners think a conflict means they broke something. They didn't. A conflict is Git being careful: instead of guessing and maybe throwing away someone's work, it stops and asks you. The danger isn't the conflict, it's resolving it **carelessly**.

- Every team hits conflicts, so handling them calmly is a core skill.
- A **wrong resolution** silently breaks the build or drops someone's fix, including security fixes.
- Interviewers often ask "how do you resolve a merge conflict?".

</En>
<Ur>

Bohot se naye log samajhte hain conflict ka matlab unhon ne kuch tor diya. Aisa nahi. Conflict Git ki ehtiyaat hai: andaza laga kar shayad kisi ka kaam phenkne ke bajaye wo ruk kar aap se poochta hai. Khatra conflict me nahi, use **laparwahi** se hal karne me hai.

- Har team ko conflicts aate hain, isliye sukoon se hal karna bunyadi hunar hai.
- **Ghalat hal** chupke se build tor deta hai ya kisi ka fix gira deta hai, security fixes samet.
- Interview me aksar poochte hain "merge conflict kaise hal karte ho?".

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

You'll meet conflicts in `git merge`, `git pull`, `git rebase`, `git cherry-pick`, `git stash pop`, and in GitHub pull requests ("This branch has conflicts that must be resolved").

</En>
<Ur>

Conflicts `git merge`, `git pull`, `git rebase`, `git cherry-pick`, `git stash pop` me, aur GitHub pull requests me ("This branch has conflicts that must be resolved") milte hain.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
git status                       # which files are unmerged?
# open each file, choose the final text, delete the markers
git add <file>                   # mark it resolved
git commit                       # merge   (or: git rebase --continue)
git merge --abort                # or give up and go back
```

</En>
<Ur>

```text
git status                       # kaunsi files unmerged hain?
# har file kholo, aakhri text chuno, nishan mitao
git add <file>                   # hal shuda ka nishan
git commit                       # merge   (ya: git rebase --continue)
git merge --abort                # ya chhor kar wapas
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Two people edit the **same sentence** in a shared document while offline. One writes "Meeting at **3 pm**", the other "Meeting at **4 pm**". When they sync, the software can't know which is right, so it shows **both** and asks a human. That's a merge conflict. If they had edited **different sentences**, both changes would have been combined automatically.

</En>
<Ur>

Do log offline hote hue saanjhe document me **ek hi jumla** badalte hain. Ek likhta hai "Meeting at **3 pm**", doosra "Meeting at **4 pm**". Sync par software nahi jaan sakta kaunsa durust hai, isliye **dono** dikha kar insaan se poochta hai. Yahi merge conflict hai. Agar unhon ne **alag jumle** badle hote, to dono tabdeeliyan khud jur jatin.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Create and spot a conflict">

<Tr>
<En>

When both sides changed the same line, Git stops the merge and prints `CONFLICT (content): Merge conflict in <file>`. Nothing is committed yet; you're **in the middle of a merge**. `git status` lists conflicted files under "Unmerged paths", and `git diff --name-only --diff-filter=U` prints just their names.

</En>
<Ur>

Jab dono taraf ne wahi line badli ho, Git merge rok kar `CONFLICT (content): Merge conflict in <file>` chhaapta hai. Abhi kuch commit nahi hua; aap **merge ke beech** me hain. `git status` conflict wali files "Unmerged paths" ke neeche dikhata hai, aur `git diff --name-only --diff-filter=U` sirf un ke naam.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q app && cd app
printf 'APP_NAME=Shop\nPORT=3000\nTIMEOUT=30\n' > config.env && git add . && git commit -qm "Add config"
git switch -q -c feature/port
sed -i 's/PORT=3000/PORT=8080/' config.env && git commit -qam "Use port 8080"
git switch -q main
sed -i 's/PORT=3000/PORT=5000/' config.env && git commit -qam "Use port 5000"
git merge feature/port
echo "--- conflicted files:"; git diff --name-only --diff-filter=U
```

```text output
Auto-merging config.env
CONFLICT (content): Merge conflict in config.env
Automatic merge failed; fix conflicts and then commit the result.
--- conflicted files:
config.env
```

<Happened>
<Tr>
<En>

- `config.env` has three settings; "Add config" is the common base.
- `feature/port` changed `PORT=3000` to `8080`, and `main` changed the **same line** to `5000`.
- `git merge` combined what it could, then stopped:
  - `Auto-merging config.env`: Git tried this file.
  - `CONFLICT (content)`: it couldn't, because the changes overlap.
  - `Automatic merge failed; fix conflicts and then commit the result.`: your next job.
- `--diff-filter=U` lists only **U**nmerged files, very handy when a merge touches dozens of files and only a few conflict.

</En>
<Ur>

- `config.env` me teen settings hain; "Add config" mushtarka base hai.
- `feature/port` ne `PORT=3000` ko `8080` kiya, aur `main` ne **wahi line** `5000` ki.
- `git merge` ne jo jor saka jora, phir ruk gaya:
  - `Auto-merging config.env`: Git ne ye file aazmayi.
  - `CONFLICT (content)`: nahi jor saka, tabdeeliyan takra rahi hain.
  - `Automatic merge failed; fix conflicts and then commit the result.`: aap ka agla kaam.
- `--diff-filter=U` sirf **U**nmerged files dikhata hai, bohot kaam ka jab merge darjanon files chhuye aur sirf kuch me conflict ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Read the markers">

<Tr>
<En>

Between `<<<<<<< HEAD` and `=======` is **your** version; between `=======` and `>>>>>>> branch` is **theirs**. Lines outside the markers merged fine. A file can contain several conflict hunks, so search for `<<<<<<<` in your editor.

</En>
<Ur>

`<<<<<<< HEAD` aur `=======` ke beech **aap ka** version hai; `=======` aur `>>>>>>> branch` ke beech **un ka**. Nishanon ke bahar ki lines theek merge ho gayin. Ek file me kai conflict hunks ho sakte hain, isliye editor me `<<<<<<<` dhoondhein.

</Ur>
</Tr>

```bash
cd app
cat config.env
```

```text output
APP_NAME=Shop
<<<<<<< HEAD
PORT=5000
=======
PORT=8080
>>>>>>> feature/port
TIMEOUT=30
```

<Happened>
<Tr>
<En>

- `APP_NAME=Shop` and `TIMEOUT=30` sit outside the markers: nobody disagreed, so they're already final.
- `<<<<<<< HEAD` starts **our** side. HEAD is `main`, the branch we're merging **into**, so `PORT=5000` is ours.
- `=======` separates the sides; `PORT=8080` is **theirs**.
- `>>>>>>> feature/port` ends the conflict and names the other branch.

The markers are plain text written into your file. The program won't run with them inside, which is why you must remove every one.

</En>
<Ur>

- `APP_NAME=Shop` aur `TIMEOUT=30` nishanon ke bahar hain: kisi ka ikhtilaf nahi, isliye ye pehle se aakhri hain.
- `<<<<<<< HEAD` **hamari** taraf shuru karta hai. HEAD `main` hai, jis branch **me** hum merge kar rahe hain, isliye `PORT=5000` hamara hai.
- `=======` dono taraf ko alag karta hai; `PORT=8080` **un ka** hai.
- `>>>>>>> feature/port` conflict khatam karta hai aur doosri branch ka naam deta hai.

Nishan aap ki file me likha saada text hain. In ke hote program nahi chalega, isliye har ek mitana zaroori hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Resolve: edit, add, commit">

<Tr>
<En>

Make the file look **exactly** how it should end up (one side, the other, or a combination) and delete all marker lines. First understand **why** each side made its change: `git log --merge -p file` shows the commits from both sides that touched the file. Git trusts whatever you `git add`; it doesn't check that the result makes sense. Then: edit → `git add file` → run the tests → `git commit`.

</En>
<Ur>

File ko **bilkul** waisa banayen jaisa aakhir me hona chahiye (ek taraf, doosri, ya dono ka milaap) aur saari nishan wali lines mitayen. Pehle samjhein har taraf ne tabdeeli **kyun** ki: `git log --merge -p file` dono taraf ke wo commits dikhata hai jinhon ne file chhui. Git jo bhi aap `git add` karein us par bharosa karta hai; check nahi karta ke nateeja maqool hai. Phir: badlo → `git add file` → tests chalao → `git commit`.

</Ur>
</Tr>

```bash
cd app
git log --merge --format='%s' -- config.env
# decision after talking to the team: 8080 is correct
printf 'APP_NAME=Shop\nPORT=8080\nTIMEOUT=30\n' > config.env
grep -c '^<<<<<<<\|^=======\|^>>>>>>>' config.env | sed 's/$/ markers left/'
git add config.env
git commit -q --no-edit
git log --graph --format=%s
```

```text output
Use port 5000
Use port 8080
0 markers left
*   Merge branch 'feature/port'
|\  
| * Use port 8080
* | Use port 5000
|/  
* Add config
```

<Happened>
<Tr>
<En>

- `git log --merge` listed both commits that touched the file. Read their messages to understand the intent.
- We decided 8080 is right (in real life: ask the authors, check the ticket) and wrote the final file. We could equally keep 5000, or write something new like `PORT=${PORT:-8080}`.
- `grep -c` counted leftover marker lines: 0.
- `git add` told Git "resolved"; `git commit --no-edit` finished with the default message "Merge branch 'feature/port'".

</En>
<Ur>

- `git log --merge` ne file chhune wale dono commits dikhaye. Maqsad samajhne ke liye un ke messages parhein.
- Hum ne tay kiya 8080 durust hai (asal zindagi me: likhne walon se poochein, ticket dekhein) aur aakhri file likhi. 5000 bhi rakh sakte the, ya kuch naya jaise `PORT=${PORT:-8080}`.
- `grep -c` ne bachi nishan lines ginin: 0.
- `git add` ne Git ko "hal ho gaya" bataya; `git commit --no-edit` ne default message "Merge branch 'feature/port'" se khatam kiya.

</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>In VS Code the same conflict shows clickable options above it: **Accept Current Change** (ours), **Accept Incoming Change** (theirs), **Accept Both Changes** and **Compare Changes**. Clicking one just edits the text for you; you still save, `git add` and commit.</En>
<Ur>VS Code me yahi conflict upar click hone wale options dikhata hai: **Accept Current Change** (ours), **Accept Incoming Change** (theirs), **Accept Both Changes** aur **Compare Changes**. Click karna bas aap ke liye text badal deta hai; save, `git add` aur commit phir bhi aap karte hain.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Take one whole side: ours or theirs">

<Tr>
<En>

`git checkout --ours file` or `git checkout --theirs file` replaces the file with one side completely (`git restore --ours file` is the newer spelling). It's faster when one version is clearly right: generated files, lock files, build output, or files you know are obsolete on one side.

</En>
<Ur>

`git checkout --ours file` ya `git checkout --theirs file` file ko poori tarah ek taraf se badal deta hai (`git restore --ours file` naya andaaz hai). Jab ek version saaf tor par durust ho to ye tez hai: banayi gayi files, lock files, build output, ya aisi files jo aap jaante hain ek taraf purani ho chuki hain.

</Ur>
</Tr>

```bash
git init -q lock && cd lock
echo "lock v1" > package-lock.json && git add . && git commit -qm "Lock v1"
git switch -q -c deps && echo "lock from deps branch" > package-lock.json && git commit -qam "Update deps"
git switch -q main && echo "lock from main" > package-lock.json && git commit -qam "Other update"
git merge -q deps >/dev/null 2>&1
git checkout -q --theirs package-lock.json
cat package-lock.json
git add package-lock.json && git commit -q --no-edit && echo "merged with their lock file (then run npm install to regenerate)"
```

```text output
lock from deps branch
merged with their lock file (then run npm install to regenerate)
```

<Happened>
<Tr>
<En>

- `package-lock.json` changed differently on both branches, so the merge conflicted. Lock files are huge, machine-made files, and fixing them by hand is a bad idea.
- `--theirs` replaced the whole file with the `deps` version; `cat` confirms it.
- `git add` + `git commit` completed the merge.

The safest real-world approach for lock files: take one side, then run `npm install` (or `pnpm install`, `poetry lock`…) so the tool regenerates the lock file correctly, and commit that.

</En>
<Ur>

- `package-lock.json` dono branches par alag badli, isliye merge me conflict aaya. Lock files bohot bari, machine ki banayi files hain, aur unhe haath se theek karna bura khayal hai.
- `--theirs` ne poori file `deps` wale version se badal di; `cat` tasdeeq karta hai.
- `git add` + `git commit` ne merge mukammal kiya.

Lock files ke liye asal duniya ka sab se mehfooz tareeqa: ek taraf lo, phir `npm install` (ya `pnpm install`, `poetry lock`…) chalao taa ke tool lock file durust dobara banaye, aur wo commit karo.

</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>**During a rebase, ours and theirs are swapped.** "Ours" is the branch you're rebasing onto (for example `main`), and "theirs" is your own commit being replayed.</En>
<Ur>**Rebase ke doran ours aur theirs ulat jate hain.** "Ours" wo branch hai jis par aap rebase kar rahe hain (maslan `main`), aur "theirs" aap ka apna commit jo dobara chal raha hai.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Abort safely">

<Tr>
<En>

`git merge --abort` (also `rebase --abort`, `cherry-pick --abort`) returns everything to exactly how it was before you started. Use it when the conflict is bigger than expected, or you merged the wrong branch. `git status` tells you which operation is in progress. Commit or stash your own changes before merging, so abort can restore everything cleanly.

</En>
<Ur>

`git merge --abort` (aur `rebase --abort`, `cherry-pick --abort`) sab kuch bilkul waisa kar deta hai jaisa shuru se pehle tha. Jab conflict umeed se bara ho, ya ghalat branch merge ho gayi ho, tab istemal karein. `git status` batata hai kaunsa amal jari hai. Merge se pehle apni tabdeeliyan commit ya stash karein, taa ke abort sab saaf wapas kar sake.

</Ur>
</Tr>

```bash
git init -q ab && cd ab
echo "a" > f && git add . && git commit -qm "A"
git switch -q -c x && echo "x" > f && git commit -qam "X"
git switch -q main && echo "m" > f && git commit -qam "M"
git merge -q x >/dev/null 2>&1
git status | grep -m1 -o 'You have unmerged paths'
git merge --abort
echo "after abort: f=$(cat f); status lines: $(git status -s | wc -l)"
```

```text output
You have unmerged paths
after abort: f=m; status lines: 0
```

<Happened>
<Tr>
<En>Both branches changed `f`, so the merge stopped (output hidden), and `git status` confirmed `You have unmerged paths`. After `git merge --abort`, `f` holds `main`'s `m` again and `git status -s` prints nothing: clean, as if we never started.</En>
<Ur>Dono branches ne `f` badli, to merge ruka (output chhupaya), aur `git status` ne `You have unmerged paths` ki tasdeeq ki. `git merge --abort` ke baad `f` me phir `main` ka `m` hai aur `git status -s` kuch nahi chhaapta: saaf, jaise kabhi shuru hi nahi kiya.</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>Not sure what you're doing? Abort, ask a teammate, and try again calmly. Abort is always safe.</En>
<Ur>Yaqeen nahi ke kya kar rahe hain? Abort karein, saathi se poochein, aur sukoon se dobara koshish karein. Abort hamesha mehfooz hai.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Conflicts during a rebase">

<Tr>
<En>

A rebase replays your commits **one at a time**, so you may resolve a conflict **for each commit**. The status says "You are currently rebasing". The steps differ slightly: fix → `git add` → `git rebase --continue` (**not** `git commit`). Repeat until it's done.

</En>
<Ur>

Rebase aap ke commits **ek ek kar ke** dobara chalata hai, isliye **har commit ke liye** conflict hal karna pad sakta hai. Status kehta hai "You are currently rebasing". Qadam thore alag hain: theek karo → `git add` → `git rebase --continue` (`git commit` **nahi**). Khatam hone tak dohrayen.

</Ur>
</Tr>

```bash
git init -q rb && cd rb
echo "title=Home" > page && git add . && git commit -qm "Base"
git switch -q -c feature && echo "title=Welcome Home" > page && git commit -qam "Better title"
git switch -q main && echo "title=Homepage" > page && git commit -qam "Rename title"
git switch -q feature
git rebase main >/dev/null 2>&1 || echo "conflict while replaying: $(git log -1 --format=%s REBASE_HEAD)"
echo "title=Welcome to the Homepage" > page
git add page
GIT_EDITOR=true git rebase --continue >/dev/null 2>&1
git log --format=%s
cat page
```

```text output
conflict while replaying: Better title
Better title
Rename title
Base
title=Welcome to the Homepage
```

<Happened>
<Tr>
<En>

- `feature` changed the title to "Welcome Home"; `main` changed the same line to "Homepage".
- The rebase stopped while replaying "Better title". `REBASE_HEAD` is the commit being replayed, so `git log -1 REBASE_HEAD` printed its message.
- We wrote a combined title that respects both intentions, `git add`ed it, and ran `git rebase --continue`. `GIT_EDITOR=true` accepted the message without an editor.
- History is linear, and the file has our resolved content.

If 5 commits all touch the conflicting lines, you may resolve up to 5 times in one rebase. Then a merge (one resolution) or squashing your commits first is easier.

</En>
<Ur>

- `feature` ne title "Welcome Home" kiya; `main` ne wahi line "Homepage" ki.
- Rebase "Better title" chalate hue ruka. `REBASE_HEAD` wo commit hai jo dobara chal raha hai, isliye `git log -1 REBASE_HEAD` ne us ka message chhaapa.
- Hum ne dono iraadon ka lihaaz rakhta milaa jula title likha, `git add` kiya, aur `git rebase --continue` chalaya. `GIT_EDITOR=true` ne editor ke baghair message maan liya.
- Tareekh seedhi hai, aur file me hamara hal shuda mawad hai.

Agar 5 commits sab conflict wali lines chhuyen, to ek rebase me 5 dafa tak hal karna pad sakta hai. Tab merge (ek dafa hal) ya pehle commits squash karna aasaan hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Delete/modify conflicts">

<Tr>
<En>

One branch deleted a file while the other changed it, so Git can't decide whether the file should exist. It happens in refactors that move or remove files. Status shows `deleted by us` or `deleted by them`. To keep it: `git add file`. To remove it: `git rm file`. Then commit.

</En>
<Ur>

Ek branch ne file mita di jab ke doosri ne use badla, isliye Git tay nahi kar sakta file honi chahiye ya nahi. Ye files hatane ya muntaqil karne wale refactors me hota hai. Status `deleted by us` ya `deleted by them` dikhata hai. Rakhni hai: `git add file`. Hatani hai: `git rm file`. Phir commit.

</Ur>
</Tr>

```bash
git init -q dm && cd dm
echo "old helper" > helper.js && git add . && git commit -qm "Add helper"
git switch -q -c cleanup && git rm -q helper.js && git commit -qm "Remove unused helper"
git switch -q main && echo "used helper" > helper.js && git commit -qam "Improve helper"
git merge -q cleanup 2>&1 | grep CONFLICT | sed 's/ Version.*//; s/ *$//'
git status -s
git rm -q helper.js && git commit -q --no-edit && echo "resolved: file removed"
```

```text output
CONFLICT (modify/delete): helper.js deleted in cleanup and modified in HEAD.
UD helper.js
resolved: file removed
```

<Happened>
<Tr>
<En>`cleanup` deleted `helper.js`; `main` modified it. The merge reported `CONFLICT (modify/delete)`, and `UD` means **U**pdated by us (main), **D**eleted by them (cleanup). We decided it really is unused, so `git rm` resolved it by deleting. To keep `main`'s version instead, you'd run `git add helper.js`.</En>
<Ur>`cleanup` ne `helper.js` mitayi; `main` ne use badla. Merge ne `CONFLICT (modify/delete)` bataya, aur `UD` ka matlab hum ne **U**pdate ki (main), unhon ne **D**elete ki (cleanup). Hum ne tay kiya ye waqai bekaar hai, isliye `git rm` ne mita kar hal kiya. `main` ka version rakhna ho to `git add helper.js` chalate.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Better markers: the zdiff3 style">

<Tr>
<En>

With `merge.conflictStyle=zdiff3`, Git also shows the **original (base)** text between `|||||||` and `=======`. Seeing what the line was **before** tells you what each side intended, which makes decisions much easier. Set it once: `git config --global merge.conflictStyle zdiff3` (Git 2.35+; use `diff3` on older versions).

</En>
<Ur>

`merge.conflictStyle=zdiff3` ke saath Git `|||||||` aur `=======` ke beech **asal (base)** text bhi dikhata hai. Line **pehle** kya thi ye dekh kar pata chalta hai har taraf ka iraada kya tha, jis se faisle bohot aasaan hote hain. Ek dafa set karein: `git config --global merge.conflictStyle zdiff3` (Git 2.35+; purane versions par `diff3`).

</Ur>
</Tr>

```bash

git init -q z && cd z
echo "timeout=30" > cfg && git add . && git commit -qm "Base"
git switch -q -c a && echo "timeout=60" > cfg && git commit -qam "A"
git switch -q main && echo "timeout=10" > cfg && git commit -qam "M"
git merge -q a >/dev/null 2>&1

```

||||||| <base commit>

>>>>>>> a

<Happened>
<Tr>
<En>

</En>

Base `timeout=30` tha; `main` ne ise 10 kiya aur branch `a` ne 60. Ab conflict ke **teen** hisse hain: ours (10), **asal** base (30), aur theirs (60). `sed` sirf base hash chhupata hai. Aakhri do lines safai karti hain taa ke doosri misaalen default andaaz istemal karen.

<Step title="rerere, tools and habits">

<Tr>
<En>

- **rerere** ("**re**use **re**corded **re**solution") remembers how you resolved a conflict and applies it automatically the next time the same conflict appears, which helps when you rebase a long branch again and again. Turn it on with `git config --global rerere.enabled true`, and still review the result.
- **Tools:** VS Code (including its 3-way merge editor), JetBrains IDEs, `git mergetool`, and GitHub's web conflict editor for simple cases are faster and less error-prone than editing markers by hand.
- **Prevention:** small PRs, pull or rebase often, don't reformat whole files in feature branches, and talk to teammates working in the same area.

</En>
<Ur>

- **rerere** ("**re**use **re**corded **re**solution") yaad rakhta hai aap ne conflict kaise hal kiya aur agli dafa wahi conflict aaye to khud laga deta hai, jo lambi branch ko baar baar rebase karte hue madad karta hai. `git config --global rerere.enabled true` se on karein, aur phir bhi nateeja check karein.
- **Tools:** VS Code (us ka 3-way merge editor samet), JetBrains IDEs, `git mergetool`, aur saade cases ke liye GitHub ka web conflict editor haath se nishan badalne se tez aur kam ghalti wale hain.
- **Bachao:** chhote PRs, aksar pull ya rebase, feature branches me poori files reformat na karein, aur ek hi hisse par kaam karne wale saathiyon se baat karein.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Conflict = same lines changed on both sides (or modify vs delete). It's normal.
- Ours = current branch (HEAD); theirs = incoming. **Swapped in a rebase.**
- Understand both changes first: `git log --merge`.

- Turn on zdiff3; consider rerere; keep PRs small to avoid conflicts.

<DeepDive title="Real world: the rate limit that almost vanished">

Two developers update `routes.js` on the same day: one adds a `/reports` route, the other adds rate limiting to all routes. The second PR shows "This branch has conflicts". The developer runs `git fetch && git rebase origin/main` and sees the conflict with zdiff3 markers. The base shows the original route list, so she realises the correct result is **both**: the new route **with** rate limiting. She edits, runs the test suite, `git rebase --continue`, and pushes with `--force-with-lease`. A careless "Accept Current" would have silently removed rate limiting from the new endpoint, a real security bug.

</DeepDive>

<DeepDive title="Security lens">

Conflict resolution is unreviewed code: the merge commit's changes often get far less attention than the PR itself.

- Security checks (input validation, auth middleware, rate limits) are classic victims of a bad resolution; re-check them.
- Re-run CI, including SAST and tests, after resolving. Never bypass required checks "because it's only a merge".
- Add a CI or pre-commit check that fails on leftover conflict markers.
- For sensitive files (CI workflows, auth, infrastructure), ask the CODEOWNER to review the resolution.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What causes a merge conflict and how do you resolve one?">
A conflict occurs when two branches change the same lines of a file differently, or one modifies a file the other deletes, so Git cannot combine them automatically. I check git status for unmerged files, open each one, understand both changes using the conflict markers and the commit history, edit the file into the correct final version without markers, git add it, run the tests, and then commit the merge or continue the rebase.
</QA>

<QA q="What do ours and theirs mean, and how do they differ in a rebase?">
In a merge, ours is the current branch and theirs is the branch being merged in. During a rebase the roles are reversed from the user's point of view: ours is the branch being rebased onto, such as main, and theirs is the commit from your branch that is being replayed.
</QA>

<QA q="How can a team reduce merge conflicts?">
Keep branches short-lived and pull requests small, integrate changes from main frequently, avoid large formatting-only changes mixed with features, use consistent automatic formatters, split very large files, and communicate when several people work on the same area.
</QA>

</DeepDive>

<DeepDive title="More practice">

1. Create a conflict on one line, resolve it by hand, and commit the merge.
2. Create the same conflict during a rebase and resolve it with `--continue`.
3. Use `git checkout --theirs` for one file and `--ours` for another.
4. Enable zdiff3 and compare its markers with the default style.
5. Write a tiny script that fails if any tracked file contains conflict markers.
