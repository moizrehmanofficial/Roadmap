<BigIdea>
<Tr>
<En>
**`git rebase main`** takes your branch's commits and **replays** them on top of the latest `main`. The result is **new commits** with new hashes and a straight, linear history. **Interactive rebase** (`git rebase -i`) lets you **squash**, **reword**, **reorder** or **drop** commits before you share them, and **`git cherry-pick`** copies one commit onto another branch. The golden rule: **never rewrite commits other people already have**. If anything goes wrong, **`git rebase --abort`** or **`git reflog`** brings you back.
</En>
<Ur>
**`git rebase main`** aap ki branch ke commits le kar unhe taaza `main` ke upar **dobara chalata** hai. Nateeja **naye commits** hain, naye hashes ke saath, aur ek seedhi tareekh. **Interactive rebase** (`git rebase -i`) share karne se pehle commits ko **squash**, **reword**, **reorder** ya **drop** karne deta hai, aur **`git cherry-pick`** ek commit doosri branch par copy karta hai. Sunehra qaida: **jo commits doosron ke paas pahunch chuke hon unhe kabhi dobara na likho**. Kuch ghalat ho jaye to **`git rebase --abort`** ya **`git reflog`** wapas le aata hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Rebasing and amending **rewrite history**: they create new commits to replace old ones. The old commits aren't deleted immediately; they're just no longer pointed to by a branch, and stay reachable through the reflog for a while.

```text
before:  Base ── Hotfix (main)          after rebase:  Base ── Hotfix ── step1' ── step2'
            └── step1 ── step2 (feature)                       (main)        (feature)
```

</En>
<Ur>

Rebase aur amend **tareekh dobara likhte** hain: purane commits ki jagah naye banate hain. Purane commits foran nahi mit-te; bas ab koi branch un ki taraf ishara nahi karti, aur wo kuch arse tak reflog ke zariye mil sakte hain.

```text
before:  Base ── Hotfix (main)          after rebase:  Base ── Hotfix ── step1' ── step2'
            └── step1 ── step2 (feature)                       (main)        (feature)
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Look at two histories of the same feature. History 1: "wip", "fix", "Merge main into feature", "fix again", "Merge main into feature", "final". History 2: "Add profile page", "Add avatar upload". Both contain the same code, but only the second helps a reviewer, or a developer reading the history a year later. Rebasing is how you turn the first into the second **before** you share it.

- **Clean, linear history** that's easy to read, search (bisect) and revert.
- **Tidy PRs:** reviewers see logical commits instead of "wip", "fix", "fix again".
- **Up-to-date branches** without dozens of "Merge main into feature" commits.
- Open-source projects often require a clean commit series.

</En>
<Ur>

Ek hi feature ki do tareekhen dekhein. Pehli: "wip", "fix", "Merge main into feature", "fix again", "Merge main into feature", "final". Doosri: "Add profile page", "Add avatar upload". Dono me code ek jaisa hai, lekin sirf doosri reviewer ki, ya saal baad tareekh parhne wale developer ki madad karti hai. Rebase se aap share karne se **pehle** pehli ko doosri bana dete hain.

- **Saaf, seedhi tareekh** jo parhna, dhoondhna (bisect) aur revert karna aasaan ho.
- **Saaf PRs:** reviewer "wip", "fix", "fix again" ke bajaye mantiqi commits dekhta hai.
- **Taaza branches**, darjanon "Merge main into feature" commits ke baghair.
- Open-source projects aksar saaf commits ka silsila maangte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- Updating **your own** feature branch with the latest `main`.
- Cleaning up commits **before** opening (or merging) a PR.
- **Never** on `main` or any branch others have built work on.

</En>
<Ur>

- **Apni** feature branch ko taaza `main` se update karna.
- PR kholne (ya merge) se **pehle** commits saaf karna.
- `main` ya kisi aisi branch par **kabhi nahi** jis par doosron ne kaam banaya ho.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
git rebase main                    # replay my branch on top of main
git rebase -i main                 # edit the commit list first
git commit --fixup=<hash>          # mark a fix for an earlier commit
git cherry-pick -x <hash>          # copy one commit here
git push --force-with-lease        # update my own rewritten branch
git rebase --abort / git reflog    # escape hatches
```

</En>
<Ur>

```text
git rebase main                    # meri branch main ke upar dobara
git rebase -i main                 # pehle commits ki list badlo
git commit --fixup=<hash>          # pehle commit ke liye fix ka nishan
git cherry-pick -x <hash>          # ek commit yahan copy
git push --force-with-lease        # apni dobara likhi branch update
git rebase --abort / git reflog    # bachne ke raaste
```

</Ur>
</Tr>
</How>
</Glance>

## Learn it step by step

<Walkthrough>

<Step title="Rebase vs merge">

<Tr>
<En>

Both bring `main`'s changes into your branch. **Merge** adds a merge commit and keeps exactly what happened. **Rebase** rewrites your commits so they sit on top of `main`, giving a straight line. Your commits get **new hashes** because their parent changed. Run `git rebase main` while you're on your feature branch.

</En>
<Ur>

Dono `main` ki tabdeeliyan aap ki branch me laate hain. **Merge** merge commit jorta hai aur bilkul wahi rakhta hai jo hua. **Rebase** aap ke commits dobara likhta hai taa ke wo `main` ke upar baithen, seedhi line bana kar. Aap ke commits ko **naye hashes** milte hain kyun ke un ka parent badal gaya. Apni feature branch par hote hue `git rebase main` chalayen.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q app && cd app
echo base > base.txt && git add . && git commit -qm "Base"
git switch -q -c feature
echo a > a.txt && git add . && git commit -qm "Feature step 1"
echo b > b.txt && git add . && git commit -qm "Feature step 2"
git switch -q main
echo fix > fix.txt && git add . && git commit -qm "Hotfix on main"
git switch -q feature
old=$(git rev-parse --short HEAD)
git rebase -q main
new=$(git rev-parse --short HEAD)
[ "$old" != "$new" ] && echo "tip commit got a new hash after rebase"
git log --graph --format=%s
```

```text output
tip commit got a new hash after rebase
* Feature step 2
* Feature step 1
* Hotfix on main
* Base
```

<Happened>
<Tr>
<En>

- `feature` got two commits; meanwhile `main` got "Hotfix on main", so the branches **diverged**.
- We saved the tip hash in `old`, then `git rebase main` did three things: (1) set our two commits aside, (2) moved `feature` to the tip of `main`, (3) re-applied our commits one by one on top.
- `new` differs from `old`: same changes and message, but a different parent, so it's a **new** commit.
- The graph is now a straight line, and merging `feature` into `main` would be a simple fast-forward.

**Rebase or merge?** Both are correct. Rebase gives a cleaner history; merge never rewrites anything. Many teams rebase their own feature branches and merge (or squash) into `main`.

</En>
<Ur>

- `feature` par do commits aaye; isi doran `main` par "Hotfix on main" aaya, to branches **alag ho gayin**.
- Hum ne tip hash `old` me rakha, phir `git rebase main` ne teen kaam kiye: (1) hamare do commits side par rakhe, (2) `feature` ko `main` ki nok par le gaya, (3) hamare commits ek ek kar ke upar dobara lagaye.
- `new` `old` se alag hai: wahi tabdeeliyan aur message, lekin parent alag, isliye ye **naya** commit hai.
- Graph ab seedhi line hai, aur `feature` ko `main` me merge karna seedha fast-forward hoga.

**Rebase ya merge?** Dono durust hain. Rebase saaf tareekh deta hai; merge kabhi kuch dobara nahi likhta. Bohot si teams apni feature branches rebase karti hain aur `main` me merge (ya squash) karti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="When a rebase hits a conflict">

<Tr>
<En>

If a replayed commit touches lines that also changed on `main`, the rebase **stops** at that commit, because Git can't guess which version you want. `git status` shows the conflicted file. You then have three choices: fix the file → `git add file` → `git rebase --continue`; `git rebase --skip` (drop this commit); or `git rebase --abort` (go back to exactly how things were).

</En>
<Ur>

Agar dobara lagaya gaya commit un lines ko chhuye jo `main` par bhi badli, to rebase us commit par **ruk jata** hai, kyun ke Git andaza nahi laga sakta aap kaunsa version chahte hain. `git status` conflict wali file dikhata hai. Phir aap ke teen raaste hain: file theek karo → `git add file` → `git rebase --continue`; `git rebase --skip` (ye commit chhor do); ya `git rebase --abort` (bilkul pehle jaisa wapas).

</Ur>
</Tr>

```bash
git init -q c && cd c
echo "color=blue" > config && git add . && git commit -qm "Base config"
git switch -q -c feature && echo "color=green" > config && git commit -qam "Use green"
git switch -q main && echo "color=red" > config && git commit -qam "Use red"
git switch -q feature
git rebase main >/dev/null 2>&1 || echo "rebase stopped: conflict"
git status -s
git rebase --abort
echo "after abort, config is: $(cat config); branch: $(git branch --show-current)"
```

```text output
rebase stopped: conflict
UU config
after abort, config is: color=green; branch: feature
```

<Happened>
<Tr>
<En>

- `feature` changed `color=blue` to `green`, and `main` changed the **same line** to `red`.
- Replaying "Use green" on top of "Use red" hit a conflict, so the rebase stopped and returned an error code (`|| echo` printed our message).
- `UU config` = **U**nmerged on both sides: the file needs your decision.
- `git rebase --abort` cancelled everything: branch, files and history are exactly as before.

Resolving conflicts step by step is its own lesson, **Resolving Merge Conflicts**.

</En>
<Ur>

- `feature` ne `color=blue` ko `green` kiya, aur `main` ne **wahi line** `red` ki.
- "Use red" ke upar "Use green" lagane me conflict aaya, to rebase ruka aur error code diya (`|| echo` ne hamara message chhaapa).
- `UU config` = dono taraf **U**nmerged: file ko aap ka faisla chahiye.
- `git rebase --abort` ne sab radd kar diya: branch, files aur tareekh bilkul pehle jaisi.

Conflicts qadam ba qadam hal karna alag sabaq hai, **Resolving Merge Conflicts**.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Interactive rebase: clean up before sharing">

<Tr>
<En>

`git rebase -i <base>` opens a list of your commits, oldest first. You change the word in front of each line to decide what happens: `pick` (keep), `reword` (change the message), `squash` (combine, keep both messages), `fixup` (combine, drop this message), `drop` (remove), and you reorder by moving lines. Use it before opening or merging a PR, with `git rebase -i main` or `git rebase -i HEAD~4`.

The editor shows something like:

```text
pick 1a2b3c4 Add search box
pick 5d6e7f8 fix typo
pick 9a8b7c6 wip
pick 3c4d5e6 Add results list
```

You edit it to:

```text
pick 1a2b3c4 Add search box
fixup 5d6e7f8 fix typo
fixup 9a8b7c6 wip
pick 3c4d5e6 Add results list
```

</En>
<Ur>

`git rebase -i <base>` aap ke commits ki list kholta hai, purane pehle. Har line ke aage ka lafz badal kar aap tay karte hain kya hoga: `pick` (rakho), `reword` (message badlo), `squash` (milao, dono messages rakho), `fixup` (milao, ye message phenko), `drop` (hatao), aur lines upar neeche kar ke tarteeb badalte hain. PR kholne ya merge se pehle `git rebase -i main` ya `git rebase -i HEAD~4` se istemal karein.

Editor kuch aisa dikhata hai:

```text
pick 1a2b3c4 Add search box
pick 5d6e7f8 fix typo
pick 9a8b7c6 wip
pick 3c4d5e6 Add results list
```

Aap ise aisa badalte hain:

```text
pick 1a2b3c4 Add search box
fixup 5d6e7f8 fix typo
fixup 9a8b7c6 wip
pick 3c4d5e6 Add results list
```

</Ur>
</Tr>

<Tr>
<En>Below, `GIT_SEQUENCE_EDITOR` makes that same edit automatically, so the example runs without an editor:</En>
<Ur>Neeche `GIT_SEQUENCE_EDITOR` yahi tabdeeli khud kar deta hai, taa ke misaal editor ke baghair chale:</Ur>
</Tr>

```bash
git init -q s && cd s
git commit -q --allow-empty -m "Start"
for m in "Add search box" "fix typo" "wip" "Add results list"; do echo "$m" >> search.txt; git add .; git commit -qm "$m"; done
GIT_SEQUENCE_EDITOR="sed -i -e 's/^pick \(.*\) fix typo/fixup \1 fix typo/' -e 's/^pick \(.*\) wip/fixup \1 wip/'" git rebase -q -i HEAD~4
git log --format=%s
echo "content kept: $(wc -l < search.txt) lines"
```

```text output
Add results list
Add search box
Start
content kept: 4 lines
```

<Happened>
<Tr>
<En>

- The loop made two real commits and two messy ones ("fix typo", "wip").
- The `sed` command changed `pick` to `fixup` on the messy lines, exactly what you'd type by hand.
- `fixup` means "melt this commit into the one above it and throw away its message", so both were folded into "Add search box".
- Result: 2 clean commits instead of 4, and `search.txt` still has all 4 lines. No code was lost, only the noisy history.

</En>
<Ur>

- Loop ne do asli aur do ganday commits banaye ("fix typo", "wip").
- `sed` command ne ganday lines par `pick` ko `fixup` kiya, bilkul wahi jo aap haath se likhte.
- `fixup` ka matlab "is commit ko upar wale me ghol do aur is ka message phenk do", isliye dono "Add search box" me mil gaye.
- Nateeja: 4 ke bajaye 2 saaf commits, aur `search.txt` me ab bhi chaaron lines. Koi code nahi khoya, sirf shor wali tareekh.

</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>Normally you just run `git rebase -i HEAD~4`, edit the words, save and close; Git does the rest. To use VS Code as the editor: `git config --global core.editor "code --wait"`.</En>
<Ur>Aam tor par aap bas `git rebase -i HEAD~4` chalate hain, lafz badalte hain, save kar ke band karte hain; baqi Git karta hai. VS Code ko editor banane ke liye: `git config --global core.editor "code --wait"`.</Ur>
</Tr>
</Callout>

<Step title="Fixup commits and autosquash">

<Tr>
<En>

A reviewer says "please fix the variable name in your first commit". `git commit --fixup=<hash>` creates a commit named "fixup! original message", and `git rebase -i --autosquash` moves it into place and squashes it automatically. No manual list editing. `git config --global rebase.autoSquash true` makes it the default.

</En>
<Ur>

Reviewer kehta hai "apne pehle commit me variable ka naam theek karo". `git commit --fixup=<hash>` "fixup! original message" naam ka commit banata hai, aur `git rebase -i --autosquash` use sahi jagah le ja kar khud squash kar deta hai. List haath se badalne ki zaroorat nahi. `git config --global rebase.autoSquash true` ise default bana deta hai.

</Ur>
</Tr>

```bash
git init -q f && cd f
git commit -q --allow-empty -m "Start"
echo "let nmae" > user.js && git add . && git commit -qm "Add user module"
echo "x" > other.js && git add . && git commit -qm "Add other module"
echo "let name" > user.js && git add . && git commit -q --fixup=HEAD~1
git log --format=%s | head -1
GIT_SEQUENCE_EDITOR=true git rebase -q -i --autosquash HEAD~3
git log --format=%s
cat user.js
```

```text output
fixup! Add user module
Add other module
Add user module
Start
let name
```

<Happened>
<Tr>
<En>

- "Add user module" had a typo (`nmae`), and another commit came after it.
- After fixing the file, `--fixup=HEAD~1` made a commit called `fixup! Add user module`: a note saying "this belongs to that commit".
- `--autosquash` moved it right under "Add user module" and marked it `fixup`. `GIT_SEQUENCE_EDITOR=true` accepted the list without opening an editor.
- Now "Add user module" already contains the fix, and `user.js` says `let name`.

</En>
<Ur>

- "Add user module" me typo tha (`nmae`), aur us ke baad ek aur commit tha.
- File theek karne ke baad `--fixup=HEAD~1` ne `fixup! Add user module` naam ka commit banaya: ek parchi ke "ye us commit ka hai".
- `--autosquash` ne use "Add user module" ke theek neeche rakha aur `fixup` lagaya. `GIT_SEQUENCE_EDITOR=true` ne editor khole baghair list maan li.
- Ab "Add user module" me fix pehle se shamil hai, aur `user.js` me `let name` hai.

</Ur>
</Tr>
</Happened>

<Step title="Amend: fix the last commit">

<Tr>
<En>

`git commit --amend` replaces the last commit with a new one: a new message and/or extra staged changes. Forgot a file? Typo in the message? Amend it, before pushing (or on your own branch with force-with-lease). `--no-edit` keeps the message. It's a rewrite, so the commit gets a new hash.

</En>
<Ur>

`git commit --amend` aakhri commit ko naye se badal deta hai: naya message aur/ya izafi staged tabdeeliyan. File bhool gaye? Message me typo? Push se pehle amend karein (ya apni branch par force-with-lease ke saath). `--no-edit` message wahi rakhta hai. Ye dobara likhna hai, isliye commit ko naya hash milta hai.

</Ur>
</Tr>

```bash
git init -q am && cd am
echo code > app.py && git add . && git commit -qm "Add app"
echo "# tests" > test_app.py && git add test_app.py
git commit -q --amend --no-edit
git show --stat --format=%s HEAD | awk 'NF' | sed -E 's/ +\| +/ | /'
```

```text output
Add app
 app.py | 1 +
 test_app.py | 1 +
 2 files changed, 2 insertions(+)
```

<Happened>
<Tr>
<En>"Add app" was committed with only `app.py`, and we forgot the test. After `git add test_app.py`, `--amend --no-edit` added it to the **last** commit with the same message. `git show --stat` confirms both files are in "Add app", with no separate "add forgotten file" commit.</En>
<Ur>"Add app" sirf `app.py` ke saath commit hua, aur test bhool gaye. `git add test_app.py` ke baad `--amend --no-edit` ne use **aakhri** commit me usi message ke saath jor diya. `git show --stat` tasdeeq karta hai dono files "Add app" me hain, koi alag "bhooli file jori" commit nahi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Cherry-pick: copy one commit">

<Tr>
<En>

`git cherry-pick <hash>` applies the changes of **one** commit onto the current branch as a new commit. It's how you bring a single fix to a release branch without merging everything else, for example backporting a security fix to an older version. `-x` adds "(cherry picked from commit …)" to the message for traceability. For whole features, merge instead.

</En>
<Ur>

`git cherry-pick <hash>` **ek** commit ki tabdeeliyan mojooda branch par naye commit ke tor par lagata hai. Isi tarah aap baqi sab merge kiye baghair sirf ek fix release branch par laate hain, maslan security fix purane version me pahunchana (backport). `-x` message me "(cherry picked from commit …)" jorta hai taa ke asal pata chale. Poore features ke liye merge karein.

</Ur>
</Tr>

```bash
git init -q cp && cd cp
echo v1 > app && git add . && git commit -qm "Release 1.0" && git branch release-1.0
echo feature > big.txt && git add . && git commit -qm "Big new feature"
echo patched > security.txt && git add . && git commit -qm "Fix XSS in search"
fix=$(git rev-parse HEAD)
git switch -q release-1.0
git cherry-pick -x "$fix" >/dev/null
git log --format=%s
ls
git log -1 --format=%b | sed -E 's/[0-9a-f]{40}/<hash>/'
```

```text output
Fix XSS in search
Release 1.0
app
security.txt
(cherry picked from commit <hash>)
```

<Happened>
<Tr>
<En>

- `main` went on with "Big new feature" (not ready for old customers) and "Fix XSS in search" (needed by everyone).
- On `release-1.0`, cherry-pick copied **only** the security fix: `ls` shows `security.txt` but no `big.txt`.
- Thanks to `-x`, the message ends with `(cherry picked from commit <hash>)`, so anyone can trace where the fix came from.

</En>
<Ur>

- `main` "Big new feature" (purane customers ke liye tayyar nahi) aur "Fix XSS in search" (sab ko chahiye) ke saath aage barhi.
- `release-1.0` par cherry-pick ne **sirf** security fix copy kiya: `ls` me `security.txt` hai lekin `big.txt` nahi.
- `-x` ki wajah se message `(cherry picked from commit <hash>)` par khatam hota hai, taa ke koi bhi fix ka asal dhoondh sake.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The golden rule and force-with-lease">

<Tr>
<En>

**Never rewrite commits others have pulled.** Rewritten commits are different commits, so teammates' copies diverge and work can be lost. After rewriting **your own** pushed branch, update it with `git push --force-with-lease`. Unlike plain `--force`, which overwrites blindly, it refuses if the server has commits you haven't seen. And protect `main` so force pushes are impossible there.

</En>
<Ur>

**Jo commits doosre pull kar chuke hon unhe kabhi dobara na likho.** Dobara likhe commits alag commits hain, isliye saathiyon ki copies alag ho jati hain aur kaam kho sakta hai. **Apni** push shuda branch dobara likhne ke baad use `git push --force-with-lease` se update karein. Saada `--force` andha dhund mita deta hai, jab ke ye inkaar karta hai agar server par aise commits hon jo aap ne nahi dekhe. Aur `main` ko protect karein taa ke wahan force push na ho sake.

</Ur>
</Tr>

```bash
git init -q --bare server.git
git clone -q server.git me 2>/dev/null && cd me
git commit -q --allow-empty -m "Start" && git push -q -u origin main
git switch -q -c feature && git commit -q --allow-empty -m "My work" && git push -q -u origin feature
# a teammate pushes to the same branch
git clone -q ../server.git ../mate && cd ../mate && git switch -q feature && git commit -q --allow-empty -m "Teammate fix" && git push -q
cd ../me
git commit -q --amend --allow-empty -m "My work (reworded)"
git push -q --force-with-lease 2>&1 | grep -o 'stale info' | sed 's/^/rejected: /'
git fetch -q && git log --format=%s origin/feature | head -1 | sed 's/^/remote still has: /'
```

```text output
rejected: stale info
remote still has: Teammate fix
```

<Happened>
<Tr>
<En>

- We pushed `feature`; a teammate then added "Teammate fix" to the same branch and pushed.
- Not knowing that, we amended our commit (rewriting history) and tried to push.
- `--force-with-lease` means "overwrite **only if** the server still has what I last saw". It had a commit we hadn't seen, so the push was rejected with `stale info`.
- The server still has "Teammate fix". With plain `--force`, it would have vanished.

</En>
<Ur>

- Hum ne `feature` push ki; phir saathi ne usi branch par "Teammate fix" jor kar push kiya.
- Ye jaane baghair hum ne apna commit amend kiya (tareekh dobara likhi) aur push ki koshish ki.
- `--force-with-lease` ka matlab "mita kar likho **sirf agar** server par ab bhi wahi hai jo main ne aakhri dafa dekha". Wahan aisa commit tha jo hum ne nahi dekha, isliye push `stale info` ke saath radd hua.
- Server par ab bhi "Teammate fix" hai. Saade `--force` se wo ghayab ho jata.

</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>**Rule of thumb:** rebasing a branch only you use is fine. Rebasing a branch someone else also commits to needs coordination first.</En>
<Ur>**Aam qaida:** aisi branch rebase karna jo sirf aap istemal karte hain theek hai. Jis branch par koi aur bhi commit karta ho, use rebase karne se pehle baat kar lein.</Ur>
</Tr>
</Callout>

<Step title="Recover with ORIG_HEAD and reflog">

<Tr>
<En>

Rebases and amends never destroy commits immediately, so you can always go back. Git saves the position before a rebase or merge in **`ORIG_HEAD`**, and the **reflog** records every position HEAD has been at (commits, rebases, resets) for about 90 days. Find the entry from before the mistake and reset to it.

</En>
<Ur>

Rebase aur amend commits foran tabah nahi karte, isliye aap hamesha wapas ja sakte hain. Git rebase ya merge se pehle ki jagah **`ORIG_HEAD`** me rakhta hai, aur **reflog** HEAD ki har jagah (commits, rebases, resets) takreeban 90 din tak record karta hai. Ghalti se pehle wali entry dhoondhein aur us par reset karein.

</Ur>
</Tr>

```bash
git init -q r && cd r
for m in one two three; do echo "$m" > "$m.txt"; git add .; git commit -q -m "$m"; done
GIT_SEQUENCE_EDITOR="sed -i '/ two$/d'" git rebase -q -i HEAD~2   # oops: dropped "two"
git log --format=%s | tr '\n' ' '; echo
git reset -q --hard ORIG_HEAD
git log --format=%s | tr '\n' ' '; echo
```

```text output
three one 
three two one 
```

<Happened>
<Tr>
<En>The interactive rebase deleted the line for "two", so "two" was dropped and the log showed "three one". `git reset --hard ORIG_HEAD` moved the branch back to where it was before the rebase, and "two" is back.</En>
<Ur>Interactive rebase ne "two" ki line mita di, to "two" gir gaya aur log ne "three one" dikhaya. `git reset --hard ORIG_HEAD` ne branch ko rebase se pehle wali jagah wapas kiya, aur "two" laut aaya.</Ur>
</Tr>
</Happened>

<Tr>
<En>

For older mistakes, run `git reflog`. Each line looks like `a1b2c3d HEAD@{3}: rebase (start): checkout main`. Find the line from **before** the mistake, then run `git reset --hard HEAD@{3}`, or `git switch -c rescue HEAD@{3}` to look first.

</En>
<Ur>

Purani ghaltiyon ke liye `git reflog` chalayen. Har line aisi hoti hai: `a1b2c3d HEAD@{3}: rebase (start): checkout main`. Ghalti se **pehle** wali line dhoondhein, phir `git reset --hard HEAD@{3}` chalayen, ya pehle dekhne ke liye `git switch -c rescue HEAD@{3}`.

</Ur>
</Tr>

</Step>

## Common mistakes

<Compare>
<Bad title="Rewrite a shared branch and force it">

```text
git switch main
git rebase -i HEAD~5      # rewriting commits everyone already has
git push --force          # teammates' commits can vanish
```

</Bad>
<Good title="Rewrite only your own branch, push with a lease">

```text
git switch feature/profile
git fetch && git rebase origin/main
git rebase -i origin/main
git push --force-with-lease
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Panicking mid-rebase:** `git status` tells you exactly where you are, and `--abort` always works.
- **Squashing everything into one giant commit**, losing useful history.
- **Cherry-picking whole features commit by commit** instead of merging.
- **Forgetting that rebased commits are new:** CI runs again and signatures must be redone.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Rebase ke beech ghabrana:** `git status` bilkul batata hai aap kahan hain, aur `--abort` hamesha chalta hai.
- **Sab kuch ek bohot bare commit me squash karna**, kaam ki tareekh kho dena.
- **Poore features commit ba commit cherry-pick karna** merge ke bajaye.
- **Bhoolna ke rebase shuda commits naye hain:** CI dobara chalta hai aur signatures dobara karne padte hain.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Rebase replays your commits on a new base: new hashes, straight history.
- Merge keeps history as it happened; rebase rewrites it.
- Conflict mid-rebase: fix → `git add` → `--continue`, or `--abort`.
- `git rebase -i`: pick, reword, squash, fixup, drop, reorder.
- `--fixup` + `--autosquash` answer review comments cleanly.
- `--amend` fixes the last commit; `cherry-pick -x` copies one commit.
- Never rewrite shared history; use `--force-with-lease` on your own branch.
- `ORIG_HEAD` and `git reflog` undo almost any mistake.

</En>
<Ur>

- Rebase aap ke commits naye base par dobara chalata hai: naye hashes, seedhi tareekh.
- Merge tareekh jaisi hui waisi rakhta hai; rebase use dobara likhta hai.
- Rebase ke beech conflict: theek karo → `git add` → `--continue`, ya `--abort`.
- `git rebase -i`: pick, reword, squash, fixup, drop, reorder.
- `--fixup` + `--autosquash` review comments ka saaf jawab.
- `--amend` aakhri commit theek karta hai; `cherry-pick -x` ek commit copy karta hai.
- Saanjhi tareekh kabhi dobara na likho; apni branch par `--force-with-lease`.

<DeepDive title="Real world: a clean open-source contribution">

A maintainer asks a contributor to "rebase on main and squash the fixup commits". The contributor runs `git fetch upstream && git rebase upstream/main`, resolves one conflict, then `git rebase -i --autosquash upstream/main` to fold three review-fix commits into the commits they fix, and pushes with `git push --force-with-lease`. The PR now has two clean commits on top of the latest `main` and is merged with "Rebase and merge", so `main` stays perfectly linear.

</DeepDive>

<DeepDive title="Security lens">

History rewriting is powerful, and in an attacker's hands it can hide what changed. Protect important branches from force pushes.

- Enable "**Do not allow force pushes**" and "**Do not allow deletions**" on `main` and release branches.
- **Rewriting history doesn't remove a leaked secret** from clones, forks, caches or CI logs: rotate the secret first (see **Keeping Secrets Out of Git**).
- Rebased or cherry-picked commits lose their original signature; re-sign them (`git rebase --exec 'git commit --amend --no-edit -S'`, or sign by default).
- When backporting security fixes, `cherry-pick -x` keeps an audit trail from the release fix to the original commit.
- Review the **final diff** after a rebase: a conflict resolved wrongly can silently drop a security check.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between git merge and git rebase?">
Both integrate changes from one branch into another. Merge preserves history as it happened and adds a merge commit when histories have diverged. Rebase replays the current branch's commits on top of another base, creating new commits and a linear history without a merge commit. Rebase rewrites history, so it should only be used on commits that have not been shared with others.
</QA>

<QA q="What is the golden rule of rebasing?">
Never rebase or otherwise rewrite commits that exist outside your own repository and that other people may have based work on, such as main or a shared branch. Rewriting them creates different commits and forces everyone else to reconcile diverged histories.
</QA>

<QA q="Why use --force-with-lease instead of --force?">
--force overwrites the remote branch unconditionally, which can delete commits someone else pushed. --force-with-lease only overwrites if the remote branch is still at the commit you last fetched, so if someone else has pushed in the meantime the push is rejected.
</QA>

<QA q="How do you recover commits lost after a bad rebase or reset?">
Use git reflog to find the commit where HEAD was before the operation, then reset to it or create a branch there, for example git reset --hard HEAD@{2}, or use ORIG_HEAD. Commits stay recoverable through the reflog until they are garbage-collected, by default after about 90 days for reachable entries.
</QA>

</DeepDive>

  <Term name="Interactive rebase">Edit, squash, reorder or drop commits.</Term>
  <Term name="Fixup / squash">Fold a commit into an earlier one.</Term>
  <Term name="Autosquash">Automatically order fixup! commits during rebase.</Term>
  <Term name="Amend">Replace the latest commit.</Term>
  <Term name="Cherry-pick">Apply one commit onto the current branch.</Term>
  <Term name="Force-with-lease">Force push that refuses to overwrite unseen work.</Term>
  <Term name="Reflog">Local log of where HEAD has been.</Term>
</Terms>
