<BigIdea>
<Tr>
<En>
**GitHub Actions** runs commands for you automatically when something happens in your repository. A **workflow** is a YAML file in **`.github/workflows/`** that says **when** to run (**`on:`** push, pull request, schedule, tag…) and **what** to run (**`jobs:`**). Each job runs on a fresh virtual machine called a **runner** and has **steps**: a shell command (**`run:`**) or a ready-made **action** (**`uses:`**). Typical use: on every pull request, install, lint, test and build (**CI**); on merge to `main` or a tag, deploy (**CD**). Keep **`permissions:`** minimal, never paste untrusted input into `run:`, and pin third-party actions to a commit SHA.
</En>
<Ur>
**GitHub Actions** aap ki repository me kuch hone par khud commands chalata hai. **Workflow** **`.github/workflows/`** me ek YAML file hai jo batati hai **kab** chalna hai (**`on:`** push, pull request, schedule, tag…) aur **kya** chalana hai (**`jobs:`**). Har job ek taaza virtual machine par chalti hai jise **runner** kehte hain, aur us me **steps** hote hain: shell command (**`run:`**) ya bana banaya **action** (**`uses:`**). Aam istemal: har pull request par install, lint, test aur build (**CI**); `main` me merge ya tag par deploy (**CD**). **`permissions:`** kam se kam rakhein, `run:` me na-bharose wala input kabhi na daalein, aur third-party actions ko commit SHA par pin karein.
</Ur>
</Tr>
</BigIdea>

## Picture it

<Tr>
<En>

Imagine a restaurant where every new dish (your code change) must pass a **checklist** before it reaches customers: fresh ingredients (dependencies install), recipe followed (lint), taste test (tests), plated correctly (build). Doing this by hand every time is slow, and people skip steps when busy. GitHub Actions is a **robot kitchen assistant**: the moment a new dish arrives (a push or PR), it runs the whole checklist the same way every time, in a clean kitchen (a fresh runner), and puts a ✓ or ✗ on the order ticket (the pull request). If everything passes and the head chef approves, the robot can also **serve the dish** (deploy).

</En>
<Ur>

Socho ek restaurant jahan har nayi dish (aap ki code tabdeeli) customers tak pahunchne se pehle **checklist** se guzarti hai: taaza ajza (dependencies install), recipe ki pairwi (lint), chakh kar dekhna (tests), sahi tarah plate me (build). Har dafa haath se karna sust hai, aur masroofi me log qadam chhor dete hain. GitHub Actions **robot kitchen assistant** hai: nayi dish aate hi (push ya PR) wo har dafa ek hi tarah poori checklist chalata hai, saaf kitchen me (taaza runner), aur order ticket (pull request) par ✓ ya ✗ lagata hai. Sab pass ho aur head chef manzoor kare, to robot **dish serve** bhi kar sakta hai (deploy).

## Learn it step by step

<Walkthrough>

<Step title="Your first workflow">

<Tr>
<En>

A workflow is a YAML file with three main parts: `name` (shown in the Actions tab), `on` (when to run) and `jobs` (what to run). Once pushed, GitHub runs it automatically; there's no server for you to set up. YAML uses **indentation with spaces** (never tabs), `key: value` pairs, and `- ` for list items.

</En>
<Ur>

Workflow teen bare hisson wali YAML file hai: `name` (Actions tab me dikhta hai), `on` (kab chalna hai) aur `jobs` (kya chalana hai). Push hote hi GitHub ise khud chalata hai; aap ko koi server set nahi karna. YAML **spaces wali indentation** (tabs kabhi nahi), `key: value` jore, aur list items ke liye `- ` istemal karta hai.

</Ur>
</Tr>

```bash
git init -q shop && cd shop
mkdir -p .github/workflows
cat > .github/workflows/hello.yml <<'EOF'
name: Hello CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  say-hello:
    runs-on: ubuntu-latest
    steps:
      - name: Greet
        run: echo "Hello from GitHub Actions, commit ${{ github.sha }}"
      - name: Show the machine
        run: |
          uname -s
          echo "Running as $(whoami)"
EOF
actionlint -shellcheck= -pyflakes= && echo "actionlint: workflow is valid"
```

```text output
actionlint: workflow is valid
```

<Happened>
<Tr>
<En>

- `on:` lists the triggers: a `push` to `main`, or any `pull_request`.
- `jobs:` holds one job with the id `say-hello`; `runs-on: ubuntu-latest` asks for a fresh Ubuntu VM (others: `windows-latest`, `macos-latest`).
- Each `- name:` starts a step. `run:` executes shell commands; `${{ github.sha }}` is an **expression** GitHub replaces with the commit hash **before** the shell runs. `run: |` starts a multi-line script.
- `actionlint` (a free workflow checker, covered later) found no errors. `-shellcheck= -pyflakes=` only turns off its optional extra checks.

After `git push`, open the repo's **Actions** tab to watch it run and read each step's logs.

</En>
<Ur>

- `on:` triggers batata hai: `main` par `push`, ya koi bhi `pull_request`.
- `jobs:` me `say-hello` id wali ek job hai; `runs-on: ubuntu-latest` taaza Ubuntu VM maangta hai (doosre: `windows-latest`, `macos-latest`).
- Har `- name:` ek step shuru karta hai. `run:` shell commands chalata hai; `${{ github.sha }}` **expression** hai jise GitHub shell chalne se **pehle** commit hash se badalta hai. `run: |` kai lines wali script shuru karta hai.
- `actionlint` (muft workflow checker, aage aayega) ko koi ghalti nahi mili. `-shellcheck= -pyflakes=` sirf us ke izafi checks band karta hai.

`git push` ke baad repo ka **Actions** tab khol kar ise chalta dekhein aur har step ke logs parhein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Triggers: on:">

<Tr>
<En>

Different automation should run at different moments: tests on every PR, deployment only on `main` or tags. Choose the smallest set of triggers that does the job. Filters: `branches`, `tags`, `paths` (only when certain files change), `paths-ignore`.

```yaml
on:
  push:
    branches: [main]            # pushes to main (e.g. after a PR is merged)
    tags: ['v*']                # version tags like v1.4.0
  pull_request:
    branches: [main]            # PRs that want to merge into main
    paths-ignore: ['docs/**', '**.md']   # skip if only docs changed
  workflow_dispatch:            # adds a "Run workflow" button
  schedule:
    - cron: '30 2 * * 1'        # every Monday 02:30 UTC
```

| Event | Fires when | Typical use |
| --- | --- | --- |
| `pull_request` | A PR is opened, updated or reopened | CI: lint, test, build, scan |
| `push` (branches) | Commits arrive on that branch | Deploy to staging after merge |
| `push` (tags) | A tag is pushed | Release, deploy to production |
| `workflow_dispatch` | Someone clicks "Run workflow" | Manual tasks, re-deploys |
| `schedule` | A cron time (UTC) is reached | Nightly security audit |

Cron has five fields: minute, hour, day of month, month, day of week. `30 2 * * 1` = minute 30, hour 2, any day, any month, Monday. Times are in **UTC**, and runs can start a few minutes late when GitHub is busy.

</En>
<Ur>

Alag automation alag waqt chalni chahiye: har PR par tests, sirf `main` ya tags par deployment. Kaam karne wale sab se kam triggers chunein. Filters: `branches`, `tags`, `paths` (sirf khaas files badalne par), `paths-ignore`.

```yaml
on:
  push:
    branches: [main]            # pushes to main (e.g. after a PR is merged)
    tags: ['v*']                # version tags like v1.4.0
  pull_request:
    branches: [main]            # PRs that want to merge into main
    paths-ignore: ['docs/**', '**.md']   # skip if only docs changed
  workflow_dispatch:            # adds a "Run workflow" button
  schedule:
    - cron: '30 2 * * 1'        # every Monday 02:30 UTC
```

| Event | Kab chalta hai | Aam istemal |
| --- | --- | --- |
| `pull_request` | PR khule, update ho ya dobara khule | CI: lint, test, build, scan |
| `push` (branches) | Us branch par commits aayen | Merge ke baad staging deploy |
| `push` (tags) | Tag push ho | Release, production deploy |
| `workflow_dispatch` | Koi "Run workflow" dabaye | Haath ke kaam, dobara deploy |
| `schedule` | Cron waqt (UTC) aa jaye | Raat ka security audit |

Cron ke paanch hisse: minute, ghanta, mahine ka din, mahina, hafte ka din. `30 2 * * 1` = minute 30, ghanta 2, koi bhi din, koi bhi mahina, Monday. Waqt **UTC** me hai (apne timezone se convert karein), aur GitHub masroof ho to runs kuch minute der se shuru ho sakte hain.

</Ur>
</Tr>

</Step>

<Step title="Jobs, runners and steps">

<Tr>
<En>

A workflow has one or more **jobs**. Each job gets its **own fresh runner**, so there are no leftovers from previous runs, and its **steps** run in order on that machine. Jobs run **in parallel** by default; `needs:` makes one wait for another. Files are **not** shared between jobs automatically (use artifacts or cache). If any step exits non-zero, the job stops, is marked ✗, and later steps are skipped.

```text
job "lint"  ─► runner A: checkout → install → lint        ┐ run at the same time
job "test"  ─► runner B: checkout → install → test        ┘
job "build" ─► runner C (waits for lint + test via needs:) → checkout → install → build
```

| Step type | Looks like | Use for |
| --- | --- | --- |
| `run:` | `run: npm test` | Your own shell commands |
| `uses:` | `uses: actions/setup-node@v4` | Reusable actions by GitHub or the community |

</En>
<Ur>

Workflow me ek ya zyada **jobs** hoti hain. Har job ko **apna taaza runner** milta hai, isliye pichhle runs ka kuch nahi bachta, aur us ke **steps** us machine par tarteeb se chalte hain. Jobs default me **saath saath** chalti hain; `needs:` ek ko doosri ka intezar karwata hai. Files jobs ke darmiyan khud **share nahi** hotin (artifacts ya cache istemal karein). Koi step non-zero de to job ruk jati hai, ✗ lagta hai, aur baad ke steps chhoot jate hain.

```text
job "lint"  ─► runner A: checkout → install → lint        ┐ run at the same time
job "test"  ─► runner B: checkout → install → test        ┘
job "build" ─► runner C (waits for lint + test via needs:) → checkout → install → build
```

| Step ki qisam | Shakal | Kis ke liye |
| --- | --- | --- |
| `run:` | `run: npm test` | Aap ki apni shell commands |
| `uses:` | `uses: actions/setup-node@v4` | GitHub ya community ke bane actions |

</Ur>
</Tr>

</Step>

<Step title="CI is just your commands, run automatically">

<Tr>
<En>

A CI job does exactly what you'd type on your own computer: install, lint, test, build. If the commands work locally in a clean folder, they'll almost always work in CI, and when CI fails you reproduce it locally with the same commands. Put them in `package.json` scripts (or a Makefile) so CI and developers run **identical** commands. Tests must exit 0 on success and non-zero on failure; that exit code turns a step green or red.

</En>
<Ur>

CI job bilkul wahi karti hai jo aap apne computer par likhte: install, lint, test, build. Agar commands saaf folder me local chalti hain, to takreeban hamesha CI me bhi chalengi, aur CI fail ho to wahi commands local chala kar masla dohrate hain. Inhe `package.json` scripts (ya Makefile) me rakhein taa ke CI aur developers **bilkul ek jaisi** commands chalayen. Tests kaamyabi par 0 aur nakaami par non-zero exit dein; yahi exit code step ko hara ya laal karta hai.

</Ur>
</Tr>

```bash
mkdir -p shop-app/src shop-app/test && cd shop-app
cat > package.json <<'EOF'
{ "name": "shop", "version": "1.0.0", "type": "module",
  "scripts": { "lint": "node --check src/cart.js", "test": "node --test --test-reporter=tap" } }
EOF
echo 'export const total = (items) => items.reduce((sum, i) => sum + i.price * i.qty, 0);' > src/cart.js
cat > test/cart.test.js <<'EOF'
import { test } from "node:test";
import assert from "node:assert/strict";
import { total } from "../src/cart.js";
test("empty cart costs 0", () => assert.equal(total([]), 0));
test("price is multiplied by quantity", () => assert.equal(total([{ price: 100, qty: 3 }]), 300));
EOF
npm run lint --silent && echo "lint: passed"
npm test --silent | grep -E '^(ok|not ok|# (pass|fail))'
echo "exit code: ${PIPESTATUS[0]}"
```

```text output
lint: passed
ok 1 - empty cart costs 0
ok 2 - price is multiplied by quantity
# pass 2
# fail 0
exit code: 0
```

<Happened>
<Tr>
<En>

- `lint` uses `node --check` (syntax only) as a stand-in for a real linter like ESLint; `test` runs Node's built-in test runner, which finds `*.test.js` files in `test/`.
- Both tests passed (`grep` keeps the key lines; the full output also has timings that change every run).
- `${PIPESTATUS[0]}` is the exit code of `npm test`, the first command in the pipe: `0` = success. In CI a non-zero code here fails the job.

</En>
<Ur>

- `lint` asli linter (ESLint) ki jagah `node --check` (sirf syntax) istemal karta hai; `test` Node ka andar bana test runner chalata hai jo `test/` me `*.test.js` files dhoondhta hai.
- Dono tests pass hue (`grep` ahem lines rakhta hai; poore output me har dafa badalne wale timings bhi hote hain).
- `${PIPESTATUS[0]}` `npm test` ka exit code hai, pipe ki pehli command: `0` = kaamyabi. CI me yahan non-zero code job fail karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Use actions: checkout, setup and cache">

<Tr>
<En>

The runner starts **empty**: your code isn't even there until `actions/checkout` runs. `actions/setup-node` (or `setup-python`, `setup-java`) installs a language version, and caching reuses downloaded dependencies between runs. Find actions on the **GitHub Marketplace**; configure them with `with:` inputs listed in each action's README. Prefer official (`actions/*`) or well-known, verified publishers.

</En>
<Ur>

Runner **khaali** shuru hota hai: `actions/checkout` chalne tak aap ka code wahan hai hi nahi. `actions/setup-node` (ya `setup-python`, `setup-java`) zubaan ka version install karta hai, aur caching runs ke darmiyan download shuda dependencies dobara istemal karti hai. Actions **GitHub Marketplace** par milte hain; har action ki README me diye `with:` inputs se set karein. Sarkari (`actions/*`) ya mashhoor, tasdeeq shuda publishers ko tarjeeh dein.

</Ur>
</Tr>

```bash
cd shop-app && git init -q
mkdir -p .github/workflows
cat > .github/workflows/ci.yml <<'EOF'
name: CI
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
EOF
actionlint -shellcheck= -pyflakes= && echo "ci.yml is valid"
```

```text output
ci.yml is valid
```

<Happened>
<Tr>
<En>

- `permissions: contents: read` gives the automatic token read-only access.
- `actions/checkout@v4` cloned the repo at the triggering commit; `setup-node` installed Node 22, and `cache: npm` caches npm packages (keyed on `package-lock.json`) so the next run is faster.
- `npm ci` installs exactly what the lockfile says: faster and stricter than `npm install`, which is why CI uses it. Then the same lint and test commands as locally.

That's a complete, real CI pipeline for a Node.js project. Python would use `actions/setup-python@v5` with `pip install -r requirements.txt` and `pytest`.

</En>
<Ur>

- `permissions: contents: read` khud milne wale token ko sirf parhne ki rasai deta hai.
- `actions/checkout@v4` ne trigger wale commit par repo clone ki; `setup-node` ne Node 22 install kiya, aur `cache: npm` npm packages cache karta hai (`package-lock.json` ki bunyad par) taa ke agla run tez ho.
- `npm ci` bilkul wahi install karta hai jo lockfile kehti hai: `npm install` se tez aur sakht, isi liye CI ise istemal karta hai. Phir wahi lint aur test commands jo local chalayin.

Ye Node.js project ki mukammal, asli CI pipeline hai. Python me `actions/setup-python@v5`, `pip install -r requirements.txt` aur `pytest` hote.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Matrix builds: test many versions at once">

<Tr>
<En>

`strategy.matrix` runs the same job several times with different values, such as Node 20, 22 and 24, or Linux and Windows, because your code must work on every version your users run. Lists multiply: 3 Node versions × 2 operating systems = 6 jobs. `fail-fast: false` lets the others finish when one fails, so you see every failure.

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [20, 22, 24]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test
```

</En>
<Ur>

`strategy.matrix` ek hi job ko alag values ke saath kai dafa chalata hai, jaise Node 20, 22 aur 24, ya Linux aur Windows, kyun ke aap ka code har us version par chalna chahiye jo users chalate hain. Lists zarb hoti hain: 3 Node versions × 2 operating systems = 6 jobs. `fail-fast: false` ek fail hone par baqi ko khatam hone deta hai, taa ke har nakaami nazar aaye.

<Step title="Job order with needs: and conditions with if:">

<Tr>
<En>

`needs: [job-a]` makes a job wait until those jobs succeed; `if:` runs a job or step only when a condition is true. Never deploy code that failed its tests, and only deploy from `main`. Useful values: `github.event_name`, `github.ref` (`refs/heads/main`), `github.ref_name` (`main`), and `success()`, `failure()`, `always()`. If a needed job fails, the dependent job is **skipped**.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

  deploy:
    needs: test                                   # wait for test to pass
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/deploy.sh
      - name: Tell the team it failed
        if: failure()
        run: echo "Deploy failed for ${{ github.sha }}"
```

How to read it: on a pull request, `test` runs and `deploy` is **skipped** (the event isn't `push`). On a push to `main`, `deploy` starts only if `test` passes. If the deploy script fails, the last step runs because of `if: failure()`.

</En>
<Ur>

`needs: [job-a]` job ko tab tak rokta hai jab tak wo jobs kaamyab na hon; `if:` job ya step sirf shart sach hone par chalata hai. Fail tests wala code kabhi deploy na karein, aur sirf `main` se deploy karein. Kaam ki values: `github.event_name`, `github.ref` (`refs/heads/main`), `github.ref_name` (`main`), aur `success()`, `failure()`, `always()`. Zaroori job fail ho to us par munhasir job **skip** hoti hai.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

  deploy:
    needs: test                                   # wait for test to pass
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/deploy.sh
      - name: Tell the team it failed
        if: failure()
        run: echo "Deploy failed for ${{ github.sha }}"
```

Kaise parhein: pull request par `test` chalta hai aur `deploy` **skip** (event `push` nahi). `main` par push me `deploy` sirf `test` pass hone par shuru hota hai. Deploy script fail ho to aakhri step `if: failure()` ki wajah se chalta hai.

</Ur>
</Tr>

</Step>

<Step title="Contexts and expressions">

<Tr>
<En>

`${{ ... }}` reads values from **contexts**: `github` (event, branch, commit, actor), `secrets`, `vars`, `env`, `matrix`, `steps`, `runner`. Use them in `if:`, `with:`, `env:` and names. **Important:** GitHub replaces expressions **before** the shell runs, as plain text pasted into your script. That's why untrusted values must never go directly into `run:` (see script injection below).

| Expression | Example value |
| --- | --- |
| `${{ github.event_name }}` | `pull_request` |
| `${{ github.ref_name }}` | `main` or `v1.4.0` |
| `${{ github.sha }}` | `3f2a1b9c...` (full commit hash) |
| `${{ github.actor }}` | `alex-carter` |
| `${{ github.repository }}` | `alex-carter/devguide` |
| `${{ runner.os }}` | `Linux` |
| `${{ matrix.node }}` | `22` |
| `${{ secrets.DEPLOY_TOKEN }}` | `***` (masked in logs) |

Steps can share values through the **`$GITHUB_OUTPUT`** file: `echo "version=1.4.0" >> "$GITHUB_OUTPUT"` in a step with `id: meta`, then `${{ steps.meta.outputs.version }}` later.

</En>
<Ur>

`${{ ... }}` **contexts** se values parhta hai: `github` (event, branch, commit, actor), `secrets`, `vars`, `env`, `matrix`, `steps`, `runner`. Inhe `if:`, `with:`, `env:` aur naamon me istemal karein. **Ahem:** GitHub expressions shell chalne se **pehle** badalta hai, saade text ki tarah aap ki script me chipka kar. Isi liye na-bharose wali values kabhi seedha `run:` me nahi jani chahiyen (neeche script injection dekhein).

| Expression | Misaali value |
| --- | --- |
| `${{ github.event_name }}` | `pull_request` |
| `${{ github.ref_name }}` | `main` ya `v1.4.0` |
| `${{ github.sha }}` | `3f2a1b9c...` (poora commit hash) |
| `${{ github.actor }}` | `alex-carter` |
| `${{ github.repository }}` | `alex-carter/devguide` |
| `${{ runner.os }}` | `Linux` |
| `${{ matrix.node }}` | `22` |
| `${{ secrets.DEPLOY_TOKEN }}` | `***` (logs me chhupa) |

Steps **`$GITHUB_OUTPUT`** file se values share kar sakte hain: `id: meta` wale step me `echo "version=1.4.0" >> "$GITHUB_OUTPUT"`, phir baad me `${{ steps.meta.outputs.version }}`.

</Ur>
</Tr>

<Step title="Secrets, variables and environments">

<Tr>
<En>

Workflows need credentials to deploy, and those must never be in the repo. **Secrets** are encrypted values masked in logs; **variables** (`vars`) are non-secret settings; **environments** (`staging`, `production`) group secrets and add protection such as required **reviewers** before each deployment. Set them in **Settings → Secrets and variables → Actions** or with `gh secret set DEPLOY_TOKEN`. Pass secrets to commands through `env:`, never by printing them. Secrets are **not** given to workflows triggered by PRs from forks.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production          # needs approval if the environment requires reviewers
    steps:
      - uses: actions/checkout@v4
      - name: Deploy
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
          API_URL: ${{ vars.API_URL }}
        run: ./scripts/deploy.sh      # the script reads $DEPLOY_TOKEN and $API_URL
```

If a step accidentally prints a secret, GitHub shows `***`. Don't rely on it: encoded or partial values are **not** masked.

</En>
<Ur>

Workflows ko deploy ke liye credentials chahiyen, aur wo kabhi repo me nahi hone chahiyen. **Secrets** logs me chhupi encrypted values hain; **variables** (`vars`) ghair raaz settings; **environments** (`staging`, `production`) secrets ko group karte hain aur hifazat jorte hain, jaise har deployment se pehle lazmi **reviewers**. Inhe **Settings → Secrets and variables → Actions** me ya `gh secret set DEPLOY_TOKEN` se set karein. Secrets commands ko `env:` se dein, chhaap kar kabhi nahi. Forks ke PRs se chalne wale workflows ko secrets **nahi** milte.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production          # needs approval if the environment requires reviewers
    steps:
      - uses: actions/checkout@v4
      - name: Deploy
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
          API_URL: ${{ vars.API_URL }}
        run: ./scripts/deploy.sh      # the script reads $DEPLOY_TOKEN and $API_URL
```

Koi step ghalti se secret chhaape to GitHub `***` dikhata hai. Is par bharosa na karein: encoded ya adhoori values **nahi** chhupti.

</Ur>
</Tr>

</Step>

<Step title="GITHUB_TOKEN and permissions:">

<Tr>
<En>

Every run gets an automatic, short-lived token, `GITHUB_TOKEN`, that can act on **this** repository: read code, comment on PRs, create releases, push packages. It expires when the job ends, but if a step is compromised, that token is what the attacker gets, so keep it small. Set `permissions:` at the top of every workflow and grant more only to the job that needs it (`contents: write` for releases, `pull-requests: write` for PR comments, `id-token: write` for OIDC). Also set the repo default to read-only under **Settings → Actions → General → Workflow permissions**.

```yaml
permissions:
  contents: read            # default for every job in this file

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write       # only this job may create releases / push tags
    steps:
      - uses: actions/checkout@v4
      - run: gh release create "${{ github.ref_name }}" --generate-notes
        env:
          GH_TOKEN: ${{ github.token }}
```

</En>
<Ur>

Har run ko khud ek chhoti umar ka token, `GITHUB_TOKEN`, milta hai jo **isi** repository par kaam kar sakta hai: code parhna, PRs par tabsira, releases banana, packages push karna. Job khatam hone par ye expire hota hai, lekin agar koi step compromise ho to hamla awar ko yahi token milta hai, isliye ise chhota rakhein. Har workflow ke upar `permissions:` set karein aur zyada sirf us job ko dein jise chahiye (`contents: write` releases ke liye, `pull-requests: write` PR tabsiron ke liye, `id-token: write` OIDC ke liye). Repo ka default bhi **Settings → Actions → General → Workflow permissions** me read-only karein.

```yaml
permissions:
  contents: read            # default for every job in this file

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write       # only this job may create releases / push tags
    steps:
      - uses: actions/checkout@v4
      - run: gh release create "${{ github.ref_name }}" --generate-notes
        env:
          GH_TOKEN: ${{ github.token }}
```

<Step title="Artifacts: keeping files from a run">

<Tr>
<En>

Runners are deleted after the job. **Artifacts** are files you upload during a run (build output, test reports, coverage) so you can download them later or pass them to another job: build once, then deploy exactly that build. Use `actions/upload-artifact@v4` and `download-artifact@v4`; they expire after a retention period (90 days by default). **Cache** is different: it only speeds up installs and may disappear any time.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: site
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: site
          path: dist/
      - run: ls dist/    # exactly the files the build job produced
```

</En>
<Ur>

Job ke baad runners mita diye jate hain. **Artifacts** wo files hain jo run ke doran upload karte hain (build output, test reports, coverage) taa ke baad me download karein ya doosri job ko dein: ek dafa build, phir bilkul wahi build deploy. `actions/upload-artifact@v4` aur `download-artifact@v4` istemal karein; ye ek muddat (default 90 din) ke baad expire hote hain. **Cache** alag hai: sirf installs tez karta hai aur kabhi bhi ghayab ho sakta hai.

```yaml

    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/upload-artifact@v4

          name: site
          path: dist/

  deploy:
    needs: build

    steps:
```

<Step title="Script injection: never paste untrusted input into run:">

<Tr>
<En>

`${{ }}` values are inserted into the script **as text before Bash runs**. If the value comes from an attacker (PR title, branch name, issue body, commit message), they can put shell commands in it, and those commands run on your runner with your token and, in some events, your secrets. The fix: put the value in an **environment variable** with `env:` and use `"$VAR"` (quoted); the shell then treats it as data, never code. Below we simulate exactly what GitHub does.

</En>
<Ur>

`${{ }}` values **Bash chalne se pehle text ki tarah** script me daali jati hain. Agar value hamla awar se aaye (PR title, branch ka naam, issue ki tafseel, commit message), wo us me shell commands rakh sakta hai, aur wo commands aap ke runner par aap ke token ke saath, aur kuch events me aap ke secrets ke saath, chalti hain. Hal: value ko `env:` se **environment variable** me daalein aur `"$VAR"` (quotes ke saath) istemal karein; shell phir ise data samajhta hai, code kabhi nahi. Neeche hum bilkul wahi nakal karte hain jo GitHub karta hai.

</Ur>
</Tr>

```bash
title='Fix typo"; echo "ATTACKER CODE RUNS HERE: could steal $SECRET_TOKEN'
export SECRET_TOKEN="(secret value)"
echo "--- unsafe: run: echo \"PR title is \${{ github.event.pull_request.title }}\""
unsafe_template='echo "PR title is ${{ github.event.pull_request.title }}"'
script="${unsafe_template/'${{ github.event.pull_request.title }}'/$title}"
bash -c "$script"
echo "--- safe: env: PR_TITLE: \${{ ... }}  and  run: echo \"PR title is \$PR_TITLE\""
PR_TITLE="$title" bash -c 'echo "PR title is $PR_TITLE"'
```

```text output
--- unsafe: run: echo "PR title is ${{ github.event.pull_request.title }}"
PR title is Fix typo
ATTACKER CODE RUNS HERE: could steal (secret value)
--- safe: env: PR_TITLE: ${{ ... }}  and  run: echo "PR title is $PR_TITLE"
PR title is Fix typo"; echo "ATTACKER CODE RUNS HERE: could steal $SECRET_TOKEN
```

<Happened>
<Tr>
<En>

- `title` is what an attacker types as a PR title: `";` closes the `echo` string, then a second command follows.
- `${unsafe_template/pattern/$title}` replaced the expression with the title, exactly as GitHub does before starting Bash.
- `bash -c "$script"` saw **two** commands: the attacker's ran and could read `$SECRET_TOKEN`. In a real workflow it could send the token to their server.
- In the safe version the title arrived as an environment variable and was printed as plain text; nothing in it ran.

The fixed workflow:

```yaml
- name: Show PR title safely
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: echo "PR title is $PR_TITLE"
```

</En>
<Ur>

- `title` wo hai jo hamla awar PR title me likhta hai: `";` `echo` string band karta hai, phir doosri command aati hai.
- `${unsafe_template/pattern/$title}` ne expression ko title se badla, bilkul jaise GitHub Bash shuru karne se pehle karta hai.
- `bash -c "$script"` ne **do** commands dekhin: hamla awar ki chali aur `$SECRET_TOKEN` parh saki. Asli workflow me wo token apne server par bhej sakti thi.
- Mehfooz version me title environment variable ban kar aaya aur saade text ki tarah chhapa; us me se kuch nahi chala.

Theek kiya hua workflow:

```yaml
- name: Show PR title safely
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: echo "PR title is $PR_TITLE"
```

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Pin actions, and beware of pull_request_target">

<Tr>
<En>

`uses: some/action@v3` runs **someone else's code** in your pipeline, and tags like `v3` can be moved by the owner, or by an attacker who compromises them. In March 2025 the popular `tj-actions/changed-files` action was compromised and its tags were repointed to code that dumped CI secrets into logs, affecting thousands of repos. Pin to a full 40-character commit SHA with the version in a comment; Dependabot or Renovate keep pins updated.

```yaml
# risky: the tag can be moved to different code at any time
- uses: some-org/useful-action@v2

# safer: an exact, unchangeable commit; the comment says which version it is
- uses: some-org/useful-action@1f5a3c9d2b7e8a4f6c0d1e2b3a4c5d6e7f8a9b0c # v2.3.1
```

Also be careful with `pull_request_target`: it runs with the **base** repo's secrets and write token, even for PRs from forks. **Never** check out and run the PR's code in it; use plain `pull_request` for building and testing contributions.

| Event | Code that runs | Secrets for fork PRs | Write token for fork PRs |
| --- | --- | --- | --- |
| `pull_request` | The PR's code | **No** | **No** (read-only) |
| `pull_request_target` | The **base** branch's workflow | **Yes** | **Yes** |

</En>
<Ur>

`uses: some/action@v3` aap ki pipeline me **kisi aur ka code** chalata hai, aur `v3` jaise tags maalik, ya unhe compromise karne wala hamla awar, hila sakta hai. March 2025 me mashhoor `tj-actions/changed-files` action compromise hua aur us ke tags aise code par hila diye gaye jo CI secrets logs me ugal deta tha, hazaron repos mutasir hue. Poore 40 huroof ke commit SHA par pin karein aur version tabsire me likhein; Dependabot ya Renovate pins update rakhte hain.

```yaml
# risky: the tag can be moved to different code at any time
- uses: some-org/useful-action@v2

# safer: an exact, unchangeable commit; the comment says which version it is
- uses: some-org/useful-action@1f5a3c9d2b7e8a4f6c0d1e2b3a4c5d6e7f8a9b0c # v2.3.1
```

`pull_request_target` se bhi hoshyar: ye **base** repo ke secrets aur likhne wale token ke saath chalta hai, forks ke PRs ke liye bhi. Is me PR ka code **kabhi** checkout kar ke na chalayen; contributions build aur test karne ke liye saada `pull_request` istemal karein.

| Event | Kaunsa code chalta hai | Fork PRs ke liye secrets | Fork PRs ke liye likhne wala token |
| --- | --- | --- | --- |
| `pull_request` | PR ka code | **Nahi** | **Nahi** (sirf parhna) |
| `pull_request_target` | **Base** branch ka workflow | **Haan** | **Haan** |

</Ur>
</Tr>

</Step>

<Step title="Deploy to the cloud without stored keys: OIDC">

<Tr>
<En>

With **OpenID Connect (OIDC)**, a workflow asks GitHub for a short-lived identity token and exchanges it with AWS, Azure or Google Cloud for temporary credentials, so **no cloud keys are stored in GitHub at all**. Long-lived keys in secrets can leak and stay valid for years; OIDC credentials expire within an hour and can be restricted to one repo and branch. You need `permissions: id-token: write` plus the cloud's official login action; on the cloud side, a role that trusts GitHub's OIDC provider for **your** repo and branch only. The Cloud and DevSecOps tracks set this up in detail.

```yaml
permissions:
  id-token: write      # allow requesting the OIDC token
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/deploy-from-github
      aws-region: me-central-1
  - run: aws s3 sync dist/ s3://my-site-bucket/
```

</En>
<Ur>

**OpenID Connect (OIDC)** ke saath workflow GitHub se chhoti umar ka shanakhti token maangta hai aur use AWS, Azure ya Google Cloud se aarzi credentials se badalta hai, isliye **GitHub me koi cloud key save hi nahi hoti**. Secrets me rakhi lambi umar ki keys leak ho kar barson chal sakti hain; OIDC credentials ghante ke andar expire hoti hain aur ek repo aur branch tak mehdood ki ja sakti hain. Aap ko `permissions: id-token: write` aur cloud ka sarkari login action chahiye; cloud ki taraf ek role jo sirf **aap ki** repo aur branch ke liye GitHub ke OIDC provider par bharosa kare. Cloud aur DevSecOps tracks ise tafseel se set karte hain.

```yaml
permissions:
  id-token: write      # allow requesting the OIDC token
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/deploy-from-github
      aws-region: me-central-1
  - run: aws s3 sync dist/ s3://my-site-bucket/
```

</Ur>
</Tr>

```text
    runs-on: ubuntu-latest
    steps:
      - uses: some-org/greeter@1f5a3c9d2b7e8a4f6c0d1e2b3a4c5d6e7f8a9b0c # v2.3.1
      - env:
          PR_TITLE: ${{ github.event.pull_request.title }}
        run: echo "Thanks for $PR_TITLE"
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **YAML indentation errors** (tabs, or a step indented wrongly). Use an editor with YAML support, and actionlint.
- **Forgetting `actions/checkout`**, so the runner has no code and `npm ci` fails with "no package.json".
- **`npm install` instead of `npm ci`** in CI, which gives non-reproducible installs.
- **Printing secrets** (`echo $TOKEN`, `env`, `set -x`) in logs.
- **Huge, slow workflows** without caching, concurrency or path filters.
- **Expecting schedules in local time.** Cron in Actions is UTC.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **YAML indentation ki ghaltiyan** (tabs, ya step ghalat jagah). YAML support wala editor aur actionlint istemal karein.

## Try it yourself

<Challenge title="A complete, secure CI workflow">

<Tr>
<En>
Write a CI workflow for `shop-app` with triggers, read-only permissions, concurrency, a timeout, a Node matrix, and a summary job. Check it with actionlint, then run its commands locally exactly as the runner would.
</En>
<Ur>
`shop-app` ke liye CI workflow likhein: triggers, read-only permissions, concurrency, timeout, Node matrix, aur summary job ke saath. actionlint se check karein, phir us ki commands local bilkul runner ki tarah chalayen.
</Ur>
</Tr>

```bash
cd shop-app
cat > .github/workflows/ci.yml <<'EOF'
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    name: Lint and test (Node ${{ matrix.node }})
    runs-on: ubuntu-latest
    timeout-minutes: 10
    strategy:
      fail-fast: false
      matrix:
        node: [20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - name: Lint
        run: npm run lint
      - name: Test
        run: npm test

  report:
    needs: test
    if: always()
    runs-on: ubuntu-latest
    steps:
      - name: Summary
        env:
          RESULT: ${{ needs.test.result }}
          BRANCH: ${{ github.head_ref || github.ref_name }}
        run: echo "Tests on $BRANCH finished with result $RESULT" >> "$GITHUB_STEP_SUMMARY"
EOF
actionlint -shellcheck= -pyflakes= && echo "1) workflow valid"
echo "2) running the job's steps locally:"
npm run lint --silent && echo "   Lint: ok"
npm test --silent | grep -E '^# (pass|fail)' | sed 's/^/   Test: /'
RESULT=success BRANCH=main bash -c 'echo "Tests on $BRANCH finished with result $RESULT"' | sed 's/^/3) summary: /'
```

```text output
   Lint: ok
   Test: # pass 2
   Test: # fail 0
3) summary: Tests on main finished with result success
```

<DeepDive title="Real world: the broken lesson that never went live">

Alex's DevGuide site is a Next.js app deployed on Vercel. The team adds `.github/workflows/ci.yml`: on every pull request it runs `npm ci`, `npm run check:content` (validates every lesson), `npm run build`, gitleaks and actionlint, with `permissions: contents: read` and actions pinned by SHA. Branch protection on `main` requires all of these checks. One evening a contributor's PR renames a lesson file but forgets to update the curriculum. `check:content` fails with a clear error, the PR shows a red ✗, and the broken lesson never reaches the live site. After the fix, the checks turn green, the PR is approved and merged, and Vercel deploys automatically. A weekly `schedule:` workflow also runs `npm audit` and opens an issue if a dependency has a known vulnerability.

</DeepDive>

<DeepDive title="Security lens">

A CI pipeline holds the keys to your production. Treat workflow files as security-critical code and review them like authentication code.

- **Least privilege:** `permissions: contents: read` by default, extra scopes only on the job that needs them, read-only default token in repo settings.
- **No script injection:** pass every `github.event.*` value through `env:` and quote it.
- **Supply chain:** pin actions by full SHA, prefer verified publishers, keep pins updated with Dependabot, and use the organisation setting that allows only selected actions.
- **Secrets:** environments with required reviewers for production, OIDC instead of long-lived cloud keys, never echo them.
- **Untrusted contributors:** use `pull_request` (no secrets) for fork PRs, and require approval before running workflows for first-time contributors.
- **Self-hosted runners** aren't wiped between jobs. Never use them on public repositories: anyone's PR could run code on your machine.
- **Protect `.github/workflows/`** with CODEOWNERS so workflow changes need security or DevOps review.
- **Scan your workflows** with actionlint, zizmor or OpenSSF Scorecard.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the main building blocks of a GitHub Actions workflow?">
A workflow is a YAML file in .github/workflows that defines triggering events under on and one or more jobs. Each job runs on a runner, such as ubuntu-latest, and contains ordered steps, which either run shell commands with run or use reusable actions with uses. Jobs run in parallel by default unless needs defines dependencies.
</QA>

<QA q="What is the difference between CI and CD?">
Continuous integration automatically builds and tests every change, typically on each push or pull request, so integration problems are found early. Continuous delivery keeps tested code always ready to release with an automated, possibly approval-gated deployment process, and continuous deployment goes further by deploying every change that passes the pipeline to production automatically.
</QA>

<QA q="How do you handle secrets in GitHub Actions?">
Store them as repository, organisation or environment secrets and reference them with the secrets context, passing them to commands through environment variables rather than printing them. Limit the GITHUB_TOKEN with the permissions key, protect production secrets with environments that require reviewers, and prefer OIDC federation to obtain short-lived cloud credentials instead of storing long-lived keys.
</QA>

<QA q="What is script injection in GitHub Actions and how do you prevent it?">
Expressions in a run step are substituted into the script text before the shell executes it, so attacker-controlled values such as pull request titles, branch names or issue comments can contain shell commands that then execute on the runner. To prevent it, assign such values to environment variables using env and reference them as quoted shell variables, and avoid untrusted input in run steps where possible.
</QA>

<QA q="Why should you pin third-party actions to a commit SHA?">
Tags and branches of an action repository can be changed to point at different code, either by the maintainer or by an attacker who compromises the repository, as happened in the tj-actions/changed-files incident. A full commit SHA is immutable, so the workflow always runs exactly the reviewed code. Tools like Dependabot can update the pinned SHAs.
</QA>

<QA q="What is the risk of pull_request_target?">
pull_request_target runs in the context of the base repository with access to its secrets and a write-capable token, even when the pull request comes from a fork. If the workflow checks out and builds or runs the pull request's code, an attacker can execute arbitrary code with those privileges. It should only be used for trusted tasks such as labelling, never for building untrusted code.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="CI / CD">Automated testing of every change / automated delivery or deployment.</Term>
  <Term name="Workflow">Automation defined in a YAML file under .github/workflows.</Term>
  <Term name="Event">Trigger that starts a workflow, such as push or pull_request.</Term>
  <Term name="Job">Set of steps that runs on one runner.</Term>
  <Term name="Runner">Machine that executes a job, e.g. ubuntu-latest.</Term>
  <Term name="Step">A run command or a uses action within a job.</Term>
  <Term name="Action">Reusable packaged step, e.g. actions/checkout.</Term>
  <Term name="Matrix">Strategy that runs a job for each combination of values.</Term>
  <Term name="Expression">A dollar-sign double-brace value substituted by GitHub before a step runs.</Term>
  <Term name="GITHUB_TOKEN">Automatic short-lived token for the current repository.</Term>
  <Term name="Environment">Named deployment target with its own secrets and protection rules.</Term>
  <Term name="Artifact">File uploaded from a run to keep or pass between jobs.</Term>
  <Term name="OIDC">Keyless, short-lived cloud authentication for workflows.</Term>
  <Term name="actionlint">Static checker for workflow files.</Term>
</Terms>
