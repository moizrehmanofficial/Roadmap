<Callout type="tip" title="In one minute">
A **secret** is anything that gives access: passwords, API keys, tokens, private keys, database connection strings. **Never commit them.** Git keeps every version forever, so a password deleted in the next commit is **still in history**, in every clone and fork. Keep secrets in a **`.env`** file that is listed in **`.gitignore`**, commit a **`.env.example`** with empty values instead, and have your code read secrets from **environment variables**. Add guards: a **pre-commit secret scanner** (e.g. **gitleaks**) and GitHub **push protection**. If a secret does leak: **revoke/rotate it first**, then investigate and clean history. Cleaning history alone never makes a leaked secret safe again.
</Callout>

## Start from zero

<Callout type="analogy">
Committing a password is like **writing your house key's code on a page of a book that you then photocopy and hand out**. Tearing that page out of **your** copy (deleting the file in a new commit) doesn't help: every photocopy (clone, fork, CI cache, backup) still has it. The only real fix is to **change the lock** (rotate the secret). The right habit is to keep the key code on a **separate card in your wallet** (`.env`, never committed), while the book only says "the code is on the card" (`.env.example`).
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Secret** | Information that grants access | `DB_PASSWORD`, `sk_live_...`, `id_rsa` |
| **Environment variable** | A named value the operating system gives a running program | `PORT=3000`, `DB_PASSWORD=...` |
| **`.env` file** | A local file with `NAME=value` lines, loaded into environment variables | `DB_PASSWORD=hunter2` |
| **`.env.example`** | A committed template listing the needed variables, without real values | `DB_PASSWORD=` |
| **Secret scanner** | A tool that searches code and history for things that look like secrets | gitleaks, TruffleHog, GitHub secret scanning |
| **Push protection** | GitHub feature that blocks a push containing a recognised secret | "Push cannot contain secrets" |
| **Rotate / revoke** | Replace a secret with a new one / make the old one stop working | new database password |
| **Secret manager** | A secure service for storing and handing out secrets | GitHub Actions secrets, AWS Secrets Manager, Vault |

## What is it?

Keeping secrets out of Git is a set of habits and tools:

```text
 1. Separate      code (in Git)            secrets (.env, secret manager)
 2. Ignore        .gitignore: .env, *.pem, *.key, credentials.json
 3. Prevent       pre-commit hook / push protection    → block before it leaves your machine
 4. Detect        scan the full history in CI           → find old leaks
 5. Respond       revoke + rotate → investigate → clean history (optional)
```

## Why does it matter?

- **It's one of the most common real-world breaches.** Bots scan every public GitHub push within seconds for cloud keys and tokens; leaked AWS keys are often abused to mine cryptocurrency within minutes, leaving the owner with huge bills.
- **Private repos aren't safe either:** they get cloned to laptops, copied to CI systems, made public by mistake, or accessed by an attacker with one stolen token, who then searches them for more secrets.
- **Git never forgets.** Removing the line later doesn't remove it from history.
- **Interview and job relevance:** "How do you manage secrets?" is a standard DevOps and DevSecOps interview question.

## When and where do you use it?

- **From the first commit** of every project: create `.gitignore` and `.env.example` before writing code that needs a key.
- **Every commit:** the pre-commit hook runs automatically.
- **In CI:** scan the full history on every pull request.
- **In production:** secrets come from the platform (Vercel environment variables, Kubernetes Secrets, AWS Secrets Manager), never from the repository.

## Concepts one by one

### 1. What counts as a secret?

<Explain>
<What>
Anything that lets someone **log in, call an API, decrypt data or impersonate** you or your service.
</What>
<Why>
If an attacker gets it, they get the same access your application has, often to production data and money.
</Why>
<When>
Ask "could a stranger do damage with this value?" If yes, it's a secret.
</When>
<Where>
Typical hiding places: `.env` files, `config.js`, `settings.py`, `docker-compose.yml`, Terraform files and state (`terraform.tfstate`), Jupyter notebooks, test scripts, CI config, shell history pasted into scripts, and `.npmrc` / `.pypirc` files.
</Where>
<How>
Treat **all** of these as secrets: passwords, API keys, OAuth client secrets, access tokens, JWT signing keys, private keys (`.pem`, `.key`, `id_rsa`), cloud credentials, database URLs with passwords, webhook URLs (e.g. Slack), and session encryption keys.
</How>
</Explain>

| Secret | Typical look | Damage if leaked |
| --- | --- | --- |
| Cloud access key | `AKIA...` (AWS) | Attacker controls your cloud: data theft, crypto-mining bills |
| Payment API key | `sk_live_...` (Stripe) | Refunds, payouts, customer data |
| Database URL | `postgres://admin:pass@db:5432/app` | Read or delete all data |
| GitHub token | `ghp_...`, `github_pat_...` | Push malicious code, read private repos |
| Private key | `-----BEGIN PRIVATE KEY-----` | Impersonate your server, decrypt traffic |
| JWT secret | random string in config | Forge login tokens for any user, including admin |

**Not secrets:** public keys, a public Firebase web config, the **name** of a variable, or a placeholder like `DB_PASSWORD=change-me`.

### 2. History never forgets

<Explain>
<What>
Deleting a file or a line creates a **new** commit. All older commits still contain the old content.
</What>
<Why>
That's the whole point of version control: you can always see and restore old versions, including the leaked password.
</Why>
<When>
The moment a secret is pushed, assume everyone who can read the repository (and every bot scanning it) has it.
</When>
<Where>
`git log -p`, `git show <commit>:<file>`, GitHub's commit history pages, forks, clones and CI caches.
</Where>
<How>
Below, a password is committed, then "removed". It's still one command away.
</How>
</Explain>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q shop && cd shop
printf 'DB_HOST=db.internal\nDB_PASSWORD=Sup3r-S3cret-Pa55word!\n' > config.env
git add . && git commit -qm "Add database config"
sed -i '/DB_PASSWORD/d' config.env && git commit -qam "Remove password"
echo "--- current file:"; cat config.env
echo "--- but history still has it:"
git show HEAD~1:config.env | grep PASSWORD
git log -p --format='commit: %s' -S 'DB_PASSWORD' | grep -E '^(commit:|[+-]DB_PASSWORD)'
```

```text output
--- current file:
DB_HOST=db.internal
--- but history still has it:
DB_PASSWORD=Sup3r-S3cret-Pa55word!
commit: Remove password
-DB_PASSWORD=Sup3r-S3cret-Pa55word!
commit: Add database config
+DB_PASSWORD=Sup3r-S3cret-Pa55word!
```

Line by line:

- The first commit adds `config.env` **with** the password.
- `sed -i '/DB_PASSWORD/d'` deletes that line, and we commit "Remove password".
- `cat config.env` shows the current file is clean.
- `git show HEAD~1:config.env` prints the file as it was one commit earlier: the password is right there.
- `git log -p -S 'DB_PASSWORD'` searches the **whole history** for commits that added or removed that text (the "pickaxe" search). Attackers use exactly this, or automated tools that do the same.
- The `-` line shows where it was removed, and the `+` line where it was added. Both still contain the full password.

### 3. The `.env` + `.gitignore` + `.env.example` pattern

<Explain>
<What>
Real values go in `.env` (ignored by Git). A template `.env.example` with the **names** of the variables, but no real values, is committed.
</What>
<Why>
New developers know which variables they need, while real secrets never enter the repository.
</Why>
<When>
At the start of every project, before the first secret exists.
</When>
<Where>
In the project root. Frameworks load `.env` automatically or with a small library: Next.js and Vite built in, Node `--env-file=.env` (Node 20.6+), Python `python-dotenv`, Docker Compose `env_file:`.
</Where>
<How>
Add `.env` (and variants like `.env.local`, `.env.production`) to `.gitignore`, but **not** `.env.example`. A `!` rule re-includes a file that an earlier pattern ignored.
</How>
</Explain>

```bash
git init -q app && cd app
cat > .gitignore <<'EOF'
# secrets and local config
.env
.env.*
!.env.example
*.pem
*.key
EOF
printf 'DB_HOST=\nDB_PASSWORD=\nPAYMENT_API_KEY=\n' > .env.example
printf 'DB_HOST=localhost\nDB_PASSWORD=dev-password-123\nPAYMENT_API_KEY=test_key_abc\n' > .env
cp .env .env.production
touch server.key
git add .
git status -s
git check-ignore -v .env .env.production server.key | awk '{print $2, "ignored by", $1}'
```

```text output
A  .env.example
A  .gitignore
.env ignored by .gitignore:2:.env
.env.production ignored by .gitignore:3:.env.*
server.key ignored by .gitignore:6:*.key
```

Line by line:

- `.gitignore` rules:
  - `.env` ignores the main secrets file.
  - `.env.*` ignores every variant (`.env.local`, `.env.production`, …).
  - `!.env.example` makes an exception: the template **is** tracked, even though `.env.*` would match it.
  - `*.pem` and `*.key` ignore private key files.
- `.env.example` has only names with empty values. It's safe to commit.
- `.env` has the real (here: development) values.
- `git add .` stages everything that isn't ignored. `git status -s` shows only `.env.example` and `.gitignore` were added: the real secrets were skipped automatically.
- `git check-ignore -v` proves which rule ignored each file.

A new teammate runs `cp .env.example .env` and fills in their own values.

### 4. Already committed? `git rm --cached`

<Explain>
<What>
`.gitignore` only affects **untracked** files. If `.env` was already committed, Git keeps tracking it even after you add it to `.gitignore`.
</What>
<Why>
This surprises many beginners: "I added it to .gitignore, why is it still in my commits?"
</Why>
<When>
You discover a secrets file is tracked.
</When>
<Where>
`git rm --cached <file>` removes the file from Git's tracking but **keeps it on your disk**.
</Where>
<How>
Then commit. **Important:** the old commits still contain it. If real secrets were ever pushed, rotate them (concept 9).
</How>
</Explain>

```bash
git init -q late && cd late
echo "API_KEY=abc123" > .env && git add . && git commit -qm "Initial commit (oops, includes .env)"
echo ".env" > .gitignore
echo "API_KEY=new-value" > .env
git status -s
git rm -q --cached .env
git add .gitignore && git commit -qm "Stop tracking .env"
git ls-files
ls -a | grep -c '^\.env$' | sed 's/$/ .env file still on disk/'
```

```text output
 M .env
?? .gitignore
.gitignore
1 .env file still on disk
```

Line by line:

- `.env` gets committed by mistake.
- We add `.env` to `.gitignore` and change `.env`. `git status` still shows ` M .env` (modified): Git keeps tracking it, because `.gitignore` doesn't apply to files already tracked.
- `git rm --cached .env` removes it from the index (tracking) only. `--cached` is what keeps the real file on disk.
- After committing, `git ls-files` (the list of tracked files) contains only `.gitignore`.
- The `.env` file is still in the folder, so the app keeps working, and future changes to it are ignored.

The first commit still has `API_KEY=abc123`, so that key must be treated as leaked.

### 5. Read secrets from the environment

<Explain>
<What>
Code should never contain secret **values**, only the **names** of environment variables it reads at runtime.
</What>
<Why>
The same code then runs everywhere (your laptop, CI, staging, production) with different secrets supplied by each environment. Nothing sensitive is in the code.
</Why>
<When>
Always: the "config in the environment" rule from the Twelve-Factor App methodology.
</When>
<Where>
Node `process.env.DB_PASSWORD`, Python `os.environ["DB_PASSWORD"]`, Bash `$DB_PASSWORD`, Docker `-e` / `env_file`, Kubernetes Secrets, Vercel and Netlify project settings.
</Where>
<How>
Fail fast with a clear error if a required variable is missing, instead of silently using a hard-coded fallback.
</How>
</Explain>

```bash
cat > deploy.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
: "${DEPLOY_TOKEN:?DEPLOY_TOKEN is not set (see .env.example)}"
echo "deploying with a token of ${#DEPLOY_TOKEN} characters"
EOF
chmod +x deploy.sh
./deploy.sh 2>&1 | sed 's#^.*deploy.sh: line [0-9]*: ##'
DEPLOY_TOKEN="t0k3n-from-secret-manager" ./deploy.sh
grep -c 't0k3n' deploy.sh | sed 's/$/ copies of the token inside the script/'
```

```text output
DEPLOY_TOKEN: DEPLOY_TOKEN is not set (see .env.example)
deploying with a token of 25 characters
0 copies of the token inside the script
```

Line by line:

- `set -euo pipefail` makes the script stop on errors and on unset variables (see the shell scripting lessons).
- `: "${DEPLOY_TOKEN:?message}"` checks that `DEPLOY_TOKEN` exists and isn't empty. If not, Bash prints the message and exits. `:` is a command that does nothing; it's only there so the check runs.
- `${#DEPLOY_TOKEN}` is the **length** of the value. We log the length, never the secret itself: logs are often less protected than code.
- Run without the variable, the script stops with a clear message (`sed` just trims the file path from Bash's error prefix).
- Run with `DEPLOY_TOKEN=...` in front, the variable exists only for that one command, and the script works.
- `grep -c` confirms the script file contains **no** copy of the token, so it is safe to commit.

```js
// Node.js equivalent (not run here)
const token = process.env.DEPLOY_TOKEN;
if (!token) throw new Error("DEPLOY_TOKEN is not set (see .env.example)");
```

### 6. Block secrets before they're committed: a pre-commit hook

<Explain>
<What>
A **pre-commit hook** is a script Git runs before every commit. If it exits with a non-zero code, the commit is cancelled.
</What>
<Why>
Prevention is much cheaper than cleanup: a secret blocked on your laptop never needs rotating.
</Why>
<When>
Every commit, automatically.
</When>
<Where>
`.git/hooks/pre-commit` (local only, not shared). Teams share hooks with the **pre-commit** framework (`.pre-commit-config.yaml`), Husky (Node) or Lefthook, usually running **gitleaks**.
</Where>
<How>
Our simple hook blocks staged `.env`, `.pem` and `.key` files, and staged lines that assign a long value to something called password/secret/token/api_key. Real scanners use hundreds of rules plus entropy checks.
</How>
</Explain>

```bash
git init -q guarded && cd guarded
cat > .git/hooks/pre-commit <<'HOOK'
#!/usr/bin/env bash
status=0
for f in $(git diff --cached --name-only --diff-filter=AM); do
  case "$f" in
    *.env|.env*|*.pem|*.key) [ "$f" = ".env.example" ] || { echo "BLOCKED: $f looks like a secrets file"; status=1; } ;;
  esac
done
if git diff --cached -U0 | grep -iE '^\+.*(password|secret|token|api_?key)[A-Z_]*["'"'"' ]*[:=] *["'"'"'][^"'"'"']{8,}["'"'"']' >/dev/null; then
  echo "BLOCKED: a staged line looks like a hard-coded secret"; status=1
fi
[ $status -eq 0 ] || echo "Commit cancelled. Move secrets to .env (ignored) and read them from the environment."
exit $status
HOOK
chmod +x .git/hooks/pre-commit
echo 'const apiKey = "q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT";' > pay.js
git add pay.js && git commit -qm "Add payments" || true
echo 'const apiKey = process.env.PAYMENT_API_KEY;' > pay.js
git add pay.js && git commit -qm "Add payments" && echo "commit accepted"
echo "KEY=x" > prod.env && git add prod.env && git commit -qm "Add prod env" || true
```

```text output
BLOCKED: a staged line looks like a hard-coded secret
Commit cancelled. Move secrets to .env (ignored) and read them from the environment.
commit accepted
BLOCKED: prod.env looks like a secrets file
Commit cancelled. Move secrets to .env (ignored) and read them from the environment.
```

Line by line:

- The hook is written into `.git/hooks/pre-commit` and made executable (Git ignores non-executable hooks).
- `git diff --cached --name-only --diff-filter=AM` lists staged files that were **A**dded or **M**odified.
- The `case` blocks file names ending in `.env`, starting with `.env`, or ending in `.pem` / `.key`, except `.env.example`.
- `git diff --cached -U0` shows only the staged changed lines. `grep -iE` looks for added lines (`^\+`) where something named password/secret/token/apikey is assigned a **quoted** value of 8+ characters, i.e. a hard-coded literal. (The `'"'"'` pieces are just how you write a single quote inside a single-quoted string in Bash.)
- **First attempt:** `apiKey = "q8Zt..."` matches, so the hook prints the reason and exits 1. Git cancels the commit. `|| true` only keeps the example running.
- **Second attempt:** the code reads `process.env.PAYMENT_API_KEY`. There's no hard-coded value, so the commit is accepted.
- **Third attempt:** a file named `prod.env` is blocked by the file-name rule.

A hook can be skipped with `git commit --no-verify`, and each developer must install it. That's why teams **also** scan in CI and on the server (concepts 7 and 8).

### 7. Scan the whole history with gitleaks

<Explain>
<What>
**gitleaks** is a free, open-source scanner with hundreds of rules for known secret formats (AWS, GitHub, Stripe, Slack, private keys…) plus generic high-entropy patterns. It can scan the working directory, staged changes, or **every commit in history**.
</What>
<Why>
Finds secrets that were committed long ago, by anyone, including ones later "deleted".
</Why>
<When>
Once when you adopt it (full history), then on every pull request in CI and as a pre-commit hook.
</When>
<Where>
`gitleaks git .` (history), `gitleaks dir .` (files on disk), `gitleaks git --pre-commit --staged` (hook mode). In CI: the official GitHub Action `gitleaks/gitleaks-action`. Alternatives: TruffleHog (also checks whether found keys are still live), detect-secrets, GitHub secret scanning.
</Where>
<How>
Exit code 1 means leaks were found, so CI fails automatically. Use `--redact` so the report doesn't print the secrets again in logs.
</How>
</Explain>

```bash
git init -q scanme && cd scanme
echo 'PAYMENT_API_KEY="q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT"' > settings.py
git add . && git commit -qm "Add payment settings"
echo 'PAYMENT_API_KEY = os.environ["PAYMENT_API_KEY"]' > settings.py
git commit -qam "Read key from environment"
echo "--- files on disk now:"
gitleaks dir --no-banner --log-level error . ; echo "exit code: $?"
echo "--- full git history:"
gitleaks git --no-banner --redact --log-level error --report-format json --report-path ../leaks.json . ; echo "exit code: $?"
jq -r '.[] | "\(.RuleID) in \(.File) line \(.StartLine), commit \"\(.Message)\", secret: \(.Secret)"' ../leaks.json
```

```text output
--- files on disk now:
exit code: 0
--- full git history:
exit code: 1
generic-api-key in settings.py line 1, commit "Add payment settings", secret: REDACTED
```

Line by line:

- The key is committed, then replaced by an environment lookup in the next commit.
- `gitleaks dir .` scans only the files as they are **now**: clean, exit code 0. A scanner that only looks at the current files gives a false sense of safety.
- `gitleaks git .` scans **every commit**. It finds the key in the old commit and exits with code 1.
- `--redact` replaces the secret with `REDACTED` in the report. `--report-format json --report-path` writes machine-readable results, and `--log-level error` hides the progress messages.
- `jq` prints the important fields: which rule matched, the file, the line, and the commit message where it appeared.

### 8. GitHub secret scanning and push protection

<Explain>
<What>
GitHub scans repositories for secrets from 200+ providers. **Push protection** goes further: it **rejects a push** that contains a recognised secret, before it reaches the repository.
</What>
<Why>
A server-side check that works for everyone, even if they never installed a hook.
</Why>
<When>
Turn it on for every repository. For **public** repositories, secret scanning is free and GitHub also **notifies the provider** (e.g. AWS, Stripe) of leaked keys so they can revoke them. For private repositories it's part of GitHub Secret Protection (paid, for organisations).
</When>
<Where>
Repository **Settings → Code security → Secret Protection / Push protection**. Personal accounts can also enable "Push protection for yourself" in their own settings.
</Where>
<How>
If a push is blocked, remove the secret from the commit (`git commit --amend`, or an interactive rebase if it's older), rotate it if it was real, and push again. Bypassing requires a stated reason and is logged.
</How>
</Explain>

What a blocked push looks like (from GitHub, not run here):

```text
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - GITHUB PUSH PROTECTION
remote:   —————————————————————————————————————————
remote:     Resolve the following violations before pushing again
remote:     - Push cannot contain secrets
remote:       —— Stripe API Key ——————————————————
remote:         locations:
remote:           - commit: 8f3a2c1...
remote:             path: src/pay.js:3
```

### 9. A secret leaked: what now?

<Explain>
<What>
An **incident response** routine. The order matters.
</What>
<Why>
Attackers act within minutes. Cleaning Git history takes longer and **doesn't** remove copies others already made, so it can't be the first step.
</Why>
<When>
The moment you find a real secret in a commit that was pushed, or might have been seen by anyone.
</When>
<Where>
In the provider's dashboard (AWS IAM, Stripe, GitHub settings, your database), your team's chat, and the provider's access logs.
</Where>
<How>
Revoke and rotate first, then check for abuse, then clean up and prevent a repeat.
</How>
</Explain>

| Step | What to do | Example |
| --- | --- | --- |
| 1. **Revoke / rotate** | Disable the old secret and create a new one **immediately** | Delete the AWS access key, create a new one |
| 2. **Update** | Put the new secret where apps read it (secret manager, platform env vars) and redeploy | Vercel env var updated |
| 3. **Investigate** | Check the provider's logs for use of the old key since the leak | CloudTrail, Stripe logs, DB audit log |
| 4. **Inform** | Tell your team / security team; follow your incident process | Incident ticket |
| 5. **Clean history** (optional) | Rewrite history to remove the secret (next concept), force-push, ask GitHub support to purge cached views if needed | `git filter-repo` |
| 6. **Prevent** | Add the missing `.gitignore` rule, hook, CI scan and push protection | Pre-commit + gitleaks in CI |

**Never** skip step 1 because "the repo is private" or "I deleted it after one minute".

### 10. Removing a secret from history: `git filter-repo`

<Explain>
<What>
`git filter-repo` rewrites **every commit** in a repository, for example replacing a secret string with `***REMOVED***` or deleting a file from all of history.
</What>
<Why>
So the secret no longer appears when browsing or cloning the repository in the future.
</Why>
<When>
**After** rotating the secret. Mainly for repos that will be shared more widely, or where policy requires it.
</When>
<Where>
Install with `pip install git-filter-repo`. It's the tool recommended by the Git project (older: BFG Repo-Cleaner; avoid the slow, error-prone `git filter-branch`).
</Where>
<How>
It changes every commit hash after the first affected commit, so it's a **history rewrite**: coordinate with the team, force-push every branch and tag, and have everyone re-clone. Forks, existing clones, CI caches and pull request refs on GitHub can still contain the old commits.
</How>
</Explain>

```bash
git init -q cleanup && cd cleanup
echo "app" > app.js && git add . && git commit -qm "Add app"
echo 'STRIPE_KEY=q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT' > keys.txt && git add . && git commit -qm "Add keys"
echo "more" >> app.js && git commit -qam "More app code"
echo "before: $(git log --all -p | grep -c 'q8Zt3Lm9')" occurrences in history
echo 'q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT==>***REMOVED***' > ../replacements.txt
git filter-repo --force --replace-text ../replacements.txt >/dev/null 2>&1
echo "after:  $(git log --all -p | grep -c 'q8Zt3Lm9')" occurrences in history
git show HEAD~1:keys.txt
git log --format=%s
```

```text output
before: 1 occurrences in history
after:  0 occurrences in history
STRIPE_KEY=***REMOVED***
More app code
Add keys
Add app
```

Line by line:

- The secret is committed in "Add keys", and one more commit follows.
- `git log --all -p | grep -c` counts lines in the full history that contain the secret: 1.
- `replacements.txt` contains one rule: `old text==>new text`. You can list many secrets, one per line.
- `git filter-repo --replace-text` rewrites every commit, replacing the text everywhere it appears. `--force` is needed because this isn't a fresh clone (filter-repo is careful by default). We send its progress messages to `/dev/null` to keep the output short.
- Afterwards the secret appears 0 times. The old commit now contains `***REMOVED***`, while the commit messages and structure stay the same.
- Every rewritten commit has a **new hash**. You would now `git push --force --all` and `--tags` (temporarily allowing force pushes), and teammates must re-clone.

To delete a whole file from history instead: `git filter-repo --invert-paths --path keys.txt`.

### 11. Where secrets should live instead

<Explain>
<What>
Proper places that store secrets encrypted, control who can read them, and log access.
</What>
<Why>
"Not in Git" isn't enough: secrets in a shared Google Doc, chat message or email are leaks waiting to happen.
</Why>
<When>
Choose based on where the code runs.
</When>
<Where>
See the table below.
</Where>
<How>
Best of all are **no long-lived secrets**: short-lived credentials issued on demand, e.g. GitHub Actions **OIDC** to AWS/Azure/GCP instead of storing cloud keys in GitHub at all.
</How>
</Explain>

| Where the code runs | Store secrets in |
| --- | --- |
| Your laptop (development) | `.env` (ignored), or a password manager CLI (1Password, Bitwarden) |
| GitHub Actions | Repository / environment **secrets** (`${{ secrets.NAME }}`); for clouds, **OIDC** with no stored keys |
| Vercel / Netlify / Render | Project environment variables in the dashboard |
| Docker | Pass at runtime (`-e`, `--env-file`, Docker/Compose secrets), **never** `ENV` or `COPY .env` in the Dockerfile |
| Kubernetes | Kubernetes Secrets (with encryption at rest), External Secrets Operator, Sealed Secrets |
| Cloud apps | AWS Secrets Manager / SSM Parameter Store, Azure Key Vault, Google Secret Manager, HashiCorp Vault |
| Team sharing | A password manager vault, **not** Slack, WhatsApp or email |

If you **must** keep encrypted secrets in Git (common in GitOps), use tools built for it: **SOPS**, **Sealed Secrets** or **git-crypt**. The repository then only ever contains encrypted values.

## Hands-on

Set up a new project the safe way, then try to sneak a secret in:

```bash
git init -q safe-project && cd safe-project
printf '.env\n.env.*\n!.env.example\n*.pem\n*.key\nnode_modules/\n' > .gitignore
printf 'DATABASE_URL=\nJWT_SECRET=\n' > .env.example
printf 'DATABASE_URL=postgres://dev:dev@localhost/app\nJWT_SECRET=local-dev-only-secret\n' > .env
cat > .git/hooks/pre-commit <<'HOOK'
#!/usr/bin/env bash
gitleaks git --pre-commit --staged --no-banner --redact --log-level error . && exit 0
echo "pre-commit: gitleaks found a secret, commit cancelled"; exit 1
HOOK
chmod +x .git/hooks/pre-commit
echo 'const jwt = process.env.JWT_SECRET;' > auth.js
git add . && git commit -qm "Initial project setup" && echo "1) setup committed: $(git ls-files | tr '\n' ' ')"
echo 'const fallbackSecret = "q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT";' >> auth.js
git add auth.js && git commit -qm "Add fallback secret" || echo "2) blocked"
git restore --staged auth.js && git restore auth.js
echo "3) auth.js is clean again: $(cat auth.js)"
```

```text output
1) setup committed: .env.example .gitignore auth.js 
pre-commit: gitleaks found a secret, commit cancelled
2) blocked
3) auth.js is clean again: const jwt = process.env.JWT_SECRET;
```

Line by line:

- `.gitignore` and `.env.example` are created **first**, before any real values exist.
- `.env` holds local development values. It's ignored, so `git add .` never stages it.
- The pre-commit hook runs gitleaks on **staged** changes only (`--pre-commit --staged`). If gitleaks finds nothing it exits 0 and the hook allows the commit; otherwise the hook prints a message and exits 1.
- **Commit 1** succeeds. `git ls-files` lists the tracked files: `.env.example`, `.gitignore` and `auth.js`, with no `.env`. `auth.js` only reads `process.env.JWT_SECRET`, so there's nothing for gitleaks to find.
- **Commit 2** adds a hard-coded "fallback" secret. gitleaks finds it, the hook prints its message and exits 1, Git cancels the commit, and our `|| echo` prints `2) blocked`.
- `git restore --staged` unstages the change and `git restore` throws it away, so the file is back to the safe version.

"Fallback" secrets (`process.env.JWT_SECRET || "some-default"`) are a very common way real secrets end up in code. If a secret is missing, the app should **fail**, not quietly use a value everyone can read on GitHub.

## Real-world example

A developer at Alex's company builds a quick script to sync orders with a payment provider and, to test it, pastes the live API key straight into `sync.js`. He commits and pushes to a feature branch. Because the organisation turned on **push protection**, GitHub rejects the push and names the file and line. He moves the key into `.env`, reads it with `process.env.PAYMENT_API_KEY`, amends the commit and pushes again.

A month earlier, before push protection was enabled, the team wasn't so lucky: an intern committed an AWS access key to a **public** demo repo. Within minutes, automated bots found it and launched GPU servers for crypto-mining. AWS also detected the exposed key and alerted the account. The team followed the incident routine: **deactivated the key first**, terminated the unknown servers, checked CloudTrail to see what else the key had touched, created a new key stored in AWS Secrets Manager, and only then rewrote the repository history. Afterwards they added gitleaks to CI for every repository and replaced stored cloud keys in GitHub Actions with OIDC.

## Common mistakes

- **"I deleted it in the next commit, so it's fine."** It's still in history and in every clone.
- **Adding `.env` to `.gitignore` after it's already tracked** and assuming that's enough. Use `git rm --cached`, and rotate.
- **Rewriting history but not rotating** the secret. Copies already exist elsewhere.
- **Hard-coded "fallback" values:** `process.env.SECRET || "dev-secret-123"` in production code.
- **Secrets in Dockerfiles** (`ENV API_KEY=...`, `COPY .env .`): they end up inside every image layer and registry.
- **Logging secrets:** `console.log(config)` or printing environment variables in CI logs.
- **Committing `.env.example` with real values** copied from `.env`.
- **Scanning only the current files,** not the full history.
- **Sharing secrets over chat or email** instead of a password manager or secret manager.
- **Relying only on a local hook** that teammates never installed and anyone can skip with `--no-verify`.

## Security lens

<Callout type="security">
Assume any secret that touched Git is compromised. Rotation is the fix; everything else is cleanup and prevention.
</Callout>

- **Defence in depth:** `.gitignore` → pre-commit hook → push protection on the server → CI history scan → monitoring of provider alerts. Each layer catches what the previous one missed.
- **Least privilege:** give each key only the permissions it needs, so a leak does less damage (a read-only key for a reporting script, not an admin key).
- **Short-lived credentials beat stored secrets:** OIDC federation for CI, temporary cloud credentials, and tokens that expire.
- **Mask secrets in CI logs.** GitHub Actions masks registered secrets automatically, but values you derive or print in other forms (encoded, split) are not masked.
- **Watch for "secret sprawl":** the same key copied into ten repos and five CI systems. Centralise secrets in one manager and reference them.
- **Leaked keys show up in unexpected places:** Git history, Docker images, mobile app bundles, front-end JavaScript (anything sent to the browser is public), Jupyter notebook outputs and crash reports.

## Interview questions

<QA q="You accidentally pushed an API key to GitHub. What do you do?">
First revoke or rotate the key immediately at the provider, because the commit may already have been copied or scanned by bots. Then deploy the new key from a proper secret store, check the provider's logs for misuse since the leak, and inform the team or follow the incident process. After that, optionally remove the key from history with git filter-repo and a coordinated force push, and add prevention such as .gitignore rules, a pre-commit secret scanner, CI scanning and push protection.
</QA>

<QA q="Why doesn't deleting the file in a new commit remove the secret?">
Git stores every commit as a snapshot, so the earlier commit that added the file still contains it. Anyone with access to the repository history, including clones, forks and caches, can retrieve it with commands such as git show or git log -p.
</QA>

<QA q="I added .env to .gitignore but Git still tracks it. Why?">
.gitignore only applies to untracked files. Once a file has been committed, Git keeps tracking it. Running git rm --cached .env stops tracking it while keeping the local file, and committing that change removes it from future commits, though it remains in earlier history.
</QA>

<QA q="How should applications receive secrets?">
Applications should read secrets at runtime from environment variables or a secret manager, rather than having them in the code or repository. In development a git-ignored .env file can provide them, in CI the platform's secret store or short-lived OIDC credentials, and in production services such as AWS Secrets Manager, Azure Key Vault, Vault or Kubernetes Secrets, with least-privilege access and rotation.
</QA>

<QA q="What is the difference between a pre-commit secret scanner and GitHub push protection?">
A pre-commit scanner runs on the developer's machine before a commit is created, but it must be installed by each developer and can be skipped. Push protection runs on GitHub's servers and blocks pushes containing recognised secrets for everyone, with bypasses requiring a reason and being audited. Using both, plus history scanning in CI, gives defence in depth.
</QA>

## Key terms

<Terms>
  <Term name="Secret">Value that grants access, such as a password, token or key.</Term>
  <Term name=".env file">Local file of environment variables, never committed.</Term>
  <Term name=".env.example">Committed template listing required variables without values.</Term>
  <Term name="git rm --cached">Stop tracking a file but keep it on disk.</Term>
  <Term name="Pre-commit hook">Script that runs before each commit and can block it.</Term>
  <Term name="gitleaks">Open-source scanner for secrets in files and Git history.</Term>
  <Term name="Push protection">GitHub server-side blocking of pushes containing secrets.</Term>
  <Term name="Rotation">Replacing a secret with a new one and disabling the old.</Term>
  <Term name="git filter-repo">Tool to rewrite history, e.g. to remove secrets.</Term>
  <Term name="Secret manager">Service that stores, controls and audits access to secrets.</Term>
  <Term name="OIDC">Short-lived credential exchange that avoids storing cloud keys in CI.</Term>
</Terms>
