<BigIdea>
<Tr>
<En>
A **secret** is anything that gives access: passwords, API keys, tokens, private keys, database connection strings. **Never commit them.** Git keeps every version forever, so a password deleted in the next commit is **still in history**, in every clone and fork. Keep secrets in a **`.env`** file listed in **`.gitignore`**, commit a **`.env.example`** with empty values, and have your code read secrets from **environment variables**. Add guards (a **pre-commit scanner** like gitleaks, GitHub **push protection**), and if a secret does leak: **rotate it first**. Cleaning history alone never makes a leaked secret safe again.
</En>
<Ur>
**Secret (raaz)** har wo cheez hai jo rasai deti hai: passwords, API keys, tokens, private keys, database connection strings. **Inhe kabhi commit na karein.** Git har version hamesha rakhta hai, isliye agle commit me mitaya password **ab bhi tareekh me** hai, har clone aur fork me. Raaz **`.gitignore`** me likhi **`.env`** file me rakhein, khaali values wali **`.env.example`** commit karein, aur code ko raaz **environment variables** se parhne dein. Pehredaar lagayen (gitleaks jaisa **pre-commit scanner**, GitHub **push protection**), aur agar raaz leak ho jaye: **pehle use badlein (rotate)**. Sirf tareekh saaf karna leak hua raaz kabhi dobara mehfooz nahi banata.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

Keeping secrets out of Git is a set of habits and tools, in five layers:

```text
 1. Separate      code (in Git)            secrets (.env, secret manager)
 2. Ignore        .gitignore: .env, *.pem, *.key, credentials.json
 3. Prevent       pre-commit hook / push protection    → block before it leaves your machine
 4. Detect        scan the full history in CI           → find old leaks
 5. Respond       revoke + rotate → investigate → clean history (optional)
```

</En>
<Ur>

Raazon ko Git se bahar rakhna aadaton aur tools ka majmua hai, paanch tehon me:

```text
 1. Separate      code (in Git)            secrets (.env, secret manager)
 2. Ignore        .gitignore: .env, *.pem, *.key, credentials.json
 3. Prevent       pre-commit hook / push protection    → block before it leaves your machine
 4. Detect        scan the full history in CI           → find old leaks
 5. Respond       revoke + rotate → investigate → clean history (optional)
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **It's one of the most common real breaches.** Bots scan every public GitHub push within seconds for cloud keys and tokens; leaked AWS keys are often abused for crypto-mining within minutes, leaving the owner with huge bills.
- **Private repos aren't safe either:** they get cloned to laptops, copied to CI, made public by mistake, or read by an attacker with one stolen token who then searches them for more secrets.
- **Git never forgets.** Removing the line later doesn't remove it from history.
- **Interviews:** "How do you manage secrets?" is a standard DevOps and DevSecOps question.

</En>
<Ur>

- **Ye sab se aam asli breaches me se hai.** Bots har public GitHub push ko seconds me cloud keys aur tokens ke liye scan karte hain; leak hui AWS keys aksar minton me crypto-mining ke liye istemal hoti hain, aur maalik par bhaari bill aata hai.
- **Private repos bhi mehfooz nahi:** laptops par clone hoti hain, CI me copy hoti hain, ghalti se public ho jati hain, ya ek chori ke token wala hamla awar unhe parh kar mazeed raaz dhoondhta hai.
- **Git kabhi nahi bhoolta.** Baad me line hatana use tareekh se nahi hatata.
- **Interviews:** "Raaz kaise sambhalte ho?" DevOps aur DevSecOps ka aam sawal hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **From the first commit** of every project: create `.gitignore` and `.env.example` before writing code that needs a key.
- **Every commit:** the pre-commit hook runs automatically.
- **In CI:** scan the full history on every pull request.
- **In production:** secrets come from the platform (Vercel environment variables, Kubernetes Secrets, AWS Secrets Manager), never from the repository.

</En>
<Ur>

- Har project ke **pehle commit se**: key wala code likhne se pehle `.gitignore` aur `.env.example` banayen.
- **Har commit:** pre-commit hook khud chalta hai.
- **CI me:** har pull request par poori tareekh scan.
- **Production me:** raaz platform se aate hain (Vercel environment variables, Kubernetes Secrets, AWS Secrets Manager), repository se kabhi nahi.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
echo ".env" >> .gitignore          # real values stay local
cp .env .env.example               # then blank every value in the example
git rm --cached .env               # stop tracking an already-committed file
process.env.DB_PASSWORD            # code reads names, never values
gitleaks git .                     # scan every commit for secrets
# leaked? rotate FIRST, then investigate, then clean history
```

</En>
<Ur>

```text
echo ".env" >> .gitignore          # asli values local rahen
cp .env .env.example               # phir example ki har value khaali karo
git rm --cached .env               # pehle se commit file ki tracking band

gitleaks git .                     # har commit me raaz scan
# leak hua? PEHLE rotate, phir tafteesh, phir tareekh ki safai
```

</Ur>

</How>

## Picture it

<Tr>
<En>

Committing a password is like **writing your door code on a page of a book, then photocopying the book and handing it out**. Tearing the page out of **your** copy (deleting the file in a new commit) doesn't help: every photocopy (clone, fork, CI cache, backup) still has it. The only real fix is to **change the lock** (rotate the secret). The right habit is to keep the code on a **separate card in your wallet** (`.env`, never committed), while the book only says "the code is on the card" (`.env.example`).

</En>
<Ur>

Password commit karna aisa hai jaise **darwaze ka code kitab ke safhe par likh kar kitab ki photocopies baant dena**. **Apni** copy se safha phaar dena (naye commit me file mitana) kaam nahi aata: har photocopy (clone, fork, CI cache, backup) me ab bhi hai. Asal hal sirf **taala badalna** hai (raaz rotate karna). Sahi aadat ye ke code **batue ke alag card** par rakhein (`.env`, kabhi commit nahi), aur kitab me sirf likha ho "code card par hai" (`.env.example`).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="What counts as a secret?">

<Tr>
<En>

Anything that lets someone **log in, call an API, decrypt data or impersonate** you or your service. Ask: "could a stranger do damage with this value?" If yes, it's a secret. Typical hiding places: `.env` files, `config.js`, `settings.py`, `docker-compose.yml`, Terraform files and state, Jupyter notebooks, test scripts, CI config, `.npmrc` / `.pypirc`.

| Secret | Typical look | Damage if leaked |
| --- | --- | --- |
| Cloud access key | `AKIA...` (AWS) | Attacker controls your cloud: data theft, crypto-mining bills |
| Payment API key | `sk_live_...` (Stripe) | Refunds, payouts, customer data |
| Database URL | `postgres://admin:pass@db:5432/app` | Read or delete all data |
| GitHub token | `ghp_...`, `github_pat_...` | Push malicious code, read private repos |
| Private key | `-----BEGIN PRIVATE KEY-----` | Impersonate your server, decrypt traffic |
| JWT secret | random string in config | Forge login tokens for any user, admin included |

**Not secrets:** public keys, a public Firebase web config, the **name** of a variable, or a placeholder like `DB_PASSWORD=change-me`.

</En>
<Ur>

Har wo cheez jo kisi ko **login, API call, data decrypt, ya aap ya aap ki service ban jane** de. Poochein: "kya koi ajnabi is value se nuqsan kar sakta hai?" Haan, to ye raaz hai. Aam chhupne ki jagahen: `.env` files, `config.js`, `settings.py`, `docker-compose.yml`, Terraform files aur state, Jupyter notebooks, test scripts, CI config, `.npmrc` / `.pypirc`.

| Raaz | Aam shakal | Leak par nuqsan |
| --- | --- | --- |
| Cloud access key | `AKIA...` (AWS) | Hamla awar aap ka cloud chalaye: data chori, crypto-mining bills |
| Payment API key | `sk_live_...` (Stripe) | Refunds, payouts, customer data |
| Database URL | `postgres://admin:pass@db:5432/app` | Saara data parhna ya mitana |
| GitHub token | `ghp_...`, `github_pat_...` | Bad-niyat code push, private repos parhna |
| Private key | `-----BEGIN PRIVATE KEY-----` | Aap ka server ban jana, traffic decrypt |
| JWT secret | config me random string | Kisi bhi user, admin samet, ke login tokens jaali banana |

**Raaz nahi:** public keys, public Firebase web config, variable ka **naam**, ya `DB_PASSWORD=change-me` jaisa placeholder.

</Ur>
</Tr>

</Step>

<Step title="History never forgets">

<Tr>
<En>

Deleting a file or a line creates a **new** commit, and every older commit still holds the old content. That's the whole point of version control. The moment a secret is pushed, assume everyone who can read the repository (and every bot scanning it) has it. Below, a password is committed, then "removed", and it's still one command away.

</En>
<Ur>

File ya line mitana **naya** commit banata hai, aur har purane commit me purana mawad ab bhi hai. Version control ka maqsad hi yahi hai. Jis lamhe raaz push hua, maan lein ke repository parh sakne wala har shakhs (aur scan karne wala har bot) use paa chuka. Neeche password commit hota hai, phir "hataya" jata hai, aur phir bhi ek command door hai.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q shop && cd shop
printf 'DB_HOST=db.internal\nDB_PASSWORD=Sup3r-S3cret-Pa55word!\n' > config.env
git add . && git commit -qm "Add database config"
sed -i '/DB_PASSWORD/d' config.env && git commit -qam "Remove password"
echo "--- current file:"; cat config.env
echo "--- but history still has it:"
git show HEAD~1:config.env | grep PASSWORD
git log -p --format='commit: %s' -S 'DB_PASSWORD' | grep -E '^(commit:|[+-]DB_PASSWORD)'
```

```text output
--- current file:
DB_HOST=db.internal
--- but history still has it:
DB_PASSWORD=Sup3r-S3cret-Pa55word!
commit: Remove password
-DB_PASSWORD=Sup3r-S3cret-Pa55word!
commit: Add database config
+DB_PASSWORD=Sup3r-S3cret-Pa55word!
```

<Happened>
<Tr>
<En>

- The current file is clean, but `git show HEAD~1:config.env` printed the file one commit earlier: password right there.
- `git log -p -S 'DB_PASSWORD'` (the "pickaxe" search) found every commit that added or removed that text. Attackers use exactly this, or tools that do the same.
- The `+` line shows where it was added and the `-` line where it was removed; both contain the full password.

</En>
<Ur>

- Mojooda file saaf hai, lekin `git show HEAD~1:config.env` ne ek commit pehle ki file chhaapi: password wahin hai.
- `git log -p -S 'DB_PASSWORD'` ("pickaxe" search) ne har wo commit dhoondha jis ne ye text jora ya hataya. Hamla awar bilkul yahi, ya yahi karne wale tools, istemal karte hain.
- `+` line dikhati hai kahan jora gaya aur `-` line kahan hataya gaya; dono me poora password hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The .env + .gitignore + .env.example pattern">

<Tr>
<En>

Real values go in `.env`, ignored by Git. A template `.env.example` with the variable **names** but no real values is committed, so new developers know what they need while real secrets never enter the repo. Frameworks load `.env` automatically or with a small library (Next.js and Vite built in, Node `--env-file=.env`, Python `python-dotenv`, Docker Compose `env_file:`). Ignore `.env` and its variants, but **not** `.env.example`: a `!` rule re-includes a file an earlier pattern ignored.

</En>
<Ur>

Asli values `.env` me, jo Git ignore karta hai. Variables ke **naam** wala lekin asli values ke baghair saancha `.env.example` commit hota hai, taa ke naye developers jaanen kya chahiye aur asli raaz kabhi repo me na aayen. Frameworks `.env` khud ya chhoti library se load karte hain (Next.js aur Vite me andar se, Node `--env-file=.env`, Python `python-dotenv`, Docker Compose `env_file:`). `.env` aur us ki shaklen ignore karein, lekin `.env.example` **nahi**: `!` rule pehle pattern ki ignore ki file ko wapas shamil karta hai.

</Ur>
</Tr>

```bash
git init -q app && cd app
cat > .gitignore <<'EOF'
# secrets and local config
.env
.env.*
!.env.example
*.pem
*.key
EOF
printf 'DB_HOST=\nDB_PASSWORD=\nPAYMENT_API_KEY=\n' > .env.example
printf 'DB_HOST=localhost\nDB_PASSWORD=dev-password-123\nPAYMENT_API_KEY=test_key_abc\n' > .env
cp .env .env.production
touch server.key
git add .
git status -s
git check-ignore -v .env .env.production server.key | awk '{print $2, "ignored by", $1}'
```

```text output
A  .env.example
A  .gitignore
.env ignored by .gitignore:2:.env
.env.production ignored by .gitignore:3:.env.*
server.key ignored by .gitignore:6:*.key
```

<Happened>
<Tr>
<En>

- `.env` ignores the main secrets file, `.env.*` every variant, `!.env.example` makes the template an exception, and `*.pem` / `*.key` ignore private keys.
- `git add .` staged only `.env.example` and `.gitignore`: the real secrets were skipped automatically.
- `git check-ignore -v` proved which rule ignored each file.

A new teammate runs `cp .env.example .env` and fills in their own values.

</En>
<Ur>

- `.env` asal raaz wali file ignore karta hai, `.env.*` har shakal, `!.env.example` saanche ko istisna banata hai, aur `*.pem` / `*.key` private keys ignore karte hain.
- `git add .` ne sirf `.env.example` aur `.gitignore` stage kin: asli raaz khud chhoot gaye.
- `git check-ignore -v` ne sabit kiya kis rule ne kaunsi file ignore ki.

Naya saathi `cp .env.example .env` chala kar apni values bharta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Already committed? git rm --cached">

<Tr>
<En>

`.gitignore` only affects **untracked** files. If `.env` was already committed, Git keeps tracking it even after you add it to `.gitignore`, which surprises many beginners. `git rm --cached <file>` stops tracking it but **keeps it on your disk**; then commit. The old commits still contain it, so if real secrets were ever pushed, rotate them.

</En>
<Ur>

`.gitignore` sirf **untracked** files par asar karti hai. Agar `.env` pehle se commit thi, to `.gitignore` me daalne ke baad bhi Git use track karta rehta hai, jo bohot se naye logon ko hairan karta hai. `git rm --cached <file>` tracking band karta hai lekin file **disk par rakhta** hai; phir commit karein. Purane commits me ab bhi hai, isliye agar asli raaz kabhi push hue, unhe rotate karein.

</Ur>
</Tr>

```bash
git init -q late && cd late
echo "API_KEY=abc123" > .env && git add . && git commit -qm "Initial commit (oops, includes .env)"
echo ".env" > .gitignore
echo "API_KEY=new-value" > .env
git status -s
git rm -q --cached .env
git add .gitignore && git commit -qm "Stop tracking .env"
git ls-files
ls -a | grep -c '^\.env$' | sed 's/$/ .env file still on disk/'
```

```text output
 M .env
?? .gitignore
.gitignore
1 .env file still on disk
```

<Happened>
<Tr>
<En>Even with `.env` in `.gitignore`, status still showed ` M .env`: it's tracked. `git rm --cached` removed it from tracking only (`--cached` keeps the real file). After committing, `git ls-files` lists only `.gitignore`, and `.env` is still on disk so the app keeps working. The first commit still has `API_KEY=abc123`, so that key must be treated as leaked.</En>
<Ur>`.gitignore` me `.env` hone ke bawajood status ne ` M .env` dikhaya: ye track ho rahi hai. `git rm --cached` ne sirf tracking se hataya (`--cached` asli file rakhta hai). Commit ke baad `git ls-files` me sirf `.gitignore` hai, aur `.env` disk par maujood hai taa ke app chalti rahe. Pehle commit me ab bhi `API_KEY=abc123` hai, isliye wo key leak shuda samjhi jaye.</Ur>
</Tr>
</Happened>

<Step title="Read secrets from the environment">

<Tr>
<En>

Code should contain only the **names** of environment variables, never secret **values**. The same code then runs everywhere (laptop, CI, staging, production) with secrets supplied by each environment: Node `process.env.DB_PASSWORD`, Python `os.environ["DB_PASSWORD"]`, Bash `$DB_PASSWORD`, Docker `-e`, Kubernetes Secrets, Vercel settings. **Fail fast** with a clear error if a required variable is missing, instead of silently using a hard-coded fallback.

</En>
<Ur>

Code me sirf environment variables ke **naam** hon, raaz ki **values** kabhi nahi. Phir wahi code har jagah (laptop, CI, staging, production) chalta hai aur har mahol apne raaz deta hai: Node `process.env.DB_PASSWORD`, Python `os.environ["DB_PASSWORD"]`, Bash `$DB_PASSWORD`, Docker `-e`, Kubernetes Secrets, Vercel settings. Zaroori variable na ho to chupke se code me likhi fallback value lene ke bajaye saaf error ke saath **foran ruk jayen**.

</Ur>
</Tr>

```bash
cat > deploy.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
: "${DEPLOY_TOKEN:?DEPLOY_TOKEN is not set (see .env.example)}"
echo "deploying with a token of ${#DEPLOY_TOKEN} characters"
EOF
chmod +x deploy.sh
./deploy.sh 2>&1 | sed 's#^.*deploy.sh: line [0-9]*: ##'
DEPLOY_TOKEN="t0k3n-from-secret-manager" ./deploy.sh
grep -c 't0k3n' deploy.sh | sed 's/$/ copies of the token inside the script/'
```

```text output
DEPLOY_TOKEN: DEPLOY_TOKEN is not set (see .env.example)
deploying with a token of 25 characters
0 copies of the token inside the script
```

<Happened>
<Tr>
<En>

- The `:?message` check stops the script with a clear message if `DEPLOY_TOKEN` is missing or empty (`:` is a do-nothing command, there only so the check runs).
- We log the **length** of the token, never the token: logs are often less protected than code.
- `DEPLOY_TOKEN=… ./deploy.sh` set the variable for that one command only, and the script worked.
- `grep -c` confirmed the script holds **no** copy of the token, so it's safe to commit.

```js
// Node.js equivalent (not run here)
const token = process.env.DEPLOY_TOKEN;
if (!token) throw new Error("DEPLOY_TOKEN is not set (see .env.example)");
```

</En>
<Ur>

- `:?message` wala check `DEPLOY_TOKEN` na hone ya khaali hone par saaf message ke saath script rok deta hai (`:` kuch na karne wali command hai, sirf is liye ke check chale).
- Hum token ki **lambai** log karte hain, token kabhi nahi: logs aksar code se kam mehfooz hote hain.
- `DEPLOY_TOKEN=… ./deploy.sh` ne variable sirf us ek command ke liye set kiya, aur script chali.
- `grep -c` ne tasdeeq ki script me token ki **koi** copy nahi, isliye commit karna mehfooz hai.

```js
// Node.js ka barabar (yahan nahi chalaya)
const token = process.env.DEPLOY_TOKEN;

```

<Step title="Block secrets before they're committed">

<Tr>
<En>

A **pre-commit hook** is a script Git runs before every commit; a non-zero exit cancels the commit. Prevention is far cheaper than cleanup: a secret blocked on your laptop never needs rotating. `.git/hooks/pre-commit` is local only; teams share hooks with the **pre-commit** framework, Husky or Lefthook, usually running **gitleaks**. Our simple hook blocks staged `.env`, `.pem` and `.key` files, and staged lines that assign a long quoted value to something named password/secret/token/api_key.

</En>
<Ur>

**Pre-commit hook** ek script hai jo Git har commit se pehle chalata hai; non-zero exit commit radd kar deta hai. Bachao safai se kahin sasta hai: laptop par roka gaya raaz kabhi rotate nahi karna padta. `.git/hooks/pre-commit` sirf local hai; teams hooks **pre-commit** framework, Husky ya Lefthook se share karti hain, aam tor par **gitleaks** chala kar. Hamara saada hook staged `.env`, `.pem` aur `.key` files rokta hai, aur wo staged lines jo password/secret/token/api_key naam wali cheez ko lambi quoted value dein.

</Ur>
</Tr>

```bash
git init -q guarded && cd guarded
cat > .git/hooks/pre-commit <<'HOOK'
#!/usr/bin/env bash
status=0
for f in $(git diff --cached --name-only --diff-filter=AM); do
  case "$f" in
    *.env|.env*|*.pem|*.key) [ "$f" = ".env.example" ] || { echo "BLOCKED: $f looks like a secrets file"; status=1; } ;;
  esac
done
if git diff --cached -U0 | grep -iE '^\+.*(password|secret|token|api_?key)[A-Z_]*["'"'"' ]*[:=] *["'"'"'][^"'"'"']{8,}["'"'"']' >/dev/null; then
  echo "BLOCKED: a staged line looks like a hard-coded secret"; status=1
fi
[ $status -eq 0 ] || echo "Commit cancelled. Move secrets to .env (ignored) and read them from the environment."
exit $status
HOOK
chmod +x .git/hooks/pre-commit
echo 'const apiKey = "q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT";' > pay.js
git add pay.js && git commit -qm "Add payments" || true
echo 'const apiKey = process.env.PAYMENT_API_KEY;' > pay.js
git add pay.js && git commit -qm "Add payments" && echo "commit accepted"
echo "KEY=x" > prod.env && git add prod.env && git commit -qm "Add prod env" || true
```

```text output
BLOCKED: a staged line looks like a hard-coded secret
Commit cancelled. Move secrets to .env (ignored) and read them from the environment.
commit accepted
BLOCKED: prod.env looks like a secrets file
Commit cancelled. Move secrets to .env (ignored) and read them from the environment.
```

<Happened>
<Tr>
<En>

- `git diff --cached --name-only --diff-filter=AM` listed staged **A**dded or **M**odified files; the `case` blocks secret-looking names except `.env.example`.
- `git diff --cached -U0 | grep -iE …` looks for **added** lines assigning a quoted value of 8+ characters to a secret-looking name. (`'"'"'` is just how you write a single quote inside a single-quoted Bash string.)
- **Attempt 1:** a hard-coded `apiKey` was blocked. **Attempt 2:** reading `process.env.PAYMENT_API_KEY` was accepted. **Attempt 3:** `prod.env` was blocked by its name. (`|| true` only keeps the example running.)

A hook can be skipped with `git commit --no-verify`, and each developer must install it, which is why teams **also** scan in CI and on the server.

</En>
<Ur>

- `git diff --cached --name-only --diff-filter=AM` ne staged **A**dded ya **M**odified files dikhayin; `case` raaz jaise naam rokta hai siwaye `.env.example`.
- `git diff --cached -U0 | grep -iE …` aisi **juri** lines dhoondhta hai jo raaz jaise naam ko 8+ huroof ki quoted value dein. (`'"'"'` bas single-quoted Bash string ke andar single quote likhne ka tareeqa hai.)
- **Koshish 1:** code me likha `apiKey` roka gaya. **Koshish 2:** `process.env.PAYMENT_API_KEY` parhna qubool hua. **Koshish 3:** `prod.env` apne naam ki wajah se ruki. (`|| true` sirf misaal chalti rakhta hai.)

Hook `git commit --no-verify` se chhoota ja sakta hai, aur har developer ko khud lagana padta hai, isi liye teams CI aur server par **bhi** scan karti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Scan the whole history with gitleaks">

<Tr>
<En>

**gitleaks** is a free, open-source scanner with hundreds of rules for known secret formats (AWS, GitHub, Stripe, Slack, private keys…) plus generic high-entropy patterns. It can scan files on disk, staged changes, or **every commit in history**, finding secrets committed long ago and later "deleted". Run it once on the full history when you adopt it, then on every PR in CI and as a pre-commit hook. Exit code 1 means leaks were found, so CI fails automatically; `--redact` keeps the report from printing the secrets again. Alternatives: TruffleHog (also checks if keys are still live), detect-secrets.

</En>
<Ur>

**gitleaks** muft, open-source scanner hai jis ke paas maloom raaz formats (AWS, GitHub, Stripe, Slack, private keys…) ke saikron rules aur aam high-entropy patterns hain. Ye disk ki files, staged tabdeeliyan, ya **tareekh ka har commit** scan kar sakta hai, aur barson pehle commit hue phir "mitaye" gaye raaz dhoondhta hai. Apnate waqt ek dafa poori tareekh par chalayen, phir CI me har PR par aur pre-commit hook ke tor par. Exit code 1 ka matlab leaks mile, isliye CI khud fail hota hai; `--redact` report ko raaz dobara chhaapne se rokta hai. Mutabadil: TruffleHog (ye bhi check karta hai keys ab bhi zinda hain), detect-secrets.

</Ur>
</Tr>

```bash
git init -q scanme && cd scanme
echo 'PAYMENT_API_KEY="q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT"' > settings.py
git add . && git commit -qm "Add payment settings"
echo 'PAYMENT_API_KEY = os.environ["PAYMENT_API_KEY"]' > settings.py
git commit -qam "Read key from environment"
echo "--- files on disk now:"
gitleaks dir --no-banner --log-level error . ; echo "exit code: $?"
echo "--- full git history:"
gitleaks git --no-banner --redact --log-level error --report-format json --report-path ../leaks.json . ; echo "exit code: $?"
jq -r '.[] | "\(.RuleID) in \(.File) line \(.StartLine), commit \"\(.Message)\", secret: \(.Secret)"' ../leaks.json
```

```text output

exit code: 0
--- full git history:
exit code: 1
generic-api-key in settings.py line 1, commit "Add payment settings", secret: REDACTED
```

<Happened>

<En>`gitleaks dir` scanned only the current files: clean, exit 0. That's a false sense of safety. `gitleaks git` scanned **every commit**, found the key in the old one, and exited 1. `--redact` printed `REDACTED` instead of the secret, and `jq` pulled out the rule, file, line and commit message from the JSON report.</En>
<Ur>`gitleaks dir` ne sirf mojooda files scan kin: saaf, exit 0. <Step title="GitHub secret scanning and push protection">

<Tr>
<En>

GitHub scans repositories for secrets from 200+ providers. **Push protection** goes further: it **rejects a push** that contains a recognised secret before it reaches the repo, for everyone, even people who never installed a hook. For **public** repos it's free and GitHub also notifies the provider (AWS, Stripe…) so they can revoke leaked keys; for private repos it's part of GitHub Secret Protection. Turn it on under **Settings → Code security**. If a push is blocked, remove the secret from the commit (amend or interactive rebase), rotate it if it was real, and push again. Bypassing needs a stated reason and is logged.

<Step title="A secret leaked: what now?">

<Tr>
<En>

Attackers act within minutes, and cleaning Git history takes longer and **doesn't** remove copies others already made, so it can't be the first step. The order matters:

| Step | What to do | Example |
| --- | --- | --- |
| 1. **Revoke / rotate** | Disable the old secret and create a new one **immediately** | Delete the AWS access key, create a new one |
| 2. **Update** | Put the new secret where apps read it and redeploy | Vercel env var updated |
| 3. **Investigate** | Check the provider's logs for use of the old key since the leak | CloudTrail, Stripe logs, DB audit log |
| 4. **Inform** | Tell your team / security team; follow your incident process | Incident ticket |
| 5. **Clean history** (optional) | Rewrite history, force-push, ask GitHub support to purge cached views if needed | `git filter-repo` |
| 6. **Prevent** | Add the missing `.gitignore` rule, hook, CI scan and push protection | pre-commit + gitleaks in CI |

**Never** skip step 1 because "the repo is private" or "I deleted it after one minute".

</En>
<Ur>

Hamla awar minton me harkat karte hain, aur Git tareekh ki safai zyada waqt leti hai aur doosron ki banayi copies **nahi** hatati, isliye ye pehla qadam nahi ho sakta. Tarteeb ahem hai:

| Qadam | Kya karna hai | Misaal |
| --- | --- | --- |
| 1. **Revoke / rotate** | Purana raaz band karo aur **foran** naya banao | AWS access key mitao, nayi banao |
| 2. **Update** | Naya raaz wahan rakho jahan apps parhti hain aur redeploy | Vercel env var update |
| 3. **Tafteesh** | Leak ke baad purani key ka istemal provider ke logs me dekho | CloudTrail, Stripe logs, DB audit log |
| 4. **Ittila** | Team / security team ko batao; incident process follow karo | Incident ticket |
| 5. **Tareekh saaf** (ikhtiyari) | Tareekh dobara likho, force-push, zaroorat ho to GitHub support se cached views mitwao | `git filter-repo` |
| 6. **Bachao** | Ghayab `.gitignore` rule, hook, CI scan aur push protection lagao | pre-commit + CI me gitleaks |

"Repo private hai" ya "ek minute baad mita diya tha" keh kar qadam 1 **kabhi** na chhorein.

</Ur>
</Tr>

</Step>

<Step title="Remove a secret from history: git filter-repo">

<Tr>
<En>

`git filter-repo` rewrites **every commit**, for example replacing a secret string with `***REMOVED***` or deleting a file from all of history, so it no longer appears when browsing or cloning. Use it **after** rotating. It's the tool the Git project recommends (`pip install git-filter-repo`; older BFG, and avoid `git filter-branch`). It changes every commit hash after the first affected commit, so coordinate with the team, force-push every branch and tag, and have everyone re-clone. Forks, existing clones, CI caches and GitHub PR refs can still hold the old commits.

</En>
<Ur>

`git filter-repo` **har commit** dobara likhta hai, maslan raaz wali string ko `***REMOVED***` se badalna ya file ko poori tareekh se mitana, taa ke dekhne ya clone karne par wo nazar na aaye. Ise rotate karne ke **baad** istemal karein. Git project yahi tool tajweez karta hai (`pip install git-filter-repo`; purana BFG, aur `git filter-branch` se bachein). Ye pehle mutasir commit ke baad ka har hash badal deta hai, isliye team se tay karein, har branch aur tag force-push karein, aur sab dobara clone karen. Forks, maujood clones, CI caches aur GitHub PR refs me purane commits ab bhi ho sakte hain.

</Ur>
</Tr>

```bash
git init -q cleanup && cd cleanup
echo "app" > app.js && git add . && git commit -qm "Add app"
echo 'STRIPE_KEY=q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT' > keys.txt && git add . && git commit -qm "Add keys"
echo "more" >> app.js && git commit -qam "More app code"
echo "before: $(git log --all -p | grep -c 'q8Zt3Lm9')" occurrences in history
echo 'q8Zt3Lm9Vx2Rk7Wp4Ns6Hd1Fb5Jc0YgT==>***REMOVED***' > ../replacements.txt
git filter-repo --force --replace-text ../replacements.txt >/dev/null 2>&1
echo "after:  $(git log --all -p | grep -c 'q8Zt3Lm9')" occurrences in history
git show HEAD~1:keys.txt
git log --format=%s
```

```text output
before: 1 occurrences in history
after:  0 occurrences in history
STRIPE_KEY=***REMOVED***
More app code
Add keys
Add app
```

<Happened>
<Tr>
<En>

- `replacements.txt` holds one rule, `old text==>new text` (you can list many).
- `--replace-text` rewrote every commit; `--force` is needed because this isn't a fresh clone.
- The secret went from 1 occurrence to 0. The old commit now says `***REMOVED***`, and messages and structure stay the same.
- Every rewritten commit has a **new hash**, so next you'd `git push --force --all` and `--tags`, and teammates re-clone.

To delete a whole file from history instead: `git filter-repo --invert-paths --path keys.txt`.

</En>
<Ur>

- `replacements.txt` me ek rule hai, `old text==>new text` (kai likh sakte hain).
- `--replace-text` ne har commit dobara likha; `--force` is liye ke ye taaza clone nahi.
- Raaz 1 dafa se 0 par aa gaya. Purane commit me ab `***REMOVED***` hai, aur messages aur dhancha wahi hai.
- Har dobara likhe commit ka **naya hash** hai, isliye agla qadam `git push --force --all` aur `--tags`, aur saathi dobara clone karen.

Poori file tareekh se mitani ho to: `git filter-repo --invert-paths --path keys.txt`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Where secrets should live instead">

<Tr>
<En>

"Not in Git" isn't enough: secrets in a shared doc, chat or email are leaks waiting to happen. Use places that store secrets encrypted, control who can read them, and log access:

| Where the code runs | Store secrets in |
| --- | --- |
| Your laptop (development) | `.env` (ignored), or a password manager CLI (1Password, Bitwarden) |
| GitHub Actions | Repository / environment **secrets**; for clouds, **OIDC** with no stored keys |
| Vercel / Netlify / Render | Project environment variables in the dashboard |
| Docker | Pass at runtime (`-e`, `--env-file`, Compose secrets), **never** `ENV` or `COPY .env` in the Dockerfile |
| Kubernetes | Kubernetes Secrets (encrypted at rest), External Secrets Operator, Sealed Secrets |
| Cloud apps | AWS Secrets Manager / SSM, Azure Key Vault, Google Secret Manager, HashiCorp Vault |
| Team sharing | A password manager vault, **not** Slack, WhatsApp or email |

Best of all is **no long-lived secrets**: short-lived credentials issued on demand, such as GitHub Actions **OIDC** to AWS, Azure or GCP. If you **must** keep secrets in Git (common in GitOps), use tools built for it, **SOPS**, **Sealed Secrets** or **git-crypt**, so the repo only ever holds encrypted values.

</En>
<Ur>

"Git me nahi" kaafi nahi: saanjhe doc, chat ya email me raaz leak hone ka intezar hain. Aisi jagahen istemal karein jo raaz encrypt kar ke rakhen, parhne walon ko control karen, aur rasai record karen:

| Code kahan chalta hai | Raaz kahan rakhein |
| --- | --- |
| Aap ka laptop (development) | `.env` (ignored), ya password manager CLI (1Password, Bitwarden) |
| GitHub Actions | Repository / environment **secrets**; clouds ke liye **OIDC**, koi key save nahi |
| Vercel / Netlify / Render | Dashboard me project environment variables |
| Docker | Chalte waqt do (`-e`, `--env-file`, Compose secrets), Dockerfile me `ENV` ya `COPY .env` **kabhi nahi** |
| Kubernetes | Kubernetes Secrets (encrypted at rest), External Secrets Operator, Sealed Secrets |
| Cloud apps | AWS Secrets Manager / SSM, Azure Key Vault, Google Secret Manager, HashiCorp Vault |
| Team me share | Password manager vault, Slack, WhatsApp ya email **nahi** |

Sab se behtar **lambi umar ke raaz hi na hon**: zaroorat par milne wali chhoti umar ki credentials, jaise GitHub Actions se AWS, Azure ya GCP tak **OIDC**. Agar Git me raaz rakhna **lazmi** ho (GitOps me aam), to us ke liye bane tools, **SOPS**, **Sealed Secrets** ya **git-crypt**, istemal karein taa ke repo me sirf encrypted values hon.

</Ur>
</Tr>

</Step>

## Common mistakes

<Compare>
<Bad title="A hard-coded fallback secret">

```text
const jwtSecret = process.env.JWT_SECRET || "q8Zt3Lm9Vx2Rk7Wp";
// missing variable? the app quietly uses a value anyone can read on GitHub
```

</Bad>
<Good title="Fail fast, no secret in code">

```text
const jwtSecret = process.env.JWT_SECRET;
if (!jwtSecret) throw new Error("JWT_SECRET is not set (see .env.example)");
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **"I deleted it in the next commit, so it's fine."** It's still in history and every clone.
- **Adding `.env` to `.gitignore` after it's already tracked** and assuming that's enough. Use `git rm --cached`, and rotate.
- **Rewriting history but not rotating:** copies already exist elsewhere.
- **Secrets in Dockerfiles** (`ENV API_KEY=...`, `COPY .env .`): they end up in every image layer and registry.
- **Logging secrets:** `console.log(config)` or printing environment variables in CI logs.
- **Committing `.env.example` with real values** copied from `.env`.
- **Scanning only the current files**, not the full history.
- **Relying only on a local hook** that teammates never installed and anyone can skip with `--no-verify`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **"Agle commit me mita diya, to theek hai."** Ab bhi tareekh aur har clone me hai.
- **Track ho chuki `.env` ko `.gitignore` me daal kar** samajhna ke kaafi hai. `git rm --cached` karein, aur rotate.
- **Tareekh dobara likhna lekin rotate na karna:** copies pehle se kahin aur hain.
- **Dockerfiles me raaz** (`ENV API_KEY=...`, `COPY .env .`): har image layer aur registry me pahunch jate hain.
- **Raaz log karna:** `console.log(config)` ya CI logs me environment variables chhaapna.
- **`.env.example` me `.env` se copy ki asli values commit karna.**
- **Sirf mojooda files scan karna**, poori tareekh nahi.
- **Sirf local hook par bharosa** jo saathiyon ne lagaya hi nahi aur koi bhi `--no-verify` se chhor sakta hai.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- A secret is anything that grants access; never commit one.
- Git never forgets: deleting it later doesn't remove it from history.
- `.env` (ignored) for values, `.env.example` (committed) for names.

<DeepDive title="Real world: blocked once, burned once">

A developer at Alex's company builds a quick script to sync orders with a payment provider and, to test it, pastes the live API key straight into `sync.js`. He commits and pushes to a feature branch. Because the organisation turned on **push protection**, GitHub rejects the push and names the file and line. He moves the key into `.env`, reads it with `process.env.PAYMENT_API_KEY`, amends the commit and pushes again.

A month earlier, before push protection was enabled, the team wasn't so lucky: an intern committed an AWS access key to a **public** demo repo. Within minutes, automated bots found it and launched GPU servers for crypto-mining. AWS also detected the exposed key and alerted the account. The team **deactivated the key first**, terminated the unknown servers, checked CloudTrail for what else the key had touched, created a new key stored in AWS Secrets Manager, and only then rewrote the repository history. Afterwards they added gitleaks to CI for every repository and replaced stored cloud keys in GitHub Actions with OIDC.

</DeepDive>

<DeepDive title="Security lens">

Assume any secret that touched Git is compromised. Rotation is the fix; everything else is cleanup and prevention.

- **Defence in depth:** `.gitignore` → pre-commit hook → push protection → CI history scan → monitoring provider alerts. Each layer catches what the previous one missed.
- **Least privilege:** give each key only the permissions it needs (a read-only key for a reporting script, not an admin key).
- **Short-lived credentials beat stored secrets:** OIDC for CI, temporary cloud credentials, tokens that expire.
- **Mask secrets in CI logs.** GitHub Actions masks registered secrets, but values you derive or print in other forms (encoded, split) are not masked.
- **Watch for secret sprawl:** the same key copied into ten repos and five CI systems. Centralise secrets in one manager.
- **Leaks hide in unexpected places:** Docker images, mobile app bundles, front-end JavaScript (anything sent to the browser is public), notebook outputs and crash reports.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="You accidentally pushed an API key to GitHub. What do you do?">
First revoke or rotate the key immediately at the provider, because the commit may already have been copied or scanned by bots. Then deploy the new key from a proper secret store, check the provider's logs for misuse since the leak, and inform the team or follow the incident process. After that, optionally remove the key from history with git filter-repo and a coordinated force push, and add prevention such as .gitignore rules, a pre-commit secret scanner, CI scanning and push protection.
</QA>

<QA q="Why doesn't deleting the file in a new commit remove the secret?">
Git stores every commit as a snapshot, so the earlier commit that added the file still contains it. Anyone with access to the repository history, including clones, forks and caches, can retrieve it with commands such as git show or git log -p.
</QA>

<QA q="I added .env to .gitignore but Git still tracks it. Why?">
.gitignore only applies to untracked files. Once a file has been committed, Git keeps tracking it. Running git rm --cached .env stops tracking it while keeping the local file, and committing that change removes it from future commits, though it remains in earlier history.
</QA>

<QA q="How should applications receive secrets?">
Applications should read secrets at runtime from environment variables or a secret manager rather than having them in the code or repository. In development a git-ignored .env file can provide them, in CI the platform's secret store or short-lived OIDC credentials, and in production services such as AWS Secrets Manager, Azure Key Vault, Vault or Kubernetes Secrets, with least-privilege access and rotation.
</QA>

<QA q="What is the difference between a pre-commit secret scanner and GitHub push protection?">
A pre-commit scanner runs on the developer's machine before a commit is created, but each developer must install it and it can be skipped. Push protection runs on GitHub's servers and blocks pushes containing recognised secrets for everyone, with bypasses requiring a reason and being audited. Using both, plus history scanning in CI, gives defence in depth.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Secret">Value that grants access, such as a password, token or key.</Term>
  <Term name=".env file">Local file of environment variables, never committed.</Term>
  <Term name=".env.example">Committed template listing required variables without values.</Term>
  <Term name="git rm --cached">Stop tracking a file but keep it on disk.</Term>
  <Term name="Pre-commit hook">Script that runs before each commit and can block it.</Term>
  <Term name="gitleaks">Open-source scanner for secrets in files and Git history.</Term>
  <Term name="Push protection">GitHub server-side blocking of pushes containing secrets.</Term>
  <Term name="Rotation">Replacing a secret with a new one and disabling the old.</Term>
  <Term name="git filter-repo">Tool to rewrite history, e.g. to remove secrets.</Term>
  <Term name="Secret manager">Service that stores, controls and audits access to secrets.</Term>
  <Term name="OIDC">Short-lived credential exchange that avoids storing cloud keys in CI.</Term>
</Terms>

<DeepDive title="More practice">

1. Create a project with `.gitignore`, `.env` and `.env.example`, and prove with `git check-ignore -v` that `.env` is ignored.
2. Commit a fake secret, remove it in a new commit, and find it again with `git log -p -S`.
3. Install gitleaks and scan the full history of one of your own repositories.
4. Add gitleaks as a pre-commit hook and try to commit a fake key.
5. Enable push protection for your GitHub account (Settings → Code security).
6. Use `git filter-repo --replace-text` on a throwaway repo to remove a fake secret from all commits.
