<BigIdea>
<Tr>
<En>
Every working day follows the same loop: **`git pull`** (get the team's latest) → **`git switch -c feature/x`** (your own branch) → edit → **`git status`** / **`git diff`** (look at what changed) → **`git add`** → **`git commit`** (small, clear steps) → **`git push`** → open a **pull request** → review → merge → delete the branch → back to `main`. **`git stash`** parks unfinished work, and **`git restore`** throws away a bad edit. Learn this loop once and you can work in any team.
</En>
<Ur>
Har kaam ka din ek hi chakkar chalta hai: **`git pull`** (team ka taaza kaam lo) → **`git switch -c feature/x`** (apni branch) → badlo → **`git status`** / **`git diff`** (dekho kya badla) → **`git add`** → **`git commit`** (chhote, saaf qadam) → **`git push`** → **pull request** kholo → review → merge → branch mitao → wapas `main`. **`git stash`** adhoora kaam side par rakhta hai, aur **`git restore`** ghalat tabdeeli phenk deta hai. Ye chakkar ek dafa seekh lein to kisi bhi team me kaam kar sakte hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

A **workflow** is the agreed sequence of Git steps a team follows. The most common today is the **feature-branch workflow** (also called **GitHub Flow**): `main` is always working and deployable, and every change arrives through a short-lived branch and a pull request.

```text
 main:     ●───────●───────────────●  (always working, protected)
            \                     /
 feature:    ●──●──●  push → PR → review → merge
```

</En>
<Ur>

**Workflow** Git ke qadmon ka wo tay shuda silsila hai jo team follow karti hai. Aaj sab se aam **feature-branch workflow** hai (jise **GitHub Flow** bhi kehte hain): `main` hamesha chalti aur deploy ke qabil hoti hai, aur har tabdeeli ek chhoti umar wali branch aur pull request ke zariye aati hai.

```text
 main:     ●───────●───────────────●  (always working, protected)
            \                     /
 feature:    ●──●──●  push → PR → review → merge
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Picture five developers all committing straight to `main`. One pushes half-finished code at 5 pm; the next morning nobody's build works. Another overwrites a teammate's change without noticing. There's no review, so a hard-coded password goes live. The daily workflow exists to stop exactly these problems.

- **`main` stays working**: broken work stays on its branch.
- **Review catches bugs and security problems** before they ship.
- **Small commits** make it easy to find and undo a bad change.
- **Teamwork without overwriting** each other's work.

</En>
<Ur>

Socho paanch developers sab seedha `main` par commit kar rahe hain. Ek shaam 5 baje adhoora code push karta hai; agli subah kisi ka build nahi chalta. Doosra baghair dekhe saathi ki tabdeeli mita deta hai. Review nahi hai, isliye code me likha password live chala jata hai. Rozana workflow bilkul inhi masail ko rokne ke liye hai.

- **`main` chalti rehti hai**: toota kaam apni branch par rehta hai.
- **Review bugs aur security masail** ship hone se pehle pakarta hai.
- **Chhote commits** se ghalat tabdeeli dhoondhna aur wapas lena aasaan.
- **Ek doosre ka kaam mitaye baghair teamwork**.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Every working day, in every team, for code, infrastructure and documentation. You run these commands in a terminal, in VS Code's Source Control panel, or in a GUI app; the steps are the same everywhere.

</En>
<Ur>

Har kaam ke din, har team me, code, infrastructure aur documentation ke liye. Ye commands terminal me, VS Code ke Source Control panel me, ya kisi GUI app me chalti hain; qadam har jagah wahi hain.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
git switch main && git pull          # start from the latest
git switch -c feature/cart-total     # one task, one branch
git status / git diff                # look before you save
git add file && git commit -m "..."  # small, clear commits
git push -u origin feature/cart-total
# open a pull request on GitHub → review → merge
```

</En>
<Ur>

```text
git switch main && git pull          # taaze code se shuru
git switch -c feature/cart-total     # ek kaam, ek branch
git status / git diff                # save se pehle dekho
git add file && git commit -m "..."  # chhote, saaf commits
git push -u origin feature/cart-total
# GitHub par pull request kholo → review → merge
```

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

A **shared kitchen recipe book** (the GitHub repo). You never scribble directly in the master copy. Each morning you **copy the latest pages** (pull), take a **separate notebook** for your new dish (branch), and write and test your recipe there step by step (commits). Then you hand the notebook to the head chef for **review** (pull request). Only after approval are your pages added to the master book (merge).

</Ur>

## Learn it step by step

<Tr>
<En>
The examples use a local "server" repository instead of GitHub, so everything runs offline. The commands are identical with a real GitHub URL.
</En>
<Ur>
Misaalen GitHub ke bajaye ek local "server" repository istemal karti hain, taa ke sab kuch offline chale. Asli GitHub URL ke saath commands bilkul wahi hain.
</Ur>
</Tr>

<Walkthrough>

<Step title="Clone: get the project">

<Tr>
<En>

`git clone <url>` downloads the **whole repository and history** and creates a remote called `origin` pointing back to it. You do it once per project per computer. URLs look like `https://github.com/org/repo.git` (HTTPS) or `git@github.com:org/repo.git` (SSH).

</En>
<Ur>

`git clone <url>` **poori repository aur tareekh** download karta hai aur `origin` naam ka remote banata hai jo wapas us ki taraf ishara karta hai. Ye har project ke liye har computer par ek dafa hota hai. URLs aise hote hain: `https://github.com/org/repo.git` (HTTPS) ya `git@github.com:org/repo.git` (SSH).

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"
git config --global user.email "alex@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase false
# a pretend "GitHub" repo with one commit
git init -q --bare server.git
git clone -q server.git seed 2>/dev/null && cd seed
echo "# Shop" > README.md && git add . && git commit -qm "Initial commit" && git push -q origin main
cd .. && rm -rf seed
# the real start of your day: clone it
git clone -q server.git shop && cd shop
git remote -v | sed 's#/.*server.git#<url>/server.git#'
git log --oneline | cut -c9-
```

```text output
origin	<url>/server.git (fetch)
origin	<url>/server.git (push)
Initial commit
```

<Happened>
<Tr>
<En>

- The four `git config --global` lines are one-time setup per computer: name and email (stamped on every commit), `main` as the default branch, and `pull.rebase false` so `git pull` merges by default (rebase comes in a later lesson).
- `git init --bare server.git` makes a **bare** repository: history only, no working files. That's what a repo on GitHub's servers looks like, so we use it as a pretend GitHub.
- The `seed` lines just put a first commit on the "server", then delete the helper folder. On a real project that commit would already exist.
- `git clone -q server.git shop` is the real start: it downloads everything into a new folder `shop`. With GitHub you'd write `git clone https://github.com/company/shop.git`.
- `git remote -v` shows where `origin` points (`sed` only shortens the path). `cut -c9-` removes the hash so the output is the same on every computer.

After cloning you have **everything**: all files, all commits, all branches. You can work completely offline.

</En>
<Ur>

- Chaar `git config --global` lines har computer par ek dafa ki setup hain: naam aur email (har commit par lagte hain), `main` default branch, aur `pull.rebase false` taa ke `git pull` default me merge kare (rebase agle sabaq me).
- `git init --bare server.git` **bare** repository banata hai: sirf tareekh, koi working files nahi. GitHub ke servers par repo aisa hi hota hai, isliye hum ise nakli GitHub banate hain.
- `seed` wali lines sirf "server" par pehla commit daalti hain, phir madadgar folder mita deti hain. Asli project me ye commit pehle se hota.
- `git clone -q server.git shop` asli shuruaat hai: sab kuch naye folder `shop` me download karta hai. GitHub ke saath `git clone https://github.com/company/shop.git` likhte.
- `git remote -v` dikhata hai `origin` kahan hai (`sed` sirf path chhota karta hai). `cut -c9-` hash hata deta hai taa ke output har computer par ek jaisa ho.

Clone ke baad aap ke paas **sab kuch** hai: saari files, saare commits, saari branches. Aap poori tarah offline kaam kar sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Pull: start from the latest">

<Tr>
<En>

`git pull` = `git fetch` (download new commits) **+** merge them into your current branch. Starting from old code causes conflicts and duplicated work, so pull every morning and before creating a new branch. `git fetch` alone only downloads, which is handy when you want to **look before merging**.

</En>
<Ur>

`git pull` = `git fetch` (naye commits download) **+** unhe mojooda branch me merge. Purane code se shuru karna conflicts aur dohra kaam paida karta hai, isliye har subah aur nayi branch banane se pehle pull karein. Akela `git fetch` sirf download karta hai, jo tab kaam aata hai jab aap **merge se pehle dekhna** chahen.

</Ur>
</Tr>

```bash
# a teammate pushes something overnight
git clone -q server.git teammate && cd teammate
echo "MIT" > LICENSE && git add . && git commit -qm "Add license" && git push -q
cd ../shop
git fetch -q
echo "new on the server: $(git log --format=%s main..origin/main)"
git pull -q
git log --format=%s
```

```text output
new on the server: Add license
Add license
Initial commit
```

<Happened>
<Tr>
<En>

- The `teammate` lines simulate a colleague who clones, adds a `LICENSE` file and pushes it.
- In our `shop` folder, `git fetch` downloaded the new commit but did **not** touch our files or our `main`. It only updated `origin/main`, Git's record of what the server has.
- `main..origin/main` means "commits on `origin/main` that aren't on my `main`": the teammate's "Add license".
- `git pull` then brought it into our `main`, and `LICENSE` appeared in the folder.

</En>
<Ur>

- `teammate` wali lines ek saathi ki nakal hain jo clone kar ke `LICENSE` file jorta aur push karta hai.
- Hamare `shop` folder me `git fetch` ne naya commit download kiya lekin hamari files ya `main` ko **nahi** chhua. Us ne sirf `origin/main` update kiya, jo Git ka record hai ke server par kya hai.
- `main..origin/main` ka matlab "`origin/main` ke wo commits jo mere `main` par nahi": saathi ka "Add license".
- Phir `git pull` ne use hamare `main` me laya, aur folder me `LICENSE` aa gayi.

</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>**Habit:** the first command of your day is `git switch main && git pull`.</En>
<Ur>**Aadat:** din ki pehli command `git switch main && git pull` ho.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Branch: one task, one branch">

<Tr>
<En>

Before you edit anything, create a short-lived branch for that one feature or fix. It keeps `main` clean, lets you work on several things, and keeps the PR focused. Common names: `feature/cart-total`, `fix/login-redirect`, `docs/readme-setup`, often with a ticket number. `git switch -c name` creates it and moves you there (`git checkout -b name` is the older way).

</En>
<Ur>

Kuch bhi badalne se pehle us ek feature ya fix ke liye chhoti branch banayen. Is se `main` saaf rehti hai, aap kai kaam saath kar sakte hain, aur PR ek maqsad par rehta hai. Aam naam: `feature/cart-total`, `fix/login-redirect`, `docs/readme-setup`, aksar ticket number ke saath. `git switch -c name` ise bana kar wahan le jata hai (`git checkout -b name` purana tareeqa hai).

</Ur>
</Tr>

```bash
cd shop
git switch -c feature/cart-total
git branch
```

```text output
Switched to a new branch 'feature/cart-total'
* feature/cart-total
  main
```

<Happened>
<Tr>
<En>The new branch started from the latest `main`. `git branch` lists local branches, and `*` marks the current one. From now on every commit goes to `feature/cart-total`; `main` stays exactly as it was until the work is reviewed and merged.</En>
<Ur>Nayi branch taaza `main` se shuru hui. `git branch` local branches dikhata hai, aur `*` mojooda wali ko. Ab se har commit `feature/cart-total` par jayega; `main` bilkul waisi rahegi jab tak kaam review ho kar merge na ho.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Status and diff: what did I change?">

<Tr>
<En>

`git status` lists changed files. `git diff` shows the exact lines changed but **not yet staged**; `git diff --staged` shows what **will** be committed. Always look before you commit: it catches debug prints, accidental edits and secrets. In a diff, `+` lines were added, `-` lines removed, and `@@ -1 +1,2 @@` says which lines of the old and new file this piece (a **hunk**) covers.

</En>
<Ur>

`git status` badli files dikhata hai. `git diff` bilkul wo lines dikhata hai jo badli lekin **abhi stage nahi** hui; `git diff --staged` dikhata hai jo commit **hoga**. Commit se pehle hamesha dekhein: is se debug prints, ghalti ki tabdeeliyan aur raaz pakre jate hain. Diff me `+` lines juri, `-` lines hatin, aur `@@ -1 +1,2 @@` batata hai ye tukra (**hunk**) purani aur nayi file ki kaunsi lines ka hai.

</Ur>
</Tr>

```bash
cd shop
printf 'function total(items) {\n  return items.reduce((s, i) => s + i.price, 0);\n}\n' > cart.js
echo "Run: node cart.js" >> README.md
git status -s
git diff README.md | tail -3
```

```text output
 M README.md
?? cart.js
@@ -1 +1,2 @@
 # Shop
+Run: node cart.js
```

<Happened>
<Tr>
<En>

- `printf … > cart.js` created a new file; `echo … >> README.md` **appended** a line to a tracked file (`>>` adds to the end, `>` would overwrite).
- ` M` = modified but not staged; `??` = new, untracked file.
- In the diff, ` # Shop` (starting with a space) is unchanged context and `+Run: node cart.js` is the new line.
- A full diff also starts with headers like `diff --git a/README.md b/README.md`; `tail -3` cut them off to keep it short.

</En>
<Ur>

- `printf … > cart.js` ne nayi file banayi; `echo … >> README.md` ne track ki file me line **aakhir me jori** (`>>` aakhir me jorta, `>` mita kar likhta).
- ` M` = badli lekin stage nahi; `??` = nayi, untracked file.
- Diff me ` # Shop` (space se shuru) na badla hua sayaq hai aur `+Run: node cart.js` nayi line.
- Poora diff `diff --git a/README.md b/README.md` jaise headers se shuru hota hai; `tail -3` ne unhe kaat kar chhota kiya.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Stage and commit in small steps">

<Tr>
<En>

Stage related changes together, commit them with a clear message, then repeat for the next logical change. **One commit = one idea**: reviewers understand it, and `git revert` can undo it cleanly. Message style: a short imperative summary under about 50 characters ("Add cart total function"), and optionally a blank line plus a body explaining **why**.

</En>
<Ur>

Mutaliq tabdeeliyan ikatthi stage karein, saaf message se commit karein, phir agli mantiqi tabdeeli ke liye dohrayen. **Ek commit = ek khayal**: reviewer samajh jata hai, aur `git revert` use saaf wapas le sakta hai. Message ka andaaz: takreeban 50 huroof se kam hukmiya khulasa ("Add cart total function"), aur chahen to khaali line ke baad **kyun** samjhane wali tafseel.

</Ur>
</Tr>

```bash
cd shop
git add cart.js
git commit -q -m "Add cart total function"
git add README.md
git commit -q -m "Document how to run the cart"
git status -s | wc -l | sed 's/$/ files left uncommitted/'
git log --oneline main..HEAD | cut -c9-
```

```text output
0 files left uncommitted
Document how to run the cart
Add cart total function
```

<Happened>
<Tr>
<En>

- `cart.js` and `README.md` were committed **separately**, each with its own message: two small commits instead of one "update files" commit.
- `git status -s | wc -l` counted remaining changes: 0.
- `main..HEAD` means "commits on my branch that aren't on main", exactly what your PR will contain.

</En>
<Ur>

- `cart.js` aur `README.md` **alag alag** commit hue, har ek ka apna message: ek "update files" commit ke bajaye do chhote commits.
- `git status -s | wc -l` ne baqi tabdeeliyan ginin: 0.
- `main..HEAD` ka matlab "meri branch ke wo commits jo main par nahi", bilkul wahi jo aap ke PR me hoga.

</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>Before each commit, run `git diff --staged`. It shows exactly what's about to be saved, so you spot leftover `console.log` lines or secrets in time.</En>
<Ur>Har commit se pehle `git diff --staged` chalayen. Ye bilkul dikhata hai kya save hone wala hai, taa ke bache hue `console.log` ya raaz waqt par nazar aa jayen.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Push your branch">

<Tr>
<En>

`git push` uploads your commits to the remote: a backup, a way to share, and required for a pull request. Push after a few commits, and at least at the end of each day. The first push of a new branch needs `-u origin branchname`; it sets the **upstream**, so later a plain `git push` is enough.

</En>
<Ur>

`git push` aap ke commits remote par upload karta hai: backup bhi, share karne ka zariya bhi, aur pull request ke liye zaroori. Kuch commits ke baad push karein, aur kam az kam har din ke aakhir me. Nayi branch ki pehli push ko `-u origin branchname` chahiye; ye **upstream** set karta hai, taa ke baad me sirf `git push` kaafi ho.

</Ur>
</Tr>

```bash
cd shop
git push -q -u origin feature/cart-total
git status -sb | head -1
git ls-remote --heads origin | awk '{sub("refs/heads/","",$2); print "on server:", $2}'
```

```text output
## feature/cart-total...origin/feature/cart-total
on server: feature/cart-total
on server: main
```

<Happened>
<Tr>
<En>`git status -sb` shows our branch is linked to its server copy, with nothing ahead or behind. `git ls-remote --heads origin` asks the server which branches it has: ours is there now, so teammates and CI can see it, and on GitHub you can open a pull request from it.</En>
<Ur>`git status -sb` dikhata hai hamari branch server copy se juri hai, na aage na peeche. `git ls-remote --heads origin` server se poochta hai us ke paas kaunsi branches hain: hamari ab wahan hai, isliye saathi aur CI use dekh sakte hain, aur GitHub par is se pull request khol sakte hain.</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>Never `git push --force` to a shared branch. If you must after a rebase, use `--force-with-lease`, and only on **your own** branch.</En>
<Ur>Saanjhi branch par kabhi `git push --force` na karein. Rebase ke baad zaroori ho to `--force-with-lease` istemal karein, aur sirf **apni** branch par.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Pull request, review, merge">

<Tr>
<En>

On GitHub you open a PR from `feature/cart-total` into `main` (the "Compare & pull request" button, or `gh pr create`). Teammates review it, automated checks (tests, lint, security scans) run, and then it's merged. A good PR has a clear title, says what changed and why, explains how to test it, includes screenshots for UI, and stays small (under about 400 changed lines). Open it as a **draft PR** if you want early feedback.

</En>
<Ur>

GitHub par aap `feature/cart-total` se `main` me PR kholte hain ("Compare & pull request" button, ya `gh pr create`). Saathi review karte hain, automated checks (tests, lint, security scans) chalte hain, phir merge hota hai. Achhe PR ka saaf unwaan hota hai, batata hai kya aur kyun badla, test karne ka tareeqa samjhata hai, UI ke liye screenshots rakhta hai, aur chhota rehta hai (takreeban 400 badli lines se kam). Jaldi raaye chahiye to **draft PR** kholein.

</Ur>
</Tr>

```bash
# what clicking "Merge pull request" does on the server, simulated locally
cd shop
git switch -q main
git merge -q --no-ff -m "Merge pull request #12 from feature/cart-total" feature/cart-total
git push -q origin main
git branch -q -d feature/cart-total && echo "Deleted local branch feature/cart-total"
git push -q origin --delete feature/cart-total
git log --graph --format=%s | head -4
```

```text output
Deleted local branch feature/cart-total
*   Merge pull request #12 from feature/cart-total
|\  
| * Document how to run the cart
| * Add cart total function
```

<Happened>
<Tr>
<En>

- `git merge --no-ff` made a merge commit, which is what GitHub's green **Merge pull request** button does on the server.
- `git branch -d` deleted the local branch. `-d` only works if the branch is fully merged, so nothing can be lost.
- `git push origin --delete` removed the branch from the server too (GitHub can do this automatically after merging).
- The graph shows our two commits joined into `main`.

On a real team you **don't** merge locally like this: you click merge on GitHub after review and checks pass, then run `git switch main && git pull`.

</En>
<Ur>

- `git merge --no-ff` ne merge commit banaya, jo GitHub ka hara **Merge pull request** button server par karta hai.
- `git branch -d` ne local branch mitayi. `-d` sirf tab chalta hai jab branch poori merge ho chuki ho, isliye kuch kho nahi sakta.
- `git push origin --delete` ne branch server se bhi hata di (GitHub merge ke baad ye khud bhi kar sakta hai).
- Graph dikhata hai hamare do commits `main` me jur gaye.

Asli team me aap is tarah local merge **nahi** karte: review aur checks ke baad GitHub par merge dabate hain, phir `git switch main && git pull` chalate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Stash: park unfinished work">

<Tr>
<En>

An urgent bug arrives while you're halfway through something, and you need a clean folder to switch branches. `git stash` puts your uncommitted changes on a shelf and cleans the working directory; `git stash pop` brings them back. Useful variations: `git stash list`, `git stash push -m "message"`, and `git stash -u` (include untracked files).

</En>
<Ur>

Aap aadhe kaam me hain aur ek urgent bug aa jata hai, aur branch badalne ke liye saaf folder chahiye. `git stash` aap ki uncommitted tabdeeliyan shelf par rakh kar working directory saaf kar deta hai; `git stash pop` unhe wapas lata hai. Kaam ki shaklen: `git stash list`, `git stash push -m "message"`, aur `git stash -u` (untracked files samet).

</Ur>
</Tr>

```bash
cd shop
echo "half-finished discount code" >> cart.js
git stash push -q -m "discount WIP"
git status -s | wc -l | sed 's/$/ changes in working dir after stash/'
git stash list | sed 's/On main: //'
git stash pop -q
git status -s
```

```text output
0 changes in working dir after stash
stash@{0}: discount WIP
 M cart.js
```

<Happened>
<Tr>
<En>

- The stash saved the unfinished line and put `cart.js` back to its last committed state: 0 changes, so it's safe to switch branches or pull.
- `stash@{0}` is the newest entry.
- `git stash pop` re-applied it **and** removed it from the list, so `cart.js` shows as modified again. (`git stash apply` re-applies but keeps the entry, handy for applying the same change to two branches.)

</En>
<Ur>

- Stash ne adhoori line save ki aur `cart.js` ko aakhri commit wali haalat par wapas kar diya: 0 tabdeeliyan, ab branch badalna ya pull karna mehfooz hai.
- `stash@{0}` sab se naya entry hai.
- `git stash pop` ne use dobara lagaya **aur** list se hata diya, isliye `cart.js` phir badli dikhti hai. (`git stash apply` lagata hai lekin entry rakhta hai, ek hi tabdeeli do branches par lagane ke liye kaam ka.)

</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>Don't leave things in the stash for weeks; it's easy to forget them. For longer breaks, a WIP commit on your own branch is safer.</En>
<Ur>Cheezen hafton stash me na chhorein; bhool jana aasaan hai. Lambe waqfe ke liye apni branch par WIP commit zyada mehfooz hai.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Undo simple mistakes">

<Tr>
<En>

Everyone makes small mistakes many times a day. Before pushing, three commands fix most of them: `git restore file` throws away unstaged edits, `git restore --staged file` unstages a file (keeping the edits), and `git commit --amend` replaces the last commit. `git status` even prints these hints for you.

</En>
<Ur>

Har koi din me kai dafa chhoti ghaltiyan karta hai. Push se pehle teen commands zyada tar theek kar deti hain: `git restore file` unstaged tabdeeliyan phenk deta hai, `git restore --staged file` file ko unstage karta hai (tabdeeliyan rakh kar), aur `git commit --amend` aakhri commit ko badal deta hai. `git status` khud ye ishare chhaapta hai.

</Ur>
</Tr>

```bash
cd shop
git restore cart.js                      # discard the WIP edit
echo "DEBUG=true" > debug.env
git add debug.env
git restore --staged debug.env           # oops, unstage it
git status -s
rm debug.env
echo "Run tests: npm test" >> README.md
git commit -qam "Add tset instructions"
git commit -q --amend -m "Add test instructions"   # fix typo in last message
git log -1 --format=%s
```

```text output
?? debug.env
Add test instructions
```

<Happened>
<Tr>
<En>

- `git restore cart.js` brought back the last committed version. It **can't be undone**, so be sure first.
- `debug.env` was staged by mistake; `git restore --staged` unstaged it. It stayed in the folder as `??` but won't be committed. Then `rm` deleted it.
- The commit message had a typo ("tset"); `--amend` replaced that commit with a corrected one.

</En>
<Ur>

- `git restore cart.js` ne aakhri commit wala version wapas laya. Ise **wapas nahi liya ja sakta**, isliye pehle yaqeen kar lein.
- `debug.env` ghalti se stage hui; `git restore --staged` ne use unstage kiya. Wo folder me `??` ban kar rahi lekin commit nahi hogi. Phir `rm` ne use mita diya.
- Commit message me typo tha ("tset"); `--amend` ne us commit ko durust wale se badal diya.

</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>Only amend commits you haven't pushed yet. Amending creates a **new** commit with a new hash, which rewrites history others may already have.</En>
<Ur>Sirf wo commits amend karein jo abhi push nahi hue. Amend **naya** commit naye hash ke saath banata hai, jo wo tareekh badal deta hai jo doosron ke paas ho sakti hai.</Ur>
</Tr>
</Callout>

<Tr>
<En>

| Situation | Command |
| --- | --- |
| Discard edits in a file | `git restore file` |
| Unstage a file (keep the edits) | `git restore --staged file` |
| Fix the last commit's message, or add a forgotten file | `git add file && git commit --amend` |
| Undo a commit that's already pushed | `git revert <hash>` (see **Undoing Things**) |

</En>
<Ur>

| Soorat-e-haal | Command |
| --- | --- |
| File ki tabdeeliyan phenkna | `git restore file` |
| File unstage karna (tabdeeliyan rakh kar) | `git restore --staged file` |
| Aakhri commit ka message theek, ya bhooli file jorna | `git add file && git commit --amend` |
| Push ho chuka commit wapas lena | `git revert <hash>` (dekhein **Undoing Things**) |

</Ur>
</Tr>

</Step>

<Step title="Keep your branch up to date">

<Tr>
<En>

While you work, `main` moves on. Bring those changes into your branch regularly: daily for long-lived branches, and before opening or merging a PR. Small, early conflicts are far easier than one big conflict at the end. Fetch, then merge (or rebase) `origin/main` into your branch, run the tests, and push.

</En>
<Ur>

Jab aap kaam kar rahe hote hain, `main` aage barhti rehti hai. Woh tabdeeliyan baqaidagi se apni branch me laayen: lambi branches ke liye rozana, aur PR kholne ya merge se pehle. Chhote, jaldi ke conflicts aakhir ke ek bare conflict se kahin aasaan hain. Fetch karein, phir `origin/main` ko apni branch me merge (ya rebase) karein, tests chalayen, aur push karein.

</Ur>
</Tr>

```bash
cd shop && git push -q
git switch -q -c feature/coupons
echo "coupons" > coupons.js && git add . && git commit -qm "Add coupons"
# meanwhile a teammate merges into main
cd ../teammate && git pull -q && echo "v1" > VERSION && git add . && git commit -qm "Add version file" && git push -q
cd ../shop
git fetch -q
echo "main is ahead of my branch by $(git rev-list --count HEAD..origin/main) commit(s)"
git merge -q --no-edit origin/main
echo "after update: $(git rev-list --count HEAD..origin/main) behind; files: $(ls | tr '\n' ' ')"
```

```text output
main is ahead of my branch by 1 commit(s)
after update: 0 behind; files: LICENSE README.md VERSION cart.js coupons.js 
```

<Happened>
<Tr>
<En>

- We pushed the updated `main`, started `feature/coupons`, and committed `coupons.js`.
- Meanwhile the teammate added `VERSION` to `main`.
- `git rev-list --count HEAD..origin/main` counted commits on `origin/main` that our branch lacks: 1.
- After `git merge origin/main` we're 0 behind, and `VERSION` sits next to our `coupons.js`.

Do this often and every conflict stays small. Wait two weeks and you may face twenty conflicts at once.

</En>
<Ur>

- Hum ne updated `main` push ki, `feature/coupons` shuru ki, aur `coupons.js` commit ki.
- Isi doran saathi ne `main` me `VERSION` jori.
- `git rev-list --count HEAD..origin/main` ne `origin/main` ke wo commits gine jo hamari branch me nahi: 1.
- `git merge origin/main` ke baad hum 0 peeche hain, aur `VERSION` hamari `coupons.js` ke saath maujood hai.

Ye aksar karein to har conflict chhota rehta hai. Do hafte intezar karein to ek saath bees conflicts aa sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Working straight on main, then one blind commit">

```text
git add .
git commit -m "update"
git push            # pushed to main: no branch, no review, maybe a .env inside
```

</Bad>
<Good title="Branch, look, small commits, pull request">

```text
git switch main && git pull
git switch -c fix/cart-rounding
git status && git diff
git add src/cart.js && git commit -m "Fix rounding in cart total"
git push -u origin fix/cart-rounding     # then open a PR
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting `git pull`** before starting, and building on old code.
- **`git add .` without looking**: commits `.env`, logs or debug files.
- **Giant PRs** nobody can review properly.
- **Messages like "update" or "fix stuff".**
- **Force-pushing a shared branch** and destroying teammates' commits.
- **Long-lived branches** that drift for weeks and end in painful conflicts.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Shuru se pehle `git pull` bhoolna**, aur purane code par banana.
- **Baghair dekhe `git add .`**: `.env`, logs ya debug files commit.
- **Bohot bare PRs** jinhe koi theek se review na kar sake.
- **"update" ya "fix stuff" jaise messages.**
- **Saanjhi branch par force-push** kar ke saathiyon ke commits mitana.
- **Lambi branches** jo hafton door hoti jayen aur dardnaak conflicts par khatam hon.

</Ur>
</Tr>

## Try it yourself

<Challenge title="The whole day in one script">

<Tr>
<En>
Run two full daily cycles (header, then footer): pull, branch, commit, push, merge, delete. The final graph should show each feature as its own small loop joined back into `main`.
</En>
<Ur>
Do poore rozana chakkar chalayen (pehle header, phir footer): pull, branch, commit, push, merge, delete. Aakhri graph me har feature apna chhota loop ban kar `main` me wapas jurta dikhna chahiye.
</Ur>
</Tr>

```bash
git init -q --bare remote.git && git clone -q remote.git app 2>/dev/null && cd app
git commit -q --allow-empty -m "Start" && git push -q -u origin main
for task in header footer; do
  git switch -q main && git pull -q
  git switch -q -c "feature/$task"
  echo "<$task/>" > "$task.html"
  git add . && git commit -qm "Add $task"
  git push -q -u origin "feature/$task"
  git switch -q main && git merge -q --no-ff -m "Merge feature/$task" "feature/$task" && git push -q
  git branch -q -d "feature/$task"
done
git log --graph --format=%s
```

```text output
*   Merge feature/footer
|\  
| * Add footer
|/  
*   Merge feature/header
|\  
| * Add header
|/  
* Start
```

<DeepDive title="Real world: a junior developer's day">

At 9:00 Sam runs `git switch main && git pull`, picks ticket SHOP-142 and runs `git switch -c fix/SHOP-142-cart-rounding`. Over the morning she makes three small commits, pushes, and opens a draft PR at lunch so CI runs. A reviewer asks for a test; she adds a fourth commit and pushes, and the PR updates automatically. At 15:00 an urgent production bug arrives: she stashes a half-done change, switches to a new `hotfix/` branch from `main`, fixes and ships it, then comes back and runs `git stash pop`. By evening her PR is approved, merged with "Squash and merge", and the branch is deleted.

</DeepDive>

<DeepDive title="Security lens">

`git diff --staged` before every commit is your last line of defence against committing a secret.

- **Protected `main`:** require PRs, reviews and passing checks, so nobody (including admins) pushes directly.
- **CI security checks on every PR:** secret scanning, dependency scanning (SCA) and SAST.
- **Review the diff, not just the description:** careless or malicious changes hide in large PRs.
- **Use SSH keys or tokens, never passwords,** for pushing; keep tokens short-lived and narrowly scoped.
- **Don't push to the wrong remote:** check `git remote -v` in forks and mirrors.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Describe your daily Git workflow.">
I update main with git pull, create a short-lived feature branch, make small focused commits after checking git status and git diff, push the branch with -u and open a pull request. CI runs tests and security checks, teammates review, and after approval the branch is merged into main and deleted. For long-running work I regularly bring in changes from main.
</QA>

<QA q="What is the difference between git fetch and git pull?">
git fetch downloads new commits and updates remote-tracking branches such as origin/main without changing your local branches or files. git pull runs a fetch and then integrates the changes into the current branch, by merge or by rebase depending on configuration.
</QA>

<QA q="When would you use git stash?">
When I have uncommitted changes but need a clean working directory, for example to switch branches for an urgent fix or to pull. git stash saves the changes and git stash pop restores them. For longer interruptions a work-in-progress commit on the feature branch is safer.
</QA>

<QA q="What makes a good commit and a good pull request?">
A good commit contains one logical change and has a short imperative summary, with an explanation of why if needed. A good pull request is small and focused, has a clear title and a description of what changed, why and how to test it, passes automated checks, and is easy to review.
</QA>

</DeepDive>
