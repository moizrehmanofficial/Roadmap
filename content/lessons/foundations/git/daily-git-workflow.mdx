<Callout type="tip" title="In one minute">
The daily loop: **`git pull`** (get the team's latest) → **`git switch -c feature/x`** (your own branch) → edit → **`git status`** / **`git diff`** (see what changed) → **`git add`** → **`git commit -m "..."`** (small, clear steps) → **`git push -u origin feature/x`** → open a **pull request** → review → merge → delete the branch → back to `main` and `git pull`. Use **`git stash`** to park unfinished work and **`git restore`** to throw away a bad edit.
</Callout>

## Start from zero

<Callout type="analogy">
Think of a **shared kitchen recipe book** (the GitHub repo). You never scribble directly in the master copy. Each morning you **copy the latest pages** (pull), take a **separate notebook** for your new dish (branch), write and test your recipe there step by step (commits), then hand the notebook to the head chef for **review** (pull request). Only after approval are your pages added to the master book (merge).
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Clone** | Download a full copy of a repo with its history | `git clone URL` |
| **Remote / origin** | The shared copy (usually GitHub); `origin` is its default name | |
| **Pull** | Download new commits and merge them into your branch | `git pull` |
| **Push** | Upload your commits to the remote | `git push` |
| **Feature branch** | A short-lived branch for one task | `feature/cart-total` |
| **Diff** | The exact lines added and removed | `git diff` |
| **Pull request (PR)** | A request to merge your branch, with review and checks | on GitHub |
| **Stash** | A temporary shelf for unfinished changes | `git stash` |

## What is it?

A **workflow** is the agreed sequence of Git steps a team follows. The most common today is the **feature-branch (GitHub Flow)** workflow: `main` is always deployable, and every change arrives through a short-lived branch and a pull request.

```text
 main:     ●───────●───────────────●  (always working, protected)
            \                     /
 feature:    ●──●──●  push → PR → review → merge
```

## Why does it matter?

Picture five developers all committing straight to `main`. One pushes half-finished code at 5 pm; the next morning nobody's build works. Another overwrites a teammate's change without noticing. There is no review, so a hard-coded password goes live. The daily workflow exists to prevent exactly these problems.

- **`main` stays working** — broken work stays on its branch.
- **Review catches bugs and security problems** before they ship.
- **Small commits** make it easy to find and undo a bad change.
- **Teamwork without overwriting** each other's work.

## When and where do you use it?

Every working day, in every team, for code, infrastructure and documentation. You run these commands in a terminal, VS Code's Source Control panel, or a GUI — the steps are the same.

## Concepts one by one

The examples below use a local "server" repository instead of GitHub, so everything runs offline — the commands are identical with a GitHub URL.

### 1. Clone: get the project

<Explain>
<What>
`git clone <url>` downloads the full repository and history and sets up `origin` pointing to it.
</What>
<Why>
You need your own local copy to work on.
</Why>
<When>
Once per project per computer.
</When>
<Where>
URLs like `https://github.com/org/repo.git` or `git@github.com:org/repo.git` (SSH).
</Where>
<How>
`git clone URL [folder]`, then `cd` into it.
</How>
</Explain>

```bash
git config --global user.name "Moiz Rehman"
git config --global user.email "moiz@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase false
# a pretend "GitHub" repo with one commit
git init -q --bare server.git
git clone -q server.git seed 2>/dev/null && cd seed
echo "# Shop" > README.md && git add . && git commit -qm "Initial commit" && git push -q origin main
cd .. && rm -rf seed
# the real start of your day: clone it
git clone -q server.git shop && cd shop
git remote -v | sed 's#/.*server.git#<url>/server.git#'
git log --oneline | cut -c9-
```

```text output
origin	<url>/server.git (fetch)
origin	<url>/server.git (push)
Initial commit
```

Line by line:

- The four `git config --global` lines are one-time setup per computer: your name and email (stamped on every commit), `main` as the default branch name, and `pull.rebase false` so `git pull` merges by default (we'll discuss the rebase option later).
- `git init -q --bare server.git` creates a **bare** repository: history only, no working files. This is what a repository on GitHub's servers looks like. We use it as a pretend GitHub.
- The `seed` lines just put a first commit on the "server" and then delete the helper folder. On a real project that commit would already exist.
- `git clone -q server.git shop` is the real start: it downloads the whole repository into a new folder `shop` and creates a remote called `origin`. With GitHub you would write `git clone https://github.com/company/shop.git`.
- `git remote -v` shows where `origin` points (the `sed` only shortens the path).
- `git log --oneline | cut -c9-` lists the commits we received; `cut` removes the hash so the output is the same on every computer.

After cloning you have **everything**: all files, all commits, all branches. You can work completely offline.

### 2. Pull: start from the latest

<Explain>
<What>
`git pull` = `git fetch` (download new commits) + merge them into your current branch.
</What>
<Why>
Starting from old code causes conflicts and duplicated work.
</Why>
<When>
Every morning, and before creating a new branch.
</When>
<Where>
On `main`: `git switch main && git pull`.
</Where>
<How>
`git fetch` alone only downloads — useful to look before merging (`git log main..origin/main`).
</How>
</Explain>

```bash
# a teammate pushes something overnight
git clone -q server.git teammate && cd teammate
echo "MIT" > LICENSE && git add . && git commit -qm "Add license" && git push -q
cd ../shop
git fetch -q
echo "new on the server: $(git log --format=%s main..origin/main)"
git pull -q
git log --format=%s
```

```text output
new on the server: Add license
Add license
Initial commit
```

Line by line:

- The `teammate` lines simulate a colleague: they clone, add a `LICENSE` file, commit and push it to the server.
- Back in our `shop` folder, `git fetch -q` downloads the new commit but does **not** touch our files or our `main` branch. It only updates `origin/main`, Git's record of what the server has.
- `git log main..origin/main` means "commits on `origin/main` that are not on my `main`": the teammate's "Add license".
- `git pull -q` now brings that commit into our `main` (and `LICENSE` appears in our folder).
- `git log --format=%s` confirms our history now has both commits.

**Habit:** the first command of your day is `git switch main && git pull`.

### 3. Branch: one task, one branch

<Explain>
<What>
A short-lived branch for one feature or fix.
</What>
<Why>
Keeps `main` clean, lets you work on several things, and makes the PR focused.
</Why>
<When>
Before you start editing — every time.
</When>
<Where>
Common names: `feature/cart-total`, `fix/login-redirect`, `docs/readme-setup`, often with a ticket number.
</Where>
<How>
`git switch -c name` creates and moves to it. (`git checkout -b name` is the older equivalent.)
</How>
</Explain>

```bash
cd shop
git switch -c feature/cart-total
git branch
```

```text output
Switched to a new branch 'feature/cart-total'
* feature/cart-total
  main
```

Line by line:

- `git switch -c feature/cart-total` creates a new branch from where we are (the latest `main`) and moves onto it. Git prints "Switched to a new branch".
- `git branch` lists local branches. The `*` marks the current one.

From now on every commit goes to `feature/cart-total`. `main` stays exactly as it was until the work is reviewed and merged.

### 4. Status and diff: what did I change?

<Explain>
<What>
`git status` lists changed files; `git diff` shows the exact lines changed but **not yet staged**; `git diff --staged` shows what **will** be committed.
</What>
<Why>
Always look before you commit — it catches debug prints, accidental edits and secrets.
</Why>
<When>
Before every `git add` and `git commit`.
</When>
<Where>
Lines starting `+` were added, `-` removed; `@@ -1 +1,2 @@` says which lines of the old and new file this piece (a **hunk**) covers.
</Where>
<How>
`git status -s` is the short version.
</How>
</Explain>

```bash
cd shop
printf 'function total(items) {\n  return items.reduce((s, i) => s + i.price, 0);\n}\n' > cart.js
echo "Run: node cart.js" >> README.md
git status -s
git diff README.md | tail -3
```

```text output
 M README.md
?? cart.js
@@ -1 +1,2 @@
 # Shop
+Run: node cart.js
```

` M` = modified but not staged; `??` = new, untracked file.` M` = modified but not staged; `??` = new, untracked file.

Line by line:

- `printf '...' > cart.js` creates a new file with a small `total` function.
- `echo "Run: node cart.js" >> README.md` appends a line to an existing, tracked file (`>>` adds to the end; `>` would overwrite).
- `git status -s` shows the short status: `README.md` modified, `cart.js` untracked.
- `git diff README.md | tail -3` shows the end of the diff for `README.md`. The line ` # Shop` (starting with a space) is unchanged context; `+Run: node cart.js` is the new line.

A full `git diff` also starts with header lines like `diff --git a/README.md b/README.md` and `--- a/README.md` / `+++ b/README.md` (old and new version). We cut them off here with `tail` to keep the output short.

### 5. Stage and commit in small steps

<Explain>
<What>
Stage related changes together, commit them with a clear message, then repeat for the next logical change.
</What>
<Why>
One commit = one idea. Reviewers understand it; `git revert` can undo it cleanly.
</Why>
<When>
Whenever a small piece works — many times a day.
</When>
<Where>
`git add file`, `git add -p` (choose hunks interactively), `git add .` (everything — check status first!).
</Where>
<How>
Message style: short imperative summary under ~50 characters ("Add cart total function"), optional blank line and body explaining **why**.
</How>
</Explain>

```bash
cd shop
git add cart.js
git commit -q -m "Add cart total function"
git add README.md
git commit -q -m "Document how to run the cart"
git status -s | wc -l | sed 's/$/ files left uncommitted/'
git log --oneline main..HEAD | cut -c9-
```

```text output
0 files left uncommitted
Document how to run the cart
Add cart total function
```

`main..HEAD` means "commits on my branch that are not on main" — exactly what your PR will contain.`main..HEAD` means "commits on my branch that are not on main" — exactly what your PR will contain.

Line by line:

- `git add cart.js` stages only the new file, and `git commit -m "Add cart total function"` saves it as one commit.
- Then `README.md` is staged and committed separately with its own message. Two small commits, each with one purpose, instead of one "update files" commit.
- `git status -s | wc -l` counts remaining changes: 0, so everything is committed.
- `git log --oneline main..HEAD` lists our two commits, newest first.

Before each commit, a good habit is `git diff --staged`: it shows exactly what is about to be committed, so you notice leftover `console.log` lines or secrets.

### 6. Push your branch

<Explain>
<What>
`git push` uploads your commits to the remote.
</What>
<Why>
Backup, sharing, and needed for a pull request.
</Why>
<When>
After a few commits, and at least at the end of each day.
</When>
<Where>
The first push of a new branch needs `-u origin branchname` (sets "upstream", so later just `git push`).
</Where>
<How>
Never `git push --force` to shared branches; if you must after a rebase, use `--force-with-lease` on **your own** branch.
</How>
</Explain>

```bash
cd shop
git push -q -u origin feature/cart-total
git status -sb | head -1
git ls-remote --heads origin | awk '{sub("refs/heads/","",$2); print "on server:", $2}'
```

```text output
## feature/cart-total...origin/feature/cart-total
on server: feature/cart-total
on server: main
```

Line by line:

- `git push -q -u origin feature/cart-total` uploads our branch to the server. `-u` remembers the link, so later a plain `git push` or `git pull` on this branch knows where to go.
- `git status -sb | head -1` shows `## feature/cart-total...origin/feature/cart-total`: our branch is linked to the server copy, and nothing is ahead or behind.
- `git ls-remote --heads origin` asks the server which branches it has. Our branch is now there, so teammates and CI can see it, and on GitHub you can open a pull request from it.

### 7. Pull request, review, merge

<Explain>
<What>
On GitHub you open a PR from `feature/cart-total` into `main`. Teammates review, automated checks (tests, lint, security scans) run, and then it is merged.
</What>
<Why>
Four eyes and automated checks before code reaches `main`.
</Why>
<When>
When the task is done (or as a **draft PR** to get early feedback).
</When>
<Where>
GitHub "Compare & pull request" button, or `gh pr create`.
</Where>
<How>
A good PR: clear title, what and why, how to test, screenshots for UI, small size (under ~400 lines changed). After merge, delete the branch.
</How>
</Explain>

```bash
# what clicking "Merge pull request" does on the server, simulated locally
cd shop
git switch -q main
git merge -q --no-ff -m "Merge pull request #12 from feature/cart-total" feature/cart-total
git push -q origin main
git branch -q -d feature/cart-total && echo "Deleted local branch feature/cart-total"
git push -q origin --delete feature/cart-total
git log --graph --format=%s | head -4
```

```text output
Deleted local branch feature/cart-total
*   Merge pull request #12 from feature/cart-total
|\  
| * Document how to run the cart
| * Add cart total function
```

Line by line:

- `git switch -q main` moves back to `main`.
- `git merge --no-ff -m "Merge pull request #12 ..."` merges the branch with a merge commit. This is what GitHub's green **Merge pull request** button does on the server.
- `git push -q origin main` uploads the updated `main`.
- `git branch -q -d feature/cart-total` deletes the local branch. `-d` only works if the branch is fully merged, so nothing can be lost.
- `git push -q origin --delete feature/cart-total` deletes the branch on the server too (GitHub can do this automatically after merging).
- The graph shows our two commits joined into `main` by the merge commit.

On a real team you **don't** merge locally like this; you click merge on GitHub after review and checks pass, then run `git switch main && git pull`.

### 8. Stash: park unfinished work

<Explain>
<What>
`git stash` saves your uncommitted changes on a shelf and cleans the working directory; `git stash pop` brings them back.
</What>
<Why>
An urgent bug arrives while you are halfway through something — you need a clean tree to switch branches.
</Why>
<When>
Interruptions; pulling when you have local edits.
</When>
<Where>
`git stash list`, `git stash push -m "message"`, `git stash -u` (include untracked files).
</Where>
<How>
Do not leave things in the stash for weeks — it is easy to forget. A WIP commit on your branch is often better.
</How>
</Explain>

```bash
cd shop
echo "half-finished discount code" >> cart.js
git stash push -q -m "discount WIP"
git status -s | wc -l | sed 's/$/ changes in working dir after stash/'
git stash list | sed 's/On main: //'
git stash pop -q
git status -s
```

```text output
0 changes in working dir after stash
stash@{0}: discount WIP
 M cart.js
```

Line by line:

- `echo "half-finished discount code" >> cart.js` simulates unfinished work.
- `git stash push -q -m "discount WIP"` saves that change on the stash shelf with a description and restores `cart.js` to its last committed state.
- `git status -s | wc -l` prints 0: the working directory is clean, so you can safely switch branches or pull.
- `git stash list` shows saved entries. `stash@{0}` is the newest.
- `git stash pop -q` re-applies the newest stash and removes it from the list. `git status -s` shows `cart.js` modified again: the work is back.

`git stash apply` re-applies without removing the entry from the list, which is useful if you want to apply the same changes to more than one branch.

### 9. Undo simple mistakes

<Explain>
<What>
`git restore file` throws away unstaged edits; `git restore --staged file` unstages; `git commit --amend` fixes the last (unpushed) commit.
</What>
<Why>
Everyone makes small mistakes many times a day.
</Why>
<When>
Before pushing. After pushing, prefer `git revert` (covered in **Undoing Things**).
</When>
<Where>
`git status` even prints these hints.
</Where>
<How>
`git restore` permanently discards uncommitted edits — there is no undo for that.
</How>
</Explain>

```bash
cd shop
git restore cart.js                      # discard the WIP edit
echo "DEBUG=true" > debug.env
git add debug.env
git restore --staged debug.env           # oops, unstage it
git status -s
rm debug.env
echo "Run tests: npm test" >> README.md
git commit -qam "Add tset instructions"
git commit -q --amend -m "Add test instructions"   # fix typo in last message
git log -1 --format=%s
```

```text output
?? debug.env
Add test instructions
```

Line by line:

- `git restore cart.js` throws away the uncommitted change in `cart.js`, bringing back the last committed version. It can't be undone, so be sure.
- `git add debug.env` stages a file by mistake. `git restore --staged debug.env` **unstages** it: the file stays in the folder (`??` untracked) but will not be committed.
- `rm debug.env` deletes it from the folder.
- `git commit -qam "Add tset instructions"` commits with a typo in the message.
- `git commit -q --amend -m "Add test instructions"` replaces that last commit with a corrected one. Only amend commits you haven't pushed yet, because amending creates a **new** commit with a new hash.

| Situation | Command |
| --- | --- |
| Discard edits in a file | `git restore file` |
| Unstage a file (keep the edits) | `git restore --staged file` |
| Fix the last commit's message or add a forgotten file | `git add file && git commit --amend` |
| Undo a commit that is already pushed | `git revert <hash>` (see **Undoing Things**) |

### 10. Keep your branch up to date

<Explain>
<What>
While you work, `main` moves on. Bring those changes into your branch regularly.
</What>
<Why>
Smaller, earlier conflicts are far easier than one big conflict at the end.
</Why>
<When>
Daily for long-lived branches, and before opening or merging a PR.
</When>
<Where>
`git pull origin main` (merge) or `git rebase origin/main` (see **Rebasing**).
</Where>
<How>
`git fetch` then merge or rebase `origin/main` into your branch, run tests, push.
</How>
</Explain>

```bash
cd shop && git push -q
git switch -q -c feature/coupons
echo "coupons" > coupons.js && git add . && git commit -qm "Add coupons"
# meanwhile a teammate merges into main
cd ../teammate && git pull -q && echo "v1" > VERSION && git add . && git commit -qm "Add version file" && git push -q
cd ../shop
git fetch -q
echo "main is ahead of my branch by $(git rev-list --count HEAD..origin/main) commit(s)"
git merge -q --no-edit origin/main
echo "after update: $(git rev-list --count HEAD..origin/main) behind; files: $(ls | tr '\n' ' ')"
```

```text output
main is ahead of my branch by 1 commit(s)
after update: 0 behind; files: LICENSE README.md VERSION cart.js coupons.js 
```

Line by line:

- `git push -q` sends the updated `main` (with the merge from earlier) to the server.
- We start a new branch `feature/coupons` and commit `coupons.js`.
- Meanwhile the teammate pulls, adds `VERSION`, and pushes to `main`.
- `git fetch -q` updates `origin/main`. `git rev-list --count HEAD..origin/main` counts commits on `origin/main` that our branch doesn't have: 1.
- `git merge -q --no-edit origin/main` brings them into our branch. Now we are 0 behind, and `VERSION` appears next to our `coupons.js`.

Doing this often keeps every conflict small. If you wait two weeks, you may face twenty conflicts at once.

## Hands-on

The whole day in one script:

```bash
git init -q --bare remote.git && git clone -q remote.git app 2>/dev/null && cd app
git commit -q --allow-empty -m "Start" && git push -q -u origin main
for task in header footer; do
  git switch -q main && git pull -q
  git switch -q -c "feature/$task"
  echo "<$task/>" > "$task.html"
  git add . && git commit -qm "Add $task"
  git push -q -u origin "feature/$task"
  git switch -q main && git merge -q --no-ff -m "Merge feature/$task" "feature/$task" && git push -q
  git branch -q -d "feature/$task"
done
git log --graph --format=%s
```

```text output
*   Merge feature/footer
|\  
| * Add footer
|/  
*   Merge feature/header
|\  
| * Add header
|/  
* Start
```

Line by line:

- The first two lines set up a "server" (`remote.git`), clone it into `app`, and push an empty starting commit. `2>/dev/null` hides Git's harmless warning "You appear to have cloned an empty repository".
- The loop runs the whole daily cycle twice, once for `header` and once for `footer`:
  - `git switch main && git pull`: start from the latest code.
  - `git switch -c feature/$task`: a new branch for this task.
  - create the file, `git add`, `git commit`: save the work.
  - `git push -u origin feature/$task`: share it (and open a PR on GitHub).
  - merge into `main` with `--no-ff` and push: what happens after the PR is approved.
  - `git branch -d`: delete the finished branch.
- The final graph shows each feature as its own small loop joined back into `main`. That is what a healthy repository's history looks like.

## Real-world example

A typical day for a junior developer: 9:00 `git switch main && git pull`; picks ticket SHOP-142 and runs `git switch -c fix/SHOP-142-cart-rounding`. Makes three small commits over the morning, pushes, and opens a draft PR at lunch so CI runs. A reviewer asks for a test; she adds a fourth commit and pushes — the PR updates automatically. At 15:00 an urgent production bug arrives: she `git stash`es a half-done change, switches to a new `hotfix/` branch from `main`, fixes and ships it, then returns and `git stash pop`s. By evening her PR is approved, merged with "Squash and merge", and the branch is deleted.

## Common mistakes

- **Committing directly to `main`** instead of a branch.
- **Forgetting `git pull`** before starting — and building on old code.
- **`git add .` without looking** — commits `.env`, logs or debug files.
- **Giant PRs** nobody can review properly.
- **Messages like "update" or "fix stuff".**
- **Force-pushing a shared branch** and destroying teammates' commits.
- **Long-lived branches** that drift for weeks and end in painful conflicts.

## Security lens

<Callout type="security">
`git diff --staged` before every commit is your last line of defence against committing a secret.
</Callout>

- **Protected `main`**: require PRs, reviews and passing checks — nobody (including admins) pushes directly.
- **CI security checks on every PR**: secret scanning, dependency scanning (SCA), SAST.
- **Review the diff, not just the description** — malicious or careless changes hide in large PRs.
- **Use SSH keys or tokens, never passwords**, for pushing; keep tokens short-lived and scoped.
- **Don't push to the wrong remote** — check `git remote -v` in forks and mirrors.

## Interview questions

<QA q="Describe your daily Git workflow.">
I update main with git pull, create a short-lived feature branch, make small focused commits after checking git status and git diff, push the branch with -u and open a pull request. CI runs tests and security checks, teammates review, and after approval the branch is merged into main and deleted. For long-running work I regularly bring in changes from main.
</QA>

<QA q="What is the difference between git fetch and git pull?">
git fetch downloads new commits and updates remote-tracking branches such as origin/main without changing your local branches or files. git pull runs a fetch and then integrates the changes into the current branch, by merge or by rebase depending on configuration.
</QA>

<QA q="When would you use git stash?">
When I have uncommitted changes but need a clean working directory, for example to switch branches for an urgent fix or to pull. git stash saves the changes and git stash pop restores them. For longer interruptions a work-in-progress commit on the feature branch is safer.
</QA>

<QA q="What makes a good commit and a good pull request?">
A good commit contains one logical change and has a short imperative summary with an explanation of why if needed. A good pull request is small and focused, has a clear title and description of what changed, why and how to test it, passes automated checks, and is easy to review.
</QA>

## Practice

1. Create a bare repo as a "server", clone it twice, and push from one clone and pull in the other.
2. Make a branch with three small commits and list them with `git log main..HEAD`.
3. Use `git add -p` to split one file's changes into two commits.
4. Stash a change, switch branches, come back and pop it.
5. Fork a public repo on GitHub, make a small docs fix on a branch and open a pull request.

Next: **Branching and Merging**.
