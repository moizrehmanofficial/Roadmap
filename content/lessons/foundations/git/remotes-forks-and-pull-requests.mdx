<Callout type="tip" title="In one minute">
A **remote** is another copy of your repository, usually on GitHub, saved under a short name. **`origin`** is the one you cloned from. Git keeps **remote-tracking branches** like **`origin/main`**: your last-known picture of the server. **`git fetch`** updates that picture, **`git pull`** fetches and merges, and **`git push`** uploads your commits. A **fork** is your own copy of someone else's GitHub repo. You push to your fork (`origin`) and propose changes to the original (`upstream`) with a **pull request (PR)**. In a PR, the team reviews your changes and automated checks run before anything is merged.
</Callout>

## Start from zero

<Callout type="analogy">
Think of a **shared Google Drive folder** and the **copy on your laptop**. The Drive folder is the **remote**. Your laptop copy is your **local repository**. You work offline on the laptop. When you are ready, you **upload** your changes (push), and you **download** what others uploaded (fetch/pull). A **fork** is like making **your own copy of someone else's shared folder** in your own Drive: you can change anything in it. If you think your change would help the original owner, you send them a **request to include it** (a pull request). They look at it, comment, and decide whether to accept it.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Remote** | A named link to another copy of the repo | `origin` |
| **origin** | Default name of the remote you cloned from | your GitHub repo |
| **upstream** | Common name for the original project when you work on a fork | `upstream` |
| **Remote-tracking branch** | Your local, read-only snapshot of a branch on the remote | `origin/main` |
| **Tracking (upstream) branch** | The remote branch your local branch is linked to | `main` ↔ `origin/main` |
| **Ahead / behind** | How many commits you have that the remote doesn't, and the reverse | "ahead 2, behind 1" |
| **Fork** | Your own server-side copy of another person's repository | `moiz/react` from `facebook/react` |
| **Pull request (PR)** | A request to merge a branch, with discussion, review and checks | PR #42 |

## What is it?

Git is **distributed**: every clone is a full repository. Nothing is "the server" in Git itself. GitHub is just one more repository that everyone **agrees** to treat as the shared, official copy. Remotes are how your local repo knows where those other copies are.

```text
        upstream (original project, e.g. github.com/acme/shop)
            ▲  pull request                │ fetch
            │                              ▼
        origin (your fork, github.com/moiz/shop)
            ▲ push                         │ fetch / pull
            │                              ▼
                 your laptop (local repo)
```

## Why does it matter?

- **Collaboration:** every team shares code through a remote.
- **Backup:** a pushed branch survives your laptop dying.
- **Open source:** forks and PRs are how anyone in the world contributes to projects like React, Kubernetes or Linux tools.
- **Quality and security:** PRs are where code review, tests and security scans happen before code reaches `main`.
- **CI/CD:** pushes and PRs trigger pipelines (see **GitHub Actions Basics**).

## When and where do you use it?

- **Company project:** usually one remote (`origin`). Everyone pushes branches to it and opens PRs inside the same repo.
- **Open source, or a repo you can't push to:** fork it. Then `origin` is your fork and `upstream` is the original.
- **Every day:** `fetch`/`pull` in the morning, `push` when your work is ready, a PR when a task is done.

## Concepts one by one

The examples use local "server" repositories (`--bare` folders) in place of GitHub so they run offline. With GitHub, the only difference is the URL.

### 1. What a remote is: `git remote`

<Explain>
<What>
A remote is a **name** (like `origin`) saved together with a **URL**. The URL points to another copy of the repository.
</What>
<Why>
So you can type `git push origin` instead of a long URL every time, and so Git can remember what the remote's branches looked like.
</Why>
<When>
`git clone` creates `origin` automatically. You add more remotes yourself, for example `upstream` for a fork.
</When>
<Where>
It is stored in `.git/config`. `git remote -v` lists every remote with its fetch and push URL.
</Where>
<How>
`git remote add name url`, `git remote rename old new`, `git remote remove name`, `git remote set-url name newurl`.
</How>
</Explain>

```bash
git config --global user.name "Moiz Rehman"; git config --global user.email "moiz@example.com"; git config --global init.defaultBranch main
git init -q --bare github-shop.git            # pretend this is github.com/acme/shop
git init -q shop && cd shop
git remote add origin ../github-shop.git
git remote -v
echo "--- stored in .git/config:"
git config --get-regexp '^remote\.origin\.'
```

```text output
origin	../github-shop.git (fetch)
origin	../github-shop.git (push)
--- stored in .git/config:
remote.origin.url ../github-shop.git
remote.origin.fetch +refs/heads/*:refs/remotes/origin/*
```

Line by line:

- `git init -q --bare github-shop.git` creates a **bare** repository. It has history but no working files, exactly like a repo on GitHub's servers.
- `git remote add origin ../github-shop.git` saves the name `origin` for that URL. On GitHub this would be `https://github.com/acme/shop.git`.
- `git remote -v` shows two URLs per remote: one for fetching and one for pushing. They are usually the same.
- `remote.origin.fetch +refs/heads/*:refs/remotes/origin/*` is the **refspec**. It means: "every branch on the server (`refs/heads/*`) is copied to `origin/<name>` on my side." That is where `origin/main` comes from.

### 2. Push: upload your commits

<Explain>
<What>
`git push <remote> <branch>` sends your local commits to the remote and moves the remote's branch forward.
</What>
<Why>
Until you push, your commits exist only on your computer. Teammates can't see them, CI can't test them, and if your laptop dies they are lost.
</Why>
<When>
After committing a meaningful piece of work. Always before opening a PR, and at the end of the day.
</When>
<Where>
The first push of a branch: `git push -u origin branch`. The `-u` (`--set-upstream`) links your local branch to `origin/branch`, so after that a plain `git push` or `git pull` is enough.
</Where>
<How>
A push is **rejected** if the remote has commits you don't have. Git refuses to throw away someone else's work. You must pull first.
</How>
</Explain>

```bash
cd shop
echo "# Shop" > README.md && git add . && git commit -qm "Initial commit"
git push -q -u origin main
git branch -vv | sed -E 's/ [0-9a-f]{7} / <hash> /'
git ls-remote --heads origin | awk '{print "server branch:", $2}'
```

```text output
* main <hash> [origin/main] Initial commit
server branch: refs/heads/main
```

Line by line:

- `git push -q -u origin main` uploads `main` and links it to `origin/main`. `-q` only hides the progress text.
- `git branch -vv` (double v) shows each local branch with its tracking branch in brackets: `[origin/main]`.
- `git ls-remote --heads origin` asks the **server** directly which branches it has, without downloading anything.

### 3. Remote-tracking branches: `origin/main`

<Explain>
<What>
`origin/main` is a **read-only bookmark** in your local repo. It shows where `main` was on the server **the last time you talked to it**.
</What>
<Why>
Git works offline. It can't check the server every second, so it remembers the last known state. That lets you compare your work with the server without a network connection.
</Why>
<When>
Every fetch, pull and push updates it.
</When>
<Where>
`git branch -r` lists remote-tracking branches; `git branch -a` lists local and remote ones together.
</Where>
<How>
You never commit to `origin/main` directly. You compare with it (`git log main..origin/main`) and merge or rebase from it.
</How>
</Explain>

```bash
cd shop
git switch -q -c feature/cart
git commit -q --allow-empty -m "Cart work"
git push -q -u origin feature/cart
git switch -q main
echo "--- all branches (local + remote-tracking):"
git branch -a
```

```text output
--- all branches (local + remote-tracking):
  feature/cart
* main
  remotes/origin/feature/cart
  remotes/origin/main
```

`feature/cart` and `main` are **your** branches. You can commit to them. `remotes/origin/...` are Git's **memory of the server**.

### 4. Fetch: look before you merge

<Explain>
<What>
`git fetch` downloads new commits and branches from the remote and updates `origin/*`. It does **not** touch your own branches or your files.
</What>
<Why>
It is completely safe. You see what teammates did, then decide how and when to bring it in.
</Why>
<When>
Any time: before starting work, before a rebase, before reviewing a teammate's branch.
</When>
<Where>
`git fetch` (default remote), `git fetch --all` (every remote), `git fetch --prune` (also removes `origin/*` branches that were deleted on the server).
</Where>
<How>
After fetching, `git log main..origin/main` lists commits the server has and you don't. `git status` shows "behind".
</How>
</Explain>

```bash
# a teammate clones and pushes a commit
git clone -q github-shop.git teammate && cd teammate
echo "MIT" > LICENSE && git add . && git commit -qm "Add license" && git push -q
cd ../shop
git status -sb | head -1
git fetch -q
git status -sb | head -1
echo "new on server: $(git log --format=%s main..origin/main)"
ls
```

```text output
## main...origin/main
## main...origin/main [behind 1]
new on server: Add license
README.md
```

Line by line:

- Before the fetch, `git status` says nothing about being behind. Git doesn't know about the teammate's commit yet because it hasn't asked the server.
- After `git fetch`, Git knows: `[behind 1]`.
- `ls` still shows only `README.md`. Fetch **never** changes your files. `LICENSE` arrives only after you merge or pull.

### 5. Pull: fetch + integrate

<Explain>
<What>
`git pull` = `git fetch` + integrate `origin/<your-branch>` into your current branch, by **merge** (default) or **rebase**.
</What>
<Why>
It brings your branch up to date in one command.
</Why>
<When>
Every morning on `main`. Also before pushing when the push was rejected.
</When>
<Where>
`git pull` (uses the tracking branch), `git pull --rebase`, or set a default once: `git config --global pull.rebase true` (or `false`). `git pull --ff-only` refuses unless it's a simple fast-forward. That is a safe habit on `main`.
</Where>
<How>
If you and the server both have new commits, pull with merge creates a merge commit. Pull with rebase replays your commits on top of the server's.
</How>
</Explain>

```bash
cd shop
git pull -q --ff-only
git status -sb | head -1
ls
```

```text output
## main...origin/main
LICENSE
README.md
```

```text
fetch:  server ──► origin/main          (your files unchanged)
merge:  origin/main ──► main + files   (now you have the commits)
pull = fetch + merge (or rebase)
```

Now `LICENSE` is in your folder. The teammate's commit has been fetched **and** merged.

### 6. Rejected push: someone pushed first

<Explain>
<What>
If the server's branch has commits you don't have, `git push` is **rejected** with "fetch first" or "non-fast-forward".
</What>
<Why>
If Git accepted your push, it would overwrite your teammate's commits. Git protects their work.
</Why>
<When>
Very often on busy branches.
</When>
<Where>
The error message itself tells you: "Updates were rejected because the remote contains work that you do not have locally."
</Where>
<How>
`git pull` (or `git pull --rebase`), fix any conflicts, run tests, then `git push` again. **Do not** reach for `--force`.
</How>
</Explain>

```bash
cd teammate && git pull -q
echo "v1" > VERSION && git add . && git commit -qm "Add version" && git push -q
cd ../shop
echo "docs" > DOCS.md && git add . && git commit -qm "Add docs"
git push 2>&1 | grep -o 'rejected.*(fetch first)'
git pull -q --rebase
git push -q && echo "push succeeded after pull --rebase"
git log --format=%s | head -3
```

```text output
rejected]        main -> main (fetch first)
push succeeded after pull --rebase
Add docs
Add version
Add license
```

Line by line:

- The teammate pushed `Add version` first.
- Our `git push` is rejected with `(fetch first)`.
- `git pull --rebase` downloads `Add version` and replays our `Add docs` commit on top of it, so history stays a straight line.
- Now our branch contains everything the server has, so the push is a fast-forward and succeeds.

### 7. Ahead and behind

<Explain>
<What>
**Ahead N**: you have N commits the remote doesn't have yet (you need to push). **Behind N**: the remote has N commits you don't have yet (you need to pull).
</What>
<Why>
It answers "am I in sync?" at a glance.
</Why>
<When>
Before pushing, before starting work, in your shell prompt or editor status bar.
</When>
<Where>
`git status`, `git status -sb`, `git branch -vv`, `git rev-list --left-right --count main...origin/main`.
</Where>
<How>
Both at once ("ahead 1, behind 2") means you have **diverged**. Pull with merge or rebase, then push.
</How>
</Explain>

```bash
cd shop
git commit -q --allow-empty -m "Local only"
cd ../teammate && git pull -q && git commit -q --allow-empty -m "Server only" && git push -q && cd ../shop
git fetch -q
git status -sb | head -1
git rev-list --left-right --count main...origin/main | awk '{print "ahead:", $1, " behind:", $2}'
```

```text output
## main...origin/main [ahead 1, behind 1]
ahead: 1  behind: 1
```

### 8. Authentication: HTTPS vs SSH

<Explain>
<What>
GitHub needs to know who is pushing. **HTTPS** URLs use a **personal access token** (or the Git Credential Manager / `gh auth login` login flow). **SSH** URLs use a **key pair** on your computer.
</What>
<Why>
GitHub no longer accepts your account password for Git operations. Tokens and keys can be limited in scope and revoked.
</Why>
<When>
Once per computer, when you set it up.
</When>
<Where>
HTTPS: `https://github.com/acme/shop.git`. SSH: `git@github.com:acme/shop.git`. Switch between them with `git remote set-url origin <new-url>`.
</Where>
<How>
SSH setup: `ssh-keygen -t ed25519 -C "you@example.com"`, add the **public** key (`~/.ssh/id_ed25519.pub`) in GitHub → Settings → SSH and GPG keys, then test with `ssh -T git@github.com`.
</How>
</Explain>

```bash
cd shop
git remote set-url origin git@github.com:acme/shop.git
git config --get remote.origin.url
git remote set-url origin https://github.com/acme/shop.git
git config --get remote.origin.url
git remote set-url origin ../github-shop.git    # back to our local "server"
```

```text output
git@github.com:acme/shop.git
https://github.com/acme/shop.git
```

| | HTTPS + token | SSH key |
| --- | --- | --- |
| Setup | Login once with `gh auth login` or Git Credential Manager | Generate a key, add the public key to GitHub |
| Works through strict firewalls | Yes (port 443) | Sometimes blocked (port 22; GitHub also offers ssh.github.com on 443) |
| Secret on your machine | Token (stored by the credential manager) | Private key (protect it with a passphrase) |

### 9. Forks: your own copy of someone else's project

<Explain>
<What>
A **fork** is a copy of a repository under **your** GitHub account, made with the **Fork** button. GitHub remembers which repo it came from.
</What>
<Why>
You can't push to repos you don't own (e.g. `facebook/react`). Instead, you push to your fork and propose changes back with a PR.
</Why>
<When>
Contributing to open source, or in companies that use the fork workflow for strict access control.
</When>
<Where>
After forking: clone **your fork** (it becomes `origin`), then add the original as `upstream`.
</Where>
<How>
Rule: **pull from `upstream`, push to `origin`**. Open the PR from `yourname:branch` to `upstream:main`.
</How>
</Explain>

```bash
# the original open-source project and its maintainer
git init -q --bare acme-shop.git
git clone -q acme-shop.git maintainer 2>/dev/null && cd maintainer
echo "# Acme Shop" > README.md && git add . && git commit -qm "Acme initial" && git push -q origin main && cd ..
# "Fork" button = a server-side copy under your account
git clone -q --bare acme-shop.git moiz-shop.git
# clone YOUR fork, then add the original as upstream
git clone -q moiz-shop.git contrib && cd contrib
git remote add upstream ../acme-shop.git
git remote -v | sed -E 's#[^ \t]*/((moiz|acme)-shop\.git)#../\1#'
```

```text output
origin	../moiz-shop.git (fetch)
origin	../moiz-shop.git (push)
upstream	../acme-shop.git (fetch)
upstream	../acme-shop.git (push)
```

Line by line:

- `git clone --bare acme-shop.git moiz-shop.git` does what GitHub's **Fork** button does: it makes a server-side copy of the whole history.
- `git clone moiz-shop.git contrib` clones **your fork**, so `origin` points to it.
- `git remote add upstream ../acme-shop.git` adds the original project, so you can fetch its new commits.

### 10. Keeping your fork in sync

<Explain>
<What>
The original project keeps moving. Your fork does **not** update automatically.
</What>
<Why>
If your branch starts from an old `main`, your PR will have conflicts or test failures against the current code.
</Why>
<When>
Before starting every new contribution, and while a PR is open if `main` moved.
</When>
<Where>
`git fetch upstream` → `git switch main` → `git merge --ff-only upstream/main` → `git push origin main`. On GitHub there is also a **Sync fork** button.
</Where>
<How>
Never commit your own work on your fork's `main`. Keep it an exact mirror of upstream and do all work on branches. Then syncing is always a clean fast-forward.
</How>
</Explain>

```bash
# the maintainer merges something new upstream
cd maintainer && echo "fast checkout" > checkout.txt && git add . && git commit -qm "Faster checkout" && git push -q && cd ..
cd contrib
git fetch -q upstream
echo "my main is behind upstream by $(git rev-list --count main..upstream/main)"
git merge -q --ff-only upstream/main
git push -q origin main
echo "after sync: $(git rev-list --count main..upstream/main) behind; fork's main = $(git log -1 --format=%s origin/main)"
```

```text output
my main is behind upstream by 1
after sync: 0 behind; fork's main = Faster checkout
```

### 11. Pull requests: proposing a change

<Explain>
<What>
A PR asks: "please merge **this branch** (head) into **that branch** (base)". GitHub shows the commits and the diff, and gives a place for discussion, review and automated checks.
</What>
<Why>
It is the quality gate. Another person reads the code, CI runs the tests and security scans, and there is a written record of why the change was made.
</Why>
<When>
When a task is finished. Open a **draft PR** early if you want feedback before it's done.
</When>
<Where>
On GitHub after pushing a branch ("Compare & pull request" button), or with the GitHub CLI: `gh pr create --base main --title "..." --body "..."`.
</Where>
<How>
Branch → commits → push → open the PR → reviewers comment or approve → you push fixes (the PR updates automatically) → checks pass → merge → delete the branch.
</How>
</Explain>

```bash
cd contrib
git switch -q -c fix/readme-typo
echo "# Acme Shop - fast and simple" > README.md
git commit -qam "Improve README title"
git push -q -u origin fix/readme-typo
echo "PR: moiz:fix/readme-typo → acme:main"
echo "commits in PR:"; git log --format='  %s' upstream/main..HEAD
echo "files changed:"; git diff --stat upstream/main...HEAD | sed -E 's/ +\| +/ | /'
```

```text output
PR: moiz:fix/readme-typo → acme:main
commits in PR:
  Improve README title
files changed:
 README.md | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`upstream/main..HEAD` is exactly what the PR will show: the commits on your branch that are not in the project's `main` yet. `git diff upstream/main...HEAD` (three dots) shows the changes since your branch split off. GitHub's "Files changed" tab uses the same comparison.

A good PR description:

```text
## What
Clarifies the README title.

## Why
New users didn't understand what the project does (issue #87).

## How to test
Open README.md — the title now describes the project.

Closes #87
```

`Closes #87` automatically closes issue 87 when the PR is merged.

### 12. Review and merge

<Explain>
<What>
Reviewers can **Comment**, **Approve**, or **Request changes**. The author answers by pushing new commits to the same branch. When rules are satisfied, someone with permission merges.
</What>
<Why>
Two people understand every change, bugs and security issues are caught early, and knowledge spreads through the team.
</Why>
<When>
Every PR, before merging.
</When>
<Where>
GitHub "Files changed" tab: click a line to comment, or use "suggestion" blocks the author can apply with one click. Repository rules can require approvals and passing checks.
</Where>
<How>
Merge style is a team choice: merge commit, squash, or rebase (see **Branching and Merging**). After merging, delete the branch and sync your fork's `main` again.
</How>
</Explain>

```bash
# the maintainer reviews and merges the PR (what GitHub's merge button does)
cd maintainer
git fetch -q ../moiz-shop.git fix/readme-typo
git merge -q --no-ff -m "Merge pull request #88 from moiz/fix/readme-typo" FETCH_HEAD
git push -q
cd ../contrib
git switch -q main && git pull -q --ff-only upstream main && git push -q origin main
git branch -q -D fix/readme-typo && git push -q origin --delete fix/readme-typo
git log --graph --format=%s | head -4
```

```text output
*   Merge pull request #88 from moiz/fix/readme-typo
|\  
| * Improve README title
|/  
```

## Hands-on

The full fork-and-PR loop, end to end:

```bash
git init -q --bare project.git
git clone -q project.git owner 2>/dev/null && cd owner
echo "print('hi')" > app.py && git add . && git commit -qm "Initial app" && git push -q origin main && cd ..
git clone -q --bare project.git myfork.git                     # 1. Fork
git clone -q myfork.git work && cd work                          # 2. Clone your fork
git remote add upstream ../project.git && git fetch -q upstream  # 3. Add upstream
git switch -q -c feature/greeting                                # 4. Branch
echo "print('hello, world')" > app.py && git commit -qam "Friendlier greeting"   # 5. Commit
git push -q -u origin feature/greeting                           # 6. Push to your fork
echo "PR contains: $(git log --format=%s upstream/main..HEAD)"   # 7. Open PR
cd ../owner && git pull -q ../myfork.git feature/greeting        # 8. Maintainer merges
git push -q && cd ../work
git switch -q main && git pull -q upstream main && git push -q origin main      # 9. Sync fork
echo "fork main now: $(git log -1 --format=%s)"; cat app.py
```

```text output
PR contains: Friendlier greeting
fork main now: Friendlier greeting
print('hello, world')
```

## Real-world example

Moiz wants to fix a broken link in the documentation of an open-source library he uses. He clicks **Fork**, clones `github.com/moiz/library`, and adds `upstream`. He creates `docs/fix-install-link`, fixes the link, commits "Fix broken install link in README", pushes to his fork, and opens a PR to `library:main` with "Closes #1203". The CI bot runs the docs build. A maintainer comments: "please also fix the same link in CONTRIBUTING.md". Moiz commits once more and pushes, and the PR updates by itself. The maintainer approves and uses "Squash and merge". Moiz deletes his branch, presses **Sync fork**, and the project now lists him as a contributor. That is a real line on a CV.

## Common mistakes

- **Working on the fork's `main`** instead of a branch. Syncing with upstream then becomes messy.
- **Forgetting to sync** and opening a PR based on months-old code.
- **Pushing to `upstream` by mistake** (on a repo where you have access). Check `git remote -v`.
- **Thinking `fetch` updated your files.** It only updates `origin/*`; you still need to merge.
- **Answering a rejected push with `--force`** and deleting a teammate's work.
- **Huge PRs** (thousands of lines) that nobody can review properly.
- **Empty PR descriptions.** Reviewers have to guess what and why.
- **Using your GitHub password or a token pasted inside the remote URL** (`https://user:token@github.com/...`). The token is then stored in plain text in `.git/config`.

## Security lens

<Callout type="security">
A pull request is code from someone you may not know, asking to run in your project. Treat it like untrusted input.
</Callout>

- **Branch protection / rulesets on `main`:** require PRs, at least one approval, passing status checks, and no force pushes.
- **CODEOWNERS:** sensitive paths (auth, payments, `.github/workflows/`, Terraform) automatically require review from the right people.
- **PRs from forks and CI:** by default, GitHub doesn't give secrets to workflows triggered by PRs from forks. Be careful with `pull_request_target`, which **does** run with secrets. Never use it to check out and run the PR's code (see **GitHub Actions Basics**).
- **Review the actual diff, not the description.** Malicious changes hide in big PRs, dependency lock files, minified files and CI configs.
- **Typosquatted remotes:** check the URL before cloning or adding a remote (`github.com/faceb00k/react` is not React).
- **Tokens:** use fine-grained, short-lived personal access tokens with minimum scope, or SSH keys protected with a passphrase. Revoke them when a laptop is lost.
- **Never put credentials in remote URLs.** Use a credential manager or SSH.

## Interview questions

<QA q="What is the difference between origin and upstream?">
Both are just remote names. origin is the default name of the remote you cloned from. In a fork workflow it is your fork. upstream is the conventional name for the original repository you forked, which you fetch from to stay in sync and target with pull requests.
</QA>

<QA q="What is a remote-tracking branch such as origin/main?">
It is a read-only local reference that records where a branch on the remote was the last time you fetched, pulled or pushed. It lets you compare your work with the remote and merge or rebase from it, but you do not commit to it directly. git fetch updates it without changing your local branches.
</QA>

<QA q="Your push was rejected as non-fast-forward. What do you do?">
It means the remote has commits I do not have. I run git pull or git pull --rebase to integrate them, resolve any conflicts, run the tests, and push again. I would not force push, because that would overwrite other people's commits.
</QA>

<QA q="Describe the fork and pull request workflow.">
Fork the repository on GitHub, clone the fork so it becomes origin, add the original as upstream, keep main synced from upstream, create a feature branch, commit, push the branch to origin, and open a pull request from the fork's branch to upstream's main. Then address review feedback by pushing more commits until the maintainers merge it.
</QA>

<QA q="Why are pull requests from forks a security concern for CI?">
The code comes from an untrusted contributor and may try to steal secrets or abuse the CI runner. GitHub therefore does not expose repository secrets to normal pull_request workflows from forks and may require approval to run them. Workflows using pull_request_target run with secrets in the base repository's context, so they must never check out and execute the untrusted PR code.
</QA>

## Key terms

<Terms>
  <Term name="Remote">Named URL of another copy of the repository.</Term>
  <Term name="origin">Default remote created by clone.</Term>
  <Term name="upstream">Conventional name for the original repo of a fork.</Term>
  <Term name="Remote-tracking branch">Local record of a remote branch, e.g. origin/main.</Term>
  <Term name="Fetch">Download remote changes without integrating them.</Term>
  <Term name="Pull">Fetch and integrate into the current branch.</Term>
  <Term name="Push">Upload local commits to a remote branch.</Term>
  <Term name="Ahead / behind">Commits you have that the remote lacks, and vice versa.</Term>
  <Term name="Fork">Server-side copy of a repository under your account.</Term>
  <Term name="Pull request">Proposal to merge a branch, with review and checks.</Term>
</Terms>
