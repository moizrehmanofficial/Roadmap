<BigIdea>
<Tr>
<En>
A **remote** is another copy of your repository, usually on GitHub, saved under a short name. **`origin`** is the one you cloned from. Git keeps **remote-tracking branches** like **`origin/main`**: your last-known picture of the server. **`git fetch`** updates that picture, **`git pull`** fetches and merges, and **`git push`** uploads your commits. A **fork** is your own copy of someone else's GitHub repo: you push to your fork (`origin`) and propose changes to the original (`upstream`) with a **pull request**, where the team reviews your code and automated checks run before anything is merged.
</En>
<Ur>
**Remote** aap ki repository ki doosri copy hai, aam tor par GitHub par, ek chhote naam se save. **`origin`** wo hai jahan se aap ne clone kiya. Git **remote-tracking branches** rakhta hai jaise **`origin/main`**: server ki aakhri maloom tasveer. **`git fetch`** wo tasveer taaza karta hai, **`git pull`** fetch kar ke merge karta hai, aur **`git push`** aap ke commits upload karta hai. **Fork** kisi aur ki GitHub repo ki aap ki apni copy hai: aap apne fork (`origin`) par push karte hain aur asal (`upstream`) ko **pull request** se tabdeeli tajweez karte hain, jahan team code review karti hai aur merge se pehle automated checks chalte hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Git is **distributed**: every clone is a full repository, and nothing in Git itself is "the server". GitHub is just one more repository that everyone **agrees** to treat as the shared, official copy. Remotes are how your local repo knows where those other copies are.

```text
        upstream (original project, e.g. github.com/acme/shop)
            ▲  pull request                │ fetch
            │                              ▼
        origin (your fork, github.com/alex/shop)
            ▲ push                         │ fetch / pull
            │                              ▼
                 your laptop (local repo)
```

</En>
<Ur>

Git **distributed** hai: har clone poori repository hai, aur Git me khud koi "server" nahi. GitHub bas ek aur repository hai jise sab **maan lete** hain ke yahi saanjhi, sarkari copy hai. Remotes ke zariye aap ki local repo jaanti hai wo doosri copies kahan hain.

```text
        upstream (original project, e.g. github.com/acme/shop)
            ▲  pull request                │ fetch
            │                              ▼
        origin (your fork, github.com/alex/shop)
            ▲ push                         │ fetch / pull
            │                              ▼
                 your laptop (local repo)
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Collaboration:** every team shares code through a remote.
- **Backup:** a pushed branch survives your laptop dying.
- **Open source:** forks and PRs are how anyone in the world contributes to projects like React, Kubernetes or Linux tools.
- **Quality and security:** PRs are where review, tests and security scans happen before code reaches `main`.
- **CI/CD:** pushes and PRs start pipelines (see **GitHub Actions Basics**).

</En>
<Ur>

- **Mil kar kaam:** har team remote ke zariye code share karti hai.
- **Backup:** push shuda branch laptop kharab hone par bhi bachi rehti hai.
- **Open source:** forks aur PRs se duniya ka koi bhi React, Kubernetes ya Linux tools jaise projects me hissa daalta hai.
- **Mayaar aur security:** PRs me hi review, tests aur security scans hote hain, code `main` tak pahunchne se pehle.
- **CI/CD:** pushes aur PRs pipelines chalate hain (dekhein **GitHub Actions Basics**).

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **Company project:** usually one remote (`origin`). Everyone pushes branches to it and opens PRs inside the same repo.
- **Open source, or a repo you can't push to:** fork it. Then `origin` is your fork and `upstream` is the original.
- **Every day:** fetch or pull in the morning, push when work is ready, a PR when a task is done.

</En>
<Ur>

- **Company ka project:** aam tor par ek remote (`origin`). Sab usi par branches push karte aur usi repo me PRs kholte hain.
- **Open source, ya aisi repo jis par push nahi kar sakte:** fork karein. Phir `origin` aap ka fork aur `upstream` asal hai.
- **Rozana:** subah fetch ya pull, kaam tayyar ho to push, kaam khatam ho to PR.

</Ur>
</Tr>
</When>

<Tr>
<En>

```text
git fetch                          # update origin/* (files untouched)
git pull                           # fetch + merge into my branch
git push -u origin feature/x       # upload, and link the branch
git remote add upstream <url>      # fork workflow: the original project
git fetch upstream && git merge --ff-only upstream/main
```

</En>

## Picture it

<Tr>
<En>

Think of a **shared Google Drive folder** and the **copy on your laptop**. The Drive folder is the **remote**; your laptop copy is your **local repository**. You work offline, then **upload** your changes (push) and **download** what others uploaded (fetch, pull). A **fork** is like making **your own copy of someone else's shared folder** in your own Drive: you can change anything. If you think your change would help the original owner, you send them a **request to include it** (a pull request). They look, comment, and decide whether to accept it.

</En>
<Ur>

**Google Drive ka saanjha folder** aur **laptop par us ki copy** socho. Drive folder **remote** hai; laptop copy aap ki **local repository**. Aap offline kaam karte hain, phir apni tabdeeliyan **upload** (push) aur doosron ki **download** (fetch, pull) karte hain. **Fork** aisa hai jaise **kisi aur ke saanjhe folder ki apni copy** apni Drive me bana lena: kuch bhi badal sakte hain. Agar lage ke aap ki tabdeeli asal maalik ke kaam aayegi, to unhe **shamil karne ki darkhwast** bhejte hain (pull request). Wo dekhte hain, tabsira karte hain, aur faisla karte hain maanna hai ya nahi.

</Ur>
</Tr>

</En>
<Ur>

<Walkthrough>

<Step title="What a remote is: git remote">

<Tr>
<En>

A remote is a **name** (like `origin`) saved together with a **URL**, so you can type `git push origin` instead of a long URL, and so Git can remember what the remote's branches looked like. `git clone` creates `origin` automatically; you add others yourself. It's stored in `.git/config`. Commands: `git remote add name url`, `rename`, `remove`, `set-url`.

</En>
<Ur>

Remote ek **naam** (jaise `origin`) hai jo **URL** ke saath save hota hai, taa ke aap lamba URL ke bajaye `git push origin` likhen, aur Git yaad rakh sake remote ki branches kaisi thin. `git clone` `origin` khud banata hai; baqi aap jorte hain. Ye `.git/config` me save hota hai. Commands: `git remote add name url`, `rename`, `remove`, `set-url`.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q --bare github-shop.git            # pretend this is github.com/acme/shop
git init -q shop && cd shop
git remote add origin ../github-shop.git
git remote -v
echo "--- stored in .git/config:"
git config --get-regexp '^remote\.origin\.'
```

```text output
origin	../github-shop.git (fetch)
origin	../github-shop.git (push)
--- stored in .git/config:
remote.origin.url ../github-shop.git
remote.origin.fetch +refs/heads/*:refs/remotes/origin/*
```

<Happened>
<Tr>
<En>

- `git init --bare` made a repo with history but no working files, exactly like one on GitHub's servers.
- `git remote add origin …` saved the name `origin` for that URL (on GitHub: `https://github.com/acme/shop.git`).
- `git remote -v` shows a fetch and a push URL; they're usually the same.
- `+refs/heads/*:refs/remotes/origin/*` is the **refspec**: "every branch on the server is copied to `origin/<name>` on my side". That's where `origin/main` comes from.

</En>
<Ur>

- `git init --bare` ne tareekh wali lekin working files ke baghair repo banayi, bilkul GitHub ke servers wali jaisi.
- `git remote add origin …` ne us URL ke liye `origin` naam save kiya (GitHub par: `https://github.com/acme/shop.git`).
- `git remote -v` fetch aur push ka URL dikhata hai; aam tor par ek jaise.
- `+refs/heads/*:refs/remotes/origin/*` **refspec** hai: "server ki har branch mere paas `origin/<name>` me copy hoti hai". `origin/main` yahin se aata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Push: upload your commits">

<Tr>
<En>

Until you push, your commits exist only on your computer: teammates can't see them, CI can't test them, and if your laptop dies they're lost. `git push <remote> <branch>` sends them and moves the remote's branch forward. The first push of a branch: `git push -u origin branch`; `-u` links it, so later a plain `git push` or `git pull` is enough.

</En>
<Ur>

Push se pehle aap ke commits sirf aap ke computer par hain: saathi nahi dekh sakte, CI test nahi kar sakta, aur laptop kharab ho to kho jate hain. `git push <remote> <branch>` unhe bhejta hai aur remote ki branch aage barhata hai. Branch ki pehli push: `git push -u origin branch`; `-u` jorta hai, taa ke baad me sirf `git push` ya `git pull` kaafi ho.

</Ur>
</Tr>

```bash
cd shop
echo "# Shop" > README.md && git add . && git commit -qm "Initial commit"
git push -q -u origin main
git branch -vv | sed -E 's/ [0-9a-f]{7} / <hash> /'
git ls-remote --heads origin | awk '{print "server branch:", $2}'
```

```text output
* main <hash> [origin/main] Initial commit
server branch: refs/heads/main
```

<Happened>
<Tr>
<En>`git push -u origin main` uploaded `main` and linked it. `git branch -vv` shows each local branch with its tracking branch in brackets, `[origin/main]`. `git ls-remote --heads origin` asks the **server** directly which branches it has, without downloading anything.</En>
<Ur>`git push -u origin main` ne `main` upload kar ke jor di. `git branch -vv` har local branch ke saath brackets me us ki tracking branch dikhata hai, `[origin/main]`. `git ls-remote --heads origin` kuch download kiye baghair seedha **server** se poochta hai us ke paas kaunsi branches hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Remote-tracking branches: origin/main">

<Tr>
<En>

`origin/main` is a **read-only bookmark** in your local repo showing where `main` was on the server **the last time you talked to it**. Git works offline, so it remembers the last known state; every fetch, pull and push updates it. You never commit to `origin/main`: you compare with it and merge or rebase from it. `git branch -r` lists these; `git branch -a` lists local and remote together.

</En>
<Ur>

`origin/main` aap ki local repo me **sirf parhne wala bookmark** hai jo dikhata hai server par `main` kahan thi **jab aakhri dafa aap ne baat ki**. Git offline chalta hai, isliye aakhri maloom haalat yaad rakhta hai; har fetch, pull aur push ise taaza karta hai. `origin/main` par kabhi commit nahi karte: us se muqabla karte hain aur us se merge ya rebase. `git branch -r` ye dikhata hai; `git branch -a` local aur remote dono.

</Ur>
</Tr>

```bash
cd shop
git switch -q -c feature/cart
git commit -q --allow-empty -m "Cart work"
git push -q -u origin feature/cart
git switch -q main
echo "--- all branches (local + remote-tracking):"
git branch -a
```

```text output
--- all branches (local + remote-tracking):
  feature/cart
* main
  remotes/origin/feature/cart
  remotes/origin/main
```

<Happened>
<Tr>
<En>`feature/cart` and `main` are **your** branches; you can commit to them. `remotes/origin/…` are Git's **memory of the server**.</En>
<Ur>`feature/cart` aur `main` **aap ki** branches hain; in par commit kar sakte hain. `remotes/origin/…` Git ki **server ki yaad** hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fetch: look before you merge">

<Tr>
<En>

`git fetch` downloads new commits and branches and updates `origin/*`. It does **not** touch your own branches or files, so it's completely safe: see what teammates did, then decide how and when to bring it in. `git fetch --all` does every remote; `git fetch --prune` also removes `origin/*` branches deleted on the server.

</En>
<Ur>

`git fetch` naye commits aur branches download kar ke `origin/*` taaza karta hai. Ye aap ki apni branches ya files ko **nahi** chhoota, isliye bilkul mehfooz hai: dekhein saathiyon ne kya kiya, phir tay karein kab aur kaise andar lana hai. `git fetch --all` har remote ke liye; `git fetch --prune` server par mit chuki `origin/*` branches bhi hatata hai.

</Ur>
</Tr>

```bash
# a teammate clones and pushes a commit
git clone -q github-shop.git teammate && cd teammate
echo "MIT" > LICENSE && git add . && git commit -qm "Add license" && git push -q
cd ../shop
git status -sb | head -1
git fetch -q
git status -sb | head -1
echo "new on server: $(git log --format=%s main..origin/main)"
ls
```

```text output
## main...origin/main
## main...origin/main [behind 1]
new on server: Add license
README.md
```

<Happened>
<Tr>
<En>Before the fetch, `git status` didn't know about the teammate's commit, because it hadn't asked the server. After `git fetch` it says `[behind 1]`. But `ls` still shows only `README.md`: fetch **never** changes your files. `LICENSE` arrives only after a merge or pull.</En>
<Ur>Fetch se pehle `git status` saathi ke commit se be-khabar tha, kyun ke us ne server se poochha hi nahi. `git fetch` ke baad wo `[behind 1]` kehta hai. Lekin `ls` ab bhi sirf `README.md` dikhata hai: fetch aap ki files **kabhi nahi** badalta. `LICENSE` merge ya pull ke baad hi aati hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Pull: fetch + integrate">

<Tr>
<En>

`git pull` = `git fetch` + integrate `origin/<your-branch>` into your current branch, by **merge** (default) or **rebase**. Use it every morning on `main`. Set a default once with `git config --global pull.rebase true` (or `false`). `git pull --ff-only` refuses unless it's a simple fast-forward, a safe habit on `main`.

</En>
<Ur>

`git pull` = `git fetch` + `origin/<aap-ki-branch>` ko mojooda branch me **merge** (default) ya **rebase**. Har subah `main` par istemal karein. Ek dafa default set karein `git config --global pull.rebase true` (ya `false`). `git pull --ff-only` tab tak inkaar karta hai jab tak seedha fast-forward na ho, `main` par mehfooz aadat.

</Ur>
</Tr>

```bash
cd shop
git pull -q --ff-only
git status -sb | head -1
ls
```

```text output
## main...origin/main
LICENSE
README.md
```

```text
fetch:  server ──► origin/main          (your files unchanged)
merge:  origin/main ──► main + files   (now you have the commits)
pull = fetch + merge (or rebase)
```

<Happened>
<Tr>
<En>Now `LICENSE` is in the folder and we're no longer behind: the teammate's commit was fetched **and** merged.</En>
<Ur>Ab `LICENSE` folder me hai aur hum peeche nahi: saathi ka commit fetch **aur** merge dono ho gaya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Rejected push: someone pushed first">

<Tr>
<En>

If the server's branch has commits you don't have, `git push` is **rejected** with "fetch first" or "non-fast-forward". Accepting it would overwrite your teammate's work, so Git refuses. The fix: `git pull` (or `git pull --rebase`), resolve any conflicts, run the tests, push again. **Don't** reach for `--force`.

</En>
<Ur>

Agar server ki branch par aise commits hon jo aap ke paas nahi, `git push` "fetch first" ya "non-fast-forward" ke saath **radd** hota hai. Qubool karna saathi ka kaam mita deta, isliye Git inkaar karta hai. Hal: `git pull` (ya `git pull --rebase`), conflicts hal karein, tests chalayen, dobara push. `--force` ki taraf **haath na barhayen**.

</Ur>
</Tr>

```bash
cd teammate && git pull -q
echo "v1" > VERSION && git add . && git commit -qm "Add version" && git push -q
cd ../shop
echo "docs" > DOCS.md && git add . && git commit -qm "Add docs"
git push 2>&1 | grep -o 'rejected.*(fetch first)'
git pull -q --rebase
git push -q && echo "push succeeded after pull --rebase"
git log --format=%s | head -3
```

```text output
rejected]        main -> main (fetch first)
push succeeded after pull --rebase
Add docs
Add version
Add license
```

<Happened>
<Tr>
<En>The teammate pushed "Add version" first, so our push was rejected `(fetch first)`. `git pull --rebase` downloaded it and replayed our "Add docs" on top, keeping a straight line. Now our branch contains everything the server has, so the push is a fast-forward and succeeds.</En>
<Ur>Saathi ne "Add version" pehle push kiya, isliye hamari push `(fetch first)` ke saath radd hui. `git pull --rebase` ne use download kiya aur hamara "Add docs" upar dobara lagaya, seedhi line rakh kar. Ab hamari branch me server ka sab kuch hai, isliye push fast-forward hai aur kaamyab.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Ahead and behind">

<Tr>
<En>

**Ahead N** = you have N commits the remote doesn't (push needed). **Behind N** = the remote has N commits you don't (pull needed). Both at once ("ahead 1, behind 2") means you've **diverged**: pull with merge or rebase, then push. See it in `git status -sb`, `git branch -vv`, your editor's status bar, or with `git rev-list --left-right --count`.

</En>
<Ur>

**Ahead N** = aap ke paas N commits jo remote par nahi (push chahiye). **Behind N** = remote par N commits jo aap ke paas nahi (pull chahiye). Dono ek saath ("ahead 1, behind 2") ka matlab aap **alag ho gaye**: merge ya rebase se pull, phir push. Ye `git status -sb`, `git branch -vv`, editor ke status bar, ya `git rev-list --left-right --count` me dekhein.

</Ur>
</Tr>

```bash
cd shop
git commit -q --allow-empty -m "Local only"
cd ../teammate && git pull -q && git commit -q --allow-empty -m "Server only" && git push -q && cd ../shop
git fetch -q
git status -sb | head -1
git rev-list --left-right --count main...origin/main | awk '{print "ahead:", $1, " behind:", $2}'
```

```text output
## main...origin/main [ahead 1, behind 1]
ahead: 1  behind: 1
```

<Happened>
<Tr>
<En>We made "Local only" while the teammate pushed "Server only". After a fetch, Git reports both numbers: one commit to push, one to pull.</En>
<Ur>Hum ne "Local only" banaya jab ke saathi ne "Server only" push kiya. Fetch ke baad Git dono number batata hai: ek commit push karna hai, ek pull.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Authentication: HTTPS vs SSH">

<Tr>
<En>

GitHub needs to know who's pushing, and it no longer accepts your account password for Git. **HTTPS** URLs use a **personal access token** (or the Git Credential Manager / `gh auth login` flow). **SSH** URLs use a **key pair** on your computer. Set it up once per computer. SSH setup: `ssh-keygen -t ed25519 -C "you@example.com"`, add the **public** key (`~/.ssh/id_ed25519.pub`) in GitHub → Settings → SSH and GPG keys, then test with `ssh -T git@github.com`.

</En>
<Ur>

GitHub ko jaanna hai kaun push kar raha hai, aur ab Git ke liye account password nahi maanta. **HTTPS** URLs **personal access token** (ya Git Credential Manager / `gh auth login`) istemal karte hain. **SSH** URLs aap ke computer par **key pair**. Har computer par ek dafa set karein. SSH setup: `ssh-keygen -t ed25519 -C "you@example.com"`, **public** key (`~/.ssh/id_ed25519.pub`) GitHub → Settings → SSH and GPG keys me daalein, phir `ssh -T git@github.com` se test karein.

</Ur>
</Tr>

```bash
cd shop
git remote set-url origin git@github.com:acme/shop.git
git config --get remote.origin.url
git remote set-url origin https://github.com/acme/shop.git
git config --get remote.origin.url
git remote set-url origin ../github-shop.git    # back to our local "server"
```

```text output
git@github.com:acme/shop.git
https://github.com/acme/shop.git
```

<Happened>
<Tr>
<En>

`git remote set-url` switched the same remote between SSH and HTTPS forms; the last line points it back to our local "server".

| | HTTPS + token | SSH key |
| --- | --- | --- |
| Setup | Log in once with `gh auth login` or Git Credential Manager | Generate a key, add the public key to GitHub |
| Strict firewalls | Works (port 443) | Sometimes blocked (port 22; GitHub also offers ssh.github.com on 443) |
| Secret on your machine | Token (kept by the credential manager) | Private key (protect it with a passphrase) |

</En>
<Ur>

`git remote set-url` ne ek hi remote ko SSH aur HTTPS shaklon me badla; aakhri line use wapas hamare local "server" par le gayi.

| | HTTPS + token | SSH key |
| --- | --- | --- |
| Setup | `gh auth login` ya Git Credential Manager se ek dafa login | Key banao, public key GitHub me daalo |
| Sakht firewalls | Chalta hai (port 443) | Kabhi block (port 22; GitHub 443 par ssh.github.com bhi deta hai) |
| Machine par raaz | Token (credential manager rakhta hai) | Private key (passphrase se mehfooz karein) |

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Forks: your own copy of someone else's project">

<Tr>
<En>

You can't push to repos you don't own (like `facebook/react`). Instead you click **Fork**, which makes a copy under **your** account and remembers where it came from. Clone **your fork** (it becomes `origin`), then add the original as `upstream`. The rule: **pull from `upstream`, push to `origin`**, and open the PR from `yourname:branch` to `upstream:main`.

</En>
<Ur>

Jo repos aap ki nahi (jaise `facebook/react`) un par push nahi kar sakte. <Step title="Keep your fork in sync">

<Tr>
<En>

</En>
<Ur>

## Common mistakes

<Compare>
<Bad title="Rejected push? Force it">

```text
git push               # rejected (fetch first)
git push --force       # teammate's commits on the server are gone
```

</Bad>
<Good title="Pull, fix, test, push">

```text
git push               # rejected (fetch first)
git pull --rebase      # bring their commits in, replay mine on top
npm test
git push
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Working on the fork's `main`** instead of a branch, which makes syncing messy.
- **Forgetting to sync** and opening a PR based on months-old code.
- **Pushing to `upstream` by mistake** (on a repo where you have access). Check `git remote -v`.
- **Thinking `fetch` updated your files.** It only updates `origin/*`.
- **Huge PRs** nobody can review properly, and **empty PR descriptions**.
- **Putting a token inside the remote URL** (`https://user:token@github.com/...`): it's then stored in plain text in `.git/config`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Fork ki `main` par kaam** branch ke bajaye, jis se sync uljhan bhara ho jata hai.
- **Sync bhoolna** aur mahinon purane code par PR kholna.
- **Ghalti se `upstream` par push** (jis repo tak rasai ho). `git remote -v` dekhein.
- **Samajhna ke `fetch` ne files badal din.** Ye sirf `origin/*` taaza karta hai.
- **Bohot bare PRs** jinhe koi theek review na kar sake, aur **khaali PR descriptions**.
- **Remote URL me token daalna** (`https://user:token@github.com/...`): phir wo `.git/config` me saada text me save hota hai.

</Ur>
</Tr>

<DeepDive title="Real world: a first open-source contribution">

Alex wants to fix a broken link in the documentation of an open-source library he uses. He clicks **Fork**, clones `github.com/alex/library` and adds `upstream`. He creates `docs/fix-install-link`, fixes the link, commits "Fix broken install link in README", pushes to his fork, and opens a PR to `library:main` with "Closes #1203". The CI bot runs the docs build. A maintainer comments: "please also fix the same link in CONTRIBUTING.md". Alex commits once more and pushes, and the PR updates by itself. The maintainer approves and uses "Squash and merge". Alex deletes his branch, presses **Sync fork**, and the project now lists him as a contributor: a real line on a CV.

</DeepDive>

<DeepDive title="Security lens">

A pull request is code from someone you may not know, asking to run in your project. Treat it like untrusted input.

- **Branch protection / rulesets on `main`:** require PRs, at least one approval, passing status checks, and no force pushes.
- **CODEOWNERS:** sensitive paths (auth, payments, `.github/workflows/`, Terraform) automatically need review from the right people.
- **PRs from forks and CI:** by default GitHub doesn't give secrets to workflows triggered by PRs from forks. Be careful with `pull_request_target`, which **does** run with secrets: never use it to check out and run the PR's code (see **GitHub Actions Basics**).
- **Review the actual diff, not the description.** Malicious changes hide in big PRs, lock files, minified files and CI configs.
- **Typosquatted remotes:** check the URL before cloning or adding a remote (`github.com/faceb00k/react` is not React).
- **Tokens:** use fine-grained, short-lived tokens with minimum scope, or passphrase-protected SSH keys. Revoke them when a laptop is lost.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between origin and upstream?">
Both are just remote names. origin is the default name of the remote you cloned from; in a fork workflow it is your fork. upstream is the conventional name for the original repository you forked, which you fetch from to stay in sync and target with pull requests.
</QA>

<QA q="What is a remote-tracking branch such as origin/main?">
It is a read-only local reference that records where a branch on the remote was the last time you fetched, pulled or pushed. It lets you compare your work with the remote and merge or rebase from it, but you do not commit to it directly. git fetch updates it without changing your local branches.
</QA>

<QA q="Your push was rejected as non-fast-forward. What do you do?">
It means the remote has commits I do not have. I run git pull or git pull --rebase to integrate them, resolve any conflicts, run the tests, and push again. I would not force push, because that would overwrite other people's commits.
</QA>

<QA q="Describe the fork and pull request workflow.">
Fork the repository on GitHub, clone the fork so it becomes origin, add the original as upstream, keep main synced from upstream, create a feature branch, commit, push the branch to origin, and open a pull request from the fork's branch to upstream's main. Then address review feedback by pushing more commits until the maintainers merge it.
</QA>

<QA q="Why are pull requests from forks a security concern for CI?">
The code comes from an untrusted contributor and may try to steal secrets or abuse the CI runner. GitHub therefore does not expose repository secrets to normal pull_request workflows from forks and may require approval to run them. Workflows using pull_request_target run with secrets in the base repository's context, so they must never check out and execute the untrusted PR code.
</QA>

</DeepDive>
