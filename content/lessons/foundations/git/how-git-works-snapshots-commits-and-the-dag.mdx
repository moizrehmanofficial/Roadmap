<Callout type="tip" title="In one minute">
**Git** records the history of a project as a chain of **commits**. Each commit is a **snapshot** of all tracked files plus a message, an author, a time and a link to its **parent** commit(s). Every commit gets a unique ID — a **hash** like `3f2a1b9`. You work in the **working directory**, choose what to save with `git add` (the **staging area**), and save it with `git commit` (the **repository**, in `.git/`). A **branch** is just a movable label pointing at a commit; **HEAD** says which branch you are on. Commits form a graph (a **DAG**) — that is how Git can branch and merge.
</Callout>

## Start from zero

### Why version control?

Without it, projects end up like this: `final.zip`, `final-2.zip`, `final-REALLY-final.zip`, `final-moiz-fixed.zip`. Nobody knows what changed, who changed it, or how to go back.

<Callout type="analogy">
A **photo album of your project**. Every time you reach a meaningful point, you take a **photo** of the whole project (a commit) and write a caption under it ("add login page"). You can flip back to any photo, compare two photos, and give a copy of the album to teammates. A **branch** is a bookmark in the album that moves forward as you add photos; you can keep two bookmarks and add photos on different paths, then later combine them.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Repository (repo)** | A project folder whose history Git tracks | `devguide/` |
| **Commit** | A saved snapshot with a message | "fix login redirect" |
| **Hash / commit ID** | Unique fingerprint of a commit | `3f2a1b9` |
| **Working directory** | Your files as you see and edit them | |
| **Staging area (index)** | The list of changes you have chosen for the next commit | after `git add` |
| **Branch** | A named pointer to a commit | `main`, `feature/login` |
| **HEAD** | "Where I am now" — usually points to a branch | |
| **Remote** | Another copy of the repo, e.g. on GitHub | `origin` |

## What is it?

Git is a **distributed version control system**: every clone has the **full history**, so you can commit, branch and view history offline. GitHub, GitLab and Bitbucket are **hosting services** where teams share repositories — Git itself is the tool.

```text
 working directory  ──git add──►  staging area  ──git commit──►  repository (.git)
 (edit files)                     (choose changes)               (permanent history)
        ▲                                                               │
        └──────────────────── git checkout / restore ◄──────────────────┘
```

## Why does it matter?

- **Every software job uses Git** — and so do DevOps (infrastructure as code), data and security teams.
- **Safety:** every version is recoverable; mistakes can be undone.
- **Collaboration:** many people work in parallel on branches and merge.
- **Accountability and audit:** who changed what, when and why — essential for security and compliance.
- **Automation:** CI/CD pipelines start from Git events (push, pull request, tag).

## When and where do you use it?

- Every code project, from day one (`git init`).
- Configuration, Dockerfiles, Terraform, Kubernetes manifests, documentation.
- Even your own notes and scripts.

## Concepts one by one

### 1. Creating a repository

<Explain>
<What>
`git init` turns a folder into a repository by creating a hidden `.git` folder that stores the whole history.
</What>
<Why>
From that moment Git can track changes in the folder.
</Why>
<When>
Starting a new project (or `git clone` to copy an existing one).
</When>
<Where>
The project's top folder.
</Where>
<How>
Set your name and email once per computer — every commit records them.
</How>
</Explain>

```bash
git config --global user.name "Moiz Rehman"
git config --global user.email "moiz@example.com"
git config --global init.defaultBranch main
mkdir shop && cd shop
git init -q
ls -a
git status --short --branch
```

```text output
.
..
.git
## No commits yet on main
```

Deleting `.git` would delete the entire history — the files would remain, but Git would forget everything.

### 2. The three areas and `git status`

<Explain>
<What>
Files move between three places: the **working directory** (what you edit), the **staging area** (what will go into the next commit) and the **repository** (committed history).
</What>
<Why>
Staging lets you commit **some** changes and not others — clean, focused commits.
</Why>
<When>
Every commit.
</When>
<Where>
`git status` shows which files are untracked, modified, or staged.
</Where>
<How>
`git add file` stages; `git commit` saves the staged snapshot; `git status` tells you where everything is.
</How>
</Explain>

```bash
cd shop
echo "# Shop" > README.md
echo "console.log('hi')" > app.js
git status --short
git add README.md
git status --short
```

```text output
?? README.md
?? app.js
A  README.md
?? app.js
```

- `??` = untracked (Git sees it but does not track it yet).
- `A` = added to the staging area. `app.js` is still untracked because we did not add it.

### 3. Commits are snapshots

<Explain>
<What>
A commit stores a **snapshot of every tracked file** at that moment (efficiently — unchanged files are shared, not copied), plus author, date, message and the parent commit.
</What>
<Why>
Any commit can be restored completely, on its own.
</Why>
<When>
Each time you reach a small, meaningful step.
</When>
<Where>
`git log` lists them.
</Where>
<How>
`git commit -m "message"`. A good message says **why**, in the imperative: "Add login form validation".
</How>
</Explain>

```bash
cd shop
git commit -q -m "Add README"
git add app.js
git commit -q -m "Add app entry point"
echo "console.log('hello shop')" > app.js
git commit -q -am "Improve greeting"
git log --format='%s  (by %an)'
git rev-list --count HEAD | sed 's/$/ commits/'
```

```text output
Improve greeting  (by Moiz Rehman)
Add app entry point  (by Moiz Rehman)
Add README  (by Moiz Rehman)
3 commits
```

`-a` in `git commit -am` stages all **already tracked** files automatically (not new ones).

### 4. Hashes: every object has a fingerprint

<Explain>
<What>
Git names every stored object (file contents, folders, commits) by a **hash** of its content (SHA-1, 40 hex characters; SHA-256 in newer repos). We usually use the first 7 characters.
</What>
<Why>
Content-addressing makes history tamper-evident: change one byte anywhere and every later hash changes. Identical content is stored only once.
</Why>
<When>
Referring to commits (`git show 3f2a1b9`), checking integrity.
</When>
<Where>
`git log`, `git rev-parse`, `git hash-object`.
</Where>
<How>
A commit's hash depends on its snapshot, message, author, time **and its parent's hash** — that chain is what makes history trustworthy.
</How>
</Explain>

```bash
cd shop
echo "hello" | git hash-object --stdin
echo "hello" | git hash-object --stdin
echo "hello!" | git hash-object --stdin
git rev-parse HEAD | awk '{print "a full commit ID has", length($0), "hex characters"}'
```

```text output
ce013625030ba8dba906f756967f9e9ca394464a
ce013625030ba8dba906f756967f9e9ca394464a
4effa19f4f75f846c3229b9dbdbad14eff362f32
a full commit ID has 40 hex characters
```

The same content always gives the same hash (on any computer); one extra character gives a completely different one.

### 5. Inside a commit

<Explain>
<What>
A commit object points to a **tree** (the folder snapshot), its **parent** commit(s), and holds author, committer and message. Trees point to **blobs** (file contents) and other trees.
</What>
<Why>
Knowing the structure explains branching, merging and why Git is fast.
</Why>
<When>
Understanding and debugging history.
</When>
<Where>
`git cat-file -p <hash>` shows any object.
</Where>
<How>
Commit → tree → blobs; commit → parent → its tree…
</How>
</Explain>

```bash
cd shop
git cat-file -p HEAD | sed -E 's/[0-9a-f]{40}/<hash>/; s/> [0-9]+ [+-][0-9]{4}/> <date>/'
echo "--- the tree (folder snapshot) of that commit:"
git cat-file -p 'HEAD^{tree}' | awk '{print $2, $4}'
```

```text output
tree <hash>
parent <hash>
author Moiz Rehman <moiz@example.com> <date>
committer Moiz Rehman <moiz@example.com> <date>

Improve greeting
--- the tree (folder snapshot) of that commit:
blob README.md
blob app.js
```

```text
commit "Improve greeting" ──parent──► commit "Add app entry point" ──parent──► commit "Add README"
        │                                      │
        ▼ tree                                 ▼ tree
   README.md → blob ce01…                  README.md → same blob (shared, not copied)
   app.js    → blob 9a1c… (new)            app.js    → blob 4b2e…
```

### 6. Branches are just pointers

<Explain>
<What>
A branch is a tiny file containing one commit hash. When you commit on a branch, the pointer moves forward to the new commit.
</What>
<Why>
Creating a branch is instant and free — so you can make one for every feature, fix or experiment.
</Why>
<When>
For every piece of work that is not finished yet.
</When>
<Where>
`.git/refs/heads/<branch>`; `git branch`, `git switch -c name`.
</Where>
<How>
`git switch -c feature/login` creates a branch at the current commit and moves HEAD to it.
</How>
</Explain>

```bash
cd shop
git switch -q -c feature/login
echo "login()" > login.js && git add login.js && git commit -q -m "Add login"
echo "main points to:          $(git log -1 --format=%s main)"
echo "feature/login points to: $(git log -1 --format=%s feature/login)"
cat .git/HEAD
wc -c < .git/refs/heads/main | sed 's/$/ bytes: a branch file is just one hash + newline/'
```

```text output
main points to:          Improve greeting
feature/login points to: Add login
ref: refs/heads/feature/login
41 bytes: a branch file is just one hash + newline
```

### 7. HEAD: where am I?

<Explain>
<What>
`HEAD` is a pointer to your current position — normally a branch name (and through it, a commit).
</What>
<Why>
Commits are added where HEAD is; `git status` and many commands are relative to it.
</Why>
<When>
Always — every command uses it.
</When>
<Where>
`.git/HEAD`; shortcuts like `HEAD~1` (one commit before), `HEAD~2`.
</Where>
<How>
If HEAD points directly to a commit instead of a branch, you are in **detached HEAD** — new commits there belong to no branch (create one with `git switch -c` to keep them).
</How>
</Explain>

```bash
cd shop
git switch -q main
for ref in HEAD HEAD~1 HEAD~2; do printf '%-7s → %s\n' "$ref" "$(git log -1 --format=%s "$ref")"; done
```

```text output
HEAD    → Improve greeting
HEAD~1  → Add app entry point
HEAD~2  → Add README
```

### 8. The commit graph (DAG)

<Explain>
<What>
Commits point to their parents, forming a **Directed Acyclic Graph**: arrows go only backwards in time, never in loops. A merge commit has two parents.
</What>
<Why>
Branching, merging, rebasing and "what is in this release?" are all questions about this graph.
</Why>
<When>
Reading history, reviewing pull requests, debugging merges.
</When>
<Where>
`git log --oneline --graph --all`, GitHub's network graph, VS Code's Git Graph extension.
</Where>
<How>
Read from top (newest) to bottom (oldest); lines show which commit came from which.
</How>
</Explain>

```bash
cd shop
echo "price logic" > price.js && git add price.js && git commit -q -m "Add pricing"
git merge -q --no-edit feature/login
git log --graph --format='%s' --all
```

```text output
*   Merge branch 'feature/login'
|\  
| * Add login
* | Add pricing
|/  
* Improve greeting
* Add app entry point
* Add README
```

Two lines of work split after "Improve greeting" and joined again in a **merge commit** with two parents.

### 9. Ignoring files: `.gitignore`

<Explain>
<What>
A file listing patterns Git should not track.
</What>
<Why>
Dependencies (`node_modules`), build output, logs, OS junk and **secrets** (`.env`) do not belong in history.
</Why>
<When>
At the start of every project.
</When>
<Where>
`.gitignore` in the repo root (and subfolders if needed). Templates: github.com/github/gitignore.
</Where>
<How>
`.gitignore` only affects **untracked** files — a file already committed stays tracked until you `git rm --cached` it.
</How>
</Explain>

```bash
cd shop
printf 'node_modules/\n.env\n*.log\ndist/\n' > .gitignore
mkdir -p node_modules dist && touch node_modules/x .env debug.log dist/app.js notes.txt
git status --short --untracked-files=all
git check-ignore -v .env | awk '{print ".env ignored by rule:", $1}'
```

```text output
?? .gitignore
?? notes.txt
.env ignored by rule: .gitignore:2:.env
```

## Hands-on

```bash
mkdir lab && cd lab && git init -q
for step in "Create index" "Add header" "Add footer"; do
  echo "$step" >> page.html
  git add page.html
  git commit -q -m "$step"
done
echo "history (newest first):"; git log --format='  %s'
echo "file at the first commit: $(git show HEAD~2:page.html)"
echo "lines changed in the last commit: $(git diff --numstat HEAD~1 HEAD | awk '{print "+" $1, "-" $2}')"
git switch -q -c experiment && echo "risky change" >> page.html && git commit -qam "Experiment"
git switch -q main
echo "main still has $(wc -l < page.html) lines; experiment has $(git show experiment:page.html | wc -l)"
```

```text output
history (newest first):
  Add footer
  Add header
  Create index
file at the first commit: Create index
lines changed in the last commit: +1 -0
main still has 3 lines; experiment has 4
```

## Real-world example

A developer's laptop dies the day before a release. Because the team pushes every branch to GitHub, nothing is lost: on a new laptop, `git clone` brings back the **entire history**, every branch and every tag. Later, a customer reports a bug that started "sometime last month". With `git log --since="1 month ago" -- src/payments/` the team lists only commits touching payments, finds the guilty change in minutes, and sees from the commit message **why** it was made — and who to ask.

## Common mistakes

- **Huge "update" commits** mixing unrelated changes — impossible to review or revert cleanly.
- **Meaningless messages** ("fix", "changes", "asdf").
- **Committing `node_modules`, build output or `.env`** — bloats the repo and leaks secrets.
- **Working directly on `main`** for everything instead of short-lived branches.
- **Panicking in detached HEAD** — create a branch to keep your work: `git switch -c rescue`.
- **Deleting `.git` "to start fresh"** — and losing all history.

## Security lens

<Callout type="security">
Git never forgets. Anything committed — including a password removed in the next commit — stays in history and in every clone.
</Callout>

- **Secrets in history** are one of the most common real leaks; bots scan public GitHub repos within minutes. Use `.gitignore`, pre-commit secret scanners (gitleaks), and see **Keeping Secrets Out of Git**.
- **Hashes give integrity**: a changed historical commit changes all later hashes, so tampering is visible.
- **Author names are not proof** — anyone can set `user.name`; **signed commits** prove identity (see **Commit Signing and Protected Branches**).
- **History is evidence:** `git log -p` and `git blame` are investigation tools in incidents and audits.

## Interview questions

<QA q="What is the difference between Git and GitHub?">
Git is a distributed version control tool that runs locally and stores the full history of a repository in every clone. GitHub is a hosting service for Git repositories that adds collaboration features such as pull requests, code review, issues, permissions and CI with GitHub Actions.
</QA>

<QA q="What are the working directory, the staging area and the repository?">
The working directory contains the files you edit. The staging area, or index, records which changes will be included in the next commit, added with git add. The repository in the .git folder stores committed snapshots permanently. git commit turns the staged snapshot into a new commit.
</QA>

<QA q="What is a commit in Git?">
A commit is an object that records a snapshot of the tracked files through a tree object, together with the author, committer, timestamps, message and the hash of its parent commit or commits. It is identified by a hash of its content, so any change to it or its ancestors produces a different hash.
</QA>

<QA q="What is a branch, and what is HEAD?">
A branch is a lightweight movable pointer to a commit, stored as a file containing a commit hash; committing on the branch moves it forward. HEAD is a pointer to the current position, normally pointing to the checked-out branch; if it points directly to a commit, the repository is in detached HEAD state.
</QA>
