<BigIdea>
<Tr>
<En>
**Git** records a project's history as a chain of **commits**. Each commit is a **snapshot** of every tracked file, plus a message, an author and a link to the commit before it. You edit files, choose what to save with `git add`, and save it with `git commit`. A **branch** is just a movable label on a commit, and **HEAD** says where you are. That's the whole idea, and everything else in Git builds on it.
</En>
<Ur>
**Git** project ki tareekh ko **commits** ki zanjeer ki shakal me record karta hai. Har commit har track ki gayi file ka **snapshot** hai, saath me message, likhne wala aur pichhle commit ka link. Aap files badalte hain, `git add` se chunte hain kya save karna hai, aur `git commit` se save karte hain. **Branch** bas commit par laga ek hilne wala label hai, aur **HEAD** batata hai aap kahan hain. Bas yahi khayal hai, aur Git ki har cheez isi par bani hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Git is a **distributed version control system**: every clone has the **full history**, so you can commit, branch and view history offline. GitHub, GitLab and Bitbucket are **hosting services** where teams share repositories; Git itself is the tool.

```text
 working directory  ──git add──►  staging area  ──git commit──►  repository (.git)
 (edit files)                     (choose changes)               (permanent history)
        ▲                                                               │
        └──────────────────── git checkout / restore ◄──────────────────┘
```

</En>
<Ur>

Git ek **distributed version control system** hai: har clone ke paas **poori tareekh** hoti hai, isliye aap offline commit, branch aur tareekh dekh sakte hain. GitHub, GitLab aur Bitbucket **hosting services** hain jahan teams repositories share karti hain; Git khud tool hai.

```text
 working directory  ──git add──►  staging area  ──git commit──►  repository (.git)
 (edit files)                     (choose changes)               (permanent history)
        ▲                                                               │
        └──────────────────── git checkout / restore ◄──────────────────┘
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Without Git, projects end up as `final.zip`, `final-2.zip`, `final-REALLY-final.zip`. On Monday the site works; on Wednesday you change ten files; on Thursday something is broken. Which change broke it? With Git, `git diff` shows every changed line, and going back to Monday takes seconds.

- **Every software job uses Git**, and so do DevOps, data and security teams.
- **Safety:** every version is recoverable.
- **Teamwork:** many people work in parallel on branches and merge.
- **Audit:** who changed what, when and why.
- **Automation:** CI/CD pipelines start from Git events.

</En>
<Ur>

Git ke baghair projects `final.zip`, `final-2.zip`, `final-REALLY-final.zip` ban jate hain. Monday ko site chal rahi hai; Wednesday ko aap das files badalte hain; Thursday ko kuch toot jata hai. Kis tabdeeli ne tora? Git ke saath `git diff` har badli line dikhata hai, aur Monday par wapas jana seconds ka kaam hai.

- **Har software naukri me Git** hai, aur DevOps, data aur security teams me bhi.
- **Hifazat:** har version wapas laya ja sakta hai.
- **Teamwork:** bohot se log branches par saath kaam kar ke merge karte hain.
- **Hisaab:** kis ne kya, kab aur kyun badla.
- **Automation:** CI/CD pipelines Git ke waqiyat se shuru hoti hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Every project, from day one (`git init`). Even alone, Git is your undo button and backup. Also for configuration, Dockerfiles, Terraform, Kubernetes files, documentation, and your own notes and scripts.

</En>
<Ur>

Har project, pehle din se (`git init`). Akele kaam karte hue bhi Git aap ka undo button aur backup hai. Configuration, Dockerfiles, Terraform, Kubernetes files, documentation, aur apne notes aur scripts ke liye bhi.

</Ur>
</Tr>
</When>

```text
git commit -m "message"   # save a snapshot
git log --oneline         # see history
```

</En>
<Ur>

```text
git init                  # folder track karna shuru
git add <file>            # tabdeeliyan chuno

```

</Ur>
</Tr>

## Picture it

<Tr>
<En>

A **photo album of your project**. Every time you reach a meaningful point, you take a **photo** of the whole project (a commit) and write a caption under it ("add login page"). You can flip back to any photo, compare two photos, and give a copy of the album to teammates. A **branch** is a bookmark that moves forward as you add photos; you can keep two bookmarks on different paths and later combine them.

</En>
<Ur>

**Project ki photo album**. Jab bhi koi ahem marhala aaye, aap poore project ki **photo** lete hain (commit) aur neeche caption likhte hain ("login page joda"). Kisi bhi photo par wapas ja sakte hain, do photos milaa sakte hain, aur album ki copy team ko de sakte hain. **Branch** ek bookmark hai jo photos jorne par aage barhta hai; do bookmarks alag raaston par rakh kar baad me jor sakte hain.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Create a repository">

<Tr>
<En>

`git init` turns a folder into a repository by creating a hidden `.git` folder that stores all history. First, set your name and email once per computer: every commit records them. Use the same email as your GitHub account so GitHub links commits to your profile.

</En>
<Ur>

`git init` ek chhupa `.git` folder bana kar folder ko repository bana deta hai jo saari tareekh rakhta hai. Pehle har computer par ek dafa apna naam aur email set karein: har commit inhe record karta hai. GitHub account wali email istemal karein taa ke GitHub commits ko aap ki profile se jore.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"
git config --global user.email "alex@example.com"
git config --global init.defaultBranch main
mkdir shop && cd shop
git init -q
ls -a
git status --short --branch
```

```text output
.
..
.git
## No commits yet on main
```

<Happened>
<Tr>
<En>

- `--global` saves the setting for **every** repo on this computer.
- `init.defaultBranch main` makes new repos start on `main` (older Git used `master`).
- `git init -q` made the repo; `-q` only hides the "Initialized…" message.
- `ls -a` shows the only new thing: `.git`. That folder **is** the repository. Delete it and the files stay, but Git forgets all history.

</En>
<Ur>

- `--global` setting is computer ke **har** repo ke liye save karta hai.
- `init.defaultBranch main` naye repos ko `main` par shuru karta hai (purana Git `master` istemal karta tha).
- `git init -q` ne repo banaya; `-q` sirf "Initialized…" message chhupata hai.
- `ls -a` sirf nayi cheez dikhata hai: `.git`. Wo folder **hi** repository hai. Use mita dein to files rehti hain, lekin Git saari tareekh bhool jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The three areas and git status">

<Tr>
<En>

Files move between the **working directory** (what you edit), the **staging area** (what goes into the next commit) and the **repository** (history). Git notices new files but doesn't track them until you `git add` them. `git status` always tells you where everything is.

</En>
<Ur>

Files **working directory** (jo aap badalte hain), **staging area** (jo agle commit me jayega) aur **repository** (tareekh) ke darmiyan chalti hain. Git nayi files dekh leta hai lekin `git add` tak track nahi karta. `git status` hamesha batata hai kaunsi cheez kahan hai.

</Ur>
</Tr>

```bash
cd shop
echo "# Shop" > README.md
echo "console.log('hi')" > app.js
git status --short
git add README.md
git status --short
```

```text output
?? README.md
?? app.js
A  README.md
?? app.js
```

<Happened>
<Tr>
<En>

- `??` = untracked: Git sees it, but it's not part of history yet.
- After `git add README.md`, it shows `A` (added, staged). `app.js` stays `??` because we didn't add it.

Why stage at all? If you fixed a bug **and** started a feature in one afternoon, staging lets you commit the fix alone, then the feature. Each commit has one clear purpose, which makes review and undo much easier.

</En>
<Ur>

- `??` = untracked: Git dekhta hai, lekin abhi tareekh ka hissa nahi.
- `git add README.md` ke baad ye `A` (added, staged) dikhata hai. `app.js` `??` raha kyun ke hum ne use add nahi kiya.

Staging kyun? Agar aap ne ek dopahar me bug theek kiya **aur** feature shuru kiya, to staging se pehle sirf fix commit kar sakte hain, phir feature. Har commit ka ek saaf maqsad hota hai, jis se review aur undo bohot aasaan ho jate hain.

</Ur>
</Tr>
</Happened>

```text
 working directory        staging area            repository
 README.md (new)   ──add──► README.md      ──commit──► (next commit)
 app.js    (new)            (not staged)
```

</Step>

<Step title="Commits are snapshots">

<Tr>
<En>

A commit stores a **snapshot of every tracked file** (smartly: unchanged files are shared, not copied), plus author, date, message and parent. A good message completes the sentence "If applied, this commit will…": "Add README", "Fix rounding in cart total". Bad: "update", "changes", "asdf".

</En>
<Ur>

Commit **har track ki file ka snapshot** rakhta hai (aqalmandi se: na badli files share hoti hain, copy nahi), aur likhne wala, tareekh, message aur parent. Achha message is jumle ko poora karta hai "Agar laga, to ye commit…": "Add README", "Fix rounding in cart total". Bura: "update", "changes", "asdf".

</Ur>
</Tr>

```bash
cd shop
git commit -q -m "Add README"
git add app.js
git commit -q -m "Add app entry point"
echo "console.log('hello shop')" > app.js
git commit -q -am "Improve greeting"
git log --format='%s  (by %an)'
git rev-list --count HEAD | sed 's/$/ commits/'
```

```text output
Improve greeting  (by Alex Carter)
Add app entry point  (by Alex Carter)
Add README  (by Alex Carter)
3 commits
```

<Happened>
<Tr>
<En>

- The first commit saved only what was staged (`README.md`); `-m` gives the message without opening an editor.
- `-a` in `git commit -am` stages all **already tracked** files that changed. It never picks up brand-new files; those always need `git add`.
- `git log` lists newest first: `%s` = subject, `%an` = author name.

</En>
<Ur>

- Pehle commit ne sirf staged cheez (`README.md`) save ki; `-m` editor khole baghair message deta hai.
- `git commit -am` me `-a` saari **pehle se track** aur badli files stage karta hai. Bilkul nayi files kabhi nahi uthata; unhe hamesha `git add` chahiye.
- `git log` naye pehle dikhata hai: `%s` = subject, `%an` = likhne wale ka naam.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Hashes: every object has a fingerprint">

<Tr>
<En>

Git names everything it stores (file contents, folders, commits) by a **hash** of its content: 40 hex characters, usually shortened to 7. The same content always gives the same hash on any computer; one changed byte gives a completely different one. Identical content is stored once, and history becomes tamper-evident.

</En>
<Ur>

Git jo kuch rakhta hai (file ka mawad, folders, commits) us ka naam us ke mawad ke **hash** se rakhta hai: 40 hex huroof, aam tor par 7 tak chhote. Ek jaisa mawad har computer par hamesha ek hi hash deta hai; ek byte badle to bilkul alag. Ek jaisa mawad ek dafa rakha jata hai, aur tareekh me cherh chhaar pakri jati hai.

</Ur>
</Tr>

```bash
cd shop
echo "hello" | git hash-object --stdin
echo "hello" | git hash-object --stdin
echo "hello!" | git hash-object --stdin
git rev-parse HEAD | awk '{print "a full commit ID has", length($0), "hex characters"}'
```

```text output
ce013625030ba8dba906f756967f9e9ca394464a
ce013625030ba8dba906f756967f9e9ca394464a
4effa19f4f75f846c3229b9dbdbad14eff362f32
a full commit ID has 40 hex characters
```

<Happened>
<Tr>
<En>`hello` gave the same hash twice (you'll get this exact value too). `hello!` gave a totally different one. A commit's hash also includes its **parent's** hash, so nobody can quietly change an old commit: its hash, and every later one, would change.</En>
<Ur>`hello` ne do dafa ek hi hash diya (aap ko bhi bilkul yahi milega). `hello!` ne bilkul alag diya. Commit ke hash me us ke **parent** ka hash bhi shamil hai, isliye koi purana commit chupke se nahi badal sakta: us ka, aur baad ke har commit ka, hash badal jayega.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Inside a commit">

<Tr>
<En>

A commit object points to a **tree** (the folder snapshot) and its **parent**, and holds author, committer and message. Trees point to **blobs** (file contents). `git cat-file -p` shows any object.

</En>
<Ur>

Commit object ek **tree** (folder ka snapshot) aur apne **parent** ki taraf ishara karta hai, aur likhne wala, committer aur message rakhta hai. Trees **blobs** (file ka mawad) ki taraf ishara karte hain. `git cat-file -p` koi bhi object dikhata hai.

</Ur>
</Tr>

```bash
cd shop
git cat-file -p HEAD | sed -E 's/[0-9a-f]{40}/<hash>/; s/> [0-9]+ [+-][0-9]{4}/> <date>/'
echo "--- the tree (folder snapshot) of that commit:"
git cat-file -p 'HEAD^{tree}' | awk '{print $2, $4}'
```

```text output
tree <hash>
parent <hash>
author Alex Carter <alex@example.com> <date>
committer Alex Carter <alex@example.com> <date>

Improve greeting
--- the tree (folder snapshot) of that commit:
blob README.md
blob app.js
```

<Happened>
<Tr>
<En>

- `sed` only masks the real hash and time, which differ on every computer.
- The first commit of a repo has no `parent` line.
- `author` wrote the change; `committer` made the commit (they differ after a rebase or when applying someone else's patch).
- `HEAD^{tree}` = "the tree of the HEAD commit": one `blob` per file.

</En>
<Ur>

- `sed` sirf asli hash aur waqt chhupata hai, jo har computer par alag hain.
- Repo ke pehle commit me `parent` line nahi hoti.
- `author` ne tabdeeli likhi; `committer` ne commit banaya (rebase ke baad ya kisi aur ka patch lagane par ye alag hote hain).
- `HEAD^{tree}` = "HEAD commit ka tree": har file ka ek `blob`.

</Ur>
</Tr>
</Happened>

```text
commit "Improve greeting" ──parent──► commit "Add app entry point" ──parent──► commit "Add README"
        │                                      │
        ▼ tree                                 ▼ tree
   README.md → blob ce01…                  README.md → same blob (shared, not copied)
   app.js    → blob 9a1c… (new)            app.js    → blob 4b2e…
```

<Tr>
<En>That's why Git is fast and small: if a file didn't change between two commits, both trees point to the **same** blob.</En>
<Ur>Isi liye Git tez aur chhota hai: agar do commits ke darmiyan file na badli, to dono trees **ek hi** blob ki taraf ishara karte hain.</Ur>
</Tr>

</Step>

<Step title="Branches are just pointers">

<Tr>
<En>

A branch is a tiny file holding one commit hash. When you commit on it, the pointer moves forward. So creating a branch is **instant and free**, even in a huge project: make one for every feature, fix or experiment. `git switch -c name` creates it and moves you there.

</En>
<Ur>

Branch ek chhoti file hai jis me ek commit hash hota hai. Us par commit karein to pointer aage barhta hai. Isliye branch banana **foran aur muft** hai, bare project me bhi: har feature, fix ya tajurbe ke liye ek banayen. `git switch -c name` ise bana kar aap ko wahan le jata hai.

</Ur>
</Tr>

```bash
cd shop
git switch -q -c feature/login
echo "login()" > login.js && git add login.js && git commit -q -m "Add login"
echo "main points to:          $(git log -1 --format=%s main)"
echo "feature/login points to: $(git log -1 --format=%s feature/login)"
cat .git/HEAD
wc -c < .git/refs/heads/main | sed 's/$/ bytes: a branch file is just one hash + newline/'
```

```text output
main points to:          Improve greeting
feature/login points to: Add login
ref: refs/heads/feature/login
41 bytes: a branch file is just one hash + newline
```

<Happened>
<Tr>
<En>The commit went onto `feature/login`; `main` didn't move. `.git/HEAD` shows we're on `feature/login`, and a branch file is 41 bytes: a 40-character hash plus a newline.</En>
<Ur>Commit `feature/login` par gaya; `main` nahi hila. `.git/HEAD` dikhata hai hum `feature/login` par hain, aur branch file 41 bytes ki hai: 40 huroof ka hash aur ek nayi line.</Ur>
</Tr>
</Happened>

</Step>

<Step title="HEAD: where am I?">

<Tr>
<En>

`HEAD` points to your current position, normally a branch. New commits are added where HEAD is. Shortcuts: `HEAD~1` = one commit before, `HEAD~2` = two before. If HEAD points straight at a commit instead of a branch, you're in **detached HEAD**: new commits there belong to no branch, so keep them with `git switch -c rescue`.

</En>
<Ur>

`HEAD` aap ki mojooda jagah ki taraf ishara karta hai, aam tor par branch. Naye commits wahin jurte hain jahan HEAD hai. Shortcuts: `HEAD~1` = ek commit pehle, `HEAD~2` = do pehle. Agar HEAD branch ke bajaye seedha commit ki taraf ho, to aap **detached HEAD** me hain: wahan ke naye commits kisi branch ke nahi, isliye unhe `git switch -c rescue` se bachayen.

</Ur>
</Tr>

```bash
cd shop
git switch -q main
for ref in HEAD HEAD~1 HEAD~2; do printf '%-7s → %s\n' "$ref" "$(git log -1 --format=%s "$ref")"; done
```

```text output
HEAD    → Improve greeting
HEAD~1  → Add app entry point
HEAD~2  → Add README
```

<Happened>
<Tr>
<En>Switching to `main` changed the files to match it (`login.js` left the folder, but it's safe on `feature/login`). You'll use `HEAD~1` a lot: `git diff HEAD~1` (what changed in the last commit), `git show HEAD~2`.</En>
<Ur>`main` par jane se files us ke mutabiq badal gayin (`login.js` folder se chali gayi, lekin `feature/login` par mehfooz hai). Aap `HEAD~1` bohot istemal karenge: `git diff HEAD~1` (aakhri commit me kya badla), `git show HEAD~2`.</Ur>
</Tr>
</Happened>

</Step>

<Step title="The commit graph (DAG)">

<Tr>
<En>

Commits point to their parents, forming a **Directed Acyclic Graph**: arrows go only backwards in time, never in loops. A merge commit has **two** parents. Branching, merging, rebasing and "what's in this release?" are all questions about this graph. View it with `git log --oneline --graph --all`, or VS Code's Git Graph extension.

</En>
<Ur>

Commits apne parents ki taraf ishara karte hain, jis se **Directed Acyclic Graph** banta hai: teer sirf waqt me peeche jate hain, kabhi chakkar me nahi. Merge commit ke **do** parents hote hain. Branching, merging, rebasing aur "is release me kya hai?" sab is graph ke sawal hain. Ise `git log --oneline --graph --all` ya VS Code ke Git Graph extension se dekhein.

</Ur>
</Tr>

```bash
cd shop
echo "price logic" > price.js && git add price.js && git commit -q -m "Add pricing"
git merge -q --no-edit feature/login
git log --graph --format='%s' --all
```

```text output
*   Merge branch 'feature/login'
|\  
| * Add login
* | Add pricing
|/  
* Improve greeting
* Add app entry point
* Add README
```

<Happened>
<Tr>
<En>`main` and `feature/login` had **both** moved on since "Improve greeting", so the merge made a commit with two parents. `*` is a commit; `|`, `\` and `/` show lines of history splitting and joining. "Acyclic" means no commit can be its own ancestor.</En>
<Ur>"Improve greeting" ke baad `main` aur `feature/login` **dono** aage barh gaye the, isliye merge ne do parents wala commit banaya. `*` commit hai; `|`, `\` aur `/` tareekh ki lines ka bantna aur milna dikhate hain. "Acyclic" ka matlab koi commit apna hi aabaa-o-ajdaad nahi ho sakta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Ignoring files: .gitignore">

<Tr>
<En>

Dependencies (`node_modules`), build output, logs, OS junk and **secrets** (`.env`) don't belong in history. List their patterns in `.gitignore` at the repo root, and commit that file so the whole team shares the rules. It only affects **untracked** files: a file already committed stays tracked until you `git rm --cached` it. Templates: github.com/github/gitignore.

</En>
<Ur>

Dependencies (`node_modules`), build output, logs, OS ka kachra aur **raaz** (`.env`) tareekh me nahi hone chahiye. In ke patterns repo ki jar me `.gitignore` me likhein, aur ye file commit karein taa ke poori team ke rules ek hon. Ye sirf **untracked** files par asar karti hai: pehle se commit hui file `git rm --cached` tak track rehti hai. Templates: github.com/github/gitignore.

</Ur>
</Tr>

```bash
cd shop
printf 'node_modules/\n.env\n*.log\ndist/\n' > .gitignore
mkdir -p node_modules dist && touch node_modules/x .env debug.log dist/app.js notes.txt
git status --short --untracked-files=all
git check-ignore -v .env | awk '{print ".env ignored by rule:", $1}'
```

```text output
?? .gitignore
?? notes.txt
.env ignored by rule: .gitignore:2:.env
```

<Happened>
<Tr>
<En>Only `.gitignore` and `notes.txt` showed up; everything else matched a rule. `git check-ignore -v` explains **which rule** ignores a file (line 2 here), which is very handy when you can't tell why a file is or isn't ignored.</En>
<Ur>Sirf `.gitignore` aur `notes.txt` nazar aaye; baqi sab kisi rule se mil gaye. `git check-ignore -v` batata hai **kaunsa rule** file ko ignore karta hai (yahan line 2), jo tab bohot kaam aata hai jab samajh na aaye ke file kyun ignore ho rahi hai ya nahi.</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="One giant 'update' commit">

```text
git add .
git commit -m "update"        # bug fix + new feature + formatting, all mixed
```

</Bad>
<Good title="Small, focused commits">

```text
git add src/cart.js
git commit -m "Fix rounding in cart total"
git add src/login/
git commit -m "Add login form validation"
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Deleting `.git` "to start fresh"**, and losing all history.

<DeepDive title="Real world: the laptop that died before a release">

A developer's laptop dies the day before a release. Because the team pushes every branch to GitHub, nothing is lost: on a new laptop, `git clone` brings back the **entire history**, every branch and every tag. Later, a customer reports a bug that started "sometime last month". With `git log --since="1 month ago" -- src/payments/` the team lists only commits touching payments, finds the guilty change in minutes, and sees from the commit message **why** it was made, and who to ask.

</DeepDive>

<DeepDive title="Security lens">

Git never forgets. Anything committed, including a password removed in the next commit, stays in history and in every clone.

- **Secrets in history** are one of the most common real leaks; bots scan public GitHub repos within minutes. Use `.gitignore`, pre-commit secret scanners (gitleaks), and see **Keeping Secrets Out of Git**.
- **Hashes give integrity:** changing a historical commit changes every later hash, so tampering is visible.
- **Author names aren't proof:** anyone can set `user.name`; **signed commits** prove identity (see **Commit Signing and Protected Branches**).
- **History is evidence:** `git log -p` and `git blame` are investigation tools in incidents and audits.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between Git and GitHub?">
Git is a distributed version control tool that runs locally and stores the full history of a repository in every clone. GitHub is a hosting service for Git repositories that adds collaboration features such as pull requests, code review, issues, permissions and CI with GitHub Actions.
</QA>

<QA q="What are the working directory, the staging area and the repository?">
The working directory contains the files you edit. The staging area, or index, records which changes will be included in the next commit, added with git add. The repository in the .git folder stores committed snapshots permanently. git commit turns the staged snapshot into a new commit.
</QA>

<QA q="What is a commit in Git?">
A commit is an object that records a snapshot of the tracked files through a tree object, together with the author, committer, timestamps, message and the hash of its parent commit or commits. It is identified by a hash of its content, so any change to it or its ancestors produces a different hash.
</QA>

<QA q="What is a branch, and what is HEAD?">
A branch is a lightweight movable pointer to a commit, stored as a file containing a commit hash; committing on the branch moves it forward. HEAD is a pointer to the current position, normally pointing to the checked-out branch; if it points directly to a commit, the repository is in detached HEAD state.
</QA>

</DeepDive>
