<BigIdea>
<Tr>
<En>
Pick the undo tool by **where the mistake is**. Edits not committed yet → **`git restore file`**. Staged by mistake → **`git restore --staged file`**. Last commit wrong and **not pushed** → **`git commit --amend`** or **`git reset`** (`--soft` keeps changes staged, `--mixed` keeps them unstaged, `--hard` throws them away). Commit **already pushed** → **`git revert`**, which adds a new commit that undoes the old one without rewriting history. Something "lost" → **`git reflog`**, because Git remembers where HEAD has been for about 90 days.
</En>
<Ur>
Undo ka tool **ghalti ki jagah** dekh kar chunein. Abhi commit nahi hui tabdeeliyan → **`git restore file`**. Ghalti se stage hui → **`git restore --staged file`**. Aakhri commit ghalat aur **push nahi hua** → **`git commit --amend`** ya **`git reset`** (`--soft` tabdeeliyan staged rakhta hai, `--mixed` unstaged, `--hard` phenk deta hai). Commit **push ho chuka** → **`git revert`**, jo naya commit jor kar purane ko ulat deta hai, tareekh dobara likhe baghair. Kuch "kho gaya" → **`git reflog`**, kyun ke Git takreeban 90 din tak yaad rakhta hai HEAD kahan kahan raha.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Git has different undo tools because a mistake can live in different places:

```text
  working directory  ──add──►  staging area  ──commit──►  local commits  ──push──►  remote (shared)
        │                          │                          │                         │
  git restore file      git restore --staged file    git reset / --amend         git revert
  git clean (untracked)                              (rewrites history)        (new commit, safe)
```

The further right the mistake is, the more careful you must be. Once commits are shared, you **don't** rewrite them; you add a new commit that fixes things.

</En>
<Ur>

Git ke paas alag undo tools hain kyun ke ghalti alag jagahon par ho sakti hai:

```text
  working directory  ──add──►  staging area  ──commit──►  local commits  ──push──►  remote (shared)
        │                          │                          │                         │
  git restore file      git restore --staged file    git reset / --amend         git revert
  git clean (untracked)                              (rewrites history)        (new commit, safe)
```

Ghalti jitni daayen ho, utna zyada ehtiyaat chahiye. Commits share ho jayen to unhe dobara **nahi** likhte; ek naya commit jorte hain jo theek kare.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- Everyone makes mistakes: wrong file committed, bad message, a commit that broke production.
- **The wrong undo tool causes real damage:** `git reset --hard` deletes uncommitted work forever, and resetting a shared branch breaks teammates' repositories.
- Knowing `git reflog` turns "I lost a day of work!" into a two-minute fix.
- In production incidents, reverting the bad commit is often the fastest safe rollback.

</En>
<Ur>

- Har koi ghaltiyan karta hai: ghalat file commit, bura message, aisa commit jis ne production tor di.
- **Ghalat undo tool asal nuqsan karta hai:** `git reset --hard` uncommitted kaam hamesha ke liye mita deta hai, aur saanjhi branch reset karna saathiyon ki repositories tor deta hai.
- `git reflog` jaanna "mera din bhar ka kaam kho gaya!" ko do minute ka kaam bana deta hai.
- Production incidents me ghalat commit revert karna aksar sab se tez mehfooz rollback hota hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **Every day:** discard a bad experiment, unstage a file, fix a commit message.
- **Before pushing:** squash or remove local commits with reset.
- **After pushing, or in production:** revert.
- **After a scary moment:** reflog.

</En>
<Ur>

- **Rozana:** bura tajurba phenkna, file unstage karna, commit message theek karna.
- **Push se pehle:** reset se local commits squash ya hatana.
- **Push ke baad, ya production me:** revert.
- **Darawne lamhe ke baad:** reflog.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
git restore app.js              # throw away my edits
git restore --staged .env       # unstage, keep the file
git commit --amend              # fix the last (unpushed) commit
git reset --soft HEAD~3         # undo 3 local commits, keep changes staged
git revert <hash>               # undo a pushed commit with a new commit
git reflog                      # find "lost" commits
```

</En>
<Ur>

```text
git restore app.js              # meri tabdeeliyan phenko
git restore --staged .env       # unstage, file rakho
git commit --amend              # aakhri (unpushed) commit theek
git reset --soft HEAD~3         # 3 local commits wapas, tabdeeliyan staged
git revert <hash>               # push shuda commit naye commit se ulto
git reflog                      # "khoye" commits dhoondho
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **bank statement**. If you notice a mistake on a form **before submitting it**, you tear it up and fill in a new one (restore, reset, amend). Once a transaction is **on the statement** that others have seen, the bank never erases the line. It adds a **new correcting transaction**: "Refund: −500". That's `git revert`: history stays honest and everyone's copy stays consistent. And the bank's internal audit log records every action, even the cancelled ones. That's the **reflog**, your safety net for finding things you thought were gone.

</En>
<Ur>

**Bank statement** ka socho. Agar form **jama karne se pehle** ghalti dikhe, to aap use phaar kar naya bharte hain (restore, reset, amend). Jab koi len den **statement par** aa jaye jo doosre dekh chuke hon, bank kabhi wo line nahi mitata. Wo **nayi durusti wali entry** jorta hai: "Refund: −500". Yahi `git revert` hai: tareekh imaandaar rehti hai aur sab ki copy ek jaisi. Aur bank ka andaruni audit log har kaam record karta hai, radd shuda bhi. Yahi **reflog** hai, un cheezon ko dhoondhne ka hifazati jaal jinhe aap khoya hua samajhte the.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Discard uncommitted edits: git restore">

<Tr>
<En>

`git restore <file>` replaces the file in your folder with its last **staged** version, or the last **committed** one if nothing is staged. Use it when an edit got messy and you want to start over. `git restore .` does all files. (Older tutorials use `git checkout -- file`, which does the same.)

</En>
<Ur>

`git restore <file>` folder ki file ko us ke aakhri **staged** version se badal deta hai, ya aakhri **committed** se agar kuch staged na ho. Jab tabdeeli bigar jaye aur naye sire se shuru karna ho tab istemal karein. `git restore .` saari files ke liye. (Purane tutorials `git checkout -- file` likhte hain, jo yahi karta hai.)

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q shop && cd shop
printf 'price = 100\ntax = 0.17\n' > cart.py && git add . && git commit -qm "Add cart"
echo "BROKEN EXPERIMENT" > cart.py
git status -s
git restore cart.py
git status -s | wc -l | sed 's/$/ changed files after restore/'
cat cart.py
```

```text output
 M cart.py
0 changed files after restore
price = 100
tax = 0.17
```

<Happened>
<Tr>
<En>`echo … > cart.py` overwrote the whole file, and `git status` showed ` M` (modified, not staged). `git restore cart.py` brought back the committed version: no changes left, and the file is exactly as in "Add cart".</En>
<Ur>`echo … > cart.py` ne poori file mita kar likhi, aur `git status` ne ` M` dikhaya (badli, staged nahi). `git restore cart.py` ne committed version wapas laya: koi tabdeeli baqi nahi, aur file bilkul "Add cart" jaisi hai.</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>**There's no undo for this.** Uncommitted edits aren't stored anywhere in Git, so once restored they're gone. If you're unsure, `git stash` instead.</En>
<Ur>**Is ka koi undo nahi.** Uncommitted tabdeeliyan Git me kahin save nahi hotin, isliye restore ke baad wo chali gayin. Yaqeen na ho to `git stash` karein.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Take one file from an older commit">

<Tr>
<En>

"The config was right two commits ago. I want **just that file** back, not the whole project." `git restore --source=<commit> file` puts the file's content from **any** commit into your folder: `git restore --source=HEAD~2 config.yml`, `git restore --source=v1.0.0 README.md`. The result is an ordinary uncommitted change, so review it with `git diff` and commit it like any other edit.

</En>
<Ur>

"Config do commits pehle durust thi. Mujhe **sirf wo file** wapas chahiye, poora project nahi." `git restore --source=<commit> file` **kisi bhi** commit se file ka mawad aap ke folder me daal deta hai: `git restore --source=HEAD~2 config.yml`, `git restore --source=v1.0.0 README.md`. Nateeja aam uncommitted tabdeeli hai, isliye `git diff` se dekhein aur doosri tabdeeliyon ki tarah commit karein.

</Ur>
</Tr>

```bash
cd shop
sed -i 's/tax = 0.17/tax = 0.18/' cart.py && git commit -qam "Raise tax"
sed -i 's/tax = 0.18/tax = 0.99/' cart.py && git commit -qam "Oops, wrong tax"
git restore --source=HEAD~2 cart.py
git diff --stat | sed -E 's/ +\| +/ | /'
grep tax cart.py
git commit -qam "Restore tax from first version"
git log --format=%s
```

```text output
 cart.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
tax = 0.17
Restore tax from first version
Oops, wrong tax
Raise tax
Add cart
```

<Happened>
<Tr>
<En>The tax went to 0.18, then wrongly to 0.99. `--source=HEAD~2` took `cart.py` from "Add cart" (0.17), and `git diff --stat` showed it as a normal pending change. We committed it, and nothing was rewritten: history shows exactly what happened, including the fix.</En>
<Ur>Tax 0.18 hua, phir ghalti se 0.99. `--source=HEAD~2` ne `cart.py` "Add cart" se li (0.17), aur `git diff --stat` ne use aam baqi tabdeeli dikhaya. Hum ne commit kiya, aur kuch dobara nahi likha gaya: tareekh bilkul dikhati hai kya hua, fix samet.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Unstage: git restore --staged">

<Tr>
<En>

You ran `git add .` and staged something that shouldn't be in this commit: a debug file, a `.env`, an unrelated change. `git restore --staged <file>` removes it from the staging area, and **your edits stay in the file**. Completely safe: nothing is deleted. (Older: `git reset HEAD file`.)

</En>
<Ur>

Aap ne `git add .` chalaya aur kuch aisa stage ho gaya jo is commit me nahi hona chahiye: debug file, `.env`, koi be-ta'alluq tabdeeli. `git restore --staged <file>` use staging area se hata deta hai, aur **aap ki tabdeeliyan file me rehti hain**. Bilkul mehfooz: kuch nahi mit-ta. (Purana: `git reset HEAD file`.)

</Ur>
</Tr>

```bash
cd shop
echo "DB_PASSWORD=hunter2" > .env
echo "discount = 10" >> cart.py
git add .
git status -s
git restore --staged .env
git status -s
```

```text output
A  .env
M  cart.py
M  cart.py
?? .env
```

<Happened>
<Tr>
<En>`git add .` staged **everything**, including the secret `.env` (`A`, added). After `git restore --staged .env` it's back to `??` untracked, and the file still exists. `cart.py` stays staged (`M` in the first column). In real life, add `.env` to `.gitignore` next so this can't happen again.</En>
<Ur>`git add .` ne **sab kuch** stage kiya, raaz wali `.env` samet (`A`, added). `git restore --staged .env` ke baad wo wapas `??` untracked hai, aur file ab bhi maujood hai. `cart.py` staged rehti hai (pehle column me `M`). Asal zindagi me agla qadam `.env` ko `.gitignore` me daalna hai taa ke dobara na ho.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fix the last commit: --amend">

<Tr>
<En>

`git commit --amend` replaces the most recent commit with a new one: change its message, add forgotten files, or both. Do it **only if the commit hasn't been pushed** (or is on your own branch). Forms: `git commit --amend -m "New message"`, or `git add file && git commit --amend --no-edit`.

</En>
<Ur>

`git commit --amend` sab se naye commit ko naye se badal deta hai: message badlo, bhooli files jor do, ya dono. Ye **sirf tab karein jab commit push na hua ho** (ya apni branch par ho). Shaklen: `git commit --amend -m "New message"`, ya `git add file && git commit --amend --no-edit`.

</Ur>
</Tr>

```bash
cd shop
git commit -qm "Add discout"
old=$(git rev-parse --short HEAD)
git commit -q --amend -m "Add discount"
new=$(git rev-parse --short HEAD)
git log -1 --format=%s
[ "$old" != "$new" ] && echo "amend created a new commit (new hash)"
git log --format=%s | wc -l | sed 's/$/ commits in total (no extra commit added)/'
```

```text output
Add discount
amend created a new commit (new hash)
5 commits in total (no extra commit added)
```

<Happened>
<Tr>
<En>We committed the still-staged `cart.py` with a typo ("discout"), then `--amend` replaced it with a correctly named commit. The hash changed, because amend doesn't edit a commit, it **replaces** it. The total stayed at 5: the typo commit isn't on the branch any more.</En>
<Ur>Hum ne ab tak staged `cart.py` typo ("discout") ke saath commit ki, phir `--amend` ne use durust naam wale commit se badal diya. Hash badal gaya, kyun ke amend commit ko badalta nahi, **naye se badal deta** hai. Kul 5 hi rahe: typo wala commit ab branch par nahi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="git reset: three modes">

<Tr>
<En>

`git reset <commit>` moves the **current branch pointer** to another (usually older) commit. Use it to undo **local, unpushed** commits: to redo, split, combine or throw them away. `HEAD~1` = one commit back, `HEAD~3` = three back. The mode decides what happens to the changes from the commits you "removed":

| Mode | Branch pointer | Staging area | Your files | Danger |
| --- | --- | --- | --- | --- |
| `--soft` | moved back | **keeps** the changes (staged) | unchanged | Safe |
| `--mixed` (default) | moved back | cleared | **keep** the changes (unstaged) | Safe |
| `--hard` | moved back | cleared | **changes deleted** | Destroys uncommitted work |

```text
Before:  A ── B ── C   ← main (HEAD)

git reset --soft  HEAD~1   →  A ── B ← main     C's changes: staged, ready to recommit
git reset --mixed HEAD~1   →  A ── B ← main     C's changes: in your files, not staged
git reset --hard  HEAD~1   →  A ── B ← main     C's changes: gone from files (commit C still in reflog)
```

</En>
<Ur>

`git reset <commit>` **mojooda branch ka pointer** doosre (aam tor par purane) commit par le jata hai. Ise **local, unpushed** commits wapas lene ke liye istemal karein: dobara banane, torne, jorne ya phenkne ke liye. `HEAD~1` = ek commit peeche, `HEAD~3` = teen peeche. Mode tay karta hai "hataye gaye" commits ki tabdeeliyon ka kya ho:

| Mode | Branch pointer | Staging area | Aap ki files | Khatra |
| --- | --- | --- | --- | --- |
| `--soft` | peeche | tabdeeliyan **rakhta** (staged) | waisi hi | Mehfooz |
| `--mixed` (default) | peeche | saaf | tabdeeliyan **rakhti** (unstaged) | Mehfooz |
| `--hard` | peeche | saaf | **tabdeeliyan mit gayin** | Uncommitted kaam tabah |

```text
Before:  A ── B ── C   ← main (HEAD)

git reset --soft  HEAD~1   →  A ── B ← main     C's changes: staged, ready to recommit
git reset --mixed HEAD~1   →  A ── B ← main     C's changes: in your files, not staged
git reset --hard  HEAD~1   →  A ── B ← main     C's changes: gone from files (commit C still in reflog)
```

</Ur>
</Tr>

</Step>

<Step title="reset --soft: squash local commits">

<Tr>
<En>

`--soft` moves the branch back and keeps the undone changes **staged**. Perfect for "I made 3 messy commits, I want them as 1 clean commit": `git reset --soft HEAD~3 && git commit -m "Clean message"`. Your files don't change at all, and nothing is lost.

</En>
<Ur>

`--soft` branch peeche le jata hai aur wapas li gayi tabdeeliyan **staged** rakhta hai. "Main ne 3 ganday commits kiye, unhe 1 saaf commit chahiye" ke liye behtareen: `git reset --soft HEAD~3 && git commit -m "Clean message"`. Aap ki files bilkul nahi badaltin, aur kuch nahi khota.

</Ur>
</Tr>

```bash
git init -q soft && cd soft
git commit -q --allow-empty -m "Start"
for m in "wip" "more wip" "finally works"; do echo "$m" >> login.js; git add .; git commit -qm "$m"; done
git reset -q --soft HEAD~3
git status -s
git commit -qm "Add login feature"
git log --format=%s
echo "login.js still has $(wc -l < login.js) lines"
```

```text output
A  login.js
Add login feature
Start
login.js still has 3 lines
```

<Happened>
<Tr>
<En>Three messy commits each added a line. `reset --soft HEAD~3` moved `main` back to "Start", and **all** their changes stayed staged (`A login.js`). One commit turned them into "Add login feature". The file still has all three lines; only the history got tidier.</En>
<Ur>Teen ganday commits ne ek ek line jori. `reset --soft HEAD~3` ne `main` ko "Start" par wapas kiya, aur un ki **saari** tabdeeliyan staged rahin (`A login.js`). Ek commit ne unhe "Add login feature" bana diya. File me ab bhi teeno lines hain; sirf tareekh saaf hui.</Ur>
</Tr>
</Happened>

</Step>

<Step title="reset --mixed: split a commit">

<Tr>
<En>

The default mode. It moves the branch back, clears the staging area, and leaves the changes **in your files**. Use it when one commit mixes two things, like a bug fix and a new feature: `git reset HEAD~1`, then `git add` file by file (or `git add -p` piece by piece). Safe: your edits remain.

</En>
<Ur>

Default mode. Ye branch peeche le jata hai, staging area saaf karta hai, aur tabdeeliyan **aap ki files me** chhorta hai. Jab ek commit me do cheezen mili hon, jaise bug fix aur naya feature: `git reset HEAD~1`, phir file ba file `git add` (ya tukra ba tukra `git add -p`). Mehfooz: aap ki tabdeeliyan rehti hain.

</Ur>
</Tr>

```bash
git init -q mixed && cd mixed
git commit -q --allow-empty -m "Start"
echo "fix" > bugfix.js; echo "feature" > feature.js
git add . && git commit -qm "Fix bug and add feature"
git reset -q HEAD~1
git status -s
git add bugfix.js && git commit -qm "Fix null crash in checkout"
git add feature.js && git commit -qm "Add gift wrapping option"
git log --format=%s
```

```text output
?? bugfix.js
?? feature.js
Add gift wrapping option
Fix null crash in checkout
Start
```

<Happened>
<Tr>
<En>One commit held two unrelated changes. After `git reset HEAD~1` both files were still there, now untracked (`??`) because they were new in that commit. We committed them separately with clear messages, so if the feature causes problems later, it can be reverted without removing the bug fix.</En>
<Ur>Ek commit me do be-ta'alluq tabdeeliyan thin. `git reset HEAD~1` ke baad dono files maujood rahin, ab untracked (`??`) kyun ke wo usi commit me nayi thin. Hum ne unhe saaf messages ke saath alag commit kiya, taa ke feature baad me masla kare to bug fix hataye baghair revert ho sake.</Ur>
</Tr>
</Happened>

</Step>

<Step title="reset --hard: throw everything away">

<Tr>
<En>

`--hard` moves the branch back **and** makes your staging area and files match that commit exactly. Later commits, and **all uncommitted edits**, disappear from your folder. Use it to abandon a failed experiment, or to match the server exactly with `git reset --hard origin/main`. `git reset --hard HEAD` throws away only uncommitted edits.

</En>
<Ur>

`--hard` branch peeche le jata hai **aur** staging area aur files ko bilkul us commit jaisa bana deta hai. Baad ke commits, aur **saari uncommitted tabdeeliyan**, folder se ghayab. Nakaam tajurba chhorne ke liye, ya `git reset --hard origin/main` se server se bilkul milne ke liye istemal karein. `git reset --hard HEAD` sirf uncommitted tabdeeliyan phenkta hai.

</Ur>
</Tr>

```bash
git init -q hard && cd hard
echo "good" > app.txt && git add . && git commit -qm "Good state"
echo "bad 1" >> app.txt && git commit -qam "Bad experiment 1"
echo "bad 2" >> app.txt && git commit -qam "Bad experiment 2"
echo "uncommitted junk" >> app.txt
git reset --hard HEAD~2 | sed -E 's/at [0-9a-f]{7,}/at <hash>/'
cat app.txt
git status -s | wc -l | sed 's/$/ uncommitted changes left/'
```

```text output
HEAD is now at <hash> Good state
good
0 uncommitted changes left
```

<Happened>
<Tr>
<En>After "Good state" came two bad commits plus an uncommitted line. `reset --hard HEAD~2` moved `main` back and overwrote the file: only `good` remains. The two **commits** can still be recovered from the reflog; the uncommitted `uncommitted junk` line **cannot**.</En>
<Ur>"Good state" ke baad do bure commits aur ek uncommitted line aayi. `reset --hard HEAD~2` ne `main` peeche ki aur file mita kar likhi: sirf `good` bacha. Do **commits** ab bhi reflog se wapas laye ja sakte hain; uncommitted `uncommitted junk` line **nahi**.</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>Before any `reset --hard`, run `git status`. If there's anything you might want, `git stash` it first. Uncommitted work has no safety net.</En>
<Ur>Har `reset --hard` se pehle `git status` chalayen. Agar kuch bhi kaam ka ho, pehle `git stash` karein. Uncommitted kaam ka koi hifazati jaal nahi.</Ur>
</Tr>
</Callout>

</Step>

<Step title="git revert: undo a pushed commit safely">

<Tr>
<En>

`git revert <commit>` creates a **new commit** that applies the exact opposite of the given commit, so history isn't rewritten. Commits on `main` or any shared branch must never be removed, because teammates already have them; revert undoes the **effect** while keeping everyone's history consistent. Forms: `git revert HEAD`, `git revert --no-edit <hash>`, `git revert A..B`. On GitHub, merged PRs have a **Revert** button.

</En>
<Ur>

`git revert <commit>` ek **naya commit** banata hai jo diye gaye commit ka bilkul ulta lagata hai, isliye tareekh dobara nahi likhi jati. `main` ya kisi saanjhi branch ke commits kabhi hataye nahi jate, kyun ke saathiyon ke paas pehle se hain; revert **asar** ulat deta hai jab ke sab ki tareekh ek jaisi rehti hai. Shaklen: `git revert HEAD`, `git revert --no-edit <hash>`, `git revert A..B`. GitHub par merged PRs ka **Revert** button hota hai.

</Ur>
</Tr>

```bash
git init -q rv && cd rv
printf 'tax=0.17\nshipping=200\n' > settings && git add . && git commit -qm "Initial settings"
sed -i 's/shipping=200/shipping=0/' settings && git commit -qam "Free shipping for everyone"
echo "currency=USD" > locale && git add . && git commit -qm "Add currency"
bad=$(git log --format=%h --grep="Free shipping")
git revert --no-edit "$bad" >/dev/null
git log --format=%s
cat settings locale
```

```text output
Revert "Free shipping for everyone"
Add currency
Free shipping for everyone
Initial settings
tax=0.17
shipping=200
currency=USD
```

<Happened>
<Tr>
<En>

- "Free shipping for everyone" was a pushed mistake; "Add currency" came after it and is fine.
- `git log --grep` found the bad commit's hash, and `git revert --no-edit` added `Revert "Free shipping for everyone"`, changing `shipping=0` back to `200`.
- History shows the mistake **and** its correction, an honest audit trail. "Add currency" is untouched.
- If a later commit had changed the same lines, the revert would stop with a conflict: resolve it like a merge conflict, then `git revert --continue`.
- Teammates just `git pull` the revert. Nobody's history breaks.

</En>
<Ur>

- "Free shipping for everyone" push shuda ghalti thi; "Add currency" us ke baad aaya aur theek hai.
- `git log --grep` ne bure commit ka hash dhoondha, aur `git revert --no-edit` ne `Revert "Free shipping for everyone"` jora, jis ne `shipping=0` ko wapas `200` kiya.
- Tareekh ghalti **aur** us ki durusti dono dikhati hai, imaandaar audit trail. "Add currency" ko kuch nahi hua.
- Agar baad ke commit ne wahi lines badli hotin, revert conflict par rukta: merge conflict ki tarah hal karein, phir `git revert --continue`.
- Saathi bas revert `git pull` karte hain. Kisi ki tareekh nahi toot-ti.

</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>`git revert` doesn't "go back to" a commit. It undoes **one commit's changes**. To return the whole project to an old state, revert each commit after it (`git revert OLD..HEAD`) or restore files from the old commit.</En>
<Ur>`git revert` kisi commit "par wapas" nahi jata. Ye **ek commit ki tabdeeliyan** ulat-ta hai. Poore project ko purani haalat par lana ho to us ke baad ka har commit revert karein (`git revert OLD..HEAD`) ya purane commit se files restore karein.</Ur>
</Tr>
</Callout>

<Step title="Revert a merge commit">

<Tr>
<En>

A whole merged feature broke production and you want to remove all of it at once. A merge commit has two parents, so Git needs to know which side is the "main line". `git revert -m 1 <merge-hash>` means "keep parent 1 (the branch you merged **into**) and undo what the merged branch brought in".

</En>
<Ur>

Poore merge shuda feature ne production tor di aur aap sab ek dafa me hatana chahte hain. Merge commit ke do parents hain, isliye Git ko jaanna hai "main line" kaunsi hai. `git revert -m 1 <merge-hash>` ka matlab "parent 1 rakho (jis branch **me** merge kiya) aur merge hui branch jo laayi wo ulat do".

</Ur>
</Tr>

```bash
git init -q rm && cd rm
echo "home" > index.html && git add . && git commit -qm "Home page"
git switch -q -c feature/chat
echo "chat" > chat.js && git add . && git commit -qm "Add chat widget"
echo "chat css" > chat.css && git add . && git commit -qm "Style chat widget"
git switch -q main
git merge -q --no-ff -m "Merge pull request #7 feature/chat" feature/chat
echo "before revert: $(ls | tr '\n' ' ')"
git revert --no-edit -m 1 HEAD >/dev/null
echo "after revert:  $(ls | tr '\n' ' ')"
git log --format=%s | head -2
```

```text output
before revert: chat.css chat.js index.html 
after revert:  index.html 
Revert "Merge pull request #7 feature/chat"
Merge pull request #7 feature/chat
```

<Happened>
<Tr>
<En>`feature/chat` added two files and was merged like a PR. HEAD is the merge commit; parent 1 is `main` before the merge, so `-m 1` undid everything the feature brought in. Both chat files are gone in one step, and history keeps the merge and its revert.</En>
<Ur>`feature/chat` ne do files joren aur PR ki tarah merge hui. HEAD merge commit hai; parent 1 merge se pehle wali `main` hai, isliye `-m 1` ne feature ka laya sab ulat diya. Dono chat files ek qadam me chali gayin, aur tareekh merge aur us ka revert dono rakhti hai.</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>To merge the same branch again later, first **revert the revert**. Otherwise Git thinks those commits are already merged and silently skips them.</En>
<Ur>Wahi branch baad me dobara merge karni ho to pehle **revert ka revert** karein. Warna Git samajhta hai wo commits pehle se merge hain aur chupke se chhor deta hai.</Ur>

<Step title="git reflog: the safety net">

<Tr>
<En>

The reflog is a **local** diary of every commit HEAD has pointed to: commits, checkouts, resets, rebases, amends, merges. Each entry has a name like `HEAD@{2}` ("where HEAD was 2 moves ago"). Commits you "removed" aren't deleted right away, only unreferenced, so the reflog lets you find and bring them back. Entries are kept about 90 days (30 for unreachable commits). The reflog is **only on your machine**: it isn't pushed or cloned.

</En>
<Ur>

Reflog ek **local** roznamcha hai har us commit ka jis ki taraf HEAD ne ishara kiya: commits, checkouts, resets, rebases, amends, merges. Har entry ka naam `HEAD@{2}` jaisa hota hai ("2 qadam pehle HEAD kahan tha"). "Hataye" gaye commits foran nahi mit-te, sirf be-hawala hote hain, isliye reflog unhe dhoondh kar wapas lane deta hai. Entries takreeban 90 din rehti hain (be-hawala commits ke liye 30). Reflog **sirf aap ki machine par** hai: push ya clone nahi hota.

</Ur>
</Tr>

```bash
git init -q rl && cd rl
for m in "Add login" "Add signup" "Add password reset"; do echo "$m" > "$(echo "$m" | tr ' ' '-').txt"; git add .; git commit -qm "$m"; done
git reset -q --hard HEAD~2                      # disaster: two commits gone
echo "after the mistake: $(git log --format=%s | tr '\n' ',')"
git reflog --format='%gd  %gs' | head -3
git reset -q --hard 'HEAD@{1}'                  # go back to where HEAD was before the reset
echo "recovered: $(git log --format=%s | tr '\n' ',')"
```

```text output
after the mistake: Add login,
HEAD@{0}  reset: moving to HEAD~2
HEAD@{1}  commit: Add password reset
HEAD@{2}  commit: Add signup
recovered: Add password reset,Add signup,Add login,
```

<Happened>
<Tr>
<En>

- `reset --hard HEAD~2` "lost" two commits; the log showed only "Add login".
- `git reflog` listed the diary, newest first: `HEAD@{0}` is the reset, and `HEAD@{1}` is where HEAD was before it, at "Add password reset".
- `git reset --hard 'HEAD@{1}'` brought all three commits back. The quotes stop PowerShell or zsh from misreading `{}`.

**Golden rule:** if you **committed** it, Git can almost always get it back. Commit often, even as "WIP" on a branch.

</En>
<Ur>

- `reset --hard HEAD~2` ne do commits "kho" diye; log me sirf "Add login" tha.
- `git reflog` ne roznamcha dikhaya, naye pehle: `HEAD@{0}` reset hai, aur `HEAD@{1}` us se pehle HEAD ki jagah, "Add password reset" par.
- `git reset --hard 'HEAD@{1}'` ne teeno commits wapas laye. Quotes PowerShell ya zsh ko `{}` ghalat parhne se rokte hain.

**Sunehra qaida:** agar aap ne **commit** kiya tha, Git takreeban hamesha wapas la sakta hai. Aksar commit karein, branch par "WIP" ki shakal me bhi.

</Ur>
</Tr>
</Happened>

<Step title="Recover a deleted branch">

<Tr>
<En>

`git branch -D` removes only the branch **name**; the commits stay in the repository for a while. Git even prints the tip hash when deleting: `Deleted branch x (was a1b2c3d)`. `git branch <name> <hash>` recreates the branch at that commit.

</En>
<Ur>

`git branch -D` sirf branch ka **naam** hatata hai; commits kuch arse repository me rehte hain. Mitate waqt Git nok ka hash bhi chhaapta hai: `Deleted branch x (was a1b2c3d)`. `git branch <name> <hash>` us commit par branch dobara banata hai.

</Ur>
</Tr>

```bash
git init -q db && cd db
git commit -q --allow-empty -m "Start"
git switch -q -c feature/reports
echo "report" > report.js && git add . && git commit -qm "Add monthly report"
git switch -q main
tip=$(git rev-parse feature/reports)
git branch -q -D feature/reports
git branch | sed 's/^/branches now: /'
git branch feature/reports "$tip"
git log -1 --format='restored branch points to: %s' feature/reports
```

```text output
branches now: * main
restored branch points to: Add monthly report
```

<Happened>
<Tr>
<En>`tip` plays the role of the hash Git prints on deletion. After `-D` only `main` remained, and `git branch feature/reports "$tip"` brought the branch and its work back. Without a saved hash, look in `git reflog` for `checkout: moving from feature/reports to main`; the entry just before it is the branch's last commit.</En>
<Ur>`tip` us hash ka kaam karta hai jo Git mitate waqt chhaapta hai. `-D` ke baad sirf `main` bachi, aur `git branch feature/reports "$tip"` ne branch aur us ka kaam wapas laya. Hash save na ho to `git reflog` me `checkout: moving from feature/reports to main` dhoondhein; us se theek pehle wali entry branch ka aakhri commit hai.</Ur>
</Tr>
</Happened>

<Step title="Untracked files: git clean">

<Tr>
<En>

`git restore` and `git reset --hard` don't touch **untracked** files (build output, generated files, stray test files). `git clean` deletes them. `-n` is a dry run that only shows what would go, `-f` deletes files, `-d` includes folders, and `-x` includes ignored files like `node_modules`.

</En>
<Ur>

`git restore` aur `git reset --hard` **untracked** files (build output, banayi gayi files, bhatki test files) ko nahi chhoote. `git clean` unhe mitata hai. `-n` dry run hai jo sirf dikhata hai kya jayega, `-f` files mitata hai, `-d` folders samet, aur `-x` `node_modules` jaisi ignored files samet.

</Ur>
</Tr>

```bash
git init -q cl && cd cl
echo "app" > app.js && git add . && git commit -qm "App"
echo "debug" > debug.log; mkdir tmp && echo "x" > tmp/cache.bin
git clean -n -d
git clean -q -f -d
ls
```

```text output
Would remove debug.log
Would remove tmp/
app.js
```

<Happened>
<Tr>
<En>`debug.log` and `tmp/cache.bin` were never added to Git. The dry run listed them (the folder too, thanks to `-d`), then `git clean -f -d` really deleted them, leaving only the tracked `app.js`.</En>
<Ur>`debug.log` aur `tmp/cache.bin` kabhi Git me add nahi hue. Dry run ne unhe dikhaya (`-d` ki wajah se folder bhi), phir `git clean -f -d` ne waqai mita diya, sirf track ki `app.js` bachi.</Ur>
</Tr>
</Happened>

<Tr>
<En>**Always run `-n` first.** Untracked files were never in Git, so nothing can recover them.</En>
<Ur>**Hamesha pehle `-n` chalayen.** Untracked files kabhi Git me thin hi nahi, isliye koi unhe wapas nahi la sakta.</Ur>

## Common mistakes

<Compare>
<Bad title="Reset a pushed commit on main and force it">

```text
git switch main
git reset --hard HEAD~1     # the bad commit is already on GitHub
git push --force            # teammates' clones now disagree with the server
```

</Bad>
<Good title="Revert it: a new commit, nothing rewritten">

```text
git switch main && git pull
git revert --no-edit <bad-hash>
git push                    # everyone just pulls the fix
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`git reset --hard` with uncommitted work you wanted.** It's gone. Check `git status` first, or stash.
- **Using `git clean -f` without `-n` first**, deleting untracked files you needed.
- **Re-merging a reverted branch** without reverting the revert, then wondering why the changes don't appear.
- **Panicking and re-cloning the repo**, which loses the local reflog that could have saved you.
- **Forgetting the reflog is local:** a teammate's reflog can't help you, and yours isn't on GitHub.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Chahiye wala uncommitted kaam hote hue `git reset --hard`.** Wo chala gaya. Pehle `git status` dekhein, ya stash karein.
- **Pehle `-n` ke baghair `git clean -f`**, zaroori untracked files mita dena.
- **Revert hui branch dobara merge karna** revert ka revert kiye baghair, phir hairat ke tabdeeliyan kyun nahi aayin.
- **Ghabra kar repo dobara clone karna**, jis se wo local reflog kho jata hai jo bacha sakta tha.
- **Bhoolna ke reflog local hai:** saathi ka reflog aap ki madad nahi kar sakta, aur aap ka GitHub par nahi.

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- Choose the undo by where the mistake is: files, staging, local commits, or shared commits.
- `git restore` discards edits (no undo); `--staged` only unstages (safe).

- reset `--soft` = staged, `--mixed` = unstaged, `--hard` = gone.
- Pushed or on `main` → `git revert`; merged PR → `git revert -m 1`.
- Revert the revert before re-merging a reverted branch.
- `git reflog` finds "lost" commits and deleted branches.
- `git clean -n` before `git clean -fd`. Commit often: committed work is recoverable.

</En>

<DeepDive title="Real world: Friday evening rollback">

On a Friday evening, a PR adding a new payment provider is merged and deployed, and checkouts start failing. The on-call developer doesn't try to fix the bug under pressure. She clicks **Revert** on the merged PR in GitHub, which opens a PR with `git revert -m 1 <merge>`, gets a quick approval and merges it. Production is healthy in ten minutes, and history shows exactly what happened. On Monday the original author fixes the bug on a branch. Before re-merging he first **reverts the revert** (otherwise Git would treat the original commits as already merged), then adds the fix and opens a new PR.

Meanwhile another developer ran `git reset --hard` on his local branch and thought he'd lost two days of work. `git reflog` showed the commit from before the reset, and `git switch -c recovered <hash>` brought everything back.

</DeepDive>

<DeepDive title="Security lens">

Undoing a commit does not undo a leak. If a secret was ever pushed, assume it's compromised and rotate it first.

- Reverting a commit that contains a password still leaves the password in history. `reset` plus force-push doesn't remove it from forks, clones, caches or CI logs either. **Rotate the secret immediately**, then clean history if needed (see **Keeping Secrets Out of Git**).
- On protected branches force pushes are blocked, so revert is the only way to undo. That's the point: an attacker (or a mistake) can't silently erase history.
- Reverts form an audit trail of **who** undid **what** and **when**, which helps incident investigations and compliance.
- `git reset --hard` and `git clean -fdx` in CI scripts can delete files unexpectedly; use them only in disposable workspaces.
- Reflog and unreachable objects mean "deleted" sensitive data may still exist **in your local repository**. If a laptop is lost, everything in its `.git` folder is exposed too.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between git reset and git revert?">
git reset moves the current branch pointer to another commit and can rewrite history, removing commits from the branch. It is suitable for local, unpushed commits. git revert creates a new commit that applies the inverse of an existing commit, leaving history intact, so it is the safe way to undo commits that have already been shared.
</QA>

<QA q="Explain git reset --soft, --mixed and --hard.">
All three move the current branch to the given commit. --soft leaves the index and working directory unchanged, so the undone changes stay staged. --mixed, the default, resets the index but keeps the changes in the working directory as unstaged edits. --hard resets both the index and the working directory, discarding the changes and any uncommitted work.
</QA>

<QA q="How do you recover commits after an accidental git reset --hard?">
Run git reflog to see previous positions of HEAD, find the entry from before the reset, and then reset to that hash or HEAD@{n} reference, or create a new branch there with git switch -c. This works as long as the commits have not been garbage-collected. Uncommitted changes discarded by the reset cannot be recovered this way.
</QA>

<QA q="How do you undo a merged pull request on main?">
Revert the merge commit with git revert -m 1 followed by the merge commit hash, or use GitHub's Revert button, which creates a pull request containing that revert. -m 1 keeps the main line as the parent and undoes the changes introduced by the merged branch. To merge the feature again later, the revert commit must itself be reverted first.
</QA>

<QA q="What is the difference between git restore and git restore --staged?">
git restore file discards uncommitted changes in the working directory by restoring the file from the index or HEAD, which cannot be undone. git restore --staged file removes the file's changes from the staging area but keeps them in the working directory, so nothing is lost.
</QA>

</DeepDive>

  <Term name="git restore">Restore files in the working directory or index.</Term>
  <Term name="Unstage">Remove changes from the staging area, keeping the edits.</Term>
  <Term name="Amend">Replace the latest commit.</Term>
  <Term name="git reset">Move the current branch to another commit (soft, mixed, hard).</Term>

<DeepDive title="More practice">

1. Edit a file and discard the change with `git restore`. Stage another file and unstage it with `git restore --staged`.
2. Make three commits and try `reset --soft`, `--mixed` and `--hard` on copies of the repo; compare `git status` after each.
3. Push a commit to a bare "server" repo, undo it with `git revert`, and push again.
4. Merge a feature branch with `--no-ff` and revert the merge with `-m 1`.
5. Run `git reset --hard HEAD~3`, then recover the commits using only `git reflog`.
