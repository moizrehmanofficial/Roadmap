<BigIdea>
<Tr>
<En>
A **tag** is a permanent name for one specific commit, like **`v1.4.0`**. A branch moves forward with every commit; a tag **never moves**. Use **annotated tags** (`git tag -a v1.4.0 -m "..."`) for releases, because they record who tagged, when, and why. Version numbers follow **Semantic Versioning**, **MAJOR.MINOR.PATCH**: breaking change, new feature, bug fix. Tags **aren't pushed automatically** (`git push origin v1.4.0`), and on GitHub a **Release** is a tag plus release notes and downloadable files. Pushing a tag often **is** the deployment.
</En>
<Ur>
**Tag** ek khaas commit ka mustaqil naam hai, jaise **`v1.4.0`**. Branch har commit ke saath aage barhti hai; tag **kabhi nahi hilta**. Releases ke liye **annotated tags** (`git tag -a v1.4.0 -m "..."`) istemal karein, kyun ke wo record karte hain kis ne, kab, aur kyun tag kiya. Version numbers **Semantic Versioning** follow karte hain, **MAJOR.MINOR.PATCH**: toorne wali tabdeeli, naya feature, bug fix. Tags **khud push nahi hote** (`git push origin v1.4.0`), aur GitHub par **Release** tag plus release notes aur download hone wali files hai. Tag push karna aksar khud **deployment hota** hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Tags live in `.git/refs/tags/`, just like branches live in `.git/refs/heads/`. The difference is behaviour: when you commit, the current **branch** moves to the new commit, but **tags stay where you put them**. That makes them perfect for marking "this exact code is version 2.1.0".

```text
          v1.0.0          v1.1.0                 ← tags (fixed)
            │               │
 A ── B ── C ── D ── E ── F ── G ── H            ← commits
                                    │
                                   main          ← branch (moves on every commit)
```

</En>
<Ur>

Tags `.git/refs/tags/` me rehte hain, bilkul jaise branches `.git/refs/heads/` me. Farq rawaiye ka hai: commit karne par mojooda **branch** naye commit par chali jati hai, lekin **tags wahin rehte hain jahan aap ne lagaye**. Isliye ye "bilkul yahi code version 2.1.0 hai" ka nishan lagane ke liye behtareen hain.

```text
          v1.0.0          v1.1.0                 ← tags (fixed)
            │               │
 A ── B ── C ── D ── E ── F ── G ── H            ← commits
                                    │
                                   main          ← branch (moves on every commit)
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Reproducibility:** "Which code is in production?" → "v2.1.0" → `git checkout v2.1.0` shows exactly that code.
- **Bug reports:** a user on v1.9 reports a bug; you check out v1.9 and reproduce it.
- **Rollbacks:** deploying the previous version is just "deploy tag v2.0.3".
- **Automation:** CI/CD pipelines commonly build and publish when a `v*` tag is pushed.
- **Communication:** the version number tells users how risky an upgrade is.
- **Package managers** (npm, PyPI, Docker image tags, Go modules) all rely on version numbers.

</En>
<Ur>

- **Dobara bana sakna:** "Production me kaunsa code hai?" → "v2.1.0" → `git checkout v2.1.0` bilkul wahi code dikhata hai.
- **Bug reports:** v1.9 wala user bug batata hai; aap v1.9 checkout kar ke dohra lete hain.
- **Rollbacks:** pichhla version deploy karna bas "tag v2.0.3 deploy karo" hai.
- **Automation:** CI/CD pipelines aksar `v*` tag push hone par build aur publish karti hain.
- **Rabta:** version number users ko batata hai upgrade kitna khatarnak hai.
- **Package managers** (npm, PyPI, Docker image tags, Go modules) sab version numbers par chalte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- Every time you ship a version: a website deploy, a mobile app build, a library release, a Docker image.
- Marking important points: "before database migration", "submitted to client".
- On GitHub, under **Releases** on the right side of the repo page.

</En>
<Ur>

- Har dafa jab version ship karein: website deploy, mobile app build, library release, Docker image.
- Ahem marahil ka nishan: "database migration se pehle", "client ko diya".
- GitHub par repo page ki daayen taraf **Releases** me.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
git tag -a v1.4.0 -m "Release 1.4.0"     # annotated release tag
git push origin v1.4.0                   # tags aren't pushed by default
git tag -l 'v1.*' --sort=-v:refname      # list, newest version first
git switch -c hotfix/1.4.1 v1.4.0        # fix an old release
gh release create v1.4.0 --generate-notes
```

</En>
<Ur>

```text

```

## Picture it

<Tr>
<En>

A **book with editions**. The author edits the manuscript every day (commits on `main`). When a version is printed and sold, it gets a fixed label: "**2nd edition, 2026**". The manuscript keeps changing, but the 2nd edition is always exactly the same text, so anyone can say "page 40 of the 2nd edition" and everyone sees the same page. A **tag** is that edition label for your code. A **GitHub Release** is the edition **plus** the "what's new" page and the printed copies (downloadable files).

</En>
<Ur>

**Editions wali kitab**. Musannif har roz masauda badalta hai (`main` par commits). Jab koi version chhap kar bikta hai, us par mustaqil label lagta hai: "**2nd edition, 2026**". Masauda badalta rehta hai, lekin 2nd edition hamesha bilkul wahi text hai, isliye koi bhi "2nd edition ka safha 40" kahe to sab ek hi safha dekhte hain. **Tag** aap ke code ka wahi edition label hai. **GitHub Release** edition **plus** "naya kya hai" safha aur chhapi copies (download hone wali files) hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Lightweight tags">

<Tr>
<En>

A lightweight tag is only a name pointing to a commit, like a branch that never moves. It stores no author, date or message, so it's for quick **personal bookmarks** ("before-refactor"), **not** official releases. `git tag <name>` tags the current commit; `git tag name <commit>` tags another.

</En>
<Ur>

Lightweight tag sirf commit ki taraf ishara karta naam hai, jaise kabhi na hilne wali branch. Is me likhne wala, tareekh ya message nahi hota, isliye ye jaldi ke **zaati bookmarks** ("before-refactor") ke liye hai, sarkari releases ke liye **nahi**. `git tag <name>` mojooda commit tag karta hai; `git tag name <commit>` kisi aur ko.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q shop && cd shop
echo "v1 code" > app.js && git add . && git commit -qm "First version of shop"
git tag before-refactor
git tag
git cat-file -t before-refactor
cat .git/refs/tags/before-refactor | wc -c | sed 's/$/ bytes: just a commit hash/'
```

```text output
before-refactor
commit
41 bytes: just a commit hash
```

<Happened>
<Tr>
<En>`git tag` with no arguments lists tags. `git cat-file -t` prints the **type** the tag points to: `commit`, because a lightweight tag has no object of its own. The tag file is just a 40-character hash plus newline, exactly like a branch file.</En>
<Ur>Baghair arguments `git tag` tags dikhata hai. `git cat-file -t` tag ki manzil ki **qisam** chhaapta hai: `commit`, kyun ke lightweight tag ka apna koi object nahi. Tag file sirf 40 huroof ka hash aur nayi line hai, bilkul branch file jaisi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Annotated tags: the right choice for releases">

<Tr>
<En>

An annotated tag is a real Git **tag object**: it holds the commit it points to, the tagger's name and email, the date and a message, and it can be signed. Releases need that record of who released, when and why, and tools like `git describe` and GitHub use annotated tags by default. Tag the commit that was tested and approved, normally the latest on `main` after the release PR is merged.

</En>
<Ur>

Annotated tag asli Git **tag object** hai: is me manzil wala commit, tagger ka naam aur email, tareekh aur message hota hai, aur ye sign bhi ho sakta hai. Releases ko kis ne, kab aur kyun release kiya ka record chahiye, aur `git describe` aur GitHub jaise tools default me annotated tags istemal karte hain. Wo commit tag karein jo test aur manzoor hua, aam tor par release PR merge hone ke baad `main` ka aakhri.

</Ur>
</Tr>

```bash
cd shop
git tag -a v1.0.0 -m "Release 1.0.0: first public version"
git cat-file -t v1.0.0
git show v1.0.0 --no-patch | sed -E 's/^Date: .*/Date:   <date>/; s/^commit [0-9a-f]+/commit <hash>/'
```

```text output
tag
tag v1.0.0
Tagger: Alex Carter <alex@example.com>
Date:   <date>

Release 1.0.0: first public version

commit <hash>
Author: Alex Carter <alex@example.com>
Date:   <date>

    First version of shop
```

<Happened>
<Tr>
<En>

`git cat-file -t v1.0.0` now prints `tag`: the annotated tag is its own object. In `git show`, the top part (`Tagger`, `Date`, message) belongs to the **tag**, and the bottom part is the **commit** it points to.

| | Lightweight | Annotated |
| --- | --- | --- |
| Stores tagger, date, message | No | Yes |
| Can be signed (GPG/SSH) | No | Yes |
| Used by `git describe` by default | No | Yes |
| Use for | Private bookmarks | Releases |

</En>
<Ur>

`git cat-file -t v1.0.0` ab `tag` chhaapta hai: annotated tag apna object hai. `git show` me upar ka hissa (`Tagger`, `Date`, message) **tag** ka hai, aur neeche wala wo **commit** jis ki taraf ye ishara karta hai.

| | Lightweight | Annotated |
| --- | --- | --- |
| Tagger, tareekh, message rakhta hai | Nahi | Haan |
| Sign ho sakta hai (GPG/SSH) | Nahi | Haan |
| Default me `git describe` istemal karta | Nahi | Haan |
| Kis ke liye | Zaati bookmarks | Releases |

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Semantic Versioning (SemVer)">

<Tr>
<En>

A version number **MAJOR.MINOR.PATCH** where each part has a meaning, so users can tell from the number alone whether an upgrade is safe. Used by npm, PyPI, Cargo, Go modules, Docker images, apps and APIs; Git tags usually add a `v` prefix (`v2.4.1`). Bump the leftmost part that applies and reset the parts to its right to 0.

| Change | Example | Bump | Meaning for users |
| --- | --- | --- | --- |
| Bug fix, no new features | Fix wrong cart total | 2.4.1 → **2.4.2** (PATCH) | Safe to upgrade |
| New feature, old code still works | Add coupon codes | 2.4.2 → **2.5.0** (MINOR) | Safe, new things available |
| Breaking change | Remove an old API endpoint | 2.5.0 → **3.0.0** (MAJOR) | May need code changes |
| Test version before 3.0.0 | | **3.0.0-beta.1** | Not for production |

</En>
<Ur>

Version number **MAJOR.MINOR.PATCH** jis ke har hisse ka matlab hai, taa ke users sirf number se samajh jayen upgrade mehfooz hai ya nahi. npm, PyPI, Cargo, Go modules, Docker images, apps aur APIs me istemal; Git tags aam tor par `v` jorte hain (`v2.4.1`). Jo sab se baayan hissa laagu ho use barhayen aur us ke daayen hisse 0 kar dein.

| Tabdeeli | Misaal | Barhao | Users ke liye matlab |
| --- | --- | --- | --- |
| Bug fix, naya feature nahi | Cart total ki ghalti theek | 2.4.1 → **2.4.2** (PATCH) | Upgrade mehfooz |
| Naya feature, purana code chalta hai | Coupon codes joro | 2.4.2 → **2.5.0** (MINOR) | Mehfooz, nayi cheezen |
| Toorne wali tabdeeli | Purana API endpoint hatao | 2.5.0 → **3.0.0** (MAJOR) | Code badalna pad sakta hai |
| 3.0.0 se pehle test version | | **3.0.0-beta.1** | Production ke liye nahi |

</Ur>
</Tr>

<Tr>
<En>A small shell function that bumps a version, to see the rules in action:</En>
<Ur>Ek chhota shell function jo version barhata hai, qawaid amal me dekhne ke liye:</Ur>
</Tr>

```bash
bump() {                       # usage: bump <version> <major|minor|patch>
  IFS=. read -r major minor patch <<< "${1#v}"
  case $2 in
    major) echo "v$((major + 1)).0.0" ;;
    minor) echo "v$major.$((minor + 1)).0" ;;
    patch) echo "v$major.$minor.$((patch + 1))" ;;
  esac
}
bump v2.4.1 patch
bump v2.4.1 minor
bump v2.4.1 major
```

```text output
v2.4.2
v2.5.0
v3.0.0
```

<Happened>
<Tr>
<En>`${1#v}` removes the leading `v` (`v2.4.1` → `2.4.1`), and `IFS=. read` splits it on dots into three variables. A minor bump reset PATCH to 0; a major bump reset MINOR and PATCH. Versions `0.x.y` mean "early development, anything may change"; `1.0.0` is the first stable public API.</En>
<Ur>`${1#v}` shuru ka `v` hatata hai (`v2.4.1` → `2.4.1`), aur `IFS=. read` dots par teen variables me baant-ta hai. Minor bump ne PATCH 0 kiya; major bump ne MINOR aur PATCH. `0.x.y` versions ka matlab "shuruati development, kuch bhi badal sakta hai"; `1.0.0` pehli mazboot public API hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="List and sort tags">

<Tr>
<En>

"What's our latest release?", "Which v1 versions exist?" `git tag -l "v1.*"` filters by pattern, and `--sort=-v:refname` lists newest version first. Use **version** sorting: plain text sorting puts `v1.10.0` in the wrong place.

</En>
<Ur>

"Hamari aakhri release kaunsi hai?", "v1 ke kaun se versions hain?" `git tag -l "v1.*"` pattern se chhaant-ta hai, aur `--sort=-v:refname` naya version pehle dikhata hai. **Version** sorting istemal karein: saada text sorting `v1.10.0` ko ghalat jagah rakhti hai.

</Ur>
</Tr>

```bash
cd shop
for v in 1.1.0 1.2.0 1.9.0 1.10.0; do
  echo "$v" > VERSION && git add . && git commit -qm "Prepare $v"
  git tag -a "v$v" -m "Release $v"
done
echo "--- text order (wrong for versions):"; git tag -l 'v1.*' | tr '\n' ' '; echo
echo "--- version order, newest first:";   git tag -l 'v1.*' --sort=-v:refname | tr '\n' ' '; echo
echo "--- latest release: $(git describe --tags --abbrev=0)"
```

```text output
--- text order (wrong for versions):
v1.0.0 v1.1.0 v1.10.0 v1.2.0 v1.9.0 
--- version order, newest first:
v1.10.0 v1.9.0 v1.2.0 v1.1.0 v1.0.0 
--- latest release: v1.10.0
```

<Happened>
<Tr>
<En>Text order put `v1.10.0` before `v1.2.0`, because the character "1" sorts before "2". Version sorting understands that 10 is bigger than 9. `git describe --tags --abbrev=0` gives the nearest tag: the latest release.</En>
<Ur>Text tarteeb ne `v1.10.0` ko `v1.2.0` se pehle rakha, kyun ke harf "1" "2" se pehle aata hai. Version sorting samajhti hai 10 nau se bara hai. `git describe --tags --abbrev=0` qareeb tareen tag deta hai: aakhri release.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Which release contains a commit?">

<Tr>
<En>

"We fixed the payment bug in commit `a1b2c3d`. Which versions have the fix? Do customers on v1.2 need to upgrade?" `git tag --contains <commit>` lists every tag whose history includes it. The other direction: `git log v1.1.0..v1.9.0` lists commits added between two releases. Useful for security advisories, support tickets and release notes.

</En>
<Ur>

"Payment bug commit `a1b2c3d` me theek hua. Kin versions me fix hai? Kya v1.2 wale customers ko upgrade karna hai?" `git tag --contains <commit>` har wo tag dikhata hai jis ki tareekh me ye commit ho. Ulti simt: `git log v1.1.0..v1.9.0` do releases ke beech jure commits dikhata hai. Security advisories, support tickets aur release notes ke liye kaam ka.

</Ur>
</Tr>

```bash
cd shop
fix=$(git log --format=%h --grep="Prepare 1.2.0")
echo "releases that include 'Prepare 1.2.0':"; git tag --contains "$fix" --sort=v:refname | tr '\n' ' '; echo
echo "commits between v1.1.0 and v1.9.0:"; git log --format='  %s' v1.1.0..v1.9.0
```

```text output
releases that include 'Prepare 1.2.0':
v1.2.0 v1.9.0 v1.10.0 
commits between v1.1.0 and v1.9.0:
  Prepare 1.9.0
  Prepare 1.2.0
```

<Happened>
<Tr>
<En>`git log --grep` found the commit by its message, and `--contains` showed it's in v1.2.0 and every later release, but not in v1.0.0 or v1.1.0.</En>
<Ur>`git log --grep` ne message se commit dhoondha, aur `--contains` ne dikhaya ke ye v1.2.0 aur baad ki har release me hai, lekin v1.0.0 ya v1.1.0 me nahi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Push tags">

<Tr>
<En>

`git push` does **not** send tags, so experimental local tags don't reach the server by accident. Push them explicitly: `git push origin v1.10.0` (one tag, recommended), `git push --follow-tags` (commits plus annotated tags pointing to them), or `git push --tags` (every local tag, private ones too, so be careful). Many pipelines start when a `v*` tag arrives on GitHub.

</En>
<Ur>

`git push` tags **nahi** bhejta, taa ke tajurbati local tags ghalti se server tak na pahunchen. Unhe khud push karein: `git push origin v1.10.0` (ek tag, behtar), `git push --follow-tags` (commits plus un ki taraf annotated tags), ya `git push --tags` (har local tag, zaati bhi, isliye ehtiyaat). Bohot si pipelines GitHub par `v*` tag aate hi shuru hoti hain.

</Ur>
</Tr>

```bash
cd shop
git init -q --bare ../server.git && git remote add origin ../server.git
git push -q origin main
echo "tags on server after 'git push': $(git ls-remote --tags origin | wc -l)"
git push -q origin v1.10.0
git ls-remote --tags origin | awk '{print "on server:", $2}'
```

```text output
tags on server after 'git push': 0
on server: refs/tags/v1.10.0
on server: refs/tags/v1.10.0^{}
```

<Happened>
<Tr>
<En>After pushing `main`, the server had **0 tags**. `git push origin v1.10.0` sent that one. `refs/tags/v1.10.0^{}` isn't a second tag: `ls-remote` shows the tag object and, with `^{}`, the commit it points to ("peeled").</En>
<Ur>`main` push karne ke baad server par **0 tags** the. `git push origin v1.10.0` ne wo ek bheja. `refs/tags/v1.10.0^{}` doosra tag nahi: `ls-remote` tag object aur `^{}` ke saath wo commit dikhata hai jis ki taraf ye ishara karta hai ("peeled").</Ur>
</Tr>
</Happened>

</Step>

<Step title="Check out an old version">

<Tr>
<En>

`git switch --detach v1.1.0` (or `git checkout v1.1.0`) puts the files exactly as they were in that release, perfect for reproducing a customer's bug. You end up in **detached HEAD** because a tag isn't a branch; that's fine for looking around. To change things on top of an old release, create a branch: `git switch -c hotfix/1.1.1 v1.1.0`.

</En>
<Ur>

`git switch --detach v1.1.0` (ya `git checkout v1.1.0`) files bilkul waisi kar deta hai jaisi us release me thin, customer ka bug dohrane ke liye behtareen. Aap **detached HEAD** me hote hain kyun ke tag branch nahi; dekhne ke liye theek hai. Purani release ke upar tabdeeli ke liye branch banayen: `git switch -c hotfix/1.1.1 v1.1.0`.

</Ur>
</Tr>

```bash
cd shop
echo "now on main: VERSION=$(cat VERSION)"
git switch -q --detach v1.1.0
echo "at v1.1.0:   VERSION=$(cat VERSION)"
git status | head -1
git switch -q main
echo "back on main: VERSION=$(cat VERSION)"
```

```text output
now on main: VERSION=1.10.0
at v1.1.0:   VERSION=1.1.0
HEAD detached at v1.1.0
back on main: VERSION=1.10.0
```

<Happened>
<Tr>
<En>At the tag, `VERSION` showed `1.1.0` and `git status` said `HEAD detached at v1.1.0`. Switching back to `main` restored the latest files.</En>
<Ur>Tag par `VERSION` ne `1.1.0` dikhaya aur `git status` ne kaha `HEAD detached at v1.1.0`. Wapas `main` par jane se taaza files laut aayin.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Hotfix releases on an old version">

<Tr>
<En>

Customers on v1.1 need a security fix **now**, but `main` contains half-finished new features. Branch from the tag → fix → tag the PATCH version → bring the fix back into `main` (merge or cherry-pick). The fix must reach **both**, or the bug returns in the next normal release.

</En>
<Ur>

v1.1 wale customers ko security fix **abhi** chahiye, lekin `main` me adhoore naye features hain. Tag se branch → fix → PATCH version tag → fix wapas `main` me (merge ya cherry-pick). Fix **dono** jagah pahunchna zaroori hai, warna agli aam release me bug wapas aa jayega.

</Ur>
</Tr>

```bash
cd shop
git switch -q -c hotfix/1.1.1 v1.1.0
```

<Step title="git describe: a version for every build">

<Tr>
<En>

`git describe` names the current commit relative to the newest annotated tag: `v1.10.0-2-g3f2a1b9` means "2 commits after v1.10.0, at commit 3f2a1b9". Every build, even between releases, gets a unique, meaningful version for an "About" page, logs or Docker labels. Exactly on a tag it prints just the tag. `--dirty` adds `-dirty` when there are uncommitted changes; `--always` falls back to a hash if there are no tags.

</En>
<Ur>

`git describe` mojooda commit ko sab se naye annotated tag ke hawale se naam deta hai: `v1.10.0-2-g3f2a1b9` ka matlab "v1.10.0 ke 2 commits baad, commit 3f2a1b9 par". Har build ko, releases ke beech bhi, munfarid ba-maani version milta hai "About" page, logs ya Docker labels ke liye. Bilkul tag par ho to sirf tag chhaapta hai. `--dirty` uncommitted tabdeeliyon par `-dirty` jorta hai; `--always` tag na hon to hash deta hai.

</Ur>
</Tr>

```bash
git init -q d && cd d
git commit -q --allow-empty -m "Start"
git tag -a v2.0.0 -m "Release 2.0.0"
echo "on the tag:      $(git describe)"
git commit -q --allow-empty -m "Work 1"; git commit -q --allow-empty -m "Work 2"
git describe | sed -E 's/-g[0-9a-f]+$/-g<hash>/' | sed 's/^/2 commits later: /'
echo x > tmp.txt && git add tmp.txt
git describe --dirty | sed -E 's/-g[0-9a-f]+-/-g<hash>-/' | sed 's/^/with edits:      /'
```

```text output
on the tag:      v2.0.0
2 commits later: v2.0.0-2-g<hash>
with edits:      v2.0.0-2-g<hash>-dirty
```

<Happened>
<Tr>
<En>On the tag: just `v2.0.0`. Two commits later: `-2-g<hash>` (`g` stands for "git"). With a staged but uncommitted file, `--dirty` warned that this build doesn't match any commit exactly.</En>
<Ur>Tag par: sirf `v2.0.0`. Do commits baad: `-2-g<hash>` (`g` ka matlab "git"). Staged lekin uncommitted file ke saath `--dirty` ne khabardar kiya ke ye build kisi commit se bilkul nahi milta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Release notes from history">

<Tr>
<En>

A changelog lists what changed between two versions, so users know what's new, fixed, or might break. You can draft it from `git log v1.0.0..HEAD`, use GitHub's **Generate release notes** button (built from merged PRs), or tools like release-please and semantic-release. Teams using **Conventional Commits** (`feat:`, `fix:`, `feat!:` for breaking) can generate both the changelog and the next version number automatically.

</En>
<Ur>

Changelog do versions ke beech ki tabdeeliyon ki fehrist hai, taa ke users jaanen kya naya, kya theek, ya kya toot sakta hai. Aap ise `git log v1.0.0..HEAD` se bana sakte hain, GitHub ka **Generate release notes** button (merged PRs se), ya release-please aur semantic-release jaise tools. **Conventional Commits** (`feat:`, `fix:`, toorne wali ke liye `feat!:`) wali teams changelog aur agla version number dono khud bana sakti hain.

</Ur>
</Tr>

```bash
git init -q notes && cd notes
git commit -q --allow-empty -m "chore: initial setup"
git tag -a v1.0.0 -m "v1.0.0"
for m in "feat: add coupon codes" "fix: correct cart rounding" "docs: update README" "feat: add wishlist" "fix: handle empty cart"; do
  git commit -q --allow-empty -m "$m"
done
echo "## What's new since $(git describe --tags --abbrev=0)"
echo "### Features";  git log --format='- %s' --grep='^feat' v1.0.0..HEAD | sed 's/feat: //'
echo "### Bug fixes"; git log --format='- %s' --grep='^fix'  v1.0.0..HEAD | sed 's/fix: //'
```

```text output
## What's new since v1.0.0
### Features
- add wishlist
- add coupon codes
### Bug fixes
- handle empty cart
- correct cart rounding
```

<Happened>
<Tr>
<En>`--grep='^feat'` picked messages starting with `feat`, and `sed` removed the prefix. The `docs:` commit was left out. Two new features and no breaking changes, so by SemVer the next release is **v1.1.0**.</En>
<Ur>`--grep='^feat'` ne `feat` se shuru hone wale messages chune, aur `sed` ne shuruat hata di. `docs:` wala commit chhor diya gaya. Do naye features aur koi toorne wali tabdeeli nahi, isliye SemVer ke mutabiq agli release **v1.1.0** hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="GitHub Releases">

<Tr>
<En>

A GitHub Release is built on a tag and adds a title, release notes and optional **assets** (binaries, zip files, installers, checksums). It's the public "download and read what changed" page, and users can "Watch → Releases" to be notified. Create one under Repo → **Releases** → **Draft a new release**, or with the GitHub CLI:

```text
gh release create v1.1.0 \
  --title "Shop 1.1.0" \
  --generate-notes \
  ./dist/shop-1.1.0.zip ./dist/SHA256SUMS
```

This runs against GitHub (not offline): it creates the release from the existing tag, writes notes from merged PRs, and uploads two files. Mark test versions as **pre-release**, attach checksums so users can verify downloads, and automate it in GitHub Actions when a tag is pushed.

</En>
<Ur>

GitHub Release tag par banta hai aur title, release notes aur ikhtiyari **assets** (binaries, zip files, installers, checksums) jorta hai. Ye "download karo aur dekho kya badla" wala public safha hai, aur users "Watch → Releases" se ittila le sakte hain. Repo → **Releases** → **Draft a new release** me banayen, ya GitHub CLI se:

```text
gh release create v1.1.0 \
  --title "Shop 1.1.0" \
  --generate-notes \
  ./dist/shop-1.1.0.zip ./dist/SHA256SUMS
```

Ye GitHub par chalta hai (offline nahi): maujood tag se release banata hai, merged PRs se notes likhta hai, aur do files upload karta hai. Test versions ko **pre-release** mark karein, checksums lagayen taa ke users downloads ki tasdeeq kar saken, aur tag push par GitHub Actions me automate karein.

</Ur>
</Tr>

</Step>

<Step title="Move or delete a tag (only before it's public)">

<Tr>
<En>

You tagged the wrong commit **before** anyone used it: `git tag -d name` deletes it locally, `git push origin --delete name` on the server. `git tag -f` moves a tag, but anyone who already fetched it keeps the **old** one, because Git doesn't update existing tags on fetch.

</En>
<Ur>

Aap ne kisi ke istemal se **pehle** ghalat commit tag kar diya: `git tag -d name` local mitata hai, `git push origin --delete name` server par. `git tag -f` tag hilata hai, lekin jo pehle fetch kar chuke unke paas **purana** rehta hai, kyun ke Git fetch par maujood tags update nahi karta.

</Ur>
</Tr>

```bash
git init -q del && cd del
git commit -q --allow-empty -m "Good commit"
git commit -q --allow-empty -m "Broken commit"
git tag -a v3.0.0 -m "Release 3.0.0"          # oops: tagged the broken commit
git tag -d v3.0.0 | sed -E 's/ \(was .*//'
git tag -a v3.0.0 -m "Release 3.0.0" HEAD~1    # tag the right commit
git log -1 --format='v3.0.0 now points to: %s' v3.0.0
```

```text output
Deleted tag 'v3.0.0'
v3.0.0 now points to: Good commit
```

<Happened>
<Tr>
<En>The tag landed on the broken commit, so we deleted it and re-created it on `HEAD~1`, the good commit.</En>
<Ur>Tag toote commit par laga, isliye hum ne mita kar `HEAD~1`, achhe commit, par dobara banaya.</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>Once a version is public, **never** change it. Release a new PATCH version instead. Changing a published tag breaks reproducibility and trust, and looks exactly like a supply-chain attack.</En>
<Ur>Version public ho jaye to use **kabhi** na badlein. Is ke bajaye naya PATCH version release karein. Published tag badalna dobara banane ki salahiyat aur bharosa torta hai, aur bilkul supply-chain attack jaisa lagta hai.</Ur>
</Tr>
</Callout>

</Step>

## Common mistakes

<Compare>
<Bad title="Lightweight tag, pushed with everything">

```text
git tag v2.0.0          # no tagger, date or message
git push --tags         # also sends every private local tag
```

</Bad>
<Good title="Annotated tag, pushed on purpose">

```text
git tag -a v2.0.0 -m "Release 2.0.0: new checkout"
git push origin v2.0.0
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting to push the tag:** the release exists only on your laptop.
- **Moving or re-using a published version number:** users and caches keep the old one, and trust is lost.
- **Breaking changes in a MINOR or PATCH release:** users upgrade "safely" and their app breaks.
- **Tagging an untested commit** instead of the exact commit that passed CI.
- **Hotfix only on the release branch:** the bug returns because the fix never reached `main`.
- **Sorting versions as text:** `v1.10.0` appears before `v1.9.0`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Tag push karna bhoolna:** release sirf aap ke laptop par hai.
- **Published version number hilana ya dobara istemal:** users aur caches purana rakhte hain, aur bharosa jata hai.
- **MINOR ya PATCH release me toorne wali tabdeeli:** users "mehfooz" upgrade karte hain aur app toot jati hai.
- **Bina test commit tag karna** us commit ke bajaye jo CI se pass hua.
- **Hotfix sirf release branch par:** bug wapas aata hai kyun ke fix `main` tak nahi pahuncha.
- **Versions ko text ki tarah sort karna:** `v1.10.0` `v1.9.0` se pehle aata hai.

</Ur>
</Tr>

<DeepDive title="Real world: production deploys from tags">

Alex's team ships an exchange platform. Every merge to `main` deploys to **staging**; production deploys happen only from tags. When the team lead runs `git tag -a v4.7.0 -m "Release 4.7.0"` and `git push origin v4.7.0`, a GitHub Actions workflow builds the Docker image `exchange-api:4.7.0`, generates release notes from merged PRs, creates a GitHub Release and deploys to production. Two days later a rounding bug appears in withdrawals. The team branches `hotfix/4.7.1` from `v4.7.0`, fixes only that bug, tags `v4.7.1` and deploys it, without shipping the unfinished features already on `main`. If 4.7.1 had misbehaved, rollback would simply be "deploy image 4.7.0 again". The fix is also merged back into `main`.

</DeepDive>

<DeepDive title="Security lens">

A tag says "this is the official code of version X". Attackers who can move or create tags can make you ship their code under a trusted version number.

- **Protect tags:** use GitHub tag rulesets so only release managers or CI can create, update or delete `v*` tags.
- **Signed tags** (`git tag -s v1.0.0`) prove who created the release; verify with `git tag -v v1.0.0` (see **Commit Signing and Protected Branches**).
- **Never change a published tag.** In the March 2025 `tj-actions/changed-files` incident, version tags of a popular GitHub Action were repointed to malicious code.
- **Pin dependencies by commit SHA**, not by a tag that could move: in GitHub Actions, `uses: actions/checkout@<full-commit-sha>` is safer than `@v4`.
- **Publish checksums** (`SHA256SUMS`) and ideally signatures or provenance attestations (Sigstore/SLSA) with release assets.
- **Security advisories** depend on accurate versions ("affected: below 1.1.1, fixed in 1.1.1"); `git tag --contains <fix-commit>` gives that answer precisely.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a branch and a tag?">
Both are references to commits. A branch moves forward automatically when you commit on it and represents an ongoing line of work. A tag is meant to stay fixed on one commit and marks a specific point such as a release.
</QA>

<QA q="What is the difference between lightweight and annotated tags?">
A lightweight tag is only a name pointing directly to a commit. An annotated tag is a separate Git object that stores the tagger, date and message and can be cryptographically signed. Annotated tags are recommended for releases and are used by git describe by default.
</QA>

<QA q="Explain Semantic Versioning.">
Versions have the form MAJOR.MINOR.PATCH. PATCH is incremented for backward-compatible bug fixes, MINOR for backward-compatible new features with PATCH reset to zero, and MAJOR for incompatible changes with MINOR and PATCH reset to zero. Pre-release labels such as 2.0.0-beta.1 mark versions that are not yet stable.
</QA>

<QA q="Why does git push not push my tags, and how do you push them?">
Git pushes tags only when asked, so that local or experimental tags are not shared accidentally. You push a specific tag with git push origin v1.2.0, annotated tags reachable from the pushed commits with git push --follow-tags, or all tags with git push --tags.
</QA>

<QA q="How do you ship an urgent fix for an older release?">
Create a branch from the release tag, for example git switch -c hotfix/1.4.1 v1.4.0, commit only the fix, test it, create and push an annotated tag v1.4.1 and release it. Then merge or cherry-pick the fix into main so it is included in future releases.
</QA>

</DeepDive>
