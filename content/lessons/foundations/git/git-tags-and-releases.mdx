<Callout type="tip" title="In one minute">
A **tag** is a permanent name for one specific commit, like **`v1.4.0`**. A branch moves forward with every commit; a tag **never moves**. Use **annotated tags** (`git tag -a v1.4.0 -m "..."`) for releases. They store who created the tag, when, and a message. Version numbers follow **Semantic Versioning**: **MAJOR.MINOR.PATCH**. Bump MAJOR for breaking changes, MINOR for new features and PATCH for bug fixes. Tags are **not pushed automatically**: use `git push origin v1.4.0`. On GitHub, a **Release** is a tag plus release notes and downloadable files. Tag pushes often trigger the deployment pipeline.
</Callout>

## Start from zero

<Callout type="analogy">
Think of a **book with editions**. The author keeps editing the manuscript every day (commits on `main`). When a version is printed and sold, it gets a fixed label: "**2nd edition, 2026**". The manuscript keeps changing, but the 2nd edition is always exactly the same text. Anyone can say "on page 40 of the 2nd edition" and everyone sees the same page. A **tag** is that edition label for your code. A **GitHub Release** is the edition **plus** the "what's new in this edition" page and the printed copies (downloadable files).
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Tag** | A fixed name pointing to one commit | `v2.1.0` |
| **Lightweight tag** | Just a name → commit, nothing else | `git tag test-point` |
| **Annotated tag** | A full Git object with tagger, date and message | `git tag -a v2.1.0 -m "..."` |
| **Release** | A version you ship to users | "Version 2.1.0" |
| **Semantic Versioning (SemVer)** | MAJOR.MINOR.PATCH numbering rules | `2.1.0` → `2.1.1` |
| **Changelog / release notes** | List of what changed in a version | "Added dark mode" |
| **Pre-release** | A test version before the final one | `v3.0.0-beta.1` |
| **Hotfix** | An urgent fix released on top of an old version | `v2.1.1` |

## What is it?

Tags live in `.git/refs/tags/`, just like branches live in `.git/refs/heads/`. The difference is behaviour. When you commit, the current **branch** moves to the new commit. **Tags stay where you put them**. That makes them perfect for marking "this exact code is version 2.1.0".

```text
          v1.0.0          v1.1.0                 ← tags (fixed)
            │               │
 A ── B ── C ── D ── E ── F ── G ── H            ← commits
                                    │
                                   main          ← branch (moves on every commit)
```

## Why does it matter?

- **Reproducibility:** "Which code is running in production?" → "v2.1.0" → `git checkout v2.1.0` shows exactly that code.
- **Bug reports:** a user on v1.9 reports a bug. You can check out v1.9 and reproduce it.
- **Rollbacks:** deploying the previous version is "deploy tag v2.0.3".
- **Automation:** CI/CD pipelines commonly build and publish when a `v*` tag is pushed.
- **Communication:** version numbers tell users how risky an upgrade is.
- **Package managers** (npm, PyPI, Docker image tags, Go modules) all rely on version numbers.

## When and where do you use it?

- Every time you ship a version: a website deploy, a mobile app build, a library release, a Docker image.
- Marking important points: "before database migration", "submitted to client".
- On GitHub, under **Releases** (right side of the repo page).

## Concepts one by one

### 1. Lightweight tags

<Explain>
<What>
A lightweight tag is only a name pointing to a commit, like a branch that never moves. It stores no author, date or message.
</What>
<Why>
Quick personal bookmarks.
</Why>
<When>
Temporary or private markers, e.g. "before-refactor". **Not** for official releases.
</When>
<Where>
`git tag <name>` (no `-a`, `-m` or `-s`).
</Where>
<How>
It tags the current commit (HEAD) unless you give a commit: `git tag name <commit>`.
</How>
</Explain>

```bash
git config --global user.name "Moiz Rehman"; git config --global user.email "moiz@example.com"; git config --global init.defaultBranch main
git init -q shop && cd shop
echo "v1 code" > app.js && git add . && git commit -qm "First version of shop"
git tag before-refactor
git tag
git cat-file -t before-refactor
cat .git/refs/tags/before-refactor | wc -c | sed 's/$/ bytes: just a commit hash/'
```

```text output
before-refactor
commit
41 bytes: just a commit hash
```

Line by line:

- `git tag before-refactor` creates the tag on the current commit.
- `git tag` with no arguments lists all tags.
- `git cat-file -t before-refactor` prints the **type** of object the tag name points to. It is `commit`: a lightweight tag has no object of its own.
- The tag file contains only the 40-character commit hash plus a newline, like a branch file.

### 2. Annotated tags: the right choice for releases

<Explain>
<What>
An annotated tag is a real Git **tag object**. It contains the commit it points to, the tagger's name and email, the date and a message. It can also be signed.
</What>
<Why>
Releases need a record of who released it, when and why. Tools like `git describe` and GitHub use annotated tags by default.
</Why>
<When>
Every official release.
</When>
<Where>
`git tag -a v1.0.0 -m "Release 1.0.0"`. `git show v1.0.0` displays it.
</Where>
<How>
Tag the commit that was tested and approved, normally the latest commit on `main` (or a release branch) after the release PR is merged.
</How>
</Explain>

```bash
cd shop
git tag -a v1.0.0 -m "Release 1.0.0: first public version"
git cat-file -t v1.0.0
git show v1.0.0 --no-patch | sed -E 's/^Date: .*/Date:   <date>/; s/^commit [0-9a-f]+/commit <hash>/'
```

```text output
tag
tag v1.0.0
Tagger: Moiz Rehman <moiz@example.com>
Date:   <date>

Release 1.0.0: first public version

commit <hash>
Author: Moiz Rehman <moiz@example.com>
Date:   <date>

    First version of shop
```

Line by line:

- `git cat-file -t v1.0.0` now prints `tag`. The annotated tag is its own object.
- The top part (`Tagger`, `Date`, message) belongs to the **tag**.
- The bottom part is the **commit** the tag points to.

| | Lightweight | Annotated |
| --- | --- | --- |
| Stores tagger, date, message | No | Yes |
| Can be signed (GPG/SSH) | No | Yes |
| Used by `git describe` by default | No | Yes |
| Use for | Private bookmarks | Releases |

### 3. Semantic Versioning (SemVer)

<Explain>
<What>
A version number **MAJOR.MINOR.PATCH** where each part has a meaning.
</What>
<Why>
Users can tell from the number alone whether an upgrade is safe.
</Why>
<When>
Choosing the number of every new release.
</When>
<Where>
npm, PyPI, Cargo, Go modules, Docker images, mobile apps and APIs. Git tags usually add a `v` prefix: `v2.4.1`.
</Where>
<How>
Bump the leftmost part that applies and reset the parts to its right to 0. Pre-releases add a suffix: `3.0.0-beta.2`.
</How>
</Explain>

| Change | Example | Version bump | Meaning for users |
| --- | --- | --- | --- |
| Bug fix, no new features | Fix wrong cart total | 2.4.1 → **2.4.2** (PATCH) | Safe to upgrade |
| New feature, old code still works | Add coupon codes | 2.4.2 → **2.5.0** (MINOR) | Safe, new things available |
| Breaking change | Remove old API endpoint | 2.5.0 → **3.0.0** (MAJOR) | May need code changes |
| Test version before 3.0.0 | | **3.0.0-beta.1** | Not for production |

A small shell function that bumps a version, to see the rules in action:

```bash
bump() {                       # usage: bump <version> <major|minor|patch>
  IFS=. read -r major minor patch <<< "${1#v}"
  case $2 in
    major) echo "v$((major + 1)).0.0" ;;
    minor) echo "v$major.$((minor + 1)).0" ;;
    patch) echo "v$major.$minor.$((patch + 1))" ;;
  esac
}
bump v2.4.1 patch
bump v2.4.1 minor
bump v2.4.1 major
```

```text output
v2.4.2
v2.5.0
v3.0.0
```

Line by line:

- `${1#v}` removes the leading `v` from the first argument: `v2.4.1` → `2.4.1`.
- `IFS=. read -r major minor patch` splits on dots into three variables.
- A minor bump resets PATCH to 0, and a major bump resets MINOR and PATCH to 0.

`0.x.y` versions mean "early development, anything may change". `1.0.0` is the first stable public API.

### 4. Listing and finding tags

<Explain>
<What>
Commands to see which tags exist and which commits they point to.
</What>
<Why>
"What is our latest release?", "Which v2 versions exist?"
</Why>
<When>
Before tagging a new release, when investigating a bug in a version.
</When>
<Where>
`git tag -l "v2.*"` (pattern), `git tag --sort=-v:refname` (newest version first), `git tag --contains <commit>` (which releases include this commit?).
</Where>
<How>
Use `-v:refname` sorting so `v1.10.0` correctly comes after `v1.9.0`. Plain text sorting gets this wrong.
</How>
</Explain>

```bash
cd shop
for v in 1.1.0 1.2.0 1.9.0 1.10.0; do
  echo "$v" > VERSION && git add . && git commit -qm "Prepare $v"
  git tag -a "v$v" -m "Release $v"
done
echo "--- text order (wrong for versions):"; git tag -l 'v1.*' | tr '\n' ' '; echo
echo "--- version order, newest first:";   git tag -l 'v1.*' --sort=-v:refname | tr '\n' ' '; echo
echo "--- latest release: $(git describe --tags --abbrev=0)"
```

```text output
--- text order (wrong for versions):
v1.0.0 v1.1.0 v1.10.0 v1.2.0 v1.9.0 
--- version order, newest first:
v1.10.0 v1.9.0 v1.2.0 v1.1.0 v1.0.0 
--- latest release: v1.10.0
```

Notice that text order puts `v1.10.0` before `v1.2.0`, because the character "1" sorts before "2". Version sorting understands that 10 is bigger than 9.

### 5. Which release contains a commit?

<Explain>
<What>
`git tag --contains <commit>` lists every tag whose history includes that commit.
</What>
<Why>
"We fixed the payment bug in commit `a1b2c3d`. Which versions have the fix? Do customers on v1.2 need to upgrade?"
</Why>
<When>
Security advisories, support tickets, release notes.
</When>
<Where>
`git tag --contains <hash>`, or the other way round: `git log v1.2.0..v1.9.0` lists commits added between two releases.
</Where>
<How>
Combine with `git log --grep` to find the commit by its message first.
</How>
</Explain>

```bash
cd shop
fix=$(git log --format=%h --grep="Prepare 1.2.0")
echo "releases that include 'Prepare 1.2.0':"; git tag --contains "$fix" --sort=v:refname | tr '\n' ' '; echo
echo "commits between v1.1.0 and v1.9.0:"; git log --format='  %s' v1.1.0..v1.9.0
```

```text output
releases that include 'Prepare 1.2.0':
v1.2.0 v1.9.0 v1.10.0 
commits between v1.1.0 and v1.9.0:
  Prepare 1.9.0
  Prepare 1.2.0
```

### 6. Pushing tags

<Explain>
<What>
`git push` does **not** send tags. You push them explicitly.
</What>
<Why>
So that experimental local tags don't end up on the server by accident.
</Why>
<When>
Right after creating a release tag.
</When>
<Where>
`git push origin v1.10.0` (one tag, recommended), `git push --follow-tags` (pushes commits plus the annotated tags that point to them), `git push --tags` (every local tag, including private lightweight ones, so be careful).
</Where>
<How>
Many pipelines start when a tag matching `v*` arrives on GitHub, so pushing the tag often **is** the release.
</How>
</Explain>

```bash
cd shop
git init -q --bare ../server.git && git remote add origin ../server.git
git push -q origin main
echo "tags on server after 'git push': $(git ls-remote --tags origin | wc -l)"
git push -q origin v1.10.0
git ls-remote --tags origin | awk '{print "on server:", $2}'
```

```text output
tags on server after 'git push': 0
on server: refs/tags/v1.10.0
on server: refs/tags/v1.10.0^{}
```

Line by line:

- After pushing `main`, the server still has **0 tags**.
- `git push origin v1.10.0` sends that one tag.
- `refs/tags/v1.10.0^{}` is not a second tag. `ls-remote` shows the annotated tag object and, with `^{}`, the commit it points to ("peeled").

### 7. Checking out an old version

<Explain>
<What>
`git switch --detach v1.0.0` (or `git checkout v1.0.0`) puts the files exactly as they were in that release.
</What>
<Why>
Reproduce a bug a customer sees on an old version, or compare behaviour.
</Why>
<When>
Support and debugging.
</When>
<Where>
You end up in **detached HEAD** because a tag is not a branch. That is fine for looking around.
</Where>
<How>
To make changes on top of an old release (a hotfix), create a branch: `git switch -c hotfix/1.0.1 v1.0.0`.
</How>
</Explain>

```bash
cd shop
echo "now on main: VERSION=$(cat VERSION)"
git switch -q --detach v1.1.0
echo "at v1.1.0:   VERSION=$(cat VERSION)"
git status | head -1
git switch -q main
echo "back on main: VERSION=$(cat VERSION)"
```

```text output
now on main: VERSION=1.10.0
at v1.1.0:   VERSION=1.1.0
HEAD detached at v1.1.0
back on main: VERSION=1.10.0
```

### 8. Hotfix releases on an old version

<Explain>
<What>
Fix a bug in an old release without shipping everything that happened on `main` since.
</What>
<Why>
Customers on v1.1 need the security fix **now**, but `main` contains half-finished v2 features.
</Why>
<When>
Urgent fixes, long-term-support (LTS) versions.
</When>
<Where>
Branch from the tag → fix → tag the PATCH version → merge or cherry-pick the fix back into `main` so it isn't lost.
</Where>
<How>
The fix must reach **both** the hotfix release and `main`. Otherwise the bug comes back in the next normal release.
</How>
</Explain>

```bash
cd shop
git switch -q -c hotfix/1.1.1 v1.1.0
echo "sanitize input" > security.js && git add . && git commit -qm "Fix XSS in search"
git tag -a v1.1.1 -m "Release 1.1.1: security fix"
git switch -q main
git cherry-pick -x hotfix/1.1.1 >/dev/null
echo "v1.1.1 contains: $(git log --format=%s -1 v1.1.1)"
echo "main also has the fix: $(git log --format=%s -1 main)"
git tag -l 'v1.1*' --sort=v:refname | tr '\n' ' '; echo
```

```text output
v1.1.1 contains: Fix XSS in search
main also has the fix: Fix XSS in search
v1.1.0 v1.1.1 v1.10.0 
```

```text
 v1.1.0 ──► hotfix/1.1.1 ── "Fix XSS" ◄── v1.1.1 (shipped to old customers)
    │                           │ cherry-pick -x
    ▼                           ▼
   ... ── v1.10.0 ── main ── "Fix XSS" (next normal release has it too)
```

### 9. `git describe`: a version for every build

<Explain>
<What>
`git describe` names the current commit relative to the newest annotated tag: `v1.10.0-2-g3f2a1b9` means "2 commits after v1.10.0, at commit 3f2a1b9".
</What>
<Why>
Every build, even between releases, gets a unique and meaningful version string to show on an "About" page or in logs.
</Why>
<When>
CI builds, Docker image labels, app version displays.
</When>
<Where>
`git describe --tags`, `--always` (falls back to a hash if there are no tags), `--dirty` (adds `-dirty` when there are uncommitted changes).
</Where>
<How>
Exactly on a tag, it prints just the tag: `v1.10.0`.
</How>
</Explain>

```bash
git init -q d && cd d
git commit -q --allow-empty -m "Start"
git tag -a v2.0.0 -m "Release 2.0.0"
echo "on the tag:      $(git describe)"
git commit -q --allow-empty -m "Work 1"; git commit -q --allow-empty -m "Work 2"
git describe | sed -E 's/-g[0-9a-f]+$/-g<hash>/' | sed 's/^/2 commits later: /'
echo x > tmp.txt && git add tmp.txt
git describe --dirty | sed -E 's/-g[0-9a-f]+-/-g<hash>-/' | sed 's/^/with edits:      /'
```

```text output
on the tag:      v2.0.0
2 commits later: v2.0.0-2-g<hash>
with edits:      v2.0.0-2-g<hash>-dirty
```

### 10. Release notes from history

<Explain>
<What>
A changelog lists what changed between two versions. You can generate a first draft from commit messages.
</What>
<Why>
Users and teammates need to know what's new, what's fixed and what might break.
</Why>
<When>
Every release.
</When>
<Where>
`git log v1.0.0..v1.1.0`, GitHub's **Generate release notes** button (built from merged PRs), or tools like release-please and semantic-release.
</Where>
<How>
Teams using **Conventional Commits** (`feat:`, `fix:`, `feat!:` for breaking) can generate both the changelog and the next version number automatically.
</How>
</Explain>

```bash
git init -q notes && cd notes
git commit -q --allow-empty -m "chore: initial setup"
git tag -a v1.0.0 -m "v1.0.0"
for m in "feat: add coupon codes" "fix: correct cart rounding" "docs: update README" "feat: add wishlist" "fix: handle empty cart"; do
  git commit -q --allow-empty -m "$m"
done
echo "## What's new since $(git describe --tags --abbrev=0)"
echo "### Features";  git log --format='- %s' --grep='^feat' v1.0.0..HEAD | sed 's/feat: //'
echo "### Bug fixes"; git log --format='- %s' --grep='^fix'  v1.0.0..HEAD | sed 's/fix: //'
```

```text output
## What's new since v1.0.0
### Features
- add wishlist
- add coupon codes
### Bug fixes
- handle empty cart
- correct cart rounding
```

Two new features and no breaking changes, so by SemVer the next release is **v1.1.0**.

### 11. GitHub Releases

<Explain>
<What>
A GitHub Release is built on a tag and adds a title, release notes and optional **assets**: binaries, zip files, installers and checksums.
</What>
<Why>
It is the public "download and read what changed" page for each version. Users can "Watch → Releases" to be notified.
</Why>
<When>
Libraries, CLI tools, desktop and mobile apps, and any project users download.
</When>
<Where>
Repo → **Releases** → **Draft a new release**, or the GitHub CLI: `gh release create v1.1.0 --generate-notes ./dist/app.zip`.
</Where>
<How>
Mark test versions as **pre-release**. Attach checksums (`sha256sum`) so users can verify downloads. Most teams automate this in GitHub Actions when a tag is pushed.
</How>
</Explain>

```text
gh release create v1.1.0 \
  --title "Shop 1.1.0" \
  --generate-notes \
  ./dist/shop-1.1.0.zip ./dist/SHA256SUMS
```

This runs against GitHub (not offline): it creates the release from the existing tag `v1.1.0`, writes notes from the merged PRs, and uploads two files.

### 12. Moving or deleting a tag

<Explain>
<What>
`git tag -d name` deletes a local tag. `git push origin --delete name` deletes it on the server.
</What>
<Why>
You tagged the wrong commit **before** anyone used it.
</Why>
<When>
Only immediately, before the release was published or downloaded.
</When>
<Where>
`git tag -f` moves a tag, but others who already fetched it keep the **old** one. Git doesn't update existing tags on fetch.
</Where>
<How>
Once a version is public, **never** change it. Release a new PATCH version instead. Changing a published tag breaks reproducibility and trust, and looks exactly like a supply-chain attack.
</How>
</Explain>

```bash
git init -q del && cd del
git commit -q --allow-empty -m "Good commit"
git commit -q --allow-empty -m "Broken commit"
git tag -a v3.0.0 -m "Release 3.0.0"          # oops: tagged the broken commit
git tag -d v3.0.0 | sed -E 's/ \(was .*//'
git tag -a v3.0.0 -m "Release 3.0.0" HEAD~1    # tag the right commit
git log -1 --format='v3.0.0 now points to: %s' v3.0.0
```

```text output
Deleted tag 'v3.0.0'
v3.0.0 now points to: Good commit
```

## Hands-on

A complete release cycle: develop, tag, push the tag, hotfix, and list releases.

```bash
git init -q --bare remote.git
git init -q app && cd app && git remote add origin ../remote.git
echo "1.0.0" > VERSION && git add . && git commit -qm "feat: first release"
git tag -a v1.0.0 -m "Release 1.0.0" && git push -q origin main v1.0.0
echo "1.1.0" > VERSION && git commit -qam "feat: add search"
git tag -a v1.1.0 -m "Release 1.1.0" && git push -q --follow-tags origin main
git switch -q -c hotfix/1.1.1 v1.1.0
echo "1.1.1" > VERSION && git commit -qam "fix: search crash on empty query"
git tag -a v1.1.1 -m "Release 1.1.1" && git push -q origin v1.1.1
git switch -q main && git merge -q --no-edit hotfix/1.1.1 >/dev/null
echo "releases on server:"; git ls-remote --tags origin | grep -v '\^{}' | awk '{sub("refs/tags/","",$2); print "  " $2}'
echo "latest: $(git describe --tags --abbrev=0)"
```

```text output
releases on server:
  v1.0.0
  v1.1.0
  v1.1.1
latest: v1.1.1
```

Line by line:

- `git push -q origin main v1.0.0` pushes the branch and the tag in one command.
- `--follow-tags` pushes the commits plus any annotated tags pointing at them, so `v1.1.0` went up automatically.
- The hotfix is tagged `v1.1.1` and merged back into `main`, so the fix isn't lost.
- `grep -v '\^{}'` hides the "peeled" lines so each tag appears once.

## Real-world example

Moiz's team ships an exchange platform. Every merge to `main` deploys to **staging**. Production deploys only happen from tags: when the team lead runs `git tag -a v4.7.0 -m "Release 4.7.0"` and `git push origin v4.7.0`, a GitHub Actions workflow builds the Docker image `exchange-api:4.7.0`, generates release notes from merged PRs, creates a GitHub Release, and deploys to production. Two days later a rounding bug appears in withdrawals. The team branches `hotfix/4.7.1` from `v4.7.0`, fixes only that bug, tags `v4.7.1` and deploys it, without shipping the unfinished features already on `main`. If 4.7.1 had misbehaved, rolling back would simply be "deploy image 4.7.0 again". The fix is also merged back into `main`.

## Common mistakes

- **Using lightweight tags for releases.** No author, date or message, and `git describe` ignores them by default.
- **Forgetting to push the tag.** The release exists only on your laptop.
- **`git push --tags`** pushing random private tags to the shared repo.
- **Moving or re-using a published version number.** Users and caches keep the old one, and trust is lost.
- **Breaking changes in a MINOR or PATCH release.** Users upgrade "safely" and their app breaks.
- **Tagging an untested commit** instead of the exact commit that passed CI.
- **Hotfix only on the release branch.** The bug returns in the next version because the fix never reached `main`.
- **Sorting versions as text.** `v1.10.0` appears before `v1.9.0`.

## Security lens

<Callout type="security">
A tag says "this is the official code of version X". Attackers who can move or create tags can make you ship their code under a trusted version number.
</Callout>

- **Protect tags:** use GitHub tag rulesets so only release managers or CI can create, update or delete `v*` tags.
- **Signed tags** (`git tag -s v1.0.0`) prove who created the release. Verify them with `git tag -v v1.0.0` (see **Commit Signing and Protected Branches**).
- **Never change a published tag.** Tag changes are a known supply-chain attack technique: in the March 2025 `tj-actions/changed-files` incident, version tags of a popular GitHub Action were repointed to malicious code.
- **Pin dependencies by commit SHA**, not by a tag that could move. In GitHub Actions, `uses: actions/checkout@<full-commit-sha>` is safer than `@v4`.
- **Publish checksums** (`SHA256SUMS`) and ideally signatures or provenance attestations (Sigstore/SLSA) with release assets, so users can verify them.
- **Security advisories** depend on accurate versions: "affected: < 1.1.1, fixed in 1.1.1". `git tag --contains <fix-commit>` gives that answer precisely.

## Interview questions

<QA q="What is the difference between a branch and a tag?">
Both are references to commits. A branch moves forward automatically when you commit on it and represents an ongoing line of work. A tag is meant to stay fixed on one commit and marks a specific point such as a release.
</QA>

<QA q="What is the difference between lightweight and annotated tags?">
A lightweight tag is only a name pointing directly to a commit. An annotated tag is a separate Git object that stores the tagger, date and message and can be cryptographically signed. Annotated tags are recommended for releases and are used by git describe by default.
</QA>

<QA q="Explain Semantic Versioning.">
Versions have the form MAJOR.MINOR.PATCH. PATCH is incremented for backward-compatible bug fixes, MINOR for backward-compatible new features with PATCH reset to zero, and MAJOR for incompatible changes with MINOR and PATCH reset to zero. Pre-release labels such as 2.0.0-beta.1 mark versions that are not yet stable.
</QA>

<QA q="Why does git push not push my tags, and how do you push them?">
Git pushes tags only when asked so that local or experimental tags are not shared accidentally. You push a specific tag with git push origin v1.2.0, push annotated tags reachable from the pushed commits with git push --follow-tags, or all tags with git push --tags.
</QA>

<QA q="How do you ship an urgent fix for an older release?">
Create a branch from the release tag, for example git switch -c hotfix/1.4.1 v1.4.0, commit only the fix, test it, create and push an annotated tag v1.4.1 and release it. Then merge or cherry-pick the fix into main so it is included in future releases.
</QA>

## Key terms

<Terms>
  <Term name="Tag">Fixed reference to a specific commit.</Term>
