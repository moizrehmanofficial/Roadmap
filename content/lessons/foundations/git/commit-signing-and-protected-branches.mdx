<BigIdea>
<Tr>
<En>
The **author name and email on a commit are just text**: anyone can commit as anyone. A **signed commit** carries a cryptographic signature made with **your private key**, and Git or GitHub checks it with your **public key**; if it matches, GitHub shows **Verified**. **Protected branches** are rules on `main`: no direct pushes, changes arrive through PRs with **reviews** and **passing checks**, and **force pushes and deletion are blocked**. Signing proves **who** made a change; protection controls **how** it reaches `main`. You need both.
</En>
<Ur>
**Commit par likhne wale ka naam aur email sirf text hain**: koi bhi kisi ke naam se commit kar sakta hai. **Signed commit** me **aap ki private key** se bana cryptographic signature hota hai, aur Git ya GitHub use **aap ki public key** se check karta hai; mil jaye to GitHub **Verified** dikhata hai. **Protected branches** `main` par qawaid hain: seedha push nahi, tabdeeliyan PRs ke zariye **reviews** aur **pass checks** ke saath aati hain, aur **force push aur mitana band** hai. Signing sabit karti hai tabdeeli **kis ne** ki; protection control karti hai wo `main` tak **kaise** pahunche. Dono chahiye.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **Anyone can fake authorship.** Without signatures, a malicious commit can look like it came from your most trusted maintainer.
- **Supply-chain attacks** target source code: attackers who steal a token push code that gets built and shipped to thousands of users.
- **Mistakes, not just attacks:** a tired developer force-pushes to `main` and wipes a day of commits; protection makes that impossible.
- **Compliance:** SOC 2, ISO 27001 and SLSA expect reviewed, traceable, tamper-evident changes.
- **Job skill:** DevSecOps and platform roles configure branch protection, rulesets and signing for whole organisations.

</En>
<Ur>

- **Koi bhi likhne wala ban sakta hai.** Signatures ke baghair bad-niyat commit aap ke sab se bharose wale maintainer ka lag sakta hai.
- **Supply-chain attacks** source code ko nishana banate hain: token chura kar hamla awar code push karte hain jo build ho kar hazaron users tak pahunchta hai.
- **Sirf hamle nahi, ghaltiyan bhi:** thaka hua developer `main` par force-push kar ke din bhar ke commits mita deta hai; protection ye namumkin banati hai.
- **Compliance:** SOC 2, ISO 27001 aur SLSA review shuda, traceable, cherh chhaar pakarne wali tabdeeliyan maangte hain.
- **Naukri ka hunar:** DevSecOps aur platform roles poori organisations ke liye branch protection, rulesets aur signing set karte hain.

</Ur>

- **Where:** your Git config (signing), GitHub **Settings → Rules → Rulesets** or **Branches** (protection), and a `CODEOWNERS` file.

## Picture it

<Tr>
<En>

A commit's author name is like the **"From:" written on an envelope**: anyone can write any name there. A **signature** is a **wax seal made with a personal stamp** only you own (your private key). Everyone has a picture of your seal (your public key), so they can check whether the seal is genuine and whether the envelope was opened. **Protected branches** are the rules of the **office mailroom**: nobody drops letters straight into the official archive (`main`). Every letter goes through the front desk, is read by a second person (review), passes the scanner (CI checks), and once archived nobody can remove or replace it (no force push or deletion).

</En>
<Ur>

Commit par likhne wale ka naam lifafe par likhe **"From:"** jaisa hai: koi bhi koi bhi naam likh sakta hai. **Signature** ek **zaati mohar se bani laakh ki seal** hai jo sirf aap ke paas hai (private key). Sab ke paas aap ki seal ki tasveer hai (public key), isliye wo check kar sakte hain ke seal asli hai aur lifafa khola to nahi gaya. **Protected branches** **daftar ke daak khaane** ke qawaid hain: koi seedha sarkari record (`main`) me khat nahi daalta. Har khat front desk se guzarta hai, doosra shakhs parhta hai (review), scanner se guzarta hai (CI checks), aur record me jaane ke baad koi use hata ya badal nahi sakta (force push ya mitana nahi).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="The problem: authorship is just text">

<Tr>
<En>

`user.name` and `user.email` are whatever you configured, and Git **doesn't check them**: it's a content tracker, not an identity system. GitHub links a commit to an account only by matching the email, and even shows that account's avatar if someone else made the commit. The fix is cryptography: only the real owner holds the private key that can create a valid signature.

</En>
<Ur>

`user.name` aur `user.email` wahi hain jo aap ne set kiye, aur Git **inhe check nahi karta**: ye mawad track karne wala tool hai, shanakht ka nizaam nahi. GitHub commit ko account se sirf email mila kar jorta hai, aur agar kisi aur ne commit kiya ho tab bhi us account ki tasveer dikhata hai. Hal cryptography hai: sirf asli maalik ke paas wo private key hai jo durust signature bana sakti hai.

</Ur>
</Tr>

```bash
git init -q demo && cd demo
git -c user.name="Jordan Blake" -c user.email="ceo@example.com" \
    commit -q --allow-empty -m "Totally legit commit"
git log -1 --format='Author: %an <%ae>%nSigned: %G?'
```

```text output
Author: Jordan Blake <ceo@example.com>
Signed: N
```

<Happened>
<Tr>
<En>

- `git -c user.name=… -c user.email=…` set a name and email **for this one command only**: we pretended to be the company's CEO.
- Git happily created the commit. No password, no check, and `%an <%ae>` makes it look real.
- `%G?` prints the signature status: `N` = **No signature**, the only honest clue that this commit proves nothing.

Pushed to GitHub, it would even show the CEO's profile picture. Only a signature can prove who made a commit.

</En>
<Ur>

- `git -c user.name=… -c user.email=…` ne **sirf is ek command ke liye** naam aur email set kiya: hum company ke CEO ban gaye.
- Git ne khushi se commit bana diya. Koi password nahi, koi check nahi, aur `%an <%ae>` ise asli dikhata hai.
- `%G?` signature ki haalat chhaapta hai: `N` = **koi signature nahi**, wahi ek imaandaar ishara ke ye commit kuch sabit nahi karta.

GitHub par push hota to CEO ki profile tasveer bhi dikhti. Sirf signature sabit kar sakta hai commit kis ne banaya.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Keys: private and public">

<Tr>
<En>

A **key pair** is two linked files. The **private key** creates signatures and stays secret on your computer. The **public key** can only check signatures, so you share it freely (on GitHub). Anyone can verify, but only the owner can sign; even GitHub never needs your private key. Git supports **SSH keys** (simplest), **GPG/OpenPGP keys** (traditional) and **X.509 certificates** (big companies; also Sigstore's gitsign).

</En>
<Ur>

**Key pair** do jure hue files hain. **Private key** signatures banati hai aur aap ke computer par raaz rehti hai. **Public key** sirf signatures check kar sakti hai, isliye use khule aam share karte hain (GitHub par). Koi bhi verify kar sakta hai, lekin sign sirf maalik; GitHub ko bhi kabhi aap ki private key nahi chahiye. Git **SSH keys** (sab se aasaan), **GPG/OpenPGP keys** (riwayati) aur **X.509 certificates** (bari companies; Sigstore ka gitsign bhi) support karta hai.

</Ur>
</Tr>

```bash
ssh-keygen -q -t ed25519 -N "" -C "alex@example.com" -f ./signing_key
ls signing_key*
cut -d' ' -f1,3 signing_key.pub
head -1 signing_key
```

```text output
signing_key
signing_key.pub
ssh-ed25519 alex@example.com
-----BEGIN OPENSSH PRIVATE KEY-----
```

<Happened>
<Tr>
<En>

- `ssh-keygen -t ed25519` created a modern key pair; `-C` added a comment (your email) and `-f` chose the file name.
- `-N ""` means **no passphrase**, used only so this example runs without a prompt. On your real computer, set a passphrase.
- `signing_key` is private; `signing_key.pub` is public. The public key is one line: type `ssh-ed25519`, key data (hidden with `cut`), and the comment.
- The private file starts with `BEGIN OPENSSH PRIVATE KEY`. **Never** commit, paste or share it.

</En>
<Ur>

- `ssh-keygen -t ed25519` ne jadeed key pair banaya; `-C` ne tabsira (aap ki email) jora aur `-f` ne file ka naam chuna.
- `-N ""` ka matlab **koi passphrase nahi**, sirf is liye ke misaal baghair sawal ke chale. Apne asli computer par passphrase zaroor lagayen.
- `signing_key` private hai; `signing_key.pub` public. Public key ek line hai: qisam `ssh-ed25519`, key data (`cut` se chhupaya), aur tabsira.
- Private file `BEGIN OPENSSH PRIVATE KEY` se shuru hoti hai. Ise **kabhi** commit, paste ya share na karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Configure Git to sign">

<Tr>
<En>

Four settings make Git sign every commit and tag with your SSH key, so you never have to remember `-S`: `gpg.format ssh`, `user.signingkey <path to .pub>`, `commit.gpgsign true`, `tag.gpgsign true`. The names say "gpg" for historical reasons; with `gpg.format ssh`, Git uses `ssh-keygen` to sign.

</En>
<Ur>

Chaar settings Git ko har commit aur tag aap ki SSH key se sign karwati hain, taa ke `-S` yaad na rakhna pade: `gpg.format ssh`, `user.signingkey <.pub ka path>`, `commit.gpgsign true`, `tag.gpgsign true`. Naamon me "gpg" tareekhi wajah se hai; `gpg.format ssh` ke saath Git sign karne ke liye `ssh-keygen` istemal karta hai.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"
git config --global user.email "alex@example.com"
git config --global init.defaultBranch main
git config --global gpg.format ssh
git config --global user.signingkey "$PWD/signing_key.pub"
git config --global commit.gpgsign true
git config --global tag.gpgsign true
git config --global --get-regexp '^(gpg|user\.signingkey|commit|tag)' | sed "s#$PWD#~#"
```

```text output
user.signingkey ~/signing_key.pub
gpg.format ssh
commit.gpgsign true
tag.gpgsign true
```

<Happened>
<Tr>
<En>`user.signingkey` points to the **public** key; Git uses it to find the matching private key (with an SSH agent, the private key can stay inside the agent or a hardware key). The last command lists the settings as stored, grouped by section. On a real machine you'd use `~/.ssh/id_ed25519.pub`, and `user.email` must match a **verified email on your GitHub account** for the Verified badge.</En>
<Ur>`user.signingkey` **public** key ki taraf ishara karta hai; Git is se milti private key dhoondhta hai (SSH agent ke saath private key agent ya hardware key ke andar reh sakti hai). Aakhri command settings ko waise dikhati hai jaise save hain, section ba section. Asli machine par `~/.ssh/id_ed25519.pub` hoga, aur Verified badge ke liye `user.email` **aap ke GitHub account ki tasdeeq shuda email** se milni chahiye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Sign and verify commits">

<Tr>
<En>

With signing on, `git commit` adds a signature to the commit. To verify locally, Git needs to know **which key belongs to which person**: for SSH that's the **allowed signers** file (GitHub uses the keys uploaded to each account instead). Check with `git verify-commit`, `git log --show-signature`, or `%G?` codes: `G` good, `N` none, `B` bad (content changed), `U` valid but key not trusted, `E` can't check.

</En>
<Ur>

Signing on ho to `git commit` commit me signature jorta hai. Local verify ke liye Git ko jaanna hai **kaunsi key kis shakhs ki hai**: SSH ke liye ye **allowed signers** file hai (GitHub is ke bajaye har account par upload keys istemal karta hai). `git verify-commit`, `git log --show-signature`, ya `%G?` codes se check karein: `G` achha, `N` koi nahi, `B` bura (mawad badla), `U` durust lekin key par bharosa nahi, `E` check nahi ho saka.

</Ur>
</Tr>

```bash
echo "alex@example.com $(cat signing_key.pub)" > allowed_signers
git config --global gpg.ssh.allowedSignersFile "$PWD/allowed_signers"
git init -q shop && cd shop
echo "app" > app.js && git add . && git commit -qm "Add app"
git log -1 --format='status=%G?  signer=%GS  message=%s'
git verify-commit HEAD 2>&1 | sed -E 's/SHA256:[A-Za-z0-9+\/]+/SHA256:<fingerprint>/'
```

```text output
status=G  signer=alex@example.com  message=Add app
Good "git" signature for alex@example.com with ED25519 key SHA256:<fingerprint>
```

<Happened>
<Tr>
<En>The `allowed_signers` file has one line per trusted person (`email key-type key-data`); teams often keep it in the repo or CI. The commit was signed automatically, `%G?` is `G` and `%GS` names the signer. `git verify-commit` printed a readable result (`sed` hides the fingerprint, which differs for every key).</En>
<Ur>`allowed_signers` file me har bharose wale shakhs ki ek line hai (`email key-type key-data`); teams aksar ise repo ya CI me rakhti hain. Commit khud sign hua, `%G?` `G` hai aur `%GS` sign karne wale ka naam deta hai. `git verify-commit` ne parhne laayiq nateeja diya (`sed` fingerprint chhupata hai, jo har key ka alag hota hai).</Ur>
</Tr>
</Happened>

</Step>

<Step title="What a signature protects: tampering">

<Tr>
<En>

The signature covers the **whole commit object**: tree (all files), parent, author, committer and message. Change one character and it no longer matches, which makes signed history **tamper-evident**, not just "attributed". Below we copy a signed commit, change only its message, and keep the old signature, exactly what an attacker editing history would do.

</En>
<Ur>

Signature **poore commit object** ko dhaanpta hai: tree (saari files), parent, author, committer aur message. Ek harf badlo aur ye nahi milta, jis se signed tareekh me **cherh chhaar pakri jati hai**, sirf naam nahi lagta. Neeche hum signed commit copy karte hain, sirf message badalte hain, aur purana signature rakhte hain, bilkul wahi jo tareekh badalne wala hamla awar karega.

</Ur>
</Tr>

```bash
cd shop
fake=$(git cat-file commit HEAD | sed 's/^Add app$/Add app and send passwords to evil.example/' | git hash-object -t commit -w --stdin)
git log -1 --format='original: %G?  %s' HEAD
git log -1 --format='tampered: %G?  %s' "$fake"
git verify-commit "$fake" >/dev/null 2>&1 || echo "verify-commit failed (exit code $?)"
```

```text output
original: G  Add app
tampered: B  Add app and send passwords to evil.example
verify-commit failed (exit code 1)
```

<Happened>
<Tr>
<En>

- `git cat-file commit HEAD` printed the raw commit, including its `gpgsig` block; `sed` changed only the message.
- `git hash-object -w` stored the edited text as a new commit. Creating a commit needs no key, but a **valid** signature for new content needs the private key, which an attacker doesn't have.
- The original stays `G`; the copy is `B` (**bad**): Git saw the content no longer matches what was signed.
- `git verify-commit` exited with code 1, which would fail a CI job.

</En>
<Ur>

- `git cat-file commit HEAD` ne kaccha commit chhaapa, `gpgsig` hisse samet; `sed` ne sirf message badla.
- `git hash-object -w` ne badla text naye commit ki shakal me save kiya. Commit banane ke liye key nahi chahiye, lekin naye mawad ka **durust** signature private key maangta hai, jo hamla awar ke paas nahi.
- Asal `G` raha; copy `B` (**bura**) hai: Git ne dekha mawad ab sign shuda se nahi milta.
- `git verify-commit` code 1 par nikla, jo CI job fail kar deta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Unsigned and unknown-key commits">

<Tr>
<En>

Being signed isn't enough: it must be signed by a key you **trust** for that person, or an attacker could just sign with their own key. An unsigned commit shows `N`; one signed by an untrusted key shows `U`. On GitHub: **Verified** (valid, key on the committer's account), **Unverified** (invalid or someone else's key), no badge (unsigned, unless vigilant mode is on). Policy: require `G` for everything merged to `main`.

</En>
<Ur>

Sirf signed hona kaafi nahi: us shakhs ki **bharose wali** key se sign hona chahiye, warna hamla awar apni key se sign kar deta. Unsigned commit `N` dikhata hai; na-bharose wali key se signed `U`. GitHub par: **Verified** (durust, committer ke account ki key), **Unverified** (ghalat ya kisi aur ki key), koi badge nahi (unsigned, jab tak vigilant mode on na ho). Policy: `main` me merge hone wali har cheez ke liye `G` lazmi.

</Ur>
</Tr>

```bash
cd shop
git commit -q --allow-empty --no-gpg-sign -m "Quick unsigned fix"
ssh-keygen -q -t ed25519 -N "" -f ../stranger_key
git -c user.signingkey="$PWD/../stranger_key.pub" commit -q --allow-empty -m "Signed by a stranger"
git log --format='%G?  %s'
```

```text output
U  Signed by a stranger
N  Quick unsigned fix
G  Add app
```

<Happened>
<Tr>
<En>`--no-gpg-sign` turned signing off for one commit (`N`). A second key, **not** in `allowed_signers`, signed another: the signature is mathematically fine, but the key isn't trusted, so it's `U`. Only "Add app" is fully good.</En>
<Ur>`--no-gpg-sign` ne ek commit ke liye signing band ki (`N`). Doosri key ne, jo `allowed_signers` me **nahi**, ek aur sign kiya: signature hisaabi tor par theek hai, lekin key par bharosa nahi, isliye `U`. Sirf "Add app" poori tarah achha hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Signed tags">

<Tr>
<En>

Releases are what users download and deploy, so a signed tag proves the release manager created this exact version. `git tag -s v1.0.0 -m "..."` signs (with `tag.gpgsign true`, `git tag -a` signs too), and `git tag -v v1.0.0` verifies. Signing the tag protects every commit before it as well, because the tag references the commit hash, which covers the whole history.

</En>
<Ur>

Releases wo hain jo users download aur deploy karte hain, isliye signed tag sabit karta hai ke release manager ne yahi version banaya. `git tag -s v1.0.0 -m "..."` sign karta hai (`tag.gpgsign true` ke saath `git tag -a` bhi), aur `git tag -v v1.0.0` verify karta hai. Tag sign karna us se pehle ke har commit ko bhi bachata hai, kyun ke tag commit hash ka hawala deta hai, jo poori tareekh ko dhaanpta hai.

</Ur>
</Tr>

```bash
cd shop
git tag -s v1.0.0 -m "Release 1.0.0"
git tag -v v1.0.0 >/dev/null 2>&1 && echo "tag v1.0.0: signature OK"
git cat-file tag v1.0.0 | grep -c 'BEGIN SSH SIGNATURE' | sed 's/^/signature blocks in tag object: /'
```

```text output
tag v1.0.0: signature OK
signature blocks in tag object: 1
```

<Happened>
<Tr>
<En>The tag verified, and the raw tag object contains one SSH signature block.</En>
<Ur>Tag verify ho gaya, aur kacche tag object me ek SSH signature hissa hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Set it up on GitHub">

<Tr>
<En>

GitHub doesn't read your local `allowed_signers` file; it uses keys attached to your account. Upload your public key as a **Signing Key**: GitHub → **Settings → SSH and GPG keys → New SSH key → Key type: Signing Key**, or with `gh`. The same SSH key can be added twice, once as an **Authentication key** (to push) and once as a **Signing key**.

```text
# on your own computer (not run here)
```

<Tr>

<Step title="Simulate protection with a server-side hook">

<Tr>
<En>

GitHub enforces rules on its servers. Self-hosted Git servers (and GitHub Enterprise Server) can do the same with a **pre-receive hook**: a script the server runs before accepting a push; a non-zero exit rejects the whole push. Because the check runs on the **server**, no client setting can skip it. It lives in `hooks/pre-receive` of the bare repo and receives one line per updated ref: `old-hash new-hash ref-name`. Ours enforces three rules on `main`: no deletion, no force push, every new commit signed by a trusted key.

</En>
<Ur>

GitHub apne servers par qawaid lagu karta hai. Self-hosted Git servers (aur GitHub Enterprise Server) **pre-receive hook** se yahi kar sakte hain: ek script jo server push qubool karne se pehle chalata hai; non-zero exit poori push radd kar deta hai. Kyun ke check **server** par chalta hai, client ki koi setting ise chhor nahi sakti. Ye bare repo ke `hooks/pre-receive` me hota hai aur har badle ref ki ek line paata hai: `old-hash new-hash ref-name`. Hamara hook `main` par teen qawaid lagata hai: mitana nahi, force push nahi, har naya commit bharose wali key se signed.

</Ur>
</Tr>

```bash
git init -q --bare server.git
git -C server.git config gpg.format ssh
git -C server.git config gpg.ssh.allowedSignersFile "$PWD/allowed_signers"
cat > server.git/hooks/pre-receive <<'HOOK'
#!/usr/bin/env bash
zero=0000000000000000000000000000000000000000
while read -r old new ref; do
  [ "$ref" = "refs/heads/main" ] || continue
  if [ "$new" = "$zero" ]; then echo "RULE: main cannot be deleted"; exit 1; fi
  if [ "$old" != "$zero" ] && ! git merge-base --is-ancestor "$old" "$new"; then
    echo "RULE: force pushes to main are blocked"; exit 1
  fi
  range=$([ "$old" = "$zero" ] && echo "$new" || echo "$old..$new")
  for c in $(git rev-list "$range"); do
    if [ "$(git log -1 --format=%G? "$c")" != "G" ]; then
      echo "RULE: commit $(git log -1 --format=%s "$c") is not signed by a trusted key"; exit 1
    fi
  done
done
HOOK
chmod +x server.git/hooks/pre-receive
ls -l server.git/hooks/pre-receive | cut -c1-10
```

```text output
-rwxr-xr-x
```

<Happened>
<Tr>
<En>

- The two `git -C server.git config` lines give the **server** the list of trusted signing keys.
- `<<'HOOK'` writes the script; the quotes stop the shell from expanding `$ref` while writing.
- All zeros means "doesn't exist": a new branch has `old` = zeros, a deleted one has `new` = zeros. Rule 1 rejects deleting `main`.
- Rule 2: `git merge-base --is-ancestor "$old" "$new"` checks the new commit **builds on** the old one; if not, it's a force push.
- Rule 3: every new commit from `git rev-list` must have `%G?` = `G`.
- `chmod +x` matters: Git silently ignores hooks that aren't executable.

</En>
<Ur>

- Do `git -C server.git config` lines **server** ko bharose wali signing keys ki fehrist deti hain.
- `<<'HOOK'` script likhta hai; quotes shell ko likhte waqt `$ref` phailane se rokte hain.
- Sab zeros ka matlab "maujood nahi": nayi branch me `old` = zeros, mitayi gayi me `new` = zeros. Rule 1 `main` mitana radd karta hai.
- Rule 2: `git merge-base --is-ancestor "$old" "$new"` check karta hai naya commit purane ke **upar bana** hai; warna force push hai.
- Rule 3: `git rev-list` ka har naya commit `%G?` = `G` hona chahiye.
- `chmod +x` zaroori hai: Git na-chalne wale hooks chupke se nazar andaz karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Compare>
<Bad title="Protect main, but let admins bypass">

```text
  require PR, 1 approval
```


</Good>

<Tr>
<En>

More mistakes to avoid:

- **Trusting the author name** in `git log` or on GitHub as proof of who wrote something.
- **Committing with an email that isn't on your GitHub account**, so commits show Unverified or aren't linked to you.
- **Uploading the key only as an Authentication key**: it must also be a **Signing key**.
- **No passphrase on the private key**: anyone who copies the file can sign as you.
- **Required checks that don't exist** (a renamed CI job), so PRs block forever, or optional checks that block nothing.
- **Forgetting release tags:** `main` is protected, but anyone can move `v2.0.0`. Protect `v*` tags too.
- **Squash or rebase merges on your machine** losing signatures. Let GitHub do the merge (it signs), or re-sign.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- `git log` ya GitHub par **likhne wale ke naam par bharosa** ke yahi saboot hai.
- **Aisi email se commit jo GitHub account par nahi**, jis se commits Unverified dikhen ya aap se na juren.
- **Key sirf Authentication key ke tor par upload**: **Signing key** bhi honi chahiye.
- **Private key par passphrase nahi**: file copy karne wala aap ban kar sign kar sakta hai.
- **Aise lazmi checks jo maujood hi nahi** (naam badla CI job), jis se PRs hamesha ruke rahen, ya ikhtiyari checks jo kuch nahi rokte.
- **Release tags bhoolna:** `main` protected hai, lekin koi bhi `v2.0.0` hila sakta hai. `v*` tags bhi protect karein.
- **Apni machine par squash ya rebase merge** jis se signatures kho jayen. Merge GitHub ko karne dein (wo sign karta hai), ya dobara sign karein.

</Ur>

<DeepDive title="Real world: the stolen token that went nowhere">

Alex's company runs a trading platform, so a malicious change could move real money. The security team creates an **organisation ruleset** for every repository: on `main` and `release/*`, a pull request with 2 approvals is required; new pushes dismiss old approvals; Code Owner review is required; CI tests, CodeQL and secret scanning must pass; commits must be signed; force pushes and deletions are blocked, **with no bypass even for admins**. `CODEOWNERS` routes `/payments` and `/.github/workflows` to the security team.

Months later, an attacker steals a developer's personal access token from a leaked `.env` file and tries to push a change to `main` that sends withdrawal data to an external server. The push is rejected: direct pushes aren't allowed. A pull request would need two approvals and the security team's review, and the commit isn't signed with the developer's signing key, which the attacker never had. The token is revoked, and nothing reached production.

</DeepDive>

<DeepDive title="Security lens">

Signing answers "who made this commit?"; branch protection answers "could it reach main without anyone else checking?" You need both, and neither replaces careful review.

- **A signature proves a key was used, not that the person meant it.** Malware on a laptop with an unlocked key makes validly signed commits. Use passphrases, an SSH agent with confirmation, or hardware keys (YubiKey, `ed25519-sk`) that need a physical touch.
- **Revoke and rotate** signing keys when a laptop is lost or someone leaves; old commits signed with removed keys then show as unverified.
- **Protect the protections:** limit who can change rulesets and repo settings, and review the **audit log** for rule changes and bypasses.
- **CI is part of the boundary:** changes to `.github/workflows/` can steal secrets, so require Code Owner review for that path.
- **Supply-chain frameworks** (SLSA, OpenSSF Scorecard) check exactly these controls; Scorecard can audit your repo automatically.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why should commits be signed? Isn't the author field enough?">
The author name and email are arbitrary text that anyone can set in their Git config, so they prove nothing. A signature is created with the signer's private key and verified with their public key, proving the commit was made by the holder of that key and that its content, including the tree, parents and message, has not been changed since signing.
</QA>

<QA q="How do you sign commits with an SSH key?">
Generate an SSH key, then configure Git with gpg.format set to ssh, user.signingkey pointing to the public key, and commit.gpgsign and tag.gpgsign set to true. Add the public key to GitHub as a signing key. Locally, verification uses an allowed signers file configured with gpg.ssh.allowedSignersFile, and git verify-commit or git log --show-signature check signatures.
</QA>

<QA q="What branch protection rules would you set on main?">
Require pull requests with one or two approvals, dismiss stale approvals on new pushes, require code owner review for sensitive paths, require the latest push to be approved by someone else, require passing status checks such as tests and security scans, require conversation resolution and optionally signed commits and linear history, block force pushes and deletions, and do not allow administrators to bypass the rules.
</QA>

<QA q="What is CODEOWNERS used for?">
CODEOWNERS maps file paths to the users or teams responsible for them. GitHub automatically requests their review on pull requests that change those paths, and with the require code owner review rule, the pull request cannot be merged without their approval. The last matching pattern takes precedence, and the CODEOWNERS file itself should be owned by a trusted team.
</QA>

<QA q="Does a Verified badge mean a commit is safe?">
No. It means the commit was signed with a key registered to that GitHub account and was not modified afterwards. The code can still contain bugs or malicious changes if the author's machine or key was compromised or the author is malicious, so review, automated checks and branch protection are still required.
</QA>

</DeepDive>
