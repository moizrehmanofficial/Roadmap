<BigIdea>
<Tr>
<En>
A **branch** is a movable pointer to a commit, so creating one is instant and free. **`git switch -c name`** creates a branch and moves you onto it; **`git merge other`** brings another branch's commits into the one you're on. If your branch hasn't moved since the other one split off, Git just slides the pointer forward: a **fast-forward**. If both moved, Git does a **three-way merge** and records a **merge commit** with two parents. A **squash merge** turns a whole branch into one tidy commit.
</En>
<Ur>
**Branch** ek commit ki taraf hilne wala pointer hai, isliye banana foran aur muft hai. **`git switch -c name`** branch bana kar aap ko us par le jata hai; **`git merge other`** doosri branch ke commits us branch me lata hai jis par aap hain. Agar aap ki branch doosri ke alag hone ke baad nahi hili, to Git bas pointer aage khiska deta hai: **fast-forward**. Agar dono hilin, to Git **three-way merge** karta hai aur do parents wala **merge commit** banata hai. **Squash merge** poori branch ko ek saaf commit bana deta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

**Branching** lets many lines of work exist at the same time; **merging** joins them back together. Because a branch is just a 41-byte file holding a commit hash, Git encourages you to create many short-lived branches.

```text
 fast-forward:   A ── B ── C          three-way merge:   A ── B ─────── M
                           ▲                               \           /
                    main, feature                           C ── D ───┘
                                                            (M has 2 parents)
```

</En>
<Ur>

**Branching** se kaam ki kai lines ek waqt me maujood reh sakti hain; **merging** unhe wapas jorti hai. Kyun ke branch sirf ek commit hash wali 41 byte ki file hai, Git aap ko bohot si chhoti umar ki branches banane ki targheeb deta hai.

```text
 fast-forward:   A ── B ── C          three-way merge:   A ── B ─────── M
                           ▲                               \           /
                    main, feature                           C ── D ───┘
                                                            (M has 2 parents)
```

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Without branches, everyone's unfinished work would be mixed together in one place. You could never ship today's bug fix, because yesterday's half-built feature is sitting in the same code. Branches let each piece of work wait in its own place until it's ready, and merging brings it in when it is.

- Features, fixes and experiments stay isolated until they're ready.
- Several people (and CI) can work in parallel.
- Releases can be stabilised on a branch while development continues.
- Pull requests are built on branches: no branches, no code review.

</En>
<Ur>

Branches ke baghair sab ka adhoora kaam ek hi jagah mila hota. Aap aaj ka bug fix kabhi ship na kar pate, kyun ke kal ka aadha bana feature usi code me pada hai. Branches har kaam ko tayyar hone tak apni jagah intezar karne deti hain, aur merging tayyar hone par use andar le aati hai.

- Features, fixes aur tajurbe tayyar hone tak alag rehte hain.
- Kai log (aur CI) saath saath kaam kar sakte hain.
- Release ko ek branch par mazboot kiya ja sakta hai jab ke development jari rahe.
- Pull requests branches par bante hain: branches nahi, to code review nahi.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- A new branch for **every** task, started from an up-to-date `main`.
- Merging mostly happens on GitHub or GitLab through pull requests, but you also merge locally: updating your branch from `main`, hotfixes, and experiments.

</En>
<Ur>

- **Har** kaam ke liye nayi branch, taaza `main` se shuru.
- Merging zyada tar GitHub ya GitLab par pull requests ke zariye hoti hai, lekin aap local bhi merge karte hain: apni branch ko `main` se update karna, hotfixes, aur tajurbe.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```text
git switch -c feature/about        # create + switch
git switch main                    # go back
git merge feature/about            # bring it in
git merge --squash feature/x       # all changes as one commit
git branch -d feature/about        # delete when merged
```

</En>
<Ur>

```text
git switch -c feature/about        # banao + jao
git switch main                    # wapas
git merge feature/about            # andar lao
git merge --squash feature/x       # saari tabdeeliyan ek commit me
git branch -d feature/about        # merge ke baad mitao
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

A **highway with side roads**. `main` is the highway. A branch is a side road where you can build something without blocking traffic. **Merging** connects your side road back to the highway. If nobody built anything on the highway meanwhile, your road simply **becomes** the next stretch of highway (fast-forward). If the highway also grew, you need a **junction** where both roads meet (a merge commit).

</En>
<Ur>

**Highway aur us ki side roads**. `main` highway hai. Branch ek side road hai jahan aap traffic roke baghair kuch bana sakte hain. **Merging** aap ki side road ko wapas highway se jorti hai. Agar is doran highway par kisi ne kuch nahi banaya, to aap ki sarak bas highway ka agla hissa **ban jati hai** (fast-forward). Agar highway bhi barh gaya, to aap ko ek **chauraha** chahiye jahan dono sarken milen (merge commit).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Create and switch branches">

<Tr>
<En>

`git switch -c name` creates a branch at the current commit and moves you onto it; `git switch name` moves to an existing one. Switching **changes your working files** to match that branch's latest commit. `git branch` lists local branches (`*` = current); `git branch -a` includes remote ones too.

</En>
<Ur>

`git switch -c name` mojooda commit par branch bana kar aap ko us par le jata hai; `git switch name` pehle se maujood branch par le jata hai. Switch karna aap ki **working files badal deta hai** taa ke wo us branch ke aakhri commit se milen. `git branch` local branches dikhata hai (`*` = mojooda); `git branch -a` remote wali bhi.

</Ur>
</Tr>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q site && cd site
echo "home" > index.html && git add . && git commit -qm "Add home page"
git switch -q -c feature/about
echo "about us" > about.html && git add . && git commit -qm "Add about page"
git branch
ls
git switch -q main
ls
```

```text output
* feature/about
  main
about.html
index.html
index.html
```

<Happened>
<Tr>
<En>

- The first line is the usual one-time setup; then `index.html` is committed on `main`.
- `git switch -c feature/about` created the branch **and** moved onto it, and `about.html` was committed **there**.
- On `feature/about`, `ls` showed both files.
- After `git switch main`, Git updated the folder to match `main`, so `about.html` left the folder. It's **not lost**: it's safely stored in the `feature/about` commit and comes back when you switch there again.

</En>
<Ur>

- Pehli line wahi ek dafa ki setup hai; phir `index.html` `main` par commit hui.
- `git switch -c feature/about` ne branch banayi **aur** us par le gaya, aur `about.html` **wahan** commit hui.
- `feature/about` par `ls` ne dono files dikhayin.
- `git switch main` ke baad Git ne folder `main` ke mutabiq kiya, isliye `about.html` folder se chali gayi. Wo **khoi nahi**: `feature/about` ke commit me mehfooz hai aur wahan wapas jane par aa jati hai.

</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>Before switching, commit or stash your changes. If uncommitted edits would be overwritten, Git refuses with "Your local changes would be overwritten by checkout".</En>
<Ur>Switch se pehle apni tabdeeliyan commit ya stash karein. Agar uncommitted tabdeeliyan mit sakti hon, to Git "Your local changes would be overwritten by checkout" keh kar inkaar kar deta hai.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Branch from a specific point">

<Tr>
<En>

`git switch -c name <start>` creates a branch from **any** commit, tag or branch. Without a start point, it starts at HEAD. Hotfixes start from the released version; bug investigations can start from an older state: `git switch -c hotfix/1.0.1 v1.0.0`, `git switch -c test HEAD~3`.

</En>
<Ur>

`git switch -c name <start>` **kisi bhi** commit, tag ya branch se branch banata hai. Start point na dein to HEAD se shuru hoti hai. Hotfixes release shuda version se shuru hote hain; bug ki tafteesh purani haalat se ho sakti hai: `git switch -c hotfix/1.0.1 v1.0.0`, `git switch -c test HEAD~3`.

</Ur>
</Tr>

```bash
cd site
git tag v1.0
echo "contact" > contact.html && git add . && git commit -qm "Add contact page"
git switch -q -c hotfix/typo v1.0
ls
git log --format=%s
git switch -q main
```

```text output
index.html
Add home page
```

<Happened>
<Tr>
<En>

- `git tag v1.0` put a permanent label on the current commit (more in **Git Tags and Releases**).
- `contact.html` was then committed on `main`, so `main` moved past `v1.0`.
- `hotfix/typo` was created **at the tag**, not at the latest `main`, so `ls` shows only `index.html`, and the log has only the first commit.

This is how you fix a bug in the version customers are running, without shipping unfinished new work.

</En>
<Ur>

- `git tag v1.0` ne mojooda commit par mustaqil label lagaya (mazeed **Git Tags and Releases** me).
- Phir `contact.html` `main` par commit hui, to `main` `v1.0` se aage nikal gayi.
- `hotfix/typo` **tag par** bani, taaza `main` par nahi, isliye `ls` sirf `index.html` dikhata hai, aur log me sirf pehla commit hai.

Isi tarah aap us version ka bug theek karte hain jo customers chala rahe hain, adhoora naya kaam ship kiye baghair.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fast-forward merge">

<Tr>
<En>

If the current branch has **no new commits** since the other branch started, there's nothing to combine: merging just moves the pointer forward. History stays a straight line with no extra commit, and Git prints `Fast-forward`. `git merge --ff-only branch` refuses unless a fast-forward is possible, a safe habit when updating `main`.

</En>
<Ur>

Agar doosri branch ke shuru hone ke baad mojooda branch par **koi naya commit nahi**, to jorne ko kuch nahi: merge bas pointer aage khiskata hai. Tareekh seedhi line rehti hai, koi izafi commit nahi, aur Git `Fast-forward` chhaapta hai. `git merge --ff-only branch` tab tak inkaar karta hai jab tak fast-forward mumkin na ho, `main` update karte waqt mehfooz aadat.

</Ur>
</Tr>

```bash
git init -q ff && cd ff
git commit -q --allow-empty -m "A"
git switch -q -c feature
git commit -q --allow-empty -m "B"
git commit -q --allow-empty -m "C"
git switch -q main
git merge feature | head -2 | sed -E 's/[0-9a-f]{7}\.\.[0-9a-f]{7}/<old>..<new>/'
git log --graph --format=%s
```

```text output
Updating <old>..<new>
Fast-forward
* C
* B
* A
```

```text
before:  A ← main          after:  A ← B ← C ← main, feature
          ↖
           B ← C ← feature  (main simply moves to C)
```

<Happened>
<Tr>
<En>

- `main` had `A`; `feature` added `B` and `C`; `main` got nothing new.
- `git merge feature` saw that `main` is an ancestor of `feature`, so it just moved `main` to `C`.
- The graph is a straight line with no merge commit.
- `--allow-empty` makes commits with no file changes, only to keep examples short.

</En>
<Ur>

- `main` par `A` tha; `feature` ne `B` aur `C` jore; `main` par kuch naya nahi aaya.
- `git merge feature` ne dekha ke `main` `feature` ki aabaa hai, isliye bas `main` ko `C` par khiska diya.
- Graph seedhi line hai, koi merge commit nahi.
- `--allow-empty` baghair file tabdeeli ke commit banata hai, sirf misaalen chhoti rakhne ke liye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Three-way merge and merge commits">

<Tr>
<En>

When **both** branches have new commits, Git compares three snapshots: the **merge base** (the last common commit), the tip of your branch, and the tip of the other branch. It combines the changes and records a **merge commit** with two parents. `git merge-base a b` shows the common ancestor. If both sides changed the **same lines**, Git stops with a **conflict** (covered in its own lesson).

</En>
<Ur>

Jab **dono** branches par naye commits hon, Git teen snapshots milata hai: **merge base** (aakhri mushtarka commit), aap ki branch ki nok, aur doosri branch ki nok. Wo tabdeeliyan jor kar do parents wala **merge commit** record karta hai. `git merge-base a b` mushtarka aabaa dikhata hai. Agar dono taraf ne **wahi lines** badlin, to Git **conflict** par ruk jata hai (is ka alag sabaq hai).

</Ur>
</Tr>

```bash
git init -q three && cd three
printf 'title\nbody\nfooter\n' > page.txt && git add . && git commit -qm "Base"
git switch -q -c feature
sed -i 's/title/Title v2/' page.txt && git commit -qam "Improve title"
git switch -q main
sed -i 's/footer/Footer 2026/' page.txt && git commit -qam "Update footer"
echo "merge base: $(git log -1 --format=%s "$(git merge-base main feature)")"
git merge -q --no-edit feature >/dev/null
cat page.txt
git log --graph --format=%s
echo "the merge commit has $(git log -1 --format=%p | wc -w) parents"
```

```text output
merge base: Base
Title v2
body
Footer 2026
*   Merge branch 'feature'
|\  
| * Improve title
* | Update footer
|/  
* Base
the merge commit has 2 parents
```

<Happened>
<Tr>
<En>

Both changes landed: the title came from `feature` and the footer from `main`. Git decided line by line:

| Line | Base | main (ours) | feature (theirs) | Result |
| --- | --- | --- | --- | --- |
| 1 | title | title | **Title v2** | Title v2 (only feature changed it) |
| 2 | body | body | body | body (nobody changed it) |
| 3 | footer | **Footer 2026** | footer | Footer 2026 (only main changed it) |

The rule: if only one side changed a line, take that change. If **both** changed the **same** line differently, that's a conflict. `%p` prints the merge commit's parent hashes, and `wc -w` counted 2.

</En>
<Ur>

Dono tabdeeliyan aa gayin: title `feature` se aur footer `main` se. Git ne line ba line faisla kiya:

| Line | Base | main (hamari) | feature (unki) | Nateeja |
| --- | --- | --- | --- | --- |
| 1 | title | title | **Title v2** | Title v2 (sirf feature ne badli) |
| 2 | body | body | body | body (kisi ne nahi badli) |
| 3 | footer | **Footer 2026** | footer | Footer 2026 (sirf main ne badli) |

Qaida: agar sirf ek taraf ne line badli, to wo tabdeeli lo. Agar **dono** ne **wahi** line alag alag badli, to conflict hai. `%p` merge commit ke parents ke hash chhaapta hai, aur `wc -w` ne 2 gine.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="--no-ff: always record the merge">

<Tr>
<En>

`git merge --no-ff` creates a merge commit **even when a fast-forward was possible**. The graph then shows clearly which commits belonged to which feature, and the whole feature can be undone in one step. GitHub's "Create a merge commit" button does this. The trade-off is more merge commits in the history.

</En>
<Ur>

`git merge --no-ff` merge commit banata hai **chahe fast-forward mumkin ho**. Phir graph saaf dikhata hai kaunse commits kis feature ke the, aur poora feature ek qadam me wapas liya ja sakta hai. GitHub ka "Create a merge commit" button yahi karta hai. Qeemat ye ke tareekh me merge commits zyada hote hain.

</Ur>
</Tr>

```bash
git init -q noff && cd noff
git commit -q --allow-empty -m "Start"
git switch -q -c feature/login && git commit -q --allow-empty -m "Login form" && git commit -q --allow-empty -m "Login API"
git switch -q main
git merge -q --no-ff -m "Merge feature/login" feature/login
git log --graph --format=%s
```

```text output
*   Merge feature/login
|\  
| * Login API
| * Login form
|/  
* Start
```

<Happened>
<Tr>
<En>`main` had no new commits, so a fast-forward **would** have worked. `--no-ff` forced a merge commit anyway, keeping the two login commits visibly grouped. Later, `git revert -m 1 <merge-commit>` can undo the whole feature in one go.</En>
<Ur>`main` par naye commits nahi the, isliye fast-forward **chal sakta** tha. `--no-ff` ne phir bhi merge commit banaya, aur dono login commits nazar aate group me rahe. Baad me `git revert -m 1 <merge-commit>` poora feature ek dafa me wapas le sakta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Squash merge">

<Tr>
<En>

`git merge --squash branch` puts **all** of a branch's changes into the staging area so you can commit them as **one** commit. `main` stays tidy, one commit per PR, even if the branch had fifteen "fix typo" commits. This is GitHub's very common "Squash and merge" button.

</En>
<Ur>

`git merge --squash branch` branch ki **saari** tabdeeliyan staging area me daal deta hai taa ke aap unhe **ek** commit bana saken. `main` saaf rehti hai, har PR ka ek commit, chahe branch par pandrah "fix typo" commits hon. Ye GitHub ka bohot aam "Squash and merge" button hai.

</Ur>
</Tr>

```bash
git init -q sq && cd sq
git commit -q --allow-empty -m "Start"
git switch -q -c feature/search
for m in "Add search box" "fix typo" "wip" "Add results list"; do echo "$m" >> search.txt; git add .; git commit -qm "$m"; done
git switch -q main
git merge -q --squash feature/search >/dev/null
git commit -qm "Add search (#42)"
git log --format=%s
echo "search.txt has $(wc -l < search.txt) lines"
```

```text output
Add search (#42)
Start
search.txt has 4 lines
```

<Happened>
<Tr>
<En>

- The loop made four commits on `feature/search`, including messy ones like "fix typo" and "wip".
- `--squash` applied all their changes but made **no commit** and recorded no merge (`>/dev/null` hid "Squash commit -- not updating HEAD").
- One clean commit, "Add search (#42)", went onto `main`; the messy commits never reached it.
- `search.txt` still has all 4 lines: the **content** is all there, only the separate history isn't.

</En>
<Ur>

- Loop ne `feature/search` par chaar commits banaye, "fix typo" aur "wip" jaise ganday commits samet.
- `--squash` ne un ki saari tabdeeliyan lagayin lekin **koi commit nahi** banaya aur merge record nahi kiya (`>/dev/null` ne "Squash commit -- not updating HEAD" chhupaya).
- Ek saaf commit, "Add search (#42)", `main` par gaya; ganday commits wahan kabhi nahi pahunche.
- `search.txt` me ab bhi chaaron lines hain: **mawad** poora hai, sirf alag alag tareekh nahi.

</Ur>
</Tr>
</Happened>

<Callout type="warning">
<Tr>
<En>After a squash merge, Git no longer sees the branch as merged, so `git branch -d` refuses. Delete it with `git branch -D` once you've checked the squash landed.</En>
<Ur>Squash merge ke baad Git branch ko merged nahi samajhta, isliye `git branch -d` inkaar karta hai. Squash ke pahunchne ki tasdeeq ke baad `git branch -D` se mitayen.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Which merge style? GitHub's three buttons">

<Tr>
<En>

GitHub offers three ways to merge a pull request, chosen per repository in **Settings → General → Pull Requests**. Each gives history a different shape. Many teams allow only squash, for a linear, readable `main`. Whatever you pick, stay consistent within a repo.

| Button | Result on `main` | Good for |
| --- | --- | --- |
| Create a merge commit | All branch commits + a merge commit | Keeping full detail |
| Squash and merge | One commit per PR | Clean, linear history (most common) |
| Rebase and merge | Branch commits replayed on top, no merge commit | Linear history with individual commits |

</En>
<Ur>

GitHub pull request merge karne ke teen tareeqe deta hai, jo har repository ke liye **Settings → General → Pull Requests** me chune jate hain. Har ek tareekh ko alag shakal deta hai. Bohot si teams sirf squash ki ijazat deti hain, seedhi aur parhne me aasaan `main` ke liye. Jo bhi chunein, ek repo me ek jaisa rakhein.

| Button | `main` par nateeja | Kis ke liye achha |
| --- | --- | --- |
| Create a merge commit | Branch ke saare commits + merge commit | Poori tafseel rakhna |
| Squash and merge | Har PR ka ek commit | Saaf, seedhi tareekh (sab se aam) |
| Rebase and merge | Branch ke commits upar dobara, koi merge commit nahi | Alag commits ke saath seedhi tareekh |

</Ur>
</Tr>

</Step>

<Step title="Rename, delete and clean up branches">

<Tr>
<En>

Old branches clutter the repo and confuse everyone, so clean up after a PR is merged. `git branch -m old new` renames, `git branch -d name` deletes a merged branch, and `-D` forces deletion. `git branch --merged main` lists the branches that are safe to delete.

</En>
<Ur>

Purani branches repo ko bhar deti hain aur sab ko uljhati hain, isliye PR merge hone ke baad safai karein. `git branch -m old new` naam badalta hai, `git branch -d name` merged branch mitata hai, aur `-D` zabardasti mitata hai. `git branch --merged main` wo branches dikhata hai jo mitana mehfooz hai.

</Ur>
</Tr>

```bash
git init -q clean && cd clean
git commit -q --allow-empty -m "Start"
git branch done-feature && git branch -m done-feature feature/done
git switch -q -c experiment && git commit -q --allow-empty -m "Unmerged idea" && git switch -q main
echo "merged into main:"; git branch --merged main | grep -v main
git branch -d experiment 2>&1 | head -1
git branch -d feature/done | sed -E 's/ \(was .*//'
```

```text output
merged into main:
  feature/done
error: the branch 'experiment' is not fully merged.
Deleted branch feature/done
```

<Happened>
<Tr>
<En>

- `git branch done-feature` created a branch **without** switching to it; `-m` renamed it to `feature/done`.
- `experiment` got a commit that is **not** on `main`.
- Only `feature/done` is fully in `main`, so only it appears under "merged".
- `-d experiment` refused ("not fully merged"): Git protects unmerged work. Use `-D` only if you really want to throw it away.

</En>
<Ur>

- `git branch done-feature` ne branch banayi **baghair** us par gaye; `-m` ne naam `feature/done` kiya.
- `experiment` ko aisa commit mila jo `main` par **nahi**.
- Sirf `feature/done` poori tarah `main` me hai, isliye sirf wahi "merged" me aayi.
- `-d experiment` ne inkaar kiya ("not fully merged"): Git unmerged kaam bachata hai. `-D` sirf tab jab waqai phenkna ho.

</Ur>
</Tr>
</Happened>

<Callout type="tip">
<Tr>
<En>On GitHub, turn on **Settings → General → Automatically delete head branches**, and locally run `git fetch --prune` now and then to remove `origin/*` references to branches already deleted on the server.</En>
<Ur>GitHub par **Settings → General → Automatically delete head branches** on karein, aur local kabhi kabhi `git fetch --prune` chalayen taa ke server par mit chuki branches ke `origin/*` references hat jayen.</Ur>
</Tr>
</Callout>

</Step>

<Step title="Branching models">

<Tr>
<En>

A **branching model** is a team's agreement on which branches exist and how work flows between them, so everyone knows where to branch from, where to merge, and what gets deployed. It's decided once per project. Start with GitHub Flow unless you have a clear reason not to.

| Model | Branches | Best for |
| --- | --- | --- |
| GitHub Flow | `main` + short feature branches | Web apps deployed continuously |
| Git Flow | `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` | Software with scheduled, versioned releases |
| Trunk-based | `main` + branches living hours, feature flags | Fast CI/CD teams |

</En>
<Ur>

**Branching model** team ka is baat par ittefaq hai ke kaunsi branches hongi aur kaam un ke darmiyan kaise chalega, taa ke sab jaanen kahan se branch banani hai, kahan merge karna hai, aur kya deploy hota hai. Ye har project me ek dafa tay hota hai. Jab tak koi saaf wajah na ho, GitHub Flow se shuru karein.

| Model | Branches | Kis ke liye behtar |
| --- | --- | --- |
| GitHub Flow | `main` + chhoti feature branches | Lagataar deploy hone wali web apps |
| Git Flow | `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` | Tay shuda, version wali releases wala software |

## Common mistakes

<Compare>
<Bad title="Branch from a stale main and force-delete">

```text
git switch -c feature/cart     # main wasn't pulled for a week
...
git branch -D feature/cart     # -D: unmerged work gone without a warning
```

</Bad>
<Good title="Fresh start, safe delete">

```text
git switch main && git pull
git switch -c feature/cart
...
git branch -d feature/cart     # refuses if anything isn't merged yet
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Switching branches with uncommitted changes**, then getting confused about which branch they belong to.
- **Long-lived branches** that diverge for weeks.
- **Merging `main` into a feature branch dozens of times**, creating noisy history (merge less often, but regularly, or rebase).
- **Never deleting merged branches.**

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Uncommitted tabdeeliyon ke saath branch badalna**, phir uljhan ke wo kis branch ki hain.
- **Lambi branches** jo hafton alag hoti jayen.
- **Feature branch me darjanon dafa `main` merge karna**, jis se tareekh shor wali ho (kam lekin baqaidagi se merge karein, ya rebase).
- **Merged branches kabhi na mitana.**

</Ur>
</Tr>

## Try it yourself

<Challenge title="One fast-forward, one real merge">

<Tr>
<En>
Create two branches from "Release 1", merge them one after the other, and see why the first merge is a fast-forward and the second creates a merge commit.
</En>
<Ur>
"Release 1" se do branches banayen, ek ke baad ek merge karein, aur dekhein pehla merge fast-forward kyun hai aur doosra merge commit kyun banata hai.
</Ur>
</Tr>

```bash
git init -q shop && cd shop
echo "v1" > app.txt && git add . && git commit -qm "Release 1"
for f in cart payments; do
  git switch -q -c "feature/$f" main
  echo "$f" > "$f.txt" && git add . && git commit -qm "Add $f"
done
git switch -q main
git merge -q --no-edit feature/cart        # fast-forward
git merge -q --no-edit feature/payments >/dev/null  # three-way: main moved

git log --graph --format=%s
```

<DeepDive title="Real world: one commit per change">

A SaaS team uses GitHub Flow with "Squash and merge" only. Each PR becomes exactly one commit on `main`, titled like "Add CSV export (#318)", and every commit on `main` is deployed automatically. When a deploy breaks something, they find the guilty PR in seconds (one commit per change) and revert just that commit. Branches are deleted automatically after merge, a repository setting, so `git branch -a` stays short.

</DeepDive>

<DeepDive title="Security lens">

Branches are where review happens. If someone can merge without review, branching gives no protection at all.

- Protect `main` and release branches: required reviews, required status checks, no force pushes, no deletion.
- **CODEOWNERS** makes sure security-sensitive paths (auth, CI config, infrastructure) are reviewed by the right people.
- **Squash merges hide individual commits:** reviewers must review the whole PR diff, not just the final title.
- Hotfix branches still go through review, even under time pressure; attackers like rushed emergency changes.
- Delete branches holding experiments with test credentials, and rotate those credentials.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a fast-forward merge and a three-way merge?">
A fast-forward happens when the current branch has no commits that the other branch lacks, so Git simply moves the branch pointer forward and no merge commit is created. A three-way merge happens when both branches have new commits; Git combines the changes using the merge base and both branch tips and creates a merge commit with two parents.
</QA>

<QA q="What does squash merging do, and what are its pros and cons?">
Squash merging combines all changes from a branch into a single new commit on the target branch. It keeps the main history linear and readable, with one commit per pull request, and makes reverting a feature easy. The downside is that the branch's individual commits are lost from main's history and Git no longer recognises the branch as merged.
</QA>

<QA q="Compare GitHub Flow and Git Flow.">
GitHub Flow uses a single long-lived main branch plus short-lived feature branches merged through pull requests, which suits continuously deployed applications. Git Flow adds a develop branch and release and hotfix branches to manage scheduled, versioned releases, at the cost of more complexity.
</QA>

</DeepDive>
