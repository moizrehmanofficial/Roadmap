<Callout type="tip" title="In one minute">
A **branch** is a movable pointer to a commit, so creating one is instant. **`git switch -c name`** creates and enters a branch; **`git merge other`** brings another branch's commits into the current one. If your branch has not moved since the other one split off, Git just slides the pointer forward — a **fast-forward**. If both moved, Git does a **three-way merge** (using the common ancestor) and creates a **merge commit** with two parents. **Squash merge** turns a whole branch into one commit. Teams usually follow **GitHub Flow**: short branches, PRs, merge to `main`.
</Callout>

## Start from zero

<Callout type="analogy">
A **road with side roads**. `main` is the highway. A branch is a side road where you can build something without blocking traffic. **Merging** connects your side road back to the highway. If nobody else built anything on the highway meanwhile, your road simply **becomes** the next stretch of highway (fast-forward). If the highway also grew, you need a **junction** where both roads meet (a merge commit).
</Callout>

### Words you need first

| Word | Simple meaning |
| --- | --- |
| **Branch** | A named pointer to a commit that moves when you commit |
| **Merge** | Combine the history of another branch into the current one |
| **Fast-forward** | Merge where Git only moves the pointer — no new commit |
| **Merge base** | The last commit two branches have in common |
| **Merge commit** | A commit with two parents that joins two lines of work |
| **Squash** | Combine many commits into one |
| **Stale branch** | A branch nobody uses any more |

## What is it?

Branching lets many lines of work exist at once; merging joins them back together. Because a branch is just a 41-byte file holding a commit hash, Git encourages creating many short-lived branches.

## Why does it matter?

Without branches, everyone's unfinished work would be mixed together in one place. You could never ship today's bug fix because yesterday's half-built feature is sitting in the same code. Branches let each piece of work wait in its own place until it is ready, and merging brings it in when it is.

- Features, fixes and experiments are isolated until they are ready.
- Several people (and CI) can work in parallel.
- Releases can be stabilised on a branch while development continues.
- Pull requests are built on branches — no branches, no code review.

## When and where do you use it?

- A new branch for every task, from up-to-date `main`.
- Merging happens mostly on GitHub/GitLab via pull requests, but you also merge locally (updating your branch from `main`, hotfixes).

## Concepts one by one

### 1. Creating and switching branches

<Explain>
<What>
`git switch -c name` creates a branch at the current commit and switches to it; `git switch name` switches to an existing one.
</What>
<Why>
Switching changes your working files to match that branch's latest commit.
</Why>
<When>
Starting work; moving between tasks.
</When>
<Where>
`git branch` lists local branches (`*` = current); `git branch -a` includes remote ones.
</Where>
<How>
Commit or stash your changes before switching — Git refuses if your edits would be overwritten.
</How>
</Explain>

```bash
git config --global user.name "Alex Carter"; git config --global user.email "alex@example.com"; git config --global init.defaultBranch main
git init -q site && cd site
echo "home" > index.html && git add . && git commit -qm "Add home page"
git switch -q -c feature/about
echo "about us" > about.html && git add . && git commit -qm "Add about page"
git branch
ls
git switch -q main
ls
```

```text output
* feature/about
  main
about.html
index.html
index.html
```

`about.html` disappears on `main` because it only exists on the other branch — nothing is lost.`about.html` disappears on `main` because it only exists on the other branch — nothing is lost.

Line by line:

- The first line is the usual one-time setup (name, email, default branch `main`).
- `git init -q site && cd site` creates a new repo, and the next line makes the first commit with `index.html` on `main`.
- `git switch -q -c feature/about` creates the branch **and** switches to it.
- `about.html` is created and committed **on `feature/about`**.
- `git branch` shows both branches; `*` marks `feature/about` as current.
- `ls` on `feature/about` shows both files.
- `git switch -q main` switches back. Git updates the folder to match `main`'s latest commit, so `about.html` is removed from the folder. It is still safely stored in the `feature/about` commit and comes back when you switch to that branch again.

**Rule:** before switching, commit or stash your changes. If you have uncommitted edits that would be overwritten, Git refuses with "Your local changes would be overwritten by checkout".

### 2. Branching from a specific point

<Explain>
<What>
`git switch -c name <start>` creates a branch from any commit, tag or branch.
</What>
<Why>
Hotfixes start from the released version; experiments start from an older state.
</Why>
<When>
Fixing a released version, recreating a bug.
</When>
<Where>
`git switch -c hotfix/1.0.1 v1.0.0`, `git switch -c test HEAD~3`.
</Where>
<How>
Without a start point, the new branch starts at HEAD.
</How>
</Explain>

```bash
cd site
git tag v1.0
echo "contact" > contact.html && git add . && git commit -qm "Add contact page"
git switch -q -c hotfix/typo v1.0
ls
git log --format=%s
git switch -q main
```

```text output
index.html
Add home page
```

Line by line:

- `git tag v1.0` puts a permanent label on the current commit (see **Git Tags and Releases**).
- We then commit `contact.html` on `main`, so `main` has moved past `v1.0`.
- `git switch -q -c hotfix/typo v1.0` creates a branch **starting at the tag**, not at the latest `main`.
- `ls` shows only `index.html`: on this branch, the code is exactly as it was in v1.0, without `contact.html`.
- `git log` confirms the branch contains only the first commit.

This is how you fix a bug in the version customers are running, without shipping unfinished new work.

### 3. Fast-forward merge

<Explain>
<What>
If the current branch has no new commits since the other branch started, merging just moves the pointer forward.
</What>
<Why>
History stays a straight line; no extra commit.
</Why>
<When>
You merged quickly, or updated your branch first.
</When>
<Where>
Git prints `Fast-forward`.
</Where>
<How>
`git merge --ff-only branch` refuses to merge unless a fast-forward is possible — a safe habit when updating `main`.
</How>
</Explain>

```bash
git init -q ff && cd ff
git commit -q --allow-empty -m "A"
git switch -q -c feature
git commit -q --allow-empty -m "B"
git commit -q --allow-empty -m "C"
git switch -q main
git merge feature | head -2 | sed -E 's/[0-9a-f]{7}\.\.[0-9a-f]{7}/<old>..<new>/'
git log --graph --format=%s
```

```text output
Updating <old>..<new>
Fast-forward
* C
* B
* A
```

```text
before:  A ← main          after:  A ← B ← C ← main, feature
          ↖                         
           B ← C ← feature  (main simply moves to C)
```

Line by line:

- On `main` we make commit `A`, then create `feature` and add `B` and `C` there. `main` gets no new commits.
- `git merge feature` sees that `main` (at `A`) is an ancestor of `feature` (at `C`). Nothing needs combining, so Git just moves `main` forward to `C`. It prints `Updating <old>..<new>` and `Fast-forward`.
- `git log --graph` shows a straight line `A → B → C` with no merge commit.

`--allow-empty` creates commits without file changes. We use it in examples to keep things short; in real work every commit changes files.

### 4. Three-way merge and merge commits

<Explain>
<What>
When both branches have new commits, Git compares three snapshots: the **merge base**, the tip of your branch, and the tip of the other branch, then records a **merge commit** with two parents.
</What>
<Why>
It combines both sets of changes automatically when they touch different lines.
</Why>
<When>
Merging a PR into a `main` that has moved on.
</When>
<Where>
`git merge-base a b` shows the common ancestor.
</Where>
<How>
If both sides changed the **same lines**, Git stops with a **conflict** (next lessons).
</How>
</Explain>

```bash
git init -q three && cd three
printf 'title\nbody\nfooter\n' > page.txt && git add . && git commit -qm "Base"
git switch -q -c feature
sed -i 's/title/Title v2/' page.txt && git commit -qam "Improve title"
git switch -q main
sed -i 's/footer/Footer 2026/' page.txt && git commit -qam "Update footer"
echo "merge base: $(git log -1 --format=%s "$(git merge-base main feature)")"
git merge -q --no-edit feature >/dev/null
cat page.txt
git log --graph --format=%s
echo "the merge commit has $(git log -1 --format=%p | wc -w) parents"
```

```text output
merge base: Base
Title v2
body
Footer 2026
*   Merge branch 'feature'
|\  
| * Improve title
* | Update footer
|/  
* Base
the merge commit has 2 parents
```

Both changes landed: Git took the title from `feature` and the footer from `main`.Both changes landed: Git took the title from `feature` and the footer from `main`.

Line by line:

- `page.txt` starts with three lines: `title`, `body`, `footer`. That commit, "Base", is the **merge base**.
- On `feature`, `sed -i` changes line 1 to `Title v2` and we commit.
- On `main`, `sed -i` changes line 3 to `Footer 2026` and we commit.
- `git merge-base main feature` finds the last common commit: "Base".
- `git merge feature` compares three versions of each file:

| Line | Base | main (ours) | feature (theirs) | Result |
| --- | --- | --- | --- | --- |
| 1 | title | title | **Title v2** | Title v2 (only feature changed it) |
| 2 | body | body | body | body (nobody changed it) |
| 3 | footer | **Footer 2026** | footer | Footer 2026 (only main changed it) |

- The rule is simple: if only one side changed a line, take that side's change. If **both** sides changed the **same** line differently, that's a conflict.
- `git log -1 --format=%p` prints the parent hashes of the merge commit; `wc -w` counts them: 2 parents.

### 5. `--no-ff`: always record the merge

<Explain>
<What>
`git merge --no-ff` creates a merge commit even when a fast-forward was possible.
</What>
<Why>
The graph then shows clearly which commits belonged to which feature.
</Why>
<When>
Teams that like visible feature groups; GitHub's "Create a merge commit" button does this.
</When>
<Where>
`git merge --no-ff feature`.
</Where>
<How>
Trade-off: more merge commits in history.
</How>
</Explain>

```bash
git init -q noff && cd noff
git commit -q --allow-empty -m "Start"
git switch -q -c feature/login && git commit -q --allow-empty -m "Login form" && git commit -q --allow-empty -m "Login API"
git switch -q main
git merge -q --no-ff -m "Merge feature/login" feature/login
git log --graph --format=%s
```

```text output
*   Merge feature/login
|\  
| * Login API
| * Login form
|/  
* Start
```

Line by line:

- `feature/login` gets two commits; `main` gets none, so a fast-forward **would** be possible.
- `--no-ff` forces a merge commit anyway, with our message "Merge feature/login".
- The graph keeps the two login commits visibly grouped as one feature. Later, `git revert -m 1 <merge-commit>` can undo the whole feature in one step.

### 6. Squash merge

<Explain>
<What>
`git merge --squash branch` puts all of a branch's changes into the staging area so you can commit them as **one** commit.
</What>
<Why>
`main` stays tidy — one commit per PR, even if the branch had 15 "fix typo" commits.
</Why>
<When>
GitHub's "Squash and merge" option — very common.
</When>
<Where>
`git merge --squash feature && git commit -m "Add search (#42)"`.
</Where>
<How>
The individual commits are not in `main`'s history, and Git no longer sees the branch as merged — delete it with `git branch -D`.
</How>
</Explain>

```bash
git init -q sq && cd sq
git commit -q --allow-empty -m "Start"
git switch -q -c feature/search
for m in "Add search box" "fix typo" "wip" "Add results list"; do echo "$m" >> search.txt; git add .; git commit -qm "$m"; done
git switch -q main
git merge -q --squash feature/search >/dev/null
git commit -qm "Add search (#42)"
git log --format=%s
echo "search.txt has $(wc -l < search.txt) lines"
```

```text output
Add search (#42)
Start
search.txt has 4 lines
```

Line by line:

- On `feature/search` the loop makes four commits, including messy ones like "fix typo" and "wip".
- `git merge --squash feature/search` applies **all** the branch's changes to the working directory and staging area, but makes **no commit** and doesn't record a merge. (`>/dev/null` hides the message "Squash commit -- not updating HEAD".)
- `git commit -qm "Add search (#42)"` creates one clean commit.
- `git log` on `main` now shows only "Add search (#42)" and "Start": the messy commits never reach `main`.
- `search.txt` still has all 4 lines. The **content** of every commit is there, only the separate history isn't.

### 7. Which merge style? (GitHub's three buttons)

<Explain>
<What>
GitHub offers **Create a merge commit**, **Squash and merge**, and **Rebase and merge**.
</What>
<Why>
Each gives a different shape of history.
</Why>
<When>
Chosen per repository in Settings → General → Pull Requests.
</When>
<Where>
Many teams allow only squash, for a linear, readable `main`.
</Where>
<How>
Pick one style per repo and stay consistent.
</How>
</Explain>

| Button | Result on `main` | Good for |
| --- | --- | --- |
| Create a merge commit | All branch commits + a merge commit | Keeping full detail |
| Squash and merge | One commit per PR | Clean, linear history (most common) |
| Rebase and merge | Branch commits replayed on top, no merge commit | Linear history with individual commits |

### 8. Renaming, deleting and cleaning up branches

<Explain>
<What>
`git branch -m old new` renames, `git branch -d name` deletes a merged branch, `-D` forces deletion.
</What>
<Why>
Old branches clutter the repo and confuse everyone.
</Why>
<When>
After a PR is merged.
</When>
<Where>
`git branch --merged main` lists safe-to-delete branches; `git fetch --prune` removes references to remote branches already deleted.
</Where>
<How>
`-d` protects you: it refuses to delete unmerged work.
</How>
</Explain>

```bash
git init -q clean && cd clean
git commit -q --allow-empty -m "Start"
git branch done-feature && git branch -m done-feature feature/done
git switch -q -c experiment && git commit -q --allow-empty -m "Unmerged idea" && git switch -q main
echo "merged into main:"; git branch --merged main | grep -v main
git branch -d experiment 2>&1 | head -1
git branch -d feature/done | sed -E 's/ \(was .*//'
```

```text output
merged into main:
  feature/done
error: the branch 'experiment' is not fully merged.
Deleted branch feature/done
```

Line by line:

- `git branch done-feature` creates a branch without switching to it; `git branch -m done-feature feature/done` renames it.
- `experiment` gets a commit that is **not** on `main`.
- `git branch --merged main` lists branches whose commits are all already in `main`, so they are safe to delete. Only `feature/done` qualifies.
- `git branch -d experiment` refuses: "not fully merged". Git protects unmerged work. If you really want to throw it away, use `-D`.
- `git branch -d feature/done` succeeds.

On GitHub, turn on **Settings → General → Automatically delete head branches**, then locally run `git fetch --prune` from time to time to clean up `origin/*` references.

### 9. Branching models

<Explain>
<What>
A team's agreement on which branches exist and how work flows between them.
</What>
<Why>
Everyone knows where to branch from, where to merge, and what gets deployed.
</Why>
<When>
Decided once per project.
</When>
<Where>
**GitHub Flow** (most web teams), **Git Flow** (versioned/packaged software), **trunk-based development** (very short branches or feature flags, used by high-velocity teams).
</Where>
<How>
Start with GitHub Flow unless you have a clear reason not to.
</How>
</Explain>

| Model | Branches | Best for |
| --- | --- | --- |
| GitHub Flow | `main` + short feature branches | Web apps deployed continuously |
| Git Flow | `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` | Software with scheduled versioned releases |
| Trunk-based | `main` + branches living hours, feature flags | Fast CI/CD teams |

## Hands-on

```bash
git init -q shop && cd shop
echo "v1" > app.txt && git add . && git commit -qm "Release 1"
for f in cart payments; do
  git switch -q -c "feature/$f" main
  echo "$f" > "$f.txt" && git add . && git commit -qm "Add $f"
done
git switch -q main
git merge -q --no-edit feature/cart        # fast-forward
git merge -q --no-edit feature/payments >/dev/null  # three-way: main moved
git branch -d feature/cart feature/payments | sed -E 's/ \(was .*//'
ls
git log --graph --format=%s
```

```text output
Deleted branch feature/cart
Deleted branch feature/payments
app.txt
cart.txt
payments.txt
*   Merge branch 'feature/payments'
|\  
| * Add payments
* | Add cart
|/  
* Release 1
```

Line by line:

- The loop creates two branches, **both starting from `main`** at "Release 1" (`git switch -c name main`), each with one commit.
- `git merge feature/cart`: `main` has not moved, so this is a **fast-forward**. `main` now points to "Add cart".
- `git merge feature/payments`: now `main` has moved ("Add cart") **and** `feature/payments` has its own commit, so Git does a **three-way merge** and creates a merge commit.
- `git branch -d` deletes both branches; both are merged, so `-d` allows it.
- `ls` shows all three files, and the graph shows exactly what happened: one fast-forward and one real merge.

## Real-world example

A SaaS team uses GitHub Flow with "Squash and merge" only. Each PR becomes exactly one commit on `main` titled like "Add CSV export (#318)", and every commit on `main` is deployed automatically. When a deploy breaks something, they find the guilty PR in seconds — one commit per change — and revert just that commit. Branches are deleted automatically after merge (a repository setting), so `git branch -a` stays short.

## Common mistakes

- **Branching from an old, un-pulled `main`.**
- **Switching branches with uncommitted changes** and getting confused about which branch they belong to.
- **Long-lived branches** that diverge for weeks.
- **Merging `main` into a feature branch dozens of times** creating noisy history (rebase or merge less often but regularly).
- **Using `-D` without thinking** — force-deleting unmerged work.
- **Never deleting merged branches.**

## Security lens

<Callout type="security">
Branches are where review happens. If someone can merge without review, branching gives no protection at all.
</Callout>

- Protect `main` and release branches: required reviews, required status checks, no force pushes, no deletion.
- **CODEOWNERS** ensures security-sensitive paths (auth, CI config, infra) get reviewed by the right people.
- **Squash merges hide individual commits** — reviewers must review the whole PR diff, not just the final title.
- Hotfix branches still go through review, even under time pressure — attackers like rushed emergency changes.
- Delete branches containing experiments with test credentials (and rotate those credentials).

## Interview questions

<QA q="What is the difference between a fast-forward merge and a three-way merge?">
A fast-forward happens when the current branch has no commits that the other branch lacks, so Git simply moves the branch pointer forward and no merge commit is created. A three-way merge happens when both branches have new commits; Git combines the changes using the merge base and both branch tips and creates a merge commit with two parents.
</QA>

<QA q="What does squash merging do, and what are its pros and cons?">
Squash merging combines all changes from a branch into a single new commit on the target branch. It keeps the main history linear and readable with one commit per pull request and makes reverting a feature easy. The downside is that the individual commits of the branch are lost from main's history and Git no longer recognises the branch as merged.
</QA>

<QA q="Compare GitHub Flow and Git Flow.">
GitHub Flow uses a single long-lived main branch plus short-lived feature branches merged through pull requests, suiting continuously deployed applications. Git Flow adds a develop branch and release and hotfix branches to manage scheduled, versioned releases, at the cost of more complexity.
</QA>
