<BigIdea>
<Tr>
<En>
A **digital signature** is created with a **private key** and checked with the matching **public key**. A valid signature proves **authenticity** (it was made by whoever holds that private key) and **integrity** (not one bit has changed since). Anyone with the public key can verify, but only the key holder can sign, which also gives **non-repudiation**. Signatures are everywhere: HTTPS certificates, software updates, Git commits, signed releases, JWT login tokens, container images, payment webhooks. Use **Ed25519**, **ECDSA P-256** or **RSA-PSS**; always pin the expected algorithm, and add timestamps and IDs to stop **replays**.
</En>
<Ur>
**Digital signature** **private key** se banta hai aur us ki joridar **public key** se check hota hai. Durust signature **asliyat** (ye us ne banaya jis ke paas wo private key hai) aur **saalimiyat** (tab se ek bit bhi nahi badla) sabit karta hai. Public key wala koi bhi verify kar sakta hai, lekin sign sirf key ka maalik kar sakta hai, jis se **inkaar na kar sakna (non-repudiation)** bhi milta hai. Signatures har jagah hain: HTTPS certificates, software updates, Git commits, signed releases, JWT login tokens, container images, payment webhooks. **Ed25519**, **ECDSA P-256** ya **RSA-PSS** istemal karein; umeed shuda algorithm hamesha pin karein, aur **replays** rokne ke liye timestamps aur IDs joren.
</Ur>

## Picture it

<Tr>
<En>

A digital signature is a **wax seal stamped with a signet ring**, but impossible to forge. Only the owner has the ring (the private key); everyone has a picture of its pattern (the public key), so anyone can check the seal. And this seal is fused to the **exact contents** of the letter: change one word and it no longer matches. A handwritten signature can be copied onto another page; a digital signature can't be moved to a different document.

</En>
<Ur>

Digital signature **anguthi wali mohar se lagi laakh ki seal** hai, lekin jaali banana namumkin. Anguthi sirf maalik ke paas hai (private key); sab ke paas us ke naqsh ki tasveer hai (public key), isliye koi bhi seal check kar sakta hai. Aur ye seal khat ke **bilkul mawad** se juri hai: ek lafz badlo aur ye nahi milti. Haath ka dastakhat doosre safhe par copy ho sakta hai; digital signature doosre document par nahi le jaya ja sakta.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Sign and verify">

<Tr>
<En>

`sign(private_key, message)` → signature; `verify(public_key, message, signature)` → valid or invalid. Only the private key holder can produce a signature that verifies with their public key. Available in Python `cryptography`, Node `crypto.sign`/`verify`, Go `crypto/ed25519`, OpenSSL, and even `ssh-keygen -Y sign`. **Ed25519** signatures are always 64 bytes, deterministic, fast, and have no tricky parameters: a great default.

</En>
<Ur>

`sign(private_key, message)` → signature; `verify(public_key, message, signature)` → durust ya ghalat. Sirf private key ka maalik aisa signature bana sakta hai jo us ki public key se verify ho. Python `cryptography`, Node `crypto.sign`/`verify`, Go `crypto/ed25519`, OpenSSL, aur `ssh-keygen -Y sign` tak me maujood. **Ed25519** signatures hamesha 64 bytes, deterministic, tez, aur koi mushkil parameters nahi: behtareen default.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.exceptions import InvalidSignature

bank = Ed25519PrivateKey.generate()          # private key: stays inside the bank's HSM
public = bank.public_key()                   # public key: given to everyone who must verify
message = b"Pay $150,000 to account GB82WEST12345698765432"
signature = bank.sign(message)
print("signature size:", len(signature), "bytes")

public.verify(signature, message)            # raises an exception if invalid
print("original message     : valid")

checks = [
    ("amount changed       ", message.replace(b"150,000", b"950,000"), public),
    ("someone else's key   ", message, Ed25519PrivateKey.generate().public_key()),
]
for label, msg, key in checks:
    try:
        key.verify(signature, msg)
        print(label + ": valid?!")
    except InvalidSignature:
        print(label + ": InvalidSignature")
print("signing again gives the same signature:", bank.sign(message) == signature)
PY
```

```text output
signature size: 64 bytes
original message     : valid
amount changed       : InvalidSignature
someone else's key   : InvalidSignature
signing again gives the same signature: True
```

<Happened>
<Tr>
<En>

- The bank's private key would really live in an HSM; the public key goes to everyone who processes its messages. (`GB82WEST...` is a standard sample account number.)
- `sign` made a 64-byte signature. `verify` returns nothing if valid and **raises** `InvalidSignature` otherwise, so code can't accidentally ignore a failure.
- Changing 150,000 to 950,000 broke it: **integrity**. A different public key failed too: **authenticity**.
- Ed25519 is **deterministic**: same key and message, same signature, so there's no random nonce to get wrong.

</En>
<Ur>

- Bank ki private key asal me HSM me hogi; public key har us ko di jati hai jo us ke paighamat process kare. (`GB82WEST...` standard namoona account number hai.)
- `sign` ne 64-byte signature banaya. `verify` durust ho to kuch nahi lautata aur warna `InvalidSignature` **uthata** hai, isliye code ghalti se nakaami nazar andaz nahi kar sakta.
- 150,000 ko 950,000 karne se toot gaya: **saalimiyat**. Doosri public key se bhi fail: **asliyat**.
- Ed25519 **deterministic** hai: wahi key aur paigham, wahi signature, isliye ghalat karne ko koi random nonce nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Signatures cover a hash">

<Tr>
<En>

Signature algorithms sign a **hash** of the data (SHA-256 or SHA-512) rather than megabytes directly: fast and fixed-size. So the signature is only as strong as the hash: with collisions (MD5/SHA-1), an attacker could get one document signed and attach the signature to another. `openssl dgst -sha256 -sign` hashes then signs; JWT names like `RS256`/`ES256` include the hash; Ed25519 uses SHA-512 internally. With RSA, prefer **PSS** padding for signatures.

</En>
<Ur>

Signature algorithms megabytes seedha sign karne ke bajaye data ka **hash** (SHA-256 ya SHA-512) sign karte hain: tez aur muqarrar size. Isliye signature utna hi mazboot hai jitna hash: collisions (MD5/SHA-1) ke saath hamla awar ek document sign karwa kar signature doosre par laga sakta hai. `openssl dgst -sha256 -sign` hash kar ke sign karta hai; `RS256`/`ES256` jaise JWT naamon me hash shamil hai; Ed25519 andar SHA-512 istemal karta hai. RSA ke saath signatures ke liye **PSS** padding behtar.

</Ur>
</Tr>

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out rsa_signer.key 2>/dev/null
openssl pkey -in rsa_signer.key -pubout -out rsa_signer.pub
printf 'Contract: supply 500 laptops at $2,100 each\n' > contract.txt
openssl dgst -sha256 -sign rsa_signer.key -sigopt rsa_padding_mode:pss -out contract.sig contract.txt
echo "signature: $(wc -c < contract.sig) bytes"
openssl dgst -sha256 -verify rsa_signer.pub -sigopt rsa_padding_mode:pss -signature contract.sig contract.txt
sed -i 's/2,100/1,200/' contract.txt
openssl dgst -sha256 -verify rsa_signer.pub -sigopt rsa_padding_mode:pss -signature contract.sig contract.txt 2>/dev/null
```

```text output
signature: 256 bytes
Verified OK
Verification failure
```

<Happened>
<Tr>
<En>`openssl dgst -sha256 -sign … pss` hashed the contract and signed the hash with RSA-PSS; an RSA-2048 signature is 256 bytes, four times Ed25519's. The untouched contract printed `Verified OK`. After someone edited the price (`sed -i`), verification printed `Verification failure` (exit code 1); `2>/dev/null` hid OpenSSL's detailed error lines.</En>
<Ur>`openssl dgst -sha256 -sign … pss` ne contract hash kiya aur hash ko RSA-PSS se sign kiya; RSA-2048 signature 256 bytes ka hai, Ed25519 ka chaar guna. Na chhua contract `Verified OK` chhaapa. Kisi ke qeemat badalne (`sed -i`) ke baad verification ne `Verification failure` (exit code 1) diya; `2>/dev/null` ne OpenSSL ki tafseeli error lines chhupayin.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Signatures vs HMAC">

<Tr>
<En>

Both detect tampering. **HMAC** uses one **shared secret** for creating and checking, so anyone who can verify can also forge, and it can't prove authorship to a third party. **Signatures** let thousands verify without being able to sign. Use HMAC between two parties that trust each other (webhooks, internal services, session cookies); signatures for public verification, many verifiers, and non-repudiation. JWT `HS256` = HMAC (every verifying service can also mint tokens); `RS256`/`ES256`/`EdDSA` = signatures (only the auth server mints). In microservices, prefer asymmetric JWTs so a compromised service can't create admin tokens.

| | HMAC | Digital signature |
| --- | --- | --- |
| Keys | One shared secret | Private signs, public verifies |
| Who can verify? | Only secret holders | Anyone with the public key |
| Who can create? | Every secret holder | Only the private key holder |
| Non-repudiation | No | Yes |
| Speed / size | Very fast, 32 bytes | Slower, 64–512 bytes |
| Examples | Webhooks, cookies, AWS SigV4, JWT HS256 | TLS certificates, releases, Git, JWT RS256/ES256/EdDSA |

</En>
<Ur>

Dono cherh chhaar pakarte hain. **HMAC** banane aur check karne ke liye ek **saanjha raaz** leta hai, isliye jo verify kar sakta hai wo jaali bhi bana sakta hai, aur ye kisi teesre ko likhne wala sabit nahi kar sakta. **Signatures** hazaron ko sign kiye baghair verify karne deti hain. Ek doosre par bharosa karne wale do fareeqon ke beech HMAC (webhooks, andaruni services, session cookies); public tasdeeq, bohot se verifiers aur non-repudiation ke liye signatures. JWT `HS256` = HMAC (har verify karne wali service tokens bana bhi sakti hai); `RS256`/`ES256`/`EdDSA` = signatures (sirf auth server banata hai). Microservices me asymmetric JWTs behtar taa ke compromise hui service admin tokens na bana sake.

| | HMAC | Digital signature |
| --- | --- | --- |
| Keys | Ek saanjha raaz | Private sign, public verify |
| Kaun verify kare? | Sirf raaz wale | Public key wala koi bhi |
| Kaun banaye? | Har raaz wala | Sirf private key ka maalik |
| Non-repudiation | Nahi | Haan |
| Raftar / size | Bohot tez, 32 bytes | Sust, 64–512 bytes |
| Misaalen | Webhooks, cookies, AWS SigV4, JWT HS256 | TLS certificates, releases, Git, JWT RS256/ES256/EdDSA |

</Ur>
</Tr>

</Step>

<Step title="Sign releases and checksum files">

<Tr>
<En>

Projects publish `SHA256SUMS` listing each file's hash, plus a **signature of that file** (`SHA256SUMS.sig` or `.asc`). Users verify the signature first, then the checksums. In the **Hashing** lesson, an attacker controlling the download server could replace both the file and its checksum; they **can't** create a valid signature without the maintainer's private key, which isn't on the server. Get the maintainer's public key from a **trusted, separate** source (their HTTPS website, a pinned copy in your repo), never from the same place as the download.

</En>
<Ur>

Projects har file ke hash wali `SHA256SUMS` aur **us file ka signature** (`SHA256SUMS.sig` ya `.asc`) shaya karte hain. Users pehle signature verify karte hain, phir checksums. **Hashing** sabaq me download server par qabza karne wala file aur checksum dono badal sakta tha; maintainer ki private key ke baghair wo durust signature **nahi** bana sakta, jo server par hoti hi nahi. Maintainer ki public key **bharose wale, alag** source se lein (un ki HTTPS website, aap ki repo me pinned copy), download wali jagah se kabhi nahi.

</Ur>
</Tr>

```bash
openssl genpkey -algorithm ed25519 -out maintainer.key
openssl pkey -in maintainer.key -pubout -out maintainer.pub
printf 'app v2.0 binary\n' > app-2.0.tar.gz
sha256sum app-2.0.tar.gz > SHA256SUMS
openssl pkeyutl -sign -inkey maintainer.key -rawin -in SHA256SUMS -out SHA256SUMS.sig
echo "--- user verifies the genuine release:"
openssl pkeyutl -verify -pubin -inkey maintainer.pub -rawin -in SHA256SUMS -sigfile SHA256SUMS.sig && sha256sum -c SHA256SUMS
echo "--- attacker replaces the file AND the checksum on the server:"
printf 'backdoored binary\n' > app-2.0.tar.gz
sha256sum app-2.0.tar.gz > SHA256SUMS
openssl pkeyutl -verify -pubin -inkey maintainer.pub -rawin -in SHA256SUMS -sigfile SHA256SUMS.sig; echo "exit code: $?"
```

```text output
--- user verifies the genuine release:
Signature Verified Successfully
app-2.0.tar.gz: OK
--- attacker replaces the file AND the checksum on the server:
Signature Verification Failure
exit code: 1
```

<Happened>
<Tr>
<En>The maintainer signed `SHA256SUMS` (`-rawin` because Ed25519 signs the raw message). The user verified the signature with the **public** key, and `&&` ran the checksum check only if it passed. The attacker swapped in a backdoored file and a matching new `SHA256SUMS`: the checksums would "pass", but the old signature doesn't match the new checksum file and the attacker can't make a new one, so verification failed with exit code 1.</En>
<Ur>Maintainer ne `SHA256SUMS` sign ki (`-rawin` kyun ke Ed25519 kaccha paigham sign karta hai). User ne **public** key se signature verify kiya, aur `&&` ne checksum check sirf pass hone par chalaya. Hamla awar ne backdoored file aur milti nayi `SHA256SUMS` rakh di: checksums "pass" ho jate, lekin purana signature nayi checksum file se nahi milta aur hamla awar naya nahi bana sakta, isliye verification exit code 1 ke saath fail hui.</Ur>
</Tr>
</Happened>

</Step>

<Step title="JWT signatures and the classic JWT attacks">

<Tr>
<En>

A JWT is `header.payload.signature` (Base64url); the header names the algorithm (`EdDSA`, `ES256`, `RS256`, `HS256`). The server must verify the signature before trusting the claims. Libraries had famous bugs when they **trusted the token's own `alg`**: `"alg": "none"` (no signature) was accepted, and **algorithm confusion** let attackers sign an `HS256` token using the server's **public** RSA key as the HMAC secret. Defences: maintained libraries, **pin the allowed algorithm(s)**, reject `none`, check `exp`, `iss` and `aud`, and keep payloads non-sensitive (they're only encoded).

</En>
<Ur>

JWT `header.payload.signature` (Base64url) hai; header algorithm batata hai (`EdDSA`, `ES256`, `RS256`, `HS256`). Server ko claims par bharosa karne se pehle signature verify karna chahiye. Libraries me mashhoor bugs tab aaye jab unhon ne **token ke apne `alg` par bharosa** kiya: `"alg": "none"` (signature nahi) maan liya gaya, aur **algorithm confusion** ne hamla awar ko server ki **public** RSA key ko HMAC raaz bana kar `HS256` token sign karne diya. Bachao: maintained libraries, **jaiz algorithm(s) pin karein**, `none` radd karein, `exp`, `iss` aur `aud` check karein, aur payloads me hassas cheezen na rakhein (wo sirf encoded hain).

</Ur>
</Tr>

```bash
python3 - <<'PY'
import base64, json
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.exceptions import InvalidSignature

b64 = lambda raw: base64.urlsafe_b64encode(raw).decode().rstrip("=")
unb64 = lambda text: base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))

auth_server = Ed25519PrivateKey.generate()
public = auth_server.public_key()            # every API service gets only this

def issue(claims):
    h = b64(json.dumps({"alg": "EdDSA", "typ": "JWT"}).encode())
    p = b64(json.dumps(claims).encode())
    return f"{h}.{p}.{b64(auth_server.sign(f'{h}.{p}'.encode()))}"

def verify(token):
    h, p, s = token.split(".")
    if json.loads(unb64(h)).get("alg") != "EdDSA":           # pin the algorithm
        return "rejected: unexpected alg " + str(json.loads(unb64(h)).get("alg"))
    try:
        public.verify(unb64(s), f"{h}.{p}".encode())
    except InvalidSignature:
        return "rejected: bad signature"
    return "accepted: " + str(json.loads(unb64(p)))

token = issue({"sub": "1042", "role": "user"})
print("genuine token     :", verify(token))
h, p, s = token.split(".")
admin_payload = b64(json.dumps({"sub": "1042", "role": "admin"}).encode())
print("role edited       :", verify(f"{h}.{admin_payload}.{s}"))
none_header = b64(json.dumps({"alg": "none", "typ": "JWT"}).encode())
print("alg none, no sig  :", verify(f"{none_header}.{admin_payload}."))
PY
```

```text output
genuine token     : accepted: {'sub': '1042', 'role': 'user'}
role edited       : rejected: bad signature
alg none, no sig  : rejected: unexpected alg none
```

<Happened>
<Tr>
<En>The auth server signs `header.payload` with its private key; API services get only the public key, so even a hacked one can't mint tokens. `verify` first checks the algorithm is exactly `EdDSA`, **then** verifies the signature. The genuine token passed. Changing `role` to `admin` while keeping the old signature was rejected, and an `"alg": "none"` token with no signature was stopped by the pin. Real code: PyJWT or `jose` with `algorithms=["EdDSA"]`, plus `exp`, `iss` and `aud` checks.</En>
<Ur>Auth server `header.payload` ko private key se sign karta hai; API services ko sirf public key milti hai, isliye hack hui service bhi tokens nahi bana sakti. `verify` pehle check karta hai algorithm bilkul `EdDSA` hai, **phir** signature verify karta hai. Asli token pass hua. Purana signature rakh kar `role` ko `admin` karna radd hua, aur bina signature wala `"alg": "none"` token pin ne rok diya. Asli code: PyJWT ya `jose` `algorithms=["EdDSA"]` ke saath, aur `exp`, `iss`, `aud` checks.</Ur>
</Tr>
</Happened>

<Step title="Replay attacks: a valid signature can be sent twice">

<Tr>
<En>

A signature proves a message is genuine, not that it's **new**. An attacker who captures "pay invoice 1042" can **replay** it later, and the signature is still valid: double payments, repeated orders, reused tokens. Include a **timestamp** and a unique **ID** in the signed data, reject messages older than a few minutes, remember processed IDs, and make handlers **idempotent**. Stripe, Slack and AWS SigV4 all sign a timestamp.

</En>
<Ur>

from cryptography.exceptions import InvalidSignature

public = gateway.public_key()
seen_ids = set()

def send(event_id, timestamp, body):
    signed = f"{event_id}.{timestamp}.{body}".encode()      # ID and time are inside the signature
    return {"id": event_id, "ts": timestamp, "body": body, "sig": gateway.sign(signed)}

def receive(req, now):
    try:
        public.verify(req["sig"], f"{req['id']}.{req['ts']}.{req['body']}".encode())
    except InvalidSignature:
        return "rejected: bad signature"
    if now - req["ts"] > 300:
        return "rejected: too old (possible replay)"
    if req["id"] in seen_ids:
        return "rejected: already processed (replay)"
    seen_ids.add(req["id"])
    return "processed: " + req["body"]

request = send("evt_1", 1_794_300_000, '{"order":"1042","status":"paid"}')
print("10 s later  :", receive(request, now=1_794_300_010))
print("again, 20 s :", receive(request, now=1_794_300_020))
print("1 hour later:", receive(request, now=1_794_303_600))

<Step title="Choosing algorithms">

<Tr>
<En>

Today's main signature algorithms: **Ed25519**, **ECDSA** (P-256 / P-384) and **RSA** (PSS or PKCS#1 v1.5, 2048–4096 bits). New systems: Ed25519 where supported, ECDSA P-256 where standards or HSMs require it, RSA for compatibility. ECDSA needs a fresh secret random number for **every** signature: reusing or predicting it reveals the private key (it happened to Sony's PlayStation 3 key and several Bitcoin wallets); Ed25519 and deterministic ECDSA (RFC 6979) avoid that. Never use RSA under 2048 bits, MD5/SHA-1-based signatures, or DSA.

| Algorithm | Signature size | Notes |
| --- | --- | --- |
| Ed25519 | 64 bytes | Fast, deterministic, simple; SSH, Git, Signal, minisign, JWT EdDSA |
| ECDSA P-256 | ~64–72 bytes | Widely supported (TLS, HSMs, WebAuthn); nonce must be perfect |
| RSA-2048 / 3072 | 256 / 384 bytes | Universal compatibility; slow to sign, fast to verify |

</En>
<Ur>

Aaj ke bare signature algorithms: **Ed25519**, **ECDSA** (P-256 / P-384) aur **RSA** (PSS ya PKCS#1 v1.5, 2048–4096 bits). Naye systems: jahan support ho Ed25519, jahan standards ya HSMs maangen ECDSA P-256, mutabiqat ke liye RSA. ECDSA ko **har** signature ke liye taaza raaz wala random number chahiye: dohrana ya andaze ke qabil hona private key khol deta hai (Sony ke PlayStation 3 key aur kai Bitcoin wallets ke saath hua); Ed25519 aur deterministic ECDSA (RFC 6979) is se bachate hain. 2048 bits se chhota RSA, MD5/SHA-1 wale signatures, ya DSA kabhi nahi.

| Algorithm | Signature size | Notes |
| --- | --- | --- |
| Ed25519 | 64 bytes | Tez, deterministic, saada; SSH, Git, Signal, minisign, JWT EdDSA |
| ECDSA P-256 | ~64–72 bytes | Har jagah support (TLS, HSMs, WebAuthn); nonce bilkul sahi ho |
| RSA-2048 / 3072 | 256 / 384 bytes | Har jagah chalta hai; sign sust, verify tez |

## Common mistakes

<Compare>
<Bad title="Checksum only, key from the same server">

```text
curl -O https://dl.example/acme-cli
curl -O https://dl.example/SHA256SUMS
curl -O https://dl.example/maintainer.pub      # attacker controls all three
sha256sum -c SHA256SUMS && sh acme-cli
```

</Bad>
<Good title="Pinned key, signature first, then checksums">

```text
# maintainer.pub committed to your repo once, from the official HTTPS site
openssl pkeyutl -verify -pubin -inkey trusted-keys/maintainer.pub -rawin \
  -in SHA256SUMS -sigfile SHA256SUMS.sig && sha256sum -c SHA256SUMS && sh acme-cli
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Trusting the JWT `alg` header**, accepting `none`, or mixing HS256 and RS256 with the same key material.
- **No timestamp or ID in signed messages**, so they can be replayed.
- **HMAC where third parties must verify**, or sharing one HMAC secret with many services.
- **ECDSA with bad randomness** or a reused nonce, leaking the private key.
- **Obsolete algorithms:** RSA-1024, MD5/SHA-1 signatures, DSA.
- **Signing keys on build servers or laptops** without protection.
- **Assuming "signed" means "safe".** It means "unchanged since this key signed it".

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **JWT ke `alg` header par bharosa**, `none` maanna, ya ek hi key material ke saath HS256 aur RS256 milana.
- **Signed paighamat me timestamp ya ID nahi**, isliye dobara bheje ja sakte hain.
- **Jahan teesre fareeq ko verify karna ho wahan HMAC**, ya ek HMAC raaz bohot si services me baantna.
- **Buri randomness wala ECDSA** ya dohraya nonce, jo private key leak kare.
- **Purane algorithms:** RSA-1024, MD5/SHA-1 signatures, DSA.
- **Build servers ya laptops par bina hifazat signing keys**.
- **"Signed" ko "mehfooz" samajhna.** Is ka matlab "is key ke sign karne ke baad se nahi badla".

</Ur>
</Tr>

```bash
openssl genpkey -algorithm ed25519 -out release-signing.key
openssl pkey -in release-signing.key -pubout -out release-signing.pub
mkdir -p dist trusted-keys
cp release-signing.pub trusted-keys/acme-release.pub          # pinned in the CI repo
printf '#!/bin/sh\necho "acme-cli 3.1.0"\n' > dist/acme-cli
printf 'docs\n' > dist/README.md

# --- maintainer: publish release ---
(cd dist && sha256sum acme-cli README.md > SHA256SUMS)
openssl pkeyutl -sign -inkey release-signing.key -rawin -in dist/SHA256SUMS -out dist/SHA256SUMS.sig

# --- CI: verify, then install ---
verify_and_install() {
  openssl pkeyutl -verify -pubin -inkey trusted-keys/acme-release.pub -rawin \
    -in dist/SHA256SUMS -sigfile dist/SHA256SUMS.sig >/dev/null || { echo "STOP: signature invalid"; return 1; }
  (cd dist && sha256sum --quiet -c SHA256SUMS) || { echo "STOP: checksum mismatch"; return 1; }
  sh dist/acme-cli
}
echo "1) genuine release:"; verify_and_install
echo "2) only the binary swapped:"; printf '#!/bin/sh\necho "malware"\n' > dist/acme-cli; verify_and_install
echo "3) binary and SHA256SUMS swapped:"; (cd dist && sha256sum acme-cli README.md > SHA256SUMS); verify_and_install
```

<DeepDive title="Real world: SolarWinds, a perfectly signed backdoor">

In the 2020 **SolarWinds** attack, attackers inserted a backdoor into the company's build system, so the malicious update was compiled **and signed with SolarWinds' genuine code-signing certificate**. Thousands of organisations installed it because the signature was valid. The lesson: a signature proves **who** signed, not that the content is **safe**. If the build pipeline is compromised, malware gets signed too. The industry responded with supply-chain frameworks like **SLSA**: isolated, audited build systems; signing keys in HSMs or keyless Sigstore tied to the CI identity; signed **provenance** saying exactly which source and workflow produced each artefact; and transparency logs where every signature is public, so unexpected signatures are noticed.

</DeepDive>

<DeepDive title="Security lens">

A signature is only as trustworthy as the private key and the process that uses it. Protect signing keys like crown jewels and verify signatures everywhere software or data enters your system.

- **Protect signing keys:** HSMs, cloud KMS asymmetric keys, hardware tokens, or keyless signing; restrict who and which pipelines can sign; log every signing operation.
- **Enforce verification:** package managers, CI download steps, Kubernetes admission control, Secure Boot. Unchecked signatures give no security.
- **Pin identities and algorithms:** pinned public keys or certificate identities, allow-listed algorithms, `iss`/`aud`/`exp` checks.
- **Plan for compromise:** have a rotation and revocation procedure before you need it.
- **Transparency:** Sigstore's Rekor and Certificate Transparency make signatures publicly auditable, so key misuse can be detected.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does a digital signature guarantee?">
A valid signature guarantees integrity, meaning the data has not changed since it was signed, and authenticity, meaning it was signed by the holder of the private key corresponding to the public key used for verification. It also provides non-repudiation, because only that key holder could have produced it. It does not guarantee the content is safe or that the message is fresh.
</QA>

<QA q="What is the difference between a digital signature and HMAC?">
HMAC uses one shared secret key for both creating and verifying the code, so any party that can verify can also forge, and it cannot prove authorship to third parties. A digital signature uses a private key to sign and a public key to verify, so anyone can verify but only the key holder can sign, which enables public verification and non-repudiation.
</QA>

<QA q="How does signing a SHA256SUMS file protect downloads?">
The checksum file lists the hashes of the release files and is signed with the maintainer's private key. Users verify the signature with a trusted copy of the public key and then check the files against the hashes. An attacker who replaces files on the download server cannot produce a valid signature for modified checksums without the private key.
</QA>

<QA q="What are the alg none and algorithm confusion attacks on JWTs?">
In the alg none attack, an attacker sends a token whose header says no algorithm and omits the signature, and a vulnerable library accepts it unsigned. In algorithm confusion, an attacker changes the algorithm from an asymmetric one like RS256 to HS256 and signs the token with HMAC using the server's public key as the secret, which a vulnerable verifier then accepts. Verifiers must pin expected algorithms and key types.
</QA>

<QA q="How do you prevent replay of signed requests?">
Include a timestamp and a unique identifier or nonce inside the signed data, reject requests older than a short window, store processed identifiers to reject duplicates, and make handlers idempotent so that processing the same event twice has no extra effect.
</QA>

</DeepDive>
