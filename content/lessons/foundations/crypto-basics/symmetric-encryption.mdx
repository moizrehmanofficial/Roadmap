<BigIdea>
<Tr>
<En>
**Symmetric encryption** uses **one secret key** both to **encrypt** (plaintext → ciphertext) and to **decrypt**. It's fast, so it protects almost all data: disks, databases, backups, Wi-Fi and the bulk of every HTTPS connection. The standard algorithms are **AES** and **ChaCha20**, used in an **authenticated** mode (**AES-GCM**, **ChaCha20-Poly1305**) that also detects tampering. Every encryption needs a fresh **nonce**, keys must be **random** (or derived from a password with a slow KDF), and keys belong in a **KMS**, away from the data. The hard part is never the algorithm: it's **key management**.
</En>
<Ur>
**Symmetric encryption** **ek hi raaz wali key** se **encrypt** (plaintext → ciphertext) aur **decrypt** dono karti hai. Ye tez hai, isliye takreeban saara data isi se mehfooz hota hai: disks, databases, backups, Wi-Fi aur har HTTPS connection ka zyada tar hissa. Standard algorithms **AES** aur **ChaCha20** hain, jo **authenticated** mode (**AES-GCM**, **ChaCha20-Poly1305**) me chalte hain jo cherh chhaar bhi pakarta hai. Har encryption ko taaza **nonce** chahiye, keys **random** hon (ya password se sust KDF ke zariye banayi jayen), aur keys data se door **KMS** me rahen. Mushkil hissa kabhi algorithm nahi: **key management** hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Symmetric encryption is a **lockbox with one key, and copies of that same key**. Whoever has a copy can lock and unlock it: simple and fast, which is why it's used for almost everything. The difficulty is the key itself. How do you get a copy to a friend in another city without anyone copying it on the way? And where do you keep yours, so a thief who steals the box doesn't find the key taped to its lid? (Getting keys safely to the other side is what **asymmetric** encryption solves in the next lesson.)

</En>
<Ur>

Symmetric encryption **ek chaabi wala sandooq, aur usi chaabi ki copies** hai. Jis ke paas copy hai wo band bhi kar sakta hai aur khol bhi: saada aur tez, isi liye takreeban har jagah istemal hota hai. Mushkil khud chaabi hai. Doosre shehar ke dost tak copy kaise pahunchayen ke raste me koi copy na kar le? Aur apni kahan rakhein, taa ke sandooq churane wale ko chaabi us ke dhakkan par chipki na mile? (Chaabiyan mehfooz tareeqe se doosri taraf pahunchana agle sabaq ki **asymmetric** encryption hal karti hai.)

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Keys and key sizes">

<Tr>
<En>

A key is a random secret value: AES supports 128-, 192- and 256-bit keys (16, 24 or 32 bytes); ChaCha20 uses 256 bits. The key is the **only** secret: the algorithm is public and has been analysed by experts for decades, so security depends entirely on the key being random, long and secret. 2^128 possibilities is far beyond brute force; 256 bits adds margin, including against future quantum computers. Generate with `openssl rand -hex 32`, `os.urandom(32)`, or a KMS. Never use a typed password **directly** as a key.

</En>
<Ur>

Key random raaz value hai: AES 128, 192 aur 256-bit keys (16, 24 ya 32 bytes) leta hai; ChaCha20 256 bits. Key hi **akela** raaz hai: algorithm public hai aur dahaiyon se maahireen ne parkha hai, isliye security poori tarah key ke random, lambi aur raaz hone par hai. 2^128 imkanaat brute force se kahin bahar hain; 256 bits izafi gunjaish deta hai, aane wale quantum computers ke khilaf bhi. `openssl rand -hex 32`, `os.urandom(32)`, ya KMS se banayen. Likha hua password **seedha** key ke tor par kabhi na lein.

</Ur>
</Tr>

```bash
openssl rand -hex 32 | awk '{print length($0)/2 " random bytes = " length($0)*4 " bits"}'
python3 -c 'from cryptography.hazmat.primitives.ciphers.aead import AESGCM; print(len(AESGCM.generate_key(bit_length=256)), "byte AES-256 key generated")'
```

```text output
32 random bytes = 256 bits
32 byte AES-256 key generated
```

<Tr>
<En>`openssl rand -hex 32` produced 32 bytes from the OS's secure random generator as 64 hex characters (we print only the size, since the value changes every time); `AESGCM.generate_key` did the same in Python.</En>
<Ur>`openssl rand -hex 32` ne OS ke mehfooz random generator se 32 bytes 64 hex huroof me diye (hum sirf size chhaapte hain kyun ke value har dafa badalti hai); `AESGCM.generate_key` ne Python me yahi kiya.</Ur>
</Tr>

<Step title="AES-GCM: encrypt, decrypt, detect tampering">

<Tr>
<En>

**AES-GCM** is an **AEAD** cipher: it encrypts **and** adds a 16-byte **authentication tag**, and decryption refuses to return anything if the data or tag changed. Encryption alone doesn't stop **modification**: with some older modes, flipping ciphertext bits flips the same plaintext bits ("$1000" → "$9000") unnoticed. AES-GCM is your default (ChaCha20-Poly1305 is the equivalent, faster on devices without AES hardware); TLS 1.3 uses only AEAD ciphers. `decrypt` raises `InvalidTag` for a wrong key, modified data or a modified tag.

</En>
<Ur>

**AES-GCM** **AEAD** cipher hai: encrypt bhi karta hai **aur** 16-byte **authentication tag** jorta hai, aur data ya tag badla ho to decryption kuch nahi lautati. Sirf encryption **tabdeeli** nahi rokti: kuch purane modes me ciphertext ke bits palatne se plaintext ke wahi bits palat jate hain ("$1000" → "$9000") aur pata nahi chalta. AES-GCM aap ka default hai (ChaCha20-Poly1305 barabar ka hai, AES hardware ke baghair devices par tez); TLS 1.3 sirf AEAD ciphers istemal karta hai. Ghalat key, badle data ya badle tag par `decrypt` `InvalidTag` deta hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.exceptions import InvalidTag

key = bytes(range(32))           # demo only: real keys must be random
nonce = bytes(12)                # demo only: real nonces must never repeat
aes = AESGCM(key)

ciphertext = aes.encrypt(nonce, b"Salary: $185,000", None)
print("ciphertext + tag:", len(ciphertext), "bytes:", ciphertext.hex()[:40] + "...")
print("decrypted       :", aes.decrypt(nonce, ciphertext, None).decode())

tampered = bytearray(ciphertext)
tampered[0] ^= 1                 # flip one bit
try:
    aes.decrypt(nonce, bytes(tampered), None)
except InvalidTag:
    print("tampered        : InvalidTag (refused to decrypt)")

try:
    AESGCM(bytes(32)).decrypt(nonce, ciphertext, None)
except InvalidTag:
    print("wrong key       : InvalidTag")
PY
```

```text output
ciphertext + tag: 32 bytes: 5dddd9bfc755b99d2c999100341ca1a9194ec598...
decrypted       : Salary: $185,000
tampered        : InvalidTag (refused to decrypt)
wrong key       : InvalidTag
```

<Happened>
<Tr>
<En>

- `encrypt(nonce, plaintext, None)` returned **32 bytes**: 16 bytes of ciphertext (same length as the plaintext) plus the 16-byte tag. `None` = no associated data.
- `decrypt` with the same key and nonce returned the original text.
- Flipping **one bit** made decryption fail with `InvalidTag`: nothing returned, so the app can't accidentally use modified data.
- A different key also gave `InvalidTag`. GCM can't tell "wrong key" from "modified data", and doesn't need to: both mean "don't trust this".

</En>
<Ur>

- `encrypt(nonce, plaintext, None)` ne **32 bytes** diye: 16 bytes ciphertext (plaintext jitni lambai) aur 16-byte tag. `None` = associated data nahi.
- Wahi key aur nonce ke saath `decrypt` ne asal text wapas diya.
- **Ek bit** palatne se decryption `InvalidTag` ke saath fail hui: kuch nahi lauta, isliye app ghalti se badla data istemal nahi kar sakti.
- Doosri key se bhi `InvalidTag`. GCM "ghalat key" aur "badla data" me farq nahi kar sakta, aur zaroorat bhi nahi: dono ka matlab "is par bharosa mat karo".

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Why modes matter: the ECB pattern leak">

<Tr>
<En>

AES itself encrypts exactly **16 bytes**; a **mode** decides how longer data is handled. Naive **ECB** encrypts each block independently with the same key, so **identical plaintext blocks give identical ciphertext blocks** and patterns stay visible (the famous encrypted penguin image still shows the penguin). Never use ECB; some libraries default to it (Java's `Cipher.getInstance("AES")` means ECB). CBC with a random IV hides patterns but has no integrity, so it needs a correctly built HMAC; prefer AEAD.

</En>
<Ur>

AES khud bilkul **16 bytes** encrypt karta hai; **mode** tay karta hai lamba data kaise sambhala jaye. Saada **ECB** har block ko alag se usi key se encrypt karta hai, isliye **ek jaise plaintext blocks ek jaise ciphertext blocks** dete hain aur patterns nazar aate rehte hain (mashhoor encrypted penguin tasveer me penguin ab bhi dikhta hai). ECB kabhi na lein; kuch libraries default me yahi deti hain (Java ka `Cipher.getInstance("AES")` ECB hai). Random IV wala CBC patterns chhupata hai lekin saalimiyat nahi deta, isliye sahi bana HMAC chahiye; AEAD behtar.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
key = bytes(range(16))
plaintext = b"ATTACK AT DAWN!!" * 3 + b"RETREAT AT DUSK!"

def blocks(ciphertext):
    return [ciphertext[i:i+16].hex()[:12] for i in range(0, len(ciphertext), 16)]

ecb = Cipher(algorithms.AES(key), modes.ECB()).encryptor()
print("ECB:", blocks(ecb.update(plaintext) + ecb.finalize()))
cbc = Cipher(algorithms.AES(key), modes.CBC(bytes(16))).encryptor()
print("CBC:", blocks(cbc.update(plaintext) + cbc.finalize()))
PY
```

```text output
ECB: ['8a21cef935d8', '8a21cef935d8', '8a21cef935d8', '937c126da0ad']
CBC: ['8a21cef935d8', '366cbbd5f991', '1cb2af80f7f9', '1ebc21ebdef8']
```

<Happened>
<Tr>
<En>The plaintext is three copies of `ATTACK AT DAWN!!` and one `RETREAT AT DUSK!`. With **ECB** the first three ciphertext blocks are **identical**: an attacker learns "the same message three times, then something different" without any key. With **CBC** each block is mixed with the previous ciphertext, so repeats look different. (The first block matches ECB only because the demo used an all-zero IV; a real IV is random.)</En>
<Ur>Plaintext me `ATTACK AT DAWN!!` ki teen copies aur ek `RETREAT AT DUSK!` hai. **ECB** me pehle teen ciphertext blocks **bilkul ek jaise** hain: hamla awar bina key ke jaan leta hai "ek hi paigham teen dafa, phir kuch aur". **CBC** me har block pichhle ciphertext se milaya jata hai, isliye dohrao alag dikhta hai. (Pehla block ECB se sirf is liye milta hai ke demo me sab zero IV tha; asli IV random hota hai.)</Ur>
</Tr>
</Happened>

</Step>

<Step title="Nonces: never reuse one">

<Tr>
<En>

A **nonce** (or **IV**) makes encrypting the same plaintext twice give different ciphertext. For AES-GCM it's 12 bytes and **not secret** (stored next to the ciphertext). Reusing the **same nonce with the same key** is catastrophic: XOR-ing two ciphertexts cancels the key stream, leaking the XOR of the plaintexts, so knowing one reveals the other; it also lets attackers forge tags. Use a random 12-byte `os.urandom(12)` per message (safe for about 2^32 messages per key) or a never-repeating counter; libsodium and Tink handle nonces for you.

</En>
<Ur>

**Nonce** (ya **IV**) ek hi plaintext ko do dafa encrypt karne par alag ciphertext deta hai. AES-GCM me ye 12 bytes ka aur **raaz nahi** hai (ciphertext ke saath rakha jata hai). **Wahi key ke saath wahi nonce** dobara lena tabahi hai: do ciphertexts ka XOR key stream mita deta hai aur plaintexts ka XOR leak hota hai, isliye ek jaanne se doosra khul jata hai; hamla awar jaali tags bhi bana sakta hai. Har paigham ke liye random 12-byte `os.urandom(12)` (har key ke liye takreeban 2^32 paighamat tak mehfooz) ya kabhi na dohrane wala counter lein; libsodium aur Tink nonces khud sambhalte hain.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
key, nonce = bytes(range(32)), bytes(12)
aes = AESGCM(key)
p1 = b"Pay $5000 to Sam! "           # attacker knows or guesses this message
p2 = b"PIN for card: 4821"           # secret
c1 = aes.encrypt(nonce, p1, None)[:len(p1)]   # same key + SAME nonce (the bug)
c2 = aes.encrypt(nonce, p2, None)[:len(p2)]
recovered = bytes(a ^ b ^ c for a, b, c in zip(c1, c2, p1))
print("attacker recovers:", recovered.decode())
PY
```

```text output
attacker recovers: PIN for card: 4821
```

<Happened>
<Tr>
<En>Both messages used the same key and nonce, so both were XOR-ed with the **same key stream**. `[:len(p1)]` dropped the 16-byte tag. `c1 XOR c2 = p1 XOR p2`, and XOR-ing that with the known `p1` gave `p2`. The attacker never touched the key and still read the PIN. This exact mistake has broken real systems, including IoT devices, game consoles and early Wi-Fi encryption (WEP).</En>
<Ur>Dono paighamat ne wahi key aur nonce liya, isliye dono **ek hi key stream** se XOR hue. `[:len(p1)]` ne 16-byte tag hataya. `c1 XOR c2 = p1 XOR p2`, aur use maloom `p1` se XOR karne par `p2` mila. Hamla awar ne key chhui tak nahi phir bhi PIN parh liya. Isi ghalti ne asli systems tore hain, IoT devices, game consoles aur purani Wi-Fi encryption (WEP) samet.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Associated data: binding ciphertext to its context">

<Tr>
<En>

AEAD ciphers accept **associated data (AAD)**: extra information that is **authenticated but not encrypted**, like a user or record ID. It stops someone with database access from **swapping** ciphertexts between rows, for example copying their own encrypted value into an admin's row: the ciphertext only decrypts in the context it was made for. It's the third argument of `encrypt`/`decrypt`; KMS APIs call it **encryption context**. A mismatch fails with `InvalidTag`.

</En>
<Ur>

AEAD ciphers **associated data (AAD)** lete hain: izafi maloomat jo **tasdeeq hoti hai lekin encrypt nahi**, jaise user ya record ki ID. Ye database tak rasai wale ko rows ke beech ciphertexts **badalne** se rokti hai, maslan apni encrypted value admin ki row me copy karna: ciphertext sirf usi sayaq me khulta hai jis ke liye bana. Ye `encrypt`/`decrypt` ka teesra argument hai; KMS APIs ise **encryption context** kehte hain. Na milne par `InvalidTag`.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.exceptions import InvalidTag
aes, nonce = AESGCM(bytes(range(32))), bytes(12)
stored = aes.encrypt(nonce, b"SSN 078-05-1120", b"user:1042")
print("user 1042 reads:", aes.decrypt(nonce, stored, b"user:1042").decode())
try:
    aes.decrypt(nonce, stored, b"user:7")
except InvalidTag:
    print("same ciphertext copied into user 7's row: InvalidTag (swap detected)")
PY
```

```text output
user 1042 reads: SSN 078-05-1120
same ciphertext copied into user 7's row: InvalidTag (swap detected)
```

<Happened>
<Tr>
<En>The ID number was encrypted with AAD `user:1042`, the ID of its row. The AAD isn't stored in the ciphertext; the app supplies it again from the row. In user 1042's row, decryption worked; copied into user 7's row, decryption used `user:7`, the tag check failed, and the swap was detected. (`078-05-1120` is a famous sample number, never a real person's.)</En>
<Ur>ID number AAD `user:1042` ke saath encrypt hua, jo us ki row ki ID hai. AAD ciphertext me save nahi hoti; app use row se dobara deti hai. User 1042 ki row me decryption chali; user 7 ki row me copy hone par decryption ne `user:7` liya, tag check fail hua, aur adla badli pakri gayi. (`078-05-1120` mashhoor namoona number hai, kisi asli shakhs ka nahi.)</Ur>
</Tr>
</Happened>

</Step>

<Step title="Turn a password into a key">

<Tr>
<En>

When a **human** must unlock data (password manager, encrypted backup), a **password-based KDF** stretches the password plus a random **salt** into a proper key. Passwords are short and guessable; a KDF makes **each guess slow** (many rounds, or lots of memory), and the salt makes the same password give different keys for different files. Use **Argon2id** or **scrypt** (memory-hard, best), or **PBKDF2-HMAC-SHA256** with 600,000+ iterations (OWASP). Store the salt (not secret) with the ciphertext: same password + same salt = same key; new salt = completely different key.

</En>
<Ur>

Jab data **insaan** ko kholna ho (password manager, encrypted backup), **password-based KDF** password aur random **salt** ko khench kar sahi key banata hai. Passwords chhote aur andaze ke qabil hain; KDF **har andaza sust** banata hai (bohot se rounds, ya zyada memory), aur salt ek hi password se alag files ke liye alag keys banata hai. **Argon2id** ya **scrypt** (memory-hard, behtareen), ya 600,000+ iterations ke saath **PBKDF2-HMAC-SHA256** (OWASP) lein. Salt (raaz nahi) ciphertext ke saath rakhein: wahi password + wahi salt = wahi key; naya salt = bilkul alag key.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib
salt_a, salt_b = b"\x01" * 16, b"\x02" * 16     # demo salts; real ones come from os.urandom(16)
k1 = hashlib.pbkdf2_hmac("sha256", b"CorrectHorse", salt_a, 600_000)
k2 = hashlib.pbkdf2_hmac("sha256", b"CorrectHorse", salt_a, 600_000)
k3 = hashlib.pbkdf2_hmac("sha256", b"CorrectHorse", salt_b, 600_000)
print("key length       :", len(k1), "bytes")
print("same pw, same salt:", k1.hex()[:16], "equal:", k1 == k2)
print("same pw, new salt :", k3.hex()[:16])
PY
```

```text output
key length       : 32 bytes
same pw, same salt: 35db16a6f905d559 equal: True
same pw, new salt : aa5ebeb4aa490a37
```

<Happened>
<Tr>
<En>`pbkdf2_hmac` ran HMAC-SHA256 600,000 times to make a 32-byte key, which takes a noticeable fraction of a second: exactly the point, since it costs an attacker the same for every guess. Same password and salt gave the same key (decryption possible later); a new salt gave a totally different key, so attackers can't precompute keys for common passwords once and reuse them.</En>
<Ur>`pbkdf2_hmac` ne 32-byte key banane ke liye HMAC-SHA256 600,000 dafa chalaya, jo second ka mehsoos hone wala hissa leta hai: yahi maqsad hai, kyun ke hamla awar ko har andaze par itna hi kharch aata hai. Wahi password aur salt ne wahi key di (baad me decryption mumkin); naye salt ne bilkul alag key di, isliye hamla awar aam passwords ki keys ek dafa pehle se bana kar dobara istemal nahi kar sakte.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Encrypt files with OpenSSL">

<Tr>
<En>

`openssl enc` encrypts and decrypts files with a password, available on every Linux and macOS system. Always pass `-pbkdf2` and a high `-iter` (old defaults derive the key with one weak hash). `openssl enc` doesn't support GCM, so it can't detect tampering; for new work, **age** (`age -p file`) or **gpg --symmetric** are better. The output starts with `Salted__` and the random salt, which OpenSSL reads back when decrypting.

</En>
<Ur>

`openssl enc` password se files encrypt aur decrypt karta hai, har Linux aur macOS par maujood. Output `Salted__` aur random salt se shuru hota hai, jo OpenSSL decrypt karte waqt wapas parhta hai.

</Ur>

<Step title="Envelope encryption and key rotation">

<Tr>
<En>

**Envelope encryption** uses two levels of keys: a **data key (DEK)** encrypts the data, and a **master key (KEK)** inside a KMS or HSM encrypts ("wraps") the data key. You store the encrypted data **plus the wrapped data key**. The master key never leaves the KMS, every use is permission-checked and logged, and **rotating** it only re-wraps small data keys instead of re-encrypting terabytes. Used by S3, EBS, RDS, Kubernetes Secrets at rest and SOPS (AWS KMS `GenerateDataKey`, Google Cloud KMS, Azure Key Vault, Vault transit). To read: ask the KMS to unwrap the data key, then decrypt locally.

</En>
<Ur>

**Envelope encryption** keys ke do darje istemal karti hai: **data key (DEK)** data encrypt karti hai, aur KMS ya HSM ke andar **master key (KEK)** data key ko encrypt ("wrap") karti hai. Aap encrypted data **aur wrap ki hui data key** rakhte hain. Master key kabhi KMS se bahar nahi jati, har istemal ki ijazat check aur record hoti hai, aur use **rotate** karna terabytes dobara encrypt karne ke bajaye sirf chhoti data keys dobara wrap karta hai. S3, EBS, RDS, Kubernetes Secrets at rest aur SOPS isay istemal karte hain (AWS KMS `GenerateDataKey`, Google Cloud KMS, Azure Key Vault, Vault transit). Parhne ke liye: KMS se data key unwrap karwayen, phir local decrypt.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

master_key = AESGCM.generate_key(bit_length=256)        # lives in the KMS, never exported
data_key = AESGCM.generate_key(bit_length=256)          # one per file / record set
n_doc, n_wrap = os.urandom(12), os.urandom(12)

document = AESGCM(data_key).encrypt(n_doc, b"10 GB of customer records...", None)
wrapped_key = AESGCM(master_key).encrypt(n_wrap, data_key, None)
del data_key                                             # only the wrapped copy is stored
print("stored: encrypted document +", len(wrapped_key), "byte wrapped data key")

unwrapped = AESGCM(master_key).decrypt(n_wrap, wrapped_key, None)   # "KMS decrypt" call
print("read back:", AESGCM(unwrapped).decrypt(n_doc, document, None).decode())

new_master, n_new = AESGCM.generate_key(bit_length=256), os.urandom(12)
rewrapped = AESGCM(new_master).encrypt(n_new, AESGCM(master_key).decrypt(n_wrap, wrapped_key, None), None)
still_ok = AESGCM(AESGCM(new_master).decrypt(n_new, rewrapped, None)).decrypt(n_doc, document, None) == b"10 GB of customer records..."
print("master key rotated without re-encrypting the document; still readable:", still_ok)
PY
```

```text output
stored: encrypted document + 48 byte wrapped data key
read back: 10 GB of customer records...
master key rotated without re-encrypting the document; still readable: True
```

<Happened>
<Tr>
<En>The document was encrypted with the data key, and the data key with the master key: the wrapped key is 48 bytes (32 key + 16 tag). `del data_key` shows the plaintext data key isn't kept. Reading unwrapped the data key, then decrypted the document. **Rotation:** a new master key re-wrapped the same data key, so only 48 bytes were re-encrypted, the "10 GB" document wasn't touched, and it stayed readable.</En>
<Ur>Document data key se encrypt hua, aur data key master key se: wrap ki hui key 48 bytes ki hai (32 key + 16 tag). `del data_key` dikhata hai ke saada data key rakhi nahi jati. Parhne ke liye data key unwrap hui, phir document decrypt hua. **Rotation:** nayi master key ne wahi data key dobara wrap ki, isliye sirf 48 bytes dobara encrypt hue, "10 GB" document ko chhua nahi gaya, aur wo parhne ke qabil raha.</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Home-made, hard-coded, unauthenticated">

```text
KEY = b"mysecretkey12345"                       # hard-coded in the repo
cipher = AES.new(KEY, AES.MODE_ECB)             # patterns leak, no integrity
token = cipher.encrypt(pad(user_data))
```

</Bad>
<Good title="Random key from a KMS, AEAD, fresh nonce">

```text
key = kms.generate_data_key(...)                # wrapped key stored with data
nonce = os.urandom(12)
token = nonce + AESGCM(key).encrypt(nonce, user_data, b"user:1042")
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Inventing your own encryption** (XOR with a password, "custom algorithms").
- **Reusing a nonce/IV** with the same key, or using a fixed IV.
- **Encryption without integrity** (CBC or CTR without a MAC).
- **Storing the key next to the encrypted data**, or in container images.
- **A password used directly as a key**, or a fast hash of it, instead of a slow salted KDF.
- **Ignoring decryption errors** or falling back to "use the data anyway".
- **Never rotating keys**, with no plan for a leak.
- **Encrypting passwords** for storage: passwords are **hashed**, not encrypted.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Apni encryption banana** (password se XOR, "khaas algorithms").
- Wahi key ke saath **nonce/IV dohrana**, ya muqarrar IV.
- **Saalimiyat ke baghair encryption** (MAC ke baghair CBC ya CTR).
- **Key encrypted data ke saath rakhna**, ya container images me.
- **Password ko seedha key banana**, ya us ka tez hash, sust salt wale KDF ke bajaye.
- **Decryption errors nazar andaz** karna ya "phir bhi data istemal karo".
- **Keys kabhi rotate na karna**, leak ka koi mansooba nahi.
- Storage ke liye **passwords encrypt karna**: passwords **hash** hote hain, encrypt nahi.

</Ur>
</Tr>

<Tr>
<En>

</En>
<Ur>
Password → scrypt key, har file ke liye random salt aur nonce, associated data ke tor par file format header ke saath AES-GCM, aur ghalat password ya badli file par saaf errors.

```bash
cat > vault.py <<'PY'
import os, sys
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives.kdf.scrypt import Scrypt
from cryptography.exceptions import InvalidTag

MAGIC = b"DGV1"                      # file format marker + version

def derive_key(password: str, salt: bytes) -> bytes:
    return Scrypt(salt=salt, length=32, n=2**15, r=8, p=1).derive(password.encode())

def encrypt(path, password):
    data = open(path, "rb").read()
    salt, nonce = os.urandom(16), os.urandom(12)
    ct = AESGCM(derive_key(password, salt)).encrypt(nonce, data, MAGIC)
    open(path + ".vault", "wb").write(MAGIC + salt + nonce + ct)
    print(f"encrypted {len(data)} bytes -> {len(MAGIC + salt + nonce + ct)} bytes")

def decrypt(path, password):
    blob = open(path, "rb").read()
    if blob[:4] != MAGIC:
        sys.exit("not a vault file")
    salt, nonce, ct = blob[4:20], blob[20:32], blob[32:]
    try:
        print(AESGCM(derive_key(password, salt)).decrypt(nonce, ct, MAGIC).decode(), end="")
    except InvalidTag:
        print("ERROR: wrong password or file was modified")

cmd, path, password = sys.argv[1:4]
encrypt(path, password) if cmd == "enc" else decrypt(path, password)
PY
printf 'DB_PASSWORD=S3cureP@ss2026\nAPI_KEY=sk_live_example\n' > prod.env
python3 vault.py enc prod.env "my long passphrase 2026"
python3 -c 'print("plaintext visible in the vault file?", b"S3cure" in open("prod.env.vault", "rb").read())'
python3 vault.py dec prod.env.vault "my long passphrase 2026"
python3 vault.py dec prod.env.vault "wrong guess"
python3 -c '
blob = bytearray(open("prod.env.vault", "rb").read()); blob[-20] ^= 1
open("prod.env.vault", "wb").write(blob)'
python3 vault.py dec prod.env.vault "my long passphrase 2026"
```

```text output
plaintext visible in the vault file? False
DB_PASSWORD=S3cureP@ss2026
API_KEY=sk_live_example
ERROR: wrong password or file was modified
ERROR: wrong password or file was modified
```

A fresh salt and nonce per file mean encrypting twice gives different output and nonces never repeat. `MAGIC` as associated data authenticates the header. The last step flips one bit, and decryption refuses even with the right passphrase.</En>
<Ur>File format: `DGV1` (4 bytes) + salt (16) + nonce (12) + ciphertext (51) + tag (16) = 99. `n=2**15` wala scrypt har andaze par takreeban 32 MB leta hai. Har file ka taaza salt aur nonce ka matlab do dafa encrypt karne par alag output aur nonces kabhi nahi dohrate. Associated data ke tor par `MAGIC` header ki tasdeeq karta hai. <DeepDive title="Real world: the leaked credential that exposed nothing">

A fintech company stores customers' ID numbers and bank account numbers in PostgreSQL. Disk encryption (RDS encryption at rest) protects against stolen disks, but not against someone with database access through SQL injection or a leaked read-only credential. So the app adds **field-level envelope encryption**: each sensitive column is encrypted with AES-256-GCM using a data key wrapped by an AWS KMS key, with the row's primary key as **associated data** so values can't be swapped. Only the payments service's IAM role may call `kms:Decrypt`, and every call appears in CloudTrail. When a developer's database credential later leaks, the attacker dumps the tables but sees only ciphertext, and the KMS logs show no decrypt calls from unknown identities, so the team can show regulators the sensitive data wasn't exposed. The master key is rotated yearly without re-encrypting the data.

</DeepDive>

<DeepDive title="Security lens">

Encryption moves the problem from protecting data to protecting keys. Most real failures are key-management failures, not broken algorithms.

- **Use vetted, high-level libraries:** libsodium/NaCl, Google Tink, AWS Encryption SDK, `age`, or `cryptography`'s AEAD classes. They pick safe modes and nonces.
- **Keys in a KMS/HSM:** least-privilege IAM for encrypt/decrypt, audit logs, automatic rotation, separation of duties.
- **Defence in depth:** disk encryption for stolen hardware, field-level encryption for database compromise, TLS for transit. Each covers different threats.
- **Crypto-agility:** store the algorithm and key version with the ciphertext (like `DGV1`) so you can migrate later.
- **Crypto-shredding:** destroying a data key makes the data unrecoverable, useful for GDPR erasure and decommissioning.
- **Side channels:** ciphertext still leaks length and timing; compress-then-encrypt can leak secrets (CRIME/BREACH).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is symmetric encryption and what are its strengths and weaknesses?">
Symmetric encryption uses the same secret key to encrypt and decrypt. It is very fast and suitable for large amounts of data, such as disks, databases and the bulk data in TLS. Its main weakness is key distribution and management: both parties need the same secret key, it must be shared securely, and every party holding it can decrypt everything.
</QA>

<QA q="Why is ECB mode insecure?">
ECB encrypts each block independently with the same key, so identical plaintext blocks produce identical ciphertext blocks. Patterns in the plaintext remain visible in the ciphertext, as in the well-known encrypted penguin image, and blocks can be rearranged. Modes with unique nonces or IVs and integrity, such as GCM, should be used instead.
</QA>

<QA q="What is authenticated encryption and why use it?">
Authenticated encryption with associated data, such as AES-GCM or ChaCha20-Poly1305, provides confidentiality and integrity together by producing a tag that is checked on decryption. Any modification of the ciphertext, the tag or the associated data causes decryption to fail, preventing attackers from tampering with encrypted data unnoticed.
</QA>

<QA q="What happens if you reuse a nonce with AES-GCM?">
Reusing a nonce with the same key makes both messages use the same keystream, so XORing the ciphertexts reveals the XOR of the plaintexts, and knowing one plaintext reveals the other. It also leaks information that allows an attacker to forge authentication tags. Nonces must be unique per key, typically random 96-bit values or non-repeating counters.
</QA>

<QA q="What is envelope encryption?">
Envelope encryption encrypts data with a data encryption key and then encrypts that data key with a key encryption key held in a key management service or HSM. The wrapped data key is stored with the data. It keeps master keys inside the KMS with access control and auditing, allows efficient key rotation by re-wrapping only data keys, and is used by cloud services such as AWS KMS.
</QA>

</DeepDive>
