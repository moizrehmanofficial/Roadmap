<BigIdea>
<Tr>
<En>
A website should **never be able to read your password**. It stores a **password hash**: at signup it hashes the password, at login it hashes what you typed and compares. But ordinary hashes (MD5, SHA-1, SHA-256) are **too fast**: after a database leak, attackers try billions of guesses per second. Correct storage needs a unique random **salt** per user, a deliberately **slow, memory-hard** algorithm (**Argon2id** first, then **scrypt** or **bcrypt**), and a **cost** you raise over time, upgrading old hashes at login. Libraries do all of this; your job is to pick the right one, never invent your own scheme, and add breached-password checks, rate limiting and MFA around it.
</En>
<Ur>
Website ko **aap ka password kabhi parhne ke qabil nahi** hona chahiye. Wo **password hash** rakhti hai: signup par password hash karti hai, login par aap ka type kiya hash kar ke milati hai. Lekin aam hashes (MD5, SHA-1, SHA-256) **bohot tez** hain: database leak ke baad hamla awar har second arbon andaze lagate hain. Sahi tareeqe ke liye har user ka munfarid random **salt**, jaan boojh kar **sust, memory-hard** algorithm (pehle **Argon2id**, phir **scrypt** ya **bcrypt**), aur waqt ke saath barhne wali **cost** chahiye, login par purane hashes upgrade karte hue. Libraries ye sab karti hain; aap ka kaam sahi library chunna, apna tareeqa kabhi na ghadna, aur us ke gird breached-password checks, rate limiting aur MFA lagana hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Imagine a club where the doorman checks a secret phrase. A **bad** club writes every member's phrase in a notebook (plaintext): steal the notebook, get every phrase. A **better** club stores a fingerprint of each phrase (a hash), but if a thief can test a billion phrases a second, they'll still find most. The **best** club makes each check take a quarter of a second of hard work (a **slow hash**) and mixes a different random ingredient into every member's fingerprint (a **salt**). The doorman barely notices a quarter second per member, but a thief trying billions of guesses now needs centuries.

</En>
<Ur>

Ek club sochein jahan darban ek khufia jumla check karta hai. **Bura** club har member ka jumla copy me likhta hai (plaintext): copy chura lo, sab jumle mil gaye. **Behtar** club har jumle ka fingerprint (hash) rakhta hai, lekin agar chor har second arab jumle aazma sake to phir bhi zyada tar dhoondh lega. **Behtareen** club har check ko chauthai second ki mehnat banata hai (**sust hash**) aur har member ke fingerprint me alag random cheez milata hai (**salt**). Darban ko fi member chauthai second mehsoos bhi nahi hota, lekin arbon andaze lagane wale chor ko ab sadiyan chahiyen.

</Ur>
</Tr>

<Walkthrough>

<Step title="The wrong ways: plaintext and encryption">

<Tr>
<En>

Storing passwords as **plaintext**, or **encrypted** with a key the server holds, means anyone who gets the database (plus the key, usually on the same server) gets every password instantly. If a website can email you your **current** password ("Forgot password? Here it is!"), it's storing it wrongly. This still turns up in old PHP apps, internal tools, IoT devices and spreadsheets of "admin credentials". Passwords must be stored so **nobody**, not even developers or admins, can read them: that means **one-way hashing**.

</En>
<Ur>

Passwords **plaintext** me, ya server ke paas maujood key se **encrypted** rakhne ka matlab hai ke database (aur key, jo aam taur par usi server par hoti hai) paane wala fauran har password pa leta hai. Agar website aap ko aap ka **maujooda** password email kar sake ("Password bhool gaye? Ye lo!") to wo ghalat tareeqe se rakh rahi hai. Ye ab bhi purani PHP apps, andaruni tools, IoT devices aur "admin credentials" ki spreadsheets me milta hai. Passwords aise rakhne chahiyen ke **koi** bhi, developers ya admins bhi, na parh saken: yaani **ek-taraf hashing**.

</Ur>
</Tr>

</Step>

<Step title="Plain hashes: better, but crackable">

<Tr>
<En>

Storing `SHA-256(password)` without a salt has two problems. **Identical passwords give identical hashes**, so one cracked hash reveals everyone using that password. And attackers build **lookup tables** once (hash → password for billions of common passwords) and reuse them on every leak; sites like crackstation.net offer them free. LinkedIn's 2012 leak was unsalted SHA-1, and most of it was cracked within days.

</En>
<Ur>

Bina salt `SHA-256(password)` rakhne ke do masle hain. **Ek jaise passwords ke ek jaise hashes**, isliye ek crack hua hash us password wale sab log khol deta hai. Aur hamla awar ek dafa **lookup tables** banate hain (arbon aam passwords ke liye hash → password) aur har leak par dobara istemal karte hain; crackstation.net jaisi sites ye muft deti hain. LinkedIn ka 2012 leak bina salt SHA-1 tha, aur zyada tar chand dinon me crack ho gaya.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib
users = {"sam": "london123", "emma": "Emma@2026!", "jack": "london123", "grace": "123456"}
print("--- what the leaked table looks like:")
for user, password in users.items():
    print(f"  {user:6} {hashlib.sha256(password.encode()).hexdigest()[:20]}...")

common = ["123456", "password", "london123", "qwerty", "iloveyou"]
lookup = {hashlib.sha256(w.encode()).hexdigest(): w for w in common}     # built once, reused forever
print("--- attacker's lookup table result:")
for user, password in users.items():
    print(f"  {user:6} -> {lookup.get(hashlib.sha256(password.encode()).hexdigest(), 'not found')}")
PY
```

<Happened>
<Tr>
<En>Each password was hashed with SHA-256, no salt. **Sam and Jack have the same hash**: without cracking anything, an attacker knows they share a password. The lookup table maps hashes of common passwords back to the passwords, so three of four accounts fell at once. Only Emma's less common password wasn't in this tiny table (a real table with billions of entries or a GPU run would likely find it too).</En>
<Ur>Har password SHA-256 se hash hua, bina salt. **Sam aur Jack ka hash ek hai**: kuch crack kiye baghair hamla awar jaan leta hai ke dono ka password ek hai. Lookup table aam passwords ke hashes ko wapas passwords se milati hai, isliye chaar me se teen accounts fauran gire. Sirf Emma ka kam aam password is chhoti table me nahi tha (arbon entries wali asli table ya GPU run shayad use bhi dhoondh le).</Ur>
</Tr>
</Happened>

</Step>

<Step title="Salts: unique per user">

<Tr>
<En>

A **salt** is a random value (16 bytes is standard) generated **for each user**, combined with the password before hashing, and stored next to the hash. It is **not secret**. Identical passwords now give **different** hashes, and precomputed tables become useless: the attacker must attack each hash separately. Modern algorithms generate and store the salt **automatically**. But a salt doesn't make one weak password strong: `london123` can still be guessed against a single salted hash. That's why we also need **slow** hashing.

</En>
<Ur>

**Salt** ek random value hai (16 bytes standard) jo **har user ke liye** banti hai, hashing se pehle password se milti hai, aur hash ke saath rakhi jati hai. Ye **raaz nahi**. Ab ek jaise passwords ke **alag** hashes bante hain, aur pehle se bani tables bekaar ho jati hain: hamla awar ko har hash par alag hamla karna parta hai. Jadeed algorithms salt **khud** banate aur rakhte hain. Lekin salt ek kamzor password ko mazboot nahi banata: ek salted hash par `london123` phir bhi andaze se mil sakta hai. Isi liye **sust** hashing bhi chahiye.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib, os
hashes = {}
for user in ["sam", "jack"]:
    salt = os.urandom(16)                                   # new random salt for every user
    hashes[user] = hashlib.sha256(salt + b"london123").hexdigest()
    print(f"{user:6} gets a {len(salt)}-byte random salt and a {len(hashes[user])}-character hash")
print("same password, same hash?", hashes["sam"] == hashes["jack"])
PY
```

```text output
sam    gets a 16-byte random salt and a 64-character hash
jack   gets a 16-byte random salt and a 64-character hash
same password, same hash? False
```

<Happened>
<Tr>
<En>`os.urandom(16)` made a fresh 16-byte salt per user (the values change every run, so only sizes are printed). The input was `salt + password`: same password, different salts, completely different hashes, so Sam and Jack no longer look alike. This is still SHA-256, which is too **fast**; never use salted SHA-256 for real passwords.</En>
<Ur>`os.urandom(16)` ne har user ke liye naya 16-byte salt banaya (values har dafa badalti hain, isliye sirf size chhape). Input `salt + password` tha: wahi password, alag salts, bilkul alag hashes, isliye Sam aur Jack ab ek jaise nahi dikhte. Ye ab bhi SHA-256 hai jo bohot **tez** hai; asli passwords ke liye salted SHA-256 kabhi istemal na karein.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Speed is the enemy: slow hashes">

<Tr>
<En>

Password hashing algorithms are **slow** on purpose (ideally **memory-hard**), with an adjustable **cost**. Your server hashes once per login, so 100–500 ms is fine; an attacker hashes **every guess**, so making each one 400,000 times slower turns "cracked in an hour" into "not cracked in centuries". Choices: **Argon2id** (Password Hashing Competition winner, OWASP's first choice), **scrypt**, **bcrypt** (older but fine), **PBKDF2** (for FIPS, 600,000+ iterations). Tune to about 100–500 ms on production servers and raise it as hardware improves.

</En>
<Ur>

Password hashing algorithms jaan boojh kar **sust** (behtar ho to **memory-hard**) hote hain, badalne wali **cost** ke saath. Aap ka server har login par ek dafa hash karta hai, isliye 100–500 ms theek hai; hamla awar **har andaze** ko hash karta hai, isliye har ek ko 400,000 guna sust karna "ghante me crack" ko "sadiyon me bhi nahi" bana deta hai. Intikhab: **Argon2id** (Password Hashing Competition ka faateh, OWASP ki pehli pasand), **scrypt**, **bcrypt** (purana magar theek), **PBKDF2** (FIPS ke liye, 600,000+ iterations). Production servers par taqreeban 100–500 ms par set karein aur hardware behtar hone par barhayen.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import time, hashlib, bcrypt
from argon2 import PasswordHasher

def avg_seconds(fn, runs):
    start = time.perf_counter()
    for _ in range(runs):
        fn()
    return (time.perf_counter() - start) / runs

sha = avg_seconds(lambda: hashlib.sha256(b"london123").digest(), 20000)
bc = avg_seconds(lambda: bcrypt.hashpw(b"london123", bcrypt.gensalt(12)), 3)
ar = avg_seconds(lambda: PasswordHasher().hash("london123"), 3)
print("SHA-256 takes under 0.01 ms per guess:", sha < 0.00001)
print("bcrypt (cost 12) takes over 50 ms:     ", bc > 0.05)
print("Argon2id (defaults) takes over 20 ms:  ", ar > 0.02)
print("bcrypt is over 10,000x slower than SHA-256:", bc / sha > 10_000)
PY
```

```text output
SHA-256 takes under 0.01 ms per guess: True
bcrypt (cost 12) takes over 50 ms:      True
Argon2id (defaults) takes over 20 ms:   True
bcrypt is over 10,000x slower than SHA-256: True
```

<Happened>
<Tr>
<En>`avg_seconds` ran each function many times and averaged. SHA-256 took well under a microsecond (on a GPU attackers get billions per second). bcrypt cost 12 and Argon2id with defaults (64 MB, 3 passes) each took a large fraction of a second. Exact times depend on the machine, so we print comparisons, not numbers. For a user that's a short pause; for an attacker trying a billion passwords it's minutes versus many years.</En>
<Ur>`avg_seconds` ne har function bohot dafa chala kar average nikala. SHA-256 ne ek microsecond se bhi kam liya (GPU par hamla awar ko har second arbon milte hain). bcrypt cost 12 aur defaults (64 MB, 3 passes) wala Argon2id dono ne second ka bara hissa liya. Asal waqt machine par munhasir hai, isliye numbers ki jagah muqable chhape. User ke liye ye chhota sa waqfa hai; arab passwords aazmane wale ke liye ye minton aur kai saalon ka farq hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="bcrypt and its hash string">

<Tr>
<En>

**bcrypt** (1999) is a slow hash based on the Blowfish cipher with a **cost** parameter: each +1 doubles the time. It's battle-tested and the default in Laravel, Rails and Spring. Use cost 12 or higher. The output looks like `$2b$12$<22-char salt><31-char hash>` (60 characters), so you store one string. Important limit: bcrypt only uses the first **72 bytes** of a password; newer libraries refuse longer input, older ones silently ignore the rest.

</En>
<Ur>

**bcrypt** (1999) Blowfish cipher par bana sust hash hai jis me **cost** parameter hai: har +1 waqt dugna karta hai. Aazmaya hua hai aur Laravel, Rails aur Spring ka default. Cost 12 ya zyada rakhein. Output `$2b$12$<22-char salt><31-char hash>` (60 characters) jaisa hota hai, isliye ek hi string rakhte hain. Aham hadd: bcrypt password ke sirf pehle **72 bytes** istemal karta hai; nayi libraries lamba input radd karti hain, purani baqi chupke se nazar andaz karti hain.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import bcrypt
demo_salt = b"$2b$12$" + b"abcdefghijklmnopqrstuu"          # fixed only so the output is reproducible
stored = bcrypt.hashpw(b"london123", demo_salt).decode()
print(stored)
algo, cost, rest = stored.split("$")[1:]
print(f"algorithm={algo} cost={cost} (2^{cost} rounds) salt={rest[:22]} hash={rest[22:31]}...")
print("correct password:", bcrypt.checkpw(b"london123", stored.encode()))
print("capital L       :", bcrypt.checkpw(b"London123", stored.encode()))
try:
    bcrypt.hashpw(b"a" * 80, bcrypt.gensalt())
except ValueError as err:
    print("80-byte password:", err)
PY
```

```text output
$2b$12$abcdefghijklmnopqrstuu4mAvZ.Rxxqtu9Z5E8Th2xXFqKHkv6kS
algorithm=2b cost=12 (2^12 rounds) salt=abcdefghijklmnopqrstuu hash=4mAvZ.Rxx...
correct password: True
capital L       : False
80-byte password: password cannot be longer than 72 bytes, truncate manually if necessary (e.g. my_password[:72])
```

<Happened>
<Tr>
<En>

- Normally you'd call `bcrypt.gensalt(12)` for a random salt; a fixed salt here makes the output reproducible.
- The string describes itself: `2b` = version, `12` = cost (2^12 = 4,096 rounds), then 22 characters of salt and 31 of hash.
- `checkpw` reads cost and salt from the string, re-hashes the typed password and compares in constant time: `London123` with a capital L doesn't match.
- An 80-byte password was refused. With older versions, two long passwords differing only after byte 72 would both be accepted.

</En>
<Ur>

- Aam taur par random salt ke liye `bcrypt.gensalt(12)` chalate hain; yahan muqarrar salt output qaim rakhta hai.
- String apna bayan khud hai: `2b` = version, `12` = cost (2^12 = 4,096 rounds), phir 22 characters salt aur 31 hash.
- `checkpw` string se cost aur salt parhta hai, type kiya password dobara hash kar ke constant time me milata hai: bare L wala `London123` nahi milta.
- 80-byte password radd hua. Purane versions me sirf 72 byte ke baad farq wale do lambe passwords dono qubool ho jate.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Argon2id: the modern default">

<Tr>
<En>

**Argon2id** has three cost parameters: **memory** (`m`, in KiB), **iterations** (`t`) and **parallelism** (`p`). Needing lots of memory per guess makes GPU and ASIC cracking far less efficient than with bcrypt or PBKDF2. It's the first choice for new systems: `argon2-cffi` (Python), `argon2` (Node), PHP `password_hash($pw, PASSWORD_ARGON2ID)`, Spring's `Argon2PasswordEncoder`, Django's `Argon2PasswordHasher`. OWASP's minimum is m=19 MiB, t=2, p=1; library defaults are often stronger.

</En>
<Ur>

**Argon2id** ke teen cost parameters hain: **memory** (`m`, KiB me), **iterations** (`t`) aur **parallelism** (`p`). Har andaze par bohot memory maangna GPU aur ASIC cracking ko bcrypt ya PBKDF2 se kahin kam mufeed banata hai. Naye systems ki pehli pasand: `argon2-cffi` (Python), `argon2` (Node), PHP `password_hash($pw, PASSWORD_ARGON2ID)`, Spring ka `Argon2PasswordEncoder`, Django ka `Argon2PasswordHasher`. OWASP ki kam se kam hadd m=19 MiB, t=2, p=1 hai; library defaults aksar mazboot hote hain.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError
ph = PasswordHasher()
stored = ph.hash("long-mango-season-chicago-42")
parts = stored.split("$")
print("algorithm :", parts[1])
print("version   :", parts[2])
print("parameters:", parts[3])
print("salt+hash : <random each time>, total length", len(stored))
print("verify    :", ph.verify(stored, "long-mango-season-chicago-42"))
try:
    ph.verify(stored, "long-mango-season-chicago-43")
except VerifyMismatchError:
    print("wrong pw  : VerifyMismatchError")
PY
```

<Happened>
<Tr>
<En>`PasswordHasher()` used Argon2id with safe defaults and a random salt. The string records the algorithm, version (`v=19` = 0x13 = Argon2 1.3) and parameters: 65,536 KiB = 64 MiB of memory, 3 iterations, 4 lanes. `verify` returned `True` for the right password and **raised** `VerifyMismatchError` for a wrong one, so a failure can't be treated as success by accident.</En>
<Ur>`PasswordHasher()` ne mehfooz defaults aur random salt ke saath Argon2id istemal kiya. String algorithm, version (`v=19` = 0x13 = Argon2 1.3) aur parameters darj karti hai: 65,536 KiB = 64 MiB memory, 3 iterations, 4 lanes. `verify` ne sahi password par `True` diya aur ghalat par `VerifyMismatchError` **uthaya**, isliye nakaami ghalti se kaamyabi nahi samjhi ja sakti.</Ur>

<Step title="Upgrading hashes on login">

<Tr>
<En>

When a user logs in successfully, you briefly have their real password. If their stored hash uses old or weak settings, **re-hash** it with current settings and save it. Hardware gets faster, so costs must rise, and old algorithms must be phased out without forcing everyone to reset. `argon2-cffi` has `check_needs_rehash`, PHP has `password_needs_rehash`, and Django and Laravel do it automatically.

</En>
<Ur>

Jab user kaamyabi se login kare to thori der aap ke paas us ka asli password hota hai. Agar mehfooz hash purani ya kamzor settings ka hai to use maujooda settings se **dobara hash** kar ke save karein. Hardware tez hota jata hai, isliye cost barhni chahiye, aur purane algorithms sab ko reset par majboor kiye baghair khatam hone chahiyen. `argon2-cffi` me `check_needs_rehash`, PHP me `password_needs_rehash` hai, aur Django aur Laravel ye khud karte hain.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from argon2 import PasswordHasher

print("stored with:", stored.split("$")[3])

current = PasswordHasher()                                                      # today's settings
if current.verify(stored, "Emma@2026!"):
    print("login ok; needs rehash?", current.check_needs_rehash(stored))
    stored = current.hash("Emma@2026!")
    print("upgraded to:", stored.split("$")[3])
PY
```

<Ur>Purane hash ne 19 MiB aur 1 iteration istemal ki. Maujooda hasher phir bhi use **verify** kar saka kyun ke parameters string ke andar hain, isliye login chal gaya. `check_needs_rehash` ne mehfooz aur maujooda parameters milaye, alag paye, isliye password nayi settings se dobara hash ho kar save hua.</Ur>

<Step title="Peppers: a secret outside the database">

<Tr>
<En>

A **pepper** is a secret (like a key) stored **outside** the database, in a secret manager, environment variable or HSM, and mixed into every password before hashing, typically as `HMAC(pepper, password)`. If attackers steal **only** the database (SQL injection, a leaked backup), they can't even start guessing. It's an **extra** layer on top of a proper password hash, never a replacement. Plan for rotation (store a pepper version with each hash) and back it up: lose the pepper and every password becomes unverifiable. The challenge below uses one.

</En>
<Ur>

**Pepper** ek raaz (key jaisa) hai jo database se **bahar** secret manager, environment variable ya HSM me rakha jata hai, aur hashing se pehle har password me milaya jata hai, aam taur par `HMAC(pepper, password)` ki shakal me. Agar hamla awar **sirf** database churayen (SQL injection, leak hua backup) to wo andaze lagana shuru bhi nahi kar sakte. Ye sahi password hash ke upar **izafi** parat hai, kabhi us ki jagah nahi. Badalne ka intizam karein (har hash ke saath pepper version rakhein) aur backup lein: pepper kho gaya to koi password verify nahi hoga. Neeche ka challenge ek istemal karta hai.

</Ur>
</Tr>

</Step>

<Step title="Migrating a legacy MD5/SHA-1 database">

<Tr>
<En>

You inherit a system storing `md5(password)`. You can't recompute proper hashes without the passwords, and waiting for everyone to log in leaves weak hashes for years. **Wrap** immediately: store `argon2id(md5_hash)` for every user now, marked as "wrapped". At login, compute `md5(typed)`, verify it against the wrapped hash, and on success replace it with a normal `argon2id(password)`. After a deadline, force a reset for accounts that never logged in.

</En>
<Ur>

Aap ko wirse me aisa system mila jo `md5(password)` rakhta hai. Passwords ke baghair sahi hashes dobara nahi ban sakte, aur sab ke login ka intezar kamzor hashes saalon rakhta hai. Fauran **lapetein**: abhi har user ke liye `argon2id(md5_hash)` rakhein, "wrapped" nishan ke saath. Login par `md5(typed)` nikalein, wrapped hash se verify karein, aur kaamyabi par aam `argon2id(password)` se badal dein. Muddat ke baad kabhi login na karne wale accounts ka reset lazmi karein.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib
from argon2 import PasswordHasher

record = {"scheme": "argon2(md5)", "hash": ph.hash(legacy_md5)}   # wrapped today, md5 deleted
print("migrated record scheme:", record["scheme"])

typed = "Houston#2019"                                            # user logs in later
if record["scheme"] == "argon2(md5)" and ph.verify(record["hash"], hashlib.md5(typed.encode()).hexdigest()):
    record = {"scheme": "argon2", "hash": ph.hash(typed)}
print("after login:", record["scheme"], "| contains md5?", legacy_md5 in record["hash"])
PY
```

At the next login, the typed password was MD5'd, verified against the wrapped hash, and replaced with a clean `argon2(password)`.</En>
<Ur>`legacy_md5` purane database ke kamzor hash ki jagah hai. Migration ke din har MD5 hash ko khud Argon2id se hash kiya aur nanga MD5 mita diya, isliye kisi ke login se pehle bhi chori hua database sirf sust hashes rakhta hai. <Step title="Password rules that actually help">

<Tr>
<En>

Modern guidance (NIST SP 800-63B) focuses on **length** and **known-bad passwords**, not composition rules: "one uppercase, one digit, one symbol" gives `Password1!`, and forced 90-day changes give `Summer2026!` → `Autumn2026!`. Instead:

- Minimum **8** characters, preferably 12–15+; allow at least 64, spaces and all characters (passphrases).
- **Block** passwords from breach lists, dictionary words and context-specific ones (site name, username).
- **No** forced periodic changes without evidence of compromise; **no** hints or security questions.
- Allow paste and password managers.

Check breaches with Have I Been Pwned's **k-anonymity** API: send only the first 5 hex characters of the SHA-1, get all matching suffixes, compare locally.

</En>
<Ur>

Jadeed rehnumai (NIST SP 800-63B) **lambai** aur **maloom bure passwords** par tawajjo deti hai, banawat ke qawaid par nahi: "ek bara harf, ek hindsa, ek symbol" se `Password1!` banta hai, aur har 90 din lazmi tabdeeli se `Summer2026!` → `Autumn2026!`. Is ke bajaye:

- Kam se kam **8** characters, behtar 12–15+; kam se kam 64, spaces aur har character ki ijazat (passphrases).
- Breach lists, dictionary alfaaz aur siyaq wale (site ka naam, username) passwords **rokein**.
- Compromise ke saboot ke baghair **koi** lazmi tabdeeli nahi; **na** hints na security questions.
- Paste aur password managers ki ijazat.

Have I Been Pwned ke **k-anonymity** API se breaches check karein: SHA-1 ke sirf pehle 5 hex characters bhejein, saare milte suffixes lein, apne paas milayen.

</Ur>
</Tr>

<Step title="Around the hash: the rest of login security">

<Tr>
<En>

Strong hashing protects passwords **after** a breach; other controls protect **live** accounts. Attackers mostly don't crack hashes: they use **credential stuffing**, phishing and brute force against the login form. Add rate limiting and temporary lockouts, CAPTCHA after suspicious activity, **MFA** (TOTP apps, and best of all **passkeys/WebAuthn**, which resist phishing), generic error messages ("invalid username or password"), login alerts and secure reset flows. Keep login time similar for unknown and known usernames so attackers can't discover which accounts exist.

</En>
<Ur>

Mazboot hashing breach ke **baad** passwords bachati hai; doosre intizamat **zinda** accounts bachate hain. Hamla awar zyada tar hashes crack nahi karte: wo login form par **credential stuffing**, phishing aur brute force karte hain. Rate limiting aur waqti lockouts, mashkook harkat ke baad CAPTCHA, **MFA** (TOTP apps, aur sab se behtar **passkeys/WebAuthn** jo phishing se bachte hain), aam error paigham ("invalid username or password"), login alerts aur mehfooz reset flows joren. Na-maloom aur maloom usernames ke login ka waqt milta julta rakhein taa ke hamla awar ye na jaan saken kaun se accounts maujood hain.

</Ur>

<Compare>
<Bad title="Homemade and fast">

</Bad>

```text

```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Plaintext or reversible encryption** for passwords.
- **Fast hashes** (MD5, SHA-1, SHA-256, even salted) for password storage.
- **One global salt** for everyone, or a salt derived from the username.
- **Cost settings never increased** since the system was built.
- **bcrypt with long passwords** silently cut at 72 bytes.
- **Composition rules and forced resets** instead of length and breached-password checks.
- **Logging passwords** in request logs or error reports.
- **No rate limiting or MFA**, relying on hashing alone.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Passwords ke liye **plaintext ya wapas khulne wali encryption**.
- Password storage ke liye **tez hashes** (MD5, SHA-1, SHA-256, salt ke saath bhi).
- Sab ke liye **ek global salt**, ya username se bana salt.
- System bante waqt se **cost kabhi nahi barhayi**.
- **Lambe passwords ke saath bcrypt** jo chupke se 72 bytes par kaat de.
- Lambai aur breached-password checks ke bajaye **banawat ke qawaid aur lazmi resets**.
- Request logs ya error reports me **passwords log karna**.
- **Na rate limiting na MFA**, sirf hashing par bharosa.

</Ur>

```bash
ph = PasswordHasher()                                  # Argon2id, library defaults
BREACHED = {"123456", "password", "london123", "password1234", "iloveyou"}   # stand-in for HIBP
DB = "users.json"

    return hmac.new(PEPPER, password.encode(), hashlib.sha256).hexdigest()

def _load():
    return json.load(open(DB)) if os.path.exists(DB) else {}

def _save(users):
    json.dump(users, open(DB, "w"), indent=2)

def signup(username, password):
    if len(password) < 12:
        return "rejected: use at least 12 characters"
    if password.lower() in BREACHED:
        return "rejected: this password appears in known data breaches"
    users = _load()
    users[username] = {"hash": ph.hash(_peppered(password)), "failed": 0}
    _save(users)

def login(username, password):
    users = _load()
    user = users.get(username)
    if user is None:

        user["failed"] += 1
        _save(users)
        return "invalid username or password"
    user["failed"] = 0
    if ph.check_needs_rehash(user["hash"]):
        user["hash"] = ph.hash(_peppered(password))
    _save(users)
    return "welcome " + username
```

<DeepDive title="Real world: LinkedIn and the vault breach">

In 2016 it emerged that over 100 million LinkedIn passwords from a 2012 breach had been stored as **unsalted SHA-1**; most were cracked quickly and used in credential-stuffing attacks against other sites for years. In contrast, when a password manager company disclosed a breach of encrypted vaults, the outcome depended on users' master passwords and key-derivation iteration counts: old accounts with low PBKDF2 iterations were at much higher risk, which is why the company raised defaults and upgraded old accounts. A typical fix in an older e-commerce codebase: replace `md5($password)` with PHP's `password_hash($password, PASSWORD_ARGON2ID)`; wrap all MD5 hashes on migration day; upgrade at login with `password_needs_rehash`; add a breached-password check at signup and password change; rate-limit `/login`; and offer TOTP two-factor authentication for sellers and admins.

</DeepDive>

<DeepDive title="Security lens">

Assume your user table will leak one day. Good password storage decides whether that leak exposes your users' accounts everywhere, or nothing useful at all.

- **Use the framework's password API** (Django, Laravel `Hash::make`, ASP.NET Identity, Spring Security, PHP `password_hash`) with Argon2id or bcrypt at adequate cost.
- **Protect against online attacks:** rate limiting, lockouts or progressive delays, bot detection, MFA and passkeys.
- **Breach response:** force resets for affected accounts, revoke sessions, notify users. Strong hashing buys time; MFA limits damage.
- **Keep secrets out of logs:** mask password fields in logs, traces and error trackers.
- **Admin and service accounts:** long random passwords from a password manager plus phishing-resistant MFA.
- **Move toward passwordless:** passkeys (WebAuthn) leave only a public key on the server.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How should passwords be stored?">
As salted hashes produced by a slow, purpose-built password hashing function such as Argon2id, scrypt or bcrypt, with a cost tuned to roughly a few hundred milliseconds and increased over time. Never in plaintext, encrypted, or with fast general-purpose hashes. The library generates a unique random salt per password and stores algorithm, parameters, salt and hash together.
</QA>

<QA q="What is a salt and why is it needed?">
A salt is a random value unique to each password that is combined with it before hashing and stored alongside the hash. It ensures identical passwords produce different hashes, prevents attackers from using precomputed lookup or rainbow tables, and forces them to attack each hash separately. It does not need to be secret.
</QA>

<QA q="Why are fast hashes like SHA-256 bad for passwords?">
Attackers who steal hashes can compute billions of SHA-256 guesses per second on GPUs, so common and moderately complex passwords are cracked quickly. Password hashing functions are deliberately slow and, in the case of Argon2 and scrypt, memory-hard, which makes each guess expensive and GPU acceleration much less effective.
</QA>

<QA q="What is a pepper?">
A pepper is a secret value kept outside the database, for example in a secret manager or HSM, that is mixed into passwords before hashing, typically via HMAC. If only the database is stolen, attackers cannot verify guesses without the pepper. It is an additional layer, not a replacement for salted slow hashing, and needs a plan for backup and rotation.
</QA>

<QA q="How would you migrate a database of MD5 password hashes?">
Immediately wrap each MD5 hash with a strong algorithm, storing Argon2id of the MD5 value and deleting the bare MD5 hashes. At each user's next successful login, verify by computing MD5 of the typed password and checking it against the wrapped hash, then replace it with a normal Argon2id hash of the password. After a deadline, force resets for accounts that never logged in.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>

  <Term name="Salt">Random per-password value that defeats precomputed tables.</Term>
  <Term name="Pepper">Secret stored outside the database and mixed into passwords.</Term>
  <Term name="Work factor">Tunable cost making each hash deliberately slow.</Term>
  <Term name="Memory-hard">Requiring large memory per guess to resist GPU and ASIC attacks.</Term>
  <Term name="Argon2id">Modern memory-hard password hash; first choice today.</Term>
  <Term name="bcrypt">Widely used adaptive password hash with a 72-byte input limit.</Term>
  <Term name="scrypt / PBKDF2">Other password-based key derivation functions.</Term>
  <Term name="Rainbow / lookup table">Precomputed hash-to-password tables for unsalted hashes.</Term>
