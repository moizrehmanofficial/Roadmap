<Callout type="tip" title="In one minute">
A website should **never be able to read your password**. It stores a **password hash**: at signup it hashes the password, at login it hashes what you typed and compares. But ordinary hashes (MD5, SHA-1, SHA-256) are **too fast**: after a database leak, attackers try billions of guesses per second and crack most passwords. Correct storage needs three things: a unique random **salt** per user (so identical passwords get different hashes and precomputed tables are useless), a deliberately **slow, memory-hard** algorithm (**Argon2id** first choice, then **scrypt** or **bcrypt**), and **tunable cost** that you raise over time, upgrading old hashes when users log in. Libraries do all of this for you; your job is to pick the right one, never invent your own scheme, and add defences around it: breached-password checks, rate limiting and MFA.
</Callout>

## Start from zero

<Callout type="analogy">
Imagine a club where the doorman checks a secret phrase. A **bad** club writes every member's phrase in a notebook (plaintext): if the notebook is stolen, everyone's phrase leaks. A **better** club stores a fingerprint of each phrase (a hash). But if each fingerprint takes one second to compare and the thief can try a billion phrases a second, they'll still find most of them. The **best** club makes each check deliberately take a quarter of a second of hard work (a **slow hash**) and mixes a different random ingredient into every member's fingerprint (a **salt**). The doorman barely notices a quarter of a second per member, but a thief trying billions of guesses now needs centuries.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Password hash** | The stored, one-way result of hashing a password | `$argon2id$v=19$m=65536,...` |
| **Salt** | A random value, unique per user, mixed into the hash | 16 random bytes |
| **Pepper** | A secret value mixed in, stored **outside** the database | in a secret manager |
| **Work factor / cost** | How slow the hash is made on purpose | bcrypt cost 12 |
| **Memory-hard** | Needs lots of RAM, so GPUs and custom chips can't speed it up much | Argon2, scrypt |
| **Credential stuffing** | Trying leaked email/password pairs on other sites | bots testing millions of logins |
| **Dictionary attack** | Guessing passwords from a list of likely ones | rockyou.txt |
| **Lookup / rainbow table** | Precomputed hash → password tables | for unsalted hashes |
| **Rehash on login** | Upgrading an old hash when the user logs in with the right password | |

## What is it?

```text
SIGNUP                                         LOGIN
password ──┐                                    typed password ──┐
random salt┼──► Argon2id (slow, ~0.2 s) ──►    stored salt+params┼──► Argon2id ──► same hash? ──► allow / deny
params ────┘        │                                              │
                    ▼                                              │
     database: "$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>" ─────┘
     (no password, no way to reverse it)
```

The stored string contains the algorithm, the cost settings, the salt and the hash, so the server can always recompute it at login.

## Why does it matter?

- **Databases leak.** SQL injection, stolen backups, misconfigured cloud storage, insider access: assume one day your user table will be stolen.
- **People reuse passwords.** A cracked password from your shop also opens the same user's email and bank account (credential stuffing). Your storage choice protects your users **everywhere**.
- **History:** LinkedIn (2012, unsalted SHA-1), Adobe (2013, encrypted with the same key, and password hints stored in plaintext), RockYou (2009, plaintext) and many others exposed millions of passwords because of bad storage.
- **Regulation and audits:** GDPR, PCI DSS and security reviews check password storage; plaintext or MD5 is an immediate high-severity finding.

## When and where do you use it?

- **Every system with user passwords:** web apps, admin panels, APIs with password login, internal tools.
- **Frameworks often do it right by default:** Django (PBKDF2 or Argon2), Laravel and Rails (bcrypt), ASP.NET Identity (PBKDF2), Spring Security (bcrypt/Argon2 encoders). Don't replace them with your own code.
- **Not for:** API keys and tokens with high randomness (a fast hash like SHA-256 is enough there, since they can't be guessed; see **Randomness and Secure Tokens**), or data you need to read back (that's encryption).

## Concepts one by one

The examples use Python's `bcrypt` and `argon2-cffi` libraries (`pip install bcrypt argon2-cffi`).

### 1. The wrong ways: plaintext and encryption

<Explain>
<What>
Storing passwords as **plaintext** (readable) or **encrypted** (readable with a key the server holds).
</What>
<Why>
Anyone who gets the database (plus the key, which is usually on the same server) gets every password, instantly.
</Why>
<When>
Never. If a website can email you your **current** password ("Forgot password? Here it is!"), it's storing it wrongly.
</When>
<Where>
Still found in old PHP apps, internal tools, IoT devices and spreadsheets of "admin credentials".
</Where>
<How>
Passwords must be stored so that **nobody**, not even the developers or admins, can read them. That means **one-way hashing**.
</How>
</Explain>

### 2. Plain hashes: better, but crackable

<Explain>
<What>
Storing `SHA-256(password)` (or MD5/SHA-1) without a salt.
</What>
<Why>
Two problems. **Identical passwords give identical hashes**, so one cracked hash reveals everyone who used that password, and attackers can see which passwords are popular. And attackers can build **lookup tables** once (hash → password for billions of common passwords) and reuse them against every leaked database.
</Why>
<When>
Common in older systems: LinkedIn's 2012 leak was unsalted SHA-1, and most of it was cracked within days.
</When>
<Where>
Sites like crackstation.net offer huge free lookup tables for unsalted MD5/SHA-1/SHA-256 hashes.
</Where>
<How>
Below, two users with the same password have the same hash, and a tiny lookup table cracks them instantly.
</How>
</Explain>

```bash
python3 - <<'PY'
import hashlib
users = {"ali": "pakistan123", "sara": "Sara@2026!", "bilal": "pakistan123", "hina": "123456"}
print("--- what the leaked table looks like:")
for user, password in users.items():
    print(f"  {user:6} {hashlib.sha256(password.encode()).hexdigest()[:20]}...")

common = ["123456", "password", "pakistan123", "qwerty", "iloveyou"]
lookup = {hashlib.sha256(w.encode()).hexdigest(): w for w in common}     # built once, reused forever
print("--- attacker's lookup table result:")
for user, password in users.items():
    print(f"  {user:6} -> {lookup.get(hashlib.sha256(password.encode()).hexdigest(), 'not found')}")
PY
```

```text output
--- what the leaked table looks like:
  ali    38a4b906f5cb7a8b0bbf...
  sara   6227609f9da22f8fba28...
  bilal  38a4b906f5cb7a8b0bbf...
  hina   8d969eef6ecad3c29a3a...
--- attacker's lookup table result:
  ali    -> pakistan123
  sara   -> not found
  bilal  -> pakistan123
  hina   -> 123456
```

Line by line:

- Each password is hashed with SHA-256, no salt.
- **Ali and Bilal have the same hash**: without cracking anything, an attacker already knows they share a password.
- The attacker's lookup table maps hashes of common passwords back to the passwords. Built once, it works against every unsalted SHA-256 database ever leaked.
- Three of four accounts fall immediately. Only Sara's less common password isn't in this tiny table (a real table with billions of entries, or a GPU cracking run, would likely find it too).

### 3. Salts: unique per user

<Explain>
<What>
A **salt** is a random value (16 bytes is standard) generated **for each user**, combined with the password before hashing, and stored next to the hash. It is **not secret**.
</What>
<Why>
With salts, identical passwords produce **different** hashes, and precomputed lookup/rainbow tables become useless: the attacker would need a separate table for every salt, so they must attack each hash individually.
</Why>
<When>
Every password hash. Modern algorithms (bcrypt, scrypt, Argon2) generate and store the salt **automatically**.
</When>
<Where>
Inside the hash string (concepts 5 and 6), or in a separate column in old custom schemes.
</Where>
<How>
Salts don't make a single weak password strong: an attacker can still guess `pakistan123` against one salted hash. That's why we also need **slow** hashing.
</How>
</Explain>

```bash
python3 - <<'PY'
import hashlib, os
hashes = {}
for user in ["ali", "bilal"]:
    salt = os.urandom(16)                                   # new random salt for every user
    hashes[user] = hashlib.sha256(salt + b"pakistan123").hexdigest()
    print(f"{user:6} gets a {len(salt)}-byte random salt and a {len(hashes[user])}-character hash")
print("same password, same hash?", hashes["ali"] == hashes["bilal"])
PY
```

```text output
ali    gets a 16-byte random salt and a 64-character hash
bilal  gets a 16-byte random salt and a 64-character hash
same password, same hash? False
```

Line by line:

- `os.urandom(16)` creates a fresh 16-byte random salt per user. The actual values differ every run, so we only print their sizes.
- The hash input is `salt + password`. Same password, different salts, so completely different hashes.
- Ali and Bilal no longer look alike in the database, and a precomputed table for unsalted SHA-256 is useless.
- (This is still SHA-256, which is too **fast**. The next concepts fix that. Never use salted SHA-256 for real password storage.)

### 4. Speed is the enemy: slow hashes

<Explain>
<What>
Password hashing algorithms are designed to be **slow** (and ideally **memory-hard**) on purpose, with an adjustable **cost**.
</What>
<Why>
Your server hashes a password once per login: 100–500 ms is fine. An attacker must hash **every guess**: making each one 400,000 times slower turns "cracked in an hour" into "not cracked in centuries". Memory-hardness (Argon2, scrypt) blocks the cheap parallelism of GPUs and custom chips.
</Why>
<When>
Always for passwords (and for keys derived from passwords).
</When>
<Where>
**Argon2id** (winner of the Password Hashing Competition, OWASP's first choice), **scrypt**, **bcrypt** (older but still fine), **PBKDF2** (when FIPS compliance is required, with 600,000+ iterations for SHA-256).
</Where>
<How>
Tune the cost so one hash takes roughly 100–500 ms on your production servers, and raise it as hardware gets faster.
</How>
</Explain>

```bash
python3 - <<'PY'
import time, hashlib, bcrypt
from argon2 import PasswordHasher

def avg_seconds(fn, runs):
    start = time.perf_counter()
    for _ in range(runs):
        fn()
    return (time.perf_counter() - start) / runs

sha = avg_seconds(lambda: hashlib.sha256(b"pakistan123").digest(), 20000)
bc = avg_seconds(lambda: bcrypt.hashpw(b"pakistan123", bcrypt.gensalt(12)), 3)
ar = avg_seconds(lambda: PasswordHasher().hash("pakistan123"), 3)
print("SHA-256 takes under 0.01 ms per guess:", sha < 0.00001)
print("bcrypt (cost 12) takes over 50 ms:     ", bc > 0.05)
print("Argon2id (defaults) takes over 20 ms:  ", ar > 0.02)
print("bcrypt is over 10,000x slower than SHA-256:", bc / sha > 10_000)
PY
```

```text output
SHA-256 takes under 0.01 ms per guess: True
bcrypt (cost 12) takes over 50 ms:      True
Argon2id (defaults) takes over 20 ms:   True
bcrypt is over 10,000x slower than SHA-256: True
```

Line by line:

- `avg_seconds` runs a function many times and returns the average time per call.
- SHA-256 takes well under a microsecond on a normal CPU (on a GPU, attackers get billions per second).
- bcrypt with cost 12 takes hundreds of milliseconds; Argon2id with its defaults (64 MB of memory, 3 passes) takes a sizeable fraction of a second too. Exact times depend on the machine, so we print comparisons instead of numbers.
- On this machine, bcrypt was hundreds of thousands of times slower than SHA-256. For a user logging in, that's a short pause. For an attacker trying a billion passwords, it's the difference between minutes and many years.

### 5. bcrypt and its hash string

<Explain>
<What>
bcrypt (1999) is a slow hash based on the Blowfish cipher, with a **cost** parameter: each +1 doubles the time.
</What>
<Why>
It's battle-tested and available everywhere, and it's the default in many frameworks (Laravel, Rails, Spring).
</Why>
<When>
A solid choice if Argon2 isn't available. Use cost 12 or higher (tune to about 250 ms).
</When>
<Where>
The output looks like `$2b$12$<22-char salt><31-char hash>` (60 characters total), so you store just one string.
</Where>
<How>
Important limit: bcrypt only uses the first **72 bytes** of the password. Newer libraries refuse longer input; older ones silently ignore the rest. Many apps pre-hash long passwords, or simply use Argon2.
</How>
</Explain>

```bash
python3 - <<'PY'
import bcrypt
demo_salt = b"$2b$12$" + b"abcdefghijklmnopqrstuu"          # fixed only so the output is reproducible
stored = bcrypt.hashpw(b"pakistan123", demo_salt).decode()
print(stored)
algo, cost, rest = stored.split("$")[1:]
print(f"algorithm={algo} cost={cost} (2^{cost} rounds) salt={rest[:22]} hash={rest[22:31]}...")
print("correct password:", bcrypt.checkpw(b"pakistan123", stored.encode()))
print("capital P       :", bcrypt.checkpw(b"Pakistan123", stored.encode()))
try:
    bcrypt.hashpw(b"a" * 80, bcrypt.gensalt())
except ValueError as err:
    print("80-byte password:", err)
PY
```

```text output
$2b$12$abcdefghijklmnopqrstuuyn70WAwWKUDnZsTrJJMRpQI9Xy6tKh6
algorithm=2b cost=12 (2^12 rounds) salt=abcdefghijklmnopqrstuu hash=yn70WAwWK...
correct password: True
capital P       : False
80-byte password: password cannot be longer than 72 bytes, truncate manually if necessary (e.g. my_password[:72])
```

Line by line:

- Normally you'd call `bcrypt.gensalt(12)` for a random salt; here a fixed salt makes the output reproducible.
- The stored string is self-describing: `2b` = bcrypt version, `12` = cost (2^12 = 4,096 key-setup rounds), then 22 characters of salt and 31 characters of hash.
- `bcrypt.checkpw` reads the cost and salt from the stored string, re-hashes the typed password, and compares in constant time: the correct password matches, a different capitalisation doesn't.
- An 80-byte password is rejected by this bcrypt version. With older versions, two long passwords that differ only after byte 72 would both be accepted.

### 6. Argon2id: the modern default

<Explain>
<What>
**Argon2id** has three cost parameters: **memory** (`m`, in KiB), **iterations** (`t`), and **parallelism** (`p`).
</What>
<Why>
Requiring lots of memory per guess makes GPU and ASIC cracking far less efficient than with bcrypt or PBKDF2.
</Why>
<When>
First choice for new systems (OWASP's recommendation).
</When>
<Where>
`argon2-cffi` (Python), `argon2` (Node), `password_hash($pw, PASSWORD_ARGON2ID)` (PHP), Spring's `Argon2PasswordEncoder`, Django's `Argon2PasswordHasher`.
</Where>
<How>
OWASP's minimum is m=19 MiB, t=2, p=1; library defaults are often stronger (argon2-cffi: 64 MiB, t=3, p=4). Tune to your server's capacity.
</How>
</Explain>

```bash
python3 - <<'PY'
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError
ph = PasswordHasher()
stored = ph.hash("long-mango-season-lahore-42")
parts = stored.split("$")
print("algorithm :", parts[1])
print("version   :", parts[2])
print("parameters:", parts[3])
print("salt+hash : <random each time>, total length", len(stored))
print("verify    :", ph.verify(stored, "long-mango-season-lahore-42"))
try:
    ph.verify(stored, "long-mango-season-lahore-43")
except VerifyMismatchError:
    print("wrong pw  : VerifyMismatchError")
PY
```

```text output
algorithm : argon2id
version   : v=19
parameters: m=65536,t=3,p=4
salt+hash : <random each time>, total length 97
verify    : True
wrong pw  : VerifyMismatchError
```

Line by line:

- `PasswordHasher()` uses Argon2id with safe defaults and generates a random salt automatically.
- The stored string records the algorithm (`argon2id`), version (`v=19`, which is 0x13 = Argon2 version 1.3), and parameters: 65,536 KiB = 64 MiB of memory, 3 iterations, 4 lanes of parallelism.
- `ph.verify` returns `True` for the right password and raises `VerifyMismatchError` for a wrong one, so you can't accidentally treat a failure as success.

### 7. Upgrading hashes on login

<Explain>
<What>
When a user logs in successfully, you briefly have their real password. If their stored hash uses old or weak settings, **re-hash** it with current settings and save it.
</What>
<Why>
Hardware gets faster, so cost settings must rise over time, and old algorithms (MD5, SHA-1, low-cost bcrypt) must be phased out, without forcing everyone to reset their password.
</Why>
<When>
Every successful login.
</When>
<Where>
`argon2-cffi`: `check_needs_rehash`; PHP: `password_needs_rehash`; Django and Laravel do it automatically.
</Where>
<How>
Below, a hash made with old, weak settings is verified, detected as outdated, and would be replaced.
</How>
</Explain>

```bash
python3 - <<'PY'
from argon2 import PasswordHasher
old_settings = PasswordHasher(time_cost=1, memory_cost=19456, parallelism=1)   # what we used in 2021
stored = old_settings.hash("Sara@2026!")
print("stored with:", stored.split("$")[3])

current = PasswordHasher()                                                      # today's settings
if current.verify(stored, "Sara@2026!"):
    print("login ok; needs rehash?", current.check_needs_rehash(stored))
    stored = current.hash("Sara@2026!")
    print("upgraded to:", stored.split("$")[3])
PY
```

```text output
stored with: m=19456,t=1,p=1
login ok; needs rehash? True
upgraded to: m=65536,t=3,p=4
```

Line by line:

- The old hash used 19 MiB and 1 iteration.
- The current hasher can still **verify** it (the parameters are inside the string), so the login works.
- `check_needs_rehash` compares the stored parameters with the current ones: they differ, so we hash the password again with the new settings and save the new string.

### 8. Peppers: a secret outside the database

<Explain>
<What>
A **pepper** is a secret value (like a key) stored **outside** the database: in a secret manager, environment variable or HSM. It's mixed into every password before hashing, typically as `HMAC(pepper, password)`.
</What>
<Why>
If attackers steal **only** the database (SQL injection, a leaked backup), they can't even start guessing without the pepper.
</Why>
<When>
Higher-security systems, as an **extra** layer on top of a proper password hash, never instead of it.
</When>
<Where>
OWASP's Password Storage Cheat Sheet describes peppering; plan for rotating it (store a pepper version with each hash).
</Where>
<How>
If the pepper is lost, every password becomes unverifiable, so back it up securely.
</How>
</Explain>

The hands-on below uses a pepper: `HMAC-SHA256(pepper, password)` is what goes into Argon2id.

### 9. Migrating a legacy MD5/SHA-1 database

<Explain>
<What>
You inherit a system storing `md5(password)`. You can't recompute proper hashes, because you don't have the passwords.
</What>
<Why>
Waiting for every user to log in leaves weak hashes in the database for years.
</Why>
<When>
Any legacy migration.
</When>
<Where>
**Wrap** immediately: store `argon2id(md5_hash)` for every user now (marked as "wrapped"). At login, compute `md5(typed)` and verify it against the wrapped hash; on success, replace it with a normal `argon2id(password)`.
</Where>
<How>
After a deadline, force a password reset for accounts that never logged in, and delete any remaining old data.
</How>
</Explain>

```bash
python3 - <<'PY'
import hashlib
from argon2 import PasswordHasher
ph = PasswordHasher()
legacy_md5 = hashlib.md5(b"Karachi#2019").hexdigest()          # what the old system stored
record = {"scheme": "argon2(md5)", "hash": ph.hash(legacy_md5)}   # wrapped today, md5 deleted
print("migrated record scheme:", record["scheme"])

typed = "Karachi#2019"                                            # user logs in later
if record["scheme"] == "argon2(md5)" and ph.verify(record["hash"], hashlib.md5(typed.encode()).hexdigest()):
    record = {"scheme": "argon2", "hash": ph.hash(typed)}
print("after login:", record["scheme"], "| contains md5?", legacy_md5 in record["hash"])
PY
```

```text output
migrated record scheme: argon2(md5)
after login: argon2 | contains md5? False
```

Line by line:

- `legacy_md5` stands for the weak hash in the old database.
- Migration day: each MD5 hash is itself hashed with Argon2id, and the bare MD5 value is deleted. Even before anyone logs in, a stolen database now holds only slow hashes.
- At the user's next login, we MD5 the typed password, verify it against the wrapped hash, and then store a clean `argon2(password)` hash.

### 10. Password rules that actually help

<Explain>
<What>
Modern guidance (NIST SP 800-63B) focuses on **length** and **known-bad passwords**, not complex composition rules.
</What>
<Why>
"At least one uppercase, one digit, one symbol" produces `Password1!`, and forced 90-day changes produce `Summer2026!` → `Autumn2026!`. Attackers' tools know these patterns.
</Why>
<When>
Designing signup, password-change and reset flows.
</When>
<Where>
- Minimum **8** characters, preferably 12–15+; allow at least 64; allow spaces and all characters (passphrases).
- **Block** passwords found in breach lists, dictionary words, and context-specific ones (the site name, the username).
- **No** forced periodic changes unless there's evidence of compromise. **No** password hints or security questions.
- Allow paste and password managers.
</Where>
<How>
Check breached passwords with Have I Been Pwned's **k-anonymity** API: send only the first 5 hex characters of the password's SHA-1 hash, receive all matching suffixes, and compare locally. The full password or hash never leaves your server.
</How>
</Explain>

```bash
python3 - <<'PY'
import hashlib
digest = hashlib.sha1("pakistan123".encode()).hexdigest().upper()
prefix, suffix = digest[:5], digest[5:]
print("sent to https://api.pwnedpasswords.com/range/" + prefix)
print("compared locally:", suffix)
PY
```

```text output
sent to https://api.pwnedpasswords.com/range/FA6E8
compared locally: 53CACCA6DB7FBD380384118D41A25548C53
```

Line by line:

- The password's SHA-1 hash is split into a 5-character prefix and the rest.
- Only the prefix `FA6E8` is sent. The API returns every breached-password hash suffix starting with that prefix (hundreds of them) together with how often each was seen.
- Your server checks whether its suffix is in that list. The API never learns which password you checked. (SHA-1 is fine here because this is a lookup, not password storage.)

### 11. Around the hash: the rest of login security

<Explain>
<What>
Strong hashing protects passwords **after** a breach. Other controls protect **live** accounts.
</What>
<Why>
Attackers mostly don't crack hashes: they use **credential stuffing** with passwords leaked elsewhere, phishing and brute force against the login form.
</Why>
<When>
Every login endpoint.
</When>
<Where>
Rate limiting and temporary lockouts, CAPTCHA after suspicious activity, **MFA** (TOTP apps, and best of all **passkeys/WebAuthn**, which are phishing-resistant), generic error messages ("invalid username or password"), login alerts, and secure password-reset flows (see **Password Reset and MFA Flows** in the Authentication topic).
</Where>
<How>
Also keep login time similar for unknown and known usernames, so attackers can't discover which accounts exist (the hands-on does this).
</How>
</Explain>

## Hands-on

Build a small but complete password module: Argon2id with a pepper, minimum length, breached-password blocking, generic errors, lockout after failed attempts, and automatic rehashing.

```bash
cat > auth.py <<'PY'
import hashlib, hmac, json, os
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

PEPPER = os.environ["PASSWORD_PEPPER"].encode()        # from a secret manager, never in the database
ph = PasswordHasher()                                  # Argon2id, library defaults
BREACHED = {"123456", "password", "pakistan123", "password1234", "iloveyou"}   # stand-in for HIBP
DB = "users.json"

def _peppered(password):
    return hmac.new(PEPPER, password.encode(), hashlib.sha256).hexdigest()

def _load():
    return json.load(open(DB)) if os.path.exists(DB) else {}

def _save(users):
    json.dump(users, open(DB, "w"), indent=2)

def signup(username, password):
    if len(password) < 12:
        return "rejected: use at least 12 characters"
    if password.lower() in BREACHED:
        return "rejected: this password appears in known data breaches"
    users = _load()
    users[username] = {"hash": ph.hash(_peppered(password)), "failed": 0}
    _save(users)
    return "account created"

def login(username, password):
    users = _load()
    user = users.get(username)
    if user is None:
        ph.hash("dummy-password-to-keep-timing-similar")      # same work as a real check
        return "invalid username or password"
    if user["failed"] >= 5:
        return "account temporarily locked"
    try:
        ph.verify(user["hash"], _peppered(password))
    except VerifyMismatchError:
        user["failed"] += 1
        _save(users)
        return "invalid username or password"
    user["failed"] = 0
    if ph.check_needs_rehash(user["hash"]):
        user["hash"] = ph.hash(_peppered(password))
    _save(users)
    return "welcome " + username
PY
export PASSWORD_PEPPER="pep-$(openssl rand -hex 16)"
python3 - <<'PY'
```

Line by line:

- **Pepper:** read from an environment variable (in production: a secret manager). `_peppered` computes `HMAC-SHA256(pepper, password)`, which is what Argon2id hashes. A stolen `users.json` alone isn't enough to start guessing.
- **Signup rules:** at least 12 characters, and not in the breached list (checked case-insensitively, so `Password1234` is caught). Real code would query the HIBP range API from concept 10.
- **Storage:** `ph.hash` creates a salted Argon2id hash; `failed` counts failed logins.
- **Login:**
  - Unknown usernames do a dummy hash, so they take about as long as real ones, and return the **same** generic message as a wrong password (case 6). Attackers can't tell which accounts exist.
  - After 5 failures the account is locked (case 7), even for the right password. Real systems unlock after a delay or through email verification, and also rate-limit by IP address.
  - On success, failures reset, and the hash is upgraded if the settings changed.
- **Result:** the file contains only an Argon2id string with its parameters, never the password.

## Real-world example

In 2016 it emerged that over 100 million LinkedIn passwords from a 2012 breach had been stored as **unsalted SHA-1**; most were cracked quickly and used in credential-stuffing attacks against other sites for years. In contrast, when a password manager company disclosed a breach of encrypted vaults, the outcome depended on users' master passwords and on the key-derivation iteration counts: old accounts with low PBKDF2 iterations were at much higher risk than new ones, which is why the company raised the defaults and upgraded old accounts. A typical fix in a Pakistani e-commerce codebase looks like this: replace `md5($password)` with PHP's `password_hash($password, PASSWORD_ARGON2ID)`; wrap all existing MD5 hashes on migration day; upgrade on login with `password_needs_rehash`; add a breached-password check at signup and password change; rate-limit `/login`; and offer TOTP-based two-factor authentication for sellers and admins.

## Common mistakes

- **Plaintext or reversible encryption** for passwords.
- **Fast hashes** (MD5, SHA-1, SHA-256, even salted) for password storage.
- **One global salt** for all users, or a salt derived from the username.
- **Inventing a scheme** (`sha256(sha256(md5(pw)))`) instead of using bcrypt/scrypt/Argon2.
- **Cost settings never increased** since the system was built.
- **bcrypt with long passwords** silently truncated at 72 bytes.
- **Composition rules and forced resets** instead of length and breached-password checks.
- **Different error messages** for "user not found" and "wrong password" (account enumeration).
- **Logging passwords** in request logs or error reports (check your logging middleware and APM tools).
- **No rate limiting or MFA,** relying on hashing alone.

## Security lens

<Callout type="security">
Assume your user table will leak one day. Good password storage decides whether that leak exposes your users' accounts everywhere, or nothing useful at all.
</Callout>

- **Use the framework's password API** (Django, Laravel `Hash::make`, ASP.NET Identity, Spring Security, PHP `password_hash`) and configure Argon2id or bcrypt with adequate cost.
- **Protect against online attacks:** rate limiting, lockouts or progressive delays, bot detection, MFA and passkeys.
- **Breach response:** if hashes leak, force resets for affected accounts, revoke sessions, and notify users. Strong hashing buys time, and MFA limits damage.
- **Keep secrets out of logs:** mask password fields in logs, traces and error trackers.
- **Admin and service accounts** deserve the strongest protection: long random passwords from a password manager plus phishing-resistant MFA.
- **Move toward passwordless:** passkeys (WebAuthn) remove shared secrets from the server entirely, since the server stores only a public key.

## Interview questions

<QA q="How should passwords be stored?">
As salted hashes produced by a slow, purpose-built password hashing function such as Argon2id, scrypt or bcrypt, with a cost tuned to roughly a few hundred milliseconds and increased over time. Never in plaintext, encrypted, or with fast general-purpose hashes. The library generates a unique random salt per password and stores algorithm, parameters, salt and hash together.
</QA>

<QA q="What is a salt and why is it needed?">
A salt is a random value unique to each password that is combined with it before hashing and stored alongside the hash. It ensures identical passwords produce different hashes, prevents attackers from using precomputed lookup or rainbow tables, and forces them to attack each hash separately. It does not need to be secret.
</QA>

<QA q="Why are fast hashes like SHA-256 bad for passwords?">
Attackers who steal hashes can compute billions of SHA-256 guesses per second on GPUs, so common and moderately complex passwords are cracked quickly. Password hashing functions are deliberately slow and, in the case of Argon2 and scrypt, memory-hard, which makes each guess expensive and GPU acceleration much less effective.
</QA>

<QA q="What is a pepper?">
A pepper is a secret value kept outside the database, for example in a secret manager or HSM, that is mixed into passwords before hashing, typically via HMAC. If only the database is stolen, attackers cannot verify guesses without the pepper. It is an additional layer, not a replacement for salted slow hashing, and needs a plan for backup and rotation.
</QA>

<QA q="How would you migrate a database of MD5 password hashes?">
Immediately wrap each MD5 hash with a strong algorithm, storing Argon2id of the MD5 value and deleting the bare MD5 hashes. At each user's next successful login, verify by computing MD5 of the typed password and checking it against the wrapped hash, then replace it with a normal Argon2id hash of the password. After a deadline, force resets for accounts that never logged in.
</QA>

## Key terms

<Terms>
  <Term name="Password hashing">One-way, slow, salted transformation used to store passwords.</Term>
  <Term name="Salt">Random per-password value that defeats precomputed tables.</Term>
  <Term name="Pepper">Secret stored outside the database and mixed into passwords.</Term>
  <Term name="Work factor">Tunable cost making each hash deliberately slow.</Term>
  <Term name="Memory-hard">Requiring large memory per guess to resist GPU and ASIC attacks.</Term>
  <Term name="Argon2id">Modern memory-hard password hash; first choice today.</Term>
  <Term name="bcrypt">Widely used adaptive password hash with a 72-byte input limit.</Term>
  <Term name="scrypt / PBKDF2">Other password-based key derivation functions.</Term>
  <Term name="Rainbow / lookup table">Precomputed hash-to-password tables for unsalted hashes.</Term>
  <Term name="Credential stuffing">Reusing leaked credentials against other services.</Term>
  <Term name="k-anonymity check">Breached-password lookup sending only a hash prefix.</Term>
</Terms>
