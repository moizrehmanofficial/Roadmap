<BigIdea>
<Tr>
<En>
Symmetric encryption needs **both sides to already share a secret key**, which is impossible between strangers on the internet. **Asymmetric (public-key) cryptography** solves that with a **key pair**: a **public key** you give to anyone and a **private key** you never share. What the public key **encrypts**, only the matching private key can **decrypt**. It's slow and handles only small data, so real systems use **hybrid encryption** (public-key crypto protects a random AES key, which encrypts the data) or **key exchange** (X25519), where both sides compute the **same secret** without ever sending it. You use key pairs daily: SSH, HTTPS, Git signing, `age`.
</En>
<Ur>
Symmetric encryption ke liye **dono taraf pehle se ek raaz wali key** honi chahiye, jo internet par ajnabiyon ke beech namumkin hai. **Asymmetric (public-key) cryptography** ye masla **key pair** se hal karti hai: **public key** jo aap kisi ko bhi dein aur **private key** jo kabhi share na karein. Jo public key **encrypt** kare, use sirf usi ki joridar private key **decrypt** kar sakti hai. Ye sust hai aur sirf chhota data sambhalti hai, isliye asli systems **hybrid encryption** (public-key crypto ek random AES key bachati hai, jo data encrypt karti hai) ya **key exchange** (X25519) istemal karte hain, jahan dono taraf **ek hi raaz** bhije baghair nikal lete hain. Aap rozana key pairs istemal karte hain: SSH, HTTPS, Git signing, `age`.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

```text
Symmetric:   one key ─────────────► encrypt ──► decrypt ◄── same key
             problem: how did the other side get the key?

Asymmetric:  Alice's PUBLIC key ──► encrypt ──► ciphertext ──► decrypt ◄── Alice's PRIVATE key
             anyone can encrypt for Alice; only Alice can decrypt
```

The two keys are linked by maths that's easy one way and practically impossible to reverse. For RSA, multiplying two huge primes is easy, but splitting the product back into them is infeasible at 2048+ bits; elliptic curves use a different one-way operation. You can compute the public key from the private key, never the reverse.

</En>
<Ur>

```text
Symmetric:   one key ─────────────► encrypt ──► decrypt ◄── same key
             problem: how did the other side get the key?

Asymmetric:  Alice's PUBLIC key ──► encrypt ──► ciphertext ──► decrypt ◄── Alice's PRIVATE key
             anyone can encrypt for Alice; only Alice can decrypt
```

Dono keys aise hisaab se juri hain jo ek taraf aasaan aur ulta amalan namumkin hai. RSA me do bohot bare primes ka zarb aasaan hai, lekin 2048+ bits par hasil zarb ko wapas un me torna namumkin hai; elliptic curves ek alag ek-taraf amal istemal karte hain. Private key se public key nikal sakti hai, ulta kabhi nahi.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Every HTTPS connection** uses public-key crypto to agree keys with a server you've never met, then switches to symmetric encryption.
- **SSH** key logins, **Git** signing, **code signing**, **VPNs** (WireGuard uses X25519), **messaging** (Signal, WhatsApp), crypto wallets and **passkeys** are all built on key pairs.
- **Cloud and DevOps:** EC2 key pairs, GitHub deploy keys, KMS asymmetric keys, SOPS with age keys.
- **Incidents** often involve leaked private keys (committed to Git, left on servers), so handling them correctly is a core skill.

</En>
<Ur>

- **Har HTTPS connection** anjaan server ke saath keys tay karne ke liye public-key crypto istemal karta hai, phir symmetric encryption par chala jata hai.
- **SSH** key logins, **Git** signing, **code signing**, **VPNs** (WireGuard X25519 istemal karta hai), **messaging** (Signal, WhatsApp), crypto wallets aur **passkeys** sab key pairs par bane hain.
- **Cloud aur DevOps:** EC2 key pairs, GitHub deploy keys, KMS asymmetric keys, age keys ke saath SOPS.
- **Incidents** me aksar leak hui private keys hoti hain (Git me commit, servers par chhoot gayin), isliye unhe sahi sambhalna bunyadi hunar hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **Sending data without a pre-shared secret:** encrypt for their public key (in practice hybrid, via `age`, PGP or a KMS asymmetric key).
- **Setting up a secure channel:** key exchange inside TLS, SSH, WireGuard, Signal.
- **Proving identity or authorship:** digital signatures, the next lesson, which use the same key pairs the other way round.
- You rarely call RSA or X25519 directly; you use protocols and tools that do it correctly.

</En>
<Ur>

- **Pehle se saanjhe raaz ke baghair data bhejna:** un ki public key ke liye encrypt (amalan hybrid, `age`, PGP ya KMS asymmetric key se).
- **Mehfooz raasta banana:** TLS, SSH, WireGuard, Signal ke andar key exchange.
- **Shanakht ya likhne wala sabit karna:** digital signatures, agla sabaq, jo wahi key pairs ulti taraf istemal karte hain.
- RSA ya X25519 aap shazo nadir seedha bulate hain; aap aise protocols aur tools istemal karte hain jo ise sahi karte hain.

</Ur>
</Tr>

## Picture it

<Tr>
<En>

Imagine a **padlock shop that gives away open padlocks for free**. You keep the only **key** (your private key), but you hand out as many **open padlocks** (your public key) as you like. Anyone who wants to send you something private puts it in a box and **snaps your padlock shut**. Now even they can't open it again; only you can. Nobody had to secretly hand over a key beforehand: that's public-key encryption.

</En>
<Ur>

Socho ek **taalon ki dukaan jo khule taale muft baant-ti hai**. Akeli **chaabi** aap ke paas hai (private key), lekin aap jitne chahen **khule taale** (public key) baant dete hain. Jo bhi aap ko kuch raaz bhejna chahe, wo dabbe me rakh kar **aap ka taala band** kar deta hai. Ab wo khud bhi nahi khol sakta; sirf aap khol sakte hain. Kisi ko pehle se chupke se chaabi nahi deni padi: yahi public-key encryption hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Generate a key pair">

<Tr>
<En>

A key pair is generated together: first a random private key, then the public key computed from it. You need one before anyone can encrypt for you, verify your signatures or let you log in with keys. Tools: `openssl genpkey`, `ssh-keygen` (SSH and Git signing), `gpg --full-generate-key`, `age-keygen`, or a cloud KMS (keys never leave the service). Private keys are usually stored in **PEM**: Base64 text between `-----BEGIN ...-----` and `-----END ...-----` lines.

</En>
<Ur>

Key pair ikattha banta hai: pehle random private key, phir us se nikali public key. Kisi ke aap ke liye encrypt karne, aap ke signatures verify karne ya keys se login dene se pehle aap ko ek chahiye. Tools: `openssl genpkey`, `ssh-keygen` (SSH aur Git signing), `gpg --full-generate-key`, `age-keygen`, ya cloud KMS (keys service se bahar nahi jatin). Private keys aam tor par **PEM** me hoti hain: `-----BEGIN ...-----` aur `-----END ...-----` lines ke beech Base64 text.

</Ur>
</Tr>

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out alice_private.pem 2>/dev/null
openssl pkey -in alice_private.pem -pubout -out alice_public.pem
head -1 alice_private.pem
head -1 alice_public.pem
openssl pkey -in alice_public.pem -pubin -noout -text | head -1
```

```text output
-----BEGIN PRIVATE KEY-----
-----BEGIN PUBLIC KEY-----
Public-Key: (2048 bit)
```

<Happened>
<Tr>
<En>`genpkey` made a 2048-bit RSA **private** key (`2>/dev/null` hides progress dots), and `pkey -pubout` **derived** the public key from it; the reverse is impossible. The PEM headers say what each file holds: a file starting with `BEGIN PRIVATE KEY` (or `BEGIN RSA PRIVATE KEY` / `BEGIN OPENSSH PRIVATE KEY`) must **never** be shared, committed or pasted anywhere. `-text` showed it's a 2048-bit key.</En>
<Ur>`genpkey` ne 2048-bit RSA **private** key banayi (`2>/dev/null` progress ke dots chhupata hai), aur `pkey -pubout` ne us se public key **nikali**; ulta namumkin hai. PEM headers batate hain har file me kya hai: `BEGIN PRIVATE KEY` (ya `BEGIN RSA PRIVATE KEY` / `BEGIN OPENSSH PRIVATE KEY`) se shuru hone wali file **kabhi** share, commit ya kahin paste na karein. `-text` ne dikhaya ye 2048-bit key hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Encrypt with the public key, decrypt with the private key">

<Tr>
<En>

Anyone with Alice's **public** key can encrypt a message only her **private** key can decrypt, so no secret is shared in advance: Alice can publish her public key on her website. Directly, this suits only small secrets (a symmetric key, a short token). RSA must use a padding scheme: **OAEP** for encryption. The old PKCS#1 v1.5 encryption padding has led to real attacks (Bleichenbacher, ROBOT) and should be avoided.

</En>
<Ur>

Alice ki **public** key wala koi bhi aisa paigham encrypt kar sakta hai jo sirf us ki **private** key khole, isliye pehle se koi raaz share nahi karna: Alice apni public key website par laga sakti hai. Seedha ye sirf chhote raazon (symmetric key, chhota token) ke liye moozun hai. RSA ko padding scheme chahiye: encryption ke liye **OAEP**. Purani PKCS#1 v1.5 encryption padding asli hamlon (Bleichenbacher, ROBOT) ka sabab bani, us se bachein.

</Ur>
</Tr>

```bash
printf 'Meet at 7pm, bring the contract' > note.txt
openssl pkeyutl -encrypt -pubin -inkey alice_public.pem \
  -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -in note.txt -out note.enc
echo "ciphertext size: $(wc -c < note.enc) bytes"
openssl pkeyutl -decrypt -inkey alice_private.pem \
  -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -in note.enc; echo
```

```text output
ciphertext size: 256 bytes
Meet at 7pm, bring the contract
```

<Happened>
<Tr>
<En>Bob encrypted with the **public** key (`-pubin` says the key file is public), with OAEP-SHA256 padding. The ciphertext is always exactly **256 bytes** for a 2048-bit key (2048 / 8), however short the message. Alice decrypted with her **private** key and got the note back.</En>
<Ur>Bob ne **public** key se encrypt kiya (`-pubin` batata hai key file public hai), OAEP-SHA256 padding ke saath. 2048-bit key ka ciphertext hamesha bilkul **256 bytes** hota hai (2048 / 8), paigham kitna bhi chhota ho. Alice ne apni **private** key se decrypt kiya aur note wapas paaya.</Ur>
</Tr>
</Happened>

</Step>

<Step title="RSA's size limit, and hybrid encryption">

<Tr>
<En>

RSA can only encrypt data **smaller than the key** (2048-bit + OAEP-SHA256: at most 190 bytes), and it's **hundreds to thousands of times slower** than AES. So you never encrypt a file directly with RSA. **Hybrid encryption:** generate a random AES key, encrypt the data with AES-GCM, and encrypt only the 32-byte AES key with the recipient's public key. TLS, PGP, S/MIME, age and AWS KMS asymmetric keys all work like this.

</En>
<Ur>

RSA sirf **key se chhota** data encrypt kar sakta hai (2048-bit + OAEP-SHA256: zyada se zyada 190 bytes), aur AES se **saikron se hazaron guna sust** hai. Isliye file kabhi seedha RSA se encrypt nahi karte. **Hybrid encryption:** random AES key banao, data AES-GCM se encrypt karo, aur sirf 32-byte AES key ko receiver ki public key se encrypt karo. TLS, PGP, S/MIME, age aur AWS KMS asymmetric keys sab isi tarah chalte hain.

</Ur>
</Tr>

```bash
head -c 300 /dev/zero > big.bin
openssl pkeyutl -encrypt -pubin -inkey alice_public.pem -pkeyopt rsa_padding_mode:oaep \
  -pkeyopt rsa_oaep_md:sha256 -in big.bin -out big.enc 2>&1 | grep -o 'data too large for key size'
python3 - <<'PY'
import os
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

public = serialization.load_pem_public_key(open("alice_public.pem", "rb").read())
private = serialization.load_pem_private_key(open("alice_private.pem", "rb").read(), password=None)
oaep = padding.OAEP(mgf=padding.MGF1(hashes.SHA256()), algorithm=hashes.SHA256(), label=None)

data = b"x" * 5_000_000                                   # a 5 MB "file"
aes_key, nonce = AESGCM.generate_key(bit_length=256), os.urandom(12)
encrypted_data = AESGCM(aes_key).encrypt(nonce, data, None)   # fast symmetric part
wrapped_key = public.encrypt(aes_key, oaep)                     # slow public-key part, tiny input
print("sent:", len(wrapped_key), "byte wrapped key +", len(encrypted_data), "byte ciphertext")

recovered_key = private.decrypt(wrapped_key, oaep)
print("Alice decrypts the 5 MB correctly:", AESGCM(recovered_key).decrypt(nonce, encrypted_data, None) == data)
PY
```

```text output
data too large for key size
sent: 256 byte wrapped key + 5000016 byte ciphertext
Alice decrypts the 5 MB correctly: True
```

<Happened>
<Tr>
<En>300 bytes failed with **data too large for key size**. In Python, a fresh AES-256 key encrypted 5 MB with AES-GCM (5,000,016 bytes: data + 16-byte tag), and only the 32-byte AES key was wrapped with RSA-OAEP into 256 bytes. Alice unwrapped the AES key with her private key and decrypted the data: public-key crypto for **key transport**, symmetric crypto for **data**.</En>
<Ur>300 bytes **data too large for key size** ke saath fail hue. Python me taazi AES-256 key ne 5 MB AES-GCM se encrypt kiye (5,000,016 bytes: data + 16-byte tag), aur sirf 32-byte AES key RSA-OAEP se 256 bytes me wrap hui. Alice ne private key se AES key kholi aur data decrypt kiya: **key pahunchane** ke liye public-key crypto, **data** ke liye symmetric crypto.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Key exchange: agreeing a secret in public">

<Tr>
<En>

In **Diffie-Hellman** (modern version: **X25519**), each side sends only its **public** key and combines **its own private key** with **the other's public key**; both arrive at the **same shared secret**, which never crossed the network. An eavesdropper sees both public keys but can't compute it. This happens at the start of every TLS connection, SSH session and VPN tunnel (TLS 1.3 key shares, SSH `curve25519-sha256`, WireGuard, Signal). The raw secret is then fed into a **KDF** like HKDF to make the real keys.

</En>
<Ur>

**Diffie-Hellman** (jadeed shakal: **X25519**) me har taraf sirf apni **public** key bhejti hai aur **apni private key** ko **doosre ki public key** se milati hai; dono **ek hi saanjhe raaz** tak pahunchte hain, jo kabhi network se nahi guzra. Chupke se sunne wala dono public keys dekhta hai lekin raaz nahi nikal sakta. Ye har TLS connection, SSH session aur VPN tunnel ke shuru me hota hai (TLS 1.3 key shares, SSH `curve25519-sha256`, WireGuard, Signal). Phir kaccha raaz HKDF jaise **KDF** me ja kar asli keys banata hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
alice = X25519PrivateKey.generate()
bob = X25519PrivateKey.generate()
# Only public keys cross the network:
alice_secret = alice.exchange(bob.public_key())
bob_secret = bob.exchange(alice.public_key())
print("shared secret length:", len(alice_secret), "bytes | Alice and Bob agree:", alice_secret == bob_secret)
eve = X25519PrivateKey.generate()   # an eavesdropper with her own key and both public keys
print("Eve can compute it:", eve.exchange(alice.public_key()) == alice_secret)
PY
```

```text output
shared secret length: 32 bytes | Alice and Bob agree: True
Eve can compute it: False
```

```text
Alice: private a, public A ──── A ───►
                          ◄──── B ──── Bob: private b, public B
Alice computes  a × B  ═══  b × A  Bob computes      (same secret, never sent)
Eve sees A and B only  →  can't compute it
```

<Happened>
<Tr>
<En>Alice and Bob each made a fresh X25519 key pair. `alice.exchange(bob.public_key())` and Bob's mirror image both produced the **same 32 bytes**. Eve has both public keys and her own private key, but combining them gave a **different** value: without Alice's or Bob's private key, the secret is out of reach.</En>
<Ur>Alice aur Bob ne taaza X25519 key pair banaya. `alice.exchange(bob.public_key())` aur Bob ki ulti shakal dono ne **wahi 32 bytes** diye. Eve ke paas dono public keys aur apni private key hai, lekin milane se **alag** value aayi: Alice ya Bob ki private key ke baghair raaz pahunch se bahar hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Forward secrecy">

<Tr>
<En>

**Forward secrecy** means a stolen long-term private key **can't decrypt past sessions**, achieved by using **fresh, temporary ("ephemeral") key-exchange keys** for every session and deleting them afterwards. Attackers record encrypted traffic today hoping to steal a key later. With old TLS "RSA key transport" (the client encrypts the session key with the server's RSA key), one stolen server key decrypts **every recorded session**; with ephemeral Diffie-Hellman, it decrypts **nothing** from the past. TLS 1.3 **always** uses ephemeral exchange; the server's long-term key only **signs** the handshake (see **TLS and Certificates**). In TLS 1.2, prefer ECDHE suites and disable static RSA.

</En>
<Ur>

**Forward secrecy** ka matlab chori hui lambi umar ki private key **purane sessions decrypt nahi kar sakti**, jo har session ke liye **taazi, aarzi ("ephemeral") key-exchange keys** le kar baad me mita dene se hasil hota hai. Hamla awar aaj encrypted traffic record karte hain is umeed par ke baad me key chura lenge. Purane TLS "RSA key transport" me (client session key server ki RSA key se encrypt karta hai) ek chori server key **har record shuda session** khol deti hai; ephemeral Diffie-Hellman me maazi se **kuch nahi**. TLS 1.3 **hamesha** ephemeral exchange istemal karta hai; server ki lambi umar ki key sirf handshake **sign** karti hai (dekhein **TLS and Certificates**). TLS 1.2 me ECDHE suites ko tarjeeh dein aur static RSA band karein.

</Ur>
</Tr>

</Step>

<Step title="RSA vs elliptic-curve keys">

<Tr>
<En>

Two families are in use: **RSA** and **elliptic-curve cryptography (ECC)**: ECDSA/ECDH on P-256, and Ed25519 (signatures) / X25519 (key exchange) on Curve25519. ECC gives the same security with **much smaller keys** and faster operations (256-bit ECC ≈ 3072-bit RSA). Choose Ed25519/X25519 for new SSH keys, signing and key exchange; RSA 3072+ for old-system compatibility; P-256 where standards or HSMs require NIST curves.

</En>
<Ur>

Do khandan istemal me hain: **RSA** aur **elliptic-curve cryptography (ECC)**: P-256 par ECDSA/ECDH, aur Curve25519 par Ed25519 (signatures) / X25519 (key exchange). ECC **bohot chhoti keys** aur tez amal ke saath wahi security deti hai (256-bit ECC ≈ 3072-bit RSA). Nayi SSH keys, signing aur key exchange ke liye Ed25519/X25519 chunein; purane systems ke liye RSA 3072+; jahan standards ya HSMs NIST curves maangen wahan P-256.

</Ur>
</Tr>

```bash
openssl genpkey -algorithm ed25519 -out ed_private.pem
openssl pkey -in ed_private.pem -pubout -out ed_public.pem
echo "Ed25519 private key file: $(wc -c < ed_private.pem) bytes, public: $(wc -c < ed_public.pem) bytes"
echo "RSA-2048 public key file: $(wc -c < alice_public.pem) bytes"
```

```text output
Ed25519 private key file: 119 bytes, public: 113 bytes
RSA-2048 public key file: 451 bytes
```

<Happened>
<Tr>
<En>

The Ed25519 files are tiny, and most of that is PEM header text: the actual key is 32 bytes. The RSA-2048 public key file is about four times larger, for **less** security.

| Algorithm | Typical key size | Rough security | Used for |
| --- | --- | --- | --- |
| RSA | 2048 / 3072 / 4096 bits | 112 / 128 / ~140 bits | TLS certificates, older SSH, OAEP encryption |
| ECDSA / ECDH P-256 | 256 bits | 128 bits | TLS certificates, AWS KMS, HSMs |
| Ed25519 / X25519 | 256 bits | ~128 bits | SSH, Git signing, WireGuard, TLS 1.3, age |

</En>
<Ur>

Ed25519 files bohot chhoti hain, aur un ka zyada hissa PEM header ka text hai: asal key 32 bytes ki hai. RSA-2048 public key file takreeban chaar guna bari hai, **kam** security ke liye.

| Algorithm | Aam key size | Andazan security | Kis ke liye |
| --- | --- | --- | --- |
| RSA | 2048 / 3072 / 4096 bits | 112 / 128 / ~140 bits | TLS certificates, purana SSH, OAEP encryption |
| ECDSA / ECDH P-256 | 256 bits | 128 bits | TLS certificates, AWS KMS, HSMs |
| Ed25519 / X25519 | 256 bits | ~128 bits | SSH, Git signing, WireGuard, TLS 1.3, age |

</Ur>

<Step title="Key formats and fingerprints">

<Tr>
<En>

Keys come in several formats: **PEM** (Base64 text with headers), **DER** (the same in binary), **OpenSSH** (`ssh-ed25519 AAAA... comment`), PGP and JWK (JSON). A **fingerprint** is a short hash of a public key, so humans can check "is this really the right key?" without comparing long strings: when adding SSH keys to GitHub, verifying a server's host key on first connect, or configuring JWKS. Always verify a fingerprint through a **separate, trusted channel** the first time.

</En>
<Ur>

<Step title="Protect private keys">

<Tr>
<En>

A private key **is** your identity: whoever has the file can decrypt what was sent to you, log in as you, or sign as you. Leaked private keys are a common breach cause (committed to Git, baked into Docker images, left in CI logs). Protect them with a **passphrase** (the file is stored encrypted), strict **permissions** (`chmod 600`; SSH refuses keys readable by others), an **agent** (ssh-agent, 1Password, Windows Hello), or **hardware** (YubiKey, TPM, Secure Enclave, HSM, KMS) so the key can't be copied. ## Common mistakes

<Compare>
<Bad title="Private key in the repo, RSA on the whole file">

```text
git add deploy_key.pem                       # the PRIVATE key, now in history
openssl pkeyutl -encrypt -pubin -inkey bob.pub -in backup.tar -out backup.enc
# fails (too large) or, with textbook RSA, is insecure
```

</Bad>
<Good title="Share only the public key, encrypt the hybrid way">

```text
cat deploy_key.pub                            # this half is safe to share
age -r "$(cat bob.age.pub)" backup.tar > backup.tar.age   # X25519 + AEAD inside
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **RSA without proper padding** ("textbook RSA") or with PKCS#1 v1.5 encryption padding.
- **RSA keys under 2048 bits**, or choosing RSA for new systems when Ed25519/X25519 is simpler and stronger.
- **Trusting a public key without verifying it** (accepting any SSH host key), which enables man-in-the-middle attacks.
- **No passphrase and loose permissions** on private key files.
- **One key pair for everything** (encryption, signing, several environments), so one leak compromises all.
- **Forgetting to revoke** keys of people who left or machines that were decommissioned.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sahi padding ke baghair RSA** ("textbook RSA") ya PKCS#1 v1.5 encryption padding.
- **2048 bits se chhoti RSA keys**, ya naye systems ke liye RSA jab Ed25519/X25519 saada aur mazboot hai.
- **Bina tasdeeq public key par bharosa** (koi bhi SSH host key maan lena), jis se man-in-the-middle hamle hote hain.
- Private key files par **passphrase nahi aur dheeli permissions**.
- **Har kaam ke liye ek key pair** (encryption, signing, kai mahol), ek leak sab barbaad.
- Chhor jane walon ya band machines ki keys **revoke karna bhoolna**.

</Ur>
</Tr>

<Challenge title="Encrypt a file for one specific person">

<Tr>
<En>
Build `seal.py`: encrypt a file **for one person** using their public key, so nobody else (not even you, the sender) can open it. It uses the same design as the `age` tool: an ephemeral X25519 key exchange, HKDF, and AES-GCM.
</En>
<Ur>
`seal.py` banayen: kisi **ek shakhs** ke liye us ki public key se file encrypt karein, taa ke koi aur (aap, bhejne wale, bhi nahi) use khol na sake. Ye `age` tool wala design istemal karta hai: ephemeral X25519 key exchange, HKDF, aur AES-GCM.
</Ur>
</Tr>

```bash
cat > seal.py <<'PY'
import base64, os, sys
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey, X25519PublicKey
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.exceptions import InvalidTag

RAW = dict(encoding=serialization.Encoding.Raw, format=serialization.PublicFormat.Raw)

def keygen(name):
    priv = X25519PrivateKey.generate()
    raw_priv = priv.private_bytes(serialization.Encoding.Raw, serialization.PrivateFormat.Raw, serialization.NoEncryption())
    open(f"{name}.key", "w").write(base64.b64encode(raw_priv).decode() + "\n")
    open(f"{name}.pub", "w").write(base64.b64encode(priv.public_key().public_bytes(**RAW)).decode() + "\n")
    os.chmod(f"{name}.key", 0o600)
    print(f"created {name}.key (secret) and {name}.pub (share it)")

def derive(shared, eph_pub, rcpt_pub):
    return HKDF(algorithm=hashes.SHA256(), length=32, salt=None,
                info=b"devguide-seal v1" + eph_pub + rcpt_pub).derive(shared)

def seal(pub_file, path):
    rcpt_pub = base64.b64decode(open(pub_file).read())
    eph = X25519PrivateKey.generate()                       # fresh key pair for this file only
    eph_pub = eph.public_key().public_bytes(**RAW)
    key = derive(eph.exchange(X25519PublicKey.from_public_bytes(rcpt_pub)), eph_pub, rcpt_pub)
    nonce = os.urandom(12)
    ct = AESGCM(key).encrypt(nonce, open(path, "rb").read(), None)
    open(path + ".sealed", "wb").write(eph_pub + nonce + ct)
    print(f"sealed {path} for {pub_file}")

def unseal(key_file, path):
    priv = X25519PrivateKey.from_private_bytes(base64.b64decode(open(key_file).read()))
    blob = open(path, "rb").read()
    eph_pub, nonce, ct = blob[:32], blob[32:44], blob[44:]
    rcpt_pub = priv.public_key().public_bytes(**RAW)
    key = derive(priv.exchange(X25519PublicKey.from_public_bytes(eph_pub)), eph_pub, rcpt_pub)
    try:
        print(AESGCM(key).decrypt(nonce, ct, None).decode(), end="")
    except InvalidTag:
        print(f"{key_file}: cannot open this file (not the recipient)")

cmd, *args = sys.argv[1:]
{"keygen": keygen, "seal": seal, "unseal": unseal}[cmd](*args)
PY
python3 seal.py keygen emma
python3 seal.py keygen jack
printf 'Prod DB password: S3cureP@ss2026\n' > handover.txt
python3 seal.py seal emma.pub handover.txt
python3 seal.py unseal emma.key handover.txt.sealed
python3 seal.py unseal jack.key handover.txt.sealed
ls -l emma.key | cut -c1-10
```

```text output
created emma.key (secret) and emma.pub (share it)
created jack.key (secret) and jack.pub (share it)
sealed handover.txt for emma.pub
Prod DB password: S3cureP@ss2026
jack.key: cannot open this file (not the recipient)
-rw-------
```

<Hint>
<Tr>
<En>**seal** makes an **ephemeral** key pair for this one file, exchanges it with Emma's public key, runs the result through HKDF (bound to both public keys and a version label), and writes `ephemeral public key + nonce + ciphertext`; the ephemeral private key is then forgotten. **unseal** combines Emma's private key with the ephemeral public key to get the same secret. Jack's key gives a different secret, so AES-GCM fails. In practice, use the real, reviewed **age** tool.</En>
<Ur>**seal** is ek file ke liye **ephemeral** key pair banata hai, use Emma ki public key se exchange karta hai, nateeja HKDF se guzarta hai (dono public keys aur version label se bandha), aur `ephemeral public key + nonce + ciphertext` likhta hai; phir ephemeral private key bhula di jati hai. **unseal** Emma ki private key ko ephemeral public key se mila kar wahi raaz paata hai. <DeepDive title="Real world: secrets in Git, encrypted for each engineer">

A DevOps team keeps Kubernetes production secrets in Git using **SOPS** with **age** keys. Each engineer generates an age key pair; the public keys are listed in `.sops.yaml`, and the private keys stay on laptops (in the OS keychain) and in CI's secret store. When a secrets file is edited, SOPS encrypts each value with a random data key and wraps that key once **for every listed public key**: hybrid encryption, like `seal.py` but for several recipients. When an engineer leaves, the team removes their public key, runs `sops updatekeys` to re-wrap the data keys, and rotates the actual secrets, since the departing engineer could have decrypted them before. Their SSH key is removed from all servers and their GitHub access revoked: key pairs are identities, and offboarding means removing every public key that trusted them.

</DeepDive>

<DeepDive title="Security lens">

Public-key crypto removes the need to share secrets, but adds a new question: is this public key really theirs? Verifying keys matters as much as keeping private keys private.

- **Man-in-the-middle:** if an attacker gives you **their** public key while claiming to be your bank, you encrypt for the attacker. Certificates (PKI), SSH known_hosts and fingerprint checks prevent this.
- **Key storage:** hardware-backed keys (YubiKey, TPM, Secure Enclave, HSM, KMS) can't be copied by malware.
- **Inventory and rotation:** know which keys exist, who owns them and where they're trusted; rotate on a schedule and immediately after a suspected leak.
- **Forward secrecy:** prefer ephemeral key exchange so a future key compromise doesn't expose recorded traffic.
- **Post-quantum:** large quantum computers would break RSA and ECC. New standards exist (ML-KEM for key exchange, ML-DSA for signatures), and hybrid X25519 + ML-KEM is already on by default in major browsers and OpenSSH. Plan for crypto-agility.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between symmetric and asymmetric encryption?">
Symmetric encryption uses one shared secret key for encryption and decryption and is fast, but the key must be shared securely in advance. Asymmetric encryption uses a key pair, where data encrypted with the public key can only be decrypted with the private key, so no secret has to be shared beforehand. It is much slower and limited to small inputs, so real systems combine both in hybrid encryption.
</QA>

<QA q="Why do systems like TLS use hybrid encryption instead of encrypting everything with RSA?">
Public-key operations are far slower than symmetric ciphers and can only process data smaller than the key size. Hybrid schemes use public-key cryptography only to agree or transport a random symmetric key, then use a fast authenticated cipher such as AES-GCM for the actual data.
</QA>

<QA q="How does Diffie-Hellman key exchange work at a high level?">
Each party generates a private value and a corresponding public value and sends only the public value. Each party combines its own private value with the other's public value, and the mathematics ensures both arrive at the same shared secret. An eavesdropper who sees only the public values cannot compute the secret. The secret is then passed through a key derivation function to produce session keys.
</QA>

<QA q="What is forward secrecy?">
Forward secrecy means that compromise of a long-term private key does not allow decryption of past sessions. It is achieved by using ephemeral key exchange keys for each session, such as ECDHE in TLS, and discarding them afterwards, so recorded traffic cannot be decrypted later. TLS 1.3 always provides it.
</QA>

<QA q="What would you do if a private key was committed to a public GitHub repository?">
Treat it as compromised: revoke and replace it immediately by removing the public key from every system that trusts it, revoking any certificate, and generating a new key pair. Then investigate logs for misuse, rotate any secrets the key could access or decrypt, remove the key from the repository history, and add secret scanning and pre-commit hooks to prevent recurrence.
</QA>

</DeepDive>
