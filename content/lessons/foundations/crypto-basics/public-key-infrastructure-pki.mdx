<BigIdea>
<Tr>
<En>
Public-key cryptography only works if you're sure a public key **really belongs** to who it claims. Otherwise an attacker hands you **their** key and reads everything (a **man-in-the-middle**). **PKI (Public Key Infrastructure)** solves this with **certificates**: an **X.509 certificate** is a public key plus an identity (like `shop.example.com`), **signed by a Certificate Authority (CA)**. Your browser and OS ship with a **trust store** of root CAs. Roots sign **intermediate** CAs, which sign **leaf** (server) certificates: a **chain of trust**. A client accepts a certificate only if the chain reaches a trusted root, every signature is valid, it isn't **expired** or **revoked**, and the **hostname matches** its **Subject Alternative Names**.
</En>
<Ur>
Public-key cryptography tab hi kaam karti hai jab aap ko yaqeen ho ke public key **waqai** usi ki hai jis ka daawa hai. Warna hamla awar aap ko **apni** key de kar sab parh leta hai (**man-in-the-middle**). **PKI (Public Key Infrastructure)** ye **certificates** se hal karta hai: **X.509 certificate** ek public key aur ek shanakht (jaise `shop.example.com`) hai, **Certificate Authority (CA) ka sign kiya hua**. Aap ke browser aur OS ke saath root CAs ka **trust store** aata hai. Roots **intermediate** CAs ko sign karte hain, jo **leaf** (server) certificates sign karte hain: **bharose ki zanjeer**. Client certificate tab hi maanta hai jab zanjeer bharose wale root tak pohnche, har signature durust ho, wo **expire** ya **revoke** na ho, aur **hostname** us ke **Subject Alternative Names** se **mile**.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

A certificate is like a **passport**. Anyone can **claim** to be "Sam Lee", but a passport is issued by **the passport office**, which checked Sam's identity and **stamped** it in a way that's very hard to forge. A bank doesn't need to know Sam personally; it only needs to trust the passport office and check the passport is genuine, not expired, and that the photo matches the person in front of it. In PKI: passport office = **Certificate Authority**, passport = **certificate**, stamp = the CA's **digital signature**, expiry date = **validity period**, "the photo matches" = the **hostname check**.

</En>
<Ur>

Certificate **passport** jaisa hai. Koi bhi "Sam Lee" hone ka **daawa** kar sakta hai, lekin passport **passport office** jaari karta hai, jis ne Sam ki shanakht check ki aur us par aisi **mohar** lagayi jo jaali banana bohot mushkil hai. Bank ko Sam ko zaati taur par jaanne ki zaroorat nahi; use sirf passport office par bharosa aur ye check karna hai ke passport asli hai, expire nahi, aur tasveer saamne khare shakhs se milti hai. PKI me: passport office = **Certificate Authority**, passport = **certificate**, mohar = CA ka **digital signature**, expiry date = **validity period**, "tasveer milti hai" = **hostname check**.

</Ur>
</Tr>

<Step title="The problem: is this key really theirs?">

<Tr>
<En>

Encryption and signatures assume you have the **right** public key. An attacker on the network (public Wi-Fi, a hacked router, malicious DNS) can intercept your connection and send **their own** key, so encryption protects your data **all the way to the attacker**. SSH handles this with manual fingerprint checks ("trust on first use"); the web can't ask billions of users to compare fingerprints, so **CAs vouch for keys**. A CA checks that the requester controls the domain (a token on the website or in DNS), then signs a certificate binding the name to their key.

```text
You ──── "hello shop.example.com" ────► Attacker ───────► real shop.example.com
    ◄── attacker's public key ────────┘          ◄── real public key
Without PKI you can't tell the difference. With PKI, the attacker can't show
a valid certificate for shop.example.com signed by a CA you trust.
```

</En>
<Ur>

Encryption aur signatures maan kar chalte hain ke aap ke paas **sahi** public key hai. Network par hamla awar (public Wi-Fi, hack hua router, bad-niyat DNS) aap ka connection beech me pakar kar **apni** key bhej sakta hai, to encryption aap ka data **seedha hamla awar tak** mehfooz pohnchati hai. SSH ye haath se fingerprint check ("trust on first use") se sambhalta hai; web arbon users se fingerprints milane ko nahi keh sakta, isliye **CAs keys ki zamanat** dete hain. CA check karta hai ke maangne wala domain ka maalik hai (website ya DNS me token), phir naam ko us ki key se jorne wala certificate sign karta hai.

```text
You ──── "hello shop.example.com" ────► Attacker ───────► real shop.example.com
    ◄── attacker's public key ────────┘          ◄── real public key
Without PKI you can't tell the difference. With PKI, the attacker can't show
a valid certificate for shop.example.com signed by a CA you trust.
```

</Ur>
</Tr>

</Step>

<Step title="A root CA: the anchor of trust">

<Tr>
<En>

A **root CA** has a **self-signed** certificate: it vouches for itself, and clients trust it only because it's in their **trust store** (`/etc/ssl/certs`, macOS Keychain, the Windows store, Firefox, Java `cacerts`). Public roots pass audits and inclusion programmes run by Microsoft, Apple, Mozilla and Google; their private keys stay **offline** in HSMs and are used only in ceremonies. `basicConstraints=CA:true` marks a CA; `keyUsage=keyCertSign` lets it sign certificates.

</En>
<Ur>

**Root CA** ka certificate **self-signed** hota hai: wo apni zamanat khud deta hai, aur clients us par sirf isliye bharosa karte hain ke wo un ke **trust store** me hai (`/etc/ssl/certs`, macOS Keychain, Windows store, Firefox, Java `cacerts`). Public roots Microsoft, Apple, Mozilla aur Google ke audits aur inclusion programmes se guzarte hain; un ki private keys **offline** HSMs me rehti hain aur sirf khaas taqreebat me istemal hoti hain. `basicConstraints=CA:true` CA ki nishani hai; `keyUsage=keyCertSign` use certificates sign karne deta hai.

</Ur>
</Tr>

```bash
openssl req -x509 -newkey ed25519 -nodes -keyout root.key -out root.crt -days 3650 \
  -subj "/C=US/O=DevGuide Root CA/CN=DevGuide Root CA" \
  -addext "basicConstraints=critical,CA:true" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" 2>/dev/null
openssl x509 -in root.crt -noout -subject -issuer
openssl x509 -in root.crt -noout -ext basicConstraints | tail -1
```

```text output
subject=C = US, O = DevGuide Root CA, CN = DevGuide Root CA
issuer=C = US, O = DevGuide Root CA, CN = DevGuide Root CA
    CA:TRUE
```

<Happened>
<Tr>
<En>

- `openssl req -x509` creates a self-signed certificate directly. `-newkey ed25519 -nodes` makes a new key without a passphrase (lab only; a real root key is HSM- or passphrase-protected). `-days 3650` = 10 years.
- `-subj` sets the **subject**: country (`C`), organisation (`O`), common name (`CN`).
- `-addext` adds X.509 **extensions**. `critical` means clients that don't understand the extension must reject the certificate.
- **Subject and issuer are identical:** that's what "self-signed" means.

</En>
<Ur>

- `openssl req -x509` seedha self-signed certificate banata hai. `-newkey ed25519 -nodes` bina passphrase nayi key banata hai (sirf lab; asli root key HSM ya passphrase se mehfooz hoti hai). `-days 3650` = 10 saal.
- `-subj` **subject** set karta hai: mulk (`C`), idara (`O`), common name (`CN`).
- `-addext` X.509 **extensions** jorta hai. `critical` ka matlab jo clients extension na samjhen wo certificate radd karen.
- **Subject aur issuer ek jaise:** "self-signed" ka yahi matlab hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="An intermediate CA">

<Tr>
<En>

An **intermediate CA** is certified **by the root** and does the daily work of issuing server certificates. The root key stays offline; if an intermediate is compromised, the root revokes it and makes a new one, without every device in the world updating its trust store. Let's Encrypt leaves are signed by intermediates like `R11` or `E6`, signed by `ISRG Root X1`/`X2`. `pathlen:0` means this intermediate may sign leaves but no further CAs, limiting damage if it leaks.

</En>
<Ur>

**Intermediate CA** **root** se tasdeeq shuda hota hai aur roz server certificates jaari karne ka kaam karta hai. Root key offline rehti hai; intermediate compromise ho to root use revoke kar ke naya bana deta hai, duniya ke har device ko trust store update kiye baghair. Let's Encrypt ke leaves `R11` ya `E6` jaise intermediates sign karte hain, jo `ISRG Root X1`/`X2` ke sign kiye hain. `pathlen:0` ka matlab ye intermediate leaves sign kar sakta hai magar mazeed CAs nahi, taa ke leak hone par nuqsan mehdood rahe.

</Ur>
</Tr>

```bash
openssl req -newkey ed25519 -nodes -keyout inter.key -out inter.csr \
  -subj "/C=US/O=DevGuide/CN=DevGuide Issuing CA 1" 2>/dev/null
printf 'basicConstraints=critical,CA:true,pathlen:0\nkeyUsage=critical,keyCertSign,cRLSign\n' > inter.ext
openssl x509 -req -in inter.csr -CA root.crt -CAkey root.key -CAcreateserial -days 1825 \
  -extfile inter.ext -out inter.crt 2>/dev/null
openssl x509 -in inter.crt -noout -subject -issuer
```

```text output
subject=C = US, O = DevGuide, CN = DevGuide Issuing CA 1
issuer=C = US, O = DevGuide Root CA, CN = DevGuide Root CA
```

<Happened>
<Tr>
<En>The intermediate made its own key pair and a **CSR** with its name. `inter.ext` lists the extensions the root puts in (a CA, `pathlen:0`). `openssl x509 -req … -CA root.crt -CAkey root.key` makes the **root sign** the request; `-CAcreateserial` creates a serial-number file (every certificate gets a unique serial) and `-days 1825` = 5 years. The intermediate's **issuer** is now the root: the first link of the chain.</En>
<Ur>Intermediate ne apna key pair aur apne naam ki **CSR** banayi. `inter.ext` wo extensions batata hai jo root daalega (CA, `pathlen:0`). `openssl x509 -req … -CA root.crt -CAkey root.key` se **root request sign** karta hai; `-CAcreateserial` serial-number file banata hai (har certificate ka munfarid serial) aur `-days 1825` = 5 saal. Intermediate ka **issuer** ab root hai: zanjeer ki pehli kari.</Ur>
</Tr>
</Happened>

</Step>

<Step title="The Certificate Signing Request (CSR)">

<Tr>
<En>

A **CSR** holds the requester's **public key**, the requested **name**, and a signature made with the requester's **private key** (proving they own it). The private key never leaves the server, so the CA certifies a key without ever seeing the secret. CSRs come from `openssl req -new`, Certbot and cert-manager (automatically), or "Create CSR" buttons in IIS and cloud consoles. Here the shop's server creates an ECDSA P-256 key and a CSR.

</En>
<Ur>

**CSR** me maangne wale ki **public key**, maanga hua **naam**, aur us ki **private key** se bana signature hota hai (saboot ke key us ki hai). Private key server se kabhi nahi nikalti, isliye CA raaz dekhe baghair key ki tasdeeq karta hai. CSRs `openssl req -new`, Certbot aur cert-manager (khud ba khud), ya IIS aur cloud consoles ke "Create CSR" buttons se bante hain. Yahan shop ka server ECDSA P-256 key aur CSR banata hai.

</Ur>
</Tr>

```bash
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout shop.key -out shop.csr \
  -subj "/CN=shop.devguide.test" 2>/dev/null
openssl req -in shop.csr -noout -subject
openssl req -in shop.csr -noout -verify 2>&1 | tail -1
```

```text output
subject=CN = shop.devguide.test
Certificate request self-signature verify OK
```

<Happened>
<Tr>
<En>`-newkey ec -pkeyopt ec_paramgen_curve:P-256` made an ECDSA P-256 key pair (the most common type for modern TLS); `shop.key` stays on the server. The CSR asks for `shop.devguide.test`. `-verify` checked the CSR's own signature: proof that whoever made it holds the matching private key.</En>
<Ur>`-newkey ec -pkeyopt ec_paramgen_curve:P-256` ne ECDSA P-256 key pair banaya (jadeed TLS ki sab se aam qisam); `shop.key` server par rehti hai. CSR `shop.devguide.test` maangti hai. `-verify` ne CSR ka apna signature check kiya: saboot ke banane wale ke paas joridar private key hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Issuing the server certificate">

<Tr>
<En>

The intermediate signs the CSR, producing the **leaf certificate** with limiting extensions: not a CA, used for server authentication, valid for specific hostnames. A stolen server certificate then can't sign other certificates. Browsers check the hostname against the **SAN**; the old `CN` field is ignored for that. Public certificates are short-lived (90 days at Let's Encrypt; the industry maximum is shrinking to 47 days by 2029), so renewal must be automated.

</En>
<Ur>

Intermediate CSR sign kar ke **leaf certificate** banata hai, hadd lagane wali extensions ke saath: CA nahi, server authentication ke liye, khaas hostnames ke liye durust. Is tarah chori hua server certificate doosre certificates sign nahi kar sakta. Browsers hostname **SAN** se milate hain; purana `CN` field is kaam ke liye nazar andaz hota hai. Public certificates chhoti umar ke hain (Let's Encrypt par 90 din; industry ki zyada se zyada hadd 2029 tak 47 din ho rahi hai), isliye renewal automate hona zaroori hai.

</Ur>
</Tr>

```bash
printf 'basicConstraints=CA:false\nkeyUsage=critical,digitalSignature\nextendedKeyUsage=serverAuth\nsubjectAltName=DNS:shop.devguide.test,DNS:www.shop.devguide.test\n' > shop.ext
openssl x509 -req -in shop.csr -CA inter.crt -CAkey inter.key -CAcreateserial -days 90 \
  -extfile shop.ext -out shop.crt 2>/dev/null
openssl x509 -in shop.crt -noout -subject -issuer
openssl x509 -in shop.crt -noout -ext subjectAltName,extendedKeyUsage
cat shop.crt inter.crt > fullchain.pem
grep -c 'BEGIN CERTIFICATE' fullchain.pem | sed 's/$/ certificates in fullchain.pem/'
```

```text output
subject=CN = shop.devguide.test
issuer=C = US, O = DevGuide, CN = DevGuide Issuing CA 1
X509v3 Extended Key Usage: 
    TLS Web Server Authentication
X509v3 Subject Alternative Name: 
    DNS:shop.devguide.test, DNS:www.shop.devguide.test
2 certificates in fullchain.pem
```

<Happened>
<Tr>
<En>

- `shop.ext`: not a CA, key used for digital signatures (TLS handshakes), purpose server authentication, valid names `shop.devguide.test` and `www.shop.devguide.test`.
- The **intermediate** signed it for 90 days, so the chain is root → intermediate → leaf.
- OpenSSL printed the extensions in the order they're stored in the certificate.
- `fullchain.pem` = leaf + intermediate. Servers must send **both**; the client already has the root. Sending only the leaf is a very common misconfiguration: browsers sometimes cope, but many API clients, mobile apps and `curl` fail.

</En>
<Ur>

- `shop.ext`: CA nahi, key digital signatures (TLS handshakes) ke liye, maqsad server authentication, durust naam `shop.devguide.test` aur `www.shop.devguide.test`.
- **Intermediate** ne 90 din ke liye sign kiya, to zanjeer root → intermediate → leaf hai.
- OpenSSL ne extensions usi tarteeb me chhaapin jis me wo certificate me mehfooz hain.
- `fullchain.pem` = leaf + intermediate. Servers ko **dono** bhejne chahiyen; root client ke paas pehle se hai. Sirf leaf bhejna bohot aam ghalat setting hai: browsers kabhi sambhal lete hain, lekin bohot se API clients, mobile apps aur `curl` fail hote hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Verifying the chain of trust">

<Tr>
<En>

**Chain validation:** starting at the leaf, the client checks each signature with the next certificate's public key until it reaches a root in its trust store. That's how a client that has never heard of `shop.devguide.test` can trust it: it trusts the root, the root vouched for the intermediate, the intermediate vouched for the leaf. `openssl verify -CAfile <trusted roots> -untrusted <intermediates> <leaf>` mimics this ("untrusted" = use these to build the chain, but don't trust them alone).

</En>
<Ur>

**Chain validation:** leaf se shuru kar ke client har signature agle certificate ki public key se check karta hai jab tak trust store ke kisi root tak na pohnche. Isi tarah `shop.devguide.test` ka naam kabhi na sunne wala client bhi us par bharosa karta hai: wo root par bharosa karta hai, root ne intermediate ki zamanat di, intermediate ne leaf ki. `openssl verify -CAfile <trusted roots> -untrusted <intermediates> <leaf>` yahi karta hai ("untrusted" = inhen zanjeer banane me istemal karo, lekin akele bharosa na karo).

</Ur>
</Tr>

```bash
openssl verify -CAfile root.crt -untrusted inter.crt shop.crt
openssl verify -CAfile root.crt shop.crt 2>&1 | grep -o 'error [0-9]* at [0-9] depth lookup: .*'
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt -untrusted inter.crt shop.crt 2>&1 | grep -o 'error [0-9]* at [0-9] depth lookup: .*'
```

```text output
shop.crt: OK
error 20 at 0 depth lookup: unable to get local issuer certificate
error 20 at 1 depth lookup: unable to get local issuer certificate
```

<Happened>
<Tr>
<En>

- With our root trusted and the intermediate available, the chain is complete: `shop.crt: OK`.
- Without the intermediate, OpenSSL can't find who issued the leaf: **error 20** at depth 0. This is what clients see when a server forgets its intermediate, one of the most common TLS errors.
- With the system's public trust store instead of our root, our private root isn't found: error 20 at depth 1. Your private CA isn't trusted by the world, which is correct, and why internal clients need your root installed.

</En>
<Ur>

- Hamare root par bharose aur intermediate ki maujoodgi se zanjeer mukammal: `shop.crt: OK`.
- Intermediate ke baghair OpenSSL ko leaf jaari karne wala nahi milta: depth 0 par **error 20**. Jab server intermediate bhool jaye to clients yahi dekhte hain, sab se aam TLS errors me se ek.
- Hamare root ki jagah system ke public trust store se hamara private root nahi milta: depth 1 par error 20. Aap ke private CA par duniya bharosa nahi karti, jo sahi hai, aur isi liye andaruni clients par aap ka root install karna parta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Hostname checking">

<Tr>
<En>

A valid chain isn't enough: the certificate must be issued **for the name you connected to**. Clients compare the hostname with the SAN entries (a wildcard like `*.example.com` covers one label level). Otherwise an attacker with a perfectly valid certificate for `evil.example` could impersonate your shop. Browsers, `curl` and HTTP libraries do this by default; custom TLS code sometimes forgets, which is why `verify=False`, `rejectUnauthorized: false` and `InsecureSkipVerify` are dangerous.

</En>
<Ur>

Durust zanjeer kaafi nahi: certificate **usi naam ke liye** jaari hona chahiye jis se aap jure. Clients hostname ko SAN entries se milate hain (`*.example.com` jaisa wildcard ek label level dhaanpta hai). Warna `evil.example` ke bilkul durust certificate wala hamla awar aap ki shop ka roop dhaar sakta hai. Browsers, `curl` aur HTTP libraries ye khud karti hain; custom TLS code kabhi bhool jata hai, isi liye `verify=False`, `rejectUnauthorized: false` aur `InsecureSkipVerify` khatarnak hain.

</Ur>
</Tr>

```bash
openssl verify -CAfile root.crt -untrusted inter.crt -verify_hostname shop.devguide.test shop.crt
openssl verify -CAfile root.crt -untrusted inter.crt -verify_hostname www.shop.devguide.test shop.crt
openssl verify -CAfile root.crt -untrusted inter.crt -verify_hostname evil.example shop.crt 2>&1 | grep -o 'error [0-9]* at [0-9] depth lookup: .*'
```

```text output
shop.crt: OK
shop.crt: OK
error 62 at 0 depth lookup: hostname mismatch
```

<Happened>
<Tr>
<En>Both SAN names were accepted. `evil.example` isn't in the SAN, so verification failed with **error 62: hostname mismatch**, the same check that makes browsers show "Your connection is not private" (NET::ERR_CERT_COMMON_NAME_INVALID).</En>
<Ur>SAN ke dono naam qubool hue. `evil.example` SAN me nahi, isliye verification **error 62: hostname mismatch** se fail hui, wahi check jis se browsers "Your connection is not private" (NET::ERR_CERT_COMMON_NAME_INVALID) dikhate hain.</Ur>
</Tr>
</Happened>

<Step title="Validity periods, expiry and automation">

<Tr>
<En>

Every certificate has a **notBefore** and **notAfter** date; outside that window clients reject it. Short lifetimes limit the damage of a stolen key and keep automation exercised; the downside is that forgetting to renew causes outages. Automate with **ACME** clients (Certbot, Caddy, Traefik, cert-manager, managed load-balancer certificates) and **monitor expiry** (blackbox exporter, uptime monitors, `openssl x509 -checkend`).

</En>
<Ur>

Har certificate ki **notBefore** aur **notAfter** tareekh hoti hai; us waqfe se bahar clients use radd karte hain. Chhoti umar chori hui key ka nuqsan mehdood rakhti hai aur automation ko chalta rakhti hai; nuqsan ye ke renew bhoolna outage laata hai. **ACME** clients (Certbot, Caddy, Traefik, cert-manager, managed load-balancer certificates) se automate karein aur **expiry monitor** karein (blackbox exporter, uptime monitors, `openssl x509 -checkend`).

</Ur>
</Tr>

```bash
openssl x509 -in shop.crt -noout -checkend $((30*86400)) && echo "valid for at least 30 more days"
openssl x509 -in shop.crt -noout -checkend $((100*86400)) || echo "WARNING: expires within 100 days"
future=$(( $(date +%s) + 200*86400 ))
openssl verify -CAfile root.crt -untrusted inter.crt -attime "$future" shop.crt 2>&1 | grep -o 'error [0-9]* at [0-9] depth lookup: .*'
```

```text output
Certificate will not expire
valid for at least 30 more days
Certificate will expire
WARNING: expires within 100 days
error 10 at 0 depth lookup: certificate has expired
```

<Happened>
<Tr>
<En>`-checkend SECONDS` asks "still valid that many seconds from now?", prints a message and exits 0 (yes) or 1 (no): perfect for monitoring scripts and CI. Our 90-day certificate is fine for 30 more days but expires within 100. `-attime` simulated a date 200 days ahead: **error 10: certificate has expired**, exactly what clients report when renewal fails.</En>
<Ur>`-checkend SECONDS` poochhta hai "itne seconds baad bhi durust?", paigham chhaapta hai aur 0 (haan) ya 1 (nahi) se nikalta hai: monitoring scripts aur CI ke liye behtareen. Hamara 90 din ka certificate mazeed 30 din theek hai lekin 100 din ke andar expire hoga. `-attime` ne 200 din aage ki tareekh banayi: **error 10: certificate has expired**, bilkul wahi jo renewal fail hone par clients batate hain.</Ur>
</Tr>
</Happened>

<Step title="A real TLS server using your PKI">

<Tr>
<En>

A TLS server presents its chain during the handshake; the client validates chain, hostname and dates before sending any data. `openssl s_server` is a minimal test server; `openssl s_client` is a test client (great for real servers too: `openssl s_client -connect example.com:443 -servername example.com`). The server sends `shop.crt` plus `inter.crt`; the client trusts only `root.crt`.

</En>
<Ur>

TLS server handshake ke dauran apni zanjeer dikhata hai; client koi data bhejne se pehle zanjeer, hostname aur tareekhen check karta hai. `openssl s_server` chhota test server hai; `openssl s_client` test client (asli servers ke liye bhi zabardast: `openssl s_client -connect example.com:443 -servername example.com`). Server `shop.crt` aur `inter.crt` bhejta hai; client sirf `root.crt` par bharosa karta hai.

</Ur>
</Tr>

```bash
PORT=$((20000 + RANDOM % 20000))
openssl s_server -accept "$PORT" -cert shop.crt -key shop.key -cert_chain inter.crt -www -quiet >/dev/null 2>&1 &
SERVER=$!
sleep 1
echo "--- correct name, our root trusted:"
echo | openssl s_client -connect 127.0.0.1:"$PORT" -servername shop.devguide.test \
  -verify_hostname shop.devguide.test -CAfile root.crt -showcerts 2>/dev/null \
  | grep -E '^ [0-9] s:|^Verification:|Verify return code'
echo "--- wrong name:"
echo | openssl s_client -connect 127.0.0.1:"$PORT" -verify_hostname evil.example -CAfile root.crt \
  -verify_return_error 2>&1 | grep -oE 'verify error:num=[0-9]+:[a-z ]+' | head -1
kill "$SERVER"
```


<Tr>
<En>

- The server started in the background on a random port with its key, certificate and intermediate (`-cert_chain`); `$!` saved its process ID to stop it at the end.

- `Verification: OK`: chain, signatures, dates and hostname are all valid. Expecting `evil.example` failed with error 62, and `-verify_return_error` aborted the handshake.

</En>
<Ur>

- Server background me random port par apni key, certificate aur intermediate (`-cert_chain`) ke saath chala; `$!` ne aakhir me band karne ke liye us ka process ID rakha.
- Client SNI (`-servername`) ke saath jura, hostname check kiya, aur sirf hamare root par bharosa kiya.

<Step title="Revocation: when a certificate must die early">

<Tr>
<En>

If a private key leaks or a certificate was issued wrongly, the CA **revokes** it before expiry. Clients learn through **CRLs** (downloaded lists of revoked serials), **OCSP** (asking the CA about one certificate) or **OCSP stapling** (the server attaches a recent signed answer). On the public web revocation checking is unreliable (browsers "soft-fail"), so the industry moves to **short-lived certificates**: Let's Encrypt shut down OCSP in 2025 and relies on CRLs plus short lifetimes; Firefox CRLite and Chrome CRLSets push revocation data to browsers. In **private PKIs** you control the clients, so CRL/OCSP checks can be enforced. After a leak: revoke, replace the certificate **and** the key, and find out how it leaked.

</En>
<Ur>

Private key leak ho ya certificate ghalat jaari hua ho to CA use expiry se pehle **revoke** karta hai. Clients **CRLs** (revoke hue serials ki download hone wali lists), **OCSP** (ek certificate ke baare me CA se poochhna) ya **OCSP stapling** (server taaza signed jawab saath lagata hai) se jaante hain. Public web par revocation check bharose ke qabil nahi (browsers "soft-fail" karte hain), isliye industry **chhoti umar ke certificates** ki taraf ja rahi hai: Let's Encrypt ne 2025 me OCSP band kiya aur CRLs aur chhoti umar par chalta hai; Firefox CRLite aur Chrome CRLSets revocation data browsers tak pohnchate hain. **Private PKIs** me clients aap ke qaboo me hain, isliye CRL/OCSP checks lazmi kiye ja sakte hain. Leak ke baad: revoke karein, certificate **aur** key dono badlein, aur pata karein leak kaise hua.

</Ur>
</Tr>

</Step>

<Step title="Certificate Transparency and CAA">

<Tr>
<En>

Public CAs must record every certificate in **Certificate Transparency (CT) logs**: public, append-only logs anyone can search; browsers require proof of logging (SCTs). If a CA is hacked or makes a mistake and issues a certificate for **your** domain to someone else, you can find out (DigiNotar 2011 and Symantec led to this). Monitor with crt.sh (`%.yourdomain.com`), Cert Spotter or alerting services; pentesters also discover subdomains this way. Publish a **CAA DNS record** so only your chosen CAs may issue for your domain.

```text
$ dig +short CAA example.com            # which CAs may issue for this domain (example output)
0 issue "letsencrypt.org"
0 iodef "mailto:security@example.com"
```

</En>
<Ur>

Public CAs ko har certificate **Certificate Transparency (CT) logs** me darj karna hota hai: public, sirf-izafa logs jinhen koi bhi talash kar sake; browsers logging ka saboot (SCTs) maangte hain. Agar CA hack ho ya ghalti se **aap ke** domain ka certificate kisi aur ko de de, to aap ko pata chal sakta hai (DigiNotar 2011 aur Symantec ki wajah se ye bana). crt.sh (`%.yourdomain.com`), Cert Spotter ya alert services se nigrani karein; pentesters bhi isi tarah subdomains dhoondte hain. **CAA DNS record** shaya karein taa ke sirf aap ke chune CAs aap ke domain ke liye jaari kar saken.

```text
$ dig +short CAA example.com            # which CAs may issue for this domain (example output)
0 issue "letsencrypt.org"
0 iodef "mailto:security@example.com"
```

</Ur>
</Tr>

</Step>

<Step title="Private PKI and mutual TLS">

<Tr>
<En>

A **private PKI** is a CA you run for your own organisation. In **mutual TLS (mTLS)** **both** sides present certificates: the server proves itself to the client and the client to the server. Each service gets a cryptographic identity and all internal traffic is encrypted: a core part of **zero-trust**. Used in the Kubernetes control plane, service meshes (Istio/Linkerd give every pod short-lived certificates), VPNs and EAP-TLS Wi-Fi, IoT devices and B2B or banking APIs. Tools: Vault PKI, AWS Private CA, step-ca, cert-manager, SPIFFE/SPIRE, with the same root → intermediate structure you just built. In Nginx: `ssl_client_certificate` + `ssl_verify_client on`.

</En>
<Ur>

**Private PKI** wo CA hai jo aap apne idare ke liye chalate hain. **Mutual TLS (mTLS)** me **dono** taraf certificates dikhati hain: server client ko apni pehchaan sabit karta hai aur client server ko. Har service ko cryptographic shanakht milti hai aur saari andaruni traffic encrypted hoti hai: **zero-trust** ka bunyadi hissa. Kubernetes control plane, service meshes (Istio/Linkerd har pod ko chhoti umar ke certificates dete hain), VPNs aur EAP-TLS Wi-Fi, IoT devices aur B2B ya banking APIs me istemal. Tools: Vault PKI, AWS Private CA, step-ca, cert-manager, SPIFFE/SPIRE, usi root → intermediate dhaanche ke saath jo aap ne abhi banaya. Nginx me: `ssl_client_certificate` + `ssl_verify_client on`.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Silencing the error">

```text

```

</Bad>
<Good title="Fixing the cause">

```text

```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Not sending the intermediate** (only the leaf): "unable to get local issuer certificate".
- **Relying on CN instead of SAN** when issuing certificates; modern clients only check SAN.
- **Manual renewals** and no expiry monitoring.
- **Careless private keys:** committed to Git, world-readable, shared between environments.
- **One wildcard certificate everywhere**, so one compromised server exposes the key for all subdomains.
- **Keeping the root CA key online** on the machine that issues everyday certificates.
- **Self-signed certificates in production** with users trained to click through warnings.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Intermediate na bhejna** (sirf leaf): "unable to get local issuer certificate".
- **Certificates jaari karte waqt SAN ki jagah CN par bharosa**; jadeed clients sirf SAN check karte hain.
- **Haath se renewals** aur expiry ki koi nigrani nahi.
- **Lapparwahi se private keys:** Git me commit, sab ke parhne ke qabil, environments me saanjhi.
- **Har jagah ek wildcard certificate**, to ek compromise hua server saare subdomains ki key khol deta hai.
- **Root CA key online rakhna** usi machine par jo roz certificates jaari kare.
- **Production me self-signed certificates** aur users ko warnings par click karne ki aadat.

</Ur>
</Tr>

```bash
  -subj "/CN=shop.devguide.test" 2>/dev/null
check_cert() {   # usage: check_cert <cert> <hostname>
  local cert=$1 host=$2 result
  result=$(openssl verify -CAfile root.crt -untrusted inter.crt -verify_hostname "$host" "$cert" 2>&1 \
    | grep -oE 'error [0-9]+ at [0-9] depth lookup: .*|OK$' | head -1)

  end=$(openssl x509 -in "$cert" -noout -enddate | cut -d= -f2)

  else
    printf '%-10s %-24s OK    %s days left\n' "$cert" "$host" "$days"
  fi
}
```

<DeepDive title="Real world: the expired-certificate outage">

In February 2020, a large chat platform went down for many users because an **expired certificate** on an internal authentication service broke logins, and similar expiry outages have hit major mobile networks, banks and cloud services. The common causes: certificates renewed by hand, an owner who left the company, and no monitoring. Teams that fixed this for good moved to: **ACME automation** everywhere (cert-manager in Kubernetes, managed certificates on load balancers); **inventory and monitoring** of every certificate, including internal ones, with alerts at 30/14/7 days; **short-lived** internal certificates from Vault or a service mesh, so expiry is constant and therefore always automated; and **CT monitoring**, which once alerted a team that a phishing site had obtained a certificate for a lookalike domain (`paypa1-secure.example`) so they could get it taken down quickly.

</DeepDive>

<DeepDive title="Security lens">

PKI is a trust system: anyone who controls a trusted CA, or a private key with a valid certificate, can impersonate your services. Guard CA keys, automate certificates, and never switch validation off.

- **Never disable validation.** If a client fails, fix the chain, the trust store or the hostname.
- **Protect CA keys:** offline roots, HSM-backed intermediates, strict access, audit logs, and name constraints on private CAs.
- **Limit blast radius:** separate certificates per service, short lifetimes, `pathlen` and extended key usage restrictions.
- **Watch the ecosystem:** CT monitoring and CAA records.
- **TLS interception:** corporate proxies and some antivirus tools install their own root CA to inspect traffic; malware does the same to spy. Review unexpected roots in trust stores.
- **Certificate pinning** in mobile apps can stop interception but makes rotation risky; pin your own CA/intermediate keys with backups, or rely on CT and standard validation.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a certificate and what does a CA do?">
A certificate binds a public key to an identity, such as a domain name, along with a validity period and permitted uses, and is signed by a certificate authority. The CA verifies that the requester controls the identity, for example a domain, and signs the certificate so that clients who trust the CA can trust the binding.
</QA>

<QA q="Explain the chain of trust.">
A server's leaf certificate is signed by an intermediate CA, whose certificate is signed by a root CA. Clients have root certificates in their trust store. During validation the client builds the chain from the leaf through the intermediates to a trusted root, verifies every signature, and checks validity dates, constraints, revocation and that the leaf matches the requested hostname.
</QA>

<QA q="What causes the error unable to get local issuer certificate?">
The client could not build a chain from the server's certificate to a trusted root. Usually the server did not send its intermediate certificate, or the issuing root is not in the client's trust store, for example with a private CA that has not been installed on the client.
</QA>

<QA q="Why are certificate lifetimes getting shorter?">
Shorter lifetimes limit how long a stolen key or mis-issued certificate can be abused, reduce reliance on unreliable revocation checking, and force automated renewal, which in turn makes rotation routine. Public TLS certificate maximum lifetimes are being reduced step by step to 47 days by 2029.
</QA>

<QA q="What is mutual TLS and where is it used?">
In mutual TLS both sides present and verify certificates, so the server authenticates the client as well as the client authenticating the server. It is used for service-to-service authentication in service meshes and Kubernetes, zero-trust networks, VPNs and enterprise Wi-Fi, IoT devices and B2B or banking APIs.
</QA>

<DeepDive title="All key terms">

<Terms>
  <Term name="PKI">System of CAs, certificates and policies that binds keys to identities.</Term>
  <Term name="X.509 certificate">Standard certificate format: subject, public key, validity, extensions, CA signature.</Term>
  <Term name="Root CA">Self-signed trust anchor in a trust store.</Term>
  <Term name="Intermediate CA">CA certified by a root that issues leaf certificates.</Term>
  <Term name="Leaf certificate">End-entity certificate of a server, user or device.</Term>
  <Term name="CSR">Certificate Signing Request containing a public key and requested identity.</Term>
  <Term name="SAN">Subject Alternative Name: identities a certificate is valid for.</Term>
  <Term name="Trust store">Set of root certificates a client trusts.</Term>
  <Term name="Revocation (CRL / OCSP)">Mechanisms to invalidate certificates before expiry.</Term>
  <Term name="Certificate Transparency">Public logs of all publicly issued certificates.</Term>
  <Term name="ACME">Protocol for automatic certificate issuance and renewal.</Term>
  <Term name="mTLS">TLS where both client and server authenticate with certificates.</Term>
</Terms>

</DeepDive>

<DeepDive title="More practice">

1. Inspect a real certificate: `openssl s_client -connect github.com:443 -servername github.com -showcerts`, and identify the leaf, intermediate, SANs and expiry.
2. Search a famous domain on crt.sh and list the subdomains you discover.
3. Rebuild the lab PKI, add a client certificate with `extendedKeyUsage=clientAuth`, and run `s_server -Verify 1 -CAfile root.crt` to require mTLS.
4. Use `mkcert` to create a local CA and HTTPS certificate for a development site.
5. Write a cron job or GitHub Action that runs `openssl x509 -checkend` on your site's certificate and fails if it expires within 21 days.
6. Look up which CAs your domain allows (CAA record) and add one if it's missing.
