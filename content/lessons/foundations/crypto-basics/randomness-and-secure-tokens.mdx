<BigIdea>
<Tr>
<En>
Almost every security mechanism relies on values an attacker **can't guess**: encryption keys, nonces, salts, session IDs, reset links, API keys, CSRF tokens, OTP secrets. They must come from a **cryptographically secure random number generator (CSPRNG)**: `secrets` / `os.urandom` in Python, `crypto.randomBytes` in Node, `crypto.getRandomValues` in the browser, `openssl rand` in the shell. **Never** use `random`, `Math.random()`, timestamps or counters for secrets. Aim for **128+ bits of entropy** (`secrets.token_urlsafe(32)` gives 256). Treat tokens like passwords: **store only their hash**, give them an **expiry**, make sensitive ones **single-use**.
</En>
<Ur>
Taqreeban har security tareeqa aisi values par chalta hai jinhen hamla awar **andaze se na paa sake**: encryption keys, nonces, salts, session IDs, reset links, API keys, CSRF tokens, OTP secrets. Ye **cryptographically secure random number generator (CSPRNG)** se aani chahiyen: Python me `secrets` / `os.urandom`, Node me `crypto.randomBytes`, browser me `crypto.getRandomValues`, shell me `openssl rand`. Raazon ke liye `random`, `Math.random()`, timestamps ya counters **kabhi** nahi. **128+ bits entropy** ka hadaf rakhein (`secrets.token_urlsafe(32)` 256 deta hai). Tokens ko passwords ki tarah samjhen: **sirf un ka hash rakhein**, **muddat** dein, hassas tokens **ek dafa ke** banayen.
</Ur>

<Why>
<Tr>
<En>

- **Predictable tokens = account takeover.** Predict a reset token and you can reset anyone's password without touching their email.
- **Weak randomness has broken real systems:** the Debian OpenSSL bug (2006–2008) left only 32,768 possible keys per type for two years; predictable random numbers have drained crypto wallets and let attackers forge sessions.
- **Everything depends on it:** salts, AES keys and nonces, TLS handshakes and certificate serial numbers.
- **Common audit finding:** `Math.random()` tokens, sequential or time-based IDs, short OTPs without rate limits, tokens stored in plaintext.

## Picture it

<Tr>
<En>

Imagine a hotel whose room keys use **room number + today's date** as the code. It looks random to guests, but anyone who spots the pattern opens every room. A secure hotel uses codes from a **perfectly shuffled deck** nobody can predict, not even someone who saw yesterday's codes. A normal random function (`random`, `Math.random`) is a deck shuffled with a known trick: fine for games, but if you know the trick you can predict the next card. A **CSPRNG** is the perfectly shuffled deck.

</En>
<Ur>

Ek hotel sochein jis ki room keys ka code **kamre ka number + aaj ki tareekh** hai. Mehmanon ko random lagta hai, lekin jo naqsha pakar le wo har kamra khol leta hai. Mehfooz hotel **bilkul achhi tarah phente patton** se code leta hai jin ka andaza koi nahi laga sakta, kal ke codes dekhne wala bhi nahi. Aam random function (`random`, `Math.random`) maloom chaal se phente patte hain: khelon ke liye theek, lekin chaal jaan lo to agla patta bata do. **CSPRNG** bilkul achhi tarah phente patte hain.

## Learn it step by step

<Walkthrough>

<Step title="Pseudo-random is predictable">

<Tr>
<En>

A **PRNG** produces a sequence from a **seed** with a fixed formula: same seed, exactly the same sequence. Useful for reproducible simulations and tests, fatal for secrets: whoever knows or guesses the seed knows every "random" value. Python's `random` (Mersenne Twister: after 624 outputs the whole future sequence can be computed), `Math.random()`, C `rand()`, PHP `rand()`/`mt_rand()` and Java `java.util.Random` are all PRNGs. Python's own docs warn they "should not be used for security purposes".

</En>
<Ur>

**PRNG** muqarrar formula se **seed** se silsila banata hai: wahi seed, bilkul wahi silsila. Dohraye ja sakne wale simulations aur tests ke liye mufeed, raazon ke liye jaan-leva: jo seed jaane ya andaze se paaye wo har "random" value jaanta hai. Python ka `random` (Mersenne Twister: 624 outputs ke baad poora aainda silsila nikala ja sakta hai), `Math.random()`, C `rand()`, PHP `rand()`/`mt_rand()` aur Java `java.util.Random` sab PRNGs hain. Python ke apne docs khabardar karte hain ke ye "security purposes ke liye istemal na hon".

</Ur>
</Tr>

```bash
python3 - <<'PY'
import random
random.seed(42)
first = [random.randint(0, 9) for _ in range(6)]
random.seed(42)
second = [random.randint(0, 9) for _ in range(6)]
print("run 1:", first)
print("run 2:", second)
print("identical:", first == second)
PY
```

```text output
run 1: [1, 0, 4, 3, 3, 2]
run 2: [1, 0, 4, 3, 3, 2]
identical: True
```

<Happened>
<Tr>
<En>`random.seed(42)` set the starting point and six "random" digits followed. Seeding again with 42 produced the **same** six digits; anyone running this on any computer gets `[1, 0, 4, 3, 3, 2]`. That determinism is the whole problem when "random" values protect accounts.</En>
<Ur>`random.seed(42)` ne shuruati nuqta rakha aur chhe "random" hindse aaye. Dobara 42 se seed karne par **wahi** chhe hindse aaye; kisi bhi computer par chalane wala `[1, 0, 4, 3, 3, 2]` paata hai. Jab "random" values accounts bachati hon to yahi muqarrar pan poora masla hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Guessing a token made from the clock">

<Tr>
<En>

A classic bug: seed a PRNG with the current time (or a user ID, or a counter) and use the output as a token. The attacker knows **roughly when** it was created (they just clicked "Forgot password"), so they try every seed in that window: thousands of guesses, not billions. Seen in real reset tokens, coupon codes, invitation links and "random" filenames: `random.seed(time.time())`, `new Random(System.currentTimeMillis())`, `md5(time())`.

</En>
<Ur>

Ek purana bug: PRNG ko maujooda waqt (ya user ID, ya counter) se seed karo aur output token bana do. Hamla awar ko **taqreeban** maloom hai kab bana (us ne abhi "Forgot password" dabaya), isliye wo us waqfe ka har seed aazmata hai: hazaron andaze, arbon nahi. Asli reset tokens, coupon codes, invitation links aur "random" file names me dekha gaya: `random.seed(time.time())`, `new Random(System.currentTimeMillis())`, `md5(time())`.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import random
issued_at = 1_794_300_123                       # the server's clock when the victim requested a reset
random.seed(issued_at)
token = "%06d" % random.randint(0, 999_999)
print("victim's reset code:", token)

window_start = issued_at - 3600                 # attacker: "it was requested within the last hour"
for guess in range(window_start, issued_at + 1):
    random.seed(guess)
    if "%06d" % random.randint(0, 999_999) == token:
        print(f"attacker found it after {guess - window_start + 1} tries (seed {guess})")
        break
PY
```

```text output
victim's reset code: 237904
attacker found it after 3601 tries (seed 1794300123)
```

<Happened>
<Tr>
<En>The server seeded with the Unix time and made a 6-digit code. The attacker never saw it, but knew it was requested in the last hour, so the seed was one of 3,601 values. Re-creating the generator for each second, they regenerated the exact code locally, with no requests to the server. A 6-digit code "looks" like a million possibilities, but the real search space was 3,601.</En>
<Ur>Server ne Unix waqt se seed kar ke 6-digit code banaya. Hamla awar ne use kabhi nahi dekha, lekin jaanta tha ke pichhle ghante me maanga gaya, isliye seed 3,601 values me se ek tha. Har second ke liye generator dobara bana kar us ne bilkul wahi code apne paas bana liya, server ko koi request bheje baghair. 6-digit code dekhne me das laakh imkanat lagta hai, lekin asal talash sirf 3,601 thi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Cryptographically secure randomness">

<Tr>
<En>

A **CSPRNG** is seeded by the operating system from unpredictable hardware events and designed so outputs can't be predicted, even after seeing earlier ones. It's the only acceptable source for keys, tokens, salts, nonces and session IDs: Python `secrets`/`os.urandom`, Node `crypto.randomBytes`/`randomInt`/`randomUUID`, browser `crypto.getRandomValues`, Java `SecureRandom`, Go `crypto/rand`, PHP `random_bytes`/`random_int`, shell `openssl rand` or `/dev/urandom`. Don't seed it yourself or "add your own randomness": the OS does it correctly.

</En>
<Ur>

**CSPRNG** ko operating system na-maloom hardware waqiaat se seed karta hai aur ye aise bana hai ke pichhle outputs dekh kar bhi agla andaze me na aaye. Keys, tokens, salts, nonces aur session IDs ka yahi wahid qabil-e-qubool zariya hai: Python `secrets`/`os.urandom`, Node `crypto.randomBytes`/`randomInt`/`randomUUID`, browser `crypto.getRandomValues`, Java `SecureRandom`, Go `crypto/rand`, PHP `random_bytes`/`random_int`, shell `openssl rand` ya `/dev/urandom`. Ise khud seed na karein na "apni randomness milayen": OS ye sahi karta hai.

</Ur>
</Tr>

```bash
python3 -c 'import secrets; t = secrets.token_urlsafe(32); print("python  :", len(t), "chars, URL-safe")'
node -e 'const t = require("crypto").randomBytes(32).toString("base64url"); console.log("node    :", t.length, "chars, URL-safe")'
echo "openssl : $(openssl rand -hex 32 | wc -c | awk '{print $1 - 1}') hex chars"
echo "urandom : $(head -c 32 /dev/urandom | base64 | tr -d '\n=' | wc -c) Base64 chars"
python3 -c 'import secrets; print("two tokens equal?", secrets.token_hex(16) == secrets.token_hex(16))'
```

```text output
python  : 43 chars, URL-safe
node    : 43 chars, URL-safe
openssl : 64 hex chars
urandom : 43 Base64 chars
two tokens equal? False
```

<Happened>
<Tr>
<En>`secrets.token_urlsafe(32)` took **32 random bytes** (256 bits) and Base64url-encoded them: 43 URL-safe characters; Node did the same. `openssl rand -hex 32` printed 64 hex characters (`wc -c` counts the newline, so we subtracted 1), and 32 bytes from `/dev/urandom` gave the same size. Two independent tokens were never equal. We print sizes, not values, because the values differ every run, which is the point.</En>
<Ur>`secrets.token_urlsafe(32)` ne **32 random bytes** (256 bits) le kar Base64url me badle: 43 URL-safe characters; Node ne bhi yahi kiya. `openssl rand -hex 32` ne 64 hex characters chhape (`wc -c` newline bhi ginta hai, isliye 1 ghataya), aur `/dev/urandom` ke 32 bytes ne wahi size diya. Do alag tokens kabhi barabar nahi hue. Values ki jagah size chhape kyun ke values har dafa badalti hain, aur yahi to maqsad hai.</Ur>
</Tr>
</Happened>

<Step title="Entropy: how strong is a secret?">

<Tr>
<En>

**Entropy** measures unpredictability in **bits**: N bits means 2^N equally likely possibilities, and each extra bit doubles the attacker's work. For a random string, entropy = length × log2(alphabet size). 128 bits is the standard minimum for tokens and keys. Short codes (PINs, OTPs) are only acceptable because the server **limits attempts** and they **expire quickly**. Entropy only applies to **randomly chosen** values: a human-chosen 12-character password has far less real entropy than 12 random characters.

</En>
<Ur>

**Entropy** be-yaqeeni ko **bits** me naapti hai: N bits ka matlab 2^N barabar mumkina imkanat, aur har izafi bit hamla awar ka kaam dugna karta hai. Random string ke liye entropy = lambai × log2(alphabet ka size). Tokens aur keys ke liye 128 bits standard kam se kam hadd hai. Chhote codes (PINs, OTPs) sirf isliye theek hain ke server **koshishen mehdood** karta hai aur wo **jaldi expire** hote hain. Entropy sirf **random chuni** values par lagu hai: insaan ka chuna 12-character password 12 random characters se kahin kam asli entropy rakhta hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import math
secrets_list = [
    ("4-digit PIN", 10, 4),
    ("6-digit OTP", 10, 6),
    ("8 random lowercase letters", 26, 8),
    ("12 random chars a-z A-Z 0-9", 62, 12),
    ("UUIDv4 (random part)", 2, 122),
    ("token_urlsafe(32): 32 bytes", 2, 256),
]
for name, alphabet, length in secrets_list:
    bits = length * math.log2(alphabet)
    print(f"{name:30} {bits:6.1f} bits  ({alphabet}^{length} = 2^{bits:.0f} possibilities)")
PY
```

```text output
4-digit PIN                      13.3 bits  (10^4 = 2^13 possibilities)
6-digit OTP                      19.9 bits  (10^6 = 2^20 possibilities)
8 random lowercase letters       37.6 bits  (26^8 = 2^38 possibilities)
12 random chars a-z A-Z 0-9      71.5 bits  (62^12 = 2^71 possibilities)
UUIDv4 (random part)            122.0 bits  (2^122 = 2^122 possibilities)
token_urlsafe(32): 32 bytes     256.0 bits  (2^256 = 2^256 possibilities)
```

<Happened>
<Tr>
<En>`math.log2(alphabet)` is bits per character: 3.32 for digits, 4.7 for lowercase, 5.95 for 62 characters. A 6-digit OTP has only about 20 bits: at most a million guesses with unlimited tries, hence strict rate limits and short lifetimes. 12 random alphanumerics give about 71 bits: strong for a password, short of 128 for tokens. UUIDv4 has 122 random bits; `token_urlsafe(32)` has 256, far beyond brute force.</En>
<Ur>`math.log2(alphabet)` fi character bits hai: hindson ke 3.32, chhote huroof ke 4.7, 62 characters ke 5.95. 6-digit OTP me sirf taqreeban 20 bits hain: be-hadd koshishon me zyada se zyada das laakh andaze, isi liye sakht rate limits aur chhoti umar. 12 random alphanumerics taqreeban 71 bits dete hain: password ke liye mazboot, tokens ke 128 se kam. UUIDv4 me 122 random bits; `token_urlsafe(32)` me 256, brute force se kahin bahar.</Ur>
</Tr>
</Happened>

</Step>

<Step title="UUIDs: not all of them are random">

<Tr>
<En>

UUIDs are 128-bit IDs written as `8-4-4-4-12` hex digits. The **version** digit (first digit of the third group) says how they were made: **v1** = timestamp + the machine's MAC address, **v4** = random, **v7** = timestamp + random (sortable, good database keys). A v1 UUID reveals **when** and on **which machine** it was made, and neighbours are predictable. UUIDv4 from a CSPRNG (122 random bits) is fine as an unguessable ID, but for secrets like reset tokens prefer a dedicated 256-bit token.

</En>
<Ur>

UUIDs 128-bit IDs hain jo `8-4-4-4-12` hex hindson me likhi jati hain. **Version** hindsa (teesre group ka pehla hindsa) batata hai kaise bani: **v1** = timestamp + machine ka MAC address, **v4** = random, **v7** = timestamp + random (tarteeb dene ke qabil, achhi database keys). v1 UUID **kab** aur **kis machine** par bani ye bata deti hai, aur pados wali andaze me aati hain. CSPRNG se UUIDv4 (122 random bits) andaze se na milne wali ID ke taur par theek hai, lekin reset tokens jaise raazon ke liye alag 256-bit token behtar hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import uuid, datetime
v1 = uuid.UUID("c232ab00-9414-11ec-b3c8-9f6bdeced846")
created = datetime.datetime.fromtimestamp((v1.time - 0x01b21dd213814000) / 1e7, datetime.timezone.utc)
print("version  :", v1.version)
print("created  :", created.isoformat(timespec="seconds"))
print("node/MAC :", format(v1.node, "012x"))
print("uuid4 version:", uuid.uuid4().version, "(random)")
PY
```

```text output
version  : 1
created  : 2022-02-22T19:22:22+00:00
node/MAC : 9f6bdeced846
uuid4 version: 4 (random)
```

<Happened>
<Tr>
<En>`uuid.UUID("...")` parsed an existing v1 UUID (the `1` in `11ec` marks version 1). Its `time` field counts 100-nanosecond intervals since 15 October 1582; subtracting `0x01b21dd213814000` converts it to Unix time: 19:22:22 UTC on 22 February 2022. `node` is the 48-bit node ID, normally the network card's MAC, identifying the machine. `uuid.uuid4()` has no time or machine information.</En>
<Ur>`uuid.UUID("...")` ne maujooda v1 UUID parhi (`11ec` me `1` version 1 ki nishani). Us ka `time` field 15 October 1582 se 100-nanosecond waqfe ginta hai; `0x01b21dd213814000` ghatane se Unix waqt banta hai: 22 February 2022, 19:22:22 UTC. `node` 48-bit node ID hai, aam taur par network card ka MAC, jo machine pehchanta hai. `uuid.uuid4()` me na waqt na machine ki maloomat.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Random numbers in a range: avoid modulo bias">

<Tr>
<En>

A random byte has 256 values. Turning it into 0–99 with `byte % 100` makes some results more likely, because 256 isn't a multiple of 100. Biased codes, PINs or shuffles are easier to guess, and the same bug appears in home-made "random password" generators. Use range functions that do **rejection sampling** (draw again when the value falls in the uneven leftover): Python `secrets.randbelow(n)` and `secrets.choice(seq)`, Node `crypto.randomInt(min, max)`, Java `SecureRandom.nextInt(n)`, PHP `random_int(min, max)`.

</En>
<Ur>

Random byte ki 256 values hain. `byte % 100` se 0–99 banane par kuch natije zyada aate hain, kyun ke 256, 100 ka mukammal guna nahi. Jhuke hue codes, PINs ya shuffles ka andaza aasaan hota hai, aur yahi bug ghar ke bane "random password" generators me aata hai. **Rejection sampling** karne wale range functions istemal karein (jab value na-barabar bache hisse me gire to dobara nikalo): Python `secrets.randbelow(n)` aur `secrets.choice(seq)`, Node `crypto.randomInt(min, max)`, Java `SecureRandom.nextInt(n)`, PHP `random_int(min, max)`.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from collections import Counter
import secrets, string
counts = Counter(byte % 100 for byte in range(256))       # every possible byte, once each
print("byte % 100 -> value 0 appears", counts[0], "times, value 55:", counts[55], "| value 56:", counts[56], ", value 99:", counts[99])
code = f"{secrets.randbelow(1_000_000):06d}"
alphabet = string.ascii_letters + string.digits
password = "".join(secrets.choice(alphabet) for _ in range(16))
print("unbiased 6-digit code length:", len(code), "| 16-char random password length:", len(password))
PY
```

```text output
byte % 100 -> value 0 appears 3 times, value 55: 3 | value 56: 2 , value 99: 2
```

<Step title="Store tokens hashed; expire them; use them once">

<Tr>
<En>

Tokens are passwords for machines. If your database stores reset tokens, session tokens or API keys in plaintext, anyone who reads it (SQL injection, a backup, an insider) can use them at once. Store only a **hash**. Because tokens have 128+ bits, a **fast hash** (SHA-256) is enough; slow password hashing isn't needed. Look tokens up **by their hash**, which also avoids timing leaks. Show the token **once** and never again.

Then limit damage if one leaks (email forwarding, browser history, Referer headers, logs, screenshots): **short expiry** (reset links 15–60 minutes), **single use**, **binding** to one user and purpose, and **revocation** when the password changes. Keep tokens out of URLs where possible, never log them, set `Referrer-Policy: no-referrer` on pages that contain them, and store `expires_at`, `used_at` and the purpose next to the hash. The challenge below does exactly this.

</En>
<Ur>

Tokens machines ke passwords hain. Agar database reset tokens, session tokens ya API keys plaintext me rakhe to use parhne wala (SQL injection, backup, andar ka shakhs) fauran istemal kar sakta hai. Sirf **hash** rakhein. Tokens me 128+ bits hote hain, isliye **tez hash** (SHA-256) kaafi hai; sust password hashing ki zaroorat nahi. Tokens **un ke hash se** dhoondhein, jis se timing leaks se bhi bachat hoti hai. Token **ek dafa** dikhayen, phir kabhi nahi.

Phir leak hone par nuqsan mehdood karein (email forwarding, browser history, Referer headers, logs, screenshots): **chhoti muddat** (reset links 15–60 minute), **ek dafa istemal**, ek user aur maqsad se **jora hua**, aur password badalne par **mansookh**. Jahan mumkin ho tokens URLs se bahar rakhein, kabhi log na karein, un wale pages par `Referrer-Policy: no-referrer` lagayen, aur hash ke saath `expires_at`, `used_at` aur maqsad rakhein. Neeche ka challenge bilkul yahi karta hai.

</Ur>
</Tr>

</Step>

<Step title="Designing API keys">

<Tr>
<En>

A good API key is random (128+ bits), **recognisable** (a prefix like `dg_live_`), **checkable offline** (a checksum catches typos and helps scanners spot real keys), shown once and stored hashed. Prefixes let secret scanners (GitHub push protection, gitleaks) detect leaked keys; `live`/`test` prefixes stop environment mix-ups. Real examples: GitHub (`ghp_`, `github_pat_` with a checksum), Stripe (`sk_live_`, `sk_test_`), Slack (`xoxb-`). The checksum is for **typo detection**, not security: the randomness provides the security.

</En>
<Ur>

Achhi API key random (128+ bits), **pehchanne ke qabil** (`dg_live_` jaisa prefix), **offline check hone wali** (checksum typos pakarta hai aur scanners ko asli keys pehchanne me madad deta hai), ek dafa dikhayi gayi aur hash kar ke rakhi hoti hai. Prefixes secret scanners (GitHub push protection, gitleaks) ko leak hui keys pakarne dete hain; `live`/`test` prefixes environments ki gadbad rokte hain. Asli misaalen: GitHub (`ghp_`, checksum wala `github_pat_`), Stripe (`sk_live_`, `sk_test_`), Slack (`xoxb-`). Checksum **typo pakarne** ke liye hai, hifazat ke liye nahi: hifazat randomness deti hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import base64, hashlib, secrets, zlib

def new_api_key(env="live"):
    raw = base64.b32encode(secrets.token_bytes(24)).decode().rstrip("=").lower()   # 192 random bits
    checksum = format(zlib.crc32(raw.encode()), "08x")
    return f"dg_{env}_{raw}_{checksum}"

def looks_valid(key):
    parts = key.split("_")
    if len(parts) != 4 or parts[0] != "dg":
        return False
    return format(zlib.crc32(parts[2].encode()), "08x") == parts[3]

key = new_api_key()
typo = key[:-1] + ("0" if key[-1] != "0" else "1")
print("prefix:", key[:8], "| length:", len(key))
print("checksum ok:", looks_valid(key), "| with a typo:", looks_valid(typo))
print("stored in DB: sha256 hash,", len(hashlib.sha256(key.encode()).hexdigest()), "hex chars (the key itself is shown once)")
PY
```

<Step title="How authenticator codes (TOTP) work">

<Tr>
<En>

**TOTP** (RFC 6238), used by Google and Microsoft Authenticator: the server and your phone share a random **secret** (the setup QR code). Every 30 seconds both compute `HMAC-SHA1(secret, current_time / 30)` and shorten it to 6 digits, so a stolen password alone isn't enough to log in. The secret must come from a CSPRNG (typically 160 bits) and be stored encrypted, and the verify endpoint must be rate-limited (6 digits ≈ 20 bits). TOTP can be phished in real time; passkeys/WebAuthn can't. Below, a minimal TOTP checked against RFC 6238's official test vectors.

</En>
<Ur>

**TOTP** (RFC 6238), Google aur Microsoft Authenticator ise istemal karte hain: server aur aap ka phone ek random **raaz** baantte hain (setup ka QR code). Har 30 second dono `HMAC-SHA1(secret, current_time / 30)` nikal kar 6 hindson tak chhota karte hain, isliye sirf chori hua password login ke liye kaafi nahi. Raaz CSPRNG se aaye (aam taur par 160 bits) aur encrypted rakha jaye, aur verify endpoint rate-limited ho (6 hindse ≈ 20 bits). TOTP ko real time me phish kiya ja sakta hai; passkeys/WebAuthn ko nahi. Neeche chhota sa TOTP hai jo RFC 6238 ke sarkari test vectors se check hua.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import hashlib, hmac, struct

def totp(secret: bytes, unix_time: int, digits: int = 6, step: int = 30) -> str:
    counter = struct.pack(">Q", unix_time // step)              # 8-byte big-endian time counter
    mac = hmac.new(secret, counter, hashlib.sha1).digest()      # 20-byte HMAC-SHA1
    offset = mac[-1] & 0x0F                                      # "dynamic truncation"
    number = struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF
    return str(number % 10 ** digits).zfill(digits)

secret = b"12345678901234567890"                                 # RFC 6238 test secret
print("t=59         :", totp(secret, 59, digits=8), "(RFC expects 94287082)")
print("t=1111111109 :", totp(secret, 1111111109, digits=8), "(RFC expects 07081804)")
print("6-digit app code at t=59:", totp(secret, 59))
print("same code for the whole 30 s window:", totp(secret, 30) == totp(secret, 59), "| next window differs:", totp(secret, 59) != totp(secret, 60))
PY
```

```text output
t=59         : 94287082 (RFC expects 94287082)
t=1111111109 : 07081804 (RFC expects 07081804)
6-digit app code at t=59: 287082
same code for the whole 30 s window: True | next window differs: True
```

<Happened>
<Tr>
<En>`unix_time // step` turned time into a counter that grows every 30 seconds, packed as 8 bytes. `HMAC-SHA1(secret, counter)` gave 20 bytes; the last 4 bits picked an offset ("dynamic truncation") and 4 bytes from there became a 31-bit number; `% 10 ** digits` kept the last 6 or 8 digits. Both RFC vectors matched, so this is the algorithm your authenticator app runs. Times 30–59 share a code and 60 starts a new one; servers usually also accept the previous window for clock drift and must reject reused codes.</En>
<Ur>`unix_time // step` ne waqt ko counter banaya jo har 30 second barhta hai, 8 bytes me band. `HMAC-SHA1(secret, counter)` ne 20 bytes diye; aakhri 4 bits ne offset chuna ("dynamic truncation") aur wahan se 4 bytes 31-bit number bane; `% 10 ** digits` ne aakhri 6 ya 8 hindse rakhe. Dono RFC vectors mil gaye, yaani yahi algorithm aap ki authenticator app chalati hai. Waqt 30–59 ka ek code aur 60 se naya; servers aam taur par ghari ke farq ke liye pichhla waqfa bhi maante hain aur dohraye codes radd karna lazmi hai.</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Guessable, stored raw, forever valid">

```text
token = md5(email + str(time.time()))      # computable by anyone
db.save(user, token)                       # plaintext, no expiry
if request.token == db.token: reset()      # reusable forever
```

</Bad>
<Good title="CSPRNG, hashed, short-lived, single use">

```text
token = secrets.token_urlsafe(32)          # 256 bits

# redeem: look up sha256(token), check unused + unexpired, mark used
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`Math.random()`, `random`, `rand()` or `mt_rand()`** for tokens, passwords, salts or secret IDs.
- **Seeding with the time, user ID or a counter.**
- **Sequential IDs** in URLs for private resources (`/invoices/1043`), enabling IDOR when authorisation checks are missing.
- **UUIDv1 as a secret**, or assuming every UUID is random.
- **Tokens too short** (8 hex characters = 32 bits), or 6-digit codes without rate limits.
- **Modulo bias** in home-made code and password generators.
- **Logging tokens**, or tokens that never expire and survive a password change.
- **Comparing secrets with `==`** in a way that leaks timing, instead of looking up by hash or constant-time comparison.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Tokens, passwords, salts ya khufia IDs ke liye **`Math.random()`, `random`, `rand()` ya `mt_rand()`**.
- **Waqt, user ID ya counter se seed karna.**
- Private cheezon ke URLs me **silsilewar IDs** (`/invoices/1043`), jo authorisation check na hone par IDOR khol deti hain.
- **UUIDv1 ko raaz banana**, ya har UUID ko random samajhna.
- **Bohot chhote tokens** (8 hex characters = 32 bits), ya bina rate limit 6-digit codes.
- Ghar ke bane code aur password generators me **modulo bias**.
- **Tokens log karna**, ya aise tokens jo kabhi expire na hon aur password badalne ke baad bhi chalen.
- Hash se dhoondhne ya constant-time muqable ke bajaye timing leak karne wale **`==` se raaz milana**.

</Ur>
</Tr>

<Challenge title="A secure password-reset token system">

<Tr>
<En>
Build reset tokens the right way: 256-bit tokens from a CSPRNG, only hashes stored, 15-minute expiry, single use and generic errors. A fixed clock makes the results reproducible.
</En>
<Ur>
Reset tokens sahi tareeqe se banayen: CSPRNG se 256-bit tokens, sirf hashes mehfooz, 15 minute ki muddat, ek dafa istemal aur aam errors. Muqarrar ghari natije qaim rakhti hai.

```bash
python3 - <<'PY'
import hashlib, secrets

NOW = 1_794_300_000                  # fixed "current time" for the demo
tokens = {}                          # stands for a database table: token_hash -> record

def create_reset_token(user, now):
    token = secrets.token_urlsafe(32)                                   # 256-bit, URL-safe
    tokens[hashlib.sha256(token.encode()).hexdigest()] = {"user": user, "expires": now + 15 * 60, "used": False}
    return token                     # goes only into the email link, never stored

def redeem(token, now):
    record = tokens.get(hashlib.sha256(token.encode()).hexdigest())
    if record is None:
        return "invalid link"
    if record["used"]:
        return "link already used"
    if now > record["expires"]:
        return "link expired"
    record["used"] = True
    return f"ok: let {record['user']} set a new password"

link_token = create_reset_token("olivia", NOW)
print("1.", redeem(link_token, NOW + 60))          # clicked after 1 minute
print("2.", redeem(link_token, NOW + 120))         # same link clicked again
other = create_reset_token("jack", NOW)
print("3.", redeem(other, NOW + 30 * 60))           # clicked after 30 minutes
guess = link_token[:-1] + ("A" if link_token[-1] != "A" else "B")
print("4.", redeem(guess, NOW + 30))                # attacker changes one character
print("5. raw token stored anywhere in the table?", any(link_token in key for key in tokens))
PY
```

```text output
1. ok: let olivia set a new password
2. link already used
3. link expired
4. invalid link
5. raw token stored anywhere in the table? False
```

A real system also invalidates other tokens and sessions after the password change, rate-limits requests, and always says "if the account exists, we've sent an email".</En>
<Ur>`create_reset_token` sirf token ka **SHA-256** user, 15 minute baad ki muddat aur `used` flag ke saath rakhta hai, aur email ke liye kaccha token lautata hai. `redeem` aane wali cheez hash kar ke dhoondhta hai. 1: taaza link chalta hai aur used ho jata hai. 2: do dafa nahi chalta. 3: Jack ka link 15 minute se purana. 4: ek character badalne se bilkul alag hash. 5: table me sirf hashes. <DeepDive title="Real world: guessable reset codes">

A bug bounty hunter testing a food-delivery app noticed that password-reset codes were 6 digits and the verify endpoint allowed unlimited attempts. With about 20 bits of entropy and no rate limit, a script could try all one million codes in under an hour per account. Another report on a different platform found reset tokens built as `md5(email + timestamp)`, computable by anyone who knew the victim's email and roughly when the reset was requested. Both companies fixed it the same way: CSPRNG tokens with at least 128 bits (`secrets.token_urlsafe(32)`), stored as SHA-256 hashes, single-use, expiring after 15 minutes, all sessions revoked on password change, and strict rate limits with lockouts and alerts on every code-verification endpoint. The OTP stayed 6 digits for usability, but with at most 5 attempts per code and a 10-minute lifetime, guessing became impractical.

</DeepDive>

<DeepDive title="Security lens">

If a value protects something, it must be unpredictable, long enough, short-lived, single-purpose and stored hashed. Anything less turns tokens into guessable passwords.

- **Use only CSPRNG APIs** and lint for insecure ones (Bandit flags `random` in security contexts; ESLint and Semgrep rules flag `Math.random` used for tokens).
- **128-bit minimum** for tokens and keys; 256 bits costs nothing extra.
- **Rate-limit** every endpoint that checks a short code (OTP, PIN, SMS), with lockouts and monitoring.
- **Rotate and revoke:** API keys need rotation without downtime (allow two active keys), and every token type needs a revocation path.
- **Leak detection:** prefixed keys can be found by secret scanners; join GitHub's secret-scanning partner programme if you issue API keys publicly.
- **Randomness failures are silent:** VMs cloned from one snapshot, embedded devices at first boot and containers can start with low entropy; modern kernels and `getrandom()` handle this, so avoid custom randomness code.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why shouldn't Math.random or Python's random module be used for security tokens?">
They are pseudo-random generators designed for speed and statistical quality, not unpredictability. Their output is determined by an internal state and seed, so outputs can be reproduced if the seed is guessed, and for algorithms like the Mersenne Twister the internal state can be recovered from a few hundred outputs, allowing future values to be predicted. Security values must come from a cryptographically secure generator such as the secrets module or crypto.randomBytes.
</QA>

<QA q="How long should a session or reset token be?">
It should come from a CSPRNG and have at least 128 bits of entropy, commonly 256 bits, for example 32 random bytes encoded as URL-safe Base64. Short codes such as 6-digit OTPs are acceptable only with strict rate limiting, short expiry and single use.
</QA>

<QA q="How should password reset tokens be stored and validated?">
Generate a random token of at least 128 bits, send it only in the reset link, and store just its hash together with the user, purpose, expiry time and a used flag. On redemption, hash the presented token, look it up, check it is unused and unexpired, mark it used, and after the password change invalidate other tokens and sessions. Responses should not reveal whether an email address is registered.
</QA>

<QA q="Are UUIDs safe to use as secret tokens?">
Only random UUIDs, version 4 from a cryptographically secure generator, are unpredictable, with 122 random bits. Version 1 UUIDs contain a timestamp and the machine's MAC address and are predictable, and time-based versions like v7 have fewer random bits. For security-sensitive tokens, a dedicated random token of 256 bits is preferable.
</QA>

<QA q="How does TOTP work?">
The server and the authenticator app share a random secret. Both compute an HMAC of the secret with a counter derived from the current time divided into 30-second steps, dynamically truncate the result to a 31-bit number, and take the last six digits. Because both use the same secret and time, they produce the same code, which changes every 30 seconds. Servers must rate-limit attempts and reject reused codes.
</QA>

</DeepDive>
