<BigIdea>
<Tr>
<En>
A **command-line interface (CLI)** is how people, cron jobs and CI pipelines tell a script what to do: `backup /srv/data --dest s3://backups --keep 30 --dry-run`. Python's built-in **`argparse`** module turns the raw list of words in `sys.argv` into a tidy object. You describe what the tool accepts: **positional arguments** (required, identified by position, like `source`), **options** (named, usually optional, like `--dest` or the short `-t`), and **flags** (`--dry-run`, which are True or False). For each one you can set a **type** (`int`, or your own validation function), **choices**, a **default**, how many values it takes (`nargs`), and **help** text. argparse then generates `--help` for free, converts and validates the values, and when the user makes a mistake it prints a clear error with the usage line and exits with **code 2**. Bigger tools use **subcommands** (`logtool count`, `logtool grep`, like `git commit` and `git push`), each with its own arguments and handler function. Good CLIs also follow shell conventions: exit **0** on success and non-zero on failure, write data to stdout and messages or logs to stderr, accept `-` to mean stdin so they work in pipes, support `-v` for more detail, and keep the parsing in a `main(argv=None)` function that tests can call directly.
</En>
<Ur>
**Command-line interface (CLI)** woh tareeqa hai jis se log, cron jobs aur CI pipelines script ko batate hain ke kya karna hai: `backup /srv/data --dest s3://backups --keep 30 --dry-run`. Python ka built-in **`argparse`** module `sys.argv` ke khaam alfaaz ki list ko saaf object me badalta hai. Aap batate hain tool kya qubool karta hai: **positional arguments** (lazmi, jagah se pehchane jate, jaise `source`), **options** (naam wale, aam taur par ikhtiyari, jaise `--dest` ya chhota `-t`), aur **flags** (`--dry-run`, jo True ya False hote). Bare tools **subcommands** istemal karte (`logtool count`, `logtool grep`, jaise `git commit` aur `git push`), har ek apne arguments aur handler function ke saath. Achhe CLIs shell ke riwaj bhi follow karte: kamyabi par **0** aur nakami par non-zero exit, data stdout par aur paighamat ya logs stderr par, pipes me chalne ke liye `-` ko stdin samajhna, zyada tafseel ke liye `-v`, aur parsing ko aise `main(argv=None)` function me rakhna jise tests seedha bula sakein.

## Learn it step by step

<Walkthrough>

<Step title="Arguments, options, types, choices, help and errors">

<Tr>
<En>
`ping_report.py` accepts one or more hosts, a `--threshold` integer with a default, a `--format` limited to three choices, a `--fail-on-slow` flag and `--version`. Response times are faked so the output is predictable. We print the generated help, run it with defaults and with options (including JSON output), check the exit code with `--fail-on-slow`, and then make three typical mistakes. `COLUMNS=80` only fixes the width of the help text.
</En>
<Ur>
`ping_report.py` ek ya zyada hosts, default wala `--threshold` integer, teen choices tak mehdood `--format`, `--fail-on-slow` flag aur `--version` qubool karti hai. Response times farzi hain taa ke output pehle se maloom ho. Hum bani hui help print karte, defaults aur options (JSON output samait) ke saath chalate, `--fail-on-slow` ke saath exit code check karte, aur phir teen aam ghaltiyan karte hain. `COLUMNS=80` sirf help text ki chaurai tay karta hai.
</Ur>
</Tr>

```bash
export COLUMNS=80                     # fixed width so help text wraps the same everywhere
cat > ping_report.py <<'EOF'
import argparse, json, sys

def build_parser():
    p = argparse.ArgumentParser(
        prog="ping_report",
        description="Summarize response times for a list of hosts.",
        epilog="Example: ping_report web01 web02 --threshold 200 --format csv",
    )
    p.add_argument("hosts", nargs="+", help="one or more host names")
    p.add_argument("-t", "--threshold", type=int, default=500, metavar="MS",
                   help="flag hosts slower than this (default: %(default)s)")
    p.add_argument("-f", "--format", choices=["text", "csv", "json"], default="text")
    p.add_argument("--fail-on-slow", action="store_true", help="exit 1 if any host is slow")
    p.add_argument("--version", action="version", version="%(prog)s 1.4.0")
    return p

def main(argv=None):
    args = build_parser().parse_args(argv)
    fake_ms = {h: 100 + 90 * i for i, h in enumerate(args.hosts)}      # stand-in for real pings
    slow = [h for h, ms in fake_ms.items() if ms > args.threshold]
    if args.format == "json":
        print(json.dumps({"hosts": fake_ms, "slow": slow}))
    elif args.format == "csv":
        print("host,ms,slow")
        for h, ms in fake_ms.items():
            print(f"{h},{ms},{h in slow}")
    else:
        for h, ms in fake_ms.items():
            print(f"{h:<8} {ms:>4} ms {'SLOW' if h in slow else 'ok'}")
    return 1 if (args.fail_on_slow and slow) else 0

if __name__ == "__main__":
    sys.exit(main())
EOF
python3 ping_report.py --help
echo "--- normal run:"; python3 ping_report.py web01 web02 db01 web03
echo "--- options:"; python3 ping_report.py web01 web02 db01 -t 250 --format csv
python3 ping_report.py web01 web02 db01 -t 250 --fail-on-slow > /dev/null; echo "exit code with --fail-on-slow: $?"
python3 ping_report.py web01 db01 -f json
python3 ping_report.py --version
echo "--- mistakes are caught for you:"
python3 ping_report.py web01 --threshold fast 2>&1; echo "exit code: $?"
python3 ping_report.py web01 --format xml 2>&1 | tail -1
python3 ping_report.py 2>&1 | tail -1
```

<Tr>
<En>

- `--help` was **generated** from the parser: usage line, description, every argument with its help, the choices, the default (via `%(default)s`) and the epilog example. It stays correct as the code changes.
- `nargs="+"` collected all hosts into a **list**; `type=int` turned `"250"` into the integer 250; options can appear before or after positionals.
- With `--fail-on-slow`, db01 at 280 ms crossed the 250 ms threshold and the tool exited with **1**: the run worked, but the check failed. That lets `ping_report ... --fail-on-slow || alert` work in a shell or CI job.
- `-f json` produced machine-readable output, good for piping into `jq` or other tools.
- The three mistakes, a non-integer threshold, an unknown format and missing hosts, were caught **before any work happened**, each with a precise message and exit code **2**, and the usage line printed to stderr. You didn't write any of that validation.

</En>
<Ur>

- `--help` parser se **bani**: usage line, description, har argument apni help ke saath, choices, default (`%(default)s` ke zariye) aur epilog misaal. Code badalne par ye durust rehti hai.

- Teeno ghaltiyan, ghair integer threshold, na-maloom format aur ghayab hosts, **koi kaam hone se pehle** pakri gayin, har ek bilkul paigham aur exit code **2** ke saath, aur usage line stderr par print hui. Woh validation aap ne bilkul nahi likhi.

</Ur>

<Step title="Subcommands, verbosity, stdin, environment defaults and exclusive options">

<Tr>
<En>
`logtool.py` has two subcommands, `count` and `grep`, each with its own arguments and a handler attached with `set_defaults(func=...)`. A global `-v` counts how verbose to be, `--color` and `--no-color` are mutually exclusive, file arguments accept `-` for stdin, and `grep`'s `--limit` takes its default from the `LOGTOOL_LIMIT` environment variable. We count levels in a log, pipe filtered input in, grep with debug logging, search for something absent, and trigger two errors.
</En>
<Ur>
`logtool.py` me do subcommands hain, `count` aur `grep`, har ek ke apne arguments aur `set_defaults(func=...)` se jura handler. Global `-v` ginta hai ke kitni tafseel chahiye, `--color` aur `--no-color` ek doosre ke khilaf hain, file arguments stdin ke liye `-` qubool karte, aur `grep` ka `--limit` apna default `LOGTOOL_LIMIT` environment variable se leta hai. Hum log me levels ginte, chhana hua input pipe karte, debug logging ke saath grep karte, ghayab cheez dhoondte, aur do errors paida karte hain.
</Ur>
</Tr>

```bash
export COLUMNS=80
cat > logtool.py <<'EOF'
import argparse, logging, os, sys
from collections import Counter

log = logging.getLogger("logtool")

def cmd_count(args):
    levels = Counter(line.split()[1] for line in args.file if line.strip())
    for level, n in sorted(levels.items()):
        print(f"{level:<6}{n}")
    return 0

def cmd_grep(args):
    hits = [line.rstrip("\n") for line in args.file if args.pattern in line]
    log.debug("searched for %r, %d hits", args.pattern, len(hits))
    for line in hits[: args.limit]:
        print(line)
    return 0 if hits else 1                      # like grep: 1 means "nothing found"

def build_parser():
    p = argparse.ArgumentParser(prog="logtool")
    p.add_argument("-v", "--verbose", action="count", default=0, help="-v info, -vv debug")
    group = p.add_mutually_exclusive_group()
    group.add_argument("--color", action="store_true")
    group.add_argument("--no-color", action="store_true")
    sub = p.add_subparsers(dest="command", required=True)

    c = sub.add_parser("count", help="count lines per level")
    c.add_argument("file", type=argparse.FileType("r", encoding="utf-8"), help="log file, or - for stdin")
    c.set_defaults(func=cmd_count)

    g = sub.add_parser("grep", help="show matching lines")
    g.add_argument("pattern")
    g.add_argument("file", type=argparse.FileType("r", encoding="utf-8"))
    g.add_argument("-n", "--limit", type=int, default=int(os.environ.get("LOGTOOL_LIMIT", 10)))
    g.set_defaults(func=cmd_grep)
    return p

def main(argv=None):
    args = build_parser().parse_args(argv)
    level = [logging.WARNING, logging.INFO, logging.DEBUG][min(args.verbose, 2)]
    logging.basicConfig(level=level, format="%(levelname)s %(message)s", stream=sys.stderr)
    return args.func(args)

if __name__ == "__main__":
    sys.exit(main())
EOF
printf '10:00 INFO start\n10:01 ERROR db timeout\n10:02 INFO retry\n10:03 ERROR db timeout\n10:04 WARN slow\n' > app.log
python3 logtool.py --help | head -3
python3 logtool.py count app.log
echo "--- from stdin, with a pipe:"; grep -v WARN app.log | python3 logtool.py count -
echo "--- grep with -vv and a limit from the environment:"
LOGTOOL_LIMIT=1 python3 logtool.py -vv grep timeout app.log 2>&1
python3 logtool.py grep "disk full" app.log; echo "exit code (no match): $?"
python3 logtool.py --color --no-color count app.log 2>&1 | tail -1
python3 logtool.py count missing.log 2>&1 | tail -1
```

<Happened>
<Tr>
<En>

- The usage line shows `{count,grep}`: `add_subparsers(required=True)` makes a subcommand mandatory, and each subparser has its own arguments and `--help`.
- `set_defaults(func=cmd_count)` stored the handler on `args`, so `main()` just calls `args.func(args)` without an if/elif chain.
- `count -` read from **stdin**, so the tool worked at the end of a pipe (`grep -v WARN app.log | ...`), and `FileType` opened the files for us.
- `-vv` set logging to DEBUG, so the debug line appeared on **stderr** while the result went to stdout. `LOGTOOL_LIMIT=1` changed the default limit without a flag; a command-line `-n` would still override it.
- No match returned exit code **1**, like Unix `grep`, so shell scripts can test for it.
- argparse rejected `--color --no-color` together, and `FileType` turned a missing file into a clean usage error instead of a traceback.

</En>
<Ur>

- Usage line `{count,grep}` dikhati hai: `add_subparsers(required=True)` subcommand lazmi banata, aur har subparser ke apne arguments aur `--help` hain.
- `set_defaults(func=cmd_count)` ne handler `args` par rakha, isliye `main()` if/elif ki zanjeer ke baghair bas `args.func(args)` bulata hai.
- `count -` ne **stdin** se parha, isliye tool pipe ke aakhir me chala (`grep -v WARN app.log | ...`), aur `FileType` ne hamare liye files kholin.
- `-vv` ne logging ko DEBUG kiya, isliye debug line **stderr** par aayi jabke natija stdout par gaya. `LOGTOOL_LIMIT=1` ne flag ke baghair default limit badli; command-line ka `-n` ab bhi use override karega.
- Koi mel na hone par exit code **1** aaya, Unix `grep` ki tarah, taa ke shell scripts ise check kar sakein.
- argparse ne `--color --no-color` ek saath radd kiye, aur `FileType` ne ghayab file ko traceback ke bajaye saaf usage error me badla.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Parsing sys.argv by hand">

```text
host = sys.argv[1]                       # IndexError if missing
threshold = int(sys.argv[2])             # crashes on "fast"; no --help
if "--dry" in sys.argv: dry = True       # order-dependent, no validation
```

</Bad>
<Good title="Declare it and let argparse validate">

```text
p = argparse.ArgumentParser()
p.add_argument("host")
p.add_argument("--threshold", type=int, default=500)
p.add_argument("--dry-run", action="store_true")
args = p.parse_args(argv)
```

</Good>
</Compare>

<Compare>
<Bad title="Secrets as arguments, errors as exit code 0">

```text
deploy --api-key acme_live_9f8e7d...      # visible in ps, shell history and CI logs
...
except Exception as e:
    print(e)                              # script "succeeds" with exit code 0
```

</Bad>

Write `main(argv)` for a `users` tool with two subcommands: `add NAME [--role viewer|admin]` and `remove NAME [--yes]`. Keep users in a set starting with `{"jane"}`. </Ur>

<Tr>
<En>

```text
import argparse

users = {"jane"}

def add(args):
    if args.name in users:
        print(f"{args.name} already exists")
        return 1
    users.add(args.name)
    print(f"added {args.name} with role {args.role}")
    return 0

def remove(args):
    if args.name not in users:
        print(f"no such user: {args.name}")
        return 1
    if not args.yes:
        print(f"refusing to remove {args.name} without --yes")
        return 2
    users.discard(args.name)
    print(f"removed {args.name}")
    return 0

def main(argv):
    p = argparse.ArgumentParser(prog="users")
    sub = p.add_subparsers(dest="command", required=True)
    a = sub.add_parser("add")
    a.add_argument("name")
    a.add_argument("--role", choices=["viewer", "admin"], default="viewer")
    a.set_defaults(func=add)
    r = sub.add_parser("remove")
    r.add_argument("name")
    r.add_argument("--yes", action="store_true")
    r.set_defaults(func=remove)
    args = p.parse_args(argv)
    return args.func(args)

for argv in (["add", "bob", "--role", "admin"], ["add", "jane"], ["remove", "bob"],
             ["remove", "bob", "--yes"], ["remove", "carol", "--yes"]):
    print("  exit code:", main(argv))
print(sorted(users))
```

<DeepDive title="More about argparse">

**Argument groups.** `p.add_argument_group("output")` organizes related options in the help text.

**Parent parsers.** Shared options (`--verbose`, `--region`) can live in a parser passed as `parents=[common]` to each subparser.

**Config precedence.** A common order is: command-line flag, then environment variable, then config file, then built-in default.

**BooleanOptionalAction.** `action=argparse.BooleanOptionalAction` creates `--color` and `--no-color` from one definition.

**Click and Typer.** Click uses decorators; Typer builds the CLI from type hints. Both add colors, prompts and shell completion.

</DeepDive>

<DeepDive title="Real world: the cleanup script with no dry run">

A cleanup script deleted log files older than N days: `cleanup.py /var/log/app 30`. Someone swapped the arguments in a cron entry (`cleanup.py 30 /var/log/app`), the script treated "30" as a folder relative to its working directory, which happened to be a data directory with a subfolder named 30, and deleted files there.

The fixes:

1. Named options (`--folder`, `--days`) instead of two positionals that are easy to swap.
2. Validation that the folder is absolute and inside an allowed root.
3. `--dry-run` by default in new cron entries until reviewed, and a log of everything deleted.

</DeepDive>

<DeepDive title="Security lens">

- **Never pass secrets as arguments**: they appear in `ps`, shell history and CI logs; read them from the environment or a secrets manager.
- **Validate paths and values** from arguments like any untrusted input, especially before deleting or overwriting.
- **Safe defaults**: dry-run first, explicit `--yes` for destructive actions, and confirmation prompts for interactive use.
- **Avoid passing arguments to shells**: if your tool runs other commands, use `subprocess` with lists, not `shell=True` (next lesson).
- **Honest exit codes** let pipelines stop when a security check fails.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between positional arguments and options?">
Positional arguments are identified by their position and are usually required, while options are identified by names like --dest, are usually optional and can appear in any order.
</QA>

<QA q="How does argparse handle invalid input?">
It validates types, choices and required arguments, prints the usage line and an error message to stderr, and exits with status 2 before your code runs.
</QA>

<QA q="How would you implement subcommands?">
Use add_subparsers, create a subparser per command with its own arguments, and attach a handler with set_defaults so the main function can dispatch with args.func(args).
</QA>

<QA q="Why should CLIs use proper exit codes?">
Shell scripts, cron and CI rely on the exit status to detect success or failure; returning 0 on errors hides failures and lets pipelines continue incorrectly.
</QA>

<QA q="How do you make a CLI testable?">
Put parsing and dispatch in a main function that accepts an argv list and returns an exit code, keep business logic in separate functions, and call main with test arguments in pytest.
</QA>

</DeepDive>
