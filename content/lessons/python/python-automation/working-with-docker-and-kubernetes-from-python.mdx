<BigIdea>
<Tr>
<En>
You can drive Docker and Kubernetes from Python by shelling out to `docker` and `kubectl`, but their official **Python SDKs** are usually better: you get structured objects instead of text to parse, real exceptions instead of exit codes, and no shell-injection risk. The **Docker SDK** (`pip install docker`) talks to the same **Docker daemon** the CLI uses. `docker.from_env()` connects through the local socket or `DOCKER_HOST`; `client.containers.run(image, detach=True, ports=..., labels=..., environment=...)` starts a container and returns a `Container` object with `.status`, `.logs()`, `.exec_run()`, `.stop()` and `.remove()`; `client.containers.list(filters={"label": "app=demo"})` finds containers by **label**, which is how cleanup scripts target only what they own. The **Kubernetes client** (`pip install kubernetes`) talks to the cluster's **API server**. Outside the cluster it reads your **kubeconfig** (`config.load_kube_config()`), inside a pod it uses the pod's **service account** (`config.load_incluster_config()`). Then API classes such as `CoreV1Api` and `AppsV1Api` list pods, read logs, scale deployments or watch events. The same library also has typed **model classes** (`V1Deployment`, `V1Service`, `V1ConfigMap`) that you can build and turn into YAML without a cluster, which is handy for generating manifests and checking them against your team's rules in CI. Both SDKs act with your full permissions, so label what you create, keep cleanup scoped, and give automation a narrowly scoped Kubernetes service account.
</En>
<Ur>
Aap `docker` aur `kubectl` ko shell se bula kar Python se Docker aur Kubernetes chala sakte hain, magar un ki official **Python SDKs** aam taur par behtar hain: parse karne ke liye text ke bajaye structured objects, exit codes ke bajaye asal exceptions, aur shell injection ka koi khatra nahi. **Docker SDK** (`pip install docker`) usi **Docker daemon** se baat karti jis se CLI karta hai. `docker.from_env()` local socket ya `DOCKER_HOST` ke zariye jurta; `client.containers.run(image, detach=True, ports=..., labels=..., environment=...)` container shuru kar ke `.status`, `.logs()`, `.exec_run()`, `.stop()` aur `.remove()` wala `Container` object lautata; `client.containers.list(filters={"label": "app=demo"})` **label** se containers dhoondta, isi tarah safai scripts sirf apni cheezon ko nishana banati hain. **Kubernetes client** (`pip install kubernetes`) cluster ke **API server** se baat karta hai. ## Learn it step by step

<Walkthrough>

<Step title="The Docker SDK: run, wait, inspect, exec, logs, filter and clean up">

<Tr>
<En>
We install pinned `docker` and `kubernetes` packages. `containers.py` connects to the local Docker daemon, checks that the `nginx:1.29-alpine` image is present, runs it in the background with a port bound to localhost, labels, an environment variable and a memory limit, waits until it answers HTTP, reads its status and our labels, runs a command inside it, checks its logs, finds it by label, and finally stops and removes it and shows the errors for missing containers and images.
</En>
<Ur>
Hum pinned `docker` aur `kubernetes` packages install karte hain. `containers.py` local Docker daemon se jurti, check karti ke `nginx:1.29-alpine` image mojood hai, use localhost se jure port, labels, environment variable aur memory limit ke saath background me chalati, HTTP jawab dene tak intezar karti, us ka status aur hamare labels parhti, andar command chalati, logs check karti, label se dhoondti, aur aakhir me band kar ke hatati aur ghayab containers aur images ke errors dikhati hai.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z NO_PROXY=127.0.0.1
uv venv -q --python 3.13 .venv && uv pip install -q --python .venv "docker==7.1.0" "kubernetes==32.0.1"
cat > containers.py <<'EOF'
import time, urllib.request
import docker
from docker.errors import NotFound, ImageNotFound

client = docker.from_env()                       # talks to the Docker daemon (socket or DOCKER_HOST)
print("daemon reachable:", client.ping())

image = client.images.get("nginx:1.29-alpine")   # use client.images.pull(...) if it's not local yet
print("image:", image.tags[0])

c = client.containers.run(
    "nginx:1.29-alpine", name="demo-web", detach=True,
    ports={"80/tcp": ("127.0.0.1", 8089)},        # bind to localhost only
    labels={"app": "demo", "owner": "jane"},
    environment={"APP_ENV": "staging"},
    mem_limit="128m",
)

for _ in range(30):                               # wait until it answers
    try:
        with urllib.request.urlopen("http://127.0.0.1:8089/", timeout=1) as r:
            print("HTTP", r.status, "| server:", r.headers["Server"].split("/")[0])
            break
    except OSError:
        time.sleep(0.2)

c.reload()                                        # refresh attributes from the daemon
print("status:", c.status, "| name:", c.name, "| our labels:", {k: c.labels[k] for k in ("app", "owner")})
code, out = c.exec_run(["sh", "-c", "echo $APP_ENV && ls /usr/share/nginx/html"])
print("exec:", code, out.decode().split())
print("log lines mention GET:", any("GET / " in l for l in c.logs().decode().splitlines()))

mine = client.containers.list(filters={"label": "app=demo"})
print("containers with label app=demo:", [x.name for x in mine])

c.stop(timeout=5)
c.remove()
try:
    client.containers.get("demo-web")
except NotFound:
    print("removed: NotFound")
try:
    client.images.get("nginx:does-not-exist")
except ImageNotFound:
    print("ImageNotFound for a missing tag")
EOF
.venv/bin/python containers.py
```

<Happened>
<Tr>
<En>

- `docker.from_env()` used the same connection as the `docker` CLI, and `ping()` confirmed the daemon was reachable. Access to the Docker socket is effectively **root access** on the host, so be careful which scripts and containers get it.
- `containers.run(detach=True)` returned a `Container` object immediately. Binding to `("127.0.0.1", 8089)` exposed nginx only on this machine, not on every network interface.
- Containers aren't ready the moment they start, so we **polled** until HTTP returned 200. Real tests do the same with health checks or retries.
- `reload()` refreshed attributes; our **labels** were there (the image adds its own labels too, which we filtered out). `exec_run` ran `sh -c` inside the container and returned an exit code and output: our `APP_ENV` and nginx's default HTML files.
- `logs()` returned the access log, including our GET request, and `list(filters={"label": "app=demo"})` found the container by label.
- After `stop()` and `remove()`, `get()` raised **NotFound**; a missing tag raised **ImageNotFound**. Catch these specific exceptions instead of parsing CLI text.

</En>
<Ur>

- `docker.from_env()` ne `docker` CLI wala hi connection istemal kiya, aur `ping()` ne daemon tak pohanch ki tasdeeq ki. Docker socket tak rasai asal me host par **root access** hai, isliye dhyan rakhein kaun si scripts aur containers ko ye milti hai.
- `containers.run(detach=True)` ne foran `Container` object lautaya. `("127.0.0.1", 8089)` se bind karne ne nginx ko sirf isi machine par khola, har network interface par nahi.
- Containers shuru hote hi tayyar nahi hote, isliye humne 200 aane tak **baar baar poochha**. Asal tests health checks ya retries se yahi karte hain.
- `reload()` ne attributes taaza kiye; hamare **labels** mojood the (image bhi apne labels jorti hai, jinhe humne chhaan diya). `exec_run` ne container ke andar `sh -c` chala kar exit code aur output lautaya: hamara `APP_ENV` aur nginx ki default HTML files.
- `logs()` ne hamari GET request samait access log lautaya, aur `list(filters={"label": "app=demo"})` ne label se container dhoonda.
- `stop()` aur `remove()` ke baad `get()` ne **NotFound** uthaya; ghayab tag ne **ImageNotFound**. CLI ka text parse karne ke bajaye ye khaas exceptions pakrein.

</Ur>

<Step title="The Kubernetes client: connecting, building manifests and checking them">

<Tr>
<En>
The sandbox we used to verify this lesson can't run a Kubernetes cluster, so this step uses the parts of the official client that work without one, and we say so honestly. `k8s.py` tries to load a kubeconfig (we point `KUBECONFIG` at a file that doesn't exist, to show the error), builds a Deployment from typed model classes with resource requests and limits and a non-root security context, prints the start of the generated YAML, and runs a small policy check over three deployments. With a real kubeconfig, `config.load_kube_config()` succeeds and the API classes shown above talk to the cluster.
</En>
<Ur>
Is lesson ki tasdeeq ke liye istemal hua sandbox Kubernetes cluster nahi chala sakta, isliye ye qadam official client ke woh hisse istemal karta jo cluster ke baghair chalte hain, aur hum ye imandari se batate hain. `k8s.py` kubeconfig load karne ki koshish karti (error dikhane ke liye hum `KUBECONFIG` ko na-mojood file par rakhte hain), resource requests aur limits aur non-root security context ke saath typed model classes se Deployment banati, bani YAML ka shuruati hissa print karti, aur teen deployments par chhota policy check chalati hai. Asal kubeconfig ke saath `config.load_kube_config()` kamyab hota aur upar dikhayi API classes cluster se baat karti hain.
</Ur>
</Tr>

```bash
cat > k8s.py <<'EOF'
import yaml
from kubernetes import client, config
from kubernetes.config.config_exception import ConfigException

# 1. Connecting: in a pod use load_incluster_config(); on a laptop, load_kube_config()
try:
    config.load_kube_config()                 # reads ~/.kube/config (or $KUBECONFIG)
except ConfigException as e:
    print("no cluster configured here:", type(e).__name__)

# 2. Build a Deployment with typed model objects (no cluster needed)
def deployment(name, image, replicas=2, limits=True):
    container = client.V1Container(
        name=name, image=image, ports=[client.V1ContainerPort(container_port=8080)],
        resources=client.V1ResourceRequirements(
            requests={"cpu": "100m", "memory": "128Mi"},
            limits={"cpu": "500m", "memory": "256Mi"} if limits else None),
        security_context=client.V1SecurityContext(run_as_non_root=True, allow_privilege_escalation=False),
    )
    return client.V1Deployment(
        api_version="apps/v1", kind="Deployment",
        metadata=client.V1ObjectMeta(name=name, labels={"app": name}),
        spec=client.V1DeploymentSpec(
            replicas=replicas,
            selector=client.V1LabelSelector(match_labels={"app": name}),
            template=client.V1PodTemplateSpec(
                metadata=client.V1ObjectMeta(labels={"app": name}),
                spec=client.V1PodSpec(containers=[container]))))

api = client.ApiClient()
manifest = api.sanitize_for_serialization(deployment("orders-api", "registry.example.com/orders-api:1.4.2"))
text = yaml.safe_dump(manifest, sort_keys=False)
print(text.split("template:")[0].rstrip())          # first part of the generated YAML
print("...", len(text.splitlines()), "lines in total")

# 3. A policy check you could run in CI before kubectl apply
def check(m):
    problems = []
    for c in m["spec"]["template"]["spec"]["containers"]:
        if c["image"].endswith(":latest") or ":" not in c["image"].rsplit("/", 1)[-1]:
            problems.append(f"{c['name']}: pin an image tag")
        if "limits" not in c.get("resources", {}):
            problems.append(f"{c['name']}: no resource limits")
    if m["spec"]["replicas"] < 2:
        problems.append("fewer than 2 replicas")
    return problems

candidates = [deployment("orders-api", "registry.example.com/orders-api:1.4.2"),
              deployment("worker", "registry.example.com/worker:latest", replicas=1, limits=False),
              deployment("cron", "busybox")]
for d in candidates:
    m = api.sanitize_for_serialization(d)
    print(f"{m['metadata']['name']:<11}", check(m) or "OK")
EOF
KUBECONFIG="$PWD/no-such-kubeconfig" .venv/bin/python k8s.py
```

<Happened>
<Tr>
<En>

- Without a kubeconfig, `load_kube_config()` raised **ConfigException**. On a laptop the config comes from `~/.kube/config` (or `$KUBECONFIG`); inside a pod, `load_incluster_config()` uses the pod's service account token, so no credentials are copied anywhere.
- The `V1...` model classes mirror the Kubernetes API exactly. Writing `run_as_non_root=True` in Python became `runAsNonRoot: true` in the output, because `sanitize_for_serialization` converts names to the API's camelCase and drops empty fields. Typos in field names fail in Python immediately instead of being silently ignored in YAML.
- The generated YAML is a normal manifest (31 lines): you can `kubectl apply -f` it, commit it, or send the same object to the API with `AppsV1Api().create_namespaced_deployment(namespace, body)`.
- The policy check found that **worker** uses `:latest`, has no limits and only one replica, and **cron** uses an untagged image (which means `latest`). Running checks like these in CI catches problems before they reach the cluster; admission policies (Kyverno, OPA Gatekeeper) enforce them inside it.

</En>
<Ur>

- Kubeconfig ke baghair `load_kube_config()` ne **ConfigException** uthaya. Laptop par config `~/.kube/config` (ya `$KUBECONFIG`) se aati; pod ke andar `load_incluster_config()` pod ka service account token istemal karta, isliye credentials kahin copy nahi hote.
- `V1...` model classes bilkul Kubernetes API jaisi hain. Python me `run_as_non_root=True` likhna output me `runAsNonRoot: true` bana, kyunke `sanitize_for_serialization` naamon ko API ke camelCase me badalta aur khaali fields girata hai. Field ke naamon ki ghaltiyan YAML me khamoshi se nazar andaz hone ke bajaye Python me foran nakam hoti hain.
- Bani YAML aam manifest hai (31 lines): aap ise `kubectl apply -f` kar sakte, commit kar sakte, ya wahi object `AppsV1Api().create_namespaced_deployment(namespace, body)` se API ko bhej sakte hain.
- Policy check ne dhoonda ke **worker** `:latest` istemal karta, us ki limits nahi aur sirf ek replica hai, aur **cron** be-tag image (yani `latest`) istemal karta hai. CI me aise checks cluster tak pohanchne se pehle masail pakarte; admission policies (Kyverno, OPA Gatekeeper) inhe cluster ke andar lagu karti hain.

</Ur>

<Challenge title="One-off jobs and label-based cleanup">

<Tr>
<En>
With the Docker SDK and the local `nginx:1.29-alpine` image: run a one-off container that prints `$((6 * 7))` and is removed automatically, printing its output. Then start three detached containers named `ci-test-0` to `ci-test-2` with the label `purpose=ci-test`, and write `cleanup(label, dry_run=True)` that lists matching containers (including stopped ones) and removes them only when `dry_run=False`. Show a dry run, a real run, and that none are left.
</En>
<Ur>
Docker SDK aur local `nginx:1.29-alpine` image ke saath: ek dafa ka container chalayen jo `$((6 * 7))` print kare aur khud hat jaye, us ka output print karein. Phir `purpose=ci-test` label ke saath `ci-test-0` se `ci-test-2` naam ke teen detached containers shuru karein, aur `cleanup(label, dry_run=True)` likhein jo milte containers (band samait) ki list banaye aur sirf `dry_run=False` par hataye. Dry run, asal run, aur ye ke koi nahi bacha, dikhayen.
</Ur>

<Solution>

<Tr>
<En>

```text
import docker

client = docker.from_env()
IMAGE = "nginx:1.29-alpine"

# A one-off job: run, capture output, remove automatically
out = client.containers.run(IMAGE, ["sh", "-c", "echo $((6 * 7))"], remove=True)
print("job output:", out.decode().strip())

# Start three labelled containers, then clean up by label (like a CI job tidying test containers)
for i in range(3):
    client.containers.run(IMAGE, name=f"ci-test-{i}", detach=True, labels={"purpose": "ci-test"})

def cleanup(label, dry_run=True):
    found = client.containers.list(all=True, filters={"label": label})
    for c in sorted(found, key=lambda c: c.name):
        print(("would remove" if dry_run else "removing"), c.name)
        if not dry_run:
            c.remove(force=True)
    return len(found)

cleanup("purpose=ci-test")
removed = cleanup("purpose=ci-test", dry_run=False)
print("removed:", removed, "| left:", len(client.containers.list(all=True, filters={"label": "purpose=ci-test"})))

# job output: 42
# would remove ci-test-0
# would remove ci-test-1
# would remove ci-test-2
# removing ci-test-0
# removing ci-test-1
# removing ci-test-2
# removed: 3 | left: 0
```

<Challenge title="Generate a multi-document manifest">

<Tr>
<En>
Using the Kubernetes model classes, build a ConfigMap (`<name>-config` with `LOG_LEVEL` and `PORT`) and a Service (port 80 to the app's port) for `orders-api` on 8080 and `billing-api` on 9000. Write all four objects to `app.yaml` as one multi-document YAML file with `yaml.safe_dump_all`, then load it back and print the number of documents, the kinds, each Service's port mapping, and how many `---` separators the file has.
</En>
<Ur>
Kubernetes model classes se `orders-api` (8080) aur `billing-api` (9000) ke liye ConfigMap (`LOG_LEVEL` aur `PORT` wala `<name>-config`) aur Service (port 80 se app ke port tak) banayen. Chaaron objects `yaml.safe_dump_all` se ek multi-document YAML file `app.yaml` me likhein, phir wapas load kar ke documents ki tadaad, kinds, har Service ki port mapping, aur file me kitne `---` separators hain, print karein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
import yaml
from kubernetes import client

api = client.ApiClient()

def service(name, port, target):
    return client.V1Service(
        api_version="v1", kind="Service", metadata=client.V1ObjectMeta(name=name),
        spec=client.V1ServiceSpec(selector={"app": name},
                                  ports=[client.V1ServicePort(port=port, target_port=target)]))

def config_map(name, data):
    return client.V1ConfigMap(api_version="v1", kind="ConfigMap",
                              metadata=client.V1ObjectMeta(name=f"{name}-config"), data=data)

objects = []
for name, port in [("orders-api", 8080), ("billing-api", 9000)]:
    objects.append(config_map(name, {"LOG_LEVEL": "info", "PORT": str(port)}))
    objects.append(service(name, 80, port))

docs = [api.sanitize_for_serialization(o) for o in objects]
with open("app.yaml", "w", encoding="utf-8") as f:
    yaml.safe_dump_all(docs, f, sort_keys=False)

loaded = list(yaml.safe_load_all(open("app.yaml", encoding="utf-8")))
print("documents:", len(loaded), "| kinds:", sorted({d["kind"] for d in loaded}))
for d in loaded:
    if d["kind"] == "Service":
        p = d["spec"]["ports"][0]
        print(f"  {d['metadata']['name']}: port {p['port']} -> {p['targetPort']}")
print("separators in file:", open("app.yaml").read().count("\n---\n"))

# documents: 4 | kinds: ['ConfigMap', 'Service']
#   orders-api: port 80 -> 8080
#   billing-api: port 80 -> 9000
# separators in file: 3
```

<DeepDive title="More about Docker and Kubernetes from Python">

**testcontainers.** The `testcontainers` library starts Postgres, Redis, Kafka and more for a test session and removes them afterwards.

**Images.** `client.images.build(path=".", tag="app:1.0")` builds images; `client.api` exposes the low-level API for streaming build output.

**Watches.** `kubernetes.watch.Watch().stream(...)` yields events as resources change, the basis of controllers; `kopf` builds operators in Python.

**Dynamic client.** `kubernetes.dynamic` works with custom resources (CRDs) without generated classes.

**Async.** `aiodocker` and `kubernetes_asyncio` provide asyncio versions of both SDKs.

</DeepDive>

<DeepDive title="Real world: the CI runner that filled its disk">

A CI pipeline started Postgres and Redis containers for integration tests with a script, but when tests failed, the script exited before its cleanup step. Over a week, hundreds of stopped containers and their volumes piled up, the runner's disk filled, and every pipeline on that runner failed.

The fixes:

1. Containers are created with `labels={"ci-job": job_id}` and removed in a `finally` block.
2. A nightly job removes containers and volumes older than a day with the `ci-job` label.
3. Disk usage alerts on runners.

</DeepDive>

<DeepDive title="Security lens">

- **Docker socket = root**: don't expose it to untrusted code, web apps or containers.
- **Least privilege in Kubernetes**: one service account per tool, Roles limited to specific namespaces and verbs; avoid cluster-admin.
- **Secrets**: don't print `V1Secret` data or pod environment variables in reports; base64 is not encryption.
- **Pin images** by version or digest and scan them; enforce with admission policies.
- **Bind test services to localhost** and remove them reliably.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does the Docker SDK connect to Docker?">
docker.from_env reads DOCKER_HOST and related variables or defaults to the local Unix socket, and talks to the Docker Engine API, the same API the CLI uses.
</QA>

<QA q="How do you make container cleanup safe?">
Label containers when creating them, filter by that label when cleaning up, remove them in finally blocks or with remove=True, and support a dry run.
</QA>

<QA q="What is the difference between load_kube_config and load_incluster_config?">
load_kube_config reads a kubeconfig file for use outside the cluster; load_incluster_config uses the service account token and API address mounted into a pod when running inside the cluster.
</QA>

<QA q="Why build Kubernetes manifests with model classes instead of string templates?">
Typed objects catch field mistakes early, avoid YAML indentation and quoting errors, and can be serialized consistently or sent directly to the API.
</QA>

<QA q="How would you restrict what an automation script can do in a cluster?">
Create a dedicated service account with a Role or ClusterRole granting only the required verbs on required resources and namespaces, bind it, and run the script with that identity.
</QA>

</DeepDive>
