<BigIdea>
<Tr>
<En>
**Authentication** answers "who are you?", **authorization** answers "are you allowed to do this?". In a FastAPI API the usual pattern is: the client sends a username and password once to a **token endpoint**; the server checks the password against a stored **Argon2id hash** (never the password itself) and returns a short-lived **access token**, usually a **JWT**. A JWT has three dot-separated parts: a header, a payload of **claims** such as `sub` (who), `role`, `aud` (which API it's for) and `exp` (when it expires), and a **signature**. The payload is only base64 encoded, so anyone can read it, but nobody can change it without the secret, because the signature would no longer match. The client then sends `Authorization: Bearer <token>` on each request. In FastAPI, **`OAuth2PasswordBearer`** extracts that token, and a **`current_user` dependency** decodes it with a **fixed algorithm list**, checks expiry and audience, and loads the user, so a disabled account is refused even with a valid token. A second dependency such as `require_role("admin")` returns **403** when the user is known but not allowed. Login errors should be the same message for unknown users and wrong passwords, and the server should do the same hashing work in both cases. Long sessions use **refresh tokens** that are rotated on every use, and login attempts are **rate limited**.
</En>
<Ur>
**Authentication** "aap kaun hain?" ka jawab deti, **authorization** "kya aap ko ye karne ki ijazat hai?" ka. FastAPI API me aam tareeqa ye hai: client ek dafa username aur password **token endpoint** ko bhejta; server password ko mehfooz **Argon2id hash** (khud password kabhi nahi) se milata aur thori der chalne wala **access token**, aam tor par **JWT**, lautata hai. JWT ke teen nuqte se alag hisse hote: header, `sub` (kaun), `role`, `aud` (kis API ke liye) aur `exp` (kab khatam) jaise **claims** ka payload, aur **signature**. Payload sirf base64 encoded hai, isliye koi bhi ise parh sakta, lekin secret ke baghair koi ise badal nahi sakta, kyunke signature phir nahi milega. Phir client har request par `Authorization: Bearer <token>` bhejta hai. FastAPI me **`OAuth2PasswordBearer`** woh token nikalta, aur **`current_user` dependency** ise **tay algorithm list** ke saath decode karti, expiry aur audience check karti, aur user load karti hai, isliye band account durust token ke saath bhi radd hota hai. `require_role("admin")` jaisi doosri dependency **403** lautati jab user maloom ho lekin ijazat na ho. Login errors na-maloom users aur ghalat passwords ke liye ek hi paigham hon, aur server dono halaton me utna hi hashing ka kaam kare. Lambe sessions **refresh tokens** istemal karte jo har istemal par badle jate, aur login koshishon par **rate limit** lagta hai.
</Ur>

## Picture it

<Tr>
<En>

Think of a **conference with a registration desk and wristbands**.

- At **registration** you show your ID once (username and password). Staff check it against their list, which holds a fingerprint of each ID, not a copy (the **password hash**).
- You get a **wristband** printed with your name, your access level and today's date (the **JWT claims**), sealed with a hologram only the organisers can make (the **signature**). Anyone can read the wristband, but nobody can forge or edit it.
- Every door guard checks the hologram and the date (**signature and expiry**). Some doors also need "speaker" on the band (**role check, 403** if missing).
- If someone is thrown out, guards also have a short **banned list** they check (the `active` flag), because a wristband can't be taken back by itself.
- Trying wrong IDs again and again at registration gets you **asked to wait** (rate limiting).

</En>
<Ur>

**Registration desk aur wristbands wali conference** socheyn.

- **Registration** par aap ek dafa apni ID dikhate (username aur password). Staff use apni list se milata, jis me har ID ka fingerprint hai, copy nahi (**password hash**).
- Aap ko **wristband** milta jis par aap ka naam, access level aur aaj ki tareekh chhapi hai (**JWT claims**), aisi hologram ke saath jo sirf muntazimeen bana sakte (**signature**). Koi bhi wristband parh sakta, lekin koi ise jaali bana ya badal nahi sakta.
- Har darwaze ka guard hologram aur tareekh check karta (**signature aur expiry**). Kuch darwazon par band par "speaker" bhi chahiye (**role check**, na ho to **403**).
- Agar kisi ko nikala jaye, to guards ke paas chhoti **pabandi list** bhi hai jo woh dekhte (`active` flag), kyunke wristband khud wapas nahi liya ja sakta.
- Registration par baar baar ghalat IDs aazmane par aap ko **intezar karne** ko kaha jata (rate limiting).

</Ur>

<Tr>

```bash
import base64, json, secrets
from datetime import datetime, timedelta, timezone
import jwt
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()                                     # Argon2id with sensible defaults
stored = ph.hash("Tram-Lantern-42")
print("hash starts with:", stored[:30] + "...")
print("same password, new hash each time:", ph.hash("Tram-Lantern-42") != stored)
print("correct password:", ph.verify(stored, "Tram-Lantern-42"))
try:
    ph.verify(stored, "tram-lantern-42")
except VerifyMismatchError:
    print("wrong password: VerifyMismatchError")

SECRET = secrets.token_urlsafe(32)                        # in real apps: from the environment, never in code
now = datetime.now(timezone.utc)
token = jwt.encode({"sub": "jane", "scope": "orders:read", "iat": now, "exp": now + timedelta(minutes=15)},
                   SECRET, algorithm="HS256")
header, payload, signature = token.split(".")
print("token parts:", len(token.split(".")), "| header:", json.loads(base64.urlsafe_b64decode(header + "==")))
print("payload is only encoded, not encrypted:", json.loads(base64.urlsafe_b64decode(payload + "=="))["sub"])
print("decoded claims:", {k: v for k, v in jwt.decode(token, SECRET, algorithms=["HS256"]).items() if k in ("sub", "scope")})

def check(label, tok, **kw):
    try:
        jwt.decode(tok, SECRET, algorithms=["HS256"], **kw)
        print(f"{label:<28} accepted")
    except jwt.PyJWTError as e:
        print(f"{label:<28} rejected: {type(e).__name__}")

fake_payload = base64.urlsafe_b64encode(json.dumps({"sub": "admin", "scope": "admin",
               "exp": int((now + timedelta(hours=1)).timestamp())}).encode()).rstrip(b"=").decode()
check("payload edited to admin", f"{header}.{fake_payload}.{signature}")
none_header = base64.urlsafe_b64encode(b'{"alg":"none","typ":"JWT"}').rstrip(b"=").decode()
check("alg none, no signature", f"{none_header}.{fake_payload}.")
check("expired", jwt.encode({"sub": "jane", "exp": now - timedelta(seconds=1)}, SECRET, algorithm="HS256"))
check("signed with another key", jwt.encode({"sub": "jane", "exp": now + timedelta(minutes=5)}, "guessable", algorithm="HS256"))
check("missing audience claim", token, audience="orders-api")
EOF
python security_basics.py
```

<Happened>
<Tr>
<En>

- The hash string records the algorithm and its cost settings (`m=65536` KiB of memory, `t=3` passes, `p=4` lanes) plus a random salt, so hashing the same password twice gave different strings, and `verify` still matched. A wrong password, even differing only in case, raised `VerifyMismatchError`. Argon2's memory cost makes GPU guessing expensive; fast hashes like SHA-256 are the wrong tool for passwords.
- The token has **three parts**. Decoding the header and payload with plain base64 showed `HS256` and `jane`: **a JWT is not encrypted**. Never put secrets or personal data you wouldn't show the user into it.
- Changing the payload to `admin` while keeping the old signature failed with `InvalidSignatureError`.
- The `alg: none` trick (a token that claims to need no signature) failed with `InvalidAlgorithmError`, because we passed `algorithms=["HS256"]`. Always pin the algorithm list; old libraries that trusted the header's `alg` were exploited this way.
- The expired token and the token signed with a different key were rejected, and asking for `audience="orders-api"` rejected a token without an `aud` claim, which stops a token issued for one service being replayed against another.

</En>
<Ur>

- Hash string algorithm aur us ki laagat settings (`m=65536` KiB memory, `t=3` chakkar, `p=4` lanes) aur random salt record karti, isliye ek hi password do dafa hash karne par mukhtalif strings milin, aur `verify` phir bhi mila. Ghalat password, chahe sirf bare chhote huroof ka farq ho, ne `VerifyMismatchError` uthaya. Argon2 ki memory laagat GPU se andaze mehnge banati; SHA-256 jaise tez hashes passwords ke liye ghalat auzar hain.
- Token ke **teen hisse** hain. Header aur payload ko saade base64 se decode karne par `HS256` aur `jane` dikhe: **JWT encrypted nahi hota**. Is me kabhi secrets ya aisa zaati data na daalein jo aap user ko na dikhate.
- Purana signature rakh kar payload ko `admin` me badalna `InvalidSignatureError` se nakam hua.
- `alg: none` chaal (aisa token jo kehta ke signature ki zaroorat nahi) `InvalidAlgorithmError` se nakam hui, kyunke hum ne `algorithms=["HS256"]` diya. Algorithm list hamesha tay karein; header ke `alg` par bharosa karne wali purani libraries isi tarah exploit huin.
- Expired token aur doosri key se signed token radd hue, aur `audience="orders-api"` mangne se `aud` claim ke baghair token radd hua, jo ek service ke liye jaari token ko doosri par dobara chalane se rokta hai.

</Ur>

<Step title="OAuth2 password flow, current_user and roles in FastAPI">

<Tr>
<En>
`auth_app.py` reads the signing secret from the `JWT_SECRET` environment variable and keeps three users with Argon2 hashes, one of them disabled. `POST /token` accepts the standard OAuth2 form fields and returns a token with `sub`, `role`, `aud`, `iat` and `exp`. `current_user` verifies the token and re-checks that the user still exists and is active; `require_role` adds a 403 check. `try_auth.py` tests bad logins, a missing token, a member and an admin calling an admin-only endpoint, an expired token, a token for another audience, and a user disabled after logging in.
</En>
<Ur>
`auth_app.py` signing secret `JWT_SECRET` environment variable se parhti aur Argon2 hashes ke saath teen users rakhti, jin me ek band hai. `POST /token` mayari OAuth2 form fields qubool karta aur `sub`, `role`, `aud`, `iat` aur `exp` wala token lautata hai. `current_user` token tasdeeq karti aur dobara check karti ke user ab bhi mojood aur active hai; `require_role` 403 check jorti hai. `try_auth.py` ghalat logins, ghayab token, admin-only endpoint bulane wale member aur admin, expired token, doosri audience ka token, aur login ke baad band kiya gaya user test karti hai.
</Ur>
</Tr>

```bash
. .venv/bin/activate
export JWT_SECRET=acme_test_jwt_secret_please_change_me_0123456789
cat > auth_app.py <<'EOF'
import os
from datetime import datetime, timedelta, timezone
from typing import Annotated
import jwt
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError
from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from pydantic import BaseModel

SECRET = os.environ["JWT_SECRET"]
ALGORITHM, AUDIENCE, TOKEN_MINUTES = "HS256", "orders-api", 15
ph = PasswordHasher()
USERS = {"jane": {"hash": ph.hash("Tram-Lantern-42"), "role": "admin", "active": True},
         "bob": {"hash": ph.hash("Velvet-Harbor-7x"), "role": "member", "active": True},
         "old": {"hash": ph.hash("Gone-Account-99"), "role": "member", "active": False}}
DUMMY_HASH = ph.hash("dummy-password-for-timing")

app = FastAPI()
oauth2 = OAuth2PasswordBearer(tokenUrl="token")       # reads "Authorization: Bearer <token>"

class Token(BaseModel):
    access_token: str
    token_type: str = "bearer"

def authenticate(username: str, password: str):
    user = USERS.get(username)
    try:
        ph.verify(user["hash"] if user else DUMMY_HASH, password)   # same work for unknown users
    except VerifyMismatchError:
        return None
    return user if user and user["active"] else None

@app.post("/token", response_model=Token)
def login(form: Annotated[OAuth2PasswordRequestForm, Depends()]):
    user = authenticate(form.username, form.password)
    if not user:
        raise HTTPException(401, "incorrect username or password", headers={"WWW-Authenticate": "Bearer"})
    now = datetime.now(timezone.utc)
    claims = {"sub": form.username, "role": user["role"], "aud": AUDIENCE, "iat": now,
              "exp": now + timedelta(minutes=TOKEN_MINUTES)}
    return Token(access_token=jwt.encode(claims, SECRET, algorithm=ALGORITHM))

def current_user(token: Annotated[str, Depends(oauth2)]) -> dict:
    unauthorized = HTTPException(status.HTTP_401_UNAUTHORIZED, "invalid or expired token",
                                 headers={"WWW-Authenticate": "Bearer"})
    try:
        claims = jwt.decode(token, SECRET, algorithms=[ALGORITHM], audience=AUDIENCE,
                            options={"require": ["exp", "sub", "aud"]})
    except jwt.PyJWTError:
        raise unauthorized
    user = USERS.get(claims["sub"])
    if not user or not user["active"]:                  # disabled after the token was issued
        raise unauthorized
    return {"username": claims["sub"], "role": user["role"]}

def require_role(role: str):
    def checker(user: Annotated[dict, Depends(current_user)]):
        if user["role"] != role:
            raise HTTPException(403, "not allowed")
        return user
    return checker

@app.get("/me")
def me(user: Annotated[dict, Depends(current_user)]):
    return user

@app.delete("/orders/{order_id}")
def delete_order(order_id: int, user: Annotated[dict, Depends(require_role("admin"))]):
    return {"deleted": order_id, "by": user["username"]}
EOF
```

## Common mistakes

<Compare>
<Bad title="Trusting the token header and skipping checks">

```text
claims = jwt.decode(token, options={"verify_signature": False})   # anyone can forge this
# or: algorithms taken from the token header, no exp, no audience
```

</Bad>
<Good title="Pinned algorithm, required claims, audience">

```text
claims = jwt.decode(token, SECRET, algorithms=["HS256"], audience="orders-api",
                    options={"require": ["exp", "sub", "aud"]})
```

</Good>
</Compare>

<Compare>
<Bad title="Login errors that reveal which part was wrong">

```text
if username not in USERS:
    raise HTTPException(404, "no such user")          # lets attackers list accounts
if not verify(USERS[username], password):
    raise HTTPException(401, "wrong password")
```

</Bad>
<Good title="One generic message and the same work either way">

```text
user = USERS.get(username)
ok = verify(user["hash"] if user else DUMMY_HASH, password)
if not (ok and user and user["active"]):
    raise HTTPException(401, "incorrect username or password")
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **A hard-coded or short JWT secret**: generate at least 32 random bytes, load it from the environment or a secret store, and rotate it.
- **Long-lived access tokens** (days or months): keep them to minutes and use rotating refresh tokens.
- **Putting sensitive data in the payload**: it's readable by anyone holding the token.
- **Storing tokens in localStorage on sites with XSS risk**: prefer HttpOnly cookies for browser sessions, with CSRF protection.
- **Checking roles inside some endpoints but not others**: attach role dependencies at router level and test that each protected route returns 401 and 403.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Code me likha ya chhota JWT secret**: kam az kam 32 random bytes banayen, environment ya secret store se load karein, aur badalte rahein.
- **Lambe access tokens** (din ya mahine): inhe minuton tak rakhein aur badalte refresh tokens lein.
- **Payload me hassas data daalna**: token rakhne wala koi bhi ise parh sakta hai.
- **XSS ke khatre wali sites par tokens localStorage me rakhna**: browser sessions ke liye CSRF tahaffuz ke saath HttpOnly cookies behtar hain.
- **Kuch endpoints me roles check karna aur kuch me nahi**: role dependencies router level par lagayen aur test karein ke har mehfooz route 401 aur 403 lautaye.

</Ur>
</Tr>

<En>

```text
from fastapi import FastAPI, HTTPException, Request
from fastapi.testclient import TestClient
from pydantic import BaseModel

MAX_FAILS, WINDOW = 5, 15 * 60
FAILS: dict[str, list[float]] = {}
CLOCK = {"now": 1_000_000.0}                       # fake clock so the demo is repeatable
PASSWORDS = {"jane": "Tram-Lantern-42"}            # stand-in for a real hash check

class LoginIn(BaseModel):
    username: str
    password: str

app = FastAPI()

@app.post("/login")
def login(body: LoginIn, request: Request):
    key = f"{body.username.lower()}|{request.client.host}"
    now = CLOCK["now"]
    recent = [t for t in FAILS.get(key, []) if now - t < WINDOW]
    if len(recent) >= MAX_FAILS:
        retry = int(WINDOW - (now - recent[0]))
        raise HTTPException(429, "too many attempts", headers={"Retry-After": str(retry)})
    if PASSWORDS.get(body.username) != body.password:
        FAILS[key] = recent + [now]
        raise HTTPException(401, "incorrect username or password")
    FAILS.pop(key, None)
    return {"ok": True}

c = TestClient(app)
codes = []
for i in range(6):
    codes.append(c.post("/login", json={"username": "jane", "password": f"guess{i}"}).status_code)
    CLOCK["now"] += 10
print("six wrong guesses:", codes)
r = c.post("/login", json={"username": "jane", "password": "Tram-Lantern-42"})
print("right password while locked:", r.status_code, "| Retry-After:", r.headers["retry-after"])
CLOCK["now"] += 15 * 60
print("after the window:", c.post("/login", json={"username": "jane", "password": "Tram-Lantern-42"}).json())
print("failures cleared:", FAILS == {})

# six wrong guesses: [401, 401, 401, 401, 401, 429]
# right password while locked: 429 | Retry-After: 840
# after the window: {'ok': True}
# failures cleared: True
```

In production keep the counters in Redis so all workers share them, and also limit per IP across usernames to slow password spraying.

<DeepDive title="More about FastAPI authentication">

**Scopes.** `SecurityScopes` and `Security(current_user, scopes=["orders:write"])` let OAuth2 scopes appear in OpenAPI and be checked per endpoint.

**Asymmetric keys.** With RS256 or EdDSA, only the auth service holds the private key; other services verify with the public key, often fetched from a JWKS endpoint.

**External identity providers.** Instead of storing passwords yourself, accept tokens from an OpenID Connect provider (Auth0, Okta, Keycloak, Entra ID) and verify `iss`, `aud` and the signing key.

**Rehashing.** `ph.check_needs_rehash(hash)` tells you when to upgrade an old hash after a successful login, as cost settings increase.

**MFA.** Add a TOTP step (for example with `pyotp`) before issuing a full token, and issue a limited token in between.

</DeepDive>

<DeepDive title="Real world: the token that never died">

A mobile API issued JWTs valid for 365 days and checked only the signature. When a support laptop was stolen, an admin's token was in its browser storage. Disabling the admin account changed nothing, because the API never looked at accounts after login. Rotating the signing secret logged out every user at once in the middle of the working day.

The fixes:

1. Access tokens dropped to 15 minutes, with rotating refresh tokens stored server-side.
2. `current_user` checks the account status and a per-user "tokens valid after" timestamp.
3. Admin tokens require MFA and a separate audience.
4. Signing keys have IDs (`kid`), so a new key can be introduced before the old one is retired.

</DeepDive>

<DeepDive title="Security lens">

- **Passwords**: Argon2id or bcrypt, length rules over composition rules, check against breached-password lists, never log them.
- **Tokens**: short `exp`, pinned algorithms, required `aud` and `iss`, strong secret from a secret store, no sensitive data in claims.
- **Transport**: HTTPS only; never put tokens in URLs, where they end up in logs and the Referer header.
- **Abuse**: rate limit logins and token refreshes, alert on reuse of rotated refresh tokens, and log authentication failures without the credentials.
- **Authorization**: check ownership as well as role (Bob can read his orders, not Jane's), at the query level.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between 401 and 403?">
401 Unauthorized means the request isn't authenticated: no credentials, or invalid or expired ones, and it should include a WWW-Authenticate header. 403 Forbidden means the caller is authenticated but not allowed to perform the action.
</QA>

<QA q="Is a JWT encrypted? What does the signature guarantee?">
A standard signed JWT (JWS) is only base64url encoded, so anyone can read the claims. The signature guarantees integrity and origin: the claims haven't been changed and were issued by someone holding the key.
</QA>

<QA q="What is the alg none attack and how do you prevent it?">
An attacker sends a token whose header says alg none with no signature, hoping the server trusts the header and skips verification. Prevent it by always passing an explicit list of accepted algorithms when decoding.
</QA>

<QA q="How do you revoke JWTs?">
Keep access tokens short-lived, and add server-side state where needed: check the user's status or a tokens-valid-after timestamp on each request, keep a denylist of revoked jti values until they expire, and revoke refresh tokens in the database.
</QA>

<QA q="Why rotate refresh tokens?">
Each refresh token works once and is replaced, so a stolen refresh token has a short useful life, and if the old token is presented again the server detects reuse and can revoke the whole session.
</QA>

</DeepDive>
