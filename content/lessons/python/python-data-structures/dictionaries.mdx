<BigIdea>
<Tr>
<En>
A **dictionary** (`dict`) stores **key: value pairs**: `{"name": "jane", "role": "admin"}`. Instead of asking "what's at position 2?", you ask "what's the value for `role`?", and Python finds it almost instantly no matter how big the dict is, because keys are **hashed**. Keys must be **unique** and **hashable** (strings, numbers, tuples; not lists), while values can be anything, including lists and other dicts. Reading with `d[key]` raises **KeyError** if the key is missing; `d.get(key, default)` returns a default instead. Dicts are **mutable** and **keep insertion order**. You loop over `d.items()` for key and value together. Dicts are the backbone of Python data work: **counting** occurrences, **grouping** records by a field, caching, configuration, and **JSON**, which turns into nested dicts and lists with `json.loads`. The `collections` module adds two shortcuts: **`Counter`** for counting and **`defaultdict`** for grouping without checking whether a key exists.
</En>
<Ur>
**Dictionary** (`dict`) **key: value jore** rakhti hai: `{"name": "jane", "role": "admin"}`. "Jagah 2 par kya hai?" poochne ke bajaye aap poochte hain "`role` ki value kya hai?", aur Python ise takreeban foran dhoond leta hai chahe dict kitni bari ho, kyunke keys **hash** hoti hain. Keys **munfarid** aur **hashable** honi chahiyen (strings, numbers, tuples; lists nahi), jabke values kuch bhi ho sakti hain, lists aur doosri dicts samait. `d[key]` se parhna key ghayab ho to **KeyError** deta; `d.get(key, default)` is ke bajaye default lautata hai. Dicts **mutable** hain aur **daakhil hone ki tarteeb rakhti** hain. Key aur value saath lene ke liye `d.items()` par loop chalate hain. Dicts Python data kaam ki reerh hain: waqiat ki **ginti**, kisi field se records ka **group**, caching, configuration, aur **JSON**, jo `json.loads` se nested dicts aur lists ban jata hai. `collections` module do shortcuts deta hai: ginti ke liye **`Counter`** aur key ki mojoodgi check kiye baghair grouping ke liye **`defaultdict`**.
</Ur>

## Picture it

<Tr>
<En>

Think of a **real dictionary or a phone book**.

- You look up a word (the key) and read its definition (the value); you never start at page 1 and read every entry.
- Each word appears once; writing a new definition for an existing word replaces the old one.
- A word that isn't in the book can't be read (KeyError); `.get()` is saying "if it's not there, use this instead".
- A `defaultdict(list)` is a filing cabinet that creates a new empty folder the moment you file something under a new label.

</En>
<Ur>

**Asal lughat ya phone book** socheyn.

- Aap lafz (key) dhoondte aur us ki tareef (value) parhte hain; kabhi safa 1 se shuru kar ke har entry nahi parhte.
- Har lafz ek dafa aata hai; mojooda lafz ki nayi tareef likhna purani ki jagah le leta hai.
- Jo lafz kitaab me nahi woh parha nahi ja sakta (KeyError); `.get()` kehna hai "agar nahi to is ke bajaye ye lo".
- `defaultdict(list)` aisi filing cabinet hai jo naye label ke neeche kuch file karte hi naya khaali folder bana deti hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Create, read, change, loop and merge">

<Tr>
<En>
`dicts.py` creates a user record and reads it, triggers a KeyError and avoids it with `.get()`, adds, changes and removes keys, loops over a dictionary of plan limits, merges default settings with overrides in two ways, builds dicts from `zip`, keyword arguments and a comprehension, and uses `setdefault` to collect tags per host.
</En>
<Ur>
`dicts.py` user record bana kar parhti, KeyError chhedti aur `.get()` se bachti, keys jorti, badalti aur hatati, plan limits ki dictionary par loop chalati, default settings ko overrides se do tareeqon se milati, `zip`, keyword arguments aur comprehension se dicts banati, aur `setdefault` se har host ke tags jama karti hai.
</Ur>
</Tr>

```bash
cat > dicts.py <<'EOF'
user = {"name": "jane", "role": "admin", "mfa": True}      # key: value pairs
print(user["role"], len(user), "role" in user, "admin" in user)   # `in` checks KEYS

# Missing keys: [] raises, .get() returns a default
try:
    user["email"]
except KeyError as e:
    print("KeyError:", e)
print(user.get("email"), user.get("email", "no email"))

# Add, change, remove
user["email"] = "jane@example.com"        # add a new key
user["role"] = "owner"                    # change an existing one
removed = user.pop("mfa")                 # remove and return
del user["email"]
print(user, "| popped:", removed, "| pop with default:", user.pop("phone", None))

# Insertion order is kept; iterate keys, values or both
limits = {"free": 100, "pro": 10_000}
limits["team"] = 50_000
print(list(limits), list(limits.values()), list(limits.items()))
for plan, limit in limits.items():
    print(f"{plan}: {limit:,}")

# Merging: later values win
defaults = {"timeout": 30, "retries": 3, "verbose": False}
overrides = {"retries": 5, "verbose": True}
print(defaults | overrides)
config = dict(defaults); config.update(overrides, region="us-east-1")
print(config)

# Building dicts
ports = dict(zip(["ssh", "http", "https"], [22, 80, 443]))
print(ports, dict(ssh=22), {p: n for p, n in ports.items() if n < 100})

# setdefault: get the value, inserting a default first if the key is missing
tags = {}
tags.setdefault("web1", []).append("prod")
tags.setdefault("web1", []).append("eu")
print(tags)
EOF
python3 dicts.py
```

<Happened>
<Tr>
<En>

- `"role" in user` was **True** but `"admin" in user` was **False**: `in` checks **keys**, not values. Use `"admin" in user.values()` for values.
- `user["email"]` raised **KeyError: 'email'**, while `.get("email")` returned **None** and `.get("email", "no email")` the default. Use `[]` when a missing key is a bug, `.get()` when it's normal.
- Assigning to a new key **added** it; assigning to an existing key **replaced** the value. `pop` returned the removed value (**True**), and `pop("phone", None)` returned the default instead of raising.
- The dict **kept insertion order**: "team" came last because it was added last. `.items()` gave key-value pairs for the loop.
- `defaults | overrides` built a **new** dict where the overrides won (`retries` 5, `verbose` True); `.update()` did the same in place and accepted extra keyword arguments.
- `dict(zip(...))` paired two lists into a dict, and the comprehension kept only ports below 100.
- `setdefault("web1", [])` returned the existing list or inserted a new empty one, so both tags landed in the same list.

</En>
<Ur>

- `"role" in user` **True** tha magar `"admin" in user` **False**: `in` **keys** check karta hai, values nahi. Values ke liye `"admin" in user.values()` lein.
- `user["email"]` ne **KeyError: 'email'** diya, jabke `.get("email")` ne **None** aur `.get("email", "no email")` ne default lautaya. Jab ghayab key bug ho to `[]`, jab aam baat ho to `.get()` lein.
- Nayi key par assign ne use **joraa**; mojooda key par assign ne value **badli**. `pop` ne hatayi value (**True**) lautayi, aur `pop("phone", None)` ne error ke bajaye default lautaya.
- Dict ne **daakhil hone ki tarteeb rakhi**: "team" aakhir me aaya kyunke aakhir me jora gaya. `.items()` ne loop ke liye key-value jore diye.
- `defaults | overrides` ne **nayi** dict banayi jis me overrides jeete (`retries` 5, `verbose` True); `.update()` ne yahi apni jagah kiya aur izafi keyword arguments bhi liye.
- `dict(zip(...))` ne do lists jor kar dict banayi, aur comprehension ne sirf 100 se neeche wale ports rakhe.
- `setdefault("web1", [])` ne mojooda list lautayi ya nayi khaali daali, isliye dono tags ek hi list me pohanche.

</Ur>

<Step title="Counting, grouping, sorting and nested JSON">

<Tr>
<En>
`patterns.py` takes a list of `(user, event)` pairs and counts failed logins per user by hand, then counts event types with `Counter`. It groups events by user with `defaultdict(list)`, sorts the counts by value, inverts a small mapping, parses a nested JSON API response, reads deep values directly and safely, changes it, turns part of it back into JSON text, and shows why a list can't be a key.
</En>
<Ur>
`patterns.py` `(user, event)` joron ki list leti aur har user ke failed logins haath se ginti, phir `Counter` se event types ginti hai. `defaultdict(list)` se events ko user ke hisaab se group karti, ginti ko value se sort karti, chhoti mapping ulti karti, nested JSON API response parse karti, gehri values seedhe aur mehfooz tareeqe se parhti, use badalti, us ka hissa wapas JSON text banati, aur dikhati hai ke list key kyun nahi ban sakti.
</Ur>
</Tr>

```bash
cat > patterns.py <<'EOF'
import json
from collections import Counter, defaultdict

events = [("jane", "login_failed"), ("john", "login_ok"), ("jane", "login_failed"),
          ("ana", "login_failed"), ("jane", "login_ok"), ("ana", "login_failed")]

# 1. Counting, by hand and with Counter
fails = {}
for user, kind in events:
    if kind == "login_failed":
        fails[user] = fails.get(user, 0) + 1
print(fails)
c = Counter(kind for _, kind in events)
print(c, c.most_common(1), c["missing"])

# 2. Grouping with defaultdict(list)
by_user = defaultdict(list)
for user, kind in events:
    by_user[user].append(kind)
print(dict(by_user))

# 3. Sorting a dict by value, inverting it
print(sorted(fails.items(), key=lambda kv: kv[1], reverse=True))
print({v: k for k, v in {"ssh": 22, "https": 443}.items()})

# 4. Nested data from an API (JSON -> dicts and lists)
body = '''{"user": {"id": 42, "name": "jane", "roles": ["admin", "billing"],
           "address": {"city": "Austin", "zip": "78701"}},
           "meta": {"request_id": "req-9f2"}}'''
data = json.loads(body)
print(data["user"]["roles"][0], data["user"]["address"]["city"])
print(data["user"].get("phone", "n/a"), data.get("paging", {}).get("next"))   # safe nested access
data["user"]["roles"].append("support")
print(json.dumps({"id": data["user"]["id"], "roles": data["user"]["roles"]}))      # back to JSON text

# 5. Keys must be hashable
try:
    {["a"]: 1}
except TypeError as e:
    print("TypeError:", e)
EOF
python3 patterns.py
```

<Happened>
<Tr>
<En>

- `fails[user] = fails.get(user, 0) + 1` is the classic counting idiom: **jane 2, ana 2**, and john never appears because he never failed.
- `Counter` did the same in one line, sorted its display by count, offered `most_common(1)`, and returned **0** for a missing key instead of raising.
- `defaultdict(list)` created an empty list the first time each user appeared, so `by_user[user].append(...)` never needed an `if`.
- `sorted(fails.items(), key=lambda kv: kv[1], reverse=True)` ranked users by count; a dict comprehension `{v: k for k, v in ...}` swapped keys and values (only safe when values are unique).
- `json.loads` turned the JSON text into **nested dicts and lists**: `data["user"]["roles"][0]` is **admin** and `data["user"]["address"]["city"]` is **Austin**.
- `.get("phone", "n/a")` handled a missing field, and `data.get("paging", {}).get("next")` returned **None** instead of crashing when a whole section was missing. APIs leave fields out; code for it.
- The nested list was changed in place (`append("support")`), and `json.dumps` turned the data back into **JSON text**.
- A list as a key raised **unhashable type: 'list'**; use a tuple.

</En>
<Ur>

- `fails[user] = fails.get(user, 0) + 1` ginti ka mash-hoor tareeqa hai: **jane 2, ana 2**, aur john kabhi nahi aata kyunke kabhi nakam nahi hua.
- `Counter` ne yahi ek line me kiya, display ginti se sort kiya, `most_common(1)` diya, aur ghayab key par error ke bajaye **0** lautaya.
- `defaultdict(list)` ne har user ke pehli dafa aane par khaali list banayi, isliye `by_user[user].append(...)` ko kabhi `if` nahi chahiye tha.
- `sorted(fails.items(), key=lambda kv: kv[1], reverse=True)` ne users ko ginti se darja diya; dict comprehension `{v: k for k, v in ...}` ne keys aur values adal badal kin (sirf tab mehfooz jab values munfarid hon).
- `json.loads` ne JSON text ko **nested dicts aur lists** banaya: `data["user"]["roles"][0]` **admin** aur `data["user"]["address"]["city"]` **Austin** hai.
- `.get("phone", "n/a")` ne ghayab field sambhali, aur `data.get("paging", {}).get("next")` ne poora hissa ghayab hone par crash ke bajaye **None** lautaya. APIs fields chhor deti hain; is ke liye code likhein.
- Nested list apni jagah badli (`append("support")`), aur `json.dumps` ne data wapas **JSON text** banaya.
- Key ki tarah list ne **unhashable type: 'list'** diya; tuple lein.

## Common mistakes

<Compare>
<Bad title="Crashing on missing keys from external data">

```text
resp = requests.get(url, timeout=5).json()
email = resp["user"]["email"]          # KeyError the day the API omits email
for item in resp["items"]:             # KeyError when there are no items
    ...
```

</Bad>
<Good title="Expect missing fields">

```text
resp = requests.get(url, timeout=5).json()
email = resp.get("user", {}).get("email")
if email is None:
    log.warning("user has no email")
for item in resp.get("items", []):
    ...
```

</Good>
</Compare>

<Compare>
<Bad title="Changing a dict while looping over it">

```text
for ip, n in counts.items():
    if n < 3:
        del counts[ip]        # RuntimeError: dictionary changed size during iteration
```

</Bad>
<Good title="Build a new dict (or loop over a copy)">

```text
counts = {ip: n for ip, n in counts.items() if n >= 3}
# or: for ip in list(counts): ...
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`in` on a dict expecting values**: it checks keys.
- **Inverting a dict with duplicate values**: later keys silently overwrite earlier ones.
- **Using a dict where a set is enough**: `{ip: True}` just to remember IPs; use a set.
- **Relying on `json.loads` types**: JSON numbers may be int or float, and keys are always strings (`{"1": ...}`, not `{1: ...}`).
- **Deeply nested `["a"]["b"]["c"]` chains everywhere**: extract once into named variables or a small function.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Dict par `in` se values ki tawaqqo**: ye keys check karta hai.
- **Duplicate values wali dict ulti karna**: baad ki keys khamoshi se pehle walon ko mita deti hain.
- **Jahan set kaafi ho wahan dict**: sirf IPs yaad rakhne ke liye `{ip: True}`; set lein.
- **`json.loads` ki types par bharosa**: JSON numbers int ya float ho sakte, aur keys hamesha strings hoti hain (`{"1": ...}`, `{1: ...}` nahi).
- **Har jagah gehri `["a"]["b"]["c"]` zanjeeren**: ek dafa naam wale variables ya chhote function me nikal lein.

</Ur>
</Tr>

<Tr>
<En>
From `statuses = [200, 404, 200, 500, 200, 404, 301, 200]`, use a `Counter` to print each status with its count, most common first, and then the percentage of requests that were errors (status 400 or more), with one decimal.

```text
from collections import Counter
statuses = [200, 404, 200, 500, 200, 404, 301, 200]
counts = Counter(statuses)
for status, n in counts.most_common():
    print(status, n)
errors = sum(n for status, n in counts.items() if status >= 400)
print(f"errors: {errors / len(statuses):.1%}")

# 200 4
# 404 2
# 500 1
# 301 1
# errors: 37.5%
```

<DeepDive title="More about dictionaries">

**How they work.** A dict is a hash table: Python hashes the key to find a slot directly, giving average constant-time lookups, inserts and deletes. Two keys that compare equal must have equal hashes, which is why mutable objects can't be keys.

**Views.** `keys()`, `values()` and `items()` return live views that reflect later changes; `keys()` and `items()` even support set operations like `d1.keys() & d2.keys()`.

**Counter arithmetic.** Counters can be added and subtracted (`c1 + c2`), and `c.update(more_items)` adds counts.

**Other mappings.** `collections.OrderedDict` (move_to_end, for LRU caches), `ChainMap` for layered config, `types.MappingProxyType` for a read-only view.

**Typed dicts.** `typing.TypedDict` documents the expected keys of JSON-like dicts for type checkers; Pydantic validates them at run time.

</DeepDive>

<DeepDive title="Real world: the KeyError at 2 a.m.">

A monitoring script read cloud instances from an API and built a report with `inst["tags"]["Owner"]`. It ran fine for months until someone launched an instance without tags. The API omitted the `tags` key entirely, the script crashed with KeyError on that one instance, and the whole nightly report, including alerts for other instances, was never sent.

The fixes:

1. `owner = inst.get("tags", {}).get("Owner", "unassigned")` for optional data.
2. Per-item error handling: one bad record is logged and skipped, not fatal for the batch.
3. A data model (TypedDict or Pydantic) that documents which fields are optional.
4. A test with a minimal instance record that has no optional fields.

</DeepDive>

<DeepDive title="Security lens">

- **Don't trust keys from users**: merging a request body into a config or user record (`user.update(request.json)`) lets attackers set fields like `is_admin`; copy only allowed keys.
- **Hash flooding**: Python randomises string hashes per process to stop attackers forcing collisions; don't disable it.
- **Validate JSON shape** before use: missing keys, wrong types and huge nested structures from untrusted sources.
- **Don't log whole dicts** that may contain passwords or tokens; log selected keys.
- **Counters for detection**: counting failures per IP or per user is the basis of brute-force detection and rate limiting.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How is a Python dict implemented and what is its lookup complexity?">
As a hash table; lookups, inserts and deletes are O(1) on average, degrading only with many hash collisions.
</QA>

<QA q="What is the difference between d[key] and d.get(key)?">
d[key] raises KeyError if the key is missing; d.get(key, default) returns the default, None if not given.
</QA>

<QA q="Are dicts ordered?">
Yes. Since Python 3.7 dicts preserve insertion order as part of the language specification.
</QA>

<QA q="When would you use defaultdict or Counter?">
defaultdict when grouping or accumulating so missing keys get a starting value automatically; Counter for counting hashable items, with most_common and arithmetic helpers.
</QA>

<QA q="Why can't a list be a dictionary key?">
Keys must be hashable with a hash that never changes; lists are mutable, so their contents and hash could change after insertion and the key could no longer be found.
</QA>

</DeepDive>
