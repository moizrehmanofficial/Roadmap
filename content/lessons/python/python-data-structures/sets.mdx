<BigIdea>
<Tr>
<En>
A **set** is an **unordered** collection of **unique**, hashable items: `{22, 80, 443}`. Add something that's already there and nothing happens, so turning a list into a set **removes duplicates** in one step. Like dictionary keys, set items are hashed, which makes **membership tests** (`x in s`) take about the same tiny time whether the set has ten items or ten million, while searching a list gets slower as it grows. Sets also do **set maths** directly: `a | b` (**union**, everything in either), `a & b` (**intersection**, in both), `a - b` (**difference**, in a but not b), `a ^ b` (**symmetric difference**, in exactly one), plus `<=` for **subset** and `isdisjoint()`. That's exactly the language of audits: "which open ports are not allowed?" is `open_ports - allowed`, and "who gained admin since last month?" is `today - last_month`. The trade-offs: sets have **no order** and **no indexing**, can only hold hashable items, and `{}` is an empty **dict**, so an empty set is written `set()`. A **frozenset** is an immutable set that can itself be a dict key or set item.
</En>
<Ur>
**Set** **munfarid**, hashable items ka **be-tarteeb** majmua hai: `{22, 80, 443}`. Pehle se mojood cheez jorein to kuch nahi hota, isliye list ko set banana ek qadam me **duplicates hata** deta hai. Dictionary keys ki tarah set items hash hote hain, jis se **mojoodgi ke test** (`x in s`) takreeban utna hi chhota waqt lete hain chahe set me das items hon ya das million, jabke list me talash barhne ke saath sust hoti hai. Sets seedha **set ka hisaab** bhi karte hain: `a | b` (**union**, dono me se kisi me), `a & b` (**intersection**, dono me), `a - b` (**difference**, a me magar b me nahi), `a ^ b` (**symmetric difference**, bilkul ek me), aur **subset** ke liye `<=` aur `isdisjoint()`. Ye bilkul audits ki zubaan hai: "kaunse khule ports ijazat yafta nahi?" `open_ports - allowed` hai, aur "pichhle mahine se kis ko admin mila?" `today - last_month` hai. Qeemat: sets ki **koi tarteeb nahi** aur **indexing nahi**, sirf hashable items rakh sakte hain, aur `{}` khaali **dict** hai, isliye khaali set `set()` likha jata hai. **frozenset** immutable set hai jo khud dict key ya set item ban sakta hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of **guest lists drawn as circles** (a Venn diagram).

- One circle is last month's admins, the other is today's. Where they overlap is everyone who kept access (intersection); the part only in last month's circle is who was removed (difference); the part only in today's is who was added.
- Writing a name twice in a circle doesn't put the person there twice (uniqueness).
- Asking "is Bob on the list?" means checking one spot on an alphabetical index, not reading the whole list (fast membership).
- There's no "first" or "third" guest in a circle (no order, no indexing).

</En>
<Ur>

**Daairon ki shakal me mehmanon ki lists** socheyn (Venn diagram).

- Ek daaira pichhle mahine ke admins, doosra aaj ke. Jahan dono milte hain woh sab hain jin ki access rahi (intersection); jo hissa sirf pichhle mahine ke daaire me hai woh hataye gaye (difference); jo sirf aaj ke me hai woh jore gaye.
- Daaire me naam do dafa likhna shakhs ko do dafa nahi rakhta (munfaridiyat).
- "Kya Bob list par hai?" poochna alphabetical index ki ek jagah dekhna hai, poori list parhna nahi (tez mojoodgi).
- Daaire me koi "pehla" ya "teesra" mehman nahi (tarteeb nahi, indexing nahi).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Creating sets, adding and removing, and set maths">

<Tr>
<En>
`sets.py` removes duplicate IPs, shows that `{}` is a dict while `set()` is an empty set, adds and removes ports (including the difference between `discard` and `remove`), then compares last month's and today's access lists with every set operator. It also shows that lists can't go in sets and uses frozensets as dictionary keys. Because sets have no order, every result is printed through `sorted()` so the output is the same on every run.
</En>
<Ur>
`sets.py` duplicate IPs hatati, dikhati hai ke `{}` dict hai jabke `set()` khaali set, ports jorti aur hatati (`discard` aur `remove` ka farq samait), phir har set operator se pichhle mahine aur aaj ki access lists milati hai. Ye bhi dikhati hai ke lists sets me nahi ja saktin aur frozensets ko dictionary keys banati hai. Kyunke sets ki tarteeb nahi, har natija `sorted()` se print hota hai taa ke har dafa output wahi ho.
</Ur>
</Tr>

```bash
cat > sets.py <<'EOF'
# A set holds UNIQUE items with NO order. We print sorted(...) so the output is predictable.
ips = ["203.0.113.7", "198.51.100.4", "203.0.113.7", "192.0.2.10", "203.0.113.7"]
unique = set(ips)
print(len(ips), "->", len(unique), sorted(unique))

ports = {22, 80, 443}                     # literal with braces
empty = set()                             # {} would be an empty DICT
print(type(empty).__name__, type({}).__name__)

ports.add(8080); ports.add(22)            # adding an existing item does nothing
ports.discard(9999)                       # no error if missing
try:
    ports.remove(9999)                    # KeyError if missing
except KeyError as e:
    print("KeyError:", e)
print(sorted(ports), 443 in ports, 21 not in ports)

# Set maths
a = {"jane", "john", "ana"}               # had access last month
b = {"john", "ana", "bob"}                # have access now
print("union        a | b:", sorted(a | b))
print("intersection a & b:", sorted(a & b))
print("difference   a - b:", sorted(a - b), "| b - a:", sorted(b - a))
print("symmetric    a ^ b:", sorted(a ^ b))
print({"john"} <= a, a >= {"jane", "ana"}, a.isdisjoint({"zed"}))

# Only hashable items; frozenset is an immutable (and hashable) set
try:
    {[1, 2]}
except TypeError as e:
    print("TypeError:", e)
groups = {frozenset({"read"}): "viewer", frozenset({"read", "write"}): "editor"}
print(groups[frozenset({"write", "read"})])
EOF
python3 sets.py
```

<Happened>
<Tr>
<En>

- Five IPs became **three unique** ones. If you printed the set directly, the order could differ between runs: string hashes are randomised per process. Use `sorted()` whenever order matters for output.
- `type({})` is **dict**: write `set()` for an empty set.
- Adding 22 again changed nothing. `discard(9999)` quietly did nothing, while `remove(9999)` raised **KeyError**; pick `remove` when a missing item is a bug.
- With `a` as last month's users and `b` as today's: union **ana, bob, jane, john**; intersection **ana, john** (kept access); `a - b` **jane** (removed); `b - a` **bob** (added); symmetric difference **bob, jane** (changed either way).
- `{"john"} <= a` (subset), `a >= {...}` (superset) and `isdisjoint` all returned **True**.
- A list inside a set raised **unhashable type: 'list'**. `frozenset({"write", "read"})` found the **editor** entry even though the items were written in a different order: sets compare by content.

</En>
<Ur>

- Paanch IPs **teen munfarid** ban gaye. Agar set seedha print karte to har run me tarteeb mukhtalif ho sakti thi: string hashes har process me random hote hain. Jab output me tarteeb maayne rakhe to `sorted()` lein.
- `type({})` **dict** hai: khaali set ke liye `set()` likhein.
- 22 dobara jorne se kuch nahi badla. `discard(9999)` ne khamoshi se kuch nahi kiya, jabke `remove(9999)` ne **KeyError** diya; jab ghayab item bug ho to `remove` chunein.
- `a` pichhle mahine ke aur `b` aaj ke users: union **ana, bob, jane, john**; intersection **ana, john** (access rahi); `a - b` **jane** (hataya gaya); `b - a` **bob** (joraa gaya); symmetric difference **bob, jane** (kisi bhi taraf badle).
- `{"john"} <= a` (subset), `a >= {...}` (superset) aur `isdisjoint` sab ne **True** lautaya.
- Set ke andar list ne **unhashable type: 'list'** diya. `frozenset({"write", "read"})` ne alag tarteeb me likhe items ke bawajood **editor** entry dhoond li: sets mawad se milte hain.

</Ur>

<Step title="Audits, speed, ordered de-duplication and set comprehensions">

<Tr>
<En>
`audit.py` compares ports found open by a scan with an allow-list, compares two snapshots of an admin group, measures membership lookups in a 100,000-item list versus a set with `timeit`, removes duplicate events two ways (one keeps the original order), and collects unique email domains with a set comprehension.
</En>
<Ur>
`audit.py` scan me khule mile ports ko allow-list se milati, admin group ke do snapshots milati, `timeit` se 100,000 items ki list aur set me mojoodgi ki talash naapti, duplicate events do tareeqon se hatati (ek asal tarteeb rakhta hai), aur set comprehension se munfarid email domains jama karti hai.
</Ur>
</Tr>

```bash
cat > audit.py <<'EOF'
import timeit

# 1. Firewall audit: what's open that shouldn't be, and what's missing?
allowed = {22, 80, 443}
scan_results = [443, 80, 3306, 22, 6379, 3306]           # ports found open (with a duplicate)
open_ports = set(scan_results)
print("unexpected open:", sorted(open_ports - allowed))
print("allowed but closed:", sorted(allowed - open_ports))
print("all good?", open_ports <= allowed)

# 2. Access review: compare two snapshots of an admin group
last_month = {"jane", "john", "ana", "contractor-01"}
today = {"jane", "ana", "bob"}
print("removed:", sorted(last_month - today), "| added:", sorted(today - last_month))

# 3. Membership speed: a set lookup doesn't slow down as the collection grows
items = list(range(100_000))
as_list, as_set = items, set(items)
t_list = timeit.timeit(lambda: 99_999 in as_list, number=200)
t_set = timeit.timeit(lambda: 99_999 in as_set, number=200)
print("set lookup at least 100x faster:", t_list / t_set > 100)

# 4. Remove duplicates but KEEP the original order (sets don't keep order; dicts do)
events = ["login", "view", "login", "export", "view", "logout"]
print(sorted(set(events)), "<- order lost")
print(list(dict.fromkeys(events)), "<- first-seen order kept")

# 5. Set comprehension: unique email domains
emails = ["jane@example.com", "JOHN@Example.com", "ana@corp.example", "bob@example.com"]
print(sorted({e.split("@")[1].lower() for e in emails}))
EOF
python3 audit.py
```

```text output
unexpected open: [3306, 6379]
allowed but closed: []
all good? False
removed: ['contractor-01', 'john'] | added: ['bob']
set lookup at least 100x faster: True
['export', 'login', 'logout', 'view'] <- order lost
['login', 'view', 'export', 'logout'] <- first-seen order kept
['corp.example', 'example.com']
```

<Happened>
<Tr>
<En>

- `open_ports - allowed` found **3306 and 6379** (MySQL and Redis exposed): two findings for a report. `allowed - open_ports` was empty, and `open_ports <= allowed` gave a single yes/no answer for the whole audit (**False**).
- The access review found **contractor-01 and john removed** and **bob added** in one line each. The same pattern compares installed packages, firewall rules or files between two dates.
- Looking for the last number in a 100,000-item list means checking every item; the set jumps straight to it. The set was **more than 100 times faster** (in practice usually thousands of times), and the gap grows with size. If you check `in` inside a loop, make the collection a set first.
- `set(events)` lost the order of first appearance; `list(dict.fromkeys(events))` kept it (**login, view, export, logout**), because dicts remember insertion order.
- The set comprehension lower-cased each domain, so `Example.com` and `example.com` counted once: **corp.example, example.com**.

</En>
<Ur>

- `open_ports - allowed` ne **3306 aur 6379** dhoonde (MySQL aur Redis khule): report ke liye do nataij. `allowed - open_ports` khaali tha, aur `open_ports <= allowed` ne poore audit ka ek haan/nahi jawab diya (**False**).
- Access review ne ek ek line me **contractor-01 aur john hataye gaye** aur **bob joraa gaya** dhoonda. Yahi pattern do taareekhon ke beech installed packages, firewall rules ya files milata hai.
- 100,000 items ki list me aakhri number dhoondne ka matlab har item check karna hai; set seedha us tak pohanchta hai. Set **100 guna se zyada tez** tha (amalan aksar hazaron guna), aur farq size ke saath barhta hai. Agar loop ke andar `in` check karte hain to pehle collection ko set banayen.
- `set(events)` ne pehli dafa aane ki tarteeb kho di; `list(dict.fromkeys(events))` ne rakhi (**login, view, export, logout**), kyunke dicts daakhil hone ki tarteeb yaad rakhti hain.
- Set comprehension ne har domain chhote haroof me kiya, isliye `Example.com` aur `example.com` ek dafa gine gaye: **corp.example, example.com**.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Membership checks against a list in a loop">

```text
blocked = load_blocklist()            # a list of 200,000 IPs
for line in access_log:               # millions of lines
    if line.ip in blocked:            # scans the whole list every time
        alert(line)
```

</Bad>
<Good title="Convert once, check fast">

```text
blocked = set(load_blocklist())
for line in access_log:
    if line.ip in blocked:            # constant time
        alert(line)
```

</Good>
</Compare>

<Compare>
<Bad title="Relying on set order">

```text
hosts = {"web2", "web1", "db1"}
print(", ".join(hosts))               # order can change between runs
first = list(hosts)[0]                # "first" is meaningless
```

</Bad>
<Good title="Sort for output, use a list when order matters">

```text
print(", ".join(sorted(hosts)))
hosts_in_order = ["web1", "web2", "db1"]
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`{}` for an empty set**: it's a dict; use `set()`.
- **`set("admin")`**: makes a set of characters `{'a', 'd', 'i', 'm', 'n'}`; use `{"admin"}`.
- **Comparing un-normalised values**: `"Admin"` and `"admin "` are different items; strip and lowercase first.
- **Using sets when you need counts**: a set forgets how many times something appeared; use `Counter`.
- **Mutating a set while iterating it**: raises RuntimeError; iterate over a copy or build a new set.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Khaali set ke liye `{}`**: ye dict hai; `set()` lein.
- **`set("admin")`**: characters ka set banata `{'a', 'd', 'i', 'm', 'n'}`; `{"admin"}` lein.
- **Be-normalise values milana**: `"Admin"` aur `"admin "` alag items hain; pehle strip aur lowercase karein.
- **Ginti chahiye to sets**: set bhool jata hai ke kuch kitni dafa aaya; `Counter` lein.
- **Iterate karte hue set badalna**: RuntimeError deta; copy par iterate karein ya naya set banayen.

</Ur>
</Tr>

<Challenge title="First-time visitors">

<Tr>
<En>
Process a stream of visitor IPs `["192.0.2.1", "192.0.2.2", "192.0.2.1", "203.0.113.7", "192.0.2.2", "198.51.100.4"]` in order, and print "new visitor IP" only the first time each IP appears, using a `seen` set. At the end print how many unique visitors there were.
</En>
<Ur>
Visitor IPs ka silsila `["192.0.2.1", "192.0.2.2", "192.0.2.1", "203.0.113.7", "192.0.2.2", "198.51.100.4"]` tarteeb se process karein, aur `seen` set ke zariye har IP ke pehli dafa aane par hi "new visitor IP" print karein. Aakhir me print karein ke kitne munfarid visitors the.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
stream = ["192.0.2.1", "192.0.2.2", "192.0.2.1", "203.0.113.7", "192.0.2.2", "198.51.100.4"]
seen = set()
for ip in stream:
    if ip in seen:
        continue
    seen.add(ip)
```

<DeepDive title="More about sets">

**Methods vs operators.** `a.union(b, c)`, `a.intersection(...)` and `a.difference(...)` accept any iterables (lists too), while the operators need sets on both sides. In-place versions (`|=`, `&=`, `-=`, `update`, `intersection_update`) modify the set.

**Hash randomisation.** `PYTHONHASHSEED` controls string hashing; it's random per process for security, which is why set and dict-key order of strings can't be relied on across runs (dicts keep insertion order, sets don't).

**Equality vs identity.** `1`, `1.0` and `True` are equal and hash the same, so `{1, 1.0, True}` has one element.

**Big data.** For huge sets that don't fit in memory, use a database with a unique index, or probabilistic structures like Bloom filters (which can say "definitely not present" or "probably present").

**Comparing many snapshots.** `set.intersection(*list_of_sets)` finds items present in every snapshot.

</DeepDive>

<DeepDive title="Real world: the slow blocklist">

A log-processing job flagged requests from IPs on a threat-intelligence blocklist of about 300,000 addresses. It was written with the blocklist as a list. On a day with 20 million log lines, each `in` check scanned the list, and the job that used to take minutes ran for more than a day, delaying alerts.

The fixes:

1. Load the blocklist into a `frozenset` once at startup: the job went back to minutes.
2. Normalise IPs (strip whitespace, use `ipaddress.ip_address` to canonicalise) before adding and checking.
3. For blocklists of networks (CIDR ranges), use the `ipaddress` module or a dedicated lookup structure rather than expanding every address.

</DeepDive>

<DeepDive title="Security lens">

- **Allow-lists beat block-lists**: `requested - ALLOWED` finds anything not explicitly permitted.
- **Normalise before set operations**: case, whitespace, trailing dots in hostnames and IP formats can make the same thing look different.
- **Access reviews and drift detection** (users, permissions, open ports, packages) are set differences between "expected" and "actual".
- **Keep constants immutable**: `frozenset` prevents code from accidentally adding to an allow-list at runtime.
- **Don't expose set order** in security-relevant output; sort it so diffs between runs are meaningful.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a set and when would you use one?">
An unordered collection of unique hashable items with fast membership tests. Use it to remove duplicates, check membership often, or compute unions, intersections and differences.
</QA>

<QA q="What is the time complexity of x in s for a set?">
O(1) on average, because sets are hash tables; for a list it's O(n).
</QA>

<QA q="What is a frozenset?">
An immutable set. Because it can't change, it's hashable and can be used as a dictionary key or as an element of another set.
</QA>

<QA q="How do you find items in one list but not another?">
Convert both to sets and subtract: set(a) - set(b), remembering that duplicates and order are lost.
</QA>

<QA q="Why might printing a set of strings give a different order each run?">
String hashes are randomised per process for security, and set iteration order depends on hashes, so the order isn't stable; sort the items when order matters.
</QA>

</DeepDive>
