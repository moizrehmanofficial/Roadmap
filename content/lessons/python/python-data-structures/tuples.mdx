<BigIdea>
<Tr>
<En>
A **tuple** is like a list that's **frozen**: an ordered sequence you can index, slice, loop over and unpack, but can't change. You make one with **commas** (`"web1", "203.0.113.10", 443`), usually wrapped in parentheses for clarity; a single-item tuple needs a trailing comma, `("admin",)`. Because tuples are **immutable**, they say "this group of values belongs together and won't change": a coordinate, an RGB colour, a database row, a host and port. Python uses them everywhere behind the scenes: `a, b = b, a` swaps through a tuple, a function that `return`s several values returns a tuple, and `enumerate`, `zip` and `dict.items()` hand you tuples. Immutability also makes tuples **hashable** (as long as their items are), so they can be **dictionary keys** and **set members**, which lists can't. When positions like `r[2]` get hard to read, a **named tuple** gives each field a name (`login.ip`) while staying a lightweight, immutable tuple.
</En>
<Ur>
**Tuple** list jaisa hai jo **jami hui** ho: tarteeb wali sequence jise index, slice, loop aur unpack kar sakte hain, magar badal nahi sakte. Ise **commas** se banate hain (`"web1", "203.0.113.10", 443`), aam taur par wazahat ke liye qauson me; ek item ke tuple ko aakhir me comma chahiye, `("admin",)`. Kyunke tuples **immutable** hain, woh kehte hain "values ka ye group saath hai aur nahi badlega": coordinate, RGB rang, database row, host aur port. Python unhe parde ke peeche har jagah istemal karta hai: `a, b = b, a` tuple ke zariye adla badli karta, kayi values `return` karne wala function tuple lautata, aur `enumerate`, `zip` aur `dict.items()` aap ko tuples dete hain. Immutability tuples ko **hashable** bhi banati hai (jab tak un ke items hon), isliye woh **dictionary keys** aur **set members** ban sakte hain, jo lists nahi ban saktin. Jab `r[2]` jaisi jagahen parhna mushkil ho, **named tuple** har field ko naam deta hai (`login.ip`) aur halka, immutable tuple hi rehta hai.
</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Creating, unpacking and using tuples as keys">

<Tr>
<En>
`tuples.py` builds tuples with and without parentheses, shows the single-item trap, tries to change one, unpacks a server record, swaps two values, returns three values from a function, uses `(host, port)` tuples as dictionary keys (and tries the same with a list), compares tuples, and shows that a list inside a tuple can still change.
</En>
<Ur>
`tuples.py` qauson ke saath aur baghair tuples banati, ek item ka jaal dikhati, ek ko badalne ki koshish karti, server record unpack karti, do values adal badal karti, function se teen values lautati, `(host, port)` tuples ko dictionary keys banati (aur list ke saath wahi koshish karti), tuples milati, aur dikhati hai ke tuple ke andar list phir bhi badal sakti hai.
</Ur>
</Tr>

```bash
cat > tuples.py <<'EOF'
point = (10, 20)
server = "web1", "203.0.113.10", 443        # the commas make the tuple, not the parentheses
single = ("admin",)                          # one item needs a trailing comma
not_a_tuple = ("admin")
print(type(server).__name__, server[0], server[-1], len(server), type(single).__name__, type(not_a_tuple).__name__)

# Immutable: no changing, adding or removing
try:
    server[2] = 8443
except TypeError as e:
    print("TypeError:", e)
print(hasattr(server, "append"), server.count(443), server.index("203.0.113.10"))

# Unpacking: one name per item
name, ip, port = server
print(f"{name} at {ip}:{port}")
lat, lon = 51.5, -0.12                       # several assignment = tuple packing + unpacking
lat, lon = lon, lat                           # swap
print(lat, lon)

# Functions return several values as a tuple
def min_max_avg(values):
    return min(values), max(values), sum(values) / len(values)
lo, hi, avg = min_max_avg([120, 80, 300, 95])
print(lo, hi, avg, "| the raw return value:", min_max_avg([1, 2]))

# Hashable, so tuples can be dict keys and set members; lists can't
latency = {("web1", 443): 12.5, ("db1", 5432): 3.1}
print(latency[("db1", 5432)], ("web1", 443) in latency)
try:
    {["web1", 443]: 12.5}
except TypeError as e:
    print("TypeError:", e)

# Tuples compare item by item, like words in a dictionary
print((1, 9) < (2, 0), (2, 1) < (2, 3), sorted([(2, "b"), (1, "z"), (2, "a")]))

# Immutable container, but a list inside can still change
t = ("jane", ["admin"])
t[1].append("billing")
print(t)
EOF
python3 tuples.py
```

<Happened>
<Tr>
<En>

- `"web1", "203.0.113.10", 443` without brackets was a **tuple**: the commas make it. `("admin",)` was a tuple, but `("admin")` was just a **str** in parentheses. That missing comma is a classic bug.
- Assigning `server[2] = 8443` raised **TypeError**, and tuples have no `append`. Only `count` and `index` exist.
- `name, ip, port = server` unpacked the record into three readable names; the number of names must match the number of items, or you get a ValueError.
- `min_max_avg` returned **(80, 300, 148.75)** as one tuple, which the caller unpacked into three variables. That's how Python functions "return several values".
- `(host, port)` tuples worked as **dictionary keys**, but a list as a key raised **unhashable type: 'list'**: a key must never change, or the dictionary couldn't find it again.
- Tuples compare **item by item**: `(1, 9) < (2, 0)` because 1 < 2, and sorting tuples sorts by the first item, then the second.
- The tuple holding a list couldn't swap that list for another, but the **list itself changed** to include "billing". Immutability is shallow; such a tuple isn't hashable either.

</En>
<Ur>

- Brackets ke baghair `"web1", "203.0.113.10", 443` **tuple** tha: commas use banate hain. `("admin",)` tuple tha, magar `("admin")` qauson me sirf **str** tha. Ye ghayab comma mash-hoor bug hai.
- `server[2] = 8443` assign karne ne **TypeError** diya, aur tuples ke paas `append` nahi. Sirf `count` aur `index` hain.
- `name, ip, port = server` ne record ko teen parhne layak naamon me khola; naamon ki tadad items ki tadad ke barabar honi chahiye, warna ValueError milta hai.
- `min_max_avg` ne **(80, 300, 148.75)** ek tuple ki tarah lautaya, jise bulane wale ne teen variables me khola. Python functions isi tarah "kayi values lautate" hain.
- `(host, port)` tuples **dictionary keys** ki tarah chale, magar key ki tarah list ne **unhashable type: 'list'** diya: key kabhi nahi badalni chahiye, warna dictionary use dobara dhoondh nahi sakti.
- Tuples **item ba item** milte hain: `(1, 9) < (2, 0)` kyunke 1 < 2, aur tuples sort karna pehle item, phir doosre se sort karta hai.
- List wala tuple us list ko doosri se badal nahi saka, magar **list khud badli** aur "billing" shamil ho gaya. Immutability sathhi hai; aisa tuple hashable bhi nahi.

</Ur>
</Tr>
</Happened>

<Step title="Named tuples for readable records">

<Tr>
<En>
`records.py` contrasts a plain tuple with a `namedtuple`, then defines a typed `Service` record with a default value using `typing.NamedTuple`. It converts a record to a dict, "changes" a field with `_replace`, unpacks it, sorts a list of `Login` records by two fields, shows that `enumerate`, `zip` and `.items()` produce tuples, and compares the size of a tuple and a list.
</En>
<Ur>
`records.py` saade tuple ko `namedtuple` se milati, phir `typing.NamedTuple` se default value ke saath typed `Service` record banati hai. Record ko dict me badalti, `_replace` se field "badalti", use unpack karti, `Login` records ki list do fields se sort karti, dikhati hai ke `enumerate`, `zip` aur `.items()` tuples dete hain, aur tuple aur list ka size milati hai.
</Ur>
</Tr>

```bash
cat > records.py <<'EOF'
from collections import namedtuple
from typing import NamedTuple
import sys

# Plain tuples work, but r[2] doesn't say what it means
row = ("jane", 7, "203.0.113.7")
print("plain:", row[0], row[1])

# namedtuple: a tuple whose fields also have names
Login = namedtuple("Login", ["user", "failures", "ip"])
a = Login("jane", 7, "203.0.113.7")
print(a, "|", a.user, a.failures, "| still a tuple:", a[0], isinstance(a, tuple))

# The typed version (class syntax, with defaults)
class Service(NamedTuple):
    name: str
    port: int
    tls: bool = True

svc = Service("api", 443)
print(svc, svc._asdict())
svc2 = svc._replace(port=8443)            # immutable: _replace returns a NEW record
print(svc2, "| original unchanged:", svc.port)
name, port, tls = svc                      # unpacks like any tuple
print(name, port, tls)

# Records sort and group nicely
logins = [Login("john", 2, "198.51.100.4"), Login("jane", 7, "203.0.113.7"), Login("ana", 7, "192.0.2.10")]
for l in sorted(logins, key=lambda l: (-l.failures, l.user)):
    print(f"{l.user:<5} {l.failures} {l.ip}")

# enumerate, zip and dict.items() all give you tuples
print(list(enumerate(["a", "b"])), list(zip([1, 2], ["x", "y"])), list({"k": "v"}.items()))

# Tuples are a little smaller than lists with the same items
print(sys.getsizeof((1, 2, 3)) < sys.getsizeof([1, 2, 3]))
EOF
python3 records.py
```

<Happened>
<Tr>
<En>

- `row[1]` works but says nothing; the named tuple printed itself as **Login(user='jane', failures=7, ip='203.0.113.7')** and its fields read as `a.user` and `a.failures`. It's still a real tuple: `a[0]` works and `isinstance(a, tuple)` is True.
- The `NamedTuple` class version adds **type hints** and a **default** (`tls: bool = True`), so `Service("api", 443)` filled in `tls=True`.
- `_asdict()` gave a plain dict, handy for `json.dumps`. `_replace(port=8443)` returned a **new** record and left the original at 443.
- Unpacking and sorting work exactly as with plain tuples; the sort key reads clearly as `(-l.failures, l.user)`.
- `enumerate`, `zip` and `.items()` all yield **tuples**, which is why `for i, x in enumerate(...)` unpacks so naturally.
- The tuple was **smaller** than the equivalent list: lists reserve room to grow, tuples don't.

</En>
<Ur>

- `row[1]` chalta hai magar kuch nahi batata; named tuple ne khud ko **Login(user='jane', failures=7, ip='203.0.113.7')** ki tarah print kiya aur us ke fields `a.user` aur `a.failures` ki tarah parhe gaye. Ye ab bhi asal tuple hai: `a[0]` chalta aur `isinstance(a, tuple)` True hai.
- `NamedTuple` class version **type hints** aur **default** (`tls: bool = True`) jorta hai, isliye `Service("api", 443)` ne `tls=True` khud bhara.
- `_asdict()` ne saada dict diya, `json.dumps` ke liye kaam ka. `_replace(port=8443)` ne **naya** record lautaya aur asal ko 443 par chhora.
- Unpacking aur sorting bilkul saade tuples jaise chalte hain; sort key `(-l.failures, l.user)` saaf parhti hai.
- `enumerate`, `zip` aur `.items()` sab **tuples** dete hain, isi liye `for i, x in enumerate(...)` itni qudrati taur par khulta hai.
- Tuple barabar list se **chhota** tha: lists barhne ke liye jagah rakhti hain, tuples nahi.

</Ur>

## Common mistakes

<Compare>
<Bad title="The missing comma">

```text
ALLOWED_ROLES = ("admin")       # a str, not a tuple
if role in ALLOWED_ROLES:       # substring check on "admin"
    ...                         # "ad", "min" and "" all pass!
```

</Bad>
<Good title="Trailing comma, or a set">

```text
ALLOWED_ROLES = ("admin",)      # a one-item tuple
# or, for membership checks:
ALLOWED_ROLES = {"admin"}
if role in ALLOWED_ROLES:
    ...
```

</Good>
</Compare>

<Compare>
<Bad title="Magic indexes">

```text
for r in rows:
    if r[1] > 5 and r[3] != "internal":
        alert(r[0], r[2])
```

</Bad>
<Good title="Unpack or name the fields">

```text
for user, failures, ip, zone in rows:
    if failures > 5 and zone != "internal":
        alert(user, ip)
# or rows of Login(user, failures, ip, zone) and r.failures, r.zone
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Expecting `_replace` to change the tuple in place**: assign the result.
- **Unpacking the wrong number of items**: `a, b = (1, 2, 3)` raises ValueError; use `a, b, *_ = ...` if you mean to ignore extras.
- **Putting mutable items in a tuple used as a key**: it becomes unhashable.
- **Returning long tuples from functions** (`return a, b, c, d, e, f`): return a named tuple or a dataclass instead.
- **Thinking a tuple makes nested data read-only**: only the tuple's own slots are fixed.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`_replace` se tuple apni jagah badalne ki tawaqqo**: natija assign karein.
- **Ghalat tadad ke items unpack karna**: `a, b = (1, 2, 3)` ValueError deta; izafi nazar andaz karne ke liye `a, b, *_ = ...` lein.
- **Key wale tuple me mutable items rakhna**: woh unhashable ho jata hai.
- **Functions se lambe tuples lautana** (`return a, b, c, d, e, f`): named tuple ya dataclass lautayen.
- **Samajhna ke tuple nested data ko read-only banata hai**: sirf tuple ke apne khaane tay hain.

</Ur>
</Tr>

<Challenge title="A Version record">

<Tr>
<En>

</En>
<Ur>
`major`, `minor` aur `patch` ints ke saath `class Version(NamedTuple)` banayen, aur `parse(text)` function jo `"1.10.0"` ko `Version` me badle. `["1.10.0", "1.2.0", "1.9.3", "2.0.0"]` ko un ke parse kiye versions se sort karein aur sab se naye ka `_asdict()` print karein.
</Ur>

<Solution>

<Tr>
<En>

```text
from typing import NamedTuple

class Version(NamedTuple):
    major: int
    minor: int
    patch: int

def parse(text):
    major, minor, patch = (int(p) for p in text.split("."))
    return Version(major, minor, patch)

versions = ["1.10.0", "1.2.0", "1.9.3", "2.0.0"]
ordered = sorted(versions, key=parse)
print(ordered)
print(parse(ordered[-1])._asdict())

# ['1.2.0', '1.9.3', '1.10.0', '2.0.0']
# {'major': 2, 'minor': 0, 'patch': 0}
```

Because a `Version` is a tuple, comparing two versions compares major, then minor, then patch: exactly the right order.

<DeepDive title="More about tuples">

**Hashing.** A tuple's hash is computed from its items, so `hash((1, 2))` is stable within a run; a tuple containing a list raises TypeError when hashed.

**Constants and performance.** CPython stores tuple literals of constants as a single pre-built object, and creating tuples is slightly faster than lists; the bigger benefit is intent and safety.

**Named tuple vs dataclass.** Named tuples are immutable, iterable and compare like tuples; dataclasses are mutable by default (or `frozen=True`), support methods and defaults more flexibly, and don't unpack positionally unless you ask. Choose named tuples for small value records.

**Structural pattern matching.** `match point: case (0, y):` matches tuples by shape, as you saw with lists.

**Returning status pairs.** Patterns like `ok, value = try_parse(text)` are common, but exceptions or `None` are often clearer in Python.

</DeepDive>

<DeepDive title="Real world: the role that matched everything">

An admin panel kept its allowed roles in a constant, `ADMIN_ROLES = ("superadmin")`, and checked `if user.role in ADMIN_ROLES`. Because of the missing comma the constant was a string, so the check became a substring test: users with roles like "admin", "super" or even an empty role string were treated as superadmins. It went unnoticed until a pentest created a user with role "a".

The fixes:

1. `ADMIN_ROLES = frozenset({"superadmin"})`: a set makes the intent obvious and can't be a string by accident.
2. A type checker (mypy) with `ADMIN_ROLES: frozenset[str]`, which flags a str assignment.
3. Tests for roles that must be refused, including empty and partial strings.

</DeepDive>

<DeepDive title="Security lens">

- **Immutable configuration**: storing allow-lists and settings in tuples or frozensets prevents accidental runtime changes.
- **The missing comma** turns a tuple into a string and `in` into a substring check, a real authorization bug.
- **Shallow immutability**: a tuple holding a dict of permissions doesn't protect the dict.
- **Composite keys** like `(user_id, resource_id)` are a clean way to record per-user permissions or rate limits.
- **Don't leak internal structure**: converting records with `_asdict()` to JSON may expose fields you didn't mean to return; choose fields explicitly.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the main differences between lists and tuples?">
Lists are mutable, have many methods and usually hold similar items that change; tuples are immutable, hashable when their items are, slightly smaller and faster, and usually represent fixed records.
</QA>

<QA q="How do you create a tuple with one element?">
With a trailing comma, (x,) or x, because parentheses alone are just grouping.
</QA>

<QA q="Can a tuple contain mutable objects?">
Yes. The tuple can't change which objects it holds, but those objects can change themselves; such a tuple is not hashable.
</QA>

<QA q="What is a namedtuple?">
A factory in collections (or the typing.NamedTuple class syntax) that creates tuple subclasses with named fields, giving readable attribute access, a helpful repr, and helpers like _asdict and _replace.
</QA>

<QA q="How does Python return multiple values from a function?">
It returns a single tuple, which the caller can unpack into several variables.
</QA>

</DeepDive>
