<BigIdea>
<Tr>
<En>
In Python, a variable doesn't contain a value; it **refers** to an object. Assignment (`admins = team`) never copies: it makes a second name for the **same** object. Whether that matters depends on the object's type. **Immutable** objects (int, float, bool, str, tuple, frozenset, None) can't be changed after creation; every "change" builds a new object and moves the name to it, so sharing them is harmless. **Mutable** objects (list, dict, set, and most objects you create) can be changed **in place** with methods like `append`, `update` or `add`, and every name that refers to them sees the change. That gives two different operations: **mutating** an object (everyone sees it) and **rebinding** a name (only that name moves). Functions receive references too, so a function can mutate the list you passed in. When you need independent data, make a **copy**: a **shallow copy** (`.copy()`, `list(x)`, `x[:]`, `dict(x)`) duplicates only the outer container, so nested lists and dicts are still shared; a **deep copy** (`copy.deepcopy`) duplicates everything inside. The same idea explains the famous **mutable default argument** bug: a default like `findings=[]` is created once and shared by every call.
</En>
<Ur>
Python me variable value nahi rakhta; woh kisi object ki taraf **ishara** karta hai. Assignment (`admins = team`) kabhi copy nahi karta: **usi** object ka doosra naam banata hai. Ye maayne rakhta hai ya nahi, object ki type par mabni hai. **Immutable** objects (int, float, bool, str, tuple, frozenset, None) banne ke baad badle nahi ja sakte; har "tabdeeli" naya object banati aur naam ko us par le jati hai, isliye unhe baantna be-zarar hai. **Mutable** objects (list, dict, set, aur aap ke banaye zyadatar objects) `append`, `update` ya `add` jaise methods se **apni jagah** badle ja sakte hain, aur un ki taraf ishara karne wala har naam tabdeeli dekhta hai. Is se do alag kaam bante hain: object ko **mutate** karna (sab dekhte hain) aur naam ko **rebind** karna (sirf woh naam hilta hai). Functions ko bhi references milte hain, isliye function aap ki di hui list mutate kar sakta hai. Jab alag data chahiye to **copy** banayen: **shallow copy** (`.copy()`, `list(x)`, `x[:]`, `dict(x)`) sirf bahar ka container dohrati hai, isliye nested lists aur dicts ab bhi mushtarak rehti hain; **deep copy** (`copy.deepcopy`) andar ka sab dohrati hai. Yahi khayal mash-hoor **mutable default argument** bug samjhata hai: `findings=[]` jaisa default ek dafa banta aur har call me mushtarak hota hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **shared online document**.

- Sending a colleague the link is like `b = a`: there's one document, and when either of you edits it, both see the change.
- Downloading a copy is a copy: edits to your file don't affect theirs.
- A shallow copy is downloading the document when it contains **links to other documents**: you have your own copy of the main page, but the linked pages are still the shared originals. A deep copy downloads every linked page too.
- An immutable object is a printed PDF: nobody can edit it, so sharing it is always safe; "changing" it means printing a new one.

</En>
<Ur>

**Mushtarak online document** socheyn.

- Saathi ko link bhejna `b = a` jaisa hai: document ek hai, aur jab koi bhi edit kare dono tabdeeli dekhte hain.
- Copy download karna copy hai: aap ki file ki edits un ki file par asar nahi kartin.
- Shallow copy aisa document download karna hai jis me **doosre documents ke links** hon: main page ki apni copy hai, magar linked pages ab bhi mushtarak asal hain. Deep copy har linked page bhi download karti hai.
- Immutable object chhapa hua PDF hai: koi edit nahi kar sakta, isliye baantna hamesha mehfooz; "badalne" ka matlab naya chhapna hai.

## Learn it step by step

<Walkthrough>

<Step title="References, mutating and rebinding">

<Tr>
<En>
`refs.py` gives one list two names and appends through one of them, then rebinds one name. It "changes" an int and a string to show new objects are created, compares `+=` on a list with `+=` on a tuple when another name refers to the original, passes a list to one function that mutates it and another that rebinds its parameter, and lists which built-in types are mutable.
</En>
<Ur>
`refs.py` ek list ko do naam deti aur ek ke zariye append karti, phir ek naam rebind karti hai. Int aur string ko "badal" kar dikhati ke naye objects bante hain, doosre naam ke asal ki taraf ishara karte hue list par `+=` ko tuple par `+=` se milati, ek list aise function ko deti jo use mutate kare aur doosre ko jo apna parameter rebind kare, aur batati hai ke kaunsi built-in types mutable hain.
</Ur>
</Tr>

```bash
cat > refs.py <<'EOF'
# Names are references. Mutating an object is visible through every name that refers to it.
team = ["jane", "john"]
admins = team                         # same object
admins.append("ana")
print(team, team is admins, id(team) == id(admins))

# Rebinding a name never affects other names
admins = ["bob"]                      # admins now points somewhere else
print(team, admins, team is admins)

# Immutable objects can't be changed, so "changing" them makes a new object
count = 10
before = id(count)
count += 1                            # a NEW int; the name moves to it
print(count, id(count) == before)

name = "jane"
upper = name.upper()                  # a new string; the original is untouched
print(name, upper)

# += on a list MUTATES it (in place); on a tuple or str it REBINDS
nums = [1, 2]
alias = nums
nums += [3]
print(nums, alias, nums is alias)
t = (1, 2)
alias_t = t
t += (3,)
print(t, alias_t, t is alias_t)

# Functions receive references: they can mutate your list, but rebinding inside stays inside
def add_audit_tag(tags):
    tags.append("audited")            # mutates the caller's list
def replace_tags(tags):
    tags = ["new"]                    # rebinds the local name only
mine = ["prod"]
add_audit_tag(mine); replace_tags(mine)
print(mine)

print("mutable:", [type(x).__name__ for x in ([], {}, set())], "| immutable:", [type(x).__name__ for x in (1, 1.5, "s", (1,), frozenset(), True, None)])
EOF
python3 refs.py
```

```text output
['jane', 'john', 'ana'] True True
['jane', 'john', 'ana'] ['bob'] False
11 False
jane JANE
[1, 2, 3] [1, 2, 3] True
(1, 2, 3) (1, 2) False
['prod', 'audited']
mutable: ['list', 'dict', 'set'] | immutable: ['int', 'float', 'str', 'tuple', 'frozenset', 'bool', 'NoneType']
```

<Happened>
<Tr>
<En>

- `admins = team` made an **alias**: appending "ana" through `admins` showed up in `team`, and `is` and `id()` confirmed it's **one object**.
- `admins = ["bob"]` **rebound** only `admins`; `team` kept its list. Mutation affects the object; assignment affects the name.
- `count += 1` created a **new int** (the id changed), and `name.upper()` returned a new string while `name` stayed "jane": immutable objects never change under you.
- For the list, `nums += [3]` **mutated** in place, so `alias` saw `[1, 2, 3]` and `nums is alias` stayed True. For the tuple, `t += (3,)` built a **new tuple** and rebound `t`; `alias_t` kept `(1, 2)`. The same operator, two behaviours, decided by mutability.
- `add_audit_tag` changed the caller's list (**"audited" appeared**), while `replace_tags` only rebound its local name, so the caller's list was unaffected. Functions that mutate arguments should say so in their name or docstring; otherwise, return a new object.
- Built-in mutable types: **list, dict, set**. Immutable: numbers, str, tuple, frozenset, bool, None.

</En>
<Ur>

- `admins = team` ne **alias** banaya: `admins` ke zariye "ana" append karna `team` me nazar aaya, aur `is` aur `id()` ne tasdeeq ki ke ye **ek object** hai.
- `admins = ["bob"]` ne sirf `admins` ko **rebind** kiya; `team` ki list rahi. Mutation object par asar karti; assignment naam par.
- `count += 1` ne **naya int** banaya (id badli), aur `name.upper()` ne nayi string lautayi jabke `name` "jane" raha: immutable objects aap ke neeche kabhi nahi badalte.
- List ke liye `nums += [3]` ne apni jagah **mutate** kiya, isliye `alias` ne `[1, 2, 3]` dekha aur `nums is alias` True raha. Tuple ke liye `t += (3,)` ne **naya tuple** banaya aur `t` ko rebind kiya; `alias_t` ne `(1, 2)` rakha. Ek hi operator, do rawaiye, mutability tay karti hai.
- `add_audit_tag` ne bulane wale ki list badli (**"audited" aa gaya**), jabke `replace_tags` ne sirf apna local naam rebind kiya, isliye bulane wale ki list par asar nahi hua. Arguments mutate karne wale functions ko apne naam ya docstring me batana chahiye; warna naya object lautayen.
- Built-in mutable types: **list, dict, set**. Immutable: numbers, str, tuple, frozenset, bool, None.

</Ur>

<Step title="Shallow vs deep copies, and the default-argument trap">

<Tr>
<En>
`copies.py` copies a nested config dict shallowly and changes it, then deep-copies a fresh one and changes that. It checks three ways of shallow-copying a list of rows, calls a function with a mutable default argument twice, compares it with the `None`-default fix, and shows the odd result of `+=` on a list stored inside a tuple.
</En>
<Ur>
`copies.py` nested config dict ki shallow copy bana kar badalti, phir taza dict ki deep copy bana kar badalti hai. Rows ki list ko shallow copy karne ke teen tareeqe check karti, mutable default argument wala function do dafa bulati, use `None`-default wale hal se milati, aur tuple ke andar rakhi list par `+=` ka ajeeb natija dikhati hai.
</Ur>
</Tr>

```bash
cat > copies.py <<'EOF'
import copy

defaults = {"name": "web", "ports": [80, 443], "tls": {"enabled": True}}

# Shallow copy: a new outer dict, but the SAME inner list and dict
shallow = defaults.copy()             # also: dict(defaults), copy.copy(defaults)
shallow["name"] = "api"               # top-level change: independent
shallow["ports"].append(8443)         # nested change: shared!
print(defaults["name"], defaults["ports"])

# Deep copy: copies everything, all the way down
defaults = {"name": "web", "ports": [80, 443], "tls": {"enabled": True}}
deep = copy.deepcopy(defaults)
deep["ports"].append(8443)
deep["tls"]["enabled"] = False
print(defaults["ports"], defaults["tls"], "| copy:", deep["ports"], deep["tls"])

# Lists: three shallow-copy spellings, same behaviour
rows = [["jane", 2], ["john", 7]]
for c in (rows.copy(), list(rows), rows[:]):
    print(c is rows, c[0] is rows[0], end=" | ")
print()

# The mutable default argument trap: the default list is created ONCE
def add_finding(item, findings=[]):
    findings.append(item)
    return findings
print(add_finding("open port 22"), add_finding("weak cipher"))   # second call sees the first!

def add_finding_fixed(item, findings=None):
    if findings is None:
        findings = []                 # a fresh list on every call
    findings.append(item)
    return findings
print(add_finding_fixed("open port 22"), add_finding_fixed("weak cipher"))

# A strange corner: a list inside a tuple
t = ("jane", ["admin"])
try:
    t[1] += ["billing"]               # mutates the list, THEN fails to assign into the tuple
except TypeError as e:
    print("TypeError:", e, "| but t is now", t)
EOF
python3 copies.py
```

```text output
web [80, 443, 8443]
[80, 443] {'enabled': True} | copy: [80, 443, 8443] {'enabled': False}
False True | False True | False True | 
['open port 22', 'weak cipher'] ['open port 22', 'weak cipher']
['open port 22'] ['weak cipher']
TypeError: 'tuple' object does not support item assignment | but t is now ('jane', ['admin', 'billing'])
```

<Happened>
<Tr>
<En>

- After the shallow copy, changing `shallow["name"]` left the original's name as **web**, but appending to `shallow["ports"]` changed the original's ports too (**[80, 443, 8443]**): the inner list is shared.
- With `copy.deepcopy`, both the nested list and the nested dict were independent: the original kept **[80, 443]** and `enabled: True`.
- `rows.copy()`, `list(rows)` and `rows[:]` all gave a **new outer list** (`c is rows` False) whose rows were the **same objects** (`c[0] is rows[0]` True).
- `add_finding` returned the **same growing list** on both calls: the default `[]` was created once, when the function was defined, and every call without an argument reused it. With `findings=None` and a new list inside, each call got its own list.
- `t[1] += ["billing"]` raised **TypeError**, yet the list inside **did change**: `+=` first mutates the list, then tries to store it back into the tuple, which fails. A reminder that a tuple doesn't make its contents immutable.

</En>
<Ur>

- Shallow copy ke baad `shallow["name"]` badalne se asal ka naam **web** raha, magar `shallow["ports"]` me append ne asal ke ports bhi badal diye (**[80, 443, 8443]**): andar ki list mushtarak hai.
- `copy.deepcopy` ke saath nested list aur nested dict dono alag the: asal ne **[80, 443]** aur `enabled: True` rakha.
- `rows.copy()`, `list(rows)` aur `rows[:]` sab ne **nayi bahar wali list** di (`c is rows` False) jis ki rows **wahi objects** thin (`c[0] is rows[0]` True).
- `add_finding` ne dono calls par **wahi barhti list** lautayi: default `[]` ek dafa bana, jab function define hua, aur bina argument har call ne use dobara istemal kiya. `findings=None` aur andar nayi list ke saath har call ko apni list mili.
- `t[1] += ["billing"]` ne **TypeError** diya, phir bhi andar ki list **badal gayi**: `+=` pehle list mutate karta, phir use tuple me wapas rakhne ki koshish karta jo nakam hoti hai. Yaad dihani ke tuple apne mawad ko immutable nahi banata.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Copying a template shallowly">

```text
TEMPLATE = {"tags": ["base"], "limits": {"cpu": 1}}
def make_server(name):
    cfg = TEMPLATE.copy()
    cfg["name"] = name
    cfg["tags"].append(name)          # modifies TEMPLATE["tags"] for everyone
    return cfg
```

</Bad>
<Good title="Deep copy (or build fresh)">

```text
import copy
def make_server(name):
    cfg = copy.deepcopy(TEMPLATE)
    cfg["name"] = name
    cfg["tags"].append(name)
    return cfg
```

</Good>
</Compare>

<Compare>
<Bad title="Mutable default argument">

```text
def log_event(event, history=[]):
    history.append(event)
    return history
# every caller that omits history shares one ever-growing list
```

</Bad>
<Good title="None as the default">

```text
def log_event(event, history=None):
    if history is None:
        history = []
    history.append(event)
    return history
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Returning an internal list** from an object or module and letting callers mutate it; return a copy or a tuple.
- **Assuming `list(x)` or `[:]` copies nested data**: they're shallow.
- **Using `deepcopy` everywhere**: it's slow on big structures; copy only what you'll change, or build new data.
- **Comparing with `is` instead of `==`**: identity is for "same object" (and `None`), not equal values.
- **Mutating a list while other code iterates it**: copy before handing it out, or use immutable types.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Object ya module se andar ki list lautana** aur bulane walon ko mutate karne dena; copy ya tuple lautayen.
- **Samajhna ke `list(x)` ya `[:]` nested data copy karte hain**: ye shallow hain.
- **Har jagah `deepcopy`**: bare dhanchon par sust hai; sirf wahi copy karein jo badlenge, ya naya data banayen.
- **`==` ke bajaye `is` se milana**: identity "wahi object" (aur `None`) ke liye hai, barabar values ke liye nahi.
- **Doosra code iterate kar raha ho aur list mutate karna**: dene se pehle copy karein, ya immutable types lein.

</Ur>
</Tr>

<Solution>

<Tr>


<DeepDive title="More about mutability">

**Call by object reference.** Python passes references to objects ("call by sharing"): a function can mutate a mutable argument but can't make the caller's name point elsewhere.

**Interning and caching.** Small ints and some strings are reused objects, so `is` may look like it compares values; it doesn't. Use `==`.

**Custom copying.** Classes can define `__copy__` and `__deepcopy__`; `deepcopy` handles cycles with a memo dictionary.

**Immutable alternatives.** `tuple` for lists, `frozenset` for sets, `types.MappingProxyType` for read-only dict views, `@dataclass(frozen=True)` for records.

**Persistent data patterns.** Instead of mutating, build new values (`{**old, "key": new}`, `[*old, item]`); this is the style used in React state and many functional libraries, and it avoids aliasing bugs.

</DeepDive>

<DeepDive title="Real world: the permissions that spread">

A web app built each new user's permissions from a module-level `DEFAULT_PERMS = {"roles": ["viewer"]}` with `perms = DEFAULT_PERMS.copy()`. When an admin was created, the code did `perms["roles"].append("admin")`. Because the copy was shallow, the shared default list now contained "admin", and every user created afterwards, until the next restart, was an admin.

The fixes:

1. Build permissions fresh: `perms = {"roles": ["viewer"]}` inside the function (or `copy.deepcopy`).
2. Make the defaults immutable: `DEFAULT_ROLES = ("viewer",)`, so an accidental `append` raises an error instead of silently spreading.
3. A test that creates an admin and then a normal user and checks the normal user has no admin role.

</DeepDive>

<DeepDive title="Security lens">

- **Shared mutable state leaks between users and requests**: module-level lists and dicts in web apps are shared by every request in the process.
- **Immutable defaults for security settings** (`frozenset` of roles, tuples of allowed origins) prevent accidental runtime changes.
- **Defensive copies at trust boundaries**: copy input you store, and return copies of internal data, so callers can't tamper with your state.
- **Mutable default arguments** in request handlers can mix one user's data into another's response.
- **Deep copy untrusted structures carefully**: very deep or cyclic data can be slow; validate size and depth first.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between mutable and immutable objects?">
Mutable objects such as lists, dicts and sets can be changed in place, and the change is visible through every reference. Immutable objects such as ints, strings and tuples can't be changed; operations produce new objects.
</QA>

<QA q="Explain shallow vs deep copy.">
A shallow copy creates a new container that holds references to the same inner objects; a deep copy recursively copies the inner objects too, so the copy is fully independent.
</QA>

<QA q="Why is a mutable default argument a problem?">
Default values are evaluated once when the function is defined, so a list or dict default is shared by all calls and accumulates changes. Use None and create a new object inside the function.
</QA>

<QA q="Is Python pass-by-value or pass-by-reference?">
Neither exactly: it passes references to objects by value. A function can mutate the object it receives, but rebinding the parameter doesn't affect the caller's variable.
</QA>

<QA q="Why does x += y behave differently for lists and tuples?">
For lists, += calls an in-place method that extends the same object. Tuples have no in-place version, so += builds a new tuple and rebinds the name.
</QA>

</DeepDive>
