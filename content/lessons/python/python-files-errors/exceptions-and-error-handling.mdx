<BigIdea>
<Tr>
<En>
When Python hits a problem it can't handle, such as converting `"three"` to an int or opening a file that doesn't exist, it **raises an exception**: an object describing what went wrong. If nothing **catches** it, the program stops and prints a **traceback**. You catch exceptions with **`try`/`except`**: put the risky code in `try`, and say which **specific** exception types you can handle in `except` clauses. **`else`** runs only when no exception happened, and **`finally`** always runs, which makes it the place for cleanup. You **raise** exceptions yourself with `raise ValueError("...")` when your function receives something it can't work with; that's better than returning a special value that callers might ignore. For your own tools, define a small **exception hierarchy** (`class ScanError(Exception)` with subclasses) so callers can catch everything from your code, or just one kind. When you convert a low-level error into your own, use **`raise ... from e`** to keep the original cause. The golden rules: **catch only what you can handle**, catch it as **narrowly** as possible, never silence errors with a bare `except:`, and let unexpected errors surface where someone will see them.
</En>
<Ur>
Jab Python ko aisa masla milta hai jo woh sambhal nahi sakta, jaise `"three"` ko int banana ya aisi file kholna jo mojood nahi, to woh **exception raise** karta hai: ek object jo batata hai kya ghalat hua. Agar koi use **pakre** nahi to program ruk kar **traceback** print karta hai. Exceptions **`try`/`except`** se pakarte hain: khatre wala code `try` me rakhein, aur `except` clauses me batayen ke kaunsi **khaas** exception types sambhal sakte hain. **`else`** sirf tab chalta hai jab koi exception na ho, aur **`finally`** hamesha chalta hai, isliye safai ki jagah yahi hai. Jab aap ke function ko aisi cheez mile jis ke saath kaam na ho sake to `raise ValueError("...")` se khud exceptions **raise** karein; ye aisi khaas value lautane se behtar hai jise bulane wale nazar andaz kar dein. Apne tools ke liye chhoti **exception hierarchy** banayen (`class ScanError(Exception)` aur us ki subclasses) taa ke bulane wale aap ke code se sab kuch ya sirf ek qism pakad sakein. Jab neechle level ka error apne error me badlein to asal wajah rakhne ke liye **`raise ... from e`** lein. Sunehre qaide: **sirf wahi pakrein jo sambhal sakein**, jitna ho sake **mehdood** pakrein, kabhi khaali `except:` se errors khamosh na karein, aur ghair mutawaqqo errors ko aisi jagah aane dein jahan koi dekhe.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **kitchen during dinner service**.

- A cook trying a tricky dish is the `try` block. If the sauce splits (an exception), a specific fix exists: whisk in cold butter (`except SauceSplit`). If the oven catches fire, that's not something the cook handles; it goes up to the head chef and maybe the fire brigade (it propagates).
- Whatever happens, the cook turns the gas off at the end (`finally`).
- A cook who answers every problem with "it's fine" and serves the dish anyway is a bare `except: pass`: the customers find out later.
- A complaint card that says "dish failed: sauce split because the butter was warm" is a chained exception: the new problem and its cause together.

</En>
<Ur>

**Dinner ke waqt kitchen** socheyn.

- Mushkil dish aazmata cook `try` block hai. Agar sauce phat jaye (exception), to khaas hal mojood hai: thanda makhan milao (`except SauceSplit`). Agar oven me aag lag jaye to ye cook ka kaam nahi; ye head chef aur shayad fire brigade tak jata hai (aage jata hai).
- Kuch bhi ho, cook aakhir me gas band karta hai (`finally`).
- Jo cook har masle par "sab theek" keh kar dish phir bhi pesh kare woh khaali `except: pass` hai: customers ko baad me pata chalta hai.
- "Dish nakam: sauce phata kyunke makhan garam tha" wala shikayat card chained exception hai: naya masla aur us ki wajah saath.

## Learn it step by step

<Walkthrough>

<Step title="try, except, else, finally, raise and tracebacks">

<Tr>
<En>
`errors.py` parses ports with all four parts of a `try` statement, reads settings where some are missing and some are invalid (with two `except` clauses, one catching two types), validates arguments by raising `TypeError` and `ValueError`, and compares the EAFP and LBYL styles. Finally a small script calls a function that opens a missing file without handling the error, so we can read the traceback and see the exit code.
</En>
<Ur>
`errors.py` `try` statement ke chaaron hisson se ports parse karti, aisi settings parhti jin me kuch ghayab aur kuch ghalat hain (do `except` clauses ke saath, ek do types pakarta), `TypeError` aur `ValueError` raise kar ke arguments validate karti, aur EAFP aur LBYL andaaz milati hai. Aakhir me chhoti script aisa function bulati jo error sambhale baghair ghayab file kholta hai, taa ke hum traceback parhein aur exit code dekhein.
</Ur>
</Tr>

```bash
cat > errors.py <<'EOF'
def parse_port(text):
    try:
        port = int(text)                          # code that might fail
    except ValueError:                            # handle ONE specific kind of error
        print(f"  {text!r} is not a number")
        return None
    else:                                         # runs only if no exception happened
        print(f"  parsed {port}")
        return port
    finally:                                      # ALWAYS runs: success, failure or return
        print(f"  done with {text!r}")

for t in ["443", "https"]:
    print(parse_port(t))

# Several except clauses, and the exception object
config = {"timeout": "30", "retries": "three"}
for key in ["timeout", "retries", "port"]:
    try:
        value = int(config[key])
        print(key, "=", value, "| per minute:", 60 // value)
    except KeyError as e:
        print(f"missing setting: {e}")
    except (ValueError, ZeroDivisionError) as e:   # one clause for several types
        print(f"bad value for {key}: {type(e).__name__}: {e}")

# raise: signal an error yourself
def set_replicas(n):
    if not isinstance(n, int):
        raise TypeError(f"replicas must be an int, got {type(n).__name__}")
    if not 1 <= n <= 50:
        raise ValueError(f"replicas must be 1-50, got {n}")
    return n
for n in [3, 0, "3"]:
    try:
        print("replicas:", set_replicas(n))
    except (TypeError, ValueError) as e:
        print(f"{type(e).__name__}: {e}")

# EAFP ("easier to ask forgiveness") vs LBYL ("look before you leap")
user = {"name": "jane"}
email = user["email"] if "email" in user else "n/a"          # LBYL
try:
    email2 = user["email"]                                     # EAFP
except KeyError:
    email2 = "n/a"
print(email, email2)
EOF
python3 errors.py
echo "--- an unhandled exception stops the program with a traceback (read it bottom-up):"
python3 -c '
def load(path):
    return open(path).read()
def main():
    return load("missing.conf")
main()' 2>&1
echo "exit code: $?"
```

<Happened>
<Tr>
<En>

- For "443", `try` succeeded, so `else` printed **parsed 443**; for "https", `int()` raised **ValueError**, the `except` clause handled it and returned None. In both cases **`finally` ran**, even though both paths had a `return`.
- `timeout` worked, `retries` hit the **ValueError** branch with the exception's own message (`invalid literal for int()...`), and `port` hit **KeyError** because it wasn't in the dict. Specific clauses let you respond differently to different problems.
- `set_replicas` **raised** clear errors for 0 and for the string "3". Raising at the start of a function (validating inputs) means bad values never travel further into your program.
- EAFP (`try`/`except KeyError`) and LBYL (`if "email" in user`) gave the same result. Python code often prefers EAFP, especially where checking first could race with something else changing.
- The unhandled **FileNotFoundError** printed a traceback. Read it **from the bottom**: the last line says what happened, and the frames above show the call chain `<module>` → `main` → `load`, with the exact line. The script ended with **exit code 1**, which tells cron or CI it failed.

</En>
<Ur>

- "443" ke liye `try` kamyab hua, isliye `else` ne **parsed 443** print kiya; "https" ke liye `int()` ne **ValueError** diya, `except` clause ne use sambhala aur None lautaya. Dono soorton me **`finally` chala**, halanke dono raaston me `return` tha.
- `timeout` chala, `retries` exception ke apne paigham (`invalid literal for int()...`) ke saath **ValueError** shaakh par gaya, aur `port` **KeyError** par gaya kyunke dict me nahi tha. Khaas clauses alag masail ka alag jawab dene dete hain.
- `set_replicas` ne 0 aur string "3" ke liye wazeh errors **raise** kiye. Function ke shuru me raise karna (inputs validate karna) ka matlab kharab values kabhi program me aage nahi jatin.
- EAFP (`try`/`except KeyError`) aur LBYL (`if "email" in user`) ne wahi natija diya. Python code aksar EAFP ko tarjeeh deta hai, khaas taur par jahan pehle check karna kisi aur ke badalne se takra sakta ho.
- Na pakre **FileNotFoundError** ne traceback print kiya. Ise **neeche se** parhein: aakhri line batati kya hua, aur upar ke frames call ki zanjeer `<module>` → `main` → `load` bilkul line ke saath dikhate hain. Script **exit code 1** par khatam hui, jo cron ya CI ko nakami batata hai.

</Ur>

<Step title="Designing errors: hierarchies, chaining, re-raising, catch-alls and groups">

<Tr>
<En>
`design.py` defines a `ScanError` base class with `TargetUnreachable` (carrying the host as an attribute) and `InvalidConfig`. It skips an unreachable host, converts a JSON parsing error into `InvalidConfig` with `raise ... from`, logs and re-raises a `PermissionError`, processes a batch where one item fails in two different ways, and raises an `ExceptionGroup` handled by two `except*` clauses.
</En>
<Ur>
`design.py` `ScanError` base class ke saath `TargetUnreachable` (host ko attribute ki tarah rakhte hue) aur `InvalidConfig` define karti hai. Na pohanchne wala host chhorti, `raise ... from` se JSON parsing error ko `InvalidConfig` me badalti, `PermissionError` log kar ke dobara raise karti, aisa batch process karti jis me ek item do alag tareeqon se nakam ho, aur do `except*` clauses se sambhala gaya `ExceptionGroup` raise karti hai.
</Ur>
</Tr>

```bash
cat > design.py <<'EOF'
import json

# 1. Your own exception hierarchy: callers can catch broadly or precisely
class ScanError(Exception):
    """Base class for all errors from this tool."""
class TargetUnreachable(ScanError):
    def __init__(self, host, reason):
        super().__init__(f"{host} unreachable: {reason}")
        self.host = host
class InvalidConfig(ScanError):
    pass

def scan(host):
    if host.endswith(".invalid"):
        raise TargetUnreachable(host, "DNS lookup failed")
    return f"{host}: 3 open ports"

for h in ["web1.example.test", "old.invalid"]:
    try:
        print(scan(h))
    except TargetUnreachable as e:
        print("skipped:", e, "| host attribute:", e.host)

# 2. Chaining: turn a low-level error into a meaningful one, keeping the cause
def load_config(text):
    try:
        return json.loads(text)
    except json.JSONDecodeError as e:
        raise InvalidConfig("config.json is not valid JSON") from e

try:
    load_config('{"targets": ["web1",]}')
except ScanError as e:                           # catch via the base class
    print(f"{type(e).__name__}: {e} | caused by: {type(e.__cause__).__name__}: {e.__cause__}")

# 3. Re-raise after doing something (cleanup, logging) with a bare `raise`
def delete_host(h):
    try:
        raise PermissionError(f"not allowed to delete {h}")
    except PermissionError:
        print("audit: failed delete attempt on", h)
        raise                                     # same exception, original traceback
try:
    delete_host("db1")
except PermissionError as e:
    print("caller saw:", e)

# 4. Catch-all done right: never a bare `except:` (it also traps Ctrl+C and sys.exit)
def risky(n):
    return 10 / n
results = []
for n in [5, 0, "x"]:
    try:
        results.append(risky(n))
    except Exception as e:                        # log and continue a batch, don't hide the type
        results.append(f"error: {type(e).__name__}")
print(results)

# 5. Several errors at once (Python 3.11+): ExceptionGroup and except*
errors = [TargetUnreachable("a.invalid", "timeout"), InvalidConfig("bad port 70000")]
try:
    raise ExceptionGroup("batch failed", errors)
except* TargetUnreachable as group:
    print("unreachable:", [str(e) for e in group.exceptions])
except* InvalidConfig as group:
    print("config:", [str(e) for e in group.exceptions])
EOF
python3 design.py
```

```text output

skipped: old.invalid unreachable: DNS lookup failed | host attribute: old.invalid
InvalidConfig: config.json is not valid JSON | caused by: JSONDecodeError: Illegal trailing comma before end of array: line 1 column 20 (char 19)
audit: failed delete attempt on db1
caller saw: not allowed to delete db1
[2.0, 'error: ZeroDivisionError', 'error: TypeError']
unreachable: ['a.invalid unreachable: timeout']
config: ['bad port 70000']
```

<Happened>
<Tr>
<En>

- `except TargetUnreachable` handled only that kind of failure and could read **`e.host`**: custom exceptions can carry data that helps the caller react, not just a message.
- `load_config` caught the low-level `JSONDecodeError` and raised **InvalidConfig from e**. The caller caught it through the base class `ScanError`, got a message that makes sense to a user, and could still inspect the original cause in `__cause__` (a full traceback would show both, joined by "The above exception was the direct cause of...").
- A bare **`raise`** inside `except` re-raised the same `PermissionError` after writing an audit line, so the caller still saw the failure. Log-and-swallow would have hidden it.
- The batch caught **`Exception`** per item, recording `ZeroDivisionError` and `TypeError` and carrying on. That's the right place for a broad catch: per item, with the type recorded. Never write a bare `except:`, which also catches `KeyboardInterrupt` and `SystemExit`, so Ctrl+C and `sys.exit()` stop working.
- `ExceptionGroup` bundled two different errors (as concurrent tasks often produce), and each **`except*`** clause handled its own type from the group.

</En>
<Ur>

- `except TargetUnreachable` ne sirf wahi nakami sambhali aur **`e.host`** parh saka: custom exceptions sirf paigham nahi, aisa data bhi rakh sakti hain jo bulane wale ko react karne me madad de.
- `load_config` ne neechle level ka `JSONDecodeError` pakad kar **InvalidConfig from e** raise kiya. Bulane wale ne ise base class `ScanError` ke zariye pakra, user ke liye samajh me aane wala paigham paya, aur phir bhi `__cause__` me asal wajah dekh saka (poora traceback dono ko "The above exception was the direct cause of..." se jor kar dikhata).
- `except` ke andar khaali **`raise`** ne audit line likhne ke baad wahi `PermissionError` dobara raise kiya, isliye bulane wale ne nakami dekhi. Log kar ke nigalna use chhupa deta.
- Batch ne har item par **`Exception`** pakra, `ZeroDivisionError` aur `TypeError` darj kar ke jaari raha. Wasee pakar ki sahi jagah yahi hai: har item par, type darj kar ke. Kabhi khaali `except:` na likhein, jo `KeyboardInterrupt` aur `SystemExit` bhi pakarta hai, isliye Ctrl+C aur `sys.exit()` kaam karna band kar dete hain.
- `ExceptionGroup` ne do alag errors bandhe (jaisa saath chalne wale tasks aksar karte hain), aur har **`except*`** clause ne group se apni type sambhali.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Swallowing every error">

```text
try:
    config = load_config(path)
    connect(config["db_url"])
except:
    pass                     # typo in a key, wrong password, missing file, Ctrl+C: all silent
```

</Bad>
<Good title="Catch what you can handle, let the rest surface">

```text
try:
    config = load_config(path)
except FileNotFoundError:
    sys.exit(f"config file not found: {path}")
except InvalidConfig as e:
    sys.exit(f"config error: {e}")
connect(config["db_url"])    # other errors propagate with a full traceback
```

</Good>
</Compare>

<Compare>
<Bad title="A huge try block">

```text
try:
    data = fetch(url)
    users = parse(data)
    for u in users:
        save(u)
    send_report(users)
except KeyError:
    print("missing field")    # which step? which field? which user?
```

</Bad>
<Good title="Narrow try blocks around the risky call">

```text
data = fetch(url)
users = parse(data)
for u in users:
    try:
        save(u)
    except KeyError as e:
        log.warning("user %s missing field %s", u.get("id"), e)
send_report(users)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Returning `None` or `-1` for errors** where callers forget to check; raise an exception instead.
- **Losing the cause**: `raise MyError("failed")` inside `except` without `from e` hides why.
- **Catching an exception just to print it and continue** in code that can't really continue; the next line fails in a more confusing way.
- **Showing raw exception messages or tracebacks to end users** of a web app; they can leak paths, queries and secrets.
- **Using exceptions for normal control flow in hot loops** where a simple check is clearer and faster.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

<DeepDive title="More about exceptions">

**The hierarchy.** `BaseException` is at the top; `Exception` covers normal errors; `KeyboardInterrupt`, `SystemExit` and `GeneratorExit` derive directly from `BaseException` so `except Exception` doesn't catch them. `OSError` has subclasses like `FileNotFoundError`, `PermissionError` and `TimeoutError`.

**Notes.** `e.add_note("while loading users.csv")` (Python 3.11+) adds context that appears in the traceback without changing the exception type.

**Context managers.** `with open(...)` and `contextlib.suppress(FileNotFoundError)` handle common cleanup and ignore-this-error patterns concisely.

**traceback and logging.** `logging.exception("msg")` inside an `except` block logs the message with the full traceback; `traceback.format_exc()` returns it as text.

**Warnings.** `warnings.warn("deprecated", DeprecationWarning)` reports problems that shouldn't stop the program.

</DeepDive>

<DeepDive title="Real world: the backup that always succeeded">

A nightly backup script wrapped everything in `try: ... except Exception: print("backup error")`, then printed "backup complete" and exited with code 0. When the storage credentials expired, every night printed both lines, cron saw success, and the team discovered months later, during a restore, that there were no recent backups.

The fixes:

1. Catch only expected, recoverable errors (a single file that vanished mid-backup), and let anything else propagate.
2. Exit with a non-zero code on failure and alert on it; also alert when a backup *hasn't* reported success for 26 hours.
3. Verify the backup at the end (list and checksum the uploaded file) instead of assuming success.

</DeepDive>

<DeepDive title="Security lens">

- **Fail closed**: if an authorisation check raises an error, deny access; never let an exception path skip the check and continue.
- **Don't leak internals**: show users a generic message and an error ID; log the details (traceback, query) server-side.
- **Bare excepts hide attacks**: swallowed errors can mask injection attempts, tampering or failing security controls.
- **Clean up sensitive resources in `finally`** or with context managers: close connections, delete temporary files with secrets, release locks.
- **Don't put secrets in exception messages**: they end up in logs and error trackers.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Explain try, except, else and finally.">
try contains code that may raise; except handles specific exceptions; else runs only if try raised nothing; finally always runs afterwards, for cleanup, even if there was a return or an unhandled exception.
</QA>

<QA q="What is the difference between except Exception and a bare except?">
except Exception catches ordinary errors but not system-exiting exceptions like KeyboardInterrupt and SystemExit; a bare except catches everything, which can make programs impossible to stop and hide serious problems.
</QA>

<QA q="Why create custom exception classes?">
To signal domain-specific errors with clear names and extra data, and to let callers catch all of a library's errors via a base class or specific ones via subclasses.
</QA>

<QA q="What is exception chaining?">
Raising a new exception while handling another, with raise New from original, which records the original as `__cause__` so tracebacks show both; from None suppresses the context.
</QA>

<QA q="EAFP or LBYL?">
EAFP tries the operation and handles exceptions; LBYL checks conditions first. Python favours EAFP, especially when a check could become outdated before the action (race conditions), while LBYL can be clearer for simple, cheap checks.
</QA>

</DeepDive>
