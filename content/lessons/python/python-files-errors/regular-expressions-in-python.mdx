<BigIdea>
<Tr>
<En>
A **regular expression** (regex) is a small pattern language for text. `\d` means "a digit", `+` means "one or more", so `\d+` finds numbers; `\d{4}-\d{2}-\d{2}` finds dates like 2026-11-23. Python's **`re`** module applies patterns: **`re.search`** finds the first match anywhere, **`re.match`** only at the start, **`re.fullmatch`** requires the whole string to match (what you want for validation), **`re.findall`** and **`re.finditer`** return every match, **`re.sub`** replaces, and **`re.split`** splits on a pattern. Parentheses create **groups** that capture parts of a match, and **named groups** like `(?P<year>\d{4})` let you read them by name. Always write patterns as **raw strings** (`r"\d+"`) so backslashes reach the regex engine unchanged. Quantifiers are **greedy** by default (they grab as much as possible); add `?` to make them **lazy**. For anything long, **compile** the pattern once and use `re.VERBOSE` so you can lay it out with comments. Regex is powerful but easy to get wrong: unanchored validation accepts junk around the valid part, and some patterns (nested quantifiers like `(a+)+`) can take exponential time on hostile input, a denial-of-service bug called **ReDoS**. For structured formats such as HTML, JSON or emails in full generality, use a real parser instead.
</En>
<Ur>
**Regular expression** (regex) text ke patterns ki chhoti zaban hai. `\d` ka matlab "ek digit", `+` ka matlab "ek ya zyada", isliye `\d+` numbers dhoondta; `\d{4}-\d{2}-\d{2}` 2026-11-23 jaisi dates dhoondta hai. ## Picture it

<Tr>
<En>

Think of a **stencil** laid over a page of text.

- The stencil has shaped holes: "a digit here, then a dash, then two digits". You slide it along the line until every hole lines up with matching characters: that's a match.
- `search` slides across the whole page, `match` only checks the first position, and `fullmatch` needs the stencil to be exactly the length of the text.
- Groups are holes painted in different colours so you can read off just the year or just the order number.
- A badly designed stencil with nested flexible holes can be tried in millions of positions before giving up, which is ReDoS.

</En>
<Ur>

Text ke safhe par rakhe **stencil** ko socheyn.

- Stencil me shakal wale surakh hain: "yahan ek digit, phir dash, phir do digits". Aap use line par sarkate hain jab tak har surakh milte characters par na baith jaye: yahi mel hai.
- `search` poore safhe par sarkata, `match` sirf pehli jagah check karta, aur `fullmatch` chahta hai ke stencil bilkul text jitna lamba ho.
- Groups mukhtalif rangon me range surakh hain taa ke aap sirf saal ya sirf order number parh sakein.
- Nested lachakdaar surakhon wala bura bana stencil haar maanne se pehle lakhon jagahon par aazmaya ja sakta hai, yahi ReDoS hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="search, match, findall, groups, sub, split and greedy matching">

<Tr>
<En>
`regex_basics.py` runs the main `re` functions on one sentence with two order numbers, two dates and an email. It extracts dates with named groups, loops with `finditer`, redacts the email, reorders a date in a replacement, splits on mixed separators, compares greedy and lazy matching on HTML tags, validates codes with `fullmatch`, and shows why patterns need raw strings and word boundaries.
</En>
<Ur>
`regex_basics.py` do order numbers, do dates aur ek email wale ek jumle par `re` ke ahem functions chalati hai. Named groups se dates nikalti, `finditer` se loop karti, email chhupati, replacement me date ki tarteeb badalti, mile jule separators par todti, HTML tags par greedy aur lazy mel ka muqabla karti, `fullmatch` se codes validate karti, aur dikhati hai ke patterns ko raw strings aur word boundaries kyun chahiye.
</Ur>
</Tr>

```bash
cat > regex_basics.py <<'EOF'
import re

text = "Order #1042 shipped 2026-11-23 to jane@example.com; order #987 pending since 2026-10-02."

print(re.search(r"\d+", text).group())             # first match anywhere
print(re.match(r"\d+", text))                       # match only at the START -> None
print(re.findall(r"#(\d+)", text))                  # all matches; returns the group
print(re.findall(r"\d{4}-\d{2}-\d{2}", text))       # dates: exactly 4-2-2 digits

# Groups and named groups
m = re.search(r"(?P<year>\d{4})-(?P<month>\d{2})-(?P<day>\d{2})", text)
print(m.group(0), "|", m.group("year"), m.group("month"), "|", m.groupdict(), "| span:", m.span())

# finditer gives match objects with positions
for m in re.finditer(r"order #(\d+)", text, flags=re.IGNORECASE):
    print("order", m.group(1), "at", m.start())

# Substitute, split
print(re.sub(r"[\w.+-]+@[\w-]+\.[\w.]+", "[email]", text))
print(re.sub(r"(\d{4})-(\d{2})-(\d{2})", r"\3/\2/\1", "due 2026-12-01"))
print(re.split(r"[,;\s]+", "web01, web02;db01   cache01"))

# Greedy vs lazy
html = "<b>bold</b> and <i>italic</i>"
print(re.findall(r"<.+>", html), "vs", re.findall(r"<.+?>", html))

# fullmatch for validation, and raw strings
print(bool(re.fullmatch(r"[A-Z]{2}-\d{4}", "KB-0001")), bool(re.fullmatch(r"[A-Z]{2}-\d{4}", "KB-0001x")))
print(len("\b"), len(r"\b"))                         # "\b" is a backspace char; r"\b" is a word boundary
print(re.findall(r"\bcat\b", "cat catalog bobcat cat."))
EOF
python3 regex_basics.py
```

<Happened>
<Tr>
<En>

- `search` found **1042**, the first run of digits anywhere. `match` returned **None** because the text starts with "Order", not a digit; this surprises many people.
- `findall` with one group returned just the group (**['1042', '987']**), and the date pattern found both dates.
- Named groups made the match self-describing: `groupdict()` gave year, month and day, and `span()` the start and end positions (as strings: convert with `int` if needed).
- `finditer` with `re.IGNORECASE` matched both "Order" and "order" and gave positions.
- `sub` replaced the email with **[email]**; in the date example, `\3/\2/\1` reused the groups to reorder it. `split` handled commas, semicolons and runs of spaces in one go.
- `<.+>` was **greedy** and swallowed the whole string from the first `<` to the last `>`; `<.+?>` was **lazy** and matched each tag separately. (To process real HTML, use a parser.)
- `fullmatch` accepted `KB-0001` and rejected `KB-0001x`. `"\b"` without `r` is a single backspace character, while `r"\b"` is a word boundary, so `\bcat\b` found "cat" twice but not inside "catalog" or "bobcat".

</En>
<Ur>

- `search` ne **1042** dhoonda, kahin bhi digits ka pehla silsila. `match` ne **None** lautaya kyunke text "Order" se shuru hota hai, digit se nahi; ye bohat logon ko hairan karta hai.
- Ek group wale `findall` ne sirf group lautaya (**['1042', '987']**), aur date pattern ne dono dates dhoondin.
- Named groups ne mel ko khud wazeh bana diya: `groupdict()` ne saal, mahina aur din diye, aur `span()` ne shuru aur aakhir ki jagahen (strings ki shakal me: zaroorat ho to `int` se badlein).
- `re.IGNORECASE` wale `finditer` ne "Order" aur "order" dono milaye aur jagahen bataein.
- `sub` ne email ko **[email]** se badla; date wali misaal me `\3/\2/\1` ne groups dobara istemal kar ke tarteeb badli. `split` ne commas, semicolons aur spaces ke silsilon ko ek hi dafa sambhala.
- `<.+>` **greedy** tha aur pehle `<` se aakhri `>` tak poori string nigal gaya; `<.+?>` **lazy** tha aur har tag alag milaya. (Asal HTML ke liye parser lein.)
- `fullmatch` ne `KB-0001` qubool aur `KB-0001x` radd kiya. `r` ke baghair `"\b"` ek backspace character hai, jabke `r"\b"` word boundary, isliye `\bcat\b` ne "cat" do dafa dhoonda magar "catalog" ya "bobcat" ke andar nahi.

<Step title="Parsing logs, masking secrets, anchors and ReDoS">

<Tr>
<En>
`regex_logs.py` compiles a verbose, commented pattern for web server access logs with named groups, counts failed logins per IP and reports server errors, masks API keys and passwords in a URL, shows how an unanchored pattern accepts bad input, and times a pattern with nested quantifiers against a simple one.
</En>
<Ur>
`regex_logs.py` web server access logs ke liye named groups wala, comments ke saath verbose pattern compile karti, har IP ke nakam logins ginti aur server errors batati, URL me API keys aur passwords chhupati, dikhati hai ke anchors ke baghair pattern ghalat input kaise qubool karta, aur nested quantifiers wale pattern ko saade pattern ke muqable me time karti hai.
</Ur>
</Tr>

```bash
cat > regex_logs.py <<'EOF'
import re, time
from collections import Counter

LOG = re.compile(r"""
    ^(?P<ip>\d{1,3}(?:\.\d{1,3}){3})\s      # client IP
    \S+\s\S+\s                               # identity and user (unused)
    \[(?P<time>[^\]]+)\]\s                   # [23/Nov/2026:10:15:32 +0000]
    "(?P<method>[A-Z]+)\s(?P<path>\S+)\s[^"]*"\s
    (?P<status>\d{3})\s(?P<size>\d+|-)
""", re.VERBOSE)

lines = [
    '203.0.113.7 - - [23/Nov/2026:10:15:32 +0000] "GET /login HTTP/1.1" 200 512',
    '203.0.113.7 - - [23/Nov/2026:10:15:33 +0000] "POST /login HTTP/1.1" 401 64',
    '198.51.100.4 - - [23/Nov/2026:10:15:34 +0000] "GET /api/orders?id=1 HTTP/1.1" 500 -',
    '203.0.113.7 - - [23/Nov/2026:10:15:35 +0000] "POST /login HTTP/1.1" 401 64',
    'garbage line that does not match',
]
failed, bad = Counter(), 0
for line in lines:
    m = LOG.match(line)
    if not m:
        bad += 1
        continue
    d = m.groupdict()
    if d["path"].startswith("/login") and d["status"] == "401":
        failed[d["ip"]] += 1
    if d["status"].startswith("5"):
        print("server error:", d["method"], d["path"], d["time"])
print("failed logins:", dict(failed), "| unparsed lines:", bad)

# Masking secrets before logging
SECRET = re.compile(r"(api[_-]?key|token|password)=([^&\s]+)", re.IGNORECASE)
print(SECRET.sub(r"\1=***", "GET /pay?api_key=acme_live_9f8e7d&user=jane&Password=hunter2"))

# Validation needs anchors
weak = re.compile(r"\d{5}")
print("weak accepts:", bool(weak.search("abc12345xyz")), "| fullmatch:", bool(weak.fullmatch("abc12345xyz")))

# Catastrophic backtracking (ReDoS): nested quantifiers on input that almost matches
evil = re.compile(r"^(a+)+$")
for n in (12, 25):
    start = time.perf_counter()
    evil.match("a" * n + "!")
    took = time.perf_counter() - start
    print(f"n={n}: {'slow' if took > 0.05 else 'fast'}")
safe = re.compile(r"^a+$")
start = time.perf_counter(); safe.match("a" * 100_000 + "!")
print("simple pattern on 100k chars fast:", time.perf_counter() - start < 0.05)
EOF
python3 regex_logs.py
```

```text output
server error: GET /api/orders?id=1 23/Nov/2026:10:15:34 +0000
failed logins: {'203.0.113.7': 2} | unparsed lines: 1
GET /pay?api_key=***&user=jane&Password=***
weak accepts: True | fullmatch: False
n=12: fast
n=25: slow
simple pattern on 100k chars fast: True
```

<Happened>
<Tr>
<En>

- `re.VERBOSE` let us split the pattern over lines with comments; whitespace inside the pattern is ignored, so literal spaces are written as `\s`. Compiling once and reusing it is clearer and avoids re-parsing the pattern.
- `match` plus `groupdict()` turned each line into fields. We found **2 failed logins** from 203.0.113.7 (the start of brute-force detection, like fail2ban does) and the **500 error** on `/api/orders`. The garbage line didn't match and was counted instead of crashing the script.
- The `SECRET` pattern replaced the values of `api_key` and `Password` with `***`, keeping the names. Mask secrets **before** they reach logs.
- `\d{5}` with `search` **accepted** "abc12345xyz" because five digits appear somewhere in it. For validation use `fullmatch` (or `^...$` with `match`).
- `^(a+)+$` on 12 a's plus "!" was instant, but on 25 it took **over a second**: each extra character roughly doubles the work, because the engine tries every way to split the a's between the two `+`. An attacker can freeze a server with one request. The simple `^a+$` handled 100,000 characters instantly. Avoid nested quantifiers, limit input length, and consider the `regex` package with timeouts or Google's RE2 for untrusted patterns.

</En>
<Ur>

- `re.VERBOSE` ne humein pattern comments ke saath kai lines me todne diya; pattern ke andar whitespace nazar andaz hota hai, isliye asal spaces `\s` likhe gaye. Ek dafa compile kar ke dobara istemal zyada wazeh hai aur pattern dobara parse karne se bachata hai.
- `match` aur `groupdict()` ne har line ko fields me badla. Humne 203.0.113.7 se **2 nakam logins** (fail2ban ki tarah brute-force pakarne ki shuruat) aur `/api/orders` par **500 error** dhoonda. Kachra line mel nahi khayi aur script crash karne ke bajaye gini gayi.
- `SECRET` pattern ne `api_key` aur `Password` ki values `***` se badlin, naam qaim rakhe. Secrets logs tak pohanchne se **pehle** chhupayen.
- `search` ke saath `\d{5}` ne "abc12345xyz" **qubool** kiya kyunke us me kahin paanch digits hain. Validation ke liye `fullmatch` (ya `match` ke saath `^...$`) lein.
- `^(a+)+$` 12 a's aur "!" par foran chala, magar 25 par **ek second se zyada** laga: har zayed character kaam taqreeban dugna karta hai, kyunke engine a's ko dono `+` me baantne ka har tareeqa aazmata hai. Hamla awar ek request se server jama kar sakta hai. Saade `^a+$` ne 100,000 characters foran sambhale. Nested quantifiers se bachein, input ki lambai mehdood karein, aur na-qabil-e-bharosa patterns ke liye timeouts wala `regex` package ya Google ka RE2 dekhein.

</Ur>

## Common mistakes

<Compare>
<Bad title="Validation without anchors">

```text
if re.search(r"\d{5}", zip_code):            # "abc12345; DROP TABLE" passes
    save(zip_code)
if re.match(r"[a-z]+", username):            # "admin<script>" passes (match only checks the start)
    save(username)
```

</Bad>

```text

    save(zip_code)

    save(username)
```

<En>

More mistakes to avoid:

- **Calling `.group()` on `None`**: check that the match succeeded first.
- **Forgetting to escape special characters**: `.` matches anything; use `\.` or `re.escape(user_text)` when searching for literal text.
- **Building patterns from user input without `re.escape`**: users can inject expensive or wrong patterns.
- **Trying to validate emails perfectly with regex**: use a simple check and send a confirmation email.
- **Unreadable one-line monsters**: use `re.VERBOSE`, named groups and comments.

From the text below, use one compiled pattern with named groups to extract each invoice's number, amount and currency, and print them as dicts with the amount converted to `Decimal`. Text: `"Invoice INV-2026-001: 1,250.00 USD. Invoice INV-2026-002: 89.99 EUR. Ref INV-X: n/a"`.

```text
from decimal import Decimal

INVOICE = re.compile(r"(?P<number>INV-\d{4}-\d{3}):\s(?P<amount>[\d,]+\.\d{2})\s(?P<currency>[A-Z]{3})")

for m in INVOICE.finditer(text):
    d = m.groupdict()
    d["amount"] = Decimal(d["amount"].replace(",", ""))
    print(d)
```

Write `redact(line)` that replaces email addresses with `[email]`, the value after `Bearer ` in an Authorization header with `[token]`, and any run of 13 to 16 digits (possibly separated by spaces or dashes in groups of four) with `[card]`.
```text
import re

EMAIL = re.compile(r"[\w.+-]+@[\w-]+(?:\.[\w-]+)+")
BEARER = re.compile(r"(Bearer\s+)\S+")
CARD = re.compile(r"\b(?:\d[ -]?){12,15}\d\b")

def redact(line):
    line = EMAIL.sub("[email]", line)
    line = BEARER.sub(r"\1[token]", line)
    return CARD.sub("[card]", line)
```

<DeepDive title="More about regex">

**Alternation.** A vertical bar means "or": `cat` or `dog`; group it to limit its scope.

**Lookarounds.** `(?=...)` and `(?!...)` check what follows without consuming it, for example a password rule "contains a digit".

**Flags.** `re.MULTILINE` makes `^` and `$` match at every line, `re.DOTALL` lets `.` match newlines, and `re.ASCII` restricts `\d` and `\w` to ASCII (by default they include other scripts' digits and letters).

**Replacement functions.** `re.sub` accepts a function that receives the match and returns the replacement, useful for computed replacements.

**Tools.** Online testers like regex101 explain patterns step by step; `grep -E` and `sed -E` use similar syntax on the command line.

</DeepDive>

<DeepDive title="Real world: the outage caused by one regex">

A well-known CDN outage in 2019 was caused by a single new firewall rule whose regex contained nested `.*` patterns. When deployed globally, it caused catastrophic backtracking, CPU on every edge server hit 100%, and traffic failed worldwide for about half an hour.

The lessons applied afterwards:

1. Regex engines with guaranteed linear time for rules that run on untrusted traffic.
2. Staged rollouts for configuration, not just code.
3. CPU limits and kill switches for rule evaluation.

</DeepDive>

<DeepDive title="Security lens">

- **ReDoS**: avoid nested or overlapping quantifiers on user input, limit input sizes, and use linear-time engines (RE2) for untrusted patterns.
- **Anchored validation** with `fullmatch`; allow-lists (what's allowed) are safer than block-lists.
- **Don't sanitize HTML with regex** to prevent XSS; use a proper sanitizer and output escaping.
- **Escape user text** with `re.escape` when inserting it into a pattern.
- **Redact secrets** (tokens, passwords, card numbers) in logs with tested patterns.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between re.search, re.match and re.fullmatch?">
search finds the first match anywhere in the string, match only tries at the beginning, and fullmatch succeeds only if the entire string matches the pattern.
</QA>

<QA q="What is the difference between greedy and lazy quantifiers?">
Greedy quantifiers match as many characters as possible and back off if needed, while lazy quantifiers, written with a trailing question mark, match as few as possible.
</QA>

<QA q="When should you not use regex?">
For nested or structured formats such as HTML, JSON, CSV and URLs, where dedicated parsers handle edge cases correctly, and for simple checks that string methods handle more clearly.
</QA>

<QA q="What causes catastrophic backtracking?">
Patterns with nested or ambiguous quantifiers, such as (a+)+, where the engine can split the input in exponentially many ways and tries them all when the overall match fails.
</QA>

<QA q="Why compile a regex?">
Compiling creates a reusable pattern object, which avoids repeated parsing in loops, lets you attach flags once, and gives the pattern a descriptive name.
</QA>

</DeepDive>
