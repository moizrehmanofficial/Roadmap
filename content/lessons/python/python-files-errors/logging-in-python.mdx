<BigIdea>
<Tr>
<En>
**Logging** records what a program is doing so you can understand it later, especially when something goes wrong in production where you can't attach a debugger. Python's built-in **`logging`** module gives every message a **level**: `DEBUG` (details for developers), `INFO` (normal events), `WARNING` (something odd but handled), `ERROR` (an operation failed) and `CRITICAL` (the program may not continue). You configure logging **once** at program start, for example with **`logging.basicConfig(level=logging.INFO, format=...)`**, and each module gets its own **named logger** with **`logging.getLogger(__name__)`**. Anything below the configured level is dropped cheaply, so debug messages can stay in the code. Pass values as **arguments** (`log.info("user %s", user_id)`) instead of f-strings, and inside `except` blocks call **`log.exception(...)`** to include the traceback. Under the hood a logger sends **records** to **handlers** (where logs go: console, file, rotating file, syslog), each with a **formatter** (how they look: plain text or JSON) and optional **filters** (drop or modify records, for example redacting passwords). Production systems usually write **structured (JSON) logs** with context such as a request ID, so tools like Loki, Elasticsearch or CloudWatch can search them, and they never log secrets.
</En>
<Ur>
**Logging** record karti hai ke program kya kar raha hai taa ke baad me samajh sakein, khaas kar jab production me kuch ghalat ho jahan debugger nahi laga sakte. Python ka built-in **`logging`** module har paigham ko **level** deta hai: `DEBUG` (developers ke liye tafseelat), `INFO` (aam waqiat), `WARNING` (kuch ajeeb magar sambhala gaya), `ERROR` (koi kaam nakam hua) aur `CRITICAL` (program shayad jaari na reh sake). Aap logging program ke shuru me **ek dafa** configure karte hain, maslan **`logging.basicConfig(level=logging.INFO, format=...)`** se, aur har module ko **`logging.getLogger(__name__)`** se apna **naam wala logger** milta hai. Configure kiye level se neeche ki har cheez sasti tarah gira di jati hai, isliye debug paighamat code me reh sakte hain. Values f-strings ke bajaye **arguments** ke taur par dein (`log.info("user %s", user_id)`), aur `except` blocks ke andar traceback shamil karne ke liye **`log.exception(...)`** bulayen. Andar se logger **records** ko **handlers** (logs kahan jate: console, file, rotating file, syslog) tak bhejta hai, har ek ke saath **formatter** (kaise dikhte: saada text ya JSON) aur ikhtiyari **filters** (records girate ya badalte, maslan passwords chhupana). Production systems aam taur par request ID jaise context ke saath **structured (JSON) logs** likhte hain, taa ke Loki, Elasticsearch ya CloudWatch jaise tools unhe dhoond sakein, aur kabhi secrets log nahi karte.
</Ur>

## Picture it

<Tr>
<En>

Think of a **ship's logbook system**.

- Every crew member (logger) writes entries marked routine, notice, warning, damage or emergency (levels).
- The captain decides once what gets recorded: in calm seas only warnings and above, during an investigation everything.
- Copies of entries are sent to different places (handlers): the bridge screen, the paper logbook, and headquarters by radio, each in its own format (formatters).
- An officer reviews entries before they're sent and blacks out the safe combination if someone wrote it down (filters).

## Learn it step by step

<Walkthrough>

<Step title="Levels, basicConfig, named loggers and log.exception">

<Tr>
<En>
`basics.py` logs before any configuration, then configures logging with `basicConfig` and a custom format, logs at every level from a named logger, logs an exception with its traceback, uses a child logger, quiets a third-party library's logger, and prints a logger's effective level. We send stderr to stdout and strip the folder from paths so the output is the same on any machine.
</En>
<Ur>
`basics.py` kisi configuration se pehle log karti, phir `basicConfig` aur apne format se logging configure karti, naam wale logger se har level par log karti, exception us ke traceback ke saath log karti, child logger istemal karti, third-party library ka logger khamosh karti, aur logger ka asal level print karti hai. Hum stderr ko stdout par bhejte aur paths se folder hata dete hain taa ke output har machine par ek jaisa ho.
</Ur>
</Tr>

```bash
cat > basics.py <<'EOF'
import logging, sys

# Before any configuration: only WARNING and above are shown, on stderr
logging.debug("hidden: default level is WARNING")
logging.warning("disk usage at %d%%", 91)

# Configure once, at program start (force=True replaces the default setup above)
logging.basicConfig(level=logging.INFO, stream=sys.stdout, force=True,
                    format="%(levelname)-8s %(name)s: %(message)s")

log = logging.getLogger("billing")          # one named logger per module: getLogger(__name__)
log.debug("not shown: below INFO")
log.info("charging customer %s for $%.2f", "cus_1042", 49.5)    # lazy %-formatting
log.warning("retrying payment, attempt %d of %d", 2, 3)
log.error("payment failed for %s", "cus_1042")

def risky():
    return {"plan": "pro"}["price"]
try:
    risky()
except KeyError:
    log.exception("could not price order 1042")   # ERROR + full traceback

logging.getLogger("billing.stripe").info("child loggers inherit config")
logging.getLogger("urllib3").setLevel(logging.WARNING)   # quiet a noisy library
logging.getLogger("urllib3").info("you won't see this")
print("effective level of billing.stripe:", logging.getLevelName(logging.getLogger("billing.stripe").getEffectiveLevel()))
EOF
python3 basics.py 2>&1 | sed "s#$PWD/##"
```

<Happened>
<Tr>
<En>

- Without configuration, Python only shows **WARNING and above** in a bare `LEVEL:logger:message` format on stderr; the debug message vanished.
- `basicConfig(..., force=True)` replaced that default with our format and level INFO. Call it **once** at the entry point of the application; libraries should never call it.
- `getLogger("billing")` created a named logger; in real modules use `getLogger(__name__)` so the name shows which module logged. `debug` was dropped because it's below INFO.
- Arguments like `"for $%.2f", 49.5` are formatted **only if the record is emitted**, which is cheaper than f-strings and lets log platforms group identical messages.
- `log.exception` logged at **ERROR** and appended the full traceback, including the exact line and the `KeyError`. Use it inside `except`; outside, there is no traceback to add.
- `billing.stripe` is a **child** of `billing`, so it used the same configuration. Setting `urllib3` to WARNING silenced that library's info messages, a common fix for noisy dependencies.

</En>
<Ur>

- Configuration ke baghair Python stderr par saade `LEVEL:logger:message` format me sirf **WARNING aur upar** dikhata hai; debug paigham ghayab ho gaya.
- `basicConfig(..., force=True)` ne us default ko hamare format aur INFO level se badal diya. Ise application ke entry point par **ek dafa** bulayen; libraries ko ise kabhi nahi bulana chahiye.
- `getLogger("billing")` ne naam wala logger banaya; asal modules me `getLogger(__name__)` lein taa ke naam bataye kis module ne log kiya. `debug` gira diya gaya kyunke woh INFO se neeche hai.
- `"for $%.2f", 49.5` jaise arguments **sirf tab format hote jab record bheja jaye**, jo f-strings se sasta hai aur log platforms ko ek jaise paighamat ikatthe karne deta hai.
- `log.exception` ne **ERROR** par log kiya aur poora traceback joda, bilkul line aur `KeyError` samait. Ise `except` ke andar lein; bahar jorne ko koi traceback nahi hota.
- `billing.stripe` `billing` ka **child** hai, isliye usne wahi configuration li. `urllib3` ko WARNING par rakhne se us library ke info paighamat khamosh ho gaye, shor machane wali dependencies ka aam hal.

</Ur>
</Tr>

<Step title="Handlers, JSON formatting, context, redaction and rotation">

<Tr>
<En>
`advanced.py` builds a logger with two handlers: the console gets INFO and above as **JSON** through a custom formatter and a filter that redacts secret fields, while a **rotating file** gets everything as plain text and keeps at most three small files. We log with extra context (user, IP, request ID), including one record that carries a password, then an exception, then a burst of debug messages that forces rotation. Finally we list the files and show the newest one with timestamps hidden.
</En>
<Ur>
`advanced.py` do handlers wala logger banati: console ko custom formatter aur secret fields chhupane wale filter ke zariye INFO aur upar **JSON** me milta, jabke **rotating file** ko sab kuch saade text me milta aur woh zyada se zyada teen chhoti files rakhti hai. Hum zayed context (user, IP, request ID) ke saath log karte, jis me ek record password bhi rakhta hai, phir exception, phir debug paighamat ki bauchhar jo rotation karwati hai. Aakhir me files ki list aur taazi file timestamps chhupa kar dikhate hain.
</Ur>
</Tr>

```bash
cat > advanced.py <<'EOF'
import json, logging, logging.handlers, sys

class JsonFormatter(logging.Formatter):
    def format(self, record):
        data = {"level": record.levelname, "logger": record.name, "msg": record.getMessage()}
        data.update(getattr(record, "ctx", {}))                 # extra fields
        if record.exc_info:
            data["error"] = repr(record.exc_info[1])
        return json.dumps(data)

class RedactFilter(logging.Filter):
    SECRETS = ("password", "token", "api_key")
    def filter(self, record):
        ctx = getattr(record, "ctx", None)
        if ctx:
            record.ctx = {k: ("***" if k in self.SECRETS else v) for k, v in ctx.items()}
        return True                                             # keep the record

log = logging.getLogger("api")
log.setLevel(logging.DEBUG)
log.propagate = False

console = logging.StreamHandler(sys.stdout)                     # console: INFO+, JSON
console.setLevel(logging.INFO)
console.setFormatter(JsonFormatter())
console.addFilter(RedactFilter())

rotating = logging.handlers.RotatingFileHandler("api.log", maxBytes=300, backupCount=2, encoding="utf-8")
rotating.setLevel(logging.DEBUG)                                # file: everything, plain text
rotating.setFormatter(logging.Formatter("%(asctime)s %(levelname)s %(message)s", "%Y-%m-%dT%H:%M:%S"))
log.addHandler(console)
log.addHandler(rotating)

log.info("login ok", extra={"ctx": {"user": "jane", "ip": "203.0.113.7", "request_id": "req-7f3a"}})
log.warning("login failed", extra={"ctx": {"user": "bob", "password": "hunter2", "request_id": "req-7f3b"}})
log.debug("cache miss for key user:42")                         # file only
try:
    1 / 0
except ZeroDivisionError:
    log.error("report crashed", exc_info=True, extra={"ctx": {"request_id": "req-7f3c"}})
for i in range(8):
    log.debug("heartbeat %d", i)
EOF
python3 advanced.py
echo "--- files:"; ls api.log*
echo "--- newest file, timestamps hidden:"; sed -E 's/^[0-9T:-]{19} /<time> /' api.log
```

```text output
<time> DEBUG heartbeat 7
```

<Happened>
<Tr>
<En>

- The console printed **one JSON object per line** with fields (`user`, `ip`, `request_id`) instead of a sentence. Log platforms parse these, so you can search "all logs for req-7f3b" or "failed logins by IP".
- `RedactFilter` replaced the password with `***` before the record was formatted. Filters run for every record, so one filter protects every log call.
- The `ERROR` record included the exception as a field because we passed `exc_info=True`.
- The **debug** messages never reached the console (its handler level is INFO) but did go to the file (its level is DEBUG): **handlers have their own levels**, so one logger can feed a quiet console and a detailed file.
- `RotatingFileHandler(maxBytes=300, backupCount=2)` started a new file whenever `api.log` would grow past 300 bytes, keeping **api.log.1** and **api.log.2** and deleting older ones. Real values are more like 10 MB and 5 backups; without rotation logs fill disks.
- We set `propagate = False` so records don't also reach the root logger and print twice.

</En>
<Ur>

- Console ne jumle ke bajaye fields (`user`, `ip`, `request_id`) ke saath **har line ek JSON object** print kiya. Log platforms inhe parse karte hain, isliye aap "req-7f3b ke tamam logs" ya "IP ke hisaab se nakam logins" dhoond sakte hain.
- `RedactFilter` ne record format hone se pehle password ko `***` se badla. Filters har record par chalte hain, isliye ek filter har log call ki hifazat karta hai.
- `ERROR` record ne exception ko field ke taur par shamil kiya kyunke humne `exc_info=True` diya.
- **Debug** paighamat console tak kabhi nahi pohanche (us ke handler ka level INFO hai) magar file me gaye (us ka level DEBUG hai): **handlers ke apne levels hote hain**, isliye ek logger khamosh console aur tafseeli file dono ko bhar sakta hai.
- `RotatingFileHandler(maxBytes=300, backupCount=2)` ne jab bhi `api.log` 300 bytes se barhne wali hoti nayi file shuru ki, **api.log.1** aur **api.log.2** rakhin aur purani delete kar din. Asal values 10 MB aur 5 backups jaisi hoti hain; rotation ke baghair logs disks bhar dete hain.
- Humne `propagate = False` rakha taa ke records root logger tak bhi na jayen aur do dafa print na hon.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="print and f-strings, swallowing errors">

```text
def charge(order):
    try:
        gateway.charge(order)
    except Exception as e:
        print(f"error: {e}")                      # no level, no traceback, no context
    print(f"charged {order.card_number}")         # leaks card data
```

</Bad>
<Good title="Named logger, exception with traceback, no secrets">

```text
log = logging.getLogger(__name__)

def charge(order):
    try:
        gateway.charge(order)
    except GatewayError:
        log.exception("charge failed for order %s", order.id)
        raise
    log.info("charged order %s (card ending %s)", order.id, order.card_last4)
```

</Good>
</Compare>

<Compare>
<Bad title="Configuring logging inside a library">

```text
# mylib/client.py
import logging
logging.basicConfig(level=logging.DEBUG)      # hijacks every app that imports it
logging.info("client ready")                  # logs on the root logger
```

</Bad>
<Good title="Libraries only get a logger">

```text
# mylib/client.py
import logging
log = logging.getLogger(__name__)
log.debug("client ready")                     # the application decides what to show
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Logging secrets or personal data**: passwords, tokens, full card numbers, session cookies.
- **`log.error(str(e))` instead of `log.exception`**: the traceback is lost.
- **Logging the same exception at every layer**: log once where you handle it; otherwise one error looks like five.
- **DEBUG level in production by default**: huge volume, cost and more chance of leaking data.
- **Writing user input into logs unescaped**: newlines can forge fake log lines (log injection); structured JSON logs avoid this.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Secrets ya zaati data log karna**: passwords, tokens, poore card numbers, session cookies.
- **`log.exception` ke bajaye `log.error(str(e))`**: traceback kho jata hai.
- **Har layer par wahi exception log karna**: jahan sambhalein wahan ek dafa log karein; warna ek error paanch jaisa lagta hai.
- **Production me default DEBUG level**: bohat zyada miqdar, kharcha aur data leak ka zyada imkaan.
- **User input escape kiye baghair logs me likhna**: newlines jaali log lines bana sakti hain (log injection); structured JSON logs is se bachate hain.

</Ur>
</Tr>

<Challenge title="Count levels with a custom handler">

<Tr>
<En>
Write a `CountingHandler(logging.Handler)` that counts records per level name in a dict, attach it to a logger named `jobs` set to DEBUG (with `propagate = False`), log 2 debug, 3 info, 1 warning and 2 error messages, and print the counts. Then raise the handler's level to WARNING, log one more info and one more error, and print the counts again.
</En>
<Ur>
`CountingHandler(logging.Handler)` likhein jo har level ke naam ke records dict me gine, ise DEBUG par set `jobs` naam ke logger se joren (`propagate = False` ke saath), 2 debug, 3 info, 1 warning aur 2 error paighamat log karein, aur ginti print karein. Phir handler ka level WARNING tak barhayen, ek aur info aur ek aur error log karein, aur ginti dobara print karein.
</Ur>

<Solution>

<Tr>
<En>

```text
import logging
```

```text
import logging, sys

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter("%(levelname)s [%(request_id)s] %(message)s"))
base = logging.getLogger("web")
base.setLevel(logging.INFO)
base.propagate = False
base.addHandler(handler)

def handle(request_id, ms):
    log = logging.LoggerAdapter(base, {"request_id": request_id})
    log.info("start")
    if ms is not None:
        log.info("done in %d ms", ms)

handle("req-001", 42)
handle("req-002", None)
```

<DeepDive title="More about logging">

**dictConfig.** `logging.config.dictConfig` sets up loggers, handlers and formatters from a dict, often loaded from YAML, so configuration lives outside code.

**Libraries.** `structlog` and `python-json-logger` make structured logging easier; `loguru` offers a simpler API.

**Performance.** Logging calls are cheap when disabled; for expensive values check `log.isEnabledFor(logging.DEBUG)` first. `QueueHandler` moves slow I/O to a background thread.

**Time.** Set `Formatter.converter = time.gmtime` and an ISO format to log in UTC.

**Warnings.** `logging.captureWarnings(True)` routes `warnings` messages into logging.

</DeepDive>

<DeepDive title="Real world: the incident nobody could trace">

An API returned occasional 500 errors. Each service printed messages like "error happened" with no timestamps in UTC, no request IDs, and exceptions caught with `print(e)`. Engineers spent two days correlating logs by guessing times across servers in different zones.

The fixes:

1. JSON logs with UTC timestamps, service name, level and a request ID generated at the edge and passed in a header to every service.
2. `log.exception` wherever errors are handled.
3. Central log search with alerts on ERROR rates.

The next similar incident was diagnosed in minutes by searching one request ID.

</DeepDive>

<DeepDive title="Security lens">

- **Never log secrets**: passwords, tokens, API keys, session IDs, full card numbers; add redaction filters as a safety net.
- **Log security events**: logins (success and failure), permission changes, admin actions, with who, what, when and from where.
- **Log injection**: user input containing newlines can fake entries; JSON logs or escaping prevent it.
- **Protect log files**: restrictive permissions, and ship them off the host so attackers can't erase them.
- **Retention and privacy**: logs may contain personal data; keep them only as long as needed.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the standard logging levels in Python?">
DEBUG, INFO, WARNING, ERROR and CRITICAL, with numeric values 10 to 50; records below a logger's or handler's level are ignored.
</QA>

<QA q="Why should libraries not call basicConfig?">
Logging configuration belongs to the application; a library calling basicConfig changes the root logger for every program that imports it. Libraries should only create named loggers.
</QA>

<QA q="What is the difference between a logger, a handler and a formatter?">
A logger is what code calls to create records, a handler sends records to a destination such as the console or a file, and a formatter turns a record into the final text.
</QA>

<QA q="Why pass arguments to log calls instead of using f-strings?">
Arguments are only formatted if the record is emitted, saving work when the level is disabled, and the constant message template lets log tools group similar events.
</QA>

<QA q="How do you include a traceback in a log?">
Call log.exception inside an except block, or pass exc_info=True to another logging method.
</QA>

</DeepDive>
