<BigIdea>
<Tr>
<En>
A **detection** is a rule that looks at events and raises an **alert** when something suspicious happens. On a Linux server, `/var/log/auth.log` (or `journalctl -u ssh`) records SSH logins and `sudo` commands, which is where many attacks first become visible. Writing a detection script means four steps. **Parse** each line into an event with a timestamp, a type and fields (user, IP, command), using precise regexes and skipping lines you don't understand. **Keep state**: most attacks are patterns over time, not single lines, so you track recent failures per IP in a **sliding window** (a `deque` of timestamps that drops entries older than, say, five minutes). **Apply rules** with clear thresholds and **severities**: ten failed logins in five minutes is a brute-force attempt (medium), a successful password login from an IP that just failed several times may be a compromised account (high), and `sudo cat /etc/shadow` is high no matter what. **Emit alerts** in a structured format such as JSON Lines that a SIEM, ticketing system or chat bot can consume, fire each alert **once** rather than on every following line, and return an **exit code** automation can act on. Every threshold is a trade-off: too low and analysts drown in **false positives**, too high and real attacks slip through as **false negatives**, so test rules against known good and bad data.
</En>
<Ur>
**Detection** aisa qaida hai jo events dekhta aur jab kuch mashkook ho to **alert** uthata hai. Linux server par `/var/log/auth.log` (ya `journalctl -u ssh`) SSH logins aur `sudo` commands record karta hai, aur yahin kai hamle pehli dafa nazar aate hain. Detection script likhne ke chaar qadam hain. Har line ko timestamp, qism aur fields (user, IP, command) wale event me **parse** karein, durust regexes ke saath aur na samajh aane wali lines chhor kar. **State rakhein**: zyadatar hamle akeli lines nahi balke waqt ke saath patterns hain, isliye aap har IP ki haaliya nakamiyan **sliding window** me rakhte hain (timestamps ka `deque` jo maslan paanch minute se purani entries gira deta). Wazeh hadd aur **severities** ke saath **qawaid lagayen**: paanch minute me das nakam logins brute-force koshish (medium), aisi IP se kamyab password login jo abhi kai dafa nakam hui ho shayad hack hua account (high), aur `sudo cat /etc/shadow` har haal me high. **Alerts** JSON Lines jaisi structured shakal me **nikalein** jise SIEM, ticketing system ya chat bot parh sake, har alert har agli line par nahi balke **ek dafa** chalayen, aur aisa **exit code** lautayen jis par automation amal kar sake. Har hadd ek samjhauta hai: bohat kam to analysts **false positives** me doob jate, bohat zyada to asal hamle **false negatives** ban kar nikal jate, isliye qawaid ko maloom achhe aur bure data par test karein.
</Ur>

## Picture it

<Tr>
<En>

Think of a **night guard watching the building's door log**.

- One person mistyping their PIN is normal. The same stranger trying ten codes in five minutes is not: that's a threshold inside a time window.
- If that stranger finally gets in, that's far more serious than the failed attempts: the severity goes up.
- The guard writes **one** report per incident, not one per failed attempt, or nobody would read them.
- Set the rule too strict and the guard calls the police every time an employee forgets their code (false positives); too loose and a real burglar walks in unnoticed (false negatives).

</En>
<Ur>

**Building ke darwaze ka log dekhta raat ka guard** socheyn.

- Ek shakhs ka apna PIN ghalat likhna aam hai. Wahi ajnabi paanch minute me das codes aazmaye to aam nahi: ye waqt ki window ke andar hadd hai.
- Agar woh ajnabi aakhir andar aa jaye, to ye nakam koshishon se kahin zyada sangeen hai: severity barh jati hai.
- Guard har waqiye ki **ek** report likhta, har nakam koshish ki nahi, warna koi nahi parhega.
- Qaida bohat sakht rakhein to guard har us waqt police bulata jab koi mulazim code bhoole (false positives); bohat dheela to asal chor bina nazar aaye andar chala jata (false negatives).

## Learn it step by step

<Walkthrough>

<Step title="A realistic auth.log and a sliding-window brute-force rule">

<Tr>
<En>
`make_auth_log.py` writes a synthetic `auth.log` with a normal user's logins, a brute-force run of 40 failures from one IP against several usernames, a slower series of failures for `bob` followed by a successful password login and a suspicious `sudo` command, and one harmless typo. `bruteforce.py` parses the failed-login lines, keeps a five-minute sliding window of failures per IP, alerts once when an IP reaches ten, and lists IPs that stayed below the threshold.
</En>
<Ur>
`make_auth_log.py` ek farzi `auth.log` likhti hai jis me aam user ke logins, ek IP se kai usernames par 40 nakamiyon ka brute-force silsila, `bob` ke liye nakamiyon ka dheema silsila jis ke baad kamyab password login aur mashkook `sudo` command, aur ek be-zarar typo hai. `bruteforce.py` nakam login wali lines parse karti, har IP ki nakamiyon ki paanch minute ki sliding window rakhti, IP ke das tak pohanchne par ek dafa alert karti, aur hadd se neeche rehne wali IPs ki list deti hai.
</Ur>
</Tr>

```bash
cat > make_auth_log.py <<'EOF'
# A synthetic /var/log/auth.log (sshd and sudo lines), deterministic
lines = []
def add(t, msg):
    lines.append(f"Nov 23 {t} web01 {msg}")
for i in range(3):                                                # normal user, normal day
    add(f"08:0{i}:10", f"sshd[1{i}01]: Accepted publickey for jane from 203.0.113.10 port 5{i}222 ssh2")
for i in range(40):                                               # brute force from one IP
    m, s = divmod(i * 4, 60)
    user = ["root", "admin", "oracle", "test"][i % 4]
    add(f"09:{m:02d}:{s:02d}", f"sshd[2{i:03d}]: Failed password for invalid user {user} from 198.51.100.66 port 4{i:04d} ssh2")
for i in range(6):                                                # slow guessing, then success
    add(f"10:{i * 2:02d}:00", f"sshd[3{i}00]: Failed password for bob from 192.0.2.44 port 6{i}000 ssh2")
add("10:13:05", "sshd[3700]: Accepted password for bob from 192.0.2.44 port 61999 ssh2")
add("10:14:30", "sudo:      bob : TTY=pts/1 ; PWD=/home/bob ; USER=root ; COMMAND=/usr/bin/cat /etc/shadow")
add("10:20:00", "sshd[3800]: Failed password for jane from 203.0.113.10 port 52000 ssh2")   # one typo
open("auth.log", "w").write("\n".join(lines) + "\n")
print("lines written:", len(lines))
EOF
python3 make_auth_log.py

cat > bruteforce.py <<'EOF'
import re
from collections import defaultdict, deque
from datetime import datetime, timedelta

FAILED = re.compile(r"^(?P<ts>\w{3} \d+ [\d:]{8}) \S+ sshd\[\d+\]: Failed password for (?:invalid user )?"
                    r"(?P<user>\S+) from (?P<ip>[\d.]+)")
WINDOW, THRESHOLD = timedelta(minutes=5), 10

def parse_ts(text, year=2026):
    return datetime.strptime(f"{year} {text}", "%Y %b %d %H:%M:%S")

recent = defaultdict(deque)          # ip -> timestamps of failures inside the window
alerted = set()
users = defaultdict(set)
with open("auth.log", encoding="utf-8") as f:
    for line in f:
        m = FAILED.match(line)
        if not m:
            continue
        ts, ip = parse_ts(m["ts"]), m["ip"]
        users[ip].add(m["user"])
        q = recent[ip]
        q.append(ts)
        while q and ts - q[0] > WINDOW:             # slide the window forward
            q.popleft()
        if len(q) >= THRESHOLD and ip not in alerted:
            alerted.add(ip)
            print(f"ALERT brute force: {ip} had {len(q)} failures in 5 min "
                  f"(first {q[0]:%H:%M:%S}, now {ts:%H:%M:%S}), users tried: {sorted(users[ip])}")

for ip in sorted(users):
    if ip not in alerted:
        print(f"below threshold: {ip} ({sorted(users[ip])})")
EOF
python3 bruteforce.py
```

```text output
lines written: 52
ALERT brute force: 198.51.100.66 had 10 failures in 5 min (first 09:00:00, now 09:00:36), users tried: ['admin', 'oracle', 'root', 'test']
below threshold: 192.0.2.44 (['bob'])
below threshold: 203.0.113.10 (['jane'])
```

<Happened>
<Tr>
<En>

- The regex matched both `Failed password for jane` and `Failed password for invalid user root` thanks to the optional `(?:invalid user )?` group; all other lines (accepted logins, sudo) were skipped.
- syslog timestamps have **no year**, so we added one when parsing. In real tools, take the year from the file's date or use systemd's journal, which stores full timestamps.
- Each IP got its own `deque` of failure times; old entries fell off the front once they were more than five minutes older than the newest. `198.51.100.66` reached **10 failures in 36 seconds** and triggered **one** alert, even though it went on to fail 30 more times, because we remember which IPs already alerted.
- The alert included the usernames tried (**admin, oracle, root, test**): many non-existent accounts from one IP also suggests automated password spraying, which is worth its own rule.
- `bob`'s six failures over ten minutes and `jane`'s single typo stayed **below the threshold**. The slow series is exactly what a simple brute-force rule misses, which the next step handles from another angle.

</En>
<Ur>

- Ikhtiyari `(?:invalid user )?` group ki badolat regex ne `Failed password for jane` aur `Failed password for invalid user root` dono milaye; baqi tamam lines (kamyab logins, sudo) chhor di gayin.
- syslog timestamps me **saal nahi** hota, isliye humne parse karte waqt jora. Asal tools me saal file ki taareekh se lein ya systemd ka journal istemal karein, jo poore timestamps rakhta hai.
- Har IP ko nakamiyon ke waqton ka apna `deque` mila; purani entries sab se nayi se paanch minute purani hote hi aage se gir gayin. `198.51.100.66` **36 second me 10 nakamiyon** tak pohanchi aur **ek** alert chala, halanke woh 30 dafa aur nakam hui, kyunke hum yaad rakhte hain kin IPs par pehle alert ho chuka.
- Alert me aazmaye gaye usernames (**admin, oracle, root, test**) shamil the: ek IP se kai na-mojood accounts automated password spraying ki taraf bhi ishara karte, jis ka apna qaida banana chahiye.
- `bob` ki das minute me chhe nakamiyan aur `jane` ka akela typo **hadd se neeche** rahe. Dheema silsila bilkul wahi hai jo saada brute-force qaida chhor deta, jise agla qadam doosre zaviye se sambhalta hai.

</Ur>
</Tr>

<Step title="A small rule engine with severities, JSON alerts and exit codes">

<Tr>
<En>
`detect.py` turns every interesting line into an event (failed login, accepted login, sudo command), then applies three rules: brute force (medium), a password login from an IP with recent failures (high), and sudo commands touching sensitive files or tools (high). Alerts are `@dataclass` objects, printed for humans, written as JSON Lines for machines, and the script exits with 2 when any high-severity alert fired.
</En>
<Ur>
`detect.py` har dilchasp line ko event (nakam login, kamyab login, sudo command) me badalti, phir teen qawaid lagati hai: brute force (medium), haaliya nakamiyon wali IP se password login (high), aur hassas files ya tools chhoone wali sudo commands (high). Alerts `@dataclass` objects hain, insaanon ke liye print, machines ke liye JSON Lines me likhe, aur koi high-severity alert chale to script 2 se nikalti hai.
</Ur>
</Tr>

```bash
cat > detect.py <<'EOF'
import json, re, sys
from collections import defaultdict, deque
from dataclasses import dataclass, asdict
from datetime import datetime, timedelta

PATTERNS = {
    "failed":   re.compile(r"sshd\[\d+\]: Failed password for (?:invalid user )?(?P<user>\S+) from (?P<ip>[\d.]+)"),
    "accepted": re.compile(r"sshd\[\d+\]: Accepted (?P<method>\w+) for (?P<user>\S+) from (?P<ip>[\d.]+)"),
    "sudo":     re.compile(r"sudo:\s+(?P<user>\S+) : .*COMMAND=(?P<cmd>.+)$"),
}
SENSITIVE = ("/etc/shadow", "/etc/sudoers", "useradd", "visudo", "curl ", "nc ")

@dataclass
class Alert:
    time: str
    rule: str
    severity: str
    detail: str

def events(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            ts = datetime.strptime("2026 " + line[:15], "%Y %b %d %H:%M:%S")
            for kind, rx in PATTERNS.items():
                if m := rx.search(line):
                    yield ts, kind, m.groupdict()

def detect(path):
    alerts, fails = [], defaultdict(deque)
    for ts, kind, d in events(path):
        if kind == "failed":
            q = fails[d["ip"]]
            q.append(ts)
            while q and ts - q[0] > timedelta(minutes=5):
                q.popleft()
            if len(q) == 10:                                       # fire once when crossing
                alerts.append(Alert(f"{ts:%H:%M:%S}", "ssh_bruteforce", "medium",
                                    f"{d['ip']}: 10 failed logins in 5 minutes"))
        elif kind == "accepted":
            recent = [t for t in fails[d["ip"]] if ts - t <= timedelta(minutes=30)]
            if d["method"] == "password" and len(recent) >= 3:
                alerts.append(Alert(f"{ts:%H:%M:%S}", "login_after_failures", "high",
                                    f"{d['user']} logged in from {d['ip']} after {len(recent)} failures"))
        elif kind == "sudo" and any(s in d["cmd"] for s in SENSITIVE):
            alerts.append(Alert(f"{ts:%H:%M:%S}", "sensitive_sudo", "high",
                                f"{d['user']} ran: {d['cmd']}"))
    return alerts

alerts = detect("auth.log")
for a in alerts:
    print(f"[{a.severity.upper():<6}] {a.time} {a.rule:<20} {a.detail}")
with open("alerts.jsonl", "w") as f:                 # one JSON object per line for a SIEM or chat bot
    for a in alerts:
        f.write(json.dumps(asdict(a)) + "\n")
print("alerts.jsonl lines:", sum(1 for _ in open("alerts.jsonl")))
sys.exit(2 if any(a.severity == "high" for a in alerts) else 0)
EOF
python3 detect.py; echo "exit code: $?"
```

```text output
[MEDIUM] 09:00:36 ssh_bruteforce       198.51.100.66: 10 failed logins in 5 minutes
[HIGH  ] 10:13:05 login_after_failures bob logged in from 192.0.2.44 after 3 failures
[HIGH  ] 10:14:30 sensitive_sudo       bob ran: /usr/bin/cat /etc/shadow
alerts.jsonl lines: 3
exit code: 2
```

<Happened>
<Tr>
<En>

- The brute-force rule fired **once**, at the moment the count reached exactly 10 (`len(q) == 10`), a simple way to avoid an alert on every following line.
- `bob` logged in with a **password** from `192.0.2.44` shortly after failing from the same address, so `login_after_failures` raised a **high** alert. It reported **3** failures because the shared deque only keeps the last five minutes; bob actually failed six times over ten minutes. For this rule you'd keep a longer history per IP, which is a good example of how a rule's data structure shapes what it can see.
- One minute later bob ran `sudo cat /etc/shadow`, matched by the **sensitive_sudo** rule. Together these two alerts tell a story (guessed password, then privilege use) that analysts look for: correlation matters more than any single line.
- `alerts.jsonl` holds one JSON object per alert, ready to be shipped to a SIEM, posted to a chat channel, or turned into tickets.
- The script exited with **2** because high alerts fired, so a scheduler or CI-style runner can escalate (page someone) without parsing the text.

</En>
<Ur>

- Brute-force qaida **ek dafa** chala, usi lamhe jab ginti bilkul 10 tak pohanchi (`len(q) == 10`), har agli line par alert se bachne ka saada tareeqa.
- `bob` ne usi address se nakam hone ke thori der baad `192.0.2.44` se **password** ke saath login kiya, isliye `login_after_failures` ne **high** alert uthaya. Is ne **3** nakamiyan bataein kyunke mushtarka deque sirf aakhri paanch minute rakhta hai; bob asal me das minute me chhe dafa nakam hua. Is qaide ke liye aap har IP ki lambi tareekh rakhenge, jo achhi misaal hai ke qaide ka data structure kaise tay karta hai ke woh kya dekh sakta hai.
- Ek minute baad bob ne `sudo cat /etc/shadow` chalaya, jo **sensitive_sudo** qaide se mila. Ye do alerts mil kar ek kahani batate (andaze se password, phir ikhtiyarat ka istemal) jo analysts dhoondte hain: kisi akeli line se zyada rabt ahem hai.
- `alerts.jsonl` har alert ka ek JSON object rakhti, SIEM bhejne, chat channel par post karne, ya tickets banane ke liye tayyar.
- High alerts chalne ki wajah se script **2** se nikli, isliye scheduler ya CI jaisa runner text parse kiye baghair masle ko aage barha sakta (kisi ko page kar sakta) hai.

</Ur>

## Common mistakes

<Compare>
<Bad title="An alert for every matching line">

```text
for line in log:
    if "Failed password" in line:
        send_alert(line)            # 40 alerts for one attack; analysts mute the channel
```

</Bad>
<Good title="Thresholds, windows and one alert per incident">

```text
if len(window[ip]) == THRESHOLD and ip not in alerted:
    alerted.add(ip)
    send_alert({"rule": "ssh_bruteforce", "ip": ip, "count": THRESHOLD})
```

</Good>
</Compare>

<Compare>
<Bad title="Loose substring checks">

```text
if "Accepted" in line and "root" in line:     # matches "Accepted publickey for rootkit-scanner"
    alert("root login")
```

</Bad>
<Good title="Anchored, field-aware parsing">

```text
m = re.search(r"Accepted (?P<method>\w+) for (?P<user>\S+) from (?P<ip>[\d.]+)", line)
if m and m["user"] == "root":
    alert("root_login", m.groupdict())
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Ignoring time zones and missing years** in syslog timestamps: normalize to UTC with full dates.
- **Never testing rules**: keep sample logs with known attacks and normal days, and test thresholds against both.
- **Unbounded state** (every IP ever seen in memory): expire old keys.
- **Trusting log content**: attackers control usernames and paths; never `eval` them, and escape them in reports.
- **Alerts with no context**: include who, what, when, where and why the rule fired, so a responder can act.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **syslog timestamps me time zones aur ghayab saal nazar andaz karna**: poori taareekhon ke saath UTC me normalize karein.
- **Qawaid kabhi test na karna**: maloom hamlon aur aam dinon wale sample logs rakhein, aur hadd dono par test karein.

```text
from collections import defaultdict

history = [("jane", "203.0.113.10"), ("jane", "203.0.113.10"), ("jane", "203.0.113.11"),
           ("bob", "192.0.2.20"), ("bob", "192.0.2.20")]
today = [("jane", "203.0.113.10", "08:01"), ("bob", "198.51.100.44", "10:13"),
         ("ana", "198.51.100.5", "11:00"), ("bob", "198.51.100.44", "15:40")]

def subnet(ip):
    return ".".join(ip.split(".")[:3])           # /24, so nearby addresses count as familiar

known = defaultdict(set)
for user, ip in history:
    known[user].add(subnet(ip))

for user, ip, t in today:
    if user not in known:
        print(f"{t} INFO  first login ever for {user} from {ip}")
    elif subnet(ip) not in known[user]:
        print(f"{t} ALERT {user} logged in from new network {ip} (usual: {sorted(known[user])})")
    known[user].add(subnet(ip))                    # learn it, so we alert only once

# 10:13 ALERT bob logged in from new network 198.51.100.44 (usual: ['192.0.2'])
# 11:00 INFO  first login ever for ana from 198.51.100.5
```

Learning from today's data immediately is simple but risky: an attacker who logs in once becomes "known". Real systems require a review or a waiting period before trusting new networks.

<DeepDive title="More about detection engineering">

**Sigma rules.** A YAML format for detections that converts to queries for many SIEMs, so rules are shareable and reviewable.

**MITRE ATT&CK.** Map each rule to techniques (for example T1110 Brute Force, T1078 Valid Accounts) to see coverage gaps.

**Baselines and anomalies.** Beyond fixed thresholds, compare against each user's or host's normal behaviour.

**Response automation.** fail2ban blocks IPs from log patterns; SOAR tools run playbooks when alerts fire.

**Detection as code.** Store rules in Git with tests and CI, like application code.

</DeepDive>

<DeepDive title="Real world: the alert nobody saw">

A company had a script that emailed an alert for every failed SSH login. Exposed servers generated thousands of emails a day, so the team created a filter that moved them to a folder nobody read. When an attacker finally guessed a weak password on a forgotten test server and used it to pivot, the relevant alert was buried among 40,000 others.

The fixes:

1. Brute-force alerts aggregated per IP and window, and blocking via fail2ban on every server.
2. High-severity rules for successful logins after failures and for new sudo use, routed to on-call.
3. SSH password authentication disabled in favour of keys, which removed most of the noise at the source.

</DeepDive>

<DeepDive title="Security lens">

- **Reduce the attack surface first**: key-only SSH, no root login, VPN or bastion access; detections are the second layer.
- **Protect the logs**: forward them off the host quickly so an intruder can't erase traces.
- **Treat log data as untrusted input** in parsers, dashboards and reports.
- **Tune for signal**: high-severity alerts must be rare and actionable, or they'll be ignored.
- **Practice**: replay attack logs or run purple-team exercises to confirm rules fire.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How would you detect an SSH brute-force attack from logs?">
Parse failed-login lines, track failures per source IP in a sliding time window, alert once when a threshold such as 10 in 5 minutes is reached, and include the usernames tried and the time range.
</QA>

<QA q="What is the difference between a false positive and a false negative?">
A false positive is an alert on benign activity; a false negative is a real attack that produced no alert. Lowering thresholds reduces false negatives but increases false positives.
</QA>

<QA q="Why is a successful login after many failures more severe than the failures alone?">
The failures show guessing; a success afterwards suggests the attacker found valid credentials, meaning a likely account compromise that needs immediate response.
</QA>

<QA q="How do you avoid alert fatigue?">
Aggregate events into incidents, alert once per window, set severities so only actionable alerts page people, suppress known-benign sources, and continuously tune rules based on feedback.
</QA>

<QA q="How would you test detection rules?">
Keep labelled sample logs containing known attacks and normal activity, run the rules in automated tests, and check that attacks are detected and normal data produces no alerts.
</QA>

</DeepDive>
