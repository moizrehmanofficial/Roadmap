<BigIdea>
<Tr>
<En>
Four different tools are often confused. A **hash** (`hashlib.sha256`) turns any data into a fixed-size fingerprint; it's one-way and changes completely if a single bit changes, so it's used to check **integrity** (did this file change?). An **HMAC** (`hmac.new(key, msg, sha256)`) is a hash mixed with a secret key, proving a message came from someone who knows the key and wasn't modified; webhooks and signed tokens use it. **Password hashing** is special: fast hashes let attackers try billions of guesses per second, so passwords need a **slow, salted key-derivation function** such as **scrypt**, **PBKDF2**, **bcrypt** or **Argon2**; a random **salt** makes identical passwords hash differently, and you verify by recomputing. **Encryption** is reversible with a **key**: use **authenticated encryption** (Fernet or AES-GCM from the `cryptography` library), which also detects tampering, never your own scheme. Around these, a few habits matter as much as the algorithms: compare secrets with **`hmac.compare_digest`** (constant time), generate tokens with the **`secrets`** module (not `random`), keep keys out of code and Git (environment variables or a secret manager), plan for **key rotation**, and never invent cryptography yourself.
</En>
<Ur>
Chaar mukhtalif tools aksar ulajh jate hain. **Hash** (`hashlib.sha256`) kisi bhi data ko tay size ke fingerprint me badalta; ye ek-taraf hai aur ek bit badalne par poora badal jata, isliye **integrity** check karne ke liye istemal hota (kya ye file badli?). **HMAC** (`hmac.new(key, msg, sha256)`) secret key ke saath mila hash hai, jo sabit karta ke paigham us ne bheja jo key janta hai aur badla nahi gaya; webhooks aur signed tokens ise istemal karte hain. **Password hashing** khaas hai: tez hashes hamla awaron ko har second arbon andaze lagane dete, isliye passwords ko **dheema, salted key-derivation function** chahiye jaise **scrypt**, **PBKDF2**, **bcrypt** ya **Argon2**; random **salt** ek jaise passwords ko mukhtalif hash deta, aur aap dobara hisaab kar ke tasdeeq karte hain. **Encryption** **key** ke saath ulta ho sakti hai: **authenticated encryption** (`cryptography` library ka Fernet ya AES-GCM) lein, jo chhed chhar bhi pakarti hai, apna tareeqa kabhi nahi. In ke gird chand aadatein algorithms jitni hi ahem hain: secrets ka muqabla **`hmac.compare_digest`** (constant time) se karein, tokens **`secrets`** module se banayen (`random` se nahi), keys code aur Git se bahar rakhein (environment variables ya secret manager), **key rotation** ki planning karein, aur khud kabhi cryptography ijaad na karein.
</Ur>

## Picture it

<Tr>
<En>

Think of **documents in an office**.

- A hash is a **fingerprint** of a document: you can't rebuild the document from it, but you can tell instantly if a copy has been altered.
- An HMAC is a **wax seal** pressed with a private stamp: only someone with the stamp could make it, and a broken seal shows tampering.
- Password hashing is a **safe that takes a minute to try each combination**: harmless for the owner who knows it, ruinous for a thief trying millions. The salt makes every safe's lock unique, so one cracked combination doesn't open the rest.
- Encryption is a **locked box**: anyone can carry it, only the key holder can open it, and authenticated encryption also shows if someone pried it open.

</En>
<Ur>

**Daftar ke kaghzat** socheyn.

- Hash document ka **fingerprint** hai: is se document dobara nahi bana sakte, magar foran bata sakte ke copy badli gayi ya nahi.
- HMAC zaati muhr se dabayi **lakh ki muhr** hai: sirf muhr wala hi bana sakta, aur tooti muhr chhed chhar dikhati hai.
- Password hashing aisi **tijori hai jis ka har combination aazmane me ek minute lagta**: malik ke liye jo janta hai be-zarar, lakhon aazmane wale chor ke liye tabahkun. Salt har tijori ka taala munfarid banata, isliye ek toota combination baqi nahi kholta.
- Encryption **taala laga dabba** hai: koi bhi utha sakta, sirf chaabi wala khol sakta, aur authenticated encryption ye bhi dikhati ke kisi ne zabardasti khola.

</Ur>
</Tr>

<Walkthrough>

<Step title="Hashes, file integrity, password hashing, HMAC and secure tokens">

<Tr>
<En>
`hashing.py` uses only the standard library. It hashes two nearly identical messages, checks a file against its published checksum before and after tampering, hashes and verifies passwords with salted scrypt and compares its speed with SHA-256, signs and verifies a webhook body with HMAC, and generates a URL-safe random token.
</En>
<Ur>
`hashing.py` sirf standard library istemal karti hai. Ye do taqreeban ek jaise paighamat hash karti, chhed chhar se pehle aur baad file ko us ke published checksum se milati, salted scrypt se passwords hash aur tasdeeq karti aur us ki raftar SHA-256 se milati, HMAC se webhook body sign aur tasdeeq karti, aur URL-safe random token banati hai.
</Ur>
</Tr>

```bash
cat > hashing.py <<'EOF'
import hashlib, hmac, os, secrets, time

# 1. Hashes: fixed-size fingerprints; a tiny change gives a completely different digest
for text in [b"transfer $100 to jane", b"transfer $900 to jane"]:
    print(hashlib.sha256(text).hexdigest()[:32], text.decode())
print("sha256 hex length:", len(hashlib.sha256(b"x").hexdigest()), "| md5 is broken for security, use sha256+")

# 2. File integrity: compare against a published checksum
with open("release.tar.gz", "wb") as f:
    f.write(b"pretend this is a release archive" * 1000)
def sha256_file(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(65536), b""):
            h.update(chunk)
    return h.hexdigest()
published = sha256_file("release.tar.gz")
with open("release.tar.gz", "ab") as f:
    f.write(b"!")                                   # one extra byte, e.g. a tampered download
print("checksum still matches after tampering:", sha256_file("release.tar.gz") == published)

# 3. Passwords: never plain sha256. Use a slow, salted KDF (scrypt here; argon2/bcrypt are common too)
def hash_password(password, n=2**14, r=8, p=1):
    salt = os.urandom(16)
    key = hashlib.scrypt(password.encode(), salt=salt, n=n, r=r, p=p, dklen=32)
    return f"scrypt${n}${r}${p}${salt.hex()}${key.hex()}"

def verify_password(password, stored):
    _, n, r, p, salt, key = stored.split("$")
    test = hashlib.scrypt(password.encode(), salt=bytes.fromhex(salt), n=int(n), r=int(r), p=int(p), dklen=32)
    return hmac.compare_digest(test.hex(), key)       # constant-time comparison

h1, h2 = hash_password("correct horse"), hash_password("correct horse")
print("same password, different hashes (salt):", h1 != h2, "| format:", h1.split("$")[:4])
print("verify right:", verify_password("correct horse", h1), "| verify wrong:", verify_password("Correct horse", h1))
start = time.perf_counter(); verify_password("guess", h1); slow = time.perf_counter() - start
start = time.perf_counter(); hashlib.sha256(b"guess").digest(); fast = time.perf_counter() - start
print("scrypt is deliberately over 100x slower than sha256:", slow > fast * 100)

# 4. HMAC: prove a message came from someone who knows the secret (e.g. webhook signatures)
secret = b"whsec_demo_only_not_a_real_secret"
body = b'{"event": "payment.succeeded", "amount": 4950}'
signature = hmac.new(secret, body, hashlib.sha256).hexdigest()
def verify_webhook(body, sig):
    expected = hmac.new(secret, body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, sig)
print("genuine webhook:", verify_webhook(body, signature))
print("modified amount:", verify_webhook(body.replace(b"4950", b"9950"), signature))

# 5. Random tokens for sessions, resets and API keys
token = secrets.token_urlsafe(32)
print("token length:", len(token), "| url-safe:", all(c.isalnum() or c in "-_" for c in token))
EOF
python3 hashing.py
```

<Happened>
<Tr>
<En>

- Changing **one character** ($100 to $900) produced an unrelated digest: that's the avalanche effect that makes hashes good fingerprints. SHA-256 always gives **64 hex characters**, whatever the input size.
- Adding a single byte to the "release" made its checksum **stop matching**. Always verify downloads against checksums from a trusted source (ideally signed).
- The same password hashed twice gave **different results** because each got a random **salt**, stored in the result together with the parameters (`scrypt$16384$8$1$salt$hash`) so you can verify later and raise the cost over time. Verifying recomputes with the stored salt and compares in **constant time**.
- scrypt was **over 100 times slower** than SHA-256 on purpose. A user logging in barely notices; an attacker with a stolen database now gets far fewer guesses per second, and the salt stops precomputed tables.
- The webhook HMAC verified the genuine body and **rejected the modified amount**, because only someone with the secret can produce a matching signature. `compare_digest` avoids timing leaks that `==` can have.
- `secrets.token_urlsafe(32)` gave a **43-character**, 256-bit random token from the OS's secure generator, suitable for session IDs, password reset links and API keys.

</En>
<Ur>

- **Ek character** badalne ($100 se $900) ne bilkul alag digest banaya: ye avalanche effect hai jo hashes ko achhe fingerprints banata hai. SHA-256 input ka size jo bhi ho hamesha **64 hex characters** deta hai.
- "Release" me ek byte jorne se us ka checksum **milna band** ho gaya. Downloads ko hamesha bharose wale zariye ke checksums (behtar ho to signed) se tasdeeq karein.
- Wahi password do dafa hash karne par **mukhtalif nataij** aaye kyunke har ek ko random **salt** mila, jo parameters ke saath natije me hi rakha jata (`scrypt$16384$8$1$salt$hash`) taa ke baad me tasdeeq kar sakein aur waqt ke saath qeemat barha sakein. Tasdeeq mehfooz salt ke saath dobara hisaab kar ke **constant time** me muqabla karti hai.
- scrypt jaan boojh kar SHA-256 se **100 guna se zyada dheema** tha. Login karta user mushkil se mehsoos karta; chori ke database wale hamla awar ko ab har second kahin kam andaze milte, aur salt pehle se bani tables rokta hai.
- Webhook HMAC ne asal body tasdeeq ki aur **badli raqam radd** ki, kyunke sirf secret wala hi milta signature bana sakta hai. `compare_digest` un timing leaks se bachata jo `==` me ho sakte hain.
- `secrets.token_urlsafe(32)` ne OS ke mehfooz generator se **43 character** ka, 256-bit random token diya, session IDs, password reset links aur API keys ke liye munasib.

</Ur>

<Step title="Authenticated encryption with Fernet and AES-GCM, rotation and key loading">

<Tr>
<En>
We install a pinned `cryptography` package. `encryption.py` encrypts a value with Fernet, shows that tampering or a wrong key is detected, rotates the ciphertext to a new key with `MultiFernet`, encrypts with AES-GCM using associated data and shows that a different context is rejected, and loads the key from an environment variable.
</En>
<Ur>
Hum pinned `cryptography` package install karte hain. `encryption.py` Fernet se value encrypt karti, dikhati ke chhed chhar ya ghalat key pakri jati, `MultiFernet` se ciphertext nayi key par rotate karti, associated data ke saath AES-GCM se encrypt kar ke dikhati ke mukhtalif context radd hota hai, aur key environment variable se load karti hai.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z
uv venv -q --python 3.13 .venv && uv pip install -q --python .venv "cryptography==45.0.3"
cat > encryption.py <<'EOF'
import os
from cryptography.fernet import Fernet, MultiFernet, InvalidToken
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# 1. Fernet: authenticated symmetric encryption with a simple API
key = Fernet.generate_key()                       # store in a secret manager, not in code
f = Fernet(key)
token = f.encrypt(b"card ending 4242, exp 12/28")
print("ciphertext differs each time:", token != f.encrypt(b"card ending 4242, exp 12/28"))
print("decrypted:", f.decrypt(token).decode())

tampered = token[:-5] + (b"A" if token[-5:-4] != b"A" else b"B") + token[-4:]
try:
    f.decrypt(tampered)
except InvalidToken:
    print("tampered ciphertext: InvalidToken")
try:
    Fernet(Fernet.generate_key()).decrypt(token)
except InvalidToken:
    print("wrong key: InvalidToken")

# 2. Key rotation: decrypt with old or new keys, re-encrypt with the newest
new_key = Fernet.generate_key()
mf = MultiFernet([Fernet(new_key), Fernet(key)])  # first key encrypts, all keys can decrypt
rotated = mf.rotate(token)
print("old token readable:", mf.decrypt(token) == mf.decrypt(rotated),
      "| rotated works with new key alone:", Fernet(new_key).decrypt(rotated) == b"card ending 4242, exp 12/28")

# 3. AES-GCM: lower level; never reuse a nonce with the same key
aes = AESGCM(AESGCM.generate_key(bit_length=256))
nonce = os.urandom(12)
aad = b"user_id=1042"                             # authenticated but not encrypted context
ct = aes.encrypt(nonce, b"date of birth: 1990-04-01", aad)
print("AES-GCM roundtrip:", aes.decrypt(nonce, ct, aad).decode())
try:
    aes.decrypt(nonce, ct, b"user_id=9999")       # same ciphertext, different user context
except Exception as e:
    print("wrong associated data:", type(e).__name__)

# 4. Load secrets from the environment, fail clearly if missing
os.environ["APP_ENCRYPTION_KEY"] = key.decode()   # in real life: set by the platform's secret store
def load_key():
    value = os.environ.get("APP_ENCRYPTION_KEY")
    if not value:
        raise RuntimeError("APP_ENCRYPTION_KEY is not set")
    return Fernet(value.encode())
print("key from environment decrypts:", load_key().decrypt(token) == b"card ending 4242, exp 12/28")
EOF
.venv/bin/python encryption.py
```

<Happened>
<Tr>
<En>

- Encrypting the same text twice gave **different ciphertexts**, because Fernet uses a random IV each time (and includes a timestamp). Identical inputs don't leak as identical outputs.
- Changing one character of the token, or using another key, raised **InvalidToken**: Fernet is **authenticated** (AES plus HMAC), so tampering is detected instead of silently producing garbage. Plain AES modes like ECB or unauthenticated CBC don't give you this.
- `MultiFernet([new, old])` decrypts with any listed key and encrypts with the first; `rotate()` re-encrypted the old token so the **new key alone** can read it. Rotate data gradually, then retire the old key.
- AES-GCM is the standard lower-level choice: a 256-bit key, a **12-byte nonce that must never repeat with the same key**, and optional **associated data** that is authenticated but not encrypted. Decrypting with a different `user_id` failed with **InvalidTag**, which stops an attacker from moving one user's encrypted field into another user's record.
- The key came from `APP_ENCRYPTION_KEY`, and the code fails clearly if it's missing. In production a secret manager or KMS provides it; losing the key means losing the data, so back keys up securely.

</En>
<Ur>

- Wahi text do dafa encrypt karne par **mukhtalif ciphertexts** mile, kyunke Fernet har dafa random IV istemal karta (aur timestamp shamil karta) hai. Ek jaise inputs ek jaise outputs ki shakal me leak nahi hote.
- Token ka ek character badalne, ya doosri key istemal karne, par **InvalidToken** utha: Fernet **authenticated** hai (AES aur HMAC), isliye chhed chhar khamoshi se kachra banane ke bajaye pakri jati hai. ECB ya be-authentication CBC jaise saade AES modes ye nahi dete.
- `MultiFernet([new, old])` kisi bhi di gayi key se decrypt aur pehli se encrypt karta; `rotate()` ne purana token dobara encrypt kiya taa ke **sirf nayi key** use parh sake. Data dheere dheere rotate karein, phir purani key retire karein.
- AES-GCM mayari nichle level ka intikhab hai: 256-bit key, **12-byte nonce jo usi key ke saath kabhi dohraya nahi jana chahiye**, aur ikhtiyari **associated data** jo authenticated hota magar encrypt nahi. Mukhtalif `user_id` ke saath decrypt karna **InvalidTag** ke saath nakam hua, jo hamla awar ko ek user ki encrypted field doosre user ke record me rakhne se rokta hai.
- Key `APP_ENCRYPTION_KEY` se aayi, aur ghayab ho to code wazeh tareeqe se nakam hota hai. Production me secret manager ya KMS ise deta hai; key khona data khona hai, isliye keys mehfooz tareeqe se backup karein.

## Common mistakes

<Compare>
<Bad title="Fast, unsalted password hashes and == comparisons">

```text
stored = hashlib.md5(password.encode()).hexdigest()   # cracked in seconds; same password, same hash
if hashlib.md5(attempt.encode()).hexdigest() == stored:  # timing leak
    login()
```

</Bad>
<Good title="Salted, slow KDF and constant-time checks">

```text
from argon2 import PasswordHasher          # pip install argon2-cffi
ph = PasswordHasher()
stored = ph.hash(password)                 # includes salt and parameters
ph.verify(stored, attempt)                 # raises on mismatch
```

</Good>
</Compare>

<Bad title="Encoding mistaken for encryption, keys in code">

```text
SECRET_KEY = "Zm9vYmFy..."                       # committed to Git

```

</Bad>

key = os.environ["APP_ENCRYPTION_KEY"]           # from a secret manager

<En>

More mistakes to avoid:

- **Using `random` for tokens or passwords**: it's predictable; use `secrets`.
- **Reusing an AES-GCM nonce with the same key**: it can expose plaintext and allow forgeries.
- **Storing API keys in plain text in the database**: store a hash and show the key only once.
- **Logging secrets or decrypted values** while debugging.
- **Inventing your own scheme** (XOR, custom padding, "double hashing"): use vetted libraries and defaults.

</En>

<Challenge title="PBKDF2 hashes with upgrades">

<Tr>
<En>
Using only `hashlib`, `hmac` and `os`, write `hash_password` with PBKDF2-HMAC-SHA256 (600,000 iterations, random 16-byte salt) that stores `pbkdf2_sha256$iterations$salt$hash`, `verify_password` with a constant-time comparison, and `needs_rehash` that detects old, weaker iteration counts. Simulate a hash stored years ago with 100,000 iterations and upgrade it on a successful login.
</En>
<Ur>
Sirf `hashlib`, `hmac` aur `os` istemal karte hue PBKDF2-HMAC-SHA256 (600,000 iterations, random 16-byte salt) wala `hash_password` likhein jo `pbkdf2_sha256$iterations$salt$hash` store kare, constant-time muqable wala `verify_password`, aur purane, kamzor iteration counts pakarne wala `needs_rehash`. Saalon pehle 100,000 iterations ke saath store hue hash ki naqal karein aur kamyab login par use upgrade karein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
import hashlib, hmac, os

ITERATIONS = 600_000            # OWASP's 2023 guidance for PBKDF2-HMAC-SHA256

def hash_password(password, iterations=ITERATIONS):
    salt = os.urandom(16)
    dk = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, iterations)
    return f"pbkdf2_sha256${iterations}${salt.hex()}${dk.hex()}"

def verify_password(password, stored):
    algo, iterations, salt, expected = stored.split("$")
    dk = hashlib.pbkdf2_hmac("sha256", password.encode(), bytes.fromhex(salt), int(iterations))
    return hmac.compare_digest(dk.hex(), expected)

def needs_rehash(stored, iterations=ITERATIONS):
    return int(stored.split("$")[1]) < iterations

old = hash_password("hunter2", iterations=100_000)        # stored years ago
print("valid:", verify_password("hunter2", old), "| wrong:", verify_password("hunter3", old))
if verify_password("hunter2", old) and needs_rehash(old):
    old = hash_password("hunter2")                        # upgrade at the next successful login
print("upgraded to:", old.split("$")[1], "iterations | still valid:", verify_password("hunter2", old))

# valid: True | wrong: False
# upgraded to: 600000 iterations | still valid: True
```

Build `make_token(user, ttl, now)` that creates `payload.signature`, where the payload is base64url JSON with `sub` and `exp` and the signature is base64url HMAC-SHA256 of the payload. <Solution>

<Tr>
<En>

```text
import base64, hashlib, hmac, json, time

SECRET = b"demo-signing-key-not-for-production"

def b64(data):
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def unb64(text):
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))

def make_token(user, ttl, now):
    payload = b64(json.dumps({"sub": user, "exp": now + ttl}).encode())
    sig = b64(hmac.new(SECRET, payload.encode(), hashlib.sha256).digest())
    return f"{payload}.{sig}"

def check_token(token, now):
    try:
        payload, sig = token.split(".")
    except ValueError:
        return "malformed"
    expected = b64(hmac.new(SECRET, payload.encode(), hashlib.sha256).digest())
    if not hmac.compare_digest(sig, expected):
        return "bad signature"
    data = json.loads(unb64(payload))
    if now >= data["exp"]:
        return "expired"
    return f"ok, user={data['sub']}"

now = 1_800_000_000
t = make_token("jane", ttl=900, now=now)
print(check_token(t, now + 60))
print(check_token(t, now + 901))
forged_payload = b64(json.dumps({"sub": "admin", "exp": now + 900}).encode())
print(check_token(forged_payload + "." + t.split(".")[1], now + 60))
print(check_token("not-a-token", now))

# ok, user=jane
# expired
# bad signature
# malformed
```

<DeepDive title="More about cryptography in Python">

**Argon2id.** The winner of the Password Hashing Competition; `argon2-cffi` provides `PasswordHasher` with sensible defaults and `check_needs_rehash`.

**Envelope encryption.** A cloud KMS encrypts a data key; the data key encrypts your data locally. Rotating the master key doesn't require re-encrypting everything.

**Asymmetric keys.** `cryptography` generates Ed25519 or RSA keys for signing and verifying, used for release signatures and JWTs with public verification.

**JWTs.** Use `PyJWT` with an explicit algorithm list; never accept `alg: none`, and validate `exp`, `aud` and `iss`.

**Secrets tooling.** Vault, AWS Secrets Manager, GCP Secret Manager, SOPS and sealed-secrets keep keys out of repositories.

</DeepDive>

<DeepDive title="Real world: the password table that leaked">

A service stored passwords as unsalted SHA-1 hashes. After an SQL injection exposed the users table, attackers cracked most passwords within days using GPUs and precomputed lists, then tried them on other sites where users reused them (credential stuffing).

The fixes:

1. Passwords migrated to Argon2id: existing SHA-1 hashes were wrapped (`argon2(sha1)`) immediately and fully upgraded at each user's next login.
2. Forced resets for affected accounts, with breach notifications.
3. The SQL injection fixed with parameterized queries, and multi-factor authentication offered to all users.

</DeepDive>

<DeepDive title="Security lens">

- **Passwords**: Argon2id/scrypt/bcrypt with per-user salts; tune cost so a login takes tens to hundreds of milliseconds.
- **Secrets hygiene**: no keys in code, images or logs; scan repositories; rotate on any suspicion of exposure.
- **Integrity**: verify checksums and signatures of downloads and artifacts in CI/CD.
- **Randomness**: only `secrets` and `os.urandom` for anything security-related.
- **Defaults over cleverness**: high-level, authenticated APIs (Fernet, AES-GCM, TLS) prevent most mistakes.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between hashing and encryption?">
Hashing is one-way and produces a fixed-size digest used for integrity and verification; encryption is reversible with a key and protects confidentiality.
</QA>

<QA q="Why shouldn't you hash passwords with SHA-256?">
SHA-256 is designed to be fast, so attackers can test billions of guesses per second; password hashing needs slow, memory-hard, salted functions like Argon2 or scrypt to make guessing expensive.
</QA>

<QA q="What is a salt and why is it used?">
A random value stored alongside each password hash and mixed into it, so identical passwords produce different hashes and precomputed rainbow tables are useless.
</QA>

<QA q="How do you verify a webhook?">
Compute an HMAC of the raw request body with the shared secret and compare it to the signature header in constant time; also check a timestamp to prevent replays.
</QA>

<QA q="What is authenticated encryption?">
Encryption that also produces an authentication tag, so any modification of the ciphertext or associated data is detected on decryption; examples are AES-GCM, ChaCha20-Poly1305 and Fernet.
</QA>

</DeepDive>
