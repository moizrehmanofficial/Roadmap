<BigIdea>
<Tr>
<En>
The **Python Package Index (PyPI)**, at pypi.org, is the public warehouse of Python packages that anyone can publish to. **pip** is the tool that downloads packages from PyPI and installs them, together with the packages they depend on. You run it as **`python -m pip install name`**, which guarantees you install into the same Python you'll run. You can ask for an **exact version** (`requests==2.32.3`) or a **range** (`packaging>=24,<25`); pip resolves a set of versions that fit together. `pip show` describes a package, `pip list` and `pip freeze` show what's installed, `pip uninstall` removes, and `pip check` looks for broken dependencies. To make installs **reproducible**, projects list every package with an exact version in **`requirements.txt`** and install with `pip install -r requirements.txt`. Install packages inside a **virtual environment**, not into the system Python (the next lesson). Because anyone can publish to PyPI, installing a package means **running someone else's code**: check names carefully (typosquatting like `reqeusts`), prefer well-known projects, pin versions, and for high-security setups pin **hashes** so pip refuses any file that has been changed.
</En>
<Ur>
**Python Package Index (PyPI)**, pypi.org par, Python packages ka public godam hai jahan koi bhi publish kar sakta hai. **pip** woh tool hai jo PyPI se packages download kar ke unhe un ke dependency packages samait install karta hai. Aap ise **`python -m pip install name`** se chalate hain, jo yaqeeni banata hai ke aap usi Python me install karein jise chalayenge. Aap **bilkul version** (`requests==2.32.3`) ya **range** (`packaging>=24,<25`) maang sakte hain; pip aise versions ka set dhoondta hai jo aapas me fit hon. `pip show` package bayan karta, `pip list` aur `pip freeze` installed cheezen dikhate, `pip uninstall` hatata, aur `pip check` tooti dependencies dhoondta hai. Installs ko **dobara ek jaisa** banane ke liye projects har package bilkul version ke saath **`requirements.txt`** me likhte aur `pip install -r requirements.txt` se install karte hain. Packages system Python ke bajaye **virtual environment** me install karein (agla lesson). Kyunke PyPI par koi bhi publish kar sakta hai, package install karna **kisi aur ka code chalana** hai: naam dhyan se check karein (`reqeusts` jaisi typosquatting), maroof projects ko tarjeeh dein, versions pin karein, aur zyada security wale setups me **hashes** pin karein taa ke pip badli hui har file radd kar de.
</Ur>

## Picture it

<Tr>
<En>

Think of an **app store** for code, without app review.

- PyPI is the store's warehouse, and pip is the delivery driver who fetches what you order plus every part it needs.
- Ordering "requests" gets whatever is newest today; ordering "requests 2.32.3" gets the same box every time.
- `requirements.txt` is a shopping list with exact model numbers, so a friend can buy the identical setup.
- Because nobody reviews what's uploaded, a stranger can put a box labelled "reqeusts" on the shelf next to the real one. A hash is a tamper seal: if the seal doesn't match, pip refuses delivery.

</En>
<Ur>

Code ke liye aisa **app store** socheyn jahan apps ka review nahi hota.

- PyPI store ka godam hai, aur pip delivery driver jo aap ka order aur us ka har zaroori purza laata hai.
- "requests" order karne par aaj jo sab se naya ho woh milta; "requests 2.32.3" order karne par har dafa wahi dabba.
- `requirements.txt` bilkul model numbers wali khareedari ki list hai, taa ke dost hoobahoo setup khareed sake.
- Kyunke upload hone wali cheez ka koi review nahi karta, ajnabi asal ke saath shelf par "reqeusts" likha dabba rakh sakta hai. Hash chhed chhar ki muhr hai: muhr na mile to pip delivery se inkar karta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Install, inspect, version ranges and uninstall">

<Tr>
<En>
We create a virtual environment (explained in the next lesson) so nothing touches the system Python, install an exact version of `tabulate` and use it, look at it with `pip show`, install `packaging` with a version range, list what's installed, uninstall `tabulate`, and see what happens when a package name has a typo. On Windows, activate with `.venv\Scripts\activate` instead.
</En>
<Ur>
Hum virtual environment banate hain (agle lesson me wazahat) taa ke system Python ko kuch na chhooye, `tabulate` ka bilkul version install kar ke istemal karte, `pip show` se dekhte, version range ke saath `packaging` install karte, installed cheezon ki list dekhte, `tabulate` uninstall karte, aur dekhte hain ke package ke naam me ghalti ho to kya hota hai. Windows par is ke bajaye `.venv\Scripts\activate` se activate karein.
</Ur>
</Tr>

```bash
python3 -m venv .venv                 # a private place for packages (next lesson explains)
. .venv/bin/activate
python -m pip install -q "tabulate==0.9.0"
python -c 'from tabulate import tabulate; print(tabulate([["web01", "up"], ["db01", "down"]], headers=["host", "status"]))'
echo "--- pip show:"
pip show tabulate | grep -E "^(Name|Version|Summary|Requires|Location):" | sed "s#$PWD/##"
echo "--- version ranges:"
python -m pip install -q "packaging>=24,<25"
pip show packaging | grep ^Version
echo "--- installed (pip itself hidden):"
pip list --format=freeze | grep -v "^pip=="
echo "--- uninstall:"
pip uninstall -y -q tabulate && python -c "import tabulate" 2>&1 | tail -1
echo "--- typo in a name:"
python -m pip install -q "tabulatee==0.9.0" 2>&1 | grep -m1 -o "No matching distribution found for tabulatee==0.9.0"
```

```text output
host    status
------  --------
web01   up
db01    down
--- pip show:
Name: tabulate
Version: 0.9.0
Summary: Pretty-print tabular data
Location: .venv/lib/python3.13/site-packages
Requires: 
--- version ranges:
Version: 24.2
--- installed (pip itself hidden):
packaging==24.2
tabulate==0.9.0
--- uninstall:

--- typo in a name:

```

<Happened>
<Tr>
<En>

- `python -m pip install` ran the pip that belongs to the active Python, so the package landed in **.venv**, not the system. `-q` just made pip quieter.
- `pip show` reported the version, a summary, the install **location** and **Requires** (empty here: tabulate has no dependencies).
- `packaging>=24,<25` installed **24.2**, the newest version in that range, even though newer major versions exist. Ranges let you accept bug fixes while avoiding breaking major releases.
- `pip list --format=freeze` showed exact versions in requirements format (we hid pip's own line because its version changes often).
- After `pip uninstall`, importing `tabulate` raised **ModuleNotFoundError**. Uninstalling doesn't remove dependencies that were pulled in for it.
- A one-letter typo, `tabulatee`, simply wasn't found. That was lucky: attackers register such names (typosquatting) with malicious code, and then the "typo" installs fine.

</En>
<Ur>

- `python -m pip install` ne active Python wala pip chalaya, isliye package system ke bajaye **.venv** me gaya. `-q` ne bas pip ko khamosh kiya.
- `pip show` ne version, khulasa, install ki **jagah** aur **Requires** bataya (yahan khaali: tabulate ki koi dependency nahi).
- `packaging>=24,<25` ne **24.2** install kiya, us range ka sab se naya version, halanke naye major versions mojood hain. Ranges aap ko bug fixes qubool karne aur toorne wale major releases se bachne deti hain.
- `pip list --format=freeze` ne requirements format me bilkul versions dikhaye (humne pip ki apni line chhupa di kyunke us ka version aksar badalta hai).
- `pip uninstall` ke baad `tabulate` import karne par **ModuleNotFoundError** aaya. Uninstall us ke liye aayi dependencies nahi hatata.
- Ek haroof ki ghalti, `tabulatee`, bas nahi mili. Ye khush qismati thi: hamla awar aise naam (typosquatting) nuqsan deh code ke saath register karte hain, aur phir "ghalti" baghair masle install ho jati hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="requirements.txt, freeze, check, and hash-pinned installs">

<Tr>
<En>
In a fresh environment we write a `requirements.txt` that pins `requests` and every package it depends on, install it, confirm the result with `pip freeze`, `pip check` and `pip show`. Then we download a wheel, compute its SHA-256 with `pip hash`, install it with `--require-hashes`, and finally try a requirements file whose hash has been changed.
</En>
<Ur>
Naye environment me hum aisi `requirements.txt` likhte hain jo `requests` aur us ki har dependency pin kare, use install karte, aur `pip freeze`, `pip check` aur `pip show` se natija tasdeeq karte hain. Phir ek wheel download kar ke `pip hash` se us ka SHA-256 nikalte, use `--require-hashes` ke saath install karte, aur aakhir me aisi requirements file aazmate hain jis ka hash badla gaya ho.
</Ur>
</Tr>

```bash
python3 -m venv .venv && . .venv/bin/activate
cat > requirements.txt <<'EOF'
# Direct dependency, plus everything it pulls in, all pinned
requests==2.32.3
certifi==2025.8.3
charset-normalizer==3.4.0
idna==3.10
urllib3==2.2.3
EOF
python -m pip install -q -r requirements.txt
pip freeze
pip check
echo "--- dependency tree of requests:"
pip show requests | grep -E "^(Requires|Required-by):"

echo "--- hash pinning:"
pip download -q --no-deps -d wheels "six==1.16.0"
ls wheels
HASH=$(pip hash wheels/six-1.16.0-py2.py3-none-any.whl | tail -1)
echo "$HASH"
echo "six==1.16.0 $HASH" > locked.txt
python -m pip install -q --require-hashes -r locked.txt && python -c "import six; print('six', six.__version__, 'installed with verified hash')"
echo "six==1.16.0 --hash=sha256:$(printf '0%.0s' {1..64})" > tampered.txt
python -m pip install -q --force-reinstall --require-hashes -r tampered.txt > out.txt 2>&1
echo "exit code: $?"
grep -m1 -o "THESE PACKAGES DO NOT MATCH THE HASHES" out.txt
```

```text output
certifi==2025.8.3
charset-normalizer==3.4.0
idna==3.10
packaging==24.2
requests==2.32.3
urllib3==2.2.3
No broken requirements found.
--- dependency tree of requests:
Requires: certifi, charset-normalizer, idna, urllib3
Required-by: 
--- hash pinning:
six-1.16.0-py2.py3-none-any.whl
--hash=sha256:8abb2f1d86890a2dfb989f9a77cfcfd3e47c2a354b01111771326f8aa26e0254
six 1.16.0 installed with verified hash
exit code: 1
THESE PACKAGES DO NOT MATCH THE HASHES
```

<Happened>
<Tr>
<En>

- Installing from the file gave **exactly** the listed versions, and `pip freeze` printed the same five lines: anyone running this file today or next year gets an identical environment. Pinning only `requests==2.32.3` would still pull the newest `urllib3`, `certifi` and so on, so they're pinned too (tools like `pip-tools` and `uv` generate such fully pinned files for you).
- `pip check` found **no broken requirements**, and `pip show` listed requests' four dependencies; `Required-by` is empty because nothing depends on requests.
- `pip download` fetched the **wheel** file (a ready-to-install `.whl`; source `.tar.gz` packages may run build code during install). `pip hash` printed its SHA-256.
- With `--require-hashes`, pip verified the downloaded file against the hash before installing it.
- When the hash didn't match, pip **refused** with "THESE PACKAGES DO NOT MATCH THE HASHES" and exit code **1**. If a package on PyPI or a mirror were replaced with a tampered file, a hash-pinned install would stop instead of running it.

</En>
<Ur>

- File se install karne par **bilkul** likhe hue versions mile, aur `pip freeze` ne wahi paanch lines print kin: aaj ya agle saal ye file chalane wale har shakhs ko hoobahoo environment milega. Sirf `requests==2.32.3` pin karna phir bhi sab se naya `urllib3`, `certifi` waghera laata, isliye woh bhi pin hain (`pip-tools` aur `uv` jaise tools aisi mukammal pinned files aap ke liye banate hain).
- `pip check` ko **koi tooti requirement nahi** mili, aur `pip show` ne requests ki chaar dependencies bataein; `Required-by` khaali hai kyunke koi requests par mabni nahi.
- `pip download` ne **wheel** file laayi (install ke liye tayyar `.whl`; source `.tar.gz` packages install ke dauran build code chala sakte hain). `pip hash` ne us ka SHA-256 print kiya.
- `--require-hashes` ke saath pip ne install se pehle download hui file ko hash se milaya.
- Jab hash nahi mila to pip ne "THESE PACKAGES DO NOT MATCH THE HASHES" aur exit code **1** ke saath **inkar** kiya. Agar PyPI ya mirror par koi package chhed chhar wali file se badal diya jata, to hash-pinned install use chalane ke bajaye ruk jata.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="sudo pip into the system Python, nothing pinned">

```text
sudo pip install requests           # may break OS tools; which Python is this pip?
pip install flask                   # whatever version is newest today
```

</Bad>
<Good title="Virtual environment, python -m pip, pinned file">

```text
python3 -m venv .venv && . .venv/bin/activate
python -m pip install -r requirements.txt     # exact, reviewed versions
```

</Good>
</Compare>

<Compare>
<Bad title="Installing whatever a blog post names">

```text
pip install python-jwt-tools        # never heard of it; 3 downloads; created yesterday
pip install reqeusts                # typo
```

</Bad>
<Good title="Check before you install">

```text
# 1. Open pypi.org/project/<name>: maintainers, release history, linked repository
# 2. Check the repository's activity and the package's download numbers
# 3. Copy the exact name from the official docs
python -m pip install "PyJWT==2.10.1"
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`pip` and `python` pointing at different installations**: always `python -m pip`.
- **`pip freeze` in a polluted environment**: it captures every package, including leftovers; freeze from a clean virtual environment.
- **Never updating**: pinned versions still need regular, tested upgrades for security fixes (`pip list --outdated`, `pip-audit`, Dependabot).
- **Mixing `--break-system-packages` into normal work**: it exists for special cases; use a virtual environment instead.
- **Putting secrets in index URLs** inside committed requirement files.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`pip` aur `python` ka mukhtalif installations ki taraf ishara**: hamesha `python -m pip`.
- **Ganday environment me `pip freeze`**: ye har package pakar leta hai, bache khuche samait; saaf virtual environment se freeze karein.
- **Kabhi update na karna**: pinned versions ko bhi security fixes ke liye baqaida, test kiye upgrades chahiye (`pip list --outdated`, `pip-audit`, Dependabot).
- **Aam kaam me `--break-system-packages` milana**: ye khaas halaat ke liye hai; is ke bajaye virtual environment lein.
- **Commit hone wali requirement files me index URLs ke andar secrets.**

</Ur>
</Tr>

## Try it yourself

<Challenge title="Find unpinned requirements">

<Tr>
<En>
Write `unpinned(text)` that reads the contents of a requirements file, ignores blank lines and `#` comments (including comments at the end of a line), and returns the lines that don't pin an exact version with `==`. Test it on a file containing `requests==2.32.3`, `flask>=3.0`, `# tools`, `pyyaml`, `boto3 ~= 1.35.0  # aws`, `urllib3==2.2.3` and an empty line.
</En>
<Ur>
`unpinned(text)` likhein jo requirements file ka mawad parhe, khaali lines aur `#` comments (line ke aakhir wale comments samait) nazar andaz kare, aur woh lines lautaye jo `==` se bilkul version pin nahi karti. Ise aisi file par test karein jis me `requests==2.32.3`, `flask>=3.0`, `# tools`, `pyyaml`, `boto3 ~= 1.35.0  # aws`, `urllib3==2.2.3` aur ek khaali line ho.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
def unpinned(text):
    result = []
    for line in text.splitlines():
        line = line.split("#", 1)[0].strip()
        if line and "==" not in line:
            result.append(line)
    return result

reqs = """requests==2.32.3
flask>=3.0
# tools
pyyaml

boto3 ~= 1.35.0  # aws
urllib3==2.2.3
"""
print(unpinned(reqs))

# ['flask>=3.0', 'pyyaml', 'boto3 ~= 1.35.0']
```

</En>

<Challenge title="Which versions does a range allow?">

<Tr>
<En>
Using the `packaging` library (installed alongside pip in most environments; otherwise `pip install packaging`), check which of the versions `2.31.0`, `2.32.0`, `2.32.5`, `2.33.0` and `3.0.0` are allowed by `~=2.32.0` and by `>=2.31,<3,!=2.32.0`, and which is the newest allowed by each.
</En>
<Ur>
`packaging` library (zyadatar environments me pip ke saath install; warna `pip install packaging`) istemal karte hue check karein ke versions `2.31.0`, `2.32.0`, `2.32.5`, `2.33.0` aur `3.0.0` me se kaun se `~=2.32.0` aur `>=2.31,<3,!=2.32.0` qubool karte hain, aur har ek me sab se naya kaun sa hai.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

<DeepDive title="More about pip">

**Wheels and tags.** A wheel name like `py2.py3-none-any` says which Pythons, ABIs and platforms it supports; packages with C code ship separate wheels for Linux, macOS and Windows.

**Constraints files.** `-c constraints.txt` limits versions without forcing installation, useful in monorepos.

**Private indexes.** Companies host internal packages on Artifactory, Nexus or AWS CodeArtifact; `--index-url` points pip at them.

**Caching.** pip caches downloads; in Docker builds, `--no-cache-dir` keeps images smaller.

**Auditing.** `pip-audit` checks installed versions against known vulnerability databases.

</DeepDive>

<DeepDive title="Real world: the dependency confusion attack">

A company used an internal package named `acme-billing-utils` from a private index, and its build installed with `--extra-index-url` pointing at both PyPI and the private index. A security researcher published a package with the same name and a higher version number on public PyPI. pip picked the higher version from PyPI, and the researcher's harmless proof-of-concept code ran inside the company's build servers.

The fixes:

1. Use a single index (a proxy that serves both internal and vetted public packages) instead of `--extra-index-url`.
2. Reserve internal names on PyPI.
3. Pin versions and hashes in lock files.

</DeepDive>

<DeepDive title="Security lens">

- **Installing is executing**: setup scripts and imported modules run with your permissions; install untrusted packages only in isolated environments.
- **Typosquatting and lookalikes**: copy names from official docs; be wary of new packages with few downloads.
- **Dependency confusion**: avoid `--extra-index-url` with private package names.
- **Pin and hash** for production; review dependency updates like code changes.
- **Scan regularly** with `pip-audit` or Dependabot, and remove packages you no longer use.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between pip install package and pip install -r requirements.txt?">
The first installs one package and resolves its dependencies at whatever versions are newest and compatible; the second installs everything listed in the file, typically with pinned versions for a reproducible environment.
</QA>

<QA q="What does pip freeze output, and when should you use it?">
It lists every installed package with its exact version in requirements format; use it from a clean virtual environment to capture a reproducible set of dependencies.
</QA>

<QA q="What is the difference between a wheel and an sdist?">
A wheel is a prebuilt archive installed by copying files, while an sdist is a source archive that must be built during installation and may execute build scripts.
</QA>

<QA q="Why should libraries not pin exact versions?">
Exact pins in libraries cause conflicts when applications combine several libraries; libraries declare compatible ranges and applications pin exact versions.
</QA>

<QA q="How do you protect a build from tampered packages?">
Pin exact versions with hashes and install with --require-hashes, use a trusted single index, and audit dependencies for known vulnerabilities.
</QA>

</DeepDive>
