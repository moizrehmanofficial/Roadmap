<BigIdea>
<Tr>
<En>
A project's dependencies have two layers. The first is **what you ask for**: "requests, version 2.31 or newer but below 3", plus dev-only tools like pytest. The second is **what actually gets installed**: requests 2.32.3 **and** the exact versions of certifi, idna, urllib3 and charset-normalizer it pulled in. Good dependency management writes the first layer in **`pyproject.toml`** (the standard project file) and records the second in a **lock file** generated by a tool, so every laptop, CI run and server installs the same versions. A plain `requirements.txt` from `pip freeze` mixes the two layers and makes upgrades guesswork. **uv** (from Astral, written in Rust and very fast) handles the whole flow: `uv init` creates the project, **`uv add`** records a dependency and updates the lock, `uv add --dev` adds development tools in a separate **dependency group**, **`uv.lock`** pins every package (with hashes) for every platform, **`uv sync`** makes `.venv` match the lock exactly, and **`uv run`** runs commands inside the environment, syncing first. In CI you run `uv sync --locked` so the build fails if the lock is stale, and `uv export` writes a `requirements.txt` for tools that need one. **Poetry** offers a similar workflow (`poetry add`, `poetry.lock`), and **pip-tools** (or `uv pip compile`) keeps the older pattern of a short `requirements.in` compiled into a fully pinned `requirements.txt`.
</En>
<Ur>
Project ki dependencies ki do layers hain. Pehli **jo aap maangte hain**: "requests, version 2.31 ya naya magar 3 se neeche", aur pytest jaise sirf dev ke tools. Doosri **jo asal me install hota hai**: requests 2.32.3 **aur** certifi, idna, urllib3 aur charset-normalizer ke bilkul versions jo woh saath laaya. Achi dependency management pehli layer **`pyproject.toml`** (mayari project file) me likhti aur doosri tool ki banayi **lock file** me record karti hai, taa ke har laptop, CI run aur server wahi versions install kare. `pip freeze` se bani saadi `requirements.txt` dono layers mila deti aur upgrades ko andaza bazi bana deti hai. **uv** (Astral ka, Rust me likha aur bohat tez) poora silsila sambhalta hai: `uv init` project banata, **`uv add`** dependency record kar ke lock update karta, `uv add --dev` development tools alag **dependency group** me jorta, **`uv.lock`** har platform ke liye har package (hashes ke saath) pin karta, **`uv sync`** `.venv` ko bilkul lock jaisa banata, aur **`uv run`** pehle sync kar ke environment ke andar commands chalata hai. CI me aap `uv sync --locked` chalate hain taa ke lock purana ho to build nakam ho, aur `uv export` un tools ke liye `requirements.txt` likhta hai jinhe ye chahiye. **Poetry** milta julta tareeqa deta hai (`poetry add`, `poetry.lock`), aur **pip-tools** (ya `uv pip compile`) purana tareeqa qaim rakhta hai jis me chhoti `requirements.in` se mukammal pinned `requirements.txt` compile hoti hai.

<Why>
<Tr>
<En>

- "It worked yesterday" bugs often come from a transitive dependency silently upgrading.
- Separating dev tools keeps production images smaller and with less attack surface.
- Lock files make upgrades deliberate and reviewable: the diff shows exactly what changed.

</En>
<Ur>

- "Kal chal raha tha" wale bugs aksar khamoshi se upgrade hui transitive dependency se aate hain.
- Dev tools alag rakhna production images ko chhota aur kam hamle ki satah wala rakhta hai.
- Lock files upgrades ko soch samajh kar aur review ke qabil banati hain: diff bilkul batata hai kya badla.

</Ur>

</Why>

## Picture it

<Tr>
<En>

Think of **a recipe and a shopping receipt**.

- `pyproject.toml` is the recipe: "flour, any good brand; eggs, large". It says what you need and what's acceptable.
- The lock file is the receipt from the shop: exact brands, sizes and batch numbers of everything bought, including the baking powder the flour mix needed.
- To bake the identical cake elsewhere, you shop from the receipt, not the recipe.
- When you want newer ingredients, you deliberately go shopping again (re-lock) and compare the new receipt with the old one.

</En>
<Ur>

**Recipe aur khareedari ki raseed** socheyn.

- `pyproject.toml` recipe hai: "aata, koi bhi acha brand; ande, bare". Ye batati hai kya chahiye aur kya qabil-e-qubool hai.
- Lock file dukan ki raseed hai: khareedi gayi har cheez ke bilkul brands, size aur batch numbers, us baking powder samait jo aate ke mix ko chahiye tha.
- Kahin aur hoobahoo cake banane ke liye aap recipe se nahi, raseed se khareedari karte hain.
- Jab naye ajza chahiye hon, to aap soch kar dobara khareedari (re-lock) karte aur nayi raseed ka purani se muqabla karte hain.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |

| **Direct dependency** | Something you import and declared | `requests` |
| **Transitive dependency** | Pulled in by a dependency | `urllib3` |

## Learn it step by step

<Walkthrough>

<Step title="A uv project: init, add, dev dependencies, lock, tree and run">

<Tr>
<En>
We create an application project with `uv init`, add `requests` with a version range and `pytest` as a dev dependency, look at the resulting `pyproject.toml`, list every version pinned in `uv.lock`, print the runtime dependency tree, and run a script with `uv run`. The `UV_EXCLUDE_NEWER` line is only for this lesson: it makes uv ignore releases after June 2025 so the output is the same whenever you run it. Leave it out in real projects.
</En>
<Ur>
Hum `uv init` se application project banate, `requests` version range ke saath aur `pytest` dev dependency ke taur par jorte, nateeje me bani `pyproject.toml` dekhte, `uv.lock` me pin har version ki list banate, runtime dependency darakht print karte, aur `uv run` se script chalate hain. `UV_EXCLUDE_NEWER` wali line sirf is lesson ke liye hai: ye uv ko June 2025 ke baad ki releases nazar andaz karwati hai taa ke aap jab bhi chalayen output wahi ho. Asal projects me ise na likhein.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z   # demo only: resolve as of June 2025 so this output never changes
uv init -q --app --no-package --vcs none --author-from none --python 3.13 --name invoices invoices
cd invoices && ls -A
uv add -q "requests>=2.31,<3"
uv add -q --dev "pytest==8.3.5"
echo "--- pyproject.toml:"; cat pyproject.toml
echo "--- uv.lock pins every package:"
grep -A1 '^name = ' uv.lock | grep -E '^(name|version)' | paste -d' ' - - | sed -E 's/name = "([^"]+)" version = "([^"]+)"/\1==\2/' | grep -v '^invoices'
echo "--- runtime dependency tree:"; uv tree -q --no-dev
cat > main.py <<'EOF'
import requests
print("requests", requests.__version__, "ready")
EOF
uv run -q main.py
ls -A
```

<Tr>
<En>

- `uv init` created **pyproject.toml**, **main.py**, **README.md** and **.python-version** (which pins the Python version for the project; uv can download that Python if it's missing). Normally it also runs `git init` and writes a `.gitignore`; we turned that off with `--vcs none`.
- `uv add` wrote the **range** into `dependencies`, and `uv add --dev` put pytest into a separate **dev group**. You declare intent; you don't hand-edit versions of transitive packages.
- **uv.lock** pinned all ten packages: requests and its four dependencies, pytest and its own (iniconfig, packaging, pluggy), and **colorama**, which pytest only needs on Windows. The lock is **universal**: one file covers Linux, macOS and Windows, using markers so each platform installs what it needs.
- `uv tree --no-dev` showed what production will install and why each package is there.
- `uv run` created `.venv` (visible in the final listing), synced it with the lock, and ran the script, without any activation step. Commit `pyproject.toml`, `uv.lock` and `.python-version`; ignore `.venv`.

</En>
<Ur>

- `uv init` ne **pyproject.toml**, **main.py**, **README.md** aur **.python-version** banayi (jo project ka Python version pin karti; ghayab ho to uv woh Python download kar sakta hai). Aam taur par ye `git init` bhi chalata aur `.gitignore` likhta hai; humne `--vcs none` se band kiya.
- `uv add` ne **range** ko `dependencies` me likha, aur `uv add --dev` ne pytest ko alag **dev group** me rakha. Aap irada likhte hain; transitive packages ke versions haath se edit nahi karte.
- **uv.lock** ne dason packages pin kiye: requests aur us ki chaar dependencies, pytest aur us ki apni (iniconfig, packaging, pluggy), aur **colorama**, jo pytest ko sirf Windows par chahiye. Lock **universal** hai: ek file Linux, macOS aur Windows ko cover karti, markers ke saath taa ke har platform wahi install kare jo use chahiye.
- `uv tree --no-dev` ne dikhaya ke production kya install karega aur har package kyun hai.
- `uv run` ne `.venv` banaya (aakhri list me nazar aata), use lock ke saath sync kiya, aur baghair activation ke script chalayi. `pyproject.toml`, `uv.lock` aur `.python-version` commit karein; `.venv` ignore karein.

<Step title="Locked installs, stale-lock checks, exports and compiling requirements">

<Tr>
<En>
We copy the committed files to a fresh folder, as a teammate or CI would see them, and install exactly the lock without dev tools. Then we add a dependency to `pyproject.toml` by hand without re-locking and let `uv lock --check` catch it, re-lock, export a plain and a hash-pinned `requirements.txt`, and finally use the classic `requirements.in` workflow with `uv pip compile`.
</En>
<Ur>
Hum commit hui files naye folder me copy karte hain, jaise teammate ya CI unhe dekhega, aur dev tools ke baghair bilkul lock install karte hain. Phir dobara lock kiye baghair haath se `pyproject.toml` me dependency jorte aur `uv lock --check` ko pakarne dete, dobara lock karte, saadi aur hash-pinned `requirements.txt` export karte, aur aakhir me `uv pip compile` ke saath purana `requirements.in` tareeqa istemal karte hain.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z
cd invoices
# A teammate (or CI) gets the repo without .venv and installs exactly what's locked
mkdir ../clone && cp pyproject.toml uv.lock .python-version main.py ../clone/ && cd ../clone
uv sync -q --locked --no-dev                       # production: no pytest
uv run -q --no-sync python -c 'from importlib.metadata import version as v; print("clone:", "requests", v("requests"), "urllib3", v("urllib3"))'
uv run -q --no-sync python -c 'import pytest' 2>&1 | tail -1

# Someone edits pyproject.toml by hand but forgets to re-lock: CI catches it
sed -i 's/"requests>=2.31,<3",/"requests>=2.31,<3",\n    "humanize>=4",/' pyproject.toml
uv lock --check > check.txt 2>&1; echo "uv lock --check exit code: $?"
grep -o "needs to be updated" check.txt | head -1
uv lock -q && uv lock --check -q && echo "after uv lock: lock file up to date"

# Export for tools that only understand requirements.txt (Docker images, older platforms)
uv export -q --no-dev --no-hashes --no-header --no-annotate -o requirements.txt
cat requirements.txt
uv export -q --no-dev --no-header -o requirements-hashed.txt && echo "hash lines in hashed export: $(grep -c -- '--hash=sha256' requirements-hashed.txt)"

# The classic two-file workflow without a project: requirements.in -> compiled requirements.txt
printf 'requests>=2.31,<3\n' > requirements.in
uv pip compile -q requirements.in --no-header --no-annotate -o compiled.txt && cat compiled.txt
```

<Happened>
<Tr>
<En>

- The clone got **exactly** requests 2.32.3 and urllib3 2.4.0 from the lock, and `--no-dev` left pytest out (**ModuleNotFoundError**), which is what production images want.
- After the hand edit, `uv lock --check` exited with **1** because the lock **needs to be updated**. Put `uv sync --locked` or `uv lock --check` in CI so a forgotten re-lock fails the build instead of installing something unreviewed.
- `uv lock` resolved the new dependency (humanize **4.12.3**, the newest before the cut-off date) and the check passed.
- `uv export` produced a pinned `requirements.txt` for tools that don't understand `uv.lock`. The default export includes **hashes** (25 lines here, one per allowed wheel or source file), ready for `pip install --require-hashes`.
- `uv pip compile` turned a one-line `requirements.in` into a fully pinned list, the same idea as pip-tools' `pip-compile`. You edit the short `.in` file and commit both.

</En>
<Ur>

- Clone ko lock se **bilkul** requests 2.32.3 aur urllib3 2.4.0 mile, aur `--no-dev` ne pytest chhor diya (**ModuleNotFoundError**), jo production images chahti hain.
- Haath ki tabdeeli ke baad `uv lock --check` **1** ke saath nikla kyunke lock ko **update ki zaroorat** hai. CI me `uv sync --locked` ya `uv lock --check` rakhein taa ke bhoola hua re-lock bina review ki cheez install karne ke bajaye build nakam kare.
- `uv lock` ne nayi dependency resolve ki (humanize **4.12.3**, cut-off date se pehle ka sab se naya) aur check paas hua.
- `uv export` ne un tools ke liye pinned `requirements.txt` banayi jo `uv.lock` nahi samajhte. Default export me **hashes** shamil hain (yahan 25 lines, har ijazat wali wheel ya source file ki ek), `pip install --require-hashes` ke liye tayyar.
- `uv pip compile` ne ek line ki `requirements.in` ko mukammal pinned list me badla, pip-tools ke `pip-compile` wala hi khayal. Aap chhoti `.in` file edit karte aur dono commit karte hain.

</Ur>

## Common mistakes

<Compare>
<Bad title="Freezing everything into one file">

```text
pip install requests pytest black ipython
pip freeze > requirements.txt       # 40 lines: what did we actually ask for?
# production installs pytest, black and ipython too
```

</Bad>
<Good title="Declare intent, lock the rest, separate dev tools">

```text
uv add "requests>=2.31,<3"
uv add --dev pytest ruff
uv sync --locked --no-dev            # production
```

</Good>
</Compare>

<Compare>
<Bad title="CI that re-resolves">

```text
# CI
uv sync                              # quietly updates uv.lock if it's stale
pip install -r requirements.in       # ranges: different versions every run
```

</Bad>
<Good title="CI that installs the lock or fails">

```text
# CI
uv sync --locked                     # error if uv.lock doesn't match pyproject.toml
uv run pytest
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Not committing the lock file** for applications: then it does nothing.
- **Hand-editing `uv.lock` or `poetry.lock`**: always regenerate with the tool.
- **Upgrading everything at once** (`uv lock --upgrade`) right before a release; upgrade regularly and in small steps, and review the lock diff.
- **Mixing tools** (pip installs into a uv- or Poetry-managed `.venv`): the next sync removes or conflicts with them.
- **Exact pins in a published library's `dependencies`**: they cause conflicts for every application using it.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Applications ke liye lock file commit na karna**: phir ye kuch nahi karti.
- **`uv.lock` ya `poetry.lock` haath se edit karna**: hamesha tool se dobara banayen.
- **Release se theek pehle sab kuch ek saath upgrade** (`uv lock --upgrade`); baqaida aur chhote qadmon me upgrade karein, aur lock ka diff review karein.
- **Tools milana** (uv ya Poetry ke `.venv` me pip installs): agla sync unhe hata deta ya takraata hai.
- **Publish hui library ki `dependencies` me bilkul pins**: ye use karne wali har application ke liye takraav banate hain.

</Ur>
</Tr>

<Challenge title="Read a lock file">

<Tr>
<En>
`uv.lock` is TOML. Using the built-in `tomllib`, parse the snippet below and print each package as `name==version`, sorted by name, skipping the project itself (the package whose source is `editable` or `virtual`). Snippet: three `[[package]]` tables: `name = "invoices"` with `source = { virtual = "." }`, `name = "requests"` version `2.32.3`, and `name = "idna"` version `3.10`, both with a registry source.
</En>

`uv.lock` TOML hai. lock_text = '''
version = 1

[[package]]
name = "invoices"
version = "0.1.0"
source = { virtual = "." }

name = "requests"
version = "2.32.3"
source = { registry = "https://pypi.org/simple" }

[[package]]
name = "idna"
version = "3.10"
source = { registry = "https://pypi.org/simple" }

    for p in lock["package"]

<Tr>
<En>

```text
def parse(lines):
    return dict(line.split("==") for line in lines)

def lock_diff(old, new):
    a, b = parse(old), parse(new)
    for name in sorted(b.keys() - a.keys()):
        print(f"+ {name} {b[name]}")
    for name in sorted(a.keys() - b.keys()):
        print(f"- {name} {a[name]}")
    for name in sorted(a.keys() & b.keys()):
        if a[name] != b[name]:
            print(f"~ {name} {a[name]} -> {b[name]}")

lock_diff(
    ["requests==2.32.3", "urllib3==2.2.3", "idna==3.10", "six==1.16.0"],
    ["requests==2.32.4", "urllib3==2.2.3", "idna==3.10", "certifi==2025.4.26"],
)

# + certifi 2025.4.26
# - six 1.16.0
# ~ requests 2.32.3 -> 2.32.4
```

A short summary like this, posted on a pull request, makes dependency updates easy to review.

<DeepDive title="More about dependency management">

**Poetry in one minute.** `poetry new` or `poetry init`, `poetry add requests`, `poetry add --group dev pytest`, `poetry install`, `poetry run pytest`, `poetry lock`. It also builds and publishes packages. Its lock is per-project like uv's.

**Python versions.** `uv python install 3.13` and `.python-version` pin the interpreter too; Poetry relies on pyenv or the system.

**Inline script metadata.** A single script can declare its dependencies in a comment block (PEP 723), and `uv run script.py` builds a throwaway environment for it.

**Automated updates.** Dependabot and Renovate open pull requests that update lock files on a schedule, with your tests running against them.

**Docker caching.** Copy `pyproject.toml` and `uv.lock` first and run `uv sync --locked --no-install-project`, then copy the source, so dependency layers are cached between builds.

</DeepDive>

<DeepDive title="Real world: the Friday transitive upgrade">

A service pinned only its direct dependencies in `requirements.txt`. On a Friday, a new release of a transitive dependency changed a default timeout. Nothing in the repository changed, but the next Docker build picked up the new version, and requests to a slow partner API started failing in production.

The fixes:

1. Move to `pyproject.toml` plus a lock file, and build images with `uv sync --locked`.
2. Weekly automated update pull requests that run the full test suite.
3. Changelogs are reviewed for any package whose major or minor version changes.

</DeepDive>

<DeepDive title="Security lens">

- **Lock with hashes** so a tampered or replaced file can't be installed silently.
- **Fail CI on stale locks**: unreviewed resolution is how unexpected packages sneak in.
- **Keep dev tools out of production** images to reduce attack surface.
- **Scan the lock**: `uv export` into `pip-audit`, or use Dependabot alerts, to find known CVEs.
- **Review lock diffs** in pull requests: new transitive packages deserve a look.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between pyproject.toml dependencies and a lock file?">
pyproject.toml lists direct dependencies with acceptable version ranges, while the lock file records the exact resolved versions, and usually hashes, of every direct and transitive package so installs are reproducible.
</QA>

<QA q="Why not just use pip freeze?">
freeze captures everything installed, including dev tools and leftovers, without distinguishing direct from transitive dependencies, which makes upgrades and removals hard to manage.
</QA>

<QA q="How do you make sure CI installs exactly what was reviewed?">
Install from the committed lock with a command that refuses to update it, such as uv sync --locked or poetry install with a lock check, and fail the build if it is out of date.
</QA>

<QA q="What are dependency groups?">
Named sets of dependencies, such as dev or test, that are installed only when requested, keeping tools like pytest and linters out of production environments.
</QA>

<QA q="How would you upgrade a single dependency safely?">
Run a targeted upgrade such as uv lock --upgrade-package name, review the lock diff and changelog, run the test suite, and merge it as its own change.
</QA>

</DeepDive>
