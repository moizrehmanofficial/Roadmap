<BigIdea>
<Tr>
<En>
By default pip installs packages into one shared place for the whole Python installation, so every project on the machine would share the same versions, and upgrading a package for one project could break another or even break operating-system tools written in Python. A **virtual environment** solves this: it's a folder (by convention **`.venv`** in the project) containing its own `python` and its own **site-packages** where packages go. Create one with **`python3 -m venv .venv`**. **Activating** it (`. .venv/bin/activate` on Linux and macOS, `.venv\Scripts\activate` on Windows) puts its `python` and `pip` first on your PATH for the current terminal, so `python -m pip install` now installs into the project only; `deactivate` switches back. Activation is just a convenience: running **`.venv/bin/python`** directly uses the environment too, which is how cron jobs, systemd services and Dockerfiles use it. A venv is **disposable**: you don't copy it or commit it to Git (add `.venv/` to `.gitignore`); you commit `requirements.txt` and recreate the environment anywhere with `python3 -m venv .venv` plus `pip install -r requirements.txt`. Since Python 3.11 many Linux distributions even refuse system-wide `pip install` (PEP 668, "externally managed environment"), so virtual environments are the normal way to work.
</En>
<Ur>
Default me pip packages poori Python installation ki ek mushtarka jagah me install karta hai, isliye machine ka har project wahi versions share karta, aur ek project ke liye package upgrade karna doosre ko, ya Python me likhe operating system ke tools tak ko, tor sakta tha. **Virtual environment** ye hal karta hai: ye ek folder hai (riwaj ke mutabiq project me **`.venv`**) jis me apna `python` aur apna **site-packages** hota hai jahan packages jate hain. Ise **`python3 -m venv .venv`** se banayen. Ise **activate** karna (Linux aur macOS par `. .venv/bin/activate`, Windows par `.venv\Scripts\activate`) mojooda terminal ke liye us ke `python` aur `pip` ko PATH me sab se aage rakhta hai, isliye ab `python -m pip install` sirf project me install karta hai; `deactivate` wapas le jata hai. Activation bas sahulat hai: **`.venv/bin/python`** seedha chalana bhi environment istemal karta hai, isi tarah cron jobs, systemd services aur Dockerfiles ise istemal karte hain. Venv **phenk dene layak** hai: aap ise copy ya Git me commit nahi karte (`.venv/` ko `.gitignore` me daalein); aap `requirements.txt` commit karte aur kahin bhi `python3 -m venv .venv` aur `pip install -r requirements.txt` se environment dobara banate hain. Python 3.11 se kai Linux distributions system-wide `pip install` se inkar bhi karti hain (PEP 668, "externally managed environment"), isliye virtual environments kaam ka aam tareeqa hain.
</Ur>

## Picture it

<Tr>
<En>

Think of **separate toolboxes for separate jobs**.

- The system Python is the building's shared tool room: if one tenant swaps the wrench for a different size, everyone else's work is affected, and the building's maintenance staff depend on it too.
- A virtual environment is a personal toolbox kept in each project's room, with exactly the tools that project needs.
- Activating it is picking up that toolbox for this job; deactivating is putting it down.
- `requirements.txt` is the label listing what goes in the box, so if the box is lost, you fill a new one exactly the same way.

</En>
<Ur>

**Mukhtalif kaamon ke liye alag toolboxes** socheyn.

- System Python imarat ka mushtarka tool room hai: agar ek kirayedar paana doosre size se badal de, to sab ka kaam mutasir hota hai, aur imarat ka maintenance staff bhi is par mabni hai.
- Virtual environment har project ke kamre me rakha zaati toolbox hai, bilkul un auzaron ke saath jo us project ko chahiye.
- Ise activate karna is kaam ke liye toolbox uthana hai; deactivate karna use neeche rakhna.
- `requirements.txt` dabbe me jane wali cheezon ki list wala label hai, taa ke dabba kho jaye to aap naya bilkul usi tarah bhar sakein.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Create, activate, install, deactivate, and run directly">

<Tr>
<En>
We create `.venv`, look inside it and at its config, check whether Python is running in a virtual environment before and after activating, install `humanize` and see where it was installed, deactivate and confirm the system Python can't see the package, and finally run the venv's Python directly without activating.
</En>
<Ur>
Hum `.venv` banate, us ke andar aur us ki config dekhte, activate karne se pehle aur baad check karte hain ke Python virtual environment me chal raha hai ya nahi, `humanize` install kar ke dekhte hain kahan install hua, deactivate kar ke tasdeeq karte hain ke system Python package nahi dekh sakta, aur aakhir me activate kiye baghair venv ka Python seedha chalate hain.
</Ur>
</Tr>

```bash
python3 -m venv .venv
ls .venv
grep -E "^(include-system-site-packages|version)" .venv/pyvenv.cfg | sed -E 's/= 3\.13\.[0-9]+/= 3.13.x/'

check() { python -c 'import sys; print("in venv:", sys.prefix != sys.base_prefix)'; }
echo "--- before activating:"; check
. .venv/bin/activate                     # Windows: .venv\Scripts\activate
echo "--- after activating:"; check
echo "python is: $(command -v python | sed "s#$PWD/##")"
python -m pip install -q "humanize==4.11.0"
python -c 'import humanize; print(humanize.naturalsize(3_500_000), "|", humanize.intcomma(1234567))'
python -c 'import humanize, os; print("installed in:", os.path.relpath(humanize.__file__))'
deactivate
echo "--- after deactivate:"; check
python3 -c "import humanize" 2>&1 | tail -1
echo "--- without activating, call the venv's python directly:"
.venv/bin/python -c 'import humanize; print("works:", humanize.intword(2_500_000))'
```

<Happened>
<Tr>
<En>

- `python3 -m venv .venv` created **bin**, **lib** (where site-packages lives), **include** and **pyvenv.cfg** (Linux also adds a `lib64` link; Windows uses `Scripts` and `Lib`). The config says it was made from Python 3.13 and does **not** see system packages.
- `sys.prefix != sys.base_prefix` is the reliable test for "am I in a virtual environment?". It was False before activation and **True** after.
- Activation made `python` mean **.venv/bin/python**. Your prompt usually shows `(.venv)` as a reminder.
- `humanize` was installed under **.venv/lib/python3.13/site-packages**, inside the project.
- After `deactivate`, the system `python3` raised **ModuleNotFoundError**: the system was untouched.
- Calling **.venv/bin/python** directly used the environment without activating it. This is how you run project scripts from cron, systemd units (`ExecStart=/srv/app/.venv/bin/python app.py`) or Dockerfiles.

</En>
<Ur>

- `python3 -m venv .venv` ne **bin**, **lib** (jahan site-packages hai), **include** aur **pyvenv.cfg** banaye (Linux `lib64` link bhi jorta; Windows `Scripts` aur `Lib` istemal karta hai). Config batati hai ke ye Python 3.13 se bana aur system packages **nahi** dekhta.
- `sys.prefix != sys.base_prefix` "kya main virtual environment me hun?" ka bharose wala test hai. Activation se pehle False aur baad **True** tha.
- Activation ne `python` ka matlab **.venv/bin/python** bana diya. Aap ka prompt aam taur par yaad dahani ke liye `(.venv)` dikhata hai.
- `humanize` project ke andar **.venv/lib/python3.13/site-packages** me install hua.
- `deactivate` ke baad system `python3` ne **ModuleNotFoundError** diya: system ko kuch nahi hua.
- **.venv/bin/python** seedha bulane se activate kiye baghair environment istemal hua. Isi tarah aap project scripts cron, systemd units (`ExecStart=/srv/app/.venv/bin/python app.py`) ya Dockerfiles se chalate hain.

</Ur>

<Step title="Side-by-side versions, rebuilding, and keeping .venv out of Git">

<Tr>
<En>
We create two projects with their own environments and install a different version of `humanize` in each. Then, in one project, we save the dependencies with `pip freeze`, add a `.gitignore`, delete the environment completely and rebuild it from `requirements.txt`, and check which files Git would commit.
</En>
<Ur>
Hum apne apne environments wale do projects banate aur har ek me `humanize` ka mukhtalif version install karte hain. Phir ek project me `pip freeze` se dependencies save karte, `.gitignore` jorte, environment poora delete kar ke `requirements.txt` se dobara banate, aur check karte hain ke Git kaun si files commit karega.
</Ur>
</Tr>

```bash
# Two projects, two different versions of the same package, side by side
for p in old-app new-app; do mkdir -p $p && python3 -m venv $p/.venv; done
old-app/.venv/bin/python -m pip install -q "humanize==4.9.0"
new-app/.venv/bin/python -m pip install -q "humanize==4.11.0"
for p in old-app new-app; do
  echo "$p: $($p/.venv/bin/python -c 'from importlib.metadata import version; print("humanize", version("humanize"))')"
done

# Record dependencies, then throw the environment away and rebuild it
cd new-app
.venv/bin/python -m pip freeze > requirements.txt
cat requirements.txt
printf '.venv/\n__pycache__/\n' > .gitignore          # never commit the venv itself
rm -rf .venv
python3 -m venv .venv && .venv/bin/python -m pip install -q -r requirements.txt
echo "rebuilt: $(.venv/bin/python -m pip freeze)"
echo "venv over 5 MB: $([ $(du -sm .venv | cut -f1) -gt 5 ] && echo yes), and all of it can be recreated"
git init -q . && git add -A && echo "files git would commit: $(git diff --cached --name-only | tr '\n' ' ')"
```

```text output
old-app: humanize 4.9.0
new-app: humanize 4.11.0
humanize==4.11.0
rebuilt: humanize==4.11.0
venv over 5 MB: yes, and all of it can be recreated
files git would commit: .gitignore requirements.txt 
```

<Happened>
<Tr>
<En>

- **old-app** has humanize **4.9.0** and **new-app** has **4.11.0** on the same machine, with no conflict. Without venvs, installing one would have replaced the other.
- `pip freeze` captured the environment's exact contents into `requirements.txt`.
- We deleted `.venv` entirely and rebuilt it with two commands; the result was **identical**. Treat environments as cattle, not pets: when something's odd, rebuild.
- The venv was **over 5 MB** even with one small package (real projects reach hundreds of MB). It contains machine-specific paths, so copying it to another machine or committing it doesn't work. With `.venv/` in `.gitignore`, Git would commit only **.gitignore** and **requirements.txt**.

</En>
<Ur>

- Ek hi machine par **old-app** me humanize **4.9.0** aur **new-app** me **4.11.0** hai, baghair takraav ke. Venvs ke baghair ek install karna doosre ko badal deta.
- `pip freeze` ne environment ka bilkul mawad `requirements.txt` me mehfooz kiya.
- Humne `.venv` poora delete kar ke do commands se dobara banaya; natija **hoobahoo** tha. Environments ko pets nahi, cattle samjhein: kuch ajeeb ho to dobara banayen.
- Ek chhote package ke saath bhi venv **5 MB se zyada** tha (asal projects saikron MB tak pohanchte hain). Is me machine ke mutabiq paths hote hain, isliye ise doosri machine par copy ya commit karna kaam nahi karta. `.gitignore` me `.venv/` ke saath Git sirf **.gitignore** aur **requirements.txt** commit karta.

</Ur>

## Common mistakes

<Compare>
<Bad title="Installing globally and committing the venv">

```text
sudo pip install flask                 # system Python; may break OS tools
git add .                              # commits .venv/ with thousands of files
```

</Bad>
<Good title="Per-project venv, ignored by Git">

```text
python3 -m venv .venv && . .venv/bin/activate
python -m pip install -r requirements.txt
echo ".venv/" >> .gitignore
git add requirements.txt app.py .gitignore
```

</Good>
</Compare>

<Compare>
<Bad title="Relying on activation in automation">

```text
# crontab
0 2 * * * python3 /srv/report/report.py      # system python: ModuleNotFoundError
```

</Bad>
<Good title="Call the environment's Python by path">

```text
# crontab
0 2 * * * /srv/report/.venv/bin/python /srv/report/report.py
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting which environment is active** and installing into the wrong one: check the prompt or `python -c "import sys; print(sys.prefix)"`.
- **Moving or renaming the project folder**: scripts inside the venv contain absolute paths; recreate it.
- **Upgrading the base Python** (3.12 to 3.13) and expecting old venvs to work: recreate them.
- **PowerShell refusing `Activate.ps1`**: adjust the execution policy for your user (`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`) or call `.venv\Scripts\python` directly.
- **Using `--break-system-packages` to "fix" PEP 668 errors** instead of creating a venv.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bhool jana ke kaun sa environment active hai** aur ghalat me install karna: prompt ya `python -c "import sys; print(sys.prefix)"` check karein.
- **Project folder hilana ya naam badalna**: venv ke andar scripts me absolute paths hote hain; dobara banayen.
- **Base Python upgrade karna** (3.12 se 3.13) aur purane venvs ke chalne ki tawaqqo: dobara banayen.
- **PowerShell ka `Activate.ps1` se inkar**: apne user ke liye execution policy badlein (`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`) ya `.venv\Scripts\python` seedha bulayen.
- **PEP 668 errors "theek" karne ke liye `--break-system-packages`** venv banane ke bajaye.

</Ur>
</Tr>

<Challenge title="Where am I running?">

<Tr>
<En>
Write `describe_env()` that returns a one-line description: whether the current interpreter is in a virtual environment, the Python version as `major.minor`, and whether a module named `humanize` can be imported (use `importlib.util.find_spec`, which doesn't actually import it). Run it with the system `python3`.
</En>
<Ur>
`describe_env()` likhein jo ek line ki tafseel lautaye: mojooda interpreter virtual environment me hai ya nahi, `major.minor` ki shakal me Python version, aur `humanize` naam ka module import ho sakta hai ya nahi (`importlib.util.find_spec` lein, jo asal me import nahi karta). Ise system `python3` se chalayen.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
import sys
from importlib.util import find_spec

def describe_env():
    in_venv = sys.prefix != sys.base_prefix
    version = f"{sys.version_info.major}.{sys.version_info.minor}"
    has_humanize = find_spec("humanize") is not None
    where = "virtual environment" if in_venv else "system Python"
    return f"{where}, Python {version}, humanize available: {has_humanize}"

print(describe_env())

# system Python, Python 3.13, humanize available: False
```

Run the same file with `.venv/bin/python` from the lesson and it reports a virtual environment with humanize available.

</En>

<Challenge title="Create a venv from Python">

<Tr>
<En>
Use the `venv` module's `venv.create(path, with_pip=False)` to create an environment in a folder named `scratch-env`, then use `subprocess.run` to execute its Python (`scratch-env/bin/python`, or `Scripts\python.exe` on Windows) with code that prints whether it's in a virtual environment. Print that output and whether `pyvenv.cfg` exists.
</En>
<Ur>
`venv` module ka `venv.create(path, with_pip=False)` istemal kar ke `scratch-env` naam ke folder me environment banayen, phir `subprocess.run` se us ka Python (`scratch-env/bin/python`, ya Windows par `Scripts\python.exe`) aise code ke saath chalayen jo print kare ke woh virtual environment me hai ya nahi. Woh output aur ye ke `pyvenv.cfg` mojood hai ya nahi, print karein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
import subprocess, sys, venv
from pathlib import Path

env_dir = Path("scratch-env")
venv.create(env_dir, with_pip=False)          # with_pip=False is faster; enough for this test
python = env_dir / ("Scripts/python.exe" if sys.platform == "win32" else "bin/python")

result = subprocess.run(
    [str(python), "-c", "import sys; print('in venv:', sys.prefix != sys.base_prefix)"],
    capture_output=True, text=True, check=True,
)
print(result.stdout.strip(), "| pyvenv.cfg exists:", (env_dir / "pyvenv.cfg").exists())

# in venv: True | pyvenv.cfg exists: True
```

</En>

<DeepDive title="More about virtual environments">

**How activation works.** The activate script prepends `.venv/bin` to PATH, sets `VIRTUAL_ENV` and changes the prompt; `deactivate` restores them. Nothing else changes.

**How isolation works.** On startup Python finds `pyvenv.cfg` next to its executable and uses the venv's site-packages instead of the system's.

**Other tools.** `virtualenv` (older, more features), `conda` (also manages non-Python libraries), and `uv venv` (very fast) create similar environments.

**Docker.** Many images create a venv in the image, for example at `/opt/venv`, and put its `bin` on PATH, which keeps the image's system Python clean.

**IDE integration.** VS Code and PyCharm detect `.venv` in the project and use it for running and linting.

</DeepDive>

<DeepDive title="Real world: the server where pip broke yum">

An administrator ran `sudo pip install --upgrade` for a library on a CentOS server to fix one script. The upgrade replaced a version that the system package manager's own Python code depended on, and `yum` stopped working. Fixing it required manually reinstalling system packages during a maintenance window.

The fixes:

1. Application scripts run from their own venvs under `/srv/<app>/.venv`.
2. System-wide pip installs were blocked, which PEP 668 now does by default on many distributions.
3. Admin tools are installed with `pipx`.

</DeepDive>

<DeepDive title="Security lens">

- **Isolation limits blast radius**: a compromised or broken dependency affects one project, not the whole system.
- **Least privilege**: never `sudo pip`; venvs live in folders owned by the service user.
- **Rebuild from pinned, hashed requirements** in CI and production instead of copying environments between machines.
- **Don't trust a downloaded `.venv`**: its scripts can contain arbitrary code; recreate environments yourself.
- **Scan per environment** with `pip-audit` to see exactly what each service ships.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What problem do virtual environments solve?">
They isolate each project's packages and versions from other projects and from the system Python, preventing conflicts and making dependencies reproducible.
</QA>

<QA q="What does activating a virtual environment actually do?">
It prepends the environment's bin or Scripts folder to PATH, sets VIRTUAL_ENV and changes the prompt, so python and pip resolve to the environment's executables.
</QA>

<QA q="Why not commit the virtual environment to version control?">
It is large, contains platform- and path-specific files, and can be recreated exactly from a requirements or lock file, which is what should be committed.
</QA>

<QA q="How do you use a virtual environment in a systemd service or cron job?">
Reference the environment's interpreter by absolute path, such as /srv/app/.venv/bin/python, without activating it.
</QA>

<QA q="What is the externally-managed-environment error?">
It comes from PEP 668: the distribution marks its Python as managed by the OS package manager, so pip refuses to install system-wide and you should use a virtual environment or pipx.
</QA>

</DeepDive>
