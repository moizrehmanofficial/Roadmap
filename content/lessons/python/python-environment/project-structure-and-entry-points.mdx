<BigIdea>
<Tr>
<En>
A professional Python project separates **what the code does** from **how it's started**. The logic lives in an importable **package**: a folder with `__init__.py` and modules such as `core.py`, placed under **`src/`** (the **src layout**) so that tests and tools import the *installed* package rather than whatever happens to be in the current folder. Command-line handling lives in its own module, typically `cli.py`, with a **`main(argv=None)`** function that parses arguments, calls the logic and returns an **exit code**; because it takes arguments, tests can call it directly. Tests live in **`tests/`**, and **`pyproject.toml`** describes the project, its dependencies and its **entry points**. There are three standard ways to start a program: the **`if __name__ == "__main__":`** guard runs code only when a file is executed, not when it's imported; a **`__main__.py`** inside the package makes **`python -m package`** work; and a **console script** declared under **`[project.scripts]`** (`invoicer = "invoicer.cli:main"`) makes the installer create a real command named `invoicer` that calls that function. Running a module inside a package as a plain file (`python src/invoicer/cli.py`) breaks its relative imports, so use `python -m` or the installed command instead.
</En>
<Ur>
Professional Python project **code kya karta hai** ko **kaise shuru hota hai** se alag rakhta hai. Logic ek import hone wale **package** me hoti hai: `__init__.py` aur `core.py` jaise modules wala folder, jo **`src/`** ke neeche rakha jata hai (**src layout**) taa ke tests aur tools mojooda folder me pari cheez ke bajaye *installed* package import karein. Command-line ka kaam apne module me hota hai, aam taur par `cli.py`, jis me **`main(argv=None)`** function arguments parse karta, logic bulata aur **exit code** lautata hai; kyunke ye arguments leta hai, tests ise seedha bula sakte hain. Tests **`tests/`** me hote hain, aur **`pyproject.toml`** project, us ki dependencies aur us ke **entry points** bayan karti hai. Program shuru karne ke teen mayari tareeqe hain: **`if __name__ == "__main__":`** guard code sirf tab chalata hai jab file chalayi jaye, import par nahi; package ke andar **`__main__.py`** **`python -m package`** chalne deta hai; aur **`[project.scripts]`** ke neeche likha **console script** (`invoicer = "invoicer.cli:main"`) installer se `invoicer` naam ki asal command banwata hai jo woh function bulati hai. Package ke andar ke module ko saadi file ki tarah chalana (`python src/invoicer/cli.py`) us ke relative imports tor deta hai, isliye `python -m` ya installed command lein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **restaurant**.

- `core.py` is the kitchen: it cooks, and it doesn't care whether the order came by phone, app or waiter.
- `cli.py` is the waiter: takes the order (arguments), passes it to the kitchen, brings back the plate (output) and the bill (exit code).
- The three entry points are three doors into the same restaurant: the staff entrance (`python file.py`), the side door (`python -m invoicer`) and the front door with a sign on it (the `invoicer` command).
- The src layout keeps the kitchen behind a wall, so inspectors (tests) can only test the restaurant as customers experience it, not by wandering into the storeroom.

</En>

- `core.py` kitchen hai: ye pakata hai, aur use parwah nahi ke order phone, app ya waiter se aaya.
- `cli.py` waiter hai: order (arguments) leta, kitchen tak pohanchata, plate (output) aur bill (exit code) wapas laata hai.
- Teen entry points ek hi restaurant ke teen darwaze hain: staff ka darwaza (`python file.py`), side ka darwaza (`python -m invoicer`) aur board wala saamne ka darwaza (`invoicer` command).
- Src layout kitchen ko deewar ke peeche rakhta hai, taa ke inspectors (tests) restaurant ko waise hi test karein jaise customers dekhte hain, store room me ghoom kar nahi.

## Learn it step by step

<Walkthrough>

<Step title="Build a src-layout project with a CLI, python -m and tests">

<Tr>
<En>
We create the `invoicer` project by hand: a `pyproject.toml` with a console script, dev dependencies and a build backend; a package with `__init__.py`, `core.py` (pure logic using `Decimal`), `cli.py` (argparse and `main(argv)`) and `__main__.py`; and two tests. `uv sync` installs the project into `.venv` in editable mode, then we run the command, `python -m invoicer` and pytest. The `UV_EXCLUDE_NEWER` line only keeps versions fixed for this lesson.
</En>
<Ur>
Hum `invoicer` project haath se banate hain: console script, dev dependencies aur build backend wali `pyproject.toml`; `__init__.py`, `core.py` (`Decimal` wali khaalis logic), `cli.py` (argparse aur `main(argv)`) aur `__main__.py` wala package; aur do tests. `uv sync` project ko editable mode me `.venv` me install karta, phir hum command, `python -m invoicer` aur pytest chalate hain. `UV_EXCLUDE_NEWER` wali line sirf is lesson ke versions tay rakhti hai.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z   # demo only: fixed versions
mkdir -p invoicer/src/invoicer invoicer/tests && cd invoicer
cat > pyproject.toml <<'EOF'
[project]
name = "invoicer"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []

[project.scripts]
invoicer = "invoicer.cli:main"          # command name = "package.module:function"

[dependency-groups]
dev = ["pytest==8.3.5"]

[build-system]
requires = ["uv_build>=0.7,<0.14"]
build-backend = "uv_build"
EOF
cat > src/invoicer/__init__.py <<'EOF'
"""Small invoice helpers."""
__version__ = "0.1.0"
EOF
cat > src/invoicer/core.py <<'EOF'
from decimal import Decimal

def total(amounts, tax_rate="0"):
    subtotal = sum((Decimal(a) for a in amounts), Decimal("0"))
    return (subtotal * (1 + Decimal(tax_rate))).quantize(Decimal("0.01"))
EOF
cat > src/invoicer/cli.py <<'EOF'
import argparse, sys
from . import __version__
from .core import total

def main(argv=None):
    parser = argparse.ArgumentParser(prog="invoicer", description="Invoice totals")
    parser.add_argument("amounts", nargs="+")
    parser.add_argument("--tax", default="0")
    parser.add_argument("--version", action="version", version=f"%(prog)s {__version__}")
    args = parser.parse_args(argv)
    print(f"total: ${total(args.amounts, args.tax)}")
    return 0

if __name__ == "__main__":
    sys.exit(main())
EOF
cat > src/invoicer/__main__.py <<'EOF'
import sys
from .cli import main
sys.exit(main())
EOF
cat > tests/test_core.py <<'EOF'
from invoicer.core import total

def test_total_with_tax():
    assert str(total(["10", "20.50"], "0.1")) == "33.55"

def test_total_without_tax():
    assert str(total(["0.1", "0.2"])) == "0.30"
EOF
find . -type f | sort
uv sync -q
echo "--- the console command:"; uv run -q invoicer 10 20.50 --tax 0.1; uv run -q invoicer --version
echo "--- python -m runs __main__.py:"; uv run -q python -m invoicer 99.99
echo "--- tests:"; uv run -q pytest -q tests | sed -E 's/ in [0-9.]+s/ in <time>/'
```

<Tr>
<En>

- `python src/invoicer/cli.py` failed with **"attempted relative import with no known parent package"**: run as a file, `cli.py` is just a script called `__main__`, not `invoicer.cli`, so `from .core import ...` has no package to be relative to. Use `python -m invoicer` or the installed command.

## Common mistakes

<Compare>
<Bad title="Everything at module level in one file">

```text
# tool.py
import sys
amounts = sys.argv[1:]                 # runs on import, even from tests
print(sum(float(a) for a in amounts))  # logic, I/O and floats mixed together
```

</Bad>
<Good title="Logic, main(argv) and the guard">

```text
def total(amounts): ...                # pure, testable

def main(argv=None) -> int:
    args = parse(argv)
    print(total(args.amounts))
    return 0

if __name__ == "__main__":
    raise SystemExit(main())
```

</Good>
</Compare>

<Compare>
<Bad title="Fixing imports with sys.path hacks">

```text
# tests/test_core.py
import sys; sys.path.insert(0, "../src")   # breaks when run from another folder
from invoicer.core import total
```

</Bad>
<Good title="Install the project, then import normally">

```text
uv sync                 # or: python -m pip install -e .
uv run pytest           # tests import invoicer like any user would
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Running files inside a package directly** (`python src/pkg/cli.py`): use `python -m pkg.cli` or the console script.
- **Naming a module like a standard or third-party one** (`json.py`, `requests.py`, `logging.py`): it shadows the real one.
- **Calling `sys.exit` deep inside logic**: raise exceptions there and convert them to exit codes in `main()`.
- **Forgetting `__init__.py`** or listing the wrong package in build settings: the wheel ships without your code; the src layout plus tests catches this.
- **Putting secrets or local config files inside the package folder**: they get built into the wheel.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Package ke andar ki files seedha chalana** (`python src/pkg/cli.py`): `python -m pkg.cli` ya console script lein.
- **Module ka naam standard ya third-party jaisa rakhna** (`json.py`, `requests.py`, `logging.py`): ye asal wale ko chhupa deta hai.
- **Logic ke andar gehraai me `sys.exit` bulana**: wahan exceptions uthayen aur `main()` me unhe exit codes me badlein.
- **`__init__.py` bhoolna** ya build settings me ghalat package likhna: wheel aap ke code ke baghair jati hai; src layout aur tests ise pakarte hain.
- **Package folder ke andar secrets ya local config files rakhna**: ye wheel me build ho jati hain.

</Ur>
</Tr>

```text
import argparse, contextlib, io, sys

def main(argv=None):
    parser = argparse.ArgumentParser(prog="greet")
    parser.add_argument("name")
    parser.add_argument("--shout", action="store_true")
    args = parser.parse_args(argv)
    if not args.name.strip():
        print("greet: name must not be empty", file=sys.stderr)
        return 2
    message = f"Hello, {args.name}!"
    print(message.upper() if args.shout else message)
    return 0

for argv in (["Jane"], ["Jane", "--shout"], ["   "]):

    try:

        print("argparse error exit code:", e.code)

# HELLO, JANE!
# exit code: 0
# exit code: 2
# argparse error exit code: 2
```

<Challenge title="Resolve an entry point string">

<Tr>
<En>
Console scripts are written as `"package.module:function"`. Write `load_entry_point(spec)` that splits the string, imports the module with `importlib.import_module` and returns the function (support dotted attributes after the colon). Test it with `"json:dumps"` on `{"ok": True}`, `"os.path:join"` on `"logs", "app.log"`, and a missing module, which should raise a clear `ValueError`.
</En>
<Ur>
Console scripts `"package.module:function"` ki shakal me likhe jate hain. `load_entry_point(spec)` likhein jo string todta, `importlib.import_module` se module import karta aur function lautata hai (colon ke baad dots wale attributes bhi). Ise `{"ok": True}` par `"json:dumps"`, `"logs", "app.log"` par `"os.path:join"`, aur ghayab module ke saath test karein, jo wazeh `ValueError` uthaye.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
import importlib

def load_entry_point(spec):
    module_name, _, attr_path = spec.partition(":")
    try:
        obj = importlib.import_module(module_name)
    except ModuleNotFoundError as e:
        raise ValueError(f"cannot load {spec!r}: {e}") from e
    for attr in attr_path.split("."):
        obj = getattr(obj, attr)
    return obj

print(load_entry_point("json:dumps")({"ok": True}))
print(load_entry_point("os.path:join")("logs", "app.log"))
try:
    load_entry_point("invoicer_missing.cli:main")
except ValueError as e:
    print(e)

# {"ok": true}
# logs/app.log
# cannot load 'invoicer_missing.cli:main': No module named 'invoicer_missing'
```

This is essentially what the generated launcher script does for `invoicer.cli:main`. (On Windows, the second line prints `logs\app.log`.)

<DeepDive title="More about project structure">

**Build backends.** `uv_build`, `hatchling`, `setuptools`, `flit-core` and `pdm-backend` all read `[project]` from pyproject.toml; you pick one in `[build-system]`.

**Package data.** Non-Python files (templates, default configs) go inside the package and are read with `importlib.resources`, which works even from a zipped wheel.

**Versions.** Keep one source of truth, for example `version` in pyproject.toml read at runtime with `importlib.metadata.version("invoicer")`.

**Bigger apps.** Split by feature (`billing/`, `users/`) rather than by type (`models/`, `views/`) once a package grows; keep `cli.py` and API routes thin.

**CLI frameworks.** `click` and `typer` reduce argparse boilerplate and add subcommands, colors and shell completion.

</DeepDive>

<DeepDive title="Real world: the wheel without the code">

A team published an internal tool to their package index. Their local tests passed, but users installing it got `ModuleNotFoundError: No module named 'reporter.exporters'`. A new subpackage had been added without an `__init__.py` and wasn't picked up by the build configuration, but tests run from the project root imported the source folder directly, so nobody noticed.

The fixes:

1. Switch to the src layout so tests import only the installed package.
2. CI builds the wheel, installs it into a clean environment and runs a smoke test of the console script.
3. A check that lists the wheel's contents on every release.

</DeepDive>

<DeepDive title="Security lens">

- **Don't ship secrets**: `.env`, keys and local configs must stay outside the package folder and be excluded from builds; inspect wheel contents.
- **Entry points run with the user's permissions**: validate arguments and paths in `main()` before acting.
- **Exit codes matter** for automation: return non-zero on failure so pipelines don't continue after a silent error.
- **Avoid import-time side effects** (network calls, file writes) so importing a module for inspection or tests is safe.
- **Name collisions**: a local `requests.py` or `logging.py` can shadow real modules and change behaviour unexpectedly.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does if __name__ == '__main__' do?">
It runs the guarded code only when the file is executed as the main program; when the module is imported, `__name__` is the module's name and the block is skipped.
</QA>

<QA q="What is the src layout and why use it?">
The package lives under a src directory instead of the project root, so it can't be imported accidentally from the working directory; tests run against the installed package, catching packaging errors.
</QA>

<QA q="How do console script entry points work?">
pyproject.toml maps a command name to a module and function; on installation the installer writes a small launcher script or executable that imports and calls that function and exits with its return value.
</QA>

<QA q="Why do relative imports fail when running a module file directly?">
Run as a script, the module is named `__main__` and has no parent package, so imports relative to the package can't be resolved; run it with python -m package.module instead.
</QA>

<QA q="What is an editable install?">
An installation that points to the project's source files instead of copying them, so code changes take effect without reinstalling; created by pip install -e or uv sync for the project.
</QA>

</DeepDive>
