<BigIdea>
<Tr>
<En>
An **automated test** is a small function that runs a piece of your code with known inputs and checks the result. Run the whole suite after every change and you know within seconds whether you broke something, which is what makes refactoring, upgrades and fast deploys safe. **pytest** is the standard Python test runner. It finds files named `test_*.py` and functions named `test_*`, and you check results with a plain **`assert`**; when one fails, pytest shows the values on both sides. **`@pytest.mark.parametrize`** runs one test over a table of inputs, **`pytest.raises`** checks that bad input raises the right error, and **`pytest.approx`** compares floats. **Fixtures** provide what tests need: a function decorated with `@pytest.fixture` that tests request by naming it as a parameter; code after `yield` is teardown. Shared fixtures go in **`conftest.py`**, and pytest ships handy built-ins such as **`tmp_path`** (a fresh temporary folder) and **`monkeypatch`** (temporarily set environment variables or attributes). Tests must be fast and **deterministic**, so you replace the outside world, such as network calls, clocks and paid APIs, with **mocks** like `unittest.mock.patch`. pytest exits with **code 0** when everything passes and non-zero otherwise, which is how CI pipelines decide whether to merge or deploy.
</En>
<Ur>
**Automated test** chhota function hai jo aap ke code ka hissa maloom inputs ke saath chala kar natija check karta hai. Har tabdeeli ke baad poora suite chalayen to seconds me pata chal jata hai ke kuch toota ya nahi, aur yahi refactoring, upgrades aur tez deploys ko mehfooz banata hai. **pytest** Python ka mayari test runner hai. Ye `test_*.py` naam ki files aur `test_*` naam ke functions dhoondta hai, aur aap nataij saade **`assert`** se check karte hain; nakam hone par pytest dono taraf ki values dikhata hai. **`@pytest.mark.parametrize`** ek test ko inputs ki table par chalata, **`pytest.raises`** check karta ke ghalat input sahi error uthaye, aur **`pytest.approx`** floats ka muqabla karta hai. **Fixtures** woh dete hain jo tests ko chahiye: `@pytest.fixture` wala function jise tests parameter ke taur par naam le kar maangte hain; `yield` ke baad ka code teardown hai. Mushtarka fixtures **`conftest.py`** me jate, aur pytest **`tmp_path`** (taaza temporary folder) aur **`monkeypatch`** (environment variables ya attributes waqti taur par set karna) jaise kaam ke built-ins deta hai. Tests tez aur **deterministic** hone chahiye, isliye aap bahar ki duniya, jaise network calls, ghariyan aur paid APIs, ko `unittest.mock.patch` jaise **mocks** se badalte hain. Sab paas hone par pytest **code 0** ke saath nikalta warna non-zero, isi se CI pipelines faisla karti hain ke merge ya deploy karein ya nahi.

## Picture it

<Tr>
<En>

Think of a **pre-flight checklist**.

- Before every flight the crew runs the same checks: fuel, flaps, instruments. Each check has an expected value; any mismatch stops the takeoff (a failing test stops the deploy).
- Parametrize is checking every tyre with the same procedure instead of writing a separate procedure for each.
- Fixtures are the ground crew who set up the plane before each check and tidy up afterwards.
- Mocks are a flight simulator: you can test the engine-failure procedure without actually breaking an engine or flying anywhere.

</En>
<Ur>

**Udaan se pehle ki checklist** socheyn.

- Har flight se pehle crew wahi checks karta hai: fuel, flaps, instruments. Har check ki tawaqqo wali value hai; koi farq takeoff rok deta hai (nakam test deploy rokta hai).
- Parametrize har tyre ko ek hi tareeqe se check karna hai, har ek ke liye alag tareeqa likhne ke bajaye.
- Fixtures ground crew hain jo har check se pehle jahaz tayyar karte aur baad me samet'te hain.
- Mocks flight simulator hain: aap asal engine tore ya kahin ure baghair engine fail hone ka tareeqa test kar sakte hain.

</Ur>
</Tr>

<Walkthrough>

<Step title="assert, parametrize, raises, approx, failures and -k">

<Tr>
<En>
We create a small `shop` project: `pricing.py` with a discount and a shipping function, a `pyproject.toml` that tells pytest where tests are and lets them import the project, and `tests/test_pricing.py` with plain asserts, parametrized tables, an exception test, a float comparison and one deliberately wrong test. We run pytest with `uvx` (pinned to pytest 8.3.5 and Python 3.13), print the exit code, then run only the shipping tests. The cache plugin is disabled only to keep the demo folder clean.
</En>
<Ur>
Hum chhota `shop` project banate hain: discount aur shipping function wali `pricing.py`, aisi `pyproject.toml` jo pytest ko batati ke tests kahan hain aur unhe project import karne deti, aur saade asserts, parametrized tables, exception test, float muqable aur ek jaan boojh kar ghalat test wali `tests/test_pricing.py`. Hum `uvx` se pytest chalate (pytest 8.3.5 aur Python 3.13 par pin), exit code print karte, phir sirf shipping tests chalate hain. Cache plugin sirf demo folder saaf rakhne ke liye band hai.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z     # demo only: fixed versions
mkdir -p shop/tests && cd shop
cat > pyproject.toml <<'EOF'
[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]          # so tests can import pricing.py from the project root
EOF
cat > pricing.py <<'EOF'
from decimal import Decimal

def apply_discount(price, percent):
    if not 0 <= percent <= 100:
        raise ValueError(f"percent must be 0-100, got {percent}")
    return (Decimal(price) * (100 - Decimal(percent)) / 100).quantize(Decimal("0.01"))

def shipping(total, country):
    if country == "US":
        return Decimal("0") if total >= 50 else Decimal("5.99")
    return Decimal("19.99")
EOF
cat > tests/test_pricing.py <<'EOF'
import pytest
from decimal import Decimal
from pricing import apply_discount, shipping

def test_ten_percent_off():
    assert apply_discount("80.00", 10) == Decimal("72.00")

@pytest.mark.parametrize("price, percent, expected", [
    ("100", 0, "100.00"),
    ("100", 100, "0.00"),
    ("19.99", 15, "16.99"),
    ("0.10", 50, "0.05"),
])
def test_discount_table(price, percent, expected):
    assert apply_discount(price, percent) == Decimal(expected)

@pytest.mark.parametrize("bad", [-1, 101])
def test_rejects_invalid_percent(bad):
    with pytest.raises(ValueError, match="0-100"):
        apply_discount("10", bad)

@pytest.mark.parametrize("total, country, fee", [(49.99, "US", "5.99"), (50, "US", "0"), (10, "CA", "19.99")])
def test_shipping(total, country, fee):
    assert shipping(total, country) == Decimal(fee)

def test_float_math_needs_approx():
    assert 0.1 + 0.2 == pytest.approx(0.3)

def test_deliberately_wrong():               # to see how pytest reports a failure
    assert apply_discount("50", 20) == Decimal("45.00")
EOF
uvx -q --python 3.13 pytest@8.3.5 -q -p no:cacheprovider 2>&1 | sed -E 's/ in [0-9.]+s/ in <time>/'
echo "exit code: ${PIPESTATUS[0]}"
echo "--- run only shipping tests, verbose:"
uvx -q --python 3.13 pytest@8.3.5 -p no:cacheprovider -k shipping -v 2>&1 | grep -o "test_shipping.* PASSED"
```

<Step title="Fixtures, conftest.py, tmp_path, monkeypatch, mocks and skip">

<Tr>
<En>
We add `orders.py`, which exports orders from a database to a CSV file named after an environment variable and converts totals using a live exchange-rate API. A `db` fixture in `conftest.py` creates an in-memory SQLite database with test data and closes it afterwards. The tests use `tmp_path` and `monkeypatch` for the export, `unittest.mock.patch` to replace the network call with a fake response and with a timeout, and `skip` for a test that needs real credentials. Then we run the whole suite once more.
</En>
<Ur>
Hum `orders.py` jorte hain, jo database se orders aisi CSV file me export karti jis ka naam environment variable par hai aur live exchange-rate API se totals badalti hai. `conftest.py` me `db` fixture test data ke saath in-memory SQLite database banata aur baad me band karta hai. Tests export ke liye `tmp_path` aur `monkeypatch`, network call ko jaali jawab aur timeout se badalne ke liye `unittest.mock.patch`, aur asal credentials maangne wale test ke liye `skip` istemal karte hain. Phir hum poora suite ek dafa aur chalate hain.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z
cd shop
cat > orders.py <<'EOF'
import json, os, sqlite3, urllib.request

def fetch_json(url):                                   # real network call
    with urllib.request.urlopen(url, timeout=5) as r:
        return json.load(r)

def eur_total(usd_total):
    rate = fetch_json("https://api.example.com/rates")["EUR"]
    return round(usd_total * rate, 2)

def export_orders(db, folder):
    rows = db.execute("SELECT id, total FROM orders ORDER BY id").fetchall()
    path = os.path.join(folder, f"orders-{os.environ.get('APP_ENV', 'dev')}.csv")
    with open(path, "w", encoding="utf-8") as f:
        f.write("id,total\n" + "".join(f"{i},{t}\n" for i, t in rows))
    return path
EOF
cat > tests/conftest.py <<'EOF'
import sqlite3, pytest

@pytest.fixture
def db():                                   # shared by every test file in tests/
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE orders (id INTEGER, total REAL)")
    conn.executemany("INSERT INTO orders VALUES (?, ?)", [(2, 15.5), (1, 99.0)])
    yield conn                              # the test runs here
    conn.close()                            # teardown, even if the test fails
EOF
cat > tests/test_orders.py <<'EOF'
from unittest.mock import patch
import pytest
import orders

def test_export_writes_sorted_csv(db, tmp_path, monkeypatch):
    monkeypatch.setenv("APP_ENV", "test")          # restored after the test
    path = orders.export_orders(db, tmp_path)      # tmp_path: a fresh empty folder
    assert path.endswith("orders-test.csv")
    assert open(path).read() == "id,total\n1,99.0\n2,15.5\n"

def test_eur_total_without_network():
    with patch("orders.fetch_json", return_value={"EUR": 0.5}) as fake:
        assert orders.eur_total(80) == 40.0
    fake.assert_called_once_with("https://api.example.com/rates")

def test_eur_total_api_down():
    with patch("orders.fetch_json", side_effect=TimeoutError("api timeout")):
        with pytest.raises(TimeoutError):
            orders.eur_total(80)

@pytest.mark.skip(reason="needs real credentials; runs in the nightly job")
def test_real_api():
    orders.fetch_json("https://api.example.com/rates")
EOF
uvx -q --python 3.13 pytest@8.3.5 -p no:cacheprovider -v tests/test_orders.py 2>&1 | grep -oE "test_[a-z_]+ (PASSED|FAILED|SKIPPED)"
uvx -q --python 3.13 pytest@8.3.5 -p no:cacheprovider -q 2>&1 | tail -1 | sed -E 's/ in [0-9.]+s/ in <time>/'
```

test_eur_total_api_down PASSED
test_real_api SKIPPED

<Happened>
<Tr>
<En>

- `test_export_writes_sorted_csv` asked for `db`, `tmp_path` and `monkeypatch` simply by **naming them as parameters**; pytest created each one fresh for this test. The `db` fixture lives in `conftest.py`, so every test file in `tests/` can use it without importing anything, and the code after `yield` closed the connection afterwards.
- `tmp_path` gave an empty folder that's unique to the test, so tests never write into your project or interfere with each other. `monkeypatch.setenv` set `APP_ENV=test` and undid it when the test ended.
- `patch("orders.fetch_json", return_value=...)` replaced the network function **where it's used** (in the `orders` module) for the duration of the `with` block. The test ran offline, instantly and deterministically, and `assert_called_once_with` verified the URL. `side_effect=TimeoutError(...)` simulated the API being down, so the error path is tested too.
- The real-API test was **SKIPPED** with a reason. Tests that need credentials or the network belong in a separate, explicitly marked group.
- The final run reported **14 passed, 1 skipped, 1 failed**: the deliberately wrong test from step 1 still fails, so the suite's exit code stays non-zero until it's fixed.

</En>
<Ur>

- `test_export_writes_sorted_csv` ne `db`, `tmp_path` aur `monkeypatch` bas **parameters ke taur par naam le kar** maange; pytest ne har ek is test ke liye naya banaya. `db` fixture `conftest.py` me hai, isliye `tests/` ki har test file kuch import kiye baghair ise istemal kar sakti hai, aur `yield` ke baad ke code ne baad me connection band kiya.
- `tmp_path` ne test ke liye makhsoos khaali folder diya, isliye tests kabhi aap ke project me nahi likhte ya ek doosre me dakhal nahi dete. `monkeypatch.setenv` ne `APP_ENV=test` set kiya aur test khatam hone par wapas kiya.
- `patch("orders.fetch_json", return_value=...)` ne network function ko **jahan istemal hota hai** (`orders` module me) `with` block ki muddat ke liye badla. Test offline, foran aur deterministic tareeqe se chala, aur `assert_called_once_with` ne URL tasdeeq kiya. `side_effect=TimeoutError(...)` ne API band hone ki naqal ki, isliye error wala raasta bhi test hua.
- Asal API wala test wajah ke saath **SKIPPED** hua. Credentials ya network maangne wale tests alag, wazeh nishan wale group me hone chahiye.
- Aakhri run ne **14 passed, 1 skipped, 1 failed** bataya: qadam 1 ka jaan boojh kar ghalat test ab bhi nakam hai, isliye theek hone tak suite ka exit code non-zero rehta hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Tests that depend on the outside world">

```text
def test_eur_total():
    assert orders.eur_total(80) == 73.6      # calls the real API: slow, flaky, rate changes daily

def test_report():
    export_orders(prod_db, "/home/jane/reports")   # touches real data and folders
```

</Bad>
<Good title="Isolated, deterministic tests">

```text
def test_eur_total():
    with patch("orders.fetch_json", return_value={"EUR": 0.5}):
        assert orders.eur_total(80) == 40.0

def test_report(db, tmp_path):
    export_orders(db, tmp_path)
```

</Good>
</Compare>

<Compare>
<Bad title="Copy-pasted tests and weak assertions">

```text
def test_discount_1(): assert apply_discount("100", 10)
def test_discount_2(): assert apply_discount("50", 20)     # only checks "truthy"
def test_bad():
    try: apply_discount("10", 150)
    except: pass                                            # passes even with no error
```

</Bad>
<Good title="Parametrize and precise checks">

```text
@pytest.mark.parametrize("price, pct, expected", [("100", 10, "90.00"), ("50", 20, "40.00")])
def test_discount(price, pct, expected):
    assert apply_discount(price, pct) == Decimal(expected)

def test_bad():
    with pytest.raises(ValueError, match="0-100"):
        apply_discount("10", 150)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Patching in the wrong place**: patch the name where it's looked up (`orders.fetch_json`), not where it's defined, if the module imported it with `from ... import`.
- **Tests that depend on each other or on order**: each test must set up its own state; fixtures help.
- **Testing implementation details** instead of behaviour, so every refactor breaks tests.
- **Ignoring flaky tests**: a test that fails randomly destroys trust; fix the cause (time, ordering, network).
- **Chasing 100% coverage** instead of testing the logic that matters: edge cases, errors and security checks.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ghalat jagah patch karna**: naam wahan patch karein jahan dhoonda jata hai (`orders.fetch_json`), jahan define hua wahan nahi, agar module ne use `from ... import` se import kiya ho.
- **Ek doosre ya tarteeb par mabni tests**: har test apni state khud tayyar kare; fixtures madad karte hain.
- **Rawaiye ke bajaye andaruni tafseelat test karna**, isliye har refactor tests tor deta hai.
- **Kabhi kabhi nakam hone wale tests nazar andaz karna**: ittefaqan nakam hone wala test bharosa khatam karta; wajah (waqt, tarteeb, network) theek karein.
- **Ahem logic test karne ke bajaye 100% coverage ke peeche bhagna**: edge cases, errors aur security checks.

</Ur>
</Tr>

<Tr>
<En>
Write `parse_size(text)` that turns strings like `"512B"`, `"10KB"`, `" 2 mb "` and `"1GB"` into bytes (1 KB = 1024 B) and raises `ValueError` for input like `"10"`, `"12XB"`, `"abcKB"` and `"-5MB"`. Write a test file with one parametrized test for valid inputs and one for invalid inputs, run pytest on it from Python with `subprocess`, and print the summary line (without the timing) and the exit code.
</En>
<Ur>
`parse_size(text)` likhein jo `"512B"`, `"10KB"`, `" 2 mb "` aur `"1GB"` jaisi strings ko bytes me badle (1 KB = 1024 B) aur `"10"`, `"12XB"`, `"abcKB"` aur `"-5MB"` jaise input par `ValueError` uthaye. Durust inputs ke liye ek aur ghalat inputs ke liye ek parametrized test wali test file likhein, `subprocess` ke saath Python se us par pytest chalayen, aur khulase ki line (timing ke baghair) aur exit code print karein.

<Solution>

<Tr>
<En>

```text
import re, subprocess, sys, textwrap
from pathlib import Path

Path("sizes.py").write_text(textwrap.dedent('''
    UNITS = {"B": 1, "KB": 1024, "MB": 1024 ** 2, "GB": 1024 ** 3}

    def parse_size(text):
        text = text.strip().upper()
        for unit in sorted(UNITS, key=len, reverse=True):
            if text.endswith(unit):
                number = text[: -len(unit)].strip()
                if not number.isdigit():
                    raise ValueError(f"bad size: {text!r}")
                return int(number) * UNITS[unit]
        raise ValueError(f"unknown unit: {text!r}")
'''))
Path("test_sizes.py").write_text(textwrap.dedent('''
    import pytest
    from sizes import parse_size

    @pytest.mark.parametrize("text, expected", [
        ("512B", 512), ("10KB", 10240), (" 2 mb ", 2097152), ("1GB", 1073741824),
    ])
    def test_valid(text, expected):
        assert parse_size(text) == expected

    @pytest.mark.parametrize("text", ["10", "12XB", "abcKB", "-5MB"])
    def test_invalid(text):
        with pytest.raises(ValueError):
            parse_size(text)
'''))
result = subprocess.run([sys.executable, "-m", "pytest", "-q", "-p", "no:cacheprovider", "test_sizes.py"],
                        capture_output=True, text=True)
print(re.sub(r" in [\d.]+s", "", result.stdout.strip().splitlines()[-1]), "| exit code:", result.returncode)
# 8 passed | exit code: 0
```

Path("backup.py").write_text(textwrap.dedent('''
    import os
    from datetime import datetime, timezone

    def backup_path(folder, now=None):

        assert path.endswith("prod-db-20261124-0230.sql.gz")

<DeepDive title="More about pytest">

**Fixture scopes.** `@pytest.fixture(scope="session")` creates expensive things (a Docker database, a browser) once per run instead of once per test.

**Plugins.** `pytest-cov` (coverage), `pytest-xdist` (`-n auto` runs tests in parallel), `pytest-asyncio` (async tests), `pytest-mock` (a `mocker` fixture), `hypothesis` (property-based tests).

**Markers.** Custom markers like `@pytest.mark.integration` plus `-m "not integration"` split fast and slow suites.

**Testcontainers.** Integration tests can start real Postgres, Redis or LocalStack containers for the duration of a test session.

**Snapshot and golden files.** Compare generated output (reports, configs) against stored expected files.

</DeepDive>

<DeepDive title="Real world: the discount that went negative">

A promotion allowed stacking two discount codes. Nobody had a test for combined discounts above 100%, and a customer found that two codes made the total negative, which the payment system treated as a refund. Several thousand dollars were "refunded" before monitoring caught it.

The fixes:

1. A regression test reproducing the exact combination, written before the fix.
2. Parametrized tests for boundaries (0%, 100%, stacked codes, rounding) and a validation that totals can never be negative.
3. Tests run in CI on every pull request, with the payment service's tests required to pass before deploy.

</DeepDive>

<DeepDive title="Security lens">

- **Test the negative paths**: invalid input, missing permissions, expired tokens and oversized payloads must fail safely; write tests that prove it.
- **Regression-test every security fix** so the vulnerability can't quietly return.
- **No real secrets in tests**: use fake values and mocks; never point tests at production.
- **Isolate test data**: `tmp_path` and per-test databases prevent tests from touching real files.
- **Run security tools alongside tests in CI** (linters like bandit, dependency audits).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a fixture in pytest?">
A function decorated with pytest.fixture that provides a resource or setup to tests that request it by parameter name; code after a yield runs as teardown, and scope controls how often it's created.
</QA>

<QA q="How do you test that a function raises an exception?">
Use with pytest.raises(ExpectedError, match=pattern): around the call; the test fails if the exception isn't raised or the message doesn't match.
</QA>

<QA q="What is the difference between unit and integration tests?">
Unit tests check a small piece of code in isolation with dependencies mocked and run very fast; integration tests check that components work together with real dependencies such as databases or services.
</QA>

<QA q="Where should you patch with unittest.mock?">
Where the name is looked up at runtime, usually the module that uses it, such as orders.fetch_json, rather than where it was originally defined.
</QA>

<QA q="How do tests fit into CI/CD?">
The pipeline runs the test suite on every push or pull request; a non-zero exit code fails the build, blocking merges and deployments until the tests pass.
</QA>

</DeepDive>
