<BigIdea>
<Tr>
<En>
In Python, **functions are objects**: you can store them in variables, pass them to other functions and return them from functions. A **decorator** uses this. It's a function that takes a function and returns a **new function** that usually calls the original and adds something before or after: logging, timing, retrying, caching, checking permissions. Writing **`@announce`** above `def multiply(...)` is just shorthand for `multiply = announce(multiply)`. Inside, the decorator defines a **wrapper** that accepts **`*args, **kwargs`** so it works with any signature, calls the original function, and returns its result. Because the wrapper replaces the original, it would hide the function's name and docstring, so you decorate the wrapper with **`functools.wraps(func)`**. Several decorators can be **stacked**; the one closest to `def` is applied first. When a decorator needs settings, like `@retry(times=3)`, you write a **decorator factory**: a function that takes the settings and returns the actual decorator, which is why there are three nested functions. The standard library ships useful ones such as `functools.lru_cache`, `functools.cache`, `property`, `staticmethod` and `dataclasses.dataclass`, and frameworks use decorators for routes, fixtures, CLI commands and tasks.
</En>
<Ur>
Python me **functions objects hain**: aap unhe variables me rakh, doosre functions ko de aur functions se lauta sakte hain. **Decorator** isi ko istemal karta hai. Ye aisa function hai jo function le kar **naya function** lautata hai jo aam taur par asal ko bulata aur pehle ya baad me kuch jorta hai: logging, timing, retry, caching, permissions check. `def multiply(...)` ke upar **`@announce`** likhna bas `multiply = announce(multiply)` ka mukhtasar hai. Andar decorator ek **wrapper** banata hai jo **`*args, **kwargs`** leta hai taa ke har signature ke saath chale, asal function bulata, aur us ka natija lautata hai. Kyunke wrapper asal ki jagah le leta hai, ye function ka naam aur docstring chhupa deta, isliye aap wrapper par **`functools.wraps(func)`** lagate hain. Kai decorators **upar neeche** lag sakte hain; `def` ke sab se qareeb wala pehle lagta hai. Jab decorator ko settings chahiye hon, jaise `@retry(times=3)`, to aap **decorator factory** likhte hain: aisa function jo settings le kar asal decorator lautaye, isi liye teen functions ek doosre ke andar hote hain. Standard library `functools.lru_cache`, `functools.cache`, `property`, `staticmethod` aur `dataclasses.dataclass` jaise kaam ke decorators deti hai, aur frameworks routes, fixtures, CLI commands aur tasks ke liye decorators istemal karte hain.
</Ur>

<What>
<Tr>

```text
def decorator(func):                     # takes a function
    @functools.wraps(func)               # keep name, docstring, __wrapped__
    def wrapper(*args, **kwargs):        # accepts any arguments
        # before
        result = func(*args, **kwargs)   # call the original
        # after
        return result
    return wrapper                       # returns the new function

@decorator          # same as: target = decorator(target)
def target(): ...

def factory(setting):                    # decorator WITH arguments
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs): ...
        return wrapper
    return decorator

@factory(setting=3) # same as: target = factory(setting=3)(target)
def target(): ...
```

## Picture it

<Tr>
<En>

Think of **gift wrapping**.

- The function is the gift. A decorator puts it in a wrapper: the gift inside is unchanged, but now there's a card on the outside (logging), a timer (timing), or a lock (a permission check).
- Whoever receives it handles the wrapped box exactly as they'd handle the gift: same arguments in, same result out.
- `functools.wraps` copies the label from the gift onto the wrapping paper, so you still know what's inside.
- Stacked decorators are layers of paper: the innermost layer goes on first, and when it's opened, the outermost layer is opened first.

</En>
<Ur>

**Tohfa lapetna** socheyn.

- Function tohfa hai. Decorator use wrapper me rakhta hai: andar ka tohfa waisa hi rehta, magar ab bahar card (logging), timer (timing), ya taala (permission check) hai.
- Jo bhi use leta hai, lapete dabbe ko bilkul tohfe ki tarah istemal karta hai: wahi arguments andar, wahi natija bahar.
- `functools.wraps` tohfe ka label lapetne wale kaghaz par copy karta hai, taa ke aap ab bhi janein ke andar kya hai.
- Upar neeche ke decorators kaghaz ki tahen hain: sab se andar wali tah pehle lagti, aur kholte waqt sab se bahar wali pehle khulti hai.

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Functions as objects, writing a decorator, wraps and stacking">

<Tr>
<En>
`deco_basics.py` passes a function to another function, writes an `announce` decorator and applies it first by hand and then with `@`, shows that a plain wrapper hides the decorated function's name and docstring, fixes that with `functools.wraps`, and stacks two decorators to see which one is applied first.
</En>
<Ur>
`deco_basics.py` ek function doosre function ko deti, `announce` decorator likh kar pehle haath se aur phir `@` se lagati, dikhati hai ke saada wrapper decorate hue function ka naam aur docstring chhupa deta hai, `functools.wraps` se ise theek karti, aur do decorators upar neeche laga kar dekhti hai ke kaun pehle lagta hai.
</Ur>
</Tr>

```bash
cat > deco_basics.py <<'EOF'
import functools

# Functions are objects: they can be passed around and returned
def shout(text):
    return text.upper() + "!"

def apply(func, value):
    return func(value)

print(apply(shout, "deploy done"), "| name:", shout.__name__)

# A decorator is a function that takes a function and returns a new one
def announce(func):
    def wrapper(*args, **kwargs):
        print(f"-> calling {func.__name__}{args}")
        result = func(*args, **kwargs)
        print(f"<- {func.__name__} returned {result!r}")
        return result
    return wrapper

def add(a, b):
    return a + b

add_logged = announce(add)            # decorating by hand
add_logged(2, 3)

@announce                             # the same thing with @ syntax
def multiply(a, b):
    """Multiply two numbers."""
    return a * b

multiply(4, 5)
print("name:", multiply.__name__, "| doc:", multiply.__doc__)   # metadata lost!

# functools.wraps copies the original's name, docstring and more
def announce_fixed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@announce_fixed
def divide(a, b):
    """Divide a by b."""
    return a / b

print("name:", divide.__name__, "| doc:", divide.__doc__, "| original:", divide.__wrapped__.__name__)

# Stacking: the decorator nearest the function is applied first
def bold(f):
    @functools.wraps(f)
    def w(): return f"<b>{f()}</b>"
    return w
def italic(f):
    @functools.wraps(f)
    def w(): return f"<i>{f()}</i>"
    return w

@bold
@italic
def label():
    return "status"
print(label())
EOF
python3 deco_basics.py
```

```text output
DEPLOY DONE! | name: shout
-> calling add(2, 3)
<- add returned 5
-> calling multiply(4, 5)
<- multiply returned 20
name: wrapper | doc: None
name: divide | doc: Divide a by b. | original: divide
<b><i>status</i></b>
```

<Happened>
<Tr>
<En>

- `apply(shout, "deploy done")` worked because `shout` is just an object; a function name without parentheses refers to the function, with parentheses calls it.
- `announce(add)` returned `wrapper`, which printed before and after calling `add`. Writing **`@announce`** above `multiply` did exactly the same at definition time; there's no extra magic.
- The wrapper took `*args, **kwargs` and passed them through, so it works for any function, and it **returned the result**: forget that `return` and every decorated function returns `None`.
- Without `wraps`, `multiply.__name__` became **wrapper** and its docstring **None**, which breaks logs, debugging, documentation tools and frameworks that read names. With `functools.wraps`, `divide` kept its name and docstring, and `__wrapped__` points to the original (handy in tests).
- `@bold` over `@italic` produced **`<b><i>status</i></b>`**: `italic` wrapped `label` first, then `bold` wrapped the result, so `bold` runs outermost.

</En>
<Ur>

- `apply(shout, "deploy done")` chala kyunke `shout` bas ek object hai; brackets ke baghair function ka naam function ki taraf ishara karta, brackets ke saath use bulata hai.
- `announce(add)` ne `wrapper` lautaya, jis ne `add` bulane se pehle aur baad print kiya. `multiply` ke upar **`@announce`** likhne ne define karte waqt bilkul yahi kiya; koi zayed jaadu nahi.
- Wrapper ne `*args, **kwargs` le kar aage bheje, isliye ye har function ke saath chalta hai, aur us ne **natija lautaya**: woh `return` bhoolein to har decorate hua function `None` lautayega.
- `wraps` ke baghair `multiply.__name__` **wrapper** aur docstring **None** ban gaya, jo logs, debugging, documentation tools aur naam parhne wale frameworks tor deta hai. `functools.wraps` ke saath `divide` ne apna naam aur docstring rakha, aur `__wrapped__` asal ki taraf ishara karta hai (tests me kaam ka).
- `@italic` ke upar `@bold` ne **`<b><i>status</i></b>`** banaya: `italic` ne pehle `label` lapeta, phir `bold` ne natija lapeta, isliye `bold` sab se bahar chalta hai.

</Ur>

<Step title="Real decorators: timing, retry with arguments, caching and access control">

<Tr>
<En>
`deco_real.py` builds four decorators you'll see in real code: `@timed` measures a call using `try/finally`, `@retry(...)` is a factory that retries only chosen exceptions with exponential backoff, `functools.lru_cache` memoizes a recursive Fibonacci function, and `@require_role(...)` blocks a call unless the current user has a role.
</En>
<Ur>
`deco_real.py` chaar decorators banati jo aap asal code me dekhenge: `@timed` `try/finally` se call naapta, `@retry(...)` aisi factory hai jo exponential backoff ke saath sirf chuni exceptions retry karti, `functools.lru_cache` recursive Fibonacci function ko memoize karta, aur `@require_role(...)` call rokta hai jab tak mojooda user ke paas role na ho.
</Ur>
</Tr>

```bash
cat > deco_real.py <<'EOF'
import functools, time

# 1. Timing
def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            ms = (time.perf_counter() - start) * 1000
            print(f"[timed] {func.__name__} took {'under' if ms < 200 else 'over'} 200 ms")
    return wrapper

@timed
def build_report():
    time.sleep(0.05)
    return "report.pdf"
print(build_report())

# 2. A decorator with arguments: a factory that returns a decorator
def retry(times=3, exceptions=(Exception,), delay=0.0):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    print(f"[retry] {func.__name__} attempt {attempt}/{times} failed: {e}")
                    if attempt == times:
                        raise
                    time.sleep(delay * 2 ** (attempt - 1))       # exponential backoff
        return wrapper
    return decorator

calls = {"n": 0}
@retry(times=3, exceptions=(ConnectionError,))
def fetch_rates():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ConnectionError("upstream timeout")
    return {"USD": 1.0, "EUR": 0.92}
print(fetch_rates())

@retry(times=2, exceptions=(ConnectionError,))
def bad_input():
    raise ValueError("not retried: wrong exception type")
try:
    bad_input()
except ValueError as e:
    print("ValueError:", e)

# 3. Caching with the standard library
@functools.lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)
print("fib(80) =", fib(80), "|", fib.cache_info())

# 4. Access control
current_user = {"name": "jane", "roles": {"viewer"}}
def require_role(role):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            if role not in current_user["roles"]:
                raise PermissionError(f"{current_user['name']} needs role {role!r} for {func.__name__}")
            return func(*args, **kwargs)
        return wrapper
    return decorator

@require_role("admin")
def delete_user(user_id):
    return f"deleted {user_id}"
try:
    delete_user(42)
except PermissionError as e:
    print("PermissionError:", e)
current_user["roles"].add("admin")
print(delete_user(42))
EOF
python3 deco_real.py
```

```text output
[timed] build_report took under 200 ms
report.pdf
[retry] fetch_rates attempt 1/3 failed: upstream timeout
[retry] fetch_rates attempt 2/3 failed: upstream timeout
{'USD': 1.0, 'EUR': 0.92}
ValueError: not retried: wrong exception type
fib(80) = 23416728348467685 | CacheInfo(hits=78, misses=81, maxsize=None, currsize=81)
PermissionError: jane needs role 'admin' for delete_user
deleted 42
```

<Happened>
<Tr>
<En>

- `@timed` used `try/finally`, so the timing is reported even when the function raises. (We print "under/over 200 ms" so the output is stable; real code logs the actual milliseconds.)
- `@retry(times=3, exceptions=(ConnectionError,))` has **three layers**: `retry(...)` received the settings and returned `decorator`, which wrapped the function. `fetch_rates` failed twice with ConnectionError and succeeded on the third try. The backoff (`delay * 2 ** (attempt - 1)`) is 0 here to keep the demo fast.
- `bad_input` raised **ValueError**, which isn't in the retry list, so it failed immediately. Only retry errors that might succeed next time (timeouts, 503s), never bugs or bad input, and only for operations that are safe to repeat.
- `lru_cache` turned an exponential recursive Fibonacci into **81 computations** with 78 cache hits; `fib(80)` would otherwise take ages. Cache only **pure** functions whose arguments are hashable, and set `maxsize` for unbounded inputs.
- `@require_role("admin")` raised **PermissionError** for jane, then allowed the call after the role was added. Frameworks do the same with decorators like `@login_required`; the check runs before any of the function's code.

</En>
<Ur>

- `@timed` ne `try/finally` istemal kiya, isliye function error uthaye tab bhi timing report hoti hai. (Output mustaqil rakhne ke liye hum "under/over 200 ms" print karte; asal code asal milliseconds log karta hai.)
- `@retry(times=3, exceptions=(ConnectionError,))` ki **teen tahen** hain: `retry(...)` ne settings le kar `decorator` lautaya, jis ne function lapeta. `fetch_rates` do dafa ConnectionError se nakam aur teesri koshish par kamyab hua. Demo tez rakhne ke liye backoff (`delay * 2 ** (attempt - 1)`) yahan 0 hai.
- `bad_input` ne **ValueError** uthaya, jo retry list me nahi, isliye foran nakam hua. Sirf woh errors retry karein jo agli dafa kamyab ho sakte (timeouts, 503s), bugs ya ghalat input kabhi nahi, aur sirf aise kaam jo dohrane me mehfooz hon.
- `lru_cache` ne exponential recursive Fibonacci ko 78 cache hits ke saath **81 hisaabon** me badal diya; warna `fib(80)` me zamane lagte. Sirf **khaalis** functions cache karein jin ke arguments hashable hon, aur be-had inputs ke liye `maxsize` rakhein.
- `@require_role("admin")` ne jane ke liye **PermissionError** uthaya, phir role jurne ke baad call ki ijazat di. Frameworks `@login_required` jaise decorators se yahi karte hain; check function ke kisi bhi code se pehle chalta hai.

</Ur>

## Common mistakes

<Compare>
<Bad title="Wrapper that loses the result and metadata">

```text
def logged(func):
    def wrapper(*args):                    # no **kwargs: keyword calls break
        print("calling", func.__name__)
        func(*args)                        # result thrown away -> returns None
    return wrapper
```

</Bad>
<Good title="Complete wrapper">

```text
def logged(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("calling", func.__name__)
        return func(*args, **kwargs)
    return wrapper
```

</Good>
</Compare>

<Compare>
<Bad title="Forgetting the factory call, or retrying everything">

```text
@retry                                     # retry is a factory: this passes the function as `times`
def charge_card(order): ...

@retry(times=5, exceptions=(Exception,))   # retries bugs and double-charges customers
def charge_card(order): ...
```

</Bad>
<Good title="Call the factory, retry only safe, transient errors">

```text
@retry(times=3, exceptions=(TimeoutError, ConnectionError), delay=0.5)
def fetch_exchange_rates(): ...            # read-only, safe to repeat
# payments: use idempotency keys before ever retrying
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Caching functions with side effects or changing data** (`lru_cache` on "get current balance"): stale results.
- **`lru_cache` on methods** keeps `self` alive forever; prefer caching module-level functions or `functools.cached_property`.
- **Doing work at decoration time by accident**: code in the decorator body (outside `wrapper`) runs once at import.
- **Hiding important behaviour in decorators** so readers can't tell what a function really does; name them clearly.
- **Decorating `async def` functions with a sync wrapper**: the wrapper must be `async def` and `await` the call.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Side effects ya badalte data wale functions cache karna** ("mojooda balance lao" par `lru_cache`): purane nataij.
- **Methods par `lru_cache`** `self` ko hamesha zinda rakhta hai; module level functions ya `functools.cached_property` cache karna behtar hai.
- **Ghalti se decoration ke waqt kaam karna**: decorator ki body (`wrapper` se bahar) ka code import par ek dafa chalta hai.
- **Ahem rawaiya decorators me chhupana** taa ke parhne wala na jaan sake function asal me kya karta; unke naam wazeh rakhein.
- **`async def` functions par sync wrapper lagana**: wrapper `async def` ho aur call ko `await` kare.

</Ur>
</Tr>

<Tr>
<En>

```text
import functools
from collections import deque

def rate_limit(max_calls, per_seconds, clock):
    def decorator(func):
        recent = deque()
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            now = clock()
            while recent and now - recent[0] >= per_seconds:
                recent.popleft()
            if len(recent) >= max_calls:
                raise RuntimeError("rate limit exceeded")
            recent.append(now)
            return func(*args, **kwargs)
        return wrapper
    return decorator

fake_now = [0.0]
@rate_limit(max_calls=3, per_seconds=1.0, clock=lambda: fake_now[0])
def send_sms(to):
    return f"sent to {to}"

for t, to in [(0.0, "a"), (0.0, "b"), (0.0, "c"), (0.5, "d"), (1.1, "e")]:
    fake_now[0] = t
    try:
        print(f"t={t}: {send_sms(to)}")
    except RuntimeError as e:
        print(f"t={t}: {e}")

# t=0.0: sent to a
# t=0.0: sent to b
# t=0.0: sent to c
# t=0.5: rate limit exceeded
# t=1.1: sent to e
```

<DeepDive title="More about decorators">

**Class decorators.** A decorator can take a class and return it modified, which is how `@dataclass` adds `__init__` and `__repr__`.

**Classes as decorators.** An object with `__call__` can be a decorator and keep state in attributes.

**Typing decorators.** `typing.ParamSpec` and `TypeVar` let type checkers see the decorated function's real signature.

**Registration decorators.** Some decorators just record the function in a registry and return it unchanged, like routes in a web framework.

**Libraries.** `tenacity` provides production retry decorators (backoff, jitter, stop conditions); `cachetools` adds TTL caches.

</DeepDive>

<DeepDive title="Real world: the retry storm">

A service wrapped every call to its database in a retry decorator: 5 attempts, no delay, retrying on any exception. During a brief database slowdown, every request retried five times instantly, multiplying load by five, which turned a slowdown into a full outage that lasted until traffic was cut.

The fixes:

1. Retry only timeouts and connection errors, with exponential backoff plus random jitter.
2. A total retry budget per request and a circuit breaker that stops calling a failing dependency for a while.
3. Retries only for idempotent operations.

</DeepDive>

<DeepDive title="Security lens">

- **Auth decorators must fail closed**: if the user or role can't be determined, deny.
- **Don't log secrets in logging decorators**: arguments may include passwords or tokens; redact or log only names.
- **Caching per user**: a cache keyed only on arguments can leak one user's data to another; include the user in the key or don't cache.
- **Retries and idempotency**: retrying non-idempotent actions (payments, emails) causes duplicates; use idempotency keys.
- **Order matters**: an auth decorator must wrap outside a caching one, or cached results can bypass the check.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a decorator in Python?">
A callable that takes a function (or class) and returns a replacement, usually a wrapper that adds behaviour before or after calling the original; the @ syntax applies it at definition time.
</QA>

<QA q="Why should a wrapper use *args and **kwargs?">
So it can accept and forward any combination of positional and keyword arguments, making the decorator work with functions of any signature.
</QA>

<QA q="What does functools.wraps do?">
It copies the wrapped function's name, docstring, module and other attributes onto the wrapper and sets `__wrapped__`, so introspection, logging and tools see the original function.
</QA>

<QA q="How do you write a decorator that takes arguments?">
Write a factory function that accepts the arguments and returns a decorator, which in turn returns the wrapper, giving three nested levels.
</QA>

<QA q="When is caching with lru_cache inappropriate?">
For functions with side effects, results that depend on changing external state or time, unhashable arguments, or per-user data that must not be shared, and when unbounded inputs could exhaust memory.
</QA>

</DeepDive>
