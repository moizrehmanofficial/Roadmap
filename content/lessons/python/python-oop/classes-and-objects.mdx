<BigIdea>
<Tr>
<En>
So far your data has lived in dicts and lists, and your logic in separate functions. A **class** puts them together: it's a **blueprint** for a new type that has **data** (attributes) and **behaviour** (methods). Each **object** (or **instance**) made from the class has its own copy of the data: `web = Server("web1", "10.0.0.10")` and `db = Server("db1", "10.0.0.20")` are two separate servers. The special method **`__init__`** runs when an object is created and sets up its attributes. Every method's first parameter, by convention called **`self`**, is the object the method was called on, so `web.open_port(22)` is really `Server.open_port(web, 22)`. Attributes set on `self` are **instance attributes** (one per object); variables defined directly in the class body are **class attributes**, shared by every instance, which is perfect for constants and counters but a trap for mutable data like lists and dicts. `@classmethod` methods receive the class instead of an instance and are often used as **alternative constructors**, while `@staticmethod` is a plain function that simply lives inside the class. Use a class when data and the operations on it naturally belong together and the object has **state** that changes over time.
</En>
<Ur>
Ab tak aap ka data dicts aur lists me raha, aur mantiq alag functions me. **Class** unhe ikattha karti hai: ye nayi type ka **naqsha** hai jis me **data** (attributes) aur **rawaiya** (methods) hota hai. Class se bana har **object** (ya **instance**) data ki apni copy rakhta hai: `web = Server("web1", "10.0.0.10")` aur `db = Server("db1", "10.0.0.20")` do alag servers hain. Khaas method **`__init__`** object banne par chalta aur us ke attributes set karta hai. Har method ka pehla parameter, riwaj se **`self`**, woh object hai jis par method bulaya gaya, isliye `web.open_port(22)` asal me `Server.open_port(web, 22)` hai. `self` par set attributes **instance attributes** hain (har object ka ek); class ke jism me seedhe bane variables **class attributes** hain, har instance me mushtarak, jo constants aur counters ke liye behtareen magar lists aur dicts jaise mutable data ke liye jaal hain. `@classmethod` methods instance ke bajaye class paate hain aur aksar **alternative constructors** ki tarah istemal hote hain, jabke `@staticmethod` saada function hai jo bas class ke andar rehta hai. Class tab lein jab data aur us par kaam qudrati taur par saath hon aur object ki **state** waqt ke saath badalti ho.
</Ur>

## Picture it

<Tr>
<En>

Think of a **form template and the filled-in forms**.

- The class is the blank template: it says every server has a name, an IP and a list of ports, and what you can do with one.
- Each object is a filled-in copy. Writing on web1's form doesn't change db1's.
- `self` is "this form": when you say "open port 22", the method writes on the form you're holding.
- A class attribute is a note printed on the template itself: every copy shows it, and if you scribble on that shared note, everyone sees the scribble.

</En>
<Ur>

**Form ka template aur bhare hue forms** socheyn.

- Class khaali template hai: batata hai ke har server ka naam, IP aur ports ki list hoti hai, aur us ke saath kya kar sakte hain.
- Har object bhari hui copy hai. web1 ke form par likhna db1 ka form nahi badalta.
- `self` "ye form" hai: jab aap kehte "port 22 kholo", method us form par likhta hai jo aap ke haath me hai.
- Class attribute khud template par chhapa note hai: har copy use dikhati, aur agar us mushtarak note par kuch likh dein to sab ko nazar aata hai.

## Learn it step by step

<Walkthrough>

<Step title="Define a class, create objects, call methods">

<Tr>
<En>
`classes.py` defines a `Server` class with `__init__`, two methods and four attributes, creates two servers, changes them through methods and directly, and inspects them with `type`, `isinstance`, `is` and `vars`. It shows that `web.describe()` is the same as `Server.describe(web)`, triggers the error you get when a method forgets `self`, and counts instances with a class attribute.
</En>
<Ur>
`classes.py` `__init__`, do methods aur chaar attributes wali `Server` class define karti, do servers banati, unhe methods aur seedhe badalti, aur `type`, `isinstance`, `is` aur `vars` se dekhti hai. Dikhati hai ke `web.describe()` wahi hai jo `Server.describe(web)`, `self` bhoolne wale method ka error chhedti, aur class attribute se instances ginti hai.
</Ur>
</Tr>

```bash
cat > classes.py <<'EOF'
class Server:
    """A server we manage."""

    def __init__(self, name, ip, ports=None):     # runs when you create an object
        self.name = name                           # instance attributes: each object has its own
        self.ip = ip
        self.ports = list(ports or [])
        self.up = True

    def open_port(self, port):                    # a method: a function that belongs to the class
        if port not in self.ports:
            self.ports.append(port)

    def describe(self):
        state = "up" if self.up else "down"
        return f"{self.name} ({self.ip}) {state}, ports {sorted(self.ports)}"

web = Server("web1", "10.0.0.10", [80, 443])      # create an instance (an object)
db = Server("db1", "10.0.0.20")
web.open_port(22)
db.open_port(5432)
db.up = False                                       # attributes can be read and changed
print(web.describe())
print(db.describe())
print(type(web).__name__, isinstance(db, Server), web is db, web.ports is db.ports)
print(vars(db))                                     # the object's attributes as a dict

# web.describe() is shorthand for Server.describe(web): self IS the object
print(Server.describe(web) == web.describe())

# Forgetting self
class Broken:
    def hello():
        return "hi"
try:
    Broken().hello()
except TypeError as e:
    print("TypeError:", e)

# Class attributes are shared by all instances
class Counter:
    created = 0                                     # class attribute
    def __init__(self):
        Counter.created += 1
a, b, c = Counter(), Counter(), Counter()
print("instances created:", Counter.created, a.created)
EOF
python3 classes.py
```

```text output
web1 (10.0.0.10) up, ports [22, 80, 443]
db1 (10.0.0.20) down, ports [5432]
Server True False False
{'name': 'db1', 'ip': '10.0.0.20', 'ports': [5432], 'up': False}
True
TypeError: Broken.hello() takes 0 positional arguments but 1 was given
instances created: 3 3
```

<Happened>
<Tr>
<En>

- `Server("web1", ...)` called `__init__` with `self` set to the brand-new object, which stored the name, IP, ports and `up` flag on it. `db` got **its own** attributes: changing `db.up` didn't touch `web`, and `web.ports is db.ports` was **False** because `__init__` built a new list each time.
- `web.open_port(22)` added 22 to web's ports only. Methods change the object they're called on.
- `vars(db)` showed an object's attributes are just a **dict** underneath.
- `Server.describe(web) == web.describe()` was **True**: Python passes the object as the first argument automatically. That's all `self` is.
- `Broken().hello()` failed with **takes 0 positional arguments but 1 was given**: Python passed the object, but `hello` had no parameter for it. Every regular method needs `self` first.
- `Counter.created` is a **class attribute**: all three instances incremented the same number and could read it as `a.created`.

</En>
<Ur>

- `Server("web1", ...)` ne `__init__` ko bilkul naye object ke `self` ke saath bulaya, jis ne us par naam, IP, ports aur `up` flag rakha. `db` ko **apne** attributes mile: `db.up` badalne se `web` ko kuch nahi hua, aur `web.ports is db.ports` **False** tha kyunke `__init__` ne har dafa nayi list banayi.
- `web.open_port(22)` ne sirf web ke ports me 22 jora. Methods usi object ko badalte hain jis par bulaye jayen.
- `vars(db)` ne dikhaya ke object ke attributes neeche bas ek **dict** hain.
- `Server.describe(web) == web.describe()` **True** tha: Python object ko khud pehle argument ki tarah deta hai. `self` bas yahi hai.
- `Broken().hello()` **takes 0 positional arguments but 1 was given** se nakam hua: Python ne object diya, magar `hello` ke paas us ke liye parameter nahi tha. Har aam method ko pehle `self` chahiye.
- `Counter.created` **class attribute** hai: teeno instances ne ek hi number badhaya aur use `a.created` ki tarah parh sake.

</Ur>
</Tr>
</Happened>

<Step title="A stateful class: LoginTracker">

<Tr>
<En>
`tracker.py` models a security feature as a class. A `LoginTracker` stores failure counts and locked users per instance, locks a user after `limit` consecutive failures, resets on success and can unlock. A class method `strict()` builds a tracker with a lower limit, and a static method `parse()` turns a log line into arguments. We replay eight login attempts, unlock a user, show that two trackers don't share state, and then show what goes wrong when the failure dict is a class attribute.
</En>
<Ur>
`tracker.py` security feature ko class ki tarah model karti hai. `LoginTracker` har instance me nakamiyon ki ginti aur locked users rakhta, `limit` lagatar nakamiyon ke baad user lock karta, kamyabi par reset karta aur unlock kar sakta hai. Class method `strict()` kam had wala tracker banata, aur static method `parse()` log line ko arguments me badalta hai. Hum aath login koshishen dohrate, ek user unlock karte, dikhate ke do trackers state nahi baantte, aur phir dikhate hain ke failure dict class attribute ho to kya ghalat hota hai.
</Ur>
</Tr>

```bash
cat > tracker.py <<'EOF'
class LoginTracker:
    """Counts consecutive failed logins per user and locks after a limit."""

    default_limit = 5                               # class attribute: a shared default

    def __init__(self, limit=None):
        self.limit = limit or self.default_limit
        self.failures = {}                          # per-instance state (not shared!)
        self.locked = set()

    def record(self, user, success):
        if user in self.locked:
            return "locked"
        if success:
            self.failures.pop(user, None)
            return "ok"
        self.failures[user] = self.failures.get(user, 0) + 1
        if self.failures[user] >= self.limit:
            self.locked.add(user)
            return "now locked"
        return f"failed ({self.failures[user]}/{self.limit})"

    def unlock(self, user):
        self.locked.discard(user)
        self.failures.pop(user, None)

    @classmethod
    def strict(cls):                                # alternative constructor
        return cls(limit=3)

    @staticmethod
    def parse(line):                                # a plain helper that lives in the class
        user, result = line.split()
        return user, result == "ok"

t = LoginTracker.strict()
for line in ["jane fail", "jane fail", "john ok", "jane ok", "ana fail", "ana fail", "ana fail", "ana ok"]:
    user, success = LoginTracker.parse(line)
    print(f"{line:<10} -> {t.record(user, success)}")
t.unlock("ana")
print(t.record("ana", True), "| locked:", t.locked, "| limit:", t.limit)

# Two trackers don't share state
relaxed = LoginTracker()
relaxed.record("jane", False)
print("relaxed:", relaxed.failures, relaxed.limit, "| strict:", t.failures)

# The shared mutable class attribute trap
class BadTracker:
    failures = {}                                   # ONE dict for every instance
    def record(self, user):
        self.failures[user] = self.failures.get(user, 0) + 1
x, y = BadTracker(), BadTracker()
x.record("jane")
print("y sees x's data:", y.failures)
EOF
python3 tracker.py
```

```text output
jane fail  -> failed (1/3)
jane fail  -> failed (2/3)
john ok    -> ok
jane ok    -> ok
ana fail   -> failed (1/3)
ana fail   -> failed (2/3)
ana fail   -> now locked
ana ok     -> locked
ok | locked: set() | limit: 3
relaxed: {'jane': 1} 5 | strict: {}
y sees x's data: {'jane': 1}
```

<Happened>
<Tr>
<En>

- The tracker's **state** (failures and locked users) changed with every `record` call: jane's two failures were **reset** by her success, while ana hit **3/3** and was locked; her later correct password returned **locked**. The logic and the data it needs live in one place.
- `LoginTracker.strict()` is a **class method**: it received the class as `cls` and returned `cls(limit=3)`. Alternative constructors like `from_line`, `from_config` or `strict` are the classic use.
- `LoginTracker.parse(line)` is a **static method**: no `self`, no `cls`, just a helper grouped with the class because it's about login lines.
- `unlock("ana")` cleared her lock, so her next login was **ok**.
- `relaxed` and `t` kept **separate** failure dicts and limits (5 versus 3) because `__init__` created new ones per instance.
- `BadTracker` put `failures = {}` in the class body, so **every instance shared one dict**: `y` saw `x`'s data. In a server handling many users or requests, that's a data leak. Mutable state belongs in `__init__`.

</En>
<Ur>

- Tracker ki **state** (failures aur locked users) har `record` call ke saath badli: jane ki do nakamiyan us ki kamyabi se **reset** huin, jabke ana **3/3** tak pohanch kar lock hui; us ka baad ka sahi password **locked** lautaya. Mantiq aur us ka zaroori data ek jagah rehte hain.
- `LoginTracker.strict()` **class method** hai: is ne class ko `cls` ki tarah paya aur `cls(limit=3)` lautaya. `from_line`, `from_config` ya `strict` jaise alternative constructors is ka mash-hoor istemal hain.
- `LoginTracker.parse(line)` **static method** hai: `self` nahi, `cls` nahi, bas helper jo class ke saath group hai kyunke login lines ke bare me hai.
- `unlock("ana")` ne us ka lock saaf kiya, isliye us ka agla login **ok** tha.
- `relaxed` aur `t` ne **alag** failure dicts aur hadein (5 ya 3) rakhin kyunke `__init__` ne har instance ke liye naye banaye.
- `BadTracker` ne `failures = {}` class ke jism me rakha, isliye **har instance ne ek dict baanti**: `y` ne `x` ka data dekha. Kayi users ya requests sambhalne wale server me ye data leak hai. Mutable state `__init__` me hoti hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Mutable data as a class attribute">

```text
class Cart:
    items = []                     # shared by every cart!
    def add(self, item):
        self.items.append(item)

a, b = Cart(), Cart()
a.add("book")
print(b.items)                     # ['book']
```

</Bad>
<Good title="Create per-instance data in __init__">

```text
class Cart:
    def __init__(self):
        self.items = []
    def add(self, item):
        self.items.append(item)
```

</Good>
</Compare>

<Compare>
<Bad title="Forgetting self">

```text
class Server:
    def __init__(self, name):
        name = name                # a local variable, lost after __init__
    def describe():                # missing self
        return name                # NameError, even if self were there
```

</Bad>
<Good title="Store on self, read from self">

```text
class Server:
    def __init__(self, name):
        self.name = name
    def describe(self):
        return self.name
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Classes with only `__init__` and no behaviour**: a dataclass or NamedTuple is simpler.
- **Classes with one method and no state**: that's a function.
- **Setting new attributes outside `__init__`** in random methods: readers can't see what an object holds; initialise everything in `__init__`.
- **Calling a method on the class without an instance**: `Server.describe()` fails; create an object first.
- **Giant "manager" classes that do everything**: split by responsibility.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sirf `__init__` wali classes, rawaiye ke baghair**: dataclass ya NamedTuple zyada saada hai.
- **Ek method aur state ke baghair classes**: ye function hai.
- **`__init__` ke bahar be-tarteeb methods me naye attributes set karna**: parhne wale nahi dekh sakte object me kya hai; sab `__init__` me shuru karein.
- **Instance ke baghair class par method bulana**: `Server.describe()` nakam hota; pehle object banayen.
- **Sab kuch karne wali bari "manager" classes**: zimmedari ke hisaab se torein.

</Ur>
</Tr>

<Challenge title="A Firewall class">

<Tr>
<En>
Write `class Firewall` with an `__init__` that takes a list of allowed ports, a method `allow(port)`, a method `block(port)`, a method `check(port)` that returns "allow" or "deny", and a class method `web_server()` returning a firewall that allows 80 and 443. Create a web firewall, allow 22, block 80, and check 22, 80 and 443.
</En>
<Ur>
`class Firewall` likhein jis ka `__init__` ijazat yafta ports ki list le, `allow(port)` method, `block(port)` method, "allow" ya "deny" lautane wala `check(port)` method, aur 80 aur 443 ki ijazat dene wala firewall lautane wala class method `web_server()` ho. Web firewall banayen, 22 ki ijazat dein, 80 block karein, aur 22, 80 aur 443 check karein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
class Firewall:
    def __init__(self, allowed=None):
        self.allowed = set(allowed or [])

    def allow(self, port):
        self.allowed.add(port)

    def block(self, port):
        self.allowed.discard(port)

    def check(self, port):
        return "allow" if port in self.allowed else "deny"

    @classmethod
    def web_server(cls):
        return cls([80, 443])

fw = Firewall.web_server()
fw.allow(22)
fw.block(80)
print({p: fw.check(p) for p in (22, 80, 443)})

# {22: 'allow', 80: 'deny', 443: 'allow'}
```

</En>

<DeepDive title="More about classes">

**Attribute lookup.** `obj.x` checks the instance's `__dict__`, then the class, then base classes; assigning `obj.x = 1` always writes to the instance, which is how an instance can hide a class attribute.

**`__slots__`.** Declaring `__slots__ = ("name", "ip")` stops new attributes and saves memory for millions of small objects.

**Everything is an object.** Classes themselves are objects (instances of `type`), so you can pass them around and call them to create instances.

**Bound methods.** `web.describe` (without parentheses) is a bound method that remembers `web`; you can store it and call it later.

**Naming.** Classes use PascalCase (`LoginTracker`); a leading underscore (`_cache`) marks attributes as internal, covered in Properties and Encapsulation.

</DeepDive>

<DeepDive title="Real world: the shared session cache">

A web app's API client class kept a cache of user tokens as a class attribute, `tokens = {}`, so it could be reused between requests. Each request created a new client for the logged-in user. Because the dict was shared by every instance in the process, a lookup bug returned another user's cached token under load, and one user briefly saw another user's data.

The fixes:

1. Move per-user state into `__init__` (`self.token = ...`).
2. If a shared cache is really needed, key it explicitly by user ID in a dedicated, tested cache object with expiry.
3. A concurrency test with many users that asserts each response belongs to the requesting user.

</DeepDive>

<DeepDive title="Security lens">

- **Class attributes are shared across users and requests**: never store per-user secrets or state there.
- **Objects that hold secrets** (API clients with tokens) should avoid printing them in `__repr__` and logs; you'll see how in Dunder Methods.
- **Validate in `__init__`**: an object that can only be created with valid data (a port between 1 and 65535) prevents bad state spreading.
- **Keep security state behind methods** like `record()` and `unlock()` so rules (limits, resets, audit logging) can't be bypassed by editing attributes directly.
- **Deserialising objects** from untrusted data with pickle can run code; use JSON and explicit constructors.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a class and an object?">
A class is a definition or blueprint describing attributes and methods; an object is a specific instance created from the class, with its own attribute values.
</QA>

<QA q="What is self in Python?">
The conventional name for a method's first parameter, which receives the instance the method was called on; obj.method(x) is equivalent to Class.method(obj, x).
</QA>

<QA q="Class attributes versus instance attributes?">
Class attributes are defined in the class body and shared by all instances; instance attributes are set on self, usually in `__init__`, and belong to one object. Mutable class attributes are shared state and a common bug.
</QA>

<QA q="What's the difference between @classmethod and @staticmethod?">
A class method receives the class as its first argument and can create instances or use class data; a static method receives neither the instance nor the class and is just a function namespaced in the class.
</QA>

<QA q="When would you use a class instead of functions?">
When data and the operations on it belong together, especially when the object has state that changes over time or several related objects of the same kind are needed.
</QA>

</DeepDive>
