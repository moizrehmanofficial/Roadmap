<BigIdea>
<Tr>
<En>
**Inheritance** lets a new class (the **subclass** or child) start from an existing one (the **base class** or parent) and add or change behaviour: `class EmailNotifier(Notifier)`. The subclass gets every method of the parent; it can **override** a method by defining one with the same name, and call the parent's version with **`super()`**. Code that works with the parent type works with any subclass too, so a loop calling `n.notify(...)` on a mix of notifiers does the right thing for each: that's **polymorphism**. An **abstract base class** (from `abc`) can declare methods every subclass **must** implement, and Python refuses to create objects that don't. Inheritance models an **is-a** relationship and should be used sparingly, for genuine specialisations. **Composition** models **has-a**: an `Audit` *has* a port checker and a notifier, stores them as attributes, and calls their methods. Passing those parts in from outside (**dependency injection**) means you can swap them, for example a fake notifier in tests. The common advice, "favour composition over inheritance", exists because deep inheritance trees are rigid and expose more than you intend, while composed objects stay small and replaceable.
</En>
<Ur>
**Inheritance** nayi class (**subclass** ya child) ko mojooda class (**base class** ya parent) se shuru kar ke rawaiya jorne ya badalne deti hai: `class EmailNotifier(Notifier)`. Subclass ko parent ka har method milta hai; woh usi naam ka method bana kar use **override** kar sakti, aur **`super()`** se parent ka version bula sakti hai. Jo code parent type ke saath chalta hai woh har subclass ke saath bhi chalta hai, isliye notifiers ke mile jule majmue par `n.notify(...)` bulane wala loop har ek ke liye sahi kaam karta hai: yahi **polymorphism** hai. **Abstract base class** (`abc` se) aise methods bata sakti hai jo har subclass ko **lazmi** banane hon, aur Python aise objects banane se inkar karta hai jo na banayen. Inheritance **is-a** rishta model karti hai aur kam istemal honi chahiye, asal khaas qismon ke liye. **Composition** **has-a** model karti hai: `Audit` ke *paas* port checker aur notifier hai, unhe attributes ki tarah rakhta aur un ke methods bulata hai. Un hisson ko bahar se dena (**dependency injection**) ka matlab aap unhe badal sakte hain, maslan tests me nakli notifier. Aam mashwara, "inheritance ke bajaye composition ko tarjeeh do", is liye hai ke gehre inheritance darakht sakht hote aur iraade se zyada dikhate hain, jabke jore hue objects chhote aur badalne layak rehte hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of **vehicles and a delivery company**.

- Inheritance: a delivery van **is a** vehicle. It has everything a vehicle has (wheels, engine, a `drive()` method) plus a cargo area. An electric van overrides how it refuels.
- Polymorphism: the dispatcher just says `drive()` to every vehicle; each knows how to do it.
- Composition: the delivery company **has** vans, drivers and a routing system. It isn't a van. If the routing system is replaced, the company keeps working: you plug in the new one.
- Inheriting a company from a van ("the company is a van with offices") would be absurd, and that's exactly the `BadStack(list)` mistake.

</En>
<Ur>

**Gaariyan aur delivery company** socheyn.

- Inheritance: delivery van **ek** gaari hai. Is ke paas gaari ki har cheez hai (pahiye, engine, `drive()` method) aur cargo ki jagah bhi. Electric van fuel bharne ka tareeqa override karti hai.
- Polymorphism: dispatcher har gaari ko bas `drive()` kehta hai; har ek jaanti hai kaise karna hai.
- Composition: delivery company ke **paas** vans, drivers aur routing system hain. Ye van nahi. Routing system badle to company chalti rehti hai: naya laga dete hain.
- Company ko van se inherit karna ("company daftaron wali van hai") be-maani hoga, aur bilkul yahi `BadStack(list)` wali ghalti hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Inheritance, overriding, super() and abstract base classes">

<Tr>
<En>
`inherit.py` defines an abstract `Notifier` with shared logic in `notify()` and an abstract `send()`. `EmailNotifier` adds a recipient and calls the parent's `__init__` with `super()`, `ChatNotifier` implements `send`, and `UrgentChatNotifier` extends `ChatNotifier`, reusing its `send` through `super()`. We loop over all three, check types and the method resolution order, and try to create the abstract base class and a subclass that forgot to implement `send`.
</En>
<Ur>
`inherit.py` `notify()` me mushtarak mantiq aur abstract `send()` wali abstract `Notifier` define karti hai. `EmailNotifier` recipient jorti aur `super()` se parent ka `__init__` bulati, `ChatNotifier` `send` banati, aur `UrgentChatNotifier` `ChatNotifier` ko barhati aur `super()` ke zariye us ka `send` dobara istemal karti hai. Hum teeno par loop chalate, types aur method resolution order check karte, aur abstract base class aur `send` bhoolne wali subclass banane ki koshish karte hain.
</Ur>
</Tr>

```bash
cat > inherit.py <<'EOF'
from abc import ABC, abstractmethod

class Notifier(ABC):
    """Base class: what every notifier has in common."""
    def __init__(self, name):
        self.name = name
        self.sent = 0

    def notify(self, message):                     # shared behaviour, written once
        self.sent += 1
        return self.send(f"[{self.name}] {message}")

    @abstractmethod
    def send(self, text):                          # each subclass MUST provide this
        ...

class EmailNotifier(Notifier):                     # "is a" Notifier
    def __init__(self, name, to):
        super().__init__(name)                     # run the parent's __init__ first
        self.to = to
    def send(self, text):
        return f"email to {self.to}: {text}"

class ChatNotifier(Notifier):
    def send(self, text):
        return f"chat #{self.name}: {text}"

class UrgentChatNotifier(ChatNotifier):            # extend a subclass and reuse its send
    def send(self, text):
        return super().send(text.upper()) + " @here"

notifiers = [EmailNotifier("ops", "oncall@example.com"), ChatNotifier("alerts"), UrgentChatNotifier("sec")]
for n in notifiers:                                # polymorphism: same call, different behaviour
    print(n.notify("disk 91% on db1"))

u = notifiers[2]
print(isinstance(u, ChatNotifier), isinstance(u, Notifier), issubclass(EmailNotifier, ChatNotifier))
print([c.__name__ for c in UrgentChatNotifier.__mro__])          # method resolution order
print("sent:", [n.sent for n in notifiers])

try:
    Notifier("base")                               # abstract: can't be created directly
except TypeError as e:
    print("TypeError:", e)

class Incomplete(Notifier):                        # forgot to implement send
    pass
try:
    Incomplete("x")
except TypeError as e:
    print("TypeError:", e)
EOF
python3 inherit.py
```

```text output
email to oncall@example.com: [ops] disk 91% on db1
chat #alerts: [alerts] disk 91% on db1
chat #sec: [SEC] DISK 91% ON DB1 @here
True True False
['UrgentChatNotifier', 'ChatNotifier', 'Notifier', 'ABC', 'object']
sent: [1, 1, 1]
TypeError: Can't instantiate abstract class Notifier without an implementation for abstract method 'send'
TypeError: Can't instantiate abstract class Incomplete without an implementation for abstract method 'send'
```

<Happened>
<Tr>
<En>

- One loop called `notify()` on three different objects and got **three different results**: polymorphism. `notify` (counting and prefixing) was written once in the base class; only `send` differs.
- `EmailNotifier.__init__` called `super().__init__(name)` so the parent set up `name` and `sent`; then it added `to`. Forgetting `super().__init__` is a classic bug: `self.sent` would never exist.
- `UrgentChatNotifier.send` changed the text and then called `super().send(...)`, reusing `ChatNotifier`'s formatting instead of copying it.
- `isinstance(u, Notifier)` was **True** (an urgent chat notifier is a notifier), but `EmailNotifier` isn't a `ChatNotifier`. The **MRO** shows the order Python searches for a method: the class itself, then each parent, up to `object`.
- Creating `Notifier` directly, or a subclass without `send`, raised **TypeError**: abstract base classes catch missing implementations at creation time instead of at the first call.

</En>
<Ur>

- Ek loop ne teen alag objects par `notify()` bulaya aur **teen alag natije** paye: polymorphism. `notify` (ginti aur prefix) base class me ek dafa likha gaya; sirf `send` alag hai.
- `EmailNotifier.__init__` ne `super().__init__(name)` bulaya taa ke parent `name` aur `sent` set kare; phir `to` jora. `super().__init__` bhoolna mash-hoor bug hai: `self.sent` kabhi wujood me na aata.
- `UrgentChatNotifier.send` ne text badla aur phir `super().send(...)` bulaya, `ChatNotifier` ki formatting copy karne ke bajaye dobara istemal ki.
- `isinstance(u, Notifier)` **True** tha (urgent chat notifier notifier hai), magar `EmailNotifier` `ChatNotifier` nahi. **MRO** woh tarteeb dikhata hai jis me Python method dhoondta hai: khud class, phir har parent, `object` tak.
- `Notifier` seedha, ya `send` ke baghair subclass banana **TypeError** deta hai: abstract base classes ghayab implementations ko pehli call ke bajaye banne ke waqt pakarti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Composition, dependency injection and a test double">

<Tr>
<En>
`compose.py` builds an `Audit` from two parts passed into its constructor: a `PortChecker` (here with fixed scan results) and a notifier. It runs once with a `ConsoleNotifier`, then again with a `FakeNotifier` that records messages so a test can check them. Finally it compares a `BadStack` that inherits from `list` with a `Stack` that contains one.
</En>
<Ur>
`compose.py` constructor me diye gaye do hisson se `Audit` banati hai: `PortChecker` (yahan tay shuda scan natijon ke saath) aur notifier. Ek dafa `ConsoleNotifier` ke saath chalti, phir `FakeNotifier` ke saath jo paighamat record karta hai taa ke test unhe check kare. Aakhir me `list` se inherit karne wale `BadStack` ko list rakhne wale `Stack` se milati hai.
</Ur>
</Tr>

```bash
cat > compose.py <<'EOF'
# Composition: an object HAS other objects and delegates work to them
class PortChecker:
    def __init__(self, open_ports):
        self.open_ports = open_ports                  # pretend scan results per host
    def open_on(self, host):
        return self.open_ports.get(host, [])

class ConsoleNotifier:
    def send(self, text):
        print("  ALERT:", text)

class FakeNotifier:                                   # same method name, records instead of sending
    def __init__(self):
        self.messages = []
    def send(self, text):
        self.messages.append(text)

class Audit:
    RISKY = {23, 3389, 6379}
    def __init__(self, checker, notifier):            # the parts are passed in (dependency injection)
        self.checker = checker
        self.notifier = notifier
    def run(self, hosts):
        findings = 0
        for host in hosts:
            for port in sorted(set(self.checker.open_on(host)) & self.RISKY):
                self.notifier.send(f"{host} has risky port {port} open")
                findings += 1
        return findings

checker = PortChecker({"web1": [22, 443], "db1": [22, 6379], "win1": [3389, 445, 23]})
print("findings:", Audit(checker, ConsoleNotifier()).run(["web1", "db1", "win1"]))

fake = FakeNotifier()                                 # swap a part: perfect for tests
assert Audit(checker, fake).run(["db1"]) == 1
assert fake.messages == ["db1 has risky port 6379 open"]
print("test with fake notifier passed:", fake.messages)

# Inheritance misuse: a Stack that IS-A list exposes every list method
class BadStack(list):
    def push(self, item):
        self.append(item)
s = BadStack()
s.push("a"); s.push("b"); s.insert(0, "sneaky")       # insert breaks the "stack" idea
print("BadStack allows:", s)

class Stack:                                          # composition: HAS-A list, exposes only what it should
    def __init__(self):
        self._items = []
    def push(self, item):
        self._items.append(item)
    def pop(self):
        return self._items.pop()
    def __len__(self):
        return len(self._items)
st = Stack(); st.push("a"); st.push("b")
print("Stack:", st.pop(), len(st), hasattr(st, "insert"))
EOF
python3 compose.py
```

```text output
  ALERT: db1 has risky port 6379 open
  ALERT: win1 has risky port 23 open
  ALERT: win1 has risky port 3389 open
findings: 3
test with fake notifier passed: ['db1 has risky port 6379 open']
BadStack allows: ['sneaky', 'a', 'b']
Stack: b 1 False
```

<Happened>
<Tr>
<En>

- `Audit` doesn't know or care **how** ports are checked or alerts are sent; it **has** a checker and a notifier and calls their methods. It found **3 risky ports** (Redis on db1, telnet and RDP on win1) and printed alerts through the console notifier.
- Because the notifier was **passed in**, the test swapped in `FakeNotifier`, which records instead of sending, and asserted exactly what would have been sent. No network, no real alerts, fast and reliable tests. The fake doesn't inherit from anything: Python only needs it to have a `send` method (duck typing).
- `BadStack(list)` inherited **every** list method, so `insert(0, "sneaky")` slipped an item under the stack. Inheritance exposes the parent's whole interface, whether or not it makes sense.
- `Stack` **contains** a list and exposes only `push`, `pop` and `len`; `hasattr(st, "insert")` is **False**. That's "favour composition over inheritance" in miniature.

</En>
<Ur>

- `Audit` ko parwah nahi ke ports **kaise** check hote ya alerts kaise jate hain; us ke **paas** checker aur notifier hai aur woh un ke methods bulata hai. Is ne **3 khatarnak ports** dhoonde (db1 par Redis, win1 par telnet aur RDP) aur console notifier se alerts print kiye.
- Kyunke notifier **bahar se diya gaya**, test ne `FakeNotifier` laga diya, jo bhejne ke bajaye record karta hai, aur bilkul check kiya ke kya bheja jata. Network nahi, asal alerts nahi, tez aur bharosemand tests. Nakli kisi se inherit nahi karta: Python ko bas us ke paas `send` method chahiye (duck typing).
- `BadStack(list)` ne list ka **har** method inherit kiya, isliye `insert(0, "sneaky")` ne stack ke neeche item ghusa diya. Inheritance parent ka poora interface dikhati hai, chahe maayne rakhe ya nahi.
- `Stack` list **rakhta** hai aur sirf `push`, `pop` aur `len` dikhata hai; `hasattr(st, "insert")` **False** hai. Ye chhoti shakal me "inheritance ke bajaye composition" hai.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Forgetting super().__init__">

```text
class EmailNotifier(Notifier):
    def __init__(self, name, to):
        self.to = to                 # parent never ran: no self.name, no self.sent
EmailNotifier("ops", "a@example.com").notify("hi")   # AttributeError: no attribute 'sent'
```

</Bad>
<Good title="Initialise the parent first">

```text
class EmailNotifier(Notifier):
    def __init__(self, name, to):
        super().__init__(name)
        self.to = to
```

</Good>
</Compare>

<Compare>
<Bad title="Hard-wired dependencies">

```text
class Audit:
    def __init__(self):
        self.notifier = SlackNotifier(token=os.environ["SLACK_TOKEN"])   # created inside
# every test sends real Slack messages, or fails without a token
```

</Bad>
<Good title="Inject them">

```text
class Audit:
    def __init__(self, notifier):
        self.notifier = notifier

Audit(SlackNotifier(token=...))   # production
Audit(FakeNotifier())             # tests
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Deep inheritance chains** (five levels of subclasses): hard to follow; flatten or compose.
- **Inheriting just to reuse one helper method**: move the helper to a function or a component.
- **Type checks instead of polymorphism**: `if isinstance(n, Email): ... elif isinstance(n, Chat): ...` belongs in each class's own method.
- **Subclasses that break the parent's promises** (a "read-only" subclass whose `write` raises): code using the parent type will fail unexpectedly.
- **Multiple inheritance without understanding the MRO**: keep mixins small and cooperative, or avoid them.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Gehri inheritance zanjeeren** (subclasses ke paanch levels): samajhna mushkil; seedha karein ya compose karein.
- **Sirf ek helper method dobara istemal karne ke liye inherit karna**: helper ko function ya component me le jayen.
- **Polymorphism ke bajaye type checks**: `if isinstance(n, Email): ... elif isinstance(n, Chat): ...` har class ke apne method me hona chahiye.
- **Subclasses jo parent ke wade torein** ("read-only" subclass jis ka `write` error de): parent type istemal karne wala code achanak nakam hoga.
- **MRO samjhe baghair multiple inheritance**: mixins chhote aur ta'awun wale rakhein, ya bachein.

</Ur>
</Tr>

<Challenge title="A family of checks">

<Tr>
<En>

Write `run_all(checks, host)` that returns a dict of check name to result. Hosts are dicts like `{"name": "web1", "open_ports": [22, 443]}`.
</En>
<Ur>
`name` aur abstract `run(host)` wali abstract `Check` banayen jo True (pass) ya False lautaye. `PortClosedCheck(port)` aur `HostnamePrefixCheck(prefix)` banayen. `run_all(checks, host)` likhein jo check ke naam se natije ki dict lautaye. Hosts `{"name": "web1", "open_ports": [22, 443]}` jaisi dicts hain.
</Ur>

<Solution>

<Tr>
<En>

```text
from abc import ABC, abstractmethod

class Check(ABC):
    def __init__(self, name):
        self.name = name
    @abstractmethod
    def run(self, host): ...

class PortClosedCheck(Check):
    def __init__(self, port):
        super().__init__(f"port {port} closed")
        self.port = port
    def run(self, host):
```

<DeepDive title="More about inheritance and composition">

**Protocols instead of base classes.** `typing.Protocol` lets a type checker accept any object with the right methods (like `FakeNotifier`), without inheritance: structural typing for duck-typed Python.

**Multiple inheritance and mixins.** Python supports several parents; the C3 linearisation (the MRO) decides lookup order, and `super()` follows the MRO, which makes cooperative mixins possible.

**Liskov substitution principle.** A subclass should be usable anywhere the parent is, without surprises; violating it is the usual sign inheritance was the wrong tool.

**Wrapping with delegation.** A wrapper can forward unknown attributes with `__getattr__`, adding behaviour such as caching or logging around any object.

**Exceptions.** Custom exception hierarchies (`class AppError(Exception)`, `class AuthError(AppError)`) are one of the best uses of inheritance in Python.

</DeepDive>

<DeepDive title="Real world: the notifier hierarchy that froze">

A monitoring codebase started with `Notifier`, then `EmailNotifier`, `HtmlEmailNotifier`, `BatchedHtmlEmailNotifier`, `RetryingBatchedHtmlEmailNotifier`... each adding one feature by subclassing. Adding retries to the Slack notifier meant duplicating the retry subclass, and a fix in the batching layer broke HTML formatting three levels down.

The fixes:

1. Keep a small set of notifiers that only know how to send (email, Slack, webhook).
2. Add features as wrappers that hold any notifier: `Retrying(notifier)`, `Batched(notifier)`, combined freely: `Retrying(Batched(Slack(...)))`.
3. A `Protocol` with one `send` method for the type checker; fakes for tests.

</DeepDive>

<DeepDive title="Security lens">

- **Inject security components** (auth checkers, crypto, HTTP clients) so you can test failure paths with fakes and swap implementations without editing callers.
- **Subclasses can weaken security**: overriding a `validate()` or `check_permission()` method to always return True silently disables protection; review overrides of security methods carefully.
- **Abstract methods for mandatory controls**: an abstract `authorize()` ensures every handler type must implement it.
- **Wrappers for cross-cutting controls**: logging, rate limiting and audit trails can wrap any client consistently.
- **Avoid exposing too much**: inheriting from `dict` or `list` gives callers methods that bypass your validation; compose instead.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between inheritance and composition?">
Inheritance creates an is-a relationship where a subclass reuses and specialises a parent's interface and behaviour; composition creates a has-a relationship where an object holds other objects and delegates work to them. Composition is usually more flexible and less coupled.
</QA>

<QA q="What does super() do?">
It returns a proxy that calls the next class in the method resolution order, typically the parent, letting a subclass extend rather than replace inherited behaviour, for example in `__init__.`
</QA>

<QA q="What is an abstract base class?">
A class that can't be instantiated and declares abstract methods that concrete subclasses must implement; Python raises TypeError if you instantiate a class with unimplemented abstract methods.
</QA>

<QA q="What is the method resolution order?">
The order in which Python searches a class and its bases for an attribute, computed with C3 linearisation and visible in `__mro__`; it matters with multiple inheritance.
</QA>

<QA q="What is dependency injection and why use it?">
Passing an object's collaborators in from outside rather than creating them inside, which makes components replaceable and testable with fakes or mocks.
</QA>

</DeepDive>
