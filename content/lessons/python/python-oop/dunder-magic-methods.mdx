<BigIdea>
<Tr>
<En>
When you write `len(x)`, `x == y`, `x in y`, `for item in x`, `x[0]`, `x + y`, `print(x)` or `with x:`, Python doesn't have special knowledge of your class. It calls a **special method** on the object: `__len__`, `__eq__`, `__contains__`, `__iter__`, `__getitem__`, `__add__`, `__str__`, `__enter__`... They're nicknamed **dunder** ("double underscore") or **magic** methods. Defining them lets your objects behave like built-in types. The most important is **`__repr__`**, the developer-facing text shown in the REPL, logs and inside lists, which every class should have; **`__str__`** is the friendlier text for `print()`. **`__eq__`** defines equality, and if you define it, define **`__hash__`** too so equal objects can be set members and dict keys. **`__lt__`** plus `@functools.total_ordering` makes objects sortable. A handful of container methods make an object work with `in`, `len`, `for` and indexing, and **`__enter__`/`__exit__`** turn it into a **context manager** whose cleanup always runs. You rarely call dunder methods yourself; you implement them, and Python calls them.
</En>
<Ur>
Jab aap `len(x)`, `x == y`, `x in y`, `for item in x`, `x[0]`, `x + y`, `print(x)` ya `with x:` likhte hain, to Python ko aap ki class ka khaas ilm nahi hota. Woh object par **special method** bulata hai: `__len__`, `__eq__`, `__contains__`, `__iter__`, `__getitem__`, `__add__`, `__str__`, `__enter__`... Aap dunder methods khud shayad hi bulate hain; aap unhe banate hain, aur Python unhe bulata hai.

## Picture it

<Tr>
<En>

Think of **standard sockets in a wall**.

- Python's built-ins (`len`, `==`, `for`, `with`, `print`) are appliances with standard plugs.
- Dunder methods are the sockets your class provides. If your class has a `__len__` socket, the `len` appliance plugs straight in; if it doesn't, you get a TypeError ("object of type X has no len()").
- You don't push electricity yourself; you just install the right socket, and the appliance knows what to do.
- `__enter__` and `__exit__` are like a light switch with an automatic timer: the light comes on when you walk in (`with`) and is guaranteed to go off when you leave, even if you leave in a hurry (an exception).

</En>
<Ur>

**Deewar me standard sockets** socheyn.

- Python ke built-ins (`len`, `==`, `for`, `with`, `print`) standard plugs wale appliances hain.
- Dunder methods woh sockets hain jo aap ki class deti hai. Agar class me `__len__` socket ho to `len` appliance seedha lag jata hai; na ho to TypeError milta hai ("object of type X has no len()").
- Aap khud bijli nahi dhakelte; bas sahi socket lagate hain, aur appliance jaanta hai kya karna hai.
- `__enter__` aur `__exit__` khud-kaar timer wale light switch jaise hain: andar aate hi (`with`) batti jalti aur nikalne par bujhne ki zamanat hai, chahe jaldi me niklein (exception).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Printing, equality, hashing, ordering and truthiness">

<Tr>
<En>
`dunders.py` gives an `ApiKey` a `__repr__` that masks the secret and a `__str__` for people, compares that with a class without either, makes a `Version` class comparable, hashable and sortable with `__eq__`, `__hash__`, `__lt__` and `total_ordering`, and gives a `Batch` a length and truthiness. The `sed` at the end hides the memory address in the default repr, because it changes on every run.
</En>
<Ur>
`dunders.py` `ApiKey` ko secret chhupane wala `__repr__` aur logon ke liye `__str__` deti, use dono ke baghair wali class se milati, `__eq__`, `__hash__`, `__lt__` aur `total_ordering` se `Version` class ko muqable, hash aur sort hone layak banati, aur `Batch` ko lambai aur truthiness deti hai. Aakhir ka `sed` default repr me memory address chhupata hai, kyunke ye har run par badalta hai.
</Ur>
</Tr>

```bash
cat > dunders.py <<'EOF'
from functools import total_ordering

class ApiKey:
    def __init__(self, name, secret):
        self.name, self.secret = name, secret
    def __repr__(self):                          # for developers: shown in the REPL, logs, lists
        return f"ApiKey(name={self.name!r}, secret='{self.secret[:4]}...')"
    def __str__(self):                           # for people: used by print() and str()
        return f"key '{self.name}'"

key = ApiKey("billing", "acme_live_9f8e7d6c5b4a")
print(key)                                       # __str__
print(repr(key), [key])                          # __repr__ (containers use repr)
print(f"{key} / {key!r}")

class Plain:
    def __init__(self, x): self.x = x
print(Plain(1))                                  # the default repr isn't helpful

@total_ordering                                  # fills in <=, >, >= from __eq__ and __lt__
class Version:
    def __init__(self, text):
        self.parts = tuple(int(p) for p in text.split("."))
    def __repr__(self):
        return "Version(" + ".".join(map(str, self.parts)) + ")"
    def __eq__(self, other):
        return isinstance(other, Version) and self.parts == other.parts
    def __hash__(self):                          # equal objects must hash the same
        return hash(self.parts)
    def __lt__(self, other):
        return self.parts < other.parts

vs = [Version("1.10.0"), Version("1.2.0"), Version("1.9.3"), Version("1.2.0")]
print(sorted(vs), max(vs))
print(Version("1.2.0") == Version("1.2.0"), Version("2.0") >= Version("1.99"), len(set(vs)))

class Batch:
    def __init__(self, items): self.items = list(items)
    def __len__(self): return len(self.items)    # len(batch); also makes empty batches falsy
    def __bool__(self): return bool(self.items)
print(len(Batch([1, 2, 3])), bool(Batch([])), "empty!" if not Batch([]) else "")
EOF
python3 dunders.py | sed "s/ at 0x[0-9a-f]*>/ at 0x...>/"      # hide the memory address, it changes every run
```

```text output
key 'billing' / ApiKey(name='billing', secret='acme...')
<__main__.Plain object at 0x...>
[Version(1.2.0), Version(1.2.0), Version(1.9.3), Version(1.10.0)] Version(1.10.0)

```

<Tr>
<En>

- `print(key)` used **`__str__`** ("key 'billing'"); `repr(key)` and the list display used **`__repr__`**. In f-strings, `{key}` uses `__str__` and `{key!r}` uses `__repr__`.
- Our `__repr__` showed only **`acme...`** of the secret. Objects end up in logs, error messages and debuggers through `repr`, so classes holding credentials should never print them in full.
- Without either method, Python fell back to **`<__main__.Plain object at 0x...>`**: useless when debugging. Always write a `__repr__`, ideally one that looks like the code to recreate the object.
- With `__lt__` (plus `total_ordering` for the other comparisons), `sorted` put **1.10.0 last** and `max` found it: real version order, not text order.
- `__eq__` made two `Version("1.2.0")` objects equal, and `__hash__` (based on the same tuple) let the set drop the duplicate: **3** unique versions. If you define `__eq__` without `__hash__`, Python makes the objects unhashable, so they can't go in sets.
- `__len__` made `len()` work and `__bool__` made an empty batch falsy, so `if not batch:` reads naturally.

</En>
<Ur>

- `print(key)` ne **`__str__`** ("key 'billing'") istemal kiya; `repr(key)` aur list ke display ne **`__repr__`**. f-strings me `{key}` `__str__` aur `{key!r}` `__repr__` istemal karta hai.

- `__lt__` (aur doosre comparisons ke liye `total_ordering`) ke saath `sorted` ne **1.10.0 aakhir me** rakha aur `max` ne use dhoonda: asal version tarteeb, text ki tarteeb nahi.
- `__eq__` ne do `Version("1.2.0")` objects barabar kiye, aur `__hash__` (usi tuple par mabni) ne set ko duplicate girane diya: **3** munfarid versions. Agar `__hash__` ke baghair `__eq__` define karein to Python objects ko unhashable bana deta hai, isliye woh sets me nahi ja sakte.
- `__len__` ne `len()` chalaya aur `__bool__` ne khaali batch ko falsy banaya, isliye `if not batch:` qudrati parhta hai.

<Step title="Containers, operators, callables and context managers">

<Tr>
<En>
`containers.py` builds a `Blocklist` that supports `in`, `len`, `for`, indexing and slicing, `+` with another list, and being called like a function to decide allow or deny. Then a `Timer` class implements `__enter__` and `__exit__` so it can wrap a block with `with`: we use it once for code that succeeds and once for code that raises an error.
</En>
<Ur>
`containers.py` aisi `Blocklist` banati hai jo `in`, `len`, `for`, indexing aur slicing, doosri list ke saath `+`, aur allow ya deny tay karne ke liye function ki tarah bulaye jane ko support kare. Phir `Timer` class `__enter__` aur `__exit__` banati hai taa ke `with` se block lapet sake: hum ise ek dafa kamyab hone wale code aur ek dafa error dene wale code ke liye istemal karte hain.
</Ur>
</Tr>

```bash
cat > containers.py <<'EOF'
import time

class Blocklist:
    """Behaves like a built-in container: in, len, for, [], +, and calling it."""
    def __init__(self, ips=()):
        self._ips = sorted(set(ips))
    def __contains__(self, ip):                  # ip in blocklist
        return ip in self._ips
    def __len__(self):
        return len(self._ips)
    def __iter__(self):                          # for ip in blocklist
        return iter(self._ips)
    def __getitem__(self, index):                # blocklist[0], blocklist[1:3]
        return self._ips[index]
    def __add__(self, other):                    # blocklist + other -> a NEW blocklist
        return Blocklist(self._ips + list(other))
    def __call__(self, ip):                      # blocklist(ip): use the object like a function
        return "deny" if ip in self else "allow"
    def __repr__(self):
        return f"Blocklist({self._ips})"

a = Blocklist(["203.0.113.7", "198.51.100.4"])
b = a + ["192.0.2.66", "203.0.113.7"]
print("203.0.113.7" in a, len(b), b[0], b[-2:])
print([ip for ip in b], list(map(b, ["192.0.2.66", "192.0.2.1"])))
print(a, b, sorted(b, reverse=True)[0])

# A context manager: __enter__ runs at the start of `with`, __exit__ ALWAYS runs at the end
class Timer:
    def __init__(self, label):
        self.label = label
    def __enter__(self):
        self.start = time.perf_counter()
        print(f"start {self.label}")
        return self
    def __exit__(self, exc_type, exc, tb):
        took = time.perf_counter() - self.start
        status = "failed: " + exc_type.__name__ if exc_type else "ok"
        print(f"end {self.label} ({status}, {'under' if took < 1 else 'over'} 1 s)")
        return False                             # don't swallow exceptions

with Timer("scan"):
    sum(range(100_000))
try:
    with Timer("import"):
        int("not a number")
except ValueError:
    print("the error still reached the caller")
EOF
python3 containers.py
```

```text output
True 3 192.0.2.66 ['198.51.100.4', '203.0.113.7']
['192.0.2.66', '198.51.100.4', '203.0.113.7'] ['deny', 'allow']
Blocklist(['198.51.100.4', '203.0.113.7']) Blocklist(['192.0.2.66', '198.51.100.4', '203.0.113.7']) 203.0.113.7
```

<Happened>
<Tr>
<En>

- `in`, `len`, `b[0]`, `b[-2:]`, a comprehension, `sorted` and `map` all worked on our own class, because it implements the container methods. `__getitem__` received a **slice object** for `b[-2:]` and simply passed it to the internal list.
- `a + [...]` called `__add__`, which returned a **new** `Blocklist` (duplicates removed, sorted) and left `a` unchanged. Operators should usually return new objects rather than modify the left-hand one.
- `__call__` let us pass the blocklist itself to `map` as a function: `b(ip)` returned **deny** or **allow**.
- `with Timer("scan"):` called `__enter__` before the block and `__exit__` after it. In the second case `int("not a number")` raised **ValueError**, yet `__exit__` still ran and reported **failed: ValueError**, then returned False so the error continued to the caller. That guarantee is why files, locks and database transactions use `with`.

</En>
<Ur>

- `in`, `len`, `b[0]`, `b[-2:]`, comprehension, `sorted` aur `map` sab hamari apni class par chale, kyunke ye container methods banati hai. `b[-2:]` ke liye `__getitem__` ko **slice object** mila aur us ne use bas andar ki list ko de diya.
- `a + [...]` ne `__add__` bulaya, jis ne **nayi** `Blocklist` lautayi (duplicates hata kar, sorted) aur `a` ko waisa hi chhora. Operators ko aam taur par baayen wale ko badalne ke bajaye naye objects lautane chahiyen.
- `__call__` ne humein blocklist ko khud function ki tarah `map` ko dene diya: `b(ip)` ne **deny** ya **allow** lautaya.
- `with Timer("scan"):` ne block se pehle `__enter__` aur baad me `__exit__` bulaya. Doosri soorat me `int("not a number")` ne **ValueError** diya, phir bhi `__exit__` chala aur **failed: ValueError** bataya, phir False lautaya taa ke error bulane wale tak pohanche. Yahi zamanat hai jis wajah se files, locks aur database transactions `with` istemal karte hain.

</Ur>

## Common mistakes

<Compare>
<Bad title="Secrets in __repr__">

```text
class DbConfig:
    def __init__(self, url):
        self.url = url        # postgres://app:S3cret@db:5432/shop
    def __repr__(self):
        return f"DbConfig(url={self.url!r})"
log.error("connect failed: %r", config)     # password now in the logs
```

</Bad>
<Good title="Mask sensitive fields">

```text
import re
class DbConfig:
    def __init__(self, url):
        self.url = url
    def __repr__(self):
        safe = re.sub(r":[^:@/]+@", ":***@", self.url)
        return f"DbConfig(url={safe!r})"
```

</Good>
</Compare>

<Compare>
<Bad title="__eq__ without __hash__ (or a mutable hash)">

```text
class User:
    def __init__(self, email): self.email = email
    def __eq__(self, other): return self.email == other.email
{User("a@example.com")}       # TypeError: unhashable type: 'User'
```

</Bad>
<Good title="Hash the same fields you compare, keep them immutable">

```text
class User:
    def __init__(self, email): self._email = email.lower()
    @property
    def email(self): return self._email
    def __eq__(self, other): return isinstance(other, User) and self._email == other._email
    def __hash__(self): return hash(self._email)
# or: @dataclass(frozen=True)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Calling dunders directly** (`x.__len__()`): use `len(x)`; the built-in does extra checks.
- **`__eq__` that crashes on other types**: return `NotImplemented` (or False) when `other` isn't your type.
- **`__exit__` returning True by accident**: it swallows exceptions silently.
- **Operators that mutate** (`__add__` changing `self`): surprising; use `__iadd__` for `+=` if you want in-place behaviour.
- **Writing all of this by hand for simple records**: dataclasses generate `__repr__`, `__eq__` and ordering for you (next lesson).

</En>
<Ur>

- **Dunders seedhe bulana** (`x.__len__()`): `len(x)` lein; built-in izafi checks karta hai.
- **Doosri types par crash karne wala `__eq__`**: jab `other` aap ki type na ho to `NotImplemented` (ya False) lautayen.
- **Ittefaqan True lautane wala `__exit__`**: exceptions khamoshi se nigal jata hai.
- **Badalne wale operators** (`__add__` ka `self` badalna): hairan kun; apni jagah wale rawaiye ke liye `+=` ka `__iadd__` lein.

```text
    def __repr__(self):
        return f"Money({self.cents}, {self.currency!r})"

        return f"${self.cents // 100}.{self.cents % 100:02d}"

        return hash((self.cents, self.currency))

        return self.cents < other.cents
```

```text
    def __init__(self, action, user):

    def __enter__(self):
        AUDIT_LOG.append(f"{self.user} started {self.action}")
```

<DeepDive title="More about special methods">

**NotImplemented.** Comparison and arithmetic methods should return `NotImplemented` for unsupported types, letting Python try the other operand's method (`__radd__`) before raising TypeError.

**contextlib.** `@contextmanager` turns a generator function with one `yield` into a context manager, often simpler than a class; `contextlib.suppress`, `ExitStack` and `closing` cover common cases.

**Attribute hooks.** `__getattr__` (called for missing attributes) enables proxies and wrappers; `__setattr__` and `__getattribute__` intercept all access but are easy to misuse.

**Format and conversions.** `__format__` controls f-string format specs, `__int__`, `__float__` and `__index__` support conversions and slicing, `__bytes__` supports `bytes(obj)`.

**Lifecycle.** `__new__` creates the object before `__init__` runs; `__del__` runs on garbage collection but isn't reliable for cleanup, so use context managers.

</DeepDive>

<DeepDive title="Real world: the token in the error tracker">

An internal API client class had no custom `__repr__`, so Python's default was harmless. Then a developer added a dataclass-style `__repr__` that printed every field "for easier debugging", including `token`. When a request failed, the exception message included `repr(client)`, the error tracker stored it, and dozens of people with dashboard access could read a production API token.

The fixes:

1. Rotate the token immediately.
2. Mask or exclude secret fields in `__repr__` (with dataclasses: `field(repr=False)`).
3. Scrub secrets in the error tracker's settings as a second layer.
4. A test asserting the secret never appears in `repr(client)` or `str(client)`.

</DeepDive>

<DeepDive title="Security lens">

- **`__repr__` ends up in logs, tracebacks and error trackers**: mask passwords, tokens, keys and personal data.
- **Context managers for security-critical cleanup**: closing connections, releasing locks, zeroing temporary secrets and writing audit records happen even when errors occur.
- **`__exit__` must not swallow exceptions** unintentionally; a returned True hides failures such as failed permission checks.
- **Equality and hashing on identity fields** (normalised email, user ID) avoid duplicate accounts like `Jane@Example.com` and `jane@example.com`.
- **Avoid `__getattr__` magic around security objects**: hidden forwarding makes it hard to review what can be accessed.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between __repr__ and __str__?">
`__repr__` is an unambiguous representation for developers, used by repr(), the REPL and containers, ideally looking like code that recreates the object; `__str__` is a readable representation for end users, used by print and str, and falls back to `__repr__`.
</QA>

<QA q="Why must __eq__ and __hash__ be consistent?">
Sets and dicts find items by hash and then compare with equality; objects that are equal must have equal hashes, otherwise lookups fail. Defining `__eq__` alone makes a class unhashable by default.
</QA>

<QA q="How do you make a custom class iterable?">
Implement `__iter__` returning an iterator (often iter(some_list) or a generator), or implement `__getitem__` with integer indexes as a fallback.
</QA>

<QA q="What is a context manager?">
An object implementing `__enter__` and `__exit__`, used with the with statement to set up and reliably tear down resources, with `__exit__` receiving any exception raised in the block.
</QA>

<QA q="What does __call__ do?">
It makes instances callable like functions, useful for configurable function-like objects such as validators, strategies or stateful callbacks.
</QA>

</DeepDive>
