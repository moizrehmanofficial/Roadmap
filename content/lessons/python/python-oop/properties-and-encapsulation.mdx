<BigIdea>
<Tr>
<En>
**Encapsulation** is the idea that an object is responsible for its own data: outside code asks the object to do things through methods, and the object enforces the rules (a port must be 1 to 65535, a quota can't go negative, a limit change must be recorded). Python doesn't have `private` like Java or C#. Instead it uses **conventions**: a name like `self.label` is **public**; a single leading underscore, `self._cache`, means **internal, don't touch** (but nothing stops you); two leading underscores, `self.__key`, trigger **name mangling** to `_Vault__key`, which avoids accidental clashes in subclasses but isn't security. The main tool for encapsulation is **`@property`**: it lets you keep the simple syntax `svc.port` and `svc.port = 8443` while running a **getter** and a **setter** behind the scenes, so every assignment is validated. A property without a setter is **read-only**, ideal for **computed values** like `url` or `remaining`. Because you can turn a plain attribute into a property later without changing callers, Python code starts with plain attributes and adds properties only when rules are needed. Expensive computed values can use **`functools.cached_property`**: calculated on first access, then stored.
</En>
<Ur>
**Encapsulation** ye khayal hai ke object apne data ka zimmedar hai: bahar ka code methods ke zariye object se kaam karwata, aur object qaide lagu karta hai (port 1 se 65535 hona chahiye, quota manfi nahi ho sakta, had ki tabdeeli darj honi chahiye). Python me Java ya C# jaisa `private` nahi. Is ke bajaye **riwaj** hain: `self.label` jaisa naam **public** hai; ek underscore se shuru, `self._cache`, ka matlab **andar ka, mat chhuen** (magar koi rok nahi); do underscores, `self.__key`, `_Vault__key` me **name mangling** karte hain, jo subclasses me ittefaqi takrao se bachata magar security nahi. Encapsulation ka asal auzaar **`@property`** hai: ye aap ko saada syntax `svc.port` aur `svc.port = 8443` rakhne deta jabke parde ke peeche **getter** aur **setter** chalte hain, isliye har assignment validate hota hai. Setter ke baghair property **read-only** hai, `url` ya `remaining` jaisi **hisaab wali values** ke liye behtareen. Kyunke aap saade attribute ko baad me bulane walon ko badle baghair property bana sakte hain, Python code saade attributes se shuru hota aur properties sirf tab jorta hai jab qaide chahiyen. Mehngi hisaab wali values **`functools.cached_property`** istemal kar sakti hain: pehli rasai par hisaab, phir mehfooz.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- Objects that validate their own state can't be put into impossible states by careless callers.
- Rules live in one place (the setter or method), not copied into every caller.
- Clean interfaces let you change the internals later without breaking code that uses the class.

</En>
<Ur>

- Apni state validate karne wale objects ko be-parwah bulane wale na-mumkin halat me nahi daal sakte.
- Qaide ek jagah (setter ya method) rehte hain, har bulane wale me copy nahi.
- Saaf interfaces andar ka hissa baad me badalne dete hain baghair class istemal karne wala code tore.

</Ur>

## Picture it

<Tr>
<En>

Think of a **bank teller window**.

- You don't reach into the vault and change your balance; you ask the teller to deposit or withdraw (methods). The teller checks the rules (enough money, ID shown) and records every transaction.
- The balance shown on the screen is a read-only property: you can look, but typing a new number on the screen doesn't change your account.

## Learn it step by step

<Walkthrough>

<Step title="Properties with validation, read-only values and naming conventions">

<Tr>
<En>
`props.py` builds a `Service` whose `port` is a property: reading returns `_port`, assigning runs a setter that rejects anything that isn't an int from 1 to 65535. Because `__init__` assigns `self.port`, even construction is validated. A computed `url` property has no setter. We change the port, try three bad values, a bad constructor argument and assigning to `url`, then look at public, `_internal` and `__mangled` names on a `Vault`.
</En>
<Ur>
`props.py` aisi `Service` banati jis ka `port` property hai: parhna `_port` lautata, assign karna aisa setter chalata jo 1 se 65535 tak int ke ilawa sab radd kare. Kyunke `__init__` `self.port` assign karta hai, banana bhi validate hota hai. Hisaab wali `url` property ka setter nahi. Hum port badalte, teen ghalat values, ghalat constructor argument aur `url` par assign aazmate, phir `Vault` par public, `_internal` aur `__mangled` naam dekhte hain.
</Ur>
</Tr>

```bash
cat > props.py <<'EOF'
class Service:
    def __init__(self, name, port):
        self.name = name
        self.port = port                       # goes through the setter below, so it's validated too

    @property
    def port(self):                            # read like an attribute: svc.port
        return self._port

    @port.setter
    def port(self, value):                     # assignment runs this: svc.port = 8443
        if not isinstance(value, int) or not 1 <= value <= 65535:
            raise ValueError(f"invalid port {value!r}")
        self._port = value

    @property
    def url(self):                             # computed, read-only (no setter)
        scheme = "https" if self._port in (443, 8443) else "http"
        return f"{scheme}://{self.name}:{self._port}"

svc = Service("api.example.test", 443)
print(svc.port, svc.url)
svc.port = 8080                                # looks like a plain assignment...
print(svc.url)
for bad in (0, "443", 70000):
    try:
        svc.port = bad                         # ...but the rules still apply
    except ValueError as e:
        print("ValueError:", e)
try:
    Service("x", -1)                           # __init__ is protected too
except ValueError as e:
    print("ValueError:", e)
try:
    svc.url = "http://evil.example"
except AttributeError as e:
    print("AttributeError:", e)

# Naming conventions: public, _internal, __mangled
class Vault:
    def __init__(self):
        self.label = "prod secrets"            # public
        self._cache = {}                       # internal: "please don't touch" (not enforced)
        self.__key = "k-123"                   # name-mangled to _Vault__key
v = Vault()
print(v.label, v._cache, hasattr(v, "__key"), v._Vault__key)
EOF
python3 props.py
```

```text output
443 https://api.example.test:443
http://api.example.test:8080
ValueError: invalid port 0
ValueError: invalid port '443'
ValueError: invalid port 70000
ValueError: invalid port -1
AttributeError: property 'url' of 'Service' object has no setter
prod secrets {} False k-123
```

<Happened>
<Tr>
<En>

- `svc.port` and `svc.port = 8080` look like plain attribute access, but they ran the getter and setter. Callers get simple syntax; the class keeps control.
- The setter rejected **0**, the string **'443'** and **70000**. Since `__init__` also uses `self.port = port`, `Service("x", -1)` failed too: there's no way to create or reach an invalid state.
- `url` was **computed** from the current port each time (switching from https to http when the port changed), and assigning to it raised **property 'url' of 'Service' object has no setter**: read-only.
- `v._cache` was readable: a single underscore is only a convention, telling other developers it's internal. `hasattr(v, "__key")` was **False** because Python renamed it, but `v._Vault__key` still returned the value. Name mangling prevents accidents, not access, so never treat it as protection for secrets.

</En>
<Ur>

- `svc.port` aur `svc.port = 8080` saade attribute jaise dikhte hain, magar inhone getter aur setter chalaye. Bulane walon ko saada syntax milta; class qaboo rakhti hai.
- Setter ne **0**, string **'443'** aur **70000** radd kiye. Kyunke `__init__` bhi `self.port = port` istemal karta hai, `Service("x", -1)` bhi nakam hua: ghalat halat banane ya pohanchne ka koi raasta nahi.
- `url` har dafa mojooda port se **hisaab** hua (port badalne par https se http), aur us par assign ne **property 'url' of 'Service' object has no setter** diya: read-only.
- `v._cache` parha ja saka: ek underscore sirf riwaj hai, doosre developers ko batata ke ye andar ka hai. `hasattr(v, "__key")` **False** tha kyunke Python ne naam badla, magar `v._Vault__key` ne phir bhi value lautayi. Name mangling hadson se bachata hai, rasai se nahi, isliye ise kabhi secrets ki hifazat na samjhein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Encapsulating rules: an API quota and cached values">

<Tr>
<En>
`account.py` builds an `ApiQuota` where the counters are internal and only methods change them: `consume(n)` refuses to go over the limit and records every attempt, `raise_limit()` requires an approver and refuses to go below current usage. `remaining` and `history` are read-only properties, and `history` returns a tuple copy. We use it, try to cheat twice, and then use `cached_property` in a `Report` to compute a value only once.
</En>
<Ur>
`account.py` aisa `ApiQuota` banati jis ke counters andar ke hain aur sirf methods unhe badalte hain: `consume(n)` had se upar jane se inkar karta aur har koshish darj karta, `raise_limit()` manzoori dene wala maangta aur mojooda istemal se neeche jane se inkar karta hai. `remaining` aur `history` read-only properties hain, aur `history` tuple copy lautati hai. Hum ise istemal karte, do dafa dhoka dene ki koshish karte, phir `Report` me `cached_property` se value sirf ek dafa hisaab karte hain.
</Ur>
</Tr>

```bash
cat > account.py <<'EOF'
from functools import cached_property

class ApiQuota:
    """Encapsulates a quota: callers use methods, the rules live inside."""

    def __init__(self, owner, limit):
        if limit <= 0:
            raise ValueError("limit must be positive")
        self.owner = owner
        self._limit = limit
        self._used = 0
        self._history = []

    @property
    def remaining(self):
        return self._limit - self._used

    @property
    def history(self):
        return tuple(self._history)            # a read-only copy, not the internal list

    def consume(self, n=1):
        if n <= 0:
            raise ValueError("n must be positive")
        if n > self.remaining:
            self._history.append(f"denied {n}")
            return False
        self._used += n
        self._history.append(f"used {n}")
        return True

    def raise_limit(self, new_limit, approved_by):
        if new_limit < self._used:
            raise ValueError("new limit below current usage")
        self._history.append(f"limit {self._limit}->{new_limit} by {approved_by}")
        self._limit = new_limit

q = ApiQuota("jane", 5)
print([q.consume(2), q.consume(2), q.consume(2)], "remaining:", q.remaining)
q.raise_limit(10, approved_by="ana")
print(q.consume(2), q.remaining)
print(q.history)
try:
    q.remaining = 1000                          # no setter: can't fake the quota
except AttributeError as e:
    print("AttributeError:", e)
try:
    q.history.append("used 0")                  # the copy is a tuple
except AttributeError as e:
    print("AttributeError:", e)

# cached_property: compute once on first access, then store
class Report:
    def __init__(self, lines):
        self.lines = lines
        self.computed = 0
    @cached_property
    def failures(self):
        self.computed += 1
        return sum(1 for l in self.lines if " 401 " in l)

r = Report(["GET / 200 ", "POST /login 401 ", "POST /login 401 "])
print(r.failures, r.failures, "computed", r.computed, "time(s)")
EOF
python3 account.py
```

```text output
[True, True, False] remaining: 1
True 4
('used 2', 'used 2', 'denied 2', 'limit 5->10 by ana', 'used 2')
AttributeError: property 'remaining' of 'ApiQuota' object has no setter
AttributeError: 'tuple' object has no attribute 'append'
2 2 computed 1 time(s)
```

<Happened>
<Tr>
<En>

- Two `consume(2)` calls succeeded and the third was **denied** (only 1 remaining): the invariant "never use more than the limit" is enforced inside the class, not by every caller.
- `raise_limit(10, approved_by="ana")` changed the limit **and recorded who approved it**. Because the limit can only change through this method, the audit trail can't be skipped.
- `history` showed every event in order, including the denial.
- `q.remaining = 1000` failed (no setter), and `q.history.append(...)` failed because callers get a **tuple copy**, not the internal list. Returning internal mutable objects lets callers bypass your rules.
- `r.failures` was computed on first access and then reused: `computed 1 time(s)` although it was read twice. Use `cached_property` for expensive values whose inputs don't change after creation.

</En>
<Ur>

- Do `consume(2)` calls kamyab hui aur teesri **radd** hui (sirf 1 bacha): qaida "had se zyada kabhi istemal nahi" class ke andar lagu hai, har bulane wale ke zariye nahi.
- `raise_limit(10, approved_by="ana")` ne had badli **aur darj kiya ke kis ne manzoori di**. Kyunke had sirf is method se badal sakti hai, audit trail chhoota nahi ja sakta.
- `history` ne har waqia tarteeb se dikhaya, inkar samait.
- `q.remaining = 1000` nakam hua (setter nahi), aur `q.history.append(...)` nakam hua kyunke bulane walon ko **tuple copy** milti hai, andar ki list nahi. Andar ke mutable objects lautana bulane walon ko aap ke qaide phalangne deta hai.
- `r.failures` pehli rasai par hisaab hua aur phir dobara istemal hua: do dafa parhne ke bawajood `computed 1 time(s)`. Mehngi values ke liye `cached_property` lein jin ke inputs banne ke baad na badlein.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Getters and setters for everything (Java style)">

```text
class Host:
    def __init__(self, name):
        self._name = name
    def get_name(self):
        return self._name
    def set_name(self, value):
        self._name = value
host.set_name(host.get_name().upper())
```

</Bad>
<Good title="Plain attributes until you need rules">

```text
class Host:
    def __init__(self, name):
        self.name = name
host.name = host.name.upper()
# later, if names must be validated, turn name into a property: callers don't change
```

</Good>
</Compare>

<Compare>
<Bad title="Validation only in __init__">

```text
class Service:
    def __init__(self, port):
        if not 1 <= port <= 65535:
            raise ValueError
        self.port = port
svc = Service(443)
svc.port = -1          # nothing stops this
```

</Bad>
<Good title="Validate in the setter, and use it from __init__">

```text
class Service:
    def __init__(self, port):
        self.port = port
    @property
    def port(self): return self._port
    @port.setter
    def port(self, value):
        if not 1 <= value <= 65535:
            raise ValueError(f"bad port {value}")
        self._port = value
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Infinite recursion in a property**: a setter that does `self.port = value` instead of `self._port = value` calls itself forever.
- **Slow or side-effect-heavy properties**: readers expect attribute access to be cheap; use a method (`fetch_status()`) for network calls.
- **Returning internal lists or dicts**: callers can change them without going through your rules; return copies or tuples.
- **Treating `_` or `__` as security**: anyone can read them; secrets need real protection (not keeping them at all, or a secret manager).
- **`cached_property` on data that changes**: the cached value goes stale; delete the attribute (`del obj.failures`) or use a plain property.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Property me kabhi na khatam hone wali recursion**: `self._port = value` ke bajaye `self.port = value` karne wala setter khud ko hamesha bulata hai.
- **Sust ya side effects wali properties**: parhne wale attribute rasai ko sasta samajhte hain; network calls ke liye method (`fetch_status()`) lein.
- **Andar ki lists ya dicts lautana**: bulane wale aap ke qaidon se guzre baghair unhe badal sakte hain; copies ya tuples lautayen.
- **`_` ya `__` ko security samajhna**: koi bhi parh sakta hai; secrets ko asal hifazat chahiye (unhe rakhna hi nahi, ya secret manager).
- **Badalne wale data par `cached_property`**: cached value purani ho jati hai; attribute delete karein (`del obj.failures`) ya saadi property lein.

</Ur>
</Tr>

## Try it yourself

<Challenge title="A validated User">

<Tr>
<En>
Write `class User` with an `email` property whose setter strips and lower-cases the value and rejects anything without exactly one `@` and a dot after it, a `role` property that only accepts "viewer", "editor" or "admin", and a read-only `is_admin` property. Show that `User(" Jane@Example.COM ", "admin")` normalises the email and that bad values raise ValueError.
</En>
<Ur>
`class User` likhein jis ki `email` property ka setter value strip aur lower-case kare aur jis me bilkul ek `@` aur us ke baad dot na ho use radd kare, `role` property sirf "viewer", "editor" ya "admin" qabool kare, aur read-only `is_admin` property ho. Dikhayen ke `User(" Jane@Example.COM ", "admin")` email normalise karta hai aur ghalat values ValueError deti hain.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
class User:
    ROLES = ("viewer", "editor", "admin")

    def __init__(self, email, role="viewer"):
        self.email = email
        self.role = role

    @property
    def email(self):
        return self._email

    @email.setter
    def email(self, value):
        value = value.strip().lower()
        user, sep, domain = value.partition("@")
        if not user or not sep or "@" in domain or "." not in domain:
            raise ValueError(f"invalid email {value!r}")
        self._email = value

    @property
    def role(self):
        return self._role

    @role.setter
    def role(self, value):
        if value not in self.ROLES:
            raise ValueError(f"invalid role {value!r}")
        self._role = value

    @property
    def is_admin(self):
        return self._role == "admin"

u = User(" Jane@Example.COM ", "admin")
print(u.email, u.role, u.is_admin)
```

<Tr>
<En>

<DeepDive title="More about properties">

**Descriptors.** `property` is a descriptor: an object with `__get__`/`__set__` stored on the class. You can write your own descriptors to reuse validation across many attributes (for example a `PortField` used by several classes).

**Properties in dataclasses.** Combine a dataclass field named `_port` with a property `port`, or validate in `__post_init__`; Pydantic handles this declaratively with validators.

**`__setattr__` guards.** Overriding `__setattr__` can block or log all attribute changes, useful for audit trails, but it affects every assignment and is easy to get wrong.

**Read-only views.** `types.MappingProxyType(self._config)` gives callers a live, read-only view of a dict.

**Python's philosophy.** "We're all consenting adults here": Python trusts developers and relies on conventions; enforce critical rules in code paths that matter, and test them.

</DeepDive>

<DeepDive title="Real world: the discount that went negative">

An online shop's `Order` class had a public `discount` attribute. The checkout code set it from a coupon, and a support tool let staff adjust it. A bug in the support tool allowed a discount larger than the order total, and some orders were charged negative amounts, refunding money to customers' cards.

The fixes:

1. `discount` became a property whose setter rejects values below 0 or above the current subtotal.
2. Discounts can only be applied through `apply_coupon(code)` and `staff_adjust(amount, approved_by)`, both recording an audit entry.
3. A read-only `total` property computes `max(subtotal - discount, 0)`, and payments refuse totals of zero or less without a manual review.

</DeepDive>

<DeepDive title="Security lens">

- **Underscores are not access control**: don't store secrets on objects that get logged or serialised, whatever their names.
- **Validate on every write path**: setters and methods are the single place to enforce limits, roles and formats; validation only in `__init__` is easy to bypass later.
- **Audit sensitive changes inside methods** (who raised a limit, who granted a role) so it can't be skipped.
- **Return read-only views** of permissions, allow-lists and histories so callers can't quietly escalate.
- **Avoid exposing `vars(obj)` or `asdict(obj)` directly** in APIs and logs; choose fields explicitly.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does Python handle private attributes?">
Python has no enforced private attributes. A single leading underscore marks an attribute as internal by convention; a double leading underscore triggers name mangling to `_ClassName__attr` to avoid clashes in subclasses, but both remain accessible.
</QA>

<QA q="What is a property and why use one?">
A property makes method calls look like attribute access, letting a class compute values or validate assignments while keeping a simple interface, and letting you change a plain attribute into managed access later without changing callers.
</QA>

<QA q="How do you create a read-only attribute?">
Define a property with only a getter; assignments then raise AttributeError. Store the underlying value in an internal attribute.
</QA>

<QA q="What is encapsulation?">
Bundling data with the methods that operate on it and hiding internal details behind a clear interface, so the object can maintain its invariants.
</QA>

<QA q="What is cached_property?">
A decorator from functools that computes a property's value on first access and stores it on the instance, so later reads don't recompute it.
</QA>

</DeepDive>
