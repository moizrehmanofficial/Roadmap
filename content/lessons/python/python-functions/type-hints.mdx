<BigIdea>
<Tr>
<En>
Python is dynamically typed: a variable can hold any type and nothing is checked until the code runs. **Type hints** (annotations) let you add the missing information without changing that: `def make_url(host: str, port: int = 443) -> str:` says "host is a string, port an int, and it returns a string". Collections say what they hold: `list[int]`, `dict[str, int]`, `tuple[str, bool]`. A value that may be missing is `str | None`. Functions passed as arguments are `Callable[[int], int]`. Crucially, **Python does not enforce hints at runtime**: the interpreter stores them and moves on, so passing the wrong type still runs. The value comes from **tools**: your editor uses hints for autocomplete and inline warnings, and a **type checker** such as **mypy** or **pyright** reads the whole program and reports mismatches **before** you run it: calling a method on something that might be `None`, passing a `str` where a list was expected, a typo in a dictionary key, a value outside an allowed set. More precise types (`Literal`, `TypedDict`, dataclasses, generics) let the checker catch more. Add hints gradually, starting with function signatures in code that others use.
</En>
<Ur>
Python dynamically typed hai: variable koi bhi type rakh sakta aur code chalne tak kuch check nahi hota. **Type hints** (annotations) ise badle baghair ghayab maloomat jorne dete hain: `def make_url(host: str, port: int = 443) -> str:` kehta hai "host string hai, port int, aur ye string lautata hai". Collections batati hain ke un me kya hai: `list[int]`, `dict[str, int]`, `tuple[str, bool]`. Jo value ghayab ho sakti hai woh `str | None` hai. Arguments ki tarah diye functions `Callable[[int], int]` hain. Ahem baat: **Python runtime par hints lagu nahi karta**: interpreter unhe rakh kar aage barh jata hai, isliye ghalat type dena phir bhi chalta hai. Faida **tools** se aata hai: aap ka editor hints ko autocomplete aur line me warnings ke liye istemal karta, aur **mypy** ya **pyright** jaisa **type checker** poora program parh kar chalane se **pehle** be-mel batata hai: aisi cheez par method bulana jo shayad `None` ho, list ki jagah `str` dena, dictionary key me typo, ijazat yafta set se bahar value. Zyada durust types (`Literal`, `TypedDict`, dataclasses, generics) checker ko zyada pakarne dete hain. Hints dheere dheere jorein, un code ke function signatures se shuru kar ke jo doosre istemal karte hain.
</Ur>

## Picture it

<Tr>
<En>

Think of **labels on electrical plugs and sockets**.

- A label like "230 V, 10 A" on a socket is a type hint: it says what the socket expects.
- Nothing physically stops you from plugging in the wrong device: Python, like the socket, doesn't enforce the label.
- An electrician who walks through the building checking every label against every device before the power is switched on is the type checker.
- `str | None` is a socket labelled "may be switched off": the checker reminds you to check before you plug in.

## Learn it step by step

<Walkthrough>

<Step title="Annotating functions and variables">

<Tr>
<En>
`hints.py` annotates a URL builder (including a keyword-only parameter and a default), functions taking a `list[int]` and a list of `(str, bool)` tuples, a dict variable, a lookup that may return `None`, and a function that takes another function. It calls them normally, prints the stored annotations, and then deliberately passes the wrong types.
</En>
<Ur>
`hints.py` URL banane wale function (keyword-only parameter aur default samait), `list[int]` aur `(str, bool)` tuples ki list lene wale functions, dict variable, `None` lauta sakne wala lookup, aur doosra function lene wale function ko annotate karti hai. Unhe aam tareeqe se bulati, mehfooz annotations print karti, aur phir jaan boojh kar ghalat types deti hai.
</Ur>
</Tr>

```bash
cat > hints.py <<'EOF'
from collections.abc import Callable

# Annotations describe what a function expects and returns
def make_url(host: str, port: int = 443, *, tls: bool = True) -> str:
    return f"{'https' if tls else 'http'}://{host}:{port}"

# Built-in collections take the item type in brackets
def total_size(sizes: list[int]) -> int:
    return sum(sizes)

def failures_by_user(events: list[tuple[str, bool]]) -> dict[str, int]:
    counts: dict[str, int] = {}               # variables can be annotated too
    for user, ok in events:
        if not ok:
            counts[user] = counts.get(user, 0) + 1
    return counts

# "This or None": X | None (older code writes Optional[X])
def find_user(users: dict[int, str], user_id: int) -> str | None:
    return users.get(user_id)

# Functions as arguments: Callable[[argument types], return type]
def apply_all(values: list[int], func: Callable[[int], int]) -> list[int]:
    return [func(v) for v in values]

print(make_url("example.test"), total_size([1024, 2048]))
print(failures_by_user([("jane", False), ("john", True), ("jane", False)]))
print(find_user({1: "jane"}, 1), find_user({1: "jane"}, 2), apply_all([1, 2, 3], lambda x: x * 10))

# Hints are stored, but NOT enforced when the program runs
print(make_url.__annotations__)
print(total_size([1.5, 2.5]), make_url(host=8080, port="eighty"))   # wrong types, still runs!
EOF
python3 hints.py
```

```text output
https://example.test:443 3072
{'jane': 2}
jane None [10, 20, 30]
{'host': <class 'str'>, 'port': <class 'int'>, 'tls': <class 'bool'>, 'return': <class 'str'>}
4.0 https://8080:eighty
```

<Happened>
<Tr>
<En>

- With correct arguments, everything behaved normally: hints don't change how code runs.
- `counts: dict[str, int] = {}` annotated a variable, useful when it starts empty and the checker can't guess the types.
- `find_user` returned **None** for a missing ID, exactly as `-> str | None` promised. A type checker would force callers to handle that case before calling string methods on the result.
- `Callable[[int], int]` described the `func` parameter: a function taking an int and returning an int, which the lambda satisfied.
- `make_url.__annotations__` showed the hints are stored on the function: libraries like FastAPI, Pydantic and dataclasses read them at runtime.
- `total_size([1.5, 2.5])` returned **4.0** and `make_url(host=8080, port="eighty")` produced the nonsense **https://8080:eighty** with **no error**. Python doesn't check hints; that's the type checker's job, in the next step.

</En>
<Ur>

- Sahi arguments ke saath sab aam tareeqe se chala: hints code chalne ka tareeqa nahi badalte.
- `counts: dict[str, int] = {}` ne variable annotate kiya, kaam ka jab woh khaali shuru ho aur checker types ka andaza na laga sake.
- `find_user` ne ghayab ID ke liye **None** lautaya, bilkul jaise `-> str | None` ne wada kiya tha. Type checker bulane walon ko natije par string methods bulane se pehle ye soorat sambhalne par majboor karta.
- `Callable[[int], int]` ne `func` parameter bayan kiya: int le kar int lautane wala function, jo lambda ne poora kiya.
- `make_url.__annotations__` ne dikhaya ke hints function par mehfooz hain: FastAPI, Pydantic aur dataclasses jaisi libraries unhe runtime par parhti hain.
- `total_size([1.5, 2.5])` ne **4.0** lautaya aur `make_url(host=8080, port="eighty")` ne be-maani **https://8080:eighty** **baghair error** ke banaya. Python hints check nahi karta; ye type checker ka kaam hai, agle qadam me.

</Ur>
</Tr>
</Happened>

<Step title="Richer types, and mypy catching real bugs">

<Tr>
<En>
`typed_app.py` uses a type alias (`type Port = int`), a `Literal` for severities, a `TypedDict` describing a finding, a dataclass, and a generic function `first[T]`. It contains three bugs on purpose: indexing a value that may be `None`, passing a string where a list of ports is expected, and an invalid severity. We run it with Python, then check it with **mypy** (run on demand with `uvx`).
</En>
<Ur>
`typed_app.py` type alias (`type Port = int`), severities ke liye `Literal`, finding bayan karne wali `TypedDict`, dataclass, aur generic function `first[T]` istemal karti hai. Is me jaan boojh kar teen bugs hain: aisi value ko index karna jo `None` ho sakti hai, ports ki list ki jagah string dena, aur ghalat severity. Hum ise Python se chalate, phir **mypy** (`uvx` se maang par chala kar) se check karte hain.
</Ur>
</Tr>

```bash
cat > typed_app.py <<'EOF'
from dataclasses import dataclass
from typing import Literal, TypedDict

type Port = int                                   # a type alias (Python 3.12+ syntax)
Severity = Literal["low", "medium", "high"]       # only these exact strings

class Finding(TypedDict):                         # the expected shape of a JSON-like dict
    host: str
    port: Port
    severity: Severity

@dataclass
class Host:
    name: str
    open_ports: list[Port]

def first[T](items: list[T]) -> T | None:         # generic: returns the same type it gets
    return items[0] if items else None

def risky(host: Host) -> list[Finding]:
    return [{"host": host.name, "port": p, "severity": "high"} for p in host.open_ports if p in (23, 3389)]

def summary(findings: list[Finding]) -> str:
    worst = first(findings)
    return f"{len(findings)} findings, first on port {worst['port']}"   # bug: worst may be None

web = Host("web1", [22, 23, 443])
print(summary(risky(web)))
print(len(risky(Host("db1", "5432"))))           # bug: a str instead of list[int]
bad: Finding = {"host": "web2", "port": 22, "severity": "critical"}   # bug: not an allowed severity
EOF
python3 typed_app.py                              # Python itself runs it without complaint
echo "--- mypy reads the hints and finds the bugs without running anything:"
uvx -q mypy@2.4.1 --no-error-summary --hide-error-context typed_app.py | sed 's/^typed_app.py://'
```

```text output
1 findings, first on port 23
0
--- mypy reads the hints and finds the bugs without running anything:
25: error: Value of type "Finding | None" is not indexable  [index]
29: error: Argument 2 to "Host" has incompatible type "str"; expected "list[int]"  [arg-type]
30: error: Incompatible types (expression has type "Literal['critical']", TypedDict item "severity" has type "Literal['low', 'medium', 'high']")  [typeddict-item]
```

<Happened>
<Tr>
<En>

- Python ran the script **without complaint**: the example data happened to avoid the `None` case, and `"5432"` is iterable, so the port loop just looked at characters and found **0** risky ports. All three bugs were silent.
- mypy found all three **without running the code**:
  - line 25: `first()` returns `Finding | None`, so `worst['port']` **may crash** when there are no findings. The fix is to check `if worst is None:` first; after that check, mypy narrows the type to `Finding`.
  - line 29: `Host("db1", "5432")` passes a **str** where `list[int]` is expected.
  - line 30: `"critical"` isn't one of the `Literal` severities, caught because the dict was declared as a `Finding`.
- `def first[T](items: list[T]) -> T | None` (Python 3.12+ syntax) tells the checker that `first` returns the same type as the list's items, which is how it knew `worst` was a `Finding`.
- Run the checker in your editor and in CI so these errors block merges, just like failing tests.

</En>
<Ur>

- Python ne script **baghair shikayat** chalayi: misaal ke data ne ittefaqan `None` wali soorat se bachaya, aur `"5432"` iterable hai, isliye port loop ne bas characters dekhe aur **0** khatarnak ports paye. Teeno bugs khamosh the.
- mypy ne teeno **code chalaye baghair** dhoonde:
  - line 25: `first()` `Finding | None` lautata hai, isliye jab koi finding na ho to `worst['port']` **crash ho sakta** hai. Hal pehle `if worst is None:` check karna hai; us check ke baad mypy type ko `Finding` tak mehdood kar deta hai.
  - line 29: `Host("db1", "5432")` `list[int]` ki jagah **str** deta hai.
  - line 30: `"critical"` `Literal` severities me se nahi, pakra gaya kyunke dict ko `Finding` bataya gaya tha.
- `def first[T](items: list[T]) -> T | None` (Python 3.12+ syntax) checker ko batata hai ke `first` list ke items wali type hi lautata hai, isi tarah use pata tha ke `worst` `Finding` hai.
- Checker ko editor aur CI me chalayen taa ke ye errors fail hote tests ki tarah merges rokein.

</Ur>

## Common mistakes

<Compare>
<Bad title="Believing hints validate input">

```text
def set_port(port: int) -> None:
    config["port"] = port

set_port(request.args["port"])   # a str from the URL; nothing stops it at runtime
```

</Bad>
<Good title="Validate at the boundary, hint the rest">

```text
def parse_port(text: str) -> int:
    port = int(text)                       # raises ValueError on bad input
    if not 1 <= port <= 65535:
        raise ValueError(f"port out of range: {port}")
    return port

set_port(parse_port(request.args["port"]))
```

</Good>
</Compare>

<Compare>
<Bad title="Ignoring the None in an optional return">

```text
def find_user(user_id: int) -> User | None: ...

user = find_user(7)
print(user.email)        # mypy: Item "None" of "User | None" has no attribute "email"
```

</Bad>
<Good title="Narrow first">

```text
user = find_user(7)
if user is None:
    raise LookupError("user 7 not found")
print(user.email)        # the checker knows user is a User here
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`Any` everywhere**: it silences the checker; use specific types or `object`.
- **Old-style imports** (`from typing import List, Dict, Optional`): modern Python uses `list[int]`, `dict[str, int]`, `X | None`.
- **Wrong hints that "work" because nobody runs a checker**: hints that are never checked go stale; run mypy or pyright in CI.
- **`# type: ignore` to make errors disappear** without a comment explaining why.
- **Over-annotating obvious locals** (`count: int = 0`); let the checker infer them.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Har jagah `Any`**: checker ko khamosh karta; khaas types ya `object` lein.
- **Purane andaaz ke imports** (`from typing import List, Dict, Optional`): jadeed Python `list[int]`, `dict[str, int]`, `X | None` istemal karta hai.
- **Ghalat hints jo is liye "chalte" hain ke koi checker nahi chalata**: kabhi check na hone wale hints purane ho jate; CI me mypy ya pyright chalayen.
- **Errors ghayab karne ke liye `# type: ignore`** baghair wajah ke comment ke.
- **Wazeh locals ko zarurat se zyada annotate karna** (`count: int = 0`); checker ko andaza lagane dein.

</Ur>
</Tr>

<Challenge title="Annotate and check">

<Solution>

<Tr>
<En>

```text
type Entry = tuple[str, int]

def parse(line: str) -> Entry:
    parts = line.split()
    return parts[0], int(parts[-1])

def errors(entries: list[Entry]) -> list[str]:
    return [ip for ip, status in entries if status >= 500]

def worst(entries: list[Entry]) -> Entry | None:
    return max(entries, key=lambda e: e[1], default=None)

entries = [parse("203.0.113.7 GET / 500"), parse("192.0.2.1 GET / 200")]
print(errors(entries), worst(entries))
errors(["203.0.113.7"])        # mypy: List item 0 has incompatible type "str"; expected "tuple[str, int]"

# ['203.0.113.7'] ('203.0.113.7', 500)   then the last line fails at runtime too, with ValueError
```

</En>

<DeepDive title="More about typing">

**Protocols.** `typing.Protocol` describes "anything with these methods" (structural typing), so a function can accept any object with a `.read()` method without inheritance.

**Strictness.** `mypy --strict` or pyright's strict mode requires hints everywhere and forbids implicit `Any`; enable it gradually per module.

**Runtime use of hints.** Dataclasses, Pydantic, FastAPI and Typer read annotations to generate fields, validation, API schemas and CLI options.

**Annotations evaluation.** Since Python 3.14, annotations are evaluated lazily, so forward references to classes defined later no longer need quotes.

**Stubs.** Libraries without hints can ship separate `.pyi` stub files (often `types-...` packages on PyPI) so checkers understand them.

</DeepDive>

<DeepDive title="Real world: the None that reached production">

A billing job had `def get_customer(id) -> Customer` that actually returned `None` for deleted customers, but nobody had run a type checker and the hint lied. A nightly invoice run hit a deleted customer, crashed on `customer.email`, and left half the invoices unsent.

The fixes:

1. Correct the hint to `-> Customer | None`.
2. Run mypy in CI; it immediately flagged six call sites that ignored the `None` case.
3. Handle each site explicitly: skip and log deleted customers in the invoice run.
4. Test data now includes deleted customers.

</DeepDive>

<DeepDive title="Security lens">

- **Hints are not validation**: never rely on `port: int` to stop malicious input; parse and check values at the boundary (or use Pydantic).
- **Literal and enums for security-relevant values** (roles, actions, severities) make invalid values visible to the checker.
- **`Any` hides unsafe flows**: data typed as `Any` can reach dangerous calls without the checker noticing; keep untrusted data typed as `str` until validated.
- **NewType for tainted versus clean data**: `SafeHtml = NewType("SafeHtml", str)` lets the checker enforce that only escaped strings reach templates.
- **Type checking in CI** is a cheap extra safety net for refactors in security-sensitive code.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Are type hints enforced at runtime?">
No. CPython stores annotations but doesn't check them; static type checkers like mypy and pyright analyse them, and some libraries such as Pydantic use them for runtime validation.
</QA>

<QA q="How do you annotate a value that can be None?">
With a union, X | None (or Optional[X] in older code), and then check for None before using it so the checker can narrow the type.
</QA>

<QA q="What is a TypedDict and when would you use it?">
A way to declare the expected keys and value types of a dictionary, useful for JSON-like data passed around as dicts, so a checker can catch missing or misspelled keys and wrong value types.
</QA>

<QA q="What are generics?">
Types parameterised by other types, such as list[int], and functions or classes written with type variables so the relationship between input and output types is preserved, for example def first[T](items: list[T]) -> T.
</QA>

<QA q="What's the benefit of adding type hints to a dynamic language?">
Earlier detection of bugs, better editor support and documentation, and safer refactoring, while keeping Python's flexibility because hints are optional and gradual.
</QA>

</DeepDive>
