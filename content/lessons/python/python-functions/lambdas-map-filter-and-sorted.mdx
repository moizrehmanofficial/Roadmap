<BigIdea>
<Tr>
<En>
A **lambda** is a small, unnamed function written as an expression: `lambda u: u[1]` means "take `u`, return `u[1]`". It can have parameters but only **one expression** (no statements, no assignments), and it returns that expression's value. Lambdas exist for one main reason: many functions take **another function as an argument**, and writing a full `def` for a one-line rule is overkill. The most important of these is **`key=`** in `sorted()`, `list.sort()`, `min()` and `max()`: the key function turns each item into the value to compare, so you can sort users by failures, hosts by CPU, or names ignoring case. You can also pass **existing functions** directly (`key=str.casefold`, `map(int, texts)`) or use **`operator.itemgetter` / `attrgetter`**. **`map(func, items)`** applies a function to every item and **`filter(func, items)`** keeps the items for which it returns something truthy; both are **lazy**, like generator expressions. In modern Python, a **comprehension** is usually clearer than `map`/`filter` with a lambda, while `key=` with a lambda remains the everyday idiom. When a lambda grows complex or needs a name, write a `def`.
</En>
<Ur>
**Lambda** expression ki shakal me likha chhota, be-naam function hai: `lambda u: u[1]` ka matlab "`u` lo, `u[1]` lautao". Is ke parameters ho sakte magar sirf **ek expression** (statements nahi, assignments nahi), aur ye usi expression ki value lautata hai. Lambdas ki asal wajah ek hai: bohot se functions **doosre function ko argument** ki tarah lete hain, aur ek line ke qaide ke liye poora `def` likhna zarurat se zyada hai. In me sab se ahem `sorted()`, `list.sort()`, `min()` aur `max()` ka **`key=`** hai: key function har item ko muqable wali value me badalta hai, isliye aap users ko nakamiyon se, hosts ko CPU se, ya naamon ko case nazar andaz kar ke sort kar sakte hain. Aap **mojooda functions** seedhe bhi de sakte hain (`key=str.casefold`, `map(int, texts)`) ya **`operator.itemgetter` / `attrgetter`** istemal kar sakte hain. **`map(func, items)`** har item par function lagata aur **`filter(func, items)`** woh items rakhta hai jin ke liye truthy lautaye; dono generator expressions ki tarah **sust** hain. Jadeed Python me lambda wale `map`/`filter` se aam taur par **comprehension** zyada wazeh hai, jabke lambda wala `key=` roz ka tareeqa hai. Jab lambda pecheeda ho jaye ya naam chahiye ho to `def` likhein.
</Ur>

## Picture it

<Tr>
<En>

Think of **asking a helper to sort a pile of files**.

- `sorted()` is the helper; `key=` is the sticky note you give them: "sort by the date in the top corner".

- `map` is "stamp every file with today's date"; `filter` is "keep only the ones marked urgent".

## Learn it step by step

<Walkthrough>

<Step title="Lambdas as key functions, and map and filter">

<Tr>
<En>
`lambdas.py` compares a lambda with an equivalent `def`, sorts user tuples by one field and by two fields (one descending), picks max and min records, uses `itemgetter` and `attrgetter` as ready-made keys, sorts names with `str.casefold`, converts and filters ports with `map` and `filter`, shows that `map` objects are lazy and single-use, and finishes with the comprehension equivalents.
</En>
<Ur>
`lambdas.py` lambda ko barabar `def` se milati, user tuples ko ek field aur do fields (ek ulta) se sort karti, max aur min records chunti, `itemgetter` aur `attrgetter` ko tayyar keys ki tarah istemal karti, naamon ko `str.casefold` se sort karti, `map` aur `filter` se ports badalti aur filter karti, dikhati hai ke `map` objects sust aur ek dafa ke hain, aur comprehension ke barabar versions par khatam hoti hai.
</Ur>
</Tr>

```bash
cat > lambdas.py <<'EOF'
from operator import itemgetter, attrgetter
from typing import NamedTuple

# A lambda is a small, unnamed function: lambda PARAMETERS: EXPRESSION
double = lambda x: x * 2                  # works, but a def is clearer when you need a name
def double_def(x):
    return x * 2
print(double(21), double_def(21), (lambda a, b: a + b)(2, 3))

# Lambdas shine as short arguments to other functions, especially key=
users = [("jane", 7, "admin"), ("john", 2, "viewer"), ("ana", 7, "viewer"), ("bob", 0, "admin")]
print(sorted(users, key=lambda u: u[1]))                     # by failures
print(sorted(users, key=lambda u: (-u[1], u[0])))            # failures desc, then name
print(max(users, key=lambda u: u[1])[0], min(users, key=lambda u: len(u[0]))[0])
print(sorted(users, key=itemgetter(2, 0)))                   # operator.itemgetter: same idea, faster

class Host(NamedTuple):
    name: str
    cpu: float
hosts = [Host("web1", 71.5), Host("db1", 93.0), Host("web2", 12.25)]
print([h.name for h in sorted(hosts, key=attrgetter("cpu"), reverse=True)])

names = ["ana", "Zed", "bob", "Ana"]
print(sorted(names), sorted(names, key=str.casefold))        # pass an existing function too

# map: apply a function to every item. filter: keep items where the function is truthy.
ports_text = ["22", "80", "443", "8080"]
ports = list(map(int, ports_text))
print(ports, list(filter(lambda p: p < 1024, ports)))
print(list(map(lambda h: h.name.upper(), hosts)), list(filter(None, ["a", "", "b", None, "c"])))

# map and filter are lazy, like generator expressions
m = map(int, ["1", "2"])
print(type(m).__name__, list(m), list(m))

# The same with comprehensions (usually preferred when you'd need a lambda)
print([int(p) for p in ports_text], [p for p in ports if p < 1024])
EOF
python3 lambdas.py
```

<Tr>
<En>

- `double = lambda x: x * 2` and `def double_def` gave the same **42**. Assigning a lambda to a name works, but PEP 8 (and ruff's E731) prefers a `def`, which has a real name in tracebacks.
- `key=lambda u: u[1]` sorted by failures, and `key=lambda u: (-u[1], u[0])` sorted by failures **descending** and then name: the tuple key with a minus sign is the standard trick for mixed directions. Ties (jane and ana with 7) were broken by name.
- `max(..., key=...)` returned the **whole record** with the most failures (**jane**, the first of the tied ones), not just the number.
- `itemgetter(2, 0)` sorted by role then name, and `attrgetter("cpu")` by the `cpu` field of named tuples: the same as lambdas, slightly faster, and easy to read.
- Plain `sorted(names)` put **'Ana'** and **'Zed'** before lowercase names; `key=str.casefold` gave a case-insensitive order. Any one-argument function can be a key.
- `map(int, ...)` converted text to ints, `filter(lambda p: p < 1024, ...)` kept privileged ports, and `filter(None, ...)` dropped every falsy item (empty strings and `None`).
- A `map` object is lazy: the first `list(m)` used it up and the second was **empty**. The comprehensions on the last line did the same jobs and read more naturally.

</En>
<Ur>

- `double = lambda x: x * 2` aur `def double_def` ne wahi **42** diya. Lambda ko naam se assign karna chalta hai, magar PEP 8 (aur ruff ka E731) `def` ko tarjeeh deta hai, jis ka tracebacks me asal naam hota hai.
- `key=lambda u: u[1]` ne nakamiyon se sort kiya, aur `key=lambda u: (-u[1], u[0])` ne nakamiyon ko **ulti tarteeb** aur phir naam se: minus ke nishan wali tuple key mili jhuli simton ki standard tarkeeb hai. Barabari (7 wale jane aur ana) naam se tooti.
- `max(..., key=...)` ne sab se zyada nakamiyon wala **poora record** (**jane**, barabar walon me pehla) lautaya, sirf number nahi.
- `itemgetter(2, 0)` ne role phir naam se sort kiya, aur `attrgetter("cpu")` ne named tuples ke `cpu` field se: lambdas jaisa, thora tez, aur parhne me aasaan.
- Saade `sorted(names)` ne **'Ana'** aur **'Zed'** ko chhote haroof walon se pehle rakha; `key=str.casefold` ne case nazar andaz karne wali tarteeb di. Koi bhi ek argument wala function key ban sakta hai.
- `map(int, ...)` ne text ko ints banaya, `filter(lambda p: p < 1024, ...)` ne privileged ports rakhe, aur `filter(None, ...)` ne har falsy item (khaali strings aur `None`) gira diya.
- `map` object sust hai: pehle `list(m)` ne use khatam kiya aur doosra **khaali** tha. Aakhri line ki comprehensions ne wahi kaam kiye aur zyada qudrati parhe gaye.

<Step title="A pipeline, reduce, any/all, partial and lambda limits">

<Tr>
<En>
`pipeline.py` counts failed logins per IP with `filter` then `map` then `Counter`, and again with a single generator expression. It finds the two slowest events, ranks users by event count, sums durations with `reduce` and with `sum`, checks conditions with `any` and `all`, uses `functools.partial` to make a "slower than 100 ms" test without a lambda, and shows the SyntaxError you get when a lambda tries to contain a statement.
</En>
<Ur>
`pipeline.py` `filter` phir `map` phir `Counter` se har IP ke failed logins ginti, aur dobara ek generator expression se. Do sab se sust events dhoondti, users ko events ki ginti se darja deti, `reduce` aur `sum` se durations jorti, `any` aur `all` se shartein check karti, lambda ke baghair "100 ms se sust" test banane ke liye `functools.partial` istemal karti, aur dikhati hai ke lambda me statement rakhne ki koshish par SyntaxError milta hai.
</Ur>
</Tr>

```bash
cat > pipeline.py <<'EOF'
from collections import Counter
from functools import reduce, partial

events = [
    {"user": "jane", "ip": "203.0.113.7", "ok": False, "ms": 120},
    {"user": "john", "ip": "198.51.100.4", "ok": True, "ms": 80},
    {"user": "jane", "ip": "203.0.113.7", "ok": False, "ms": 95},
    {"user": "ana", "ip": "192.0.2.10", "ok": False, "ms": 300},
    {"user": "ana", "ip": "203.0.113.7", "ok": True, "ms": 60},
]

# filter -> map -> count, as a small pipeline
failed = filter(lambda e: not e["ok"], events)
ips = map(lambda e: e["ip"], failed)
print(Counter(ips).most_common())

# The comprehension version reads more naturally in Python
print(Counter(e["ip"] for e in events if not e["ok"]).most_common())

# Sorting dictionaries by a value, and dict items by value
print([e["user"] for e in sorted(events, key=lambda e: e["ms"], reverse=True)][:2])
per_user = Counter(e["user"] for e in events)
print(sorted(per_user.items(), key=lambda kv: (-kv[1], kv[0])))

# reduce folds a sequence into one value (sum/max/any/all are usually clearer)
print(reduce(lambda acc, e: acc + e["ms"], events, 0), sum(e["ms"] for e in events))

# any / all with a function-style condition
print(any(e["ms"] > 250 for e in events), all(e["ip"].count(".") == 3 for e in events))

# partial: pre-fill arguments instead of writing a lambda
def over(limit, event):
    return event["ms"] > limit
slow = list(filter(partial(over, 100), events))
print(len(slow), [e["user"] for e in slow])

# Lambdas can only hold ONE expression: no statements, no assignments
for code in ["lambda x: return x", "lambda x: y = x"]:
    try:
        compile(code, "<example>", "eval")
    except SyntaxError as e:
        print("SyntaxError:", e.msg)
EOF
python3 pipeline.py
```

```text output
[('203.0.113.7', 2), ('192.0.2.10', 1)]
['ana', 'jane']
[('ana', 2), ('jane', 2), ('john', 1)]
655 655
True True
2 ['jane', 'ana']
SyntaxError: invalid syntax
SyntaxError: invalid syntax
```

<Tr>
<En>

- The `filter` then `map` pipeline and the one-line generator expression gave the same answer: **203.0.113.7 twice, 192.0.2.10 once**. Both are lazy; the comprehension version is the more common Python style.
- Sorting dicts with `key=lambda e: e["ms"]` found the slowest events (**ana, jane**), and sorting `Counter.items()` by `(-count, name)` ranked users with ties in alphabetical order.
- `reduce(lambda acc, e: acc + e["ms"], events, 0)` and `sum(e["ms"] for e in events)` both gave **655**; the `sum` version is clearer. Reach for `reduce` only when no built-in fits.
- `any` found an event over 250 ms, and `all` confirmed every IP had four parts.
- `partial(over, 100)` created a one-argument function "is this event over 100 ms?" from a two-argument one, finding **jane and ana**.
- Putting `return` or an assignment inside a lambda is a **SyntaxError**: a lambda is one expression. If you need statements, write a `def`.

</En>
<Ur>

- `filter` phir `map` wali pipeline aur ek line ke generator expression ne wahi jawab diya: **203.0.113.7 do dafa, 192.0.2.10 ek dafa**. Dono sust hain; comprehension wala version Python ka zyada aam andaaz hai.

## Common mistakes

<Compare>
<Bad title="Lambda soup">

```text
result = list(map(lambda x: x.strip().lower(), filter(lambda x: x and not x.startswith("#"),
                  map(lambda l: l.split("=")[0], lines))))
```

</Bad>
<Good title="A comprehension (or a named function)">

```text
keys = [line.split("=")[0] for line in lines]
result = [k.strip().lower() for k in keys if k and not k.startswith("#")]
```

</Good>
</Compare>

<Compare>
<Bad title="Wrapping a function in a pointless lambda">

```text
sorted(names, key=lambda n: str.lower(n))
list(map(lambda t: int(t), texts))
```

</Bad>
<Good title="Pass the function itself">

```text
sorted(names, key=str.lower)
list(map(int, texts))
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Expecting `map`/`filter` to return lists**: wrap them in `list()` if you need a list, and remember they're single-use.
- **Calling the key function**: `key=str.lower()` is wrong; pass `key=str.lower` (no parentheses).
- **Lambdas in loops capturing the loop variable** late (see Scope and Closures).
- **Using `reduce` where `sum`, `max`, `any`, `all` or `"".join` fit**.
- **Sorting by a key that can be `None` for some items**: comparing None with numbers raises TypeError; handle it in the key (`key=lambda x: x or 0`).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`map`/`filter` se lists ki tawaqqo**: list chahiye to `list()` me lapetein, aur yaad rakhein ye ek dafa ke hain.
- **Key function ko bulana**: `key=str.lower()` ghalat hai; `key=str.lower` dein (qausen ke baghair).
- **Loops me lambdas jo loop variable der se pakrein** (Scope and Closures dekhein).
- **Jahan `sum`, `max`, `any`, `all` ya `"".join` bane wahan `reduce`**.
- **Aisi key se sort jo kuch items ke liye `None` ho**: None ko numbers se milana TypeError deta; key me sambhalein (`key=lambda x: x or 0`).

</Ur>
</Tr>

<DeepDive title="More about functional tools">

**Sort stability.** Python's sort is stable, so you can also sort in passes: first by the secondary key, then by the primary, each with its own `reverse`.

**itertools.** `groupby` (after sorting), `accumulate` (running totals), `starmap`, `takewhile`, `dropwhile` and `chain` combine well with key functions.

**operator module.** `operator.add`, `mul`, `methodcaller("strip")` and the getters replace many small lambdas.

**functools.cache and lru_cache.** Memoise a pure function's results; combined with small functions they speed up repeated work.

**Readability.** Python's creator moved `reduce` to `functools` because explicit loops and built-ins are usually clearer; favour clarity over cleverness.

</DeepDive>

<DeepDive title="Real world: the leaderboard that lied">

A security dashboard ranked "riskiest users" with `sorted(users, key=lambda u: u["risk"], reverse=True)[:10]`. Some users had no risk score yet, stored as `None`. On a busy day the job crashed with `TypeError: '<' not supported between instances of 'float' and 'NoneType'`. A quick fix, `key=lambda u: u["risk"] or 0`, hid unscored users at the bottom, where nobody looked, including a newly compromised account still being scored.

The fixes:

1. Separate unscored users and list them explicitly as "pending score".
2. A key that sorts `None` deliberately: `key=lambda u: (u["risk"] is None, -(u["risk"] or 0))`.
3. Tests with missing, zero and maximum scores.

</DeepDive>

<DeepDive title="Security lens">

- **Never build lambdas or functions from user input** with `eval`; pick from a fixed dict of allowed functions instead.
- **Sorting untrusted data with complex keys** can be slow or raise errors on unexpected types; validate first.
- **`filter` and comprehension predicates** are a clean place to apply allow-list checks before data goes further.
- **Hidden failures in lazy pipelines**: errors surface only when the data is consumed, possibly far from the bug; consume in a clear place with error handling.
- **Ranking by risk or failures** is a common security report; make sure missing data is visible, not sorted away.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a lambda and what are its limitations?">
An anonymous function defined with a single expression. It can't contain statements such as return, assignments or loops, and it has no name in tracebacks, so complex or reused logic should use def.
</QA>

<QA q="How does the key argument of sorted work?">
sorted calls the key function once per item and compares the returned values instead of the items, so you can sort by a field, a computed value or a tuple of values.
</QA>

<QA q="map and filter versus comprehensions?">
They do the same transformations and filtering. map and filter are handy with existing functions like int, while comprehensions are usually more readable when the logic would need a lambda. All are lazy except list comprehensions.
</QA>

<QA q="What does functools.partial do?">
It returns a new callable with some positional or keyword arguments of an existing function already filled in.
</QA>

<QA q="How do you sort by two keys in different directions?">
Use a tuple key and negate numeric fields that should be descending, or sort twice using stability, first by the secondary key and then by the primary key.
</QA>

</DeepDive>
