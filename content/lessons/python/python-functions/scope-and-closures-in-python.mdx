<BigIdea>
<Tr>
<En>
A **scope** is a region of code where a name is visible. When Python meets a name, it searches four scopes in order, the **LEGB rule**: **Local** (inside the current function), **Enclosing** (inside any function that contains this one), **Global** (the module's top level) and **Built-in** (names like `len` and `print`). The first match wins. Reading a global from inside a function just works. **Assigning** is different: if a function assigns to a name anywhere in its body, Python treats that name as **local for the whole function**, so reading it before the assignment raises **UnboundLocalError**. The `global` and `nonlocal` keywords tell Python "this assignment is to the outer name", but in most code it's cleaner to **pass values in and return results out**. Functions defined inside other functions can use the enclosing function's variables even after that function has returned: that's a **closure**. Closures let you build **function factories** (`make_multiplier(1024)`) and give a function **private state** (a counter, a rate limiter) without a class or a global. One trap: closures look a variable up **when they run**, not when they're created, so lambdas created in a loop all see the loop variable's last value unless you capture it.
</En>
<Ur>
**Scope** code ka woh ilaqa hai jahan koi naam nazar aata hai. Jab Python ko koi naam milta hai to woh chaar scopes tarteeb se dhoondta hai, **LEGB qaida**: **Local** (mojooda function ke andar), **Enclosing** (is ko samete kisi bhi function ke andar), **Global** (module ka top level) aur **Built-in** (`len` aur `print` jaise naam). Pehla mel jeet jata hai. Function ke andar se global parhna bas chal jata hai. **Assign** karna alag hai: agar function apne jism me kahin bhi kisi naam ko assign kare, to Python us naam ko **poore function ke liye local** maanta hai, isliye assignment se pehle use parhna **UnboundLocalError** deta hai. `global` aur `nonlocal` keywords Python ko batate hain "ye assignment bahar wale naam ko hai", magar zyadatar code me **values andar dena aur natije bahar lautana** zyada saaf hai. Doosre functions ke andar bane functions us bahar wale function ke variables istemal kar sakte hain, us ke lautne ke baad bhi: yahi **closure** hai. Closures **function factories** (`make_multiplier(1024)`) banane aur function ko class ya global ke baghair **niji state** (counter, rate limiter) dene dete hain. Ek jaal: closures variable ko **chalne ke waqt** dhoondte hain, banne ke waqt nahi, isliye loop me bani lambdas sab loop variable ki aakhri value dekhti hain jab tak aap use pakad na lein.
</Ur>

## Learn it step by step

<Walkthrough>

<Step title="LEGB, UnboundLocalError, global and shadowing">

<Tr>
<En>
`scope.py` defines the same name at three levels and prints it from each, reads a global constant inside a function, tries to increment a global without declaring it, does it with `global`, compares that with passing and returning, mutates a global set without `global`, and finally shadows the built-in `list` and removes the shadow with `del`.
</En>
<Ur>
`scope.py` ek hi naam teen levels par define kar ke har ek se print karti, function ke andar global constant parhti, baghair elaan global badhane ki koshish karti, `global` ke saath karti, use dene aur lautane se milati, `global` ke baghair global set mutate karti, aur aakhir me built-in `list` ko chhupati aur `del` se chhupav hatati hai.
</Ur>
</Tr>

```bash
cat > scope.py <<'EOF'
# Python looks names up in this order: Local -> Enclosing -> Global -> Built-in (LEGB)
level = "global"

def outer():
    level = "enclosing"
    def inner():
        level = "local"
        print("inner sees:", level)
    inner()
    print("outer sees:", level)

outer()
print("module sees:", level)
print("built-in len is found last:", len("abc"))

# Reading a global inside a function is fine...
MAX_ATTEMPTS = 5
def is_locked(failures):
    return failures >= MAX_ATTEMPTS
print(is_locked(6))

# ...but ASSIGNING to a name makes it local for the WHOLE function
counter = 0
def broken_increment():
    counter += 1                      # Python decided `counter` is local, and it has no value yet
try:
    broken_increment()
except UnboundLocalError as e:
    print("UnboundLocalError:", e)

# global lets a function rebind a module-level name (use sparingly)
def increment():
    global counter
    counter += 1
increment(); increment()
print("counter:", counter)

# Better: pass values in and return results out
def incremented(value):
    return value + 1
print(incremented(counter))

# Mutating a global object doesn't need `global` (no rebinding happens)
seen = set()
def remember(ip):
    seen.add(ip)
remember("203.0.113.7")
print(seen)

# Shadowing a built-in hides it
list = ["web1"]                       # now `list` is our variable, not the type
try:
    list("abc")
except TypeError as e:
    print("TypeError:", e)
del list                              # remove our name; the built-in is visible again
print(list("abc"))
EOF
python3 scope.py
```

```text output
inner sees: local
outer sees: enclosing
module sees: global
built-in len is found last: 3
True
UnboundLocalError: cannot access local variable 'counter' where it is not associated with a value
counter: 2
3
{'203.0.113.7'}
TypeError: 'list' object is not callable
['a', 'b', 'c']
```

<Happened>
<Tr>
<En>

- Each function saw its **own nearest** `level`: inner saw "local", outer "enclosing", the module "global". Assigning inside a function creates a new local name; it doesn't touch the outer ones.
- `len` wasn't defined anywhere in our code, so lookup fell through to the **built-in** scope.
- `is_locked` read `MAX_ATTEMPTS` from the global scope without any keyword: **reading** is always allowed.
- `broken_increment` raised **UnboundLocalError**: because `counter += 1` assigns, `counter` was local for the whole function, and the local had no value yet. The global of the same name was never consulted.
- `global counter` made the assignment target the module's name, so two calls left it at **2**. It works, but any function can now change `counter`, which makes bugs hard to trace. `incremented(value)` does the same job by taking a value and returning one.
- `seen.add(...)` changed a global set **without** `global`: it mutates the object; it doesn't rebind the name.
- After `list = [...]`, calling `list("abc")` failed with **'list' object is not callable**; `del list` removed our name and the built-in came back.

</En>
<Ur>

- Har function ne apna **sab se qareebi** `level` dekha: inner ne "local", outer ne "enclosing", module ne "global". Function ke andar assign karna naya local naam banata hai; bahar walon ko nahi chhoota.
- `len` hamare code me kahin define nahi tha, isliye talash **built-in** scope tak gayi.
- `is_locked` ne kisi keyword ke baghair global scope se `MAX_ATTEMPTS` parha: **parhna** hamesha jaaiz hai.
- `broken_increment` ne **UnboundLocalError** diya: kyunke `counter += 1` assign karta hai, `counter` poore function ke liye local tha, aur local ki abhi koi value nahi thi. Usi naam ka global kabhi dekha hi nahi gaya.
- `global counter` ne assignment ko module ke naam ki taraf kiya, isliye do calls ne use **2** par chhora. Ye chalta hai, magar ab koi bhi function `counter` badal sakta hai, jo bugs dhoondna mushkil banata hai. `incremented(value)` value le kar aur lauta kar wahi kaam karta hai.
- `seen.add(...)` ne `global` ke **baghair** global set badla: ye object mutate karta hai; naam rebind nahi karta.
- `list = [...]` ke baad `list("abc")` bulana **'list' object is not callable** se nakam hua; `del list` ne hamara naam hataya aur built-in wapas aa gaya.

</Ur>
</Tr>
</Happened>

<Step title="Closures: factories, private state and late binding">

<Tr>
<En>
`closures.py` builds unit converters with a `make_multiplier` factory and peeks at the remembered value. It creates two independent counters with `nonlocal`, builds a rate limiter that allows 3 calls per 60 seconds and feeds it six timestamps, and finally shows the late-binding trap with lambdas created in a comprehension, plus the default-argument fix.
</En>
<Ur>
`closures.py` `make_multiplier` factory se units badalne wale banati aur yaad rakhi value jhaank kar dekhti hai. `nonlocal` se do alag counters banati, 60 second me 3 calls ki ijazat dene wala rate limiter bana kar use chhe timestamps khilati, aur aakhir me comprehension me bani lambdas ke saath late-binding jaal, aur default-argument wala hal dikhati hai.
</Ur>
</Tr>

```bash
cat > closures.py <<'EOF'
# A closure is an inner function that REMEMBERS variables from the function that created it
def make_multiplier(factor):
    def multiply(x):
        return x * factor              # `factor` comes from the enclosing scope
    return multiply

to_kb, to_mb = make_multiplier(1 / 1024), make_multiplier(1 / 1024 ** 2)
print(to_kb(2048), round(to_mb(5_242_880), 1))
print(to_kb.__closure__[0].cell_contents)          # the remembered value

# nonlocal lets the inner function rebind the remembered variable: a private counter
def make_counter():
    count = 0
    def increment():
        nonlocal count
        count += 1
        return count
    return increment

failed_jane, failed_john = make_counter(), make_counter()
failed_jane(); failed_jane(); failed_john()
print("jane:", failed_jane(), "| john:", failed_john())   # each closure has its own count

# A practical closure: a simple rate limiter with its own memory
def make_limiter(max_calls):
    calls = []
    def allow(now):
        while calls and now - calls[0] >= 60:      # forget calls older than a minute
            calls.pop(0)
        if len(calls) < max_calls:
            calls.append(now)
            return True
        return False
    return allow

allow = make_limiter(3)
print([allow(t) for t in (0, 10, 20, 30, 65, 70)])

# Late binding: closures look the variable up when CALLED, not when created
handlers = [lambda: f"port {port}" for port in (22, 80, 443)]
print([h() for h in handlers])                    # all see the loop's LAST value
handlers = [lambda port=port: f"port {port}" for port in (22, 80, 443)]
print([h() for h in handlers])                    # default argument captures each value
EOF
python3 closures.py
```

```text output
2.0 5.0
0.0009765625
jane: 3 | john: 2
[True, True, True, False, True, True]
['port 443', 'port 443', 'port 443']
['port 22', 'port 80', 'port 443']
```

<Happened>
<Tr>
<En>

- `make_multiplier(1 / 1024)` returned a **new function** that still knew its `factor` after `make_multiplier` had finished. `to_kb(2048)` gave **2.0**, and `__closure__` showed the remembered value stored in a "cell".
- Each call to `make_counter()` created a fresh `count`, so jane's counter reached **3** while john's was at **2**: separate private state, no globals, no class. `nonlocal` was needed because `count += 1` rebinds the enclosing name.
- The rate limiter remembered its own `calls` list: the first three calls were **allowed**, the fourth (at 30 s) was **refused**, and once the oldest calls were more than 60 seconds old, calls at 65 s and 70 s were allowed again. That's the core of real rate limiting.
- All three lambdas from the first comprehension returned **port 443**: they look up `port` when called, after the loop has finished. Binding it as a default argument (`port=port`) froze each value at creation time, giving **22, 80, 443**.

</En>
<Ur>

- `make_multiplier(1 / 1024)` ne **naya function** lautaya jo `make_multiplier` ke khatam hone ke baad bhi apna `factor` jaanta tha. `to_kb(2048)` ne **2.0** diya, aur `__closure__` ne "cell" me rakhi yaad wali value dikhayi.
- `make_counter()` ki har call ne taza `count` banaya, isliye jane ka counter **3** tak pohncha jabke john ka **2** par tha: alag niji state, globals nahi, class nahi. `nonlocal` zaroori tha kyunke `count += 1` enclosing naam rebind karta hai.
- Rate limiter ne apni `calls` list yaad rakhi: pehli teen calls ki **ijazat** mili, chauthi (30 s par) **radd** hui, aur jab purani calls 60 second se zyada purani hui to 65 s aur 70 s wali calls ki phir ijazat mili. Asal rate limiting ka dil yahi hai.
- Pehle comprehension ki teeno lambdas ne **port 443** lautaya: woh `port` call ke waqt dhoondti hain, loop khatam hone ke baad. Default argument (`port=port`) ki tarah jorne ne har value banne ke waqt jama di, **22, 80, 443** de kar.

</Ur>

## Common mistakes

<Compare>
<Bad title="Global state for everything">

```text
total = 0
errors = []

def process(line):
    global total
    total += 1
    if "ERROR" in line:
        errors.append(line)
# every caller shares total and errors; tests interfere with each other
```

</Bad>
<Good title="Inputs in, results out">

```text
def process(lines):
    total = 0
    errors = []
    for line in lines:
        total += 1
        if "ERROR" in line:
            errors.append(line)
    return total, errors
```

</Good>
</Compare>

<Compare>
<Bad title="Callbacks in a loop that all see the last value">

```text
buttons = []
for host in ["web1", "web2", "db1"]:
    buttons.append(lambda: restart(host))     # every button restarts db1
```

</Bad>
<Good title="Capture the value">

```text
buttons = []
for host in ["web1", "web2", "db1"]:
    buttons.append(lambda host=host: restart(host))
# or: functools.partial(restart, host)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Naming variables after built-ins**: `list`, `dict`, `str`, `id`, `type`, `input`, `max` silently hide the real thing.
- **Expecting a loop variable to be local to the loop**: in Python it stays defined after the loop, in the function's scope.
- **`global` inside a function to "fix" UnboundLocalError**: usually the real fix is a parameter and a return value.
- **Module-level mutable caches in web apps**: they're shared by every request and user.
- **Forgetting `nonlocal`** when a closure must update its remembered counter.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Built-ins ke naam par variables**: `list`, `dict`, `str`, `id`, `type`, `input`, `max` khamoshi se asal cheez chhupate hain.
- **Loop variable ke loop tak mehdood hone ki tawaqqo**: Python me ye loop ke baad bhi function ke scope me mojood rehta hai.
- **UnboundLocalError "theek" karne ke liye function ke andar `global`**: aam taur par asal hal parameter aur return value hai.
- **Web apps me module level mutable caches**: har request aur user me mushtarak hote hain.
- **`nonlocal` bhoolna** jab closure ko apna yaad rakha counter update karna ho.

</Ur>
</Tr>

<Tr>

```text
    if ip in banned:
        blocked += 1
    return blocked
```

```text
def count_blocked(ips, banned):
    return sum(1 for ip in ips if ip in banned)

for ip in ["203.0.113.7", "192.0.2.1", "203.0.113.7"]:
```

<Challenge title="A prefix logger factory">

<Tr>
<En>
Write `make_logger(prefix)` that returns a function `log(message)` which prints `[prefix #N] message`, where N counts that logger's messages starting at 1. Create loggers for "auth" and "billing" and show they count independently.
</En>
<Ur>
`make_logger(prefix)` likhein jo `log(message)` function lautaye jo `[prefix #N] message` print kare, jahan N us logger ke paighamat 1 se ginta ho. "auth" aur "billing" ke loggers banayen aur dikhayen ke woh alag alag ginte hain.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
def make_logger(prefix):
    n = 0
    def log(message):
        nonlocal n
        n += 1
        print(f"[{prefix} #{n}] {message}")
    return log

auth, billing = make_logger("auth"), make_logger("billing")
auth("login ok")
auth("login failed")
billing("invoice sent")
```

<DeepDive title="More about scope">

**Compile-time decision.** Python decides which names are local when it compiles a function, by scanning for assignments, which is why the error happens even if the assignment line never runs.

**Class bodies.** A class body has its own namespace, but methods don't see class-level names directly; they use `self.name` or `ClassName.name`.

**Comprehension scope.** Comprehensions have their own scope, so their loop variables don't leak, but they can read enclosing names.

**Decorators are closures.** `def decorator(func): def wrapper(*args, **kwargs): ... return wrapper` keeps `func` in the closure.

**Inspecting scopes.** `globals()` and `locals()` return dictionaries of the current names; `func.__code__.co_varnames` lists a function's locals.

</DeepDive>

<DeepDive title="Real world: the request that saw another user's data">

A small Flask service cached the current user's permissions in a module-level variable: `current_perms = load_perms(user)` at the start of each request, read by helper functions later. Under load, two requests on different threads interleaved: one request set `current_perms` for an admin, and before it finished, another request for a normal user read the admin's permissions.

The fixes:

1. Pass the user and permissions explicitly as parameters through the request's call chain.
2. Use the framework's request-scoped context (`flask.g`), which is isolated per request.
3. A load test that runs many users concurrently and checks every response only contains that user's data.

</DeepDive>

<DeepDive title="Security lens">

- **Global mutable state is shared** by all threads, requests and users in a process; never keep per-user data in module variables.
- **Closures can capture secrets**: a function holding an API key in its closure keeps it in memory; don't log or serialise such objects.
- **Shadowing security functions** (`open`, `input`, `hash`) by accident can bypass the behaviour you expect.
- **Rate limiters and counters** built as closures are per process; across several servers you need shared storage (Redis).
- **Late-binding bugs** in callbacks (wrong host restarted, wrong user notified) can have real security impact; test them.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the LEGB rule?">
The order Python uses to resolve names: Local scope, then Enclosing function scopes, then the module's Global scope, then Built-ins; the first match is used.
</QA>

<QA q="What causes UnboundLocalError?">
A function assigns to a name somewhere in its body, making it local, and the code reads it before that assignment runs; the global with the same name isn't used.
</QA>

<QA q="What is the difference between global and nonlocal?">
global makes assignments target the module-level name; nonlocal makes them target the nearest enclosing function's name. Both are only needed for rebinding, not mutation.
</QA>

<QA q="What is a closure and where are closures used?">
A nested function that keeps references to variables from its enclosing scope after that scope has finished. They're used in decorators, callbacks, factories and for encapsulating small amounts of state.
</QA>

<QA q="Explain late binding in closures.">
Closures look up captured variables when they're called, not when they're defined, so functions created in a loop all see the variable's final value unless the value is bound at creation, for example with a default argument.
</QA>
