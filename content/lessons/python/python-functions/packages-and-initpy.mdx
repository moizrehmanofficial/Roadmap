<BigIdea>
<Tr>
<En>
A **package** is a **folder of modules** that you import with dotted names: `netkit.ports`, `netkit.report.text`. The folder usually contains an **`__init__.py`** file, which marks it as a regular package and **runs the first time** the package is imported. `__init__.py` can be empty, or it can define the package's **public API**: importing the most useful functions from submodules so users can write `from netkit import host_report` instead of digging into the internal layout, plus `__all__` and `__version__`. Inside a package, modules import each other either **absolutely** (`from netkit.ips import is_private`) or **relatively** (`from ..ips import is_private`, where each dot means "one package up"). A **`__main__.py`** file makes the package runnable with **`python -m netkit`**. Relative imports only work when Python knows the file is part of a package, which is why running a file inside a package directly (`python netkit/report/text.py`) fails; use `python -m netkit.report.text` instead. Finally, a **`pyproject.toml`** turns the folder into an **installable project**: `pip install -e .` (or `uv pip install -e .`) makes it importable from anywhere and can create **console commands** that call your functions.
</En>
<Ur>
**Package** **modules ka folder** hai jise dotted naamon se import karte hain: `netkit.ports`, `netkit.report.text`. Folder me aam taur par **`__init__.py`** file hoti hai, jo use aam package ki nishani deti aur package ke pehli dafa import hone par **chalti** hai. `__init__.py` khaali ho sakti hai, ya package ki **public API** bana sakti hai: submodules se sab se kaam ke functions import kar ke taa ke users andar ka dhancha khodne ke bajaye `from netkit import host_report` likhein, saath `__all__` aur `__version__`. Package ke andar modules ek doosre ko ya to **absolute** (`from netkit.ips import is_private`) ya **relative** (`from ..ips import is_private`, jahan har dot ka matlab "ek package upar") import karte hain. **`__main__.py`** file package ko **`python -m netkit`** se chalane layak banati hai. Relative imports tabhi chalte hain jab Python ko pata ho ke file package ka hissa hai, isi liye package ke andar ki file seedhi chalana (`python netkit/report/text.py`) nakam hota hai; is ke bajaye `python -m netkit.report.text` lein. Aakhir me **`pyproject.toml`** folder ko **install hone wala project** banati hai: `pip install -e .` (ya `uv pip install -e .`) use kahin se bhi import hone layak banata aur aap ke functions bulane wali **console commands** bana sakta hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **company with departments**.

- The package is the company building; modules are offices; a subpackage is a department with its own floor.
- `__init__.py` is the reception desk: the first thing that happens when you arrive, and the place that tells visitors "for reports, ask for host_report" so they don't wander the corridors.
- An absolute import is a full address ("netkit building, report floor, text office"); a relative import is "the office one floor up".
- `__main__.py` is the front door you use when you visit the company itself rather than a particular office.
- Installing the package is listing the company in the city directory, so anyone anywhere can find it by name.

</En>

## Learn it step by step

<Walkthrough>

<Step title="Build a package with a subpackage, an API and __main__.py">

<Tr>
<En>
We build `netkit` with two modules (`ips`, `ports`), a `report` subpackage whose `text.py` uses relative imports, an `__init__.py` that re-exports the main functions and prints a line when it runs, and a `__main__.py`. `use_it.py` imports the package three ways. Then we run the package with `python -m`, try running `text.py` directly, and list the files.
</En>
<Ur>
Hum do modules (`ips`, `ports`), aisa `report` subpackage jis ki `text.py` relative imports istemal kare, ahem functions re-export karne aur chalne par line print karne wali `__init__.py`, aur `__main__.py` ke saath `netkit` banate hain. `use_it.py` package ko teen tareeqon se import karti hai. Phir hum package ko `python -m` se chalate, `text.py` seedhi chalane ki koshish karte, aur files ki list banate hain.
</Ur>
</Tr>

```bash
# A package is a folder of modules. Layout:
#   netkit/__init__.py  netkit/ips.py  netkit/ports.py  netkit/__main__.py  netkit/report/__init__.py  netkit/report/text.py
mkdir -p netkit/report
cat > netkit/ips.py <<'EOF'
import ipaddress

def is_private(ip):
    return ipaddress.ip_address(ip).is_private
EOF
cat > netkit/ports.py <<'EOF'
RISKY = {21: "ftp", 23: "telnet", 3306: "mysql", 6379: "redis"}

def risky(ports):
    return {p: RISKY[p] for p in ports if p in RISKY}
EOF
cat > netkit/report/__init__.py <<'EOF'
EOF
cat > netkit/report/text.py <<'EOF'
from ..ips import is_private          # relative import: ".." = the parent package (netkit)
from ..ports import risky

def host_report(ip, ports):
    found = risky(ports)
    lines = [f"{ip} ({'private' if is_private(ip) else 'public'})"]
    lines += [f"  risky port {p} ({name})" for p, name in sorted(found.items())] or ["  no risky ports"]
    return "\n".join(lines)
EOF
cat > netkit/__init__.py <<'EOF'
"""netkit: tiny network audit helpers."""
from .ips import is_private               # re-export the main functions at the top level
from .report.text import host_report

__all__ = ["is_private", "host_report"]
__version__ = "0.1.0"
print(f"  [netkit/__init__.py ran]")
EOF
cat > netkit/__main__.py <<'EOF'
import sys
from netkit import host_report
ip, *ports = sys.argv[1:]
print(host_report(ip, [int(p) for p in ports]))
EOF
cat > use_it.py <<'EOF'
import netkit                                   # runs netkit/__init__.py
from netkit.ports import risky                  # absolute import of a submodule
import netkit.report.text as text

print(netkit.__version__, netkit.is_private("10.0.0.5"), risky([22, 23, 6379]))
print(netkit.host_report("8.8.8.8", [22, 443, 3306]))
print(text.host_report is netkit.host_report)
EOF
python3 use_it.py
echo "--- python -m runs the package's __main__.py:"
python3 -m netkit 192.168.1.20 22 21
echo "--- running a file inside the package directly breaks its relative imports:"
python3 netkit/report/text.py 2>&1 | tail -1
find . -name "*.py" -not -path "*/__pycache__/*" | sort
```

```text output
  [netkit/__init__.py ran]
0.1.0 True {23: 'telnet', 6379: 'redis'}
8.8.8.8 (public)
  risky port 3306 (mysql)
True
--- python -m runs the package's __main__.py:
  [netkit/__init__.py ran]
192.168.1.20 (private)
  risky port 21 (ftp)
--- running a file inside the package directly breaks its relative imports:
ImportError: attempted relative import with no known parent package

./netkit/ips.py
./netkit/ports.py
./netkit/report/__init__.py
./netkit/report/text.py
./use_it.py
```

<Happened>
<Tr>
<En>

- `import netkit` ran **`netkit/__init__.py`** once (its print appeared once), which imported the submodules it re-exports. That's why `netkit.is_private` and `netkit.host_report` worked without the user knowing they live in `ips.py` and `report/text.py`.
- `from netkit.ports import risky` and `import netkit.report.text as text` reached into submodules with **absolute** dotted paths. `text.host_report is netkit.host_report` was **True**: re-exporting doesn't copy anything, it's the same function under a shorter name.
- `text.py` used `from ..ips import is_private`: two dots climbed from `netkit.report` to `netkit`. Relative imports keep a package working if you rename or move it as a whole.
- `python -m netkit 192.168.1.20 22 21` ran **`__main__.py`** and found the risky FTP port.
- Running `python netkit/report/text.py` failed with **attempted relative import with no known parent package**: run directly, the file is just a script called `__main__`, not `netkit.report.text`, so `..` means nothing. Use `python -m netkit.report.text` from the project root.
- The standard library's `ipaddress` decided private versus public; it knows ranges such as 10/8, 172.16/12 and 192.168/16 (and treats documentation ranges as non-global), so `8.8.8.8` was **public**.

</En>
<Ur>

- `import netkit` ne **`netkit/__init__.py`** ek dafa chalayi (us ka print ek dafa aaya), jis ne re-export hone wale submodules import kiye. Isi liye `netkit.is_private` aur `netkit.host_report` user ko ye jaane baghair chale ke woh `ips.py` aur `report/text.py` me rehte hain.
- `from netkit.ports import risky` aur `import netkit.report.text as text` **absolute** dotted raaston se submodules tak pohanche. `text.host_report is netkit.host_report` **True** tha: re-export kuch copy nahi karta, ye chhote naam ke saath wahi function hai.
- `text.py` ne `from ..ips import is_private` istemal kiya: do dots `netkit.report` se `netkit` tak chadhe. Relative imports package ko poora naam badalne ya hilane par bhi chalta rakhte hain.
- `python -m netkit 192.168.1.20 22 21` ne **`__main__.py`** chalayi aur khatarnak FTP port dhoonda.
- `python netkit/report/text.py` chalana **attempted relative import with no known parent package** se nakam hua: seedha chalane par file bas `__main__` naam ki script hai, `netkit.report.text` nahi, isliye `..` ka koi matlab nahi. Project root se `python -m netkit.report.text` lein.
- Private ya public ka faisla standard library ke `ipaddress` ne kiya; woh 10/8, 172.16/12 aur 192.168/16 jaisi ranges jaanta (aur documentation ranges ko ghair global maanta) hai, isliye `8.8.8.8` **public** tha.

</Ur>
</Tr>
</Happened>

<Step title="Make it installable with pyproject.toml">

<Tr>
<En>
We add a `pyproject.toml` with project metadata, a build backend (hatchling) and a `[project.scripts]` entry that turns `netkit.__main__:main` into a command called `netkit-report`. After moving the argument handling into a `main()` function and removing the demo print, we create a virtual environment with uv and do an **editable install**. Then, from a completely different folder, we import netkit and run the new command.
</En>
<Ur>
Hum project metadata, build backend (hatchling) aur `[project.scripts]` entry wali `pyproject.toml` jorte hain jo `netkit.__main__:main` ko `netkit-report` naam ki command banati hai. Arguments ka kaam `main()` function me le jane aur demo print hatane ke baad, hum uv se virtual environment bana kar **editable install** karte hain. Phir bilkul doosre folder se netkit import karte aur nayi command chalate hain.
</Ur>
</Tr>

```bash
# Make netkit installable: a pyproject.toml, then an editable install into a virtual environment
cat > pyproject.toml <<'EOF'
[project]
name = "netkit"
version = "0.1.0"
requires-python = ">=3.12"

[project.scripts]
netkit-report = "netkit.__main__:main"     # creates a command that calls netkit.__main__.main()

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
EOF
cat > netkit/__main__.py <<'EOF'
import sys
from netkit import host_report

def main():
    ip, *ports = sys.argv[1:]
    print(host_report(ip, [int(p) for p in ports]))

if __name__ == "__main__":
    main()
EOF
sed -i '/__init__.py ran/d' netkit/__init__.py           # remove the demo print
uv venv -q .venv && uv pip install -q --python .venv/bin/python -e .
cd /tmp                                                    # somewhere else entirely
"$OLDPWD/.venv/bin/python" -c 'import netkit; print("imported from anywhere:", netkit.__version__, netkit.is_private("172.16.5.4"))'
"$OLDPWD/.venv/bin/netkit-report" 8.8.8.8 23 443
cd "$OLDPWD"
.venv/bin/python -c 'import netkit, os; print("code lives in:", os.path.relpath(netkit.__file__))'
```

```text output
imported from anywhere: 0.1.0 True
8.8.8.8 (public)
  risky port 23 (telnet)
code lives in: netkit/__init__.py
```

<Happened>
<Tr>
<En>

- After the editable install, `import netkit` worked from **/tmp**, far from the project folder, with no `PYTHONPATH`: the package is registered in the venv's site-packages and points back at the source.
- **Editable** means changes to the `.py` files take effect immediately without reinstalling, which is what you want while developing. A normal install copies the code into site-packages.
- `[project.scripts]` created **`.venv/bin/netkit-report`**, a real command that calls `main()`: this is how tools like `ruff`, `black` and `pytest` provide their commands.
- `netkit.__file__` confirmed the code is loaded from the project's own `netkit/__init__.py`.
- `requires-python` and a version number are the minimum metadata; dependencies go in `dependencies = [...]`, which `uv add` and `pip install` respect. The next module, Packages and Environments, goes deeper.

</En>
<Ur>

- Editable install ke baad `import netkit` project folder se door **/tmp** se, `PYTHONPATH` ke baghair chala: package venv ke site-packages me darj hai aur source ki taraf ishara karta hai.
- **Editable** ka matlab `.py` files ki tabdeeliyan dobara install kiye baghair foran asar karti hain, jo development ke dauran chahiye. Aam install code ko site-packages me copy karta hai.
- `[project.scripts]` ne **`.venv/bin/netkit-report`** banayi, asal command jo `main()` bulati hai: isi tarah `ruff`, `black` aur `pytest` jaise tools apni commands dete hain.
- `netkit.__file__` ne tasdeeq ki ke code project ki apni `netkit/__init__.py` se load hota hai.
- `requires-python` aur version number kam se kam metadata hain; dependencies `dependencies = [...]` me jati hain, jinhe `uv add` aur `pip install` maante hain. Agla module, Packages and Environments, mazeed gehra jata hai.

</Ur>

## Common mistakes

<Compare>
<Bad title="Running files inside a package as scripts">

```text
cd netkit/report
python text.py           # ImportError: attempted relative import with no known parent package
# "fixed" by adding sys.path hacks at the top of every file
```

</Bad>
<Good title="Run modules with -m from the project root">

```text
cd myproject
python -m netkit.report.text
python -m netkit 8.8.8.8 22
# or install the project (pip install -e .) and use its entry points
```

</Good>
</Compare>

<Compare>
<Bad title="A heavy, side-effect-full __init__.py">

```text
# netkit/__init__.py
import pandas, boto3, requests            # slow imports for everyone
CONFIG = load_config_from_network()       # network call on import
logging.basicConfig(level="DEBUG")        # changes the app's logging
```

</Bad>
<Good title="A small __init__.py that defines the API">

```text
# netkit/__init__.py
"""netkit: tiny network audit helpers."""
from .ips import is_private
from .report.text import host_report

__all__ = ["is_private", "host_report"]
__version__ = "0.1.0"
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Naming the package like an existing library** (`requests`, `test`, `email`): it shadows or gets shadowed.
- **Mixing relative and absolute styles randomly**: choose one per project.
- **Circular imports through `__init__.py`**: submodules importing `from netkit import x` while `__init__` imports them; import from the submodule directly.
- **Forgetting `__init__.py` in a subfolder** and wondering why tools treat it differently (it becomes a namespace package).
- **Committing `.venv`, `__pycache__`, `*.egg-info` or `dist/`**: add them to `.gitignore`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Package ka naam mojooda library jaisa** (`requests`, `test`, `email`): chhupata hai ya chhup jata hai.
- **Relative aur absolute andaaz be-tarteeb milana**: har project ke liye ek chunein.
- **`__init__.py` ke zariye circular imports**: submodules `from netkit import x` karein jabke `__init__` unhe import kare; seedha submodule se import karein.
- **Subfolder me `__init__.py` bhoolna** aur hairan hona ke tools use alag kyun samajhte hain (ye namespace package ban jata hai).
- **`.venv`, `__pycache__`, `*.egg-info` ya `dist/` commit karna**: unhe `.gitignore` me jorein.

</Ur>
</Tr>

<DeepDive title="More about packages">

**src layout.** Putting the package under `src/` stops Python from importing it from the current folder by accident, so tests run against the installed package; most modern templates use it.

**Namespace packages.** Folders without `__init__.py` can form one package spread across several locations (PEP 420), used by large organisations to split a namespace across distributions.

**Build backends.** hatchling, setuptools, flit, pdm-backend and uv's own backend turn a `pyproject.toml` project into wheels; `uv build` or `python -m build` creates them for publishing.

**Package data.** Non-Python files (templates, JSON schemas) are read with `importlib.resources.files("netkit") / "data.json"`, which works even from zipped installs.

**Versioning.** `importlib.metadata.version("netkit")` reads the installed version, which avoids keeping `__version__` in two places.

</DeepDive>

<DeepDive title="Real world: the import that only worked in one folder">

A security team's scanner was a folder of scripts that imported each other by plain names. It worked when run from its own folder, and a cron job did `cd /opt/scanner && python scan.py`. When a new teammate ran it from their home directory, or CI ran tests from the repo root, imports failed, and someone added `sys.path.insert(0, ...)` lines to every file, which then imported the wrong `config.py` from another project on one server.

The fixes:

1. Restructure into a `src/scanner/` package with relative imports and a `pyproject.toml`.
2. An entry point `scanner = "scanner.cli:main"`, installed with `pip install -e .` on developer machines and a normal install on servers.
3. Remove every `sys.path` hack; CI installs the package and runs `pytest`.

</DeepDive>

<DeepDive title="Security lens">

- **Package import executes code**, including `__init__.py`; installing a malicious package runs its build and import code, so vet dependencies.
- **Dependency confusion**: an internal package name that also exists on public PyPI can be hijacked; use unique names and configure your package index carefully.
- **Avoid `sys.path` hacks**: inserting writable or relative directories can let attackers plant modules that get imported instead of yours.
- **Entry points run with the user's permissions**; tools that need privileges should drop them or be clearly separated.
- **Don't ship secrets in package data**; wheels are easy to unpack.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a module and a package?">
A module is a single Python file; a package is a directory of modules (usually with an `__init__.py`) imported with dotted names, possibly containing subpackages.
</QA>

<QA q="What is __init__.py used for?">
It marks a regular package, runs when the package is first imported, and is commonly used to define the package's public API, `__all__` and version; it can be empty.
</QA>

<QA q="Relative vs absolute imports?">
Absolute imports use the full dotted path from the top-level package; relative imports use dots relative to the current package. Relative imports only work inside packages, not in scripts run directly.
</QA>

<QA q="What does python -m do?">
It finds a module or package by import name and runs it as `__main__`, setting up sys.path so package-relative imports work; for a package it runs its `__main__.py.`
</QA>

<QA q="What is an editable install?">
An installation that registers the project in the environment but points at the source directory, so code changes take effect without reinstalling; created with pip install -e or uv pip install -e.
</QA>

</DeepDive>
