<BigIdea>
<Tr>
<En>
A **function** is a named block of code that does one job. You **define** it once with `def name(parameters):` and an indented body, and **call** it as many times as you like with `name(arguments)`. **Parameters** are the names in the definition; **arguments** are the values you pass when calling. Inside, **`return value`** hands a result back to the caller and ends the function immediately; a function that never reaches `return` gives back **`None`**. That's the key difference from `print()`: printing shows text to a person, returning gives a value to the rest of your program. Parameters can have **default values** (`port=443`), making them optional. A **docstring** under the `def` line documents what the function does. Functions are **values** too: you can store them in variables and dicts, and pass them to other functions. Good functions are **small**, do **one thing**, have a clear name (a verb: `parse_line`, `is_failed_login`) and, when possible, are **pure**: their result depends only on their inputs and they don't change anything outside. Pure, small functions are easy to understand, reuse and **test**.
</En>
<Ur>
**Function** code ka naam wala block hai jo ek kaam karta hai. Aap ise `def name(parameters):` aur indent jism ke saath ek dafa **define** karte, aur `name(arguments)` se jitni dafa chahein **call** karte hain. **Parameters** definition ke naam hain; **arguments** woh values hain jo call karte waqt dete hain. Andar **`return value`** natija bulane wale ko wapas deta aur function foran khatam karta hai; jo function kabhi `return` tak na pohanche woh **`None`** lautata hai. Yahi `print()` se ahem farq hai: print insaan ko text dikhata hai, return baqi program ko value deta hai. Parameters ki **default values** ho sakti hain (`port=443`), jo unhe ikhtiyari banati hain. `def` line ke neeche **docstring** batati hai ke function kya karta hai. Functions **values** bhi hain: unhe variables aur dicts me rakh sakte aur doosre functions ko de sakte hain. Ache functions **chhote** hote, **ek kaam** karte, wazeh naam rakhte (fail: `parse_line`, `is_failed_login`) aur jahan mumkin ho **pure** hote hain: un ka natija sirf inputs par mabni hota aur woh bahar kuch nahi badalte. Pure, chhote functions samajhna, dobara istemal karna aur **test** karna aasaan hai.
</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="def, return, defaults and functions as values">

<Tr>
<En>
`basics.py` defines and calls `greet`, compares a function that prints with one that returns, builds URLs with defaults and keyword arguments, classifies status codes with several `return` statements, returns three values at once, stores small functions in a dict and passes one to another function, reads a function's name and docstring, and calls a function with a missing argument.
</En>
<Ur>
`basics.py` `greet` define aur call karti, print karne wale function ko return karne wale se milati, defaults aur keyword arguments se URLs banati, kayi `return` statements se status codes ki darja bandi karti, ek saath teen values lautati, chhote functions dict me rakh kar ek ko doosre function ko deti, function ka naam aur docstring parhti, aur ghayab argument ke saath function call karti hai.
</Ur>
</Tr>

```bash
cat > basics.py <<'EOF'
# def NAME(PARAMETERS): an indented body. Calling it runs the body.
def greet(name):
    """Return a greeting for name."""
    return f"Hello, {name}!"

message = greet("Jane")                  # "Jane" is the argument; name is the parameter
print(message, greet("John"))

# return gives a value back; print only shows text
def shout(text):
    print(text.upper())                  # shows something, returns None
result = shout("deploy done")
print("shout returned:", result)

# A parameter with a default value is optional
def make_url(host, port=443, scheme="https"):
    return f"{scheme}://{host}:{port}"
print(make_url("example.test"), make_url("example.test", 8080), make_url("example.test", scheme="http", port=80))

# Several return statements: the first one reached ends the function
def classify(status):
    if status >= 500:
        return "server error"
    if status >= 400:
        return "client error"
    return "ok"
print([classify(s) for s in (200, 404, 503)])

# Return several values (a tuple), unpack at the call
def stats(values):
    return min(values), max(values), sum(values) / len(values)
low, high, avg = stats([120, 80, 300, 95])
print(low, high, avg)

# Functions are values: store them, pass them, call them later
checks = {"ok": lambda code: code < 400, "error": lambda code: code >= 400}
def count_matching(codes, test):
    return sum(1 for c in codes if test(c))
print(count_matching([200, 404, 500, 301], checks["error"]), greet.__name__, greet.__doc__)

# Calling with the wrong number of arguments
try:
    greet()
except TypeError as e:
    print("TypeError:", e)
EOF
python3 basics.py
```

```text output
Hello, Jane! Hello, John!
DEPLOY DONE
shout returned: None
https://example.test:443 https://example.test:8080 http://example.test:80
['ok', 'client error', 'server error']
80 300 148.75
2 greet Return a greeting for name.
TypeError: greet() missing 1 required positional argument: 'name'
```

<Happened>
<Tr>
<En>

- `greet("Jane")` **returned** a string, which we stored in `message` and printed; the same function worked for John. Define once, call many times.
- `shout` printed **DEPLOY DONE** but returned **None**: there's no `return` in it. If you need the value later (to save, compare or test), return it; printing is only for people.
- `make_url` used its defaults when we left them out, and keyword arguments (`scheme="http", port=80`) could be given in any order. Defaults keep common calls short.
- `classify` returned as soon as a condition matched, so each status got exactly one label; no `else` was needed after a `return`.
- `stats` returned a **tuple** that we unpacked into `low, high, avg`.
- `count_matching` took a **function** as its second argument and called it for each code. Passing behaviour as an argument is a core Python idea you'll see in `sorted(key=...)`, `map` and callbacks.
- `greet.__name__` and `greet.__doc__` show that functions are objects with attributes, and calling `greet()` without its argument raised a clear **TypeError** naming the missing parameter.

</En>
<Ur>

- `greet("Jane")` ne string **return** ki, jo humne `message` me rakh kar print ki; wahi function John ke liye chala. Ek dafa define, kayi dafa call.
- `shout` ne **DEPLOY DONE** print kiya magar **None** lautaya: us me `return` nahi. Agar value baad me chahiye (save, muqabla ya test ke liye) to return karein; print sirf logon ke liye hai.
- `make_url` ne chhoray gaye defaults istemal kiye, aur keyword arguments (`scheme="http", port=80`) kisi bhi tarteeb me diye ja sakte the. Defaults aam calls chhoti rakhte hain.
- `classify` ne shart milte hi return kiya, isliye har status ko bilkul ek label mila; `return` ke baad `else` ki zaroorat nahi thi.
- `stats` ne **tuple** lautaya jise humne `low, high, avg` me khola.
- `count_matching` ne apne doosre argument ki tarah **function** liya aur har code ke liye use bulaya. Rawaiya argument ki tarah dena Python ka bunyadi khayal hai jo aap `sorted(key=...)`, `map` aur callbacks me dekhenge.
- `greet.__name__` aur `greet.__doc__` dikhate hain ke functions attributes wale objects hain, aur argument ke baghair `greet()` bulane ne ghayab parameter ka naam lene wala wazeh **TypeError** diya.

</Ur>

<Step title="Designing with functions: a report, tests and recursion">

<Tr>
<En>
`report.py` turns the failed-login report from earlier lessons into five small functions: `parse_line` (one line to a tuple, or None for garbage), `is_failed_login` (a pure yes/no check), `count_failures`, `format_report` and `main`. Before running the report, a few `assert` lines test the pieces, including a garbage line and an empty result. Finally, `count_leaves` uses recursion to count every plain value in a nested config, however deep it goes.
</En>
<Ur>
`report.py` pichhle lessons ki failed-login report ko paanch chhote functions me badalti hai: `parse_line` (ek line se tuple, ya kachre ke liye None), `is_failed_login` (pure haan/nahi check), `count_failures`, `format_report` aur `main`. Report chalane se pehle chand `assert` lines hisson ko test karti hain, kachra line aur khaali natija samait. Aakhir me `count_leaves` recursion se nested config ki har saadi value ginta hai, chahe kitni gehri ho.
</Ur>
</Tr>

```bash
cat > access.log <<'EOF'
203.0.113.7 - - [23/Nov/2026:10:15:32 +0000] "POST /login HTTP/1.1" 401 512
198.51.100.4 - - [23/Nov/2026:10:15:33 +0000] "POST /login HTTP/1.1" 401 512
203.0.113.7 - - [23/Nov/2026:10:15:35 +0000] "POST /login HTTP/1.1" 401 512
203.0.113.9 - - [23/Nov/2026:10:15:40 +0000] "GET /api/orders HTTP/1.1" 200 2048
this line is garbage
203.0.113.7 - - [23/Nov/2026:10:15:41 +0000] "POST /login HTTP/1.1" 401 512
EOF
cat > report.py <<'EOF'
"""Failed-login report, split into small functions that each do one job."""
from collections import Counter


def parse_line(line):
    """Return (ip, method, path, status) or None if the line isn't a log entry."""
    parts = line.split()
    if len(parts) < 9 or not parts[8].isdigit():
        return None
    return parts[0], parts[5].strip('"'), parts[6], int(parts[8])


def is_failed_login(entry):
    """Pure function: depends only on its input, changes nothing."""
    _, method, path, status = entry
    return method == "POST" and path == "/login" and status == 401


def count_failures(lines):
    entries = (parse_line(l) for l in lines)
    return Counter(e[0] for e in entries if e and is_failed_login(e))


def format_report(counts, threshold=3):
    rows = [f"{ip:<15} {n:>3}{'  <- block' if n >= threshold else ''}" for ip, n in counts.most_common()]
    return "\n".join(rows) or "no failed logins"


def main(path):
    with open(path, encoding="utf-8") as f:
        print(format_report(count_failures(f)))


# Small functions are easy to test
assert parse_line("this line is garbage") is None
assert parse_line('1.2.3.4 - - [d +0000] "GET / HTTP/1.1" 200 10') == ("1.2.3.4", "GET", "/", 200)
assert is_failed_login(("1.2.3.4", "POST", "/login", 401))
assert not is_failed_login(("1.2.3.4", "GET", "/login", 401))
assert format_report(Counter()) == "no failed logins"
print("all checks passed")

if __name__ == "__main__":
    main("access.log")
EOF
python3 report.py

# Recursion: a function that calls itself, here to count values in nested config of any depth
python3 - <<'EOF'
def count_leaves(data):
    if isinstance(data, dict):
        return sum(count_leaves(v) for v in data.values())
    if isinstance(data, list):
        return sum(count_leaves(v) for v in data)
    return 1                                  # base case: a plain value
config = {"web": {"ports": [80, 443], "tls": {"cert": "a.pem", "key": "a.key"}}, "debug": False}
print("leaf values:", count_leaves(config))
EOF
```

```text output
all checks passed
203.0.113.7       3  <- block
198.51.100.4      1
leaf values: 5
```

<Happened>
<Tr>
<En>

- Each function does **one job**, and `main` reads like a sentence: format the report of the failures counted in the file. If the log format changes, only `parse_line` changes.
- `parse_line` returned **None** for "this line is garbage" instead of crashing, and `count_failures` skipped it with `if e`. Handling bad input at the edge keeps the rest simple.
- `is_failed_login` is **pure**: no files, no printing, just input to output. That made it trivial to test with two `assert` lines.
- **all checks passed** printed before the report: if any assertion had been false, Python would have stopped with an AssertionError pointing at that line. You'll replace these quick checks with pytest later, but the habit is the same.
- The report flagged **203.0.113.7** with 3 failures and a `<- block` marker, using the `threshold=3` default.
- `count_leaves` called itself for every dict and list, and returned 1 at the **base case** (a plain value), counting **5** values in the nested config. Every recursive function needs a base case, or it recurses until Python raises RecursionError.

</En>
<Ur>

- Har function **ek kaam** karta, aur `main` jumle ki tarah parhta hai: file me gini nakamiyon ki report format karo. Log ka format badle to sirf `parse_line` badalta hai.
- `parse_line` ne "this line is garbage" ke liye crash ke bajaye **None** lautaya, aur `count_failures` ne `if e` se use chhora. Kinare par kharab input sambhalna baqi ko saada rakhta hai.
- `is_failed_login` **pure** hai: files nahi, print nahi, sirf input se output. Is se do `assert` lines se test karna aasaan hua.
- Report se pehle **all checks passed** print hua: agar koi assertion jhooti hoti to Python us line ki taraf ishara karte AssertionError ke saath ruk jata. Baad me aap in jaldi checks ki jagah pytest lenge, magar aadat wahi hai.
- Report ne `threshold=3` default se **203.0.113.7** ko 3 nakamiyon aur `<- block` nishan ke saath mark kiya.
- `count_leaves` ne har dict aur list ke liye khud ko bulaya, aur **base case** (saadi value) par 1 lautaya, nested config me **5** values gin kar. Har recursive function ko base case chahiye, warna Python ke RecursionError dene tak recursion chalta hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Printing instead of returning">

```text
def total_size(sizes):
    print(sum(sizes))

if total_size([1024, 2048]) > 2000:     # TypeError: '>' not supported between instances of 'NoneType' and 'int'
    alert()
```

</Bad>
<Good title="Return the value; print at the edge">

```text
def total_size(sizes):
    return sum(sizes)

size = total_size([1024, 2048])
print(size)
if size > 2000:
    alert()
```

</Good>
</Compare>

<Compare>
<Bad title="One function that does everything">

```text
def run():
    # 80 lines: read the file, parse, filter, count, format, email the report,
    # write a CSV, clean up temp files...
```

</Bad>
<Good title="Small named steps">

```text
def run(path):
    entries = parse_file(path)
    failures = count_failures(entries)
    report = format_report(failures)
    send_report(report)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting the parentheses**: `greet` is the function object, `greet()` calls it.
- **Using a variable from outside instead of a parameter**: pass what the function needs; hidden inputs make it hard to test.
- **Mutable default arguments** (`def f(items=[])`): use `None` (see Mutability and Copying).
- **Returning different types for success and failure** without saying so: document it, or raise an exception for errors.
- **Defining a function after the line that calls it** at the top level of a script: Python runs top to bottom, so call it after the `def`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Qausen bhoolna**: `greet` function object hai, `greet()` use bulata hai.
- **Parameter ke bajaye bahar ka variable istemal karna**: function ko jo chahiye de; chhupe inputs test karna mushkil banate hain.
- **Mutable default arguments** (`def f(items=[])`): `None` lein (Mutability and Copying dekhein).
- **Kamyabi aur nakami par mukhtalif types lautana** baghair bataye: document karein, ya errors ke liye exception raise karein.
- **Script ke top level par function ko bulane wali line ke baad define karna**: Python upar se neeche chalta hai, isliye `def` ke baad bulayen.

</Ur>
</Tr>

<Tr>
<En>
Write `valid_port(value)` that accepts an int or a string, returns the port as an int if it's a whole number from 1 to 65535, and returns `None` otherwise (including for "abc", "0", "70000" and " 443 " with spaces, which should be accepted after stripping). Add `assert` checks for at least five cases.
</En>
<Ur>

</Ur>

<Solution>

<Tr>
<En>

```text
def valid_port(value):
    """Return value as an int port (1-65535), or None if it isn't one."""
    text = str(value).strip()
    if not text.isdigit():
        return None
    port = int(text)
    return port if 1 <= port <= 65535 else None

assert valid_port(443) == 443
assert valid_port(" 443 ") == 443
assert valid_port("abc") is None
assert valid_port("0") is None
assert valid_port("70000") is None
assert valid_port("-5") is None
print("valid_port ok")

# valid_port ok
```

<DeepDive title="More about functions">

**First-class functions.** Functions can be assigned, stored in data structures, passed and returned; this enables callbacks, decorators and dispatch tables.

**Defaults are evaluated once.** At definition time, which is why mutable defaults are shared and why `def f(when=datetime.now())` freezes the time.

**Recursion limits.** CPython limits recursion depth (about 1000 by default, `sys.getrecursionlimit()`); for very deep structures use an explicit stack and a loop.

**Generators.** A function with `yield` produces values lazily; you'll see them with iterators.

**Testing.** `assert` statements are stripped when Python runs with `-O`, so don't use them for runtime validation in production code; use them for tests and invariants, and move tests to pytest.

</DeepDive>

<DeepDive title="Real world: the script nobody could change">

A 600-line monitoring script grew over two years as one long sequence of statements. When the log format changed, the parsing logic turned out to be duplicated in four places, two of which were missed, so some alerts silently stopped. Nobody wanted to touch it because there was no way to test any part separately.

The fixes:

1. Extract one `parse_line` function used everywhere, with tests for each known log format.
2. Split the rest into functions for checks, thresholds and notifications, each with a docstring.
3. Keep side effects (reading files, sending alerts) at the edges in `main`, and the logic pure in between.
4. Add pytest tests for the pure functions to CI, so future format changes are caught immediately.

</DeepDive>

<DeepDive title="Security lens">

- **Centralise security logic in one function** (input validation, permission checks, escaping) so it's applied consistently and fixed in one place.
- **Validate at the boundary**: functions that receive external data should reject bad input early with a clear result or exception.
- **Don't rely on `assert` for security checks**: they disappear with `python -O`; use `if` and raise.
- **Avoid hidden global state** in functions that handle different users or requests.
- **Recursion on untrusted nested data** (JSON) can hit recursion limits; limit depth or use iterative processing.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between return and print?">
return passes a value back to the caller and ends the function; print writes text to standard output and returns None. Functions should usually return values and leave printing to the caller.
</QA>

<QA q="What is a pure function and why is it useful?">
A function whose output depends only on its inputs and which causes no side effects. It's predictable, easy to test, safe to reuse and easy to reason about.
</QA>

<QA q="What does it mean that functions are first-class objects in Python?">
They can be assigned to variables, stored in collections, passed as arguments and returned from other functions, just like any other value.
</QA>

<QA q="What happens with a function that returns several values?">
It returns a single tuple, which the caller can unpack into several names.
</QA>

<QA q="When would you use recursion?">
For naturally recursive structures such as trees, nested data and directory hierarchies, with a clear base case, keeping depth limits in mind.
</QA>

</DeepDive>
