<BigIdea>
<Tr>
<En>
A **module** is simply a `.py` file. Its functions, classes and variables become available to other code through **`import`**. There are three common styles: `import netutils` (then write `netutils.describe(...)`, which keeps it clear where a name comes from), `from netutils import describe` (bring specific names in directly) and `import numpy as np` (an alias for long names). The first time a module is imported, Python **runs its top-level code once**, creates a module object and stores it in **`sys.modules`**; later imports reuse that cached object. Inside the module, **`__name__`** is the module's name when imported, but `"__main__"` when the file is run directly, which is why the `if __name__ == "__main__":` guard works. To find a module, Python searches the folders in **`sys.path`** in order: the folder of the script you ran, then any `PYTHONPATH` folders, the **standard library**, and **site-packages** where pip installs things. The first match wins, which leads to a classic bug: a file of yours called `random.py`, `json.py` or `email.py` **shadows** the standard library module. When nothing matches, you get **ModuleNotFoundError**: usually a typo, a package not installed in the active environment, or running from the wrong folder.
</En>
<Ur>
**Module** bas ek `.py` file hai. Us ke functions, classes aur variables **`import`** ke zariye doosre code ko milte hain. Teen aam andaaz hain: `import netutils` (phir `netutils.describe(...)` likhein, jo wazeh rakhta hai ke naam kahan se aaya), `from netutils import describe` (khaas naam seedhe le aayen) aur `import numpy as np` (lambe naamon ke liye alias). Pehli dafa module import hone par Python **us ka top-level code ek dafa chalata**, module object banata aur use **`sys.modules`** me rakhta hai; baad ke imports usi cached object ko istemal karte hain. Module ke andar **`__name__`** import hone par module ka naam hota hai, magar file seedhi chalane par `"__main__"`, isi liye `if __name__ == "__main__":` guard kaam karta hai. Module dhoondne ke liye Python **`sys.path`** ke folders tarteeb se dekhta hai: jo script chalayi us ka folder, phir `PYTHONPATH` ke folders, **standard library**, aur **site-packages** jahan pip cheezen install karta hai. Pehla mel jeetta hai, jis se mash-hoor bug banta hai: aap ki `random.py`, `json.py` ya `email.py` naam ki file standard library ke module ko **chhupa** deti hai. Jab kuch na mile to **ModuleNotFoundError** milta hai: aam taur par typo, active environment me package install na hona, ya ghalat folder se chalana.
</Ur>

## Picture it

<Tr>
<En>

Think of a **toolbox with labelled drawers**.

- Each module is a drawer. `import netutils` brings the whole drawer to your bench, and you say "the describe tool from the netutils drawer". `from netutils import describe` takes just that one tool out.
- The first time you open a drawer, someone unpacks and sets it up (the module's top-level code runs). After that, it stays on the bench (the cache).
- When you ask for a drawer by name, the helper checks shelves in order: your desk, then the company store, then the shop down the street. If you've labelled one of your own drawers "random", that's the one you get.

</En>

**Label wali daraazon ka toolbox** socheyn.

- Pehli dafa daraaz kholne par koi use khol kar tayyar karta hai (module ka top-level code chalta hai). Us ke baad woh bench par rehti hai (cache).
- Jab aap naam se daraaz maangte hain to madadgar tarteeb se shelves dekhta hai: aap ki desk, phir company ka store, phir gali ki dukaan. Agar aap ne apni kisi daraaz par "random" likh diya hai to wahi milegi.

## Learn it step by step

<Walkthrough>

<Step title="Write a module and import it three ways">

<Tr>
<En>
`netutils.py` is a module with a docstring, a constant, two functions, a print in its top-level code (so we can see when it runs) and a `__main__` guard. `app.py` imports it as a whole, then specific names, then with an alias, checks the module cache, lists the module's public names, and imports a few standard library modules the same way. Finally we run `netutils.py` directly.
</En>
<Ur>
`netutils.py` docstring, constant, do functions, top-level code me ek print (taa ke dekh sakein kab chalta hai) aur `__main__` guard wala module hai. `app.py` ise poora, phir khaas naam, phir alias ke saath import karti, module cache check karti, module ke public naamon ki list banati, aur chand standard library modules ko usi tarah import karti hai. Aakhir me hum `netutils.py` seedha chalate hain.
</Ur>
</Tr>

```bash
# A module is just a .py file. Let's write one.
cat > netutils.py <<'EOF'
"""Small helpers for network scripts."""
print(f"  [netutils top-level code runs, __name__ = {__name__!r}]")

DEFAULT_PORTS = (22, 80, 443)

def is_private(ip):
    return ip.startswith(("10.", "192.168.")) or ip.startswith(tuple(f"172.{n}." for n in range(16, 32)))

def describe(ip):
    return f"{ip} is {'private' if is_private(ip) else 'public'}"

if __name__ == "__main__":
    print(describe("10.0.0.5"))       # runs only when executed directly
EOF
cat > app.py <<'EOF'
import netutils                                   # 1. import the module, use module.name
print(netutils.describe("203.0.113.7"), netutils.DEFAULT_PORTS)

from netutils import is_private, DEFAULT_PORTS    # 2. import specific names
print(is_private("192.168.1.10"), DEFAULT_PORTS)

import netutils as nu                             # 3. an alias
print(nu is netutils)                             # same module object: imported only once

import sys
print("cached in sys.modules:", "netutils" in sys.modules)
print("public names:", [n for n in dir(netutils) if not n.startswith("_")])
print("docstring:", netutils.__doc__, "| file:", netutils.__file__.rsplit("/", 1)[-1])

# Standard library modules work the same way
import json, math
from datetime import date
from pathlib import Path
print(json.dumps({"ok": True}), math.ceil(4.2), date(2026, 11, 23).isoformat(), Path("logs/app.log").suffix)
EOF
python3 app.py
echo "--- running the module directly:"
python3 netutils.py
```

```text output

True (22, 80, 443)
True
cached in sys.modules: True
public names: ['DEFAULT_PORTS', 'describe', 'is_private']
docstring: Small helpers for network scripts. | file: netutils.py
{"ok": true} 5 2026-11-23 .log
--- running the module directly:
  [netutils top-level code runs, __name__ = '__main__']
```

<Happened>
<Tr>
<En>

- The module's top-level print appeared **only once**, even though `app.py` imported `netutils` three times: the first import ran the file and cached it, and later imports reused the cached module (`nu is netutils` is True, and it's in `sys.modules`).
- When imported, `__name__` was **`'netutils'`**; when we ran the file directly it was **`'__main__'`**, so the guarded `describe("10.0.0.5")` ran only then. That's how a module can double as a small command-line tool.
- `import netutils` meant writing `netutils.describe(...)`, which makes the source obvious; `from netutils import is_private` let us write `is_private(...)` directly. Both are fine; pick clarity.
- `dir(netutils)` listed its public names, and the docstring and `__file__` describe the module.
- Standard library modules (`json`, `math`, `datetime`, `pathlib`) are imported exactly the same way: there's nothing special about them except where they live.

</En>
<Ur>

- Module ka top-level print **sirf ek dafa** aaya, halanke `app.py` ne `netutils` teen dafa import kiya: pehle import ne file chala kar cache ki, aur baad ke imports ne cached module istemal kiya (`nu is netutils` True hai, aur ye `sys.modules` me hai).
- Import hone par `__name__` **`'netutils'`** tha; file seedhi chalane par **`'__main__'`** tha, isliye guard wala `describe("10.0.0.5")` sirf tab chala. Isi tarah module chhota command-line tool bhi ban sakta hai.
- `import netutils` ka matlab `netutils.describe(...)` likhna tha, jo sarchashma wazeh karta hai; `from netutils import is_private` ne seedha `is_private(...)` likhne diya. Dono theek hain; wazahat chunein.
- `dir(netutils)` ne us ke public naam bataye, aur docstring aur `__file__` module bayan karte hain.
- Standard library modules (`json`, `math`, `datetime`, `pathlib`) bilkul isi tarah import hote hain: un me kuch khaas nahi siwaye is ke ke kahan rehte hain.

</Ur>
</Tr>
</Happened>

<Step title="How Python finds modules, and what goes wrong">

<Tr>
<En>
We print the start of `sys.path`, then create a file called `random.py` next to a script that imports `random`, and see what happens before and after removing it. We trigger ModuleNotFoundError with a typo and by running from a different folder, fix the second with `PYTHONPATH`, and import a module twice and then reload it to watch how often its top-level code runs.
</En>
<Ur>
Hum `sys.path` ka shuru print karte, phir `random` import karne wali script ke saath `random.py` naam ki file banate, aur use hatane se pehle aur baad dekhte hain kya hota hai. Typo se aur doosre folder se chala kar ModuleNotFoundError chhedte, doosre ko `PYTHONPATH` se theek karte, aur module do dafa import kar ke phir reload karte hain taa ke dekhein us ka top-level code kitni dafa chalta hai.
</Ur>
</Tr>

```bash
# Where does Python look? sys.path: the script's folder first, then the standard library, then site-packages
python3 -c 'import sys; print([p.rsplit("/", 2)[-1] or p for p in sys.path][:4], "...")'

# 1. Shadowing: a local file named like a standard module wins
mkdir -p shadow && cd shadow
cat > random.py <<'EOF'
print("this is MY random.py, not the standard library!")
EOF
cat > game.py <<'EOF'
import random
print(random.randint(1, 6))
EOF
python3 game.py 2>&1 | sed -n '1p;$p' | sed "s#$PWD/##"
rm random.py && rm -rf __pycache__
python3 -c 'import random; random.seed(1); print("after renaming the file:", random.randint(1, 6))'
cd ..

# 2. ModuleNotFoundError: a typo, a missing install, or the wrong folder
python3 -c 'import netutil' 2>&1 | tail -1
mkdir -p elsewhere && cd elsewhere
python3 -c 'import netutils' 2>&1 | tail -1               # netutils.py is in the parent folder
PYTHONPATH=.. python3 -c 'import netutils; print(netutils.describe("172.20.0.1"))'
cd ..

# 3. Importing runs the module's top-level code once, then uses the cache
python3 -c '
import netutils
import netutils
import importlib
importlib.reload(netutils)
'
```

```text output

this is MY random.py, not the standard library!
AttributeError: module 'random' has no attribute 'randint' (consider renaming 'random.py' since it has the same name as the standard library module named 'random' and prevents importing that standard library module)
after renaming the file: 2

ModuleNotFoundError: No module named 'netutils'

  [netutils top-level code runs, __name__ = 'netutils']
  [netutils top-level code runs, __name__ = 'netutils']
```

<Happened>
<Tr>
<En>

- `sys.path` starts with `''` (the current folder, for `-c`; for a script it's the script's folder), followed by the standard library locations. Your own folder comes **first**.
- Because of that, `import random` loaded **our** `random.py`, which printed its message and had no `randint`. Python 3.13 even suggests renaming the file. After deleting it (and its `__pycache__`), the real module worked. Never name your files after standard or installed modules: `random.py`, `json.py`, `email.py`, `requests.py`, `test.py` are common culprits.
- `import netutil` (a typo) and importing `netutils` from another folder both raised **ModuleNotFoundError**. The module existed, just not on the search path.
- `PYTHONPATH=..` added the parent folder to `sys.path`, so the import worked. It's a quick fix; for real projects, structure code as a package and install it, or run with `python -m` from the project root.
- Importing twice ran the top-level code once; `importlib.reload` ran it **again**. Reloading is handy in a REPL but rarely needed in programs.

</En>
<Ur>

- `sys.path` `''` (mojooda folder, `-c` ke liye; script ke liye script ka folder) se shuru hota, phir standard library ki jagahen. Aap ka apna folder **pehle** aata hai.
- Isi wajah se `import random` ne **hamari** `random.py` load ki, jis ne apna paigham print kiya aur us me `randint` nahi tha. Python 3.13 file ka naam badalne ka mashwara bhi deta hai. Use (aur us ka `__pycache__`) delete karne ke baad asal module chala. Apni files ka naam kabhi standard ya installed modules par na rakhein: `random.py`, `json.py`, `email.py`, `requests.py`, `test.py` aam mujrim hain.
- `import netutil` (typo) aur doosre folder se `netutils` import karna dono ne **ModuleNotFoundError** diya. Module mojood tha, bas talash ke raaste par nahi.
- `PYTHONPATH=..` ne parent folder `sys.path` me jora, isliye import chal gaya. Ye jaldi ka hal hai; asal projects ke liye code ko package banayen aur install karein, ya project root se `python -m` ke saath chalayen.
- Do dafa import ne top-level code ek dafa chalaya; `importlib.reload` ne use **dobara** chalaya. Reload REPL me kaam ka hai magar programs me shayad hi chahiye.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Doing work at import time">

```text
# reports.py
import requests
DATA = requests.get("https://api.example.test/users", timeout=10).json()   # runs on import!
print("loaded", len(DATA))
def summary(): ...
# just importing reports now makes a network call and prints
```

</Bad>
<Good title="Define at import, act when called">

```text
# reports.py
import requests

def load_users():
    return requests.get("https://api.example.test/users", timeout=10).json()

def summary(users): ...

if __name__ == "__main__":
    print(summary(load_users()))
```

</Good>
</Compare>

<Compare>
<Bad title="Star imports">

```text
from os import *
from netutils import *
open("x")          # which open? os has its own open() that takes flags, not a mode string
```

</Bad>
<Good title="Explicit names">

```text
import os
from netutils import describe, is_private
open("x")          # the built-in open, obviously
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Naming a file like a module you use**: `requests.py` breaks `import requests`.
- **Installing a package for one Python and running another**: use `python -m pip install` with the same interpreter, inside the venv.
- **Circular imports** (a imports b, b imports a): move shared code into a third module or import inside a function.
- **Editing `sys.path` in code** to make imports work: fix the project structure instead.
- **Unused imports**: they slow startup and confuse readers; ruff's F401 finds them.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **File ka naam istemal hone wale module jaisa rakhna**: `requests.py` `import requests` tor deti hai.
- **Ek Python ke liye package install kar ke doosra chalana**: venv ke andar usi interpreter ke saath `python -m pip install` lein.
- **Circular imports** (a b ko import kare, b a ko): mushtarak code teesre module me le jayen ya function ke andar import karein.
- **Imports chalane ke liye code me `sys.path` badalna**: is ke bajaye project ka dhancha theek karein.
- **Ghair istemal imports**: startup sust aur parhne walon ko uljhan; ruff ka F401 inhe dhoondta hai.

</Ur>
</Tr>

<Challenge title="Split a script into a module">

<Tr>
<En>
Create `validators.py` with `valid_port(value)` (from the functions lesson) and `valid_ip(text)` that returns True when the text has four dot-separated numbers from 0 to 255. Import both in `check.py`, test five inputs, and make `validators.py` print a self-test result only when run directly.
</En>
<Ur>

<Solution>

<Tr>
<En>

```text
# validators.py
def valid_port(value):
    text = str(value).strip()
    return text.isdigit() and 1 <= int(text) <= 65535

def valid_ip(text):
    parts = text.split(".")
    return len(parts) == 4 and all(p.isdigit() and 0 <= int(p) <= 255 for p in parts)

if __name__ == "__main__":
    assert valid_ip("192.0.2.1") and not valid_ip("999.1.1.1")
    print("validators self-test ok")

# check.py
from validators import valid_ip, valid_port
for value in ["192.0.2.1", "10.0.0", "443", "70000", "256.1.1.1"]:
    print(value, valid_ip(value), valid_port(value))

# python3 check.py
# 192.0.2.1 True False
# 10.0.0 False False
# 443 False True
# 70000 False False
# 256.1.1.1 False False
```

The standard library's `ipaddress.ip_address()` is the robust way to validate IPs; writing it once yourself shows how modules let you reuse such checks everywhere.

</En>

<DeepDive title="More about imports">

**The import system.** Finders locate a module (file, zip, built-in, frozen) and loaders execute it; `importlib.util.find_spec("json")` shows what would be imported.

**Bytecode cache.** Python saves compiled `.pyc` files in `__pycache__` to start faster next time; they're safe to delete and shouldn't be committed.

**`__all__`.** A module can list its public names in `__all__`, which controls `from module import *` and documents the API.

**Lazy imports.** Importing inside a function delays the cost until it's needed and can break circular imports; Python 3.15 adds explicit lazy imports for this.

**Running modules.** `python -m package.module` runs a module with the right `sys.path` for packages; it's the reliable way to run code inside a project.

</DeepDive>

<DeepDive title="Real world: the email module that broke deployments">

A developer added a helper file called `email.py` to a project to format notification messages. Everything worked locally. In production, a library the project depended on did `import email.utils` from the standard library, got the local `email.py` instead, and crashed at startup. The error, `ModuleNotFoundError: No module named 'email.utils'; 'email' is not a package`, sent the team looking at the library for hours.

The fixes:

1. Rename the file to `notifications.py` and delete the stale `__pycache__`.
2. Move application code into a package (`myapp/notifications.py`) so its names can't collide with top-level modules.
3. A CI check that imports the app in a clean environment, catching startup import errors before deploys.

</DeepDive>

<DeepDive title="Security lens">

- **Module shadowing can be an attack**: a malicious `random.py` or `requests.py` dropped into a script's folder (or the current directory) runs when the script imports it. Don't run scripts from untrusted folders, and be careful with writable directories on `sys.path`.
- **Import-time code runs automatically**: importing an untrusted module is the same as running it.
- **Typosquatted packages** on PyPI exploit misspelled imports and installs; double-check names.
- **`PYTHONPATH` and `.pth` files** change what gets imported; attackers with write access to them can hijack programs.
- **Pin and audit dependencies** (`pip-audit`, `uv lock`) since every import of a third-party package runs its code.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What happens when you import a module?">
Python checks sys.modules; if it isn't there, it searches sys.path for it, creates a module object, executes the module's top-level code in that object's namespace, caches it in sys.modules and binds the name in the importing scope.
</QA>

<QA q="What is the purpose of if __name__ == '__main__'?">
It runs code only when the file is executed directly, not when it's imported, so a module can be both importable and runnable.
</QA>

<QA q="import module vs from module import name?">
The first binds the module and you access names through it, which is explicit and avoids clashes; the second binds specific names directly in your namespace, which is shorter but can hide where names come from. Both load the whole module.
</QA>

<QA q="How does Python decide where to find a module?">
It searches the directories in sys.path in order: the script's directory, PYTHONPATH entries, the standard library and site-packages, taking the first match.
</QA>

<QA q="How do you fix a circular import?">
Restructure so shared code lives in a separate module, import inside the function that needs it, or import the module rather than names from it so attributes are resolved later.
</QA>

</DeepDive>
