<BigIdea>
<Tr>
<En>
A **conditional** runs a block of code only when a condition is true. `if condition:` starts it; the block underneath is **indented**. `elif` ("else if") adds more conditions, checked **top to bottom**, and the **first true branch wins**: the rest are skipped. `else` catches everything left over. Conditions are any expressions: comparisons (`status >= 400`), membership (`role in ("admin", "owner")`), truthiness (`if cart:` means "not empty") and combinations with **`and`**, **`or`** and **`not`**. Two habits make conditionals readable: **guard clauses** that handle the special or failing cases first and `return` early, so the main path isn't buried in nesting; and the **conditional expression** `a if condition else b` for simple one-line choices. Since Python 3.10, **`match`** compares a value against **patterns**: exact values, lists of a certain shape (`["scan", host, *ports]`), dictionaries with certain keys, alternatives (`"quit" | "exit"`), extra conditions (**guards**) and a wildcard `_`. It shines when parsing commands, messages and JSON.
</En>
<Ur>
**Conditional** code ka block tabhi chalata hai jab shart sach ho. `if condition:` shuru karta hai; neeche ka block **indent** hota hai. `elif` ("else if") mazeed shartein jorta hai, jo **upar se neeche** check hoti hain, aur **pehli sach shaakh jeet jati hai**: baqi chhor di jati hain. `else` jo bacha sab pakarta hai. Shartein koi bhi expressions hain: muqable (`status >= 400`), mojoodgi (`role in ("admin", "owner")`), truthiness (`if cart:` yani "khaali nahi") aur **`and`**, **`or`** aur **`not`** ke saath jor. Do aadaten conditionals ko parhne layak banati hain: **guard clauses** jo khaas ya nakam soorten pehle sambhal kar jaldi `return` karti hain, taa ke asal raasta nesting me dafan na ho; aur saade ek line ke intekhab ke liye **conditional expression** `a if condition else b`. Python 3.10 se **`match`** kisi value ko **patterns** se milata hai: bilkul values, kisi shakal ki lists (`["scan", host, *ports]`), kuch keys wali dictionaries, mutabadil (`"quit" | "exit"`), izafi shartein (**guards**) aur wildcard `_`. Ye commands, messages aur JSON parse karne me chamakta hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **security checkpoint with several doors in a row**.

- You walk up to the first door: "VIP pass?" If yes, you go through it and never see the other doors. If no, you move on to the next: "Staff badge?" and so on (if, elif).

## Learn it step by step

<Walkthrough>

<Step title="if, elif, else, combined conditions and guard clauses">

<Tr>
<En>
`decide.py` classifies HTTP status codes with an `if/elif/else` chain, then shows a broken version with the branches in the wrong order. `can_login()` applies a login policy using guard clauses and `and`, `not` and `in`, for four users. Finally, a conditional expression describes a cart and a `None` check picks a greeting.
</En>
<Ur>
`decide.py` `if/elif/else` zanjeer se HTTP status codes ki darja bandi karti, phir ghalat tarteeb wali shaakhon ka toota version dikhati hai. `can_login()` guard clauses aur `and`, `not` aur `in` se chaar users par login policy lagata hai. Aakhir me conditional expression cart bayan karta aur `None` check istiqbal chunta hai.
</Ur>
</Tr>

```bash
cat > decide.py <<'EOF'
def classify(status):
    if status >= 500:
        return "server error"
    elif status >= 400:
        return "client error"
    elif status >= 300:
        return "redirect"
    elif status >= 200:
        return "success"
    else:
        return "informational"

for s in [200, 301, 404, 503, 101]:
    print(s, classify(s))

# Order matters: the first true branch wins, the rest are skipped
def bad_classify(status):
    if status >= 200:
        return "success"            # 404 and 503 stop here!
    elif status >= 400:
        return "client error"
    return "other"
print("bad version says 404 is:", bad_classify(404))

# Combining conditions
def can_login(user):
    if not user["active"]:
        return "denied: account disabled"
    if user["failed"] >= 5 and not user["mfa"]:
        return "denied: too many failures"
    if user["role"] in ("admin", "owner") and not user["mfa"]:
        return "denied: admins need MFA"
    return "allowed"

users = [
    {"name": "jane", "active": True,  "failed": 0, "mfa": True,  "role": "admin"},
    {"name": "john", "active": True,  "failed": 6, "mfa": False, "role": "viewer"},
    {"name": "ana",  "active": True,  "failed": 1, "mfa": False, "role": "owner"},
    {"name": "bob",  "active": False, "failed": 0, "mfa": True,  "role": "viewer"},
]
for u in users:
    print(f"{u['name']:<5} {can_login(u)}")

# Conditional expression (one-line if/else) and truthiness checks
cart = []
print("cart is", "empty" if not cart else f"{len(cart)} items")
nickname = None
print("hello,", nickname if nickname is not None else "guest")
EOF
python3 decide.py
```

```text output
200 success
301 redirect
404 client error
503 server error
101 informational
bad version says 404 is: success
jane  allowed
john  denied: too many failures
ana   denied: admins need MFA
bob   denied: account disabled
cart is empty
hello, guest
```

<Happened>
<Tr>
<En>

- `classify` checked from the highest range down, so each status landed in exactly one branch: **404 client error**, **503 server error**, and 101 fell through to `else`.
- `bad_classify` tested `>= 200` first, so **404 was called "success"**: the first true branch wins and later branches are never reached. With ranges, go from most specific to least, or use both bounds (`400 <= s < 500`).
- `can_login` handled each refusal as a **guard clause** with an early `return`. The order expresses policy: a disabled account is refused before anything else, and **ana** (an owner without MFA) was denied even with only one failure. The happy path, `"allowed"`, sits at the bottom with no nesting.
- `user["role"] in ("admin", "owner")` is a clean way to test several values; it's much safer than `role == "admin" or "owner"`, which is always true (see the mistakes below).
- `"empty" if not cart else ...` chose a value in one line; an empty list is falsy. `nickname if nickname is not None else "guest"` checks specifically for **None**, so an empty string or 0 would still be kept.

</En>
<Ur>

- `classify` ne sab se unchi range se neeche check kiya, isliye har status bilkul ek shaakh me gaya: **404 client error**, **503 server error**, aur 101 `else` tak gira.
- `bad_classify` ne pehle `>= 200` test kiya, isliye **404 ko "success" kaha**: pehli sach shaakh jeet jati aur baad ki shaakhon tak kabhi nahi pohancha jata. Ranges me sab se khaas se kam khaas ki taraf jayen, ya dono hadein lein (`400 <= s < 500`).
- `can_login` ne har inkar ko jaldi `return` wali **guard clause** ki tarah sambhala. Tarteeb policy batati hai: band account sab se pehle radd hota, aur **ana** (MFA ke baghair owner) sirf ek failure par bhi mana hui. Khushi ka raasta, `"allowed"`, nesting ke baghair neeche hai.
- `user["role"] in ("admin", "owner")` kayi values test karne ka saaf tareeqa hai; ye `role == "admin" or "owner"` se kahin mehfooz hai, jo hamesha sach hota hai (neeche ghaltiyan dekhein).
- `"empty" if not cart else ...` ne ek line me value chuni; khaali list falsy hai. `nickname if nickname is not None else "guest"` khaas taur par **None** check karta, isliye khaali string ya 0 phir bhi rakhe jate.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Pattern matching with match and case">

<Tr>
<En>
`handle()` parses commands typed into a tiny admin console by matching the list of words against patterns: fixed words, captured names, a `*ports` rest capture, a guard that refuses internal IPs, an or-pattern for quit/exit, the empty list, and a wildcard. `describe()` matches dictionaries shaped like JSON events, picking out values by key, matching specific values, binding with `as`, checking a type with `str(kind)`, and falling back to `_`.
</En>
<Ur>
`handle()` ek chhoti admin console me likhi commands ko alfaaz ki list patterns se mila kar parse karta hai: tay alfaaz, pakre gaye naam, `*ports` baqi ka capture, internal IPs radd karne wala guard, quit/exit ke liye or-pattern, khaali list, aur wildcard. `describe()` JSON events jaisi dictionaries milata hai, key se values nikal kar, khaas values mila kar, `as` se jor kar, `str(kind)` se type check kar ke, aur `_` par gir kar.
</Ur>
</Tr>

```bash
cat > commands.py <<'EOF'
# match (Python 3.10+): compare a value against patterns, top to bottom
def handle(command):
    match command.split():
        case ["help"]:
            return "commands: scan HOST [PORT...], block IP, quit"
        case ["scan", host]:
            return f"scanning {host} on default ports"
        case ["scan", host, *ports]:                       # capture the rest
            return f"scanning {host} on ports {', '.join(ports)}"
        case ["block", ip] if ip.startswith("10."):        # a guard
            return f"refusing to block internal address {ip}"
        case ["block", ip]:
            return f"blocking {ip}"
        case ["quit" | "exit"]:                            # or-pattern
            return "bye"
        case []:
            return "(empty line)"
        case _:                                            # wildcard: anything else
            return f"unknown command: {command!r}"

for c in ["help", "scan example.test", "scan example.test 22 443", "block 10.0.0.5",
          "block 203.0.113.7", "exit", "", "delete everything"]:
    print(f"{c!r:<28} -> {handle(c)}")

# Matching dictionaries, such as JSON events from an API
def describe(event):
    match event:
        case {"type": "login", "user": user, "success": False}:
            return f"failed login for {user}"
        case {"type": "login", "user": user}:
            return f"{user} logged in"
        case {"type": "deploy", "env": "production" as env, "by": who}:
            return f"{who} deployed to {env}!"
        case {"type": str(kind)}:
            return f"unhandled event type {kind}"
        case _:
            return "not an event"

for e in [{"type": "login", "user": "jane", "success": False},
          {"type": "login", "user": "john", "success": True, "ip": "203.0.113.7"},
          {"type": "deploy", "env": "production", "by": "ana"},
          {"type": "backup"}, ["oops"]]:
    print(describe(e))
EOF
python3 commands.py
```

```text output
'help'                       -> commands: scan HOST [PORT...], block IP, quit
'scan example.test'          -> scanning example.test on default ports
'scan example.test 22 443'   -> scanning example.test on ports 22, 443
'block 10.0.0.5'             -> refusing to block internal address 10.0.0.5
'block 203.0.113.7'          -> blocking 203.0.113.7
'exit'                       -> bye
''                           -> (empty line)
'delete everything'          -> unknown command: 'delete everything'
failed login for jane
john logged in
ana deployed to production!
unhandled event type backup
not an event
```

<Happened>
<Tr>
<En>

- `case ["scan", host]` matched a two-word list starting with "scan" and **captured** the second word into `host`. `case ["scan", host, *ports]` matched longer lists, collecting the rest into **ports**. Order matters again: the exact two-word case came first.
- `case ["block", ip] if ip.startswith("10.")` only matched when the **guard** was true, so `10.0.0.5` was refused and `203.0.113.7` fell to the next case and was blocked.
- `["quit" | "exit"]` matched either word; `[]` caught the empty line; `_` caught **everything else**, giving a clear "unknown command" instead of silently doing nothing.
- Mapping patterns matched dictionaries that **contain** the listed keys (extra keys like `"ip"` are fine). `"success": False` matched only failed logins; John's event fell through to the general login case.
- `"production" as env` matched a specific value and bound it, and `{"type": str(kind)}` matched any event whose type is a string. `["oops"]` isn't a dict, so only `_` matched: **not an event**.
- `match` doesn't fall through like C's `switch`: exactly one case runs, or none if there's no `_`.

</En>
<Ur>

- `case ["scan", host]` ne "scan" se shuru hone wali do alfaaz ki list milayi aur doosra lafz `host` me **pakra**. `case ["scan", host, *ports]` ne lambi lists milayin, baqi **ports** me jama kar ke. Tarteeb phir maayne rakhti hai: bilkul do alfaaz wala case pehle tha.
- `case ["block", ip] if ip.startswith("10.")` tabhi mila jab **guard** sach tha, isliye `10.0.0.5` radd hua aur `203.0.113.7` agle case par gira aur block hua.
- `["quit" | "exit"]` ne dono me se koi lafz milaya; `[]` ne khaali line pakri; `_` ne **baqi sab** pakra, khamoshi se kuch na karne ke bajaye wazeh "unknown command" de kar.
- Mapping patterns ne aisi dictionaries milayin jin me darj keys **mojood** hon (`"ip"` jaisi izafi keys theek hain). `"success": False` ne sirf failed logins milaye; John ka event aam login case par gira.
- `"production" as env` ne khaas value milayi aur jori, aur `{"type": str(kind)}` ne har woh event milaya jis ki type string ho. `["oops"]` dict nahi, isliye sirf `_` mila: **not an event**.
- `match` C ke `switch` ki tarah aage nahi girta: bilkul ek case chalta hai, ya `_` na ho to koi nahi.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="or with a bare value">

```text
role = "viewer"
if role == "admin" or "owner":       # parsed as (role == "admin") or ("owner")
    grant_everything()               # runs for EVERY role: "owner" is truthy
```

</Bad>
<Good title="Compare each value, or use in">

```text
if role == "admin" or role == "owner":
    grant_everything()
# clearer:
if role in {"admin", "owner"}:
    grant_everything()
```

</Good>
</Compare>

<Compare>
<Bad title="Arrow-shaped nesting">

```text
def delete_file(user, file):
    if user:
        if user.active:
            if file.owner == user.name or user.is_admin:
                file.delete()
                return "deleted"
            else:
                return "forbidden"
        else:
            return "disabled"
    else:
        return "login required"
```

</Bad>
<Good title="Guard clauses, happy path last">

```text
def delete_file(user, file):
    if not user:
        return "login required"
    if not user.active:
        return "disabled"
    if file.owner != user.name and not user.is_admin:
        return "forbidden"
    file.delete()
    return "deleted"
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`=` instead of `==`** in a condition: Python raises a SyntaxError (good), but read the message.
- **`if x == True:`** or **`if len(items) > 0:`**: write `if x:` and `if items:`.
- **`if not value:` when 0 or "" are valid**: check `if value is None:` instead.
- **Forgetting the colon or the indentation**: every `if`, `elif`, `else` and `case` line ends with `:` and its body is indented.
- **Missing `case _`** in a `match`: unexpected input silently does nothing.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Shart me `==` ke bajaye `=`**: Python SyntaxError deta hai (acha), magar paigham parhein.
- **`if x == True:`** ya **`if len(items) > 0:`**: `if x:` aur `if items:` likhein.
- **`if not value:` jab 0 ya "" durust hon**: is ke bajaye `if value is None:` check karein.
- **Colon ya indentation bhoolna**: har `if`, `elif`, `else` aur `case` line `:` par khatam hoti aur us ka jism indent hota hai.
- **`match` me `case _` na hona**: ghair mutawaqqo input khamoshi se kuch nahi karta.

</Ur>
</Tr>

<Challenge title="Password policy">

<Tr>
<En>

Test it on `"short1A"`, `"longenoughpassword1A"`, `"alllowercase123"`, `"Correct-Horse-42"`. Use guard clauses and `any(ch.isdigit() for ch in pw)`.

<Solution>

<Tr>
<En>

```text
def check_password(pw):
    if len(pw) < 12:
        return "too short"
    if not any(ch.isdigit() for ch in pw):
        return "needs a digit"
    if not any(ch.isupper() for ch in pw):
        return "needs an uppercase letter"
    if "password" in pw.lower():
        return "must not contain 'password'"
    return "ok"

for pw in ["short1A", "longenoughpassword1A", "alllowercase123", "Correct-Horse-42"]:
    print(f"{pw:<22} {check_password(pw)}")

# short1A                too short
# longenoughpassword1A   must not contain 'password'
# alllowercase123        needs an uppercase letter
# Correct-Horse-42       ok
```

<DeepDive title="More about conditionals">

**Dict dispatch.** Mapping fixed keys to results or functions (`handlers = {"start": start, "stop": stop}`; `handlers.get(cmd, unknown)()`) replaces long `elif` chains.

**any() and all().** `any(cond for x in items)` and `all(...)` express "at least one" and "every" checks clearly, and short-circuit.

**The walrus operator.** `if (n := len(items)) > 10:` assigns and tests in one step; use it sparingly for readability.

**Class patterns.** `match` can destructure objects: `case Point(x=0, y=y):`, and dataclasses support positional patterns via `__match_args__`.

**Value vs capture patterns.** A bare name in a case (`case status:`) always captures; to compare against a constant, use a dotted name (`case HTTPStatus.OK:`) or a literal.

</DeepDive>

<DeepDive title="Real world: the always-true admin check">

An internal dashboard checked permissions with `if user.role == "admin" or "superuser":`. In code review nobody noticed, and tests only covered admin users. Every logged-in user, including read-only contractors, could reach the admin pages for months, until an audit found deletions made by a viewer account.

The fixes:

1. Replace with `if user.role in {"admin", "superuser"}:`.
2. Deny by default: permission checks return "forbidden" unless a rule explicitly allows.
3. Tests for every role, especially the ones that should be refused.
4. A linter rule (pylint and ruff flag comparisons followed by a constant in `or`) in CI.

</DeepDive>

<DeepDive title="Security lens">

- **Deny by default**: structure checks so the final fallback is refusal, not permission.
- **Order guard clauses deliberately**: disabled accounts, missing authentication and failed MFA must be checked before anything grants access.
- **Beware truthiness on security flags**: a string `"false"` from a form is truthy; parse it into a real bool.
- **Use exact comparisons for security decisions**, not substring or prefix checks on untrusted input.
- **Handle the unexpected case**: an `else` or `case _` that logs and refuses prevents silent bypasses.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between if/elif and several separate if statements?">
In an if/elif chain only the first true branch runs; separate if statements are all evaluated and every true one runs. Use elif for mutually exclusive cases.
</QA>

<QA q="How does Python's match differ from a C-style switch?">
It matches structure, not just values: sequences, mappings, classes, captures, alternatives and guards. Cases don't fall through, exactly one runs, and there's no automatic default unless you write case _.
</QA>

<QA q="When should you write if x is None instead of if not x?">
When falsy values like 0, empty strings or empty lists are valid and only a missing value should be treated specially.
</QA>

<QA q="What is a guard clause and why use it?">
A condition at the start of a function that handles invalid or special cases and returns early, reducing nesting and making the main logic easier to read and review.
</QA>

<QA q="How can you replace a long if/elif chain?">
With a dictionary lookup for fixed values, polymorphism for type-based behaviour, or match for structured data.
</QA>

</DeepDive>
