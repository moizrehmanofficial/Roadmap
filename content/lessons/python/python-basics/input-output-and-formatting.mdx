<BigIdea>
<Tr>
<En>
Every program has three standard streams: **standard input** (stdin), where it reads; **standard output** (stdout), where its normal results go; and **standard error** (stderr), for errors, warnings and progress messages. In a terminal all three are your keyboard and screen, but the shell can **redirect** them: `< file` feeds a file into stdin, `> file` saves stdout, `2> file` saves stderr, and `|` connects one program's stdout to the next one's stdin. In Python, **`input()`** reads one line from stdin and returns it as a **string** without the newline, so you convert and validate it, usually in a loop that asks again on bad input. **`print()`** writes to stdout, with `sep` (between items), `end` (after the line) and `file` (where to write, such as `sys.stderr` or an open file). For scripts that should work in pipelines, read with **`for line in sys.stdin`**, send results to stdout and messages to stderr, and offer **JSON** output when another program will consume it. Keeping results and messages on separate streams is what lets others build on your tools.
</En>
<Ur>
Har program ke teen standard streams hote hain: **standard input** (stdin), jahan se parhta hai; **standard output** (stdout), jahan aam natije jate hain; aur **standard error** (stderr), errors, warnings aur progress paighamat ke liye. Terminal me teeno aap ka keyboard aur screen hain, magar shell unhe **redirect** kar sakta hai: `< file` file ko stdin me daalta, `> file` stdout save karta, `2> file` stderr save karta, aur `|` ek program ka stdout agle ke stdin se jorta hai. Python me **`input()`** stdin se ek line parh kar newline ke baghair **string** lautata hai, isliye aap use convert aur validate karte hain, aam taur par aise loop me jo ghalat input par dobara poochhe. **`print()`** stdout par likhta hai, `sep` (items ke beech), `end` (line ke baad) aur `file` (kahan likhna, jaise `sys.stderr` ya khuli file) ke saath. Jo scripts pipelines me chalein unke liye **`for line in sys.stdin`** se parhein, natije stdout aur paighamat stderr par bhejein, aur jab doosra program parhe to **JSON** output dein. Natije aur paighamat alag streams par rakhna hi doosron ko aap ke tools par kaam banane deta hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **kitchen with three hatches**.

- Orders come in through one hatch (stdin): from a waiter (a person typing) or a conveyor belt from another kitchen (a pipe).
- Finished plates go out of another hatch (stdout), straight to the dining room or onto the next kitchen's conveyor.
- Notes like "we're out of salmon" go through a third hatch to the manager (stderr), so they never land on a customer's plate.
- A kitchen that writes its notes on the plates is a script that prints messages to stdout: whoever receives the output has to scrape them off.

</En>
<Ur>

**Teen khirkiyon wali kitchen** socheyn.

- Orders ek khirki se aate hain (stdin): waiter se (insaan type karta hua) ya doosri kitchen ki conveyor belt se (pipe).
- Tayyar plates doosri khirki se nikalti hain (stdout), seedhi dining room ya agli kitchen ki conveyor par.
- "Salmon khatam" jaise notes teesri khirki se manager ke paas jate hain (stderr), taa ke kabhi customer ki plate par na pohanchein.
- Jo kitchen notes plates par likhe woh aisi script hai jo paighamat stdout par print kare: output paane wale ko unhe khurachna parta hai.

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="input(), validation loops and print() options">

<Tr>
<En>
`signup.py` asks for a name and an age. The age is read in a loop: text that isn't a whole number, or a number out of range, gets a message on **stderr** and the question again. Then it greets the user and shows `print()`'s `sep` and `end`. Since we can't type here, `printf` pipes four answers into the script, the same as a person typing "jane doe", "forty", "200" and "34". We run it twice, the second time hiding stderr.
</En>
<Ur>
`signup.py` naam aur umar poochhti hai. Umar loop me parhi jati hai: jo text poora number na ho, ya had se bahar number ho, use **stderr** par paigham aur dobara sawal milta hai. Phir user ka istiqbal karti aur `print()` ke `sep` aur `end` dikhati hai. Kyunke yahan type nahi kar sakte, `printf` chaar jawab script me pipe karta hai, bilkul jaise koi insaan "jane doe", "forty", "200" aur "34" type kare. Hum ise do dafa chalate hain, doosri dafa stderr chhupa kar.
</Ur>
</Tr>

```bash
cat > signup.py <<'EOF'
import sys

name = input("Your name: ").strip()          # input() always returns a str (without the newline)
while True:
    text = input("Your age: ")
    try:
        age = int(text)
    except ValueError:
        print(f"  {text!r} is not a whole number, try again", file=sys.stderr)
        continue
    if 0 < age < 130:
        break
    print("  age must be between 1 and 129", file=sys.stderr)

print(f"Welcome, {name.title()}! In 10 years you'll be {age + 10}.")
print("name", "age", sep=" | ", end=" <- sep and end changed\n")
print("a", "b", "c", sep="")
EOF
# Simulate a user typing four lines (in a terminal you'd type them)
printf 'jane doe\nforty\n200\n34\n' | python3 signup.py
echo "--- the same run with errors (stderr) hidden:"
printf 'jane doe\nforty\n200\n34\n' | python3 signup.py 2> /dev/null
```

```text output
Your name: Your age:   'forty' is not a whole number, try again
Your age:   age must be between 1 and 129
Your age: Welcome, Jane Doe! In 10 years you'll be 44.
name | age <- sep and end changed
abc
--- the same run with errors (stderr) hidden:
Your name: Your age: Your age: Your age: Welcome, Jane Doe! In 10 years you'll be 44.
name | age <- sep and end changed
abc
```

<Happened>
<Tr>
<En>

- The prompts **"Your name:"** and **"Your age:"** were printed without a line break; in a terminal your typing and Enter would complete the line. Piped input isn't echoed, which is why the answers don't appear.
- `"forty"` failed `int()`, so the loop printed a message and **asked again**; `200` was a number but out of range, so it asked again; `34` passed and the loop ended with `break`. Never trust the first answer.
- `input()` returned text; `.strip()` removed accidental spaces and `.title()` turned "jane doe" into **Jane Doe**.
- `sep=" | "` put a custom separator between items, `end=...` replaced the newline, and `sep=""` glued **abc** together.
- In the second run, `2> /dev/null` **hid the error messages** but kept the prompts and results, because errors went to stderr. That separation is what you want: a log of results without noise, or errors captured in their own file.

</En>
<Ur>

- Prompts **"Your name:"** aur **"Your age:"** line break ke baghair print hue; terminal me aap ka type karna aur Enter line mukammal karta. Pipe kiya input echo nahi hota, isi liye jawab nazar nahi aate.
- `"forty"` `int()` me nakam hua, isliye loop ne paigham print kar ke **dobara poochha**; `200` number tha magar had se bahar, isliye phir poochha; `34` pass hua aur loop `break` se khatam hua. Pehle jawab par kabhi bharosa na karein.
- `input()` ne text lautaya; `.strip()` ne ghalti ke spaces hataye aur `.title()` ne "jane doe" ko **Jane Doe** banaya.
- `sep=" | "` ne items ke beech apna separator rakha, `end=...` ne newline badla, aur `sep=""` ne **abc** jor diya.
- Doosri dafa `2> /dev/null` ne **error paighamat chhupaye** magar prompts aur natije rakhe, kyunke errors stderr par gaye. Yahi alehdgi chahiye: shor ke baghair natijon ka log, ya errors apni file me.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Pipelines: reading stdin, writing stdout, stderr and JSON">

<Tr>
<En>
`failed_logins.py` reads web server log lines from **stdin**, counts failed logins (`POST /login` with status 401) per IP, and prints a table to stdout with a total on stderr, or JSON with `--json`. It also writes a small report file with `print(file=...)`. We feed it with a pipe, with `<` redirection, send its stdout into `head`, and finally use `pprint` on a nested dictionary.
</En>
<Ur>
`failed_logins.py` **stdin** se web server ki log lines parhti, har IP ke failed logins (`POST /login` status 401 ke saath) ginti, aur stdout par table aur stderr par total print karti hai, ya `--json` ke saath JSON. Ye `print(file=...)` se chhoti report file bhi likhti hai. Hum ise pipe se, `<` redirection se khilate, us ka stdout `head` me bhejte, aur aakhir me nested dictionary par `pprint` lagate hain.
</Ur>
</Tr>

```bash
cat > access.log <<'EOF'
203.0.113.7 - - [23/Nov/2026:10:15:30 +0000] "GET / HTTP/1.1" 200 1024
203.0.113.7 - - [23/Nov/2026:10:15:32 +0000] "POST /login HTTP/1.1" 401 512
198.51.100.4 - - [23/Nov/2026:10:15:33 +0000] "POST /login HTTP/1.1" 401 512
203.0.113.7 - - [23/Nov/2026:10:15:35 +0000] "POST /login HTTP/1.1" 401 512
203.0.113.9 - - [23/Nov/2026:10:15:40 +0000] "GET /api/orders HTTP/1.1" 200 2048
EOF
cat > failed_logins.py <<'EOF'
"""Read log lines from standard input, report failed logins per IP."""
import sys, json

counts = {}
for line in sys.stdin:                         # works with pipes, files and redirection
    parts = line.split()
    if len(parts) < 9:
        continue
    ip, path, status = parts[0], parts[6], parts[8]
    if path == "/login" and status == "401":
        counts[ip] = counts.get(ip, 0) + 1

if "--json" in sys.argv:
    print(json.dumps(counts, indent=2))        # machine-readable output for other tools
else:
    for ip, n in sorted(counts.items(), key=lambda kv: -kv[1]):
        print(f"{ip:<15} {n:>3} failed")
    sys.stdout.flush()                         # keep the order when both streams share a screen
    print(f"total: {sum(counts.values())}", file=sys.stderr)   # summary on stderr

with open("report.txt", "w", encoding="utf-8") as f:           # print can write to files too
    print("failed logins:", counts, file=f)
EOF
cat access.log | python3 failed_logins.py
python3 failed_logins.py --json < access.log
python3 failed_logins.py < access.log 2> /dev/null | head -1      # stdout only, into another command
cat report.txt
python3 -c 'from pprint import pprint; pprint({"user": "jane", "roles": ["admin", "billing", "support"], "mfa": {"enabled": True, "methods": ["totp", "webauthn"]}}, width=50)'
```

```text output
203.0.113.7       2 failed
198.51.100.4      1 failed
total: 3
{
  "203.0.113.7": 2,
  "198.51.100.4": 1
}
203.0.113.7       2 failed
failed logins: {'203.0.113.7': 2, '198.51.100.4': 1}
{'mfa': {'enabled': True,
         'methods': ['totp', 'webauthn']},
 'roles': ['admin', 'billing', 'support'],
 'user': 'jane'}
```

<Happened>
<Tr>
<En>

- `for line in sys.stdin` read every line whether it came from `cat access.log |` or `< access.log`: the script doesn't care where input comes from. It processes one line at a time, so a 10 GB log works as well as 5 lines.
- The table listed **203.0.113.7 with 2** failures before **198.51.100.4 with 1**, sorted by count. The **total** went to stderr, and `sys.stdout.flush()` made sure the table appeared before it on a shared screen.
- With `--json`, the same data came out as **JSON**, ready for `jq`, another script or an API. Offer a machine-readable mode whenever your output might be consumed by code.
- `2> /dev/null | head -1` passed only stdout to `head`, which printed the **first row**; the total didn't pollute the pipe.
- `print(..., file=f)` wrote the same kind of line into **report.txt**; `with open(...)` closes the file automatically (files get their own lesson later).
- `pprint` broke the nested dictionary over several lines and **sorted its keys**, which is far easier to read than one long line when debugging configs or API responses.

</En>
<Ur>

- `for line in sys.stdin` ne har line parhi chahe woh `cat access.log |` se aayi ya `< access.log` se: script ko parwah nahi input kahan se aaya. Ye ek waqt me ek line process karti hai, isliye 10 GB ka log bhi 5 lines jaisa chalta hai.
- Table ne ginti ki tarteeb se **203.0.113.7 ke 2** failures **198.51.100.4 ke 1** se pehle dikhaye. **Total** stderr par gaya, aur `sys.stdout.flush()` ne yaqeeni banaya ke mushtarka screen par table us se pehle aaye.
- `--json` ke saath wahi data **JSON** ban kar nikla, `jq`, doosri script ya API ke liye tayyar. Jab bhi output code parh sakta ho, machine ke parhne layak mode dein.
- `2> /dev/null | head -1` ne sirf stdout `head` ko diya, jis ne **pehli row** print ki; total ne pipe ganda nahi kiya.
- `print(..., file=f)` ne wahi qism ki line **report.txt** me likhi; `with open(...)` file khud band karta hai (files ka apna lesson baad me).
- `pprint` ne nested dictionary ko kayi lines me toda aur **keys tarteeb di**, jo configs ya API responses debug karte waqt ek lambi line se kahin aasaan hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Trusting input() and crashing">

```text
age = int(input("Age: "))        # "forty" -> ValueError, program ends with a traceback
qty = input("Quantity: ")
total = qty * 9.99               # TypeError: can't multiply sequence by non-int of type 'float'
```

</Bad>
<Good title="Convert, validate, ask again">

```text
while True:
    text = input("Quantity: ").strip()
    if text.isdigit() and 1 <= int(text) <= 100:
        qty = int(text)
        break
    print("Enter a number from 1 to 100", file=sys.stderr)
total = qty * 9.99
```

</Good>
</Compare>

<Compare>
<Bad title="Mixing messages into the data">

```text
print("Starting scan...")
for host in hosts:
    print(host, status(host))
print("Done!")
# scan.py > results.txt  -> results.txt contains "Starting scan..." and "Done!"
```

</Bad>
<Good title="Data on stdout, chatter on stderr">

```text
print("Starting scan...", file=sys.stderr)
for host in hosts:
    print(host, status(host))
print("Done!", file=sys.stderr)
# results.txt contains only the data; the messages still show on screen
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Reading a whole huge file with `sys.stdin.read()`** when you could process line by line.
- **Forgetting the newline at the end of each line**: lines from stdin include `\n`; `strip()` or `split()` removes it.
- **`input()` for passwords**: they show on screen; use `getpass.getpass()`.
- **Pretty text when tools need data**: offer `--json` or CSV output.
- **Prompts in a non-interactive run** (cron, CI): accept arguments or environment variables instead of waiting for input forever.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`sys.stdin.read()` se poori bari file parhna** jab line ba line process ho sakti thi.
- **Har line ke aakhir ki newline bhoolna**: stdin ki lines me `\n` hota; `strip()` ya `split()` hatata hai.
- **Passwords ke liye `input()`**: screen par dikhte; `getpass.getpass()` lein.
- **Tools ko data chahiye to khoobsurat text**: `--json` ya CSV output dein.
- **Ghair interactive run me prompts** (cron, CI): hamesha input ka intezar karne ke bajaye arguments ya environment variables lein.

</Ur>
</Tr>

With the lesson's log the script prints `200 2` then `401 3`, and after the `sort` by count `401 3` comes first.

<Ur>
`status_count.py` likhein jo stdin se log lines parhe aur har status code ki requests ki ginti print kare, har line par `status count`, status ki tarteeb se, taa ke `python3 status_count.py < access.log | sort -k2 -n -r` chale. <Solution>

<DeepDive title="More about input and output">

**Buffering.** stdout is line-buffered in a terminal but block-buffered when piped, so output can appear late or out of order with stderr; `print(..., flush=True)`, `sys.stdout.flush()` or `python3 -u` fix that, which matters for logs in Docker.

**fileinput.** `import fileinput; for line in fileinput.input():` reads files named in arguments, or stdin if none, the same way Unix tools do.

**Rich terminal output.** Libraries like `rich` print colour, tables and progress bars; detect `sys.stdout.isatty()` so you only add colour for humans, not pipes.

**Encodings.** Streams have an encoding (`sys.stdout.encoding`); on Windows consoles, setting `PYTHONUTF8=1` avoids errors with non-ASCII text.

**Logging.** For real tools, the `logging` module (covered later) writes timestamped messages to stderr or files with levels like INFO and ERROR, instead of bare prints.

</DeepDive>

<DeepDive title="Real world: the report full of noise">

A nightly job ran `inventory.py > hosts.csv` and a second job imported `hosts.csv` into a dashboard. Someone added `print("Connecting to cloud API...")` and `print(f"Warning: {host} timed out")` for debugging. The CSV now had stray lines at the top and in the middle, the import failed on the first night and silently skipped rows on later nights.

The fixes:

1. All messages moved to stderr (later to `logging`), so stdout held only CSV.
2. The script wrote CSV with the `csv` module and a header row, and exited non-zero if any host failed.
3. The import validated the header and row count, and alerted on mismatches.

</DeepDive>

<DeepDive title="Security lens">

- **Treat all input as hostile**: validate type, range and length; reject rather than "fix" unexpected input.
- **Never pass input to `eval()` or `exec()`**: `eval(input())` lets a user run any code.
- **Hide secrets while typing**: `getpass` doesn't echo; never accept passwords as command-line arguments (visible in the process list and shell history).
- **Don't print secrets to stdout or stderr**: both end up in logs, CI output and terminals.
- **Sanitise before logging**: newlines and control characters in input can forge log entries or mess up terminals.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are stdin, stdout and stderr?">
The three standard streams every process gets: input, normal output and error output. Keeping results on stdout and diagnostics on stderr lets users redirect and pipe them independently.
</QA>

<QA q="How do you read input from a pipe in Python?">
Iterate over sys.stdin, which yields lines including the trailing newline, or use fileinput to support both file arguments and stdin.
</QA>

<QA q="Why might print output appear out of order with stderr?">
stdout is buffered when it isn't a terminal, while stderr is unbuffered, so stderr text can be written first. Flushing stdout or running Python unbuffered fixes the order.
</QA>

<QA q="How do you safely read a password in a CLI?">
With getpass.getpass, which reads from the terminal without echoing characters, rather than input() or a command-line argument.
</QA>

<QA q="How should a script handle invalid user input?">
Catch conversion errors, check ranges, explain the problem on stderr and ask again in interactive use, or exit with a non-zero code in non-interactive use.
</QA>

</DeepDive>
