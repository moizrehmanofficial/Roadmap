<BigIdea>
<Tr>
<En>
**Python** is a general-purpose programming language designed to be **easy to read**: indentation shows structure, there are few symbols, and code often reads like plain English. It's **interpreted**: you write a `.py` file and the Python interpreter runs it directly, with no separate compile step. It comes with a huge **standard library** ("batteries included": files, JSON, HTTP, dates, CSV, regex, hashing) and over half a million packages on **PyPI**. That's why it dominates **automation and scripting**, **security tooling** (scanners, exploit proofs of concept, log analysis), **DevOps and cloud** (AWS's boto3, Ansible), **data and AI**, and web backends (Django, FastAPI). To start you need two things: a **Python 3** interpreter (3.15 is the latest release; anything from 3.12 is fine for this track), and the habit of creating a **virtual environment** for each project, so its packages don't clash with other projects or the operating system's own Python. The modern tool **uv** does both: it installs Python versions and manages each project's environment and packages.
</En>
<Ur>
**Python** aam maqsad ki programming language hai jo **parhne me aasaan** banayi gayi: indentation dhancha dikhati hai, symbols kam hain, aur code aksar saadi English jaisa parhta hai. Ye **interpreted** hai: aap `.py` file likhte hain aur Python interpreter use seedha chalata hai, alag compile step ke baghair. Is ke saath bohot bari **standard library** aati hai ("batteries included": files, JSON, HTTP, dates, CSV, regex, hashing) aur **PyPI** par 500,000 se zyada packages hain. Isi wajah se ye **automation aur scripting**, **security tooling** (scanners, exploit proofs of concept, log analysis), **DevOps aur cloud** (AWS ka boto3, Ansible), **data aur AI**, aur web backends (Django, FastAPI) par chhaya hua hai. Shuru karne ke liye do cheezen chahiyen: **Python 3** interpreter (3.15 taza tareen release hai; is track ke liye 3.12 se upar koi bhi theek hai), aur har project ke liye **virtual environment** banane ki aadat, taa ke us ke packages doosre projects ya operating system ke apne Python se na takrayen. Jadeed tool **uv** dono karta hai: Python versions install karta aur har project ka environment aur packages sambhalta hai.
</Ur>

## Picture it

<Tr>
<En>

Think of a **workshop with a toolbox for each job**.

- Python is the workshop: the interpreter is the workbench where work actually happens.
- The standard library is the set of tools that came with the workshop: hammer, saw, tape measure. You can do a lot without buying anything.
- PyPI is the hardware store with half a million specialised tools.
- A virtual environment is a separate toolbox for each job. The tools you buy for fixing the car don't get mixed up with the ones for the kitchen, and you never modify the landlord's built-in tools (the operating system's Python).
- uv is the assistant who sets up the right workbench and toolbox for each job, and writes down exactly which tools were used (the lock file) so someone else can repeat it.

</En>
<Ur>

**Har kaam ke liye alag toolbox wali workshop** socheyn.

- Python workshop hai: interpreter woh workbench hai jahan asal kaam hota hai.

- PyPI hardware store hai jahan 500,000 khaas auzaar hain.
- Virtual environment har kaam ka alag toolbox hai. Gaari theek karne ke liye khareede auzaar kitchen walon se nahi milte, aur aap malik makaan ke lage hue auzaar (operating system ka Python) kabhi nahi badalte.
- uv woh madadgar hai jo har kaam ke liye sahi workbench aur toolbox lagata, aur likh leta hai ke bilkul kaunse auzaar istemal hue (lock file) taa ke koi aur dohra sake.

## Learn it step by step

<Walkthrough>

<Step title="Check Python, run a script, and use a virtual environment">

<Tr>
<En>
Most Linux machines and Macs with developer tools already have a `python3`. We check its version and location, run one line with `-c`, then a small script `first.py` that uses only the standard library. Next we create a **virtual environment** in `.venv`, activate it, install the `humanize` package from PyPI into it, and finally check whether the system Python can see that package.
</En>
<Ur>
Zyadatar Linux machines aur developer tools wale Macs me pehle se `python3` hota hai. Hum us ka version aur jagah check karte, `-c` se ek line chalate, phir chhoti script `first.py` jo sirf standard library istemal karti hai. Phir `.venv` me **virtual environment** banate, activate karte, PyPI se `humanize` package us me install karte, aur aakhir me check karte hain ke system ka Python woh package dekh sakta hai ya nahi.
</Ur>
</Tr>

```bash
python3 --version
python3 -c 'import sys; print("running from:", sys.executable)'
python3 -c 'print("Hello from Python!")'
# A first real script: Python ships with a big standard library ("batteries included")
cat > first.py <<'EOF'
import platform, datetime, json
info = {"python": platform.python_version(), "os": platform.system(), "year": datetime.date(2026, 11, 23).year}
print(json.dumps(info))
print("2 ** 100 =", 2 ** 100)       # integers have no size limit
EOF
python3 first.py
# A virtual environment: a private folder of packages for one project
python3 -m venv .venv
. .venv/bin/activate
echo "python now: $(command -v python | sed "s#$PWD/##")"
pip install -q humanize==4.17.0 2> /dev/null      # a package from PyPI, into .venv only
python -c 'import humanize; print(humanize.intcomma(1234567), "|", humanize.naturalsize(5_000_000))'
deactivate
python3 -c 'import humanize' 2>&1 | tail -1      # the system Python doesn't have it
```

```text output
Python 3.13.18
running from: /usr/local/bin/python3
Hello from Python!
{"python": "3.13.18", "os": "Linux", "year": 2026}
2 ** 100 = 1267650600228229401496703205376
python now: .venv/bin/python
1,234,567 | 5.0 MB
ModuleNotFoundError: No module named 'humanize'
```

<Happened>
<Tr>
<En>

- This machine has **Python 3.13** at `/usr/local/bin/python3`. Your version and path may differ; on Windows the command is often `py` or `python`. If the command isn't found, Python isn't installed or isn't on your PATH.
- `first.py` used `platform`, `datetime` and `json` without installing anything: that's the standard library. It also printed **2 to the power of 100** exactly; Python integers grow as large as needed.
- After activating the venv, `python` pointed to **`.venv/bin/python`**: activation just puts `.venv/bin` first on your PATH. `pip install` then put `humanize` inside `.venv`, and it formatted **1,234,567** and **5.0 MB**.
- After `deactivate`, the system Python raised **ModuleNotFoundError**: the package exists only in that project's environment. That isolation is the whole point. Each project can have its own versions, and you never break tools that depend on the system Python (on many Linux distributions `pip install` outside a venv is refused for this reason).

</En>
<Ur>

- Is machine par `/usr/local/bin/python3` me **Python 3.13** hai. Aap ka version aur raasta mukhtalif ho sakta; Windows par command aksar `py` ya `python` hoti hai. Agar command na mile to Python install nahi ya PATH par nahi.
- `first.py` ne kuch install kiye baghair `platform`, `datetime` aur `json` istemal kiye: yahi standard library hai. Us ne **2 ki power 100** bhi bilkul theek print ki; Python integers jitne bare chahiye ho jate hain.
- Venv activate karne ke baad `python` **`.venv/bin/python`** ki taraf gaya: activation bas `.venv/bin` ko PATH me sab se aage rakhta hai. Phir `pip install` ne `humanize` ko `.venv` ke andar rakha, aur us ne **1,234,567** aur **5.0 MB** format kiye.
- `deactivate` ke baad system Python ne **ModuleNotFoundError** diya: package sirf us project ke environment me hai. Yahi alehdgi asal maqsad hai. Har project ke apne versions ho sakte, aur aap system Python par mabni tools kabhi nahi torte (isi wajah se kayi Linux distributions venv ke bahar `pip install` se inkar karti hain).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Install Python 3.15 and create a project with uv">

<Tr>
<En>
**uv** installs Python versions alongside whatever the system has, and manages projects. We install Python 3.15, create a project called `hello-py` pinned to it, write `main.py`, add `humanize` as a dependency, look at the files uv created, and run the script with `uv run`, which uses the project's own environment automatically: no activate step.
</En>
<Ur>
**uv** system me jo bhi ho us ke saath Python versions install karta aur projects sambhalta hai. Hum Python 3.15 install karte, us par tay `hello-py` naam ka project banate, `main.py` likhte, `humanize` ko dependency ki tarah jorte, uv ki banayi files dekhte, aur script `uv run` se chalate hain, jo project ka apna environment khud istemal karta hai: activate ka qadam nahi.
</Ur>
</Tr>

```bash
# uv: one fast tool that installs Python itself, creates projects and manages packages
uv python install 3.15 -q
uv python find 3.15 > /dev/null && echo "Python 3.15 is available to uv"
rm -rf hello-py && uv init hello-py --python 3.15 -q && cd hello-py
cat > main.py <<'EOF'
import sys
import humanize

def main():
    print(f"Python {sys.version_info.major}.{sys.version_info.minor} from the project's .venv")
    print("Files downloaded:", humanize.intword(3_400_000))

if __name__ == "__main__":
    main()
EOF
uv add -q humanize==4.17.0
grep -A2 '^dependencies' pyproject.toml
cat .python-version
uv run main.py
ls -a | grep -E '^(\.venv|uv\.lock|pyproject\.toml)$'
```

```text output
Python 3.15 is available to uv
dependencies = [
    "humanize==4.17.0",
]
3.15
Python 3.15 from the project's .venv
Files downloaded: 3.4 million
.venv
pyproject.toml
uv.lock
```

<Happened>
<Tr>
<En>

- uv installed **Python 3.15** without replacing the system's 3.13. Different projects can use different versions side by side.
- `uv init` wrote **`pyproject.toml`** (project name, Python requirement, dependencies) and **`.python-version`** with **3.15**, so everyone working on the project gets the same version.
- `uv add` recorded **`humanize==4.17.0`** in `dependencies`, created **`.venv`** and wrote **`uv.lock`** with the exact version of every package. Commit `pyproject.toml`, `.python-version` and `uv.lock`; never commit `.venv` (uv's default `.gitignore` excludes it).
- `uv run main.py` ran with **Python 3.15** from the project's environment and printed **3.4 million**. The `if __name__ == "__main__":` line means "run `main()` only when this file is run directly, not when it's imported"; you'll see it in almost every script.

</En>
<Ur>

- uv ne system ka 3.13 badle baghair **Python 3.15** install kiya. Mukhtalif projects saath saath mukhtalif versions istemal kar sakte hain.
- `uv init` ne **`pyproject.toml`** (project ka naam, Python ki shart, dependencies) aur **3.15** wali **`.python-version`** likhi, taa ke project par kaam karne wale sab ko wahi version mile.
- `uv add` ne `dependencies` me **`humanize==4.17.0`** darj kiya, **`.venv`** banaya aur har package ke bilkul version ke saath **`uv.lock`** likhi. `pyproject.toml`, `.python-version` aur `uv.lock` commit karein; `.venv` kabhi commit na karein (uv ki default `.gitignore` use bahar rakhti hai).
- `uv run main.py` project ke environment ke **Python 3.15** se chala aur **3.4 million** print kiya. `if __name__ == "__main__":` line ka matlab hai "`main()` sirf tab chalao jab ye file seedhi chalayi jaye, import hone par nahi"; ye aap takreeban har script me dekhenge.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Installing packages into the system Python">

```text
sudo pip install requests boto3 scapy
# error: externally-managed-environment   (or worse, it works and breaks an OS tool)
# every project shares one set of versions; upgrading one breaks another
```

</Bad>
<Good title="One environment per project">

```text
cd my-scanner
python3 -m venv .venv && source .venv/bin/activate
pip install requests scapy
# or: uv init my-scanner && cd my-scanner && uv add requests scapy
# command-line tools you want everywhere: uv tool install httpie   (or pipx install)
```

</Good>
</Compare>

<Compare>
<Bad title="Using Python 2 or an ancient Python 3">

```text
python --version        -> Python 2.7.18   (end of life since 2020)
print "hello"           # Python 2 syntax; SyntaxError in Python 3
```

</Bad>
<Good title="A supported Python 3">

```text
python3 --version       -> Python 3.12 or newer
print("hello")          # print is a function in Python 3
uv python install 3.15  # when the system version is too old
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Windows "Add python.exe to PATH" unticked**: `python` isn't found, or opens the Microsoft Store; tick it, or use `py` / uv.
- **Naming your file after a module**: a script called `json.py` or `random.py` hides the real module when you import it.
- **Forgetting to activate**: `pip install` goes to the wrong Python; check with `which python` (`where python` on Windows) or use `uv run`.
- **Committing `.venv`**: it's large and machine-specific; commit the dependency list and lock file instead.
- **Copying code with smart quotes or mixed tabs and spaces** from documents: Python cares about quotes and indentation.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Windows par "Add python.exe to PATH" tick na karna**: `python` nahi milta, ya Microsoft Store khulta; tick karein, ya `py` / uv lein.
- **File ka naam module jaisa rakhna**: `json.py` ya `random.py` naam ki script import par asal module chhupa deti hai.
- **Activate karna bhoolna**: `pip install` ghalat Python me jata; `which python` (Windows par `where python`) se check karein ya `uv run` lein.
- **`.venv` commit karna**: bara aur machine ke mutabiq hota; is ke bajaye dependency list aur lock file commit karein.
- **Documents se smart quotes ya mili jhuli tabs aur spaces wala code copy karna**: Python quotes aur indentation ka khayal rakhta hai.

</Ur>
</Tr>

<Challenge title="Which Python is running?">

<Tr>
<En>
A teammate says "I installed requests but `import requests` says ModuleNotFoundError". List three commands or checks you'd ask them to run, and the likely causes.
</En>
<Ur>
Ek saathi kehta hai "main ne requests install kiya magar `import requests` ModuleNotFoundError deta hai". Teen commands ya checks batayen jo aap unhe chalane ko kahenge, aur mumkina wajahen.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

1. `python -c "import sys; print(sys.executable)"`: which interpreter is running the code.
2. `python -m pip show requests`: whether that same interpreter has the package. Using `python -m pip` instead of bare `pip` guarantees the same Python.
3. `which -a python python3 pip` (or `where python` on Windows): whether several Pythons are on the PATH.

Likely causes: pip installed into another Python (system vs venv, or 3.12 vs 3.15), the venv isn't activated in this terminal, or the editor (VS Code) uses a different interpreter than the terminal; select the `.venv` interpreter in the editor.

</En>
<Ur>

1. `python -c "import sys; print(sys.executable)"`: kaunsa interpreter code chala raha hai.
2. `python -m pip show requests`: kya usi interpreter ke paas package hai. Khaali `pip` ke bajaye `python -m pip` wahi Python yaqeeni banata hai.
3. `which -a python python3 pip` (Windows par `where python`): kya PATH par kayi Pythons hain.

Mumkina wajahen: pip ne kisi aur Python me install kiya (system ya venv, ya 3.12 ya 3.15), is terminal me venv activate nahi, ya editor (VS Code) terminal se alag interpreter istemal karta hai; editor me `.venv` wala interpreter chunein.

</Ur>

<DeepDive title="More about Python and its tooling">

**Release cycle.** A new feature version every October (3.14 in 2025, 3.15 in 2026), each supported for five years: two with bug fixes, then security fixes only. Check status at devguide.python.org/versions.

**Implementations.** CPython is the reference; PyPy has a JIT for speed; MicroPython runs on microcontrollers. Recent CPython versions added an experimental JIT and a free-threaded build without the GIL.

**How Python runs code.** Source is compiled to bytecode (cached as `.pyc` files in `__pycache__`) and executed by the interpreter's virtual machine, which is why there's no visible compile step.

**Tool landscape.** pip + venv are built in; pipx and `uv tool` install CLI tools in isolation; Poetry and PDM manage projects; uv covers most of these in one fast binary.

**Editors.** VS Code with the Python extension, or PyCharm. Point the editor at the project's `.venv` so autocomplete and the debugger use the right packages.

</DeepDive>

<DeepDive title="Real world: the script that worked on my machine">

A security analyst wrote a log-parsing script on their laptop and shared it with the team. It failed on every other machine: one had Python 3.9, where a newer syntax feature didn't exist; another had a different version of a parsing library that changed its output; the server refused `pip install` entirely because of the system's externally managed Python.

The fixes:

1. The script became a uv project with `.python-version` and `uv.lock` committed.
2. Teammates ran `uv run parse_logs.py`, which installed the right Python and exact packages automatically.
3. The server used the same project, so results were identical everywhere.
4. A short README listed the two commands needed: install uv, then `uv run`.

</DeepDive>

<DeepDive title="Security lens">

- **Install packages only from trusted sources** and watch for typosquatting (`reqeusts` instead of `requests`), a common supply-chain attack on PyPI.
- **Pin and lock dependencies** so a compromised new release isn't pulled in silently; review updates.
- **Don't run `sudo pip install`**: it executes package install code as root and can overwrite system files.
- **Keep Python updated** to a supported version for security fixes; scan dependencies with `pip-audit` or similar.
- **Download installers only from python.org**, your OS package manager or the official uv install instructions.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why is Python so popular for automation and security work?">
It's quick to write and easy to read, has a large standard library for files, networking, parsing and crypto, and a huge ecosystem of packages, so scripts, tools and integrations can be built fast and maintained by others.
</QA>

<QA q="What is a virtual environment and why use one?">
An isolated directory with its own interpreter link and installed packages for one project. It prevents version conflicts between projects and avoids modifying the system Python that OS tools depend on.
</QA>

<QA q="What is the difference between pip and uv?">
pip installs packages into the current environment. uv is a separate, much faster tool that also installs Python versions, creates and manages project environments, resolves and locks dependencies, and runs commands inside the project's environment.
</QA>

<QA q="What is a lock file?">
A file listing the exact resolved version of every direct and indirect dependency, such as uv.lock, so installs are reproducible across machines and over time.
</QA>

<QA q="Is Python compiled or interpreted?">
CPython compiles source to bytecode automatically and then interprets that bytecode, so from the user's point of view it runs scripts directly without a separate build step.
</QA>

</DeepDive>
