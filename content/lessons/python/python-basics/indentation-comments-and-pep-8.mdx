<BigIdea>
<Tr>
<En>
Most languages use braces to group code and indentation only for looks. Python uses **indentation itself**: a line ending in a **colon** (`if`, `for`, `while`, `def`, `class`, `with`, `try`, `match`) starts a **block**, and the block is every following line indented further. When the indentation goes back, the block ends. So indentation must be **consistent**: the standard is **four spaces** per level, and mixing tabs and spaces is an error. **Comments** start with `#` and are ignored by Python; good ones explain **why** (a policy, a workaround, a ticket), because the code already says what. **Docstrings** are strings placed first in a module, function or class; they're stored with the object, so `help()`, editors and documentation tools show them. **PEP 8** is Python's official style guide: `snake_case` for functions and variables, `PascalCase` for classes, `UPPER_CASE` for constants, spaces around operators, one import per line at the top, two blank lines between top-level functions, and lines kept reasonably short. You don't need to memorise it: a **linter** like **ruff** points out problems (including real bugs such as unused variables or `== None`), and a **formatter** (`ruff format`, or Black) rewrites layout automatically, so the whole team's code looks the same.
</En>
<Ur>
Zyadatar languages code group karne ke liye braces aur indentation sirf khoobsurti ke liye istemal karti hain. Python **khud indentation** istemal karta hai: **colon** par khatam line (`if`, `for`, `while`, `def`, `class`, `with`, `try`, `match`) **block** shuru karti hai, aur block woh tamam agli lines hain jo zyada indent hon. Indentation wapas aaye to block khatam. Isliye indentation **mustaqil** honi chahiye: standard har level ke liye **chaar spaces** hai, aur tabs aur spaces milana error hai. **Comments** `#` se shuru hote aur Python unhe nazar andaz karta hai; ache comments **kyun** samjhate hain (policy, jugaar, ticket), kyunke code pehle hi batata hai kya. **Docstrings** module, function ya class me sab se pehle rakhi strings hain; ye object ke saath mehfooz hoti hain, isliye `help()`, editors aur documentation tools unhe dikhate hain. **PEP 8** Python ka sarkari style guide hai: functions aur variables ke liye `snake_case`, classes ke liye `PascalCase`, constants ke liye `UPPER_CASE`, operators ke ird gird spaces, upar har line par ek import, top-level functions ke beech do khaali lines, aur munasib had tak chhoti lines. Ise yaad karne ki zaroorat nahi: **ruff** jaisa **linter** masail batata hai (asal bugs samait, jaise ghair istemal variables ya `== None`), aur **formatter** (`ruff format`, ya Black) layout khud dobara likhta hai, taa ke poori team ka code ek jaisa dikhe.
</Ur>

## Picture it

<Tr>
<En>

Think of an **outline for a document**.

- Headings and sub-points are shown by how far they're indented. Move a bullet left and it no longer belongs to the heading above; that's exactly how Python decides which lines are inside an `if` or a loop.
- Comments are sticky notes in the margin: useful when they say "we do it this way because of the auditor's rule", useless when they say "this is a bullet point".
- PEP 8 is the house style of a publisher: everyone uses the same fonts and spacing so readers can focus on the content.
- The formatter is the copy editor who fixes spacing and layout without touching the meaning; the linter is the proofreader who flags actual mistakes.

</En>

- Headings aur zimni nukaat is se dikhte hain ke kitne andar indent hain. Bullet ko baayen khiskayen to woh upar wali heading ka nahi rehta; bilkul isi tarah Python tay karta hai ke kaunsi lines `if` ya loop ke andar hain.

- PEP 8 publisher ka ghar ka style hai: sab wahi fonts aur spacing istemal karte taa ke parhne wale mawad par dhyan dein.

## Learn it step by step

<Walkthrough>

<Step title="Blocks, the four indentation errors, comments and docstrings">

<Tr>
<En>
`ok.py` has three nested levels (function, loop, if/else) plus a line back at the function's level. Then four tiny files each break indentation differently: a missing indent after `if`, an indent where none belongs, a line indented to a level that doesn't exist, and a tab mixed with spaces. Finally `docs.py` shows a module docstring, a "why" comment and a function docstring, which we read back through `__doc__`.
</En>
<Ur>
`ok.py` me teen nested levels hain (function, loop, if/else) aur ek line wapas function ke level par. Phir chaar chhoti files har ek alag tareeqe se indentation torti hain: `if` ke baad indent ghayab, jahan nahi chahiye wahan indent, aise level par indent line jo mojood nahi, aur spaces ke saath mila tab. Aakhir me `docs.py` module docstring, "kyun" wala comment aur function docstring dikhati hai, jo hum `__doc__` ke zariye wapas parhte hain.
</Ur>
</Tr>

```bash
# Indentation IS the syntax: a block is the indented lines after a colon
cat > ok.py <<'EOF'
def check(ports):
    for port in ports:
        if port < 1024:
            print(port, "privileged")
        else:
            print(port, "unprivileged")
    print("done")          # back at the function's level: runs once, after the loop

check([22, 8080])
EOF
python3 ok.py
printf 'if True:\nprint("no indent")\n' > e1.py
printf 'x = 1\n    y = 2\n' > e2.py
printf 'for i in range(2):\n    print(i)\n  print("half-indented")\n' > e3.py
printf 'if True:\n\tprint("tab")\n        print("spaces")\n' > e4.py
for f in e1 e2 e3 e4; do python3 $f.py 2>&1 | tail -1; done

# Comments explain WHY; docstrings document WHAT a module or function does
cat > docs.py <<'EOF'
"""Helpers for checking login attempts."""

MAX_FAILURES = 5  # matches the identity provider's lockout policy (ticket SEC-142)


def is_locked(failures: int) -> bool:
    """Return True when an account has reached the failure limit.

    Args:
        failures: consecutive failed logins since the last success.
    """
    return failures >= MAX_FAILURES
EOF
python3 -c 'import docs; print(docs.__doc__); print(docs.is_locked.__doc__.splitlines()[0]); print(docs.is_locked(5))'
```

```text output

8080 unprivileged
done
IndentationError: expected an indented block after 'if' statement on line 1
IndentationError: unexpected indent
IndentationError: unindent does not match any outer indentation level
TabError: inconsistent use of tabs and spaces in indentation
Helpers for checking login attempts.
Return True when an account has reached the failure limit.
True
```

<Happened>
<Tr>
<En>

- In `ok.py`, `print("done")` is indented only as far as the `for`, so it's **after** the loop and ran **once**. Indent it four more spaces and it would run on every round: same characters, different program.
- **expected an indented block after 'if' statement**: a colon promises a block, and none came.
- **unexpected indent**: a line was indented where no block had started.
- **unindent does not match any outer indentation level**: the line moved back to 2 spaces, but the only levels were 0 and 4.
- **TabError**: one line used a tab and the next spaces. They can look identical in an editor, which is why the rule is spaces only; set your editor to insert 4 spaces when you press Tab.
- The module and function **docstrings** came back through `__doc__` (and `help(docs)` would show them nicely). The comment next to `MAX_FAILURES` explains **why** the value is 5 and where it comes from; Python ignored it completely.

</En>
<Ur>

- `ok.py` me `print("done")` sirf `for` jitna indent hai, isliye loop ke **baad** hai aur **ek dafa** chala. Chaar spaces aur indent karein to har chakkar par chalta: wahi characters, alag program.
- **expected an indented block after 'if' statement**: colon block ka wada karta hai, aur koi nahi aaya.
- **unexpected indent**: aisi jagah line indent thi jahan koi block shuru nahi hua tha.
- **unindent does not match any outer indentation level**: line 2 spaces par wapas aayi, magar levels sirf 0 aur 4 the.
- **TabError**: ek line ne tab aur agli ne spaces istemal kiye. Editor me ye bilkul ek jaise dikh sakte hain, isi liye qaida sirf spaces hai; editor ko Tab dabane par 4 spaces daalne par set karein.
- Module aur function ki **docstrings** `__doc__` se wapas aayin (aur `help(docs)` unhe achhe se dikhata). `MAX_FAILURES` ke saath comment samjhata hai ke value 5 **kyun** hai aur kahan se aayi; Python ne use poori tarah nazar andaz kiya.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Let ruff lint and format a messy file">

<Tr>
<En>
`messy.py` works, but breaks a lot of PEP 8: several imports on one line, unused imports, CamelCase function and argument names, `== None`, an unused variable, statements crammed onto one line, inconsistent spacing and indentation. `uvx` downloads and runs **ruff** without installing it permanently. We lint the file with the pycodestyle (E, W), pyflakes (F) and naming (N) rules, then let `ruff format` rewrite its layout and check that it still prints the same thing.
</En>
<Ur>
`messy.py` chalti hai, magar PEP 8 ke bohot qaide torti hai: ek line par kayi imports, ghair istemal imports, CamelCase function aur argument naam, `== None`, ghair istemal variable, ek line me thoonse statements, be-tarteeb spacing aur indentation. `uvx` **ruff** ko mustaqil install kiye baghair download kar ke chalata hai. </Ur>
</Tr>

cat > messy.py <<'EOF'
import os, sys
import json
def CheckHost(HostName,Port = 22):
    if HostName == None :
        return False
    result=HostName+':'+str(Port)
    unused = 42
    return result
def main( ):
  hosts=['web1','db1']

<Tr>
<En>

- ruff reported **10 problems** with line and column numbers and a rule code. **F401** (unused imports) and **F841** (unused variable) are often real bugs: a variable you meant to use, or a leftover. **E711** says compare to `None` with `is`. **N802/N803** want `snake_case` names. **E401** and **E701** dislike several imports or statements on one line.

- Program ne pehle aur baad **wahi output** print kiya: formatting kabhi rawaiya nahi badalti, isi liye teams ise save par aur CI me baghair behas chala sakti hain.

## Common mistakes

<Compare>
<Bad title="Comments that repeat the code">

```text
# add 1 to count
count += 1
# loop over users
for user in users:
    # check if locked
    if user.failures >= 5:
```

</Bad>
<Good title="Comments that explain why">

```text
count += 1
for user in users:
    # 5 matches the identity provider's lockout (SEC-142); keep them in sync
    if user.failures >= MAX_FAILURES:
```

</Good>
</Compare>

<Compare>
<Bad title="A line that drifted out of the loop">

```text
total = 0
for size in sizes:
    total += size
print_progress(total)          # meant to run every round, runs once
alert_if_large(total)
```

</Bad>
<Good title="Indent what belongs to the loop">

```text
total = 0
for size in sizes:
    total += size
    print_progress(total)      # every round
alert_if_large(total)          # once, after the loop
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Commented-out code left behind**: delete it; Git remembers.
- **Copying code from web pages or chat** with non-breaking spaces or tabs: reformat it before running.
- **Fighting the formatter**: agree on ruff format or Black and stop debating spacing in reviews.
- **Out-of-date comments** that contradict the code: update or remove them in the same change.
- **Very long lines and deeply nested blocks**: split long expressions inside parentheses, and use guard clauses to reduce nesting.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Comment kiya hua code chhor dena**: delete karein; Git yaad rakhta hai.
- **Web pages ya chat se** non-breaking spaces ya tabs wala code copy karna: chalane se pehle reformat karein.
- **Formatter se larna**: ruff format ya Black par ittefaq karein aur reviews me spacing ki behas band karein.
- **Purane comments** jo code ke khilaf hon: usi tabdeeli me update karein ya hatayen.
- **Bohot lambi lines aur gehre nested blocks**: lambe expressions qauson ke andar torein, aur nesting kam karne ke liye guard clauses lein.

</Ur>
</Tr>

<DeepDive title="More about style and tooling">

**Line continuation.** Inside parentheses, brackets and braces you can break lines freely; avoid backslash continuations. Formatters wrap long calls one argument per line with a trailing comma.

**Docstring conventions.** PEP 257 covers the basics; Google and NumPy styles add sections for Args, Returns and Raises that documentation tools understand.

**Import order.** Standard library, then third-party, then your own modules, each group separated by a blank line; ruff's `I` rules sort them for you.

**Pre-commit hooks.** The `pre-commit` tool runs ruff (and other checks) on every commit, so badly formatted code never reaches the repository.

**Beyond style.** `ruff` also has bug-finding rule sets (B for bugbear, S for security checks similar to Bandit, UP for modernising syntax). Type checkers like mypy and pyright are covered with type hints later.

</DeepDive>

<DeepDive title="Real world: the deploy that ran twice">

A deployment script restarted services in a loop and then posted a summary to the team chat. During a quick edit in a web-based editor, the `notify_chat()` line was accidentally indented into the loop. The script still ran without errors, but now posted a "deploy finished" message after each of 40 services, and the on-call engineer, seeing "finished" early, started verifying a half-deployed system.

The fixes:

1. Code review with a diff that showed the indentation change clearly.
2. ruff format in CI so indentation was always standard and changes stood out.
3. A test that mocks `notify_chat` and asserts it's called exactly once.
4. Editors set to show whitespace and indentation guides.

</DeepDive>

<DeepDive title="Security lens">

- **Linters catch security smells**: ruff's S rules flag `eval`, `subprocess` with `shell=True`, hard-coded passwords, weak hashes and insecure temp files.
- **Unused imports and variables** can hide mistakes, such as a sanitised value that's computed but never used.
- **Don't put secrets or internal URLs in comments**; comments ship with the code and live in Git history.
- **Consistent formatting makes malicious changes easier to spot** in reviews; hidden characters (zero-width spaces, look-alike letters) are a known supply-chain trick that linters and editors can highlight.
- **Readable code is reviewable code**: clear names and small blocks are a security feature.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why does indentation matter in Python?">
It is the syntax that defines blocks. Lines indented under a header ending in a colon belong to that block, so changing indentation can change which code runs, and inconsistent indentation is a syntax error.
</QA>

<QA q="What is PEP 8?">
The official style guide for Python code, covering naming conventions, indentation, whitespace, line length, imports and other layout rules to keep code consistent and readable.
</QA>

<QA q="What is the difference between a comment and a docstring?">
A comment starts with # and is discarded by the interpreter. A docstring is a string literal as the first statement of a module, class or function, stored in its doc attribute and shown by help and documentation tools.
</QA>

<QA q="What's the difference between a linter and a formatter?">
A linter analyses code for style violations and likely bugs and reports them, sometimes with fixes. A formatter rewrites the code's layout to a consistent style without changing its behaviour.
</QA>

<QA q="Why use is None instead of == None?">
None is a singleton, so identity is the correct and fastest check, and == can be overridden by a class's equality method to return surprising results.
</QA>

</DeepDive>
