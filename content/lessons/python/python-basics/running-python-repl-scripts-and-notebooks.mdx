<BigIdea>
<Tr>
<En>
The **REPL** (Read, Eval, Print, Loop) is what you get when you type `python3` with nothing after it: a `>>>` prompt where each line runs immediately and the value of an expression is printed for you. It's a calculator, a scratchpad and a way to explore an object (`type()`, `dir()`, `help()`), but nothing you type is saved. A **script** is a `.py` file you run with `python3 file.py`: it's saved, repeatable, can be versioned in Git, takes **arguments** (`sys.argv`), and tells the caller whether it worked with an **exit code** (0 means success). That makes scripts the backbone of automation, cron jobs and CI. A **Jupyter notebook** (`.ipynb`) is a document of cells you run one at a time, keeping each cell's output (tables, charts) next to the code and your notes; it's ideal for exploring data and writing up an investigation, less so for code that has to run unattended. Most real work moves through all three: try an idea in the REPL, explore in a notebook, then turn it into a script.
</En>
<Ur>
**REPL** (Read, Eval, Print, Loop) woh hai jo `python3` ke baad kuch na likhne par milta hai: `>>>` prompt jahan har line foran chalti aur expression ki value aap ke liye print hoti hai. Ye calculator, kachcha kaam karne ki jagah, aur kisi object ko khangalne ka tareeqa hai (`type()`, `dir()`, `help()`), magar jo likhein woh save nahi hota. **Script** `.py` file hai jo `python3 file.py` se chalti hai: save hoti, dohrayi ja sakti, Git me rakhi ja sakti, **arguments** leti (`sys.argv`), aur **exit code** se bulane wale ko batati hai ke kaam hua ya nahi (0 ka matlab kamyabi). Isi liye scripts automation, cron jobs aur CI ki reerh ki haddi hain. **Jupyter notebook** (`.ipynb`) cells ka document hai jinhe aap ek ek kar ke chalate hain, har cell ka output (tables, charts) code aur aap ke notes ke saath rehta hai; ye data khangalne aur tehqeeq likhne ke liye behtareen hai, aise code ke liye kam jo baghair nigrani chale. Zyadatar asal kaam teeno se guzarta hai: REPL me idea aazmayen, notebook me khangalein, phir use script banayen.
</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="The REPL: instant answers">

<Tr>
<En>
In a terminal you'd type `python3` and then lines at the `>>>` prompt. To show a session here, `replay.py` feeds lines into Python's own REPL engine (the `code` module, which powers the interactive prompt) and prints them with the prompts, exactly as you'd see them. We try arithmetic, `_`, a variable, a method, `len` and `type`, a multi-line loop (note the `...` continuation prompt and the empty line that ends it), and an error.
</En>
<Ur>
Terminal me aap `python3` likh kar `>>>` prompt par lines likhenge. Yahan session dikhane ke liye `replay.py` lines ko Python ke apne REPL engine (`code` module, jo interactive prompt chalata hai) me daalta aur prompts ke saath print karta hai, bilkul jaise aap dekhenge. Hum hisaab, `_`, variable, method, `len` aur `type`, kayi line ka loop (`...` continuation prompt aur use khatam karne wali khaali line dekhein), aur ek error aazmate hain.
</Ur>
</Tr>

```bash
# Python's own REPL engine (the code module), fed the lines you'd type at >>>
cat > replay.py <<'EOF'
import code, sys
console = code.InteractiveConsole()
more = False
for line in sys.stdin.read().splitlines():
    print(("... " if more else ">>> ") + line, flush=True)
    more = console.push(line)
EOF
python3 replay.py 2>&1 <<'EOF'
2 + 3
_ * 10
name = "Jane"
name.upper()
len(name)
type(3.5)
for port in [22, 80, 443]:
    print("open:", port)

10 / 0
print("the REPL keeps going after an error")
EOF
```

```text output
>>> 2 + 3
5
>>> _ * 10
50
>>> name = "Jane"
>>> name.upper()
'JANE'
>>> len(name)
4
>>> type(3.5)
<class 'float'>
>>> for port in [22, 80, 443]:
...     print("open:", port)
... 
open: 22
open: 80
open: 443
>>> 10 / 0
Traceback (most recent call last):
  File "<console>", line 1, in <module>
ZeroDivisionError: division by zero
>>> print("the REPL keeps going after an error")
the REPL keeps going after an error
```

<Happened>
<Tr>
<En>

- Expressions like `2 + 3` and `name.upper()` printed their value **without `print()`**: that's the "P" in REPL. The assignment `name = "Jane"` is a statement, so nothing was shown.
- `_` held the **last result** (5), so `_ * 10` gave 50: handy for calculations.
- `type(3.5)` showed **`<class 'float'>`**: the REPL is the fastest way to ask Python what something is. `dir(obj)` lists what you can do with it and `help(obj)` shows its documentation.
- The `for` line opened a block, so the prompt changed to **`...`** until an empty line ended it, then the loop ran.
- `10 / 0` printed a **traceback** ending in `ZeroDivisionError: division by zero`, and the session **carried on**. Read tracebacks from the bottom: the last line says what went wrong, the lines above say where.
- Since Python 3.13 the real REPL also has colours, multi-line editing with arrow keys, and `exit` works without parentheses. For an even richer shell, try IPython.

</En>
<Ur>

- `2 + 3` aur `name.upper()` jaise expressions ne apni value **`print()` ke baghair** dikhayi: yahi REPL ka "P" hai. Assignment `name = "Jane"` statement hai, isliye kuch nahi dikha.
- `_` me **pichhla natija** (5) tha, isliye `_ * 10` ne 50 diya: hisaab ke liye kaam ka.
- `type(3.5)` ne **`<class 'float'>`** dikhaya: Python se kisi cheez ke bare me poochne ka sab se tez tareeqa REPL hai. `dir(obj)` batata hai us ke saath kya kar sakte, aur `help(obj)` us ki documentation dikhata hai.
- `for` line ne block khola, isliye prompt **`...`** ho gaya jab tak khaali line ne use khatam na kiya, phir loop chala.
- `10 / 0` ne `ZeroDivisionError: division by zero` par khatam hone wala **traceback** print kiya, aur session **chalta raha**. Tracebacks neeche se parhein: aakhri line batati kya ghalat hua, upar wali lines batati kahan.
- Python 3.13 se asal REPL me rang, arrow keys se kayi line ki editing bhi hai, aur `exit` qauson ke baghair chalta hai. Aur behtar shell ke liye IPython aazmayen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Scripts: arguments, exit codes, shebang and __name__">

<Tr>
<En>
`check_ports.py` takes port numbers as arguments and reports which are in an allow-list. It returns exit code **0** if all are allowed, **1** if any aren't, and **2** for wrong usage. We run it three ways, run it directly thanks to its shebang line, import it from another piece of code, and finally use `-m` to run a standard-library module as a tool.
</En>
<Ur>
`check_ports.py` port numbers arguments ki tarah leti aur batati hai ke kaunse allow-list me hain. Sab ijazat yafta hon to exit code **0**, koi na ho to **1**, aur ghalat istemal par **2** lautati hai. Hum ise teen tareeqon se chalate, shebang line ki badaulat seedha chalate, doosre code se import karte, aur aakhir me `-m` se standard library ka module tool ki tarah chalate hain.
</Ur>
</Tr>

```bash
cat > check_ports.py <<'EOF'
#!/usr/bin/env python3
"""Check which of the given ports are in an allow-list."""
import sys

ALLOWED = {22, 80, 443}

def main(args):
    if not args:
        print("usage: check_ports.py PORT [PORT ...]", file=sys.stderr)
        return 2                       # exit code 2: wrong usage
    bad = [int(p) for p in args if int(p) not in ALLOWED]
    for p in args:
        print(f"{p:>5}  {'ok' if int(p) in ALLOWED else 'NOT ALLOWED'}")
    return 1 if bad else 0             # non-zero tells scripts and CI that something failed

if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
EOF
python3 check_ports.py 22 443;      echo "exit code: $?"
python3 check_ports.py 80 3306;     echo "exit code: $?"
python3 check_ports.py;             echo "exit code: $?"
chmod +x check_ports.py && ./check_ports.py 22 && echo "(ran directly thanks to the #! line)"
# Importing the file does NOT run main(): __name__ is the module name, not "__main__"
python3 -c 'import check_ports; print("imported; ALLOWED =", sorted(check_ports.ALLOWED))'
# -m runs a module from the standard library (or your package) as a script
echo '{"host":"example.test","ports":[22,443]}' | python3 -m json.tool --indent 2
```

```text output
   22  ok
  443  ok
exit code: 0
   80  ok
 3306  NOT ALLOWED
exit code: 1
usage: check_ports.py PORT [PORT ...]
exit code: 2
   22  ok
(ran directly thanks to the #! line)
imported; ALLOWED = [22, 80, 443]
{
  "host": "example.test",
  "ports": [
    22,
    443
  ]
}
```

<Happened>
<Tr>
<En>

- `sys.argv[1:]` held the arguments as **strings** (`'22'`, `'443'`), so the script converted them with `int()`. `sys.argv[0]` is the script's own name.
- The exit codes **0, 1 and 2** were visible through `$?`. That's how shell scripts, cron, CI pipelines and other programs know whether your script succeeded; `sys.exit(main(...))` passes the number on. The usage message went to **stderr** so it doesn't mix with real output.
- After `chmod +x`, `./check_ports.py 22` worked because of the **shebang** line `#!/usr/bin/env python3`, which tells Linux and macOS which interpreter to use. (Windows ignores it; the `py` launcher can read it.)
- Importing the file printed `ALLOWED` but **didn't run `main()`**: when a file is imported, `__name__` is its module name, not `"__main__"`. That guard lets the same file be both a runnable script and a reusable module.
- `python3 -m json.tool` ran a module from the standard library as a command and pretty-printed the JSON. Other useful ones: `python3 -m http.server` (serve a folder), `python3 -m venv`, `python3 -m pip`.

</En>
<Ur>

- `sys.argv[1:]` me arguments **strings** ki tarah the (`'22'`, `'443'`), isliye script ne unhe `int()` se badla. `sys.argv[0]` script ka apna naam hai.
- Exit codes **0, 1 aur 2** `$?` se nazar aaye. Isi tarah shell scripts, cron, CI pipelines aur doosre programs jaante hain ke aap ki script kamyab hui ya nahi; `sys.exit(main(...))` number aage deta hai. Usage paigham **stderr** par gaya taa ke asal output se na mile.
- `chmod +x` ke baad `./check_ports.py 22` **shebang** line `#!/usr/bin/env python3` ki wajah se chala, jo Linux aur macOS ko interpreter batati hai. (Windows ise nazar andaz karta; `py` launcher parh sakta hai.)
- File import karne par `ALLOWED` print hua magar **`main()` nahi chala**: import hone par `__name__` module ka naam hota hai, `"__main__"` nahi. Ye guard ek hi file ko chalne wali script aur dobara istemal hone wala module dono banne deta hai.
- `python3 -m json.tool` ne standard library ka module command ki tarah chalaya aur JSON saaf print kiya. Doosre kaam ke: `python3 -m http.server` (folder serve), `python3 -m venv`, `python3 -m pip`.

</Ur>
</Tr>
</Happened>

<Step title="Notebooks: cells with saved outputs">

<Tr>
<En>
A notebook file is just **JSON**: a list of cells with their source code and, after running, their outputs. `make_nb.py` creates `logins.ipynb` with three cells about failed logins. Jupyter's `nbconvert` then runs it from top to bottom in a Python 3.15 kernel (exactly what "Run All" does in JupyterLab or VS Code) and saves the outputs into the file, and we read them back.
</En>
<Ur>
Notebook file bas **JSON** hai: cells ki list, un ke source code ke saath aur chalne ke baad un ke outputs. `make_nb.py` failed logins ke bare me teen cells wali `logins.ipynb` banati hai. Phir Jupyter ka `nbconvert` ise Python 3.15 kernel me upar se neeche chalata (bilkul jo JupyterLab ya VS Code me "Run All" karta hai) aur outputs file me save karta hai, aur hum unhe wapas parhte hain.
</Ur>
</Tr>

```bash
# A notebook is a JSON file of cells; Jupyter runs them in order and stores each output
cat > make_nb.py <<'EOF'
import json
cells = [
    "failed_logins = {'jane': 2, 'john': 7, 'admin': 31}",
    "total = sum(failed_logins.values())\ntotal",
    "for user, n in sorted(failed_logins.items(), key=lambda x: -x[1]):\n    print(f'{user:<6} {n:>3} ' + '#' * (n // 2))",
]
nb = {"nbformat": 4, "nbformat_minor": 5, "metadata": {"kernelspec": {"name": "python3", "display_name": "Python 3", "language": "python"}},
      "cells": [{"cell_type": "code", "id": f"c{i}", "metadata": {}, "source": s, "outputs": [], "execution_count": None} for i, s in enumerate(cells)]}
json.dump(nb, open("logins.ipynb", "w"), indent=1)
EOF
python3 make_nb.py
uv run -q --no-project --python 3.15 --with nbconvert==7.17.2 --with ipykernel==7.4.0 \
  jupyter nbconvert --to notebook --execute --inplace logins.ipynb 2> /dev/null
python3 - <<'EOF'
import json
for cell in json.load(open("logins.ipynb"))["cells"]:
    source = "".join(cell["source"])
    print(f"In [{cell['execution_count']}]:", source.splitlines()[0])
    for out in cell["outputs"]:
        text = out.get("text") or out.get("data", {}).get("text/plain", "")
        print("".join(text).rstrip())
EOF
```

```text output
In [1]: failed_logins = {'jane': 2, 'john': 7, 'admin': 31}
In [2]: total = sum(failed_logins.values())
40
In [3]: for user, n in sorted(failed_logins.items(), key=lambda x: -x[1]):
admin   31 ###############
john     7 ###
jane     2 #
```

<Happened>
<Tr>
<En>

- Each cell got an **execution number** (`In [1]`, `In [2]`, `In [3]`) showing the order it ran in.
- Cell 1 only assigned a variable, so it had **no output**. Cell 2 ended with the expression `total`, and like the REPL the notebook displayed it (**40**). Cell 3 used `print()` and its text, a small bar chart of failed logins, was saved too.
- Variables live in the **kernel** between cells: cell 2 used `failed_logins` from cell 1. That's powerful but risky: running cells out of order, or deleting a cell whose variable others still use, leaves a notebook that only works in your current session. Use "Restart and Run All" before sharing.
- Because outputs are stored in the file, a notebook can show results without being re-run, which is why they're great for reports, and why you should clear outputs that contain secrets or personal data before committing.

</En>
<Ur>

- Har cell ko **execution number** mila (`In [1]`, `In [2]`, `In [3]`) jo chalne ki tarteeb dikhata hai.
- Cell 1 ne sirf variable assign kiya, isliye **koi output nahi**. Cell 2 expression `total` par khatam hua, aur REPL ki tarah notebook ne use dikhaya (**40**). Cell 3 ne `print()` istemal kiya aur us ka text, failed logins ka chhota bar chart, bhi save hua.
- Variables cells ke beech **kernel** me rehte hain: cell 2 ne cell 1 ka `failed_logins` istemal kiya. Ye taqatwar magar khatarnak hai: cells be-tarteeb chalana, ya aisa cell delete karna jis ka variable doosre ab bhi istemal karte, aisi notebook chhorta hai jo sirf aap ke mojooda session me chalti hai. Share karne se pehle "Restart and Run All" karein.
- Kyunke outputs file me rehte hain, notebook dobara chalaye baghair natije dikha sakti hai, isi liye reports ke liye behtareen hai, aur isi liye commit se pehle secrets ya zaati data wale outputs saaf karein.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Typing shell commands at the Python prompt (and the reverse)">

```text
>>> pip install requests
  File "<stdin>", line 1
    pip install requests
        ^^^^^^^
SyntaxError: invalid syntax

$ print("hi")
bash: syntax error near unexpected token `"hi"'
```

</Bad>
<Good title="Know which prompt you're at">

```text
$ pip install requests        # $ or PS> : the shell (terminal)
$ python3 tool.py
>>> import requests           # >>> : the Python REPL
>>> exit()
```

</Good>
</Compare>

<Compare>
<Bad title="A script that always succeeds">

```text
def main():
    if not config_ok():
        print("config error")
        return              # exit code 0: cron and CI think everything worked
main()
```

</Bad>
<Good title="Report failure with the exit code">

```text
import sys
def main():
    if not config_ok():
        print("config error", file=sys.stderr)
        return 1
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Expecting the REPL to save your work**: paste anything worth keeping into a `.py` file.
- **Forgetting `print()` in scripts**: a bare expression like `total` shows in the REPL but prints nothing in a script.
- **Windows line endings in a shebang script** (`\r\n`): Linux reports `/usr/bin/env: 'python3\r': No such file`; save with LF endings.
- **Out-of-order notebook cells**: always restart and run all before trusting or sharing a result.
- **Committing notebooks with huge outputs or secrets**: clear outputs, or use tools like `nbstripout`.

</En>

<DeepDive title="More about running Python">

**IPython and Jupyter.** IPython is an enhanced REPL with tab completion, `?` for help, `%timeit` and shell commands with `!`; Jupyter kernels are built on it. JupyterLab, VS Code and Google Colab all open `.ipynb` files.

**Interpreter flags.** `-c` runs a string, `-m` a module, `-i` enters the REPL after a script, `-u` disables output buffering (useful in Docker logs), `-X importtime` shows slow imports, `-W error` turns warnings into errors.

**Script metadata.** A script can declare its own dependencies in a `# /// script` comment block (PEP 723); `uv run script.py` reads it and installs them in a temporary environment, which is great for single-file tools.

**Command-line interfaces.** For more than a couple of arguments, use `argparse` from the standard library (help text, types, defaults) or libraries like Typer and Click.

**Notebooks in Git.** Pair a notebook with a plain `.py` version using Jupytext, or strip outputs with nbstripout, so diffs stay readable.

</DeepDive>

<DeepDive title="Real world: the cron job that never failed">

An operations team had a Python script that rotated logs and uploaded them to object storage every night. One week the storage credentials expired. The script caught the exception, printed "upload failed" and finished normally, so its exit code was 0. Cron considered every run a success, the monitoring dashboard stayed green, and three weeks of logs were silently missing when an incident investigation needed them.

The fixes:

1. Errors are written to stderr and the script returns exit code 1 on any failure.
2. The scheduler alerts on non-zero exit codes and on runs that don't happen at all (a "dead man's switch" check-in).
3. The script logs a final summary line with counts, which the monitoring system checks.
4. A test calls `main()` with broken credentials and asserts it returns non-zero.

</DeepDive>

<DeepDive title="Security lens">

- **Don't paste untrusted code into the REPL or a notebook**: it runs with your user's permissions and credentials.
- **Notebooks from strangers are code**: opening is safe, running cells is not; read them first.
- **Clear notebook outputs** that contain tokens, personal data or internal hostnames before sharing or committing.
- **Never put secrets in command-line arguments**: other users on the machine can see them in the process list; use environment variables or files.
- **Watch `python3 -m http.server`**: it serves the whole folder to anyone who can reach the port; bind it to `127.0.0.1` with `--bind`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does if __name__ == '__main__' do?">
It runs the guarded code only when the file is executed directly. When the file is imported, `__name__` is the module's name, so importers get its functions and classes without triggering the script's main behaviour.
</QA>

<QA q="Why do exit codes matter for scripts?">
Shells, schedulers, CI systems and other programs decide whether a command succeeded by its exit code. Returning non-zero on failure lets pipelines stop, retries happen and alerts fire.
</QA>

<QA q="What is the difference between python script.py and python -m package.module?">
The first runs a file by path. The second finds a module through the import system and runs it as `__main__`, so imports inside a package work correctly and you can run tools that ship with Python or installed packages.
</QA>

<QA q="What are the downsides of notebooks?">
Hidden state from out-of-order execution, hard-to-review diffs, outputs that can leak data, and difficulty testing and reusing code. Mature code is usually moved into modules and scripts that notebooks import.
</QA>

<QA q="What does the shebang line do?">
On Unix-like systems, #!/usr/bin/env python3 tells the OS which interpreter to use when the file is executed directly, after it has been made executable with chmod +x.
</QA>

</DeepDive>
