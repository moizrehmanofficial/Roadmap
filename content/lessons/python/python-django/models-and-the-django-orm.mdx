<BigIdea>
<Tr>
<En>
A **model** is a Python class that describes a database table: each **field** (`CharField`, `DecimalField`, `ForeignKey`...) becomes a column, and each instance is a row. Django's **ORM** (object-relational mapper) turns Python queries into SQL for whichever database you use (SQLite in development, PostgreSQL or MySQL in production), always with **parameters**, so normal ORM code is safe from SQL injection. Schema changes are tracked as **migrations**: `makemigrations` writes a migration file describing what changed in your models, `sqlmigrate` shows the SQL it will run, and `migrate` applies it. Queries start from a model's **manager**, `Product.objects`, and return **QuerySets**: lazy, chainable descriptions of a query (`.filter(stock__gt=0).exclude(...).order_by("-price")[:10]`) that only hit the database when you iterate, slice or evaluate them. Double underscores express **lookups** (`price__lt=50`) and follow **relations** (`category__name="Audio"`). **Aggregates** (`Count`, `Sum`, `Avg`) summarize, and `annotate` adds computed values per row. Good ORM code also knows the database: use **`select_related`/`prefetch_related`** to avoid the N+1 query problem, **`F()`** expressions to update values in the database without race conditions, **`transaction.atomic`** for all-or-nothing changes, and **constraints** so the database itself rejects bad data.
</En>
<Ur>
**Model** aisi Python class hai jo database table bayan karti: har **field** (`CharField`, `DecimalField`, `ForeignKey`...) column banti, aur har instance ek row. Django ka **ORM** (object-relational mapper) Python queries ko jo bhi database aap istemal karein (development me SQLite, production me PostgreSQL ya MySQL) us ke SQL me badalta, hamesha **parameters** ke saath, isliye aam ORM code SQL injection se mehfooz hai. Schema ki tabdeeliyan **migrations** ki shakal me record hoti hain: `makemigrations` aap ke models me kya badla us ki migration file likhta, `sqlmigrate` dikhata ke kaun sa SQL chalega, aur `migrate` use lagu karta hai. Queries model ke **manager** `Product.objects` se shuru hoti aur **QuerySets** lautati hain: query ki lazy, zanjeer banane layak tafseel (`.filter(stock__gt=0).exclude(...).order_by("-price")[:10]`) jo sirf tab database tak jati jab aap iterate, slice ya evaluate karein. Dohre underscores **lookups** (`price__lt=50`) bayan karte aur **relations** follow karte hain (`category__name="Audio"`). **Aggregates** (`Count`, `Sum`, `Avg`) khulasa banate, aur `annotate` har row me hisaab ki values jorta hai. Achha ORM code database ko bhi samajhta hai: N+1 query masle se bachne ke liye **`select_related`/`prefetch_related`**, race conditions ke baghair database me values update karne ke liye **`F()`** expressions, sab ya kuch nahi wali tabdeeliyon ke liye **`transaction.atomic`**, aur **constraints** taa ke database khud ghalat data radd kare.
</Ur>

<Why>
<Tr>
<En>

- Models are the single source of truth for your schema, versioned with migrations.
- QuerySets are composable and database-independent, and parameterized by default.
- Most Django performance and data-integrity problems are ORM problems: N+1 queries, races, missing constraints.

</En>
<Ur>

- Models aap ke schema ka wahid sachcha zariya hain, migrations ke saath versioned.
- QuerySets jor ke banne wale aur database se azad hain, aur default me parameterized.
- Django ke zyadatar performance aur data-integrity ke masail ORM ke masail hain: N+1 queries, races, ghayab constraints.

</Ur>
</Tr>

```text
from django.db import transaction
from django.db.models import F

@transaction.atomic
def place_order(product_id, qty):
    updated = (Product.objects
               .filter(id=product_id, stock__gte=qty)        # check and update in one statement
               .update(stock=F("stock") - qty))
    if not updated:
        raise ValueError("out of stock")
    return Order.objects.create(product_id=product_id, quantity=qty)
```

## Picture it

<Tr>
<En>

Think of a **library with a very fast librarian**.

- Models are the catalogue cards that define what's recorded about each book (title, shelf, author).
- A QuerySet is a request slip you keep refining ("science books... in English... newest first... top 10") without the librarian moving yet; only when you say "bring them" (iterate) do they fetch.
- The N+1 problem is asking for ten books and then sending the librarian back to the author shelf ten separate times; `select_related` is asking for books *with* their authors in one trip.
- `F()` is telling the librarian "reduce the copies count by one" instead of reading the number, walking away, and writing your own number back, which goes wrong if two people do it at once.

</En>
<Ur>

**Bohat tez librarian wali library** socheyn.

- Models catalogue cards hain jo tay karti ke har kitaab ke bare me kya likha jaye (unwaan, shelf, musannif).
- QuerySet darkhwast ki parchi hai jise aap behtar karte rehte ("science ki kitaben... English me... nayi pehle... top 10") jabke librarian abhi hila nahi; sirf jab aap kehte "le aao" (iterate) tab woh laata hai.
- N+1 masla das kitaben maang kar phir librarian ko das alag dafa musannif wali shelf par bhejna hai; `select_related` ek hi chakkar me kitaben *un ke musannifon ke saath* maangna hai.
- `F()` librarian se kehna hai "copies ki ginti ek kam kar do", number parh kar, ja kar, apna number wapas likhne ke bajaye, jo do log ek saath karein to bigar jata hai.

</Ur>
</Tr>

```bash
from django.db import models

class Category(models.Model):
    name = models.CharField(max_length=50, unique=True)

    def __str__(self):
        return self.name

class Product(models.Model):
    category = models.ForeignKey(Category, on_delete=models.PROTECT, related_name="products")
    name = models.CharField(max_length=100)
    sku = models.CharField(max_length=20, unique=True)
    price = models.DecimalField(max_digits=8, decimal_places=2)
    stock = models.PositiveIntegerField(default=0)
    active = models.BooleanField(default=True)
    created = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["name"]
        constraints = [models.CheckConstraint(condition=models.Q(price__gt=0), name="price_positive")]

    def __str__(self):
        return f"{self.name} ({self.sku})"
EOF

    Product(category=periph, name="Mouse", sku="MS-01", price=Decimal("19.99"), stock=0),
    Product(category=periph, name="Webcam", sku="WC-01", price=Decimal("64.00"), stock=5, active=False),

    Product(category=audio, name="Speaker", sku="SP-01", price=Decimal("120.00"), stock=8),

print("all:", [p.name for p in Product.objects.all()])                     # Meta.ordering = name
print("in stock and active:", list(Product.objects.filter(active=True, stock__gt=0).values_list("sku", flat=True)))
print("under $50 or out of stock:", [p.name for p in Product.objects.filter(Q(price__lt=50) | Q(stock=0))])

t = Product.objects.aggregate(items=Count("id"), avg_price=Avg("price"), units=Sum("stock"))
print("totals:", t["items"], "products, average price", round(t["avg_price"], 2), "|", t["units"], "units in stock")
for c in Category.objects.annotate(n=Count("products"), stock_value=Sum(F("products__price") * F("products__stock"))).order_by("name"):
    print(f"  {c.name:<12} products={c.n}  stock value=${c.stock_value}")
```

<Happened>
<Tr>
<En>

- `makemigrations` compared the models with the previous migrations (none) and wrote **0001_initial.py**; `sqlmigrate` showed the `CREATE TABLE` it will run. Commit migration files with your code, and review them like code.
- `bulk_create` inserted five rows in one query. `Meta.ordering = ["name"]` made `all()` come back alphabetically without asking.
- `filter(active=True, stock__gt=0)` combined conditions with AND; `Q(price__lt=50) | Q(stock=0)` expressed OR; `exclude(category__name=...)` followed the ForeignKey with a double underscore, which becomes a JOIN.
- `get()` returned exactly one object (it raises `DoesNotExist` or `MultipleObjectsReturned` otherwise), and `price` came back as a **Decimal**, never a float, which is what you want for money.
- `aggregate` returned totals for the whole table, while `annotate` computed **per category** values (product count and stock value) with `Count` and `Sum` over `F()` expressions, all in one SQL query with `GROUP BY`. (SQLite drops trailing zeros in that computed sum; PostgreSQL keeps decimals exact.)
- `str(queryset.query)` showed the SQL Django generates, handy for debugging. The real query is always sent with parameters, which is why ORM filters are safe from SQL injection.

</En>
<Ur>

- `makemigrations` ne models ko pichhli migrations (koi nahi) se mila kar **0001_initial.py** likhi; `sqlmigrate` ne woh `CREATE TABLE` dikhaya jo chalega. Migration files code ke saath commit karein, aur code ki tarah review karein.

- `filter(active=True, stock__gt=0)` ne sharait AND se jorin; `Q(price__lt=50) | Q(stock=0)` ne OR bayan kiya; `exclude(category__name=...)` ne dohre underscore se ForeignKey follow ki, jo JOIN ban jati hai.
- `get()` ne bilkul ek object lautaya (warna `DoesNotExist` ya `MultipleObjectsReturned` uthata hai), aur `price` **Decimal** ban kar wapas aaya, float kabhi nahi, jo paise ke liye chahiye.
- `aggregate` ne poori table ke totals lautaye, jabke `annotate` ne `F()` expressions par `Count` aur `Sum` ke saath **har category** ki values (products ki ginti aur stock value) hisaab kin, sab `GROUP BY` wali ek SQL query me. (SQLite us hisaab wale jama me aakhri zeros gira deta; PostgreSQL decimals bilkul durust rakhta hai.)
- `str(queryset.query)` ne Django ka banaya SQL dikhaya, debugging ke liye kaam ka. Asal query hamesha parameters ke saath bheji jati, isi liye ORM filters SQL injection se mehfooz hain.

<Step title="N+1 queries, F() updates, transactions, constraints and safe raw SQL">

<Tr>
<En>
`orm_details.py` uses the same database. It counts the queries needed to print each product with its category, with and without `select_related`; decrements stock with an `F()` update; runs a transaction where the second statement fails and checks the first was rolled back; triggers the price check constraint; tries to delete a category that still has products; uses `get_or_create`; and runs a parameterized raw query with an injection attempt.
</En>
<Ur>
`orm_details.py` wahi database istemal karti hai. Ye `select_related` ke saath aur baghair har product ko us ki category ke saath print karne ke liye queries ginti; `F()` update se stock kam karti; aisi transaction chalati jis ka doosra statement nakam hota aur check karti ke pehla rollback hua; price ki check constraint chalati; aisi category delete karne ki koshish karti jis ke products abhi hain; `get_or_create` istemal karti; aur injection koshish ke saath parameterized raw query chalati hai.
</Ur>
</Tr>

```bash
. .venv/bin/activate && cd shop
cat > orm_details.py <<'EOF'
import os, django
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings"); django.setup()
from decimal import Decimal
from django.db import IntegrityError, connection, transaction
from django.db.models import F, ProtectedError
from django.test.utils import CaptureQueriesContext
from catalog.models import Category, Product

# 1. The N+1 query problem and select_related
with CaptureQueriesContext(connection) as q:
    names = [f"{p.name}/{p.category.name}" for p in Product.objects.all()]     # 1 + one per product
print("without select_related:", len(q.captured_queries), "queries")
with CaptureQueriesContext(connection) as q:
    names = [f"{p.name}/{p.category.name}" for p in Product.objects.select_related("category")]
print("with select_related:   ", len(q.captured_queries), "query (a JOIN)")

# 2. Updates in the database with F() (no read-modify-write race)
Product.objects.filter(sku="KB-01").update(stock=F("stock") - 2)
print("keyboard stock after selling 2:", Product.objects.get(sku="KB-01").stock)

# 3. Transactions: all or nothing
try:
    with transaction.atomic():
        Product.objects.filter(sku="HS-01").update(stock=F("stock") - 1)
        Product.objects.create(category_id=1, name="Broken", sku="KB-01", price=Decimal("5"))  # duplicate SKU
except IntegrityError as e:
    print("IntegrityError:", str(e).split(":")[0], "-> headset stock still", Product.objects.get(sku="HS-01").stock)

# 4. Constraints are enforced by the database
try:
    Product.objects.create(category_id=1, name="Free thing", sku="FR-01", price=Decimal("0"))
except IntegrityError as e:
    print("IntegrityError:", e)

# 5. on_delete=PROTECT stops deleting a category that still has products
try:
    Category.objects.get(name="Audio").delete()
except ProtectedError:
    print("ProtectedError: Audio still has products")

# 6. get_or_create, and safe raw SQL with parameters
cat, created = Category.objects.get_or_create(name="Cables")
print("get_or_create:", cat.name, "created:", created, "| second time created:", Category.objects.get_or_create(name="Cables")[1])
user_input = "x' OR '1'='1"
safe = Product.objects.raw("SELECT * FROM catalog_product WHERE sku = %s", [user_input])
print("parameterized raw SQL with injection attempt returns:", len(list(safe)), "rows")
EOF
python orm_details.py
```

<Happened>
<Tr>
<En>

- Accessing `p.category` inside the loop ran **6 queries**: one for the products plus one per product. With 5,000 products that's 5,001 queries and a slow page. `select_related("category")` fetched everything in **1 query** with a JOIN. Use `CaptureQueriesContext` (or django-debug-toolbar) to spot this.
- `update(stock=F("stock") - 2)` ran a single `UPDATE ... SET stock = stock - 2` in the database: no read-then-write, so two simultaneous sales can't overwrite each other.
- Inside `transaction.atomic()`, the headset stock update succeeded but the duplicate SKU raised **IntegrityError**, so the whole block **rolled back**: headset stock was still 3. Without the transaction, half the operation would have been saved.
- The database itself rejected a zero price with the **price_positive** CHECK constraint. Validation in forms is good; constraints guarantee it for every code path, scripts and admin included.
- `on_delete=PROTECT` raised **ProtectedError** instead of silently deleting products along with their category, as `CASCADE` would have.
- `get_or_create` created "Cables" once and found it the second time. The raw query passed the malicious input as a **parameter** (`%s` plus a list), so it was treated as a literal SKU and matched nothing. Never build SQL with f-strings.

</En>
<Ur>

- Loop ke andar `p.category` parhne se **6 queries** chalin: products ke liye ek aur har product ki ek. 5,000 products par ye 5,001 queries aur dheema page hai. `select_related("category")` ne JOIN ke saath sab kuch **1 query** me laaya. Ise pakarne ke liye `CaptureQueriesContext` (ya django-debug-toolbar) lein.

## Common mistakes

<Compare>
<Bad title="N+1 queries and read-modify-write">

```text
for order in Order.objects.all():
    print(order.customer.email)          # one extra query per order
product = Product.objects.get(id=pid)
product.stock = product.stock - 1        # two concurrent requests both read 5, both write 4
product.save()
```

</Bad>
<Good title="Fetch related rows once, update in the database">

```text
for order in Order.objects.select_related("customer"):
    print(order.customer.email)
Product.objects.filter(id=pid, stock__gt=0).update(stock=F("stock") - 1)
```

</Good>
</Compare>

<Compare>
<Bad title="Floats for money and SQL from strings">

```text
price = models.FloatField()                                      # 0.1 + 0.2 problems
Product.objects.raw(f"SELECT * FROM catalog_product WHERE sku = '{sku}'")   # SQL injection
```

</Bad>
<Good title="Decimals and parameters">

```text
price = models.DecimalField(max_digits=10, decimal_places=2)
Product.objects.raw("SELECT * FROM catalog_product WHERE sku = %s", [sku])
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Editing applied migrations** or deleting them on shared databases: create new migrations instead.
- **`CASCADE` everywhere**: deleting one row can silently remove thousands; choose `PROTECT` or `SET_NULL` where data matters.
- **`len(queryset)` or `if queryset:` on huge tables**: use `.count()` and `.exists()`.
- **Missing indexes** on fields you filter or order by often: add `db_index=True` or `Meta.indexes`.
- **Loading whole objects for one column**: use `values_list`, `only` or `iterator()` for big exports.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Lagu ho chuki migrations edit karna** ya mushtarka databases par unhe delete karna: is ke bajaye nayi migrations banayen.
- **Har jagah `CASCADE`**: ek row delete karna khamoshi se hazaron hata sakta; jahan data ahem ho `PROTECT` ya `SET_NULL` chunein.
- **Bari tables par `len(queryset)` ya `if queryset:`**: `.count()` aur `.exists()` lein.
- **Jin fields par aksar filter ya sort karte un par indexes nahi**: `db_index=True` ya `Meta.indexes` jorein.
- **Ek column ke liye poore objects load karna**: bare exports ke liye `values_list`, `only` ya `iterator()` lein.

</Ur>

```text
import django
from django.conf import settings

bob = Customer.objects.create(email="bob@example.com")
ana = Customer.objects.create(email="ana@example.com")
for c, total, status in [(jane, "120.00", "paid"), (jane, "35.50", "paid"), (jane, "20.00", "refunded"),
                         (bob, "15.00", "paid"), (ana, "300.00", "pending")]:
    Order.objects.create(customer=c, total=Decimal(total), status=status)

report = (Order.objects.filter(status="paid")                     # GROUP BY customer, paid orders only
          .values("customer__email")
          .annotate(orders=Count("id"), revenue=Sum("total"))
          .order_by("-revenue"))
for row in report:
    print(f"{row['customer__email']:<18} paid orders: {row['orders']}  revenue: ${row['revenue']}")
paying = Order.objects.filter(status="paid").values("customer")
print("customers with no paid orders:", list(Customer.objects.exclude(id__in=paying).values_list("email", flat=True)))

# jane@example.com   paid orders: 2  revenue: $155.5
# bob@example.com    paid orders: 1  revenue: $15
# customers with no paid orders: ['ana@example.com']
```

Define an `Account` model with a unique owner and an integer balance in cents, plus a `CheckConstraint` that the balance can't go below zero. <Solution>

<Tr>
<En>

```text
import django
from django.conf import settings

settings.configure(INSTALLED_APPS=["django.contrib.contenttypes"],
                   DATABASES={"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}})
django.setup()

from django.db import IntegrityError, connection, models, transaction
from django.db.models import F

class Account(models.Model):
    owner = models.CharField(max_length=30, unique=True)
    balance = models.IntegerField()                      # cents
    class Meta:
        app_label = "bank"
        constraints = [models.CheckConstraint(condition=models.Q(balance__gte=0), name="no_overdraft")]

with connection.schema_editor() as editor:
    editor.create_model(Account)
Account.objects.create(owner="jane", balance=10_000)
Account.objects.create(owner="bob", balance=2_000)

def transfer(src, dst, cents):
    try:
        with transaction.atomic():
            Account.objects.filter(owner=dst).update(balance=F("balance") + cents)
            Account.objects.filter(owner=src).update(balance=F("balance") - cents)
        return "ok"
    except IntegrityError:
        return "refused (would overdraw)"

def balances():
    return dict(Account.objects.order_by("owner").values_list("owner", "balance"))

print("transfer 3000 jane->bob:", transfer("jane", "bob", 3_000), balances())
print("transfer 9000 bob->jane:", transfer("bob", "jane", 9_000), balances())

# transfer 3000 jane->bob: ok {'bob': 5000, 'jane': 7000}
# transfer 9000 bob->jane: refused (would overdraw) {'bob': 5000, 'jane': 7000}
```

The credit to jane ran first and succeeded, but the failed debit rolled it back, so no money appeared from nowhere.

<DeepDive title="More about the ORM">

**Locking.** `select_for_update()` inside a transaction locks rows (PostgreSQL/MySQL) when a check and an update must be atomic across several statements.

**Custom managers and QuerySet methods.** `Product.objects.active().in_stock()` keeps common filters in one place.

**Data migrations.** `RunPython` operations transform existing data during a migration; keep them reversible and small.

**Zero-downtime changes.** Add nullable columns first, backfill, then make them required; avoid long table locks on big tables.

**Async ORM.** Django supports `await Product.objects.aget(...)` and async iteration in async views.

</DeepDive>

<DeepDive title="Real world: the page with 3,000 queries">

An order history page rendered each order with its customer, items and product names. Locally it showed ten orders and felt fast. In production, a large customer's page made over 3,000 queries and took eight seconds, and under load the database CPU spiked.

The fixes:

1. `select_related("customer")` and `prefetch_related("items__product")` reduced it to four queries.
2. Pagination of 50 orders per page.
3. A test asserting the number of queries (`assertNumQueries`) so the regression can't return unnoticed.

</DeepDive>

<DeepDive title="Security lens">

- **SQL injection**: the ORM parameterizes for you; with `raw()`, `extra()` or cursors, always pass parameters, never format strings.
- **Mass assignment**: don't pass request data straight into `Model.objects.create(**request.POST)`; use forms or serializers with explicit fields.
- **Integrity**: constraints and transactions prevent corrupted states that attackers could exploit (negative balances, duplicate redemptions).
- **Authorization in queries**: always scope queries to the current user (`Order.objects.filter(customer=request.user)`) to avoid IDOR bugs.
- **Sensitive fields**: avoid returning whole objects in APIs; select only fields you mean to expose.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the N+1 query problem and how do you fix it in Django?">
Loading a list with one query and then accessing a related object per item triggers one extra query per item; fix it with select_related for ForeignKey or OneToOne and prefetch_related for reverse or many-to-many relations.
</QA>

<QA q="What's the difference between aggregate and annotate?">
aggregate returns a single dict summarizing the whole QuerySet, while annotate adds a computed value to each row, often combined with values() to produce GROUP BY results.
</QA>

<QA q="Why use F expressions?">
They reference column values inside the database, so updates like stock minus one happen atomically in a single SQL statement, avoiding race conditions and extra queries.
</QA>

<QA q="What does transaction.atomic do?">
It runs the enclosed database operations in a transaction, committing them together if the block succeeds and rolling all of them back if an exception occurs.
</QA>

<QA q="How do migrations work?">
makemigrations compares models with the state described by existing migrations and writes new migration files; migrate applies unapplied migrations in dependency order and records them in the django_migrations table.
</QA>

</DeepDive>
