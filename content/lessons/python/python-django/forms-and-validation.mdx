<BigIdea>
<Tr>
<En>
Browser forms send everything as **strings**, and anyone can send anything: missing fields, wrong types, huge values, extra fields, or a request forged from another site. A Django **Form** class declares what you expect: fields such as `EmailField`, `IntegerField(min_value=1, max_value=10)` and `ChoiceField`. When you create the form with the submitted data and call **`is_valid()`**, Django converts each value to the right Python type, checks the built-in rules, and then runs your own validation: a **`clean_<field>()`** method to check or normalize one field (for example uppercasing a coupon code and checking it exists), and **`clean()`** for rules that involve several fields (express shipping limited to five items). Valid values end up in **`cleaned_data`**; problems end up in **`errors`**, attached to fields or to the whole form. A **ModelForm** builds the fields from a model, includes model checks such as uniqueness, and can `save()` straight to the database. In views, the standard pattern is: on GET show an empty form; on POST bind the data, and if it's valid do the work and **redirect** (Post/Redirect/Get, so refreshing doesn't resubmit), otherwise re-render the page with errors and the user's input. Every POST form must include `csrf_token`, or Django's **CSRF** protection rejects it with 403.
</En>
<Ur>
Browser forms sab kuch **strings** ki shakal me bhejte, aur koi bhi kuch bhi bhej sakta hai: ghayab fields, ghalat types, bohat bari values, zayed fields, ya doosri site se jaali banayi request. Django **Form** class batati ke aap kya tawaqqo rakhte hain: `EmailField`, `IntegerField(min_value=1, max_value=10)` aur `ChoiceField` jaise fields. Jab aap bheje gaye data ke saath form bana kar **`is_valid()`** bulate, Django har value ko sahi Python type me badalta, built-in qawaid check karta, aur phir aap ki apni validation chalata hai: ek field check ya normalize karne ke liye **`clean_<field>()`** method (maslan coupon code bare haroof me kar ke check karna ke mojood hai), aur kai fields wale qawaid ke liye **`clean()`** (express shipping paanch items tak mehdood). Durust values **`cleaned_data`** me aati; masail **`errors`** me, fields se ya poore form se jure. **ModelForm** model se fields banata, uniqueness jaise model checks shamil karta, aur seedha database me `save()` kar sakta hai. Views me mayari pattern ye hai: GET par khaali form dikhayen; POST par data jorein, aur durust ho to kaam kar ke **redirect** karein (Post/Redirect/Get, taa ke refresh dobara submit na kare), warna errors aur user ke input ke saath page dobara dikhayen. Har POST form me `csrf_token` hona chahiye, warna Django ki **CSRF** hifazat use 403 se radd karti hai.
</Ur>

## Picture it

<Tr>
<En>

Think of a **bank teller checking a deposit slip**.

- The slip has labelled boxes (fields), and each box has rules: account number must be digits, amount must be a number within limits (built-in validation).
- The teller tidies what's written ("welcome10" becomes "WELCOME10") and checks it against records (a `clean_coupon` method).
- Some checks need two boxes together: "express deposit only under $5,000" (`clean()`).
- If something's wrong, the teller hands the slip back with each mistake circled, keeping what you wrote (errors re-rendered with input). Only a fully correct slip is processed (`cleaned_data`), and a stamp proves it came from this counter, not a forged copy (CSRF token).

</En>
<Ur>

**Bank teller jo deposit slip check karta** socheyn.

- Slip par label wale khane (fields) hain, aur har khane ke qawaid: account number digits hon, raqam hadd ke andar number ho (built-in validation).
- Teller likha hua saaf karta ("welcome10" ban jata "WELCOME10") aur record se milata hai (`clean_coupon` method).
- Kuch checks ko do khane saath chahiye: "express deposit sirf $5,000 se kam" (`clean()`).
- Kuch ghalat ho to teller har ghalti par ghera laga kar, aap ka likha rakhte hue, slip wapas deta hai (input ke saath errors dobara dikhana). Sirf poori tarah durust slip par amal hota (`cleaned_data`), aur muhr sabit karti ke ye isi counter se aayi, jaali copy nahi (CSRF token).

</Ur>
</Tr>

```bash
from django import forms
from django.core.exceptions import ValidationError
from .models import Coupon

class CheckoutForm(forms.Form):
    email = forms.EmailField()
    quantity = forms.IntegerField(min_value=1, max_value=10)
    shipping = forms.ChoiceField(choices=[("standard", "Standard"), ("express", "Express")])
    coupon = forms.CharField(required=False, max_length=20)
    gift_message = forms.CharField(required=False, widget=forms.Textarea, max_length=200)

    def clean_coupon(self):                          # one field: normalize and check
        code = self.cleaned_data["coupon"].strip().upper()
        if code and not Coupon.objects.filter(code=code).exists():
            raise ValidationError("Unknown coupon code.")
        return code

    def clean(self):                                 # several fields together
        data = super().clean()
        if data.get("shipping") == "express" and data.get("quantity", 0) > 5:
            raise ValidationError("Express shipping is limited to 5 items.")
        return data

class CouponForm(forms.ModelForm):
    class Meta:
        model = Coupon
        fields = ["code", "percent"]

    def clean_percent(self):
        p = self.cleaned_data["percent"]
        if not 1 <= p <= 50:
            raise ValidationError("Discounts must be between 1 and 50 percent.")
        return p
EOF
```

<En>

- The good submission was valid. `cleaned_data["quantity"]` was the **int** 3, not the string "3", and the coupon `" welcome10 "` came back as **WELCOME10** because `clean_coupon` stripped, uppercased and checked it against the database.

```bash
from django.contrib import messages
from django.shortcuts import redirect, render
from .forms import CheckoutForm

def checkout(request):
    if request.method == "POST":
        form = CheckoutForm(request.POST)
        if form.is_valid():
            data = form.cleaned_data                         # only validated, typed values
            messages.success(request, f"Order for {data['quantity']} item(s) placed.")
            return redirect("orders:done")                   # Post/Redirect/Get
    else:
        form = CheckoutForm(initial={"quantity": 1, "shipping": "standard"})
    return render(request, "orders/checkout.html", {"form": form})

def done(request):
    return render(request, "orders/done.html")
EOF
```

<Happened>
<Tr>
<En>

- The GET response contained a hidden **csrfmiddlewaretoken** field from the `csrf_token` tag, and the quantity was pre-filled from `initial`.
- Posting without the token returned **403 Forbidden**: Django's CSRF middleware rejected it. That's what stops another website from making a logged-in user's browser submit your forms.
- Posting invalid data returned **200** with the page re-rendered: the email error appeared next to the field and the user's typed value **"nope" was kept**, so they only fix what's wrong.
- Valid data took the success path: the view used `cleaned_data`, added a message, and **redirected (302)** to `/done/`, which showed "Order for 2 item(s) placed." Because the browser ends on a GET page, refreshing doesn't place the order twice.
- The view never touched `request.POST` directly after validation. Using only `cleaned_data` means extra fields an attacker adds to the POST are simply ignored.

</En>
<Ur>

- GET response me `csrf_token` tag se chhupa **csrfmiddlewaretoken** field tha, aur quantity `initial` se pehle se bhari thi.
- Token ke baghair post karne par **403 Forbidden** aaya: Django ke CSRF middleware ne use radd kiya. Yahi doosri website ko login user ke browser se aap ke forms submit karwane se rokta hai.
- Ghalat data post karne par page dobara dikha kar **200** aaya: email ka error field ke saath nazar aaya aur user ki likhi value **"nope" qaim rahi**, isliye woh sirf ghalat cheez theek karta hai.
- Durust data kamyabi ke raaste gaya: view ne `cleaned_data` istemal kiya, paigham jora, aur `/done/` par **redirect (302)** kiya, jis ne "Order for 2 item(s) placed." dikhaya. Kyunke browser GET page par khatam hota, refresh order do dafa nahi karta.

## Common mistakes

<Compare>
<Bad title="Trusting request.POST directly">

```text
def checkout(request):
    qty = int(request.POST["quantity"])            # ValueError / KeyError -> 500
    Order.objects.create(**request.POST.dict())    # mass assignment: user sets price, status...
    return render(request, "done.html")            # refresh = second order
```

</Bad>
<Good title="Validate with a form, use cleaned_data, redirect">

```text
form = CheckoutForm(request.POST)
if form.is_valid():
    Order.objects.create(customer=request.user, quantity=form.cleaned_data["quantity"])
    return redirect("orders:done")
```

</Good>
</Compare>

<Compare>
<Bad title="ModelForm exposing every field, CSRF disabled">

```text
class UserForm(forms.ModelForm):
    class Meta:
        model = User
        fields = "__all__"              # is_staff, is_superuser editable by the user

@csrf_exempt                            # "the form kept failing"
def update_profile(request): ...
```

</Bad>
<Good title="Explicit fields and CSRF on">

```text
class ProfileForm(forms.ModelForm):
    class Meta:
        model = User
        fields = ["first_name", "last_name"]
# template: <form method="post">{% csrf_token %} ...
```

</Good>

<Tr>
<En>

More mistakes to avoid:

- **Validation only in JavaScript or HTML attributes**: always validate on the server.
- **Catching ValidationError and continuing**: invalid data must not be processed.
- **Echoing passwords back** into re-rendered forms: `PasswordInput` doesn't, keep it that way.
- **Uploading files without limits**: check size and type, and store them outside the web root.
- **Checking uniqueness only in the form**: concurrent requests can race; keep a database unique constraint.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Validation sirf JavaScript ya HTML attributes me**: hamesha server par validate karein.
- **ValidationError pakar kar aage chalna**: ghalat data process nahi hona chahiye.
- **Dobara dikhaye forms me passwords wapas bharna**: `PasswordInput` nahi bharta, aisa hi rakhein.
- **Hadd ke baghair files upload karna**: size aur type check karein, aur web root ke bahar rakhein.
- **Uniqueness sirf form me check karna**: ek saath requests takra sakti; database ki unique constraint rakhein.

```text
import django
from django.conf import settings
settings.configure(USE_I18N=False)
django.setup()

from datetime import date
from django import forms
from django.core.exceptions import ValidationError

class BookingForm(forms.Form):
    guest = forms.CharField(max_length=50)
    check_in = forms.DateField()
    check_out = forms.DateField()
    guests = forms.IntegerField(min_value=1, max_value=4)

    def __init__(self, *args, today, **kwargs):          # inject "today" so tests are repeatable
        super().__init__(*args, **kwargs)
        self.today = today

    def clean_guest(self):
        return " ".join(self.cleaned_data["guest"].split()).title()

    def clean(self):
        data = super().clean()
        ci, co = data.get("check_in"), data.get("check_out")
        if ci and ci < self.today:
            self.add_error("check_in", "Check-in can't be in the past.")
        if ci and co:
            if co <= ci:
                raise ValidationError("Check-out must be after check-in.")
            if (co - ci).days > 14:
                raise ValidationError("Bookings are limited to 14 nights.")
        return data

today = date(2026, 11, 24)
cases = {
    "ok":      {"guest": "  jane   cooper ", "check_in": "2026-12-01", "check_out": "2026-12-05", "guests": "2"},
    "past":    {"guest": "Bob", "check_in": "2026-11-01", "check_out": "2026-11-03", "guests": "1"},
    "reverse": {"guest": "Ana", "check_in": "2026-12-10", "check_out": "2026-12-08", "guests": "5"},
    "long":    {"guest": "Lee", "check_in": "2026-12-01", "check_out": "2027-01-01", "guests": "2"},
}
for name, data in cases.items():
    f = BookingForm(data, today=today)
    if f.is_valid():
        d = f.cleaned_data
        print(f"{name:<8} OK  {d['guest']}, {(d['check_out'] - d['check_in']).days} nights")
    else:
        print(f"{name:<8} ERR " + "; ".join(f"{k}: {v[0]}" for k, v in f.errors.items()))

# ok       OK  Jane Cooper, 4 nights
# past     ERR check_in: Check-in can't be in the past.
# reverse  ERR guests: Ensure this value is less than or equal to 4.; __all__: Check-out must be after check-in.
# long     ERR __all__: Bookings are limited to 14 nights.
```

```text
import django
from django.conf import settings
settings.configure(USE_I18N=False)
django.setup()

from django import forms
```

```text
class SignupForm(forms.Form):
    email = forms.EmailField()
    password = forms.CharField(widget=forms.PasswordInput, min_length=12)
    is_admin = forms.BooleanField(required=False)        # a field an attacker might try to set

ALLOWED = {"email", "password"}

def register(post_data):
    form = SignupForm(post_data)
    if not form.is_valid():
        return {k: v[0] for k, v in form.errors.items()}
    user = {k: v for k, v in form.cleaned_data.items() if k in ALLOWED}   # never trust extra fields
    user["is_admin"] = False
    user["password"] = "***"          # in a real app: hash it (Django's set_password), never store or log it
    return user

print(register({"email": "jane@example.com", "password": "correct horse battery", "is_admin": "on"}))
print(register({"email": "jane@example.com", "password": "short"}))
print("password field HTML:", str(SignupForm()["password"]))
print("re-rendered with data:", str(SignupForm({"password": "secret-value-123"})["password"]))

# {'email': 'jane@example.com', 'password': '***', 'is_admin': False}
# {'password': 'Ensure this value has at least 12 characters (it has 5).'}
# password field HTML: <input type="password" name="password" minlength="12" required id="id_password">
# re-rendered with data: <input type="password" name="password" minlength="12" required id="id_password">
```

<DeepDive title="More about forms">

**Validators.** Reusable functions (`validators=[validate_sku]`) or built-ins like `RegexValidator` and `MaxValueValidator` work on both model and form fields.

**Formsets.** `formset_factory` and `inlineformset_factory` handle many similar forms, such as order lines, in one page.

**Generic editing views.** `CreateView`, `UpdateView` and `DeleteView` wrap the GET/POST pattern for ModelForms.

**Rendering.** Django 5 renders forms with templates (`as_div`), and libraries like django-crispy-forms control layout.

**File uploads.** `request.FILES`, `FileField`, size limits in settings, and storage backends such as S3.

</DeepDive>

<DeepDive title="Real world: the price field in the request">

A shop's checkout view created orders with `Order.objects.create(**request.POST.dict())`, because the form template happened to include product, quantity and price as hidden fields. A curious customer edited the hidden price in their browser's developer tools and bought a laptop for $1.

The fixes:

1. A form that accepts only product and quantity; the price comes from the database.
2. Totals recalculated on the server at payment time, with a database constraint against non-positive amounts.
3. A test that posts extra fields and asserts they're ignored.

</DeepDive>

<DeepDive title="Security lens">

- **Never trust input**: validate type, range, length and format on the server for every field.
- **Allow-list fields**: forms and serializers should accept only what the user may change.
- **CSRF**: keep the middleware and token; for APIs with tokens instead of cookies, use DRF's authentication classes.
- **Output encoding**: show validated input back through templates so it stays escaped.
- **Rate limiting**: sign-up, login and contact forms attract bots; add rate limits or CAPTCHAs.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between clean_field and clean in a Django form?">
clean_field validates or normalizes a single field after its built-in validation and returns the cleaned value; clean runs after all fields and handles rules involving several fields, raising form-wide errors or using add_error.
</QA>

<QA q="What is a ModelForm?">
A form whose fields are generated from a model's fields, including their validation and uniqueness checks, with a save method that creates or updates the model instance.
</QA>

<QA q="What is the Post/Redirect/Get pattern?">
After a successful POST, the server redirects to a GET page, so refreshing or using the back button doesn't resubmit the form.
</QA>

<QA q="How does Django's CSRF protection work?">
The middleware sets a secret cookie and requires a matching token in each unsafe request, typically from the csrf_token tag in forms; requests from other sites can't read the token, so they're rejected with 403.
</QA>

<QA q="What is mass assignment and how do you prevent it?">
Saving request data directly into a model so users can set fields they shouldn't; prevent it by using forms or serializers with explicit field lists and setting sensitive fields in code.
</QA>

</DeepDive>
