<BigIdea>
<Tr>
<En>
**Django REST Framework (DRF)** is the standard way to build JSON APIs with Django. It adds three main building blocks. A **serializer** converts model instances to JSON and back, and **validates** incoming data: field types, lengths, choices, your own `validate_<field>` methods and a `validate()` for rules that involve several fields. Fields can be **read-only** (like an owner the server sets) or **write-only** (like a password the API should never send back). A **ViewSet** groups the standard actions (list, create, retrieve, update, partial update, destroy) for a model, and a **router** turns it into URLs like `/api/tasks/` and `/api/tasks/<id>/`, with **pagination** built in. The third block is **security**, which you configure explicitly. **Authentication classes** identify the caller from a session, a token or a JWT; **permission classes** decide whether the request is allowed, both globally (`IsAuthenticated` by default) and per object (`has_object_permission`); and **throttling** limits how many requests a user can make, answering **429 Too Many Requests** when exceeded. The most important habit is to **scope the queryset**: `get_queryset()` should return only the objects the current user may see, so another user's IDs simply give **404**, and fields like `owner` must be set by the server (`perform_create`), never trusted from the request body.
</En>
<Ur>
**Django REST Framework (DRF)** Django ke saath JSON APIs banane ka mayari tareeqa hai. Ye teen bunyadi building blocks jorta hai. **Serializer** model instances ko JSON me aur wapas badalta, aur aane wale data ko **validate** karta hai: field types, lambai, choices, aap ke apne `validate_<field>` methods aur kai fields wale qawaid ke liye `validate()`. Fields **read-only** (jaise server ka set kiya owner) ya **write-only** (jaise password jo API kabhi wapas na bheje) ho sakte hain. **ViewSet** kisi model ke mayari kaam (list, create, retrieve, update, partial update, destroy) ek jagah jorta, aur **router** use `/api/tasks/` aur `/api/tasks/<id>/` jaise URLs banata, andar se **pagination** ke saath. Teesra block **security** hai, jo aap wazeh taur par configure karte hain. **Authentication classes** caller ko session, token ya JWT se pehchanti; **permission classes** tay karti ke request ki ijazat hai ya nahi, poori API par (default `IsAuthenticated`) aur har object par (`has_object_permission`); aur **throttling** mehdood karti ke user kitni requests kar sakta, had paar hone par **429 Too Many Requests** deti. Sab se ahem aadat **queryset ko mehdood karna** hai: `get_queryset()` sirf woh objects lautaye jo mojooda user dekh sakta, taa ke doosre user ki IDs bas **404** dein, aur `owner` jaise fields server set kare (`perform_create`), request body se kabhi bharosa na kiya jaye.
</Ur>

<Why>
<Tr>
<En>

- One backend can serve a website, mobile apps and partner integrations through the same API.
- Serializers give consistent validation and error messages for every endpoint.
- API security failures (broken object-level authorization, mass assignment, no rate limiting) top the OWASP API Top 10; DRF has tools for each.

</En>

- Ek backend ek hi API ke zariye website, mobile apps aur partner integrations ki khidmat kar sakta hai.

## Picture it

<Tr>
<En>

Think of a **bank teller window**.

- The serializer is the **form** you fill in: required boxes, allowed values, and a clerk who rejects it with notes next to each wrong box (400 with field errors). Some boxes are "office use only" (read-only), and your PIN goes in but is never printed on the receipt (write-only).
- Authentication is showing your card; permissions are the rules about what this card may do.
- The scoped queryset means the teller's screen only ever shows **your** accounts. Typing someone else's account number gives "no such account" (404), not their balance.
- Throttling is the "maximum 5 transactions per minute" sign that stops someone emptying accounts in a hurry.

</En>
<Ur>

**Bank ki teller khirki** socheyn.

- Serializer woh **form** hai jo aap bharte: lazmi khaane, ijazat wali values, aur clerk jo har ghalat khaane ke saath notes laga kar wapas karta (field errors ke saath 400). Kuch khaane "sirf daftari istemal" hain (read-only), aur aap ka PIN andar jata magar raseed par kabhi nahi chhapta (write-only).
- Authentication card dikhana hai; permissions qawaid hain ke ye card kya kar sakta.
- Mehdood queryset ka matlab teller ki screen sirf **aap ke** accounts dikhati. Kisi aur ka account number likhna "aisa account nahi" (404) deta, us ka balance nahi.
- Throttling "har minute zyada se zyada 5 transactions" ka board hai jo kisi ko jaldi me accounts khaali karne se rokta.

</Ur>

<Step title="Serializers, validation, a ModelViewSet, a router and pagination">

<Tr>
<En>
We install pinned Django and DRF, create a `tasks` app with a `Task` model, a `TaskSerializer` that makes `owner` read-only and checks the priority range, a `TaskViewSet` that sets the owner from the logged-in user, and a router. from rest_framework import serializers
from .models import Task

class TaskSerializer(serializers.ModelSerializer):
    owner = serializers.ReadOnlyField(source="owner.username")      # set by the server, never by the client

    class Meta:
        model = Task
        fields = ["id", "owner", "title", "priority", "done"]

<Happened>
<Tr>
<En>

- Each POST returned **201 Created** with the saved object, including the `id` and the `owner` the server set from the logged-in user.
- The invalid task got **400** with an error **per field**: a blank title and our custom priority rule. The `"owner": "mallory"` in the body was simply **ignored**, because `owner` is a `ReadOnlyField`. That's how you block **mass assignment**: decide explicitly which fields clients may write.
- Pagination wrapped the list in `count`, `results` and a `next` URL, so clients can walk large collections page by page without the server returning everything at once.
- `PATCH` changed only `done` (partial update), `DELETE` returned **204 No Content**, and a GET afterwards gave **404**. The router built all these routes, and the API root lists them.
- At this stage, though, the API has no real authentication and every user can see every task. Step 2 fixes that.

</En>
<Ur>

- Har POST ne mehfooz object ke saath **201 Created** lautaya, `id` aur us `owner` samait jo server ne login user se set kiya.
- Ghalat task ko **har field ke** error ke saath **400** mila: khaali title aur hamara custom priority qaida. Body me `"owner": "mallory"` bas **nazar andaz** hua, kyunke `owner` `ReadOnlyField` hai. **Mass assignment** isi tarah rokte hain: wazeh tay karein ke clients kaun se fields likh sakte hain.
- Pagination ne list ko `count`, `results` aur `next` URL me lapeta, taa ke clients bari collections page ba page chal sakein aur server sab kuch ek saath na lautaye.
- `PATCH` ne sirf `done` badla (partial update), `DELETE` ne **204 No Content** lautaya, aur us ke baad GET ne **404** diya. Router ne ye tamam routes banaye, aur API root unki list deta hai.
- Magar is marhale par API me asal authentication nahi aur har user har task dekh sakta hai. Qadam 2 ise theek karta hai.

<Step title="Token authentication, ownership, scoped querysets and throttling">

<Tr>
<En>
We add an `IsOwner` object permission, scope `get_queryset()` to the current user, switch the API to `TokenAuthentication` with `IsAuthenticated` by default, add a user throttle of 5 requests per minute, and expose `obtain_auth_token` at `/api/token/`. `try_auth.py` calls the API without a token, tries a bad login, gets tokens for jane and bob, checks what each can see and do with jane's task, has bob try to create a task owned by jane, and finally sends seven quick requests to hit the throttle.
</En>
<Ur>
Hum `IsOwner` object permission jorte, `get_queryset()` ko mojooda user tak mehdood karte, API ko default `IsAuthenticated` ke saath `TokenAuthentication` par le jate, har minute 5 requests ki user throttle jorte, aur `/api/token/` par `obtain_auth_token` kholte hain. `try_auth.py` token ke baghair API bulati, ghalat login aazmati, jane aur bob ke tokens leti, check karti ke har ek jane ke task ke saath kya dekh aur kar sakta, bob se jane ke naam ka task banwane ki koshish karti, aur aakhir me throttle se takraane ke liye saat jaldi requests bhejti hai.
</Ur>

from rest_framework import permissions

class IsOwner(permissions.BasePermission):
    message = "You can only change your own tasks."
    def has_object_permission(self, request, view, obj):
        return obj.owner == request.user

<Happened>
<Tr>
<En>

- Without a token the API answered **401** with "Authentication credentials were not provided". `TokenAuthentication` sends a `WWW-Authenticate` header, which is why this is 401 rather than 403.
- `/api/token/` exchanged a username and password for a **40-character token**; wrong credentials got **400**. Clients then send `Authorization: Token <token>` on every request. Treat tokens like passwords: HTTPS only, never in URLs or logs, and revoke them when needed.
- jane saw her two remaining tasks; **bob saw 0**, and reading or deleting jane's task 1 gave **404**, because `get_queryset()` only contains bob's rows. That defeats BOLA/IDOR at the root, and `IsOwner` is a second layer for any view that fetches objects differently.
- bob's attempt to create a task with `"owner": "jane"` produced a task owned by **bob**: the owner comes from `perform_create`, not the request.
- With a limit of 5 per minute, the sixth and seventh requests got **429** ("Request was throttled"), and DRF adds a `Retry-After` header. Throttling uses Django's cache; in production, configure a shared cache such as Redis so the limit applies across all servers.

</En>
<Ur>

- Token ke baghair API ne "Authentication credentials were not provided" ke saath **401** diya. `TokenAuthentication` `WWW-Authenticate` header bhejta, isi liye ye 403 ke bajaye 401 hai.

## Common mistakes

<Compare>
<Bad title="Global queryset and client-controlled fields">

```text
class InvoiceViewSet(viewsets.ModelViewSet):
    queryset = Invoice.objects.all()                  # every user can read every invoice by ID
    serializer_class = InvoiceSerializer              # fields = "__all__" -> client can set owner, paid, total
```

</Bad>
<Good title="Scoped queryset, explicit fields, server-set owner">

```text
class InvoiceViewSet(viewsets.ModelViewSet):
    serializer_class = InvoiceSerializer              # fields listed; owner/paid/total read-only
    permission_classes = [IsAuthenticated]
    def get_queryset(self):
        return Invoice.objects.filter(customer=self.request.user)
    def perform_create(self, serializer):
        serializer.save(customer=self.request.user)
```

</Good>
</Compare>

<Compare>
<Bad title="Open defaults">

```text
REST_FRAMEWORK = {
    "DEFAULT_PERMISSION_CLASSES": ["rest_framework.permissions.AllowAny"],   # every new endpoint is public
}
```

</Bad>
<Good title="Secure by default, opt out deliberately">

```text
REST_FRAMEWORK = {
    "DEFAULT_PERMISSION_CLASSES": ["rest_framework.permissions.IsAuthenticated"],
    "DEFAULT_THROTTLE_CLASSES": ["rest_framework.throttling.UserRateThrottle",
                                 "rest_framework.throttling.AnonRateThrottle"],
    "DEFAULT_THROTTLE_RATES": {"user": "1000/hour", "anon": "50/hour"},
}
# public endpoints: permission_classes = [AllowAny] on that view only
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`fields = "__all__"`** in serializers: new model fields become writable and visible automatically.
- **Returning secrets in responses**: password hashes, tokens, internal notes; use explicit fields and `write_only`.
- **Unbounded list endpoints**: always paginate.
- **Leaving the browsable API and debug pages open in production** without authentication.
- **Checking permissions in `list` but not in custom actions** (`@action`): every action needs the same care.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Serializers me `fields = "__all__"`**: naye model fields khud likhne aur dekhne ke qabil ban jate hain.
- **Responses me secrets lautana**: password hashes, tokens, andaruni notes; wazeh fields aur `write_only` lein.
- **Be-had list endpoints**: hamesha paginate karein.
- **Production me browsable API aur debug pages authentication ke baghair khule chhorna.**
- **`list` me permissions check karna magar custom actions (`@action`) me nahi**: har action ko yahi dhyan chahiye.

</Ur>

<Tr>
<En>

```text
import django
from django.conf import settings
settings.configure(INSTALLED_APPS=["django.contrib.contenttypes", "django.contrib.auth", "rest_framework"],
                   DATABASES={"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}})
django.setup()
from rest_framework import serializers

class SignupSerializer(serializers.Serializer):
    username = serializers.RegexField(r"^[a-z0-9_]{3,20}$",
                                      error_messages={"invalid": "3-20 lowercase letters, digits or _"})
    email = serializers.EmailField()
    password = serializers.CharField(write_only=True, min_length=12)
    password2 = serializers.CharField(write_only=True)
    age = serializers.IntegerField(min_value=13, required=False)

    def validate(self, data):                          # cross-field checks
        if data["password"] != data["password2"]:
            raise serializers.ValidationError({"password2": "passwords do not match"})
        return data

for payload in [
    {"username": "jane_c", "email": "jane@example.com", "password": "Tram-Lantern-42", "password2": "Tram-Lantern-42"},
    {"username": "Jane C!", "email": "not-an-email", "password": "short", "password2": "short", "age": 9},
    {"username": "bob", "email": "bob@example.com", "password": "Velvet-Harbor-7", "password2": "Velvet-Harbor-8"},
]:
    s = SignupSerializer(data=payload)
    if s.is_valid():
        print("valid ->", s.validated_data["username"], "| password in output:", "password" in s.data)
    else:
        print("errors ->", {k: str(v[0]) for k, v in s.errors.items()})

# valid -> jane_c | password in output: False
# errors -> {'username': '3-20 lowercase letters, digits or _', 'email': 'Enter a valid email address.', 'password': 'Ensure this field has at least 12 characters.', 'age': 'Ensure this value is greater than or equal to 13.'}
# errors -> {'password2': 'passwords do not match'}
```

Note that the passwords never appear in `s.data` because they're `write_only`.

<En>
Write a permission class `ReadOnlyOrStaff` that denies anonymous users, lets authenticated users use safe methods (GET, HEAD, OPTIONS), and allows writes only for staff. Use it on an `Announcements` `APIView` with `get` and `post`, and test it with `APIRequestFactory` and `force_authenticate` for an anonymous user, a member and a staff user.

<Solution>

<Tr>
<En>

```text
import django
from django.conf import settings
settings.configure(INSTALLED_APPS=["django.contrib.contenttypes", "django.contrib.auth", "rest_framework"],
                   DATABASES={"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}},
                   ROOT_URLCONF=__name__, ALLOWED_HOSTS=["testserver"])
django.setup()
from django.contrib.auth.models import AnonymousUser, User
from django.core.management import call_command
from rest_framework import permissions
from rest_framework.response import Response
from rest_framework.test import APIRequestFactory, force_authenticate
from rest_framework.views import APIView

urlpatterns = []
call_command("migrate", verbosity=0)

class ReadOnlyOrStaff(permissions.BasePermission):
    """Anyone authenticated may read; only staff may write."""
    def has_permission(self, request, view):
        if not request.user or not request.user.is_authenticated:
            return False
        return request.method in permissions.SAFE_METHODS or request.user.is_staff

class Announcements(APIView):
    permission_classes = [ReadOnlyOrStaff]
    def get(self, request):
        return Response(["Maintenance on Saturday"])
    def post(self, request):
        return Response({"created": request.data.get("text")}, status=201)

view = Announcements.as_view()
rf = APIRequestFactory()
staff = User.objects.create_user("ana", is_staff=True); member = User.objects.create_user("bob")
for who in [None, member, staff]:
    for method in ("get", "post"):
        req = getattr(rf, method)("/announcements/", {"text": "New VPN"}, format="json")
        if who:
            force_authenticate(req, user=who)
        resp = view(req)
        print(f"{(who.username if who else 'anonymous'):<9} {method.upper():<4} {resp.status_code}")

# anonymous GET  403
# anonymous POST 403
# bob       GET  200
# bob       POST 403
# ana       GET  200
# ana       POST 201
```

Anonymous requests get 403 here, not 401, because the default authentication classes in this minimal setup don't send a `WWW-Authenticate` header.

<DeepDive title="More about DRF">

**JWT.** `djangorestframework-simplejwt` issues short-lived access tokens and refresh tokens; keep access tokens short and rotate refresh tokens.

**Filtering.** `django-filter` adds `?done=true&priority=1` filtering; combine with `SearchFilter` and `OrderingFilter`, always on the scoped queryset.

**Schema and docs.** `drf-spectacular` generates an OpenAPI schema and Swagger UI from your viewsets and serializers.

**Nested data.** Nested serializers display related objects; writing nested data needs explicit `create`/`update` methods.

**Performance.** Use `select_related` and `prefetch_related` in `get_queryset()` to avoid N+1 queries in list endpoints.

</DeepDive>

<DeepDive title="Real world: the API that trusted the client">

A mobile app's order API used a serializer with `fields = "__all__"`. A curious user intercepted the app's traffic and noticed the `Order` JSON contained `status` and `discount_percent`. Sending a PATCH with `"discount_percent": 100` and `"status": "paid"` worked. The web frontend never exposed those fields, so nobody had considered them.

The fixes:

1. Explicit serializer fields, with `status`, `discount_percent` and totals read-only and computed on the server.
2. Separate serializers for customers and staff.
3. Tests that send unexpected fields and assert they're ignored, plus OWASP API Top 10 reviews for new endpoints.

</DeepDive>

<DeepDive title="Security lens">

- **BOLA** (API1): scope querysets and check object permissions on every action.
- **Broken authentication** (API2): HTTPS only, short-lived tokens, rate-limited login, no tokens in URLs.
- **Mass assignment / object property authorization** (API3): explicit fields, read-only server-controlled values.
- **Unrestricted resource consumption** (API4): pagination, throttling and size limits.
- **Function-level authorization** (API5): admin-only actions must check staff or specific permissions, not just "logged in".

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does a DRF serializer do?">
It converts between model instances or Python data and primitive types for JSON, and validates incoming data with field definitions and custom validate methods, exposing errors per field.
</QA>

<QA q="How do you restrict users to their own objects in DRF?">
Override get_queryset to filter by request.user, set ownership in perform_create, and add an object-level permission class as a second check.
</QA>

<QA q="What is the difference between authentication and permission classes in DRF?">
Authentication classes determine who the caller is from credentials such as sessions or tokens; permission classes decide whether that caller may perform the request, globally and per object.
</QA>

<QA q="How do you protect an API against mass assignment?">
List serializer fields explicitly, mark server-controlled fields read-only, use separate serializers for different roles, and never use fields set to all on models with sensitive columns.
</QA>

<QA q="How does throttling work in DRF?">
Throttle classes count requests per user or IP in the cache over a time window and return 429 with Retry-After when the configured rate is exceeded; production needs a shared cache.
</QA>

</DeepDive>
