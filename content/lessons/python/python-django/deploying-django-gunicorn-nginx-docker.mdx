<BigIdea>
<Tr>
<En>
`python manage.py runserver` is single-process, unoptimized and not security-reviewed: never use it in production. A production Django deployment usually has three layers. **Gunicorn** is a WSGI **application server**: a master process starts several **worker processes** that each run your Django code, restarts workers that crash or hang (`--timeout`), and on **SIGTERM** stops gracefully by finishing in-flight requests. **Nginx** sits in front as a **reverse proxy**: it terminates **TLS** (HTTPS), redirects HTTP to HTTPS, adds headers like **HSTS**, serves **static files** directly from disk (far faster than Python), limits request sizes and timeouts, and forwards everything else to Gunicorn with headers that describe the original request (`Host`, `X-Forwarded-For`, `X-Forwarded-Proto`). Django must be configured to match: production settings from the **environment**, `STATIC_ROOT` filled by **`collectstatic`**, `ALLOWED_HOSTS`, and `SECURE_PROXY_SSL_HEADER` so it knows the original request was HTTPS. **Docker** packages Python, your dependencies and code into an **image** that runs the same on a laptop, a VM or Kubernetes; good images pin dependencies, run as a **non-root user** and keep secrets out of the image. **Docker Compose** wires the containers together, injects configuration from an `.env` file and uses a **health check** so Nginx only starts once Django is ready.
</En>
<Ur>
`python manage.py runserver` ek process wala, be-optimize aur security review ke baghair hai: production me kabhi istemal na karein. Production Django deployment me aam taur par teen tahen hoti hain. **Gunicorn** WSGI **application server** hai: master process kai **worker processes** shuru karta jo har ek aap ka Django code chalata, crash ya atakne wale workers dobara shuru karta (`--timeout`), aur **SIGTERM** par jaari requests khatam kar ke aaram se rukta hai. **Nginx** saamne **reverse proxy** ke taur par baithta: ye **TLS** (HTTPS) khatam karta, HTTP ko HTTPS par redirect karta, **HSTS** jaise headers jorta, **static files** seedha disk se serve karta (Python se kahin tez), request ke size aur timeouts mehdood karta, aur baqi sab Gunicorn ko asal request batane wale headers (`Host`, `X-Forwarded-For`, `X-Forwarded-Proto`) ke saath aage bhejta hai. Django ko bhi mel khane wali configuration chahiye: **environment** se production settings, **`collectstatic`** se bhara `STATIC_ROOT`, `ALLOWED_HOSTS`, aur `SECURE_PROXY_SSL_HEADER` taa ke use pata ho ke asal request HTTPS thi. **Docker** Python, aap ki dependencies aur code ko aisi **image** me band karta jo laptop, VM ya Kubernetes par ek jaisi chalti; achhi images dependencies pin karti, **non-root user** ke taur par chalti aur secrets image se bahar rakhti hain. **Docker Compose** containers ko aapas me jorta, `.env` file se configuration deta aur **health check** istemal karta taa ke Nginx sirf tab shuru ho jab Django tayyar ho.
</Ur>

## Picture it

<Tr>
<En>

Think of a **busy restaurant**.

- Nginx is the **host at the door**: checks bookings (TLS, host), hands out menus and water directly (static files), turns away people with oversized luggage (body limits), and seats everyone else.
- Gunicorn is the **head chef** who never cooks but manages several **cooks** (workers). If a cook freezes on one dish too long, the chef replaces them; at closing time (SIGTERM) the chef lets cooks finish current orders before turning off the stoves.
- Django is the **recipe book** the cooks follow.
- Docker is the **food truck**: the same kitchen, equipment and recipes, parked anywhere. Compose is the plan of how the truck, the host's stand and the fridge connect.

</En>
<Ur>

**Masroof restaurant** socheyn.

- Nginx darwaze par **host** hai: bookings check karta (TLS, host), menu aur paani seedha deta (static files), bohat bare saman wale logon ko lautata (body limits), aur baqi sab ko bithata hai.
- Gunicorn **head chef** hai jo khud nahi pakata magar kai **cooks** (workers) sambhalta hai. Agar koi cook ek dish par zyada der atak jaye to chef use badal deta; band hone ke waqt (SIGTERM) chef cooks ko mojooda orders poore karne deta phir chulhe band karta.
- Django woh **recipe book** hai jo cooks follow karte hain.

## Learn it step by step

<Walkthrough>

<Step title="Gunicorn with production settings: static files, proxy headers, hosts and graceful shutdown">

<Tr>
<En>
We install pinned Django and Gunicorn, create `settings_prod.py` that reads secrets from the environment, sets `STATIC_ROOT`, trusts `X-Forwarded-Proto`, redirects to HTTPS except for `/health/`, and logs to the console without disabling Gunicorn's loggers. We add a `/health/` endpoint, run `collectstatic` and `check --deploy`, start Gunicorn with two workers, and use `curl` to test the health check, a plain HTTP request, a request that arrived through an HTTPS proxy, and an unknown host. Finally we stop Gunicorn with SIGTERM and look at its access log.
</En>
<Ur>
Hum pinned Django aur Gunicorn install karte, aisi `settings_prod.py` banate jo secrets environment se parhti, `STATIC_ROOT` set karti, `X-Forwarded-Proto` par bharosa karti, `/health/` ke ilawa HTTPS par redirect karti, aur Gunicorn ke loggers band kiye baghair console par log karti hai. Hum `/health/` endpoint jorte, `collectstatic` aur `check --deploy` chalate, do workers ke saath Gunicorn shuru karte, aur `curl` se health check, saadi HTTP request, HTTPS proxy se aayi request, aur na-maloom host test karte hain. Aakhir me SIGTERM se Gunicorn band kar ke us ka access log dekhte hain.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z NO_PROXY=127.0.0.1,localhost
uv venv -q --python 3.13 .venv && uv pip install -q --python .venv "django==5.2.1" "gunicorn==23.0.0"
. .venv/bin/activate
mkdir app && django-admin startproject config app && cd app
cat > config/settings_prod.py <<'EOF'
import os
from .settings import *

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
DEBUG = False
ALLOWED_HOSTS = os.environ["DJANGO_ALLOWED_HOSTS"].split(",")
STATIC_ROOT = BASE_DIR / "staticfiles"                  # collectstatic copies everything here
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
SECURE_SSL_REDIRECT = True
SECURE_REDIRECT_EXEMPT = [r"^health/$"]                 # load balancers check health over plain HTTP
SESSION_COOKIE_SECURE = CSRF_COOKIE_SECURE = True
LOGGING = {"version": 1, "disable_existing_loggers": False, "handlers": {"console": {"class": "logging.StreamHandler"}},
           "root": {"handlers": ["console"], "level": "WARNING"}}    # logs to stdout/stderr
EOF
cat >> config/urls.py <<'EOF'
from django.http import JsonResponse
urlpatterns += [path("health/", lambda r: JsonResponse({"status": "ok"}))]
EOF
export DJANGO_SETTINGS_MODULE=config.settings_prod DJANGO_ALLOWED_HOSTS=shop.example.com,localhost,127.0.0.1
export DJANGO_SECRET_KEY="$(python -c 'from django.core.management.utils import get_random_secret_key as g; print(g())')"
python manage.py collectstatic --noinput -v 0 && echo "admin CSS collected: $(test -f staticfiles/admin/css/base.css && echo yes)"
python manage.py check --deploy 2>&1 | grep -oE "security\.W[0-9]+" | tr '\n' ' '; echo "<- remaining warnings (HSTS is set at Nginx in step 2)"

gunicorn config.wsgi:application --bind 127.0.0.1:8011 --workers 2 --timeout 30 \
  --access-logfile access.log --error-logfile error.log > app.log 2>&1 &
GUNICORN=$!
sleep 2
echo "gunicorn workers under the master process: $(pgrep -P $GUNICORN | wc -l)"
curl --noproxy "*" -s -H "Host: shop.example.com" http://127.0.0.1:8011/health/; echo
curl --noproxy "*" -s -o /dev/null -w "plain http /admin/ -> %{http_code} %{redirect_url}\n" -H "Host: shop.example.com" http://127.0.0.1:8011/admin/
echo "via proxy (X-Forwarded-Proto: https) /admin/ -> $(curl --noproxy "*" -s -D - -o /dev/null -H "Host: shop.example.com" \
  -H "X-Forwarded-Proto: https" http://127.0.0.1:8011/admin/ | grep -iE '^(HTTP|location)' | tr -d '\r' | tr '\n' ' ')"
curl --noproxy "*" -s -o /dev/null -w "unknown host -> %{http_code}\n" -H "Host: evil.example" http://127.0.0.1:8011/health/
echo "rejected host was logged: $(grep -q 'Invalid HTTP_HOST' app.log && echo yes)"
kill -TERM $GUNICORN; wait $GUNICORN 2>/dev/null
echo "master still running after SIGTERM: $(kill -0 $GUNICORN 2>/dev/null && echo yes || echo no) | access log lines: $(wc -l < access.log)"
tail -1 access.log | cut -d'"' -f2
```

<Happened>
<Tr>
<En>

- `collectstatic` copied every app's static files (including the admin's CSS) into `staticfiles/`, the folder Nginx will serve. Django doesn't serve static files when `DEBUG = False`.
- `check --deploy` left only **W004** (HSTS), because Nginx adds that header in step 2. Choose one place for each header to avoid duplicates.
- Gunicorn's master started **2 workers**. A common starting point is `2 × CPU cores + 1`, adjusted for memory; `--timeout` kills and replaces a worker stuck on one request.
- `/health/` answered over plain HTTP because it's in `SECURE_REDIRECT_EXEMPT`; load balancers and Docker health checks usually call it without TLS.
- A plain HTTP request for `/admin/` got **301 to https**. The same request carrying `X-Forwarded-Proto: https` (as Nginx will send) was treated as secure and reached the admin's login redirect. Without `SECURE_PROXY_SSL_HEADER` that would be an endless redirect loop behind a TLS-terminating proxy.
- An unknown Host got **400**, and the rejection was logged. Our `LOGGING` uses `"disable_existing_loggers": False`; with the default `True`, Django's config would silently disable Gunicorn's access logger, a common source of "Gunicorn writes no logs".
- After **SIGTERM** the master finished current work and exited, and the access log held all four requests. Orchestrators (systemd, Docker, Kubernetes) send SIGTERM first and only SIGKILL after a grace period.

</En>
<Ur>

- `collectstatic` ne har app ki static files (admin ki CSS samait) `staticfiles/` me copy kin, woh folder jo Nginx serve karega. `DEBUG = False` hone par Django static files serve nahi karta.
- `check --deploy` ne sirf **W004** (HSTS) chhora, kyunke qadam 2 me Nginx woh header jorta hai. Duplicates se bachne ke liye har header ki ek jagah chunein.
- Gunicorn ke master ne **2 workers** shuru kiye. Aam shuruati andaza `2 × CPU cores + 1` hai, memory ke hisaab se kam zyada; `--timeout` ek request par atke worker ko khatam kar ke badal deta hai.
- `/health/` ne saade HTTP par jawab diya kyunke ye `SECURE_REDIRECT_EXEMPT` me hai; load balancers aur Docker health checks aam taur par ise TLS ke baghair bulate hain.
- `/admin/` ki saadi HTTP request ko **https par 301** mila. `X-Forwarded-Proto: https` wali wahi request (jaise Nginx bhejega) secure samjhi gayi aur admin ke login redirect tak pohanchi. `SECURE_PROXY_SSL_HEADER` ke baghair TLS khatam karne wale proxy ke peeche ye na khatam hone wala redirect loop hota.
- Na-maloom Host ko **400** mila, aur inkar log hua. Hamara `LOGGING` `"disable_existing_loggers": False` istemal karta; default `True` ke saath Django ki config khamoshi se Gunicorn ka access logger band kar deti, jo "Gunicorn koi log nahi likhta" ki aam wajah hai.
- **SIGTERM** ke baad master ne mojooda kaam khatam kar ke exit kiya, aur access log me chaaron requests thin. Orchestrators (systemd, Docker, Kubernetes) pehle SIGTERM bhejte aur muhlat ke baad hi SIGKILL.

</Ur>
</Tr>

<Step title="Docker image from pinned wheels, Nginx with TLS and static files, and Compose">

<Tr>
<En>
We download exact wheels for the pinned requirements so the Docker build needs no network, and write a Dockerfile that installs only from those wheels, copies the code, runs `collectstatic` at build time with a throwaway key, and switches to a non-root user. Nginx gets a self-signed certificate for the demo, redirects HTTP to HTTPS, adds HSTS, hides its version, serves `/static/` from a shared volume and proxies the rest to Gunicorn, overwriting `X-Forwarded-Proto`. Compose injects secrets from `.env`, waits for Django's health check before starting Nginx, and publishes ports on localhost only. We start everything, test it with `curl`, and tear it down.
</En>
<Ur>
Hum pinned requirements ki bilkul wheels download karte taa ke Docker build ko network na chahiye, aur aisi Dockerfile likhte jo sirf unhi wheels se install karti, code copy karti, waqti key ke saath build ke waqt `collectstatic` chalati, aur non-root user par jati hai. Nginx ko demo ke liye self-signed certificate milta, ye HTTP ko HTTPS par redirect karta, HSTS jorta, apna version chhupata, mushtarka volume se `/static/` serve karta aur `X-Forwarded-Proto` overwrite karte hue baqi Gunicorn ko bhejta hai. Compose `.env` se secrets deta, Nginx shuru karne se pehle Django ke health check ka intezar karta, aur ports sirf localhost par kholta hai. Hum sab shuru karte, `curl` se test karte, aur band kar dete hain.
</Ur>
</Tr>

```bash
export UV_EXCLUDE_NEWER=2025-06-01T00:00:00Z NO_PROXY=127.0.0.1,localhost
. .venv/bin/activate && cd app
# 1. Dependencies as pinned wheels (reproducible builds; no network needed inside docker build)
printf 'django==5.2.1\ngunicorn==23.0.0\nasgiref==3.8.1\nsqlparse==0.5.3\npackaging==25.0\n' > requirements.txt
uvx -q --python 3.13 pip download -q --no-deps --only-binary=:all: --python-version 3.13 \
  --platform manylinux2014_x86_64 -d wheels -r requirements.txt && ls wheels | sed 's/-py3.*//'

cat > Dockerfile <<'EOF'
FROM python:3.13-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 DJANGO_SETTINGS_MODULE=config.settings_prod
RUN useradd --uid 10001 --create-home app
WORKDIR /app
COPY requirements.txt wheels/ /tmp/wheels/
RUN pip install --no-cache-dir --no-index --find-links /tmp/wheels -r /tmp/wheels/requirements.txt \
 && rm -rf /tmp/wheels
COPY manage.py ./
COPY config/ config/
RUN DJANGO_SECRET_KEY=build-only DJANGO_ALLOWED_HOSTS=localhost python manage.py collectstatic --noinput -v 0
USER app
EXPOSE 8000
CMD ["gunicorn", "config.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3", "--access-logfile", "-"]
EOF
printf '.venv\n*.log\n*.pid\n.env\nstaticfiles\n__pycache__\n' > .dockerignore

# 2. Nginx terminates TLS, serves /static/ itself and proxies the rest to Gunicorn
mkdir -p nginx/certs
openssl req -x509 -newkey rsa:2048 -nodes -days 1 -subj "/CN=localhost" \
  -keyout nginx/certs/key.pem -out nginx/certs/cert.pem 2>/dev/null
cat > nginx/default.conf <<'EOF'
server {
    listen 80;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    ssl_certificate     /etc/nginx/certs/cert.pem;
    ssl_certificate_key /etc/nginx/certs/key.pem;
    server_tokens off;
    client_max_body_size 5m;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location /static/ {
        alias /static/;
        expires 30d;
    }
    location / {
        proxy_pass http://web:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;   # overwrite: clients can't fake it
        proxy_read_timeout 30s;
    }
}
EOF

# 3. Compose: secrets from an .env file that never goes into Git or the image
echo "DJANGO_SECRET_KEY=$(python -c 'import secrets; print(secrets.token_urlsafe(50))')" > .env   # no $ signs: compose would try to expand them
echo "DJANGO_ALLOWED_HOSTS=localhost" >> .env
cat > compose.yaml <<'EOF'
services:
  web:
    build: .
    env_file: .env
    volumes: ["static:/app/staticfiles"]
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health/', timeout=3)"]
      interval: 5s
      retries: 5
  nginx:
    image: nginx:1.29-alpine
    ports: ["127.0.0.1:8080:80", "127.0.0.1:8443:443"]
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
```

## Common mistakes

<Compare>
<Bad title="runserver in production, secrets in the image">

```text
FROM python:3.13
COPY . .                                   # includes .env, .git and local junk
RUN pip install -r requirements.txt        # unpinned, as root
ENV DJANGO_SECRET_KEY=prod-secret-123      # baked into every layer
CMD python manage.py runserver 0.0.0.0:8000
```

</Bad>
<Good title="Pinned, non-root, Gunicorn, secrets at runtime">

```text
FROM python:3.13-slim
RUN useradd --uid 10001 --create-home app
COPY requirements.txt wheels/ /tmp/wheels/
RUN pip install --no-cache-dir --no-index --find-links /tmp/wheels -r /tmp/wheels/requirements.txt
COPY manage.py config/ ...                 # with a .dockerignore
USER app
CMD ["gunicorn", "config.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3"]
# DJANGO_SECRET_KEY comes from the orchestrator's secret store at runtime
```

</Good>
</Compare>

<Compare>
<Bad title="Trusting whatever the client sends as X-Forwarded-Proto">

```text
location / {
    proxy_pass http://web:8000;
    proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto;   # client-controlled
}
```

</Bad>
<Good title="The proxy sets it from what it actually saw">

```text
location / {
    proxy_pass http://web:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;    # or "https" on a TLS-only server block
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Running migrations automatically in every container start**: with several replicas they race; run them once as a release step.
- **Too many or too few workers**: start from `2 × cores + 1`, then measure memory and latency.
- **Publishing Gunicorn's port to the internet**: only Nginx should be reachable; bind Gunicorn to localhost or an internal network.
- **No request size limit or timeouts**: set `client_max_body_size`, proxy timeouts and Gunicorn `--timeout`.
- **Ignoring logs and health**: send stdout logs to a central system and alert on failing health checks.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Har container start par khud migrations chalana**: kai replicas ke saath ye takraati hain; release ke qadam ke taur par ek dafa chalayen.
- **Bohat zyada ya bohat kam workers**: `2 × cores + 1` se shuru karein, phir memory aur latency naapein.
- **Gunicorn ka port internet par kholna**: sirf Nginx tak pohanch honi chahiye; Gunicorn ko localhost ya andaruni network se bind karein.
- **Request size limit ya timeouts nahi**: `client_max_body_size`, proxy timeouts aur Gunicorn `--timeout` set karein.
- **Logs aur health nazar andaz karna**: stdout logs markazi system ko bhejein aur nakam health checks par alert karein.

</Ur>
</Tr>

```text
def gunicorn_settings(cpus, memory_mb, per_worker_mb=150, io_heavy=False):
    """Pick a worker setup: (2 x CPUs) + 1, capped by memory."""
    workers = 2 * cpus + 1
    workers = min(workers, max(1, (memory_mb - 256) // per_worker_mb))   # leave room for the OS
    conf = {"workers": workers, "timeout": 30, "graceful_timeout": 30, "max_requests": 1000,
            "max_requests_jitter": 100}                                    # recycle workers to limit leaks
    if io_heavy:
        conf |= {"worker_class": "gthread", "threads": 4}
    return conf

def render(conf):
    return "\n".join(f"{k} = {v!r}" for k, v in conf.items())

for cpus, mem, io in [(1, 512, False), (2, 2048, False), (4, 1024, True)]:
    print(f"--- {cpus} CPU, {mem} MB, io_heavy={io}")
```

<Solution>

<Tr>
<En>

```text
import django
from django.conf import settings
settings.configure(INSTALLED_APPS=["django.contrib.contenttypes"],
                   DATABASES={"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}},
                   ALLOWED_HOSTS=["testserver"])
django.setup()
from unittest.mock import patch
from django.db import connection, OperationalError
from django.http import JsonResponse
from django.test import RequestFactory

def live(request):
    return JsonResponse({"status": "ok"})               # the process is up

def ready(request):
    try:
        with connection.cursor() as cur:                # dependencies reachable?
            cur.execute("SELECT 1")
    except OperationalError:
        return JsonResponse({"status": "unavailable", "db": "down"}, status=503)
    return JsonResponse({"status": "ok", "db": "ok"})

rf = RequestFactory()
print("live :", live(rf.get("/health/live/")).status_code)
r = ready(rf.get("/health/ready/")); print("ready:", r.status_code, r.content.decode())
with patch.object(connection, "cursor", side_effect=OperationalError("connection refused")):
    r = ready(rf.get("/health/ready/")); print("ready (db down):", r.status_code, r.content.decode())

# live : 200
# ready: 200 {"status": "ok", "db": "ok"}
# ready (db down): 503 {"status": "unavailable", "db": "down"}
```

Orchestrators restart containers that fail liveness, but only stop sending traffic to ones that fail readiness, so a database outage doesn't cause a restart storm.

<DeepDive title="More about deploying Django">

**Real certificates.** Let's Encrypt with certbot (or Caddy, which automates it) replaces the self-signed demo certificate.

**WhiteNoise.** Serves compressed, cache-busted static files from Django itself, handy on PaaS or behind an Ingress without Nginx.

**ASGI.** For async views and WebSockets, run `gunicorn -k uvicorn.workers.UvicornWorker config.asgi:application` or Daphne.

**Zero-downtime deploys.** Rolling updates (start new containers, wait for readiness, then stop old ones) plus backward-compatible migrations.

**Media files.** User uploads belong in object storage (django-storages + S3), not inside containers.

</DeepDive>

<DeepDive title="Real world: the deploy that dropped orders">

A shop deployed by stopping its single Django container and starting a new one. During each deploy, in-flight checkout requests were killed mid-transaction, and for about 20 seconds customers saw 502 errors. The container also ran `migrate` on start, and once two copies raced and left a migration half-applied.

The fixes:

1. Two replicas behind the proxy with rolling updates gated on a readiness check.
2. Gunicorn given a graceful timeout longer than the slowest request, and the orchestrator's stop grace period set to match.
3. Migrations moved to a single release job that runs before the rollout, written to be backward-compatible.

</DeepDive>

<DeepDive title="Security lens">

- **Minimize exposure**: only Nginx (or the load balancer) is public; Gunicorn and the database stay on internal networks.
- **Least privilege containers**: non-root user, read-only filesystem where possible, no extra capabilities.
- **Secrets at runtime**: from a secret manager or orchestrator, never in images, Dockerfiles or Git.
- **Supply chain**: pinned and hashed dependencies, minimal base images, image scanning (Trivy) in CI.
- **Hardened proxy**: TLS 1.2+, HSTS, hidden versions, body size limits, timeouts and rate limits for login endpoints.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why put Nginx in front of Gunicorn?">
Nginx handles TLS, slow clients, static files, request limits and buffering efficiently, protecting the limited pool of Python workers, and adds security headers and redirects.
</QA>

<QA q="How many Gunicorn workers should you run?">
A common start is two times the CPU cores plus one, adjusted for memory per worker and measured latency; I/O-heavy apps may use threaded or async workers instead.
</QA>

<QA q="What is SECURE_PROXY_SSL_HEADER for?">
Behind a TLS-terminating proxy, Django sees plain HTTP; this setting tells Django which header indicates the original request was HTTPS, avoiding redirect loops, as long as the proxy always overwrites that header.
</QA>

<QA q="How do you make a Docker image for Django secure?">
Use a slim pinned base, install pinned dependencies, copy only needed files with a .dockerignore, run as a non-root user, inject secrets at runtime, and scan the image.
</QA>

<QA q="How should database migrations be run during deployment?">
As a single release step before new code receives traffic, with migrations designed to be backward-compatible so old and new versions can run during a rolling update.
</QA>

</DeepDive>
