<BigIdea>
<Tr>
<En>
Two questions protect every web app. **Authentication** asks *who are you?* and **authorization** asks *what may you do?* Django's `django.contrib.auth` answers both. Users are stored in the `User` model, and passwords are never stored as text: `create_user` and `set_password` save a **salted PBKDF2 hash** with a high iteration count, and `check_password` verifies by recomputing it. The built-in **`LoginView`** checks the username and password, rejects bad credentials with a generic message, and on success starts a **session**: Django stores the user's ID server-side and gives the browser a `sessionid` cookie. Every request then has **`request.user`**, either a real user or `AnonymousUser`. Views are protected with **`@login_required`** (redirects to `LOGIN_URL` with a `next` parameter) and, for class-based views, `LoginRequiredMixin`. Authorization comes in layers. **Model permissions** (`add_`, `change_`, `delete_`, `view_` per model, plus custom ones in `Meta.permissions`) are granted to users directly or, better, through **groups**, and checked with `user.has_perm("app.codename")` or `@permission_required`. Staff-only pages use `is_staff` checks. But permissions say "may edit notes", not "may edit *this* note", so every view that loads a specific object needs an **object-level check**, typically filtering by `owner=request.user`. Forgetting that check is the classic **IDOR** vulnerability.
</En>
<Ur>
Har web app ki hifazat do sawal karte hain. **Authentication** poochhta hai *aap kaun hain?* aur **authorization** poochhta hai *aap kya kar sakte hain?* Django ka `django.contrib.auth` dono ka jawab deta hai. Users `User` model me rakhe jate hain, aur passwords kabhi text ki shakal me nahi rakhe jate: `create_user` aur `set_password` zyada iterations ke saath **salted PBKDF2 hash** save karte, aur `check_password` dobara hisaab kar ke tasdeeq karta hai. Built-in **`LoginView`** username aur password check karta, ghalat credentials ko aam paigham ke saath radd karta, aur kamyabi par **session** shuru karta hai: Django user ki ID server par rakhta aur browser ko `sessionid` cookie deta hai. Phir har request me **`request.user`** hota hai, ya asal user ya `AnonymousUser`. Views **`@login_required`** (`next` parameter ke saath `LOGIN_URL` par redirect) aur class-based views ke liye `LoginRequiredMixin` se mehfooz hote hain. Authorization tahon me aati hai. **Model permissions** (har model ke liye `add_`, `change_`, `delete_`, `view_`, aur `Meta.permissions` me custom) users ko seedha ya, behtar, **groups** ke zariye di jati hain, aur `user.has_perm("app.codename")` ya `@permission_required` se check hoti hain. Sirf staff wale pages `is_staff` checks istemal karte hain. Magar permissions kehti hain "notes edit kar sakta hai", "*ye* note edit kar sakta hai" nahi, isliye kisi khaas object ko load karne wale har view ko **object-level check** chahiye, aam taur par `owner=request.user` se chhaan kar. Woh check bhoolna mashhoor **IDOR** kamzori hai.
</Ur>

## Picture it

<Tr>
<En>

Think of an **office building**.

- At reception you show ID (authentication). You get a **visitor badge** for the day (the session cookie); guards check the badge, not your ID, at every door.
- The badge's colour says which floors you may enter (permissions); colours are handed out by role, such as "engineering" or "finance" (groups).
- Even on the right floor, you may open only **your own** desk drawer (object-level checks). A badge that opens every drawer on the floor is the IDOR bug.
- The reception desk never writes your PIN in a book; it keeps a one-way fingerprint of it (password hashing).

</En>
<Ur>

**Office building** socheyn.

- Reception par aap ID dikhate hain (authentication). Aap ko din bhar ke liye **visitor badge** milta hai (session cookie); guards har darwaze par aap ki ID nahi, badge check karte hain.
- Badge ka rang batata ke aap kin manzilon par ja sakte hain (permissions); rang role ke hisaab se milte hain, jaise "engineering" ya "finance" (groups).
- Sahi manzil par bhi aap sirf **apni** desk ki daraz khol sakte hain (object-level checks). Manzil ki har daraz kholne wala badge IDOR bug hai.
- Reception desk kabhi aap ka PIN kitab me nahi likhta; ye us ka ek-taraf fingerprint rakhta hai (password hashing).

<Happened>
<Tr>
<En>

- `create_user` stored `pbkdf2_sha256$1000000$salt$hash`: the algorithm, **one million** iterations and a random salt. The plain password appears nowhere. `check_password` verified by recomputing. Never assign `user.password = "..."` directly; always use `set_password` or `create_user`.
- Visiting the dashboard anonymously redirected to **`/login/?next=/dashboard/`**: `@login_required` sent the user to `LOGIN_URL` and remembered where they wanted to go.
- A wrong password re-displayed the form (200) with Django's **generic message**, which doesn't reveal whether the username or the password was wrong, making account enumeration harder.
- The right password redirected to the dashboard and set the **`sessionid`** cookie. Django also rotates the session key on login, preventing session fixation.
- Logout is a **POST** in modern Django (so other sites can't log users out with a link); afterwards the dashboard redirected to login again.
- With CSRF checks enforced, a login POST without the token got **403**. Django's CSRF middleware protects every form, including login.

</En>
<Ur>

- `create_user` ne `pbkdf2_sha256$1000000$salt$hash` rakha: algorithm, **one million** iterations aur random salt. Saada password kahin nazar nahi aata. `check_password` ne dobara hisaab kar ke tasdeeq ki. Kabhi `user.password = "..."` seedha na rakhein; hamesha `set_password` ya `create_user` lein.
- Bina login dashboard par jane se **`/login/?next=/dashboard/`** par redirect hua: `@login_required` ne user ko `LOGIN_URL` par bheja aur yaad rakha ke woh kahan jana chahta tha.
- Ghalat password ne form dobara dikhaya (200) Django ke **aam paigham** ke saath, jo nahi batata ke username ghalat tha ya password, is se accounts dhoondna mushkil hota hai.
- Sahi password ne dashboard par redirect kiya aur **`sessionid`** cookie set ki. Django login par session key bhi badalta hai, jo session fixation rokta hai.
- Jadeed Django me logout **POST** hai (taa ke doosri sites link se users ko logout na kar sakein); is ke baad dashboard phir login par redirect hua.
- CSRF checks lagu hone par token ke baghair login POST ko **403** mila. Django ka CSRF middleware login samait har form ki hifazat karta hai.

<Step title="Permissions, custom permissions, groups, staff checks and object-level access">

<Tr>
<En>
We add a `Note` model with an owner and a custom `edit_any_note` permission, and three views: `note_detail` shows only the user's own notes, `note_edit` requires the `change_note` permission and also the owner (or `edit_any_note`), and `staff_report` is staff only. `try_perms.py` creates two groups, **editors** (change_note) and **moderators** (change_note + edit_any_note), puts jane and bob in editors and ana (a staff member) in moderators, creates one note owned by jane, and checks what each user can do, plus a logged-in user with no permissions and an anonymous visitor.
</En>
<Ur>
Hum owner aur custom `edit_any_note` permission wala `Note` model, aur teen views jorte hain: `note_detail` sirf user ke apne notes dikhata, `note_edit` `change_note` permission aur owner (ya `edit_any_note`) bhi maangta, aur `staff_report` sirf staff ke liye hai. `try_perms.py` do groups banati, **editors** (change_note) aur **moderators** (change_note + edit_any_note), jane aur bob ko editors me aur ana (staff member) ko moderators me daalti, jane ka ek note banati, aur check karti ke har user kya kar sakta, saath bina permissions wala logged-in user aur bina login visitor bhi.
</Ur>
</Tr>

```bash
. .venv/bin/activate && cd site
cat > notes/models.py <<'EOF'
from django.conf import settings
from django.db import models

class Note(models.Model):
    owner = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="notes")
    title = models.CharField(max_length=100)
    body = models.TextField()
EOF
cat > notes/views.py <<'EOF'
from django.contrib.auth.decorators import login_required, permission_required, user_passes_test
from django.core.exceptions import PermissionDenied
from django.http import HttpResponse
from django.shortcuts import get_object_or_404
from .models import Note

@login_required
def dashboard(request):
    return HttpResponse(f"Welcome, {request.user.username}")

@login_required
def note_detail(request, pk):
    note = get_object_or_404(Note, pk=pk, owner=request.user)      # object-level: only your own notes
    return HttpResponse(note.title)

@login_required
@permission_required("notes.change_note", raise_exception=True)    # model-level permission
def note_edit(request, pk):
    note = get_object_or_404(Note, pk=pk)
    if note.owner != request.user and not request.user.has_perm("notes.edit_any_note"):
        raise PermissionDenied
    note.title = request.POST.get("title", note.title)
    note.save()
    return HttpResponse(f"saved: {note.title}")

@user_passes_test(lambda u: u.is_active and u.is_staff)
def staff_report(request):
    return HttpResponse(f"{Note.objects.count()} notes in total")
EOF

    class Meta:
        permissions = [("edit_any_note", "Can edit notes owned by anyone")]
EOF

import os, django, logging
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings"); django.setup()
logging.disable(logging.WARNING)
from django.contrib.auth.models import Group, Permission, User
from django.test import Client
from django.test.utils import setup_test_environment
from notes.models import Note
setup_test_environment()                      # allows the "testserver" host, like the test runner does

jane = User.objects.get(username="jane")                 # created in the previous step
bob = User.objects.create_user("bob", password="pw-bob-123")
ana = User.objects.create_user("ana", password="pw-ana-123", is_staff=True)

editors = Group.objects.create(name="editors")
editors.permissions.add(Permission.objects.get(codename="change_note"))
jane.groups.add(editors); bob.groups.add(editors)
moderators = Group.objects.create(name="moderators")
moderators.permissions.add(Permission.objects.get(codename="change_note"), Permission.objects.get(codename="edit_any_note"))
ana.groups.add(moderators)

n1 = Note.objects.create(owner=jane, title="Jane's plan", body="...")
print("jane perms:", sorted(p for p in jane.get_all_permissions()))
print("bob can change_note:", bob.has_perm("notes.change_note"), "| edit_any_note:", bob.has_perm("notes.edit_any_note"))

def as_user(user):
    c = Client(); c.force_login(user); return c

for name, user in [("jane", jane), ("bob", bob), ("ana", ana)]:
    c = as_user(user)
    view = c.get(f"/notes/{n1.pk}/").status_code
    edit = c.post(f"/notes/{n1.pk}/edit/", {"title": f"edited by {name}"}).status_code
    staff = c.get("/staff/report/").status_code
    print(f"{name:<5} view own-only: {view}  edit: {edit}  staff report: {staff}")
print("final title:", Note.objects.get(pk=n1.pk).title)

viewer = User.objects.create_user("viewer", password="pw-viewer-1")     # logged in, no permissions
print("no change_note permission -> edit:", as_user(viewer).post(f"/notes/{n1.pk}/edit/").status_code)
print("anonymous -> staff report:", Client().get("/staff/report/").status_code)
EOF
python try_perms.py
```

<Happened>
<Tr>
<En>

- `get_all_permissions()` showed jane's permission came through the **editors** group. Managing roles through groups means adding a new editor is one line, and auditing "who can edit?" means looking at one group.
- **bob** has `change_note` too, yet viewing jane's note returned **404** and editing returned **403**. The model permission says he may edit notes; the object-level checks say not *this* note. Without `owner=request.user`, bob could read any note by changing the ID in the URL (IDOR).
- **ana** couldn't view the note (it isn't hers) but could edit it because moderators have the custom `edit_any_note` permission, the final title is "edited by ana", and as staff she was the only one allowed into the staff report.
- A logged-in user without `change_note` got **403** because `raise_exception=True` turns a missing permission into Forbidden instead of a confusing login redirect.
- The anonymous visitor was redirected (**302**) from the staff report to the login page: `user_passes_test` redirects anyone who fails, which is why we used `raise_exception` for the permission check.
- 404 versus 403 is a choice: 404 hides that the object exists (good for private data), 403 is clearer when the user knows it exists.

</En>
<Ur>

- `get_all_permissions()` ne dikhaya ke jane ki permission **editors** group se aayi. Groups ke zariye roles sambhalne ka matlab naya editor jorna ek line hai, aur "kaun edit kar sakta?" ka audit ek group dekhna hai.

## Common mistakes

<Compare>
<Bad title="Login required, but no ownership check">

```text
@login_required
def invoice(request, pk):
    inv = Invoice.objects.get(pk=pk)          # any logged-in user can read any invoice: /invoices/2/
    return render(request, "invoice.html", {"inv": inv})
```

</Bad>
<Good title="Scope every query to the user">

```text
@login_required
def invoice(request, pk):
    inv = get_object_or_404(Invoice, pk=pk, customer=request.user)
    return render(request, "invoice.html", {"inv": inv})
```

</Good>
</Compare>

<Compare>
<Bad title="Hand-rolled password handling">

```text
user.password = request.POST["password"]          # stored in plain text
if User.objects.filter(username=u, password=p).exists():
    request.session["user"] = u                   # no session rotation, no rate limiting
```

</Bad>
<Good title="Use Django's auth">

```text
user.set_password(request.POST["password"]); user.save()
user = authenticate(request, username=u, password=p)
if user is not None:
    login(request, user)                          # rotates the session key
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Checking permissions only in templates** (hiding a button): always enforce in the view or API too.
- **Making everyone a superuser** for convenience: give groups the exact permissions they need.
- **No rate limiting on login**: add django-axes or a reverse-proxy limit against brute force.
- **Different error messages for "no such user" and "wrong password"**: they reveal which accounts exist.
- **Logging out with GET links**: use POST, as Django 5 requires.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sirf templates me permissions check karna** (button chhupana): view ya API me bhi hamesha lagu karein.
- **Sahulat ke liye sab ko superuser banana**: groups ko bilkul wahi permissions dein jo chahiye.
- **Login par rate limiting nahi**: brute force ke khilaf django-axes ya reverse-proxy limit jorein.
- **"Aisa user nahi" aur "ghalat password" ke alag paighamat**: ye batate kaun se accounts mojood hain.
- **GET links se logout**: POST lein, jaisa Django 5 maangta hai.

</Ur>

```text
import django
from django.conf import settings

settings.configure(
    INSTALLED_APPS=["django.contrib.auth", "django.contrib.contenttypes"],
    DATABASES={"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}},
```
```text
    ROOT_URLCONF=__name__, LOGIN_URL="/login/", ALLOWED_HOSTS=["testserver"],
)
django.setup()
from django.contrib.auth.mixins import LoginRequiredMixin, UserPassesTestMixin
from django.contrib.auth.models import AnonymousUser, User
from django.core.exceptions import PermissionDenied
from django.core.management import call_command
from django.http import HttpResponse
from django.test import RequestFactory
from django.views import View

urlpatterns = []
call_command("migrate", verbosity=0)

INVOICES = {1: "jane", 2: "bob"}            # invoice id -> owner username

class InvoiceView(LoginRequiredMixin, UserPassesTestMixin, View):
    raise_exception = False                  # anonymous users get redirected to the login page
    def test_func(self):
        owner = INVOICES.get(self.kwargs["pk"])
        return self.request.user.is_superuser or owner == self.request.user.username
    def handle_no_permission(self):
        if self.request.user.is_authenticated:
            raise PermissionDenied           # logged in but not allowed: 403, not a login redirect
        return super().handle_no_permission()
    def get(self, request, pk):
        return HttpResponse(f"invoice {pk}")

jane = User.objects.create_user("jane"); bob = User.objects.create_user("bob")
admin = User.objects.create_superuser("admin", password="x-admin-pw-1")
rf = RequestFactory()
view = InvoiceView.as_view()
for who in [AnonymousUser(), jane, bob, admin]:
    request = rf.get("/invoices/1/"); request.user = who
    try:
        r = view(request, pk=1)
        result = r.status_code if r.status_code != 200 else f"200 {r.content.decode()}"
        if r.status_code == 302:
            result = f"302 -> {r['Location']}"
    except PermissionDenied:
        result = "403 PermissionDenied"
    print(f"{who.username or 'anonymous':<9} {result}")

# anonymous 302 -> /login/?next=/invoices/1/
# jane      200 invoice 1
# bob       403 PermissionDenied
# admin     200 invoice 1
```

<DeepDive title="More about Django auth">

**Custom user model.** Start every new project with `AUTH_USER_MODEL = "accounts.User"` subclassing `AbstractUser`; changing it later is painful.

**Password hashers.** Add `Argon2PasswordHasher` first in `PASSWORD_HASHERS` (needs `argon2-cffi`); old hashes upgrade automatically at login.

**Object permissions.** django-guardian or django-rules provide per-object permission systems when ownership isn't enough.

**MFA and SSO.** django-allauth adds social login, email verification and TOTP; django-otp adds two-factor authentication.

**Session security.** `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_HTTPONLY`, `SESSION_COOKIE_AGE` and `SESSION_EXPIRE_AT_BROWSER_CLOSE` tune the session cookie (see the Django Security Settings lesson).

</DeepDive>

<DeepDive title="Real world: the invoice IDOR">

A billing portal let customers download invoices at `/invoices/<id>/pdf/`. The view had `@login_required` but fetched invoices with `Invoice.objects.get(pk=id)`. A customer noticed sequential IDs, changed the number, and downloaded another company's invoice, including names, addresses and amounts. A script could have downloaded all of them.

The fixes:

1. Every invoice query filtered by the logged-in customer's account, returning 404 otherwise.
2. A test for every endpoint that fetches objects, checking that another user gets 404.
3. Random, non-sequential public IDs (UUIDs) as defense in depth, not as the main control.

</DeepDive>

<DeepDive title="Security lens">

- **Broken access control** (OWASP A01): check ownership on the server for every object, every method (GET, POST, DELETE).
- **Credential attacks**: rate-limit logins, offer MFA, use strong password validators and breached-password checks.
- **Least privilege**: few superusers, staff with specific permissions, roles via groups, regular reviews.
- **Session hygiene**: secure cookie flags, logout via POST, session rotation on login and privilege changes.
- **Test authorization**: automated tests that try other users' IDs catch IDORs before attackers do.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between authentication and authorization?">
Authentication verifies identity, for example with a password; authorization decides what an authenticated identity may do, for example with permissions and ownership checks.
</QA>

<QA q="How does Django keep a user logged in between requests?">
After login it stores the user's ID in a server-side session and sends a session ID cookie; on each request, middleware loads the session and sets request.user.
</QA>

<QA q="What are Django model permissions and how are they assigned?">
Django creates add, change, delete and view permissions for each model, plus custom ones from Meta.permissions; they're assigned to users directly or through groups and checked with has_perm.
</QA>

<QA q="How do you prevent IDOR in Django?">
Scope object lookups to the current user, for example get_object_or_404(Model, pk=pk, owner=request.user), apply the same checks in APIs and for every HTTP method, and test with other users' IDs.
</QA>

<QA q="When should a view return 403 versus 404?">
Return 403 when the user may know the resource exists but isn't allowed; return 404 to avoid revealing the existence of private objects belonging to others.
</QA>

</DeepDive>
