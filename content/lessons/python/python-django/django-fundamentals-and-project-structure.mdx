<BigIdea>
<Tr>
<En>
**Django** follows a simple loop: a **request** comes in, Django matches its path against your **URL patterns**, calls the matching **view** (a Python function or class), and the view returns a **response** (HTML, JSON, a redirect or an error). Everything else, such as the database layer, templates, forms and the admin, helps views do their job. A Django codebase has two levels. The **project** is the whole site: `manage.py` (the command-line entry point), and a settings package (often named `config`) with **`settings.py`** (configuration: installed apps, database, middleware, security options), the root **`urls.py`**, and `wsgi.py`/`asgi.py` for production servers. **Apps** are self-contained feature areas (`catalog`, `orders`, `accounts`), each with its own models, views, URLs, admin and tests, and they must be listed in `INSTALLED_APPS`. You create them with `django-admin startproject` and `python manage.py startapp`; `migrate` creates database tables, `check` validates the configuration, `runserver` starts a development server (never for production), and `test` runs your tests. URL patterns use **converters** like `<int:product_id>`, apps are attached with **`include`**, and named routes with an **app namespace** let you build URLs with **`reverse()`** instead of hard-coding them.
</En>
<Ur>
**Django** ek saade chakkar par chalta hai: **request** aati, Django us ke path ko aap ke **URL patterns** se milata, milte **view** (Python function ya class) ko bulata, aur view **response** (HTML, JSON, redirect ya error) lautata hai. Baqi sab, jaise database layer, templates, forms aur admin, views ki madad karte hain. Django codebase ke do darje hain. **Project** poori site hai: `manage.py` (command-line ka entry point), aur settings package (aksar `config` naam) jis me **`settings.py`** (configuration: installed apps, database, middleware, security options), root **`urls.py`**, aur production servers ke liye `wsgi.py`/`asgi.py` hain. **Apps** apne aap me mukammal feature ke hisse hain (`catalog`, `orders`, `accounts`), har ek ke apne models, views, URLs, admin aur tests, aur unhe `INSTALLED_APPS` me likhna lazmi hai. Aap inhe `django-admin startproject` aur `python manage.py startapp` se banate hain; `migrate` database tables banata, `check` configuration jaanchta, `runserver` development server chalata (production ke liye kabhi nahi), aur `test` aap ke tests chalata hai. URL patterns `<int:product_id>` jaise **converters** istemal karte, apps **`include`** se jurti hain, aur **app namespace** wale naam ke routes aap ko URLs hard-code karne ke bajaye **`reverse()`** se banane dete hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **department store**.

- The project is the store building: one address, one set of rules (settings), one directory at the entrance (root URLs).
- Apps are departments: electronics, clothing, returns. Each runs itself (its own views, models, URLs) but follows store rules and is listed in the directory (`INSTALLED_APPS`).
- A request is a customer asking at the entrance; the directory sends them to the right department (`include`), where a clerk (the view) serves them and hands back a bag (the response).
- `reverse()` is asking the directory "where is electronics?" instead of memorizing "third floor, left", so moving a department doesn't break every sign in the store.

</En>
<Ur>

**Department store** socheyn.

- Project store ki imarat hai: ek pata, qawaid ka ek set (settings), darwaze par ek directory (root URLs).
- Apps departments hain: electronics, kapre, wapsi. Har ek khud chalta (apne views, models, URLs) magar store ke qawaid maanta aur directory me likha hota hai (`INSTALLED_APPS`).
- Request darwaze par poochhta customer hai; directory use sahi department bhejti (`include`), jahan clerk (view) khidmat kar ke thaila (response) deta hai.
- `reverse()` "teesri manzil, baayen" yaad karne ke bajaye directory se poochhna hai "electronics kahan hai?", taa ke department hilne se store ka har board na toote.

</Ur>
</Tr>

<Step title="Views, URL patterns, include, reverse and tests">

<Tr>
<En>
We write two views in `catalog/views.py` (an HTML home page and a JSON product detail that raises 404 for unknown IDs), give the app its own `urls.py` with a namespace, include it from the root URLs, register the app in `INSTALLED_APPS`, and add four tests. A small script then uses Django's test client to request a few URLs and `reverse()` a URL by name, and finally we run the test suite.
</En>
<Ur>
Hum `catalog/views.py` me do views likhte (HTML home page aur JSON product detail jo na-maloom IDs par 404 uthata), app ko namespace ke saath apni `urls.py` dete, use root URLs se include karte, app ko `INSTALLED_APPS` me register karte, aur chaar tests jorte hain. Phir chhoti script Django ke test client se chand URLs maangti aur naam se URL `reverse()` karti, aur aakhir me hum test suite chalate hain.
</Ur>
</Tr>

```bash
. .venv/bin/activate && cd shop
cat > catalog/views.py <<'EOF'
from django.http import Http404, HttpResponse, JsonResponse

PRODUCTS = {1: {"name": "Keyboard", "price": "49.50"}, 2: {"name": "Mouse", "price": "19.99"}}

def home(request):
    return HttpResponse("<h1>Shop</h1><p>Welcome!</p>")

def product_detail(request, product_id):          # product_id comes from the URL, already an int
    product = PRODUCTS.get(product_id)
    if product is None:
        raise Http404("No such product")
    return JsonResponse({"id": product_id, **product})
EOF
cat > catalog/urls.py <<'EOF'
from django.urls import path
from . import views

app_name = "catalog"
urlpatterns = [
    path("", views.home, name="home"),
    path("products/<int:product_id>/", views.product_detail, name="product-detail"),
]
EOF
cat > config/urls.py <<'EOF'
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("catalog.urls")),          # the app owns its own URLs
]
EOF
sed -i 's/    "django.contrib.staticfiles",/    "django.contrib.staticfiles",\n    "catalog",/' config/settings.py
cat > catalog/tests.py <<'EOF'
from django.test import TestCase
from django.urls import reverse

class CatalogTests(TestCase):
    def test_home(self):
        r = self.client.get(reverse("catalog:home"))
        self.assertContains(r, "Welcome")

    def test_product_json(self):
        r = self.client.get(reverse("catalog:product-detail", args=[1]))
        self.assertEqual(r.json(), {"id": 1, "name": "Keyboard", "price": "49.50"})

    def test_missing_product_is_404(self):
        self.assertEqual(self.client.get("/products/99/").status_code, 404)

    def test_non_integer_id_does_not_match(self):
        self.assertEqual(self.client.get("/products/abc/").status_code, 404)
EOF
python manage.py check
cat > explore.py <<'EOF'
import django, logging, os
logging.disable(logging.WARNING)                  # hide Django's "Not Found" log lines here
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")
django.setup()                                    # what manage.py does before any command
from django.test import Client
from django.urls import reverse

c = Client(HTTP_HOST="localhost")
print("reverse():", reverse("catalog:product-detail", args=[2]))
for url in ["/", "/products/2/", "/products/99/", "/admin/"]:
    r = c.get(url)
    print(f"{url:<15} {r.status_code}  {r.headers['Content-Type'].split(';')[0]:<17} {r.headers.get('Location', '')}".rstrip())
print(c.get("/products/2/").json())
EOF
python explore.py
python manage.py test catalog 2>&1 | grep -oE "^(Ran [0-9]+ tests|OK|FAILED.*)"
```

<Happened>
<Tr>
<En>

- A view is just a function that takes a **request** and returns a **response**. `HttpResponse` returned HTML; `JsonResponse` serialized a dict and set `Content-Type: application/json`.
- `<int:product_id>` matched only digits and passed an **int** to the view, so `/products/abc/` never reached it (the test confirms a 404). Raising **Http404** produced a proper 404 response for an unknown ID.
- The root `urls.py` only does `include("catalog.urls")`; the app owns its routes. With `app_name = "catalog"`, `reverse("catalog:product-detail", args=[2])` built **/products/2/**, so templates and redirects never hard-code paths.
- `/admin/` answered **302** to the login page: the admin is already wired up and protected (we'll use it in a later lesson).
- `django.setup()` is what `manage.py` does before running a command: it reads settings and loads apps, which standalone scripts must do too. We used `HTTP_HOST="localhost"` because Django validates the Host header even in tests (outside the test runner).
- `manage.py test` created a **separate test database**, ran **4 tests**, and reported **OK**. `TestCase` wraps each test in a transaction, so tests don't affect each other or your real data.

</En>
<Ur>

- View bas ek function hai jo **request** le kar **response** lautata hai. `HttpResponse` ne HTML lautaya; `JsonResponse` ne dict serialize kar ke `Content-Type: application/json` set kiya.
- `<int:product_id>` ne sirf digits milaye aur view ko **int** diya, isliye `/products/abc/` us tak kabhi nahi pohancha (test 404 ki tasdeeq karta hai). **Http404** uthane ne na-maloom ID ke liye durust 404 response banaya.
- Root `urls.py` sirf `include("catalog.urls")` karta; app apne routes ki maalik hai. `app_name = "catalog"` ke saath `reverse("catalog:product-detail", args=[2])` ne **/products/2/** banaya, isliye templates aur redirects kabhi paths hard-code nahi karte.
- `/admin/` ne login page par **302** diya: admin pehle se jura aur mehfooz hai (hum agle lesson me istemal karenge).
- `django.setup()` wahi hai jo `manage.py` command chalane se pehle karta: settings parhta aur apps load karta, jo alag scripts ko bhi karna parta hai. Humne `HTTP_HOST="localhost"` istemal kiya kyunke Django tests me bhi (test runner ke bahar) Host header jaanchta hai.
- `manage.py test` ne **alag test database** banaya, **4 tests** chalaye, aur **OK** bataya. `TestCase` har test ko transaction me lapetta, isliye tests ek doosre ya aap ke asal data ko mutasir nahi karte.

</Ur>

## Common mistakes

<Compare>
<Bad title="Hard-coded URLs and forgetting to register the app">

```text
# settings.py: "catalog" missing from INSTALLED_APPS -> models, templates, migrations ignored
return redirect("/products/" + str(pid) + "/")       # breaks when the URL changes
```

</Bad>
<Good title="Registered app and named URLs">

```text
INSTALLED_APPS = [..., "catalog"]
return redirect("catalog:product-detail", product_id=pid)
# templates: {% url 'catalog:product-detail' product.id %}
```

</Good>
</Compare>

<Compare>
<Bad title="Using the development setup in production">

```text
DEBUG = True                      # shows stack traces and settings to visitors
ALLOWED_HOSTS = ["*"]
python manage.py runserver 0.0.0.0:80
```

</Bad>
<Good title="Production server and settings from the environment">

```text
DEBUG = os.environ.get("DJANGO_DEBUG") == "1"
ALLOWED_HOSTS = os.environ["DJANGO_ALLOWED_HOSTS"].split(",")
gunicorn config.wsgi:application --bind 127.0.0.1:8000    # behind Nginx
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **One giant app for everything**: split by feature (catalog, orders, accounts) so code stays navigable.
- **Committing `db.sqlite3` or the `SECRET_KEY`**: keep them out of Git; load secrets from the environment.
- **Business logic inside `urls.py` or giant views**: keep views thin and move logic into functions or model methods.
- **Forgetting the trailing slash convention**: Django redirects `/health` to `/health/` (with `APPEND_SLASH`), which breaks POSTs; be consistent.
- **Skipping `manage.py check` and tests** in CI.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Har cheez ke liye ek bari app**: feature ke hisaab se baantein (catalog, orders, accounts) taa ke code me raasta milta rahe.
- **`db.sqlite3` ya `SECRET_KEY` commit karna**: inhe Git se bahar rakhein; secrets environment se load karein.
- **`urls.py` ya bare views me business logic**: views patle rakhein aur logic functions ya model methods me le jayen.
- **Aakhri slash ka riwaj bhoolna**: Django `/health` ko `/health/` par redirect karta (`APPEND_SLASH` ke saath), jo POSTs torta; yaksaan rahein.
- **CI me `manage.py check` aur tests chhorna.**

</Ur>
</Tr>

<Challenge title="Django in a single file">

<Tr>

import django, logging
logging.disable(logging.WARNING)
from django.conf import settings

settings.configure(                                  # a whole Django project in one file
    DEBUG=True, ROOT_URLCONF=__name__, ALLOWED_HOSTS=["localhost"],
    SECRET_KEY="demo-only-not-secret",
    MIDDLEWARE=["django.middleware.common.CommonMiddleware"],   # adds the trailing-slash redirect
)
django.setup()

from django.http import JsonResponse
from django.test import Client
from django.urls import path

def health(request):
    return JsonResponse({"status": "ok"})

def greet(request, name):
    return JsonResponse({"message": f"Hello, {name.replace('-', ' ').title()}!"})

urlpatterns = [
    path("health/", health),
    path("greet/<slug:name>/", greet),
]

c = Client(HTTP_HOST="localhost")
for url in ["/health/", "/greet/jane-cooper/", "/greet/bad name/", "/health"]:
    r = c.get(url)
    body = r.json() if r.headers["Content-Type"] == "application/json" else r.headers.get("Location", "")
    print(f"{url:<20} {r.status_code}  {body}".rstrip())

# /health/             200  {'status': 'ok'}
# /greet/jane-cooper/  200  {'message': 'Hello, Jane Cooper!'}

<Tr>
<En>
Register a `year` path converter that matches only 2000 to 2099, converts to an `int`, and formats back with four digits. Use it in `orders/<year:year>/`, show `reverse("archive", args=[2026])`, and request `/orders/2026/`, `/orders/1999/` and `/orders/26/`.
</En>
<Ur>
`year` path converter register karein jo sirf 2000 se 2099 milaye, `int` me badle, aur chaar digits ke saath wapas format kare. Ise `orders/<year:year>/` me istemal karein, `reverse("archive", args=[2026])` dikhayen, aur `/orders/2026/`, `/orders/1999/` aur `/orders/26/` maangein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
import django, logging
logging.disable(logging.WARNING)
from django.conf import settings

settings.configure(DEBUG=True, ROOT_URLCONF=__name__, ALLOWED_HOSTS=["localhost"], SECRET_KEY="demo-only")
django.setup()

from django.http import HttpResponse
from django.test import Client
from django.urls import path, register_converter, reverse

class YearConverter:
    regex = r"20\d{2}"                       # only years 2000-2099 match
    def to_python(self, value):
        return int(value)
    def to_url(self, value):
        return f"{value:04d}"

register_converter(YearConverter, "year")

def archive(request, year):
    return HttpResponse(f"orders from {year} (type {type(year).__name__})")

urlpatterns = [path("orders/<year:year>/", archive, name="archive")]

c = Client(HTTP_HOST="localhost")
print("reverse:", reverse("archive", args=[2026]))
for url in ["/orders/2026/", "/orders/1999/", "/orders/26/"]:
    r = c.get(url)
    print(f"{url:<14} {r.status_code}  {r.content.decode() if r.status_code == 200 else ''}".rstrip())

# reverse: /orders/2026/
# /orders/2026/  200  orders from 2026 (type int)
# /orders/1999/  404
# /orders/26/    404
```

Converters keep validation in the URL layer, so the view only receives well-formed values.

<DeepDive title="More about Django's structure">

**Middleware.** A chain of hooks around every request (security headers, sessions, CSRF, authentication) configured in `MIDDLEWARE`; order matters.

**Class-based views.** `View`, `TemplateView`, `ListView` and `DetailView` package common patterns; function views stay perfectly fine for simple cases.

**Settings per environment.** Many teams read settings from environment variables (`django-environ`) or split `settings/base.py`, `dev.py`, `prod.py`.

**ASGI.** Django supports async views and runs under Uvicorn or Daphne via `asgi.py`, useful for websockets with Channels.

**Project layouts.** Cookiecutter Django and similar templates provide production-ready structures with Docker, settings and CI.

</DeepDive>

<DeepDive title="Real world: the debug page that leaked settings">

A small company deployed a Django site with `DEBUG = True` copied from development. When a visitor hit a broken page, Django's detailed error page showed the full stack trace, installed apps, request data and many settings values. A security researcher found database host names and an API key in environment-derived settings on that page.

The fixes:

1. `DEBUG` read from the environment and false by default in production, with `manage.py check --deploy` in CI.
2. Error reporting moved to Sentry, with custom 404 and 500 pages for visitors.
3. Exposed keys rotated, and secrets loaded from a secret manager.

</DeepDive>

<DeepDive title="Security lens">

- **DEBUG off and ALLOWED_HOSTS set** in production; `check --deploy` flags missing protections.
- **SECRET_KEY** signs sessions and tokens; keep it secret and out of Git.
- **Built-in protections** (CSRF, XSS escaping in templates, clickjacking middleware, SQL injection safety in the ORM) only work if you don't bypass them.
- **Use the production server stack** (Gunicorn/Uvicorn behind Nginx with HTTPS).
- **Keep Django updated**: security releases come regularly.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Explain Django's request-response cycle.">
A request passes through middleware, the URL resolver matches its path to a view using the URLconf, the view runs (often using models and templates) and returns a response, which passes back through middleware to the client.
</QA>

<QA q="What's the difference between a project and an app?">
A project is the configuration and root URLconf for a whole site; an app is a self-contained package for one feature area, registered in INSTALLED_APPS, that can be reused across projects.
</QA>

<QA q="What does manage.py do?">
It's a thin wrapper around django-admin that sets DJANGO_SETTINGS_MODULE for the project and runs management commands like migrate, runserver, test, shell and createsuperuser.
</QA>

<QA q="Why use URL names and reverse?">
They decouple code and templates from the actual paths, so routes can change in one place without breaking links, redirects or tests.
</QA>

<QA q="How are Django tests isolated?">
The test runner creates a separate test database, and TestCase wraps each test in a transaction that is rolled back afterwards.
</QA>

</DeepDive>
