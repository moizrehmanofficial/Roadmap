<BigIdea>
<Tr>
<En>
A Django page is produced in three steps. The **URLconf** matches the request path (for example `p/<slug:slug>/`) to a **view**. The view gathers data, usually with the ORM, and calls **`render(request, template_name, context)`**, where the context is a dict of values. The **template** is an HTML file with Django's template language: **variables** in double curly braces print values, **filters** after a pipe transform them (`upper`, `default`, `length`, `date`), and **tags** in curly-brace-percent pairs add logic (`for` with an `empty` branch, `if`, `url`, `extends`, `block`, `include`). **Template inheritance** keeps pages consistent: `base.html` defines the layout with named blocks, and each page `extends` it and fills in only its blocks. For security, Django **auto-escapes** every variable, so a product named `<script>` is shown as text instead of running, which prevents most cross-site scripting (XSS); the `safe` filter and `mark_safe` turn that protection off and must only be used on HTML you generated yourself. For common patterns, **class-based views** such as `ListView` and `DetailView` do the work for you: they fetch objects, choose the template name by convention, return 404 for missing objects and paginate lists with `paginate_by`. Keep views thin, put logic in models or helper functions, and keep templates focused on presentation.
</En>
<Ur>
Django page teen qadmon me banta hai. **URLconf** request ke path (maslan `p/<slug:slug>/`) ko **view** se milata hai. View data jama karta, aam taur par ORM se, aur **`render(request, template_name, context)`** bulata, jahan context values ki dict hai. **Template** Django ki template zaban wali HTML file hai: dohre curly braces me **variables** values print karte, pipe ke baad **filters** unhe badalte (`upper`, `default`, `length`, `date`), aur curly-brace-percent joron me **tags** logic jorte (`empty` shakh wala `for`, `if`, `url`, `extends`, `block`, `include`). **Template inheritance** pages ko yaksaan rakhti: `base.html` naam wale blocks ke saath layout define karta, aur har page use `extends` kar ke sirf apne blocks bharta hai. Security ke liye Django har variable ko **auto-escape** karta, isliye `<script>` naam ka product chalne ke bajaye text ki tarah dikhta, jo zyadatar cross-site scripting (XSS) rokta hai; `safe` filter aur `mark_safe` ye hifazat band karte aur sirf apni banayi HTML par istemal hone chahiye. Aam patterns ke liye **class-based views** jaise `ListView` aur `DetailView` aap ka kaam karte: objects laate, riwaj se template ka naam chunte, ghayab objects par 404 lautate aur `paginate_by` se lists ke pages banate hain. Views patle rakhein, logic models ya helper functions me rakhein, aur templates ko pesh karne tak mehdood rakhein.
</Ur>

## Picture it

<Tr>
<En>

Think of a **magazine printing house**.

- The base template is the magazine's master layout: masthead, page numbers, footer. Every article page uses it and only fills in the article area (blocks).
- The view is the editor who gathers the facts (data) and hands them to layout with instructions (context).
- Variables and filters are placeholders on the page ("NAME in capitals here"); tags are the layout rules ("repeat this box for every product, or print 'none' if empty").
- Auto-escaping is the proofreader who prints everything readers send in letters exactly as typed, so nobody can sneak printer commands into the magazine; `safe` is telling the proofreader "trust this text completely".

</En>
<Ur>

**Magazine chhapne wala ghar** socheyn.

- Base template magazine ka master layout hai: masthead, safha number, footer. Har mazmoon ka safha ise istemal karta aur sirf mazmoon ki jagah bharta hai (blocks).
- View woh editor hai jo haqaiq (data) jama kar ke hidayat (context) ke saath layout ko deta hai.
- Variables aur filters safhe par jagah rakhne wale nishan hain ("yahan NAAM bare haroof me"); tags layout ke qawaid hain ("har product ke liye ye dabba dohrao, ya khaali ho to 'koi nahi' chhapo").
- Auto-escaping woh proofreader hai jo qariyon ke khaton me bheja sab kuch bilkul waisa hi chhapta jaisa likha gaya, taa ke koi magazine me printer ki commands na ghusa sake; `safe` proofreader se kehna hai "is text par poora bharosa karo".

</Ur>

<Tr>
<En>

- Before any data existed, the `for` loop's **`empty`** branch printed "No products yet." without an extra `if`.
- The title block in `base.html` was overridden by the list page, which used the **`length`** filter: "Products (3)". Every page shares the nav link, which came from the `url` tag, so it follows URL changes automatically.

<Tr>

```bash

cat > catalog/views.py <<'EOF'
from django.db.models import Q
from django.views.generic import DetailView, ListView
from .models import Product

class ProductListView(ListView):
    model = Product
    context_object_name = "products"
    paginate_by = 2                                   # small, to show pagination

    def get_queryset(self):
        qs = super().get_queryset()
        q = self.request.GET.get("q", "").strip()
        if q:
            qs = qs.filter(Q(name__icontains=q) | Q(description__icontains=q))
        return qs

class ProductDetailView(DetailView):
    model = Product                                   # looks up by slug, 404 if missing
EOF

from django.urls import path
from . import views
app_name = "catalog"
urlpatterns = [

]

import re
from django.test import TestCase
from django.urls import reverse
from .models import Product

def items(response):
    return re.findall(r"<li>(.*?)</li>", response.content.decode())

class ProductPagesTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        for name, desc in [("Keyboard", "mechanical"), ("Mouse", "wireless"), ("Speaker", "wireless audio"),
                           ("Webcam", "1080p")]:
            Product.objects.create(name=name, slug=name.lower(), price="10.00", description=desc)

    def test_first_page_has_two_items(self):
        r = self.client.get(reverse("catalog:list"))
        self.assertEqual(items(r), ["Keyboard", "Mouse"])
        self.assertContains(r, "page 1 of 2")

    def test_second_page(self):
        self.assertEqual(items(self.client.get("/?page=2")), ["Speaker", "Webcam"])

    def test_search_in_description(self):
        self.assertEqual(items(self.client.get("/?q=WIRELESS")), ["Mouse", "Speaker"])

    def test_detail_uses_template_and_404(self):
        r = self.client.get(reverse("catalog:detail", args=["mouse"]))
        self.assertTemplateUsed(r, "catalog/product_detail.html")
        self.assertEqual(self.client.get("/p/nope/").status_code, 404)

    def test_names_are_escaped(self):
        Product.objects.create(name="<b>bold</b>", slug="bold", price="1.00")
        self.assertContains(self.client.get("/?q=bold"), "&lt;b&gt;bold&lt;/b&gt;")
EOF
```

<Tr>
<En>

- `ListView` fetched `Product.objects.all()` (with the model's ordering), used the conventional template name `catalog/product_list.html`, and with `paginate_by = 2` added `page_obj`, `paginator` and `is_paginated` to the context. - Overriding `get_queryset` added search: `?q=WIRELESS` matched descriptions case-insensitively with `icontains` and a `Q` OR, giving **Mouse, Speaker**. The "next" link carried the search term with `urlencode`, so paging doesn't lose the filter.

- The escaping test proved user-supplied HTML is rendered as `&lt;b&gt;`. Keeping such a test protects you if someone later adds `safe` in a template.

## Common mistakes

<Compare>
<Bad title="Logic and queries inside templates, disabling escaping">

```text
{% for order in user.orders.all %}             {# one query per user, plus one per item below #}
  {% for item in order.items.all %}{{ item.product.name }}{% endfor %}
{% endfor %}
{{ review.text|safe }}                          {# stored XSS #}
```

</Bad>
<Good title="Prepare data in the view, keep escaping on">

```text
orders = (Order.objects.filter(customer=request.user)
          .prefetch_related("items__product"))
return render(request, "orders/list.html", {"orders": orders})
# template: {{ review.text|linebreaksbr }}  (escapes, then adds <br>)
```

</Good>
</Compare>

<Compare>
<Bad title="Hard-coded links and catching every error as 404">

```text
<a href="/products/{{ p.id }}/">...</a>
try:
    product = Product.objects.get(slug=slug)
except Exception:
    raise Http404                     # hides real bugs (database down, typos)
```

</Bad>
<Good title="Named URLs and specific lookups">

```text
<a href="{% url 'catalog:detail' p.slug %}">...</a>
product = get_object_or_404(Product, slug=slug)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Templates in the wrong folder or without the app subfolder**: two apps' `index.html` files will clash.
- **Forgetting `csrf_token` in POST forms**: Django rejects the request with 403.
- **Unpaginated lists** of thousands of rows: always paginate.
- **Building HTML with string concatenation in views**: let templates do it, with escaping.
- **Putting secrets or internal IDs in templates** that end up in page source.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ghalat folder me ya app subfolder ke baghair templates**: do apps ki `index.html` files takraayengi.
- **POST forms me `csrf_token` bhoolna**: Django request ko 403 se radd karta hai.
- **Hazaron rows ki be-pages lists**: hamesha paginate karein.
- **Views me string jor kar HTML banana**: ye kaam escaping ke saath templates ko karne dein.
- **Templates me secrets ya andaruni IDs rakhna** jo page source me pohanch jate hain.

</Ur>

```text
settings.configure()
django.setup()

from decimal import Decimal
from django.template import Context, Engine, Library

register = Library()

@register.filter
def money(value, currency="$"):
    """Format a Decimal or number as money with thousands separators."""
    return f"{currency}{Decimal(value):,.2f}"

@register.filter
def initials(name):
    return "".join(part[0].upper() for part in name.split() if part)

engine = Engine(libraries={"shop_tags": __name__})      # this module is the tag library
t = engine.from_string("{% load shop_tags %}{{ total|money }} | {{ total|money:'EUR ' }} | {{ who|initials }}")
print(t.render(Context({"total": Decimal("1234567.5"), "who": "jane marie cooper"})))

# $1,234,567.50 | EUR 1,234,567.50 | JMC
```

<DeepDive title="More about views and templates">

**Context processors** add values to every template (the current user, site settings) through `TEMPLATES["OPTIONS"]["context_processors"]`.

**Custom tags and filters** live in `templatetags/` modules and are loaded with the `load` tag.

**Static files.** CSS, JS and images go in `static/`, are referenced with the `static` tag, and are collected for production with `collectstatic`.

**Mixins.** `LoginRequiredMixin` and `PermissionRequiredMixin` add access control to class-based views.

**Jinja2.** Django can use Jinja2 as an alternative template engine when you need more speed or features.

</DeepDive>

<DeepDive title="Real world: the review that stole sessions">

An online shop displayed customer reviews with `review.text|safe` so that line breaks would render. An attacker submitted a review containing a script that sent visitors' session cookies to an outside server. Because the session cookie wasn't HttpOnly and the template trusted the text, several admin sessions were hijacked.

The fixes:

1. Templates switched to `linebreaksbr`, which escapes first and then adds line breaks.
2. Session cookies set to HttpOnly and Secure, and a Content-Security-Policy that blocks inline scripts.
3. A test that submits HTML in a review and asserts it renders escaped, plus a search of the codebase for every `safe` and `mark_safe`.

</DeepDive>

<DeepDive title="Security lens">

- **XSS**: keep auto-escaping on; treat `safe`, `mark_safe`, `autoescape off` and `format_html` misuse as code-review red flags.
- **IDOR**: detail views must scope queries to what the user may see (`get_object_or_404(Order, pk=pk, customer=request.user)`).
- **CSRF**: every POST form needs `csrf_token`; never mark views `csrf_exempt` without a strong reason.
- **Information leaks**: don't render debug data, stack traces or internal fields in templates.
- **Open redirects**: validate `next` parameters with `url_has_allowed_host_and_scheme`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is template inheritance in Django?">
A base template defines the overall layout with named blocks; child templates extend it and override only specific blocks, so shared structure lives in one place.
</QA>

<QA q="How does Django protect templates against XSS?">
It auto-escapes variable output, converting characters like angle brackets and quotes to HTML entities, unless the value is explicitly marked safe.
</QA>

<QA q="When would you use a class-based view instead of a function-based view?">
When the view matches a common pattern such as listing, showing, creating or editing a model, so generic views and mixins remove boilerplate; function views remain clearer for unusual logic.
</QA>

<QA q="What does get_object_or_404 do?">
It runs a get query and raises Http404 if no object matches, so the user receives a proper 404 response instead of an unhandled exception.
</QA>

<QA q="How do you paginate a list in Django?">
Set paginate_by on a ListView, or use the Paginator class manually, then render page_obj and links that request ?page=N, preserving other query parameters.
</QA>

</DeepDive>
