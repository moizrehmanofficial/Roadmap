<BigIdea>
<Tr>
<En>
**Core Web Vitals** are three numbers Google uses to describe user experience, measured on **real visitors** (field data) and judged at the **75th percentile** of page visits. **LCP (Largest Contentful Paint)**: when the biggest image or text block in the viewport appears; good is **≤ 2.5 s**, poor is over 4 s. **INP (Interaction to Next Paint)**: how long the page takes to visibly respond to clicks, taps and key presses, using the slowest interactions of the visit; good is **≤ 200 ms**, poor over 500 ms. **CLS (Cumulative Layout Shift)**: how much visible content unexpectedly moves; good is **≤ 0.1**, poor over 0.25. INP replaced FID (First Input Delay) in March 2024. The fixes are mostly well known: for LCP, a fast server, no render-blocking resources, and the hero image discovered and downloaded early; for CLS, give images, ads and embeds reserved space; for INP, keep the main thread free, break up long tasks and show feedback before heavy work. Lab tools (Lighthouse, DevTools) help you debug, but field data from real users decides.
</En>
<Ur>
**Core Web Vitals** Google ke teen numbers hain jo user ke tajurbe ko bayan karte hain, **asli visitors** par napay jate hain (field data) aur page visits ke **75th percentile** par parkhe jate hain. **LCP (Largest Contentful Paint)**: viewport me sab se bari image ya text block kab nazar aata hai; achha **≤ 2.5 s**, bura 4 s se zyada. **INP (Interaction to Next Paint)**: page clicks, taps aur key presses ka nazar aane wala jawab kitni dair me deta hai, visit ki sab se sust interactions ke hisaab se; achha **≤ 200 ms**, bura 500 ms se zyada. **CLS (Cumulative Layout Shift)**: nazar aane wala content kitna achanak hilta hai; achha **≤ 0.1**, bura 0.25 se zyada. INP ne March 2024 me FID (First Input Delay) ki jagah li. Hal zyadatar maloom hain: LCP ke liye tez server, render rokne wale resources nahi, aur hero image jaldi dhoondi aur download ho; CLS ke liye images, ads aur embeds ko jagah pehle se dein; INP ke liye main thread khaali rakhein, lambe tasks torein aur bhaari kaam se pehle feedback dikhayen. Lab tools (Lighthouse, DevTools) debug me madad karte hain, magar faisla asli users ka field data karta hai.
</Ur>

## Picture it

<Tr>
<En>

Think of **ordering at a restaurant**.

- **LCP** is how long until your main dish arrives. Bread on the table early is nice, but you judge the wait by the main course.
- **INP** is how quickly the waiter reacts when you raise your hand. If they finish polishing every glass before even nodding at you, it feels like being ignored, even if the eventual service is fine.
- **CLS** is the table being moved while you're eating: your plate slides just as you reach for it, and you knock over a glass (or tap the wrong button).
- The fixes are restaurant common sense: start cooking the main dish first (preload the hero), set the table before guests arrive (reserve space), and acknowledge customers before doing long tasks (feedback, then work).

</En>
<Ur>

**Restaurant me order** socheyn.

- **LCP** ye hai ke asal khana kitni dair me aata hai. Mez par jaldi roti achhi hai, magar intezar ka faisla asal khane se hota hai.
- **INP** ye hai ke haath uthane par waiter kitni jaldi jawab deta hai. Agar woh aap ki taraf sar hilane se pehle har gilas chamkaye, to nazar andaz hone jaisa lagta hai, chahe baad ki khidmat theek ho.
- **CLS** khana khate waqt mez ka khisakna hai: aap ka plate theek usi waqt khisakta hai jab aap haath barhate hain, aur gilas gir jata hai (ya ghalat button dab jata hai).
- Hal restaurant ki aam samajh hain: asal khana pehle pakana shuru karo (hero preload), mehmanon se pehle mez lagao (jagah pehle se), aur lambe kaam se pehle customer ko jawab do (pehle feedback, phir kaam).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Measure a slow product page">

<Tr>
<En>
`server.js` serves a product page with four classic problems: a **render-blocking stylesheet** that takes 800 ms, a **lazy-loaded hero image without width and height** that takes 3.5 s, a **banner injected** above the content after 1.2 s, and a click handler that does 600 ms of work **before** showing any feedback. The page loads Google's `web-vitals` library and stores the latest LCP, CLS and INP in `window.vitals`. `measure.js` opens the page in Chrome, waits for the late content, clicks the button like a user, and prints the ratings. Delays simulate a slow server and network, so the numbers are lab numbers; the ratings are what we compare.
</En>
<Ur>
`server.js` chaar classic maslon wala product page deta hai: 800 ms lene wali **render rokne wali stylesheet**, 3.5 s lene wali **bina width aur height ki lazy-loaded hero image**, 1.2 s baad content ke upar **ghusaya gaya banner**, aur click handler jo koi feedback dikhane se **pehle** 600 ms ka kaam karta hai. Page Google ki `web-vitals` library load karta aur taaza LCP, CLS aur INP `window.vitals` me rakhta hai. `measure.js` Chrome me page kholta hai, der se aane wale content ka intezar karta hai, user ki tarah button dabata hai, aur ratings chhapta hai. Delays sust server aur network ki naqal hain, isliye numbers lab ke hain; hum ratings milate hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 web-vitals@6.2.3 --silent && npm install -D @playwright/test@1.65.1 --silent
cat > server.js <<'EOF'
// One product page in two versions: /bad and /good. Delays simulate a slow network and server.
import express from 'express';
import { deflateSync, crc32 } from 'node:zlib';
import { randomBytes } from 'node:crypto';
const app = express();
// a real photo-like PNG (800x400 of noise): browsers ignore near-empty images when picking the LCP element
function png(w, h) {
  const chunk = (type, data) => { const len = Buffer.alloc(4); len.writeUInt32BE(data.length); const td = Buffer.concat([Buffer.from(type), data]); const crc = Buffer.alloc(4); crc.writeUInt32BE(crc32(td)); return Buffer.concat([len, td, crc]); };
  const ihdr = Buffer.alloc(13); ihdr.writeUInt32BE(w, 0); ihdr.writeUInt32BE(h, 4); ihdr[8] = 8; ihdr[9] = 2;
  const rows = []; for (let y = 0; y < h; y++) rows.push(Buffer.from([0]), randomBytes(w * 3));
  return Buffer.concat([Buffer.from([137, 80, 78, 71, 13, 10, 26, 10]), chunk('IHDR', ihdr), chunk('IDAT', deflateSync(Buffer.concat(rows))), chunk('IEND', Buffer.alloc(0))]);
}
const heroPng = png(800, 400);
const wait = (ms) => new Promise((r) => setTimeout(r, ms));
app.get('/hero.png', async (req, res) => { await wait(Number(req.query.delay ?? 0)); res.type('png').send(heroPng); });
app.get('/app.css', async (req, res) => { await wait(Number(req.query.delay ?? 0)); res.type('css').send('body{font-family:sans-serif;margin:0} p{font-size:18px}'); });
app.use('/vendor', express.static('node_modules/web-vitals/dist'));
const vitals = `<script src="/vendor/web-vitals.iife.js"></script><script>
  window.vitals = {};
  for (const m of ['LCP', 'CLS', 'INP']) webVitals['on' + m]((x) => { window.vitals[m] = { value: x.value, rating: x.rating }; }, { reportAllChanges: true, durationThreshold: 0 });
</script>`;

app.get('/bad', (req, res) => res.send(`<!doctype html><html><head><meta name="viewport" content="width=device-width">
  <link rel="stylesheet" href="/app.css?delay=800">                     <!-- slow, render-blocking CSS -->
  ${vitals}</head><body>
  <div id="banner"></div>
  <img src="/hero.png?delay=3500" loading="lazy" alt="Desk lamp">         <!-- slow, lazy, no size -->
  <h1>Desk lamp</h1><p>A warm, dimmable lamp for late-night coding.</p><p>$35.00</p>
  ${'<p>Solid oak base, brass arm, three brightness levels and a USB-C port for your phone.</p>'.repeat(10)}
  <button id="buy">Add to cart</button><p id="msg"></p>
  <script>
    setTimeout(() => { document.getElementById('banner').innerHTML = '<div style="height:200px;background:#fc0">Free shipping today!</div>'; }, 1200);  // pushes content down
    document.getElementById('buy').onclick = () => {
      const end = performance.now() + 600; while (performance.now() < end) {}          // heavy work before any visual feedback
      document.getElementById('msg').textContent = 'Added!';
    };
  </script></body></html>`));

import { existsSync } from 'node:fs';
if (existsSync('good.js')) (await import('./good.js')).default(app, vitals);   // the fixed page, added in the next step
app.listen(3000);
EOF
cat > measure.js <<'EOF'
import { chromium } from '@playwright/test';
const browser = await chromium.launch({ channel: 'chrome' });
for (const path of process.argv.slice(2)) {
  const page = await browser.newPage({ viewport: { width: 800, height: 900 } });
  await page.goto(`http://localhost:3000${path}`, { waitUntil: 'load' });
  await page.waitForTimeout(4500);                                    // let late content arrive
  await page.click('#buy');                                           // a real user interaction
  await page.waitForTimeout(1500);
  await page.keyboard.press('Tab');                                   // input ends the LCP measurement
  const v = await page.evaluate(() => window.vitals);
  const fmt = (m) => `${m}: ${v[m]?.rating ?? 'n/a'}`;
  console.log(`${path.padEnd(6)} ${fmt('LCP')}  ${fmt('CLS')} (${v.CLS?.value.toFixed(2)})  ${fmt('INP')}`);
  await page.close();
}
await browser.close();
EOF
node server.js & S=$!; sleep 1
node measure.js /bad
kill $S; wait $S 2> /dev/null || true
```

```text output
/bad   LCP: poor  CLS: needs-improvement (0.19)  INP: poor
```

<Happened>
<Tr>
<En>

- **LCP poor**: the largest element is the hero image, which the browser found late (after the blocking CSS), treated as low priority (`loading="lazy"`), and received after 3.5 s. Lazy-loading the LCP image is one of the most common LCP mistakes.
- **CLS needs improvement (0.19)**: the banner pushed everything down 200 px, and the image without dimensions reserved no space before it arrived, so the text jumped again. Each unexpected shift adds a score based on how much of the viewport moved and how far.
- **INP poor**: the click handler blocked the main thread for 600 ms before updating the text, so the next paint after the click came 600+ ms later. Users experience that as "the button didn't work" and click again.
- web-vitals with `reportAllChanges` reports values as they change; in production you'd report the final values when the page is hidden, which is the library's default.

</En>
<Ur>

- **LCP poor**: sab se bara element hero image hai, jo browser ne der se dhoondi (blocking CSS ke baad), kam tarjeeh di (`loading="lazy"`), aur 3.5 s baad mili. LCP image ko lazy-load karna sab se aam LCP ghaltiyon me se hai.
- **CLS needs improvement (0.19)**: banner ne sab kuch 200 px neeche dhakel diya, aur bina size ki image ne aane se pehle koi jagah nahi rakhi, isliye text phir uchhla. Har ghair mutawaqqa shift is hisaab se score jorti hai ke viewport ka kitna hissa kitna door hila.
- **INP poor**: click handler ne text update karne se pehle 600 ms main thread roka, isliye click ke baad agla paint 600+ ms baad aaya. Users ise "button kaam nahi kar raha" samajhte aur dobara dabate hain.
- `reportAllChanges` ke saath web-vitals badalte hi qeematen batata hai; production me aap page chhupne par aakhri qeematen report karenge, jo library ka default hai.

</Ur>
</Tr>
</Happened>

<Step title="Fix each metric, measure again">

<Tr>
<En>
`good.js` adds `/good`, the same page with targeted fixes: **critical CSS inlined** (nothing render-blocking), the hero **preloaded** with `fetchpriority="high"`, not lazy, with **width and height**, and served from an optimized source (the delay drops to 600 ms, standing in for a smaller image on a CDN); a `min-height` **reserves the banner's space**; and the click handler shows **"Adding…" first, yields** with `setTimeout(0)`, then does the same 600 ms of work. Both pages are measured again.
</En>
<Ur>
`good.js` `/good` jorta hai, wahi page nishana bande fixes ke saath: **critical CSS inline** (kuch render nahi rokta), hero `fetchpriority="high"` ke saath **preload**, lazy nahi, **width aur height** ke saath, aur behtar zariye se serve (delay 600 ms ho jata hai, CDN par chhoti image ki jagah); `min-height` **banner ki jagah pehle se rakhta** hai; aur click handler pehle **"Adding…" dikhata, yield karta** hai `setTimeout(0)` se, phir wahi 600 ms ka kaam karta hai. Dono pages dobara napay jate hain.
</Ur>
</Tr>

```bash
cat > good.js <<'EOF'
export default (app, vitals) => app.get('/good', (req, res) => res.send(`<!doctype html><html><head><meta name="viewport" content="width=device-width">
  <style>body{font-family:sans-serif;margin:0} p{font-size:18px}</style>     <!-- critical CSS inline: nothing blocks rendering -->
  <link rel="preload" as="image" href="/hero.png?delay=600" fetchpriority="high">   <!-- start the hero download immediately -->
  ${vitals}</head><body>
  <div id="banner" style="min-height:200px"></div>                         <!-- space reserved for the late banner -->
  <img src="/hero.png?delay=600" width="800" height="400" fetchpriority="high" alt="Desk lamp">   <!-- sized, eager, optimized/CDN -->
  <h1>Desk lamp</h1><p>A warm, dimmable lamp for late-night coding.</p><p>$35.00</p>
  ${'<p>Solid oak base, brass arm, three brightness levels and a USB-C port for your phone.</p>'.repeat(10)}
  <button id="buy">Add to cart</button><p id="msg"></p>
  <script>
    setTimeout(() => { document.getElementById('banner').innerHTML = '<div style="height:200px;background:#fc0">Free shipping today!</div>'; }, 1200);
    document.getElementById('buy').onclick = async () => {
      document.getElementById('msg').textContent = 'Adding…';               // visual feedback first
      await new Promise((r) => setTimeout(r, 0));                             // yield so the browser can paint
      const end = performance.now() + 600; while (performance.now() < end) {} // the same heavy work, after the paint
      document.getElementById('msg').textContent = 'Added!';
    };
  </script></body></html>`));
EOF
```

<Happened>
<Tr>
<En>

- **LCP good**: with no blocking CSS and the image requested immediately at high priority, the hero rendered in well under 2.5 s. Most real LCP wins come from exactly these: discover the LCP resource early, prioritize it, make it small (AVIF/WebP, right size, CDN), and keep TTFB low.
- **CLS 0.00**: the image's `width`/`height` let the browser reserve the right box before it loaded, and the banner filled space that was already there. Nothing visible moved.
- **INP good**: the handler still does 600 ms of work, but the browser **painted "Adding…" first**. INP measures until the next paint, so the user sees an immediate response. Better still, move heavy work off the main thread (Web Workers), split it into chunks with `scheduler.yield()`, or do it on the server.
- The `/bad` page measured the same as before, so the improvements come from the changes, not from luck. Always measure before and after, and confirm with field data once deployed.

</En>
<Ur>

- **LCP good**: blocking CSS na hone aur image ke foran ooncha tarjeeh se maange jane par hero 2.5 s se kaafi pehle render hua. Zyadatar asli LCP faide bilkul inhi se aate hain: LCP resource jaldi dhoondein, tarjeeh dein, chhota karein (AVIF/WebP, sahi size, CDN), aur TTFB kam rakhein.
- **CLS 0.00**: image ke `width`/`height` ne browser ko load se pehle sahi dabba rakhne diya, aur banner ne pehle se mojood jagah bhari. Kuch nazar aane wala nahi hila.
- **INP good**: handler ab bhi 600 ms kaam karta hai, magar browser ne **pehle "Adding…" paint kiya**. INP agle paint tak napta hai, isliye user ko fori jawab dikhta hai. Is se bhi behtar, bhaari kaam main thread se hatayen (Web Workers), `scheduler.yield()` se tukron me torein, ya server par karein.
- `/bad` page pehle jaisa napa gaya, isliye behtari tabdeeliyon se aayi, qismat se nahi. Hamesha pehle aur baad me napein, aur deploy ke baad field data se tasdeeq karein.

## Common mistakes

<Compare>
<Bad title="Lazy-loading the hero image">

```text
<img src="/hero.jpg" loading="lazy">                 <!-- delays the LCP image, no size reserved -->
<div style="background-image:url(/hero.jpg)"></div>  <!-- discovered only after CSS loads -->
```

</Bad>
<Good title="Eager, prioritized, sized">

```text
<img src="/hero.avif" width="1200" height="600" fetchpriority="high" alt="…">
<img src="/footer-badge.png" width="120" height="40" loading="lazy" alt="…">   <!-- lazy only below the fold -->
```

</Good>
</Compare>

<Compare>
<Bad title="Heavy work before feedback">

```text
button.onclick = () => {
  recalculateEverything();          // 400 ms of JavaScript
  render(bigList);                  // another 200 ms
  status.textContent = 'Saved';     // user sees this after 600 ms
};
```

</Bad>
<Good title="Feedback first, then yield and chunk">

```text
button.onclick = async () => {
  status.textContent = 'Saving…';
  await scheduler.yield?.() ?? new Promise((r) => setTimeout(r, 0));   // let the browser paint
  for (const chunk of chunks(items, 200)) { process(chunk); await scheduler.yield?.(); }
  status.textContent = 'Saved';
};
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Optimizing Lighthouse scores only**: lab tests use one device and network; your users' field data can differ a lot.
- **Testing on a fast laptop**: most users have slower phones; test with CPU and network throttling.
- **Injecting content above existing content** (cookie banners, promos) without reserved space; use overlays or reserved slots.
- **Web fonts causing shifts**: use `font-display: optional` or `swap` with matched fallback metrics (`size-adjust`).
- **Too much third-party JavaScript** (tag managers, chat widgets) on the main thread.
- **Client-rendering the main content** of content pages; server rendering or static generation usually helps LCP.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sirf Lighthouse scores behtar karna**: lab tests ek device aur network istemal karte hain; aap ke users ka field data bohot mukhtalif ho sakta hai.
- **Tez laptop par test karna**: zyadatar users ke phones sust hain; CPU aur network throttling ke saath test karein.
- **Mojooda content ke upar content ghusana** (cookie banners, promos) bina jagah ke; overlays ya pehle se rakhi jagahen lein.
- **Web fonts se shifts**: `font-display: optional` ya mel khati fallback metrics (`size-adjust`) ke saath `swap` lein.
- **Main thread par bohot zyada teesre fareeq ka JavaScript** (tag managers, chat widgets).
- **Content pages ka asal content client par render karna**; server rendering ya static generation aam taur par LCP me madad karte hain.

</Ur>
</Tr>

<DeepDive title="More about Core Web Vitals">

**LCP sub-parts.** LCP = TTFB + resource load delay + resource load duration + element render delay. web-vitals' attribution build reports each part, so you know whether to fix the server, discovery, download size or rendering.

**INP phases.** Input delay (main thread busy when the user clicks), processing time (your handlers), and presentation delay (rendering the next frame). Long tasks from other scripts cause input delay even if your handler is fast.

**CLS windows.** CLS uses the largest burst ("session window") of shifts, not the sum over the whole visit; shifts within 500 ms after user input don't count.

**Frameworks.** Next.js `next/image` sets sizes and priority, `next/font` reduces font shifts; React 18+ transitions (`startTransition`) keep inputs responsive during heavy renders.

**Other useful metrics.** TTFB, FCP and TBT (lab) aren't Core Web Vitals but explain them.

**bfcache.** Making pages eligible for the back/forward cache gives instant back navigations and great LCP for those visits; avoid `unload` handlers and `Cache-Control: no-store` where not needed.

</DeepDive>

<DeepDive title="Real world: the cookie banner that cost conversions">

An online store added a consent banner that loaded from a third-party script and was inserted at the top of the page, pushing the product grid down about 150 px roughly a second after load. Their CLS at the 75th percentile went from 0.04 to 0.31 on mobile, and analytics showed more mis-taps on "Add to wishlist" (which moved into the spot where "Add to cart" had been). Mobile conversion dropped noticeably over the following weeks.

The fixes:

1. The banner became a fixed overlay at the bottom of the screen, which doesn't shift content.
2. The consent script loads with `async`, and its placeholder space is reserved where needed.
3. Field data from the web-vitals library, split by page type and release, now gates releases: a regression above the threshold blocks the next deploy.
4. A Playwright test measures CLS on the top five templates in CI.

</DeepDive>

<DeepDive title="Security lens">

- **Third-party scripts affect both performance and security**: each one runs with full page access; audit and limit them.
- **RUM endpoints are public**: validate and rate-limit incoming beacon data, and don't trust it for anything security-relevant.
- **Don't send personal data** in performance beacons (full URLs with tokens, user ids) without need and consent.
- **Self-hosting critical assets** (fonts, scripts) improves speed and reduces reliance on outside domains, but keep them updated.
- **Subresource Integrity** on any third-party script that stays.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the Core Web Vitals?">
Largest Contentful Paint for loading, good at 2.5 seconds or less; Interaction to Next Paint for responsiveness, good at 200 milliseconds or less; and Cumulative Layout Shift for visual stability, good at 0.1 or less, each assessed at the 75th percentile of real user visits.
</QA>

<QA q="How would you improve a poor LCP?">
Find the LCP element and its timing breakdown, reduce server response time with caching or edge rendering, remove render-blocking resources, make the LCP resource discoverable in the HTML, preload and prioritize it, never lazy-load it, and compress and size images correctly, serving them from a CDN.
</QA>

<QA q="What causes poor INP and how do you fix it?">
Long main-thread tasks during or before interactions: heavy handlers, large renders, third-party scripts. Fix by giving visual feedback first, yielding to the browser, splitting work, debouncing, moving work to Web Workers or the server, and reducing JavaScript.
</QA>

<QA q="How do you prevent layout shifts?">
Set width and height or aspect-ratio on images and video, reserve space for ads, embeds and late-loading components, avoid inserting content above existing content, and manage web font loading with fallback metric overrides.
</QA>

<QA q="What's the difference between lab and field data?">
Lab data comes from controlled tests like Lighthouse on one device and network, good for debugging and regression checks. Field data comes from real users on varied devices and networks and is what Core Web Vitals assessments use.
</QA>

</DeepDive>
