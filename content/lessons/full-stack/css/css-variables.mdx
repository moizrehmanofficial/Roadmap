<Callout type="tip" title="In one minute">
**CSS variables** (officially **custom properties**) store values you reuse: declare one with a double-dash name, `--brand: #f59e0b;`, and use it with **`var(--brand)`**. Unlike Sass variables, they are **live in the browser**: they follow the **cascade** and **inheritance**, so you can declare them on `:root` for the whole page and **override** them in any element, class or media query, and everything using them updates instantly. That makes **theming** (dark mode = swap a few variables), **design tokens** (spacing and colour scales) and **component customisation** (`.btn { --btn-bg: …; }`) simple. `var(--x, fallback)` provides a fallback; JavaScript can read and change variables with `getPropertyValue` and `setProperty`; **`@property`** registers a typed variable that can be animated.
</Callout>

## Start from zero

<Callout type="analogy">
Imagine your house's colours are written on a **paint card stuck on the fridge**: "Main colour: mango yellow". Every room's painter looks at the card instead of remembering the colour. To repaint the whole house, you change one card. That's a variable on `:root`. Now a **child's room** has its own card on its door: "Main colour: sky blue". Painters in that room read the closest card first. That's overriding a variable on a specific element: it applies to that element and everything inside it, while the rest of the house keeps the fridge card.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Custom property** | The official name for a CSS variable | `--brand` |
| **var()** | Function that reads a custom property | `color: var(--brand)` |
| **:root** | The top element (`<html>`), used for global variables | `:root { --gap: 1rem; }` |
| **Fallback** | Value used when the variable isn't defined | `var(--x, red)` |
| **Scope** | Where a variable is visible: the element and its descendants | |
| **Design token** | A named design decision stored as a variable | `--space-4: 1rem` |
| **Theme** | A set of token values | light, dark |
| **@property** | Rule that gives a variable a type and initial value | `syntax: '<color>'` |

## What is it?

```css
:root {
  --brand: #f59e0b;        /* declare (global) */
  --radius: 0.5rem;
  --space: 1rem;
}

.button {
  background: var(--brand);               /* use */
  border-radius: var(--radius);
  padding: calc(var(--space) / 2) var(--space);
}

.sale {
  --brand: #dc2626;        /* override for .sale and everything inside it */
}
```

Any button inside `.sale` turns red; all others stay orange, with no new button rules.

## Why does it matter?

- **One source of truth:** brand colours, spacing and fonts are defined once. Changing the brand colour is a one-line change.
- **Theming:** dark mode, high-contrast mode, per-customer themes in white-label products, all by swapping variables.
- **Runtime changes:** unlike Sass/Less variables (replaced at build time), CSS variables can change in the browser: per element, per media query, on hover, or from JavaScript.
- **Design systems:** Tailwind v4, shadcn/ui, Material Design 3, Bootstrap 5 and Radix all expose their design tokens as CSS variables.

## When and where do you use it?

- Global tokens on `:root`: colours, spacing scale, font sizes, radii, shadows, z-indexes, durations.
- Themes: override tokens under `[data-theme="dark"]` or `@media (prefers-color-scheme: dark)`.
- Components: local variables as a "styling API" (`--card-padding`).
- Values set from JavaScript or inline styles: progress percentages, positions, user-chosen colours.

## Concepts one by one

### 1. Declaring and using variables

<Explain>
<What>
- Declare: a property whose name starts with **two dashes**, inside any rule: `--main-color: #1f2937;`. Names are **case-sensitive** (`--Brand` ≠ `--brand`).
- Use: `var(--main-color)` anywhere a value (or part of one) is allowed: `border: 1px solid var(--main-color)`.
- Values can be anything: colours, lengths, numbers, strings, whole lists (`--shadow: 0 1px 2px rgb(0 0 0 / 0.1), 0 4px 8px rgb(0 0 0 / 0.1);`).
</What>
<Why>
Reuse and consistency, plus the ability to change values at runtime.
</Why>
<When>
Whenever a value is used in more than one place or might need to change by context.
</When>
<Where>
`var()` can't be used in property **names**, selectors or media query conditions (`@media (min-width: var(--bp))` doesn't work).
</Where>
<How>
Reading computed values in a real browser:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
:root { --brand: #f59e0b; --space: 1rem; --radius: 8px; --shadow: 0 1px 2px rgb(0 0 0 / 0.2); }
.btn { background: var(--brand); padding: calc(var(--space) / 2) var(--space);
       border-radius: var(--radius); box-shadow: var(--shadow); }
</style><button class="btn" type="button">Buy</button>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    print("raw --brand on :root:", repr(page.evaluate("getComputedStyle(document.documentElement).getPropertyValue('--brand')")))
    s = page.eval_on_selector(".btn", "e => { const c = getComputedStyle(e); return [c.backgroundColor, c.padding, c.borderRadius, c.boxShadow] }")
    for name, value in zip(["background", "padding", "border-radius", "box-shadow"], s):
        print(f"{name:14} {value}")
    browser.close()
PY
```

```text output
raw --brand on :root: '#f59e0b'
background     rgb(245, 158, 11)
padding        8px 16px
border-radius  8px
box-shadow     rgba(0, 0, 0, 0.2) 0px 1px 2px 0px
```

Line by line:

- Reading `--brand` itself returns the **text** you wrote (`#f59e0b`): the browser doesn't interpret an ordinary custom property's value until it's used.
- Where it's used in `background`, it becomes a real colour, `rgb(245, 158, 11)`.
- `calc(var(--space) / 2) var(--space)` became `8px 16px`.
- A whole multi-part value (the shadow) can be stored in one variable.

### 2. Scope, inheritance and the cascade

<Explain>
<What>
Custom properties are ordinary properties as far as the cascade is concerned:
- A declaration applies to the elements its selector matches.
- They are **inherited**: descendants see the value unless they override it.
- Specificity, source order and media queries decide which declaration wins, as with any property.
</What>
<Why>
This is what makes them powerful: override a variable on a container, and every descendant that uses it changes.
</Why>
<When>
Global values on `:root`; overrides on sections (`.sidebar { --text: … }`), states (`.btn:hover { --btn-bg: … }`), or media queries (`@media (min-width: 768px) { :root { --space: 1.5rem } }`).
</When>
<Where>
Changing a variable on `:root` makes the browser recompute styles for the whole page; that's fine for themes, but for values that change many times per second (mouse position), set them on the smallest element that needs them.
</Where>
<How>
One rule for all buttons, three different results from scope and media queries:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
:root { --brand: rgb(245, 158, 11); --space: 8px; }
@media (min-width: 1000px) { :root { --space: 16px; } }
.sale { --brand: rgb(220, 38, 38); }
.btn { background: var(--brand); padding: var(--space); }
.btn:hover { --brand: rgb(30, 64, 175); }
</style>
<button class="btn" id="normal" type="button">Normal</button>
<section class="sale"><button class="btn" id="sale" type="button">Sale</button></section>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    for width in [600, 1200]:
        page = browser.new_page(viewport={"width": width, "height": 400})
        page.set_content(html)
        info = [page.eval_on_selector(el, "e => getComputedStyle(e).backgroundColor + ' pad ' + getComputedStyle(e).paddingTop") for el in ["#normal", "#sale"]]
        print(f"screen {width}px: normal = {info[0]} | sale = {info[1]}")
        if width == 600:
            page.hover("#normal")
            print("             hovered normal =", page.eval_on_selector("#normal", "e => getComputedStyle(e).backgroundColor"))
        page.close()
    browser.close()
PY
```

```text output
screen 600px: normal = rgb(245, 158, 11) pad 8px | sale = rgb(220, 38, 38) pad 8px
             hovered normal = rgb(30, 64, 175)
screen 1200px: normal = rgb(245, 158, 11) pad 16px | sale = rgb(220, 38, 38) pad 16px
```

Line by line:

- Both buttons use the same `.btn` rule.
- The one inside `.sale` inherits the overridden `--brand` and turns red.
- Hovering changes the variable **on the button itself** (`.btn:hover` sets `--brand`), so the background becomes blue: state changes can be written as "change a variable".
- On a wide screen, the media query changes `--space` on `:root`, so every button's padding grows to 16px.

### 3. Fallbacks and invalid values

<Explain>
<What>
- `var(--name, fallback)` uses the fallback when `--name` is **not defined** (or is the special "guaranteed-invalid" value). The fallback can contain commas and even another `var()`: `var(--btn-bg, var(--brand, orange))`.
- If a variable **is** defined but its value is invalid for the property where it's used (e.g. `--size: red; width: var(--size)`), the declaration becomes **"invalid at computed-value time"**: the property falls back to its **inherited** value (if it's an inherited property) or its **initial** value, not to an earlier declaration in your CSS.
</What>
<Why>
Fallbacks let components work even if a theme forgets a token. The invalid-value behaviour explains some confusing bugs.
</Why>
<When>
Use fallbacks in reusable components; keep the token names consistent so you rarely need them.
</When>
<Where>
Because the browser can't check a variable's value when parsing, the usual CSS "if a declaration is invalid, the previous one applies" rule doesn't help. `@property` (concept 8) can give a variable a type and a safe initial value.
</Where>
<How>
Undefined, defined, and invalid variables:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
:root { --brand: rgb(245, 158, 11); --bad: 20px; }
body { color: rgb(17, 24, 39); }
#a { color: var(--missing, rgb(22, 163, 74)); }
#b { color: var(--missing, var(--brand)); }
#c { color: var(--missing); }
#d { color: blue; color: var(--bad); }
#e { background-color: red; background-color: var(--bad); }
</style>
<p id="a">a</p><p id="b">b</p><p id="c">c</p><p id="d">d</p><p id="e">e</p>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el, desc in [("#a", "missing + fallback"), ("#b", "missing + var fallback"), ("#c", "missing, no fallback"),
                     ("#d", "invalid value (color)"), ("#e", "invalid value (background)")]:
        prop = "backgroundColor" if el == "#e" else "color"
        print(f"{desc:28} -> {page.eval_on_selector(el, f'e => getComputedStyle(e).{prop}')}")
    browser.close()
PY
```

```text output
missing + fallback           -> rgb(22, 163, 74)
missing + var fallback       -> rgb(245, 158, 11)
missing, no fallback         -> rgb(17, 24, 39)
invalid value (color)        -> rgb(17, 24, 39)
invalid value (background)   -> rgba(0, 0, 0, 0)
```

Line by line:

- `#a`: `--missing` isn't defined, so the green fallback is used.
- `#b`: the fallback is itself a variable, which resolves to the brand orange.
- `#c`: no fallback, so the declaration is invalid at computed-value time; `color` is inherited, so it takes the body's dark colour.
- `#d`: `--bad` is `20px`, not a colour. The earlier `color: blue` does **not** come back: `color` falls back to the inherited body colour.
- `#e`: `background-color` isn't inherited, so it falls back to its initial value, `transparent` (`rgba(0, 0, 0, 0)`), not the earlier red.

### 4. Design tokens

<Explain>
<What>
**Design tokens** are named design decisions: colours, spacing, font sizes, radii, shadows, durations. Good token systems have two layers:
- **Primitive tokens:** the raw palette and scales: `--orange-500: #f59e0b; --space-4: 1rem;`.
- **Semantic tokens:** what a value is **for**: `--color-primary: var(--orange-500); --color-text-muted: var(--gray-600); --space-card: var(--space-4);`.
Components use **semantic** tokens.
</What>
<Why>
Changing a theme means re-pointing semantic tokens, without touching components. Names describe purpose, so developers don't need to remember hex codes.
</Why>
<When>
Any project with more than a handful of components. Designers' tools (Figma variables) can export tokens to CSS.
</When>
<Where>
Keep scales small and consistent (a spacing scale like 4, 8, 12, 16, 24, 32, 48, 64px), and avoid one-off values.
</Where>
<How>
A small token file:
</How>
</Explain>

```css
:root {
  /* Primitive tokens */
  --gray-50: #f9fafb;  --gray-200: #e5e7eb;  --gray-600: #4b5563;  --gray-900: #111827;
  --orange-500: #f59e0b;  --orange-700: #b45309;  --red-600: #dc2626;
  --space-1: 0.25rem;  --space-2: 0.5rem;  --space-3: 0.75rem;  --space-4: 1rem;  --space-6: 1.5rem;  --space-8: 2rem;
  --text-sm: 0.875rem;  --text-base: 1rem;  --text-lg: 1.125rem;  --text-2xl: 1.5rem;
  --radius-sm: 0.25rem;  --radius-md: 0.5rem;  --radius-full: 9999px;
  --duration-fast: 150ms;  --duration-normal: 250ms;

  /* Semantic tokens: what components use */
  --color-bg: #ffffff;
  --color-surface: var(--gray-50);
  --color-border: var(--gray-200);
  --color-text: var(--gray-900);
  --color-text-muted: var(--gray-600);
  --color-primary: var(--orange-500);
  --color-primary-text: var(--gray-900);
  --color-danger: var(--red-600);
}
```

### 5. Theming and dark mode

<Explain>
<What>
A theme is just a different set of semantic token values. Two common ways to switch:
- **Automatic:** `@media (prefers-color-scheme: dark) { :root { … } }`.
- **User choice:** a `data-theme` attribute on `<html>`, set by a toggle and saved in `localStorage`: `[data-theme="dark"] { … }`.
Often both: follow the system by default, and let users override.
</What>
<Why>
Components don't change at all; only token values do.
</Why>
<When>
Dark mode, high contrast, seasonal themes, white-label products (each customer's brand colours).
</When>
<Where>
Also set `color-scheme: light` / `dark` so browser-drawn controls (inputs, scrollbars) match. To avoid a flash of the wrong theme on page load, set the `data-theme` attribute in a tiny inline script in the `<head>` before the page renders.
</Where>
<How>
Toggle the theme in the result below.
</How>
</Explain>

```html preview-js h=260 noqa
<style>
  :root { --bg: #ffffff; --surface: #f9fafb; --text: #111827; --muted: #4b5563; --border: #e5e7eb; --primary: #f59e0b; color-scheme: light; }
  [data-theme="dark"] { --bg: #0f172a; --surface: #1e293b; --text: #f1f5f9; --muted: #cbd5e1; --border: #334155; --primary: #fbbf24; color-scheme: dark; }
  body { margin: 0; padding: 16px; background: var(--bg); color: var(--text); font-family: system-ui, sans-serif; transition: background-color 0.2s, color 0.2s; }
  .card { padding: 16px; border: 1px solid var(--border); border-radius: 12px; background: var(--surface); max-width: 320px; }
  .card p { color: var(--muted); }
  .btn { padding: 8px 14px; border: 0; border-radius: 8px; background: var(--primary); color: #111827; font: inherit; }
</style>
<button type="button" id="toggle">Toggle theme</button>
<div class="card" style="margin-top: 12px">
  <h2>Kent mangoes</h2>
  <p>Every colour on this card comes from a variable.</p>
  <button class="btn" type="button">Add to cart</button>
  <p><label>Note <input placeholder="form controls follow color-scheme"></label></p>
</div>
<script>
  document.getElementById("toggle").addEventListener("click", () => {
    const root = document.documentElement;
    root.dataset.theme = root.dataset.theme === "dark" ? "light" : "dark";
  });
</script>
```

Line by line:

- Light values are on `:root`; dark values override the same names under `[data-theme="dark"]`.
- Every component rule uses only variables, so the whole page switches when the attribute changes.
- `color-scheme` makes the input field switch to a dark style too.
- The script toggles `data-theme` on `<html>`; a real site would also save the choice in `localStorage`.

### 6. Component APIs with variables

<Explain>
<What>
A component can declare **local** variables with defaults and use them internally. Users of the component customise it by setting those variables, without knowing its internal selectors:
```css
.btn {
  --btn-bg: var(--color-primary);
  --btn-fg: var(--color-primary-text);
  --btn-pad-y: 0.5em;
  --btn-pad-x: 1em;
  background: var(--btn-bg);
  color: var(--btn-fg);
  padding: var(--btn-pad-y) var(--btn-pad-x);
}
.btn.danger { --btn-bg: var(--color-danger); --btn-fg: white; }
.btn.compact { --btn-pad-y: 0.25em; --btn-pad-x: 0.5em; }
```
</What>
<Why>
Variants are short, specificity stays low, and overrides from outside (`.toolbar .btn { --btn-pad-x: 0.75em }`) don't need to repeat property declarations.
</Why>
<When>
Buttons, cards, inputs, badges, layouts (`.stack { --stack-gap: 1rem; display: grid; gap: var(--stack-gap); }`).
</When>
<Where>
Prefix local variables with the component name (`--btn-*`) to avoid collisions, since variables inherit into every descendant.
</Where>
<How>
Inline styles can set variables too: `<div class="progress" style="--value: 72%">` with `.progress::after { width: var(--value); }`. This is a clean way to pass data from HTML or JavaScript into CSS.
</How>
</Explain>

```html preview h=150 noqa
<style>
  body { font-family: system-ui, sans-serif; }
  .progress { height: 12px; border-radius: 999px; background: #e5e7eb; overflow: hidden; margin: 8px 0; max-width: 300px; }
  .progress::after { content: ""; display: block; height: 100%; width: var(--value, 0%); background: var(--bar, #f59e0b); }
</style>
<p>Order packed</p><div class="progress" style="--value: 100%; --bar: #16a34a"></div>
<p>Out for delivery</p><div class="progress" style="--value: 60%"></div>
<p>Payment</p><div class="progress" style="--value: 25%; --bar: #dc2626"></div>
```

Line by line:

- One CSS rule draws all three bars; each element passes its own `--value` (and optionally `--bar`) through the `style` attribute.
- The pseudo-element reads them with fallbacks (0% and orange).

### 7. Variables and JavaScript

<Explain>
<What>
- Read: `getComputedStyle(element).getPropertyValue("--brand")` (returns the text, possibly with surrounding spaces, so `.trim()` it).
- Write: `element.style.setProperty("--brand", "#16a34a")`.
- Remove an inline override: `element.style.removeProperty("--brand")`.
</What>
<Why>
JavaScript changes a variable once and CSS handles every place it's used: user-chosen theme colours, cursor-following effects, values from sliders, scroll progress.
</Why>
<When>
Interactive effects and settings. Prefer toggling classes or data attributes for discrete states (themes), and variables for continuous values (positions, percentages).
</When>
<Where>
`element.style.--brand = …` does **not** work; use `setProperty`.
</Where>
<How>
Reading and updating from a script:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
:root { --brand: #f59e0b; --progress: 0%; }
.bar { width: var(--progress); height: 10px; background: var(--brand); }
</style><div class="track" style="width: 400px"><div class="bar" id="bar"></div></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    print("read --brand:", page.evaluate("getComputedStyle(document.documentElement).getPropertyValue('--brand').trim()"))
    for value in ["25%", "80%"]:
        page.evaluate(f"document.documentElement.style.setProperty('--progress', '{value}')")
        print(f"set --progress {value}: bar width =", page.eval_on_selector("#bar", "e => e.offsetWidth"), "px")
    page.evaluate("document.documentElement.style.setProperty('--brand', 'rgb(22, 163, 74)')")
    print("after setProperty --brand: bar colour =", page.eval_on_selector("#bar", "e => getComputedStyle(e).backgroundColor"))
    browser.close()
PY
```

```text output
read --brand: #f59e0b
set --progress 25%: bar width = 100 px
set --progress 80%: bar width = 320 px
after setProperty --brand: bar colour = rgb(22, 163, 74)
```

Line by line:

- `getPropertyValue('--brand')` returns the declared text.
- Setting `--progress` on the root changes the bar's width: 25% of its 400px track = 100px, then 320px. No other style was touched.
- Changing `--brand` recolours everything that uses it.

### 8. @property: typed and animatable variables

<Explain>
<What>
`@property` registers a custom property with a **type** (`syntax`), whether it **inherits**, and an **initial value**:
```css
@property --angle {
  syntax: "<angle>";
  inherits: false;
  initial-value: 0deg;
}
```
Types include `<length>`, `<percentage>`, `<color>`, `<number>`, `<integer>`, `<angle>`, `<time>` and combinations.
</What>
<Why>
- Normal custom properties are just text, so the browser can't **animate** them smoothly (it can only flip from one value to the other). A typed property can be transitioned and animated, for example the angle of a gradient or a number in a counter.
- Invalid values fall back to the declared initial value, which is safer.
- `inherits: false` stops a variable from leaking into descendants, which also helps performance.
</Why>
<When>
Animated gradients, progress rings, counters, any transition of a variable.
</When>
<Where>
Supported in all modern browsers since 2024. It can also be registered from JavaScript with `CSS.registerProperty()`.
</Where>
<How>
Sampling an animation of a registered vs an unregistered property halfway through:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
@property --typed { syntax: "<number>"; inherits: false; initial-value: 0; }
.box { --plain: 0; --typed: 0; animation: grow 10s linear paused; animation-delay: -5s; }
@keyframes grow { to { --plain: 100; --typed: 100; } }
</style><div class="box" id="b"></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    plain, typed = page.eval_on_selector("#b", "e => { const s = getComputedStyle(e); return [s.getPropertyValue('--plain').trim(), s.getPropertyValue('--typed').trim()] }")
    print(f"halfway through the animation: --plain = {plain}, --typed = {typed}")
    browser.close()
PY
```

```text output
halfway through the animation: --plain = 100, --typed = 50
```

Line by line:

- The animation lasts 10s, is paused, and starts 5s in (negative delay), so we read values exactly at the halfway point.
- The unregistered `--plain` is just text, so it can't be interpolated: it has already flipped to the end value, 100.
- The registered `--typed` is a number, so the browser interpolates it: exactly 50 halfway. That's what makes smooth animations of variables possible.

### 9. Sass variables vs CSS variables

<Explain>
<What>
| | Sass/Less `$var` | CSS `--var` |
| --- | --- | --- |
| Exists in | Build step only | The browser, at runtime |
| Follows cascade/inheritance | No | Yes |
| Can change by element, media query, hover | No (only by recompiling) | Yes |
| Changeable from JavaScript | No | Yes |
| Usable in media query conditions and selectors | Yes | No |
| Works without a build tool | No | Yes |
</What>
<Why>
Sass variables are still useful for build-time things (breakpoints in media queries, loops); CSS variables are better for anything themeable or dynamic.
</Why>
<When>
Many projects use Sass variables (or JavaScript constants) for breakpoints and CSS variables for everything else.
</When>
<Where>
In Tailwind v4, the theme is defined with CSS variables (`@theme { --color-brand: … }`), and utility classes read them.
</Where>
<How>
Prefer CSS variables unless you need one of the two features they lack.
</How>
</Explain>

### 10. Debugging variables

<Explain>
<What>
In DevTools, the Styles panel shows where each variable is declared; hovering a `var(--x)` shows its current value, and the Computed tab lists all custom properties for the selected element. Firefox and Chrome show a warning when a variable is undefined.
</What>
<Why>
Most variable bugs are typos (`--colour-primary` vs `--color-primary`), case differences, a missing declaration in one theme, or a value that's invalid where it's used.
</Why>
<When>
Whenever a style "disappears": an invalid or undefined variable makes the property silently fall back to inherited or initial values.
</When>
<Where>
Lint tools (Stylelint with plugins) and design-token pipelines can check that every `var()` refers to a defined token.
</Where>
<How>
Keep all tokens in one file, and give theme overrides exactly the same names.
</How>
</Explain>

A themeable button and card system with primitive and semantic tokens, component variables and a system/dark theme.

## Real-world example

Before custom properties shipped in browsers (2016–2017), teams theming large products had to compile a separate stylesheet per theme with Sass, or swap whole CSS files with JavaScript. GitHub, for example, offers many colour themes (light, dark, dimmed, high-contrast and colour-blind variants); its Primer design system defines them as CSS variables like `--fgColor-default` and `--bgColor-muted`, so switching theme just changes which set of values is active, with no page reload. Similarly, shadcn/ui components only reference variables such as `--primary` and `--radius`, which is why teams can restyle the whole library by editing a dozen token values.

## Common mistakes

- **Forgetting the double dash** (`-brand`) or `var()` (`color: --brand`).
- **Typos and case differences** in names, silently producing invalid values.
- **Expecting the previous declaration to apply** when a variable's value is invalid.
- **Using `var()` in media query conditions or selectors,** which isn't supported.
- **Only primitive tokens** (`--orange-500` in components), making theming hard; add semantic tokens.
- **Generic local names** (`--bg`) that leak into nested components; prefix them (`--card-bg`).
- **`element.style.--x = ...`** instead of `setProperty`.
- **Expecting unregistered variables to animate smoothly;** use `@property`.
- **Changing `:root` variables on every mouse move,** causing whole-page style recalculation.

## Security lens

<Callout type="security">
CSS variables are often fed from user settings or URLs. Treat their values as untrusted input.
</Callout>

- **User-chosen values:** if users can pick a theme colour or upload "custom CSS" that sets variables, validate the values server-side (e.g. a strict hex colour pattern). A value like `url(https://attacker.example/track)` placed into a variable used by `background` makes visitors' browsers send requests to the attacker.
- **Inline style injection:** building `style="--name: <user input>"` without escaping can break out of the attribute and inject HTML. Use framework bindings (`style={{ "--x": value }}` in React) or proper escaping, and a Content Security Policy that restricts `style-src` and image/font sources.
- **Contrast and readability:** themes built from user-chosen colours can produce unreadable text; compute contrast (see the Accessibility lesson) and reject or adjust colours below 4.5:1, especially for security warnings.
- **Don't store secrets in CSS:** values in variables are visible to anyone through DevTools.

## Interview questions

<QA q="What are CSS custom properties and how do they differ from Sass variables?">
Custom properties are properties whose names begin with two dashes and whose values are read with the var function. They live in the browser at runtime, follow the cascade and inheritance, can differ per element or media query, and can be read and changed from JavaScript. Sass variables are replaced at build time, so they cannot change at runtime, but they can be used in places custom properties cannot, such as media query conditions and selectors.
</QA>

<QA q="How do you implement dark mode with CSS variables?">
Define semantic colour tokens on the root, such as background, surface, text and border, and use only those in components. Override the same token names under a prefers-color-scheme dark media query, a data-theme attribute set by a user toggle, or both, and set the color-scheme property so browser controls match. Components then change theme without any changes to their rules.
</QA>

<QA q="What happens if a CSS variable holds a value that is invalid for the property using it?">
The declaration becomes invalid at computed-value time. Instead of falling back to an earlier declaration in the cascade, the property behaves as if it were set to unset: inherited properties take the parent's value and others take their initial value. Registering the property with the property at-rule gives it a type and initial value to fall back to.
</QA>

<QA q="How do you read and change a CSS variable from JavaScript?">
Read it with getComputedStyle on the element followed by getPropertyValue with the variable name, trimming whitespace, and change it with the element's style setProperty method, or remove an inline value with removeProperty. Everything using the variable updates automatically.
</QA>

<QA q="Why would you use the @property rule?">
It registers a custom property with a syntax type, inheritance behaviour and an initial value. This lets the browser interpolate the variable in transitions and animations, such as animating a gradient angle or number, provides a safe fallback for invalid values, and can prevent inheritance when it's not needed.
</QA>

## Key terms

<Terms>
  <Term name="Custom property">CSS property named with a double-dash prefix.</Term>
  <Term name="var()">Function reading a custom property, with optional fallback.</Term>
  <Term name=":root">Selector for the html element, used for global variables.</Term>
  <Term name="Fallback value">Value used when a variable is undefined.</Term>
  <Term name="Invalid at computed-value time">Variable value invalid where it is used.</Term>
  <Term name="Design token">Named design decision such as a colour or spacing value.</Term>
  <Term name="Primitive token">Raw palette or scale value.</Term>
  <Term name="Semantic token">Token named by purpose, pointing to a primitive.</Term>
  <Term name="Theme">A set of token values such as light or dark.</Term>
  <Term name="color-scheme">Tells the browser which colour schemes the page supports.</Term>
  <Term name="@property">Registers a typed, animatable custom property.</Term>
  <Term name="setProperty">JavaScript method to change a CSS variable.</Term>
</Terms>
