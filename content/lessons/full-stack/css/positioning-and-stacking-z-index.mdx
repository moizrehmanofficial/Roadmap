<BigIdea>
<Tr>
<En>
By default elements sit in **normal flow**: blocks stack, inline content flows. **`position`** changes that. **`relative`** nudges an element (its space stays reserved) and, more importantly, becomes the **anchor** for absolute children. **`absolute`** leaves the flow and is placed with `top`/`right`/`bottom`/`left` against the nearest **positioned ancestor**. **`fixed`** is placed against the **viewport** and stays put when scrolling. **`sticky`** scrolls normally until an offset (like `top: 0`), then sticks within its parent. When elements overlap, **`z-index`** decides, but only inside the same **stacking context**: `opacity`, `transform` or a positioned parent's `z-index` create new contexts, which is why `z-index: 9999` sometimes "fails". Modals and popovers belong in `<dialog>` or `popover`, which use the **top layer**.
</En>
<Ur>
Default me elements **normal flow** me hote hain: blocks upar neeche, inline mawad behta hua. **`position`** ye badalta hai. **`relative`** element ko thora khiskata hai (us ki jagah rakhi rehti hai) aur, sab se ahem, absolute bachon ka **langar** banta hai. **`absolute`** flow se nikal kar qareeb tareen **positioned ancestor** ke hisaab se `top`/`right`/`bottom`/`left` se rakha jata hai. **`fixed`** **viewport** ke hisaab se rakha jata hai aur scroll par jagah nahi chhorta. **`sticky`** kisi offset (jaise `top: 0`) tak aam scroll hota hai, phir parent ke andar chipak jata hai. Jab elements ek doosre par chadhen to **`z-index`** faisla karta hai, magar sirf usi **stacking context** ke andar: `opacity`, `transform` ya positioned parent ka `z-index` naye contexts banate hain, isi liye `z-index: 9999` kabhi "fail" hota hai. Modals aur popovers `<dialog>` ya `popover` me hon, jo **top layer** istemal karte hain.
</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Static and relative">

<Tr>
<En>`static` is the default: in flow, and `top`/`left`/`z-index` do nothing. `relative` stays in flow but offsets **shift it visually**; its original space is **still reserved**, so neighbours don't move. It's mostly used not to move things but to make the element a **containing block** for absolute children and to allow `z-index`. Big relative offsets for layout are a bad idea: they leave a hole and overlap content.</En>
<Ur>`static` default hai: flow me, aur `top`/`left`/`z-index` kuch nahi karte. `relative` flow me rehta hai magar offsets use **nazar me khiskate** hain; us ki asal jagah **ab bhi rakhi** rehti hai, isliye pados nahi hilte. Ye zyada tar cheezen hilane ke liye nahi balke element ko absolute bachon ka **containing block** banane aur `z-index` ki ijazat ke liye hota hai. Layout ke liye bare relative offsets bura khayal hain: khala chhorte aur mawad par chadhte hain.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0}
div { height: 50px; width: 100px; }
#shifted { position: relative; top: 20px; left: 30px; }
</style>
<div id="first">first</div><div id="shifted">shifted</div><div id="third">third</div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el in ["#first", "#shifted", "#third"]:
        r = page.eval_on_selector(el, "e => { const b = e.getBoundingClientRect(); return [b.x, b.y] }")
        print(f"{el:9} x={r[0]:<4} y={r[1]}")
    browser.close()
PY
```

```text output
#first    x=0    y=0
#shifted  x=30   y=70
#third    x=0    y=100
```

<Happened>
<Tr>
<En>Without offsets `#shifted` would sit at y=50; `top: 20px; left: 30px` drew it at (30, 70). `#third` is still at y=100: the original space is kept, so `#shifted` now overlaps it by 20px. `top: 20px` means "20px down from the normal position", not from the top of the page.</En>
<Ur>Offsets ke baghair `#shifted` y=50 par hota; `top: 20px; left: 30px` ne use (30, 70) par banaya. `#third` ab bhi y=100 par hai: asal jagah rakhi gayi, isliye `#shifted` ab us par 20px chadha hai. `top: 20px` ka matlab "aam jagah se 20px neeche", page ke upar se nahi.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Absolute positioning and the containing block">

<Tr>
<En>An absolute element **leaves the flow** (takes no space; siblings close the gap) and is placed against its **containing block**: the **padding box of the nearest ancestor whose `position` isn't `static`**, or else the initial containing block (viewport-sized, at the top of the page). That's how badges sit in card corners and icons inside inputs. Always add `position: relative` to the intended parent; forgetting it is the number one positioning bug. Setting `left` and `right` (or `inset: 0`) stretches it; without width it shrinks to content; ancestors with `transform`, `filter`, `perspective` or `contain: paint` also become containing blocks.</En>
<Ur>Absolute element **flow se nikal jata** hai (jagah nahi leta; siblings khala band kar dete hain) aur apne **containing block** ke hisaab se rakha jata hai: **qareeb tareen aise ancestor ka padding box jis ki `position` `static` na ho**, warna initial containing block (viewport jitna, page ke upar). Isi tarah badges card ke kono me aur icons inputs ke andar baithte hain. Mutalliqa parent par hamesha `position: relative` lagayen; bhoolna positioning ka sab se bara bug hai. `left` aur `right` (ya `inset: 0`) dono dene se phailta hai; width ke baghair mawad jitna sukerta hai; `transform`, `filter`, `perspective` ya `contain: paint` wale ancestors bhi containing block bante hain.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0}
.card { width: 200px; height: 120px; margin: 40px; padding: 10px; border: 2px solid; }
.badge { position: absolute; top: 0; right: 0; width: 50px; height: 20px; }
#anchored { position: relative; }
</style>
<div class="card" id="loose"><span class="badge" id="b1">NEW</span>Card without position</div>
<div class="card" id="anchored"><span class="badge" id="b2">NEW</span>Card with position: relative</div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 800, "height": 600})
    page.set_content(html)
    for card, badge in [("#loose", "#b1"), ("#anchored", "#b2")]:
        c = page.eval_on_selector(card, "e => { const r = e.getBoundingClientRect(); return [r.x, r.y, r.right] }")
        b = page.eval_on_selector(badge, "e => { const r = e.getBoundingClientRect(); return [r.x, r.y, r.right] }")
        print(f"{card:9} card x={c[0]}..{c[2]} y={c[1]}  ->  badge x={b[0]}..{b[2]} y={b[1]}")
    browser.close()
PY
```

```text output
#loose    card x=40..264 y=40  ->  badge x=750..800 y=0
#anchored card x=40..264 y=224  ->  badge x=212..262 y=226
```

<Happened>
<Tr>
<En>The first card has no positioned ancestor, so its badge used the **initial containing block** (the 800px viewport): x=750..800, y=0, the page's corner, far from its card. The second card has `position: relative`, so its badge sits in the card's corner: right edge at 262 and top at 226 because offsets are measured from the **padding box**, inside the 2px border.</En>
<Ur>Pehle card ka koi positioned ancestor nahi, isliye us ke badge ne **initial containing block** (800px viewport) istemal kiya: x=750..800, y=0, page ka kona, card se door. Doosre card par `position: relative` hai, isliye badge card ke kone me hai: daayan kinara 262 aur upar 226 par kyun ke offsets 2px border ke andar **padding box** se naape jate hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Offsets and inset">

<Tr>
<En>`top`, `right`, `bottom`, `left` set distances from the containing block's edges (for relative, from the normal position). `inset` is the shorthand: `inset: 0` is all four; `inset: 10px 20px` is top/bottom then left/right. Logical versions exist (`inset-block-start`, `inset-inline-end`), and percentages use the containing block's size. `inset: 0` is the shortest full-cover overlay (`absolute`) or backdrop (`fixed`). If you set `top`, `bottom` and `height`, `bottom` is ignored. Below, two ways to centre an absolute box, and a full cover.</En>
<Ur>`top`, `right`, `bottom`, `left` containing block ke kinaron se faasla tay karte hain (relative me aam jagah se). `inset` mukhtasar hai: `inset: 0` chaaron; `inset: 10px 20px` pehle upar/neeche phir baayen/daayen. Logical shaklen bhi hain (`inset-block-start`, `inset-inline-end`), aur percentages containing block ke size ke hisaab se. `inset: 0` poora dhaanpne wale overlay (`absolute`) ya backdrop (`fixed`) ka sab se chhota tareeqa hai. `top`, `bottom` aur `height` teeno den to `bottom` nazar andaz hota hai. Neeche absolute dabba beech me karne ke do tareeqe, aur poora dhaanpna.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0}
.parent { position: relative; width: 400px; height: 200px; }
.box { position: absolute; width: 100px; height: 50px; }
#transform { top: 50%; left: 50%; transform: translate(-50%, -50%); }
#margin { inset: 0; margin: auto; }
#cover { position: absolute; inset: 0; }
</style>
<div class="parent"><div class="box" id="transform"></div></div>
<div class="parent" id="p2"><div class="box" id="margin"></div></div>
<div class="parent" id="p3"><div id="cover"></div></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el in ["#transform", "#margin", "#cover"]:
        r = page.eval_on_selector(el, "e => { const b = e.getBoundingClientRect(); const p = e.parentElement.getBoundingClientRect(); return [b.x - p.x, b.y - p.y, b.width, b.height] }")
        print(f"{el:10} at ({r[0]:.0f}, {r[1]:.0f}) inside parent, size {r[2]:.0f}x{r[3]:.0f}")
    browser.close()
PY
```

```text output
#transform at (150, 75) inside parent, size 100x50
#margin    at (150, 75) inside parent, size 100x50
#cover     at (0, 0) inside parent, size 400x200
```

<Happened>
<Tr>
<En>**transform:** `top: 50%; left: 50%` puts the corner at the centre (200, 100), and `translate(-50%, -50%)` pulls it back by half its own size to (150, 75); works even when the size is unknown. **inset + margin auto:** with all offsets 0 and a fixed size, `margin: auto` splits the space, also centring. **cover:** `inset: 0` with no size stretched to the full 400 × 200: perfect for overlays and clickable card links.</En>
<Ur>**transform:** `top: 50%; left: 50%` kona beech (200, 100) par rakhta hai, aur `translate(-50%, -50%)` use apne aadhe size jitna wapas (150, 75) kheenchta hai; size na maloom ho tab bhi chalta hai. **inset + margin auto:** saare offsets 0 aur muqarrar size ke saath `margin: auto` jagah baant kar beech me karta hai. **cover:** bina size `inset: 0` poore 400 × 200 par phail gaya: overlays aur clickable card links ke liye behtareen.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fixed positioning">

<Tr>
<En>`position: fixed` leaves the flow and is placed against the **viewport**, so it stays put on screen while the page scrolls: floating buttons, chat widgets, cookie banners, toasts, full-screen overlays. Use sparingly and leave room so it doesn't hide content (e.g. `padding-bottom` on the body for a bottom bar). **Gotcha:** if any ancestor has `transform`, `filter`, `perspective` or similar, `fixed` behaves like `absolute` against **that ancestor** and scrolls with it, a common cause of broken modals inside animated containers.</En>
<Ur>`position: fixed` flow se nikal kar **viewport** ke hisaab se rakha jata hai, isliye page scroll ho to bhi screen par wahin rehta hai: tairte buttons, chat widgets, cookie banners, toasts, poori screen ke overlays. Kam istemal karein aur jagah chhoren taa ke mawad na chhupe (maslan neeche ki patti ke liye body par `padding-bottom`). **Dhoka:** agar kisi ancestor par `transform`, `filter`, `perspective` waghaira ho to `fixed` **us ancestor** ke hisaab se `absolute` jaisa ho kar us ke saath scroll hota hai, animated containers ke andar toote modals ki aam wajah.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0; height: 3000px}
.chat { position: fixed; right: 16px; bottom: 16px; width: 60px; height: 60px; }
.normal { margin-top: 100px; height: 40px; }
.transformed { transform: translateX(0); margin-top: 200px; height: 100px; }
.inner { position: fixed; top: 0; left: 0; width: 50px; height: 20px; }
</style>
<div class="normal" id="normal">normal</div>
<button class="chat" id="chat" type="button">Chat</button>
<div class="transformed"><div class="inner" id="inner">x</div></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 800, "height": 600})
    page.set_content(html)
    for scroll in [0, 500]:
        page.evaluate(f"window.scrollTo(0, {scroll})")
        pos = {el: page.eval_on_selector(el, "e => Math.round(e.getBoundingClientRect().y)") for el in ["#normal", "#chat", "#inner"]}
        print(f"scrollY={scroll:<4} on-screen y: normal={pos['#normal']:<5} chat={pos['#chat']:<5} fixed-inside-transform={pos['#inner']}")
    browser.close()
PY
```

```text output

scrollY=500  on-screen y: normal=-400  chat=524   fixed-inside-transform=-160
```

<Tr>
<En>The normal element moved up 500px with the scroll (100 → −400). The chat button stayed at y=524 (600 − 16 − 60) whatever the scroll. The "fixed" element inside a transformed parent was **not** fixed: it sat at the top of the transformed div (y=340) and scrolled away with it, exactly like `absolute`.</En>
<Ur>Aam element scroll ke saath 500px upar gaya (100 → −400). Chat button scroll kuch bhi ho y=524 (600 − 16 − 60) par raha. Transformed parent ke andar ka "fixed" element fixed **nahi** tha: wo transformed div ke upar (y=340) baitha aur us ke saath scroll ho gaya, bilkul `absolute` ki tarah.</Ur>
</Tr>

<Step title="Sticky positioning">

<Tr>
<En>

`position: sticky; top: 0` stays in flow until scrolling would move it past the offset from its **scroll container** (usually the viewport), then it **sticks**, but only while its **parent** is visible. Sticky headers, table headers and list section titles need no JavaScript. Why sticky "doesn't work":

- No offset (`top`, `bottom`…).
- The parent is no taller than the sticky element, so there's no room.
- An ancestor with `overflow: hidden/auto/scroll` becomes the scroll container and doesn't scroll.
- In flex or grid, the item stretches to full height (use `align-self: start`).

Scroll inside the result: each letter sticks until its section ends.

</En>
<Ur>

`position: sticky; top: 0` flow me rehta hai jab tak scroll use apne **scroll container** (aam taur par viewport) se offset ke paar na le jaye, phir **chipak** jata hai, magar sirf jab tak us ka **parent** nazar aaye. Sticky headers, table headers aur list ke section titles ko JavaScript nahi chahiye. Sticky "kyun nahi chalta":

- Offset nahi (`top`, `bottom`…).
- Parent sticky element se ooncha nahi, isliye chipakne ki jagah nahi.
- `overflow: hidden/auto/scroll` wala ancestor scroll container ban jata hai aur khud scroll nahi hota.
- Flex ya grid me item poori oonchai tak phailta hai (`align-self: start` lagayen).

Result ke andar scroll karein: har harf apna section khatam hone tak chipakta hai.

</Ur>
</Tr>

<Step title="Stacking order without z-index">

<Tr>
<En>

Within each stacking context the browser paints, bottom to top:

1. The context's background and borders.
2. Positioned elements with **negative** z-index.
3. Non-positioned blocks, in HTML order.
4. Floats.
5. Inline content.
6. Positioned elements with `z-index: auto` or `0`, in **HTML order**.
7. Positive z-index, lowest first.

So without z-index, a **positioned** element is above non-positioned ones, and **later** above earlier. Often you don't need z-index at all. `z-index` only affects positioned elements and flex/grid items. Below, `elementFromPoint` reports what's on top.

</En>
<Ur>

Har stacking context me browser neeche se upar is tarteeb me rangta hai:

1. Context ka background aur borders.
2. **Manfi** z-index wale positioned elements.
3. Na positioned blocks, HTML tarteeb me.
4. Floats.
5. Inline mawad.
6. `z-index: auto` ya `0` wale positioned elements, **HTML tarteeb** me.
7. Musbat z-index, chhota pehle.

Isliye bina z-index **positioned** element na positioned walon ke upar, aur **baad wala** pehle wale ke upar hota hai. Aksar z-index ki zaroorat hi nahi. `z-index` sirf positioned elements aur flex/grid items par asar karta hai. Neeche `elementFromPoint` batata hai upar kya hai.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
def top_at(page, html):
    page.set_content("<!DOCTYPE html><title>t</title><style>body{margin:0} div{width:100px;height:100px}</style>" + html)
    return page.evaluate("document.elementFromPoint(60, 60).id")
cases = {
    "two normal boxes, B pulled up":         '<div id="A"></div><div id="B" style="margin-top:-50px"></div>',
    "A positioned, B normal":                '<div id="A" style="position:relative"></div><div id="B" style="margin-top:-50px"></div>',
    "both positioned (later wins)":          '<div id="A" style="position:relative"></div><div id="B" style="position:relative;margin-top:-50px"></div>',
    "both positioned, A z-index 1":          '<div id="A" style="position:relative;z-index:1"></div><div id="B" style="position:relative;margin-top:-50px"></div>',
    "z-index on non-positioned A (ignored)": '<div id="A" style="z-index:99"></div><div id="B" style="margin-top:-50px"></div>',
}
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    for name, html in cases.items():
        print(f"{name:38} on top: {top_at(page, html)}")
    browser.close()
PY
```

A positioned, B normal                 on top: A

<Happened>
<Tr>
<En>B overlaps A's lower half (negative margin) and we test (60, 60) in the overlap. Two normal blocks: later (B) wins. Only A positioned: A is painted in a later step, so on top. Both positioned: HTML order again, B. `z-index: 1` on A beats B's `auto`. `z-index: 99` on a non-positioned element does **nothing**, so B stays on top.</En>
<Ur>B A ke neeche aadhe hisse par chadha hai (manfi margin) aur hum overlap me (60, 60) test karte hain. Do aam blocks: baad wala (B) jeeta. Sirf A positioned: A baad ke qadam me rangta hai, isliye upar. Dono positioned: phir HTML tarteeb, B. A par `z-index: 1` B ke `auto` se jeeta. Na positioned element par `z-index: 99` **kuch nahi** karta, isliye B upar rehta hai.</Ur>

<Step title="Stacking contexts: why z-index: 9999 fails">

<Tr>
<En>

A **stacking context** is a group stacked as one unit: children's `z-index` only competes **inside** it, and the whole group is placed using the **parent's** z-index. A child at 9999 inside a context at 1 can never beat a sibling context at 2. Common creators:

- `<html>`; `position: relative/absolute` **with** a `z-index`; `fixed` or `sticky` always.
- Flex and grid items with a `z-index`.
- `opacity` < 1, `transform`, `filter`, `backdrop-filter`, `perspective`, `clip-path`, `mask`.
- `mix-blend-mode`, `isolation: isolate`, `will-change`, `contain: layout/paint`.

Fixes: move the overlay elsewhere in the DOM (end of `<body>`, what React portals do), raise the **parent's** z-index, or remove the property that created the context. DevTools' Layers panel helps.

</En>
<Ur>

**Stacking context** ek ikai ki tarah rakha group hai: bachon ka `z-index` sirf us ke **andar** muqabla karta hai, aur poora group **parent ke** z-index se rakha jata hai. 1 wale context ke andar 9999 wala bachcha 2 wale sibling context se kabhi nahi jeet sakta. Aam banane wale:

- `<html>`; `z-index` **ke saath** `position: relative/absolute`; `fixed` ya `sticky` hamesha.
- `z-index` wale flex aur grid items.
- `opacity` < 1, `transform`, `filter`, `backdrop-filter`, `perspective`, `clip-path`, `mask`.
- `mix-blend-mode`, `isolation: isolate`, `will-change`, `contain: layout/paint`.

Hal: overlay ko DOM me kahin aur le jayen (`<body>` ka aakhir, React portals yahi karte hain), **parent ka** z-index barhayen, ya context banane wali property hatayen. DevTools ka Layers panel madad karta hai.

</Ur>
</Tr>

<Tr>
<En>(50, 100) is where the open dropdown overlaps the banner. **Broken:** the header (1) is a context, so the dropdown's 9999 counts only inside it, and the banner's 2 wins. **Raising the parent** to 3 lifts the whole header, dropdown included. **Removing** the header's z-index ends its context, so 9999 competes directly with 2 and wins. **opacity: 0.99** silently creates a context again (painted at level 0), so the banner wins: animations on opacity or transform often cause "random" z-index bugs.</En>
<Ur>(50, 100) wo jagah hai jahan khula dropdown banner par chadhta hai. **Toota:** header (1) context hai, isliye dropdown ka 9999 sirf us ke andar ginta hai, aur banner ka 2 jeet ta hai. **Parent ko** 3 karne se poora header, dropdown samet, upar uthta hai. Header ka z-index **hatane** se us ka context khatam, isliye 9999 seedha 2 se muqabla kar ke jeet ta hai. **opacity: 0.99** chupke se phir context banata hai (level 0 par rangta hai), isliye banner jeet ta hai: opacity ya transform par animations aksar "achanak" z-index bugs laati hain.</Ur>

<Step title="A z-index scale and isolation">

<Tr>
<En>

Define a small, named **z-index scale** instead of random numbers (teams with arbitrary values end up with 999, 9999, 99999 and nobody knows what's above what), and use `isolation: isolate` to create a stacking context with no side effects, so a component's internal z-indexes can't leak out. Tailwind offers `z-10`…`z-50` and an `isolate` utility.

```text
:root {
  --z-dropdown: 100;
  --z-sticky: 200;
  --z-overlay: 300;
  --z-modal: 400;
  --z-toast: 500;
}
.modal { z-index: var(--z-modal); }
.card  { isolation: isolate; }   /* internal z-indexes stay inside */
```

</En>
<Ur>

Be-tarteeb numbers ke bajaye chhota, naam wala **z-index paimana** banayen (be-tarteeb values wali teams aakhir me 999, 9999, 99999 tak pohnchti hain aur kisi ko pata nahi kya kis ke upar hai), aur `isolation: isolate` se bina side effect stacking context banayen, taa ke component ke andar ke z-index bahar na rissen. Tailwind `z-10`…`z-50` aur `isolate` utility deta hai.

```text
:root {
  --z-dropdown: 100;
  --z-sticky: 200;
  --z-overlay: 300;
  --z-modal: 400;
  --z-toast: 500;
}
.modal { z-index: var(--z-modal); }
.card  { isolation: isolate; }   /* andar ke z-index andar hi */
```

</Ur>

<Step title="The top layer: dialog and popover">

<Tr>

No more z-index or `overflow: hidden` problems for modals and menus, plus built-in accessibility. Supported in all modern browsers (popover since 2024). For placing a popover next to its button, CSS anchor positioning is arriving; until then libraries like Floating UI compute positions. Open both below: they appear above a header with `z-index: 99999`.</En>
<Ur>Jadeed HTML me **top layer** hai jo har stacking context ke upar banti hai, z-index kuch bhi ho. ## Common mistakes

<Compare>
<Bad title="Escalating z-index">

```text
.badge { position: absolute; top: 0; right: 0; }   /* parent not positioned: page corner */
header { position: relative; z-index: 1; }
.dropdown { z-index: 99999; }                       /* still behind the banner */
.modal { position: fixed; z-index: 2147483647; }    /* inside a transformed parent */
```

</Bad>
<Good title="Anchors, scale, top layer">

```text
.card { position: relative; }  .badge { position: absolute; top: 8px; right: 8px; }
:root { --z-dropdown: 100; --z-modal: 400; }
.dropdown { z-index: var(--z-dropdown); }
dialog.showModal()             /* top layer: no z-index needed */
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Absolute positioning for page layout**, breaking when content or screen size changes.
- **z-index on a non-positioned element** (not a flex/grid item): it does nothing.
- **Accidental stacking contexts** from `opacity`, `transform` or `filter` in animations.
- **Sticky without an offset**, or inside an `overflow: hidden` ancestor.
- **Fixed headers covering content and focused elements**; add padding and `scroll-padding-top`.
- **Hand-built modals** instead of `<dialog>`, missing focus trapping and Escape.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Page layout ke liye absolute positioning**, jo mawad ya screen badalte hi toot jaye.
- **Na positioned element par z-index** (flex/grid item bhi nahi): kuch nahi karta.
- Animations me `opacity`, `transform` ya `filter` se **ghalti ke stacking contexts**.
- **Bina offset sticky**, ya `overflow: hidden` ancestor ke andar.
- **Mawad aur focus wale elements ko dhaanpte fixed headers**; padding aur `scroll-padding-top` joren.
- `<dialog>` ke bajaye **haath ke bane modals**, focus qaid aur Escape ke baghair.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Layout with flow, Flexbox and Grid; positioning for overlays and exceptions.
- `relative` keeps its space and anchors absolute children.
- `absolute` uses the nearest positioned ancestor's padding box; `inset: 0` covers it.
- `fixed` follows the viewport, unless a transformed ancestor captures it.
- `sticky` needs an offset, room in its parent and no non-scrolling overflow ancestor.
- Without z-index: positioned above non-positioned, later above earlier.
- z-index competes only within a stacking context; `opacity`/`transform` create contexts.
- Use a named z-index scale, `isolation: isolate`, and `<dialog>`/`popover` for the top layer.

<DeepDive title="Real world: z-index arms races">

Many large sites have had z-index values grow out of control. Third-party chat widgets, ad scripts and cookie banners often use 2147483647 (the largest 32-bit integer) to stay on top, sites respond with even bigger numbers, and nobody can tell what's above what. Modern design systems fix this with named z-index tokens, `isolation: isolate` on components, and React **portals** that render modals and menus at the end of `<body>`, outside any transformed or overflow-hidden parent. With `<dialog>` and the `popover` attribute in every major browser, most of these workarounds are no longer needed for new code, and component libraries are moving their menus and dialogs to the native elements.

</DeepDive>

<DeepDive title="Security lens">

Overlapping and positioned elements are how many UI-deception attacks work.

- **Clickjacking:** an attacker's page loads your site in a transparent `<iframe>` over a fake button, so users click your "Delete account" or "Transfer" unknowingly. Send `Content-Security-Policy: frame-ancestors 'none'` (or `'self'`), or `X-Frame-Options: DENY`.
- **Overlay injection:** users who can add CSS or HTML can place a fake login form or warning over your page with `position: fixed; inset: 0`. Sanitise user HTML, remove `style` attributes, set a CSP.
- **Full-card link overlays** intercept clicks for everything below; keep secondary controls above them so users don't trigger the wrong action.
- **Fixed banners** must not cover important notices or the checkout confirm button.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between relative, absolute, fixed and sticky positioning?">
Relative keeps the element in normal flow and offsets it visually from its normal position, keeping its original space. Absolute removes it from flow and positions it relative to the nearest positioned ancestor. Fixed removes it from flow and positions it relative to the viewport, so it doesn't move when scrolling. Sticky keeps it in flow until scrolling reaches a given offset, then it sticks within its parent's bounds.
</QA>

<QA q="What is the containing block of an absolutely positioned element?">
It is the padding box of the nearest ancestor whose position is not static, or of an ancestor with properties like transform or filter. If no such ancestor exists, it is the initial containing block, which has the size of the viewport at the top of the document.
</QA>

<QA q="What is a stacking context, and why can z-index 9999 fail?">
A stacking context is a group of elements painted together as a unit; z-index values of descendants only compete within it, and the whole group is ordered in its parent context by the root element's own z-index. If an element with z-index 9999 is inside a context whose root has z-index 1, it cannot appear above a sibling context with z-index 2. Stacking contexts are created by positioned elements with a z-index, fixed and sticky elements, opacity below 1, transforms, filters, isolation and similar properties.
</QA>

<QA q="Why might position sticky not work?">
Common causes are a missing offset such as top zero, a parent that is no taller than the sticky element so there is no room to stick, an ancestor with overflow hidden, auto or scroll that becomes the scroll container without actually scrolling, and a flex or grid item stretched to the container's full height.
</QA>

<QA q="How should you build modals and menus so they appear above everything?">
Use the native dialog element opened with showModal, or the popover attribute, which render in the browser's top layer above all stacking contexts and provide behaviour such as Escape handling, focus management and light dismiss. In frameworks, portals that render overlays at the end of the body also avoid stacking and overflow issues.
</QA>

</DeepDive>
