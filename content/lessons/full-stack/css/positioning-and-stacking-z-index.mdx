<Callout type="tip" title="In one minute">
By default, elements sit in **normal flow**: blocks stack, inline content flows in lines. The **`position`** property changes that. **`relative`** nudges an element from where it would be (its space stays reserved) and, more importantly, becomes the **anchor** for absolutely positioned children. **`absolute`** removes the element from the flow and positions it with `top`/`right`/`bottom`/`left` relative to its nearest **positioned ancestor** (the containing block). **`fixed`** positions relative to the **viewport** (it stays put when scrolling). **`sticky`** scrolls normally until it reaches an offset (like `top: 0`), then sticks within its parent. When elements overlap, **`z-index`** decides which is on top, but only among elements in the same **stacking context**: properties like `opacity`, `transform` or `z-index` on a positioned parent create a new context, which is why `z-index: 9999` sometimes "doesn't work". Modals and popovers should use `<dialog>` or `popover`, which render in the browser's **top layer** above everything.
</Callout>

## Start from zero

<Callout type="analogy">
Think of a **noticeboard**. Normal flow is pinning papers in neat rows. **Relative** positioning is shifting one paper a little while its original spot stays empty. **Absolute** positioning is taking a sticky note and placing it at an exact spot **on a particular paper** (its positioned parent), say "10 cm from the top-right corner". **Fixed** is a sticker on your **glasses**: wherever you look (scroll), it's in the same place. **Sticky** is a bookmark that moves with the pages until it hits the top of the book, then stays there until its chapter ends. **z-index** decides which paper is on top when papers overlap, but papers pinned inside a folder (a **stacking context**) can never come out above another folder that's on top.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Normal flow** | Default layout of blocks and inline content | paragraphs stacking |
| **Positioned element** | Any `position` except `static` | `position: relative` |
| **Offsets** | `top`, `right`, `bottom`, `left` | `top: 10px` |
| **inset** | Shorthand for all four offsets | `inset: 0` |
| **Containing block** | The box an element positions against | nearest positioned ancestor |
| **Viewport** | The visible area of the browser window | |
| **z-index** | Stacking order number | `z-index: 10` |
| **Stacking context** | A group whose children are stacked together | created by `opacity < 1` |
| **Top layer** | Special layer above all content | `<dialog>`, popovers |

## What is it?

The five values of `position`:

| Value | In normal flow? | Offsets relative to | Scrolls with page? |
| --- | --- | --- | --- |
| `static` (default) | Yes | Offsets ignored | Yes |
| `relative` | Yes (space kept) | Its own normal position | Yes |
| `absolute` | **No** | Nearest positioned ancestor (else the initial containing block) | Yes, with that ancestor |
| `fixed` | **No** | The viewport | **No** |
| `sticky` | Yes | Its scroll container, within its parent | Until it sticks |

```css
.card   { position: relative; }                       /* anchor */
.badge  { position: absolute; top: 8px; right: 8px; } /* corner of the card */
.header { position: sticky; top: 0; }                 /* sticks while scrolling */
.chat   { position: fixed; right: 16px; bottom: 16px; } /* always visible */
```

## Why does it matter?

- Badges, tooltips, dropdown menus, sticky headers, "back to top" buttons, overlays, chat widgets and modals all use positioning.
- Misusing it causes some of the most frustrating bugs: elements jumping to the page corner, menus hidden behind other content, sticky headers that don't stick, z-index wars with values like 99999.
- Positioning is for **overlays and exceptions**; the main layout should use flow, Flexbox and Grid. Knowing the difference keeps layouts responsive.

## When and where do you use it?

- `relative`: as an anchor for absolute children (most common use), or small visual nudges.
- `absolute`: badges, icons inside inputs, tooltips, dropdowns, overlays covering a card.
- `fixed`: elements tied to the screen (chat button, cookie banner), full-screen overlays.
- `sticky`: table headers, section headings, sidebars, navigation that stays visible.

## Concepts one by one

### 1. Static and relative

<Explain>
<What>
`static` is the default: the element is in normal flow and `top`/`left`/`z-index` have no effect. `relative` keeps the element in normal flow but lets offsets **shift it visually** from its normal position; the space it originally took is **still reserved**, so other elements don't move.
</What>
<Why>
Relative positioning is mostly used not to move things, but to make the element a **containing block** for absolute children, and to allow `z-index`.
</Why>
<When>
`position: relative` on cards, buttons, inputs and any element whose children will be absolutely positioned.
</When>
<Where>
Large relative offsets for layout are a bad idea: the element moves but leaves a hole, and may overlap other content.
</Where>
<How>
Measuring a relatively shifted element and its neighbour:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0}
div { height: 50px; width: 100px; }
#shifted { position: relative; top: 20px; left: 30px; }
</style>
<div id="first">first</div><div id="shifted">shifted</div><div id="third">third</div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el in ["#first", "#shifted", "#third"]:
        r = page.eval_on_selector(el, "e => { const b = e.getBoundingClientRect(); return [b.x, b.y] }")
        print(f"{el:9} x={r[0]:<4} y={r[1]}")
    browser.close()
PY
```

```text output
#first    x=0    y=0
#shifted  x=30   y=70
#third    x=0    y=100
```

Line by line:

- Without offsets, `#shifted` would be at y=50. With `top: 20px; left: 30px` it's drawn at (30, 70).
- `#third` is still at y=100, exactly where it would be anyway: the shifted element's original space is kept, so it now overlaps `#third` by 20px.
- `top: 20px` means "move down 20px from the top of the normal position", not "20px from the top of the page".

### 2. Absolute positioning and the containing block

<Explain>
<What>
An absolutely positioned element is **removed from normal flow** (it takes no space, siblings close the gap) and is placed using offsets relative to its **containing block**: the **padding box of the nearest ancestor whose `position` is not `static`**. If there is none, it's the initial containing block (the size of the viewport, at the top of the page).
</What>
<Why>
This is how you put a badge in a card's corner, an icon inside an input, or a close button in a dialog.
</Why>
<When>
Always add `position: relative` to the intended parent. Forgetting it is the number one positioning bug: the element jumps to the corner of the page or of some unrelated ancestor.
</When>
<Where>
- `top: 0; right: 0` = top-right corner of the parent's padding box.
- Setting both `left` and `right` (or `inset: 0`) stretches the element between them.
- Without offsets, an absolute element stays where it would have been in the flow, but still takes no space.
- An absolute element's width shrinks to fit its content, unless you set `width` or both `left` and `right`.
- Ancestors with `transform`, `filter`, `perspective`, `contain: paint` or `will-change: transform` also become containing blocks.
</Where>
<How>
The same badge with and without a positioned parent:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0}
.card { width: 200px; height: 120px; margin: 40px; padding: 10px; border: 2px solid; }
.badge { position: absolute; top: 0; right: 0; width: 50px; height: 20px; }
#anchored { position: relative; }
</style>
<div class="card" id="loose"><span class="badge" id="b1">NEW</span>Card without position</div>
<div class="card" id="anchored"><span class="badge" id="b2">NEW</span>Card with position: relative</div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 800, "height": 600})
    page.set_content(html)
    for card, badge in [("#loose", "#b1"), ("#anchored", "#b2")]:
        c = page.eval_on_selector(card, "e => { const r = e.getBoundingClientRect(); return [r.x, r.y, r.right] }")
        b = page.eval_on_selector(badge, "e => { const r = e.getBoundingClientRect(); return [r.x, r.y, r.right] }")
        print(f"{card:9} card x={c[0]}..{c[2]} y={c[1]}  ->  badge x={b[0]}..{b[2]} y={b[1]}")
    browser.close()
PY
```

```text output
#loose    card x=40..264 y=40  ->  badge x=750..800 y=0
#anchored card x=40..264 y=224  ->  badge x=212..262 y=226
```

Line by line:

- The first card has no positioned ancestor, so its badge is positioned against the **initial containing block** (the 800px wide viewport): top-right corner of the page, x=750 to 800, y=0. Far from its card.
- The second card has `position: relative`, so its badge is in the card's top-right corner. The card's border box spans x=40..264; the badge's right edge is at 262 because offsets are measured from the **padding box** (inside the 2px border), and its top is at 226 (224 + 2px border).

### 3. Offsets and inset

<Explain>
<What>
- `top`, `right`, `bottom`, `left` set distances from the containing block's edges (for relative: from the normal position).
- `inset` is the shorthand: `inset: 0` = all four 0; `inset: 10px 20px` = top/bottom 10, left/right 20 (same order as margin).
- Logical versions: `inset-block-start`, `inset-inline-end` and so on.
- Percentages are relative to the containing block's size.
</What>
<Why>
`inset: 0` is the shortest way to make an overlay cover its parent completely.
</Why>
<When>
Full-cover overlays (`position: absolute; inset: 0`), full-screen backdrops (`position: fixed; inset: 0`).
</When>
<Where>
If you set `top` and `bottom` but also `height`, `bottom` is ignored (in left-to-right documents, `left` wins over `right` the same way).
</Where>
<How>
Centring an absolutely positioned box, two ways:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0}
.parent { position: relative; width: 400px; height: 200px; }
.box { position: absolute; width: 100px; height: 50px; }
#transform { top: 50%; left: 50%; transform: translate(-50%, -50%); }
#margin { inset: 0; margin: auto; }
#cover { position: absolute; inset: 0; }
</style>
<div class="parent"><div class="box" id="transform"></div></div>
<div class="parent" id="p2"><div class="box" id="margin"></div></div>
<div class="parent" id="p3"><div id="cover"></div></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el in ["#transform", "#margin", "#cover"]:
        r = page.eval_on_selector(el, "e => { const b = e.getBoundingClientRect(); const p = e.parentElement.getBoundingClientRect(); return [b.x - p.x, b.y - p.y, b.width, b.height] }")
        print(f"{el:10} at ({r[0]:.0f}, {r[1]:.0f}) inside parent, size {r[2]:.0f}x{r[3]:.0f}")
    browser.close()
PY
```

```text output
#transform at (150, 75) inside parent, size 100x50
#margin    at (150, 75) inside parent, size 100x50
#cover     at (0, 0) inside parent, size 400x200
```

Line by line:

- **transform method:** `top: 50%; left: 50%` puts the box's top-left corner at the centre (200, 100); `translate(-50%, -50%)` moves it back by half its own size, so it's centred at (150, 75). Works even when the box's size is unknown.
- **inset + margin auto:** with all offsets 0 and a fixed size, `margin: auto` splits the leftover space, also centring it.
- **cover:** `inset: 0` without a size stretches the element to the parent's full 400 × 200, perfect for overlays and clickable card links.

### 4. Fixed positioning

<Explain>
<What>
`position: fixed` removes the element from flow and positions it relative to the **viewport**, so it stays in the same place on screen while the page scrolls.
</What>
<Why>
Floating action buttons, chat widgets, cookie banners, full-screen overlays, toasts.
</Why>
<When>
Use sparingly: fixed elements cover content, especially on small screens. Leave space so they don't hide important text (e.g. add `padding-bottom` to the body for a fixed bottom bar).
</When>
<Where>
**Gotcha:** if any ancestor has `transform`, `filter`, `perspective` or similar, `fixed` behaves like `absolute` relative to **that ancestor**, and scrolls with it. A common cause: a fixed modal inside an animated (transformed) container.
</Where>
<How>
Scrolling the page and measuring where elements are on screen:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0; height: 3000px}
.chat { position: fixed; right: 16px; bottom: 16px; width: 60px; height: 60px; }
.normal { margin-top: 100px; height: 40px; }
.transformed { transform: translateX(0); margin-top: 200px; height: 100px; }
.inner { position: fixed; top: 0; left: 0; width: 50px; height: 20px; }
</style>
<div class="normal" id="normal">normal</div>
<button class="chat" id="chat" type="button">Chat</button>
<div class="transformed"><div class="inner" id="inner">x</div></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 800, "height": 600})
    page.set_content(html)
    for scroll in [0, 500]:
        page.evaluate(f"window.scrollTo(0, {scroll})")
        pos = {el: page.eval_on_selector(el, "e => Math.round(e.getBoundingClientRect().y)") for el in ["#normal", "#chat", "#inner"]}
        print(f"scrollY={scroll:<4} on-screen y: normal={pos['#normal']:<5} chat={pos['#chat']:<5} fixed-inside-transform={pos['#inner']}")
    browser.close()
PY
```

```text output
scrollY=0    on-screen y: normal=100   chat=524   fixed-inside-transform=340
scrollY=500  on-screen y: normal=-400  chat=524   fixed-inside-transform=-160
```

Line by line:

- The normal element moves up by 500px when the page scrolls 500px (from y=100 on screen to −400, off-screen).
- The chat button stays at y=524 on screen (600 − 16 − 60) whatever the scroll position.
- The "fixed" element inside a transformed parent is **not** fixed to the viewport: it's positioned at the top of the transformed div (y=340) and scrolls away with it, exactly like `absolute`.

### 5. Sticky positioning

<Explain>
<What>
`position: sticky; top: 0` keeps the element in normal flow until scrolling would move it past the given offset from its **scroll container** (usually the viewport); then it **sticks**. It stays stuck only while its **parent** is still visible: when the parent scrolls away, the sticky element goes with it.
</What>
<Why>
Sticky headers, table headers, section titles in long lists, sidebars that follow the user. No JavaScript scroll listeners needed.
</Why>
<When>
Navigation bars, `<thead>` cells, alphabet headings in contact lists.
</When>
<Where>
Why sticky "doesn't work":
- No offset set (`top`, `bottom`…): sticky needs one.
- The parent is as tall as the sticky element itself, so there's no room to stick.
- An ancestor has `overflow: hidden`, `auto` or `scroll`, which makes **it** the scroll container. If that ancestor doesn't actually scroll, nothing sticks.
- In a flex or grid container, the item stretches to the container's height (use `align-self: start`).
</Where>
<How>
Scroll inside the result below: each letter heading sticks until its section ends.
</How>
</Explain>

```html preview h=260 noqa
<style>
  body { margin: 0; font-family: system-ui, sans-serif; }
  .list { height: 240px; overflow-y: auto; border: 1px solid #e5e7eb; }
  .list h2 { position: sticky; top: 0; margin: 0; padding: 4px 12px; font-size: 0.9rem;
             background: #1f2937; color: white; }
  .list p { margin: 0; padding: 8px 12px; border-bottom: 1px solid #f3f4f6; }
</style>
<div class="list">
  <section><h2>A</h2><p>Alex</p><p>Amelia</p><p>Andrew</p><p>Ava</p></section>
  <section><h2>B</h2><p>Ben</p><p>Bella</p><p>Brown</p></section>
  <section><h2>C</h2><p>Carter</p><p>Chloe</p><p>Connor</p><p>Cora</p></section>
  <section><h2>D</h2><p>Daniel</p><p>Daisy</p><p>Dylan</p></section>
</div>
```

Line by line:

- `.list` is the scroll container (`overflow-y: auto` with a fixed height).
- Each `h2` is `sticky` with `top: 0`: when its section reaches the top of the list, the heading stays there.
- Because each heading's containing block is its own `<section>`, the next section pushes the previous heading out, like a phone's contacts app.
- A background colour is needed, otherwise the scrolling text would show through the stuck heading.

Measured in a real browser for a page-level sticky header:

```bash
python3 - <<'PY'

header { position: sticky; top: 0; height: 50px; background: white; }
.hero { height: 200px; }

<div class="hero"></div>
<header id="h">Sticky header</header>

```

Line by line:

- Normally the header starts at y=200 (below the hero), scrolls up to y=100, then sticks at y=0 once the page has scrolled past it.
- Wrapped in a parent with `overflow: hidden`, that parent becomes the header's scroll container; it never scrolls itself, and it's only as tall as the header, so the header scrolls off-screen (−400).

### 6. Stacking order without z-index

<Explain>
<What>
When boxes overlap, the browser paints them in a fixed order within each stacking context (from bottom to top):
1. The context's background and borders.
2. Positioned elements with **negative** z-index.
3. Non-positioned block boxes, in HTML order.
4. Floats.
5. Inline content (text, inline elements).
6. Positioned elements with `z-index: auto` or `0`, in **HTML order**.
7. Positioned elements with positive z-index, lowest first.
</What>
<Why>
Without any z-index, a **positioned** element is painted above non-positioned ones, and **later** elements above earlier ones.
</Why>
<When>
Often you don't need z-index at all; just make the element that should be on top positioned, or put it later in the HTML.
</When>
<Where>
`z-index` only affects positioned elements (any `position` except static), flex items and grid items.
</Where>
<How>
`document.elementFromPoint(x, y)` returns the topmost element at a point, which tells us what's on top:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
def top_at(page, html):
    page.set_content("<!DOCTYPE html><title>t</title><style>body{margin:0} div{width:100px;height:100px}</style>" + html)
    return page.evaluate("document.elementFromPoint(60, 60).id")
cases = {
    "two normal boxes, B pulled up":         '<div id="A"></div><div id="B" style="margin-top:-50px"></div>',
    "A positioned, B normal":                '<div id="A" style="position:relative"></div><div id="B" style="margin-top:-50px"></div>',
    "both positioned (later wins)":          '<div id="A" style="position:relative"></div><div id="B" style="position:relative;margin-top:-50px"></div>',
    "both positioned, A z-index 1":          '<div id="A" style="position:relative;z-index:1"></div><div id="B" style="position:relative;margin-top:-50px"></div>',
    "z-index on non-positioned A (ignored)": '<div id="A" style="z-index:99"></div><div id="B" style="margin-top:-50px"></div>',
}
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    for name, html in cases.items():
        print(f"{name:38} on top: {top_at(page, html)}")
    browser.close()
PY
```

```text output
two normal boxes, B pulled up          on top: B
A positioned, B normal                 on top: A
both positioned (later wins)           on top: B
both positioned, A z-index 1           on top: A
z-index on non-positioned A (ignored)  on top: B
```

Line by line:

- In every case B overlaps the bottom half of A (B is pulled up with a negative margin), and we check the point (60, 60), which is in the overlap.
- Two normal blocks: the later one (B) is on top.
- If only A is positioned, A is painted in a later step, so it's on top even though it comes first in the HTML.
- Both positioned: HTML order decides again, so B.
- `z-index: 1` on A puts it above B's `auto`.
- `z-index: 99` on a non-positioned element does **nothing** (it's not a flex/grid item either), so B stays on top.

### 7. Stacking contexts: why z-index: 9999 doesn't work

<Explain>
<What>
A **stacking context** is a group of elements stacked together as one unit. Children's `z-index` values only compete **inside** their context; the whole context is then placed in its parent context using the **parent element's** z-index. So a child with `z-index: 9999` inside a context with `z-index: 1` can never appear above a sibling context with `z-index: 2`.
</What>
<Why>
This explains nearly every "my dropdown/modal is behind something even with a huge z-index" bug.
</Why>
<When>
These create a new stacking context (common ones):
- The root `<html>` element.
- `position: relative`/`absolute` **with** a `z-index` other than `auto`.
- `position: fixed` or `sticky` (always).
- Flex and grid items with a `z-index` other than `auto`.
- `opacity` less than 1.
- `transform`, `filter`, `backdrop-filter`, `perspective`, `clip-path`, `mask`.
- `mix-blend-mode` other than normal, `isolation: isolate`.
- `will-change` with one of the above, `contain: layout`/`paint`.
</When>
<Where>
Chrome DevTools' **Layers** panel and the Elements panel's "stacking context" hints help find them. Fixes: move the overlay elsewhere in the DOM (often the end of `<body>`, which is what React "portals" do), raise the **parent context's** z-index, or remove the property that created the context.
</Where>
<How>
A dropdown with `z-index: 9999` inside a header with `z-index: 1`, against a page section with `z-index: 2`:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
base = """<!DOCTYPE html><title>t</title><style>body{margin:0}
header { position: relative; z-index: 1; height: 50px; }
.dropdown { position: absolute; top: 40px; left: 0; width: 200px; height: 150px; z-index: 9999; }
.banner { position: relative; z-index: 2; height: 100px; }
%s
</style>
<header id="header"><div class="dropdown" id="dropdown">menu</div></header>
<section class="banner" id="banner">banner</section>"""
fixes = {
    "header z-index 1 vs banner 2": "",
    "fix: header z-index 3":        "header { z-index: 3; }",
    "fix: no z-index on header":    "header { z-index: auto; }",
    "opacity on header (new ctx)":  "header { z-index: auto; opacity: 0.99; }",
}
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    for name, extra in fixes.items():
        page.set_content(base % extra)
        print(f"{name:30} topmost at (50, 100): {page.evaluate('document.elementFromPoint(50, 100).id')}")
    browser.close()
PY
```

```text output
header z-index 1 vs banner 2   topmost at (50, 100): banner
fix: header z-index 3          topmost at (50, 100): dropdown
fix: no z-index on header      topmost at (50, 100): dropdown
opacity on header (new ctx)    topmost at (50, 100): banner
```

Line by line:

- The point (50, 100) is where the open dropdown overlaps the banner.
- **Broken:** the header (z-index 1) is a stacking context; the dropdown's 9999 only counts inside it. The banner's context (2) beats the header's (1), so the banner covers the menu.
- **Raising the parent's** z-index to 3 lifts the whole header context, dropdown included, above the banner.
- **Removing** the header's z-index means it no longer creates a context, so the dropdown's 9999 competes directly with the banner's 2 and wins.
- **opacity: 0.99** silently creates a stacking context again (with `z-index: auto`, it's painted at level 0), so the banner wins. Animations that change opacity or transform often cause these "random" z-index bugs.

### 8. A z-index scale and isolation

<Explain>
<What>
- Define a small, named **z-index scale** instead of random numbers:
```css
:root {
  --z-dropdown: 100;
  --z-sticky: 200;
  --z-overlay: 300;
  --z-modal: 400;
  --z-toast: 500;
}
```
- **`isolation: isolate`** creates a stacking context without any other side effect, so a component's internal z-indexes can't leak out and fight the rest of the page.
</What>
<Why>
Teams that use arbitrary values end up with 999, 9999, 99999 and nobody knows what's above what.
</Why>
<When>
Every project with overlays. Put `isolation: isolate` on components that use z-index internally (cards with layered images, carousels).
</When>
<Where>
Tailwind provides `z-10` … `z-50` and an `isolate` utility.
</Where>
<How>
Use `z-index: var(--z-modal)` in components.
</How>
</Explain>

### 9. The top layer: dialog and popover

<Explain>
<What>
Modern HTML has a **top layer**, rendered above every stacking context, whatever the z-indexes. Elements enter it with:
- `<dialog>` opened with `dialog.showModal()` (with a `::backdrop` and a focus trap, and Escape closes it).
- Elements with the **`popover`** attribute, opened with `popovertarget` buttons or `showPopover()` (menus, tooltips, toasts; light-dismiss by clicking outside).
- Fullscreen elements.
</What>
<Why>
No more z-index or `overflow: hidden` problems for modals and menus, plus built-in accessibility behaviour (focus, Escape, inert background for modals).
</Why>
<When>
Modals, confirmation dialogs, dropdown menus, tooltips, toasts.
</When>
<Where>
Supported in all modern browsers (popover since 2024). For positioning a popover next to its button, **CSS anchor positioning** (`anchor-name`, `position-anchor`, `position-area`) is arriving in browsers; until it's everywhere, libraries like Floating UI compute positions with JavaScript.
</Where>
<How>
Open the dialog and the popover in the result below; both appear above a header with `z-index: 99999`.
</How>
</Explain>

```html preview-js h=300 noqa
<style>
  body { margin: 0; font-family: system-ui, sans-serif; }
  .header { position: sticky; top: 0; z-index: 99999; padding: 12px; background: #1f2937; color: white; }
  .content { padding: 12px; }
  dialog { border: 0; border-radius: 12px; padding: 20px; max-width: 280px; }
  dialog::backdrop { background: rgb(0 0 0 / 0.5); }
  [popover] { border: 1px solid #e5e7eb; border-radius: 8px; padding: 8px 12px; }
</style>
<div class="header">Header with z-index 99999</div>
<div class="content">
  <button type="button" id="open">Open dialog</button>
  <button type="button" popovertarget="menu">Open popover</button>
  <div id="menu" popover>Popover menu<br>(click outside to close)</div>
</div>
<dialog id="dlg">
  <p>This modal dialog is in the top layer, above the header.</p>
  <form method="dialog"><button type="submit">Close</button></form>
</dialog>
<script>
  document.getElementById("open").addEventListener("click", () => document.getElementById("dlg").showModal());
</script>
```

Line by line:

- The header has a huge z-index, yet the dialog, its dimmed `::backdrop`, and the popover appear above it: the top layer is outside normal stacking.
- `showModal()` makes the rest of the page inert and traps focus; Escape or the Close button (inside `form method="dialog"`) closes it.
- The popover needs no JavaScript at all: `popovertarget="menu"` toggles the element with `popover`, and clicking outside closes it.

## Real-world example

Many large sites have had z-index values grow out of control. Third-party chat widgets, ad scripts and cookie banners often use values like 2147483647 (the largest 32-bit integer) to make sure they're on top, so sites respond with even bigger numbers, and nobody can tell what's above what. Modern design systems fix this with named z-index tokens, `isolation: isolate` on components, and React **portals** (rendering modals and menus at the end of `<body>`, outside any transformed or overflow-hidden parent). With `<dialog>` and the `popover` attribute now in every major browser, most of these workarounds are no longer needed for new code, and component libraries are moving their menus and dialogs to these native elements.

## Common mistakes

- **Forgetting `position: relative` on the parent** of an absolute element.
- **Using absolute positioning for page layout,** which breaks when content or screen size changes.
- **Raising z-index endlessly** instead of finding the stacking context.
- **z-index on a non-positioned element** (and not a flex/grid item), which does nothing.
- **Accidental stacking contexts** from `opacity`, `transform` or `filter` in animations.
- **Sticky without an offset,** or inside an `overflow: hidden` ancestor.
- **Fixed elements inside transformed parents.**
- **Fixed headers or bars covering content and focused elements;** add matching padding and `scroll-padding-top`.
- **Building modals by hand** instead of `<dialog>`, missing focus trapping and Escape.

## Security lens

<Callout type="security">
Overlapping and positioned elements are how many UI-deception attacks work.
</Callout>

- **Clickjacking:** an attacker's page loads your site in a transparent `<iframe>` positioned over a fake button, so users click your "Delete account" or "Transfer" while thinking they're clicking something harmless. Defend by sending `Content-Security-Policy: frame-ancestors 'none'` (or `'self'`), or `X-Frame-Options: DENY`.
- **Overlay injection:** if users can add CSS or HTML (themes, profiles, CMS content), they can position a fake login form or fake warning over your page with `position: fixed; inset: 0`. Sanitise user HTML, remove `style` attributes, and set a CSP.
- **Full-card link overlays:** an `::after` overlay intercepts clicks for everything below it. Make sure secondary controls are above it (as in the hands-on), so users don't trigger the wrong action.
- **Fixed banners hiding consent or warnings:** don't let cookie bars or chat widgets cover important notices or the confirm button in checkout.

## Interview questions

<QA q="What is the difference between relative, absolute, fixed and sticky positioning?">
Relative keeps the element in normal flow and offsets it visually from its normal position, keeping its original space. Absolute removes it from flow and positions it relative to the nearest positioned ancestor. Fixed removes it from flow and positions it relative to the viewport, so it doesn't move when scrolling. Sticky keeps it in flow until scrolling reaches a given offset, then it sticks within its parent's bounds.
</QA>

<QA q="What is the containing block of an absolutely positioned element?">
It is the padding box of the nearest ancestor whose position is not static, or of an ancestor with properties like transform or filter. If no such ancestor exists, it is the initial containing block, which has the size of the viewport at the top of the document.
</QA>

<QA q="What is a stacking context, and why can z-index 9999 fail?">
A stacking context is a group of elements painted together as a unit; z-index values of descendants only compete within it, and the whole group is ordered in its parent context by the root element's own z-index. If an element with z-index 9999 is inside a context whose root has z-index 1, it cannot appear above a sibling context with z-index 2. Stacking contexts are created by positioned elements with a z-index, fixed and sticky elements, opacity below 1, transforms, filters, isolation and similar properties.
</QA>

<QA q="Why might position sticky not work?">
Common causes are a missing offset such as top zero, a parent that is no taller than the sticky element so there is no room to stick, an ancestor with overflow hidden, auto or scroll that becomes the scroll container without actually scrolling, and a flex or grid item stretched to the container's full height.
</QA>

<QA q="How should you build modals and menus so they appear above everything?">
Use the native dialog element opened with showModal, or the popover attribute, which render in the browser's top layer above all stacking contexts and provide behaviour such as Escape handling, focus management and light dismiss. In frameworks, portals that render overlays at the end of the body also avoid stacking and overflow issues.
</QA>

## Key terms

<Terms>
  <Term name="Normal flow">Default layout of block and inline boxes.</Term>
  <Term name="position">Property choosing static, relative, absolute, fixed or sticky.</Term>
  <Term name="Offsets">The top, right, bottom and left properties.</Term>
  <Term name="inset">Shorthand for all four offsets.</Term>
  <Term name="Containing block">Box against which an element is positioned.</Term>
  <Term name="Viewport">Visible area of the browser window.</Term>
  <Term name="Sticky positioning">Normal flow until a scroll offset, then stuck.</Term>
  <Term name="z-index">Stacking level of positioned, flex and grid items.</Term>
  <Term name="Stacking context">Group of elements stacked together as one unit.</Term>
  <Term name="isolation">Property creating a stacking context without side effects.</Term>
