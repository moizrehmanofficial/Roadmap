<BigIdea>
<Tr>
<En>
CSS has two motion tools. A **transition** animates a property **between two states** when it changes (hover, focus, a class toggle): `transition: background-color 200ms ease-out;`. An **animation** uses **`@keyframes`** to run a sequence of steps by itself, any number of times: `animation: spin 1s linear infinite;`. Both use a **duration**, a **timing function** (easing: `ease`, `linear`, `ease-in-out`, `cubic-bezier()`, `steps()`) and an optional **delay**. Animate **`transform`** (translate, scale, rotate) and **`opacity`** whenever possible: the GPU can run them without recalculating layout, so they stay smooth at 60fps; animating `width`, `height`, `top` or `margin` triggers layout every frame and can stutter. Keep UI transitions short (about 150–300ms), use motion to **explain** changes rather than decorate, and always respect **`prefers-reduced-motion`**.
</En>
<Ur>
CSS ke paas harkat ke do auzaar hain. **Transition** property badalne par use **do halaton ke darmiyan** animate karta hai (hover, focus, class toggle): `transition: background-color 200ms ease-out;`. **Animation** **`@keyframes`** se qadmon ki tarteeb khud chalati hai, jitni dafa chahein: `animation: spin 1s linear infinite;`. Dono me **duration**, **timing function** (easing: `ease`, `linear`, `ease-in-out`, `cubic-bezier()`, `steps()`) aur ikhtiyari **delay** hota hai. Jahan mumkin ho **`transform`** (translate, scale, rotate) aur **`opacity`** animate karein: GPU inhe layout dobara nikale baghair chalata hai, isliye 60fps par hamwar rehte hain; `width`, `height`, `top` ya `margin` animate karna har frame par layout chalata hai aur atak sakta hai. UI transitions chhote rakhein (taqreeban 150–300ms), harkat sajawat ke bajaye tabdeeli **samjhane** ke liye, aur hamesha **`prefers-reduced-motion`** ka khayal rakhein.
</Ur>

## Picture it

<Tr>
<En>

A **transition** is a **dimmer switch**: you turn the light from off to on, and instead of jumping, it fades over half a second. You only choose the start and end; the dimmer handles the in-between. An **animation** is a **flip book**: you draw key pages (0%, 50%, 100%) and the book plays them in order, as many times as you like, with nobody touching a switch. **Easing** is how a car moves: it doesn't jump to full speed, it accelerates, cruises and brakes. Eased motion feels natural; constant speed feels mechanical.

</En>
<Ur>

**Transition** **dimmer switch** hai: aap batti band se chalu karte hain, aur jhatke ke bajaye aadhe second me roshan hoti hai. Aap sirf shuru aur aakhir chunte hain; beech ka kaam dimmer karta hai. **Animation** **flip book** hai: aap khaas safhe (0%, 50%, 100%) banate hain aur kitab unhe tarteeb se chalati hai, jitni dafa chahein, koi switch chhue baghair. **Easing** gaari ki chaal hai: ye ek dum poori raftaar par nahi jati, tez hoti, chalti aur break lagati hai. Easing wali harkat qudrati lagti hai; ek jaisi raftaar mashini.

## Learn it step by step

<Walkthrough>

<Step title="Transitions">

<Tr>
<En>The `transition` shorthand is **property**, **duration**, **timing function**, **delay**, with several transitions separated by commas: `transition: opacity 200ms ease-out 50ms, transform 300ms ease;` (longhands: `transition-property`, `-duration`, `-timing-function`, `-delay`). Without it changes are instant; with it the browser interpolates. Put it on the **base** state, not only `:hover`, so it runs both entering and leaving. Avoid `transition: all`: it animates properties you didn't intend, layout ones included. Below we pause a 1-second transition with the Web Animations API (how the browser exposes CSS transitions to JavaScript) and sample its colour.</En>
<Ur>`transition` shorthand **property**, **duration**, **timing function**, **delay** hai, kai transitions commas se alag: `transition: opacity 200ms ease-out 50ms, transform 300ms ease;` (longhands: `transition-property`, `-duration`, `-timing-function`, `-delay`). Is ke baghair tabdeeli foran hoti hai; is ke saath browser beech ki values nikalta hai. Ise **asal** halat par lagayen, sirf `:hover` par nahi, taa ke aate aur jate dono waqt chale. `transition: all` se bachen: ye anchahi properties bhi animate karta hai, layout wali samet. Neeche hum Web Animations API (jis se browser CSS transitions JavaScript ko dikhata hai) se 1 second ka transition rok kar us ka rang naapte hain.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.box { width: 100px; height: 20px; background-color: rgb(0, 0, 0); transition: background-color 1000ms linear; }
.box.on { background-color: rgb(200, 100, 0); }
</style><div class="box" id="b"></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    page.eval_on_selector("#b", "e => { e.classList.add('on'); window.anim = e.getAnimations()[0]; anim.pause(); }")
    print("animation created:", page.evaluate("anim.constructor.name + ' of ' + anim.transitionProperty"))
    for t in [0, 250, 500, 750, 1000]:
        colour = page.eval_on_selector("#b", f"e => {{ anim.currentTime = {t}; return getComputedStyle(e).backgroundColor }}")
        print(f"t = {t:4}ms  background {colour}")
    browser.close()
PY
```

```text output
animation created: CSSTransition of background-color
t =    0ms  background rgb(0, 0, 0)
t =  250ms  background rgb(50, 25, 0)
t =  500ms  background rgb(100, 50, 0)
t =  750ms  background rgb(150, 75, 0)
t = 1000ms  background rgb(200, 100, 0)
```

<Happened>
<Tr>
<En>Adding `on` changed the colour and started a 1000ms transition; the browser created a `CSSTransition` object, which the script paused. Setting `currentTime` jumped to a moment and `getComputedStyle` showed the in-between value. With `linear` each channel moves at a constant rate: at 250ms (25%) red is 25% of 200 = 50, green 25% of 100 = 25. Every CSS transition and animation is a real `Animation` object JavaScript can inspect, pause or reverse.</En>
<Ur>`on` lagane se rang badla aur 1000ms ka transition shuru hua; browser ne `CSSTransition` object banaya, jise script ne roka. `currentTime` set karne se ek lamhe par chhalang lagi aur `getComputedStyle` ne beech ki value dikhayi. `linear` me har channel ek raftaar se chalta hai: 250ms (25%) par laal 200 ka 25% = 50, hara 100 ka 25% = 25. Har CSS transition aur animation asli `Animation` object hai jise JavaScript dekh, rok ya ulta chala sakti hai.</Ur>
</Tr>
</Happened>

<Step title="What can be animated">

<Tr>
<En>A property transitions if the browser can **interpolate** it: numbers, lengths, percentages, colours, transforms, shadows, `opacity`, `filter`, `clip-path`, gradient positions (not the gradient itself, unless via `@property` variables). Discrete properties (`display`, `visibility`, `font-family`) switch at one moment. So `height: 0` → `height: auto` doesn't animate (the classic problem); use `grid-template-rows: 0fr` → `1fr` (which does), `interpolate-size: allow-keywords` in newer browsers, or `<details>` with `::details-content`. `visibility` combined with opacity switches at the right end, so a fade-out also hides content from screen readers when finished. The grid trick:</En>
<Ur>Property tab transition hoti hai jab browser us ki beech ki values **nikal** sake: numbers, lambaiyan, percentages, rang, transforms, shadows, `opacity`, `filter`, `clip-path`, gradient ki jagah (khud gradient nahi, jab tak `@property` variables na hon). Alag alag values wali properties (`display`, `visibility`, `font-family`) ek lamhe me badalti hain. Isliye `height: 0` → `height: auto` animate nahi hota (mashhoor masla); `grid-template-rows: 0fr` → `1fr` (jo hota hai), naye browsers me `interpolate-size: allow-keywords`, ya `::details-content` ke saath `<details>` lein. Opacity ke saath `visibility` sahi aakhir par badalti hai, isliye fade-out khatam hone par mawad screen readers se bhi chhup jata hai. Grid wala tareeqa:</Ur>
</Tr>

Button ka `aria-expanded` screen readers ko halat batata hai.</Ur>

<Step title="Easing: timing functions">

<Tr>
<En>A timing function maps **time progress** (0 → 1) to **value progress** (0 → 1). `linear` is constant; `ease` (default) quick start, gentle end; `ease-in` slow start (things leaving); `ease-out` fast start, slow end (arrivals, UI responses); `ease-in-out` slow-fast-slow (moving across the screen); `cubic-bezier(x1, y1, x2, y2)` custom curves, where y outside 0–1 overshoots; `steps(n)` jumps in n steps (sprites, clocks); `linear(...)` approximates springs and bounces. Typical: hover/press and menus `ease-out` 100–200ms; moves `ease-in-out` 200–400ms; exits `ease-in`, a bit faster; spinners `linear`. Most UI transitions should be **150–300ms**. Sampling real `opacity` transitions:</En>
<Ur>Timing function **waqt ki taraqqi** (0 → 1) ko **value ki taraqqi** (0 → 1) se jorta hai. `linear` ek jaisa; `ease` (default) tez shuru, narm aakhir; `ease-in` sust shuru (jati cheezen); `ease-out` tez shuru, sust aakhir (aati cheezen, UI ke jawab); `ease-in-out` sust-tez-sust (screen par harkat); `cubic-bezier(x1, y1, x2, y2)` apne curves, jahan 0–1 se bahar y had se aage jata hai; `steps(n)` n qadmon me chhalang (sprites, ghariyan); `linear(...)` springs aur uchhal ki naqal. Aam taur par: hover/press aur menus `ease-out` 100–200ms; harkat `ease-in-out` 200–400ms; nikalna `ease-in`, thora tez; spinners `linear`. Zyada tar UI transitions **150–300ms** hon. Asli `opacity` transitions ki jaanch:</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
easings = ["linear", "ease", "ease-in", "ease-out", "ease-in-out", "cubic-bezier(0.34, 1.56, 0.64, 1)", "steps(4)"]
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    print(f"{'timing function':36} 25%    50%    75%  of the time")
    for e in easings:
        page.set_content(f"""<!DOCTYPE html><title>t</title><style>
          .b {{ opacity: 0; transition: opacity 1000ms {e}; }} .b.on {{ opacity: 1; }}</style><div class="b" id="b"></div>""")
        values = page.eval_on_selector("#b", """e => { e.classList.add('on'); const a = e.getAnimations()[0]; a.pause();
            return [250, 500, 750].map(t => { a.currentTime = t; return Number(getComputedStyle(e).opacity).toFixed(2) }) }""")
        print(f"{e:36} " + "   ".join(values))
    browser.close()
PY
```

<Step title="Transforms">

<Tr>
<En>`transform` (and the individual properties `translate`, `scale`, `rotate`) visually moves, resizes or rotates an element **without changing layout**: neighbours don't move. `translate: 0 -4px` moves, `scale: 1.05` grows 5%, `rotate: 45deg` rotates, plus `skewX()` and 3D functions; `transform-origin` sets the pivot (default centre), and `translate` percentages use the element's **own** size. They're the main motion tool: cheap and non-disruptive (hover lifts, `scale: 0.97` presses, slide-ins, flips, spinners). The individual properties transition independently and don't overwrite each other, unlike several `transform` declarations. A transform also creates a stacking context. Proof that it doesn't move neighbours while a margin does:</En>
<Ur>`transform` (aur alag properties `translate`, `scale`, `rotate`) element ko dekhne me hilata, barhata ya ghumata hai **layout badle baghair**: parosi nahi hilte. `translate: 0 -4px` hilata, `scale: 1.05` 5% barhata, `rotate: 45deg` ghumata hai, saath `skewX()` aur 3D functions; `transform-origin` dhuri tay karta hai (default beech), aur `translate` ke percentages element ke **apne** size se hain. Ye harkat ka asal auzaar hain: saste aur kuch na bigarne wale (hover par uthna, `scale: 0.97` dabana, slide-ins, palatna, spinners). Alag properties ek doosre se azad transition hoti hain aur ek doosre ko mitati nahi, kai `transform` declarations ke baraks. Transform stacking context bhi banata hai. Saboot ke ye parosi nahi hilata jabke margin hilata hai:</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>body{margin:0} div{height:40px}
#t { translate: 0 30px; } #m { margin-top: 30px; }
</style>
<section id="s1"><div>a</div><div id="t">transformed</div><div id="after1">next</div></section>
<section id="s2"><div>a</div><div id="m">margin</div><div id="after2">next</div></section>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el, nxt in [("#t", "#after1"), ("#m", "#after2")]:
        y = page.evaluate(f"""[document.querySelector('{el}'), document.querySelector('{nxt}')].map(e =>
            Math.round(e.getBoundingClientRect().y - e.parentElement.getBoundingClientRect().y))""")
        print(f"{el}: element drawn at y={y[0]}, next element at y={y[1]}")
    browser.close()
PY
```

```text output
#t: element drawn at y=70, next element at y=80
#m: element drawn at y=70, next element at y=110
```

<Happened>
<Tr>
<En>Both elements moved down 30px, so both were drawn at y=70 instead of 40. With `translate` the next element stayed at y=80, its normal spot: layout didn't change (the moved element now overlaps it). With `margin-top` the next element was pushed to y=110: everything below was recalculated, which animating margins forces on every frame.</En>
<Ur>Dono elements 30px neeche gaye, isliye dono 40 ke bajaye y=70 par bane. `translate` ke saath agla element apni aam jagah y=80 par raha: layout nahi badla (hila hua element ab us par chadha hai). `margin-top` ke saath agla element y=110 tak dhakela gaya: neeche sab dobara nikala gaya, jo margins animate karna har frame par karata hai.</Ur>

<Step title="Performance: cheap and expensive properties">

<Tr>
<En>Each frame the browser may **style** → **layout** (sizes, positions) → **paint** (pixels) → **composite** (layers on the GPU). **`transform`** and **`opacity`** usually need only compositing: cheap. `color`, `background`, `box-shadow` need paint: moderate. `width`, `height`, `top`, `left`, `margin`, `padding`, `font-size` need layout then paint: expensive, possibly page-wide. At 60fps there are about **16.7ms per frame** (8.3ms at 120Hz) for everything, your JavaScript included. So move with `translate`, resize with `scale`, fade with `opacity`, and for a big hover shadow fade a pseudo-element's opacity. `will-change: transform` prepares a layer; use it sparingly. DevTools' **Performance** panel and **Rendering → Paint flashing** show what's repainted.</En>
<Ur>Har frame me browser shayad **style** → **layout** (sizes, jagahen) → **paint** (pixels) → **composite** (GPU par tahen) karta hai. **`transform`** aur **`opacity`** ko aam taur par sirf compositing chahiye: sasta. `color`, `background`, `box-shadow` ko paint: darmiyana. `width`, `height`, `top`, `left`, `margin`, `padding`, `font-size` ko layout phir paint: mehanga, shayad poore page par. 60fps par har frame ke liye taqreeban **16.7ms** (120Hz par 8.3ms) hain, sab kuch samet aap ki JavaScript. Isliye `translate` se hilayen, `scale` se size badlein, `opacity` se mand karein, aur bare hover shadow ke liye pseudo-element ki opacity badlein. `will-change: transform` layer tayyar karta hai; kam istemal karein. DevTools ka **Performance** panel aur **Rendering → Paint flashing** dikhate hain kya dobara paint hua.</Ur>
</Tr>

```text

  box-shadow: 0 12px 32px rgb(0 0 0 / 0.18);
  opacity: 0; transition: opacity 200ms ease-out;      /* animate opacity, not box-shadow */
}

.card:hover::after { opacity: 1; }
```

<Happened>
<Tr>
<En>The expensive shadow is painted once on `::after`; hover only animates its `opacity` and the card's `translate`, both compositor-friendly, so the lift stays smooth even on slow phones.</En>
<Ur>Mehanga shadow `::after` par ek dafa paint hota hai; hover sirf us ki `opacity` aur card ka `translate` animate karta hai, dono compositor ke liye aasan, isliye slow phones par bhi uthna hamwar rehta hai.</Ur>

<Step title="Keyframe animations">

<Tr>
<En>`@keyframes name { from {…} 50% {…} to {…} }` defines steps; `animation: pulse 2s ease-in-out 0s infinite alternate both running;` applies them. **iteration-count** is a number or `infinite`. **direction**: `normal`, `reverse`, `alternate` (forwards then back), `alternate-reverse`. **fill-mode**: `none` (default: own styles before and after), `forwards` (keep the last keyframe after), `backwards` (first keyframe during the delay), `both`. **play-state**: `running`/`paused`. Missing `from`/`to` use the element's current values. Common bug: an entrance animation that "jumps back" at the end because fill-mode is `none`; use `forwards`/`both` or make normal styles equal the last keyframe. Sampling:</En>
<Ur>`@keyframes name { from {…} 50% {…} to {…} }` qadam tay karta hai; `animation: pulse 2s ease-in-out 0s infinite alternate both running;` inhe lagata hai. **iteration-count** number ya `infinite`. **direction**: `normal`, `reverse`, `alternate` (aage phir peechhe), `alternate-reverse`. **fill-mode**: `none` (default: pehle aur baad apne styles), `forwards` (baad me aakhri keyframe), `backwards` (delay me pehla keyframe), `both`. **play-state**: `running`/`paused`. Ghayab `from`/`to` element ki maujooda values lete hain. Aam bug: aamad ki animation aakhir me "wapas uchhalti" hai kyun ke fill-mode `none` hai; `forwards`/`both` lein ya aam styles aakhri keyframe jaise rakhein. Jaanch:</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
@keyframes slide { from { translate: 0px; } to { translate: 100px; } }
.a { animation: slide 1000ms linear 2 alternate; }
.none { animation: slide 1000ms linear 500ms 1 none; }
.both { animation: slide 1000ms linear 500ms 1 both; }
</style><div class="a" id="alt"></div><div class="none" id="none"></div><div class="both" id="both"></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    # keep a reference to each animation: a finished animation with fill "none" disappears from getAnimations()
    page.evaluate("window.A = {}; document.querySelectorAll('div').forEach(e => { A[e.id] = e.getAnimations()[0]; A[e.id].pause(); })")
    def at(el, t):
        return page.eval_on_selector(el, f"e => {{ A[e.id].currentTime = {t}; return getComputedStyle(e).translate }}")
    print("alternate, 2 iterations:", [at("#alt", t) for t in [0, 500, 1000, 1500, 1999]])
    print("fill none (500ms delay):", [at("#none", t) for t in [0, 250, 1000, 1500, 2000]])
    print("fill both (500ms delay):", [at("#both", t) for t in [0, 250, 1000, 1500, 2000]])
    browser.close()
PY
```

fill both (500ms delay): ['0px', '0px', '50px', '100px', '100px']

<En>**alternate:** iteration one went 0 → 100px, iteration two came back (50px at 1500ms, almost 0 at 1999ms). **fill none:** during the 500ms delay the element showed its own style (`none`), was at 50px at 1000ms, and jumped back to `none` after the end. **fill both:** the first keyframe (0px) applied during the delay and the last (100px) was **kept** after the end.</En>
<Ur>**alternate:** pehli dafa 0 → 100px, doosri dafa wapas (1500ms par 50px, 1999ms par taqreeban 0). **fill none:** 500ms delay me element ne apna style (`none`) dikhaya, 1000ms par 50px tha, aur khatam hone ke baad wapas `none` par uchhla. **fill both:** delay me pehla keyframe (0px) laga aur aakhir ke baad aakhri (100px) **qaim** raha.</Ur>

<Step title="Entering and leaving: @starting-style and allow-discrete">

<Tr>
<En>Transitions don't run when an element first appears (no "before" value), and `display` is discrete. Two features, in all major browsers since 2024, fix this. **`@starting-style { … }`** defines the values to transition **from** when an element is first rendered or leaves `display: none`. **`transition-behavior: allow-discrete`** lets `display` (and `overlay` for top-layer elements) join a transition, so the element stays visible until the exit finishes. Use them for `<dialog>`, `popover`, toasts and anything toggled with `display: none` or `hidden`, previously done with JavaScript timers. Older browsers just show and hide. A popover that fades and scales, no JavaScript:</En>
<Ur>Element pehli dafa nazar aaye to transitions nahi chalti (koi "pehle" ki value nahi), aur `display` alag values wali hai. 2024 se tamam bare browsers me do features ye theek karte hain. **`@starting-style { … }`** wo values tay karta hai jin **se** transition shuru ho jab element pehli dafa bane ya `display: none` se nikle. **`transition-behavior: allow-discrete`** `display` (aur top-layer elements ke liye `overlay`) ko transition me shamil karta hai, isliye element nikalne ki animation khatam hone tak nazar aata hai. `<dialog>`, `popover`, toasts aur `display: none` ya `hidden` se toggle hone wali har cheez ke liye, jo pehle JavaScript timers se hota tha. Purane browsers bas dikhate chhupate hain. Mand aur chhota bara hone wala popover, bina JavaScript:</Ur>
</Tr>

```html preview h=220 noqa
<style>
  body { font-family: system-ui, sans-serif; }

    padding: 12px 16px; border: 1px solid #e5e7eb; border-radius: 10px;
    opacity: 0; scale: 0.95;
    transition: opacity 200ms ease-out, scale 200ms ease-out,
                display 200ms allow-discrete, overlay 200ms allow-discrete;
  }
  [popover]:popover-open { opacity: 1; scale: 1; }
  @starting-style {
    [popover]:popover-open { opacity: 0; scale: 0.95; }
  }
</style>
<button type="button" popovertarget="info">Delivery info</button>
<div id="info" popover>Orders before 2 pm arrive tomorrow.</div>
```

<Tr>
<En>Closed, the popover is transparent and slightly smaller; open (`:popover-open`), fully visible at normal size. `@starting-style` made opening start from opacity 0 and scale 0.95, and `display`/`overlay … allow-discrete` kept it rendered in the top layer until the closing transition ended, so closing animated too.</En>
<Ur>Band halat me popover shaffaf aur thora chhota hai; khula (`:popover-open`) poora nazar aata aam size par. `@starting-style` ne khulna opacity 0 aur scale 0.95 se shuru karaya, aur `display`/`overlay … allow-discrete` ne band hone ki transition khatam hone tak use top layer me rakha, isliye band hona bhi animate hua.</Ur>

<Step title="Animation events and the Web Animations API">

<Tr>
<En>Events: `transitionstart`, `transitionend`, `transitioncancel`, `animationstart`, `animationiteration`, `animationend`, `animationcancel`. The **Web Animations API** (`element.animate(keyframes, options)`) uses the same engine as CSS and returns an `Animation` with `play()`, `pause()`, `reverse()`, `finish()`, `cancel()`, `currentTime`, `playbackRate` and a `finished` promise. Use it to run code after an animation (remove a faded element) or animate runtime values; Motion (Framer Motion) builds on it. `transitionend` fires once **per property** and not at all if interrupted or nothing changed, so prefer `getAnimations()` with `finished` promises.</En>
<Ur>Events: `transitionstart`, `transitionend`, `transitioncancel`, `animationstart`, `animationiteration`, `animationend`, `animationcancel`. **Web Animations API** (`element.animate(keyframes, options)`) CSS wala engine istemal karti hai aur `play()`, `pause()`, `reverse()`, `finish()`, `cancel()`, `currentTime`, `playbackRate` aur `finished` promise wala `Animation` deti hai. Animation ke baad code chalane (mand hua element hatana) ya chalte waqt ki values animate karne ke liye; Motion (Framer Motion) isi par bani hai. `transitionend` **har property** par ek dafa chalta hai aur beech me rukne ya kuch na badalne par bilkul nahi, isliye `finished` promises ke saath `getAnimations()` behtar hai.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title><div id='toast'>Saved</div>")
    result = page.evaluate("""async () => {
        const el = document.getElementById('toast');
        const anim = el.animate(
            [{ opacity: 1, translate: '0 0' }, { opacity: 0, translate: '0 -20px' }],
            { duration: 300, easing: 'ease-in', fill: 'forwards' });
        anim.pause(); anim.currentTime = 150;
        const mid = { opacity: Number(getComputedStyle(el).opacity).toFixed(2), translate: getComputedStyle(el).translate.replace(/[\\d.]+px/g, m => parseFloat(m).toFixed(1) + 'px') };
        anim.play();
        await anim.finished;          // resolves when the animation ends
        const end = getComputedStyle(el).opacity;
        el.remove();
        return { mid, end, stillInPage: document.getElementById('toast') !== null };
    }""")
    print(result)
    browser.close()
PY
```

<Step title="Scroll-driven animations and view transitions">

<Tr>
<En>**Scroll-driven animations:** `animation-timeline: scroll()` (scroll progress of a container) or `view()` (an element crossing the viewport) drives a normal `@keyframes` animation by scroll instead of time: reading progress bars, fade-in on enter. **View transitions:** `document.startViewTransition(() => updateTheDOM())` (and `@view-transition { navigation: auto; }` for multi-page sites) animates between two page states, with cross-fades and elements morphing via `view-transition-name`. Both replace scroll listeners and heavy libraries and run off the main thread. Scroll-driven animations work in Chrome/Edge (2023) and Safari (2025), Firefox behind a flag at the time of writing; same-document view transitions are in all major browsers. Use them as enhancements. Scroll inside the box:</En>
<Ur>**Scroll-driven animations:** `animation-timeline: scroll()` (container ke scroll ki taraqqi) ya `view()` (element ka viewport se guzarna) aam `@keyframes` animation ko waqt ke bajaye scroll se chalata hai: parhne ki progress bars, aane par fade-in. **View transitions:** `document.startViewTransition(() => updateTheDOM())` (aur kai pages wali sites ke liye `@view-transition { navigation: auto; }`) page ki do halaton ke darmiyan animate karta hai, cross-fades aur `view-transition-name` se badalte elements ke saath. Dono scroll listeners aur bhari libraries ki jagah lete hain aur main thread se hat kar chalte hain. Scroll-driven animations Chrome/Edge (2023) aur Safari (2025) me, Firefox me likhte waqt flag ke peechhe; ek document wali view transitions tamam bare browsers me. Inhe izafi behtari ke taur par lein. Dabbe ke andar scroll karein:</Ur>

<Step title="Reduced motion and good motion design">

<Tr>
<En>`@media (prefers-reduced-motion: reduce)` is true when users asked their OS to minimise motion; for people with vestibular disorders motion can cause dizziness, nausea and headaches. Remove or replace large movement, parallax, zooms, spinning and auto-play (cross-fades are usually fine). Never flash more than three times per second (WCAG 2.3.1), give pause/stop controls for anything moving over 5 seconds (WCAG 2.2.2), and keep motion short and purposeful. Safest default: add movement **only** under `no-preference`:</En>
<Ur>`@media (prefers-reduced-motion: reduce)` tab sach hai jab users ne apne OS se harkat kam karne ka kaha ho; vestibular masail walon ke liye harkat chakkar, matli aur sar dard la sakti hai. Bari harkat, parallax, zoom, ghoomna aur khud chalne wali cheezen hatayen ya badlein (cross-fades aam taur par theek). Second me teen dafa se zyada kabhi na chamkayen (WCAG 2.3.1), 5 second se zyada hilne wali har cheez ke liye rokne ke controls dein (WCAG 2.2.2), aur harkat chhoti aur bamaqsad rakhein. Sab se mehfooz default: harkat **sirf** `no-preference` ke neeche dalein:</Ur>
</Tr>

```text
.card { transition: opacity 200ms ease-out; }                  /* always: subtle fade */
@media (prefers-reduced-motion: no-preference) {
  .card { transition: opacity 200ms ease-out, translate 200ms ease-out; }  /* movement only if OK */
  .card:hover { translate: 0 -4px; }
}
```

<Happened>
<Tr>
<En>Everyone gets the gentle opacity fade; only users who haven't asked for reduced motion also get the lift. Nothing breaks for either group.</En>
<Ur>Har kisi ko narm opacity fade milta hai; sirf wo users jinhone kam harkat nahi maangi uthne wala effect bhi paate hain. Kisi group ke liye kuch nahi toot ta.</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Janky, snapping and unconditional">

```text
.btn:hover { transition: all 600ms; background: #d97706; }  /* all + hover only + slow */
.menu { transition: left 300ms; } .menu.open { left: 0; }   /* layout every frame */
.panel { height: 0; transition: height 300ms; }
.panel.open { height: auto; }                                /* doesn't animate */
@keyframes in { from { opacity: 0; } to { opacity: 1; } }
.toast { opacity: 0; animation: in 300ms; }                  /* jumps back to 0 */
```

</Bad>
<Good title="Listed, transform-based, reduced-motion aware">

```text
.btn { transition: background-color 150ms ease-out; }
.menu { translate: -100% 0; transition: translate 250ms ease-out; }
.menu.open { translate: 0 0; }
.panel { display: grid; grid-template-rows: 0fr; transition: grid-template-rows 300ms; }
.panel.open { grid-template-rows: 1fr; }
.toast { opacity: 0; animation: in 300ms forwards; }
@media (prefers-reduced-motion: reduce) { .menu { transition: none; } }
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Durations that are too long** (500ms+) for everyday UI.
- **Trying to transition `display`** without `@starting-style` or `allow-discrete`.
- **Overusing `will-change`**, wasting memory on layers.
- **Auto-playing motion without pause controls.**
- **Relying on `transitionend`**, which never fires when the transition is interrupted.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Rozmarra UI ke liye bohot lambe durations** (500ms+).
- **`@starting-style` ya `allow-discrete` ke baghair `display` ko transition karna.**
- **`will-change` ka zyada istemal**, layers par memory zaya.
- **Rokne ke controls ke baghair khud chalne wali harkat.**
- **`transitionend` par bharosa**, jo transition beech me rukne par kabhi nahi chalta.

</Ur>
</Tr>

<DeepDive title="Real world: Reduce Motion and motion systems">

Apple's iOS 7 (2013) introduced heavy parallax and zooming transitions, and many users reported motion sickness; Apple added a "Reduce Motion" setting in response, and browsers later exposed it to websites as `prefers-reduced-motion`. On the web, motion design systems now publish explicit rules: Google's Material Design specifies durations (around 200–300ms for most UI changes) and standard easing curves, and IBM's Carbon distinguishes "productive" motion (quick, subtle, everyday UI) from "expressive" motion (important moments). Performance matters as much as style: many sites have improved interaction responsiveness by replacing JavaScript scroll handlers and `top`/`left` animations with transforms, opacity and, more recently, scroll-driven animations.

</DeepDive>

<DeepDive title="Security lens">

Motion can be used to mislead users, and animation timing can interact with security-sensitive actions.

- **Moving targets:** a button that moves or appears with a delay just as the user clicks can redirect the click to a different action (abused in clickjacking and in dark patterns that trick users into subscriptions). Keep confirm/cancel buttons stable, and ignore clicks on elements that became visible only milliseconds earlier for sensitive actions.
- **Hidden content during animations:** content with `opacity: 0` or translated off-screen is still in the page and focusable. Make closed menus and dialogs truly hidden (`display: none`, `hidden`, or `inert`) so keyboard users can't tab into invisible controls.
- **Timing-based UI deception:** countdown animations and fake "only 2 left!" pulses are manipulative patterns that consumer-protection regulators increasingly treat as deceptive.
- **Seizure safety:** flashing more than three times per second can trigger seizures; there have been real attacks posting flashing images to epilepsy support communities. Never let user-generated content auto-play flashing animations.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a CSS transition and a CSS animation?">
A transition animates a property between its old and new value when that value changes, for example on hover or when a class is added, so it needs a trigger and has only a start and an end. An animation uses keyframes to define any number of intermediate steps and runs by itself, with control over iteration count, direction, fill mode and play state.
</QA>

<QA q="Why should you animate transform and opacity instead of top, left, width or height?">
Changes to transform and opacity can usually be handled by the compositor on the GPU without recalculating layout or repainting, so they stay smooth. Changing geometric properties like top, left, width, height or margin forces layout and paint on every frame, which can affect large parts of the page and cause dropped frames, especially on slower devices.
</QA>

<QA q="What does animation-fill-mode do?">
It controls which styles apply outside the animation's active period. None, the default, uses the element's own styles before and after. Forwards keeps the final keyframe's values after the animation ends, backwards applies the first keyframe during the delay, and both does both.
</QA>

<QA q="How do you animate an element appearing from display none?">
Use the starting-style at-rule to define the initial values the element should transition from when it is first displayed, and set transition-behavior to allow-discrete for the display property, and for overlay with dialogs and popovers, so the element stays rendered until the exit transition finishes. Older approaches toggled classes with JavaScript timers.
</QA>

<QA q="How do you make animations accessible?">
Respect the prefers-reduced-motion media query by removing or reducing large movements, parallax and auto-playing animations, keep durations short and motion purposeful, avoid flashing more than three times per second, provide controls to pause anything that moves for more than five seconds, and make sure content hidden by animation is also hidden from keyboard and screen-reader users.
</QA>

</DeepDive>
