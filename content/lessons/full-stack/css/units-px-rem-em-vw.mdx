<Callout type="tip" title="In one minute">
CSS lengths are **absolute** (`px`; also `cm`, `in`, `pt`, rarely used on screens) or **relative** to something else. **`rem`** is relative to the **root** (`<html>`) font size: 16px by default, and larger if the user increased their browser's font size, so `rem` is the best default for **font sizes and most spacing**. **`em`** is relative to the **current element's** font size (or the parent's, for `font-size` itself), so it **compounds** when nested: handy for padding inside buttons, risky for font sizes. **`%`** depends on the property: widths use the parent's width, `font-size` uses the parent's font size, `translate` uses the element's own size. **`vw`/`vh`** are 1% of the viewport width/height; on phones use **`dvh`**/**`svh`** for full-height sections. **`ch`** (width of "0") is great for readable line lengths (`max-width: 65ch`). Use **`px`** for things that shouldn't scale with text (borders, shadows), and combine units with **`calc()`**, **`min()`**, **`max()`** and **`clamp()`**.
</Callout>

## Start from zero

<Callout type="analogy">
Measuring in `px` is like giving directions in **metres**: always the same. Measuring in `rem` is like measuring in **"hand widths of the head of the family"**: if the head of the family has bigger hands (the user set a bigger font), everything measured that way grows together. `em` is "hand widths of **whoever is standing next to you**": if each person in a chain stands next to someone slightly bigger, sizes keep growing down the chain (compounding). `vw` is "a hundredth of the **room's** width": move to a bigger room (screen), and everything measured that way grows.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Absolute unit** | Fixed length | `px` |
| **Relative unit** | Length based on something else | `rem`, `em`, `%`, `vw` |
| **CSS pixel** | Reference unit, about 1/96 of an inch at arm's length | `1px` |
| **Root font size** | Font size of `<html>` | 16px by default |
| **rem** | Root em: multiples of the root font size | `1.5rem` = 24px |
| **em** | Multiples of the element's font size | `0.5em` |
| **vw / vh** | 1% of viewport width / height | `100vw` |
| **ch** | Width of the "0" character | `65ch` |
| **Computed value** | The final pixel value the browser uses | `24px` |
| **calc()** | Arithmetic with mixed units | `calc(100% - 2rem)` |

## What is it?

The main units side by side, with a 16px root font size:

| Unit | Relative to | 1 unit = (typical) | Good for |
| --- | --- | --- | --- |
| `px` | Nothing (fixed) | 1px | Borders, shadows, small fixed details |
| `rem` | Root (`html`) font size | 16px | Font sizes, spacing, most sizes |
| `em` | Element's font size | depends | Padding/margins that scale with the element's text |
| `%` | Depends on the property (usually the parent) | depends | Widths, fluid layouts |
| `vw` / `vh` | Viewport width / height | 1% of the screen | Full-screen sections, fluid type (with rem) |
| `dvh` / `svh` / `lvh` | Dynamic / small / large viewport height | 1% | Mobile full-height sections |
| `ch` | Width of "0" in the current font | ~0.5em | Line lengths, input widths |
| `lh` | Element's line height | depends | Vertical rhythm |
| `cqi` / `cqw` | Container inline size / width | 1% of container | Component sizes in container queries |

## Why does it matter?

- **Accessibility:** many users set a larger default font in their browser (Settings → Appearance → Font size). Sizes in `px` ignore that setting; sizes in `rem` respect it. WCAG requires text to be resizable to 200% without breaking.
- **Responsiveness:** relative units let layouts adapt without media queries for every size.
- **Consistency:** design systems define spacing and type scales in `rem`, so everything scales together.
- **Bugs:** "why is this text getting bigger and bigger in nested lists?" (em compounding), "why is my 100vh section cut off on the phone?" (mobile browser bars) and "why is my 100vw element causing horizontal scrolling?" (scrollbars) are all unit questions.

## When and where do you use it?

Every time you write a length in CSS. The quick rules at the end of this lesson cover the everyday choices.

## Concepts one by one

### 1. px: the CSS pixel

<Explain>
<What>
`px` is an absolute unit, but a CSS pixel is **not** a physical screen pixel. It's defined so that things look about the same size on different devices: on a phone with a device pixel ratio of 3, one CSS pixel is drawn with 3 × 3 physical pixels. `1in` is always `96px`, `1cm` ≈ `37.8px`, `1pt` = `1.333px` (these physical units are mostly useful for print stylesheets).
</What>
<Why>
Pixels are predictable: `1px` borders stay thin, shadows stay crisp.
</Why>
<When>
Borders (`1px solid`), outlines, box shadows, small icons, hairline dividers, `border-radius` (either px or rem is fine).
</When>
<Where>
Avoid `px` for font sizes and for spacing tied to text: it doesn't respond to the user's font-size preference (browser **zoom** still scales px, but the font-size setting doesn't).
</Where>
<How>
Converting physical units in a real browser:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
units = ["1in", "1cm", "1mm", "1pt", "1pc", "1px"]
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title><div id='d'></div>")
    for u in units:
        w = page.eval_on_selector("#d", "(e, u) => { e.style.width = u; return getComputedStyle(e).width }", u)
        print(f"{u:4} = {w}")
    browser.close()
PY
```

```text output
1in  = 96px
1cm  = 37.7812px
1mm  = 3.76562px
1pt  = 1.32812px
1pc  = 16px
1px  = 1px
```

Line by line:

- The browser converts every absolute unit to CSS pixels using the fixed ratio 1in = 96px, so 1cm is mathematically 37.795px. Chromium then stores layout sizes in steps of 1/64 px, which is why it reports 37.7812px.
- A `1cm` element is not exactly 1cm on your physical screen (that depends on the screen), but it is exactly 1cm when printed at 100%.
- `pt` (points) and `pc` (picas) come from print typography; `12pt` = 16px.

### 2. rem: relative to the root font size

<Explain>
<What>
`1rem` equals the computed `font-size` of the `<html>` element. Browsers default to **16px**, but users can change that in settings (e.g. to 20px). So `1.5rem` = 24px by default, 30px for that user.
</What>
<Why>
`rem` gives you one scaling factor for the whole page, controlled by the user's preference. It doesn't compound, because every `rem` refers to the same root.
</Why>
<When>
Font sizes, spacing (padding, margin, gap), max-widths of containers, media-query breakpoints. Most design systems and Tailwind (`p-4` = `1rem`) use rem.
</When>
<Where>
Don't set `html { font-size: 16px; }` in pixels: that overrides the user's choice. If you change the root size at all, use a percentage (`html { font-size: 100%; }` is the default). The old trick `html { font-size: 62.5% }` (to make 1rem = 10px) works but makes every third-party component tiny; it's rarely worth it now.
</Where>
<How>
Simulating a user who set their default font to 20px (125%), and comparing px with rem:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.px  { font-size: 18px; padding: 16px; }
.rem { font-size: 1.125rem; padding: 1rem; }
</style>
<p class="px">Sized in px</p><p class="rem">Sized in rem</p>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    for root in ["100%", "125%"]:
        page.set_content(html.replace("<style>", f"<style>html {{ font-size: {root}; }}"))
        rootpx = page.evaluate("getComputedStyle(document.documentElement).fontSize")
        for cls in [".px", ".rem"]:
            fs, pad = page.eval_on_selector(cls, "e => [getComputedStyle(e).fontSize, getComputedStyle(e).paddingTop]")
            print(f"user setting {rootpx:5} {cls:5} font-size {fs:6} padding {pad}")
    browser.close()
PY
```

```text output
user setting 16px  .px   font-size 18px   padding 16px
user setting 16px  .rem  font-size 18px   padding 16px
user setting 20px  .px   font-size 18px   padding 16px
user setting 20px  .rem  font-size 22.5px padding 20px
```

Line by line:

- With the default 16px root, `18px` and `1.125rem` (1.125 × 16) look identical.
- A user who chose a 20px default font (here simulated with `html { font-size: 125% }`): the `px` text **ignores** their choice and stays 18px, while the `rem` text grows to 22.5px and its padding to 20px, keeping the same proportions.

### 3. em: relative to the element's font size

<Explain>
<What>
- For **`font-size`**, `1em` is the **parent's** font size (`font-size: 1.5em` = 1.5 × parent).
- For **every other property**, `1em` is the element's **own** computed font size (`padding: 0.5em` on a 20px button = 10px).
</What>
<Why>
Components scale as a unit: a button's padding in `em` stays proportional when you make the button's text larger.
</Why>
<When>
Padding and margins inside components (buttons, badges, tags), icon sizes next to text (`width: 1em`), spacing around headings (`margin-bottom: 0.5em`), letter-spacing.
</When>
<Where>
**Compounding:** nested elements with `font-size` in `em` multiply: a list item with `font-size: 1.2em` inside another such list item is 1.2 × 1.2 = 1.44 times the base, and so on. Use `rem` for font sizes to avoid it.
</Where>
<How>
Nested lists with `em` vs `rem` font sizes, and an em-based button:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.em li  { font-size: 1.2em; }
.rem li { font-size: 1.2rem; }
.btn { padding: 0.5em 1em; }
.btn.small { font-size: 0.875rem; }
.btn.large { font-size: 1.25rem; }
</style>
<ul class="em"><li id="e1">Level 1<ul><li id="e2">Level 2<ul><li id="e3">Level 3</li></ul></li></ul></li></ul>
<ul class="rem"><li id="r1">Level 1<ul><li id="r2">Level 2<ul><li id="r3">Level 3</li></ul></li></ul></li></ul>
<button class="btn small" type="button">Small</button><button class="btn large" type="button">Large</button>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for prefix, label in [("e", "1.2em"), ("r", "1.2rem")]:
        sizes = [page.eval_on_selector(f"#{prefix}{i}", "e => getComputedStyle(e).fontSize") for i in (1, 2, 3)]
        print(f"font-size {label:6} by level: {sizes}")
    for cls in [".small", ".large"]:
        fs, pt, pl = page.eval_on_selector(f".btn{cls}", "e => { const s = getComputedStyle(e); return [s.fontSize, s.paddingTop, s.paddingLeft] }")
        print(f"button {cls:7} font {fs:5} padding {pt} {pl}")
    browser.close()
PY
```

```text output
font-size 1.2em  by level: ['19.2px', '23.04px', '27.648px']
font-size 1.2rem by level: ['19.2px', '19.2px', '19.2px']
button .small  font 14px  padding 7px 14px
button .large  font 20px  padding 10px 20px
```

Line by line:

- With `1.2em`, each level multiplies its parent's size: 16 × 1.2 = 19.2, then × 1.2 = 23.04, then 27.648px. Deeply nested lists or comments become huge.
- With `1.2rem`, every level is 1.2 × the root: always 19.2px.
- The buttons share `padding: 0.5em 1em`. The small one (14px text) gets 7px × 14px padding, the large one (20px text) 10px × 20px: the padding scales with the text automatically, so both look proportionally the same.

### 4. Percentages: relative to what?

<Explain>
<What>
A percentage's reference depends on the property:
| Property | % of… |
| --- | --- |
| `width`, `max-width`, `left`, `right`, `margin-*`, `padding-*` (**all four sides**) | the containing block's **width** |
| `height`, `top`, `bottom` | the containing block's **height** (only if that height is definite) |
| `font-size` | the parent's font size |
| `line-height` | the element's own font size |
| `translate`, `transform: translate()` | the element's **own** size |
| `border-radius` | the element's own size (width for horizontal, height for vertical radius) |
| `background-position` | (container size − image size) |
</What>
<Why>
Most "percentage doesn't work" bugs come from the wrong reference: `height: 50%` inside a parent with `height: auto` does nothing, and `padding-top: 10%` is 10% of the **width**, not the height.
</Why>
<When>
Fluid widths, centring with `translate(-50%, -50%)`, circles with `border-radius: 50%`.
</When>
<Where>
The old "padding-top: 56.25%" trick for 16:9 boxes relied on vertical padding using the width; today use `aspect-ratio: 16 / 9`.
</Where>
<How>
The same `50%` on different properties of one element inside a 400 × 200 parent:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.parent { width: 400px; height: 200px; font-size: 20px; position: relative; }
.auto-parent { width: 400px; }
.child { width: 50%; height: 50%; padding-top: 10%; font-size: 50%; translate: 50% 0; border-radius: 50%; position: absolute; top: 50%; }
.child2 { height: 50%; }
</style>
<div class="parent"><div class="child" id="c">x</div></div>
<div class="auto-parent"><div class="child2" id="c2">x</div></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    s = page.eval_on_selector("#c", """e => { const s = getComputedStyle(e); return {
        width: s.width, height: s.height, paddingTop: s.paddingTop, fontSize: s.fontSize,
        top: s.top, translate: s.translate, borderRadius: s.borderRadius } }""")
    for k, v in s.items():
        print(f"{k:12} 50% (or 10%) -> {v}")
    print("height: 50% in an auto-height parent ->", page.eval_on_selector("#c2", "e => getComputedStyle(e).height"))
    browser.close()
PY
```

```text output
width        50% (or 10%) -> 200px
height       50% (or 10%) -> 100px
paddingTop   50% (or 10%) -> 40px
fontSize     50% (or 10%) -> 10px
top          50% (or 10%) -> 100px
translate    50% (or 10%) -> 50%
borderRadius 50% (or 10%) -> 50%
height: 50% in an auto-height parent -> 18px
```

Line by line:

- `width: 50%` is half the parent's 400px width; `height: 50%` is half its 200px height; `top: 50%` is also half the height.
- `padding-top: 10%` is 40px: 10% of the parent's **width** (400px), not its height.
- `font-size: 50%` is half the parent's 20px font.
- `translate` and `border-radius` keep their percentage in the computed style, because they depend on the element's own size, which is known only at layout time.
- `height: 50%` inside a parent with automatic height is ignored (treated as `auto`), so the child is just its content's height (18px).

### 5. Viewport units: vw, vh, dvh, svh, lvh

<Explain>
<What>
- `1vw` = 1% of the viewport width; `1vh` = 1% of the viewport height; `vmin`/`vmax` = the smaller/larger of the two.
- On mobile, the browser's address bar shows and hides as you scroll, so the "viewport height" changes. Newer units make this explicit:
  - `svh`: **small** viewport height (bars visible): always fits.
  - `lvh`: **large** viewport height (bars hidden).
  - `dvh`: **dynamic**: changes as the bars move.
  - Plain `vh` behaves like `lvh` on mobile, so `100vh` can be taller than what's visible.
- Logical versions exist too: `vi` / `vb`, `svi`, `dvb` etc.
</What>
<Why>
Full-screen heroes, sticky footers, modals sized to the screen, fluid typography.
</Why>
<When>
- Full-height sections: `min-height: 100svh` (or `100dvh`).
- Fluid sizes: always combine with rem in `clamp()`.
</When>
<Where>
**`100vw` includes the vertical scrollbar** on desktop browsers with classic scrollbars, so `width: 100vw` is wider than the page and causes horizontal scrolling. Use `width: 100%` for full-width elements.
</Where>
<How>
Measuring viewport units on a page with a classic scrollbar:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
body { margin: 0; } .tall { height: 2000px; }
html { scrollbar-gutter: stable; }   /* reserve scrollbar space, like a classic Windows scrollbar */
#vw { width: 100vw; } #pct { width: 100%; } #vh { height: 100vh; width: 10px; } #half { width: 50vmin; }
</style><div id="vw"></div><div id="pct"></div><div id="vh"></div><div id="half"></div><div class="tall"></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 1000, "height": 600})
    page.set_content(html)
    print("window.innerWidth:", page.evaluate("innerWidth"), " page width (without scrollbar):", page.evaluate("document.body.clientWidth"))
    for el in ["#vw", "#pct", "#vh", "#half"]:
        w, h = page.eval_on_selector(el, "e => [e.offsetWidth, e.offsetHeight]")
        print(f"{el:5} {w}x{h}")
    print("100vw sticks out past the page by:", page.evaluate("document.querySelector('#vw').offsetWidth - document.body.clientWidth"), "px")
    browser.close()
PY
```

```text output
window.innerWidth: 1000  page width (without scrollbar): 985
#vw   1000x0
#pct  985x0
#vh   10x600
#half 300x0
100vw sticks out past the page by: 15 px
```

Line by line:

- This headless browser uses overlay scrollbars that take no space (like macOS and phones), so `scrollbar-gutter: stable` reserves the 15px a classic Windows scrollbar would take.
- The window is 1000px wide, but the 15px vertical scrollbar leaves 985px for the page.
- `100vw` is 1000px: it **includes** the scrollbar, so the element is 15px wider than the page and creates a horizontal scrollbar.
- `100%` is 985px and fits.
- `100vh` is the full 600px viewport height.
- `50vmin` is 50% of the smaller dimension (600px): 300px.

### 6. ch, ex, lh and other font-relative units

<Explain>
<What>
- **`ch`**: width of the "0" glyph in the element's font. About 0.5em in most fonts, exactly 1 character in monospace fonts.
- **`ex`**: height of the lowercase "x".
- **`lh`**: the element's computed line height; **`rlh`** the root's.
- **`cap`**: height of capital letters; **`ic`**: width of a CJK ideograph.
</What>
<Why>
`max-width: 65ch` keeps paragraphs at a comfortable 60–75 characters per line whatever the font size. `lh` lets spacing match the text rhythm.
</Why>
<When>
Text containers, input widths (`width: 6ch` for a postcode field), code blocks, spacing between paragraphs (`margin-block: 1lh`).
</When>
<Where>
`ch` varies with the font, so `65ch` in a narrow font is narrower than in a wide one; that's the point.
</Where>
<How>
`ch` in different fonts and sizes:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
p { max-width: 65ch; margin: 0; }
#mono { font-family: monospace; font-size: 16px; }
#sans { font-family: sans-serif; font-size: 16px; }
#big  { font-family: sans-serif; font-size: 20px; }
#lh   { font-size: 16px; line-height: 1.5; margin-block-end: 1lh; }
</style>
<p id="mono">mono</p><p id="sans">sans</p><p id="big">big</p><p id="lh">lh</p>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 1400, "height": 600})
    page.set_content(html)
    for el in ["#mono", "#sans", "#big"]:
        w = page.eval_on_selector(el, "e => e.getBoundingClientRect().width")
        print(f"{el:6} 65ch = {w:.1f}px  (1ch = {w / 65:.2f}px)")
    print("#lh    margin-block-end 1lh =", page.eval_on_selector("#lh", "e => getComputedStyle(e).marginBottom"))
    browser.close()
PY
```

```text output
#mono  65ch = 626.1px  (1ch = 9.63px)
#sans  65ch = 578.4px  (1ch = 8.90px)
#big   65ch = 723.0px  (1ch = 11.12px)
#lh    margin-block-end 1lh = 24px
```

Line by line:

- The paragraphs have no text long enough to fill them, so their width equals `max-width` (the viewport is wider): that's 65 times the "0" width of each font.
- In the 16px monospace font, "0" is about 9.63px wide; in the 16px sans-serif font, 8.90px; at 20px it scales up to 11.12px.
- `1lh` equals the line height: 16px × 1.5 = 24px, so the paragraph is followed by exactly one blank line of space.

### 7. Unitless line-height

<Explain>
<What>
`line-height` accepts a number without a unit (`1.5`), a length (`24px`, `1.5rem`), or a percentage/em.
</What>
<Why>
With a **unitless** number, children inherit the **ratio** and recompute it for their own font size. With `em`, `%` or `px`, children inherit the **computed pixels**, so a large heading inside a container with `line-height: 1.5em` (computed from the container's small font) gets cramped lines that overlap.
</Why>
<When>
Always use unitless line-height: `body { line-height: 1.5; }`, headings around `1.1–1.25`.
</When>
<Where>
This is one of the few places where "no unit" is the best unit.
</Where>
<How>
A 32px heading inside a 16px container:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.box { font-size: 16px; } h2 { font-size: 32px; margin: 0; }
#a { line-height: 1.5; } #b { line-height: 1.5em; } #c { line-height: 150%; }
</style>
<div class="box" id="a"><h2>Unitless</h2></div><div class="box" id="b"><h2>em</h2></div><div class="box" id="c"><h2>percent</h2></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for el, label in [("#a", "1.5"), ("#b", "1.5em"), ("#c", "150%")]:
        print(f"container line-height {label:6} -> h2 (32px) line-height {page.eval_on_selector(el + ' h2', 'e => getComputedStyle(e).lineHeight')}")
    browser.close()
PY
```

```text output
container line-height 1.5    -> h2 (32px) line-height 48px
container line-height 1.5em  -> h2 (32px) line-height 24px
container line-height 150%   -> h2 (32px) line-height 24px
```

Line by line:

- **Unitless 1.5:** the heading inherits the ratio and computes 32 × 1.5 = 48px. Correct.
- **1.5em** and **150%:** the container computes 16 × 1.5 = 24px, and the heading inherits **24px**: less than its own 32px font size, so lines of a wrapped heading would overlap.

### 8. calc(), min(), max() and clamp()

<Explain>
<What>
- **`calc()`** does arithmetic with mixed units: `calc(100% - 2rem)`, `calc(100vh - 64px)`. Spaces around `+` and `-` are required.
- **`min(a, b, …)`** picks the smallest: `width: min(100%, 600px)` = "600px, but never wider than the container".
- **`max(a, b, …)`** picks the largest: `padding: max(1rem, 3vw)`.
- **`clamp(min, preferred, max)`** = `max(min, min(preferred, max))`.
</What>
<Why>
They replace many media queries and make sizes adapt smoothly.
</Why>
<When>
Container widths (`min(100% - 2rem, 1200px)`), fluid spacing and type, sizes that subtract a header height, sidebars.
</When>
<Where>
`calc()` can be nested inside the others and used with CSS variables: `calc(var(--space) * 2)`.
</Where>
<How>
Evaluated at two screen widths:
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
body { margin: 0; }
#calc  { width: calc(100% - 2rem); }
#min   { width: min(100%, 600px); }
#max   { width: max(50%, 300px); }
#clamp { width: clamp(280px, 60%, 720px); }
#wrap  { width: min(100% - 2rem, 1200px); margin-inline: auto; }
</style><div id="calc"></div><div id="min"></div><div id="max"></div><div id="clamp"></div><div id="wrap"></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    for width in [375, 1440]:
        page = browser.new_page(viewport={"width": width, "height": 600})
        page.set_content(html)
        sizes = {el: page.eval_on_selector(el, "e => e.offsetWidth") for el in ["#calc", "#min", "#max", "#clamp", "#wrap"]}
        print(f"screen {width:4}px:", "  ".join(f"{k}={v}" for k, v in sizes.items()))
        page.close()

```

```text output
screen  375px: #calc=343  #min=375  #max=300  #clamp=280  #wrap=343
screen 1440px: #calc=1408  #min=600  #max=720  #clamp=720  #wrap=1200
```

Line by line:

- `calc(100% - 2rem)`: 375 − 32 = 343px; 1440 − 32 = 1408px.
- `min(100%, 600px)`: the full 375px on the phone, capped at 600px on the desktop.
- `max(50%, 300px)`: 50% of 375 is 187.5, so the 300px minimum wins; on the desktop 50% = 720px wins.
- `clamp(280px, 60%, 720px)`: 60% of 375 = 225 is below 280, so 280px; 60% of 1440 = 864 is above 720, so 720px.
- `min(100% - 2rem, 1200px)` (no `calc` needed inside `min`) is a one-line responsive container: 16px of space on each side on phones, a 1200px maximum on desktops.

### 9. Choosing units: practical rules

<Explain>
<What>
| What | Recommended | Why |
| --- | --- | --- |
| Font sizes | `rem` (`clamp()` with rem + vw for headings) | Respects user settings, no compounding |
| Spacing (padding, margin, gap) | `rem`; `em` inside components | Scales with text |
| Borders, outlines, shadows | `px` | Should stay thin and crisp |
| Layout widths | `%`, `fr`, `min()`, `max-width` in rem or ch | Fluid |
| Text column width | `ch` (`max-width: 65ch`) | Readable line length |
| Line height | Unitless (`1.5`) | Correct inheritance |
| Full-screen heights | `svh` / `dvh` (fallback `vh`) | Mobile browser bars |
| Breakpoints | `px` or `em`/`rem` | `em` follows the user's font size |
| Component-relative sizes | `cqi` in container queries | Size relative to the component |
| Icons next to text | `em` (`width: 1em; height: 1em`) | Match the text size |
</What>
<Why>
These defaults avoid the most common accessibility and responsive bugs.
</Why>
<When>
Start from these and break the rules only with a reason.
</When>
<Where>
Design tools usually give values in px; convert by dividing by 16 (24px → 1.5rem). Tailwind's spacing scale does it for you (`p-6` = 1.5rem = 24px).
</Where>
<How>
In media queries, `rem`/`em` refer to the browser's default font size (not your `html` rule), so `@media (min-width: 48em)` is 768px for most users and scales for users with larger text.
</How>
</Explain>

## Real-world example

For years, many sites set font sizes in px. When browsers added page zoom (which scales px too), it seemed not to matter. But browser **font-size settings** (used by many older and low-vision users, and by Android's system font size in some browsers) only scale relative units. Accessibility audits frequently flag px-based text that doesn't respond to these settings, and GOV.UK's design system, Bootstrap 5 and Tailwind all moved to rem-based type and spacing scales. Another famous bug: the iOS Safari `100vh` problem, where full-screen hero sections were cut off behind the browser's toolbar; the `svh`/`dvh`/`lvh` units were added to CSS in 2022 specifically to solve it, and are now supported in all major browsers.

## Common mistakes

- **Font sizes in px,** ignoring user font settings.
- **Setting `html { font-size: 10px }` or other px values** on the root.
- **em font sizes in nested components,** causing compounding.
- **`width: 100vw`** causing horizontal scrolling because of the scrollbar.
- **`height: 100vh` on mobile** hiding content behind browser bars.
- **Percentage heights in auto-height parents,** which do nothing.
- **Forgetting that vertical padding/margin percentages use the width.**
- **Line height with units,** causing cramped headings.
- **Pure `vw` font sizes** that are tiny on phones and don't respond to zoom; use `clamp()` with rem.
- **Missing spaces in calc:** `calc(100%-2rem)` is invalid.

## Security lens

<Callout type="security">
Units don't create vulnerabilities by themselves, but sizing decisions can hide information or break security UI for some users.
</Callout>

- **Readable security text:** warnings, consent text, transaction amounts and permission prompts must scale with the user's font settings (use rem) and never be shrunk with tiny fixed sizes; regulators treat unreadable "fine print" as deceptive.
- **Zoom and reflow:** users at 200–400% zoom (or large font settings) must still see full URLs, recipients and confirm/cancel buttons; viewport-sized containers (`height: 100vh; overflow: hidden`) can cut them off.
- **Tiny invisible elements:** `font-size: 0`, `1px` × `1px` boxes or `0.01rem` text can hide content from sighted users while keeping it in the page, a technique used in phishing emails and hidden-text SEO spam. Don't use these tricks for anything users need to see, and expect security filters to flag them.

## Interview questions

<QA q="What is the difference between rem and em?">
Rem is relative to the root element's font size, so it's consistent everywhere on the page and respects the user's default font size. Em is relative to the font size of the current element, or of the parent when used in font-size itself, so it scales with local text but compounds when nested elements also use em for font sizes.
</QA>

<QA q="Why should font sizes be in rem rather than px?">
Browsers let users set a default font size, and rem values scale with it while px values ignore it. Using rem for text and most spacing keeps the layout proportional for users who need larger text, which supports accessibility requirements for resizable text.
</QA>

<QA q="What do percentages refer to in CSS?">
It depends on the property. Widths, horizontal offsets and all margins and paddings, even vertical ones, refer to the containing block's width. Heights and vertical offsets refer to its height, but only if that height is definite. Font-size refers to the parent's font size, line-height to the element's own font size, and translate and border-radius to the element's own dimensions.
</QA>

<QA q="What problem do dvh, svh and lvh solve?">
On mobile browsers, the visible viewport height changes as address and tool bars appear and disappear, so 100vh may be taller than the visible area and hide content. The small viewport unit always fits with bars visible, the large unit assumes bars are hidden, and the dynamic unit updates as the bars move.
</QA>

<QA q="What does clamp() do and how would you use it for typography?">
Clamp takes a minimum, a preferred and a maximum value and returns the preferred value limited to that range. For fluid typography you combine a rem part with a viewport part as the preferred value, for example 1rem plus 3vw, and set rem minimum and maximum sizes, so text scales smoothly between screen sizes while still respecting user font settings and staying within readable limits.
</QA>

## Key terms

<Terms>
  <Term name="Absolute unit">Fixed length such as px.</Term>
  <Term name="CSS pixel">Reference unit of 1/96 inch, independent of device pixels.</Term>
  <Term name="rem">Multiple of the root element's font size.</Term>
  <Term name="em">Multiple of the element's or parent's font size.</Term>
  <Term name="Compounding">Nested em font sizes multiplying each other.</Term>
  <Term name="Viewport units">vw, vh, vmin and vmax, percentages of the viewport.</Term>
  <Term name="Dynamic viewport units">dvh, svh and lvh for changing mobile viewports.</Term>
  <Term name="ch">Width of the zero character in the current font.</Term>
  <Term name="lh">The element's computed line height.</Term>
  <Term name="Unitless line-height">Ratio inherited and recomputed per element.</Term>
  <Term name="calc()">Arithmetic combining different units.</Term>
  <Term name="clamp()">Value limited between a minimum and maximum.</Term>
</Terms>
