<BigIdea>
<Tr>
<En>
CSS lengths are **absolute** (`px`) or **relative** to something else. **`rem`** follows the **root** font size (16px by default, larger if the user raised it), so it's the best default for **font sizes and most spacing**. **`em`** follows the **current element's** font size (the parent's, for `font-size` itself), so it **compounds** when nested: great for padding inside buttons, risky for font sizes. **`%`** depends on the property: widths use the parent's width, `font-size` the parent's font, `translate` the element's own size. **`vw`/`vh`** are 1% of the viewport; on phones use **`dvh`**/**`svh`** for full-height sections. **`ch`** gives readable line lengths (`max-width: 65ch`). Use **`px`** for things that shouldn't scale (borders, shadows), and combine units with **`calc()`**, **`min()`**, **`max()`**, **`clamp()`**.
</En>
<Ur>
CSS ki lambaiyan **absolute** (`px`) ya kisi aur cheez ke **nisbat** hoti hain. **`rem`** **root** font size ke saath chalta hai (default 16px, user barhaye to zyada), isliye **font sizes aur zyada tar faasle** ke liye behtareen default hai. **`em`** **maujooda element** ke font size ke saath chalta hai (`font-size` me parent ka), isliye nested hone par **zarb** hota jata hai: buttons ke andar padding ke liye zabardast, font sizes ke liye khatarnak. **`%`** property par munhasir hai: chaurai parent ki chaurai, `font-size` parent ka font, `translate` element ka apna size. **`vw`/`vh`** viewport ka 1% hain; phones par poori oonchai ke hisson ke liye **`dvh`**/**`svh`**. **`ch`** parhne ke qabil line ki lambai deta hai (`max-width: 65ch`). Na barhne wali cheezon (borders, shadows) ke liye **`px`**, aur units ko **`calc()`**, **`min()`**, **`max()`**, **`clamp()`** se milayen.
</Ur>

<Why>
<Tr>
<En>

- **Accessibility:** many users raise their browser's default font size; `px` ignores it, `rem` respects it. WCAG requires text resizable to 200% without breaking.
- **Responsiveness:** relative units adapt without a media query per size.
- **Consistency:** design systems define spacing and type scales in `rem`, so everything scales together.
- **Bugs:** text growing in nested lists (em compounding), `100vh` cut off on phones, `100vw` causing sideways scroll: all unit questions.

</En>
<Ur>

- **Rasai:** kai users browser ka default font size barhate hain; `px` use nazar andaz karta hai, `rem` maanta hai. WCAG text ko bina toote 200% tak barhne ke qabil maangta hai.
- **Responsiveness:** nisbati units har size ki media query ke baghair dhal jati hain.
- **Yaksaniyat:** design systems faasle aur text ke paimane `rem` me rakhte hain, taa ke sab ikattha barhe.
- **Bugs:** nested lists me barhta text (em ka zarb), phones par kata `100vh`, side scroll karata `100vw`: sab units ke sawal hain.

## Picture it

<Tr>
<En>

Measuring in `px` is like directions in **metres**: always the same. `rem` is like measuring in **"hand widths of the head of the family"**: if the head has bigger hands (the user set a bigger font), everything measured that way grows together. `em` is "hand widths of **whoever is next to you**": if each person in a chain stands next to someone slightly bigger, sizes keep growing down the chain (compounding). `vw` is "a hundredth of the **room's** width": move to a bigger room (screen) and everything grows.

</En>
<Ur>

`px` me naapna **meter** me raasta batane jaisa hai: hamesha wahi. `rem` **"ghar ke sarbarah ke haath ki chaurai"** me naapna hai: sarbarah ke haath bare (user ne bara font rakha) to is tarah naapi har cheez ikatthe barhti hai. `em` "**saath khare shakhs** ke haath ki chaurai" hai: zanjeer me har koi thore bare ke saath khara ho to neeche jate hue size barhte jate hain (zarb). `vw` "**kamre** ki chaurai ka sauwan hissa" hai: bare kamre (screen) me jao to sab barh jata hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="px: the CSS pixel">

<Tr>
<En>`px` is absolute, but a CSS pixel is **not** a physical pixel: it's defined so things look about the same size everywhere (on a DPR 3 phone, one CSS pixel is 3 × 3 physical pixels). `1in` is always `96px`, `1cm` ≈ `37.8px`, `1pt` = `1.333px`; physical units are mostly for print. Pixels are predictable, so use them for borders, outlines, shadows, hairlines and small icons. Avoid them for font sizes and text-related spacing: they ignore the user's font-size setting (browser **zoom** scales px, the font-size setting doesn't).</En>
<Ur>`px` absolute hai, magar CSS pixel physical pixel **nahi**: ye aise tay hai ke cheezen har jagah taqreeban ek size ki dikhen (DPR 3 phone par ek CSS pixel 3 × 3 physical pixels). `1in` hamesha `96px`, `1cm` ≈ `37.8px`, `1pt` = `1.333px`; physical units zyada tar print ke liye. Pixels umeed ke mutabiq hain, isliye borders, outlines, shadows, bareek lakeeron aur chhote icons ke liye. Font sizes aur text se jure faasle ke liye in se bachen: ye user ki font-size setting nazar andaz karte hain (browser **zoom** px barhata hai, font-size setting nahi).</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
units = ["1in", "1cm", "1mm", "1pt", "1pc", "1px"]
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title><div id='d'></div>")
    for u in units:
        w = page.eval_on_selector("#d", "(e, u) => { e.style.width = u; return getComputedStyle(e).width }", u)
        print(f"{u:4} = {w}")
    browser.close()
PY
```

```text output
1in  = 96px
1cm  = 37.7812px
1mm  = 3.76562px
1pt  = 1.32812px
1pc  = 16px
1px  = 1px
```

<Happened>
<Tr>
<En>The browser converted each unit using 1in = 96px, so 1cm is mathematically 37.795px; Chromium stores layout sizes in 1/64 px steps, hence 37.7812px. A `1cm` element isn't exactly 1cm on your screen (that depends on the screen) but is exactly 1cm when printed at 100%. `pt` and `pc` come from print typography: `12pt` = 16px.</En>
<Ur>Browser ne har unit 1in = 96px se badli, isliye 1cm hisaab se 37.795px hai; Chromium layout sizes 1/64 px ke qadmon me rakhta hai, isliye 37.7812px. `1cm` element aap ki screen par bilkul 1cm nahi (screen par munhasir) magar 100% par print me bilkul 1cm hai. `pt` aur `pc` print typography se aaye: `12pt` = 16px.</Ur>
</Tr>
</Happened>

</Step>

<Step title="rem: relative to the root font size">

<Tr>
<En>`1rem` equals the computed `font-size` of `<html>`: 16px by default, but users can change it (say to 20px), so `1.5rem` is 24px by default and 30px for that user. One scaling factor for the whole page, controlled by the user, and no compounding. Use it for font sizes, spacing, container max-widths and breakpoints; most design systems and Tailwind (`p-4` = `1rem`) do. Never set `html { font-size: 16px; }` in pixels: it overrides the user. The old `html { font-size: 62.5% }` trick (1rem = 10px) shrinks third-party components and is rarely worth it.</En>
<Ur>`1rem` `<html>` ke computed `font-size` ke barabar hai: default 16px, magar users badal sakte hain (maslan 20px), isliye `1.5rem` default me 24px aur us user ke liye 30px. Poore page ka ek paimana, user ke qaboo me, aur koi zarb nahi. Font sizes, faasle, container max-widths aur breakpoints ke liye; zyada tar design systems aur Tailwind (`p-4` = `1rem`) yahi karte hain. `html { font-size: 16px; }` pixels me kabhi na likhein: ye user ki marzi mita deta hai. Purana `html { font-size: 62.5% }` jugaad (1rem = 10px) third-party components chhote kar deta hai aur kam hi faida deta hai.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.px  { font-size: 18px; padding: 16px; }
.rem { font-size: 1.125rem; padding: 1rem; }
</style>
<p class="px">Sized in px</p><p class="rem">Sized in rem</p>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    for root in ["100%", "125%"]:
        page.set_content(html.replace("<style>", f"<style>html {{ font-size: {root}; }}"))
        rootpx = page.evaluate("getComputedStyle(document.documentElement).fontSize")
        for cls in [".px", ".rem"]:
            fs, pad = page.eval_on_selector(cls, "e => [getComputedStyle(e).fontSize, getComputedStyle(e).paddingTop]")
            print(f"user setting {rootpx:5} {cls:5} font-size {fs:6} padding {pad}")
    browser.close()
PY
```

```text output
user setting 16px  .px   font-size 18px   padding 16px
user setting 16px  .rem  font-size 18px   padding 16px
user setting 20px  .px   font-size 18px   padding 16px
user setting 20px  .rem  font-size 22.5px padding 20px
```

<Happened>
<Tr>
<En>At the default 16px root, `18px` and `1.125rem` looked identical. For a user with a 20px default (simulated with `html { font-size: 125% }`), the `px` text **ignored** their choice and stayed 18px, while the `rem` text grew to 22.5px with 20px padding, keeping its proportions.</En>
<Ur>Default 16px root par `18px` aur `1.125rem` ek jaise the. 20px default wale user ke liye (`html { font-size: 125% }` se banaya), `px` text ne us ki marzi **nazar andaz** ki aur 18px raha, jabke `rem` text 22.5px aur padding 20px tak barha, tanasub qaim rakhte hue.</Ur>
</Tr>
</Happened>

</Step>

<Step title="em: relative to the element's font size">

<Tr>
<En>For **`font-size`**, `1em` is the **parent's** font size; for **every other property**, it's the element's **own** computed font size (`padding: 0.5em` on a 20px button = 10px). So components scale as a unit: a button's em padding stays proportional to its text. Use em for padding inside buttons, badges and tags, icons next to text (`width: 1em`), heading margins and letter-spacing. **Compounding:** nested `font-size` in em multiplies (1.2 × 1.2 = 1.44…), so use `rem` for font sizes.</En>
<Ur>**`font-size`** ke liye `1em` **parent** ka font size hai; **baqi har property** ke liye element ka **apna** computed font size (20px button par `padding: 0.5em` = 10px). Isliye components ikai ki tarah barhte hain: button ki em padding us ke text ke tanasub me rehti hai. Buttons, badges aur tags ki padding, text ke saath icons (`width: 1em`), headings ke margins aur letter-spacing ke liye em. **Zarb:** nested `font-size` em me zarb hota hai (1.2 × 1.2 = 1.44…), isliye font sizes ke liye `rem`.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.em li  { font-size: 1.2em; }
.rem li { font-size: 1.2rem; }
.btn { padding: 0.5em 1em; }
.btn.small { font-size: 0.875rem; }
.btn.large { font-size: 1.25rem; }
</style>
<ul class="em"><li id="e1">Level 1<ul><li id="e2">Level 2<ul><li id="e3">Level 3</li></ul></li></ul></li></ul>
<ul class="rem"><li id="r1">Level 1<ul><li id="r2">Level 2<ul><li id="r3">Level 3</li></ul></li></ul></li></ul>
<button class="btn small" type="button">Small</button><button class="btn large" type="button">Large</button>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    for prefix, label in [("e", "1.2em"), ("r", "1.2rem")]:
        sizes = [page.eval_on_selector(f"#{prefix}{i}", "e => getComputedStyle(e).fontSize") for i in (1, 2, 3)]
        print(f"font-size {label:6} by level: {sizes}")
    for cls in [".small", ".large"]:
        fs, pt, pl = page.eval_on_selector(f".btn{cls}", "e => { const s = getComputedStyle(e); return [s.fontSize, s.paddingTop, s.paddingLeft] }")
        print(f"button {cls:7} font {fs:5} padding {pt} {pl}")
    browser.close()
PY
```

```text output
font-size 1.2em  by level: ['19.2px', '23.04px', '27.648px']
font-size 1.2rem by level: ['19.2px', '19.2px', '19.2px']
button .small  font 14px  padding 7px 14px
button .large  font 20px  padding 10px 20px
```

<Happened>
<Tr>
<En>With `1.2em` each level multiplied its parent: 19.2, 23.04, 27.648px, so deeply nested lists or comments become huge. With `1.2rem` every level is 19.2px. Both buttons share `padding: 0.5em 1em`: the 14px one gets 7 × 14px, the 20px one 10 × 20px, so padding scales with the text automatically.</En>
<Ur>`1.2em` ke saath har level ne apne parent ko zarb diya: 19.2, 23.04, 27.648px, isliye gehri nested lists ya comments bohot bare ho jate hain. `1.2rem` ke saath har level 19.2px hai. Dono buttons ki `padding: 0.5em 1em` ek hai: 14px wale ko 7 × 14px, 20px wale ko 10 × 20px, isliye padding text ke saath khud barhti hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Percentages: relative to what?">

<Tr>
<En>

A percentage's reference depends on the property:

| Property | % of… |
| --- | --- |
| `width`, `max-width`, `left`, `right`, `margin-*`, `padding-*` (**all four sides**) | the containing block's **width** |
| `height`, `top`, `bottom` | the containing block's **height** (only if definite) |
| `font-size` | the parent's font size |
| `line-height` | the element's own font size |
| `translate` | the element's **own** size |
| `border-radius` | the element's own size |

Most "percentage doesn't work" bugs are the wrong reference: `height: 50%` in an `auto`-height parent does nothing, and `padding-top: 10%` is 10% of the **width**. The old `padding-top: 56.25%` trick for 16:9 boxes relied on that; today use `aspect-ratio: 16 / 9`.

</En>
<Ur>

Percentage ka hawala property par munhasir hai:

| Property | Kis ka %… |
| --- | --- |
| `width`, `max-width`, `left`, `right`, `margin-*`, `padding-*` (**chaaron taraf**) | containing block ki **chaurai** |
| `height`, `top`, `bottom` | containing block ki **oonchai** (sirf tay ho to) |
| `font-size` | parent ka font size |
| `line-height` | element ka apna font size |
| `translate` | element ka **apna** size |
| `border-radius` | element ka apna size |

Zyada tar "percentage nahi chalta" bugs ghalat hawala hain: `auto` oonchai wale parent me `height: 50%` kuch nahi karta, aur `padding-top: 10%` **chaurai** ka 10% hai. 16:9 dabbon ka purana `padding-top: 56.25%` jugaad isi par tha; aaj `aspect-ratio: 16 / 9` lein.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
.parent { width: 400px; height: 200px; font-size: 20px; position: relative; }
.auto-parent { width: 400px; }
.child { width: 50%; height: 50%; padding-top: 10%; font-size: 50%; translate: 50% 0; border-radius: 50%; position: absolute; top: 50%; }
.child2 { height: 50%; }
</style>
<div class="parent"><div class="child" id="c">x</div></div>
<div class="auto-parent"><div class="child2" id="c2">x</div></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(html)
    s = page.eval_on_selector("#c", """e => { const s = getComputedStyle(e); return {
        width: s.width, height: s.height, paddingTop: s.paddingTop, fontSize: s.fontSize,
        top: s.top, translate: s.translate, borderRadius: s.borderRadius } }""")
    for k, v in s.items():
        print(f"{k:12} 50% (or 10%) -> {v}")
    print("height: 50% in an auto-height parent ->", page.eval_on_selector("#c2", "e => getComputedStyle(e).height"))
    browser.close()
PY
```

```text output
width        50% (or 10%) -> 200px
height       50% (or 10%) -> 100px
paddingTop   50% (or 10%) -> 40px
fontSize     50% (or 10%) -> 10px
top          50% (or 10%) -> 100px
translate    50% (or 10%) -> 50%
borderRadius 50% (or 10%) -> 50%
height: 50% in an auto-height parent -> 18px
```

<Happened>
<Tr>
<En>`width: 50%` is half the 400px width; `height` and `top` half the 200px height. `padding-top: 10%` is 40px: 10% of the **width**. `font-size: 50%` is half the parent's 20px. `translate` and `border-radius` stay as percentages because they depend on the element's own size, known only at layout. In an auto-height parent, `height: 50%` was ignored (just its content, 18px).</En>
<Ur>`width: 50%` 400px chaurai ka aadha; `height` aur `top` 200px oonchai ka aadha. `padding-top: 10%` 40px hai: **chaurai** ka 10%. `font-size: 50%` parent ke 20px ka aadha. `translate` aur `border-radius` percentage hi rehte hain kyun ke element ke apne size par munhasir hain, jo layout par hi maloom hota hai. Auto oonchai wale parent me `height: 50%` nazar andaz hua (sirf mawad, 18px).</Ur>
</Tr>
</Happened>

</Step>

<Step title="Viewport units: vw, vh, dvh, svh, lvh">

<Tr>
<En>`1vw`/`1vh` are 1% of the viewport width/height; `vmin`/`vmax` the smaller/larger. On phones the address bar shows and hides, so viewport height changes: **`svh`** (small, bars visible) always fits, **`lvh`** (large, bars hidden), **`dvh`** (dynamic) follows the bars, and plain `vh` behaves like `lvh`, so `100vh` can overflow. Use `min-height: 100svh` (or `100dvh`) for full-height sections and always pair vw with rem in `clamp()` for type. Gotcha: **`100vw` includes the vertical scrollbar** on desktops with classic scrollbars, so `width: 100vw` causes sideways scroll; use `width: 100%`.</En>
<Ur>`1vw`/`1vh` viewport chaurai/oonchai ka 1%; `vmin`/`vmax` chhota/bara. Phones par address bar dikhta chhupta hai, isliye viewport oonchai badalti hai: **`svh`** (chhoti, bars nazar) hamesha fit, **`lvh`** (bari, bars chhupe), **`dvh`** (badalti) bars ke saath chalti, aur saada `vh` `lvh` jaisa hai, isliye `100vh` bahar nikal sakta hai. Poori oonchai ke hisson ke liye `min-height: 100svh` (ya `100dvh`) aur text ke liye vw ko hamesha `clamp()` me rem ke saath. Dhoka: classic scrollbars wale desktops par **`100vw` me khara scrollbar shamil** hai, isliye `width: 100vw` side scroll karata hai; `width: 100%` lein.</Ur>
</Tr>

<Step title="ch, ex, lh and other font-relative units">

<Tr>
<En>**`ch`** is the width of "0" in the element's font (about 0.5em; exactly one character in monospace). **`ex`** is the height of "x"; **`lh`** the computed line height (**`rlh`** the root's); **`cap`** capital height; **`ic`** a CJK ideograph's width. `max-width: 65ch` keeps paragraphs at a comfortable 60–75 characters whatever the font size, and `lh` matches spacing to text rhythm. Use them for text containers, input widths (`width: 6ch` for a ZIP code), code blocks and paragraph spacing (`margin-block: 1lh`). `ch` varies by font; that's the point.</En>
<Ur>**`ch`** element ke font me "0" ki chaurai hai (taqreeban 0.5em; monospace me bilkul ek character). **`ex`** "x" ki oonchai; **`lh`** computed line height (**`rlh`** root ki); **`cap`** bare huroof ki oonchai; **`ic`** CJK ideograph ki chaurai. `max-width: 65ch` paragraphs ko font size kuch bhi ho aaram deh 60–75 characters par rakhta hai, aur `lh` faasle ko text ke tawazun se milata hai. Text containers, input chaurai (ZIP code ke liye `width: 6ch`), code blocks aur paragraph ke faasle (`margin-block: 1lh`) ke liye. `ch` font ke saath badalta hai; yahi to maqsad hai.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
p { max-width: 65ch; margin: 0; }
#mono { font-family: monospace; font-size: 16px; }
#sans { font-family: sans-serif; font-size: 16px; }
#big  { font-family: sans-serif; font-size: 20px; }
#lh   { font-size: 16px; line-height: 1.5; margin-block-end: 1lh; }
</style>
<p id="mono">mono</p><p id="sans">sans</p><p id="big">big</p><p id="lh">lh</p>"""

    browser = p.chromium.launch()
```

<Step title="Unitless line-height">

<Tr>
<En>`line-height` accepts a unitless number (`1.5`), a length or a percentage/em. With a **unitless** number children inherit the **ratio** and recompute it for their own font size; with `em`, `%` or `px` they inherit the **computed pixels**, so a large heading inside a container with `line-height: 1.5em` gets cramped, overlapping lines. Always use unitless: `body { line-height: 1.5; }`, headings around 1.1–1.25. One of the few places where "no unit" is the best unit.</En>
<Ur>`line-height` bina unit number (`1.5`), lambai ya percentage/em leta hai. **Bina unit** number me bachche **tanasub** wirse me le kar apne font size ke liye dobara nikalte hain; `em`, `%` ya `px` me **nikale hue pixels** lete hain, isliye `line-height: 1.5em` wale container ke andar bari heading ki lines tang aur ek doosre par chadhti hain. Hamesha bina unit: `body { line-height: 1.5; }`, headings taqreeban 1.1–1.25. Un chand jagahon me se ek jahan "koi unit nahi" behtareen unit hai.</Ur>
</Tr>

<Step title="calc(), min(), max() and clamp()">

<Tr>
<En>**`calc()`** does arithmetic with mixed units (`calc(100% - 2rem)`; spaces around `+` and `-` are required). **`min()`** picks the smallest (`width: min(100%, 600px)` = 600px but never wider than the container), **`max()`** the largest, and **`clamp(min, preferred, max)`** = `max(min, min(preferred, max))`. They replace many media queries: container widths (`min(100% - 2rem, 1200px)`), fluid spacing and type, sizes minus a header. `calc()` nests inside the others and works with variables (`calc(var(--space) * 2)`).</En>
<Ur>**`calc()`** mili juli units ka hisaab karta hai (`calc(100% - 2rem)`; `+` aur `-` ke gird spaces lazmi). **`min()`** sab se chhota chunta hai (`width: min(100%, 600px)` = 600px magar container se kabhi chaura nahi), **`max()`** sab se bara, aur **`clamp(min, preferred, max)`** = `max(min, min(preferred, max))`. Ye kai media queries ki jagah lete hain: container chaurai (`min(100% - 2rem, 1200px)`), lachakdar faasle aur text, header ghata kar sizes. `calc()` doosron ke andar chalta hai aur variables ke saath bhi (`calc(var(--space) * 2)`).</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<!DOCTYPE html><title>t</title><style>
body { margin: 0; }
#calc  { width: calc(100% - 2rem); }
#min   { width: min(100%, 600px); }
#max   { width: max(50%, 300px); }
#clamp { width: clamp(280px, 60%, 720px); }
#wrap  { width: min(100% - 2rem, 1200px); margin-inline: auto; }
</style><div id="calc"></div><div id="min"></div><div id="max"></div><div id="clamp"></div><div id="wrap"></div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    for width in [375, 1440]:
        page = browser.new_page(viewport={"width": width, "height": 600})
        page.set_content(html)
        sizes = {el: page.eval_on_selector(el, "e => e.offsetWidth") for el in ["#calc", "#min", "#max", "#clamp", "#wrap"]}
        print(f"screen {width:4}px:", "  ".join(f"{k}={v}" for k, v in sizes.items()))
        page.close()
    browser.close()
PY
```

```text output
screen 1440px: #calc=1408  #min=600  #max=720  #clamp=720  #wrap=1200
```

<Tr>
<En>`calc(100% - 2rem)`: 343 and 1408. `min(100%, 600px)`: the full 375 on the phone, capped at 600. `max(50%, 300px)`: 187.5 loses to 300 on the phone, 720 wins on desktop. `clamp(280px, 60%, 720px)`: 225 is raised to 280, 864 is capped at 720. `min(100% - 2rem, 1200px)` (no `calc` needed inside `min`) is a one-line responsive container: 16px each side on phones, 1200px max on desktops.</En>
<Ur>`calc(100% - 2rem)`: 343 aur 1408. `min(100%, 600px)`: phone par poore 375, desktop par 600 ki had. `max(50%, 300px)`: phone par 187.5 300 se haara, desktop par 720 jeeta. `clamp(280px, 60%, 720px)`: 225 barh kar 280, 864 ruk kar 720. `min(100% - 2rem, 1200px)` (`min` ke andar `calc` ki zaroorat nahi) ek line ka responsive container hai: phones par har taraf 16px, desktops par 1200px had.</Ur>

<Step title="Choosing units in practice">

<Tr>
<En>Start from the table in "At a glance" and break the rules only with a reason. Design tools usually give px values: divide by 16 to get rem (24px → 1.5rem); Tailwind's scale does it for you (`p-6` = 1.5rem). In media queries, `rem`/`em` refer to the browser's default font size (not your `html` rule), so `@media (min-width: 48em)` is 768px for most users and scales for users with larger text. Component-relative sizes inside container queries use `cqi`.</En>
<Ur>"At a glance" ki table se shuru karein aur qawaid sirf wajah ke saath toren. Design tools aam taur par px dete hain: rem ke liye 16 se taqseem karein (24px → 1.5rem); Tailwind ka paimana ye khud karta hai (`p-6` = 1.5rem). Media queries me `rem`/`em` browser ke default font size (aap ke `html` rule nahi) ko maante hain, isliye `@media (min-width: 48em)` zyada tar users ke liye 768px aur bare text walon ke liye barhta hai. Container queries ke andar component ke nisbat sizes `cqi` se.</Ur>
</Tr>

<Compare>
<Bad title="Pixel-locked and scrollbar-blind">

```text
html { font-size: 10px; }                 /* overrides the user's setting */

.hero { width: 100vw; height: 100vh; }    /* sideways scroll + cut off on phones */
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Font sizes in px**, ignoring user font settings.
- **Percentage heights in auto-height parents**, which do nothing.
- **Forgetting vertical padding/margin percentages use the width.**
- **Pure `vw` font sizes**, tiny on phones and poor with zoom; use `clamp()` with rem.

</En>

- **px me font sizes**, user ki font settings nazar andaz.
- **Auto oonchai wale parents me percentage heights**, jo kuch nahi kartin.
- **Bhoolna ke upar neeche ki padding/margin ke percentages chaurai se hain.**
- **Khaalis `vw` font sizes**, phones par chhote aur zoom ke saath kamzor; rem wala `clamp()` lein.

</Ur>

<DeepDive title="Real world: px fonts and the 100vh bug">

For years many sites set font sizes in px; when browsers added page zoom (which scales px too) it seemed not to matter. But browser **font-size settings**, used by many older and low-vision users and by Android's system font size in some browsers, only scale relative units. Accessibility audits frequently flag px text that ignores them, and GOV.UK's design system, Bootstrap 5 and Tailwind all moved to rem-based type and spacing. Another famous bug: iOS Safari's `100vh` problem, with full-screen heroes cut off behind the toolbar; `svh`/`dvh`/`lvh` were added to CSS in 2022 to solve it and now work in all major browsers.

</DeepDive>

<DeepDive title="Security lens">

Units don't create vulnerabilities by themselves, but sizing can hide information or break security UI for some users.

- **Readable security text:** warnings, consent text, amounts and permission prompts must scale with user font settings (rem), never tiny fixed sizes; regulators treat unreadable "fine print" as deceptive.
- **Zoom and reflow:** at 200–400% zoom, users must still see full URLs, recipients and confirm/cancel buttons; `height: 100vh; overflow: hidden` containers can cut them off.
- **Tiny invisible elements:** `font-size: 0`, 1 × 1px boxes or `0.01rem` text hide content from sighted users while keeping it in the page, a trick used in phishing emails and hidden-text SEO spam; security filters flag it.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between rem and em?">
Rem is relative to the root element's font size, so it's consistent everywhere on the page and respects the user's default font size. Em is relative to the font size of the current element, or of the parent when used in font-size itself, so it scales with local text but compounds when nested elements also use em for font sizes.
</QA>

<QA q="Why should font sizes be in rem rather than px?">
Browsers let users set a default font size, and rem values scale with it while px values ignore it. Using rem for text and most spacing keeps the layout proportional for users who need larger text, which supports accessibility requirements for resizable text.
</QA>

<QA q="What do percentages refer to in CSS?">
It depends on the property. Widths, horizontal offsets and all margins and paddings, even vertical ones, refer to the containing block's width. Heights and vertical offsets refer to its height, but only if that height is definite. Font-size refers to the parent's font size, line-height to the element's own font size, and translate and border-radius to the element's own dimensions.
</QA>

<QA q="What problem do dvh, svh and lvh solve?">
On mobile browsers, the visible viewport height changes as address and tool bars appear and disappear, so 100vh may be taller than the visible area and hide content. The small viewport unit always fits with bars visible, the large unit assumes bars are hidden, and the dynamic unit updates as the bars move.
</QA>

<QA q="What does clamp() do and how would you use it for typography?">
Clamp takes a minimum, a preferred and a maximum value and returns the preferred value limited to that range. For fluid typography you combine a rem part with a viewport part as the preferred value, for example 1rem plus 3vw, and set rem minimum and maximum sizes, so text scales smoothly between screen sizes while still respecting user font settings and staying within readable limits.
</QA>

</DeepDive>
