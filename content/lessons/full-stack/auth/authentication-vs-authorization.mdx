---
title: "Authentication vs Authorization"
summary: "Two words that sound alike and protect against different things. Learn from zero that authentication answers who you are (log in, prove it, get 401 when you can't) and authorization answers what you may do (roles, ownership and rules, 403 or 404 when you may not). Build both as Express middleware, watch a logged-in customer read someone else's order through a route that only checked login, and put every permission decision into one deny-by-default policy function you can test as a table. All verified with Express 5 and Node.js 22."
level: beginner
minutes: 30
prerequisites: ["Middleware Pattern", "HTTP Status Codes"]
tags: ["Auth", "Security", "Express", "Authorization"]

<BigIdea>
<Tr>
<En>
**Authentication (authn)** answers **"who are you?"**: the user proves their identity with a password, a code, a passkey or a "Sign in with Google", and from then on each request carries proof (a session cookie or a token). If that proof is missing or invalid, the answer is **401 Unauthorized** (badly named: it really means "unauthenticated"). **Authorization (authz)** answers **"what are you allowed to do?"**: given a known user, may they read this order, refund that payment, open the admin page? If not, the answer is **403 Forbidden**, or **404** when even admitting the thing exists would leak information. Authentication always comes first, but it is **not enough**: the most common serious API bug (OWASP's number one, broken access control) is a route that checks "logged in" and forgets "allowed". Check permissions **on the server, on every request, for every resource**, and **deny by default**: if no rule says yes, the answer is no.
</En>
<Ur>
**Authentication (authn)** jawab deta hai **"aap kaun hain?"**: user password, code, passkey ya "Sign in with Google" se apni pehchan sabit karta hai, aur us ke baad har request saboot saath laati hai (session cookie ya token). Agar saboot na ho ya ghalat ho to jawab **401 Unauthorized** hai (naam bura hai: asal matlab "unauthenticated"). **Authorization (authz)** jawab deta hai **"aap ko kya karne ki ijazat hai?"**: maloom user ke liye, kya woh ye order parh sakta hai, woh payment refund kar sakta hai, admin page khol sakta hai? Agar nahi to jawab **403 Forbidden** hai, ya **404** jab cheez ke mojood hone ka iqrar bhi maloomat leak kare. Authentication hamesha pehle aata hai, magar **kafi nahi**: sab se aam sangeen API bug (OWASP ka number ek, broken access control) aisa route hai jo "logged in" check karta aur "ijazat" bhool jata hai. Ijazat **server par, har request par, har resource ke liye** check karein, aur **default inkaar**: agar koi rule haan na kahe to jawab nahi hai.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- Mixing them up causes real breaches: "logged in" is not "allowed".
- Correct status codes tell clients what to do: 401 means log in again, 403 means don't retry.
- Separating them keeps code clean: one middleware identifies the user, one policy decides.
- Interviews and security reviews use these exact terms.

</En>
<Ur>

- Dono ko gaddmadd karna asal breaches ka sabab banta hai: "logged in" matlab "ijazat" nahi.
- Sahi status codes clients ko batate hain kya karna hai: 401 ka matlab dobara login, 403 ka matlab dobara koshish na karo.
- Dono ko alag rakhna code saaf rakhta hai: ek middleware user pehchanta hai, ek policy faisla karti hai.
- Interviews aur security reviews yahi alfaaz istemal karte hain.

</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a hotel.

- At the front desk you show your passport. The clerk checks it and gives you a key card: that's **authentication**. The key card is your session or token; you don't show your passport again at every door.
- Your key card opens **your** room, the gym and the pool, but not other guests' rooms or the staff office: that's **authorization**. The same card, different answers depending on the door.
- No card at all? The door won't even ask what you want: **401**. A valid card at the wrong door: **403**.
- The dangerous hotel is the one where any valid key card opens every room, because someone only checked "is this a real card?".

</En>
<Ur>

Ek hotel socheyn.

- Front desk par aap passport dikhate hain. Clerk check kar ke key card deta hai: ye **authentication** hai. Key card aap ka session ya token hai; har darwaze par dobara passport nahi dikhate.
- Aap ka key card **aap ka** kamra, gym aur pool kholta hai, magar doosre mehmanon ke kamre ya staff office nahi: ye **authorization** hai. Wahi card, darwaze ke hisaab se mukhtalif jawab.
- Card hi nahi? Darwaza ye bhi nahi poochhta ke aap ko kya chahiye: **401**. Ghalat darwaze par sahi card: **403**.
- Khatarnak hotel woh hai jahan har sahi key card har kamra kholta hai, kyunke kisi ne sirf "kya ye asli card hai?" check kiya.

## Learn it step by step

<Walkthrough>

<Step title="Authentication and authorization as Express middleware">

<Tr>
<En>
A tiny API with three users (two customers and an admin), fake tokens and two orders. `authenticate` turns a `Bearer` token into `req.user` or answers 401. The orders route checks **ownership**, `requireRole('admin')` protects the stats, and one route on purpose checks only login. A script calls every route as different people.
</En>
<Ur>
Teen users (do customers aur ek admin), nakli tokens aur do orders wali chhoti API. `authenticate` `Bearer` token ko `req.user` banata hai ya 401 deta hai. Orders route **malikana haq** check karta hai, `requireRole('admin')` stats ki hifazat karta hai, aur ek route jaan boojh kar sirf login check karta hai. Ek script har route ko mukhtalif logon ki tarah bulata hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 --silent
cat > server.js <<'EOF'
import express from 'express';

// Fake data. Real apps use a database, sessions or JWTs (next lessons).
const users = { 1: { id: 1, name: 'Jane Doe', role: 'customer' }, 2: { id: 2, name: 'John Smith', role: 'customer' }, 3: { id: 3, name: 'Ana Lee', role: 'admin' } };
const tokens = { 'tok-jane': 1, 'tok-john': 2, 'tok-ana': 3 };
const orders = { 101: { id: 101, ownerId: 1, total: 40 }, 102: { id: 102, ownerId: 2, total: 75 } };

// AUTHENTICATION: who are you? Failure = 401 Unauthorized
function authenticate(req, res, next) {
  const token = req.get('authorization')?.replace(/^Bearer /, '');
  const user = users[tokens[token]];
  if (!user) return res.status(401).set('WWW-Authenticate', 'Bearer').json({ error: 'log in first' });
  req.user = user;
  next();
}
// AUTHORIZATION: are you allowed? Failure = 403 Forbidden
const requireRole = (role) => (req, res, next) =>
  req.user.role === role ? next() : res.status(403).json({ error: `requires role ${role}` });

const app = express();
app.get('/me', authenticate, (req, res) => res.json(req.user));
app.get('/orders/:id', authenticate, (req, res) => {
  const order = orders[req.params.id];
  // ownership check: customers see their own orders, admins see all
  if (!order || (order.ownerId !== req.user.id && req.user.role !== 'admin'))
    return res.status(404).json({ error: 'order not found' });   // 404 hides that the order exists
  res.json(order);
});
app.get('/admin/stats', authenticate, requireRole('admin'), (req, res) => res.json({ orders: Object.keys(orders).length }));
// BUG on purpose: logged in is checked, permission is not ("the button is hidden in the UI anyway")
app.delete('/unsafe/orders/:id', authenticate, (req, res) => { delete orders[req.params.id]; res.json({ deleted: req.params.id }); });
export default app;
EOF
cat > try.js <<'EOF'
import app from './server.js';
const server = app.listen(3000);
const call = async (method, path, token) => {
  const res = await fetch('http://localhost:3000' + path, { method, headers: token ? { authorization: `Bearer ${token}` } : {} });
  const who = token ? token.replace('tok-', '') : 'nobody';
  console.log(`${who.padEnd(7)} ${method.padEnd(6)} ${path.padEnd(20)} -> ${res.status} ${await res.text()}`);
};
await call('GET', '/me');
await call('GET', '/me', 'tok-fake');
await call('GET', '/me', 'tok-jane');
await call('GET', '/orders/101', 'tok-jane');
await call('GET', '/orders/102', 'tok-jane');
await call('GET', '/orders/102', 'tok-ana');
await call('GET', '/admin/stats', 'tok-jane');
await call('GET', '/admin/stats', 'tok-ana');
await call('DELETE', '/unsafe/orders/102', 'tok-jane');
await call('GET', '/orders/102', 'tok-john');
server.close();
EOF
node try.js
```

<Happened>
<Tr>
<En>

- **Nobody** and the **fake token** got **401**: authentication failed, so the server never even looked at what they asked for. The `WWW-Authenticate: Bearer` header tells clients how to authenticate.
- Jane is authenticated, so `/me` works. She can read **her** order 101, but order 102 belongs to John, so she gets **404**: the API doesn't confirm that the order exists. Ana, an admin, can read it.
- Jane on `/admin/stats` got **403**: the server knows exactly who she is, she just isn't allowed.
- The `/unsafe` route only checked that Jane was logged in, so she **deleted John's order**, and John now gets 404 for his own order. Hiding the delete button in the UI doesn't help: anyone can send the request with `curl`. This is broken access control (IDOR / BOLA).

</En>
<Ur>

- **Nobody** aur **nakli token** ko **401** mila: authentication nakam hui, isliye server ne ye dekha hi nahi ke unhon ne kya maanga. `WWW-Authenticate: Bearer` header clients ko batata hai ke authenticate kaise karna hai.
- Jane authenticated hai, isliye `/me` chalta hai. Woh **apna** order 101 parh sakti hai, magar order 102 John ka hai, isliye use **404** milta hai: API order ke mojood hone ki tasdeeq nahi karti. Ana, jo admin hai, use parh sakti hai.
- `/admin/stats` par Jane ko **403** mila: server bilkul janta hai woh kaun hai, bas use ijazat nahi.
- `/unsafe` route ne sirf ye check kiya ke Jane logged in hai, isliye us ne **John ka order mita diya**, aur ab John ko apne hi order par 404 milta hai. UI me delete button chhupane se faida nahi: koi bhi `curl` se request bhej sakta hai. Ye broken access control (IDOR / BOLA) hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="One deny-by-default policy for every decision">

<Tr>
<En>
Instead of scattering `if (user.role === …)` across routes, put every rule in one `can(user, action, resource)` function. Rules combine **roles** (admin, support) and **attributes** (owner, order total). Unknown actions and missing users are denied. The script prints a permission matrix, which is also a ready-made test table.
</En>
<Ur>
Routes me `if (user.role === …)` bikherne ke bajaye har rule ek `can(user, action, resource)` function me rakhein. Rules **roles** (admin, support) aur **attributes** (malik, order ka total) milate hain. Anjaan kaam aur ghayab users inkaar hote hain. Script ijazaton ki matrix chhapta hai, jo tayyar test table bhi hai.
</Ur>
</Tr>

```bash
cat > policy.js <<'EOF'
// One place that answers "can this user do this action on this resource?"
const rules = {
  'order:read':   (user, order) => user.role === 'admin' || order.ownerId === user.id,
  'order:refund': (user, order) => user.role === 'admin' || (user.role === 'support' && order.total <= 100),
  'order:delete': (user) => user.role === 'admin',
};
export function can(user, action, resource) {
  if (!user) return false;                       // not authenticated: never allowed
  const rule = rules[action];
  return rule ? rule(user, resource) : false;    // unknown action: deny by default
}
EOF
cat > matrix.js <<'EOF'
import { can } from './policy.js';
const people = { jane: { id: 1, role: 'customer' }, sam: { id: 4, role: 'support' }, ana: { id: 3, role: 'admin' }, nobody: null };
const small = { id: 101, ownerId: 1, total: 40 };    // Jane's order, $40
const big   = { id: 103, ownerId: 2, total: 250 };   // John's order, $250
const checks = [['order:read', small], ['order:read', big], ['order:refund', small], ['order:refund', big], ['order:delete', big], ['order:export', small]];
console.log('action'.padEnd(26) + Object.keys(people).map((p) => p.padEnd(8)).join(''));
for (const [action, order] of checks)
  console.log(`${action} #${order.id} ($${order.total})`.padEnd(26) + Object.values(people).map((u) => (can(u, action, order) ? 'yes' : '-').padEnd(8)).join(''));
EOF
node matrix.js
```

```text output
action                    jane    sam     ana     nobody  
order:read #101 ($40)     yes     -       yes     -       
order:read #103 ($250)    -       -       yes     -       
order:refund #101 ($40)   -       yes     yes     -       
order:refund #103 ($250)  -       -       yes     -       
order:delete #103 ($250)  -       -       yes     -       
order:export #101 ($40)   -       -       -       -       
```

<Happened>
<Tr>
<En>

- Jane can read her own order but not John's: an **ownership** rule.
- Sam from support can refund the $40 order but not the $250 one: a rule using a **role and an attribute** of the resource together. Requirements like this are why simple role checks often aren't enough.
- Ana, the admin, can do everything that has a rule, yet even she is denied **`order:export`**, because nobody wrote a rule for it. That's **deny by default**: forgetting a rule fails safe instead of opening a hole.
- **Nobody** (not authenticated) gets nothing, regardless of the rule.
- Because the policy is a pure function, you can unit-test every row of this table and review permission changes in one file. Routes call `can()`, and data queries should filter the same way (for example, `WHERE owner_id = $1`) so lists don't leak other users' rows.

</En>
<Ur>

- Jane apna order parh sakti hai magar John ka nahi: **malikana haq** ka rule.
- Support wala Sam $40 wala order refund kar sakta hai magar $250 wala nahi: aisa rule jo **role aur resource ki attribute** dono milata hai. Aisi zaroorton ki wajah se saade role checks aksar kafi nahi hote.
- Admin Ana har us kaam ko kar sakti hai jis ka rule hai, phir bhi **`order:export`** se inkaar hota hai, kyunke kisi ne us ka rule nahi likha. Yahi **default inkaar** hai: rule bhoolna surakh kholne ke bajaye mehfooz nakami deta hai.
- **Nobody** (authenticated nahi) ko kuch nahi milta, rule chahe kuch bhi ho.
- Kyunke policy pure function hai, aap is table ki har row ka unit test kar sakte hain aur ijazat ki tabdeeliyan ek file me review kar sakte hain. Routes `can()` bulate hain, aur data queries bhi isi tarah filter karein (maslan `WHERE owner_id = $1`) taa ke lists doosre users ki rows leak na karein.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Logged in means allowed">

```text
app.patch('/invoices/:id', authenticate, async (req, res) => {
  await db.invoice.update(req.params.id, req.body);   // any user can edit any invoice
  res.sendStatus(204);
});
```

</Bad>
<Good title="Check the permission for this resource">

```text
app.patch('/invoices/:id', authenticate, async (req, res) => {
  const invoice = await db.invoice.find(req.params.id);
  if (!can(req.user, 'invoice:update', invoice)) return res.sendStatus(404);
  await db.invoice.update(invoice.id, pick(req.body, ['dueDate', 'notes']));
  res.sendStatus(204);
});
```

</Good>
</Compare>

<Compare>
<Bad title="Trusting the client to say who it is">

```text
// body: { "userId": 7, "role": "admin" }
app.post('/reports', (req, res) => {
  if (req.body.role === 'admin') return runReport(req.body.userId);
});
```

</Bad>
<Good title="Identity and role come from the verified session">

```text
app.post('/reports', authenticate, (req, res) => {
  if (!can(req.user, 'report:run')) return res.sendStatus(403);
  return runReport(req.user.id);
});
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Authorization only in the frontend**: hidden buttons and guarded pages are UX, not security. The API must check.
- **401 vs 403 swapped**: clients log users out on 401; use 403 when the user is known but not allowed.
- **Checking on the list but not the item** (or the other way round): `/orders` filters by owner, but `/orders/:id` doesn't.
- **Roles copied into long-lived tokens**: a demoted admin keeps admin rights until the token expires. Keep tokens short or look up permissions.
- **Allow lists by default**: "block these roles" breaks the moment a new role appears. Prefer "allow these".

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Authorization sirf frontend me**: chhupe buttons aur guarded pages UX hain, security nahi. API ko check karna hai.
- **401 aur 403 ulat**: clients 401 par users ko logout karte hain; jab user maloom ho magar ijazat na ho to 403 dein.
- **List par check, item par nahi** (ya ulta): `/orders` malik ke hisaab se filter karta hai, magar `/orders/:id` nahi.
- **Roles lambi umar wale tokens me copy**: hataya gaya admin token expire hone tak admin rehta hai. Tokens chhote rakhein ya ijazaten dobara dekhein.
- **Default ijazat wali lists**: "in roles ko roko" naya role aate hi toot jata hai. "In ko ijazat do" behtar hai.

</Ur>
</Tr>

<Tr>
<En>

</En>

</Ur>

<Tr>
<En>

1. Authentication: **401** (the client should refresh the token or log in again).
2. Authorization: **403**.

4. Authentication: **401** with `WWW-Authenticate`.
5. Authorization: **403** with a clear message such as "upgrade required" (some APIs use 402 Payment Required; be consistent and document it).

</En>

1. Authentication: **401** (client token refresh kare ya dobara login).
2. Authorization: **403**.
3. Authorization: **404** taa ke file ki mojoodgi zahir na ho (ghair hassas resources ke liye 403 bhi theek hai).
4. Authentication: `WWW-Authenticate` ke saath **401**.
5. Authorization: "upgrade required" jaise wazeh paigham ke saath **403** (kuch APIs 402 Payment Required istemal karti hain; yaksan rahein aur documentation me likhein).

<DeepDive title="More about authn and authz">

**Authentication factors.** Something you know (password), something you have (phone, security key), something you are (fingerprint, via passkeys). MFA combines two or more.

**Where identity lives.** Server-side sessions with a cookie, or self-contained tokens such as JWTs; or an identity provider (Auth0, Clerk, Cognito, Keycloak, Supabase Auth) that handles login and gives your app a verified identity via OpenID Connect.

**Authorization models.** RBAC (roles), ABAC (attributes of user, resource and environment), ReBAC (relationships, like Google Drive sharing, as in Zanzibar, OpenFGA or SpiceDB), and ACLs per object. Real apps mix them.

**Policy engines.** For complex rules, tools like OPA (Rego), Cedar or Casbin keep policies outside code and make them testable and auditable.

**Service-to-service.** Machines authenticate too: API keys, client credentials in OAuth, or mutual TLS, followed by the same kind of authorization.

</DeepDive>

<DeepDive title="Real world: changing one number in the URL">

A fintech app let users download their monthly statements from `/api/statements/58213.pdf`. The endpoint checked that the request had a valid session, then loaded the statement by ID. A user curious about the URL changed the number by one and got a stranger's statement, then wrote a script that downloaded thousands more before reporting it.

The fix had several layers:

1. Every statement query became `WHERE id = $1 AND user_id = $2`, using the session's user ID.
2. A central `can()` policy with tests for each resource type, and a lint rule flagging routes that load data without calling it.
3. Random, non-sequential IDs for documents (which helps but is not a fix on its own).
4. Alerts on unusual access patterns, such as one account downloading many documents quickly.

</DeepDive>

<DeepDive title="Security lens">

- **Broken access control** is the top OWASP risk: test every endpoint as another user, an anonymous user and a lower role.
- **Mass assignment**: let users change only allowed fields; never accept `role`, `ownerId` or `isAdmin` from the body.
- **Deny by default** in policies and in middleware order: protect routes globally and open the few public ones explicitly.
- **Consistent errors**: return the same 404 for "doesn't exist" and "not yours" to avoid ID enumeration.
- **Audit logs** for sensitive actions: who did what, to which resource, allowed or denied.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between authentication and authorization?">
Authentication verifies identity, who the user or service is, using credentials like passwords, keys or tokens. Authorization decides what that identity may do with a given resource, using roles, ownership and policies. Authentication comes first; authorization happens on every action.
</QA>

<QA q="When do you return 401 versus 403?">
401 when the request is not authenticated: no credentials, or invalid or expired ones, ideally with a WWW-Authenticate header. 403 when the user is authenticated but not permitted. For private resources, 404 can be used to avoid revealing existence.
</QA>

<QA q="What is IDOR or BOLA, and how do you prevent it?">
Insecure direct object reference, or broken object level authorization, is accessing another user's object by changing an identifier. Prevent it by checking ownership or permission for every object on the server, scoping queries to the current user, and testing endpoints as other users.
</QA>

<QA q="Why is hiding buttons in the UI not authorization?">
Clients are controlled by users, who can send any request directly with tools like curl. Only checks on the server, before reading or changing data, enforce permissions.
</QA>

<QA q="What is deny by default?">
A design where access is refused unless an explicit rule allows it, so missing rules, new roles or new actions fail safe instead of opening access.
</QA>

</DeepDive>
