<BigIdea>
<Tr>
<En>
A **JWT** (JSON Web Token, said "jot") is three base64url parts joined by dots: a **header** (which algorithm signed it), a **payload** of **claims** (`sub` who it's about, `exp` when it expires, `iss` who issued it, `aud` who it's for, plus your own like `role`), and a **signature**. The issuer signs header and payload with a secret (HS256) or a private key (RS256, ES256); any API with the secret or the **public key** can check the signature and trust the claims **without a database lookup**. That's the appeal: stateless verification across many services. The catches: the payload is **only encoded, not encrypted**, so never put secrets in it; verification must check the **algorithm, signature, issuer, audience and expiry**, every time; and a JWT stays valid until it expires, so **revocation is hard**. The usual design is **short-lived access tokens** (5 to 15 minutes) plus a **refresh token** that the auth server can revoke, asymmetric keys published as a **JWKS** so APIs never hold signing keys, and sessions instead of JWTs for plain browser apps.
</En>
<Ur>
**JWT** (JSON Web Token, "jot" bola jata hai) teen base64url hisse hain jo dots se jure hain: **header** (kis algorithm ne sign kiya), **claims** ka **payload** (`sub` kis ke bare me, `exp` kab expire, `iss` kis ne jaari kiya, `aud` kis ke liye, plus aap ke apne jaise `role`), aur **signature**. Jaari karne wala header aur payload ko secret (HS256) ya private key (RS256, ES256) se sign karta hai; jis API ke paas secret ya **public key** ho woh signature check kar ke claims par **database dekhe baghair** bharosa kar sakti hai. Yahi kashish hai: kayi services me stateless tasdeeq. Pareshaniyan: payload **sirf encoded hai, encrypted nahi**, isliye is me kabhi raaz na rakhein; tasdeeq ko har dafa **algorithm, signature, issuer, audience aur expiry** check karni hai; aur JWT expire hone tak valid rehta hai, isliye **revoke karna mushkil** hai. Aam design hai **kam umar wale access tokens** (5 se 15 minute) plus **refresh token** jise auth server revoke kar sake, **JWKS** ke tor par publish ki gayi asymmetric keys taa ke APIs ke paas signing keys kabhi na hon, aur saadi browser apps ke liye JWT ke bajaye sessions.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **festival wristband**.

- At the entrance, staff check your ticket and put a wristband on you: printed with your name, your area (VIP or general) and the day it's valid. That's the JWT: anyone can read what's printed.
- The band has a **hologram seal** only the festival can produce (the signature). Guards at every stage check the seal and the date, no phone call to the ticket office needed: stateless verification.
- If you write "VIP" on your band with a marker, the seal no longer matches: rejected.
- A band from a different festival (wrong issuer), for tomorrow's show (wrong audience), or from last week (expired) doesn't get you in either.
- The problem: if someone steals your band, guards can't know unless the office hands them a list of cancelled bands. So bands are made to last only a short time, and you get a new one from the office (refresh token) when it runs out.

</En>
<Ur>

**Festival ka wristband** socheyn.

- Darwaze par staff ticket check kar ke aap ko wristband pehnata hai: us par aap ka naam, aap ka area (VIP ya general) aur valid din chhapa hai. Ye JWT hai: chhapa hua koi bhi parh sakta hai.
- Band par **hologram seal** hai jo sirf festival bana sakta hai (signature). Har stage ke guard seal aur tareekh check karte hain, ticket office ko phone ki zaroorat nahi: stateless tasdeeq.
- Agar aap marker se band par "VIP" likh dein to seal mel nahi khata: rad.
- Doosre festival ka band (ghalat issuer), kal ke show ka (ghalat audience), ya pichle hafte ka (expired) bhi andar nahi jane deta.
- Masla: agar koi aap ka band chura le to guards ko pata nahi chalta jab tak office unhe cancel shuda bands ki list na de. Isliye band thori der chalne ke liye banaye jate hain, aur khatam hone par office se naya milta hai (refresh token).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Inside a JWT, and the checks that make it safe">

<Tr>
<En>
With the `jose` library we sign an HS256 access token for `user_1`, valid for 15 minutes, then decode its parts by hand. Verification always passes the expected **issuer, audience and algorithm**. A fixed clock keeps the output repeatable. Then we attack it five ways: wait until it expires, edit the payload, use it at another API, send an unsigned `alg: none` token, and sign with a guessed secret.
</En>
<Ur>
`jose` library se hum `user_1` ke liye 15 minute valid HS256 access token sign karte hain, phir us ke hisse haath se decode karte hain. Tasdeeq hamesha mutawaqqa **issuer, audience aur algorithm** deti hai. Mustaqil ghari output ko dohrane layak rakhti hai. Phir hum paanch tarah hamla karte hain: expire hone ka intezar, payload edit, doosri API par istemal, unsigned `alg: none` token, aur guess kiye secret se sign.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install jose@6.2.18 --silent
cat > hs256.js <<'EOF'
import { SignJWT, jwtVerify, UnsecuredJWT } from 'jose';

const secret = new TextEncoder().encode('a-32-byte-or-longer-random-secret-from-env!!');
const NOW = 1_800_000_000;                               // fixed clock so the output is repeatable
const at = (seconds) => ({ currentDate: new Date((NOW + seconds) * 1000) });
const expect = { issuer: 'https://auth.example.com', audience: 'shop-api', algorithms: ['HS256'] };

// 1. Issue a short-lived access token
const token = await new SignJWT({ role: 'customer' })
  .setProtectedHeader({ alg: 'HS256', typ: 'JWT' })
  .setSubject('user_1').setIssuer(expect.issuer).setAudience(expect.audience)
  .setIssuedAt(NOW).setExpirationTime(NOW + 15 * 60).setJti('tok_001')
  .sign(secret);
const [header, payload, signature] = token.split('.');
console.log('token parts (header.payload.signature) lengths:', header.length, payload.length, signature.length);
console.log('header :', Buffer.from(header, 'base64url').toString());
console.log('payload:', Buffer.from(payload, 'base64url').toString(), '  <- readable by anyone, not encrypted');

// 2. Verify: signature, algorithm, issuer, audience and expiry
const check = async (label, jwt, options) => {
  try { const { payload } = await jwtVerify(jwt, secret, { ...expect, ...options }); console.log(`${label.padEnd(36)} OK   sub=${payload.sub} role=${payload.role}`); }
  catch (e) { console.log(`${label.padEnd(36)} FAIL ${e.code}`); }
};
await check('valid token, 1 minute later', token, at(60));
await check('same token, 16 minutes later', token, at(16 * 60));

// 3. Tamper: change the payload to role "admin" and keep the old signature
const forged = Buffer.from(JSON.stringify({ ...JSON.parse(Buffer.from(payload, 'base64url')), role: 'admin' })).toString('base64url');
await check('payload edited to role=admin', `${header}.${forged}.${signature}`, at(60));

// 4. Wrong audience: a token meant for another service
await check('token used at the wrong API', token, { ...at(60), audience: 'billing-api' });

// 5. The "alg: none" trick: an unsigned token
const unsigned = new UnsecuredJWT({ role: 'admin' }).setSubject('user_1').setIssuer(expect.issuer).setAudience(expect.audience).setIssuedAt(NOW).setExpirationTime(NOW + 900).encode();
console.log('unsigned token ends with a dot:', unsigned.endsWith('.'));
await check('alg=none token', unsigned, at(60));

// 6. Signed with a different secret
const other = await new SignJWT({ role: 'admin' }).setProtectedHeader({ alg: 'HS256' }).setSubject('user_1').setIssuer(expect.issuer).setAudience(expect.audience).setIssuedAt(NOW).setExpirationTime(NOW + 900).sign(new TextEncoder().encode('guessed-secret-guessed-secret-guessed!!'));
await check('signed with a guessed secret', other, at(60));
EOF
node hs256.js
```

<Happened>
<Tr>
<En>

- The token is three base64url parts. Decoding the header and payload needed **no key**: anyone who sees a JWT (logs, browser storage, a proxy) can read the claims. Keep them minimal and never put passwords, card numbers or personal details there.
- One minute after issue the token verified; **16 minutes** later `jwtVerify` rejected it with `ERR_JWT_EXPIRED`. Expiry is checked on every request, with no server state.
- Changing `role` to `admin` broke the signature: the HMAC covers the exact bytes of header and payload, and without the secret you can't make a new one.
- The token for `shop-api` failed at `billing-api`: checking **`aud`** stops a token stolen from one service being replayed at another. Checking **`iss`** does the same for tokens from other issuers.
- An **unsigned** token (`alg: none`, empty signature) was refused because we allowed only `HS256`. Old libraries that trusted the header's `alg` accepted such tokens. Always pin `algorithms`.
- A token signed with another secret failed. HS256 is only as strong as the secret: use at least 32 random bytes from the environment, and remember every service that verifies also holds the power to **sign**.

</En>
<Ur>

- Token teen base64url hisse hai. Header aur payload decode karne ke liye **koi key nahi** chahiye thi: jo bhi JWT dekhe (logs, browser storage, proxy) woh claims parh sakta hai. Inhe kam se kam rakhein aur kabhi passwords, card numbers ya zaati tafseelat na rakhein.
- Jaari hone ke ek minute baad token tasdeeq hua; **16 minute** baad `jwtVerify` ne `ERR_JWT_EXPIRED` ke saath rad kiya. Expiry har request par check hoti hai, server state ke baghair.
- `role` ko `admin` karne se signature toot gaya: HMAC header aur payload ke bilkul wahi bytes cover karta hai, aur secret ke baghair aap naya nahi bana sakte.
- `shop-api` ka token `billing-api` par nakam hua: **`aud`** check karna ek service se chura token doosri par chalne se rokta hai. **`iss`** check karna doosre issuers ke tokens ke liye yahi karta hai.
- **Unsigned** token (`alg: none`, khaali signature) rad hua kyunke hum ne sirf `HS256` ki ijazat di. Purani libraries jo header ke `alg` par bharosa karti thin aise tokens qubool kar leti thin. Hamesha `algorithms` tay karein.
- Doosre secret se signed token nakam hua. HS256 utna hi mazboot hai jitna secret: environment se kam az kam 32 random bytes lein, aur yaad rakhein ke tasdeeq karne wali har service ke paas **sign** karne ki taqat bhi hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Asymmetric keys, JWKS, key rotation and revocation">

<Tr>
<En>
Now an **auth server** signs with ES256 private keys and publishes only the **public** keys as a JWKS. The **API** verifies with the JWKS, picking the key by the token's `kid`, and checks a tiny Redis **denylist**. We rotate to a new key, keep the old one during an overlap, retire it, and revoke a token by its `jti` at logout.
</En>
<Ur>
Ab ek **auth server** ES256 private keys se sign karta hai aur sirf **public** keys JWKS ke tor par publish karta hai. **API** JWKS se tasdeeq karti hai, token ke `kid` se key chunti hai, aur Redis ki chhoti **denylist** check karti hai. Hum nayi key par rotate karte hain, overlap ke dauran purani rakhte hain, use hatate hain, aur logout par token ko us ke `jti` se revoke karte hain.
</Ur>
</Tr>

```bash
npm install redis@6.3.1 --silent
redis-cli -n 4 flushdb > /dev/null
cat > es256.js <<'EOF'
import { SignJWT, jwtVerify, generateKeyPair, exportJWK, createLocalJWKSet } from 'jose';
import { createClient } from 'redis';
const NOW = 1_800_000_000;
const clock = { currentDate: new Date((NOW + 60) * 1000) };

// ---- auth server: holds PRIVATE keys and publishes PUBLIC keys as a JWKS ----
const keys = [];
async function addKey(kid) {
  const { privateKey, publicKey } = await generateKeyPair('ES256');
  keys.push({ kid, privateKey, publicJwk: { ...(await exportJWK(publicKey)), kid, alg: 'ES256', use: 'sig' } });
}
const jwks = () => ({ keys: keys.map((k) => k.publicJwk) });         // served at /.well-known/jwks.json
const issue = (sub, jti) => {
  const k = keys.at(-1);                                             // always sign with the newest key
  return new SignJWT({ role: 'customer' }).setProtectedHeader({ alg: 'ES256', kid: k.kid })
    .setSubject(sub).setIssuer('https://auth.example.com').setAudience('shop-api')
    .setIssuedAt(NOW).setExpirationTime(NOW + 900).setJti(jti).sign(k.privateKey);
};

// ---- API: only has the public JWKS, plus a small denylist for logged-out tokens ----
const redis = createClient({ url: 'redis://localhost:6379/4' }); await redis.connect();
async function api(label, token) {
  try {
    const { payload, protectedHeader } = await jwtVerify(token, createLocalJWKSet(jwks()),
      { issuer: 'https://auth.example.com', audience: 'shop-api', algorithms: ['ES256'], ...clock });
    if (await redis.exists(`revoked:${payload.jti}`)) throw Object.assign(new Error(), { code: 'TOKEN_REVOKED' });
    console.log(`${label.padEnd(40)} 200 sub=${payload.sub} (kid ${protectedHeader.kid})`);
  } catch (e) { console.log(`${label.padEnd(40)} 401 ${e.code}`); }
}

await addKey('2026-11');
const oldToken = await issue('user_1', 'tok_a');
console.log('public JWKS has', jwks().keys.length, 'key(s), private key fields present:', 'd' in jwks().keys[0]);
await api('token signed with key 2026-11', oldToken);

// Rotate: add a new key, sign new tokens with it, keep the old public key for a while
await addKey('2026-12');
const newToken = await issue('user_2', 'tok_b');
await api('new token (key 2026-12)', newToken);
await api('old token during the overlap', oldToken);

// Retire the old key once all its tokens have expired
keys.shift();
await api('old token after the old key is removed', oldToken);

// Logout before expiry: remember the jti until the token would have expired anyway
await redis.set('revoked:tok_b', '1', { EX: 900 });
await api('new token after logout (jti revoked)', newToken);
await redis.quit();
EOF
node es256.js
```

```text output
public JWKS has 1 key(s), private key fields present: false
token signed with key 2026-11            200 sub=user_1 (kid 2026-11)
new token (key 2026-12)                  200 sub=user_2 (kid 2026-12)
old token during the overlap             200 sub=user_1 (kid 2026-11)
old token after the old key is removed   401 ERR_JWKS_NO_MATCHING_KEY
new token after logout (jti revoked)     401 TOKEN_REVOKED
```

<Happened>
<Tr>
<En>

- The JWKS contains only **public** key data (`'d' in key` is false: the private part never leaves the auth server). APIs can verify but cannot mint tokens, so a compromised API can't create admin tokens. Real APIs fetch the JWKS with `createRemoteJWKSet(new URL('…/.well-known/jwks.json'))`, which caches it.
- The header's **`kid`** told the API which key to use. After adding key `2026-12`, new tokens used it while old tokens still verified with `2026-11`: rotation with **no forced logout**.
- Once the old key was removed from the JWKS, its remaining tokens failed with `ERR_JWKS_NO_MATCHING_KEY`. Retire a key only after the longest token lifetime has passed.
- A JWT stays valid until `exp`, so logout needs extra work. Storing the `jti` in Redis with a TTL equal to the remaining lifetime blocked it immediately. This brings back a lookup on each request, which is why the bigger defense is **short access tokens**, and refresh tokens that the auth server can revoke.

</En>
<Ur>

- JWKS me sirf **public** key ka data hai (`'d' in key` false hai: private hissa auth server se kabhi bahar nahi jata). APIs tasdeeq kar sakti hain magar tokens bana nahi saktin, isliye hack hui API admin tokens nahi bana sakti. Asal APIs JWKS `createRemoteJWKSet(new URL('…/.well-known/jwks.json'))` se laati hain, jo use cache karta hai.
- Header ke **`kid`** ne API ko bataya kaunsi key lena hai. Key `2026-12` jorne ke baad naye tokens ne use istemal kiya jabke purane tokens `2026-11` se tasdeeq hote rahe: **zabardasti logout ke baghair** rotation.
- Purani key JWKS se hatne par us ke baqi tokens `ERR_JWKS_NO_MATCHING_KEY` ke saath nakam hue. Key tab hatayen jab sab se lambi token umar guzar jaye.
- JWT `exp` tak valid rehta hai, isliye logout ko extra kaam chahiye. `jti` ko baqi umar jitne TTL ke saath Redis me rakhne se woh foran ruk gaya. Is se har request par lookup wapas aata hai, isi liye bara bachao **chhote access tokens** hain, aur refresh tokens jinhe auth server revoke kar sake.

</Ur>
</Tr>
</Happened>

<Compare>
<Bad title="Long-lived tokens full of data">

```text
sign({ id: 1, email, phone, address, role: 'admin', permissions: [...] }, secret, { expiresIn: '30d' })
// readable by anyone, stale for a month, impossible to revoke
```

</Bad>
<Good title="Small, short-lived access token plus a refresh token">

```text
access:  { sub: 'user_1', role: 'customer' }, exp 15 minutes
refresh: random opaque string stored (hashed) by the auth server, rotated on each use
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Storing tokens in `localStorage`**: any XSS can steal them. For browser apps prefer HttpOnly cookies (or sessions).
- **Using `jwt.decode()` anywhere for decisions**: decode is for debugging; only verified claims count.
- **Accepting any algorithm**: pin `algorithms`; never let the token choose between HMAC and RSA with the same key.
- **No `aud` / `iss` checks**: tokens from other services or tenants get accepted.
- **Trusting stale claims**: a role in a token stays until expiry; re-check critical permissions on the server.
- **Weak HS256 secrets** like `secret` or a word: they can be brute-forced offline from any token.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Tokens `localStorage` me rakhna**: koi bhi XSS unhe chura sakta hai. Browser apps ke liye HttpOnly cookies (ya sessions) behtar hain.
- **Faislon ke liye kahin bhi `jwt.decode()`**: decode debugging ke liye hai; sirf tasdeeq shuda claims maane jate hain.
- **Koi bhi algorithm qubool karna**: `algorithms` tay karein; token ko ek hi key ke saath HMAC aur RSA me chunne na dein.
- **`aud` / `iss` checks nahi**: doosri services ya tenants ke tokens qubool ho jate hain.
- **Purane claims par bharosa**: token me role expiry tak rehta hai; ahem ijazaten server par dobara check karein.
- **Kamzor HS256 secrets** jaise `secret` ya koi lafz: kisi bhi token se offline brute-force ho sakte hain.

</Ur>
</Tr>

<DeepDive title="More about JWTs">

**Algorithms.** HS256 (shared secret) is fine when one service both signs and verifies. RS256 is the most widely supported asymmetric choice; ES256 and EdDSA give smaller keys and signatures.

**Clock skew.** Servers' clocks differ slightly; libraries accept a small `clockTolerance` (for example 30 seconds) for `exp` and `nbf`.

**Opaque vs JWT access tokens.** Opaque tokens are random strings checked against the auth server (introspection); revocable, but need a lookup. JWTs avoid the lookup. Some systems use opaque tokens externally and JWTs internally.

**Sender-constrained tokens.** DPoP and mutual TLS bind a token to a key the client holds, so a stolen token is useless on its own.

**Libraries.** `jose` works in Node.js, browsers, Deno and edge runtimes; `jsonwebtoken` is older and Node-only. In NestJS, `@nestjs/jwt` and Passport's JWT strategy wrap the same ideas.

</DeepDive>

<DeepDive title="Real world: the secret in the sample code">

A company's API verified HS256 tokens with a secret that had been copied from a tutorial years earlier: a short English phrase. A security researcher took a token from the public mobile app, ran an offline dictionary attack against its signature, and found the secret within minutes. With it, they could sign tokens for any user, including admins.

The response:

1. Switched to ES256: the private key lives only in the auth service (in a KMS), and APIs load the JWKS.
2. Access tokens shortened from 24 hours to 10 minutes, with rotating refresh tokens.
3. Every service now pins `algorithms`, `iss` and `aud`, enforced by a shared verification library.
4. Secret scanning in CI and a rule that no secrets appear in sample code or documentation.

</DeepDive>

<DeepDive title="Security lens">

- **Algorithm confusion**: accepting `alg: none`, or verifying an RS256 public key as an HS256 secret. Pin algorithms per key.
- **Token leakage**: tokens in URLs end up in logs and referrers; send them in headers or cookies only.
- **XSS**: tokens readable by JavaScript can be exfiltrated; HttpOnly cookies limit that, and CSRF protection then becomes necessary.
- **Key management**: keep private keys in a KMS or secret manager, rotate on a schedule and immediately after a suspected leak.
- **Sensitive claims**: payloads are visible; if you must carry private data, use JWE or, better, look it up on the server.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a JWT and how is it verified?">
A compact token of base64url header, payload and signature. The verifier recomputes or checks the signature with the shared secret or the issuer's public key, using an algorithm it expects, then validates claims such as expiry, issuer and audience before trusting the payload.
</QA>

<QA q="What are the downsides of JWTs?">
They can't be revoked easily before expiry, the payload is readable, claims can go stale, they are larger than session ids, and misconfigured verification such as accepting none or not checking audience leads to serious vulnerabilities.
</QA>

<QA q="Why use access and refresh tokens?">
Short-lived access tokens limit the damage of theft and stale claims without a lookup per request. Long-lived refresh tokens are stored and checked by the auth server, so they can be rotated, revoked and monitored for reuse.
</QA>

<QA q="HS256 or RS256?">
HS256 uses one shared secret for signing and verifying, so every verifier can also sign. RS256 or ES256 sign with a private key and verify with a public key, so many services can verify while only the issuer can sign, and keys can be published as a JWKS.
</QA>

<QA q="Where should a browser app store tokens?">
Preferably not in localStorage. Use HttpOnly, Secure, SameSite cookies, often via a backend-for-frontend that keeps tokens server-side and gives the browser a session cookie.
</QA>

</DeepDive>
