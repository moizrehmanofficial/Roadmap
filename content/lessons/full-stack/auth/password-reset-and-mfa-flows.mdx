<BigIdea>
<Tr>
<En>
A login is only as strong as its **recovery path**: if "forgot password" can be abused, nobody needs to crack the password. A safe reset flow **gives the same answer whether or not the email exists**, emails a **long random token** that is **stored only as a hash**, **expires in minutes**, works **once**, and on success **changes the password, logs out every session and notifies the user**. **Multi-factor authentication (MFA)** adds something you **have** to something you **know**. The common second factor is **TOTP**: the server and the user's authenticator app share a secret, and both compute a 6-digit code from that secret and the current 30-second time window, so the code changes constantly and needs no network. To be safe it also needs a small **drift window**, **replay protection**, **rate limits** (only a million possible codes) and **single-use recovery codes** for lost phones. Stronger still are **passkeys / WebAuthn**, which can't be phished; SMS codes are the weakest option.
</En>
<Ur>
Login utna hi mazboot hai jitna us ka **recovery ka rasta**: agar "forgot password" ka ghalat istemal ho sake to kisi ko password torne ki zaroorat nahi. Mehfooz reset flow **email mojood ho ya na ho, ek jaisa jawab deta hai**, **lamba random token** email karta hai jo **sirf hash ki shakal me rakha** jata hai, **minton me expire** hota hai, **ek dafa** chalta hai, aur kamyabi par **password badalta, har session se logout karta aur user ko ittila deta** hai. **Multi-factor authentication (MFA)** jo aap **jante** hain us me jo aap ke **paas** hai woh jorta hai. Aam doosra factor **TOTP** hai: server aur user ki authenticator app ek raaz share karte hain, aur dono us raaz aur mojooda 30 second ki khirki se 6 hindson ka code banate hain, isliye code musalsal badalta hai aur network nahi chahiye. Mehfooz rehne ke liye ise chhoti **drift khirki**, **replay se hifazat**, **rate limits** (sirf das lakh mumkin codes) aur gum phones ke liye **ek dafa wale recovery codes** bhi chahiye. Is se bhi mazboot **passkeys / WebAuthn** hain jinhe phish nahi kiya ja sakta; SMS codes sab se kamzor hain.
</Ur>

## Picture it

<Tr>
<En>

Think of a hotel when a guest loses their key card.

- The front desk won't say "yes, Jane is staying in room 512" to anyone who asks. It says "if you're a guest, we'll help you", and sends a one-time code to the phone already on file: no leaking who's a guest.
- The code works once, for a few minutes. When the new card is made, **every old card stops working**, including any a thief might hold.
- MFA is the **safe in the room**: even with the key card, you need the PIN that only you know, or here, the code on your phone that changes every 30 seconds.
- Recovery codes are the **sealed envelope at reception** with a spare PIN, usable once if you forget yours.

</En>
<Ur>

Socheyn ek mehman ka key card gum ho jaye to hotel kya karta hai.

- Front desk har poochhne wale ko "haan, Jane kamra 512 me hai" nahi kehta. Woh kehta hai "agar aap mehman hain to hum madad karenge", aur pehle se darj phone par ek dafa ka code bhejta hai: kaun mehman hai ye leak nahi hota.
- Code ek dafa, chand minton ke liye chalta hai. Naya card bante hi **har purana card band** ho jata hai, chor ke paas wala bhi.
- MFA kamre ki **tijori** hai: key card ke saath bhi woh PIN chahiye jo sirf aap jante hain, ya yahan, aap ke phone par har 30 second badalne wala code.
- Recovery codes **reception par band lifafa** hain jis me extra PIN hai, apna bhool jayen to ek dafa istemal ho sakta hai.

</Ur>

<Walkthrough>

<Step title="A password reset flow that doesn't leak or linger">

<Tr>
<En>
`reset.js` keeps users, sessions and reset tokens in memory (a database in real life), with a **fake clock** so we can jump forward 20 minutes. "Sent" emails go to an `outbox` array. We request resets for an unknown and a known email, then try an expired link, a guessed token, a weak password, the real link, and the same link twice.
</En>
<Ur>
`reset.js` users, sessions aur reset tokens memory me rakhta hai (asal me database), **nakli ghari** ke saath taa ke hum 20 minute aage ja sakein. "Bheji gayi" emails `outbox` array me jati hain. Hum na maloom aur maloom email ke liye reset maangte hain, phir expired link, guess kiya token, kamzor password, asli link, aur wahi link do dafa aazmate hain.
</Ur>
</Tr>

```bash
cat > reset.js <<'EOF'
import { randomBytes, createHash, scryptSync, timingSafeEqual } from 'node:crypto';

let now = Date.parse('2026-11-23T10:00:00Z');              // fake clock so we can jump forward
const minutes = (m) => { now += m * 60_000; };
const sha256 = (s) => createHash('sha256').update(s).digest('hex');
const hashPw = (pw, salt = randomBytes(16).toString('hex')) => `${salt}:${scryptSync(pw, salt, 32).toString('hex')}`;
const checkPw = (pw, stored) => { const [s, h] = stored.split(':'); return timingSafeEqual(Buffer.from(h, 'hex'), scryptSync(pw, s, 32)); };

const users = new Map([['jane@example.com', { id: 1, passwordHash: hashPw('old password 123') }]]);
const sessions = new Set(['sess-laptop', 'sess-phone']);         // Jane is logged in on two devices
const resetTokens = new Map();                                   // sha256(token) -> { userId, expiresAt, used }
const outbox = [];

// Step 1: "Forgot password?" -- the same answer whether or not the email exists
function requestReset(email) {
  const user = users.get(email.trim().toLowerCase());
  if (user) {
    const token = randomBytes(32).toString('base64url');            // 256 bits, unguessable
    resetTokens.set(sha256(token), { userId: user.id, expiresAt: now + 15 * 60_000, used: false });
    outbox.push({ to: email, link: `https://shop.example.com/reset?token=${token}` });
  }
  return 'If that email has an account, we sent a reset link.';
}
// Step 2: the link is opened and a new password submitted
function resetPassword(token, newPassword) {
  const rec = resetTokens.get(sha256(token));
  if (!rec || rec.used || now > rec.expiresAt) return 'invalid or expired link';
  if (newPassword.length < 12) return 'password too short';
  rec.used = true;                                                 // single use
  for (const [k, r] of resetTokens) if (r.userId === rec.userId) resetTokens.delete(k);   // kill other pending links
  const user = [...users.values()].find((u) => u.id === rec.userId);
  user.passwordHash = hashPw(newPassword);
  sessions.clear();                                                // log out everywhere
  outbox.push({ to: 'jane@example.com', note: 'Your password was changed. Not you? Contact support.' });
  return 'password changed';
}
const login = (email, pw) => { const u = users.get(email); return u && checkPw(pw, u.passwordHash) ? 'logged in' : 'wrong email or password'; };
const tokenFromEmail = () => new URL(outbox.at(-1).link).searchParams.get('token');

console.log('reset for unknown email :', requestReset('nobody@example.com'));
console.log('reset for Jane          :', requestReset('Jane@Example.com'));
console.log('emails sent so far      :', outbox.length);
const t1 = tokenFromEmail();
console.log('stored in the database  : a', [...resetTokens.keys()][0].length, 'char SHA-256 hash; raw token stored?', resetTokens.has(t1));

minutes(20);
console.log('link used after 20 min  :', resetPassword(t1, 'brand new password!'));
requestReset('jane@example.com');
const t2 = tokenFromEmail();
minutes(3);
console.log('guessed token           :', resetPassword(randomBytes(32).toString('base64url'), 'brand new password!'));
console.log('new link, short password:', resetPassword(t2, 'short'));
console.log('new link, good password :', resetPassword(t2, 'brand new password!'));
console.log('same link again         :', resetPassword(t2, 'another password!!'));
console.log('login, old password     :', login('jane@example.com', 'old password 123'));
console.log('login, new password     :', login('jane@example.com', 'brand new password!'));
console.log('sessions still active   :', sessions.size);
console.log('last email              :', outbox.at(-1).note);
EOF
node reset.js
```

<Happened>
<Tr>
<En>

- The unknown email and Jane's email got the **same message**, and only one email was actually sent: an attacker can't use this form to find out who has an account. (Keep the **timing** similar too, for example by sending emails from a background queue.)
- The database stores the token's **SHA-256 hash**, not the token. Anyone who reads the database (a leak, a backup, a curious admin) can't use pending links. A fast hash is fine here because the token is 256 random bits; passwords need slow hashes because people choose guessable ones.
- The first link failed after **20 minutes** (15-minute expiry). A **guessed** token failed. The new link rejected a **short** password, then worked, then **failed the second time**: tokens are single use, and any other pending links for the user are deleted.
- After the reset the old password stopped working, the new one worked, **every session ended** (an attacker logged in with the old password is kicked out), and Jane got a "your password was changed" email, her chance to react if it wasn't her.
- Email addresses were normalized (`Jane@Example.com` → `jane@example.com`) so the same account is always found.

</En>
<Ur>

- Na maloom email aur Jane ki email ko **ek jaisa paigham** mila, aur asal me sirf ek email gayi: hamla awar is form se nahi jaan sakta ke kis ka account hai. (**Waqt** bhi milta julta rakhein, maslan emails background queue se bhej kar.)
- Database token nahi, us ka **SHA-256 hash** rakhta hai. Jo bhi database parhe (leak, backup, tajassus wala admin) woh baqi links istemal nahi kar sakta. Yahan tez hash theek hai kyunke token 256 random bits hai; passwords ko sust hash chahiye kyunke log guess hone wale chunte hain.
- Pehla link **20 minute** baad nakam hua (15 minute expiry). **Guess** kiya token nakam hua. Naye link ne **chhota** password rad kiya, phir chala, phir **doosri dafa nakam** hua: tokens ek dafa ke hain, aur user ke baqi pending links mita diye jate hain.
- Reset ke baad purana password band hua, naya chala, **har session khatam** hua (purane password se logged in hamla awar bahar), aur Jane ko "your password was changed" email mili, agar woh na ho to us ka react karne ka mauqa.
- Email addresses normalize kiye gaye (`Jane@Example.com` → `jane@example.com`) taa ke hamesha wahi account mile.

</Ur>
</Tr>

<Step title="TOTP from scratch, plus the parts that make MFA safe">

<Tr>
<En>
`totp.js` implements HOTP/TOTP in a few lines of `node:crypto` and checks it against **RFC 6238's official test vectors**. Then it enrolls a user with a random secret and an `otpauth://` URI (what the QR code contains), verifies codes with a ±1 step drift window and replay protection, issues hashed **recovery codes**, and locks after **5 wrong codes**. All times are fixed so the output is repeatable. In production use a maintained library (for example `otplib`), but knowing the mechanics helps you configure it correctly.
</En>
<Ur>
`totp.js` `node:crypto` ki chand lines me HOTP/TOTP banata hai aur use **RFC 6238 ke sarkari test vectors** se check karta hai. Phir random secret aur `otpauth://` URI (jo QR code me hota hai) se user ko enroll karta hai, ±1 step drift khirki aur replay hifazat ke saath codes check karta hai, hash shuda **recovery codes** deta hai, aur **5 ghalat codes** par lock karta hai. Saare waqt mustaqil hain taa ke output dohraya ja sake. Production me maintained library (maslan `otplib`) lein, magar andar ka nizam jaanna use sahi configure karne me madad deta hai.
</Ur>
</Tr>

```bash
cat > totp.js <<'EOF'
import { createHmac, randomBytes, createHash, timingSafeEqual } from 'node:crypto';

// ---- TOTP (RFC 6238): HMAC of the current 30-second step, cut down to 6 digits ----
function hotp(secret, counter, digits = 6) {
  const msg = Buffer.alloc(8); msg.writeBigUInt64BE(BigInt(counter));
  const h = createHmac('sha1', secret).update(msg).digest();
  const offset = h[h.length - 1] & 0xf;
  const bin = (h.readUInt32BE(offset) & 0x7fffffff) % 10 ** digits;
  return String(bin).padStart(digits, '0');
}
const step = (unixSeconds) => Math.floor(unixSeconds / 30);
const totp = (secret, unixSeconds, digits) => hotp(secret, step(unixSeconds), digits);

// 1. Check the implementation against the official RFC 6238 test vectors (8 digits, SHA-1)
const rfcSecret = Buffer.from('12345678901234567890');
for (const [t, expected] of [[59, '94287082'], [1111111109, '07081804'], [2000000000, '69279037']])
  console.log(`RFC test t=${String(t).padEnd(10)} ${totp(rfcSecret, t, 8)} ${totp(rfcSecret, t, 8) === expected ? 'matches' : 'WRONG'}`);

// 2. Enrollment: a random secret, shown once as a QR code (otpauth URI) for the authenticator app
const base32 = (buf) => { const a = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ234567'; let bits = '', out = ''; for (const b of buf) bits += b.toString(2).padStart(8, '0'); for (let i = 0; i + 5 <= bits.length; i += 5) out += a[parseInt(bits.slice(i, i + 5), 2)]; return out; };
const secret = randomBytes(20);
const uri = `otpauth://totp/Shop:jane@example.com?secret=${base32(secret)}&issuer=Shop&digits=6&period=30`;
console.log('enrollment URI:', uri.replace(/secret=\w+/, 'secret=<32 base32 chars>'), '| secret length', base32(secret).length);

// 3. Verification on the server: allow one step of clock drift, never accept the same step twice
const user = { secret, lastStep: -1, failures: 0, recovery: [] };
function verifyCode(code, now) {
  if (user.failures >= 5) return 'locked: too many attempts';
  for (const drift of [-1, 0, 1]) {
    const s = step(now) + drift;
    if (timingSafeEqual(Buffer.from(hotp(user.secret, s)), Buffer.from(code.padEnd(6).slice(0, 6)))) {
      if (s <= user.lastStep) return 'rejected: code already used';
      user.lastStep = s; user.failures = 0; return 'ok';
    }
  }
  user.failures++; return 'wrong code';
}
const T = 1_800_000_000;                                           // fixed "now"
const phone = (t) => totp(secret, t);                              // what the authenticator app shows
console.log('code from the phone        :', verifyCode(phone(T), T));
console.log('same code again (replay)   :', verifyCode(phone(T), T + 5));
console.log('phone clock 30s behind     :', verifyCode(phone(T + 30), T + 60));
console.log('code from 2 minutes ago    :', verifyCode(phone(T - 120), T + 60));

// 4. Recovery codes: shown once, stored hashed, each works one time
const sha = (s) => createHash('sha256').update(s).digest('hex');
const codes = Array.from({ length: 8 }, () => randomBytes(5).toString('hex').match(/.{5}/g).join('-'));
user.recovery = codes.map(sha);
const useRecovery = (c) => { const i = user.recovery.indexOf(sha(c)); if (i < 0) return 'invalid recovery code'; user.recovery.splice(i, 1); return `ok, ${user.recovery.length} left`; };
console.log('recovery code format       :', codes[0].replace(/\w/g, 'x'));
console.log('use a recovery code        :', useRecovery(codes[0]));
console.log('use it again               :', useRecovery(codes[0]));

// 5. Brute force: 1,000,000 possible codes, so attempts must be limited
for (let i = 0; i < 4; i++) verifyCode('000000', T + 90);    // plus the one wrong code above = 5
console.log('after 5 wrong codes        :', verifyCode(phone(T + 90), T + 90));
EOF
node totp.js
```

<Happened>
<Tr>
<En>

- Our implementation produced exactly the RFC's codes, so the algorithm is right: HMAC-SHA1 over the 30-second step counter, then "dynamic truncation" to a number, cut to 6 (or 8) digits. The phone and server never talk; they just share the secret and the time.
- Enrollment created a 160-bit random secret, base32-encoded to 32 characters, inside an `otpauth://` URI the app scans as a QR code. Store the secret **encrypted** and activate MFA only after the user types one valid code, which proves the app was set up correctly.
- The phone's code worked; the **same code a few seconds later was rejected**, because we remember the last used step. Without this, a code seen over someone's shoulder or captured by a phishing page could be reused within the window.
- A phone whose clock was **30 seconds behind** still worked thanks to the ±1 step window; a code from **2 minutes ago** didn't. Wider windows make guessing easier.
- Recovery codes are random, **stored as hashes**, and each worked **once**. Show them once at setup, let users regenerate them, and count each use as a security event.
- With only a million possible codes (three accepted per attempt), unlimited guessing would succeed eventually, so after **5 wrong codes** the account locks (or slows down). Notify the user too: someone who gets that far already knows the password.

</En>
<Ur>

- Hamari implementation ne bilkul RFC wale codes banaye, isliye algorithm sahi hai: 30 second step counter par HMAC-SHA1, phir "dynamic truncation" se number, 6 (ya 8) hindson tak kata hua. Phone aur server kabhi baat nahi karte; bas raaz aur waqt share karte hain.

<Tr>
<En>

More mistakes to avoid:

- **Reset tokens in logs and analytics**: the URL appears in server logs, `Referer` headers and analytics tools. Exchange it for a short session on first load, or strip it.
- **Host header injection**: building the link from the request's `Host` header lets attackers send victims links to the attacker's domain. Use a configured base URL.
- **Not ending sessions** after a reset or password change: the attacker stays logged in.
- **Disabling MFA with only a password**: require an MFA code (or recovery code) to turn MFA off or change the phone.
- **Storing TOTP secrets in plain text**: a database leak would let attackers generate codes. Encrypt them with a key outside the database.
- **Support resets MFA too easily**: social engineering of support staff bypasses everything; require strong identity checks.

</En>

<DeepDive title="More about resets and MFA">

**Passkeys (WebAuthn / FIDO2).** The device creates a key pair per site; the private key never leaves it, and the browser binds each signature to the real domain, so phishing pages get nothing usable. Libraries such as SimpleWebAuthn handle the server side. Passkeys can replace passwords entirely.

**Magic links and email codes.** Passwordless login with the same rules as reset tokens: random, hashed, short-lived, single use. Their security equals that of the user's email account.

**Push and number matching.** Apps like Microsoft Authenticator send a push; showing a number the user must type defeats "MFA fatigue" attacks where users approve random prompts.

**Step-up authentication.** Ask for MFA again for sensitive actions, and record how the user authenticated (`amr`, `acr` claims in OIDC).

**Password rules.** NIST guidance: long passwords (at least 8, encourage 15+), allow all characters, check against breached-password lists (Have I Been Pwned's k-anonymity API), no forced periodic changes, no composition rules.

</DeepDive>

<DeepDive title="Real world: the reset link that went to the attacker">

A web app built password reset links from the incoming request's `Host` header. An attacker requested a reset for a victim's email, but sent the request with `Host: attacker.example`. The app emailed the victim a genuine-looking message whose link pointed to the attacker's server. When the victim clicked it (or their email scanner previewed it), the token arrived in the attacker's logs, and the attacker reset the password.

The fixes:

1. All links built from a configured `APP_URL`, never from request headers; the reverse proxy rejects unknown hosts.
2. Reset tokens shortened to 15 minutes and bound to a single use.
3. Resetting the password ends all sessions and emails the user; MFA, if enabled, is still required after the reset.
4. Security tests for Host header injection added to CI.

</DeepDive>

<DeepDive title="Security lens">

- **Rate limit** reset requests per email and IP, and MFA attempts per account.
- **Recovery is an attack surface**: security questions are weak; support-driven MFA resets need verification and a waiting period.
- **SIM swap** makes SMS codes unreliable for high-value accounts; prefer TOTP or passkeys.
- **Audit and notify** on password changes, MFA changes, recovery code use and logins from new devices.
- **Constant-time comparisons** for codes and tokens, and never log them.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you design a secure password reset?">
Respond identically for any email, generate a long random single-use token, store only its hash with a short expiry, send it by email to the address on file using a configured base URL, and on reset validate the token, enforce password rules, invalidate other tokens and sessions, and notify the user.
</QA>

<QA q="How does TOTP work?">
The server and authenticator share a secret. Both compute an HMAC of the secret and the number of 30-second intervals since the Unix epoch, then truncate it to a 6-digit code. The server accepts the current code with a small drift window and rejects reused steps.
</QA>

<QA q="Why are passkeys more secure than OTP codes?">
They use public-key cryptography bound to the site's origin, so there is no shared secret to steal from the server and nothing a user can type into a phishing site. OTP codes can be phished and relayed in real time.
</QA>

<QA q="What are recovery codes and how should they be stored?">
Single-use backup codes generated at MFA setup for when the device is lost. They are shown once, stored as hashes, removed after use, regenerable, and their use triggers a notification.
</QA>

<QA q="What is account enumeration and where does it happen?">
Learning whether an account exists from differences in responses or timing, typically on login, registration and password reset forms. Prevent it with uniform messages, similar timing and rate limiting.
</QA>

</DeepDive>
