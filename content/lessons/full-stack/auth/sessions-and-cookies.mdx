<BigIdea>
<Tr>
<En>
HTTP is **stateless**: each request arrives on its own, and the server has no built-in idea that it came from the person who logged in a minute ago. A **cookie** fixes that: the server sends `Set-Cookie: sid=…`, and the browser automatically sends `Cookie: sid=…` back with every later request to that site. With **server-side sessions**, the cookie holds only a long **random, signed session id**; the actual data (user id, cart, roles) lives on the server in a **session store** such as Redis or a database. That makes logout real (delete the session and the cookie is worthless), lets you end sessions remotely, and keeps secrets out of the browser. Safety comes from a few rules: cookie attributes **HttpOnly** (JavaScript can't read it), **Secure** (HTTPS only), **SameSite=Lax** (not sent on most cross-site requests), a sensible **expiry**; **a new session id at login** (against session fixation); **destroying the session on logout**; and never storing passwords, only salted hashes.
</En>
<Ur>
HTTP **stateless** hai: har request akeli aati hai, aur server ko khud se ye andaza nahi ke ye usi shakhs ki hai jo ek minute pehle login hua. **Cookie** ye hal karti hai: server `Set-Cookie: sid=…` bhejta hai, aur browser us site ki har agli request ke saath khud `Cookie: sid=…` wapas bhejta hai. **Server-side sessions** me cookie sirf ek lambi **random, signed session id** rakhti hai; asal data (user id, cart, roles) server par **session store** me rehta hai, jaise Redis ya database. Is se logout asli hota hai (session mitao aur cookie bekaar), aap sessions door se khatam kar sakte hain, aur raaz browser se bahar rehte hain. Hifazat chand usoolon se aati hai: cookie attributes **HttpOnly** (JavaScript parh nahi sakta), **Secure** (sirf HTTPS), **SameSite=Lax** (zyadatar cross-site requests par nahi jati), munasib **expiry**; **login par nayi session id** (session fixation ke khilaf); **logout par session destroy**; aur passwords kabhi nahi, sirf salted hashes rakhna.
</Ur>

## Picture it

<Tr>
<En>

Think of a coat check at a theater.

- You hand over your coat and get a **numbered ticket**. The ticket is the cookie; the coat stays behind the counter (the session store).
- The ticket number is random and stamped (signed), so you can't write a different number on it and walk off with someone else's coat.
- When you leave, the attendant takes your coat back and **tears up the ticket**: logout destroys the session, and an old ticket is worthless.
- A stranger who hands you a ticket before you check your coat can't use it later, because the attendant gives you a **fresh ticket** when you actually hand over the coat (new session id at login).
- If the theater changes staff mid-show, your coat is still on the rack, because the rack isn't in anyone's pocket (sessions in Redis survive app restarts).

</En>
<Ur>

Theater ka coat check socheyn.

- Aap coat dete hain aur **number wala ticket** milta hai. Ticket cookie hai; coat counter ke peeche rehta hai (session store).
- Ticket ka number random aur mohar laga (signed) hai, isliye aap us par doosra number likh kar kisi aur ka coat nahi le ja sakte.
- Jate waqt attendant coat wapas deta aur **ticket phaar deta** hai: logout session mitata hai, aur purana ticket bekaar hai.
- Koi ajnabi coat dene se pehle aap ko ticket thama de to baad me use istemal nahi kar sakta, kyunke asal me coat dene par attendant **naya ticket** deta hai (login par nayi session id).
- Show ke beech staff badal jaye to bhi aap ka coat rack par hai, kyunke rack kisi ki jeb me nahi (Redis me sessions app restart ke baad bhi rehte hain).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Login, the session cookie, and a real logout">

<Tr>
<En>
`app.js` is an Express app with `express-session` storing sessions in Redis. Passwords are checked against salted **scrypt** hashes. Login copies the cart over and calls `regenerate()` for a fresh session id; logout calls `destroy()`. `client.js` acts like a tiny browser that keeps the `sid` cookie. `demo1.js` walks through the life of one session.
</En>
<Ur>
`app.js` ek Express app hai jo `express-session` se sessions Redis me rakhti hai. Passwords salted **scrypt** hashes se check hote hain. Login cart saath le jata aur nayi session id ke liye `regenerate()` bulata hai; logout `destroy()` bulata hai. `client.js` ek chhote browser ki tarah `sid` cookie rakhta hai. `demo1.js` ek session ki poori zindagi dikhata hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module
npm install express@5.1.0 express-session@1.19.0 connect-redis@11.0.0 redis@6.3.1 --silent
redis-cli -n 3 flushdb > /dev/null
cat > app.js <<'EOF'
import express from 'express';
import session from 'express-session';
import { RedisStore } from 'connect-redis';
import { createClient } from 'redis';
import { scryptSync, randomBytes, timingSafeEqual } from 'node:crypto';

// Passwords are stored as salted scrypt hashes, never in plain text
const hash = (password, salt = randomBytes(16).toString('hex')) => `${salt}:${scryptSync(password, salt, 32).toString('hex')}`;
const verify = (password, stored) => { const [salt, h] = stored.split(':'); return timingSafeEqual(Buffer.from(h, 'hex'), scryptSync(password, salt, 32)); };
const users = { 'jane@example.com': { id: 1, name: 'Jane Doe', passwordHash: hash('correct horse battery') } };

export const redis = createClient({ url: 'redis://localhost:6379/3' });
await redis.connect();

export function createApp() {
  const app = express();
  app.use(express.json());
  app.use(session({
    store: new RedisStore({ client: redis, prefix: 'sess:' }),
    name: 'sid',
    secret: process.env.SESSION_SECRET ?? 'dev-only-secret-change-me',
    resave: false,
    saveUninitialized: false,             // no session (and no cookie) until we store something
    rolling: true,                        // every request pushes the expiry forward
    cookie: { httpOnly: true, sameSite: 'lax', secure: process.env.NODE_ENV === 'production', maxAge: 30 * 60 * 1000 },
  }));

  app.post('/cart', (req, res) => { req.session.cart = ['book']; res.json({ cart: req.session.cart }); });
  app.post('/login', (req, res, next) => {
    const user = users[req.body.email];
    if (!user || !verify(req.body.password, user.passwordHash)) return res.status(401).json({ error: 'wrong email or password' });
    const cart = req.session.cart;
    req.session.regenerate(async (err) => {              // new session id at login: stops session fixation
      if (err) return next(err);
      Object.assign(req.session, { userId: user.id, cart });
      await redis.sAdd(`user_sessions:${user.id}`, req.sessionID);
      res.json({ hello: user.name });
    });
  });
  const requireLogin = (req, res, next) => (req.session.userId ? next() : res.status(401).json({ error: 'log in first' }));
  app.get('/me', requireLogin, (req, res) => res.json({ userId: req.session.userId, cart: req.session.cart }));
  app.post('/logout', requireLogin, (req, res, next) => {
    const { sessionID: id, session: { userId } } = req;
    req.session.destroy(async (err) => {                // delete it on the server, not just the cookie
      if (err) return next(err);
      await redis.sRem(`user_sessions:${userId}`, id);
      res.clearCookie('sid').json({ bye: true });
    });
  });
  app.post('/logout-everywhere', requireLogin, async (req, res) => {
    const ids = await redis.sMembers(`user_sessions:${req.session.userId}`);
    if (ids.length) await redis.del([...ids.map((id) => `sess:${id}`), `user_sessions:${req.session.userId}`]);
    res.clearCookie('sid').json({ endedSessions: ids.length });
  });
  return app;
}
EOF
cat > client.js <<'EOF'
// A tiny "browser": remembers the sid cookie it receives and sends it back
export function browser(port) {
  let cookie = null;
  return {
    get cookie() { return cookie; }, set cookie(c) { cookie = c; },
    async call(method, path, body) {
      const res = await fetch(`http://localhost:${port}${path}`, { method, headers: { 'content-type': 'application/json', ...(cookie && { cookie }) }, body: body && JSON.stringify(body) });
      const set = res.headers.get('set-cookie');
      if (set) cookie = set.split(';')[0];
      return { status: res.status, setCookie: set, body: await res.text() };
    },
  };
}
EOF
cat > demo1.js <<'EOF'
import { createApp, redis } from './app.js';
import { browser } from './client.js';
const server = createApp().listen(3000);
const b = browser(3000);
const show = (label, r) => console.log(`${label.padEnd(34)} -> ${r.status} ${r.body}`);
const sid = () => decodeURIComponent(b.cookie.split('=')[1]).slice(2).split('.')[0];   // "s:<id>.<signature>"

show('GET /me (no cookie)', await b.call('GET', '/me'));
show('POST /login (wrong password)', await b.call('POST', '/login', { email: 'jane@example.com', password: 'guess' }));
console.log('cookie so far:', b.cookie);
await b.call('POST', '/cart');
const before = sid();
const login = await b.call('POST', '/login', { email: 'jane@example.com', password: 'correct horse battery' });
show('POST /login (right password)', login);
console.log('Set-Cookie attributes:', login.setCookie.split('; ').slice(1).map((a) => a.split('=')[0]).join(', '));
console.log('session id changed at login:', before !== sid() ? 'yes' : 'NO');
show('GET /me (with cookie)', await b.call('GET', '/me'));

const stored = JSON.parse(await redis.get(`sess:${sid()}`));
console.log('stored in Redis:', JSON.stringify({ userId: stored.userId, cart: stored.cart, httpOnly: stored.cookie.httpOnly }));
const ttl = await redis.ttl(`sess:${sid()}`);
console.log('expires in about 30 minutes:', ttl > 1790 && ttl <= 1800 ? 'yes' : `no (${ttl})`);

const old = b.cookie;
show('POST /logout', await b.call('POST', '/logout'));
console.log('session still in Redis after logout:', (await redis.exists(`sess:${before}`)) + (await redis.exists(`sess:${sid()}`)) ? 'yes' : 'no');
b.cookie = old;
show('GET /me (old cookie replayed)', await b.call('GET', '/me'));
server.close(); await redis.quit();
EOF
node demo1.js
```

<Happened>
<Tr>
<En>

- Without a cookie, `/me` answered **401**. A wrong password also got 401 and **no cookie**: with `saveUninitialized: false`, no session is created until there's something to store.
- Adding to the cart created an anonymous session. At login, `regenerate()` gave the browser a **new session id** and we copied the cart into it. If an attacker had planted a session id in the victim's browser before login (**session fixation**), it now points nowhere.
- The `Set-Cookie` header carried **HttpOnly** and **SameSite**. `Secure` is turned on in production (`NODE_ENV=production`), because it stops the cookie being sent over plain HTTP, which this local demo uses.
- Redis holds the real data (`userId`, the cart) under `sess:<id>`, with a TTL of about 30 minutes. The browser only has the id. `rolling: true` moves the expiry forward on each request, giving an idle timeout.
- Logout **destroyed** the session in Redis. Replaying the old cookie afterwards got 401: the server, not the browser, decides whether a session exists. Clearing the cookie alone wouldn't have been enough.

</En>
<Ur>

- Cookie ke baghair `/me` ne **401** diya. Ghalat password ko bhi 401 mila aur **koi cookie nahi**: `saveUninitialized: false` ke saath jab tak rakhne ko kuch na ho session nahi banta.
- Cart me daalne se gumnaam session bana. Login par `regenerate()` ne browser ko **nayi session id** di aur hum ne cart us me copy kiya. Agar hamla awar ne login se pehle victim ke browser me session id laga di hoti (**session fixation**), to woh ab kahin nahi le jati.
- `Set-Cookie` header me **HttpOnly** aur **SameSite** the. `Secure` production (`NODE_ENV=production`) me on hota hai, kyunke woh saade HTTP par cookie bhejna rokta hai, jo ye local demo istemal karta hai.
- Asal data (`userId`, cart) Redis me `sess:<id>` ke neeche hai, taqreeban 30 minute TTL ke saath. Browser ke paas sirf id hai. `rolling: true` har request par expiry aage barhata hai, jo idle timeout deta hai.
- Logout ne Redis me session **destroy** kiya. Us ke baad purani cookie dobara bhejne par 401 mila: session mojood hai ya nahi ye server tay karta hai, browser nahi. Sirf cookie saaf karna kafi na hota.

</Ur>
</Tr>
</Happened>

<Step title="Restarts, forged cookies and logging out everywhere">

<Tr>
<En>
`devices.js` starts a **fresh Node process** each time, with a new app instance, and keeps each device's cookie in `cookies.json`. Jane logs in on a laptop and a phone. We check that both sessions survive the "restart", forge the laptop's cookie, and then end every session from the laptop.
</En>
<Ur>
`devices.js` har dafa **naya Node process** shuru karta hai, nayi app instance ke saath, aur har device ki cookie `cookies.json` me rakhta hai. Jane laptop aur phone par login karti hai. Hum check karte hain ke dono sessions "restart" ke baad bhi hain, laptop ki cookie jaali banate hain, aur phir laptop se har session khatam karte hain.
</Ur>
</Tr>

```bash
cat > devices.js <<'EOF'
// Each run is a fresh Node process: a new app instance, like after a restart or on another server
import { readFileSync, writeFileSync, existsSync } from 'node:fs';
import { createApp, redis } from './app.js';
import { browser } from './client.js';
const server = createApp().listen(3000);
const saved = existsSync('cookies.json') ? JSON.parse(readFileSync('cookies.json', 'utf8')) : {};
const [command, device] = process.argv.slice(2);
const b = browser(3000);
b.cookie = saved[device] ?? null;
const show = (r) => console.log(`${device.padEnd(7)} ${command.padEnd(18)} -> ${r.status} ${r.body}`);

if (command === 'login') show(await b.call('POST', '/login', { email: 'jane@example.com', password: 'correct horse battery' }));
if (command === 'me') show(await b.call('GET', '/me'));
if (command === 'logout-everywhere') show(await b.call('POST', '/logout-everywhere'));
if (command === 'forge') {            // change one character of the session id inside the signed cookie
  const [name, value] = b.cookie.split('=');
  const raw = decodeURIComponent(value);
  b.cookie = `${name}=${encodeURIComponent(raw.slice(0, 2) + (raw[2] === 'a' ? 'b' : 'a') + raw.slice(3))}`;
  show(await b.call('GET', '/me'));
}
if (command === 'login') writeFileSync('cookies.json', JSON.stringify({ ...saved, [device]: b.cookie }));
server.close(); await redis.quit();
EOF
rm -f cookies.json
node devices.js login laptop
node devices.js login phone
echo "sessions for Jane in Redis: $(redis-cli -n 3 scard user_sessions:1)"
echo "--- a new process (= app restarted) still knows both devices, because sessions live in Redis"
node devices.js me laptop
node devices.js me phone
echo "--- a forged cookie fails the signature check"
node devices.js forge laptop
echo "--- log out of all devices (after a password change or a stolen phone)"
node devices.js logout-everywhere laptop
node devices.js me phone
echo "sessions left in Redis: $(redis-cli -n 3 --scan --pattern 'sess:*' | wc -l)"
```

<Happened>
<Tr>
<En>

- Each login added the session id to a Redis set `user_sessions:1`, so the app knows all of Jane's active sessions.
- New processes recognized both devices: sessions live in **Redis**, so restarts, deploys and multiple app servers behind a load balancer all work. The default in-memory store loses every session on restart and doesn't work with more than one server.
- Changing one character of the session id broke the **HMAC signature** made with `secret`, so express-session ignored the cookie: 401. Signing prevents tampering; the id's randomness prevents guessing.
- `logout-everywhere` deleted both sessions and the set, and the phone was logged out instantly. Do this after a password change, when a device is lost, or when an admin disables an account. With stateless tokens this is much harder (next lesson).

</En>
<Ur>

- Har login ne session id ko Redis set `user_sessions:1` me joda, isliye app Jane ki saari active sessions janti hai.
- Naye processes ne dono devices pehchane: sessions **Redis** me hain, isliye restarts, deploys aur load balancer ke peeche kayi app servers sab chalte hain. Default in-memory store restart par har session kho deta hai aur ek se zyada server ke saath nahi chalta.
- Session id ka ek harf badalne se `secret` se bana **HMAC signature** toot gaya, isliye express-session ne cookie nazar andaz ki: 401. Signing chhed-chhaar rokta hai; id ka random hona guess karna rokta hai.
- `logout-everywhere` ne dono sessions aur set mitaye, aur phone foran logout ho gaya. Ye password badalne ke baad, device gum hone par, ya admin ke account band karne par karein. Stateless tokens ke saath ye kaafi mushkil hai (agla lesson).

</Ur>

## Common mistakes

<Compare>
<Bad title="Putting user data in a readable, unsigned cookie">

```text
res.cookie('user', JSON.stringify({ id: 1, role: 'customer' }));
// the user edits it to {"id":1,"role":"admin"} in DevTools
```

</Bad>
<Good title="Random signed id in the cookie, data on the server">

```text
app.use(session({ store: new RedisStore({ client }), secret: process.env.SESSION_SECRET,
  cookie: { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 30 * 60 * 1000 } }));
req.session.userId = user.id;    // role is looked up on the server
```

</Good>
</Compare>

<Compare>
<Bad title="Logging in without a new session id">

```text
app.post('/login', (req, res) => {
  if (ok) req.session.userId = user.id;   // same id as before login: session fixation
  res.sendStatus(204);
});
```

</Bad>
<Good title="Regenerate on login, destroy on logout">

```text
req.session.regenerate((err) => { req.session.userId = user.id; res.sendStatus(204); });
// logout
req.session.destroy(() => res.clearCookie('sid').sendStatus(204));
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Missing `Secure` in production**: the cookie can leak over plain HTTP. Behind a proxy, set `app.set('trust proxy', 1)` so Express knows the request was HTTPS.
- **The default MemoryStore in production**: leaks memory, loses sessions on restart, breaks with several servers.
- **A weak or committed secret**: anyone with it can sign cookies. Load it from the environment; support rotation with an array of secrets.
- **Storing passwords or using fast hashes** (MD5, SHA-256): use argon2, scrypt or bcrypt with a salt.
- **No idle and absolute timeout**: sessions that never end. Use `maxAge` with rolling, plus a maximum lifetime.
- **`SameSite=None` without need**: it sends cookies on cross-site requests, so you need CSRF protection.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Production me `Secure` ghayab**: cookie saade HTTP par leak ho sakti hai. Proxy ke peeche `app.set('trust proxy', 1)` lagayen taa ke Express ko pata ho ke request HTTPS thi.
- **Production me default MemoryStore**: memory leak, restart par sessions gum, kayi servers ke saath toot jata hai.
- **Kamzor ya commit kiya hua secret**: jis ke paas ho woh cookies sign kar sakta hai. Environment se load karein; secrets ki array se rotation sambhalein.
- **Passwords rakhna ya tez hashes** (MD5, SHA-256): salt ke saath argon2, scrypt ya bcrypt lein.
- **Idle aur absolute timeout nahi**: kabhi khatam na hone wale sessions. Rolling ke saath `maxAge`, aur zyada se zyada umar lagayen.
- **Bila zaroorat `SameSite=None`**: ye cross-site requests par cookies bhejta hai, isliye CSRF hifazat chahiye.

</Ur>

<DeepDive title="More about sessions and cookies">

**Cookie scope.** `Domain` and `Path` decide where a cookie is sent; without `Domain`, it stays on the exact host. Prefixes `__Host-` and `__Secure-` make browsers enforce safe settings.

**SameSite details.** `Strict` never sends the cookie from other sites (even following a link in an email, the first request arrives logged out); `Lax` sends it on top-level navigations with GET; `None` always sends it and requires `Secure`. Modern browsers treat cookies without `SameSite` as `Lax`.

**CSRF.** With `SameSite=Lax`, most cross-site POSTs don't carry the cookie, but older browsers, `SameSite=None` and same-site subdomains still need CSRF tokens or checking the `Origin` header for state-changing requests.

**Session stores.** Redis is fast with built-in expiry; Postgres works well for smaller apps and lets you join sessions to users; signed or encrypted cookie sessions (`cookie-session`, iron-session) keep everything in the cookie, which brings JWT-like trade-offs.

**Frameworks.** NestJS uses the same `express-session`; Next.js apps often use Auth.js or iron-session; Supabase and Clerk manage sessions for you.

</DeepDive>

<DeepDive title="Real world: the session that never ended">

A SaaS company let users stay logged in for a year with a cookie whose session id was stored in a database. When an employee left a customer company, the customer's admin removed them from the account, but the ex-employee's browser still had a valid session: the app checked the session, not whether the user still belonged to the account. Months later, the former employee exported the customer list.

The fixes:

1. Every request loads the user and membership fresh from the database (cached for seconds), so removed users lose access immediately.
2. Removing a user or changing a password deletes all of their sessions.
3. A 30-day absolute session lifetime with a 7-day idle timeout, and re-authentication for exports.
4. A "devices and sessions" page so users can see and end their own sessions.

</DeepDive>

<DeepDive title="Security lens">

- **Session hijacking**: steal the cookie, become the user. HttpOnly, Secure, short lifetimes and HTTPS everywhere reduce the risk.
- **XSS** can't read HttpOnly cookies but can still make requests as the user from the page; fix XSS itself.
- **Brute force and credential stuffing**: rate limit login, use MFA, and check passwords against breached-password lists.
- **Login errors**: say "wrong email or password", not which one, to avoid revealing registered emails.
- **Rotate the secret** with `secret: [newSecret, oldSecret]`; new cookies are signed with the first, old ones still verify.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do server-side sessions work?">
After login, the server creates a session record in a store with the user's data, keyed by a random id, and sends the id in a cookie. The browser sends the cookie with each request; the server verifies it, loads the session and knows the user. Logout deletes the record.
</QA>

<QA q="What do HttpOnly, Secure and SameSite do?">
HttpOnly hides the cookie from JavaScript, limiting theft through XSS. Secure sends it only over HTTPS. SameSite controls whether it is sent with cross-site requests, which defends against CSRF: Strict never, Lax on top-level GET navigations, None always.
</QA>

<QA q="What is session fixation and how do you prevent it?">
An attacker makes the victim use a session id the attacker knows, then waits for the victim to log in with it. Prevent it by issuing a new session id at login and on privilege changes, and by not accepting session ids from URLs.
</QA>

<QA q="Sessions or JWTs?">
Sessions are simple, revocable instantly and keep data on the server, but need a shared store. JWTs are self-contained and verifiable without a store, good for APIs and distributed services, but hard to revoke before expiry. Many apps use sessions for browsers and tokens for APIs.
</QA>

<QA q="How should passwords be stored?">
Never in plain text or with fast hashes. Use a slow, salted, memory-hard algorithm such as argon2id, scrypt or bcrypt, compare in constant time, and rehash when parameters are upgraded.
</QA>

</DeepDive>
