<BigIdea>
<Tr>
<En>
**OAuth 2.0** is a standard for **delegated access**: a user lets an app (the **client**) do specific things on their behalf at another service, without giving the app their password. The user logs in at the **authorization server** (Google, GitHub, Auth0, your company's identity provider), agrees to share certain **scopes**, and the client receives an **access token** to call the **resource server** (the API). **OpenID Connect (OIDC)** is a thin layer on top of OAuth that adds **login**: an **ID token** (a JWT that says who the user is, for this client) and a standard **userinfo** endpoint. For apps with users, the one flow to use is the **authorization code flow with PKCE**: the browser carries only a short-lived, single-use **code**; the client's backend swaps it for tokens over a direct connection; **PKCE** proves the swap comes from the same client that started the login; **state** stops forged callbacks; and **nonce** ties the ID token to this login. Machines with no user use the **client credentials** flow. Old flows (implicit, password grant) are deprecated.
</En>
<Ur>
**OAuth 2.0** **delegated access** ka standard hai: user ek app (**client**) ko doosri service par apni taraf se khaas kaam karne deta hai, app ko apna password diye baghair. User **authorization server** (Google, GitHub, Auth0, aap ki company ka identity provider) par login karta hai, kuch **scopes** share karne par razi hota hai, aur client ko **resource server** (API) bulane ke liye **access token** milta hai. **OpenID Connect (OIDC)** OAuth ke upar patli tah hai jo **login** jorti hai: **ID token** (JWT jo batata hai user kaun hai, is client ke liye) aur standard **userinfo** endpoint. Users wali apps ke liye istemal karne wala ek hi flow hai **PKCE ke saath authorization code flow**: browser sirf kam umar, ek dafa wala **code** le jata hai; client ka backend use seedhe connection par tokens se badalta hai; **PKCE** sabit karta hai ke badalne wala wahi client hai jis ne login shuru kiya; **state** jaali callbacks rokta hai; aur **nonce** ID token ko is login se jorta hai. Jin machines ke saath user nahi hota woh **client credentials** flow istemal karti hain. Purane flows (implicit, password grant) deprecated hain.
</Ur>

## Picture it

<Tr>
<En>

Think of a **valet key** for a car.

- You want a valet to park your car, but you don't hand over your full key ring with your house keys. You give a **valet key** that only starts the engine and can't open the trunk: limited scope.
- In OAuth, you don't give the app your Google password. Google (the authorization server) gives the app a limited key (access token) after **you** approve it at Google's own desk.
- The handover happens in two steps: Google gives you a **claim ticket** (the code) to carry to the app, and the app exchanges the ticket for the key directly at Google's counter, showing its ID (client secret) and the matching half of a torn ticket it kept (PKCE). A ticket stolen on the way is useless.
- OIDC adds a **name badge** (ID token) with the key, so the app also knows who you are, not just that it may drive your car.

</En>
<Ur>

Gaari ki **valet key** socheyn.

- Aap chahte hain valet gaari park kare, magar ghar ki chabiyon wala poora guchha nahi dete. Aap **valet key** dete hain jo sirf engine chalati hai aur trunk nahi kholti: mehdood scope.
- OAuth me aap app ko apna Google password nahi dete. Google (authorization server) app ko mehdood chabi (access token) deta hai jab **aap** Google ke apne counter par manzoori dete hain.
- Hawala do qadmon me hota hai: Google aap ko app tak le jane ke liye **claim ticket** (code) deta hai, aur app ticket ko seedha Google ke counter par chabi se badalti hai, apni ID (client secret) aur phate ticket ka woh aadha hissa dikha kar jo us ne rakha (PKCE). Raste me chura ticket bekaar hai.
- OIDC chabi ke saath **naam ka badge** (ID token) jorta hai, taa ke app ye bhi jane ke aap kaun hain, sirf ye nahi ke woh aap ki gaari chala sakti hai.

</Ur>
</Tr>

Is ka login page Jane ka hashed password check karta aur us ki ijazat darj karta hai. `flow.js` client app hai, `openid-client` ke saath: ye provider dhoondti hai, "browser" ko authorization URL par bhejti hai, redirects follow karti hai, code ko tokens se badalti hai, userinfo bulati hai, aur phir do hamle aazmati hai.
```bash
npm init -y > /dev/null && npm pkg set type=module
npm install oidc-provider@9.15.1 openid-client@6.9.1 express@5.1.0 --silent
cat > provider.js <<'EOF'
// A tiny OpenID Connect provider, playing the role of "Google" or "Auth0"
import Provider from 'oidc-provider';
import express from 'express';
import { scryptSync, randomBytes, timingSafeEqual, generateKeyPairSync } from 'node:crypto';

const hash = (pw, salt = randomBytes(16).toString('hex')) => `${salt}:${scryptSync(pw, salt, 32).toString('hex')}`;
const check = (pw, stored) => { const [salt, h] = stored.split(':'); return timingSafeEqual(Buffer.from(h, 'hex'), scryptSync(pw, salt, 32)); };
const accounts = { 'jane@example.com': { sub: 'u_8f2a', name: 'Jane Doe', passwordHash: hash('correct horse battery') } };

export const ISSUER = 'http://localhost:4000';
const provider = new Provider(ISSUER, {
  clients: [{ client_id: 'shop-app', client_secret: 'shop-app-secret-from-env', redirect_uris: ['http://localhost:3000/callback'], application_type: 'native' }],
  findAccount: (ctx, sub) => {
    const [email, a] = Object.entries(accounts).find(([, acc]) => acc.sub === sub);
    return { accountId: sub, claims: () => ({ sub, email, email_verified: true, name: a.name }) };
  },
  claims: { openid: ['sub'], email: ['email', 'email_verified'], profile: ['name'] },
  features: { devInteractions: { enabled: false } },
  pkce: { required: () => true },
  jwks: { keys: [generateKeyPairSync('rsa', { modulusLength: 2048 }).privateKey.export({ format: 'jwk' })] },   // load from a secret store in real life
  ttl: { AccessToken: 600, IdToken: 600, AuthorizationCode: 60, Interaction: 600, Grant: 86400, Session: 86400 },
});
provider.on('server_error', (ctx, err) => console.error('provider error:', err));

const app = express();
// The provider's own login page: the user types the password HERE, never into the client app
app.get('/interaction/:uid', async (req, res) => {
  const { params } = await provider.interactionDetails(req, res);
  res.type('text').send(`Sign in to continue to ${params.client_id}. POST login + password to /interaction/${req.params.uid}/login`);
});
app.post('/interaction/:uid/login', express.urlencoded({ extended: false }), async (req, res) => {
  const { params } = await provider.interactionDetails(req, res);
  const acc = accounts[req.body.login];
  if (!acc || !check(req.body.password, acc.passwordHash)) return res.status(401).type('text').send('wrong email or password');
  const grant = new provider.Grant({ accountId: acc.sub, clientId: params.client_id });
  grant.addOIDCScope(params.scope);                     // the user agrees to share these scopes
  await provider.interactionFinished(req, res, { login: { accountId: acc.sub }, consent: { grantId: await grant.save() } }, { mergeWithLastSubmission: false });
});
app.use(provider.callback());
export const startProvider = () => app.listen(4000);
EOF
cat > flow.js <<'EOF'
import * as client from 'openid-client';
import { startProvider, ISSUER } from './provider.js';
const idp = startProvider();
const redact = (u) => u.replace(/(code|state|nonce|code_challenge|iss)=[^&]+/g, '$1=…');

// A tiny browser with a cookie jar, following redirects by hand so we can see each hop
const jar = new Map();
async function browse(url, init = {}) {
  const res = await fetch(url, { ...init, redirect: 'manual', headers: { ...init.headers, cookie: [...jar].map(([k, v]) => `${k}=${v}`).join('; ') } });
  for (const c of res.headers.getSetCookie()) { const [kv] = c.split(';'); const [k, v] = kv.split('='); jar.set(k, v); }
  return res;
}

// 1. The client app discovers the provider's endpoints
const config = await client.discovery(new URL(ISSUER), 'shop-app', 'shop-app-secret-from-env', undefined, { execute: [client.allowInsecureRequests] });
const meta = config.serverMetadata();
console.log('1. discovered endpoints:', ['authorization_endpoint', 'token_endpoint', 'userinfo_endpoint', 'jwks_uri'].map((k) => meta[k].replace(ISSUER, '')).join('  '));

// 2. "Sign in with Example ID": build the authorization URL with PKCE, state and nonce
const verifier = client.randomPKCECodeVerifier();
const state = client.randomState(), nonce = client.randomNonce();
const authUrl = client.buildAuthorizationUrl(config, {
  redirect_uri: 'http://localhost:3000/callback', scope: 'openid email profile',
  code_challenge: await client.calculatePKCECodeChallenge(verifier), code_challenge_method: 'S256', state, nonce,
});
console.log('2. browser goes to:', redact(authUrl.href.replace(ISSUER, '')));

// 3. At the provider: login page, password, redirect back to the app with a code
let res = await browse(authUrl);
const loginPage = new URL(res.headers.get('location'), ISSUER);
console.log('3. provider shows:', await (await browse(loginPage)).text().then((t) => t.split('.')[0]));
res = await browse(`${loginPage}/login`, { method: 'POST', headers: { 'content-type': 'application/x-www-form-urlencoded' }, body: 'login=jane@example.com&password=guess' });
console.log('   wrong password ->', res.status, await res.text());
res = await browse(`${loginPage}/login`, { method: 'POST', headers: { 'content-type': 'application/x-www-form-urlencoded' }, body: 'login=jane@example.com&password=correct horse battery' });
while (!res.headers.get('location').startsWith('http://localhost:3000')) res = await browse(new URL(res.headers.get('location'), ISSUER));
const callback = new URL(res.headers.get('location'));
console.log('   redirect back to:', redact(callback.href));

// 4. The app's backend swaps the code for tokens (with its secret and the PKCE verifier)
const tokens = await client.authorizationCodeGrant(config, callback, { pkceCodeVerifier: verifier, expectedState: state, expectedNonce: nonce });
const claims = tokens.claims();
console.log('4. token types:', Object.keys(tokens).filter((k) => k.endsWith('token')).join(', '), '| access token expires in', tokens.expires_in, 's');
console.log('   ID token (verified by openid-client): iss=%s sub=%s aud=%s nonce matches=%s', claims.iss, claims.sub, claims.aud, claims.nonce === nonce);
const info = await client.fetchUserInfo(config, tokens.access_token, claims.sub);
console.log('   userinfo with the access token:', JSON.stringify(info));

// 5. Attacks that must fail
const again = await client.authorizationCodeGrant(config, callback, { pkceCodeVerifier: verifier, expectedState: state, expectedNonce: nonce }).catch((e) => e);
console.log('5. reuse the same code:', again.error ?? again.code);
const forgedState = await client.authorizationCodeGrant(config, callback, { pkceCodeVerifier: verifier, expectedState: 'attacker-state', expectedNonce: nonce }).catch((e) => e);
console.log('   callback with a state we did not send:', forgedState.code);
idp.close();
EOF
node flow.js
```

<Happened>
<Tr>
<En>

- The warning is the provider reminding us that its built-in storage is in memory. A real deployment plugs in a database or Redis adapter, and loads signing keys from a secret store (we generated one at startup).
- **Discovery** read `/.well-known/openid-configuration`, so the client learned every endpoint from the issuer URL alone.
- The authorization URL carried `client_id`, an exact `redirect_uri`, the **scopes**, a **PKCE** `code_challenge` (a SHA-256 hash of a secret `code_verifier` the client keeps), plus random **state** and **nonce**.
- The password went to the **provider's** login page, never to `shop-app`. A wrong password failed there. After login, the provider redirected the browser back with a short-lived **code**, the **state** and its **iss**.
- The client's backend exchanged the code for an **access token** and an **ID token**. `openid-client` verified the ID token's signature (with the provider's JWKS), `iss`, `aud` (= `shop-app`), expiry and that the **nonce** matched. The access token then fetched the user's email and name from **userinfo**. In a real app, the next step is to create your own session (previous lesson) keyed by `iss` + `sub`, not by email.
- Reusing the same code returned **`invalid_grant`**: codes are single-use, so a code leaked through logs or history is worthless. A callback whose `state` didn't match what we stored was rejected, which stops an attacker from logging the victim into the attacker's account (login CSRF).

</En>
<Ur>

- Warning provider ki yaad dehani hai ke us ki built-in storage memory me hai. Asal deployment database ya Redis adapter lagati hai, aur signing keys secret store se load karti hai (hum ne startup par ek banayi).
- **Discovery** ne `/.well-known/openid-configuration` parha, isliye client ne sirf issuer URL se har endpoint seekh liya.
- Authorization URL me `client_id`, bilkul theek `redirect_uri`, **scopes**, **PKCE** `code_challenge` (client ke rakhe raaz `code_verifier` ka SHA-256 hash), aur random **state** aur **nonce** the.
- Password **provider ke** login page par gaya, `shop-app` par kabhi nahi. Ghalat password wahin nakam hua. Login ke baad provider ne browser ko kam umar **code**, **state** aur apne **iss** ke saath wapas bheja.
- Client ke backend ne code ko **access token** aur **ID token** se badla. `openid-client` ne ID token ka signature (provider ke JWKS se), `iss`, `aud` (= `shop-app`), expiry aur **nonce** ka milna check kiya. Phir access token ne **userinfo** se user ka email aur naam laya. Asal app me agla qadam apna session banana hai (pichla lesson), `iss` + `sub` ki bunyad par, email par nahi.
- Wahi code dobara istemal karne par **`invalid_grant`** mila: codes ek dafa ke hain, isliye logs ya history se leak hua code bekaar hai. Jis callback ka `state` hamare rakhe hue se mel nahi khaya woh rad hua, jo hamla awar ko victim ko hamla awar ke account me login karane se rokta hai (login CSRF).

</Ur>

<Step title="Machine to machine: client credentials and scopes">

<Tr>
<En>
A `report-service` needs to read orders at night. There's no user, so it authenticates **as itself** with the **client credentials** grant and is only allowed the `orders:read` scope. The provider issues **JWT access tokens** for the orders API (audience `https://api.example.com`). The API verifies them with the provider's JWKS (`jose`) and checks the scope for each route.
</En>
<Ur>
Ek `report-service` ko raat ko orders parhne hain. Koi user nahi, isliye ye **client credentials** grant se **khud ki pehchan** karata hai aur ise sirf `orders:read` scope ki ijazat hai. Provider orders API (audience `https://api.example.com`) ke liye **JWT access tokens** jaari karta hai. API inhe provider ke JWKS (`jose`) se tasdeeq karti hai aur har route ke liye scope check karti hai.
</Ur>
</Tr>

```bash
npm install jose@6.2.18 --silent
cat > m2m.js <<'EOF'
import Provider from 'oidc-provider';
import express from 'express';
import { generateKeyPairSync } from 'node:crypto';
import { createRemoteJWKSet, jwtVerify } from 'jose';
const API = 'https://api.example.com';

// ---- authorization server: issues JWT access tokens for the orders API ----
const provider = new Provider('http://localhost:4000', {
  clients: [{ client_id: 'report-service', client_secret: 'report-secret-from-env', grant_types: ['client_credentials'], response_types: [], redirect_uris: [], scope: 'orders:read' }],
  scopes: ['orders:read', 'orders:write'],
  ttl: { ClientCredentials: 300 },
  jwks: { keys: [generateKeyPairSync('rsa', { modulusLength: 2048 }).privateKey.export({ format: 'jwk' })] },
  features: {
    devInteractions: { enabled: false },
    clientCredentials: { enabled: true },
    resourceIndicators: {
      enabled: true,
      defaultResource: () => API,
      useGrantedResource: () => true,
      getResourceServerInfo: () => ({ audience: API, scope: 'orders:read orders:write', accessTokenFormat: 'jwt', accessTokenTTL: 300 }),
    },
  },
});
```

## Common mistakes

<Compare>
<Bad title="Using OAuth access tokens as proof of login">

```text
// client receives an access token from somewhere and calls the provider's API
const me = await fetch('https://idp/userinfo', { headers: { authorization: `Bearer ${tokenFromRequest}` } });
login(me.email);   // a token issued to ANOTHER app also works here
```

</Bad>
<Good title="Use OIDC: verify the ID token issued to you">

```text
const tokens = await client.authorizationCodeGrant(config, callbackUrl,
  { pkceCodeVerifier, expectedState, expectedNonce });   // checks iss, aud = your client_id, nonce, exp
const { iss, sub } = tokens.claims();
const user = await findOrCreateUser({ iss, sub });     // key accounts by iss + sub
```

</Good>
</Compare>

<Compare>
<Bad title="Loose redirect URIs and no state">

```text
redirect_uris: ['https://app.example.com/*']        // wildcard: open redirect, code theft
GET /auth?client_id=app&response_type=code&redirect_uri=…   // no state, no PKCE
```

</Bad>
<Good title="Exact redirect URIs, state, nonce and PKCE">

```text
redirect_uris: ['https://app.example.com/auth/callback']
GET /auth?client_id=app&response_type=code&redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fcallback
         &scope=openid%20email&state=…&nonce=…&code_challenge=…&code_challenge_method=S256
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Linking accounts by email alone**: an unverified email at one provider can take over an account. Use `iss` + `sub`, and only trust `email_verified`.
- **Putting the client secret in a SPA or mobile app**: anyone can extract it. Those are public clients; rely on PKCE, or use a backend.
- **Asking for broad scopes "just in case"**: users decline, and a breach exposes more. Request the minimum, and more later if needed.
- **Implicit flow or password grant**: tokens in URLs, apps handling passwords. Both are removed in OAuth 2.1.
- **Storing provider tokens unencrypted**: refresh tokens to someone's Google Drive are as sensitive as passwords.
- **Skipping logout at the provider**: ending your session doesn't end the user's session at the provider; use RP-initiated logout if needed.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sirf email se accounts jorna**: ek provider par ghair tasdeeq shuda email account chheen sakti hai. `iss` + `sub` lein, aur sirf `email_verified` par bharosa karein.
- **SPA ya mobile app me client secret rakhna**: koi bhi nikal sakta hai. Ye public clients hain; PKCE par bharosa karein, ya backend lein.
- **"Shayad zaroorat pare" wale bare scopes maangna**: users inkaar karte hain, aur breach zyada khol deti hai. Kam se kam maangein, zaroorat ho to baad me aur.
- **Implicit flow ya password grant**: URLs me tokens, apps ka passwords sambhalna. Dono OAuth 2.1 me hata diye gaye.
- **Provider tokens bina encryption ke rakhna**: kisi ke Google Drive ke refresh tokens passwords jitne hassas hain.
- **Provider par logout chhorna**: apna session khatam karna provider par user ka session khatam nahi karta; zaroorat ho to RP-initiated logout lein.

</Ur>
</Tr>

<DeepDive title="More about OAuth and OIDC">

**OAuth 2.1.** Consolidates best practice: PKCE for every client, exact redirect URI matching, no implicit or password grants, refresh token rotation or sender-constraining for public clients.

**Refresh tokens.** Requested with the `offline_access` scope (OIDC) or provider-specific options such as Google's `access_type=offline`. Store them encrypted and handle revocation.

**Backend-for-frontend (BFF).** The SPA talks only to its own backend with a session cookie; the backend runs the OAuth flow and holds tokens. This avoids tokens in the browser entirely.

**Token introspection and revocation.** RFC 7662 lets an API ask the authorization server if an opaque token is active; RFC 7009 lets clients revoke tokens.

**Identity providers.** Auth0, Okta, Microsoft Entra ID, Google, AWS Cognito, Keycloak, Clerk and Supabase Auth all speak OIDC; libraries like Auth.js, Passport and openid-client handle the client side.

**SAML.** The older XML-based single sign-on standard, still common in enterprises; OIDC is its modern replacement for new apps.

</DeepDive>

<DeepDive title="Real world: account takeover through Sign in with…">

An app supported "Sign in with Google" and email/password, and linked accounts automatically by email. It also added a smaller provider that let users set any email address without verifying it. An attacker created an account at that provider with a victim's email, clicked "Sign in with …" on the app, and was logged straight into the victim's existing account.

The fixes:

1. Accounts are linked by `iss` + `sub`, never by email alone.
2. Automatic linking only happens when `email_verified` is true from a provider known to verify emails; otherwise, the user must log in to the existing account first and link from settings.
3. Linking a new login method sends a notification email.
4. Providers that can't vouch for email ownership were removed.

</DeepDive>

<DeepDive title="Security lens">

- **Redirect URI validation** is the backbone of OAuth security: exact matches, HTTPS, no open redirects on the callback page.
- **state, nonce and PKCE** each stop a different attack: forged callbacks, replayed ID tokens and stolen codes.
- **Client secrets** belong in server-side environment variables or a secret manager, rotated regularly; never in front-end bundles.
- **Consent phishing**: malicious apps ask users for broad scopes on a real provider. Admins can restrict which apps users may approve.
- **Mix-up attacks** with several providers: check the `iss` parameter on the callback (RFC 9207), as openid-client does.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between OAuth 2.0 and OpenID Connect?">
OAuth 2.0 is an authorization framework that lets a client obtain access tokens to call APIs on a user's behalf. OpenID Connect builds on it for authentication, adding the ID token, the openid scope, standard claims, discovery and the userinfo endpoint.
</QA>

<QA q="Walk through the authorization code flow with PKCE.">
The client creates a code verifier and its hash, redirects the user to the authorization endpoint with client id, redirect URI, scopes, state and the challenge. The user authenticates and consents; the server redirects back with a code and state. The client checks state and sends the code, verifier and its credentials to the token endpoint, receiving access, ID and optionally refresh tokens.
</QA>

<QA q="Why was the implicit flow deprecated?">
It returned tokens directly in the URL fragment, exposing them to browser history, logs and malicious scripts, and couldn't use refresh tokens safely. Authorization code with PKCE now works for browser apps and is safer.
</QA>

<QA q="What are state and nonce for?">
State is a random value checked on the callback to prevent cross-site request forgery and forged authorization responses. Nonce is embedded in the ID token and checked to make sure the token was issued for this particular login request, preventing replay.
</QA>

<QA q="When do you use client credentials?">
For machine-to-machine calls where no user is involved, such as a backend job calling an API. The client authenticates with its own credentials and gets a token limited to the scopes it is allowed.
</QA>

</DeepDive>
