<BigIdea>
<Tr>
<En>
With REST, the **server** decides what each endpoint returns: a product page might need `/products/1`, then `/products/1/reviews`, then `/users/…` for each reviewer, and still get fields it doesn't use. **GraphQL** turns that around: there's **one endpoint** (`POST /graphql`), and the **client sends a query** describing exactly the shape it wants, `{ product(id: "p1") { name reviews { rating author { name } } } }`, and gets back JSON in exactly that shape. The server publishes a typed **schema** (types, fields, `Query` for reads, `Mutation` for writes), and each field that needs work has a **resolver** function. Unknown fields are rejected before anything runs, and the schema doubles as documentation. The price: caching is harder than with plain GET URLs, errors come back with **HTTP 200** and an `errors` array, and nested fields can trigger the **N+1 problem** (one query for the list plus one per item), which you fix with **DataLoader** batching. Public GraphQL APIs also need limits on query depth and cost, because clients write the queries.
</En>
<Ur>
REST me **server** tay karta hai ke har endpoint kya lautaye: product page ko `/products/1`, phir `/products/1/reviews`, phir har reviewer ke liye `/users/…` chahiye ho sakte hain, aur phir bhi aise fields milte hain jo istemal nahi hote. **GraphQL** ise palat deta hai: **ek endpoint** hai (`POST /graphql`), aur **client query bhejta hai** jo bilkul wo shakal bayan karti hai jo use chahiye, `{ product(id: "p1") { name reviews { rating author { name } } } }`, aur JSON bilkul usi shakal me wapas paata hai. Server typed **schema** shaya karta hai (types, fields, parhne ke liye `Query`, likhne ke liye `Mutation`), aur kaam maangne wale har field ka ek **resolver** function hota hai. Anjaan fields kuch chalne se pehle rad ho jate hain, aur schema documentation ka kaam bhi deta hai. Qeemat: saade GET URLs ke muqable caching mushkil, errors **HTTP 200** aur `errors` array ke saath aate hain, aur nested fields **N+1 masla** paida kar sakte hain (list ki ek query plus har item ki ek), jise aap **DataLoader** batching se theek karte hain. Public GraphQL APIs ko query ki gehrai aur kharche ki hadd bhi chahiye, kyunke queries clients likhte hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of **a set menu vs a buffet where you fill in an order form**.

- A **REST** restaurant serves **set plates**: plate #1 always has rice, chicken and salad. If you only want the chicken, you still get the rest; if you also want soup, you order a second plate (another request).
- A **GraphQL** restaurant hands you an **order form listing every dish** (the schema). You tick exactly what you want, "chicken, no rice, plus the soup, plus the chef's name", and get one tray with exactly that (one response in the shape of your query).
- In the kitchen, each dish has its own **cook** (resolver). If the waiter sends the soup cook to the storeroom **once per guest** for 100 guests, that's 100 trips (N+1). A smart waiter **collects all soup orders first** and makes **one trip** (DataLoader).

</En>
<Ur>

**Set menu bamuqabla order form bhar kar buffet** ka sochein.

- **REST** restaurant **set plates** deta hai: plate #1 me hamesha chawal, chicken aur salad. Agar sirf chicken chahiye to bhi baqi milta hai; soup bhi chahiye to doosri plate mangwayen (ek aur request).
- **GraphQL** restaurant aap ko **har dish wala order form** deta hai (schema). Aap bilkul wahi tick karte hain jo chahiye, "chicken, chawal nahi, saath soup, aur chef ka naam", aur bilkul wahi ek tray me milta hai (aap ki query ki shakal me ek response).
- Kitchen me har dish ka apna **bawarchi** (resolver) hai. Agar waiter 100 mehmanon ke liye soup wale bawarchi ko **har mehman par ek dafa** store room bheje to 100 chakkar (N+1). Samajhdar waiter **pehle saare soup orders jama** karta hai aur **ek chakkar** lagwata hai (DataLoader).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Schema, resolvers, queries, mutations and errors">

<Tr>
<En>
`db.js` is a pretend database that **counts every query**. `server.js` defines the schema in SDL (products, reviews, users, an `addReview` mutation) and resolvers: `Query` fields load data, `Product.reviews` and `Review.author` load related data, and the mutation validates the rating with a `GraphQLError`. graphql-yoga serves it at `/graphql`. The `gql` helper posts a query (and optional variables) with curl.
</En>
<Ur>
`db.js` ek naqli database hai jo **har query ginta** hai. `server.js` SDL me schema (products, reviews, users, `addReview` mutation) aur resolvers bayan karta hai: `Query` fields data load karte hain, `Product.reviews` aur `Review.author` mutaliqa data load karte hain, aur mutation `GraphQLError` se rating check karti hai. graphql-yoga ise `/graphql` par serve karta hai. `gql` helper curl se query (aur ikhtiyari variables) post karta hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install graphql@17.1.0 graphql-yoga@6.1.0 dataloader@2.2.3 --silent
cat > db.js <<'EOF'
// A pretend database that counts every query, so we can see what GraphQL costs
export const stats = { queries: 0 };
const q = (rows) => { stats.queries++; return Promise.resolve(rows); };
const users    = [{ id: "u1", name: "Jane Doe" }, { id: "u2", name: "John Smith" }, { id: "u3", name: "Ana Lee" }];
const products = [
  { id: "p1", name: "Desk Lamp",   priceCents: 2999, category: "lighting" },
  { id: "p2", name: "Floor Lamp",  priceCents: 8900, category: "lighting" },
  { id: "p3", name: "Monitor Arm", priceCents: 5400, category: "desk" },
];
export const reviews = [
  { id: "r1", productId: "p1", userId: "u1", rating: 5, comment: "Bright and cheap" },
  { id: "r2", productId: "p1", userId: "u2", rating: 4, comment: "Good" },
  { id: "r3", productId: "p2", userId: "u3", rating: 3, comment: "Wobbly" },
  { id: "r4", productId: "p3", userId: "u1", rating: 5, comment: "Solid" },
];
export const db = {
  products:          (category) => q(products.filter((p) => !category || p.category === category)),
  productById:       (id)  => q(products.find((p) => p.id === id) ?? null),
  reviewsByProduct:  (id)  => q(reviews.filter((r) => r.productId === id)),
  reviewsByProducts: (ids) => q(reviews.filter((r) => ids.includes(r.productId))),   // one query for many
  userById:          (id)  => q(users.find((u) => u.id === id)),
  usersByIds:        (ids) => q(users.filter((u) => ids.includes(u.id))),            // one query for many
};
EOF
cat > server.js <<'EOF'
import { createServer } from "node:http";
import { createSchema, createYoga } from "graphql-yoga";
import { GraphQLError } from "graphql";
import { db, reviews, stats } from "./db.js";

const typeDefs = /* GraphQL */ `
  type Query {
    products(category: String): [Product!]!
    product(id: ID!): Product
  }
  type Product { id: ID!  name: String!  priceCents: Int!  category: String!  reviews: [Review!]! }
  type Review  { id: ID!  rating: Int!  comment: String!  author: User! }
  type User    { id: ID!  name: String! }
  type Mutation {
    addReview(productId: ID!, rating: Int!, comment: String!): Review!
  }
`;

// One resolver per field that needs work; the rest come straight from the object
const resolvers = {
  Query: {
    products: (_, { category }) => db.products(category),
    product: (_, { id }) => db.productById(id),
  },
  Product: { reviews: (product) => db.reviewsByProduct(product.id) },
  Review:  { author: (review) => db.userById(review.userId) },
  Mutation: {
    addReview: (_, { productId, rating, comment }) => {
      if (rating < 1 || rating > 5)
        throw new GraphQLError("rating must be between 1 and 5", { extensions: { code: "BAD_USER_INPUT", field: "rating" } });
      const review = { id: `r${reviews.length + 1}`, productId, userId: "u2", rating, comment };
      reviews.push(review);
      return review;
    },
  },
};

const yoga = createYoga({ schema: createSchema({ typeDefs, resolvers }), graphiql: false, logging: false });
createServer((req, res) => {
  if (req.url === "/stats") return res.end(JSON.stringify(stats));
  yoga(req, res);
}).listen(4000);
EOF
node server.js & PID=$!
until curl -s localhost:4000/stats > /dev/null; do sleep 0.1; done
gql() {   # $1 = query, $2 = variables (optional JSON)
  body=$(node -e 'console.log(JSON.stringify({ query: process.argv[1], variables: JSON.parse(process.argv[2] || "{}") }))' "$1" "$2")
  curl -s localhost:4000/graphql -H 'content-type: application/json' -d "$body" -w '  [HTTP %{http_code}]\n'
}
echo "1) only the fields asked for:"
gql '{ products(category: "lighting") { name priceCents } }'
echo "2) nested data + variables, one request:"
gql 'query Product($id: ID!) { product(id: $id) { name reviews { rating author { name } } } }' '{"id":"p1"}'
echo "3) unknown id -> null, not an error:"
gql '{ product(id: "p99") { name } }'
echo "4) a field that does not exist (rejected before running):"
gql '{ products { name color } }'
echo "5) mutation, valid then invalid:"
gql 'mutation { addReview(productId: "p3", rating: 4, comment: "Sturdy") { id rating author { name } } }'
gql 'mutation { addReview(productId: "p3", rating: 9, comment: "!!!") { id } }'
kill $PID
```

```text output

{"data":{"products":[{"name":"Desk Lamp","priceCents":2999},{"name":"Floor Lamp","priceCents":8900}]}}  [HTTP 200]
2) nested data + variables, one request:
{"data":{"product":{"name":"Desk Lamp","reviews":[{"rating":5,"author":{"name":"Jane Doe"}},{"rating":4,"author":{"name":"John Smith"}}]}}}  [HTTP 200]
3) unknown id -> null, not an error:
{"data":{"product":null}}  [HTTP 200]
4) a field that does not exist (rejected before running):
{"errors":[{"message":"Cannot query field \"color\" on type \"Product\".","locations":[{"line":1,"column":19}],"extensions":{"code":"GRAPHQL_VALIDATION_FAILED"}}]}  [HTTP 200]
5) mutation, valid then invalid:
{"data":{"addReview":{"id":"r5","rating":4,"author":{"name":"John Smith"}}}}  [HTTP 200]
{"errors":[{"message":"rating must be between 1 and 5","locations":[{"line":1,"column":12}],"path":["addReview"],"extensions":{"code":"BAD_USER_INPUT","field":"rating"}}],"data":null}  [HTTP 200]
```

<Happened>
<Tr>
<En>

- Query 1 asked for `name` and `priceCents` of lighting products and got **exactly those fields**, nothing else (no `id`, no `category`).
- Query 2 fetched a product, its reviews and each reviewer's name in **one request**: with REST this would be three or more calls. Values were passed as **variables** (`$id`), never pasted into the query text, just like SQL parameters.
- An unknown product returned `"product": null`, because the field is nullable (`Product` without `!`). Not-found is usually data, not an error, in GraphQL.
- Asking for a field that doesn't exist (`color`) was **rejected before any resolver ran**: the schema is checked first. The error has a message, a location in the query and a code.
- The valid mutation returned the new review in the shape asked for. The invalid one returned `"data": null` plus an `errors` entry with `path` and `extensions` (`BAD_USER_INPUT`, `field`), which clients use to show the error next to the right input.
- All responses were **HTTP 200**. In GraphQL, the HTTP status mostly says "the request reached the server"; clients must check the `errors` array. Newer servers return 400 for invalid queries when the client accepts `application/graphql-response+json`.

</En>
<Ur>

- Query 1 ne lighting products ke `name` aur `priceCents` maange aur **bilkul wahi fields** mile, aur kuch nahi (na `id`, na `category`).
- Query 2 ne product, us ke reviews aur har reviewer ka naam **ek request** me liya: REST me ye teen ya zyada calls hotin. Values **variables** (`$id`) ke tor par gayin, query text me kabhi chipkayi nahi gayin, bilkul SQL parameters ki tarah.
- Anjaan product ne `"product": null` lautaya, kyunke field nullable hai (`!` ke baghair `Product`). GraphQL me "nahi mila" aam taur par data hai, error nahi.
- Na mojood field (`color`) maangna **kisi resolver ke chalne se pehle rad** hua: schema pehle check hota hai. Error me message, query me jagah aur code hai.
- Sahi mutation ne naya review maangi gayi shakal me lautaya. Ghalat wali ne `"data": null` plus `path` aur `extensions` (`BAD_USER_INPUT`, `field`) wali `errors` entry lautayi, jise clients error ko sahi input ke paas dikhane ke liye istemal karte hain.
- Saare responses **HTTP 200** the. GraphQL me HTTP status zyada tar ye batata hai ke "request server tak pahunchi"; clients ko `errors` array check karna lazmi hai. Naye servers ghalat queries par 400 lautate hain jab client `application/graphql-response+json` qubool kare.

</Ur>

<Step title="The N+1 problem and DataLoader">

<Tr>
<En>
One query asks for all products, their reviews, and each review's author. We count how many database queries it causes with the current resolvers. Then `loaders.js` creates two **DataLoaders** per request: they collect every `.load(key)` call made in the same tick and fetch them with **one** query (`reviewsByProducts`, `usersByIds`). We switch the two resolvers to the loaders and count again.
</En>
<Ur>
Ek query saare products, un ke reviews, aur har review ka author maangti hai. Hum ginte hain ke mojooda resolvers ke saath ye kitni database queries karwati hai. Phir `loaders.js` har request ke liye do **DataLoaders** banata hai: ye ek hi tick me hone wali har `.load(key)` call jama karte aur **ek** query se laate hain (`reviewsByProducts`, `usersByIds`). Hum dono resolvers ko loaders par badal kar dobara ginte hain.
</Ur>
</Tr>

```bash
QUERY='{ products { name reviews { rating author { name } } } }'
count() {   # run the query once and report how many database queries it caused
  node server.js & PID=$!
  until curl -s localhost:4000/stats > /dev/null; do sleep 0.1; done
  body=$(node -e 'console.log(JSON.stringify({ query: process.argv[1] }))' "$QUERY")
  curl -s localhost:4000/graphql -H 'content-type: application/json' -d "$body" > result.json
  echo "$1: $(node -pe 'JSON.parse(require("fs").readFileSync("result.json")).data.products.length') products," \
       "$(node -pe 'JSON.parse(require("fs").readFileSync("result.json")).data.products.flatMap((p) => p.reviews).length') reviews" \
       "-> database queries: $(curl -s localhost:4000/stats | node -pe 'JSON.parse(require("fs").readFileSync(0)).queries')"
  cp result.json "$2.json"
  kill $PID; wait $PID 2>/dev/null
}
count "naive resolvers" naive
# DataLoader: collect every .load(key) made in the same tick, then fetch them all in one query
cat > loaders.js <<'EOF'
import DataLoader from "dataloader";
import { db } from "./db.js";

// New loaders for every request, so cached data never leaks between users
export function createLoaders() {
  return {
    reviewsByProduct: new DataLoader(async (productIds) => {
      const rows = await db.reviewsByProducts(productIds);
      return productIds.map((id) => rows.filter((r) => r.productId === id));   // same order as the keys
    }),
    userById: new DataLoader(async (ids) => {
      const rows = await db.usersByIds(ids);
      return ids.map((id) => rows.find((u) => u.id === id));
    }),
  };
}
EOF
sed -i 's/import { db, reviews, stats } from ".\/db.js";/import { db, reviews, stats } from ".\/db.js";\nimport { createLoaders } from ".\/loaders.js";/' server.js
sed -i 's/  Product: { reviews: (product) => db.reviewsByProduct(product.id) },/  Product: { reviews: (product, _args, ctx) => ctx.reviewsByProduct.load(product.id) },/' server.js
sed -i 's/  Review:  { author: (review) => db.userById(review.userId) },/  Review:  { author: (review, _args, ctx) => ctx.userById.load(review.userId) },/' server.js
sed -i 's/graphiql: false, logging: false });/graphiql: false, logging: false, context: () => createLoaders() });/' server.js
count "with DataLoader " batched
echo "identical responses: $(cmp -s naive.json batched.json && echo yes)"
```

```text output
naive resolvers: 3 products, 4 reviews -> database queries: 8
with DataLoader : 3 products, 4 reviews -> database queries: 3
identical responses: yes
```

<Happened>
<Tr>
<En>

- The naive resolvers made **8** database queries for 3 products and 4 reviews: 1 for the product list, **1 per product** for reviews (3), and **1 per review** for the author (4). With 100 products and 1,000 reviews that's 1,101 queries for one request. This is the **N+1 problem**, and GraphQL makes it easy to fall into because each resolver only sees its own parent.
- With DataLoader the same query made **3**: one for products, one batched query for all reviews, one batched query for all authors, no matter how many items there are. The responses were **identical**.
- The batch function must return results **in the same order as the keys**, with one entry per key (an empty array or `undefined` when nothing matches); that's why it maps over `productIds`.
- Loaders are created **per request** in `context`. DataLoader also caches within a request (two reviews by the same user load that user once), and a per-request cache can't leak one user's data to another.

</En>
<Ur>

- Saade resolvers ne 3 products aur 4 reviews ke liye **8** database queries kin: product list ki 1, reviews ke liye **har product ki 1** (3), aur author ke liye **har review ki 1** (4). 100 products aur 1,000 reviews ke saath ek request ki 1,101 queries. Ye **N+1 masla** hai, aur GraphQL me is me girna aasan hai kyunke har resolver sirf apna parent dekhta hai.
- DataLoader ke saath wahi query **3** queries ki: ek products ki, saare reviews ki ek batched query, saare authors ki ek batched query, chahe items kitne hi hon. Responses **bilkul ek jaise** the.
- Batch function ko nataij **keys ki tarteeb me**, har key ki ek entry ke saath lautane hote hain (kuch na mile to khaali array ya `undefined`); isi liye ye `productIds` par map karta hai.
- Loaders `context` me **har request ke liye** bante hain. DataLoader ek request ke andar cache bhi karta hai (ek hi user ke do reviews us user ko ek dafa load karte hain), aur har request ka cache ek user ka data doosre tak nahi pahuncha sakta.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Building queries with string concatenation">

```text
const query = `{ product(id: "${userInput}") { name } }`;    // injection, no caching of the query text
```

</Bad>
<Good title="Fixed query text, values as variables">

```text
const query = 'query ($id: ID!) { product(id: $id) { name } }';
fetch('/graphql', { method: 'POST', body: JSON.stringify({ query, variables: { id: userInput } }) });
```

</Good>
</Compare>

<Compare>
<Bad title="Checking only the HTTP status on the client">

```text
const res = await fetch('/graphql', …);
if (res.ok) render((await res.json()).data.product);   // data may be null; the error is in "errors"
```

</Bad>
<Good title="Check the errors array">

```text
const { data, errors } = await (await fetch('/graphql', …)).json();
if (errors?.length) return showErrors(errors);          // use extensions.code and path
render(data.product);
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Resolvers that query the database per item**: use DataLoader (or join in the parent resolver) for every list-to-related lookup.
- **A global DataLoader** shared between requests: cached data leaks across users and never refreshes.
- **No depth or cost limits** on a public API: a client can send a deeply nested query that multiplies work exponentially.
- **Exposing your database tables 1:1** as the schema: design the schema for clients, not for storage.
- **Leaking internal errors**: production servers should mask unexpected errors (graphql-yoga does by default) and only return intentional `GraphQLError`s.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Har item par database poochne wale resolvers**: har list-se-mutaliqa lookup ke liye DataLoader (ya parent resolver me join) lein.
- **Requests ke darmiyan mushtarka global DataLoader**: cached data users ke paar risata hai aur kabhi taaza nahi hota.
- **Public API par gehrai ya kharche ki hadd nahi**: client bohot gehri nested query bhej sakta hai jo kaam ko kai guna barha de.
- **Database tables ko 1:1 schema bana dena**: schema clients ke liye design karein, storage ke liye nahi.
- **Andaruni errors leak karna**: production servers ko ghair-mutawaqqa errors chhupane chahiye (graphql-yoga default me karta hai) aur sirf jaan boojh kar banaye `GraphQLError` lautane chahiye.

</Ur>
</Tr>

<Challenge title="Extend the schema">

<Tr>
<En>
Add an `averageRating: Float` field to `Product` (null when there are no reviews) and a query `topProducts(limit: Int = 3): [Product!]!` sorted by average rating. Write the SDL and resolvers, and say how to avoid N+1 for `averageRating` when listing products.
</En>
<Ur>
`Product` me `averageRating: Float` field jorein (reviews na hon to null) aur average rating se sorted `topProducts(limit: Int = 3): [Product!]!` query. SDL aur resolvers likhein, aur batayen ke products ki list me `averageRating` ke liye N+1 se kaise bachein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
type Product { …  averageRating: Float }
type Query   { …  topProducts(limit: Int = 3): [Product!]! }

Product: {
  averageRating: async (product, _args, ctx) => {
    const reviews = await ctx.reviewsByProduct.load(product.id);   // batched, and cached for reviews too
    return reviews.length ? reviews.reduce((s, r) => s + r.rating, 0) / reviews.length : null;
  },
},
Query: {
  topProducts: (_, { limit }) => db.topProductsByRating(Math.min(limit, 50)),   // sorted in SQL, capped
},
```

Reusing the `reviewsByProduct` loader means `averageRating` and `reviews` in the same query share one batched load. For large data, compute averages in SQL (`GROUP BY product_id`) inside a dedicated loader instead of loading every review.

</En>

<Challenge title="Protect a public GraphQL API">

<Tr>
<En>
Your public GraphQL API has `User.friends: [User!]!`. Someone sends `{ user(id: 1) { friends { friends { friends { friends { friends { name } } } } } } }`. Explain the risk and list four protections.
</En>
<Ur>
Aap ki public GraphQL API me `User.friends: [User!]!` hai. Koi `{ user(id: 1) { friends { friends { friends { friends { friends { name } } } } } } }` bhejta hai. Khatra samjhayen aur chaar hifazati tadabeer likhein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>
If each user has 200 friends, five levels means up to 200⁵ (320 billion) user lookups from one small request: a denial-of-service attack. Protections:

1. **Depth limit** (for example max 6) and **cost/complexity analysis** that rejects queries above a budget, counting list sizes.
2. **Pagination on list fields** (`friends(first: 20)`) with a maximum page size, so no field returns unbounded lists.
3. **Persisted queries** (allow only query hashes your apps registered) for first-party clients, which blocks arbitrary queries entirely.
4. **Timeouts and rate limits** per client, ideally based on query cost rather than request count, plus disabling introspection in production if the schema isn't meant to be public.

</En>
<Ur>
Agar har user ke 200 dost hon to paanch satahen ek chhoti request se 200⁵ (320 arab) user lookups tak ban sakti hain: denial-of-service hamla. Hifazati tadabeer:

1. **Gehrai ki hadd** (maslan zyada se zyada 6) aur **kharche/pechidgi ka tajziya** jo list sizes gin kar budget se zyada queries rad kare.
2. **List fields par pagination** (`friends(first: 20)`) zyada se zyada page size ke saath, taa ke koi field be-hadd list na lautaye.
3. Apne clients ke liye **persisted queries** (sirf wo query hashes jo aap ki apps ne register kiye), jo marzi ki queries ko bilkul rok deti hain.
4. Har client ke **timeouts aur rate limits**, behtar hai request ginti ke bajaye query ke kharche par, plus agar schema public nahi hona to production me introspection band.

<DeepDive title="More about GraphQL">

**Fragments.** Reusable field sets (`fragment ProductCard on Product { name priceCents }`) let each UI component declare its own data needs.

**Subscriptions.** Real-time updates over WebSockets or server-sent events (`subscription { orderUpdated(id: "o1") { status } }`).

**Schema-first vs code-first.** SDL strings (as here) or code that builds the schema (Pothos, NestJS `@nestjs/graphql` with decorators, TypeGraphQL).

**Federation.** Several services each own part of one combined graph (Apollo Federation, GraphQL Mesh).

**Caching.** Normalized client caches (Apollo Client, urql) key objects by `__typename` and `id`; server-side, use persisted queries over GET so CDNs can cache.

**Evolution.** Instead of versions, mark fields `@deprecated(reason: "use priceMoney")` and track field usage before removing.

</DeepDive>

<DeepDive title="Real world: the dashboard that took the database down">

A startup launched a GraphQL API for its new dashboard. Development data had 20 projects with a few tasks each; every page loaded instantly.

The first enterprise customer had 3,000 projects, each with hundreds of tasks and assignees. Their dashboard query (`projects { tasks { assignee { name avatar } } }`) produced over 400,000 database queries per page load. The database connection pool was exhausted within minutes of the customer's team logging in, and every other customer's app slowed to a crawl.

The fixes:

1. DataLoaders for every relation, created per request, which brought the query down to five SQL queries.
2. Pagination on `projects` and `tasks` (`first`, `after`), with a maximum of 100.
3. A query cost limit based on requested list sizes, rejecting expensive queries with a clear error.
4. Logging of query cost and resolver timing per operation name, with alerts on slow operations.

</DeepDive>

<DeepDive title="Security lens">

- **Authorization in resolvers or the data layer**, not just at the endpoint: every field that returns private data must check the caller's rights.
- **Depth, cost and timeout limits**, and capped list sizes, against denial of service.
- **Introspection**: fine for public schemas; disable it in production for private ones, though this isn't real security on its own.
- **Error masking**: never return stack traces or database errors; graphql-yoga masks unexpected errors by default.
- **Batching attacks**: some servers accept arrays of operations or aliases (`a1: login(…) a2: login(…)`); rate limit by operation and field, not just by HTTP request.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What problems does GraphQL solve compared with REST?">
Over-fetching and under-fetching: clients request exactly the fields they need in one round trip, across related resources, from a typed schema that serves as a contract and documentation. It also lets APIs evolve by adding fields without versions.
</QA>

<QA q="What is a resolver?">
A function that produces the value of a field. It receives the parent object, the field's arguments, a per-request context and info about the query, and may return a value or a promise. Fields without a resolver use the parent object's property of the same name.
</QA>

<QA q="What is the N+1 problem in GraphQL and how do you fix it?">
Resolving a list and then a related field for each item issues one query for the list plus one per item. Fix it with DataLoader, which batches all loads requested in the same tick into one query and caches per request, or by joining in the parent resolver.
</QA>

<QA q="How are errors returned in GraphQL?">
In an errors array alongside data, each with a message, locations, a path and optional extensions such as an error code; partial data can be returned with errors. The HTTP status is often 200, so clients must inspect the errors array.
</QA>

<QA q="How do you secure a public GraphQL API?">
Enforce authorization per field or in the data layer, limit query depth and complexity, paginate lists with maximum sizes, set timeouts and cost-based rate limits, mask internal errors, consider persisted queries, and control introspection.
</QA>

</DeepDive>
