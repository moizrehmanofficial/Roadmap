<BigIdea>
<Tr>
<En>
Once an API is published, **other people's code depends on its exact shape**: mobile apps that users don't update for months, partner integrations, scripts you've never seen. Renaming a field, changing a type or removing an endpoint is a **breaking change** that crashes them. **Adding** things (a new optional field, a new endpoint) is usually **safe**. **Versioning** lets you make breaking changes without breaking anyone: old clients keep calling **v1**, new clients use **v2**, and v1 is retired on an announced date. The version can live in the **URL** (`/v1/customers`, the most common and easiest to see), or in a **header** (`API-Version: 2`). Good practice: keep **one** internal model and serve old versions by **translating** to the old shape, mark old versions with **`Deprecation`** and **`Sunset`** headers, give clients time to move, and run **contract checks** in CI so nobody breaks a version by accident. Most of the time, the best versioning strategy is to **evolve without breaking**, and create a new version only when you truly must.
</En>
<Ur>
Jab API shaya ho jaye to **doosron ka code us ki bilkul shakal par munhasir** hota hai: mobile apps jinhen users mahinon update nahi karte, partner integrations, scripts jo aap ne kabhi dekhe bhi nahi. Field ka naam badalna, type badalna ya endpoint hatana **breaking change** hai jo unhen crash karta hai. Cheezen **jorna** (naya ikhtiyari field, naya endpoint) aam taur par **mehfooz** hai. **Versioning** aap ko kisi ko tore baghair breaking changes karne deti hai: purane clients **v1** bulate rehte hain, naye clients **v2** istemal karte hain, aur v1 elaan shuda tareekh par retire hota hai. Version **URL** me ho sakta hai (`/v1/customers`, sab se aam aur dekhne me aasan), ya **header** me (`API-Version: 2`). Achha tareeqa: andar **ek** model rakhein aur purane versions ko purani shakal me **tarjuma** kar ke dein, purane versions par **`Deprecation`** aur **`Sunset`** headers lagayen, clients ko muntaqil hone ka waqt dein, aur CI me **contract checks** chalayen taa ke koi ghalti se version na tore. Zyada tar waqt behtareen versioning strategy **tore baghair barhna** hai, aur naya version sirf tab banayen jab waqai zaroori ho.
</Ur>
</Tr>
</BigIdea>

| --- | --- |
| Add a new endpoint | no |
| Add an optional request field | no |
| Add a response field | no (clients must ignore unknown fields) |

<Tr>
<En>

- You can't update every client at once: mobile users, partners and third-party scripts update on their own schedule.
- Breaking a public API costs trust and support time; breaking a partner integration can cost contracts.
- A clear version policy lets your team keep improving the API without fear.

</En>

<When>
<Tr>
<En>

## Picture it

<Tr>
<En>

Think of **electrical sockets in a building being upgraded**.

- Adding a **new socket** on the wall doesn't bother any existing device (an additive change).
- Changing the **shape of the old sockets** would make every existing plug useless (a breaking change).
- So the building installs the **new sockets** (v2) and puts **adapters** on a few old ones (v1 translating to the new wiring): the wiring behind the wall is the same.
- A **notice on each old socket** says "these adapters will be removed on 30 June 2027; please switch your plugs" (`Deprecation` and `Sunset`).
- An **inspector** checks after every renovation that every plug that worked before still fits (contract checks).

</En>
<Ur>

**Imarat me bijli ke sockets ki upgrade** ka sochein.

- Deewar par **naya socket** jorna kisi mojooda aale ko pareshan nahi karta (jorne wali tabdeeli).
- **Purane sockets ki shakal** badalna har mojooda plug ko bekar kar deta (breaking change).
- Isliye imarat **naye sockets** (v2) lagati hai aur chand purane sockets par **adapters** (v1 jo nayi wiring me tarjuma kare): deewar ke peeche wiring wahi hai.
- **Har purane socket par notice** likha hai "ye adapters 30 June 2027 ko hata diye jayenge; apne plugs badal lein" (`Deprecation` aur `Sunset`).
- Har marammat ke baad **inspector** check karta hai ke pehle chalne wala har plug ab bhi fit hota hai (contract checks).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Two versions from one model, plus deprecation headers">

<Tr>
<En>
The internal model splits names into `firstName`/`lastName` and stores money as `{ amountCents, currency }`. **v2** returns that shape. **v1**, the old contract, had a single `name` and `balance` as a decimal number in dollars: its router **translates** the same data and adds `Deprecation`, `Sunset` and `Link` headers. A third route shows header-based versioning on one URL with `API-Version`.
</En>
<Ur>
Andaruni model naam ko `firstName`/`lastName` me baant'ta hai aur paise `{ amountCents, currency }` ki shakal me rakhta hai. **v2** yahi shakal lautata hai. **v1**, purane muahide, me ek `name` aur dollars me decimal number ke tor par `balance` tha: us ka router wahi data **tarjuma** karta hai aur `Deprecation`, `Sunset` aur `Link` headers jorta hai. Teesra route ek URL par `API-Version` ke saath header par mabni versioning dikhata hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 --silent
cat > service.js <<'EOF'
// The internal model: shaped the way the app works TODAY (v2-style)
const customers = [{ id: 1, firstName: "Jane", lastName: "Doe", email: "jane@example.com",
                     balance: { amountCents: 125000, currency: "USD" }, tier: "gold" }];
export const findCustomer = (id) => customers.find((c) => c.id === id);
EOF
cat > app.js <<'EOF'
import express from "express";
import { findCustomer } from "./service.js";
const app = express();
const notFound = (res) => res.status(404).json({ error: { code: "not_found", message: "Customer not found" } });

// ---- v2: the current contract ----
const v2 = express.Router();
v2.get("/customers/:id", (req, res) => {
  const c = findCustomer(Number(req.params.id));
  if (!c) return notFound(res);
  res.json({ id: c.id, firstName: c.firstName, lastName: c.lastName, email: c.email, balance: c.balance, tier: c.tier });
});

// ---- v1: the old contract, kept alive by translating the same data ----
const v1 = express.Router();
v1.use((req, res, next) => {
  res.set("Deprecation", "@1767225600");                                   // deprecated since 2026-01-01
  res.set("Sunset", "Wed, 30 Jun 2027 23:59:59 GMT");                       // removed after this date
  res.set("Link", '</v2/customers>; rel="successor-version"');
  next();
});
v1.get("/customers/:id", (req, res) => {
  const c = findCustomer(Number(req.params.id));
  if (!c) return notFound(res);
  res.json({ id: c.id, name: `${c.firstName} ${c.lastName}`, email: c.email, balance: c.balance.amountCents / 100 });
});

app.use("/v1", v1);
app.use("/v2", v2);

// ---- alternative: the version in a header, same URL ----
app.get("/customers/:id", (req, res, next) => {
  const version = req.get("API-Version") ?? "2";                            // default: latest stable
  const router = { 1: v1, 2: v2 }[version];
  if (!router) return res.status(400).json({ error: { code: "unsupported_version", message: "API-Version must be 1 or 2" } });
  res.set("API-Version", version);
  req.url = `/customers/${req.params.id}`;
  router(req, res, next);
});
app.listen(3000);
EOF
node app.js & PID=$!
until curl -s localhost:3000/v2/customers/1 > /dev/null; do sleep 0.1; done
r() {
  out=$(curl -s -i localhost:3000$1 "${@:2}" | tr -d '\r')
  echo "GET $1${2:+ ($3)} -> $(echo "$out" | head -1 | cut -d' ' -f2)"
  echo "$out" | grep -iE '^(deprecation|sunset|link|api-version):' | sed 's/^/    /'
  echo "    $(echo "$out" | sed '1,/^$/d')"
}
r /v1/customers/1
r /v2/customers/1
r /customers/1 -H 'API-Version: 1'
r /customers/1
r /customers/1 -H 'API-Version: 3'
kill $PID
```

<Happened>
<Tr>
<En>

- `/v1` and `/v2` returned **the same customer in two shapes**. There's one data source and one business logic; v1 is a thin translation layer. Copying the whole codebase per version means fixing every bug twice and the versions slowly diverging.
- v1 responses carried **`Deprecation`** (since when, as a Unix timestamp), **`Sunset`** (the date v1 stops working) and **`Link`** with `rel="successor-version"` (where to go). Client SDKs and API gateways can detect these and warn developers; your logs can find who still calls v1.
- The header route served v1 with `API-Version: 1`, defaulted to **v2** when no header was sent, and echoed the version it used. Choosing the default matters: defaulting to "latest" means a client that never sends the header can break on the next major version, so many APIs default to the version a client first registered with.
- An unknown version got a clear **400** listing the valid values.

</En>
<Ur>

- `/v1` aur `/v2` ne **ek hi customer do shaklon me** lautaya. Data ka ek source aur ek business logic hai; v1 patli tarjume ki parat hai. Har version ke liye poora codebase copy karne ka matlab hai har bug do dafa theek karna aur versions ka aahista aahista alag ho jana.
- v1 responses ke saath **`Deprecation`** (kab se, Unix timestamp me), **`Sunset`** (jis tareekh v1 band hoga) aur `rel="successor-version"` ke saath **`Link`** (kahan jana hai) the. Client SDKs aur API gateways inhen pehchan kar developers ko khabardar kar sakte hain; aap ke logs dhoondh sakte hain ke ab bhi kaun v1 bulata hai.
- Header route ne `API-Version: 1` par v1 diya, header na hone par **v2** default liya, aur istemal kiya gaya version wapas bataya. Default chunna ahem hai: "latest" default ka matlab hai jo client kabhi header nahi bhejta wo agle major version par toot sakta hai, isliye bohot si APIs us version ko default rakhti hain jis par client ne pehli dafa register kiya.
- Anjaan version ko sahi values ki list ke saath wazeh **400** mila.

</Ur>
</Tr>
</Happened>

<Step title="Catching breaking changes automatically">

<Tr>
<En>
`contract.js` turns a response into its **shape**: every field path and its JSON type. `check.js` saves the shape of v1 and v2 the first time (what clients depend on today), then compares later responses against it: removed fields and changed types are **breaking**, new fields are fine. We run it today, after adding a `phone` field, and after a refactor renames `amountCents`.
</En>
<Ur>
`contract.js` response ko us ki **shakal** me badalta hai: har field ka path aur us ki JSON type. `check.js` pehli dafa v1 aur v2 ki shakal mehfooz karta hai (aaj clients jis par munhasir hain), phir baad ke responses ko us se milata hai: hataye gaye fields aur badli types **breaking** hain, naye fields theek hain. Hum ise aaj chalate hain, `phone` field jorne ke baad, aur us refactor ke baad jo `amountCents` ka naam badalta hai.
</Ur>
</Tr>

```bash
cat > contract.js <<'EOF'
// Describe a response by its shape: every field path and its JSON type
const typeOf = (v) => (v === null ? "null" : Array.isArray(v) ? "array" : typeof v);
function shape(value, path = "", out = {}) {
  out[path || "(root)"] = typeOf(value);
  if (typeOf(value) === "object") for (const [k, v] of Object.entries(value)) shape(v, path ? `${path}.${k}` : k, out);
  return out;
}

// Compare what clients rely on (the saved contract) with what the API returns now
export function compare(contract, response) {
  const now = shape(response);
  const problems = [];
  for (const [path, type] of Object.entries(contract)) {
    if (!(path in now)) problems.push(`removed ${path}`);
    else if (now[path] !== type) problems.push(`${path} changed ${type} -> ${now[path]}`);
  }
  const added = Object.keys(now).filter((p) => !(p in contract));
  return { breaking: problems, added };
}
export { shape };
EOF
cat > check.js <<'EOF'
import { readFileSync, writeFileSync, existsSync } from "node:fs";
import { compare, shape } from "./contract.js";

for (const v of ["v1", "v2"]) {
  const body = await (await fetch(`http://localhost:3000/${v}/customers/1`)).json();
  const file = `${v}-contract.json`;
  if (!existsSync(file)) { writeFileSync(file, JSON.stringify(shape(body))); console.log(`${v}: contract saved (${Object.keys(shape(body)).length} fields)`); continue; }
  const { breaking, added } = compare(JSON.parse(readFileSync(file)), body);
  console.log(`${v}: ${breaking.length ? "BREAKING -> " + breaking.join("; ") : "compatible"}${added.length ? ` (added: ${added.join(", ")})` : ""}`);
}
EOF
run() { node app.js & PID=$!; until curl -s localhost:3000/v2/customers/1 > /dev/null; do sleep 0.1; done; node check.js; kill $PID; wait $PID 2>/dev/null; }
echo "--- 1. today: record what clients depend on"; run
echo "--- 2. additive change: v2 also returns phone"
sed -i 's/tier: "gold" }];/tier: "gold", phone: "+1 555 0100" }];/' service.js
sed -i 's/balance: c.balance, tier: c.tier });/balance: c.balance, tier: c.tier, phone: c.phone });/' app.js
run
echo "--- 3. a refactor renames amountCents to amount (a decimal string)"
sed -i 's/balance: { amountCents: 125000, currency: "USD" }/balance: { amount: "1250.00", currency: "USD" }/' service.js
run
```

```text output

v1: contract saved (5 fields)
v2: contract saved (9 fields)
--- 2. additive change: v2 also returns phone
v1: compatible
v2: compatible (added: phone)
--- 3. a refactor renames amountCents to amount (a decimal string)
v1: BREAKING -> balance changed number -> null
v2: BREAKING -> removed balance.amountCents (added: balance.amount, phone)
```

<Happened>
<Tr>
<En>

- Adding `phone` to v2 was **compatible**: clients that ignore unknown fields (tolerant readers) are unaffected, and v1 didn't change at all.
- The innocent-looking refactor in the **shared service** broke **both** versions: v2 lost `balance.amountCents`, and v1's translation now computed `undefined / 100`, which is `NaN`, which JSON turns into **`null`**. No error, no crash on the server: old clients would simply start showing an empty or zero balance.
- That's the value of an automated check: it runs in CI on every pull request and fails the build before the change ships, instead of a partner reporting it weeks later.
- Real projects do this with an OpenAPI description and a diff tool (for example `oasdiff`), or with consumer-driven contract tests (Pact), where each client publishes what it relies on. The idea is the same: compare what you promised with what you now return.

</En>
<Ur>

- v2 me `phone` jorna **compatible** tha: anjaan fields nazar andaz karne wale clients (tolerant readers) par asar nahi, aur v1 bilkul nahi badla.
- **Mushtarka service** me masoom lagne wale refactor ne **dono** versions tor diye: v2 se `balance.amountCents` gaya, aur v1 ka tarjuma ab `undefined / 100` hisaab karta tha, jo `NaN` hai, jise JSON **`null`** bana deta hai. Server par na koi error na crash: purane clients bas khaali ya sifar balance dikhane lagte.
- Khud kaar jaanch ki yahi qeemat hai: ye har pull request par CI me chalti hai aur tabdeeli ship hone se pehle build fail kar deti hai, bajaye is ke ke hafton baad koi partner batata.
- Asli projects ye OpenAPI description aur diff tool (maslan `oasdiff`) se karte hain, ya consumer-driven contract tests (Pact) se, jahan har client shaya karta hai ke wo kis par bharosa karta hai. Khayal wahi hai: jo wada kiya tha us ka muqabla us se karein jo ab lautate hain.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Changing a field in place">

```text
// v1 yesterday: { "price": 19.99 }
// v1 today:     { "price": { "amount": 1999, "currency": "USD" } }   // every client parsing a number breaks
```

</Bad>
<Good title="Add the new shape, deprecate the old one">

```text
// v1 today: { "price": 19.99, "priceMoney": { "amount": 1999, "currency": "USD" } }
// docs: "price is deprecated and will be removed in v2"
// v2: { "price": { "amount": 1999, "currency": "USD" } }
```

</Good>
</Compare>

<Compare>
<Bad title="A copy of the codebase per version">

```text
src/v1/…   (frozen copy, missing two years of bug fixes)
src/v2/…   (current code)
```

</Bad>
<Good title="One core, thin version adapters">

```text
src/customers/service.ts        // one model, one set of rules
src/api/v2/customers.ts         // current representation
src/api/v1/customers.ts         // maps the current model to the old shape
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Versioning every small change** (v1, v2, … v17): clients can't keep up; prefer additive evolution.
- **Removing a version with no warning**: announce dates, add headers, email registered developers, watch traffic before turning it off.
- **Clients that fail on unknown fields** (strict schema validation of responses): they turn every additive change into a breaking one.
- **Forgetting errors and behavior are part of the contract**: changing an error code, a default page size or a sort order breaks clients too.
- **No usage data per version**: log the version on every request so you know who to contact before a sunset.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Har chhoti tabdeeli par naya version** (v1, v2, … v17): clients saath nahi chal sakte; jorne wala irtiqa behtar hai.
- **Bina khabar version hatana**: tareekhen elaan karein, headers lagayen, registered developers ko email karein, band karne se pehle traffic dekhein.
- **Anjaan fields par nakam hone wale clients** (responses ki sakht schema validation): ye har jorne wali tabdeeli ko breaking bana dete hain.
- **Bhoolna ke errors aur rawaiya bhi muahide ka hissa hain**: error code, default page size ya sort order badalna bhi clients torta hai.
- **Har version ke istemal ka data nahi**: har request par version log karein taa ke sunset se pehle pata ho kis se rabta karna hai.

</Ur>
</Tr>

<DeepDive title="More about versioning">

**Date-based versions.** Each client is pinned to the API version from its signup date; the server runs a chain of small "version change" transformations to downgrade new responses for older pins. Clients upgrade one date at a time.

**NestJS.** `app.enableVersioning({ type: VersioningType.URI })` plus `@Version('1')` on controllers or routes; header and media-type versioning are built in too.

**GraphQL.** GraphQL APIs usually avoid versions: fields are added, old ones marked `@deprecated`, and usage per field is tracked before removal.

**Semantic versioning for SDKs.** Client libraries follow semver (major for breaking changes), which is separate from, but related to, the API's version.

</DeepDive>

<DeepDive title="Real world: the cents that became dollars">

A payments company changed `amount` in its webhook payload from cents (`1999`) to a decimal string (`"19.99"`) to "match the dashboard". The change went out on a Tuesday under the same webhook version; the changelog said "improved amount formatting".

Merchants' systems parsed the string, many with code like `parseInt(amount)`, which turned `"19.99"` into `19`. Refund amounts, invoice totals and accounting exports went wrong for two days before anyone connected the problem to the release.

The fixes:

1. The change was reverted; `amount` went back to integer cents.
2. A new field, `amountDecimal`, was added for those who wanted it.
3. Webhook payloads got explicit versions and per-merchant pinning.
4. Every pull request touching API models ran an OpenAPI diff that blocked type changes on existing fields without a version bump.

</DeepDive>

<DeepDive title="Security lens">

- **Old versions keep old vulnerabilities**: security fixes must reach every supported version, which is another reason to keep them thin and few.
- **Retire insecure versions on a firm date**, even if some clients complain; give them a migration path.
- **Don't let version translation bypass checks**: authorization and validation live in the shared core, not in each version layer.
- **Inventory**: forgotten old versions (`/v0`, `/beta`) are a common attack surface; list and monitor every exposed version.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What counts as a breaking change in an API?">
Anything that makes a correctly written existing client fail or misbehave: removing or renaming fields or endpoints, changing types or formats, making optional inputs required, changing status or error codes, and changing default behavior such as sorting. Adding optional fields or new endpoints is generally non-breaking.
</QA>

<QA q="What are the common API versioning strategies?">
Version in the URL path, in a custom header, in the Accept media type, or by date with per-client pinning. URL versioning is the most visible and easiest to route and cache; headers keep URLs stable; date-based versions allow many small changes.
</QA>

<QA q="How do you deprecate an API version?">
Announce it with a date and migration guide, add Deprecation, Sunset and Link headers, measure usage per client, contact remaining users, possibly run brownouts, then return 410 Gone after the sunset date.
</QA>

<QA q="How do you avoid maintaining many copies of code for each version?">
Keep a single domain model and business logic, and implement each version as a thin translation layer that maps requests and responses between the version's contract and the current model.
</QA>

<QA q="How can you prevent accidental breaking changes?">
Treat the API description such as OpenAPI as the contract, diff it in CI, run contract or consumer-driven tests, review changes to API models, and make clients tolerant of unknown fields.
</QA>

</DeepDive>
