<BigIdea>
<Tr>
<En>
Every HTTP response starts with a three-digit **status code** that tells the client, in one number, **what happened**, before it reads a single byte of the body. The first digit is the **family**: **2xx** it worked, **3xx** go somewhere else, **4xx** the **client** must change something (fix the input, log in, slow down), **5xx** the **server** failed and the same request might work later. Picking the right code matters because browsers, `fetch`, proxies, caches, load balancers, monitoring and retry logic all act on it automatically: a `301` gets cached forever, a `503` with `Retry-After` gets retried politely, a `200` with an error message hidden in the body fools everyone. A small set of codes covers almost everything: **200, 201, 204, 301/308, 304, 400, 401, 403, 404, 409, 422, 429, 500, 503**. And clients must check the code: `fetch` happily resolves on a `404` or `500`.
</En>
<Ur>
Har HTTP response teen hindson wale **status code** se shuru hota hai jo client ko ek number me batata hai ke **kya hua**, body ka ek byte parhne se pehle. Pehla hindsa **khandan** hai: **2xx** kaam ho gaya, **3xx** kahin aur jao, **4xx** **client** ko kuch badalna hai (input theek karo, log in karo, aahista chalo), **5xx** **server** nakam hua aur wahi request baad me chal sakti hai. Sahi code chunna ahem hai kyunke browsers, `fetch`, proxies, caches, load balancers, monitoring aur retry logic sab is par khud amal karte hain: `301` hamesha ke liye cache hota hai, `Retry-After` wala `503` tameez se dobara bheja jata hai, aur body me chhupe error message wala `200` sab ko dhoka deta hai. Codes ka chhota sa set taqreeban sab kuch sambhal leta hai: **200, 201, 204, 301/308, 304, 400, 401, 403, 404, 409, 422, 429, 500, 503**. Aur clients ko code check karna lazmi hai: `fetch` `404` ya `500` par bhi khushi se resolve ho jata hai.
</Ur>

<Why>
<Tr>
<En>

- Clients branch on the code: show a form error (422), send to login (401), show "try again later" (503).

## Picture it

<Tr>
<En>

Think of **sending a parcel through a courier office**.

- **2xx**: "Delivered" (200), "Delivered, here's the tracking number for the new account we opened" (201), "We've accepted it and it'll go out tonight" (202).
- **3xx**: "They've moved, we forwarded it to the new address" (301/308), or "You already have the latest catalogue, no need to send it again" (304).
- **4xx**: the problem is **your parcel**: the form is unreadable (400), the address doesn't exist (404), you need to show ID (401), ID shown but you're not allowed to send this (403), you've sent too many today, come back in 30 minutes (429).
- **5xx**: the problem is **the courier**: the sorting machine broke (500), the office is closed for stock-taking, reopen at 2 pm (503).
- Retrying makes sense only for 5xx and 429. Resending an unreadable form a hundred times won't make it readable.

</En>
<Ur>

**Courier office se parcel bhejne** ka sochein.

- **2xx**: "Pahunch gaya" (200), "pahunch gaya, aap ke liye khole gaye naye account ka tracking number ye raha" (201), "le liya hai, aaj raat nikal jayega" (202).
- **3xx**: "Wo ghar badal chuke, naye pate par bhej diya" (301/308), ya "aap ke paas pehle se taaza catalogue hai, dobara bhejne ki zaroorat nahi" (304).
- **4xx**: masla **aap ke parcel** me hai: form parha nahi jata (400), pata mojood nahi (404), shanakht dikhani hogi (401), shanakht dikhayi magar ye bhejne ki ijazat nahi (403), aaj bohot bhej chuke, 30 minute baad aayen (429).
- **5xx**: masla **courier** me hai: sorting machine kharab (500), daftar stock ginti ke liye band, 2 baje khulega (503).
- Dobara koshish sirf 5xx aur 429 par samajh me aati hai. Na parhe jane wala form sau dafa bhejne se parha nahi jayega.

</Ur>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Status code** | Three-digit result of a request | `404` |
| **Reason phrase** | Human text next to the code | `Not Found` |
| **Status family** | First digit: 1xx–5xx | 4xx = client error |

## Learn it step by step

<Walkthrough>

<Step title="A tour of the codes you'll actually use">

<Tr>
<En>
One Express server returns each important code on purpose, with the headers that belong to it. The `r` helper prints the method, path, status, the interesting headers (`Location`, `Retry-After`, `WWW-Authenticate`, `ETag`) and the body. We also follow two redirects with `curl -L` to see what happens to a `POST`.
</En>
<Ur>
Ek Express server har ahem code jaan boojh kar us ke mutaliqa headers ke saath lautata hai. `r` helper method, path, status, dilchasp headers (`Location`, `Retry-After`, `WWW-Authenticate`, `ETag`) aur body chhapta hai. Hum `curl -L` se do redirects bhi follow karte hain taa ke dekhen ke `POST` ka kya hota hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 --silent
cat > app.js <<'EOF'
import express from "express";
const app = express();
app.set("etag", false);                        // we set ETags ourselves where we want them
app.use(express.json());
const fail = (res, status, code, message) => res.status(status).json({ error: { code, message } });

// --- 2xx success ---
app.get("/ok", (req, res) => res.json({ hello: "world" }));                                   // 200
app.post("/items", (req, res) => res.status(201).location("/items/7").json({ id: 7 }));        // 201
app.delete("/items/7", (req, res) => res.status(204).end());                                  // 204
app.post("/exports", (req, res) => res.status(202).location("/exports/91").json({ status: "queued" }));  // 202

// --- 3xx redirects ---
app.all("/old-301", (req, res) => res.redirect(301, "/echo"));
app.all("/old-308", (req, res) => res.redirect(308, "/echo"));
app.all("/echo", (req, res) => res.json({ method: req.method }));
app.get("/logo", (req, res) => {
  if (req.get("If-None-Match") === '"abc"') return res.status(304).end();                     // 304
  res.set("ETag", '"abc"').send("<svg/>");
});

// --- 4xx: the client must change something ---
app.post("/signup", (req, res) => {
  if (typeof req.body?.email !== "string") return fail(res, 400, "bad_request", "email must be a string");
  if (!req.body.email.includes("@")) return fail(res, 422, "invalid_email", "email is not valid");
  if (req.body.email === "taken@example.com") return fail(res, 409, "email_taken", "email already registered");
  res.status(201).json({ ok: true });
});
app.get("/admin", (req, res) => {
  const auth = req.get("Authorization");
  if (!auth) return res.set("WWW-Authenticate", "Bearer").status(401).json({ error: { code: "unauthenticated", message: "log in first" } });
  if (auth !== "Bearer admin-token") return fail(res, 403, "forbidden", "admins only");
  res.json({ secret: 42 });
});
app.get("/search", (req, res) => res.set("Retry-After", "30").status(429).json({ error: { code: "rate_limited", message: "slow down" } }));

// --- 5xx: the server failed ---
app.get("/crash", () => { throw new Error("connect ECONNREFUSED 10.0.4.12:5432"); });                       // a bug
app.get("/maintenance", (req, res) => res.set("Retry-After", "120").status(503).json({ error: { code: "maintenance", message: "back soon" } }));

app.use((req, res) => fail(res, 404, "not_found", `No route ${req.method} ${req.path}`));      // unknown route
app.use((err, req, res, next) => {                                                             // never leak details
  if (err.type === "entity.parse.failed") return fail(res, 400, "bad_json", "body is not valid JSON");
  console.error(err.message);
  fail(res, 500, "internal", "something went wrong");
});
app.listen(3000);
EOF
node app.js 2> server.err & PID=$!
until curl -s localhost:3000/ok > /dev/null; do sleep 0.1; done
r() {   # METHOD PATH [BODY] [extra curl args...]
  m=$1; p=$2; b=$3; shift 3 2>/dev/null
  out=$(curl -s -i -X $m localhost:3000$p -H 'content-type: application/json' ${b:+-d "$b"} "$@" | tr -d '\r')
  st=$(echo "$out" | head -1 | cut -d' ' -f2)
  hdr=$(echo "$out" | grep -iE '^(location|retry-after|www-authenticate|etag):' | tr '\n' ' ')
  body=$(echo "$out" | sed '1,/^$/d')
  printf '%-17s %s %s%s\n' "$m $p" "$st" "$hdr" "$body" | sed 's/ *$//'
}
echo "--- 2xx"
r GET /ok; r POST /items '{}'; r DELETE /items/7; r POST /exports '{}'
echo "--- 3xx"
r GET /old-301; r GET /logo; r GET /logo '' -H 'If-None-Match: "abc"'
echo "POST /old-301, follow redirect -> $(curl -s -L -d x localhost:3000/old-301)"
echo "POST /old-308, follow redirect -> $(curl -s -L -d x localhost:3000/old-308)"
echo "--- 4xx"
r POST /signup '{"email":123}'; r POST /signup '{"email":"nope"}'; r POST /signup '{"email":"taken@example.com"}'
r POST /signup '{"email":'
r GET /admin; r GET /admin '' -H 'Authorization: Bearer user-token'; r GET /admin '' -H 'Authorization: Bearer admin-token'
r GET /search; r GET /nope
echo "--- 5xx"
r GET /crash; r GET /maintenance
echo "server log (not sent to the client): $(cat server.err)"
kill $PID
```

<Happened>
<Tr>
<En>

- **2xx**: `201` came with `Location`, `204` with **no body at all**, and `202` pointed to a status resource (`/exports/91`) the client can poll.
- **3xx**: after a `301`, curl re-sent our `POST` as a **`GET`**: browsers and most clients do this for historical reasons, so the body is lost. `308` kept the **`POST`**. For APIs and forms, use **308** (permanent) or **307** (temporary). `304` had no body: the client's copy with ETag `"abc"` was still current.
- **400 vs 422 vs 409**: a number where a string belongs and broken JSON are **400** (the request itself is malformed); a well-formed but invalid email is **422**; a valid email that's already registered is **409** (conflict with existing data). Express's JSON parser error was mapped to our error format instead of its default HTML page.
- **401 vs 403**: no token → **401** with `WWW-Authenticate: Bearer` (tells the client how to authenticate); a valid token without permission → **403**.
- **429** and **503** carried **`Retry-After`**, so clients know when to try again.
- The crash returned a generic **500**; the real reason (a database IP and port) went only to the **server log**. Error details help attackers; the client needs only a code and maybe a request ID.

</En>
<Ur>

- **2xx**: `201` `Location` ke saath aaya, `204` **bilkul bina body**, aur `202` ne status resource (`/exports/91`) ki taraf ishara kiya jise client baar baar check kar sakta hai.
- **3xx**: `301` ke baad curl ne hamara `POST` **`GET`** bana kar bheja: browsers aur zyada tar clients tareekhi wajah se aisa karte hain, isliye body kho jati hai. `308` ne **`POST`** rakha. APIs aur forms ke liye **308** (mustaqil) ya **307** (aarzi) lein. `304` me body nahi thi: client ki ETag `"abc"` wali copy abhi taaza thi.
- **400 vs 422 vs 409**: string ki jagah number aur toota JSON **400** hain (request khud bigri hai); sahi shakal wali magar ghalat email **422**; sahi email jo pehle se registered hai **409** (mojooda data se takrao). Express ke JSON parser ka error us ke default HTML page ke bajaye hamare error format me badla gaya.
- **401 vs 403**: token nahi → `WWW-Authenticate: Bearer` ke saath **401** (client ko batata hai authenticate kaise kare); sahi token magar ijazat nahi → **403**.
- **429** aur **503** ke saath **`Retry-After`** tha, taa ke clients jaanen ke dobara kab koshish karni hai.
- Crash ne aam **500** lautaya; asal wajah (database ka IP aur port) sirf **server log** me gayi. Error ki tafseel hamla karne walon ki madad karti hai; client ko sirf code aur shayad request ID chahiye.

</Ur>

<Step title="The client side: res.ok and smart retries">

<Tr>
<En>
A flaky server returns `503` twice before succeeding, `429` once, and `404` for a missing order. First, a naive client that just calls `.json()`. Then a careful `request()` helper that checks `res.ok`, retries **only** retryable codes (408, 429, 502, 503, 504), waits as long as `Retry-After` says (capped), and gives up after 3 attempts.
</En>
<Ur>
Ek ghair-mustaqil server kamyab hone se pehle do dafa `503`, ek dafa `429`, aur ghaib order ke liye `404` lautata hai. Pehle ek saada client jo bas `.json()` bulata hai. Phir ek ehtiyaat wala `request()` helper jo `res.ok` check karta hai, **sirf** dobara koshish laiq codes (408, 429, 502, 503, 504) par retry karta hai, utna intezar karta hai jitna `Retry-After` kahe (hadd ke saath), aur 3 koshishon ke baad haar maan leta hai.
</Ur>
</Tr>

```bash
cat > flaky.js <<'EOF'
import express from "express";
const app = express();
const calls = {};
const count = (k) => (calls[k] = (calls[k] ?? 0) + 1);
app.get("/flaky", (req, res) => count("flaky") <= 2
  ? res.set("Retry-After", "1").status(503).json({ error: { code: "unavailable" } })
  : res.json({ data: "report ready" }));
app.get("/limited", (req, res) => count("limited") === 1
  ? res.set("Retry-After", "1").status(429).json({ error: { code: "rate_limited" } })
  : res.json({ data: "results" }));
app.get("/missing", (req, res) => { count("missing"); res.status(404).json({ error: { code: "not_found", message: "Order not found" } }); });
app.get("/calls", (req, res) => res.json(calls));
app.listen(3001);
EOF
cat > client.js <<'EOF'
const base = "http://localhost:3001";

// 1. The classic bug: fetch only throws on network errors, NOT on 404 or 500
const naive = await (await fetch(`${base}/missing`)).json();
console.log("naive client got:", JSON.stringify(naive), "(and carried on as if it worked)");

// 2. A careful client: check res.ok, retry only what can succeed later, honor Retry-After
const RETRYABLE = new Set([408, 429, 502, 503, 504]);
async function request(path, { attempts = 3 } = {}) {
  for (let attempt = 1; ; attempt++) {
    const res = await fetch(base + path);
    if (res.ok) return { status: res.status, attempt, body: await res.json() };
    const body = await res.json().catch(() => null);
    if (!RETRYABLE.has(res.status) || attempt === attempts) {
      const err = new Error(`${res.status} ${body?.error?.code ?? ""}`.trim());
      err.status = res.status;
      throw err;
    }
    const waitS = Math.min(Number(res.headers.get("Retry-After") ?? 2 ** attempt), 10);   // server's hint, capped
    await new Promise((r) => setTimeout(r, waitS * 1000));
  }
}

for (const path of ["/flaky", "/limited", "/missing"]) {
  const t0 = Date.now();
  try {
    const r = await request(path);
    console.log(`${path.padEnd(9)} -> ${r.status} after ${r.attempt} attempt(s), waited >= ${r.attempt - 1}s: ${Date.now() - t0 >= (r.attempt - 1) * 1000}`);
  } catch (e) {
    console.log(`${path.padEnd(9)} -> gave up immediately with ${e.message} (a 404 won't change by retrying)`);
  }
}
console.log("calls the server saw:", JSON.stringify(await (await fetch(`${base}/calls`)).json()));
EOF
node flaky.js & PID=$!
until curl -s localhost:3001/calls > /dev/null; do sleep 0.1; done
node client.js
kill $PID
```

naive client got: {"error":{"code":"not_found","message":"Order not found"}} (and carried on as if it worked)

/limited  -> 200 after 2 attempt(s), waited >= 1s: true

<Tr>
<En>

- The naive client got the **error body** and treated it as data: `fetch` only rejects on network failures, never because of the status code. - `/flaky` succeeded on the **3rd** attempt after waiting the 1 s the server asked for each time; `/limited` succeeded on the 2nd. Respecting `Retry-After` helps an overloaded server recover instead of hammering it.
- `/missing` failed **immediately** with no retries: a 404 won't turn into a 200 by asking again. The server saw it twice only because the naive client asked once too.
- Retry only **idempotent** requests (GET, PUT, DELETE) automatically. Retrying a `POST` that may already have succeeded needs an idempotency key (see REST API Design).
- In real apps add **jitter** (a little randomness) to waits so thousands of clients don't retry at the same instant.

</En>

## Common mistakes

<Compare>
<Bad title="200 for everything, errors hidden in the body">

```text
HTTP/1.1 200 OK
{ "success": false, "error": "User not found" }
// caches store it, monitoring sees no errors, fetch says res.ok === true
```

</Bad>
<Good title="The status code tells the truth">

```text
HTTP/1.1 404 Not Found
{ "error": { "code": "not_found", "message": "User not found" } }
```

</Good>
</Compare>

<Compare>
<Bad title="500 with internal details">

```text
HTTP/1.1 500 Internal Server Error
{ "error": "QueryFailedError: relation \"users\" … at /app/src/db.ts:42", "dbHost": "10.0.4.12" }
```

</Bad>
<Good title="Generic message, details in logs, a request ID to correlate">

```text
HTTP/1.1 500 Internal Server Error
{ "error": { "code": "internal", "message": "Something went wrong", "requestId": "req_8f2a" } }
// server log: requestId=req_8f2a QueryFailedError … (full stack)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **401 for "not allowed"**: a logged-in user without permission gets 403; 401 makes clients think they should log in again.
- **404 for validation errors** ("product 99 in your cart doesn't exist") when the URL itself is fine: that's 422 or 409 about the body.
- **`301` for temporary moves**: browsers cache 301 indefinitely; use 302/307 when it might change back.
- **Returning 500 for bad input**: invalid client data is a 4xx; 5xx alerts should mean the server is at fault.
- **Retrying everything**: retrying 400/401/403/404/422 just multiplies load.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **"Ijazat nahi" ke liye 401**: bina ijazat logged-in user ko 403 milna chahiye; 401 clients ko lagta hai ke dobara log in karna hai.
- **Validation errors ke liye 404** ("aap ke cart ka product 99 mojood nahi") jab URL khud theek ho: ye body ke baare me 422 ya 409 hai.
- **Aarzi muntaqili ke liye `301`**: browsers 301 ko be-had cache karte hain; jab wapas badal sakta ho to 302/307 lein.
- **Ghalat input par 500 lautana**: client ka ghalat data 4xx hai; 5xx alerts ka matlab hona chahiye ke ghalti server ki hai.
- **Har cheez dohrana**: 400/401/403/404/422 dohrana sirf bojh barhata hai.

</Ur>
</Tr>

<Tr>
<En>

<Solution>

<Tr>
<En>

- `GET` timeout: retry with exponential backoff and jitter (for example 1 s, 2 s, 4 s), at most 3 times.

- `502`: retryable with backoff; usually a proxy or deploy hiccup.
- `POST /payments` timeout: retry **only** with the same `Idempotency-Key`; without it, check the payment's status first.

</En>

<DeepDive title="More about status codes">

**1xx.** `100 Continue` lets a client check headers before sending a large body; `103 Early Hints` lets the server suggest preloading assets before the final response. You'll rarely send them yourself.

**More useful 4xx.** `405 Method Not Allowed` (+ `Allow`), `406 Not Acceptable`, `410 Gone` (deliberately removed, won't come back), `412 Precondition Failed` and `428 Precondition Required` (ETags), `413 Content Too Large`, `415 Unsupported Media Type` (wrong `Content-Type`).

**Gateway codes.** `502` means a proxy got an invalid response from your app (often it crashed); `504` means the proxy gave up waiting (your app was too slow). Seeing them usually points at the app, not the proxy.

**Standards.** Status codes are defined in RFC 9110; error bodies can follow RFC 9457 Problem Details.

</DeepDive>

<DeepDive title="Real world: the invisible outage">

A food-delivery API returned `200 OK` for everything and put `"success": false` in the body on errors, a pattern copied from an old internal framework.

One evening, the payment provider started failing. Every checkout returned `200` with `"success": false, "error": "payment provider timeout"`. Dashboards, which counted 5xx responses, stayed green. The load balancer's health checks were happy. The CDN even cached some error responses for a menu endpoint, because they were 200s.

Restaurants noticed first: no orders for 40 minutes on a busy night. Engineers found the problem by reading raw logs.

The fixes:

1. Real status codes: `502` when an upstream provider fails, `503` when overloaded, `4xx` for client errors, with one error format.
2. Alerts on the 5xx rate and on checkout success rate.
3. `Cache-Control: no-store` on error responses and on personalized endpoints.
4. The mobile app was updated to check status codes instead of `success`.

</DeepDive>

<DeepDive title="Security lens">

- **Don't leak internals in errors**: no stack traces, SQL, hostnames or file paths; log them with a request ID instead.
- **404 instead of 403** for resources the caller shouldn't know exist (other users' orders, private repos).
- **Same response for "no such user" and "wrong password"** on login (401 with one message), so attackers can't discover which emails are registered.
- **429 with `Retry-After`** on login, signup and password reset to slow down brute force.
- **Avoid open redirects**: never redirect to a URL taken from a query parameter without checking it against an allowlist.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between 401 and 403?">
401 means the request isn't authenticated: no credentials or invalid ones, and the response should include WWW-Authenticate. 403 means the server knows who the caller is, but they aren't allowed to do this.
</QA>

<QA q="When would you use 422 instead of 400?">
400 for requests that can't be understood at all, such as malformed JSON or wrong types; 422 for well-formed requests whose content fails validation or business rules, such as an invalid email or a negative quantity. Many teams pick one convention and apply it consistently.
</QA>

<QA q="What's the difference between 301, 302, 307 and 308?">
301 and 308 are permanent, 302 and 307 temporary. With 301 and 302, clients historically change POST to GET; 307 and 308 require the client to repeat the same method and body.
</QA>

<QA q="Which status codes should a client retry?">
Usually 408, 429, 502, 503 and 504, plus network errors, with exponential backoff, jitter and Retry-After when present, and only for idempotent requests or ones protected by an idempotency key. Other 4xx codes need the client to change the request.
</QA>

<QA q="Why is returning 200 with an error in the body a bad idea?">
Caches, proxies, monitoring, browsers and HTTP clients interpret the status code: errors get cached, dashboards show success, fetch reports res.ok true, and retry logic can't distinguish failures. The status code should reflect the real outcome.
</QA>

</DeepDive>
