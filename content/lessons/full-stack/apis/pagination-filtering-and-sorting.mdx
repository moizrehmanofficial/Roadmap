<BigIdea>
<Tr>
<En>
An endpoint like `GET /orders` can't return all 100,000 orders at once: it would be slow, use huge amounts of memory and crash phones. So list endpoints return **one page at a time** and let clients **filter** (`?status=paid`) and **sort** (`?sort=-total`). The simplest scheme is **offset pagination** (`?page=2&per_page=20` → `LIMIT 20 OFFSET 20`): easy to build, supports "jump to page 7" and total counts, but the database must **read and skip** every row before the offset, so deep pages get slower and slower, and if rows are added while someone pages through, items **shift** and appear twice or get skipped. **Cursor (keyset) pagination** instead says "give me the next 20 **after this item**" (`WHERE (created_at, id) < (…) ORDER BY created_at DESC, id DESC LIMIT 20`): it uses an index to jump straight there, costs the same on page 1 or page 5,000, and stays correct while data changes. Whatever you choose: **cap the page size**, turn every filter into a **query parameter**, allow sorting only on an **allowlist** of columns, and always add a **unique tie-breaker** (like `id`) to the sort.
</En>
<Ur>
`GET /orders` jaisa endpoint ek saath saare 100,000 orders nahi lauta sakta: ye sust hoga, bohot memory lega aur phones crash karega. Isliye list endpoints **ek waqt me ek page** lautate hain aur clients ko **filter** (`?status=paid`) aur **sort** (`?sort=-total`) karne dete hain. Sab se saada tareeqa **offset pagination** hai (`?page=2&per_page=20` → `LIMIT 20 OFFSET 20`): banana aasan, "page 7 par jao" aur kul ginti deta hai, magar database ko offset se pehle ki har row **parh kar chhorni** parti hai, isliye gehre pages zyada se zyada sust hote hain, aur agar koi page palat raha ho aur rows jurti jayen to items **khisak** kar do dafa aate ya chhoot jate hain. **Cursor (keyset) pagination** is ke bajaye kehta hai "**is item ke baad** ke agle 20 do" (`WHERE (created_at, id) < (…) ORDER BY created_at DESC, id DESC LIMIT 20`): ye index se seedha wahan pahunchta hai, page 1 ho ya page 5,000 ek jitna kharcha, aur data badalte hue bhi durust rehta hai. Jo bhi chunein: **page size ki hadd** rakhein, har filter ko **query parameter** banayen, sorting sirf columns ki **allowlist** par, aur sort me hamesha **unique tie-breaker** (jaise `id`) jorein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of reading a **very long list of names in a phone book**.

- **Offset**: "Read me names 90,001 to 90,020." The reader starts at name 1 and counts all the way to 90,000 before reading anything out. Asked for the next 20, they count from 1 again.
- If someone **adds a new name near the top** while you're between requests, every name moves down one place, and the first name of your next batch is one you already heard.
- **Cursor**: "The last name you read me was *Smith, J.*; read the 20 after that." The reader opens the book at *Smith* using the alphabetical tabs (the index) and continues. New names added elsewhere don't change where *Smith* is.
- **Sorting** is choosing which order the book is printed in, but only orders the publisher supports (the allowlist), and with a rule for identical names (the tie-breaker).

</En>
<Ur>

**Phone book me naamon ki bohot lambi list** parhne ka sochein.

- **Offset**: "Mujhe naam 90,001 se 90,020 tak sunao." Parhne wala naam 1 se shuru kar ke 90,000 tak ginta hai, phir kuch sunata hai. Agle 20 maangen to phir 1 se ginta hai.
- Agar aap ki darkhwaston ke beech koi **upar ke qareeb naya naam jor de**, to har naam ek jagah neeche khisak jata hai, aur agle batch ka pehla naam wo hota hai jo aap sun chuke.
- **Cursor**: "Aap ne aakhri naam *Smith, J.* sunaya tha; us ke baad ke 20 sunao." Parhne wala alphabet ke tabs (index) se kitab *Smith* par kholta hai aur aage barhta hai. Kahin aur jure naye naam *Smith* ki jagah nahi badalte.
- **Sorting** ye chunna hai ke kitab kis tarteeb me chhapi ho, magar sirf wo tarteeb jo publisher deta hai (allowlist), aur ek jaise naamon ke liye ek qaida (tie-breaker).

</Ur>
</Tr>

<Walkthrough>

<Step title="Offset pagination, filters and safe sorting">

<Tr>
<En>
A PostgreSQL table gets 100,000 orders with predictable values, plus an index on `(created_at DESC, id DESC)`. `GET /orders` validates `page` and `per_page` (max 100), turns `status`, `min_total` and `customer` into bound parameters, and accepts `sort` only from an allowlist, with `-` for descending and `id` as tie-breaker. The response carries `meta` with totals. A small `show.js` prints each response compactly.
</En>
<Ur>
PostgreSQL table me andaze ke mutabiq values wale 100,000 orders aur `(created_at DESC, id DESC)` par index daala jata hai. `GET /orders` `page` aur `per_page` (zyada se zyada 100) check karta hai, `status`, `min_total` aur `customer` ko bound parameters banata hai, aur `sort` sirf allowlist se qubool karta hai, ulte ke liye `-` aur tie-breaker ke tor par `id`. Response me kul ginti wala `meta` hota hai. Chhota `show.js` har response mukhtasar chhapta hai.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
psql -q -h localhost -U postgres -c 'DROP DATABASE IF EXISTS shop' -c 'CREATE DATABASE shop' 2> /dev/null
psql -q -h localhost -U postgres -d shop <<'SQL'
CREATE TABLE orders (
  id          serial PRIMARY KEY,
  customer    text NOT NULL,
  status      text NOT NULL,
  total_cents int  NOT NULL,
  created_at  timestamptz NOT NULL
);
-- 100,000 orders with predictable values
INSERT INTO orders (customer, status, total_cents, created_at)
SELECT 'customer' || (i % 500), (ARRAY['pending','paid','shipped','cancelled'])[i % 4 + 1],
       (i * 37) % 20000 + 100, '2026-01-01'::timestamptz + i * interval '5 minutes'
FROM generate_series(1, 100000) AS i;
CREATE INDEX ON orders (created_at DESC, id DESC);
SQL
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 pg@8.23.1 --silent
cat > app.js <<'EOF'
import express from "express";
import pg from "pg";
const db = new pg.Pool({ connectionString: "postgres://postgres:postgres@localhost:5432/shop" });
const app = express();
const fail = (res, status, code, message) => res.status(status).json({ error: { code, message } });

// Only these columns may be sorted on: user input never goes into SQL directly
const SORTABLE = { created_at: "created_at", total: "total_cents", id: "id" };
const STATUSES = ["pending", "paid", "shipped", "cancelled"];

app.get("/orders", async (req, res) => {
  // ---- pagination: page + per_page with sane limits ----
  const page = Number(req.query.page ?? 1);
  const perPage = Number(req.query.per_page ?? 20);
  if (!Number.isInteger(page) || page < 1) return fail(res, 400, "invalid_page", "page must be a positive integer");
  if (!Number.isInteger(perPage) || perPage < 1 || perPage > 100) return fail(res, 400, "invalid_per_page", "per_page must be 1-100");

  // ---- filtering: each filter becomes a parameter, never string-concatenated ----
  const where = [], params = [];
  if (req.query.status) {
    if (!STATUSES.includes(req.query.status)) return fail(res, 400, "invalid_status", `status must be one of ${STATUSES.join(", ")}`);
    params.push(req.query.status); where.push(`status = $${params.length}`);
  }
  if (req.query.min_total) { params.push(Number(req.query.min_total)); where.push(`total_cents >= $${params.length}`); }
  if (req.query.customer)  { params.push(req.query.customer);          where.push(`customer = $${params.length}`); }
  const whereSql = where.length ? `WHERE ${where.join(" AND ")}` : "";

  // ---- sorting: "-total" = descending; only allowlisted fields ----
  const sortParam = req.query.sort ?? "-created_at";
  const field = SORTABLE[sortParam.replace(/^-/, "")];
  if (!field) return fail(res, 400, "invalid_sort", `sort must be one of ${Object.keys(SORTABLE).join(", ")} (prefix - for descending)`);
  const dir = sortParam.startsWith("-") ? "DESC" : "ASC";

  const { rows } = await db.query(
    `SELECT id, customer, status, total_cents FROM orders ${whereSql}
     ORDER BY ${field} ${dir}, id ${dir} LIMIT ${perPage} OFFSET ${(page - 1) * perPage}`, params);   // id = tie-breaker
  const { rows: [{ count }] } = await db.query(`SELECT count(*)::int FROM orders ${whereSql}`, params);
  res.json({ data: rows, meta: { page, per_page: perPage, total: count, total_pages: Math.ceil(count / perPage) } });
});
app.listen(3000);
EOF
node app.js & PID=$!
until curl -s localhost:3000/orders > /dev/null; do sleep 0.1; done
cat > show.js <<'EOF'
// prints a compact summary of one response
const r = await (await fetch("http://localhost:3000/orders" + process.argv[2])).json();
if (r.error) console.log("  ->", r.error.code + ":", r.error.message);
else {
  console.log("  -> meta", JSON.stringify(r.meta));
  console.log("     ids", r.data.map((o) => o.id).join(", "), "| first:", JSON.stringify(r.data[0]));
}
EOF
show() { node show.js "$1"; }
echo "GET /orders?per_page=3";                                      show "?per_page=3"
echo "GET /orders?per_page=3&page=2";                               show "?per_page=3&page=2"
echo "GET /orders?status=paid&min_total=19900&sort=-total&per_page=3"; show "?status=paid&min_total=19900&sort=-total&per_page=3"
echo "GET /orders?customer=customer7&sort=id&per_page=2";           show "?customer=customer7&sort=id&per_page=2"
echo "GET /orders?per_page=5000";                                   show "?per_page=5000"

kill $PID
```

<Happened>
<Tr>
<En>

- Page 1 and page 2 returned consecutive orders (newest first, the default sort), and `meta` told the client there are 100,000 orders in 33,334 pages.
- Filters combined with `AND`: 250 paid orders of at least $199.00, sorted by `-total`. Every value went to PostgreSQL as `$1`, `$2`…, so a filter like `?customer=x' OR '1'='1` is just a customer name that matches nothing.
- `sort=id` returned customer7's orders oldest first. Because the sort always ends with `id`, rows with equal values (many orders share a total) come back in a **stable** order; without a tie-breaker, the database may return them in a different order on each request, and items jump between pages.
- `per_page=5000` was rejected: always cap page sizes.
- `sort=password` and `sort=id;DROP TABLE orders` were rejected. Column names can't be sent as `$1` parameters, so `ORDER BY` is a classic SQL injection spot; mapping the input through an allowlist (`SORTABLE`) means only known column names ever reach the SQL.

</En>
<Ur>

- Page 1 aur page 2 ne lagatar orders lautaye (naye pehle, default sort), aur `meta` ne client ko bataya ke 33,334 pages me 100,000 orders hain.
- Filters `AND` se jure: kam az kam $199.00 ke 250 paid orders, `-total` se sorted. Har value PostgreSQL ko `$1`, `$2`… ke tor par gayi, isliye `?customer=x' OR '1'='1` jaisa filter bas ek customer ka naam hai jo kisi se mel nahi khata.
- `sort=id` ne customer7 ke orders purane pehle lautaye. Kyunke sort hamesha `id` par khatam hota hai, barabar values wali rows (bohot se orders ka total ek jaisa hai) **mustahkam** tarteeb me aati hain; tie-breaker ke baghair database har request par mukhtalif tarteeb de sakta hai, aur items pages ke darmiyan uchhalte hain.
- `per_page=5000` rad hua: hamesha page size ki hadd rakhein.
- `sort=password` aur `sort=id;DROP TABLE orders` rad hue. Column names `$1` parameters ke tor par nahi bheje ja sakte, isliye `ORDER BY` SQL injection ki mashhoor jagah hai; input ko allowlist (`SORTABLE`) se guzarne ka matlab hai sirf jaane pehchane column names SQL tak pahunchte hain.

</Ur>
</Tr>

<Step title="Why offset breaks down, and cursor pagination">

<Tr>
<En>
First we ask PostgreSQL (`EXPLAIN ANALYZE`) how many rows it reads to return 20 rows deep in the list, with an offset and with a keyset condition. Then a second server offers `GET /feed` with **cursor pagination**: the cursor is the last item's `(created_at, id)`, base64url-encoded. We page through both APIs while a new order is created between page 1 and page 2.
</En>
<Ur>
Pehle hum PostgreSQL se (`EXPLAIN ANALYZE`) poochte hain ke list me gehrai par 20 rows lautane ke liye wo kitni rows parhta hai, offset ke saath aur keyset shart ke saath. Phir doosra server **cursor pagination** wala `GET /feed` deta hai: cursor aakhri item ka `(created_at, id)` hai, base64url me encode. Hum dono APIs ke pages palatte hain jab ke page 1 aur page 2 ke beech naya order banta hai.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
# 1. Cost: how many rows does PostgreSQL read to return 20 rows deep in the list?
rows_read() { psql -h localhost -U postgres -d shop -tA -c "EXPLAIN (ANALYZE, FORMAT JSON) $1" \
  | node -e 'const p = JSON.parse(require("fs").readFileSync(0))[0].Plan; console.log(p.Plans[0]["Actual Rows"])'; }
echo "OFFSET 90000 LIMIT 20 -> rows read: $(rows_read "SELECT id FROM orders ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 90000")"
echo "keyset (cursor) 20     -> rows read: $(rows_read "SELECT id FROM orders WHERE (created_at, id) < ('2026-02-04 06:20+00', 10001) ORDER BY created_at DESC, id DESC LIMIT 20")"
# 2. Cursor pagination endpoint
cat > feed.js <<'EOF'
import express from "express";
import pg from "pg";
const db = new pg.Pool({ connectionString: "postgres://postgres:postgres@localhost:5432/shop" });
const app = express();
app.use(express.json());

// The cursor is the sort key of the last item (timestamp as text, so no microseconds are lost),
// encoded so clients treat it as opaque
const encode = (o) => Buffer.from(JSON.stringify([o.created_at, o.id])).toString("base64url");
const decode = (c) => JSON.parse(Buffer.from(c, "base64url").toString());

app.get("/feed", async (req, res) => {
  const limit = Math.min(Number(req.query.limit ?? 20), 100);
  const params = [limit + 1];                                   // fetch one extra to know if there's more
  let where = "";
  if (req.query.cursor) {
    try { params.push(...decode(req.query.cursor)); } catch { return res.status(400).json({ error: { code: "invalid_cursor" } }); }
    where = "WHERE (created_at, id) < ($2, $3)";                // continue right after the last item seen
  }
  const { rows } = await db.query(
    `SELECT id, created_at::text FROM orders ${where} ORDER BY created_at DESC, id DESC LIMIT $1`, params);
  const hasMore = rows.length > limit;
  const page = rows.slice(0, limit);
  res.json({ data: page.map((o) => o.id), next_cursor: hasMore ? encode(page.at(-1)) : null });
});

app.post("/orders", async (req, res) => {
  const { rows: [o] } = await db.query(
    "INSERT INTO orders (customer, status, total_cents, created_at) VALUES ('customer1', 'pending', 500, now() + interval '1 year') RETURNING id");
  res.status(201).json(o);
});
app.listen(3001);
EOF
node app.js & A=$!
node feed.js & B=$!
until curl -s localhost:3000/orders > /dev/null && curl -s localhost:3001/feed > /dev/null; do sleep 0.1; done
ids() { node -e 'console.log(JSON.parse(require("fs").readFileSync(0)).data.map((o) => o.id ?? o).join(", "))'; }
echo "--- offset pages while a new order arrives"
echo "page 1: $(curl -s 'localhost:3000/orders?per_page=3&page=1' | ids)"
echo "        (new order $(curl -s -X POST localhost:3001/orders | node -pe 'JSON.parse(require("fs").readFileSync(0)).id') created)"
echo "page 2: $(curl -s 'localhost:3000/orders?per_page=3&page=2' | ids)   <- 99998 again: everything shifted by one"
echo "--- cursor pages while a new order arrives"
P1=$(curl -s 'localhost:3001/feed?limit=3')
echo "page 1: $(echo "$P1" | ids)"
echo "        next_cursor: $(echo "$P1" | node -pe 'JSON.parse(require("fs").readFileSync(0)).next_cursor')"
echo "        (new order $(curl -s -X POST localhost:3001/orders | node -pe 'JSON.parse(require("fs").readFileSync(0)).id') created)"
C=$(echo "$P1" | node -pe 'JSON.parse(require("fs").readFileSync(0)).next_cursor')
echo "page 2: $(curl -s "localhost:3001/feed?limit=3&cursor=$C" | ids)   <- continues exactly after page 1"
echo "tampered cursor: $(curl -s 'localhost:3001/feed?cursor=abc')"
kill $A $B
```

<Happened>
<Tr>
<En>

- To return 20 rows at `OFFSET 90000`, PostgreSQL read **90,020** rows and threw 90,000 away. The keyset query read **20**: the index on `(created_at DESC, id DESC)` let it jump straight to the position. Offset cost grows with page depth; cursor cost doesn't.
- With offset, a new order arriving between requests pushed everything down one place, so page 2 started with **99998, which page 1 had already shown**. On a feed, users see duplicates; with deletions instead, they silently miss items.
- With cursors, page 2 continued **exactly after** page 1 even though another order was created in between: the query asks for rows "after (created_at, id) of the last item", not "after position 3".
- The response returns `next_cursor` (null on the last page). Fetching `limit + 1` rows tells us whether there's more without a separate count query.
- The cursor is **opaque**: clients pass it back unchanged. A malformed cursor got a clean 400. The timestamp is kept as **text** from PostgreSQL, because JavaScript `Date` drops microseconds, which would make cursor comparisons subtly wrong.

</En>
<Ur>

- `OFFSET 90000` par 20 rows lautane ke liye PostgreSQL ne **90,020** rows parhin aur 90,000 phenk din. Keyset query ne **20** parhin: `(created_at DESC, id DESC)` wale index ne use seedha us jagah pahuncha diya. Offset ka kharcha page ki gehrai ke saath barhta hai; cursor ka nahi.

## Common mistakes

<Compare>
<Bad title="Sort column straight from the query string">

```text
const sort = req.query.sort;                                        // "id; DROP TABLE orders --"
db.query(`SELECT * FROM orders ORDER BY ${sort} LIMIT ${req.query.limit}`);   // injection + no limit cap
```

</Bad>
<Good title="Allowlist the column, cap the limit, bind the values">

```text
const field = SORTABLE[req.query.sort?.replace(/^-/, '')] ?? 'created_at';
const limit = Math.min(Number(req.query.limit) || 20, 100);
db.query(`SELECT … ORDER BY ${field} DESC, id DESC LIMIT $1`, [limit]);
```

</Good>
</Compare>

<Compare>
<Bad title="Sorting by a non-unique column only">

```text
ORDER BY total_cents DESC LIMIT 20 OFFSET 20
-- many orders share a total: their order is undefined, items repeat or vanish across pages
```

</Bad>
<Good title="Always end with a unique tie-breaker">

```text
ORDER BY total_cents DESC, id DESC LIMIT 20 OFFSET 20
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **No index for the sort**: pagination on an unindexed column sorts the whole table every request. Index the columns you sort and filter on, in the same order.
- **`count(*)` on every request of a huge table**: it can cost more than the page itself. Cache it, estimate it, or drop it for feeds.
- **Exposing raw cursor contents** as an API contract: clients start building cursors themselves, and you can't change the format. Encode them and document them as opaque.
- **Accepting any filter field** (`?where=…`, `?filter[password_hash]=…`): allowlist filterable fields too.
- **Different page shapes per endpoint**: use the same `data` + `meta` (or `next_cursor`) envelope everywhere.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sort ke liye index nahi**: bina index wale column par pagination har request par poora table sort karti hai. Jin columns par sort aur filter karte hain unhen usi tarteeb me index karein.
- **Bohot bare table par har request me `count(*)`**: ye page se bhi mehnga par sakta hai. Cache karein, andaza lagayen, ya feeds ke liye chhor dein.
- **Cursor ka kacha mawad** API muahide ke tor par dikhana: clients khud cursors banane lagte hain, aur aap format nahi badal sakte. Encode karein aur band dibba likhein.
- **Koi bhi filter field qubool karna** (`?where=…`, `?filter[password_hash]=…`): filter hone wale fields ki bhi allowlist rakhein.
- **Har endpoint ka mukhtalif page dhancha**: har jagah ek hi `data` + `meta` (ya `next_cursor`) lifafa istemal karein.

</Ur>
</Tr>

```text
WHERE (price_cents, id) < (4999, 120)
```

<DeepDive title="More about pagination">

**Previous page with cursors.** Return a `prev_cursor` (first item's key), query with the comparison and order reversed, then reverse the results.

**Link headers.** Some APIs (GitHub) put `next`/`prev` URLs in a `Link` header; others return `links` in the body. Either way, clients should follow the URL rather than build it.

**Approximate counts.** `SELECT reltuples FROM pg_class WHERE relname = 'orders'` gives an instant estimate for "about 2.3 million results".

**Filter syntax.** Simple `?status=paid` covers most needs; for ranges use `min_`/`max_` or `price[gte]=…`. Avoid exposing a general query language unless you can secure and index it.

**Search.** Text search belongs in full-text indexes (PostgreSQL `tsvector`, or a search engine), not `LIKE '%…%'` on large tables.

</DeepDive>

<DeepDive title="Real world: the export that never finished">

An analytics product let customers export all their events through the public API using `?page=N&per_page=1000`. Small customers were fine. A large customer with 40 million events started an export script.

The first pages took milliseconds; page 10,000 took 9 seconds, because each request skipped 10 million rows. The database CPU stayed at 100% for hours, slowing every other customer. Meanwhile new events kept arriving, so the export contained thousands of duplicates and missed others.

The fixes:

1. The events endpoint switched to cursor pagination on `(occurred_at, id)` with a composite index; deep pages became as fast as the first.
2. `per_page` was capped at 1,000, and `page` above 100 was rejected with a message pointing to the cursor API.
3. Large exports moved to an asynchronous job (`202 Accepted`) that writes a file to storage.
4. Per-customer rate limits protected everyone else from one heavy client.

</DeepDive>

<DeepDive title="Security lens">

- **SQL injection in ORDER BY and filters**: allowlist identifiers, bind all values.
- **Denial of service**: cap page size, limit page depth for offset, add timeouts and rate limits to list endpoints.
- **Data leaks through filters**: always add the caller's own scope (`WHERE tenant_id = … AND user_id = …`) before user filters.
- **Enumeration**: sequential IDs in lists and cursors can reveal business volume; consider opaque IDs.
- **Tampered cursors**: validate decoded cursor values (types, ranges) and, if they contain anything sensitive, sign or encrypt them.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between offset and cursor pagination?">
Offset pagination skips N rows and returns M, supporting page numbers and totals but becoming slow for deep pages and unstable when data changes. Cursor or keyset pagination continues after the last item's sort key using an indexed comparison, giving constant performance and stable results but only next and previous navigation.
</QA>

<QA q="Why is OFFSET slow on large tables?">
The database still has to produce and discard every row before the offset, so the cost grows linearly with the offset, even with an index.
</QA>

<QA q="How do you safely let clients choose a sort field?">
Map the requested field through an allowlist of known column names, parse a direction prefix, append a unique tie-breaker, and never interpolate raw input; identifiers can't be bound as query parameters.
</QA>

<QA q="What is a tie-breaker and why is it needed?">
A unique column such as id added at the end of the sort. Without it, rows with equal sort values have no defined order, so they can appear on multiple pages or none, and keyset cursors can't identify a unique position.
</QA>

<QA q="What should a paginated response contain?">
The page of items plus navigation: for offset, page, page size, and optionally total and total pages; for cursors, the next cursor or a next link and whether more items exist, in a consistent envelope across endpoints.
</QA>

</DeepDive>
