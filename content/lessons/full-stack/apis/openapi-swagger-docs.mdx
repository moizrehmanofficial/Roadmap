<BigIdea>
<Tr>
<En>
**OpenAPI** (formerly called **Swagger**) is a standard format, written in YAML or JSON, that describes an HTTP API completely: every **path**, the **operations** on it (GET, POST…), their **parameters**, **request bodies**, possible **responses** and the **schemas** (shapes) of all data. Because it's machine-readable, one file powers many tools: **interactive docs** (Swagger UI, Redoc), **linters** that catch mistakes, **generated clients and TypeScript types** so frontend code can't call the API wrongly, **mock servers**, **contract tests**, and **runtime validation** that rejects bad requests and catches buggy responses. You can write the file first and build to it (**contract-first**), or generate it from code, as NestJS does with decorators (**code-first**). Either way the rule is the same: the OpenAPI document is the **single source of truth** for the API, and everything else is generated from it or checked against it, so docs and code can't silently drift apart.
</En>
<Ur>
**OpenAPI** (pehle **Swagger** kehlata tha) YAML ya JSON me likha muqarrar format hai jo HTTP API ko mukammal bayan karta hai: har **path**, us par **operations** (GET, POST…), un ke **parameters**, **request bodies**, mumkina **responses** aur saare data ke **schemas** (shaklen). Kyunke ye machine ke parhne laiq hai, ek file bohot se tools chalati hai: **interactive docs** (Swagger UI, Redoc), ghaltiyan pakarne wale **linters**, **generated clients aur TypeScript types** taa ke frontend code API ko ghalat na bula sake, **mock servers**, **contract tests**, aur **runtime validation** jo ghalat requests rad karti aur bug wale responses pakarti hai. Aap file pehle likh kar us ke mutabiq bana sakte hain (**contract-first**), ya code se bana sakte hain, jaise NestJS decorators se karta hai (**code-first**). Dono surat me qaida ek hai: OpenAPI document API ka **wahid asal source** hai, aur baqi sab is se banta ya is se check hota hai, taa ke docs aur code khamoshi se alag na ho jayen.
</Ur>

## Picture it

<Tr>
<En>

Think of an **architect's blueprint for a building**.

- The **blueprint** (the OpenAPI file) shows every room (path), every door into it (operation), what you may carry in (request body) and what you'll find inside (responses).
- A **building inspector** reads the blueprint before construction and spots a door that leads to a room that doesn't exist (the linter catching a broken `$ref`).
- **Visitors' maps** are printed from the blueprint, so they're always right (Swagger UI).
- **Furniture makers** measure from the blueprint, so the sofa fits the door (generated types for clients).
- A **guard at each door** checks visitors against the blueprint's rules on the way in and on the way out (runtime request and response validation).

</En>
<Ur>

**Imarat ke liye architect ke naqshe** ka sochein.

- **Naqsha** (OpenAPI file) har kamra (path), us ka har darwaza (operation), andar kya le ja sakte hain (request body) aur andar kya milega (responses) dikhata hai.
- **Building inspector** tameer se pehle naqsha parh kar aisa darwaza pakarta hai jo na mojood kamre me khulta hai (linter toota `$ref` pakarta hai).
- **Mehmanon ke nakshe** naqshe se chhape jate hain, isliye hamesha durust hote hain (Swagger UI).
- **Furniture banane wale** naqshe se naap lete hain, isliye sofa darwaze se guzar jata hai (clients ke liye generated types).
- **Har darwaze par chowkidar** andar aate aur bahar jate naqshe ke qawaid se check karta hai (runtime request aur response validation).

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Write the contract, lint it, generate types">

<Tr>
<En>
`openapi.yaml` describes three operations (`listOrders`, `createOrder`, `getOrder`) and reusable schemas: `OrderStatus` (an enum), `OrderItem`, `NewOrder` (what clients send), `Order` (what the API returns) and `Error`. One `$ref` contains a typo on purpose. We lint the file with Redocly's recommended rules (a few rules that don't matter for a local demo are switched off in `redocly.yaml`), fix the typo, generate TypeScript types with openapi-typescript, and type-check a small client written with openapi-fetch that contains two mistakes.
</En>
<Ur>
`openapi.yaml` teen operations (`listOrders`, `createOrder`, `getOrder`) aur dobara istemal hone wale schemas bayan karta hai: `OrderStatus` (enum), `OrderItem`, `NewOrder` (jo clients bhejte hain), `Order` (jo API lautati hai) aur `Error`. Ek `$ref` me jaan boojh kar typo hai. Hum Redocly ke recommended qawaid se file lint karte hain (maqami demo me ghair-ahem chand qawaid `redocly.yaml` me band hain), typo theek karte hain, openapi-typescript se TypeScript types banate hain, aur openapi-fetch se likhe chhote client ko type-check karte hain jis me do ghaltiyan hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module
npm install -D @redocly/cli@2.82.0 openapi-typescript@7.13.0 typescript@5.9.3 --silent
npm install openapi-fetch@0.17.0 --silent
cat > openapi.yaml <<'EOF'
openapi: 3.1.0
info:
  title: Shop API
  version: 1.0.0
  description: Orders for the example shop.
servers:
  - url: http://localhost:3000
paths:
  /orders:
    get:
      operationId: listOrders
      summary: List orders
      parameters:
        - name: status
          in: query
          schema: { $ref: '#/components/schemas/OrderStatus' }
      responses:
        '200':
          description: A page of orders
          content:
            application/json:
              schema:
                type: object
                required: [data]
                properties:
                  data: { type: array, items: { $ref: '#/components/schemas/Order' } }
    post:
      operationId: createOrder
      summary: Create an order
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/NewOrder' }
      responses:
        '201':
          description: Created
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '400':
          description: Invalid input
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Error' }
  /orders/{id}:
    get:
      operationId: getOrder
      summary: Get one order
      parameters:
        - { name: id, in: path, required: true, schema: { type: integer, minimum: 1 } }
      responses:
        '200':
          description: The order
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Oder' }        # typo on purpose
        '404':
          description: Not found
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Error' }
components:
  schemas:
    OrderStatus: { type: string, enum: [pending, paid, shipped] }
    OrderItem:
      type: object
      additionalProperties: false
      required: [sku, qty]
      properties:
        sku: { type: string }
        qty: { type: integer, minimum: 1, maximum: 100 }
    NewOrder:
      type: object
      additionalProperties: false
      required: [customerEmail, items]
      properties:
        customerEmail: { type: string, format: email }
        items: { type: array, minItems: 1, items: { $ref: '#/components/schemas/OrderItem' } }
    Order:
      type: object
      required: [id, customerEmail, items, status, totalCents]
      properties:
        id: { type: integer }
        customerEmail: { type: string, format: email }
        items: { type: array, items: { $ref: '#/components/schemas/OrderItem' } }
        status: { $ref: '#/components/schemas/OrderStatus' }
        totalCents: { type: integer }
    Error:
      type: object
      required: [error]
      properties:
        error:
          type: object
          required: [code, message]
          properties:
            code: { type: string }
            message: { type: string }
EOF
printf 'extends:\n  - recommended\nrules:\n  security-defined: off\n  info-license: off\n  no-server-example.com: off\n  operation-4xx-response: off\n' > redocly.yaml
lint() { npx redocly lint openapi.yaml --format=stylish 2>&1 | grep -E ' error | warning |Woohoo|failed' | sed -E 's/^ *//; s/ +/ /g; s/ *🎉//; s/^❌ //'; }
echo "--- lint the contract"; lint
sed -i "s|schemas/Oder' }        # typo on purpose|schemas/Order' }|" openapi.yaml
echo "--- after fixing the typo"; lint
echo "--- generate TypeScript types from it"
npx openapi-typescript openapi.yaml -o api-types.ts > /dev/null 2>&1
sed -n '/^    schemas: {/,/^    };/p' api-types.ts | sed -n '2,22p'
cat > client.ts <<'EOF'
import createClient from "openapi-fetch";
import type { paths } from "./api-types.js";

const api = createClient<paths>({ baseUrl: "http://localhost:3000" });

export async function demo() {
  const { data } = await api.GET("/orders/{id}", { params: { path: { id: 7 } } });
  console.log(data?.totalCents);
  await api.POST("/orders", { body: { customerEmail: "jane@example.com", items: [{ sku: "lamp", quantity: 2 }] } });  // typo: qty
  await api.GET("/orders", { params: { query: { status: "delivered" } } });                                       // not in the enum
}
EOF
echo "--- type-check a client written against the contract"
npx tsc --noEmit --strict --module nodenext --moduleResolution nodenext --skipLibCheck client.ts 2>&1 \
  | sed -E "s/^client.ts\(([0-9]+),[0-9]+\): error TS[0-9]+: /line \1: /; s/ & \{\}'/'/; s/\.$//"
```

<Happened>
<Tr>
<En>

- The linter found the broken reference (`Oder` instead of `Order`) with its exact line and column. Without linting, docs would render a missing schema and code generators would fail or produce `unknown`. After the fix: valid.
- openapi-typescript turned the schemas into TypeScript: the enum became a union `"pending" | "paid" | "shipped"`, `format: email` became a comment, and `$ref`s became references to other types. Regenerate whenever the spec changes (in CI or a pre-build script).
- The client, typed with `paths`, was checked against the contract by the compiler: sending `quantity` instead of `qty` and filtering by a status that doesn't exist (`delivered`) were both **compile errors**. Paths, parameters and response types are all checked, and `data?.totalCents` is known to be a number.
- This is the biggest practical win of OpenAPI: when the API changes, regenerate types and the compiler lists every place in the frontend that must change.

</En>
<Ur>

- Linter ne toota hawala (`Order` ki jagah `Oder`) us ki bilkul line aur column ke saath pakra. Lint ke baghair docs ghaib schema dikhatin aur code generators nakam hote ya `unknown` banate. Theek karne ke baad: valid.
- openapi-typescript ne schemas ko TypeScript me badla: enum union `"pending" | "paid" | "shipped"` bana, `format: email` comment bana, aur `$ref`s doosri types ke hawale bane. Jab bhi spec badle dobara generate karein (CI ya pre-build script me).
- `paths` se typed client ko compiler ne contract se check kiya: `qty` ki jagah `quantity` bhejna aur na mojood status (`delivered`) se filter karna dono **compile errors** bane. Paths, parameters aur response types sab check hote hain, aur `data?.totalCents` ka number hona maloom hai.
- OpenAPI ka sab se bara amli faida yahi hai: API badle to types dobara banayen aur compiler frontend ki har wo jagah bata deta hai jise badalna zaroori hai.

</Ur>
</Tr>
</Happened>

<Step title="Serve docs and validate at runtime">

<Tr>
<En>
An Express server serves the contract at `/openapi.json`, interactive **Swagger UI** at `/docs`, and puts **express-openapi-validator** in front of the handlers with `validateRequests` (reporting all errors) and `validateResponses` on. The handlers contain no validation code at all. One handler has a bug: for order 2 it sends `totalCents` as a string.
</En>
<Ur>
Express server contract ko `/openapi.json` par, interactive **Swagger UI** ko `/docs` par deta hai, aur handlers ke aage `validateRequests` (saare errors batane ke saath) aur `validateResponses` on kar ke **express-openapi-validator** rakhta hai. Handlers me validation ka koi code nahi. Ek handler me bug hai: order 2 ke liye wo `totalCents` string bana kar bhejta hai.
</Ur>
</Tr>

```bash
npm install express@5.1.0 express-openapi-validator@5.6.2 swagger-ui-express@5.0.1 yaml@2.9.1 --silent
cat > server.js <<'EOF'
import express from "express";
import * as OpenApiValidator from "express-openapi-validator";
import swaggerUi from "swagger-ui-express";
import { parse } from "yaml";
import { readFileSync } from "node:fs";

const spec = parse(readFileSync("openapi.yaml", "utf8"));
const orders = [{ id: 1, customerEmail: "jane@example.com", items: [{ sku: "lamp", qty: 1 }], status: "paid", totalCents: 2999 }];
const app = express();
app.use(express.json());

app.get("/openapi.json", (req, res) => res.json(spec));               // the contract, for tools and clients
app.use("/docs", swaggerUi.serve, swaggerUi.setup(spec));             // interactive docs from the same file

// Every request AND response is checked against openapi.yaml
app.use(OpenApiValidator.middleware({ apiSpec: "./openapi.yaml", validateRequests: { allErrors: true }, validateResponses: true }));

app.get("/orders", (req, res) => res.json({ data: orders.filter((o) => !req.query.status || o.status === req.query.status) }));
app.post("/orders", (req, res) => {
  const order = { id: orders.length + 1, ...req.body, status: "pending", totalCents: req.body.items.reduce((s, i) => s + i.qty * 2999, 0) };
  orders.push(order);
  res.status(201).json(order);
});
app.get("/orders/:id", (req, res) => {
  const order = orders.find((o) => o.id === Number(req.params.id));
  if (!order) return res.status(404).json({ error: { code: "not_found", message: "Order not found" } });
  if (order.id === 2) return res.json({ ...order, totalCents: String(order.totalCents) });   // a bug: number sent as string
  res.json(order);
});

app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  res.status(status).json({ error: { code: status === 500 ? "internal" : "invalid_request",
    message: err.errors?.map((e) => `${e.path} ${e.message}`).join("; ") ?? err.message } });
});
app.listen(3000);
EOF
node server.js & PID=$!
until curl -s localhost:3000/openapi.json > /dev/null; do sleep 0.1; done
r() { echo "$1 $2 ${3:+$3 }-> $(curl -s -X $1 "localhost:3000$2" -H 'content-type: application/json' ${3:+-d "$3"} -w ' %{http_code}')"; }
r POST /orders '{"customerEmail":"john@example.com","items":[{"sku":"lamp","qty":2}]}'
r POST /orders '{"customerEmail":"john@example.com","items":[{"sku":"lamp","quantity":2}]}'
r POST /orders '{"customerEmail":"not-an-email","items":[{"sku":"lamp","qty":0}]}'
r GET '/orders?status=delivered'
r GET /orders/abc
r GET /orders/2
echo "GET /docs -> $(curl -s -L localhost:3000/docs/ -o docs.html -w '%{http_code}'), page title: $(grep -o '<title>[^<]*' docs.html | cut -c8-)"
echo "GET /openapi.json -> paths: $(curl -s localhost:3000/openapi.json | node -pe 'Object.keys(JSON.parse(require("fs").readFileSync(0)).paths).join(", ")')"
kill $PID
```

<Happened>
<Tr>
<En>

- The valid order was created with **201**. Every invalid request was rejected with **400** and precise messages derived from the spec: a missing `qty` plus an unknown `quantity` (`additionalProperties: false`), a bad email format and `qty` below the minimum (both reported thanks to `allErrors`), a status outside the enum, and a non-integer path parameter. None of that was written by hand.
- `GET /orders/2` returned **500**: response validation caught the server sending `totalCents` as a string, breaking the promise in the contract. Without it, clients would silently receive `"5998"` and maybe concatenate instead of add. Response validation costs CPU, so many teams enable it in development, tests and staging, and sample it in production.
- Swagger UI at `/docs` and `/openapi.json` are generated from the same file, so the docs can't fall out of date.
- Note the schema design: `NewOrder` (input) and `Order` (output) are separate. Reusing one schema with `additionalProperties: false` for both, or combining them with `allOf`, often makes responses fail validation, because extra fields like `id` count as "additional".

</En>
<Ur>

- Sahi order **201** ke saath bana. Har ghalat request spec se bane durust messages ke saath **400** se rad hui: ghaib `qty` plus anjaan `quantity` (`additionalProperties: false`), ghalat email format aur kam az kam se kam `qty` (`allErrors` ki wajah se dono bataye gaye), enum se bahar status, aur integer na hone wala path parameter. In me se kuch bhi haath se nahi likha gaya.
- `GET /orders/2` ne **500** lautaya: response validation ne server ko `totalCents` string bana kar bhejte pakar liya, jo contract ka wada torta hai. Is ke baghair clients khamoshi se `"5998"` paate aur shayad jorne ke bajaye joor dete. Response validation CPU khata hai, isliye bohot si teams ise development, tests aur staging me on rakhti hain, aur production me namoona leti hain.
- `/docs` par Swagger UI aur `/openapi.json` usi file se bante hain, isliye docs purane nahi ho sakte.
- Schema design par dhyan dein: `NewOrder` (input) aur `Order` (output) alag hain. `additionalProperties: false` ke saath dono ke liye ek schema istemal karna, ya `allOf` se milana, aksar responses ki validation nakam karta hai, kyunke `id` jaise izafi fields "additional" gine jate hain.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Docs written by hand, separate from the code">

```text
README.md: "POST /orders accepts { email, items }"
code:      expects { customerEmail, items }       // docs drifted months ago; nobody noticed
```

</Bad>
<Good title="One contract, everything checked against it">

```text
openapi.yaml → Swagger UI (docs)
             → openapi-typescript (client types)
             → express-openapi-validator (requests + responses)
             → CI: redocly lint + oasdiff breaking-change check
```

</Good>
</Compare>

<Compare>
<Bad title="Vague schemas">

```text
responses:
  '200':
    description: OK
    content:
      application/json:
        schema: { type: object }          # tells clients nothing; generates `Record<string, unknown>`
```

</Bad>
<Good title="Precise schemas with required fields">

```text
schema:
  type: object
  required: [id, status, totalCents]
  properties:
    id: { type: integer }
    status: { $ref: '#/components/schemas/OrderStatus' }
    totalCents: { type: integer, description: Total in cents (USD) }
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Documenting only the happy path**: list error responses (400, 401, 404, 409, 429) with the error schema, so clients know what to handle.
- **Forgetting `required`**: without it every property is optional, and generated types are full of `?`.
- **Exposing internal endpoints** in public docs: keep admin or internal operations in a separate spec, or filter them out.
- **Leaving Swagger UI open in production with "Try it out" against live data**: protect it or point it at a sandbox.
- **Never regenerating clients**: wire type generation into the build so it can't go stale.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sirf kamyabi ka raasta likhna**: error responses (400, 401, 404, 409, 429) error schema ke saath likhein, taa ke clients jaanen ke kya sambhalna hai.
- **`required` bhoolna**: is ke baghair har property ikhtiyari hai, aur generated types `?` se bhare hote hain.
- **Public docs me andaruni endpoints dikhana**: admin ya andaruni operations alag spec me rakhein, ya chhaant dein.
- **Production me live data par "Try it out" ke saath Swagger UI khula chhorna**: ise mehfooz karein ya sandbox ki taraf karein.
- **Clients kabhi dobara generate na karna**: type generation ko build me jorein taa ke purani na ho sake.

</Ur>
</Tr>

<DeepDive title="More about OpenAPI">

**OpenAPI 3.1 and JSON Schema.** 3.1 uses full JSON Schema 2020-12 (`type: [string, "null"]` for nullable, `unevaluatedProperties`), unlike 3.0's subset with `nullable: true`.

**Mock servers.** Prism or similar tools serve example responses straight from the spec, so frontends can start before the backend exists.

**SDK generation.** OpenAPI Generator and other tools produce clients in many languages; publish them with semantic versions.

**Examples.** `example` / `examples` on schemas and operations make docs far more useful and feed mock servers.

**Code-first in NestJS.** See the OpenAPI / Swagger in NestJS lesson: DTO decorators produce the same document, which you can lint, diff and generate clients from just the same.

**Overlays and bundling.** Split big specs into files and bundle them (`redocly bundle`); overlays adjust a spec for public vs internal audiences.

</DeepDive>

<DeepDive title="Real world: the docs nobody trusted">

A logistics company had a partner API documented in a wiki page. Over two years, fields were renamed, endpoints added and error codes changed, but the wiki was updated only sometimes. Partners learned to ignore it and asked support instead; integrating a new partner took six weeks of back-and-forth.

The team wrote an OpenAPI file for the existing API and turned on response validation in staging. Within a day it reported 37 mismatches between what the API actually returned and what they had written: nullable fields that weren't marked nullable, dates in two different formats, an endpoint returning 200 with an error body.

The fixes:

1. Each mismatch was either fixed in the code or documented honestly in the spec.
2. Docs were generated from the spec on every deploy, with examples for every operation.
3. CI ran lint and a breaking-change diff on every pull request touching the spec or the handlers.
4. Partners got generated SDKs and a sandbox; onboarding dropped from six weeks to under one.

</DeepDive>

<DeepDive title="Security lens">

- **Describe security**: declare `securitySchemes` and apply them per operation, so docs and tools know which endpoints need auth (and reviewers notice ones that don't).
- **Strict schemas are a defense**: `additionalProperties: false`, string formats, lengths and enums block mass assignment and junk input before handlers run.
- **Don't publish internal details**: internal endpoints, debug parameters and example data with real customer information don't belong in public specs.
- **Protect Swagger UI** in production, or disable "Try it out" against live systems.
- **Response validation can prevent leaks**: if a handler accidentally returns `passwordHash`, a strict response schema can block it.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is OpenAPI and how is it related to Swagger?">
OpenAPI is a standard specification for describing HTTP APIs in YAML or JSON. Swagger was the original name of the specification; today Swagger refers to tools such as Swagger UI and Swagger Editor that work with OpenAPI documents.
</QA>

<QA q="What's the difference between contract-first and code-first?">
Contract-first writes and agrees on the OpenAPI document before implementing, then validates the code against it; code-first generates the document from annotations or types in the code. Contract-first suits public or multi-team APIs, code-first suits single-team services.
</QA>

<QA q="What can you generate or automate from an OpenAPI document?">
Interactive docs, client SDKs and TypeScript types, server stubs, mock servers, request and response validation, contract and fuzz tests, linting and breaking-change detection between versions.
</QA>

<QA q="Why validate responses as well as requests?">
Response validation proves the server keeps its own contract, catching bugs such as wrong types, missing required fields or leaked extra fields before clients rely on them; it's often enabled in tests and staging because of its cost.
</QA>

<QA q="How do you keep API docs from going out of date?">
Make the OpenAPI document the source of truth, generate docs and clients from it automatically, validate the implementation against it in tests or at runtime, and lint and diff it in CI on every change.
</QA>

</DeepDive>
