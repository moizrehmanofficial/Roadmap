<BigIdea>
<Tr>
<En>
Debugging is a process, not luck: **reproduce** the problem, **narrow down** where it happens, **look** at the real values there, **fix**, and **confirm** the fix (ideally with a test). Node.js gives you a tool for every kind of bug. For **errors**, read the **stack trace** from the top: it names the error, the file and the line; async stack traces and `error.cause` show how you got there. For **wrong values**, log precisely (`console.table`, labels, types) or, better, pause the program with a **breakpoint** using the **inspector** (`node --inspect`) from VS Code or Chrome DevTools and inspect every variable. For **slowness**, record a **CPU profile** (`--cpu-prof`) to see which function uses the time instead of guessing. For **growing memory**, measure `heapUsed` over time and take **heap snapshots** to see which objects pile up and who holds on to them. In production, good **logs**, **metrics** and **error tracking** are your debugger.
</En>
<Ur>
Debugging qismat nahi, ek tareeqa hai: masla **dobara paida** karein, jagah **tang** karein ke kahan hota hai, wahan asli values **dekhein**, **theek** karein, aur fix ki **tasdeeq** karein (behtar hai test se). Node.js har qism ke bug ke liye auzaar deta hai. **Errors** ke liye **stack trace** upar se parhein: ye error, file aur line batata hai; async stack traces aur `error.cause` dikhate hain ke aap wahan kaise pohanche. **Ghalat values** ke liye durust tareeqe se log karein (`console.table`, labels, types) ya, behtar, VS Code ya Chrome DevTools se **inspector** (`node --inspect`) ke zariye **breakpoint** par program rok kar har variable dekhein. **Susti** ke liye andaze ke bajaye **CPU profile** (`--cpu-prof`) record karein taa ke dikhe ke kaun sa function waqt leta hai. **Barhti memory** ke liye waqt ke saath `heapUsed` naapein aur **heap snapshots** lein taa ke dikhe ke kaun se objects jama ho rahe hain aur unhen kaun pakre hue hai. Production me achhe **logs**, **metrics** aur **error tracking** aap ka debugger hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **doctor** with a patient.

- First the **symptoms** and **when they happen** (reproduce the bug). "It hurts when I do this" is worth more than "something is wrong".
- The **patient's history** (the stack trace): what happened, in which order, leading to the problem.
- **Tests** that measure exactly (logs and breakpoints): blood pressure, temperature, not guesses.
- An **X-ray** to see inside without surgery: a CPU profile shows where time goes, a heap snapshot shows what fills memory.
- Treat the **cause**, not the symptom, then a **follow-up visit** to check it's really gone (a regression test).

</En>
<Ur>

Mareez ke saath **doctor** ka sochein.

- Pehle **alamaat** aur **ye kab hoti hain** (bug dobara paida karna). "Ye karne par dard hota hai" "kuch ghalat hai" se kahin qeemti hai.
- **Mareez ki history** (stack trace): kya hua, kis tarteeb me, jo masle tak le gaya.
- Bilkul naapne wale **tests** (logs aur breakpoints): blood pressure, bukhar, andaze nahi.
- Operation ke baghair andar dekhne ke liye **X-ray**: CPU profile dikhata hai waqt kahan jata hai, heap snapshot dikhata hai memory kis se bharti hai.
- Alamat nahi, **wajah** ka ilaaj, phir check karne ke liye **dobara visit** ke wo sach me chala gaya (regression test).

</Ur>
</Tr>

<Walkthrough>

<Step title="Look at the real data: a NaN total">

<Tr>
<En>
The cart total prints `NaN`. Instead of staring at the code, look at the **data** and log each step with **labels and types**.
</En>
<Ur>
Cart ka total `NaN` print hota hai. Code ko ghoorne ke bajaye **data** dekhein aur har qadam **labels aur types** ke saath log karein.
</Ur>
</Tr>

```bash
cat > cart.mjs <<'EOF'
const cart = [
  { name: "Mug", price: 12, qty: 2 },
  { name: "Desk Lamp", price: 30, qty: "1" },   // came from a form: a string
  { name: "Notebook", price: 5 },                // qty missing
];

function total(items) {
  let sum = 0;
  for (const item of items) sum += item.price * item.qty;
  return sum;
}
console.log("total:", total(cart));

// Step 1: look at the data as a table
console.table(cart);

// Step 2: log each step with labels and types
let sum = 0;
for (const item of cart) {
  const line = item.price * item.qty;
  sum += line;
  console.log(`${item.name.padEnd(10)} qty=${JSON.stringify(item.qty)} (${typeof item.qty}) line=${line} running=${sum}`);
}
EOF
node cart.mjs
```

```text output
total: NaN
┌─────────┬─────────────┬───────┬─────┐
│ (index) │ name        │ price │ qty │
├─────────┼─────────────┼───────┼─────┤
│ 0       │ 'Mug'       │ 12    │ 2   │
│ 1       │ 'Desk Lamp' │ 30    │ '1' │
│ 2       │ 'Notebook'  │ 5     │     │
└─────────┴─────────────┴───────┴─────┘
Mug        qty=2 (number) line=24 running=24
Desk Lamp  qty="1" (string) line=30 running=54
Notebook   qty=undefined (undefined) line=NaN running=NaN
```

<Happened>
<Tr>
<En>

- `console.table` immediately shows two odd values: `'1'` in quotes (a string) and an empty `qty`.
- The labelled log pinpoints the moment it breaks: the string `"1"` happened to work (`30 * "1"` is 30), but `5 * undefined` is `NaN`, and `NaN` poisons every sum after it.
- `JSON.stringify` and `typeof` in logs reveal what `console.log(x)` can hide (a string `"1"` and the number `1` print the same in many places).
- The real fix isn't in `total()`: validate input where it enters the system (a zod schema with `z.coerce.number().int().min(1)` for `qty`), so bad data is rejected with a clear message.

</En>
<Ur>

- `console.table` foran do ajeeb values dikhata hai: quotes me `'1'` (string) aur khaali `qty`.
- Labels wala log bilkul wo lamha batata hai jab ye toot'ta hai: string `"1"` ittefaq se chal gayi (`30 * "1"` 30 hai), magar `5 * undefined` `NaN` hai, aur `NaN` us ke baad har jor ko zehrila kar deta hai.
- Logs me `JSON.stringify` aur `typeof` wo dikhate hain jo `console.log(x)` chhupa sakta hai (string `"1"` aur number `1` kai jagah ek jaise print hote hain).
- Asli fix `total()` me nahi: input ko wahan validate karein jahan wo system me aata hai (`qty` ke liye `z.coerce.number().int().min(1)` wala zod schema), taa ke ghalat data wazeh paighaam ke saath radd ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Read stack traces, including async ones and causes">

<Tr>
<En>
When you wrap an error, keep the original as **`cause`**. Node's stack traces also include the **async** callers that awaited the failing function.
</En>
<Ur>
Jab error lapetein to asli ko **`cause`** ki tarah rakhein. Node ke stack traces fail hone wale function ka **await** karne wale **async** callers bhi shamil karte hain.
</Ur>
</Tr>

```bash
cat > async-stack.mjs <<'EOF'
async function loadUser(id) {
  await new Promise((r) => setTimeout(r, 10));
  throw new Error(`User ${id} not found`);
}
async function loadOrders(userId) {
  try {
    await loadUser(userId);
  } catch (err) {
    throw new Error("Could not load orders", { cause: err });   // keep the original error
  }
}
async function handleRequest() {
  await loadOrders(42);
}
try {
  await handleRequest();
} catch (err) {
  console.log(err.message);
  console.log("cause:", err.cause.message);
  console.log(err.stack.split("\n").slice(0, 4).join("\n"));
}
EOF
node async-stack.mjs
```

```text output
Could not load orders
cause: User 42 not found
Error: Could not load orders
    at loadOrders (file:///home/you/async-stack.mjs:9:11)
    at async handleRequest (file:///home/you/async-stack.mjs:13:3)
    at async file:///home/you/async-stack.mjs:16:3
```

<Happened>
<Tr>
<En>

- Read a stack trace **top down**: the first line is the error, the next `at …` line is where it was thrown (`async-stack.mjs`, line **9**, column 11), then who called it.
- `at async handleRequest` shows the trace survived the `await`s. Node keeps these async frames for `async`/`await` code; old callback code loses them, one more reason to use promises.
- The friendly message ("Could not load orders") is for the caller, and `err.cause` keeps the technical reason ("User 42 not found"). Loggers like pino print the whole chain.
- With TypeScript or bundled code, run Node with `--enable-source-maps` so the lines point to your original `.ts` files.

</En>
<Ur>

- Stack trace **upar se neeche** parhein: pehli line error hai, agli `at …` line wo jagah hai jahan throw hua (`async-stack.mjs`, line **9**, column 11), phir kis ne use call kiya.
- `at async handleRequest` dikhata hai ke trace `await`s ke baad bhi bacha raha. Node `async`/`await` code ke liye ye async frames rakhta hai; purana callback code unhen kho deta hai, promises istemal karne ki ek aur wajah.
- Dostana paighaam ("Could not load orders") caller ke liye hai, aur `err.cause` takneeki wajah ("User 42 not found") rakhta hai. pino jaise loggers poori zanjeer print karte hain.
- TypeScript ya bundled code ke saath Node ko `--enable-source-maps` se chalayen taa ke lines aap ki asli `.ts` files ki taraf ishara karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What an unhandled rejection does">

<Tr>
<En>
A promise that rejects with nobody listening is an **unhandled rejection**. Since Node 15, it crashes the process. Recognise this output: you'll see it in container logs.
</En>
<Ur>
Aisa promise jo reject ho aur koi sun na raha ho **unhandled rejection** hai. Node 15 se ye process crash kar deta hai. Ye output pehchanein: aap ise container logs me dekhenge.
</Ur>
</Tr>

```bash
cat > crash.mjs <<'EOF'
async function charge() {
  throw new Error("Payment provider timed out");
}
charge();   // no await, no .catch: an unhandled rejection
setTimeout(() => console.log("this never runs"), 100);
EOF
node crash.mjs; echo "exit code: $?"
```

```text output
file:///home/you/crash.mjs:2
  throw new Error("Payment provider timed out");
        ^

Error: Payment provider timed out
    at charge (file:///home/you/crash.mjs:2:9)
    at file:///home/you/crash.mjs:4:1
    at ModuleJob.run (node:internal/modules/esm/module_job:343:25)
    at async onImport.tracePromise.__proto__ (node:internal/modules/esm/loader:681:26)
    at async asyncRunEntryPointWithESMLoader (node:internal/modules/run_main:117:5)

Node.js v22.23.4
exit code: 1
```

<Happened>
<Tr>
<En>

- Node printed the source line with a `^` marker, the error and stack, then its version, and exited with code **1**. The timer never ran: the whole process was gone.
- Frames from `node:internal/…` are Node's own code; your bug is in the first frames that point to **your** files (`crash.mjs:2` and `crash.mjs:4`, the call without `await`).
- Fixes: `await` promises inside `try/catch`, add `.catch()` to fire-and-forget calls, and lint for it (`@typescript-eslint/no-floating-promises`).
- A `process.on("unhandledRejection", …)` handler should **log and exit** (let the supervisor restart you), not swallow the error and continue in an unknown state.

</En>
<Ur>

- Node ne `^` nishaan ke saath source line, error aur stack, phir apna version print kiya, aur code **1** ke saath band hua. Timer kabhi nahi chala: poora process khatam tha.
- `node:internal/…` wale frames Node ka apna code hain; aap ka bug pehle un frames me hai jo **aap ki** files ki taraf ishara karte hain (`crash.mjs:2` aur `crash.mjs:4`, `await` ke baghair call).
- Hal: promises ko `try/catch` ke andar `await` karein, "chala ke bhool jao" calls me `.catch()` jorein, aur lint karein (`@typescript-eslint/no-floating-promises`).
- `process.on("unhandledRejection", …)` handler ko **log kar ke exit** karna chahiye (supervisor ko dobara shuru karne dein), error nigal kar na maloom halat me jari nahi rehna chahiye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Find a slow function with a CPU profile">

<Tr>
<En>
A report of 100,000 rows takes seconds. Instead of guessing, record a **CPU profile**. Normally you'd open the `.cpuprofile` file in Chrome DevTools (Performance panel) or VS Code; here a small script reads it and lists the hottest function.
</En>
<Ur>
100,000 rows ki report seconds leti hai. Andaze ke bajaye **CPU profile** record karein. Aam taur par aap `.cpuprofile` file Chrome DevTools (Performance panel) ya VS Code me kholte; yahan chhota script use parh kar sab se garam function batata hai.
</Ur>
</Tr>

```bash
cat > slow.mjs <<'EOF'
function formatPrice(n) {
  return new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" }).format(n);   // created every call!
}
function buildReport(rows) {
  return rows.map((r) => `${r.id}: ${formatPrice(r.amount)}`).join("\n");
}
const rows = Array.from({ length: 100_000 }, (_, i) => ({ id: i, amount: i * 1.5 }));
buildReport(rows);
EOF
node --cpu-prof --cpu-prof-dir=profiles slow.mjs
cat > top.mjs <<'EOF'
import { readdirSync, readFileSync } from "node:fs";
const file = readdirSync("profiles").find((f) => f.endsWith(".cpuprofile"));
const { nodes, samples } = JSON.parse(readFileSync(`profiles/${file}`, "utf8"));
const byId = new Map(nodes.map((n) => [n.id, n]));
const hits = new Map();
for (const id of samples) {
  const name = byId.get(id).callFrame.functionName || "(anonymous)";
  hits.set(name, (hits.get(name) ?? 0) + 1);
}
const [hottest] = [...hits].sort((a, b) => b[1] - a[1]);
console.log("profile written:", file.endsWith(".cpuprofile"));
console.log("function where the CPU spent the most time:", hottest[0]);
EOF
node top.mjs
cat > fixed.mjs <<'EOF'
const usd = new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" });   // created once
const slowFormat = (n) => new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" }).format(n);
const rows = Array.from({ length: 100_000 }, (_, i) => ({ id: i, amount: i * 1.5 }));

rows.map((r) => slowFormat(r.amount));
const before = performance.now() - t;
t = performance.now();

const after = performance.now() - t;
console.log(`reusing the formatter is more than 20x faster: ${before / after > 20}`);
EOF
node fixed.mjs
```

<Step title="Find a memory leak with a heap snapshot">

<Tr>
<En>
A classic leak: a `Map` used as a cache that only ever grows. We simulate 50,000 requests, measure how much the heap grew, then take a **heap snapshot** and count the objects of class `Session` in it. Then the same with a fix that keeps at most 1,000 sessions.
</En>
<Ur>
Mashhoor leak: cache ki tarah istemal hone wala `Map` jo sirf barhta hai. Hum 50,000 requests ki naqal karte hain, naapte hain ke heap kitna barha, phir **heap snapshot** le kar us me class `Session` ke objects ginte hain. Phir wahi fix ke saath jo zyada se zyada 1,000 sessions rakhta hai.
</Ur>
</Tr>

```bash
cat > leak.mjs <<'EOF'
import { writeHeapSnapshot } from "node:v8";
import { readFileSync, rmSync } from "node:fs";

class Session {
  constructor(id) { this.id = id; this.data = "x".repeat(1000) + id; }
}
const fixed = process.argv[2] === "fixed";
const sessions = new Map();
const MAX = 1000;

function handleRequest(i) {
  sessions.set(`s${i}`, new Session(i));
  if (fixed && sessions.size > MAX) {
    sessions.delete(sessions.keys().next().value);   // drop the oldest (Maps keep insertion order)
  }
}

const mb = () => process.memoryUsage().heapUsed / 1024 / 1024;
global.gc();
const before = mb();
for (let i = 0; i < 50_000; i++) handleRequest(i);
global.gc();
const grew = mb() - before;

// Take a heap snapshot and count objects by class name
const file = writeHeapSnapshot();
const snap = JSON.parse(readFileSync(file, "utf8"));
rmSync(file);
const { node_fields, node_types } = snap.snapshot.meta;
const nameIdx = node_fields.indexOf("name"), typeIdx = node_fields.indexOf("type");
let count = 0;
for (let i = 0; i < snap.nodes.length; i += node_fields.length) {
  if (node_types[0][snap.nodes[i + typeIdx]] === "object" && snap.strings[snap.nodes[i + nameIdx]] === "Session") count++;
}
const growth = grew > 20 ? "by 20+ MB" : grew < 5 ? "by under 5 MB" : `by ${Math.round(grew)} MB`;
console.log(`${fixed ? "fixed" : "leaky"}: heap grew ${growth}, Session objects alive: ${count}`);
EOF
node --expose-gc leak.mjs
node --expose-gc leak.mjs fixed
```

```text output
leaky: heap grew by 20+ MB, Session objects alive: 50000
fixed: heap grew by under 5 MB, Session objects alive: 1000
```

<Happened>
<Tr>
<En>

- The leaky version kept **all 50,000** sessions alive (20+ MB of heap) because the `Map` still referenced them; the garbage collector can only free objects nothing points to.
- The fixed version kept **1,000** and the heap barely grew. In a real server, the leaky version grows with every request until it hits the heap limit and crashes ("JavaScript heap out of memory").
- In Chrome DevTools (Memory tab) the workflow is: take snapshot 1, send traffic, take snapshot 2, choose **Comparison**, sort by "# New". The **Retainers** panel then shows the chain keeping the objects alive (here: `sessions` → Map → Session).
- Usual suspects: unbounded caches and Maps, event listeners never removed, timers never cleared, closures holding big objects, global arrays used as queues. Use an LRU cache with a size limit (`lru-cache`) or a TTL, and `WeakMap` for data attached to objects.
- `--expose-gc` and `global.gc()` are only for experiments like this, to get stable measurements; never in production code.

</En>
<Ur>

- Leaky version ne **tamam 50,000** sessions zinda rakhe (20+ MB heap) kyun ke `Map` ab bhi un ka hawala rakhta tha; garbage collector sirf wo objects azad kar sakta hai jin ki taraf kuch ishara na kare.
- Fixed version ne **1,000** rakhe aur heap mushkil se barha. Asli server me leaky version har request ke saath barhta hai yahan tak ke heap ki hadd se takra kar crash ho ("JavaScript heap out of memory").
- Chrome DevTools (Memory tab) me tareeqa: snapshot 1 lein, traffic bhejein, snapshot 2 lein, **Comparison** chunein, "# New" se tarteeb dein. Phir **Retainers** panel objects ko zinda rakhne wali zanjeer dikhata hai (yahan: `sessions` → Map → Session).
- Aam mushtabah: be-hadd caches aur Maps, kabhi na hataye event listeners, kabhi na saaf kiye timers, bare objects pakre closures, queues ki tarah istemal hone wali global arrays. Size ki hadd wala LRU cache (`lru-cache`) ya TTL lein, aur objects se jure data ke liye `WeakMap`.
- `--expose-gc` aur `global.gc()` sirf aise tajurbon ke liye hain, mustahkam naap ke liye; production code me kabhi nahi.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Guess, change, hope">

```text
"It's probably the database."  → add an index → still slow
"Maybe the JSON?"               → change the parser → still slow
// two days later the profile shows a regex compiled in a loop
```

</Bad>
<Good title="Measure first">

```text
1. Reproduce:  curl the slow endpoint 100 times, note p95 = 2.4 s
2. Profile:    node --cpu-prof server.mjs + load test → hottest function
3. Fix it:     move the regex out of the loop
4. Confirm:    p95 = 90 ms, add a benchmark or test so it stays fast
```

</Good>
</Compare>

<Compare>
<Bad title="Swallowing errors">

```text
try {
  await saveOrder(order);
} catch {
  // ignore
}
// the bug happens, nothing is logged, the order is silently lost
```

</Bad>
<Good title="Handle, add context, or rethrow">

```text
try {
  await saveOrder(order);
} catch (err) {
  logger.error({ err, orderId: order.id, requestId }, "saving order failed");
  throw new Error("Could not save your order", { cause: err });
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Reading only the last line** of a stack trace (often Node internals) instead of the first frames in your code.
- **Leaving debug logs** (`console.log("here 2")`) in commits; use a logger with levels, or logpoints.
- **`--inspect` on `0.0.0.0` in production**: anyone who can reach port 9229 can run code in your process.
- **Profiling in development mode** with dev-only overhead; profile a production-like build with real data sizes.
- **Calling `process.exit()` in error handlers** before logs are flushed, losing the very message you needed.
- **Fixing symptoms** (`|| 0` to hide `NaN`) instead of the cause (validating input).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Apne code ke pehle frames ke bajaye stack trace ki **sirf aakhri line parhna** (aksar Node ka andaruni code).
- Commits me **debug logs chhorna** (`console.log("here 2")`); levels wala logger ya logpoints lein.
- **Production me `0.0.0.0` par `--inspect`**: jo bhi port 9229 tak pohanch sake wo aap ke process me code chala sakta hai.
- Sirf development ke bojh ke saath **development mode me profiling**; asli data size ke saath production jaisi build profile karein.
- Logs flush hone se pehle **error handlers me `process.exit()`**, wahi paighaam kho dena jo chahiye tha.
- Wajah (input validation) ke bajaye **alamat theek karna** (`NaN` chhupane ke liye `|| 0`).

</Ur>
</Tr>

<DeepDive title="More debugging tools">

**Useful flags.** `--trace-warnings` (where a warning came from), `--trace-uncaught`, `--trace-exit` (who called `process.exit`), `--stack-trace-limit=50` (longer traces), `--heapsnapshot-near-heap-limit=2` (write snapshots automatically before an out-of-memory crash), `--heapsnapshot-signal=SIGUSR2` (take one on demand in production).

**`NODE_DEBUG`.** `NODE_DEBUG=http,net node app.mjs` prints Node's own internal debug logs for those modules; many libraries use the `debug` package with `DEBUG=express:*`.

**`util.inspect`.** `console.dir(obj, { depth: null, colors: true })` prints deeply nested objects that `console.log` would cut off as `[Object]`.

**Diagnostic reports.** `node --report-on-fatalerror` writes a JSON report (stack, heap stats, environment, handles) when Node crashes.

**Debugging tests.** `node --inspect-brk --test` or the VS Code test explorer; Vitest and Jest have debug modes.

**Clinic.js and 0x.** Open-source tools that run your app under load and produce flame graphs and diagnoses (event loop delay, I/O, GC pressure).

**Production observability.** Structured logs (pino), error tracking (Sentry), metrics (Prometheus), traces (OpenTelemetry) tell you *where* to look before you ever attach a debugger.

**`git bisect`.** When "it worked last week", let Git binary-search the commits: mark a good and a bad commit, test each step, and it finds the change that introduced the bug.

</DeepDive>

<DeepDive title="Real world: the leak that only happened on Fridays">

A company's Node.js notification service ran fine all week but crashed with "JavaScript heap out of memory" every Friday afternoon. Restarting fixed it, so for weeks the team just restarted it on Fridays.

Memory graphs finally showed the pattern: memory grew slowly all week and very fast on Fridays. Fridays were when the marketing team sent their weekly newsletter, which triggered thousands of notifications.

An engineer started the service in staging with `--heapsnapshot-signal=SIGUSR2`, replayed a newsletter's worth of traffic, and took two snapshots an hour apart. The comparison showed hundreds of thousands of new `Timeout` objects and closures. Their retainers pointed to a retry helper: for every failed email it scheduled a `setTimeout` retry and stored the timer in a `Map` keyed by message ID, so it could cancel the retry if the email later succeeded. Successful retries never removed their entry, and each entry held the whole email body in its closure.

The fix was three lines: delete the Map entry when a retry finished, cap retries at five, and keep only the message ID in the closure. Memory became flat, and the Friday restarts stopped. The team also added an alert on heap growth rate and kept `--heapsnapshot-near-heap-limit=2` enabled so the next leak would leave evidence automatically.

</DeepDive>

<DeepDive title="Security lens">

- **The inspector is remote code execution by design**: only bind it to `127.0.0.1` (the default), never `--inspect=0.0.0.0` on a reachable server; use SSH tunnels.
- **Heap snapshots and core dumps contain secrets**: passwords, tokens, user data in memory. Treat them as sensitive files and delete them after use.
- **Logs**: never log passwords, tokens, full cookies or card numbers; redact (Environment Configuration lesson).
- **Error responses**: stack traces belong in logs, not in HTTP responses.
- **Debug endpoints** (`/debug`, `/heap`) added during an investigation must be removed or protected before deploying.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you debug a Node.js application?">
Reproduce the issue, read the stack trace, add targeted structured logging, and use the inspector with --inspect or --inspect-brk from VS Code or Chrome DevTools to set breakpoints, conditional breakpoints and watches. For performance use CPU profiles; for memory, heap snapshots; in production rely on logs, metrics, traces and error tracking.
</QA>

<QA q="How would you find a memory leak in Node.js?">
Confirm growth with heap metrics over time, reproduce with load, take heap snapshots before and after, compare them to see which object types increase, and inspect the retainer chains to find what keeps them alive, such as unbounded caches, listeners, timers or closures. Fix the reference and verify memory becomes stable.
</QA>

<QA q="How do you find out why an endpoint is slow?">
Measure latency first, then record a CPU profile while generating load, using --cpu-prof, the DevTools Performance panel or tools like Clinic.js, and look at the hottest functions in the flame graph. Also check event loop delay and I/O timings, since slowness can come from waiting on databases rather than CPU.
</QA>

<QA q="What happens with unhandled promise rejections?">
Since Node 15 an unhandled rejection is treated like an uncaught exception: Node prints the error and exits with code 1. You should await or catch every promise, and global handlers should log and exit rather than swallow the error.
</QA>

<QA q="What's the purpose of error.cause?">
It attaches the original error to a new, higher-level error, so you can add context like "could not load orders" without losing the low-level reason and its stack trace, which loggers and debuggers can show as a chain.
</QA>

</DeepDive>

<DeepDive title="More practice">

1. Set a conditional breakpoint in VS Code on one of your loops and inspect only the unusual items.
2. Add `{ cause }` to the errors in one of your services and check how your logger prints them.

4. Create a deliberate leak (an ever-growing array), take two heap snapshots in DevTools and find it in the Comparison view.
