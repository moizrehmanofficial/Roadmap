<BigIdea>
<Tr>
<En>
Almost no Node.js project is written from scratch: you build on **packages** other people published to the **npm registry** (over three million of them). **npm**, which comes with Node.js, downloads them into a **`node_modules`** folder. Your project's **`package.json`** is its ID card and shopping list: name, version, **scripts** (`npm run dev`), and the packages it needs with **version ranges** (`"express": "^5.1.0"` means "5.1.0 or any newer 5.x"). Because ranges allow newer versions, two installs on different days could get different code. **`package-lock.json`** fixes that: it records the **exact** version, download URL and **integrity hash** of every package, including the dependencies of your dependencies. Commit both files, never `node_modules`. On servers and in CI, run **`npm ci`**, which installs exactly what the lockfile says and fails if it doesn't match `package.json`. Packages run code on your machine, so choose them carefully and audit them.
</En>
<Ur>
Taqreeban koi Node.js project shuru se nahi likha jata: aap un **packages** par banate hain jo doosre logon ne **npm registry** par shaya kiye (teen million se zyada). **npm**, jo Node.js ke saath aata hai, unhen **`node_modules`** folder me download karta hai. Aap ke project ki **`package.json`** us ka shanakhti card aur khareedari ki list hai: naam, version, **scripts** (`npm run dev`), aur zaroori packages **version ranges** ke saath (`"express": "^5.1.0"` ka matlab "5.1.0 ya koi naya 5.x"). Kyun ke ranges naye versions ki ijazat deti hain, mukhtalif dinon ki do installs alag code le sakti hain. **`package-lock.json`** ise theek karti hai: ye har package ka **bilkul** version, download URL aur **integrity hash** likhti hai, aap ki dependencies ki dependencies samet. Dono files commit karein, `node_modules` kabhi nahi. Servers aur CI par **`npm ci`** chalayen, jo bilkul wahi install karta hai jo lockfile kehti hai aur `package.json` se na mile to fail hota hai. Packages aap ki machine par code chalate hain, isliye unhen dhyaan se chunein aur audit karein.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **Reproducible builds**: "works on my machine" bugs often come from different dependency versions; the lockfile makes every install identical.

- **Every Node.js, React and Next.js job** uses npm (or pnpm/yarn/bun, which follow the same ideas).

</En>
<Ur>

- **Dobara ek jaisi builds**: "meri machine par chalta hai" wale bugs aksar mukhtalif dependency versions se aate hain; lockfile har install ko ek jaisa banati hai.

## Picture it

<Tr>
<En>

Think of **baking from a recipe**.

- `package.json` is the **recipe**: "flour (any brand, at least 500 g), sugar (version 2 or newer)". It's flexible on purpose.
- `package-lock.json` is the **receipt from the last time it worked**: "Brand X flour, batch 2.1.3, bought from this shop, checksum on the bag". Follow the receipt and the cake tastes the same every time.
- `node_modules` is the **pantry**: you don't send the pantry to a friend, you send the recipe and the receipt; they can stock their own.
- `npm ci` is a **strict baker** who throws out the pantry and buys exactly what the receipt says, and refuses to bake if the recipe and receipt disagree.
- An ingredient that brings its own ingredients (express needs 60 other packages) is why one line in the recipe can fill a whole shelf.

</En>
<Ur>

**Recipe se baking** ka sochein.

- `package.json` **recipe** hai: "aata (koi bhi brand, kam az kam 500 g), cheeni (version 2 ya naya)". Ye jaan boojh kar lachakdar hai.
- `package-lock.json` **pichhli kamyab dafa ki raseed** hai: "Brand X aata, batch 2.1.3, is dukan se, theli par checksum". Raseed par chalein to cake har dafa ek jaisa banta hai.
- `node_modules` **godaam** hai: aap dost ko godaam nahi bhejte, recipe aur raseed bhejte hain; wo apna bhar sakta hai.
- `npm ci` **sakht baker** hai jo godaam khaali kar ke bilkul wahi khareedta hai jo raseed kehti hai, aur recipe aur raseed na milein to bake karne se inkaar karta hai.
- Aisa ingredient jo apne ingredients saath laye (express ko 60 doosre packages chahiyen) isi liye recipe ki ek line poora shelf bhar sakti hai.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |

## Learn it step by step

<Walkthrough>

<Step title="Create package.json">

<Tr>
<En>
`npm init -y` creates a `package.json` with default answers. Every Node project, library or app, starts with one.
</En>
<Ur>
`npm init -y` default jawabon ke saath `package.json` banata hai. Har Node project, library ho ya app, isi se shuru hota hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null
cat package.json
```

```text output
{
  "name": "lab",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}
```

<Happened>
<Tr>
<En>

- `name` came from the folder name (`lab`). `version` and `license` matter if you **publish** a package; for an app you can leave them.
- `main` is the entry file other code gets when it imports a **library**. Apps usually add `"private": true` so they can never be published by accident.
- `scripts` holds named commands; the default `test` just fails with a message.

</En>
<Ur>

- `name` folder ke naam (`lab`) se aaya. `version` aur `license` tab ahem hain jab aap package **shaya** karein; app ke liye chhor sakte hain.
- `main` wo entry file hai jo doosra code **library** import karne par leta hai. Apps aam taur par `"private": true` jorti hain taa ke ghalti se kabhi shaya na hon.
- `scripts` naam wale commands rakhta hai; default `test` bas paighaam ke saath fail hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Install a package">

<Tr>
<En>
`npm install ms@2.1.3` downloads the small `ms` package (it converts "2 days" to milliseconds) into `node_modules`, adds it to `package.json`, and creates a lockfile.
</En>
<Ur>
`npm install ms@2.1.3` chhota `ms` package (jo "2 days" ko milliseconds me badalta hai) `node_modules` me download karta hai, use `package.json` me jorta hai, aur lockfile banata hai.
</Ur>
</Tr>

```bash
npm install ms@2.1.3 --silent
node -p "require('./package.json').dependencies"
node -e "const ms = require('ms'); console.log(ms('2 days'), ms(90000))"
ls
ls node_modules
```

```text output
{ ms: '^2.1.3' }
172800000 2m
node_modules
package-lock.json
package.json
ms
```

<Happened>
<Tr>
<En>

- Even though we asked for exactly `2.1.3`, npm saved the **range** `^2.1.3` in `package.json`. Use `npm install --save-exact` (or `save-exact=true` in `.npmrc`) if you want exact versions there.
- `require('ms')` found the package by looking in `node_modules`. No path needed.
- `package-lock.json` appeared next to `package.json`. Both go in git; `node_modules` doesn't.

</En>
<Ur>

- Humne bilkul `2.1.3` maanga phir bhi npm ne `package.json` me **range** `^2.1.3` mehfooz ki. Wahan bilkul versions chahiyen to `npm install --save-exact` (ya `.npmrc` me `save-exact=true`) lein.
- `require('ms')` ne `node_modules` me dekh kar package dhoonda. Path ki zaroorat nahi.
- `package.json` ke saath `package-lock.json` aa gayi. Dono git me jati hain; `node_modules` nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What the lockfile records">

<Tr>
<En>
The lockfile lists every installed package with its exact version, where it was downloaded from, and a hash of the file.
</En>
<Ur>
Lockfile har install hue package ko us ke bilkul version, download ki jagah, aur file ke hash ke saath likhti hai.
</Ur>
</Tr>

```bash
node -p "const l = require('./package-lock.json'); JSON.stringify({ lockfileVersion: l.lockfileVersion, ms: l.packages['node_modules/ms'] }, null, 2)"
```

```text output
{
  "lockfileVersion": 3,
  "ms": {
    "version": "2.1.3",
    "resolved": "https://registry.npmjs.org/ms/-/ms-2.1.3.tgz",
    "integrity": "sha512-6FlzubTLZG3J2a/NVCAleEhjzq5oxgHyaCU9yYXvcLsvoVaHJq/s5xXI6/XXP6tz7R9xAOtHnSO/tXtF3WRTlA==",
    "license": "MIT"
  }
}
```

<Happened>
<Tr>
<En>

- **`version`**: exactly 2.1.3, even though `package.json` allows any 2.x from 2.1.3 up.
- **`resolved`**: the exact tarball URL.
- **`integrity`**: a SHA-512 hash of that tarball. If anyone (a compromised mirror, a man-in-the-middle) serves different bytes, the install fails.
- Lockfile changes should be reviewed in pull requests like code: a lockfile diff shows exactly which packages changed versions.

</En>
<Ur>

- **`version`**: bilkul 2.1.3, halanke `package.json` 2.1.3 se upar koi bhi 2.x allow karti hai.
- **`resolved`**: bilkul tarball URL.
- **`integrity`**: us tarball ka SHA-512 hash. Agar koi (hack hua mirror, darmiyan ka aadmi) mukhtalif bytes de to install fail hota hai.
- Lockfile ki tabdeeliyan pull requests me code ki tarah review honi chahiyen: lockfile ka diff bilkul batata hai ke kin packages ke versions badle.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Version ranges: ^, ~ and exact">

<Tr>
<En>
Packages follow **semantic versioning**: `MAJOR.MINOR.PATCH`. A major bump may break your code; minor adds features; patch fixes bugs. Ranges say which updates you accept. We installed the `semver` package (the same library npm uses) as a dev dependency and tested four versions against three ranges.
</En>
<Ur>
Packages **semantic versioning** follow karte hain: `MAJOR.MINOR.PATCH`. Major tabdeeli aap ka code tor sakti hai; minor features jorti hai; patch bugs theek karti hai. Ranges batati hain ke aap kaun si updates qubool karte hain. Humne `semver` package (wahi library jo npm istemal karta hai) dev dependency ki tarah install kiya aur chaar versions ko teen ranges par test kiya.
</Ur>
</Tr>

```bash
npm install --save-dev semver@7.8.6 --silent
for v in 1.2.3 1.9.0 2.0.0 1.2.2; do
  printf "%-6s  ^1.2.3:%-5s ~1.2.3:%-5s 1.2.3:%s\n" "$v" \
    "$(npx semver -r '^1.2.3' $v >/dev/null && echo yes || echo no)" \
    "$(npx semver -r '~1.2.3' $v >/dev/null && echo yes || echo no)" \
    "$(npx semver -r '1.2.3' $v >/dev/null && echo yes || echo no)"
done
```

```text output
1.2.3   ^1.2.3:yes   ~1.2.3:yes   1.2.3:yes
1.9.0   ^1.2.3:yes   ~1.2.3:no    1.2.3:no
2.0.0   ^1.2.3:no    ~1.2.3:no    1.2.3:no
1.2.2   ^1.2.3:no    ~1.2.3:no    1.2.3:no
```

<Happened>
<Tr>
<En>

- **`^1.2.3`** (caret, npm's default): any `1.x.y` from 1.2.3 up. Accepts new features and fixes, **not** 2.0.0.
- **`~1.2.3`** (tilde): only patches, `1.2.x` from 1.2.3 up. 1.9.0 is refused.
- **`1.2.3`**: exactly that version.
- For `0.x` versions, caret is stricter: `^0.4.1` allows only `0.4.x`, because in 0.x every minor change may break things.
- `npx semver` ran the command from the locally installed package (`node_modules/.bin`), with no global install.

</En>
<Ur>

- **`^1.2.3`** (caret, npm ka default): 1.2.3 se upar koi bhi `1.x.y`. Naye features aur fixes qubool, 2.0.0 **nahi**.
- **`~1.2.3`** (tilde): sirf patches, 1.2.3 se upar `1.2.x`. 1.9.0 radd.
- **`1.2.3`**: bilkul wahi version.
- `0.x` versions ke liye caret zyada sakht hai: `^0.4.1` sirf `0.4.x` allow karta hai, kyun ke 0.x me har minor tabdeeli cheezein tor sakti hai.
- `npx semver` ne command maqami install hue package (`node_modules/.bin`) se chalaya, global install ke baghair.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Scripts: names for your commands">

<Tr>
<En>
`scripts` gives short names to commands. npm adds `node_modules/.bin` to the PATH while a script runs, so installed tools work without `npx`. A script named `pre<name>` runs automatically before `<name>`, and arguments after `--` are passed through.
</En>
<Ur>
`scripts` commands ko chhote naam deta hai. Script chalte waqt npm `node_modules/.bin` ko PATH me jorta hai, isliye install hue tools `npx` ke baghair chalte hain. `pre<name>` naam ki script `<name>` se pehle khud chalti hai, aur `--` ke baad ke arguments aage diye jate hain.
</Ur>
</Tr>

```bash
npm pkg set scripts.greet="node greet.mjs" scripts.pregreet="echo '(pregreet runs first)'" type=module
cat > greet.mjs <<'EOF'
import ms from "ms";
const name = process.argv[2] ?? "friend";
console.log(`Hello, ${name}! A week is ${ms("7d")} ms.`);
EOF
npm run greet --silent
npm run greet --silent -- Emma
node -p "require('./package.json').scripts"
```

```text output
(pregreet runs first)
Hello, friend! A week is 604800000 ms.
(pregreet runs first)
Hello, Emma! A week is 604800000 ms.
{
  test: 'echo "Error: no test specified" && exit 1',
  greet: 'node greet.mjs',
  pregreet: "echo '(pregreet runs first)'"
}
```

<Happened>
<Tr>
<En>

- `npm pkg set` edited `package.json` from the command line: two scripts and `"type": "module"` (so `.js` files would be ES modules too).
- `pregreet` ran before `greet` both times. Use pre/post scripts sparingly; explicit commands (`"build": "npm run lint && next build"`) are easier to follow.
- `-- Emma` passed `Emma` to the script as `process.argv[2]`.
- `--silent` hides npm's own banner lines. `npm test` and `npm start` work without `run`.

</En>
<Ur>

- `npm pkg set` ne command line se `package.json` badli: do scripts aur `"type": "module"` (taa ke `.js` files bhi ES modules hon).
- Dono dafa `pregreet` `greet` se pehle chala. Pre/post scripts kam istemal karein; wazeh commands (`"build": "npm run lint && next build"`) samajhne me aasan hain.
- `-- Emma` ne `Emma` ko script me `process.argv[2]` ki tarah diya.
- `--silent` npm ki apni banner lines chhupata hai. `npm test` aur `npm start` `run` ke baghair chalte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="npm ci: install exactly the lockfile">

<Tr>
<En>
On a CI server or in a Dockerfile, you want exactly what was tested. `npm ci` deletes `node_modules` and installs precisely the lockfile, and it **fails** if `package.json` and the lockfile disagree.
</En>
<Ur>
CI server ya Dockerfile me aap bilkul wahi chahte hain jo test hua. `npm ci` `node_modules` mita kar bilkul lockfile install karta hai, aur `package.json` aur lockfile me ikhtilaf ho to **fail** hota hai.
</Ur>
</Tr>

```bash
npm ls
rm -rf node_modules
npm ci --silent
npm ls ms
npm pkg set dependencies.picocolors="^1.1.0"
npm ci 2>&1 | grep -E "can only install|Missing"
npm install --silent
npm ls picocolors
```

```text output
lab@1.0.0 /home/you
├── ms@2.1.3
└── semver@7.8.6

lab@1.0.0 /home/you
└── ms@2.1.3

npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
npm error Missing: picocolors@1.1.1 from lock file
lab@1.0.0 /home/you
└── picocolors@1.1.1

```

<Happened>
<Tr>
<En>

- After deleting `node_modules`, `npm ci` restored **exactly** `ms@2.1.3` from the lockfile.
- We then added `picocolors` to `package.json` by hand, without installing. `npm ci` refused: the lockfile didn't contain it. This catches "I edited package.json but forgot to commit the lockfile" before it reaches production.
- `npm install` resolved the new range (to 1.1.1), installed it and updated the lockfile. Developers run `npm install`; machines run `npm ci`.

</En>
<Ur>

- `node_modules` mitane ke baad `npm ci` ne lockfile se **bilkul** `ms@2.1.3` wapas kiya.
- Phir humne install kiye baghair haath se `picocolors` `package.json` me joda. `npm ci` ne inkaar kiya: lockfile me wo nahi tha. Ye "package.json badli magar lockfile commit karna bhool gaya" ko production tak pohanchne se pehle pakar leta hai.
- `npm install` ne nayi range (1.1.1 tak) resolve ki, install kiya aur lockfile update ki. Developers `npm install` chalate hain; machines `npm ci`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Transitive dependencies: one line, many packages">

<Tr>
<En>
Packages depend on other packages. Installing Express, a popular web framework, shows how quickly that adds up.
</En>
<Ur>
Packages doosre packages par munhasir hote hain. Express, mashhoor web framework, install karna dikhata hai ke ye kitni jaldi barhta hai.
</Ur>
</Tr>


## Common mistakes

<Compare>
<Bad title="Committing node_modules, ignoring the lockfile">

```text
# .gitignore
package-lock.json          ✗ every install can get different versions
# and node_modules/ committed: huge repo, platform-specific binaries
```

</Bad>
<Good title="Commit the recipe and the receipt">

```text
# .gitignore
node_modules/
# committed: package.json + package-lock.json
# CI / Dockerfile:
RUN npm ci --omit=dev
```

</Good>
</Compare>

<Compare>
<Bad title="Build tools in dependencies, runtime libraries in devDependencies">

```text
"dependencies":    { "typescript": "^5.9.0", "eslint": "^9.0.0" }
"devDependencies": { "express": "^5.1.0" }       ✗ missing at runtime with --omit=dev
```

</Bad>
<Good title="Runtime needs vs development tools">

```text
"dependencies":    { "express": "^5.1.0", "zod": "^4.0.0" }
"devDependencies": { "typescript": "^5.9.0", "eslint": "^9.0.0", "vitest": "^3.0.0" }
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Deleting the lockfile to "fix" an install problem**: it silently upgrades hundreds of packages. Fix the specific conflict instead.
- **Mixing package managers** (a `package-lock.json` and a `yarn.lock` or `pnpm-lock.yaml` in one repo).
- **`sudo npm install -g`** or installing global tools you could run with `npx` or keep as devDependencies.
- **Installing a package from a tutorial without checking it**: typos (`expres`, `reqeusts`) are a known attack ("typosquatting").
- **Running `npm install` in CI** instead of `npm ci`.
- **Ignoring `npm audit` completely**, or blindly running `npm audit fix --force` (it can install breaking major versions).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Install ka masla "theek" karne ke liye lockfile mitana**: ye chupke se saikron packages upgrade kar deta hai. Is ke bajaye mukhsoos takrao theek karein.
- **Package managers milana** (ek repo me `package-lock.json` aur `yarn.lock` ya `pnpm-lock.yaml`).
- **`sudo npm install -g`** ya aise global tools install karna jo `npx` se chal sakte ya devDependencies ho sakte hain.
- **Tutorial se package check kiye baghair install karna**: typos (`expres`, `reqeusts`) maloom hamla hain ("typosquatting").
- **CI me `npm ci` ke bajaye `npm install` chalana**.
- **`npm audit` ko bilkul nazar andaz karna**, ya andha dhund `npm audit fix --force` chalana (ye torne wale major versions install kar sakta hai).

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- `package.json`: metadata, scripts and dependency **ranges**; `package-lock.json`: **exact** versions, URLs and integrity hashes. Commit both; ignore `node_modules`.
- SemVer: MAJOR (breaking) . MINOR (features) . PATCH (fixes). `^` allows minor+patch, `~` allows patch, no symbol means exact.
- `npm install` for development (updates the lockfile); **`npm ci`** for CI, Docker and servers (exact, fails if out of sync).
- `dependencies` for runtime; `devDependencies` for build, test and tooling.
- Scripts run with `node_modules/.bin` on the PATH; pass arguments after `--`.
- One dependency can bring dozens more (`npm explain`, `npm ls`); keep dependencies few and trusted, and run `npm audit`.

</En>

- `package.json`: maloomat, scripts aur dependency **ranges**; `package-lock.json`: **bilkul** versions, URLs aur integrity hashes. Dono commit karein; `node_modules` ignore karein.

<DeepDive title="More about npm and packages">

**Other package managers.** **pnpm** stores each package version once on disk and links it into projects (fast, saves space, strict about undeclared dependencies). **Yarn** and **Bun** have their own lockfiles. They all read `package.json`; pick one per project and enable it with Corepack or the `packageManager` field.

**`engines`.** `"engines": { "node": ">=22" }` documents (and with `engine-strict`, enforces) which Node versions the project supports.

**`exports` and `type`.** Libraries use `"exports"` to define their public entry points (and separate ESM/CommonJS builds); `"type": "module"` makes `.js` files ES modules.

**`overrides`.** Force a transitive dependency to a specific version, for example to apply a security fix before the parent package updates: `"overrides": { "debug": "4.4.3" }`.

**Workspaces.** `"workspaces": ["apps/*", "packages/*"]` manages several packages in one repo (a monorepo), linking them together with one lockfile.

**Publishing.** `npm publish` uploads a package; use `"files"` to whitelist what's included, 2FA on your npm account, and `npm publish --provenance` from CI to prove where it was built.

**Private registries.** Companies use GitHub Packages, Verdaccio or Artifactory, configured in `.npmrc` per scope (`@acme:registry=…`).

</DeepDive>

<DeepDive title="Real world: the package that went missing">

In March 2016, a developer unpublished his 273 packages from npm after a naming dispute. One of them was **left-pad**, 11 lines of code that pads a string with spaces. Thousands of projects depended on it indirectly, including Babel and React's tooling. Within minutes, builds around the world started failing with "404 Not Found: left-pad". npm restored the package about two hours later, an unprecedented step.

Lessons the ecosystem took from it:

1. npm changed its rules so packages that others depend on can't simply be unpublished after 72 hours.
2. Teams realised how many tiny transitive dependencies they had, and started asking "do we need this package?".
3. Companies began caching packages in private registries or proxies, so a registry problem doesn't stop their builds.
4. Lockfiles plus `npm ci` became standard practice, so builds were at least reproducible.

Later incidents had darker causes: `event-stream` (2018) received a malicious update after a new maintainer took over, targeting a cryptocurrency wallet; `ua-parser-js` and `coa` (2021) were hijacked to install password stealers; in 2025 a phishing campaign compromised maintainers of very popular packages like `chalk` and `debug` for a few hours. Each time, projects with pinned lockfiles that didn't blindly update were much less likely to be affected.

</DeepDive>

<DeepDive title="Security lens">

- **Install scripts run code on your machine**: `preinstall`/`postinstall` scripts execute during `npm install`. Use `npm ci --ignore-scripts` where possible, or pnpm/Bun which don't run dependency scripts by default unless allowed.
- **Pin and review**: commit the lockfile, review lockfile diffs, and let tools (Dependabot, Renovate) open update PRs you can test.
- **Check before installing**: popularity, maintenance, number of maintainers, and the exact spelling. Prefer the standard library (Node has `fetch`, `crypto.randomUUID`, `util.parseArgs`, `node:test`).
- **`npm audit`** reports known vulnerabilities in your tree; fix the ones that are reachable in your app first.
- **Protect your npm account** with 2FA if you publish anything, and use granular tokens in CI.
- **Never store secrets in `package.json`** or `.npmrc` committed to git; use environment variables.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between package.json and package-lock.json?">
package.json declares the project's metadata, scripts and the version ranges of its direct dependencies. package-lock.json records the exact resolved version, source URL and integrity hash of every package in the dependency tree, including transitive ones, so installs are reproducible.
</QA>

<QA q="What's the difference between npm install and npm ci?">
npm install installs according to package.json, may update the lockfile and keeps existing node_modules. npm ci deletes node_modules and installs exactly what the lockfile specifies, never modifies it, and fails if package.json and the lockfile disagree, which makes it suitable for CI and production builds.
</QA>

<QA q="Explain semantic versioning and caret vs tilde ranges.">
SemVer is MAJOR.MINOR.PATCH, where major versions may break compatibility, minor versions add backward-compatible features and patches fix bugs. Caret allows updates that don't change the left-most non-zero part, so caret 1.2.3 allows up to but not including 2.0.0. Tilde allows only patch updates, so tilde 1.2.3 allows 1.2.x.
</QA>

<QA q="What are dependencies vs devDependencies?">
dependencies are needed at runtime by the application or library. devDependencies are only needed for development tasks such as building, testing, linting and type checking, and are skipped with npm ci omit dev or when the package is installed as a dependency of another project.
</QA>

<QA q="How do you protect a Node.js project from supply-chain attacks?">
Commit and review lockfiles, install with npm ci, minimise and vet dependencies, disable or restrict install scripts, run npm audit and automated update tools, use a private registry or proxy cache, enable 2FA and provenance for publishing, and avoid typosquatted package names.
</QA>

</DeepDive>
