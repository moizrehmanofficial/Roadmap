<BigIdea>
<Tr>
<En>
A union type like `number | string` says "this could be either". Before you can use string-only or number-only features, you have to **check** which one you actually have. The good news: TypeScript **reads your checks**. After `if (typeof value === "string")`, it knows that inside the `if`, `value` is a `string`, and in the `else`, it's whatever is left. This is called **narrowing**: the type gets narrower as your code learns more. The checks that teach TypeScript something are called **type guards**: `typeof`, truthiness, `===`, `in`, `instanceof`, `Array.isArray`, and comparing a discriminant like `kind`. When those aren't enough, you can write your **own** type guard (a function returning `value is Product`). And with `never`, you can make the compiler **prove** that every case of a union has been handled, so adding a new variant shows you every place that needs updating.
</En>
<Ur>
`number | string` jaisi union type kehti hai "ye dono me se koi bhi ho sakta hai". Sirf string ya sirf number wali features istemal karne se pehle aap ko **check** karna parta hai ke asal me aap ke paas kaun sa hai. Achhi khabar: TypeScript **aap ke checks parhti hai**. `if (typeof value === "string")` ke baad wo janti hai ke `if` ke andar `value` `string` hai, aur `else` me jo bacha wo. Ise **narrowing** kehte hain: jaise jaise aap ka code zyada janta hai, type tang hoti jati hai. Jo checks TypeScript ko kuch sikhate hain unhen **type guards** kehte hain: `typeof`, truthiness, `===`, `in`, `instanceof`, `Array.isArray`, aur `kind` jaise discriminant ka muqabla. Jab ye kafi na hon, aap **apna** type guard likh sakte hain (aisa function jo `value is Product` wapas kare). Aur `never` ke saath aap compiler se **sabit karwa** sakte hain ke union ki har surat sambhali gayi, taa ke naya variant jorna aap ko har wo jagah dikhaye jise update karna hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

| Guard | Checks | Narrows |
| --- | --- | --- |
| `typeof x === "string"` | primitive kind | `string`, `number`, `boolean`, `bigint`, `symbol`, `undefined`, `function`, `object` |
| `if (x)` | truthiness | removes `null`, `undefined` (and `""`, `0`, `false`) |
| `x === null`, `x !== undefined` | equality | removes or keeps exact values |
| `"fly" in x` | property exists | object types that have that property |
| `x instanceof Error` | class / constructor | that class |
| `Array.isArray(x)` | array | the array member |
| `x.kind === "card"` | discriminant | one variant of a discriminated union |
| `isProduct(x)` with `x is Product` | your own logic | whatever you declare |
| `assertIsString(x)` with `asserts x is string` | throws if wrong | the rest of the scope |

</En>
<Ur>

| Guard | Kya check karta hai | Kya tang karta hai |
| --- | --- | --- |
| `typeof x === "string"` | primitive ki qism | `string`, `number`, `boolean`, `bigint`, `symbol`, `undefined`, `function`, `object` |
| `if (x)` | truthiness | `null`, `undefined` (aur `""`, `0`, `false`) hata deta hai |
| `x === null`, `x !== undefined` | barabri | bilkul theek values hatata ya rakhta hai |
| `"fly" in x` | property maujood hai | wo object types jin ke paas wo property ho |

</What>
<Why>
<Tr>
<En>

- **Unions are only useful if you can safely get the specific type back out.**
- **No extra syntax**: ordinary JavaScript checks you'd write anyway become type information.
- **External data starts as `unknown`**: narrowing is how you safely turn it into real types.
- **Exhaustiveness checks** turn "we forgot to handle the new status" from a production bug into a compile error.

</En>
<Ur>

- **Unions tabhi kaam ki hain jab aap mehfooz tareeqe se khaas type wapas nikal sakein.**
- **Koi izafi syntax nahi**: aam JavaScript checks jo aap waise bhi likhte, type ki maloomat ban jate hain.
- **Bahar ka data `unknown` se shuru hota hai**: narrowing hi use mehfooz tareeqe se asli types me badalne ka tareeqa hai.
- **Exhaustiveness checks** "hum naya status sambhalna bhool gaye" ko production bug ke bajaye compile error bana dete hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| You have | Narrow with |
| --- | --- |
| `number \| string` | `typeof` |
| `T \| null \| undefined` | `!== null`, `!= null`, or truthiness (careful with `0` and `""`) |
| objects with different properties | `"prop" in x` |
| class instances, errors | `instanceof` |
| `T \| T[]` | `Array.isArray` |
| discriminated union | `switch (x.kind)` + `never` default |
| `unknown` from JSON / APIs | a custom type guard (or a validation library like zod) |
| "this must be true or the program can't continue" | an assertion function |

</En>
<Ur>

| Aap ke paas hai | Is se narrow karein |
| --- | --- |
| `number \| string` | `typeof` |
| `T \| null \| undefined` | `!== null`, `!= null`, ya truthiness (`0` aur `""` se hoshiyar) |
| mukhtalif properties wale objects | `"prop" in x` |
| class instances, errors | `instanceof` |
| `T \| T[]` | `Array.isArray` |
| discriminated union | `switch (x.kind)` + `never` default |
| JSON / APIs se `unknown` | apna type guard (ya zod jaisi validation library) |
| "ye sach hona chahiye warna program aage nahi chal sakta" | assertion function |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Write a normal JavaScript check: `if (typeof value === "string") { … }`.
2. Inside the block, use the narrowed type freely; after an early `return`, the rest of the function has the remaining types.
3. For complex shapes, write `function isX(v: unknown): v is X { … }`.
4. In `switch` statements over a union, add `default: return assertNever(x)`.

</En>
<Ur>

1. Aam JavaScript check likhein: `if (typeof value === "string") { … }`.
2. Block ke andar tang type azadi se istemal karein; jaldi `return` ke baad function ke baqi hisse me bachi hui types hoti hain.
3. Pecheeda shakalon ke liye `function isX(v: unknown): v is X { … }` likhein.
4. Union par `switch` statements me `default: return assertNever(x)` jorein.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Picture a **mail room** that receives **sealed boxes** labelled "might be a letter, a parcel or a book".

- You can't do much with a sealed box: you can't read it (it might be a parcel) and you can't unwrap it (it might be a letter). That's a **union**: you may only do what's safe for everything it could be.
- The clerk runs each box through a **sorting machine** with gates: "Is it flat and light?" → the **letters** chute. "Does it have a barcode starting with BK?" → the **books** chute. Everything else → **parcels**. Each gate is a **type guard**.
- Once a box goes down the letters chute, everyone downstream **knows** it's a letter and can open it like one. That's **narrowing**.
- The last chute is labelled "**should be empty**". If anything ever lands there, a new kind of mail exists that no gate handles, and an alarm goes off. That's the `never` **exhaustiveness check**.

</En>
<Ur>

Ek **mail room** ka tasavvur karein jahan **band dabbe** aate hain jin par likha hai "khat, parcel ya kitaab ho sakta hai".

- Band dabbe ke saath zyada kuch nahi kar sakte: aap use parh nahi sakte (shayad parcel ho) aur khol nahi sakte (shayad khat ho). Ye **union** hai: aap sirf wo kar sakte hain jo har mumkina cheez ke liye mehfooz ho.
- Clerk har dabba darwazon wali **sorting machine** se guzarta hai: "Kya ye chapta aur halka hai?" → **khaton** ka chute. "Kya is ka barcode BK se shuru hota hai?" → **kitabon** ka chute. Baqi sab → **parcels**. Har darwaza ek **type guard** hai.
- Jab dabba khaton wale chute se neeche jata hai, aage sab **jante** hain ke ye khat hai aur use khat ki tarah khol sakte hain. Ye **narrowing** hai.
- Aakhri chute par likha hai "**khaali hona chahiye**". Agar kabhi kuch wahan gire to dak ki aisi nayi qism maujood hai jise koi darwaza nahi sambhalta, aur alarm baj jata hai. Ye `never` wala **exhaustiveness check** hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="typeof: the first type guard">

<Tr>
<En>
`typeof` is plain JavaScript. TypeScript watches it and narrows the variable in each branch. After a `return`, the rest of the function only sees the types that are left.
</En>
<Ur>
`typeof` saada JavaScript hai. TypeScript use dekhti hai aur har shaakh me variable ko tang karti hai. `return` ke baad function ka baqi hissa sirf bachi hui types dekhta hai.
</Ur>
</Tr>

```typescript
function format(value: number | string | Date): string {
  if (typeof value === "number") {
    return "$" + value.toFixed(2);
  }
  if (typeof value === "string") {
    return value.trim().toUpperCase();
  }
  return value.toISOString().slice(0, 10);
}

console.log(format(4.5));
console.log(format("  mug  "));
console.log(format(new Date(Date.UTC(2026, 10, 12))));
```

```text output
$4.50
MUG
2026-11-12
```

<Happened>
<Tr>
<En>

- In the first `if`, `value` is a `number`, so `toFixed` is allowed.
- After that `if` returns, TypeScript removes `number`: what's left is `string | Date`.
- The second `if` handles `string`, so the last line only sees `Date`, and `toISOString` is allowed **without any check**.
- This is **control flow analysis**: TypeScript follows every `if`, `return` and `throw` like a reader would.

</En>
<Ur>

- Pehle `if` me `value` `number` hai, isliye `toFixed` ki ijazat hai.
- Wo `if` return kar de to TypeScript `number` hata deti hai: bacha `string | Date`.
- Doosra `if` `string` sambhalta hai, isliye aakhri line sirf `Date` dekhti hai, aur `toISOString` **baghair kisi check ke** jaiz hai.
- Ye **control flow analysis** hai: TypeScript har `if`, `return` aur `throw` ke peeche bilkul ek parhne wale ki tarah chalti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Seeing the narrowed type">

<Tr>
<En>
In VS Code you can **hover** a variable to see its type at that exact line. Without an editor, a quick trick is to assign it to a variable of a type you **think** it has: tsc complains if you're wrong.
</En>
<Ur>
VS Code me aap variable par **hover** kar ke usi line par us ki type dekh sakte hain. Editor ke baghair ek fori tareeqa ye hai ke use aisi type ke variable ko dein jo aap **samajhte** hain ke us ki hai: ghalat hon to tsc shikayat karta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function format(value: number | string | Date) {
  if (typeof value === "number") {
    const a: number = value;
  } else if (typeof value === "string") {
    const b: string = value;
  } else {
    const c: Date = value;
    const d: string = value;
  }
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(8,11): error TS2322: Type 'Date' is not assignable to type 'string'.
```

<Happened>
<Tr>
<En>

- Lines 3, 5 and 7 passed, so the types are exactly what we expected in each branch.
- Line 8 failed and the message **names** the narrowed type: in the `else`, `value` is a `Date`.
- Hovering in the editor is the everyday way. This trick is handy when reading code in a terminal or a code review.

</En>
<Ur>

- Lines 3, 5 aur 7 paas hui, yani har shaakh me types bilkul wahi hain jo humne socha.
- Line 8 fail hui aur paighaam tang type ka **naam** leta hai: `else` me `value` `Date` hai.
- Editor me hover karna rozmarra ka tareeqa hai. Ye tarkeeb terminal me ya code review me code parhte waqt kaam aati hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Truthiness and equality narrowing">

<Tr>
<En>
`if (name)` removes `null` and `undefined`, but it also treats `""`, `0` and `false` as "missing". When `0` or an empty string is a real value, compare with `null` explicitly.
</En>
<Ur>
`if (name)` `null` aur `undefined` hata deta hai, magar ye `""`, `0` aur `false` ko bhi "ghayab" samajhta hai. Jab `0` ya khaali string asli value ho, `null` se saaf muqabla karein.
</Ur>
</Tr>

```typescript
function greet(name: string | null | undefined): string {
  if (!name) {
    return "Hello, guest";
  }
  return "Hello, " + name.toUpperCase();
}
console.log(greet("sara"));
console.log(greet(null));
console.log(greet(""));

function discountLabel(percent: number | null): string {
  if (percent === null) return "no discount";
  return percent + "% off";
}
function discountLabelBuggy(percent: number | null): string {
  if (!percent) return "no discount";
  return percent + "% off";
}
console.log(discountLabel(0), "|", discountLabel(null));
console.log(discountLabelBuggy(0), "| buggy: 0% was a real value");
```

```text output
Hello, SARA
Hello, guest
Hello, guest
0% off | no discount
no discount | buggy: 0% was a real value
```

<Happened>
<Tr>
<En>

- In `greet`, treating an empty name like a missing one is what we want, so `!name` is fine. After the early `return`, `name` is a `string`.
- In `discountLabelBuggy`, `!percent` also catches `0`. TypeScript is happy (both versions compile), but the **behaviour** is wrong: a 0% discount isn't "no discount".
- `percent === null` removes exactly `null`. Use `x != null` (two `=`) to remove both `null` and `undefined` in one check.

</En>
<Ur>

- `greet` me khaali naam ko ghayab naam ki tarah samajhna wahi hai jo hum chahte hain, isliye `!name` theek hai. Jaldi `return` ke baad `name` `string` hai.
- `discountLabelBuggy` me `!percent` `0` ko bhi pakar leta hai. TypeScript khush hai (dono versions compile hote hain), magar **bartao** ghalat hai: 0% discount "koi discount nahi" nahi.
- `percent === null` bilkul `null` hatata hai. Ek hi check me `null` aur `undefined` dono hatane ke liye `x != null` (do `=`) lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The typeof null trap">

<Tr>
<En>
In JavaScript, `typeof null` is `"object"`, a famous historical bug. TypeScript knows this, so `typeof value === "object"` does **not** remove `null`.
</En>
<Ur>
JavaScript me `typeof null` `"object"` hai, ek mashhoor tareekhi bug. TypeScript ye janti hai, isliye `typeof value === "object"` `null` **nahi** hatata.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Settings = { theme: string };

function themeOf(value: Settings | string | null): string {
  if (typeof value === "object") {
    return value.theme;
  }
  return value;
}

function themeFixed(value: Settings | string | null): string {
  if (value === null) return "light";
  if (typeof value === "object") return value.theme;
  return value;
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,12): error TS18047: 'value' is possibly 'null'.
```

<Happened>
<Tr>
<En>

- Inside the first `if`, `value` is `Settings | null`, so `value.theme` could crash. TypeScript caught a real bug.
- `themeFixed` handles `null` first, then `typeof … === "object"` leaves only `Settings`.
- Arrays are `"object"` too. Use `Array.isArray` for them.

</En>
<Ur>

- Pehle `if` ke andar `value` `Settings | null` hai, isliye `value.theme` crash kar sakta hai. TypeScript ne asli bug pakra.
- `themeFixed` pehle `null` sambhalta hai, phir `typeof … === "object"` sirf `Settings` chhorta hai.
- Arrays bhi `"object"` hain. Un ke liye `Array.isArray` lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="in, instanceof and Array.isArray">

<Tr>
<En>
For objects, `typeof` isn't enough. Use `"prop" in x` to tell shapes apart by a property, `instanceof` for class instances like errors, and `Array.isArray` for "one or many" inputs.
</En>
<Ur>
Objects ke liye `typeof` kafi nahi. Shakalon ko property se alag karne ke liye `"prop" in x`, errors jaise class instances ke liye `instanceof`, aur "ek ya kai" inputs ke liye `Array.isArray` lein.
</Ur>
</Tr>

```typescript
type Dog = { name: string; bark: () => string };
type Bird = { name: string; fly: () => string };

function move(animal: Dog | Bird): string {
  if ("fly" in animal) {
    return animal.name + " " + animal.fly();
  }
  return animal.name + " " + animal.bark();
}
console.log(move({ name: "Rex", bark: () => "barks" }));
console.log(move({ name: "Tweety", fly: () => "flies away" }));

function toList(input: string | string[]): string[] {
  if (Array.isArray(input)) return input;
  return [input];
}
console.log(toList("mug"), toList(["pen", "lamp"]));

class NotFoundError extends Error {
  status = 404;
}
function handle(err: unknown): string {
  if (err instanceof NotFoundError) return "404: " + err.message;
  if (err instanceof Error) return "500: " + err.message;
  return "unknown error: " + String(err);
}
console.log(handle(new NotFoundError("No such order")));
console.log(handle(new TypeError("x is undefined")));
console.log(handle("boom"));
```

```text output
Rex barks
Tweety flies away
[ 'mug' ] [ 'pen', 'lamp' ]
404: No such order
500: x is undefined
unknown error: boom
```

<Happened>
<Tr>
<En>

- `"fly" in animal` narrowed to `Bird` in the `if`, and to `Dog` after it. `name` was usable everywhere because both have it.
- `Array.isArray` turned `string | string[]` into `string[]` (and `string` afterwards), a common pattern for functions that accept one item or a list.
- In a `catch` block the error is `unknown` (anything can be thrown). `instanceof` checks are the safe way in: **most specific class first**, because a `NotFoundError` is also an `Error`.
- `instanceof` only works with classes (things made with `new`). Plain objects from JSON aren't instances of anything, so use `in`, a discriminant or a custom guard for them.

</En>
<Ur>

- `"fly" in animal` ne `if` me `Bird` aur us ke baad `Dog` tak tang kiya. `name` har jagah istemal ho saka kyun ke dono ke paas hai.
- `Array.isArray` ne `string | string[]` ko `string[]` (aur baad me `string`) bana diya, ek item ya list qubool karne wale functions ka aam pattern.
- `catch` block me error `unknown` hota hai (kuch bhi throw ho sakta hai). `instanceof` checks andar jaane ka mehfooz raasta hain: **sab se khaas class pehle**, kyun ke `NotFoundError` bhi `Error` hai.
- `instanceof` sirf classes ke saath chalta hai (jo `new` se bani hon). JSON ke saade objects kisi ke instance nahi, isliye un ke liye `in`, discriminant ya apna guard lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Your own type guard: value is Product">

<Tr>
<En>
When a check is too complex for one expression, put it in a function whose return type is a **type predicate**: `value is Product`. When the function returns `true`, TypeScript narrows the argument to `Product`.
</En>
<Ur>
Jab check ek expression ke liye bohot pecheeda ho, use aise function me rakhein jis ki return type **type predicate** ho: `value is Product`. Jab function `true` wapas kare, TypeScript argument ko `Product` tak tang kar deti hai.
</Ur>
</Tr>

```typescript
type Product = { name: string; price: number };

function isProduct(value: unknown): value is Product {
  return (
    typeof value === "object" &&
    value !== null &&
    "name" in value &&
    typeof value.name === "string" &&
    "price" in value &&
    typeof value.price === "number"
  );
}

const fromApi: unknown = JSON.parse('[{"name":"Mug","price":12},{"name":"Pen"},"oops"]');

if (Array.isArray(fromApi)) {
  for (const item of fromApi) {
    if (isProduct(item)) {
      console.log("ok:", item.name, "$" + item.price);
    } else {
      console.log("skipped:", JSON.stringify(item));
    }
  }
}

const items: (Product | null)[] = [{ name: "Lamp", price: 30 }, null, { name: "Cup", price: 6 }];
const real = items.filter((p): p is Product => p !== null);
console.log(real.map((p) => p.name).join(", "));
```

```text output
ok: Mug $12
skipped: {"name":"Pen"}
skipped: "oops"
Lamp, Cup
```

<Happened>
<Tr>
<En>

- `JSON.parse` data is typed `unknown` here on purpose: we don't trust it. `isProduct` checks every field at runtime, and its `value is Product` return type tells TypeScript what a `true` result means.
- `{"name":"Pen"}` had no price and `"oops"` wasn't an object; both were skipped instead of crashing later.
- Inside `isProduct`, notice the guards build on each other: after `"name" in value`, TypeScript allows `value.name`.
- `filter` with a type predicate turns `(Product | null)[]` into `Product[]`. (TypeScript 5.5+ can often infer this predicate from `p !== null` by itself.)
- **Warning**: TypeScript trusts your predicate. If `isProduct` checked only `name`, it would still claim `Product`. Keep guards honest, or use a validation library (zod lesson).

</En>
<Ur>

- `JSON.parse` ka data yahan jaan boojh kar `unknown` hai: humen us par bharosa nahi. `isProduct` runtime par har field check karta hai, aur us ki `value is Product` return type TypeScript ko batati hai ke `true` nateeje ka matlab kya hai.
- `{"name":"Pen"}` ki price nahi thi aur `"oops"` object nahi tha; dono baad me crash karne ke bajaye chhor diye gaye.
- `isProduct` ke andar dekhein ke guards ek doosre par khare hote hain: `"name" in value` ke baad TypeScript `value.name` ki ijazat deti hai.
- Type predicate ke saath `filter` `(Product | null)[]` ko `Product[]` bana deta hai. (TypeScript 5.5+ aksar `p !== null` se ye predicate khud nikal leti hai.)
- **Khabardar**: TypeScript aap ke predicate par bharosa karti hai. Agar `isProduct` sirf `name` check karta, tab bhi `Product` ka daawa karta. Guards imaandar rakhein, ya validation library lein (zod lesson).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Assertion functions: throw or narrow">

<Tr>
<En>
Sometimes there's no sensible "else": if a config value is missing, the app can't start. An **assertion function** throws when the check fails and, with `asserts value is string`, narrows the variable for **all the code after the call**.
</En>
<Ur>
Kabhi koi maqool "else" nahi hota: agar config ki value ghayab ho to app shuru nahi ho sakti. **Assertion function** check fail hone par throw karta hai aur `asserts value is string` ke saath call ke **baad ke tamam code** ke liye variable tang kar deta hai.
</Ur>
</Tr>

```typescript
function assertIsString(value: unknown, name: string): asserts value is string {
  if (typeof value !== "string") {
    throw new TypeError(name + " must be a string, got " + typeof value);
  }
}

function readEnv(env: Record<string, unknown>): string {
  const url = env.DATABASE_URL;
  assertIsString(url, "DATABASE_URL");
  return url.toLowerCase();
}

console.log(readEnv({ DATABASE_URL: "POSTGRES://DB.EXAMPLE.COM/SHOP" }));
try {
  readEnv({ DATABASE_URL: 5432 });
} catch (e) {
  console.log((e as Error).message);
}
```

```text output
postgres://db.example.com/shop
DATABASE_URL must be a string, got number
```

<Happened>
<Tr>
<En>

- Before `assertIsString`, `url` is `unknown`. After it, TypeScript treats `url` as `string`, with no `if` needed.
- With a bad value, the function throws a **clear** error at startup instead of a confusing crash somewhere deep inside the app.
- Node's `assert` from `node:assert` is typed the same way: `assert(user)` narrows away `null` and `undefined`.

</En>
<Ur>

- `assertIsString` se pehle `url` `unknown` hai. Us ke baad TypeScript `url` ko `string` samajhti hai, kisi `if` ki zaroorat nahi.
- Buri value par function startup par hi **saaf** error throw karta hai, app ke andar kahin gehrai me ulajhane wale crash ke bajaye.
- `node:assert` ka Node `assert` bhi isi tarah typed hai: `assert(user)` `null` aur `undefined` hata deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Exhaustiveness: make the compiler prove every case">

<Tr>
<En>
After every case of a union has been handled, the remaining type is `never` (nothing is left). A helper that **only accepts `never`** turns "I forgot a case" into a compile error.
</En>
<Ur>
Jab union ki har surat sambhal li jaye, bachi hui type `never` hoti hai (kuch nahi bacha). Aisa helper jo **sirf `never` qubool kare** "main ek surat bhool gaya" ko compile error bana deta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; size: number }
  | { kind: "triangle"; base: number; height: number };

function assertNever(value: never): never {
  throw new Error("Unhandled case: " + JSON.stringify(value));
}

function area(s: Shape): number {
  switch (s.kind) {
    case "circle":
      return Math.PI * s.radius ** 2;
    case "square":
      return s.size ** 2;
    default:
      return assertNever(s);
  }
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(17,26): error TS2345: Argument of type '{ kind: "triangle"; base: number; height: number; }' is not assignable to parameter of type 'never'.
```

<Happened>
<Tr>
<En>

- `circle` and `square` were handled, so in `default`, `s` is still the **triangle**. Passing it where `never` is required is an error, and the message tells you exactly **which** variant is missing.
- Add `case "triangle": return (s.base * s.height) / 2;` and the error disappears: now `s` really is `never` in `default`.
- This is clearer than relying on "missing return" errors, and it also works in `switch` statements that don't return anything.

</En>
<Ur>

- `circle` aur `square` sambhale gaye, isliye `default` me `s` ab bhi **triangle** hai. Use wahan dena jahan `never` chahiye error hai, aur paighaam bilkul batata hai ke **kaun sa** variant ghayab hai.
- `case "triangle": return (s.base * s.height) / 2;` jorein aur error ghayab: ab `default` me `s` sach me `never` hai.
- Ye "missing return" errors par bharosa karne se zyada wazeh hai, aur aise `switch` statements me bhi chalta hai jo kuch wapas nahi karte.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The complete, exhaustive version">

<Tr>
<En>
With every case handled, the program compiles and runs. The `assertNever` call also protects you at **runtime**, if bad data sneaks past the types.
</En>
<Ur>
Har surat sambhalne ke baad program compile hota aur chalta hai. `assertNever` call **runtime** par bhi bachata hai, agar bura data types se chhup kar guzar jaye.
</Ur>
</Tr>

```typescript
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; size: number }
  | { kind: "triangle"; base: number; height: number };

function assertNever(value: never): never {
  throw new Error("Unhandled case: " + JSON.stringify(value));
}

function area(s: Shape): number {
  switch (s.kind) {
    case "circle":
      return Math.PI * s.radius ** 2;
    case "square":
      return s.size ** 2;
    case "triangle":
      return (s.base * s.height) / 2;
    default:
      return assertNever(s);
  }
}

const shapes: Shape[] = [
  { kind: "circle", radius: 1 },
  { kind: "square", size: 3 },
  { kind: "triangle", base: 4, height: 5 },
];
for (const s of shapes) console.log(s.kind, area(s).toFixed(2));

try {
  area({ kind: "hexagon", side: 2 } as any);
} catch (e) {
  console.log((e as Error).message);
}
```

```text output
circle 3.14
square 9.00
triangle 10.00
Unhandled case: {"kind":"hexagon","side":2}
```

<Happened>
<Tr>
<En>

- All three shapes work.
- The `as any` line simulates data that lied about its type (for example, an API added a new shape). Instead of silently returning `undefined`, the code fails loudly with a message that names the unknown case.
- `as any` switches type checking off; it's used here only to simulate bad data. Avoid it in real code.

</En>
<Ur>

- Teeno shakalen chalti hain.
- `as any` wali line aise data ki naqal hai jis ne apni type ke baare me jhoot bola (maslan API ne nayi shakal jor di). Khamoshi se `undefined` wapas karne ke bajaye code zor se fail hota hai, aise paighaam ke saath jo anjaan surat ka naam leta hai.
- `as any` type checking band kar deta hai; yahan sirf bure data ki naqal ke liye istemal hua. Asli code me is se bachein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Where narrowing gets lost">

<Tr>
<En>
Narrowing is about **one variable at one point in the code**. A narrowed **property** (`user.nickname`) doesn't stay narrowed inside a callback, because TypeScript can't be sure the object wasn't changed before the callback runs. Copy it into a `const` first.
</En>
<Ur>
Narrowing **code ke ek muqam par ek variable** ke baare me hai. Tang ki hui **property** (`user.nickname`) callback ke andar tang nahi rehti, kyun ke TypeScript yaqeen nahi kar sakti ke callback chalne se pehle object badla nahi gaya. Pehle use `const` me copy karein.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type User = { name: string; nickname?: string };

function labels(user: User, tags: string[]) {
  if (user.nickname) {
    const direct = user.nickname.toUpperCase();
    return tags.map((t) => t + ":" + user.nickname.toUpperCase());
  }
  return [];
}

function labelsFixed(user: User, tags: string[]) {
  const nickname = user.nickname;
  if (nickname) {
    return tags.map((t) => t + ":" + nickname.toUpperCase());
  }
  return [];
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(6,38): error TS18048: 'user.nickname' is possibly 'undefined'.
```

<Happened>
<Tr>
<En>

- Line 5 (directly inside the `if`) is fine: the narrowing holds there.
- Line 6 is inside an arrow function. That callback could, in theory, run later, after someone set `user.nickname = undefined`, so TypeScript forgets the check.
- `labelsFixed` copies the value into a `const`. A `const` can never change, so its narrowing survives into the callback.
- Narrowing also resets after you assign a new value to the variable.

</En>
<Ur>

- Line 5 (seedha `if` ke andar) theek hai: narrowing wahan qaim hai.
- Line 6 arrow function ke andar hai. Wo callback nazariyati taur par baad me chal sakta hai, jab kisi ne `user.nickname = undefined` kar diya ho, isliye TypeScript check bhool jati hai.
- `labelsFixed` value ko `const` me copy karta hai. `const` kabhi nahi badalta, isliye us ki narrowing callback tak bachi rehti hai.
- Variable ko nayi value dene ke baad bhi narrowing reset ho jati hai.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Silencing the checker with as">

```text
function total(value: unknown) {
  const order = value as { items: { price: number }[] };
  return order.items.reduce((sum, i) => sum + i.price, 0);
}
// compiles, then crashes at runtime when value is null or has no items
```

</Bad>
<Good title="Narrow with a real check">

```text
function total(value: unknown) {
  if (!isOrder(value)) throw new TypeError("Invalid order");
  return value.items.reduce((sum, i) => sum + i.price, 0);
}
// isOrder is a type guard that checks the shape at runtime
```

</Good>
</Compare>

<Compare>
<Bad title="A type guard that lies">

```typescript
type Product = { name: string; price: number };
function isProduct(value: any): value is Product {
  return typeof value.name === "string";
}
const data: unknown = { name: "Pen" };
if (isProduct(data)) console.log((data.price * 2).toFixed(2));
```

```text output
NaN
```

</Bad>
<Good title="Check every field you claim">

```typescript
type Product = { name: string; price: number };
function isProduct(value: any): value is Product {
  return typeof value?.name === "string" && typeof value?.price === "number";
}
const data: unknown = { name: "Pen" };
if (isProduct(data)) console.log((data.price * 2).toFixed(2));
else console.log("not a valid product");
```

```text output
not a valid product
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Using `if (x)` when `0` or `""` are valid values.** Compare with `null` / `undefined` instead.
- **Forgetting `typeof null === "object"`.** Check `null` first.
- **Ordering `instanceof` checks from general to specific.** `Error` before `NotFoundError` means the specific branch never runs.
- **Using `instanceof` on plain JSON objects.** They're never class instances.
- **Leaving `switch` statements without an exhaustive `default`**, so new variants slip through silently.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Jab `0` ya `""` jaiz values hon tab `if (x)` istemal karna.** Is ke bajaye `null` / `undefined` se muqabla karein.
- **`typeof null === "object"` bhool jana.** Pehle `null` check karein.
- **`instanceof` checks aam se khaas ki tarteeb me rakhna.** `NotFoundError` se pehle `Error` ka matlab khaas shaakh kabhi nahi chalti.
- **Saade JSON objects par `instanceof` lagana.** Wo kabhi class instances nahi hote.
- **`switch` statements ko exhaustive `default` ke baghair chhorna**, taa ke naye variants khamoshi se nikal jayen.

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- **Narrowing**: TypeScript follows your `if`, `return`, `throw` and `switch` and refines union types.
- Built-in guards: `typeof`, truthiness, `===` / `!=` with `null`, `in`, `instanceof`, `Array.isArray`, discriminant checks.

- Assertion functions (`asserts v is T`) throw or narrow for the rest of the scope.
- Exhaustiveness: `default: return assertNever(x)` makes forgotten cases compile errors and fails loudly at runtime.
- Narrowed properties are lost inside callbacks; copy them into a `const`.

<DeepDive title="More about narrowing">

**`satisfies` vs annotations vs narrowing.** `const config = { … } satisfies Config` checks a value against a type but keeps its narrower inferred type, so later code can rely on the exact literals. It's a cousin of narrowing that happens at declaration.

**Narrowing with `switch (true)`.** Since TypeScript 5.3, `switch (true) { case typeof x === "string": … }` narrows in each case, which reads nicely for long chains of conditions.

**Discriminants other than strings.** Booleans and numbers work too: `{ ok: true; data: T } | { ok: false; error: string }` is a popular result type, narrowed with `if (result.ok)`.

**Optional chaining and narrowing.** `if (user?.address?.city)` narrows `user` and `address` to non-null inside the block.

**Function calls don't reset narrowing.** TypeScript assumes a function call doesn't change your local variables. That's usually right but can be wrong if a function mutates shared state (a known, deliberate trade-off for usability).

**`unknown` vs `any`.** Narrowing works on both, but `any` lets you skip it entirely. Prefer `unknown` for values you haven't checked yet: the compiler then forces the narrowing.

**Inferred type predicates (5.5+).** Arrow functions like `(x) => x !== undefined` are inferred as predicates, so `array.filter((x) => x !== undefined)` returns a properly narrowed array without writing `x is T`.

</DeepDive>

<DeepDive title="Real world: the refund status nobody handled">

A payments dashboard showed an icon for each transaction status: `"pending" | "paid" | "failed"`. The icon function used `if`/`else if` chains and ended with `else return "✓"`, so anything unknown looked **paid**.

The payment provider later added `"refunded"`. The backend type was updated, everything compiled, and refunded payments appeared with a green tick. Accountants reconciled the month against the dashboard and the numbers were off by thousands of dollars before anyone noticed.

The fix:

1. Every status `switch` got `default: return assertNever(status)`. Updating the type now produced compile errors listing every component that had to decide what "refunded" looks like.
2. The API response was validated at runtime (zod), so an unexpected status from the provider triggered an alert instead of a wrong icon.
3. A team rule: **no catch-all `else` for unions**; handle each member explicitly.

</DeepDive>

<DeepDive title="Security lens">

- **Authorization should narrow, not assume.** Model the user as `{ kind: "guest" } | { kind: "member"; id: string } | { kind: "admin"; id: string }` and check `kind` before any privileged action; a forgotten case becomes a compile error, not a privilege bug.
- **Never trust `as` on request data.** `req.body as Order` is a promise you can't keep; narrow with a real validator.
- **Type guards must check everything they claim.** A guard that claims `Admin` after only checking `role` exists is an authorization bypass waiting to happen.
- **Default-deny in exhaustive switches**: if `assertNever` throws at runtime because of unexpected data, treat it as "access denied", never "allowed".

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is narrowing in TypeScript?">
It is the process of refining a variable's type to a more specific one based on control flow, such as typeof checks, equality checks, in, instanceof, discriminant comparisons and early returns, so that type-specific operations become allowed.
</QA>

<QA q="What is a user-defined type guard?">
A function whose return type is a type predicate such as value is Product. When it returns true, TypeScript narrows the argument to that type. TypeScript trusts the predicate, so the runtime check must be correct.
</QA>

<QA q="How do you make sure a switch handles every member of a union?">
Add a default branch that passes the value to a function accepting never. If any member is not handled, the leftover type is not never and the call fails to compile. At runtime the function can throw for unexpected values.
</QA>

<QA q="What is the difference between a type guard and an assertion function?">
A type guard returns a boolean and narrows inside the branch where it is true. An assertion function returns nothing and throws if the condition fails, narrowing the variable for all code after the call.
</QA>

<QA q="Why can narrowing on an object property be lost inside a callback?">
The callback may run later, after the property could have been changed, so TypeScript does not carry the narrowing into it. Copying the property into a const variable preserves the narrowing.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Narrowing">Refining a type to a more specific one based on checks.</Term>
  <Term name="Type guard">An expression TypeScript uses to narrow a type.</Term>
  <Term name="Control flow analysis">TypeScript tracking types through branches, returns and throws.</Term>
  <Term name="Truthiness narrowing">Using a truthy check to remove null and undefined.</Term>
  <Term name="in narrowing">Using the in operator to distinguish object types by a property.</Term>
  <Term name="instanceof narrowing">Using instanceof to narrow to a class type.</Term>
  <Term name="Type predicate">A return type of the form x is T.</Term>
  <Term name="User-defined type guard">A function with a type predicate return type.</Term>
  <Term name="Assertion function">A function declared with asserts that throws or narrows.</Term>
  <Term name="Exhaustiveness check">Using never to ensure every union member is handled.</Term>

<DeepDive title="More practice">

1. Write `isNonEmptyString(v: unknown): v is string` and use it to filter a mixed array.
2. Write `assertDefined<T>(v: T | null | undefined): asserts v is T` and use it on a `find` result.
3. Convert a long `if`/`else if` chain over a status union into a `switch` with `assertNever`.
4. Write `describe(x: unknown)` that prints "number", "string", "array of N", "null", "object with keys …" using guards.
