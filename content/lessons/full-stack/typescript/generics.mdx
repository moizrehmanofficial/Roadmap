<BigIdea>
<Tr>
<En>
Some code does the **same job for any type**: "give me the first item of a list" works for a list of numbers, of strings or of users. Writing one version per type is repetitive, and using `any` throws the types away. **Generics** solve this. You add a **type parameter**, usually written `<T>`, which is a **placeholder for a type**, just like a normal parameter is a placeholder for a value. `function first<T>(list: T[]): T` means "whatever type of list you give me, I give back one item of **that same type**". When you call it, TypeScript **fills in** `T` for you from the argument. Generics also work for types (`type ApiResponse<T> = { data: T }`), and you already use them: `Array<string>`, `Promise<User>`, `useState<number>()`. You can limit what `T` may be with `extends`.
</En>
<Ur>
Kuch code **har type ke liye ek hi kaam** karta hai: "list ka pehla item do" numbers ki list, strings ki list ya users ki list sab ke liye chalta hai. Har type ka alag version likhna dohrana hai, aur `any` istemal karne se types zaya ho jati hain. **Generics** ye masla hal karte hain. Aap ek **type parameter** jorte hain, aam taur par `<T>` likha jata hai, jo **type ke liye placeholder** hai, bilkul jaise aam parameter value ka placeholder hota hai. `function first<T>(list: T[]): T` ka matlab hai "aap mujhe jis type ki list denge, main **usi type** ka ek item wapas dunga". Call karte waqt TypeScript argument se `T` aap ke liye khud **bhar** deta hai. Generics types ke liye bhi chalte hain (`type ApiResponse<T> = { data: T }`), aur aap inhe pehle se istemal kar rahe hain: `Array<string>`, `Promise<User>`, `useState<number>()`. `T` kya ho sakta hai ye `extends` se mehdood kiya ja sakta hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

A type parameter goes in angle brackets `< >` after the function name:

```ts
function first<T>(list: T[]): T | undefined {
  return list[0];
}

first([10, 20]);        // T is number  → number | undefined
first(["a", "b"]);      // T is string  → string | undefined
```

Read `first<T>(list: T[]): T` as **"first works for some type T: it takes a list of T and gives back a T"**.

</En>
<Ur>

Type parameter function ke naam ke baad angle brackets `< >` me jata hai:

```ts
function first<T>(list: T[]): T | undefined {
  return list[0];
}

first([10, 20]);        // T number hai  → number | undefined
first(["a", "b"]);      // T string hai  → string | undefined
```

`first<T>(list: T[]): T` ko aise parhein: **"first kisi type T ke liye kaam karta hai: T ki list leta hai aur ek T wapas deta hai"**.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **One function, every type.** No `firstNumber`, `firstString`, `firstUser`.
- **No lost information.** Unlike `any`, the result keeps its exact type, so autocomplete and error checking keep working.
- **Reusable data shapes.** `ApiResponse<User>` and `ApiResponse<Order>` share one definition.
- **Reading real code.** React, TanStack Query, Prisma, zod and the standard library are full of generics. Understanding `<T>` lets you read their types and error messages.

</En>
<Ur>

- **Ek function, har type.** Na `firstNumber`, na `firstString`, na `firstUser`.
- **Koi maloomat zaya nahi.** `any` ke baraks nateeja apni bilkul durust type rakhta hai, isliye autocomplete aur error checking chalti rehti hai.
- **Dobara istemal hone wali data shakalen.** `ApiResponse<User>` aur `ApiResponse<Order>` ek hi tareef share karte hain.
- **Asli code parhna.** React, TanStack Query, Prisma, zod aur standard library generics se bhari hain. `<T>` samajhne se aap in ki types aur error messages parh sakte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Use a generic when **the type of the output depends on the type of the input**, or when a container or wrapper should hold "some type chosen later":

- helpers on lists: first, last, group, unique, paginate,
- wrappers: API responses, results, boxes, caches, queues,
- functions that pick properties from objects.

If a type parameter is used only **once**, you probably don't need it.

</En>
<Ur>

Generic tab lein jab **output ki type input ki type par munhasir ho**, ya jab koi container ya wrapper "baad me chuni jane wali koi type" rakhe:

- lists par helpers: first, last, group, unique, paginate,
- wrappers: API responses, results, boxes, caches, queues,
- aise functions jo objects se properties chunte hain.

Agar type parameter sirf **ek dafa** istemal ho to shayad us ki zaroorat nahi.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```ts
// generic function
function wrap<T>(value: T): T[] { return [value]; }

// generic type
type ApiResponse<T> = { data: T; error: string | null };

// limited with extends
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
```

</En>
<Ur>

```ts
// generic function
function wrap<T>(value: T): T[] { return [value]; }

// generic type
type ApiResponse<T> = { data: T; error: string | null };

// extends se mehdood
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **lunch box with a label holder** on the lid. The box itself is always the same design: it opens, closes and keeps food fresh. What goes **inside** changes every day. When you pack it, you slide a card into the label holder: "Sandwich". Now everyone knows what's inside, and when you open it, you get a sandwich, not "some food".

- The box design is the **generic**: `Box<T>`.
- The empty label holder is the **type parameter**, `T`.
- Sliding in the card "Sandwich" is choosing `T = Sandwich`, either by writing it (`Box<Sandwich>`) or by TypeScript reading it from what you packed.

Using `any` instead is like a box with **no** label: it still holds food, but whoever opens it has no idea what to expect. And `extends` is a rule printed on the box, like "**liquids only**": you can choose the label, but only from things that fit the rule.

</En>
<Ur>

Ek **lunch box** ka sochein jis ke dhakkan par **label rakhne ki jagah** hai. Dabba hamesha ek hi design ka hai: khulta hai, band hota hai aur khana taaza rakhta hai. Is ke **andar** kya hai wo roz badalta hai. Pack karte waqt aap label wali jagah me card dalte hain: "Sandwich". Ab sab ko maloom hai ke andar kya hai, aur kholne par aap ko sandwich milta hai, "koi khana" nahi.

- Dabbe ka design **generic** hai: `Box<T>`.
- Label ki khaali jagah **type parameter** `T` hai.
- "Sandwich" ka card dalna `T = Sandwich` chunna hai, ya to likh kar (`Box<Sandwich>`) ya TypeScript ke is se parh lene se ke aap ne kya pack kiya.

Is ke bajaye `any` lena aisa dabba hai jis par **koi** label nahi: khana phir bhi rehta hai, magar kholne wale ko andaza nahi ke kya milega. Aur `extends` dabbe par chhapa qaida hai, jaise "**sirf maa'e cheezen**": aap label chun sakte hain, magar sirf un cheezon me se jo qaide par poori utren.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Generic** | Code that works with a type chosen later | `function first<T>(…)` |
| **Type parameter** | The placeholder for that type | `T` |
| **Type argument** | The actual type filled in | `string` in `first<string>(…)` |
| **Inference** | TypeScript filling in `T` from the arguments | `first([1, 2])` → `T` is `number` |
| **Generic type** | A type with a type parameter | `type Box<T> = { value: T }` |
| **Constraint** | A limit on what `T` can be | `T extends { length: number }` |
| **`keyof`** | The union of an object type's keys | `keyof User` is `"id" \| "name"` |
| **Indexed access** | The type of one property | `User["name"]` is `string` |
| **Default type** | Used when no type argument is given | `<T = unknown>` |
| **Angle brackets** | `< >`, where type parameters go | |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Generic** | Code jo baad me chuni gayi type ke saath kaam kare | `function first<T>(…)` |
| **Type parameter** | Us type ka placeholder | `T` |
| **Type argument** | Asal type jo bhari jaye | `first<string>(…)` me `string` |
| **Inference** | TypeScript ka arguments se `T` bharna | `first([1, 2])` → `T` `number` hai |
| **Generic type** | Type parameter wali type | `type Box<T> = { value: T }` |
| **Constraint** | `T` kya ho sakta hai us ki had | `T extends { length: number }` |
| **`keyof`** | Object type ki keys ka union | `keyof User` yaani `"id" \| "name"` |
| **Indexed access** | Ek property ki type | `User["name"]` yaani `string` |
| **Default type** | Jab type argument na diya jaye to istemal hone wali | `<T = unknown>` |
| **Angle brackets** | `< >`, jahan type parameters jate hain | |

</Ur>
</Tr>

## Learn it step by step

<Tr>
<En>
**TypeScript** blocks can be run on the page. **Checker** blocks show the real output of `npx tsc --noEmit --strict app.ts` for the code saved into `app.ts`.
</En>
<Ur>
**TypeScript** blocks page par chalaye ja sakte hain. **Checker** blocks `app.ts` me mehfooz code par `npx tsc --noEmit --strict app.ts` ka asli output dikhate hain.
</Ur>
</Tr>

<Walkthrough>

<Step title="The problem: one job, many types">

<Tr>
<En>
We want a helper that returns the last item of a list. Two obvious attempts both have a problem. One copies the function per type; the other uses `any`, which lets bugs through.
</En>
<Ur>
Hum aisa helper chahte hain jo list ka aakhri item wapas kare. Do seedhi koshishon me dono me masla hai. Ek har type ke liye function copy karti hai; doosri `any` istemal karti hai, jo bugs ko guzarne deta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function lastNumber(list: number[]): number { return list[list.length - 1]; }
function lastString(list: string[]): string { return list[list.length - 1]; }

function lastAny(list: any[]): any {
  return list[list.length - 1];
}

const city = lastAny(["Austin", "Denver"]);
city.toUpperCse();
const total = lastAny([5, 10]) + lastAny(["oops"]);
EOF
npx tsc --noEmit --strict app.ts
echo "checker finished with no errors"
```

```text output
checker finished with no errors
```

<Happened>
<Tr>
<En>

- `lastNumber` and `lastString` are the same code twice. For users, orders and products you'd need more copies.
- `lastAny` works for everything, but its result is `any`. `toUpperCse` (a typo) and adding a number to text were **not reported**. The checker printed nothing at all.
- We want both: **one** function, **and** an exact result type. That's what a generic gives you.

</En>
<Ur>

- `lastNumber` aur `lastString` ek hi code do dafa hain. Users, orders aur products ke liye mazeed copies chahiye hongi.
- `lastAny` har cheez ke liye chalta hai, magar us ka nateeja `any` hai. `toUpperCse` (typo) aur text me number jorna **report nahi hue**. Checker ne kuch bhi print nahi kiya.
- Hamen dono chahiyen: **ek** function, **aur** bilkul durust nateeje ki type. Generic yahi deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Your first type parameter">

<Tr>
<En>
Add `<T>` after the function name. Now `T` can be used as a type inside the function: `list: T[]` and the return type `T | undefined` (the list might be empty).
</En>
<Ur>
Function ke naam ke baad `<T>` jorein. Ab function ke andar `T` type ki tarah istemal ho sakta hai: `list: T[]` aur return type `T | undefined` (list khaali bhi ho sakti hai).
</Ur>
</Tr>

```typescript
function last<T>(list: T[]): T | undefined {
  return list[list.length - 1];
}

const lastPrice = last([5, 10, 15]);
const lastCity = last(["Austin", "Denver"]);
const lastUser = last([{ name: "Sara" }, { name: "Alex" }]);
const nothing = last([]);

console.log(lastPrice, lastCity, lastUser?.name, nothing);
```

```text output
15 Denver Alex undefined
```

<Happened>
<Tr>
<En>

- One function served numbers, strings and objects.
- `T` is just a name. `T` (for "Type") is the tradition; you'll also see `Item`, `TData`, `K` (key) and `V` (value).
- At runtime the generic disappears like every type. The JavaScript that runs is simply `function last(list) { … }`.
- The difference shows up in the **checker**, as the next step proves.

</En>
<Ur>

- Ek function ne numbers, strings aur objects sab ka kaam kiya.
- `T` bas ek naam hai. `T` ("Type" ke liye) riwayat hai; `Item`, `TData`, `K` (key) aur `V` (value) bhi nazar aate hain.
- Chalte waqt generic bhi har type ki tarah ghayab ho jata hai. Jo JavaScript chalti hai wo bas `function last(list) { … }` hai.
- Farq **checker** me nazar aata hai, jaisa agla qadam sabit karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="TypeScript fills in T for you">

<Tr>
<En>
When you call a generic function, TypeScript looks at the arguments and **infers** `T`. The result then has the exact type, so mistakes are caught again.
</En>
<Ur>
Generic function call karte waqt TypeScript arguments dekh kar `T` **infer** karta hai. Phir nateeje ki bilkul durust type hoti hai, isliye ghaltiyan phir se pakri jati hain.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function wrap<T>(value: T): T[] {
  return [value];
}

const prices = wrap(5);
const names = wrap("Sara");

prices[0].toUpperCase();
names[0].toUpperCse();
const total: number = names[0];
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(8,11): error TS2339: Property 'toUpperCase' does not exist on type 'number'.
app.ts(9,10): error TS2551: Property 'toUpperCse' does not exist on type 'string'. Did you mean 'toUpperCase'?
app.ts(10,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

<Happened>
<Tr>
<En>

- `wrap(5)`: TypeScript saw a number, set `T = number`, so `prices` is `number[]`.
- `wrap("Sara")`: `T = string`, so `names` is `string[]`.
- Now all three mistakes are reported, including the typo, with a suggestion. Compare this with the silence of `any` in step 1.
- You never wrote `number` or `string` anywhere. Inference did it.

</En>
<Ur>

- `wrap(5)`: TypeScript ne number dekha, `T = number` rakha, isliye `prices` `number[]` hai.
- `wrap("Sara")`: `T = string`, isliye `names` `string[]` hai.
- Ab teeno ghaltiyan report hui hain, typo samet, mashware ke saath. Qadam 1 me `any` ki khamoshi se muqabla karein.
- Aap ne kahin bhi `number` ya `string` nahi likha. Inference ne kar diya.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Writing the type yourself">

<Tr>
<En>
Sometimes there's nothing to infer from, or the inferred type is too narrow. Then you pass the type argument yourself, in `< >` after the name. This is very common with empty starting values.
</En>
<Ur>
Kabhi andaza lagane ke liye kuch nahi hota, ya nikali gayi type bohot tang hoti hai. Tab aap type argument khud naam ke baad `< >` me dete hain. Khaali shuruati values ke saath ye bohot aam hai.
</Ur>
</Tr>

```typescript
function createList<T>(): T[] {
  return [];
}

const tags = createList<string>();
tags.push("sale");
tags.push("new");

const seenIds = new Set<number>();
seenIds.add(7);
seenIds.add(7);
seenIds.add(9);

const prices = new Map<string, number>();
prices.set("pen", 2);

console.log(tags, seenIds.size, prices.get("pen"));
```

```text output
[ 'sale', 'new' ] 2 2
```

<Happened>
<Tr>
<En>

- `createList()` takes no arguments, so there's nothing to infer `T` from. `createList<string>()` says it directly.
- `Set<number>` and `Map<string, number>` are generic classes from JavaScript's standard library. The type arguments tell TypeScript what goes inside.
- In React you'll write exactly this: `useState<string | null>(null)`, because from `null` alone TypeScript can't guess you'll later store a string.

</En>
<Ur>

- `createList()` koi argument nahi leta, isliye `T` ka andaza lagane ke liye kuch nahi. `createList<string>()` seedha bata deta hai.
- `Set<number>` aur `Map<string, number>` JavaScript ki standard library ki generic classes hain. Type arguments TypeScript ko batate hain ke andar kya jayega.
- React me aap bilkul yahi likhenge: `useState<string | null>(null)`, kyun ke sirf `null` se TypeScript andaza nahi laga sakta ke baad me aap string rakhenge.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Generics you already use">

<Tr>
<En>
You've met generic types without knowing it. `string[]` is short for **`Array<string>`**. An async function returns **`Promise<T>`**: a promise that will hold a `T`. Array methods such as `map` are generic too: the type of the new array comes from what your callback returns.
</En>
<Ur>
Aap anjaane me generic types se mil chuke hain. `string[]` **`Array<string>`** ka chhota roop hai. Async function **`Promise<T>`** wapas karta hai: aisa promise jis me `T` hoga. `map` jaise array methods bhi generic hain: nayi array ki type wahan se aati hai jo aap ka callback wapas karta hai.
</Ur>
</Tr>

```typescript
type User = { id: number; name: string };

const ids: Array<number> = [1, 2, 3];

const labels = ids.map((id) => "user-" + id);

async function getUser(id: number): Promise<User> {
  return { id: id, name: "Sara" };
}

const user = await getUser(1);
console.log(labels, user.name);
```

```text output
[ 'user-1', 'user-2', 'user-3' ] Sara
```

<Happened>
<Tr>
<En>

- `Array<number>` and `number[]` are identical. Most people write `number[]`.
- `map` is declared roughly as `map<U>(fn: (item: T) => U): U[]`. Our callback returns strings, so `U = string` and `labels` is `string[]`.
- `Promise<User>` says "this function finishes later with a `User`". `await` unwraps it, so `user` is a `User`.

</En>
<Ur>

- `Array<number>` aur `number[]` bilkul ek hain. Zyada tar log `number[]` likhte hain.
- `map` taqreeban aise bayan hai: `map<U>(fn: (item: T) => U): U[]`. Hamara callback strings wapas karta hai, isliye `U = string` aur `labels` `string[]` hai.
- `Promise<User>` kehta hai "ye function baad me `User` ke saath khatam hoga". `await` use kholta hai, isliye `user` `User` hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="More than one type parameter">

<Tr>
<En>
A function can have several type parameters, separated by commas. Each one is filled in independently.
</En>
<Ur>
Function ke kai type parameters ho sakte hain, commas se alag. Har ek alag se bhara jata hai.
</Ur>
</Tr>

```typescript
function makePair<A, B>(first: A, second: B): [A, B] {
  return [first, second];
}

function mapObject<V, R>(obj: Record<string, V>, fn: (value: V) => R): Record<string, R> {
  const result: Record<string, R> = {};
  for (const [key, value] of Object.entries(obj)) {
    result[key] = fn(value);
  }
  return result;
}

const entry = makePair("Sara", 92);
const pricesInCents = { pen: 250, bag: 4000 };
const pricesInDollars = mapObject(pricesInCents, (cents) => "$" + (cents / 100).toFixed(2));

console.log(entry);
console.log(pricesInDollars);
```

```text output
[ 'Sara', 92 ]
{ pen: '$2.50', bag: '$40.00' }
```

<Happened>
<Tr>
<En>

- `makePair("Sara", 92)` inferred `A = string` and `B = number`, so `entry` is the tuple `[string, number]`.
- `mapObject` takes an object of `V` values and a function from `V` to `R`, and returns an object of `R` values. Here `V = number` (cents) and `R = string` (labels). The same function could turn numbers into booleans or users into names.
- Notice how the types **connect** input to output. That connection is the whole point of a generic.

</En>
<Ur>

- `makePair("Sara", 92)` ne `A = string` aur `B = number` nikala, isliye `entry` tuple `[string, number]` hai.
- `mapObject` `V` values wala object aur `V` se `R` banane wala function leta hai, aur `R` values wala object wapas karta hai. Yahan `V = number` (cents) aur `R = string` (labels). Yahi function numbers ko booleans ya users ko naamon me bhi badal sakta hai.
- Dekhein types kaise input ko output se **jorti** hain. Generic ka asal maqsad yahi jor hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Generic types: one shape, many contents">

<Tr>
<En>
Types and interfaces can have type parameters too. A classic example is an API response wrapper: the outer shape is always the same, but `data` changes. You can also give a type parameter a **default**.
</En>
<Ur>
Types aur interfaces ke bhi type parameters ho sakte hain. Mashhoor misaal API response ka wrapper hai: bahar ki shakal hamesha wahi, magar `data` badalta hai. Type parameter ko **default** bhi diya ja sakta hai.
</Ur>
</Tr>

```typescript
type ApiResponse<T> = {
  data: T | null;
  error: string | null;
  fetchedAt: string;
};

type User = { id: number; name: string };
type Product = { sku: string; price: number };

const userResponse: ApiResponse<User> = {
  data: { id: 1, name: "Sara" },
  error: null,
  fetchedAt: "2026-11-11",
};

const productsResponse: ApiResponse<Product[]> = {
  data: null,
  error: "Server unavailable",
  fetchedAt: "2026-11-11",
};

interface Page<Item, Meta = { total: number }> {
  items: Item[];
  meta: Meta;
}

const firstPage: Page<string> = { items: ["a", "b"], meta: { total: 40 } };

console.log(userResponse.data?.name);
console.log(productsResponse.error);
console.log(firstPage.items.length, "of", firstPage.meta.total);
```

```text output
Sara
Server unavailable
2 of 40
```

<Happened>
<Tr>
<En>

- `ApiResponse<User>` means "an API response whose `data` is a `User`". `ApiResponse<Product[]>` holds a list of products. One definition, any payload.
- With generic **types** you usually write the type argument, because there's no function call to infer it from.
- `Page<Item, Meta = { total: number }>` has a default for `Meta`, so `Page<string>` was enough.

</En>
<Ur>

- `ApiResponse<User>` ka matlab "aisa API response jis ka `data` `User` hai". `ApiResponse<Product[]>` products ki list rakhta hai. Ek tareef, koi bhi mawad.
- Generic **types** ke saath aam taur par type argument likhna parta hai, kyun ke andaza lagane ke liye koi function call nahi hoti.
- `Page<Item, Meta = { total: number }>` me `Meta` ka default hai, isliye `Page<string>` kaafi tha.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Limit T with extends">

<Tr>
<En>
Inside a plain generic, TypeScript knows nothing about `T`, so you can't use any properties. A **constraint**, `T extends Something`, says "T can be any type, as long as it has at least this". Then you may use those properties.
</En>
<Ur>
Saade generic ke andar TypeScript `T` ke baare me kuch nahi jaanta, isliye aap koi property istemal nahi kar sakte. **Constraint**, `T extends Something`, kehta hai "T koi bhi type ho sakta hai, basharte us me kam az kam ye ho". Phir wo properties istemal ki ja sakti hain.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function longestBad<T>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

const word = longest("pear", "banana");
const list = longest([1, 2], [1, 2, 3]);
const num = longest(10, 20);
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(2,12): error TS2339: Property 'length' does not exist on type 'T'.
app.ts(2,24): error TS2339: Property 'length' does not exist on type 'T'.
app.ts(11,21): error TS2345: Argument of type 'number' is not assignable to parameter of type '{ length: number; }'.
```

<Happened>
<Tr>
<En>

- `longestBad` fails: `T` could be a number, and numbers have no `length`.
- `longest` adds `extends { length: number }`. Strings and arrays both have a numeric `length`, so they're accepted, and the result keeps their exact type (`string`, `number[]`).
- `longest(10, 20)` is rejected: numbers don't meet the constraint.
- Read `extends` here as "**must have at least**", not as class inheritance.

</En>
<Ur>

- `longestBad` nakaam hai: `T` number ho sakta hai, aur numbers ki `length` nahi hoti.
- `longest` `extends { length: number }` jorta hai. Strings aur arrays dono ki number wali `length` hai, isliye wo qubool hain, aur nateeja un ki durust type rakhta hai (`string`, `number[]`).
- `longest(10, 20)` mustarad hai: numbers constraint par poore nahi utarte.
- Yahan `extends` ko "**kam az kam ye hona chahiye**" parhein, class ki wirasat nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Only real keys: keyof">

<Tr>
<En>
`keyof User` is the union of `User`'s property names. Combined with a second type parameter, `K extends keyof T`, you can write a function that only accepts **real** keys of an object, and returns the **exact** type of that property, written `T[K]`.
</En>
<Ur>
`keyof User` `User` ki properties ke naamon ka union hai. Doosre type parameter `K extends keyof T` ke saath aap aisa function likh sakte hain jo object ki sirf **asli** keys qubool kare, aur us property ki **bilkul durust** type wapas kare, jo `T[K]` likhi jati hai.
</Ur>
</Tr>

```typescript
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

const user = { id: 7, name: "Sara", isAdmin: false };
const products = [
  { sku: "PEN-1", price: 2 },
  { sku: "BAG-4", price: 40 },
];

const name = getProperty(user, "name");
const admin = getProperty(user, "isAdmin");
const prices = pluck(products, "price");

console.log(name.toUpperCase(), admin, prices);
```

```text output
SARA false [ 2, 40 ]
```

<Happened>
<Tr>
<En>

- `getProperty(user, "name")` returns a `string` (that's `T["name"]`), so `toUpperCase` is allowed. `getProperty(user, "isAdmin")` returns a `boolean`.
- `pluck(products, "price")` returns `number[]`: each item's `price`.
- Try `getProperty(user, "email")` in an editor: it's an error, because `"email"` isn't one of `"id" | "name" | "isAdmin"`. Typos in key names are caught.

</En>
<Ur>

- `getProperty(user, "name")` `string` wapas karta hai (yaani `T["name"]`), isliye `toUpperCase` ki ijazat hai. `getProperty(user, "isAdmin")` `boolean` wapas karta hai.
- `pluck(products, "price")` `number[]` wapas karta hai: har item ki `price`.
- Editor me `getProperty(user, "email")` aazmayen: ye error hai, kyun ke `"email"` `"id" | "name" | "isAdmin"` me se nahi. Key ke naamon me typos pakre jate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Generic helpers with callbacks">

<Tr>
<En>
Many useful helpers take a list of `T` and a function that does something with each `T`. The callback's parameter is typed automatically from the list.
</En>
<Ur>
Kai mufeed helpers `T` ki list aur aisa function lete hain jo har `T` ke saath kuch kare. Callback ka parameter list se khud ba khud type ho jata hai.
</Ur>
</Tr>

```typescript
function groupBy<T, K extends string>(items: T[], getKey: (item: T) => K): Record<K, T[]> {
  const groups = {} as Record<K, T[]>;
  for (const item of items) {
    const key = getKey(item);
    (groups[key] ??= []).push(item);
  }
  return groups;
}

type Order = { id: number; status: "paid" | "shipped"; total: number };

const orders: Order[] = [
  { id: 1, status: "paid", total: 20 },
  { id: 2, status: "shipped", total: 35 },
  { id: 3, status: "paid", total: 15 },
];

const byStatus = groupBy(orders, (order) => order.status);
console.log(Object.keys(byStatus));
console.log(byStatus.paid.map((o) => o.id));
```

```text output
[ 'paid', 'shipped' ]
[ 1, 3 ]
```

<Happened>
<Tr>
<En>

- In `(order) => order.status`, we never annotated `order`. TypeScript knew it's an `Order` because `items` is `Order[]`.
- The key type `K` was inferred as `"paid" | "shipped"`, so the result is `Record<"paid" | "shipped", Order[]>`, and `byStatus.paid` is known to be a list of orders.
- `as Record<K, T[]>` is an assertion: we start with an empty object and promise it will match. It's acceptable here because the loop fills it in; keep such assertions small and local.
- `??=` means "if it's null or undefined, set it to this first".

</En>
<Ur>

- `(order) => order.status` me humne `order` par annotation nahi lagayi. TypeScript jaanta tha ke ye `Order` hai kyun ke `items` `Order[]` hai.
- Key ki type `K` `"paid" | "shipped"` nikali gayi, isliye nateeja `Record<"paid" | "shipped", Order[]>` hai, aur maloom hai ke `byStatus.paid` orders ki list hai.
- `as Record<K, T[]>` assertion hai: hum khaali object se shuru karte hain aur waada karte hain ke ye mil jayega. Yahan ye qabil-e-qubool hai kyun ke loop ise bhar deta hai; aisi assertions chhoti aur ek jagah tak mehdood rakhein.
- `??=` ka matlab "agar ye null ya undefined hai to pehle ise ye bana do".

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Generic classes">

<Tr>
<En>
Classes can be generic too. A queue, a cache or a store can hold "items of some type", chosen when you create it.
</En>
<Ur>
Classes bhi generic ho sakti hain. Queue, cache ya store "kisi type ke items" rakh sakte hain, jo banate waqt chuni jati hai.
</Ur>
</Tr>

```typescript
class Queue<T> {
  private items: T[] = [];

  add(item: T): void {
    this.items.push(item);
  }

  next(): T | undefined {
    return this.items.shift();
  }

  get size(): number {
    return this.items.length;
  }
}

type Job = { id: number; task: string };

const jobs = new Queue<Job>();
jobs.add({ id: 1, task: "send email" });
jobs.add({ id: 2, task: "resize image" });

console.log(jobs.size);
console.log(jobs.next()?.task);
console.log(jobs.size);
```

```text output
2
send email
1
```

<Happened>
<Tr>
<En>

- `class Queue<T>` uses `T` for what it stores, what `add` accepts and what `next` returns.
- `new Queue<Job>()` fixed `T = Job`. Adding a string to `jobs` would be a checker error.
- `private items` means code outside the class can't touch the array directly (checked by TypeScript).

</En>
<Ur>

- `class Queue<T>` `T` ko is ke liye istemal karti hai ke kya rakhti hai, `add` kya qubool karta hai aur `next` kya wapas karta hai.
- `new Queue<Job>()` ne `T = Job` muqarrar kar diya. `jobs` me string dalna checker ka error hota.
- `private items` ka matlab class ke bahar ka code array ko seedha nahi chhu sakta (TypeScript check karta hai).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="When not to use a generic">

<Tr>
<En>
A type parameter earns its place only when it **links** two or more things: an input to an output, or two inputs to each other. If `T` appears just once, it does nothing a plain type wouldn't.
</En>
<Ur>
Type parameter tabhi apni jagah ka haqdar hai jab wo do ya zyada cheezon ko **jore**: input ko output se, ya do inputs ko aapas me. Agar `T` sirf ek dafa aaye to wo kuch nahi karta jo saadi type na karti.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function logValue<T>(value: T): void {
  console.log(value);
}

function logValueSimple(value: unknown): void {
  console.log(value);
}

function parse<T>(json: string): T {
  return JSON.parse(json);
}

const user = parse<{ name: string }>('{"nmae": "Sara"}');
console.log(user.name.toUpperCase());
EOF
npx tsc --noEmit --strict app.ts && echo "no type errors" && node --experimental-strip-types --no-warnings app.ts 2>&1 | grep TypeError | sed 's/^ *//'
```

```text output
no type errors
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
```

<Happened>
<Tr>
<En>

- `logValue<T>` uses `T` once. `logValueSimple(value: unknown)` does exactly the same; prefer it.
- `parse<T>` is worse: `T` appears **only in the return type**, so the caller just picks a type and TypeScript believes it. It's an `as` in disguise.
- The checker found no errors, yet running it crashed: the JSON had `nmae`, not `name`. A generic can't check data from outside.
- For parsing, return `unknown` and validate, or use a schema library whose generic is backed by a real runtime check.

</En>
<Ur>

- `logValue<T>` `T` ko ek dafa istemal karta hai. `logValueSimple(value: unknown)` bilkul wahi karta hai; isi ko tarjeeh dein.
- `parse<T>` is se bhi bura hai: `T` **sirf return type me** aata hai, isliye call karne wala bas koi type chun leta hai aur TypeScript us par yaqeen kar leta hai. Ye bheys badla hua `as` hai.
- Checker ko koi error nahi mila, phir bhi chalane par crash hua: JSON me `nmae` tha, `name` nahi. Generic bahar ke data ko check nahi kar sakta.
- Parsing ke liye `unknown` wapas karein aur validate karein, ya aisi schema library lein jis ke generic ke peechhe chalte waqt ka asli check ho.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Using any instead of a generic">

```ts
function first(list: any[]): any {
  return list[0];
}
// first(names).toUpperCse() is not caught
```

</Bad>
<Good title="Keep the type with T">

```ts
function first<T>(list: T[]): T | undefined {
  return list[0];
}
```

</Good>
</Compare>

<Compare>
<Bad title="Using properties of an unconstrained T">

```ts

  return item.id;   // error: 'id' does not exist on type 'T'
}
```

</Bad>
<Good title="Constrain it">

```ts
function getId<T extends { id: number }>(item: T) {
  return item.id;
}
```

</Good>
</Compare>

<Compare>
<Bad title="Passing a type argument the checker could infer">

```ts
const pair = makePair<string, number>("Sara", 92);
```

<Tr>
<En>Not wrong, just noise. Let inference work.</En>
<Ur>Ghalat nahi, bas faltu. Inference ko kaam karne dein.</Ur>
</Tr>

</Bad>
<Good title="Write it only when there is nothing to infer from">

```ts
const pair = makePair("Sara", 92);
const [items, setItems] = useState<string[]>([]);
```

</Good>
</Compare>

<Compare>
<Bad title="A generic only in the return type">

```ts
async function getJson<T>(url: string): Promise<T> {
  return (await fetch(url)).json();   // trusts the caller blindly
}
```

</Bad>
<Good title="Return unknown, or validate">

```ts
async function getJson(url: string): Promise<unknown> {
  return (await fetch(url)).json();
}
// then check the shape with a schema before using it
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Too many type parameters.** `<T, U, V, W>` is usually a sign the function does too much.
- **Confusing `extends` with inheritance.** In `<T extends X>`, it means "T must fit X".
- **Long cryptic names in short code, or `T` in long code.** In a 3-line helper, `T` is fine; in a big type, `TItem` and `TError` are clearer.
- **Generic React components without need.** A `Select<T>` makes sense; most components don't need a type parameter.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bohot zyada type parameters.** `<T, U, V, W>` aam taur par is baat ki nishani hai ke function bohot zyada kaam karta hai.
- **`extends` ko wirasat samajhna.** `<T extends X>` me is ka matlab hai "T ko X me fit hona chahiye".
- **Chhote code me lambe pecheeda naam, ya lambe code me `T`.** 3 line ke helper me `T` theek hai; bari type me `TItem` aur `TError` zyada saaf hain.
- **Baghair zaroorat ke generic React components.** `Select<T>` samajh me aata hai; zyada tar components ko type parameter nahi chahiye.

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- A **type parameter** (`<T>`) is a placeholder for a type, chosen when the code is used.
- Generics let one function or type work for many types **without losing** the exact type, unlike `any`.
- TypeScript usually **infers** `T` from the arguments; write `<string>` yourself when there's nothing to infer from.
- You already use generics: `Array<T>`, `Promise<T>`, `Set<T>`, `Map<K, V>`, `map`, `useState<T>`.
- Generic types: `type ApiResponse<T> = { data: T }`, with optional defaults `<T = unknown>`.
- **Constraints**: `T extends { length: number }` lets you use those properties.
- `K extends keyof T` accepts only real keys; `T[K]` is that property's type.
- If `T` appears only once, or only in the return type, you probably don't need it.

</En>

<DeepDive title="More generic techniques">

**Inference from several places.** With `function merge<T>(a: T, b: T)`, calling `merge(1, "a")` fails, because TypeScript picks `T` from the first argument. Unions or separate parameters (`<A, B>`) fix it.

**`const` type parameters** (TypeScript 5.0+): `function tuple<const T extends readonly unknown[]>(…items: T)` infers literal types (`["a", 1]` instead of `(string | number)[]`) without callers writing `as const`.

**Generic arrow functions** in `.tsx` files need a trailing comma or a constraint so the `<T>` isn't read as JSX: `const first = <T,>(list: T[]) => list[0];`.

**Generic React components.** A list or select component can be generic so the item type flows from props to callbacks:

```text
function List<T>({ items, render }: { items: T[]; render: (item: T) => React.ReactNode }) {
  return <ul>{items.map((item, i) => <li key={i}>{render(item)}</li>)}</ul>;
}
```

**Conditional types** pick a type based on another: `type ElementOf<T> = T extends (infer U)[] ? U : never;`. `infer` extracts part of a type. Built-in helpers like `ReturnType<F>` and `Awaited<P>` are written this way.

**Mapped types** loop over keys: `type Optional<T> = { [K in keyof T]?: T[K] };`. The built-in `Partial`, `Readonly` and `Pick` are mapped types; the next lesson covers them.

**Variance.** A `Box<Dog>` may or may not be usable as a `Box<Animal>`, depending on whether `T` is only read (safe) or also written. TypeScript works this out from how `T` is used; you can annotate it with `in` and `out` on type parameters.

**Performance.** Very deep generic and conditional types can slow the editor down. If hovering over a type takes seconds, simplify it.

</DeepDive>

<DeepDive title="Real world: the fetch helper that lied">

A team wrote a small helper used in hundreds of places:

```ts
async function api<T>(path: string): Promise<T> {
  const res = await fetch("/api" + path);
  return res.json();
}

const user = await api<User>("/me");
```

It felt fully typed: every call site had autocomplete and every component received a `User`. But `T` appears only in the return type, so it was really `res.json() as T`. Nothing checked the response.

When the backend renamed `user.fullName` to `user.name`, the front end compiled without a single error and rendered blank names everywhere. When an endpoint started returning `{ error: "unauthorized" }` with a 200 status for expired sessions, components tried to read `user.orders.length` and crashed.

The fix kept the convenient call style but made the generic honest by tying it to a runtime schema:

```text
async function api<S extends z.ZodTypeAny>(path: string, schema: S): Promise<z.infer<S>> {
  const res = await fetch("/api" + path);
  if (!res.ok) throw new Error("HTTP " + res.status);
  return schema.parse(await res.json());
}

const user = await api("/me", UserSchema);
```

Now `T` is inferred from a schema that actually checks the data, and a mismatch fails loudly at the boundary with a message naming the bad field.

</DeepDive>

<DeepDive title="Security lens">

Generics make code reusable; they can also make unchecked data look checked.

- **Return-only generics are assertions.** `function get<T>(): T` lets any caller claim any type. In security-sensitive code (auth tokens, permissions, payment responses), treat them like `as` and require runtime validation.
- **Generic data access helpers** such as `findById<T>(table, id)` must still enforce authorization. A generic repository that fetches any record by id makes it easy to forget the "does this user own this record?" check. Build the ownership check into the helper's signature, for example by requiring a `userId`.
- **`keyof` for safe field selection.** Accepting only `keyof User` for sort or filter fields prevents typos, but a request's query string is still a plain string at runtime. Validate it against an allow-list before using it in a database query, or it becomes an injection point.
- **Shared generic types across client and server** (for example with tRPC or a shared `ApiResponse<T>`) keep both sides aligned, but the server must never trust that the client sent a correctly typed body.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are generics in TypeScript?">
Generics let you write functions, types, interfaces and classes with type parameters, placeholders for types that are supplied when the code is used. They let one implementation work with many types while preserving the specific type information, for example a function that returns an element of the same type as the array it receives.
</QA>

<QA q="How is a generic different from using any?">
any discards type information, so the result of a function using any can be misused without errors. A generic links input and output types, so the caller gets back exactly the type they passed in, and every later use is still checked.
</QA>

<QA q="What is a generic constraint?">
A constraint written with extends restricts which types can be used for a type parameter, for example requiring that T has a length property or that K is a key of T. Inside the generic code you can then safely use the members guaranteed by the constraint.
</QA>

<QA q="What do keyof and indexed access types do?">
keyof produces a union of the property names of a type. An indexed access type such as T of K gives the type of property K in T. Together they let you write functions that accept only valid keys and return the matching property type.
</QA>

<QA q="When should you explicitly pass a type argument?">
When the compiler cannot infer it, for example when there are no arguments of that type, when the initial value is empty such as null or an empty array, or when the inferred type would be too narrow. Otherwise inference is preferred.
</QA>

<QA q="Give examples of generics in the standard library or React.">
Array of T, Promise of T, Map of K and V, Set of T, and the generic signatures of array methods such as map and filter. In React, useState of T, useRef of T and the props types of generic components; in libraries, query hooks typed by the data they return.
</QA>

</DeepDive>
