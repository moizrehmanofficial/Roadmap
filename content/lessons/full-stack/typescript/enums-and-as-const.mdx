<BigIdea>
<Tr>
<En>
Most apps have **fixed lists of values**: user roles (`ADMIN`, `EDITOR`, `VIEWER`), order statuses, subscription plans, T-shirt sizes. Writing those as loose strings all over the code invites typos and makes renaming painful. TypeScript offers two ways to give the list **one home**. An **enum** (`enum Role { Admin = "ADMIN", … }`) is a TypeScript feature that creates both a **type** and a real **object** at runtime. It's handy, but it's one of the few TypeScript features that **isn't plain JavaScript**: it generates extra code, and tools that only strip types (like Node's built-in TypeScript support) refuse it. The modern alternative is a normal object or array marked **`as const`**: TypeScript then keeps the exact literal values and makes them read-only, and with `typeof` and `keyof` you get a union type from it. Same safety and autocomplete, but it's just JavaScript.
</En>
<Ur>
Zyada tar apps me **values ki muqarrar lists** hoti hain: user roles (`ADMIN`, `EDITOR`, `VIEWER`), order statuses, subscription plans, T-shirt sizes. Inhen poore code me khuli strings ki tarah likhna typos ko dawat deta hai aur naam badalna takleef deh banata hai. TypeScript list ko **ek ghar** dene ke do tareeqe deti hai. **Enum** (`enum Role { Admin = "ADMIN", … }`) TypeScript ki feature hai jo **type** aur runtime par asli **object** dono banati hai. Ye kaam ki hai, magar TypeScript ki un chand features me se hai jo **saada JavaScript nahi**: ye izafi code banati hai, aur jo tools sirf types hatate hain (jaise Node ki built-in TypeScript support) use mustarad karte hain. Jadeed mutabadil ek aam object ya array hai jis par **`as const`** laga ho: phir TypeScript bilkul theek literal values barqarar rakhti hai aur unhen read-only bana deti hai, aur `typeof` aur `keyof` se aap us se union type nikal lete hain. Wahi hifazat aur autocomplete, magar ye bas JavaScript hai.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **One source of truth**: rename a value in one place, and the compiler finds every use.
- **Typos are caught** and the editor autocompletes the allowed values.
- **You often need the list at runtime too**: for dropdowns, validation, and looping, not just for types.
- **Knowing enum trade-offs** helps you read existing code and pick the style your team uses.

</En>
<Ur>

- **Sach ka ek zariya**: value ka naam ek jagah badlein, aur compiler har istemal dhoond leta hai.
- **Typos pakre jate hain** aur editor jaiz values autocomplete karta hai.
- **List aksar runtime par bhi chahiye hoti hai**: dropdowns, validation aur loops ke liye, sirf types ke liye nahi.
- **Enum ke faide nuqsaan jaanna** maujooda code parhne aur team ka style chunne me madad karta hai.

</Ur>
</Tr>

<Tr>

| Situation | Good choice |

<How>
<Tr>
<En>

1. Write the values once: `const ROLES = ["admin", "editor", "viewer"] as const;`
2. Derive the type: `type Role = (typeof ROLES)[number];`
3. Use `Role` in function parameters and object types.
4. Use `ROLES` at runtime for loops, dropdowns and validation.

</En>
<Ur>

1. Values ek dafa likhein: `const ROLES = ["admin", "editor", "viewer"] as const;`
2. Type nikalein: `type Role = (typeof ROLES)[number];`
3. Function parameters aur object types me `Role` istemal karein.
4. Runtime par loops, dropdowns aur validation ke liye `ROLES` istemal karein.

</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of the **menu board** in a coffee shop.

- Without a menu, every cashier writes orders by hand: "latte", "Latte", "lattee". The kitchen guesses. That's loose strings everywhere.
- An **enum** is a menu printed by a special printer that only the shop owns. It's neat and official, but the printer also produces an extra sheet of paper (generated code), and some delivery partners can't read that format.
- An **`as const` object** is the same menu written on an ordinary laminated card. Anyone can read it (it's plain JavaScript), and the lamination means nobody is supposed to scribble on it (read-only types).
- But lamination isn't a safe: someone determined can still peel it and scribble. `as const` protects you **at compile time**; it doesn't freeze the object at runtime (that's `Object.freeze`).

</En>
<Ur>

Coffee shop ke **menu board** ka sochein.

- Menu ke baghair har cashier haath se order likhta hai: "latte", "Latte", "lattee". Kitchen andaza lagata hai. Ye har jagah khuli strings hain.
- **Enum** aisa menu hai jo ek khaas printer se chhapta hai jo sirf shop ke paas hai. Saaf aur sarkari hai, magar printer ek izafi kaghaz bhi nikalta hai (generated code), aur kuch delivery partners wo format nahi parh sakte.
- **`as const` object** wahi menu ek aam laminated card par likha hua hai. Koi bhi parh sakta hai (ye saada JavaScript hai), aur lamination ka matlab koi us par likhne wala nahi (read-only types).
- Magar lamination tijori nahi: koi zid kare to utar kar likh sakta hai. `as const` **compile time par** hifazat karta hai; ye runtime par object ko jama nahi karta (wo `Object.freeze` hai).

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Enum** | A named set of constants that is both a type and an object | `enum Role { … }` |
| **Member** | One entry of an enum | `Role.Admin` |
| **Numeric enum** | Members get numbers 0, 1, 2… | `Status.Paid` is `1` |
| **String enum** | Members get explicit strings | `Role.Admin` is `"ADMIN"` |
| **Reverse mapping** | Numeric enums map numbers back to names | `Status[1]` is `"Paid"` |
| **`as const`** | Keep literal types and make everything read-only | `[1, 2] as const` |
| **const assertion** | The official name of `as const` | |
| **Tuple** | A fixed-length array with known types per position | `readonly ["en", "fr"]` |
| **`typeof` (type position)** | The type of a value | `typeof Role` |
| **`keyof`** | Union of an object type's keys | `keyof typeof Role` |
| **Indexed access type** | The type at a key | `(typeof SIZES)[number]` |
| **`satisfies`** | Check a value matches a type without changing its inferred type | `satisfies Record<Plan, number>` |
| **Erasable syntax** | TypeScript that can be removed to leave valid JS | type annotations (not enums) |

</En>

## Learn it step by step

<Walkthrough>

<Step title="A numeric enum and the JavaScript it becomes">

<Tr>
<En>
Write `enum`, a name, and the members. By default the first member is `0`, the next `1`, and so on. Let's compile it with `tsc` and look at the JavaScript it **generates**.
</En>
<Ur>
`enum`, ek naam, aur members likhein. Default me pehla member `0`, agla `1`, waghaira hota hai. Ise `tsc` se compile karte hain aur dekhte hain ke ye kaun sa JavaScript **banata** hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
enum Status {
  Pending,
  Paid,
  Shipped,
}
console.log(Status.Paid);
console.log(Status[2]);
console.log(Status);
EOF
npx tsc --strict --target es2022 app.ts
sed -n '/var Status/,/})(Status/p' app.js
echo "--- running app.js ---"
node app.js
```

```text output
var Status;
(function (Status) {
    Status[Status["Pending"] = 0] = "Pending";
    Status[Status["Paid"] = 1] = "Paid";
    Status[Status["Shipped"] = 2] = "Shipped";
})(Status || (Status = {}));
--- running app.js ---
1
Shipped
{
  '0': 'Pending',
  '1': 'Paid',
  '2': 'Shipped',
  Pending: 0,
  Paid: 1,
  Shipped: 2
}
```

<Happened>
<Tr>
<En>

- Unlike type annotations, which simply disappear, an enum **becomes real code**: a function that fills an object.
- `Status.Paid` is just the number `1`. `Status[2]` goes the other way: number to name. That's a **reverse mapping**, and it's why the object has six keys.
- Numbers make logs and database rows hard to read (`status: 1`, but what's 1?). And inserting a new member in the middle **renumbers** everything after it, silently changing stored data's meaning.

</En>
<Ur>

- Type annotations ke bar-aks, jo bas ghayab ho jati hain, enum **asli code ban jata hai**: ek function jo object bharta hai.
- `Status.Paid` bas number `1` hai. `Status[2]` ulti taraf jata hai: number se naam. Ye **reverse mapping** hai, aur isi wajah se object ki chhe keys hain.
- Numbers logs aur database rows ko parhna mushkil banate hain (`status: 1`, magar 1 kya hai?). Aur beech me naya member jorna baad ke sab ko **dobara number** de deta hai, khamoshi se mehfooz data ka matlab badal kar.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="String enums: readable values">

<Tr>
<En>
Give each member an explicit string and the values become readable in logs, JSON and the database. String enums have no reverse mapping.
</En>
<Ur>
Har member ko saaf string dein aur values logs, JSON aur database me parhne layaq ban jati hain. String enums ki reverse mapping nahi hoti.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
enum Role {
  Admin = "ADMIN",
  Editor = "EDITOR",
  Viewer = "VIEWER",
}
function canEdit(role: Role): boolean {
  return role === Role.Admin || role === Role.Editor;
}
console.log(canEdit(Role.Editor), canEdit(Role.Viewer));
console.log(Object.values(Role));
console.log(JSON.stringify({ user: "sara", role: Role.Admin }));
EOF
npx tsc --strict --target es2022 app.ts && node app.js
```

```text output
true false
[ 'ADMIN', 'EDITOR', 'VIEWER' ]
{"user":"sara","role":"ADMIN"}
```

<Happened>
<Tr>
<En>

- `Role.Admin` **is** the string `"ADMIN"` at runtime, so JSON and logs are clear.
- `Object.values(Role)` lists the values, which is useful for dropdowns. (With a numeric enum it would mix names and numbers because of the reverse mapping.)
- If you use enums at all, **string enums are the safer choice**.

</En>
<Ur>

- Runtime par `Role.Admin` **bilkul** string `"ADMIN"` hai, isliye JSON aur logs saaf hain.
- `Object.values(Role)` values ki list deta hai, jo dropdowns ke liye kaam ki hai. (Numeric enum ke saath reverse mapping ki wajah se naam aur numbers mil jate.)
- Agar enums istemal karein hi, to **string enums mehfooz intikhab hain**.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Enums are strict about where values come from">

<Tr>
<En>
A string enum parameter only accepts the **enum member**, not the plain string with the same value. Numeric enums accept matching numbers but reject numbers outside the list.
</En>
<Ur>
String enum wala parameter sirf **enum member** qubool karta hai, wahi value wali saadi string nahi. Numeric enums milte julte numbers qubool karte hain magar list se bahar ke numbers mustarad karte hain.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
enum Role {
  Admin = "ADMIN",
  Editor = "EDITOR",
}
enum Status {
  Pending,
  Paid,
}
function canEdit(role: Role) { return role === Role.Admin; }
function label(s: Status) { return s; }

canEdit(Role.Admin);
canEdit("ADMIN");
label(Status.Paid);
label(1);
label(42);
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(13,9): error TS2345: Argument of type '"ADMIN"' is not assignable to parameter of type 'Role'.
app.ts(16,7): error TS2345: Argument of type '42' is not assignable to parameter of type 'Status'.
```

<Happened>
<Tr>
<En>

- Line 13: `"ADMIN"` is refused even though `Role.Admin === "ADMIN"`. String enums behave like their own special type. That's strict, but awkward when the value comes from JSON or an API: you need a conversion or a cast.
- Line 15: `label(1)` is allowed because `1` matches `Status.Paid`.
- Line 16: `42` is refused because no member has that value.

</En>
<Ur>

- Line 13: `"ADMIN"` mustarad hai halanke `Role.Admin === "ADMIN"`. String enums apni alag khaas type ki tarah bartao karte hain. Ye sakhti hai, magar jab value JSON ya API se aaye to mushkil: aap ko tabdeeli ya cast chahiye.
- Line 15: `label(1)` jaiz hai kyun ke `1` `Status.Paid` se milta hai.
- Line 16: `42` mustarad hai kyun ke kisi member ki ye value nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Enums aren't plain JavaScript">

<Tr>
<En>
Node.js can now run `.ts` files directly by **stripping** the types. That works because type annotations can just be erased. An enum can't be erased (it generates code), so Node refuses it. TypeScript's `erasableSyntaxOnly` option reports the same thing at compile time.
</En>
<Ur>
Node.js ab `.ts` files ko types **hata kar** seedha chala sakta hai. Ye is liye chalta hai ke type annotations bas mitaye ja sakte hain. Enum mitaya nahi ja sakta (ye code banata hai), isliye Node use mustarad karta hai. TypeScript ka `erasableSyntaxOnly` option compile time par yahi baat batata hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
enum Role {
  Admin = "ADMIN",
  Editor = "EDITOR",
}
console.log(Role.Admin);
EOF
node --experimental-strip-types --no-warnings app.ts 2>&1 | sed -n '1,7p'
echo "--- tsc with erasableSyntaxOnly ---"
npx tsc --noEmit --strict --erasableSyntaxOnly app.ts
```

```text output
/home/you/app.ts:1
  > enum Role {
      Admin = "ADMIN",
      Editor = "EDITOR",
  > }
    console.log(Role.Admin);

--- tsc with erasableSyntaxOnly ---
app.ts(1,6): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
```

<Happened>
<Tr>
<En>

- Node printed the enum and stopped with an error (`TypeScript enum is not supported in strip-only mode`). Bundlers like esbuild and SWC can compile enums, but the trend in the ecosystem is toward **TypeScript that is just JavaScript plus erasable types**.
- `erasableSyntaxOnly` (TypeScript 5.8+) lets a project forbid enums, `namespace`s and parameter properties so the code works with type-stripping tools.
- That's the main reason many teams now use `as const` instead.

</En>
<Ur>

- Node ne enum print kiya aur error ke saath ruk gaya (`TypeScript enum is not supported in strip-only mode`). esbuild aur SWC jaise bundlers enums compile kar sakte hain, magar ecosystem ka rujhan **aise TypeScript ki taraf hai jo bas JavaScript plus mitne wali types ho**.
- `erasableSyntaxOnly` (TypeScript 5.8+) project ko enums, `namespace`s aur parameter properties mana karne deta hai taa ke code type hatane wale tools ke saath chale.
- Yahi bari wajah hai ke bohot si teams ab `as const` istemal karti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What as const does">

<Tr>
<En>
Normally TypeScript **widens** object properties (`"dark"` becomes `string`) and lets you change them. Adding `as const` after a value keeps every literal exactly and makes everything, deeply, **read-only**.
</En>
<Ur>
Aam taur par TypeScript object properties ko **phaila** deti hai (`"dark"` `string` ban jata hai) aur unhen badalne deti hai. Value ke baad `as const` lagane se har literal bilkul waisa rehta hai aur sab kuch, gehrai tak, **read-only** ho jata hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
const plain = { theme: "dark", retries: 3, langs: ["en", "fr"] };
const frozen = { theme: "dark", retries: 3, langs: ["en", "fr"] } as const;

const t1: "dark" = plain.theme;
const t2: "dark" = frozen.theme;

frozen.retries = 5;
frozen.langs.push("de");
plain.retries = 5;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(4,7): error TS2322: Type 'string' is not assignable to type '"dark"'.
app.ts(7,8): error TS2540: Cannot assign to 'retries' because it is a read-only property.
app.ts(8,14): error TS2339: Property 'push' does not exist on type 'readonly ["en", "fr"]'.
```

<Happened>
<Tr>
<En>

- Line 4: `plain.theme` was widened to `string`. Line 5: `frozen.theme` kept the exact literal `"dark"`.
- Line 7: every property of `frozen` is `readonly`.
- Line 8: the array became `readonly ["en", "fr"]`, a read-only **tuple**, which has no `push`.
- Line 9: the plain object can still be changed.
- `as const` produces **no extra JavaScript**. It's pure type information.

</En>
<Ur>

- Line 4: `plain.theme` `string` tak phaila diya gaya. Line 5: `frozen.theme` ne bilkul literal `"dark"` rakha.
- Line 7: `frozen` ki har property `readonly` hai.
- Line 8: array `readonly ["en", "fr"]` ban gayi, ek read-only **tuple**, jis me `push` nahi.
- Line 9: saada object ab bhi badla ja sakta hai.
- `as const` **koi izafi JavaScript nahi** banata. Ye khalis type ki maloomat hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="An as const object instead of an enum">

<Tr>
<En>
Write the values in a normal object with `as const`, then derive a union type from it. Giving the type the **same name** as the object lets you use `Role.Admin` (the value) and `Role` (the type) just like an enum.
</En>
<Ur>
Values ko `as const` ke saath aam object me likhein, phir us se union type nikalein. Type ko object ka **wahi naam** dene se aap `Role.Admin` (value) aur `Role` (type) bilkul enum ki tarah istemal kar sakte hain.
</Ur>
</Tr>

```typescript
const Role = {
  Admin: "ADMIN",
  Editor: "EDITOR",
  Viewer: "VIEWER",
} as const;

type Role = (typeof Role)[keyof typeof Role];

function canEdit(role: Role): boolean {
  return role === Role.Admin || role === Role.Editor;
}

console.log(canEdit(Role.Editor));
console.log(canEdit("VIEWER"));
console.log(Object.values(Role));
```

```text output
true
false
[ 'ADMIN', 'EDITOR', 'VIEWER' ]
```

<Happened>
<Tr>
<En>

Read the type from the inside out:

1. `typeof Role` is the object's type: `{ readonly Admin: "ADMIN"; readonly Editor: "EDITOR"; readonly Viewer: "VIEWER" }`.
2. `keyof typeof Role` is the union of its keys: `"Admin" | "Editor" | "Viewer"`.
3. `(typeof Role)[keyof typeof Role]` looks up the value at every key: `"ADMIN" | "EDITOR" | "VIEWER"`.

- Unlike a string enum, the plain string `"VIEWER"` is accepted, which is convenient for values from JSON. `"VIEWER2"` would still be an error.
- This file runs with Node's type stripping. No generated code.

</En>
<Ur>

Type ko andar se bahar ki taraf parhein:

1. `typeof Role` object ki type hai: `{ readonly Admin: "ADMIN"; readonly Editor: "EDITOR"; readonly Viewer: "VIEWER" }`.
2. `keyof typeof Role` us ki keys ka union hai: `"Admin" | "Editor" | "Viewer"`.
3. `(typeof Role)[keyof typeof Role]` har key par value dekhta hai: `"ADMIN" | "EDITOR" | "VIEWER"`.

- String enum ke bar-aks saadi string `"VIEWER"` qubool hai, jo JSON se aane wali values ke liye aasan hai. `"VIEWER2"` phir bhi error hogi.
- Ye file Node ke type stripping ke saath chalti hai. Koi generated code nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="An as const array: the list and the type together">

<Tr>
<En>
When you need to **loop over** the values (a dropdown, validation), an `as const` array is the simplest home. `(typeof SIZES)[number]` means "the type of any element", which gives the union.
</En>
<Ur>
Jab values par **loop** chahiye (dropdown, validation), `as const` array sab se saada ghar hai. `(typeof SIZES)[number]` ka matlab "kisi bhi element ki type", jo union deta hai.
</Ur>
</Tr>

```typescript
const SIZES = ["small", "medium", "large"] as const;
type Size = (typeof SIZES)[number];

function isSize(value: string): value is Size {
  return (SIZES as readonly string[]).includes(value);
}

for (const s of SIZES) console.log("<option>" + s + "</option>");
console.log(isSize("medium"), isSize("huge"));
```

```text output
<option>small</option>
<option>medium</option>
<option>large</option>
true false
```

<Happened>
<Tr>
<En>

- One line of data gives you **both** the runtime list (for the dropdown) and the type `"small" | "medium" | "large"`.
- Add `"x-large"` to the array and the type updates automatically; there's nothing else to keep in sync.
- `isSize` is a type guard (previous lesson) that turns an untrusted string, from a URL or form, into a `Size`. The `as readonly string[]` cast is needed because `includes` on a tuple of literals only accepts those literals.

</En>
<Ur>

- Data ki ek line aap ko runtime list (dropdown ke liye) aur type `"small" | "medium" | "large"` **dono** deti hai.
- Array me `"x-large"` jorein aur type khud update ho jati hai; sync rakhne ke liye aur kuch nahi.
- `isSize` type guard hai (pichhla lesson) jo URL ya form ki na-qabil-e-bharosa string ko `Size` me badalta hai. `as readonly string[]` cast zaroori hai kyun ke literals ke tuple par `includes` sirf wahi literals qubool karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="satisfies: check the shape, keep the literals">

<Tr>
<En>
`satisfies` checks that a value matches a type **without** replacing its inferred type. Combined with `as const`, you get exact literals **and** a guarantee that every key is present and correctly spelled.
</En>
<Ur>
`satisfies` check karta hai ke value kisi type se milti hai, us ki nikali hui type **badle baghair**. `as const` ke saath milayen to aap ko bilkul theek literals **aur** ye zamanat milti hai ke har key maujood aur sahi spelling wali hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Plan = "free" | "pro" | "team";

const LIMITS = {
  free: 3,
  pro: 50,
  teams: 500,
} as const satisfies Record<Plan, number>;

const PRICES = {
  free: 0,
  pro: 12,
  team: 49,
} as const satisfies Record<Plan, number>;

const p: 12 = PRICES.pro;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(6,3): error TS2561: Object literal may only specify known properties, but 'teams' does not exist in type 'Record<Plan, number>'. Did you mean to write 'team'?
```

<Happened>
<Tr>
<En>

- `LIMITS` misspelled `team` as `teams`. `satisfies Record<Plan, number>` caught it, with a suggestion. If a plan were missing, it would be caught too.
- `PRICES` passed, and `PRICES.pro` still has the exact type `12` (line 15 passed), because `satisfies` didn't widen it to `number`.
- With a type annotation (`const PRICES: Record<Plan, number> = …`) you'd get the check but lose the literals.

</En>
<Ur>

- `LIMITS` ne `team` ko `teams` likha. `satisfies Record<Plan, number>` ne use mashware ke saath pakra. Agar koi plan ghayab hota to wo bhi pakra jata.
- `PRICES` paas hua, aur `PRICES.pro` ki ab bhi bilkul type `12` hai (line 15 paas hui), kyun ke `satisfies` ne use `number` tak nahi phailaya.
- Type annotation (`const PRICES: Record<Plan, number> = …`) ke saath check milta magar literals kho jate.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="as const is not a runtime lock">

<Tr>
<En>
`as const` only exists at compile time. If code escapes the type checker (with `as any`, or plain JavaScript), the object can still be changed. For a real runtime lock, use `Object.freeze`.
</En>
<Ur>
`as const` sirf compile time par maujood hai. Agar code type checker se bach nikle (`as any` se, ya saade JavaScript se), object ab bhi badla ja sakta hai. Asli runtime taale ke liye `Object.freeze` lein.
</Ur>
</Tr>

```typescript
const LIMITS = { free: 3, pro: 50 } as const;
console.log(Object.isFrozen(LIMITS));
(LIMITS as any).free = 999;
console.log("after sneaky change:", LIMITS.free);

const FROZEN = Object.freeze({ free: 3, pro: 50 });
try {
  (FROZEN as any).free = 999;
} catch (e) {
  console.log("blocked:", (e as Error).message);
}
console.log("frozen still:", FROZEN.free);
```

```text output
false
after sneaky change: 999
blocked: Cannot assign to read only property 'free' of object '#<Object>'
frozen still: 3
```

<Happened>
<Tr>
<En>

- `as const` didn't freeze anything: `Object.isFrozen` is `false` and the sneaky assignment worked.
- `Object.freeze` blocks changes at runtime (in strict mode, which modules always use, it throws). TypeScript also types a frozen object as `Readonly`.
- `Object.freeze` is **shallow**: nested objects and arrays inside are still changeable unless you freeze them too.

</En>
<Ur>

- `as const` ne kuch jama nahi kiya: `Object.isFrozen` `false` hai aur chhupi tabdeeli chal gayi.
- `Object.freeze` runtime par tabdeeliyan rokta hai (strict mode me, jo modules hamesha istemal karte hain, ye throw karta hai). TypeScript frozen object ko `Readonly` type bhi deti hai.
- `Object.freeze` **sathi** hai: andar ke nested objects aur arrays ab bhi badle ja sakte hain jab tak unhen bhi freeze na karein.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Numeric enum values stored in a database">

```text
enum Status { Pending, Paid, Shipped }
// rows saved as status = 0, 1, 2
// later someone inserts "Cancelled" after Pending:
enum Status { Pending, Cancelled, Paid, Shipped }
// every stored 1 ("Paid") now reads as "Cancelled"
```

</Bad>
<Good title="Readable, stable string values">

```text
const STATUSES = ["pending", "paid", "shipped", "cancelled"] as const;
type Status = (typeof STATUSES)[number];
// rows saved as status = "paid": order in the list doesn't matter
```

</Good>
</Compare>

<Compare>
<Bad title="Forgetting as const">

```bash
cat > app.ts <<'EOF'
const SIZES = ["small", "medium", "large"];
type Size = (typeof SIZES)[number];
const s: Size = "gigantic";
EOF
npx tsc --noEmit --strict app.ts && echo "tsc: no errors (Size is just string)"
```

```text output
tsc: no errors (Size is just string)
```

</Bad>
<Good title="With as const the union is exact">

```bash
cat > app.ts <<'EOF'
const SIZES = ["small", "medium", "large"] as const;
type Size = (typeof SIZES)[number];
const s: Size = "gigantic";
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(3,7): error TS2322: Type '"gigantic"' is not assignable to type '"large" | "medium" | "small"'.
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Mixing styles**: some lists as enums, others as `as const`, others as loose strings. Pick one convention per project.
- **Expecting `as const` to freeze at runtime.** Use `Object.freeze` when you need that.
- **Using `Object.values` on a numeric enum** and getting names and numbers mixed together.
- **Trusting external strings as `Role` without checking.** Validate with a guard like `isSize` or a schema.
- **Writing the list twice** (once as a type, once as an array). Derive the type from the array.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Styles milana**: kuch lists enums, kuch `as const`, kuch khuli strings. Har project me ek riwayat chunein.
- **`as const` se runtime par jama hone ki umeed.** Jab zaroorat ho to `Object.freeze` lein.
- **Numeric enum par `Object.values`** aur naam aur numbers mile jule milna.
- **Bahar ki strings ko baghair check `Role` maan lena.** `isSize` jaise guard ya schema se validate karein.
- **List do dafa likhna** (ek dafa type, ek dafa array). Type array se nikalein.

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- **Enums** create a type **and** generated JavaScript; numeric enums count from 0 and have reverse mappings; string enums are more readable.
- Enums aren't erasable: Node's type stripping and `erasableSyntaxOnly` reject them.
- **`as const`** keeps literal types and makes values deeply `readonly`, with no generated code.
- Union from an object: `(typeof X)[keyof typeof X]`. From an array: `(typeof X)[number]`.
- Give the type the same name as the object to use it like an enum.
- `as const satisfies SomeType` checks completeness and spelling while keeping literals.
- `as const` is compile-time only; `Object.freeze` (shallow) locks at runtime.
- Prefer readable string values for anything stored or sent over the network.

</En>

<DeepDive title="More about enums">

**`const enum`.** `const enum Dir { Up, Down }` is inlined: `Dir.Up` becomes `0` in the output and no object is generated. It saves bytes but breaks with tools that compile one file at a time (`isolatedModules`), so most projects avoid it.

**Computed and initialised members.** Numeric members can start elsewhere (`Low = 1`) or use expressions (`Read = 1 << 0, Write = 1 << 1`), which is how **bit flags** are written: `perms & Perm.Write`.

**Declaration merging.** Two `enum` blocks with the same name merge. It's rarely useful and often surprising.

**Enum types in unions.** Each member is also a type: `function f(s: Status.Paid | Status.Shipped)`.

**Iterating enums.** `Object.keys` on a numeric enum gives both numbers and names; filter with `isNaN(Number(k))`. With `as const` objects there's no such trap.

**When enums still make sense.** Large existing codebases (Angular projects use them a lot), generated API clients, and teams that like the `Enum.Member` namespace style. String enums used consistently are perfectly fine.

**`keyof typeof` vs values.** `keyof typeof Role` gives the **keys** (`"Admin"`), and indexing gives the **values** (`"ADMIN"`). Decide which one your API uses and be consistent.

</DeepDive>

<DeepDive title="Real world: the status that changed meaning overnight">

A delivery app stored order status as a numeric enum: `Created, Paid, Packed, Shipped, Delivered`, saved in the database as 0 to 4.

A developer added `Cancelled` and, wanting it near the start, wrote it right after `Created`. Every later member shifted by one. Nothing failed to compile. After the deploy, all existing "Paid" orders (stored as `1`) appeared as **Cancelled**, "Packed" orders appeared as "Paid", and the warehouse stopped packing them. Some customers received automated "your order was cancelled" emails.

The rollback fixed the display, but orders created during the bad hour had been saved with the new numbers, so they had to be fixed by hand.

Afterwards the team switched to `const ORDER_STATUSES = ["created", "paid", …] as const`, stored readable strings, added a database `CHECK` constraint listing the allowed values, and wrote a test that fails if a status is ever removed. Readable values are self-describing: the order in the list no longer matters.

</DeepDive>

<DeepDive title="Security lens">

- **Types don't validate input.** A `role: Role` parameter doesn't stop a request body from saying `"role": "SUPERADMIN"`. Check against the runtime list (`ROLES.includes(value)`) or a schema before trusting it.
- **Default-deny role checks.** `switch` on roles with an exhaustive `default` that denies access, so a new role gets **no** permissions until someone explicitly grants them.
- **Don't let clients pick privileged values.** Even a valid role like `"admin"` should never be accepted from a sign-up form; set it on the server.
- **Freeze security-relevant config** (`Object.freeze`) if third-party code runs in the same process, since `as const` won't stop runtime changes.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a numeric enum and a string enum?">
Numeric enum members get auto-incrementing numbers and a reverse mapping from number to name. String enum members have explicit string values and no reverse mapping, which makes logs and stored data readable and stable when members are reordered.
</QA>

<QA q="Why might a team avoid TypeScript enums?">
Enums are not erasable syntax: they generate runtime code, are rejected by type-stripping tools and the erasableSyntaxOnly option, numeric enums are easy to misuse, and string enums don't accept equal plain strings. An as const object or array with a derived union gives similar safety using plain JavaScript.
</QA>

<QA q="What does as const do?">
It is a const assertion that keeps literal types instead of widening them and marks all properties and array elements as readonly, turning arrays into readonly tuples. It has no runtime effect.
</QA>

<QA q="How do you get a union type of the values of an as const object?">
Use an indexed access type with keyof: the type of the object indexed by its own keys, written as typeof X indexed by keyof typeof X. For an as const array, index with number instead.
</QA>

<QA q="What is the difference between satisfies and a type annotation?">
An annotation sets the variable's type to the annotated type, so extra precision is lost. satisfies checks that the value is compatible with the type while keeping the value's own inferred, often narrower, type.
</QA>

</DeepDive>

<Terms>
  <Term name="Enum">A TypeScript construct naming a set of constants, creating both a type and a runtime object.</Term>
  <Term name="Numeric enum">An enum whose members are numbers, auto-incrementing from 0 by default.</Term>
  <Term name="String enum">An enum whose members are explicit string values.</Term>
  <Term name="Reverse mapping">The number-to-name lookup generated for numeric enums.</Term>
  <Term name="const enum">An enum whose members are inlined at compile time.</Term>
  <Term name="Const assertion">The as const syntax that keeps literal types and adds readonly.</Term>
  <Term name="Readonly tuple">A fixed-length, unchangeable array type.</Term>
  <Term name="keyof">An operator producing the union of an object type's keys.</Term>
  <Term name="Indexed access type">Looking up a property type with square brackets.</Term>
