<BigIdea>
<Tr>
<En>
So far each value had **one** type: a `number`, a `string`, a `Customer`. Real programs need more expressive labels. A **union** type, written with `|`, means **"one of these"**: `number | string` accepts either. A **literal** type is a type that allows **exactly one value**: the type `"small"` only accepts the text `"small"`. Combine the two and you get a precise menu: `"small" | "medium" | "large"`, so a typo like `"Medium"` is caught before the code runs. Give each object variant a shared `kind` field with a different literal value and you have a **discriminated union**: TypeScript can tell a card payment from a PayPal payment and knows exactly which fields each one has. Finally, an **intersection**, written with `&`, means **"all of these at once"**: it glues object types together, like an id plus timestamps plus product fields.
</En>
<Ur>
Ab tak har value ki **ek** type thi: `number`, `string`, `Customer`. Asli programs ko zyada wazeh labels chahiyen. **Union** type, jo `|` se likhi jati hai, ka matlab **"in me se koi ek"**: `number | string` dono me se koi bhi qubool karti hai. **Literal** type aisi type hai jo **sirf ek value** ki ijazat de: type `"small"` sirf text `"small"` qubool karti hai. Dono ko milayen to aap ko bilkul theek menu milta hai: `"small" | "medium" | "large"`, isliye `"Medium"` jaisi typo code chalne se pehle pakri jati hai. Har object variant ko ek mushtarka `kind` field mukhtalif literal value ke saath dein aur aap ke paas **discriminated union** hai: TypeScript card payment ko PayPal payment se alag pehchan sakti hai aur bilkul janti hai ke har ek ke paas kaun se fields hain. Aakhir me, **intersection**, jo `&` se likhi jati hai, ka matlab **"ye sab ek saath"**: ye object types ko jor deti hai, jaise id plus timestamps plus product fields.
</Ur>
</Tr>

<Why>
<Tr>
<En>

- **Data is messy**: ids from different systems, values that may be missing, API responses that are either success or error.
- **Literal unions catch typos** in statuses, sizes, roles and event names, and give you autocomplete in the editor.
- **Discriminated unions make impossible states impossible**: a card payment can't accidentally have a PayPal email.
- **Intersections let you build big types from small reusable pieces.**

</En>
<Ur>

- **Data be-tarteeb hota hai**: mukhtalif systems ki ids, values jo ghayab ho sakti hain, API responses jo ya kamyabi hain ya error.
- **Literal unions typos pakarte hain** statuses, sizes, roles aur event names me, aur editor me autocomplete dete hain.
- **Discriminated unions na-mumkin halaton ko na-mumkin banate hain**: card payment ghalti se PayPal email nahi rakh sakti.
- **Intersections chhote dobara istemal hone wale tukron se bari types banane dete hain.**

</Ur>

<How>
<Tr>
<En>

1. Write the possible types with `|` between them: `type Id = number | string`.
2. For fixed choices, list the exact values: `type Size = "small" | "medium" | "large"`.
3. For object variants, add a `kind` field with a different literal in each, then `switch (p.kind)`.
4. To combine object types, join them with `&`.

</En>
<Ur>

1. Mumkina types ke darmiyan `|` likhein: `type Id = number | string`.
2. Muqarrar choices ke liye bilkul theek values likhein: `type Size = "small" | "medium" | "large"`.
3. Object variants ke liye har ek me mukhtalif literal ke saath `kind` field jorein, phir `switch (p.kind)`.
4. Object types milane ke liye unhen `&` se jorein.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of a **coffee shop order form**.

- The **size** box isn't a free-text field. It's three tick boxes: Small, Medium, Large. That's a **union of literal types**: only those exact choices exist, so nobody can order a "Medum".
- The **payment** section says "Card / PayPal / Cash". If you tick **Card**, the form shows "last 4 digits". If you tick **PayPal**, it shows "email". Cash shows nothing extra. The ticked box is the **discriminant** (`kind`), and it decides which other fields exist: a **discriminated union**.
- The **customer id** box accepts the old numeric ids and the new ones like `A-1007`: a **union** `number | string`.
- When the order is saved, the system **staples** extra sheets onto it: an id sheet and a timestamps sheet. The saved record has everything from all the sheets at once: an **intersection**.

</En>
<Ur>

**Coffee shop ke order form** ka sochein.

- **Size** ka khana khula text field nahi. Ye teen tick boxes hain: Small, Medium, Large. Ye **literal types ka union** hai: sirf yahi choices maujood hain, isliye koi "Medum" order nahi kar sakta.
- **Payment** wala hissa kehta hai "Card / PayPal / Cash". Agar aap **Card** tick karein to form "aakhri 4 hindse" dikhata hai. **PayPal** tick karein to "email" dikhata hai. Cash kuch izafi nahi dikhata. Tick hua khana **discriminant** (`kind`) hai, aur wahi tay karta hai ke kaun se doosre fields maujood hain: **discriminated union**.
- **Customer id** ka khana purani number wali ids aur `A-1007` jaisi nayi ids dono qubool karta hai: **union** `number | string`.
- Jab order save hota hai, system us par izafi kaghaz **staple** karta hai: id wala kaghaz aur timestamps wala kaghaz. Save hue record me sab kaghazon ki har cheez ek saath hai: **intersection**.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="A union: this type or that type">

<Tr>
<En>
Put `|` between types to say "any one of these". Here, older customers have numeric ids and newer ones have text ids, and both are valid.
</En>
<Ur>
Types ke darmiyan `|` laga kar kahein "in me se koi bhi ek". Yahan purane customers ki number wali ids hain aur naye customers ki text wali, aur dono jaiz hain.
</Ur>
</Tr>

```typescript
type Id = number | string;

function showId(id: Id): string {
  return "Your id is " + id;
}

console.log(showId(42));
console.log(showId("A-1007"));

const ids: Id[] = [1, "B-2", 3];
console.log(ids.length, "ids");
```

```text output
Your id is 42
Your id is A-1007
3 ids
```

<Happened>
<Tr>
<En>

- `type Id = number | string` names the union so we can reuse it.
- `showId` accepted both a number and a string.
- `Id[]` is an array where each item may be either: `[1, "B-2", 3]` is fine.
- Joining with `+` works for both members, which is why TypeScript allowed it. Next we'll see what it **doesn't** allow.

</En>
<Ur>

- `type Id = number | string` union ko naam deta hai taa ke dobara istemal ho sake.
- `showId` ne number aur string dono qubool kiye.
- `Id[]` aisi array hai jis ka har item dono me se koi bhi ho sakta hai: `[1, "B-2", 3]` theek hai.
- `+` se jorna dono members ke liye chalta hai, isi liye TypeScript ne ijazat di. Aage dekhenge ke ye kya **nahi** karne deti.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="You can only use what every member has">

<Tr>
<En>
With a union, TypeScript only lets you do things that are safe for **every** member. `toUpperCase` exists on strings but not on numbers, so it's refused until you check which one you have.
</En>
<Ur>
Union ke saath TypeScript sirf wo kaam karne deti hai jo **har** member ke liye mehfooz ho. `toUpperCase` strings par maujood hai magar numbers par nahi, isliye jab tak aap check na karein ke aap ke paas kaun sa hai, ye mana hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Id = number | string;

function showId(id: Id) {
  return id.toUpperCase();
}

showId(true);
const n: Id = null;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(4,13): error TS2339: Property 'toUpperCase' does not exist on type 'Id'.
  Property 'toUpperCase' does not exist on type 'number'.
app.ts(7,8): error TS2345: Argument of type 'boolean' is not assignable to parameter of type 'Id'.
app.ts(8,7): error TS2322: Type 'null' is not assignable to type 'Id'.
```

<Happened>
<Tr>
<En>

- Line 4: the second line of the message explains **why**: `number` has no `toUpperCase`. If `id` were `42`, the program would crash.
- Line 7: `true` isn't a member of the union.
- Line 8: `null` isn't either. With `strict`, "nothing" must be stated: `number | string | null`.
- The fix for line 4 is **narrowing**: `if (typeof id === "string") return id.toUpperCase();`. Inside that `if`, TypeScript knows `id` is a string. The next lesson is all about this.

</En>
<Ur>

- Line 4: paighaam ki doosri line **wajah** batati hai: `number` ke paas `toUpperCase` nahi. Agar `id` `42` hota to program crash ho jata.
- Line 7: `true` union ka member nahi.
- Line 8: `null` bhi nahi. `strict` ke saath "kuch nahi" saaf likhna parta hai: `number | string | null`.
- Line 4 ka hal **narrowing** hai: `if (typeof id === "string") return id.toUpperCase();`. Us `if` ke andar TypeScript janti hai ke `id` string hai. Agla lesson poora isi ke baare me hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Literal types: a fixed menu of values">

<Tr>
<En>
A string, number or boolean **value** can be used as a type. `"small"` as a type allows only `"small"`. A union of literals is a closed list of choices, checked letter by letter.
</En>
<Ur>
String, number ya boolean **value** ko type ke taur par istemal kiya ja sakta hai. Type ke taur par `"small"` sirf `"small"` ki ijazat deta hai. Literals ka union choices ki band list hai, jo harf ba harf check hoti hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Size = "small" | "medium" | "large";
type Dice = 1 | 2 | 3 | 4 | 5 | 6;

function price(size: Size): number {
  if (size === "small") return 3;
  if (size === "medium") return 4;
  return 5;
}

price("medium");
price("Medium");
price("extra-large");

let roll: Dice = 4;
roll = 7;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(11,7): error TS2345: Argument of type '"Medium"' is not assignable to parameter of type 'Size'.
app.ts(12,7): error TS2345: Argument of type '"extra-large"' is not assignable to parameter of type 'Size'.
app.ts(15,1): error TS2322: Type '7' is not assignable to type 'Dice'.
```

<Happened>
<Tr>
<En>

- `price("medium")` passed. `"Medium"` (capital M) and `"extra-large"` were rejected: the exact kind of typo that would otherwise silently fall through to the `return 5` line and charge the wrong price.
- Number literals work the same way: a `Dice` can't be 7.
- In VS Code, typing `price("` now shows the three sizes as **autocomplete** suggestions.
- Compared with a plain `string`, the literal union documents the allowed values right in the type.

</En>
<Ur>

- `price("medium")` paas hua. `"Medium"` (bara M) aur `"extra-large"` mustarad hue: bilkul wahi typo jo warna khamoshi se `return 5` wali line tak gir kar ghalat qeemat leti.
- Number literals bhi isi tarah chalte hain: `Dice` 7 nahi ho sakta.
- VS Code me ab `price("` likhne par teeno sizes **autocomplete** mashwaron me nazar aate hain.
- Saade `string` ke muqable me literal union jaiz values ko type me hi likh deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Widening: const keeps the literal, let doesn't">

<Tr>
<En>
When TypeScript infers a type, `const x = "small"` gets the literal type `"small"` (it can never change), but `let x = "small"` gets `string` (you might reassign it). Object properties are also widened, because properties can be changed.
</En>
<Ur>
Jab TypeScript khud type nikalti hai, `const x = "small"` ko literal type `"small"` milti hai (ye kabhi badal nahi sakta), magar `let x = "small"` ko `string` milti hai (aap dobara value de sakte hain). Object properties bhi phaila di jati hain (widen), kyun ke properties badli ja sakti hain.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
const a = "small";
let b = "small";
const order = { size: "small", qty: 1 };

type Size = "small" | "medium" | "large";
function price(size: Size) { return size === "small" ? 3 : 5; }

price(a);
price(b);
price(order.size);

let c: Size = "small";
const order2: { size: Size; qty: number } = { size: "small", qty: 1 };
price(c);
price(order2.size);
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(9,7): error TS2345: Argument of type 'string' is not assignable to parameter of type 'Size'.
app.ts(10,7): error TS2345: Argument of type 'string' is not assignable to parameter of type 'Size'.
```

<Happened>
<Tr>
<En>

- `price(a)` passed: `a` is a `const`, so its type is exactly `"small"`.
- `price(b)` failed: `b` is a `let`, so TypeScript widened it to `string`, and "any string" isn't necessarily a `Size`.
- `price(order.size)` failed for the same reason: `order.size` could be changed to any string later.
- The fix is to **annotate**: `let c: Size` and `order2: { size: Size; … }` keep the narrow type. The upcoming **Enums and as const** lesson shows another tool, `as const`, that freezes literals in place.

</En>
<Ur>

- `price(a)` paas hua: `a` `const` hai, isliye us ki type bilkul `"small"` hai.
- `price(b)` fail hua: `b` `let` hai, isliye TypeScript ne use `string` tak phaila diya, aur "koi bhi string" zaroori nahi ke `Size` ho.
- `price(order.size)` isi wajah se fail hua: `order.size` baad me kisi bhi string me badla ja sakta hai.
- Hal **annotate** karna hai: `let c: Size` aur `order2: { size: Size; … }` tang type barqarar rakhte hain. Aane wala **Enums and as const** lesson ek aur auzaar, `as const`, dikhata hai jo literals ko apni jagah jama deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Nullable values: T | null">

<Tr>
<En>
"Maybe nothing" is just a union with `null` (or `undefined`). With `strict` on, TypeScript forces you to handle the "nothing" case before using the value.
</En>
<Ur>
"Shayad kuch nahi" bas `null` (ya `undefined`) ke saath union hai. `strict` on ho to TypeScript value istemal karne se pehle "kuch nahi" wali surat sambhalne par majboor karti hai.
</Ur>
</Tr>

```typescript
function findEmail(id: number): string | null {
  return id === 1 ? "sara@example.com" : null;
}

for (const id of [1, 2]) {
  const email = findEmail(id);
  console.log(id, email === null ? "no email" : email.toUpperCase());
}
```

```text output
1 SARA@EXAMPLE.COM
2 no email
```

<Happened>
<Tr>
<En>

- The return type `string | null` is honest: callers can see "this might not find anything".
- Calling `email.toUpperCase()` **without** the check gives `error TS18047: 'email' is possibly 'null'.` That's the error that prevents the famous "Cannot read properties of null" crash.
- After `email === null ? … :`, the other branch knows `email` is a `string`.
- Choose one convention: many teams use `null` for "deliberately empty" and `undefined` for "not set".

</En>
<Ur>

- Return type `string | null` imaandar hai: call karne wale dekh sakte hain ke "shayad ise kuch na mile".
- Check ke **baghair** `email.toUpperCase()` call karne par `error TS18047: 'email' is possibly 'null'.` aata hai. Yahi error mashhoor "Cannot read properties of null" crash se bachata hai.
- `email === null ? … :` ke baad doosri shaakh janti hai ke `email` `string` hai.
- Ek riwayat chunein: bohot si teams "jaan boojh kar khaali" ke liye `null` aur "set nahi hua" ke liye `undefined` istemal karti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Discriminated unions: variants told apart by kind">

<Tr>
<En>
Give each object variant a field with the **same name** but a **different literal value** (here `kind`). TypeScript uses that field to know exactly which variant you have, and therefore which other fields exist.
</En>
<Ur>
Har object variant ko **ek hi naam** ka magar **mukhtalif literal value** wala field dein (yahan `kind`). TypeScript ye field istemal kar ke bilkul janti hai ke aap ke paas kaun sa variant hai, aur isliye kaun se doosre fields maujood hain.
</Ur>
</Tr>

```typescript
type Card = { kind: "card"; last4: string };
type PayPal = { kind: "paypal"; email: string };
type Cash = { kind: "cash" };
type Payment = Card | PayPal | Cash;

function describe(p: Payment): string {
  switch (p.kind) {
    case "card":
      return "Card ending in " + p.last4;
    case "paypal":
      return "PayPal account " + p.email;
    case "cash":
      return "Cash on delivery";
  }
}

const payments: Payment[] = [
  { kind: "card", last4: "4242" },
  { kind: "paypal", email: "sara@example.com" },
  { kind: "cash" },
];
for (const p of payments) console.log(describe(p));
```

```text output
Card ending in 4242
PayPal account sara@example.com
Cash on delivery
```

<Happened>
<Tr>
<En>

- Inside `case "card":` TypeScript knows `p` is a `Card`, so `p.last4` is allowed. Inside `case "paypal":` it's a `PayPal`, so `p.email` is allowed.
- `Cash` has no extra fields at all, and that's fine.
- This pattern is everywhere: Redux actions (`type`), API results (`status: "success" | "error"`), UI states (`"loading" | "ready" | "failed"`), shapes in a drawing app.
- The field name doesn't matter (`kind`, `type`, `tag`), as long as every variant has it with a unique literal.

</En>
<Ur>

- `case "card":` ke andar TypeScript janti hai ke `p` `Card` hai, isliye `p.last4` ki ijazat hai. `case "paypal":` ke andar ye `PayPal` hai, isliye `p.email` ki ijazat hai.
- `Cash` ke paas koi izafi field nahi, aur ye theek hai.
- Ye pattern har jagah hai: Redux actions (`type`), API nataij (`status: "success" | "error"`), UI halaten (`"loading" | "ready" | "failed"`), drawing app me shakalen.
- Field ka naam ahem nahi (`kind`, `type`, `tag`), bas har variant ke paas ho aur us ka literal munfarid ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What the discriminant protects you from">

<Tr>
<En>
The checker stops you mixing variants, inventing new ones, and forgetting to handle one.
</En>
<Ur>
Checker aap ko variants milane, naye gharne, aur kisi ko sambhalna bhoolne se rokta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Card = { kind: "card"; last4: string };
type PayPal = { kind: "paypal"; email: string };
type Payment = Card | PayPal;

function bad(p: Payment) {
  return p.email;
}
function good(p: Payment) {
  if (p.kind === "paypal") return p.email;
  return p.last4;
}
const x: Payment = { kind: "card", email: "a@example.com" };
const y: Payment = { kind: "crypto", last4: "1" };
EOF
npx tsc --noEmit --strict app.ts

type Card = { kind: "card"; last4: string };

type GiftCard = { kind: "gift"; code: string };

  switch (p.kind) {
    case "card":
      return "Card ending in " + p.last4;
    case "paypal":
```

<Tr>

- `bad` ne kind check kiye baghair `p.email` parha: card ke paas email nahi. `good` pehle check karta hai, aur `if (p.kind === "paypal") return …` ke baad TypeScript janti hai ke function ka baqi hissa sirf `Card` dekhta hai.

<Step title="Intersection: everything at once">

<Tr>
<En>
`A & B` is a type that has **all** the properties of A **and** all of B. It's the natural way to build a big object type from small reusable pieces.
</En>
<Ur>
`A & B` aisi type hai jis ke paas A ki **tamam** properties **aur** B ki tamam properties hon. Chhote dobara istemal hone wale tukron se bari object type banane ka ye qudrati tareeqa hai.
</Ur>
</Tr>

```typescript
type HasId = { id: number };
type HasTimestamps = { createdAt: string; updatedAt: string };
type Product = { name: string; price: number };

type ProductRecord = HasId & HasTimestamps & Product;

const mug: ProductRecord = {
  id: 7,
  name: "Mug",
  price: 12,
  createdAt: "2026-01-05",
  updatedAt: "2026-03-18",
};

function summary(p: ProductRecord): string {
  return "#" + p.id + " " + p.name + " $" + p.price + " (updated " + p.updatedAt + ")";
}
console.log(summary(mug));
```

```text output
#7 Mug $12 (updated 2026-03-18)
```

<Happened>
<Tr>
<En>

- `ProductRecord` requires all five properties: `id`, `createdAt`, `updatedAt`, `name`, `price`.
- `HasId` and `HasTimestamps` can be reused for users, orders and invoices too. That's what makes intersections useful.
- With interfaces you'd write `interface ProductRecord extends HasId, HasTimestamps, Product {}`. Both give the same result for plain objects.

</En>
<Ur>

- `ProductRecord` ko paanchon properties chahiyen: `id`, `createdAt`, `updatedAt`, `name`, `price`.
- `HasId` aur `HasTimestamps` users, orders aur invoices ke liye bhi dobara istemal ho sakti hain. Yahi intersections ko kaam ka banata hai.
- Interfaces ke saath aap `interface ProductRecord extends HasId, HasTimestamps, Product {}` likhte. Saade objects ke liye dono ka nateeja ek jaisa hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Intersections that can't exist become never">

<Tr>
<En>
An intersection must satisfy **every** part. If the parts contradict each other, no value can satisfy them, and the type collapses to `never`.
</En>
<Ur>
Intersection ko **har** hissa poora karna hota hai. Agar hisse ek doosre se takrayen to koi value unhen poora nahi kar sakti, aur type `never` me badal jati hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type HasId = { id: number };
type Product = { name: string; price: number };
type ProductRecord = HasId & Product;

const pen: ProductRecord = { id: 8, name: "Pen" };

type A = { code: string };
type B = { code: number };
type AB = A & B;
const weird: AB = { code: "X1" };

type Impossible = "card" & "cash";
const nope: Impossible = "card";
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,7): error TS2322: Type '{ id: number; name: string; }' is not assignable to type 'ProductRecord'.
  Property 'price' is missing in type '{ id: number; name: string; }' but required in type 'Product'.
app.ts(10,21): error TS2322: Type 'string' is not assignable to type 'never'.
app.ts(13,7): error TS2322: Type '"card"' is not assignable to type 'never'.
```

<Happened>
<Tr>
<En>

- `pen` forgot `price`, and the message even says which piece (`Product`) required it.
- In `AB`, `code` must be a string **and** a number at the same time. Nothing is both, so `code` becomes `never`.
- `"card" & "cash"` is a value that is exactly "card" **and** exactly "cash": impossible, so `never`.
- A surprise `never` in an error message usually means an intersection with conflicting parts.

</En>
<Ur>

- `pen` `price` bhool gaya, aur paighaam ye bhi batata hai ke kis tukre (`Product`) ko is ki zaroorat thi.
- `AB` me `code` ko ek hi waqt me string **aur** number hona hai. Koi cheez dono nahi, isliye `code` `never` ban jata hai.
- `"card" & "cash"` aisi value hai jo bilkul "card" **aur** bilkul "cash" ho: na-mumkin, isliye `never`.
- Error paighaam me achanak `never` aam taur par takrate hisson wale intersection ki nishani hai.

</Ur>
</Tr>
</Happened>

<Step title="Unions of arrays and template literal types">

<Tr>
<En>
Two more tools. **Where** you put the `|` matters for arrays. And **template literal types** build string unions from other unions, with the same backtick syntax as JavaScript template strings.
</En>
<Ur>
Do mazeed auzaar. Arrays ke liye `|` **kahan** lagaya ye ahem hai. Aur **template literal types** doosre unions se string unions banati hain, JavaScript template strings jaise backtick syntax ke saath.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Mixed = (number | string)[];
type Either = number[] | string[];

const m: Mixed = [1, "two", 3];
const e1: Either = [1, 2, 3];
const e2: Either = [1, "two", 3];

type Side = "top" | "bottom";
type Align = "left" | "right";
type Corner = `${Side}-${Align}`;
const c1: Corner = "top-left";
const c2: Corner = "left-top";
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(6,7): error TS2322: Type '(string | number)[]' is not assignable to type 'Either'.
  Type '(string | number)[]' is not assignable to type 'string[]'.
    Type 'string | number' is not assignable to type 'string'.
      Type 'number' is not assignable to type 'string'.
app.ts(12,7): error TS2322: Type '"left-top"' is not assignable to type '"top-left" | "top-right" | "bottom-left" | "bottom-right"'.
```

<Happened>
<Tr>
<En>

- `(number | string)[]` is **one array with mixed items**. `number[] | string[]` is **either an all-number array or an all-string array**. `e2` mixes them, so it's rejected.
- Long error messages are nested: each indented line goes one level deeper into **why**. Read the last line first: `number` isn't `string`.
- `Corner` expanded into every combination: 2 × 2 = 4 strings. `"left-top"` is the wrong order, so it's caught.
- Template literal types are handy for CSS class names, event names (`"click" | "hover"` → `` `on${Capitalize<…>}` ``) and route strings.

</En>
<Ur>

- `(number | string)[]` **mili juli items wali ek array** hai. `number[] | string[]` **ya poori number wali array ya poori string wali array** hai. `e2` dono milata hai, isliye mustarad hai.
- Lambe error paighaam tah dar tah hote hain: har andar ko khiski line **wajah** me ek darja aur gehra jati hai. Aakhri line pehle parhein: `number` `string` nahi.
- `Corner` har combination me phail gaya: 2 × 2 = 4 strings. `"left-top"` ghalat tarteeb hai, isliye pakra gaya.
- Template literal types CSS class names, event names (`"click" | "hover"` → `` `on${Capitalize<…>}` ``) aur route strings ke liye kaam ki hain.

## Common mistakes

<Compare>
<Bad title="Plain string for a fixed set of values">

```bash
cat > app.ts <<'EOF'
type Order = { id: number; status: string };
const o: Order = { id: 1, status: "shiped" };
console.log("no error, typo saved to the database:", o.status);
EOF
npx tsc --noEmit --strict app.ts && echo "tsc: no errors"
```

```text output
tsc: no errors
```

</Bad>
<Good title="A literal union catches the typo">

```bash
cat > app.ts <<'EOF'
type Status = "pending" | "shipped" | "delivered";
type Order = { id: number; status: Status };
const o: Order = { id: 1, status: "shiped" };
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(3,27): error TS2820: Type '"shiped"' is not assignable to type 'Status'. Did you mean '"shipped"'?
```

</Good>
</Compare>

<Compare>
<Bad title="Optional fields instead of variants">

```text
type Payment = {
  method: "card" | "paypal";
  last4?: string;   // only for cards… but nothing enforces it
  email?: string;   // only for PayPal… but nothing enforces it
};
// { method: "card", email: "x@example.com" } is allowed, and so is
// { method: "paypal" } with no email at all
```

</Bad>
<Good title="One variant per case">

```text
type Payment =
  | { method: "card"; last4: string }
  | { method: "paypal"; email: string };
// each method has exactly the fields it needs, and they're required
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Using a union member's method without checking** (`id.toUpperCase()` on `number | string`). Narrow first.
- **Confusing `|` and `&`**: for object types, `A | B` is "one of them" (fewer guaranteed properties), `A & B` is "both" (more properties).
- **Expecting `let` to keep a literal type.** Annotate it, or use `const`.
- **Forgetting `null` in the return type** of functions that can find nothing, which hides the "not found" case from callers.
- **A discriminant that isn't a literal** (`kind: string`): TypeScript can't use it to tell variants apart.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Check kiye baghair union member ka method istemal karna** (`number | string` par `id.toUpperCase()`). Pehle narrow karein.
- **`|` aur `&` me ulajhna**: object types ke liye `A | B` "in me se ek" hai (kam yaqeeni properties), `A & B` "dono" hai (zyada properties).
- **`let` se literal type barqarar rehne ki umeed.** Annotate karein, ya `const` lein.
- **Kuch na dhoondh paane wale functions ki return type me `null` bhool jana**, jo call karne walon se "nahi mila" ki surat chhupa deta hai.
- **Aisa discriminant jo literal na ho** (`kind: string`): TypeScript is se variants alag nahi kar sakti.

</Ur>
</Tr>

```typescript
type UserState =

    case "loading":
```

## Remember

<Takeaways>
<Tr>
<En>

- `A | B` (union) = **one of** these; you can only use what **every** member has until you narrow.
- A **literal type** allows exactly one value; a **union of literals** is a fixed menu that catches typos and gives autocomplete.
- `const` keeps literal types; `let` and object properties **widen** to `string`/`number` unless annotated.
- "Maybe nothing" is `T | null` or `T | undefined`.
- **Discriminated unions**: object variants with a shared literal field (`kind`), handled with `switch`; TypeScript knows each variant's fields.
- `A & B` (intersection) = **all of** these at once; great for combining small object types; contradictions become `never`.
- `(A | B)[]` is a mixed array; `A[] | B[]` is one or the other. Template literal types build string unions.

</En>
<Ur>

- `A | B` (union) = in me se **koi ek**; narrow karne tak sirf wahi istemal kar sakte hain jo **har** member ke paas ho.
- **Literal type** sirf ek value ki ijazat deti hai; **literals ka union** muqarrar menu hai jo typos pakarta aur autocomplete deta hai.
- `const` literal types barqarar rakhta hai; `let` aur object properties annotate na hon to `string`/`number` tak **phail** jati hain.
- "Shayad kuch nahi" `T | null` ya `T | undefined` hai.
- **Discriminated unions**: mushtarka literal field (`kind`) wale object variants, `switch` se sambhale jate hain; TypeScript har variant ke fields janti hai.
- `A & B` (intersection) = ye **sab** ek saath; chhoti object types milane ke liye behtareen; takrao `never` ban jata hai.
- `(A | B)[]` mili juli array hai; `A[] | B[]` ek ya doosri. Template literal types string unions banati hain.

</Ur>
</Tr>
</Takeaways>

<DeepDive title="More about unions and intersections">

**Unions of object types and common properties.** For `Pet | Fish` where both have `name`, `x.name` is allowed because every member has it. Properties that only some members have are not accessible until you narrow (with `in`, `kind` checks and so on).

**Unions vs intersections as sets.** Think of a type as the set of values it allows. A union is the **combined** set (more values allowed, fewer guaranteed properties). An intersection is the **overlap** (fewer values allowed, more guaranteed properties). That's why `A & B` for object types has *more* properties.

**`&` vs `extends`.** `interface C extends A, B {}` reports a clear error if A and B conflict, while `A & B` silently produces `never` for the conflicting property. Interfaces can also be faster for the checker in very large codebases. For small types, pick whichever reads better.

**Distributive behaviour.** Many type operations apply to each union member separately: a template literal type with two unions of 2 members makes 4 strings. Watch out for huge cross products: TypeScript limits a union to about 100,000 members.

**Literal types beyond strings.** `true`/`false` are literals (`boolean` is just `true | false`). Numeric literals are useful for fixed values like HTTP codes: `200 | 201 | 204`.

**Branded types (preview).** `type UserId = string & { __brand: "UserId" }` makes two kinds of string ids incompatible, so you can't pass an order id where a user id is expected. It's a common intersection trick.

</DeepDive>

<DeepDive title="Real world: the order that was 'shiped'">

An online shop stored order status as a plain `string`. One endpoint set `status: "shiped"` (one p). Nothing crashed. The warehouse dashboard filtered for `"shipped"`, so those orders simply vanished from every list. Customers emailed asking where their packages were, and support couldn't find the orders.

The fix took two parts:

1. `type OrderStatus = "pending" | "paid" | "shipped" | "delivered" | "cancelled"`, used in every function, the database model and the API response type. The compiler immediately flagged the typo, with a "Did you mean" suggestion.
2. The UI's status badge became a `switch` on the status. When the team later added `"refunded"`, the compiler listed every switch that didn't handle it yet.

The same idea protects roles (`"admin" | "editor"`), feature flags, event names and country codes. If a value comes from a fixed list, its type should say so.

</DeepDive>

<DeepDive title="Security lens">

- **Types don't exist at runtime.** A `role: "admin" | "viewer"` type doesn't stop a request body containing `"role": "superuser"`. Validate external input at runtime (the **Typing APIs and External Data (zod)** lesson) before trusting it as a union.
- **Discriminated unions make permission states explicit**: `{ kind: "guest" } | { kind: "user"; id } | { kind: "admin"; id }` forces code to check which one it has before using an id.
- **Avoid optional-field bags for security decisions**: `{ isAdmin?: boolean; userId?: string }` allows "admin with no user". A union makes such impossible combinations unrepresentable.
- **Exhaustive handling of states** (next lesson) means a new status like `"suspended"` can't slip through code paths that grant access by default.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a union and an intersection type?">
A union means a value is one of the member types, so you can only use what all members share until you narrow. An intersection means a value satisfies all member types at once, so for object types it has all of their properties combined.
</QA>

<QA q="What is a discriminated union and why is it useful?">
It is a union of object types that each have a common property with a distinct literal value, such as kind. Checking that property narrows the value to one variant, so TypeScript knows exactly which other properties exist, and it can check that every variant is handled.
</QA>

<QA q="What is literal type widening?">
When TypeScript infers a type for a mutable location such as a let variable or an object property, it widens a literal like 'small' to its general type string. A const variable keeps the literal type because it can never change. Annotations or as const prevent widening.
</QA>

<QA q="When does an intersection become never?">
When its parts are contradictory, such as two different string literals, or object types whose shared property has incompatible types. No value can satisfy all parts, so the type, or that property, becomes never.
</QA>

<QA q="What is the difference between (string | number)[] and string[] | number[]?">
The first is an array whose individual elements can each be a string or a number. The second is either an array of only strings or an array of only numbers.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Union type">A type allowing values of any one of several member types.</Term>
  <Term name="Intersection type">A type combining all members, requiring every property of each.</Term>
  <Term name="Literal type">A type that allows exactly one specific value.</Term>
  <Term name="Widening">Inferring a general type such as string from a literal for mutable locations.</Term>
  <Term name="Discriminant">The shared literal property used to tell union variants apart.</Term>
  <Term name="Discriminated union">A union of object types distinguished by a discriminant.</Term>
  <Term name="never">The empty type, with no possible values.</Term>
  <Term name="Nullable type">A union that includes null or undefined.</Term>
  <Term name="Template literal type">A string type built by combining other string literal types.</Term>
  <Term name="Branded type">An intersection with a marker property to make similar types incompatible.</Term>
</Terms>
