<BigIdea>
<Tr>
<En>
So far you've **written** types by hand. Now you'll **compute** them from other types. A **mapped type** is a loop over keys: `{ [K in keyof User]: boolean }` means "for every key of `User`, make a property with that same name, typed `boolean`". Add `?` or `readonly` (or remove them with `-`) and you've rebuilt `Partial`, `Required` and `Readonly`. Add `as` and you can **rename** keys (`name` → `getName`) or **drop** them. A **conditional type** is an if/else for types: `T extends string ? "yes" : "no"`. Inside it, `infer` lets you **pull out** a piece of another type, like the item type of an array or the value inside a `Promise`. Together they let one change to a source type (adding a field to `User`) flow automatically into every derived type: form errors, update payloads, event handler maps. You won't write these every day, but you'll read them in libraries constantly, and a few well-placed ones remove a lot of duplication.
</En>
<Ur>
Ab tak aap ne types haath se **likhi** hain. Ab aap unhen doosri types se **hisaab** kar ke banayenge. **Mapped type** keys par ek loop hai: `{ [K in keyof User]: boolean }` ka matlab "`User` ki har key ke liye usi naam ki property banao, jis ki type `boolean` ho". `?` ya `readonly` jorein (ya `-` se hatayen) aur aap ne `Partial`, `Required` aur `Readonly` dobara bana liye. `as` jorein aur aap keys ka **naam badal** sakte hain (`name` → `getName`) ya unhen **nikal** sakte hain. **Conditional type** types ke liye if/else hai: `T extends string ? "yes" : "no"`. Is ke andar `infer` aap ko doosri type ka ek tukra **bahar nikalne** deta hai, jaise array ke item ki type ya `Promise` ke andar ki value. Mil kar ye source type me ek tabdeeli (`User` me field jorna) ko khud ba khud har nikli hui type tak pohancha dete hain: form errors, update payloads, event handler maps. Aap ye rozana nahi likhenge, magar libraries me inhen musalsal parhenge, aur sahi jagah lagi chand types bohot si dohrai khatam kar deti hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

| Pattern | Syntax | Example result |
| --- | --- | --- |
| Map every key | `{ [K in keyof T]: X }` | every property becomes `X` |
| Keep the property's type | `{ [K in keyof T]: T[K] }` | a copy of `T` |
| Make optional / required | `?` / `-?` | `Partial` / `Required` |
| Add / remove readonly | `readonly` / `-readonly` | `Readonly` / mutable copy |
| Rename keys | `` [K in keyof T as `get${Capitalize<…>}`] `` | `getName`, `getPrice` |
| Drop keys | `as … ? K : never` | only number fields |
| Conditional type | `T extends U ? X : Y` | pick a type by a test |
| Extract a part | `T extends (infer I)[] ? I : T` | item type of an array |
| Distribution | conditional on a naked `T` | runs once per union member |

</En>
<Ur>

| Pattern | Syntax | Misali nateeja |
| --- | --- | --- |
| Har key map karo | `{ [K in keyof T]: X }` | har property `X` ban jati hai |
| Property ki type rakho | `{ [K in keyof T]: T[K] }` | `T` ki copy |
| Ikhtiyari / zaroori banao | `?` / `-?` | `Partial` / `Required` |
| readonly jorna / hatana | `readonly` / `-readonly` | `Readonly` / badalne wali copy |
| Keys ka naam badlo | `` [K in keyof T as `get${Capitalize<…>}`] `` | `getName`, `getPrice` |
| Keys nikalo | `as … ? K : never` | sirf number wale fields |
| Conditional type | `T extends U ? X : Y` | test se type chuno |
| Hissa nikalo | `T extends (infer I)[] ? I : T` | array ke item ki type |
| Distribution | khule `T` par conditional | har union member ke liye ek dafa |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **No duplication**: derive "form errors", "update payload" and "flags" types from one source type instead of retyping fields.
- **Changes flow automatically**: add a field to `User` and every derived type picks it up, and the compiler shows code that needs updating.
- **Reading library types**: React, Prisma, tRPC and zod are full of mapped and conditional types.
- **Understanding utility types**: `Partial`, `Pick`, `Record`, `Exclude` and `ReturnType` are just a few lines each.

</En>
<Ur>

- **Koi dohrai nahi**: fields dobara likhne ke bajaye ek source type se "form errors", "update payload" aur "flags" types nikalein.
- **Tabdeeliyan khud pohanchti hain**: `User` me field jorein aur har nikli type use le leti hai, aur compiler wo code dikhata hai jise update karna hai.
- **Library types parhna**: React, Prisma, tRPC aur zod mapped aur conditional types se bhare hain.
- **Utility types samajhna**: `Partial`, `Pick`, `Record`, `Exclude` aur `ReturnType` har ek bas chand lines hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| You need | Reach for |
| --- | --- |
| "same keys, different value type" | mapped type |
| "same object, all optional / read-only" | built-in `Partial` / `Readonly` first |
| "only the keys whose values are numbers" | mapped type with `as` filter |
| "the type inside an array / promise / function" | conditional type with `infer` (or `Awaited`, `ReturnType`) |
| "remove some members from a union" | `Exclude` (a distributive conditional) |
| A one-off object shape | just write it; don't over-engineer |

</En>
<Ur>

| Aap ko chahiye | Ye lein |
| --- | --- |
| "wahi keys, mukhtalif value type" | mapped type |
| "wahi object, sab ikhtiyari / read-only" | pehle bana banaya `Partial` / `Readonly` |
| "sirf wo keys jin ki values numbers hain" | `as` filter wala mapped type |
| "array / promise / function ke andar ki type" | `infer` wala conditional type (ya `Awaited`, `ReturnType`) |
| "union se kuch members hatana" | `Exclude` (distributive conditional) |
| Ek dafa ki object shakal | bas likh dein; zaroorat se zyada mat banayen |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Start from the source type: `type User = { … }`.
2. Write the loop: `type X<T> = { [K in keyof T]: … }`.
3. Decide each property's new type, using `T[K]` for "the original type".
4. Check the result by assigning a sample object and reading tsc's errors (or hover in the editor).

</En>
<Ur>

1. Source type se shuru karein: `type User = { … }`.
2. Loop likhein: `type X<T> = { [K in keyof T]: … }`.
3. Har property ki nayi type tay karein, "asal type" ke liye `T[K]` istemal kar ke.
4. Ek namoona object de kar aur tsc ke errors parh kar (ya editor me hover kar ke) nateeja check karein.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **spreadsheet** of customer fields: `id`, `name`, `email`.

- A **mapped type** is filling a new column next to every row with a formula. "For every field, add a checkbox" gives `{ id: boolean; name: boolean; email: boolean }`. If someone adds a `phone` row, the formula fills it in automatically.
- **`?` and `readonly`** are like marking every row in the new column "optional" or "locked".
- **Key remapping (`as`)** is a formula on the row **names**: "for `name`, make a row called `getName`". Returning `never` from that formula **hides the row**.
- A **conditional type** is an `IF()` formula: `IF(type is number, "show in totals", "skip")`.
- **`infer`** is like a formula that reads **inside** a cell: "this cell holds a list of prices; give me the type of one price".

</En>
<Ur>

Customer fields ki ek **spreadsheet** ka sochein: `id`, `name`, `email`.

- **Mapped type** har row ke saath formula se ek naya column bharna hai. "Har field ke liye checkbox jorein" se `{ id: boolean; name: boolean; email: boolean }` milta hai. Agar koi `phone` ki row jore, formula use khud bhar deta hai.
- **`?` aur `readonly`** naye column ki har row ko "ikhtiyari" ya "band" nishaan zad karne jaise hain.
- **Key remapping (`as`)** row ke **naamon** par formula hai: "`name` ke liye `getName` naam ki row banao". Us formula se `never` wapas karna **row chhupa** deta hai.
- **Conditional type** `IF()` formula hai: `IF(type number hai, "totals me dikhao", "chhor do")`.
- **`infer`** aisa formula hai jo cell ke **andar** parhta hai: "is cell me prices ki list hai; mujhe ek price ki type do".

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **`keyof T`** | Union of `T`'s keys | `"id" \| "name"` |
| **`T[K]`** | Type of property `K` in `T` | `User["name"]` is `string` |
| **Mapped type** | A type built by looping over keys | `{ [K in keyof T]: … }` |
| **`in`** (in a type) | "for each member of this union" | `[K in "a" \| "b"]` |
| **Modifier** | `readonly` or `?` on a property | `readonly id` |
| **`-?`, `-readonly`** | Remove a modifier | `Required`, mutable |
| **Key remapping** | `as` clause renaming or filtering keys | `` as `get${…}` `` |
| **Conditional type** | `A extends B ? X : Y` | `IsString<T>` |
| **`infer`** | Declare a type variable to capture inside a conditional | `infer Item` |
| **Distributive** | Conditional applied to each union member separately | `Exclude` |
| **`Capitalize`** | Built-in string type helper | `Capitalize<"name">` is `"Name"` |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **`keyof T`** | `T` ki keys ka union | `"id" \| "name"` |
| **`T[K]`** | `T` me property `K` ki type | `User["name"]` `string` hai |
| **Mapped type** | Keys par loop se bani type | `{ [K in keyof T]: … }` |
| **`in`** (type me) | "is union ke har member ke liye" | `[K in "a" \| "b"]` |
| **Modifier** | Property par `readonly` ya `?` | `readonly id` |
| **`-?`, `-readonly`** | Modifier hatana | `Required`, badalne wala |

| **`infer`** | Conditional ke andar pakarne ke liye type variable | `infer Item` |
| **Distributive** | Har union member par alag lagne wala conditional | `Exclude` |
| **`Capitalize`** | Bana banaya string type helper | `Capitalize<"name">` `"Name"` hai |

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Your first mapped type">

<Tr>
<En>
`[K in keyof T]` loops over every key of `T`. Whatever you write after the colon becomes that key's type. Here every field of `User` becomes a `boolean` ("was this field changed?").
</En>
<Ur>
`[K in keyof T]` `T` ki har key par loop chalata hai. Colon ke baad jo likhein wo us key ki type ban jati hai. Yahan `User` ka har field `boolean` ban jata hai ("kya ye field badla?").
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type User = { id: number; name: string; email: string };

type Flags<T> = { [K in keyof T]: boolean };
type UserFlags = Flags<User>;

const changed: UserFlags = { id: false, name: true, email: "yes" };
const partial: UserFlags = { name: true };
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(6,53): error TS2322: Type 'string' is not assignable to type 'boolean'.
app.ts(7,7): error TS2739: Type '{ name: true; }' is missing the following properties from type 'Flags<User>': id, email
```

<Happened>
<Tr>
<En>

- `Flags<User>` became `{ id: boolean; name: boolean; email: boolean }`: same keys, new value type.
- Line 6: `email: "yes"` isn't a boolean. Line 7: every key is required, so `id` and `email` are missing.
- `Flags` is generic: `Flags<Product>` would work just as well. Add a `phone` field to `User` and `UserFlags` gets `phone: boolean` automatically.

</En>
<Ur>

- `Flags<User>` `{ id: boolean; name: boolean; email: boolean }` ban gaya: wahi keys, nayi value type.
- Line 6: `email: "yes"` boolean nahi. Line 7: har key zaroori hai, isliye `id` aur `email` ghayab hain.
- `Flags` generic hai: `Flags<Product>` bhi bilkul chalega. `User` me `phone` field jorein aur `UserFlags` ko khud `phone: boolean` mil jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Keep the original types: T[K]">

<Tr>
<En>
Usually you want each property's **original** type. `T[K]` means "the type of key `K` in `T`". With modifiers you can rebuild the built-in helpers: `?` makes properties optional, `-?` removes optional, `-readonly` removes read-only.
</En>
<Ur>
Aam taur par aap har property ki **asal** type chahte hain. `T[K]` ka matlab "`T` me key `K` ki type". Modifiers ke saath aap bane banaye helpers dobara bana sakte hain: `?` properties ko ikhtiyari karta hai, `-?` ikhtiyari hatata hai, `-readonly` read-only hatata hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type User = { readonly id: number; name: string; nickname?: string };

type MyPartial<T> = { [K in keyof T]?: T[K] };
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Complete<T> = { [K in keyof T]-?: T[K] };

const draft: MyPartial<User> = { name: "Sara" };
const m: Mutable<User> = { id: 1, name: "Sara" };
m.id = 2;
const c: Complete<User> = { id: 1, name: "Sara" };
const u: User = { id: 1, name: "Sara" };
u.id = 2;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(10,7): error TS2741: Property 'nickname' is missing in type '{ id: number; name: string; }' but required in type 'Complete<User>'.
app.ts(12,3): error TS2540: Cannot assign to 'id' because it is a read-only property.
```

<Happened>
<Tr>
<En>

- `MyPartial<User>` accepted `{ name: "Sara" }`: every key became optional. That's exactly how the built-in `Partial` is written.
- `Mutable<User>` allowed `m.id = 2` (line 9) because `-readonly` removed the lock. On the original `User`, line 12 is refused.
- `Complete<User>` used `-?`, so `nickname` became required (line 10). The built-in version is `Required`.

</En>
<Ur>

- `MyPartial<User>` ne `{ name: "Sara" }` qubool kiya: har key ikhtiyari ban gayi. Bana banaya `Partial` bilkul isi tarah likha gaya hai.
- `Mutable<User>` ne `m.id = 2` (line 9) ki ijazat di kyun ke `-readonly` ne taala hata diya. Asal `User` par line 12 mustarad hai.
- `Complete<User>` ne `-?` istemal kiya, isliye `nickname` zaroori ban gaya (line 10). Bana banaya version `Required` hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A practical mapped type: form errors">

<Tr>
<En>
A form's error object has the **same keys** as the form, but each value is an optional error message. Deriving it means the two can never drift apart.
</En>
<Ur>
Form ke error object ki **wahi keys** hoti hain jo form ki, magar har value ikhtiyari error paighaam hoti hai. Ise nikalne ka matlab dono kabhi ek doosre se door nahi ho sakte.
</Ur>
</Tr>

```typescript
type SignupForm = { name: string; email: string; age: number };
type FormErrors<T> = { [K in keyof T]?: string };

function validate(form: SignupForm): FormErrors<SignupForm> {
  const errors: FormErrors<SignupForm> = {};
  if (form.name.trim() === "") errors.name = "Name is required";
  if (!form.email.includes("@")) errors.email = "Email looks wrong";
  if (form.age < 13) errors.age = "You must be 13 or older";
  return errors;
}

console.log(validate({ name: "Sara", email: "sara@example.com", age: 29 }));
console.log(validate({ name: " ", email: "sara.example.com", age: 9 }));
```

```text output
{}
{
  name: 'Name is required',
  email: 'Email looks wrong',
  age: 'You must be 13 or older'
}
```

<Happened>
<Tr>
<En>

- `FormErrors<SignupForm>` is `{ name?: string; email?: string; age?: string }`. Notice `age` is a **number** in the form but its error is a **string**: mapped types don't have to keep the original type.
- A typo like `errors.emial = …` would be a compile error.
- Add a `password` field to `SignupForm` and `errors.password` becomes available immediately.

</En>
<Ur>

- `FormErrors<SignupForm>` `{ name?: string; email?: string; age?: string }` hai. Dhyan dein `age` form me **number** hai magar us ka error **string** hai: mapped types ke liye asal type rakhna zaroori nahi.
- `errors.emial = …` jaisi typo compile error hogi.
- `SignupForm` me `password` field jorein aur `errors.password` foran dastiyab ho jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Renaming keys with as">

<Tr>
<En>
After the loop you can add `as` and a new name. Template literal types build it: for key `name`, `` `get${Capitalize<K>}` `` gives `getName`. (`string & K` keeps only string keys, since `keyof` can also include numbers and symbols.)
</En>
<Ur>
Loop ke baad aap `as` aur naya naam jor sakte hain. Template literal types use banati hain: key `name` ke liye `` `get${Capitalize<K>}` `` `getName` deta hai. (`string & K` sirf string keys rakhta hai, kyun ke `keyof` me numbers aur symbols bhi ho sakte hain.)
</Ur>
</Tr>

```typescript
type Product = { name: string; price: number; inStock: boolean };

type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K];
};

function makeGetters(p: Product): Getters<Product> {
  return {
    getName: () => p.name,
    getPrice: () => p.price,
    getInStock: () => p.inStock,
  };
}

const g = makeGetters({ name: "Lamp", price: 30, inStock: true });
console.log(g.getName(), g.getPrice(), g.getInStock());
```

```text output
Lamp 30 true
```

<Happened>
<Tr>
<En>

- `Getters<Product>` is `{ getName: () => string; getPrice: () => number; getInStock: () => boolean }`. Each getter returns the **original** type thanks to `T[K]`.
- If `makeGetters` forgot one, TypeScript would say: `missing the following properties from type 'Getters<Product>': getInStock, getPrice`.
- `Capitalize`, `Uncapitalize`, `Uppercase` and `Lowercase` are built-in helpers for string types.

</En>
<Ur>

- `Getters<Product>` `{ getName: () => string; getPrice: () => number; getInStock: () => boolean }` hai. `T[K]` ki badolat har getter **asal** type wapas karta hai.
- Agar `makeGetters` koi bhool jata, TypeScript kehti: `missing the following properties from type 'Getters<Product>': getInStock, getPrice`.
- `Capitalize`, `Uncapitalize`, `Uppercase` aur `Lowercase` string types ke bane banaye helpers hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Typed event handlers">

<Tr>
<En>
Renaming keys shines for event systems: one map of event names to payloads generates the `onClick`, `onSubmit` handler props, each with the right payload type.
</En>
<Ur>
Keys ka naam badalna event systems me chamakta hai: event names se payloads ka ek map `onClick`, `onSubmit` handler props banata hai, har ek sahi payload type ke saath.
</Ur>
</Tr>

```typescript
type Events = {
  click: { x: number; y: number };
  keypress: { key: string };
  submit: { formId: string };
};

type Handlers = {
  [E in keyof Events as `on${Capitalize<E>}`]?: (payload: Events[E]) => void;
};

function emit<E extends keyof Events>(handlers: Handlers, event: E, payload: Events[E]) {
  const name = ("on" + event[0].toUpperCase() + event.slice(1)) as keyof Handlers;
  const handler = handlers[name] as ((p: Events[E]) => void) | undefined;
  if (handler) handler(payload);
  else console.log("no handler for", event);
}

const handlers: Handlers = {
  onClick: (p) => console.log("clicked at", p.x, p.y),
  onSubmit: (p) => console.log("submitted", p.formId),
};

emit(handlers, "click", { x: 10, y: 20 });
emit(handlers, "submit", { formId: "signup" });
emit(handlers, "keypress", { key: "Enter" });
```

```text output
clicked at 10 20
submitted signup
no handler for keypress
```

<Happened>
<Tr>
<En>

- In `onClick: (p) => …`, TypeScript **knows** `p` is `{ x: number; y: number }`, with no annotation needed.
- `emit(handlers, "click", …)` requires the click payload; passing `{ key: "Enter" }` for `"click"` would be an error.
- The `as` casts inside `emit` are needed because building `"on" + …` at runtime produces a plain `string`; the types outside the function stay fully safe. This is the same idea React uses for its `onClick`/`onChange` props.

</En>
<Ur>

- `onClick: (p) => …` me TypeScript **janti** hai ke `p` `{ x: number; y: number }` hai, annotation ki zaroorat nahi.
- `emit(handlers, "click", …)` click ka payload maangta hai; `"click"` ke liye `{ key: "Enter" }` dena error hota.
- `emit` ke andar `as` casts is liye zaroori hain ke runtime par `"on" + …` banana saadi `string` deta hai; function ke bahar ki types poori mehfooz rehti hain. React apne `onClick`/`onChange` props ke liye yahi khayal istemal karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The handler map catches mistakes">

<Tr>
<En>
Let's see the same types reject a wrong payload property and a handler for an event that doesn't exist.
</En>
<Ur>
Dekhte hain ke wahi types ghalat payload property aur ghair maujood event ke handler ko kaise mustarad karti hain.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Events = {
  click: { x: number; y: number };
  submit: { formId: string };
};
type Handlers = {
  [E in keyof Events as `on${Capitalize<E>}`]?: (payload: Events[E]) => void;
};
const h: Handlers = {
  onClick: (p) => console.log(p.formId),
  onHover: () => {},
};
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(9,33): error TS2339: Property 'formId' does not exist on type '{ x: number; y: number; }'.
app.ts(10,3): error TS2353: Object literal may only specify known properties, and 'onHover' does not exist in type 'Handlers'.
```

<Happened>
<Tr>
<En>

- The click handler tried to read the submit payload's field.
- `onHover` isn't generated from any event name. Add `hover: {…}` to `Events` and it becomes valid.

</En>
<Ur>

- Click handler ne submit payload ka field parhne ki koshish ki.
- `onHover` kisi event name se nahi bana. `Events` me `hover: {…}` jorein aur ye jaiz ho jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Filtering keys with never">

<Tr>
<En>
If the `as` clause produces `never`, that key is **dropped**. Combine it with a conditional type to keep only the keys whose values match something.
</En>
<Ur>
Agar `as` hissa `never` banaye to wo key **nikal** di jati hai. Ise conditional type ke saath milayen taa ke sirf wo keys rahen jin ki values kisi cheez se milti hon.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Product = { id: number; name: string; price: number; tags: string[] };

type OnlyNumbers<T> = { [K in keyof T as T[K] extends number ? K : never]: T[K] };
type KeysOfType<T, V> = { [K in keyof T]: T[K] extends V ? K : never }[keyof T];

const n: OnlyNumbers<Product> = { id: 1, price: 2, name: "x" };
const k1: KeysOfType<Product, number> = "price";
const k2: KeysOfType<Product, number> = "name";
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(6,52): error TS2353: Object literal may only specify known properties, and 'name' does not exist in type 'OnlyNumbers<Product>'.
app.ts(8,7): error TS2322: Type '"name"' is not assignable to type 'KeysOfType<Product, number>'.
```

<Happened>
<Tr>
<En>

- `OnlyNumbers<Product>` is `{ id: number; price: number }`. For `name` and `tags`, the test `T[K] extends number` was false, so the key became `never` and disappeared.
- `KeysOfType<Product, number>` is `"id" | "price"`. It maps each key to itself or `never`, then `[keyof T]` collects all the values into a union (`never` vanishes from unions). `"price"` passed, `"name"` failed.
- This is how you'd type something like `sortBy(products, key)` where only numeric keys make sense.

</En>
<Ur>

- `OnlyNumbers<Product>` `{ id: number; price: number }` hai. `name` aur `tags` ke liye test `T[K] extends number` jhoota tha, isliye key `never` ban kar ghayab ho gayi.
- `KeysOfType<Product, number>` `"id" | "price"` hai. Ye har key ko khud ya `never` se milata hai, phir `[keyof T]` tamam values ko union me jama karta hai (`never` unions se ghayab ho jata hai). `"price"` paas hua, `"name"` fail.
- `sortBy(products, key)` jaisi cheez ko aap isi tarah type karenge jahan sirf number wali keys ka matlab banta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Conditional types: if/else for types">

<Tr>
<En>
`T extends U ? X : Y` reads "if `T` fits into `U`, the result is `X`, otherwise `Y`". And `infer` declares a placeholder that TypeScript fills in while matching, so you can pull a type out.
</En>
<Ur>
`T extends U ? X : Y` ka matlab "agar `T` `U` me fit ho to nateeja `X`, warna `Y`". Aur `infer` ek jagah rakhne wala elaan karta hai jise TypeScript milate waqt bharti hai, taa ke aap type bahar nikal sakein.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type IsString<T> = T extends string ? "yes" : "no";

const a: IsString<"hello"> = "yes";
const b: IsString<42> = "no";
const c: IsString<42> = "yes";

type ArrayItem<T> = T extends (infer Item)[] ? Item : T;
const d: ArrayItem<number[]> = 5;
const e: ArrayItem<string> = "plain";
const f: ArrayItem<boolean[]> = "true";
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,7): error TS2322: Type '"yes"' is not assignable to type '"no"'.
app.ts(10,7): error TS2322: Type 'string' is not assignable to type 'boolean'.
```

<Happened>
<Tr>
<En>

- `IsString<"hello">` is `"yes"`; `IsString<42>` is `"no"`, so line 5 failed.
- `ArrayItem<number[]>`: does `number[]` match "an array of **something**"? Yes, and `infer Item` captured that something: `number`. So `d` must be a number.
- `ArrayItem<string>` isn't an array, so the "else" branch returns `string` itself.
- `ArrayItem<boolean[]>` is `boolean`, so the text `"true"` fails.

</En>
<Ur>

- `IsString<"hello">` `"yes"` hai; `IsString<42>` `"no"` hai, isliye line 5 fail hui.
- `ArrayItem<number[]>`: kya `number[]` "**kisi cheez** ki array" se milta hai? Haan, aur `infer Item` ne wo cheez pakar li: `number`. Isliye `d` number hona chahiye.
- `ArrayItem<string>` array nahi, isliye "else" shaakh khud `string` wapas karti hai.
- `ArrayItem<boolean[]>` `boolean` hai, isliye text `"true"` fail hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="infer in practice: ReturnType and Awaited">

<Tr>
<En>
`infer` can capture a function's return type or a promise's value. That's how the built-in `ReturnType` and `Awaited` work, and it lets you reuse the type a function **already returns** instead of writing it again.
</En>
<Ur>
`infer` function ki return type ya promise ki value pakar sakta hai. Bane banaye `ReturnType` aur `Awaited` isi tarah kaam karte hain, aur ye aap ko wo type dobara istemal karne deta hai jo function **pehle se wapas karta** hai, use dobara likhne ke bajaye.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;
type Unwrap<P> = P extends Promise<infer V> ? V : P;

function createUser(name: string) {
  return { id: 1, name, createdAt: new Date() };
}
async function fetchTotal() {
  return 42;
}

type NewUser = MyReturnType<typeof createUser>;
type Total = Unwrap<MyReturnType<typeof fetchTotal>>;
type Total2 = Awaited<ReturnType<typeof fetchTotal>>;

const u: NewUser = { id: 1, name: "Sara" };
const t: Total = "42";
const t2: Total2 = 42;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(15,7): error TS2741: Property 'createdAt' is missing in type '{ id: number; name: string; }' but required in type '{ id: number; name: string; createdAt: Date; }'.
app.ts(16,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

<Happened>
<Tr>
<En>

- `MyReturnType<typeof createUser>` matched "a function returning **R**" and captured `R`: `{ id: number; name: string; createdAt: Date }`. We never wrote that type by hand.
- `fetchTotal` returns `Promise<number>`; `Unwrap` reached inside the promise and found `number`.
- Line 17 used the built-ins `Awaited<ReturnType<…>>`, which do the same thing (and `Awaited` also unwraps nested promises).
- `typeof createUser` turns the **function value** into its **type** so it can be passed to a type helper.

</En>
<Ur>

- `MyReturnType<typeof createUser>` "**R** wapas karne wala function" se mila aur `R` pakar liya: `{ id: number; name: string; createdAt: Date }`. Humne ye type kabhi haath se nahi likhi.
- `fetchTotal` `Promise<number>` wapas karta hai; `Unwrap` promise ke andar pohancha aur `number` paya.
- Line 17 ne bane banaye `Awaited<ReturnType<…>>` istemal kiye, jo yahi karte hain (aur `Awaited` nested promises bhi kholta hai).
- `typeof createUser` **function value** ko us ki **type** me badalta hai taa ke use type helper ko diya ja sake.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Distribution over unions">

<Tr>
<En>
When a conditional type checks a bare type parameter and you pass a **union**, it runs **once per member** and joins the results. That's how `Exclude` and `NonNullable` remove members. Wrap both sides in `[ ]` to turn distribution off.
</En>
<Ur>
Jab conditional type khule type parameter ko check kare aur aap **union** dein, to ye **har member ke liye ek dafa** chalti hai aur nataij jor deti hai. `Exclude` aur `NonNullable` members isi tarah hatate hain. Distribution band karne ke liye dono taraf `[ ]` lagayen.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type MyExclude<T, U> = T extends U ? never : T;
type MyNonNullable<T> = T extends null | undefined ? never : T;

type Status = "draft" | "published" | "archived";
type Visible = MyExclude<Status, "archived">;
const v1: Visible = "draft";
const v2: Visible = "archived";

type MaybeName = string | null | undefined;
const n1: MyNonNullable<MaybeName> = "Sara";
const n2: MyNonNullable<MaybeName> = null;

type ToArray<T> = T extends any ? T[] : never;
type ToArrayOnce<T> = [T] extends [any] ? T[] : never;
const t1: ToArray<string | number> = ["a", 1];
const t2: ToArrayOnce<string | number> = ["a", 1];
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(7,7): error TS2322: Type '"archived"' is not assignable to type 'Visible'.
app.ts(11,7): error TS2322: Type 'null' is not assignable to type 'string'.
app.ts(15,7): error TS2322: Type '(string | number)[]' is not assignable to type 'string[] | number[]'.
  Type '(string | number)[]' is not assignable to type 'string[]'.
    Type 'string | number' is not assignable to type 'string'.
      Type 'number' is not assignable to type 'string'.
```

<Happened>
<Tr>
<En>

- `MyExclude<Status, "archived">` ran three times: `"draft"` → `"draft"`, `"published"` → `"published"`, `"archived"` → `never`. Joined: `"draft" | "published"`.
- `MyNonNullable` dropped `null` and `undefined`, leaving `string`.
- `ToArray<string | number>` distributed into `string[] | number[]` (either array), so the mixed array failed. `ToArrayOnce` with `[T]` didn't distribute and produced `(string | number)[]`, which accepts it.
- Most of the time distribution is what you want. Reach for `[T]` only when you mean "the union as a whole".

</En>
<Ur>

- `MyExclude<Status, "archived">` teen dafa chala: `"draft"` → `"draft"`, `"published"` → `"published"`, `"archived"` → `never`. Jor kar: `"draft" | "published"`.
- `MyNonNullable` ne `null` aur `undefined` gira diye, `string` bacha.
- `ToArray<string | number>` `string[] | number[]` (ya ye ya wo array) me bant gaya, isliye mili juli array fail hui. `[T]` wale `ToArrayOnce` ne bantwara nahi kiya aur `(string | number)[]` banaya, jo use qubool karta hai.
- Zyada tar bantwara hi wo hai jo aap chahte hain. `[T]` tab lein jab matlab "poora union ek saath" ho.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Retyping the same fields by hand">

```text
type User = { id: number; name: string; email: string; phone: string };
type UserUpdate = { name?: string; email?: string; phone?: string };
type UserErrors = { name?: string; email?: string };   // phone forgotten
// add "avatarUrl" to User and both of these silently fall behind
```

</Bad>
<Good title="Derive from one source">

```text
type User = { id: number; name: string; email: string; phone: string };
type UserUpdate = Partial<Omit<User, "id">>;
type UserErrors = { [K in keyof UserUpdate]?: string };
// add a field to User and both follow automatically
```

</Good>
</Compare>

<Compare>
<Bad title="Clever types nobody can read">

```text
type DeepX<T> = T extends object ? { [K in keyof T as K extends `_${string}` ? never
  : K]: T[K] extends (...a: any) => any ? T[K] : DeepX<T[K]> } : T;
// used once, for one object, and every error message is now unreadable
```

</Bad>
<Good title="Simple, named, documented">

```text
/** Removes keys that start with "_" (private fields) from a type. */
type WithoutPrivate<T> = {
  [K in keyof T as K extends `_${string}` ? never : K]: T[K];
};
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Building your own helper when a built-in exists** (`Partial`, `Required`, `Readonly`, `Pick`, `Omit`, `Record`, `Exclude`, `Extract`, `NonNullable`, `ReturnType`, `Parameters`, `Awaited`).
- **Forgetting `string & K`** with template literals over `keyof`, which may include number or symbol keys.
- **Being surprised by distribution**: wrap in `[T]` when you want the union treated as one.
- **Thinking these types exist at runtime.** They only describe shapes; you still need code that builds the objects.
- **Deep recursive types on huge objects**, which slow the editor down and produce "Type instantiation is excessively deep" errors.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bana banaya maujood ho phir bhi apna helper banana** (`Partial`, `Required`, `Readonly`, `Pick`, `Omit`, `Record`, `Exclude`, `Extract`, `NonNullable`, `ReturnType`, `Parameters`, `Awaited`).
- **`keyof` par template literals ke saath `string & K` bhool jana**, jis me number ya symbol keys ho sakti hain.
- **Bantware par hairan hona**: jab union ko ek samajhna ho to `[T]` me lapetein.
- **Ye samajhna ke ye types runtime par maujood hain.** Ye sirf shakalen bayan karti hain; objects banane wala code phir bhi chahiye.
- **Bohot bare objects par gehri recursive types**, jo editor ko sust karti hain aur "Type instantiation is excessively deep" errors deti hain.

</Ur>
</Tr>

<Challenge title="Nullable fields">

<En>
Write `Nullable<T>` that makes every property's type `T[K] | null`. Use it to type a `Profile` row from a database where any column may be `null`, then write a function that prints each field or "(empty)".

`Nullable<T>` likhein jo har property ki type `T[K] | null` bana de. Ise database ki `Profile` row type karne ke liye istemal karein jahan koi bhi column `null` ho sakta hai, phir function likhein jo har field ya "(empty)" print kare.

```typescript
type Nullable<T> = { [K in keyof T]: T[K] | null };
type Profile = { name: string; city: string; bio: string };

function show(row: Nullable<Profile>): void {
  for (const key of Object.keys(row) as (keyof Profile)[]) {
    console.log(key.padEnd(5), row[key] ?? "(empty)");
  }
}

show({ name: "Emma", city: null, bio: "Coffee and code" });
```

city  (empty)
bio   Coffee and code

## Remember

<Takeaways>
<Tr>
<En>

- **Mapped types** loop over keys: `{ [K in keyof T]: … }`; `T[K]` is the original property type.
- Modifiers: `?`, `readonly`, and their removal with `-?`, `-readonly`. That's how `Partial`, `Required`, `Readonly` are built.
- **`as` remapping** renames keys (template literal types + `Capitalize`) or drops them by returning `never`.
- **Conditional types**: `T extends U ? X : Y`; **`infer`** captures a part (`ReturnType`, `Awaited`, array items).
- Conditionals on a bare `T` **distribute** over unions; wrap in `[T]` to stop it.
- Derive types (form errors, updates, handlers) from one source so they never drift.
- Prefer built-in utility types; keep custom ones small, named and documented.

</En>
<Ur>

- **Mapped types** keys par loop chalati hain: `{ [K in keyof T]: … }`; `T[K]` asal property type hai.
- Modifiers: `?`, `readonly`, aur `-?`, `-readonly` se un ka hatana. `Partial`, `Required`, `Readonly` isi tarah bane hain.
- **`as` remapping** keys ka naam badalta hai (template literal types + `Capitalize`) ya `never` wapas kar ke unhen nikal deta hai.
- **Conditional types**: `T extends U ? X : Y`; **`infer`** ek hissa pakarta hai (`ReturnType`, `Awaited`, array items).
- Khule `T` par conditionals unions par **bant** jate hain; rokne ke liye `[T]` me lapetein.
- Types (form errors, updates, handlers) ek source se nikalein taa ke kabhi door na hon.
- Bane banaye utility types pasand karein; apne helpers chhote, naam wale aur samjhaye hue rakhein.

</Ur>
</Tr>

<DeepDive title="More about mapped and conditional types">

**Built-ins, rewritten.** `Pick<T, K>` is `{ [P in K]: T[P] }` with `K extends keyof T`. `Record<K, V>` is `{ [P in K]: V }`. `Omit<T, K>` is `Pick<T, Exclude<keyof T, K>>`. `Extract<T, U>` is `T extends U ? T : never`. `Parameters<F>` uses `infer` on the argument list.

**Homomorphic mapped types.** A mapped type over `keyof T` **preserves** the original `readonly` and `?` modifiers, which is why `{ [K in keyof T]: T[K] }` keeps optional properties optional. Mapping over an arbitrary union (`[K in "a" | "b"]`) has nothing to preserve.

**Mapping arrays and tuples.** A homomorphic mapped type applied to an array or tuple produces an array or tuple, so `Nullable<[string, number]>` is `[string | null, number | null]`.

**Recursive types.** `type DeepPartial<T> = { [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K] }` works for nested config objects. Be careful with functions, dates and arrays, and with very deep or wide objects that slow the checker.

**`infer` with constraints.** `T extends [infer First extends string, ...unknown[]] ? First : never` captures and checks at once.

**Template literal inference.** `` T extends `${infer Head}-${infer Tail}` `` can split strings at the type level, which libraries use to type route parameters like `/users/:id`.

**Type-level tests.** Projects use helpers like `Expect<Equal<A, B>>` or tools like `tsd` / Vitest's `expectTypeOf` to test that complex types produce what they should.

</DeepDive>

<DeepDive title="Real world: one schema, every type">

A team's admin panel had a `Product` type, plus hand-written `ProductCreateInput`, `ProductUpdateInput`, `ProductFilters`, `ProductFormErrors` and `ProductColumnVisibility`, six types listing the same eleven fields.

When they added `sku`, two of the six were forgotten. The create form sent `sku` but the filter panel couldn't filter by it, and the column toggle was missing. Each was a small bug report; together they cost days.

They replaced the copies with derived types:

- `ProductCreateInput = Omit<Product, "id" | "createdAt">`
- `ProductUpdateInput = Partial<ProductCreateInput>`
- `ProductFormErrors = { [K in keyof ProductCreateInput]?: string }`
- `ProductColumnVisibility = { [K in keyof Product]: boolean }`
- `ProductFilters` built from `KeysOfType<Product, string | number>`

Now adding a field to `Product` makes the compiler point at every component that must handle it, and nothing else needs to be edited by hand. Later, when they adopted zod, the `Product` type itself was derived from the schema (`z.infer`), so even the source of truth came from one place.

</DeepDive>

<DeepDive title="Security lens">

- **Derived input types limit mass assignment.** `UpdateUser = Partial<Pick<User, "name" | "bio">>` documents that clients may only change those fields, but you must also **enforce** it at runtime by picking only those keys from the request body.
- **Strip sensitive fields by type.** `type PublicUser = Omit<User, "passwordHash" | "resetToken">` and a function returning `PublicUser` make leaking those fields a compile error, as long as the function really builds a new object without them.
- **Types aren't validation.** A mapped type can't stop extra properties arriving in JSON; combine with a schema validator (next lessons).
- **Avoid `as` casts to "make the type work"** in mapped-type code; a wrong cast can hide a field you meant to remove.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a mapped type?">
A type that iterates over a union of keys, usually keyof T, to create a new object type, optionally transforming each property's type, adding or removing readonly and optional modifiers, or remapping keys with an as clause.
</QA>

<QA q="How would you implement Partial and Required?">
Partial maps every key of T to an optional property with type T indexed by K. Required does the same but uses the minus-question-mark modifier to remove optionality.
</QA>

<QA q="What is a distributive conditional type?">
A conditional type whose checked type is a naked type parameter. When given a union, it is applied to each member separately and the results are combined into a union. Wrapping the type in a one-element tuple prevents distribution.
</QA>

<QA q="What does infer do and where can it be used?">
infer introduces a type variable inside the extends clause of a conditional type, which TypeScript fills in from the matched type. It is used to extract return types, parameter types, promise values, array element types and parts of template literal strings.
</QA>

<QA q="How can you remove keys from a type based on their value type?">
Use key remapping in a mapped type with a conditional: map each key to itself when its value type matches and to never otherwise, since keys remapped to never are dropped.
</QA>

</DeepDive>
