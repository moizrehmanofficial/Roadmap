<BigIdea>
<Tr>
<En>
In a real app one piece of data appears in many forms. A `User` has an `id`, `name`, `email` and `password`. A **form to edit** a user only sends some fields. A **public profile** must never include the password. A **"create user"** request doesn't have an `id` yet. You could write four separate types by hand, but then they drift apart. **Utility types** are ready-made generics that **build new types from existing ones**: `Partial<User>` makes every field optional, `Pick<User, "id" | "name">` keeps only some fields, `Omit<User, "password">` removes some, `Readonly<User>` locks them, `Record<K, V>` builds lookup objects, and `ReturnType`, `Parameters` and `Awaited` read types off functions. Describe your data **once**, derive the rest, and a change to `User` flows everywhere automatically.
</En>
<Ur>
Asli app me data ka ek hissa kai shakalon me aata hai. `User` ke paas `id`, `name`, `email` aur `password` hain. User ko **edit karne ka form** sirf kuch fields bhejta hai. **Public profile** me password kabhi nahi hona chahiye. **"Create user"** request ke paas abhi `id` nahi hoti. Aap chaar alag types haath se likh sakte hain, magar phir wo ek doosre se alag hoti chali jati hain. **Utility types** bane banaye generics hain jo **maujooda types se nayi types banate hain**: `Partial<User>` har field ko ikhtiyari banata hai, `Pick<User, "id" | "name">` sirf kuch fields rakhta hai, `Omit<User, "password">` kuch hata deta hai, `Readonly<User>` unhe taala laga deta hai, `Record<K, V>` lookup objects banata hai, aur `ReturnType`, `Parameters` aur `Awaited` functions se types parhte hain. Apna data **ek dafa** bayan karein, baqi nikal lein, aur `User` me tabdeeli khud ba khud har jagah pohanch jati hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Start from one type:

```ts
type User = { id: number; name: string; email: string; password: string };
```

| Utility | Result | Use it for |
| --- | --- | --- |
| `Partial<User>` | every field optional | update / patch data |
| `Required<T>` | every field required | settings after defaults |
| `Readonly<User>` | every field read-only | data that must not change |
| `Pick<User, "id" \| "name">` | only `id` and `name` | public or summary views |
| `Omit<User, "password">` | everything except `password` | safe responses, create forms |
| `Record<"admin" \| "viewer", boolean>` | an object with those keys | lookup tables |
| `Exclude<A, B>` / `Extract<A, B>` | remove / keep union members | narrowing statuses |
| `NonNullable<T>` | removes `null` and `undefined` | after a check |
| `ReturnType<typeof fn>` | what `fn` returns | reuse a function's output type |
| `Parameters<typeof fn>` | `fn`'s parameter types, as a tuple | wrappers |
| `Awaited<T>` | the value inside a promise | async results |

</En>
<Ur>

Ek type se shuru karein:

```ts
type User = { id: number; name: string; email: string; password: string };
```

| Utility | Nateeja | Kis ke liye |
| --- | --- | --- |
| `Partial<User>` | har field ikhtiyari | update / patch ka data |
| `Required<T>` | har field zaroori | defaults ke baad ki settings |
| `Readonly<User>` | har field sirf parhne wali | aisa data jo badalna nahi chahiye |
| `Pick<User, "id" \| "name">` | sirf `id` aur `name` | public ya khulasa views |
| `Omit<User, "password">` | `password` ke ilawa sab | mehfooz responses, create forms |
| `Record<"admin" \| "viewer", boolean>` | in keys wala object | lookup tables |
| `Exclude<A, B>` / `Extract<A, B>` | union ke members hatana / rakhna | statuses tang karna |
| `NonNullable<T>` | `null` aur `undefined` hata deta hai | check ke baad |
| `ReturnType<typeof fn>` | `fn` jo wapas karta hai | function ke output ki type dobara istemal |
| `Parameters<typeof fn>` | `fn` ke parameters ki types, tuple me | wrappers |
| `Awaited<T>` | promise ke andar ki value | async nateeje |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **One source of truth.** Add `phone` to `User`, and `Partial<User>`, `Omit<User, "password">` and every other derived type get it too.
- **Less typing, fewer mistakes.** No copying ten fields into a second type and forgetting one.
- **Safety by construction.** A response typed as `Omit<User, "password">` **can't** accidentally include the password field.
- **Reading library types.** React, Next.js, Prisma and others use these everywhere (`Partial<Props>`, `ReturnType<typeof …>`).

</En>
<Ur>

- **Sach ka ek zariya.** `User` me `phone` jorein, aur `Partial<User>`, `Omit<User, "password">` aur har nikali gayi type ko bhi mil jata hai.
- **Kam likhna, kam ghaltiyan.** Das fields doosri type me copy kar ke ek bhoolne ka masla khatam.
- **Banawat se hifazat.** `Omit<User, "password">` type wala response ghalti se password field shamil **nahi kar sakta**.
- **Libraries ki types parhna.** React, Next.js, Prisma aur doosri libraries inhe har jagah istemal karti hain (`Partial<Props>`, `ReturnType<typeof …>`).

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Whenever you're about to write a type that is **"like X, but…"**:

- "like `User` but every field optional" → `Partial<User>`
- "like `User` but without the password" → `Omit<User, "password">`
- "only the name and email of `User`" → `Pick<User, "name" | "email">`
- "whatever this function returns" → `ReturnType<typeof fn>`

</En>
<Ur>

Jab bhi aap aisi type likhne wale hon jo **"X jaisi hai, magar…"**:

- "`User` jaisi magar har field ikhtiyari" → `Partial<User>`
- "`User` jaisi magar password ke baghair" → `Omit<User, "password">`
- "`User` ka sirf naam aur email" → `Pick<User, "name" | "email">`
- "jo bhi ye function wapas kare" → `ReturnType<typeof fn>`

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```ts
type User = { id: number; name: string; email: string; password: string };

type UserUpdate = Partial<Omit<User, "id">>;      // edit any field except id
type PublicUser = Omit<User, "password">;          // safe to send
type NewUser = Omit<User, "id">;                   // id comes from the database
```

Utilities can be **combined**: the inside runs first, like nested function calls.

</En>
<Ur>

```ts
type User = { id: number; name: string; email: string; password: string };

type UserUpdate = Partial<Omit<User, "id">>;      // id ke ilawa koi bhi field edit
type PublicUser = Omit<User, "password">;          // bhejne ke liye mehfooz
type NewUser = Omit<User, "id">;                   // id database se aati hai
```

Utilities **jori** ja sakti hain: andar wali pehle chalti hai, nested function calls ki tarah.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **master photo** of a document, and a photocopier with special buttons.

- **Partial**: "copy, but every box becomes *optional*" — a change-of-details form where you only fill in what changed.
- **Pick**: "copy only these boxes" — the part of the form that goes on a visitor badge.
- **Omit**: "copy everything **except** these boxes" — the version you can post on a notice board, with the private boxes cut out.
- **Readonly**: "copy, then **laminate** it" — you can read it, but not write on it.

The important bit: you never redraw the form by hand. If the **master** gains a new box, every copy made from it gets that box too, automatically. That's why utility types beat writing similar types twice.

</En>
<Ur>

Kisi document ki **asal tasveer** aur khaas buttons wali photocopy machine ka sochein.

- **Partial**: "copy karo, magar har khaana *ikhtiyari* ban jaye" — tafseelat badalne ka form jis me sirf wahi bharein jo badla.
- **Pick**: "sirf ye khaane copy karo" — form ka wo hissa jo visitor badge par jata hai.
- **Omit**: "in khaanon ke **ilawa** sab copy karo" — wo version jo notice board par lagaya ja sake, private khaane kaat kar.
- **Readonly**: "copy karo, phir **laminate** kar do" — parh sakte hain, likh nahi sakte.

Ahem baat: aap form kabhi haath se dobara nahi banate. Agar **asal** me naya khaana aaye to us se bani har copy ko wo khaana khud ba khud mil jata hai. Isi liye utility types milti julti types do dafa likhne se behtar hain.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Utility type** | A built-in generic that transforms a type | `Partial<User>` |
| **Derived type** | A type built from another type | `type PublicUser = Omit<User, "password">` |
| **Union of keys** | Property names joined with `\|` | `"id" \| "name"` |
| **`keyof`** | All keys of a type as a union | `keyof User` |
| **`typeof` (in a type)** | The type of a value or function | `typeof config` |
| **`as const`** | Treat a value as exact and read-only | `["S", "M"] as const` |
| **Mapped type** | A type built by looping over keys | `{ [K in keyof T]?: T[K] }` |
| **Patch** | A partial update: only changed fields | `{ name: "Alex" }` |
| **Tuple** | Fixed list of types, used by `Parameters` | `[number, string]` |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Utility type** | Bana banaya generic jo type ko badalta hai | `Partial<User>` |
| **Derived type** | Doosri type se bani type | `type PublicUser = Omit<User, "password">` |
| **Keys ka union** | `\|` se jore gaye property ke naam | `"id" \| "name"` |

<Walkthrough>

<Step title="The problem: copies that drift apart">

<Tr>
<En>
Here a developer wrote an `UpdateUser` type by copying fields from `User`. Later `User.age` was changed to a `number`, but the copy wasn't updated. TypeScript can't help, because the two types aren't connected.
</En>
<Ur>
Yahan ek developer ne `User` se fields copy kar ke `UpdateUser` type likhi. Baad me `User.age` ko `number` bana diya gaya, magar copy update nahi hui. TypeScript madad nahi kar sakta, kyun ke dono types aapas me juri hui nahi.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type User = { id: number; name: string; age: number };

type UpdateUserCopy = { name?: string; age?: string };

function applyUpdate(user: User, update: UpdateUserCopy) {
  return { ...user, ...update };
}

const updated = applyUpdate({ id: 1, name: "Sara", age: 28 }, { age: "29" });
const nextYear: number = updated.age + 1;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(10,26): error TS2365: Operator '+' cannot be applied to types 'string | number' and 'number'.
```

<Happened>
<Tr>
<En>

- The update was **accepted** with `age: "29"` as text, because the hand-written copy still said `string`.
- The error appears two lines later, far from the real cause, as a confusing message about `string | number`. At runtime `updated.age + 1` would be `"291"`.
- The fix isn't to update the copy more carefully. It's to **not have a copy**: derive the update type from `User`, as the next step does.

</En>
<Ur>

- Update `age: "29"` text ke saath **qubool** hua, kyun ke haath se likhi copy ab bhi `string` kehti thi.
- Error do line baad aata hai, asal wajah se door, `string | number` ke baare me ek uljhe hue paighaam ki shakal me. Chalte waqt `updated.age + 1` `"291"` hota.
- Hal ye nahi ke copy ko zyada dhyan se update karein. Hal ye hai ke **copy ho hi nahi**: update type `User` se nikalein, jaisa agla qadam karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Partial: every field optional">

<Tr>
<En>
`Partial<T>` makes a copy of `T` where **every property is optional**. It's exactly the shape of an update: "send any of these fields, and only these fields".
</En>
<Ur>
`Partial<T>` `T` ki aisi copy banata hai jis me **har property ikhtiyari** ho. Ye bilkul update ki shakal hai: "in me se koi bhi fields bhejo, aur sirf yahi fields".
</Ur>
</Tr>

```typescript
type User = { id: number; name: string; email: string; age: number };

function updateUser(user: User, changes: Partial<User>): User {
  return { ...user, ...changes };
}

const sara: User = { id: 1, name: "Sara", email: "sara@example.com", age: 28 };

console.log(updateUser(sara, { age: 29 }));
console.log(updateUser(sara, { name: "Sara Lee", email: "sara.lee@example.com" }));
console.log(updateUser(sara, {}).name);
```

```text output
{ id: 1, name: 'Sara', email: 'sara@example.com', age: 29 }
{ id: 1, name: 'Sara Lee', email: 'sara.lee@example.com', age: 28 }
Sara
```

<Happened>
<Tr>
<En>

- `Partial<User>` is `{ id?: number; name?: string; email?: string; age?: number }`, written for you.
- Any combination of fields, even none, is accepted. Spread copies the old user and then the changes on top.
- Because it's **derived**, it can't drift: if `age` becomes a string in `User`, it becomes a string in `Partial<User>` too.

</En>
<Ur>

- `Partial<User>` yaani `{ id?: number; name?: string; email?: string; age?: number }`, aap ke liye likha hua.
- Fields ka koi bhi mel, koi bhi field na ho tab bhi, qubool hai. Spread purane user ko copy karta hai aur phir upar tabdeeliyan.
- Chunke ye **nikali gayi** hai, ye alag nahi ho sakti: agar `User` me `age` string ban jaye to `Partial<User>` me bhi string ban jati hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Partial still checks types and names">

<Tr>
<En>
Optional doesn't mean "anything goes". Every field you do send must still exist and have the right type.
</En>
<Ur>
Ikhtiyari ka matlab "sab chalta hai" nahi. Jo bhi field aap bhejte hain wo maujood honi chahiye aur us ki type sahi honi chahiye.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type User = { id: number; name: string; age: number };

function updateUser(user: User, changes: Partial<User>): User {
  return { ...user, ...changes };
}

const sara: User = { id: 1, name: "Sara", age: 28 };
updateUser(sara, { age: "29" });
updateUser(sara, { nmae: "Alex" });
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(8,20): error TS2322: Type 'string' is not assignable to type 'number'.
app.ts(9,20): error TS2353: Object literal may only specify known properties, and 'nmae' does not exist in type 'Partial<User>'.
```

<Happened>
<Tr>
<En>

- The text `"29"` for `age` is now caught **at the call**, where the mistake is.
- The typo `nmae` is caught too, and the message mentions `Partial<User>` by name.
- Compare with step 1: same idea, but connected to `User`, so it stays correct.

</En>
<Ur>

- `age` ke liye text `"29"` ab **call par hi** pakra jata hai, jahan ghalti hai.
- Typo `nmae` bhi pakra jata hai, aur paighaam `Partial<User>` ka naam leta hai.
- Qadam 1 se muqabla karein: wahi khayal, magar `User` se jura hua, isliye durust rehta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Required and Readonly">

<Tr>
<En>
`Required<T>` is the opposite of `Partial`: every property becomes **required**. It's useful after you've filled in defaults. `Readonly<T>` makes every property **read-only**.
</En>
<Ur>
`Required<T>` `Partial` ka ulta hai: har property **zaroori** ban jati hai. Defaults bharne ke baad ye mufeed hai. `Readonly<T>` har property ko **sirf parhne wala** bana deta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Options = { theme?: "light" | "dark"; pageSize?: number };

function withDefaults(options: Options): Required<Options> {
  return { theme: "light", pageSize: 20, ...options };
}

const settings = withDefaults({ pageSize: 50 });
const rows: number = settings.pageSize;
const raw: Options = { pageSize: 50 };
const rawRows: number = raw.pageSize;

type Config = Readonly<{ apiUrl: string; retries: number }>;
const config: Config = { apiUrl: "https://api.example.com", retries: 3 };
config.retries = 5;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(10,7): error TS2322: Type 'number | undefined' is not assignable to type 'number'.
  Type 'undefined' is not assignable to type 'number'.
app.ts(14,8): error TS2540: Cannot assign to 'retries' because it is a read-only property.
```

<Happened>
<Tr>
<En>

- `withDefaults` returns `Required<Options>`, so after it every setting is guaranteed. `settings.pageSize` is a plain `number`.
- `raw.pageSize` is still optional (`number | undefined`), so using it as a `number` is an error. (Some errors have a second, indented line explaining the reason.)
- `Readonly<…>` blocked `config.retries = 5`. Good for configuration, constants and data you received and shouldn't change.

</En>
<Ur>

- `withDefaults` `Required<Options>` wapas karta hai, isliye us ke baad har setting yaqeeni hai. `settings.pageSize` saada `number` hai.
- `raw.pageSize` ab bhi ikhtiyari hai (`number | undefined`), isliye use `number` ki tarah istemal karna error hai. (Kuch errors ki doosri, andar ki taraf hati line wajah samjhati hai.)
- `Readonly<…>` ne `config.retries = 5` rok diya. Configuration, constants aur aise mile hue data ke liye achha hai jise badalna nahi chahiye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Pick: keep only some fields">

<Tr>
<En>
`Pick<T, Keys>` builds a type with **only** the listed properties. The keys are written as a union of strings. Typos in the key list are caught, because they must be real keys of `T`.
</En>
<Ur>
`Pick<T, Keys>` aisi type banata hai jis me **sirf** likhi gayi properties hon. Keys strings ke union ki shakal me likhi jati hain. Key list me typos pakre jate hain, kyun ke unhe `T` ki asli keys hona chahiye.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type User = { id: number; name: string; email: string; password: string; isAdmin: boolean };

type UserCard = Pick<User, "id" | "name">;

function renderCard(user: UserCard) {
  return "#" + user.id + " " + user.name + " " + user.email;
}

const card: UserCard = { id: 1, name: "Sara" };

type Broken = Pick<User, "id" | "fullName">;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(6,55): error TS2339: Property 'email' does not exist on type 'UserCard'.
app.ts(11,26): error TS2344: Type '"fullName" | "id"' does not satisfy the constraint 'keyof User'.
  Type '"fullName"' is not assignable to type 'keyof User'.
```

<Happened>
<Tr>
<En>

- `UserCard` has only `id` and `name`. Code that receives a card can't read `email` or `password`: they simply aren't part of the type.
- Creating a card needs only those two fields.
- `Pick<User, "fullName">` fails: `Pick` is declared as `Pick<T, K extends keyof T>`, the same constraint you wrote in the Generics lesson. Every key must be one of `keyof User`.

</En>
<Ur>

- `UserCard` me sirf `id` aur `name` hain. Card lene wala code `email` ya `password` nahi parh sakta: wo type ka hissa hi nahi.
- Card banane ke liye sirf yahi do fields chahiyen.
- `Pick<User, "fullName">` nakaam hai: `Pick` `Pick<T, K extends keyof T>` ki shakal me bayan hai, wahi constraint jo aap ne Generics lesson me likha tha. Har key `keyof User` me se honi chahiye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Omit: everything except some fields">

<Tr>
<En>
`Omit<T, Keys>` is the reverse of `Pick`: it keeps everything **except** the listed keys. Two everyday uses: a "safe" type without secrets, and a "new record" type without the fields the database fills in.
</En>
<Ur>
`Omit<T, Keys>` `Pick` ka ulta hai: likhi gayi keys ke **ilawa** sab rakhta hai. Rozmarra ke do istemal: secrets ke baghair "mehfooz" type, aur un fields ke baghair "naya record" type jo database bharta hai.
</Ur>
</Tr>

```typescript
type User = {
  id: number;
  name: string;
  email: string;
  passwordHash: string;
  createdAt: string;
};

type PublicUser = Omit<User, "passwordHash">;
type NewUser = Omit<User, "id" | "createdAt">;

function toPublic(user: User): PublicUser {
  const { passwordHash, ...rest } = user;
  return rest;
}

let nextId = 1;
function createUser(input: NewUser): User {
  return { id: nextId++, ...input, createdAt: "2026-11-11" };
}

const sara = createUser({ name: "Sara", email: "sara@example.com", passwordHash: "x9f2…" });
console.log(sara.id, sara.createdAt);
console.log(toPublic(sara));
console.log("passwordHash" in toPublic(sara));
```

```text output
1 2026-11-11
{
  id: 1,
  name: 'Sara',
  email: 'sara@example.com',
  createdAt: '2026-11-11'
}
false
```

<Happened>
<Tr>
<En>

- `PublicUser` is `User` minus `passwordHash`. `toPublic` uses rest destructuring to actually remove it at runtime, and the return type makes sure the result matches.
- `NewUser` is `User` minus `id` and `createdAt`: callers of `createUser` don't (and can't) supply those; the function adds them.
- If `User` gains a `phone` field, both derived types get it with no extra work.
- Important: `Omit` only changes the **type**. The rest-destructuring line is what really strips the password from the object.

</En>
<Ur>

- `PublicUser` `User` minus `passwordHash` hai. `toPublic` chalte waqt ise waqai hatane ke liye rest destructuring istemal karta hai, aur return type yaqeeni banati hai ke nateeja mile.
- `NewUser` `User` minus `id` aur `createdAt` hai: `createUser` call karne wale ye nahi dete (aur de bhi nahi sakte); function inhe jorta hai.
- Agar `User` me `phone` field aaye to dono nikali gayi types ko baghair izafi kaam ke mil jati hai.
- Ahem: `Omit` sirf **type** badalta hai. Rest destructuring wali line hi object se password asal me hatati hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Record: a value for every key">

<Tr>
<En>
`Record<Keys, Value>` builds an object type with those keys, each holding that value type. With a union of keys, **every** key must be present, so nothing is forgotten.
</En>
<Ur>
`Record<Keys, Value>` aisi object type banata hai jis me wo keys hon, har ek me wo value type. Keys ke union ke saath **har** key maujood honi chahiye, isliye kuch nahi bhoolta.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Role = "viewer" | "editor" | "admin";

const canDelete: Record<Role, boolean> = {
  viewer: false,
  editor: false,
  admin: true,
};

const labels: Record<Role, string> = {
  viewer: "Viewer",
  editor: "Editor",
};
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(9,7): error TS2741: Property 'admin' is missing in type '{ viewer: string; editor: string; }' but required in type 'Record<Role, string>'.
```

<Happened>
<Tr>
<En>

- `canDelete` has an entry for all three roles: accepted.
- `labels` forgot `admin`: rejected. When someone adds a `"guest"` role to `Role`, every `Record<Role, …>` in the codebase becomes an error until it's given a value for `"guest"`. That's exactly what you want for permissions.
- `Record<string, number>` (with `string` keys) is the looser form you met before, for keys you don't know in advance.

</En>
<Ur>

- `canDelete` me teeno roles ki entry hai: qubool.
- `labels` `admin` bhool gaya: mustarad. Jab koi `Role` me `"guest"` role jore to codebase ka har `Record<Role, …>` tab tak error ban jata hai jab tak use `"guest"` ki value na mile. Permissions ke liye bilkul yahi chahiye.
- `Record<string, number>` (`string` keys ke saath) wo dheela form hai jo pehle dekha, un keys ke liye jo pehle se maloom nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Exclude, Extract and NonNullable: work on unions">

<Tr>
<En>
These three act on **union types**. `Exclude<U, X>` removes members, `Extract<U, X>` keeps only matching members, and `NonNullable<T>` removes `null` and `undefined`.
</En>
<Ur>
Ye teeno **union types** par kaam karte hain. `Exclude<U, X>` members hatata hai, `Extract<U, X>` sirf milte hue members rakhta hai, aur `NonNullable<T>` `null` aur `undefined` hata deta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Status = "draft" | "pending" | "published" | "archived";

type Visible = Exclude<Status, "draft" | "archived">;
type Finished = Extract<Status, "published" | "archived" | "deleted">;

const a: Visible = "pending";
const b: Visible = "draft";
const c: Finished = "archived";
const d: Finished = "deleted";

type MaybeName = string | null | undefined;
const displayName: NonNullable<MaybeName> = null;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(7,7): error TS2322: Type '"draft"' is not assignable to type 'Visible'.
app.ts(9,7): error TS2322: Type '"deleted"' is not assignable to type 'Finished'.
app.ts(12,7): error TS2322: Type 'null' is not assignable to type 'string'.
```

<Happened>
<Tr>
<En>

- `Visible` is `"pending" | "published"`: `"draft"` was excluded, so it's rejected.
- `Finished` keeps only the members of `Status` that match the second list: `"published" | "archived"`. `"deleted"` was never in `Status`, so it isn't in `Finished` either.
- `NonNullable<string | null | undefined>` is just `string`.
- `Exclude` and `Extract` work on **unions** (like `Status`); `Omit` and `Pick` work on **object keys**. Mixing them up is a common confusion.

</En>
<Ur>

- `Visible` yaani `"pending" | "published"`: `"draft"` nikal diya gaya, isliye wo mustarad hai.
- `Finished` `Status` ke sirf wo members rakhta hai jo doosri list se milte hain: `"published" | "archived"`. `"deleted"` kabhi `Status` me tha hi nahi, isliye `Finished` me bhi nahi.
- `NonNullable<string | null | undefined>` bas `string` hai.
- `Exclude` aur `Extract` **unions** par kaam karte hain (jaise `Status`); `Omit` aur `Pick` **object ki keys** par. In ko aapas me milana aam uljhan hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Types from functions: ReturnType, Parameters, Awaited">

<Tr>
<En>
Sometimes the most accurate description of a type is "whatever this function returns". `typeof fn` gives the function's type; `ReturnType<…>` reads its output, `Parameters<…>` reads its inputs as a tuple, and `Awaited<…>` unwraps a promise.
</En>
<Ur>
Kabhi kisi type ki sab se durust tareef hoti hai "jo bhi ye function wapas kare". `typeof fn` function ki type deta hai; `ReturnType<…>` us ka output parhta hai, `Parameters<…>` us ke inputs tuple ki shakal me, aur `Awaited<…>` promise ko kholta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function createSession(userId: number, remember: boolean) {
  return { token: "abc123", userId, expiresIn: remember ? 30 : 1 };
}

async function loadProfile(id: number) {
  return { id, name: "Sara", plan: "pro" as const };
}

type Session = ReturnType<typeof createSession>;
type SessionArgs = Parameters<typeof createSession>;
type Profile = Awaited<ReturnType<typeof loadProfile>>;

const s: Session = { token: "t", userId: 1, expiresIn: 30 };
const args: SessionArgs = [1, "yes"];
const p: Profile = { id: 1, name: "Sara", plan: "free" };
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(14,31): error TS2322: Type 'string' is not assignable to type 'boolean'.
app.ts(15,43): error TS2322: Type '"free"' is not assignable to type '"pro"'.
```

<Happened>
<Tr>
<En>

- `Session` is `{ token: string; userId: number; expiresIn: number }`, taken straight from what `createSession` returns. We never wrote it out.
- `SessionArgs` is the tuple `[userId: number, remember: boolean]`, so `"yes"` in second place is wrong.
- `loadProfile` is async, so `ReturnType` gives a `Promise<…>`; `Awaited` unwraps it to the profile object. (`"pro" as const` made `plan` the literal `"pro"`, which is why `"free"` fails.)
- `typeof` here is the **type-level** `typeof`: it means "the type of this value", not the runtime `typeof` that returns `"function"`.

</En>
<Ur>

- `Session` yaani `{ token: string; userId: number; expiresIn: number }`, seedha us se li gayi jo `createSession` wapas karta hai. Humne ise kabhi likha hi nahi.
- `SessionArgs` tuple `[userId: number, remember: boolean]` hai, isliye doosri jagah `"yes"` ghalat hai.
- `loadProfile` async hai, isliye `ReturnType` `Promise<…>` deta hai; `Awaited` use khol kar profile object bana deta hai. (`"pro" as const` ne `plan` ko literal `"pro"` bana diya, isi liye `"free"` nakaam hai.)
- Yahan `typeof` **type ki satah** wala `typeof` hai: is ka matlab "is value ki type", wo chalte waqt wala `typeof` nahi jo `"function"` wapas karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Types from values: as const and typeof">

<Tr>
<En>
Often you need the same list in two places: as a **value** (to show options or validate input) and as a **type** (to check code). Write the array once with `as const`, then get the union type from it with `typeof list[number]`.
</En>
<Ur>
Aksar wahi list do jagah chahiye hoti hai: **value** ki shakal me (options dikhane ya input validate karne ke liye) aur **type** ki shakal me (code check karne ke liye). Array ek dafa `as const` ke saath likhein, phir `typeof list[number]` se us ki union type nikal lein.
</Ur>
</Tr>

```typescript
const SIZES = ["S", "M", "L", "XL"] as const;
type Size = (typeof SIZES)[number];

function isSize(value: string): value is Size {
  return (SIZES as readonly string[]).includes(value);
}

function priceFor(size: Size): number {
  return size === "XL" ? 25 : 20;
}

for (const input of ["M", "XXL", "XL"]) {
  if (isSize(input)) {
    console.log(input, "costs $" + priceFor(input));
  } else {
    console.log(input, "is not a size we sell. Choose from:", SIZES.join(", "));
  }
}
```

```text output
M costs $20
XXL is not a size we sell. Choose from: S, M, L, XL
XL costs $25
```

<Happened>
<Tr>
<En>

- `as const` keeps the exact strings (`"S"`, `"M"`, …) instead of widening them to `string`, and makes the array read-only.
- `(typeof SIZES)[number]` means "the type of any item in `SIZES`": `"S" | "M" | "L" | "XL"`. Add `"XXL"` to the array, and the type updates by itself.
- The **same array** is used at runtime to validate text input and to show the list of choices. One list, no chance of the type and the value disagreeing.
- `value is Size` is a **type guard**: after `isSize(input)` returns true, TypeScript treats `input` as a `Size`, so `priceFor(input)` is allowed.

</En>
<Ur>

- `as const` bilkul muqarrar strings (`"S"`, `"M"`, …) rakhta hai, unhe `string` tak phailane ke bajaye, aur array ko sirf parhne wala bana deta hai.
- `(typeof SIZES)[number]` ka matlab "`SIZES` ke kisi bhi item ki type": `"S" | "M" | "L" | "XL"`. Array me `"XXL"` jorein, aur type khud update ho jati hai.
- **Wahi array** chalte waqt text input validate karne aur chunaav ki list dikhane me istemal hoti hai. Ek list, type aur value ke ikhtilaf ka koi imkaan nahi.
- `value is Size` **type guard** hai: `isSize(input)` ke true wapas karne ke baad TypeScript `input` ko `Size` samajhta hai, isliye `priceFor(input)` ki ijazat hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Combine them">

<Tr>
<En>
Utilities nest like function calls, and that's where they shine. A typical "edit profile" form: any field may change **except** `id`, and `email` must always be sent.
</En>
<Ur>
Utilities function calls ki tarah ek doosre me aati hain, aur yahin chamakti hain. Aam "edit profile" form: `id` ke **ilawa** koi bhi field badal sakti hai, aur `email` hamesha bheji jani chahiye.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type User = { id: number; name: string; email: string; bio: string; age: number };

type ProfileForm = Partial<Omit<User, "id" | "email">> & Pick<User, "email">;

const ok: ProfileForm = { email: "sara@example.com", bio: "Hi!" };
const noEmail: ProfileForm = { name: "Sara" };
const withId: ProfileForm = { email: "sara@example.com", id: 5 };
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(6,7): error TS2322: Type '{ name: string; }' is not assignable to type 'ProfileForm'.
  Property 'email' is missing in type '{ name: string; }' but required in type 'Pick<User, "email">'.
app.ts(7,58): error TS2353: Object literal may only specify known properties, and 'id' does not exist in type 'ProfileForm'.
```

<Happened>
<Tr>
<En>

Read it from the inside out:

1. `Omit<User, "id" | "email">` → `name`, `bio`, `age`.
2. `Partial<…>` → those three become optional.
3. `& Pick<User, "email">` → add `email`, required.

- `ok` sends the email and one optional field: accepted.
- `noEmail` forgot the required email.
- `withId` tried to send `id`, which the form type doesn't allow at all.
- If this gets hard to read, give the steps names: `type EditableFields = Omit<User, "id" | "email">;` and so on.

</En>
<Ur>

Ise andar se bahar ki taraf parhein:

1. `Omit<User, "id" | "email">` → `name`, `bio`, `age`.
2. `Partial<…>` → ye teeno ikhtiyari ban jate hain.
3. `& Pick<User, "email">` → `email` jorna, zaroori.

- `ok` email aur ek ikhtiyari field bhejta hai: qubool.
- `noEmail` zaroori email bhool gaya.
- `withId` ne `id` bhejne ki koshish ki, jis ki form type bilkul ijazat nahi deti.
- Agar ye parhna mushkil ho jaye to qadmon ko naam dein: `type EditableFields = Omit<User, "id" | "email">;` waghaira.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="How they're made: write your own">

<Tr>
<En>
Utility types aren't magic. Most are short **mapped types**: they loop over the keys of a type with `[K in keyof T]`. Once you see that, you can write your own.
</En>
<Ur>
Utility types jaadu nahi. Zyada tar chhoti **mapped types** hain: ye `[K in keyof T]` se type ki keys par loop chalati hain. Ye dekh lein to aap apni bhi likh sakte hain.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type MyPartial<T> = { [K in keyof T]?: T[K] };
type Nullable<T> = { [K in keyof T]: T[K] | null };

type Product = { name: string; price: number };

const draft: MyPartial<Product> = { name: "Lamp" };
const fromCsv: Nullable<Product> = { name: "Lamp", price: null };
const wrong: Nullable<Product> = { name: 5, price: null };
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(8,36): error TS2322: Type 'number' is not assignable to type 'string'.
```

<Happened>
<Tr>
<En>

- `[K in keyof T]` means "for each key `K` of `T`". `T[K]` is that key's type.
- `MyPartial` adds `?` to every key: that's exactly how the built-in `Partial` is written.
- `Nullable` (not built in) allows `null` in every field: handy for data from a spreadsheet or a form where cells can be empty.
- You won't write mapped types every day, but recognising `[K in keyof T]` helps you read library types and error messages.

</En>
<Ur>

- `[K in keyof T]` ka matlab "`T` ki har key `K` ke liye". `T[K]` us key ki type hai.
- `MyPartial` har key par `?` lagata hai: bilkul isi tarah bana banaya `Partial` likha gaya hai.
- `Nullable` (bana banaya nahi) har field me `null` ki ijazat deta hai: spreadsheet ya form ke data ke liye kaam ka jahan khaane khaali ho sakte hain.
- Mapped types aap roz nahi likhenge, magar `[K in keyof T]` pehchanna library types aur error messages parhne me madad deta hai.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Copying fields into a second type">

```ts
type User = { id: number; name: string; email: string };
type UserUpdate = { name?: string; email?: string };
```

<Tr>
<En>The two will drift apart the next time `User` changes.</En>
<Ur>Agli dafa `User` badle to dono alag ho jayengi.</Ur>
</Tr>

</Bad>
<Good title="Derive it">

```ts
type UserUpdate = Partial<Omit<User, "id">>;
```

</Good>
</Compare>

<Compare>
<Bad title="Trusting Omit to remove data">

```ts
function toPublic(user: User): Omit<User, "password"> {
  return user;   // compiles, but the password is still in the object
}
```

<Tr>
<En>An object with extra properties fits a smaller type, so this compiles, and the password is sent.</En>
<Ur>Izafi properties wala object chhoti type me fit ho jata hai, isliye ye compile ho jata hai, aur password bhej diya jata hai.</Ur>
</Tr>

</Bad>
<Good title="Remove it at runtime too">

```ts
function toPublic(user: User): Omit<User, "password"> {
  const { password, ...rest } = user;
  return rest;
}
```

</Good>
</Compare>

<Compare>
<Bad title="Using Omit on a union of strings">

```ts
type Status = "draft" | "published" | "archived";
type Live = Omit<Status, "archived">;   // not what you want
```

</Bad>
<Good title="Exclude is for unions">

```ts
type Live = Exclude<Status, "archived">;   // "draft" | "published"
```

</Good>
</Compare>

<Compare>
<Bad title="Partial for a create request">

```ts
function createUser(data: Partial<User>) { /* … */ }
createUser({});   // allowed, but a user needs a name and email
```

</Bad>
<Good title="Omit only what the server adds">

```ts
function createUser(data: Omit<User, "id" | "createdAt">) { /* … */ }
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Huge nested utility chains nobody can read.** Name the intermediate steps.
- **Thinking `Readonly` is deep.** It only locks the top level; nested objects can still be changed.
- **Forgetting `typeof`** in `ReturnType<createSession>`. You need `ReturnType<typeof createSession>`.
- **Using `Partial` to silence "missing property" errors** where the fields are actually required.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Utilities ki lambi nested zanjeeren jo koi parh na sake.** Beech ke qadmon ko naam dein.
- **Sochna ke `Readonly` gehra hai.** Ye sirf upar ki satah ko taala lagata hai; andar ke objects ab bhi badal sakte hain.
- **`ReturnType<createSession>` me `typeof` bhoolna.** `ReturnType<typeof createSession>` chahiye.
- **"Missing property" errors chup karane ke liye `Partial`** jahan fields asal me zaroori hain.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Describe your data **once**; derive the other shapes with utility types so they never drift.
- `Partial` = all optional (updates). `Required` = all required (after defaults). `Readonly` = can't reassign (top level only).
- `Pick` keeps some keys; `Omit` removes some keys. Both work on **object** types.
- `Record<Keys, Value>` with a union of keys forces an entry for every key.
- `Exclude`, `Extract` and `NonNullable` work on **unions**.
- `ReturnType<typeof fn>`, `Parameters<typeof fn>` and `Awaited<…>` take types from functions and promises.
- `as const` plus `(typeof list)[number]` gives a union type from an array you also use at runtime.
- Utility types change types only: remove secrets from objects with code, not just with `Omit`.

</En>
<Ur>

- Apna data **ek dafa** bayan karein; doosri shakalen utility types se nikalein taa ke kabhi alag na hon.
- `Partial` = sab ikhtiyari (updates). `Required` = sab zaroori (defaults ke baad). `Readonly` = dobara set nahi (sirf upar ki satah).
- `Pick` kuch keys rakhta hai; `Omit` kuch keys hatata hai. Dono **object** types par chalte hain.
- Keys ke union ke saath `Record<Keys, Value>` har key ki entry lazmi karta hai.
- `Exclude`, `Extract` aur `NonNullable` **unions** par chalte hain.
- `ReturnType<typeof fn>`, `Parameters<typeof fn>` aur `Awaited<…>` functions aur promises se types lete hain.
- `as const` aur `(typeof list)[number]` aisi array se union type dete hain jo chalte waqt bhi istemal hoti hai.
- Utility types sirf types badalti hain: objects se secrets code se hatayen, sirf `Omit` se nahi.

<DeepDive title="How the built-ins are written, and a few more">

The standard library defines them in a few lines each:

```text
type Partial<T>   = { [P in keyof T]?: T[P] };
type Required<T>  = { [P in keyof T]-?: T[P] };          // -? removes optional
type Readonly<T>  = { readonly [P in keyof T]: T[P] };
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Record<K extends keyof any, T> = { [P in K]: T };
type Exclude<T, U> = T extends U ? never : T;            // distributive conditional
type Extract<T, U> = T extends U ? T : never;
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
type NonNullable<T> = T & {};
```

**`Omit` is not checked strictly.** Its key parameter is `keyof any`, so `Omit<User, "pasword">` (a typo) is not an error; it just omits nothing. Some teams define a `StrictOmit<T, K extends keyof T>`.

**Distributive conditional types.** `Exclude` works because a conditional type applied to a union runs once per member and the results are joined.

**More built-ins:** `ReadonlyArray<T>`, `InstanceType<typeof SomeClass>`, `ConstructorParameters<…>`, `ThisParameterType<…>`, the string helpers `Uppercase<"a">`, `Lowercase`, `Capitalize`, `Uncapitalize`, and `NoInfer<T>` (TypeScript 5.4) to stop a parameter from influencing inference.

**Deep versions.** `Partial` and `Readonly` are shallow. Libraries such as type-fest provide `PartialDeep`, `ReadonlyDeep`, `SetOptional` and many others.

**Key remapping.** Mapped types can rename keys with `as` and template literal types, for example turning every `name` key into a `getName` method.

**`satisfies`.** `const config = { … } satisfies Record<string, Route>` checks a value against a type **without** widening it, so you keep the exact literal types for later `typeof` tricks.

</DeepDive>

<DeepDive title="Real world: the profile endpoint that leaked hashes">

A team had a typed API handler:

```ts
type User = { id: number; name: string; email: string; passwordHash: string };
type PublicUser = Omit<User, "passwordHash">;

async function getProfile(id: number): Promise<PublicUser> {
  const user = await db.user.findUnique({ where: { id } });
  return user;   // compiles
}
```

Everyone assumed `PublicUser` guaranteed the hash wasn't sent. But TypeScript allows an object with **extra** properties wherever a smaller type is expected, so returning the full database row compiled cleanly, and `res.json(profile)` sent `passwordHash` to every client. A security researcher found it by opening the browser's network tab.

The fixes, from quickest to most robust:

1. **Remove at runtime:** `const { passwordHash, ...publicUser } = user; return publicUser;`.
2. **Select only safe columns** in the query (`select: { id: true, name: true, email: true }`), so the secret never leaves the database.
3. **Validate output** with a schema that strips unknown keys before sending.

The lesson: utility types describe what you **intend**; only code decides what actually goes over the wire.

</DeepDive>

<DeepDive title="Security lens">

Derived types are a strong tool for keeping sensitive data in its place, as long as you remember they are compile-time only.

- **Separate input, storage and output types.** `CreateUserInput = Pick<User, "name" | "email">` for requests (no `isAdmin`, no `id`), `User` for the database, `PublicUser = Omit<User, "passwordHash" | "resetToken">` for responses. This blocks mass-assignment and data-leak bugs at the type level.
- **Back the types with code.** Strip fields with destructuring or explicit `select`s, and validate request bodies at runtime. A type alone never removes a field.
- **`Record<Role, Permission>`** makes adding a role a compile error until every permission table is updated, so a new role can't silently inherit a default.
- **`Readonly` for security config.** Lock allowed origins, rate limits and role lists so they aren't modified by accident (and consider `Object.freeze` for runtime protection).
- **Derive from the source of truth.** Generate `User` from your database schema (Prisma, Drizzle) or OpenAPI spec, so a new sensitive column shows up in the base type and you consciously decide whether each derived type includes it.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are utility types?">
They are built-in generic types that transform existing types, for example making all properties optional with Partial, selecting properties with Pick, removing them with Omit, or extracting the return type of a function with ReturnType. They let you derive related types from a single source of truth.
</QA>

<QA q="What is the difference between Pick and Omit?">
Pick builds a type containing only the listed keys of another type, and its keys are checked against keyof. Omit builds a type containing every key except the listed ones; its keys are not strictly checked, so a misspelt key is silently ignored.
</QA>

<QA q="What is the difference between Omit and Exclude?">
Omit removes properties from an object type by key. Exclude removes members from a union type. For example, Exclude on a union of status strings removes some statuses, while Omit on a User type removes some fields.
</QA>

<QA q="When would you use Partial, and what is a common misuse?">
Partial suits update or patch payloads where any subset of fields may be sent. A common misuse is typing creation input as Partial, which allows required fields to be missing; Omit of the server-generated fields is usually correct for creation.
</QA>

<QA q="How do you get the type of a function's return value or parameters?">
Use ReturnType or Parameters with typeof the function, for example ReturnType of typeof createSession. For async functions, wrap ReturnType in Awaited to get the resolved value rather than the promise.
</QA>

<QA q="How can you keep a runtime list and a union type in sync?">
Declare the list once with as const so its elements keep their literal types, then derive the union with typeof the list indexed by number. The same list can be used at runtime for validation and display.
</QA>

<QA q="Are utility types enforced at runtime?">
No. Like all types they are erased. Returning an object with extra properties where an Omit type is expected compiles, so sensitive fields must be removed in code and inputs must be validated at runtime.
</QA>

</DeepDive>
