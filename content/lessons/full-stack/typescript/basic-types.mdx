<BigIdea>
<Tr>
<En>
**TypeScript** is **JavaScript plus labels**. Next to a variable or a function's inputs you write what **kind** of value belongs there: `let age: number = 25;`. A program called the **TypeScript checker** (`tsc`) reads your code **before it runs** and complains if anything doesn't fit: a string where a number should be, a property name with a typo, a value that might be `null`. Those labels are called **type annotations**, and often you don't even need them, because TypeScript can **infer** (work out) the type from the value. When the check passes, the labels are simply removed and ordinary JavaScript runs. So TypeScript doesn't change what your program does; it **catches mistakes early**, while you're still typing, instead of when a user clicks a button.
</En>
<Ur>
**TypeScript** **JavaScript aur labels** ka naam hai. Variable ya function ke inputs ke saath aap likhte hain ke wahan kis **qisam** ki value aayegi: `let age: number = 25;`. **TypeScript checker** (`tsc`) naam ka program aap ka code **chalne se pehle** parhta hai aur agar koi cheez fit na ho to shikayat karta hai: jahan number hona chahiye wahan string, property ke naam me typo, aisi value jo `null` ho sakti hai. In labels ko **type annotations** kehte hain, aur aksar inki zaroorat bhi nahi parti, kyun ke TypeScript value se type khud **infer** kar leta hai (andaza laga leta hai). Check paas hone par labels hata diye jate hain aur aam JavaScript chalti hai. Yaani TypeScript aap ke program ka kaam nahi badalta; ye **ghaltiyan jaldi pakarta hai**, jab aap abhi type kar rahe hote hain, us waqt nahi jab user button dabata hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

A **type annotation** is a colon and a type after a name:

```ts
let userName: string = "Sara";
let age: number = 25;
let isMember: boolean = true;

function getTotal(price: number, quantity: number): number {
  return price * quantity;
}
```

Read `age: number` as **"age, which is a number"**. The `: number` after the `( )` of the function means "this function gives back a number".

</En>
<Ur>

**Type annotation** naam ke baad colon aur type hai:

```ts
let userName: string = "Sara";
let age: number = 25;
let isMember: boolean = true;

function getTotal(price: number, quantity: number): number {
  return price * quantity;
}
```

`age: number` ko aise parhein: **"age, jo ek number hai"**. Function ke `( )` ke baad wala `: number` ka matlab hai "ye function number wapas deta hai".

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Mistakes show up while you type,** with a red underline in the editor, not as a crash in front of a user.
- **Autocomplete.** The editor knows `user` has `name` and `email`, so it suggests them and catches `user.emial`.
- **Safe changes.** Rename a property and TypeScript lists every place that needs updating.
- **Code explains itself.** `function send(to: string, amount: number)` tells you how to call it.
- **It's the default.** Most React and Next.js jobs and projects use TypeScript.

</En>
<Ur>

- **Ghaltiyan type karte waqt nazar aati hain,** editor me laal lakeer ke saath, user ke saamne crash ki shakal me nahi.
- **Autocomplete.** Editor ko maloom hai ke `user` ke paas `name` aur `email` hain, isliye wo inhe suggest karta hai aur `user.emial` pakar leta hai.
- **Mehfooz tabdeeliyan.** Property ka naam badlein aur TypeScript har wo jagah bata deta hai jise update karna hai.
- **Code khud samjhata hai.** `function send(to: string, amount: number)` batata hai ke ise kaise call karna hai.
- **Yahi default hai.** Zyada tar React aur Next.js ki jobs aur projects TypeScript istemal karte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Where | Annotate? |
| --- | --- |
| Function **parameters** | **Yes**, always |
| Variables given a value right away | Usually **no**: TypeScript infers it |
| Empty variables or empty arrays filled later | **Yes** |
| A function's **return** type | Optional; useful for exported functions |
| Data from outside (APIs, forms, JSON) | **Yes**, and check it at runtime too |

</En>
<Ur>

| Kahan | Annotation lagayen? |
| --- | --- |
| Function ke **parameters** | **Haan**, hamesha |
| Variables jinhe foran value mil jaye | Aam taur par **nahi**: TypeScript khud nikal leta hai |
| Khaali variables ya khaali arrays jo baad me bharen | **Haan** |
| Function ki **return** type | Ikhtiyari; export hone wale functions ke liye mufeed |
| Bahar se aane wala data (APIs, forms, JSON) | **Haan**, aur chalte waqt bhi check karein |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Write code in a `.ts` file (or `.tsx` for React).
2. The editor checks it as you type. You can also run the checker yourself: `npx tsc --noEmit`.
3. Fix what it reports.
4. A build tool (Next.js, Vite, `tsc`) removes the types and produces plain JavaScript.

</En>
<Ur>

1. Code `.ts` file me likhein (React ke liye `.tsx`).
2. Editor type karte hi check karta hai. Checker khud bhi chala sakte hain: `npx tsc --noEmit`.
3. Jo wo bataye use theek karein.
4. Build tool (Next.js, Vite, `tsc`) types hata kar saada JavaScript bana deta hai.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **parcel sorting centre**. Every slot on the shelf has a **label**: "Letters", "Small boxes", "Fragile". In plain JavaScript, there are no labels: anyone can drop anything anywhere, and you only find out a glass vase was thrown in the "Heavy items" bin when it **breaks** at the customer's door.

TypeScript is a **checker at the door** who reads the label on every slot and every parcel **before** the delivery van leaves. "This slot says *Letters*, but you put a box in it. Fix that first." Nothing is delivered until everything matches.

Once the check is done, the labels don't travel with the parcels. The van carries exactly the same parcels it would have carried anyway. That's why **types disappear when the code runs**: they're for checking, not for the journey.

</En>
<Ur>

Ek **parcel chhantne wale markaz** ka sochein. Shelf ke har khaane par **label** laga hai: "Letters", "Chhote dabbe", "Nazuk". Saada JavaScript me koi label nahi: koi bhi kuch bhi kahin bhi rakh sakta hai, aur pata tab chalta hai jab "Bhaari saman" wale dabbe me phenka gaya sheeshe ka guldaan customer ke darwaze par **toot** jata hai.

TypeScript **darwaze par khara checker** hai jo delivery van chalne se **pehle** har khaane aur har parcel ka label parhta hai. "Is khaane par *Letters* likha hai, magar aap ne dabba rakh diya. Pehle ise theek karein." Jab tak sab kuch mil na jaye kuch deliver nahi hota.

Check ho jane ke baad labels parcels ke saath safar nahi karte. Van wahi parcels le jati hai jo waise bhi le jati. Isi liye **code chalte waqt types ghayab ho jati hain**: ye check karne ke liye hain, safar ke liye nahi.

</Ur>
</Tr>

## Learn it step by step

<Tr>
<En>

Two kinds of examples appear below:

- **TypeScript** blocks have a **Run** button. The page removes the types and runs the code, just like a real build does.
- **Checker** blocks show what TypeScript's checker, `tsc`, said about some code. They start with `cat > app.ts <<'EOF'` … `EOF`, which only means "save these lines into a file called `app.ts`". The last line, `npx tsc --noEmit --strict app.ts`, means "check this file with all safety checks on, and don't produce any JavaScript". We ran each one for real; the output is exactly what it printed.

</En>
<Ur>

Neeche do qisam ki misaalen hain:

- **TypeScript** blocks par **Run** ka button hai. Page types hata kar code chalata hai, bilkul jaise asli build karta hai.
- **Checker** blocks dikhate hain ke TypeScript ke checker `tsc` ne kisi code ke baare me kya kaha. Ye `cat > app.ts <<'EOF'` … `EOF` se shuru hote hain, jis ka matlab sirf ye hai ke "ye lines `app.ts` naam ki file me mehfooz karo". Aakhri line `npx tsc --noEmit --strict app.ts` ka matlab hai "is file ko tamam hifazati checks ke saath check karo, aur koi JavaScript na banao". Humne har ek asal me chalaya; output bilkul wahi hai jo us ne print kiya.

</Ur>
</Tr>

<Walkthrough>

<Step title="The mistake JavaScript only finds too late">

<Tr>
<En>
Here is plain JavaScript with a one-letter typo: `nme` instead of `name`. JavaScript happily starts running, and only crashes when it reaches the broken line.
</En>
<Ur>
Ye saada JavaScript hai jis me ek harf ka typo hai: `name` ke bajaye `nme`. JavaScript khushi se chalna shuru kar deta hai, aur tab crash hota hai jab toote hue line tak pohanchta hai.
</Ur>
</Tr>

```javascript
function welcome(user) {
  return "Welcome, " + user.name.toUpperCase();
}

console.log("Page loaded");

try {
  console.log(welcome({ nme: "Sara" }));
} catch (error) {
  console.log(error.name + ": " + error.message);
}
```

```text output
Page loaded
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
```

<Happened>
<Tr>
<En>

- "Page loaded" printed: JavaScript had no idea anything was wrong.
- `user.name` was `undefined` (the object has `nme`, not `name`), and asking `undefined` for `toUpperCase` crashed.
- In a real app this crash happens **in a user's browser**, maybe weeks after the typo was written, maybe only on one rarely used page.

</En>
<Ur>

- "Page loaded" print hua: JavaScript ko bilkul andaza nahi tha ke kuch ghalat hai.
- `user.name` `undefined` tha (object me `nme` hai, `name` nahi), aur `undefined` se `toUpperCase` maangne par crash hua.
- Asli app me ye crash **user ke browser me** hota hai, shayad typo likhne ke hafton baad, shayad sirf kisi kam istemal hone wale page par.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="TypeScript finds it before anything runs">

<Tr>
<En>
Now the same code in TypeScript. The only change is `user: { name: string }`, which says "`user` is an object with a `name` that is a string". Then we ask the checker.
</En>
<Ur>
Ab wahi code TypeScript me. Sirf ek tabdeeli hai: `user: { name: string }`, jo kehta hai "`user` aisa object hai jis ka `name` string hai". Phir hum checker se poochte hain.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function welcome(user: { name: string }) {
  return "Welcome, " + user.name.toUpperCase();
}

console.log(welcome({ nme: "Sara" }));
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,23): error TS2561: Object literal may only specify known properties, but 'nme' does not exist in type '{ name: string; }'. Did you mean to write 'name'?
```

<Happened>
<Tr>
<En>

- `app.ts(5,23)` means **line 5, column 23**: exactly where `nme` is.
- The message says `nme` isn't a property the function accepts, and even suggests the fix: *Did you mean to write 'name'?*
- Nothing ran. The mistake was caught at your desk, not in a user's browser. In an editor like VS Code you'd see this as a red underline the moment you typed `nme`.
- `TS2561` is the error's code number. You can search for it if a message is unclear.

</En>
<Ur>

- `app.ts(5,23)` ka matlab hai **line 5, column 23**: bilkul wahan jahan `nme` hai.
- Paighaam kehta hai ke `nme` aisi property nahi jo function qubool karta ho, aur hal bhi batata hai: *Did you mean to write 'name'?*
- Kuch nahi chala. Ghalti aap ki mez par pakri gayi, user ke browser me nahi. VS Code jaise editor me ye `nme` type karte hi laal lakeer ki shakal me nazar aati.
- `TS2561` error ka code number hai. Paighaam samajh na aaye to ise search kar sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The three everyday types">

<Tr>
<En>
The basic types have the same names as the JavaScript types you already know, in lowercase: `string`, `number`, `boolean`. Put a colon and the type after the variable name.
</En>
<Ur>
Bunyadi types ke naam wahi hain jo JavaScript ki types ke aap pehle se jante hain, chhote huroof me: `string`, `number`, `boolean`. Variable ke naam ke baad colon aur type likhein.
</Ur>
</Tr>

```typescript
let userName: string = "Sara";
let age: number = 25;
let isMember: boolean = true;

age = age + 1;
userName = userName + " Lee";

console.log(userName, age, isMember);
console.log(typeof age);
```

```text output
Sara Lee 26 true
number
```

<Happened>
<Tr>
<En>

- `: string`, `: number` and `: boolean` are the annotations. Changing a value is fine as long as the **type** stays the same.
- `typeof age` is still `"number"`: TypeScript uses the same types JavaScript already has.
- Use lowercase. `String` and `Number` (capital letters) are different things, the wrapper objects, and you almost never want them.

</En>
<Ur>

- `: string`, `: number` aur `: boolean` annotations hain. Value badalna theek hai jab tak **type** wahi rahe.
- `typeof age` ab bhi `"number"` hai: TypeScript wahi types istemal karta hai jo JavaScript ke paas pehle se hain.
- Chhote huroof lein. `String` aur `Number` (bare huroof) alag cheezen hain, wrapper objects, aur inki zaroorat taqreeban kabhi nahi parti.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Putting the wrong type in">

<Tr>
<En>
Once a variable is a `number`, it stays a number. Here's what happens when we try to put text in it, or call a method that numbers don't have.
</En>
<Ur>
Variable ek dafa `number` ho jaye to number hi rehta hai. Dekhein kya hota hai jab hum us me text rakhne ki koshish karte hain, ya aisa method call karte hain jo numbers ke paas nahi.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
let age: number = 25;
age = "twenty-six";

let city: string = "Austin";
city.push("!");
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(2,1): error TS2322: Type 'string' is not assignable to type 'number'.
app.ts(5,6): error TS2339: Property 'push' does not exist on type 'string'.
```

<Happened>
<Tr>
<En>

- **TS2322**, *"Type X is not assignable to type Y"*, is the error you'll see most. It means "you're putting the wrong kind of thing in this slot".
- **TS2339**, *"Property X does not exist on type Y"*, means "this kind of value doesn't have that". `push` is an array method; strings don't have it.
- Every error is found in one pass. You fix them all before the program ever runs.

</En>
<Ur>

- **TS2322**, *"Type X is not assignable to type Y"*, wo error hai jo sab se zyada nazar aayega. Matlab "aap is khaane me ghalat qisam ki cheez rakh rahe hain".
- **TS2339**, *"Property X does not exist on type Y"*, ka matlab "is qisam ki value ke paas ye cheez nahi". `push` array ka method hai; strings ke paas nahi.
- Saare errors ek hi dafa me mil jate hain. Program chalne se pehle aap sab theek kar lete hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Let TypeScript work out the type">

<Tr>
<En>
You don't have to label everything. When you give a variable a value straight away, TypeScript **infers** its type from that value, and checks it just as strictly.
</En>
<Ur>
Har cheez par label lagana zaroori nahi. Jab aap variable ko foran value dete hain to TypeScript us value se type **infer** kar leta hai, aur utni hi sakhti se check karta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
let city = "Austin";
let visitors = 120;
const prices = [5, 12, 8];

city = 42;
visitors = visitors + 1;
prices.push("free");
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,1): error TS2322: Type 'number' is not assignable to type 'string'.
app.ts(7,13): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```

<Happened>
<Tr>
<En>

- `let city = "Austin"` has no annotation, but TypeScript saw a string and made `city` a `string`. So `city = 42` is an error.
- `visitors + 1` is fine: a number plus a number.
- `[5, 12, 8]` became `number[]` (an array of numbers), so pushing `"free"` is an error.
- **The rule most teams follow:** don't annotate what TypeScript already knows. Write `let city = "Austin"`, not `let city: string = "Austin"`. Annotate function parameters and anything that starts empty.

</En>
<Ur>

- `let city = "Austin"` par koi annotation nahi, magar TypeScript ne string dekhi aur `city` ko `string` bana diya. Isliye `city = 42` error hai.
- `visitors + 1` theek hai: number jama number.
- `[5, 12, 8]` `number[]` (numbers ki array) ban gaya, isliye `"free"` push karna error hai.
- **Zyada tar teams ka qaida:** jo TypeScript pehle se jaanta hai us par annotation na lagayen. `let city = "Austin"` likhein, `let city: string = "Austin"` nahi. Function ke parameters aur khaali shuru hone wali cheezon par annotation lagayen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Typing functions: inputs and output">

<Tr>
<En>
Function **parameters** need annotations, because TypeScript can't guess what callers will pass. You can also annotate the **return type** after the `( )`.
</En>
<Ur>
Function ke **parameters** ko annotations chahiyen, kyun ke TypeScript andaza nahi laga sakta ke call karne wale kya denge. `( )` ke baad **return type** par bhi annotation lagayi ja sakti hai.
</Ur>
</Tr>

```typescript
function getTotal(price: number, quantity: number): number {
  return price * quantity;
}

const formatPrice = (amount: number): string => "$" + amount.toFixed(2);

function greet(name: string, greeting: string = "Hello"): string {
  return greeting + ", " + name + "!";
}

console.log(getTotal(12.5, 3));
console.log(formatPrice(getTotal(12.5, 3)));
console.log(greet("Sara"));
```

```text output
37.5
$37.50
Hello, Sara!
```

<Happened>
<Tr>
<En>

- `(price: number, quantity: number)` labels each input. `): number` says the function gives back a number.
- Arrow functions are typed the same way: `(amount: number): string => …`.
- A parameter with a default value (`greeting: string = "Hello"`) is automatically optional for callers.
- Because `getTotal` returns a number, passing its result to `formatPrice` (which wants a number) is safe.

</En>
<Ur>

- `(price: number, quantity: number)` har input par label lagata hai. `): number` kehta hai ke function number wapas deta hai.
- Arrow functions bhi isi tarah type hote hain: `(amount: number): string => …`.
- Default value wala parameter (`greeting: string = "Hello"`) call karne walon ke liye khud ba khud ikhtiyari ho jata hai.
- Chunke `getTotal` number wapas karta hai, us ka nateeja `formatPrice` (jise number chahiye) ko dena mehfooz hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Calling a function the wrong way">

<Tr>
<En>
This is where TypeScript saves the most time: every call to a typed function is checked, everywhere in your project.
</En>
<Ur>
Yahan TypeScript sab se zyada waqt bachata hai: typed function ki har call, poore project me har jagah, check hoti hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
function getTotal(price: number, quantity: number): number {
  return price * quantity;
}

getTotal("10", 2);
getTotal(10);

function getLabel(price: number): string {
  return price;
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,10): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
app.ts(6,1): error TS2554: Expected 2 arguments, but got 1.
app.ts(9,3): error TS2322: Type 'number' is not assignable to type 'string'.
```

<Happened>
<Tr>
<En>

- `getTotal("10", 2)`: the text `"10"` isn't a number. In plain JavaScript this would quietly work by accident with `*`, and break later with `+`.
- `getTotal(10)`: a missing argument. JavaScript would have made `quantity` `undefined` and returned `NaN`.
- In `getLabel`, the function promised a `string` but returned a number. The checker holds you to the return type you wrote.

</En>
<Ur>

- `getTotal("10", 2)`: text `"10"` number nahi. Saade JavaScript me ye `*` ke saath ittefaq se chupke se chal jata, aur baad me `+` ke saath toot jata.
- `getTotal(10)`: ek argument ghayab. JavaScript `quantity` ko `undefined` bana kar `NaN` wapas karta.
- `getLabel` me function ne `string` ka waada kiya magar number wapas kiya. Checker aap ko aap ki likhi return type ka paband rakhta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Arrays and tuples">

<Tr>
<En>
An array type is the item type followed by `[]`: `string[]` means "an array of strings". A **tuple** is an array with a fixed length where each position has its own type, such as a pair of coordinates.
</En>
<Ur>
Array ki type item ki type ke baad `[]` hai: `string[]` ka matlab "strings ki array". **Tuple** muqarrar lambai wali array hai jis me har jagah ki apni type hoti hai, jaise coordinates ka jora.
</Ur>
</Tr>

```typescript
const tags: string[] = ["sale", "new"];
const scores: number[] = [90, 85, 72];
const cart: string[] = [];

cart.push("milk");
cart.push("bread");

const point: [number, number] = [10, 20];
const entry: [string, number] = ["Sara", 92];

const [x, y] = point;
console.log(tags.length, cart, x + y);
console.log(entry[0] + " scored " + entry[1]);
```

```text output
2 [ 'milk', 'bread' ] 30
Sara scored 92
```

<Happened>
<Tr>
<En>

- `const cart: string[] = []` **needs** the annotation. An empty array gives TypeScript nothing to infer from.
- `[number, number]` is a tuple: exactly two numbers, in that order. `[string, number]` is a name then a score.
- Tuples work with destructuring: `const [x, y] = point` gives two numbers.
- You'll also see `Array<string>`: it means exactly the same as `string[]`.

</En>
<Ur>

- `const cart: string[] = []` ko annotation ki **zaroorat** hai. Khaali array se TypeScript ko andaza lagane ke liye kuch nahi milta.
- `[number, number]` tuple hai: bilkul do numbers, isi tarteeb me. `[string, number]` pehle naam phir score.
- Tuples destructuring ke saath chalte hain: `const [x, y] = point` do numbers deta hai.
- `Array<string>` bhi nazar aayega: is ka matlab bilkul wahi hai jo `string[]` ka.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Object types and optional properties">

<Tr>
<En>
An object type lists each property and its type, inside `{ }`. A `?` after a property name makes it **optional**: it may be missing.
</En>
<Ur>
Object ki type `{ }` ke andar har property aur us ki type likhti hai. Property ke naam ke baad `?` use **ikhtiyari** bana deta hai: wo ghayab ho sakti hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
let product: { name: string; price: number; discount?: number };

product = { name: "Bag", price: 40 };
product = { name: "Pen", price: 2, discount: 0.5 };
product = { name: "Shoes" };
product = { name: "Hat", price: 15, colour: "red" };

const finalPrice = product.price - product.discount;
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,1): error TS2741: Property 'price' is missing in type '{ name: string; }' but required in type '{ name: string; price: number; discount?: number | undefined; }'.
app.ts(6,37): error TS2353: Object literal may only specify known properties, and 'colour' does not exist in type '{ name: string; price: number; discount?: number | undefined; }'.
app.ts(8,36): error TS18048: 'product.discount' is possibly 'undefined'.
```

<Happened>
<Tr>
<En>

- Lines 3 and 4 are fine: `discount` is optional, so it can be there or not.
- Line 5 forgot the required `price`.
- Line 6 added `colour`, which the type doesn't mention. TypeScript assumes that's a typo or a mistake.
- Line 8 is the clever one: because `discount` is optional, it might be `undefined`, and `40 - undefined` is `NaN`. TypeScript makes you handle that case (for example `product.discount ?? 0`).
- Writing long object types inline gets messy. The next lesson shows how to give them a name with `interface` and `type`.

</En>
<Ur>

- Lines 3 aur 4 theek hain: `discount` ikhtiyari hai, isliye ho ya na ho.
- Line 5 zaroori `price` bhool gayi.
- Line 6 ne `colour` jor diya, jis ka type me zikr hi nahi. TypeScript samajhta hai ke ye typo ya ghalti hai.
- Line 8 sab se hoshiyar hai: chunke `discount` ikhtiyari hai, wo `undefined` ho sakta hai, aur `40 - undefined` `NaN` hai. TypeScript aap se ye surat sambhalwata hai (maslan `product.discount ?? 0`).
- Lambi object types ko line ke andar likhna gadbad ho jata hai. Agla lesson dikhata hai ke `interface` aur `type` se inhe naam kaise diya jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Union types: this or that">

<Tr>
<En>
A **union type**, written with `|`, means "one of these". `string | number` accepts either. You'll often see it with `null` for "a value, or nothing yet". Before you use a union, you **check** which one you have; TypeScript follows your `if` and knows the type inside it.
</En>
<Ur>
**Union type**, jo `|` se likhi jati hai, ka matlab "in me se ek". `string | number` dono me se koi bhi qubool karta hai. Ye aksar `null` ke saath nazar aata hai, "koi value, ya abhi kuch nahi" ke liye. Union istemal karne se pehle aap **check** karte hain ke aap ke paas kaun si hai; TypeScript aap ke `if` ko samajhta hai aur andar ki type jaanta hai.
</Ur>
</Tr>

```typescript
function formatId(id: string | number): string {
  if (typeof id === "number") {
    return "#" + id.toFixed(0);
  }
  return "#" + id.toUpperCase();
}

let selectedSize: string | null = null;

function describe(size: string | null): string {
  if (size === null) {
    return "No size chosen";
  }
  return "Size " + size;
}

console.log(formatId(42), formatId("ab7"));
console.log(describe(selectedSize));
selectedSize = "M";
console.log(describe(selectedSize));
```

```text output
#42 #AB7
No size chosen
Size M
```

<Happened>
<Tr>
<En>

- Inside `if (typeof id === "number")`, TypeScript knows `id` is a number, so `toFixed` is allowed. After that `if` returns, the only thing left is a string, so `toUpperCase` is allowed. This is called **narrowing**.
- `string | null` is how you say "maybe missing". After `if (size === null) return …`, TypeScript knows `size` is a string.
- Without the checks, TypeScript would refuse, because `toFixed` doesn't exist on strings and you can't add `null` to text safely.

</En>
<Ur>

- `if (typeof id === "number")` ke andar TypeScript jaanta hai ke `id` number hai, isliye `toFixed` ki ijazat hai. Wo `if` return kar de to baqi sirf string bachti hai, isliye `toUpperCase` ki ijazat hai. Ise **narrowing** kehte hain.
- `string | null` "shayad ghayab" kehne ka tareeqa hai. `if (size === null) return …` ke baad TypeScript jaanta hai ke `size` string hai.
- Checks ke baghair TypeScript inkar karta, kyun ke strings par `toFixed` nahi hota aur `null` ko text me mehfooz tareeqe se nahi joda ja sakta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Literal types: only these exact values">

<Tr>
<En>
A type can be an exact value. `"small" | "medium" | "large"` allows only those three strings. This is perfect for settings and statuses, and the editor will autocomplete the choices.
</En>
<Ur>
Type ek bilkul muqarrar value bhi ho sakti hai. `"small" | "medium" | "large"` sirf in teen strings ki ijazat deta hai. Ye settings aur statuses ke liye behtareen hai, aur editor in chunaavon ka autocomplete bhi karta hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
let size: "small" | "medium" | "large" = "medium";
size = "large";
size = "huge";

function setStatus(status: "draft" | "published") {
  console.log(status);
}
setStatus("published");
setStatus("Published");
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(3,1): error TS2322: Type '"huge"' is not assignable to type '"large" | "medium" | "small"'.
app.ts(9,11): error TS2345: Argument of type '"Published"' is not assignable to parameter of type '"draft" | "published"'.
```

<Happened>
<Tr>
<En>

- `"huge"` isn't one of the three allowed sizes.
- `"Published"` with a capital P isn't `"published"`. A plain `string` type would have let that typo through, and some `if (status === "published")` check would silently never be true.
- Literal unions are one of TypeScript's most useful features. The "Union, Intersection and Literal Types" lesson goes deeper.

</En>
<Ur>

- `"huge"` teen jaiz sizes me se nahi.
- Bare P wala `"Published"` `"published"` nahi hai. Saadi `string` type ye typo guzarne deti, aur koi `if (status === "published")` check chupke se kabhi sach na hota.
- Literal unions TypeScript ki sab se mufeed khoobiyon me se hain. "Union, Intersection and Literal Types" lesson is me aur gehrai tak jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="any vs unknown">

<Tr>
<En>
Sometimes you really don't know a type, for example data you just received. **`any`** switches checking **off**: anything goes, so bugs get through. **`unknown`** means "could be anything, so prove what it is before you use it". Prefer `unknown`.
</En>
<Ur>
Kabhi kabhi aap ko waqai type maloom nahi hoti, maslan abhi aaya hua data. **`any`** checking **band** kar deta hai: sab chalta hai, isliye bugs guzar jate hain. **`unknown`** ka matlab hai "kuch bhi ho sakta hai, isliye istemal se pehle sabit karo ke ye kya hai". `unknown` ko tarjeeh dein.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
const fromApiA: any = JSON.parse('{"price": "12"}');
const totalA: number = fromApiA.price * 2 + fromApiA.prise;

const fromApiB: unknown = JSON.parse('{"price": "12"}');
const totalB = fromApiB.price * 2;

if (typeof fromApiB === "object" && fromApiB !== null && "price" in fromApiB) {
  console.log(fromApiB.price);
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(5,16): error TS18046: 'fromApiB' is of type 'unknown'.
```

<Happened>
<Tr>
<En>

- Line 2 has **two** bugs: `price` is really the text `"12"`, and `prise` is a typo. With `any`, TypeScript reported **nothing**. `any` is like taking the checker off duty.
- Line 5 used `unknown`, and TypeScript refused: "you haven't checked what this is yet".
- Lines 7–9 do the check (it's an object, not null, and has a `price`), and then reading `price` is allowed.
- In real projects you'd use a validation library such as **zod** to do these checks in one line. The rule: **`any` turns TypeScript off; `unknown` keeps it on.**

</En>
<Ur>

- Line 2 me **do** bugs hain: `price` asal me text `"12"` hai, aur `prise` typo hai. `any` ke saath TypeScript ne **kuch** nahi bataya. `any` checker ko chhutti par bhejne jaisa hai.
- Line 5 ne `unknown` istemal kiya, aur TypeScript ne inkar kar diya: "aap ne abhi check nahi kiya ke ye kya hai".
- Lines 7–9 check karti hain (ye object hai, null nahi, aur is me `price` hai), aur phir `price` parhne ki ijazat hai.
- Asli projects me ye checks ek line me karne ke liye **zod** jaisi validation library lagti hai. Qaida: **`any` TypeScript ko band karta hai; `unknown` use chalu rakhta hai.**

</Ur>
</Tr>
</Happened>

</Step>

<Step title="void and never">

<Tr>
<En>
Two special return types. **`void`** means the function doesn't give anything back; it just does something (logs, saves). **`never`** means the function never finishes normally: it always throws an error or runs forever.
</En>
<Ur>
Do khaas return types. **`void`** ka matlab function kuch wapas nahi deta; bas kuch karta hai (log, save). **`never`** ka matlab function kabhi aam tareeqe se khatam nahi hota: hamesha error phenkta hai ya hamesha chalta rehta hai.
</Ur>
</Tr>

```typescript
function logOrder(id: number): void {
  console.log("Order", id, "saved");
}

function fail(message: string): never {
  throw new Error(message);
}

function getDiscount(code: string): number {
  if (code === "SAVE10") return 10;
  if (code === "SAVE20") return 20;
  fail("Unknown code: " + code);
}

logOrder(501);
console.log(getDiscount("SAVE20"));
try {
  getDiscount("FREE");
} catch (error) {
  console.log((error as Error).message);
}
```

```text output
Order 501 saved
20
Unknown code: FREE
```

<Happened>
<Tr>
<En>

- `logOrder` returns `void`: callers know not to use its result.
- `fail` returns `never`. TypeScript understands that code after a call to `fail` can't be reached, so `getDiscount` is still allowed to promise a `number` even though its last line doesn't return one.
- `(error as Error)` tells TypeScript "treat this as an `Error`". Caught errors are `unknown` in strict mode, because anything can be thrown. `as` is called a **type assertion**: use it sparingly, because TypeScript just believes you.

</En>
<Ur>

- `logOrder` `void` return karta hai: call karne walon ko maloom hai ke is ka nateeja istemal nahi karna.
- `fail` `never` return karta hai. TypeScript samajhta hai ke `fail` ki call ke baad ka code pohancha nahi ja sakta, isliye `getDiscount` ab bhi `number` ka waada kar sakta hai halanke us ki aakhri line kuch wapas nahi karti.
- `(error as Error)` TypeScript se kehta hai "ise `Error` samjho". Strict mode me pakre gaye errors `unknown` hote hain, kyun ke kuch bhi phenka ja sakta hai. `as` ko **type assertion** kehte hain: kam istemal karein, kyun ke TypeScript bas aap par yaqeen kar leta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Types disappear when the code runs">

<Tr>
<En>
This is the most important thing to understand about TypeScript. The types are **removed** before the code runs. They check your code; they don't check the data that arrives while the program is running.
</En>
<Ur>
TypeScript ke baare me samajhne wali sab se ahem baat yahi hai. Code chalne se pehle types **hata** di jati hain. Ye aap ka code check karti hain; program chalte waqt aane wala data check nahi kartin.
</Ur>
</Tr>

```typescript
function double(n: number): number {
  return n * 2;
}

const fromForm: any = "21";
console.log(double(fromForm));

const typed = "21" as unknown as number;
console.log(typed + 1);
console.log(typeof typed);
```

```text output
42
211
string
```

<Happened>
<Tr>
<En>

- We forced text into `double` through `any`. TypeScript was silenced, and at runtime there was no check at all: `"21" * 2` happened to give 42.
- `as unknown as number` lies to TypeScript. It believes us, so `typed + 1` looks like maths, but the value is really the text `"21"`, and the result is `"211"`.
- `typeof typed` shows the truth: it's a `string`. The `number` label was gone before the code ran.
- So: TypeScript protects the code **you** write. Anything from **outside** (forms, URLs, APIs, files, `JSON.parse`) must still be checked while the program runs. That's what validation libraries such as zod are for.

</En>
<Ur>

- Humne `any` ke zariye text ko zabardasti `double` me dala. TypeScript ko chup kara diya gaya, aur chalte waqt koi check tha hi nahi: `"21" * 2` ittefaq se 42 de gaya.
- `as unknown as number` TypeScript se jhoot bolta hai. Wo hum par yaqeen karta hai, isliye `typed + 1` hisaab lagta hai, magar value asal me text `"21"` hai, aur nateeja `"211"`.
- `typeof typed` sach dikhata hai: ye `string` hai. `number` ka label code chalne se pehle hi ja chuka tha.
- Yaani: TypeScript us code ki hifazat karta hai jo **aap** likhte hain. **Bahar** se aane wali har cheez (forms, URLs, APIs, files, `JSON.parse`) ko program chalte waqt bhi check karna zaroori hai. Zod jaisi validation libraries isi liye hain.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Annotating everything">

```ts
const city: string = "Austin";
const count: number = 3;
const items: string[] = ["a", "b"];
```

<Tr>
<En>It isn't wrong, but it's noise. TypeScript already knew all three.</En>
<Ur>Ye ghalat nahi, magar faltu hai. TypeScript teeno pehle se jaanta tha.</Ur>
</Tr>

</Bad>
<Good title="Annotate parameters and empty starts">

```ts
const city = "Austin";
const items: string[] = [];
function greet(name: string) { /* … */ }
```

</Good>
</Compare>

<Compare>
<Bad title="Reaching for any to silence an error">

```ts
const user: any = await response.json();
user.nmae.toUpperCase();   // no error until it crashes
```

</Bad>
<Good title="unknown, then check (or validate)">

```ts
const data: unknown = await response.json();
// check the shape, or use a validator, before using it
```

</Good>
</Compare>

<Compare>
<Bad title="Capitalised type names">

```ts
let name: String = "Sara";
let total: Number = 10;
```

</Bad>
<Good title="Lowercase primitives">

```ts
let name: string = "Sara";
let total: number = 10;
```

</Good>
</Compare>

<Compare>
<Bad title="Ignoring a possible undefined">

```ts
function finalPrice(price: number, discount?: number) {
  return price - discount;   // error: possibly undefined
}
```

</Bad>
<Good title="Give it a fallback">

```ts
function finalPrice(price: number, discount?: number) {
  return price - (discount ?? 0);
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Using `as` to make errors go away.** An assertion is a promise you make to TypeScript. If it's wrong, the bug comes back at runtime.
- **Trusting types for outside data.** A `User` type on `await res.json()` is a hope, not a check.
- **Turning `strict` off** because the errors are annoying. Most of TypeScript's value comes from strict mode.
- **Fighting the error message.** Read it slowly: it says what you gave, what was expected, and where.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Errors ghayab karne ke liye `as` istemal karna.** Assertion aap ka TypeScript se kiya gaya waada hai. Ghalat ho to bug chalte waqt wapas aa jata hai.
- **Bahar ke data ke liye types par bharosa.** `await res.json()` par `User` type ek umeed hai, check nahi.
- **Errors tang karein to `strict` band kar dena.** TypeScript ki zyada tar qadr strict mode se aati hai.
- **Error message se larna.** Ise aahista parhein: ye batata hai aap ne kya diya, kya chahiye tha, aur kahan.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- TypeScript is JavaScript plus types, checked **before** the code runs, then removed.
- Annotate with a colon: `age: number`, `name: string`, `isMember: boolean`, lowercase.
- Let **inference** handle values set right away; annotate **parameters** and things that start empty.
- Arrays: `string[]`. Tuples: `[number, number]`. Objects: `{ name: string; price?: number }`.
- `?` makes a property optional, so it may be `undefined`: handle it with `??` or a check.
- Unions (`string | null`) mean "one of these"; check with `if` and TypeScript narrows the type.
- Literal types (`"draft" | "published"`) allow only exact values.
- Prefer `unknown` to `any`. `void` = returns nothing; `never` = never returns.
- Types don't exist at runtime: validate data from outside.

</En>
<Ur>

- TypeScript JavaScript aur types hai, code chalne se **pehle** check, phir hata di jati hain.

<DeepDive title="How TypeScript fits into a project">

**Setting up.** `npm install --save-dev typescript` adds the compiler; `npx tsc --init` creates a `tsconfig.json`. Next.js, Vite and most templates create both for you.

**`tsconfig.json`** controls the checker. The settings that matter most at first:

| Option | What it does |
| --- | --- |
| `"strict": true` | Turns on all strict checks, including `strictNullChecks` and `noImplicitAny`. Always on in new projects. |
| `"noEmit": true` | Only check; let another tool (Next.js, Vite) produce the JavaScript. |
| `"target"` | Which JavaScript version to output. |
| `"noUncheckedIndexedAccess"` | Treats `list[i]` as possibly `undefined`. Stricter, catches real bugs. |

**Checking vs building.** Modern tools such as esbuild, SWC (inside Next.js) and Node.js's own type stripping just **delete** the types without checking them, because that's fast. The checking happens in your editor and in a separate `tsc --noEmit` step, usually in CI. So a project can build and run with type errors unless CI runs `tsc`.

**`noImplicitAny`.** Without strict mode, an unannotated parameter silently becomes `any`. With it, TypeScript reports `Parameter 'x' implicitly has an 'any' type`, which is why you annotate parameters.

**Structural typing.** TypeScript compares **shapes**, not names. Any object with the right properties fits a type, whatever it's called. The "extra property" error you saw only applies to object literals written directly in place; an existing variable with extra properties is accepted.

**`.d.ts` files** describe the types of JavaScript libraries. Packages either ship them or get them from DefinitelyTyped (`npm install -D @types/lodash`).

**Inference of `const`.** `let size = "M"` is `string`, but `const size = "M"` is the literal type `"M"`, because a `const` can never change. `as const` makes a whole object or array literal and read-only.

**Gradual adoption.** A JavaScript project can rename files one at a time from `.js` to `.ts`, and `// @ts-check` at the top of a `.js` file turns on checking using JSDoc comments.

</DeepDive>

<DeepDive title="Real world: the price that was text">

A shop's checkout page read the coupon discount from the API and calculated:

```ts
const total = subtotal - coupon.amount;
```

The API had always sent `amount` as a number. One day the backend team changed their database driver, and decimal columns started arriving as **strings** (`"5.00"`), which is common for money to avoid rounding errors. Subtraction still worked, because `-` converts text to numbers. Then a later change added a delivery fee: `subtotal - coupon.amount + delivery`. Now some totals were text, and customers saw prices like `"45.005"`.

The front end had a `Coupon` type saying `amount: number`, so TypeScript reported nothing. The type described what the developers **expected**, not what arrived.

The fix had two parts:

1. **Validate at the edge.** Parse the response with a schema (zod) that converts `"5.00"` to `5` or rejects it, so the rest of the code can trust its types.
2. **Generate types from the source of truth.** The team generated their API types from the backend's OpenAPI description, so when the backend changed a field's type, the front end's build failed immediately instead of the customer finding out.

</DeepDive>

<DeepDive title="Security lens">

TypeScript makes many bugs impossible, but it is **not** a security boundary.

- **No runtime protection.** Types are erased. An attacker sends whatever JSON they like; `req.body as LoginRequest` doesn't check anything. Validate every request body, query string, header and webhook payload with a runtime schema.
- **`any` hides dangerous flows.** A value typed `any` can flow into SQL queries, `innerHTML` or shell commands without any warning. Many teams ban `any` with the lint rule `@typescript-eslint/no-explicit-any`.
- **Assertions are trust.** `as User`, `as unknown as T` and the non-null assertion `value!` tell the checker to stop looking. Review them like you'd review a disabled security check.
- **Unions model permissions well.** `role: "viewer" | "editor" | "admin"` makes a typo such as `"Admin"` a compile error, so a permission check can't silently fail. Pair it with exhaustive checks (using `never`) so adding a new role forces every permission switch to be updated.
- **Type confusion in user input.** Frameworks may give you a string, an array or an object for the same query parameter. A schema validator rejects the unexpected shapes before they reach your logic.
- **Generated types from your database or API** keep the front end and back end in step, which removes a whole class of "the field changed type" bugs.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is TypeScript and why use it?">
TypeScript is a superset of JavaScript that adds static types. A compiler checks the types before the code runs and then removes them, producing plain JavaScript. It catches mistakes such as wrong argument types, misspelled properties and unhandled null values early, and powers editor autocomplete and safe refactoring.
</QA>

<QA q="What is type inference?">
It is the compiler working out a type from context, usually from an initial value or a function's return statements. Variables initialised with a value rarely need annotations; parameters usually do, because their values come from callers.
</QA>

<QA q="What is the difference between any and unknown?">
any disables type checking for that value, so any operation is allowed and errors slip through. unknown accepts any value too, but no operations are allowed until the code narrows it to a specific type with a check such as typeof or a validation function. unknown is the safe choice for values of unknown shape.
</QA>

<QA q="What are void and never?">
void is the return type of a function that does not return a useful value. never is the type of something that can never happen, such as the return type of a function that always throws or loops forever, and the type a variable has after every possibility has been ruled out.
</QA>

<QA q="Does TypeScript check types at runtime?">
No. Types exist only at compile time and are erased in the generated JavaScript. Data coming from outside the program must be validated at runtime, for example with a schema library such as zod.
</QA>

<QA q="What does strict mode do?">
The strict compiler option turns on a family of checks, including strictNullChecks, which makes null and undefined separate types that must be handled, and noImplicitAny, which reports parameters and variables whose type would silently become any. New projects should always enable it.
</QA>

<QA q="What is a tuple?">
A tuple is an array type with a fixed number of elements where each position has its own type, for example a string followed by a number. It is useful for small fixed groupings such as coordinates or key and value pairs.
</QA>

</DeepDive>
