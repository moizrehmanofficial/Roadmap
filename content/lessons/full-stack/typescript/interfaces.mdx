<BigIdea>
<Tr>
<En>
In the last lesson you wrote object types inline, like `{ name: string; price: number }`. That gets long, and you'd have to repeat it everywhere. Instead, you can give a shape a **name** once and reuse it. There are two ways: a **type alias** (`type Product = { … }`) and an **interface** (`interface Product { … }`). For describing objects they do almost the same job: list the properties and their types, mark some as **optional** (`?`) or **read-only** (`readonly`), nest one shape inside another, and build bigger shapes from smaller ones (`extends` or `&`). A `type` can also name things that aren't objects, such as unions (`type Status = "draft" | "published"`). Named shapes are how real projects describe their data: a `User`, an `Order`, the props of a React component, the body of an API response.
</En>
<Ur>
Pichhle lesson me aap ne object types line ke andar likhin, jaise `{ name: string; price: number }`. Ye lambi ho jati hain, aur inhe har jagah dohrana parta. Is ke bajaye aap shakal ko ek dafa **naam** de kar dobara istemal kar sakte hain. Is ke do tareeqe hain: **type alias** (`type Product = { … }`) aur **interface** (`interface Product { … }`). Objects bayan karne ke liye dono taqreeban ek hi kaam karte hain: properties aur un ki types likhna, kuch ko **ikhtiyari** (`?`) ya **sirf parhne wali** (`readonly`) banana, ek shakal ko doosri ke andar rakhna, aur chhoti shakalon se bari banana (`extends` ya `&`). `type` un cheezon ko bhi naam de sakta hai jo objects nahi, jaise unions (`type Status = "draft" | "published"`). Asli projects apna data naam wali shakalon se hi bayan karte hain: `User`, `Order`, React component ke props, API response ki body.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

The same shape, written both ways:

```ts
type Product = {
  name: string;
  price: number;
  discount?: number;      // optional
};

interface Customer {
  readonly id: number;    // can't be changed
  name: string;
  email: string;
}
```

Read `type Product = { … }` as **"from now on, `Product` means an object with these properties"**. Names of types start with a capital letter by convention.

</En>
<Ur>

Wahi shakal, dono tareeqon se:

```ts
type Product = {
  name: string;
  price: number;
  discount?: number;      // ikhtiyari
};

interface Customer {
  readonly id: number;    // badla nahi ja sakta
  name: string;
  email: string;
}
```

`type Product = { … }` ko aise parhein: **"ab se `Product` ka matlab hai in properties wala object"**. Riwayat ke mutabiq types ke naam bare harf se shuru hote hain.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Write the shape once.** Every function, variable and component that handles a product uses `Product`.
- **One place to change.** Add `stock: number` to `Product`, and TypeScript points to every place that now needs it.
- **Readable code.** `function ship(order: Order)` says far more than `function ship(order: { id: number; items: … })`.
- **Shared language with your team and your API.** Types often mirror the database and the API, so front end and back end agree on the data.

</En>
<Ur>

- **Shakal ek dafa likho.** Product sambhalne wala har function, variable aur component `Product` istemal karta hai.
- **Badalne ki ek jagah.** `Product` me `stock: number` jorein, aur TypeScript har wo jagah dikha deta hai jahan ab is ki zaroorat hai.
- **Parhne ke qabil code.** `function ship(order: Order)` `function ship(order: { id: number; items: … })` se kahin zyada batata hai.
- **Team aur API ke saath mushtarak zabaan.** Types aksar database aur API ka aks hoti hain, isliye front end aur back end data par muttafiq rehte hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Make a named shape as soon as the same object type appears **twice**, or as soon as it has more than two or three properties.

| You want to name… | Use |
| --- | --- |
| An object shape | `interface` or `type` (pick one style per project) |
| A union: `"S" \| "M" \| "L"`, `string \| number` | `type` |
| A tuple or a function type | `type` |
| A shape other code (or a library) must be able to add to | `interface` |

</En>
<Ur>

Jaise hi wahi object type **do dafa** aaye, ya jaise hi us me do teen se zyada properties hon, use naam de dein.

| Aap naam dena chahte hain… | Lein |
| --- | --- |
| Object ki shakal | `interface` ya `type` (har project me ek andaaz) |
| Union: `"S" \| "M" \| "L"`, `string \| number` | `type` |
| Tuple ya function ki type | `type` |
| Aisi shakal jis me doosra code (ya library) izafa kar sake | `interface` |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```ts
type Product = { name: string; price: number };

function label(product: Product): string {
  return product.name + ": $" + product.price;
}

const pen: Product = { name: "Pen", price: 2 };
const items: Product[] = [pen, { name: "Bag", price: 40 }];
```

</En>
<Ur>

```ts
type Product = { name: string; price: number };

function label(product: Product): string {
  return product.name + ": $" + product.price;
}

const pen: Product = { name: "Pen", price: 2 };
const items: Product[] = [pen, { name: "Bag", price: 40 }];
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

A named type is a **blank form** with labelled boxes. The **form** for a library card says: *Full name*, *Email*, *Member since*, and an optional box *Phone (if you have one)*. The form itself isn't anybody's card; it's the **template** every card must follow. Each filled-in card is an object.

TypeScript is the **clerk** who checks every filled-in card against the form: a box left empty that isn't optional, an extra box someone drew in the margin, a date written in the name box. All rejected.

`readonly` is a box **printed in ink** after the card is issued, like the member number: you can read it but not rub it out. `extends` is a **longer form** that says "everything on the basic form, **plus** these boxes", like a student card that adds *School*. And a union of shapes is a desk with **several different forms**: you pick the one whose title matches what you're doing, and the clerk checks the boxes for that form.

</En>
<Ur>

Naam wali type label wale khaanon ka **khaali form** hai. Library card ke **form** par likha hai: *Poora naam*, *Email*, *Member kab se*, aur ek ikhtiyari khaana *Phone (agar ho)*. Form khud kisi ka card nahi; ye wo **saancha** hai jis ki har card ko pairwi karni hai. Har bhara hua card ek object hai.

TypeScript wo **clerk** hai jo har bhare hue card ko form se milata hai: khaali chhora gaya khaana jo ikhtiyari nahi, kisi ka haashiye me banaya hua izafi khaana, naam ke khaane me likhi tareekh. Sab mustarad.

`readonly` card jaari hone ke baad **siyahi se chhapa** khaana hai, jaise member number: parh sakte hain, mita nahi sakte. `extends` **lamba form** hai jo kehta hai "bunyadi form ka sab kuch, **aur** ye khaane", jaise student card jo *School* jorta hai. Aur shakalon ka union aisi mez hai jis par **kai alag forms** hain: aap wo form chunte hain jis ka unwaan aap ke kaam se milta hai, aur clerk usi form ke khaane check karta hai.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Type alias** | A name for any type, made with `type` | `type Id = string` |
| **Interface** | A name for an object shape, made with `interface` | `interface User { … }` |
| **Property** | One named entry in a shape | `name: string` |
| **Optional property** | May be missing (`undefined`) | `phone?: string` |
| **`readonly`** | Can be read but not reassigned | `readonly id: number` |
| **Nested type** | A shape used inside another | `address: Address` |
| **`extends`** | An interface that adds to another | `interface Admin extends User` |
| **Intersection (`&`)** | A type that has **all** properties of both | `User & Timestamps` |
| **Union (`\|`)** | One of several types | `Card \| PayPal` |
| **Discriminated union** | A union whose members share a "kind" property | `kind: "card"` |
| **Index signature** | Any key of a given type | `{ [key: string]: number }` |
| **Structural typing** | Shapes match by their properties, not their names | |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Type alias** | Kisi bhi type ka naam, `type` se banaya gaya | `type Id = string` |
| **Interface** | Object ki shakal ka naam, `interface` se banaya gaya | `interface User { … }` |
| **Property** | Shakal ki ek naam wali entry | `name: string` |
| **Optional property** | Ghayab ho sakti hai (`undefined`) | `phone?: string` |
| **`readonly`** | Parhi ja sakti hai, dobara set nahi | `readonly id: number` |
| **Nested type** | Doosri ke andar istemal hone wali shakal | `address: Address` |
| **`extends`** | Interface jo doosre me izafa kare | `interface Admin extends User` |
| **Intersection (`&`)** | Aisi type jis me dono ki **saari** properties hon | `User & Timestamps` |
| **Union (`\|`)** | Kai types me se ek | `Card \| PayPal` |
| **Discriminated union** | Union jis ke members me ek mushtarak "kind" property ho | `kind: "card"` |
| **Index signature** | Di gayi type ki koi bhi key | `{ [key: string]: number }` |
| **Structural typing** | Shakalen apni properties se milti hain, naamon se nahi | |

</Ur>
</Tr>

## Learn it step by step

<Tr>
<En>
As in the last lesson: **TypeScript** blocks can be run on the page, and **checker** blocks show the real output of `npx tsc --noEmit --strict app.ts` for the code saved into `app.ts`.
</En>
<Ur>
Pichhle lesson ki tarah: **TypeScript** blocks page par chalaye ja sakte hain, aur **checker** blocks `app.ts` me mehfooz kiye gaye code par `npx tsc --noEmit --strict app.ts` ka asli output dikhate hain.
</Ur>
</Tr>

<Walkthrough>

<Step title="Name a shape with type">

<Tr>
<En>
Write `type`, a name, `=`, and the object type. Then use the name anywhere you'd write a type.
</En>
<Ur>
`type`, ek naam, `=`, aur object type likhein. Phir jahan bhi type likhte wahan ye naam istemal karein.
</Ur>
</Tr>

```typescript
type Product = {
  name: string;
  price: number;
  inStock: boolean;
};

const pen: Product = { name: "Pen", price: 2, inStock: true };
const bag: Product = { name: "Bag", price: 40, inStock: false };

function label(product: Product): string {
  const status = product.inStock ? "in stock" : "sold out";
  return product.name + " ($" + product.price + ") - " + status;
}

console.log(label(pen));
console.log(label(bag));
```

```text output
Pen ($2) - in stock
Bag ($40) - sold out
```

<Happened>
<Tr>
<En>

- `type Product = { … }` doesn't create any value. It only teaches TypeScript a new word, `Product`.
- `pen`, `bag` and the `product` parameter all use that word. If the shape changes, you change it in one place.
- Properties are separated with `;` (commas also work). Each line is "name, colon, type", just like inline types.

</En>
<Ur>

- `type Product = { … }` koi value nahi banata. Ye sirf TypeScript ko ek naya lafz sikhata hai, `Product`.
- `pen`, `bag` aur `product` parameter sab yahi lafz istemal karte hain. Shakal badle to aap ek jagah badalte hain.
- Properties `;` se alag hoti hain (commas bhi chalte hain). Har line "naam, colon, type" hai, bilkul line ke andar wali types ki tarah.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The same shape with interface">

<Tr>
<En>
An **interface** describes an object shape too. There's no `=`, and it can only describe objects. For everyday object shapes, `type` and `interface` are interchangeable.
</En>
<Ur>
**Interface** bhi object ki shakal bayan karta hai. Is me `=` nahi hota, aur ye sirf objects bayan kar sakta hai. Rozmarra ki object shakalon ke liye `type` aur `interface` ek doosre ki jagah le sakte hain.
</Ur>
</Tr>

```typescript
interface Customer {
  id: number;
  name: string;
  email: string;
}

const customers: Customer[] = [
  { id: 1, name: "Sara", email: "sara@example.com" },
  { id: 2, name: "Alex", email: "alex@example.com" },
];

function findCustomer(list: Customer[], id: number): Customer | undefined {
  return list.find((customer) => customer.id === id);
}

console.log(findCustomer(customers, 2)?.email);
console.log(findCustomer(customers, 9)?.email ?? "not found");
```

```text output
alex@example.com
not found
```

<Happened>
<Tr>
<En>

- `Customer[]` is "an array of customers", using the named shape.
- `find` might not find anything, so the honest return type is `Customer | undefined`. TypeScript then makes callers deal with "not found", which is why we used `?.` and `??`.
- Whether you write `type` or `interface` here makes no difference to the result.

</En>
<Ur>

- `Customer[]` ka matlab "customers ki array", naam wali shakal ke saath.
- `find` ko shayad kuch na mile, isliye imaandar return type `Customer | undefined` hai. Phir TypeScript call karne walon se "nahi mila" ki surat sambhalwata hai, isi liye humne `?.` aur `??` lagaya.
- Yahan `type` likhein ya `interface`, nateeje me koi farq nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The checker holds every object to the shape">

<Tr>
<En>
Once a shape has a name, every place that uses the name is checked: missing properties, misspelled ones and wrong types.
</En>
<Ur>
Shakal ko naam mil jaye to har wo jagah check hoti hai jo naam istemal karti hai: ghayab properties, ghalat spelling wali, aur ghalat types.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
interface Customer {
  id: number;
  name: string;
  email: string;
}

const a: Customer = { id: 1, name: "Sara" };
const b: Customer = { id: 2, name: "Alex", emial: "alex@example.com" };
const c: Customer = { id: "3", name: "Emma", email: "emma@example.com" };

function sendWelcome(customer: Customer) {
  return "Sending to " + customer.mail;
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(7,7): error TS2741: Property 'email' is missing in type '{ id: number; name: string; }' but required in type 'Customer'.
app.ts(8,44): error TS2561: Object literal may only specify known properties, but 'emial' does not exist in type 'Customer'. Did you mean to write 'email'?
app.ts(9,23): error TS2322: Type 'string' is not assignable to type 'number'.
app.ts(12,35): error TS2551: Property 'mail' does not exist on type 'Customer'. Did you mean 'email'?
```

<Happened>
<Tr>
<En>

- Notice the messages now say **`Customer`** instead of a long `{ … }`. Named types make errors easier to read.
- Line 7 forgot `email`. Line 8 misspelled it. Line 9 gave a text id. Line 12 read a property that doesn't exist.
- Four bugs, found before anything ran, and two come with a suggested fix.

</En>
<Ur>

- Dhyan dein ke ab paighaam lambe `{ … }` ke bajaye **`Customer`** kehte hain. Naam wali types errors ko parhna aasan banati hain.
- Line 7 `email` bhool gayi. Line 8 ne us ki spelling ghalat ki. Line 9 ne text id di. Line 12 ne aisi property parhi jo maujood hi nahi.
- Chaar bugs, kuch bhi chalne se pehle mil gaye, aur do ke saath hal ka mashwara bhi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Optional and read-only properties">

<Tr>
<En>
A `?` after the name makes a property **optional**. `readonly` in front of the name makes it **read-only**: it can be set when the object is created, but not changed afterwards.
</En>
<Ur>
Naam ke baad `?` property ko **ikhtiyari** bana deta hai. Naam se pehle `readonly` use **sirf parhne wala** bana deta hai: object bante waqt set ho sakti hai, baad me badli nahi ja sakti.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
interface Order {
  readonly id: number;
  total: number;
  note?: string;
}

const order: Order = { id: 501, total: 42 };
order.total = 45;
order.id = 999;

const shout = order.note.toUpperCase();
const safe = order.note?.toUpperCase() ?? "(no note)";
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(9,7): error TS2540: Cannot assign to 'id' because it is a read-only property.
app.ts(11,15): error TS18048: 'order.note' is possibly 'undefined'.
```

<Happened>
<Tr>
<En>

- Creating the order without a `note` was fine, because `note` is optional.
- Changing `total` was fine. Changing `id` was refused: it's `readonly`. IDs, creation dates and anything that identifies a record are good candidates.
- Line 11 read the optional `note` as if it were always there. TypeScript knows it might be `undefined`.
- Line 12 is the safe version: `?.` stops if there's no note, and `??` supplies a fallback.
- `readonly` is a compile-time rule only. It doesn't freeze the object at runtime (that's `Object.freeze`).

</En>
<Ur>

- `note` ke baghair order banana theek tha, kyun ke `note` ikhtiyari hai.
- `total` badalna theek tha. `id` badalne se inkar hua: ye `readonly` hai. IDs, banne ki tareekh aur record ki pehchaan wali har cheez is ke achhe umeedwar hain.
- Line 11 ne ikhtiyari `note` ko aise parha jaise wo hamesha maujood ho. TypeScript jaanta hai ke wo `undefined` ho sakta hai.
- Line 12 mehfooz version hai: note na ho to `?.` ruk jata hai, aur `??` mutabadil deta hai.
- `readonly` sirf compile ke waqt ka qaida hai. Ye chalte waqt object ko jama nahi karta (ye kaam `Object.freeze` ka hai).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Shapes inside shapes">

<Tr>
<En>
Real data is nested: an order has a customer, a customer has an address, an order has a list of items. Give each piece its own name and build them up.
</En>
<Ur>
Asli data nested hota hai: order ka customer hota hai, customer ka address, order ke items ki list. Har hisse ko apna naam dein aur unhe jor kar banayen.
</Ur>
</Tr>

```typescript
type Address = {
  street: string;
  city: string;
  zip: string;
};

type OrderItem = {
  name: string;
  price: number;
  quantity: number;
};

type Order = {
  id: number;
  shipTo: Address;
  items: OrderItem[];
};

const order: Order = {
  id: 501,
  shipTo: { street: "12 Oak Lane", city: "Austin", zip: "78701" },
  items: [
    { name: "Pen", price: 2, quantity: 3 },
    { name: "Bag", price: 40, quantity: 1 },
  ],
};

function orderTotal(o: Order): number {
  return o.items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

console.log("Ship to:", order.shipTo.city);
console.log("Total: $" + orderTotal(order));
```

```text output
Ship to: Austin
Total: $46
```

<Happened>
<Tr>
<En>

- `Order` uses `Address` for `shipTo` and `OrderItem[]` for `items`. Small named pieces, combined.
- `Address` can now be reused for a billing address, a store location, a user profile.
- Inside `reduce`, TypeScript knows each `item` is an `OrderItem`, so typing `item.` in an editor would suggest `name`, `price` and `quantity`.

</En>
<Ur>

- `Order` `shipTo` ke liye `Address` aur `items` ke liye `OrderItem[]` istemal karta hai. Chhote naam wale hisse, jore hue.
- `Address` ab billing address, dukaan ki jagah, user profile me dobara kaam aa sakta hai.
- `reduce` ke andar TypeScript jaanta hai ke har `item` `OrderItem` hai, isliye editor me `item.` likhte hi `name`, `price` aur `quantity` ka mashwara milta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Functions inside shapes">

<Tr>
<En>
A shape can describe functions too: a **method** (`total(): number`) or a property holding a function (`onSave: (id: number) => void`). A function type is written like an arrow: `(inputs) => return type`.
</En>
<Ur>
Shakal functions bhi bayan kar sakti hai: **method** (`total(): number`) ya aisi property jis me function ho (`onSave: (id: number) => void`). Function ki type arrow ki tarah likhi jati hai: `(inputs) => return type`.
</Ur>
</Tr>

```typescript
interface Cart {
  items: number[];
  add(price: number): void;
  total(): number;
}

type Formatter = (amount: number) => string;

const toDollars: Formatter = (amount) => "$" + amount.toFixed(2);

const cart: Cart = {
  items: [],
  add(price) {
    this.items.push(price);
  },
  total() {
    return this.items.reduce((sum, p) => sum + p, 0);
  },
};

cart.add(2.5);
cart.add(40);
console.log(toDollars(cart.total()));
```

```text output
$42.50
```

<Happened>
<Tr>
<En>

- `add(price: number): void` describes a method: it takes a number and returns nothing.
- `type Formatter = (amount: number) => string` names a function shape. Any function with that shape fits.
- Because `toDollars` is typed as a `Formatter`, its parameter `amount` didn't need its own annotation; TypeScript took it from the type. The same happened for `price` inside `cart.add`.

</En>
<Ur>

- `add(price: number): void` ek method bayan karta hai: number leta hai aur kuch wapas nahi karta.
- `type Formatter = (amount: number) => string` function ki shakal ko naam deta hai. Is shakal ka har function fit hota hai.
- Chunke `toDollars` ki type `Formatter` hai, us ke parameter `amount` ko apni annotation ki zaroorat nahi thi; TypeScript ne type se le li. `cart.add` ke andar `price` ke saath bhi yahi hua.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Build bigger shapes: extends and &">

<Tr>
<En>
Often one shape is "another shape, plus a bit more". An interface can **extend** another. A type alias can do the same with an **intersection**, written `&`, which means "has everything from both".
</En>
<Ur>
Aksar ek shakal "doosri shakal, aur thora sa mazeed" hoti hai. Interface doosre ko **extend** kar sakta hai. Type alias yahi kaam **intersection** se karta hai, jo `&` se likha jata hai, aur jis ka matlab hai "dono ki har cheez".
</Ur>
</Tr>

```typescript
interface User {
  id: number;
  name: string;
}

interface Admin extends User {
  permissions: string[];
}

type Timestamps = {
  createdAt: string;
  updatedAt: string;
};

type SavedUser = User & Timestamps;

const admin: Admin = { id: 1, name: "Sara", permissions: ["refunds", "reports"] };
const saved: SavedUser = {
  id: 2,
  name: "Alex",
  createdAt: "2026-01-05",
  updatedAt: "2026-03-18",
};

function greet(user: User): string {
  return "Hi " + user.name;
}

console.log(greet(admin), "/", greet(saved));
console.log(admin.permissions.length, saved.createdAt);
```

```text output
Hi Sara / Hi Alex
2 2026-01-05
```

<Happened>
<Tr>
<En>

- `Admin extends User` means an admin has `id` and `name` **plus** `permissions`.
- `User & Timestamps` combines two separate shapes. `Timestamps` can be mixed into many types.
- `greet` asks for a `User`, and both an `Admin` and a `SavedUser` were accepted, because they have everything a `User` has. Extra properties don't matter here.

</En>
<Ur>

- `Admin extends User` ka matlab hai admin ke paas `id` aur `name` **aur** `permissions` hain.
- `User & Timestamps` do alag shakalon ko jorta hai. `Timestamps` kai types me milaya ja sakta hai.
- `greet` `User` maangta hai, aur `Admin` aur `SavedUser` dono qubool hue, kyun ke un ke paas wo sab hai jo `User` ke paas hai. Yahan izafi properties se farq nahi parta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Shapes match by what they contain">

<Tr>
<En>
TypeScript doesn't care what a type is **called**, only what it **contains**. This is **structural typing**. But there's one special rule: an object written **directly in place** with an extra property is treated as a probable typo.
</En>
<Ur>
TypeScript ko is se gharz nahi ke type ka **naam** kya hai, sirf is se ke us me **kya hai**. Ise **structural typing** kehte hain. Magar ek khaas qaida hai: jo object **wahin likha** gaya ho aur us me izafi property ho, use mumkina typo samjha jata hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
interface HasName {
  name: string;
}

function shout(thing: HasName) {
  return thing.name.toUpperCase();
}

const product = { name: "Bag", price: 40 };
shout(product);

shout({ name: "Pen", price: 2 });
shout({ title: "Lamp" });
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(12,22): error TS2353: Object literal may only specify known properties, and 'price' does not exist in type 'HasName'.
app.ts(13,9): error TS2353: Object literal may only specify known properties, and 'title' does not exist in type 'HasName'.
```

<Happened>
<Tr>
<En>

- `product` was never declared as `HasName`, yet `shout(product)` was accepted. It has a `name` that's a string, and that's all `HasName` asks for.
- Line 12 passed the **same kind** of object, but written in place. TypeScript complains about `price`: when you write an object right where it's used, an unknown property is usually a mistake.
- Line 13 has no `name` at all, so it fails for that reason too.
- Rule of thumb: **existing variables** may have extra properties; **fresh object literals** may not.

</En>
<Ur>

- `product` ko kabhi `HasName` nahi kaha gaya, phir bhi `shout(product)` qubool hua. Is me string wala `name` hai, aur `HasName` bas yahi maangta hai.
- Line 12 ne **usi qisam** ka object diya, magar wahin likh kar. TypeScript `price` par shikayat karta hai: jab aap object istemal ki jagah hi likhte hain to anjaan property aam taur par ghalti hoti hai.
- Line 13 me `name` hai hi nahi, isliye wo is wajah se bhi nakaam hai.
- Aasan qaida: **pehle se bane variables** me izafi properties ho sakti hain; **taaza likhe object literals** me nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What only type can do: unions and other shapes">

<Tr>
<En>
`interface` describes objects only. `type` can name **any** type: unions, literal values, tuples, functions, primitives. Unions of literal values are one of the most useful things you can name.
</En>
<Ur>
`interface` sirf objects bayan karta hai. `type` **kisi bhi** type ko naam de sakta hai: unions, literal values, tuples, functions, primitives. Literal values ke unions un mufeed tareen cheezon me se hain jinhe naam diya ja sakta hai.
</Ur>
</Tr>

```typescript
type Status = "pending" | "paid" | "shipped" | "cancelled";
type Id = string | number;
type Point = [number, number];

interface Shipment {
  id: Id;
  status: Status;
  location: Point;
}

const shipment: Shipment = { id: "SH-77", status: "paid", location: [30.27, -97.74] };

function canCancel(status: Status): boolean {
  return status === "pending" || status === "paid";
}

console.log(shipment.status, "->", canCancel(shipment.status) ? "can cancel" : "too late");
shipment.status = "shipped";
console.log(shipment.status, "->", canCancel(shipment.status) ? "can cancel" : "too late");
```

```text output
paid -> can cancel
shipped -> too late
```

<Happened>
<Tr>
<En>

- `Status` lists the four allowed values. A typo like `"shiped"` would be a checker error everywhere.
- `Id` is "a string or a number", reusable for every ID in the app.
- `Point` names a tuple.
- The interface then uses all three. This mix (`type` for unions, `interface` or `type` for objects) is very common.

</En>
<Ur>

- `Status` chaar jaiz values likhta hai. `"shiped"` jaisa typo har jagah checker ka error hoga.
- `Id` ka matlab "string ya number", app ki har ID ke liye dobara istemal hone wala.
- `Point` ek tuple ko naam deta hai.
- Phir interface teeno ko istemal karta hai. Ye milawat (unions ke liye `type`, objects ke liye `interface` ya `type`) bohot aam hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="One of several kinds: discriminated unions">

<Tr>
<En>
Sometimes data comes in **different kinds** with different properties. A payment might be a card (with the last four digits) or a bank transfer (with a reference). Give each kind a shared property with a literal value, usually `kind` or `type`, and make a union. Checking that property tells TypeScript which kind you have.
</En>
<Ur>
Kabhi data **mukhtalif qismon** me aata hai jin ki properties alag hoti hain. Payment card ho sakti hai (aakhri chaar digits ke saath) ya bank transfer (reference ke saath). Har qisam ko literal value wali ek mushtarak property dein, aam taur par `kind` ya `type`, aur union banayen. Wo property check karne se TypeScript ko pata chal jata hai ke aap ke paas kaun si qisam hai.
</Ur>
</Tr>

```typescript
type CardPayment = { kind: "card"; last4: string };
type BankPayment = { kind: "bank"; reference: string };
type CashPayment = { kind: "cash" };

type Payment = CardPayment | BankPayment | CashPayment;

function describe(payment: Payment): string {
  switch (payment.kind) {
    case "card":
      return "Card ending " + payment.last4;
    case "bank":
      return "Bank transfer ref " + payment.reference;
    case "cash":
      return "Cash on delivery";
  }
}

const payments: Payment[] = [
  { kind: "card", last4: "4417" },
  { kind: "bank", reference: "TX-9031" },
  { kind: "cash" },
];

for (const p of payments) {
  console.log(describe(p));
}
```

```text output
Card ending 4417
Bank transfer ref TX-9031
Cash on delivery
```

<Happened>
<Tr>
<En>

- `kind` is the **discriminant**: every member has it, with a different literal value.
- Inside `case "card"`, TypeScript knows `payment` is a `CardPayment`, so `payment.last4` is allowed. In `case "bank"`, only `reference` is. Reading `last4` there would be an error.
- This pattern models loading states (`"loading" | "success" | "error"`), API responses, form steps and Redux actions. It's one of the most valuable things TypeScript offers.

</En>
<Ur>

- `kind` **discriminant** hai: har member ke paas ye hai, alag literal value ke saath.
- `case "card"` ke andar TypeScript jaanta hai ke `payment` `CardPayment` hai, isliye `payment.last4` ki ijazat hai. `case "bank"` me sirf `reference` ki. Wahan `last4` parhna error hota.
- Ye namoona loading ki halaton (`"loading" | "success" | "error"`), API responses, form ke qadmon aur Redux actions ko bayan karta hai. TypeScript ki sab se qeemti cheezon me se ek hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Never forget a case">

<Tr>
<En>
When you add a new kind to a union, every `switch` over it should handle the new kind too. A small trick with `never` makes TypeScript remind you.
</En>
<Ur>
Union me nayi qisam jorein to us par chalne wale har `switch` ko bhi nayi qisam sambhalni chahiye. `never` ke saath ek chhota sa tareeqa TypeScript se ye yaad dilwata hai.
</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
type Payment =
  | { kind: "card"; last4: string }
  | { kind: "bank"; reference: string }
  | { kind: "wallet"; provider: string };

function fee(payment: Payment): number {
  switch (payment.kind) {
    case "card":
      return 0.3;
    case "bank":
      return 0;
    default:
      const unhandled: never = payment;
      throw new Error("Unhandled payment");
  }
}
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(13,13): error TS2322: Type '{ kind: "wallet"; provider: string; }' is not assignable to type 'never'.
```

<Happened>
<Tr>
<En>

- Someone added `"wallet"` to `Payment` but forgot to give it a fee.
- In the `default` branch, every handled kind has been ruled out. If all kinds were handled, `payment` would be `never` (nothing left), and assigning it to a `never` variable would be fine.
- Because `"wallet"` is still possible, the assignment fails, and the error message names exactly the kind you forgot.
- This is called an **exhaustive check**. Add a `case "wallet":` and the error disappears.

</En>
<Ur>

- Kisi ne `Payment` me `"wallet"` jora magar us ki fee dena bhool gaya.
- `default` hisse me har sambhali gayi qisam khaarij ho chuki hai. Agar saari qismen sambhal li gayi hotin to `payment` `never` hota (kuch baqi nahi), aur use `never` variable me rakhna theek hota.
- Chunke `"wallet"` ab bhi mumkin hai, ye rakhna nakaam hota hai, aur error bilkul wahi qisam batata hai jo aap bhool gaye.
- Ise **exhaustive check** kehte hain. `case "wallet":` jorein aur error ghayab ho jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Objects used as lookup tables">

<Tr>
<En>
Sometimes you don't know the keys in advance, only their type: stock counts by product name, prices by country code. Use an **index signature**, `{ [key: string]: number }`, or the built-in shortcut **`Record<string, number>`**.
</En>
<Ur>
Kabhi aap ko keys pehle se maloom nahi hotin, sirf un ki type: product ke naam ke hisaab se stock, country code ke hisaab se prices. **Index signature** `{ [key: string]: number }` lein, ya bana banaya shortcut **`Record<string, number>`**.
</Ur>
</Tr>

```typescript
type Stock = { [productName: string]: number };
const stock: Stock = { pens: 120, bags: 8 };
stock.notebooks = 45;

type Size = "S" | "M" | "L";
const shirtPrices: Record<Size, number> = { S: 18, M: 20, L: 25 };

for (const [name, count] of Object.entries(stock)) {
  console.log(name + ": " + count);
}
console.log("M costs $" + shirtPrices.M);
```

```text output
pens: 120
bags: 8
notebooks: 45
M costs $20
```

<Happened>
<Tr>
<En>

- `{ [productName: string]: number }` means "any string key, and every value is a number". Adding `notebooks` later is allowed.
- `Record<Size, number>` means "an object with a key for **each** size, each holding a number". Forgetting `L` would be an error, so `Record` with a union of keys guarantees nothing is missing.

</En>
<Ur>

- `{ [productName: string]: number }` ka matlab "koi bhi string key, aur har value number". Baad me `notebooks` jorne ki ijazat hai.
- `Record<Size, number>` ka matlab "aisa object jis me **har** size ki key ho, har ek me number". `L` bhoolna error hota, isliye keys ke union ke saath `Record` zamanat deta hai ke kuch ghayab nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="type or interface: which one?">

<Tr>
<En>

For object shapes, both work. The real differences are small:

| | `interface` | `type` |
| --- | --- | --- |
| Describes objects | Yes | Yes |
| Unions, tuples, primitives, function types | No | **Yes** |
| Combine shapes | `extends` | `&` |
| Can be declared twice and **merged** | **Yes** | No (error) |
| Error messages | Show the name | Sometimes show the full shape |

**A simple rule many teams use:** use `type` for everything, and switch to `interface` only when you need declaration merging (for example, adding fields to a library's types). Other teams use `interface` for object shapes and `type` for the rest. Both are fine; **being consistent** matters more than which you choose.

</En>
<Ur>

Object ki shakalon ke liye dono chalte hain. Asal farq chhote hain:

| | `interface` | `type` |
| --- | --- | --- |
| Objects bayan karta hai | Haan | Haan |
| Unions, tuples, primitives, function types | Nahi | **Haan** |
| Shakalen jorna | `extends` | `&` |
| Do dafa bayan ho kar **mil** sakta hai | **Haan** | Nahi (error) |
| Error messages | Naam dikhate hain | Kabhi poori shakal dikhate hain |

**Aasan qaida jo kai teams istemal karti hain:** har cheez ke liye `type` lein, aur `interface` par sirf tab jayen jab declaration merging chahiye ho (maslan kisi library ki types me fields jorni hon). Doosri teams object shakalon ke liye `interface` aur baqi ke liye `type` leti hain. Dono theek hain; kaun sa chunein is se zyada **yaksaniyat** ahem hai.

</Ur>
</Tr>

```bash
cat > app.ts <<'EOF'
interface Settings {
  theme: string;
}
interface Settings {
  fontSize: number;
}
const settings: Settings = { theme: "dark" };

type Profile = { name: string };
type Profile = { age: number };
EOF
npx tsc --noEmit --strict app.ts
```

```text output
app.ts(7,7): error TS2741: Property 'fontSize' is missing in type '{ theme: string; }' but required in type 'Settings'.
app.ts(9,6): error TS2300: Duplicate identifier 'Profile'.
app.ts(10,6): error TS2300: Duplicate identifier 'Profile'.
```

<Happened>
<Tr>
<En>

- The two `interface Settings` blocks were **merged** into one shape with `theme` **and** `fontSize`, which is why `fontSize` is now required.
- Declaring `type Profile` twice is simply an error.
- Merging is how libraries let you add your own fields, for example extending the type of a request object. In your own code, accidental merging can be confusing, which is one reason some teams prefer `type`.

</En>
<Ur>

- Do `interface Settings` blocks **mil kar** ek shakal ban gaye jis me `theme` **aur** `fontSize` hain, isi liye ab `fontSize` zaroori hai.
- `type Profile` ko do dafa bayan karna seedha error hai.
- Merging se libraries aap ko apne fields jorne deti hain, maslan request object ki type barhana. Apne code me ghalti se hone wali merging uljhan paida kar sakti hai, yahi ek wajah hai ke kuch teams `type` pasand karti hain.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Repeating the same inline shape">

```ts
function save(user: { id: number; name: string; email: string }) {}
function show(user: { id: number; name: string; email: string }) {}
```

</Bad>
<Good title="Name it once">

```ts
type User = { id: number; name: string; email: string };
function save(user: User) {}
function show(user: User) {}
```

</Good>
</Compare>

<Compare>
<Bad title="Making everything optional to silence errors">

```ts
type Order = { id?: number; total?: number; items?: string[] };
// every use now needs ?. and ?? checks
```

</Bad>
<Good title="Optional only when it can really be missing">

```ts
type Order = { id: number; total: number; items: string[]; note?: string };
```

</Good>
</Compare>

<Compare>
<Bad title="One shape with many optional fields for different kinds">

```ts
type Payment = { kind: string; last4?: string; reference?: string };
```

<Tr>
<En>Nothing stops a "card" without `last4`, or a "bank" with a card number.</En>
<Ur>Kuch nahi rokta ke "card" `last4` ke baghair ho, ya "bank" card number ke saath.</Ur>
</Tr>

</Bad>
<Good title="A discriminated union">

```ts
type Payment =
  | { kind: "card"; last4: string }
  | { kind: "bank"; reference: string };
```

</Good>
</Compare>

<Compare>
<Bad title="Trying to make a union with interface">

```ts
interface Status = "draft" | "published";   // syntax error
```

</Bad>
<Good title="Unions need type">

```ts
type Status = "draft" | "published";
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Lowercase type names** like `type user`. Use `User`, so types and values are easy to tell apart.
- **Prefixing interfaces with `I`** (`IUser`). It's an old habit from other languages; modern TypeScript code doesn't do it.
- **Expecting `readonly` to protect data at runtime.** It's only a compile-time rule.
- **Huge "god" types** with 40 optional fields. Split them into smaller named pieces.
- **Writing the same type on the front end and back end by hand.** Share or generate it so they can't drift apart.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Chhote harf se type ke naam** jaise `type user`. `User` lein, taa ke types aur values alag pehchani jayen.
- **Interfaces ke naam se pehle `I`** (`IUser`). Ye doosri languages ki purani aadat hai; jadeed TypeScript code aisa nahi karta.
- **Umeed ke `readonly` chalte waqt data ki hifazat karega.** Ye sirf compile ke waqt ka qaida hai.
- **40 ikhtiyari fields wali bari "har kaam ki" types.** Inhe chhote naam wale hisson me taqseem karein.
- **Front end aur back end par wahi type haath se likhna.** Ise share ya generate karein taa ke dono me farq na aaye.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Name a shape once with `type Name = { … }` or `interface Name { … }`, and reuse it everywhere.
- `?` = optional (may be `undefined`); `readonly` = can't be reassigned (checker only).
- Build big shapes from small ones: nest them, `extends` for interfaces, `&` for types.
- Shapes match by **what they contain** (structural typing). Fresh object literals can't have extra properties.
- `type` can also name unions, literals, tuples and function types; `interface` can only describe objects but can be merged.
- **Discriminated unions** (`kind: "card" | "bank"`) model "one of several kinds"; a `never` check makes sure every kind is handled.
- `Record<Key, Value>` and index signatures describe lookup tables.
- Pick one style and stay consistent.

</En>
<Ur>

- Shakal ko ek dafa `type Name = { … }` ya `interface Name { … }` se naam dein, aur har jagah dobara istemal karein.
- `?` = ikhtiyari (`undefined` ho sakti hai); `readonly` = dobara set nahi ho sakti (sirf checker).
- Chhoti shakalon se bari banayen: nest karein, interfaces ke liye `extends`, types ke liye `&`.
- Shakalen **apne andar ki cheezon** se milti hain (structural typing). Taaza object literals me izafi properties nahi ho saktin.
- `type` unions, literals, tuples aur function types ko bhi naam de sakta hai; `interface` sirf objects bayan karta hai magar mil sakta hai.
- **Discriminated unions** (`kind: "card" | "bank"`) "kai qismon me se ek" bayan karte hain; `never` check yaqeeni banata hai ke har qisam sambhali gayi.
- `Record<Key, Value>` aur index signatures lookup tables bayan karte hain.
- Ek andaaz chunein aur us par qaim rahein.

</Ur>
</Tr>
</Takeaways>

<DeepDive title="More about shapes">

**Excess property checks** only apply to object literals assigned directly to a typed target. Spreading (`{ ...extra }`), assigning through a variable or using a type assertion skips them.

**Index signatures are loose.** With `{ [key: string]: number }`, reading `stock.anything` has type `number`, even when the key doesn't exist. Enable `noUncheckedIndexedAccess` to make it `number | undefined`, or use `Map`.

**`extends` vs `&`.** `extends` reports conflicting property types as an error at the declaration. `&` silently produces `never` for a conflicting property (`{ id: string } & { id: number }` makes `id: never`), which surfaces later as confusing errors.

**Declaration merging** is how you augment libraries:

```text
// types/express.d.ts
declare global {
  namespace Express {
    interface Request { userId?: string }
  }
}
```

**Methods vs function properties.** `save(): void` (method syntax) is checked more loosely ("bivariantly") than `save: () => void` under `strictFunctionTypes`. The property form is slightly safer.

**`readonly` arrays**: `readonly string[]` or `ReadonlyArray<string>` remove `push`, `pop` and other mutating methods from the type.

**Class implementation.** `class Store implements Cart { … }` makes the compiler check that a class has everything an interface lists.

**Recursive types** work with both: `type Category = { name: string; children: Category[] }` describes a tree.

**Generating types.** For APIs, tools generate types from OpenAPI documents; for databases, ORMs such as Prisma and Drizzle generate them from the schema; for runtime validation, zod lets you write a schema once and get the type with `z.infer<typeof schema>`.

</DeepDive>

<DeepDive title="Real world: the order status nobody handled">

An online store had an order type with a status field typed as `string`. The dashboard showed a coloured badge for each status:

```ts
const colour =
  order.status === "paid" ? "green" :
  order.status === "shipped" ? "blue" :
  order.status === "cancelled" ? "red" : "grey";
```

The warehouse team added a new status, `"on_hold"`, for orders flagged for fraud review. Nothing in the front end had to change for the code to compile, so nobody noticed that held orders showed a grey "pending" badge. Support agents kept shipping them.

The fix was to make the status a literal union, `type OrderStatus = "pending" | "paid" | "shipped" | "cancelled" | "on_hold"`, generated from the backend's schema, and to write the badge logic as a `switch` with an exhaustive `never` check. The next time someone added a status, the front-end build failed with a message naming the new value, and the developer had to decide what it should look like before the change could ship.

</DeepDive>

<DeepDive title="Security lens">

Shapes describe what you **expect**; attackers send what they **want**.

- **A type is not validation.** `const body = req.body as CreateUserRequest` checks nothing. Use a runtime schema that rejects unknown and missing fields, and derive the TypeScript type from it so the two can't disagree.
- **Separate input and output types.** A `User` type that includes `passwordHash` and `isAdmin` should never be the type of a request body (mass assignment) or of a response (data leak). Define `CreateUserInput` with only the allowed fields and `PublicUser` with only the safe ones, for example `Pick<User, "id" | "name">`.
- **Discriminated unions for permissions.** `role: "viewer" | "editor" | "admin"` with exhaustive checks means adding a role forces every permission decision to be revisited, instead of silently falling into a default branch that might grant access.
- **`readonly` for identifiers** prevents accidental reassignment of IDs and owner fields in your own code, though it doesn't stop a malicious client from sending different values.
- **Index signatures with user keys.** `Record<string, Handler>` looked up with `handlers[userInput]` can hit inherited keys such as `constructor`. Validate keys against a union of allowed names, or use `Map`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between an interface and a type alias?">
Both can describe object shapes and are usually interchangeable for that. A type alias can also name unions, intersections, tuples, primitives and function types, while an interface only describes object shapes. Interfaces can be declared multiple times and are merged, which libraries use for augmentation; type aliases cannot be redeclared. Interfaces combine with extends; type aliases combine with intersections.
</QA>

<QA q="What is structural typing?">
TypeScript checks compatibility by comparing the members of types rather than their names. Any value with at least the required properties and compatible types fits, regardless of how its type was declared. The exception is object literals written directly against a type, which are also checked for unknown extra properties.
</QA>

<QA q="What is a discriminated union?">
A union of object types that all share a property with a distinct literal value, such as kind or type. Checking that property, often in a switch, narrows the value to one member so its specific properties can be used safely. Combined with an exhaustive never check, it guarantees every variant is handled.
</QA>

<QA q="What do optional and readonly modifiers do?">
A question mark after a property name makes it optional, so its type includes undefined and code must handle its absence. readonly prevents the property from being reassigned after creation, but only at compile time; it does not freeze the object at runtime.
</QA>

<QA q="What is an index signature and when would you use Record?">
An index signature describes an object whose keys are not known in advance but share a type, such as string keys with number values. Record takes a key type and a value type and produces the same kind of object; with a union of literal keys it requires every key to be present.
</QA>

<QA q="What is the difference between extends and an intersection?">
Both combine shapes. An interface that extends another must be compatible with it, and conflicts are reported at the declaration. An intersection merges the types and, for conflicting property types, produces never for that property, which surfaces as an error later where the value is used.
</QA>

</DeepDive>
