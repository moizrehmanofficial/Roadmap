<BigIdea>
<Tr>
<En>
A React app is a **tree of components**, and **props** are the wires between them. A parent passes props to a child like arguments to a function: `<ProductCard name="Mug" price={12} onAdd={addToCart} />`, and the child receives one object, `{ name, price, onAdd }`. Props can be **any** JavaScript value: text, numbers, booleans, arrays, objects, functions, and even other elements. Two rules keep apps predictable. Props are **read-only**: a child never changes them. And data flows **down**, while changes flow **up**: if a child needs to change something, the parent passes a **function** as a prop and the child calls it. **Composition** is the habit of building flexible components by **passing pieces in** (especially through `children` and "slot" props) instead of adding more and more options. A `Card` that accepts any content beats a `ProductCard`, `UserCard` and `OrderCard` that each copy the same border and padding. Master props and composition and the rest of React (state, context, hooks) slots in naturally.
</En>
<Ur>
React app **components ka darakht** hai, aur **props** un ke darmiyan ki taarein hain. Parent child ko props aise deta hai jaise function ko arguments: `<ProductCard name="Mug" price={12} onAdd={addToCart} />`, aur child ko ek object milta hai, `{ name, price, onAdd }`. Props **koi bhi** JavaScript value ho sakte hain: text, numbers, booleans, arrays, objects, functions, aur doosre elements bhi. Do qawaid apps ko qabil-e-paishgoi rakhte hain. Props **sirf parhne ke liye** hain: child unhen kabhi nahi badalta. Aur data **neeche** behta hai, jabke tabdeeliyan **upar** jati hain: agar child ko kuch badalna ho to parent **function** prop ke taur par deta hai aur child use call karta hai. **Composition** mazeed options jorte jane ke bajaye **tukre andar de kar** (khaas taur par `children` aur "slot" props ke zariye) lachakdar components banane ki aadat hai. Koi bhi content qubool karne wala `Card` un `ProductCard`, `UserCard` aur `OrderCard` se behtar hai jo har ek wahi border aur padding copy karte hain. Props aur composition par maharat ho jaye to React ka baqi hissa (state, context, hooks) qudrati taur par jagah le leta hai.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **Reuse**: one `Button` or `Card` used in hundreds of places, configured by props.
- **Predictability**: one-way data flow means you always know where a value comes from.
- **Flexibility without bloat**: composition (`children`, slots) handles new needs without new options.
- **Design systems and UI libraries** (shadcn/ui, Radix, MUI) are built entirely on these patterns.

</En>

- **Dobara istemal**: ek `Button` ya `Card` saikron jagah, props se configure.

- **Bina phulaye lachak**: composition (`children`, slots) naye options ke baghair nayi zarooratein sambhalta hai.
- **Design systems aur UI libraries** (shadcn/ui, Radix, MUI) poori tarah inhi patterns par bani hain.

</Ur>

<How>
<Tr>
<En>

1. Decide what the component **needs** from outside; those are its props.
2. Destructure them in the parameter list, with defaults for optional ones.
3. For anything the parent must react to, accept an `onX` function prop.
4. For flexible content, accept `children` (or named slots) instead of many options.

</En>
<Ur>

1. Tay karein ke component ko bahar se **kya chahiye**; wahi us ke props hain.
2. Unhen parameter list me destructure karein, ikhtiyari walon ke liye defaults ke saath.
3. Jis cheez par parent ko jawab dena ho, us ke liye `onX` function prop qubool karein.
4. Lachakdar content ke liye bohot se options ke bajaye `children` (ya naam wale slots) qubool karein.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of a **restaurant kitchen**.

- The **head chef** (parent) gives each cook an **order ticket** (props): "Burger, no onions, extra cheese". The cook follows the ticket but **never rewrites it** (props are read-only).
- When a dish is ready, the cook **rings the bell** (calls a callback prop like `onReady`). The chef decides what happens next. Information goes down on tickets and comes back up as bells.
- A **plate** doesn't care what's on it: burger, salad or cake. It just frames whatever you put in the middle. That's a component with `children`.
- A **bento box** has named compartments: main, side, dessert. That's a component with **slots** (`header`, `sidebar`, `footer`).
- If the chef had to pass a message through five cooks to reach the dishwasher, that's **prop drilling**. Sometimes a kitchen-wide noticeboard (context) is better.

</En>
<Ur>

Ek **restaurant ke kitchen** ka sochein.

- **Head chef** (parent) har cook ko **order ki parchi** (props) deta hai: "Burger, piyaz nahi, izafi cheese". Cook parchi ki pairwi karta hai magar use **kabhi dobara nahi likhta** (props sirf parhne ke liye hain).
- Dish tayyar hone par cook **ghanti bajata** hai (`onReady` jaisa callback prop call karta hai). Chef tay karta hai ke aage kya ho. Maloomat parchiyon par neeche jati hai aur ghantiyon ki shakal me upar aati hai.
- **Plate** ko parwah nahi ke us par kya hai: burger, salad ya cake. Ye bas beech me rakhi har cheez ko frame karti hai. Ye `children` wala component hai.
- **Bento box** ke naam wale khane hote hain: main, side, dessert. Ye **slots** (`header`, `sidebar`, `footer`) wala component hai.
- Agar chef ko dishwasher tak paighaam pohanchane ke liye paanch cooks se guzarna pare, ye **prop drilling** hai. Kabhi poore kitchen ka notice board (context) behtar hota hai.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Prop** | A value passed from parent to child | `price={12}` |

## Learn it step by step

<Walkthrough>

<Step title="Destructuring props with default values">

<Tr>
<En>
A component receives **one** argument: the props object. Destructure it right in the parameter list and give optional props **defaults**. Missing props are `undefined`, so the default kicks in.
</En>
<Ur>
Component ko **ek** argument milta hai: props object. Ise seedha parameter list me destructure karein aur ikhtiyari props ko **defaults** dein. Ghayab props `undefined` hote hain, isliye default lag jata hai.
</Ur>
</Tr>

```jsx preview h=150
function Badge({ label, count = 0, tone = "gray" }) {
  const colors = { gray: "#e2e8f0", green: "#bbf7d0", red: "#fecaca" };
  return (
    <span style={{ background: colors[tone], padding: "2px 10px", borderRadius: 999, marginRight: 8 }}>
      {label}: {count}
    </span>
  );
}

export default function App() {
  return (
    <p>
      <Badge label="Inbox" count={12} tone="green" />
      <Badge label="Errors" count={3} tone="red" />
      <Badge label="Drafts" />
    </p>
  );
}
```

<Happened>
<Tr>
<En>

- Three badges: "Inbox: 12" (green), "Errors: 3" (red) and "Drafts: 0" (gray). The last one received no `count` or `tone`, so the defaults `0` and `"gray"` were used.
- `function Badge({ label, count = 0, tone = "gray" })` is the same as `function Badge(props) { const { label, count = 0, tone = "gray" } = props; … }`, just shorter.
- Defaults apply only when a prop is `undefined`. Passing `count={null}` would show "Errors: " with nothing, because `null` is a real value.
- Props are named in **camelCase** (`onClick`, `maxItems`), and a component's name starts with a **capital letter**.

</En>
<Ur>

- Teen badges: "Inbox: 12" (hara), "Errors: 3" (laal) aur "Drafts: 0" (surmai). Aakhri ko na `count` mila na `tone`, isliye defaults `0` aur `"gray"` istemal hue.
- `function Badge({ label, count = 0, tone = "gray" })` bilkul `function Badge(props) { const { label, count = 0, tone = "gray" } = props; … }` jaisa hai, bas chhota.
- Defaults sirf tab lagte hain jab prop `undefined` ho. `count={null}` dene se "Errors: " khaali dikhta, kyun ke `null` asli value hai.
- Props **camelCase** me naam rakhte hain (`onClick`, `maxItems`), aur component ka naam **bare harf** se shuru hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Every kind of value can be a prop">

<Tr>
<En>
Strings can be written in quotes; everything else goes in curly braces. A prop written with no value is `true`.
</En>
<Ur>
Strings quotes me likhi ja sakti hain; baqi sab curly braces me jata hai. Bina value likha prop `true` hota hai.
</Ur>
</Tr>

```jsx preview h=230
function Inspect(props) {
  return (
    <ul>
      {Object.entries(props).map(([key, value]) => (
        <li key={key}>
          <code>{key}</code>: {typeof value} {typeof value === "function" ? "" : "→ " + JSON.stringify(value)}
        </li>
      ))}
    </ul>
  );
}

export default function App() {
  return (
    <Inspect
      title="Spring sale"
      discount={15}
      featured
      archived={false}
      tags={["mugs", "lamps"]}
      owner={{ name: "Sara", id: 7 }}
      onSelect={() => alert("selected")}
    />
  );
}
```

<Happened>
<Tr>
<En>

The list shows:

```text
title: string → "Spring sale"
discount: number → 15
featured: boolean → true
archived: boolean → false
tags: object → ["mugs","lamps"]
owner: object → {"name":"Sara","id":7}
onSelect: function
```

- `discount="15"` (quotes) would be the **string** `"15"`, a common source of `"15" + 5 = "155"` bugs. Numbers need braces.
- `featured` with no value is `true`. To pass `false`, write `archived={false}` (or leave it out and use a default).
- Arrays and objects need **double** braces for literals: the outer `{}` means "JavaScript here", the inner `{}` is the object.
- Two names are special and never reach your component as props: `key` (used by React for lists) and `ref` in older React versions (React 19 passes `ref` as a normal prop).

</En>
<Ur>

List ye dikhati hai:

```text
title: string → "Spring sale"
discount: number → 15
featured: boolean → true
archived: boolean → false
tags: object → ["mugs","lamps"]
owner: object → {"name":"Sara","id":7}
onSelect: function
```

- `discount="15"` (quotes) **string** `"15"` hota, `"15" + 5 = "155"` wale bugs ki aam wajah. Numbers ko braces chahiyen.
- Bina value `featured` `true` hai. `false` dene ke liye `archived={false}` likhein (ya chhor dein aur default lein).
- Arrays aur objects ke literals ko **dohre** braces chahiyen: bahar ka `{}` matlab "yahan JavaScript", andar ka `{}` object hai.
- Do naam khaas hain aur aap ke component tak props ki tarah kabhi nahi pohanchte: `key` (lists ke liye React istemal karta hai) aur purane React versions me `ref` (React 19 `ref` ko aam prop ki tarah deta hai).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Data down, events up">

<Tr>
<En>
A child can't change its props, and it doesn't own the parent's state. So when something happens in the child (a click), it **calls a function** the parent passed in. The parent updates its state, and new props flow down.
</En>
<Ur>
Child apne props nahi badal sakta, aur wo parent ki state ka malik nahi. Isliye jab child me kuch ho (click), wo parent ka diya **function call** karta hai. Parent apni state update karta hai, aur naye props neeche behte hain.
</Ur>
</Tr>

```jsx preview h=200
import { useState } from "react";

function QuantityPicker({ value, min = 1, max = 5, onChange }) {
  return (
    <span>
      <button onClick={() => onChange(value - 1)} disabled={value <= min}>−</button>
      <strong style={{ margin: "0 10px" }}>{value}</strong>
      <button onClick={() => onChange(value + 1)} disabled={value >= max}>+</button>
    </span>
  );
}

export default function App() {
  const [qty, setQty] = useState(1);
  const price = 12;
  return (
    <div>
      <p>Mug, ${price} each</p>
      <QuantityPicker value={qty} onChange={setQty} />
      <p>Total: ${(qty * price).toFixed(2)}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Clicking **+** three times shows 4 and "Total: $48.00"; **+** then disables at 5. **−** disables at 1.
- `QuantityPicker` has **no state** of its own. It shows `value` and reports changes with `onChange(newValue)`. The parent owns `qty`, so it can also use it for the total.
- This "controlled component" pattern (value + onChange) is how inputs, toggles, tabs and pickers are usually designed, and it's exactly how native `<input value onChange>` works in React (Forms lesson).
- Name callback props `onSomething` (`onChange`, `onSelect`, `onClose`), and the parent functions that handle them `handleSomething`.

</En>
<Ur>

- **+** teen dafa dabane par 4 aur "Total: $48.00" dikhta hai; phir 5 par **+** band ho jata hai. **−** 1 par band hota hai.
- `QuantityPicker` ki apni **koi state nahi**. Ye `value` dikhata hai aur tabdeeliyan `onChange(newValue)` se batata hai. Parent `qty` ka malik hai, isliye ise total ke liye bhi istemal kar sakta hai.
- Ye "controlled component" pattern (value + onChange) hai jis tarah inputs, toggles, tabs aur pickers aam taur par banaye jate hain, aur React me native `<input value onChange>` bilkul isi tarah kaam karta hai (Forms lesson).
- Callback props ka naam `onSomething` rakhein (`onChange`, `onSelect`, `onClose`), aur unhen sambhalne wale parent functions ka `handleSomething`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="children: components that wrap anything">

<Tr>
<En>
Whatever you put **between** a component's tags arrives as the `children` prop. Wrapper components (cards, panels, modals, layouts) just place `children` where the content belongs, so they can wrap anything.
</En>
<Ur>
Component ke tags ke **darmiyan** jo kuch rakhein wo `children` prop ki shakal me pohanchta hai. Wrapper components (cards, panels, modals, layouts) bas `children` ko content ki jagah rakhte hain, isliye wo kuch bhi lapet sakte hain.
</Ur>
</Tr>

```jsx preview h=300
function Card({ title, children }) {
  return (
    <section style={{ border: "1px solid #cbd5e1", borderRadius: 10, padding: 12, marginBottom: 10 }}>
      <h3 style={{ margin: "0 0 6px" }}>{title}</h3>
      {children}
    </section>
  );
}

export default function App() {
  return (
    <div>
      <Card title="Mug">
        <p>Ceramic, 350 ml</p>
        <button>Add to cart · $12</button>
      </Card>
      <Card title="Your account">
        <ul>
          <li>Orders: 4</li>
          <li>Wishlist: 2 items</li>
        </ul>
      </Card>
      <Card title="Empty card" />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- One `Card` wraps a product, a list and nothing at all. It doesn't know or care what's inside.
- `children` can be text, elements, an array, or `undefined` (the third card). React renders `undefined` as nothing.
- This is the core of composition: the card owns the **frame** (border, padding, title), the parent owns the **content**. Changing the card's style later updates every card in the app.

</En>
<Ur>

- Ek `Card` product, list aur bilkul kuch nahi ko lapetta hai. Ise maloom ya parwah nahi ke andar kya hai.
- `children` text, elements, array, ya `undefined` (teesra card) ho sakta hai. React `undefined` ko kuch nahi ki tarah render karta hai.
- Yahi composition ki jaan hai: card **frame** (border, padding, title) ka malik hai, parent **content** ka. Baad me card ka style badalna app ke har card ko update kar deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Named slots for several areas">

<Tr>
<En>
When a wrapper has **more than one** area, pass JSX through ordinary props. Each prop is a "slot". `children` usually stays the main content.
</En>
<Ur>
Jab wrapper ke **ek se zyada** hisse hon, aam props ke zariye JSX dein. Har prop ek "slot" hai. `children` aam taur par asal content rehta hai.
</Ur>
</Tr>

```jsx preview h=260
function Panel({ header, actions, footer, children }) {
  return (
    <div style={{ border: "1px solid #94a3b8", borderRadius: 10, overflow: "hidden" }}>
      <div style={{ display: "flex", justifyContent: "space-between", padding: 10, background: "#f1f5f9" }}>
        <strong>{header}</strong>
        <span>{actions}</span>
      </div>
      <div style={{ padding: 10 }}>{children}</div>
      {footer && <div style={{ padding: 10, borderTop: "1px solid #e2e8f0", fontSize: 13 }}>{footer}</div>}
    </div>
  );
}

export default function App() {
  return (
    <Panel
      header="Order A-1001"
      actions={<><button>Edit</button> <button>Cancel</button></>}
      footer={<em>Last updated 2 hours ago</em>}
    >
      <p>2 × Mug, 1 × Desk Lamp</p>
      <p>Total: $54.00</p>
    </Panel>
  );
}
```

<Happened>
<Tr>
<En>

- The panel shows a grey header bar with "Order A-1001" on the left and two buttons on the right, the order lines in the middle, and an italic footer.
- `actions` received a **fragment** (`<>…</>`) holding two buttons: any JSX can go into a slot.
- `{footer && …}` renders the footer area only when a footer was given. Leave the `footer` prop out and the border disappears too.
- Slots keep the panel in charge of **layout** while every page decides **what** goes in each area.

</En>
<Ur>

- Panel surmai header bar dikhata hai jis ke baayen "Order A-1001" aur daayen do buttons hain, beech me order ki lines, aur italic footer.
- `actions` ko do buttons wala **fragment** (`<>…</>`) mila: slot me koi bhi JSX ja sakta hai.
- `{footer && …}` footer ka hissa sirf tab dikhata hai jab footer diya gaya ho. `footer` prop chhor dein aur border bhi ghayab ho jata hai.
- Slots panel ko **layout** ka zimmedar rakhte hain jabke har page tay karta hai ke har hisse me **kya** jaye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Composition beats a pile of options">

<Tr>
<En>
A common trap is adding a boolean or string prop for every new need: `showIcon`, `iconPosition`, `showClose`, `isDanger`, `titleSize`… Each one doubles the combinations to test. Compare an "options" alert with a composed one.
</En>
<Ur>
Aam jaal har nayi zaroorat ke liye boolean ya string prop jorna hai: `showIcon`, `iconPosition`, `showClose`, `isDanger`, `titleSize`… Har ek aazmane wali combinations dugni kar deta hai. "Options" wale alert ka composed wale se muqabla karein.
</Ur>
</Tr>

```jsx preview h=270
// Option-heavy: every new need means another prop and another if
function AlertWithOptions({ title, message, isDanger, showIcon, showRetry }) {
  return (
    <div style={{ padding: 10, marginBottom: 8, borderRadius: 8, background: isDanger ? "#fee2e2" : "#e0f2fe" }}>
      {showIcon && (isDanger ? "⚠️ " : "ℹ️ ")}
      <strong>{title}</strong> {message} {showRetry && <button>Retry</button>}
    </div>
  );
}

// Composed: a frame plus small pieces you can combine freely
function Alert({ tone = "info", children }) {
  return (
    <div style={{ padding: 10, marginBottom: 8, borderRadius: 8, background: tone === "danger" ? "#fee2e2" : "#e0f2fe" }}>
      {children}
    </div>
  );
}
const AlertTitle = ({ children }) => <strong>{children} </strong>;

export default function App() {
  return (
    <div>
      <AlertWithOptions title="Payment failed." message="Your card was declined." isDanger showIcon showRetry />
      <Alert tone="danger">
        ⚠️ <AlertTitle>Payment failed.</AlertTitle>
        Your card was declined. <button>Retry</button> <a href="#">Use PayPal instead</a>
      </Alert>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Both alerts look similar. But the composed one also has a "Use PayPal instead" link, which needed **no change** to `Alert`. The options version would need yet another prop (`showAltPayment`?) and another `if`.
- Composition moves decisions to the **place that knows** (the page), keeping shared components small and stable.
- This is the style of modern UI libraries: `<Dialog><DialogTitle/>…</Dialog>`, `<Card><CardHeader/>…</Card>` (shadcn/ui, Radix).
- Options are still fine for genuinely small variations, such as `tone` or `size`. Use judgement: if you're adding the fourth boolean, consider composing.

</En>
<Ur>

- Dono alerts milte julte lagte hain. Magar composed wale me "Use PayPal instead" link bhi hai, jis ke liye `Alert` me **koi tabdeeli** nahi chahiye thi. Options wale version ko ek aur prop (`showAltPayment`?) aur ek aur `if` chahiye hota.
- Composition faisle **janne wali jagah** (page) par le jati hai, mushtarka components ko chhota aur mustahkam rakhte hue.
- Jadeed UI libraries ka yahi andaaz hai: `<Dialog><DialogTitle/>…</Dialog>`, `<Card><CardHeader/>…</Card>` (shadcn/ui, Radix).

</Ur>
</Tr>

<Step title="Forwarding props with rest and spread">

<Tr>
<En>
A wrapper around a native element should accept **all** the normal attributes (`type`, `disabled`, `aria-label`, `onClick`…) without listing each one. Pull out the props you handle yourself, collect the rest with `...rest`, and spread them onto the element. Merge `className` carefully.
</En>
<Ur>
Native element ke gird wrapper ko **tamam** aam attributes (`type`, `disabled`, `aria-label`, `onClick`…) har ek ki list banaye baghair qubool karne chahiyen. Jo props aap khud sambhalte hain unhen nikalein, baqi `...rest` me jama karein, aur element par spread karein. `className` ehtiyat se milayen.
</Ur>
</Tr>

```jsx preview h=200
function Button({ variant = "primary", className = "", children, ...rest }) {
  const styles = {
    primary: { background: "#0d9488", color: "white", border: "1px solid #0d9488" },
    ghost: { background: "transparent", color: "#0d9488", border: "1px solid #0d9488" },
  };
  return (
    <button
      {...rest}
      className={("btn " + className).trim()}
      style={{ ...styles[variant], padding: "6px 14px", borderRadius: 8, marginRight: 8 }}
    >
      {children}
    </button>
  );
}

export default function App() {
  return (
    <div>
      <Button onClick={() => alert("Saved!")}>Save</Button>
      <Button variant="ghost" type="button" aria-label="Close dialog">✕</Button>
      <Button disabled title="Fill in the form first">Submit</Button>
      <p id="info">The third button is disabled; hover it to see its title.</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- `onClick`, `type`, `aria-label`, `disabled` and `title` were never mentioned in `Button`, yet they all reached the real `<button>` through `{...rest}`.
- `variant` and `className` were pulled out **before** `...rest`, so `variant` doesn't end up as an unknown HTML attribute, and our `className` merges with the caller's instead of being overwritten.
- **Order matters** when spreading: props written **after** `{...rest}` win. Here our `className` and `style` come last, so callers can't accidentally replace the base class (put `{...rest}` last if you want callers to be able to override).
- With Tailwind, projects use a helper like `cn()` (clsx + tailwind-merge) to merge class names safely.

</En>
<Ur>

- `onClick`, `type`, `aria-label`, `disabled` aur `title` ka `Button` me kabhi zikr nahi hua, phir bhi sab `{...rest}` ke zariye asli `<button>` tak pohanche.
- `variant` aur `className` `...rest` se **pehle** nikale gaye, isliye `variant` anjaan HTML attribute nahi banta, aur hamari `className` call karne wale ki class ke saath milti hai, us ki jagah nahi leti.
- Spread karte waqt **tarteeb ahem hai**: `{...rest}` ke **baad** likhe props jeet'te hain. Yahan hamari `className` aur `style` aakhir me hain, isliye call karne wale ghalti se buniyadi class nahi badal sakte (agar chahte hain ke call karne wale badal sakein to `{...rest}` aakhir me rakhein).
- Tailwind ke saath projects class names mehfooz tareeqe se milane ke liye `cn()` (clsx + tailwind-merge) jaisa helper istemal karte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Passing functions that render: render props">

<Tr>
<En>
Sometimes a component handles the **logic** (filtering, paging, sorting) but the parent should decide **how each item looks**. Pass a function prop that returns JSX.
</En>
<Ur>
Kabhi component **logic** (filtering, paging, sorting) sambhalta hai magar parent ko tay karna hota hai ke **har item kaisa dikhe**. JSX wapas karne wala function prop dein.

import { useState } from "react";

function FilterableList({ items, getText, renderItem, placeholder = "Filter…" }) {
  const [q, setQ] = useState("");
  const shown = items.filter((item) => getText(item).toLowerCase().includes(q.toLowerCase()));
  return (
    <div>
      <input value={q} onChange={(e) => setQ(e.target.value)} placeholder={placeholder} />

      <small>{shown.length} of {items.length}</small>

}

const users = [
  { id: 1, name: "Sara Lee", role: "admin" },
  { id: 2, name: "Alex Kim", role: "editor" },
  { id: 3, name: "Emma Stone", role: "viewer" },
];

}

<Step title="Prop drilling, and when to stop">

<Tr>
<En>

**Prop drilling** is passing a prop through several components that don't use it, just to reach a deep child:

```text
<App user={user}>                → uses nothing
  <Layout user={user}>           → uses nothing
    <Sidebar user={user}>        → uses nothing
      <AccountMenu user={user}>  → finally uses user.name
```

It's not wrong (it's explicit and easy to trace), but it gets tiring and fragile at 4+ levels. Options:

1. **Composition first**: let `App` render `<AccountMenu user={user} />` itself and pass it into `Layout` as a slot (`sidebar={<Sidebar menu={<AccountMenu user={user} />} />}`). The middle components no longer need to know about `user`.
2. **Context** (`useContext`, covered in the hooks lesson) for values many components need: current user, theme, language.
3. **A state library** (Zustand, Redux; State Management lesson) for large, frequently updated app state.

</En>
<Ur>

**Prop drilling** prop ko aise kai components se guzarna hai jo use istemal nahi karte, sirf gehre child tak pohanchne ke liye:

```text
<App user={user}>                → kuch istemal nahi karta
  <Layout user={user}>           → kuch istemal nahi karta
    <Sidebar user={user}>        → kuch istemal nahi karta
      <AccountMenu user={user}>  → aakhir user.name istemal karta hai
```

Ye ghalat nahi (saaf hai aur peecha karna aasan hai), magar 4+ darjon par thakane wala aur nazuk ho jata hai. Options:

1. **Pehle composition**: `App` ko khud `<AccountMenu user={user} />` render karne dein aur use slot ke taur par `Layout` me dein (`sidebar={<Sidebar menu={<AccountMenu user={user} />} />}`). Beech ke components ko ab `user` ke baare me jaanne ki zaroorat nahi.
2. **Context** (`useContext`, hooks lesson me) un values ke liye jo bohot se components ko chahiyen: maujooda user, theme, zabaan.
3. **State library** (Zustand, Redux; State Management lesson) bari, baar baar update hone wali app state ke liye.

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- Composition is often overlooked: passing **elements** instead of **data** removes drilling without any new tools.
- Reach for context when many unrelated components need the same value, not just to avoid two levels of props.

</En>
<Ur>

- Composition ko aksar nazarandaz kiya jata hai: **data** ke bajaye **elements** dena bina kisi naye auzaar ke drilling khatam kar deta hai.
- Context tab lein jab bohot se ghair mutaliqa components ko wahi value chahiye ho, sirf props ke do darjon se bachne ke liye nahi.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Changing a prop inside the child">

```text
function Cart({ items }) {
  items.push({ name: "Free gift" });   // mutates the parent's array!
  return <ul>{items.map(…)}</ul>;
}
// the parent's data changes behind its back; renders become unpredictable
```

</Bad>
<Good title="Derive a new value, or ask the parent">

```text
function Cart({ items, onAddGift }) {
  const shown = [...items, { name: "Free gift" }];   // new array, props untouched
  return <><ul>{shown.map(…)}</ul><button onClick={onAddGift}>Keep gift</button></>;
}
```

</Good>
</Compare>

<Compare>
<Bad title="Calling the callback while rendering">

```text
<button onClick={onDelete(item.id)}>Delete</button>
// onDelete runs immediately on every render (and may loop forever)
```

</Bad>
<Good title="Pass a function">

```text
<button onClick={() => onDelete(item.id)}>Delete</button>
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Numbers in quotes** (`price="12"`): it's a string.
- **Copying props into state** (`useState(props.value)`) and expecting it to update when the prop changes: it won't. Use the prop directly, or derive from it.
- **Lowercase component names** (`<card>`): React treats them as HTML tags.
- **Spreading everything onto DOM elements** (`{...props}`) including custom props like `variant`, which produces invalid HTML attributes and console warnings.
- **Boolean-prop explosions** instead of composition.
- **Drilling five levels** when a slot or context would be simpler.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Quotes me numbers** (`price="12"`): ye string hai.
- **Props ko state me copy karna** (`useState(props.value)`) aur prop badalne par update ki umeed rakhna: ye nahi hoga. Prop seedha istemal karein, ya us se nikalein.
- **Chhote harf wale component names** (`<card>`): React unhen HTML tags samajhta hai.
- **DOM elements par sab kuch spread karna** (`{...props}`), `variant` jaise custom props samet, jo ghalat HTML attributes aur console warnings banata hai.
- Composition ke bajaye **boolean props ka dhamaka**.
- Jab slot ya context aasan ho tab **paanch darje drill karna**.

</Ur>
</Tr>

<DeepDive title="More about props and composition">

**Compound components.** A parent and several children that share hidden state through context: `<Tabs><Tabs.List><Tabs.Trigger value="a"/></Tabs.List><Tabs.Panel value="a"/></Tabs>`. Radix and shadcn/ui use this pattern heavily.

**`asChild` / polymorphic components.** Libraries let a component render as another element (`<Button asChild><a href="/x">…</a></Button>`, or `as="a"`) while keeping its styles and behaviour.

**`ref` as a prop (React 19).** Function components can receive `ref` like any other prop and pass it to a DOM element; earlier versions needed `forwardRef`.

**`React.Children` and `cloneElement`.** Older APIs for inspecting or modifying children. They're fragile (they break with fragments and wrappers); prefer explicit props, slots or context.

**Props and re-renders.** When a parent re-renders, its children re-render too, receiving new props (even if equal). New object/function props are new references each render, which matters only when you use `memo` (React Performance lesson).

**Default props vs defaults in destructuring.** `Component.defaultProps` is deprecated for function components; use parameter defaults.

**Server and client components (Next.js).** Props passed from server components to client components must be serialisable (no functions, except server actions), because they travel over the network.

</DeepDive>

<DeepDive title="Real world: the Button with 23 props">

A startup's shared `Button` component started simple. Over two years, every team added "just one more prop": `isLoading`, `loadingText`, `iconLeft`, `iconRight`, `iconOnly`, `isDanger`, `isWarning`, `isLink`, `href`, `newTab`, `fullWidth`, `size`, `rounded`, `shadow`, `uppercase`… 23 props, 400 lines, and a test file nobody dared touch. Some combinations (`isLink` + `isLoading` + `iconOnly`) rendered invalid HTML; others silently ignored props.

The redesign followed this lesson:

1. `Button` kept a small set of **variants** (`variant`, `size`) and forwarded every native attribute with `...rest`.
2. Icons and spinners became **children**: `<Button><Spinner /> Saving…</Button>`.
3. Links used composition: `<Button asChild><Link href="/pricing">Pricing</Link></Button>`, so the element was a real `<a>` with button styling.
4. Danger/warning became a single `variant` value instead of booleans.

The component shrank to 60 lines, invalid combinations became impossible, and new needs (a button with a badge, a button with a keyboard shortcut hint) needed **no changes** to `Button` at all.

</DeepDive>

<DeepDive title="Security lens">

- **Props carrying user data are rendered as text by default** (`{comment.text}`) and are safe. `dangerouslySetInnerHTML={{ __html: … }}` is the exception: only with sanitised HTML (DOM lesson).
- **URL props** (`href`, `src`) can carry `javascript:` URLs from user input. Validate that user-provided links start with `https://` (or use a URL allowlist).
- **Spreading untrusted objects onto elements** (`<div {...userSettings}>`) can inject event handlers or `dangerouslySetInnerHTML`. Only spread props you control.
- **Hidden props aren't secret**: anything passed to client components (in Next.js, to `"use client"` components) is sent to the browser. Don't pass tokens or private fields as props.
- **Authorization can't live in props alone**: hiding a "Delete" button for non-admins is UX; the server must still check permissions.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are props in React?">
Props are the inputs to a component, passed by the parent as attributes in JSX and received as a single read-only object. They can be any JavaScript value, including functions and elements, and they let parents configure and communicate with children.
</QA>

<QA q="What is one-way data flow?">
Data is passed from parent to child through props, and children cannot modify those props. When a child needs to change data, it calls a callback function provided by the parent, which updates its own state and re-renders with new props.
</QA>

<QA q="What is the children prop and why is it useful?">
children holds whatever is placed between a component's opening and closing tags. It allows building generic wrappers like cards, layouts and modals that render arbitrary content, which is the basis of composition in React.
</QA>

<QA q="What is prop drilling and how can you avoid it?">
Prop drilling is passing props through intermediate components that don't use them to reach a deeply nested component. It can be reduced by composition, passing elements as children or slots so intermediate components don't need the data, or by using context or a state management library for widely shared values.
</QA>

<QA q="Why prefer composition over many configuration props?">
Each boolean or option prop multiplies the number of combinations to support and test, and the component grows with every new requirement. Composition lets callers combine small pieces for new needs without changing the shared component, keeping it small, flexible and stable.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Props">Read-only inputs passed from a parent component to a child.</Term>
  <Term name="Default prop value">A value used when a prop is not provided, set in destructuring.</Term>
  <Term name="Callback prop">A function prop the child calls to notify the parent.</Term>
  <Term name="One-way data flow">Data moving from parents to children, with events moving up via callbacks.</Term>
  <Term name="Controlled component">A component whose value is provided by props and changes reported via a callback.</Term>
  <Term name="children">The content placed between a component's tags.</Term>
  <Term name="Slot">A prop that receives JSX for a specific region of a component.</Term>
  <Term name="Composition">Building UIs by combining components and passing them into each other.</Term>
  <Term name="Rest props">Remaining props collected with the rest syntax.</Term>
  <Term name="Prop spreading">Passing all properties of an object as props with spread syntax.</Term>
  <Term name="Render prop">A function prop that returns elements to render.</Term>
  <Term name="Prop drilling">Passing props through components that don't need them.</Term>
  <Term name="ReactNode">The TypeScript type for anything React can render.</Term>
</Terms>
