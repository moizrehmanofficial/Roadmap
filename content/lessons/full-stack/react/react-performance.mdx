<BigIdea>
<Tr>
<En>
React's model is simple: when **state changes**, the component that owns it **re-renders**, and so do **all its children**, by default. React then compares the result with the previous one and updates only the DOM that actually changed. Re-rendering is usually cheap, so most apps never need tuning. Slowness appears in specific situations: a parent with lots of children re-renders on every keystroke; a child does **expensive work** every render; a huge list renders thousands of rows; the initial JavaScript bundle is too big. The rule is **measure first** (render counters, React DevTools Profiler, the browser Performance panel), then apply the matching fix. **Move state down** or pass components as `children` so fewer components re-render. Wrap stable children in **`memo`** and give them **stable props** (`useMemo`, `useCallback`). **`useMemo`** expensive calculations. Mark slow, non-urgent updates as **transitions** (`useTransition`, `useDeferredValue`) so typing stays instant. **Split code** with `lazy`, and **virtualise** long lists. The new **React Compiler** applies much of the memoisation automatically.
</En>
<Ur>
React ka model saada hai: jab **state badalti** hai, us ka malik component **dobara render** hota hai, aur default me us ke **tamam children** bhi. Phir React nateeje ko pichhle se milata hai aur sirf wahi DOM update karta hai jo asal me badla. Dobara render hona aam taur par sasta hai, isliye zyada tar apps ko kabhi tuning ki zaroorat nahi. Susti khaas suraton me aati hai: bohot se children wala parent har key par dobara render hota hai; child har render par **mehnga kaam** karta hai; bohot bari list hazaron rows render karti hai; shuruati JavaScript bundle bohot bara hai. Qaida hai **pehle naapo** (render counters, React DevTools Profiler, browser ka Performance panel), phir milta hal lagao. **State neeche le jayen** ya components ko `children` ki tarah dein taa ke kam components dobara render hon. Mustahkam children ko **`memo`** me lapetein aur unhen **mustahkam props** dein (`useMemo`, `useCallback`). Mehnge hisaab ko **`useMemo`** karein. Sust, ghair fori updates ko **transitions** (`useTransition`, `useDeferredValue`) nishaan zad karein taa ke typing fori rahe. `lazy` se **code baantein**, aur lambi lists ko **virtualise** karein. Naya **React Compiler** zyada tar memoisation khud lagata hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **restaurant** where the manager changes the **soup of the day** on a whiteboard.

- By default, every time the board changes, **every waiter** walks over to re-read the **entire menu** (all children re-render), even the dessert waiter whose menu didn't change. Usually that's quick and harmless.
- If the dessert menu is a 40-page book, re-reading it each time is wasteful. Give the dessert waiter a note: "only re-read if the dessert list changes" (`memo`). But if the manager hands over a **freshly photocopied** dessert list each time, identical but new paper, the waiter can't tell it's the same and re-reads anyway (new object props → use `useMemo`).
- Better still: put the soup board **in the kitchen** where only the soup cook sees it (move state down).
- A **rush order** ("customer at the door") should be handled before **re-printing all the menus** (transitions: urgent updates first).
- Don't carry the **whole cookbook** to every table; bring the pages people actually order from (code splitting).

</En>
<Ur>

Ek **restaurant** ka sochein jahan manager whiteboard par **aaj ka soup** badalta hai.

- Default me har dafa board badalne par **har waiter** **poora menu** dobara parhne jata hai (tamam children dobara render), dessert wala waiter bhi jis ka menu nahi badla. Aam taur par ye tez aur be-zarar hai.
- Agar dessert menu 40 safhon ki kitaab ho to har dafa dobara parhna fuzool hai. Dessert waiter ko note dein: "sirf tab dobara parho jab dessert list badle" (`memo`). Magar agar manager har dafa **taaza photocopy** wali dessert list de, bilkul wahi magar naya kaghaz, to waiter nahi pehchan sakta ke wahi hai aur phir bhi parhta hai (naye object props → `useMemo` lein).
- Is se bhi behtar: soup board **kitchen me** rakhein jahan sirf soup wala cook use dekhe (state neeche le jana).
- **Jaldi wala order** ("customer darwaze par") **tamam menus dobara chhapne** se pehle sambhalna chahiye (transitions: fori updates pehle).
- Har table par **poori cookbook** na le jayen; wo safhe layen jin se log asal me order karte hain (code splitting).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="When does a component re-render?">

<Tr>
<En>

A component re-renders when:

1. **Its own state changes** (`useState`, `useReducer`).
2. **Its parent re-renders** (by default all children re-render, whether their props changed or not).
3. **A context it reads changes**.
4. **An external store value it selected changes** (Zustand, Redux).

Props changing is **not** a separate trigger: props only change because the parent re-rendered. Each box below counts its renders. Type in the input.

</En>
<Ur>

Component dobara render hota hai jab:

1. **Us ki apni state badle** (`useState`, `useReducer`).
2. **Us ka parent dobara render ho** (default me tamam children dobara render hote hain, props badle ya nahi).
3. **Jo context wo parhta hai wo badle**.
4. **Chuni hui external store value badle** (Zustand, Redux).

Props badalna **alag** wajah nahi: props sirf parent ke dobara render hone se badalte hain. Neeche har dabba apne renders ginta hai. Input me type karein.

</Ur>
</Tr>

```jsx preview h=240
import { useRef, useState } from "react";

function useRenders() { const r = useRef(0); r.current += 1; return r.current; }

function Header() {
  return <p>Header (no props) · renders: {useRenders()}</p>;
}
function Greeting({ name }) {
  return <p>Hello, {name || "stranger"} · renders: {useRenders()}</p>;
}
function Footer() {
  return <p>Footer (no props) · renders: {useRenders()}</p>;
}

export default function App() {
  const [name, setName] = useState("");
  return (
    <div>
      <input value={name} onChange={(e) => setName(e.target.value)} placeholder="Your name" />
      <Header />
      <Greeting name={name} />
      <Footer />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Type "Sara" (4 keys): **all three** children show 5 renders. `Header` and `Footer` have no props at all, yet they re-rendered because their parent (`App`) did.
- That's normal and usually fine: React renders, compares, and changes only the DOM text that differs (just the greeting). Rendering ≠ updating the DOM.
- It becomes a problem only if the children are **expensive** or there are **many** of them. Next: how to avoid it.

</En>
<Ur>

- "Sara" (4 keys) likhein: **teeno** children 5 renders dikhate hain. `Header` aur `Footer` ke koi props hi nahi, phir bhi wo dobara render hue kyun ke un ka parent (`App`) hua.
- Ye aam aur aksar theek hai: React render karta hai, milata hai, aur sirf wahi DOM text badalta hai jo mukhtalif ho (sirf greeting). Render ≠ DOM update.
- Ye sirf tab masla banta hai jab children **mehnge** hon ya **bohot se** hon. Agla: is se kaise bachein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fix 1: move state down, or pass children">

<Tr>
<En>
The cheapest optimisation is structural. If only a small part of the page uses the state, put the state **in that part**. And if a stateful wrapper must surround expensive content, pass that content as **`children`**: elements created by the parent don't re-render when the wrapper's state changes.
</En>
<Ur>
Sab se sasti optimisation banawati hai. Agar page ka sirf chhota hissa state istemal karta hai to state **usi hisse me** rakhein. Aur agar state wale wrapper ko mehnge content ko gherna ho to wo content **`children`** ki tarah dein: parent ke banaye elements wrapper ki state badalne par dobara render nahi hote.
</Ur>
</Tr>

```jsx preview h=270
import { useRef, useState } from "react";

function useRenders() { const r = useRef(0); r.current += 1; return r.current; }

function ExpensiveChart() {
  const start = performance.now();
  while (performance.now() - start < 20) {}   // pretend 20 ms of work
  return <p>📊 ExpensiveChart · renders: {useRenders()}</p>;
}

// State moved down: only this small component re-renders while typing
function NameInput() {
  const [name, setName] = useState("");
  return <p><input value={name} onChange={(e) => setName(e.target.value)} placeholder="Type here" /> {name}</p>;
}

// Stateful wrapper that receives the expensive part as children
function HoverCard({ children }) {
  const [hovered, setHovered] = useState(false);
  return (
    <div onMouseEnter={() => setHovered(true)} onMouseLeave={() => setHovered(false)}
         style={{ padding: 8, border: "1px solid", borderColor: hovered ? "#0d9488" : "#cbd5e1" }}>
      {children}
    </div>
  );
}

export default function App() {
  return (
    <div>
      <NameInput />
      <HoverCard>
        <ExpensiveChart />
      </HoverCard>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Typing in the input never re-renders the chart: the `name` state lives in `NameInput`, so only `NameInput` re-renders. Typing stays smooth.
- Hovering the card changes `HoverCard`'s state and border colour, but the chart's render count stays at **1**. `<ExpensiveChart />` was created by `App`, which didn't re-render, so React reuses the same element.
- If the state lived in `App` instead, every keystroke would cost 20 ms of chart work: noticeable lag. These two techniques need no `memo` at all, and should be your first move.

</En>
<Ur>

- Input me type karna chart ko kabhi dobara render nahi karta: `name` state `NameInput` me hai, isliye sirf `NameInput` dobara render hota hai. Typing hamwar rehti hai.
- Card par hover `HoverCard` ki state aur border ka rang badalta hai, magar chart ki render ginti **1** par rehti hai. `<ExpensiveChart />` `App` ne banaya, jo dobara render nahi hua, isliye React wahi element dobara istemal karta hai.
- Agar state is ke bajaye `App` me hoti to har key chart ke 20 ms ke kaam ki qeemat leti: mehsoos hone wali atkan. In do tareeqon ko `memo` ki bilkul zaroorat nahi, aur ye aap ki pehli chaal honi chahiye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fix 2: memo, and why it breaks with new props">

<Tr>
<En>
`memo(Component)` tells React: "skip re-rendering this component if its props are **the same** as last time". Props are compared with `Object.is` (same reference). Objects, arrays and functions created during render are **new every time**, so they defeat `memo` unless you keep them stable with `useMemo` and `useCallback`.
</En>
<Ur>
`memo(Component)` React ko kehta hai: "agar props pichhli dafa jaise **wahi** hon to is component ka dobara render chhor do". Props `Object.is` (wahi reference) se milaye jate hain. Render ke dauran bane objects, arrays aur functions **har dafa naye** hote hain, isliye wo `memo` ko bekaar kar dete hain jab tak aap unhen `useMemo` aur `useCallback` se mustahkam na rakhein.
</Ur>
</Tr>

```jsx preview h=280
import { memo, useCallback, useMemo, useRef, useState } from "react";

function useRenders() { const r = useRef(0); r.current += 1; return r.current; }

const ProductList = memo(function ProductList({ label, products, onSelect }) {
  return <p>{label}: {products.length} products · renders: {useRenders()} <button onClick={() => onSelect(products[0])}>select first</button></p>;
});

const all = [{ id: 1, name: "Mug", inStock: true }, { id: 2, name: "Lamp", inStock: false }, { id: 3, name: "Pen", inStock: true }];

export default function App() {
  const [count, setCount] = useState(0);
  const [selected, setSelected] = useState(null);

  // ✗ new array and new function on every render
  const inStockNew = all.filter((p) => p.inStock);
  const onSelectNew = (p) => setSelected(p.name);

  // ✓ same array and same function until their inputs change
  const inStockStable = useMemo(() => all.filter((p) => p.inStock), []);
  const onSelectStable = useCallback((p) => setSelected(p.name), []);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Unrelated state: {count}</button> Selected: {selected ?? "none"}
      <ProductList label="memo + new props" products={inStockNew} onSelect={onSelectNew} />
      <ProductList label="memo + stable props" products={inStockStable} onSelect={onSelectStable} />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Click **Unrelated state** three times: the first list shows 4 renders, the second stays at **1**.
- Both lists are wrapped in `memo`, but the first receives a new `products` array and a new `onSelect` function each render (`filter` and the arrow function create fresh ones), so `memo` sees "changed" and re-renders.
- `useMemo` returns the **same** array, and `useCallback` the **same** function, until their dependencies change, so `memo` can skip.
- Both "select first" buttons still work, because the stable function calls `setSelected`, which never changes.
- Memoisation has a cost (comparisons, memory, harder code). Use it where a profile shows a real problem, typically for **expensive** or **numerous** children.

</En>
<Ur>

- **Unrelated state** teen dafa dabayen: pehli list 4 renders dikhati hai, doosri **1** par rehti hai.
- Dono lists `memo` me lipti hain, magar pehli ko har render par nayi `products` array aur naya `onSelect` function milta hai (`filter` aur arrow function naye banate hain), isliye `memo` "badla" dekhta hai aur dobara render karta hai.
- `useMemo` dependencies badalne tak **wahi** array, aur `useCallback` **wahi** function wapas karta hai, isliye `memo` chhor sakta hai.
- Dono "select first" buttons ab bhi kaam karte hain, kyun ke mustahkam function `setSelected` call karta hai, jo kabhi nahi badalta.
- Memoisation ki qeemat hai (muqable, memory, mushkil code). Ise wahan lein jahan profile asli masla dikhaye, aam taur par **mehnge** ya **bohot se** children ke liye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fix 3: memoise expensive calculations">

<Tr>
<En>
If a component does heavy work during render (sorting thousands of rows, building chart data), `useMemo` caches the result and recalculates only when its inputs change. Unrelated re-renders (like toggling a theme) then become cheap.
</En>
<Ur>
Agar component render ke dauran bhaari kaam karta hai (hazaron rows sort karna, chart ka data banana), `useMemo` nateeja cache karta hai aur sirf inputs badalne par dobara hisaab karta hai. Phir ghair mutaliqa renders (jaise theme toggle) saste ho jate hain.
</Ur>
</Tr>

```jsx preview h=230
import { useMemo, useState } from "react";

const orders = Array.from({ length: 200_000 }, (_, i) => ({ id: i, total: (i * 7919) % 1000 }));

function sortOrders(list, direction) {
  return [...list].sort((a, b) => (direction === "asc" ? a.total - b.total : b.total - a.total));
}

export default function App() {
  const [direction, setDirection] = useState("asc");
  const [dark, setDark] = useState(false);
  const [useCache, setUseCache] = useState(true);

  const start = performance.now();
  const cached = useMemo(() => sortOrders(orders, direction), [direction]);
  const sorted = useCache ? cached : sortOrders(orders, direction);
  const ms = (performance.now() - start).toFixed(1);

  return (
    <div style={{ background: dark ? "#0f172a" : "#fff", color: dark ? "#fff" : "#000", padding: 10 }}>
      <label><input type="checkbox" checked={useCache} onChange={(e) => setUseCache(e.target.checked)} /> use useMemo</label>{" "}
      <button onClick={() => setDark(!dark)}>Toggle theme</button>{" "}
      <button onClick={() => setDirection(direction === "asc" ? "desc" : "asc")}>Sort {direction === "asc" ? "desc" : "asc"}</button>
      <p>Top order total: {sorted[0].total} · render work: {ms} ms</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- With **use useMemo** ticked, **Toggle theme** shows a render time near **0 ms**: the sorted array came from the cache. **Sort desc** takes tens of milliseconds once, because the input changed.
- Untick it, then toggle the theme: every render sorts 200,000 orders again (tens of ms, more on a phone), even though the order didn't change.
- `useMemo` is for **expensive** work. Wrapping cheap expressions (`a + b`, a 10-item filter) costs more than it saves.
- If even a single calculation is too slow, move it to a Web Worker (Web Workers lesson) or do it on the server.

</En>
<Ur>

- **use useMemo** tick ho to **Toggle theme** render ka waqt **0 ms** ke qareeb dikhata hai: sorted array cache se aayi. **Sort desc** ek dafa darjanon milliseconds leta hai, kyun ke input badla.
- Tick hatayen, phir theme toggle karein: har render 200,000 orders dobara sort karta hai (darjanon ms, phone par zyada), halanke tarteeb nahi badli.
- `useMemo` **mehnge** kaam ke liye hai. Saste expressions (`a + b`, 10 items ka filter) lapetna bachat se zyada qeemat leta hai.
- Agar ek akela hisaab bhi bohot sust ho to use Web Worker me le jayen (Web Workers lesson) ya server par karein.

</Ur>
</Tr>
</Happened>

<Step title="Fix 4: keep typing responsive with useDeferredValue">

<Tr>
<En>
Sometimes the slow part **must** update, just not instantly: filtering a big list as the user types. `useDeferredValue(query)` gives you a copy of `query` that React updates **after** the urgent update (the input) has been shown. The input stays instant; the list catches up. Type fast in both boxes.
</En>
<Ur>
Kabhi sust hissa **zaroor** update hona chahiye, bas foran nahi: user ke type karte waqt bari list filter karna. `useDeferredValue(query)` aap ko `query` ki copy deta hai jise React fori update (input) dikhane ke **baad** update karta hai. Input fori rehta hai; list peeche se aa milti hai. Dono boxes me tez type karein.
</Ur>
</Tr>

```jsx preview h=300
import { memo, useDeferredValue, useState } from "react";

const items = Array.from({ length: 300 }, (_, i) => "Product " + (i + 1));

const SlowList = memo(function SlowList({ query }) {
  const shown = items.filter((p) => p.includes(query));
  return (
    <ul style={{ height: 80, overflow: "auto", margin: "4px 0" }}>
      {shown.map((p) => <SlowItem key={p} text={p} />)}
    </ul>
  );
});

function SlowItem({ text }) {
  const start = performance.now();
  while (performance.now() - start < 0.3) {}   // each row costs 0.3 ms
  return <li>{text}</li>;
}

function Search({ deferred }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);
  const listQuery = deferred ? deferredQuery : query;
  const stale = query !== listQuery;
  return (
    <div style={{ display: "inline-block", width: 240, verticalAlign: "top", marginRight: 12 }}>
      <strong>{deferred ? "useDeferredValue" : "Plain state"}</strong><br />
      <input value={query} onChange={(e) => setQuery(e.target.value)} placeholder="Type 1 2 3 quickly" />
      <div style={{ opacity: stale ? 0.5 : 1 }}><SlowList query={listQuery} /></div>
    </div>
  );
}

export default function App() {
  return <div><Search deferred={false} /><Search deferred /></div>;
}
```

<Happened>
<Tr>
<En>

- In **Plain state**, each keystroke must render up to 300 slow rows (~90 ms) before the letter appears: typing feels sticky, especially with CPU throttling.
- In **useDeferredValue**, letters appear immediately. The list keeps showing the previous results (dimmed while stale) and updates when React has time; if you keep typing, React **abandons** outdated list renders.
- `memo` on `SlowList` matters here: it lets React skip the list during the urgent render (its `query` prop hasn't changed yet).
- `useTransition` does the same for state you set yourself: `startTransition(() => setFilter(value))`, and gives you `isPending` for a spinner. Use it for tab switches and heavy filters.

</En>
<Ur>

- **Plain state** me har key ko harf nazar aane se pehle 300 tak sust rows (~90 ms) render karni parti hain: typing chipchipi lagti hai, khaas taur par CPU throttling ke saath.
- **useDeferredValue** me huroof foran nazar aate hain. List pichhle nataij dikhati rehti hai (purane hone ke dauran halki) aur jab React ke paas waqt ho tab update hoti hai; agar aap type karte rahein to React purane list renders **chhor** deta hai.
- Yahan `SlowList` par `memo` ahem hai: ye React ko fori render ke dauran list chhorne deta hai (us ka `query` prop abhi nahi badla).
- `useTransition` khud set ki gayi state ke liye yahi karta hai: `startTransition(() => setFilter(value))`, aur spinner ke liye `isPending` deta hai. Ise tab switches aur bhaari filters ke liye lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fix 5: code splitting with lazy and Suspense">

<Tr>
<En>
Users download your JavaScript before the app becomes interactive. Rarely used, heavy parts (charts, editors, admin screens, modals) can be loaded **only when needed** with `lazy(() => import("./Chart"))`, wrapped in `<Suspense>` to show a fallback while the code downloads. Here the "download" is simulated with a 1-second delay.
</En>
<Ur>
App interactive hone se pehle users aap ka JavaScript download karte hain. Kam istemal hone wale, bhaari hisse (charts, editors, admin screens, modals) `lazy(() => import("./Chart"))` se **sirf zaroorat par** load ho sakte hain, code download hote waqt fallback dikhane ke liye `<Suspense>` me lipte hue. Yahan "download" ki naqal 1 second ki der se ki gayi hai.
</Ur>
</Tr>

```jsx preview h=220
import { lazy, Suspense, useState } from "react";

// In a real app: const SalesChart = lazy(() => import("./SalesChart"));
const SalesChart = lazy(() =>
  new Promise((resolve) =>
    setTimeout(() => resolve({
      default: function SalesChart() {
        const data = [12, 30, 22, 45, 38];
        return (
          <div style={{ display: "flex", alignItems: "flex-end", gap: 6, height: 80 }}>
            {data.map((v, i) => <div key={i} style={{ width: 24, height: v * 1.6, background: "#0d9488" }} title={"$" + v + "k"} />)}
          </div>
        );
      },
    }), 1000)
  )
);

export default function App() {
  const [show, setShow] = useState(false);
  return (
    <div>
      <p>Dashboard summary: 128 orders this week.</p>
      <button onClick={() => setShow(true)} disabled={show}>Show sales chart</button>
      {show && (
        <Suspense fallback={<p>Loading chart…</p>}>
          <SalesChart />
        </Suspense>
      )}
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- The page is usable immediately. Clicking **Show sales chart** shows "Loading chart…" for a second, then the bar chart. Later renders are instant: the module is downloaded once.
- With a real `import()`, the bundler (Vite, Next.js, webpack) puts the chart in a **separate file** that isn't part of the initial download, so the first page loads faster.
- Next.js already splits code **per route**. For heavy client components inside a page, use `next/dynamic` (`dynamic(() => import("./Chart"), { ssr: false })`).
- Split by **user journey**, not every tiny component: each chunk is a network request. Preloading on hover (`import("./Chart")` in `onMouseEnter`) hides the delay.

</En>
<Ur>

- Page foran istemal ke qabil hai. **Show sales chart** dabane par ek second "Loading chart…" dikhta hai, phir bar chart. Baad ke renders fori hain: module ek dafa download hota hai.
- Asli `import()` ke saath bundler (Vite, Next.js, webpack) chart ko **alag file** me rakhta hai jo shuruati download ka hissa nahi, isliye pehla page tez load hota hai.
- Next.js pehle se code **har route ke hisaab se** baant'ta hai. Page ke andar bhaari client components ke liye `next/dynamic` lein (`dynamic(() => import("./Chart"), { ssr: false })`).
- **User ke safar** ke hisaab se baantein, har chhote component ke hisaab se nahi: har chunk network request hai. Hover par preload (`onMouseEnter` me `import("./Chart")`) der chhupa deta hai.

</Ur>

<Step title="The React Compiler">

<Tr>
<En>

The **React Compiler** (stable since 2025) is a build-time tool that analyses your components and inserts the equivalent of `useMemo`, `useCallback` and `memo` **automatically**, wherever it's safe. With it enabled:

- Most manual memoisation becomes unnecessary; components skip re-rendering when their inputs haven't changed.
- Your code must follow the **Rules of React**: components and hooks are pure during render, props and state aren't mutated, hooks follow their rules. Code that breaks them is skipped (the ESLint plugin reports it).

```text
// next.config.ts
const nextConfig = { reactCompiler: true };
export default nextConfig;
// (requires: npm install -D babel-plugin-react-compiler)
```

</En>
<Ur>

**React Compiler** (2025 se stable) build ke waqt chalne wala tool hai jo aap ke components ka jaiza le kar jahan mehfooz ho wahan `useMemo`, `useCallback` aur `memo` ke barabar **khud** daal deta hai. Is ke on hone par:

- Zyada tar haath ki memoisation ghair zaroori ho jati hai; components inputs na badalne par dobara render chhor dete hain.
- Aap ke code ko **Rules of React** maanne honge: components aur hooks render ke dauran khalis hon, props aur state badle na jayen, hooks apne qawaid maanein. Inhen torne wala code chhor diya jata hai (ESLint plugin is ki report deta hai).

```text

// (zaroori: npm install -D babel-plugin-react-compiler)
```

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- The compiler fixes **unnecessary re-renders**. It doesn't fix giant lists (virtualise), huge bundles (split code), slow algorithms (better algorithms or workers) or too much state in one context.
- Understanding `memo`, `useMemo` and `useCallback` still matters: for existing codebases, for libraries that require stable references, and for reading the Profiler.
- Structural fixes (state down, `children`, split contexts) remain the clearest wins and work with or without the compiler.

## Common mistakes

<Compare>
<Bad title="Memoising everything 'just in case'">

```text
const total = useMemo(() => price * qty, [price, qty]);            // cheaper to just multiply
const onClick = useCallback(() => setOpen(true), []);              // passed to a plain <button>
export default memo(Label);                                        // tiny component, props change every time
// more code, more memory, no measurable gain
```

</Bad>
<Good title="Measure, then fix the real hotspot">

```text
// Profiler: ProductTable (2,000 rows) re-renders on every keystroke in the header search
// Fix: move search state into <HeaderSearch>, and memo(ProductTable) with stable props
```

</Good>
</Compare>

<Compare>
<Bad title="memo defeated by an inline object">

```text
const Map = memo(MapView);
<Map options={{ zoom: 12, center }} onMove={(c) => setCenter(c)} />
// new options object + new function every render: memo never skips
```

</Bad>
<Good title="Stable props">

```text
const options = useMemo(() => ({ zoom: 12, center }), [center]);
const onMove = useCallback((c) => setCenter(c), []);
<Map options={options} onMove={onMove} />
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Optimising without measuring**, or measuring in development mode only.
- **Defining components inside other components** (`function Parent() { function Row() {…} }`): `Row` is a new component type every render, so React remounts it and loses its state.
- **Index keys or random keys** in lists (Lists lesson), causing extra work and bugs.
- **Huge context values that change often**.
- **Heavy libraries in the initial bundle** (charts, editors, date libraries) when they're only used on one screen.
- **Rendering thousands of DOM nodes** instead of paginating or virtualising.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Naape baghair optimise karna**, ya sirf development mode me naapna.
- **Components ke andar components banana** (`function Parent() { function Row() {…} }`): `Row` har render par nayi component type hai, isliye React use dobara mount karta hai aur us ki state kho deta hai.
- Lists me **index keys ya random keys** (Lists lesson), jo izafi kaam aur bugs banati hain.
- **Aksar badalne wali bari context values**.
- Sirf ek screen par istemal hone wali **bhaari libraries shuruati bundle me** (charts, editors, date libraries).
- Paginate ya virtualise karne ke bajaye **hazaron DOM nodes render karna**.

</Ur>
</Tr>

<DeepDive title="More about React performance">

**Render and commit phases.** Render calls your components and builds the new tree (pure, can be interrupted in concurrent mode). Commit applies DOM changes and runs layout effects, then effects. Slow renders hurt INP; slow effects can block too.

**Automatic batching.** React 18+ batches multiple state updates in the same event (even in promises and timeouts) into one render.

**Concurrent rendering.** Transitions let React interrupt a long render to handle input, then resume. That's why deferred renders can be abandoned when outdated.

**`memo` comparison.** You can pass a custom `arePropsEqual` as the second argument, but it's easy to get wrong (stale callbacks); prefer stable props.

**Server components.** In Next.js, server components ship **no JavaScript** to the browser. Moving non-interactive parts (layouts, static lists, markdown rendering) to server components shrinks the bundle more than any memoisation.

**Images and fonts.** `next/image` (sizes, lazy loading, modern formats) and `next/font` often improve LCP more than component tweaks.

**Effects that cascade.** Chains of `useEffect` → `setState` → render → effect cause extra renders; derive values during render or handle logic in event handlers instead.

**Memory leaks.** Uncleaned subscriptions, timers and listeners keep components alive and slow long sessions (Custom Hooks lesson).

</DeepDive>

<DeepDive title="Real world: the invoice editor that froze on every keystroke">

A finance app's invoice editor had a form with 30 fields and a live preview of the invoice (line items, totals, a PDF-like layout, a chart of payment history). All form state lived in the top-level `InvoicePage`, and on a mid-range laptop each keystroke took about 180 ms to show up. Customers typing a long description saw letters arrive in bursts.

The React Profiler, with "why did this render", showed that every keystroke re-rendered the entire preview and the chart (about 140 ms), plus a `formatCurrency` function creating a new `Intl.NumberFormat` for each of 200 cells.

The fixes, in order:

1. Each field group became its own component with **local state**, reporting changes upward with a debounced callback, so typing re-rendered one small component.
2. The preview received the invoice through **`useDeferredValue`**, so it updated just after typing instead of blocking it.
3. The chart was wrapped in **`memo`** with a **`useMemo`**-stabilised data array that depended only on payment history.
4. `Intl.NumberFormat` was created **once** outside the component.
5. The PDF export library (400 KB) moved behind **`lazy`**, loaded only when clicking "Export".

Keystroke latency fell to about 8 ms, and the initial page load dropped by 30 percent. The Profiler numbers before and after went into the pull request, which made the review easy.

</DeepDive>

<DeepDive title="Security lens">

- **Lazy-loaded chunks are public files**: code splitting doesn't hide admin features. Protect admin routes and APIs on the server; never rely on "the code isn't loaded" as access control.
- **Profiling and source maps in production** can expose source code and data; keep source maps private and don't ship debug builds.
- **Performance shortcuts must not skip security**: caching or memoising per-user data must be keyed by user; a module-level memo cache can leak one user's data to another on the server.
- **Denial of service through rendering**: user-controlled sizes (a request to render 1,000,000 rows) should be limited on the server and paginated.
- **Third-party scripts** (chat widgets, analytics) are frequent performance and security risks at once; load them lazily and only from trusted sources.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What causes a React component to re-render?">
A change in its own state, a re-render of its parent, a change in a context it consumes, or a change in an external store value it subscribes to. Rendering produces a new description of the UI, and React then commits only the DOM changes that differ.
</QA>

<QA q="When should you use memo, useMemo and useCallback?">
Use memo to skip re-rendering a component whose props are usually unchanged and whose render is expensive or frequent. Use useMemo to cache expensive computations or keep object props referentially stable, and useCallback to keep function props stable, mainly when passed to memoised children or used in effect dependencies. Measure first; avoid using them for trivial work.
</QA>

<QA q="How do useTransition and useDeferredValue improve responsiveness?">
They mark some updates as non-urgent so React can render urgent updates like typing first and render the heavy update in the background, interrupting or discarding it if newer input arrives. useTransition wraps a state update and provides isPending; useDeferredValue gives a lagging copy of a value.
</QA>

<QA q="What is code splitting and how do you do it in React?">
Splitting the JavaScript bundle into chunks loaded on demand so the initial download is smaller. In React you use lazy with a dynamic import and render the component inside Suspense with a fallback; frameworks like Next.js also split per route and provide next/dynamic.
</QA>

<QA q="How would you approach a slow React page?">
Reproduce it with CPU throttling, use the React Profiler to see which components render and why, and the Performance panel for long tasks. Apply structural fixes such as moving state down or splitting context, then memoisation, deferring heavy updates, code splitting or virtualisation, and verify with measurements.
</QA>

<DeepDive title="All key terms">

<Terms>
  <Term name="Re-render">Calling a component again to compute updated output.</Term>
  <Term name="Commit">Applying computed changes to the DOM.</Term>
  <Term name="memo">A wrapper that skips re-rendering when props are shallowly equal.</Term>
  <Term name="Referential equality">Two values being the same object in memory.</Term>
  <Term name="useMemo">A hook that caches a computed value between renders.</Term>
  <Term name="useCallback">A hook that caches a function between renders.</Term>
  <Term name="Moving state down">Placing state in the lowest component that needs it.</Term>
  <Term name="Transition">A non-urgent, interruptible state update.</Term>
  <Term name="useDeferredValue">A hook returning a value that updates after urgent renders.</Term>
  <Term name="Code splitting">Dividing code into chunks loaded on demand.</Term>
  <Term name="lazy">A function that defines a component loaded with a dynamic import.</Term>
  <Term name="Suspense">A component showing a fallback while children load.</Term>
  <Term name="Virtualisation">Rendering only the visible portion of a long list.</Term>
  <Term name="React Profiler">A DevTools tool recording render timings and causes.</Term>
  <Term name="React Compiler">A build tool that automatically memoises components and values.</Term>
</Terms>

<DeepDive title="More practice">

1. Turn on "Highlight updates" in React DevTools for one of your projects and find the noisiest component.
2. Profile a keystroke in a form, write down the commit time, apply one fix and measure again.
3. Replace an expensive inline calculation with `useMemo` and confirm the gain with `performance.now()`.
4. Add `useTransition` to a tab switch that renders a heavy panel and show a pending indicator.
5. Lazy-load a chart library and compare the bundle sizes in `next build` output.
6. Enable the React Compiler in a small Next.js app and remove manual `useCallback`s; check the Profiler.
