<BigIdea>
<Tr>
<En>
Data that comes from a server (products, orders, the user's profile) is different from ordinary UI state. You don't own it: it lives on the server, other people can change it, and your copy can become **stale**. Fetching it with `useEffect` + `useState` works for one screen, but soon you need **more**: show cached data instantly when the user returns to a page, avoid three components firing the same request, refresh in the background, retry when the network blips, cancel outdated requests, and refresh the list after the user adds an item. **TanStack Query** (formerly React Query) handles all of this. You describe each piece of data with a **query key** (`["products", category]`) and a **query function** that fetches it. The library keeps a **cache** keyed by those keys, decides when data is **fresh or stale**, deduplicates and retries requests, and re-renders components that use the data. Changes go through **mutations**, after which you **invalidate** the affected queries so they refetch. Your components shrink to `const { data, status } = useQuery(...)`.
</En>
<Ur>
Server se aane wala data (products, orders, user ka profile) aam UI state se mukhtalif hai. Aap is ke malik nahi: ye server par rehta hai, doosre log ise badal sakte hain, aur aap ki copy **purani** ho sakti hai. Ise `useEffect` + `useState` se lana ek screen ke liye chalta hai, magar jald hi aap ko **aur** chahiye: user ke page par wapas aane par cache ka data foran dikhana, teen components ko wahi request bhejne se rokna, pas-e-parda taaza karna, network ke jhatke par dobara koshish, purani requests mansookh karna, aur user ke item jorne ke baad list taaza karna. **TanStack Query** (pehle React Query) ye sab sambhalta hai. Aap data ke har tukre ko **query key** (`["products", category]`) aur use lane wale **query function** se bayan karte hain. Library un keys ke hisaab se **cache** rakhti hai, tay karti hai ke data **taaza ya purana** hai, requests ko dohrane se bachati aur dobara koshish karti hai, aur data istemal karne wale components dobara render karti hai. Tabdeeliyan **mutations** se hoti hain, jin ke baad aap mutasir queries ko **invalidate** karte hain taa ke wo dobara fetch hon. Aap ke components `const { data, status } = useQuery(...)` tak simat jate hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **newspaper delivered to your office**.

- The newspaper (server data) is printed elsewhere; you only have a **copy**.
- A copy from this morning is **fresh**; by the afternoon it's **stale**, still readable, but worth replacing when convenient. That's `staleTime`.
- If three colleagues ask "can you get today's paper?" at the same moment, the office manager makes **one** trip, not three (**deduplication**).
- When you come back from lunch, you can read the morning copy **immediately** while someone fetches the afternoon edition (**stale-while-revalidate**).
- Copies nobody has looked at for a week are thrown out (`gcTime`).
- When you **submit a letter to the editor** (a mutation), you know tomorrow's paper will change, so you mark today's as outdated (**invalidation**).
- Each paper is filed under a label: "Times, Sports, Monday" (the **query key**). A different label is a different copy.

</En>
<Ur>

**Daftar me pohanchne wale akhbar** ka sochein.

- Akhbar (server data) kahin aur chhapta hai; aap ke paas sirf **copy** hai.
- Aaj subah ki copy **taaza** hai; dopahar tak **purani**, ab bhi parhne layaq magar mauqa milne par badalne layaq. Ye `staleTime` hai.
- Agar teen saathi ek hi lamhe poochein "aaj ka akhbar la sakte ho?", office manager teen ke bajaye **ek** chakkar lagata hai (**deduplication**).
- Lunch se wapas aane par aap subah ki copy **foran** parh sakte hain jabke koi dopahar ka edition lata hai (**stale-while-revalidate**).
- Jin copies ko hafte bhar kisi ne nahi dekha unhen phenk diya jata hai (`gcTime`).
- Jab aap **editor ko khat** bhejte hain (mutation), aap jante hain ke kal ka akhbar badlega, isliye aaj wale ko purana nishaan zad karte hain (**invalidation**).
- Har akhbar ek label ke neeche file hota hai: "Times, Sports, Monday" (**query key**). Mukhtalif label mukhtalif copy hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Why not just useEffect?">

<Tr>
<En>

The `useFetch` hook from the Custom Hooks lesson already handled loading, errors and cancelling. But real apps need more, and each item is real code you'd have to write and maintain:

| Need | Hand-written `useEffect` | TanStack Query |
| --- | --- | --- |
| Loading / error / data | yes, manual state | built in |
| Cancel outdated requests | manual `AbortController` | built in (`signal` passed to `queryFn`) |
| Cache between pages | build a global cache | built in, keyed by query key |
| Same request from 3 components | 3 requests | 1 request (deduplicated) |
| Show old data while refreshing | complex | stale-while-revalidate by default |
| Retry on failure | manual loop | `retry: 3` (default) with backoff |
| Refresh when the tab regains focus / network returns | manual listeners | built in |
| Refresh the list after adding an item | prop drilling or global events | `invalidateQueries` |
| Pagination, infinite scroll | lots of code | `keepPreviousData`, `useInfiniteQuery` |
| Devtools to inspect the cache | none | `ReactQueryDevtools` |

</En>
<Ur>

Custom Hooks lesson ka `useFetch` hook loading, errors aur mansookhi pehle hi sambhal raha tha. Magar asli apps ko aur chahiye, aur har cheez asli code hai jo aap ko likhna aur sambhalna parega:

| Zaroorat | Haath se likha `useEffect` | TanStack Query |
| --- | --- | --- |
| Loading / error / data | haan, haath ki state | bana banaya |
| Purani requests mansookh | haath se `AbortController` | bana banaya (`queryFn` ko `signal` milta hai) |
| Pages ke darmiyan cache | global cache banao | bana banaya, query key se |
| 3 components se wahi request | 3 requests | 1 request (deduplicated) |
| Taaza karte waqt purana data dikhana | pecheeda | default me stale-while-revalidate |
| Nakami par dobara koshish | haath ka loop | `retry: 3` (default) backoff ke saath |
| Tab par focus wapas aane / network lautne par taaza karna | haath ke listeners | bana banaya |
| Item jorne ke baad list taaza karna | prop drilling ya global events | `invalidateQueries` |
| Pagination, infinite scroll | bohot sa code | `keepPreviousData`, `useInfiniteQuery` |
| Cache dekhne ke Devtools | koi nahi | `ReactQueryDevtools` |

</Ur>
</Tr>

<Step title="The cache and deduplication">

<Tr>
<En>
We start a small product API (it counts requests) and ask the query client for the same data several times: once, again, and then three times **at the same moment**, like three components mounting together.
</En>
<Ur>
Hum chhoti product API shuru karte hain (jo requests ginti hai) aur query client se wahi data kai dafa maangte hain: ek dafa, dobara, aur phir teen dafa **ek hi lamhe**, jaise teen components ek saath mount hon.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module
npm install @tanstack/query-core --silent > /dev/null 2>&1
cat > api.mjs <<'EOF'
import http from "node:http";

let products = [
  { id: 1, name: "Mug", price: 12 },
  { id: 2, name: "Desk Lamp", price: 30 },
];
let hits = 0;
let flaky = 0;

const server = http.createServer(async (req, res) => {
  hits++;
  const send = (status, data) => { res.writeHead(status, { "content-type": "application/json" }); res.end(JSON.stringify(data)); };
  if (req.method === "GET" && req.url === "/api/products") return setTimeout(() => send(200, products), 50);
  if (req.method === "POST" && req.url === "/api/products") {
    let body = ""; for await (const c of req) body += c;
    const p = { id: products.length + 1, ...JSON.parse(body) };
    products = [...products, p];
    return send(201, p);
  }
  if (req.url === "/api/flaky") return ++flaky < 3 ? send(503, { error: "busy" }) : send(200, { ok: true, attempt: flaky });
  send(404, { error: "not found" });
});

export function start() {
  return new Promise((r) => server.listen(0, () => r({
    base: "http://localhost:" + server.address().port,
    hits: () => hits,
    stop: () => server.close(),
  })));
}

export async function getJson(url, init) {
  const res = await fetch(url, init);
  const body = await res.json();
  if (!res.ok) throw new Error("HTTP " + res.status + ": " + body.error);
  return body;
}
EOF
cat > cache.mjs <<'EOF'
import { QueryClient } from "@tanstack/query-core";
import { start, getJson } from "./api.mjs";
const { base, hits, stop } = await start();

const queryClient = new QueryClient();
const productsQuery = { queryKey: ["products"], queryFn: () => getJson(base + "/api/products"), staleTime: 60_000 };

const first = await queryClient.fetchQuery(productsQuery);
console.log("1st:", first.map((p) => p.name), "| server hits:", hits());

const second = await queryClient.fetchQuery(productsQuery);
console.log("2nd:", second.map((p) => p.name), "| server hits:", hits(), "(from cache)");

const [a, b, c] = await Promise.all([
  queryClient.fetchQuery({ ...productsQuery, queryKey: ["products", "dedupe"] }),
  queryClient.fetchQuery({ ...productsQuery, queryKey: ["products", "dedupe"] }),
  queryClient.fetchQuery({ ...productsQuery, queryKey: ["products", "dedupe"] }),
]);
console.log("3 components asked at once → server hits:", hits(), "| same object?", a === b && b === c);

console.log("cached state:", queryClient.getQueryState(["products"]).status, "| stale?", queryClient.getQueryCache().find({ queryKey: ["products"] }).isStale());
stop();
EOF
node cache.mjs
```

```text output
1st: [ 'Mug', 'Desk Lamp' ] | server hits: 1
2nd: [ 'Mug', 'Desk Lamp' ] | server hits: 1 (from cache)
3 components asked at once → server hits: 2 | same object? true
cached state: success | stale? false
```

<Happened>
<Tr>
<En>

- The second request for `["products"]` didn't touch the server: the data was in the cache and still **fresh** (`staleTime: 60_000`, one minute).
- Three simultaneous requests for a new key (`["products", "dedupe"]`) caused **one** server hit, and all three callers got the **same** object. In React, three components calling `useQuery` with the same key share one request and one cache entry.
- The cache is keyed by the **query key**, so `["products"]` and `["products", "dedupe"]` are different entries.
- In React the same query looks like this:

```text
function ProductList() {
  const { data, status, error } = useQuery({
    queryKey: ["products"],
    queryFn: ({ signal }) => getJson("/api/products", { signal }),
    staleTime: 60_000,
  });
  if (status === "pending") return <p>Loading…</p>;
  if (status === "error") return <p>Couldn't load products: {error.message}</p>;
  return <ul>{data.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
}
```

</En>
<Ur>

- `["products"]` ki doosri request ne server ko nahi chhua: data cache me tha aur ab bhi **taaza** tha (`staleTime: 60_000`, ek minute).
- Nayi key (`["products", "dedupe"]`) ki teen saath requests ne **ek** server hit kiya, aur teeno call karne walon ko **wahi** object mila. React me wahi key ke saath `useQuery` call karne wale teen components ek request aur ek cache entry baant'te hain.
- Cache **query key** se hai, isliye `["products"]` aur `["products", "dedupe"]` alag entries hain.
- React me wahi query aisi dikhti hai:


<Step title="Query keys: include every input">

<Tr>
<En>

The query key is how the cache tells data apart, and it's also the **dependency list** of the query: when the key changes, a new query runs. So put **every variable the query function uses** into the key.

```text
function ProductPage({ category, page }) {
  const { data } = useQuery({
    queryKey: ["products", { category, page }],          // category and page are in the key
    queryFn: () => getJson(`/api/products?category=${category}&page=${page}`),
  });
}
```

| Key | Cached separately |
| --- | --- |
| `["products"]` | the full list |
| `["products", { category: "lamps", page: 1 }]` | lamps, page 1 |
| `["products", { category: "lamps", page: 2 }]` | lamps, page 2 |
| `["product", 42]` | one product |
| `["user", userId, "orders"]` | one user's orders |

</En>
<Ur>

Query key se cache data alag pehchanta hai, aur ye query ki **dependency list** bhi hai: key badalne par nayi query chalti hai. Isliye **query function ka istemal kiya har variable** key me rakhein.

```text
function ProductPage({ category, page }) {
  const { data } = useQuery({
    queryKey: ["products", { category, page }],          // category aur page key me hain
    queryFn: () => getJson(`/api/products?category=${category}&page=${page}`),
  });
}
```

| Key | Alag cache hota hai |
| --- | --- |
| `["products"]` | poori list |
| `["products", { category: "lamps", page: 1 }]` | lamps, page 1 |
| `["products", { category: "lamps", page: 2 }]` | lamps, page 2 |
| `["product", 42]` | ek product |
| `["user", userId, "orders"]` | ek user ke orders |

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- If you forget `page` in the key, page 2 would show page 1's cached data, a classic bug. The ESLint plugin `@tanstack/eslint-plugin-query` catches missing dependencies.
- Keys are **hierarchical**: `invalidateQueries({ queryKey: ["products"] })` matches every key that **starts with** `"products"`, so one call refreshes all product lists and pages.
- Objects in keys are compared by value (`{ page: 1, category: "lamps" }` equals `{ category: "lamps", page: 1 }`).
- Many teams keep keys in one place (a "query key factory": `productKeys.list(filters)`) to avoid typos.

</En>
<Ur>

- Agar aap key me `page` bhool jayen to page 2 page 1 ka cache data dikhayega, mashhoor bug. ESLint plugin `@tanstack/eslint-plugin-query` ghayab dependencies pakarta hai.
- Keys **darja ba darja** hain: `invalidateQueries({ queryKey: ["products"] })` `"products"` se **shuru hone wali** har key se milta hai, isliye ek call tamam product lists aur pages taaza kar deti hai.
- Keys me objects value se milaye jate hain (`{ page: 1, category: "lamps" }` barabar hai `{ category: "lamps", page: 1 }` ke).
- Bohot si teams typos se bachne ke liye keys ek jagah rakhti hain ("query key factory": `productKeys.list(filters)`).

<Step title="Fresh, stale and background refetching">

<Tr>
<En>

Two timers control the cache:

| Setting | Default | Meaning |
| --- | --- | --- |
| `staleTime` | `0` | how long data is **fresh**. Fresh data is served from cache without refetching. |
| `gcTime` | 5 minutes | how long data with **no components using it** stays in memory before being deleted. |

With the default `staleTime: 0`, cached data is shown **instantly** but immediately considered stale, so TanStack Query refetches it in the background when:

- a new component using that query **mounts**,
- the browser window **regains focus** (`refetchOnWindowFocus`),
- the network **reconnects** (`refetchOnReconnect`),
- or on an interval if you set `refetchInterval`.

</En>
<Ur>

Do timers cache ko control karte hain:

| Setting | Default | Matlab |
| --- | --- | --- |
| `staleTime` | `0` | data kitni der **taaza** hai. Taaza data dobara fetch kiye baghair cache se diya jata hai. |
| `gcTime` | 5 minute | **jise koi component istemal na kare** wo data mitaye jane se pehle kitni der memory me rahe. |

Default `staleTime: 0` ke saath cache ka data **foran** dikhta hai magar foran purana gina jata hai, isliye TanStack Query ise pas-e-parda dobara fetch karta hai jab:

- us query wala naya component **mount** ho,
- browser window par **focus wapas** aaye (`refetchOnWindowFocus`),
- network **dobara jure** (`refetchOnReconnect`),
- ya agar aap `refetchInterval` set karein to waqfe par.

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- `status` stays `"success"` during a background refetch, so the list doesn't flash a spinner; `isFetching` becomes `true`, which you can use for a subtle "Updating…" indicator.
- Choose `staleTime` by how fast the data changes: product catalogue: a few minutes; list of countries: `Infinity`; a live order queue: 0 plus `refetchInterval`.
- A common surprise: "my API is called every time I switch tabs". That's refetch-on-focus with `staleTime: 0`. Raise `staleTime` rather than turning off the feature.

</En>
<Ur>

- Pas-e-parda refetch ke dauran `status` `"success"` rehta hai, isliye list spinner nahi chamkati; `isFetching` `true` ho jata hai, jise aap halke "Updating…" ishare ke liye istemal kar sakte hain.
- `staleTime` is hisaab se chunein ke data kitni jaldi badalta hai: product catalogue: chand minute; countries ki list: `Infinity`; zinda order queue: 0 plus `refetchInterval`.
- Aam hairat: "har dafa tab badalne par meri API call hoti hai". Ye `staleTime: 0` ke saath focus par refetch hai. Feature band karne ke bajaye `staleTime` barhayen.

</Ur>
</Tr>
</Happened>

<Step title="Mutations and invalidation">

<Tr>
<En>
Here an **observer** watches the products query (that's what `useQuery` does inside a component), then a **mutation** creates a product and, on success, **invalidates** the list so it refetches. Watch what the "UI" shows.
</En>
<Ur>
Yahan ek **observer** products query dekhta hai (component ke andar `useQuery` yahi karta hai), phir **mutation** product banati hai aur kamyabi par list ko **invalidate** karti hai taa ke wo dobara fetch ho. Dekhein "UI" kya dikhata hai.
</Ur>
</Tr>

```bash
cat > mutate.mjs <<'EOF'
import { QueryClient, MutationObserver, QueryObserver } from "@tanstack/query-core";
import { start, getJson } from "./api.mjs";
const { base, hits, stop } = await start();

const queryClient = new QueryClient();

// Like useQuery: an observer that is notified whenever the cached data changes
const observer = new QueryObserver(queryClient, {
  queryKey: ["products"],
  queryFn: () => getJson(base + "/api/products"),
});
const unsubscribe = observer.subscribe((result) => {
  if (result.status === "success") console.log("UI shows:", result.data.map((p) => p.name).join(", "), result.isFetching ? "(refreshing…)" : "");
});
await new Promise((r) => setTimeout(r, 150));

// Like useMutation: create a product, then invalidate the list
const addProduct = new MutationObserver(queryClient, {
  mutationFn: (newProduct) =>
    getJson(base + "/api/products", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify(newProduct),
    }),
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ["products"] }),
});
const created = await addProduct.mutate({ name: "Notebook", price: 6.5 });
console.log("created:", created);
await new Promise((r) => setTimeout(r, 150));
console.log("server hits:", hits());
unsubscribe();
stop();
EOF
```

<Step title="Retries with backoff, and errors">

<Tr>
<En>
Queries retry failed requests automatically (3 times by default, with exponential backoff). Our `/api/flaky` endpoint fails twice with 503, then succeeds. A request that fails every time ends in the `error` status.
</En>
<Ur>
Queries nakam requests khud dobara chalati hain (default me 3 dafa, exponential backoff ke saath). Hamara `/api/flaky` endpoint do dafa 503 ke saath fail hota hai, phir kamyab. Har dafa fail hone wali request `error` status par khatam hoti hai.
</Ur>
</Tr>

```bash
cat > retry.mjs <<'EOF'
import { QueryClient } from "@tanstack/query-core";
import { start, getJson } from "./api.mjs";
const { base, stop } = await start();

const queryClient = new QueryClient();
const t0 = Date.now();
const data = await queryClient.fetchQuery({
  queryKey: ["flaky"],
  queryFn: async ({ queryKey }) => {
    try {
      return await getJson(base + "/api/flaky");
    } catch (e) {
      console.log("attempt failed:", e.message);
      throw e;
    }
  },
  retry: 3,
  retryDelay: (attempt) => 100 * 2 ** attempt,
});
console.log("result:", data, "| after ~" + Math.round((Date.now() - t0) / 100) * 100 + " ms");

try {
  await queryClient.fetchQuery({ queryKey: ["missing"], queryFn: () => getJson(base + "/api/nope"), retry: 1, retryDelay: 50 });
} catch (e) {
  console.log("gave up:", e.message, "| query status:", queryClient.getQueryState(["missing"]).status);
}
stop();
EOF
node retry.mjs
```

```text output
attempt failed: HTTP 503: busy
result: { ok: true, attempt: 3 } | after ~300 ms
gave up: HTTP 404: not found | query status: error
```

<Happened>
<Tr>
<En>

- Two failures, waits of 100 ms and 200 ms (our `retryDelay`), then success: the user never saw an error.
- The 404 was retried once (`retry: 1`) and then gave up, leaving the query in `status: "error"` with the error saved for the UI.
- The query function **must throw** on failure. Plain `fetch` doesn't throw on 404/500 (fetch lesson), which is why `getJson` checks `res.ok`.
- Retrying a 404 is pointless. A smarter rule: `retry: (count, error) => error.status >= 500 && count < 3`.
- Errors can also go to an Error Boundary (`throwOnError: true`) or a global handler (`QueryCache({ onError })`) for toasts and logging.

</En>
<Ur>

- Do nakamiyan, 100 ms aur 200 ms ke intezar (hamara `retryDelay`), phir kamyabi: user ne kabhi error nahi dekha.
- 404 ek dafa dobara chala (`retry: 1`) phir chhor diya, query ko UI ke liye mehfooz error ke saath `status: "error"` me chhorte hue.
- Query function ko nakami par **throw karna zaroori** hai. Saada `fetch` 404/500 par throw nahi karta (fetch lesson), isi liye `getJson` `res.ok` check karta hai.
- 404 dobara chalana bekaar hai. Zyada samajhdar qaida: `retry: (count, error) => error.status >= 500 && count < 3`.
- Errors Error Boundary (`throwOnError: true`) ya toasts aur logging ke liye global handler (`QueryCache({ onError })`) tak bhi ja sakte hain.

</Ur>

<Step title="Optimistic updates with rollback">

<Tr>
<En>
For small, likely-to-succeed actions (toggling a checkbox, liking a post), waiting for the server feels slow. An **optimistic update** changes the cache **immediately**, and if the server rejects the change, **rolls back** to the saved previous value.
</En>
<Ur>
Chhote, kamyabi ke qareeb amal (checkbox toggle, post like) ke liye server ka intezar sust lagta hai. **Optimistic update** cache **foran** badalta hai, aur agar server tabdeeli radd kare to mehfooz pichhli value par **wapas** jata hai.
</Ur>
</Tr>

```bash
cat > optimistic.mjs <<'EOF'
import { QueryClient, MutationObserver } from "@tanstack/query-core";

const queryClient = new QueryClient();
queryClient.setQueryData(["todos"], [{ id: 1, title: "Pack order", done: false }]);
const show = (label) => console.log(label.padEnd(22), JSON.stringify(queryClient.getQueryData(["todos"])));

// Pretend server: fails when the title is empty
const saveToggle = (todo) =>
  new Promise((resolve, reject) => setTimeout(() => (todo.title ? resolve(todo) : reject(new Error("Server rejected"))), 100));

const toggle = new MutationObserver(queryClient, {
  mutationFn: saveToggle,
  onMutate: async (todo) => {
    const previous = queryClient.getQueryData(["todos"]);
    queryClient.setQueryData(["todos"], (old) => old.map((t) => (t.id === todo.id ? { ...t, done: !t.done } : t)));
    show("optimistic:");
    return { previous };
  },
  onError: (error, todo, context) => {
    queryClient.setQueryData(["todos"], context.previous);
    show("rolled back (" + error.message + "):");
  },
});

show("start:");
await toggle.mutate({ id: 1, title: "Pack order" });
show("saved:");
await toggle.mutate({ id: 1, title: "" }).catch(() => {});
EOF
node optimistic.mjs
```

```text output
start:                 [{"id":1,"title":"Pack order","done":false}]
optimistic:            [{"id":1,"title":"Pack order","done":true}]
saved:                 [{"id":1,"title":"Pack order","done":true}]
optimistic:            [{"id":1,"title":"Pack order","done":false}]
rolled back (Server rejected): [{"id":1,"title":"Pack order","done":true}]
```

<Happened>
<Tr>
<En>

- First toggle: the cache flipped to `done: true` **before** the 100 ms server call finished, then stayed that way when the server agreed.
- Second toggle: the UI flipped to `false` instantly, the server rejected it, and `onError` restored the saved snapshot (`done: true`).
- The recipe: in `onMutate`, cancel in-flight queries for that key (`await queryClient.cancelQueries(...)`), snapshot the old data, write the optimistic data, and return the snapshot as **context**; in `onError`, restore it; in `onSettled`, invalidate to sync with the server.
- Use optimistic updates for small, reversible actions. For payments or anything with serious side effects, show a pending state and wait for the server.

</En>
<Ur>

- Pehla toggle: 100 ms ki server call khatam hone se **pehle** cache `done: true` par palat gaya, phir server ke muttafiq hone par waisa hi raha.
- Doosra toggle: UI foran `false` par palta, server ne radd kiya, aur `onError` ne mehfooz snapshot (`done: true`) wapas lagaya.
- Tarkeeb: `onMutate` me us key ki chalti queries mansookh karein (`await queryClient.cancelQueries(...)`), purane data ka snapshot lein, optimistic data likhein, aur snapshot **context** ke taur par wapas karein; `onError` me use wapas lagayen; `onSettled` me server se sync ke liye invalidate karein.
- Optimistic updates chhote, wapas hone layaq amal ke liye lein. Payments ya sangeen asar wali kisi cheez ke liye pending halat dikhayen aur server ka intezar karein.

</Ur>
</Tr>
</Happened>

<Step title="Dependent queries, pagination and prefetching">

<Tr>
<En>

Common patterns, each a few lines with TanStack Query:


## Common mistakes

<Compare>
<Bad title="Missing variables in the query key">

```text
useQuery({
  queryKey: ["products"],
  queryFn: () => getJson(`/api/products?page=${page}`),   // page isn't in the key
});
// changing page shows page 1's cached data and never refetches
```

</Bad>
<Good title="Every input is part of the key">

```text
useQuery({
  queryKey: ["products", { page }],
  queryFn: () => getJson(`/api/products?page=${page}`),
});
```

</Good>
</Compare>

<Compare>
<Bad title="Copying query data into state">

```text
const { data } = useQuery({ queryKey: ["todos"], queryFn: getTodos });
const [todos, setTodos] = useState([]);
useEffect(() => { if (data) setTodos(data); }, [data]);
// two sources of truth: background refetches and your edits fight each other
```

</Bad>
<Good title="Use the query data directly; change it with mutations">

```text
const { data: todos = [] } = useQuery({ queryKey: ["todos"], queryFn: getTodos });
const toggle = useMutation({ mutationFn: toggleTodo, onSuccess: () => queryClient.invalidateQueries({ queryKey: ["todos"] }) });
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Query functions that don't throw** on HTTP errors, so failures look like successful empty data.
- **Creating a new `QueryClient` on every render** (or a shared module-level one on the server).
- **Forgetting to invalidate** after a mutation, so the list stays out of date.
- **`staleTime: 0` everywhere** causing constant refetches; set sensible defaults.
- **Using TanStack Query for client-only UI state** like "is the modal open".
- **Retrying non-idempotent mutations automatically** (duplicate orders).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **HTTP errors par throw na karne wale query functions**, taa ke nakamiyan kamyab khaali data jaisi lagein.
- **Har render par naya `QueryClient` banana** (ya server par mushtarka module-level wala).
- Mutation ke baad **invalidate karna bhoolna**, taa ke list purani rahe.
- **Har jagah `staleTime: 0`** jo musalsal refetch karata hai; samajhdar defaults set karein.
- **Sirf client wali UI state ke liye TanStack Query istemal karna** jaise "kya modal khula hai".
- **Ghair idempotent mutations ko khud dobara chalana** (dohre orders).

</Ur>
</Tr>

Loading, error aur kamyabi ki halaten render karein.

<Solution>

```text
export function useProduct(id) {
  return useQuery({
    queryKey: ["product", id],
    queryFn: ({ signal }) => getJson(`/api/products/${id}`, { signal }),
    staleTime: 5 * 60_000,
    enabled: id != null,
  });
}

export function useUpdatePrice() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: ({ id, price }) =>
      getJson(`/api/products/${id}`, {
        method: "PUT",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ price }),
      }),
    onSuccess: (updated) => {
      queryClient.setQueryData(["product", updated.id], updated);     // detail page updates instantly
      queryClient.invalidateQueries({ queryKey: ["products"] });      // lists refetch
    },
  });
}

function ProductPage({ id }) {
  const { data: product, status, error } = useProduct(id);
  const updatePrice = useUpdatePrice();
  if (status === "pending") return <p>Loading…</p>;
  if (status === "error") return <p role="alert">{error.message}</p>;
  return (
    <div>
      <h2>{product.name}: ${product.price}</h2>
      <button disabled={updatePrice.isPending}
              onClick={() => updatePrice.mutate({ id, price: product.price + 1 })}>
        {updatePrice.isPending ? "Saving…" : "Raise price by $1"}
      </button>
    </div>
  );
}
```

## Remember

<Takeaways>
<Tr>
<En>

- **Server state** is cached remote data; manage it with a query library, not ad-hoc `useEffect` or global stores.
- `useQuery({ queryKey, queryFn })`: key = identity + dependencies; `queryFn` must **throw** on errors.
- The cache **deduplicates** requests and shares data across components.
- `staleTime` = fresh period (default 0); `gcTime` = how long unused data stays (default 5 min); stale data is refetched in the background on mount, focus and reconnect.
- `status` for first load; `isFetching` for background refreshes.
- Changes: `useMutation` + `invalidateQueries` (or `setQueryData`); optimistic updates need a snapshot and rollback.
- Retries with backoff are built in (queries yes, mutations no by default).
- Patterns: `enabled` for dependent queries, `keepPreviousData` for pagination, `useInfiniteQuery`, prefetching.
- One `QueryClient` per browser session; use the Devtools.

</En>

<DeepDive title="More about TanStack Query">

**`select`.** Transform or pick part of the data per component (`select: (data) => data.length`); components re-render only when the selected result changes.

**Structural sharing.** When refetched data is deeply equal to the old data, the library keeps the old references, so `memo`-ised components don't re-render needlessly.

**`queryOptions` helper.** Define `const productQuery = (id) => queryOptions({ queryKey: ["product", id], queryFn: … })` once and reuse it in `useQuery`, `prefetchQuery` and `invalidateQueries` with full TypeScript types.

**Suspense.** `useSuspenseQuery` integrates with `<Suspense>` boundaries and always returns data (no pending branch in the component).

**Persistence.** `persistQueryClient` can save the cache to storage for offline-first apps (mind what you store).

**Network mode.** Queries pause while offline and resume when the network returns; mutations can be queued.

**Alternatives.** SWR (smaller, similar ideas), RTK Query (for Redux apps), Apollo/urql (GraphQL), and Next.js server components with `fetch` caching for data that can load on the server.

**Testing.** Wrap components in a fresh `QueryClient` per test with `retry: false`, and mock the network with MSW (Mock Service Worker).

</DeepDive>

<DeepDive title="Real world: 40 requests to open one page">

A team's order dashboard showed a header with the user's name, a sidebar with notification counts, a table of orders and a details panel. Each component fetched its own data in a `useEffect`. Opening the page fired **40 requests**: the user profile alone was requested by seven components, the notification count every time the sidebar re-rendered, and switching between orders refetched everything.

They moved data access into a few hooks built on TanStack Query:

1. `useMe()` (`["me"]`, `staleTime` 5 minutes): seven components, **one** request.
2. `useNotifications()` with `refetchInterval: 30_000` instead of refetching on every render.
3. `useOrders(filters)` with filters in the key and `keepPreviousData`, so paging felt instant.
4. `useOrder(id)` with prefetching when the mouse hovered over a row.
5. Mutations ("mark as shipped") invalidated `["orders"]` and updated `["order", id]` directly.

Page load went from 40 requests to 4, switching orders became instant thanks to prefetching, and several "the table shows old status after I updated it" bugs disappeared because invalidation replaced hand-written list updates.

</DeepDive>

<DeepDive title="Security lens">

- **Clear the cache on logout** (`queryClient.clear()`): otherwise the next person on a shared device may briefly see the previous user's data.
- **Include the user (or tenant) in keys for per-user data** when one client may serve different accounts, so caches never mix.
- **Never share a `QueryClient` between requests on the server**: one user's data could leak into another's page.
- **The cache is readable in the browser** (Devtools, memory); don't fetch data the user isn't allowed to see, and enforce authorization on the API, not by hiding queries.
- **Validate responses** in query functions (zod) so a compromised or changed API can't put unexpected shapes into your UI.
- **Don't automatically retry non-idempotent mutations**, and use idempotency keys for payments.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What problems does TanStack Query solve compared with fetching in useEffect?">
It provides a shared cache keyed by query keys, request deduplication, stale-while-revalidate background refetching, retries with backoff, refetch on focus and reconnect, cancellation, pagination and infinite queries, mutation handling with cache invalidation and optimistic updates, and devtools, removing a lot of error-prone manual code.
</QA>

<QA q="What is the difference between staleTime and gcTime?">
staleTime is how long fetched data is considered fresh, during which it is served from cache without refetching. gcTime is how long inactive query data, with no observers, stays in the cache before being garbage collected.
</QA>

<QA q="How do you update the UI after a mutation?">
Either invalidate the affected queries in the mutation's onSuccess so active ones refetch from the server, or update the cache directly with setQueryData using the mutation's response, or apply an optimistic update in onMutate with a rollback in onError and invalidation in onSettled.
</QA>

<QA q="Why should every variable used in the query function be in the query key?">
Because the key identifies the cached data and acts as the query's dependency list. If a variable is missing, different inputs would share one cache entry and changing the variable would not trigger a refetch, showing wrong data.
</QA>

<QA q="What is server state and why treat it differently from client state?">
Server state is data owned by a remote source that the client only caches; it can be changed by others and become out of date, and it requires fetching, caching, synchronisation and invalidation. Client state is owned by the UI. Mixing them in a global store leads to stale data and duplicated logic.
</QA>

</DeepDive>
