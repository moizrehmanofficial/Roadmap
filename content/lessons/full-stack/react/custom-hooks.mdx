<BigIdea>
<Tr>
<En>
React's built-in hooks (`useState`, `useEffect`, `useRef`…) let a component remember things and react to changes. Real components often combine them into small **recipes**: "a boolean with toggle/on/off", "a value that updates 300 ms after typing stops", "data loaded from a URL with loading and error states", "a setting saved in localStorage". Copying these recipes between components leads to duplicated code and duplicated bugs. A **custom hook** packages a recipe into a **function whose name starts with `use`** and that **calls other hooks**: `useDebouncedValue(search, 300)`, `useFetch("/api/products")`. Components then read like a description of **what** they need, not **how** it works. The key fact that surprises beginners: hooks share **logic**, not **state**. Two components calling `useToggle()` each get their own independent boolean, exactly as if each had written the code itself. Custom hooks follow the same **rules of hooks**: call them at the top level of components or other hooks, never inside conditions or loops.
</En>
<Ur>
React ke bane banaye hooks (`useState`, `useEffect`, `useRef`…) component ko cheezen yaad rakhne aur tabdeeliyon par amal karne dete hain. Asli components aksar inhen chhoti **tarkeebon** me jorte hain: "toggle/on/off wala boolean", "aisi value jo typing rukne ke 300 ms baad update ho", "URL se load hua data loading aur error halaton ke saath", "localStorage me mehfooz setting". Ye tarkeebein components ke darmiyan copy karna dohra code aur dohre bugs laata hai. **Custom hook** tarkeeb ko **aise function me band karta hai jis ka naam `use` se shuru ho** aur jo **doosre hooks call kare**: `useDebouncedValue(search, 300)`, `useFetch("/api/products")`. Phir components is ka bayan lagte hain ke unhen **kya** chahiye, ye nahi ke wo **kaise** kaam karta hai. Wo haqeeqat jo naye seekhne walon ko hairan karti hai: hooks **logic** baant'te hain, **state** nahi. `useToggle()` call karne wale do components ko har ek ka apna aazad boolean milta hai, bilkul aise jaise har ek ne code khud likha ho. Custom hooks wahi **hooks ke qawaid** maante hain: unhen components ya doosre hooks ke top level par call karein, kabhi shart ya loop ke andar nahi.
</Ur>
</Tr>
</BigIdea>

<How>
<Tr>
<En>

1. Find the stateful code you want to reuse (the hooks and the functions that use them).
2. Move it into `function useSomething(inputs) { … }`; name must start with `use`.
3. Return what callers need: an array for 1–2 values (like `useState`), an object for more.
4. Call it at the top level of components; each call gets its own state.

</En>
<Ur>

1. Dobara istemal karne wala stateful code dhoondhein (hooks aur unhen istemal karne wale functions).
2. Ise `function useSomething(inputs) { … }` me le jayen; naam `use` se shuru hona zaroori.
3. Call karne walon ki zaroorat wapas karein: 1–2 values ke liye array (`useState` ki tarah), zyada ke liye object.
4. Ise components ke top level par call karein; har call ko apni state milti hai.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of **recipes in a cookbook**.

- A recipe ("chocolate chip cookies") describes **how** to combine basic steps: mix, chill, bake. A custom hook describes how to combine basic hooks: state, effect, ref.
- Ten people can follow the same recipe and each gets **their own batch** of cookies. Following a recipe doesn't share the cookies. Likewise, ten components calling `useCart()` each get their own state, unless the recipe itself says "fetch the shared tin from the cupboard" (context or a store).
- A good recipe has a clear name and a short ingredient list (inputs) and tells you what you'll end up with (return value).
- The recipe only works if you follow its steps **in order every time** (rules of hooks): you can't decide to skip "chill the dough" on Tuesdays.

</En>
<Ur>

**Cookbook ki tarkeebon** ka sochein.

- Tarkeeb ("chocolate chip cookies") bayan karti hai ke buniyadi qadam **kaise** jorne hain: milao, thanda karo, bake karo. Custom hook bayan karta hai ke buniyadi hooks kaise jorne hain: state, effect, ref.
- Das log ek hi tarkeeb par chal sakte hain aur har ek ko **apna batch** cookies milta hai. Tarkeeb par chalna cookies nahi baant'ta. Isi tarah `useCart()` call karne wale das components ko har ek ki apni state milti hai, jab tak tarkeeb khud na kahe "almari se mushtarka dabba lao" (context ya store).
- Achhi tarkeeb ka saaf naam aur chhoti ajza ki list (inputs) hoti hai aur batati hai ke aakhir me kya milega (wapas aane wali value).
- Tarkeeb tabhi chalti hai jab aap us ke qadam **har dafa usi tarteeb se** karein (hooks ke qawaid): aap mangal ko "aata thanda karo" chhorne ka faisla nahi kar sakte.

</Ur>
</Tr>

<Step title="Extract your first hook: useToggle">

<Tr>
<En>
Showing/hiding things is everywhere: menus, password fields, details panels. Instead of writing `useState` plus three small functions each time, put them in `useToggle`.
</En>
<Ur>
Cheezen dikhana/chhupana har jagah hai: menus, password fields, details panels. Har dafa `useState` plus teen chhote functions likhne ke bajaye unhen `useToggle` me rakhein.
</Ur>
</Tr>

```jsx preview h=200
import { useState, useCallback } from "react";

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  return [on, toggle, setOn];
}

function PasswordField() {
  const [visible, toggleVisible] = useToggle();
  return (
    <p>
      <input type={visible ? "text" : "password"} defaultValue="correct-horse" />{" "}
      <button onClick={toggleVisible}>{visible ? "Hide" : "Show"}</button>
    </p>
  );
}

function Details() {
  const [open, toggleOpen, setOpen] = useToggle(true);
  return (
    <div>
      <button onClick={toggleOpen}>{open ? "▾" : "▸"} Shipping details</button>{" "}
      <button onClick={() => setOpen(false)}>Collapse</button>
      {open && <p>Ships in 2–3 business days. Free over $50.</p>}
    </div>
  );
}

export default function App() {
  return (
    <div>
      <PasswordField />
      <PasswordField />
      <Details />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Click **Show** on the first password field: only that one reveals its text. The second field stays hidden. **Each call to `useToggle` has its own state.**
- `useToggle` returns an array like `useState`, so each component names the parts (`visible`, `toggleVisible`) and can ignore what it doesn't need.
- The updater form `setOn((v) => !v)` avoids stale values if toggled quickly, and `useCallback` keeps `toggle` the same function between renders (handy if it's passed to memoised children).
- A custom hook is just a function. React doesn't know `useToggle` exists; it only sees the `useState` call inside, attached to whichever component called it.

</En>
<Ur>

- Pehle password field par **Show** dabayen: sirf wahi apna text dikhata hai. Doosra field chhupa rehta hai. **`useToggle` ki har call ki apni state hai.**
- `useToggle` `useState` ki tarah array wapas karta hai, isliye har component hisson ko naam deta hai (`visible`, `toggleVisible`) aur jo na chahiye use nazarandaz kar sakta hai.
- Updater wala `setOn((v) => !v)` jaldi jaldi toggle par purani values se bachata hai, aur `useCallback` `toggle` ko renders ke darmiyan wahi function rakhta hai (memoised children ko dene par kaam ka).
- Custom hook bas function hai. React ko `useToggle` ke hone ka pata nahi; wo sirf andar ki `useState` call dekhta hai, jo usi component se jurti hai jis ne ise call kiya.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The rules of hooks, and why they exist">

<Tr>
<En>

React identifies each hook in a component by its **call order**: "the first `useState`, the second `useState`, the first `useEffect`…". So the order must be **identical on every render**:

1. **Only call hooks at the top level** of a component or custom hook: not inside `if`, loops, nested functions or after an early `return`.
2. **Only call hooks from React functions**: components and custom hooks, not regular utilities or event handlers.
3. **Name custom hooks `useSomething`**, so React's ESLint plugin can check the rules inside them.

```text
function Profile({ userId }) {
  if (!userId) return <p>Not logged in</p>;   // ✗ early return before hooks
  const [tab, setTab] = useState("posts");    // sometimes called, sometimes not
  …
}

function Profile({ userId }) {
  const [tab, setTab] = useState("posts");    // ✓ hooks first, always
  if (!userId) return <p>Not logged in</p>;
  …
}
```

</En>
<Ur>

React component ke har hook ko us ki **call ki tarteeb** se pehchanta hai: "pehla `useState`, doosra `useState`, pehla `useEffect`…". Isliye tarteeb **har render par bilkul ek jaisi** honi chahiye:

1. **Hooks sirf top level par call karein**, component ya custom hook ke: `if`, loops, nested functions ke andar ya jaldi `return` ke baad nahi.
2. **Hooks sirf React functions se call karein**: components aur custom hooks, aam utilities ya event handlers se nahi.
3. **Custom hooks ka naam `useSomething` rakhein**, taa ke React ka ESLint plugin un ke andar qawaid check kar sake.

```text
function Profile({ userId }) {
  if (!userId) return <p>Not logged in</p>;   // ✗ hooks se pehle jaldi return
  const [tab, setTab] = useState("posts");    // kabhi call hota hai, kabhi nahi
  …
}

function Profile({ userId }) {
  const [tab, setTab] = useState("posts");    // ✓ hooks pehle, hamesha
  if (!userId) return <p>Not logged in</p>;
  …
}
```

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- In the bad version, when `userId` changes from empty to set, the number of hooks changes between renders. React throws "Rendered more hooks than during the previous render" (or worse, mixes up state).
- Put conditions **inside** hooks instead: `useEffect(() => { if (!userId) return; … }, [userId])`.
- `eslint-plugin-react-hooks` (included in Next.js and Vite templates) flags these mistakes and missing effect dependencies. Keep it on.
- React 19's `use()` is the one exception that can be called conditionally; normal hooks can't.

</En>
<Ur>

- Ghalat version me jab `userId` khaali se set hota hai, renders ke darmiyan hooks ki tadaad badal jati hai. React "Rendered more hooks than during the previous render" throw karta hai (ya bura, state ulat palat kar deta hai).
- Shartein hooks ke **andar** rakhein: `useEffect(() => { if (!userId) return; … }, [userId])`.
- `eslint-plugin-react-hooks` (Next.js aur Vite templates me shamil) ye ghaltiyan aur effect ki ghayab dependencies pakarta hai. Ise on rakhein.
- React 19 ka `use()` wahid istisna hai jo shart ke saath call ho sakta hai; aam hooks nahi.

</Ur>
</Tr>
</Happened>

<Step title="useDebouncedValue: a hook with an effect and cleanup">

<Tr>
<En>
Custom hooks can contain effects. This one returns a value that only updates after the input has been still for a while, which is perfect for search boxes. The cleanup cancels the pending timer whenever the value changes again.
</En>
<Ur>
Custom hooks me effects ho sakte hain. Ye aisi value wapas karta hai jo input ke kuch der thame rehne ke baad hi update hoti hai, search boxes ke liye behtareen. Cleanup har dafa value dobara badalne par pending timer mansookh karta hai.
</Ur>
</Tr>

```jsx preview h=230
import { useEffect, useState } from "react";

function useDebouncedValue(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  return debounced;
}

const products = ["Desk Lamp", "Floor Lamp", "Lamp Shade", "Mug", "Notebook", "Pen"];

export default function App() {
  const [query, setQuery] = useState("");
  const debouncedQuery = useDebouncedValue(query, 400);
  const results = products.filter((p) => p.toLowerCase().includes(debouncedQuery.toLowerCase()));

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} placeholder="Search products" />
      <p>Typing: "{query}" · Searching for: "{debouncedQuery}"</p>
      <ul>{results.map((r) => <li key={r}>{r}</li>)}</ul>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Type "lamp" quickly: "Typing" updates with every letter, but "Searching for" stays at the old value and only jumps to "lamp" 400 ms after you stop. The list then shows the three lamps.
- Each keystroke changes `value`, so React runs the cleanup (clearing the old timer) before starting a new one. Only the last timer survives.
- In a real app, the `debouncedQuery` would go into a fetch (`useFetch` below or TanStack Query), so you send one request per pause instead of one per letter.
- The input itself stays responsive because it's driven by `query`, not the debounced value.

</En>
<Ur>

- Jaldi se "lamp" likhein: "Typing" har harf ke saath update hota hai, magar "Searching for" purani value par rehta hai aur aap ke rukne ke 400 ms baad hi "lamp" par koodta hai. Phir list teeno lamps dikhati hai.
- Har key `value` badalti hai, isliye React naya timer shuru karne se pehle cleanup chalata hai (purana timer saaf karte hue). Sirf aakhri timer bachta hai.
- Asli app me `debouncedQuery` fetch me jati (neeche `useFetch` ya TanStack Query), taa ke aap har harf ke bajaye har waqfe par ek request bhejein.
- Input khud jawab deta rehta hai kyun ke wo `query` se chalta hai, debounced value se nahi.

</Ur>
</Tr>
</Happened>

<Step title="useLocalStorage: same API as useState, but remembered">

<Tr>
<En>
This hook behaves like `useState` but also saves the value to localStorage and reads it back on the next visit. It must cope with storage being **unavailable** or containing **corrupt** data (Cookies and Storage lesson). This preview runs in a sandboxed frame without storage, so you'll see the fallback in action.
</En>
<Ur>
Ye hook `useState` ki tarah bartao karta hai magar value localStorage me mehfooz bhi karta hai aur agli visit par wapas parhta hai. Ise storage ke **ghair dastiyab** hone ya us me **kharab** data hone se nimatna hota hai (Cookies aur Storage lesson). Ye preview bina storage wale sandboxed frame me chalta hai, isliye aap fallback ko kaam karte dekhenge.
</Ur>
</Tr>

```jsx preview h=200
import { useEffect, useState } from "react";

function readStorage(key, initialValue) {
  try {
    const raw = window.localStorage.getItem(key);
    return { value: raw === null ? initialValue : JSON.parse(raw), available: true };
  } catch {
    return { value: initialValue, available: false };
  }
}

function useLocalStorage(key, initialValue) {
  const [state, setState] = useState(() => readStorage(key, initialValue));

  useEffect(() => {
    if (!state.available) return;
    try {
      window.localStorage.setItem(key, JSON.stringify(state.value));
    } catch {
      // storage full or blocked: keep working in memory
    }
  }, [key, state]);

  const setValue = (next) =>
    setState((s) => ({ ...s, value: typeof next === "function" ? next(s.value) : next }));

  return [state.value, setValue, state.available];
}

export default function App() {
  const [theme, setTheme, saved] = useLocalStorage("theme", "light");
  const [fontSize, setFontSize] = useLocalStorage("font-size", 16);

  return (
    <div style={{ background: theme === "dark" ? "#0f172a" : "#fff", color: theme === "dark" ? "#f8fafc" : "#0f172a",
                  padding: 12, fontSize }}>
      <button onClick={() => setTheme((t) => (t === "light" ? "dark" : "light"))}>Theme: {theme}</button>{" "}
      <button onClick={() => setFontSize((s) => Math.min(s + 2, 24))}>A+</button>
      <button onClick={() => setFontSize((s) => Math.max(s - 2, 12))}>A−</button>
      <p>{saved ? "Saved in localStorage: reload and it stays." : "Storage isn't available here, so settings are kept in memory only."}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- The buttons switch the theme and font size. In this preview the message says storage isn't available and the settings are kept in memory, so the page keeps working. In a normal page (your own app), the message says "Saved in localStorage" and the settings survive a reload.
- `useState(() => readStorage(…))` uses a **lazy initialiser**: storage is read once, on the first render, not on every render.
- The setter accepts a value **or** an updater function, exactly like `useState`, so callers don't need to learn a new API.
- In Next.js, `localStorage` doesn't exist during server rendering. A production version reads storage in an effect (or uses `useSyncExternalStore`) to avoid hydration mismatches, and can listen to the `storage` event to sync tabs.

</En>
<Ur>

- Buttons theme aur font size badalte hain. Is preview me paighaam kehta hai ke storage dastiyab nahi aur settings memory me rakhi ja rahi hain, isliye page chalta rehta hai. Aam page (aap ki apni app) me paighaam kehta hai "Saved in localStorage" aur settings reload ke baad bhi bachti hain.
- `useState(() => readStorage(…))` **lazy initialiser** istemal karta hai: storage pehle render par ek dafa parha jata hai, har render par nahi.
- Setter value **ya** updater function qubool karta hai, bilkul `useState` ki tarah, isliye call karne walon ko nayi API nahi seekhni.
- Next.js me server rendering ke dauran `localStorage` maujood nahi. Production version hydration ke farq se bachne ke liye storage effect me parhta hai (ya `useSyncExternalStore` istemal karta hai), aur tabs sync karne ke liye `storage` event sun sakta hai.

</Ur>
</Tr>
</Happened>

</Step>

The fetch logic from earlier lessons (status, errors, `res.ok`, aborting stale requests) is a perfect candidate for a hook. Here `fakeFetch` pretends to be a server so the demo works offline. Switch quickly between users and try the failing one.
</En>
<Ur>
Pichhle lessons ki fetch logic (status, errors, `res.ok`, purani requests abort karna) hook ke liye behtareen umeedwar hai. Yahan `fakeFetch` server ka roop dhaarta hai taa ke demo offline chale. Users ke darmiyan jaldi badlein aur fail hone wala aazmayen.
</Ur>

```jsx preview h=240
  const id = Number(url.split("/").pop());
  const users = { 1: { name: "Sara Lee", orders: 4 }, 2: { name: "Alex Kim", orders: 11 } };
  return new Promise((resolve, reject) => {
    const t = setTimeout(() => {
      resolve(users[id]
        ? new Response(JSON.stringify(users[id]), { headers: { "content-type": "application/json" } })
        : new Response(JSON.stringify({ error: "User not found" }), { status: 404 }));
    }, 300 + id * 200);
    signal.addEventListener("abort", () => { clearTimeout(t); reject(new DOMException("Aborted", "AbortError")); });
  });
}

function useFetch(url) {
  const [state, setState] = useState({ status: "loading", data: null, error: null });

  useEffect(() => {
    const controller = new AbortController();
    setState({ status: "loading", data: null, error: null });
    fakeFetch(url, { signal: controller.signal })
      .then(async (res) => {
        const body = await res.json();
        if (!res.ok) throw new Error(body.error ?? "HTTP " + res.status);
        setState({ status: "success", data: body, error: null });
      })
      .catch((error) => {
        if (error.name !== "AbortError") setState({ status: "error", data: null, error: error.message });
      });
    return () => controller.abort();
  }, [url]);

  return state;
}

function UserCard({ id }) {
  const { status, data, error } = useFetch("/api/users/" + id);
  if (status === "loading") return <p>Loading user {id}…</p>;
  if (status === "error") return <p style={{ color: "#dc2626" }}>Couldn't load user {id}: {error}</p>;
  return <p><strong>{data.name}</strong> has {data.orders} orders.</p>;
}

export default function App() {
  const [id, setId] = useState(1);
  return (
    <div>
      {[1, 2, 3].map((n) => (
        <button key={n} onClick={() => setId(n)} disabled={n === id}>User {n}</button>
      ))}
      <UserCard id={id} />
    </div>
  );
}
```

<Step title="useKeyboardShortcut: listeners and the latest handler">

<Tr>
<En>
Hooks that add event listeners must remove them in cleanup. A subtle problem: if the handler uses state, re-adding the listener on every render is wasteful, but keeping an old one shows **stale** values. The fix is to store the latest handler in a ref.
</En>
<Ur>
Event listeners jorne wale hooks ko cleanup me unhen hatana zaroori hai. Ek bareek masla: agar handler state istemal kare to har render par listener dobara jorna fuzool hai, magar purana rakhna **purani** values dikhata hai. Hal ye hai ke taaza handler ref me rakhein.
</Ur>
</Tr>

```jsx preview h=200
import { useEffect, useRef, useState } from "react";

function useKeyboardShortcut(key, handler, { ctrl = false } = {}) {
  const handlerRef = useRef(handler);
  handlerRef.current = handler; // always the latest function, no re-subscribe

  useEffect(() => {
    function onKeyDown(e) {
      if (e.key.toLowerCase() === key && (!ctrl || e.ctrlKey || e.metaKey)) {
        e.preventDefault();
        handlerRef.current(e);
      }
    }
    window.addEventListener("keydown", onKeyDown);
    return () => window.removeEventListener("keydown", onKeyDown);
  }, [key, ctrl]);
}

export default function App() {
  const [count, setCount] = useState(0);
  const [log, setLog] = useState("Click here, then press N or Ctrl/⌘+S");

  useKeyboardShortcut("n", () => setCount((c) => c + 1));
  useKeyboardShortcut("s", () => setLog("Saved draft with " + count + " notes"), { ctrl: true });

  return (
    <div>
      <p>Notes: <strong>{count}</strong></p>
      <p>{log}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Press **N** three times: Notes becomes 3. Then **Ctrl+S** (or **⌘+S**): "Saved draft with 3 notes": the **current** count, not 0.
- The listener is added once per key (effect depends only on `key` and `ctrl`), but it always calls `handlerRef.current`, which is updated every render. Without the ref, the Ctrl+S handler would be the one from the **first** render and would say "0 notes" (a **stale closure**).
- `preventDefault()` stops the browser's own Ctrl+S "Save page" dialog.
- React is adding `useEffectEvent` for exactly this "latest handler" pattern; until then, the ref is the standard solution.

</En>
<Ur>

- **N** teen dafa dabayen: Notes 3 ho jata hai. Phir **Ctrl+S** (ya **⌘+S**): "Saved draft with 3 notes": **maujooda** count, 0 nahi.
- Listener har key ke liye ek dafa jurta hai (effect sirf `key` aur `ctrl` par munhasir hai), magar hamesha `handlerRef.current` call karta hai, jo har render par update hota hai. Ref ke baghair Ctrl+S handler **pehle** render wala hota aur "0 notes" kehta (**stale closure**).
- `preventDefault()` browser ka apna Ctrl+S "Save page" dialog rokta hai.
- React bilkul isi "taaza handler" pattern ke liye `useEffectEvent` jor raha hai; tab tak ref hi mayari hal hai.

</Ur>
</Tr>
</Happened>

<Step title="Hooks share logic, not state">

<Tr>
<En>
This is the most common misunderstanding. If you want two components to see the **same** value, calling the same hook in both is not enough: each call creates separate state. Compare a hook-only counter with a context-backed one.
</En>
<Ur>
Ye sab se aam ghalat fehmi hai. Agar aap chahte hain ke do components **wahi** value dekhein, dono me ek hi hook call karna kafi nahi: har call alag state banati hai. Sirf hook wale counter ka context wale se muqabla karein.
</Ur>
</Tr>

```jsx preview h=230
import { createContext, useContext, useState } from "react";

// Hook only: every caller gets its own count
function useCartCount() {
  const [count, setCount] = useState(0);
  return { count, add: () => setCount((c) => c + 1) };
}

// Hook + context: every caller shares the provider's count
const CartContext = createContext(null);
function CartProvider({ children }) {
  const cart = useCartCount();
  return <CartContext.Provider value={cart}>{children}</CartContext.Provider>;
}
function useSharedCart() {
  const cart = useContext(CartContext);
  if (!cart) throw new Error("useSharedCart must be used inside <CartProvider>");
  return cart;
}

function Header({ useCart }) { const { count } = useCart(); return <p>Header badge: {count}</p>; }
function ProductButton({ useCart }) { const { add } = useCart(); return <button onClick={add}>Add to cart</button>; }

export default function App() {
  return (
    <div>
      <h4>Separate state</h4>
      <Header useCart={useCartCount} /><ProductButton useCart={useCartCount} />
      <h4>Shared through context</h4>
      <CartProvider>
        <Header useCart={useSharedCart} /><ProductButton useCart={useSharedCart} />
      </CartProvider>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- In **Separate state**, clicking "Add to cart" does nothing to the header badge: the button's `useCartCount()` and the header's `useCartCount()` are two different counters.
- In **Shared through context**, the badge goes up with each click: both components read the one `cart` created inside `CartProvider`.
- The `useSharedCart` hook wraps `useContext` and throws a helpful error when used outside the provider, a very common custom-hook pattern.
- (Passing hooks as props here is only to compare both versions side by side; in real code each component calls its hook directly.)

</En>
<Ur>

- **Separate state** me "Add to cart" dabane se header badge par koi asar nahi: button ka `useCartCount()` aur header ka `useCartCount()` do mukhtalif counters hain.
- **Shared through context** me har click ke saath badge barhta hai: dono components `CartProvider` ke andar bana ek `cart` parhte hain.
- `useSharedCart` hook `useContext` ko lapetta hai aur provider ke bahar istemal hone par madadgar error throw karta hai, bohot aam custom-hook pattern.
- (Yahan hooks ko props ki tarah dena sirf dono versions ka saath saath muqabla karne ke liye hai; asli code me har component apna hook seedha call karta hai.)

<Step title="Designing a good hook">

<Tr>
<En>

| Guideline | Example |
| --- | --- |
| Name it after **what** it provides | `useOnlineStatus`, not `useWindowEvents` |
| Return an **array** for 1–2 values meant to be renamed, an **object** for more | `[value, setValue]` vs `{ data, error, status, refetch }` |
| Keep inputs few and explicit | `useDebouncedValue(value, ms)` |
| Always **clean up** timers, listeners, subscriptions and requests | `return () => controller.abort()` |
| Keep returned functions stable when cheap (`useCallback`) | callers can pass them to memoised children |
| Don't hide unrelated behaviour | a fetch hook shouldn't also log analytics |
| Don't wrap a single built-in hook for no reason | `useMyState = useState` adds nothing |
| Test it with `renderHook` | Testing Library |

</En>
<Ur>

| Usool | Misaal |
| --- | --- |
| Naam is par rakhein ke **kya** deta hai | `useOnlineStatus`, `useWindowEvents` nahi |
| Naam badalne wali 1–2 values ke liye **array**, zyada ke liye **object** wapas karein | `[value, setValue]` vs `{ data, error, status, refetch }` |
| Inputs kam aur saaf rakhein | `useDebouncedValue(value, ms)` |
| Timers, listeners, subscriptions aur requests hamesha **saaf** karein | `return () => controller.abort()` |
| Sasta ho to wapas kiye functions mustahkam rakhein (`useCallback`) | call karne wale unhen memoised children ko de sakte hain |
| Ghair mutaliqa bartao na chhupayen | fetch hook analytics log na kare |
| Bila wajah ek akele bane banaye hook ko na lapetein | `useMyState = useState` kuch nahi jorta |
| `renderHook` se test karein | Testing Library |

</Ur>

## Common mistakes

<Compare>
<Bad title="Calling a hook conditionally">

```text
function Search({ enabled }) {
  if (enabled) {
    const debounced = useDebouncedValue(query, 300);   // ✗ hook inside if
  }
}
```

</Bad>
<Good title="Always call it; put the condition inside">

```text
function Search({ enabled }) {
  const debounced = useDebouncedValue(query, 300);     // ✓ every render
  const effectiveQuery = enabled ? debounced : "";
}
```

</Good>
</Compare>

<Compare>
<Bad title="An effect without cleanup inside a hook">

```text
function useInterval(callback, ms) {
  useEffect(() => {
    setInterval(callback, ms);        // never cleared: keeps running after unmount,
  }, [callback, ms]);                 // and a new one starts every time deps change
}
```

</Bad>
<Good title="Clean up every subscription">

```text
function useInterval(callback, ms) {
  const saved = useRef(callback);
  saved.current = callback;
  useEffect(() => {
    const id = setInterval(() => saved.current(), ms);
    return () => clearInterval(id);
  }, [ms]);
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Expecting a hook to share state** between components (use context or a store).
- **Naming a hook without `use`** (`getUser()` calling `useState`): lint can't check it, and readers can't tell.
- **Calling hooks in event handlers or plain functions.**
- **Returning new objects/functions every render** that callers put in effect dependencies, causing effects to re-run endlessly.
- **Reading `window`/`localStorage` during render in server-rendered apps**, causing hydration errors.
- **Over-abstracting**: a hook used once that hides two lines of obvious code.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Components ke darmiyan **hook se state baantne ki umeed** (context ya store lein).
- **Bina `use` ke hook ka naam** (`useState` call karne wala `getUser()`): lint check nahi kar sakta, aur parhne wale nahi pehchan sakte.
- **Event handlers ya aam functions me hooks call karna.**
- **Har render par naye objects/functions wapas karna** jinhen call karne wale effect dependencies me rakhein, jis se effects bila hadd dobara chalen.
- **Server-rendered apps me render ke dauran `window`/`localStorage` parhna**, jis se hydration errors aate hain.
- **Hadd se zyada abstraction**: ek dafa istemal hone wala hook jo wazeh code ki do lines chhupaye.

</Ur>
</Tr>

```jsx preview h=170
import { useEffect, useState } from "react";

function useCountdown(seconds) {
  const [remaining, setRemaining] = useState(seconds);
  const [running, setRunning] = useState(false);

  useEffect(() => {
    if (!running) return;
    const id = setInterval(() => {
      setRemaining((r) => {
        if (r <= 1) { setRunning(false); return 0; }
        return r - 1;
      });
    }, 1000);
    return () => clearInterval(id);
  }, [running]);

  return {
    remaining,
    running,
    start: () => remaining > 0 && setRunning(true),
    reset: () => { setRunning(false); setRemaining(seconds); },
  };
}

function Timer({ seconds, label }) {
  const { remaining, running, start, reset } = useCountdown(seconds);
  return (
    <p>
      {label}: <strong>{remaining}s</strong>{" "}
      <button onClick={start} disabled={running || remaining === 0}>Start</button>
      <button onClick={reset}>Reset</button>
      {remaining === 0 && " Done!"}
    </p>
  );
}

export default function App() {
  return (
    <div>
      <Timer seconds={5} label="Tea" />
      <Timer seconds={10} label="Eggs" />
    </div>
  );
}
```

```jsx preview h=120
import { useEffect, useState } from "react";

function useOnlineStatus() {
  const [online, setOnline] = useState(() => navigator.onLine);
  useEffect(() => {
    const on = () => setOnline(true);
    const off = () => setOnline(false);
    window.addEventListener("online", on);
    window.addEventListener("offline", off);
    return () => {
      window.removeEventListener("online", on);
      window.removeEventListener("offline", off);

}
```

<DeepDive title="More about custom hooks">

**`useSyncExternalStore`.** The correct primitive for subscribing to external stores (browser APIs, Zustand, Redux): `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)`. It avoids tearing in concurrent rendering and supports SSR.

**`useEffectEvent`.** A newer React API for the "latest handler" pattern: functions declared with it can read fresh props/state inside effects without being dependencies.

**Composing hooks.** Hooks can call other custom hooks: `useProductSearch` might use `useDebouncedValue` and `useFetch`. Keep each layer small.

**Testing.** `renderHook(() => useCountdown(5))` from Testing Library runs a hook in a test component; wrap updates in `act`, and use fake timers for time-based hooks.

**TypeScript.** Type inputs and returns explicitly for public hooks: `function useLocalStorage<T>(key: string, initial: T): [T, (v: T | ((p: T) => T)) => void]`. Generics let callers keep precise types.

**Return stability.** Returning `{ data, refetch }` creates a new object each render. If callers use it in effect dependencies, return stable pieces or wrap with `useMemo`.

**Server components.** Hooks only run in client components (`"use client"` in Next.js). Logic for server components is plain async functions, not hooks.

</DeepDive>

<DeepDive title="Real world: twelve copies of the same bug">

A dashboard had twelve widgets (sales, orders, signups, stock levels…), each with its own copy-pasted data-loading code: `useState` for data, loading and error, plus a `useEffect` calling `fetch`. None of them aborted requests or checked `res.ok`.

Two bugs kept appearing in support tickets. Switching the date range quickly showed numbers from the **previous** range (stale responses), and when the API returned a 500, widgets showed "undefined" instead of an error.

A developer replaced all twelve copies with one `useDashboardQuery(endpoint, range)` hook built like `useFetch` in this lesson: one `status` state, `res.ok` checks, `AbortController` cleanup, and a shared error component. Fixing both bugs took one afternoon, and the fix applied to every widget at once. Later the team swapped the hook's insides for TanStack Query's `useQuery` (adding caching and background refresh) without touching any of the twelve widgets, because they only depended on the hook's simple `{ status, data, error }` interface.

</DeepDive>

<DeepDive title="Security lens">

- **Hooks run in the browser**: don't put secrets (API keys) into hook code or the URLs they fetch; call your own backend.
- **`useLocalStorage` data is user-editable and readable by any script on the page**: never store tokens or personal data there; validate what you read back.
- **Validate fetched data** inside data hooks (zod) before returning it, so every component gets trusted shapes.
- **Clean up subscriptions** (WebSockets, intervals): forgotten ones keep sending requests with the user's credentials after they navigate away or log out.
- **Clear user-specific hook caches on logout** (TanStack Query's `queryClient.clear()`), especially on shared devices.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a custom hook and why would you write one?">
A custom hook is a JavaScript function whose name starts with use and which calls other hooks. It extracts reusable stateful logic, such as subscriptions, timers or data fetching, from components so the logic can be shared, tested and maintained in one place while components stay focused on rendering.
</QA>

<QA q="Do two components using the same custom hook share state?">
No. Each call to a hook creates independent state tied to the component that called it. To share state, lift it to a common parent, provide it through context, or use an external store.
</QA>

<QA q="What are the rules of hooks?">
Call hooks only at the top level of function components or custom hooks, never inside conditions, loops, nested functions or after early returns, and only from React functions. React relies on a consistent call order between renders to associate hooks with their state.
</QA>

<QA q="How do you avoid stale closures in a hook that adds an event listener?">
Store the latest callback in a ref updated on every render and have the listener call ref.current, so the listener can be registered once while always using the newest props and state. React's useEffectEvent addresses the same problem.
</QA>

<QA q="How would you design a data-fetching hook?">
Accept the URL or key as input, keep a single state object with status, data and error, run the request in an effect that depends on the input, check response.ok, ignore or abort stale requests with an AbortController in the cleanup, and return a small stable interface. In production, libraries like TanStack Query provide caching, retries and deduplication.
</QA>

</DeepDive>

  <Term name="Custom hook">A function starting with use that composes other hooks into reusable logic.</Term>
  <Term name="Rules of hooks">Constraints requiring hooks to be called at the top level of React functions.</Term>
  <Term name="Stateful logic">Code that stores and updates values across renders.</Term>
  <Term name="Lazy initial state">Passing a function to useState so the initial value is computed once.</Term>
  <Term name="Effect cleanup">A function returned from an effect that undoes its work.</Term>
  <Term name="Debounced value">A value that updates only after changes stop for a delay.</Term>
  <Term name="Stale closure">A function capturing outdated values from a previous render.</Term>
  <Term name="Latest ref pattern">Keeping the newest callback in a ref to avoid stale closures.</Term>
  <Term name="useSyncExternalStore">A hook for subscribing to external data sources safely.</Term>
  <Term name="useEffectEvent">An API for reading the latest values inside effects without adding dependencies.</Term>
  <Term name="renderHook">A testing utility that renders a hook in isolation.</Term>
</Terms>

</DeepDive>
