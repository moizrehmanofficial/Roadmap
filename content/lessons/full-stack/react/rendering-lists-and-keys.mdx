<BigIdea>
<Tr>
<En>
React doesn't have a special "loop" in JSX. You use plain JavaScript: **`array.map()`** turns each item into an element, and React renders the resulting array. The catch is that lists **change**: items are added, removed, reordered and filtered. To update the screen efficiently and correctly, React needs to know **which element is which** between renders. That's what the **`key`** prop is for: a stable, unique id per item (`key={product.id}`). With good keys, React moves, keeps or removes exactly the right elements, together with their state (an input's text, a checkbox, an open menu). With bad keys, especially the **array index**, React can attach the wrong state to the wrong item, which is a real and confusing bug. The rest is ordinary JavaScript: `filter` and `toSorted` to derive what to show (never mutating state), grouping into sections, showing an empty state, and for very long lists, paginating or virtualising.
</En>
<Ur>
React ke JSX me koi khaas "loop" nahi. Aap saada JavaScript istemal karte hain: **`array.map()`** har item ko element me badalta hai, aur React nikli hui array render karta hai. Mushkil ye hai ke lists **badalti** hain: items jurte, hat'te, tarteeb badalte aur filter hote hain. Screen ko tez aur sahi update karne ke liye React ko renders ke darmiyan jaanna hota hai ke **kaun sa element kaun sa hai**. **`key`** prop isi liye hai: har item ki mustahkam, munfarid id (`key={product.id}`). Achhi keys ke saath React bilkul sahi elements ko, un ki state samet (input ka text, checkbox, khula menu), khiskata, rakhta ya hatata hai. Buri keys ke saath, khaas taur par **array index**, React ghalat state ghalat item se jor sakta hai, jo asli aur ulajhane wala bug hai. Baqi aam JavaScript hai: dikhane wali cheez nikalne ke liye `filter` aur `toSorted` (state ko kabhi badle baghair), hisson me jama karna, khaali halat dikhana, aur bohot lambi lists ke liye pagination ya virtualisation.
</Ur>
</Tr>

<Why>
<Tr>
<En>

- **Lists are everywhere**: tables, feeds, carts, menus, search results, chat.
- **Wrong keys cause real bugs**: text typed into one row jumping to another, wrong item deleted, animations on the wrong element.
- **Correct keys are faster**: React reuses existing DOM nodes instead of rebuilding them.
- **Interview favourite**: "why shouldn't you use the index as a key?"

</En>
<Ur>

- **Lists har jagah hain**: tables, feeds, carts, menus, search ke nataij, chat.
- **Ghalat keys asli bugs banati hain**: ek row me likha text doosri me koodna, ghalat item mit jana, ghalat element par animation.
- **Sahi keys tez hain**: React maujooda DOM nodes dobara banane ke bajaye dobara istemal karta hai.
- **Interview ka pasandida**: "index ko key kyun nahi banana chahiye?"

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Key choice |
| --- | --- |
| Data from a database / API | its id (`order.id`, `user.uuid`) |
| Items created in the browser | an id generated when created (`crypto.randomUUID()`) |
| A static list that never changes order and has no state | index is acceptable |
| Items with a natural unique field | that field (`country.code`, `file.path`) |
| Two lists merged from different sources | prefix to avoid collisions (`"user-" + id`) |
| Never | `Math.random()` or `crypto.randomUUID()` **inside** render |

</En>
<Ur>

| Soorat-e-haal | Key ka intikhab |
| --- | --- |
| Database / API ka data | us ki id (`order.id`, `user.uuid`) |
| Browser me bane items | bante waqt bani id (`crypto.randomUUID()`) |
| Jamid list jis ki tarteeb kabhi na badle aur state na ho | index chal jata hai |
| Qudrati munfarid field wale items | wo field (`country.code`, `file.path`) |
| Mukhtalif zariyon se mili do lists | takrao se bachne ke liye prefix (`"user-" + id`) |
| Kabhi nahi | render ke **andar** `Math.random()` ya `crypto.randomUUID()` |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Keep the data as an array in props or state.
2. Derive what to show (`filter`, `toSorted`, `slice`) without changing the original.
3. `map` each item to JSX and put `key={item.id}` on the **outermost** element returned.
4. Handle the empty case.

</En>
<Ur>

1. Data ko props ya state me array ki shakal me rakhein.
2. Dikhane wali cheez nikalein (`filter`, `toSorted`, `slice`) asal ko badle baghair.
3. Har item ko JSX me `map` karein aur wapas kiye **sab se bahar** ke element par `key={item.id}` lagayen.
4. Khaali surat sambhalein.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of a **coat check** at a theatre.

- Every coat gets a **numbered ticket** that belongs to that coat for the whole evening (a key). When people leave in any order, the attendant hands back the right coat by ticket number.
- Now imagine the attendant labels coats by **hook position** instead: "the coat on hook 1". When someone at hook 1 leaves early and everyone shifts left, the person who had hook 2 now gets... the coat on hook 1. That's using the **array index** as a key.
- A ticket number written fresh every time you look at the coat (a random key on every render) is useless: nothing ever matches, so every coat is treated as new.

</En>
<Ur>

Theatre ke **coat check** ka sochein.

- Har coat ko **number wala ticket** milta hai jo poori shaam usi coat ka hota hai (key). Jab log kisi bhi tarteeb me jate hain, attendant ticket number se sahi coat wapas deta hai.
- Ab sochein attendant coats ko **khoonti ki jagah** se pehchanta hai: "khoonti 1 wala coat". Jab khoonti 1 wala jaldi chala jaye aur sab baayen khisak jayen, to khoonti 2 wale ko milta hai... khoonti 1 wala coat. Ye **array index** ko key banana hai.
- Har dafa coat dekhte waqt naya likha ticket number (har render par random key) bekaar hai: kuch kabhi nahi milta, isliye har coat naya samjha jata hai.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **`map`** | Array method turning each item into something else | `items.map(i => <li/>)` |
| **Key** | A stable identity for an element among its siblings | `key={item.id}` |
| **Siblings** | Elements with the same parent | the `<li>`s in one `<ul>` |
| **Reconciliation** | React comparing the new tree with the old one | after every render |
| **Index key** | Using the array position as key | `key={i}` |
| **Stable id** | An id that stays the same for the item's lifetime | database id |
| **Fragment** | Groups elements without adding a DOM node | `<Fragment key>` |
| **Derived list** | A list computed from state, not stored separately | filtered/sorted result |
| **`toSorted`** | Sort that returns a new array | ES2023 |
| **Empty state** | What to show when there are no items | "No orders yet" |

## Learn it step by step

<Walkthrough>

<Step title="From an array to elements with map">

<Tr>
<En>
JSX can render an **array of elements**. `map` builds that array from your data. Put the `key` on the element you return.
</En>
<Ur>
JSX **elements ki array** render kar sakta hai. `map` aap ke data se wo array banata hai. `key` us element par lagayen jo aap wapas karte hain.
</Ur>
</Tr>

```jsx preview h=170
const products = [
  { id: "p1", name: "Mug", price: 12 },
  { id: "p2", name: "Desk Lamp", price: 30 },
  { id: "p3", name: "Notebook", price: 6.5 },
];

export default function App() {
  const items = products.map((p) => (
    <li key={p.id}>
      {p.name}: ${p.price.toFixed(2)}
    </li>
  ));
  return (
    <div>
      <ul>{items}</ul>
      <p>{products.length} products</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Three list items appear: "Mug: $12.00", "Desk Lamp: $30.00", "Notebook: $6.50".
- `items` is a plain array of JSX elements, and `{items}` renders them in order. Usually you write the `map` inline inside the JSX; storing it in a variable just makes the idea visible.
- The `key` isn't shown on the page and isn't passed to your component as a prop. It's information **for React**.
- Without keys, React prints a warning in development ("Each child in a list should have a unique key prop") and falls back to using the index, with the problems shown next.

</En>
<Ur>

- Teen list items nazar aate hain: "Mug: $12.00", "Desk Lamp: $30.00", "Notebook: $6.50".
- `items` JSX elements ki saadi array hai, aur `{items}` unhen tarteeb se render karta hai. Aam taur par aap `map` JSX ke andar hi likhte hain; variable me rakhna bas khayal ko wazeh karta hai.
- `key` page par nazar nahi aati aur aap ke component ko prop ki tarah nahi milti. Ye **React ke liye** maloomat hai.
- Keys ke baghair React development me warning print karta hai ("Each child in a list should have a unique key prop") aur index istemal karne par aa jata hai, un maslon ke saath jo aage dikhaye gaye hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The index-key bug you can see">

<Tr>
<En>
Each row below has its own input (with its own state inside the DOM). Type a note into **every** row of both lists, then click **Add to top** on both. Watch where your notes go.
</En>
<Ur>
Neeche har row ka apna input hai (DOM ke andar apni state ke saath). Dono lists ki **har** row me note likhein, phir dono par **Add to top** dabayen. Dekhein aap ke notes kahan jate hain.
</Ur>
</Tr>

```jsx preview h=330
import { useState } from "react";

function TaskList({ title, useIndexKey }) {
  const [tasks, setTasks] = useState([
    { id: 1, text: "Pack order A-1001" },
    { id: 2, text: "Email Sara" },
  ]);
  const [nextId, setNextId] = useState(3);

  function addToTop() {
    setTasks([{ id: nextId, text: "New urgent task" }, ...tasks]);
    setNextId(nextId + 1);
  }

  return (
    <div style={{ display: "inline-block", verticalAlign: "top", width: 260, marginRight: 16 }}>
      <h4>{title}</h4>
      <button onClick={addToTop}>Add to top</button>
      <ul>
        {tasks.map((task, index) => (
          <li key={useIndexKey ? index : task.id}>
            {task.text} <input placeholder="note" size={10} />
          </li>
        ))}
      </ul>
    </div>
  );
}

export default function App() {
  return (
    <div>
      <TaskList title="key={index}" useIndexKey />
      <TaskList title="key={task.id}" />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

Type "fragile" next to "Pack order A-1001" and "urgent" next to "Email Sara" in **both** lists, then add to top:

- **key=index** list: the new task appears at the top, but **"fragile" is now next to "New urgent task"** and "urgent" next to "Pack order A-1001". The notes stayed at **positions** 0 and 1, and the last row has an empty input. Wrong data on the wrong row.
- **key=id** list: the new task gets a fresh, empty input, and each note stays with **its** task.

Why: with index keys, React sees "key 0 still exists, key 1 still exists, key 2 is new". So it keeps the first two `<li>` elements (with their inputs) and just changes their text, then adds a new `<li>` at the end. With id keys it sees "id 3 is new, ids 1 and 2 moved", inserts a new element at the top and moves the existing ones.

The same bug affects checkboxes, focus, animations, and **component state** inside each row. Imagine a "Delete" confirmation open on the wrong order.

</En>
<Ur>

**Dono** lists me "Pack order A-1001" ke saath "fragile" aur "Email Sara" ke saath "urgent" likhein, phir add to top karein:

- **key=index** list: naya task upar aata hai, magar **"fragile" ab "New urgent task" ke saath hai** aur "urgent" "Pack order A-1001" ke saath. Notes **jagahon** 0 aur 1 par rahe, aur aakhri row ka input khaali hai. Ghalat row par ghalat data.
- **key=id** list: naye task ko naya, khaali input milta hai, aur har note **apne** task ke saath rehta hai.

Wajah: index keys ke saath React dekhta hai "key 0 ab bhi hai, key 1 ab bhi hai, key 2 nayi hai". Isliye wo pehle do `<li>` elements (un ke inputs samet) rakhta hai aur bas un ka text badalta hai, phir aakhir me naya `<li>` jorta hai. Id keys ke saath wo dekhta hai "id 3 nayi hai, ids 1 aur 2 khiski", upar naya element daalta hai aur maujooda ko khiskata hai.

Yahi bug checkboxes, focus, animations, aur har row ke andar ki **component state** ko bhi lagta hai. Sochein "Delete" ki tasdeeq ghalat order par khuli ho.

</Ur>
</Tr>
</Happened>

<Step title="Where the key goes, and Fragments">

<Tr>
<En>
The key belongs on the **outermost** element returned from `map`, not on something inside it, and not inside the child component. If each item needs several sibling elements, wrap them in a `Fragment` with the key (the short `<>…</>` syntax can't take a key).
</En>
<Ur>
Key `map` se wapas kiye **sab se bahar** ke element par lagti hai, us ke andar kisi cheez par nahi, aur child component ke andar nahi. Agar har item ko kai bhai elements chahiyen, unhen key wale `Fragment` me lapetein (chhota `<>…</>` syntax key nahi le sakta).
</Ur>
</Tr>

```jsx preview h=220
import { Fragment } from "react";

const specs = [
  { id: "cap", label: "Capacity", value: "350 ml" },
  { id: "mat", label: "Material", value: "Ceramic" },
  { id: "dish", label: "Dishwasher safe", value: "Yes" },
];

function SpecRow({ label, value }) {
  return <li>{label}: <strong>{value}</strong></li>;
}

export default function App() {
  return (
    <div>
      <dl>
        {specs.map((s) => (
          <Fragment key={s.id}>
            <dt>{s.label}</dt>
            <dd>{s.value}</dd>
          </Fragment>
        ))}
      </dl>
      <ul>
        {specs.map((s) => (
          <SpecRow key={s.id} label={s.label} value={s.value} />
        ))}
      </ul>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- The `<dl>` gets a `<dt>`/`<dd>` pair per spec, with no extra wrapper element (valid HTML for definition lists).
- `<SpecRow key={s.id} …/>`: the key is on the component **where it's used in the list**, not on the `<li>` inside `SpecRow`. `SpecRow` doesn't receive `key` as a prop; pass the id separately (`id={s.id}`) if it needs it.
- Keys only need to be unique **among siblings**: two different lists can both contain `key="cap"`.

</En>
<Ur>

- `<dl>` ko har spec ka `<dt>`/`<dd>` jora milta hai, bina kisi izafi wrapper element ke (definition lists ke liye jaiz HTML).
- `<SpecRow key={s.id} …/>`: key component par **list me jahan istemal hua** wahan hai, `SpecRow` ke andar ke `<li>` par nahi. `SpecRow` ko `key` prop ki tarah nahi milti; zaroorat ho to id alag se dein (`id={s.id}`).
- Keys ko sirf **bhaiyon me** munfarid hona chahiye: do mukhtalif lists dono me `key="cap"` ho sakti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Filtering and sorting without mutating">

<Tr>
<En>
Keep the full list in state (or props) and **derive** what to show on every render. Use `filter` and `toSorted` (which return new arrays). Never call `.sort()` on state: it sorts the original in place.
</En>
<Ur>
Poori list state (ya props) me rakhein aur har render par dikhane wali cheez **nikalein**. `filter` aur `toSorted` (jo nayi arrays wapas karte hain) lein. State par kabhi `.sort()` call na karein: ye asal ko wahin sort kar deta hai.
</Ur>
</Tr>

```jsx preview h=300
import { useState } from "react";

const products = [
  { id: 1, name: "Mug", price: 12, inStock: true },
  { id: 2, name: "Desk Lamp", price: 30, inStock: false },
  { id: 3, name: "Notebook", price: 6.5, inStock: true },
  { id: 4, name: "Floor Lamp", price: 85, inStock: true },
];

export default function App() {
  const [onlyInStock, setOnlyInStock] = useState(false);
  const [sort, setSort] = useState("name");

  const shown = products
    .filter((p) => !onlyInStock || p.inStock)
    .toSorted((a, b) => (sort === "price" ? a.price - b.price : a.name.localeCompare(b.name)));

  return (
    <div>
      <label><input type="checkbox" checked={onlyInStock} onChange={(e) => setOnlyInStock(e.target.checked)} /> In stock only</label>
      {" "}
      <select value={sort} onChange={(e) => setSort(e.target.value)}>
        <option value="name">Sort by name</option>
        <option value="price">Sort by price</option>
      </select>
      <ol>
        {shown.map((p) => (
          <li key={p.id} style={{ color: p.inStock ? "inherit" : "#94a3b8" }}>
            {p.name}: ${p.price}{p.inStock ? "" : " (sold out)"}
          </li>
        ))}
      </ol>
      <small>Original order still: {products.map((p) => p.name).join(", ")}</small>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- By default: Desk Lamp (sold out), Floor Lamp, Mug, Notebook (alphabetical). "Sort by price" gives Notebook, Mug, Desk Lamp, Floor Lamp. Ticking "In stock only" removes Desk Lamp.
- The footer proves the original array never changed: "Mug, Desk Lamp, Notebook, Floor Lamp".
- Because keys are ids, React **moves** the existing `<li>`s when the order changes instead of rewriting their contents.
- `shown` isn't stored in state. It's recalculated each render from `products`, `onlyInStock` and `sort`, so it can never get out of sync. (For very expensive calculations, wrap it in `useMemo`.)
- `localeCompare` sorts text correctly for people (case and accents); `a.price - b.price` sorts numbers.

</En>
<Ur>

- Default me: Desk Lamp (sold out), Floor Lamp, Mug, Notebook (huroof-e-tahaji se). "Sort by price" Notebook, Mug, Desk Lamp, Floor Lamp deta hai. "In stock only" tick karne se Desk Lamp hat jata hai.
- Footer sabit karta hai ke asal array kabhi nahi badli: "Mug, Desk Lamp, Notebook, Floor Lamp".
- Chunke keys ids hain, tarteeb badalne par React maujooda `<li>` ko un ka maal dobara likhne ke bajaye **khiskata** hai.
- `shown` state me mehfooz nahi. Ye har render par `products`, `onlyInStock` aur `sort` se dobara nikalta hai, isliye kabhi be-mel nahi ho sakta. (Bohot mehnge hisaab ke liye ise `useMemo` me lapetein.)
- `localeCompare` text ko logon ke liye sahi sort karta hai (case aur accents); `a.price - b.price` numbers sort karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Adding, removing and updating items in state">

<Tr>
<En>
Lists in state follow the **immutable** update rules from the useState lesson: create a new array every time. Here's the full set of everyday operations on a shopping list.
</En>
<Ur>
State me lists useState lesson ke **immutable** update ke qawaid maanti hain: har dafa nayi array banayen. Ye shopping list par rozmarra ke tamam amal hain.
</Ur>
</Tr>

```jsx preview h=300
import { useState } from "react";

export default function App() {
  const [items, setItems] = useState([
    { id: "a1", name: "Coffee beans", done: false },
    { id: "a2", name: "Oat milk", done: true },
  ]);
  const [text, setText] = useState("");

  function add() {
    if (!text.trim()) return;
    setItems([...items, { id: crypto.randomUUID(), name: text.trim(), done: false }]);
    setText("");
  }
  const toggle = (id) => setItems(items.map((i) => (i.id === id ? { ...i, done: !i.done } : i)));
  const remove = (id) => setItems(items.filter((i) => i.id !== id));
  const clearDone = () => setItems(items.filter((i) => !i.done));

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} placeholder="Add an item" />
      <button onClick={add}>Add</button>
      <ul>
        {items.map((i) => (
          <li key={i.id}>
            <label style={{ textDecoration: i.done ? "line-through" : "none" }}>
              <input type="checkbox" checked={i.done} onChange={() => toggle(i.id)} /> {i.name}
            </label>{" "}
            <button onClick={() => remove(i.id)} aria-label={"Remove " + i.name}>✕</button>
          </li>
        ))}
      </ul>
      <button onClick={clearDone}>Clear completed</button> <small>{items.filter((i) => i.done).length} done</small>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **Add**: `[...items, newItem]` (or `[newItem, ...items]` for the top). The id is created **once**, when the item is created, with `crypto.randomUUID()`.
- **Update one**: `map` returning a changed copy for the matching id and the same object for the rest.
- **Remove**: `filter` out the id. **Clear completed**: `filter` by a condition.
- Try adding "Bread", ticking it, then **Clear completed**: both done items disappear and "0 done" shows.
- Never use `push`, `splice` or assignment on state arrays: React compares references, so mutating the same array may not re-render at all.

</En>
<Ur>

- **Add**: `[...items, newItem]` (ya upar ke liye `[newItem, ...items]`). Id item bante waqt **ek dafa** `crypto.randomUUID()` se banti hai.
- **Ek update**: `map` jo milti id ke liye badli copy aur baqi ke liye wahi object wapas kare.
- **Hatana**: id `filter` se nikalein. **Clear completed**: shart se `filter`.
- "Bread" jor kar, tick kar ke, phir **Clear completed** dabayen: dono mukammal items ghayab ho jate hain aur "0 done" dikhta hai.
- State arrays par kabhi `push`, `splice` ya assignment na karein: React references ka muqabla karta hai, isliye wahi array badalna shayad dobara render hi na kare.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Empty states and grouped lists">

<Tr>
<En>
A list can be empty; show something helpful instead of a blank space. Lists also often need **sections** (orders by status, contacts by letter). Group the data first, then map over groups and items, each with their own keys.
</En>
<Ur>
List khaali ho sakti hai; khaali jagah ke bajaye kuch madadgar dikhayen. Lists ko aksar **hisse** bhi chahiye hote hain (status ke hisaab se orders, harf ke hisaab se contacts). Pehle data group karein, phir groups aur items par map karein, har ek ki apni keys ke saath.
</Ur>
</Tr>

```jsx preview h=300
import { useState } from "react";

const allOrders = [
  { id: "A-1", customer: "Sara", status: "paid" },
  { id: "A-2", customer: "Alex", status: "pending" },
  { id: "A-3", customer: "Emma", status: "paid" },
  { id: "A-4", customer: "Liam", status: "shipped" },
];

export default function App() {
  const [orders, setOrders] = useState(allOrders);

  if (orders.length === 0) {
    return (
      <div>
        <p>No orders yet. When customers buy something, it shows up here.</p>
        <button onClick={() => setOrders(allOrders)}>Load sample orders</button>
      </div>
    );
  }

  const groups = Object.groupBy(orders, (o) => o.status);

  return (
    <div>
      {Object.entries(groups).map(([status, list]) => (
        <section key={status}>
          <h4 style={{ margin: "8px 0 2px", textTransform: "capitalize" }}>{status} ({list.length})</h4>
          <ul style={{ margin: 0 }}>
            {list.map((o) => <li key={o.id}>{o.id} · {o.customer}</li>)}
          </ul>
        </section>
      ))}
      <button onClick={() => setOrders([])}>Clear all</button>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Three sections appear: **Paid (2)** with A-1 and A-3, **Pending (1)** with A-2, **Shipped (1)** with A-4. Sections use the status as key; rows use the order id.
- **Clear all** shows the empty state with a helpful sentence and an action, much better than a blank area.
- `Object.groupBy(items, fn)` (ES2024) builds `{ paid: [...], pending: [...], shipped: [...] }`. In older environments, use `reduce`.
- Section order follows first appearance; to force an order, map over a fixed array like `["pending", "paid", "shipped"]` and look up each group.

</En>
<Ur>

- Teen hisse nazar aate hain: **Paid (2)** A-1 aur A-3 ke saath, **Pending (1)** A-2 ke saath, **Shipped (1)** A-4 ke saath. Hisse status ko key banate hain; rows order id ko.
- **Clear all** madadgar jumle aur ek amal ke saath khaali halat dikhata hai, khaali jagah se kahin behtar.

<Step title="Using a key to reset a component">

<Tr>
<En>
Keys aren't only for lists. When a component's key **changes**, React throws away the old instance (and its state) and creates a fresh one. That's the cleanest way to reset a form when you switch to a different item.
</En>
<Ur>
Keys sirf lists ke liye nahi. Jab component ki key **badalti** hai, React purana instance (aur us ki state) phenk kar naya banata hai. Doosre item par jane par form reset karne ka ye sab se saaf tareeqa hai.
</Ur>
</Tr>

```jsx preview h=230
import { useState } from "react";

function NoteEditor({ contact }) {
  const [note, setNote] = useState("");
  return (
    <div>
      <p>Private note about <strong>{contact}</strong>:</p>
      <textarea value={note} onChange={(e) => setNote(e.target.value)} rows={2} cols={30} />
    </div>
  );
}

export default function App() {
  const [contact, setContact] = useState("Sara");
  return (
    <div>
      {["Sara", "Alex", "Emma"].map((name) => (
        <button key={name} onClick={() => setContact(name)} disabled={name === contact}>{name}</button>
      ))}
      <h4>Without key</h4>
      <NoteEditor contact={contact} />
      <h4>With key={"{contact}"}</h4>
      <NoteEditor key={contact} contact={contact} />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Type "VIP customer" in **both** text areas while Sara is selected, then click **Alex**.

- **With key**: the text area is empty. The key changed from "Sara" to "Alex", so React created a brand-new `NoteEditor`.
- This replaces awkward `useEffect(() => setNote(""), [contact])` code. Use it for profile pages, chat threads, editors: anywhere the "same" component shows a different entity.

</En>
<Ur>

- Sara chuna hua ho tab **dono** text areas me "VIP customer" likhein, phir **Alex** dabayen.
- **Bina key**: note ab bhi "VIP customer" kehta hai, ab bazahir Alex ke baare me. React ne wahi `NoteEditor` instance rakha, isliye us ki state bachi rahi.

| **`content-visibility: auto`** | CSS lets the browser skip off-screen rendering work | long static lists |

## Common mistakes

<Compare>
<Bad title="Random keys generated during render">

```text
{items.map((item) => <Row key={Math.random()} item={item} />)}
// every render gets new keys: every row is destroyed and recreated,
// inputs lose focus and typed text, and it's slow
```

</Bad>
<Good title="Ids that live with the data">

```text
// when creating:  { id: crypto.randomUUID(), name }
{items.map((item) => <Row key={item.id} item={item} />)}
```

</Good>
</Compare>

<Compare>
<Bad title="Sorting state in place">

```text
const sorted = products.sort((a, b) => a.price - b.price);   // mutates props/state!
```

</Bad>
<Good title="Sort a copy">

```text
const sorted = products.toSorted((a, b) => a.price - b.price);
// or: [...products].sort(...)
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Index as key** in lists that can be reordered, filtered, or have inputs/state per row.
- **Key on the wrong element** (inside the child component instead of where it's used in the `map`).
- **Duplicate keys** (two items with the same id), which causes items to disappear or duplicate. Fix the data.
- **Forgetting `return`** in a `map` callback with braces (`map((x) => { <li/> })` returns `undefined`).
- **Storing filtered/sorted copies in state** alongside the original; derive them instead.
- **`{count && <List/>}`** when `count` can be `0`: it renders a literal `0`. Use `count > 0 &&`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Aisi lists me **index ko key** banana jin ki tarteeb badal sakti ho, jo filter hon, ya jin ki har row me inputs/state ho.
- **Ghalat element par key** (`map` me jahan istemal hua wahan ke bajaye child component ke andar).
- **Dohri keys** (ek hi id wale do items), jo items ko ghayab ya dohra karti hain. Data theek karein.
- Braces wale `map` callback me **`return` bhoolna** (`map((x) => { <li/> })` `undefined` wapas karta hai).
- Asal ke saath **filtered/sorted copies state me rakhna**; un ke bajaye nikalein.
- Jab `count` `0` ho sakta ho tab **`{count && <List/>}`**: ye seedha `0` render karta hai. `count > 0 &&` lein.

</Ur>
</Tr>

  const [songs, setSongs] = useState([
    { id: "s1", title: "Morning Coffee" },
    { id: "s2", title: "City Lights" },
    { id: "s3", title: "Long Drive" },

    const target = index + delta;
    if (target < 0 || target >= songs.length) return;
    const next = [...songs];
    [next[index], next[target]] = [next[target], next[index]];
    setSongs(next);

  return (

        </li>

## Remember

<Takeaways>
<Tr>
<En>

- Render lists with `array.map((item) => <El key={item.id} … />)`.
- **Keys** give items an identity among siblings; use stable, unique ids from the data.
- **Index keys** break when items are inserted, removed, filtered or reordered and rows have state.
- Never generate keys during render (`Math.random`, `randomUUID` in JSX); create ids when items are created.
- The key goes on the **outermost** element in the `map` (use `<Fragment key>` for groups); it isn't passed as a prop.
- Derive filtered/sorted/grouped views with `filter`, `toSorted`, `Object.groupBy`; never mutate state.
- Always design the **empty state**.
- Change a component's `key` to **reset** its state.
- For huge lists: paginate, filter on the server, or virtualise.

</En>
<Ur>

- Lists `array.map((item) => <El key={item.id} … />)` se render karein.
- **Keys** items ko bhaiyon me pehchan deti hain; data ki mustahkam, munfarid ids lein.

<DeepDive title="More about keys and reconciliation">

**How reconciliation uses keys.** For each list, React compares old and new children by key. Same key and same type → update in place. New key → create. Missing key → remove. Keys let React detect moves instead of seeing "everything changed".

**Type changes reset too.** If an element at the same position changes type (`<input>` → `<textarea>`, or `ComponentA` → `ComponentB`), React also destroys the old subtree and its state.

**Keys must be strings or numbers.** Objects aren't allowed; convert compound identities to strings (`order.id + "-" + line.sku`).

**Keys and animations.** Animation libraries (Framer Motion's `AnimatePresence`) rely on keys to know which element left or entered, so exit animations play on the right item.

**Server data without ids.** If an API returns items without ids, ask for them. As a last resort, derive a stable id from content (a hash of unique fields), never from position.

**`Children.toArray`** assigns keys to children when you need to manipulate them, but explicit keys in your own `map` are clearer.

**Performance.** Correct keys avoid recreating DOM nodes. For re-rendering costs of large lists, combine keys with `memo` on row components (React Performance lesson).

</DeepDive>

<DeepDive title="Real world: the wrong order got refunded">

A support dashboard listed a customer's recent orders, each row with a "Refund" button that opened an inline confirmation form (reason dropdown, amount, notes) kept in the row component's state. Rows used `key={index}`.

A new feature added real-time updates: when a new order arrived, it was inserted at the **top** of the list. One afternoon an agent opened the refund form on order #3 and started typing the reason. A new order arrived, the list shifted down, and the open form, with its typed reason and amount, was now displayed next to a **different** order. The agent clicked "Confirm" and refunded the wrong order.

The fix was one word, `key={order.id}`, plus a test that inserts an item at the top while a row's form is open and asserts the form stays with its original order. The team also added the React ESLint rule that flags array indexes used as keys, and made refund confirmations show the order number in the button text ("Refund #A-1042").

</DeepDive>

<DeepDive title="Security lens">

- **List items are often user-generated** (comments, names, product titles). Render them as text (`{item.name}`), never with `dangerouslySetInnerHTML`.
- **Paginate on the server**: returning 100,000 records to the browser can leak data a user shouldn't see in bulk and lets anyone scrape everything; also enforce per-user filtering in the query.
- **Don't expose internal ids you don't want guessed** as the only protection: sequential ids in keys and URLs are fine only if the server checks that the user may access each item.
- **Bulk actions on selected rows** must send ids the server re-validates for ownership, not trust the list the client shows.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why does React need keys for list items?">
Keys give each element a stable identity among its siblings so that during reconciliation React can match old and new children, updating, moving, inserting or removing the correct elements and preserving their state instead of re-creating everything.
</QA>

<QA q="When is it acceptable to use the array index as a key?">
When the list is static or only appended to, is never reordered, filtered or has items inserted or removed in the middle, and the items have no internal state such as inputs. Otherwise an index key can attach state to the wrong item.
</QA>

<QA q="What happens if you use Math.random as a key?">
Every render produces new keys, so React treats all items as new, unmounting and remounting them each time. This loses state such as focus and input values and hurts performance.
</QA>

<QA q="How can you reset a component's state when a prop changes?">
Give the component a key derived from that prop, such as the selected user's id. When the key changes, React unmounts the old instance and mounts a new one with fresh state.
</QA>

<QA q="How would you render a list of 50,000 rows efficiently?">
Avoid rendering all of them: use server-side pagination or filtering, infinite loading, or list virtualisation that renders only visible rows, while keeping stable keys and memoising row components where useful.
</QA>

</DeepDive>
