<BigIdea>
<Tr>
<En>
**State** is any data that can change while the app runs and should update the screen. Most state is **local**: a dropdown's open flag belongs in that dropdown. Problems start when several distant components need the **same** state: a cart badge in the header, an "Add to cart" button deep in a product grid and a checkout page. You have a ladder of tools, and you should climb only as high as you need. **Lift state up** to the nearest common parent and pass it down as props. When drilling gets painful, **Context** makes a value available to a whole subtree, but every component that reads it re-renders when it changes. For complex update rules, **`useReducer`** centralises them as actions. For app-wide state that changes often, an **external store** like **Zustand** or **Redux Toolkit** lives outside React; components **subscribe with selectors** and re-render only when their slice changes. And two big categories usually don't belong in any of these: **server data** (use TanStack Query, next lesson) and **URL state** (filters, tabs, page numbers: keep them in the URL).
</En>
<Ur>
**State** aisa koi bhi data hai jo app chalte waqt badal sakta hai aur screen ko update karna chahiye. Zyada tar state **local** hoti hai: dropdown ka khula flag usi dropdown ka hai. Masle tab shuru hote hain jab kai door ke components ko **wahi** state chahiye: header me cart badge, product grid me gehra "Add to cart" button aur checkout page. Aap ke paas auzaaron ki seerhi hai, aur aap ko utna hi upar chadhna chahiye jitni zaroorat ho. State ko qareebi mushtarka parent tak **upar le jayen** aur props se neeche dein. Jab drilling takleef deh ho, **Context** value ko poore subtree ke liye dastiyab karta hai, magar use parhne wala har component us ke badalne par dobara render hota hai. Pecheeda update ke qawaid ke liye **`useReducer`** unhen actions ki shakal me ek jagah karta hai. Aksar badalne wali poori app ki state ke liye **Zustand** ya **Redux Toolkit** jaisa **external store** React ke bahar rehta hai; components **selectors ke saath subscribe** karte hain aur sirf apne hisse ke badalne par dobara render hote hain. Aur do bari qismen aam taur par in me se kahin nahi jatin: **server ka data** (TanStack Query lein, agla lesson) aur **URL state** (filters, tabs, page numbers: unhen URL me rakhein).
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

| Tool | What it is | Re-renders | Good for |
| --- | --- | --- | --- |
| `useState` (local) | state inside one component | that component | most UI state |
| Lifting state up | state in a common parent, passed as props | parent + children | siblings sharing data |
| **Context** | value provided to a subtree | **every consumer** when the value changes | theme, current user, locale, rarely-changing values |
| `useReducer` | state + a reducer function handling actions | like `useState` | complex, related updates |
| **Zustand** | tiny external store with hooks | only components whose **selected** slice changed | app-wide client state |
| **Redux Toolkit** | structured external store (slices, actions, devtools) | only components whose selected slice changed | large apps, big teams, strict patterns |
| TanStack Query | cache for **server** data | components using that query | anything loaded from an API |
| URL (`searchParams`) | state in the address bar | page/route | filters, sorting, tabs, pagination |

</En>

<Why>
<Tr>
<En>

- **Shared data must stay consistent**: the cart badge and the checkout page must agree.
- **Performance**: putting everything in one Context can make every keystroke re-render the whole app.
- **Maintainability**: a clear home for each kind of state makes bugs easier to find.
- **Jobs and codebases**: you'll meet Context, Zustand and Redux in real projects and need to read all three.

</En>
<Ur>

- **Mushtarka data yaksan rehna chahiye**: cart badge aur checkout page ko muttafiq hona chahiye.
- **Performance**: sab kuch ek Context me rakhna har key par poori app dobara render kar sakta hai.
- **Dekh bhaal**: har qism ki state ka saaf ghar bugs dhoondhna aasan banata hai.
- **Naukriyan aur codebases**: asli projects me aap Context, Zustand aur Redux se milenge aur teeno parhne honge.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Question | Answer |
| --- | --- |
| Does only one component use it? | keep it local |
| Do a parent and a few children use it? | lift it up |
| Is it read in many places but changes rarely (theme, user, locale)? | Context |
| Does it change often and is read in many places (cart, editor, filters panel)? | Zustand (or Redux Toolkit) |
| Did it come from the server? | TanStack Query / SWR / server components |
| Should a shared link or reload keep it (filters, page, tab)? | the URL |
| Is it a form's in-progress values? | the form (React Hook Form / local state) |

</En>
<Ur>

| Sawal | Jawab |
| --- | --- |
| Kya sirf ek component ise istemal karta hai? | local rakhein |
| Kya parent aur chand children istemal karte hain? | upar le jayen |
| Kya ye bohot jagah parha jata hai magar kam badalta hai (theme, user, locale)? | Context |
| Kya ye aksar badalta aur bohot jagah parha jata hai (cart, editor, filters panel)? | Zustand (ya Redux Toolkit) |
| Kya ye server se aaya? | TanStack Query / SWR / server components |
| Kya share kiya link ya reload ise rakhe (filters, page, tab)? | URL |
| Kya ye form ki adhoori values hain? | form (React Hook Form / local state) |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Start local. Lift state only when another component needs it.
2. Use Context for low-frequency values; split contexts by concern and memoise the value.
3. When updates get complex, move them into a reducer with named actions.
4. For frequently changing shared client state, create a Zustand store and read it with **selectors**.
5. Keep server data in a query cache and shareable UI state in the URL.

</En>
<Ur>

1. Local se shuru karein. State sirf tab upar le jayen jab doosre component ko chahiye.
2. Kam badalne wali values ke liye Context lein; contexts ko maqsad ke hisaab se baantein aur value memoise karein.
3. Jab updates pecheeda ho jayen, unhen naam wale actions ke saath reducer me le jayen.
4. Aksar badalne wali mushtarka client state ke liye Zustand store banayen aur use **selectors** se parhein.
5. Server data query cache me aur share hone layaq UI state URL me rakhein.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of how information is shared in an **office**.

- A note on **your own desk** is local state. Nobody else needs it.
- When two people in a team need it, they put it on the **team's whiteboard** (lifting state up).
- A **company-wide announcement** on every floor's screen (Context) is great for things that rarely change, like the holiday schedule. But every time it changes, **everyone** stops to read it, even people it doesn't concern.
- A **shared spreadsheet** with notifications (an external store) lets each person **subscribe only to the columns they care about**: the warehouse watches stock levels, finance watches totals. A change to stock doesn't interrupt finance.
- Information from **suppliers** (server data) isn't something you invent; you keep a **cached copy** and refresh it (TanStack Query).
- A **bookmark** to "the report filtered to March, page 2" (URL state) lets you send exactly that view to a colleague.

</En>
<Ur>

**Daftar** me maloomat baantne ke tareeqe ka sochein.

- **Apni desk** par note local state hai. Kisi aur ko is ki zaroorat nahi.
- Jab team ke do logon ko chahiye, wo use **team ki whiteboard** par likhte hain (state upar le jana).
- Har manzil ki screen par **company bhar ka elaan** (Context) kam badalne wali cheezon ke liye behtareen hai, jaise chhuttiyon ka schedule. Magar har dafa badalne par **sab** use parhne ke liye rukte hain, wo bhi jin se is ka taaluq nahi.
- Notifications wali **mushtarka spreadsheet** (external store) har shakhs ko **sirf apne mutaliqa columns ko subscribe** karne deti hai: warehouse stock dekhta hai, finance totals. Stock ki tabdeeli finance ko nahi rokti.
- **Suppliers** ki maloomat (server data) aap khud nahi gharte; aap **cache ki hui copy** rakhte hain aur use taaza karte hain (TanStack Query).
- "March tak filter ki hui report, safha 2" ka **bookmark** (URL state) aap ko bilkul wahi nazara saathi ko bhejne deta hai.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Local state** | Owned by one component | `isOpen` |
| **Global / shared state** | Needed by many components | cart, user |
| **Lifting state up** | Moving state to a common parent | sibling filters + list |
| **Provider** | Component that supplies a context value | `<CartProvider>` |
| **Consumer** | Component reading a context | `useContext(CartContext)` |
| **Reducer** | `(state, action) => newState` | `cartReducer` |
| **Action** | Object describing what happened | `{ type: "cart/added", payload }` |
| **Dispatch** | Send an action to the reducer/store | `dispatch(added(item))` |
| **Store** | Object holding state outside React, with subscribe | Zustand, Redux |
| **Selector** | Function picking part of the state | `(s) => s.items.length` |
| **Slice** | A section of a Redux store with its reducers | `cartSlice` |
| **Server state** | Data owned by the backend, cached in the client | products, orders |
| **Derived state** | Computed from other state, not stored | cart total |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Local state** | Ek component ki milkiyat | `isOpen` |

| **Provider** | Context value dene wala component | `<CartProvider>` |

<Step title="Step 1 on the ladder: lifting state up">

<Tr>
<En>
Two siblings, a filter box and a product list, need the same search text. Neither can own it, so it moves to their **parent**, which passes the value down and a setter to the input.
</En>
<Ur>
Do bhai, filter box aur product list, ko wahi search text chahiye. Koi ek is ka malik nahi ho sakta, isliye ye un ke **parent** me jata hai, jo value neeche aur setter input ko deta hai.
</Ur>
</Tr>

```jsx preview h=220
import { useState } from "react";

function FilterBox({ query, onQueryChange }) {
  return <input value={query} onChange={(e) => onQueryChange(e.target.value)} placeholder="Filter products" />;
}

function ProductList({ query }) {
  const products = ["Desk Lamp", "Floor Lamp", "Mug", "Notebook"];
  const shown = products.filter((p) => p.toLowerCase().includes(query.toLowerCase()));
  return <ul>{shown.map((p) => <li key={p}>{p}</li>)}</ul>;
}

export default function App() {
  const [query, setQuery] = useState("");
  return (
    <div>
      <FilterBox query={query} onQueryChange={setQuery} />
      <ProductList query={query} />
      <small>Parent knows the query: "{query}"</small>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Typing "lamp" filters the list to the two lamps, and the parent's footer shows the same text.
- This is the first tool to reach for, and often the only one needed. It's explicit: you can see in the code exactly where `query` comes from.
- It becomes painful when the common parent is many levels above the components that use the value (prop drilling, Props lesson).

</En>
<Ur>

- "lamp" likhne par list do lamps tak filter ho jati hai, aur parent ka footer wahi text dikhata hai.
- Ye pehla auzaar hai jis tak pohanchna chahiye, aur aksar akela zaroori. Ye saaf hai: aap code me bilkul dekh sakte hain ke `query` kahan se aati hai.
- Ye tab takleef deh ho jata hai jab mushtarka parent value istemal karne wale components se bohot darje upar ho (prop drilling, Props lesson).

</Ur>
</Tr>
</Happened>

<Step title="Context: provide once, read anywhere below">

<Tr>
<En>
Context removes drilling: a **Provider** high in the tree supplies a value, and any component below reads it with `useContext`. Wrapping it in a custom hook (Custom Hooks lesson) gives a nice API and a clear error if the provider is missing.
</En>
<Ur>
Context drilling khatam karta hai: darakht me upar **Provider** value deta hai, aur neeche ka koi bhi component use `useContext` se parhta hai. Ise custom hook me lapetna (Custom Hooks lesson) achhi API aur provider na hone par saaf error deta hai.
</Ur>
</Tr>

```jsx preview h=230
import { createContext, useContext, useMemo, useState } from "react";

const ThemeContext = createContext(null);

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState("light");
  const value = useMemo(() => ({ theme, toggle: () => setTheme((t) => (t === "light" ? "dark" : "light")) }), [theme]);
  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used inside <ThemeProvider>");
  return ctx;
}

// Deep inside the tree: no props needed
function ThemeButton() {
  const { theme, toggle } = useTheme();
  return <button onClick={toggle}>Switch to {theme === "light" ? "dark" : "light"}</button>;
}
function Panel() {
  const { theme } = useTheme();
  const dark = theme === "dark";
  return (
    <div style={{ background: dark ? "#0f172a" : "#f8fafc", color: dark ? "#f8fafc" : "#0f172a", padding: 12, borderRadius: 8 }}>
      <p>Current theme: {theme}</p>
      <ThemeButton />
    </div>
  );
}
const Layout = () => <section><h4>Settings</h4><Panel /></section>;

export default function App() {
  return (
    <ThemeProvider>
      <Layout />
    </ThemeProvider>
  );
}
```

<Happened>
<Tr>
<En>

- Clicking the button switches the panel between light and dark. `Layout` never mentions the theme: no drilling.
- The value is wrapped in `useMemo` so it's a **new object only when `theme` changes**. Without it, every render of `ThemeProvider` would create a new object and re-render all consumers even when nothing changed.
- Context is perfect for values that are read widely and change **rarely**: theme, locale, the logged-in user, feature flags, a toast function.

</En>
<Ur>

- Button dabane se panel light aur dark ke darmiyan badalta hai. `Layout` kabhi theme ka zikr nahi karta: drilling nahi.
- Value `useMemo` me lipti hai taa ke ye **sirf `theme` badalne par naya object** ho. Is ke baghair `ThemeProvider` ka har render naya object banata aur kuch na badalne par bhi tamam consumers dobara render karta.
- Context un values ke liye behtareen hai jo bohot jagah parhi jati hain aur **kam** badalti hain: theme, locale, login user, feature flags, toast function.

</Ur>
</Tr>
</Happened>

<Step title="The Context catch: every consumer re-renders">

<Tr>
<En>
When a context value changes, **every** component that reads that context re-renders, even if it only uses a part that didn't change. Each box below counts its own renders. Type in the name field and watch the counters.
</En>
<Ur>
Jab context value badalti hai, wo context parhne wala **har** component dobara render hota hai, chahe wo sirf aisa hissa istemal kare jo nahi badla. Neeche har dabba apne renders ginta hai. Name field me type karein aur counters dekhein.
</Ur>
</Tr>

```jsx preview h=250
import { createContext, memo, useContext, useRef, useState } from "react";

const AppContext = createContext(null);

function useRenderCount() {
  const count = useRef(0);
  count.current += 1;
  return count.current;
}

const NameField = memo(function NameField() {
  const { user, setUser } = useContext(AppContext);
  const renders = useRenderCount();
  return <p><input value={user.name} onChange={(e) => setUser({ ...user, name: e.target.value })} /> renders: {renders}</p>;
});

const CartBadge = memo(function CartBadge() {
  const { cartCount } = useContext(AppContext);   // doesn't use user at all
  const renders = useRenderCount();
  return <p>Cart: {cartCount} items · renders: {renders}</p>;
});

const Footer = memo(function Footer() {
  const renders = useRenderCount();                // doesn't read the context
  return <p>Footer · renders: {renders}</p>;
});

export default function App() {
  const [user, setUser] = useState({ name: "Sara" });
  const [cartCount] = useState(2);
  return (
    <AppContext.Provider value={{ user, setUser, cartCount }}>
      <NameField />
      <CartBadge />
      <Footer />
    </AppContext.Provider>
  );
}
```

<Happened>
<Tr>
<En>

- Type " Lee" (4 characters): **NameField** goes to 5 renders, as expected. **CartBadge also goes to 5**, although the cart never changed: it reads the same context object, which is new on every keystroke. **Footer stays at 1**: it doesn't read the context (and `memo` stops it re-rendering with its parent).
- With a few components this doesn't matter. With a big tree reading one giant "AppContext" that changes on every keystroke, it makes the whole app sluggish.
- Fixes: **split** contexts by concern (`UserContext`, `CartContext`), keep fast-changing values out of context, memoise the value, or use an external store with selectors (next steps).

</En>
<Ur>

- " Lee" (4 huroof) likhein: **NameField** 5 renders tak jata hai, umeed ke mutabiq. **CartBadge bhi 5 tak jata hai**, halanke cart kabhi nahi badla: ye wahi context object parhta hai, jo har key par naya hai. **Footer 1 par rehta hai**: ye context nahi parhta (aur `memo` use parent ke saath dobara render hone se rokta hai).
- Chand components ke saath ye ahem nahi. Har key par badalne wale ek bare "AppContext" ko parhne wale bare darakht ke saath ye poori app ko sust kar deta hai.
- Hal: contexts ko maqsad ke hisaab se **baantein** (`UserContext`, `CartContext`), tezi se badalne wali values context se bahar rakhein, value memoise karein, ya selectors wala external store lein (agle qadam).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="useReducer: complex updates as named actions">

<Tr>
<En>
When state has several fields that change together and many ways to change them, scattering `setState` calls gets messy. A **reducer** puts every rule in one pure function: given the current state and an **action** (what happened), return the new state.
</En>
<Ur>
Jab state ke kai fields ek saath badlen aur unhen badalne ke bohot tareeqe hon, `setState` calls bikherna gandagi banata hai. **Reducer** har qaida ek khalis function me rakhta hai: maujooda state aur **action** (kya hua) diya jaye to nayi state wapas karo.
</Ur>
</Tr>

```jsx preview h=270
import { useReducer } from "react";

function cartReducer(state, action) {
  switch (action.type) {
    case "added": {
      const existing = state.items.find((i) => i.id === action.product.id);
      const items = existing
        ? state.items.map((i) => (i.id === action.product.id ? { ...i, qty: i.qty + 1 } : i))
        : [...state.items, { ...action.product, qty: 1 }];
      return { ...state, items };
    }
    case "removed":
      return { ...state, items: state.items.filter((i) => i.id !== action.id) };
    case "couponApplied":
      return { ...state, discount: action.code === "SAVE10" ? 0.1 : 0 };
    default:
      throw new Error("Unknown action: " + action.type);
  }
}

const products = [{ id: "mug", name: "Mug", price: 12 }, { id: "lamp", name: "Desk Lamp", price: 30 }];

export default function App() {
  const [cart, dispatch] = useReducer(cartReducer, { items: [], discount: 0 });
  const subtotal = cart.items.reduce((s, i) => s + i.price * i.qty, 0);
  const total = subtotal * (1 - cart.discount);

  return (
    <div>
      {products.map((p) => (
        <button key={p.id} onClick={() => dispatch({ type: "added", product: p })}>Add {p.name}</button>
      ))}
      <button onClick={() => dispatch({ type: "couponApplied", code: "SAVE10" })}>Apply SAVE10</button>
      <ul>
        {cart.items.map((i) => (
          <li key={i.id}>{i.name} × {i.qty} <button onClick={() => dispatch({ type: "removed", id: i.id })}>✕</button></li>
        ))}
      </ul>
      <p>Subtotal ${subtotal.toFixed(2)} · Total ${total.toFixed(2)}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Add Mug twice and Desk Lamp once: "Mug × 2", "Desk Lamp × 1", subtotal $54.00. **Apply SAVE10**: total $48.60.
- Components just **describe what happened** (`dispatch({ type: "added", product })`); the reducer decides **how** state changes. All cart rules live in one testable function.
- The reducer is **pure** and **immutable**: it returns new objects and never edits `state`. The `default` case throws, so a typo in an action type fails loudly.
- `useReducer` + Context (provide `cart` and `dispatch`) is a classic "mini-Redux" for medium apps. Splitting them into two contexts means components that only dispatch don't re-render when the cart changes.

</En>
<Ur>

- Mug do dafa aur Desk Lamp ek dafa jorein: "Mug × 2", "Desk Lamp × 1", subtotal $54.00. **Apply SAVE10**: total $48.60.
- Components bas **bayan karte hain ke kya hua** (`dispatch({ type: "added", product })`); reducer tay karta hai ke state **kaise** badle. Cart ke tamam qawaid ek test ho sakne wale function me hain.
- Reducer **khalis** aur **immutable** hai: naye objects wapas karta hai aur `state` kabhi nahi badalta. `default` case throw karta hai, isliye action type ki typo zor se fail hoti hai.
- `useReducer` + Context (`cart` aur `dispatch` provide karna) darmiyani apps ke liye mashhoor "mini-Redux" hai. Inhen do contexts me baantne ka matlab sirf dispatch karne wale components cart badalne par dobara render nahi hote.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="How external stores work: a 20-line store with selectors">

<Tr>
<En>
Zustand and Redux keep state **outside React** in a store with three abilities: `getState`, `setState` and `subscribe`. Components connect with React's `useSyncExternalStore` and a **selector**, and re-render only when **their selected value** changes. Here's the whole idea from scratch. Click both buttons and watch the render counters.
</En>
<Ur>
Zustand aur Redux state ko **React ke bahar** teen salahiyaton wale store me rakhte hain: `getState`, `setState` aur `subscribe`. Components React ke `useSyncExternalStore` aur **selector** se jurte hain, aur sirf tab dobara render hote hain jab **un ki chuni hui value** badle. Ye poora khayal shuru se hai. Dono buttons dabayen aur render counters dekhein.
</Ur>
</Tr>

```jsx preview h=250
import { useRef, useSyncExternalStore } from "react";

// A tiny store: this is essentially what Zustand does
function createStore(initial) {
  let state = initial;
  const listeners = new Set();
  return {
    getState: () => state,
    setState: (partial) => {
      state = { ...state, ...(typeof partial === "function" ? partial(state) : partial) };
      listeners.forEach((l) => l());
    },
    subscribe: (listener) => { listeners.add(listener); return () => listeners.delete(listener); },
  };
}

const store = createStore({ cartCount: 0, userName: "Sara" });

function useStore(selector) {
  return useSyncExternalStore(store.subscribe, () => selector(store.getState()));
}

function useRenders() { const r = useRef(0); r.current += 1; return r.current; }

function CartBadge() {
  const count = useStore((s) => s.cartCount);
  return <p>🛒 {count} · renders: {useRenders()}</p>;
}
function Greeting() {
  const name = useStore((s) => s.userName);
  return <p>Hello, {name} · renders: {useRenders()}</p>;
}

export default function App() {
  return (
    <div>
      <CartBadge />
      <Greeting />
      <button onClick={() => store.setState((s) => ({ cartCount: s.cartCount + 1 }))}>Add to cart</button>{" "}
      <button onClick={() => store.setState({ userName: store.getState().userName === "Sara" ? "Alex" : "Sara" })}>Switch user</button>
    </div>
  );
}
```

<Tr>
<En>

- Click **Add to cart** three times: the badge shows 3 and its renders go to 4, while **Greeting stays at 1**. Click **Switch user**: only Greeting re-renders.
- `useSyncExternalStore(subscribe, getSnapshot)` re-renders a component only when the snapshot (the **selected** value) changes. That's the key advantage over one big Context.
- Notice `App` doesn't hold the state and never re-renders; the store lives outside React, so any component (or plain function) can read and update it without providers.
- Selectors should return **primitive values or stable references**. Returning a new object each time (`(s) => ({ a: s.a })`) would look "changed" on every check.

</En>
<Ur>

- **Add to cart** teen dafa dabayen: badge 3 dikhata hai aur us ke renders 4 tak jate hain, jabke **Greeting 1 par rehta hai**. **Switch user** dabayen: sirf Greeting dobara render hota hai.
- `useSyncExternalStore(subscribe, getSnapshot)` component ko sirf tab dobara render karta hai jab snapshot (**chuni hui** value) badle. Ek bare Context ke muqable me yahi asal faida hai.
- Dekhein `App` state nahi rakhta aur kabhi dobara render nahi hota; store React ke bahar rehta hai, isliye koi bhi component (ya saada function) providers ke baghair use parh aur update kar sakta hai.
- Selectors ko **primitive values ya mustahkam references** wapas karne chahiyen. Har dafa naya object wapas karna (`(s) => ({ a: s.a })`) har check par "badla hua" lagega.

</Ur>

<Step title="Real Redux Toolkit">

<Tr>
<En>
Redux is the older, more structured approach: one store, state changed **only** by dispatching **actions** to **reducers**. **Redux Toolkit** (RTK) is the modern way to write it: `createSlice` generates action creators and reducers, and Immer lets reducers look like they mutate while producing new immutable state.
</En>
<Ur>
Redux purana, zyada muntazam tareeqa hai: ek store, state **sirf** **reducers** ko **actions** dispatch kar ke badalti hai. **Redux Toolkit** (RTK) ise likhne ka jadeed tareeqa hai: `createSlice` action creators aur reducers banata hai, aur Immer reducers ko aisa dikhne deta hai jaise wo badal rahe hon jabke nayi immutable state banti hai.
</Ur>
</Tr>

```bash
cat > redux-cart.mjs <<'EOF'
import { configureStore, createSlice } from "@reduxjs/toolkit";

const cartSlice = createSlice({
  name: "cart",
  initialState: { items: [] },
  reducers: {
    added(state, action) {
      const item = state.items.find((i) => i.id === action.payload.id);
      if (item) item.qty += 1;              // Immer lets you "mutate" a draft safely
      else state.items.push({ ...action.payload, qty: 1 });
    },
    removed(state, action) {
      state.items = state.items.filter((i) => i.id !== action.payload);
    },
  },
});

const { added, removed } = cartSlice.actions;
const store = configureStore({ reducer: { cart: cartSlice.reducer } });

const selectTotal = (state) => state.cart.items.reduce((s, i) => s + i.price * i.qty, 0);

console.log("action object:", added({ id: "mug", name: "Mug", price: 12 }));
const before = store.getState();
store.dispatch(added({ id: "mug", name: "Mug", price: 12 }));
store.dispatch(added({ id: "mug", name: "Mug", price: 12 }));
store.dispatch(added({ id: "lamp", name: "Desk Lamp", price: 30 }));
console.log(store.getState().cart.items);
console.log("total:", selectTotal(store.getState()));
store.dispatch(removed("mug"));
console.log("total after remove:", selectTotal(store.getState()));
console.log("old state untouched:", before.cart.items.length, "items; new object?", before !== store.getState());
EOF
node redux-cart.mjs
```

<Tr>
<En>

- `added(...)` just **creates an action object** `{ type: "cart/added", payload }`. Nothing changes until it's dispatched.
- The reducer wrote `item.qty += 1` and `state.items.push(...)`, yet the old state object still had 0 items: Immer turned those "mutations" into a brand-new immutable state.
- Every change is a named, serialisable action, so **Redux DevTools** can show a timeline of everything that happened and "time-travel" between states, a big help in large apps.
- In React: wrap the app in `<Provider store={store}>`, read with `useSelector((s) => s.cart.items.length)`, and update with `const dispatch = useDispatch(); dispatch(added(product))`. RTK Query adds data fetching and caching to the same store.

</En>
<Ur>

- `added(...)` bas **action object banata** hai `{ type: "cart/added", payload }`. Dispatch hone tak kuch nahi badalta.
- Reducer ne `item.qty += 1` aur `state.items.push(...)` likha, phir bhi purane state object me 0 items the: Immer ne in "tabdeeliyon" ko bilkul nayi immutable state me badal diya.
- Har tabdeeli naam wala, serialise hone layaq action hai, isliye **Redux DevTools** har hone wali cheez ki timeline dikha sakta hai aur states ke darmiyan "time-travel" kar sakta hai, bari apps me bari madad.

</Ur>

<Step title="What doesn't belong in a global store">

<Tr>
<En>

Many "state management" problems disappear once two kinds of state leave the store:

**Server state** (products, orders, the user's profile) is owned by the backend. Copying it into Zustand/Redux means writing your own loading flags, caching, refetching, deduplication and invalidation, and it goes stale. A query library does all of that (next lesson):

```text
const { data: products, status } = useQuery({ queryKey: ["products", category], queryFn: fetchProducts });
```

**URL state** (search terms, filters, sort order, current tab, page number) should live in the URL, so reloads, the back button and shared links all work:

```text
// Next.js
const params = useSearchParams();               // read ?category=lamps&sort=price
const router = useRouter();
router.push("?" + new URLSearchParams({ category: "lamps", sort: "price" }));
```

What's left for a client store is usually small: UI state shared across distant components (cart before checkout, sidebar open, editor selection, wizard progress) and user preferences.

</En>
<Ur>

Bohot se "state management" ke masle tab ghayab ho jate hain jab do qism ki state store se nikal jaye:

**Server state** (products, orders, user ka profile) backend ki milkiyat hai. Ise Zustand/Redux me copy karne ka matlab apne loading flags, caching, dobara fetch, deduplication aur invalidation likhna hai, aur ye purana ho jata hai. Query library ye sab karti hai (agla lesson):

```text
const { data: products, status } = useQuery({ queryKey: ["products", category], queryFn: fetchProducts });
```

**URL state** (search terms, filters, sort order, maujooda tab, page number) URL me rehni chahiye, taa ke reloads, back button aur share kiye links sab chalein:

```text
// Next.js
const params = useSearchParams();               // ?category=lamps&sort=price parho
const router = useRouter();
router.push("?" + new URLSearchParams({ category: "lamps", sort: "price" }));
```

Client store ke liye jo bachta hai wo aam taur par chhota hai: door ke components me baanti UI state (checkout se pehle cart, sidebar khula, editor ka intikhab, wizard ki pesh raft) aur user ki preferences.

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- A common sign of trouble: Redux slices full of `isLoading`, `error` and `data` for every endpoint. That's a hand-written query cache; replace it with TanStack Query or RTK Query.
- Another: filters stored in a global store that reset on reload and can't be shared. Move them to the URL.
- Derived values (totals, counts, filtered lists) shouldn't be stored at all; compute them with selectors.

</En>
<Ur>

- Masle ki aam nishani: har endpoint ke liye `isLoading`, `error` aur `data` se bhari Redux slices. Ye haath se likha query cache hai; ise TanStack Query ya RTK Query se badlein.
- Ek aur: global store me rakhe filters jo reload par reset hon aur share na ho sakein. Unhen URL me le jayen.
- Nikali hui values (totals, ginti, filtered lists) bilkul mehfooz nahi honi chahiyen; selectors se hisaab karein.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="One giant context for everything">

```text
<AppContext.Provider value={{ user, setUser, cart, setCart, theme, setTheme, searchQuery, setSearchQuery }}>
// typing in the search box re-renders every component that reads AppContext
```

</Bad>
<Good title="Split by concern; fast-changing state elsewhere">

```text
<AuthProvider>          {/* changes on login/logout */}
  <ThemeProvider>       {/* changes rarely */}
    <App />             {/* cart in a Zustand store, search query in the URL */}
  </ThemeProvider>
</AuthProvider>
```

</Good>
</Compare>

<Compare>
<Bad title="Copying server data into a global store">

```text
const useStore = create((set) => ({
  products: [], productsLoading: false, productsError: null,
  loadProducts: async () => { set({ productsLoading: true }); … },
}));
// no caching rules, no refetch, stale after edits, duplicated per endpoint
```

</Bad>
<Good title="Query cache for server data">

```text
const { data: products, status, error } = useQuery({
  queryKey: ["products"],
  queryFn: () => getJson("/api/products"),
});
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Reaching for a global store first**, for state only one component uses.
- **Selecting the whole store** (`useCart()` with no selector, or `useSelector((s) => s)`): every change re-renders the component.
- **Selectors that return new objects/arrays each time** without equality checks (use `useShallow` in Zustand, or select primitives).
- **Mutating state** outside Immer (`state.items.push` in a Zustand `set` without the immer middleware, or in a plain reducer).
- **Storing derived values** (totals, filtered lists) that can drift out of sync.
- **Forgetting `useMemo` on a Context value object**, causing re-renders on every provider render.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Sirf ek component ki state ke liye **pehle global store ki taraf jana**.
- **Poora store select karna** (bina selector `useCart()`, ya `useSelector((s) => s)`): har tabdeeli component dobara render karti hai.
- **Har dafa naye objects/arrays wapas karne wale selectors** bina equality check ke (Zustand me `useShallow` lein, ya primitives select karein).
- Immer ke bahar **state badalna** (immer middleware ke baghair Zustand `set` me `state.items.push`, ya saade reducer me).
- **Nikali hui values mehfooz karna** (totals, filtered lists) jo be-mel ho sakti hain.
- **Context value object par `useMemo` bhoolna**, jis se har provider render par dobara renders hote hain.

</Ur>
</Tr>

```jsx preview h=220
import { useSyncExternalStore } from "react";

function createStore(initial) {
  let state = initial;
  const listeners = new Set();
  return {
    getState: () => state,
    setState: (fn) => { state = fn(state); listeners.forEach((l) => l()); },
    subscribe: (l) => { listeners.add(l); return () => listeners.delete(l); },
  };
}

const toastStore = createStore([]);
let nextId = 1;
function notify(message) {
  const id = nextId++;
  toastStore.setState((list) => [...list, { id, message }]);
  setTimeout(() => toastStore.setState((list) => list.filter((t) => t.id !== id)), 3000);
}

function Toasts() {
  const toasts = useSyncExternalStore(toastStore.subscribe, toastStore.getState);
  return (
    <div aria-live="polite">
      {toasts.map((t) => <p key={t.id} style={{ background: "#ecfeff", padding: 6, margin: "4px 0" }}>{t.message}</p>)}
    </div>
  );
}

const SaveButton = () => <button onClick={() => notify("Profile saved")}>Save profile</button>;
const CopyButton = () => <button onClick={() => notify("Link copied")}>Copy link</button>;

export default function App() {
  return (
    <div>
      <SaveButton /> <CopyButton />
      <Toasts />
    </div>
  );
}
```

<DeepDive title="More about state management">

**`useSyncExternalStore` and tearing.** In concurrent rendering, a store could change mid-render so different components show different values ("tearing"). `useSyncExternalStore` prevents this, which is why modern store libraries use it.

**Zustand details.** `useShallow` from `zustand/react/shallow` lets selectors return small objects safely: `useCart(useShallow((s) => ({ items: s.items, total: s.total })))`. Slices pattern splits a big store into files. In Next.js, create per-request stores (via context) for server-rendered state to avoid sharing data between users.

**Redux Toolkit extras.** `createAsyncThunk` for async logic, `createEntityAdapter` for normalised collections, `createSelector` (Reselect) for memoised derived data, RTK Query for API caching with automatic invalidation tags.

**Normalisation.** Store collections by id (`{ byId: { "p1": {...} }, allIds: ["p1"] }`) so updates to one item don't require searching arrays, and the same item isn't duplicated in several places.

**State machines.** For flows with clear stages (checkout, onboarding, media players), modelling states and allowed transitions (XState, or a reducer with a `status` field) prevents impossible combinations.

**Signals.** Some frameworks (Solid, Preact Signals, Angular) use fine-grained reactive "signals" that update only what depends on them; React's compiler and stores with selectors aim at similar efficiency differently.

**Server components.** In Next.js, much data never needs client state at all: fetch it in server components and pass it as props.

</DeepDive>

<DeepDive title="Real world: the slow typing in the admin panel">

An admin panel used a single `AppContext` holding the logged-in user, permissions, theme, the open order, the order form's draft values and the sidebar search text. It was convenient: any component could read anything.

As the app grew to about 300 components, users complained that typing in the order notes field lagged noticeably. The React DevTools Profiler showed why: each keystroke updated the draft in `AppContext`, and **240 components** re-rendered, including the sidebar, the header and every table row.

The refactor followed this lesson's ladder:

1. The draft moved into the order **form** itself (React Hook Form), so typing no longer touched shared state at all.
2. The sidebar search text moved into the **URL** (`?q=`), which also made searches shareable.
3. The open order and its lists moved to **TanStack Query** (server state), with the order id in the route.
4. `AuthContext` (user + permissions) and `ThemeContext` stayed as small contexts that change rarely.
5. A small **Zustand** store held the remaining shared UI state (sidebar collapsed, selected rows), read with selectors.

After the change, a keystroke in the notes field re-rendered 1 component. The code was also easier to follow, because each piece of state had an obvious home.

</DeepDive>

<DeepDive title="Security lens">

- **Client state is visible and editable** by the user (DevTools, Redux DevTools, React DevTools). Never keep secrets, tokens or other users' data in it, and never trust it for authorization.
- **Persisted stores** (`persist` middleware → localStorage) inherit localStorage's risks (Cookies and Storage lesson): store only preferences or non-sensitive data, and validate on load.
- **Clear stores on logout** (`store.setState(initialState)` / RTK reset action) and clear query caches, especially on shared devices.
- **Server-side rendering**: a module-level store in Next.js server code is shared by **all requests**: one user's cart could appear for another. Create stores per request on the server.
- **Disable or protect Redux DevTools in production** if your state contains personal data.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="When would you use Context versus a state management library?">
Context suits values that many components read but that change infrequently, such as theme, locale or the authenticated user, because every consumer re-renders when the value changes. For shared client state that changes often or is read in many places, a store like Zustand or Redux with selectors limits re-renders to components whose selected data changed and adds tooling.
</QA>

<QA q="What problem does lifting state up solve?">
It allows sibling or distant components to share and stay consistent on the same data by moving the state to their closest common ancestor, which passes values and update functions down as props, preserving one-way data flow.
</QA>

<QA q="What is the difference between server state and client state?">
Server state is owned by the backend and must be fetched, cached, refreshed and invalidated, and can become stale. Client state is owned by the UI, such as whether a modal is open. Server state is best handled by a query cache library, while client state can use local state, context or a store.
</QA>

<QA q="How does Redux Toolkit simplify Redux?">
It provides configureStore with good defaults and devtools, createSlice to generate action creators and reducers from one definition, and uses Immer so reducers can be written with mutable-looking code that produces immutable updates, plus utilities such as createAsyncThunk and RTK Query.
</QA>

<QA q="How can you prevent unnecessary re-renders with Context?">
Split contexts by concern so consumers only subscribe to what they need, memoise the provided value with useMemo, separate state and dispatch into different contexts, keep rapidly changing values out of context, and memoise expensive child components.
</QA>

</DeepDive>
