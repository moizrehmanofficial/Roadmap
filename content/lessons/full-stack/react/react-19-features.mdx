<BigIdea>
<Tr>
<En>
React 19 is about making the most common app pattern, **"the user does something, we talk to the server, the UI updates"**, much less work. Before, every submit button needed its own `isPending`, `error` and success state, plus manual "optimistic" tricks and careful race handling. Now an async function passed to `startTransition` or a form's `action` is an **Action**: React tracks its pending state for you (`useTransition`, `useActionState`, `useFormStatus`), shows **optimistic** UI with `useOptimistic` that reverts automatically, and resets forms after success. The new **`use()`** reads a promise (suspending until it resolves) or a context, and unlike other hooks it can be called inside conditions. Small but welcome changes remove boilerplate: **`ref` is a regular prop** (goodbye `forwardRef`), ref callbacks can return **cleanup** functions, `<Context>` itself is the provider, and `<title>` / `<meta>` tags rendered anywhere move into the document head. Later 19.x releases added **`<Activity>`** (hide UI while keeping its state) and **`useEffectEvent`**. In frameworks like Next.js, **Server Components** and **Server Actions** build on all of this.
</En>
<Ur>
React 19 sab se aam app pattern, **"user kuch karta hai, hum server se baat karte hain, UI update hoti hai"**, ko bohot kam mehnat wala banane ke baare me hai. Pehle har submit button ko apni `isPending`, `error` aur kamyabi ki state chahiye thi, plus haath ki "optimistic" tarkeebein aur race ka ehtiyat se intezam. Ab `startTransition` ya form ke `action` ko diya async function **Action** hai: React us ki pending halat khud track karta hai (`useTransition`, `useActionState`, `useFormStatus`), `useOptimistic` se **optimistic** UI dikhata hai jo khud wapas palat'ta hai, aur kamyabi ke baad forms reset karta hai. Naya **`use()`** promise (resolve hone tak suspend kar ke) ya context parhta hai, aur doosre hooks ke bar-aks ise shartein ke andar bhi call kiya ja sakta hai. Chhoti magar khushgawar tabdeeliyan boilerplate khatam karti hain: **`ref` aam prop hai** (`forwardRef` ko alvida), ref callbacks **cleanup** functions wapas kar sakte hain, `<Context>` khud provider hai, aur kahin bhi render hue `<title>` / `<meta>` tags document head me chale jate hain. Baad ki 19.x releases ne **`<Activity>`** (state rakhte hue UI chhupana) aur **`useEffectEvent`** joda. Next.js jaise frameworks me **Server Components** aur **Server Actions** in sab par khare hain.
</Ur>

## Learn it step by step

<Walkthrough>

<Step title="Actions: async transitions track pending for you">

<Tr>
<En>
In React 19, `startTransition` accepts an **async** function. While it runs, `isPending` is `true`, with no `useState(false)` + `try/finally` needed. Here the "server" takes a second, and the name "Error" fails.
</En>
<Ur>
React 19 me `startTransition` **async** function qubool karta hai. Jab tak wo chale, `isPending` `true` rehta hai, `useState(false)` + `try/finally` ki zaroorat nahi. Yahan "server" ek second leta hai, aur naam "Error" fail hota hai.
</Ur>
</Tr>

```jsx preview h=200
import { useState, useTransition } from "react";

function updateNameOnServer(name) {
  return new Promise((resolve, reject) =>
    setTimeout(() => (name === "Error" ? reject(new Error("Name not allowed")) : resolve(name)), 1000)
  );
}

export default function App() {
  const [name, setName] = useState("Sara");
  const [draft, setDraft] = useState("Sara Lee");
  const [error, setError] = useState(null);
  const [isPending, startTransition] = useTransition();

  function handleSave() {
    startTransition(async () => {
      try {
        const saved = await updateNameOnServer(draft);
        startTransition(() => { setName(saved); setError(null); });
      } catch (e) {
        setError(e.message);
      }
    });
  }

  return (
    <div>
      <p>Saved name: <strong>{name}</strong></p>
      <input value={draft} onChange={(e) => setDraft(e.target.value)} />{" "}
      <button onClick={handleSave} disabled={isPending}>{isPending ? "Saving…" : "Save"}</button>
      {error && <p role="alert" style={{ color: "#dc2626" }}>{error}</p>}
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Click **Save**: the button shows "Saving…" for a second, then "Saved name: Sara Lee". Type "Error" and save: after the pause, "Name not allowed".
- `isPending` covers the **whole** async function, including the `await`. The input stays responsive throughout, because transitions don't block urgent updates.
- The state update **after** an `await` is wrapped in `startTransition` again: currently React needs that to treat it as part of the transition (a known limitation that future versions remove).
- If the user clicks several times, React handles the queue of actions in order, avoiding the classic "last response wins" race.

</En>
<Ur>

- **Save** dabayen: button ek second "Saving…" dikhata hai, phir "Saved name: Sara Lee". "Error" likh kar save karein: waqfe ke baad "Name not allowed".
- `isPending` **poore** async function ko dhakta hai, `await` samet. Input poore waqt jawab deta rehta hai, kyun ke transitions fori updates ko nahi rokte.
- `await` ke **baad** ka state update dobara `startTransition` me lipta hai: filhal React ko ise transition ka hissa samajhne ke liye ye chahiye (maloom hadd jo aane wale versions hata denge).
- Agar user kai dafa dabaye, React actions ki qatar tarteeb se sambhalta hai, mashhoor "aakhri jawab jeet'ta hai" race se bachte hue.

</Ur>
</Tr>
</Happened>

<Step title="Form actions, useActionState and useFormStatus">

<Tr>
<En>

The Forms lesson showed `useActionState` in detail. In summary:

```text
import { useActionState } from "react";
import { useFormStatus } from "react-dom";

function SubmitButton() {
  const { pending } = useFormStatus();        // reads the nearest parent <form>
  return <button disabled={pending}>{pending ? "Saving…" : "Save"}</button>;
}

export function ProfileForm() {
  const [state, formAction] = useActionState(async (prev, formData) => {
    const result = await saveProfile(formData);   // fetch, or a Server Action in Next.js
    return result.ok ? { message: "Saved" } : { error: result.error };
  }, {});

  return (
    <form action={formAction}>
      <input name="displayName" />
      <SubmitButton />                              {/* no props needed */}
      {state.error && <p role="alert">{state.error}</p>}
      {state.message && <p>{state.message}</p>}
    </form>
  );
}
```

</En>
<Ur>

Forms lesson ne `useActionState` tafseel se dikhaya. Khulasa:


<Step title="useOptimistic: show the result before the server answers">

<Tr>
<En>
`useOptimistic(state, updateFn)` returns a temporary version of `state` that you can change **during an action**. When the action finishes, React throws the optimistic version away and shows the real state, so failures **roll back automatically**. Send a few messages; any message containing "fail" is rejected by the pretend server.
</En>
<Ur>
`useOptimistic(state, updateFn)` `state` ka aarzi version wapas karta hai jise aap **action ke dauran** badal sakte hain. Action khatam hone par React optimistic version phenk kar asli state dikhata hai, isliye nakamiyan **khud palat** jati hain. Chand paighaam bhejein; "fail" wala har paighaam naqli server radd karta hai.
</Ur>
</Tr>

```jsx preview h=280
import { useOptimistic, useState, useTransition } from "react";

function sendToServer(text) {
  return new Promise((resolve, reject) =>
    setTimeout(() => (text.includes("fail") ? reject(new Error("Couldn't send")) : resolve({ id: Date.now(), text })), 1200)
  );
}

export default function App() {
  const [messages, setMessages] = useState([{ id: 1, text: "Hi! Is the mug still available?" }]);
  const [optimisticMessages, addOptimistic] = useOptimistic(messages, (current, newText) => [
    ...current,
    { id: "temp-" + newText, text: newText, sending: true },
  ]);
  const [text, setText] = useState("");
  const [error, setError] = useState(null);
  const [, startTransition] = useTransition();

  function send() {
    const value = text.trim();
    if (!value) return;
    setText("");
    setError(null);
    startTransition(async () => {
      addOptimistic(value);
      try {
        const saved = await sendToServer(value);
        startTransition(() => setMessages((m) => [...m, saved]));
      } catch (e) {
        setError(e.message + ": " + value);
      }
    });
  }

  return (
    <div>
      <ul>
        {optimisticMessages.map((m) => (
          <li key={m.id} style={{ color: m.sending ? "#94a3b8" : "inherit" }}>
            {m.text} {m.sending && <small>(sending…)</small>}
          </li>
        ))}
      </ul>
      <input value={text} onChange={(e) => setText(e.target.value)} placeholder="Type a message" />{" "}
      <button onClick={send}>Send</button>
      {error && <p role="alert" style={{ color: "#dc2626" }}>{error}</p>}
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Send "Yes, it is": it appears **instantly** in grey with "(sending…)", then turns normal when the server confirms about a second later.
- Send "this will fail": it appears in grey, then **disappears** and an error shows. We never wrote rollback code: when the action ended, React dropped the optimistic list and showed the real `messages`, which never included the failed one.
- The update function `(current, newText) => …` describes how to apply an optimistic change, so several pending messages stack correctly.
- Compare with the TanStack Query lesson's manual snapshot/rollback; with TanStack Query you can also use its `variables` from `useMutation` for optimistic UI.

</En>
<Ur>

- "Yes, it is" bhejein: ye surmai rang me "(sending…)" ke saath **foran** nazar aata hai, phir taqreeban ek second baad server ki tasdeeq par aam ho jata hai.
- "this will fail" bhejein: ye surmai me nazar aata hai, phir **ghayab** ho jata hai aur error dikhta hai. Humne kabhi rollback code nahi likha: action khatam hone par React ne optimistic list chhor kar asli `messages` dikhaye, jin me nakam paighaam kabhi tha hi nahi.
- Update function `(current, newText) => …` bayan karta hai ke optimistic tabdeeli kaise lagani hai, isliye kai pending paighaam sahi tah me jamte hain.
- TanStack Query lesson ke haath ke snapshot/rollback se muqabla karein; TanStack Query ke saath aap optimistic UI ke liye `useMutation` ke `variables` bhi istemal kar sakte hain.

</Ur>
</Tr>
</Happened>

<Step title="use(): reading a promise with Suspense">

<Tr>
<En>
`use(promise)` reads the value of a promise **during render**. Until it resolves, the component **suspends** and the nearest `<Suspense>` shows its fallback; if it rejects, the nearest error boundary handles it. The promise must be created **outside** render (in a parent, a cache, a framework loader or a server component), not inside the component that calls `use`.
</En>
<Ur>
`use(promise)` **render ke dauran** promise ki value parhta hai. Resolve hone tak component **suspend** hota hai aur qareebi `<Suspense>` apna fallback dikhata hai; reject ho to qareebi error boundary use sambhalta hai. Promise render ke **bahar** banna chahiye (parent, cache, framework loader ya server component me), `use` call karne wale component ke andar nahi.
</Ur>
</Tr>

```jsx preview h=220
import { Suspense, use, useState } from "react";

function fetchProduct(id) {
  const products = { 1: { name: "Mug", price: 12, stock: 31 }, 2: { name: "Desk Lamp", price: 30, stock: 4 } };
  return new Promise((resolve) => setTimeout(() => resolve(products[id]), 800));
}

function ProductDetails({ productPromise }) {
  const product = use(productPromise);         // suspends until resolved
  return <p><strong>{product.name}</strong>: ${product.price} · {product.stock} in stock</p>;
}

export default function App() {
  const [productPromise, setProductPromise] = useState(() => fetchProduct(1));
  return (
    <div>
      <button onClick={() => setProductPromise(fetchProduct(1))}>Mug</button>{" "}
      <button onClick={() => setProductPromise(fetchProduct(2))}>Desk Lamp</button>
      <Suspense fallback={<p>Loading product…</p>}>
        <ProductDetails productPromise={productPromise} />
      </Suspense>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- First "Loading product…" for 0.8 s, then "Mug: $12 · 31 in stock". Clicking **Desk Lamp** creates a new promise in an event handler; the fallback shows again, then "Desk Lamp: $30 · 4 in stock".
- `ProductDetails` has no loading state at all: it's written as if the data were already there. Loading is handled by the `<Suspense>` boundary around it.

- To avoid showing the fallback again when switching, wrap the update in `startTransition`: React keeps the old content visible until the new data is ready.

</En>
<Ur>

<Step title="ref as a prop, and ref cleanup functions">

<Tr>
<En>
Function components now receive `ref` like any other prop, so reusable inputs no longer need `forwardRef`. And a **ref callback** can return a **cleanup function**, called when the element is removed, perfect for observers and listeners attached to a DOM node.
</En>
<Ur>
Function components ko ab `ref` kisi bhi doosre prop ki tarah milta hai, isliye dobara istemal hone wale inputs ko `forwardRef` ki zaroorat nahi. Aur **ref callback** **cleanup function** wapas kar sakta hai, jo element hatne par call hota hai, DOM node se jure observers aur listeners ke liye behtareen.
</Ur>
</Tr>

```jsx preview h=240
import { useCallback, useRef, useState } from "react";

// React 19: ref is just a prop
function TextField({ label, ref, ...rest }) {
  return <label>{label} <input ref={ref} {...rest} /></label>;
}

export default function App() {
  const inputRef = useRef(null);
  const [showBox, setShowBox] = useState(true);
  const [log, setLog] = useState([]);
  const add = (msg) => setLog((l) => [...l.slice(-3), msg]);

  // stable ref callback: an inline one would re-run on every render
  const boxRef = useCallback((node) => {
    add("box attached, width " + Math.round(node.getBoundingClientRect().width) + "px");
    return () => add("box removed: cleanup ran");
  }, []);

  return (
    <div>
      <TextField label="Email" ref={inputRef} placeholder="you@example.com" />{" "}
      <button onClick={() => inputRef.current.focus()}>Focus email</button>
      <p>
        <button onClick={() => setShowBox(!showBox)}>{showBox ? "Remove" : "Add"} box</button>
      </p>
      {showBox && (
        <div
          ref={boxRef}
          style={{ width: 180, boxSizing: "border-box", padding: 8, background: "#e0f2fe" }}
        >
          Measured box
        </div>
      )}
      <pre>{log.join("\n")}</pre>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **Focus email** focuses the input inside `TextField`, which simply destructured `ref` from its props.
- The log shows "box attached, width 180px". Clicking **Remove box** logs "box removed: cleanup ran"; **Add box** attaches it again.
- The callback is wrapped in `useCallback`: an inline arrow is a **new** function every render, so React would run the cleanup and attach again each time (and here, logging to state would loop forever).
- Before React 19, ref callbacks were called again with `null` on removal; now you return a cleanup, like `useEffect`. Typical uses: `ResizeObserver`, `IntersectionObserver`, third-party widgets bound to a node.
- In TypeScript, type it as a normal prop: `ref?: React.Ref<HTMLInputElement>`, or use `ComponentProps<"input">`, which already includes `ref`.

</En>
<Ur>

- **Focus email** `TextField` ke andar ke input par focus lata hai, jis ne bas apne props se `ref` destructure kiya.
- Log "box attached, width 180px" dikhata hai. **Remove box** dabane par "box removed: cleanup ran" log hota hai; **Add box** use dobara jorta hai.
- Callback `useCallback` me lipta hai: inline arrow har render par **naya** function hai, isliye React har dafa cleanup chala kar dobara jorta (aur yahan state me log karna hamesha loop karta).
- React 19 se pehle hatne par ref callbacks dobara `null` ke saath call hote the; ab aap `useEffect` ki tarah cleanup wapas karte hain. Aam istemal: `ResizeObserver`, `IntersectionObserver`, node se bandhe third-party widgets.
- TypeScript me ise aam prop ki tarah type karein: `ref?: React.Ref<HTMLInputElement>`, ya `ComponentProps<"input">` lein, jis me `ref` pehle se shamil hai.

</Ur>

<Step title="useEffectEvent: latest values without re-running effects">

<Tr>
<En>
An effect sometimes needs a value it shouldn't **react** to. Here a chat connection depends on the room, and a notification should use the current "muted" setting. Putting `muted` in the dependencies would reconnect every time you toggle it; leaving it out shows a **stale** value. `useEffectEvent` (React 19.2) fixes this: functions created with it always see the latest props and state, and aren't dependencies.
</En>
<Ur>
Effect ko kabhi aisi value chahiye hoti hai jis par use **amal** nahi karna. Yahan chat connection room par munhasir hai, aur notification ko maujooda "muted" setting istemal karni chahiye. `muted` ko dependencies me rakhna har toggle par dobara jorta; chhorna **purani** value dikhata. `useEffectEvent` (React 19.2) ise theek karta hai: is se bane functions hamesha taaza props aur state dekhte hain, aur dependencies nahi hote.
</Ur>
</Tr>

```jsx preview h=240
import { useEffect, useEffectEvent, useState } from "react";

function fakeConnect(room, onMessage) {
  const id = setInterval(() => onMessage("New message in #" + room), 1500);
  return () => clearInterval(id);
}

export default function App() {
  const [room, setRoom] = useState("general");
  const [muted, setMuted] = useState(false);
  const [log, setLog] = useState([]);
  const add = (line) => setLog((l) => [...l.slice(-4), line]);

  const onMessage = useEffectEvent((text) => {
    add(muted ? "(muted) " + text : "🔔 " + text);   // always reads the current `muted`
  });

  useEffect(() => {
    add("connected to #" + room);
    const disconnect = fakeConnect(room, onMessage);
    return () => { disconnect(); add("disconnected from #" + room); };
  }, [room]);                                        // onMessage isn't a dependency

  return (
    <div>
      <select value={room} onChange={(e) => setRoom(e.target.value)}>
        <option>general</option><option>orders</option>
      </select>{" "}
      <label><input type="checkbox" checked={muted} onChange={(e) => setMuted(e.target.checked)} /> mute</label>
      <pre>{log.join("\n")}</pre>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- The log shows "connected to #general" and a 🔔 message every 1.5 s. Tick **mute**: new messages show "(muted)", and there's **no** reconnect. Change the room: "disconnected from #general", "connected to #orders".
- Without `useEffectEvent`, you'd either reconnect on every mute toggle (if `muted` were a dependency) or keep notifying with the old setting (if it weren't). This is the same "latest ref" pattern from the Custom Hooks lesson, now built in.
- Only call effect events **from effects**; don't pass them to other components or call them during render.

</En>
<Ur>

- Log "connected to #general" aur har 1.5 s par 🔔 paighaam dikhata hai. **mute** tick karein: naye paighaam "(muted)" dikhate hain, aur dobara jorna **nahi** hota. Room badlein: "disconnected from #general", "connected to #orders".
- `useEffectEvent` ke baghair aap ya har mute toggle par dobara jorte (agar `muted` dependency hota) ya purani setting ke saath notify karte rehte (agar na hota). Ye Custom Hooks lesson ka wahi "latest ref" pattern hai, ab bana banaya.
- Effect events sirf **effects se** call karein; unhen doosre components ko na dein ya render ke dauran call na karein.

</Ur>
</Tr>
</Happened>

<Step title="Server Components, Server Actions and upgrading">

<Tr>
<En>

Some React 19 features only work inside a framework (Next.js App Router, React Router v7 framework mode):

- **Server Components** run only on the server (or at build time). They can be `async`, read databases directly, and send **no JavaScript** to the browser. Interactive parts are marked `"use client"`.
- **Server Functions / Server Actions** are `async` functions marked `"use server"` that the client can call, for example as a `<form action>`. The framework handles the network request; you validate input and check permissions inside.

```text
// app/products/page.tsx (Server Component)
export default async function ProductsPage() {
  const products = await db.product.findMany();      // runs on the server
  return <ProductList products={products} />;
}

// app/actions.ts
"use server";
export async function addToWishlist(formData: FormData) {
  const user = await requireUser();                 // always check auth
  const id = z.coerce.number().parse(formData.get("productId"));
  await db.wishlist.create({ data: { userId: user.id, productId: id } });
}
```

**Upgrading from React 18** (the codemods `npx codemod react/19/migration-recipe` automate most of it):

| Removed / changed | Use instead |
| --- | --- |
| `ReactDOM.render`, `hydrate` | `createRoot`, `hydrateRoot` |
| `propTypes`, `defaultProps` on function components | TypeScript, default parameter values |
| String refs, legacy context | `useRef` / ref callbacks, `createContext` |
| `forwardRef` (still works) | `ref` as a prop |
| `<Context.Provider>` (still works) | `<Context value>` |
| `react-test-renderer`, `act` from `react-dom/test-utils` | Testing Library, `act` from `react` |

</En>
<Ur>

Kuch React 19 features sirf framework ke andar chalti hain (Next.js App Router, React Router v7 framework mode):

- **Server Components** sirf server par (ya build ke waqt) chalte hain. Ye `async` ho sakte hain, databases seedha parh sakte hain, aur browser ko **koi JavaScript** nahi bhejte. Interactive hisse `"use client"` se nishaan zad hote hain.
- **Server Functions / Server Actions** `"use server"` se nishaan zad `async` functions hain jinhen client call kar sakta hai, maslan `<form action>` ki tarah. Framework network request sambhalta hai; aap andar input validate aur permissions check karte hain.

</Ur>
</Tr>

<Tr>
<En>

- Server Components and Server Actions are covered properly in the Next.js module; the key idea here is that **Actions** work the same whether the function runs on the client or the server.
- A Server Action is a **public HTTP endpoint**: anyone can call it with any input. Validate (zod) and authorise inside every one, exactly like an API route.

</Ur>

## Common mistakes

<Compare>
<Bad title="Creating a promise during render for use()">

```text
function Product({ id }) {
  const product = use(fetchProduct(id));   // new promise every render → suspends forever
  return <h2>{product.name}</h2>;
}
```

</Bad>
<Good title="Create it outside render (parent, cache or server)">

```text
// Server Component (Next.js) passes the promise down
export default function Page({ params }) {
  const productPromise = getProduct(params.id);   // not awaited
  return <Suspense fallback={<Skeleton />}><Product productPromise={productPromise} /></Suspense>;
}
// or on the client: useSuspenseQuery({ queryKey: ["product", id], queryFn })
```

</Good>
</Compare>

<Compare>
<Bad title="Still hand-rolling pending state">

```text
const [saving, setSaving] = useState(false);
async function save() {
  setSaving(true);
  try { await saveProfile(data); } finally { setSaving(false); }
}
// no ordering of repeated clicks, more state to keep in sync
```

</Bad>
<Good title="Use an Action">

```text
const [isPending, startTransition] = useTransition();
const save = () => startTransition(async () => { await saveProfile(data); });
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Calling `useOptimistic`'s setter outside an action/transition** (React warns, and the optimistic state reverts immediately).
- **Using `useFormStatus` in the same component that renders the `<form>`**: it reads a **parent** form, so put it in a child (like `SubmitButton`).
- **Rendering `<title>` with several children** (`<title>Cart ({count})</title>` makes an array); build one string.
- **Treating Server Actions as private**: always validate and authorise.
- **Using `use()` without a `<Suspense>` boundary** (and an error boundary) above it.
- **Calling effect events during render** or passing them to child components.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`useOptimistic` ka setter action/transition ke bahar call karna** (React warning deta hai, aur optimistic state foran palat jati hai).
- **`<form>` render karne wale usi component me `useFormStatus` istemal karna**: ye **parent** form parhta hai, isliye ise child me rakhein (jaise `SubmitButton`).
- **Kai children ke saath `<title>` render karna** (`<title>Cart ({count})</title>` array banata hai); ek string banayen.
- **Server Actions ko private samajhna**: hamesha validate aur authorise karein.
- **Upar `<Suspense>` hadd (aur error boundary) ke baghair `use()` istemal karna**.
- **Render ke dauran effect events call karna** ya unhen child components ko dena.

</Ur>
</Tr>

```jsx preview h=150
  calls++;
  return new Promise((resolve, reject) =>
    setTimeout(() => (calls % 3 === 0 ? reject(new Error("Couldn't save your like")) : resolve(liked)), 800)
  );
}

export default function App() {
  const [post, setPost] = useState({ liked: false, likes: 41 });
  const [optimistic, setOptimistic] = useOptimistic(post, (current, liked) => ({
    liked,
    likes: current.likes + (liked ? 1 : -1),
  }));
  const [error, setError] = useState(null);
  const [isPending, startTransition] = useTransition();

  function toggle() {
    const next = !optimistic.liked;
    setError(null);
    startTransition(async () => {
      setOptimistic(next);
      try {
        await saveLike(next);
        startTransition(() => setPost((p) => ({ liked: next, likes: p.likes + (next ? 1 : -1) })));
      } catch (e) {
        setError(e.message);
      }
    });
  }

  return (
    <p>
      <button onClick={toggle} disabled={isPending} aria-pressed={optimistic.liked}>
        {optimistic.liked ? "♥" : "♡"} {optimistic.likes}
      </button>{" "}
      {error && <span role="alert" style={{ color: "#dc2626" }}>{error}</span>}
    </p>
  );
}
```

<DeepDive title="More React 19 details">

**Action ordering.** Multiple submissions of the same `useActionState` action run sequentially; each receives the previous state, so results arrive in order.

**`useActionState` with Server Actions.** In Next.js, passing a Server Action to `useActionState` enables **progressive enhancement**: the form posts to the server even before hydration, and the returned state is rendered on the next page load.

**`useOptimistic` and transitions.** Optimistic updates must happen inside an Action; the optimistic value persists until **all** pending actions in that transition finish.

**Suspense improvements.** When a component suspends, React now commits the fallback immediately and "pre-warms" sibling components, reducing waterfalls.

**`cache()` (server).** Deduplicates function calls during one server request in Server Components, for example `const getUser = cache(async (id) => …)`.

**Custom elements.** React 19 fully supports Web Components: props are set as properties when the element defines them.

**`ViewTransition` (canary/experimental).** Integrates the browser's View Transitions API for animated navigation; check React's release notes for its status.

**React Compiler.** Works best with React 19 and the patterns in this lesson (React Performance lesson).

</DeepDive>

<DeepDive title="Real world: deleting 400 lines from a settings page">

A SaaS app's settings page had nine small forms (profile, password, notifications, billing address…). Each had its own `isSaving`, `error` and `successMessage` state, a `handleSubmit` with `try/catch/finally`, a "saved!" timeout, and a custom `SubmitButton` that took `isSaving` as a prop. Some forms forgot `finally`, so a failed request left the button stuck on "Saving…" until reload.

After upgrading to React 19 and Next.js, the team migrated form by form:

1. Each form became `<form action={formAction}>` with `useActionState`, calling a **Server Action** that validated with zod, checked the session and returned `{ fieldErrors }` or `{ message }`.
2. One shared `SubmitButton` used `useFormStatus()`, with no props.
3. The notification toggles used `useOptimistic`, so switches flipped instantly and reverted if saving failed.
4. The "connected accounts" panel used `use()` with a promise started in the server component, removing a `useEffect` + loading state.

The page lost about 400 lines of state-management code, the stuck-button bug disappeared (Actions always end), and the forms now worked even before JavaScript finished loading on slow phones.

</DeepDive>

<DeepDive title="Security lens">

- **Server Actions are public endpoints**: validate every input (zod), check authentication and authorisation inside each one, and never trust hidden form fields (like `userId`) from the client.
- **Optimistic UI is not confirmation**: never optimistic-update anything that implies money moved or access changed; wait for the server.
- **Server Components can access secrets** (database, API keys); make sure only safe, serialisable data is passed to client components as props, since props are sent to the browser.
- **Metadata tags** built from user content (`<title>{product.name}</title>`) are rendered as text and safe, but don't build `<meta>` URLs or `<link href>` from unvalidated input.
- **Hydration mismatches** are not security issues themselves, but disabling warnings to hide them can mask real bugs; fix the cause.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are Actions in React 19?">
Actions are async functions run inside transitions, either via startTransition or passed to a form's action prop. React tracks their pending state, handles sequential execution of repeated submissions, integrates with optimistic updates and error handling, and resets forms after successful form actions.
</QA>

<QA q="How does useOptimistic work?">
It takes the current state and an update function and returns an optimistic copy plus a setter. During an action you apply optimistic changes that render immediately; when the action completes, React discards the optimistic state and renders the real state, which automatically rolls back failures.
</QA>

<QA q="What is the use API and how does it differ from useContext?">
use reads the value of a promise, suspending until it resolves, or the value of a context. Unlike useContext and other hooks, it may be called conditionally and inside loops. Promises passed to it should be created outside the rendering component, typically by a server component, loader or cache.
</QA>

<QA q="What changed with refs in React 19?">
Function components receive ref as a regular prop, so forwardRef is unnecessary, and ref callbacks can return a cleanup function that runs when the element is detached, instead of being called with null.
</QA>

<QA q="What are Server Components and Server Actions?">
Server Components render only on the server, can be async and access server resources directly, and send no JavaScript to the client. Server Actions are server functions marked with use server that client code can call, for example as form actions; the framework creates the network endpoint, so they must validate input and check permissions.
</QA>

</DeepDive>
