<BigIdea>
<Tr>
<En>
A component's main job is to **return JSX**: to describe the screen. But sometimes it also needs to **do something** in the outside world: start a timer, listen for key presses, connect to a chat server, or load data from an API. Those are **side effects**, and they don't belong in the middle of drawing. **`useEffect`** lets you say "**after** React has updated the screen, run this code". You pass it a function and a **dependency array**: `useEffect(() => { … }, [userId])`. The array decides **when** it runs: after every render (no array), only once when the component appears (`[]`), or whenever one of the listed values changes (`[userId]`). The function can **return a cleanup function**, which React runs before the effect runs again and when the component disappears, so timers stop and listeners are removed.
</En>
<Ur>
Component ka asal kaam **JSX wapas karna** hai: screen bayan karna. Magar kabhi use bahar ki duniya me **kuch karna** bhi hota hai: timer shuru karna, keys dabane ko sunna, chat server se jurna, ya API se data lana. Ye **side effects** hain, aur inki jagah screen banane ke beech me nahi. **`useEffect`** aap ko kehne deta hai "React screen update kar le, **us ke baad** ye code chalao". Aap ise ek function aur **dependency array** dete hain: `useEffect(() => { … }, [userId])`. Array tay karti hai ke ye **kab** chale: har render ke baad (array nahi), sirf ek dafa jab component aaye (`[]`), ya jab bhi likhi gayi values me se koi badle (`[userId]`). Function ek **cleanup function wapas** kar sakta hai, jise React effect ke dobara chalne se pehle aur component ke ghayab hone par chalata hai, taa ke timers ruk jayen aur listeners hat jayen.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

```jsx
import { useEffect } from "react";

useEffect(() => {
  // 1. do something after the screen updates
  const id = setInterval(tick, 1000);

  // 2. optional: undo it
  return () => clearInterval(id);
}, [/* 3. when to run again */]);
```

Read it as: **"After rendering, start this. Before running it again, or when the component goes away, stop it. Run it again only when these values change."**

</En>
<Ur>

```jsx
import { useEffect } from "react";

useEffect(() => {
  // 1. screen update hone ke baad kuch karo
  const id = setInterval(tick, 1000);

  // 2. ikhtiyari: use wapas karo
  return () => clearInterval(id);
}, [/* 3. dobara kab chalana hai */]);
```

Ise aise parhein: **"Render ke baad ye shuru karo. Dobara chalane se pehle, ya jab component chala jaye, ise roko. Dobara sirf tab chalao jab ye values badlen."**

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Rendering must stay pure.** Timers, subscriptions and network requests would run on every render, and React may render more often than you expect.
- **Some things live outside React:** the browser's timers and events, a WebSocket, a third-party map or chart, the page title.
- **Things must be cleaned up.** A timer that keeps running after its component is gone wastes resources and causes bugs.
- **Keeping in sync.** When `userId` changes, the chat connection or the loaded profile should follow it automatically.

</En>
<Ur>

- **Rendering pure rehni chahiye.** Timers, subscriptions aur network requests har render par chal jate, aur React aap ki umeed se zyada dafa render kar sakta hai.
- **Kuch cheezen React se bahar rehti hain:** browser ke timers aur events, WebSocket, kisi aur ka bana map ya chart, page ka title.
- **Cheezon ki safai zaroori hai.** Component chale jane ke baad bhi chalta rehne wala timer wasail zaya karta hai aur bugs paida karta hai.
- **Mel me rakhna.** Jab `userId` badle to chat connection ya load ki gayi profile khud ba khud us ke saath chale.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Use an effect for… | Don't use an effect for… |
| --- | --- |
| Timers and intervals | Values you can calculate from props or state |
| Listening to window or document events | Reacting to a button click (use the click handler) |
| Connecting to something (chat, WebSocket) | Resetting state when a prop changes (use a `key`) |
| Loading data when the screen needs it (or use a data library) | Sending a form (use the submit handler) |
| Controlling non-React code (maps, video players) | Transforming data for display |

</En>
<Ur>

| Effect is ke liye lein… | Effect is ke liye na lein… |
| --- | --- |
| Timers aur intervals | Wo values jo props ya state se nikal sakti hain |
| Window ya document ke events sunna | Button click ka jawab (click handler lein) |
| Kisi cheez se jurna (chat, WebSocket) | Prop badalne par state reset karna (`key` lein) |
| Jab screen ko zaroorat ho to data load karna (ya data library) | Form bhejna (submit handler lein) |
| Ghair-React code chalana (maps, video players) | Dikhane ke liye data badalna |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```jsx
useEffect(() => { … });            // after EVERY render
useEffect(() => { … }, []);        // once, after the first render
useEffect(() => { … }, [a, b]);    // after the first render, and when a or b changes
```

</En>
<Ur>

```jsx
useEffect(() => { … });            // HAR render ke baad
useEffect(() => { … }, []);        // ek dafa, pehle render ke baad
useEffect(() => { … }, [a, b]);    // pehle render ke baad, aur jab a ya b badle
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **shop assistant who rearranges a shop window**. Their main job is the display: putting the right products in the window for today (that's **rendering**).

But some jobs happen **after** the display is ready: switching on the window lights, starting the rotating sign, putting up a "Back in 5 minutes" timer. Those are **effects**.

- The **dependency list** is a note: "only redo the lights if the **season** changes". No note at all means "redo it every time you touch the window". An empty note means "do it once, when the shop opens".
- The **cleanup** is the closing routine: before setting up a new sign, take the old one down; when the shop closes, switch off the lights. If you skip cleanup, you end up with three signs spinning at once and lights burning all night.

</En>
<Ur>

Ek **dukaan ke assistant** ka sochein jo dukaan ki khirki sajata hai. Us ka asal kaam display hai: aaj ke liye khirki me sahi products rakhna (ye **rendering** hai).

Magar kuch kaam display tayyar hone ke **baad** hote hain: khirki ki battiyan jalana, ghoomne wala board chalana, "5 minute me wapas" ka timer lagana. Ye **effects** hain.

- **Dependency list** ek note hai: "battiyan sirf tab dobara karo jab **mausam** badle". Koi note na ho to matlab "har dafa khirki chhoo kar ye dobara karo". Khaali note ka matlab "ek dafa karo, jab dukaan khule".
- **Cleanup** band karne ka maamool hai: naya board lagane se pehle purana utaaro; dukaan band ho to battiyan bujhao. Cleanup chhor dein to teen board ek saath ghoom rahe hote hain aur battiyan saari raat jalti hain.

</Ur>
</Tr>

<Tr>

<Walkthrough>

<Step title="Effects run after the screen updates">

<Tr>
<En>
Here a component logs while rendering, and also has an effect. Watch the order in the grey box, then click the button a few times.
</En>
<Ur>
Yahan component render karte waqt log karta hai, aur us ka ek effect bhi hai. Grey dabbe me tarteeb dekhein, phir button kuch dafa click karein.
</Ur>
</Tr>

```jsx preview h=230
import { useState, useEffect } from "react";

const logBox = document.body.appendChild(document.createElement("pre"));
logBox.style.cssText = "background:#f3f4f6;padding:8px;font-size:12px;margin:12px 16px 0";
function log(message) {
  logBox.textContent += message + "\n";
}

export default function App() {
  const [count, setCount] = useState(0);
  log("1. rendering with count = " + count);

  useEffect(() => {
    log("2. effect ran, the screen now shows " + count);
  });

  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

<Happened>
<Tr>
<En>

- First React **rendered** (line 1), put the button on the page, and **then** ran the effect (line 2).
- Each click causes a re-render, and the effect runs again after it. With **no dependency array**, an effect runs after **every** render.
- Inside the effect, the screen is already updated. That's the moment to touch things outside React.

</En>
<Ur>

- Pehle React ne **render** kiya (line 1), button page par rakha, aur **phir** effect chalaya (line 2).
- Har click dobara render karata hai, aur us ke baad effect phir chalta hai. **Dependency array ke baghair** effect **har** render ke baad chalta hai.
- Effect ke andar screen pehle hi update ho chuki hoti hai. React se bahar ki cheezen chhoone ka yahi waqt hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The dependency array decides when">

<Tr>
<En>
Usually you don't want an effect after every render. The **second argument** is a list of values; React re-runs the effect only when one of them has changed since the last render. Type in the box, then click the button, and watch which effects run.
</En>
<Ur>
Aam taur par aap har render ke baad effect nahi chahte. **Doosra argument** values ki list hai; React effect tabhi dobara chalata hai jab pichhle render se in me se koi badli ho. Dabbe me type karein, phir button click karein, aur dekhein kaun se effects chalte hain.
</Ur>
</Tr>

```jsx preview h=270
import { useState, useEffect } from "react";

const logBox = document.body.appendChild(document.createElement("pre"));
logBox.style.cssText = "background:#f3f4f6;padding:8px;font-size:12px;margin:12px 16px 0";
function log(message) {
  logBox.textContent += message + "\n";
}

export default function App() {
  const [count, setCount] = useState(0);
  const [name, setName] = useState("");

  useEffect(() => {
    log("[] → runs once, when the component first appears");
  }, []);

  useEffect(() => {
    log("[count] → count is now " + count);
  }, [count]);

  return (
    <div>
      <input value={name} onChange={(e) => setName(e.target.value)} placeholder="Type here" />{" "}
      <button onClick={() => setCount(count + 1)}>Count: {count}</button>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- On the first render, **both** effects ran.
- Typing re-renders the component on every key, but **neither** effect runs: `[]` never re-runs, and `count` didn't change.
- Clicking the button changes `count`, so only the `[count]` effect runs again.
- React compares each dependency with its previous value using `Object.is`. If all are the same, the effect is skipped.

</En>
<Ur>

- Pehle render par **dono** effects chale.
- Type karna har key par component dobara render karta hai, magar **koi** effect nahi chalta: `[]` kabhi dobara nahi chalta, aur `count` nahi badla.
- Button click karne se `count` badalta hai, isliye sirf `[count]` wala effect dobara chalta hai.
- React har dependency ka us ki pichhli value se `Object.is` ke zariye muqabla karta hai. Sab wahi hon to effect chhor diya jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A ticking clock: effects with cleanup">

<Tr>
<En>
A clock needs a timer that runs every second. That's a side effect, so it goes in `useEffect`. The effect **returns a cleanup function** that stops the timer. Use the button to show and hide the clock.
</En>
<Ur>
Ghari ko aisa timer chahiye jo har second chale. Ye side effect hai, isliye `useEffect` me jata hai. Effect ek **cleanup function wapas** karta hai jo timer rokta hai. Ghari dikhane aur chhupane ke liye button istemal karein.
</Ur>
</Tr>

```jsx preview h=240
import { useState, useEffect } from "react";

const logBox = document.body.appendChild(document.createElement("pre"));
logBox.style.cssText = "background:#f3f4f6;padding:8px;font-size:12px;margin:12px 16px 0";
function log(message) {
  logBox.textContent += message + "\n";
}

function Stopwatch() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    log("timer started");
    const id = setInterval(() => {
      setSeconds((s) => s + 1);
    }, 1000);

    return () => {
      clearInterval(id);
      log("timer stopped (cleanup)");
    };
  }, []);

  return <p style={{ fontSize: 28, margin: "8px 0" }}>{seconds}s</p>;
}

export default function App() {
  const [visible, setVisible] = useState(true);
  return (
    <div>
      <button onClick={() => setVisible(!visible)}>{visible ? "Hide" : "Show"} stopwatch</button>
      {visible && <Stopwatch />}
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- When `Stopwatch` appears (**mounts**), the effect starts an interval that adds 1 every second.
- Click **Hide**: the component is removed (**unmounts**), and React runs the **cleanup**, which calls `clearInterval`. The log shows "timer stopped".
- Click **Show**: it's a brand-new `Stopwatch`, starting from 0 with a new timer.
- `setSeconds((s) => s + 1)` uses an updater, so the interval never needs to read `seconds` itself (see step 6 for why that matters).

</En>
<Ur>

- Jab `Stopwatch` aata hai (**mount**), effect ek interval shuru karta hai jo har second 1 jorta hai.
- **Hide** click karein: component hat jata hai (**unmount**), aur React **cleanup** chalata hai, jo `clearInterval` call karta hai. Log "timer stopped" dikhata hai.
- **Show** click karein: ye bilkul naya `Stopwatch` hai, 0 se naye timer ke saath shuru.
- `setSeconds((s) => s + 1)` updater istemal karta hai, isliye interval ko khud `seconds` parhne ki zaroorat nahi (qadam 6 batata hai ye kyun ahem hai).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What happens without cleanup">

<Tr>
<En>
Same idea, but this effect forgets to clean up, and it re-runs whenever `speed` changes. Change the speed a few times and watch the counter.
</En>
<Ur>
Wahi khayal, magar ye effect safai bhool jata hai, aur `speed` badalne par dobara chalta hai. Speed kuch dafa badlein aur counter dekhein.
</Ur>
</Tr>

```jsx preview h=200
import { useState, useEffect } from "react";

let running = 0;

export default function App() {
  const [ticks, setTicks] = useState(0);
  const [speed, setSpeed] = useState(1000);

  useEffect(() => {
    running = running + 1;
    setInterval(() => setTicks((t) => t + 1), speed);
    // no cleanup: the old interval keeps going!
  }, [speed]);

  return (
    <div>
      <p>Ticks: {ticks}</p>
      <button onClick={() => setSpeed(1000)}>Slow</button>{" "}
      <button onClick={() => setSpeed(500)}>Fast</button>{" "}
      <button onClick={() => setSpeed(speed === 999 ? 1000 : 999)}>Change speed</button>
      <p style={{ color: "#b91c1c" }}>Intervals started so far: {running}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Each time `speed` changes, the effect starts a **new** interval, but the old ones are never stopped. After three changes, four intervals are adding to `ticks` at once, so the counter speeds up wildly.
- This is a **leak**. In a real app it might be several chat connections, duplicated event handlers or requests that never stop.
- The fix is one line: keep the id and return `() => clearInterval(id)`. React then stops the old interval **before** starting the new one.
- (The red counter is updated as a side effect of rendering, which is only acceptable in a demo like this.)

</En>
<Ur>

- Har dafa `speed` badalne par effect **naya** interval shuru karta hai, magar purane kabhi nahi rukte. Teen tabdeeliyon ke baad chaar intervals ek saath `ticks` me jor rahe hote hain, isliye counter be-qaboo tez ho jata hai.
- Ye **leak** hai. Asli app me ye kai chat connections, dohre event handlers ya kabhi na rukne wali requests ho sakti hain.
- Hal ek line ka hai: id rakhein aur `() => clearInterval(id)` wapas karein. Phir React naya interval shuru karne se **pehle** purana rok deta hai.
- (Laal counter render ke side effect ki shakal me update hota hai, jo sirf aisi demo me qabil-e-qubool hai.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Listening to browser events">

<Tr>
<En>
Events on the whole window or document (key presses, scrolling, resizing) don't come through JSX props. Add the listener in an effect and **remove it** in the cleanup. Click inside the result box once, then press some keys.
</En>
<Ur>
Poori window ya document ke events (keys dabana, scroll, size badalna) JSX props se nahi aate. Listener effect me jorein aur cleanup me **hata dein**. Result ke dabbe ke andar ek dafa click karein, phir kuch keys dabayen.
</Ur>
</Tr>

```jsx preview h=150
import { useState, useEffect } from "react";

export default function App() {
  const [lastKey, setLastKey] = useState("none yet");
  const [count, setCount] = useState(0);

  useEffect(() => {
    function handleKeyDown(event) {
      setLastKey(event.key);
      setCount((c) => c + 1);
    }
    window.addEventListener("keydown", handleKeyDown);
    return () => window.removeEventListener("keydown", handleKeyDown);
  }, []);

  return (
    <div>
      <p>Last key pressed: <strong>{lastKey}</strong></p>
      <p>Keys pressed: {count}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- The effect adds **one** listener when the component appears. Every key press updates two pieces of state.
- The cleanup removes **the same function** with `removeEventListener`. It must be the same function object, which is why `handleKeyDown` is defined inside the effect and used in both places.
- `[]` means: add once, remove when the component goes away. Without cleanup, a component that appears and disappears repeatedly would pile up listeners.
- Real uses: keyboard shortcuts, closing a menu with Escape, tracking scroll position.

</En>
<Ur>

- Component aane par effect **ek** listener jorta hai. Har key dabana state ke do hisse update karta hai.
- Cleanup `removeEventListener` se **wahi function** hatata hai. Ye wahi function object hona chahiye, isi liye `handleKeyDown` effect ke andar bana hai aur dono jagah istemal hota hai.
- `[]` ka matlab: ek dafa jorna, component jaye to hatana. Cleanup ke baghair baar baar aane jane wala component listeners ka dher laga deta.
- Asli istemal: keyboard shortcuts, Escape se menu band karna, scroll ki jagah ka hisaab.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The stale value trap">

<Tr>
<En>
An effect's function is a **closure**: it remembers the values from the render in which it was created. With `[]`, it's created only once, so it keeps seeing the **first** render's values forever. Watch the left counter.
</En>
<Ur>
Effect ka function ek **closure** hai: wo us render ki values yaad rakhta hai jis me wo bana. `[]` ke saath ye sirf ek dafa banta hai, isliye hamesha **pehle** render ki values dekhta rehta hai. Baayan counter dekhein.
</Ur>
</Tr>

```jsx preview h=150
import { useState, useEffect } from "react";

function StaleCounter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>Stale: {count}</p>;
}

function FreshCounter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount((c) => c + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>Fresh: {count}</p>;
}

export default function App() {
  return (
    <div style={{ display: "flex", gap: 40, fontSize: 20 }}>
      <StaleCounter />
      <FreshCounter />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **Stale** goes to 1 and stops there. The interval was created during the first render, when `count` was `0`, so every tick runs `setCount(0 + 1)`.
- **Fresh** keeps counting. The updater `(c) => c + 1` asks React for the **current** value each time, so the closure doesn't need to remember `count` at all.
- The other fix is to list `count` as a dependency, which recreates the interval on every change. The updater is simpler here.
- The editor rule `react-hooks/exhaustive-deps` warns about exactly this: a value used inside an effect but missing from its array.

</En>
<Ur>

- **Stale** 1 tak jata hai aur wahin ruk jata hai. Interval pehle render me bana, jab `count` `0` tha, isliye har tick `setCount(0 + 1)` chalata hai.
- **Fresh** ginta rehta hai. Updater `(c) => c + 1` har dafa React se **maujooda** value maangta hai, isliye closure ko `count` yaad rakhne ki zaroorat hi nahi.
- Doosra hal `count` ko dependency me likhna hai, jo har tabdeeli par interval dobara banata hai. Yahan updater zyada aasan hai.
- Editor ka qaida `react-hooks/exhaustive-deps` bilkul is par khabardar karta hai: effect ke andar istemal hui value jo array me na ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Loading data in an effect">

<Tr>
<En>
A component often needs data when it appears or when an id changes. The effect starts the request; state holds the result and a loading flag. Effects can't be `async` themselves, so define an async function inside and call it. Here `fetchUser` is a pretend server that answers after a short delay.
</En>
<Ur>
Component ko aksar data tab chahiye hota hai jab wo aaye ya jab id badle. Effect request shuru karta hai; state nateeja aur loading ka nishaan rakhti hai. Effects khud `async` nahi ho sakte, isliye andar async function bana kar call karein. Yahan `fetchUser` naqli server hai jo thori der baad jawab deta hai.
</Ur>
</Tr>

```jsx preview h=200
import { useState, useEffect } from "react";

const USERS = {
  1: { name: "Sara Lee", city: "Austin" },
  2: { name: "Alex Kim", city: "Denver" },
  3: { name: "Emma Stone", city: "Boston" },
};

function fetchUser(id) {
  return new Promise((resolve) => setTimeout(() => resolve(USERS[id]), 600));
}

function Profile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    async function load() {
      setLoading(true);
      const data = await fetchUser(userId);
      setUser(data);
      setLoading(false);
    }
    load();
  }, [userId]);

  if (loading) return <p>Loading user {userId}…</p>;
  return <p><strong>{user.name}</strong> lives in {user.city}.</p>;
}

export default function App() {
  const [userId, setUserId] = useState(1);
  return (
    <div>
      {[1, 2, 3].map((id) => (
        <button key={id} onClick={() => setUserId(id)} style={{ marginRight: 6, fontWeight: id === userId ? 700 : 400 }}>
          User {id}
        </button>
      ))}
      <Profile userId={userId} />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- When `Profile` appears, the effect runs with `userId = 1`: it shows "Loading…", waits for the data, then shows the user.
- Click **User 2**: `userId` changes, so the effect runs again and loads the new user. That's what `[userId]` is for: **keep the profile in sync with the id**.
- `useEffect(async () => …)` isn't allowed, because an async function returns a promise, and React expects the effect to return either nothing or a cleanup function.
- This version has a hidden bug when answers arrive in a different order. The next step shows it.

</En>
<Ur>

- `Profile` aane par effect `userId = 1` ke saath chalta hai: "Loading…" dikhata hai, data ka intezar karta hai, phir user dikhata hai.
- **User 2** click karein: `userId` badalta hai, isliye effect phir chalta hai aur naya user load karta hai. `[userId]` isi liye hai: **profile ko id ke saath mel me rakhna**.
- `useEffect(async () => …)` ki ijazat nahi, kyun ke async function promise wapas karta hai, aur React effect se ya to kuch nahi ya cleanup function ki umeed karta hai.
- Is version me ek chhupa bug hai jab jawab alag tarteeb me aayen. Agla qadam use dikhata hai.

</Ur>
</Tr>

<Step title="Race conditions: ignore old answers">

<Tr>
<En>
Here user 1's server is **slow** (2 seconds) and the others are fast. Click **User 1** and then, quickly, **User 2**, in both panels. Wait two seconds and compare.
</En>
<Ur>
Yahan user 1 ka server **sust** hai (2 seconds) aur baqi tez. Dono panels me **User 1** aur phir jaldi se **User 2** click karein. Do second intezar karein aur muqabla karein.
</Ur>
</Tr>

```jsx preview h=230
import { useState, useEffect } from "react";

const USERS = { 1: "Sara Lee", 2: "Alex Kim", 3: "Emma Stone" };

function fetchUser(id) {
  const delay = id === 1 ? 2000 : 300;
  return new Promise((resolve) => setTimeout(() => resolve(USERS[id]), delay));
}

function BuggyProfile({ userId }) {
  const [name, setName] = useState("…");
  useEffect(() => {
    fetchUser(userId).then((result) => setName(result));
  }, [userId]);
  return <p>Buggy — selected {userId}, showing: <strong>{name}</strong></p>;
}

function SafeProfile({ userId }) {
  const [name, setName] = useState("…");
  useEffect(() => {
    let ignore = false;
    fetchUser(userId).then((result) => {
      if (!ignore) setName(result);
    });
    return () => {
      ignore = true;
    };
  }, [userId]);
  return <p>Safe — selected {userId}, showing: <strong>{name}</strong></p>;
}

function Picker({ Profile }) {
  const [userId, setUserId] = useState(3);
  return (
    <div style={{ marginBottom: 8 }}>
      {[1, 2, 3].map((id) => (
        <button key={id} onClick={() => setUserId(id)} style={{ marginRight: 6 }}>User {id}</button>
      ))}
      <Profile userId={userId} />
    </div>
  );
}

export default function App() {
  return (
    <div>
      <Picker Profile={BuggyProfile} />
      <Picker Profile={SafeProfile} />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **Buggy:** you selected user 2, and Alex appeared after 0.3 seconds. But user 1's slow answer was still on its way; when it arrived at 2 seconds, it **overwrote** Alex with Sara. The screen now says "selected 2, showing Sara Lee".
- **Safe:** each effect run has its own `ignore` variable. When `userId` changed, React ran the **cleanup** of the previous run, setting **its** `ignore` to `true`. So when user 1's late answer arrived, it was thrown away.
- This is a **race condition**: two requests racing, the slower one finishing last. It happens on real networks all the time (search boxes, tabs, pagination).
- Data libraries such as TanStack Query, SWR, and Next.js server components handle this for you, which is one reason they're recommended over hand-written fetching effects.

</En>
<Ur>

- **Buggy:** aap ne user 2 chuna, aur Alex 0.3 second baad aa gaya. Magar user 1 ka sust jawab abhi raste me tha; jab wo 2 second par pohancha to us ne Alex ki jagah Sara **likh di**. Screen ab kehti hai "selected 2, showing Sara Lee".
- **Safe:** effect ki har dafa ki apni `ignore` variable hai. Jab `userId` badla, React ne pichhli dafa ka **cleanup** chalaya, jis ne **us ka** `ignore` `true` kar diya. Isliye jab user 1 ka der se aaya jawab pohancha to use phenk diya gaya.
- Ye **race condition** hai: do requests ki daud, sust wali aakhir me khatam. Asli networks par ye hamesha hota hai (search boxes, tabs, pagination).
- TanStack Query, SWR aur Next.js server components jaisi data libraries ye aap ke liye sambhalti hain, yahi ek wajah hai ke haath se likhe fetching effects ke bajaye inki tajweez di jati hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Infinite loops">

<Tr>
<En>
An effect that **sets state** causes a re-render. If the effect then runs again after that render and sets state again, you've built a loop that never stops. These are the three usual causes.
</En>
<Ur>
Jo effect **state set** kare wo dobara render karata hai. Agar us render ke baad effect phir chale aur phir state set kare, to aap ne kabhi na rukne wala loop bana diya. Ye teen aam wajahen hain.
</Ur>
</Tr>

```text
// 1. No dependency array: runs after every render, and sets state every time
useEffect(() => {
  setCount(count + 1);
});

// 2. Depends on the state it changes
useEffect(() => {
  setItems([...items, "new"]);
}, [items]);

// 3. An object or array created during render as a dependency
const options = { sort: "name" };          // a NEW object on every render
useEffect(() => {
  fetchList(options).then(setList);        // sets state → re-render → new options → runs again
}, [options]);
```

<Happened>
<Tr>
<En>

- **1:** render → effect → `setCount` → render → effect → … forever. The page freezes or React stops with "Maximum update depth exceeded".
- **2:** setting `items` changes `items`, which re-runs the effect, which changes `items` again.
- **3:** `{ sort: "name" }` looks the same each time, but it's a **new object** on every render, and dependencies are compared with `Object.is`. Fix it by depending on the primitive (`[sort]`), or moving the object inside the effect.
- Before writing `setSomething` inside an effect, ask: "Could this be calculated during render instead?" Usually it can.

</En>
<Ur>

- **1:** render → effect → `setCount` → render → effect → … hamesha. Page jam jata hai ya React "Maximum update depth exceeded" ke saath ruk jata hai.
- **2:** `items` set karna `items` badalta hai, jo effect dobara chalata hai, jo phir `items` badalta hai.
- **3:** `{ sort: "name" }` har dafa ek jaisa dikhta hai, magar har render par **naya object** hai, aur dependencies `Object.is` se mili jati hain. Hal: primitive par munhasir karein (`[sort]`), ya object effect ke andar le jayen.
- Effect ke andar `setSomething` likhne se pehle poochein: "Kya ise render ke dauran nikala ja sakta hai?" Aam taur par haan.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="You might not need an effect">

<Tr>
<En>
Effects are for talking to things **outside** React. A very common mistake is using them for things React already handles: calculating values and responding to user actions.
</En>
<Ur>
Effects React se **bahar** ki cheezon se baat karne ke liye hain. Bohot aam ghalti inhe un kaamon ke liye istemal karna hai jo React pehle se sambhalta hai: values nikalna aur user ke kaamon ka jawab dena.
</Ur>
</Tr>

```jsx preview h=200
import { useState } from "react";

export default function App() {
  const [firstName, setFirstName] = useState("Sara");
  const [lastName, setLastName] = useState("Lee");
  const [message, setMessage] = useState("");

  // Calculated during render: no effect, no extra state
  const fullName = (firstName + " " + lastName).trim();

  // Responds to a click: put it in the handler, not in an effect
  function handleSave() {
    setMessage("Saved " + fullName + " at the moment you clicked.");
  }

  return (
    <div style={{ display: "grid", gap: 8, maxWidth: 300 }}>
      <input value={firstName} onChange={(e) => setFirstName(e.target.value)} />
      <input value={lastName} onChange={(e) => setLastName(e.target.value)} />
      <p>Full name: <strong>{fullName}</strong></p>
      <button onClick={handleSave}>Save</button>
      <p>{message}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- `fullName` updates instantly as you type, with **no effect**. The tempting version, `useEffect(() => setFullName(first + " " + last), [first, last])`, renders twice per keystroke (once stale, once correct) and adds a state variable that can go out of sync.
- Saving happens because the user **clicked**, so it belongs in `handleSave`. If you set a flag and react to it in an effect, the save can fire again on unrelated re-renders, or twice in Strict Mode.
- A useful test: **"Does this code run because the component is showing, or because the user did something?"** Showing → maybe an effect. User action → event handler.

</En>
<Ur>

- `fullName` type karte hi foran update hota hai, **baghair effect** ke. Lalchane wala version, `useEffect(() => setFullName(first + " " + last), [first, last])`, har key par do dafa render karta hai (ek dafa purana, ek dafa sahi) aur aisi state variable jorta hai jo be-mel ho sakti hai.
- Save is liye hota hai ke user ne **click** kiya, isliye ye `handleSave` me hai. Agar aap nishaan set kar ke effect me us ka jawab dein to save ghair mutaliq renders par phir chal sakta hai, ya Strict Mode me do dafa.
- Mufeed test: **"Kya ye code is liye chalta hai ke component dikh raha hai, ya is liye ke user ne kuch kiya?"** Dikh raha hai → shayad effect. User ka kaam → event handler.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Why effects run twice in development">

<Tr>
<En>
In development, `<StrictMode>` (on by default in Next.js and Vite templates) makes React **mount, unmount and mount again** every component the first time it appears. So every effect runs, cleans up, and runs again. It's a test, not a bug.
</En>
<Ur>
Development me `<StrictMode>` (Next.js aur Vite templates me default chalu) React se har component ko pehli dafa aate waqt **mount, unmount aur dobara mount** karwata hai. Isliye har effect chalta hai, safai karta hai, aur phir chalta hai. Ye test hai, bug nahi.
</Ur>
</Tr>

```text
Development, with Strict Mode            Production
---------------------------------        ----------------
timer started                            timer started
timer stopped (cleanup)
timer started
```

<Happened>
<Tr>
<En>

- If your effect has a correct cleanup, running it twice changes nothing the user can see: the first timer is stopped before the second starts.
- If something breaks (two chat connections, a request sent twice, a listener added twice), Strict Mode has found a **missing cleanup** before your users did.
- Don't "fix" it by removing Strict Mode or by using a flag to stop the second run. Fix the cleanup. For requests, the `ignore` pattern (or a data library) makes the duplicate harmless.

</En>
<Ur>

- Agar aap ke effect ka cleanup durust hai to use do dafa chalana user ko nazar aane wali koi cheez nahi badalta: doosra timer shuru hone se pehle pehla ruk jata hai.
- Agar kuch toot jaye (do chat connections, do dafa bheji gayi request, do dafa jora gaya listener) to Strict Mode ne aap ke users se pehle **ghayab cleanup** pakar liya.
- Ise Strict Mode hata kar ya doosri dafa rokne wale nishaan se "theek" na karein. Cleanup theek karein. Requests ke liye `ignore` namoona (ya data library) dohre ko be-zarar bana deta hai.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="An async effect function">

```jsx
useEffect(async () => {
  const data = await fetchUser(id);
  setUser(data);
}, [id]);
```

</Bad>
<Good title="Async function inside, with an ignore flag">

```jsx
useEffect(() => {
  let ignore = false;
  async function load() {
    const data = await fetchUser(id);
    if (!ignore) setUser(data);
  }
  load();
  return () => { ignore = true; };
}, [id]);
```

</Good>
</Compare>

<Compare>
<Bad title="Missing cleanup">

```jsx
useEffect(() => {
  window.addEventListener("resize", onResize);
}, []);
```

</Bad>
<Good title="Remove what you add">

```jsx
useEffect(() => {
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize);
}, []);
```

</Good>
</Compare>

<Compare>
<Bad title="Leaving out a dependency">

```jsx
useEffect(() => {
  connect(roomId);
}, []);   // roomId changes, but the old room stays connected
```

</Bad>
<Good title="List every value the effect uses">

```jsx
useEffect(() => {
  const connection = connect(roomId);
  return () => connection.close();
}, [roomId]);
```

</Good>
</Compare>

<Compare>
<Bad title="An effect for derived data">

```jsx
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(items.reduce((s, i) => s + i.price, 0));
}, [items]);
```

</Bad>
<Good title="Calculate during render">

```jsx
const total = items.reduce((s, i) => s + i.price, 0);
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Setting state in an effect with no dependency array**: an infinite loop.
- **Objects or functions created during render as dependencies**: they're new every time, so the effect runs every time.
- **Running user-action logic in an effect** (sending analytics, posting a form) instead of the event handler.
- **Silencing the dependency lint rule** instead of fixing the cause.
- **Fetching in many components with hand-written effects**, with no caching or error handling. Use a data library or server components for real apps.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Dependency array ke baghair effect me state set karna**: kabhi na khatam hone wala loop.
- **Render ke dauran bane objects ya functions dependencies me**: ye har dafa naye hote hain, isliye effect har dafa chalta hai.
- **User ke kaam wali logic effect me chalana** (analytics bhejna, form post karna) event handler ke bajaye.
- **Dependency lint rule ko chup karana** wajah theek karne ke bajaye.
- **Kai components me haath se likhe effects se fetch karna**, baghair caching ya error handling ke. Asli apps ke liye data library ya server components lein.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- `useEffect` runs code **after** the screen updates, for things outside React: timers, listeners, connections, data loading.
- No array: after every render. `[]`: once on mount. `[a, b]`: on mount and whenever `a` or `b` changes.
- Return a **cleanup** to undo the effect; React runs it before re-running and on unmount.
- List every value the effect uses as a dependency, or use updater functions to avoid stale values.
- Effects can't be `async`; call an async function inside, and ignore results from outdated runs.
- Setting state in an effect can loop; avoid object dependencies created during render.
- Don't use effects for derived values or user actions. Calculate during render; handle clicks in handlers.
- Strict Mode runs effects twice in development to catch missing cleanups.

</En>
<Ur>

- `useEffect` screen update hone ke **baad** React se bahar ki cheezon ke liye code chalata hai: timers, listeners, connections, data loading.
- Array nahi: har render ke baad. `[]`: mount par ek dafa. `[a, b]`: mount par aur jab bhi `a` ya `b` badle.
- Effect wapas karne ke liye **cleanup** wapas karein; React ise dobara chalane se pehle aur unmount par chalata hai.
- Effect jo bhi value istemal kare use dependency me likhein, ya purani values se bachne ke liye updater functions lein.
- Effects `async` nahi ho sakte; andar async function call karein, aur purani dafa ke nateeje nazar andaz karein.
- Effect me state set karna loop bana sakta hai; render ke dauran bane objects ko dependencies na banayen.
- Derived values ya user ke kaamon ke liye effects na lein. Render ke dauran nikalein; clicks handlers me sambhalein.
- Strict Mode development me ghayab cleanups pakarne ke liye effects do dafa chalata hai.

</Ur>
</Tr>

<DeepDive title="Effects in more detail">

**Think "synchronise", not "lifecycle".** Older class components had `componentDidMount` and `componentDidUpdate`. With effects, it's simpler to think: "this effect keeps something outside React **in sync** with these values". Start syncing, stop syncing; React decides when.

**Timing.** Effects run after the browser has painted. `useLayoutEffect` runs after the DOM is updated but **before** paint, for measuring sizes and positions without a visible flicker. It blocks painting, so use it only when needed.

**Dependencies are compared with `Object.is`.** Primitives compare by value; objects, arrays and functions by reference. To keep a function or object stable between renders, move it inside the effect, outside the component, or wrap it in `useCallback` / `useMemo` (next lesson).

**`AbortController` for fetches.** Instead of (or in addition to) an `ignore` flag, you can actually cancel the request:

```text
useEffect(() => {
  const controller = new AbortController();
  fetch("/api/users/" + id, { signal: controller.signal })
    .then((r) => r.json())
    .then(setUser)
    .catch((e) => { if (e.name !== "AbortError") setError(e); });
  return () => controller.abort();
}, [id]);
```

**Resetting state when a prop changes.** Instead of `useEffect(() => setComment(""), [postId])`, render `<CommentBox key={postId} />`; a new key gives a fresh component with fresh state.

**Data fetching in practice.** Hand-written fetching effects lack caching, deduplication, retries and background refresh. TanStack Query (`useQuery`), SWR, or server components in Next.js (`await` data directly in the component on the server) are the usual choices in real apps.

**`useEffectEvent`** (React 19.2+) lets an effect call a function that always sees the latest props and state without adding it to the dependencies, for example logging the current theme when a chat connects.

**Custom hooks.** Repeated effects are extracted into functions such as `useInterval(callback, delay)`, `useWindowSize()` or `useOnlineStatus()`, which keeps components short.

</DeepDive>

<DeepDive title="Real world: the search box that charged for every keystroke">

A team built a product search that called a paid search API:

```jsx
useEffect(() => {
  searchApi(query).then(setResults);
}, [query]);
```

It worked in testing. In production, the bill for the search API was several times the forecast. Every keystroke changed `query`, so typing "running shoes" sent **13** requests. Worse, responses for "run" sometimes arrived after "running shoes", so users saw results that didn't match the box (a race condition).

The fix combined three ideas from this lesson:

1. **Debounce:** wait until the user stops typing for 300 ms before searching. That's an effect with a `setTimeout` and a cleanup that cancels it when `query` changes again.
2. **Ignore or abort stale requests** in the cleanup.
3. **Skip empty or very short queries.**

```jsx
useEffect(() => {
  if (query.trim().length < 2) return;
  const controller = new AbortController();
  const timer = setTimeout(() => {
    searchApi(query, { signal: controller.signal }).then(setResults).catch(() => {});
  }, 300);
  return () => {
    clearTimeout(timer);
    controller.abort();
  };
}, [query]);
```

Requests dropped by about 80%, and stale results disappeared. Later the team moved to TanStack Query, which added caching so going back to a previous search was instant.

</DeepDive>

<DeepDive title="Security lens">

Effects are where components talk to the network and the browser, so that's where care is needed.

- **Don't put secrets in client-side fetches.** An effect that calls a third-party API with an API key exposes the key to every visitor. Call your own server, which holds the key.
- **Validate fetched data** before putting it in state and rendering it. An API that returns HTML for a `bio` field is safe to show with `{bio}` (escaped), but not with `dangerouslySetInnerHTML`.
- **Clean up subscriptions.** Leaked listeners and sockets can keep receiving data for a user who has logged out, and show it to the next person on a shared computer. Close connections in cleanups and on logout.
- **Race conditions can show the wrong person's data.** On an admin screen that switches between customers, a late response for customer A arriving after you selected customer B can lead to actions on the wrong record. Use the `ignore`/abort pattern, and include the record id in any action you send.
- **`postMessage` and storage events.** If an effect listens for `message` events from other windows, always check `event.origin` before trusting the data.
- **Rate limiting.** Effects that fire on every keystroke or re-render can hammer your own API. Debounce on the client, and enforce limits on the server anyway.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is useEffect used for?">
It runs side effects after React commits a render: synchronising with systems outside React such as timers, subscriptions, browser events, network connections and non-React libraries. Rendering itself should stay pure, so this kind of code belongs in effects or event handlers.
</QA>

<QA q="Explain the dependency array.">
It lists the reactive values the effect uses. With no array the effect runs after every render; with an empty array it runs once after mount; with values it runs after mount and whenever any of them changes, compared with Object.is. Leaving out a value the effect uses causes stale closures.
</QA>

<QA q="What is the cleanup function and when does it run?">
It is the function returned from the effect. React calls it before running the effect again because dependencies changed, and when the component unmounts. It should undo whatever the effect set up, such as clearing intervals, removing listeners or closing connections.
</QA>

<QA q="Why do effects run twice in development?">
React Strict Mode mounts, unmounts and remounts components in development to verify that effects clean up correctly. A correct effect with proper cleanup behaves the same; the double run exposes leaks. It does not happen in production.
</QA>

<QA q="How do you fetch data in useEffect correctly?">
Define and call an async function inside the effect, store loading, data and error in state, list the inputs such as the id as dependencies, and in the cleanup either set an ignore flag or abort the request so outdated responses are not applied. In production apps a data-fetching library or server components are usually preferable.
</QA>

<QA q="What is a stale closure in an effect?">
The effect's function captures props and state from the render in which it was created. If it keeps running, for example in an interval, after those values change but the effect is not re-created, it uses outdated values. Fix it by listing the dependencies or using functional state updates.
</QA>

<QA q="When should you not use useEffect?">
For values that can be computed from props and state during render, for responding to user events which belong in event handlers, and for resetting state when a prop changes, which can be done with a key. Unnecessary effects cause extra renders and synchronisation bugs.
</QA>

</DeepDive>
