<BigIdea>
<Tr>
<En>
A component is a function that React calls to draw part of the screen. If you just change a normal variable, React doesn't know anything happened, and the screen stays the same. **State** is the component's **memory**: a value React keeps for you between draws. You create it with the **`useState`** hook: `const [count, setCount] = useState(0);`. You get two things: the **current value** (`count`) and a **setter function** (`setCount`). Calling the setter with a new value tells React "this changed", and React **re-renders**: it calls your component again, now with the new value, and updates the page. Two rules make state work: **always change it through the setter**, and for objects and arrays, give the setter a **new** object or array rather than changing the old one.
</En>
<Ur>
Component aisa function hai jise React screen ka hissa banane ke liye call karta hai. Agar aap sirf aam variable badal dein to React ko pata hi nahi chalta ke kuch hua, aur screen waisi ki waisi rehti hai. **State** component ki **yaad dasht** hai: aisi value jo React aap ke liye har dafa banane ke darmiyan sambhal kar rakhta hai. Ise **`useState`** hook se banaya jata hai: `const [count, setCount] = useState(0);`. Aap ko do cheezen milti hain: **maujooda value** (`count`) aur **setter function** (`setCount`). Setter ko nayi value ke saath call karna React ko batata hai "ye badal gaya", aur React **dobara render** karta hai: aap ka component nayi value ke saath phir call karta hai aur page update kar deta hai. State do qawaid se chalti hai: **ise hamesha setter se badlein**, aur objects aur arrays ke liye setter ko purane ko badalne ke bajaye **naya** object ya array dein.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
```

Read the first line of the component as: **"Give me a remembered value called `count`, starting at 0, and a function `setCount` to change it."**

</En>
<Ur>

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
```

Component ki pehli line ko aise parhein: **"Mujhe `count` naam ki yaad rakhi jane wali value do, jo 0 se shuru ho, aur use badalne ke liye `setCount` function."**

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Interactivity.** Everything a user can change needs state: what's typed in a box, whether a menu is open, which tab is selected, what's in the cart.
- **The screen follows the data.** You never update the page by hand. You change state; React redraws what depends on it.
- **Each component remembers its own things.** Two counters on a page count separately.
- **Fewer bugs.** Because React redraws from the current state, the screen can't get "out of sync" with your data.

</En>
<Ur>

- **Interactivity.** Har wo cheez jo user badal sake state chahti hai: box me kya likha hai, menu khula hai ya nahi, kaun sa tab chuna hai, cart me kya hai.
- **Screen data ke peechhe chalti hai.** Aap page haath se kabhi update nahi karte. State badalte hain; jo us par munhasir hai React use dobara bana deta hai.
- **Har component apni cheezen yaad rakhta hai.** Page par do counters alag alag ginte hain.
- **Kam bugs.** Chunke React maujooda state se dobara banata hai, screen aap ke data se "be-mel" nahi ho sakti.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Use state for a value that:

- **changes** while the page is open, **and**
- should **change what's on screen**, **and**
- **can't be calculated** from props or other state.

If a value never changes, use a normal `const`. If it can be calculated (a total from a cart), calculate it during render instead of storing it.

</En>
<Ur>

State aisi value ke liye lein jo:

- page khula hone ke dauran **badalti** ho, **aur**
- **screen par dikhne wali cheez badle**, **aur**
- props ya doosri state se **nikali na ja sake**.

Agar value kabhi nahi badalti to aam `const` lein. Agar nikali ja sakti ho (cart se total) to use mehfooz karne ke bajaye render ke dauran nikal lein.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```jsx
const [name, setName] = useState("");            // text
const [isOpen, setIsOpen] = useState(false);     // yes / no
const [items, setItems] = useState([]);          // list

setName("Sara");                                  // new value
setIsOpen((open) => !open);                       // based on the previous value
setItems((list) => [...list, "Pen"]);             // a NEW array
```

</En>
<Ur>

```jsx
const [name, setName] = useState("");            // text
const [isOpen, setIsOpen] = useState(false);     // haan / nahi
const [items, setItems] = useState([]);          // list

setName("Sara");                                  // nayi value
setIsOpen((open) => !open);                       // pichhli value par mabni
setItems((list) => [...list, "Pen"]);             // NAYI array
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Imagine your component is a **painter** who paints a picture of the screen, and **state** is a **whiteboard** on the wall that the painter reads before every painting.

- A normal variable is like a note the painter scribbles **while** painting. When the painting is done, the note is thrown away; the next painting starts from scratch.
- State is written on the whiteboard, which **stays** between paintings.
- The **setter** is the only marker allowed to write on the whiteboard. Writing with it also rings a bell: "something changed, paint again!" The painter reads the new value and paints a fresh picture.
- If you sneak up and change the whiteboard with your finger (mutating state directly), no bell rings, so nobody repaints, and the picture on the wall is out of date.

</En>
<Ur>

Sochein aap ka component ek **painter** hai jo screen ki tasveer banata hai, aur **state** deewar par laga **whiteboard** hai jise painter har tasveer se pehle parhta hai.

- Aam variable us note jaisa hai jo painter tasveer banate **waqt** ghaseet leta hai. Tasveer khatam hote hi note phenk diya jata hai; agli tasveer shuru se banti hai.
- State whiteboard par likhi hai, jo tasveeron ke darmiyan **qaim** rehti hai.
- **Setter** wahid marker hai jis se whiteboard par likhne ki ijazat hai. Is se likhna ghanti bhi bajata hai: "kuch badla, dobara banao!" Painter nayi value parhta hai aur nayi tasveer banata hai.
- Agar aap chupke se ungli se whiteboard badal dein (state ko seedha mutate karna), koi ghanti nahi bajti, isliye koi dobara nahi banata, aur deewar wali tasveer purani reh jati hai.

</Ur>
</Tr>

<Walkthrough>

<Step title="Why a normal variable isn't enough">

<Tr>
<En>
Let's try the obvious thing first: a `let` variable that goes up on every click. Click the button a few times.
</En>
<Ur>
Pehle seedhi cheez aazmate hain: `let` variable jo har click par barhe. Button kuch dafa click karein.
</Ur>
</Tr>

```jsx preview h=110
export default function App() {
  let count = 0;

  function handleClick() {
    count = count + 1;
  }

  return <button onClick={handleClick}>Clicked {count} times</button>;
}
```

<Happened>
<Tr>
<En>

- The button always says **"Clicked 0 times"**, however much you click.
- Two problems. First, changing `count` doesn't tell React anything, so React never redraws.
- Second, even if React did redraw, it would call `App()` again, which runs `let count = 0` again. A normal variable is created fresh on every render and forgets everything.
- We need a value that **survives** between renders **and** tells React to redraw when it changes. That's state.

</En>
<Ur>

- Button hamesha **"Clicked 0 times"** kehta hai, aap jitna bhi click karein.
- Do masle hain. Pehla, `count` badalne se React ko kuch pata nahi chalta, isliye React kabhi dobara nahi banata.
- Doosra, agar React dobara bana bhi deta to wo `App()` phir call karta, jo `let count = 0` phir chalata. Aam variable har render par naya banta hai aur sab bhool jata hai.
- Hamen aisi value chahiye jo renders ke darmiyan **bachi** rahe **aur** badalne par React ko dobara banane ka kahe. Yahi state hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="useState: a value React remembers">

<Tr>
<En>
Import `useState` from React and call it at the top of the component. It returns a pair, which we unpack with array destructuring: the current value and its setter.
</En>
<Ur>
React se `useState` import karein aur component ke upar call karein. Ye ek jora wapas karta hai, jise hum array destructuring se kholte hain: maujooda value aur us ka setter.
</Ur>
</Tr>

```jsx preview h=110
import { useState } from "react";

export default function App() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
  }

  return <button onClick={handleClick}>Clicked {count} times</button>;
}
```

<Happened>
<Tr>
<En>

Now each click works. Here's exactly what happens on one click:

1. You click. React runs `handleClick`, which calls `setCount(0 + 1)`.
2. React stores `1` as the new state and schedules a **re-render**.
3. React calls `App()` again. This time `useState(0)` ignores the `0` (it's only the **initial** value) and returns the stored `1`.
4. The JSX now says "Clicked 1 times", and React updates the button's text on the page.

- The names are your choice. The convention is `[thing, setThing]`.
- `count` is a `const`: you never assign to it. You ask React for a new value with the setter.

</En>
<Ur>

Ab har click kaam karta hai. Ek click par bilkul ye hota hai:

1. Aap click karte hain. React `handleClick` chalata hai, jo `setCount(0 + 1)` call karta hai.
2. React `1` ko nayi state ke taur par rakh leta hai aur **dobara render** muqarrar karta hai.
3. React `App()` phir call karta hai. Is dafa `useState(0)` `0` ko nazar andaz karta hai (wo sirf **shuruati** value hai) aur rakhi hui `1` wapas karta hai.
4. JSX ab "Clicked 1 times" kehta hai, aur React page par button ka text update kar deta hai.

- Naam aap ki marzi hain. Riwayat `[thing, setThing]` hai.
- `count` `const` hai: aap is me kabhi value nahi rakhte. Setter se React se nayi value maangte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Each component has its own state">

<Tr>
<En>
State belongs to **one copy** of a component on the page. Use the same component twice, and each copy remembers its own value.
</En>
<Ur>
State page par component ki **ek copy** ki hoti hai. Wahi component do dafa istemal karein, aur har copy apni value yaad rakhti hai.
</Ur>
</Tr>

```jsx preview h=150
import { useState } from "react";

function LikeCounter({ label }) {
  const [likes, setLikes] = useState(0);
  return (
    <p>
      {label}: {likes} likes{" "}
      <button onClick={() => setLikes(likes + 1)}>Like</button>
    </p>
  );
}

export default function App() {
  return (
    <div>
      <LikeCounter label="Notebook" />
      <LikeCounter label="Desk lamp" />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Click "Like" on the notebook three times: only the notebook's count goes up.
- Each `<LikeCounter />` on the page gets its own private `likes`. They don't share, even though they come from the same function.
- `{" "}` adds a space between the text and the button (JSX trims spaces at line breaks).

</En>
<Ur>

- Notebook ke "Like" par teen dafa click karein: sirf notebook ki ginti barhti hai.
- Page par har `<LikeCounter />` ko apna private `likes` milta hai. Ye share nahi karte, halanke ek hi function se bane hain.
- `{" "}` text aur button ke darmiyan space jorta hai (JSX line breaks par spaces kaat deta hai).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Text, true/false and other kinds of state">

<Tr>
<En>
State can hold any value. Two very common kinds: **text from an input** and a **yes/no toggle**. An input whose value comes from state, and which updates state on every keystroke, is called a **controlled input**.
</En>
<Ur>
State koi bhi value rakh sakti hai. Do bohot aam qismen: **input ka text** aur **haan/nahi toggle**. Aisa input jis ki value state se aaye aur jo har key dabane par state update kare, **controlled input** kehlata hai.
</Ur>
</Tr>

```jsx preview h=190
import { useState } from "react";

export default function App() {
  const [name, setName] = useState("");
  const [showTips, setShowTips] = useState(false);

  return (
    <div>
      <label>
        Your name:{" "}
        <input value={name} onChange={(e) => setName(e.target.value)} placeholder="Type here" />
      </label>
      <p>{name ? "Hello, " + name + "!" : "Please type your name."}</p>
      <p>{name.length} characters</p>

      <button onClick={() => setShowTips(!showTips)}>
        {showTips ? "Hide tips" : "Show tips"}
      </button>
      {showTips && <p>Tip: your name is never stored.</p>}
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Type in the box: the greeting and the character count update **with every key**.
- `onChange` runs on each keystroke; `e.target.value` is the input's current text. We store it with `setName`, and `value={name}` shows the stored text back in the box. React is now the single source of truth for that field.
- The toggle flips a boolean: `setShowTips(!showTips)`. `{showTips && …}` shows the tip only when it's `true`.

</En>
<Ur>

- Dabbe me type karein: salam aur characters ki ginti **har key ke saath** update hoti hai.
- `onChange` har key par chalta hai; `e.target.value` input ka maujooda text hai. Hum use `setName` se rakhte hain, aur `value={name}` rakha hua text dabbe me wapas dikhata hai. Ab us field ke sach ka wahid zariya React hai.
- Toggle boolean palat deta hai: `setShowTips(!showTips)`. `{showTips && …}` tip tabhi dikhata hai jab ye `true` ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="State is a snapshot">

<Tr>
<En>
Inside one render, a state value **never changes**. Calling the setter doesn't change the variable you're holding; it asks for a **new render** with a new value. So calling `setCount(count + 1)` three times in a row only adds one. Click both buttons and compare.
</En>
<Ur>
Ek render ke andar state ki value **kabhi nahi badalti**. Setter call karne se aap ke haath wala variable nahi badalta; ye nayi value ke saath **naye render** ki darkhwast karta hai. Isliye `setCount(count + 1)` teen dafa lagatar call karna sirf ek jorta hai. Dono buttons click kar ke muqabla karein.
</Ur>
</Tr>

```jsx preview h=150
import { useState } from "react";

export default function App() {
  const [count, setCount] = useState(0);

  function addThreeWrong() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  function addThreeRight() {
    setCount((c) => c + 1);
    setCount((c) => c + 1);
    setCount((c) => c + 1);
  }

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={addThreeWrong}>+3 (wrong)</button>{" "}
      <button onClick={addThreeRight}>+3 (right)</button>{" "}
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **+3 (wrong)** adds only **1**. During this render `count` is, say, `0`, so all three calls say "set it to `0 + 1`". Setting it to 1 three times is still 1.
- **+3 (right)** adds **3**. `setCount((c) => c + 1)` passes an **updater function**. React queues them and runs each with the result of the previous one: 0 → 1 → 2 → 3.
- Rule: when the new value **depends on the old one**, pass an updater: `setCount((c) => c + 1)`, `setIsOpen((open) => !open)`.

</En>
<Ur>

- **+3 (wrong)** sirf **1** jorta hai. Is render me `count` maslan `0` hai, isliye teeno calls kehti hain "ise `0 + 1` kar do". Use teen dafa 1 karna phir bhi 1 hai.
- **+3 (right)** **3** jorta hai. `setCount((c) => c + 1)` **updater function** deta hai. React inhe qataar me rakhta hai aur har ek ko pichhle ke nateeje ke saath chalata hai: 0 → 1 → 2 → 3.
- Qaida: jab nayi value **purani par munhasir** ho to updater dein: `setCount((c) => c + 1)`, `setIsOpen((open) => !open)`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Objects in state: replace, don't change">

<Tr>
<En>
State can be an object, such as a form with several fields. But React only re-renders when you give the setter a **different** object. If you change the existing object and pass it back, React sees "the same object as before" and does nothing.
</En>
<Ur>
State object bhi ho sakti hai, jaise kai fields wala form. Magar React tabhi dobara render karta hai jab aap setter ko **alag** object dein. Agar aap maujooda object badal kar wapas dein to React "pehle wala hi object" dekhta hai aur kuch nahi karta.
</Ur>
</Tr>

```jsx preview h=200
import { useState } from "react";

export default function App() {
  const [user, setUser] = useState({ name: "Sara", city: "Austin", plan: "free" });

  function upgradeWrong() {
    user.plan = "pro";
    setUser(user);
  }

  function upgradeRight() {
    setUser({ ...user, plan: "pro" });
  }

  return (
    <div>
      <p>{user.name} from {user.city} is on the <strong>{user.plan}</strong> plan.</p>
      <button onClick={upgradeWrong}>Upgrade (wrong)</button>{" "}
      <button onClick={upgradeRight}>Upgrade (right)</button>{" "}
      <button onClick={() => setUser({ ...user, plan: "free" })}>Back to free</button>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **Upgrade (wrong)** changes `user.plan` inside the existing object, then passes the **same** object to `setUser`. React compares old and new with `Object.is`, sees no change, and skips the re-render. The screen still says "free", even though the object secretly says "pro".
- **Upgrade (right)** creates a **new** object: `{ ...user, plan: "pro" }` copies every field, then overrides `plan`. A new object means a change, so React re-renders.
- Treat state as **read-only**. To change it, make a new version.

</En>
<Ur>

- **Upgrade (wrong)** maujooda object ke andar `user.plan` badalta hai, phir **wahi** object `setUser` ko deta hai. React purane aur naye ka `Object.is` se muqabla karta hai, koi tabdeeli nahi dekhta, aur render chhor deta hai. Screen ab bhi "free" kehti hai, halanke object chupke se "pro" kehta hai.
- **Upgrade (right)** **naya** object banata hai: `{ ...user, plan: "pro" }` har field copy karta hai, phir `plan` par nayi value rakhta hai. Naya object yaani tabdeeli, isliye React dobara render karta hai.
- State ko **sirf parhne wali** samjhein. Badalna ho to naya version banayen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A form with one state object">

<Tr>
<En>
A common pattern: keep all form fields in one object, and use a single change handler that reads the input's `name` attribute to know which field to update.
</En>
<Ur>
Aam namoona: form ki saari fields ek object me rakhein, aur ek hi change handler lein jo input ka `name` attribute parh kar jaane ke kaun si field update karni hai.
</Ur>
</Tr>

```jsx preview h=230
import { useState } from "react";

export default function App() {
  const [form, setForm] = useState({ name: "", email: "", size: "M" });

  function handleChange(e) {
    const { name, value } = e.target;
    setForm((prev) => ({ ...prev, [name]: value }));
  }

  return (
    <div style={{ display: "grid", gap: 8, maxWidth: 280 }}>
      <input name="name" value={form.name} onChange={handleChange} placeholder="Name" />
      <input name="email" value={form.email} onChange={handleChange} placeholder="Email" />
      <select name="size" value={form.size} onChange={handleChange}>
        <option>S</option>
        <option>M</option>
        <option>L</option>
      </select>
      <pre style={{ background: "#f3f4f6", padding: 8, margin: 0 }}>{JSON.stringify(form, null, 2)}</pre>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Type in either box or change the size: the box below shows the state object updating live.
- Each input has a `name` matching a key in `form`. In `handleChange`, `[name]: value` is a **computed key** (from the Objects lesson): it sets whichever field the input belongs to.
- `setForm((prev) => ({ ...prev, [name]: value }))` copies the previous form and changes one field. The updater form is the safe habit when building on the previous value.

</En>
<Ur>

- Kisi bhi dabbe me type karein ya size badlein: neeche wala dabba state object ko zinda update hota dikhata hai.
- Har input ka `name` `form` ki kisi key se milta hai. `handleChange` me `[name]: value` **computed key** hai (Objects lesson se): ye wahi field set karta hai jis ka input hai.
- `setForm((prev) => ({ ...prev, [name]: value }))` pichhla form copy karta hai aur ek field badalta hai. Pichhli value par banate waqt updater form mehfooz aadat hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Arrays in state: add, remove, update">

<Tr>
<En>
The same rule applies to arrays: never `push`, `splice` or assign to an index. Build a **new** array. You already know the three tools from the Arrays lesson: **spread** to add, **`filter`** to remove, **`map`** to change one item.
</En>
<Ur>
Arrays par bhi yahi qaida hai: kabhi `push`, `splice` ya index par value na rakhein. **Nayi** array banayen. Teeno auzaar aap Arrays lesson se jaante hain: jorne ke liye **spread**, hatane ke liye **`filter`**, ek item badalne ke liye **`map`**.
</Ur>
</Tr>

```jsx preview h=270
import { useState } from "react";

let nextId = 4;

export default function App() {
  const [todos, setTodos] = useState([
    { id: 1, text: "Buy milk", done: false },
    { id: 2, text: "Wash car", done: true },
    { id: 3, text: "Call Sam", done: false },
  ]);
  const [text, setText] = useState("");

  function add() {
    if (!text.trim()) return;
    setTodos([...todos, { id: nextId++, text: text.trim(), done: false }]);
    setText("");
  }

  function toggle(id) {
    setTodos(todos.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  function remove(id) {
    setTodos(todos.filter((t) => t.id !== id));
  }

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} placeholder="New task" />{" "}
      <button onClick={add}>Add</button>
      <ul>
        {todos.map((t) => (
          <li key={t.id}>
            <label style={{ textDecoration: t.done ? "line-through" : "none" }}>
              <input type="checkbox" checked={t.done} onChange={() => toggle(t.id)} /> {t.text}
            </label>{" "}
            <button onClick={() => remove(t.id)}>✕</button>
          </li>
        ))}
      </ul>
      <p>{todos.filter((t) => !t.done).length} left to do</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **Add:** `[...todos, newTodo]` is a new array with everything old plus the new item. Then the input is cleared with `setText("")`.
- **Tick a box:** `map` returns a new array where the matching todo is replaced by a **new object** with `done` flipped; every other item is kept as is.
- **✕:** `filter` returns a new array without that todo.
- "left to do" isn't stored anywhere: it's **calculated** from `todos` on every render, so it's always right. That's the next step's topic.

</En>
<Ur>

- **Add:** `[...todos, newTodo]` nayi array hai jis me purana sab aur naya item hai. Phir `setText("")` se input saaf hota hai.
- **Dabba tick karein:** `map` nayi array wapas karta hai jis me milne wala todo **naye object** se badal diya jata hai jis ka `done` palta hua hai; baqi har item waisa hi rehta hai.
- **✕:** `filter` us todo ke baghair nayi array wapas karta hai.
- "left to do" kahin mehfooz nahi: ye har render par `todos` se **nikala** jata hai, isliye hamesha durust hai. Agla qadam isi ke baare me hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Don't store what you can calculate">

<Tr>
<En>
If a value can be **worked out** from props or existing state, calculate it during render. Storing a copy in a second state means you must keep two things in sync, and sooner or later they won't be.
</En>
<Ur>
Agar koi value props ya maujooda state se **nikali** ja sakti ho to use render ke dauran nikalein. Doosri state me copy rakhne ka matlab hai do cheezon ko ek saath rakhna, aur der saver wo be-mel ho jati hain.
</Ur>
</Tr>

```jsx preview h=230
import { useState } from "react";

const PRODUCTS = [
  { id: 1, name: "Notebook", price: 5 },
  { id: 2, name: "Desk lamp", price: 30 },
  { id: 3, name: "Pen", price: 2 },
  { id: 4, name: "Backpack", price: 45 },
];

export default function App() {
  const [query, setQuery] = useState("");
  const [maxPrice, setMaxPrice] = useState(50);

  const visible = PRODUCTS.filter(
    (p) => p.name.toLowerCase().includes(query.toLowerCase()) && p.price <= maxPrice
  );
  const total = visible.reduce((sum, p) => sum + p.price, 0);

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} placeholder="Search" />{" "}
      <label>
        Max ${maxPrice}{" "}
        <input type="range" min="0" max="50" value={maxPrice} onChange={(e) => setMaxPrice(Number(e.target.value))} />
      </label>
      <ul>
        {visible.map((p) => (
          <li key={p.id}>{p.name} — ${p.price}</li>
        ))}
      </ul>
      <p>{visible.length} shown, worth ${total}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Only **two** things are state: what you typed and the slider position. That's what the user actually changes.
- `visible` and `total` are **derived**: recalculated from state on every render. Type "pen" or move the slider, and both are always correct.
- If you stored `visible` in its own state, you'd have to remember to update it whenever `query` **or** `maxPrice` **or** the product list changed. Calculating it removes that whole class of bug.
- Note `Number(e.target.value)`: inputs always give text, even range sliders (from the Data Types lesson).

</En>
<Ur>

- Sirf **do** cheezen state hain: jo aap ne type kiya aur slider ki jagah. User asal me yahi badalta hai.
- `visible` aur `total` **derived** hain: har render par state se dobara nikale jate hain. "pen" type karein ya slider hilayen, dono hamesha durust.
- Agar aap `visible` ko us ki apni state me rakhte to har dafa `query` **ya** `maxPrice` **ya** products ki list badalne par use update karna yaad rakhna parta. Nikalna is poori qisam ke bug ko khatam kar deta hai.
- `Number(e.target.value)` par dhyan dein: inputs hamesha text dete hain, range sliders bhi (Data Types lesson se).

</Ur>
</Tr>
</Happened>

<Step title="Sharing state: lift it up">

<Tr>
<En>
Two components that need the **same** state can't each own a copy. Move the state up to their closest **common parent**, and pass it down as props, along with a function to change it.
</En>
<Ur>
Do components jinhe **ek hi** state chahiye, dono apni copy nahi rakh sakte. State ko un ke sab se qareebi **mushtarak parent** tak upar le jayen, aur use props ki shakal me neeche bhejein, saath use badalne ka function bhi.
</Ur>
</Tr>

```jsx preview h=220
import { useState } from "react";

function Tabs({ active, onChange }) {
  const tabs = ["Description", "Reviews", "Shipping"];
  return (
    <div style={{ display: "flex", gap: 6 }}>
      {tabs.map((tab) => (
        <button
          key={tab}
          onClick={() => onChange(tab)}
          style={{ fontWeight: tab === active ? 700 : 400, borderColor: tab === active ? "#1f2937" : "#cbd5e1" }}
        >
          {tab}
        </button>
      ))}
    </div>
  );
}

function Panel({ active }) {
  const text = {
    Description: "A warm desk lamp with three brightness levels.",
    Reviews: "4.6 out of 5 from 212 reviews.",
    Shipping: "Ships in 2 days. Free over $50.",
  };
  return <p style={{ border: "1px solid #e5e7eb", padding: 10, borderRadius: 8 }}>{text[active]}</p>;
}

export default function App() {
  const [active, setActive] = useState("Description");
  return (
    <div>
      <Tabs active={active} onChange={setActive} />
      <Panel active={active} />
      <p style={{ color: "#6b7280" }}>Showing: {active}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- `Tabs` and `Panel` both need to know the active tab, so the state lives in their parent, `App`.
- `App` passes the value down (`active={active}`) and passes the setter down as a callback (`onChange={setActive}`).
- When you click a tab, `Tabs` calls `onChange("Reviews")`, which is `setActive`. `App` re-renders, and **both** children receive the new value.
- Data flows **down** as props; changes flow **up** through callbacks. This is the core of how React apps are wired together.

</En>
<Ur>

- `Tabs` aur `Panel` dono ko active tab jaanna hai, isliye state un ke parent `App` me rehti hai.
- `App` value neeche bhejta hai (`active={active}`) aur setter ko callback ki shakal me neeche bhejta hai (`onChange={setActive}`).
- Tab click karne par `Tabs` `onChange("Reviews")` call karta hai, jo `setActive` hai. `App` dobara render hota hai, aur **dono** children ko nayi value milti hai.
- Data props ki shakal me **neeche** behta hai; tabdeeliyan callbacks ke zariye **upar** jati hain. React apps isi tarah jore jate hain.

</Ur>
</Tr>
</Happened>

<Step title="The rules of hooks">

<Tr>
<En>

`useState` is a **hook**: a React function whose name starts with `use`. React remembers which state belongs to which hook **by the order** the hooks are called in. So there are two rules:

1. **Only call hooks at the top level** of a component: not inside `if`, loops, nested functions or after an early `return`.
2. **Only call hooks from React components** (or from your own custom hooks).

If a hook is skipped on one render and not the next, every hook after it gets the wrong state.

</En>
<Ur>

`useState` ek **hook** hai: React ka aisa function jis ka naam `use` se shuru ho. React yaad rakhta hai ke kaun si state kis hook ki hai, hooks ke call hone ki **tarteeb se**. Isliye do qawaid hain:

1. **Hooks sirf component ki sab se upar ki satah par call karein**: `if`, loops, andar ke functions me ya jaldi wale `return` ke baad nahi.
2. **Hooks sirf React components se call karein** (ya apne custom hooks se).

Agar koi hook ek render me chhoot jaye aur agle me na chhoote to us ke baad ke har hook ko ghalat state milti hai.

</Ur>
</Tr>

```text
// Wrong: the number of hooks changes between renders
function Profile({ user }) {
  if (!user) return <p>Loading…</p>;
  const [tab, setTab] = useState("posts");      // skipped while loading
}

// Right: hooks first, conditions after
function Profile({ user }) {
  const [tab, setTab] = useState("posts");
  if (!user) return <p>Loading…</p>;
}
```

<Happened>
<Tr>
<En>

- In the wrong version, the first render (no user yet) calls **zero** hooks; the next render calls **one**. React reports an error like "Rendered more hooks than during the previous render".
- Moving every hook above the first `return` fixes it. The editor plugin `eslint-plugin-react-hooks`, included in Next.js and Vite templates, warns you about this automatically.

</En>
<Ur>

- Ghalat version me pehla render (abhi user nahi) **zero** hooks call karta hai; agla render **ek**. React "Rendered more hooks than during the previous render" jaisa error deta hai.
- Har hook ko pehle `return` se upar le jana ise theek kar deta hai. Editor plugin `eslint-plugin-react-hooks`, jo Next.js aur Vite ke templates me shamil hai, is par khud ba khud khabardar karta hai.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Changing state directly">

```jsx
user.plan = "pro";
setUser(user);          // same object: no re-render

items.push(newItem);
setItems(items);        // same array: no re-render
```

</Bad>
<Good title="Give the setter a new value">

```jsx
setUser({ ...user, plan: "pro" });
setItems([...items, newItem]);
```

</Good>
</Compare>

<Compare>
<Bad title="Using state right after setting it">

```jsx
setCount(count + 1);
console.log(count);     // still the old value
```

<Tr>
<En>State is a snapshot. The new value arrives on the next render.</En>
<Ur>State ek tasveer hai. Nayi value agle render par aati hai.</Ur>
</Tr>

</Bad>
<Good title="Compute the next value once and use it">

```jsx
const next = count + 1;
setCount(next);
console.log(next);
```

</Good>
</Compare>

<Compare>
<Bad title="Several updates based on the same old value">

```jsx
setCount(count + 1);
setCount(count + 1);    // still only +1 in total
```

</Bad>
<Good title="Updater functions">

```jsx
setCount((c) => c + 1);
setCount((c) => c + 1); // +2
```

</Good>
</Compare>

<Compare>
<Bad title="Storing a value you could calculate">

```jsx
const [items, setItems] = useState([]);
const [count, setCount] = useState(0);   // must be kept in sync by hand
```

</Bad>
<Good title="Derive it">

```jsx
const [items, setItems] = useState([]);
const count = items.length;
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Calling the setter during render** (`setCount(count + 1)` directly in the component body). It triggers another render, which calls it again: an infinite loop. Set state in event handlers.
- **Forgetting `Number(…)`** on values from inputs, so `"5" + 1` becomes `"51"`.
- **An input with `value` but no `onChange`.** It becomes read-only. Add a change handler (or use `defaultValue` for an uncontrolled input).
- **Copying props into state** (`useState(props.price)`). The state won't follow later prop changes; usually just use the prop.
- **Calling `useState` inside an `if` or a loop.**

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Render ke dauran setter call karna** (component ki body me seedha `setCount(count + 1)`). Ye naya render chalata hai, jo use phir call karta hai: kabhi na khatam hone wala loop. State event handlers me set karein.
- **Inputs ki values par `Number(…)` bhoolna**, jis se `"5" + 1` `"51"` ban jata hai.
- **`value` wala input magar `onChange` nahi.** Ye sirf parhne wala ban jata hai. Change handler jorein (ya uncontrolled input ke liye `defaultValue` lein).
- **Props ko state me copy karna** (`useState(props.price)`). State baad ki prop tabdeeliyon ke peechhe nahi chalegi; aam taur par seedha prop istemal karein.
- **`if` ya loop ke andar `useState` call karna.**

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- State is a component's memory. Normal variables reset on every render and don't trigger updates.
- `const [value, setValue] = useState(initial)`: the initial value is used only on the first render.
- Calling the setter schedules a **re-render**; React calls your component again with the new value.
- Each copy of a component has its own state.
- State is a **snapshot** within a render; use updater functions (`setX(x => …)`) when the new value depends on the old.
- Never mutate state. Objects: `{ ...obj, field: v }`. Arrays: spread to add, `filter` to remove, `map` to change.
- Calculate what you can; store only what the user changes.
- Shared state lives in the closest common parent: values go down as props, changes come up through callbacks.
- Call hooks only at the top level of components.

</En>

- State component ki yaad dasht hai. Aam variables har render par naye bante hain aur update nahi karate.
- `const [value, setValue] = useState(initial)`: shuruati value sirf pehle render par istemal hoti hai.
- Setter call karna **dobara render** muqarrar karta hai; React aap ka component nayi value ke saath phir call karta hai.
- Component ki har copy ki apni state hoti hai.

- State kabhi mutate na karein. Objects: `{ ...obj, field: v }`. Arrays: jorne ke liye spread, hatane ke liye `filter`, badalne ke liye `map`.
- Jo nikal sake wo nikalein; sirf wahi rakhein jo user badalta hai.
- Mushtarak state sab se qareebi mushtarak parent me rehti hai: values props ki shakal me neeche, tabdeeliyan callbacks se upar.

<DeepDive title="How state really works">

**Batching.** React groups all state updates from one event (and, since React 18, from timeouts and promises too) into a **single re-render**. That's why three setter calls in one click cause one render, not three.

**Bail-out.** If you set state to a value that is `Object.is`-equal to the current one, React may skip the re-render. That's why mutating and passing the same object does nothing.

**Where state lives.** State isn't stored in your function. React keeps it next to the component's **position in the tree**. Render a different component at the same position, or change its `key`, and the state is thrown away. Render the same component at the same position, and the state is kept, even if props change. `<Form key={userId} />` is the idiomatic way to reset a form when the user changes.

**Lazy initial state.** `useState(expensiveCalculation())` runs the calculation on **every** render (the result is just ignored after the first). Pass a function instead, `useState(() => expensiveCalculation())`, and React calls it only once. Common for reading from `localStorage`.

**Choosing the shape.**
- Group values that always change together (`{ x, y }`).
- Avoid contradictory state: instead of `isLoading`, `isError` and `isSuccess` booleans, use one `status: "loading" | "error" | "success"`.
- Avoid duplication: store the selected **id**, not a copy of the selected object.
- Avoid deep nesting; flatten if updates become painful.

**`useReducer`.** When many events update the same state in different ways, `useReducer(reducer, initialState)` moves the update logic into one pure function: `(state, action) => newState`.

**TypeScript.** `useState(0)` infers `number`. When the initial value doesn't show the full type, pass it: `useState<string | null>(null)`, `useState<Todo[]>([])`.

**Libraries such as Immer** (used by Redux Toolkit) let you write "mutating" code that is turned into immutable updates behind the scenes.

</DeepDive>

<DeepDive title="Real world: the cart badge that lagged one behind">

A shop's "Add to cart" button did this:

```jsx

  setCart([...cart, product]);
  analytics.track("cart_size", cart.length);
  setBadge(cart.length);
}
```

Customers saw the cart badge in the header show **one less** than the number of items, and the analytics dashboard said average cart size was lower than real orders. Both `cart.length` reads used the **snapshot** from the current render, before the new item existed.

The team fixed it in two steps. First, they calculated the new cart once and used it everywhere:

```jsx
const nextCart = [...cart, product];
setCart(nextCart);
analytics.track("cart_size", nextCart.length);
```

Second, they deleted the `badge` state entirely. The badge was **derived** data (`cart.length`), so the header now just reads it during render and can never disagree with the cart again. Two state variables that must always match are a warning sign: usually one of them shouldn't be state.

</DeepDive>

<DeepDive title="Security lens">

State lives in the user's browser, so treat it as the user's data, not yours.

- **Client state is not trusted.** Prices, discounts, roles and "isAdmin" flags in React state can be changed by anyone with DevTools or a browser extension. The server must recalculate totals and check permissions; never send `price` from the client and charge it.
- **Hiding a button isn't access control.** `{user.isAdmin && <DeleteButton />}` improves the UI, but the delete API must still check the user's role on the server.
- **Sensitive data in state stays in memory.** Don't keep passwords, full card numbers or tokens in component state longer than needed; clear form fields after submission.
- **`localStorage` for lazy initial state.** Anything there can be read by any script running on your page, including injected ones. Don't put tokens or personal data there, and validate what you read back, since the user (or an attacker) can edit it.
- **Rendering state is safe by default.** Text from inputs shown with `{name}` is escaped, so a user typing HTML can't inject scripts, unless you use `dangerouslySetInnerHTML`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is state in React and how is it different from props?">
State is data a component owns and can change over time with a setter, which causes a re-render. Props are read-only inputs given by a parent. A component can pass its state down to children as props, and children request changes by calling callbacks passed from the parent.
</QA>

<QA q="Why should you not mutate state directly?">
React decides whether to re-render by comparing the old and new state references. Mutating an object or array and passing the same reference back looks like no change, so the UI does not update. Mutation also breaks features that rely on previous values, such as memoised components and concurrent rendering. Create new objects and arrays instead.
</QA>

<QA q="Why does calling setCount(count + 1) twice only increment once?">
State values are snapshots for the current render. Both calls read the same count, so both schedule the same new value. Passing an updater function, setCount of c to c plus one, makes React apply each update to the result of the previous one.
</QA>

<QA q="Is setState synchronous?">
No. Calling the setter schedules an update; the state variable in the current render keeps its old value, and React batches updates from the same event into one re-render. The new value is available on the next render.
</QA>

<QA q="What does lifting state up mean?">
When several components need the same data, the state is moved to their closest common ancestor. The ancestor passes the value down as props and passes callbacks that let children request changes, keeping a single source of truth.
</QA>

<QA q="What are the rules of hooks?">
Hooks must be called at the top level of a component or custom hook, never inside conditions, loops or nested functions, so that they run in the same order on every render. They may only be called from React function components or custom hooks.
</QA>

<QA q="What is derived state and why avoid storing it?">
Derived state is a value that can be computed from props or other state, such as a filtered list or a total. Storing it separately requires keeping copies in sync and leads to bugs when they diverge; computing it during render keeps it always correct.
</QA>

</DeepDive>

<Terms>
  <Term name="State">Data a component remembers between renders.</Term>
  <Term name="Hook">A React function starting with use that adds a capability to a component.</Term>
  <Term name="useState">The hook that declares a state variable and its setter.</Term>
  <Term name="Setter">The function returned by useState that schedules an update.</Term>
  <Term name="Re-render">React calling a component again to produce updated UI.</Term>
  <Term name="Snapshot">The fixed value of state during one render.</Term>
  <Term name="Updater function">A function passed to a setter that receives the previous state.</Term>
  <Term name="Batching">Grouping several state updates into one re-render.</Term>
  <Term name="Immutable update">Creating a new object or array instead of changing the old one.</Term>
  <Term name="Controlled input">A form field whose value is driven by state.</Term>
  <Term name="Derived value">A value computed from state or props during render.</Term>
  <Term name="Lifting state up">Moving shared state to a common parent component.</Term>
