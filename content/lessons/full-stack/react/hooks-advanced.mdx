<BigIdea>
<Tr>
<En>
You already know `useState` (remember a value and re-render) and `useEffect` (do something after rendering). Four more hooks each fix one specific problem. **`useContext`** shares a value, such as the current user or the colour theme, with **every component below** a provider, so you don't have to pass it as a prop through every level. **`useRef`** gives you a **box that survives re-renders but doesn't cause them**: perfect for a page element you want to focus, or a timer id. **`useMemo`** remembers the **result of a calculation** and only redoes it when its inputs change. **`useCallback`** remembers a **function**, so a child wrapped in `memo` doesn't re-render just because it received a "new" function. The last two are **performance tools**: reach for them when something is actually slow, not by default.
</En>
<Ur>
Aap `useState` (value yaad rakhna aur dobara render karna) aur `useEffect` (render ke baad kuch karna) jaante hain. Chaar aur hooks har ek kisi khaas masle ka hal hain. **`useContext`** koi value, jaise maujooda user ya rang ki theme, provider ke **neeche har component** ke saath share karta hai, taa ke use har satah se prop ki shakal me guzarna na pare. **`useRef`** aap ko aisa **dabba deta hai jo renders ke darmiyan bacha rehta hai magar render nahi karata**: us page element ke liye behtareen jis par focus karna ho, ya timer ki id ke liye. **`useMemo`** **hisaab ka nateeja** yaad rakhta hai aur use tabhi dobara karta hai jab us ke inputs badlen. **`useCallback`** ek **function** yaad rakhta hai, taa ke `memo` me lipta child sirf is liye dobara render na ho ke use "naya" function mila. Aakhri do **performance ke auzaar** hain: inhe tab lein jab koi cheez waqai sust ho, aadatan nahi.
</Ur>
</Tr>
</BigIdea>

<Glance>
<What>
<Tr>
<En>

| Hook | Problem it solves | One-line example |
| --- | --- | --- |
| `useContext` | Passing the same prop through many levels | `const theme = useContext(ThemeContext);` |
| `useRef` | Remember something **without** re-rendering, or reach a DOM element | `const inputRef = useRef(null);` |
| `useMemo` | A slow calculation repeated on every render | `const sorted = useMemo(() => sort(list), [list]);` |
| `useCallback` | A new function on every render breaks `memo` | `const onSave = useCallback(() => save(id), [id]);` |

</En>

</What>
<Why>
<Tr>
<En>

- **Context** keeps components clean: a button deep in the page can read the theme or the logged-in user directly.
- **Refs** cover the things state can't: focusing an input, scrolling to an element, keeping an interval id, remembering a previous value, all without extra renders.
- **`useMemo` and `useCallback`** keep big lists, charts and heavy components fast when unrelated state changes.
- You'll see all four constantly in real codebases and libraries, so you need to read them even before you write them.

</En>
<Ur>

- **Context** components ko saaf rakhta hai: page me gehra rakha button theme ya login user seedha parh sakta hai.
- **Refs** un cheezon ka ahata karte hain jo state nahi kar sakti: input par focus, kisi element tak scroll, interval ki id rakhna, pichhli value yaad rakhna, sab izafi renders ke baghair.
- **`useMemo` aur `useCallback`** ghair mutaliq state badalne par bari lists, charts aur bhaari components ko tez rakhte hain.
- Asli codebases aur libraries me ye chaaron har jagah nazar aate hain, isliye inhe likhne se pehle bhi parhna aana chahiye.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

- **`useContext`**: data many components need, which changes rarely: theme, language, logged-in user, a shopping cart.
- **`useRef`**: a DOM element you must call methods on (`focus`, `scrollIntoView`), or a value that must persist but **shouldn't** update the screen.
- **`useMemo`**: a calculation you have **measured** as slow, or an object/array that must stay the same between renders.
- **`useCallback`**: a function passed to a `memo` child or used as an effect dependency.

</En>
<Ur>

- **`useContext`**: aisa data jo kai components ko chahiye aur kam badalta ho: theme, zabaan, login user, shopping cart.
- **`useRef`**: DOM element jis par methods call karne hon (`focus`, `scrollIntoView`), ya aisi value jo bachi rahe magar screen update **na** kare.
- **`useMemo`**: aisa hisaab jise aap ne **naap kar** sust paya ho, ya object/array jo renders ke darmiyan wahi rehna chahiye.
- **`useCallback`**: `memo` child ko diya gaya function, ya effect ki dependency ke taur par istemal hone wala function.

</Ur>
</Tr>
</When>

## Picture it

<Tr>
<En>

Imagine an **office building**.

- **Context** is the building's **public announcement system**. Instead of the manager telling the floor supervisor, who tells the team lead, who tells you "today's dress code is casual", the announcement is broadcast and anyone in the building can hear it directly. Everyone **inside** the building (below the provider) can listen.
- A **ref** is your **desk drawer**. You can keep things in it, take them out and change them, and nobody gets an email about it. Compare that with **state**, which is the **notice board**: every change is announced and everyone looks again (a re-render).
- **`useMemo`** is a **sticky note with an answer** on your monitor: "Monthly total for March: $4,210". As long as March's numbers haven't changed, you read the note instead of adding everything up again.
- **`useCallback`** is giving a colleague the **same phone number** every day. A colleague who only updates their contacts when your number changes (a `memo` child) has nothing to do if the number is the same.

</En>
<Ur>

Ek **daftar ki imarat** ka sochein.

- **Context** imarat ka **public announcement system** hai. Manager ke floor supervisor ko, supervisor ke team lead ko, aur team lead ke aap ko "aaj ka libaas aam hai" batane ke bajaye, elaan nashar hota hai aur imarat me har koi seedha sun sakta hai. Imarat ke **andar** (provider ke neeche) har koi sun sakta hai.
- **Ref** aap ki **mez ki daraaz** hai. Aap is me cheezen rakh sakte, nikal sakte aur badal sakte hain, aur kisi ko email nahi jati. Is ka **state** se muqabla karein, jo **notice board** hai: har tabdeeli ka elaan hota hai aur har koi dobara dekhta hai (dobara render).
- **`useMemo`** monitor par laga **jawab wala sticky note** hai: "March ka mahana total: $4,210". Jab tak March ke numbers nahi badle, aap sab dobara jorne ke bajaye note parh lete hain.
- **`useCallback`** saathi ko roz **wahi phone number** dena hai. Jo saathi contacts sirf tab update karta hai jab aap ka number badle (`memo` child), number wahi ho to use kuch nahi karna parta.

</Ur>
</Tr>

<Step title="The problem: prop drilling">

<Tr>
<En>
The theme is chosen at the top, but only the button at the bottom uses it. Every component in between has to accept `theme` and pass it on, even though it doesn't care.
</En>
<Ur>
Theme sab se upar chuni jati hai, magar sirf sab se neeche wala button use istemal karta hai. Beech ke har component ko `theme` lena aur aage dena parta hai, halanke use is se koi gharz nahi.
</Ur>
</Tr>

```jsx preview h=170
import { useState } from "react";

function Page({ theme }) {
  return <Sidebar theme={theme} />;
}

function Sidebar({ theme }) {
  return <Menu theme={theme} />;
}

function Menu({ theme }) {
  return <ThemedButton theme={theme} />;
}

function ThemedButton({ theme }) {
  const dark = theme === "dark";
  return (
    <button style={{ background: dark ? "#111827" : "#fff", color: dark ? "#fff" : "#111827" }}>
      I am a {theme} button
    </button>
  );
}

export default function App() {
  const [theme, setTheme] = useState("light");
  return (
    <div>
      <label>
        <input type="checkbox" checked={theme === "dark"} onChange={(e) => setTheme(e.target.checked ? "dark" : "light")} />{" "}
        Dark mode
      </label>
      <p><Page theme={theme} /></p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- It works, but `Page`, `Sidebar` and `Menu` exist only to **pass `theme` along**. This is called **prop drilling**.
- With 10 levels and 5 shared values (theme, user, language, cart, permissions), every component's props fill up with things it doesn't use, and moving a component means rewiring props everywhere.

</En>
<Ur>

- Ye chalta hai, magar `Page`, `Sidebar` aur `Menu` sirf **`theme` aage bhejne** ke liye hain. Ise **prop drilling** kehte hain.
- 10 satahon aur 5 mushtarak values (theme, user, zabaan, cart, permissions) ke saath har component ke props aisi cheezon se bhar jate hain jo wo istemal nahi karta, aur component ki jagah badalne ka matlab har jagah props dobara jorna.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="useContext: share without passing">

<Tr>
<En>
Three steps: **create** a context, **provide** a value around part of the tree, and **read** it with `useContext` in any component below. The components in between don't mention it at all.
</En>
<Ur>
Teen qadam: context **banayen**, darakht ke kisi hisse ke gird value **faraham** karein, aur neeche kisi bhi component me `useContext` se use **parhein**. Beech ke components is ka zikr tak nahi karte.
</Ur>
</Tr>

```jsx preview h=170
import { createContext, useContext, useState } from "react";

const ThemeContext = createContext("light");

function Page() {
  return <Sidebar />;
}

function Sidebar() {
  return <Menu />;
}

function Menu() {
  return <ThemedButton />;
}

function ThemedButton() {
  const theme = useContext(ThemeContext);
  const dark = theme === "dark";
  return (
    <button style={{ background: dark ? "#111827" : "#fff", color: dark ? "#fff" : "#111827" }}>
      I am a {theme} button
    </button>
  );
}

export default function App() {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext value={theme}>
      <label>
        <input type="checkbox" checked={theme === "dark"} onChange={(e) => setTheme(e.target.checked ? "dark" : "light")} />{" "}
        Dark mode
      </label>
      <p><Page /></p>
    </ThemeContext>
  );
}
```

<Happened>
<Tr>
<En>

- `createContext("light")` makes the context. `"light"` is the **default**, used only if there's no provider above.
- `<ThemeContext value={theme}>` provides the current theme to everything inside it. (Before React 19 you wrote `<ThemeContext.Provider value={theme}>`; you'll still see that in older code.)
- `useContext(ThemeContext)` in `ThemedButton` reads the nearest provider's value. `Page`, `Sidebar` and `Menu` no longer take any props.
- Tick the box: the state in `App` changes, the provider gets a new value, and **every component that reads the context re-renders** with it.

</En>
<Ur>

- `createContext("light")` context banata hai. `"light"` **default** hai, jo sirf tab istemal hota hai jab upar koi provider na ho.
- `<ThemeContext value={theme}>` apne andar har cheez ko maujooda theme faraham karta hai. (React 19 se pehle aap `<ThemeContext.Provider value={theme}>` likhte the; purane code me ye ab bhi nazar aayega.)
- `ThemedButton` me `useContext(ThemeContext)` sab se qareebi provider ki value parhta hai. `Page`, `Sidebar` aur `Menu` ab koi props nahi lete.
- Dabba tick karein: `App` ki state badalti hai, provider ko nayi value milti hai, aur **context parhne wala har component** us ke saath dobara render hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Context with state: a shared cart">

<Tr>
<En>
A context can hold **any** value, including an object with state **and** functions to change it. Wrapping the read in a small custom hook (`useCart`) gives a clean API and a helpful error if someone forgets the provider.
</En>
<Ur>
Context **koi bhi** value rakh sakta hai, aisa object bhi jis me state **aur** use badalne ke functions hon. Parhne ko ek chhote custom hook (`useCart`) me lapetna saaf API deta hai aur agar koi provider bhool jaye to madadgaar error.
</Ur>
</Tr>

```jsx preview h=230
import { createContext, useContext, useState } from "react";

const CartContext = createContext(null);

function CartProvider({ children }) {
  const [items, setItems] = useState([]);
  const add = (name) => setItems((list) => [...list, name]);
  const clear = () => setItems([]);
  return <CartContext value={{ items, add, clear }}>{children}</CartContext>;
}

function useCart() {
  const cart = useContext(CartContext);
  if (!cart) throw new Error("useCart must be used inside <CartProvider>");
  return cart;
}

function Header() {
  const { items } = useCart();
  return <p style={{ fontWeight: 700 }}>🛒 {items.length} items</p>;
}

function Product({ name }) {
  const { add } = useCart();
  return <button onClick={() => add(name)} style={{ marginRight: 6 }}>Add {name}</button>;
}

function CartFooter() {
  const { items, clear } = useCart();
  return (
    <p>
      {items.join(", ") || "Nothing yet"} <button onClick={clear}>Clear</button>
    </p>
  );
}

export default function App() {
  return (
    <CartProvider>
      <Header />
      <Product name="Pen" />
      <Product name="Notebook" />
      <CartFooter />
    </CartProvider>
  );
}
```

<Happened>
<Tr>
<En>

- `CartProvider` owns the state and provides `{ items, add, clear }`.
- `Header`, `Product` and `CartFooter` are siblings that never pass anything to each other, yet clicking "Add Pen" updates the header count and the footer list at once.
- `useCart()` is a **custom hook**: a function starting with `use` that calls other hooks. It hides the context object and throws a clear error if used outside the provider, instead of failing later with "cannot read properties of null".
- This "provider + custom hook" pattern is how auth, theme, language and cart state are commonly shared.

</En>
<Ur>

- `CartProvider` state ka maalik hai aur `{ items, add, clear }` faraham karta hai.
- `Header`, `Product` aur `CartFooter` aise saathi hain jo ek doosre ko kuch nahi dete, phir bhi "Add Pen" click karna header ki ginti aur footer ki list ek saath update karta hai.
- `useCart()` ek **custom hook** hai: `use` se shuru hone wala function jo doosre hooks call kare. Ye context object chhupata hai aur provider ke bahar istemal hone par saaf error deta hai, baad me "cannot read properties of null" ke saath nakaam hone ke bajaye.
- Auth, theme, zabaan aur cart ki state aam taur par isi "provider + custom hook" namoone se share hoti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="useRef for page elements: focus a box">

<Tr>
<En>
Sometimes you need the **real DOM element**, for example to focus an input or scroll to a section. Create a ref with `useRef(null)`, attach it with `ref={…}`, and after rendering React puts the element in `ref.current`.
</En>
<Ur>
Kabhi aap ko **asli DOM element** chahiye hota hai, maslan input par focus karne ya kisi hisse tak scroll karne ke liye. `useRef(null)` se ref banayen, `ref={…}` se jorein, aur render ke baad React element ko `ref.current` me rakh deta hai.
</Ur>
</Tr>

```jsx preview h=190
import { useRef } from "react";

export default function App() {
  const searchRef = useRef(null);
  const bottomRef = useRef(null);

  return (
    <div>
      <input ref={searchRef} placeholder="Search products" />{" "}
      <button onClick={() => searchRef.current.focus()}>Focus search</button>{" "}
      <button onClick={() => bottomRef.current.scrollIntoView({ behavior: "smooth" })}>Jump to bottom</button>
      <div style={{ height: 400, background: "linear-gradient(#fff, #e5e7eb)" }} />
      <p ref={bottomRef}>You reached the bottom.</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- `ref={searchRef}` tells React "put this `<input>` element into `searchRef.current`".
- **Focus search** calls the browser's own `focus()` method on that element. There's no JSX prop for "focus now", which is why you need the element itself.
- **Jump to bottom** scrolls the second ref's element into view.
- `ref.current` is `null` during the first render (the element doesn't exist yet), so use it in event handlers or effects, not while rendering.

</En>
<Ur>

- `ref={searchRef}` React se kehta hai "ye `<input>` element `searchRef.current` me rakh do".
- **Focus search** us element par browser ka apna `focus()` method call karta hai. "Abhi focus karo" ka koi JSX prop nahi, isi liye element khud chahiye.
- **Jump to bottom** doosre ref ke element ko nazar me scroll karta hai.
- Pehle render ke dauran `ref.current` `null` hota hai (element abhi bana hi nahi), isliye ise event handlers ya effects me istemal karein, render karte waqt nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Ref vs state: who triggers a re-render?">

<Tr>
<En>
A ref is also just a box for **any value** that should survive between renders. The difference from state: changing `ref.current` does **not** re-render. Click each button a few times, then click **Show**.
</En>
<Ur>
Ref kisi bhi **value** ke liye bas ek dabba bhi hai jo renders ke darmiyan bachi rehni chahiye. State se farq: `ref.current` badalna dobara render **nahi** karta. Har button kuch dafa click karein, phir **Show** click karein.
</Ur>
</Tr>

```jsx preview h=170
import { useRef, useState } from "react";

export default function App() {
  const refClicks = useRef(0);
  const [stateClicks, setStateClicks] = useState(0);
  const [, forceShow] = useState(0);

  return (
    <div>
      <button onClick={() => { refClicks.current = refClicks.current + 1; }}>Ref +1</button>{" "}
      <button onClick={() => setStateClicks(stateClicks + 1)}>State +1</button>{" "}
      <button onClick={() => forceShow((n) => n + 1)}>Show</button>
      <p>Ref clicks shown on screen: {refClicks.current}</p>
      <p>State clicks shown on screen: {stateClicks}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **State +1** updates the screen immediately: setting state re-renders.
- **Ref +1** changes `refClicks.current`, but the screen doesn't move. The value **is** being counted; nobody re-rendered to show it.
- **Show** re-renders the component (by changing an unrelated state), and the ref's real count appears. Clicking **State +1** reveals it too: any re-render reads the latest `ref.current`.
- Rule: if it's **shown on screen**, use state. If it's only for your code (a timer id, a previous value, "has this run already?"), use a ref.

</En>
<Ur>

- **State +1** screen foran update karta hai: state set karna dobara render karta hai.
- **Ref +1** `refClicks.current` badalta hai, magar screen nahi hilti. Value gini **ja rahi** hai; bas use dikhane ke liye kisi ne dobara render nahi kiya.
- **Show** component ko dobara render karta hai (ek ghair mutaliq state badal kar), aur ref ki asli ginti nazar aa jati hai. **State +1** click karna bhi ise dikha deta hai: har dobara render taza tareen `ref.current` parhta hai.
- Qaida: agar ye **screen par dikhti** hai to state lein. Agar sirf aap ke code ke liye hai (timer id, pichhli value, "kya ye pehle chal chuka?"), to ref lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A ref for a timer id">

<Tr>
<En>
A start/stop stopwatch needs to remember the **interval id** so the Stop button can clear it. The id isn't shown on screen, so a ref is the right place for it.
</En>
<Ur>
Start/stop stopwatch ko **interval id** yaad rakhni hai taa ke Stop button use hata sake. Id screen par nahi dikhti, isliye ref is ki sahi jagah hai.
</Ur>
</Tr>

```jsx preview h=160
import { useRef, useState, useEffect } from "react";

export default function App() {
  const [seconds, setSeconds] = useState(0);
  const timerRef = useRef(null);

  function start() {
    if (timerRef.current !== null) return;
    timerRef.current = setInterval(() => setSeconds((s) => s + 1), 1000);
  }

  function stop() {
    clearInterval(timerRef.current);
    timerRef.current = null;
  }

  useEffect(() => stop, []);

  return (
    <div>
      <p style={{ fontSize: 28, margin: "4px 0" }}>{seconds}s</p>
      <button onClick={start}>Start</button>{" "}
      <button onClick={stop}>Stop</button>{" "}
      <button onClick={() => { stop(); setSeconds(0); }}>Reset</button>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- **Start** saves the interval id in `timerRef.current`. Clicking Start again does nothing, because an id is already stored, so you can't start two timers.
- **Stop** reads the same id from the ref and clears it.
- A normal variable (`let timerId`) wouldn't work: it's recreated on every render (every tick), so Stop would lose the id. State would work but would cause an extra pointless re-render.
- `useEffect(() => stop, [])` returns `stop` as the cleanup, so the timer is cleared if the component disappears.

</En>
<Ur>

- **Start** interval id ko `timerRef.current` me mehfooz karta hai. Dobara Start click karne se kuch nahi hota, kyun ke id pehle se rakhi hai, isliye do timers shuru nahi ho sakte.
- **Stop** ref se wahi id parhta hai aur use hata deta hai.
- Aam variable (`let timerId`) kaam nahi karta: wo har render (har tick) par naya banta hai, isliye Stop id kho deta. State kaam karti magar ek izafi bekaar render karati.
- `useEffect(() => stop, [])` `stop` ko cleanup ke taur par wapas karta hai, isliye component ghayab ho to timer hat jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="useMemo: don't redo slow work">

<Tr>
<En>
Every re-render runs the whole component again, including any calculation in it. If a calculation is slow and its inputs haven't changed, that's wasted time. **`useMemo(fn, deps)`** remembers the result and only recalculates when a dependency changes. Type in the **note** box in both panels and watch the log.
</En>
<Ur>
Har dobara render poora component phir chalata hai, us ke andar ka har hisaab samet. Agar hisaab sust ho aur us ke inputs na badle hon to ye waqt zaya karna hai. **`useMemo(fn, deps)`** nateeja yaad rakhta hai aur sirf tab dobara hisaab karta hai jab koi dependency badle. Dono panels me **note** wale dabbe me type karein aur log dekhein.
</Ur>
</Tr>

```jsx preview h=300
import { useMemo, useState } from "react";

const logBox = document.body.appendChild(document.createElement("pre"));
logBox.style.cssText = "background:#f3f4f6;padding:8px;font-size:12px;margin:12px 16px 0;max-height:90px;overflow:auto";
function log(message) {
  logBox.textContent = message + "\n" + logBox.textContent;
}

const NUMBERS = Array.from({ length: 200000 }, (_, i) => i);

function countMultiples(n, label) {
  log(label + ": counting multiples of " + n + " in 200,000 numbers…");
  return NUMBERS.filter((x) => x % n === 0).length;
}

function Plain() {
  const [n, setN] = useState(7);
  const [note, setNote] = useState("");
  const count = countMultiples(n, "plain");
  return (
    <p>
      Plain: <input type="number" value={n} onChange={(e) => setN(Number(e.target.value) || 1)} style={{ width: 60 }} />{" "}
      → {count} · note <input value={note} onChange={(e) => setNote(e.target.value)} style={{ width: 90 }} />
    </p>
  );
}

function Memoised() {
  const [n, setN] = useState(7);
  const [note, setNote] = useState("");
  const count = useMemo(() => countMultiples(n, "memo"), [n]);
  return (
    <p>
      Memo: <input type="number" value={n} onChange={(e) => setN(Number(e.target.value) || 1)} style={{ width: 60 }} />{" "}
      → {count} · note <input value={note} onChange={(e) => setNote(e.target.value)} style={{ width: 90 }} />
    </p>
  );
}

export default function App() {
  return (
    <div>
      <Plain />
      <Memoised />
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Typing in **Plain**'s note box re-renders `Plain`, and the slow count runs **again on every key**, even though `n` didn't change. The log fills with "plain: counting…".
- Typing in **Memo**'s note box re-renders too, but `useMemo` sees that `n` is the same and returns the remembered count. No new "memo: counting…" lines.
- Change the number in **Memo**: now `n` changed, so it recalculates once.
- `useMemo` takes a function (not its result) and a dependency array, just like `useEffect`, but it runs **during** render and returns a value.

</En>
<Ur>

- **Plain** ke note wale dabbe me type karna `Plain` ko dobara render karta hai, aur sust ginti **har key par phir** chalti hai, halanke `n` nahi badla. Log "plain: counting…" se bhar jata hai.
- **Memo** ke note wale dabbe me type karna bhi dobara render karta hai, magar `useMemo` dekhta hai ke `n` wahi hai aur yaad rakhi gayi ginti wapas kar deta hai. Koi nayi "memo: counting…" line nahi.
- **Memo** me number badlein: ab `n` badla, isliye ye ek dafa dobara hisaab karta hai.
- `useMemo` function leta hai (us ka nateeja nahi) aur dependency array, bilkul `useEffect` ki tarah, magar ye render ke **dauran** chalta hai aur value wapas karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Same contents, different object">

<Tr>
<En>
Objects and arrays created during render are **new** every time, even if their contents are identical. Things that compare with `===` (effect dependencies, `memo`) see them as "changed". `useMemo` can keep the **same** object until its inputs really change.
</En>
<Ur>
Render ke dauran bane objects aur arrays har dafa **naye** hote hain, chahe andar ka mawad bilkul ek jaisa ho. Jo cheezen `===` se muqabla karti hain (effect dependencies, `memo`) unhe "badla hua" samajhti hain. `useMemo` **wahi** object rakh sakta hai jab tak us ke inputs waqai na badlen.
</Ur>
</Tr>

```jsx preview h=230
import { useEffect, useMemo, useState } from "react";

const logBox = document.body.appendChild(document.createElement("pre"));
logBox.style.cssText = "background:#f3f4f6;padding:8px;font-size:12px;margin:12px 16px 0;max-height:90px;overflow:auto";
function log(message) {
  logBox.textContent = message + "\n" + logBox.textContent;
}

export default function App() {
  const [sortBy, setSortBy] = useState("name");
  const [clicks, setClicks] = useState(0);

  const plainOptions = { sortBy: sortBy, pageSize: 20 };
  const memoOptions = useMemo(() => ({ sortBy: sortBy, pageSize: 20 }), [sortBy]);

  useEffect(() => log("plain options effect ran (would refetch!)"), [plainOptions]);
  useEffect(() => log("memo options effect ran"), [memoOptions]);

  return (
    <div>
      <button onClick={() => setClicks(clicks + 1)}>Unrelated click ({clicks})</button>{" "}
      <button onClick={() => setSortBy(sortBy === "name" ? "price" : "name")}>Sort by {sortBy === "name" ? "price" : "name"}</button>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- Click **Unrelated click**: the component re-renders, `plainOptions` is a brand-new object, so its effect runs again (imagine it refetching data each time). `memoOptions` is the **same** object as before, so its effect is skipped.
- Click **Sort by**: `sortBy` really changed, so **both** effects run.
- This is the main reason `useMemo` appears in real code: not only speed, but keeping objects **stable** so effects and memoised children don't run for nothing.

</En>
<Ur>

- **Unrelated click** click karein: component dobara render hota hai, `plainOptions` bilkul naya object hai, isliye us ka effect phir chalta hai (sochein ke ye har dafa data dobara mangwa raha ho). `memoOptions` pehle wala **hi** object hai, isliye us ka effect chhor diya jata hai.
- **Sort by** click karein: `sortBy` waqai badla, isliye **dono** effects chalte hain.
- Asli code me `useMemo` ki bari wajah yahi hai: sirf raftaar nahi, balke objects ko **pakka** rakhna taa ke effects aur memoised children bekaar na chalen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="memo and useCallback: skip re-rendering children">

<Tr>
<En>
When a parent re-renders, **all its children re-render** by default. Wrapping a child in **`memo`** makes React skip it if its props are the same (`===`) as last time. But a function created during render is **new** every time, so it breaks `memo`. **`useCallback`** keeps the same function. Type in the box and watch which rows re-render.
</En>
<Ur>
Jab parent dobara render ho to default me **us ke saare children dobara render** hote hain. Child ko **`memo`** me lapetna React se use chhorwata hai agar us ke props pichhli dafa jaise (`===`) hon. Magar render ke dauran bana function har dafa **naya** hota hai, isliye ye `memo` ko tor deta hai. **`useCallback`** wahi function rakhta hai. Dabbe me type karein aur dekhein kaun si rows dobara render hoti hain.
</Ur>
</Tr>

```jsx preview h=290
import { memo, useCallback, useState } from "react";

const logBox = document.body.appendChild(document.createElement("pre"));
logBox.style.cssText = "background:#f3f4f6;padding:8px;font-size:12px;margin:12px 16px 0;max-height:90px;overflow:auto";
function log(message) {
  logBox.textContent = message + "\n" + logBox.textContent;
}

const Row = memo(function Row({ label, onRemove }) {
  log("rendered row: " + label);
  return (
    <li>
      {label} <button onClick={onRemove}>✕</button>
    </li>
  );
});

export default function App() {
  const [text, setText] = useState("");
  const [items, setItems] = useState(["Pen", "Notebook"]);

  const removeFirstPlain = () => setItems((list) => list.slice(1));
  const removeFirstStable = useCallback(() => setItems((list) => list.slice(1)), []);

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} placeholder="Type here" />
      <ul>
        <Row label="A (new function each render)" onRemove={removeFirstPlain} />
        <Row label="B (useCallback)" onRemove={removeFirstStable} />
      </ul>
      <p>Items: {items.join(", ")}</p>
    </div>
  );
}
```

<Happened>
<Tr>
<En>

- At first both rows render once.
- Type a letter: `App` re-renders. **Row A** re-renders on every key: its `onRemove` is a brand-new arrow function each time, so `memo` sees different props. **Row B** does **not** re-render: `useCallback` returned the same function, so all its props are identical and `memo` skips it.
- `useCallback(fn, deps)` is just `useMemo(() => fn, deps)`: it remembers the function itself.
- `useCallback` **on its own** does nothing useful. It only matters when the function goes to a `memo` child, or into a dependency array.

</En>
<Ur>

- Shuru me dono rows ek dafa render hoti hain.
- Ek harf type karein: `App` dobara render hota hai. **Row A** har key par dobara render hoti hai: us ka `onRemove` har dafa bilkul naya arrow function hai, isliye `memo` alag props dekhta hai. **Row B** dobara render **nahi** hoti: `useCallback` ne wahi function wapas kiya, isliye us ke saare props ek jaise hain aur `memo` use chhor deta hai.
- `useCallback(fn, deps)` bas `useMemo(() => fn, deps)` hai: ye khud function yaad rakhta hai.
- `useCallback` **akela** koi faida nahi deta. Ye sirf tab ahem hai jab function `memo` child ko jaye, ya dependency array me.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="When not to use useMemo and useCallback">

<Tr>
<En>

Memoisation isn't free: React must store the old value and compare dependencies on every render, and the code gets harder to read. Use it when there's a **reason**:

| Use it | Skip it |
| --- | --- |
| A calculation you measured as slow (sorting thousands of rows, heavy maths) | `items.length`, `a + b`, a short `filter` |
| An object/array/function used in an effect's dependencies | A function passed to a plain `<button onClick>` |
| A prop passed to a `memo` child that is expensive to render | Children that are cheap to render anyway |
| A context value object (so consumers don't re-render needlessly) | Values that change on every render anyway |

**Measure first** with the React DevTools Profiler. Also, the **React Compiler** (stable since late 2025) can add memoisation automatically at build time; in projects that use it, you'll write these hooks far less often.

</En>
<Ur>

Memoisation muft nahi: React ko har render par purani value rakhni aur dependencies milani parti hain, aur code parhna mushkil ho jata hai. Ise tab lein jab koi **wajah** ho:

| Lein | Chhor dein |
| --- | --- |
| Aisa hisaab jise aap ne naap kar sust paya (hazaron rows sort karna, bhaari hisaab) | `items.length`, `a + b`, chhota `filter` |
| Effect ki dependencies me istemal hone wala object/array/function | Saade `<button onClick>` ko diya gaya function |
| `memo` child ko diya gaya prop jise render karna mehanga ho | Children jinhe render karna waise hi sasta ho |
| Context ki value wala object (taa ke consumers bekaar render na hon) | Values jo waise bhi har render par badalti hain |

Pehle React DevTools Profiler se **naapein**. Saath hi, **React Compiler** (2025 ke aakhir se stable) build ke waqt khud memoisation jor sakta hai; jin projects me ye istemal hota hai wahan aap ye hooks bohot kam likhenge.

</Ur>
</Tr>

```text
// Over-optimised: three hooks that buy nothing
const count = useMemo(() => items.length, [items]);
const label = useMemo(() => "Hi " + name, [name]);
const onClick = useCallback(() => setOpen(true), []);
return <button onClick={onClick}>{label} ({count})</button>;

// Same behaviour, simpler and just as fast
const count = items.length;
return <button onClick={() => setOpen(true)}>Hi {name} ({count})</button>;
```

<Happened>
<Tr>
<En>

- `items.length` and string joining take microseconds; caching them costs more than computing them.
- `<button>` is a built-in element, not a `memo` component, so a stable `onClick` changes nothing.
- Start with the simple version. Add `useMemo`/`useCallback` when a profile or a dependency problem tells you to.

</En>
<Ur>

- `items.length` aur string jorna microseconds lete hain; inhe yaad rakhna inhe nikalne se zyada mehanga hai.
- `<button>` bana banaya element hai, `memo` component nahi, isliye pakka `onClick` kuch nahi badalta.
- Saade version se shuru karein. `useMemo`/`useCallback` tab jorein jab profile ya dependency ka masla aap ko bataye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Context re-renders and how to keep them cheap">

<Tr>
<En>
Every component that calls `useContext(X)` re-renders when X's value changes. If the provider builds a **new object** on every render, all consumers re-render even when nothing they use changed. Memoise the value, and split contexts that change at different speeds.
</En>
<Ur>
`useContext(X)` call karne wala har component X ki value badalne par dobara render hota hai. Agar provider har render par **naya object** banaye to saare consumers dobara render hote hain, chahe un ki istemal ki cheez na badli ho. Value ko memoise karein, aur alag raftaar se badalne wale contexts ko alag karein.
</Ur>
</Tr>

```text
function AuthProvider({ children }) {
  const [user, setUser] = useState(null);

  // Without useMemo: a new object every time AuthProvider re-renders,
  // so every useContext(AuthContext) caller re-renders too.
  const value = useMemo(() => ({ user, login: setUser, logout: () => setUser(null) }), [user]);

  return <AuthContext value={value}>{children}</AuthContext>;
}

// Fast-changing data (mouse position, typing) doesn't belong in the same
// context as slow-changing data (user, theme). Give each its own context.
```

<Happened>
<Tr>
<En>

- With `useMemo`, the value object only changes when `user` changes, so consumers re-render only on login or logout.
- Context is great for **rarely changing, widely needed** data. For data that changes many times a second, or large app state with many parts, a state library (Zustand, Redux Toolkit) lets components subscribe to only the slice they use.

</En>
<Ur>

- `useMemo` ke saath value object sirf tab badalta hai jab `user` badle, isliye consumers sirf login ya logout par dobara render hote hain.
- Context **kam badalne wale, har jagah chahiye hone wale** data ke liye behtareen hai. Second me kai dafa badalne wale data, ya bohot hisson wali bari app state ke liye, state library (Zustand, Redux Toolkit) components ko sirf usi hisse ko subscribe karne deti hai jo wo istemal karte hain.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Reading context with no provider above">

```jsx
const CartContext = createContext(null);
function Header() {
  const { items } = useContext(CartContext);   // TypeError: null
}
```

</Bad>
<Good title="A custom hook with a clear error">

```jsx
function useCart() {
  const cart = useContext(CartContext);
  if (!cart) throw new Error("useCart must be used inside <CartProvider>");
  return cart;
}
```

</Good>
</Compare>

<Compare>
<Bad title="Showing a ref on screen">

```jsx
const clicks = useRef(0);
<button onClick={() => clicks.current++}>Clicked {clicks.current}</button>
// the number never updates
```

</Bad>
<Good title="Use state for what is displayed">

```jsx
const [clicks, setClicks] = useState(0);
<button onClick={() => setClicks(clicks + 1)}>Clicked {clicks}</button>
```

</Good>
</Compare>

<Compare>
<Bad title="Using ref.current during render">

```jsx
const inputRef = useRef(null);
inputRef.current.focus();          // null on the first render: crash
return <input ref={inputRef} />;
```

</Bad>
<Good title="Use it in an effect or a handler">

```jsx
const inputRef = useRef(null);
useEffect(() => inputRef.current.focus(), []);
return <input ref={inputRef} />;
```

</Good>
</Compare>

<Compare>
<Bad title="useCallback without memo">

```jsx
const handleClick = useCallback(() => setOpen(true), []);
return <button onClick={handleClick}>Open</button>;
```

<Tr>
<En>Extra code for no benefit: `<button>` isn't memoised.</En>
<Ur>Bina faide ke izafi code: `<button>` memoised nahi.</Ur>
</Tr>

</Bad>
<Good title="Keep it simple">

```jsx
return <button onClick={() => setOpen(true)}>Open</button>;
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Putting everything in one giant context.** Any change re-renders every consumer. Split by topic.
- **Using context to avoid passing props one or two levels.** Plain props are clearer for short distances.
- **Missing dependencies in `useMemo`/`useCallback`**, which return stale values. The lint rule catches these.
- **Using `useMemo` for side effects.** It's for calculating values; side effects go in `useEffect`.
- **Changing a ref during render** (except for one-time initialisation). Refs are for handlers and effects.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sab kuch ek bare context me rakhna.** Koi bhi tabdeeli har consumer ko dobara render karti hai. Mauzu ke hisaab se alag karein.
- **Ek do satah props dene se bachne ke liye context istemal karna.** Chhote faslon ke liye saade props zyada saaf hain.
- **`useMemo`/`useCallback` me dependencies chhor dena**, jo purani values wapas karti hain. Lint rule inhe pakarta hai.
- **Side effects ke liye `useMemo`.** Ye values nikalne ke liye hai; side effects `useEffect` me jate hain.
- **Render ke dauran ref badalna** (ek dafa ki shuruaat ke ilawa). Refs handlers aur effects ke liye hain.

</Ur>
</Tr>

```jsx preview h=180
    if (!form.name.trim()) {
      nameRef.current.focus();
      setMessage("Please enter your name.");
      return;
    }
    if (!form.email.trim()) {
      emailRef.current.focus();
      setMessage("Please enter your email.");
      return;
    }
    setMessage("Sent!");
  }

  return (
    <div style={{ display: "grid", gap: 8, maxWidth: 260 }}>
      <input ref={nameRef} value={form.name} onChange={(e) => setForm({ ...form, name: e.target.value })} placeholder="Name" />
      <input ref={emailRef} value={form.email} onChange={(e) => setForm({ ...form, email: e.target.value })} placeholder="Email" />
      <button onClick={submit}>Submit</button>
      <p>{message}</p>
    </div>
  );
}
```

<DeepDive title="More about these hooks">

**Context lookup.** `useContext` finds the **nearest** provider above the component. Providers can be nested to override a value for one part of the tree (a dark sidebar inside a light page).

**Context and `memo`.** A `memo` component still re-renders when a context it reads changes; `memo` only looks at props.

**`use(Context)`** (React 19) reads a context like `useContext`, but can be called inside conditions and loops.

**Refs to your own components.** In React 19, `ref` is a normal prop for function components: `function Input({ ref, ...props }) { return <input ref={ref} {...props} />; }`. Older code used `forwardRef`. `useImperativeHandle` lets a component expose a limited API (for example only `focus()`) through its ref.

**Callback refs.** `ref={(node) => { … }}` runs when the element is attached and detached; in React 19 it can return a cleanup function. Useful for measuring elements.

**Previous value pattern.**

```text
function usePrevious(value) {
  const ref = useRef();
  useEffect(() => { ref.current = value; }, [value]);
  return ref.current;   // the value from the previous render
}
```

**`useMemo` is a hint.** React may throw away a memoised value (for example to free memory) and recompute it, so never rely on it for correctness, only for performance.

**`memo` with a custom comparison.** `memo(Component, (prev, next) => prev.id === next.id)` replaces the default shallow props check.

**React Compiler.** It analyses components at build time and inserts the equivalent of `useMemo`, `useCallback` and `memo` automatically. With it enabled, most manual memoisation becomes unnecessary; the compiler requires components to follow the rules of React (pure render, no mutation of props or state).

**Other hooks worth knowing:** `useReducer` (state with many update types), `useId` (stable ids for labels), `useTransition` and `useDeferredValue` (keep typing responsive during heavy updates), `useSyncExternalStore` (subscribe to non-React stores), `useOptimistic` and `useActionState` (React 19 form actions).

</DeepDive>

<DeepDive title="Real world: the dashboard that slowed to a crawl">

An analytics dashboard had one big context:

```jsx
<AppContext.Provider value={{ user, theme, filters, setFilters, liveVisitors }}>
```

`liveVisitors` updated every second from a WebSocket. Because the provider created a new object every render, and every widget called `useContext(AppContext)`, **every chart re-rendered every second**, even charts that only used `theme`. On older laptops the page stuttered and typing in the filter box lagged.

The team fixed it in three steps:

1. **Split the context** into `UserContext`, `ThemeContext`, `FiltersContext` and `LiveContext`, so a widget re-renders only when what it reads changes.
2. **Memoised provider values** with `useMemo`, so re-rendering a provider for unrelated reasons didn't produce a new value.
3. **Wrapped heavy chart components in `memo`** and passed `useCallback` handlers, after confirming with the Profiler that they were the expensive part.

Render time per second dropped from about 180 ms to under 10 ms. The lesson they wrote in their docs: "Context is for sharing, not for fast-changing state; measure before memoising, then memoise the expensive part."

</DeepDive>

<DeepDive title="Security lens">

These hooks change how data flows, so they affect what can leak and where.

- **Context is not a security boundary.** Anything in a context provider on the client is in the browser's memory and visible with React DevTools. An `AuthContext` that holds `isAdmin: true` only controls what the UI shows; every admin API must check permissions on the server.
- **Don't put secrets in context.** API keys, refresh tokens or other users' data placed in a top-level provider are reachable from any component and any browser extension. Keep tokens in HttpOnly cookies handled by the server.
- **Clear sensitive state on logout.** Providers that cache user data (cart, messages, profile) should reset when the user logs out; otherwise the next person on a shared computer may see it. Remounting the provider with a `key` tied to the user id is a simple way.
- **DOM refs bypass React's escaping.** `ref.current.innerHTML = userText` reintroduces cross-site scripting that JSX normally prevents. Use `textContent`, or let React render the text.
- **Refs to third-party widgets.** When you pass a DOM node to a non-React library (maps, editors, payment fields), that library has full control of it; load such scripts only from trusted sources and keep them updated.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the Context API and when should you use it?">
Context lets a parent provide a value that any descendant can read with useContext, avoiding prop drilling. It suits widely needed, infrequently changing data such as theme, locale and the authenticated user. Every consumer re-renders when the value changes, so fast-changing or large state is often better in a dedicated state library.
</QA>

<QA q="What is the difference between useRef and useState?">
Both persist values across renders. Updating state schedules a re-render so the UI reflects the new value; mutating ref.current does not trigger a render. Use state for anything displayed, and refs for DOM elements and values used only by code, such as timer ids or previous values.
</QA>

<QA q="How do you access a DOM element in React?">
Create a ref with useRef(null), pass it to the element's ref attribute, and read ref.current in an event handler or effect after the element has mounted. During the first render it is still null.
</QA>

<QA q="What do useMemo and useCallback do?">
useMemo caches the result of a calculation between renders and recomputes it only when its dependencies change. useCallback caches a function definition the same way. They are used to avoid expensive recalculation and to keep object and function references stable for memoised children and effect dependencies.
</QA>

<QA q="What is React.memo and how does it relate to useCallback?">
memo wraps a component so React skips re-rendering it when its props are shallowly equal to the previous props. Functions and objects created during the parent's render are new each time, which defeats memo; useCallback and useMemo keep those props referentially stable so memo can work.
</QA>

<QA q="Why can overusing useMemo and useCallback be harmful?">
Each adds memory use, dependency comparisons on every render and code complexity, and incorrect dependency lists cause stale values. For cheap calculations or props passed to non-memoised components they provide no benefit. Optimise based on profiling, or rely on the React Compiler.
</QA>

<QA q="Why do all context consumers re-render when the provider re-renders?">
If the provider passes a new object or array as its value on each render, the value is not equal to the previous one, so React re-renders every component that reads it. Memoising the value with useMemo and splitting unrelated data into separate contexts limits these re-renders.
</QA>

</DeepDive>
