<BigIdea>
<Tr>
<En>
A **route** is a rule: "for **this method** and **this path pattern**, run **this function**". Paths can contain **parameters**: in `/users/:userId/orders/:orderId`, the parts after `:` match anything in that position and arrive in **`req.params`** as **strings**. The **query string** after `?` (`/search?q=mug&max=20`) arrives in **`req.query`**, also as strings (and as an array when a key repeats). Express checks routes **in the order you register them** and uses the first match, so specific paths like `/products/count` must come before `/products/:id`. As an API grows, you group related routes in an **`express.Router()`**, a mini-app with its own routes and middleware, and **mount** it under a prefix such as `/api/v1/products`. `router.param("id", …)` validates and loads a resource once for every route that uses `:id`, and `router.route("/:id")` chains several methods on one path, with `.all()` returning **405 Method Not Allowed** for the rest. Express 5 uses a stricter path syntax: named wildcards (`/*filepath`) and braces for optional parts (`/:year{.:format}`).
</En>
<Ur>
**Route** ek qaida hai: "**is method** aur **is path pattern** ke liye **ye function** chalao". Paths me **parameters** ho sakte hain: `/users/:userId/orders/:orderId` me `:` ke baad wale hisse us jagah kuch bhi milate hain aur **`req.params`** me **strings** ban kar aate hain. `?` ke baad ki **query string** (`/search?q=mug&max=20`) **`req.query`** me aati hai, ye bhi strings (aur key dohraye to array). Express routes ko **us tarteeb se** check karta hai jis me aap unhen register karte hain aur pehla milan istemal karta hai, isliye `/products/count` jaise mukhsoos paths `/products/:id` se pehle aane chahiyen. API barhne par aap mutaliqa routes ko **`express.Router()`** me jama karte hain, apne routes aur middleware wali mini-app, aur use `/api/v1/products` jaise prefix ke neeche **mount** karte hain. `router.param("id", …)` `:id` istemal karne wale har route ke liye resource ek dafa validate aur load karta hai, aur `router.route("/:id")` ek path par kai methods jorta hai, baqi ke liye `.all()` **405 Method Not Allowed** deta hai. Express 5 sakht path syntax istemal karta hai: naam wale wildcards (`/*filepath`) aur ikhtiyari hisson ke liye braces (`/:year{.:format}`).
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **large office building**.

- The **street address** gets you to the building (the host and port); the **floor and room number** (the path) gets you to the right office: `/floor/3/room/12`.
- A sign that says "Room **any number** on floor 3 → reception of department C" is a **route parameter**: one rule for many rooms.
- Notes you hand over at reception, like "ask for someone who speaks French, ground floor only", are the **query string**: they don't change which office you go to, they shape what you get there.
- Each **department** has its own reception and internal directory (a **Router**); the lobby only knows "Sales is on floor 2" (mounting under a prefix).
- Signs are read **top to bottom**: if "any room → reception" is written above "room 99 → server room", nobody ever reaches the server room (route order).

</En>
<Ur>

**Bari daftari imarat** ka sochein.

- **Gali ka pata** aap ko imarat tak le jata hai (host aur port); **manzil aur kamre ka number** (path) sahi daftar tak: `/floor/3/room/12`.
- Board jis par likha ho "manzil 3 par **koi bhi** kamra → shoba C ka reception" **route parameter** hai: bohot se kamron ke liye ek qaida.
- Reception par diye gaye note, jaise "French bolne wala chahiye, sirf ground floor", **query string** hain: ye nahi badalte ke aap kis daftar jate hain, balke ye ke wahan kya milta hai.
- Har **shoba** ka apna reception aur andaruni fehrist hai (**Router**); lobby sirf janti hai "Sales doosri manzil par hai" (prefix ke neeche mount karna).
- Boards **upar se neeche** parhe jate hain: agar "koi bhi kamra → reception" "kamra 99 → server room" se upar likha ho to koi kabhi server room tak nahi pohanchta (routes ki tarteeb).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Params, wildcards, optional parts and query strings">

<Tr>
<En>
This app shows every kind of route pattern. The loop calls each URL and prints exactly what Express put into `req.params` or `req.query`.
</En>
<Ur>
Ye app har qism ka route pattern dikhati hai. Loop har URL call kar ke bilkul wahi print karta hai jo Express ne `req.params` ya `req.query` me rakha.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 --silent
cat > params.js <<'EOF'
import express from "express";
const app = express();

app.get("/users/:userId/orders/:orderId", (req, res) => {
  res.json({ params: req.params, types: [typeof req.params.userId, typeof req.params.orderId] });
});
app.get("/files/*filepath", (req, res) => res.json({ filepath: req.params.filepath }));
app.get("/reports/:year{.:format}", (req, res) => res.json(req.params));
app.get("/products/count", (req, res) => res.json({ route: "count" }));
app.get("/products/:id", (req, res) => res.json({ route: ":id", id: req.params.id }));
app.get("/search", (req, res) => res.json({ query: req.query }));

app.listen(3000);
EOF
node params.js &
sleep 1
for p in /users/42/orders/1001 /files/docs/2026/invoice.pdf /reports/2026 /reports/2026.csv /products/count /products/7 /products/hello \
         "/search?q=mug&max=20" "/search?tag=blue&tag=ceramic" "/search?filter[price]=10"; do
  printf "%-32s %s\n" "$p" "$(curl -s -g "http://localhost:3000$p")"
done
kill %1
```

/files/docs/2026/invoice.pdf     {"filepath":["docs","2026","invoice.pdf"]}
/reports/2026                    {"year":"2026"}
/reports/2026.csv                {"year":"2026","format":"csv"}
/products/count                  {"route":"count"}
/products/7                      {"route":":id","id":"7"}
/products/hello                  {"route":":id","id":"hello"}

<Happened>
<Tr>
<En>

- **Params are always strings**: `"42"`, not `42`. Convert and validate them (`/products/hello` reached the `:id` route with `id: "hello"`, which you must reject).
- The named wildcard `*filepath` captured the rest of the path as an **array** of segments in Express 5 (join with `/` if you need a string, and never pass it straight to the file system).
- `{.:format}` made the extension optional: `/reports/2026` and `/reports/2026.csv` both matched.
- `/products/count` was answered by the `count` route because it was registered **first**. Swap the two and `count` would be treated as an id.
- Query values are strings; a repeated key (`tag`) became an array. Express 5's default "simple" query parser doesn't build nested objects, so `filter[price]=10` stays a flat key named `filter[price]`. That's safer (no surprise objects), and if you need nested queries you can opt into the extended parser.

</En>
<Ur>

- **Params hamesha strings hain**: `"42"`, `42` nahi. Unhen badlein aur validate karein (`/products/hello` `id: "hello"` ke saath `:id` route tak pohancha, jise aap ko radd karna hai).
- Naam wale wildcard `*filepath` ne Express 5 me path ka baqi hissa segments ki **array** ki tarah pakra (string chahiye to `/` se jorein, aur ise kabhi seedha file system ko na dein).
- `{.:format}` ne extension ikhtiyari kiya: `/reports/2026` aur `/reports/2026.csv` dono mile.
- `/products/count` ka jawab `count` route ne diya kyun ke wo **pehle** register hua. Dono ki jagah badlein to `count` id samjha jata.
- Query values strings hain; dohrayi key (`tag`) array ban gayi. Express 5 ka default "simple" query parser nested objects nahi banata, isliye `filter[price]=10` `filter[price]` naam ki seedhi key rehti hai. Ye zyada mehfooz hai (achanak objects nahi), aur nested queries chahiyen to aap extended parser chun sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Routers, router.param and app.route">

<Tr>
<En>
Now a structured version: each resource gets a **Router** in its own file. `router.param("id")` validates the id and loads the product **once** for all `:id` routes, and `router.route("/:id")` defines GET and DELETE plus a 405 for everything else. The router is mounted at `/api/v1/products`.
</En>
<Ur>
Ab munazzam version: har resource ko apni file me **Router** milta hai. `router.param("id")` id validate kar ke tamam `:id` routes ke liye product **ek dafa** load karta hai, aur `router.route("/:id")` GET aur DELETE plus baqi har cheez ke liye 405 banata hai. Router `/api/v1/products` par mount hota hai.
</Ur>
</Tr>

```bash
mkdir -p routes
cat > routes/products.js <<'EOF'
import { Router } from "express";

const products = [{ id: 1, name: "Mug", price: 12 }, { id: 2, name: "Desk Lamp", price: 30 }];
export const productsRouter = Router();

// Runs for every route below that has :id: validate once, attach the product
productsRouter.param("id", (req, res, next, value) => {
  const id = Number(value);
  if (!Number.isInteger(id) || id < 1) return res.status(400).json({ error: "id must be a positive integer" });
  const product = products.find((p) => p.id === id);
  if (!product) return res.status(404).json({ error: `Product ${id} not found` });
  req.product = product;
  next();
});

productsRouter
  .route("/")
  .get((req, res) => res.json(products))
  .post((req, res) => res.status(201).json({ todo: "create" }));

productsRouter
  .route("/:id")
  .get((req, res) => res.json(req.product))
  .delete((req, res) => res.sendStatus(204))
  .all((req, res) => res.set("Allow", "GET, DELETE").status(405).json({ error: "Method not allowed" }));
EOF
cat > routes/health.js <<'EOF'
import { Router } from "express";
export const healthRouter = Router();
healthRouter.get("/", (req, res) => res.json({ status: "ok" }));
EOF
cat > app.js <<'EOF'
import express from "express";
import { productsRouter } from "./routes/products.js";
import { healthRouter } from "./routes/health.js";

const app = express();
app.use("/api/v1/products", productsRouter);   // every route in the router gets this prefix
app.use("/health", healthRouter);
app.listen(3000);
EOF
node app.js &
sleep 1
c() { printf "%-32s %s\n" "$1 $2" "$(curl -s -X $1 -w ' → %{http_code}' "http://localhost:3000$2")"; }
c GET /api/v1/products
c GET /api/v1/products/2
c GET /api/v1/products/99
c GET /api/v1/products/abc
c DELETE /api/v1/products/1
c PATCH /api/v1/products/1
c GET /API/V1/PRODUCTS/1
c GET /api/v1/products/1/
c GET /health
kill %1
```

<Happened>
<Tr>
<En>

- Inside the router, paths are **relative**: `"/:id"` became `/api/v1/products/:id` when mounted. Moving the whole resource to `/api/v2` is a one-line change in `app.js`.
- `router.param` answered **400** for `abc` and **404** for 99 before any route handler ran, and attached `req.product` for the others. The GET handler is a single line.
- `.all()` on the same route answered **405** with an `Allow` header for `PATCH`, which tells clients which methods exist.
- By default Express routing is **case-insensitive** and ignores a **trailing slash** (`/API/V1/PRODUCTS/1` and `/1/` both matched). Turn on `caseSensitive`/`strict` in `Router({ ... })` if you need exact matching.
- `/health` lives in its own small router: the pattern stays the same as the app grows to dozens of resources.

</En>
<Ur>

- Router ke andar paths **relative** hain: mount hone par `"/:id"` `/api/v1/products/:id` ban gaya. Poore resource ko `/api/v2` par le jana `app.js` me ek line ki tabdeeli hai.
- `router.param` ne kisi route handler ke chalne se pehle `abc` ke liye **400** aur 99 ke liye **404** diya, aur baqi ke liye `req.product` joda. GET handler ek line ka hai.
- Usi route par `.all()` ne `PATCH` ke liye `Allow` header ke saath **405** diya, jo clients ko batata hai ke kaun se methods maujood hain.
- Default me Express routing **case-insensitive** hai aur **aakhri slash** ko nazar andaz karti hai (`/API/V1/PRODUCTS/1` aur `/1/` dono mile). Bilkul milan chahiye to `Router({ ... })` me `caseSensitive`/`strict` on karein.
- `/health` apne chhote router me hai: app ke darjanon resources tak barhne par bhi pattern wahi rehta hai.

</Ur>
</Tr>
</Happened>

<Step title="Designing clean routes">

<Tr>
<En>

Good REST-style routes follow a few conventions:

| Action | Method + path | Success status |
| --- | --- | --- |
| List products (filtered, paginated) | `GET /api/v1/products?category=mugs&page=2` | 200 |
| Get one product | `GET /api/v1/products/:id` | 200 (404 if missing) |
| Create a product | `POST /api/v1/products` | 201 + `Location` |
| Replace a product | `PUT /api/v1/products/:id` | 200 or 204 |
| Update some fields | `PATCH /api/v1/products/:id` | 200 |
| Delete a product | `DELETE /api/v1/products/:id` | 204 |
| A user's orders | `GET /api/v1/users/:userId/orders` | 200 |
| An action that isn't CRUD | `POST /api/v1/orders/:id/cancel` | 200 / 202 |

</En>
<Ur>

Achhe REST andaz ke routes chand riwayaat follow karte hain:

| Amal | Method + path | Kamyabi ka status |
| --- | --- | --- |
| Products ki list (filter, pages) | `GET /api/v1/products?category=mugs&page=2` | 200 |
| Ek product | `GET /api/v1/products/:id` | 200 (na ho to 404) |
| Product banana | `POST /api/v1/products` | 201 + `Location` |
| Product poora badalna | `PUT /api/v1/products/:id` | 200 ya 204 |
| Kuch fields update | `PATCH /api/v1/products/:id` | 200 |
| Product mitana | `DELETE /api/v1/products/:id` | 204 |
| User ke orders | `GET /api/v1/users/:userId/orders` | 200 |
| Aisa amal jo CRUD nahi | `POST /api/v1/orders/:id/cancel` | 200 / 202 |

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- **Nouns in paths, verbs in methods**: `POST /products`, not `/createProduct`.
- Plural, lowercase, hyphenated names: `/order-items`, not `/OrderItem`.
- Keep nesting shallow (one level). `/orders/:id` is better than `/users/:u/orders/:o/items/:i` when IDs are unique anyway.
- Never put secrets or personal data in paths or query strings (they end up in logs, browser history and analytics); use the body or headers.
- The APIs module covers REST design, pagination and versioning in depth.

</En>
<Ur>

- **Paths me ism, methods me fe'l**: `POST /products`, `/createProduct` nahi.
- Jama, chhote huroof, hyphen wale naam: `/order-items`, `/OrderItem` nahi.
- Nesting kam rakhein (ek level). IDs pehle se unique hon to `/users/:u/orders/:o/items/:i` se `/orders/:id` behtar hai.
- Raaz ya zaati data kabhi paths ya query strings me na rakhein (ye logs, browser history aur analytics me jate hain); body ya headers lein.
- APIs module REST design, pagination aur versioning gehrai se samjhata hai.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Generic route registered before the specific one">

```text
router.get("/:id", getProduct);
router.get("/count", countProducts);   // never reached: "count" matches :id first
```

</Bad>
<Good title="Specific first (or validate the param)">

```text
router.get("/count", countProducts);
router.get("/:id", getProduct);        // plus router.param("id", …) to reject non-numbers
```

</Good>
</Compare>

<Compare>
<Bad title="Trusting params and query values">

```text
router.get("/:id", async (req, res) => {
  const product = await db.query(`SELECT * FROM products WHERE id = ${req.params.id}`);   // SQL injection!
  const limit = req.query.limit;                                                       // "1000000" or ["1","2"]
});
```

</Bad>
<Good title="Convert, validate, parameterise">

```text
const id = z.coerce.number().int().positive().parse(req.params.id);
const limit = z.coerce.number().int().min(1).max(100).default(20).parse(req.query.limit);
const product = await db.query("SELECT * FROM products WHERE id = $1", [id]);
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Express 4 wildcard syntax in Express 5** (`app.get("*", …)`, `/:id?`): it now throws "Missing parameter name"; use `/*splat` and `{/:id}`.
- **Forgetting `mergeParams: true`** on a nested router, so `req.params.userId` is `undefined` inside it.
- **Using query strings for identity** (`/orders?id=7`) when a path param fits better, or path params for optional filters.
- **No 404/405 handling**, so clients get HTML pages or confusing errors.
- **Huge route files** with every resource in `app.js`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Express 5 me Express 4 ka wildcard syntax** (`app.get("*", …)`, `/:id?`): ye ab "Missing parameter name" throw karta hai; `/*splat` aur `{/:id}` lein.
- Nested router par **`mergeParams: true` bhoolna**, jis se us ke andar `req.params.userId` `undefined` hota hai.

- **404/405 handling nahi**, jis se clients ko HTML pages ya uljhe errors milte hain.
- `app.js` me har resource ke saath **bari route files**.

</Ur>
</Tr>

<DeepDive title="More about routing">

**How matching works.** Express compiles each path with path-to-regexp into a regular expression. Express 5 (path-to-regexp v8) removed inline regex in strings (`/:id(\\d+)`) to prevent ReDoS; validate in `router.param` or middleware instead, or pass a real `RegExp` object as the path.

**`next("route")`.** Inside a route handler, `next("route")` skips the remaining handlers of the current route and continues with the next matching route; `next("router")` leaves the current router.

**Query parser settings.** `app.set("query parser", "extended")` enables nested objects with the `qs` library (`filter[price][lt]=10`); keep "simple" unless you need it, and validate either way.

**Router-level middleware.** `router.use(requireAuth)` protects every route in that router only, a clean way to secure `/admin` routes.

**Route listing.** Express doesn't list routes for you; tools like `express-list-endpoints` help, and OpenAPI generators document them.

**Performance.** Linear matching is fine for hundreds of routes. Frameworks like Fastify use radix trees for faster matching with thousands of routes.

</DeepDive>

<DeepDive title="Real world: the route that showed everyone's invoices">

An accounting SaaS had a route `GET /api/invoices/:id/pdf` that streamed an invoice PDF. Authentication middleware checked that the user was logged in, and the handler loaded `Invoice.findById(req.params.id)` and streamed the file.

A customer noticed that their invoice IDs were sequential (`/api/invoices/10231/pdf`) and tried `10230`. They got another company's invoice, including addresses and amounts. A simple script could have downloaded every invoice in the system.

The problem wasn't the routing syntax; it was what the route trusted. `:id` came from the URL, and the handler never checked whether the invoice belonged to the logged-in customer (an IDOR, insecure direct object reference).

The fixes:

1. A `router.param("invoiceId")` loaded the invoice **scoped to the current account** (`findOne({ id, accountId: req.user.accountId })`) and answered 404 otherwise, for every invoice route at once.
2. Public IDs became random UUIDs instead of sequential numbers, so they couldn't be guessed (defence in depth, not a replacement for the check).
3. Automated tests requested another tenant's resources for every route and expected 404.
4. Access logs were reviewed to confirm no one had scraped invoices before the fix.

</DeepDive>

<DeepDive title="Security lens">

- **Validate every param and query value** (type, range, format); they're attacker-controlled strings.
- **Authorise per resource**: loading by `:id` must also check ownership (IDOR is one of the most common API vulnerabilities).
- **Wildcard params and the file system**: never join `req.params.filepath` into a path without traversal checks.
- **Parameterised database queries** only; never put params into SQL strings.
- **Limits on list endpoints**: cap `limit`/`pageSize` so clients can't request millions of rows.
- **Don't leak existence**: return 404 for resources the user can't access, not 403, when the existence itself is sensitive.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between req.params, req.query and req.body?">
req.params holds named route parameters from the path, such as id in /products/:id. req.query holds the parsed query string after the question mark, used for filters, search and pagination. req.body holds the parsed request body, which requires body-parsing middleware like express.json. All are client-controlled and must be validated.
</QA>

<QA q="What is express.Router used for?">
It creates a modular, mountable set of routes and middleware, so related routes can live in their own file and be attached under a prefix with app.use, for example to version an API or apply authentication to a group of routes.
</QA>

<QA q="Why does route order matter in Express?">
Express checks middleware and routes in the order they're registered and stops at the first handler that sends a response, so generic patterns like /:id must come after specific paths like /count, and catch-all handlers like 404 must come last.
</QA>

<QA q="What changed in route path syntax in Express 5?">
Express 5 uses path-to-regexp v8: wildcards must be named, like /*splat, optional parts are wrapped in curly braces, the question-mark optional parameter syntax and inline regular expressions in strings were removed, which reduces ReDoS risks.
</QA>

<QA q="How would you handle a 405 Method Not Allowed in Express?">
Define the supported methods on a route with router.route(path) and add .all() at the end that sets an Allow header listing the supported methods and responds with status 405.
</QA>

</DeepDive>
