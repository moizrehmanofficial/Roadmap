<BigIdea>
<Tr>
<En>
In the Building an HTTP Server lesson, you wrote routing with `if` statements, parsed JSON bodies by hand, set headers yourself and wrapped everything in `try/catch`. **Express** packages all of that into a small, flexible framework. You create an **app**, register **routes** like `app.get("/products", handler)`, and each handler receives an enhanced **`req`** (with `req.params`, `req.query`, `req.body`) and **`res`** (with `res.json()`, `res.status()`, `res.redirect()`…). Cross-cutting features (parsing JSON, serving files, logging, security headers, authentication) are **middleware**: functions that run for many routes, added with `app.use()`. Express sets sensible headers for you (`Content-Type`, `Content-Length`, `ETag`), answers unknown routes with 404, and in **Express 5** catches errors from **async** handlers automatically and turns them into 500 responses without leaking details in production. It's minimal by design: Express doesn't choose your database, validation or folder structure, which is why it's everywhere and why the next lessons add those pieces.
</En>
<Ur>
Building an HTTP Server lesson me aap ne `if` statements se routing likhi, JSON bodies haath se parse kin, headers khud set kiye aur sab `try/catch` me lapeta. **Express** ye sab ek chhote, lachakdar framework me samet deta hai. Aap **app** banate hain, `app.get("/products", handler)` jaise **routes** register karte hain, aur har handler ko behtar **`req`** (`req.params`, `req.query`, `req.body` ke saath) aur **`res`** (`res.json()`, `res.status()`, `res.redirect()`… ke saath) milta hai. Har jagah lagne wali features (JSON parse karna, files dena, logging, security headers, authentication) **middleware** hain: functions jo bohot se routes ke liye chalte hain, `app.use()` se jorte hain. Express aap ke liye munasib headers set karta hai (`Content-Type`, `Content-Length`, `ETag`), na maloom routes ko 404 deta hai, aur **Express 5** me **async** handlers ke errors khud pakar kar unhen production me tafseelat leak kiye baghair 500 responses banata hai. Ye jaan boojh kar mukhtasar hai: Express aap ka database, validation ya folder structure nahi chunta, isi liye ye har jagah hai aur isi liye agle lessons ye hisse jorte hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **hotel front desk**.

- Without Express, you're the night porter doing everything by hand: answering the door, reading every guest's note, finding the right room, writing every receipt from scratch.
- Express is a **well-run reception**: a **directory** of who handles what ("room bookings → desk 2", "complaints → manager": routes), **standard forms** for receipts (`res.json`, `res.status`), and a **security guard, luggage scanner and concierge** that every guest passes before reaching a desk (middleware).
- If a desk has a problem it can't handle, the issue goes to the **duty manager** automatically (the error handler), who apologises politely to the guest without showing them the internal incident report.

</En>
<Ur>

**Hotel ke front desk** ka sochein.

- Express ke baghair aap raat ke chowkidar hain jo sab haath se karta hai: darwaza kholna, har mehman ka note parhna, sahi kamra dhoondhna, har raseed shuru se likhna.
- Express **achhi tarah chalti reception** hai: kaun kya sambhalta hai us ki **fehrist** ("kamra booking → desk 2", "shikayatein → manager": routes), raseedon ke **muqarrar form** (`res.json`, `res.status`), aur **security guard, saman scanner aur concierge** jin se har mehman desk tak pohanchne se pehle guzarta hai (middleware).
- Agar desk ko aisa masla ho jo wo na sambhal sake, to masla khud **duty manager** (error handler) tak jata hai, jo mehman se narmi se maafi mangta hai, andaruni incident report dikhaye baghair.

</Ur>
</Tr>

<Step title="Your first Express app">

<Tr>
<En>
Install Express, define two routes and start the server. Then look at the complete responses, headers included, for a known route, a JSON route and an unknown path.
</En>
<Ur>

npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 --silent

import express from "express";

const app = express();

app.get("/", (req, res) => {

<Step title="Response helpers and status codes">

<Tr>
<En>
The `res` object has a helper for every common answer. `res.status()` returns `res`, so calls can be **chained**. This app shows each helper and what the client actually receives.
</En>
<Ur>
`res` object me har aam jawab ke liye helper hai. `res.status()` `res` wapas karta hai, isliye calls **chain** ho sakti hain. Ye app har helper aur client ko asal me milne wali cheez dikhati hai.
</Ur>
</Tr>

```bash
cat > responses.js <<'EOF'
import express from "express";

const app = express();
app.disable("x-powered-by");           // don't advertise the framework

app.get("/text", (req, res) => res.send("plain text"));
app.get("/json", (req, res) => res.json({ id: 1, name: "Mug" }));
app.post("/products", (req, res) => res.status(201).json({ id: 4 }));
app.delete("/products/4", (req, res) => res.sendStatus(204));
app.get("/old-shop", (req, res) => res.redirect(301, "/shop"));
app.get("/report.csv", (req, res) => {
  res.type("csv").set("Cache-Control", "no-store");
  res.send("id,total\n1,42.50\n");
});

app.listen(3000);
EOF
node responses.js &
sleep 1
for req in "GET /text" "GET /json" "POST /products" "DELETE /products/4" "GET /old-shop" "GET /report.csv"; do
  set -- $req
  curl -s -X $1 -o body.txt -D headers.txt "http://localhost:3000$2"
  status=$(head -1 headers.txt | cut -d' ' -f2)
  type=$(grep -i "^content-type" headers.txt | cut -d' ' -f2- | tr -d '\r')
  extra=$(grep -i -E "^(location|cache-control):" headers.txt | tr -d '\r' | tr '\n' ' ')
  printf "%-20s %s  %-32s %s| %s\n" "$req" "$status" "${type:--}" "$extra" "$(tr '\n' ' ' < body.txt)"
done
echo "X-Powered-By headers in the last response: $(grep -ci "x-powered-by" headers.txt)"
kill %1
```

```text output

GET /json            200  application/json; charset=utf-8  | {"id":1,"name":"Mug"}

GET /report.csv      200  text/csv; charset=utf-8          Cache-Control: no-store | id,total 1,42.50

```

<Happened>
<Tr>
<En>

- **201** for a created resource, **204** with an empty body for a successful delete, **301** with a `Location` header for a moved page. `res.redirect` even added a small text body for old clients.
- `res.type("csv")` turned a short name into the full `Content-Type: text/csv`; `res.set()` adds any header.
- `app.disable("x-powered-by")` removed the framework banner (0 headers found). The helmet middleware does this and much more (Security Middleware lesson).
- Each handler must send **exactly one** response. Calling `res.json()` twice throws "Cannot set headers after they are sent"; use `return res.json(...)` in early exits.

</En>
<Ur>

- Bane resource ke liye **201**, kamyab delete ke liye khaali body ke saath **204**, muntaqil page ke liye `Location` header ke saath **301**. `res.redirect` ne purane clients ke liye chhoti text body bhi jori.
- `res.type("csv")` ne chhote naam ko poore `Content-Type: text/csv` me badla; `res.set()` koi bhi header jorta hai.
- `app.disable("x-powered-by")` ne framework ka banner hata diya (0 headers mile). helmet middleware ye aur bohot kuch karta hai (Security Middleware lesson).
- Har handler ko **bilkul ek** response bhejna chahiye. `res.json()` do dafa call karna "Cannot set headers after they are sent" throw karta hai; jaldi nikalne ke liye `return res.json(...)` lein.

</Ur>
</Tr>
</Happened>

<Step title="Built-in middleware: static files and JSON bodies">

<Tr>
<En>
Two middleware functions ship with Express. `express.static("public")` serves files from a folder (with correct content types and path-traversal protection). `express.json()` reads JSON request bodies and puts the parsed object on `req.body`.
</En>
<Ur>
Express ke saath do middleware functions aate hain. `express.static("public")` folder se files deta hai (sahi content types aur path-traversal hifazat ke saath). `express.json()` JSON request bodies parh kar parse hua object `req.body` par rakhta hai.
</Ur>
</Tr>

```bash
mkdir -p public && echo "<h1>Acme Store</h1>" > public/index.html && echo "h1 { color: teal; }" > public/site.css
cat > static.js <<'EOF'
import express from "express";

const app = express();
app.use(express.static("public"));        // serves files from ./public
app.use(express.json());                   // parses JSON request bodies into req.body

app.post("/echo", (req, res) => {
  res.json({ youSent: req.body, type: typeof req.body.qty });
});

app.listen(3000);
EOF
node static.js &
sleep 1
curl -s http://localhost:3000/
curl -s -o /dev/null -w "site.css: %{http_code} %{content_type}\n" http://localhost:3000/site.css
curl -s -X POST -H "Content-Type: application/json" -d '{"name":"Mug","qty":2}' http://localhost:3000/echo; echo
kill %1
```

```text output
<h1>Acme Store</h1>
site.css: 200 text/css; charset=utf-8
{"youSent":{"name":"Mug","qty":2},"type":"number"}
```

<Happened>
<Tr>
<En>

- `/` served `public/index.html` automatically; `site.css` got `text/css`. In the raw `node:http` version this took a whole function with a traversal check.
- `express.json()` parsed the body, so `req.body.qty` is the **number** 2. Without the middleware, `req.body` is `undefined`.
- `app.use(fn)` runs `fn` for every request, in the order you add them. `express.json()` has a default body limit of 100 KB and only parses requests whose `Content-Type` is JSON.
- Parsed doesn't mean valid: `req.body` is whatever the client sent. Validate it before use (Validation with zod lesson).

</En>
<Ur>

- `/` ne khud `public/index.html` diya; `site.css` ko `text/css` mila. Kache `node:http` version me is ke liye traversal check ke saath poora function laga tha.
- `express.json()` ne body parse ki, isliye `req.body.qty` **number** 2 hai. Middleware ke baghair `req.body` `undefined` hai.
- `app.use(fn)` har request ke liye `fn` chalata hai, us tarteeb me jis me aap jorte hain. `express.json()` ki default body limit 100 KB hai aur ye sirf wo requests parse karta hai jin ka `Content-Type` JSON ho.
- Parse hone ka matlab durust hona nahi: `req.body` wahi hai jo client ne bheja. Istemal se pehle validate karein (Validation with zod lesson).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Errors in async handlers (Express 5)">

<Tr>
<En>
In Express 4, an error thrown inside an `async` handler was an unhandled rejection: the request hung or the process crashed. **Express 5** catches rejected promises and sends them to the error handler. With `NODE_ENV=production`, the client gets a generic message while the details go to the server's log.
</En>
<Ur>
Express 4 me `async` handler ke andar throw hua error unhandled rejection tha: request latki rehti ya process crash hota. **Express 5** reject hue promises pakar kar unhen error handler ko bhejta hai. `NODE_ENV=production` ke saath client ko aam paighaam milta hai jab ke tafseelat server ke log me jati hain.
</Ur>
</Tr>

```bash
cat > errors.js <<'EOF'
import express from "express";

const app = express();

async function loadOrders() {
  throw new Error("Database connection refused (db-7.internal:5432)");
}

// Express 5: a rejected promise from an async handler goes to the error handler
app.get("/orders", async (req, res) => {
  const orders = await loadOrders();
  res.json(orders);
});

app.listen(3000);
EOF
NODE_ENV=production node errors.js 2>server.log &
sleep 1
curl -s -w "\nstatus: %{http_code}\n" http://localhost:3000/orders | grep -E "<pre>|status"
sleep 0.3
kill %1
echo "--- server log (first line):"
head -1 server.log
```

```text output
<pre>Internal Server Error</pre>
status: 500
--- server log (first line):
Error: Database connection refused (db-7.internal:5432)
```

<Happened>
<Tr>
<En>

- The client saw only "Internal Server Error" with status **500**; the internal host name and port stayed out of the response.
- The full error and stack went to stderr (our `server.log`). In development (`NODE_ENV` not `production`) Express shows the stack in the page to help you debug, which is why `NODE_ENV=production` matters in production.
- The process kept running. In Express 4 you'd need `try/catch` in every async handler or a wrapper like `express-async-errors`.
- The default error page is HTML. APIs should add their own error-handling middleware that returns JSON and logs with context (Error Handling Middleware lesson).

</En>
<Ur>

- Client ne sirf status **500** ke saath "Internal Server Error" dekha; andaruni host ka naam aur port response se bahar rahe.
- Poora error aur stack stderr (hamari `server.log`) me gaya. Development me (`NODE_ENV` `production` na ho) Express debugging me madad ke liye page me stack dikhata hai, isi liye production me `NODE_ENV=production` ahem hai.
- Process chalta raha. Express 4 me har async handler me `try/catch` ya `express-async-errors` jaisa wrapper chahiye hota.
- Default error page HTML hai. APIs ko apna error-handling middleware jorna chahiye jo JSON de aur context ke saath log kare (Error Handling Middleware lesson).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="How a request flows through an app">

<Tr>
<En>

Every request walks down the list of middleware and routes **in the order they were added**, until one sends a response:

```text
request ─▶ app.use(helmet())           security headers         (calls next)
        ─▶ app.use(express.json())     parse body               (calls next)
        ─▶ app.use(requestLogger)      log method + path        (calls next)
        ─▶ app.get("/health", …)       path doesn't match       (skipped)
        ─▶ app.get("/products", …)     matches → res.json(...)  ◀─ response sent, chain stops
        ─▶ app.use(notFound)           only reached if nothing answered
        ─▶ app.use(errorHandler)       only reached when something called next(err) or threw
```

</En>
<Ur>

Har request middleware aur routes ki list me **us tarteeb se** chalti hai jis me unhen joda gaya, jab tak koi response na bhej de:

```text
request ─▶ app.use(helmet())           security headers         (next call karta hai)
        ─▶ app.use(express.json())     body parse               (next call karta hai)
        ─▶ app.use(requestLogger)      method + path log        (next call karta hai)
        ─▶ app.get("/health", …)       path nahi milta          (chhor diya)
        ─▶ app.get("/products", …)     milta hai → res.json(...) ◀─ response gaya, zanjeer ruki
        ─▶ app.use(notFound)           sirf tab jab kisi ne jawab na diya
        ─▶ app.use(errorHandler)       sirf tab jab kisi ne next(err) call kiya ya throw kiya
```

</Ur>
</Tr>

<Tr>

- **Order matters**: `express.json()` must come before routes that read `req.body`; the 404 and error handlers go **last**.
- A middleware either sends a response or calls `next()` to pass the request on. Forgetting both leaves the client waiting forever.
- The next three lessons zoom into this picture: routing and parameters, writing middleware, and reading body, query and headers.

</En>
<Ur>

- **Tarteeb ahem hai**: `express.json()` `req.body` parhne wale routes se pehle hona chahiye; 404 aur error handlers **aakhir** me jate hain.
- Middleware ya to response bhejta hai ya request aage dene ke liye `next()` call karta hai. Dono bhoolna client ko hamesha intezar me chhor deta hai.
- Agle teen lessons is tasveer ko qareeb se dekhte hain: routing aur parameters, middleware likhna, aur body, query aur headers parhna.

## Common mistakes

<Compare>
<Bad title="Sending two responses">

```text
app.get("/products/:id", async (req, res) => {
  const product = await findProduct(req.params.id);
  if (!product) res.status(404).json({ error: "Not found" });   // no return!
  res.json(product);                                            // runs too → "Cannot set headers after they are sent"
});
```

</Bad>
<Good title="Return after responding">

```text
app.get("/products/:id", async (req, res) => {
  const product = await findProduct(req.params.id);
  if (!product) return res.status(404).json({ error: "Not found" });
  res.json(product);
});
```

</Good>
</Compare>

<Compare>
<Bad title="Middleware in the wrong order">

```text
app.post("/products", createProduct);   // req.body is undefined here
app.use(express.json());                 // added too late
```

</Bad>
<Good title="Parsers first, routes next, 404 and errors last">

```text
app.use(express.json());
app.post("/products", createProduct);
app.use(notFound);
app.use(errorHandler);
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Running Express 4 patterns on Express 5** (or the reverse): Express 5 changed route path syntax (`/*splat` instead of `*`), removed some old methods (`res.send(status, body)`) and handles async errors.
- **Not setting `NODE_ENV=production`**: stack traces appear in error pages and some caching is disabled.
- **Using `res.send(object)` and `res.json` interchangeably without thinking**: prefer `res.json` for APIs so the intent is explicit.
- **Leaving `X-Powered-By` on**, and no security headers at all.
- **Business logic inside route handlers** in big apps; extract services (Structuring an Express Project lesson).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Express 5 par Express 4 ke patterns chalana** (ya ulta): Express 5 ne route path syntax badla (`*` ke bajaye `/*splat`), kuch purane methods hataye (`res.send(status, body)`) aur async errors sambhalta hai.
- **`NODE_ENV=production` set na karna**: error pages me stack traces aate hain aur kuch caching band hoti hai.
- **Soche baghair `res.send(object)` aur `res.json` ko ek doosre ki jagah istemal karna**: APIs ke liye `res.json` behtar hai taa ke irada wazeh ho.
- **`X-Powered-By` on chhorna**, aur security headers bilkul nahi.
- Bari apps me **route handlers ke andar business logic**; services alag karein (Structuring an Express Project lesson).

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- `express()` creates an app; `app.get/post/put/patch/delete(path, handler)` defines routes; `app.listen(port)` starts it.

<DeepDive title="More about Express">

**What Express adds to `req` and `res`.** Express wraps Node's `IncomingMessage` and `ServerResponse`, so you can still use low-level APIs (`res.write`, streaming, `req.on("data")`) when needed.

**Express 5 changes.** Released as stable in 2024 after years in beta: async error handling, path-to-regexp v8 (`/files/*splat`, `/:file{.:ext}` for optional parts), removed deprecated APIs (`req.param()`, `res.send(status)`), `req.body` is `undefined` when no parser ran, Node 18+ required. Migration guides and codemods exist for Express 4 apps.

**`app.listen` returns a server.** `const server = app.listen(3000)` gives you the Node `http.Server`, useful for graceful shutdown (`server.close()`) and for tests.

**Settings.** `app.set("trust proxy", 1)` when behind a reverse proxy (so `req.ip` and `req.protocol` are correct), `app.set("json spaces", 2)` for pretty JSON in development, `app.set("etag", false)` to disable ETags.

**Rendering HTML.** Express supports template engines (EJS, Pug, Handlebars) with `res.render()`, still common for admin panels and emails.

**Alternatives.** Fastify (faster, schema-based), Hono (tiny, runs on edge runtimes), Koa (async middleware by the Express authors), NestJS (structured framework that can run on Express or Fastify).

</DeepDive>

<DeepDive title="Real world: the error page that leaked the database password">

A startup's Express 4 API ran in production with no `NODE_ENV` set, because the Dockerfile only had `CMD ["node", "server.js"]`. One day the database went down for maintenance. Every request that touched it failed, and Express's default error handler, thinking it was in development, returned the full stack trace as HTML.

The error message from the database driver included the connection string: user, password, host and port. A user who saw the strange page posted a screenshot in a public community forum, asking whether the site was broken.

The response:

1. The database password was rotated immediately and the forum post removed with the user's help.
2. `ENV NODE_ENV=production` was added to the Dockerfile, and a startup check refused to run in production without it.
3. A custom JSON error handler returned `{ "error": "Internal server error", "requestId": "…" }` and logged the details (with secrets redacted) to the log service.
4. The database client was configured to never include connection strings in error messages, and the team moved to Express 5, where async errors reach the handler reliably.

One missing environment variable turned a routine outage into a security incident.

</DeepDive>

<DeepDive title="Security lens">

- **`NODE_ENV=production`** so default error pages don't show stack traces.
- **Remove `X-Powered-By`** and add security headers (helmet); limit body sizes (`express.json({ limit: "100kb" })` is the default).
- **Validate all input** from `req.body`, `req.query` and `req.params`; parsed isn't trusted.
- **`express.static`**: serve only a dedicated public folder, never the project root (it would expose `.env` and source code).
- **Keep Express and its dependencies updated**; Express 5 fixed several older ReDoS issues in path matching.
- **Behind a proxy**, configure `trust proxy` correctly, or attackers can spoof `X-Forwarded-For` to bypass IP-based rate limits.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is Express and what does it add to Node's http module?">
Express is a minimal web framework built on Node's http module. It adds routing by method and path, middleware composition with app.use, request and response helpers like req.params, req.query, res.json and res.status, built-in body parsing and static file serving, and centralised error handling.
</QA>

<QA q="What is middleware in Express?">
A function with access to req, res and next that runs during the request pipeline in the order it was registered. It can modify the request or response, end the request by sending a response, or call next to pass control on, or next with an error to skip to error handlers.
</QA>

<QA q="What's the difference between res.send and res.json?">
res.json always serialises the value as JSON and sets the application/json content type. res.send handles strings as HTML or text, buffers as binary and objects as JSON, choosing the type from the value. For APIs res.json is clearer.
</QA>

<QA q="How does Express 5 handle errors in async route handlers?">
If a handler returns a rejected promise or throws inside an async function, Express 5 catches it and passes the error to the error-handling middleware, so you don't need try catch or wrapper libraries as in Express 4.
</QA>

<QA q="Why does middleware order matter?">
Express runs middleware and routes sequentially in registration order, so parsers and security middleware must come before the routes that depend on them, and 404 and error handlers must be registered last to catch what earlier handlers didn't handle.
</QA>

</DeepDive>
