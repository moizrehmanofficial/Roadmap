<BigIdea>
<Tr>
<En>
A request is more than a URL. Data can arrive in four places, and Express gives each its own property. The **body** (`req.body`) holds what the client sends with POST, PUT and PATCH, but only after a **body-parsing middleware** has read it: `express.json()` for JSON, `express.urlencoded()` for HTML forms, `express.raw()` when you need the exact bytes (for webhook signatures), and multer for file uploads. Without the right parser, or with a different `Content-Type`, `req.body` stays empty. The **query string** (`req.query`) carries options like `?page=2&tag=blue`: always strings, sometimes arrays, often missing. **Headers** (`req.get("Content-Type")`) carry metadata: the body's format, what the client accepts, the language, the user agent, and credentials in `Authorization`. **Cookies** are a header too; `cookie-parser` turns them into `req.cookies`. Behind a proxy, `req.ip` and `req.protocol` are only correct if you configure **`trust proxy`**. All of these are **client-controlled**: parse them, give missing ones defaults, convert types, and validate before you trust anything.
</En>
<Ur>
Request URL se zyada hai. Data chaar jagahon se aa sakta hai, aur Express har ek ko apni property deta hai. **Body** (`req.body`) wo rakhti hai jo client POST, PUT aur PATCH ke saath bhejta hai, magar sirf tab jab **body-parsing middleware** use parh chuka ho: JSON ke liye `express.json()`, HTML forms ke liye `express.urlencoded()`, bilkul bytes chahiyen to `express.raw()` (webhook signatures ke liye), aur file uploads ke liye multer. Sahi parser ke baghair, ya mukhtalif `Content-Type` ke saath, `req.body` khaali rehti hai. **Query string** (`req.query`) `?page=2&tag=blue` jaise options laati hai: hamesha strings, kabhi arrays, aksar ghayab. **Headers** (`req.get("Content-Type")`) maloomat laate hain: body ka format, client kya qubool karta hai, zabaan, user agent, aur `Authorization` me credentials. **Cookies** bhi header hain; `cookie-parser` unhen `req.cookies` banata hai. Proxy ke peeche `req.ip` aur `req.protocol` tabhi sahi hain jab aap **`trust proxy`** set karein. Ye sab **client ke control** me hain: parse karein, ghayab walon ko defaults dein, types badlein, aur kisi par bharosa karne se pehle validate karein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **parcel sent by post**.

- The **address** is the path and query: where it goes, plus notes like "leave at the back door" (`?delivery=back`).
- The **labels stuck on the box** are headers: "FRAGILE" (`Content-Type`), "return to sender if not home" (`Accept`), the sender's ID card (`Authorization`), "deliver in French" (`Accept-Language`).
- The **contents** are the body. Before anyone can use them, someone has to **unpack** them the right way: a letter is read, a bag of coins is counted (the right body parser for the content type). If the box is too heavy, the post office refuses it (413). If the letter is torn, it can't be read (400).
- A **loyalty card** you show every visit is a cookie.
- When a **courier company** hands the parcel on, the original sender's address is on a forwarding sticker (`X-Forwarded-For`); you only trust that sticker if you trust the courier (`trust proxy`).

</En>
<Ur>

**Daak se bheje gaye parcel** ka sochein.

- **Pata** path aur query hai: kahan jana hai, plus "peechhe ke darwaze par chhor dein" jaise notes (`?delivery=back`).
- **Dabbe par chipke labels** headers hain: "FRAGILE" (`Content-Type`), "ghar na hon to wapas bhejein" (`Accept`), bhejne wale ka shanakhti card (`Authorization`), "French me deliver karein" (`Accept-Language`).
- **Andar ka saman** body hai. Istemal se pehle kisi ko use sahi tareeqe se **kholna** parta hai: khat parha jata hai, sikkon ki theli gini jati hai (content type ke liye sahi body parser). Dabba bohot bhari ho to daak khana use radd karta hai (413). Khat phata ho to parha nahi ja sakta (400).
- Har dafa dikhaya jane wala **loyalty card** cookie hai.
- Jab **courier company** parcel aage deti hai to asal bhejne wale ka pata forwarding sticker (`X-Forwarded-For`) par hota hai; aap us sticker par tabhi bharosa karte hain jab courier par bharosa ho (`trust proxy`).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Request bodies: JSON, forms, and what happens otherwise">

<Tr>
<En>
The same endpoint receives six different requests. A small error handler shows the error **type** and status that the JSON parser produces.
</En>
<Ur>
Ek hi endpoint chhe mukhtalif requests leta hai. Chhota error handler JSON parser ka banaya error **type** aur status dikhata hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 cookie-parser@1.4.7 --silent
cat > bodies.js <<'EOF'
import express from "express";
const app = express();

app.use(express.json({ limit: "10kb" }));                  // application/json
app.use(express.urlencoded({ extended: false }));          // HTML forms: application/x-www-form-urlencoded

app.post("/echo", (req, res) => {
  res.json({ contentType: req.get("Content-Type") ?? null, body: req.body ?? null });
});

app.use((err, req, res, next) => {
  res.status(err.status ?? 500).json({ error: err.type ?? "server_error", status: err.status });
});
app.listen(3000);
EOF
node bodies.js &
sleep 1
U=http://localhost:3000/echo
curl -s -X POST -H "Content-Type: application/json" -d '{"name":"Mug","qty":2,"tags":["a","b"]}' $U; echo
curl -s -X POST -d 'name=Mug&qty=2&gift=on' $U; echo
curl -s -X POST -H "Content-Type: text/plain" -d 'just text' $U; echo
curl -s -X POST $U; echo
curl -s -X POST -H "Content-Type: application/json" -d '{"name": "Mug",}' -w " %{http_code}" $U; echo
head -c 20000 /dev/zero | tr '\0' 'a' | sed 's/.*/{"note":"&"}/' | curl -s -X POST -H "Content-Type: application/json" --data-binary @- -w " %{http_code}" $U; echo
kill %1
```

```text output
{"contentType":"application/json","body":{"name":"Mug","qty":2,"tags":["a","b"]}}
{"contentType":"application/x-www-form-urlencoded","body":{"name":"Mug","qty":"2","gift":"on"}}
{"contentType":"text/plain","body":null}
{"contentType":null,"body":null}
{"error":"entity.parse.failed","status":400} 400
{"error":"entity.too.large","status":413} 413
```

<Happened>
<Tr>
<En>

- **JSON** kept its types: `qty` is the number 2, `tags` an array.
- An **HTML form** (curl's default `-d` format) arrived as strings only: `qty` is `"2"`, and a checked checkbox is `"on"`. Convert before using.
- **`text/plain`** and a request with **no body** left `req.body` empty (`null` in our output; it's `undefined` in Express 5). No parser matched the content type, so nothing was read. That's the usual reason for "req.body is undefined": the client didn't send `Content-Type: application/json`.
- A **trailing comma** made the JSON invalid: the parser answered **400** with type `entity.parse.failed` instead of crashing.
- A 20 KB body over our 10 KB limit: **413** `entity.too.large`, rejected while reading. Keep limits small for APIs; raise them only on routes that need it.

</En>
<Ur>

- **JSON** ne apni types rakhin: `qty` number 2 hai, `tags` array.
- **HTML form** (curl ka default `-d` format) sirf strings ban kar aaya: `qty` `"2"` hai, aur tick kiya checkbox `"on"`. Istemal se pehle badlein.
- **`text/plain`** aur **bina body** wali request ne `req.body` khaali chhori (hamare output me `null`; Express 5 me ye `undefined` hai). Koi parser content type se nahi mila, isliye kuch nahi parha gaya. "req.body undefined hai" ki aam wajah yahi hai: client ne `Content-Type: application/json` nahi bheja.
- **Aakhri comma** ne JSON ghalat bana diya: parser ne crash ke bajaye `entity.parse.failed` type ke saath **400** diya.
- Hamari 10 KB hadd se upar 20 KB body: **413** `entity.too.large`, parhte waqt hi radd. APIs ke liye hadd chhoti rakhein; sirf zaroorat wale routes par barhayen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Query strings, headers, cookies and the client IP">

<Tr>
<En>
Query values may be missing, single or repeated; normalise them. Headers are read with `req.get()`, cookies with `cookie-parser`, and `req.ip`/`req.protocol` come from `X-Forwarded-*` headers only because we told Express to trust the proxy (here: our own machine).
</En>
<Ur>
Query values ghayab, akeli ya dohrayi ho sakti hain; unhen yaksan karein. Headers `req.get()` se parhe jate hain, cookies `cookie-parser` se, aur `req.ip`/`req.protocol` `X-Forwarded-*` headers se sirf isliye aate hain ke humne Express ko proxy par bharosa karne ka kaha (yahan: hamari apni machine).
</Ur>
</Tr>

```bash
cat > query-headers.js <<'EOF'
import express from "express";
import cookieParser from "cookie-parser";

const app = express();
app.set("trust proxy", "loopback");          // we're behind a proxy on the same machine
app.use(cookieParser());

app.get("/products", (req, res) => {
  const page = Number(req.query.page ?? 1);
  const tags = [req.query.tag ?? []].flat();  // one value, several values, or none → always an array
  res.json({ page, typeofPage: typeof page, tags, sort: req.query.sort ?? "newest" });
});

app.get("/whoami", (req, res) => {
  res.json({
    userAgent: req.get("user-agent"),
    acceptsJson: Boolean(req.accepts("json")),
    language: req.acceptsLanguages("de", "en", "fr") || "en",
    ip: req.ip,
    protocol: req.protocol,
    theme: req.cookies.theme ?? "light",
    authHeader: req.get("authorization") ? "present" : "missing",
  });
});
app.listen(3000);
EOF
node query-headers.js &
sleep 1
curl -s "http://localhost:3000/products?page=2&tag=blue&tag=ceramic"; echo
curl -s "http://localhost:3000/products?tag=blue"; echo
curl -s "http://localhost:3000/products"; echo
curl -s -A "AcmeApp/2.1" -H "Accept-Language: fr-CA,fr;q=0.9,en;q=0.8" -H "Cookie: theme=dark; other=1" \
     -H "X-Forwarded-For: 203.0.113.7" -H "X-Forwarded-Proto: https" -H "Authorization: Bearer abc" \
     http://localhost:3000/whoami; echo
kill %1
```

```text output
{"page":2,"typeofPage":"number","tags":["blue","ceramic"],"sort":"newest"}
{"page":1,"typeofPage":"number","tags":["blue"],"sort":"newest"}
{"page":1,"typeofPage":"number","tags":[],"sort":"newest"}
{"userAgent":"AcmeApp/2.1","acceptsJson":true,"language":"fr","ip":"203.0.113.7","protocol":"https","theme":"dark","authHeader":"present"}
```

<Happened>
<Tr>
<En>

- `[req.query.tag ?? []].flat()` turned "two tags", "one tag" and "no tag" into an array every time, so the rest of the code handles one shape. Missing `page` and `sort` got defaults.
- `req.accepts("json")` and `req.acceptsLanguages(...)` do **content negotiation**: the client preferred French, which we support, so we got `"fr"`.
- `cookie-parser` split the `Cookie` header into `req.cookies` (`theme: "dark"`).
- `req.ip` and `req.protocol` came from `X-Forwarded-For` / `X-Forwarded-Proto` **only because** `trust proxy` allows the request's direct sender (loopback) to set them. If you trust everyone, any client can claim any IP, which defeats IP-based rate limiting and logging. Set it to exactly your proxy setup (`1` for one load balancer, or its IP ranges).
- We only reported whether `Authorization` was present; never log full tokens.

</En>
<Ur>

- `[req.query.tag ?? []].flat()` ne "do tags", "ek tag" aur "koi tag nahi" ko har dafa array banaya, isliye baqi code ek hi shakal sambhalta hai. Ghayab `page` aur `sort` ko defaults mile.
- `req.accepts("json")` aur `req.acceptsLanguages(...)` **content negotiation** karte hain: client ne French pasand ki, jise hum support karte hain, isliye `"fr"` mila.
- `cookie-parser` ne `Cookie` header ko `req.cookies` (`theme: "dark"`) me baanta.
- `req.ip` aur `req.protocol` `X-Forwarded-For` / `X-Forwarded-Proto` se **sirf isliye** aaye ke `trust proxy` request ke seedhe bhejne wale (loopback) ko inhen set karne deta hai. Agar sab par bharosa karein to koi bhi client koi bhi IP ka daawa kar sakta hai, jo IP par mabni rate limiting aur logging bekaar kar deta hai. Ise bilkul apne proxy setup par rakhein (ek load balancer ke liye `1`, ya us ki IP ranges).
- Humne sirf ye bataya ke `Authorization` maujood hai ya nahi; poore tokens kabhi log na karein.

</Ur>
</Tr>
</Happened>

<Step title="Raw bodies for webhook signatures">

<Tr>
<En>
Payment providers (Stripe, PayPal, GitHub webhooks) sign each request with a shared secret: an **HMAC** over the **exact bytes** of the body. If you parse and re-stringify the JSON first, spacing or key order can change and the signature won't match. So use `express.raw()` on that one route, verify, and only then parse.
</En>
<Ur>
Payment providers (Stripe, PayPal, GitHub webhooks) har request ko mushtarka secret se sign karte hain: body ke **bilkul bytes** par **HMAC**. Agar aap pehle JSON parse kar ke dobara string banayen to spacing ya keys ki tarteeb badal sakti hai aur signature nahi milta. Isliye us ek route par `express.raw()` lein, tasdeeq karein, aur sirf tab parse karein.
</Ur>
</Tr>

```bash
cat > webhook.js <<'EOF'
import express from "express";
import { createHmac, timingSafeEqual } from "node:crypto";

const SECRET = "whsec_test_123";
const app = express();

// Raw bytes for this ONE route: the signature is computed over the exact bytes sent
app.post("/webhooks/payments", express.raw({ type: "application/json" }), (req, res) => {
  const expected = createHmac("sha256", SECRET).update(req.body).digest("hex");
  const given = req.get("X-Signature") ?? "";
  const ok = given.length === expected.length && timingSafeEqual(Buffer.from(given), Buffer.from(expected));
  if (!ok) return res.status(400).json({ error: "bad signature" });
  const event = JSON.parse(req.body.toString("utf8"));
  res.json({ received: event.type, bodyWasBuffer: Buffer.isBuffer(req.body) });
});

app.use(express.json());   // every other route gets parsed JSON
app.listen(3000);
EOF
node webhook.js &
sleep 1
BODY='{"type":"payment.succeeded","amount":4250}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "whsec_test_123" | awk '{print $2}')
curl -s -X POST -H "Content-Type: application/json" -H "X-Signature: $SIG" -d "$BODY" http://localhost:3000/webhooks/payments; echo
curl -s -X POST -H "Content-Type: application/json" -H "X-Signature: $SIG" -d '{"type":"payment.succeeded","amount":1}' http://localhost:3000/webhooks/payments; echo
kill %1
```

```text output
{"received":"payment.succeeded","bodyWasBuffer":true}
{"error":"bad signature"}
```

<Happened>
<Tr>
<En>

- With the correct signature, the route verified the bytes and then parsed them: the event was accepted.
- An attacker who changes the amount (4250 → 1) but reuses the old signature is rejected: the HMAC of different bytes is different, and they don't know the secret to compute a new one.
- The webhook route is registered **before** `app.use(express.json())`; otherwise the JSON parser would consume the body first and `req.body` would no longer be the raw bytes.
- `timingSafeEqual` compares in constant time (Password Storage lesson); check equal lengths first, because it throws on different lengths. Real providers also sign a timestamp to stop replays; their SDKs (for example `stripe.webhooks.constructEvent`) do all of this for you, but still need the raw body.

</En>
<Ur>

- Sahi signature ke saath route ne bytes tasdeeq kiye aur phir parse kiye: event qubool hua.
- Hamla awar jo amount badle (4250 → 1) magar purana signature dobara istemal kare, radd hota hai: mukhtalif bytes ka HMAC mukhtalif hai, aur naya banane ke liye wo secret nahi jante.
- Webhook route `app.use(express.json())` se **pehle** register hai; warna JSON parser pehle body kha jata aur `req.body` kache bytes na rehte.
- `timingSafeEqual` mustaqil waqt me muqabla karta hai (Password Storage lesson); pehle barabar lengths check karein, kyun ke mukhtalif lengths par ye throw karta hai. Asli providers replay rokne ke liye timestamp bhi sign karte hain; un ke SDKs (maslan `stripe.webhooks.constructEvent`) ye sab aap ke liye karte hain, magar phir bhi kacha body chahiye.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Using query values as they are">

```text
const page = req.query.page;                       // "2", undefined, or ["1","2"]
const offset = (page - 1) * 20;                    // NaN when missing; ["1","2"] - 1 → NaN
db.products.findMany({ skip: offset, take: req.query.limit });   // limit = "1000000"
```

</Bad>
<Good title="Defaults, conversion, limits">

```text
const Query = z.object({
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
});
const { page, limit } = Query.parse(req.query);    // 400 on invalid input (Validation lesson)
db.products.findMany({ skip: (page - 1) * limit, take: limit });
```

</Good>

More mistakes to avoid:

- **Forgetting the `Content-Type` header** in client code (`fetch(url, { method: "POST", body: JSON.stringify(data) })` without `headers: { "Content-Type": "application/json" }`), then wondering why `req.body` is empty.
- **Huge body limits** on every route (`limit: "50mb"`) instead of only where needed.
- **Parsing JSON before verifying a webhook**, so signatures never match.
- **Reading secrets from query strings** (`?token=…`): they end up in logs, browser history and Referer headers.
- **Assuming header values are trustworthy** (`X-User-Id`, `X-Admin`): any client can send any header.
- **Logging whole request bodies** that may contain passwords or card numbers.

</En>

  const q = String(req.query.q ?? "").trim();

<DeepDive title="More about requests">

**Parser options.** `express.json({ strict: true })` (default) only accepts objects and arrays; `type` chooses which content types it handles (for example `application/vnd.api+json`); `verify(req, res, buf)` lets you keep a copy of the raw buffer while still parsing, an alternative for webhooks.

**`extended` URL encoding.** `express.urlencoded({ extended: true })` uses the `qs` library to build nested objects from `user[name]=Emma`; `false` keeps flat keys and is safer.

**Signed cookies.** `cookieParser(secret)` plus `res.cookie("cart", id, { signed: true })` lets you detect tampering via `req.signedCookies`. For sessions, use proper session middleware (Authentication in Express lesson).

**Idempotency keys.** Payment APIs accept an `Idempotency-Key` header so retried POSTs don't create duplicate charges; the server stores the key with the first result.

**Conditional requests.** `If-None-Match` (with ETags) and `If-Modified-Since` let clients reuse cached responses; Express answers 304 automatically for `res.send`/`res.json` with ETags.

**Streaming bodies.** For very large uploads, read `req` as a stream (it's a Node readable stream) and pipe it to storage instead of buffering with a parser.

</DeepDive>

<DeepDive title="Real world: the rate limiter anyone could bypass">

A ticketing site protected its "reserve seats" endpoint with an IP-based rate limiter: 10 requests per minute per IP. The API ran behind a cloud load balancer, so a developer had set `app.set("trust proxy", true)` after noticing that every request seemed to come from the load balancer's IP.

When a popular concert went on sale, bots reserved thousands of seats within seconds. The logs showed tens of thousands of different client IPs, which looked like a huge distributed attack. In reality, a handful of servers were sending requests with a random `X-Forwarded-For` header each time. With `trust proxy: true`, Express believed the **leftmost** address in that header, which the client controls, so each request appeared to come from a new IP and the rate limiter never triggered.

The fix had three parts:

1. `trust proxy` was set to the number of proxies actually in front of the app (`1`), so Express used the address the load balancer itself appended, which clients can't forge.
2. The limiter moved to a shared Redis store and also keyed on the logged-in account, not just the IP.
3. Seat reservation required a short-lived token from the queue page, so bots couldn't call the endpoint directly.

The next sale had the same bot traffic, but each bot server was limited to 10 reservations per minute, and real fans got their tickets.

</DeepDive>

<DeepDive title="Security lens">

- **Body size limits** prevent memory exhaustion; set them per route.
- **Prototype pollution**: avoid parsers or merges that turn keys like `__proto__` into object properties (Express 5's simple query parser and `extended: false` forms are safer); validate with a schema that strips unknown keys.
- **Content-type confusion**: only parse the types you expect, and reject others with 415 on write endpoints.
- **Headers are user input**: `X-Forwarded-*`, `Host`, custom headers; configure `trust proxy` precisely and don't build URLs from `Host` without validation (host header injection).
- **Secrets belong in headers or bodies**, not query strings; redact `Authorization` and cookies in logs.
- **Webhooks**: verify signatures on the raw body, check timestamps, and handle duplicates idempotently.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Why might req.body be undefined in Express?">
Because no body-parsing middleware ran for that request: express.json wasn't registered, was registered after the route, or the request's Content-Type didn't match the parser, for example a fetch without Content-Type application/json. In Express 5 req.body is undefined when no parser handled the body.
</QA>

<QA q="What's the difference between req.params, req.query and req.body?">
req.params are values from the route path, req.query values from the URL query string, and req.body the parsed request body. Params and query values are strings, body types depend on the parser, and all are client-controlled.
</QA>

<QA q="What does trust proxy do and why is it important?">
It tells Express which proxies to trust when deriving req.ip, req.ips, req.protocol and req.hostname from X-Forwarded headers. Without it, behind a load balancer you see the proxy's IP; trusting too much lets clients spoof their IP and protocol.
</QA>

<QA q="How do you verify webhook signatures in Express?">
Use express.raw on the webhook route so the exact bytes are available, compute the HMAC with the shared secret and compare it to the signature header in constant time, check the timestamp to prevent replays, and only then parse the JSON. Provider SDKs implement this but still need the raw body.
</QA>

<QA q="How should you handle query parameters for pagination?">
Treat them as optional strings: apply defaults, convert to numbers, enforce minimums and a maximum page size, and return 400 for invalid values, ideally with a schema validator, before using them in database queries.
</QA>

</DeepDive>
