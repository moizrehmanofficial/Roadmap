<BigIdea>
<Tr>
<En>
Clicking through Postman after every change doesn't scale: you forget cases, and a fix in one route quietly breaks another. **Automated API tests** send requests to your app and **assert** what comes back: the **status code**, important **headers** and the **JSON body**. **supertest** makes this easy: you give it your Express `app` (not a URL), it starts the app on a temporary port behind the scenes, sends the request, and gives you the response. Combined with Node's built-in **`node:test`** runner and **`assert`**, you need no other tools. Good API tests come from good structure: an **app factory** (`createApp(deps)`) lets each test build the app with **fresh, fake dependencies**, so tests don't depend on each other or on a real database. Test more than the happy path: **invalid input**, **duplicates**, **missing authentication**, **someone else's data**, and **error responses that must not leak secrets**. These are exactly the bugs that reach production when nobody checks.
</En>
<Ur>
Har tabdeeli ke baad Postman me click karte rehna nahi chalta: aap cases bhool jate hain, aur ek route ka fix chupke se doosra tor deta hai. **Automated API tests** aap ki app ko requests bhejte hain aur jo wapas aata hai us ki **tasdeeq (assert)** karte hain: **status code**, ahem **headers** aur **JSON body**. **supertest** ise aasan banata hai: aap use apni Express `app` dete hain (URL nahi), wo parde ke peeche app ko aarzi port par chalata hai, request bhejta hai, aur response deta hai. Node ke built-in **`node:test`** runner aur **`assert`** ke saath kisi aur auzaar ki zaroorat nahi. Achhe API tests achhe structure se aate hain: **app factory** (`createApp(deps)`) har test ko **taaza, nakli dependencies** ke saath app banane deti hai, isliye tests ek doosre ya asli database par munhasir nahi hote. Sirf seedha raasta test na karein: **ghalat input**, **dohraye records**, **ghayab authentication**, **kisi aur ka data**, aur **aise error responses jo raaz zahir na karen**. Bilkul yahi bugs production tak pohanchte hain jab koi check nahi karta.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **car's safety inspection**.

- The inspector doesn't drive the car on public roads (production). They put it on a **test bench** (supertest) that spins the wheels, presses the brakes and reads the results.
- Every car is inspected from the **same starting state** (fresh data in `beforeEach`), so one car's mud doesn't affect the next result.
- The checklist isn't just "does it start?" (happy path). It's "do the brakes work when wet?" (invalid input), "does the door lock against strangers?" (other users' data), "does the airbag fire without injuring?" (500s that don't leak).
- If a mechanic later changes a part, the **same checklist** runs again (CI), and a failure points to the exact item.

</En>
<Ur>

**Gari ki safety inspection** ka sochein.

- Inspector gari public sarkon (production) par nahi chalata. Use **test bench** (supertest) par rakhta hai jo pahiye ghumata, brakes dabata aur nataij parhta hai.
- Har gari **ek hi shuruati halat** (`beforeEach` me taaza data) se jaanchi jati hai, isliye ek gari ki mitti agle nateeje par asar nahi dalti.
- Checklist sirf "kya chalti hai?" (seedha raasta) nahi. "Geeli halat me brakes kaam karte hain?" (ghalat input), "darwaza ajnabiyon ke liye band hota hai?" (doosre users ka data), "airbag chot pohanchaye baghair khulta hai?" (zahir na karne wale 500s).
- Agar mechanic baad me koi purza badle, **wahi checklist** dobara chalti hai (CI), aur nakami bilkul us item ki taraf ishara karti hai.

</Ur>

## Learn it step by step

<Walkthrough>

<Step title="An app factory and seven supertest tests">

<Tr>
<En>
The app is a small task API with authentication, validation, duplicates, ownership and a route that crashes. `createApp` takes a `store` array and a `verifyToken` function, so tests can pass simple fakes: two known tokens instead of real JWTs. The tests cover the cases from the table above.
</En>
<Ur>
App authentication, validation, duplicates, malkiyat aur crash hone wale route wali chhoti task API hai. `createApp` `store` array aur `verifyToken` function leta hai, isliye tests saada nakli cheezen de sakte hain: asli JWTs ke bajaye do maloom tokens. Tests oopar ki table wale cases cover karte hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 zod@4.6.7 --silent && npm install -D supertest@7.3.2 --silent
mkdir -p src test
cat > src/app.js <<'EOF'
import express from "express";
import { z } from "zod";

const CreateTask = z.object({ title: z.string().trim().min(3).max(100), dueDate: z.iso.date().optional() });

// App factory: tests pass in their own store and token checker
export function createApp({ store, verifyToken }) {
  const app = express();
  app.use(express.json());

  const requireAuth = (req, res, next) => {
    const user = verifyToken(req.get("Authorization")?.replace(/^Bearer /, "") ?? "");
    if (!user) return res.status(401).json({ error: "unauthenticated" });
    req.user = user;
    next();
  };

  app.get("/tasks", requireAuth, (req, res) => res.json(store.filter((t) => t.userId === req.user.id)));
  app.post("/tasks", requireAuth, (req, res) => {
    const parsed = CreateTask.safeParse(req.body);
    if (!parsed.success) return res.status(400).json({ error: "validation_failed", details: z.flattenError(parsed.error).fieldErrors });
    if (store.some((t) => t.userId === req.user.id && t.title === parsed.data.title)) return res.status(409).json({ error: "duplicate" });
    const task = { id: store.length + 1, userId: req.user.id, done: false, ...parsed.data };
    store.push(task);
    res.status(201).location(`/tasks/${task.id}`).json(task);
  });
  app.get("/tasks/:id", requireAuth, (req, res) => {
    const task = store.find((t) => t.id === Number(req.params.id) && t.userId === req.user.id);
    if (!task) return res.status(404).json({ error: "not_found" });
    res.json(task);
  });
  app.get("/crash", () => { throw new Error("db password=hunter2 rejected"); });
  app.use((err, req, res, next) => res.status(500).json({ error: "internal_error" }));
  return app;
}
EOF
cat > test/tasks.test.js <<'EOF'
import { describe, test, beforeEach } from "node:test";
import assert from "node:assert/strict";
import request from "supertest";
import { createApp } from "../src/app.js";

const tokens = { "token-emma": { id: 1 }, "token-liam": { id: 2 } };
let app, store;

beforeEach(() => {                                          // a fresh app and store for every test
  store = [{ id: 1, userId: 2, title: "Liam's private task", done: false }];
  app = createApp({ store, verifyToken: (t) => tokens[t] ?? null });
});
const asEmma = (req) => req.set("Authorization", "Bearer token-emma");

describe("POST /tasks", () => {
  test("creates a task and returns 201 with Location", async () => {
    const res = await asEmma(request(app).post("/tasks")).send({ title: "  Buy milk ", dueDate: "2026-12-01" });
    assert.equal(res.status, 201);
    assert.equal(res.headers.location, "/tasks/2");
    assert.deepEqual(res.body, { id: 2, userId: 1, done: false, title: "Buy milk", dueDate: "2026-12-01" });
    assert.equal(store.length, 2);
  });

  test("rejects invalid input with field errors", async () => {
    const res = await asEmma(request(app).post("/tasks")).send({ title: "x", dueDate: "tomorrow" });
    assert.equal(res.status, 400);
    assert.deepEqual(Object.keys(res.body.details).sort(), ["dueDate", "title"]);
  });

  test("returns 409 for a duplicate title", async () => {
    await asEmma(request(app).post("/tasks")).send({ title: "Buy milk" }).expect(201);
    await asEmma(request(app).post("/tasks")).send({ title: "Buy milk" }).expect(409);
  });
});

describe("authentication and authorisation", () => {
  test("401 without a token", async () => {
    await request(app).get("/tasks").expect(401, { error: "unauthenticated" });
  });
  test("users only see their own tasks", async () => {
    const res = await asEmma(request(app).get("/tasks")).expect(200);
    assert.deepEqual(res.body, []);
  });
  test("another user's task is a 404, not a 403", async () => {
    await asEmma(request(app).get("/tasks/1")).expect(404);
  });
});

test("500 responses don't leak internal details", async () => {
  const res = await request(app).get("/crash").expect(500);
  assert.doesNotMatch(res.text, /hunter2|stack|Error:/);
});
EOF
node --test --test-reporter=spec "test/**/*.test.js" 2>&1 | sed -E 's/ \([0-9.]+ms\)//' | grep -vE "^ℹ (duration|cancelled|skipped|todo)"
```

<Happened>
<Tr>
<En>

- **No server, no port**: `request(app)` started the app internally for each request, so tests can't clash over port 3000 and need no cleanup.
- **`beforeEach`** built a new store and app for every test, so the duplicate test's "Buy milk" didn't make the create test fail, and tests can run in any order.
- **Two assertion styles**: `res.status`/`res.body` with `assert` for detailed checks (the trimmed title, the `Location` header, the store growing), and supertest's `.expect(401, {...})` for short status-and-body checks.
- **Shape, not exact text**: the validation test checks **which fields** failed, not zod's exact messages, so upgrading zod won't break it.
- **Security tests**: no token → 401; Emma's list doesn't include Liam's task; Liam's task by ID → 404; and the crashing route's 500 body doesn't contain the password from the error message. These are the tests that catch data leaks.
- The fake `verifyToken` keeps auth out of these tests. Separate tests (or a few end-to-end ones) should check the real JWT verification once.

</En>
<Ur>

- **Na server, na port**: `request(app)` ne har request ke liye app andar hi chalayi, isliye tests port 3000 par nahi takrate aur safai ki zaroorat nahi.
- **`beforeEach`** ne har test ke liye naya store aur app banaya, isliye duplicate test ke "Buy milk" ne create test fail nahi kiya, aur tests kisi bhi tarteeb me chal sakte hain.
- **Assertion ke do tareeqe**: tafseeli checks ke liye `assert` ke saath `res.status`/`res.body` (trim hua title, `Location` header, store ka barhna), aur chhote status-aur-body checks ke liye supertest ka `.expect(401, {...})`.
- **Shakal, bilkul text nahi**: validation test **kaun se fields** fail hue check karta hai, zod ke bilkul paighaam nahi, isliye zod upgrade use nahi torega.
- **Security tests**: token nahi → 401; Emma ki list me Liam ka task nahi; ID se Liam ka task → 404; aur crash wale route ki 500 body me error message ka password nahi. Yahi tests data leaks pakarte hain.
- Nakli `verifyToken` auth ko in tests se bahar rakhta hai. Alag tests (ya chand end-to-end) asli JWT verification ek dafa check karein.

</Ur>
</Tr>
</Happened>

<Step title="Watch a test catch a bug">

<Tr>
<En>
A teammate "simplifies" the lookup in `GET /tasks/:id` and drops the ownership check. Everything still works when you try it with your own account. Let's see what the tests say, then undo the change.
</En>
<Ur>
Ek saathi `GET /tasks/:id` ki talaash "aasan" karta hai aur malkiyat ka check hata deta hai. Apne account se aazmayen to sab kuch chalta hai. Dekhte hain tests kya kehte hain, phir tabdeeli wapas karte hain.
</Ur>
</Tr>

```bash
# Introduce a bug: forget the ownership check on GET /tasks/:id
sed -i 's/ \&\& t.userId === req.user.id);$/);/' src/app.js
grep -n 'store.find' src/app.js
node --test --test-reporter=spec "test/**/*.test.js" > result.txt 2>&1
grep -E "^ℹ (pass|fail)" result.txt
grep -m1 -E "^ *✖ another" result.txt | sed -E 's/ \([0-9.]+ms\)//; s/^ +//'
grep -m1 -oE "expected 404[^']*" result.txt
# Undo the bug
sed -i 's/t.id === Number(req.params.id));$/t.id === Number(req.params.id) \&\& t.userId === req.user.id);/' src/app.js
node --test --test-reporter=dot "test/**/*.test.js" > /dev/null && echo "all tests pass again"
```

```text output
28:    const task = store.find((t) => t.id === Number(req.params.id));
ℹ pass 6
ℹ fail 1
✖ another user's task is a 404, not a 403
expected 404 "Not Found", got 200 "OK"
all tests pass again
```

<Happened>
<Tr>
<En>

- The change looked harmless, but one test failed with a precise message: **expected 404, got 200**. Emma could now read Liam's task, the IDOR bug from the Authentication lesson.
- Without this test, the bug would have passed code review and manual testing, because the author only tried their own tasks.
- After restoring the check, all tests passed again (the `dot` reporter prints almost nothing on success, so we print our own message).
- Run this suite in **CI** on every pull request, and make merging require it to pass. When you fix a bug, first write a test that reproduces it; that test then guards against the same regression forever.

</En>
<Ur>

- Tabdeeli be-zarar lagti thi, magar ek test bilkul paighaam ke saath fail hua: **expected 404, got 200**. Emma ab Liam ka task parh sakti thi, Authentication lesson wala IDOR bug.
- Is test ke baghair bug code review aur haath ki testing se guzar jata, kyun ke likhne wale ne sirf apne tasks aazmaye.
- Check wapas lane ke baad tamam tests phir pass hue (`dot` reporter kamyabi par taqreeban kuch print nahi karta, isliye hum apna paighaam print karte hain).
- Ye suite har pull request par **CI** me chalayen, aur merge ke liye pass hona zaroori banayen. Bug theek karte waqt pehle aisa test likhein jo use dohraye; phir wo test hamesha usi regression se bachata hai.

## Common mistakes

<Compare>
<Bad title="Tests that share state and a running server">

```text
// server must be started manually on :3000 before the tests…
const BASE = "http://localhost:3000";
test("create", async () => { await fetch(BASE + "/tasks", { method: "POST", ... }); });
test("list is empty", async () => { /* fails or passes depending on test order */ });
```

</Bad>
<Good title="Fresh app per test, no port">

```text
beforeEach(() => { app = createApp({ store: [], verifyToken: fakeVerify }); });
test("list is empty", async () => { await asEmma(request(app).get("/tasks")).expect(200, []); });
```

</Good>
</Compare>

<Compare>
<Bad title="Only testing the happy path">

```text
test("create task", async () => {
  await request(app).post("/tasks").set(auth).send({ title: "Buy milk" }).expect(201);
});   // nothing about invalid input, auth, other users, or errors
```

</Bad>
<Good title="Test the edges that matter">

```text
test("400 on invalid input")          test("401 without token")
test("409 on duplicate")              test("404 for another user's task")
test("500 without internal details")  test("403 for non-admins")
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Asserting on exact error message text from libraries**: brittle; assert codes and field names.
- **Mocking everything**, including Express and your own services: tests then check the mocks, not your code.
- **Hitting real external services** (payments, email) in tests: slow, flaky and sometimes costly. Use fakes at the boundary.
- **Tests that pass when the code is broken**: forgetting `await`, so the assertion runs after the test finished. Always `await` supertest calls.
- **Testing implementation details** (which repository method was called) instead of behaviour (what the client gets).
- **Never running against a real database**: add a smaller set of tests with a disposable test database (Docker, Testcontainers) for SQL and constraints.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Libraries ke error messages ke bilkul text par assert karna**: kamzor; codes aur field names par assert karein.
- **Sab kuch mock karna**, Express aur apni services samet: phir tests mocks check karte hain, aap ka code nahi.
- **Tests me asli bahari services bulana** (payments, email): sust, be-bharosa aur kabhi mehenge. Sarhad par nakli cheezen lein.
- **Code toota ho phir bhi pass hone wale tests**: `await` bhoolna, jis se assertion test khatam hone ke baad chalti hai. supertest calls ko hamesha `await` karein.
- Rawaiye (client ko kya milta hai) ke bajaye **implementation ki tafseel test karna** (kaun sa repository method bula).
- **Kabhi asli database par na chalana**: SQL aur constraints ke liye disposable test database (Docker, Testcontainers) ke saath tests ka chhota set jorein.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Test PATCH /tasks/:id">

<Tr>
<En>
Add `PATCH /tasks/:id` that lets the owner set `done: true/false` (and nothing else; unknown keys → 400). Write tests for: success (200, store updated), invalid body (`done: "yes"` → 400), unknown key (`userId: 1` → 400), other user's task (404), no token (401). Which test would catch a mass-assignment bug?
</En>
<Ur>
`PATCH /tasks/:id` jorein jo malik ko `done: true/false` set karne de (aur kuch nahi; na maloom keys → 400). In ke tests likhein: kamyabi (200, store update), ghalat body (`done: "yes"` → 400), na maloom key (`userId: 1` → 400), doosre user ka task (404), token nahi (401). Kaun sa test mass-assignment bug pakrega?
</Ur>
</Tr>

<Solution>

<Tr>
<En>

Route: validate the body with `z.object({ done: z.boolean() }).strict()`, find the task with **both** `id` and `userId`, return 404 if missing, then set only `task.done`. Tests, using the same `beforeEach`:

```text
test("owner can mark a task done", async () => {
  store.push({ id: 2, userId: 1, title: "Mine", done: false });
  const res = await asEmma(request(app).patch("/tasks/2")).send({ done: true }).expect(200);
  assert.equal(res.body.done, true);
  assert.equal(store[1].done, true);
});
test("400 for a non-boolean", () => asEmma(request(app).patch("/tasks/2")).send({ done: "yes" }).expect(400));
test("400 for unknown keys", () => asEmma(request(app).patch("/tasks/2")).send({ done: true, userId: 1 }).expect(400));
test("404 for another user's task", () => asEmma(request(app).patch("/tasks/1")).send({ done: true }).expect(404));
test("401 without token", () => request(app).patch("/tasks/1").send({ done: true }).expect(401));
```

The **unknown key** test catches mass assignment: if someone later writes `Object.assign(task, req.body)`, sending `userId: 1` would move Liam's task to Emma; the strict schema and this test prevent that. Returning the supertest promise from the test function (as in the one-liners) is the same as awaiting it.

</En>
<Ur>

Route: body `z.object({ done: z.boolean() }).strict()` se validate karein, task `id` aur `userId` **dono** se dhoondhein, na mile to 404, phir sirf `task.done` set karein. Tests, usi `beforeEach` ke saath:


<Challenge title="Plan a test strategy">

<Tr>
<En>
Your Express API has 40 endpoints, PostgreSQL, Stripe payments and SendGrid emails. Tests take 12 minutes and fail randomly about once a day. Propose a strategy: what to test at which level, what to fake, and how to make the suite fast and reliable.
</En>
<Ur>
Aap ki Express API ke 40 endpoints, PostgreSQL, Stripe payments aur SendGrid emails hain. Tests 12 minute lete hain aur taqreeban roz ek dafa be-wajah fail hote hain. Strategy tajweez karein: kis level par kya test karein, kya nakli banayen, aur suite ko tez aur bharosemand kaise banayen.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

1. **Unit tests** for services and business rules with in-memory repositories: hundreds of tests in a few seconds.
2. **supertest API tests** for every endpoint's happy and sad paths (validation, 401/403/404, errors), with fake repositories or one shared test database; this is the bulk of the confidence.
3. **Repository tests** against a real PostgreSQL in Docker (Testcontainers), each test inside a transaction that's rolled back, to check SQL, constraints and migrations.
4. **Fake Stripe and SendGrid** behind your own interfaces (a `PaymentGateway`, a `Mailer`); add a few contract tests using Stripe's test mode in a nightly job, not on every PR.
5. **Fix flakiness**: no shared state between tests, no real network, no fixed ports, no `sleep`; fake time for date logic; run tests in random order to expose hidden dependencies; quarantine and fix flaky tests instead of retrying them forever.
6. **Speed**: run files in parallel (`node --test` does by default), keep database tests small, and run the slow end-to-end suite after merge or nightly.

</En>
<Ur>

1. In-memory repositories ke saath services aur business qawaid ke **unit tests**: chand second me saikron tests.
2. Har endpoint ke seedhe aur ulte raaston (validation, 401/403/404, errors) ke liye **supertest API tests**, nakli repositories ya ek mushtarka test database ke saath; zyada tar bharosa yahin se aata hai.
3. SQL, constraints aur migrations check karne ke liye Docker (Testcontainers) me asli PostgreSQL par **repository tests**, har test aisi transaction me jo wapas le li jaye.
4. Apne interfaces (`PaymentGateway`, `Mailer`) ke peeche **nakli Stripe aur SendGrid**; har PR par nahi, raat ki job me Stripe ke test mode ke saath chand contract tests jorein.
5. **Be-bharosagi theek karein**: tests me mushtarka state nahi, asli network nahi, muqarrar ports nahi, `sleep` nahi; tareekh ki logic ke liye nakli waqt; chhupi dependencies samne lane ke liye tests random tarteeb me chalayen; be-bharosa tests ko hamesha retry karne ke bajaye alag kar ke theek karein.
6. **Raftaar**: files parallel chalayen (`node --test` default me karta hai), database tests chhote rakhein, aur sust end-to-end suite merge ke baad ya raat ko chalayen.

</Ur>

<DeepDive title="More about testing APIs">

**Vitest and Jest.** Popular alternatives to `node:test` with watch mode, snapshots and rich mocking; supertest works the same with all of them.

**Agents for cookies.** `request.agent(app)` keeps cookies between requests, which is how you test session login → protected route → logout flows.

**Database tests.** Testcontainers starts a real PostgreSQL/MongoDB in Docker for the test run; wrap each test in a transaction and roll it back, or truncate tables in `beforeEach`.

**HTTP mocking.** `nock` or `undici`'s `MockAgent` intercept outgoing HTTP calls so you can simulate a payment provider's success, failure and timeout.

**Contract tests and schemas.** Validate responses against your OpenAPI spec or zod schemas in tests, so documentation and behaviour can't drift.

**Coverage.** `node --test --experimental-test-coverage` (or c8/Vitest coverage) shows untested lines; use it to find missed branches, not as a target to game.

</DeepDive>

<DeepDive title="Real world: the refactor that would have shipped a data leak">

A team migrated a 60-endpoint Express 4 API to Express 5 and, at the same time, moved queries from raw SQL to an ORM. The diff touched almost every route file. Code review was impossible to do thoroughly; reviewers skimmed.

The project had a supertest suite of about 900 tests, written over two years, including a rule from an earlier incident: every endpoint that takes an ID must have a test proving that another tenant's ID returns 404. On the migration branch, 14 tests failed. Twelve were harmless (an error message format changed). Two were serious: in the ORM version of the invoices and reports repositories, the `tenantId` condition had been dropped from `findUnique` because the ORM's `findUnique` only accepts unique fields, and the developer had "temporarily" removed the extra condition to make it compile.

Without the tests, any customer could have read any other customer's invoices after the deploy. With them, the fix took ten minutes: use `findFirst` with both conditions. The team's lead summed it up in the retrospective: "We didn't need reviewers to spot the bug. We needed one test per rule we'd already been burned by."

</DeepDive>

<DeepDive title="Security lens">

- **Write security regression tests**: cross-user and cross-tenant access, role checks, mass assignment, rate limits, and no secrets in error responses or logs.
- **Test both 401 and 403 paths** for every protected route; a missing middleware shows up as a 200.
- **Use fake secrets in tests**, never production keys, and keep test databases free of real customer data.
- **Run tests in CI** with branch protection, so security tests can't be skipped.
- **Add tests for every vulnerability you fix**, so it can't come back.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you test an Express API?">
Export an app factory, build the app with test dependencies, and use supertest to send requests and assert status codes, headers and bodies with a test runner like node:test, Vitest or Jest. Cover happy paths, validation errors, authentication, authorisation, not found, conflicts and error handling, plus fewer tests against a real database.
</QA>

<QA q="Why export the app separately from the code that calls listen()?">
So tests can create the app without binding to a fixed port; supertest starts it on an ephemeral port, which avoids conflicts, allows parallel test files and lets each test inject its own dependencies.
</QA>

<QA q="How do you keep tests isolated?">
Create fresh state in beforeEach, avoid shared mutable globals, use per-test data or transactions that are rolled back, avoid real network calls and fixed ports, and make tests independent of execution order.
</QA>

<QA q="What's the difference between unit, integration and end-to-end tests?">
Unit tests check a function or class in isolation; integration tests check several parts working together, such as routes, middleware and validation through HTTP or code against a real database; end-to-end tests exercise the whole deployed system as a user would. Lower levels are faster and more numerous.
</QA>

<QA q="How would you test authorisation rules?">
Create fixtures for at least two users or tenants and different roles, then assert that each protected endpoint returns 401 without credentials, 403 for insufficient roles, and 404 or 403 with no data for another user's resources, for every operation including reads, updates and deletes.
</QA>

</DeepDive>
