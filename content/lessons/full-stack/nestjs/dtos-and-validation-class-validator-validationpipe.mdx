<BigIdea>
<Tr>
<En>
A **DTO** (Data Transfer Object) is a class that describes the **shape of data crossing the boundary** of your API: what a client may send in a body or query string. In NestJS, you decorate its properties with rules from **class-validator** (`@IsString()`, `@Length(2, 100)`, `@IsPositive()`), and type the controller parameter with it: `@Body() dto: CreateProductDto`. A global **`ValidationPipe`** then runs on every request: it turns the plain JSON into an instance of your class (with **class-transformer**), validates it, and answers **400** with every problem if anything is wrong, so your controller only ever sees valid data. Three options matter most: **`whitelist`** strips properties without decorators, **`forbidNonWhitelisted`** rejects them instead (so `"isAdmin": true` becomes an error, not a silent field), and **`transform`** gives you real class instances, converts query strings to numbers with `@Type(() => Number)` and applies default values. It's the Nest counterpart of the zod middleware you built in Express: same goals, expressed as decorated classes that also produce TypeScript types and, later, OpenAPI docs.
</En>
<Ur>
**DTO** (Data Transfer Object) aisi class hai jo aap ki API ki **sarhad paar karne wale data ki shakal** bayan karti hai: client body ya query string me kya bhej sakta hai. NestJS me aap is ki properties ko **class-validator** ke qawaid (`@IsString()`, `@Length(2, 100)`, `@IsPositive()`) se decorate karte hain, aur controller parameter ki type yahi rakhte hain: `@Body() dto: CreateProductDto`. Phir global **`ValidationPipe`** har request par chalta hai: ye saade JSON ko aap ki class ke instance me badalta hai (**class-transformer** se), validate karta hai, aur kuch ghalat ho to har masle ke saath **400** deta hai, isliye aap ka controller hamesha sirf durust data dekhta hai. Teen options sab se ahem hain: **`whitelist`** bina decorators wali properties hata deta hai, **`forbidNonWhitelisted`** unhen hatane ke bajaye radd karta hai (isliye `"isAdmin": true` chupke se reh jane ke bajaye error banta hai), aur **`transform`** asli class instances deta hai, `@Type(() => Number)` se query strings ko numbers banata hai aur default values lagata hai. Ye Express me banaye zod middleware ka Nest wala roop hai: wahi maqasid, decorated classes ki shakal me jo TypeScript types aur baad me OpenAPI docs bhi dete hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of an **airport check-in desk**.

- The airline publishes the **rules** for a bag (the DTO): at most 23 kg, these dimensions, no liquids over 100 ml. Each rule is printed on the form (a decorator on a property).
- The **check-in agent** (ValidationPipe) checks every bag before it goes to the plane (the controller). Problems are listed all at once: "overweight, and the handle is too long", not one per visit.
- Items **not on the allowed list** are either quietly removed (`whitelist`) or the whole bag is refused (`forbidNonWhitelisted`).
- The agent also **converts** things to the airline's standard: "about 20 pounds" becomes "9 kg" (`transform`, `@Type`), and a missing seat preference gets "any" (default values).
- The rules for **changing a booking** are the same rules with everything optional (`PartialType`).

</En>
<Ur>

**Airport ke check-in desk** ka sochein.

- Airline bag ke **qawaid** shaya karti hai (DTO): zyada se zyada 23 kg, ye naap, 100 ml se zyada liquids nahi. Har qaida form par chhapa hai (property par decorator).
- **Check-in agent** (ValidationPipe) har bag jahaz (controller) tak jane se pehle check karta hai. Masle ek saath batata hai: "wazan zyada, aur handle bohot lamba", har chakkar me ek nahi.
- **Ijazat wali list me na hone wali cheezen** ya chupke se nikal di jati hain (`whitelist`) ya poora bag radd hota hai (`forbidNonWhitelisted`).
- Agent cheezon ko airline ke mayaar me **badalta** bhi hai: "taqreeban 20 pound" "9 kg" ban jata hai (`transform`, `@Type`), aur ghayab seat ki pasand ko "koi bhi" milta hai (default values).
- **Booking badalne** ke qawaid wahi qawaid hain, sab ikhtiyari (`PartialType`).

</Ur>
</Tr>

```bash
import {
  ArrayMaxSize, IsArray, IsIn, IsInt, IsOptional, IsPositive, IsString,
  Length, Max, Min, ValidateNested,
} from 'class-validator';

export class DimensionsDto {
  @IsInt() @Min(1) width: number;
  @IsInt() @Min(1) height: number;
}

export class CreateProductDto {
  @IsString() @Length(2, 100)

  @IsPositive()
  price: number;

  dimensions?: DimensionsDto;
}
```

<Happened>
<Tr>
<En>

- **Valid body**: the controller received a real `CreateProductDto` instance (`isDtoInstance: true`, thanks to `transform`), and the missing `currency` got its default `USD`.
- **Invalid body**: **seven** messages at once, including nested ones (`dimensions.width`, `dimensions.height` was missing so it failed `@IsInt` and `@Min`) and per-item array checks (`each value in tags must be a string`). The controller never ran.
- **Over-posting**: `"isAdmin": true` was rejected with `property isAdmin should not exist`. With only `whitelist: true` it would have been silently removed; `forbidNonWhitelisted` makes it visible, which helps catch client bugs and probing.
- **Query DTO**: `page=3` arrived as a string, `@Type(() => Number)` converted it, and `limit` got its default 20. Out-of-range values were rejected.
- Without `transform: true`, `query.page` would still be the string `"3"` and defaults wouldn't apply, even though TypeScript says `number`. TypeScript types alone never validate or convert anything at runtime.

</En>
<Ur>

- **Durust body**: controller ko asli `CreateProductDto` instance mila (`isDtoInstance: true`, `transform` ki badolat), aur ghayab `currency` ko default `USD` mila.
- **Ghalat body**: ek saath **saat** paighaam, nested samet (`dimensions.width`, `dimensions.height` ghayab tha isliye `@IsInt` aur `@Min` par fail hua) aur array ke har item ke checks (`each value in tags must be a string`). Controller kabhi nahi chala.
- **Zyada fields**: `"isAdmin": true` `property isAdmin should not exist` ke saath radd hua. Sirf `whitelist: true` ke saath ye chupke se hat jata; `forbidNonWhitelisted` ise zahir karta hai, jo client bugs aur jaanch partaal pakarne me madad karta hai.
- **Query DTO**: `page=3` string ban kar aaya, `@Type(() => Number)` ne convert kiya, aur `limit` ko default 20 mila. Hadd se bahar values radd huin.
- `transform: true` ke baghair `query.page` ab bhi string `"3"` hota aur defaults lagu na hote, chahe TypeScript `number` kahe. Akeli TypeScript types runtime par kabhi kuch validate ya convert nahi kartin.

</Ur>
</Tr>

<Step title="PATCH DTOs, a custom rule and better errors">

<Tr>
<En>
`UpdateProductDto` reuses the create rules with `PartialType(OmitType(...))` (all optional, `currency` not changeable) and adds `salePrice` with a custom `@LowerThan('price')` decorator. An `exceptionFactory` reshapes errors into `{ field: [messages] }`.
</En>
<Ur>
`UpdateProductDto` `PartialType(OmitType(...))` se create ke qawaid dobara istemal karta hai (sab ikhtiyari, `currency` na badalne qabil) aur custom `@LowerThan('price')` decorator ke saath `salePrice` jorta hai. `exceptionFactory` errors ko `{ field: [messages] }` ki shakal deta hai.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/products/dto/lower-than.validator.ts <<'EOF'
import { registerDecorator, ValidationArguments, ValidationOptions } from 'class-validator';

// A custom, cross-field rule: @LowerThan('price') on salePrice
export function LowerThan(property: string, options?: ValidationOptions) {
  return (target: object, propertyName: string) =>
    registerDecorator({
      name: 'lowerThan',
      target: target.constructor,
      propertyName,
      constraints: [property],
      options: { message: `${propertyName} must be lower than ${property}`, ...options },
      validator: {
        validate(value: unknown, args: ValidationArguments) {
          const other = (args.object as Record<string, unknown>)[args.constraints[0]];
          return typeof value !== 'number' || typeof other !== 'number' || value < other;
        },
      },
    });
}
EOF
cat > src/products/dto/update-product.dto.ts <<'EOF'
import { PartialType, OmitType } from '@nestjs/mapped-types';
import { IsOptional, IsPositive } from 'class-validator';
import { CreateProductDto } from './create-product.dto.js';
import { LowerThan } from './lower-than.validator.js';

// Every field of CreateProductDto except currency, all optional, with their validation rules kept
export class UpdateProductDto extends PartialType(OmitType(CreateProductDto, ['currency'] as const)) {
  @IsPositive() @LowerThan('price') @IsOptional()
  salePrice?: number;
}
EOF

import { NestFactory } from '@nestjs/core';
import { BadRequestException, ValidationError, ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module.js';

// Turn class-validator's errors into { field: [messages] }, including nested fields
function toFieldErrors(errors: ValidationError[], prefix = ''): Record<string, string[]> {
  return errors.reduce((acc, e) => {
    const path = prefix + e.property;
    if (e.constraints) acc[path] = Object.values(e.constraints);
    if (e.children?.length) Object.assign(acc, toFieldErrors(e.children, `${path}.`));
    return acc;
  }, {} as Record<string, string[]>);
}

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
    transform: true,
    exceptionFactory: (errors) =>
      new BadRequestException({ error: 'validation_failed', fields: toFieldErrors(errors) }),
  }));
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();
EOF
```

<Happened>
<Tr>
<En>

- `{"price":20}` passed: every field is optional in the PATCH DTO, and no default `currency` was added because `OmitType` removed that field entirely.
- The **custom validator** compared two fields and reported `salePrice must be lower than price`. `registerDecorator` gives you the whole object (`args.object`), so any cross-field rule is possible.
- `currency` is no longer allowed in updates: `OmitType` removed it, so `forbidNonWhitelisted` rejected it. This is how you protect fields that only certain flows may change (`role`, `ownerId`, `status`).
- The **error format** now groups messages by field, including nested paths (`dimensions.width`), which a front end can map to form inputs directly. Clients get one stable shape (`error: "validation_failed"`) instead of Nest's array of sentences.
- `"price":"cheap"` failed `@IsPositive` without crashing: class-validator checks types as well as values.

</En>
<Ur>

- `{"price":20}` paas hua: PATCH DTO me har field ikhtiyari hai, aur koi default `currency` nahi juda kyun ke `OmitType` ne wo field poora hata diya.
- **Custom validator** ne do fields milaye aur `salePrice must be lower than price` bataya. `registerDecorator` aap ko poora object (`args.object`) deta hai, isliye kai fields ka koi bhi qaida mumkin hai.
- Updates me `currency` ab allowed nahi: `OmitType` ne ise hata diya, isliye `forbidNonWhitelisted` ne radd kiya. Isi tarah aap aise fields mehfooz karte hain jinhen sirf khaas flows badal saken (`role`, `ownerId`, `status`).
- **Error format** ab paighaam field ke hisaab se jama karta hai, nested paths samet (`dimensions.width`), jinhen front end seedha form inputs se mila sakta hai. Clients ko Nest ke jumlon ki array ke bajaye ek mustahkam shakal (`error: "validation_failed"`) milti hai.
- `"price":"cheap"` crash kiye baghair `@IsPositive` par fail hua: class-validator values ke saath types bhi check karta hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Interfaces or plain types as DTOs">

```text
interface CreateProductDto { name: string; price: number; }   // erased at runtime: nothing to validate
@Post() create(@Body() dto: CreateProductDto) { return this.products.save(dto); }   // anything gets saved
```

</Bad>
<Good title="Classes with decorators and a global pipe">

```text
export class CreateProductDto {
  @IsString() @Length(2, 100) name: string;
  @IsPositive() price: number;
}
app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }));
```

</Good>
</Compare>

<Compare>
<Bad title="Nested object without @Type">

```text
@ValidateNested()
address: AddressDto;          // without @Type, the nested object stays a plain object and its rules are skipped
```

</Bad>
<Good title="Tell class-transformer the class">

```text
@ValidateNested() @Type(() => AddressDto)
address: AddressDto;

@ValidateNested({ each: true }) @Type(() => OrderItemDto) @ArrayMinSize(1)
items: OrderItemDto[];
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting `@IsOptional()`** on optional fields: missing values fail the other rules.
- **Using `@IsOptional()` where `null` must be rejected**: it skips validation for both `undefined` and `null`.
- **Relying on `enableImplicitConversion`** (converting by TypeScript type): `"false"` becomes `true` for booleans; be explicit with `@Type` or `@Transform`.
- **No maximums** (`@MaxLength`, `@ArrayMaxSize`, `@Max`) on strings, arrays and page sizes.
- **Copying the create DTO for updates** instead of `PartialType`, so the two drift apart.
- **Returning entities with sensitive fields**: DTOs validate input; for output, use serialisation (`ClassSerializerInterceptor`, `@Exclude`) or explicit mapping.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Ikhtiyari fields par **`@IsOptional()` bhoolna**: ghayab values baqi qawaid par fail hoti hain.
- **Jahan `null` radd karna ho wahan `@IsOptional()` lagana**: ye `undefined` aur `null` dono ke liye validation chhor deta hai.
- **`enableImplicitConversion` par bharosa** (TypeScript type se convert): booleans ke liye `"false"` `true` ban jata hai; `@Type` ya `@Transform` se wazeh rahein.
- Strings, arrays aur page sizes par **zyada se zyada hadd nahi** (`@MaxLength`, `@ArrayMaxSize`, `@Max`).
- `PartialType` ke bajaye **updates ke liye create DTO copy karna**, jis se dono alag hote jate hain.
- **Hassas fields wali entities return karna**: DTOs input validate karte hain; output ke liye serialisation (`ClassSerializerInterceptor`, `@Exclude`) ya wazeh mapping lein.

</Ur>
</Tr>

## Try it yourself

<Challenge title="An order DTO">

<Tr>
<En>
Write `CreateOrderDto` with: `items` (1–20 objects of `{ productId: positive int, quantity: int 1–10 }`), optional `couponCode` (4–12 uppercase letters or digits), `shippingMethod` (`standard` or `express`, default `standard`), and `shippingAddress` (`{ line1, city, postalCode, country: 2-letter code }`).
</En>
<Ur>
`CreateOrderDto` likhein jis me ho: `items` (`{ productId: musbat int, quantity: int 1–10 }` ke 1–20 objects), ikhtiyari `couponCode` (4–12 bare huroof ya hindse), `shippingMethod` (`standard` ya `express`, default `standard`), aur `shippingAddress` (`{ line1, city, postalCode, country: 2 huroof ka code }`).
</Ur>
</Tr>

<Solution>

```text
export class OrderItemDto {
  @IsInt() @IsPositive() productId: number;
  @IsInt() @Min(1) @Max(10) quantity: number;
}

export class AddressDto {
  @IsString() @Length(1, 200) line1: string;
  @IsString() @Length(1, 100) city: string;
  @IsString() @Length(3, 12) postalCode: string;
  @IsISO31661Alpha2() country: string;
}

export class CreateOrderDto {
  @IsArray() @ArrayMinSize(1) @ArrayMaxSize(20)
  @ValidateNested({ each: true }) @Type(() => OrderItemDto)
  items: OrderItemDto[];

  @IsOptional() @Matches(/^[A-Z0-9]{4,12}$/)
  couponCode?: string;

  @IsOptional() @IsIn(['standard', 'express'])
  shippingMethod: 'standard' | 'express' = 'standard';

  @ValidateNested() @Type(() => AddressDto)
  shippingAddress: AddressDto;
}
```

<Tr>
<En>
To accept lowercase coupons and uppercase them, add `@Transform(({ value }) => typeof value === 'string' ? value.trim().toUpperCase() : value)` above `couponCode`; transforms run before validation when `transform: true`. Duplicate product IDs need a custom validator (or a check in the service).
</En>
<Ur>
Chhote huroof wale coupons qubool kar ke bara karne ke liye `couponCode` ke upar `@Transform(({ value }) => typeof value === 'string' ? value.trim().toUpperCase() : value)` jorein; `transform: true` ke saath transforms validation se pehle chalte hain. Dohraye product IDs ke liye custom validator (ya service me check) chahiye.
</Ur>
</Tr>

A mobile app (older versions still in use) sends an extra `deviceModel` field to `POST /feedback` that your DTO doesn't have. A partner integration sometimes sends `role` to `PATCH /users/:id`. <En>

## Remember

<Takeaways>
<Tr>
<En>

- DTOs are classes whose properties carry class-validator decorators.
- One global `ValidationPipe({ whitelist, forbidNonWhitelisted, transform })` validates every body and query.
- `transform` creates instances, applies `@Type` conversions and defaults; nested objects need `@ValidateNested` + `@Type`.
- Derive update DTOs with `PartialType`, `PickType`, `OmitType`; omit fields clients must not change.
- Custom decorators handle cross-field rules; `exceptionFactory` shapes the error response.
- Set maximums everywhere; validate input with DTOs and control output separately.

<DeepDive title="More about DTOs">

**`@Transform`.** Normalise values before validation: trim strings, lowercase emails, parse `"true"/"false"` into booleans explicitly.

**Validation groups.** `@IsNotEmpty({ groups: ['create'] })` and `new ValidationPipe({ groups: ['create'] })` apply different rules in different flows, though separate DTOs are usually clearer.

**Async validators.** `@ValidatorConstraint({ async: true })` classes can query the database (for example "email not taken"); still enforce uniqueness with a database constraint.

**Swagger integration.** Import `PartialType` from `@nestjs/swagger` instead of `@nestjs/mapped-types` so derived DTOs also appear correctly in the OpenAPI docs; the CLI plugin can infer docs from DTO types.

**zod in Nest.** Some teams prefer zod schemas with a custom pipe (or libraries like `nestjs-zod`) to share schemas with front ends; the principles are identical.

**Performance.** class-transformer and class-validator are reflection-heavy; for very hot endpoints, measure, and keep DTOs flat where possible.

</DeepDive>

<DeepDive title="Real world: the price field nobody validated">

An events platform let organisers create ticket types through `POST /events/:id/tickets`. The DTO had `@IsString() name` and `@IsInt() quantity`, but `price` was declared as `price: number` with **no decorator**. The global `ValidationPipe` used `transform: true` but not `whitelist`.

Because `price` had no decorator, it wasn't validated at all. An organiser's integration script had a bug that sent prices in cents as strings with a minus sign for discounts, like `"-500"`. The value went straight into the database (the column accepted numeric strings), creating tickets with negative prices. Buyers who found them received money back on checkout through the payment provider's refund flow, until finance noticed a negative revenue day.

The postmortem changes:

1. `whitelist: true` and `forbidNonWhitelisted: true` were enabled globally, so undecorated properties could no longer slip through; this immediately surfaced 14 other DTO fields without validation.
2. `price` got `@IsInt() @Min(0) @Max(1_000_000)`, with amounts stored in cents as integers.
3. A unit test iterated over all DTO classes and failed if any property lacked a class-validator decorator.
4. The database column got a `CHECK (price >= 0)` constraint as a final safety net.

A property without a decorator isn't "unvalidated input you'll check later"; with `whitelist` off, it's an open door.

</DeepDive>

<DeepDive title="Security lens">

- **Always `whitelist`** (and usually `forbidNonWhitelisted`) to block mass assignment.
- **Bound every value**: string lengths, array sizes, numeric ranges, nested depth; combine with body size limits.
- **Separate DTOs per flow**: users can't send `role`, `ownerId`, `verified`, `price` overrides unless that flow is authorised for it.
- **Validation is not authorisation**: a valid `productId` still needs an ownership or permission check.
- **Keep error messages user-safe**: validation messages are fine, but don't echo secrets or internal details.
- **Back validation with database constraints** (NOT NULL, CHECK, UNIQUE, foreign keys).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a DTO in NestJS and why use classes?">
A Data Transfer Object describes the shape of data entering or leaving the API. Classes are used because they exist at runtime, so validation decorators can be attached and class-transformer can instantiate them, unlike interfaces.
</QA>

<QA q="What do whitelist, forbidNonWhitelisted and transform do in ValidationPipe?">
whitelist strips properties without validation decorators, forbidNonWhitelisted rejects requests containing them with 400, and transform converts payloads into DTO instances, applying @Type conversions and default values.
</QA>

<QA q="How do you validate nested objects and arrays?">
Use @ValidateNested, with each: true for arrays, together with @Type(() => NestedDto) so class-transformer creates instances of the nested class and its decorators are applied.
</QA>

<QA q="How do you create an update DTO without duplicating rules?">
Extend PartialType of the create DTO, optionally combined with PickType or OmitType, from @nestjs/mapped-types or @nestjs/swagger, which copies validation metadata and makes fields optional.
</QA>

<QA q="How do you implement a cross-field validation rule?">
Write a custom decorator with registerDecorator or a ValidatorConstraint class that reads other properties from args.object, or use @ValidateIf for conditional rules.
</QA>

</DeepDive>
