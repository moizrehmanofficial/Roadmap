<BigIdea>
<Tr>
<En>
In the Express module you **built your own architecture**: feature folders, routes that only speak HTTP, services with business rules, factories that receive their dependencies, a shared error handler. It works, but every team builds it slightly differently, and nothing enforces it. **NestJS** makes that architecture the **framework**. Code lives in **modules** (one per feature). **Controllers** handle HTTP using **decorators** (`@Controller('products')`, `@Get(':id')`, `@Body()`), so routes are declared right on the methods. **Providers** such as services are marked `@Injectable()`, and Nest's **dependency injection (DI) container** creates them and passes them into constructors automatically, which replaces the manual wiring in `server.js`. Built-in **pipes** convert and validate input (`ParseIntPipe` turns `"1"` into `1` and `"abc"` into a 400), and built-in **exceptions** (`NotFoundException`) become consistent JSON errors. Under the hood, Nest still runs on **Express** (or Fastify), so everything you learned applies. The cost: more concepts, decorators and boilerplate. The payoff: large codebases and teams that all follow the same structure.
</En>
<Ur>
Express module me aap ne **apni architecture khud banai**: feature folders, sirf HTTP bolne wale routes, business qawaid wali services, dependencies lene wali factories, mushtarka error handler. Ye chalti hai, magar har team ise thora mukhtalif banati hai, aur koi ise lazmi nahi karta. **NestJS** us architecture ko **framework** bana deta hai. Code **modules** me rehta hai (har feature ka ek). **Controllers** **decorators** (`@Controller('products')`, `@Get(':id')`, `@Body()`) se HTTP sambhalte hain, isliye routes methods par hi bayan hote hain. Services jaise **providers** par `@Injectable()` lagta hai, aur Nest ka **dependency injection (DI) container** unhen bana kar khud constructors me deta hai, jo `server.js` ki haath ki wiring ki jagah leta hai. Built-in **pipes** input convert aur validate karte hain (`ParseIntPipe` `"1"` ko `1` aur `"abc"` ko 400 banata hai), aur built-in **exceptions** (`NotFoundException`) yaksan JSON errors bante hain. Andar se Nest ab bhi **Express** (ya Fastify) par chalta hai, isliye jo seekha sab kaam aata hai. Qeemat: zyada concepts, decorators aur boilerplate. Faida: bare codebases aur teams jo sab ek hi structure maante hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

- The **independent restaurant** (Express) can arrange its kitchen any way it likes. A great chef builds an excellent system; another chef across town builds a confusing one. New staff must learn each kitchen from scratch.

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Decorator** | `@Something` attached to a class, method or parameter that adds metadata | `@Get(':id')` |
| **Module** | Groups controllers and providers of one feature | `ProductsModule` |
| **Root module** | The module Nest starts from | `AppModule` |
| **Controller** | Class that handles routes for a path prefix | `@Controller('products')` |
| **Provider** | Anything Nest can inject: services, repositories, factories | `ProductsService` |
| **`@Injectable()`** | Marks a class as a provider | services |
| **Dependency injection** | Nest creates and passes in dependencies | constructor parameters |
| **Pipe** | Transforms or validates input before the handler | `ParseIntPipe` |
| **`HttpException`** | Base class for errors that map to HTTP responses | `NotFoundException` |
| **Nest CLI** | Command-line tool to create, generate and build | `nest g service` |
| **`NestFactory`** | Creates the application from the root module | `NestFactory.create(AppModule)` |

<Step title="Write the service and controller">

<Tr>
<En>
The service holds the products and the business rules and throws Nest exceptions; the controller declares three routes with decorators and receives the service through its constructor. Then we build, run and call the API.
</En>
<Ur>
Service products aur business qawaid rakhti hai aur Nest exceptions throw karti hai; controller decorators se teen routes bayan karta hai aur service apne constructor ke zariye leta hai. Phir hum build kar ke API chalate aur bulate hain.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/products/products.service.ts <<'EOF'
import { Injectable, NotFoundException, ConflictException } from '@nestjs/common';

export interface Product { id: number; name: string; price: number; }

@Injectable()                                    // Nest can create it and inject it where needed
export class ProductsService {
  private products: Product[] = [{ id: 1, name: 'Travel Mug', price: 24 }];

  findAll(): Product[] {
    return this.products;
  }

  findOne(id: number): Product {
    const product = this.products.find((p) => p.id === id);
    if (!product) throw new NotFoundException(`Product ${id} not found`);   // becomes a 404 response
    return product;
  }

  create(data: { name: string; price: number }): Product {
    if (this.products.some((p) => p.name === data.name)) throw new ConflictException('Name already exists');
    const product = { id: this.products.length + 1, ...data };
    this.products.push(product);
    return product;
  }
}
EOF
cat > src/products/products.controller.ts <<'EOF'
import { Body, Controller, Get, Param, ParseIntPipe, Post } from '@nestjs/common';
import { ProductsService } from './products.service.js';

@Controller('products')                          // every route below starts with /products
export class ProductsController {
  constructor(private readonly productsService: ProductsService) {}   // injected by Nest

  @Get()
  findAll() {
    return this.productsService.findAll();       // returned objects are sent as JSON
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {   // "1" → 1, "abc" → 400
    return this.productsService.findOne(id);
  }

  @Post()                                        // POST answers 201 by default
  create(@Body() body: { name: string; price: number }) {
    return this.productsService.create(body);
  }
}
EOF
npm run build --silent
NO_COLOR=1 node dist/main.js > server.log 2>&1 &
sleep 2
J="Content-Type: application/json"
curl -s localhost:3000/products; echo
curl -s localhost:3000/products/1; echo
curl -s -w " %{http_code}\n" localhost:3000/products/abc
curl -s -w " %{http_code}\n" localhost:3000/products/9
curl -s -X POST -H "$J" -d '{"name":"Desk Lamp","price":39}' -w " %{http_code}\n" localhost:3000/products
curl -s -X POST -H "$J" -d '{"name":"Desk Lamp","price":39}' -w " %{http_code}\n" localhost:3000/products
kill %1
grep -E "Mapped|RoutesResolver" server.log | sed -E "s/^.*LOG //; s/ \+[0-9]+ms$//"
```

<Happened>
<Tr>
<En>

- **No `res.json`, no `next`**: controller methods simply **return** data; Nest sends it as JSON with 200 (or **201** for `@Post`).
- **Dependency injection**: we never wrote `new ProductsService()`. Because the service is `@Injectable()` and listed in the module's `providers`, Nest created **one instance** and passed it to the controller's constructor.
- **`ParseIntPipe`** converted `"1"` to the number 1 and rejected `abc` with a **400** before our method ran: the Express `validate()` middleware, as a parameter decorator.
- **Exceptions**: `NotFoundException` and `ConflictException` thrown in the service became **404** and **409** with the standard JSON shape, no error handler needed. (Throwing HTTP exceptions from services is common in Nest, though some teams prefer domain errors mapped by an exception filter.)
- The log lists the routes Nest discovered: `{/products, GET}`, `{/products/:id, GET}`, `{/products, POST}`.
- `@Body()` accepted any JSON here; there's no validation of `name` and `price` yet. The DTOs and Validation lesson adds `ValidationPipe` with class-validator.

</En>
<Ur>

- **Na `res.json`, na `next`**: controller methods bas data **return** karte hain; Nest use 200 (ya `@Post` ke liye **201**) ke saath JSON me bhejta hai.
- **Dependency injection**: humne kabhi `new ProductsService()` nahi likha. Kyun ke service `@Injectable()` hai aur module ke `providers` me hai, Nest ne **ek instance** banaya aur controller ke constructor ko diya.
- **`ParseIntPipe`** ne `"1"` ko number 1 banaya aur hamare method chalne se pehle `abc` ko **400** ke saath radd kiya: Express ka `validate()` middleware, parameter decorator ki shakal me.
- **Exceptions**: service me throw hue `NotFoundException` aur `ConflictException` mayaari JSON shakal ke saath **404** aur **409** bane, error handler ki zaroorat nahi. (Nest me services se HTTP exceptions throw karna aam hai, halanke kuch teams exception filter se milaye gaye domain errors pasand karti hain.)
- Log wo routes dikhata hai jo Nest ne dhoondhe: `{/products, GET}`, `{/products/:id, GET}`, `{/products, POST}`.
- Yahan `@Body()` ne koi bhi JSON qubool kiya; `name` aur `price` ki abhi koi validation nahi. DTOs and Validation lesson class-validator ke saath `ValidationPipe` jorta hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Creating dependencies with new">

```text
@Controller('orders')
export class OrdersController {
  private orders = new OrdersService(new OrdersRepository(new Pool()));   // DI bypassed: hard to test and configure
}
```

</Bad>
<Good title="Let the container inject them">

```text
@Controller('orders')
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}   // OrdersService is a provider in OrdersModule
}
```

</Good>
</Compare>

<Compare>
<Bad title="Business logic in controllers">

```text
@Post()
async create(@Body() body) {
  const exists = await this.db.query('SELECT …');        // SQL in the controller
  if (body.price > 1000 && !body.approved) { … }          // rules in the controller
}
```

</Bad>
<Good title="Thin controllers, rules in services">

```text
@Post()
create(@Body() dto: CreateProductDto) {
  return this.productsService.create(dto);
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting to add a provider to a module** (or to `exports` when another module needs it): Nest fails at startup with "Nest can't resolve dependencies of …".
- **One giant `AppModule`** with every controller and provider: split by feature.
- **Circular imports between modules**: usually a sign the boundary is wrong; extract a shared module.
- **Fighting the framework** by writing raw Express handlers everywhere through `@Res()`: you lose interceptors, serialisation and standard errors.
- **Choosing Nest for a tiny service** where an Express file would do.
- **Missing `.js` in relative imports** in ES module projects.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Provider ko module me jorna bhoolna** (ya `exports` me jab doosre module ko chahiye): Nest startup par "Nest can't resolve dependencies of …" ke saath fail hota hai.
- Har controller aur provider wala **ek dio-qamat `AppModule`**: feature ke hisaab se taqseem karein.
- **Modules ke darmiyan circular imports**: aam taur par nishani ke hadd ghalat hai; mushtarka module nikalein.
- Har jagah `@Res()` ke zariye kache Express handlers likh kar **framework se larna**: interceptors, serialisation aur mayaari errors kho dete hain.
- Chhoti service ke liye **Nest chunna** jahan ek Express file kafi ho.
- ES module projects me relative imports me **`.js` bhoolna**.

</Ur>
</Tr>

<DeepDive title="More about NestJS">

**How decorators work.** `@Get(':id')` stores metadata on the method (the HTTP method and path). At startup, Nest reads this metadata with `reflect-metadata`, and constructor parameter **types** tell the DI container what to inject.

**The request pipeline.** Middleware → guards (can this request proceed?) → interceptors (before) → pipes (transform/validate) → handler → interceptors (after) → exception filters on errors. Later lessons cover each.

**Platform swap.** `NestFactory.create(AppModule, new FastifyAdapter())` runs the same app on Fastify for higher throughput; code that avoids Express-specific `@Req()`/`@Res()` moves without changes.

**Beyond HTTP.** The same modules and providers power microservices (TCP, Redis, NATS, Kafka transports), GraphQL resolvers, WebSocket gateways, CLI apps and standalone scripts (`NestFactory.createApplicationContext`).

**Provider scopes.** Providers are singletons by default; request-scoped providers exist for per-request state but cost performance.

**Monorepos.** `nest g app` and `nest g library` create workspaces with several apps and shared libraries.

</DeepDive>

<DeepDive title="Real world: the Express codebase nobody wanted to touch">

A logistics company's main API started as a small Express app. Over five years, 30 developers added 400 routes. Each wave of developers had its own style: some files used controllers and services, others put SQL in route handlers, three different validation libraries were in use, and errors came back in five different JSON shapes. New hires took about two months to become productive, and the front-end team kept a wiki page of "which endpoints return errors in which format".

The company didn't rewrite everything. They introduced NestJS **next to** the Express app: Nest can mount an existing Express instance, so new features were built as Nest modules under `/v2`, with `ValidationPipe`, a global exception filter producing one error format, guards for auth and generated OpenAPI docs. Old routes were moved into Nest modules whenever someone had to change them anyway.

After 18 months, about 80% of traffic went through Nest modules. Onboarding time dropped to about three weeks, because every feature followed the same layout and the CLI generated the skeleton. The remaining Express routes were the rarely touched ones, and nobody minded leaving them.

The structure itself wasn't new: it's what a disciplined Express team would build. What changed was that the framework enforced it, so it survived turnover.

</DeepDive>

<DeepDive title="Security lens">

- **Validate globally**: enable `ValidationPipe` with `whitelist` and `forbidNonWhitelisted` (DTOs lesson) so unknown fields are stripped or rejected.
- **Guards for authentication and authorisation** on controllers, and consider a global guard that requires auth unless a route is explicitly marked public.
- **Exception filters** should never expose stack traces in production; Nest's default hides internal errors as a generic 500.
- **helmet, CORS and rate limiting** work in Nest too (`app.use(helmet())`, `app.enableCors()`, `@nestjs/throttler`).
- **Keep dependencies updated**: Nest projects pull in many packages; use `npm audit` and Dependabot.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is NestJS and why use it over plain Express?">
A TypeScript framework for Node.js backends that runs on Express or Fastify and provides an opinionated architecture with modules, controllers, providers and dependency injection, plus built-in pipes, guards, interceptors, exception filters and integrations. It enforces consistent structure, which helps large teams and long-lived codebases.
</QA>

<QA q="What is a module in NestJS?">
A class decorated with @Module that groups related controllers and providers, declares which other modules it imports and which of its providers it exports. The application is a tree of modules starting from the root AppModule.
</QA>

<QA q="How does dependency injection work in NestJS?">
Providers decorated with @Injectable are registered in a module. When Nest instantiates a class, it reads the constructor parameter types, resolves matching providers from the module and its imports, creates them as singletons by default, and passes them in.
</QA>

<QA q="What's the difference between a controller and a provider?">
Controllers handle incoming requests and map routes to methods using decorators; providers contain logic or resources, such as services and repositories, that can be injected into controllers or other providers.
</QA>

<QA q="When would you not choose NestJS?">
For very small services, prototypes or edge functions where its abstractions, decorators and startup cost outweigh the benefits, or when the team prefers minimal, explicit code with Express, Fastify or Hono.
</QA>

</DeepDive>
