<BigIdea>
<Tr>
<En>
**Passport** is the most widely used authentication library for Node.js. It organises authentication into **strategies**: "local" checks a username and password, "jwt" checks a bearer token, "google" handles OAuth, and hundreds more exist. **`@nestjs/passport`** turns each strategy into a Nest **guard**: `AuthGuard('local')` runs the local strategy, `AuthGuard('jwt')` runs the JWT strategy. You write a small class per strategy with a **`validate()`** method: whatever it returns becomes **`req.user`**, and throwing `UnauthorizedException` answers **401**. The flow for an API is: `POST /auth/login` uses the **local** strategy to compare the password with a **bcrypt hash**, and if it matches, **`@nestjs/jwt`** signs a short-lived **access token** containing the user's ID (`sub`) and roles. Every other request sends `Authorization: Bearer <token>`; a **global `JwtAuthGuard`** verifies the signature, issuer and expiry and loads the user, unless the route is marked `@Public()`. It's the same security as the Express version, with the plumbing handled by guards and DI.
</En>
<Ur>
**Passport** Node.js ki sab se zyada istemal hone wali authentication library hai. Ye authentication ko **strategies** me baantti hai: "local" username aur password check karti hai, "jwt" bearer token check karti hai, "google" OAuth sambhalti hai, aur saikron aur maujood hain. **`@nestjs/passport`** har strategy ko Nest **guard** bana deta hai: `AuthGuard('local')` local strategy chalata hai, `AuthGuard('jwt')` JWT strategy. Aap har strategy ke liye **`validate()`** method wali chhoti class likhte hain: jo ye wapas kare wo **`req.user`** banta hai, aur `UnauthorizedException` throw karne se **401** milta hai. API ke liye flow ye hai: `POST /auth/login` **local** strategy se password ko **bcrypt hash** se milata hai, aur mil jaye to **`@nestjs/jwt`** user ki ID (`sub`) aur roles wala kam muddat ka **access token** sign karta hai. Har doosri request `Authorization: Bearer <token>` bhejti hai; **global `JwtAuthGuard`** signature, issuer aur expiry tasdeeq kar ke user load karta hai, jab tak route `@Public()` na ho. Ye Express wale version jaisi hi security hai, bas plumbing guards aur DI sambhalte hain.
</Ur>
</Tr>

<Tr>
<En>

- Passport strategies are battle-tested; you don't hand-write token parsing or verification.

- Guards integrate with the rest of Nest: `req.user` for `@CurrentUser()`, roles guards, `@Public()`.
- This is the setup most NestJS job descriptions and codebases expect you to know.

## Picture it

<Tr>
<En>

Think of a **conference** with a registration desk and session rooms.

- At **registration** (login), you show your ID and confirmation code. The staff check them against their list (local strategy, bcrypt compare). If either is wrong, you just hear "we can't find that registration" (the same 401 for both).
- If it matches, you get a **badge** printed with your name, your ticket type, and "valid today", stamped with the organiser's **hologram** (the signed JWT).
- At every **session room** (protected route), a scanner checks the hologram and the date (JWT strategy) and lets you in. Nobody calls the registration desk again.
- A badge with the ticket type changed by hand fails the hologram check (tampered token). Yesterday's badge fails the date check (expired token).
- The **coffee area** is open to everyone (`@Public()`).

</En>

Registration desk aur session rooms wali **conference** ka sochein.

<Step title="Login with the local strategy, protect everything with JWT">

<Tr>
<En>
Users are stored with bcrypt hashes. `LocalStrategy` checks the login; `JwtStrategy` checks tokens and reloads the user. `AuthController.login` signs a 15-minute token. `JwtAuthGuard` extends `AuthGuard('jwt')`, is global, and skips routes marked `@Public()`. We try wrong credentials, a real login, the token's payload, `/me` with and without a token, the default `/` route, and a tampered token.
</En>
<Ur>
Users bcrypt hashes ke saath rakhe gaye hain. `LocalStrategy` login check karti hai; `JwtStrategy` tokens check kar ke user dobara load karti hai. `AuthController.login` 15 minute ka token sign karta hai. `JwtAuthGuard` `AuthGuard('jwt')` ko barhata hai, global hai, aur `@Public()` wale routes chhor deta hai. Hum ghalat credentials, asli login, token ka payload, token ke saath aur baghair `/me`, default `/` route, aur chheda hua token aazmate hain.
</Ur>
</Tr>

import { Injectable } from '@nestjs/common';
import bcrypt from 'bcryptjs';

export interface User { id: number; email: string; roles: string[]; passwordHash: string }

@Injectable()
export class UsersService {
  // In a real app these rows live in a database; passwords are only ever stored hashed
  private readonly users: User[] = [
    { id: 1, email: 'emma@example.com', roles: ['admin'], passwordHash: bcrypt.hashSync('blue-teapot-2026', 10) },
    { id: 2, email: 'liam@example.com', roles: ['customer'], passwordHash: bcrypt.hashSync('green-kettle-2026', 10) },
  ];
  findByEmail(email: string) { return this.users.find((u) => u.email === email); }
  findById(id: number) { return this.users.find((u) => u.id === id); }
}

cat > src/auth/strategies.ts <<'EOF'
import { Injectable, UnauthorizedException } from '@nestjs/common';
import { PassportStrategy } from '@nestjs/passport';
import { Strategy as LocalStrategyBase } from 'passport-local';
import { ExtractJwt, Strategy as JwtStrategyBase } from 'passport-jwt';
import bcrypt from 'bcryptjs';
import { UsersService } from './users.service.js';

export const JWT_SECRET = process.env.JWT_SECRET ?? 'dev-only-secret-change-me-at-least-32-chars';
const DUMMY_HASH = bcrypt.hashSync('not-a-real-password', 10);   // same work for unknown emails

// "local": email + password from the request body → user
@Injectable()
export class LocalStrategy extends PassportStrategy(LocalStrategyBase) {
  constructor(private readonly users: UsersService) {
    super({ usernameField: 'email' });
  }
  async validate(email: string, password: string) {
    const user = this.users.findByEmail(email);
    const ok = await bcrypt.compare(password, user?.passwordHash ?? DUMMY_HASH);
    if (!user || !ok) throw new UnauthorizedException('Invalid email or password');
    return { id: user.id, email: user.email, roles: user.roles };   // becomes req.user
  }
}

// "jwt": Authorization: Bearer <token> → verified payload → user
@Injectable()
export class JwtStrategy extends PassportStrategy(JwtStrategyBase) {
  constructor(private readonly users: UsersService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      secretOrKey: JWT_SECRET,
      algorithms: ['HS256'],
      issuer: 'shop-api',
      ignoreExpiration: false,
    });
  }
  validate(payload: { sub: number }) {
    const user = this.users.findById(payload.sub);           // still exists? (deleted users lose access)
    if (!user) throw new UnauthorizedException();
    return { id: user.id, email: user.email, roles: user.roles };
  }
}
EOF
cat > src/auth/auth.ts <<'EOF'
import { Controller, ExecutionContext, Get, HttpCode, Injectable, Module, Post, Req, SetMetadata, UseGuards } from '@nestjs/common';
import { APP_GUARD, Reflector } from '@nestjs/core';
import { AuthGuard, PassportModule } from '@nestjs/passport';
import { JwtModule, JwtService } from '@nestjs/jwt';
import { UsersService } from './users.service.js';
import { JwtStrategy, JWT_SECRET, LocalStrategy } from './strategies.js';

export const Public = () => SetMetadata('isPublic', true);

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {             // global: every route needs a valid JWT...
  constructor(private readonly reflector: Reflector) { super(); }
  canActivate(ctx: ExecutionContext) {
    const isPublic = this.reflector.getAllAndOverride<boolean>('isPublic', [ctx.getHandler(), ctx.getClass()]);
    return isPublic ? true : super.canActivate(ctx);            // ...unless marked @Public()
  }
}

@Controller('auth')
export class AuthController {
  constructor(private readonly jwt: JwtService) {}

  @Public()
  @UseGuards(AuthGuard('local'))                                // runs LocalStrategy.validate first
  @Post('login')
  @HttpCode(200)
  login(@Req() req: { user: { id: number; email: string; roles: string[] } }) {
    const { id, email, roles } = req.user;
    return { accessToken: this.jwt.sign({ sub: id, email, roles }), tokenType: 'Bearer', expiresIn: 900 };
  }

  @Get('me')
  me(@Req() req: { user: unknown }) {
    return req.user;
  }
}

@Module({
  imports: [
    PassportModule,
    JwtModule.register({
      secret: JWT_SECRET,
      signOptions: { expiresIn: Number(process.env.JWT_TTL_SECONDS ?? 900), issuer: 'shop-api', algorithm: 'HS256' },
    }),
  ],
  controllers: [AuthController],
  providers: [UsersService, LocalStrategy, JwtStrategy, { provide: APP_GUARD, useClass: JwtAuthGuard }],
})
export class AuthModule {}
EOF

<Happened>
<Tr>
<En>

- A **wrong password** and an **unknown email** got the **same** 401 message, and both paths ran a bcrypt comparison (`DUMMY_HASH`), so attackers can't discover which emails have accounts from the message or the response time.
- The login route is `@Public()` (otherwise the global JWT guard would demand a token to get a token) and uses `AuthGuard('local')`, which called `LocalStrategy.validate` with the body's `email` and `password` (`usernameField: 'email'`). Its return value arrived as `req.user`.
- The token's **payload** is readable by anyone (base64url): `sub`, `email`, `roles`, `iat`, `exp` (exactly 900 s later) and `iss`. It's **signed**, not encrypted, so never put secrets in it.
- `/auth/me` with the token returned the user built by `JwtStrategy.validate`. Reloading the user there means a **deleted** user loses access immediately, and their current roles are used; the cost is one lookup per request (cache it if needed).
- Without a token, `/auth/me` **and** the default `/` route got 401: the guard is global, so even the generated `AppController` is protected now. That's the safe default.
- The **tampered** token (`sub` changed from 1 to 2 to impersonate Liam) failed signature verification: 401. The secret must be long, random, and come from configuration, never the fallback string used here for the demo.

</En>
<Ur>

- **Ghalat password** aur **na maloom email** ko **ek jaisa** 401 paighaam mila, aur dono raaston par bcrypt comparison chala (`DUMMY_HASH`), isliye hamla awar paighaam ya jawab ke waqt se nahi jaan sakte ke kin emails ke accounts hain.
- Login route `@Public()` hai (warna global JWT guard token lene ke liye bhi token maangta) aur `AuthGuard('local')` istemal karta hai, jis ne body ke `email` aur `password` (`usernameField: 'email'`) ke saath `LocalStrategy.validate` bulaya. Us ki wapas value `req.user` ban kar aayi.
- Token ka **payload** har koi parh sakta hai (base64url): `sub`, `email`, `roles`, `iat`, `exp` (bilkul 900 s baad) aur `iss`. Ye **signed** hai, encrypted nahi, isliye is me kabhi raaz na rakhein.
- Token ke saath `/auth/me` ne `JwtStrategy.validate` ka banaya user wapas kiya. Wahan user dobara load karne ka matlab hai ke **mitaya gaya** user foran rasai kho deta hai, aur us ke maujooda roles istemal hote hain; qeemat har request par ek lookup hai (zaroorat ho to cache karein).
- Token ke baghair `/auth/me` **aur** default `/` route ko 401 mila: guard global hai, isliye bana hua `AppController` bhi ab mehfooz hai. Yahi mehfooz default hai.
- **Chheda hua** token (Liam banne ke liye `sub` 1 se 2 kiya) signature tasdeeq me fail hua: 401. Secret lamba, random aur configuration se aana chahiye, kabhi wo fallback string nahi jo yahan demo ke liye istemal hui.

</Ur>

<Happened>
<Tr>
<En>

- The fresh token worked; two seconds later the **same** token was rejected with 401, because `passport-jwt` checks `exp` (we set `ignoreExpiration: false` explicitly; never set it to `true` in production).
- Short lifetimes limit the damage of a stolen token: there's no session to delete, so expiry is your main revocation tool.
- To keep users logged in, issue a **refresh token** at login (long-lived, stored hashed in the database, sent only to `/auth/refresh`, rotated on each use) and exchange it for new access tokens. Logging out deletes the refresh token.
- Clients should handle 401 by trying one refresh, then sending the user to the login screen.

</En>
<Ur>

- Taaza token chala; do second baad **wahi** token 401 ke saath radd hua, kyun ke `passport-jwt` `exp` check karta hai (humne `ignoreExpiration: false` wazeh tor par set kiya; production me ise kabhi `true` na karein).
- Kam muddat chori hue token ka nuqsan mehdood karti hai: mitane ko koi session nahi, isliye expiry wapsi ka aap ka sab se bara auzaar hai.
- Users ko login rakhne ke liye login par **refresh token** dein (lambi muddat, database me hash kar ke rakha, sirf `/auth/refresh` ko bheja jaye, har istemal par rotate) aur ise naye access tokens se badlein. Logout refresh token mita deta hai.
- Clients 401 par ek dafa refresh aazmayen, phir user ko login screen par bhejein.

</Ur>

## Common mistakes

<Compare>
<Bad title="Different errors and plain-text comparison">

```text
const user = await this.users.findByEmail(email);
if (!user) throw new NotFoundException('No account with this email');     // reveals accounts
if (user.password !== password) throw new UnauthorizedException('Wrong password');   // plain-text passwords!
```

</Bad>
<Good title="Hash, compare, one message">

```text
const ok = await bcrypt.compare(password, user?.passwordHash ?? DUMMY_HASH);
if (!user || !ok) throw new UnauthorizedException('Invalid email or password');
```

</Good>
</Compare>

<Compare>
<Bad title="Weak JWT configuration">

```text
JwtModule.register({ secret: 'secret', signOptions: { expiresIn: '30d' } })   // guessable secret, month-long tokens
super({ jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(), secretOrKey: 'secret', ignoreExpiration: true })
```

</Bad>
<Good title="Strong secret from config, short tokens, pinned algorithm">

```text
JwtModule.registerAsync({
  inject: [ConfigService],
  useFactory: (cfg: ConfigService) => ({
    secret: cfg.getOrThrow('JWT_SECRET'),                       // 32+ random bytes, never in Git
    signOptions: { expiresIn: 900, issuer: 'shop-api', algorithm: 'HS256' },
  }),
})
// strategy: algorithms: ['HS256'], issuer: 'shop-api', ignoreExpiration: false
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Putting sensitive data in the payload** (password hashes, addresses, internal flags): anyone can decode it.
- **Trusting roles in old tokens forever**: reload the user in `validate()` or keep tokens short so role changes apply quickly.
- **Forgetting `@Public()` on login and sign-up** after making the guard global (you can't log in) or, worse, making whole controllers public by accident.
- **Storing tokens in `localStorage`** in browser apps: prefer HttpOnly cookies.
- **No rate limiting on `/auth/login`**: add `@nestjs/throttler` with a strict limit.
- **Logging the `Authorization` header** or the token response.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Payload me hassas data rakhna** (password hashes, pate, andaruni flags): koi bhi ise decode kar sakta hai.
- **Purane tokens ke roles par hamesha bharosa**: `validate()` me user dobara load karein ya tokens chhote rakhein taa ke role ki tabdeeliyan jaldi lagu hon.
- Guard global karne ke baad **login aur sign-up par `@Public()` bhoolna** (aap login nahi kar sakte) ya, bura, ghalti se poore controllers public kar dena.
- Browser apps me **tokens `localStorage` me rakhna**: HttpOnly cookies behtar hain.
- **`/auth/login` par rate limiting nahi**: sakht hadd ke saath `@nestjs/throttler` jorein.
- **`Authorization` header ya token wala response log karna**.

</Ur>
</Tr>

<Challenge title="Add sign-up">

<Tr>
<En>
Add `POST /auth/signup` (public) with a DTO (`email`, `password` with at least 12 characters). Hash the password with bcrypt (cost 12), reject duplicate emails with 409, store the user, and return a token like login does. What should the response be for a duplicate email, and why might some apps answer 201 anyway?
</En>
<Ur>
`POST /auth/signup` (public) DTO ke saath jorein (`email`, kam az kam 12 huroof wala `password`). Password bcrypt (cost 12) se hash karein, dohraye emails 409 ke saath radd karein, user rakhein, aur login ki tarah token wapas karein. Dohraye email par jawab kya ho, aur kuch apps phir bhi 201 kyun de sakti hain?
</Ur>
</Tr>

<Solution>

```text
export class SignupDto {
  @IsEmail() @Transform(({ value }) => String(value).trim().toLowerCase()) email: string;
  @IsString() @MinLength(12) @MaxLength(128) password: string;
}

@Public()
@Post('signup')
async signup(@Body() dto: SignupDto) {
  if (this.users.findByEmail(dto.email)) throw new ConflictException('Email already registered');
  const user = this.users.create({ email: dto.email, roles: ['customer'], passwordHash: await bcrypt.hash(dto.password, 12) });
  return { accessToken: this.jwt.sign({ sub: user.id, email: user.email, roles: user.roles }), tokenType: 'Bearer' };
}
```

<Tr>
<En>
409 is honest and convenient, but it tells anyone which emails are registered (account enumeration). Privacy-sensitive apps instead always answer "Check your inbox to confirm your email": a new user gets a confirmation link, an existing user gets an email saying "someone tried to sign up with your address". Either way, rely on a unique index in the database, not only the check in code, to prevent duplicates under concurrent requests.
</En>
<Ur>
409 imandar aur aasan hai, magar ye har kisi ko batata hai ke kaun se emails registered hain (account enumeration). Privacy ka khayal rakhne wali apps is ke bajaye hamesha kehti hain "Apna email confirm karne ke liye inbox check karein": naye user ko confirmation link milta hai, maujooda user ko email milti hai ke "kisi ne aap ke pate se sign up ki koshish ki". Dono soorton me saath chalti requests me dohraye records rokne ke liye sirf code ke check par nahi, database ke unique index par bharosa karein.
</Ur>

<Tr>
<En>
Your React app runs on the same site as the API. Change the setup so the access token is set as an HttpOnly cookie at login and read from that cookie by `JwtStrategy`. What else must you add once authentication relies on cookies?
</En>
<Ur>
Aap ki React app API wali site par hi chalti hai. Setup badlein taa ke login par access token HttpOnly cookie ki tarah set ho aur `JwtStrategy` use usi cookie se parhe. Authentication cookies par munhasir hone ke baad aur kya jorna hoga?

<Solution>

```text
// login: set the cookie instead of returning the token
login(@Req() req, @Res({ passthrough: true }) res: Response) {
  const token = this.jwt.sign({ sub: req.user.id, roles: req.user.roles });
  res.cookie('access_token', token, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 15 * 60 * 1000, path: '/' });
  return { loggedIn: true };
}

// strategy: read from the cookie (needs cookie-parser), fall back to the header for non-browser clients
jwtFromRequest: ExtractJwt.fromExtractors([
  (req) => req?.cookies?.access_token ?? null,
  ExtractJwt.fromAuthHeaderAsBearerToken(),
]),
```

</En>

<DeepDive title="More about Passport and JWT in Nest">

**Without Passport.** The Nest docs also show a plain `AuthGuard` that calls `JwtService.verifyAsync()` directly; fewer dependencies, same result for JWT-only APIs.

**Multiple strategies.** `AuthGuard(['jwt', 'api-key'])` tries strategies in order, for example user tokens and machine API keys on the same routes.

**Refresh strategy.** A separate `JwtStrategy` named `'jwt-refresh'` with its own secret, reading the refresh cookie, protects only `/auth/refresh`.

**OAuth.** `passport-google-oauth20` with `AuthGuard('google')` on `/auth/google` and its callback; on success, find or create the user and issue your own tokens.

**Asymmetric keys.** Sign with a private key (RS256/ES256) and let other services verify with the public key, often published via JWKS (`passport-jwt` with `jwks-rsa`).

**Token revocation.** Store a `tokenVersion` on the user and in the token; increment it on password change or "log out everywhere", and compare it in `validate()`.

</DeepDive>

<DeepDive title="Real world: the JWT secret in the GitHub repository">

A startup's NestJS API used `JwtModule.register({ secret: process.env.JWT_SECRET || 'super-secret-key' })`. In production the environment variable was set correctly. But in a staging environment created hastily for a partner demo, the variable was missing, so staging silently used `'super-secret-key'`, which was also visible in the public GitHub repository of an open-source SDK the company had published.

Staging used a copy of production data (anonymised, mostly). A researcher found the fallback string in the repository, signed a token with `"sub": 1, "roles": ["admin"]` and used it against the staging API, gaining admin access. Because `validate()` only decoded the payload without loading the user, any `sub` and any role were accepted.

The fixes:

1. The fallback was removed; `ConfigService.getOrThrow('JWT_SECRET')` with a startup check for length (at least 32 bytes) made a missing secret crash the app instead of weakening it.
2. Each environment got its own random secret from the secrets manager, rotated every quarter.
3. `JwtStrategy.validate()` loaded the user and used roles from the database, not from the token.
4. Staging got synthetic data instead of production copies.
5. A secret scanner (gitleaks) ran in CI for all repositories.

The pattern `process.env.X || 'default'` is convenient for ports; for secrets, it's a vulnerability waiting for a misconfigured environment.

</DeepDive>

<DeepDive title="Security lens">

- **Secrets**: long, random, per environment, from a secrets manager; no fallbacks in code.
- **Passwords**: bcrypt or argon2 with a sensible cost; never log or return them.
- **Tokens**: short expiry, pinned algorithm, issuer/audience checks; refresh tokens rotated and stored hashed.
- **Login endpoint**: rate limiting, same error for all failures, monitoring for credential stuffing, optional MFA.
- **Revocation**: reload users or check a token version; delete refresh tokens on logout and password change.
- **Transport**: HTTPS only; HttpOnly, Secure, SameSite cookies for browsers.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does authentication with Passport work in NestJS?">
You create strategy classes by extending PassportStrategy with a Passport strategy such as passport-local or passport-jwt and implement validate, whose return value becomes request.user. AuthGuard with the strategy name applies it as a guard on routes or globally.
</QA>

<QA q="Describe a JWT login flow.">
The client posts credentials; a local strategy verifies the password hash; the server signs a short-lived JWT with the user ID and roles and returns it. The client sends it as a bearer token, and a JWT guard verifies the signature, issuer and expiry and loads the user for each request. Refresh tokens extend sessions.
</QA>

<QA q="What's the difference between authentication and authorisation in Nest?">
Authentication establishes who the user is, typically with Passport strategies and the JWT guard setting request.user; authorisation decides what they may do, with roles guards, policies and ownership checks in services.
</QA>

<QA q="How do you prevent user enumeration at login?">
Return the same error message and status for unknown emails and wrong passwords, and perform a password hash comparison even when the user doesn't exist so response times are similar, plus rate limiting.
</QA>

<QA q="How can you revoke JWTs before they expire?">
Keep access tokens short-lived and revoke refresh tokens server-side; for immediate revocation, store a token version or denylist of token IDs and check it in the JWT strategy's validate method.
</QA>

</DeepDive>
