<BigIdea>
<Tr>
<En>
Every Nest app already has an **exception layer**: when something throws and nobody catches it, Nest turns it into a response. If the error is an **`HttpException`** (`NotFoundException`, `BadRequestException`, …), the client gets its status and message. **Anything else** (a `TypeError`, a database error) becomes `{"statusCode":500,"message":"Internal server error"}`, which is safe but unhelpful: a duplicate-key error should be a **409**, and clients can't correlate a 500 with your logs. **Exception filters** let you take over. A filter is a class marked **`@Catch(...)`** with a `catch(exception, host)` method that writes the response. `@Catch()` with no arguments catches **everything**; `@Catch(SomeError)` catches only that type. Registered globally with **`APP_FILTER`**, one filter can give **every** error the same JSON shape, attach a **request ID**, keep validation details, translate library errors (Prisma's `P2002` → 409) and log unexpected errors while hiding their details. Narrower filters on a controller handle **domain errors**, so services can throw meaningful errors like `InsufficientStockError` without knowing anything about HTTP.
</En>
<Ur>
Har Nest app ke paas pehle se ek **exception layer** hai: jab kuch throw ho aur koi na pakre, Nest use response bana deta hai. Agar error **`HttpException`** hai (`NotFoundException`, `BadRequestException`, …), client ko us ka status aur paighaam milta hai. **Baqi sab** (`TypeError`, database error) `{"statusCode":500,"message":"Internal server error"}` ban jata hai, jo mehfooz magar bekaar hai: duplicate-key error **409** hona chahiye, aur clients 500 ko aap ke logs se nahi jor sakte. **Exception filters** aap ko ikhtiyar dete hain. Filter **`@Catch(...)`** wali class hai jis ka `catch(exception, host)` method response likhta hai. Bina arguments ke `@Catch()` **sab kuch** pakarta hai; `@Catch(SomeError)` sirf wahi qism. **`APP_FILTER`** se globally register ho kar ek filter **har** error ko ek jaisi JSON shakal de sakta hai, **request ID** jor sakta hai, validation ki tafseel rakh sakta hai, library errors ka tarjuma kar sakta hai (Prisma ka `P2002` → 409) aur ghair mutawaqqa errors ko unki tafseel chhupa kar log kar sakta hai. Controller par tang filters **domain errors** sambhalte hain, isliye services `InsufficientStockError` jaise ba-maani errors throw kar sakti hain, HTTP ke baare me kuch jane baghair.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of an **airline's customer service desk** that handles every problem on a trip.

- Without it, each department talks to passengers its own way: the gate says "Flight cancelled", the baggage office hands over a technical incident report, and the kitchen just says "error". (Nest's defaults, plus raw errors.)
- With a **central desk** (global filter), every problem comes back in the **same format**: a short code, a clear sentence, and a **case number** (request ID) the passenger can quote later.
- Internal details ("hydraulic pump P2002 failed on aircraft 7") go into the **engineering log**, not to the passenger, who hears "your flight is delayed for a technical reason".
- Some problems have their own **specialist counter**: "overbooked" is handled by the rebooking desk with seat options (a targeted filter for a domain error).

</En>
<Ur>

Safar ke har masle ko sambhalne wale **airline ke customer service desk** ka sochein.

- Is ke baghair har department musafiron se apne tareeqe se baat karta hai: gate kehta hai "Flight cancelled", baggage office takneeki waqia ki report thama deta hai, aur kitchen bas "error" kehta hai. (Nest ke defaults, plus kache errors.)
- **Markazi desk** (global filter) ke saath har masla **ek hi format** me wapas aata hai: chhota code, wazeh jumla, aur **case number** (request ID) jo musafir baad me bata sake.
- Andaruni tafseel ("aircraft 7 par hydraulic pump P2002 fail") **engineering log** me jati hai, musafir ko nahi, jo sunta hai "takneeki wajah se flight der se hai".
- Kuch maslon ka apna **mahir counter** hai: "overbooked" ko rebooking desk seat ke options ke saath sambhalta hai (domain error ke liye mukhsoos filter).

<Step title="One global catch-all filter">

<Tr>
<En>
`AllExceptionsFilter` uses `@Catch()` to catch everything, maps each kind of error to a status and a body, adds the request ID (from `X-Request-Id` or a new UUID), logs 5xx errors, and replies through `HttpAdapterHost`. It's registered with `APP_FILTER` so it gets dependency injection.
</En>
<Ur>
`AllExceptionsFilter` sab kuch pakarne ke liye `@Catch()` istemal karta hai, har qism ke error ko status aur body se milata hai, request ID jorta hai (`X-Request-Id` se ya naya UUID), 5xx errors log karta hai, aur `HttpAdapterHost` ke zariye jawab deta hai. Ise `APP_FILTER` se register kiya gaya hai taa ke dependency injection mile.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/all-exceptions.filter.ts <<'EOF'
import { ArgumentsHost, Catch, ExceptionFilter, HttpException, HttpStatus, Logger } from '@nestjs/common';
import { HttpAdapterHost } from '@nestjs/core';
import { randomUUID } from 'node:crypto';

type ErrorBody = { code: string; message: string; details?: unknown };

@Catch()                                                    // no argument: catch EVERYTHING
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger('Errors');
  constructor(private readonly adapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost) {
    const { httpAdapter } = this.adapterHost;
    const ctx = host.switchToHttp();
    const req = ctx.getRequest();
    const requestId = (req.headers['x-request-id'] as string) ?? randomUUID();
    const [status, body] = this.toResponse(exception);

    if (status >= 500) {
      const err = exception as Error;
      this.logger.error(`[${requestId}] ${req.method} ${req.url} ${err?.name}: ${err?.message}`);
    }
    httpAdapter.reply(ctx.getResponse(), { error: { ...body, requestId } }, status);
  }

  private toResponse(e: unknown): [number, ErrorBody] {
    if (e instanceof HttpException) {
      const res = e.getResponse() as string | { message?: string | string[] };
      const msg = typeof res === 'string' ? res : res.message;
      const status = e.getStatus();
      return Array.isArray(msg)
        ? [status, { code: 'validation_failed', message: 'Invalid input', details: msg }]
        : [status, { code: HttpStatus[status]?.toLowerCase() ?? 'error', message: msg ?? e.message }];
    }
    if ((e as { code?: string })?.code === 'P2002') {        // Prisma unique constraint
      return [409, { code: 'conflict', message: 'This resource already exists' }];
    }
    return [500, { code: 'internal_error', message: 'Something went wrong' }];   // never leak details
  }
}
EOF
cat > src/app.module.ts <<'EOF'
import { Module } from '@nestjs/common';
import { APP_FILTER } from '@nestjs/core';
import { AppController } from './app.controller.js';
import { AppService } from './app.service.js';
import { OrdersController } from './orders.controller.js';
import { AllExceptionsFilter } from './all-exceptions.filter.js';

@Module({
  controllers: [AppController, OrdersController],
  providers: [AppService, { provide: APP_FILTER, useClass: AllExceptionsFilter }],   // global, with DI
})
export class AppModule {}
EOF
```

<Happened>
<Tr>
<En>

- **Every** response now has the same shape: `{ error: { code, message, details?, requestId } }`. Clients check `error.code` (`not_found`, `validation_failed`, `conflict`, `internal_error`) instead of parsing messages.
- Validation messages moved into `details`, so `message` is always a string.
- The Prisma `P2002` error became **409 conflict** with a safe message; the original text (with the column name) was not sent.
- The bug became **500 internal_error** with "Something went wrong", and the **log line** contains the same `req-42`, the route and the real error. When a user reports `req-42`, you find the cause in seconds.
- Even the unknown route's 404 uses the new shape, because Nest's router throws a `NotFoundException` that the filter catches.
- 4xx errors aren't logged as errors: they're the client's mistakes, and logging them at error level would hide real problems. In a real app, use the request ID from your logging middleware (Logging lesson) so logs and error responses share it.

</En>
<Ur>

- **Har** response ki ab ek hi shakal hai: `{ error: { code, message, details?, requestId } }`. Clients paighaam parse karne ke bajaye `error.code` (`not_found`, `validation_failed`, `conflict`, `internal_error`) check karte hain.
- Validation paighaam `details` me chale gaye, isliye `message` hamesha string hai.
- Prisma `P2002` error mehfooz paighaam ke saath **409 conflict** bana; asal text (column ke naam ke saath) nahi bheja gaya.

- Na maloom route ka 404 bhi nayi shakal me hai, kyun ke Nest ka router `NotFoundException` throw karta hai jise filter pakar leta hai.
- 4xx errors error ki tarah log nahi hote: ye client ki ghaltiyan hain, aur unhen error level par log karna asli maslon ko chhupa deta. Asli app me apne logging middleware (Logging lesson) ki request ID istemal karein taa ke logs aur error responses use share karein.

</Ur>

<Step title="A targeted filter for a domain error">

<Tr>
<En>
The service throws `InsufficientStockError`, a plain class with no HTTP knowledge. `InsufficientStockFilter` catches only that type and answers **422** with the available quantity. It's applied to the controller with `@UseFilters`.
</En>
<Ur>
Service `InsufficientStockError` throw karti hai, HTTP ke ilm ke baghair saadi class. `InsufficientStockFilter` sirf yahi qism pakarta hai aur dastyab miqdar ke saath **422** deta hai. Ise `@UseFilters` se controller par lagaya gaya hai.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/stock.ts <<'EOF'
import { ArgumentsHost, Catch, Controller, ExceptionFilter, Param, ParseIntPipe, Post, UseFilters } from '@nestjs/common';
import type { Response } from 'express';

// A domain error: the service knows nothing about HTTP
export class InsufficientStockError extends Error {
  constructor(readonly productId: number, readonly available: number) {
    super(`Only ${available} left for product ${productId}`);
  }
}

@Catch(InsufficientStockError)                           // only this error type
export class InsufficientStockFilter implements ExceptionFilter {
  catch(e: InsufficientStockError, host: ArgumentsHost) {
    host.switchToHttp().getResponse<Response>().status(422).json({
      error: { code: 'insufficient_stock', message: e.message, details: { productId: e.productId, available: e.available } },
    });
  }
}

@Controller('stock')
@UseFilters(InsufficientStockFilter)                     // closer than the global filter, so it wins
export class StockController {
  @Post(':productId/reserve/:qty')
  reserve(@Param('productId', ParseIntPipe) productId: number, @Param('qty', ParseIntPipe) qty: number) {
    const available = 3;
    if (qty > available) throw new InsufficientStockError(productId, available);
    return { reserved: qty };
  }
}
EOF
```

## Common mistakes

<Compare>
<Bad title="Returning exception details to the client">

```text
@Catch()
export class LeakyFilter implements ExceptionFilter {
  catch(e: any, host: ArgumentsHost) {
    host.switchToHttp().getResponse().status(500).json({ message: e.message, stack: e.stack, sql: e.query });
  }
}
```

</Bad>
<Good title="Safe message out, details in the logs">

```text
if (status >= 500) this.logger.error(`[${requestId}] ${err.name}: ${err.message}`, err.stack);
reply({ error: { code: 'internal_error', message: 'Something went wrong', requestId } }, 500);
```

</Good>
</Compare>

<Compare>
<Bad title="HTTP exceptions deep in domain code">

```text
// inventory.service.ts, also used by a queue worker and a CLI
if (qty > available) throw new UnprocessableEntityException('Not enough stock');   // HTTP concept in the domain
```

</Bad>
<Good title="Domain errors + a filter at the edge">

```text
if (qty > available) throw new InsufficientStockError(productId, available);
// HTTP: @Catch(InsufficientStockError) → 422; queue worker: retry or dead-letter; CLI: print a message
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Registering a global filter with `app.useGlobalFilters(new X())`** when it needs injected services: no DI; use `APP_FILTER`.
- **Catching everything in a filter but forgetting `HttpException`s**: every 404 becomes a 500.
- **Logging 4xx at error level**: alert fatigue.
- **Different error shapes in different modules**: one global filter, a documented format.
- **Swallowing errors in try/catch inside handlers** just to return a custom shape: throw and let the filter format it.
- **Forgetting non-HTTP contexts**: in WebSocket or microservice handlers, `switchToHttp()` doesn't apply; check `host.getType()`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Jab filter ko inject hui services chahiyen to **`app.useGlobalFilters(new X())` se register karna**: DI nahi; `APP_FILTER` lein.
- **Filter me sab kuch pakarna magar `HttpException`s bhoolna**: har 404 500 ban jata hai.
- **4xx ko error level par log karna**: alerts ki thakan.
- **Mukhtalif modules me mukhtalif error shaklein**: ek global filter, documented format.
- Sirf apni shakal wapas karne ke liye **handlers ke andar try/catch me errors nigalna**: throw karein aur filter ko format karne dein.
- **Non-HTTP contexts bhoolna**: WebSocket ya microservice handlers me `switchToHttp()` lagu nahi; `host.getType()` check karein.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Problem Details format">

<Tr>
<En>
Change the global filter to answer with RFC 9457 Problem Details: `Content-Type: application/problem+json` and a body like `{ "type": "https://example.com/problems/not-found", "title": "Not Found", "status": 404, "detail": "Order 7 not found", "instance": "/orders/7", "requestId": "req-42" }`. How would you include validation errors?
</En>
<Ur>
Global filter badlein taa ke RFC 9457 Problem Details ke saath jawab de: `Content-Type: application/problem+json` aur `{ "type": "https://example.com/problems/not-found", "title": "Not Found", "status": 404, "detail": "Order 7 not found", "instance": "/orders/7", "requestId": "req-42" }` jaisi body. Validation errors kaise shamil karenge?
</Ur>
</Tr>

<Solution>

```text
catch(exception: unknown, host: ArgumentsHost) {
  const ctx = host.switchToHttp();
  const req = ctx.getRequest();
  const res = ctx.getResponse();
  const [status, body] = this.toResponse(exception);           // same mapping as before
  const problem = {
    type: `https://example.com/problems/${body.code.replaceAll('_', '-')}`,
    title: HttpStatus[status]?.replaceAll('_', ' ') ?? 'Error',
    status,
    detail: body.message,
    instance: req.url,
    requestId: req.headers['x-request-id'] ?? randomUUID(),
    ...(body.details ? { errors: body.details } : {}),          // extension member for validation errors
  };
  this.adapterHost.httpAdapter.setHeader(res, 'Content-Type', 'application/problem+json');
  this.adapterHost.httpAdapter.reply(res, problem, status);
}
```

<Tr>
<En>
RFC 9457 allows **extension members**, so validation errors go in a field such as `errors` (an array of `{ field, message }` objects is friendlier than raw strings). The `type` URI should point to documentation explaining the problem; clients treat it as the stable identifier.
</En>
<Ur>
RFC 9457 **extension members** ki ijazat deta hai, isliye validation errors `errors` jaise field me jate hain (`{ field, message }` objects ki array kache strings se zyada dostana hai). `type` URI masle ki wazahat wali documentation ki taraf ishara kare; clients ise mustahkam pehchan samajhte hain.
</Ur>
</Tr>

</Solution>

<Challenge title="Map a family of database errors">

<Tr>
<En>
Extend `toResponse` for PostgreSQL errors thrown by `pg`: `23505` unique violation → 409, `23503` foreign key violation → 409 (or 422), `23502` not-null violation → 400, `57014` query cancelled (statement timeout) → 503. Why should none of these send the original message?
</En>
<Ur>
`pg` ke throw kiye PostgreSQL errors ke liye `toResponse` barhayen: `23505` unique violation → 409, `23503` foreign key violation → 409 (ya 422), `23502` not-null violation → 400, `57014` query cancelled (statement timeout) → 503. In me se koi asal paighaam kyun na bheje?
</Ur>
</Tr>

<Solution>

```text
const PG: Record<string, [number, string, string]> = {
  '23505': [409, 'conflict', 'This resource already exists'],
  '23503': [409, 'reference_conflict', 'A related resource is missing or still in use'],
  '23502': [400, 'missing_field', 'A required field is missing'],
  '57014': [503, 'timeout', 'The request took too long, please try again'],
};
const code = (e as { code?: string })?.code;
if (code && PG[code]) { const [s, c, m] = PG[code]; return [s, { code: c, message: m }]; }
```

<Tr>
<En>
PostgreSQL messages contain table, column, constraint and sometimes value names (`Key (email)=(emma@example.com) already exists`), which reveal your schema and possibly other users' data. Log them with the request ID; send a generic message. Better still, catch expected cases (like duplicate emails) in the service and throw a specific domain error with a user-friendly message.
</En>
<Ur>
PostgreSQL paighaamon me table, column, constraint aur kabhi values ke naam hote hain (`Key (email)=(emma@example.com) already exists`), jo aap ka schema aur shayad doosre users ka data zahir karte hain. Unhen request ID ke saath log karein; aam paighaam bhejein. Is se bhi behtar, mutawaqqa soorten (jaise dohraye emails) service me pakar kar user dost paighaam wala mukhsoos domain error throw karein.
</Ur>

<DeepDive title="More about exception filters">

**Extending `BaseExceptionFilter`.** `class X extends BaseExceptionFilter { catch(e, host) { /* log */ super.catch(e, host); } }` adds behaviour while keeping Nest's default responses.

**Error tracking.** Call Sentry (`@sentry/nestjs`) or another tracker from the filter for 5xx errors, with the request ID as a tag.

**Exceptions with causes.** `new ServiceUnavailableException('Payments down', { cause: err, description: '…' })` keeps the original error for logs.

**Microservices and WebSockets.** `RpcException` and `WsException` with `BaseRpcExceptionFilter` / `BaseWsExceptionFilter`; one filter can branch on `host.getType()`.

**Translations.** Filters can localise messages using the `Accept-Language` header and stable error codes.

**Testing filters.** Instantiate the filter with a fake `HttpAdapterHost` and a mocked `ArgumentsHost`, or test through e2e requests with supertest.

</DeepDive>

<DeepDive title="Real world: the mobile app that parsed error messages">

A food delivery company's mobile app needed to show different screens for different errors: "restaurant closed", "address outside delivery area", "item sold out". The NestJS API threw `BadRequestException('Restaurant is closed')`, `BadRequestException('Address not in delivery zone')` and so on. The app decided what to show by **matching the message text**.

It worked until a product manager asked for friendlier wording. A backend developer changed "Restaurant is closed" to "This restaurant is closed right now. Try again later!". The mobile app, which compared strings exactly, fell back to a generic error dialog for every closed restaurant, and support tickets doubled over a weekend. Fixing it needed an app store release, which took days.

The redesign:

1. Domain errors (`RestaurantClosedError`, `OutsideDeliveryZoneError`, `ItemSoldOutError`) were thrown by services.
2. A global filter turned them into `{ error: { code: "restaurant_closed", message, details } }` with codes documented in the API reference and treated as part of the contract.
3. The app switched on `error.code` and only displayed `message`; wording could change freely.
4. A contract test listed all error codes; removing or renaming one failed CI.

Messages are for humans and can change; codes are for programs and must not.

</DeepDive>

<DeepDive title="Security lens">

- **Never expose stack traces, SQL, file paths, internal IPs** or library versions in responses.
- **Generic messages for authentication failures** to avoid account enumeration.
- **Prefer 404 over 403** for resources the user shouldn't know exist.
- **Log enough to investigate** (request ID, route, user ID, error) but redact secrets and personal data.
- **Rate-limit or alert on bursts of 4xx/5xx**: they can indicate scanning or attacks.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is an exception filter in NestJS?">
A class decorated with @Catch that implements ExceptionFilter and handles exceptions thrown during request processing, building the response to send to the client.
</QA>

<QA q="How does Nest handle exceptions without custom filters?">
Its built-in exception layer turns HttpException instances into responses with their status and message, and turns any other error into a 500 Internal server error response while logging it.
</QA>

<QA q="How do you create a consistent error format across the app?">
Write a global filter with @Catch() registered via APP_FILTER that maps HttpExceptions, validation errors, known library errors and unknown errors to one response shape with stable error codes and a request ID, logging server errors.
</QA>

<QA q="What's the difference between exception filters and interceptors for error handling?">
Filters handle any uncaught exception from any layer and produce the final response; interceptors can catch errors from the handler with catchError and transform or rethrow them, usually for specific routes or dependencies.
</QA>

<QA q="Why use domain errors instead of HttpExceptions in services?">
Services stay independent of HTTP, so they can be reused from queues, CLIs or other transports, while filters translate domain errors into the right HTTP status at the edge.
</QA>

</DeepDive>
