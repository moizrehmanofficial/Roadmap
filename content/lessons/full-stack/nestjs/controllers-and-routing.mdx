<BigIdea>
<Tr>
<En>
A **controller** is a class whose methods handle HTTP requests. Instead of `router.get("/products/:id", handler)`, you write `@Controller('products')` on the class and `@Get(':id')` on a method; Nest combines them into `GET /products/:id` at startup. Inputs come in through **parameter decorators**: `@Param('id')` for path parameters, `@Query('page')` for the query string, `@Body()` for the parsed JSON body, `@Headers('user-agent')` and `@Ip()` for request details. **Pipes** attached to a parameter convert and check it (`ParseIntPipe`, `DefaultValuePipe`), so the method receives a real number or never runs. The method **returns** a value and Nest sends it as JSON with **200** (or **201** for `@Post`); decorators like `@HttpCode(204)`, `@Header()` and `@Redirect()` change the response. App-wide, `setGlobalPrefix('api')` and **versioning** (`/api/v1`, `/api/v2`) organise URLs. Two things work just like Express: **route order matters** (`:id` declared before `today` swallows it), and if you need the raw response for cookies, use `@Res({ passthrough: true })` so Nest still handles the rest.
</En>
<Ur>
**Controller** aisi class hai jis ke methods HTTP requests sambhalte hain. `router.get("/products/:id", handler)` ke bajaye aap class par `@Controller('products')` aur method par `@Get(':id')` likhte hain; Nest startup par dono ko jor kar `GET /products/:id` banata hai. Inputs **parameter decorators** se aate hain: path parameters ke liye `@Param('id')`, query string ke liye `@Query('page')`, parse hui JSON body ke liye `@Body()`, request ki tafseel ke liye `@Headers('user-agent')` aur `@Ip()`. Parameter par lage **pipes** use convert aur check karte hain (`ParseIntPipe`, `DefaultValuePipe`), isliye method ko asli number milta hai ya wo chalta hi nahi. Method value **return** karta hai aur Nest use **200** (ya `@Post` ke liye **201**) ke saath JSON me bhejta hai; `@HttpCode(204)`, `@Header()` aur `@Redirect()` jaise decorators response badalte hain. Poori app me `setGlobalPrefix('api')` aur **versioning** (`/api/v1`, `/api/v2`) URLs munazzam karte hain. Do cheezen bilkul Express jaisi hain: **routes ki tarteeb ahem hai** (`today` se pehle bayan hua `:id` use nigal leta hai), aur cookies ke liye kacha response chahiye to `@Res({ passthrough: true })` lein taa ke baqi kaam Nest hi kare.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- Routes, inputs and response details are **declared next to the method**, so one glance shows the whole endpoint.
- Pipes on parameters remove manual `Number(...)`/`isNaN` checks and guarantee types inside the method.
- Returning values (instead of calling `res.json`) lets interceptors, serialisation and exception filters work on every route.
- Prefixes and versioning let you evolve an API without breaking existing clients.

</En>
<Ur>

- Routes, inputs aur response ki tafseel **method ke saath bayan** hoti hai, isliye ek nazar me poora endpoint dikhta hai.
- Parameters par pipes haath ke `Number(...)`/`isNaN` checks hata dete hain aur method ke andar types ki zamanat dete hain.
- Values return karna (`res.json` bulane ke bajaye) interceptors, serialisation aur exception filters ko har route par kaam karne deta hai.
- Prefixes aur versioning maujooda clients toray baghair API ko barhane dete hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Need | Use |
| --- | --- |
| Numeric ID in the path | `@Param('id', ParseIntPipe)` (or `ParseUUIDPipe` for UUIDs) |

| Whole JSON body | `@Body() dto: CreateProductDto` with validation (next lessons) |
| 204 after DELETE | `@HttpCode(HttpStatus.NO_CONTENT)` |
| Set a cookie or dynamic status | `@Res({ passthrough: true }) res` |
| Stream a file | `StreamableFile` return value (or full `@Res()`) |
| Breaking change for some clients | `@Version('2')` |

## Picture it

<Tr>
<En>

Think of a **hotel reception** with labelled windows.

- The sign above a group of windows is `@Controller('rooms')`; each window's label is a route (`GET :id`, `POST`, `DELETE :id`).
- Guests fill in **form fields**: room number (path), "late checkout? yes/no" (query), the booking form itself (body), their ID card (headers).
- A clerk **checks and converts** each field before passing it on (pipes): "room 'abc'? That's not a number, please fix it" (400).
- The window decides **how to answer**: a key card (200 + JSON), "booking created" (201), "checked out, nothing to return" (204), "this desk moved, go to window 3" (301).
- Windows are checked **in order**: if the "room number" window is first and accepts anything, the "today's deals" window behind it never gets visitors.

</En>
<Ur>

Labels wali khirkiyon ke saath **hotel reception** ka sochein.

- Khirkiyon ke group ke upar ka board `@Controller('rooms')` hai; har khirki ka label route hai (`GET :id`, `POST`, `DELETE :id`).
- Mehmaan **form ke khane** bharte hain: kamra number (path), "der se checkout? haan/nahi" (query), booking form khud (body), un ka ID card (headers).
- Clerk har khana aage dene se pehle **check aur convert** karta hai (pipes): "kamra 'abc'? Ye number nahi, theek karein" (400).
- Khirki tay karti hai ke **kaise jawab de**: key card (200 + JSON), "booking ban gayi" (201), "checkout ho gaya, dene ko kuch nahi" (204), "ye desk muntaqil ho gaya, khirki 3 par jayen" (301).
- Khirkiyan **tarteeb se** dekhi jati hain: agar "kamra number" wali khirki pehle ho aur sab qubool kare, to peechhe wali "aaj ki deals" khirki tak koi nahi pohanchta.

</Ur>
</Tr>

<Step title="A full CRUD controller">

<Tr>
<En>
One controller covers listing with paging and sorting, a static route, a redirect, a single item with a cache header, create, partial update and delete. We call every route and print the routes Nest mapped.
</En>
<Ur>
Ek controller paging aur sorting ke saath list, static route, redirect, cache header ke saath ek item, banana, juzvi update aur mitana cover karta hai. Hum har route bulate hain aur Nest ke map kiye routes print karte hain.
</Ur>
</Tr>

```bash
npx -y @nestjs/cli@12.0.13 new shop-api --package-manager npm --skip-git --strict > /dev/null 2>&1
cd shop-api
npx nest g controller products --flat --no-spec > /dev/null      # --flat: no products/ folder for this demo
cat > src/products.controller.ts <<'EOF'
import {
  Body, Controller, DefaultValuePipe, Delete, Get, Header, HttpCode, HttpStatus,
  Param, ParseIntPipe, Patch, Post, Query, Redirect,
} from '@nestjs/common';

type Product = { id: number; name: string; price: number };
const products: Product[] = [
  { id: 1, name: 'Travel Mug', price: 24 },
  { id: 2, name: 'Desk Lamp', price: 39 },
];

@Controller('products')
export class ProductsController {
  @Get()                                            // GET /products?page=1&limit=1&sort=price
  list(
    @Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number,
    @Query('limit', new DefaultValuePipe(10), ParseIntPipe) limit: number,
    @Query('sort') sort?: string,
  ) {
    const sorted = sort === 'price' ? [...products].sort((a, b) => a.price - b.price) : products;
    return { page, limit, items: sorted.slice((page - 1) * limit, page * limit) };
  }

  @Get('cheapest')                                  // static route: declared BEFORE ':id'
  cheapest() {
    return [...products].sort((a, b) => a.price - b.price)[0];
  }

  @Get('old-catalog')
  @Redirect('/products', 301)                       // permanent redirect
  oldCatalog() {}

  @Get(':id')
  @Header('Cache-Control', 'public, max-age=60')    // a fixed response header
  findOne(@Param('id', ParseIntPipe) id: number) {
    return products.find((p) => p.id === id) ?? null;
  }

  @Post()                                           // 201 by default
  create(@Body() body: Omit<Product, 'id'>) {
    const product = { id: products.length + 1, ...body };
    products.push(product);
    return product;
  }

  @Patch(':id')
  update(@Param('id', ParseIntPipe) id: number, @Body('price') price: number) {   // pick one body field
    const product = products.find((p) => p.id === id)!;
    product.price = price;
    return product;
  }

  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)                  // 204 instead of 200
  remove(@Param('id', ParseIntPipe) id: number) {
    products.splice(products.findIndex((p) => p.id === id), 1);
  }
}
EOF
npm run build --silent
NO_COLOR=1 node dist/main.js > server.log 2>&1 &
sleep 2

curl -s "$U?page=2&limit=1&sort=price"; echo

curl -s -D - -o /dev/null "$U/1" | grep -iE "^(HTTP|cache-control)" | tr -d '\r'
```

<Happened>
<Tr>
<En>

- **Query parameters**: with no query, `DefaultValuePipe` supplied `page: 1` and `limit: 10`, and `ParseIntPipe` turned `"2"`/`"1"` into numbers. `page=two` was rejected with **400** before the method ran.
- **`cheapest`** worked because it's declared **before** `:id` (step 3 shows the opposite).
- **`@Header`** added `Cache-Control` to the single-product response; **`@Redirect`** answered 301 with a `Location` of `/products`.
- **`@Post`** answered **201** automatically. **`@Patch`** used `@Body('price')` to read only that field, so the extra `"name":"ignored"` had no effect (real apps validate the whole body with a DTO instead).
- **`@Delete`** with `@HttpCode(HttpStatus.NO_CONTENT)` returned **204** and no body.
- The startup log lists every mapped route in declaration order, which is a quick way to check your URLs.

</En>
<Ur>

- **Query parameters**: bina query ke `DefaultValuePipe` ne `page: 1` aur `limit: 10` diye, aur `ParseIntPipe` ne `"2"`/`"1"` ko numbers banaya. `page=two` method chalne se pehle **400** ke saath radd hua.
- **`cheapest`** isliye chala ke ye `:id` se **pehle** bayan hai (qadam 3 ulta dikhata hai).
- **`@Header`** ne ek product ke response me `Cache-Control` joda; **`@Redirect`** ne `/products` ki `Location` ke saath 301 diya.
- **`@Post`** ne khud **201** diya. **`@Patch`** ne `@Body('price')` se sirf wahi field parha, isliye izafi `"name":"ignored"` ka koi asar nahi hua (asli apps is ke bajaye DTO se poori body validate karti hain).
- `@HttpCode(HttpStatus.NO_CONTENT)` wale **`@Delete`** ne **204** aur khaali body di.
- Startup log har map hua route bayan ki tarteeb se dikhata hai, jo apne URLs check karne ka jaldi tareeqa hai.

</Ur>
</Tr>
</Happened>

<Step title="Global prefix, versioning, headers and cookies">

<Tr>
<En>
`main.ts` adds an `/api` prefix and URI versioning with a default of v1. A new controller reads the user agent and IP, offers a v2 response for the same path, and sets a cookie and a 202 status through the passthrough response.
</En>
<Ur>
`main.ts` `/api` prefix aur v1 default ke saath URI versioning jorta hai. Naya controller user agent aur IP parhta hai, usi path ke liye v2 response deta hai, aur passthrough response ke zariye cookie aur 202 status set karta hai.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/main.ts <<'EOF'
import { NestFactory } from '@nestjs/core';
import { VersioningType } from '@nestjs/common';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.setGlobalPrefix('api');                                   // every route starts with /api
  app.enableVersioning({ type: VersioningType.URI, defaultVersion: '1' });   // /api/v1/..., /api/v2/...
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();
EOF
cat > src/session.controller.ts <<'EOF'
import { Controller, Get, Headers, Ip, Post, Res, Version } from '@nestjs/common';
import type { Response } from 'express';

@Controller('session')
export class SessionController {
  @Get('info')
  info(@Headers('user-agent') userAgent: string, @Ip() ip: string) {
    return { userAgent, ip };
  }

  @Get('info')
  @Version('2')                                     // same path, new response shape for v2
  infoV2(@Headers('user-agent') userAgent: string) {
    return { client: { userAgent }, apiVersion: 2 };
  }

  @Post('theme')
  setTheme(@Res({ passthrough: true }) res: Response) {   // passthrough: Nest still sends the return value
    res.cookie('theme', 'dark', { httpOnly: true, sameSite: 'lax' });
    res.status(202);
    return { saved: true };
  }
}
EOF
sed -i "s#import { AppService } from './app.service.js';#&\nimport { SessionController } from './session.controller.js';#; s#controllers: \[AppController, ProductsController\]#controllers: [AppController, ProductsController, SessionController]#" src/app.module.ts
grep controllers src/app.module.ts
npm run build --silent
NO_COLOR=1 node dist/main.js > server.log 2>&1 &
sleep 2
curl -s -A "AcmeApp/2.1" localhost:3000/api/v1/session/info; echo
curl -s -A "AcmeApp/2.1" localhost:3000/api/v2/session/info; echo
curl -s -o /dev/null -w "old path without /api/v1: %{http_code}\n" localhost:3000/products
curl -s -D - -X POST localhost:3000/api/v1/session/theme | grep -iE "^(HTTP|set-cookie|\{)" | tr -d '\r'
kill %1
```

<Happened>
<Tr>
<En>

- `/api/v1/session/info` and `/api/v2/session/info` reached **different methods** with the same `@Get('info')`. Old clients keep v1 while new clients move to v2; you remove v1 when nobody uses it.
- After `setGlobalPrefix('api')` and versioning, the old `/products` URL answered **404**: every route, including the products controller from step 1, now lives under `/api/v1`. Add the prefix and versioning at the start of a project, not after clients exist.
- `@Headers('user-agent')` and `@Ip()` read request details (behind a proxy, configure `trust proxy` for `@Ip()` to be correct, as in Express).
- `@Res({ passthrough: true })` gave access to Express's `res` for `res.cookie()` and `res.status(202)`, while Nest still serialised the returned `{ saved: true }`. Without `passthrough`, Nest stops handling the response: you'd have to call `res.json()` yourself, and interceptors would no longer apply.

</En>
<Ur>

- `/api/v1/session/info` aur `/api/v2/session/info` wahi `@Get('info')` ke saath **mukhtalif methods** tak pohanche. Purane clients v1 rakhte hain jab ke naye v2 par chale jate hain; jab koi istemal na kare to v1 hata dein.
- `setGlobalPrefix('api')` aur versioning ke baad purane `/products` URL ne **404** diya: har route, qadam 1 ka products controller samet, ab `/api/v1` ke neeche hai. Prefix aur versioning project ke shuru me jorein, clients ban jane ke baad nahi.
- `@Headers('user-agent')` aur `@Ip()` request ki tafseel parhte hain (proxy ke peeche `@Ip()` sahi hone ke liye `trust proxy` set karein, Express ki tarah).
- `@Res({ passthrough: true })` ne `res.cookie()` aur `res.status(202)` ke liye Express ka `res` diya, jab ke Nest ne phir bhi wapas aaya `{ saved: true }` serialise kiya. `passthrough` ke baghair Nest response sambhalna band kar deta hai: aap ko khud `res.json()` bulana parta, aur interceptors lagu na hote.

</Ur>
</Tr>
</Happened>

<Step title="Route order: the swallowed route">

<Tr>
<En>
This controller declares `:id` **before** `today`. Both are valid routes, but only one can win for `/deals/today`.
</En>
<Ur>
Ye controller `today` se **pehle** `:id` bayan karta hai. Dono durust routes hain, magar `/deals/today` ke liye sirf ek jeet sakta hai.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/deals.controller.ts <<'EOF'
import { Controller, Get, Param, ParseIntPipe } from '@nestjs/common';

@Controller('deals')
export class DealsController {
  @Get(':id')                                      // declared FIRST: it also matches /deals/today
  findOne(@Param('id', ParseIntPipe) id: number) {
    return { deal: id };
  }

  @Get('today')                                    // never reached
  today() {
    return { deal: 'today' };
  }
}
EOF

npm run build --silent
NO_COLOR=1 node dist/main.js > server.log 2>&1 &
```

- `/deals/7` worked. `/deals/today` was matched by **`:id`** first, so `ParseIntPipe` tried to parse `"today"` and answered **400**. The `today()` method never runs.

</En>

## Common mistakes

<Compare>
<Bad title="Taking over the response with @Res()">

```text
@Get(':id')
findOne(@Param('id') id: string, @Res() res: Response) {
  const product = this.products.findOne(Number(id));      // no pipe: "abc" → NaN
  res.status(200).json(product);                           // interceptors and serialisation bypassed
}
```

</Bad>
<Good title="Pipes in, return value out">

```text
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
  return this.products.findOne(id);
}
```

</Good>
</Compare>

<Compare>
<Bad title="Logic in the controller">

```text
@Post()
create(@Body() body: any) {
  if (!body.name || body.price < 0) throw new BadRequestException();   // validation by hand
  this.db.push({ ...body, id: Date.now() });                           // data access
}
```

</Bad>
<Good title="Thin controller">

```text
@Post()
create(@Body() dto: CreateProductDto) {     // validated by ValidationPipe (DTOs lesson)
  return this.products.create(dto);         // rules and data in the service
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting that path and query values are strings**: without a pipe, `@Param('id') id: number` is still a string at runtime, because TypeScript types don't convert anything.
- **Declaring parameter routes before static ones**.
- **Using `@Body() body: any`** and passing it straight to the database (mass assignment).
- **Returning `null` for a missing record** instead of throwing `NotFoundException` (404).
- **Adding a global prefix or versioning after launch**, breaking every existing client.
- **Mixing `@Res()` without passthrough with a `return`**: the request hangs because Nest waits for you to send the response.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ye bhoolna ke path aur query values strings hain**: pipe ke baghair `@Param('id') id: number` runtime par ab bhi string hai, kyun ke TypeScript types kuch convert nahi kartin.
- **Static routes se pehle parameter routes bayan karna**.
- **`@Body() body: any` istemal karna** aur use seedha database ko dena (mass assignment).
- Ghayab record ke liye `NotFoundException` (404) throw karne ke bajaye **`null` return karna**.
- **Launch ke baad global prefix ya versioning jorna**, jis se har maujooda client toot jata hai.
- **Passthrough ke baghair `@Res()` ko `return` ke saath milana**: request latak jati hai kyun ke Nest intezar karta hai ke response aap bhejein.

</Ur>
</Tr>

## Try it yourself

<Challenge title="An orders controller">

<Tr>
<En>
Write `OrdersController` (prefix `orders`) with: `GET /` with optional `status` and `page` (default 1) query parameters; `GET /:id` with a UUID (`ParseUUIDPipe`); `POST /` returning 201 and a `Location` header pointing to the new order; `POST /:id/cancel` returning 200 (not 201); `DELETE /:id` returning 204.
</En>
<Ur>
`OrdersController` (prefix `orders`) likhein jis me ho: ikhtiyari `status` aur `page` (default 1) query parameters ke saath `GET /`; UUID (`ParseUUIDPipe`) ke saath `GET /:id`; 201 aur nayi order ki taraf ishara karne wala `Location` header dene wala `POST /`; 200 (201 nahi) dene wala `POST /:id/cancel`; 204 dene wala `DELETE /:id`.
</Ur>
</Tr>

<Solution>

```text
@Controller('orders')
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}

  @Get()
  list(@Query('status') status?: string, @Query('page', new DefaultValuePipe(1), ParseIntPipe) page = 1) {
    return this.orders.list({ status, page });
  }

  @Get(':id')
  findOne(@Param('id', ParseUUIDPipe) id: string) {
    return this.orders.findOne(id);
  }

  @Post()
  create(@Body() dto: CreateOrderDto, @Res({ passthrough: true }) res: Response) {
    const order = this.orders.create(dto);
    res.location(`/api/v1/orders/${order.id}`);
    return order;                                   // 201 by default for @Post
  }

  @Post(':id/cancel')
  @HttpCode(HttpStatus.OK)                          // an action, not a creation
  cancel(@Param('id', ParseUUIDPipe) id: string) {
    return this.orders.cancel(id);
  }

  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  remove(@Param('id', ParseUUIDPipe) id: string) {
    this.orders.remove(id);
  }
}
```

<Tr>
<En>
`ParseUUIDPipe` rejects malformed IDs with 400 before any database call. `POST /:id/cancel` is a common pattern for actions that don't fit CRUD; it changes state but doesn't create a resource, so 200 is the right status. The `Location` header uses the passthrough response because it depends on the new ID.
</En>
<Ur>
`ParseUUIDPipe` kharab IDs ko kisi database call se pehle 400 ke saath radd karta hai. `POST /:id/cancel` CRUD me fit na hone wale actions ka aam tareeqa hai; ye state badalta hai magar resource nahi banata, isliye 200 sahi status hai. `Location` header passthrough response istemal karta hai kyun ke wo nayi ID par munhasir hai.
</Ur>
</Tr>

</Solution>

</Challenge>

```text
@Controller('users')
export class UsersController {

  @Get('me')
  me(@Req() req) { return req.user; }
```

Chaar masle dhoondein.

```text
@Controller('users')
export class UsersController {
  @Get(':id')
  findOne(@Param('id') id: number) { return this.users.findOne(id); }

  @Get('me')
  me(@Req() req) { return req.user; }

  @Delete(':id')
  remove(@Param('id') id: number, @Res() res: Response) { this.users.remove(id); return { deleted: true }; }
}
```

</Ur>

<Solution>

<Tr>
<En>

1. `@Param('id') id: number` has no pipe, so `id` is really a string; use `ParseIntPipe`.
2. `@Get('me')` comes after `@Get(':id')`, so `/users/me` goes to `findOne("me")`.
3. `remove` injects `@Res()` without passthrough and returns a value, so Nest never sends a response and the request hangs; remove `@Res()` (and probably return 204).
4. There's no authentication or authorisation: anyone can read or delete any user. Protect the controller with a guard and check that users can only delete themselves or are admins (Guards lesson). Also, `this.users` is used but never injected through a constructor.

</En>
<Ur>

1. `@Param('id') id: number` par koi pipe nahi, isliye `id` asal me string hai; `ParseIntPipe` lein.
2. `@Get('me')` `@Get(':id')` ke baad hai, isliye `/users/me` `findOne("me")` par jata hai.
3. `remove` passthrough ke baghair `@Res()` inject karta aur value return karta hai, isliye Nest kabhi response nahi bhejta aur request latak jati hai; `@Res()` hatayen (aur shayad 204 wapas karein).
4. Koi authentication ya authorisation nahi: koi bhi kisi bhi user ko parh ya mita sakta hai. Controller ko guard se mehfooz karein aur check karein ke users sirf khud ko mita saken ya admin hon (Guards lesson). Saath hi, `this.users` istemal hua magar constructor se kabhi inject nahi hua.

<DeepDive title="More about controllers">

**Async handlers.** Methods can be `async` or return an RxJS `Observable`; Nest waits for the result and sends it.

**Custom parameter decorators.** `createParamDecorator((data, ctx) => ctx.switchToHttp().getRequest().user)` creates `@CurrentUser()`, a common pattern after authentication.

**Other versioning types.** Header versioning (`X-API-Version`), media type versioning (`Accept: application/json;v=2`), or a custom extractor.

**Sub-domain routing.** `@Controller({ host: ':tenant.example.com' })` with `@HostParam('tenant')` for multi-tenant apps.

**Streaming files.** Return `new StreamableFile(createReadStream(path))` and set `Content-Type`/`Content-Disposition` with `@Header` or passthrough.

**Server-Sent Events.** `@Sse('events')` returning an Observable streams events to the browser over one HTTP connection.

</DeepDive>

<DeepDive title="Real world: the v2 that broke the mobile app">

A delivery app's NestJS API had no versioning. The team wanted to change `GET /orders/:id` so that `address` became an object (`{ street, city, zip }`) instead of a single string, for a new web dashboard. The change was deployed on a Friday afternoon.

The web dashboard worked. The Android and iOS apps, which had cached millions of installs on older versions that users hadn't updated, displayed `[object Object]` as the delivery address and, worse, crashed on the order screen for some users because the code called `.split(",")` on the address. Rolling back the API fixed the apps but broke the newly deployed dashboard.

The fix on Monday:

1. `app.enableVersioning({ type: VersioningType.URI, defaultVersion: '1' })`, so all existing URLs kept working as `/v1` with the default.
2. The new response shape was added under `@Version('2')`, and the dashboard was pointed to `/v2`.
3. The mobile apps were updated to request `/v2`; v1 stayed for 12 months, with logging of which app versions still called it.
4. API contract tests (snapshots of v1 responses) were added so a change to v1's shape would fail CI.

Mobile clients can't be updated on your schedule, which is why public and mobile APIs should be versioned from day one.

</DeepDive>

<DeepDive title="Security lens">

- **Validate every input**: pipes for params and queries, `ValidationPipe` with DTOs for bodies (next lessons); never trust types alone.
- **Protect controllers with guards** (authentication and roles), ideally a global "deny unless public" guard.
- **Avoid `@Req()`/`@Res()` shortcuts** that bypass interceptors handling serialisation (for example removing `passwordHash` from responses).
- **Set secure cookie flags** (`httpOnly`, `secure`, `sameSite`) when using passthrough responses.
- **Don't leak whether resources exist** for other users; use 404 consistently.
- **Retire old API versions** deliberately; unmaintained versions often miss security fixes.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you define routes in NestJS?">
With a @Controller decorator providing a path prefix on the class and HTTP method decorators like @Get, @Post, @Patch and @Delete with sub-paths on methods; Nest combines them, plus any global prefix and version, into routes at startup.
</QA>

<QA q="How do you access request data in a controller method?">
Through parameter decorators: @Param for path params, @Query for query strings, @Body for the body, @Headers for headers, @Ip for the client IP, and @Req for the whole request when necessary, combined with pipes for conversion and validation.
</QA>

<QA q="What's the difference between returning a value and using @Res()?">
Returning a value lets Nest handle serialisation, status codes, interceptors and exception filters. Injecting @Res switches to library-specific mode where you must send the response yourself and lose those features, unless you use passthrough mode.
</QA>

<QA q="How do you change the status code of a route?">
Use @HttpCode on the method for a fixed status, throw an HttpException subclass for errors, or set it dynamically through a passthrough response object.
</QA>

<QA q="How do you version an API in NestJS?">
Enable versioning in main.ts with a type such as URI, header or media type and a default version, then mark controllers or routes with @Version, so different versions of the same path map to different handlers.
</QA>

</DeepDive>
