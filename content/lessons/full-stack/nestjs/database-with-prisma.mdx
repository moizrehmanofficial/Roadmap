<BigIdea>
<Tr>
<En>
**Prisma** is a database toolkit where everything starts from one file, **`schema.prisma`**. In it you describe your **models** (tables), their fields and **relations** in a short, readable language. From that schema Prisma does two things. **`prisma migrate dev`** compares the schema with the database and writes a **SQL migration** for you, which you commit and later apply in production with `migrate deploy`. **`prisma generate`** produces a **fully typed client**: `prisma.customer.findMany({ where, select, include })` knows every model, field and relation, so a typo or wrong type is a compile error, and the result type matches exactly what you selected. In NestJS you wrap the client in a **`PrismaService`** provider and inject it. Errors come back with stable **codes** (`P2002` unique violation, `P2025` record not found) that you map to HTTP responses, and **`$transaction`** groups several operations so they all succeed or all roll back. Prisma 7 talks to the database through a **driver adapter** (for PostgreSQL, `@prisma/adapter-pg`) and reads the connection URL from **`prisma.config.ts`**.
</En>
<Ur>
**Prisma** aisa database toolkit hai jahan sab kuch ek file, **`schema.prisma`**, se shuru hota hai. Is me aap apne **models** (tables), un ke fields aur **relations** ek chhoti, parhne laiq zaban me likhte hain. Us schema se Prisma do kaam karta hai. **`prisma migrate dev`** schema ko database se milata hai aur aap ke liye **SQL migration** likhta hai, jise aap commit karte aur baad me production par `migrate deploy` se lagate hain. **`prisma generate`** **mukammal typed client** banata hai: `prisma.customer.findMany({ where, select, include })` har model, field aur relation jaanta hai, isliye typo ya ghalat type compile error ban jata hai, aur nateeje ki type bilkul wahi hoti hai jo aap ne select kiya. NestJS me aap client ko **`PrismaService`** provider me lapet kar inject karte hain. Errors mustaqil **codes** (`P2002` unique ki khilaf warzi, `P2025` record nahi mila) ke saath aate hain jinhen aap HTTP responses me badalte hain, aur **`$transaction`** kai amal ikatthe karta hai taa ke sab kamyab hon ya sab wapas ho jayen. Prisma 7 database se **driver adapter** ke zariye baat karta hai (PostgreSQL ke liye `@prisma/adapter-pg`) aur connection URL **`prisma.config.ts`** se parhta hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of an **architect's blueprint**.

- The **blueprint** (`schema.prisma`) describes every room and how rooms connect (models and relations).
- When the blueprint changes, the architect writes **renovation instructions** for the builders ("knock through this wall, add a window"): those are **migrations**, applied in order to the real building.
- From the same blueprint, the architect prints a **guidebook** for everyone who works in the building, listing exactly which rooms and doors exist (the **generated client**). Ask for a room that isn't in the guidebook and you're corrected before you start walking (a type error).
- A **transaction** is a moving crew that either moves the whole set of furniture to the new room, or, if something doesn't fit, puts everything back where it was.

</En>
<Ur>

**Architect ke naqshe** ka sochein.

- **Naqsha** (`schema.prisma`) har kamra aur kamre aapas me kaise jurte hain bayan karta hai (models aur relations).
- Jab naqsha badle, architect mistriyon ke liye **marammat ki hidayat** likhta hai ("ye deewar todo, khirki lagao"): ye **migrations** hain, jo tarteeb se asli imarat par lagti hain.
- Usi naqshe se architect imarat me kaam karne wale har shakhs ke liye **rehnuma kitab** chhapta hai jo bilkul batati hai ke kaun se kamre aur darwaze hain (**generated client**). Kitab me na hone wala kamra maangen to chalne se pehle hi tok diye jate hain (type error).
- **Transaction** samaan uthane wali team hai jo ya to poora furniture naye kamre me le jati hai, ya agar kuch fit na ho to sab wapas apni jagah rakh deti hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Schema, first migration, typed client and a Nest API">

<Tr>
<En>
We describe `Customer` and `Order` in `schema.prisma` (with a unique email and an index on `customerId`), point `prisma.config.ts` at the database, run `migrate dev` and `generate`, then build a small API: `PrismaService` extends the generated `PrismaClient` with the PostgreSQL adapter, and a controller creates customers (with a nested first order), lists them with order counts, filters orders and renames customers.
</En>
<Ur>
Hum `schema.prisma` me `Customer` aur `Order` likhte hain (unique email aur `customerId` par index ke saath), `prisma.config.ts` ko database ki taraf karte hain, `migrate dev` aur `generate` chalate hain, phir chhoti API banate hain: `PrismaService` generated `PrismaClient` ko PostgreSQL adapter ke saath extend karta hai, aur controller customers banata hai (nested pehle order ke saath), un ki list orders ki ginti ke saath deta hai, orders filter karta hai aur customers ka naam badalta hai.
</Ur>
</Tr>

import { Injectable, OnModuleDestroy } from '@nestjs/common';
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from './generated/prisma/client.js';

@Injectable()
export class PrismaService extends PrismaClient implements OnModuleDestroy {
  constructor() {
    super({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL! }) });   // Prisma 7: a driver adapter
  }
  onModuleDestroy() { return this.$disconnect(); }
}
EOF
cat > src/customers.controller.ts <<'EOF'
import { Body, ConflictException, Controller, Get, NotFoundException, Param, ParseIntPipe, Patch, Post } from '@nestjs/common';
import { Prisma } from './generated/prisma/client.js';
import { PrismaService } from './prisma.service.js';

@Controller('customers')
export class CustomersController {
  constructor(private readonly prisma: PrismaService) {}

  @Post()
  async create(@Body() body: { email: string; name: string; firstOrderCents?: number }) {
    try {
      return await this.prisma.customer.create({
        data: {
          email: body.email,
          name: body.name,
          ...(body.firstOrderCents && { orders: { create: { totalCents: body.firstOrderCents } } }),   // nested write
        },
        include: { orders: { select: { id: true, totalCents: true, status: true } } },
      });
    } catch (e) {
      if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002')
        throw new ConflictException('Email already registered');          // unique constraint
      throw e;
    }
  }

  @Get()
  list() {
    return this.prisma.customer.findMany({
      select: { id: true, name: true, _count: { select: { orders: true } } },
      orderBy: { id: 'asc' },
    });
  }

  @Get(':id/orders')
  async orders(@Param('id', ParseIntPipe) id: number) {
    return this.prisma.order.findMany({
      where: { customerId: id, totalCents: { gte: 1000 } },               // typed filters
      select: { id: true, totalCents: true, status: true },
    });
  }

  @Patch(':id')
  async rename(@Param('id', ParseIntPipe) id: number, @Body() body: { name: string }) {
    try {
      return await this.prisma.customer.update({ where: { id }, data: { name: body.name }, select: { id: true, name: true } });
    } catch (e) {
      if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2025')
        throw new NotFoundException('Customer not found');               // record to update not found
      throw e;
    }
  }
}
EOF

import { Module } from '@nestjs/common';
import { CustomersController } from './customers.controller.js';
import { PrismaService } from './prisma.service.js';

@Module({ controllers: [CustomersController], providers: [PrismaService] })
export class AppModule {}
EOF

<Happened>
<Tr>
<En>

- `migrate dev` turned the schema into SQL: two tables, a **unique index** for `@unique` on email and a normal index for `@@index([customerId])`. The migration folder is named with a timestamp plus your name (`…_init`); commit it with your code.
- `generate` wrote the typed client into `src/generated/prisma`. Prisma 7 no longer generates into `node_modules`, and needs a **driver adapter** (`PrismaPg`) when creating the client.
- One `create` with a nested `orders: { create: … }` inserted the customer **and** the order; `include` with a `select` returned only the order fields we asked for.
- The duplicate email failed with Prisma error **`P2002`** (unique constraint), which we mapped to **409**. Without that `catch`, the client would see a 500.
- `select` with `_count` returned each customer's order count without loading the orders. `where: { totalCents: { gte: 1000 } }` is fully typed: a misspelled field or a string instead of a number won't compile.
- Updating a missing customer threw **`P2025`**, mapped to **404**.

</En>
<Ur>

- `migrate dev` ne schema ko SQL me badla: do tables, email par `@unique` ke liye **unique index** aur `@@index([customerId])` ke liye aam index. Migration folder ka naam timestamp plus aap ka naam (`…_init`) hai; ise apne code ke saath commit karein.
- `generate` ne typed client `src/generated/prisma` me likha. Prisma 7 ab `node_modules` me generate nahi karta, aur client banate waqt **driver adapter** (`PrismaPg`) maangta hai.
- Nested `orders: { create: … }` wale ek `create` ne customer **aur** order dono daale; `select` ke saath `include` ne sirf maange gaye order fields lautaye.
- Dohri email Prisma error **`P2002`** (unique constraint) ke saath nakam hui, jise humne **409** me badla. Is `catch` ke baghair client ko 500 milta.
- `_count` wale `select` ne orders load kiye baghair har customer ke orders ki ginti lautayi. `where: { totalCents: { gte: 1000 } }` mukammal typed hai: ghalat likha field ya number ki jagah string compile nahi hoga.
- Ghaib customer update karne par **`P2025`** aaya, jise **404** me badla.

</Ur>
</Tr>
</Happened>

<Step title="A second migration and interactive transactions">

<Tr>
<En>
The product team adds a `Product` model with stock, and orders get an optional `sku`. We run a second migration and check `migrate status`. Then `placeOrder` runs inside `$transaction`: it creates the order and takes stock with an **atomic conditional update** (`updateMany` where `stock >= qty`). If no row was updated, it throws, and the whole transaction rolls back. Finally four customers try to buy the last lamp at the same moment.
</En>
<Ur>
Product team stock wala `Product` model jorti hai, aur orders ko ikhtiyari `sku` milta hai. Hum doosri migration chalate aur `migrate status` check karte hain. Phir `placeOrder` `$transaction` ke andar chalta hai: order banata hai aur **atomic shart wale update** (`updateMany` jahan `stock >= qty`) se stock leta hai. Agar koi row update na ho to error phenkta hai, aur poora transaction wapas ho jata hai. Aakhir me chaar customers ek hi lamhe aakhri lamp khareedne ki koshish karte hain.
</Ur>
</Tr>

```bash
cd shop-api
export DATABASE_URL=postgres://postgres:postgres@localhost:5432/shop
# 1. Change the schema: add products with stock, and link orders to a product
cat >> prisma/schema.prisma <<'EOF'

model Product {
  id         Int    @id @default(autoincrement())
  sku        String @unique
  priceCents Int
  stock      Int
}
EOF
sed -i 's/  status     String   @default("pending")/  status     String   @default("pending")\n  sku        String?/' prisma/schema.prisma
npx prisma migrate dev --name add_products > /dev/null 2>&1
npx prisma generate > /dev/null 2>&1
echo "migrations: $(ls prisma/migrations | grep -v toml | sed -E 's/^[0-9]+_//' | xargs)"
echo "new SQL:"; grep -vE '^--|^$' prisma/migrations/*_add_products/migration.sql | grep -E 'ALTER|CREATE TABLE' | tr -s ' ' | sed 's/^/  /'
echo "status: $(npx prisma migrate status 2>&1 | grep -E 'up to date')"
# 2. Place an order in one transaction: take stock and create the order, or do neither
cat > src/place-order.ts <<'EOF'
import { PrismaService } from './prisma.service.js';

const prisma = new PrismaService();

async function placeOrder(customerId: number, sku: string, qty: number) {
  return prisma.$transaction(async (tx) => {
    const product = await tx.product.findUniqueOrThrow({ where: { sku } });
    const order = await tx.order.create({ data: { customerId, sku, totalCents: product.priceCents * qty } });
    // atomic "take stock only if enough is left"
    const taken = await tx.product.updateMany({ where: { sku, stock: { gte: qty } }, data: { stock: { decrement: qty } } });
    if (taken.count === 0) throw new Error(`not enough ${sku}`);       // throwing rolls back the order too
    return order;
  });
}

await prisma.product.create({ data: { sku: 'lamp', priceCents: 2000, stock: 3 } });
const state = async () => `stock ${(await prisma.product.findUnique({ where: { sku: 'lamp' } }))!.stock}, lamp orders ${await prisma.order.count({ where: { sku: 'lamp' } })}`;

console.log('start:            ', await state());
await placeOrder(1, 'lamp', 2);
console.log('order 2 lamps:    ', await state());
await placeOrder(1, 'lamp', 5).catch((e) => console.log('order 5 lamps:     failed,', e.message));
console.log('after the failure:', await state());

// 4 customers try to buy the last lamp at the same moment
const results = await Promise.allSettled([1, 2, 1, 2].map((c) => placeOrder(c, 'lamp', 1)));
console.log('4 parallel orders for 1 lamp:', results.filter((r) => r.status === 'fulfilled').length, 'succeeded');
console.log('end:              ', await state());
await prisma.$disconnect();
EOF
npm run build --silent
node dist/place-order.js
```

<Happened>
<Tr>
<En>

- The second migration contained only the **difference**: `ALTER TABLE "Order" ADD COLUMN "sku"` and `CREATE TABLE "Product"`. Migrations run in order, and `migrate status` confirmed the database matches. In production you run `npx prisma migrate deploy`, which applies pending migrations without generating new ones.
- Ordering 2 lamps took stock from 3 to 1 and created one order.
- Ordering 5 failed: the conditional update matched no row, we threw, and the order created a moment earlier inside the transaction was **rolled back**: still 1 order and stock 1. Without the transaction, you'd have an order for stock you don't have.
- Four parallel orders for the last lamp: exactly **one** succeeded and stock ended at **0**, never negative. `stock: { gte: qty }` plus `decrement` is a single atomic `UPDATE … WHERE stock >= 1`, so PostgreSQL lets only one through. Reading the stock, checking it in JavaScript and then writing it would let several orders pass.
- Keep transactions short: no HTTP calls or slow work inside them, since they hold locks and a database connection.

</En>
<Ur>

- Doosri migration me sirf **farq** tha: `ALTER TABLE "Order" ADD COLUMN "sku"` aur `CREATE TABLE "Product"`. Migrations tarteeb se chalti hain, aur `migrate status` ne tasdeeq ki ke database mel khata hai. Production me aap `npx prisma migrate deploy` chalate hain, jo nayi migrations banaye baghair baqi migrations lagata hai.
- 2 lamps ke order ne stock 3 se 1 kiya aur ek order banaya.
- 5 ka order nakam hua: shart wale update ne koi row nahi pakri, humne error phenka, aur transaction ke andar lamha pehle bana order **wapas** ho gaya: ab bhi 1 order aur stock 1. Transaction ke baghair aap ke paas aise stock ka order hota jo hai hi nahi.
- Aakhri lamp ke liye chaar ek saath orders: bilkul **ek** kamyab hua aur stock **0** par khatam hua, kabhi manfi nahi. `stock: { gte: qty }` plus `decrement` ek atomic `UPDATE … WHERE stock >= 1` hai, isliye PostgreSQL sirf ek ko guzarne deta hai. Stock parh kar JavaScript me check karna aur phir likhna kai orders ko guzar jane deta.
- Transactions chhote rakhein: andar HTTP calls ya sust kaam nahi, kyunke wo locks aur database connection pakre rakhte hain.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Check in JavaScript, then write">

```text
const p = await prisma.product.findUnique({ where: { sku } });
if (p.stock < qty) throw new Error('not enough');
await prisma.product.update({ where: { sku }, data: { stock: p.stock - qty } });   // two requests both pass the check
```

</Bad>
<Good title="Atomic conditional update">

```text
const { count } = await prisma.product.updateMany({
  where: { sku, stock: { gte: qty } },
  data: { stock: { decrement: qty } },
});
if (count === 0) throw new ConflictException('Not enough stock');
```

</Good>
</Compare>

<Compare>
<Bad title="A new PrismaClient per request">

```text
@Get()
list() {
  const prisma = new PrismaClient({ adapter });      // new connection pool every request
  return prisma.customer.findMany();
}
```

</Bad>
<Good title="One PrismaService, injected">

```text
@Injectable()
export class PrismaService extends PrismaClient implements OnModuleDestroy { … }

constructor(private readonly prisma: PrismaService) {}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Editing applied migrations** or the database by hand: Prisma detects the drift. Change the schema and create a new migration.
- **Running `migrate dev` in production**: it can reset the database. Use `migrate deploy`.
- **Forgetting `prisma generate`** after a schema change: the client's types no longer match the database. Run it in your build step.
- **Returning whole records** with fields like `passwordHash`: use `select`, or `omit`, to return only safe fields.
- **N+1 queries**: looping over customers and querying orders for each; use `include`, or a single `findMany` with `where: { customerId: { in: ids } }`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Lag chuki migrations** ya database ko haath se badalna: Prisma farq (drift) pakar leta hai. Schema badlein aur nayi migration banayen.
- **Production me `migrate dev` chalana**: ye database reset kar sakta hai. `migrate deploy` lein.
- **Schema badalne ke baad `prisma generate` bhoolna**: client ki types database se mel nahi khatin. Ise apne build step me chalayen.
- **Poore records lautana** jin me `passwordHash` jaise fields hon: sirf mehfooz fields lautane ke liye `select` ya `omit` lein.
- **N+1 queries**: customers par loop kar ke har ek ke orders poochna; `include` lein, ya `where: { customerId: { in: ids } }` ke saath ek `findMany`.

</Ur>
</Tr>

<Tr>

  customer   Customer @relation(fields: [customerId], references: [id])

  product    Product  @relation(fields: [productId], references: [id])

  rating     Int
  comment    String

<Challenge title="Renaming a column safely">

<Tr>
<En>
You change `name String` to `fullName String` in `Customer` and run `migrate dev`. Prisma warns that data will be lost. Why, and how do you rename without losing data, given the app runs several instances during deploys?
</En>
<Ur>
Aap `Customer` me `name String` ko `fullName String` karte hain aur `migrate dev` chalate hain. Prisma khabardar karta hai ke data khoya jayega. Kyun, aur data khoye baghair naam kaise badlein, jab ke deploys ke dauran app ke kai instances chalte hain?
</Ur>
</Tr>

<Solution>

<Tr>
<En>
Prisma sees one field removed and another added, so its default migration drops `name` and adds an empty `fullName`. Options:

- Quick rename (one instance, short downtime acceptable): `migrate dev --create-only`, replace the generated SQL with `ALTER TABLE "Customer" RENAME COLUMN "name" TO "fullName";`, then apply.
- Zero-downtime (several instances): **expand and contract**. Add `fullName` (nullable) and backfill it from `name`; deploy code that writes both and reads `fullName`; make it required; in a later release, remove `name`. Alternatively keep the database column and rename only in code with `fullName String @map("name")`.

</En>
<Ur>
Prisma ko ek field hatta aur doosra jurta dikhta hai, isliye us ki default migration `name` mitati aur khaali `fullName` jorti hai. Ikhtiyarat:

- Jaldi rename (ek instance, thori bandish qabil-e-qubool): `migrate dev --create-only`, generated SQL ko `ALTER TABLE "Customer" RENAME COLUMN "name" TO "fullName";` se badlein, phir lagayen.
- Bina bandish (kai instances): **expand and contract**. `fullName` (nullable) jorein aur `name` se bharein; aisa code deploy karein jo dono me likhe aur `fullName` parhe; use zaroori banayen; baad ki release me `name` hatayen. <DeepDive title="More about Prisma">

**Raw SQL.** `prisma.$queryRaw` with a tagged template (values are parameterized) for reports Prisma's API can't express; TypedSQL generates types for `.sql` files.

**Client extensions.** `prisma.$extends` adds computed fields, custom methods or query hooks, for example soft deletes or setting a tenant ID.

**Seeding.** Configure a seed script in `prisma.config.ts` and run `npx prisma db seed` to fill development databases.

**Pagination.** Offset (`skip`, `take`) is simple; cursor pagination (`cursor`, `take`) stays fast on large tables.

**Prisma vs TypeORM.** Prisma: schema-first, generated types, query results typed by selection. TypeORM: entities as decorated classes, repositories, more traditional ORM patterns. Both run migrations and transactions; choose by team preference and existing code.

</DeepDive>

<DeepDive title="Real world: the oversold concert">

A ticketing startup sold seats for a small concert. The booking code read the event with Prisma, checked `ticketsLeft > 0` in JavaScript, then updated `ticketsLeft: event.ticketsLeft - 1` and created the ticket. It worked perfectly in testing.

When tickets went on sale, thousands of fans clicked at once. Many requests read the same `ticketsLeft` value, all passed the check, and all wrote back. The venue had 300 seats; the system sold 1,140 tickets.

The fixes:

1. Booking became one `$transaction`: an atomic `updateMany({ where: { id, ticketsLeft: { gt: 0 } }, data: { ticketsLeft: { decrement: 1 } } })`, then the ticket insert, rolling back if no row matched.
2. A database `CHECK (tickets_left >= 0)` constraint, added to the migration SQL, as a last line of defense.
3. Idempotency keys on the booking endpoint so retries didn't create duplicate tickets.
4. A load test that fires a thousand concurrent bookings against a 300-seat event and asserts exactly 300 tickets.

</DeepDive>

<DeepDive title="Security lens">

- **Injection**: Prisma's query API and tagged `$queryRaw` templates are parameterized; never build SQL strings with `$queryRawUnsafe` and user input.
- **Over-exposure**: select only safe fields; never return password hashes, tokens or internal flags.
- **Mass assignment**: don't pass `req.body` straight into `data`; whitelist fields via DTOs.
- **Least-privilege database user**: the app's role shouldn't be able to drop tables; run migrations with a separate role.
- **Secrets**: keep `DATABASE_URL` in the environment or a secret manager, not in `prisma.config.ts` or the repo.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does Prisma differ from a traditional ORM like TypeORM?">
Prisma is schema-first: a Prisma schema defines models, migrations are generated from it, and a client is generated with types that follow each query's select and include. TypeORM defines entities as decorated classes and uses repositories or active records. Both support migrations, relations and transactions.
</QA>

<QA q="How do you use Prisma in NestJS?">
Create a PrismaService that extends the generated PrismaClient, passing a driver adapter in Prisma 7, implement OnModuleDestroy to disconnect, register it as a provider (often in a global PrismaModule) and inject it into services.
</QA>

<QA q="What's the difference between migrate dev and migrate deploy?">
migrate dev is for development: it creates new migrations from schema changes, applies them, and may reset the database on drift. migrate deploy applies existing pending migrations only, safely, and is used in CI and production.
</QA>

<QA q="How do you handle concurrency when decrementing stock?">
Use an atomic conditional update such as updateMany with where stock greater than or equal to quantity and a decrement, inside a transaction with the related writes, and check the affected count; optionally add a database check constraint. Reading, checking in code and writing back allows races.
</QA>

<QA q="How do you handle Prisma errors in an API?">
Catch PrismaClientKnownRequestError and map codes to HTTP responses, for example P2002 unique violation to 409 and P2025 record not found to 404, often in a global exception filter, and let unexpected errors become 500 without leaking details.
</QA>

</DeepDive>
