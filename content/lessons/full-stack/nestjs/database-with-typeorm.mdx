<BigIdea>
<Tr>
<En>
An **ORM** (object-relational mapper) lets you work with database rows as TypeScript objects. **TypeORM** is the ORM Nest has supported the longest. You describe each table as an **entity** class: `@Entity('products')` on the class, `@Column()`, `@PrimaryGeneratedColumn()` and relation decorators like `@ManyToOne()` on properties. **`@nestjs/typeorm`** connects it to Nest: `TypeOrmModule.forRoot()` opens one connection pool for the app, `TypeOrmModule.forFeature([Product])` makes a **`Repository<Product>`** injectable with `@InjectRepository(Product)`, and you call `find`, `save` and the **query builder** on it. Three habits separate demos from production. First, **migrations**: generate SQL from your entity changes, review it, commit it, and run it on deploy; never let `synchronize: true` change a real database. Second, let the **database enforce rules** too (unique indexes, CHECK constraints, foreign keys), and translate its errors into 409/400 responses. Third, use **transactions** and **atomic updates** for anything that must stay consistent, like decrementing stock while creating an order, so concurrent requests can't oversell.
</En>
<Ur>
**ORM** (object-relational mapper) aap ko database rows ke saath TypeScript objects ki tarah kaam karne deta hai. **TypeORM** wo ORM hai jise Nest sab se pehle se support karta hai. Aap har table ko **entity** class ki tarah bayan karte hain: class par `@Entity('products')`, properties par `@Column()`, `@PrimaryGeneratedColumn()` aur `@ManyToOne()` jaise relation decorators. **`@nestjs/typeorm`** ise Nest se jorta hai: `TypeOrmModule.forRoot()` app ke liye ek connection pool kholta hai, `TypeOrmModule.forFeature([Product])` **`Repository<Product>`** ko `@InjectRepository(Product)` se inject hone qabil banata hai, aur aap is par `find`, `save` aur **query builder** bulate hain. Teen aadatein demos ko production se alag karti hain. Pehli, **migrations**: entity ki tabdeeliyon se SQL banayen, review karein, commit karein, aur deploy par chalayen; `synchronize: true` ko kabhi asli database badalne na dein. Doosri, **database ko bhi qawaid lagu karne dein** (unique indexes, CHECK constraints, foreign keys), aur us ke errors ko 409/400 responses me badlein. Teesri, jo cheez yaksan rehni chahiye us ke liye **transactions** aur **atomic updates** lein, jaise order banate waqt stock ghatana, taa ke saath chalti requests zyada na bech saken.
</Ur>

## Picture it

<Tr>
<En>

Think of a **library** with a card catalogue.

- Each **shelf type** has a printed **template** describing its cards: title, author, shelf number (an entity describing a table).
- When the library adds a new field, say "language", the head librarian writes a **renovation plan** ("add a language column to every card"), it's reviewed, filed in the history book, and carried out on a quiet day (a migration). Nobody lets a robot rebuild the shelves on its own during opening hours (`synchronize: true` in production).
- The **front desk staff** (repositories) fetch, add and update cards for visitors, following simple requests ("all books by this author, sorted by title").
- For unusual questions ("how many books per language, with total pages?"), a **researcher** writes a precise query (query builder).
- Lending the **last copy** to two people at the same moment must not be possible: the desk checks and marks the copy as lent in one move (atomic update inside a transaction).

</En>
<Ur>

Card catalogue wali **library** ka sochein.

- Har **shelf ki qism** ka chhapa hua **namoona** hai jo us ke cards bayan karta hai: title, musannif, shelf number (table bayan karne wali entity).

<Step title="Entities and a migration">

<Tr>
<En>
We create three entities (categories, products, orders) with a unique product name, a CHECK constraint for price and stock, and foreign keys. A `DataSource` file is shared by the app and the TypeORM CLI. Then we **generate** a migration from the entities, print its important parts, and **run** it against a fresh PostgreSQL database. The examples use a local PostgreSQL with user and password `postgres` (the Docker command above starts one); `psql` recreates the demo database. Timestamps in names are replaced with `<timestamp>`.
</En>
<Ur>
Hum teen entities banate hain (categories, products, orders) munfarid product naam, price aur stock ke CHECK constraint, aur foreign keys ke saath. `DataSource` file app aur TypeORM CLI dono istemal karte hain. Phir hum entities se migration **banate** hain, us ke ahem hisse print karte hain, aur naye PostgreSQL database par **chalate** hain. Misalein user aur password `postgres` wala local PostgreSQL istemal karti hain (oopar ki Docker command ek chalati hai); `psql` demo database dobara banata hai. Naamon ke timestamps `<timestamp>` se badle gaye hain.
</Ur>

```bash
import {
  Check, Column, CreateDateColumn, Entity, Index, JoinColumn, ManyToOne, OneToMany, PrimaryGeneratedColumn,
} from 'typeorm';

@Entity('categories')
export class Category {
  @PrimaryGeneratedColumn() id: number;
  @Column({ length: 50, unique: true }) name: string;
  @OneToMany(() => Product, (p) => p.category) products: Product[];
}

@Entity('products')
@Check(`"price_cents" > 0 AND "stock" >= 0`)                  // the database enforces the rules too
export class Product {
  @PrimaryGeneratedColumn() id: number;
  @Index({ unique: true }) @Column({ length: 100 }) name: string;
  @Column({ name: 'price_cents', type: 'integer' }) priceCents: number;   // money as integer cents
  @Column({ type: 'integer', default: 0 }) stock: number;
  @ManyToOne(() => Category, (c) => c.products, { nullable: false, onDelete: 'RESTRICT' })
  @JoinColumn({ name: 'category_id' })
  category: Category;
  @CreateDateColumn({ name: 'created_at' }) createdAt: Date;
}

@Entity('orders')
export class Order {
  @PrimaryGeneratedColumn() id: number;
  @ManyToOne(() => Product, { nullable: false }) @JoinColumn({ name: 'product_id' }) product: Product;
  @Column({ type: 'integer' }) quantity: number;
  @Column({ name: 'total_cents', type: 'integer' }) totalCents: number;
}
EOF

// Used by the TypeORM CLI (migrations) and by the Nest app

  type: 'postgres' as const,

  migrations: ['dist/migrations/*.js'],

};
export default new DataSource(dataSourceOptions);
```

<Happened>
<Tr>
<En>

- `migration:generate` compared the entities with the (empty) database and wrote the SQL to create three tables, the unique index on `name`, the CHECK constraint and two foreign keys. You read this file in code review like any other change.
- `@JoinColumn({ name: 'category_id' })` gave the foreign key a snake_case name; without it TypeORM would create `categoryId`.
- `migration:run` applied it and recorded it in the **`migrations`** table, so running it again does nothing. On deploy, run pending migrations before starting the new version of the app.
- The CLI works on the **compiled** JavaScript (`dist/data-source.js`) because the project uses ES modules; that's why we build before generating and again before running.
- Money is stored as **integer cents** (`price_cents`), avoiding floating-point rounding errors.

</En>
<Ur>

- `migration:generate` ne entities ko (khaali) database se milaya aur teen tables, `name` par unique index, CHECK constraint aur do foreign keys banane ka SQL likha. Aap ye file kisi bhi tabdeeli ki tarah code review me parhte hain.

```bash
import { BadRequestException, ConflictException, Injectable, NotFoundException } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { QueryFailedError, Repository } from 'typeorm';
import { Category, Product } from './entities.js';

@Injectable()
export class CatalogService {
  constructor(
    @InjectRepository(Product) private readonly products: Repository<Product>,
    @InjectRepository(Category) private readonly categories: Repository<Category>,
  ) {}

  async createCategory(name: string) {
    return this.categories.save(this.categories.create({ name }));
  }

  async createProduct(data: { name: string; priceCents: number; stock: number; categoryId: number }) {
    try {
      const product = this.products.create({ ...data, category: { id: data.categoryId } });
      const { id } = await this.products.save(product);
      return this.findOne(id);
    } catch (e) {
      const code = e instanceof QueryFailedError ? (e.driverError as { code?: string }).code : undefined;
      if (code === '23505') throw new ConflictException('A product with this name already exists');  // unique_violation
      if (code === '23514') throw new BadRequestException('Price must be positive and stock not negative'); // check_violation
      if (code === '23503') throw new BadRequestException('Category does not exist');                    // foreign_key_violation
      throw e;
    }
  }

  async findOne(id: number) {
    const product = await this.products.findOne({ where: { id }, relations: { category: true } });
    if (!product) throw new NotFoundException(`Product ${id} not found`);
    return product;
  }

  // Repository API: filter, sort, paginate
  list(categoryName?: string, page = 1, pageSize = 2) {
    return this.products.find({
      where: categoryName ? { category: { name: categoryName } } : {},
      relations: { category: true },
      order: { priceCents: 'ASC' },
      skip: (page - 1) * pageSize,
      take: pageSize,
      select: { id: true, name: true, priceCents: true, category: { name: true } },
    });
  }

  // Query builder: aggregates and joins the repository API can't express
  stats() {
    return this.categories
      .createQueryBuilder('c')
      .leftJoin('c.products', 'p')
      .select('c.name', 'category')
      .addSelect('COUNT(p.id)::int', 'products')
      .addSelect('COALESCE(SUM(p.stock), 0)::int', 'unitsInStock')
      .groupBy('c.name')
      .orderBy('c.name')
      .getRawMany();
  }
}
EOF

import { CatalogService } from './catalog.service.js';

@Controller()
export class CatalogController {

}
```

<Happened>
<Tr>
<En>

- `save()` inserted rows and returned them with generated IDs; `findOne({ relations: { category: true } })` loaded the product with its category via a JOIN.
- The **database** rejected the bad data, and the service translated each SQLSTATE code: `23505` duplicate name → **409**, `23514` CHECK (price 0) → **400**, `23503` missing category → **400**. Even if validation in the API missed something, the data stays correct.
- **Paging**: Kitchen products sorted by price, two per page: page 1 has Spice Rack and Travel Mug, page 2 Teapot. `select` returned only the requested columns, so internal fields didn't leave the database.
- **Query builder**: one SQL query with a LEFT JOIN, `COUNT` and `SUM` grouped by category; the repository API can't express aggregates like this. `getRawMany()` returns plain rows with the aliases you chose.
- Values went into queries as **parameters** (`:productId`, `where` objects), never concatenated strings, which prevents SQL injection.

</En>
<Ur>

- `save()` ne rows insert kin aur bani IDs ke saath wapas kin; `findOne({ relations: { category: true } })` ne product ko us ki category ke saath JOIN se load kiya.
- **Database** ne kharab data radd kiya, aur service ne har SQLSTATE code ka tarjuma kiya: `23505` dohraya naam → **409**, `23514` CHECK (price 0) → **400**, `23503` ghayab category → **400**. API ki validation kuch chhor bhi de to data sahi rehta hai.

<Step title="Transactions and race-free stock updates">

<Tr>
<En>
`OrdersService.place()` runs inside `dataSource.transaction()`. It decrements stock with **one conditional UPDATE** (only if enough stock is left), then creates the order. The demo fires **six simultaneous orders** for a product with 4 in stock, then simulates a failure after the stock update to show the rollback.
</En>
<Ur>
`OrdersService.place()` `dataSource.transaction()` ke andar chalta hai. Ye **ek shart wale UPDATE** se stock ghatata hai (sirf jab kafi stock bacha ho), phir order banata hai. Demo 4 stock wale product ke liye **chhe orders ek saath** bhejta hai, phir rollback dikhane ke liye stock update ke baad nakami ka dikhawa karta hai.

```bash
cd shop-api
export DATABASE_URL=postgres://postgres:postgres@localhost:5432/shop_typeorm
cat > src/catalog/orders.service.ts <<'EOF'
import { ConflictException, Injectable } from '@nestjs/common';
import { DataSource } from 'typeorm';
import { Order, Product } from './entities.js';

@Injectable()
export class OrdersService {
  constructor(private readonly dataSource: DataSource) {}

  // Everything inside runs in ONE database transaction: all of it commits, or none of it does
  place(productId: number, quantity: number, failAfterStockUpdate = false) {
    return this.dataSource.transaction(async (manager) => {
      // Atomic, race-free stock check: the WHERE clause only matches if enough stock is left
      const result = await manager
        .createQueryBuilder()
        .update(Product)
        .set({ stock: () => `stock - ${Number(quantity)}` })
        .where('id = :productId AND stock >= :quantity', { productId, quantity })
        .returning('price_cents')
        .execute();
      if (result.affected === 0) throw new ConflictException('Not enough stock');

      if (failAfterStockUpdate) throw new Error('payment provider timeout');   // simulate a failure mid-way

      const priceCents = result.raw[0].price_cents as number;
      return manager.save(manager.create(Order, { product: { id: productId }, quantity, totalCents: priceCents * quantity }));
    });
  }
}
```

<En>

- **No overselling**: of six concurrent orders, exactly **4 succeeded** and 2 got "Not enough stock"; stock ended at **0**, never negative. - **Rollback**: the simulated payment failure happened **after** the stock update, inside the transaction. Stock stayed at 10 and no order was saved: everything in the callback was rolled back.

## Common mistakes

<Compare>
<Bad title="synchronize: true in production">

```text
TypeOrmModule.forRoot({ ..., synchronize: true })
// rename a property → TypeORM drops the old column and creates a new one: data gone
```

</Bad>
<Good title="Migrations reviewed and run on deploy">

```text
TypeOrmModule.forRoot({ ..., synchronize: false, migrations: ['dist/migrations/*.js'] })
// npx typeorm migration:generate src/migrations/RenameX -d dist/data-source.js   → review the SQL
// deploy: npx typeorm migration:run -d dist/data-source.js, then start the app
```

</Good>
</Compare>

<Compare>
<Bad title="Read-check-write in application code">

```text
const product = await repo.findOneBy({ id });
if (product.stock < qty) throw new ConflictException();
product.stock -= qty;
await repo.save(product);            // two requests at once: both pass the check
```

</Bad>
<Good title="One atomic statement in a transaction">

```text
const r = await manager.createQueryBuilder().update(Product)
  .set({ stock: () => `stock - ${Number(qty)}` })
  .where('id = :id AND stock >= :qty', { id, qty }).execute();
if (r.affected === 0) throw new ConflictException('Not enough stock');
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **N+1 queries**: loading a list, then each item's relation in a loop. Use `relations` or a join to load them in one query.
- **Returning entities with sensitive columns** (`passwordHash`) straight to clients: use `select`, response DTOs or serialisation.
- **String-concatenated SQL** in `query()` or `where` strings: always use parameters.
- **Forgetting indexes** on columns you filter or join by; check with `EXPLAIN`.
- **Eager relations everywhere** (`eager: true`): every query loads data you don't need.
- **Floating-point money columns**: use integer cents or `numeric`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **N+1 queries**: list load karna, phir loop me har item ka relation. Unhen ek query me load karne ke liye `relations` ya join lein.
- **Hassas columns wali entities** (`passwordHash`) seedha clients ko dena: `select`, response DTOs ya serialisation lein.
- `query()` ya `where` strings me **string jor kar bana SQL**: hamesha parameters lein.
- Jin columns se filter ya join karte hain un par **indexes bhoolna**; `EXPLAIN` se check karein.
- **Har jagah eager relations** (`eager: true`): har query aisa data load karti hai jo nahi chahiye.
- **Floating-point paise ke columns**: integer cents ya `numeric` lein.

</Ur>
</Tr>

<Tr>
<En>
This endpoint is slow with 500 orders. How many queries does it run, and how do you fix it?

```text
async listOrders() {
  const orders = await this.orders.find();

    o.product = await this.products.findOneByOrFail({ id: o.productId });
  }
```

<Ur>
Ye endpoint 500 orders ke saath sust hai. Ye kitni queries chalata hai, aur ise kaise theek karenge?

```text
async listOrders() {

    o.product = await this.products.findOneByOrFail({ id: o.productId });
  }
```

</Ur>

<Solution>

<Tr>
<En>

**501 queries**: one for the orders, then one per order for its product (the "N+1" pattern), each with a network round trip. Fix by loading the relation in the same query:

```text
return this.orders.find({ relations: { product: true }, take: 50, order: { id: 'DESC' } });
```

That's one query with a JOIN (and a page limit, because returning 500 rows at once is a second problem). If you need only some product fields, use `select`. For many-to-many or large child lists, TypeORM's `relationLoadStrategy: 'query'` runs one extra query per relation instead of per row.

</En>
<Ur>

**501 queries**: ek orders ke liye, phir har order ke product ke liye ek ("N+1" tareeqa), har ek network ke chakkar ke saath. Relation usi query me load kar ke theek karein:

```text
return this.orders.find({ relations: { product: true }, take: 50, order: { id: 'DESC' } });
```

Ye JOIN wali ek query hai (aur page ki hadd ke saath, kyun ke ek saath 500 rows lautana doosra masla hai). Agar product ke sirf kuch fields chahiyen to `select` lein. Many-to-many ya bari child lists ke liye TypeORM ka `relationLoadStrategy: 'query'` har row ke bajaye har relation par ek izafi query chalata hai.

</Ur>

<DeepDive title="More about TypeORM">

**Configuration from ConfigService.** `TypeOrmModule.forRootAsync({ inject: [ConfigService], useFactory: (c) => ({ ...c.getOrThrow('database'), autoLoadEntities: true }) })`.

**Isolation levels and locks.** `dataSource.transaction('SERIALIZABLE', …)` or `setLock('pessimistic_write')` (SELECT … FOR UPDATE) for read-then-write logic that can't be one statement.

**Optimistic locking.** `@VersionColumn()` increments on each save; a stale save fails, which suits edit forms where conflicts are rare.

**Soft deletes.** `@DeleteDateColumn()` with `softDelete()` keeps rows for audits; normal queries exclude them.

**Subscribers and listeners.** `@BeforeInsert()` or entity subscribers run logic on writes; keep business rules in services where they're visible.

**Testing.** Run repository tests against a real PostgreSQL (Testcontainers) and wrap each test in a rolled-back transaction; SQLite behaves differently enough to hide bugs.

</DeepDive>

<DeepDive title="Real world: the flash sale that sold 1,300 of 1,000">

An electronics retailer ran a flash sale for a game console: 1,000 units at a discount, starting at noon. The NestJS checkout service loaded the product, compared `product.stock >= quantity` in JavaScript, then saved `product.stock - quantity` with `repository.save()`. Under normal traffic, nobody had noticed a problem.

At noon, about 40,000 requests arrived in two minutes. Many requests read the same stock value before any of them wrote, so they all passed the check, and their saves overwrote each other. The database showed stock reaching 0 a few seconds in, but 1,312 orders had been confirmed and charged. The company had to cancel 312 orders, refund customers, and apologise publicly.

The fix was small:

1. The stock check and decrement became one statement inside the order transaction: `UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1`; zero affected rows meant "sold out".
2. A `CHECK (stock >= 0)` constraint was added as a safety net, so any future code path that tried to oversell would fail instead.
3. Payment capture moved after the order was reserved, and reservations expired after 10 minutes if payment didn't complete.
4. A load test with 500 concurrent buyers for 50 units ran in CI before every sale.

The next flash sale sold exactly its stock.

</DeepDive>

<DeepDive title="Security lens">

- **Parameterised queries only**; never build SQL from request input.
- **Least-privilege database users**: the app's user can read/write data but not drop tables; migrations run with a separate role.
- **Select only needed columns** and never return secrets stored in rows.
- **Scope queries by user or tenant** (`where: { id, ownerId: user.id }`) to prevent IDOR.
- **Don't expose database error messages**; map codes to safe responses and log details.
- **Encrypt connections** (`ssl: true`) to managed databases and keep credentials in a secrets manager.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you use TypeORM in NestJS?">
Configure the connection with TypeOrmModule.forRoot or forRootAsync, define entities with decorators, register them per module with TypeOrmModule.forFeature, inject repositories with @InjectRepository, and manage schema changes with migrations.
</QA>

<QA q="Why use migrations instead of synchronize?">
Migrations are explicit, reviewable SQL changes applied in order and recorded in the database, so they're safe to run in production and reproducible across environments; synchronize can make destructive changes automatically.
</QA>

<QA q="How do you prevent race conditions when decrementing stock?">
Use a single atomic conditional update such as UPDATE … SET stock = stock - n WHERE id = ? AND stock >= n and check the affected rows, within a transaction with the order insert, optionally backed by a CHECK constraint; or lock the row with SELECT … FOR UPDATE.
</QA>

<QA q="What is the N+1 query problem?">
Loading a list with one query and then running one additional query per item to load related data, causing many round trips; solve it by loading relations with joins or batched queries.
</QA>

<QA q="How do you run several writes atomically with TypeORM?">
Use dataSource.transaction with a callback and perform every query through the provided EntityManager, or a QueryRunner with startTransaction, commitTransaction and rollbackTransaction.
</QA>

</DeepDive>
