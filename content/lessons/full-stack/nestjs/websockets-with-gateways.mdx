<BigIdea>
<Tr>
<En>
HTTP is a conversation where the **client always speaks first**: it sends a request, the server answers, done. For chats, live order tracking, notifications or collaborative editing, the **server** needs to speak whenever something happens. A **WebSocket** keeps one connection open in both directions, so either side can send messages at any time. **Socket.IO** adds conveniences on top: automatic reconnection, named **events**, **acknowledgements** (a reply to a specific message), and **rooms** (groups of connections you can broadcast to). In Nest, a **gateway** is a class marked `@WebSocketGateway()`; its methods with **`@SubscribeMessage('event')`** handle incoming events, much like controller routes, and the injected **`@WebSocketServer()`** lets you emit to everyone, to a room, or to one socket. Gateways are providers, so **ordinary services can inject them** and push events when data changes, for example when an order's status is updated over HTTP. Security matters even more than with HTTP: **authenticate in the handshake**, validate every incoming message, and only let clients join rooms they're allowed to see.
</En>
<Ur>
HTTP aisi baat cheet hai jahan **client hamesha pehle bolta hai**: request bhejta hai, server jawab deta hai, khatam. Chats, live order tracking, notifications ya mil kar editing ke liye **server** ko jab bhi kuch ho bolna hota hai. **WebSocket** ek connection dono taraf khula rakhta hai, isliye koi bhi taraf kabhi bhi paighaam bhej sakti hai. **Socket.IO** is ke upar sahooliyat jorta hai: khud dobara connect hona, naam wale **events**, **acknowledgements** (kisi khaas paighaam ka jawab), aur **rooms** (connections ke groups jinhen broadcast kiya ja sake). Nest me **gateway** `@WebSocketGateway()` wali class hai; is ke **`@SubscribeMessage('event')`** wale methods aane wale events sambhalte hain, controller routes ki tarah, aur inject hua **`@WebSocketServer()`** sab ko, kisi room ko, ya ek socket ko emit karne deta hai. Gateways providers hain, isliye **aam services unhen inject kar sakti hain** aur data badalne par events bhej sakti hain, maslan jab HTTP par order ka status update ho. Security HTTP se bhi zyada ahem hai: **handshake me authenticate karein**, har aane wala paighaam validate karein, aur clients ko sirf un rooms me jane dein jinhen dekhne ki unhen ijazat hai.
</Ur>

</En>

## Picture it

<Tr>
<En>

Think of the difference between **sending letters** and a **phone conference line**.

- HTTP is **letters**: you write, wait for a reply, and nobody writes to you unless you wrote first.
- A WebSocket is an **open phone line**: once connected, either side can talk whenever they like.
- **Socket.IO rooms** are **breakout rooms** on the conference call: the support agent and the customer join "order 1001", and only people in that room hear what's said there.
- The **operator** checks your PIN before connecting you (handshake authentication); callers with a wrong PIN are disconnected immediately.
- When the **warehouse** updates a parcel's status, it can announce it straight into the order's room (a service emitting through the gateway).

</En>
<Ur>

**Khat bhejne** aur **phone conference line** ka farq sochein.

- HTTP **khat** hai: aap likhte hain, jawab ka intezar karte hain, aur koi aap ko nahi likhta jab tak aap ne pehle na likha ho.
- WebSocket **khuli phone line** hai: connect hone ke baad koi bhi taraf jab chahe baat kar sakti hai.
- **Socket.IO rooms** conference call ke **alag kamre** hain: support agent aur customer "order 1001" me shamil hote hain, aur sirf us kamre ke log wahan ki baat sunte hain.
- **Operator** jorne se pehle aap ka PIN check karta hai (handshake authentication); ghalat PIN wale callers foran kaat diye jate hain.
- Jab **warehouse** parcel ka status update kare, wo seedha order ke kamre me elaan kar sakta hai (gateway ke zariye emit karne wali service).

</Ur>
</Tr>

<Step title="A support chat with authentication, rooms and errors">

<Tr>
<En>
The `/support` gateway authenticates each connection from `handshake.auth.token` (a fixed map stands in for JWT verification), lets clients join a room per order, broadcasts messages to the room, and rejects invalid messages with `WsException`. A Node script plays four people: Eve with a stolen token, support agent Emma, customer Liam, and another customer Ava. Events from different sockets can arrive in any order, so the script prints each step's events sorted by person.
</En>
<Ur>
`/support` gateway har connection ko `handshake.auth.token` se authenticate karta hai (muqarrar map JWT verification ki jagah hai), clients ko har order ke room me jane deta hai, paighaam room me broadcast karta hai, aur ghalat paighaam `WsException` se radd karta hai. Node script chaar logon ka kirdar ada karta hai: churaye token wali Eve, support agent Emma, customer Liam, aur doosri customer Ava. Mukhtalif sockets ke events kisi bhi tarteeb me aa sakte hain, isliye script har qadam ke events shakhs ke hisaab se tarteeb de kar print karta hai.
</Ur>
</Tr>

```bash
npx -y @nestjs/cli@12.0.13 new shop-api --package-manager npm --skip-git --strict > /dev/null 2>&1
cd shop-api
npm install @nestjs/websockets@12.5.0 @nestjs/platform-socket.io@12.5.0 --silent

cat > src/chat.gateway.ts <<'EOF'
import {
  ConnectedSocket, MessageBody, OnGatewayConnection, OnGatewayDisconnect, SubscribeMessage,
  WebSocketGateway, WebSocketServer, WsException,
} from '@nestjs/websockets';
import type { Server, Socket } from 'socket.io';

// Stand-in for real token verification (JWT lesson)
const TOKENS: Record<string, string> = { 'token-emma': 'Emma', 'token-liam': 'Liam', 'token-ava': 'Ava' };

@WebSocketGateway({ namespace: '/support', cors: { origin: ['https://shop.example.com'] } })
export class SupportGateway implements OnGatewayConnection, OnGatewayDisconnect {
  @WebSocketServer() server: Server;

  // Authenticate during the handshake: reject before any message is handled
  handleConnection(client: Socket) {
    const name = TOKENS[client.handshake.auth?.token as string];
    if (!name) {
      client.emit('error_message', 'Unauthorized');
      return client.disconnect(true);
    }
    client.data.name = name;
  }

  handleDisconnect(client: Socket) {
    for (const room of client.data.rooms ?? []) this.server.to(room).emit('left', client.data.name);
  }

  @SubscribeMessage('join')
  join(@ConnectedSocket() client: Socket, @MessageBody() room: string) {
    client.join(room);
    client.data.rooms = [...(client.data.rooms ?? []), room];   // remembered for handleDisconnect
    client.to(room).emit('joined', client.data.name);           // everyone in the room except the sender
    return { joined: room };                                     // acknowledgement to the sender only
  }

  @SubscribeMessage('message')
  message(@ConnectedSocket() client: Socket, @MessageBody() body: { room: string; text: string }) {
    const text = String(body?.text ?? '').trim();
    if (!text || text.length > 500) throw new WsException('Message must be 1-500 characters');
    if (!client.rooms.has(body.room)) throw new WsException('Join the room first');
    this.server.to(body.room).emit('message', { from: client.data.name, text });   // everyone in the room
    return { delivered: true };
  }
}
EOF

import { io } from 'socket.io-client';

const URL = 'http://localhost:3000/support';
const ORDER = ['Eve', 'Emma', 'Liam', 'Ava'];
```

<Happened>
<Tr>
<En>

- **Handshake auth**: Eve's stolen token was rejected in `handleConnection`; she got one `error_message` and was disconnected before she could send anything. Authenticate here (or with a Socket.IO middleware) rather than in every handler.
- **Acknowledgements**: `emitWithAck('join', …)` received the handler's **return value** (`{ joined: … }`), the WebSocket equivalent of an HTTP response.
- **Rooms**: when Liam joined, `client.to(room)` told **Emma** (already in the room) but not Liam himself. His message went to **everyone in the room** with `server.to(room)`, including Liam, then he got his `delivered` acknowledgement.
- **Ava** isn't in the room, so her message was rejected with a `WsException`, which Socket.IO delivers as an **`exception`** event. Without this check, anyone could post into any order's chat just by knowing the room name.
- **Validation**: an empty message became an `exception` too. Notice that Nest echoes the original payload in `cause`; keep that in mind before sending sensitive data in messages (or use a custom WebSocket exception filter to shape the error).
- **Disconnect**: when Liam left, `handleDisconnect` told the rooms he had joined (`left`). Socket.IO removes sockets from rooms automatically; we only notify.

</En>
<Ur>

- **Handshake auth**: Eve ka churaya token `handleConnection` me radd hua; use ek `error_message` mila aur kuch bhejne se pehle hi disconnect kar di gayi. Har handler ke bajaye yahan (ya Socket.IO middleware se) authenticate karein.
- **Acknowledgements**: `emitWithAck('join', …)` ko handler ki **return value** (`{ joined: … }`) mili, jo HTTP response ka WebSocket wala roop hai.
- **Rooms**: jab Liam shamil hua, `client.to(room)` ne **Emma** ko bataya (jo pehle se room me thi) magar khud Liam ko nahi. Us ka paighaam `server.to(room)` se **room ke har shakhs** tak gaya, Liam samet, phir use apna `delivered` acknowledgement mila.
- **Ava** room me nahi, isliye us ka paighaam `WsException` ke saath radd hua, jise Socket.IO **`exception`** event ki shakal me pohanchata hai. Is check ke baghair koi bhi sirf room ka naam jaan kar kisi bhi order ki chat me likh sakta tha.
- **Validation**: khaali paighaam bhi `exception` bana. Dekhein ke Nest asal payload `cause` me wapas bhejta hai; paighaamon me hassas data bhejne se pehle ye yaad rakhein (ya error ki shakal dene ke liye custom WebSocket exception filter lein).
- **Disconnect**: jab Liam gaya, `handleDisconnect` ne un rooms ko bataya jin me wo shamil tha (`left`). Socket.IO sockets ko rooms se khud nikal deta hai; hum sirf ittila dete hain.

</Ur>
</Tr>

<Step title="Pushing events from an HTTP endpoint">

<Tr>
<En>
`OrdersService` injects the gateway and emits `order_status` into an order's room whenever the status changes. An HTTP `PATCH` endpoint triggers it. Liam's client watches order 1001; we send three status updates for it and one for another order.
</En>
<Ur>
`OrdersService` gateway inject karti hai aur status badalne par order ke room me `order_status` emit karti hai. HTTP `PATCH` endpoint ise chalata hai. Liam ka client order 1001 dekhta hai; hum is ke teen status updates aur ek doosre order ka update bhejte hain.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/orders.ts <<'EOF'
import { Body, Controller, Injectable, Module, Param, ParseIntPipe, Patch } from '@nestjs/common';
import { SupportGateway } from './chat.gateway.js';

// A normal service pushes events to connected clients through the gateway's server
@Injectable()
export class OrdersService {
  constructor(private readonly gateway: SupportGateway) {}
  updateStatus(orderId: number, status: string) {
    this.gateway.server.to(`order-${orderId}`).emit('order_status', { orderId, status });
    return { orderId, status };
  }
}

@Controller('orders')
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}
  @Patch(':id/status')
  update(@Param('id', ParseIntPipe) id: number, @Body('status') status: string) {
    return this.orders.updateStatus(id, status);
  }
}
EOF
cat > src/app.module.ts <<'EOF'
import { Module } from '@nestjs/common';
import { SupportGateway } from './chat.gateway.js';
import { OrdersController, OrdersService } from './orders.js';

@Module({ controllers: [OrdersController], providers: [SupportGateway, OrdersService] })
export class AppModule {}
EOF
```

<Tr>
<En>

- Each `PATCH` updated the order and **pushed** the change to Liam instantly, without Liam asking: no polling.
- The update for order **2002** went to room `order-2002`, where nobody was listening, so Liam didn't receive it.
- The gateway is just a provider: `OrdersService` injected it like any other service. In bigger apps, emit domain events (`order.status_changed`) with `@nestjs/event-emitter` or a queue, and let the gateway listen, so the orders module doesn't depend on the WebSocket layer.
- This demo's `PATCH` endpoint and the `join` handler have no authorisation: in a real app, only staff may change statuses, and a customer may only join rooms for **their own** orders (check ownership in `join`).

</En>
<Ur>

- Har `PATCH` ne order update kiya aur tabdeeli Liam ko foran **push** ki, Liam ke pooche baghair: koi polling nahi.
- Order **2002** ka update room `order-2002` me gaya, jahan koi nahi sun raha tha, isliye Liam ko nahi mila.
- Gateway bas ek provider hai: `OrdersService` ne ise kisi bhi service ki tarah inject kiya. Bari apps me `@nestjs/event-emitter` ya queue se domain events (`order.status_changed`) emit karein aur gateway ko sunne dein, taa ke orders module WebSocket tabqe par munhasir na ho.
- Is demo ke `PATCH` endpoint aur `join` handler me koi authorisation nahi: asli app me sirf staff status badal sakta hai, aur customer sirf **apne** orders ke rooms me shamil ho sakta hai (`join` me malkiyat check karein).

## Common mistakes

<Compare>
<Bad title="Trusting the room name from the client">

```text
@SubscribeMessage('join')
join(@ConnectedSocket() c: Socket, @MessageBody() room: string) {
  c.join(room);                 // "order-1" … "order-99999": anyone can listen to every order
}
```

</Bad>
<Good title="Check access before joining">

```text
@SubscribeMessage('join')
async join(@ConnectedSocket() c: Socket, @MessageBody() orderId: number) {
  const order = await this.orders.findForUser(c.data.user, orderId);   // throws if not theirs
  c.join(`order-${order.id}`);
  return { joined: order.id };
}
```

</Good>

<Tr>
<En>

More mistakes to avoid:

- **No validation of message payloads**: use DTOs with `ValidationPipe` on gateways (`@UsePipes(new ValidationPipe())`).
- **Running several instances without the Redis adapter**: users on different servers can't see each other's room messages.
- **CORS `origin: '*'`** for authenticated sockets; allow your front-end origins only.
- **Unbounded messages and connections**: limit message size (`maxHttpBufferSize`), rate-limit events, and cap connections per user.
- **Using WebSockets for everything**: request/response operations (load a page of orders) are simpler and cacheable over HTTP.
- **Assuming delivery**: clients disconnect; persist important messages and let clients fetch missed ones after reconnecting.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Paighaam ke payloads ki validation nahi**: gateways par `ValidationPipe` ke saath DTOs lein (`@UsePipes(new ValidationPipe())`).

- **Har cheez ke liye WebSockets**: request/response wale kaam (orders ka page load karna) HTTP par zyada saade aur cache hone qabil hain.

<Challenge title="Typing indicators">

<Tr>
<En>
Add a `typing` event: when a user starts typing in a room, everyone **else** in the room receives `{ user, typing: true }`; when they stop (or send the message), `typing: false`. The server must ignore `typing` events for rooms the socket hasn't joined, and never send the event back to the sender.
</En>
<Ur>
`typing` event jorein: jab user room me type karna shuru kare, room me **baqi** sab ko `{ user, typing: true }` mile; jab ruke (ya paighaam bheje), `typing: false`. Server un rooms ke `typing` events nazar andaz kare jin me socket shamil nahi, aur event kabhi bhejne wale ko wapas na bheje.
</Ur>
</Tr>

<Solution>

```text
@SubscribeMessage('typing')
typing(@ConnectedSocket() client: Socket, @MessageBody() body: { room: string; typing: boolean }) {
  if (!client.rooms.has(body?.room)) return;                         // silently ignore: not a member
  client.to(body.room).emit('typing', { user: client.data.name, typing: Boolean(body.typing) });
}
```

<Tr>
<En>
`client.to(room)` excludes the sender, unlike `server.to(room)`. On the client, emit `typing: true` on the first keystroke and `typing: false` after a pause (debounce about 2 seconds) or on send. Typing events are frequent and unimportant, so they're a good candidate for Socket.IO's `volatile` emits (dropped if the client isn't ready) and a per-socket rate limit.
</En>
<Ur>
`server.to(room)` ke bar-aks `client.to(room)` bhejne wale ko shamil nahi karta. Client par pehle key dabane par `typing: true` aur waqfe ke baad (taqreeban 2 second debounce) ya bhejne par `typing: false` emit karein. Typing events aksar aate aur kam ahem hain, isliye ye Socket.IO ke `volatile` emits (client tayyar na ho to chhor diye jate hain) aur har socket ki rate limit ke liye achhe umeedwar hain.
</Ur>
</Tr>

<Challenge title="Scale to three servers">

<Tr>
<En>
The app now runs on three instances behind a load balancer. Liam is connected to server A and Emma to server B. What breaks, and what do you change?
</En>
<Ur>
App ab load balancer ke peeche teen instances par chalti hai. Liam server A se juda hai aur Emma server B se. Kya tootta hai, aur aap kya badlenge?
</Ur>
</Tr>

<Solution>

<Tr>
<En>

- **Rooms are per process**: `server.to('order-1001')` on server A only reaches sockets connected to A, so Emma on B never sees Liam's messages. HTTP-triggered status pushes hit whichever server handled the `PATCH`.
- **Fix**: use the **Socket.IO Redis adapter** (`@socket.io/redis-adapter`) via a custom `IoAdapter` in Nest; emits are published through Redis and delivered by every instance to its local sockets.
- **Sticky sessions**: Socket.IO's HTTP long-polling fallback needs each client to keep hitting the same server; enable sticky sessions on the load balancer, or force the `websocket` transport.
- Also plan for **reconnects** during deploys (clients reconnect to other instances and must re-join rooms) and persist messages so nothing is lost.

</En>
<Ur>

- **Rooms har process ke hain**: server A par `server.to('order-1001')` sirf A se jure sockets tak pohanchta hai, isliye B par Emma kabhi Liam ke paighaam nahi dekhti. HTTP se chalne wale status push us server se jate hain jis ne `PATCH` sambhala.
- **Hal**: Nest me custom `IoAdapter` ke zariye **Socket.IO Redis adapter** (`@socket.io/redis-adapter`) lein; emits Redis ke zariye shaya hote hain aur har instance unhen apne local sockets tak pohanchata hai.
- **Sticky sessions**: Socket.IO ke HTTP long-polling fallback ke liye har client ko usi server tak jana hota hai; load balancer par sticky sessions on karein, ya `websocket` transport lazmi karein.
- Deploys ke dauran **dobara connect** hone ka bhi socho (clients doosre instances se jurte hain aur rooms me dobara shamil hona parta hai) aur paighaam mehfooz karein taa ke kuch zaya na ho.

## Remember

<Takeaways>
<Tr>
<En>

- WebSockets keep a two-way connection open; Socket.IO adds events, acks, rooms and reconnection.
- A gateway handles events with `@SubscribeMessage`; returning a value acknowledges the sender.
- Authenticate in `handleConnection`; store the user on `client.data`.
- Use rooms for groups; `server.to(room)` includes the sender, `client.to(room)` excludes it.

- Services can inject the gateway to push updates; use the Redis adapter when running several instances.

<DeepDive title="More about gateways">

**Guards, pipes and filters.** `@UseGuards()`, `@UsePipes(new ValidationPipe())` and `@UseFilters()` work on gateway handlers; use `context.switchToWs().getClient()` inside them and throw `WsException`.

**Socket.IO middleware.** `afterInit(server)` can register `server.use((socket, next) => …)` to authenticate before `handleConnection`.

**Plain `ws`.** `@nestjs/platform-ws` uses the lightweight `ws` library (no rooms or acks built in) when you need raw WebSockets or a non-Socket.IO client.

**Server-Sent Events.** For one-way streams, `@Sse('events')` returning an Observable is simpler, works over plain HTTP and reconnects automatically in browsers.

**Message delivery.** Socket.IO offers acknowledgements and connection state recovery, but "exactly once" delivery needs persistence: store messages with IDs and let clients request what they missed.

**Testing.** Start the app on a random port in tests and connect with `socket.io-client`, as the demo script does.

</DeepDive>

<DeepDive title="Real world: the order tracker that leaked addresses">

A food delivery startup added live tracking: when a courier's position changed, the API emitted `courier_location` to a room named after the order, and the customer's app joined `order-<id>` with a `join` event. Order IDs were sequential. Authentication was checked at connection, so only logged-in users could connect.

A user noticed in the app's network traffic that joining a room was a simple `join` with the order number. A short script connected once with their own account and joined `order-1` to `order-50000`. It received live courier positions and, because the event payload included the delivery address for the courier app's convenience, the home addresses of thousands of customers in real time.

The fixes:

1. `join` loaded the order and checked that the user was its customer, its courier or support staff; otherwise it threw `WsException('Not found')`.
2. Room names used random order UUIDs instead of sequential numbers (defence in depth, not a replacement for the check).
3. Payloads were split by audience: customers received only the courier's approximate position and ETA; addresses were never sent to customer rooms.
4. A rate limit on `join` events per socket and alerts on unusual join patterns were added.

Authentication answered "who are you?"; the bug was that nobody asked "may you listen to this room?".

</DeepDive>

<DeepDive title="Security lens">

- **Authenticate the handshake** and disconnect unauthenticated sockets.
- **Authorise every room join and action**, just like HTTP endpoints (BOLA applies to WebSockets too).
- **Validate and size-limit every message**; rate-limit events per socket.
- **Restrict CORS origins** and use `wss://` (TLS) in production.
- **Send each audience only the data it needs**; rooms are not access control by themselves.
- **Re-check permissions on long-lived connections** when roles change or tokens expire.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between HTTP and WebSockets?">
HTTP is request-response, with the client initiating every exchange; WebSockets upgrade an HTTP connection to a persistent, full-duplex channel where both client and server can send messages at any time with low overhead.
</QA>

<QA q="How do you implement WebSockets in NestJS?">
Create a gateway class with @WebSocketGateway, handle events with @SubscribeMessage methods using @MessageBody and @ConnectedSocket, emit through the @WebSocketServer instance, implement lifecycle interfaces such as OnGatewayConnection, and register the gateway as a provider.
</QA>

<QA q="What are rooms in Socket.IO?">
Server-side groups of sockets; sockets join or leave rooms, and the server can emit to all sockets in a room, which is used for chats, per-resource updates and multi-tenant channels.
</QA>

<QA q="How do you authenticate WebSocket connections?">
Send a token in the handshake (Socket.IO auth payload or a cookie), verify it in a Socket.IO middleware or handleConnection, attach the user to the socket, disconnect on failure, and authorise each room join and action.
</QA>

<QA q="How do you scale Socket.IO to multiple servers?">
Use an adapter such as the Redis adapter so events and room broadcasts are shared across instances, and configure sticky sessions if the polling transport is used.
</QA>

</DeepDive>
