<BigIdea>
<Tr>
<En>
A **SaaS** product like a project tracker or an online store builder serves many customer companies, called **tenants**, from one running app. Each tenant must see **only its own data**, as if it had the app to itself. You can separate data three ways: **shared tables with a `tenant_id` column** (cheapest, most common), a **schema per tenant**, or a **database per tenant** (strongest isolation, most work). In NestJS you **resolve the tenant once per request** (from the subdomain, a header, or the signed-in user's token) in middleware, check it exists, and keep it in **`AsyncLocalStorage`** so any service can read it without passing it around. Every query then filters by that tenant, and the tenant for new rows comes from the context, **never from the request body**. Because one forgotten `WHERE tenant_id = …` exposes every customer's data, add a second line of defense: **PostgreSQL Row-Level Security (RLS)**, where the database itself only returns and accepts rows for the tenant set on the current transaction.
</En>
<Ur>
Project tracker ya online store builder jaisa **SaaS** product ek chalti app se bohot si customer companies ko serve karta hai, jinhen **tenants** kehte hain. Har tenant ko **sirf apna data** dikhna chahiye, jaise app sirf usi ki ho. Data teen tareeqon se alag kar sakte hain: **`tenant_id` column wale mushtarka tables** (sab se sasta, sab se aam), **har tenant ka schema**, ya **har tenant ka database** (sab se mazboot alagi, sab se zyada kaam). NestJS me aap middleware me **har request par ek dafa tenant pehchante** hain (subdomain, header, ya sign-in user ke token se), check karte hain ke wo mojood hai, aur use **`AsyncLocalStorage`** me rakhte hain taa ke koi bhi service use aage pass kiye baghair parh sake. Phir har query us tenant se filter hoti hai, aur naye rows ka tenant context se aata hai, **request body se kabhi nahi**. Kyunke ek bhoola hua `WHERE tenant_id = …` har customer ka data khol deta hai, defense ki doosri line jorein: **PostgreSQL Row-Level Security (RLS)**, jahan database khud sirf mojooda transaction par set tenant ki rows lautata aur qubool karta hai.
</Ur>
</Tr>
</BigIdea>

## Picture it

<Tr>
<En>

Think of an **apartment building**.

- Every family (**tenant**) shares the building, the lift and the plumbing (one app, one database), which keeps rent low.
- At the entrance, the **doorman** checks which apartment you belong to (tenant middleware) and gives you a key card for that floor (the tenant context).
- Inside, every door you open checks the card (`WHERE tenant_id = …`).
- **Row-Level Security** is the **lock on each apartment door**: even if the doorman makes a mistake or a staff member walks the wrong corridor (a forgotten filter), the door simply won't open.
- A few wealthy families want a **house of their own** (database per tenant): more privacy, much more cost.

</En>
<Ur>

**Apartment building** ka sochein.

- Har khandan (**tenant**) building, lift aur plumbing baant'ta hai (ek app, ek database), jis se kiraya kam rehta hai.
- Darwaze par **chowkidar** check karta hai ke aap kis apartment ke hain (tenant middleware) aur us manzil ka key card deta hai (tenant context).
- Andar har darwaza card check karta hai (`WHERE tenant_id = …`).
- **Row-Level Security** **har apartment ke darwaze ka taala** hai: chahe chowkidar ghalti kare ya koi mulazim ghalat rahdari me chala jaye (bhoola filter), darwaza khulega hi nahi.
- Kuch ameer khandan **apna ghar** chahte hain (har tenant ka database): zyada privacy, kahin zyada kharcha.

</Ur>
</Tr>

```bash
import { AsyncLocalStorage } from 'node:async_hooks';

// Holds the current tenant for everything that runs during one request
export const tenantContext = new AsyncLocalStorage<{ tenantId: string }>();

export function currentTenant(): string {
  const ctx = tenantContext.getStore();
  if (!ctx) throw new Error('No tenant in context');   // fail closed, never "all tenants"
  return ctx.tenantId;
}
EOF

import { BadRequestException, Injectable, NestMiddleware, NotFoundException } from '@nestjs/common';
import type { NextFunction, Request, Response } from 'express';
import { Db } from './db.js';
import { tenantContext } from './tenant-context.js';

@Injectable()
export class TenantMiddleware implements NestMiddleware {
  constructor(private readonly db: Db) {}

  async use(req: Request, _res: Response, next: NextFunction) {
    // Real apps take this from the subdomain (acme.example.com) or the signed-in user's token
    const tenantId = req.header('x-tenant-id');
    if (!tenantId) return next(new BadRequestException('Missing tenant'));
    const [tenant] = await this.db.query('SELECT id FROM tenants WHERE id = $1', [tenantId]);
    if (!tenant) return next(new NotFoundException('Unknown tenant'));
    tenantContext.run({ tenantId }, () => next());
  }
}

import { Db } from './db.js';
import { currentTenant } from './tenant-context.js';

@Controller()
export class ProjectsController {
  constructor(private readonly db: Db) {}

  @Get('projects')
  list() {
    return this.db.query('SELECT id, name FROM projects WHERE tenant_id = $1 ORDER BY id', [currentTenant()]);
  }

  @Get('projects/:id')
  async one(@Param('id', ParseIntPipe) id: number) {
    const [p] = await this.db.query('SELECT id, name FROM projects WHERE id = $1 AND tenant_id = $2', [id, currentTenant()]);

    return p;
```

<Step title="Row-Level Security as a safety net">

<Tr>
<En>
Now the database enforces isolation. We create a normal role `app_user` (superusers bypass RLS), enable and **force** RLS on `projects`, and add a policy comparing `tenant_id` with the setting `app.tenant_id`. The `Db` service runs each query in a transaction that first calls `set_config('app.tenant_id', <tenant>, true)`. The buggy report code is **unchanged**.
</En>
<Ur>
Ab database alagi nafiz karta hai. Hum aam role `app_user` banate hain (superusers RLS chhor dete hain), `projects` par RLS on aur **force** karte hain, aur aisi policy jorte hain jo `tenant_id` ko `app.tenant_id` setting se milati hai. `Db` service har query aise transaction me chalati hai jo pehle `set_config('app.tenant_id', <tenant>, true)` bulata hai. Ghalti wala report code **wahi** hai.
</Ur>
</Tr>

```bash
cd saas-api
export PGPASSWORD=postgres
# The app connects as a normal role (superusers and table owners skip RLS unless forced)
psql -q -h localhost -U postgres -d saas <<'SQL' 2> /dev/null
DROP ROLE IF EXISTS app_user;
CREATE ROLE app_user LOGIN PASSWORD 'app_pass';
GRANT SELECT ON tenants TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON projects TO app_user;
GRANT USAGE ON SEQUENCE projects_id_seq TO app_user;
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
ALTER TABLE projects FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON projects
  USING      (tenant_id = current_setting('app.tenant_id', true))    -- which rows you can see
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true));   -- which rows you can write
SQL
cat > src/db.ts <<'EOF'
import { Injectable, OnModuleDestroy } from '@nestjs/common';
import { Pool } from 'pg';
import { tenantContext } from './tenant-context.js';

@Injectable()
export class Db implements OnModuleDestroy {
  readonly pool = new Pool({ connectionString: process.env.DATABASE_URL ?? 'postgres://postgres:postgres@localhost:5432/saas' });

  // Every query runs in a transaction that tells PostgreSQL the current tenant
  async query(sql: string, params: unknown[] = []) {
    const client = await this.pool.connect();
    try {
      await client.query('BEGIN');
      const tenantId = tenantContext.getStore()?.tenantId ?? '';
      await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);   // true = this transaction only
      const { rows } = await client.query(sql, params);
      await client.query('COMMIT');
      return rows;
    } catch (err) {
      await client.query('ROLLBACK');
      throw err;
    } finally {
      client.release();
    }
  }
  onModuleDestroy() { return this.pool.end(); }
}
EOF
```

<Tr>
<En>

- The same buggy report now returned **3** for Acme and **1** for Globex: PostgreSQL silently added the policy to the query, so the forgotten filter no longer leaks.
- With **no tenant set**, `SELECT count(*)` returned **0**: RLS fails closed. A background job that forgets to set the tenant sees nothing instead of everything.
- Writing a Globex row while acting as Acme was **rejected** by the `WITH CHECK` part of the policy.
- `set_config(..., true)` applies to the **current transaction only**. That matters with connection pools: a plain `SET` would stay on the pooled connection and leak into the next request, possibly for another tenant.
- RLS doesn't replace the `WHERE tenant_id` filters (they help indexes and make intent clear); it catches the mistakes. Remember that superusers and, unless forced, table owners **bypass** RLS, so the app must connect as a normal role.

</En>
<Ur>

- Wahi ghalti wali report ab Acme ke liye **3** aur Globex ke liye **1** lautati hai: PostgreSQL ne khamoshi se policy query me jor di, isliye bhoola filter ab leak nahi karta.
- **Koi tenant set na hone** par `SELECT count(*)` ne **0** lautaya: RLS band ho kar nakam hota hai. Tenant set karna bhoolne wali background job sab kuch ke bajaye kuch nahi dekhti.
- Acme ban kar Globex ki row likhna policy ke `WITH CHECK` hisse ne **rad** kar diya.
- `set_config(..., true)` **sirf mojooda transaction** par lagta hai. Connection pools ke saath ye ahem hai: saada `SET` pooled connection par reh jata aur agli request me, shayad kisi aur tenant ki, risat.
- RLS `WHERE tenant_id` filters ki jagah nahi leta (wo indexes me madad karte aur irada wazeh karte hain); ye ghaltiyan pakarta hai. Yaad rahe ke superusers aur, force na ho to, table owners RLS **chhor** dete hain, isliye app ko aam role se connect karna chahiye.

</Ur>

## Common mistakes

<Compare>
<Bad title="Trusting the tenant from the client">

```text
@Post('projects')
create(@Body() body) {
  return this.db.query('INSERT INTO projects (tenant_id, name) VALUES ($1, $2)', [body.tenantId, body.name]);
}
```

</Bad>
<Good title="Tenant from the verified context">

```text
@Post('projects')
create(@Body() body: CreateProjectDto) {
  return this.db.query('INSERT INTO projects (tenant_id, name) VALUES ($1, $2)', [currentTenant(), body.name]);
}
```

</Good>

<Bad title="Session-wide setting on a pooled connection">

```text
await pool.query(`SET app.tenant_id = '${tenantId}'`);   // stays on the connection, and it's SQL injection
const rows = await pool.query('SELECT * FROM projects'); // may even run on a different connection
```

</Bad>
<Good title="Transaction-local setting on one client">

```text
const client = await pool.connect();
await client.query('BEGIN');
await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);
const { rows } = await client.query('SELECT * FROM projects');
await client.query('COMMIT'); client.release();
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Caches and queues without the tenant**: cache keys, job payloads, file paths and search indexes all need the tenant ID too.
- **Unique constraints without the tenant**: `UNIQUE (email)` stops two companies from having the same user email; use `UNIQUE (tenant_id, email)`.
- **Background jobs with no tenant context**: wrap each job in `tenantContext.run({ tenantId: job.data.tenantId }, …)`.
- **Trusting a subdomain or header without checking the user belongs to that tenant**: a user of Acme must not access `globex.example.com` with their Acme token.
- **No tests for isolation**: add e2e tests that log in as tenant A and try to read, update and delete tenant B's records.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Tenant ke baghair caches aur queues**: cache keys, job payloads, file paths aur search indexes sab ko bhi tenant ID chahiye.
- **Tenant ke baghair unique constraints**: `UNIQUE (email)` do companies ko ek jaisi user email rakhne se rokta hai; `UNIQUE (tenant_id, email)` lein.
- **Tenant context ke baghair background jobs**: har job ko `tenantContext.run({ tenantId: job.data.tenantId }, …)` me lapeten.
- **Ye check kiye baghair subdomain ya header par bharosa ke user usi tenant ka hai**: Acme ka user apne Acme token se `globex.example.com` tak na pahunche.
- **Alagi ke tests nahi**: tenant A ban kar log in karne wale aur tenant B ke records parhne, badalne aur mitane ki koshish karne wale e2e tests jorein.

</Ur>

<DeepDive title="More about multi-tenancy">

**Tenant from the token.** After login, put the tenant ID in the JWT and resolve the tenant from it; if you also use subdomains, check they match.

**ORMs.** With TypeORM or Prisma, wrap each request's work in a transaction that sets `app.tenant_id` first (Prisma client extensions or a TypeORM `QueryRunner`), or use a library such as `nestjs-cls` to carry the context.

**Schema per tenant.** Set `search_path` per transaction (`SET LOCAL search_path = tenant_acme`); migrations must run for every schema.

**Database per tenant.** Keep a tenant registry with connection details, create pools lazily and cap them; watch total connection counts.

**Fairness.** Per-tenant rate limits, query timeouts and job queue priorities keep one tenant from slowing everyone.

**Data export and deletion.** Tenants leave: be able to export all their data and delete it everywhere (DB, caches, files, backups policy).

</DeepDive>

<DeepDive title="Real world: the support dashboard query">

A B2B analytics company used shared tables with `tenant_id` filters in a repository layer. Every endpoint went through it, and isolation tests passed.

An engineer added an internal "top customers by events" query for the support team and, to reuse code, exposed a variant on the customer dashboard behind a feature flag. The variant called a raw query helper that skipped the repository. When the flag was turned on for a beta group, beta customers saw a leaderboard containing other companies' names and event volumes.

A customer reported it within an hour. The fix and follow-up:

1. The flag was turned off, and the raw helper removed from customer-facing code.
2. RLS was enabled on all tenant tables, with the app connecting as a non-owner role and setting `app.tenant_id` per transaction. Internal support tools got a separate role with an explicit, audited bypass.
3. A test helper ran every e2e test twice, as two tenants, and failed if any response contained the other tenant's IDs.
4. The incident was disclosed to affected customers, as their contracts required.

</DeepDive>

<DeepDive title="Security lens">

- **Authorization is per tenant**: check both "is this user in this tenant?" and "what role do they have there?".
- **Fail closed**: missing tenant context should mean no data, never all data.
- **Separate roles**: the app's database role can't bypass RLS; admin tools use a different, audited role.
- **Encryption keys per tenant** for highly sensitive data, so one tenant's key leak doesn't expose others.
- **Log the tenant ID** on every request and audit event so you can investigate who accessed what.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the main multi-tenant data models?">
Shared database and tables with a tenant ID column, a separate schema per tenant in one database, and a separate database per tenant. They trade cost and operational simplicity against isolation strength, per-tenant backups and data residency.
</QA>

<QA q="How would you pass the current tenant through a NestJS request?">
Resolve it in middleware from the subdomain, header or token, validate it, and store it in AsyncLocalStorage (or a library like nestjs-cls) for the duration of the request. Request-scoped providers also work but make the whole dependency chain request-scoped and slower.
</QA>

<QA q="What is PostgreSQL Row-Level Security and how does it help?">
RLS attaches policies to a table that filter which rows a session can read (USING) and write (WITH CHECK). With a policy comparing tenant_id to a per-transaction setting, the database enforces isolation even if application code forgets a filter.
</QA>

<QA q="What are the pitfalls of RLS with connection pools?">
Settings made with a plain SET persist on the connection and can leak to the next request; use transaction-local settings. Also, superusers and table owners bypass RLS unless it's forced, so the app must use a normal role.
</QA>

<QA q="Besides the database, where can tenant data leak?">
Caches, search indexes, file storage paths, queued jobs, logs, analytics events, emails sent to the wrong tenant's users, and unique constraints that span tenants. Each needs the tenant ID included and checked.
</QA>

</DeepDive>
