<BigIdea>
<Tr>
<En>
An API is only as useful as its documentation, and hand-written docs drift out of date the moment someone adds a field. **OpenAPI** (formerly Swagger) is a standard **JSON/YAML description** of an HTTP API: every path, method, parameter, request body, response and authentication scheme, with schemas for the data. Tools read it to render **interactive docs** (Swagger UI, Redoc), generate **client SDKs and types**, run contract tests and import into Postman. **`@nestjs/swagger`** builds this document **from your code**: routes come from controllers, body and response shapes come from DTO classes, and decorators like `@ApiTags`, `@ApiOkResponse`, `@ApiBearerAuth` and `@ApiProperty({ example })` add what code alone can't say. The **CLI plugin** goes further: it reads TypeScript types, class-validator rules and comments at compile time, so most `@ApiProperty` decorators become unnecessary. Because the docs are generated from the same classes that validate requests, they stay accurate, and a front end can generate its types from them instead of guessing.
</En>
<Ur>
API utni hi kaam ki hai jitni us ki documentation, aur haath se likhi docs us lamhe purani ho jati hain jab koi field jorta hai. **OpenAPI** (pehle Swagger) HTTP API ki mayaari **JSON/YAML tafseel** hai: har path, method, parameter, request body, response aur authentication ka tareeqa, data ke schemas ke saath. Tools ise parh kar **interactive docs** (Swagger UI, Redoc) dikhate hain, **client SDKs aur types** banate hain, contract tests chalate hain aur Postman me import karte hain. **`@nestjs/swagger`** ye document **aap ke code se** banata hai: routes controllers se, body aur response ki shaklein DTO classes se aati hain, aur `@ApiTags`, `@ApiOkResponse`, `@ApiBearerAuth` aur `@ApiProperty({ example })` jaise decorators wo jorte hain jo akela code nahi keh sakta. **CLI plugin** aur aage jata hai: ye compile time par TypeScript types, class-validator ke qawaid aur comments parhta hai, isliye zyada tar `@ApiProperty` decorators ki zaroorat nahi rehti. Kyun ke docs unhi classes se banti hain jo requests validate karti hain, wo durust rehti hain, aur front end andaze lagane ke bajaye un se apni types bana sakta hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **restaurant menu** printed straight from the kitchen's recipe system.

- Every dish on the menu (endpoint) appears automatically when the chef adds a recipe (controller method), with its ingredients (request body) and what arrives on the plate (response).
- Notes like "spicy", "contains nuts", "ask for the wine list" (examples, enums, auth) are added by the chef on the recipe card, so they're never forgotten on the menu.
- Because the menu is generated from the recipes, it can't list a dish that doesn't exist or miss a new one, unlike a menu someone retypes every season.
- Delivery apps (front ends, partners) import the same menu to build their ordering screens (generated types and SDKs).

</En>
<Ur>

Kitchen ke recipe system se seedha chhapne wale **restaurant menu** ka sochein.

- Menu par har dish (endpoint) khud aa jati hai jab chef recipe jorta hai (controller method), us ke ajza (request body) aur plate par aane wali cheez (response) ke saath.
- "Teekha", "moongphali shamil", "wine list maangein" jaise notes (examples, enums, auth) chef recipe card par jorta hai, isliye menu par kabhi nahi bhoolte.
- Kyun ke menu recipes se banta hai, ye na koi ghair maujood dish dikha sakta hai na nayi chhor sakta hai, us menu ke bar-aks jo koi har mausam dobara type karta hai.
- Delivery apps (front ends, partners) apni order screens banane ke liye wahi menu import karti hain (bani hui types aur SDKs).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Swagger UI and a documented controller">

<Tr>
<En>
We document a products API: DTOs with `@ApiProperty` (examples, lengths, an enum and a default), an update DTO built with `PartialType` from `@nestjs/swagger`, a controller with tags, response types, a 404 and bearer auth, and the Swagger setup in `main.ts`. Then we download `/docs-json` and print a summary of every operation.
</En>
<Ur>
Hum products API document karte hain: `@ApiProperty` wale DTOs (examples, lambai, enum aur default), `@nestjs/swagger` ke `PartialType` se bana update DTO, tags, response types, 404 aur bearer auth wala controller, aur `main.ts` me Swagger setup. Phir `/docs-json` download kar ke har operation ka khulasa print karte hain.
</Ur>
</Tr>

```bash
npx -y @nestjs/cli@12.0.13 new shop-api --package-manager npm --skip-git --strict > /dev/null 2>&1
cd shop-api
npm install @nestjs/swagger@12.1.2 class-validator@0.15.1 class-transformer@0.5.1 --silent
mkdir -p src/products
cat > src/products/product.dto.ts <<'EOF'
import { ApiProperty, ApiPropertyOptional, PartialType } from '@nestjs/swagger';
import { IsIn, IsInt, IsOptional, IsPositive, IsString, Length } from 'class-validator';

export class CreateProductDto {
  @ApiProperty({ example: 'Travel Mug', minLength: 2, maxLength: 100 })
  @IsString() @Length(2, 100)
  name: string;

  @ApiProperty({ example: 2400, description: 'Price in cents' })
  @IsInt() @IsPositive()
  priceCents: number;

  @ApiPropertyOptional({ enum: ['USD', 'EUR'], default: 'USD' })
  @IsOptional() @IsIn(['USD', 'EUR'])
  currency?: string;
}

export class UpdateProductDto extends PartialType(CreateProductDto) {}   // from @nestjs/swagger: docs stay correct

export class ProductDto extends CreateProductDto {
  @ApiProperty({ example: 1 }) id: number;
}
EOF
cat > src/products/products.controller.ts <<'EOF'
import { Body, Controller, Get, NotFoundException, Param, ParseIntPipe, Patch, Post } from '@nestjs/common';
import {
  ApiBearerAuth, ApiCreatedResponse, ApiNotFoundResponse, ApiOkResponse, ApiOperation, ApiTags,
} from '@nestjs/swagger';
import { CreateProductDto, ProductDto, UpdateProductDto } from './product.dto.js';

const products: ProductDto[] = [{ id: 1, name: 'Travel Mug', priceCents: 2400, currency: 'USD' }];

@ApiTags('products')
@Controller('products')
export class ProductsController {
  @Get()
  @ApiOperation({ summary: 'List products' })
  @ApiOkResponse({ type: [ProductDto] })
  list() { return products; }

  @Get(':id')
  @ApiOkResponse({ type: ProductDto })
  @ApiNotFoundResponse({ description: 'No product with this id' })
  findOne(@Param('id', ParseIntPipe) id: number) {
    const p = products.find((x) => x.id === id);
    if (!p) throw new NotFoundException();
    return p;
  }

  @Post()
  @ApiBearerAuth()
  @ApiCreatedResponse({ type: ProductDto })
  create(@Body() dto: CreateProductDto) {
    const p = { id: products.length + 1, currency: 'USD', ...dto };
    products.push(p);
    return p;
  }

  @Patch(':id')
  @ApiBearerAuth()
  @ApiOkResponse({ type: ProductDto })
  update(@Param('id', ParseIntPipe) id: number, @Body() dto: UpdateProductDto) {
    return { ...this.findOne(id), ...dto };
  }
}
EOF
cat > src/main.ts <<'EOF'
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule, { logger: false });
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }));

  const config = new DocumentBuilder()
    .setTitle('Shop API')
    .setDescription('Products and orders')
    .setVersion('1.0')
    .addBearerAuth()                                   // shows an "Authorize" button in the UI
    .build();
  const document = SwaggerModule.createDocument(app, config);
  SwaggerModule.setup('docs', app, document);          // UI at /docs, JSON at /docs-json

  await app.listen(3000);
}
await bootstrap();
EOF
sed -i "s#import { AppService } from './app.service.js';#&\nimport { ProductsController } from './products/products.controller.js';#; s#controllers: \[AppController\]#controllers: [AppController, ProductsController]#" src/app.module.ts
npm run build --silent
node dist/main.js > server.log 2>&1 & PID=$!
sleep 2
curl -s -o /dev/null -w "GET /docs -> %{http_code} %{content_type}\n" localhost:3000/docs
curl -s localhost:3000/docs-json > openapi.json
kill $PID; wait $PID 2>/dev/null
node -e '
const d = require("./openapi.json");
console.log("openapi", d.openapi, "|", d.info.title, d.info.version);
for (const [path, ops] of Object.entries(d.paths))
  for (const [method, op] of Object.entries(ops))
    console.log(`${method.toUpperCase().padEnd(6)} ${path.padEnd(16)} ${Object.keys(op.responses).join(",")} ${op.security ? "(auth)" : ""}`.trimEnd());
console.log("CreateProductDto:", JSON.stringify(d.components.schemas.CreateProductDto));
console.log("UpdateProductDto required:", JSON.stringify(d.components.schemas.UpdateProductDto.required ?? []));
'
```

<Happened>
<Tr>
<En>

- `/docs` served the **Swagger UI** HTML page; open it in a browser to see grouped endpoints, schemas with examples, a "Try it out" button and an **Authorize** button for the bearer token.
- The document lists every operation with its documented responses: `GET /products/{id}` has 200 **and** 404; `POST` and `PATCH` are marked as needing auth (from `@ApiBearerAuth()`). Path parameters appear as `{id}`, the OpenAPI syntax.
- `CreateProductDto` came out with types, examples, length limits, the enum and the default, and `required: ["name","priceCents"]` (because `currency` used `@ApiPropertyOptional`).
- `UpdateProductDto` has **no required fields**: `PartialType` imported from `@nestjs/swagger` (not `@nestjs/mapped-types`) also makes the documented fields optional. Import from the wrong package and the docs would say all fields are required.
- Note `priceCents` is documented as `number` even though validation requires an integer: with manual `@ApiProperty`, docs and validators can disagree. The plugin in the next step closes some of that gap.
- The default `GET /` from the starter app appears too; document or remove routes you don't want in the contract.

</En>
<Ur>

- `/docs` ne **Swagger UI** ka HTML page diya; ise browser me kholen to group hue endpoints, examples wale schemas, "Try it out" button aur bearer token ke liye **Authorize** button nazar aate hain.
- Document har operation ko us ke documented responses ke saath dikhata hai: `GET /products/{id}` ke 200 **aur** 404 hain; `POST` aur `PATCH` auth wale nishan zad hain (`@ApiBearerAuth()` se). Path parameters OpenAPI ke andaz `{id}` me aate hain.
- `CreateProductDto` types, examples, lambai ki hadd, enum aur default ke saath aaya, aur `required: ["name","priceCents"]` (kyun ke `currency` ne `@ApiPropertyOptional` istemal kiya).
- `UpdateProductDto` me **koi zaroori field nahi**: `@nestjs/swagger` (na ke `@nestjs/mapped-types`) se import kiya `PartialType` documented fields ko bhi ikhtiyari banata hai. Ghalat package se import karein to docs kahengi ke tamam fields zaroori hain.
- Dekhein ke `priceCents` `number` ki tarah document hua halanke validation integer maangti hai: haath ke `@ApiProperty` ke saath docs aur validators mukhtalif ho sakte hain. Agle qadam ka plugin is farq ka kuch hissa band karta hai.
- Starter app ka default `GET /` bhi aata hai; jo routes muahide me nahi chahiyen unhen document karein ya hata dein.

</Ur>

<Step title="The CLI plugin and generated client types">

<Tr>
<En>
We enable the Swagger CLI plugin in `nest-cli.json` with `classValidatorShim` and `introspectComments`, add a review DTO with **no** Swagger decorators (only class-validator rules and JSDoc comments), then generate TypeScript types for a front end from the document with `openapi-typescript`.
</En>
<Ur>
Hum `nest-cli.json` me `classValidatorShim` aur `introspectComments` ke saath Swagger CLI plugin on karte hain, **bina** Swagger decorators wala review DTO jorte hain (sirf class-validator ke qawaid aur JSDoc comments), phir `openapi-typescript` se document se front end ke liye TypeScript types banate hain.
</Ur>
</Tr>

```bash
cd shop-api
# 1) Let the Swagger CLI plugin read TypeScript types, class-validator rules and comments
cat > nest-cli.json <<'EOF'
{
  "$schema": "https://json.schemastore.org/nest-cli",
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "deleteOutDir": true,
    "plugins": [{ "name": "@nestjs/swagger", "options": { "classValidatorShim": true, "introspectComments": true } }]
  }
}
EOF
cat > src/products/review.dto.ts <<'EOF'
import { IsInt, IsOptional, IsString, Max, MaxLength, Min } from 'class-validator';

// No @ApiProperty anywhere: the plugin generates the docs from types, validators and comments
export class CreateReviewDto {
  /** Star rating from 1 to 5 */
  @IsInt() @Min(1) @Max(5)
  stars: number;

  /** Optional text shown under the rating */
  @IsOptional() @IsString() @MaxLength(500)
  comment?: string;
}
EOF
cat >> src/products/products.controller.ts <<'EOF'

import { CreateReviewDto } from './review.dto.js';

@ApiTags('reviews')
@Controller('products/:id/reviews')
export class ReviewsController {
  @Post()
  create(@Param('id', ParseIntPipe) id: number, @Body() dto: CreateReviewDto) {
    return { productId: id, ...dto };
  }
}
EOF
sed -i "s#import { ProductsController } from './products/products.controller.js';#import { ProductsController, ReviewsController } from './products/products.controller.js';#; s#ProductsController\]#ProductsController, ReviewsController]#" src/app.module.ts
npm run build --silent
node dist/main.js > server.log 2>&1 & PID=$!
sleep 2
curl -s localhost:3000/docs-json > openapi.json
kill $PID; wait $PID 2>/dev/null
node -e 'console.log(JSON.stringify(require("./openapi.json").components.schemas.CreateReviewDto, null, 1))'
```

<Happened>
<Tr>
<En>

- The plugin produced the schema **without any `@ApiProperty`**: types from TypeScript (`number`, `string`), `required` from the optional `?`, descriptions from the `/** … */` comments, and `minimum`/`maximum`/`maxLength` from the class-validator decorators (`classValidatorShim`).
- One source of truth: change the validator to `@Max(10)` and the docs change on the next build.
- `openapi-typescript` turned the document into TypeScript types; a React app can import them and get compile errors if the API changes shape (`components["schemas"]["CreateReviewDto"]`). Tools like `orval` or `openapi-fetch` go further and generate typed fetch functions.
- The plugin works at compile time, so it only applies when building with the Nest CLI (`nest build`/`nest start`), or with the equivalent TypeScript transformer in other build setups.

</En>
<Ur>

- Plugin ne **bina kisi `@ApiProperty`** ke schema banaya: types TypeScript se (`number`, `string`), `required` ikhtiyari `?` se, descriptions `/** … */` comments se, aur `minimum`/`maximum`/`maxLength` class-validator decorators se (`classValidatorShim`).
- Sachai ka ek zariya: validator ko `@Max(10)` karein aur agle build par docs badal jati hain.
- `openapi-typescript` ne document ko TypeScript types me badla; React app unhen import kar sakti hai aur API ki shakal badalne par compile errors paati hai (`components["schemas"]["CreateReviewDto"]`). `orval` ya `openapi-fetch` jaise tools aur aage ja kar typed fetch functions banate hain.
- Plugin compile time par kaam karta hai, isliye ye sirf Nest CLI (`nest build`/`nest start`) se build karne par, ya doosre build setups me barabar TypeScript transformer ke saath lagu hota hai.

</Ur>

## Common mistakes

<Compare>
<Bad title="Docs that say less than the API does">

```text
@Get(':id')
findOne(@Param('id') id: string) { … }     // docs show only "200", no schema, no 404, no auth
```

</Bad>
<Good title="Document responses, errors and auth">

```text
@Get(':id')
@ApiBearerAuth()
@ApiOkResponse({ type: OrderDto })
@ApiNotFoundResponse({ description: 'Order not found or not yours' })
findOne(@Param('id', ParseUUIDPipe) id: string) { … }
```

</Good>
</Compare>

<Compare>
<Bad title="Public docs for an internal API, in production">

```text
SwaggerModule.setup('docs', app, document);     // every internal and admin endpoint listed for anyone
```

</Bad>
<Good title="Only where it's appropriate">

```text
if (config.get('NODE_ENV') !== 'production') SwaggerModule.setup('docs', app, document);
// or protect /docs with auth, or publish a separate public document that includes only public endpoints
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Importing `PartialType` from `@nestjs/mapped-types`** in a Swagger project: validation works, docs are wrong.
- **Returning entities while documenting DTOs**: the docs promise one shape and the API returns another; return the documented type.
- **No examples**: consumers have to guess formats (dates, money, IDs).
- **Forgetting error responses** (400, 401, 403, 404, 409), which clients must handle.
- **Changing the document without reviewing diffs**: removing a field or making one required breaks clients; check with tools like `oasdiff` in CI.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Swagger project me **`@nestjs/mapped-types` se `PartialType` import karna**: validation chalti hai, docs ghalat hoti hain.
- **DTOs document kar ke entities wapas karna**: docs ek shakal ka waada karti hain aur API doosri wapas karti hai; documented type wapas karein.
- **Examples nahi**: istemal karne walon ko formats (tareekhen, paisa, IDs) ka andaza lagana parta hai.
- **Error responses bhoolna** (400, 401, 403, 404, 409), jinhen clients ko sambhalna parta hai.
- **Diffs review kiye baghair document badalna**: field hatana ya zaroori banana clients tor deta hai; CI me `oasdiff` jaise tools se check karein.

</Ur>
</Tr>

<Challenge title="Document the error format">

<Tr>
<En>
Your API returns errors as `{ error: { code, message, requestId } }` (Exception Filters lesson). Create an `ErrorResponseDto` and make every endpoint document 400, 401 and 500 with it without repeating three decorators on each method.
</En>
<Ur>
Aap ki API errors `{ error: { code, message, requestId } }` ki shakal me deti hai (Exception Filters lesson). `ErrorResponseDto` banayen aur har method par teen decorators dohraye baghair har endpoint par is ke saath 400, 401 aur 500 document karein.
</Ur>
</Tr>

<Solution>

```text
class ErrorBodyDto {
  @ApiProperty({ example: 'validation_failed' }) code: string;
  @ApiProperty({ example: 'Invalid input' }) message: string;
  @ApiProperty({ example: '3f9a1c2e' }) requestId: string;
}
export class ErrorResponseDto {
  @ApiProperty({ type: ErrorBodyDto }) error: ErrorBodyDto;
}

// a composed decorator
export const ApiStandardErrors = () =>
  applyDecorators(
    ApiBadRequestResponse({ type: ErrorResponseDto }),
    ApiUnauthorizedResponse({ type: ErrorResponseDto }),
    ApiInternalServerErrorResponse({ type: ErrorResponseDto }),
  );

@ApiStandardErrors()            // on a controller: applies to all its routes
@Controller('products')
export class ProductsController { … }
```

<En>
`applyDecorators` combines several decorators into one, which keeps controllers readable and makes the error contract consistent. Put endpoint-specific errors (404, 409) on the individual methods.
</En>
<Ur>
`applyDecorators` kai decorators ko ek me jorta hai, jo controllers ko parhne qabil aur error ka muahida yaksan rakhta hai. Endpoint ke mukhsoos errors (404, 409) alag methods par lagayen.
</Ur>

<Challenge title="Catch breaking changes in CI">

<Tr>
<En>
Describe a CI step that fails a pull request if it introduces a breaking change to the API contract. What counts as breaking?
</En>
<Ur>
Aisa CI qadam bayan karein jo pull request ko fail kare agar wo API muahide me tor dene wali tabdeeli laye. Kya tor dene wala shumar hota hai?
</Ur>
</Tr>

<Solution>

<Tr>
<En>

1. Add a script that boots the app (or builds the document without listening) and writes `openapi.json`.
2. In CI, generate it on the main branch and on the pull request branch.
3. Compare them with `oasdiff breaking main.json pr.json` (or a similar tool) and fail on breaking changes; post the full changelog as a comment.

**Breaking**: removing an endpoint or response field, renaming fields, changing a type, making an optional request field required, adding a required request field, narrowing enums in requests, changing auth requirements. **Usually safe**: adding endpoints, adding optional request fields, adding response fields (if clients ignore unknown fields). Breaking changes should go into a new API version.

</En>
<Ur>

1. Aisa script jorein jo app chalaye (ya listen kiye baghair document banaye) aur `openapi.json` likhe.
2. CI me ise main branch aur pull request branch dono par banayen.
3. Unhen `oasdiff breaking main.json pr.json` (ya mila julta tool) se milayen aur tor dene wali tabdeeliyon par fail karein; poora changelog comment ki tarah daalein.

**Tor dene wali**: endpoint ya response field hatana, fields ke naam badalna, type badalna, ikhtiyari request field ko zaroori banana, zaroori request field jorna, requests me enums tang karna, auth ki shart badalna. **Aam taur par mehfooz**: endpoints jorna, ikhtiyari request fields jorna, response fields jorna (agar clients na maloom fields nazar andaz karte hon). Tor dene wali tabdeeliyan naye API version me jani chahiyen.

</Ur>
</Tr>

<DeepDive title="More about OpenAPI in Nest">

**Generics and wrappers.** For `{ data: T[], meta }` envelopes, use `@ApiExtraModels` with `getSchemaPath` (or a custom decorator) to describe generic responses.

**Writing the document to a file.** Build it in a script with `NestFactory.create(AppModule, { preview: true })` or a normal create without `listen()`, and `writeFileSync('openapi.json', …)` for CI and publishing.

**Versioning.** With URI versioning, you can create one document per version using the `include` option or separate modules.

**Other UIs.** Scalar and Redoc render the same document with different layouts; `@nestjs/swagger` lets you serve the JSON and plug in any of them.

**zod-based schemas.** Libraries like `nestjs-zod` or `@anatine/zod-openapi` produce OpenAPI from zod schemas if you validate with zod.

**Webhooks and callbacks.** OpenAPI 3.1 can also document webhooks your API sends to clients.

</DeepDive>

<DeepDive title="Real world: the field that disappeared from the mobile app">

A travel company's NestJS API served a web app and two mobile apps. A backend developer refactored the booking response, renaming `departureTime` to `departsAt` "for consistency". All backend tests passed; the web app was updated in the same pull request.

The mobile apps, released weeks earlier, still read `departureTime`. After the deploy, they showed "Invalid date" on every booking screen. The fix needed an emergency backend patch returning both fields, and a mobile release that took four days to reach most users.

Afterwards the team made the contract explicit:

1. Swagger was already generating docs; now a CI job generated `openapi.json` on every pull request and ran `oasdiff breaking` against the main branch.
2. Breaking changes failed the build unless the PR had a "breaking-change" label and an API version bump (`/v2`).
3. The mobile and web apps generated their API types from the published document, so removed fields caused compile errors in the client repositories immediately.
4. Deprecated fields were marked with `@ApiProperty({ deprecated: true })` and removed only after analytics showed old app versions were no longer in use.

The OpenAPI document had existed all along; it only started preventing incidents once it was treated as a contract and checked automatically.

</DeepDive>

<DeepDive title="Security lens">

- **Don't publish internal or admin endpoints** in public docs; restrict `/docs` in production or generate a separate public document.
- **Never put real secrets or personal data in examples.**
- **Documented auth is not enforced auth**: `@ApiBearerAuth()` only describes; guards protect.
- **Keep the spec accurate**: security scanners and API gateways may rely on it to validate requests.
- **Review contract diffs** for accidentally exposed fields (like `passwordHash` appearing in a response schema).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is OpenAPI and why use it?">
A standard, machine-readable description of HTTP APIs covering endpoints, parameters, bodies, responses and authentication. It powers interactive documentation, client and type generation, contract testing and API tooling, and serves as a contract between API producers and consumers.
</QA>

<QA q="How does NestJS generate OpenAPI documentation?">
@nestjs/swagger scans controllers, route decorators and DTO classes with SwaggerModule.createDocument, combined with metadata from decorators like @ApiProperty, @ApiOkResponse and @ApiTags, and optionally the CLI plugin that infers metadata at compile time; SwaggerModule.setup serves the UI and JSON.
</QA>

<QA q="What does the Swagger CLI plugin do?">
It's a TypeScript transformer that adds OpenAPI metadata automatically from property types, optional markers, class-validator decorators and JSDoc comments, reducing the need for manual @ApiProperty decorators.
</QA>

<QA q="How do you prevent breaking API changes?">
Treat the OpenAPI document as a contract: generate it in CI, compare it with the previous version using a diff tool, fail on breaking changes, version the API for intentional breaks, and deprecate fields before removing them.
</QA>

<QA q="Code-first vs design-first API development?">
Code-first generates the specification from the implementation, which keeps them in sync with little effort; design-first writes the specification first, enabling early review and parallel client development, with contract tests ensuring the implementation matches.
</QA>

</DeepDive>
