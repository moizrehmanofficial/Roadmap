<BigIdea>
<Tr>
<En>
Everything in a URL arrives as **text**: `/orders/42` gives you `"42"`, `?inStock=true` gives you `"true"`, `?ids=3,7` gives you `"3,7"`. A **pipe** is a small class that runs **just before** your controller method, receives one argument (a path param, a query value, the body) and does one of two things: **transform** it into what your method actually wants, or **throw** an exception so the method never runs. Nest ships pipes for the common cases: `ParseIntPipe`, `ParseFloatPipe`, `ParseBoolPipe`, `ParseUUIDPipe`, `ParseEnumPipe`, `ParseArrayPipe`, `DefaultValuePipe`, and the `ValidationPipe` from the previous lesson. Writing your own is just implementing **`transform(value, metadata)`**: trim strings, normalise a slug, or even look up a record and hand the method a loaded entity instead of an ID. Pipes can be attached to one **parameter**, a whole **method** or **controller**, or the whole **app**, and they run in that outer-to-inner order. The result: methods contain only business logic, with inputs that are already the right type and already checked.
</En>
<Ur>
URL ki har cheez **text** ban kar aati hai: `/orders/42` aap ko `"42"` deta hai, `?inStock=true` `"true"` deta hai, `?ids=3,7` `"3,7"` deta hai. **Pipe** chhoti class hai jo controller method se **bilkul pehle** chalti hai, ek argument leti hai (path param, query value, body) aur do me se ek kaam karti hai: use us cheez me **badalti** hai jo aap ka method asal me chahta hai, ya exception **throw** karti hai taa ke method kabhi na chale. Nest aam soorton ke liye pipes deta hai: `ParseIntPipe`, `ParseFloatPipe`, `ParseBoolPipe`, `ParseUUIDPipe`, `ParseEnumPipe`, `ParseArrayPipe`, `DefaultValuePipe`, aur pichhle lesson ka `ValidationPipe`. Apna pipe likhna bas **`transform(value, metadata)`** banana hai: strings trim karna, slug yaksan karna, ya record dhoondh kar method ko ID ke bajaye load hui entity dena. Pipes ek **parameter**, poore **method** ya **controller**, ya poori **app** par lag sakte hain, aur isi bahar se andar ki tarteeb me chalte hain. Nateeja: methods me sirf business logic hoti hai, aur inputs pehle se sahi type ke aur check kiye hue.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- Without pipes, every handler repeats `Number(...)`, `isNaN`, `=== "true"` and their error responses, and some forget.
- Pipes fail **before** business logic runs, so bad input never reaches services or the database.
- Custom pipes make cross-cutting conversions (trimming, slugs, loading entities) reusable and testable on their own.

</En>
<Ur>

- Pipes ke baghair har handler `Number(...)`, `isNaN`, `=== "true"` aur un ke error responses dohrata hai, aur kuch bhool jate hain.
- Pipes business logic chalne se **pehle** fail hote hain, isliye kharab input kabhi services ya database tak nahi pohanchta.
- Custom pipes har jagah kaam aane wali tabdeeliyan (trim, slugs, entities load karna) dobara istemal ke qabil aur alag se testable banate hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Input | Pipe |
| --- | --- |
| Numeric ID in the path | `ParseIntPipe` (or `ParseUUIDPipe` for UUIDs) |
| Optional number in the query | `ParseIntPipe({ optional: true })` or `DefaultValuePipe` + `ParseIntPipe` |
| `?flag=true` | `DefaultValuePipe(false)` + `ParseBoolPipe` |
| `?ids=1,2,3` | `ParseArrayPipe({ items: Number, separator: ',' })` |
| A fixed set of values | `ParseEnumPipe(MyEnum)` |
| A whole body or query object | `ValidationPipe` + DTO |
| Same clean-up on many routes | a custom pipe with `@UsePipes` |
| "Load X by ID or 404" on many routes | an injectable custom pipe |

</En>

## Picture it

<Tr>
<En>

Think of a **water treatment line** before a city's taps.

- Water from the river (raw request values) passes through a series of **stations** before reaching homes (your method).
- Some stations **change** the water: filter it, adjust the pH (transformation pipes: `"42"` → 42, trimming).
- Some stations **test** it and shut the valve if something's wrong (validation pipes throwing 400).
- The stations are arranged **in order**: the city-wide plant first (global pipes), then the district station (controller), then the street filter (method), and finally the tap filter on one sink (parameter pipe).
- A clever station can even **swap** what's delivered: you order "item 1" and receive the item itself (a pipe that loads the entity).

</En>
<Ur>

Shehar ke nalkon se pehle **paani saaf karne ki line** ka sochein.

- Darya ka paani (kachi request values) gharon (aap ka method) tak pohanchne se pehle kai **stations** se guzarta hai.
- Kuch stations paani **badalte** hain: chhante hain, pH theek karte hain (transformation pipes: `"42"` → 42, trim).
- Kuch stations **test** karte hain aur kuch ghalat ho to valve band karte hain (400 throw karne wale validation pipes).
- Stations **tarteeb se** lage hain: pehle poore shehar ka plant (global pipes), phir ilaqe ka station (controller), phir gali ka filter (method), aur aakhir me ek sink ka nalke ka filter (parameter pipe).
- Hoshiyar station jo pohanchaya jata hai use **badal** bhi sakta hai: aap "item 1" maangte hain aur khud item milta hai (entity load karne wala pipe).

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |

## Learn it step by step

<Walkthrough>

<Step title="The built-in pipes">

<Tr>
<En>
A search endpoint uses five built-in pipes on query values, plus `ParseUUIDPipe` and a `ParseIntPipe` that answers 404 instead of 400. `ParseArrayPipe` relies on class-validator and class-transformer internally, so we install them.
</En>
<Ur>
Search endpoint query values par paanch built-in pipes istemal karta hai, plus `ParseUUIDPipe` aur aisa `ParseIntPipe` jo 400 ke bajaye 404 deta hai. `ParseArrayPipe` andar se class-validator aur class-transformer par munhasir hai, isliye hum unhen install karte hain.
</Ur>
</Tr>

```bash
npx -y @nestjs/cli@12.0.13 new shop-api --package-manager npm --skip-git --strict > /dev/null 2>&1
cd shop-api
npm install class-validator@0.15.1 class-transformer@0.5.1 --silent    # ParseArrayPipe uses them internally
cat > src/search.controller.ts <<'EOF'
import {
  Controller, DefaultValuePipe, Get, HttpStatus, Param, ParseArrayPipe, ParseBoolPipe,
  ParseEnumPipe, ParseFloatPipe, ParseIntPipe, ParseUUIDPipe, Query,
} from '@nestjs/common';

enum Sort { Newest = 'newest', Price = 'price', Rating = 'rating' }

@Controller('search')
export class SearchController {
  @Get()
  search(
    @Query('ids', new ParseArrayPipe({ items: Number, separator: ',', optional: true })) ids?: number[],
    @Query('inStock', new DefaultValuePipe(false), ParseBoolPipe) inStock?: boolean,
    @Query('maxPrice', new ParseFloatPipe({ optional: true })) maxPrice?: number,
    @Query('sort', new DefaultValuePipe(Sort.Newest), new ParseEnumPipe(Sort)) sort?: Sort,
  ) {
    return { ids, inStock, maxPrice, sort };
  }

  @Get('orders/:id')
  order(@Param('id', new ParseUUIDPipe({ version: '4' })) id: string) {
    return { id };
  }

  @Get('page/:n')
  page(@Param('n', new ParseIntPipe({ errorHttpStatusCode: HttpStatus.NOT_FOUND })) n: number) {
    return { page: n };                       // "/page/abc" is a missing page, not a bad request
  }
}
EOF
sed -i "s#import { AppService } from './app.service.js';#&\nimport { SearchController } from './search.controller.js';#; s#controllers: \[AppController\]#controllers: [AppController, SearchController]#" src/app.module.ts
npm run build --silent
NO_COLOR=1 node dist/main.js > server.log 2>&1 &
sleep 2
U=localhost:3000/search
curl -s "$U"; echo
curl -s "$U?ids=3,7,12&inStock=true&maxPrice=19.99&sort=price"; echo
curl -s "$U?ids=3,x"; echo
curl -s "$U?inStock=yes"; echo
curl -s "$U?sort=cheapest"; echo
curl -s "$U/orders/0f8fad5b-d9cb-469f-a165-70867728950e"; echo
curl -s "$U/orders/12345"; echo
curl -s -w " %{http_code}\n" "$U/page/abc"
kill %1
```

<Happened>
<Tr>
<En>

- **No query**: `DefaultValuePipe` supplied `inStock: false` and `sort: "newest"`; `ids` and `maxPrice` were `optional`, so they're simply absent (undefined isn't sent in JSON).
- **All set**: `"3,7,12"` became `[3, 7, 12]`, `"true"` became `true`, `"19.99"` became `19.99`, and `"price"` was accepted as an enum value. The method got real types without one line of conversion code.
- **Bad values** each got a precise 400: `[1] item must be a number` points at the second array item; `yes` isn't a boolean string; `cheapest` isn't in the enum; `12345` isn't a v4 UUID.
- **`errorHttpStatusCode: 404`**: for `/page/abc` a "not found" makes more sense than "bad request". Every built-in parse pipe accepts this option, and an `exceptionFactory` for full control.
- Without `class-validator` installed, the app refused to start with "The class-validator package is missing", because `ParseArrayPipe` uses it to check items.

</En>
<Ur>

- **Query nahi**: `DefaultValuePipe` ne `inStock: false` aur `sort: "newest"` diye; `ids` aur `maxPrice` `optional` the, isliye bas ghayab hain (undefined JSON me nahi jata).
- **Sab set**: `"3,7,12"` `[3, 7, 12]` bana, `"true"` `true` bana, `"19.99"` `19.99` bana, aur `"price"` enum value ki tarah qubool hua. Method ko conversion code ki ek line ke baghair asli types milin.
- **Ghalat values** ko har ek ko bilkul 400 mila: `[1] item must be a number` array ke doosre item ki taraf ishara karta hai; `yes` boolean string nahi; `cheapest` enum me nahi; `12345` v4 UUID nahi.
- **`errorHttpStatusCode: 404`**: `/page/abc` ke liye "bad request" se zyada "not found" mauzoon hai. Har built-in parse pipe ye option leta hai, aur poore control ke liye `exceptionFactory` bhi.
- `class-validator` install kiye baghair app ne "The class-validator package is missing" ke saath shuru hone se inkaar kiya, kyun ke `ParseArrayPipe` items check karne ke liye ise istemal karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Custom pipes and where they run">

<Tr>
<En>
Three custom pipes: `TrimStringsPipe` cleans body strings; `LogPipe` prints where it runs; `ProductByIdPipe` is injectable, receives `ProductsService`, and turns an ID into a product or a 404. We attach `LogPipe` at all four levels to see the order.
</En>
<Ur>
Teen custom pipes: `TrimStringsPipe` body ki strings saaf karta hai; `LogPipe` print karta hai ke wo kahan chala; `ProductByIdPipe` injectable hai, `ProductsService` leta hai, aur ID ko product ya 404 me badalta hai. Tarteeb dekhne ke liye hum `LogPipe` chaaron levels par lagate hain.
</Ur>
</Tr>

```bash
cd shop-api
cat > src/pipes.ts <<'EOF'
import {
  ArgumentMetadata, Body, Controller, Get, Injectable, NotFoundException, Param,
  ParseIntPipe, PipeTransform, Post, UsePipes,
} from '@nestjs/common';

// 1) A transformation pipe: trims every string in the body
@Injectable()
export class TrimStringsPipe implements PipeTransform {
  transform(value: unknown, meta: ArgumentMetadata) {
    if (meta.type !== 'body' || typeof value !== 'object' || value === null) return value;
    return Object.fromEntries(
      Object.entries(value).map(([k, v]) => [k, typeof v === 'string' ? v.trim() : v]),
    );
  }
}

// 2) A pipe that logs where it runs, to see the order
export class LogPipe implements PipeTransform {
  constructor(private readonly label: string) {}
  transform(value: unknown, meta: ArgumentMetadata) {
    console.log(`${this.label.padEnd(10)} ${meta.type}${meta.data ? `:${meta.data}` : ''} = ${JSON.stringify(value)}`);
    return value;
  }
}

// 3) An injectable pipe that turns an ID into a loaded entity (or a 404)
@Injectable()
export class ProductsService {
  private products = new Map([[1, { id: 1, name: 'Travel Mug' }]]);
  find(id: number) { return this.products.get(id); }
}

@Injectable()
export class ProductByIdPipe implements PipeTransform<number> {
  constructor(private readonly products: ProductsService) {}
  transform(id: number) {
    const product = this.products.find(id);
    if (!product) throw new NotFoundException(`Product ${id} not found`);
    return product;
  }
}

@Controller('pipes')
@UsePipes(new LogPipe('controller'))
export class PipesController {
  @Get('products/:id')
  @UsePipes(new LogPipe('method'))
  findOne(@Param('id', new LogPipe('param'), ParseIntPipe, ProductByIdPipe) product: { id: number; name: string }) {
    return product;                              // the handler receives the entity, not the ID
  }

  @Post('reviews')
  @UsePipes(TrimStringsPipe)
  review(@Body() body: Record<string, unknown>) {
    return body;
  }
}
EOF
cat > src/main.ts <<'EOF'
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';
import { LogPipe } from './pipes.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(new LogPipe('global'));
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();
EOF
sed -i "s#import { SearchController } from './search.controller.js';#&\nimport { PipesController, ProductsService, ProductByIdPipe } from './pipes.js';#; s#SearchController\]#SearchController, PipesController]#; s#providers: \[AppService\]#providers: [AppService, ProductsService, ProductByIdPipe]#" src/app.module.ts
npm run build --silent
NO_COLOR=1 node dist/main.js > server.log 2>&1 &
sleep 2
curl -s localhost:3000/pipes/products/1; echo
curl -s localhost:3000/pipes/products/9; echo
curl -s -X POST -H "Content-Type: application/json" -d '{"title":"  Great mug  ","stars":5}' localhost:3000/pipes/reviews; echo
kill %1
echo "== server log for the first request"
grep -E '^(global|controller|method|param) ' server.log | head -4
```

```text output

{"message":"Product 9 not found","error":"Not Found","statusCode":404}
{"title":"Great mug","stars":5}
== server log for the first request

method     param:id = "1"

```

<Happened>
<Tr>
<En>

- **Entity pipe**: the parameter pipes ran left to right: log, `ParseIntPipe` (`"1"` → 1), then `ProductByIdPipe` (1 → the product). The handler received `{ id: 1, name: "Travel Mug" }` and has no lookup or 404 code. For ID 9, the pipe threw `NotFoundException`.
- **Injectable pipes**: because `ProductByIdPipe` was passed as a **class** (not `new ProductByIdPipe()`), Nest created it through DI and injected `ProductsService`. Pass an instance only when the pipe needs constructor options and no dependencies, like `new LogPipe('param')`.
- **Trim pipe**: `"  Great mug  "` arrived as `"Great mug"`. It checks `meta.type === 'body'` so it leaves params and queries alone.
- **Order**: the log shows **global → controller → method → parameter**, each receiving the output of the previous one. Global pipes see every argument of every route, so they must be cheap and generic (like `ValidationPipe`).
- `ArgumentMetadata` told each pipe what it was handling: `type` (`body`, `query`, `param`, `custom`), `data` (`id`), and `metatype` (the declared TypeScript class, which is how `ValidationPipe` knows which DTO to use).

</En>
<Ur>

- **Entity pipe**: parameter pipes baayen se daayen chale: log, `ParseIntPipe` (`"1"` → 1), phir `ProductByIdPipe` (1 → product). Handler ko `{ id: 1, name: "Travel Mug" }` mila aur us me na dhoondhne ka code hai na 404 ka. ID 9 ke liye pipe ne `NotFoundException` throw kiya.
- **Injectable pipes**: kyun ke `ProductByIdPipe` **class** ki tarah diya gaya (`new ProductByIdPipe()` nahi), Nest ne use DI se banaya aur `ProductsService` inject ki. Instance sirf tab dein jab pipe ko constructor options chahiyen aur dependencies nahi, jaise `new LogPipe('param')`.
- **Trim pipe**: `"  Great mug  "` `"Great mug"` ban kar aaya. Ye `meta.type === 'body'` check karta hai isliye params aur queries ko nahi chhuta.
- **Tarteeb**: log **global → controller → method → parameter** dikhata hai, har ek pichhle ka output leta hai. Global pipes har route ka har argument dekhte hain, isliye unhen sasta aur aam hona chahiye (`ValidationPipe` ki tarah).
- `ArgumentMetadata` ne har pipe ko bataya ke wo kya sambhal raha hai: `type` (`body`, `query`, `param`, `custom`), `data` (`id`), aur `metatype` (bayan ki gayi TypeScript class, jis se `ValidationPipe` janta hai ke kaun sa DTO istemal kare).

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Converting by hand in every handler">

```text
@Get()
list(@Query('page') page: string, @Query('inStock') inStock: string) {
  const p = Number(page) || 1;               // "abc" silently becomes 1
  const s = inStock === 'true';              // "yes", "1", "TRUE" silently become false
}
```

</Bad>
<Good title="Declare it with pipes">

```text
@Get()
list(
  @Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number,
  @Query('inStock', new DefaultValuePipe(false), ParseBoolPipe) inStock: boolean,
) { … }
```

</Good>
</Compare>

<Compare>
<Bad title="Instantiating an injectable pipe">

```text
@Param('id', ParseIntPipe, new ProductByIdPipe())   // TS error or undefined ProductsService at runtime
```

</Bad>
<Good title="Pass the class; let DI build it">

```text
@Param('id', ParseIntPipe, ProductByIdPipe)
// and register ProductsService (and the pipe if you like) as providers in the module
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Putting `DefaultValuePipe` after the parse pipe**: the parse pipe fails on `undefined` first. Default first, then parse.
- **Business rules in pipes** ("users may only buy 5 per day"): pipes are for shaping and checking input; rules belong in services.
- **Authorisation in pipes**: use guards; pipes run after guards and don't know about permissions.
- **Heavy work in global pipes** (database calls for every argument of every route).
- **Using an entity-loading pipe without an ownership check**: loading "product 7" isn't the same as "you may edit product 7".
- **Forgetting that pipes don't run for `@Req()` or `@Res()` arguments**, only for decorated parameters like `@Body`, `@Query`, `@Param`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`DefaultValuePipe` ko parse pipe ke baad rakhna**: parse pipe pehle `undefined` par fail ho jata hai. Pehle default, phir parse.
- **Pipes me business qawaid** ("users roz sirf 5 khareed sakte hain"): pipes input ki shakal dene aur check karne ke liye hain; qawaid services me.
- **Pipes me authorisation**: guards istemal karein; pipes guards ke baad chalte hain aur ijazaton ka pata nahi rakhte.
- **Global pipes me bhari kaam** (har route ke har argument par database calls).
- **Ownership check ke baghair entity load karne wala pipe**: "product 7 load karna" aur "aap product 7 edit kar sakte hain" ek baat nahi.
- **Ye bhoolna ke pipes `@Req()` ya `@Res()` arguments par nahi chalte**, sirf `@Body`, `@Query`, `@Param` jaise decorated parameters par.

</Ur>
</Tr>

</Ur>

<Solution>

```text
@Injectable()
export class ParseSlugPipe implements PipeTransform<string, string> {
  transform(value: string) {
    const slug = String(value ?? '').trim().toLowerCase().replace(/\s+/g, '-');
    if (!/^[a-z0-9]+(?:-[a-z0-9]+)*$/.test(slug) || slug.length < 3 || slug.length > 80) {
      throw new BadRequestException('Invalid slug');
    }
    return slug;
  }
}

@Get(':slug') findOne(@Param('slug', ParseSlugPipe) slug: string) { … }
```

</En>

<DeepDive title="More about pipes">

**Where pipes sit in the lifecycle.** Middleware → guards → interceptors (before) → **pipes** → handler → interceptors (after) → exception filters. A pipe can rely on guards having authenticated the user.

**Pipes on custom decorators.** `@CurrentUser(new ValidationPipe({ validateCustomDecorators: true }))` validates values produced by your own parameter decorators.

**Async pipes.** `transform` may return a promise; Nest awaits it, which is how entity-loading pipes query the database.

**Global pipes with DI.** `app.useGlobalPipes(new X())` can't inject dependencies; register `{ provide: APP_PIPE, useClass: X }` in a module instead.

**`ParseFilePipe`.** Validates uploaded files (size, type) with validators like `MaxFileSizeValidator` and `FileTypeValidator`.

**zod pipes.** A pipe that runs `schema.parse(value)` lets you use zod schemas instead of class-validator DTOs.

</DeepDive>

<DeepDive title="Real world: the boolean that was always false">

A retailer's NestJS API had a `GET /products?includeArchived=true` endpoint used by the internal admin tool. The handler read the value as `@Query('includeArchived') includeArchived: boolean` and passed it to the repository. TypeScript was happy.

For months, admins reported two opposite problems. First, archived products appeared even when the checkbox was off: without a pipe, the value was the **string** `"false"`, and the repository's `if (includeArchived)` treated any non-empty string as true. A developer "fixed" it by changing the check to `includeArchived === true`. After that, archived products **never** appeared, because the string `"true"` is never strictly equal to the boolean `true`. On top of that, one admin screen sent `includeArchived=1` and another `includeArchived=true`.

Two pipes fixed it permanently:

1. `@Query('includeArchived', new DefaultValuePipe(false), ParseBoolPipe)` made the parameter a real boolean and rejected `1`, so the admin tool's inconsistent screen was found and fixed.
2. A lint rule flagged `@Query`/`@Param` parameters typed as `number` or `boolean` without a parse pipe or a DTO.

The bug was never in the business logic; it was trusting a TypeScript type annotation to convert data it never touches.

</DeepDive>

<DeepDive title="Security lens">

- **Parse and bound every input**: IDs, numbers and enums should never reach queries as arbitrary strings.
- **Use `ParseUUIDPipe` for UUID IDs** to reject injection-style payloads early.
- **Entity-loading pipes still need authorisation** checks on the loaded record.
- **Keep error messages generic** for sensitive lookups (404 rather than revealing whether something exists for another tenant).
- **Global `ValidationPipe` with whitelist** remains the main defence for bodies.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a pipe in NestJS?">
A class implementing PipeTransform that receives a handler argument before the method runs and either returns a transformed value or throws an exception, used for type conversion and validation.
</QA>

<QA q="What are some built-in pipes?">
ValidationPipe, ParseIntPipe, ParseFloatPipe, ParseBoolPipe, ParseArrayPipe, ParseUUIDPipe, ParseEnumPipe, DefaultValuePipe and ParseFilePipe.
</QA>

<QA q="At which levels can pipes be applied, and in what order do they run?">
Globally, on a controller, on a method with @UsePipes, or on a single parameter. They run from global to controller to method to parameter, and multiple pipes on one parameter run left to right.
</QA>

<QA q="How do you write a pipe that needs a service?">
Make it @Injectable, inject the service in its constructor, and pass the pipe class rather than an instance so Nest resolves it through DI; for global use, register it with the APP_PIPE token.
</QA>

<QA q="What's the difference between pipes and guards?">
Guards decide whether a request may proceed, typically for authentication and authorisation, and run before pipes; pipes transform and validate handler arguments.
</QA>

</DeepDive>
