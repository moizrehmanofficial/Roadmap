<BigIdea>
<Tr>
<En>
A **provider** is anything Nest's dependency injection container can **create and hand out**. Most providers are **services**: classes marked `@Injectable()` that hold business logic, called by controllers and other services. But a provider can also be a **plain value** (configuration), the **result of a function** (a database client built from config), or an **alias** for another provider. Each provider is registered under an **injection token**, the key Nest uses to find it. A class is its own token, so `constructor(private gateway: PaymentGateway)` just works; values and functions use a string or symbol token and need `@Inject(TOKEN)`. The power comes from separating **what you ask for** (an abstract `PaymentGateway`) from **what you get** (a fake in development, a real card gateway in production), decided in **one place**: the module's provider list. **Async factories** let Nest wait for things like database connections before building anything that depends on them, and **lifecycle hooks** let providers warm caches at startup and close connections at shutdown.
</En>
<Ur>
**Provider** wo har cheez hai jo Nest ka dependency injection container **bana kar de** sake. Zyada tar providers **services** hain: `@Injectable()` wali classes jo business logic rakhti hain, jinhen controllers aur doosri services bulati hain. Magar provider **saada value** (configuration), **function ka nateeja** (config se bana database client), ya kisi doosre provider ka **alias** bhi ho sakta hai. Har provider ek **injection token** ke neeche register hota hai, wo key jis se Nest use dhoondta hai. Class khud apna token hai, isliye `constructor(private gateway: PaymentGateway)` bas chal jata hai; values aur functions string ya symbol token istemal karte hain aur `@Inject(TOKEN)` chahte hain. Taqat is me hai ke **aap kya maangte hain** (abstract `PaymentGateway`) aur **aap ko kya milta hai** (development me nakli, production me asli card gateway) alag ho, aur faisla **ek jagah** ho: module ki provider list. **Async factories** Nest ko database connections jaisi cheezon ka intezar karne deti hain, un par munhasir koi cheez banane se pehle, aur **lifecycle hooks** providers ko startup par cache garam karne aur shutdown par connections band karne dete hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

| Registration | Meaning | Typical use |
| --- | --- | --- |
| `ProductsService` | short for `{ provide: ProductsService, useClass: ProductsService }` | ordinary services |
| `{ provide: Token, useClass: Impl }` | create `Impl` when `Token` is requested | swap implementations |
| `{ provide: TOKEN, useValue: value }` | hand out an existing value | config, constants, test fakes |
| `{ provide: TOKEN, useFactory: fn, inject: [...] }` | call `fn` with other providers; can be `async` | clients built from config, DB connections |
| `{ provide: TOKEN, useExisting: Other }` | alias: same instance under another token | backwards compatibility, multiple interfaces |

| Token type | Inject with |
| --- | --- |
| class / abstract class | the constructor parameter type alone |
| string or `Symbol` | `@Inject(TOKEN)` |
| TypeScript interface | not possible (interfaces vanish at runtime): use an abstract class or token |

</En>

<Why>
<Tr>
<En>

- **Swappable implementations**: fake payments in development and tests, real ones in production, with no change in the services that use them.
- **Testability**: tests replace any provider (`overrideProvider`) without touching code.
- **Centralised creation**: connection setup, retries and configuration live in factories, not scattered `new` calls.
- **Clean startup and shutdown**: hooks open and close resources in the right order.

</En>
<Ur>

- **Badalne qabil implementations**: development aur tests me nakli payments, production me asli, un ko istemal karne wali services me koi tabdeeli ke baghair.
- **Testing aasan**: tests code chhue baghair koi bhi provider badal dete hain (`overrideProvider`).
- **Markazi banawat**: connection setup, retries aur configuration factories me rehte hain, bikhre `new` calls me nahi.
- **Saaf shuru aur band**: hooks resources sahi tarteeb se kholte aur band karte hain.

</Ur>

## Picture it

<Tr>
<En>

Think of a **staffing agency** that supplies workers to a company.

- The company asks for a **role**, not a person: "send us a payment clerk" (the token, `PaymentGateway`).
- The agency's **roster** (the module's providers) decides who fills each role: a trainee for practice days (fake gateway), an experienced clerk on live days (card gateway). The company's workflow doesn't change.
- Some roles are filled by **handing over a tool**, not a person: a company stamp or a clock (`useValue`).
- Some workers need **preparation** before they can start: a driver needs a car that has to be fetched first (async factory); the agency waits until the car arrives before sending the driver.
- Workers have a **first-day routine** (onModuleInit) and **clock out** properly when the office closes (onApplicationShutdown).
- "Payments" and "PaymentGateway" can be **two names for the same person** (useExisting).

</En>
<Ur>

Company ko mulazim dene wali **staffing agency** ka sochein.

- Company **ohda** maangti hai, shakhs nahi: "humen payment clerk bhejo" (token, `PaymentGateway`).
- Agency ka **roster** (module ke providers) tay karta hai ke har ohda kaun bharta hai: practice ke dinon me trainee (nakli gateway), live dinon me tajurbekar clerk (card gateway). Company ka kaam ka tareeqa nahi badalta.
- Kuch ohde shakhs ke bajaye **auzaar de kar** bhare jate hain: company ki mohar ya ghari (`useValue`).
- Kuch mulazimon ko shuru karne se pehle **tayyari** chahiye: driver ko gari chahiye jo pehle lani hai (async factory); agency gari aane tak driver ko nahi bhejti.
- Mulazimon ka **pehle din ka mamool** (onModuleInit) hai aur daftar band hone par wo theek se **clock out** karte hain (onApplicationShutdown).
- "Payments" aur "PaymentGateway" **ek hi shakhs ke do naam** ho sakte hain (useExisting).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Four kinds of providers, one service">

<Tr>
<En>
`CheckoutService` asks for a `PaymentGateway`, a clock and an alias. The module decides what they are: options (`useValue`), a fixed clock (`useValue` with a function), a gateway chosen by a factory from the options (`useFactory`), and an alias (`useExisting`). A small script runs the service without an HTTP server, once with the default mode and once with `PAYMENTS_MODE=card`.
</En>
<Ur>
`CheckoutService` `PaymentGateway`, ek clock aur ek alias maangti hai. Module tay karta hai ke wo kya hain: options (`useValue`), muqarrar clock (function ke saath `useValue`), options se factory ka chuna gateway (`useFactory`), aur alias (`useExisting`). Chhota script service ko HTTP server ke baghair chalata hai, ek dafa default mode me aur ek dafa `PAYMENTS_MODE=card` ke saath.
</Ur>
</Tr>

```bash
npx -y @nestjs/cli@12.0.13 new shop-api --package-manager npm --skip-git --strict > /dev/null 2>&1
cd shop-api
mkdir -p src/payments
cat > src/payments/payment-gateway.ts <<'EOF'
// An abstract class works as both a TypeScript type AND a runtime injection token
export abstract class PaymentGateway {
  abstract charge(amountCents: number): Promise<{ id: string; provider: string }>;
}

export class FakePaymentGateway extends PaymentGateway {
  async charge(amountCents: number) {
    return { id: `fake_${amountCents}`, provider: 'fake' };
  }
}

export class CardPaymentGateway extends PaymentGateway {
  constructor(private readonly apiKey: string) { super(); }
  async charge(amountCents: number) {
    return { id: `ch_${amountCents}`, provider: `card (key ending ${this.apiKey.slice(-4)})` };
  }
}
EOF
cat > src/payments/tokens.ts <<'EOF'
export const PAYMENTS_OPTIONS = 'PAYMENTS_OPTIONS';   // string tokens for values that have no class
export const CLOCK = 'CLOCK';
EOF
cat > src/payments/checkout.service.ts <<'EOF'
import { Inject, Injectable } from '@nestjs/common';
import { PaymentGateway } from './payment-gateway.js';
import { CLOCK } from './tokens.js';

@Injectable()
export class CheckoutService {
  constructor(
    private readonly gateway: PaymentGateway,                  // class token: no @Inject needed
    @Inject(CLOCK) private readonly now: () => Date,           // string token: @Inject required
    @Inject('Payments') private readonly alias: PaymentGateway,
  ) {}

  async pay(totalDollars: number) {
    const charge = await this.gateway.charge(Math.round(totalDollars * 100));
    return { ...charge, at: this.now().toISOString(), aliasIsSameInstance: this.alias === this.gateway };
  }
}
EOF
cat > src/payments/payments.module.ts <<'EOF'
import { Module } from '@nestjs/common';
import { PaymentGateway, FakePaymentGateway, CardPaymentGateway } from './payment-gateway.js';
import { CheckoutService } from './checkout.service.js';
import { PAYMENTS_OPTIONS, CLOCK } from './tokens.js';

@Module({
  providers: [
    CheckoutService,                                           // shorthand for { provide: CheckoutService, useClass: CheckoutService }
    { provide: PAYMENTS_OPTIONS, useValue: { mode: process.env.PAYMENTS_MODE ?? 'fake', apiKey: 'sk_test_51Hx9a7Qz' } },
    { provide: CLOCK, useValue: () => new Date('2026-11-15T10:00:00Z') },   // a fixed clock for this demo
    {
      provide: PaymentGateway,                                 // token: the abstract class
      useFactory: (opts: { mode: string; apiKey: string }) =>
        opts.mode === 'card' ? new CardPaymentGateway(opts.apiKey) : new FakePaymentGateway(),
      inject: [PAYMENTS_OPTIONS],                              // factory arguments, in order
    },
    { provide: 'Payments', useExisting: PaymentGateway },     // alias: same instance, second token
  ],
  exports: [CheckoutService],
})
export class PaymentsModule {}
EOF
cat > src/demo.ts <<'EOF'
import { NestFactory } from '@nestjs/core';
import { PaymentsModule } from './payments/payments.module.js';
import { CheckoutService } from './payments/checkout.service.js';

// An application context: the DI container without an HTTP server (scripts, workers, CLIs)
const app = await NestFactory.createApplicationContext(PaymentsModule, { logger: false });
console.log(JSON.stringify(await app.get(CheckoutService).pay(42.5)));
await app.close();
EOF
npm run build --silent
node dist/demo.js
PAYMENTS_MODE=card node dist/demo.js
```

```text output
{"id":"fake_4250","provider":"fake","at":"2026-11-15T10:00:00.000Z","aliasIsSameInstance":true}
{"id":"ch_4250","provider":"card (key ending a7Qz)","at":"2026-11-15T10:00:00.000Z","aliasIsSameInstance":true}
```

<Happened>
<Tr>
<En>

- The **same `CheckoutService` code** used a fake gateway in the first run and the card gateway in the second. Only the factory's input changed; nothing that uses `PaymentGateway` knows which one it got.
- **Abstract class as token**: `PaymentGateway` is abstract, so it can't be instantiated, but it exists at runtime and works as a token. A TypeScript `interface` would disappear after compilation, which is why Nest code uses abstract classes (or tokens) for "interfaces".
- **`useFactory` + `inject`**: Nest resolved `PAYMENTS_OPTIONS` first and passed it into the factory. Factories can inject any providers, including other services.
- **`useValue` for a clock**: the timestamp is always `2026-11-15T10:00:00Z`. Injecting time (and IDs, randomness) instead of calling `new Date()` directly makes code testable.
- **`useExisting`**: `'Payments'` and `PaymentGateway` returned the **same instance** (`aliasIsSameInstance: true`). `useClass` would have created a second one.
- Only 4 digits of the API key appear in the output; never log full secrets.
- `createApplicationContext` builds the container without HTTP, which is how you run Nest code in scripts, cron jobs and queue workers.

</En>
<Ur>

- **Wahi `CheckoutService` code** ne pehli dafa nakli gateway aur doosri dafa card gateway istemal kiya. Sirf factory ka input badla; `PaymentGateway` istemal karne wali koi cheez nahi janti ke use kaun sa mila.
- **Abstract class bator token**: `PaymentGateway` abstract hai, isliye is ka instance nahi ban sakta, magar ye runtime par maujood hai aur token ka kaam karti hai. TypeScript `interface` compilation ke baad ghayab ho jata, isi liye Nest code "interfaces" ke liye abstract classes (ya tokens) istemal karta hai.
- **`useFactory` + `inject`**: Nest ne pehle `PAYMENTS_OPTIONS` resolve kiya aur factory ko diya. Factories koi bhi providers inject kar sakti hain, doosri services samet.
- **Clock ke liye `useValue`**: timestamp hamesha `2026-11-15T10:00:00Z` hai. Seedha `new Date()` bulane ke bajaye waqt (aur IDs, randomness) inject karna code ko testable banata hai.
- **`useExisting`**: `'Payments'` aur `PaymentGateway` ne **wahi instance** diya (`aliasIsSameInstance: true`). `useClass` doosra bana deta.
- Output me API key ke sirf 4 hindse aate hain; poore raaz kabhi log na karein.
- `createApplicationContext` HTTP ke baghair container banata hai, jo scripts, cron jobs aur queue workers me Nest code chalane ka tareeqa hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Async factories and lifecycle hooks">

<Tr>
<En>
The `DB` provider is an **async factory** that takes 200 ms to "connect". `InventoryService` depends on it, warms a cache in `onModuleInit`, and closes the connection in `onApplicationShutdown`. The numbered lines show the order Nest runs everything.
</En>
<Ur>
`DB` provider aisi **async factory** hai jo "connect" hone me 200 ms leti hai. `InventoryService` is par munhasir hai, `onModuleInit` me cache garam karti hai, aur `onApplicationShutdown` me connection band karti hai. Number wali lines wo tarteeb dikhati hain jis me Nest sab kuch chalata hai.
</Ur>
</Tr>

```bash
cd shop-api
mkdir -p src/inventory
cat > src/inventory/inventory.module.ts <<'EOF'
import { Inject, Injectable, Module, OnApplicationShutdown, OnModuleInit } from '@nestjs/common';

export const DB = 'DB';
type Db = { query(sql: string): Promise<number>; close(): Promise<void> };

@Injectable()
export class InventoryService implements OnModuleInit, OnApplicationShutdown {
  constructor(@Inject(DB) private readonly db: Db) {
    console.log('3. InventoryService constructed (the DB is already connected)');
  }
  async onModuleInit() {                              // runs once all providers exist
    console.log(`4. onModuleInit: cache warmed with ${await this.db.query('SELECT count(*) FROM products')} products`);
  }
  async onApplicationShutdown(signal?: string) {      // app.close(), or SIGTERM with enableShutdownHooks()
    await this.db.close();
    console.log(`6. onApplicationShutdown (${signal ?? 'app.close()'}): DB connection closed`);
  }
}

@Module({
  providers: [
    InventoryService,
    {
      provide: DB,
      useFactory: async (): Promise<Db> => {          // async factory: Nest waits before creating dependents
        console.log('1. connecting to the database...');
        await new Promise((r) => setTimeout(r, 200));
        console.log('2. connected');
        return { query: async () => 42, close: async () => {} };
      },
    },
  ],
})
export class InventoryModule {}
EOF
cat > src/inventory-demo.ts <<'EOF'
import { NestFactory } from '@nestjs/core';
import { InventoryModule } from './inventory/inventory.module.js';

const app = await NestFactory.createApplicationContext(InventoryModule, { logger: false });
console.log('5. app ready');
await app.close();
EOF
npm run build --silent
node dist/inventory-demo.js
```

```text output
1. connecting to the database...
2. connected
3. InventoryService constructed (the DB is already connected)
4. onModuleInit: cache warmed with 42 products
5. app ready
6. onApplicationShutdown (app.close()): DB connection closed
```

<Happened>
<Tr>
<En>

- **1-2**: Nest awaited the async factory before anything else. **3**: only then did it construct `InventoryService`, so the constructor always receives a connected client, never a promise.
- **4**: `onModuleInit` ran after all providers were created. Use it for async startup work (warming caches, checking a connection); constructors can't be `async`.
- **5**: the app was ready only after initialisation finished. In an HTTP app, `listen()` happens after this, so no request arrives before the cache is warm.
- **6**: `app.close()` triggered `onApplicationShutdown`, which closed the connection. In production call `app.enableShutdownHooks()` in `main.ts` so a `SIGTERM` from Docker or Kubernetes triggers the same hooks (with the signal name).
- Other hooks: `onApplicationBootstrap` (after all modules initialised), `onModuleDestroy` and `beforeApplicationShutdown` (before connections close, for example to stop accepting work).

</En>
<Ur>

- **1-2**: Nest ne kuch bhi aur karne se pehle async factory ka intezar kiya. **3**: tabhi `InventoryService` banai, isliye constructor ko hamesha connected client milta hai, promise kabhi nahi.
- **4**: `onModuleInit` tamam providers banne ke baad chala. Ise async startup ke kaam (cache garam karna, connection check karna) ke liye istemal karein; constructors `async` nahi ho sakte.
- **5**: app initialisation mukammal hone ke baad hi tayyar hui. HTTP app me `listen()` is ke baad hota hai, isliye cache garam hone se pehle koi request nahi aati.
- **6**: `app.close()` ne `onApplicationShutdown` chalaya, jis ne connection band kiya. Production me `main.ts` me `app.enableShutdownHooks()` bulayen taa ke Docker ya Kubernetes ka `SIGTERM` yahi hooks chalaye (signal ke naam ke saath).
- Doosre hooks: `onApplicationBootstrap` (tamam modules tayyar hone ke baad), `onModuleDestroy` aur `beforeApplicationShutdown` (connections band hone se pehle, maslan naya kaam lena band karne ke liye).

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Choosing implementations inside the service">

```text
@Injectable()
export class CheckoutService {
  private gateway = process.env.NODE_ENV === 'production'
    ? new CardPaymentGateway(process.env.CARD_KEY!)      // env reads and `new` scattered in services
    : new FakePaymentGateway();
}
```

</Bad>
<Good title="Decide in the module, inject the abstraction">

```text
{ provide: PaymentGateway, useFactory: (cfg: ConfigService) =>
    cfg.get('PAYMENTS_MODE') === 'card' ? new CardPaymentGateway(cfg.getOrThrow('CARD_KEY')) : new FakePaymentGateway(),
  inject: [ConfigService] }

constructor(private readonly gateway: PaymentGateway) {}
```

</Good>
</Compare>

<Compare>
<Bad title="Async work in the constructor">

```text
constructor(private readonly db: Db) {
  this.db.query('SELECT …').then((rows) => (this.cache = rows));   // not awaited: requests may see an empty cache
}
```

</Bad>
<Good title="Use onModuleInit">

```text
async onModuleInit() {
  this.cache = await this.db.query('SELECT …');   // Nest waits before the app is ready
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Injecting an interface**: `constructor(private gw: IPaymentGateway)` compiles but fails at runtime because the interface doesn't exist; use an abstract class or `@Inject(TOKEN)`.
- **Typos in string tokens**: `'Clock'` vs `'CLOCK'` fails at startup; export tokens as constants (or `Symbol`s) from one file.
- **Forgetting `inject` in a factory**: the factory receives `undefined` arguments.
- **Keeping per-request state in a singleton service** (`this.currentUser = …`).
- **Using `useClass` when you wanted an alias**: you get two instances with separate state.
- **No shutdown handling**: open DB connections and unfinished jobs when the container is stopped.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Interface inject karna**: `constructor(private gw: IPaymentGateway)` compile hota hai magar runtime par fail hota hai kyun ke interface maujood nahi; abstract class ya `@Inject(TOKEN)` lein.
- **String tokens me typos**: `'Clock'` vs `'CLOCK'` startup par fail hota hai; tokens ek file se constants (ya `Symbol`s) ki tarah export karein.
- **Factory me `inject` bhoolna**: factory ko `undefined` arguments milte hain.
- **Singleton service me har request ki state rakhna** (`this.currentUser = …`).
- **Alias chahiye tha magar `useClass` istemal kiya**: alag state wale do instances milte hain.
- **Shutdown ka intezam nahi**: container rukne par khule DB connections aur adhoori jobs.

</Ur>
</Tr>

    await this.mailer.send(email, 'Welcome!', 'Thanks for joining.');
  }
}

<DeepDive title="More about providers">

**Optional dependencies.** `@Optional()` lets a provider work when a dependency isn't registered (it receives `undefined`).

**Property injection.** `@Inject(TOKEN) private readonly x` on a property instead of the constructor; useful in base classes, but constructor injection is clearer.

**Multiple implementations.** Register several providers under one token array (`{ provide: PLUGINS, useFactory: (...p) => p, inject: [A, B, C] }`) to build plugin systems.

**Scopes.** `@Injectable({ scope: Scope.REQUEST })` creates a provider per request (for example, per-tenant connections); everything that depends on it becomes request-scoped too, which costs performance. `Scope.TRANSIENT` gives each consumer its own instance.

**Non-class providers in exports.** Export tokens just like classes: `exports: [CLOCK, PaymentGateway]`.

**`ModuleRef`.** Resolve providers at runtime (`moduleRef.get(Token)` or `moduleRef.resolve()` for scoped ones) for strategy patterns chosen per request.

</DeepDive>

<DeepDive title="Real world: the payment provider switch that took one line">

An online course platform used a payment provider whose fees rose sharply. The CTO wanted to move to a cheaper provider, keep the old one for existing subscriptions, and try a third provider in one country.

Luckily, two years earlier a developer had written the payments code behind an abstract `PaymentGateway` class with methods like `createCheckout`, `refund` and `verifyWebhook`. Services only injected `PaymentGateway`. The concrete class was chosen by a `useFactory` provider in `PaymentsModule`.

The migration became:

1. Write `NewProviderGateway extends PaymentGateway`, with its own tests using recorded API responses.
2. Change the factory to choose the gateway per checkout: a small `GatewayRouter` provider picked the implementation by country and subscription age.
3. Run the existing checkout and refund tests against all three gateways (the tests used the abstract interface).
4. Switch traffic gradually with a feature flag injected via `useValue` from the config service.

The change shipped in two weeks with no changes to the course, subscription or invoicing services. A comparable migration in another team's Express codebase, where the old provider's SDK was imported directly in 70 files, was estimated at three months.

</DeepDive>

<DeepDive title="Security lens">

- **Secrets through config providers**, never hard-coded in services or committed to Git; validate them at startup in the factory (`getOrThrow`).
- **Use fake gateways only outside production**: guard the factory so a misconfiguration can't silently use a fake payment provider in production (fail fast instead).
- **Close connections on shutdown** to avoid leaking resources and half-finished writes.
- **Don't store user data in singleton fields**; it can leak across requests.
- **Mask secrets in logs and errors**, as the demo did with the API key.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a provider in NestJS?">
Anything Nest's dependency injection container can create and inject, registered under a token in a module: typically @Injectable service classes, but also values, factory results and aliases.
</QA>

<QA q="What are the custom provider types?">
useClass to instantiate a class for a token, useValue to supply an existing value, useFactory to supply the result of a possibly async function that can inject other providers, and useExisting to alias one token to another provider.
</QA>

<QA q="How do you inject something that isn't a class?">
Register it under a string or Symbol token and use @Inject(TOKEN) on the constructor parameter; for interface-like contracts, use an abstract class as the token instead.
</QA>

<QA q="How do you handle async initialisation, such as a database connection?">
Use an async useFactory provider so Nest awaits the connection before creating dependents, and lifecycle hooks such as onModuleInit for async setup and onApplicationShutdown with enableShutdownHooks for cleanup.
</QA>

<QA q="Why inject a clock instead of calling new Date()?">
It makes time a controllable dependency, so tests can fix the current time and verify date logic deterministically without mocking globals.
</QA>

</DeepDive>
