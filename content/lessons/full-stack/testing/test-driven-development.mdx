<BigIdea>
<Tr>
<En>
**Test-driven development (TDD)** flips the usual order: you write a small **failing test** for the next piece of behavior **before** the code exists. The loop is **Red → Green → Refactor**: **red**, write one test and see it fail (which proves the test can fail and really checks something); **green**, write the **simplest code** that makes it pass, even if it looks naive; **refactor**, improve names and structure while all tests stay green. Then repeat with the next example. Each new example forces the code to become a little more general, so you only build what a test demands, and you end up with a full safety net as a side effect. TDD shines for logic with clear inputs and outputs (parsers, pricing, validation), for **bug fixes** (first a test that reproduces the bug), and for designing APIs from the **outside in**, starting from the request and response you want. It's a discipline, not a religion: spikes and UI experiments can come first, with tests added once the shape is clear.
</En>
<Ur>
**Test-driven development (TDD)** aam tarteeb ulat deta hai: aap behavior ke agle hisse ke liye chhota **fail hota test** code ke mojood hone se **pehle** likhte hain. Chakkar hai **Red → Green → Refactor**: **red**, ek test likhein aur fail hota dekhein (jo sabit karta hai ke test fail ho sakta hai aur waqai kuch check karta hai); **green**, **sab se saada code** likhein jo use pass kare, chahe bhola lage; **refactor**, naam aur dhancha behtar karein jabke saare tests green rahein. Phir agli misaal ke saath dohrayen. Har nayi misaal code ko thora aur aam banne par majboor karti hai, isliye aap sirf wahi banate hain jo test maange, aur saath hi poora hifazati jaal ban jata hai. TDD saaf inputs aur outputs wale logic (parsers, qeematen, validation), **bug fixes** (pehle bug dohrane wala test), aur **bahar se andar** APIs design karne me chamakta hai, jo request aur response aap chahte hain wahan se shuru kar ke. Ye nazm hai, mazhab nahi: spikes aur UI tajurbe pehle ho sakte hain, shakal wazeh hone par tests jorein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of **rock climbing with a rope and anchors**.

- Before each move up, the climber clips the rope into a new anchor (writes a test). If they slip, they fall only to the last anchor, not to the ground.
- Each move is small: reach the next hold, clip, rest (red, green, refactor).
- A climber who scrambles up 20 meters without anchors and then tries to add them all at the top (tests written after the fact) has taken all the risk already, and some anchors end up in useless places.
- The anchors also mark the route for the next climber: your tests document how the code is meant to behave.

</En>
<Ur>

**Rassi aur anchors ke saath rock climbing** socheyn.

- Har qadam upar se pehle climber rassi naye anchor me lagata hai (test likhta hai). Phisle to sirf pichle anchor tak girta hai, zameen tak nahi.
- Har qadam chhota hai: agli pakar tak pohncho, clip karo, aaram (red, green, refactor).
- Jo climber anchors ke baghair 20 meter upar chadh kar sab upar ja kar lagane ki koshish kare (baad me likhe tests), woh saara khatra pehle hi le chuka hai, aur kuch anchors bekaar jagahon par lagte hain.
- Anchors agle climber ke liye rasta bhi batate hain: aap ke tests bayan karte hain ke code ka rawaiya kaisa hona chahiye.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Red, green, refactor: a duration parser in three cycles">

<Tr>
<En>
We build `parseDuration('1h30m15s') → 5415` (seconds) test-first. The `run` helper shows only test names, results and the first error line. Cycle 1 starts with an empty file and one example; the "green" code returns a constant on purpose. Cycle 2 adds hours, cycle 3 combined units and invalid input, ending with a refactored, general implementation.
</En>
<Ur>
Hum `parseDuration('1h30m15s') → 5415` (seconds) test-first banate hain. `run` helper sirf tests ke naam, nataij aur pehli error line dikhata hai. Chakkar 1 khaali file aur ek misaal se shuru hota hai; "green" code jaan boojh kar constant lautata hai. Chakkar 2 ghante jorta hai, chakkar 3 mile jule units aur ghalat input, aur aakhir me refactor shuda, aam implementation.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install -D vitest@5.1.1 --silent
mkdir -p src && touch src/duration.js
run() {   # run the tests and show only names, results and the first error line
  npx vitest run --reporter=verbose 2>&1 | sed -E 's/ [0-9]+ms//; s/\x1b\[[0-9;]*m//g' \
    | grep -E '^ +(✓|×) |^ +Tests |^(TypeError|AssertionError|Error):' | sed -E 's#src/duration.test.js > ##' | awk '!seen[$0]++'
}
test_file() { { echo "import { it, expect } from 'vitest';"; echo "import { parseDuration } from './duration.js';"; cat; } > src/duration.test.js; }

echo "=== cycle 1 RED: the first, simplest example"
test_file <<'EOF'
it('reads minutes', () => expect(parseDuration('5m')).toBe(300));
EOF
run
echo "=== cycle 1 GREEN: the least code that passes (yes, really)"
echo "export const parseDuration = (text) => 300;" > src/duration.js
run

echo "=== cycle 2 RED: a second example forces a real implementation"
test_file <<'EOF'
it('reads minutes', () => expect(parseDuration('5m')).toBe(300));
it('reads hours', () => expect(parseDuration('2h')).toBe(7200));
EOF
run
echo "=== cycle 2 GREEN"
cat > src/duration.js <<'EOF'
export function parseDuration(text) {
  const n = Number(text.slice(0, -1));
  return text.endsWith('h') ? n * 3600 : n * 60;
}
EOF
run

echo "=== cycle 3 RED: combined units and bad input"
test_file <<'EOF'
it('reads minutes', () => expect(parseDuration('5m')).toBe(300));
it('reads hours', () => expect(parseDuration('2h')).toBe(7200));
it('reads combined units', () => expect(parseDuration('1h30m15s')).toBe(5415));
it('rejects nonsense', () => expect(() => parseDuration('soon')).toThrow('Invalid duration'));
EOF
run
echo "=== cycle 3 GREEN, then REFACTOR with the tests as a safety net"
cat > src/duration.js <<'EOF'
const SECONDS = { h: 3600, m: 60, s: 1 };
export function parseDuration(text) {
  if (!/^(\d+[hms])+$/.test(text)) throw new Error(`Invalid duration: ${text}`);
  let total = 0;
  for (const [, n, unit] of text.matchAll(/(\d+)([hms])/g)) total += Number(n) * SECONDS[unit];
  return total;
}
EOF
run
```

<Happened>
<Tr>
<En>

- **Cycle 1 red**: `parseDuration is not a function`. Seeing the test fail first matters: a test that has never failed might not be testing anything.
- **Cycle 1 green**: `() => 300` looks silly, but it's honest. The only behavior we specified is "5m is 300". It also proves the test wiring works before any real logic exists.
- **Cycle 2 red**: the second example (`2h → 7200`) broke the constant: **triangulation**. The green code then became general enough for both, and no more.
- **Cycle 3 red**: two new tests failed for clear reasons: `NaN` for combined units, and "expected [Function] to throw" because there was no validation yet.
- **Cycle 3 green + refactor**: a regex validates the format, and a `SECONDS` lookup table replaces the `if`. All four tests stayed green, so the redesign was safe. We never wrote code a test didn't ask for, and ended with a complete set of examples documenting the function.

</En>
<Ur>

- **Chakkar 1 red**: `parseDuration is not a function`. Test ko pehle fail hota dekhna ahem hai: jo test kabhi fail nahi hua shayad kuch test hi na kar raha ho.
- **Chakkar 1 green**: `() => 300` bewaqoofi lagti hai, magar imandar hai. Hum ne sirf ek rawaiya bayan kiya "5m 300 hai". Ye ye bhi sabit karta hai ke koi asli logic hone se pehle test ki wiring chal rahi hai.
- **Chakkar 2 red**: doosri misaal (`2h → 7200`) ne constant tora: **triangulation**. Phir green code dono ke liye kafi aam bana, is se zyada nahi.
- **Chakkar 3 red**: do naye tests wazeh wajah se fail hue: mile jule units ke liye `NaN`, aur "expected [Function] to throw" kyunke abhi validation nahi thi.
- **Chakkar 3 green + refactor**: regex format check karta hai, aur `SECONDS` lookup table `if` ki jagah leti hai. Chaaron tests green rahe, isliye naya design mehfooz tha. Hum ne kabhi aisa code nahi likha jo kisi test ne na maanga ho, aur aakhir me function ko bayan karne wali misalon ka mukammal set mila.

</Ur>

<Step title="TDD for a bug fix, and outside-in for an endpoint">

<Tr>
<En>
A bug report says `"2h 15m"` and `"1H"` are rejected. We first add a test that **reproduces** it, see it fail, then fix it. Next we build an HTTP endpoint **outside-in**: write supertest tests for `GET /timer?duration=…` before the route exists, see them fail with 404, then add the route using the already-tested parser.
</En>
<Ur>
Bug report kehti hai ke `"2h 15m"` aur `"1H"` rad hote hain. Hum pehle aisa test jorte hain jo use **dohraye**, fail hota dekhte hain, phir theek karte hain. Us ke baad HTTP endpoint **bahar se andar** banate hain: route mojood hone se pehle `GET /timer?duration=…` ke supertest tests likhte hain, 404 ke saath fail hota dekhte hain, phir pehle se tested parser istemal kar ke route jorte hain.
</Ur>
</Tr>

```bash
npm install express@5.1.0 --silent && npm install -D supertest@7.3.2 --silent
run() {
  npx vitest run --reporter=verbose 2>&1 | sed -E 's/ [0-9]+ms//; s/\x1b\[[0-9;]*m//g' \
    | grep -E '^ +(✓|×) |^ +Tests |^(TypeError|AssertionError|Error):' | sed -E 's#src/[a-z.]+\.test\.js > ##' | awk '!seen[$0]++'
}
echo "=== bug report: \"2h 15m\" and \"1H\" are rejected. RED: reproduce it as a test first"
cat >> src/duration.test.js <<'EOF'
it('allows spaces and capital letters (bug #42)', () => {
  expect(parseDuration('2h 15m')).toBe(8100);
  expect(parseDuration('1H')).toBe(3600);
});
EOF
run | grep -E 'bug #42|Tests|Error'
echo "=== GREEN: normalize the input, all old tests still pass"
cat > src/duration.js <<'EOF'
const SECONDS = { h: 3600, m: 60, s: 1 };
export function parseDuration(input) {
  const text = String(input).replace(/\s+/g, '').toLowerCase();      // the fix: one line
  if (!/^(\d+[hms])+$/.test(text)) throw new Error(`Invalid duration: ${input}`);
  let total = 0;
  for (const [, n, unit] of text.matchAll(/(\d+)([hms])/g)) total += Number(n) * SECONDS[unit];
  return total;
}
EOF
run | grep -E 'Tests|Error'

echo "=== outside-in: start from the HTTP behavior you want. RED"
cat > src/app.test.js <<'EOF'
import { it, expect } from 'vitest';
import request from 'supertest';
import { app } from './app.js';
it('GET /timer converts a duration', async () => {
  await request(app).get('/timer?duration=1h30m').expect(200, { seconds: 5400 });
});
it('GET /timer rejects a bad duration with 400', async () => {
  const res = await request(app).get('/timer?duration=soon').expect(400);
  expect(res.body.error).toMatch(/Invalid duration/);
});
EOF
echo "import express from 'express'; export const app = express();" > src/app.js
run | grep -E 'GET /timer|Tests|Error'
echo "=== GREEN: the route reuses the unit-tested parser"
cat > src/app.js <<'EOF'
import express from 'express';
import { parseDuration } from './duration.js';
export const app = express();
app.get('/timer', (req, res) => {
  try { res.json({ seconds: parseDuration(req.query.duration ?? '') }); }
  catch (e) { res.status(400).json({ error: e.message }); }
});
EOF
run | grep -E 'GET /timer|Tests'
```

```text output

 × allows spaces and capital letters (bug #42)
Error: Invalid duration: 2h 15m
      Tests  1 failed | 4 passed (5)
=== GREEN: normalize the input, all old tests still pass
      Tests  5 passed (5)
=== outside-in: start from the HTTP behavior you want. RED
 × GET /timer converts a duration
 × GET /timer rejects a bad duration with 400
Error: expected 200 "OK", got 404 "Not Found"
Error: expected 400 "Bad Request", got 404 "Not Found"
```

<Happened>
<Tr>
<En>

- The regression test failed with the **exact error users saw** (`Invalid duration: 2h 15m`): proof that we reproduced the bug, not something else. The fix was one line; all 5 tests passed, so the old behavior didn't break. The test now guards bug #42 forever.
- The endpoint tests described the API first: a 200 with `{ seconds: 5400 }` and a 400 with the parser's message. Both failed with **404**, the right reason: the route didn't exist yet.
- The route itself was tiny because the hard logic was already built and tested underneath. That's the outside-in rhythm: an outer test sets the goal, inner unit tests (written TDD-style) do the detailed work, and the outer test turns green when everything is wired together.

</En>
<Ur>

- Regression test **bilkul wahi error** ke saath fail hua jo users ne dekha (`Invalid duration: 2h 15m`): saboot ke hum ne bug hi dohraya, kuch aur nahi. Fix ek line thi; saare 5 tests pass hue, isliye purana rawaiya nahi toota. Test ab hamesha bug #42 ki hifazat karta hai.
- Endpoint tests ne pehle API bayan ki: `{ seconds: 5400 }` ke saath 200 aur parser ke paigham ke saath 400. Dono **404** se fail hue, sahi wajah: route abhi mojood nahi tha.
- Route khud chhota tha kyunke mushkil logic pehle se neeche bana aur tested tha. Yahi bahar se andar ki taal hai: bahar ka test maqsad tay karta hai, andar ke unit tests (TDD andaz me likhe) tafseeli kaam karte hain, aur sab jurne par bahar ka test green ho jata hai.

## Common mistakes

<Compare>
<Bad title="Writing many tests, then all the code">

```text
// 25 tests written up front for every feature you can imagine
// then 300 lines of code, then 19 failures to untangle at once
```

</Bad>
<Good title="One test, one small step">

```text
it('reads minutes', …)        -> red -> green -> refactor
it('reads hours', …)          -> red -> green -> refactor
it('reads combined units', …) -> red -> green -> refactor
```

</Good>
</Compare>

<Compare>
<Bad title="Fixing a bug without reproducing it">

```text
// "users can't enter 2h 15m" -> change the regex, click around, ship
// next month someone tightens the regex again; nobody notices
```

</Bad>
<Good title="Failing test first, then the fix">

```text
it('allows spaces and capital letters (bug #42)', () => expect(parseDuration('2h 15m')).toBe(8100));
// see it fail with the user's error -> fix -> green -> the test stays
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Skipping the red step**: if you never saw it fail, the test might be broken (wrong import, missing `await`).
- **Skipping refactor**: TDD without cleanup leaves a pile of special cases.
- **Writing more code than the test needs**: extra features have no tests and no proven need.
- **Testing private details**: tests coupled to internals make refactoring painful. Test through the public function or API.
- **Giant steps**: if a cycle takes an hour, the step was too big. Split the example.
- **Treating TDD as all-or-nothing**: spike to learn, then delete the spike and rebuild test-first.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Red qadam chhorna**: agar kabhi fail hota nahi dekha to test toota ho sakta hai (ghalat import, ghayab `await`).
- **Refactor chhorna**: safai ke baghair TDD khaas halaton ka dher chhorta hai.
- **Test ki zaroorat se zyada code likhna**: extra features ke na tests hain na sabit shuda zaroorat.
- **Nijji tafseelat test karna**: andaruni hisson se jure tests refactoring ko takleef deh banate hain. Public function ya API ke zariye test karein.
- **Bare qadam**: agar ek chakkar ghanta le to qadam bara tha. Misaal ko torein.
- **TDD ko sab ya kuch nahi samajhna**: seekhne ke liye spike karein, phir spike mita kar test-first dobara banayen.

</Ur>
</Tr>

<Challenge title="TDD a password strength checker">

<Tr>
<En>
Build `checkPassword(pw)` returning `{ ok, problems: [] }` test-first, one rule per cycle: (1) at least 12 characters; (2) not in a small list of common passwords; (3) not containing the user's email name (pass it as a second argument). Write your test list first, then show the order of red/green steps.
</En>
<Ur>
`checkPassword(pw)` test-first banayen jo `{ ok, problems: [] }` lautaye, har chakkar me ek rule: (1) kam az kam 12 huroof; (2) aam passwords ki chhoti list me na ho; (3) user ki email ka naam shamil na ho (doosre argument ke tor par dein). Pehle apni test list likhein, phir red/green qadmon ki tarteeb dikhayen.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text
test list:
  "correct horse battery"           -> ok
  "short"                           -> problem "too short"
  "password1234"                    -> problem "too common"
  "jane-rocks-2026" + jane@example.com -> problem "contains your name"

cycle 1: it('accepts a long password') -> red (not a function) -> green: return { ok: true, problems: [] }
cycle 2: it('rejects short ones')       -> red -> green: if (pw.length < 12) problems.push('too short')
```

<DeepDive title="More about TDD">

**Origins.** Kent Beck popularized TDD with Extreme Programming; his book "Test-Driven Development: By Example" introduced the test list, fake it and triangulation.

**Schools.** Classic (Chicago) TDD grows designs from the inside with real objects; London-school (mockist) TDD works outside-in with mocks for collaborators not yet written. Many developers mix both.

**BDD.** Behavior-driven development phrases tests as scenarios ("Given a cart over $50, when I apply SAVE10, then…"), sometimes with tools like Cucumber, to share examples with non-developers.

**Legacy code.** Before changing untested code, write characterization tests that record what it does now, then refactor in small steps (Michael Feathers, "Working Effectively with Legacy Code").

**Mutation testing.** Tools like Stryker change your code on purpose (`>` to `>=`) and check that a test fails, measuring test strength better than coverage.

**Research.** Studies on TDD show mixed productivity results but generally fewer defects; the benefits depend heavily on step size and discipline.

</DeepDive>

<DeepDive title="Real world: the rounding bug that kept coming back">

An invoicing service had a rounding bug where some line items were off by a cent. A developer fixed it by changing `Math.round` to `toFixed(2)`. Three months later, another developer "simplified" the code back to `Math.round` for performance, and the bug returned, this time on a large customer's quarterly invoice, which their finance team caught.

What the team changed:

1. Bugs are fixed test-first: the pull request must include a test that fails without the fix. Reviewers check out the test alone to see it fail.
2. A table of the exact problematic amounts from both incidents became a permanent test.
3. Money logic moved to integer cents with a single, TDD-built rounding function.
4. Mutation testing (Stryker) runs weekly on the billing module to find weak tests.

</DeepDive>

<DeepDive title="Security lens">

- **Security bugs deserve regression tests too**: an injection, an authorization bypass or a token check, reproduced as a failing test, fixed, and kept.
- **Write tests for the attack before the defense**: "user B gets 404 for user A's invoice" fails first, then you add the check.
- **Abuse cases in the test list**: empty input, huge input, unicode tricks, negative numbers, repeated requests.
- **Don't let a quick green hide a hole**: "fake it" is a step, not a shipping strategy; the next test must force real validation.
- **Keep security tests fast** so they run on every change, not only in a nightly suite.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is test-driven development?">
A practice where you write a failing automated test for a small piece of behavior first, write the minimum code to pass it, then refactor while keeping tests green, repeating in short cycles.
</QA>

<QA q="What are the benefits and costs of TDD?">
Benefits are high coverage, tests that are proven to fail, simpler designs driven by usage, and safe refactoring. Costs are upfront time, a learning curve, and less value for exploratory or highly visual work.
</QA>

<QA q="Why write the minimum code to pass a test?">
It prevents speculative features, keeps steps small and verifiable, and lets additional examples drive the design toward the real general solution, a technique called triangulation.
</QA>

<QA q="How do you apply TDD to bug fixes?">
Reproduce the bug with a test that fails for the same reason users see, fix the code until it passes, and keep the test as a regression guard.
</QA>

<QA q="What is outside-in TDD?">
Starting with a high-level test of the desired behavior, such as an API or UI test, and implementing the inner components test-first until the outer test passes.
</QA>

</DeepDive>
