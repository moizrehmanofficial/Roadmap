<BigIdea>
<Tr>
<En>
A **test** is a small program that runs your code with known inputs and **checks** the result: "an empty cart costs $0", "an order of $50 ships free". You run the whole set with one command, in seconds, as often as you like, and your CI server runs it on every pull request. That turns "I hope I didn't break anything" into "62 tests passed": tests catch **regressions** (things that used to work and broke), document the rules in a form that can't go out of date, and make refactoring safe. Different tests trade **speed** for **realism**, which is what the **testing pyramid** shows: a wide base of **unit tests** (one function, no network or database, milliseconds each), a middle layer of **integration tests** (several parts together, such as your route plus a real database), and a small top of **end-to-end tests** (the whole running app, like a user would use it). Write most tests where they are cheap and fast, and enough higher-level tests to catch what only shows up when the pieces are connected.
</En>
<Ur>
**Test** ek chhota program hai jo aap ka code maloom inputs ke saath chalata aur nateeja **check** karta hai: "khaali cart $0 ka hai", "$50 ka order muft ship hota hai". Aap poora set ek command se, seconds me, jitni dafa chahein chalate hain, aur aap ka CI server har pull request par chalata hai. Is se "umeed hai kuch toota nahi" "62 tests pass hue" ban jata hai: tests **regressions** (jo pehle chalta tha aur toot gaya) pakarte hain, rules ko aisi shakal me likhte hain jo purani nahi hoti, aur refactoring ko mehfooz banate hain. Mukhtalif tests **raftaar** ke badle **haqeeqat** dete hain, aur yahi **testing pyramid** dikhata hai: **unit tests** ki chauri bunyad (ek function, network ya database nahi, har ek milliseconds), **integration tests** ki darmiyani tah (kayi hisse saath, jaise aap ka route plus asli database), aur **end-to-end tests** ki chhoti choti (poori chalti app, jaise user istemal karega). Zyada tests wahan likhein jahan woh saste aur tez hain, aur itne ooper wale tests jo sirf hisson ke jurne par zahir hone wali cheezen pakar sakein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of how a **car** is checked before it reaches you.

- Every bolt, sensor and chip is tested on its own at the factory, thousands of times, quickly and cheaply: **unit tests**.
- Then the engine is run on a test stand with the real gearbox and fuel system: **integration tests**. Slower, but they catch parts that each work alone and fail together.
- Finally a driver takes a few finished cars around a test track: **end-to-end tests**. The most realistic, the slowest and most expensive, so only a few.
- Nobody tests only on the track: a failure there tells you "something is wrong", not which bolt. And nobody tests only bolts: a perfect bolt in the wrong hole still loses a wheel.

</En>
<Ur>

Socheyn **gaari** aap tak pohnchne se pehle kaise check hoti hai.

- Har bolt, sensor aur chip factory me akela test hota hai, hazaron dafa, jaldi aur sasta: **unit tests**.
- Phir engine asli gearbox aur fuel system ke saath test stand par chalaya jata hai: **integration tests**. Sust, magar woh hisse pakarte hain jo akele chalte aur saath fail hote hain.
- Aakhir me ek driver chand tayyar gaariyan test track par chalata hai: **end-to-end tests**. Sab se haqeeqi, sab se sust aur mehnge, isliye sirf chand.
- Koi sirf track par test nahi karta: wahan nakami batati hai "kuch ghalat hai", ye nahi ke kaunsa bolt. Aur koi sirf bolts test nahi karta: ghalat surakh me perfect bolt bhi pahiya gira deta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Your first tests, and the refactor they catch">

<Tr>
<En>
`cartTotal()` adds up a cart in **cents**, applies a `SAVE10` coupon on orders of $50 or more, and charges $4.99 shipping below $50 (after the discount). Six tests, written with Node's built-in `node:test` and `assert`, describe those rules. Then a teammate "simplifies" one line. Timings are removed from the runner's output so it stays repeatable.
</En>
<Ur>
`cartTotal()` cart ko **cents** me jorta hai, $50 ya zyada ke orders par `SAVE10` coupon lagata hai, aur $50 se kam par (discount ke baad) $4.99 shipping leta hai. Node ke built-in `node:test` aur `assert` se likhe chhe tests ye rules bayan karte hain. Phir ek saathi ek line "saada" kar deta hai. Output dohrane layak rakhne ke liye runner ke output se waqt hata diye gaye hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module
cat > cart.js <<'EOF'
// Prices are in cents to avoid floating-point surprises
export function cartTotal(items, { coupon } = {}) {
  const subtotal = items.reduce((sum, i) => sum + i.priceCents * i.qty, 0);
  const discount = coupon === 'SAVE10' && subtotal >= 5000 ? Math.round(subtotal * 0.1) : 0;
  const shipping = subtotal - discount >= 5000 || subtotal === 0 ? 0 : 499;
  return subtotal - discount + shipping;
}
EOF
cat > cart.test.js <<'EOF'
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { cartTotal } from './cart.js';

const book = { priceCents: 1999, qty: 1 };
const lamp = { priceCents: 4500, qty: 1 };

test('empty cart costs nothing', () => assert.equal(cartTotal([]), 0));
test('small order pays $4.99 shipping', () => assert.equal(cartTotal([book]), 1999 + 499));
test('orders of $50 or more ship free', () => assert.equal(cartTotal([book, lamp]), 6499));
test('SAVE10 takes 10% off orders of $50+', () => assert.equal(cartTotal([book, lamp], { coupon: 'SAVE10' }), 5849));
test('SAVE10 does nothing under $50', () => assert.equal(cartTotal([book], { coupon: 'SAVE10' }), 2498));
test('discount that drops the order under $50 brings shipping back', () =>
  assert.equal(cartTotal([{ priceCents: 5200, qty: 1 }], { coupon: 'SAVE10' }), 5200 - 520 + 499));
EOF
run() { node --test --test-reporter=spec 2>&1 | sed -E 's/ \([0-9.]+m?s\)//' | grep -vE '^ℹ (duration_ms|cancelled|skipped|todo|suites)'; }
echo "--- 1. the tests describe the rules, and they pass"
run

echo "--- 2. a teammate \"simplifies\" the code: free shipping is now decided before the discount"
sed -i 's/const shipping = subtotal - discount >= 5000/const shipping = subtotal >= 5000/' cart.js
node --test --test-reporter=spec 2>&1 | sed -E 's/ \([0-9.]+m?s\)//' > out.txt; code=${PIPESTATUS[0]}
grep -E '^ℹ (pass|fail)' out.txt
sed -n '/^test at/,/!==/p' out.txt | grep -v '^ *$'
echo "exit code: $code   (non-zero, so CI blocks the merge)"
```

```text output
--- 1. the tests describe the rules, and they pass
✔ empty cart costs nothing
✔ small order pays $4.99 shipping
✔ orders of $50 or more ship free
✔ SAVE10 takes 10% off orders of $50+
✔ SAVE10 does nothing under $50
✔ discount that drops the order under $50 brings shipping back
ℹ tests 6
ℹ pass 6
ℹ fail 0
--- 2. a teammate "simplifies" the code: free shipping is now decided before the discount
ℹ pass 5
ℹ fail 1
test at cart.test.js:13:1
✖ discount that drops the order under $50 brings shipping back
  AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
  4680 !== 5179
exit code: 1   (non-zero, so CI blocks the merge)
```

<Happened>
<Tr>
<En>

- Each test name reads like a rule, and together they are a precise spec. The test names are what you'll see when one fails, so write them as sentences about behavior.
- The change looked harmless and the app would still "work", but one rule silently changed: a $52 order with the coupon drops to $46.80 and should pay shipping again. Exactly one test failed, named the rule, and showed **4680 !== 5179**, pointing straight at the bug.
- The runner exited with **code 1**. That's what CI looks at: a failing test blocks the merge before customers see the bug.
- Testing in **cents** with integers avoids floating-point surprises (`0.1 + 0.2`), and edge cases (empty cart, exactly $50, discounts crossing the threshold) are where bugs hide. Good tests aim there.

</En>
<Ur>

- Har test ka naam ek rule ki tarah parha jata hai, aur saath me woh ek theek spec hain. Fail hone par yahi naam nazar aate hain, isliye inhe rawaiye ke bare me jumlon ki tarah likhein.
- Tabdeeli masoom lagti thi aur app ab bhi "chalti", magar ek rule khamoshi se badal gaya: coupon ke saath $52 ka order $46.80 ho jata hai aur use dobara shipping deni chahiye. Theek ek test fail hua, rule ka naam liya, aur **4680 !== 5179** dikhaya, seedha bug ki taraf ishara.
- Runner **code 1** ke saath band hua. CI yahi dekhta hai: fail hota test customers ke bug dekhne se pehle merge rok deta hai.
- Integers ke saath **cents** me test karna floating-point ki hairaniyon (`0.1 + 0.2`) se bachata hai, aur edge cases (khaali cart, theek $50, threshold paar karte discounts) wahan hain jahan bugs chhupte hain. Achhe tests wahin nishana lagate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The pyramid in practice: what each layer catches">

<Tr>
<En>
A "top customers" report has three parts: `formatTop()` (pure logic), `topCustomers()` (SQL), and an Express route. The SQL has a bug: `ORDER BY total ASC` returns the **smallest** customers. We test it three ways: **unit** tests (the formatter, and `topCustomers` with a fake database), an **integration** test (the app in-process with a real PostgreSQL), and an **end-to-end** test (the real server started as its own process, called over HTTP). Then we fix the SQL and run all three again.
</En>
<Ur>
"Top customers" report ke teen hisse hain: `formatTop()` (khalis logic), `topCustomers()` (SQL), aur ek Express route. SQL me bug hai: `ORDER BY total ASC` **sab se chhote** customers lautata hai. Hum ise teen tarah test karte hain: **unit** tests (formatter, aur nakli database ke saath `topCustomers`), **integration** test (asli PostgreSQL ke saath usi process me app), aur **end-to-end** test (asli server apne process me shuru, HTTP se bulaya). Phir SQL theek kar ke teeno dobara chalate hain.
</Ur>
</Tr>

```bash
npm install express@5.1.0 pg@8.23.1 --silent
export PGPASSWORD=postgres
psql -q -h localhost -U postgres -c 'DROP DATABASE IF EXISTS shop_test' -c 'CREATE DATABASE shop_test' 2> /dev/null
psql -q -h localhost -U postgres -d shop_test -c "CREATE TABLE orders (customer text, total_cents int)" \
  -c "INSERT INTO orders VALUES ('Jane Doe', 9000), ('Jane Doe', 6000), ('John Smith', 2000), ('Ana Lee', 12000), ('Omar Ali', 500)"
mkdir -p src test
cat > src/report.js <<'EOF'
// Pure logic: easy to unit test
export const formatTop = (rows) => rows.map((r, i) => `${i + 1}. ${r.customer} ($${(r.total / 100).toFixed(2)})`);
// Data access: the SQL has a bug (ASC instead of DESC), so it returns the SMALLEST customers
export const topCustomers = async (db, limit) =>
  (await db.query('SELECT customer, sum(total_cents)::int AS total FROM orders GROUP BY customer ORDER BY total ASC LIMIT $1', [limit])).rows;
EOF
cat > src/app.js <<'EOF'
import express from 'express';
import { formatTop, topCustomers } from './report.js';
export const createApp = (db) => express().get('/reports/top', async (req, res) => res.json(formatTop(await topCustomers(db, 2))));
EOF
cat > src/server.js <<'EOF'
import pg from 'pg';
import { createApp } from './app.js';
const db = new pg.Pool({ connectionString: process.env.DATABASE_URL });
createApp(db).listen(process.env.PORT, () => console.log('ready'));
EOF
# 1. Unit tests: pure function, and the route with a FAKE database
cat > test/unit.test.js <<'EOF'
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { formatTop, topCustomers } from '../src/report.js';
test('formats ranked lines', () => assert.deepEqual(formatTop([{ customer: 'Ana Lee', total: 12000 }]), ['1. Ana Lee ($120.00)']));
test('topCustomers returns what the database returns', async () => {
  const fakeDb = { query: async () => ({ rows: [{ customer: 'Ana Lee', total: 12000 }] }) };   // the SQL never runs
  assert.deepEqual(await topCustomers(fakeDb, 2), [{ customer: 'Ana Lee', total: 12000 }]);
});
EOF
# 2. Integration test: the app with a REAL PostgreSQL, in-process
cat > test/integration.test.js <<'EOF'
import { test, after } from 'node:test';
import assert from 'node:assert/strict';
import pg from 'pg';
import { createApp } from '../src/app.js';
const db = new pg.Pool({ connectionString: 'postgres://postgres:postgres@localhost:5432/shop_test' });
after(() => db.end());
test('GET /reports/top lists the two biggest customers', async () => {
  const server = createApp(db).listen(0);
  const res = await fetch(`http://localhost:${server.address().port}/reports/top`);
  assert.deepEqual(await res.json(), ['1. Jane Doe ($150.00)', '2. Ana Lee ($120.00)']);
  server.close();
});
EOF
# 3. End-to-end test: start the real server as a separate process, like production
cat > test/e2e.test.js <<'EOF'
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { spawn } from 'node:child_process';
test('the running server answers the report', async () => {
  const proc = spawn('node', ['src/server.js'], { env: { ...process.env, PORT: '3456', DATABASE_URL: 'postgres://postgres:postgres@localhost:5432/shop_test' } });
  await new Promise((ok, fail) => { const t = setTimeout(() => fail(new Error('server did not start')), 5000); proc.stdout.once('data', () => { clearTimeout(t); ok(); }); });
  try {
    const res = await fetch('http://localhost:3456/reports/top');
    assert.equal(res.status, 200);
    assert.equal((await res.json())[0], '1. Jane Doe ($150.00)');
  } finally { proc.kill(); }
});
EOF
layer() { timeout 60 node --test "test/$1.test.js" > /dev/null 2>&1 && r=PASS || r=FAIL; printf '%-12s %s\n' "$1" "$r"; }
echo "--- with the SQL bug"
layer unit; layer integration; layer e2e
echo "--- fix the SQL (ASC -> DESC) and run again"
sed -i 's/ORDER BY total ASC/ORDER BY total DESC/' src/report.js
layer unit; layer integration; layer e2e
```

```text output
--- with the SQL bug
unit         PASS
integration  FAIL
e2e          FAIL
--- fix the SQL (ASC -> DESC) and run again
unit         PASS
integration  PASS
e2e          PASS
```

<Happened>
<Tr>
<En>

- The **unit tests passed with the bug**. The formatter is fine, and the fake database returned whatever we told it to; the real SQL never ran. Unit tests prove your logic under your assumptions, not that your assumptions about the database are right.
- The **integration test failed**: running the real query against real data returned the wrong customers. Bugs in SQL, ORM mappings, JSON shapes and middleware order live at this layer.
- The **end-to-end test failed too**, and it would also have caught problems the others can't: the server not starting, a missing environment variable, a wrong port.
- After fixing `ASC` → `DESC`, all three passed. The unit tests run in milliseconds; the integration test needs a database; the e2e test has to start a whole server process. That cost difference is why the pyramid has many unit tests, fewer integration tests and only a few e2e tests, each layer doing what it does best.

</En>
<Ur>

- **Unit tests bug ke saath pass hue**. Formatter theek hai, aur nakli database ne wahi lautaya jo hum ne kaha; asli SQL kabhi chala hi nahi. Unit tests aap ke mafrozon ke tahat aap ka logic sabit karte hain, ye nahi ke database ke bare me aap ke mafrozat sahi hain.
- **Integration test fail hua**: asli data par asli query ne ghalat customers lautaye. SQL, ORM mappings, JSON shakal aur middleware ki tarteeb ke bugs isi tah par rehte hain.
- **End-to-end test bhi fail hua**, aur ye woh masle bhi pakarta jo baqi nahi pakar sakte: server ka shuru na hona, ghayab environment variable, ghalat port.
- `ASC` → `DESC` theek karne ke baad teeno pass hue. Unit tests milliseconds me chalte hain; integration test ko database chahiye; e2e test ko poora server process shuru karna parta hai. Isi qeemat ke farq ki wajah se pyramid me bohot unit tests, kam integration tests aur sirf chand e2e tests hain, har tah woh karti hai jo woh sab se achha karti hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Testing implementation details">

```text
test('cartTotal calls reduce once', () => {
  const spy = vi.spyOn(Array.prototype, 'reduce');
  cartTotal([book]);
  expect(spy).toHaveBeenCalledTimes(1);   // breaks on any refactor, catches no real bug
});
```

</Bad>
<Good title="Testing behavior through the public interface">

```text
test('small order pays $4.99 shipping', () => {
  assert.equal(cartTotal([book]), 1999 + 499);   // survives refactors, fails when the rule breaks
});
```

</Good>
</Compare>

<Compare>
<Bad title="An upside-down pyramid (the ice-cream cone)">

```text
5 unit tests, 0 integration tests, 120 browser E2E tests
-> 40-minute CI, random failures, nobody knows which part broke
```

</Bad>
<Good title="Many fast tests, a few slow ones">

```text
400 unit tests (seconds) + 60 integration tests (a minute, real DB in Docker)
+ 8 E2E tests for sign-up, login, checkout, refund
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Tests that never fail**: write the test, then break the code on purpose once to see it fail.
- **Mocking everything**: tests that only check your mocks pass while the real system is broken, as the SQL bug showed.
- **Chasing 100% coverage**: coverage shows what ran, not what was checked. Aim for meaningful assertions on important code.
- **Ignoring flaky tests**: a test that fails randomly trains everyone to ignore failures. Fix or remove it.
- **Tests that depend on each other or on order**: each test sets up its own data.
- **Not running tests in CI**: tests only on one laptop protect nobody.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Kabhi fail na hone wale tests**: test likhein, phir ek dafa jaan boojh kar code toren aur fail hota dekhein.
- **Har cheez mock karna**: sirf aap ke mocks check karne wale tests pass hote hain jabke asli system toota hota hai, jaise SQL bug ne dikhaya.
- **100% coverage ke peeche bhagna**: coverage batati hai kya chala, ye nahi ke kya check hua. Ahem code par ba-maani assertions ka nishana rakhein.
- **Flaky tests nazar andaz karna**: be-tarteeb fail hone wala test sab ko nakamiyan nazar andaz karna sikhata hai. Theek karein ya hata dein.
- **Ek doosre ya tarteeb par munhasir tests**: har test apna data khud set karta hai.
- **CI me tests na chalana**: sirf ek laptop par tests kisi ki hifazat nahi karte.

</Ur>
</Tr>

<DeepDive title="More about testing strategy">

**Other shapes.** The "testing trophy" (popular for frontends) puts most weight on integration tests; the idea is the same: favor tests that give the most confidence per second of runtime.

**Test runners.** Node's built-in `node:test` needs no install; Vitest and Jest add watch mode, snapshots, mocking helpers and coverage (next lesson). Playwright drives real browsers for E2E.

**Test doubles.** Fakes (working lightweight implementations), stubs (canned answers), mocks (verify calls) and spies (record calls). Use them at boundaries you don't control, such as payment providers and email.

**Static checks.** TypeScript, ESLint and schema validation catch whole classes of bugs before any test runs; they're the layer under the pyramid.

**Contract tests.** When services talk to each other, contract tests (for example with Pact) check both sides agree on the API shape without full E2E environments.

**Production checks.** Smoke tests after deploy, health checks, monitoring and feature flags catch what tests can't.

</DeepDive>

<DeepDive title="Real world: the green build that shipped a broken checkout">

A team had 2,000 unit tests and 95% coverage. Their payment service was tested with a mocked payment provider client that returned `{ status: 'succeeded' }`. When the provider's real API started returning `{ status: 'requires_action' }` for 3-D Secure cards, the code treated it as a failure. All tests passed; a third of European checkouts failed for two days.

What they changed:

1. Integration tests against the provider's sandbox for the main payment paths, run nightly and before releases.
2. The mock was rebuilt from recorded real responses, including the less common statuses.
3. One E2E test pays with each of the provider's test cards (plain, 3-D Secure, declined) on a staging deploy.
4. Alerts on checkout success rate, which would have caught it in minutes instead of days.

</DeepDive>

<DeepDive title="Security lens">

- **Security rules deserve tests**: 401 without a session, 403 for the wrong role, 404 for another tenant's data. Regression tests stop old vulnerabilities from coming back.
- **Never test against production data or services** with real customers; use seeded, fake data.
- **Keep secrets out of tests and fixtures**: use test keys and environment variables in CI.
- **Dependency updates** are much safer with a good test suite, so you can apply security patches quickly.
- **Fuzz and property-based tests** (for example fast-check) find inputs you'd never think of, including ones that crash parsers.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the testing pyramid?">
A guideline to have many fast, isolated unit tests at the base, fewer integration tests in the middle that check components working together, and a small number of slow end-to-end tests at the top that exercise the whole system like a user.
</QA>

<QA q="What's the difference between unit and integration tests?">
Unit tests check one unit in isolation, replacing collaborators with test doubles, and run in milliseconds. Integration tests run several real components together, such as code plus a real database, and catch wiring, query and configuration problems.
</QA>

<QA q="Is 100% code coverage a good goal?">
Not by itself. Coverage measures executed lines, not meaningful assertions, and chasing it leads to low-value tests. Use it to find untested important code, and focus on behavior and risk.
</QA>

<QA q="How do you deal with flaky tests?">
Treat them as bugs: find the cause, often timing, shared state, order dependence or external services; fix them with deterministic data, waiting on conditions instead of sleeps, and isolation; quarantine temporarily if needed but don't ignore them.
</QA>

<QA q="What should you test first in an existing codebase without tests?">
The most critical and most frequently changed paths, and every bug as it is fixed, often starting with a few integration or end-to-end tests around key flows before refactoring, then adding unit tests as code is improved.
</QA>

</DeepDive>
