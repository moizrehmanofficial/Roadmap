<BigIdea>
<Tr>
<En>
A **unit test** checks one small piece of code (usually a function) on its own: given these inputs, expect this output, or this error. Because it touches no network, database or real clock, it runs in **milliseconds**, so you can have hundreds and run them on every save. **Vitest** and **Jest** are the most popular JavaScript test runners; their APIs are nearly identical (`describe`, `it`/`test`, `expect`, `vi.fn()`/`jest.fn()`). Vitest is faster, works with ESM and TypeScript out of the box, and is the default for Vite projects; Jest is everywhere in older code and React Native. The skills transfer completely: pick the right **matcher** (`toBe` for primitives and identity, `toEqual` for contents, `toThrow` for errors), cover edge cases with **table-driven tests**, control time with **fake timers**, `await` async results with **`resolves`/`rejects`**, and read **coverage** as a map of untested code, not a score to max out. Good unit tests test **behavior**, have descriptive names, and fail with a message that tells you exactly what broke.
</En>
<Ur>
**Unit test** code ka ek chhota hissa (aam taur par function) akela check karta hai: ye inputs do, ye output ya ye error ki tawaqqo. Kyunke ye network, database ya asli ghari ko nahi chhuta, ye **milliseconds** me chalta hai, isliye aap ke saikron ho sakte hain aur har save par chal sakte hain. **Vitest** aur **Jest** sab se mashhoor JavaScript test runners hain; un ki APIs taqreeban ek jaisi hain (`describe`, `it`/`test`, `expect`, `vi.fn()`/`jest.fn()`). Vitest tez hai, ESM aur TypeScript ke saath seedha chalta hai, aur Vite projects ka default hai; Jest purane code aur React Native me har jagah hai. Hunar poori tarah muntaqil hota hai: sahi **matcher** chunein (primitives aur pehchan ke liye `toBe`, mawad ke liye `toEqual`, errors ke liye `toThrow`), **table-driven tests** se edge cases cover karein, **fake timers** se waqt qaboo karein, **`resolves`/`rejects`** se async nataij `await` karein, aur **coverage** ko untested code ka naqsha samjhein, zyada karne wala score nahi. Achhe unit tests **rawaiya** test karte hain, wazeh naam rakhte hain, aur aise paigham ke saath fail hote hain jo bilkul batata hai kya toota.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **kitchen scale being calibrated**.

- You put known weights on it (100 g, 500 g, 1 kg) and check the display each time: that's a **table-driven test**: inputs and expected outputs side by side.
- You also try the awkward cases: nothing on the scale, something too heavy, a wet bag: **edge cases** and **error cases**.
- You don't test the scale by cooking a full dinner (that's an end-to-end test); you test it on the bench, quickly, in isolation.
- And when you need to know whether a timer goes off after 10 minutes, you don't wait 10 minutes: you **fast-forward the clock** (fake timers).

</En>
<Ur>

**Kitchen scale ki calibration** socheyn.

- Aap us par maloom wazan rakhte hain (100 g, 500 g, 1 kg) aur har dafa display check karte hain: ye **table-driven test** hai: inputs aur mutawaqqa outputs saath saath.
- Aap mushkil surten bhi aazmate hain: scale par kuch nahi, bohot bhaari cheez, geela thaila: **edge cases** aur **error cases**.
- Aap scale ko poora khana paka kar test nahi karte (ye end-to-end test hai); bench par, jaldi, akela test karte hain.
- Aur jab jaanna ho ke timer 10 minute baad bajta hai, to 10 minute intezar nahi karte: **ghari aage chala dete hain** (fake timers).

</Ur>
</Tr>

<Walkthrough>

<Step title="Matchers, tables and failure diffs">

<Tr>
<En>
`money.js` parses prices into cents, formats cents, splits a bill without losing a cent, and builds an invoice. `money.test.js` uses `describe`/`it`, two `test.each` tables (valid and invalid prices), and the everyday matchers. Then a "cleanup" removes the leftover-cents logic in `splitBill`, and we read the failure. Timings and colors are stripped from the output.
</En>
<Ur>
`money.js` qeematon ko cents me parse karta, cents format karta, ek cent khoye baghair bill baantta, aur invoice banata hai. `money.test.js` `describe`/`it`, do `test.each` tables (sahi aur ghalat qeematen), aur rozmarra ke matchers istemal karta hai. Phir ek "safai" `splitBill` me bache cents wala logic hata deti hai, aur hum nakami parhte hain. Output se waqt aur rang hata diye gaye hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install -D vitest@5.1.1 --silent
mkdir -p src
cat > src/money.js <<'EOF'
export function parsePrice(input) {
  const match = /^\$?(\d{1,7})(?:\.(\d{2}))?$/.exec(String(input).trim());
  if (!match) throw new Error(`Invalid price: ${input}`);
  return Number(match[1]) * 100 + Number(match[2] ?? 0);          // cents
}
export const formatCents = (cents) => `$${(cents / 100).toFixed(2)}`;
export function splitBill(totalCents, people) {
  if (!Number.isInteger(people) || people < 1) throw new RangeError('people must be a positive integer');
  const base = Math.floor(totalCents / people);
  return Array.from({ length: people }, (_, i) => base + (i < totalCents % people ? 1 : 0));   // first ones pay the leftover cents
}
export const makeInvoice = (customer, items) => ({
  customer, items, total: items.reduce((s, i) => s + i.cents, 0), createdAt: new Date().toISOString(),
});
EOF
cat > src/money.test.js <<'EOF'
import { describe, it, test, expect } from 'vitest';
import { parsePrice, formatCents, splitBill, makeInvoice } from './money.js';

describe('parsePrice', () => {
  // test.each: one test per row, the table IS the spec
  test.each([
    ['19.99', 1999], ['$19.99', 1999], ['  5 ', 500], ['0.50', 50],
  ])('parses %j as %i cents', (input, cents) => expect(parsePrice(input)).toBe(cents));

  test.each(['abc', '1.5', '-3.00', '', '12345678'])('rejects %j', (bad) =>
    expect(() => parsePrice(bad)).toThrow(/Invalid price/));
});

describe('splitBill', () => {
  it('never loses a cent', () => {
    const shares = splitBill(1000, 3);
    expect(shares).toEqual([334, 333, 333]);                        // toEqual compares contents
    expect(shares.reduce((a, b) => a + b)).toBe(1000);
  });
  it('rejects zero people', () => expect(() => splitBill(1000, 0)).toThrow(RangeError));
});

describe('makeInvoice', () => {
  it('totals the items and stamps a date', () => {
    const inv = makeInvoice('Jane Doe', [{ cents: 1999 }, { cents: 500 }]);
    expect(inv).toMatchObject({ customer: 'Jane Doe', total: 2499 });   // only the fields we care about
    expect(inv.createdAt).toMatch(/^\d{4}-\d{2}-\d{2}T/);
    expect(inv.items).toHaveLength(2);
  });
  it('toBe checks identity, toEqual checks contents', () => {
    expect({ a: 1 }).toEqual({ a: 1 });
    expect({ a: 1 }).not.toBe({ a: 1 });                           // two different objects
    expect(0.1 + 0.2).not.toBe(0.3);
    expect(0.1 + 0.2).toBeCloseTo(0.3);
  });
});

it('formatCents shows dollars', () => expect(formatCents(2499)).toBe('$24.99'));
EOF
clean() { sed -E 's/ [0-9]+ms//; s/\x1b\[[0-9;]*m//g' | grep -vE '^ *(Start at|Duration|RUN )' | grep -v '^ *$'; }
echo "--- 1. all green"
npx vitest run --reporter=verbose 2>&1 | clean
echo "--- 2. a 'cleanup' drops the leftover cents in splitBill; see how the failure reads"
sed -i 's/base + (i < totalCents % people ? 1 : 0)/base/' src/money.js
npx vitest run > out.txt 2>&1
clean < out.txt | sed -n '/^ FAIL/,/\^/p'
clean < out.txt | grep -E '^ +Tests '
```

<Happened>
<Tr>
<En>

- Each `test.each` row became its **own named test** (`parses "$19.99" as 1999 cents`, `rejects "1.5"`), so when one row fails you know which input. Adding a case is one line.
- `toThrow(/Invalid price/)` needs the call wrapped in a function (`() => parsePrice(bad)`), otherwise the error is thrown before `expect` can catch it.
- `toEqual` compared the arrays' **contents**; `toBe` checks **identity**, so two separate `{ a: 1 }` objects are not `toBe`. `0.1 + 0.2` isn't exactly `0.3`, which is why `toBeCloseTo` exists (and why money is in cents).
- `toMatchObject` checked only `customer` and `total`, ignoring the changing `createdAt`, and `toMatch` checked its format with a regex.
- After the "cleanup", the failure showed the test path (`splitBill > never loses a cent`), a **diff** (`-334` expected, `+333` received) and the exact line. That's what good unit tests give you: the bug is found before you even open the code.

</En>
<Ur>

- Har `test.each` row **apna naam wala test** ban gayi (`parses "$19.99" as 1999 cents`, `rejects "1.5"`), isliye ek row fail ho to pata hota hai kaunsa input. Naya case ek line hai.
- `toThrow(/Invalid price/)` ko call function me lipti chahiye (`() => parsePrice(bad)`), warna error `expect` ke pakarne se pehle phenka jata hai.
- `toEqual` ne arrays ka **mawad** milaya; `toBe` **pehchan** check karta hai, isliye do alag `{ a: 1 }` objects `toBe` nahi. `0.1 + 0.2` bilkul `0.3` nahi, isi liye `toBeCloseTo` hai (aur isi liye paisa cents me hai).
- `toMatchObject` ne sirf `customer` aur `total` check kiye, badalta `createdAt` nazar andaz kiya, aur `toMatch` ne regex se us ka format check kiya.
- "Safai" ke baad nakami ne test ka rasta (`splitBill > never loses a cent`), **diff** (`-334` mutawaqqa, `+333` mila) aur theek line dikhayi. Achhe unit tests yahi dete hain: code kholne se pehle hi bug mil jata hai.

</Ur>

<Step title="Fake timers, async tests and coverage">

<Tr>
<En>
`timing.js` has a `debounce`, a coupon that expires after N days, and an async `loadCustomer` that calls an API. The tests use **fake timers** (no real waiting), `vi.setSystemTime` to move the clock, a `vi.fn()` to count calls, a tiny hand-made API stub, and `resolves`/`rejects`. Finally we run all tests with **coverage**. (Mocking gets its own lesson later.)
</En>
<Ur>
`timing.js` me `debounce`, N din baad expire hone wala coupon, aur API bulane wala async `loadCustomer` hai. Tests **fake timers** (asli intezar nahi), ghari hilane ke liye `vi.setSystemTime`, calls ginne ke liye `vi.fn()`, chhota haath ka bana API stub, aur `resolves`/`rejects` istemal karte hain. Aakhir me saare tests **coverage** ke saath chalate hain. (Mocking ka apna lesson baad me hai.)
</Ur>
</Tr>

```bash
npm install -D @vitest/coverage-v8@5.1.1 --silent
sed -i 's/^  return Array.from({ length: people }, (_, i) => base);/  return Array.from({ length: people }, (_, i) => base + (i < totalCents % people ? 1 : 0));/' src/money.js
cat > src/timing.js <<'EOF'
export function debounce(fn, ms) {                 // run fn once, ms after the LAST call
  let timer;
  return (...args) => { clearTimeout(timer); timer = setTimeout(() => fn(...args), ms); };
}
export function createCoupon(code, validDays) {
  const expiresAt = Date.now() + validDays * 24 * 60 * 60 * 1000;
  return { code, isValid: () => Date.now() < expiresAt };
}
export async function loadCustomer(id, api) {
  const res = await api.get(`/customers/${id}`);
  if (res.status === 404) throw new Error(`Customer ${id} not found`);
  if (res.status >= 500) return { id, name: 'Unknown', fromCache: true };   // fallback, not tested yet
  return res.body;
}
EOF
cat > src/timing.test.js <<'EOF'
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest';
import { debounce, createCoupon, loadCustomer } from './timing.js';

describe('with fake timers', () => {
  beforeEach(() => vi.useFakeTimers());
  afterEach(() => vi.useRealTimers());

  it('debounce calls once, after the typing stops', () => {
    const search = vi.fn();                        // a function that records its calls
    const onType = debounce(search, 300);
    onType('j'); onType('ja'); onType('jan');
    vi.advanceTimersByTime(299);
    expect(search).not.toHaveBeenCalled();
    vi.advanceTimersByTime(1);                     // no real waiting: the test takes microseconds
    expect(search).toHaveBeenCalledTimes(1);
    expect(search).toHaveBeenCalledWith('jan');
  });

  it('a coupon expires after its validity', () => {
    vi.setSystemTime(new Date('2026-11-01T12:00:00Z'));
    const coupon = createCoupon('WELCOME', 7);
    vi.setSystemTime(new Date('2026-11-08T11:59:59Z'));
    expect(coupon.isValid()).toBe(true);
    vi.setSystemTime(new Date('2026-11-08T12:00:00Z'));
    expect(coupon.isValid()).toBe(false);
  });
});

describe('async code', () => {
  const api = (status, body) => ({ get: async () => ({ status, body }) });   // a tiny hand-made stub
  it('returns the customer', async () => {
    await expect(loadCustomer(1, api(200, { id: 1, name: 'Jane Doe' }))).resolves.toEqual({ id: 1, name: 'Jane Doe' });
  });
  it('throws a clear error for 404', async () => {
    await expect(loadCustomer(9, api(404))).rejects.toThrow('Customer 9 not found');
  });
});
EOF
clean() { sed -E 's/ [0-9]+ms//; s/\x1b\[[0-9;]*m//g' | grep -vE '^ *(Start at|Duration|RUN )' | grep -v '^ *$'; }
echo "--- tests with fake timers and async code"
npx vitest run src/timing.test.js --reporter=verbose 2>&1 | clean
echo "--- coverage: which lines did the tests actually run?"
npx vitest run --coverage --coverage.reporter=text --coverage.include='src/**' 2>&1 | clean | sed -n '/^ *% Coverage/,$p' | grep -E '\|'
```

<Happened>
<Tr>
<En>

- The debounce test "waited" 300 ms in no time: `advanceTimersByTime(299)` showed nothing had run, one more millisecond ran the function **once**, with the **last** argument. Real `setTimeout` waits would make tests slow and flaky.
- `vi.setSystemTime` set `Date.now()`, so the coupon was valid one second before 7 days and invalid exactly at 7 days: boundaries tested precisely, no matter when the test runs. `afterEach(vi.useRealTimers)` restores the clock for other tests.
- `resolves.toEqual` and `rejects.toThrow` must be **awaited**; without `await` the test can finish before the promise settles and pass by accident.
- The stub `api` returned whatever status we wanted, so we tested `loadCustomer`'s **logic** without a server.
- Coverage shows the report's honest limits: `timing.js` has **100% lines** but **75% branches**, and line **12**, the 500-error fallback, is listed as uncovered: that branch never ran. Fully covered files (`money.js`) are hidden from the table. Coverage tells you what's untested; it can't tell you whether the tested code is checked well.

</En>
<Ur>

- Debounce test ne 300 ms baghair waqt ke "intezar" kiya: `advanceTimersByTime(299)` ne dikhaya kuch nahi chala, ek aur millisecond ne function **ek dafa**, **aakhri** argument ke saath chalaya. Asli `setTimeout` intezar tests ko sust aur flaky banata.

## Common mistakes

<Compare>
<Bad title="Forgetting to await async assertions">

```text
it('throws for 404', () => {
  expect(loadCustomer(9, api(404))).rejects.toThrow('not found');   // not awaited: may pass anyway
});
```

</Bad>
<Good title="Await, or return, the expectation">

```text
it('throws for 404', async () => {
  await expect(loadCustomer(9, api(404))).rejects.toThrow('Customer 9 not found');
});
```

</Good>
</Compare>

<Compare>
<Bad title="One giant test with vague names">

```text
it('works', () => {
  expect(parsePrice('19.99')).toBe(1999);
  expect(() => parsePrice('abc')).toThrow();
  expect(splitBill(1000, 3)).toEqual([334, 333, 333]);
  // first failure hides the rest, and "works" says nothing
});
```

</Bad>
<Good title="Small tests named after behavior">

```text
test.each([['19.99', 1999], ['$19.99', 1999]])('parses %j as %i cents', …);
it('rejects text that is not a price', …);
it('never loses a cent when splitting', …);
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`toBe` on objects or arrays**: fails even when contents match; use `toEqual`.
- **`expect(fn()).toThrow()`**: the error escapes; pass a function: `expect(() => fn()).toThrow()`.
- **Real timers and `sleep`** in unit tests: slow and flaky; use fake timers and restore them afterwards.
- **Shared mutable state between tests**: reset in `beforeEach`, never rely on test order.
- **Asserting on the current date** or random values: freeze time and seed or inject randomness.
- **Snapshot everything**: huge snapshots get approved without reading; prefer explicit assertions for logic.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Objects ya arrays par `toBe`**: mawad milne par bhi fail; `toEqual` lein.
- **`expect(fn()).toThrow()`**: error nikal jata hai; function dein: `expect(() => fn()).toThrow()`.
- **Unit tests me asli timers aur `sleep`**: sust aur flaky; fake timers lein aur baad me wapas karein.
- **Tests ke beech shared badalta state**: `beforeEach` me reset karein, tests ki tarteeb par kabhi bharosa na karein.
- **Aaj ki tareekh** ya random qeematon par assert: waqt rokein aur randomness seed ya inject karein.
- **Har cheez ka snapshot**: bare snapshots bina parhe manzoor ho jate hain; logic ke liye wazeh assertions behtar hain.

</Ur>
</Tr>

<Tr>
<En>

```text
export function createLimiter(max, windowMs) {
  let start = Date.now(), count = 0;
  return { allow() {
    if (Date.now() - start >= windowMs) { start = Date.now(); count = 0; }
    return ++count <= max;
  } };
}

describe('createLimiter', () => {
  beforeEach(() => vi.useFakeTimers());
  afterEach(() => vi.useRealTimers());
  it('allows max calls per window', () => {
    const limiter = createLimiter(3, 1000);
    expect([limiter.allow(), limiter.allow(), limiter.allow(), limiter.allow()]).toEqual([true, true, true, false]);
    vi.advanceTimersByTime(999);
    expect(limiter.allow()).toBe(false);
    vi.advanceTimersByTime(1);
    expect(limiter.allow()).toBe(true);
  });
});
```

<DeepDive title="More about Vitest and Jest">

**Configuration.** `vitest.config.ts` (or the `test` key in `vite.config.ts`) sets the environment (`node`, `jsdom`, `happy-dom` for DOM code), setup files, coverage thresholds and globals. Jest uses `jest.config.js`; for TypeScript it needs `ts-jest` or Babel, while Vitest handles TS natively.

**Migrating Jest to Vitest.** Mostly `jest.fn` → `vi.fn`, `jest.mock` → `vi.mock`, and adding imports or `globals: true`. Matchers are compatible.

**Snapshots.** `toMatchSnapshot()` and inline snapshots are handy for serializers and error messages, but review every update.

**Property-based testing.** `fast-check` generates hundreds of random inputs to check properties such as "splitBill always sums to the total".

**Testing React components.** Testing Library plus Vitest's `jsdom` environment tests components the way users interact with them.

**Coverage thresholds.** Configure minimums (for example 80% branches on `src/domain`) to stop coverage dropping, without making it the goal.

</DeepDive>

<DeepDive title="Real world: the test that always passed">

A team's refund logic had a test `it('rejects refunds over the order total', () => { expect(refund(order, 500)).rejects.toThrow(); })`. It was green for a year. When someone changed `refund` so it no longer threw, the test still passed, because the expectation was never awaited and the test function returned before the promise was checked. Customers received refunds larger than their orders until finance noticed.

The fixes:

1. Every async expectation is awaited; the lint rule `vitest/valid-expect` (and `jest/valid-expect` in Jest projects) now enforces it.
2. A habit of seeing each new test fail once by breaking the code temporarily.
3. `expect.assertions(n)` in tests that check errors inside callbacks.
4. Property-based tests for money logic ("a refund never exceeds what was paid").

</DeepDive>

<DeepDive title="Security lens">

- **Unit-test security logic directly**: permission checks, input validation, token expiry, password rules.
- **Edge cases are attack inputs**: empty strings, huge numbers, unicode, negative amounts, `__proto__` keys.
- **Don't put real secrets in tests**; use clearly fake values and environment variables in CI.
- **Freeze time** for expiry logic so tests check the exact boundary attackers would probe.
- **Keep the test toolchain updated**: dev dependencies run on developer machines and CI with access to code and secrets.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What makes a good unit test?">
It is fast, isolated and deterministic, tests one behavior through the public interface, has a descriptive name, follows arrange-act-assert, and fails with a clear message when the behavior breaks.
</QA>

<QA q="toBe vs toEqual?">
toBe uses Object.is, so it checks primitives and object identity. toEqual recursively compares contents, so two separate objects or arrays with the same values are equal.
</QA>

<QA q="How do you test code that uses timers or dates?">
Use fake timers to control setTimeout and setInterval and set the system time, advance time explicitly in the test, and restore real timers afterwards.
</QA>

<QA q="How do you test async functions?">
Make the test async and await the result, or use await expect(promise).resolves or rejects. Forgetting to await can make failing tests pass.
</QA>

<QA q="Vitest or Jest?">
They share an API. Vitest is faster, ESM- and TypeScript-native and integrates with Vite; Jest is mature with a huge ecosystem and is common in existing projects and React Native. Choose based on the project's tooling.
</QA>

</DeepDive>
