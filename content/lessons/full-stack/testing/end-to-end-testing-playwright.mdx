<BigIdea>
<Tr>
<En>
An **end-to-end (E2E) test** drives your **whole application** from the outside, like a user: it opens a real browser, loads real pages from your running server, types into fields, clicks buttons and checks what appears on screen. It's the only kind of test that proves the HTML, JavaScript, CSS, cookies, server, database and their wiring all work **together**. **Playwright** is the modern tool for this: it starts your app before the tests, controls Chromium, Firefox and WebKit, finds elements with **user-facing locators** (`getByRole('button', { name: 'Place order' })`, `getByLabel('Email')`), **waits automatically** for elements to be ready, and uses **web-first assertions** (`await expect(locator).toHaveText(…)`) that retry until the page catches up. E2E tests are the slowest and most fragile layer of the pyramid, so keep them few and focused on **critical journeys** (sign up, log in, checkout), make them **independent**, never use fixed sleeps, mock only what you can't control (payment providers), and use **traces and screenshots** to debug failures.
</En>
<Ur>
**End-to-end (E2E) test** aap ki **poori application** ko bahar se chalata hai, user ki tarah: asli browser kholta hai, aap ke chalte server se asli pages load karta hai, fields me type karta hai, buttons dabata hai aur screen par jo aaye use check karta hai. Ye wahid qism ka test hai jo sabit karta hai ke HTML, JavaScript, CSS, cookies, server, database aur un ki wiring sab **saath** kaam karte hain. **Playwright** is ka jadeed auzaar hai: ye tests se pehle aap ki app chalata hai, Chromium, Firefox aur WebKit qaboo karta hai, **user ki nazar wale locators** (`getByRole('button', { name: 'Place order' })`, `getByLabel('Email')`) se elements dhoondta hai, elements tayyar hone ka **khud intezar** karta hai, aur **web-first assertions** (`await expect(locator).toHaveText(…)`) istemal karta hai jo page ke pohanchne tak dobara koshish karti hain. E2E tests pyramid ki sab se sust aur nazuk tah hain, isliye inhe kam aur **ahem safar** (sign up, login, checkout) par markooz rakhein, **azad** banayen, kabhi mustaqil sleeps na lagayen, sirf woh mock karein jo aap ke qaboo me nahi (payment providers), aur nakamiyan debug karne ke liye **traces aur screenshots** lein.
</Ur>
</Tr>

<Why>
<Tr>
<En>

- Proves the critical journeys work in a real browser, end to end.
- Catches bugs nothing else sees: broken JavaScript, wrong redirects, cookies, CSS hiding a button.
- User-facing locators double as an accessibility check: if Playwright can't find "the Place order button", neither can a screen reader.
- Runs before every release or deploy as a safety net.

</En>
<Ur>

- Sabit karta hai ke ahem safar asli browser me shuru se aakhir tak chalte hain.

- User ki nazar wale locators accessibility check bhi hain: agar Playwright "Place order button" nahi dhoond sakta to screen reader bhi nahi.

## Picture it

<Tr>
<En>

Think of a **mystery shopper**.

- A store hires someone to walk in like a normal customer: find the product, ask for help, pay at the register, get a receipt. Every department might pass its own inspection (unit and integration tests), yet the shopper is the one who notices the card machine is unplugged.
- The shopper doesn't look at the store's internal systems; they use **what customers see**: signs, labels, buttons (role and label locators).
- A good shopper waits for the cashier to finish before deciding the till is broken (auto-waiting); a bad one checks the screen the instant they hand over the card and reports a false problem (the flaky test).
- They take photos when something goes wrong (screenshots and traces), and they visit a few times a month, not every hour, because each visit is expensive (few E2E tests).

</En>
<Ur>

**Mystery shopper** socheyn.

- Ek store kisi ko aam customer ki tarah andar bhejta hai: product dhoondo, madad maango, counter par pay karo, raseed lo. Har department apni jaanch pass kar sakta hai (unit aur integration tests), phir bhi shopper hi dekhta hai ke card machine ka plug nikla hua hai.
- Shopper store ke andaruni systems nahi dekhta; woh **jo customers dekhte hain** woh istemal karta hai: nishanat, labels, buttons (role aur label locators).
- Achha shopper cashier ke khatam hone ka intezar karta hai phir faisla karta hai ke till kharab hai (auto-waiting); bura card dete hi screen dekh kar ghalat shikayat kar deta hai (flaky test).
- Kuch ghalat ho to tasveeren leta hai (screenshots aur traces), aur mahine me chand dafa aata hai, har ghante nahi, kyunke har visit mehngi hai (kam E2E tests).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="A real journey: log in, add to cart, check out">

<Tr>
<En>
`server.js` is a tiny shop: a login form, products with "Add" buttons that call a deliberately **slow API** (300 ms), a cart page with a total, and checkout. `playwright.config.js` tells Playwright to **start the app** (`webServer`), use `baseURL`, and keep traces and screenshots of failures. The tests use **role and label locators** and web-first assertions only. Note: the config uses `channel: 'chrome'`, the Chrome already installed on the machine; with Playwright's own browsers (`npx playwright install chromium`), just remove that line. Durations are removed from the output.
</En>
<Ur>
`server.js` ek chhoti dukan hai: login form, "Add" buttons wale products jo jaan boojh kar **sust API** (300 ms) bulate hain, total wala cart page, aur checkout. `playwright.config.js` Playwright ko **app chalane** (`webServer`), `baseURL` lene, aur nakamiyon ke traces aur screenshots rakhne ko kehta hai. Tests sirf **role aur label locators** aur web-first assertions istemal karte hain. Note: config `channel: 'chrome'` istemal karta hai, machine par pehle se installed Chrome; Playwright ke apne browsers (`npx playwright install chromium`) ke saath bas woh line hata dein. Output se waqt hata diye gaye hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module scripts.start="node server.js"
npm install express@5.1.0 --silent && npm install -D @playwright/test@1.65.1 --silent
cat > server.js <<'EOF'
// A tiny shop: login, products, cart, checkout. Pages are plain HTML with a little JavaScript.
import express from 'express';
import { randomUUID } from 'node:crypto';
const app = express();
app.use(express.urlencoded({ extended: false }), express.json());
const sessions = new Map();                                    // sid -> { email, cart: [] }
const products = [{ id: 1, name: 'Desk lamp', cents: 3500 }, { id: 2, name: 'Notebook', cents: 899 }, { id: 3, name: 'Coffee mug', cents: 1250 }];
const page = (title, body) => `<!doctype html><html lang="en"><head><meta charset="utf-8"><title>${title}</title></head><body><main>${body}</main></body></html>`;
const sessionOf = (req) => sessions.get(/sid=([\w-]+)/.exec(req.get('cookie') ?? '')?.[1]);
const money = (c) => `$${(c / 100).toFixed(2)}`;

app.get('/login', (req, res) => res.send(page('Log in', `
  <h1>Log in</h1>${req.query.error ? '<p role="alert">Wrong email or password</p>' : ''}
  <form method="post" action="/login">
    <label>Email <input name="email" type="email"></label>
    <label>Password <input name="password" type="password"></label>
    <button>Log in</button>
  </form>`)));
app.post('/login', (req, res) => {
  if (req.body.email !== 'jane@example.com' || req.body.password !== 'correct horse battery') return res.redirect('/login?error=1');
  const sid = randomUUID(); sessions.set(sid, { email: req.body.email, cart: [] });
  res.set('Set-Cookie', `sid=${sid}; HttpOnly; SameSite=Lax; Path=/`).redirect('/');
});
app.use((req, res, next) => (sessionOf(req) ? next() : res.redirect('/login')));
app.get('/', (req, res) => res.send(page('Shop', `
  <h1>Products</h1><p>Signed in as ${sessionOf(req).email}</p>
  <ul>${products.map((p) => `<li>${p.name} ${money(p.cents)} <button data-id="${p.id}" aria-label="Add ${p.name} to cart">Add</button></li>`).join('')}</ul>
  <a href="/cart">Cart (<span id="count">${sessionOf(req).cart.length}</span>)</a>
  <script>
    document.querySelectorAll('button[data-id]').forEach((b) => b.onclick = async () => {
      const r = await fetch('/api/cart', { method: 'POST', headers: { 'content-type': 'application/json' }, body: JSON.stringify({ id: Number(b.dataset.id) }) });
      document.getElementById('count').textContent = (await r.json()).count;
    });
  </script>`)));
app.post('/api/cart', async (req, res) => {
  await new Promise((r) => setTimeout(r, 300));               // a slow API, like real life
  const s = sessionOf(req); s.cart.push(products.find((p) => p.id === req.body.id));
  res.json({ count: s.cart.length });
});
app.get('/cart', (req, res) => {
  const cart = sessionOf(req).cart, total = cart.reduce((t, p) => t + p.cents, 0);
  res.send(page('Cart', `<h1>Your cart</h1><ul>${cart.map((p) => `<li>${p.name}</li>`).join('')}</ul>
    <p>Total: <strong data-testid="total">${money(total)}</strong></p>
    <button id="pay" ${cart.length ? '' : 'disabled'}>Place order</button><p id="status" role="status"></p>
    <script>
      document.getElementById('pay').onclick = async () => {
        const r = await fetch('/api/checkout', { method: 'POST' });
        if (r.ok) location.href = '/orders/' + (await r.json()).orderId;
        else document.getElementById('status').textContent = 'Payment failed, please try again';
      };
    </script>`));
});
app.post('/api/checkout', (req, res) => { const s = sessionOf(req); const n = s.cart.length; s.cart = []; res.json({ orderId: 1000 + n }); });
app.get('/orders/:id', (req, res) => res.send(page('Order placed', `<h1>Thank you!</h1><p>Order #${req.params.id} is confirmed.</p>`)));
app.listen(process.env.PORT ?? 3000);
EOF
cat > playwright.config.js <<'EOF'
import { defineConfig } from '@playwright/test';
export default defineConfig({
  testDir: 'e2e',
  webServer: { command: 'npm start', url: 'http://localhost:3000/login', reuseExistingServer: false },   // Playwright starts the app
  use: { baseURL: 'http://localhost:3000', channel: 'chrome', trace: 'retain-on-failure', screenshot: 'only-on-failure' },
  workers: 1,
});
EOF
mkdir -p e2e
cat > e2e/checkout.spec.js <<'EOF'
import { test, expect } from '@playwright/test';

async function logIn(page, password = 'correct horse battery') {
  await page.goto('/login');
  await page.getByLabel('Email').fill('jane@example.com');
  await page.getByLabel('Password').fill(password);
  await page.getByRole('button', { name: 'Log in' }).click();
}

test('a customer can buy two items', async ({ page }) => {
  await logIn(page);
  await expect(page.getByText('Signed in as jane@example.com')).toBeVisible();
  await page.getByRole('button', { name: 'Add Desk lamp to cart' }).click();
  await page.getByRole('button', { name: 'Add Notebook to cart' }).click();
  await expect(page.getByRole('link', { name: 'Cart (2)' })).toBeVisible();   // waits for the slow API
  await page.getByRole('link', { name: /Cart/ }).click();
  await expect(page.getByTestId('total')).toHaveText('$43.99');
  await page.getByRole('button', { name: 'Place order' }).click();
  await expect(page).toHaveURL(/\/orders\/\d+$/);
  await expect(page.getByRole('heading', { name: 'Thank you!' })).toBeVisible();
});

test('a wrong password shows an error and stays on the login page', async ({ page }) => {
  await logIn(page, 'guess');
  await expect(page.getByRole('alert')).toHaveText('Wrong email or password');
  await expect(page).toHaveURL(/\/login/);
});

test('pages need a login', async ({ page }) => {
  await page.goto('/cart');
  await expect(page).toHaveURL(/\/login$/);
});

test('an empty cart cannot be ordered', async ({ page }) => {
  await logIn(page);
  await page.getByRole('link', { name: /Cart/ }).click();
  await expect(page.getByRole('button', { name: 'Place order' })).toBeDisabled();
});
EOF
npx playwright test --reporter=list 2>&1 | sed -E 's/ \([0-9.]+m?s\)//' | grep -v '^ *$'
```

<Happened>
<Tr>
<En>

- Playwright ran `npm start`, waited until `/login` answered, ran the tests in a real Chrome, and stopped the server afterwards. No manual setup.
- The journey test went through everything a customer would: the form (found by its **labels**), the redirect and session cookie, two clicks on buttons found by their **accessible names**, the slow cart API, the cart page and its total (**$35.00 + $8.99 = $43.99**), the checkout `fetch`, and the redirect to the confirmation page.
- `toBeVisible` for "Cart (2)" **waited** for both slow API responses; no `sleep` anywhere. Every `expect` with `await` retries until it passes (default timeout 5 s).
- The wrong-password test checked the **`alert` role** and the URL; the "pages need a login" test checked a redirect; the empty-cart test checked that **Place order is disabled**. Each test logs in by itself, so any one of them can run alone.
- Because these locators use roles and labels, they also tell you the page is reasonably accessible. If a button had no accessible name, writing the test would have been the first hint.

</En>
<Ur>

- Playwright ne `npm start` chalaya, `/login` ke jawab dene tak intezar kiya, asli Chrome me tests chalaye, aur baad me server band kiya. Koi haath ka setup nahi.
- Safar wala test har us cheez se guzra jis se customer guzarta: form (apne **labels** se mila), redirect aur session cookie, **accessible names** se mile buttons par do clicks, sust cart API, cart page aur us ka total (**$35.00 + $8.99 = $43.99**), checkout `fetch`, aur confirmation page ka redirect.
- "Cart (2)" ke `toBeVisible` ne dono sust API jawabon ka **intezar** kiya; kahin `sleep` nahi. `await` wala har `expect` pass hone tak dobara koshish karta hai (default timeout 5 s).
- Ghalat password test ne **`alert` role** aur URL check kiya; "pages need a login" test ne redirect check kiya; khaali cart test ne check kiya ke **Place order disabled** hai. Har test khud login karta hai, isliye koi bhi akela chal sakta hai.
- Kyunke ye locators roles aur labels istemal karte hain, ye ye bhi batate hain ke page munasib had tak accessible hai. Agar kisi button ka accessible naam na hota to test likhna pehla ishara hota.

</Ur>

<Step title="Flaky reads, network mocking, and debugging failures">

<Tr>
<En>
Four more tests, two of them **wrong on purpose**. One reads the cart count right after clicking "Add"; its twin uses a web-first assertion. One **mocks the checkout API** with `page.route` to return 502 and checks the error message. The last uses a locator for a button that doesn't exist ("Buy now"), with a 1-second timeout. Then we look at the error messages and the evidence Playwright saved.
</En>
<Ur>
Chaar aur tests, un me se do **jaan boojh kar ghalat**. Ek "Add" dabane ke foran baad cart ki ginti parhta hai; us ka jurwan web-first assertion istemal karta hai. Ek `page.route` se **checkout API mock** karta hai taa ke 502 lautaye aur error paigham check karta hai. Aakhri aise button ka locator istemal karta hai jo mojood nahi ("Buy now"), 1 second timeout ke saath. Phir hum error paigham aur Playwright ka mehfooz saboot dekhte hain.
</Ur>
</Tr>

```bash
cat > e2e/lessons.spec.js <<'EOF'
import { test, expect } from '@playwright/test';
test.beforeEach(async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('jane@example.com');
  await page.getByLabel('Password').fill('correct horse battery');
  await page.getByRole('button', { name: 'Log in' }).click();
});

test('WRONG: reads the count right after clicking', async ({ page }) => {
  await page.getByRole('button', { name: 'Add Coffee mug to cart' }).click();
  expect(await page.locator('#count').textContent()).toBe('1');   // the API hasn't answered yet
});

test('RIGHT: a web-first assertion waits for the count', async ({ page }) => {
  await page.getByRole('button', { name: 'Add Coffee mug to cart' }).click();
  await expect(page.locator('#count')).toHaveText('1');           // retries until it passes or times out
});

test('payment failure shows a message (network mocked)', async ({ page }) => {
  await page.route('**/api/checkout', (route) => route.fulfill({ status: 502, body: 'bad gateway' }));
  await page.getByRole('button', { name: 'Add Notebook to cart' }).click();
  await expect(page.locator('#count')).toHaveText('1');
  await page.getByRole('link', { name: /Cart/ }).click();
  await page.getByRole('button', { name: 'Place order' }).click();
  await expect(page.getByRole('status')).toHaveText('Payment failed, please try again');
});

test('WRONG: a locator for a button that was renamed', async ({ page }) => {
  await expect(page.getByRole('button', { name: 'Buy now' })).toBeVisible({ timeout: 1000 });
});
EOF
npx playwright test e2e/lessons.spec.js --reporter=list > out.txt 2>&1
sed -E 's/ \([0-9.]+m?s\)//' out.txt | grep -E '^ +(✓|✘) ' | sed -E 's/^ +(✓|✘) +[0-9]+ /\1 /'
echo "--- why the first WRONG test failed"
grep -m1 -A1 'Expected: "1"' out.txt | sed 's/^ *//'
echo "--- why the second WRONG test failed"
grep -m1 -E 'Locator: ' out.txt | sed 's/^ *//'; grep -m1 'element(s) not found' out.txt | sed 's/^ *//'
echo "--- evidence saved for each failed test"
find test-results -type f \( -name '*.png' -o -name 'trace.zip' \) | sed -E 's#test-results/[^/]+/#test-results/<test>/#' | sort | uniq -c
```

## Common mistakes

<Compare>
<Bad title="Fixed sleeps and CSS-structure selectors">

```text
await page.click('#app > div:nth-child(3) > button.btn-primary');
await page.waitForTimeout(2000);                 // too slow on fast days, too short on slow ones
expect(await page.textContent('.cart .count')).toBe('2');
```

</Bad>
<Good title="User-facing locators and web-first assertions">

```text
await page.getByRole('button', { name: 'Add Notebook to cart' }).click();
await expect(page.getByRole('link', { name: 'Cart (2)' })).toBeVisible();
```

</Good>
</Compare>

<Compare>
<Bad title="Tests that depend on each other">

```text
test('log in', …);
test('add to cart', …);      // assumes the previous test's page and session
test('checkout', …);         // fails alone, and breaks with parallel workers
```

</Bad>
<Good title="Each test sets up its own state">

```text
test.beforeEach(async ({ page }) => logIn(page));   // or reuse a saved storageState
test('checkout', async ({ page }) => { /* adds its own items, then checks out */ });
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Testing everything end to end**: slow, flaky suites. Push details down to unit and integration tests.
- **`expect(await locator.textContent())`**: one-shot checks race the page; use `await expect(locator).toHaveText()`.
- **Shared test accounts and data** across parallel runs: tests overwrite each other's carts. Create users per test or per worker.
- **Mocking your own backend** in E2E tests: then it isn't end to end. Mock only external services.
- **Ignoring flaky tests or adding retries everywhere**: retries hide real race conditions. Find the cause in the trace.
- **Hard-coded production URLs or real payment cards**: use a test environment and the provider's test cards.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Har cheez end to end test karna**: sust, flaky suites. Tafseelat unit aur integration tests me neeche bhejein.
- **`expect(await locator.textContent())`**: ek dafa ke checks page se dor lagate hain; `await expect(locator).toHaveText()` lein.
- **Parallel runs me shared test accounts aur data**: tests ek doosre ke carts likh dete hain. Har test ya har worker ke users banayen.
- **E2E tests me apna backend mock karna**: phir ye end to end nahi. Sirf bahar ki services mock karein.
- **Flaky tests nazar andaz karna ya har jagah retries**: retries asli race conditions chhupate hain. Trace me wajah dhoondein.
- **Production URLs ya asli payment cards hard-code karna**: test environment aur provider ke test cards lein.

</Ur>
</Tr>

<DeepDive title="More about Playwright">

**Browsers and devices.** Projects can run the same tests in Chromium, Firefox and WebKit (Safari's engine), and emulate phones (`devices['iPhone 15']`), locales, time zones and geolocation.

**Parallelism and sharding.** Tests run in parallel workers by default; `--shard=1/4` splits a big suite across CI machines. That's why isolation matters.

**API testing.** The `request` fixture sends HTTP calls in the same test, handy for seeding data quickly before a UI check.

**Visual comparisons.** `await expect(page).toHaveScreenshot()` compares pixels against a baseline; useful for design-critical pages, but needs stable fonts and data.

**Accessibility checks.** `@axe-core/playwright` scans pages for accessibility violations inside your E2E tests.

**Alternatives.** Cypress runs inside the browser with a great debugger; Selenium/WebDriver has the widest language support. Playwright is the common choice for new projects.

</DeepDive>

<DeepDive title="Real world: the checkout that only broke in Safari">

An e-commerce team had strong unit and integration tests and ran E2E tests in Chromium only. A frontend change used a date-input API that Safari implemented differently, so iPhone users couldn't choose a delivery date and the "Continue" button stayed disabled. Mobile Safari was 40% of their traffic; orders dropped for a weekend before support tickets made the cause clear.

What they changed:

1. The checkout journey runs in Chromium, Firefox and WebKit, plus an iPhone viewport project.
2. A post-deploy smoke test runs the checkout on production with a test product and a test card.
3. Conversion-rate alerts per browser family.
4. The flaky-test policy: any E2E failure is triaged within a day using its trace, never just retried.

</DeepDive>

<DeepDive title="Security lens">

- **Test security journeys end to end**: logging out really ends access, protected pages redirect, another user's order URL shows "not found".
- **Keep test credentials secret**: store passwords for test accounts in CI secrets, never in the repository; ignore saved `storageState` files.
- **Never run destructive E2E tests against production**; smoke tests there should use dedicated test accounts and products.
- **Traces contain everything**: cookies, request bodies, screenshots. Treat CI artifacts as sensitive and expire them.
- **Third-party scripts** (analytics, chat widgets) can be blocked with `page.route` in tests to keep runs stable and private.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is an end-to-end test and when is it worth it?">
A test that drives the complete system from the user interface through the backend and database. It's worth it for critical user journeys where a failure is costly, while details are covered by cheaper unit and integration tests.
</QA>

<QA q="What causes flaky E2E tests and how do you prevent them?">
Timing assumptions, fixed sleeps, one-shot reads, shared state between tests, dependence on external services and unstable selectors. Prevent them with auto-waiting actions, web-first assertions, isolated data per test, mocking external services and user-facing locators.
</QA>

<QA q="Why use role-based locators?">
They find elements the way users and assistive technology do, are resilient to markup and CSS changes, and failing to find an element by role often reveals an accessibility issue.
</QA>

<QA q="How do you speed up a large E2E suite?">
Reuse authentication with storageState, seed data through APIs instead of the UI, run tests in parallel and shard across machines, and move detailed checks to lower test levels.
</QA>

<QA q="How do you debug an E2E failure from CI?">
Open the trace for the failed test to see each action with the DOM snapshot, network requests and console logs, along with screenshots or video, then reproduce locally with the UI mode if needed.
</QA>

</DeepDive>
