<BigIdea>
<Tr>
<En>
An **operator** is a symbol that does something with values: `+` adds, `>` compares, `&&` combines conditions, `??` picks a fallback. Most operators expect a particular **type**: `-` wants numbers, `>` wants two things of the same kind. When you give them a different type, JavaScript doesn't stop with an error; it quietly **converts** the value first. This automatic conversion is called **type coercion**. It's why `"5" - 2` is `3` but `"5" + 2` is `"52"`, and why `"10" < "9"` is `true`. Coercion follows a small set of rules. Once you know them, you can predict every result, and more importantly, you'll know when to **convert on purpose** so your code never depends on a guess.
</En>
<Ur>
**Operator** ek nishaan hai jo values ke saath kuch karta hai: `+` jorta hai, `>` muqabla karta hai, `&&` sharten jorta hai, `??` mutabadil chunta hai. Zyada tar operators ek khaas **type** chahte hain: `-` numbers chahta hai, `>` ek hi qisam ki do cheezen. Jab aap inhe mukhtalif type dete hain, JavaScript error par nahi rukti; khamoshi se pehle value **badal** deti hai. Is khud ba khud tabdeeli ko **type coercion** kehte hain. Isi wajah se `"5" - 2` `3` hai magar `"5" + 2` `"52"`, aur `"10" < "9"` `true` hai. Coercion chand qawaid par chalti hai. Inhe jaan lein to har nateeje ka andaza laga sakte hain, aur sab se ahem, aap ko pata hoga ke kab **jaan boojh kar badalna** hai taa ke aap ka code kabhi andaze par na chale.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **Every decision in a program uses operators**: "is the cart empty?", "is the user an admin **and** logged in?", "use the saved name **or** 'Guest'".
- **Coercion causes some of the most common bugs**: totals that become `"105"`, prices sorted as text, a quantity of `0` replaced by a default.
- **Interviewers love these questions** (`[] + {}`, `"10" < "9"`), and knowing the rules shows you understand the language.

</En>
<Ur>

- **Program ka har faisla operators istemal karta hai**: "kya cart khaali hai?", "kya user admin hai **aur** login hai?", "mehfooz naam lo **ya** 'Guest'".

</Ur>

<En>

## Picture it

<Tr>
<En>

Imagine a **currency exchange booth at an airport** that never refuses a transaction.

- You hand over euros and ask for something priced in dollars. Instead of saying "wrong currency", the booth **silently exchanges** your money first, at its own fixed rules. That's coercion.
- Usually it's convenient. But some rules surprise travellers: give it **text** and ask to **add**, and it glues the notes together instead (`"5" + 2` → `"52"`). Ask it to **subtract**, and it converts to numbers (`"5" - 2` → `3`).
- Smart travellers **exchange their money themselves first** (`Number(x)`), so they always know exactly what they're paying with.

</En>
<Ur>

Airport par aisa **currency exchange booth** sochein jo kabhi len den se inkaar nahi karta.

- Aap euros dete hain aur dollar wali cheez maangte hain. "Ghalat currency" kehne ke bajaye booth apne tay qawaid par pehle **khamoshi se aap ke paise badal** deta hai. Ye coercion hai.
- Aam taur par ye aasaan hai. Magar kuch qawaid musafiron ko hairan karte hain: use **text** dein aur **jorne** ka kahein, to wo notes ko chipka deta hai (`"5" + 2` → `"52"`). **Ghatane** ka kahein, to numbers me badalta hai (`"5" - 2` → `3`).
- Samajhdar musafir **pehle khud paise badalte hain** (`Number(x)`), taa ke hamesha bilkul pata ho ke kis cheez se adaigi kar rahe hain.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Comparison operators">

<Tr>
<En>
Comparison operators ask a yes/no question and answer with a **boolean**: `true` or `false`. Use `===` for "equal" and `!==` for "not equal".
</En>
<Ur>
Muqable ke operators haan/nahi ka sawal poochte hain aur **boolean** me jawab dete hain: `true` ya `false`. "Barabar" ke liye `===` aur "barabar nahi" ke liye `!==` lein.
</Ur>
</Tr>

```javascript
const stock = 3;
const ordered = 5;

console.log(ordered > stock);
console.log(ordered <= 10);
console.log(stock === 3, stock !== 3);

const canShip = ordered <= stock;
console.log("can ship?", canShip);
```

```text output
true
true
true false
can ship? false
```

<Happened>
<Tr>
<En>

- Each comparison produced a boolean you can print, store in a variable (`canShip`) or use in an `if`.
- `>=` means "greater than **or equal**". There's no `=>` comparison (that's arrow-function syntax) and no `=<`.
- A single `=` **assigns** a value; it never compares. `===` compares.

</En>
<Ur>

- Har muqable ne boolean banaya jo aap print kar sakte hain, variable me rakh sakte hain (`canShip`) ya `if` me istemal kar sakte hain.
- `>=` ka matlab "bara **ya barabar**". `=>` muqabla nahi (wo arrow function ka syntax hai) aur `=<` nahi hota.
- Akela `=` value **deta** hai; kabhi muqabla nahi karta. `===` muqabla karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Comparing strings">

<Tr>
<En>
Strings are compared **character by character** using each character's code, like a dictionary that puts all **capital letters before lowercase** ones. Digits in text are compared as characters too, not as numbers.
</En>
<Ur>
Strings **character ba character** har character ke code se compare hoti hain, us lughat ki tarah jo tamam **bare huroof ko chhote huroof se pehle** rakhti hai. Text me hindse bhi characters ki tarah compare hote hain, numbers ki tarah nahi.
</Ur>
</Tr>

```javascript
console.log("apple" < "banana");
console.log("apple" < "apricot");
console.log("Zebra" < "apple");
console.log("10" < "9");
console.log(10 < 9);
console.log("item2" < "item10");

// Sort names the way people expect
console.log(["bob", "Alice", "carol"].sort());
console.log(["bob", "Alice", "carol"].sort((a, b) => a.localeCompare(b)));
```

```text output
true
true
true
true
false
false
[ 'Alice', 'bob', 'carol' ]
[ 'Alice', 'bob', 'carol' ]
```

<Happened>
<Tr>
<En>

- `"apple" < "apricot"`: both start with `ap`, then `p` comes before `r`, so true.
- `"Zebra" < "apple"` is true because every capital letter has a smaller code than every lowercase letter.
- `"10" < "9"` is **true**: as text, `"1"` comes before `"9"`, just like "apple" before "banana". The numbers `10 < 9` are false. This is why prices or versions stored as text sort wrongly.
- `"item2" < "item10"` is false for the same reason.
- `localeCompare` compares the way people expect for a language (and can ignore case or sort numbers naturally with options). Here both sorts happen to agree; with names like `"Émile"` or `"zoe"` vs `"Zoe"` they wouldn't.

</En>
<Ur>

- `"apple" < "apricot"`: dono `ap` se shuru, phir `p`, `r` se pehle aata hai, isliye true.
- `"Zebra" < "apple"` true hai kyun ke har bare harf ka code har chhote harf se kam hai.
- `"10" < "9"` **true** hai: text ki tarah `"1"`, `"9"` se pehle aata hai, bilkul "apple" ki tarah "banana" se pehle. Numbers `10 < 9` false hain. Isi wajah se text me rakhi qeematen ya versions ghalat sort hote hain.
- `"item2" < "item10"` isi wajah se false hai.
- `localeCompare` waise compare karta hai jaise kisi zaban ke log umeed karte hain (aur options se case nazarandaz kar sakta ya numbers qudrati tarah sort kar sakta hai). Yahan dono sort ittefaq se ek jaise hain; `"Émile"` ya `"zoe"` vs `"Zoe"` jaise naamon ke saath nahi honge.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Comparing different types">

<Tr>
<En>
When you compare a string with a number using `<`, `>`, `<=` or `>=`, JavaScript converts the string to a **number** first. `null` becomes `0` and `undefined` becomes `NaN`, and any comparison with `NaN` is false.
</En>
<Ur>
Jab aap `<`, `>`, `<=` ya `>=` se string ka number se muqabla karte hain, JavaScript pehle string ko **number** me badalti hai. `null` `0` ban jata hai aur `undefined` `NaN`, aur `NaN` ke saath har muqabla false hai.
</Ur>
</Tr>

```javascript
console.log("10" > 9);
console.log("abc" > 9, "abc" < 9);
console.log(null >= 0, null > 0);
console.log(undefined > 0, undefined < 0, undefined >= 0);

const input = "25"; // from a form
console.log(input > 100, Number(input) > 100);
```

```text output
true
false false
true false
false false false
false false
```

<Happened>
<Tr>
<En>

- `"10" > 9`: `"10"` became 10, and 10 > 9 is true.
- `"abc"` became `NaN`, so it's neither bigger nor smaller than 9. Both answers are **false**.
- `null >= 0` is true but `null > 0` is false (null becomes 0, and 0 >= 0). This odd pair is a classic interview question.
- `undefined` becomes `NaN`, so **every** comparison with it is false. A missing value silently fails a limit check like `if (qty > 10)`.
- Comparing two **strings** never converts: `"25" > "100"` would be true (text order). Convert input explicitly and the question becomes clear.

</En>
<Ur>

- `"10" > 9`: `"10"` 10 bana, aur 10 > 9 true hai.
- `"abc"` `NaN` bana, isliye ye 9 se na bara hai na chhota. Dono jawab **false**.
- `null >= 0` true hai magar `null > 0` false (null 0 banta hai, aur 0 >= 0). Ye ajeeb jora interview ka mashhoor sawal hai.
- `undefined` `NaN` banta hai, isliye is ke saath **har** muqabla false hai. Ghayab value `if (qty > 10)` jaisa hadd ka check khamoshi se fail kar deti hai.
- Do **strings** ka muqabla kabhi nahi badalta: `"25" > "100"` true hota (text ki tarteeb). Input khud badlein aur sawal wazeh ho jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="&& and || return values, not just booleans">

<Tr>
<En>
`&&` ("and") and `||` ("or") are usually read as true/false logic, but they actually **return one of their operands**. `a || b` returns `a` if `a` is truthy, otherwise `b`. `a && b` returns `a` if `a` is falsy, otherwise `b`. They also **stop early** (short-circuit) as soon as the answer is known.
</En>
<Ur>
`&&` ("aur") aur `||` ("ya") aam taur par true/false mantiq ki tarah parhe jate hain, magar asal me ye **apne operands me se ek wapas** karte hain. `a || b` `a` wapas karta hai agar `a` truthy ho, warna `b`. `a && b` `a` wapas karta hai agar `a` falsy ho, warna `b`. Ye jawab maloom hote hi **jaldi ruk** bhi jate hain (short-circuit).
</Ur>
</Tr>

```javascript
const isLoggedIn = true;
const isAdmin = false;
console.log(isLoggedIn && isAdmin, isLoggedIn || isAdmin, !isAdmin);

console.log("Alex" || "Guest");
console.log("" || "Guest");
console.log("Alex" && "Welcome back");
console.log(0 && "never reached");

function log(msg) {
  console.log("ran:", msg);
  return true;
}
false && log("A");
true || log("B");
true && log("C");
```

```text output
false true true
Alex
Guest
Welcome back
0
ran: C
```

<Happened>
<Tr>
<En>

- With booleans they work like plain logic: "logged in **and** admin" is false; "logged in **or** admin" is true; `!` flips a boolean.
- `"Alex" || "Guest"` returned `"Alex"` (the first truthy value). `"" || "Guest"` returned `"Guest"` because the empty string is **falsy**.
- `"Alex" && "Welcome back"` returned the second value because the first was truthy; `0 && …` returned `0` itself, the first falsy value.
- `false && log("A")` never called `log`: once the left side is false, "and" can't be true, so JavaScript skips the right side. Same for `true || log("B")`. Only `"C"` ran.
- Falsy values are `false`, `0`, `""`, `null`, `undefined` and `NaN` (plus `-0` and `0n`). Everything else is truthy. (The Truthy, Falsy and Nullish lesson goes deeper.)

</En>
<Ur>

- Booleans ke saath ye saadi mantiq ki tarah chalte hain: "login **aur** admin" false hai; "login **ya** admin" true; `!` boolean ulat deta hai.
- `"Alex" || "Guest"` ne `"Alex"` (pehli truthy value) wapas kiya. `"" || "Guest"` ne `"Guest"` wapas kiya kyun ke khaali string **falsy** hai.
- `"Alex" && "Welcome back"` ne doosri value wapas ki kyun ke pehli truthy thi; `0 && …` ne khud `0` wapas kiya, pehli falsy value.
- `false && log("A")` ne `log` kabhi call nahi kiya: baayan hissa false hote hi "aur" true nahi ho sakta, isliye JavaScript daayan hissa chhor deti hai. `true || log("B")` me bhi yahi. Sirf `"C"` chala.
- Falsy values `false`, `0`, `""`, `null`, `undefined` aur `NaN` hain (saath `-0` aur `0n`). Baqi sab truthy. (Truthy, Falsy and Nullish lesson aur gehrai me jata hai.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="?? for safe defaults">

<Tr>
<En>
`||` replaces **every** falsy value, including `0` and `""`, which are often real, valid values. The **nullish coalescing** operator `??` only replaces `null` and `undefined`: "use the fallback only if the value is **missing**".
</En>
<Ur>
`||` **har** falsy value badal deta hai, `0` aur `""` samet, jo aksar asli aur sahi values hoti hain. **Nullish coalescing** operator `??` sirf `null` aur `undefined` badalta hai: "fallback sirf tab lo jab value **ghayab** ho".
</Ur>
</Tr>

```javascript
const settings = { volume: 0, nickname: "", theme: null };

console.log("volume ||:", settings.volume || 50);
console.log("volume ??:", settings.volume ?? 50);

console.log("nickname ||:", JSON.stringify(settings.nickname || "Guest"));
console.log("nickname ??:", JSON.stringify(settings.nickname ?? "Guest"));

console.log("theme ??:", settings.theme ?? "light");
console.log("missing ??:", settings.fontSize ?? 16);
```

```text output
volume ||: 50
volume ??: 0
nickname ||: "Guest"
nickname ??: ""
theme ??: light
missing ??: 16
```

<Happened>
<Tr>
<En>

- The user chose volume **0** (mute). `||` threw that away and used 50, a real bug. `??` kept 0.
- An empty nickname: with `||` it becomes "Guest"; with `??` it stays empty. Which is right depends on what you want. Pick on purpose.
- `null` and a property that doesn't exist (`undefined`) both got their fallbacks with `??`.
- Rule of thumb: **`??` for defaults**, `||` only when you deliberately want empty strings and zeros replaced too.

</En>
<Ur>

- User ne volume **0** (mute) chuna. `||` ne use phenk kar 50 le liya, asli bug. `??` ne 0 rakha.
- Khaali nickname: `||` ke saath "Guest" ban jata hai; `??` ke saath khaali rehta hai. Kaun sahi hai ye is par munhasir hai ke aap kya chahte hain. Jaan boojh kar chunein.
- `null` aur jo property maujood hi nahi (`undefined`) dono ko `??` se fallback mila.
- Aam qaida: **defaults ke liye `??`**, `||` sirf tab jab aap jaan boojh kar khaali strings aur zero bhi badalna chahein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The ternary operator">

<Tr>
<En>
`condition ? valueIfTrue : valueIfFalse` picks one of two values in a single expression. It's perfect for short choices inside a line, like a label or a CSS class.
</En>
<Ur>
`condition ? valueIfTrue : valueIfFalse` ek hi expression me do me se ek value chunta hai. Line ke andar chhote intikhab ke liye behtareen hai, jaise label ya CSS class.
</Ur>
</Tr>

```javascript
const stock = 0;
console.log(stock > 0 ? "In stock" : "Sold out");

const items = 1;
console.log(`You have ${items} ${items === 1 ? "item" : "items"} in your cart`);

const score = 72;
const grade = score >= 90 ? "A" : score >= 80 ? "B" : score >= 70 ? "C" : "F";
console.log("grade:", grade);
```

```text output
Sold out
You have 1 item in your cart
grade: C
```

<Happened>
<Tr>
<En>

- `stock > 0` was false, so the value after `:` was chosen.
- Inside a template literal, the ternary picked "item" vs "items", a very common use.
- Ternaries can be chained (the grade), but beyond two levels an `if…else` or a lookup is easier to read.
- A ternary **produces a value**; use `if` when you want to **do** different things (several statements).

</En>
<Ur>

- `stock > 0` false tha, isliye `:` ke baad wali value chuni gayi.
- Template literal ke andar ternary ne "item" ya "items" chuna, bohot aam istemal.
- Ternaries zanjeer ki tarah jor sakte hain (grade), magar do levels se aage `if…else` ya lookup parhne me aasaan hai.
- Ternary **value banata** hai; jab mukhtalif kaam **karne** hon (kai statements) to `if` lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Assignment shortcuts, ++ and --">

<Tr>
<En>
`x += 5` is short for `x = x + 5` (also `-=`, `*=`, `/=`, `%=`, `**=`). The logical versions `??=`, `||=` and `&&=` assign only when needed. `++` and `--` add or subtract 1, and **where** you put them matters if you use the result.
</En>
<Ur>
`x += 5`, `x = x + 5` ka mukhtasar hai (saath `-=`, `*=`, `/=`, `%=`, `**=`). Mantiqi versions `??=`, `||=` aur `&&=` sirf zaroorat par value dete hain. `++` aur `--` 1 jorte ya ghatate hain, aur agar nateeja istemal karein to inhe **kahan** rakha ye ahem hai.
</Ur>
</Tr>

```javascript
let total = 100;
total += 20;
total -= 5;
total *= 2;
console.log("total:", total);
```

<Tr>

<Step title="Coercion with +: text wins">

<Tr>
<En>
`+` does two jobs: adding numbers and **joining text**. If **either** side is a string, `+` converts the other side to a string and joins them. Everything else (`-`, `*`, `/`, `%`, `**`) always converts to **numbers**.
</En>
<Ur>
`+` do kaam karta hai: numbers jorna aur **text jorna**. Agar **koi ek** taraf string ho, to `+` doosri taraf ko string me badal kar dono ko jor deta hai. Baqi sab (`-`, `*`, `/`, `%`, `**`) hamesha **numbers** me badalte hain.
</Ur>
</Tr>


<Happened>
<Tr>
<En>

- Any string next to `+` turns the operation into **joining**: `"5" + 2` → `"52"`.
- `-`, `*`, `/`, `%` only do math, so `"5" - 2` → 3 and `"5" * "2"` → 10.
- `+` works **left to right**: `1 + 2 + "3"` is `3 + "3"` → `"33"`; `"1" + 2 + 3` is `"12" + 3` → `"123"`.

- **Unary `+`** (`+"5"`) converts to a number, like `Number("5")`. It's short but easy to miss; `Number(…)` is clearer.

</En>
<Ur>

- `+` ke saath koi bhi string amal ko **jorne** me badal deti hai: `"5" + 2` → `"52"`.
- `-`, `*`, `/`, `%` sirf hisaab karte hain, isliye `"5" - 2` → 3 aur `"5" * "2"` → 10.

<Step title="Precedence: which operator goes first">

<Tr>
<En>
Operators have an order. From first to last (simplified): brackets → `!` and unary `+`/`-`/`typeof` → `**` → `* / %` → `+ -` → comparisons `< > <= >=` → equality `=== !==` → `&&` → `||` and `??` → `? :` → assignment `=`.
</En>
<Ur>
Operators ki tarteeb hoti hai. Pehle se aakhir tak (saada shakal me): brackets → `!` aur unary `+`/`-`/`typeof` → `**` → `* / %` → `+ -` → muqable `< > <= >=` → barabari `=== !==` → `&&` → `||` aur `??` → `? :` → assignment `=`.
</Ur>
</Tr>

```javascript

const isOwner = true;
const isLocked = true;

console.log(isAdmin || isOwner && !isLocked);
console.log((isAdmin || isOwner) && !isLocked);

console.log(2 + 3 > 4 && 10 % 3 === 1);
```

```text output

true true
true
```

<Happened>
<Tr>
<En>

- Line 1 is read as `isAdmin || (isOwner && !isLocked)` = false || (true && false) = **false**.
- Here the bracketed version gives the same answer, but with `isAdmin = true` they'd differ (true vs false). Brackets make the intent explicit; use them.
- `!0 === true`: `!` goes first → `true === true` → true. `!(0 === true)` → `!false` → true. Same result here, different meaning.
- Mixing `??` directly with `&&` or `||` is **not allowed** without brackets: `a || b ?? c` is a SyntaxError. Write `(a || b) ?? c`.

</En>
<Ur>

- Line 1 aise parhi jati hai: `isAdmin || (isOwner && !isLocked)` = false || (true && false) = **false**.
- Yahan brackets wala version wahi jawab deta hai, magar `isAdmin = true` ke saath farq hota (true vs false). Brackets niyat wazeh karte hain; inhe lagayen.
- `!0 === true`: `!` pehle → `true === true` → true. `!(0 === true)` → `!false` → true. Yahan nateeja ek, matlab mukhtalif.
- `??` ko seedha `&&` ya `||` ke saath baghair brackets milana **mana** hai: `a || b ?? c` SyntaxError hai. `(a || b) ?? c` likhein.

<DeepDive title="How objects become primitives">

When an operator needs a primitive from an object, JavaScript calls **`ToPrimitive`**:

1. If the object has a `Symbol.toPrimitive` method, call it with a hint (`"number"`, `"string"` or `"default"`).
2. Otherwise, for the number/default hint try `valueOf()` then `toString()`; for the string hint try `toString()` then `valueOf()`.

That's why `Date` objects subtract nicely (`date2 - date1` gives milliseconds, via `valueOf`) but join as text with `+` (`date + ""` gives a readable string).

```text
const price = {
  cents: 1999,
  [Symbol.toPrimitive](hint) {
    return hint === "number" ? this.cents : `$${(this.cents / 100).toFixed(2)}`;
  },
};
// +price → 1999      `${price}` → "$19.99"
```

**Other operators.** `in` checks if a property exists (`"id" in user`); `instanceof` checks a prototype chain; `delete` removes a property; `void` returns `undefined`; the comma operator evaluates several expressions and returns the last. Bitwise operators (`&`, `|`, `^`, `~`, `<<`, `>>`, `>>>`) work on 32-bit integers.

**Optional chaining** `a?.b` and **spread** `...` have their own lesson.

</DeepDive>

<DeepDive title="Real world: the free orders">

A store's checkout had a minimum order rule: `if (cartTotal < minimum) showError()`. The minimum came from a settings API as a string, `"25"`, and the cart total was calculated from item prices that, after a refactor, were also stored as strings in the browser.

Comparing two strings meant **text order**: `"100" < "25"` is true (because `"1"` < `"2"`), so customers with large carts were blocked, and `"3" < "25"` is false, so a $3 cart was allowed through. Meanwhile, the server trusted the browser's total, which had been built with `+` and become `"1999" + "500"` = `"1999500"`.

The fixes:

1. Convert API values at the boundary: `const minimum = Number(settings.minimum)`, and reject `NaN`.
2. Keep prices as integer cents (numbers) everywhere in the app.
3. Recalculate totals and minimums **on the server** from the database, ignoring any total sent by the browser.
4. Turn on TypeScript so `string < number` comparisons and `string + number` additions are flagged before shipping.

Lesson: coercion bugs often hide where data **enters** your program. Convert and validate right there.

</DeepDive>

<DeepDive title="Security lens">

- **Type confusion in checks.** `if (user.role == 1)` passes for `"1"`, `[1]` and `true`. Attackers sending JSON can choose the type. Use `===` and validate types (zod, TypeScript at the boundary).
- **`NaN` and `undefined` bypass limits**: `undefined > 100` and `NaN > 100` are false, so `if (amount > limit) deny()` lets them through. Check `Number.isFinite(amount)` first, and fail closed.
- **`||` defaults can erase deliberate values**: a permission level of `0` replaced by a default of `1` is a privilege bug. Use `??`.
- **String building for queries or HTML** with `+` is how injection happens. Use parameterised queries and safe templating instead of concatenation.
- **Prototype tricks**: objects from JSON can include keys like `__proto__` or `toString`. Don't use user data as property names in plain objects without care; prefer `Map` or `Object.create(null)`.

</DeepDive>

<QA q="What is type coercion in JavaScript?">
It is the automatic conversion of a value from one type to another when an operator or function expects a different type, for example converting a string to a number for subtraction or a number to a string when concatenating with plus.
</QA>

<QA q="Why does [] + {} produce [object Object]?">
The plus operator converts both objects to primitives. An empty array becomes an empty string and a plain object becomes the string [object Object]; because one side is a string, plus concatenates them.
</QA>

<QA q="What is the difference between the logical OR and the nullish coalescing operator?">
OR returns the right side whenever the left side is falsy, including 0, empty string and false. Nullish coalescing returns the right side only when the left side is null or undefined, so valid falsy values are preserved.
</QA>

<QA q="What do the logical AND and OR operators return?">
They return one of their operands, not necessarily a boolean. OR returns the first truthy operand or the last operand; AND returns the first falsy operand or the last operand. Both short-circuit and skip evaluating the right side when the result is already determined.
</QA>

<QA q="Why is null >= 0 true while null > 0 and null == 0 are false?">
Relational comparisons convert null to the number 0, so null >= 0 is 0 >= 0 which is true and null > 0 is false. Loose equality has special rules where null is only equal to undefined, so null == 0 is false.
</QA>
