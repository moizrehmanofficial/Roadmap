<BigIdea>
<Tr>
<En>
An **error** is JavaScript's way of saying "I can't continue with this". When something goes wrong (reading a property of `null`, broken JSON, an invalid price), an **Error object** is **thrown**. If nothing catches it, the current task stops and the error is printed. **`try { … } catch (error) { … }`** lets you catch errors from a block of code and decide what to do: show a friendly message, use a fallback, retry, or let it continue upward. **`finally`** runs no matter what, perfect for cleanup. You can **`throw`** your own errors when input breaks your rules, and create **custom error classes** so different problems get different responses (400 for bad input, 404 for missing data, 500 for bugs). The skill isn't catching everything; it's catching **what you can handle**, at the right place, and never hiding bugs.
</En>
<Ur>
**Error** JavaScript ka ye kehne ka tareeqa hai ke "main is ke saath aage nahi chal sakti". Jab kuch ghalat ho (`null` ki property parhna, toota JSON, ghalat qeemat), ek **Error object** **phenka** jata hai. Agar koi use na pakre, maujooda kaam ruk jata hai aur error print hota hai. **`try { … } catch (error) { … }`** aap ko code ke ek block ke errors pakar kar faisla karne deta hai ke kya karna hai: dostana paighaam dikhana, fallback lena, dobara koshish karna, ya use upar jane dena. **`finally`** har haal me chalta hai, safai ke liye behtareen. Jab input aap ke qawaid tore to aap apne errors **`throw`** kar sakte hain, aur **custom error classes** bana sakte hain taa ke mukhtalif masail ko mukhtalif jawab milen (ghalat input ke liye 400, ghayab data ke liye 404, bugs ke liye 500). Hunar sab kuch pakarna nahi; hunar ye hai ke **jo sambhal sakte hain** wo sahi jagah pakrein, aur bugs kabhi na chhupayen.
</Ur>
</Tr>

<Why>
<Tr>
<En>

- **Real programs meet bad input, missing data and failing networks every day.** Without handling, one error can crash a server or blank a page.
- **Good errors are good UX**: "Please enter a quantity from 1 to 99" instead of a frozen form or "undefined".
- **Good errors are good debugging**: a clear message, a cause and a stack trace point straight at the problem.
- **Bad error handling hides bugs**: an empty `catch {}` turns a crash you'd notice into wrong data you won't.

</En>
<Ur>

- **Asli programs ko roz ghalat input, ghayab data aur fail hote networks milte hain.** Sambhale baghair ek error server crash ya page khaali kar sakta hai.
- **Achhe errors achha UX hain**: jame hue form ya "undefined" ke bajaye "Please enter a quantity from 1 to 99".
- **Achhe errors achhi debugging hain**: saaf paighaam, wajah aur stack trace seedha masle ki taraf ishara karte hain.
- **Buri error handling bugs chhupati hai**: khaali `catch {}` us crash ko jo aap dekhte, ghalat data me badal deta hai jo aap nahi dekhenge.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Approach |
| --- | --- |
| Input breaks your rules | `throw` a specific error (or return a result object) |
| You can recover (fallback, retry, friendly message) | `try…catch` there |
| You can't do anything useful | Don't catch; let it go up to a place that can |
| Resources to release (connections, loading spinners) | `finally` |
| Async code | `try…catch` around `await`, or `.catch()` |
| Edge of the app (API handler, React error boundary) | Catch everything, log details, return a safe message |

</En>
<Ur>

| Soorat-e-haal | Tareeqa |
| --- | --- |
| Input aap ke qawaid tore | Khaas error `throw` karein (ya result object wapas karein) |
| Aap sambhal sakte hain (fallback, retry, dostana paighaam) | Wahan `try…catch` |
| Aap kuch kaam ka nahi kar sakte | Na pakrein; use us jagah tak jane dein jo kar sake |
| Chhorne wale resources (connections, loading spinners) | `finally` |
| Async code | `await` ke gird `try…catch`, ya `.catch()` |
| App ka kinara (API handler, React error boundary) | Sab pakrein, tafseel log karein, mehfooz paighaam dein |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Validate early and `throw new Error("clear message")` (or a custom error) when something is wrong.
2. Wrap code that can fail **and** that you can handle in `try…catch`.
3. In `catch`, handle the errors you expect; **rethrow** the rest.
4. Put cleanup in `finally`.
5. Show users a safe message; log the full error for developers.

</En>
<Ur>

1. Jaldi validate karein aur kuch ghalat ho to `throw new Error("saaf paighaam")` (ya custom error) karein.
2. Jo code fail ho sakta hai **aur** jise aap sambhal sakte hain, use `try…catch` me lapetein.
3. `catch` me mutawaqqa errors sambhalein; baqi **dobara phenk** dein.
4. Safai `finally` me rakhein.
5. Users ko mehfooz paighaam dikhayen; developers ke liye poora error log karein.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of a **restaurant kitchen**.

- A cook who finds the fridge empty **shouts** "No eggs!" (`throw`). They don't quietly serve an empty plate.
- The **head chef** (`catch`) hears it and decides: swap to a different dish (fallback), send someone to the store (retry), or tell the waiter to apologise to the customer (friendly message).
- If a junior cook can't fix a problem, they don't hide it; they pass it **up** to someone who can (rethrow).
- No matter how the order went, **someone cleans the station** at the end (`finally`).
- Different shouts mean different responses: "Customer asked for something not on the menu" (400), "We're out of that" (404), "The oven is on fire!" (500, call for help).
- The customer hears "Sorry, that dish isn't available tonight", not "Fridge 3 compressor fault code E42" (safe message vs logs).

</En>
<Ur>

**Restaurant ki kitchen** ka sochein.

- Jo cook fridge khaali paye wo **chillata** hai "Ande nahi hain!" (`throw`). Wo khamoshi se khaali plate nahi bhejta.
- **Head chef** (`catch`) sun kar faisla karta hai: doosri dish (fallback), kisi ko store bhejna (retry), ya waiter se kehna ke customer se maafi maange (dostana paighaam).
- Agar junior cook masla theek na kar sake to use chhupata nahi; use **upar** us tak bhejta hai jo kar sake (rethrow).
- Order kaisa bhi gaya ho, aakhir me **koi station saaf karta hai** (`finally`).
- Mukhtalif cheekhon ke mukhtalif jawab: "Customer ne aisi cheez maangi jo menu par nahi" (400), "Wo khatam ho gaya" (404), "Oven me aag lagi hai!" (500, madad bulao).
- Customer ko "Maazrat, wo dish aaj nahi hai" sunai deta hai, "Fridge 3 compressor fault code E42" nahi (mehfooz paighaam vs logs).

## Learn it step by step

<Walkthrough>

<Step title="throw and try…catch">

<Tr>
<En>
`throw` stops the current function immediately and jumps to the nearest `catch` up the call chain. Code inside `try` runs normally until something throws; then the rest of `try` is skipped and `catch` runs with the error. After `catch`, the program continues.
</En>
<Ur>
`throw` maujooda function ko foran rok deta hai aur call chain me upar sab se qareebi `catch` tak koodta hai. `try` ke andar ka code aam tarah chalta hai jab tak kuch error na phenke; phir `try` ka baqi hissa chhoot jata hai aur `catch` error ke saath chalta hai. `catch` ke baad program jaari rehta hai.
</Ur>
</Tr>

```javascript
function parsePrice(text) {
  const value = Number(text);
  if (!Number.isFinite(value) || value < 0) {
    throw new Error(`Invalid price: "${text}"`);
  }
  return Math.round(value * 100);
}

for (const input of ["19.99", "free", "-5"]) {
  try {
    console.log(input, "→", parsePrice(input), "cents");
  } catch (error) {
    console.log(input, "→", error.message);
  }
}
console.log("The program keeps running");
```

```text output
19.99 → 1999 cents
free → Invalid price: "free"
-5 → Invalid price: "-5"
The program keeps running
```

<Happened>
<Tr>
<En>

- For "free" and "-5", `parsePrice` threw before reaching `return`. The `console.log` inside `try` was skipped, and `catch` printed the message.
- Each loop round has its own `try`, so one bad input didn't stop the others.
- Without `try…catch`, the first bad input would have stopped the whole program.
- The message includes the bad value, which makes the problem obvious.

</En>
<Ur>

- "free" aur "-5" ke liye `parsePrice` ne `return` tak pohanchne se pehle error phenka. `try` ke andar ka `console.log` chhoot gaya, aur `catch` ne paighaam print kiya.
- Har loop chakkar ka apna `try` hai, isliye ek ghalat input ne baqi ko nahi roka.
- `try…catch` ke baghair pehla ghalat input poora program rok deta.
- Paighaam me ghalat value shamil hai, jo masla wazeh kar deti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="finally always runs">

<Tr>
<En>
`finally` runs after `try` and `catch`, **whether or not** an error happened, and even when `try` or `catch` contains a `return`. Use it to release resources: close connections, stop loading spinners, unlock buttons.
</En>
<Ur>
`finally` `try` aur `catch` ke baad chalta hai, **chahe** error hua ho ya nahi, aur tab bhi jab `try` ya `catch` me `return` ho. Ise resources chhorne ke liye lein: connections band karna, loading spinners rokna, buttons kholna.
</Ur>
</Tr>

```javascript
function loadReport(shouldFail) {
  console.log("open connection");
  try {
    if (shouldFail) throw new Error("query failed");
    return "report data";
  } catch (error) {
    console.log("handled:", error.message);
    return "fallback data";
  } finally {
    console.log("close connection");
  }
}

console.log(loadReport(false));
console.log(loadReport(true));
```

```text output
open connection
close connection
report data
open connection
handled: query failed
close connection
fallback data
```

<Happened>
<Tr>
<En>

- In both runs, "close connection" printed, **before** the function's return value reached the caller.
- In the failing run, `catch` handled the error and returned a fallback; `finally` still ran.
- A classic UI use: `setLoading(true); try { await save(); } finally { setLoading(false); }`, so the spinner never gets stuck.

</En>
<Ur>

- Dono dafa "close connection" print hua, function ki wapas hone wali value call karne wale tak pohanchne se **pehle**.
- Fail hone wali dafa `catch` ne error sambhala aur fallback wapas kiya; `finally` phir bhi chala.
- UI ka mashhoor istemal: `setLoading(true); try { await save(); } finally { setLoading(false); }`, taa ke spinner kabhi atka na rahe.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Built-in error types">

<Tr>
<En>
JavaScript throws different error types for different problems. They all extend `Error`, so `instanceof Error` is true for every one, and `error.message` explains what happened.
</En>
<Ur>
JavaScript mukhtalif masail ke liye mukhtalif error types phenkti hai. Sab `Error` ko extend karti hain, isliye har ek ke liye `instanceof Error` true hai, aur `error.message` batata hai kya hua.
</Ur>

```javascript
const attempts = [
  () => null.length,
  () => undefinedVariable + 1,
  () => JSON.parse("{bad json}"),
  () => (1.5).toFixed(200),
  () => new Array(-1),
  () => decodeURIComponent("%"),

for (const attempt of attempts) {
  try {
    attempt();
  } catch (error) {
    console.log(error.constructor.name.padEnd(15), error instanceof Error, "|", error.message);
  }
}
```

| Type | Aam taur par matlab |

- Bilkul theek paighaam browsers me mukhtalif ho sakte hain; error **types** mayari hain.

<Step title="The Error object: message, stack, and never throw strings">

<Tr>
<En>
An `Error` has a `name`, a `message` and a `stack` (the path of function calls that led to it). You **can** throw any value, even a string, but then you lose the stack and `instanceof Error` checks fail. Always throw `Error` objects.
</En>
<Ur>
`Error` ka `name`, `message` aur `stack` (function calls ka wo raasta jo us tak le gaya) hota hai. Aap koi bhi value phenk **sakte** hain, string bhi, magar phir stack kho jata hai aur `instanceof Error` checks fail hote hain. Hamesha `Error` objects phenkein.
</Ur>
</Tr>

```javascript
const err = new Error("Card declined");
console.log(err.name, "|", err.message, "|", err.stack.split("\n")[0]);
console.log(typeof err.stack, err.stack.split("\n").length > 1);

try {
  throw "out of stock";
} catch (e) {
  console.log(typeof e, e instanceof Error, e.stack);
}
```

```text output
Error | Card declined | Error: Card declined
string true
string false undefined
```

<Happened>
<Tr>
<En>

- The stack's first line is "Name: message"; the following lines (not printed here, because they include file paths) list each function call with file, line and column.
- The thrown string has **no stack** (`undefined`), so logs can't tell you where it came from, and code that checks `error.message` gets `undefined`.
- Error-tracking services (Sentry and similar) rely on the stack to group and locate errors.

</En>
<Ur>

- Stack ki pehli line "Name: message" hai; agli lines (yahan print nahi kin, kyun ke un me file paths hain) har function call ko file, line aur column ke saath dikhati hain.
- Phenki gayi string ka **stack nahi** (`undefined`), isliye logs nahi bata sakte ke ye kahan se aayi, aur `error.message` check karne wale code ko `undefined` milta hai.
- Error tracking services (Sentry waghaira) errors ko ikattha karne aur dhoondne ke liye stack par chalti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Custom errors and choosing a response">

<Tr>
<En>
Create your own error classes for situations your app knows about. At the **edge** of your app (an API handler, a top-level function), check the error type with `instanceof` and respond appropriately. Anything unexpected becomes a generic 500 and gets logged.
</En>
<Ur>
Un soorton ke liye apni error classes banayen jo aap ki app jaanti hai. App ke **kinare** (API handler, top-level function) par `instanceof` se error ki type check karein aur munasib jawab dein. Jo bhi ghair mutawaqqa ho wo aam 500 ban jata hai aur log hota hai.
</Ur>
</Tr>

```javascript
class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

class NotFoundError extends Error {
  constructor(resource, id) {
    super(`${resource} ${id} not found`);
    this.name = "NotFoundError";
  }
}

function handle(fn) {
  try {
    return { status: 200, body: fn() };
  } catch (error) {
    if (error instanceof ValidationError) {
      return { status: 400, body: { field: error.field, message: error.message } };
    }
    if (error instanceof NotFoundError) {
      return { status: 404, body: { message: error.message } };
    }
    console.log("[log] unexpected:", error.name, error.message);
    return { status: 500, body: { message: "Something went wrong" } };
  }
}

console.log(handle(() => "ok"));
console.log(handle(() => { throw new ValidationError("email", "Email is required"); }));
console.log(handle(() => { throw new NotFoundError("Order", 42); }));
console.log(handle(() => null.total));
```

```text output
{ status: 200, body: 'ok' }
{ status: 400, body: { field: 'email', message: 'Email is required' } }
{ status: 404, body: { message: 'Order 42 not found' } }
[log] unexpected: TypeError Cannot read properties of null (reading 'total')
{ status: 500, body: { message: 'Something went wrong' } }
```

<Happened>
<Tr>
<En>

- Expected problems got specific, helpful responses: the field name for validation, a clear "not found".
- The `TypeError` was a **bug**. It was logged with its details for developers, and the user got a generic message that reveals nothing about the code.
- This is exactly how frameworks like Express, NestJS and Next.js route handlers organise error handling.

</En>
<Ur>

- Mutawaqqa masail ko khaas, madadgar jawab mile: validation ke liye field ka naam, saaf "not found".
- `TypeError` ek **bug** tha. Ye developers ke liye apni tafseel ke saath log hua, aur user ko aam paighaam mila jo code ke baare me kuch zahir nahi karta.
- Express, NestJS aur Next.js route handlers jaise frameworks error handling bilkul isi tarah tarteeb dete hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Wrapping errors with a cause">

<Tr>
<En>
When you catch a low-level error and throw a clearer one, pass the original as **`cause`**. The new error explains **what** failed in your terms; the cause keeps the technical **why**.
</En>
<Ur>
Jab aap neeche ke level ka error pakar kar zyada saaf error phenkein, to asal ko **`cause`** ki tarah dein. Naya error aap ki zaban me batata hai **kya** fail hua; cause takneeki **kyun** rakhta hai.
</Ur>
</Tr>

```javascript
function readConfig(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    throw new Error("Config file is not valid JSON", { cause: error });
  }
}

try {
  readConfig("{port: 3000}");
} catch (error) {
  console.log(error.message);
  console.log("caused by:", error.cause.name, "-", error.cause.message);
}
```

```text output
Config file is not valid JSON
caused by: SyntaxError - Expected property name or '}' in JSON at position 1 (line 1 column 2)
```

<Happened>
<Tr>
<En>

- The caller sees a meaningful message ("Config file is not valid JSON") instead of a bare parser message.
- Nothing is lost: `error.cause` holds the original `SyntaxError` with its exact position. Node and browser consoles print the cause chain automatically.

</En>
<Ur>

- Call karne wale ko saade parser paighaam ke bajaye ba-maani paighaam ("Config file is not valid JSON") nazar aata hai.
- Kuch nahi khota: `error.cause` me asal `SyntaxError` us ki bilkul theek jagah ke saath hai. Node aur browser consoles cause ki zanjeer khud print karte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Catch what you can handle, rethrow the rest">

<Tr>
<En>
A `catch` block catches **everything**, including bugs you didn't expect. Check the error, handle the cases you understand, and **rethrow** anything else with `throw error;` so it isn't silently swallowed.
</En>
<Ur>
`catch` block **sab kuch** pakarta hai, un bugs samet jin ki aap ko umeed nahi thi. Error check karein, jo soorten samajhte hain unhe sambhalein, aur baqi sab ko `throw error;` se **dobara phenk** dein taa ke wo khamoshi se nigla na jaye.
</Ur>
</Tr>

```javascript
function parseQty(text) {
  const n = Number(text);
  if (!Number.isInteger(n) || n < 1) throw new RangeError("Quantity must be a whole number from 1");
  return n;
}

function addToCart(text) {
  try {
    return "added " + parseQty(text);
  } catch (error) {
    if (error instanceof RangeError) return "Please enter a valid quantity";

  }

console.log(addToCart("2"), "|", addToCart("0"));

try {
  addToCart({

      throw new TypeError("weird input");
```

<Tr>

- The unexpected `TypeError` was **not** turned into "Please enter a valid quantity" (which would have hidden a real problem). It was rethrown and reached the outer `catch` with its original type and message.

</En>

<Step title="Errors in async code">

<Tr>
<En>
A rejected promise behaves like a thrown error **when you `await` it**: `try…catch` catches it. Without `await`, the error escapes the `try`. With promise chains, use `.catch()`. A rejection nobody handles becomes an **unhandled rejection** (a warning in browsers, a crash in modern Node).
</En>
<Ur>
Rejected promise **`await` karne par** phenke gaye error ki tarah bartao karta hai: `try…catch` use pakar leta hai. `await` ke baghair error `try` se bach nikalta hai. Promise chains ke saath `.catch()` lein. Jise koi na sambhale wo rejection **unhandled rejection** ban jata hai (browsers me warning, jadeed Node me crash).
</Ur>
</Tr>

```javascript
function fetchOrder(id) {
  return new Promise((resolve, reject) => {
    setTimeout(() => (id > 0 ? resolve({ id, total: 40 }) : reject(new Error("Order not found"))), 10);
  });
}

async function show(id) {
  try {
    const order = await fetchOrder(id);
    console.log("order", order.id, "total", order.total);
  } catch (error) {
    console.log("could not load order:", error.message);
  }
}
await show(7);
await show(-1);

async function forgotAwait() {
  try {
    return fetchOrder(-2);
  } catch {
    console.log("never printed");
  }
}
await forgotAwait().catch((e) => console.log("escaped the try/catch:", e.message));

fetchOrder(-3)
  .then((o) => console.log(o))
  .catch((e) => console.log(".catch got:", e.message));
```

```text output
order 7 total 40
could not load order: Order not found
escaped the try/catch: Order not found
.catch got: Order not found
```

<Happened>
<Tr>
<En>

- With `await` inside `try`, the rejection was caught just like a thrown error.
- `forgotAwait` returned the promise **without awaiting it**. The function left the `try` block before the promise failed, so its `catch` never ran; the error went to the caller instead. Writing `return await fetchOrder(-2)` would have caught it.
- `.catch()` at the end of a `.then()` chain handles any failure in the chain.
- Always handle rejections somewhere: an unhandled one can crash a Node server.

</En>
<Ur>

- `try` ke andar `await` ke saath rejection bilkul phenke gaye error ki tarah pakra gaya.
- `forgotAwait` ne promise ko **await kiye baghair** wapas kiya. Function promise fail hone se pehle `try` block se nikal gaya, isliye us ka `catch` kabhi nahi chala; error is ke bajaye call karne wale tak gaya. `return await fetchOrder(-2)` likhna use pakar leta.
- `.then()` chain ke aakhir me `.catch()` chain ki har nakami sambhalta hai.
- Rejections hamesha kahin na kahin sambhalein: unhandled rejection Node server crash kar sakta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Expected failures as values">

<Tr>
<En>
Not every failure needs an exception. For things that fail **often and normally** (validating a form field, parsing optional input), returning a **result object** like `{ ok, value, error }` makes the caller handle both cases explicitly. For several async tasks where some may fail, `Promise.allSettled` gives you every result.
</En>
<Ur>
Har nakami ko exception ki zaroorat nahi. Jo cheezen **aksar aur aam taur par** fail hoti hain (form field validate karna, ikhtiyari input parse karna), un ke liye `{ ok, value, error }` jaisa **result object** wapas karna call karne wale ko dono soorten wazeh taur par sambhalne par majboor karta hai. Kai async kaamon ke liye jin me se kuch fail ho sakte hain, `Promise.allSettled` har nateeja deta hai.
</Ur>
</Tr>

```javascript
function parseAge(text) {
  const n = Number(text);
  if (!Number.isInteger(n) || n < 0 || n > 130) return { ok: false, error: "Age must be 0–130" };
  return { ok: true, value: n };
}

for (const t of ["34", "abc", "200"]) {
  const result = parseAge(t);
  console.log(t, result.ok ? "→ age " + result.value : "→ " + result.error);
}

const results = await Promise.allSettled([
  Promise.resolve(1),
  Promise.reject(new Error("timeout")),
  Promise.resolve(3),
]);
console.log(results.map((r) => (r.status === "fulfilled" ? r.value : "failed: " + r.reason.message)));
```

```text output
34 → age 34
abc → Age must be 0–130
200 → Age must be 0–130
[ 1, 'failed: timeout', 3 ]
```

<Happened>
<Tr>
<En>

- `parseAge` never throws; the caller checks `result.ok`. It's clear from the return value that failure is possible.
- `Promise.allSettled` waited for all three promises and reported each one's outcome, so one failure didn't hide the other two results. (`Promise.all` would reject as soon as one fails.)
- Rule of thumb: **exceptions for exceptional or unexpected situations**, result values for routine "no" answers. Schema libraries like zod offer both (`parse` throws, `safeParse` returns a result).

</En>
<Ur>

- `parseAge` kabhi error nahi phenkta; call karne wala `result.ok` check karta hai. Wapas aane wali value se saaf hai ke nakami mumkin hai.
- `Promise.allSettled` ne teeno promises ka intezar kiya aur har ek ka nateeja bataya, isliye ek nakami ne baqi do nataij nahi chhupaye. (`Promise.all` ek ke fail hote hi reject ho jata.)
- Aam qaida: **ghair mamooli ya ghair mutawaqqa soorton ke liye exceptions**, roz ke "nahi" jawabon ke liye result values. zod jaisi schema libraries dono deti hain (`parse` error phenkta hai, `safeParse` result deta hai).

</Ur>
</Tr>
</Happened>

</Step>

<Compare>
<Bad title="Swallowing every error">

```javascript
  try {
    return order.items.reduce((sum, i) => sum + i.price, 0);

    return 0;
```

```javascript
  getTotal({ itemz: [] });
```

<Tr>
<En>

More mistakes to avoid:

- **Forgetting `await` inside `try`**, so async errors escape.
- **Catching too high or too low**: catching inside every tiny function adds noise; catching nowhere crashes the app. Catch where you can **do something useful**.
- **Using exceptions for normal control flow** (like "user not found" in a search). Return a result or `null`.
- **Losing the original error** when wrapping it. Pass `{ cause: error }`.
- **Unhandled promise rejections** from fire-and-forget calls. Add `.catch()`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`try` ke andar `await` bhoolna**, jis se async errors bach nikalte hain.
- **Bohot upar ya bohot neeche pakarna**: har chhote function me pakarna shor barhata hai; kahin na pakarna app crash karta hai. Wahan pakrein jahan **kuch kaam ka kar sakein**.
- **Aam control flow ke liye exceptions istemal karna** (jaise search me "user not found"). Result ya `null` wapas karein.
- **Lapette waqt asal error kho dena.** `{ cause: error }` dein.
- **"Chala kar bhool jao" calls se unhandled promise rejections.** `.catch()` jorein.

</Ur>
</Tr>

Write `checkout(cart)` that throws a `ValidationError` (with a `field`) if the cart is empty or any quantity isn't a positive integer, and otherwise returns the total in cents. Then write `submit(cart)` that calls it and returns `{ ok: true, total }` or `{ ok: false, message }` for validation errors, rethrowing anything else.
</En>
<Ur>
`checkout(cart)` likhein jo cart khaali ho ya koi quantity musbat poora number na ho to `ValidationError` (`field` ke saath) phenke, warna total cents me wapas kare. Phir `submit(cart)` likhein jo ise call kare aur validation errors ke liye `{ ok: true, total }` ya `{ ok: false, message }` wapas kare, baqi sab dobara phenke.
</Ur>

```javascript
class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

function checkout(cart) {
  if (cart.length === 0) throw new ValidationError("cart", "Your cart is empty");
  for (const item of cart) {
    if (!Number.isInteger(item.qty) || item.qty < 1) {
      throw new ValidationError("qty", `Quantity for ${item.name} must be at least 1`);
    }
  }
  return cart.reduce((sum, item) => sum + item.priceCents * item.qty, 0);
}

function submit(cart) {
  try {
    return { ok: true, total: checkout(cart) };
  } catch (error) {
    if (error instanceof ValidationError) return { ok: false, message: error.message };
    throw error;
  }
}

console.log(submit([{ name: "Mug", priceCents: 899, qty: 2 }]));
console.log(submit([]));
console.log(submit([{ name: "Lamp", priceCents: 2999, qty: 0 }]));
```

```text output

{ ok: false, message: 'Your cart is empty' }
{ ok: false, message: 'Quantity for Lamp must be at least 1' }
```

<Challenge title="Retry with finally">

<Tr>
<En>
Write `withRetry(task, attempts)` that calls an async `task` up to `attempts` times, returning the first success. If all attempts fail, throw an `Error("All attempts failed")` with the last error as `cause`. Log "attempt N finished" in a `finally` each time. Test with a task that fails twice, then succeeds.
</En>
<Ur>
`withRetry(task, attempts)` likhein jo async `task` ko zyada se zyada `attempts` dafa call kare, aur pehli kamyabi wapas kare. Agar sab koshishen fail hon to aakhri error ko `cause` ki tarah rakh kar `Error("All attempts failed")` phenke. Har dafa `finally` me "attempt N finished" log karein. Aise task se test karein jo do dafa fail ho, phir kamyab ho.
</Ur>

<Solution>

```javascript
async function withRetry(task, attempts) {
  let lastError;
  for (let i = 1; i <= attempts; i++) {
    try {
      return await task(i);
    } catch (error) {
      lastError = error;
    } finally {
      console.log("attempt", i, "finished");
    }
  }
  throw new Error("All attempts failed", { cause: lastError });
}

const flaky = async (n) => {
  if (n < 3) throw new Error("network error " + n);
  return "data on attempt " + n;
};

console.log(await withRetry(flaky, 5));
try {
  await withRetry(flaky, 2);
} catch (error) {
  console.log(error.message, "| cause:", error.cause.message);
}
```

```text output
attempt 1 finished
attempt 2 finished
attempt 3 finished
data on attempt 3
attempt 1 finished
attempt 2 finished
All attempts failed | cause: network error 2
```

<En>
`return await` matters here: without `await`, the `try` would finish before the task fails and the retry wouldn't catch anything. `finally` runs even on the successful `return`.
</En>
<Ur>
Yahan `return await` ahem hai: `await` ke baghair `try` task ke fail hone se pehle khatam ho jata aur retry kuch na pakarta. `finally` kamyab `return` par bhi chalta hai.

<DeepDive title="More about errors">

**Global safety nets.** Browsers: `window.addEventListener("error", …)` and `"unhandledrejection"`. Node: `process.on("uncaughtException")` and `process.on("unhandledRejection")`. Use them to **log and exit cleanly**, not to keep a broken process running.

**React error boundaries** catch rendering errors in a part of the UI and show a fallback; Next.js uses `error.tsx` files for the same idea per route.

**`AggregateError`** holds several errors at once (thrown by `Promise.any` when all promises reject).

**`Error.captureStackTrace`** (V8) and `error.stack` formatting differ between engines; don't parse stack strings for logic.

**`catch` without a binding.** `catch { … }` is fine when you don't need the error object, but only when ignoring it is truly correct.

**Assertions.** `console.assert` only logs. For "this must never happen" checks, `throw new Error("Invariant failed: …")` or Node's `assert` module.

**Typed errors in TypeScript.** `catch (error)` gives `unknown`; narrow with `if (error instanceof Error)` before using `error.message`.

**Error codes.** Many APIs add a stable `code` property (`"ERR_MODULE_NOT_FOUND"`, `"ENOENT"`). Check codes rather than message text, which can change.

</DeepDive>

<DeepDive title="Real world: the silent zero">

An e-commerce analytics job summed daily revenue:

```text
function dayRevenue(orders) {
  try {
    return orders.reduce((sum, o) => sum + o.payment.amount, 0);
  } catch {
    return 0;   // "just in case"
  }
}
```

A payment-provider change introduced orders with `payment: null` (paid later by invoice). The `reduce` threw a `TypeError` on the first such order, the `catch` returned **0**, and the dashboard showed $0 revenue for those days. Finance noticed three weeks later, after decisions had been made based on "falling sales".

The fix:

1. Remove the blanket `catch`. Let unexpected errors crash the job and **alert** someone.
2. Handle the known case explicitly: `o.payment?.amount ?? 0` for orders paid later, plus a separate "invoiced" total.
3. Validate input with a schema, so new shapes fail loudly at the boundary.
4. Add a sanity check: if revenue is 0 on a day with orders, raise an alert.

Lesson: a `catch` that returns a "safe" default isn't safe if the default is **wrong**. Prefer loud failures for unexpected problems.

</DeepDive>

<DeepDive title="Security lens">

- **Don't leak internals.** Stack traces, SQL errors, file paths and library versions in responses help attackers. Send a generic message plus an error id; keep details in server logs.
- **Fail closed.** If an authorisation check throws, the request must be **denied**, not allowed by a `catch` that "continues".
- **Don't log secrets** inside error messages (tokens, passwords, full card numbers). Redact before logging.
- **Timing and enumeration.** "User not found" vs "Wrong password" lets attackers find valid accounts; use one message ("Invalid email or password").
- **Resource cleanup** in `finally` prevents leaks (open connections, locks) that attackers could exploit to exhaust your server.
- **Crash, don't limp.** After an uncaught exception, a Node process may be in an unknown state; log, exit, and let the process manager restart it.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between throw and return for signalling failure?">
throw interrupts the normal flow and unwinds the call stack until a catch handles it, so callers cannot ignore it accidentally. Returning a value such as null or a result object keeps normal flow and requires the caller to check it, which suits expected, routine failures.
</QA>

<QA q="When does finally run, and what is it used for?">
It runs after try and any catch, whether an error occurred or not and even if try or catch returned. It is used for cleanup such as closing connections, releasing locks or hiding loading indicators.
</QA>

<QA q="How do you handle errors with async/await?">
Wrap awaited calls in try/catch, because a rejected awaited promise throws at the await. Use return await inside try when returning a promise, add .catch to promise chains, and ensure no rejection is left unhandled.
</QA>

<QA q="Why create custom error classes?">
They carry extra context such as a field or status code, give clearer names in logs, and let handlers distinguish error kinds with instanceof to respond appropriately, for example mapping validation errors to 400 responses.
</QA>

<QA q="Why is an empty catch block dangerous?">
It swallows every error, including unexpected bugs, so the program continues with wrong or missing data and the root cause becomes very hard to find.
</QA>

</DeepDive>
