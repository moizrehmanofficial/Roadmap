<BigIdea>
<Tr>
<En>
**JavaScript** is a programming language: text instructions that a computer follows. The computer can't read the text directly, so a program called a **JavaScript engine** reads it and runs it. Every web **browser** has an engine built in (Chrome's is called **V8**), which is why JavaScript is the language of web pages: it can change what you see, react to clicks and talk to servers. **Node.js** takes the same V8 engine **out of the browser**, so the same language can run on your computer or a server, read files and power back ends. The language is the same in both places; what's different is the **extra tools** each one gives you (`document` in the browser, `process` and files in Node). Wherever it runs, the **console** is your window into the program: `console.log(…)` prints a value so you can see what your code is doing.
</En>
<Ur>
**JavaScript** ek programming language hai: text ki hidayat jin par computer amal karta hai. Computer text ko seedha nahi parh sakta, isliye ek program jise **JavaScript engine** kehte hain use parh kar chalata hai. Har web **browser** me engine bana hota hai (Chrome wale ka naam **V8** hai), isi liye JavaScript web pages ki language hai: ye jo nazar aata hai use badal sakti hai, clicks par jawab de sakti hai aur servers se baat kar sakti hai. **Node.js** wahi V8 engine **browser se bahar** le aata hai, taa ke wahi language aap ke computer ya server par chal sake, files parh sake aur back ends chala sake. Language dono jagah ek hi hai; farq un **izafi auzaar** ka hai jo har jagah milte hain (browser me `document`, Node me `process` aur files). Jahan bhi chale, **console** program ke andar jhaankne ki khirki hai: `console.log(…)` ek value print karta hai taa ke aap dekh sakein ke aap ka code kya kar raha hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of JavaScript as a **recipe written in English**, and the engine as a **cook who reads English**.

- The **browser** is a restaurant kitchen. The cook (V8) follows your recipe, and the kitchen has special equipment: the dining room you can rearrange (`document`, the page), a bell to call customers (`alert`), a phone to call suppliers (`fetch`).
- **Node.js** is the same cook moved into a **food factory**. Same language, same skills, but different equipment: storage rooms (files), loading docks (servers and networks), and the factory's own control panel (`process`). There's no dining room, so there's no `document`.
- The **console** is the cook's **notepad**. Whenever you write `console.log(…)`, the cook writes a note you can read later, so you know exactly what happened and in what order.

</En>
<Ur>

JavaScript ko **English me likhi recipe** samjhein, aur engine ko **English parhne wala cook**.

- **Browser** restaurant ki kitchen hai. Cook (V8) aap ki recipe par chalta hai, aur kitchen me khaas saaman hai: dining hall jise aap dobara saja sakte hain (`document`, page), customers ko bulane ki ghanti (`alert`), suppliers ko call karne ka phone (`fetch`).
- **Node.js** wahi cook hai jo **khane ki factory** me chala gaya. Wahi language, wahi hunar, magar mukhtalif saaman: store rooms (files), loading docks (servers aur networks), aur factory ka apna control panel (`process`). Dining hall nahi, isliye `document` nahi.
- **Console** cook ki **notepad** hai. Jab bhi aap `console.log(…)` likhte hain, cook ek note likh deta hai jo aap baad me parh sakte hain, taa ke bilkul pata ho ke kya hua aur kis tarteeb se.

</Ur>
</Tr>

<Step title="Your first line of JavaScript">

<Tr>
<En>
`console.log(…)` prints whatever you put inside the brackets. Text goes in quotes; numbers and sums don't. You can print several things at once by separating them with commas.
</En>
<Ur>
`console.log(…)` brackets ke andar jo bhi rakhein print kar deta hai. Text quotes me jata hai; numbers aur jor nahi. Commas se alag kar ke ek saath kai cheezen print kar sakte hain.
</Ur>
</Tr>

```javascript
console.log("Hello, world!");
console.log(2 + 3);
console.log("2 + 3");
console.log("Total:", 19.99, "items:", 3);
```

```text output
Hello, world!
5
2 + 3
Total: 19.99 items: 3
```

<Happened>
<Tr>
<En>

- `2 + 3` without quotes is **math**, so the engine calculated `5`.
- `"2 + 3"` in quotes is **text** (a string), so it was printed exactly as written.
- With commas, `console.log` prints each value with a **space** between them.
- Press **Run** above, then **Edit**, change a number and run again. You can't break anything.

</En>
<Ur>

- Baghair quotes ke `2 + 3` **hisaab** hai, isliye engine ne `5` nikala.
- Quotes me `"2 + 3"` **text** (string) hai, isliye bilkul waise hi print hua jaise likha tha.
- Commas ke saath `console.log` har value ke darmiyan **space** de kar print karta hai.
- Upar **Run** dabayen, phir **Edit**, koi number badal kar dobara chalayen. Aap kuch nahi tor sakte.

</Ur>
</Tr>
</Happened>

<Step title="Code runs from top to bottom">

<Tr>
<En>
The engine reads your program **one statement at a time, from the first line to the last**, like reading a recipe. A statement usually ends with a semicolon `;`. Anything after `//` on a line is a **comment**: a note for humans that the engine skips.
</En>
<Ur>
Engine aap ka program **ek waqt me ek statement, pehli line se aakhri tak** parhta hai, jaise recipe parhte hain. Statement aam taur par semicolon `;` par khatam hota hai. Line me `//` ke baad jo kuch ho wo **comment** hai: insaanon ke liye note jise engine chhor deta hai.
</Ur>
</Tr>

```javascript
// Step 1: start the order
console.log("1. Take the order");

// Step 2: cook
console.log("2. Cook the food"); // this comment is ignored too

/* A comment can also
   span several lines */
console.log("3. Serve");
```

```text output
1. Take the order
2. Cook the food
3. Serve
```

<Happened>
<Tr>
<En>

- The messages appeared in the **same order** as the lines. Later you'll meet things that change the order (conditions, loops, functions, waiting for a server), but the default is always top to bottom.
- `//` comments last until the end of the line; `/* … */` comments can cover many lines.
- Use comments to explain **why** you did something, not what each line obviously does.

</En>
<Ur>

- Paighaam lines ki **usi tarteeb** me aaye. Baad me aap aisi cheezen dekhenge jo tarteeb badalti hain (sharten, loops, functions, server ka intezar), magar default hamesha upar se neeche hai.
- `//` comments line ke aakhir tak rehte hain; `/* … */` comments kai lines par phail sakte hain.
- Comments se ye samjhayen ke aap ne kuch **kyun** kiya, ye nahi ke har line wazeh taur par kya karti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The console toolkit">

<Tr>
<En>
`console` has more than `log`. `warn` and `error` show messages as warnings and errors (yellow and red in a browser). `info` is like `log`. `table` shows a list of objects as a neat table.
</En>
<Ur>
`console` me `log` se zyada hai. `warn` aur `error` paighaam ko warning aur error ki shakal me dikhate hain (browser me peela aur laal). `info` `log` jaisa hai. `table` objects ki list ko saaf table ki shakal me dikhata hai.
</Ur>
</Tr>

```javascript
console.info("Loading products…");
console.warn("Stock is low for: Desk lamp");
console.error("Could not load prices");

const products = [
  { name: "Notebook", price: 5, inStock: true },
  { name: "Desk lamp", price: 30, inStock: false },
];
console.table(products);
```

```text output
Loading products…
Stock is low for: Desk lamp
Could not load prices
┌─────────┬─────────────┬───────┬─────────┐
│ (index) │ name        │ price │ inStock │
├─────────┼─────────────┼───────┼─────────┤
│ 0       │ 'Notebook'  │ 5     │ true    │
│ 1       │ 'Desk lamp' │ 30    │ false   │
└─────────┴─────────────┴───────┴─────────┘
```

<Happened>
<Tr>
<En>

- In a terminal all three messages look plain; in a browser's console, `warn` gets a **yellow** background and `error` a **red** one, and you can filter by level. Press Run here to see the colors.
- `console.table` turned the list into rows and columns. The `(index)` column is each item's position, starting at 0. Text values are shown in quotes so you can tell `'5'` (text) from `5` (number).
- Use `error` for real problems so they stand out; many monitoring tools collect `console.error` messages from servers.

</En>
<Ur>

- Terminal me teeno paighaam saade lagte hain; browser ke console me `warn` ka background **peela** aur `error` ka **laal** hota hai, aur aap level ke hisaab se filter kar sakte hain. Rang dekhne ke liye yahan Run dabayen.
- `console.table` ne list ko rows aur columns me badal diya. `(index)` column har item ki jagah hai, 0 se shuru. Text values quotes me dikhti hain taa ke `'5'` (text) aur `5` (number) me farq ho sake.
- Asli masail ke liye `error` istemal karein taa ke wo numayan hon; bohot se monitoring tools servers se `console.error` paighaam ikatthe karte hain.

</Ur>
</Tr>
</Happened>

<Step title="group, count and assert">

<Tr>
<En>
Three more helpers keep long output readable: `group` indents related lines, `count` counts how often a line runs, and `assert` prints an error **only when** a check is false.
</En>
<Ur>
Teen aur madadgar lambe output ko parhne layaq rakhte hain: `group` mutaliqa lines ko andar ki taraf karta hai, `count` ginta hai ke ek line kitni dafa chali, aur `assert` error **sirf tab** print karta hai jab check ghalat ho.
</Ur>
</Tr>

```javascript
console.group("Order #1042");
console.log("Notebook x 2");
console.log("Desk lamp x 1");
console.groupEnd();
console.log("Done");

console.count("click");
console.count("click");
console.count("click");

const total = 40;
console.assert(total === 40, "Total should be 40");
console.assert(total > 100, "Total is below 100:", total);
```

```text output
Order #1042
  Notebook x 2
  Desk lamp x 1
Done
click: 1
click: 2
click: 3
Assertion failed: Total is below 100: 40
```

<Happened>
<Tr>
<En>

- Lines between `group` and `groupEnd` were **indented** under the title. Groups can be nested.
- `count("click")` keeps its own counter per label, handy for "how many times did this run?".
- The first `assert` was **true**, so it printed nothing. The second was false, so it printed `Assertion failed:` and the message. Unlike a real error, `assert` doesn't stop the program.

</En>
<Ur>

- `group` aur `groupEnd` ke darmiyan ki lines title ke neeche **andar ki taraf** hui. Groups ek doosre ke andar bhi ho sakte hain.
- `count("click")` har label ka apna counter rakhta hai, "ye kitni dafa chala?" ke liye kaam ka.
- Pehla `assert` **sahi** tha, isliye kuch print nahi hua. Doosra ghalat tha, isliye `Assertion failed:` aur paighaam print hua. Asli error ke baraks `assert` program nahi rokta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Running JavaScript in a web page">

<Tr>
<En>
In a page, JavaScript goes in a `<script>` tag, either written inline or loaded from a file with `src`. Browser JavaScript can **read and change the page** through `document`. The example below changes a heading and logs a message.
</En>
<Ur>
Page me JavaScript `<script>` tag me jati hai, ya to wahin likhi hui ya `src` ke saath file se load hui. Browser ki JavaScript `document` ke zariye **page parh aur badal sakti hai**. Neeche ka namoona heading badalta hai aur ek paighaam log karta hai.
</Ur>
</Tr>

```html preview-js h=120
<h1 id="title">Loading…</h1>
<p>Open DevTools (F12) → Console to see the log message.</p>

<script>
  const title = document.querySelector("#title");
  title.textContent = "Welcome to Acme Store";
  console.log("The heading was changed by JavaScript");
</script>
```

```html
<!-- In a real project, keep JavaScript in its own file -->
<head>
  <script src="app.js" defer></script>
</head>
```

<Happened>
<Tr>
<En>

- The heading in the result says "Welcome to Acme Store", not "Loading…": JavaScript ran after the `<h1>` existed and changed its text.
- `console.log` in a page doesn't show on the page itself. It goes to the **DevTools console** (F12). That's where you'll see your logs and any errors.
- `defer` tells the browser: download `app.js` while reading the HTML, but **run it after the page is built**. Without it, a script in `<head>` would run before the `<h1>` exists and `document.querySelector("#title")` would find nothing.

</En>
<Ur>

- Nateeje me heading "Welcome to Acme Store" kehti hai, "Loading…" nahi: JavaScript `<h1>` ke banne ke baad chali aur us ka text badal diya.
- Page me `console.log` khud page par nazar nahi aata. Ye **DevTools console** (F12) me jata hai. Wahin aap ko apne logs aur errors nazar aayenge.
- `defer` browser ko kehta hai: HTML parhte hue `app.js` download karo, magar **page banne ke baad chalao**. Is ke baghair `<head>` ka script `<h1>` banne se pehle chal jata aur `document.querySelector("#title")` ko kuch na milta.

</Ur>
</Tr>
</Happened>

<Step title="Running JavaScript with Node.js">

<Tr>
<En>
Node.js runs a `.js` file from the terminal. Install it from nodejs.org (choose the **LTS** version), then check it works with `node --version`. Save code in a file and run `node` with the file name.
</En>
<Ur>
Node.js terminal se `.js` file chalata hai. nodejs.org se install karein (**LTS** version chunein), phir `node --version` se check karein ke chal raha hai. Code file me save karein aur file ke naam ke saath `node` chalayen.
</Ur>
</Tr>

```bash
cat > hello.js <<'EOF'
const name = "Alex";
console.log("Hello, " + name + "!");
console.log("2 + 3 =", 2 + 3);
EOF
node hello.js
```

```text output
Hello, Alex!
2 + 3 = 5
```

<Happened>
<Tr>
<En>

- `cat > hello.js <<'EOF' … EOF` just created the file (you can also make it in VS Code). `node hello.js` ran it top to bottom and printed to the **terminal**.
- When the last line finishes, the program **ends** and you get your terminal prompt back. A server program instead keeps running, waiting for requests, until you press **Ctrl+C**.
- Type `node` with no file to open the **REPL**: type `2 + 3`, press Enter, see `5`. Type `.exit` (or press Ctrl+C twice) to leave.

</En>
<Ur>

- `cat > hello.js <<'EOF' … EOF` ne bas file banayi (aap VS Code me bhi bana sakte hain). `node hello.js` ne use upar se neeche chalaya aur **terminal** par print kiya.
- Aakhri line khatam hote hi program **khatam** hota hai aur terminal prompt wapas mil jata hai. Server program is ke bajaye chalta rehta hai, requests ka intezar karta hai, jab tak aap **Ctrl+C** na dabayen.
- **REPL** kholne ke liye baghair file ke `node` likhein: `2 + 3` likhein, Enter dabayen, `5` dekhein. Bahar nikalne ke liye `.exit` likhein (ya do dafa Ctrl+C).

</Ur>
</Tr>
</Happened>

<Step title="Same language, different tools">

<Tr>
<En>
The core language (numbers, text, `if`, functions, arrays…) works the same everywhere. The **extra objects** depend on where you are. `typeof` tells you whether something exists: `"undefined"` means it's not there.
</En>
<Ur>
Bunyadi language (numbers, text, `if`, functions, arrays…) har jagah ek jaisi chalti hai. **Izafi objects** is par munhasir hain ke aap kahan hain. `typeof` batata hai ke koi cheez maujood hai ya nahi: `"undefined"` ka matlab wo nahi hai.
</Ur>
</Tr>

```bash
node -e 'console.log(typeof document, typeof window, typeof process, typeof globalThis)'
```

```text output
undefined undefined object object
```

```text
The same line typed into a browser tab's console:

object object undefined object
```

<Happened>
<Tr>
<En>

| | Browser | Node.js |
| --- | --- | --- |
| `document` (the page) | yes | no |
| `window` (the browser tab) | yes | no |
| `process` (the running program) | no | yes |
| `globalThis` (the global object, everywhere) | yes | yes |

- That's why `document.querySelector(…)` in Node fails with `ReferenceError: document is not defined`, and `process.env` in a browser fails too.
- `globalThis` is the standard name that works in both. In a browser it **is** `window`.
- Frameworks like Next.js run some of your code in Node (the server) and some in the browser, so this difference matters a lot later.

</En>
<Ur>

| | Browser | Node.js |
| --- | --- | --- |
| `document` (page) | haan | nahi |
| `window` (browser tab) | haan | nahi |
| `process` (chalta program) | nahi | haan |
| `globalThis` (global object, har jagah) | haan | haan |

- Isi liye Node me `document.querySelector(…)` `ReferenceError: document is not defined` ke saath fail hota hai, aur browser me `process.env` bhi fail hota hai.
- `globalThis` mayari naam hai jo dono me chalta hai. Browser me ye `window` **hi** hai.
- Next.js jaise frameworks aap ka kuch code Node (server) me aur kuch browser me chalate hain, isliye ye farq aage bohot ahem hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="When an error stops the program">

<Tr>
<En>
If the engine hits something it can't do, such as using a name that doesn't exist, it throws an **error**: it prints what went wrong and **where**, and **stops**. Lines after the error don't run.
</En>
<Ur>
Agar engine ko koi aisi cheez mile jo wo nahi kar sakta, jaise aisa naam istemal karna jo maujood nahi, to wo **error** phenkta hai: batata hai kya ghalat hua aur **kahan**, aur **ruk jata hai**. Error ke baad ki lines nahi chaltin.
</Ur>
</Tr>

```bash
cat > order.js <<'EOF'
```

<Step title="What the engine does with your code">

<Tr>
<En>

You don't need this to write code, but it helps you understand speed and errors. When you run a file, the engine:

1. **Parses** the text: checks the grammar and builds a tree of your code. A grammar mistake (a **SyntaxError**, like a missing bracket) stops everything **before a single line runs**.
2. **Interprets** it: starts running quickly, statement by statement.
3. **Compiles hot code**: code that runs many times (for example, inside a loop) is turned into fast machine code while the program runs. This is called **JIT** (just-in-time) compilation, and it's why modern JavaScript is fast.

</En>
<Ur>

Code likhne ke liye iski zaroorat nahi, magar ye raftaar aur errors samajhne me madad karta hai. Jab aap file chalate hain, engine:

1. Text ko **parse** karta hai: grammar check karta aur aap ke code ka darakht banata hai. Grammar ki ghalti (**SyntaxError**, jaise ghayab bracket) **ek bhi line chalne se pehle** sab rok deti hai.
2. Use **interpret** karta hai: statement ba statement jaldi chalana shuru karta hai.
3. **Garm code compile** karta hai: jo code bohot dafa chale (maslan loop ke andar) program chalte hue tez machine code me badal diya jata hai. Ise **JIT** (just-in-time) compilation kehte hain, aur isi wajah se jadeed JavaScript tez hai.

</Ur>
</Tr>

<Tr>
<En>

More mistakes to avoid:

- **Looking for `console.log` output on the page.** It goes to the DevTools console (browser) or the terminal (Node).
- **Ignoring the red error** and guessing instead. Read the message and the line number first.
- **Typing `node` commands inside the Node REPL** (`> node app.js`). Leave the REPL with `.exit`, then run the command in the normal terminal.
- **Leaving dozens of debug logs** in finished code. Remove them, or use a proper logger on servers.

</En>

- **Page par `console.log` ka output dhoondna.** Ye DevTools console (browser) ya terminal (Node) me jata hai.
- **Laal error ko nazarandaz kar ke andaze lagana.** Pehle paighaam aur line number parhein.

<DeepDive title="More about engines and runtimes">

**ECMAScript.** The official name of the language standard is ECMAScript, updated every year (ES2015, ES2024…). Engines implement the standard; browsers and Node add APIs that aren't part of it (the DOM, `fetch` in older Node versions, `fs`).

**Other runtimes.** **Deno** and **Bun** are newer runtimes with built-in TypeScript, testing and package tools. Cloudflare Workers and Vercel's edge runtime run JavaScript close to users with a smaller, web-standard API.

**Script loading options.**

| Attribute | Downloads | Runs |
| --- | --- | --- |
| none | blocks HTML parsing | immediately |
| `defer` | in parallel | after parsing, in order |
| `async` | in parallel | as soon as downloaded, any order |
| `type="module"` | in parallel | deferred by default; enables `import`/`export` |

**The event loop.** JavaScript runs one piece of code at a time on one main thread. Waiting (timers, network, files) happens elsewhere; when it finishes, the callback is queued and runs when the thread is free. That's why a long loop freezes a web page. (The Event Loop lesson covers this.)

**Other console tools.** `console.time("label")` and `console.timeEnd("label")` measure how long code takes; `console.trace()` prints the current stack; `console.dir(obj, { depth: null })` in Node prints every level.

**DevTools beyond the console.** The **Sources** panel lets you set **breakpoints** to pause code and inspect values line by line; the `debugger;` statement does the same from code. The Debugging JavaScript lesson covers this.

</DeepDive>

<DeepDive title="Real world: the console.log that leaked tokens">

A developer debugging a login problem added `console.log("user", user)` to a Next.js page component. It worked: the object appeared in the browser console, the bug was found, and the change was pushed with the log still in it.

The `user` object included an access token and the user's email. Because the component also rendered on the server, the same log was written to the **server logs** for every page view, and those logs were shipped to a third-party logging service that the whole support team could read. Weeks later, an audit found thousands of valid tokens sitting in the logging service.

The fix:

1. Rotate the signing keys so every leaked token became invalid.
2. Delete the affected logs and limit who could read them.
3. Add an ESLint rule (`no-console`) that fails the build on stray `console.log`, allowing only `console.warn` and `console.error`.
4. Use a logger that **redacts** fields like `token`, `password` and `authorization` automatically.

Lesson: `console.log` is perfect for learning and debugging, but on servers logs are **stored, copied and shared**. Never log secrets, and remove debug logs before you ship.

</DeepDive>

<DeepDive title="Security lens">

- **Anything in the browser is visible.** Users can open DevTools, read your JavaScript, change variables and call your functions. Never trust checks that only happen in browser code; repeat them on the server.
- **Never put secrets in front-end JavaScript** (API keys with real permissions, passwords). They're readable by anyone.
- **Don't log sensitive data**, in the browser or on servers. Redact tokens, passwords and personal data.
- **"Self-XSS" scams**: attackers tell people to paste code into the console "to get free coins". That code runs with the victim's login. This is why Facebook and others show a big warning in their console.
- **Only run code you understand** with Node.js. A script has the same access to your files as you do.
- **Keep Node.js updated** to a supported LTS version; old versions stop receiving security fixes.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a JavaScript engine and a runtime?">
The engine, such as V8, parses and executes JavaScript code. A runtime, such as a browser or Node.js, embeds the engine and adds APIs and an event loop, for example the DOM and fetch in browsers or file system and process APIs in Node.js.
</QA>

<QA q="What is Node.js and why is it useful?">
Node.js is a JavaScript runtime built on V8 that runs outside the browser. It provides APIs for files, networking and processes, which lets developers build servers, command-line tools and build systems in the same language as the front end.
</QA>

<QA q="What is the difference between a SyntaxError and a ReferenceError in terms of when they occur?">
A SyntaxError is detected while the code is parsed, so none of that script runs. A ReferenceError happens at runtime when the code reaches a reference to an undeclared name, so earlier statements have already executed.
</QA>

<QA q="What do defer and async do on a script tag?">
Both download the script without blocking HTML parsing. A deferred script runs after the document has been parsed and deferred scripts keep their order. An async script runs as soon as it finishes downloading, in no guaranteed order.
</QA>

<QA q="What is JIT compilation?">
Just-in-time compilation is when the engine compiles frequently executed code into optimized machine code while the program is running, based on how the code is actually used, which makes hot code paths much faster than pure interpretation.
</QA>

</DeepDive>
