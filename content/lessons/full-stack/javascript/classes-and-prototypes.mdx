<BigIdea>
<Tr>
<En>
A **class** is a **blueprint** for making many objects of the same kind. You describe once what every product (or account, or shape) has, its **data** (`name`, `price`) and its **behaviour** (`label()`, `applyDiscount()`), and then create as many as you need with **`new`**. Under the hood, JavaScript classes are built on **prototypes**: every object has a hidden link to another object, its prototype, and when you read a property the object doesn't have, JavaScript **follows the link** to look for it there. That's how a thousand products share **one** copy of each method. Classes add useful extras on top: `#private` fields nobody outside can touch, getters and setters, `static` helpers, and inheritance with `extends` and `super`. They're a tool, not a requirement: plain objects and functions are often simpler.
</En>
<Ur>
**Class** ek hi qisam ke bohot se objects banane ka **naqsha** hai. Aap ek dafa bayan karte hain ke har product (ya account, ya shape) ke paas kya hai, us ka **data** (`name`, `price`) aur us ka **bartao** (`label()`, `applyDiscount()`), aur phir **`new`** se jitne chahiyen bana lete hain. Andar se JavaScript classes **prototypes** par bani hain: har object ka ek chhupa link doosre object se hota hai, us ka prototype, aur jab aap aisi property parhte hain jo object ke paas nahi, JavaScript wahan dhoondne ke liye **link ke peechhe jati** hai. Isi tarah hazaar products har method ki **ek** copy share karte hain. Classes upar se kaam ki cheezen jorti hain: `#private` fields jinhe bahar koi chhoo nahi sakta, getters aur setters, `static` helpers, aur `extends` aur `super` ke saath inheritance. Ye ek auzaar hain, zaroorat nahi: saade objects aur functions aksar zyada aasaan hote hain.
</Ur>
</Tr>

<Why>
<Tr>
<En>

- **Many objects, one definition**: products, users, orders, game characters. A class keeps their shape and behaviour consistent.

- **You'll read classes everywhere**: Node's `Error`, `Map`, `Date`, `EventEmitter`; NestJS controllers and services; Angular components; many SDKs.

<How>
<Tr>
<En>

1. Write `class Name { … }` with a `constructor` that stores the data on `this`.
2. Add methods for behaviour; use `#private` fields for data that must be protected.
3. Create objects with `new Name(…)`.
4. Use `extends` only for a true "is a" relationship, and call `super(…)` first in the child constructor.

</En>

3. `new Name(…)` se objects banayen.

## Picture it

<Tr>
<En>

A class is like a **cookie cutter** and a **recipe card**.

- The **cookie cutter** (`constructor`) gives every cookie its shape and fillings: this one is chocolate, that one is vanilla (`this.name`, `this.price`).
- The **recipe card for decorating** (the methods) isn't copied onto each cookie. It's pinned on the bakery wall (the **prototype**). Any cookie that needs decorating, the baker looks at the **same card**.
- If a cookie has its **own** special instruction stuck on it, that's used first; otherwise the baker checks the wall, then the head office's master cards (the prototype chain up to `Object.prototype`).
- A **child class** (`extends`) is a new cutter that starts from the parent cutter's shape (`super(…)`), then adds its own touches, and its wall card can say "do what the parent does, plus sprinkles" (`super.describe()`).

</En>
<Ur>

Class **cookie cutter** aur **recipe card** jaisi hai.

- **Cookie cutter** (`constructor`) har cookie ko us ki shakal aur bharai deta hai: ye chocolate, wo vanilla (`this.name`, `this.price`).
- **Sajane ka recipe card** (methods) har cookie par copy nahi hota. Ye bakery ki deewar par laga hai (**prototype**). Jis cookie ko bhi sajana ho, baker **wahi card** dekhta hai.
- Agar kisi cookie par us ki **apni** khaas hidayat chipki ho to wo pehle istemal hoti hai; warna baker deewar dekhta hai, phir head office ke master cards (`Object.prototype` tak prototype chain).
- **Child class** (`extends`) naya cutter hai jo parent cutter ki shakal se shuru hota hai (`super(…)`), phir apni cheezen jorta hai, aur us ka deewar wala card keh sakta hai "jo parent karta hai wo karo, saath sprinkles" (`super.describe()`).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Your first class">

<Tr>
<En>
`class Product { … }` defines the blueprint. `new Product("Mug", 899)` creates an object, runs the `constructor` with `this` pointing at the new object, and returns it. Methods defined in the class are available on every instance.
</En>
<Ur>
`class Product { … }` naqsha bayan karta hai. `new Product("Mug", 899)` object banata hai, `constructor` ko naye object ki taraf ishara karte `this` ke saath chalata hai, aur use wapas karta hai. Class me bane methods har instance par milte hain.
</Ur>
</Tr>

```javascript
class Product {
  constructor(name, priceCents) {
    this.name = name;
    this.priceCents = priceCents;
  }
  label() {
    return `${this.name}: $${(this.priceCents / 100).toFixed(2)}`;
  }
}

const mug = new Product("Mug", 899);
const lamp = new Product("Lamp", 2999);
console.log(mug.label(), "|", lamp.label());
console.log(mug, typeof Product, mug instanceof Product);
console.log(mug.label === lamp.label, Object.keys(mug));
```

```text output
Mug: $8.99 | Lamp: $29.99
Product { name: 'Mug', priceCents: 899 } function true
true [ 'name', 'priceCents' ]
```

<Happened>
<Tr>
<En>

- Two products, each with its own `name` and `priceCents`, each able to `label()` itself.
- `typeof Product` is `"function"`: a class is a special kind of function. `instanceof` checks whether `mug` was made from it.
- `mug.label === lamp.label` is **true**: both use **one shared** function. And `Object.keys(mug)` lists only the data, not `label`. So where does `label` live? On the prototype (next step).
- Class names use **PascalCase** (`Product`, `ShoppingCart`) by convention.

</En>
<Ur>

- Do products, har ek ka apna `name` aur `priceCents`, har ek apna `label()` kar sakta hai.
- `typeof Product` `"function"` hai: class khaas qisam ka function hai. `instanceof` check karta hai ke kya `mug` is se bana.
- `mug.label === lamp.label` **true** hai: dono **ek share hua** function istemal karte hain. Aur `Object.keys(mug)` sirf data dikhata hai, `label` nahi. To `label` kahan rehta hai? Prototype par (agla qadam).
- Riwaj ke mutabiq class ke naam **PascalCase** me hote hain (`Product`, `ShoppingCart`).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Prototypes: where shared methods live">

<Tr>
<En>
Every object has a hidden link to a **prototype** object. When you read `obj.x` and `obj` doesn't have its **own** `x`, JavaScript looks at the prototype, then the prototype's prototype, and so on: the **prototype chain**. `Object.create(proto)` makes an object with a chosen prototype; classes set it up for you.
</En>
<Ur>
Har object ka ek **prototype** object se chhupa link hota hai. Jab aap `obj.x` parhte hain aur `obj` ke paas **apna** `x` nahi, JavaScript prototype dekhti hai, phir prototype ka prototype, waghaira: ye **prototype chain** hai. `Object.create(proto)` chune hue prototype ke saath object banata hai; classes ye aap ke liye karti hain.
</Ur>
</Tr>

```javascript
const animal = {
  speak() {
    return this.name + " makes a sound";
  },
};
const dog = Object.create(animal);
dog.name = "Rex";
console.log(dog.speak(), Object.getPrototypeOf(dog) === animal);
console.log(Object.hasOwn(dog, "name"), Object.hasOwn(dog, "speak"), "speak" in dog);

dog.speak = function () {
  return this.name + " barks";
};
console.log(dog.speak(), animal.speak.call(dog));

class Product {
  constructor(name) {
    this.name = name;
  }
  label() {
    return this.name;
  }
}
const p = new Product("Mug");
console.log(Object.getPrototypeOf(p) === Product.prototype, Object.getOwnPropertyNames(Product.prototype));
console.log(Object.getPrototypeOf(Product.prototype) === Object.prototype, Object.getPrototypeOf(Object.prototype));
console.log(typeof p.toString, Object.hasOwn(p, "toString"));
```

```text output
Rex makes a sound true
true false true
Rex barks Rex makes a sound
true [ 'constructor', 'label' ]
true null
function false
```

<Happened>
<Tr>
<En>

- `dog` has no `speak` of its own (`hasOwn` is false), but `dog.speak()` worked: JavaScript found it on `animal`, its prototype. `this` was still `dog`, so it said "Rex".
- Adding `dog.speak` **shadowed** the prototype's version: own properties are found first.
- For classes, methods live on `Product.prototype` (`constructor` and `label`), and every instance links to it. The chain continues to `Object.prototype` and ends at `null`.
- That's why `p.toString` exists: it comes from `Object.prototype`. Arrays get `map` from `Array.prototype` the same way.

</En>
<Ur>

- `dog` ka apna `speak` nahi (`hasOwn` false hai), magar `dog.speak()` chal gaya: JavaScript ne use `animal`, us ke prototype, par dhoond liya. `this` ab bhi `dog` tha, isliye "Rex" kaha.
- `dog.speak` jorne se prototype wala version **chhup gaya**: apni properties pehle milti hain.
- Classes ke liye methods `Product.prototype` par rehte hain (`constructor` aur `label`), aur har instance us se jura hota hai. Chain `Object.prototype` tak jati hai aur `null` par khatam hoti hai.
- Isi liye `p.toString` maujood hai: ye `Object.prototype` se aata hai. Arrays ko `map` bhi isi tarah `Array.prototype` se milta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fields, private fields, getters, setters and static">

<Tr>
<En>
Classes can declare **fields** directly in the body. A **`#private`** field can only be read or written by code inside the class. **Getters** and **setters** look like properties but run code. **`static`** members belong to the class itself, useful for counters and factory functions.
</En>
<Ur>
Classes body me seedha **fields** declare kar sakti hain. **`#private`** field ko sirf class ke andar ka code parh ya likh sakta hai. **Getters** aur **setters** properties jaise lagte hain magar code chalate hain. **`static`** members khud class ke hote hain, counters aur factory functions ke liye kaam ke.
</Ur>
</Tr>

```javascript
class Account {
  #balanceCents = 0;
  static count = 0;
  owner;

  constructor(owner) {
    this.owner = owner;
    Account.count++;
  }

  deposit(cents) {
    if (!Number.isInteger(cents) || cents <= 0) {
      throw new Error("Deposit must be a positive whole number of cents");
    }
    this.#balanceCents += cents;
    return this;
  }

  get balance() {
    return this.#balanceCents / 100;
  }

  set nickname(value) {
    this.owner = value.trim();
  }

  static fromJSON(data) {
    return new Account(data.owner).deposit(data.balanceCents);
  }
}

const acc = new Account("Alex").deposit(2500).deposit(500);
console.log(acc.balance, acc.owner, Account.count);

acc.nickname = "  Alexandra ";
console.log(acc.owner, acc);

try {
  acc.deposit(-5);
} catch (error) {
  console.log(error.message);
}
console.log(acc.balanceCents, Object.keys(acc));

const restored = Account.fromJSON({ owner: "Sam", balanceCents: 1999 });
console.log(restored.balance, Account.count);
```

```text output
30 Alex 1
Alexandra Account { owner: 'Alexandra' }
Deposit must be a positive whole number of cents
undefined [ 'owner' ]
19.99 2
```

<Happened>
<Tr>
<En>

- `deposit` returns `this`, so calls can be **chained**: `.deposit(2500).deposit(500)`.
- `balance` is a **getter**: you read it like a property (`acc.balance`, no brackets) and it converts cents to dollars.
- `nickname` is a **setter**: assigning to it ran the code that trims the text.
- `#balanceCents` is **truly private**: it doesn't show in `console.log`, `Object.keys` or `acc.balanceCents`, and code outside the class gets a SyntaxError if it writes `acc.#balanceCents`. The only way to change the balance is `deposit`, which validates.
- `Account.count` and `Account.fromJSON` are **static**: called on the class, not on an instance. `fromJSON` is a common "factory" pattern.

</En>
<Ur>

- `deposit` `this` wapas karta hai, isliye calls **zanjeer** ki tarah jur sakti hain: `.deposit(2500).deposit(500)`.
- `balance` **getter** hai: aap ise property ki tarah parhte hain (`acc.balance`, brackets nahi) aur ye cents ko dollars me badalta hai.
- `nickname` **setter** hai: is ko value dene se text trim karne wala code chala.
- `#balanceCents` **sach me private** hai: ye `console.log`, `Object.keys` ya `acc.balanceCents` me nazar nahi aata, aur class ke bahar ka code `acc.#balanceCents` likhe to SyntaxError milta hai. Balance badalne ka wahid tareeqa `deposit` hai, jo validate karta hai.
- `Account.count` aur `Account.fromJSON` **static** hain: class par call hote hain, instance par nahi. `fromJSON` aam "factory" pattern hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Inheritance with extends and super">

<Tr>
<En>
`class Circle extends Shape` makes a **child** class that inherits everything from `Shape`. The child's constructor must call **`super(…)`** before using `this`. A child can **override** a method, and call the parent's version with `super.method()`.
</En>
<Ur>
`class Circle extends Shape` **child** class banata hai jo `Shape` se sab kuch virasat me leti hai. Child ke constructor ko `this` istemal karne se pehle **`super(…)`** call karna zaroori hai. Child kisi method ko **override** kar sakti hai, aur parent ka version `super.method()` se call kar sakti hai.
</Ur>
</Tr>

```javascript
class Shape {
  constructor(name) {
    this.name = name;
  }
  area() {
    return 0;
  }
  describe() {
    return `${this.name} with area ${this.area().toFixed(2)}`;
  }
}

class Circle extends Shape {
  constructor(radius) {
    super("circle");
    this.radius = radius;
  }
  area() {
    return Math.PI * this.radius ** 2;
  }
}

class Square extends Shape {
  constructor(side) {
    super("square");
    this.side = side;
  }
  area() {
    return this.side ** 2;
  }
  describe() {
    return super.describe() + " (all sides equal)";
  }
}

const shapes = [new Circle(1), new Square(3), new Shape("blob")];
for (const s of shapes) console.log(s.describe());
console.log(shapes[0] instanceof Circle, shapes[0] instanceof Shape, shapes[1] instanceof Circle);

try {
  class Broken extends Shape {
    constructor() {
      this.x = 1;
      super("x");
    }
  }
  new Broken();
} catch (error) {
  console.log(error.name + ": " + error.message);
}
```

```text output
circle with area 3.14
square with area 9.00 (all sides equal)
blob with area 0.00
true true false
ReferenceError: Must call super constructor in derived class before accessing 'this' or returning from derived constructor
```

<Happened>
<Tr>
<En>

- `describe` lives only on `Shape`, but it calls `this.area()`, and each object uses **its own** `area`. This is **polymorphism**: one loop, one method call, different behaviour per type.
- `Square.describe` extended the parent's text with `super.describe()`.
- A circle is an instance of `Circle` **and** `Shape` (the chain is circle → `Circle.prototype` → `Shape.prototype` → `Object.prototype`).
- Using `this` before `super(…)` threw a `ReferenceError`: the parent must create the object first.

</En>
<Ur>

- `describe` sirf `Shape` par hai, magar ye `this.area()` call karta hai, aur har object **apna** `area` istemal karta hai. Ye **polymorphism** hai: ek loop, ek method call, har qisam ka alag bartao.
- `Square.describe` ne `super.describe()` se parent ka text barhaya.
- Circle `Circle` **aur** `Shape` dono ka instance hai (chain hai circle → `Circle.prototype` → `Shape.prototype` → `Object.prototype`).
- `super(…)` se pehle `this` istemal karna `ReferenceError` phenk gaya: parent ko pehle object banana hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Custom error classes">

<Tr>
<En>
One of the most practical uses of `extends`: your own error types. They carry extra information (like which field failed) and let you tell errors apart with `instanceof`.
</En>
<Ur>
`extends` ke sab se amli istemal me se ek: apni error types. Ye izafi maloomat saath le jati hain (jaise kaun si field fail hui) aur `instanceof` se errors me farq karne deti hain.
</Ur>
</Tr>

```javascript
class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

try {
  throw new ValidationError("email", "Email is required");
} catch (error) {
  console.log(error instanceof ValidationError, error instanceof Error, error.name, error.field, error.message);
}
```

```text output
true true ValidationError email Email is required
```

<Happened>
<Tr>
<En>

- `super(message)` let `Error` set up the message and the stack trace.
- Setting `this.name` makes logs show "ValidationError" instead of "Error".
- In a `catch`, `error instanceof ValidationError` lets you show a field message to the user, while other errors get a generic message. The Error Handling lesson builds on this.

</En>
<Ur>

- `super(message)` ne `Error` ko message aur stack trace tayyar karne diya.
- `this.name` set karne se logs "Error" ke bajaye "ValidationError" dikhate hain.
- `catch` me `error instanceof ValidationError` aap ko user ko field ka paighaam dikhane deta hai, jabke doosre errors ko aam paighaam milta hai. Error Handling lesson is par aage banta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The older style: constructor functions">

<Tr>
<En>
Before `class` (added in 2015), people wrote **constructor functions** and put methods on `.prototype` by hand. Classes do the same thing with nicer syntax and a few safety rules. You'll still see the old style in older code and libraries.
</En>
<Ur>
`class` (2015 me aaya) se pehle log **constructor functions** likhte the aur methods haath se `.prototype` par rakhte the. Classes behtar syntax aur chand hifazati qawaid ke saath yahi karti hain. Purane code aur libraries me aap ko ab bhi purana andaaz milega.
</Ur>
</Tr>

```javascript
function ProductOld(name) {
  this.name = name;
}
ProductOld.prototype.label = function () {
  return "old-style " + this.name;
};

const o = new ProductOld("Mug");
console.log(o.label(), o instanceof ProductOld);

class P {}
console.log(typeof P);
try {
  P();
} catch (error) {
  console.log(error.name + ": " + error.message);
}
```

```text output
old-style Mug true
function
TypeError: Class constructor P cannot be invoked without 'new'
```

<Happened>
<Tr>
<En>

- The old version works exactly like a class: data set in the function, shared methods on the prototype, `instanceof` works.
- One safety difference: calling a class **without `new`** throws. Calling an old constructor function without `new` silently ran it with the wrong `this`, a common bug.
- Classes are also always in strict mode, and their methods aren't enumerable (they don't show up in `for…in`).

</En>
<Ur>

- Purana version bilkul class ki tarah kaam karta hai: data function me set, share hue methods prototype par, `instanceof` chalta hai.
- Hifazat ka ek farq: class ko **baghair `new`** call karna error phenkta hai. Purane constructor function ko baghair `new` call karna khamoshi se ghalat `this` ke saath chalta tha, ek aam bug.
- Classes hamesha strict mode me bhi hoti hain, aur un ke methods enumerable nahi hote (`for…in` me nazar nahi aate).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Composition: an alternative to deep inheritance">

<Tr>
<En>
Inheritance works for clear "is a" relationships, but deep hierarchies get rigid: what if a duck needs to fly **and** swim? **Composition** builds objects from small abilities instead. **Mixins** are functions that add methods to a class; **factory functions with closures** give privacy without classes at all.
</En>
<Ur>
Inheritance wazeh "ye ek … hai" rishton ke liye chalti hai, magar gehri hierarchies sakht ho jati hain: agar batakh ko urna **aur** tairna dono chahiye to? **Composition** is ke bajaye chhoti salahiyaton se objects banata hai. **Mixins** wo functions hain jo class me methods jorte hain; **closures wale factory functions** classes ke baghair hi privacy dete hain.
</Ur>
</Tr>

```javascript
const canFly = (Base) =>
  class extends Base {
    fly() {
      return `${this.name} flies`;
    }
  };
const canSwim = (Base) =>
  class extends Base {
    swim() {
      return `${this.name} swims`;
    }
  };

class Animal {
  constructor(name) {
    this.name = name;
  }
}
class Duck extends canSwim(canFly(Animal)) {}

const d = new Duck("Daffy");
console.log(d.fly(), "|", d.swim(), "|", d instanceof Animal);

function createCounter() {
  let count = 0;
  return {
    increment: () => ++count,
    get value() {
      return count;
    },
  };
}
const c = createCounter();
c.increment();
c.increment();
console.log(c.value, c.count);
```

```text output
Daffy flies | Daffy swims | true
2 undefined
```

<Happened>
<Tr>
<En>

- `canFly` and `canSwim` each take a class and return a new class with one extra ability. `Duck` combined both without a "FlyingSwimmingAnimal" base class.
- `createCounter` keeps `count` in a **closure**: only `increment` and `value` can reach it, so `c.count` is `undefined`. This is private state without `class` or `#`.
- Rule of thumb: prefer **shallow** inheritance (one or two levels) and composition for mixing abilities. React moved from class components to function components and hooks for similar reasons.

</En>
<Ur>

- `canFly` aur `canSwim` har ek class le kar ek izafi salahiyat wali nayi class wapas karte hain. `Duck` ne "FlyingSwimmingAnimal" base class ke baghair dono mila liye.
- `createCounter` `count` ko **closure** me rakhta hai: sirf `increment` aur `value` us tak pohanch sakte hain, isliye `c.count` `undefined` hai. Ye `class` ya `#` ke baghair private state hai.
- Aam qaida: **kam gehri** inheritance (ek ya do levels) aur salahiyaten milane ke liye composition ko tarjeeh dein. React isi jaisi wajahon se class components se function components aur hooks par aaya.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

<Compare>
<Bad title="Forgetting this in the constructor">


</Bad>


</Good>
</Compare>

<Compare>
<Bad title="Defining methods inside the constructor">

```javascript
class Item {
  constructor(name) {

      return this.name;
    };
  }

console.log(new Item("a").label === new Item("b").label);
```

```text output
false
```

</Bad>
<Good title="Methods in the class body are shared">

```javascript
class Item {
  constructor(name) {
    this.name = name;
  }
  label() {
    return this.name;
  }
}
console.log(new Item("a").label === new Item("b").label);
```

```text output
true
```

</Good>
</Compare>

<Compare>
<Bad title="Public field that anyone can break">

```javascript
class Stock {
  qty = 0;
}
const s = new Stock();
s.qty = -50;
console.log(s.qty);
```

```text output
-50
```

</Bad>
<Good title="Private field with a validating method">

```javascript
class Stock {
  #qty = 0;
  add(n) {
    if (!Number.isInteger(n) || this.#qty + n < 0) throw new Error("Invalid quantity");
    this.#qty += n;
  }
  get qty() {
    return this.#qty;
  }
}
const s = new Stock();
s.add(5);
try {
  s.add(-50);
} catch (error) {
  console.log(error.message, s.qty);
}
```

```text output
Invalid quantity 5
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting `new`** (classes throw; old constructor functions silently misbehave).
- **Passing a method as a callback** and losing `this` (The this Keyword lesson): use an arrow wrapper or an arrow class field.
- **Deep inheritance chains** (`Animal → Mammal → Dog → ServiceDog → …`). Prefer composition.
- **Using a class where a plain object would do**: data from an API doesn't need a class.
- **Changing built-in prototypes** (`Array.prototype.last = …`). It can break other code and future JavaScript versions.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`new` bhoolna** (classes error phenkti hain; purane constructor functions khamoshi se ghalat chalte hain).
- **Method ko callback ki tarah bhej kar `this` khona** (The this Keyword lesson): arrow wrapper ya arrow class field lein.
- **Gehri inheritance zanjeeren** (`Animal → Mammal → Dog → ServiceDog → …`). Composition ko tarjeeh dein.
- **Jahan saada object kaafi ho wahan class lagana**: API ke data ko class ki zaroorat nahi.
- **Bane banaye prototypes badalna** (`Array.prototype.last = …`). Ye doosra code aur aane wale JavaScript versions tor sakta hai.

</Ur>
</Tr>

```javascript
class Cart {
  #items = [];

  add(name, priceCents, qty = 1) {
    if (!Number.isInteger(qty) || qty < 1) throw new Error("Quantity must be at least 1");
    this.#items.push({ name, priceCents, qty });
    return this;
  }

  remove(name) {
    this.#items = this.#items.filter((item) => item.name !== name);
    return this;
  }

  get total() {
    return this.#items.reduce((sum, item) => sum + item.priceCents * item.qty, 0);
  }

  get count() {
    return this.#items.reduce((sum, item) => sum + item.qty, 0);
  }
}

```

<DeepDive title="More about classes">

**What `new` does, step by step.** Create an empty object; set its prototype to `Class.prototype`; run the constructor with `this` bound to it; return the object (unless the constructor returns another object).

**Private methods and static blocks.** `#validate() {}` makes a private method; `static { … }` runs once when the class is defined (for complex static setup). `#field in obj` checks whether an object has a private field (a reliable brand check).

**Accessors on the prototype.** Getters/setters defined in the class body live on the prototype, like methods; fields live on each instance.

**Class fields and `this`.** Field initialisers run before the constructor body (right after `super()` in subclasses), with `this` as the instance; that's why arrow-function fields keep `this`.

**Extending built-ins.** `class Stack extends Array` works, but methods like `map` return instances of your subclass via `Symbol.species`, which can surprise you. Prefer wrapping (`#items = []`) over extending built-ins.

**`Symbol.toPrimitive`, `toString`, `toJSON`** let a class control how it converts to numbers, strings and JSON.

**TypeScript** adds `public`/`private`/`protected` modifiers (compile-time only), `abstract` classes, `implements` for interfaces, and parameter properties (`constructor(private name: string)`).

</DeepDive>

<DeepDive title="Real world: the inheritance tree nobody could change">

A company's notification system started with `class Notification` and `class EmailNotification extends Notification`. Then came `SmsNotification`, `UrgentEmailNotification`, `ScheduledUrgentEmailNotification`, `ScheduledSmsNotification` and, eventually, `ScheduledUrgentEmailWithAttachmentNotification`: fourteen classes, five levels deep.

Every new feature (say, "quiet hours") had to be added to several branches. A bug fix in `ScheduledNotification` broke `UrgentEmailNotification`, which overrode one of its methods in a way nobody remembered. New engineers needed a diagram just to add a field.

The team rewrote it with **composition**:

1. One `Notification` object with plain data: `channel`, `priority`, `sendAt`, `attachments`.
2. Small, independent functions (`applyQuietHours`, `addUnsubscribeLink`, `renderEmail`, `renderSms`), each tested alone.
3. A `send` pipeline that runs the steps relevant to each notification.

Adding "quiet hours" became one function plus one line in the pipeline. The class hierarchy disappeared.

Lesson: inheritance models **"is a"**; most features are **"has a"** or **"can do"**. When combinations multiply, compose instead of inheriting.

</DeepDive>

<DeepDive title="Security lens">

- **Use `#private` fields for secrets and invariants** (tokens, balances, internal state). Unlike `_underscore` conventions, they can't be read or changed from outside.
- **Validate in constructors and setters** so an invalid object can never exist (negative balances, missing ids).
- **Prototype pollution**: if an attacker can set `obj.__proto__.isAdmin = true` (through an unsafe merge of user JSON), **every** object inherits `isAdmin`. Validate input, avoid naive deep merges, and check `Object.hasOwn(obj, "isAdmin")` instead of `obj.isAdmin` for security flags.
- **Don't modify built-in prototypes** in apps; it can be abused and breaks assumptions in other code.
- **Freezing** a class's prototype (`Object.freeze(Account.prototype)`) prevents other code from swapping its methods at runtime.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the prototype chain?">
Every object has an internal link to a prototype object. When a property is not found on an object, JavaScript looks it up on the prototype, then on the prototype's prototype, until it reaches null. Classes and constructor functions set instances' prototype to their prototype property, which is how methods are shared.
</QA>

<QA q="Are JavaScript classes the same as classes in Java or C#?">
No. They are syntax over prototype-based inheritance. Methods live on a prototype object, instances delegate to it at runtime, and classes are functions; there is no separate compile-time class model, although classes add rules such as requiring new and strict mode.
</QA>

<QA q="What is the difference between a private #field and a property named with an underscore?">
An underscore is only a naming convention; the property is fully accessible. A #private field is enforced by the language: it cannot be read, written or detected from outside the class body and does not appear in keys, JSON or logs.
</QA>

<QA q="Why must super be called before this in a derived class constructor?">
In a derived class, the parent constructor is responsible for creating and initialising the object. Until super runs, this is uninitialised, so accessing it throws a ReferenceError.
</QA>

<QA q="When would you prefer composition over inheritance?">
When objects need combinations of behaviours, when the relationship is has-a or can-do rather than is-a, or when a hierarchy would become deep and rigid. Composition with small functions, mixins or objects keeps features independent and easier to change.
</QA>

</DeepDive>
