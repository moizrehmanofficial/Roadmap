<BigIdea>
<Tr>
<En>
Some results aren't ready immediately: a server response, a file, a timer. JavaScript can't stop and wait (that would freeze everything), so it needs a way to say **"call me back when it's ready"**. The oldest way is a **callback**: you pass a function, and it's called later with the result. That works, but when one step depends on another, callbacks nest deeper and deeper, and error handling gets repeated everywhere. A **promise** is a better tool: an object that stands for a result **that will arrive later**. It starts **pending**, then becomes **fulfilled** (with a value) or **rejected** (with an error), exactly once. You attach `.then` for success and `.catch` for errors, and you can **chain** steps in a flat line. Helpers like `Promise.all` combine many promises. And `async`/`await`, which you've already used, is simply a nicer way to write promise code.
</En>
<Ur>
Kuch nataij foran tayyar nahi hote: server ka jawab, file, timer. JavaScript ruk kar intezar nahi kar sakti (is se sab kuch jama ho jata), isliye use **"tayyar ho to mujhe wapas bulana"** kehne ka tareeqa chahiye. Sab se purana tareeqa **callback** hai: aap ek function dete hain, aur ye baad me nateeje ke saath call hota hai. Ye chalta hai, magar jab ek qadam doosre par munhasir ho, callbacks gehre se gehre nest hote jate hain, aur error handling har jagah dohrani parti hai. **Promise** behtar auzaar hai: ek object jo us nateeje ki numaindagi karta hai **jo baad me aayega**. Ye **pending** se shuru hota hai, phir bilkul ek dafa **fulfilled** (value ke saath) ya **rejected** (error ke saath) hota hai. Kamyabi ke liye `.then` aur errors ke liye `.catch` lagayen, aur qadamon ko seedhi line me **chain** kar sakte hain. `Promise.all` jaise helpers bohot se promises jorte hain. Aur `async`/`await`, jo aap pehle istemal kar chuke hain, bas promise code likhne ka behtar tareeqa hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

```javascript
const brewCoffee = () =>
  new Promise((resolve, reject) => {
    setTimeout(() => resolve("coffee ready"), 20);
  });

brewCoffee()
  .then((drink) => drink.toUpperCase())
  .then((loud) => console.log(loud))
  .catch((error) => console.log("Problem:", error.message))
  .finally(() => console.log("counter cleaned"));
```

```text output
COFFEE READY
counter cleaned
```

| --- | --- |
| Callback `(err, value) => …` | Oldest async style (Node's error-first) |
| `new Promise((resolve, reject) => …)` | Wrap work that finishes later |
| `.then(fn)` / `.catch(fn)` / `.finally(fn)` | React to success / failure / either |
| `Promise.all([…])` | Wait for all; fail if any fails |
| `Promise.allSettled([…])` | Wait for all; report each result |
| `Promise.race([…])` | First one to settle wins (timeouts) |
| `Promise.any([…])` | First success wins |
| `async` / `await` | Write promise code like normal code |

</En>

<Why>
<Tr>
<En>

- **Everything slow in JavaScript is async**: `fetch`, database queries, file reads, timers. You need to receive their results.
- **Promises are the foundation**: `fetch` returns a promise, `async` functions return promises, every modern library uses them.
- **You'll still meet callbacks**: event listeners, array methods, older Node APIs and libraries.
- **Combining async work correctly** (parallel, timeouts, partial failures) is what separates fast, reliable apps from slow, fragile ones.

</En>
<Ur>

- **JavaScript me har sust cheez async hai**: `fetch`, database queries, file parhna, timers. Un ke nataij lena zaroori hai.
- **Promises buniyad hain**: `fetch` promise deta hai, `async` functions promises dete hain, har jadeed library inhe istemal karti hai.
- **Callbacks ab bhi milenge**: event listeners, array methods, purani Node APIs aur libraries.
- **Async kaam sahi tarah jorna** (ek saath, timeouts, jazwi nakamiyan) tez, qabil-e-bharosa apps ko sust, kamzor apps se alag karta hai.

</Ur>
</Tr>
</Why>
<When>

<En>

| Situation | Use |
| --- | --- |

</En>
<Ur>

| Soorat-e-haal | Istemal |
| --- | --- |
| "Har item ke liye / click par ye karo" | callback (`map`, `addEventListener`) |
| Purani callback wali API | promise me lapetein (`promisify`) |

| Kai alag requests | `Promise.all` |

| Request jo zyada der na le | timeout ke saath `Promise.race` (ya `AbortSignal.timeout`) |
| Kai zariye aazmayen, pehla chalne wala lein | `Promise.any` |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. If a function will finish later, return a **promise** from it.
2. Consume it with `await` inside `try…catch` (or `.then().catch()`).
3. In `.then` chains, always **return** the value or promise you want to pass on.
4. Start independent work together and combine with `Promise.all`/`allSettled`.

</En>
<Ur>

1. Agar function baad me khatam hoga to us se **promise** wapas karein.
2. Ise `try…catch` ke andar `await` se (ya `.then().catch()` se) istemal karein.
3. `.then` chains me jo value ya promise aage bhejna ho use hamesha **return** karein.
4. Alag kaam ek saath shuru karein aur `Promise.all`/`allSettled` se jorein.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Ordering food at a busy **food court**.

- **Callback style**: you give the cook **your phone number** and say "call me when it's ready". Fine for one order. But if your burger needs fries that need a sauce from another stall, you end up with a chain of phone calls, each one triggering the next, and if one stall messes up, every call has to check for problems.
- **Promise style**: the cashier gives you a **buzzer** (the promise). It's **pending** while the food is made. Then it either buzzes green (**fulfilled**, here's your burger) or red (**rejected**, we're out of buns), and it does that **once**. You can decide in advance what to do in either case (`.then`, `.catch`).
- **Chaining** is handing the buzzer result straight to the next counter: "when the burger is ready, start the fries; when the fries are ready, get the sauce".
- **`Promise.all`** is ordering from three stalls and waiting until **all three** buzzers go off. **`Promise.race`** is "whichever is ready first". **`Promise.any`** is "the first one that isn't sold out".

</En>
<Ur>

Masroof **food court** me khana order karna.

- **Callback andaaz**: aap cook ko **apna phone number** dete hain aur kehte hain "tayyar ho to call karna". Ek order ke liye theek hai. Magar agar burger ko fries chahiyen jinhe doosre stall ki sauce chahiye, to phone calls ki zanjeer ban jati hai, har ek agli ko shuru karti hai, aur agar ek stall gar bar kare to har call ko masail check karne parte hain.
- **Promise andaaz**: cashier aap ko ek **buzzer** (promise) deta hai. Khana banne tak ye **pending** hai. Phir ye ya to hara bajta hai (**fulfilled**, ye raha burger) ya laal (**rejected**, buns khatam hain), aur ye **ek dafa** hota hai. Aap pehle se tay kar sakte hain ke har soorat me kya karna hai (`.then`, `.catch`).
- **Chaining** buzzer ka nateeja seedha agle counter ko dena hai: "burger tayyar ho to fries shuru karo; fries tayyar hon to sauce lo".
- **`Promise.all`** teen stalls se order kar ke tab tak intezar karna hai jab tak **teeno** buzzers na bajen. **`Promise.race`** hai "jo pehle tayyar ho". **`Promise.any`** hai "pehla jo khatam na ho".

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Callbacks: functions called for you">

<Tr>
<En>
A callback is just a function you pass to another function, which calls it for you. Some callbacks run **right away** (synchronously, like in `map`); others run **later** (asynchronously, like in `setTimeout`).
</En>
<Ur>
Callback bas ek function hai jo aap doosre function ko dete hain, jo use aap ke liye call karta hai. Kuch callbacks **foran** chalte hain (synchronously, jaise `map` me); kuch **baad me** (asynchronously, jaise `setTimeout` me).
</Ur>
</Tr>

```javascript
function greet(name, format) {
  return format(name);
}
console.log(greet("Alex", (n) => "Hi " + n), "|", greet("Alex", (n) => n.toUpperCase()));
console.log([3, 1, 2].map((n) => n * 10));

console.log("before");
setTimeout(() => console.log("async callback, later"), 0);
console.log("after");
```

```text output
Hi Alex | ALEX
[ 30, 10, 20 ]
before
after
async callback, later
```

<Happened>
<Tr>
<En>

- `greet` let the caller decide **how** to format the name by passing a function. Same with `map`: you supply what to do with each item. These run immediately.
- The `setTimeout` callback ran **after** "after": async callbacks run later, through the event loop.
- Callbacks are everywhere: event listeners, array methods, sorting comparators. The tricky part is only the **async** ones.

</En>
<Ur>

- `greet` ne function de kar call karne wale ko tay karne diya ke naam **kaise** format ho. `map` ke saath bhi yahi: aap batate hain ke har item ke saath kya karna hai. Ye foran chalte hain.
- `setTimeout` ka callback "after" ke **baad** chala: async callbacks event loop ke zariye baad me chalte hain.
- Callbacks har jagah hain: event listeners, array methods, sorting comparators. Mushkil hissa sirf **async** wale hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Error-first callbacks and the pyramid">

<Tr>
<En>
Node's classic style passes **an error first** and the result second: `callback(err, value)`. Every callback must check `err`. When one step needs the previous step's result, callbacks **nest inside each other**.
</En>
<Ur>
Node ka classic andaaz **pehle error** aur doosre nateeja deta hai: `callback(err, value)`. Har callback ko `err` check karna parta hai. Jab ek qadam ko pichhle qadam ka nateeja chahiye, callbacks **ek doosre ke andar nest** hote hain.
</Ur>
</Tr>

```javascript
const USERS = { 1: { id: 1, name: "Alex", cartId: 10 } };
const CARTS = { 10: { id: 10, items: ["Mug", "Lamp"] } };

function getUser(id, callback) {
  setTimeout(() => {
    const user = USERS[id];
    if (!user) callback(new Error(`User ${id} not found`));
    else callback(null, user);
  }, 10);
}

function getCart(cartId, callback) {
  setTimeout(() => callback(null, CARTS[cartId]), 10);
}

getUser(1, (err, user) => {
  if (err) return console.log("error:", err.message);
  getCart(user.cartId, (err2, cart) => {
    if (err2) return console.log("error:", err2.message);
    console.log(user.name, "has", cart.items.length, "items");
  });
});

getUser(99, (err, user) => {
  if (err) return console.log("error:", err.message);
  console.log(user);
});
```

```text output
error: User 99 not found
Alex has 2 items
```

<Happened>
<Tr>
<En>

- Each step checks `err` and stops early with `return`. Forget one check and errors are silently ignored.
- `getCart` lives **inside** `getUser`'s callback. With five steps you'd get five levels of indentation: the "**pyramid of doom**".
- "User 99 not found" printed first because it finished sooner (one step instead of two); async results arrive in **completion order**, not the order you wrote them.
- Other problems: you can't use `try…catch` around it, and a buggy API might call your callback twice or never.

</En>
<Ur>

- Har qadam `err` check karta hai aur `return` se jaldi ruk jata hai. Ek check bhoolein aur errors khamoshi se nazarandaz ho jate hain.
- `getCart` `getUser` ke callback ke **andar** rehta hai. Paanch qadamon ke saath paanch levels ka indentation hota: "**pyramid of doom**".
- "User 99 not found" pehle print hua kyun ke ye jaldi khatam hua (do ke bajaye ek qadam); async nataij **khatam hone ki tarteeb** se aate hain, likhne ki tarteeb se nahi.
- Doosre masail: aap is ke gird `try…catch` nahi laga sakte, aur bigri API aap ka callback do dafa ya kabhi nahi call kar sakti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Creating a promise">

<Tr>
<En>
`new Promise((resolve, reject) => { … })` creates a promise. The function inside (the **executor**) runs **immediately**; when the work finishes, call `resolve(value)` for success or `reject(error)` for failure. `.then` runs on success, `.catch` on failure, `.finally` either way.
</En>
<Ur>
`new Promise((resolve, reject) => { … })` promise banata hai. Andar ka function (**executor**) **foran** chalta hai; jab kaam khatam ho to kamyabi ke liye `resolve(value)` ya nakami ke liye `reject(error)` call karein. Kamyabi par `.then` chalta hai, nakami par `.catch`, dono par `.finally`.
</Ur>
</Tr>

```javascript
console.log("1. creating promise");
const promise = new Promise((resolve, reject) => {
  console.log("2. executor runs immediately");
  setTimeout(() => resolve("coffee ready"), 20);
});
console.log("3. promise created:", promise);
promise.then((value) => console.log("4. then got:", value));

const failed = Promise.reject(new Error("out of beans"));
failed
  .catch((e) => console.log("catch got:", e.message))
  .finally(() => console.log("finally runs either way"));
```

```text output
1. creating promise
2. executor runs immediately
3. promise created: Promise { <pending> }
catch got: out of beans
finally runs either way
4. then got: coffee ready
```

<Happened>
<Tr>
<En>

- The executor ran **synchronously** (line 2 before line 3). The promise was **pending** when logged.
- After 20ms, `resolve("coffee ready")` fulfilled it and the `.then` callback received the value.
- `Promise.reject(…)` and `Promise.resolve(…)` create already-settled promises; handy in tests and examples. The rejected one's `.catch` ran first because it didn't need to wait.

</En>
<Ur>

- Executor **synchronously** chala (line 2 line 3 se pehle). Log karte waqt promise **pending** tha.
- 20ms baad `resolve("coffee ready")` ne ise fulfil kiya aur `.then` callback ko value mili.
- `Promise.reject(…)` aur `Promise.resolve(…)` pehle se settled promises banate hain; tests aur misaalon me kaam ke. Rejected wale ka `.catch` pehle chala kyun ke use intezar nahi karna tha.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A promise settles only once">

<Tr>
<En>
A promise can be resolved or rejected **one time**. Later calls to `resolve` or `reject` are ignored. This is a big safety improvement over callbacks, which a buggy API might call twice.
</En>
<Ur>
Promise **ek dafa** resolve ya reject ho sakta hai. `resolve` ya `reject` ki baad ki calls nazarandaz ho jati hain. Ye callbacks par bari hifazati behtari hai, jinhe bigri API do dafa call kar sakti hai.
</Ur>
</Tr>

```javascript
const once = new Promise((resolve, reject) => {
  resolve("first");
  resolve("second");
  reject(new Error("too late"));
});

once.then((v) => console.log("settled with:", v));
```

```text output
settled with: first
```

<Happened>
<Tr>
<En>

- Only "first" counted. The second `resolve` and the `reject` did nothing.
- Once settled, a promise keeps its result forever: you can attach `.then` an hour later and it gets the same value immediately.

</En>
<Ur>

- Sirf "first" gina gaya. Doosre `resolve` aur `reject` ne kuch nahi kiya.
- Ek dafa settle hone ke baad promise apna nateeja hamesha rakhta hai: aap ghante baad `.then` lagayen aur use foran wahi value milti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Chaining flattens the pyramid">

<Tr>
<En>
`.then` **returns a new promise**. Whatever your callback returns becomes the next step's value; if it returns a **promise**, the chain waits for it. One `.catch` at the end handles a failure in **any** step.
</En>
<Ur>
`.then` **naya promise wapas karta** hai. Aap ka callback jo bhi wapas kare wo agle qadam ki value banti hai; agar ye **promise** wapas kare to chain us ka intezar karti hai. Aakhir me ek `.catch` **kisi bhi** qadam ki nakami sambhalta hai.
</Ur>
</Tr>

```javascript
const USERS = { 1: { id: 1, name: "Alex", cartId: 10 } };
const CARTS = { 10: { id: 10, items: ["Mug", "Lamp"] } };

const getUser = (id) =>
  new Promise((resolve, reject) =>
    setTimeout(() => (USERS[id] ? resolve(USERS[id]) : reject(new Error(`User ${id} not found`))), 10)
  );
const getCart = (cartId) => new Promise((resolve) => setTimeout(() => resolve(CARTS[cartId]), 10));

getUser(1)
  .then((user) => getCart(user.cartId).then((cart) => ({ user, cart })))
  .then(({ user, cart }) => cart.items.length + " items for " + user.name)
  .then((message) => console.log(message))
  .catch((error) => console.log("error:", error.message));

getUser(99)
  .then((user) => getCart(user.cartId))
  .then(() => console.log("never runs"))
  .catch((error) => console.log("error:", error.message));
```

```text output
error: User 99 not found
2 items for Alex
```

<Happened>
<Tr>
<En>

- The same two-step flow is now a **flat** chain: each `.then` is one step.
- Returning `getCart(…)` (a promise) made the chain wait for the cart before moving on.
- For user 99, the rejection **skipped** every `.then` and went straight to `.catch`: one place for errors.
- Passing two values forward is a bit awkward (the inner `.then` building `{ user, cart }`). `async`/`await` makes this much simpler, as you'll see at the end.

</En>
<Ur>

- Wahi do qadam ka bahao ab **seedhi** chain hai: har `.then` ek qadam hai.
- `getCart(…)` (promise) return karne se chain aage barhne se pehle cart ka intezar karti rahi.
- User 99 ke liye rejection ne har `.then` **chhor diya** aur seedha `.catch` par gaya: errors ke liye ek jagah.
- Do values aage bhejna thora mushkil hai (andar wala `.then` `{ user, cart }` bana raha hai). `async`/`await` ise kaheen aasaan banata hai, jaisa aakhir me dekhenge.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What a chain passes along">

<Tr>
<En>
Each `.then` receives what the previous one **returned**. Forget to return, and the next step gets `undefined`. A thrown error jumps to the next `.catch`; a `.catch` that returns a value **recovers**, and the chain continues.
</En>
<Ur>
Har `.then` ko wo milta hai jo pichhle ne **return** kiya. Return bhool jayen to agle qadam ko `undefined` milta hai. Phenka gaya error agle `.catch` tak koodta hai; value return karne wala `.catch` **sambhal leta** hai, aur chain jaari rehti hai.
</Ur>
</Tr>

```javascript
Promise.resolve(2)
  .then((n) => n * 10)
  .then((n) => {
    console.log("got", n);
  })
  .then((n) => console.log("next got", n))
  .then(() => {
    throw new Error("step 4 failed");
  })
  .then(() => console.log("skipped"))
  .catch((e) => {
    console.log("caught:", e.message);
    return "recovered";
  })
  .then((v) => console.log("after catch:", v));
```

```text output
got 20
next got undefined
caught: step 4 failed
after catch: recovered
```

<Happened>
<Tr>
<En>

- `n => n * 10` returned 20 (arrow functions without braces return automatically).
- The step with `{ console.log(…) }` returned **nothing**, so the next step received `undefined`. Missing `return` is the #1 promise-chain bug.
- The thrown error skipped "skipped" and landed in `.catch`.
- Because `.catch` returned "recovered", the chain was back on the success path. To keep it failed, rethrow inside `.catch`.

</En>
<Ur>

- `n => n * 10` ne 20 return kiya (braces ke baghair arrow functions khud return karte hain).
- `{ console.log(…) }` wale qadam ne **kuch return nahi** kiya, isliye agle qadam ko `undefined` mila. Ghayab `return` promise chain ka nambar 1 bug hai.
- Phenke gaye error ne "skipped" chhora aur `.catch` me aaya.
- Chunke `.catch` ne "recovered" return kiya, chain wapas kamyabi ke raaste par aa gayi. Ise fail rakhne ke liye `.catch` ke andar dobara phenkein.

</Ur>
</Tr>
</Happened>

<Step title="Turning callbacks into promises">

<Tr>
<En>
To use an old callback API with promises and `await`, **wrap** it: call the original function with a callback that calls `resolve` or `reject`. This is called **promisifying**. Node includes a ready-made helper, `util.promisify`.
</En>
<Ur>
Purani callback API ko promises aur `await` ke saath istemal karne ke liye use **lapetein**: asal function ko aisa callback de kar call karein jo `resolve` ya `reject` call kare. Ise **promisify** karna kehte hain. Node me bana banaya helper hai, `util.promisify`.
</Ur>
</Tr>

```javascript
function readSetting(key, callback) {
  setTimeout(() => (key === "theme" ? callback(null, "dark") : callback(new Error("Unknown setting: " + key))), 5);
}

function promisify(fn) {
  return (...args) =>
    new Promise((resolve, reject) => {
      fn(...args, (err, value) => (err ? reject(err) : resolve(value)));
    });
}

const readSettingAsync = promisify(readSetting);
console.log(await readSettingAsync("theme"));
try {
  await readSettingAsync("font");
} catch (error) {
  console.log(error.message);
}
```

```text output
dark
Unknown setting: font
```

<Happened>
<Tr>
<En>

- `promisify` returned a new function. It passes your arguments through, adds an error-first callback at the end, and turns `err` into `reject` and the value into `resolve`.
- Now the old API works with `await` and `try…catch`.
- In Node, `import { promisify } from "node:util"` does the same, and most built-ins already have promise versions (`node:fs/promises`, `node:timers/promises`).

</En>
<Ur>

- `promisify` ne naya function wapas kiya. Ye aap ke arguments aage deta hai, aakhir me error-first callback jorta hai, aur `err` ko `reject` aur value ko `resolve` me badalta hai.
- Ab purani API `await` aur `try…catch` ke saath chalti hai.
- Node me `import { promisify } from "node:util"` yahi karta hai, aur zyada tar bane banaye modules ke promise versions pehle se hain (`node:fs/promises`, `node:timers/promises`).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Combining promises: all, allSettled, race, any">

<Tr>
<En>
Four helpers combine several promises. `all` waits for **every** success (fails fast on the first error). `allSettled` waits for **every** result, success or failure. `race` takes the **first to settle**. `any` takes the **first success**. `race` also makes a simple timeout.
</En>
<Ur>
Chaar helpers kai promises jorte hain. `all` **har** kamyabi ka intezar karta hai (pehle error par foran fail). `allSettled` **har** nateeje ka intezar karta hai, kamyabi ho ya nakami. `race` **pehle settle hone wala** leta hai. `any` **pehli kamyabi** leta hai. `race` se saada timeout bhi banta hai.
</Ur>
</Tr>

```javascript
const delay = (ms, value, fail) =>
  new Promise((res, rej) => setTimeout(() => (fail ? rej(new Error(value)) : res(value)), ms));

console.log("all:", await Promise.all([delay(30, "a"), delay(10, "b"), delay(20, "c")]));
try {
  await Promise.all([delay(10, "a"), delay(5, "b failed", true)]);
} catch (error) {
  console.log("all rejected:", error.message);
}

const settled = await Promise.allSettled([delay(10, "a"), delay(5, "b failed", true)]);
console.log("allSettled:", settled.map((r) => r.status));

console.log("race:", await Promise.race([delay(30, "slow"), delay(10, "fast")]));
console.log("any:", await Promise.any([delay(5, "x failed", true), delay(20, "y")]));
try {
  await Promise.any([delay(5, "p", true), delay(5, "q", true)]);
} catch (error) {
  console.log("any rejected:", error.name, error.errors.map((x) => x.message));
}

function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) => setTimeout(() => reject(new Error(`Timed out after ${ms}ms`)), ms));
  return Promise.race([promise, timeout]);
}
try {
  await withTimeout(delay(100, "too slow"), 30);
} catch (error) {
  console.log(error.message);
}
```

```text output
all: [ 'a', 'b', 'c' ]
all rejected: b failed
allSettled: [ 'fulfilled', 'rejected' ]
race: fast
any: y
any rejected: AggregateError [ 'p', 'q' ]
Timed out after 30ms
```

<Happened>
<Tr>
<En>

| Helper | Resolves when | Rejects when |
| --- | --- | --- |
| `Promise.all` | all fulfil (results **in input order**) | the first rejection |
| `Promise.allSettled` | all settle (never rejects) | never |
| `Promise.race` | the first settles (fulfils) | the first settles (rejects) |
| `Promise.any` | the first fulfils | all reject (`AggregateError`) |

- `all` kept the results in the **same order** as the input, even though "b" finished first.
- `withTimeout` raced the slow work against a timer. Note: the slow work isn't **cancelled**, just ignored. For `fetch`, pass `signal: AbortSignal.timeout(ms)` to actually cancel the request.

</En>
<Ur>

| Helper | Kab resolve | Kab reject |
| --- | --- | --- |
| `Promise.all` | sab fulfil hon (nataij **input ki tarteeb** me) | pehla rejection |
| `Promise.allSettled` | sab settle hon (kabhi reject nahi) | kabhi nahi |
| `Promise.race` | pehla settle ho (fulfil) | pehla settle ho (reject) |
| `Promise.any` | pehla fulfil ho | sab reject hon (`AggregateError`) |

- `all` ne nataij input ki **usi tarteeb** me rakhe, halanke "b" pehle khatam hua.
- `withTimeout` ne sust kaam ka timer se muqabla karwaya. Note: sust kaam **cancel** nahi hota, bas nazarandaz hota hai. `fetch` ke liye request waqai cancel karne ke liye `signal: AbortSignal.timeout(ms)` dein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="async/await is promises underneath">

<Tr>
<En>
An `async` function **always returns a promise**: a returned value fulfils it, a thrown error rejects it. `await` waits for a promise and gives you its value (or throws its error). So everything in this lesson works together: you can `await` any promise and call `.then` on any `async` function.
</En>
<Ur>
`async` function **hamesha promise wapas karta** hai: return hui value use fulfil karti hai, phenka gaya error use reject karta hai. `await` promise ka intezar kar ke us ki value deta hai (ya us ka error phenkta hai). Isliye is lesson ki har cheez saath kaam karti hai: aap kisi bhi promise ko `await` kar sakte hain aur kisi bhi `async` function par `.then` call kar sakte hain.
</Ur>
</Tr>

```javascript
async function getTotal() {
  return 42;
}
const p = getTotal();
console.log(p instanceof Promise, await p);

async function fails() {
  throw new Error("nope");
}
fails().catch((e) => console.log("async throw = rejected promise:", e.message));

const USERS = { 1: { name: "Alex", cartId: 10 } };
const CARTS = { 10: { items: ["Mug", "Lamp"] } };
const getUser = async (id) => USERS[id] ?? Promise.reject(new Error(`User ${id} not found`));
const getCart = async (cartId) => CARTS[cartId];

async function summary(id) {
  try {
    const user = await getUser(id);
    const cart = await getCart(user.cartId);
    return `${cart.items.length} items for ${user.name}`;
  } catch (error) {
    return "error: " + error.message;
  }
}
console.log(await summary(1), "|", await summary(99));
```

```text output
true 42
async throw = rejected promise: nope
2 items for Alex | error: User 99 not found
```

<Happened>
<Tr>
<En>

- `getTotal()` returned a **promise** for 42, even though the function just says `return 42`.
- Throwing inside `fails` produced a rejected promise, handled with `.catch`.
- `summary` does the same user → cart flow as the callback and `.then` versions, but reads top to bottom, keeps `user` and `cart` in normal variables, and uses ordinary `try…catch`. That's why `async`/`await` is the default today; promises (and `Promise.all`) are what make it work.

</En>
<Ur>

- `getTotal()` ne 42 ka **promise** wapas kiya, halanke function bas `return 42` kehta hai.
- `fails` ke andar error phenkne se rejected promise bana, jo `.catch` se sambhala gaya.
- `summary` wahi user → cart bahao karta hai jo callback aur `.then` versions karte the, magar upar se neeche parha jata hai, `user` aur `cart` ko aam variables me rakhta hai, aur aam `try…catch` istemal karta hai. Isi liye aaj `async`/`await` default hai; promises (aur `Promise.all`) hi ise chalate hain.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Forgetting to return in .then">

```javascript
const getPrice = () => Promise.resolve(100);
getPrice()
  .then((price) => {
    price * 1.08;
  })
  .then((withTax) => console.log("with tax:", withTax));
```

```text output
with tax: undefined
```

</Bad>
<Good title="Return the value">

```javascript
const getPrice = () => Promise.resolve(100);
getPrice()
  .then((price) => price * 1.08)
  .then((withTax) => console.log("with tax:", withTax));
```

```text output
with tax: 108
```

</Good>
</Compare>

<Compare>
<Bad title="Nesting thens (a pyramid again)">

```text
getUser(1).then((user) => {
  getCart(user.cartId).then((cart) => {
    getTotals(cart).then((totals) => { … });   // errors here aren't caught outside
  });
});
```

</Bad>
<Good title="Flat chain, or async/await">

```text
const user = await getUser(1);
const cart = await getCart(user.cartId);
const totals = await getTotals(cart);
```

</Good>
</Compare>

<Compare>
<Bad title="Wrapping a promise in new Promise">

```text
function load() {
  return new Promise((resolve, reject) => {
    fetch(url).then(resolve).catch(reject);   // the "promise constructor anti-pattern"
  });
}
```

</Bad>
<Good title="Just return the promise">

```text
function load() {
  return fetch(url);
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **No `.catch` at the end of a chain** → unhandled rejections.
- **`await` in a loop for independent work** → slow. Use `Promise.all(items.map(…))` (limit concurrency for huge lists).
- **`forEach` with an async callback** → doesn't wait. Use `for…of` with `await`, or `Promise.all`.
- **Using `Promise.all` when partial failure is fine** → one failure loses all results. Use `allSettled`.
- **Calling a callback-style function and expecting a return value**: the value only arrives inside the callback.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Chain ke aakhir me `.catch` nahi** → unhandled rejections.
- **Alag kaam ke liye loop me `await`** → sust. `Promise.all(items.map(…))` lein (bohot bari lists ke liye ek saath chalne walon ki hadd rakhein).
- **Async callback ke saath `forEach`** → intezar nahi karta. `await` ke saath `for…of`, ya `Promise.all` lein.
- **Jab jazwi nakami theek ho tab `Promise.all` lagana** → ek nakami tamam nataij kho deti hai. `allSettled` lein.
- **Callback andaaz ka function call kar ke return value ki umeed rakhna**: value sirf callback ke andar aati hai.

</Ur>
</Tr>

  setTimeout(() => (sku in PRICES ? callback(null, PRICES[sku]) : callback(new Error("Unknown SKU: " + sku))), 5);

  new Promise((resolve, reject) => getPrice(sku, (err, value) => (err ? reject(err) : resolve(value))));

<Takeaways>
<Tr>
<En>

- A **callback** is a function called for you; async callbacks run later via the event loop. Node's style is error-first `(err, value)`.
- Nested callbacks create a pyramid and repeated error checks; promises fix that.
- A **promise** is pending → fulfilled or rejected, **once**. The executor runs immediately.
- `.then` returns a new promise; **return** values (or promises) to pass them on; one `.catch` at the end handles any step; `.finally` always runs.
- Wrap callback APIs with a small `promisify` (or `util.promisify`).
- `Promise.all` (all or fail fast), `allSettled` (every result), `race` (first settled, timeouts), `any` (first success).
- `async` functions return promises; `await` unwraps them. Prefer `async`/`await`, and use `Promise.all` for parallel work.

</En>

<DeepDive title="More about promises">

**Thenables.** Anything with a `.then` method is treated like a promise by `await` and `Promise.resolve`. That's how libraries' custom promise-like objects interoperate.

**Resolution with a promise.** `resolve(otherPromise)` makes your promise follow the other one; a promise can never be fulfilled **with** a promise.

**`Promise.withResolvers()`** (newer) returns `{ promise, resolve, reject }`, handy when resolve/reject must be called from outside the executor (event-based code).

**Unhandled rejections.** A rejection with no handler by the end of the current microtask cycle triggers `unhandledrejection` (browsers) or crashes Node (default since v15).

**Concurrency limits.** `Promise.all` on 10,000 requests starts them all at once. Use a limiter (p-limit, or process in batches) to keep, say, 5 in flight.

**Cancellation.** Promises can't be cancelled. Use `AbortController` with APIs that support it (`fetch`, many Node APIs, timers in `node:timers/promises`).

**Callbacks still matter.** Streams and event emitters deliver many values over time, which a single promise can't represent. Async iterators (`for await…of`) bridge the gap (Iterators and Generators lesson).

</DeepDive>

<DeepDive title="Real world: the emails that went out twice">

An order service used a callback-based email library:

```text
sendEmail(order, (err) => {
  if (err) retryLater(order);
  markAsSent(order);
});
```

Two bugs hid here. First, after an error, the code called `retryLater` **and** `markAsSent` (a missing `return`). Second, under certain network conditions, the old library called the callback **twice**: once with a timeout error, then again with success when the slow response finally arrived. Customers received duplicate confirmation emails, and some orders were marked "sent" when they had actually failed.

The fix:

1. Wrap the library in a promise. A promise settles **once**, so the duplicate callback became harmless.
2. Rewrite the logic with `async`/`await`: `try { await sendEmail(order); await markAsSent(order); } catch { await retryLater(order); }`, where the two paths are now clearly exclusive.
3. Make sending idempotent: store a `sentAt` timestamp and skip orders that already have one.

Lesson: promises give you guarantees callbacks don't: **exactly one outcome**, and errors that can't be accidentally ignored when you use `try…catch`.

</DeepDive>

<DeepDive title="Security lens">

- **Always handle rejections**: an unhandled rejection can crash a Node server, which is an easy denial of service.
- **Time-limit external calls** (`AbortSignal.timeout`) so a slow or malicious service can't hold your requests forever.
- **Limit concurrency** when the number of promises depends on user input (`Promise.all(userIds.map(fetch…))`): a request with 100,000 ids could flood your database.
- **Don't leak internal errors** from rejected promises to clients; map them to safe messages.
- **Idempotency**: retries and duplicate callbacks can repeat side effects (charges, emails). Use idempotency keys for payments and other critical actions.
- **Callbacks from untrusted code** may be called many times or never; promisify them to get single-settlement guarantees.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is callback hell and how do promises solve it?">
Callback hell is deeply nested callbacks for sequential async steps, with repeated error handling at each level. Promises return chainable objects, so steps form a flat sequence of then calls with a single catch, and async/await makes the code read sequentially.
</QA>

<QA q="What happens if you call resolve twice?">
Nothing after the first call. A promise settles exactly once, and subsequent resolve or reject calls are ignored.
</QA>

<QA q="What is the difference between Promise.all and Promise.allSettled?">
Promise.all resolves with all values in input order when every promise fulfils, and rejects as soon as one rejects. Promise.allSettled always waits for every promise and resolves with an array of status objects describing each outcome.
</QA>

<QA q="What is the difference between Promise.race and Promise.any?">
race settles with the first promise to settle, whether it fulfils or rejects. any resolves with the first promise to fulfil, ignores rejections, and rejects with an AggregateError only if all of them reject.
</QA>

<QA q="How do you convert a callback-based function to return a promise?">
Wrap it in a function that returns new Promise, calling the original with a callback that rejects on error and resolves with the result, or use util.promisify in Node for error-first callbacks.
</QA>

</DeepDive>
