<BigIdea>
<Tr>
<En>
As programs grow, one giant file becomes impossible to manage. **Modules** let you split code into many files, where **each file is its own private space**. Nothing inside a module is visible to other files unless you **`export`** it, and another file only gets what it explicitly **`import`**s. This is the **ES modules** system (`import`/`export`) built into modern JavaScript, browsers and Node.js. A module's code **runs once**, the first time anything imports it, and every importer shares the same exported values. Node.js also has an older system, **CommonJS** (`require`/`module.exports`), which you'll meet in older projects. Knowing both, plus how file extensions and `package.json` decide which one is used, saves hours of "Cannot use import statement outside a module" errors.
</En>
<Ur>
Jaise jaise programs barhte hain, ek bohot bari file sambhalna na-mumkin ho jata hai. **Modules** aap ko code kai files me baantne dete hain, jahan **har file apni private jagah hai**. Module ke andar ki koi cheez doosri files ko nazar nahi aati jab tak aap use **`export`** na karein, aur doosri file ko sirf wahi milta hai jo wo wazeh taur par **`import`** kare. Ye **ES modules** system (`import`/`export`) hai jo jadeed JavaScript, browsers aur Node.js me bana hua hai. Module ka code **ek dafa chalta** hai, pehli dafa jab koi use import kare, aur har import karne wala wahi export ki gayi values share karta hai. Node.js me ek purana system bhi hai, **CommonJS** (`require`/`module.exports`), jo aap ko purane projects me milega. Dono jaanna, aur ye bhi ke file extensions aur `package.json` kaise tay karte hain ke kaun sa istemal ho, "Cannot use import statement outside a module" errors ke ghante bachata hai.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

```text
// money.js
export const CURRENCY = "USD";
export function formatCents(cents) { … }
export default class Cart { … }

// main.js
import Cart, { formatCents, CURRENCY } from "./money.js";
import * as money from "./money.js";
const { drawChart } = await import("./charts.js");
```

| Syntax | Meaning |
| --- | --- |
| `export const x = …` / `export function f()` | named export |
| `export default …` | the module's one default export |
| `import { x, f } from "./file.js"` | import named exports (names must match) |
| `import Anything from "./file.js"` | import the default (any name you like) |
| `import { x as y } from …` | rename on import |
| `import * as mod from …` | everything as one object |
| `export { x } from "./other.js"` | re-export |
| `await import("./file.js")` | load a module on demand |

</En>

<Why>
<Tr>
<En>

- **Organisation**: one file per topic (`money.js`, `cart.js`, `api.js`) is easier to find, read and test.
- **Privacy by default**: helper functions and variables stay inside their file; no more global variables colliding.
- **Clear dependencies**: the `import` lines at the top show exactly what a file uses.
- **Every modern tool is built on modules**: npm packages, React components, Next.js pages, bundlers that remove unused code.

</En>
<Ur>

- **Tarteeb**: har mauzoo ki ek file (`money.js`, `cart.js`, `api.js`) dhoondna, parhna aur test karna aasaan hai.
- **Default me privacy**: helper functions aur variables apni file me rehte hain; global variables ka takrao khatam.
- **Wazeh dependencies**: upar ki `import` lines bilkul dikhati hain ke file kya istemal karti hai.
- **Har jadeed auzaar modules par bana hai**: npm packages, React components, Next.js pages, ghair istemal code hatane wale bundlers.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Use |
| --- | --- |
| Several helpers from one file | named exports |
| A file that's "about" one thing (a component, a class) | default export (or a named one; teams differ) |
| New Node.js project | ES modules: `"type": "module"` in `package.json` |
| Old Node.js project or package | CommonJS `require`, or `.cjs` files |
| Big code only needed sometimes (charts, editors) | dynamic `import()` |
| Browser without a bundler | `<script type="module">` |

</En>
<Ur>

| Soorat-e-haal | Istemal |
| --- | --- |
| Ek file se kai helpers | named exports |
| File jo ek cheez ke "baare me" ho (component, class) | default export (ya named; teams mukhtalif hain) |
| Naya Node.js project | ES modules: `package.json` me `"type": "module"` |
| Purana Node.js project ya package | CommonJS `require`, ya `.cjs` files |
| Bara code jo kabhi kabhi chahiye (charts, editors) | dynamic `import()` |
| Bundler ke baghair browser | `<script type="module">` |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. In the file that **provides** code, put `export` before what you want to share.
2. In the file that **uses** it, write `import { name } from "./file.js"` at the top (with the **`.js`** extension in Node and browsers).
3. In Node, add `"type": "module"` to `package.json` (or name files `.mjs`).
4. Run the entry file: `node main.js`.

</En>
<Ur>

1. Jo file code **deti** hai, us me share karne wali cheez se pehle `export` lagayen.
2. Jo file use **istemal** karti hai, us ke upar `import { name } from "./file.js"` likhein (Node aur browsers me **`.js`** extension ke saath).
3. Node me `package.json` me `"type": "module"` jorein (ya files ka naam `.mjs` rakhein).
4. Entry file chalayen: `node main.js`.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of an **office building** where each module is a **room with a hatch**.

- Everything in a room (variables, helper functions) is private. People in other rooms can't see in.
- The **hatch** is the `export` list: you choose which items to pass out. Everything else stays in the room.
- Another room **orders** items by name through its own hatch: `import { formatCents } from "./money.js"`. If they ask for something you didn't export, they get nothing.
- Each room is **set up only once**, the first time someone orders from it. After that, everyone gets items from the **same** room, so if the room keeps a counter, everyone sees the same count.
- **Dynamic `import()`** is calling a room you rarely need **only when** you need it, instead of setting it up when the building opens.

</En>
<Ur>

**Office building** ka sochein jahan har module **khirki wala kamra** hai.

- Kamre ki har cheez (variables, helper functions) private hai. Doosre kamron ke log andar nahi dekh sakte.
- **Khirki** `export` ki list hai: aap chunte hain kaun si cheezen bahar deni hain. Baqi sab kamre me rehta hai.
- Doosra kamra apni khirki se naam le kar cheezen **mangwata** hai: `import { formatCents } from "./money.js"`. Agar wo aisi cheez maangen jo aap ne export nahi ki, unhe kuch nahi milta.
- Har kamra **sirf ek dafa tayyar** hota hai, pehli dafa jab koi us se mangwaye. Us ke baad sab ko **usi** kamre se cheezen milti hain, isliye agar kamra counter rakhe to sab ko wahi ginti dikhti hai.
- **Dynamic `import()`** kam zaroori kamre ko building khulte waqt tayyar karne ke bajaye **sirf tab** bulana hai jab zaroorat ho.

</Ur>
</Tr>

## Learn it step by step

<Tr>

Run them in an empty folder, in order, because later steps reuse earlier files. (The **Run** button on this page can't run `import`/`export`, since it runs one snippet at a time.)

</En>
<Ur>

Modules ko **kai files** chahiyen, isliye ye namoone shell commands hain: `cat > file <<'EOF' … EOF` file banata hai, phir `node` use chalata hai. Har output asli hai (Node.js 22). Inhe ek khaali folder me tarteeb se chalayen, kyun ke baad ke qadam pehle ki files dobara istemal karte hain. (Is page ka **Run** button `import`/`export` nahi chala sakta, kyun ke ye ek waqt me ek tukra chalata hai.)

</Ur>
</Tr>

<Walkthrough>

<Step title="Named exports and imports">

<Tr>
<En>
Put `export` in front of anything you want to share. Import it by the **same name** inside curly braces. `"type": "module"` in `package.json` tells Node that `.js` files are ES modules.
</En>
<Ur>
Jo bhi share karna ho us se pehle `export` lagayen. Curly braces me **wahi naam** likh kar import karein. `package.json` me `"type": "module"` Node ko batata hai ke `.js` files ES modules hain.
</Ur>
</Tr>

```bash
echo '{ "type": "module" }' > package.json

cat > money.js <<'EOF'
export const CURRENCY = "USD";

export function formatCents(cents) {
  return "$" + (cents / 100).toFixed(2);
}

function roundCents(value) {
  return Math.round(value);
}

export function addTax(cents, rate) {
  return roundCents(cents * (1 + rate));
}
EOF

cat > main.js <<'EOF'
import { formatCents, addTax, CURRENCY } from "./money.js";
console.log(formatCents(addTax(1999, 0.08)), CURRENCY);
EOF

node main.js
```

```text output
$21.59 USD
```

<Happened>
<Tr>
<En>

- `main.js` imported three named exports and used them like local functions: 1999 × 1.08 = 2158.92 → rounded to 2159 → "$21.59".
- `roundCents` has **no `export`**, so it's private to `money.js`. `addTax` can use it, but no other file can.
- The path starts with `./` (relative to the current file) and **includes `.js`**. Import statements go at the **top** of the file.

</En>
<Ur>

- `main.js` ne teen named exports import kiye aur unhe local functions ki tarah istemal kiya: 1999 × 1.08 = 2158.92 → round ho kar 2159 → "$21.59".
- `roundCents` par **`export` nahi**, isliye ye `money.js` ka private hai. `addTax` ise istemal kar sakta hai, magar koi aur file nahi.
- Path `./` se shuru hota hai (maujooda file ke hisaab se) aur **`.js` shamil hai**. Import statements file ke **upar** jate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Renaming and namespace imports">

<Tr>
<En>
Use `as` to rename an import (handy when two modules export the same name). `import * as money` collects all named exports into one object.
</En>
<Ur>
Import ka naam badalne ke liye `as` lein (jab do modules ek hi naam export karein to kaam ka). `import * as money` tamam named exports ek object me ikatthe karta hai.
</Ur>
</Tr>

```bash
cat > main2.js <<'EOF'
import * as money from "./money.js";
import { formatCents as format } from "./money.js";

console.log(Object.keys(money));
console.log(format(500), typeof money.roundCents);
EOF

node main2.js
```

```text output
[ 'CURRENCY', 'addTax', 'formatCents' ]
$5.00 undefined
```

<Happened>
<Tr>
<En>

- The namespace object `money` contains exactly the three exports, sorted by name. `money.roundCents` is `undefined`: private stays private.
- `formatCents as format` gave the function a shorter local name. The original module is unchanged.
- Importing the same module twice (here, two `import` lines) doesn't load it twice.

</En>
<Ur>

- Namespace object `money` me bilkul teen exports hain, naam ke hisaab se tarteeb me. `money.roundCents` `undefined` hai: private private hi rehta hai.
- `formatCents as format` ne function ko chhota local naam diya. Asal module nahi badla.
- Ek hi module ko do dafa import karna (yahan do `import` lines) use do dafa load nahi karta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Default exports">

<Tr>
<En>
A module can have **one** `export default`. The importer chooses any name for it (no curly braces). A module can mix one default with named exports.
</En>
<Ur>
Module ka **ek** `export default` ho sakta hai. Import karne wala us ke liye koi bhi naam chunta hai (curly braces nahi). Module ek default ko named exports ke saath mila sakta hai.
</Ur>
</Tr>

```bash
cat > cart.js <<'EOF'
export default class Cart {
  items = [];
  add(item) {
    this.items.push(item);
    return this;
  }
}

export const MAX_ITEMS = 50;
EOF

cat > main3.js <<'EOF'
import ShoppingCart, { MAX_ITEMS } from "./cart.js";

const cart = new ShoppingCart().add("Mug");
console.log(cart.items, MAX_ITEMS);
EOF

node main3.js
```

```text output
[ 'Mug' ] 50
```

<Happened>
<Tr>
<En>

- The class was exported as `default` and imported as `ShoppingCart`, a name chosen by the importer.
- `MAX_ITEMS` came in as a named import in the same line.
- **Named vs default**: named exports keep names consistent across the codebase and work better with auto-import and refactoring tools, so many teams prefer them. Next.js pages and React components often use default exports by convention.

</En>
<Ur>

- Class `default` ki tarah export hui aur `ShoppingCart` ki tarah import hui, jo naam import karne wale ne chuna.
- `MAX_ITEMS` usi line me named import ki tarah aaya.
- **Named vs default**: named exports codebase me naam yaksaan rakhte hain aur auto-import aur refactoring tools ke saath behtar chalte hain, isliye bohot si teams inhe tarjeeh deti hain. Next.js pages aur React components riwaj ke mutabiq aksar default exports istemal karte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Modules run once and share state">

<Tr>
<En>
A module's top-level code runs the **first** time it's imported. Every later import gets the **same** module, so its variables are shared by everyone. Imports are **live bindings**: you see the exporter's current value, but you can't assign to an import.
</En>
<Ur>
Module ka top-level code **pehli** dafa import hone par chalta hai. Har baad wala import **wahi** module paata hai, isliye us ke variables sab share karte hain. Imports **live bindings** hain: aap export karne wale ki maujooda value dekhte hain, magar import ko value nahi de sakte.
</Ur>
</Tr>

```bash
cat > counter.js <<'EOF'
console.log("counter.js is running");
export let count = 0;
export function increment() {
  count++;
}
EOF

cat > a.js <<'EOF'
import { increment } from "./counter.js";
increment();
EOF

cat > main4.js <<'EOF'
import "./a.js";
import { count, increment } from "./counter.js";

console.log("count after a.js:", count);
increment();
console.log("count now:", count);

try {
  count = 100;
} catch (error) {
  console.log(error.name + ": " + error.message);
}
console.log(typeof this);
EOF

node main4.js
```

```text output
counter.js is running
count after a.js: 1
count now: 2
TypeError: Assignment to constant variable.
undefined
```

<Happened>
<Tr>
<En>

- "counter.js is running" printed **once**, even though both `a.js` and `main4.js` import it.
- `a.js` called `increment()`, and `main4.js` saw `count` as 1: they share one module. After another `increment()`, the **imported** `count` shows 2. That's a live binding.
- Assigning to an import throws: only the module that owns `count` can change it.
- Module code is always in strict mode, and top-level `this` is `undefined`.
- Shared module state is useful (a database connection, a cache), but dangerous on servers: it's shared across **all users' requests**.

</En>
<Ur>

- "counter.js is running" **ek dafa** print hua, halanke `a.js` aur `main4.js` dono use import karte hain.
- `a.js` ne `increment()` call kiya, aur `main4.js` ne `count` ko 1 dekha: ye ek module share karte hain. Ek aur `increment()` ke baad **import hua** `count` 2 dikhata hai. Ye live binding hai.
- Import ko value dena error phenkta hai: sirf `count` ka maalik module use badal sakta hai.
- Module ka code hamesha strict mode me hota hai, aur top-level `this` `undefined` hai.
- Share hui module state kaam ki hai (database connection, cache), magar servers par khatarnak: ye **tamam users ki requests** me share hoti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The file extension rule">

<Tr>
<En>
In Node's ES modules and in browsers, relative imports need the **full file name including `.js`**. Leaving it out is one of the most common errors. (Bundlers like Vite and Next.js let you omit it, which is why tutorials often do.)
</En>
<Ur>
Node ke ES modules aur browsers me relative imports ko **`.js` samet poora file naam** chahiye. Ise chhorna sab se aam errors me se ek hai. (Vite aur Next.js jaise bundlers ise chhorne dete hain, isi liye tutorials aksar chhor dete hain.)
</Ur>
</Tr>

```bash
cat > main5.js <<'EOF'
import { formatCents } from "./money";
EOF

node main5.js 2>&1 | grep -E "Error|Did you mean"
```

```text output
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/home/you/money' imported from /home/you/main5.js
Did you mean to import "./money.js"?
```

<Happened>
<Tr>
<En>

- Node looked for a file literally named `money` and didn't find it. Helpfully, it suggested `./money.js`.
- The error also shows the full path it tried, useful when a folder name is wrong.
- Folders aren't imported automatically either: `import … from "./utils"` fails; write `"./utils/index.js"`.

</En>
<Ur>

- Node ne bilkul `money` naam ki file dhoondi aur nahi mili. Madadgar andaaz me us ne `./money.js` ka mashwara diya.
- Error wo poora path bhi dikhata hai jo aazmaya gaya, kaam ka jab folder ka naam ghalat ho.
- Folders bhi khud import nahi hote: `import … from "./utils"` fail hota hai; `"./utils/index.js"` likhein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="CommonJS: require and module.exports">

<Tr>
<En>
Before ES modules, Node used **CommonJS**: `require()` to import and `module.exports` to export. Files ending in **`.cjs`** are always CommonJS; `.mjs` are always ES modules; plain `.js` follows the `"type"` in `package.json`. An ES module can import a CommonJS file, but `require` doesn't exist inside ES modules.
</En>
<Ur>
ES modules se pehle Node **CommonJS** istemal karta tha: import ke liye `require()` aur export ke liye `module.exports`. **`.cjs`** par khatam hone wali files hamesha CommonJS hain; `.mjs` hamesha ES modules; saadi `.js` `package.json` ke `"type"` ke mutabiq chalti hai. ES module CommonJS file import kar sakta hai, magar ES modules ke andar `require` maujood nahi.
</Ur>
</Tr>

```bash
cat > old.cjs <<'EOF'
const path = require("node:path");
function slug(s) {
  return s.toLowerCase().replaceAll(" ", "-");
}
module.exports = { slug, ext: path.extname("photo.jpg") };
EOF

cat > useold.cjs <<'EOF'
const { slug, ext } = require("./old.cjs");
console.log(slug("Hello World"), ext);
EOF
node useold.cjs

cat > mix.js <<'EOF'
import oldModule from "./old.cjs";
console.log(oldModule.slug("From ESM"));
try {
  require("./old.cjs");
} catch (error) {
  console.log(error.name + ": " + error.message);
}
EOF
node mix.js
```

```text output
hello-world .jpg
from-esm
ReferenceError: require is not defined
```

<Happened>
<Tr>
<En>

| | ES modules | CommonJS |
| --- | --- | --- |
| Import | `import { x } from "./a.js"` | `const { x } = require("./a.cjs")` |
| Export | `export …` | `module.exports = …` |
| Files | `.mjs`, or `.js` with `"type": "module"` | `.cjs`, or `.js` without `"type": "module"` |
| Loading | static, analysed before running | runs when `require` is called |
| Browsers | yes | no (needs a bundler) |

- The ES module imported the whole `module.exports` object as its **default**.
- Calling `require` inside an ES module failed: it doesn't exist there. In ES modules use `import` (or `createRequire` from `node:module` in rare cases).
- The opposite error, "Cannot use import statement outside a module", means you used `import` in a file Node treats as CommonJS. Fix it with `"type": "module"` or a `.mjs` extension.

</En>
<Ur>

| | ES modules | CommonJS |
| --- | --- | --- |
| Import | `import { x } from "./a.js"` | `const { x } = require("./a.cjs")` |
| Export | `export …` | `module.exports = …` |
| Files | `.mjs`, ya `"type": "module"` ke saath `.js` | `.cjs`, ya `"type": "module"` ke baghair `.js` |
| Load hona | static, chalne se pehle jaancha jata hai | `require` call hone par chalta hai |
| Browsers | haan | nahi (bundler chahiye) |

- ES module ne poora `module.exports` object apne **default** ki tarah import kiya.
- ES module ke andar `require` call karna fail hua: ye wahan maujood nahi. ES modules me `import` lein (ya kabhi kabhar `node:module` ka `createRequire`).
- Ulta error, "Cannot use import statement outside a module", ka matlab hai aap ne aisi file me `import` lagaya jise Node CommonJS samajhta hai. `"type": "module"` ya `.mjs` extension se theek karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Dynamic import() and top-level await">

<Tr>
<En>
`import()` (with brackets) loads a module **when the code reaches it** and returns a promise. Use it for code you don't always need, like a charting library or an admin panel. In ES modules you can `await` at the top level, outside any function.
</En>
<Ur>
`import()` (brackets ke saath) module ko **code wahan pohanchne par** load karta hai aur promise deta hai. Ise us code ke liye lein jo hamesha nahi chahiye, jaise charting library ya admin panel. ES modules me aap kisi function ke bahar top level par `await` kar sakte hain.
</Ur>
</Tr>

```bash
cat > charts.js <<'EOF'
console.log("charts.js loaded");
export function drawChart(points) {
  return `chart with ${points.length} points`;
}
EOF

cat > main6.js <<'EOF'
console.log("page ready");

const wantsChart = true;
if (wantsChart) {
  const { drawChart } = await import("./charts.js");
  console.log(drawChart([1, 2, 3]));
}

const { readFile } = await import("node:fs/promises");
const pkg = JSON.parse(await readFile("./package.json", "utf8"));
console.log(pkg.type);
EOF

node main6.js
```

```text output
page ready
charts.js loaded
chart with 3 points
module
```

<Happened>
<Tr>
<En>

- "page ready" printed **before** "charts.js loaded": the chart module was loaded only when the `if` ran. With a static `import` at the top, it would have loaded first.
- In browsers and bundlers (Next.js, Vite), dynamic `import()` creates a **separate file** that's downloaded only when needed, making the first page load smaller.
- `node:fs/promises` is a **built-in** Node module; the `node:` prefix makes that explicit.
- `await` at the top level works only in ES modules.

</En>
<Ur>

- "page ready" "charts.js loaded" se **pehle** print hua: chart module sirf tab load hua jab `if` chala. Upar static `import` hota to ye pehle load hota.
- Browsers aur bundlers (Next.js, Vite) me dynamic `import()` **alag file** banata hai jo sirf zaroorat par download hoti hai, jis se pehla page load chhota hota hai.
- `node:fs/promises` Node ka **bana banaya** module hai; `node:` prefix ise wazeh karta hai.
- Top level par `await` sirf ES modules me chalta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Re-exporting from an index file">

<Tr>
<En>
An **index file** (or "barrel") re-exports things from several files, so other code can import from one place. `export { x } from "./file.js"` re-exports without creating a local variable.
</En>
<Ur>
**Index file** (ya "barrel") kai files ki cheezen dobara export karti hai, taa ke doosra code ek jagah se import kar sake. `export { x } from "./file.js"` local variable banaye baghair dobara export karta hai.
</Ur>
</Tr>

```bash
mkdir -p utils
cat > utils/index.js <<'EOF'
export { formatCents, addTax } from "../money.js";
export { default as Cart } from "../cart.js";
EOF

cat > main7.js <<'EOF'
import { formatCents, Cart } from "./utils/index.js";
console.log(formatCents(100), new Cart().add("x").items);
EOF

node main7.js
```

```text output
$1.00 [ 'x' ]
```

<Happened>
<Tr>
<En>

- `main7.js` got functions from two files through one import.
- `export { default as Cart }` turned another file's default export into a named one.
- Barrels make imports tidy, but very large barrels can slow down builds and tests, because importing one thing loads **every** re-exported file. Keep them small, or import directly from the file.

</En>
<Ur>

- `main7.js` ko ek import ke zariye do files se functions mile.
- `export { default as Cart }` ne doosri file ke default export ko named bana diya.
- Barrels imports saaf rakhte hain, magar bohot bare barrels builds aur tests sust kar sakte hain, kyun ke ek cheez import karna **har** dobara export hui file load karta hai. Inhe chhota rakhein, ya seedha file se import karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Modules in the browser">

<Tr>
<En>

Browsers support modules natively with `<script type="module">`. Module scripts are **deferred** automatically (they run after the HTML is parsed), have their own scope, and can import other files by URL.

```html
<!-- index.html -->
<script type="module" src="./main.js"></script>
```

```text
// main.js
import { formatCents } from "./money.js";
document.querySelector("#total").textContent = formatCents(2159);
```

</En>
<Ur>

Browsers `<script type="module">` ke saath modules ko khud support karte hain. Module scripts khud **deferred** hote hain (HTML parse hone ke baad chalte hain), un ka apna scope hota hai, aur ye URL se doosri files import kar sakte hain.

```html
<!-- index.html -->
<script type="module" src="./main.js"></script>
```

```text
// main.js
import { formatCents } from "./money.js";
document.querySelector("#total").textContent = formatCents(2159);
```

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- Opening `index.html` directly from disk (`file://…`) **won't work** for modules: browsers block them for security. Serve the folder with a local server (for example `npx serve` or VS Code's Live Server).
- Variables in a module script aren't global: `formatCents` isn't on `window`, and inline `onclick="…"` attributes can't see it. Attach listeners with `addEventListener` in the module.
- Browsers don't understand bare specifiers like `"react"` without an **import map** or a bundler. In real projects, tools like Vite and Next.js bundle and optimise your modules.

</En>
<Ur>

- `index.html` ko disk se seedha kholna (`file://…`) modules ke liye **nahi chalega**: browsers hifazat ke liye inhe rok dete hain. Folder ko local server se serve karein (maslan `npx serve` ya VS Code ka Live Server).
- Module script ke variables global nahi hote: `formatCents` `window` par nahi, aur inline `onclick="…"` attributes use nahi dekh sakte. Module me `addEventListener` se listeners lagayen.
- Browsers `"react"` jaise bare specifiers ko **import map** ya bundler ke baghair nahi samajhte. Asli projects me Vite aur Next.js jaise tools aap ke modules bundle aur behtar karte hain.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Missing extension in Node ESM">

```text
import { formatCents } from "./money";      // ERR_MODULE_NOT_FOUND
```

</Bad>
<Good title="Full file name">

```text
import { formatCents } from "./money.js";
```

</Good>
</Compare>

<Compare>
<Bad title="Curly braces around a default import">

```text
// cart.js: export default class Cart {}
import { Cart } from "./cart.js";   // SyntaxError: no export named 'Cart'
```

</Bad>
<Good title="No braces for the default">

```text
import Cart from "./cart.js";
```

</Good>
</Compare>

<Compare>
<Bad title="Mixing systems">

```text
// package.json has "type": "module"
const express = require("express");   // ReferenceError: require is not defined
```

</Bad>
<Good title="Use import in ES modules">

```text
import express from "express";
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Circular imports** (`a.js` imports `b.js`, which imports `a.js`): values may be `undefined` or uninitialised at first use. Move shared code into a third module.
- **Side effects at import time** (connecting to databases, reading files) in modules that many files import. Export a function and call it when needed.
- **Storing per-user data in module variables on a server.** It's shared by every request.
- **Huge barrel files** that make every import load the whole project.
- **Opening module pages from `file://`.** Use a local server.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Circular imports** (`a.js` `b.js` import kare, jo `a.js` import kare): pehle istemal par values `undefined` ya be-tayyar ho sakti hain. Share hone wala code teesre module me rakhein.
- **Import ke waqt side effects** (databases se connect, files parhna) un modules me jinhe bohot si files import karti hain. Function export karein aur zaroorat par call karein.
- **Server par module variables me har user ka data rakhna.** Ye har request me share hota hai.
- **Bohot bari barrel files** jo har import par poora project load karwayen.
- **Module wale pages `file://` se kholna.** Local server lein.

</Ur>
</Tr>

<DeepDive title="How modules load">

**Three phases.** For ES modules the engine (1) **parses** every file to find `import`/`export` statements, building a dependency graph, (2) **links** imports to exports (that's why a misspelled named import fails before any code runs), and (3) **evaluates** each module once, dependencies first.

**Static structure** lets tools do **tree shaking**: bundlers see which exports are never imported and remove them from the final bundle. CommonJS's dynamic `require` makes this much harder.

**Package resolution.** A bare specifier like `"react"` is looked up in `node_modules`. A package's `package.json` `"exports"` field controls which files can be imported and can provide different entry points for `import` and `require`.

**`import.meta`.** `import.meta.url` is the current module's URL; Node 20+ adds `import.meta.dirname` and `import.meta.filename` (the ESM replacement for `__dirname`).

**JSON and other imports.** `import data from "./data.json" with { type: "json" }` (import attributes). Bundlers also let you import CSS, images and more.

**Node can `require()` ES modules** in recent versions (22+) when they don't use top-level await, easing migration.

</DeepDive>

<DeepDive title="Real world: the config that loaded twice">

A Node API had a `db.js` module that opened a database connection when imported, and most files imported it. During a refactor, one file imported `./db.js` and another imported `./DB.js` (different capitalisation). On the developers' Macs (case-insensitive file system) everything worked. On the Linux server, `./DB.js` failed to resolve, so someone "fixed" it by copying `db.js` to `DB.js`.

Now there were **two modules**, each opening its own connection pool. Under load, the database hit its connection limit, and requests started timing out. Meanwhile, a cache inside `db.js` was split in two, so cache invalidations from one half never reached the other: users saw stale prices.

The fix:

1. Delete the duplicate file and use one consistent path everywhere (and a lint rule that enforces matching case).
2. Move side effects out of import time: `db.js` exports a `getPool()` function that creates the pool lazily, once.
3. Add a startup log line ("db pool created") to notice duplicates immediately.

Lesson: a module is identified by its **resolved path**. Two paths mean two separate modules with separate state.

</DeepDive>

<DeepDive title="Security lens">

- **Every import runs code.** A package's top-level code executes as soon as you import it, with your app's permissions. Audit dependencies (`npm audit`), pin versions with a lockfile, and avoid unknown packages.
- **Typosquatting**: malicious packages use names close to popular ones (`expres`, `reacct`). Double-check names before installing.
- **Don't build import paths from user input** (`` import(`./plugins/${name}.js`) ``): validate against an allow-list, or attackers may load files you didn't intend.
- **Module state is shared by all requests on a server**: never keep per-user secrets or sessions in module-level variables.
- **Browser modules follow CORS** and need correct `Content-Type` headers; serving them from your own origin with a Content-Security-Policy limits what scripts can load.
- **Keep secrets out of client bundles**: anything imported into browser code ships to users (see the Vercel lesson's `server-only`).

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between named and default exports?">
A module can have many named exports, which must be imported by their exact names in curly braces, optionally renamed with as. It can have one default export, which the importer can give any name without braces.
</QA>

<QA q="What are the main differences between ES modules and CommonJS?">
ES modules use import and export, are statically analysable, load asynchronously, support top-level await, run in strict mode and work in browsers. CommonJS uses require and module.exports, loads synchronously at runtime, and is Node-specific. Node chooses based on file extension and the package.json type field.
</QA>

<QA q="What is a live binding?">
Imported names are references to the exporting module's variables, not copies. If the exporter changes the variable, importers see the new value, but importers cannot reassign it themselves.
</QA>

<QA q="Why is dynamic import useful?">
It loads a module only when the code needs it and returns a promise, enabling code splitting so rarely used features don't increase the initial load, and allowing conditional or computed module loading.
</QA>

<QA q="What is tree shaking?">
A bundler optimisation that removes exports that are never imported, made possible by the static structure of ES module import and export statements.
</QA>

</DeepDive>
