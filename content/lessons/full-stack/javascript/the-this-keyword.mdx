<BigIdea>
<Tr>
<En>
`this` is a special word that, inside a function, points to **the object the function is working for right now**. When you call `cart.total()`, inside `total` the word `this` means `cart`, so the same method can work for any cart. The key surprise: `this` is decided **when the function is called, not where it's written**. Call the same function as `cart.total()` and `this` is `cart`; pass it somewhere and call it as plain `total()` and `this` is `undefined`. There are only a few rules: the object **before the dot**, `new`, explicit `call`/`apply`/`bind`, and nothing (undefined). **Arrow functions** are the exception: they don't have their own `this` at all and use the `this` of the code around them. Knowing these rules ends the most confusing bug in JavaScript: "Cannot read properties of undefined".
</En>
<Ur>
`this` ek khaas lafz hai jo function ke andar **us object ki taraf ishara karta hai jis ke liye function is waqt kaam kar raha hai**. Jab aap `cart.total()` call karte hain, `total` ke andar `this` ka matlab `cart` hai, isliye wahi method kisi bhi cart ke liye kaam kar sakta hai. Ahem hairani: `this` **function call hone ke waqt tay hota hai, likhne ki jagah se nahi**. Wahi function `cart.total()` ki tarah call karein to `this` `cart` hai; use kahin bhej kar saade `total()` ki tarah call karein to `this` `undefined` hai. Sirf chand qawaid hain: **dot se pehle wala** object, `new`, wazeh `call`/`apply`/`bind`, aur kuch nahi (undefined). **Arrow functions** istisna hain: in ka apna `this` hota hi nahi aur ye ird gird ke code ka `this` istemal karte hain. Ye qawaid jaanna JavaScript ka sab se uljha hua bug khatam kar deta hai: "Cannot read properties of undefined".
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **Objects and classes rely on `this`** to reach their own data. You'll use it in every class you write.
- **"Lost `this`" is a top beginner bug**: passing `user.save` to a button or a timer and getting `undefined`.
- **Arrow vs regular functions** behave differently here, and choosing the right one fixes most problems instantly.
- **It's an interview favourite**: "what does this print?" questions are almost always about `this`.

</En>
<Ur>

- **Objects aur classes apne data tak pohanchne ke liye `this` par chalte hain.** Aap har class me ise istemal karenge.
- **"Khoya hua `this`" shuruati bugs me sar-e-fehrist hai**: `user.save` ko button ya timer ko de dena aur `undefined` milna.
- **Arrow aur aam functions** yahan mukhtalif bartao karte hain, aur sahi chunna zyada tar masail foran theek kar deta hai.
- **Interview ka pasandeeda hai**: "ye kya print karega?" wale sawal taqreeban hamesha `this` ke baare me hote hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| You're writing… | Use |
| --- | --- |
| A method that reads the object's data | Regular method syntax `name() { … this … }` |
| A callback inside a method (`forEach`, `setTimeout`, `then`) | Arrow function, so it keeps the method's `this` |
| A method you'll pass around as a callback | `bind` it once, or make it an arrow-function class field |
| A function that never needs `this` | Arrow or regular, either is fine |

</En>
<Ur>

| --- | --- |

| Method jise callback ki tarah aage bhejenge | Ek dafa `bind` karein, ya arrow-function class field banayen |
| Function jise kabhi `this` nahi chahiye | Arrow ya aam, dono theek |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Find the call site: how is this function being called **right now**?
2. Object before the dot? That's `this`. `new`? The new object. `call`/`apply`/`bind`? The first argument.
3. Arrow function? Ignore the call; look **outside** the arrow for `this`.
4. None of these? `this` is `undefined` (in modules, classes and strict mode).

</En>
<Ur>

1. Call ki jagah dhoondein: ye function **abhi** kaise call ho raha hai?
2. Dot se pehle object? Wahi `this` hai. `new`? Naya object. `call`/`apply`/`bind`? Pehla argument.
3. Arrow function? Call ko nazarandaz karein; `this` ke liye arrow ke **bahar** dekhein.
4. In me se kuch nahi? `this` `undefined` hai (modules, classes aur strict mode me).

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

`this` is like the word **"my"** in a phone call script that many people use.

- A support script says: "Please read **my** account number." The script is the same for everyone. Who "my" refers to depends on **who is reading it at that moment**, not who wrote the script.
- When Alex reads it (`alex.readScript()`), "my" means Alex. When Sam reads it (`sam.readScript()`), "my" means Sam.
- If the script is **photocopied and left on a table** (`const s = alex.readScript`) and someone reads it out loud with no caller on the line (`s()`), "my" means **nobody**: `undefined`.
- **`bind`** is writing the name on the page: "**Alex's** account number". Now it means Alex no matter who reads it.
- An **arrow function** is a sticky note inside Alex's script. It doesn't have its own "my"; it uses whatever "my" means in the script it's stuck to.

</En>
<Ur>

`this` phone call ke us script me lafz **"mera"** jaisa hai jise bohot log istemal karte hain.

- Support script kehta hai: "Barah-e-meharbani **mera** account number parhein." Script sab ke liye ek hai. "Mera" kis ki taraf ishara karta hai ye is par munhasir hai ke **us lamhe kaun parh raha hai**, script kis ne likha is par nahi.
- Jab Alex parhe (`alex.readScript()`), "mera" ka matlab Alex. Jab Sam parhe (`sam.readScript()`), "mera" ka matlab Sam.
- Agar script ki **photocopy kar ke mez par chhor di** jaye (`const s = alex.readScript`) aur koi use line par kisi caller ke baghair zor se parhe (`s()`), to "mera" ka matlab **koi nahi**: `undefined`.
- **`bind`** page par naam likh dena hai: "**Alex ka** account number". Ab koi bhi parhe, matlab Alex hi hai.
- **Arrow function** Alex ke script ke andar chipka sticky note hai. Is ka apna "mera" nahi; ye wahi matlab leta hai jo us script me hai jis par ye chipka hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="this in a method">

<Tr>
<En>
A method uses `this` to reach the object it belongs to. Because `this` is filled in at call time, **one function can be shared** by many objects and still read each one's data.
</En>
<Ur>
Method apne object tak pohanchne ke liye `this` istemal karta hai. Chunke `this` call ke waqt bhara jata hai, **ek function bohot se objects me share** ho sakta hai aur phir bhi har ek ka data parh sakta hai.
</Ur>
</Tr>

```javascript
function describe() {
  return `${this.name}: $${this.price}`;
}

const mug = { name: "Mug", price: 8, describe };
const lamp = { name: "Lamp", price: 30, describe };

console.log(mug.describe());
console.log(lamp.describe());
console.log(mug.describe === lamp.describe);
```

```text output
Mug: $8
Lamp: $30
true
```

<Happened>
<Tr>
<En>

- `mug.describe` and `lamp.describe` are the **same function** (`===` is true), yet they printed different things.
- When called as `mug.describe()`, the object before the dot is `mug`, so `this.name` is "Mug". Called as `lamp.describe()`, `this` is `lamp`.
- This is how methods on classes and prototypes work: one function, many objects.

</En>
<Ur>

- `mug.describe` aur `lamp.describe` **ek hi function** hain (`===` true hai), phir bhi in ne mukhtalif cheezen print kin.
- `mug.describe()` ki tarah call hone par dot se pehle `mug` hai, isliye `this.name` "Mug" hai. `lamp.describe()` ki tarah call hone par `this` `lamp` hai.
- Classes aur prototypes ke methods aise hi kaam karte hain: ek function, bohot se objects.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Losing this">

<Tr>
<En>
If you take a method **off** its object and call it on its own, there's no object before the dot. In modern JavaScript (modules, classes, strict mode) `this` is then `undefined`, and reading `this.anything` crashes.
</En>
<Ur>
Agar aap method ko us ke object se **utaar** kar akela call karein, to dot se pehle koi object nahi hota. Jadeed JavaScript (modules, classes, strict mode) me `this` phir `undefined` hota hai, aur `this.anything` parhna crash karta hai.
</Ur>
</Tr>

```javascript
const counter = {
  count: 0,
  increment() {
    this.count++;
    return this.count;
  },
};

console.log(counter.increment());

const inc = counter.increment;
try {
  inc();
} catch (error) {
  console.log(error.name + ": " + error.message);
}

function runTwice(callback) {
  callback();
  callback();
}
try {
  runTwice(counter.increment);
} catch (error) {
  console.log("as a callback → " + error.message);
}

console.log("count is still", counter.count);
```

```text output
1
TypeError: Cannot read properties of undefined (reading 'count')
as a callback → Cannot read properties of undefined (reading 'count')
count is still 1
```

<Happened>
<Tr>
<En>

- `counter.increment()` worked: `this` was `counter`.
- `const inc = counter.increment` copied **only the function**. Calling `inc()` has no object before the dot, so `this` was `undefined` and `this.count` crashed.
- Passing `counter.increment` to `runTwice` is the same thing: inside `runTwice` it's called as plain `callback()`. This is exactly what happens when you pass a method to `setTimeout`, `addEventListener` or a React `onClick`.
- The function didn't "remember" `counter`. A regular function only gets `this` from **how it's called**.

</En>
<Ur>

- `counter.increment()` chal gaya: `this` `counter` tha.
- `const inc = counter.increment` ne **sirf function** copy kiya. `inc()` call karne me dot se pehle koi object nahi, isliye `this` `undefined` tha aur `this.count` crash hua.
- `counter.increment` ko `runTwice` me bhejna bhi yahi hai: `runTwice` ke andar ye saade `callback()` ki tarah call hota hai. Bilkul yahi hota hai jab aap method ko `setTimeout`, `addEventListener` ya React ke `onClick` me bhejte hain.
- Function ne `counter` ko "yaad" nahi rakha. Aam function `this` sirf **call ke tareeqe** se leta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Fix it with bind or an arrow wrapper">

<Tr>
<En>
Two common fixes. **`bind(obj)`** returns a new function whose `this` is locked to `obj` forever. Or wrap the call in an **arrow function** `() => obj.method()`, so the method is still called with its object before the dot.
</En>
<Ur>
Do aam hal. **`bind(obj)`** naya function deta hai jis ka `this` hamesha ke liye `obj` par band hai. Ya call ko **arrow function** `() => obj.method()` me lapetein, taa ke method ab bhi dot se pehle apne object ke saath call ho.
</Ur>
</Tr>

```javascript
const counter = {
  count: 0,
  increment() {
    this.count++;
    return this.count;
  },
};

function runTwice(callback) {
  callback();
  callback();
}

runTwice(counter.increment.bind(counter));
console.log("after bind:", counter.count);

runTwice(() => counter.increment());
console.log("after arrow wrapper:", counter.count);

const boundInc = counter.increment.bind(counter);
const other = { count: 100, boundInc };
console.log(other.boundInc(), counter.count, other.count);
```

```text output
after bind: 2
after arrow wrapper: 4
5 5 100
```

<Happened>
<Tr>
<En>

- Both fixes worked: the count went 0 → 2 → 4.
- A bound function **ignores** the object before the dot: `other.boundInc()` still changed `counter` (now 5), and `other.count` stayed 100.
- The arrow wrapper is often the most readable choice for one-off callbacks. `bind` is handy when you pass the same method many times.

</En>
<Ur>

- Dono hal kaam kar gaye: count 0 → 2 → 4 gaya.
- Bound function dot se pehle wale object ko **nazarandaz** karta hai: `other.boundInc()` ne phir bhi `counter` badla (ab 5), aur `other.count` 100 raha.
- Ek baar ke callbacks ke liye arrow wrapper aksar sab se zyada parhne layaq hai. Jab wahi method bohot dafa bhejna ho to `bind` kaam ka hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Arrow functions borrow this from outside">

<Tr>
<En>
An arrow function has **no `this` of its own**. Inside it, `this` means whatever `this` meant **where the arrow was written**. That makes arrows perfect for callbacks inside methods, and wrong for methods themselves.
</En>
<Ur>
Arrow function ka **apna `this` nahi hota**. Is ke andar `this` ka wahi matlab hai jo **jahan arrow likha gaya** wahan `this` ka tha. Is wajah se arrows methods ke andar callbacks ke liye behtareen hain, aur khud methods ke liye ghalat.
</Ur>
</Tr>

```javascript
const shop = {
  name: "Acme",
  products: ["Mug", "Lamp"],
  listRegular() {
    return this.products.map(function (p) {
      return this ? this.name + " sells " + p : "this is " + this;
    });
  },
  listArrow() {
    return this.products.map((p) => this.name + " sells " + p);
  },
  arrowMethod: () => typeof this,
};

console.log(shop.listRegular());
console.log(shop.listArrow());
console.log(shop.arrowMethod());
```

```text output
[ 'this is undefined', 'this is undefined' ]
[ 'Acme sells Mug', 'Acme sells Lamp' ]
undefined
```

<Happened>
<Tr>
<En>

- In `listRegular`, the `function (p) { … }` callback is called by `map` as a plain function, so its own `this` is `undefined`, even though the method's `this` is `shop`.
- In `listArrow`, the arrow has no `this`, so it uses the method's `this`: `shop`. **This is the main reason arrow functions exist.**
- `arrowMethod` is an arrow used **as a method**. It takes `this` from outside the object (the module's top level, where `this` is `undefined`), not from `shop`. Don't write methods as arrows in object literals.
- Before arrows, people wrote `const self = this;` above the callback. You'll still see that in older code.

</En>
<Ur>

- `listRegular` me `function (p) { … }` callback ko `map` saade function ki tarah call karta hai, isliye us ka apna `this` `undefined` hai, halanke method ka `this` `shop` hai.
- `listArrow` me arrow ka `this` nahi, isliye ye method ka `this` leta hai: `shop`. **Arrow functions ke hone ki yahi asal wajah hai.**
- `arrowMethod` ek arrow hai jo **method ki tarah** istemal hua. Ye `this` object ke bahar se leta hai (module ka top level, jahan `this` `undefined` hai), `shop` se nahi. Object literals me methods arrows ki shakal me na likhein.
- Arrows se pehle log callback ke upar `const self = this;` likhte the. Purane code me ye ab bhi milega.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="call, apply and bind">

<Tr>
<En>
Every regular function has three methods for choosing `this` yourself. **`call(thisArg, a, b)`** calls it now with arguments listed. **`apply(thisArg, [a, b])`** calls it now with arguments in an array. **`bind(thisArg, a)`** doesn't call it; it returns a new function with `this` (and optionally some arguments) fixed.
</En>
<Ur>
Har aam function ke paas khud `this` chunne ke teen methods hain. **`call(thisArg, a, b)`** ise abhi arguments ki list ke saath call karta hai. **`apply(thisArg, [a, b])`** abhi array me arguments ke saath call karta hai. **`bind(thisArg, a)`** call nahi karta; ye naya function deta hai jis ka `this` (aur chahein to kuch arguments) tay hain.
</Ur>
</Tr>

```javascript
function introduce(greeting, punctuation) {
  return greeting + ", I'm " + this.name + punctuation;
}

const alex = { name: "Alex" };
const sam = { name: "Sam" };

console.log(introduce.call(alex, "Hi", "!"));
console.log(introduce.apply(sam, ["Hello", "."]));

const samIntro = introduce.bind(sam, "Hey");
console.log(samIntro("?"));
console.log(samIntro.call(alex, "!"));
```

```text output
Hi, I'm Alex!
Hello, I'm Sam.
Hey, I'm Sam?
Hey, I'm Sam!
```

<Happened>
<Tr>
<En>

- `call` and `apply` do the same job; only the way you pass arguments differs ("**c**all = **c**ommas, **a**pply = **a**rray").
- `bind(sam, "Hey")` fixed both `this` and the first argument, so `samIntro("?")` only needed the punctuation. Pre-filling arguments like this is called **partial application**.
- Once bound, `this` can't be changed again, not even with `call(alex)`: it still said "Sam".
- These only affect regular functions. Arrows ignore `call`/`apply`/`bind` for `this`.

</En>
<Ur>

- `call` aur `apply` ek hi kaam karte hain; bas arguments dene ka tareeqa mukhtalif hai ("**c**all = **c**ommas, **a**pply = **a**rray").
- `bind(sam, "Hey")` ne `this` aur pehla argument dono tay kar diye, isliye `samIntro("?")` ko sirf punctuation chahiye tha. Is tarah arguments pehle se bharna **partial application** kehlata hai.
- Ek dafa bind hone ke baad `this` dobara nahi badal sakta, `call(alex)` se bhi nahi: ye ab bhi "Sam" keh raha tha.
- Ye sirf aam functions par asar karte hain. Arrows `this` ke liye `call`/`apply`/`bind` ko nazarandaz karte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="this with new and classes">

<Tr>
<En>
When you call a function with **`new`**, JavaScript creates a fresh empty object, sets `this` to it, runs the function, and returns it. Classes work the same way. Class methods are regular functions, so they can lose `this` too; **arrow-function class fields** are bound to the instance automatically.
</En>
<Ur>
Jab aap function ko **`new`** ke saath call karte hain, JavaScript ek naya khaali object banati hai, `this` ko us par set karti hai, function chalati hai, aur use wapas karti hai. Classes bhi aise hi chalti hain. Class methods aam functions hain, isliye ye bhi `this` kho sakte hain; **arrow-function class fields** khud instance se bandhe hote hain.
</Ur>
</Tr>

```javascript
function Product(name, price) {
  this.name = name;
  this.price = price;
}
const p = new Product("Mug", 8);
console.log(p, p instanceof Product);

class Timer {
  seconds = 0;
  tickArrow = () => {
    this.seconds++;
    return this.seconds;
  };
  tickMethod() {
    this.seconds++;
    return this.seconds;
  }
}

const t = new Timer();
const { tickArrow, tickMethod } = t;
console.log(tickArrow(), tickArrow());
try {
  tickMethod();
} catch (error) {
  console.log("tickMethod:", error.message);
}
console.log(Object.keys(t));
```

```text output
Product { name: 'Mug', price: 8 } true
1 2
tickMethod: Cannot read properties of undefined (reading 'seconds')
[ 'seconds', 'tickArrow' ]
```

<Happened>
<Tr>
<En>

- `new Product(…)` made `this` the new object, so `this.name = name` filled it in.
- `tickArrow` is a **class field** holding an arrow function. It's created per instance inside the constructor, where `this` is the instance, so it keeps working even when pulled off the object.
- `tickMethod` lives on the class's prototype and is a regular method, so pulling it off lost `this`.
- `Object.keys(t)` shows the trade-off: `tickArrow` is copied onto **every** instance (more memory), while `tickMethod` is shared. Use arrow fields for methods you pass as callbacks, like event handlers.

</En>
<Ur>

- `new Product(…)` ne `this` ko naya object banaya, isliye `this.name = name` ne use bhar diya.
- `tickArrow` ek **class field** hai jis me arrow function hai. Ye har instance ke liye constructor ke andar banta hai, jahan `this` instance hai, isliye object se utaarne par bhi chalta rehta hai.
- `tickMethod` class ke prototype par rehta hai aur aam method hai, isliye utaarne par `this` kho gaya.

## Common mistakes

<Compare>
<Bad title="Arrow function as an object method">

```javascript

  name: "Alex",

};

```

```text output
Hi, nobody
```

</Bad>
<Good title="Method syntax">

```javascript

  name: "Alex",
  greet() {

  },
};

```

```text output
Hi, Alex
```

</Good>
</Compare>

<Compare>
<Bad title="Regular callback inside a method">

```javascript
const team = {
  name: "Core",
  members: ["Ana", "Ben"],
  list() {
    return this.members.map(function (m) {
      return m + " (" + (this?.name ?? "?") + ")";
    });
  },
};
console.log(team.list());
```

```text output
[ 'Ana (?)', 'Ben (?)' ]
```

</Bad>
<Good title="Arrow callback keeps the method's this">

```javascript
const team = {
  name: "Core",
  members: ["Ana", "Ben"],
  list() {
    return this.members.map((m) => m + " (" + this.name + ")");
  },
};
console.log(team.list());
```

```text output
[ 'Ana (Core)', 'Ben (Core)' ]
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Passing `obj.method` as a callback** (`setTimeout(obj.save, 100)`, `button.onclick = obj.save`). Use `() => obj.save()` or `obj.save.bind(obj)`.
- **Calling `bind` inside a render loop** to create a new function every time when one bound function (or an arrow class field) would do.
- **Expecting `call`/`bind` to change an arrow's `this`**. They can't.
- **Destructuring methods** (`const { save } = obj; save();`): same as pulling the method off.
- **Using `this` in a function that isn't a method** at all. Pass the value as a parameter instead.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`obj.method` ko callback ki tarah bhejna** (`setTimeout(obj.save, 100)`, `button.onclick = obj.save`). `() => obj.save()` ya `obj.save.bind(obj)` lein.
- **Render loop ke andar `bind` call kar ke** har dafa naya function banana jab ek bound function (ya arrow class field) kaafi ho.
- **Ye umeed rakhna ke `call`/`bind` arrow ka `this` badal denge.** Ye nahi badal sakte.
- **Methods ko destructure karna** (`const { save } = obj; save();`): method utaarne jaisa hi hai.
- **Aise function me `this` istemal karna** jo method hai hi nahi. Is ke bajaye value parameter ki shakal me bhejein.

</Ur>
</Tr>

<DeepDive title="The rules in priority order">

When several rules could apply, this order decides:

1. **Arrow function?** `this` comes from the surrounding scope. Nothing below applies.
2. **Called with `new`?** `this` is the new object (even if the function was bound).
3. **Bound with `bind`?** `this` is the bound value.
4. **Called with `call`/`apply`?** `this` is the first argument.
5. **Called as `obj.fn()`?** `this` is `obj`.
6. **Plain call?** `undefined` in strict mode, the global object in sloppy mode.

**Sloppy mode boxing.** In sloppy mode, `call(5)` turns `this` into a `Number` object, and `call(null)` becomes the global object. Strict mode keeps the exact value.

**`this` in getters and setters** is the object being read or written, so `get total() { return this.items.length; }` works like a method.

**`super` and `this` in classes.** In a subclass constructor you must call `super(…)` before using `this`, because the parent creates the object.

**React.** Function components don't use `this` at all; hooks replaced it. Older class components needed `this.handleClick = this.handleClick.bind(this)` in the constructor, or arrow class fields.

</DeepDive>

<DeepDive title="Real world: the save button that saved nothing">

A team built a form helper class:

```text
class FormStore {
  values = {};
  save() { return fetch("/api/profile", { method: "POST", body: JSON.stringify(this.values) }); }
}
const store = new FormStore();
saveButton.addEventListener("click", store.save);
```

Nobody expected the bug it caused. Clicking Save didn't crash: the listener was a regular method, so it got the **button** as `this`, so `this.values` was `undefined`, and `JSON.stringify(undefined)` produced `undefined`. The request went out with **no body**, and the server, which treated a missing body as "no changes", returned 200 OK. Users saw "Saved!" while nothing was saved.

The fix:

1. Pass a wrapper: `addEventListener("click", () => store.save())`.
2. Make `save` an arrow class field, so it can't lose `this` again.
3. On the server, reject a missing or invalid body with **400** instead of accepting it.
4. Add a test that clicks the real button and checks the saved data.

Lesson: lost `this` doesn't always crash. Sometimes it silently uses the **wrong object**. Validate on the server too.

</DeepDive>

<DeepDive title="Security lens">

- **Bound and arrow callbacks keep their object**, which is what you want; but be careful when passing methods of privileged objects (for example, an admin API client) into code you don't control. Whoever calls the function acts with that object's power.
- **`call`/`apply` let any caller choose `this`** for regular functions. Don't make security decisions from `this` inside utilities that external code can call with a fake object (`isAdmin.call({ role: "admin" })`). Pass trusted values explicitly or use closures/private fields (`#token`).
- **Sloppy-mode `this` falling back to `window`** used to let functions accidentally read or create global variables. Use modules or `"use strict"` everywhere.
- **Private class fields** (`#secret`) can't be reached through a borrowed `this` from outside the class body, unlike normal properties.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How is the value of this determined in JavaScript?">
For regular functions it is determined by the call site: new binding gives the new object, explicit binding with call, apply or bind gives the provided value, implicit binding gives the object before the dot, and a default plain call gives undefined in strict mode or the global object in sloppy mode. Arrow functions take this lexically from the enclosing scope.
</QA>

<QA q="What is the difference between call, apply and bind?">
call and apply invoke the function immediately with a given this; call takes arguments individually and apply takes them as an array. bind returns a new function with this and optionally leading arguments permanently set, without calling it.
</QA>

<QA q="Why do methods lose this when passed as callbacks?">
Passing obj.method passes only the function reference. The receiving code later calls it as a plain function without the object, so there is no implicit binding and this becomes undefined or the global object.
</QA>

<QA q="Why should you not use arrow functions as object methods?">
Arrow functions do not have their own this, so this inside them refers to the scope where the object literal was written rather than the object, which is usually undefined or the global object.
</QA>

<QA q="What does this refer to inside an event listener?">
For a regular function listener, this is the element the listener is attached to, the same as event.currentTarget. For an arrow function, this is inherited from the surrounding scope.
</QA>

</DeepDive>
