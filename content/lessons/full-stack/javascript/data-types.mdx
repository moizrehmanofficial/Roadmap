<BigIdea>
<Tr>
<En>
Every value in JavaScript has a **type**: the *kind* of thing it is. Text is a **string**, `42` is a **number**, `true` is a **boolean**. The type decides what you can do with a value: numbers can be added, strings can be joined. There are **7 simple (primitive) types**: string, number, boolean, undefined, null, bigint and symbol, plus **objects** (which include arrays and functions). You check a type with **`typeof`**. JavaScript sometimes changes a type for you automatically (**coercion**), which is why `"5" + 1` gives `"51"`. To stay safe: convert on purpose with `Number()` and `String()`, and compare with **`===`**, never `==`.
</En>
<Ur>
JavaScript me har value ki ek **type** hoti hai: yaani wo *kis qisam* ki cheez hai. Text **string** hai, `42` **number** hai, `true` **boolean** hai. Type tay karti hai ke value ke saath kya kiya ja sakta hai: numbers jore ja sakte hain, strings mila kar lambi ki ja sakti hain. **7 saada (primitive) types** hain: string, number, boolean, undefined, null, bigint aur symbol, aur in ke ilawa **objects** (jin me arrays aur functions bhi shamil hain). Type **`typeof`** se check hoti hai. JavaScript kabhi kabhi khud hi type badal deta hai (**coercion**), isi liye `"5" + 1` ka jawab `"51"` aata hai. Mehfooz rehne ke liye: `Number()` aur `String()` se khud jaan boojh kar badlein, aur muqabla hamesha **`===`** se karein, `==` se kabhi nahi.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

A **data type** is the kind of a value. JavaScript has these:

| Type | What it holds | Example |
| --- | --- | --- |
| **string** | Text | `"Sara"`, `'hi'` |
| **number** | Whole numbers and decimals | `25`, `9.99`, `-3` |

| **undefined** | "Nothing has been put here yet" | `let x;` |

| **symbol** | A one-of-a-kind label (advanced) | `Symbol("id")` |
| **object** | A group of values: objects, arrays, functions | `{ name: "Sara" }`, `[1, 2]` |

</What>
<Why>
<Tr>
<En>

- **The same symbol does different things for different types.** `5 + 1` is `6`, but `"5" + 1` is `"51"`. If you don't know the type, you can't predict the result.
- **Data from outside is almost always text.** Whatever a user types in a form, and whatever comes from a URL, arrives as a string, even if it looks like a number.
- **Most beginner bugs are type bugs:** a total that shows `"10020"` instead of `120`, a check that is always true, a page that shows `undefined` or `NaN`.

</En>
<Ur>

- **Ek hi nishaan alag types par alag kaam karta hai.** `5 + 1` ka jawab `6` hai, magar `"5" + 1` ka `"51"`. Type maloom na ho to nateeja pehle se nahi bataya ja sakta.
- **Bahar se aane wala data taqreeban hamesha text hota hai.** User form me jo bhi likhe, aur URL se jo bhi aaye, wo string ban kar aata hai, chahe dekhne me number lage.
- **Naye seekhne walon ke zyada tar bugs type ke bugs hote hain:** total jo `120` ke bajaye `"10020"` dikhaye, check jo hamesha sach nikle, page jo `undefined` ya `NaN` dikhaye.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

You think about types **all the time**, but especially when:

- reading input from a form, a URL or a file (it's text; convert it),
- doing maths with values you didn't create yourself,
- comparing two values (`===`),
- a value might be missing (`undefined` or `null`).

</En>
<Ur>

Types ke baare me **har waqt** sochna parta hai, magar khaas taur par jab:

- form, URL ya file se input parhein (wo text hota hai; use badlein),
- aisi values par hisaab karein jo aap ne khud nahi banayin,
- do values ka muqabla karein (`===`),
- koi value ghayab ho sakti ho (`undefined` ya `null`).

</Ur>
</Tr>
</When>

```js
String(42)         // "42"       - number to text, on purpose
5 === "5"          // false      - compare value AND type
```

</En>
<Ur>

```js
typeof "Sara"      // "string"   - type poochna
Number("42")       // 42         - text se number, jaan boojh kar
String(42)         // "42"       - number se text, jaan boojh kar
5 === "5"          // false      - value AUR type dono ka muqabla
```

</Ur>

## Picture it

<Tr>
<En>

Think of a **kitchen**. You have different kinds of things: **liquids**, **powders**, **eggs**. The kind matters: you can *pour* a liquid, but you can't pour an egg; you can *crack* an egg, but not flour. If someone hands you a closed jar, the first thing you do is **read the label** to see what kind of thing is inside. In JavaScript, `typeof` is reading the label.

Now imagine a helper who, when you ask to "mix water and flour", quietly turns the water into powder first because they guessed that's what you meant. Sometimes the guess is right; sometimes you get a mess. That helper is **type coercion**: JavaScript guessing and converting types for you. A careful cook doesn't let the helper guess. They convert things themselves, on purpose.

</En>
<Ur>

Ek **kitchen** ka sochein. Aap ke paas alag alag qisam ki cheezen hain: **paani jaisi cheezen**, **powder**, **ande**. Qisam ahem hai: paani *undela* ja sakta hai, anda nahi; anda *tora* ja sakta hai, aata nahi. Koi aap ko band dabba pakraye to sab se pehle aap **label parhte** hain ke andar kis qisam ki cheez hai. JavaScript me `typeof` label parhna hai.

Ab ek madadgaar ka sochein jo "paani aur aata milao" sun kar chupke se pehle paani ko powder bana deta hai, kyun ke us ne andaza lagaya ke aap yahi chahte the. Kabhi andaza theek nikalta hai; kabhi sab gadbad ho jata hai. Ye madadgaar **type coercion** hai: JavaScript ka khud andaza laga kar type badal dena. Samajhdar bawarchi madadgaar ko andaza nahi lagane deta. Wo cheezen khud, jaan boojh kar badalta hai.

</Ur>
</Tr>

<En>

<Step title="Strings: text in quotes">

<Tr>
<En>
A string is any text between quotes. You can use double quotes `"…"`, single quotes `'…'` or backticks `` `…` ``. Backticks are special: inside them, `${name}` gets replaced by the value of `name`. Every string knows how long it is: `.length`.
</En>
<Ur>
String quotes ke darmiyan ka koi bhi text hai. Double quotes `"…"`, single quotes `'…'` ya backticks `` `…` `` teeno chalte hain. Backticks khaas hain: in ke andar `${name}` ki jagah `name` ki value aa jati hai. Har string ko apni lambai maloom hoti hai: `.length`.
</Ur>
</Tr>

```javascript
const firstName = "Sara";
const city = 'Austin';
const message = `Hi, I am ${firstName} from ${city}.`;

console.log(message);
console.log(firstName.length);
console.log(typeof "25");
```

```text output
Hi, I am Sara from Austin.
4
string
```

<Happened>
<Tr>
<En>

- Double and single quotes do exactly the same job. Pick one and stay consistent.
- The backtick string filled in `${firstName}` and `${city}` with the real values. This is called a **template literal**.
- `"Sara"` has 4 characters, so `.length` is `4`.
- **Important:** `"25"` is in quotes, so it is a **string**, not a number. It's the text made of the characters 2 and 5. Quotes always mean text.

</En>
<Ur>

- Double aur single quotes bilkul ek hi kaam karte hain. Ek chunein aur usi par rahein.
- Backtick wali string ne `${firstName}` aur `${city}` ki jagah asli values bhar din. Ise **template literal** kehte hain.
- `"Sara"` me 4 characters hain, isliye `.length` `4` hai.
- **Ahem:** `"25"` quotes me hai, isliye ye **string** hai, number nahi. Ye 2 aur 5 ke characters se bana text hai. Quotes ka matlab hamesha text.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Numbers: one type for everything">

<Tr>
<En>
Many languages have separate types for whole numbers and decimals. JavaScript has just **one**: `number`. It covers whole numbers, decimals and negatives. It also has two unusual members: `Infinity`, and `NaN` ("Not a Number"), which is what you get when maths makes no sense.
</En>
<Ur>
Kai languages me poore numbers aur decimals ki alag types hoti hain. JavaScript me sirf **ek** hai: `number`. Is me poore numbers, decimals aur manfi numbers sab aate hain. Is ke do ajeeb member bhi hain: `Infinity`, aur `NaN` ("Not a Number"), jo tab milta hai jab hisaab ka koi matlab na bane.
</Ur>
</Tr>

```javascript
console.log(10 + 5);
console.log(9.99 * 2);
console.log(10 / 4);
console.log(1 / 0);
console.log("cat" * 2);
console.log(typeof NaN);
console.log(0.1 + 0.2);
```

```text output
15
19.98
2.5
Infinity
NaN
number
0.30000000000000004
```

<Happened>
<Tr>
<En>

- Whole numbers and decimals mix freely: `10 / 4` is `2.5`, not `2`.
- Dividing by zero doesn't crash; it gives `Infinity`.
- `"cat" * 2` can't be worked out, so the answer is `NaN`. Funny but true: the type of `NaN` is still `number`. Think of it as "a number-shaped error".
- `0.1 + 0.2` is not exactly `0.3`. Computers store decimals in binary and some can't be stored exactly, like 1/3 in ordinary decimals (0.333…). This happens in almost every programming language. **For money, work in cents** (whole numbers): `10 + 20` cents is exactly `30`.

</En>
<Ur>

- Poore numbers aur decimals aaram se milte hain: `10 / 4` ka jawab `2.5` hai, `2` nahi.
- Zero se taqseem karne par program rukta nahi; `Infinity` milta hai.
- `"cat" * 2` ka hisaab ho hi nahi sakta, isliye jawab `NaN` hai. Ajeeb magar sach: `NaN` ki type phir bhi `number` hai. Ise "number ki shakal wala error" samjhein.
- `0.1 + 0.2` bilkul `0.3` nahi. Computer decimals ko binary me rakhta hai aur kuch decimals poori tarah nahi rakhe ja sakte, jaise aam ginti me 1/3 (0.333…). Ye taqreeban har programming language me hota hai. **Paison ke liye cents me kaam karein** (poore numbers): `10 + 20` cents bilkul `30` hote hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Booleans: yes or no">

<Tr>
<En>
A boolean has only two possible values: `true` and `false`. You rarely type them yourself. Mostly they are the **answer to a question**, like "is this bigger than that?"
</En>
<Ur>
Boolean ki sirf do mumkin values hain: `true` aur `false`. Inhe aap khud kam hi likhte hain. Zyada tar ye kisi **sawal ka jawab** hote hain, jaise "kya ye us se bara hai?"
</Ur>
</Tr>

```javascript
const age = 20;
const isAdult = age >= 18;
const hasTicket = false;

console.log(isAdult);
console.log(typeof isAdult);
console.log(isAdult && hasTicket);
```

```text output
true
boolean
false
```

<Happened>
<Tr>
<En>

- `age >= 18` asks "is age at least 18?" The answer, `true`, is stored in `isAdult`.
- `&&` means **and**: the result is true only if **both** sides are true. Sara is an adult but has no ticket, so the answer is `false`.
- Good boolean names read like questions: `isAdult`, `hasTicket`, `canEdit`.
- `true` (no quotes) is a boolean. `"true"` (in quotes) is a string. They are not the same thing.

</En>
<Ur>

- `age >= 18` poochta hai "kya age kam az kam 18 hai?" Jawab `true` `isAdult` me rakh diya gaya.
- `&&` ka matlab **aur** hai: nateeja tabhi true hota hai jab **dono** taraf true hon. Sara adult hai magar ticket nahi, isliye jawab `false` hai.
- Boolean ke achhe naam sawal ki tarah parhe jate hain: `isAdult`, `hasTicket`, `canEdit`.
- `true` (quotes ke baghair) boolean hai. `"true"` (quotes me) string hai. Dono ek cheez nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="undefined and null: two kinds of nothing">

<Tr>
<En>
JavaScript has two ways to say "nothing". **`undefined`** means "nobody has put a value here yet"; JavaScript uses it by itself. **`null`** means "I checked, and it is empty on purpose"; *you* write it.
</En>
<Ur>
JavaScript me "kuch nahi" kehne ke do tareeqe hain. **`undefined`** ka matlab "yahan abhi kisi ne value rakhi hi nahi"; ise JavaScript khud istemal karta hai. **`null`** ka matlab "maine dekh liya, ye jaan boojh kar khaali hai"; ise *aap* likhte hain.
</Ur>
</Tr>

```javascript
let nickname;
console.log(nickname);

const user = { name: "Sara" };
console.log(user.phone);

let selectedSeat = null;
console.log(selectedSeat);
```

```text output
undefined
undefined
null
```

<Happened>
<Tr>
<En>

- `nickname` was created but never given a value, so it's `undefined`.
- `user` has a `name` but no `phone`. Asking for something that isn't there gives `undefined`, not an error.
- `selectedSeat = null` is a message from the programmer: "there is a seat choice here, and right now it is empty."
- Picture a form: a field you **haven't reached yet** is `undefined`; a field where you wrote **"none"** is `null`.

</En>
<Ur>

- `nickname` bana to diya gaya magar value kabhi nahi di gayi, isliye `undefined` hai.
- `user` ke paas `name` hai magar `phone` nahi. Jo cheez maujood hi nahi use maangne par `undefined` milta hai, error nahi.
- `selectedSeat = null` programmer ka paighaam hai: "yahan seat ka intikhab hota hai, aur abhi ye khaali hai."
- Ek form ka sochein: jis khaane tak aap **abhi pohanche hi nahi** wo `undefined` hai; jis khaane me aap ne **"koi nahi"** likha wo `null` hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="BigInt and Symbol: the two rare ones">

<Tr>
<En>
You won't need these often, but you should recognise them. Ordinary numbers are only exact up to about 9 quadrillion (`Number.MAX_SAFE_INTEGER`). A **bigint**, written with an `n` at the end, stays exact at any size. A **symbol** is a value that is guaranteed to be unique.
</En>
<Ur>
In ki zaroorat kam parti hai, magar pehchaan honi chahiye. Aam numbers sirf taqreeban 9 quadrillion (`Number.MAX_SAFE_INTEGER`) tak bilkul durust rehte hain. **bigint**, jis ke aakhir me `n` likha jata hai, kisi bhi size par durust rehta hai. **symbol** aisi value hai jis ka apni tarah ka ek hi hona pakka hai.
</Ur>
</Tr>

```javascript
console.log(Number.MAX_SAFE_INTEGER);
console.log(9007199254740991 + 2);
console.log(9007199254740991n + 2n);
console.log(typeof 10n);

const idA = Symbol("id");
const idB = Symbol("id");
console.log(idA === idB);
console.log(typeof idA);
```

```text output
9007199254740991
9007199254740992
9007199254740993n
bigint
false
symbol
```

<Happened>
<Tr>
<En>

- Past the safe limit, an ordinary number gave a **wrong** answer: it should end in 993, but shows 992.
- The bigint version (`…991n + 2n`) is exactly right. BigInts are used for very large IDs and cryptography.
- Two symbols are never equal, even with the same description `"id"`. Libraries use them as labels that can't clash with anyone else's.

</En>
<Ur>

- Mehfooz had ke baad aam number ne **ghalat** jawab diya: aakhir me 993 hona chahiye tha, magar 992 dikha.
- bigint wala (`…991n + 2n`) bilkul sahi hai. BigInts bohot bari IDs aur cryptography me kaam aate hain.
- Do symbols kabhi barabar nahi hote, chahe description `"id"` ek hi ho. Libraries inhe aise labels ke taur par leti hain jo kisi aur ke label se takra na saken.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="typeof has two famous surprises">

<Tr>
<En>
`typeof` is reliable for strings, numbers and booleans, but it gives two answers that surprise everyone the first time.
</En>
<Ur>
`typeof` strings, numbers aur booleans ke liye bharosemand hai, magar do jawab aise deta hai jo pehli dafa har kisi ko hairan karte hain.
</Ur>
</Tr>

```javascript
console.log(typeof null);
console.log(typeof [1, 2, 3]);
console.log(typeof { name: "Sara" });
console.log(typeof function () {});

const value = null;
console.log(value === null);
console.log(Array.isArray([1, 2, 3]));
console.log(Array.isArray({ name: "Sara" }));
```

```text output
object
object
object
function
true
true
false
```

<Happened>
<Tr>
<En>

- **Surprise 1:** `typeof null` says `"object"`. This is a bug from the very first version of JavaScript in 1995. It can never be fixed, because old websites depend on it. To check for null, compare directly: `value === null`.
- **Surprise 2:** `typeof` an array also says `"object"`, because an array *is* a special kind of object. To check for an array, use `Array.isArray(value)`.
- Functions get their own answer, `"function"`, even though they are objects too.

</En>
<Ur>

- **Hairani 1:** `typeof null` `"object"` kehta hai. Ye 1995 me JavaScript ke sab se pehle version ka bug hai. Ye kabhi theek nahi ho sakta, kyun ke purani websites is par chalti hain. null check karne ke liye seedha muqabla karein: `value === null`.
- **Hairani 2:** array ka `typeof` bhi `"object"` kehta hai, kyun ke array *hai hi* ek khaas qisam ka object. Array check karne ke liye `Array.isArray(value)` lein.
- Functions ko apna jawab `"function"` milta hai, halanke wo bhi objects hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Coercion: JavaScript guesses the type for you">

<Tr>
<En>
When you mix types, JavaScript doesn't stop with an error. It quietly converts one value and carries on. This is **coercion**. The rule to remember: **`+` with a string joins text. Every other maths symbol (`-`, `*`, `/`) turns text into numbers.**
</En>
<Ur>
Jab aap types milate hain to JavaScript error de kar rukta nahi. Wo chupke se ek value badal kar aage barh jata hai. Ye **coercion** hai. Yaad rakhne wala qaida: **string ke saath `+` text jorta hai. Baqi har hisaab ka nishaan (`-`, `*`, `/`) text ko number bana deta hai.**
</Ur>
</Tr>

```javascript
console.log("5" + 1);
console.log("5" - 1);
console.log("5" * "2");
console.log(1 + 2 + "3");
console.log("3" + 1 + 2);
console.log(true + 1);
```

```text output
51
4
10
33
312
2
```

<Happened>
<Tr>
<En>

- `"5" + 1`: one side is a string, so `+` **joins**: `"5"` and `"1"` become `"51"`.
- `"5" - 1`: you can't "subtract" text, so `"5"` becomes the number 5, and the answer is `4`.
- `"5" * "2"`: both become numbers: `10`.
- `1 + 2 + "3"`: JavaScript works left to right. First `1 + 2` is `3` (numbers). Then `3 + "3"` joins: `"33"`.
- `"3" + 1 + 2`: first `"3" + 1` joins to `"31"`, then `"31" + 2` joins to `"312"`.
- `true + 1`: `true` counts as 1, so `2`.
- None of these give an error. That's exactly why coercion bugs are hard to find: the program keeps running with a wrong value.

</En>
<Ur>

- `"5" + 1`: ek taraf string hai, isliye `+` **jorta** hai: `"5"` aur `"1"` mil kar `"51"`.
- `"5" - 1`: text "ghataya" nahi ja sakta, isliye `"5"` number 5 ban jata hai, aur jawab `4`.
- `"5" * "2"`: dono number ban jate hain: `10`.
- `1 + 2 + "3"`: JavaScript baayen se daayen chalta hai. Pehle `1 + 2` ka `3` (numbers). Phir `3 + "3"` jur kar `"33"`.
- `"3" + 1 + 2`: pehle `"3" + 1` jur kar `"31"`, phir `"31" + 2` jur kar `"312"`.
- `true + 1`: `true` 1 gina jata hai, isliye `2`.
- In me se kisi par error nahi aata. Isi liye coercion ke bugs dhoondna mushkil hai: program ghalat value ke saath chalta rehta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Compare with ===, not ==">

<Tr>
<En>

</En>
<Ur>

<Happened>
<Tr>

- `!==` is the strict "not equal". Use it instead of `!=`.

</En>
<Ur>

<Step title="Primitives are copied, objects are shared">

<Tr>
<En>
The seven simple types are called **primitives**. When you copy a primitive, you get a separate copy. Objects and arrays are different: the variable holds a **link** to the object, and copying the variable copies the link, not the object.
</En>
<Ur>
Saat saada types ko **primitives** kehte hain. Primitive copy karein to alag copy milti hai. Objects aur arrays alag hain: variable me object ka **link** hota hai, aur variable copy karne se link copy hota hai, object nahi.
</Ur>
</Tr>


<Happened>
<Tr>
<En>

- `b = a` made a photocopy of the number. Changing `b` left `a` alone.
- `sameCart = cart` did **not** make a second list. Both names point to the **same** list, so adding bread through `sameCart` also shows up in `cart`.
- `[1, 2] === [1, 2]` is `false`: these are two **different** lists that happen to look alike. For objects, `===` asks "is it the very same object?", not "do they look the same?"
- `cart === sameCart` is `true`: same list, two names.

</En>
<Ur>

- `b = a` ne number ki photocopy banayi. `b` badalne se `a` par asar nahi hua.
- `sameCart = cart` ne doosri list **nahi** banayi. Dono naam **ek hi** list ki taraf ishara karte hain, isliye `sameCart` se bread dalne par wo `cart` me bhi nazar aati hai.

- `cart === sameCart` `true` hai: ek list, do naam.

</Ur>

<DeepDive title="How types work under the hood">

**Dynamic typing.** In JavaScript, types belong to **values**, not to variables. The same variable can hold a number now and a string later (`let x = 1; x = "one";`). Languages like Java or TypeScript attach types to variables and check them before the program runs; JavaScript checks nothing in advance, which is why type bugs appear at runtime.

**Primitives are immutable.** You can't change a primitive, only replace it. `"sara".toUpperCase()` returns a **new** string; the original is untouched.

**Why can a primitive have methods?** `"sara".length` works even though a string isn't an object. For a moment JavaScript wraps the primitive in a temporary object (`String`, `Number`, `Boolean`), calls the method, and throws the wrapper away. This is called **autoboxing**. Never create wrappers yourself with `new String("x")`: `typeof new String("x")` is `"object"`, and it breaks `===`.

**Numbers are 64-bit floats (IEEE 754).** There is no separate integer type. Integers are exact up to 2^53 − 1 (`Number.MAX_SAFE_INTEGER`). There are two zeros (`0` and `-0`), and `NaN !== NaN`. `Object.is(NaN, NaN)` is `true`, and `Object.is(0, -0)` is `false`.

**The full coercion rules** go through an internal step called **ToPrimitive**: for objects, JavaScript calls `valueOf()` and then `toString()`. That's why `[] + []` is `""` and `[] + {}` is `"[object Object]"`. You never need these in real code; you need to know they exist so you avoid mixing types.

**Truthy and falsy.** In an `if`, every value is treated as true or false. Exactly these are **falsy**: `false`, `0`, `-0`, `0n`, `""`, `null`, `undefined`, `NaN`. Everything else is truthy, including `"0"`, `"false"`, `[]` and `{}`.

</DeepDive>

<DeepDive title="Real world: the string that should have been a number">

A classic production bug: an online shop reads the quantity from a query string, such as `/cart?qty=2`. Everything in a URL is text. The code does `stock - qty` (works, because `-` converts) and `points + qty` (breaks, because `+` joins), so a customer with 100 points who buys 2 items ends up with `"1002"` points, which is later converted back to the number 1002.

Nothing crashes, no error is logged, and the tests that only checked subtraction pass. The fix is a rule every team adopts sooner or later: **convert and validate data at the edge of the program**, the moment it arrives from a form, URL, file or API, and reject anything that isn't what you expect.

```javascript
const qty = Number(searchParams.get("qty"));
if (!Number.isInteger(qty) || qty < 1 || qty > 99) {
  throw new Error("Invalid quantity");
}
```

This is also the main reason teams adopt **TypeScript** and validation libraries such as zod: they catch "this is a string, not a number" before the code ships.

</DeepDive>

<DeepDive title="Security lens">

Type confusion is a real source of security bugs.

- **Loose comparison in checks.** `if (user.role == 0)` or `if (token == expected)` can be true for values the author never intended (`""`, `false`, `"0"`). Always use `===` in authorization and authentication code.
- **Unexpected types in JSON.** An API expects `{ "password": "secret" }` but an attacker sends `{ "password": { "$ne": null } }`. If the server passes that object straight into a MongoDB query, it means "password is not null" and matches every user (NoSQL injection). Check that each field has the type you expect before using it.
- **Arrays where strings are expected.** In many web frameworks, `?id=1&id=2` makes `id` an array. Code that assumed a string (`id.length`, `id.includes(...)`) then behaves differently and can bypass filters.
- **Number edge cases.** `NaN`, `Infinity`, negative numbers and huge values pass a naive "is it a number?" check. A quantity of `-5` or a price of `NaN` has broken real checkout flows. Validate ranges with `Number.isInteger` and explicit minimum and maximum values.
- **Large IDs.** IDs above `Number.MAX_SAFE_INTEGER` lose precision when parsed as numbers, so two different IDs can become the same one. Keep big IDs as strings.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the primitive types in JavaScript?">
There are seven: string, number, boolean, undefined, null, bigint and symbol. Primitives are immutable and compared by value. Everything else, including arrays and functions, is an object and is compared by reference.
</QA>

<QA q="What is the difference between null and undefined?">
undefined means a value has not been assigned: an uninitialised variable, a missing property, or a function that returns nothing. null is an intentional empty value that a programmer assigns. typeof undefined is undefined, while typeof null is object, a historical bug. They are loosely equal but not strictly equal.
</QA>

<QA q="What is the difference between == and ===?">
Triple equals compares both type and value with no conversion. Double equals first converts the operands to a common type using coercion rules, which gives surprising results such as zero equalling an empty string. Use triple equals by default; the only common use of double equals is checking for both null and undefined at once with value == null.
</QA>

<QA q="Why is 0.1 + 0.2 not equal to 0.3?">
JavaScript numbers are 64-bit binary floating-point values, and 0.1 and 0.2 cannot be represented exactly in binary, so the sum has a tiny rounding error. For money, use integers such as cents, or compare with a small tolerance, or use a decimal library.
</QA>

<QA q="What is NaN and how do you check for it?">
NaN stands for Not a Number and is the result of invalid numeric operations, such as multiplying text by a number. Its type is number, and it is the only value not equal to itself, so comparing with triple equals never works. Use Number.isNaN, which returns true only for NaN.
</QA>

<QA q="What is type coercion?">
It is JavaScript automatically converting a value from one type to another during an operation. The plus operator concatenates if either operand is a string, while other arithmetic operators convert operands to numbers. Explicit conversion with Number, String and Boolean is clearer and safer than relying on coercion.
</QA>

</DeepDive>
