<BigIdea>
<Tr>
<En>
Arrays keep things **in order**; objects describe **one thing's properties**. But two jobs come up constantly that neither does well. **"Look something up by a key"**: a phone book, stock per product, a cache of results. That's a **`Map`**: keys can be **anything** (numbers, strings, even objects), it remembers insertion order, knows its `size`, and has no hidden built-in keys to trip over. **"Keep unique values and check membership fast"**: tags, visited pages, ids already processed. That's a **`Set`**: adding a duplicate does nothing, and `has()` is fast even with millions of items. Their cousins **`WeakMap`** and **`WeakSet`** use **objects** as keys and don't keep those objects alive, so you can attach extra data to objects (like DOM elements or requests) without causing memory leaks.
</En>
<Ur>
Arrays cheezen **tarteeb** se rakhti hain; objects **ek cheez ki properties** bayan karte hain. Magar do kaam musalsal aate hain jo in me se koi achhe se nahi karta. **"Key se kuch dhoondna"**: phone book, har product ka stock, nataij ka cache. Ye **`Map`** hai: keys **kuch bhi** ho sakti hain (numbers, strings, objects bhi), ye dalne ki tarteeb yaad rakhta hai, apna `size` jaanta hai, aur is me koi chhupi bani banai keys nahi jin se takraya jaye. **"Unique values rakhna aur jaldi membership check karna"**: tags, dekhe gaye pages, pehle se process hui ids. Ye **`Set`** hai: dohra daalna kuch nahi karta, aur `has()` das lakh items ke saath bhi tez hai. In ke rishtedaar **`WeakMap`** aur **`WeakSet`** **objects** ko keys ki tarah istemal karte hain aur un objects ko zinda nahi rakhte, isliye aap objects (jaise DOM elements ya requests) ke saath memory leaks paida kiye baghair izafi data jor sakte hain.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **Lookups by key are everywhere**: products by id, users by email, counts per word, results per request.
- **Objects as dictionaries have traps**: every key becomes a string, built-in names like `toString` exist already, and user-supplied keys can cause security bugs.
- **Uniqueness and fast membership checks** (`has`) are exactly what `Set` is for; checking `array.includes` in a loop gets slow quickly.
- **WeakMap prevents memory leaks** when you attach data to objects you don't own.

</En>
<Ur>

- **Key se dhoondna har jagah hai**: id se products, email se users, har lafz ki ginti, har request ke nataij.
- **Dictionaries ke taur par objects me jaal hain**: har key string ban jati hai, `toString` jaise bane banaye naam pehle se maujood hain, aur users ki di hui keys hifazat ke bugs paida kar sakti hain.
- **Unique hona aur tez membership check** (`has`) bilkul wahi hai jis ke liye `Set` hai; loop me `array.includes` check karna jaldi sust ho jata hai.
- **WeakMap memory leaks rokta hai** jab aap un objects ke saath data jorte hain jo aap ke nahi.

</Ur>
</Tr>
</Why>

## Picture it

<Tr>
<En>

- A **Map** is a **coat check**: you hand over any item (a key, which can be a coat, an umbrella, a whole suitcase), and get back exactly what's stored for it. The attendant keeps a list in the order items arrived and always knows how many there are.
- A **plain object used as a dictionary** is a coat check where every ticket is **converted to a word first** (so ticket `1` and ticket `"1"` collide), and some hooks are **already taken** by the building (`toString`, `constructor`).
- A **Set** is a **guest list at the door**: a name is either on it or not. Writing the same name twice doesn't add a second line. Checking "is Sam on the list?" is instant.
- A **WeakMap** is **sticky notes attached to guests**: the note is about that guest, and when the guest leaves the building for good, the note goes with them. Nobody has to remember to clean it up.

</En>
<Ur>

- **Map** **coat check** hai: aap koi bhi cheez dete hain (key, jo coat, chhatri, poora suitcase ho sakti hai), aur bilkul wahi wapas milta hai jo us ke liye rakha gaya. Attendant cheezon ke aane ki tarteeb se list rakhta hai aur hamesha jaanta hai ke kitni hain.
- **Dictionary ke taur par saada object** aisa coat check hai jahan har ticket **pehle lafz me badla jata** hai (isliye ticket `1` aur ticket `"1"` takrate hain), aur kuch hooks building ne **pehle se le rakhe** hain (`toString`, `constructor`).
- **Set** **darwaze par mehmanon ki list** hai: naam ya to us par hai ya nahi. Wahi naam do dafa likhna doosri line nahi jorta. "Kya Sam list par hai?" check karna foran hota hai.
- **WeakMap** **mehmanon par chipke sticky notes** hain: note us mehman ke baare me hai, aur jab mehman hamesha ke liye building chhor de to note bhi saath chala jata hai. Kisi ko use saaf karna yaad nahi rakhna parta.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Map basics">

<Tr>
<En>
Create a Map, then `set(key, value)` to add or update, `get(key)` to read, `has(key)` to check, `delete(key)` to remove. `size` counts entries. A Map is iterable: each item is a `[key, value]` pair.
</En>
<Ur>
Map banayen, phir jorne ya update karne ke liye `set(key, value)`, parhne ke liye `get(key)`, check ke liye `has(key)`, hatane ke liye `delete(key)`. `size` entries ginta hai. Map iterable hai: har item `[key, value]` jora hai.
</Ur>
</Tr>

```javascript
const stock = new Map();
stock.set("mug", 12).set("lamp", 0);
stock.set("mug", 10);
console.log(stock.get("mug"), stock.get("desk"), stock.has("lamp"), stock.size);

stock.delete("lamp");
console.log(stock);

for (const [name, qty] of stock) console.log(name, qty);
console.log([...stock.keys()], [...stock.values()], Object.fromEntries(stock));

const fromObject = new Map(Object.entries({ a: 1, b: 2 }));
console.log(fromObject);
```

```text output
10 undefined true 2
Map(1) { 'mug' => 10 }
mug 10
[ 'mug' ] [ 10 ] { mug: 10 }
Map(2) { 'a' => 1, 'b' => 2 }
```

<Happened>
<Tr>
<En>

- `set` returns the Map, so calls can be chained. Setting `"mug"` again **replaced** its value.
- `get` of a missing key returns `undefined`; `has` tells "missing" apart from "stored as `undefined`".
- `for…of` over a Map gives `[key, value]` pairs in **insertion order**; destructure them right in the loop.
- `Object.fromEntries(map)` turns a Map into an object (for JSON); `new Map(Object.entries(obj))` goes the other way.

</En>
<Ur>

- `set` Map wapas karta hai, isliye calls zanjeer ki tarah jur sakti hain. `"mug"` dobara set karne se us ki value **badal** gayi.
- Ghayab key ka `get` `undefined` deta hai; `has` "ghayab" ko "`undefined` ki shakal me mehfooz" se alag batata hai.
- Map par `for…of` **dalne ki tarteeb** se `[key, value]` jore deta hai; inhe loop me hi destructure karein.
- `Object.fromEntries(map)` Map ko object banata hai (JSON ke liye); `new Map(Object.entries(obj))` ulta karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Why not just use an object?">

<Tr>
<En>
Objects convert every key to a **string**, so different keys collide. They also come with **inherited properties** like `toString` and `constructor`, which break naive "does this key exist?" logic. A Map has neither problem.
</En>
<Ur>
Objects har key ko **string** me badalte hain, isliye mukhtalif keys takrati hain. In ke saath `toString` aur `constructor` jaisi **virasat ki properties** bhi aati hain, jo saadi "kya ye key maujood hai?" mantiq tor deti hain. Map me ye dono masail nahi.
</Ur>
</Tr>

```javascript
const viaObject = {};
viaObject[1] = "number one";
viaObject["1"] = "string one";
const user = { id: 7 };
viaObject[user] = "user data";
console.log(Object.keys(viaObject));

const viaMap = new Map();
viaMap.set(1, "number one").set("1", "string one").set(user, "user data");
console.log(viaMap.size, viaMap.get(1), viaMap.get("1"), viaMap.get(user), viaMap.get({ id: 7 }));

const counts = {};
for (const word of ["toString", "constructor", "apple"]) counts[word] = (counts[word] ?? 0) + 1;
console.log(counts.toString === 1, typeof counts.constructor);

const safe = new Map();
for (const word of ["toString", "constructor", "apple"]) safe.set(word, (safe.get(word) ?? 0) + 1);
console.log(safe);
```

```text output
[ '1', '[object Object]' ]
3 number one string one user data undefined
false string
Map(3) { 'toString' => 1, 'constructor' => 1, 'apple' => 1 }
```

<Happened>
<Tr>
<En>

- In the object, `1` and `"1"` became the **same** key (the second overwrote the first), and the `user` object became the useless string `"[object Object]"`.
- The Map kept three separate keys: the number `1`, the string `"1"` and the `user` object. A **different** object with the same contents (`{ id: 7 }`) is a different key (reference equality).
- Counting words in an object went wrong: `counts.toString` started as the **inherited function**, so `?? 0` didn't kick in and the result became a string. With a Map, every word started fresh.

</En>
<Ur>

- Object me `1` aur `"1"` **ek hi** key ban gaye (doosre ne pehle ko badal diya), aur `user` object be-faida string `"[object Object]"` ban gaya.
- Map ne teen alag keys rakhin: number `1`, string `"1"` aur `user` object. Ek jaise maal wala **doosra** object (`{ id: 7 }`) alag key hai (reference ki barabari).
- Object me lafz ginna ghalat hua: `counts.toString` shuru me **virasat ka function** tha, isliye `?? 0` lagu nahi hua aur nateeja string ban gaya. Map ke saath har lafz naye sire se shuru hua.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Counting and grouping">

<Tr>
<En>
Two everyday Map jobs: **counting** (how many times each value appears) and **grouping** (put items into buckets by some property). `Map.groupBy` and `Object.groupBy` do grouping in one call (Node 21+, modern browsers).
</En>
<Ur>
Map ke do roz ke kaam: **ginna** (har value kitni dafa aati hai) aur **groups banana** (items ko kisi property ke hisaab se baalton me daalna). `Map.groupBy` aur `Object.groupBy` ek call me groups banate hain (Node 21+, jadeed browsers).
</Ur>
</Tr>

```javascript
const words = "the cat and the hat and the bat".split(" ");
const freq = new Map();
for (const w of words) freq.set(w, (freq.get(w) ?? 0) + 1);
const top = [...freq].sort((a, b) => b[1] - a[1]).slice(0, 2);
console.log(top);

const orders = [
  { id: 1, status: "paid" },
  { id: 2, status: "pending" },
  { id: 3, status: "paid" },
];
console.log(Map.groupBy(orders, (o) => o.status));
console.log(Object.groupBy(orders, (o) => o.status));
```

```text output
[ [ 'the', 3 ], [ 'and', 2 ] ]
Map(2) {
  'paid' => [ { id: 1, status: 'paid' }, { id: 3, status: 'paid' } ],
  'pending' => [ { id: 2, status: 'pending' } ]
}
[Object: null prototype] {
  paid: [ { id: 1, status: 'paid' }, { id: 3, status: 'paid' } ],
  pending: [ { id: 2, status: 'pending' } ]
}
```

<Happened>
<Tr>
<En>

- `(freq.get(w) ?? 0) + 1` is the standard counting pattern. Spreading the Map gives `[word, count]` pairs to sort.
- `Map.groupBy` returned a Map from each status to its orders. Group keys can be anything, even objects.
- `Object.groupBy` returns a plain object **without a prototype** (`[Object: null prototype]`), so there are no inherited keys like `toString` to clash with. Use it when the result goes straight to JSON.

</En>
<Ur>

- `(freq.get(w) ?? 0) + 1` ginti ka mayari pattern hai. Map spread karne se sort karne ke liye `[word, count]` jore milte hain.
- `Map.groupBy` ne har status se us ke orders tak Map wapas kiya. Group keys kuch bhi ho sakti hain, objects bhi.
- `Object.groupBy` **prototype ke baghair** saada object deta hai (`[Object: null prototype]`), isliye `toString` jaisi virasat ki keys se takrao nahi. Jab nateeja seedha JSON me jaye to ise lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Set: unique values and fast lookups">

<Tr>
<En>
A Set stores each value **once**. `add` ignores duplicates, `has` checks membership, `delete` removes. `[...new Set(array)]` is the classic one-liner to remove duplicates. And `set.has(x)` stays fast no matter how big the set is, unlike `array.includes(x)`, which checks items one by one.
</En>
<Ur>
Set har value **ek dafa** rakhta hai. `add` dohre nazarandaz karta hai, `has` membership check karta hai, `delete` hatata hai. `[...new Set(array)]` dohre hatane ki mashhoor ek line hai. Aur `set.has(x)` set kitna bhi bara ho tez rehta hai, `array.includes(x)` ke baraks, jo items ek ek kar ke check karta hai.
</Ur>
</Tr>

```javascript
const tags = new Set(["sale", "new"]);
tags.add("sale").add("gift");
console.log(tags, tags.size, tags.has("new"));
tags.delete("new");
console.log([...tags]);

const emails = ["a@example.com", "b@example.com", "a@example.com"];
console.log([...new Set(emails)]);

const ids = Array.from({ length: 100000 }, (_, i) => i);
const idSet = new Set(ids);

let t = performance.now();
for (let i = 0; i < 2000; i++) ids.includes(99999);
const arrayTime = performance.now() - t;

t = performance.now();
for (let i = 0; i < 2000; i++) idSet.has(99999);
const setTime = performance.now() - t;

console.log("Set.has much faster than Array.includes:", setTime * 20 < arrayTime);
```

```text output
Set(3) { 'sale', 'new', 'gift' } 3 true
[ 'sale', 'gift' ]
[ 'a@example.com', 'b@example.com' ]
Set.has much faster than Array.includes: true
```

<Happened>
<Tr>
<En>

- Adding "sale" again changed nothing; the Set still had 3 values, in insertion order.
- Deduplicating emails took one line.
- Looking for the last id 2,000 times: `includes` scanned up to 100,000 items each time; `has` jumped straight to the answer, more than 20× faster here. When you check membership inside a loop, build a Set first.

</En>
<Ur>

- "sale" dobara daalne se kuch nahi badla; Set me ab bhi dalne ki tarteeb se 3 values thin.
- Emails ke dohre hatana ek line me hua.
- Aakhri id 2,000 dafa dhoondna: `includes` ne har dafa 100,000 items tak scan kiye; `has` seedha jawab tak pohancha, yahan 20× se zyada tez. Jab loop ke andar membership check karein, pehle Set banayen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Set operations">

<Tr>
<En>
Modern JavaScript (Node 22+, recent browsers) adds methods to compare Sets: `union` (everything), `intersection` (in both), `difference` (in this one but not the other), `symmetricDifference` (in exactly one), plus `isSubsetOf` and `isDisjointFrom`. Sets compare values with `===`-like equality, so two separate objects are different values.
</En>
<Ur>
Jadeed JavaScript (Node 22+, haaliya browsers) Sets ka muqabla karne ke methods jorti hai: `union` (sab kuch), `intersection` (dono me), `difference` (is me magar doosre me nahi), `symmetricDifference` (sirf ek me), saath `isSubsetOf` aur `isDisjointFrom`. Sets values ko `===` jaisi barabari se compare karte hain, isliye do alag objects mukhtalif values hain.
</Ur>
</Tr>

```javascript
const a = new Set(["js", "css", "html"]);
const b = new Set(["js", "react"]);

console.log(a.union(b), a.intersection(b), a.difference(b), a.symmetricDifference(b));
console.log(new Set(["js"]).isSubsetOf(a), a.isDisjointFrom(new Set(["go"])));

const both = new Set([...a].filter((x) => b.has(x)));
console.log(both);

const objs = new Set([{ id: 1 }, { id: 1 }]);
console.log(objs.size);
```

```text output
Set(4) { 'js', 'css', 'html', 'react' } Set(1) { 'js' } Set(2) { 'css', 'html' } Set(3) { 'css', 'html', 'react' }
true true
Set(1) { 'js' }
2
```

<Happened>
<Tr>
<En>

- `union` combined both skill lists; `intersection` found the shared one ("js"); `difference` gave what only `a` has.
- In older environments, `[...a].filter((x) => b.has(x))` gives the intersection the classic way.
- Two `{ id: 1 }` objects are **two** entries: Sets don't compare contents. To dedupe objects, use a Map keyed by id.

</En>
<Ur>

- `union` ne dono skills ki lists jor din; `intersection` ne mushtarik wali dhoondi ("js"); `difference` ne wo diya jo sirf `a` ke paas hai.
- Purane mahaul me `[...a].filter((x) => b.has(x))` classic tareeqe se intersection deta hai.
- Do `{ id: 1 }` objects **do** entries hain: Sets maal compare nahi karte. Objects ke dohre hatane ke liye id ki key wala Map lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="WeakMap and WeakSet">

<Tr>
<En>
A WeakMap's keys must be **objects**, and it holds them **weakly**: if nothing else in your program refers to the key object, it can be garbage-collected, and its WeakMap entry disappears with it. The trade-off: you can't list, count or loop over a WeakMap. WeakSet is the same idea for "have I seen this object?".
</En>
<Ur>
WeakMap ki keys **objects** honi chahiyen, aur ye unhe **kamzori se** pakarta hai: agar aap ke program me koi aur cheez key object ki taraf ishara na kare, to wo garbage collect ho sakta hai, aur us ki WeakMap entry bhi saath ghayab ho jati hai. Sauda: aap WeakMap ki list, ginti ya loop nahi kar sakte. WeakSet "kya ye object pehle dekha?" ke liye yahi khayal hai.
</Ur>
</Tr>

```javascript
const metadata = new WeakMap();
let button = { label: "Buy" };
metadata.set(button, { clicks: 0 });
metadata.get(button).clicks++;
console.log(metadata.get(button), metadata.has(button));

  metadata.set("text", 1);
} catch (error) {
  console.log(error.name + ": " + error.message);
```

<Happened>
<Tr>
<En>

- The click count is attached to `button` **without adding a property** to the button object itself.
- Strings can't be WeakMap keys (only objects and non-registered symbols).
- There's no `size`, `keys` or loop: because entries can vanish at any time, the language doesn't let you observe them.
- When `button` is no longer used anywhere (say, the element is removed from the page), its metadata is freed automatically. With a normal `Map`, the entry would keep the object alive forever: a **memory leak**.

</En>
<Ur>

- Clicks ki ginti button object me **property jore baghair** `button` ke saath juri hai.
- Strings WeakMap keys nahi ho saktin (sirf objects aur ghair registered symbols).
- `size`, `keys` ya loop nahi: chunke entries kisi bhi waqt ghayab ho sakti hain, zaban aap ko unhe dekhne nahi deti.
- Jab `button` kahin istemal na ho (maslan element page se hata diya jaye), us ka metadata khud azad ho jata hai. Aam `Map` ke saath entry object ko hamesha zinda rakhti: **memory leak**.

</Ur>
</Tr>
</Happened>

<Step title="A cache keyed by object">

<Tr>
<En>
WeakMap is perfect for **caching results per object**: compute once, store it under the object, reuse it, and let it disappear when the object does. Combined with immutable updates, a new object means a new computation.
</En>
<Ur>
WeakMap **har object ke nataij cache karne** ke liye behtareen hai: ek dafa nikalein, object ke neeche mehfooz karein, dobara istemal karein, aur object ke saath ghayab hone dein. Immutable updates ke saath milayen to naya object matlab naya hisaab.
</Ur>
</Tr>

```javascript
const cache = new WeakMap();
let calls = 0;

function totals(cart) {
  if (cache.has(cart)) return cache.get(cart);
  calls++;
  const result = cart.items.reduce((sum, item) => sum + item.price * item.qty, 0);
  cache.set(cart, result);
  return result;
}

const cart = { items: [{ price: 899, qty: 2 }, { price: 2999, qty: 1 }] };
console.log(totals(cart), totals(cart), totals(cart), "computed", calls, "time(s)");

const next = { ...cart, items: [...cart.items, { price: 450, qty: 1 }] };
console.log(totals(next), "computed", calls, "time(s)");
```

```text output
4797 4797 4797 computed 1 time(s)
5247 computed 2 time(s)
```

<Happened>
<Tr>
<En>

- Three calls with the same cart computed the total **once**.
- The updated cart is a **new object** (immutable update), so the cache missed and computed again. Correct, because the contents changed.
- Old carts that are no longer referenced drop out of the cache automatically. This is the idea behind memoised selectors in state libraries.

</En>
<Ur>

- Ek hi cart ke saath teen calls ne total **ek dafa** nikala.
- Update hua cart **naya object** hai (immutable update), isliye cache me nahi mila aur dobara nikala. Sahi, kyun ke maal badal gaya.
- Purane carts jin ki taraf ab koi ishara nahi khud cache se nikal jate hain. State libraries ke memoised selectors ke peechhe yahi khayal hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="An LRU cache and converting to JSON">

<Tr>
<En>
Because a Map remembers **insertion order**, it makes a simple **LRU cache**: on every read, move the entry to the end; when the cache is full, delete the first (least recently used) key. Maps and Sets don't turn into JSON by themselves, so convert them first.
</En>
<Ur>
Chunke Map **dalne ki tarteeb** yaad rakhta hai, ye saada **LRU cache** banata hai: har parhne par entry ko aakhir me le jao; cache bhar jaye to pehli (sab se kam haaliya istemal wali) key mita do. Maps aur Sets khud JSON nahi bante, isliye pehle badlein.
</Ur>
</Tr>

```javascript
class LRUCache {
  #max;
  #map = new Map();
  constructor(max) {
    this.#max = max;
  }
  get(key) {
    if (!this.#map.has(key)) return undefined;
    const value = this.#map.get(key);
    this.#map.delete(key);
    this.#map.set(key, value);
    return value;
  }
  set(key, value) {
    this.#map.delete(key);
    this.#map.set(key, value);
    if (this.#map.size > this.#max) this.#map.delete(this.#map.keys().next().value);
  }
  keys() {
    return [...this.#map.keys()];
  }
}

const lru = new LRUCache(2);
lru.set("a", 1);
lru.set("b", 2);
lru.get("a");
lru.set("c", 3);
console.log(lru.keys(), lru.get("b"));

const m = new Map([["x", 1]]);
console.log(JSON.stringify(m), JSON.stringify(Object.fromEntries(m)), JSON.stringify([...new Set([1, 2])]));
```

```text output
[ 'a', 'c' ] undefined
{} {"x":1} [1,2]
```

<Happened>
<Tr>
<En>

- Reading "a" moved it to the end, so when "c" pushed the cache over its limit of 2, **"b"** (least recently used) was evicted.
- `map.keys().next().value` is the **first** key in insertion order.
- `JSON.stringify(map)` gave `{}`: the data is lost. Use `Object.fromEntries(map)` (string keys) or `[...map]` (any keys, as pairs), and `[...set]` for Sets.

</En>
<Ur>

- "a" parhne se wo aakhir me chala gaya, isliye jab "c" ne cache ko 2 ki hadd se aage dhakela to **"b"** (sab se kam haaliya istemal) nikal gaya.
- `map.keys().next().value` dalne ki tarteeb me **pehli** key hai.
- `JSON.stringify(map)` ne `{}` diya: data kho gaya. `Object.fromEntries(map)` (string keys) ya `[...map]` (har qisam ki keys, jore), aur Sets ke liye `[...set]` lein.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>


</Bad>
<Good title="Build a Set once">


<Compare>
<Bad title="Object keys from user input">

```javascript
const votes = {};

```

```text output

```

</Bad>
<Good title="A Map treats every key as plain data">

```javascript
const votes = new Map();

```

```text output
1 1
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Expecting Sets to dedupe objects by content.** Key by id instead.
- **Sending a Map or Set straight to `JSON.stringify`.** Convert first.
- **Using `map.get(key) || default`** when stored values can be `0` or `""`. Use `??` or `has`.
- **Trying to loop or count a WeakMap.** It's not possible by design; use a Map if you need that.
- **Building a Map for a fixed record** (`new Map([["name", "Mug"], ["price", 8]])`) where a plain object is clearer.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Sets se objects ke maal ke hisaab se dohre hatane ki umeed.** Id ki key lein.

- **WeakMap par loop ya ginti ki koshish.** Ye design ke mutabiq na-mumkin hai; zaroorat ho to Map lein.
- **Tay shuda record ke liye Map banana** (`new Map([["name", "Mug"], ["price", 8]])`) jahan saada object zyada wazeh hai.

<Takeaways>
<Tr>
<En>

- **Map**: key → value with **any key type**, insertion order, `size`, no inherited keys. `set`/`get`/`has`/`delete`, loop `for (const [k, v] of map)`.
- Prefer Map over objects for **dynamic dictionaries**, user-supplied keys, non-string keys, counting and grouping (`Map.groupBy`).
- **Set**: unique values; `[...new Set(arr)]` dedupes; `has` is fast; set methods compare groups.
- Sets and Maps compare keys by reference: separate objects are different keys.
- **WeakMap/WeakSet**: object keys held weakly; no size or iteration; perfect for per-object data and caches without leaks.
- Map insertion order makes simple LRU caches.
- Convert for JSON: `Object.fromEntries(map)`, `[...map]`, `[...set]`.

</En>

- **Map**: **har qisam ki key** ke saath key → value, dalne ki tarteeb, `size`, virasat ki keys nahi. `set`/`get`/`has`/`delete`, loop `for (const [k, v] of map)`.

<DeepDive title="More about collections">

**Key equality.** Map and Set use **SameValueZero**: like `===`, but `NaN` equals `NaN`, and `0` equals `-0`.

**Performance.** Map and Set operations are typically constant time on average. Maps also handle frequent additions and deletions better than objects, which engines optimise for fixed shapes.

**`Object.create(null)`** makes an object with no prototype, a lightweight dictionary without inherited keys (what `Object.groupBy` returns). A Map is still clearer for dynamic keys.

**WeakRef and FinalizationRegistry** give lower-level control over weak references and cleanup callbacks. They're rarely needed and their timing is unpredictable.

**Iteration while modifying.** Deleting entries from a Map or Set during iteration is safe; added entries are visited if they're added before the loop reaches the end.

**Sorting a Map.** Maps keep insertion order, not sorted order. Sort the entries and build a new Map: `new Map([...map].sort(([a], [b]) => a.localeCompare(b)))`.

**TypeScript.** `Map<string, number>`, `Set<string>`, `WeakMap<HTMLElement, Meta>` give typed keys and values.

</DeepDive>

<DeepDive title="Real world: the cache that ate the server">

A Node API cached computed product summaries in a module-level object, keyed by request parameters: `cache[JSON.stringify(query)] = result`. It made popular pages fast. Over a few days, though, memory climbed steadily until the process crashed and restarted, every 3 or 4 days.

The cache **never removed anything**. Each unique query (including search terms typed by users and bots, page numbers, sort options) added a new entry forever. A bot crawling search pages with random terms generated millions of unique keys.

The fix:

1. Replace the object with an **LRU cache** (a Map with a size limit, like the one in this lesson; in production, the `lru-cache` package) holding at most 5,000 entries, with a time-to-live.
2. Only cache **normalised** queries (lowercased, trimmed, known sort options), and skip caching rare search terms.
3. Monitor heap size and cache hit rate.

Lesson: a cache without a size limit is a **memory leak with good intentions**. Bound it (LRU, TTL) or tie it to object lifetimes with WeakMap.

</DeepDive>

<DeepDive title="Security lens">

- **Use Map (or null-prototype objects) for user-supplied keys.** Plain objects with keys like `__proto__`, `constructor` or `toString` lead to bugs and **prototype pollution** when combined with naive merges.
- **Bound collections fed by users.** Unbounded Maps/Sets of request data are a denial-of-service vector through memory exhaustion.
- **Sets for allow-lists**: `allowedRoles.has(role)` is clear and fast. Normalise values (case, whitespace) before adding and checking.
- **WeakMap for private per-object data** keeps secrets off the object itself, so they don't appear in `JSON.stringify`, logs or `Object.keys`.
- **Don't key caches by raw user input without normalising**, or attackers can bypass caching (and rate limits keyed the same way) with trivial variations.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="When would you use a Map instead of a plain object?">
When keys are added dynamically, may come from users, are not strings, or when you need reliable size, insertion-order iteration and frequent additions and deletions without inherited-property collisions. Plain objects suit fixed-shape records and JSON.
</QA>

<QA q="How do you remove duplicates from an array?">
Create a Set from it and spread it back into an array. For objects, deduplicate by a key such as id using a Map from id to object.
</QA>

<QA q="What is the difference between Map and WeakMap?">
Map accepts any key, holds keys strongly, and is iterable with a size. WeakMap only accepts objects (and non-registered symbols) as keys, holds them weakly so entries can be garbage-collected with their keys, and cannot be iterated or sized.
</QA>

<QA q="How would you implement an LRU cache in JavaScript?">
Use a Map, which preserves insertion order. On get, delete and re-insert the key to mark it most recently used. On set, insert and, if the size exceeds the limit, delete the first key from map.keys().
</QA>

<QA q="How does a Set decide whether two values are the same?">
It uses SameValueZero equality: primitives are compared by value with NaN equal to itself, and objects are compared by reference, so separate objects with identical contents are distinct.
</QA>

</DeepDive>
