<BigIdea>
<Tr>
<En>
**JSON** (JavaScript Object Notation) is a **text format for data**. It looks almost exactly like JavaScript objects and arrays, `{"name": "Mug", "price": 8}`, but it's just **text**, so any program in any language can send it, store it and read it. It's the language APIs speak, the format of `package.json`, and what you put in `localStorage`. JavaScript has two built-in tools: **`JSON.stringify(value)`** turns a value into JSON text, and **`JSON.parse(text)`** turns JSON text back into a value. JSON is **strict** (double quotes only, no trailing commas, no comments) and **limited**: it only knows strings, numbers, booleans, `null`, arrays and plain objects. Anything else (dates, `undefined`, functions, `Map`, `BigInt`) is dropped, changed or rejected, which is where most JSON bugs come from.
</En>
<Ur>
**JSON** (JavaScript Object Notation) **data ke liye text format** hai. Ye taqreeban bilkul JavaScript objects aur arrays jaisa lagta hai, `{"name": "Mug", "price": 8}`, magar ye bas **text** hai, isliye kisi bhi language ka koi bhi program ise bhej, mehfooz aur parh sakta hai. Ye wo zaban hai jo APIs bolti hain, `package.json` ka format hai, aur jo aap `localStorage` me rakhte hain. JavaScript ke paas do bane banaye auzaar hain: **`JSON.stringify(value)`** value ko JSON text me badalta hai, aur **`JSON.parse(text)`** JSON text ko wapas value me. JSON **sakht** hai (sirf double quotes, aakhri comma nahi, comments nahi) aur **mehdood** hai: ye sirf strings, numbers, booleans, `null`, arrays aur saade objects jaanta hai. Baqi sab (dates, `undefined`, functions, `Map`, `BigInt`) gira diya, badla ya mustarad kiya jata hai, aur zyada tar JSON bugs yahin se aate hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Sending JavaScript data to another program is like **mailing a piece of furniture**.

- You can't post a sofa as-is. You **flat-pack** it into a box with instructions: that's `JSON.stringify`. The box (text) travels through the post (network) to anyone.
- At the other end, someone **assembles** it from the instructions: `JSON.parse`. They get a sofa that looks the same, but it's a **new** sofa, not the original.
- Some things **can't be flat-packed**: the warranty card stuck to the old sofa (methods), the "maybe later" sticky note (`undefined`). Those just don't make it into the box.
- Some things arrive **as a description, not the real thing**: "Delivered on 2026-11-12" printed on a label (a date becomes a string). If you want a real calendar date, you have to **rebuild** it (a reviver).
- And if the instructions are **smudged** (broken JSON), assembly stops with an error instead of building something wrong.

</En>
<Ur>

JavaScript data doosre program ko bhejna **furniture daak se bhejne** jaisa hai.

- Aap sofa waise hi post nahi kar sakte. Aap use hidayat ke saath dabbe me **khol kar flat pack** karte hain: ye `JSON.stringify` hai. Dabba (text) daak (network) ke zariye kisi tak bhi jata hai.
- Doosri taraf koi hidayat se use **jorta** hai: `JSON.parse`. Unhe ek jaisa dikhne wala sofa milta hai, magar ye **naya** sofa hai, asal nahi.
- Kuch cheezen **flat pack nahi ho saktin**: purane sofe par chipka warranty card (methods), "shayad baad me" wala sticky note (`undefined`). Ye dabbe tak pohanchti hi nahi.
- Kuch cheezen **asal ke bajaye bayan ki shakal me** pohanchti hain: label par chhapa "Delivered on 2026-11-12" (date string ban jati hai). Asli calendar date chahiye to use **dobara banana** parta hai (reviver).
- Aur agar hidayat **dhundli** hon (toota JSON), to kuch ghalat banane ke bajaye jorna error ke saath ruk jata hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="JSON.stringify: value to text">

<Tr>
<En>
`JSON.stringify(value)` returns a **string** of JSON. By default it's compact, one line with no spaces. Pass `null, 2` as the extra arguments to indent with 2 spaces for humans.
</En>
<Ur>
`JSON.stringify(value)` JSON ki **string** wapas karta hai. Default me ye mukhtasar hoti hai, ek line, baghair spaces. Insaanon ke liye 2 spaces ka indentation dene ke liye izafi arguments ki jagah `null, 2` dein.
</Ur>
</Tr>

```javascript
const product = { id: 7, name: "Desk lamp", price: 29.99, inStock: true, tags: ["home", "light"], discount: null };

const text = JSON.stringify(product);
console.log(text);
console.log(typeof text, text.length);

console.log(JSON.stringify(product, null, 2));
```

```text output
{"id":7,"name":"Desk lamp","price":29.99,"inStock":true,"tags":["home","light"],"discount":null}
string 96
{
  "id": 7,
  "name": "Desk lamp",
  "price": 29.99,
  "inStock": true,
  "tags": [
    "home",
    "light"
  ],
  "discount": null
}
```

<Happened>
<Tr>
<En>

- The result is one **string** of 96 characters. Keys got **double quotes**, as JSON requires.
- `null` survived as `null`. Strings, numbers, booleans, arrays and nested objects all have direct JSON equivalents.
- The pretty version is the same data with line breaks and indentation. Use it for logs, files people read, and debugging; use the compact form for sending over the network.

</En>
<Ur>

- Nateeja 96 characters ki ek **string** hai. Keys ko **double quotes** mile, jaisa JSON ko chahiye.
- `null` `null` hi raha. Strings, numbers, booleans, arrays aur nested objects sab ke seedhe JSON barabar hain.
- Pretty version wahi data hai, line breaks aur indentation ke saath. Ise logs, insaanon ke parhne wali files aur debugging ke liye lein; network par bhejne ke liye mukhtasar shakal lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="JSON.parse: text to value">

<Tr>
<En>
`JSON.parse(text)` reads JSON text and builds the matching JavaScript value: a new object, array, string, number, boolean or `null`.
</En>
<Ur>
`JSON.parse(text)` JSON text parh kar mutabiqa JavaScript value banata hai: naya object, array, string, number, boolean ya `null`.
</Ur>
</Tr>

```javascript
const body = '{"id":7,"name":"Desk lamp","price":29.99,"tags":["home","light"]}';
const data = JSON.parse(body);
console.log(data.name, data.tags[1], typeof data.price);

console.log(JSON.parse("42"), JSON.parse('"hi"'), JSON.parse("true"), JSON.parse("null"), JSON.parse("[1,2]"));
```

```text output
Desk lamp light number
42 hi true null [ 1, 2 ]
```

<Happened>
<Tr>
<En>

- After parsing, `data` is a normal object: dot access, array indexes, real number types.
- JSON doesn't have to be an object: a bare number, string, boolean, `null` or array is valid JSON too.
- The JSON text was written in **single quotes on the outside** so the double quotes inside didn't need escaping. In real code, this text usually comes from a network response or a file.

</En>
<Ur>

- Parse ke baad `data` aam object hai: dot access, array indexes, asli number types.
- JSON ka object hona zaroori nahi: akela number, string, boolean, `null` ya array bhi sahi JSON hai.
- JSON text **bahar single quotes** me likha gaya taa ke andar ke double quotes ko escape na karna pare. Asli code me ye text aam taur par network response ya file se aata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="JSON is strict: reading parse errors">

<Tr>
<En>
JSON is stricter than JavaScript: keys and strings need **double quotes**, no **trailing commas**, no **comments**, no `undefined`, no leading zeros. Invalid text makes `JSON.parse` throw a `SyntaxError` that tells you **where** it got stuck.
</En>
<Ur>
JSON JavaScript se zyada sakht hai: keys aur strings ko **double quotes** chahiyen, **aakhri comma** nahi, **comments** nahi, `undefined` nahi, shuru me zero nahi. Ghalat text par `JSON.parse` `SyntaxError` phenkta hai jo batata hai ke **kahan** atka.
</Ur>
</Tr>

```javascript
const attempts = ['{name: "Mug"}', "{'name': 'Mug'}", '{"name": "Mug",}', "", "undefined", '{"price": 08}'];

for (const text of attempts) {
  try {
    JSON.parse(text);
    console.log("ok:", text);
  } catch (error) {
    console.log(error.name + ":", error.message);
  }
}
```

```text output
SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)
SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)
SyntaxError: Expected double-quoted property name in JSON at position 15 (line 1 column 16)
SyntaxError: Unexpected end of JSON input
SyntaxError: "undefined" is not valid JSON
SyntaxError: Unexpected number in JSON at position 11 (line 1 column 12)
```

<Happened>
<Tr>
<En>

| Input | Problem |
| --- | --- |
| `{name: "Mug"}` | key without quotes (fine in JS, not in JSON) |
| `{'name': 'Mug'}` | single quotes |
| `{"name": "Mug",}` | trailing comma |
| `""` (empty) | nothing to parse: common when a server returns an empty body |
| `undefined` | the text "undefined" (e.g. from `localStorage` storing `String(undefined)`) |
| `{"price": 08}` | leading zero in a number |

- The position tells you where to look: column 2 means the second character.
- Exact messages differ between browsers and versions, but they're always a `SyntaxError`.
- If an API returns an HTML error page instead of JSON, you'll see something like `Unexpected token '<'`: the `<` of `<!DOCTYPE html>`. Check `response.ok` and the `Content-Type` before parsing.

</En>
<Ur>

| Input | Masla |
| --- | --- |
| `{name: "Mug"}` | key baghair quotes (JS me theek, JSON me nahi) |
| `{'name': 'Mug'}` | single quotes |
| `{"name": "Mug",}` | aakhri comma |
| `""` (khaali) | parse karne ko kuch nahi: aam jab server khaali body bheje |
| `undefined` | text "undefined" (maslan `localStorage` me `String(undefined)` mehfooz hona) |
| `{"price": 08}` | number me shuru ka zero |

- Position batati hai kahan dekhna hai: column 2 matlab doosra character.
- Bilkul theek paighaam browsers aur versions me mukhtalif hote hain, magar hamesha `SyntaxError` hote hain.
- Agar API JSON ke bajaye HTML error page bheje to `Unexpected token '<'` jaisa kuch dikhega: `<!DOCTYPE html>` ka `<`. Parse se pehle `response.ok` aur `Content-Type` check karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What gets lost or changed">

<Tr>
<En>
JSON can only hold six kinds of values. When `stringify` meets anything else, it **drops** it, **changes** it, or **throws**. This is the most important table in the lesson; the output below shows each case.
</En>
<Ur>
JSON sirf chhe qisam ki values rakh sakta hai. Jab `stringify` ko kuch aur mile, wo use **gira deta**, **badal deta** ya **error phenkta** hai. Ye lesson ki sab se ahem table hai; neeche ka output har soorat dikhata hai.
</Ur>
</Tr>

```javascript
const weird = {
  missing: undefined,
  fn() {},
  sym: Symbol("x"),
  notNumber: NaN,
  big: Infinity,
  when: new Date("2026-11-12T10:30:00Z"),
  tags: new Set(["a"]),
  map: new Map([["k", 1]]),
  list: [undefined, () => 1, NaN],
};
console.log(JSON.stringify(weird));

try {
  JSON.stringify({ n: 10n });
} catch (error) {
  console.log(error.name + ":", error.message);
}

const loop = { name: "loop" };
loop.self = loop;
try {
  JSON.stringify(loop);
} catch (error) {
  console.log(error.name + ":", error.message.split("\n")[0]);
}
```

```text output
{"notNumber":null,"big":null,"when":"2026-11-12T10:30:00.000Z","tags":{},"map":{},"list":[null,null,null]}
TypeError: Do not know how to serialize a BigInt
TypeError: Converting circular structure to JSON
```

<Happened>
<Tr>
<En>

- `missing` (undefined), `fn` and `sym` **vanished** from the object. In an array they can't vanish (positions matter), so they became `null`.
- `NaN` and `Infinity` became `null`: a "price" of `NaN` silently turns into "no price".
- The date became an ISO **string**. It looks right, but after parsing it's text, not a `Date`.
- `Set` and `Map` became `{}`: their contents were **lost**. Convert them first: `[...set]`, `Object.fromEntries(map)`.
- `BigInt` and an object that contains itself **throw** a `TypeError`.
- Important consequence: an API field you set to `undefined` is **not sent at all**. If the server must know "clear this", send `null`.

</En>
<Ur>

- `missing` (undefined), `fn` aur `sym` object se **ghayab** ho gaye. Array me ye ghayab nahi ho sakte (jaghen ahem hain), isliye `null` ban gaye.
- `NaN` aur `Infinity` `null` ban gaye: `NaN` ki "qeemat" khamoshi se "koi qeemat nahi" ban jati hai.
- Date ISO **string** ban gayi. Sahi lagti hai, magar parse ke baad ye text hai, `Date` nahi.
- `Set` aur `Map` `{}` ban gaye: in ka maal **kho gaya**. Pehle badlein: `[...set]`, `Object.fromEntries(map)`.
- `BigInt` aur khud ko shamil karne wala object `TypeError` **phenkte** hain.
- Ahem nateeja: jis API field ko aap `undefined` rakhte hain wo **bheji hi nahi jati**. Agar server ko "ise mita do" pata hona chahiye to `null` bhejein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Bringing dates back with a reviver">

<Tr>
<En>
A date goes out as a string and comes back as a string. To get a real `Date` again, pass a **reviver** function as the second argument to `JSON.parse`: it sees every key and value and can return a replacement.
</En>
<Ur>
Date string ki shakal me jati hai aur string ki shakal me wapas aati hai. Dobara asli `Date` lene ke liye `JSON.parse` ko doosre argument ke taur par **reviver** function dein: ye har key aur value dekhta hai aur us ki jagah kuch aur wapas kar sakta hai.
</Ur>
</Tr>

```javascript
const order = { id: 1, placedAt: new Date("2026-11-12T10:30:00Z") };

const copy = JSON.parse(JSON.stringify(order));
console.log(typeof copy.placedAt, copy.placedAt);

const revived = JSON.parse(JSON.stringify(order), (key, value) =>
  key === "placedAt" ? new Date(value) : value
);
console.log(revived.placedAt instanceof Date, revived.placedAt.getUTCHours());
```

```text output
string 2026-11-12T10:30:00.000Z
true 10
```

<Happened>
<Tr>
<En>

- Without a reviver, `copy.placedAt` is a **string**. Calling `copy.placedAt.getTime()` would crash.
- The reviver returned `new Date(value)` for the `placedAt` key and left everything else unchanged.
- This is also why `JSON.parse(JSON.stringify(x))` is a poor deep-copy trick: dates, `undefined`, `Map`s and more don't survive. Use `structuredClone`.
- With TypeScript or zod you can describe which fields are dates and convert them in one place.

</En>
<Ur>

- Reviver ke baghair `copy.placedAt` **string** hai. `copy.placedAt.getTime()` call karna crash karta.
- Reviver ne `placedAt` key ke liye `new Date(value)` wapas kiya aur baqi sab waisa hi chhor diya.
- Yahi wajah hai ke `JSON.parse(JSON.stringify(x))` deep copy ki kamzor chaal hai: dates, `undefined`, `Map`s aur bohot kuch nahi bachta. `structuredClone` lein.
- TypeScript ya zod ke saath aap bayan kar sakte hain ke kaun si fields dates hain aur unhe ek jagah badal sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Replacers and toJSON: control the output">

<Tr>
<En>
The second argument of `stringify` is a **replacer**. An **array of keys** is an allow-list: only those keys are written. A **function** sees every key and value; returning `undefined` drops a field. An object can also define its own **`toJSON()`** method to say how it should look in JSON.
</En>
<Ur>
`stringify` ka doosra argument **replacer** hai. **Keys ki array** allow-list hai: sirf wahi keys likhi jati hain. **Function** har key aur value dekhta hai; `undefined` wapas karna field gira deta hai. Object apna **`toJSON()`** method bhi bana sakta hai jo bataye ke JSON me wo kaisa dikhe.
</Ur>
</Tr>

```javascript
const user = { id: 1, email: "alex@example.com", passwordHash: "x9k2…", role: "customer", lastLogin: "2026-11-10" };

console.log(JSON.stringify(user, ["id", "email"]));
console.log(JSON.stringify(user, (key, value) => (key === "passwordHash" ? undefined : value)));

class Money {
  constructor(cents) {
    this.cents = cents;
  }
  toJSON() {
    return { amount: (this.cents / 100).toFixed(2), currency: "USD" };
  }
}
console.log(JSON.stringify({ total: new Money(2544) }));
```

```text output
{"id":1,"email":"alex@example.com"}
{"id":1,"email":"alex@example.com","role":"customer","lastLogin":"2026-11-10"}
{"total":{"amount":"25.44","currency":"USD"}}
```

<Happened>
<Tr>
<En>

- The allow-list wrote **only** `id` and `email`. This is the safer style: new sensitive fields added later won't leak by accident.
- The function replacer removed `passwordHash` and kept the rest. It works, but a new secret field added next month would be sent unless someone remembers to add it here.
- `Money.toJSON()` decided its own JSON shape. `Date` objects work the same way: `Date.prototype.toJSON` is why dates become ISO strings.

</En>
<Ur>

- Allow-list ne **sirf** `id` aur `email` likhe. Ye zyada mehfooz andaaz hai: baad me jure naye hassas fields ghalti se leak nahi honge.
- Function replacer ne `passwordHash` hataya aur baqi rakha. Chalta hai, magar agle mahine juri nayi secret field bheji jayegi jab tak koi yahan jorna yaad na rakhe.
- `Money.toJSON()` ne apni JSON shakal khud tay ki. `Date` objects bhi aise hi kaam karte hain: `Date.prototype.toJSON` ki wajah se dates ISO strings banti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="JSON with fetch">

<Tr>
<En>
To **send** JSON, stringify the body and set `Content-Type: application/json`. To **read** JSON, call `await response.json()`, which reads the body text and parses it. Here we build `Response` and `Request` objects directly (no network needed) to see exactly what happens.
</En>
<Ur>
JSON **bhejne** ke liye body ko stringify karein aur `Content-Type: application/json` set karein. JSON **parhne** ke liye `await response.json()` call karein, jo body ka text parh kar parse karta hai. Yahan hum `Response` aur `Request` objects seedha banate hain (network ki zaroorat nahi) taa ke bilkul dekh sakein kya hota hai.
</Ur>
</Tr>

```javascript
const response = new Response(JSON.stringify({ items: [{ id: 1, name: "Mug" }], total: 1 }), {
  headers: { "Content-Type": "application/json" },
});
console.log(response.headers.get("content-type"));
const data = await response.json();
console.log(data.items[0].name, data.total);

const request = new Request("https://api.example.com/orders", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ productId: 7, qty: 2 }),
});
console.log(request.method, await request.text());
```

```text output

Mug 1
POST {"productId":7,"qty":2}
```

<Happened>
<Tr>
<En>

- `response.json()` is `JSON.parse(await response.text())` in one step. It returns a promise, so it needs `await`, and it **throws** if the body isn't valid JSON.
- The request body is just the JSON **text**: exactly what the server receives.
- Real pattern: `const res = await fetch(url); if (!res.ok) throw new Error(…); const data = await res.json();`. Check `res.ok` first, because error pages often aren't JSON.
- Forgetting `JSON.stringify` and passing an object as `body` sends the text `"[object Object]"`.

</En>
<Ur>

- `response.json()` ek qadam me `JSON.parse(await response.text())` hai. Ye promise deta hai, isliye `await` chahiye, aur body sahi JSON na ho to **error phenkta** hai.
- Request body bas JSON **text** hai: bilkul wahi jo server ko milta hai.
- Asli pattern: `const res = await fetch(url); if (!res.ok) throw new Error(…); const data = await res.json();`. Pehle `res.ok` check karein, kyun ke error pages aksar JSON nahi hote.
- `JSON.stringify` bhool kar object ko `body` ki tarah dena text `"[object Object]"` bhejta hai.

</Ur>
</Tr>
</Happened>

<Step title="Safe parsing and checking the shape">

<Tr>
<En>
Text from storage, users or other services can be broken or unexpected. Wrap `JSON.parse` in a helper with a fallback, then **check the shape** of the result before using it. Valid JSON isn't the same as the data you expected.
</En>
<Ur>
Storage, users ya doosri services ka text toota ya ghair mutawaqqa ho sakta hai. `JSON.parse` ko fallback wale helper me lapetein, phir istemal se pehle nateeje ki **shakal check karein**. Sahi JSON aur mutawaqqa data ek cheez nahi.
</Ur>
</Tr>

```javascript
function safeParse(text, fallback) {
  try {
    return JSON.parse(text);
  } catch {
    return fallback;
  }
}
console.log(safeParse('{"theme":"dark"}', {}), safeParse("not json", {}), safeParse(null, []));

function isProduct(value) {
  return (
    typeof value === "object" &&
    value !== null &&
    Number.isInteger(value.id) &&
    typeof value.name === "string" &&
    typeof value.price === "number" &&
    value.price >= 0
  );
}

for (const text of ['{"id":1,"name":"Mug","price":8}', '{"id":"1","name":"Mug"}', "[1,2]", "null"]) {
  console.log(text, "→", isProduct(safeParse(text, null)));
}
```

```text output
{ theme: 'dark' } {} null
{"id":1,"name":"Mug","price":8} → true
{"id":"1","name":"Mug"} → false
[1,2] → false
null → false
```

<Happened>
<Tr>
<En>

- Broken text returned the fallback instead of crashing the app.
- Surprise: `safeParse(null, [])` returned `null`, not `[]`. `JSON.parse(null)` converts `null` to the text `"null"`, which is valid JSON. (`localStorage.getItem` returns `null` for a missing key, so handle that case: `safeParse(text, []) ?? []`.)
- `isProduct` rejected an id that was a string, a missing price, an array and `null`, all of which are **valid JSON**.
- In real projects, a schema library like **zod** does this checking (and gives clear error messages) in a few lines.

</En>
<Ur>

- Toote text ne app crash karne ke bajaye fallback wapas kiya.
- Hairani: `safeParse(null, [])` ne `[]` nahi, `null` wapas kiya. `JSON.parse(null)` `null` ko text `"null"` me badalta hai, jo sahi JSON hai. (`localStorage.getItem` ghayab key par `null` deta hai, isliye ye soorat sambhalein: `safeParse(text, []) ?? []`.)
- `isProduct` ne string wali id, ghayab price, array aur `null` mustarad kiye, halanke ye sab **sahi JSON** hain.
- Asli projects me **zod** jaisi schema library ye check (aur saaf error paighaam) chand lines me karti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Big numbers in JSON">

<Tr>
<En>
JSON numbers can be any size, but `JSON.parse` turns them into JavaScript numbers, which are exact only up to about 9 quadrillion. Big ids silently change. Send them as **strings**, or, in newer engines, read the original text in a reviver and make a `BigInt`.
</En>
<Ur>
JSON numbers kisi bhi size ke ho sakte hain, magar `JSON.parse` unhe JavaScript numbers me badalta hai, jo sirf taqreeban 9 quadrillion tak bilkul durust hain. Bari ids khamoshi se badal jati hain. Inhe **strings** ki shakal me bhejein, ya naye engines me reviver me asal text parh kar `BigInt` banayen.
</Ur>
</Tr>

```javascript
const text = '{"orderId": 1234567890123456789, "orderIdText": "1234567890123456789"}';

const data = JSON.parse(text);
console.log(data.orderId, data.orderIdText);

const precise = JSON.parse(text, (key, value, context) =>
  key === "orderId" ? BigInt(context.source) : value
);
console.log(precise.orderId);
console.log(JSON.stringify({ id: precise.orderId.toString() }));
```

```text output
1234567890123456800 1234567890123456789
1234567890123456789n
{"id":"1234567890123456789"}
```

<Happened>
<Tr>
<En>

- The numeric `orderId` lost its last digits (…6800). The string version kept every digit.
- The reviver's third argument, `context.source`, is the **original text** of the value (a newer feature: Node 22+, recent Chrome and Firefox), so `BigInt` gets every digit.
- Going back out, `BigInt` can't be stringified directly; `.toString()` turns it into a string first.
- The simplest rule: **ids are strings** in JSON. Don't do math with them anyway.

</En>
<Ur>

- Numeric `orderId` ke aakhri hindse kho gaye (…6800). String version ne har hindsa rakha.
- Reviver ka teesra argument, `context.source`, value ka **asal text** hai (nayi feature: Node 22+, haaliya Chrome aur Firefox), isliye `BigInt` ko har hindsa milta hai.
- Wapas bahar jate waqt `BigInt` seedha stringify nahi ho sakta; `.toString()` pehle use string banata hai.
- Sab se saada qaida: JSON me **ids strings hain**. Waise bhi un par hisaab nahi karna.

</Ur>
</Tr>
</Happened>

<Compare>

<DeepDive title="More about JSON">

**The full grammar** fits on one page (json.org): values are objects, arrays, strings, numbers, `true`, `false` or `null`. Strings must escape `"` and `\` and control characters; numbers can't have leading zeros, `+`, hex or a trailing `.`.

**Key order.** `stringify` writes keys in the object's property order (integer-like keys first, ascending, then others in insertion order). Don't rely on JSON text equality to compare objects.

**Indentation options.** The third argument can be a number (up to 10 spaces) or a string like `"\t"`.

**Related formats.**

| Format | Adds |
| --- | --- |
| JSON5 / JSONC | comments, trailing commas (VS Code and `tsconfig.json` accept JSONC) |
| NDJSON / JSON Lines | one JSON value per line, great for logs and streaming |
| JSON Schema | a standard way to describe and validate JSON shapes |
| YAML | a superset of JSON, friendlier for config files |

**Performance.** `JSON.parse` is extremely fast, often faster than a JavaScript object literal for large data. For huge payloads, stream them (NDJSON) instead of building one giant string.

**`import data from "./data.json" with { type: "json" }`** loads JSON files as modules in modern Node and browsers.

</DeepDive>

<DeepDive title="Real world: the settings that reset every week">

A dashboard saved each user's layout to `localStorage` with `JSON.stringify(layout)`. The layout object included `lastOpened: new Date()` and `pinned: new Set(["sales", "traffic"])`.

On the next visit, the app parsed the JSON and called `layout.pinned.has("sales")`, which crashed with "has is not a function": the `Set` had been saved as `{}`. A `try…catch` around the whole loader caught the crash and **reset the layout to defaults**, without logging anything. Users complained that their dashboard "forgot everything", but only after they'd pinned something; developers couldn't reproduce it with a fresh profile.

The fix:

1. Convert special types explicitly when saving (`pinned: [...layout.pinned]`, `lastOpened: date.toISOString()`) and back when loading.
2. Add a `version` field to saved JSON, so future format changes could be migrated instead of crashing.
3. Validate the loaded object's shape (with zod) and log validation failures before falling back.
4. A test saves a layout, reloads it, and checks that the `Set` and `Date` round-trip.

Lesson: **JSON round-trips only plain data**. Convert everything else on the way out and back on the way in, and never swallow errors silently.

</DeepDive>

<DeepDive title="Security lens">

- **Never use `eval` to read JSON.** `JSON.parse` only builds data; `eval` runs code.
- **Validate everything you parse** from requests, webhooks, `localStorage` and third-party APIs: types, required fields, lengths, allowed values. Valid JSON can still be malicious.
- **Don't leak secrets**: build response objects from an allow-list of fields instead of stringifying whole database records.
- **Prototype pollution**: JSON with a `"__proto__"` key is harmless to `JSON.parse` itself, but dangerous if you then deep-merge it into other objects with a naive merge function. Validate and use safe merge utilities.
- **JSON in HTML**: embedding `JSON.stringify(data)` inside a `<script>` tag can break out with `</script>`. Escape `<` as `<`, or use a framework helper.
- **Size limits**: limit request body size on the server; a 500 MB JSON body can exhaust memory.
- **Return `Content-Type: application/json`** for JSON responses so browsers never treat them as HTML.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between JSON and a JavaScript object?">
JSON is a text format with strict syntax: double-quoted keys and strings, no comments, no trailing commas, and only strings, numbers, booleans, null, arrays and objects. A JavaScript object is an in-memory value that can hold any type, including functions, dates and undefined.
</QA>

<QA q="What does JSON.stringify do with undefined, functions, NaN and dates?">
In objects, properties with undefined, function or symbol values are omitted, and in arrays they become null. NaN and Infinity become null. Dates are serialized through toJSON into ISO 8601 strings.
</QA>

<QA q="What are the replacer and reviver parameters?">
The replacer is the second argument of JSON.stringify: an array of allowed keys or a function that can change or remove values. The reviver is the second argument of JSON.parse: a function called for each key and value that can transform them, for example to rebuild Date objects.
</QA>

<QA q="Why is JSON.parse(JSON.stringify(obj)) a poor deep clone?">
It loses undefined values, functions, symbols and prototypes, turns dates into strings, converts Map and Set to empty objects, turns NaN and Infinity into null, and throws on BigInt and circular references. structuredClone handles most of these.
</QA>

<QA q="How do you handle large integer ids in JSON?">
Serialize them as strings, because JSON.parse converts numbers to doubles and loses precision above Number.MAX_SAFE_INTEGER. Alternatively, use a reviver with access to the source text to create BigInt values.
</QA>

</DeepDive>
