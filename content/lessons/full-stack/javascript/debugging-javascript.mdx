<BigIdea>
<Tr>
<En>
A **bug** is any difference between what your code **should** do and what it **actually** does. Debugging isn't guessing and changing random lines until it works; it's a **method**. First **reproduce** the problem reliably. Then **read** what the computer is telling you: the error message and stack trace point to a file and line. Then **narrow it down**: check your assumptions one at a time, with well-placed logs or by **pausing the program** with a breakpoint and looking at every variable. Once you **understand** the cause, fix it, and **prove** the fix with a test so the bug can't quietly come back. Browsers and VS Code include powerful debuggers; learning a handful of their features (breakpoints, step over, step into, watch, the Network tab) will save you more time than almost anything else.
</En>
<Ur>
**Bug** wo har farq hai jo aap ke code ke **karne chahiye** aur **asal me karne** ke darmiyan ho. Debugging andaze lagana aur kaam chalne tak bila wajah lines badalna nahi; ye ek **tareeqa** hai. Pehle masle ko qabil-e-bharosa tareeqe se **dobara paida** karein. Phir **parhein** ke computer kya keh raha hai: error paighaam aur stack trace file aur line ki taraf ishara karte hain. Phir **daira tang karein**: apne mafrooze ek ek kar ke check karein, sahi jagah ke logs ke saath ya breakpoint se **program rok kar** har variable dekh kar. Jab wajah **samajh** aa jaye, theek karein, aur test se hal **sabit** karein taa ke bug khamoshi se wapas na aa sake. Browsers aur VS Code me taqatwar debuggers hain; un ki chand features (breakpoints, step over, step into, watch, Network tab) seekhna taqreeban kisi bhi aur cheez se zyada waqt bachayega.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Debugging is **detective work**.

- A crime has been reported (the bug). First, the detective **visits the scene and recreates what happened** (reproduce). A crime you can't recreate is very hard to solve.
- The **evidence** is lying around: the error message is a note left at the scene, and the stack trace is a list of **everyone who handled the package** on its way to the crime, newest first.
- The detective doesn't arrest the first suspect. They form a theory and **check it**: "If the butler did it, the pantry key should be missing." In code: "If `rule` is undefined, logging `code` should show something unexpected."
- A **breakpoint** is freezing time: everyone stops, and the detective walks around examining every object in the room.
- After solving it, the detective writes up a **report** so the same trick can't work again (a test).

</En>
<Ur>

Debugging **jasoosi** hai.

- Ek jurm ki ittila mili (bug). Pehle jasoos **mauqe par ja kar dobara banata hai ke kya hua** (dobara paida karna). Jo jurm dobara na banaya ja sake use hal karna bohot mushkil hai.
- **Saboot** idhar udhar para hai: error paighaam mauqe par chhora gaya note hai, aur stack trace un **sab logon ki list hai jinhon ne parcel ko jurm tak pohanchne ke raaste me chhua**, sab se naya pehle.
- Jasoos pehle mashkook ko giraftar nahi karta. Wo nazariya banata hai aur use **check karta** hai: "Agar butler ne kiya to pantry ki chabi ghayab honi chahiye." Code me: "Agar `rule` undefined hai to `code` log karne se kuch ghair mutawaqqa nazar aana chahiye."
- **Breakpoint** waqt ko jama dena hai: sab ruk jate hain, aur jasoos kamre me ghoom kar har cheez ka jaiza leta hai.
- Hal karne ke baad jasoos **report** likhta hai taa ke wahi chaal dobara na chal sake (test).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Read the error and the stack trace">

<Tr>
<En>
When code crashes, the message tells you **what** went wrong and the stack trace tells you **where** and **how you got there**. Read the top frames that point to **your** files; ignore `node:internal` frames.
</En>
<Ur>
Jab code crash ho, paighaam batata hai **kya** ghalat hua aur stack trace batata hai **kahan** aur **aap wahan kaise pohanche**. Upar ke wo frames parhein jo **aap ki** files ki taraf ishara karte hain; `node:internal` frames nazarandaz karein.
</Ur>
</Tr>

```bash
cat > cart.js <<'EOF'
function applyDiscount(cart, code) {
  const rule = DISCOUNTS[code];
  return cart.total * (1 - rule.percent / 100);
}
const DISCOUNTS = { SAVE10: { percent: 10 } };
function checkout(cart, code) {
  return applyDiscount(cart, code);
}
console.log(checkout({ total: 200 }, "SAVE10"));
console.log(checkout({ total: 200 }, "save10"));
EOF
node cart.js 2>&1 | head -9
```

```text output
180
/home/you/cart.js:3
  return cart.total * (1 - rule.percent / 100);
                                ^

TypeError: Cannot read properties of undefined (reading 'percent')
    at applyDiscount (/home/you/cart.js:3:33)
    at checkout (/home/you/cart.js:7:10)
    at Object.<anonymous> (/home/you/cart.js:10:13)
```

<Happened>
<Tr>
<En>

Read it like a detective:

1. **What**: `TypeError: Cannot read properties of undefined (reading 'percent')`. Something we called `.percent` on is `undefined`. On line 3, that's `rule`.
2. **Where**: `cart.js:3:33`, line 3, column 33. The `^` points right at it.
3. **How we got there** (read the stack top to bottom): `applyDiscount` was called by `checkout` (line 7), which was called from line 10.
4. **Why**: line 10 passed `"save10"` (lowercase). `DISCOUNTS["save10"]` doesn't exist, so `rule` is `undefined`.

- The first call (line 9) worked, which is a clue: the bug depends on the **input**.
- Fix options: normalise the code (`code.toUpperCase()`), and handle unknown codes with a clear error instead of a crash.

</En>
<Ur>

Ise jasoos ki tarah parhein:

1. **Kya**: `TypeError: Cannot read properties of undefined (reading 'percent')`. Jis cheez par humne `.percent` call kiya wo `undefined` hai. Line 3 par wo `rule` hai.
2. **Kahan**: `cart.js:3:33`, line 3, column 33. `^` seedha us ki taraf ishara karta hai.
3. **Hum wahan kaise pohanche** (stack upar se neeche parhein): `applyDiscount` ko `checkout` ne call kiya (line 7), jise line 10 se call kiya gaya.
4. **Kyun**: line 10 ne `"save10"` (lowercase) diya. `DISCOUNTS["save10"]` maujood nahi, isliye `rule` `undefined` hai.

- Pehli call (line 9) chal gayi, jo ek suraagh hai: bug **input** par munhasir hai.
- Hal ke tareeqe: code ko ek jaisa karein (`code.toUpperCase()`), aur anjaan codes ko crash ke bajaye saaf error se sambhalein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Logging that actually helps">

<Tr>
<En>
`console.log` is still the most-used debugging tool. Make logs useful: **label** them, log **inputs and outputs** of the suspicious function, use `console.table` for lists and `console.assert` to flag impossible states.
</En>
<Ur>
`console.log` ab bhi sab se zyada istemal hone wala debugging auzaar hai. Logs ko kaam ka banayen: un par **label** lagayen, mashkook function ke **inputs aur outputs** log karein, lists ke liye `console.table` aur na-mumkin halaton ke liye `console.assert` lein.
</Ur>
</Tr>

```javascript
function cartTotal(items) {
  let total = 0;
  for (let i = 1; i < items.length; i++) {
    total += items[i].price * items[i].qty;
  }
  return total;
}

const items = [
  { name: "Mug", price: 5, qty: 2 },
  { name: "Pen", price: 3, qty: 1 },
];

console.log("cartTotal input:");
console.table(items);
const total = cartTotal(items);
console.log("cartTotal output:", total, "| expected:", 5 * 2 + 3 * 1);
console.assert(total === 13, "total is wrong:", total);
```

```text output
cartTotal input:
┌─────────┬───────┬───────┬─────┐
│ (index) │ name  │ price │ qty │
├─────────┼───────┼───────┼─────┤
│ 0       │ 'Mug' │ 5     │ 2   │
│ 1       │ 'Pen' │ 3     │ 1   │
└─────────┴───────┴───────┴─────┘
cartTotal output: 3 | expected: 13
Assertion failed: total is wrong: 3
```

<Happened>
<Tr>
<En>

- The input looks right (two items), the output is 3, and we expected 13: the bug is **inside** `cartTotal`.
- 3 is exactly the Pen's price × qty, so the Mug was skipped. That points at the loop: `let i = 1` skips index 0. Classic off-by-one.
- Logging input, output and the **expected** value side by side often reveals the bug without reading every line.
- Remove or downgrade debug logs before committing (a linter rule like `no-console` helps).

</En>
<Ur>

- Input sahi lagta hai (do items), output 3 hai, aur humen 13 ki umeed thi: bug `cartTotal` ke **andar** hai.
- 3 bilkul Pen ki price × qty hai, yani Mug chhoot gaya. Ye loop ki taraf ishara karta hai: `let i = 1` index 0 chhor deta hai. Mashhoor off-by-one.
- Input, output aur **mutawaqqa** value saath saath log karna aksar har line parhe baghair bug dikha deta hai.
- Commit se pehle debug logs hata dein ya kam karein (`no-console` jaisa linter rule madad karta hai).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The live-object logging trap">

<Tr>
<En>
In browser consoles, a logged object is shown **collapsed**, and when you expand it later you see its **current** contents, not what it held at the moment you logged it. If the object changed afterwards, the log lies. Log a **snapshot** instead.
</En>
<Ur>
Browser consoles me log hua object **band** dikhta hai, aur jab aap baad me use kholte hain to us ka **maujooda** maal nazar aata hai, wo nahi jo log karne ke lamhe tha. Agar object baad me badal gaya to log jhoot bolta hai. Is ke bajaye **snapshot** log karein.
</Ur>
</Tr>

```javascript
const order = { status: "pending", items: ["Mug"] };

const snapshot = structuredClone(order);
const asText = JSON.stringify(order);

order.status = "shipped";
order.items.push("Lamp");

console.log("snapshot:", snapshot);
console.log("as text: ", asText);
console.log("now:     ", order);
```

```text output
snapshot: { status: 'pending', items: [ 'Mug' ] }
as text:  {"status":"pending","items":["Mug"]}
now:      { status: 'shipped', items: [ 'Mug', 'Lamp' ] }
```

<Happened>
<Tr>
<En>

- `structuredClone` and `JSON.stringify` captured the state **at that moment**; later changes didn't affect them.
- Node and this page's runner print objects immediately, so they don't show the trap. In Chrome's console, expanding a logged `order` after the change would show "shipped" and two items, leading you to the wrong conclusion about **when** it changed.
- A small "i" icon next to expanded objects in Chrome reminds you that the value was evaluated just now.

</En>
<Ur>

- `structuredClone` aur `JSON.stringify` ne halat **us lamhe** ki pakri; baad ki tabdeeliyon ka un par asar nahi hua.
- Node aur is page ka runner objects foran print karte hain, isliye jaal nahi dikhate. Chrome ke console me tabdeeli ke baad log hua `order` kholne par "shipped" aur do items dikhte, jo aap ko ghalat nateeje par le jata ke ye **kab** badla.
- Chrome me khule objects ke saath chhota "i" icon yaad dilata hai ke value abhi abhi parhi gayi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Breakpoints: pause and look around">

<Tr>
<En>
A **breakpoint** pauses your program at a line so you can inspect **every** variable, the call stack and the page, then step through line by line. Open this preview's page in a real browser tab to practise: the "Add" button has a bug.
</En>
<Ur>
**Breakpoint** aap ke program ko ek line par rok deta hai taa ke aap **har** variable, call stack aur page dekh sakein, phir line ba line aage barh sakein. Practice ke liye is preview ka page asli browser tab me kholein: "Add" button me bug hai.
</Ur>
</Tr>

```html preview-js h=170
<p>Price: <input id="price" value="19.99"> Qty: <input id="qty" value="2" size="3"></p>
<button id="add">Add to total</button>
<p id="total">Total: $0</p>

<script>
  let total = 0;
  document.querySelector("#add").addEventListener("click", () => {
    const price = document.querySelector("#price").value;
    const qty = document.querySelector("#qty").value;
    debugger; // pauses here when DevTools is open
    total = total + price * qty;
    document.querySelector("#total").textContent = "Total: $" + total;
  });
</script>
```

<Happened>
<Tr>
<En>

Click **Add** twice: the total shows 39.98, then 79.96. That looks right… now change the price to `5` and qty to `1`, click again, and check the math. Then debug it properly:

1. Press **F12** and open the **Sources** panel (Firefox: Debugger).
2. Click **Add**. Because DevTools is open, `debugger;` **pauses** the code on that line.
3. Look at the **Scope** pane: `price` is `"19.99"` with quotes, a **string**. `qty` too.
4. Press **Step over** (F10) to run the next line, and watch `total` change.
5. Hover any variable in the code to see its value; type expressions in the **Console** while paused (`typeof price`).
6. Press **Resume** (F8) to continue.

- Here `price * qty` happens to work, because `*` converts strings to numbers. The danger is nearby: change the line to `total = total + price` and `+` would **join text**. The fix is converting at the boundary: `Number(input.value)`.
- Instead of `debugger;`, you can click a **line number** in Sources to set a breakpoint without editing code. Right-click it for a **conditional breakpoint** (only pause when `qty > 10`) or a **logpoint** (log without pausing).

</En>
<Ur>

**Add** do dafa dabayen: total 39.98, phir 79.96 dikhata hai. Sahi lagta hai… ab price `5` aur qty `1` karein, dobara dabayen, aur hisaab check karein. Phir ise sahi tarah debug karein:

1. **F12** dabayen aur **Sources** panel kholein (Firefox: Debugger).
2. **Add** dabayen. Chunke DevTools khula hai, `debugger;` code ko us line par **rok** deta hai.
3. **Scope** pane dekhein: `price` quotes ke saath `"19.99"` hai, yani **string**. `qty` bhi.
4. Agli line chalane ke liye **Step over** (F10) dabayen, aur `total` ko badalte dekhein.
5. Code me kisi bhi variable par hover kar ke us ki value dekhein; ruke hue **Console** me expressions likhein (`typeof price`).
6. Aage chalane ke liye **Resume** (F8) dabayen.

- Yahan `price * qty` ittefaq se chal jata hai, kyun ke `*` strings ko numbers me badalta hai. Khatra qareeb hai: line ko `total = total + price` karein aur `+` **text jor** dega. Hal kinare par badalna hai: `Number(input.value)`.
- `debugger;` ke bajaye aap code badle baghair breakpoint lagane ke liye Sources me **line number** par click kar sakte hain. **Conditional breakpoint** (sirf `qty > 10` par rukna) ya **logpoint** (baghair ruke log) ke liye us par right-click karein.

</Ur>
</Tr>
</Happened>

<Step title="Stepping: over, into, out">

<Tr>
<En>

While paused, the debugger toolbar moves through code one step at a time:

| Button | Key (Chrome) | Does |
| --- | --- | --- |
| **Resume** | F8 | Run until the next breakpoint |
| **Step over** | F10 | Run the current line, including any functions it calls, and stop at the next line |
| **Step into** | F11 | If the line calls a function, go inside it |
| **Step out** | Shift+F11 | Finish the current function and stop where it returns |

Useful panes while paused:

- **Scope**: every local, closure and global variable, with current values.
- **Watch**: expressions you add, re-evaluated at every step (`items.length`, `total > 100`).
- **Call Stack**: the chain of calls; click a frame to see **that** function's variables.
- **Breakpoints**: turn breakpoints on and off; tick **Pause on exceptions** to stop exactly where an error is thrown.

</En>
<Ur>

Ruke hue waqt debugger ka toolbar code me ek ek qadam chalta hai:

| Button | Key (Chrome) | Kya karta hai |
| --- | --- | --- |
| **Resume** | F8 | Agle breakpoint tak chalao |
| **Step over** | F10 | Maujooda line chalao, us ke call kiye functions samet, aur agli line par ruko |
| **Step into** | F11 | Agar line function call kare to us ke andar jao |
| **Step out** | Shift+F11 | Maujooda function mukammal karo aur jahan wo wapas aaye wahan ruko |

Ruke hue waqt kaam ke panes:

- **Scope**: har local, closure aur global variable, maujooda values ke saath.
- **Watch**: aap ke jore expressions, har qadam par dobara nikale jate hain (`items.length`, `total > 100`).
- **Call Stack**: calls ki zanjeer; **us** function ke variables dekhne ke liye frame par click karein.
- **Breakpoints**: breakpoints on aur off karein; bilkul wahan rukne ke liye jahan error phenka jaye **Pause on exceptions** par nishaan lagayen.

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- Use **step over** most of the time, and **step into** only for functions you suspect.
- **Pause on exceptions** (including caught ones) is the fastest way to find where a swallowed error came from.
- Built code (Next.js, Vite) is mapped back to your files with **source maps**, so breakpoints work in your original `.ts`/`.tsx` files.

</En>
<Ur>

- Zyada tar **step over** lein, aur **step into** sirf un functions ke liye jin par shak ho.
- **Pause on exceptions** (pakre hue samet) ye dhoondne ka sab se tez tareeqa hai ke nigla gaya error kahan se aaya.
- Bana hua code (Next.js, Vite) **source maps** se aap ki files se milaya jata hai, isliye breakpoints aap ki asal `.ts`/`.tsx` files me kaam karte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Debugging async code">

<Tr>
<En>
Async bugs often show up as a **`Promise { <pending> }`** where you expected data (a missing `await`), or as things happening in the "wrong" order. Log what you actually have, and check the order with labelled logs.
</En>
<Ur>
Async bugs aksar wahan **`Promise { <pending> }`** ki shakal me nazar aate hain jahan data ki umeed thi (ghayab `await`), ya "ghalat" tarteeb me hone wali cheezon ki shakal me. Jo asal me hai wo log karein, aur label wale logs se tarteeb check karein.
</Ur>
</Tr>

```javascript
async function getUser(id) {
  await new Promise((r) => setTimeout(r, 10));
  return { id, name: "Alex" };
}

const user = getUser(1);
console.log("user:", user);
console.log("name:", user.name);

const realUser = await getUser(1);
console.log("realUser:", realUser, "| name:", realUser.name);
```

```text output
user: Promise { <pending> }
name: undefined
realUser: { id: 1, name: 'Alex' } | name: Alex
```

<Happened>
<Tr>
<En>

- Without `await`, `user` is a **promise**, so `user.name` is `undefined`. No error, just a wrong value: a typical silent async bug.
- Seeing `Promise { <pending> }` (or `[object Promise]` on a web page) is the signal: add `await`.
- In DevTools, the Call Stack pane shows **async** frames too, so you can see which code originally started an awaited operation.

</En>
<Ur>

- `await` ke baghair `user` **promise** hai, isliye `user.name` `undefined` hai. Koi error nahi, bas ghalat value: aam khamosh async bug.
- `Promise { <pending> }` (ya web page par `[object Promise]`) nazar aana ishara hai: `await` jorein.
- DevTools me Call Stack pane **async** frames bhi dikhata hai, isliye aap dekh sakte hain ke kis code ne asal me await hone wala amal shuru kiya.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Debugging network requests">

<Tr>
<En>

When data from an API looks wrong, check the **Network** tab **before** your own code:

1. Open DevTools → **Network**, tick **Preserve log**, then reproduce the problem.
2. Click the request. **Headers** shows the URL, method and **status code** (200, 401, 404, 500…).
3. **Payload** shows what **you sent** (the request body). **Response** / **Preview** shows what **the server returned**.
4. Right-click → **Copy as cURL** to replay the exact request in a terminal (API Routes lesson).

| You see | It usually means |
| --- | --- |
| 404 | wrong URL or id |
| 401 / 403 | not logged in / not allowed |
| 400 / 422 | the server rejected your input (read the response body) |
| 500 | a server bug: check the server logs |
| CORS error in the Console | the API doesn't allow requests from your site's origin |
| 200 but wrong data | the bug is in your request or in how you read the response |

</En>
<Ur>

Jab API ka data ghalat lage to apne code se **pehle** **Network** tab check karein:

1. DevTools → **Network** kholein, **Preserve log** par nishaan lagayen, phir masla dobara paida karein.
2. Request par click karein. **Headers** URL, method aur **status code** (200, 401, 404, 500…) dikhata hai.
3. **Payload** dikhata hai ke **aap ne kya bheja** (request body). **Response** / **Preview** dikhata hai ke **server ne kya wapas kiya**.
4. Bilkul wahi request terminal me dobara chalane ke liye right-click → **Copy as cURL** (API Routes lesson).

| Aap dekhte hain | Aam taur par matlab |
| --- | --- |
| 404 | ghalat URL ya id |
| 401 / 403 | login nahi / ijazat nahi |
| 400 / 422 | server ne aap ka input mustarad kiya (response body parhein) |
| 500 | server ka bug: server logs dekhein |
| Console me CORS error | API aap ki site ke origin se requests ki ijazat nahi deti |
| 200 magar ghalat data | bug aap ki request me ya response parhne ke tareeqe me hai |

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- The Network tab tells you **which side** has the bug: if the server's response is already wrong, debugging your React component is wasted effort.
- Use **Throttling** (e.g. "Slow 4G") to reproduce bugs that only appear on slow connections, like loading spinners that never disappear or double submissions.

</En>
<Ur>

- Network tab batata hai ke bug **kis taraf** hai: agar server ka response pehle hi ghalat hai to apne React component ko debug karna be-faida mehnat hai.
- Sirf sust connections par aane wale bugs dobara paida karne ke liye **Throttling** (maslan "Slow 4G") lein, jaise kabhi na ghayab hone wale loading spinners ya dohri submissions.

</Ur>
</Tr>
</Happened>

<Step title="Prove the fix with a test">

<Tr>
<En>
Before fixing a bug, write a small **test** that fails because of it. Then fix the code and watch the test pass. Now the bug can't return unnoticed. Node has a built-in test runner, `node --test`.
</En>
<Ur>
Bug theek karne se pehle chhota **test** likhein jo us ki wajah se fail ho. Phir code theek karein aur test ko paas hote dekhein. Ab bug baghair nazar me aaye wapas nahi aa sakta. Node ka bana banaya test runner hai, `node --test`.
</Ur>
</Tr>

```bash
cat > total.test.mjs <<'EOF'
import test from "node:test";
import assert from "node:assert/strict";

function cartTotal(items) {
  let total = 0;
  for (let i = 1; i < items.length; i++) total += items[i].price * items[i].qty;
  return total;
}

test("sums every item", () => {
  assert.equal(cartTotal([{ price: 5, qty: 2 }, { price: 3, qty: 1 }]), 13);
});
EOF
node --test --test-reporter=spec total.test.mjs 2>&1 | grep -E "^(✔|✖) sums|^ℹ (pass|fail)|!==" | sed -E 's/ \([0-9.]+ms\)//'

sed -i 's/let i = 1;/let i = 0;/' total.test.mjs
node --test --test-reporter=spec total.test.mjs 2>&1 | grep -E "^(✔|✖) sums|^ℹ (pass|fail)" | sed -E 's/ \([0-9.]+ms\)//'
```

```text output
✖ sums every item
ℹ pass 0
ℹ fail 1
✖ sums every item
  3 !== 13
✔ sums every item
ℹ pass 1
ℹ fail 0
```

<Happened>
<Tr>
<En>

- The first run **failed** with `3 !== 13`, proving the test catches the bug (a test that never fails proves nothing).
- After changing `i = 1` to `i = 0` (the `sed` command edits the file), the same test **passed**.
- Keep the test. If someone reintroduces the bug in six months, the test fails before it reaches users. (Testing has its own lessons later: Vitest, Jest, Playwright.)

</En>
<Ur>

- Pehli dafa `3 !== 13` ke saath **fail** hua, jo sabit karta hai ke test bug pakarta hai (jo test kabhi fail na ho wo kuch sabit nahi karta).
- `i = 1` ko `i = 0` karne ke baad (`sed` command file badalti hai) wahi test **paas** hua.
- Test rakhein. Agar koi chhe mahine baad bug wapas laaye to test users tak pohanchne se pehle fail hoga. (Testing ke apne lessons baad me hain: Vitest, Jest, Playwright.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="When it used to work: git bisect">

<Tr>
<En>

If something worked last week and is broken now, the cause is in one of the commits since then. **`git bisect`** finds it with a binary search: you mark one good and one bad commit, Git checks out the middle one, you test and say "good" or "bad", and it halves the range each time.

```bash
git bisect start
git bisect bad                 # the current commit is broken
git bisect good v1.4.0         # this tag (or commit) was fine
# Git checks out a commit in the middle: test it, then
git bisect good                # or: git bisect bad
# …repeat until Git prints "<hash> is the first bad commit"
git bisect reset               # go back to where you started
```

</En>
<Ur>

Agar kuch pichhle hafte chalta tha aur ab toota hua hai, to wajah tab se ab tak ke kisi commit me hai. **`git bisect`** binary search se use dhoondta hai: aap ek achha aur ek bura commit nishaan zad karte hain, Git beech wala checkout karta hai, aap test kar ke "good" ya "bad" kehte hain, aur ye har dafa daira aadha kar deta hai.

```bash
git bisect start
git bisect bad                 # maujooda commit toota hua hai
git bisect good v1.4.0         # ye tag (ya commit) theek tha
# Git beech ka commit checkout karta hai: test karein, phir
git bisect good                # ya: git bisect bad
# …dohrayen jab tak Git "<hash> is the first bad commit" print na kare
git bisect reset               # wahin wapas jao jahan se shuru kiya
```

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- With 100 commits in between, bisect needs only about **7** tests (2⁷ = 128).
- If you have a script that exits with 0 when good and 1 when bad, `git bisect run npm test` does the whole search automatically.
- Once you know the commit, read its diff: the cause is usually obvious in a small change.

</En>
<Ur>

- Darmiyan 100 commits ke saath bisect ko sirf taqreeban **7** tests chahiyen (2⁷ = 128).
- Agar aap ke paas aisa script hai jo achhe par 0 aur bure par 1 ke saath exit kare, to `git bisect run npm test` poori talaash khud karta hai.
- Commit maloom hone ke baad us ka diff parhein: chhoti tabdeeli me wajah aam taur par wazeh hoti hai.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Changing random things until it works">

```text
// try: add a setTimeout? wrap in try/catch? change == to ===? reinstall node_modules?
// …it works now, nobody knows why, and it breaks again next week
```

</Bad>
<Good title="Form a guess, test it, then fix the cause">

```text
// Guess: "price is a string from the input"
// Check: breakpoint → Scope shows price: "19.99"
// Fix:   const price = Number(input.value)
// Prove: test with "19.99" and "5" inputs
```

</Good>
</Compare>

<Compare>
<Bad title="Hiding the error">

```javascript
function parseSettings(text) {
  try {
    return JSON.parse(text);
  } catch {
    return {};
  }
}
console.log(parseSettings("{theme: 'dark'}"));
```

```text output
{}
```

</Bad>
<Good title="Make the problem visible">

```javascript
function parseSettings(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    console.error("Settings are not valid JSON:", error.message, "| input:", text);
    return {};
  }
}
console.log(parseSettings("{theme: 'dark'}"));
```

```text output
Settings are not valid JSON: Expected property name or '}' in JSON at position 1 (line 1 column 2) | input: {theme: 'dark'}
{}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Debugging the wrong layer**: check the Network tab and server logs before blaming the UI.
- **Reading only the last error**: the **first** error in the console is usually the cause; later ones are consequences.
- **Not reading the whole message**: it often names the exact property, value or file.
- **Leaving `debugger;` and debug logs in committed code.** Use a linter rule.
- **Fixing the symptom** (`if (!rule) return 0`) instead of the cause (codes not normalised).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ghalat layer debug karna**: UI ko ilzam dene se pehle Network tab aur server logs check karein.
- **Sirf aakhri error parhna**: console ka **pehla** error aam taur par wajah hai; baad wale nataij hain.
- **Poora paighaam na parhna**: ye aksar bilkul wo property, value ya file batata hai.
- **Commit hue code me `debugger;` aur debug logs chhor dena.** Linter rule lein.
- **Wajah ke bajaye nishani theek karna** (`if (!rule) return 0`) (codes ek jaise nahi kiye gaye).

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- Follow a method: **reproduce → read → narrow down → understand → fix → prove**.
- Read the **first** error: message (what), `file:line:column` (where), stack (how you got there).
- Log with **labels**, inputs, outputs and expected values; `console.table`, `console.assert`; log **snapshots** of objects that change.
- Use **breakpoints** / `debugger;` to pause and inspect Scope, Watch and Call Stack; step over, into and out; turn on **Pause on exceptions**.

- Debug Node with VS Code's JavaScript Debug Terminal or `node --inspect`.
- Lock in fixes with a **failing-then-passing test**; use `git bisect` for regressions.

</En>

- Node ko VS Code ke JavaScript Debug Terminal ya `node --inspect` se debug karein.

<DeepDive title="More debugging tools">

**More breakpoint types (Chrome Sources).** DOM breakpoints (pause when an element changes: Elements → right-click → Break on), XHR/fetch breakpoints (pause when a URL is requested), event listener breakpoints (pause on any `click`), and **logpoints** (log without editing code).

**Console utilities (DevTools only).** `$0` is the element selected in Elements; `copy(value)` copies to the clipboard; `monitor(fn)` logs calls; `queryObjects(Constructor)` lists instances; `getEventListeners(el)` shows listeners.

**Performance and memory.** The Performance panel records what the main thread does (long tasks, layout, paint); the Memory panel takes heap snapshots to find leaks (compare two snapshots and look at what grew).

**React DevTools** shows the component tree, props, state and why a component re-rendered.

**Production debugging.** Error-tracking services (Sentry and similar) capture errors from users' browsers with stack traces (via uploaded source maps), breadcrumbs and environment info. Structured server logs with a request id let you follow one request across services.

**Rubber-duck debugging.** Explaining the code line by line to someone (or a rubber duck) often reveals the wrong assumption before they say a word.

**Minimal reproduction.** Remove everything unrelated until the bug still happens in the smallest possible code. It's also what maintainers ask for in GitHub issues.

</DeepDive>

<DeepDive title="Real world: the bug that only happened on Mondays">

A booking app's "This week" view showed no bookings, but only on Mondays, and only for some users. Developers couldn't reproduce it during the rest of the week, so the ticket sat for weeks with comments like "works on my machine".

Someone finally followed the method:

1. **Reproduce**: they set their computer's clock and time zone to Monday 1 AM in Sydney. The bug appeared immediately.
2. **Read**: no error, just an empty list. The Network tab showed the request `GET /bookings?from=2026-11-15&to=2026-11-21`, a week that had **already ended** in Sydney.
3. **Narrow down**: a breakpoint in `getWeekRange()` showed it calculated "start of week" using the server's UTC date, while the user's local date was already a day ahead.
4. **Fix**: calculate the week range in the **user's time zone** and send ISO instants with offsets.
5. **Prove**: a test that fakes "Monday 1 AM in Australia/Sydney" and "Sunday 11 PM in America/Los_Angeles" and checks the range for both.

Lesson: "can't reproduce" usually means "haven't found the right conditions yet". Time zones, slow networks, different data and different browsers are the usual suspects.

</DeepDive>

<DeepDive title="Security lens">

- **Never ship debug code**: `debugger;` statements, verbose logs with personal data, and debug endpoints (`/debug`, `?debug=true`) leak information.
- **Don't expose stack traces to users** in production; log them on the server with an error id.
- **Source maps** reveal your original source code. Upload them privately to your error tracker, or protect them, if your code contains anything sensitive.
- **Never run `--inspect` on a public interface**: the inspector allows arbitrary code execution. Bind to `127.0.0.1` and use SSH tunnels for remote debugging.
- **Be careful pasting production data** (tokens, customer details) into issues, chats or online tools while debugging. Redact first.
- **Watch for "self-XSS" social engineering**: never paste code a stranger gives you into your browser console.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you approach debugging an issue you can't immediately see the cause of?">
Reproduce it reliably and minimally, read any error and stack trace, form hypotheses and test them one at a time with logs or breakpoints while checking assumptions about inputs, outputs and types, narrow the problem area by halving it, then fix the root cause and add a test that fails without the fix.
</QA>

<QA q="What is the difference between step over, step into and step out?">
Step over runs the current line, including any function calls, and pauses at the next line. Step into enters a function called on the current line. Step out runs the rest of the current function and pauses after it returns to the caller.
</QA>

<QA q="What is a source map and why does it matter for debugging?">
A source map maps compiled or minified code back to the original source files, so stack traces and breakpoints refer to the code you wrote, such as TypeScript or JSX, instead of the bundled output.
</QA>

<QA q="How would you find which commit introduced a regression?">
Use git bisect: mark a known good and a known bad commit, then test the commits Git checks out in a binary search, or automate it with git bisect run and a script, until Git identifies the first bad commit.
</QA>

<QA q="Why might console.log show a different value than the one an object had when it was logged?">
Browser consoles show objects by reference and evaluate their properties when expanded, so later mutations appear. Logging a snapshot, such as a structuredClone or JSON string, preserves the state at logging time.
</QA>

</DeepDive>

<Terms>
  <Term name="Bug">A defect causing behaviour different from what was intended.</Term>
  <Term name="Reproduction">Reliably triggering a bug with known steps.</Term>
  <Term name="Stack trace">The list of active function calls when an error occurred.</Term>
  <Term name="Breakpoint">A marker where the debugger pauses execution.</Term>
  <Term name="Conditional breakpoint">A breakpoint that only pauses when an expression is true.</Term>
  <Term name="Logpoint">A breakpoint that logs a message without pausing.</Term>
  <Term name="debugger statement">Code that pauses execution when a debugger is attached.</Term>
  <Term name="Step over">Execute the current line and pause at the next.</Term>
  <Term name="Step into">Enter the function called on the current line.</Term>
  <Term name="Watch expression">An expression the debugger re-evaluates while paused.</Term>
  <Term name="Source map">A file mapping built code back to original sources.</Term>
  <Term name="Regression">A bug in something that previously worked.</Term>
  <Term name="git bisect">A Git command that binary-searches history for a bad commit.</Term>
  <Term name="Minimal reproduction">The smallest code that still shows the bug.</Term>
</Terms>

<DeepDive title="More practice">

1. Take a working function, break it on purpose, and find the bug using only the debugger.
2. Set a conditional breakpoint that pauses only on the 50th loop iteration.
3. Turn on "Pause on caught exceptions" on a real website and see what's being swallowed.
4. Debug a Node script in VS Code's JavaScript Debug Terminal.
5. Use the Network tab's "Copy as cURL" and replay a request in the terminal.
6. Write a failing `node --test` test for a bug, fix it, and watch it pass.
7. Create a small Git repo with 8 commits, break something in commit 5, and find it with `git bisect`.
