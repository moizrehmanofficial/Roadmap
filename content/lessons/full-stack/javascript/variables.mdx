## At a glance

<Glance>
<What>
<Tr>
<En>

When you use an app, it has to **remember** things. You type your name in a form, and the next page says "Welcome, Sara!". The app kept your name somewhere.

A **variable** is that "somewhere". Think of a small **box with a label** on it:

- the **label** is the variable's **name**, like `userName`
- the thing **inside** the box is what it remembers, like `Sara`. This is called the **value**.

When the program needs the information, it finds the box by its label and looks inside.

</En>
<Ur>

Jab aap koi app chalate hain, use cheezen **yaad rakhni** parti hain. Aap form me apna naam likhte hain, aur agle page par aata hai "Welcome, Sara!". App ne aap ka naam kahin sambhal kar rakha tha.

Wo "kahin" hi **variable** hai. Isay ek chhota **dabba** samjhein jis par **label** laga ho:

- **label** = variable ka **naam**, jaise `userName`
- dabbe ke **andar** jo cheez hai, jaise `Sara`. Isay **value** kehte hain.

Jab program ko wo cheez chahiye hoti hai, wo label se dabba dhoondta hai aur andar dekh leta hai.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

Without variables, a program would **forget everything immediately**. Imagine a calculator that forgets the first number as soon as you press **+**. It could never add anything.

A shopping website must remember **what's in your cart** and **your total bill**. Each of those is kept in a variable.

</En>
<Ur>

Variables ke baghair program sab kuch **foran bhool** jaye ga. Socho ek calculator jo **+** dabate hi pehla number bhool jaye. Wo kabhi jama nahi kar sakega.

Shopping website ko yaad rakhna parta hai ke **cart me kya hai** aur **total bill kitna hai**. Ye har cheez ek variable me rakhi jati hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Whenever the program needs to **remember something to use later**:

- the user's name after they log in
- the score in a game, which goes up with every point
- the total of a shop bill
- whether dark mode is **on** or **off**

In real code, almost every line uses a variable.

</En>
<Ur>

Jab bhi program ko koi cheez **baad me istemal karne ke liye yaad rakhni** ho:

- login ke baad user ka naam
- game ka score, jo har point par barhta hai
- dukaan ke bill ka total
- dark mode **on** hai ya **off**

Asal code me taqreeban har line me variable istemal hota hai.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```js
let userName = "Sara";
```

Read it like a sentence: **"Make a new box, label it `userName`, and put `Sara` inside."**

- `let` = make a new box
- `userName` = the label (name)
- `=` = put this inside
- `"Sara"` = the thing to keep (the value)

</En>
<Ur>

```js
let userName = "Sara";
```

Isay ek jumle ki tarah parhein: **"Ek naya dabba banao, us par `userName` ka label lagao, aur andar `Sara` rakh do."**

- `let` = naya dabba banao
- `userName` = label (naam)
- `=` = andar ye rakh do
- `"Sara"` = jo cheez rakhni hai (value)

</Ur>
</Tr>
</How>
</Glance>

<Step title="Make a box and look inside">

<Tr>
<En>

</En>
<Ur>

- **Line 1:** dabba banao, label `userName` lagao, andar `"Sara"` rakho.
- **Line 2:** "`userName` wale dabbe ke andar jo hai wo dikhao." Screen par **Sara** aata hai.
- Dhyan dein: humne `userName` **quotes ke baghair** likha, isliye JavaScript ne us label wala **dabba** dhoonda aur andar ki cheez dikha di.

<Step title="Text needs quotes, numbers don't">

<Tr>
<En>
Text (called a **string**) always goes inside quotes. Numbers are written without quotes, so JavaScript can do maths with them.
</En>
<Ur>
Text (jise **string** kehte hain) hamesha quotes ke andar likha jata hai. Numbers quotes ke baghair likhe jate hain, taake JavaScript un se hisaab kar sake.
</Ur>
</Tr>

```javascript
let city = "Austin";
let temperature = 31;
console.log(city);
console.log(temperature + 2);
console.log(city + " is " + temperature + " degrees today");
```

```text output
Austin
33
Austin is 31 degrees today
```

<Happened>
<Tr>
<En>

- `"Austin"` has quotes: it's text.
- `31` has no quotes: it's a number, so `temperature + 2` really adds and gives **33**.
- With text, `+` **joins** pieces together into one sentence.

</En>
<Ur>

- `"Austin"` quotes me hai: ye text hai.
- `31` quotes ke baghair hai: ye number hai, isliye `temperature + 2` waqai jama karta hai aur **33** deta hai.
- Text ke saath `+` tukron ko **jor** kar ek jumla bana deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Change what's inside the box">

<Tr>
<En>
A box made with `let` can get a **new value** later. The old value is thrown away and the new one takes its place, just like the shopkeeper crossing out the old total.
</En>
<Ur>
`let` se bane dabbe me baad me **nayi value** rakhi ja sakti hai. Purani value nikal jati hai aur nayi us ki jagah aa jati hai, bilkul jaise dukaandaar purana total kaat kar naya likhta hai.
</Ur>
</Tr>

```javascript
let total = 0;
console.log(total);
total = 150;
console.log(total);
total = total + 280;
console.log(total);
```

```text output
0
150
430
```

<Happened>
<Tr>
<En>

- `total = 150;` throws away `0` and puts `150` in the box. (No `let` this time: the box already exists.)
- `total = total + 280;` means: **take what's in the box (150), add 280, and put the answer (430) back in the box.**

</En>
<Ur>

- `total = 150;` purana `0` nikaal kar dabbe me `150` rakh deta hai. (Is dafa `let` nahi likha: dabba pehle se bana hua hai.)
- `total = total + 280;` ka matlab: **dabbe me jo hai (150) wo lo, us me 280 jamao, aur jawab (430) wapas dabbe me rakh do.**

</Ur>
</Tr>
</Happened>

</Step>

<Step title="= means 'put inside', not 'is equal to'">

<Tr>
<En>

In school maths, `x = x + 5` makes no sense. In programming, `=` is an **instruction**, not a question:

**"Work out the right side first, then put the answer in the box on the left."**

So `score = score + 5` simply means "the new score is the old score plus 5". There's also a short way to write it: `score += 5`.

To **check** if two things are equal, JavaScript uses `===` (you'll learn it in a later lesson).

</En>
<Ur>

School ki maths me `x = x + 5` ka koi matlab nahi banta. Programming me `=` ek **hukm (instruction)** hai, sawal nahi:

**"Pehle right side ka hisaab karo, phir jawab left wale dabbe me rakh do."**

To `score = score + 5` ka seedha matlab hai "naya score = purana score + 5". Isay chhota karke `score += 5` bhi likh sakte hain.

Do cheezon ko **barabar check** karne ke liye JavaScript `===` istemal karta hai (ye agle lessons me aayega).

</Ur>
</Tr>

```javascript
let score = 10;
score = score + 5;
console.log(score);
score += 5;
console.log(score);
```

```text output
15
20
```

</Step>

<Step title="A box that can never be refilled: const">

<Tr>
<En>
Some things should **never change** while the program runs, like a tax rate or a website address. Make those with `const` (short for "constant"). If any code tries to put something else in that box, JavaScript **stops it with an error**. That protects you from mistakes.
</En>
<Ur>
Kuch cheezen program chalte waqt **kabhi nahi badalni chahiyen**, jaise tax rate ya website ka address. Unhe `const` se banayen ("constant" ka chhota roop). Agar koi code us dabbe me kuch aur rakhne ki koshish kare, to JavaScript **error de kar rok deta hai**. Is tarah aap ghaltiyon se bach jate hain.
</Ur>
</Tr>

```javascript
const TAX_RATE = 0.17;
const price = 1000;
console.log("Total with tax:", price + price * TAX_RATE);

try {
  TAX_RATE = 0.2;
} catch (error) {
  console.log("Error:", error.message);
}
```

```text output
Total with tax: 1170
Error: Assignment to constant variable.
```

<Happened>
<Tr>
<En>

- `TAX_RATE` is a `const`, so trying to change it to `0.2` causes the error **"Assignment to constant variable."** In plain words: "you can't put something new in a constant box."
- `try { ... } catch { ... }` means "try this; if it fails, run the second part instead of crashing". It's only here so you can see the error message.

</En>
<Ur>

- `TAX_RATE` ek `const` hai, isliye use `0.2` me badalne par error aata hai: **"Assignment to constant variable."** Aasaan alfaaz me: "constant dabbe me nayi cheez nahi rakh sakte."
- `try { ... } catch { ... }` ka matlab: "ye try karo; agar fail ho jaye to crash hone ke bajaye doosra hissa chala do." Ye sirf isliye hai taake aap error ka message dekh sakein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Should I use let or const?">

<Tr>
<En>

Ask yourself one question: **"Will I put a different value in this box later?"**

- **No** → use `const`. This is the answer **most of the time**.
- **Yes** → use `let`.

You will also see `var` in old code and old tutorials. It's the **old** way of making variables and it causes confusing bugs, so **don't use it** in new code. (The "Go deeper" section at the bottom shows why.)

</En>
<Ur>

Apne aap se ek sawal poochein: **"Kya main baad me is dabbe me koi doosri value rakhunga?"**

- **Nahi** → `const` istemal karein. **Zyada tar** yahi jawab hota hai.
- **Haan** → `let` istemal karein.

Purane code aur purane tutorials me aap `var` bhi dekhenge. Ye variables banane ka **purana** tareeqa hai aur is se uljhe hue bugs aate hain, isliye naye code me **ise istemal na karein**. (Neeche "Go deeper" me iski wajah hai.)

</Ur>
</Tr>

<FlowStep>New variable</FlowStep>
<FlowStep>Will the value change later?</FlowStep>
<FlowStep>No → **const**</FlowStep>
<FlowStep>Yes → **let**</FlowStep>

<Step title="What can go inside a box?">

<Tr>
<En>
A box can hold different **kinds** of information. Each kind is called a **type**. These are the ones you'll use every day:
</En>
<Ur>
Dabbe me mukhtalif **qisam** ki information rakhi ja sakti hai. Har qisam ko **type** kehte hain. Ye wo types hain jo aap rozana istemal karenge:
</Ur>
</Tr>

```javascript
const age = 24;                              // number
const name = "Sam";                          // string = text
const isLoggedIn = true;                     // boolean = true or false
const cart = ["bread", "milk"];              // array = a list
const user = { name: "Sam", role: "admin" }; // object = a record with named parts
let notSetYet;                               // undefined = an empty box

console.log(typeof age, typeof name, typeof isLoggedIn);
console.log(cart[0], "and", cart.length, "items");
console.log(user.name, "is", user.role);
console.log(notSetYet);
```

```text output
number string boolean
bread and 2 items
Sam is admin
undefined
```

<Happened>
<Tr>
<En>

- `typeof` tells you **what kind** of value is in a box.
- `cart[0]` is the **first** item of the list. Computers start counting at **0**, not 1.
- `user.name` reads the `name` part of the object.
- `notSetYet` was made with nothing inside, so it shows `undefined`, which means "this box is empty".

</En>
<Ur>

- `typeof` batata hai ke dabbe me **kis qisam** ki value hai.
- `cart[0]` list ka **pehla** item hai. Computer ginti **0** se shuru karta hai, 1 se nahi.
- `user.name` object ka `name` wala hissa parhta hai.
- `notSetYet` bina kisi cheez ke banaya gaya, isliye `undefined` dikhata hai, yani "ye dabba khaali hai".

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A box only exists inside its { }">

<Tr>
<En>

Code is often grouped inside curly braces `{ }`. A variable made **inside** a pair of braces only exists **inside those braces**. The area where a variable can be used is called its **scope**.

Think of a house. Something kept in the **living room** can be seen from every room. Something kept **inside your bedroom** can't be seen from the living room. You can look out of your room, but nobody can look in.

</En>
<Ur>

Code aksar curly braces `{ }` ke andar group hota hai. Jo variable braces ke **andar** banaya jaye, wo sirf **un braces ke andar** mojood hota hai. Jis hisse me variable istemal ho sakta hai, use us ka **scope** kehte hain.

Ek ghar socho. **Living room** me rakhi cheez har kamre se nazar aati hai. **Aap ke bedroom ke andar** rakhi cheez living room se nazar nahi aati. Aap apne kamre se bahar dekh sakte hain, lekin bahar wala andar nahi dekh sakta.

</Ur>
</Tr>

```javascript
const appName = "DevGuide";          // living room: visible everywhere

if (true) {
  const badge = "★";                 // bedroom: only inside these braces
  console.log(appName, badge);       // inside: both are visible
}

console.log(typeof badge);           // outside: badge doesn't exist
```

```text output
DevGuide ★
undefined
```

<Happened>
<Tr>
<En>

- Inside the braces, the code can see `badge` **and** the outer `appName`.
- After the closing `}`, `badge` is gone, so `typeof badge` says `undefined`.
- This is useful: two different parts of a program can each have their own `total` without disturbing each other.

</En>
<Ur>

- Braces ke andar code `badge` **aur** bahar wala `appName` dono dekh sakta hai.
- Band hone wale `}` ke baad `badge` khatam ho jata hai, isliye `typeof badge` `undefined` batata hai.
- Ye faida mand hai: program ke do alag hisson ka apna apna `total` ho sakta hai, aur wo ek doosre ko kharab nahi karte.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="const lists can still get new items">

<Tr>
<En>

This surprises almost everyone. `const` means **the label stays on this box forever**. It does **not** mean the box is sealed.

So with a list or an object, you **can** add or change things **inside** the same box. You just can't swap it for a different box.

</En>
<Ur>

Ye baat taqreeban sab ko hairaan karti hai. `const` ka matlab hai **label hamesha isi dabbe par rahega**. Iska matlab ye **nahi** ke dabba seal ho gaya.

To list ya object ke saath, aap **usi dabbe ke andar** cheezen daal ya badal **sakte hain**. Bas use kisi doosre dabbe se badal nahi sakte.

</Ur>
</Tr>

```javascript
const cart = ["bread"];
cart.push("milk");                 // add an item inside the same box: allowed
console.log(cart);

try {
  cart = ["eggs"];                 // swap in a different box: not allowed
} catch (error) {
  console.log("Error:", error.message);
}
```

```text output
[ 'bread', 'milk' ]
Error: Assignment to constant variable.
```

<Happened>
<Tr>
<En>

- `cart.push("milk")` adds an item to the **same** list. Allowed.
- `cart = ["eggs"]` tries to put a **whole new list** in the box. Not allowed with `const`.

</En>
<Ur>

- `cart.push("milk")` **usi** list me ek item jorta hai. Ijazat hai.
- `cart = ["eggs"]` dabbe me **bilkul nayi list** rakhne ki koshish karta hai. `const` me iski ijazat nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Copying: numbers get a photocopy, objects get shared">

<Tr>
<En>

When you copy a **number or text** into another variable, you get a **separate copy**, like a photocopy. Scribble on the copy and the original stays clean.

When you copy a **list or object**, you don't get a new one. Both names point to the **same** thing, like sharing one Google Doc link with a friend: if they edit it, you see the change too.

</En>
<Ur>

Jab aap **number ya text** ko doosre variable me copy karte hain, to **alag copy** milti hai, jaise photocopy. Copy par kuch likh dein, asal saaf rehta hai.

Jab aap **list ya object** copy karte hain, to nayi cheez nahi banti. Dono naam **ek hi** cheez ki taraf ishara karte hain, jaise dost ke saath ek Google Doc ka link share karna: wo edit kare to aap ko bhi tabdeeli nazar aati hai.

</Ur>
</Tr>

```javascript
let a = 10;
let b = a;              // a photocopy of 10
b = 20;
console.log("numbers:", a, b);

const original = { qty: 1 };
const sameObject = original;        // NOT a copy: a second name for the same object
sameObject.qty = 99;
console.log("original:", original.qty);

const realCopy = { ...original };   // a real, separate copy
realCopy.qty = 5;
console.log("original:", original.qty, "copy:", realCopy.qty);
```

```text output
numbers: 10 20
original: 99
original: 99 copy: 5
```

<Happened>
<Tr>
<En>

- Changing `b` didn't change `a`: numbers are copied.
- Changing `sameObject` **also changed** `original`, because they are one object with two names.
- `{ ...original }` makes a **real** copy, so changing it leaves the original alone.

</En>
<Ur>

- `b` badalne se `a` nahi badla: numbers copy hote hain.
- `sameObject` badalne se `original` **bhi badal gaya**, kyunke ye ek hi object ke do naam hain.
- `{ ...original }` **asli** copy banata hai, isliye use badalne se original par koi asar nahi hota.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Give your boxes good names">

<Tr>
<En>

A good name tells everyone **what is inside the box**. `totalPrice` is clear; `x` or `data2` means nothing.

**Rules** (if you break these, the code won't run):

- Use only letters, numbers, `_` and `$`. No spaces or dashes.
- Don't start with a number: `user1` is fine, `1user` is not.
- Don't use JavaScript's own words like `let`, `const` or `class`.
- Capital letters matter: `total` and `Total` are **two different** boxes.

**Good habits** (what professionals do):

- `camelCase` for normal names: `cartTotal`, `userName`.
- `UPPER_CASE` for fixed settings: `TAX_RATE`.
- Start true/false names with `is`, `has` or `can`: `isLoggedIn`.
- Use plural names for lists: `users`, `orders`.

</En>
<Ur>

Acha naam sab ko batata hai ke **dabbe ke andar kya hai**. `totalPrice` saaf hai; `x` ya `data2` ka koi matlab nahi.

**Qawaid** (inhe torenge to code nahi chalega):

- Sirf letters, numbers, `_` aur `$`. Spaces ya dash (`-`) nahi.
- Number se shuru na karein: `user1` theek hai, `1user` nahi.
- JavaScript ke apne lafz jaise `let`, `const` ya `class` istemal na karein.
- Capital letters ka farq parta hai: `total` aur `Total` **do alag** dabbe hain.

**Achi aadatein** (jo professionals karte hain):

- Aam naamon ke liye `camelCase`: `cartTotal`, `userName`.
- Fixed settings ke liye `UPPER_CASE`: `TAX_RATE`.
- True/false wale naam `is`, `has` ya `can` se shuru karein: `isLoggedIn`.
- Lists ke liye plural naam: `users`, `orders`.

</Ur>
</Tr>

</Step>

<DeepDive title="Why var causes bugs (and the famous setTimeout puzzle)">

`var` ignores `if` and loop braces; only a **function** contains it. That's the main reason `let` and `const` were added in 2015.

```javascript
if (true) {
  var leaked = "var escaped the block";
  let contained = "let stays inside";
}
console.log(leaked);
console.log(typeof contained);
```

```text output
var escaped the block
undefined
```

The classic interview puzzle caused by this:

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log("var:", i), 0);
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log("let:", j), 0);
}
```

```text output
var: 3
var: 3
var: 3
let: 0
let: 1
let: 2
```

- `setTimeout(…, 0)` means "run this a moment later, after the current code finishes".
- With `var` there is **one** `i` for the whole loop. By the time the delayed code runs, the loop is over and `i` is 3.
- With `let`, every round gets its **own** `j`, so each delayed function remembers its own number.

</DeepDive>

<DeepDive title="Hoisting and the Temporal Dead Zone">

Before running your code, JavaScript scans it and notes every variable name. This is called **hoisting**. What a name holds before its line runs depends on the keyword:

```javascript
console.log(oldStyle);            // var: no error, just undefined
var oldStyle = "var value";

try {
  console.log(modern);            // let: in the Temporal Dead Zone
} catch (error) {
  console.log(error.name + ":", error.message);
}
let modern = "let value";

console.log(sayHi());             // function declarations work early
function sayHi() { return "hi from a hoisted function"; }
```

```text output
undefined
ReferenceError: Cannot access 'modern' before initialization
hi from a hoisted function
```

- `var` gives a silent `undefined`, which hides bugs.
- `let`/`const` give a clear error. The time between the start of the block and their line is called the **Temporal Dead Zone (TDZ)**.
- The loud error is a **good thing**: using a value before it's set is almost always a mistake.

</DeepDive>

<DeepDive title="Same name twice, and shadowing">

`var` lets you create the same name twice without any warning. `let` and `const` refuse with `SyntaxError: Identifier 'y' has already been declared`.

Making the same name in an **inner** block is allowed. It's called **shadowing**: the inner name hides the outer one inside those braces.

```javascript
var x = 1;
var x = 2;                   // var: silently allowed
console.log("x is", x);

const level = "outer";
{
  const level = "inner";     // a different variable with the same name
  console.log("inside:", level);
}
console.log("outside:", level);
```

```text output
x is 2
inside: inner
outside: outer
```

</DeepDive>

<DeepDive title="Forgetting the keyword creates a global (in old code)">

In old JavaScript, writing `totl = 500` without a keyword silently created a **global** variable, usually because of a typo. Modern code (modules, React, Next.js, Node.js modules, TypeScript) runs in **strict mode**, which throws an error instead:

```javascript
"use strict";
let total = 100;
try {
  totl = 500;               // typo, never declared
} catch (error) {
  console.log(error.name + ":", error.message);
}
console.log("total is still", total);
```

```text output
ReferenceError: totl is not defined
total is still 100
```

</DeepDive>

<DeepDive title="Freezing objects and deep copies">

To stop the **contents** of an object from changing, use `Object.freeze`:

```javascript
const settings = Object.freeze({ theme: "dark" });
try {
  settings.theme = "light";       // frozen: an error in strict mode
} catch (error) {
  console.log("Frozen:", error.name);
}
console.log(settings.theme);
```

```text output
Frozen: TypeError
dark
```

- `Object.freeze` is **shallow**: objects inside the object can still change.
- `{ ...obj }` copies only the top level. For a full copy of nested data, use `structuredClone(obj)`.

</DeepDive>

<DeepDive title="Variables and memory">

While a value can be reached through some variable, it stays in memory (RAM). When nothing points to it any more, JavaScript's **garbage collector** frees that memory automatically.

**Memory leaks** happen when a long-living variable (a global, a module-level array, a cache) keeps pointing to data that should have been thrown away. Memory use grows until the app slows down or crashes. Keep variables in the smallest scope that works, and give caches a size limit.

</DeepDive>

<DeepDive title="Real-world bug: one variable shared by every user">

A Next.js API route keeps a list of "recent searches" in a variable at the top of the file:

```javascript
// app/api/search/route.js — BUG: module-level state
let recentSearches = [];                  // lives as long as the server process

export async function GET(request) {
  const q = new URL(request.url).searchParams.get("q");
  recentSearches.push(q);                 // every user's searches go into ONE array
  return Response.json({ recent: recentSearches.slice(-5) });
}
```

It "works" on a laptop. In production:

1. **Privacy leak:** user A sees user B's searches, because every request shares the same variable.
2. **Memory leak:** the array grows forever.
3. **Inconsistency:** with several server instances, each has its own copy, so results jump around.

The fix is about **scope**: per-request data lives in variables **inside** the handler, per-user data lives in a database keyed by user ID, and only shared read-only things (a database client, settings) belong at the top of the file, as `const`.

```javascript
// Fixed
import { db } from "@/lib/db";            // shared client: module-level const is correct

export async function GET(request) {
  const userId = await getUserId(request);           // per request
  const q = new URL(request.url).searchParams.get("q");
  await db.search.create({ data: { userId, q } });
  const recent = await db.search.findMany({ where: { userId }, take: 5, orderBy: { id: "desc" } });
  return Response.json({ recent: recent.map((r) => r.q) });
}
```

</DeepDive>

<DeepDive title="Security lens">

Variables decide **where** data lives and **who** can reach it.

- **Shared state across requests** (module-level `let` in Node.js/Next.js) can leak one user's data to another.
- **Secrets in front-end variables are public.** Anything in browser JavaScript, including `NEXT_PUBLIC_*` and `VITE_*` environment variables, is visible to every visitor in DevTools. Real API keys must stay on the server.
- **Accidental globals** (old non-strict code) can be read or overwritten by any other script on the page, including injected attacker scripts.
- **Logging whole objects** (`console.log(user)`) can write passwords and tokens into logs. Log specific, safe fields.
- **Prototype pollution:** merging untrusted JSON into objects (`Object.assign(config, req.body)`) can change the behaviour of every object in the app. Validate input and copy only known fields.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the differences between var, let and const?">
var is function-scoped, can be re-declared, and is hoisted with the value undefined; at the top level of a classic script it also becomes a property of the global object. let and const are block-scoped, cannot be re-declared in the same scope, and are in the temporal dead zone until their declaration runs, so early access throws a ReferenceError. const must be initialized and cannot be reassigned, though objects it refers to can still be mutated.
</QA>

<QA q="What is hoisting?">
Before executing a scope, JavaScript registers all declarations in it. var declarations are initialized to undefined, so they can be read early without an error. Function declarations are hoisted with their full body. let, const and class declarations are registered but left uninitialized until their line runs; accessing them earlier throws a ReferenceError (the temporal dead zone).
</QA>

<QA q="If const means constant, why can I change a const array?">
const prevents rebinding the variable name to a different value; it does not make the value itself immutable. A const array or object still refers to the same object, whose contents can change. To prevent changes to the value, use Object.freeze (shallowly) or immutable update patterns.
</QA>

<QA q="Why does a for loop with var and setTimeout print 3, 3, 3, while let prints 0, 1, 2?">
var creates one function-scoped variable shared by every iteration; the callbacks run after the loop finishes, when i is already 3. let creates a new binding for each iteration, so each callback keeps its own value.
</QA>

<QA q="What is the difference between primitive and reference values?">
Primitives (string, number, boolean, null, undefined, bigint, symbol) are copied by value: assigning one variable to another makes an independent copy. Objects, arrays and functions are copied by reference: both variables point to the same object, so changes through one are visible through the other. Copying needs spread, Object.assign or structuredClone.
</QA>

</DeepDive>
