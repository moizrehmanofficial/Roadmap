<Callout type="tip" title="In one minute">
A **variable** is a named label for a value stored in memory. Create one with `const` (cannot be reassigned) or `let` (can be reassigned). Both are **block-scoped**: they exist only inside the nearest `{ }`. Avoid `var`: it is **function-scoped**, can be re-declared, and is **hoisted** with the value `undefined`, which hides bugs. `const` protects the **binding**, not the value — a `const` object can still be changed. Default to `const`; use `let` only when the value must change.
</Callout>

## What is it?

### The idea

A program needs to remember things: a user's name, a cart total, an API response, whether a menu is open. A **variable** gives a value a **name** so you can store it, read it and change it later.

```javascript
const userName = "Moiz";
let cartTotal = 0;
cartTotal = cartTotal + 1500;
console.log(userName, "has", cartTotal, "in the cart");
```

A good mental model: the value lives somewhere in memory (RAM). The variable is a **label** attached to it. When you write `userName`, JavaScript follows the label to the value.

```text
  name (binding)          value in memory
  ──────────────          ───────────────
  userName   ───────────► "Moiz"
  cartTotal  ───────────► 1500
```

### Four words you need

| Word | Meaning | Example |
| --- | --- | --- |
| **Declaration** | Creating the name | `let count;` |
| **Initialization** | Giving it its first value | `let count = 0;` |
| **Assignment** | Putting a new value into an existing variable | `count = 5;` |
| **Binding** | The connection between the name and the value | `count` → `5` |

### The three keywords

| | `const` | `let` | `var` |
| --- | --- | --- | --- |
| Added in | ES2015 (2015) | ES2015 (2015) | Original JavaScript (1995) |
| Can be reassigned | No | Yes | Yes |
| Must be initialized when declared | Yes | No (starts as `undefined`) | No (starts as `undefined`) |
| Scope | Block `{ }` | Block `{ }` | Function (or global) |
| Can be re-declared in the same scope | No | No | Yes (silently) |
| Usable before its declaration line | No — error (TDZ) | No — error (TDZ) | Yes — value is `undefined` |
| Creates a property on the global object (`window`) at top level | No | No | Yes |
| Use it? | **Default** | When the value must change | Only in legacy code |

## Why does it matter?

- **Every line of every program uses variables.** React state, API handlers, loops, configuration — all of it.
- **Most "impossible" beginner bugs are variable bugs:** a value that is `undefined` when it "should" be set, a loop where every callback prints the same number, a variable accidentally shared between requests, a typo that silently created a new global.
- **Readability:** `const` tells the reader "this never changes", which makes code much easier to reason about. In a 300-line component, that is a big deal.
- **Interviews:** `var` vs `let` vs `const`, hoisting, the temporal dead zone and closures in loops are among the most asked JavaScript questions at every level.
- **Security and correctness on the server:** a variable declared in the wrong scope in a Node.js server (module level instead of inside the request handler) is **shared between all users** — a real source of data leaks.

## When and where do you use it?

You use variables everywhere, but the *kind* of variable depends on the job:

| Situation | Use | Example |
| --- | --- | --- |
| A value that never changes after it is set | `const` | `const API_URL = "https://api.example.com";` |
| Objects and arrays you modify but never replace | `const` | `const cart = []; cart.push(item);` |
| Imported modules, functions | `const` | `const express = require("express");` |
| A counter, accumulator or flag that changes | `let` | `let retries = 0; retries++;` |
| A value set conditionally | `let` (or a `const` with a ternary) | `let label; if (x) label = "A"; else label = "B";` |
| Loop counters | `let` | `for (let i = 0; i < 10; i++)` |
| Old scripts, some legacy libraries | `var` | You will **read** it; do not write it |

Where they show up in your stack:

- **React:** `const [count, setCount] = useState(0);` — `count` is a `const` for *this render*; React gives you a new one next render.
- **Next.js / Node.js:** `const prisma = new PrismaClient();` at module level (shared), `const user = await getUser(id);` inside a handler (per request).
- **Configuration:** `const port = process.env.PORT ?? 3000;`.

## How does it work?

### 1. Declaring, initializing and assigning

```javascript
let score;              // declared, value is undefined
console.log(score);     // undefined
score = 10;             // assigned
score += 5;             // reassigned → 15
console.log(score);

const max = 100;        // const must be initialized immediately
// const min;           // SyntaxError: Missing initializer in const declaration

let a = 1, b = 2, c = 3;   // several at once (allowed, but one per line is clearer)
console.log(a + b + c);
```

### 2. Scope — where a variable exists

**Scope** is the region of code where a name can be used. JavaScript has three main kinds:

| Scope | Created by | Who uses it |
| --- | --- | --- |
| **Global** | The top level of a script | Everything |
| **Function** | Every function body | `var`, `let`, `const` |
| **Block** | Any `{ }` — `if`, `for`, `while`, `try`, or a bare block | `let` and `const` only |

```javascript
const appName = "DevGuide";            // global (module) scope

function greet(user) {
  const message = "Hello " + user;     // function scope
  if (user === "admin") {
    const badge = "★";                 // block scope: only inside this if
    console.log(message, badge);
  }
  // console.log(badge);               // ReferenceError: badge is not defined
  return message;
}

console.log(greet("admin"));
console.log(appName);
// console.log(message);               // ReferenceError: message is not defined
```

Scopes nest like boxes. Code inside a box can see variables in **its own box and every box around it**, but not in boxes inside it. This rule — decided by where you **write** the code, not where it runs — is called **lexical scope**.

```text
┌ global ───────────────────────────────┐
│ appName                               │
│ ┌ function greet ──────────────────┐  │
│ │ user, message                    │  │
│ │ ┌ if block ───────────────────┐  │  │
│ │ │ badge                       │  │  │
│ │ │ can see: badge, message,    │  │  │
│ │ │ user, appName               │  │  │
│ │ └─────────────────────────────┘  │  │
│ └──────────────────────────────────┘  │
└───────────────────────────────────────┘
```

### 3. Why `var` is different: function scope

`var` ignores blocks. It only respects function boundaries:

```javascript
if (true) {
  var leaked = "I escaped the if block";
  let contained = "I stay inside";
}
console.log(leaked);                 // works — var leaks out of blocks
try {
  console.log(contained);
} catch (e) {
  console.log("contained:", e.name); // ReferenceError
}

function demo() {
  var insideFn = "function scoped";
}
demo();
console.log(typeof insideFn);        // "undefined" — var does respect functions
```

### 4. Hoisting and the Temporal Dead Zone (TDZ)

Before running a scope, JavaScript first scans it and **registers every declaration**. This is called **hoisting**. What differs is the value the name has before its line runs:

| Declaration | Registered early? | Value before the declaration line |
| --- | --- | --- |
| `var x` | Yes | `undefined` |
| `let x` / `const x` | Yes | **Uninitialized** — any access throws `ReferenceError` |
| `function f() {}` | Yes | The whole function — callable before its line |
| `const f = () => {}` | Yes (as const) | Uninitialized — TDZ |

The time between entering a scope and reaching a `let`/`const` line is the **Temporal Dead Zone**.

```javascript
console.log(oldStyle);   // undefined — no error, which hides the bug
var oldStyle = "var";

try {
  console.log(modern);   // in the TDZ
} catch (e) {
  console.log(e.name + ": " + e.message);
}
let modern = "let";

console.log(sayHi());    // works: function declarations are fully hoisted
function sayHi() { return "hi"; }
```

The TDZ is a **feature**: reading a variable before it is set is almost always a bug, and `let`/`const` make it fail loudly instead of continuing with `undefined`.

### 5. `const` protects the binding, not the value

`const` means "this **name** will always point to this **same value**". If the value is an object or array, its contents can still change:

```javascript
const user = { name: "Sara", role: "user" };
user.role = "admin";           // allowed — changing a property
user.lastLogin = "today";      // allowed — adding a property
console.log(user);

try {
  user = { name: "Someone else" };   // not allowed — rebinding the name
} catch (e) {
  console.log(e.name + ": " + e.message);
}

const tags = ["js"];
tags.push("ts");               // allowed
console.log(tags);

// To make the VALUE read-only, freeze it (shallow: nested objects are not frozen)
const config = Object.freeze({ port: 3000, db: { host: "localhost" } });
try { config.port = 9999; } catch (e) { console.log("frozen:", e.name); }
config.db.host = "changed";    // nested object is NOT frozen
console.log(config.port, config.db.host);
```

### 6. Primitives vs references: what gets copied

This is the single most important idea for avoiding "my data changed by itself" bugs.

- **Primitive values** — `string`, `number`, `boolean`, `null`, `undefined`, `bigint`, `symbol` — are copied **by value**.
- **Objects** — including arrays, functions, dates — are accessed **by reference**: assigning copies the **arrow**, not the object.

```javascript
let a = 10;
let b = a;        // copies the value 10
b = 20;
console.log(a, b);            // 10 20 — independent

const original = { qty: 1 };
const alias = original;       // copies the reference — same object
alias.qty = 99;
console.log(original.qty);    // 99 — both names point at one object

const copy = { ...original }; // new object (shallow copy)
copy.qty = 5;
console.log(original.qty, copy.qty);   // 99 5

const deep = structuredClone({ user: { name: "A" } });  // deep copy
console.log(deep);
```

```text
let b = a        a ──► 10        b ──► 10        (two separate values)
const alias =    original ──┐
  original                  ├──► { qty: 99 }    (one object, two names)
                 alias ─────┘
```

### 7. Re-declaration and shadowing

```javascript
var x = 1;
var x = 2;                   // var: silently allowed — can overwrite something by accident
console.log(x);

let y = 1;
// let y = 2;                // SyntaxError: Identifier 'y' has already been declared

// Shadowing: an inner scope may declare the SAME name; it hides the outer one there
const level = "outer";
{
  const level = "inner";
  console.log(level);        // inner
}
console.log(level);          // outer
```

Shadowing is legal but makes code harder to read. Linters (ESLint `no-shadow`) can warn about it.

### 8. Undeclared variables and strict mode

Assigning to a name that was never declared:

- In **sloppy mode** (old scripts) → silently creates a **global variable**.
- In **strict mode** → `ReferenceError`.

ES modules (`import`/`export`), classes, Node.js ES modules, TypeScript output and modern bundlers all run in strict mode, so you will usually get the error — which is what you want. (This playground also runs in strict mode.)

```javascript
try {
  totl = 500;                // typo of "total", never declared
} catch (e) {
  console.log(e.name + ": " + e.message);
}
```

### 9. The global object

At the top level of a classic browser `<script>`, `var` and function declarations become properties of the global object (`window` in browsers). `let` and `const` do not. `globalThis` is the standard name for the global object in every environment (browser, Node.js, workers).

```javascript
console.log(typeof globalThis);          // "object"
console.log("setTimeout" in globalThis); // built-ins live there
```

In ES modules and in Node.js modules, top-level variables are **module-scoped** — they are not globals at all.

### 10. Naming rules and conventions

**Rules** (enforced by the language):

- Letters, digits, `_` and `$`; cannot start with a digit: `user1` ✓, `1user` ✗.
- Case-sensitive: `total` and `Total` are different variables.
- Cannot be a reserved word: `let`, `class`, `return`, `const`, `function`, `new`, `this`, `if`…

**Conventions** (what professional code looks like):

| Style | Used for | Example |
| --- | --- | --- |
| `camelCase` | Variables and functions | `cartTotal`, `getUser` |
| `PascalCase` | Classes, React components, types | `UserCard`, `OrderService` |
| `UPPER_SNAKE_CASE` | True constants and env-style config | `MAX_RETRIES`, `API_URL` |
| `isX`, `hasX`, `canX` | Booleans | `isLoggedIn`, `hasAccess` |
| Plural nouns | Arrays and collections | `users`, `orderIds` |

Choose names that say **what** the value is, not how it is stored: `daysUntilExpiry`, not `d` or `temp2`.

### 11. Variables and memory

When nothing refers to a value any more, the JavaScript engine's **garbage collector** frees its memory automatically. This is also how memory leaks happen in JavaScript: a variable that lives a long time (module level, a global, a cache, an event listener) keeps a reference to data that should have been freed.

## Hands-on

Each block above runs in the playground with **Run**. Then try this classic interview puzzle, which combines scope, closures and asynchronous code:

```javascript
// Predict the output BEFORE you run it.
const results = [];

for (var i = 0; i < 3; i++) {
  setTimeout(() => results.push("var: " + i), 0);
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => results.push("let: " + j), 0);
}

await new Promise((r) => setTimeout(r, 10));
console.log(results.join("  "));
```

Why: with `var` there is **one** `i` for the whole function; by the time the callbacks run, the loop has finished and `i` is 3. With `let`, each loop iteration gets a **new** `j`, and each callback closes over its own copy.

A second exercise — decide `const` or `let` for every variable, then check:

```javascript
// Rewrite with the right keywords (hint: only one needs let)
var TAX_RATE = 0.17;
var items = [{ price: 1000 }, { price: 2500 }];
var subtotal = 0;
for (var k = 0; k < items.length; k++) {
  subtotal += items[k].price;
}
var total = subtotal + subtotal * TAX_RATE;
console.log("Total:", total);
```

(Answer: `subtotal` and the loop counter need `let`; everything else should be `const`. Better still, replace the loop with `const subtotal = items.reduce((s, it) => s + it.price, 0);` — then nothing needs `let`.)

## Real-world example

A Next.js API route keeps a list of "recent searches". The first version looks harmless:

```javascript
// app/api/search/route.js — BUG: module-level state
let recentSearches = [];                  // lives as long as the server process

export async function GET(request) {
  const q = new URL(request.url).searchParams.get("q");
  recentSearches.push(q);                 // every user's searches go into ONE array
  return Response.json({ recent: recentSearches.slice(-5) });
}
```

On the developer's laptop it "works". In production:

1. **Privacy leak:** user A sees user B's searches, because the variable is shared by every request the process handles.
2. **Memory leak:** the array grows forever until the process is killed.
3. **Inconsistency:** with three server instances (or serverless functions), each has its own copy, so results jump around.

The fix is about **scope and lifetime**: per-request data lives in variables **inside** the handler; per-user data lives in a database or cache keyed by user ID; only truly shared, read-only things (a database client, configuration) belong at module level, usually as `const`.

```javascript
// Fixed
import { db } from "@/lib/db";            // shared client: module-level const is correct

export async function GET(request) {
  const userId = await getUserId(request);           // per request
  const q = new URL(request.url).searchParams.get("q");
  await db.search.create({ data: { userId, q } });
  const recent = await db.search.findMany({ where: { userId }, take: 5, orderBy: { id: "desc" } });
  return Response.json({ recent: recent.map((r) => r.q) });
}
```

## Common mistakes

- **Using `var` in new code.** Its function scope and silent re-declaration cause bugs that `let`/`const` prevent.
- **Using `let` for everything.** If it is never reassigned, make it `const` — the next reader (including you) instantly knows it will not change.
- **Thinking `const` makes objects immutable.** It only stops reassignment. Use `Object.freeze` or copies when you need immutable data.
- **Mutating shared objects by accident** (`const a = b; a.x = 1;` changes `b`). Copy with spread or `structuredClone`.
- **Reading a variable before setting it** and continuing with `undefined`. Initialize at declaration where possible.
- **Module-level mutable state in servers**, shared across users and requests.
- **Meaningless names** — `data`, `temp`, `x2` — in anything longer than three lines.
- **Shadowing** a variable with the same name in an inner scope and then using the wrong one.

## Security lens

<Callout type="security">
Variables decide **where** data lives and **who** can reach it. Wrong scope is a confidentiality bug; wrong placement of secrets is a breach.
</Callout>

- **Shared state across requests** (module-level `let` in Node.js/Next.js) can leak one user's data to another. Keep per-request and per-user data inside handlers or in proper storage.
- **Secrets in front-end variables are public.** Anything in browser JavaScript — including `NEXT_PUBLIC_*` and `VITE_*` environment variables — is shipped to every visitor and readable in DevTools. API keys with real power must stay in server-only variables.
- **Accidental globals** (sloppy mode) can be read or overwritten by any other script on the page, including third-party scripts and injected XSS payloads. Strict mode and modules prevent this.
- **Logging whole objects** (`console.log(user)`, `logger.info(req.body)`) can write passwords, tokens and personal data into logs. Log specific, safe fields.
- **Prototype pollution:** merging untrusted JSON into objects (`Object.assign(config, req.body)`) can set `__proto__` properties that change the behaviour of every object in the app. Validate input against a schema and copy only known fields.
- **Freezing configuration** (`Object.freeze`) prevents other code from tampering with security-relevant settings at runtime.

## Interview questions

<QA q="What are the differences between var, let and const?">
var is function-scoped, can be re-declared, and is hoisted with the value undefined; at the top level of a classic script it also becomes a property of the global object. let and const are block-scoped, cannot be re-declared in the same scope, and are in the temporal dead zone until their declaration runs, so early access throws a ReferenceError. const must be initialized and cannot be reassigned, though objects it refers to can still be mutated.
</QA>

<QA q="What is hoisting?">
Before executing a scope, JavaScript registers all declarations in it. var declarations are initialized to undefined, so they can be read early without an error. Function declarations are hoisted with their full body and can be called before their line. let, const and class declarations are registered but left uninitialized until their line executes; accessing them before that throws a ReferenceError (the temporal dead zone).
</QA>

<QA q="What is the temporal dead zone?">
It is the period from the start of a scope until the line where a let, const or class declaration is evaluated. During that period the variable exists but cannot be accessed; doing so throws a ReferenceError. It turns "used before assignment" bugs into immediate errors instead of silent undefined values.
</QA>

<QA q="If const means constant, why can I change a const array?">
const prevents rebinding the variable name to a different value; it does not make the value itself immutable. A const array or object still refers to the same object, whose contents can be changed with push, property assignment and so on. To prevent changes to the value, use Object.freeze (shallowly) or immutable update patterns.
</QA>

<QA q="Why does a for loop with var and setTimeout print 3, 3, 3, while let prints 0, 1, 2?">
var creates one function-scoped variable shared by every iteration; the callbacks run after the loop finishes, when i is already 3, and all of them read that same variable. let creates a new block-scoped binding for each iteration, so each callback closes over its own value of the counter.
</QA>

<QA q="What is the difference between primitive and reference values?">
Primitives (string, number, boolean, null, undefined, bigint, symbol) are immutable and copied by value: assigning one variable to another creates an independent copy. Objects, arrays and functions are reference values: assignment copies the reference, so both variables point to the same object and changes through one are visible through the other. Copying requires spread, Object.assign or structuredClone.
</QA>
