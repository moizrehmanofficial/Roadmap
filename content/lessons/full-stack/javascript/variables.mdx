<Callout type="tip" title="In one minute">
A **variable** is a name you give to a piece of information so the program can remember it and use it later — like writing a label on a box. Create one with `const` (the label can never be moved to another box) or `let` (the label can be moved). Both only exist inside the nearest pair of curly braces. Avoid the old `var`. Default to `const`; use `let` only when the value really has to change.
</Callout>

## Start from zero

### Programs need to remember things

Imagine you are a shopkeeper adding up a customer's bill on paper:

1. You write "Total: 0".
2. The customer buys bread for 150 — you cross out 0 and write 150.
3. Then milk for 280 — you cross out 150 and write 430.
4. At the end you read the total aloud: "430, please".

You needed a place to **write a number down**, give it a **name** ("Total"), **change** it, and **read** it later. A computer program needs exactly the same thing — and that is a variable.

<Callout type="analogy">
**Labelled boxes in a storeroom.** The box holds something (the value). The label on the box is the name (`total`, `userName`). When you say "bring me the `userName` box", you get what is inside it: `"Moiz"`.

**Contacts in your phone.** You do not remember 0300-1234567; you save it as "Ammi". The name "Ammi" points to the number. If the number changes, you update the contact — the name stays the same. That name is a variable.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Value** | A piece of information: a number, some text, true/false, a list… | `430`, `"Moiz"`, `true` |
| **Variable** | A name that points to a value | `total` → `430` |
| **Keyword** | A word that has special meaning in JavaScript | `const`, `let`, `var`, `if` |
| **Declare** | Create a new variable name | `let total;` |
| **Assign** | Put a value into a variable using `=` | `total = 430;` |
| **Reassign** | Put a **new** value into an existing variable | `total = 500;` |
| **`=`** | "Store the value on the right into the name on the left" — **not** "equals" from maths | `x = x + 1` |
| **`console.log(…)`** | Prints a value so you can see it | `console.log(total)` |
| **Curly braces `{ }`** | Mark the start and end of a block of code | the body of an `if` or a function |

## What is it?

A **variable** is a **named place in memory** where your program keeps a value. You:

1. **create** it (declare) with `const`, `let` or `var`,
2. **put a value** in it with `=`,
3. **use** it by writing its name,
4. (sometimes) **change** it later.

```javascript
const shopName = "Moiz General Store";
let total = 0;
total = total + 150;
total = total + 280;
console.log(shopName, "- total bill:", total);
```

```text output
Moiz General Store - total bill: 430
```

The value itself lives in the computer's memory (RAM). The variable name is the label that leads to it:

```text
  name            value in memory
  ─────────       ─────────────────────
  shopName  ───►  "Moiz General Store"
  total     ───►  430
```

## Why does it matter?

- **Without variables, a program cannot remember anything** — not the logged-in user, not the cart, not the score of a game, not the result of an API call.
- **Names make code readable.** `price * quantity` explains itself; `1500 * 3` does not.
- **Change in one place.** If the tax rate is stored once in `TAX_RATE`, you update one line instead of fifty.
- **Most beginner bugs are variable bugs:** a value that is unexpectedly `undefined`, a value that "changed by itself", a typo that created a new variable.
- **Interviews:** `var` vs `let` vs `const`, scope and hoisting are among the most asked JavaScript questions.

## When and where do you use it?

**When:** every time you need to keep a value for later — almost every line of a program.

**Where** (examples from real projects):

| Place | Example |
| --- | --- |
| A web page | `const button = document.querySelector("#buy");` |
| React | `const [count, setCount] = useState(0);` |
| Node.js / Express API | `const user = await db.user.findById(id);` |
| Configuration | `const port = 3000;` |
| Loops and counters | `for (let i = 0; i < 10; i++)` |
| Calculations | `const total = price * quantity;` |

## Concepts one by one

### 1. Creating and using a variable

<Explain>
<What>
Writing a keyword (`const` or `let`), a name, `=`, and a value. After that, writing the name anywhere gives you the value.
</What>
<Why>
So you can store information once and use it many times without typing it again.
</Why>
<When>
As soon as you have a value you will need again: user input, a result, a setting.
</When>
<Where>
Everywhere in JavaScript: browser code, Node.js, React components, scripts.
</Where>
<How>
`keyword name = value;` — for example `const city = "Rawalpindi";`. Then use `city` wherever you need it.
</How>
</Explain>

```javascript
const city = "Rawalpindi";
const temperature = 31;
console.log("City:", city);
console.log("Temperature:", temperature);
console.log(city + " is " + temperature + " degrees today");
```

```text output
City: Rawalpindi
Temperature: 31
Rawalpindi is 31 degrees today
```

Line by line:

- `const city = "Rawalpindi";` — create a variable named `city` and store the text `"Rawalpindi"` in it. Text always goes inside quotes.
- `const temperature = 31;` — numbers do **not** use quotes.
- `console.log("City:", city);` — print the label `City:` and then the value inside `city`.
- `city + " is " + …` — `+` joins text pieces together into one sentence.

### 2. What can a variable hold? (types of values)

<Explain>
<What>
A variable can hold any kind of value. The kind is called its **type**.
</What>
<Why>
Different kinds of values behave differently: you can add numbers, but you join text; you can ask true/false questions about booleans.
</Why>
<When>
Every time you store something, it has a type — you choose it by how you write the value.
</When>
<Where>
Numbers for prices and counts, strings for names and messages, booleans for on/off states, arrays for lists, objects for records like a user.
</Where>
<How>
Write the value in its own style: `42`, `"text"`, `true`, `[1, 2, 3]`, `{ name: "Ali" }`. `typeof` tells you the type.
</How>
</Explain>

```javascript
const age = 24;                              // number
const name = "Ali";                          // string (text)
const isLoggedIn = true;                     // boolean (true / false)
const cart = ["bread", "milk"];              // array (a list)
const user = { name: "Ali", role: "admin" }; // object (a record)
let notSetYet;                               // undefined (no value yet)

console.log(typeof age, typeof name, typeof isLoggedIn);
console.log(cart[0], "and", cart.length, "items");
console.log(user.name, "is", user.role);
console.log(notSetYet);
```

```text output
number string boolean
bread and 2 items
Ali is admin
undefined
```

- `cart[0]` — the first item of a list (counting starts at 0).
- `user.name` — read the `name` property from the object.
- `notSetYet` was created without a value, so it holds `undefined` ("nothing has been put here yet").

(Each type has its own lesson next: **Data Types**.)

### 3. Declare, assign, reassign

<Explain>
<What>
Three separate steps: **declare** (create the name), **assign** (store the first value), **reassign** (replace it with a new value).
</What>
<Why>
Sometimes you know the value immediately, sometimes later, and sometimes it keeps changing — like a running total.
</Why>
<When>
Declare and assign together whenever you can. Reassign only when the value really changes over time.
</When>
<Where>
Counters, totals, flags like "is the menu open", values that depend on a condition.
</Where>
<How>
`let score;` (declare) → `score = 10;` (assign) → `score = score + 5;` (reassign). Reassigning works only with `let` (and the old `var`), never with `const`.
</How>
</Explain>

```javascript
let score;                // 1. declare: the box exists but is empty
console.log(score);
score = 10;               // 2. assign: put 10 in the box
console.log(score);
score = score + 5;        // 3. reassign: take what is in the box, add 5, put it back
console.log(score);
score += 5;               // short form of: score = score + 5
console.log(score);
```

```text output
undefined
10
15
20
```

<Callout type="warning" title="= is not 'equals'">
In maths, `x = x + 5` is impossible. In programming, `=` means **"calculate the right side, then store it in the left side"**. So `score = score + 5` means "new score = old score + 5". To **compare** two values, JavaScript uses `===`.
</Callout>

### 4. `const` — a value that will not be replaced

<Explain>
<What>
A keyword that creates a variable which can **never be reassigned**. You must give it a value immediately.
</What>
<Why>
It protects you from changing something by mistake, and it tells every reader "this stays the same", which makes code easier to understand.
</Why>
<When>
By default — for **most** variables. In real code, most values are set once and never replaced.
</When>
<Where>
Settings (`const API_URL = …`), imported libraries, functions, results of calculations, objects and arrays you will modify but not replace.
</Where>
<How>
`const name = value;`. Trying `name = somethingElse` later gives a `TypeError`.
</How>
</Explain>

```javascript
const TAX_RATE = 0.17;
const price = 1000;
const total = price + price * TAX_RATE;
console.log("Total with tax:", total);

try {
  TAX_RATE = 0.2;          // not allowed
} catch (error) {
  console.log("Error:", error.message);
}
```

```text output
Total with tax: 1170
Error: Assignment to constant variable.
```

- `try { … } catch (error) { … }` — "try this; if it throws an error, catch it and run the second part instead of crashing". Used here only so you can see the error message.

### 5. `let` — a value that will change

<Explain>
<What>
A keyword that creates a variable you **can** reassign later.
</What>
<Why>
Some values must change: a counter, a running total, the current page number, how many times we retried.
</Why>
<When>
Only when you know the value will be replaced. If you never write `name = …` again after creating it, use `const` instead.
</When>
<Where>
Loop counters, totals built step by step, values decided by an `if`.
</Where>
<How>
`let name = value;` and later `name = newValue;`. Giving a value at creation is optional (it starts as `undefined`).
</How>
</Explain>

```javascript
let attempts = 0;
attempts = attempts + 1;
attempts = attempts + 1;
console.log("Login attempts:", attempts);

let message;
const hour = 20;
if (hour < 12) {
  message = "Good morning";
} else {
  message = "Good evening";
}
console.log(message);
```

```text output
Login attempts: 2
Good evening
```

- `attempts` changes twice, so it must be `let`.
- `message` gets its value inside an `if`, so it is created first with `let` and assigned later.

### 6. `var` — the old way (read it, do not write it)

<Explain>
<What>
The original keyword from 1995. It still works, but behaves in surprising ways compared to `let` and `const`.
</What>
<Why>
You need to understand it because old code, tutorials and interview questions use it. You should not use it in new code.
</Why>
<When>
Only when reading or maintaining legacy code.
</When>
<Where>
Old websites, old jQuery code, old Stack Overflow answers, some libraries.
</Where>
<How>
`var name = value;` — like `let`, but it ignores blocks, can be created twice with the same name, and can be used before its line (it is `undefined` there). Sections 7–9 show each problem.
</How>
</Explain>

| | `const` | `let` | `var` |
| --- | --- | --- | --- |
| Can be reassigned | No | Yes | Yes |
| Must get a value immediately | Yes | No | No |
| Lives inside | The nearest `{ }` block | The nearest `{ }` block | The whole function |
| Same name created twice | Error | Error | Allowed silently |
| Used before its line | Error | Error | Gives `undefined` |
| Use in new code? | **Yes — default** | When the value changes | **No** |

### 7. Scope — where a variable can be used

<Explain>
<What>
**Scope** is the area of the code where a variable name exists. Outside that area, the name is unknown.
</What>
<Why>
So that variables in one part of the program do not clash with or accidentally change variables in another part. Two functions can each have their own `total` without interfering.
</Why>
<When>
Always — every variable has a scope, decided by **where you write it**.
</When>
<Where>
Every `{ }` (an `if`, a loop, a function) creates a new scope for `let` and `const`.
</Where>
<How>
Code can see variables in its own block **and in every block around it**, but never variables inside a smaller block.
</How>
</Explain>

<Callout type="analogy">
A house: a variable created in the **living room** (outer scope) can be seen from every room. A variable created inside your **bedroom** (inner block) cannot be seen from the living room. You can look out of your room, but nobody can look in.
</Callout>

```javascript
const appName = "DevGuide";            // outer scope: visible everywhere below

function greet(user) {
  const message = "Hello " + user;     // inside the function only
  if (user === "admin") {
    const badge = "★";                 // inside this if only
    console.log(appName, message, badge);
  }
  console.log(typeof badge);           // badge does not exist here
  return message;
}

greet("admin");
console.log(typeof message);           // message does not exist here
```

```text output
DevGuide Hello admin ★
undefined
undefined
```

- Inside the `if`, all three names are visible (looking outward works).
- After the `if` closes, `badge` no longer exists. `typeof` reports `"undefined"` instead of crashing, which is why it is used here.
- Outside the function, `message` does not exist.

```text
┌ outer ─────────────────────────────┐
│ appName                            │
│ ┌ function greet ───────────────┐  │
│ │ user, message                 │  │
│ │ ┌ if block ────────────────┐  │  │
│ │ │ badge                    │  │  │
│ │ │ sees: badge, message,    │  │  │
│ │ │       user, appName      │  │  │
│ │ └──────────────────────────┘  │  │
│ └───────────────────────────────┘  │
└────────────────────────────────────┘
```

### 8. Why `var` leaks out of blocks

<Explain>
<What>
`var` ignores `if` and loop blocks. It is only contained by a **function**.
</What>
<Why>
This is the main reason `let` and `const` were added in 2015: values "escaping" from blocks caused hard-to-find bugs.
</Why>
<When>
You will meet this in old code and in interview questions.
</When>
<Where>
Loops and `if` blocks that use `var`.
</Where>
<How>
A `var` created inside `{ }` is still available after the `}`. A `let`/`const` is not.
</How>
</Explain>

```javascript
if (true) {
  var leaked = "var escaped the block";
  let contained = "let stays inside";
}
console.log(leaked);
console.log(typeof contained);
```

```text output
var escaped the block
undefined
```

The classic interview puzzle caused by this:

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log("var:", i), 0);
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log("let:", j), 0);
}
```

```text output
var: 3
var: 3
var: 3
let: 0
let: 1
let: 2
```

- `setTimeout(…, 0)` means "run this a moment later, after the current code finishes".
- With `var` there is **one** `i` shared by the whole loop. When the delayed code runs, the loop is already over and `i` is 3.
- With `let`, every round of the loop gets its **own** `j`, so each delayed function remembers its own number.

### 9. Hoisting and the Temporal Dead Zone

<Explain>
<What>
Before running your code, JavaScript first scans it and notes every variable name. This is called **hoisting**. What the name contains before its line runs depends on the keyword.
</What>
<Why>
Knowing this explains why `var` gives `undefined` instead of an error, and why `let`/`const` give a clear error when used too early.
</Why>
<When>
Whenever a variable is used above the line that creates it — usually by mistake.
</When>
<Where>
Large files and functions, code moved around during refactoring.
</Where>
<How>
`var` → `undefined` before its line (silent bug). `let`/`const` → error before their line. The area between the start of the block and the `let`/`const` line is called the **Temporal Dead Zone (TDZ)**. Function declarations are hoisted completely, so they can be called before they appear.
</How>
</Explain>

```javascript
console.log(oldStyle);            // var: no error, just undefined
var oldStyle = "var value";

try {
  console.log(modern);            // let: in the Temporal Dead Zone
} catch (error) {
  console.log(error.name + ":", error.message);
}
let modern = "let value";

console.log(sayHi());             // function declarations work early
function sayHi() { return "hi from a hoisted function"; }
```

```text output
undefined
ReferenceError: Cannot access 'modern' before initialization
hi from a hoisted function
```

The error from `let` is a **good thing**: using a value before it is set is almost always a mistake, and a loud error is much easier to fix than a silent `undefined`.

### 10. `const` with objects and arrays — the label is fixed, the contents are not

<Explain>
<What>
`const` stops the **name** from being pointed at a different value. It does **not** stop you changing what is inside an object or array.
</What>
<Why>
This surprises almost every beginner ("why can I push into a const array?"). Understanding it avoids confusion and bugs.
</Why>
<When>
Every time you store an object or array — which is constantly in real apps (users, carts, API responses).
</When>
<Where>
React state objects, configuration objects, lists of items.
</Where>
<How>
`const cart = []; cart.push("milk");` works — same box, new contents. `cart = ["bread"];` fails — that would be a different box. To lock the contents too, use `Object.freeze(…)`.
</How>
</Explain>

<Callout type="analogy">
`const` glues the **label** to the box. You can still open the box and change what is inside. You just cannot peel the label off and stick it on a different box.
</Callout>

```javascript
const user = { name: "Sara", role: "user" };
user.role = "admin";              // allowed: changing what is inside
user.city = "Lahore";             // allowed: adding something inside
console.log(user);

try {
  user = { name: "Someone else" };    // not allowed: pointing the label at a new object
} catch (error) {
  console.log("Error:", error.message);
}

const tags = ["js"];
tags.push("ts");
console.log(tags);

const settings = Object.freeze({ theme: "dark" });
try {
  settings.theme = "light";       // frozen: ignored, or an error in strict mode
} catch (error) {
  console.log("Frozen:", error.name);
}
console.log(settings.theme);
```

```text output
{ name: 'Sara', role: 'admin', city: 'Lahore' }
Error: Assignment to constant variable.
[ 'js', 'ts' ]
Frozen: TypeError
dark
```

`Object.freeze` locks the contents: in modern (strict-mode) code, changing a frozen object throws a `TypeError`; in very old scripts the change is silently ignored. Either way, `theme` stays `"dark"`.

(The exact look of printed objects differs slightly between the browser console, Node.js and the playground.)

### 11. Copying: simple values vs objects

<Explain>
<What>
When you copy a variable into another, **simple values** (numbers, strings, booleans) are copied as independent values. **Objects and arrays** are not copied — both names end up pointing at the **same** object.
</What>
<Why>
This causes the famous "my data changed by itself" bug: you edit a "copy" and the original changes too.
</Why>
<When>
Any time you write `const b = a` where `a` is an object or array, or pass an object into a function.
</When>
<Where>
React state updates, form data, API responses, carts.
</Where>
<How>
Simple values: `let b = a` makes a real copy. Objects: use `{ ...obj }` (or `[...arr]`) for a copy of the top level, and `structuredClone(obj)` for a full deep copy.
</How>
</Explain>

<Callout type="analogy">
A number is like a **photocopy** of a page — you can scribble on your copy and the original stays clean. An object is like a **shared Google Doc link** — if you send someone the link and they edit it, you see their edits, because there is only one document.
</Callout>

```javascript
let a = 10;
let b = a;          // copies the number 10
b = 20;
console.log("numbers:", a, b);

const original = { qty: 1 };
const sameObject = original;      // copies the LINK, not the object
sameObject.qty = 99;
console.log("original after editing 'sameObject':", original.qty);

const realCopy = { ...original }; // a new object with the same contents
realCopy.qty = 5;
console.log("original:", original.qty, "copy:", realCopy.qty);
```

```text output
numbers: 10 20
original after editing 'sameObject': 99
original: 99 copy: 5
```

```text
let b = a          a ──► 10      b ──► 20       (two separate values)

const sameObject   original ───┐
  = original                   ├──► { qty: 99 }  (one object, two names)
                   sameObject ─┘
```

### 12. Same name twice and "shadowing"

<Explain>
<What>
**Re-declaring** means creating a variable with a name that already exists in the same block. **Shadowing** means creating the same name in an **inner** block, which hides the outer one there.
</What>
<Why>
`var` allows re-declaring silently, so you can overwrite a value without noticing. `let`/`const` stop you with an error. Shadowing is allowed but can confuse readers.
</Why>
<When>
Mostly by accident in long files — which is exactly why the error is useful.
</When>
<Where>
Long functions, copy-pasted code, nested blocks.
</Where>
<How>
`var x = 1; var x = 2;` → allowed. `let y = 1; let y = 2;` → `SyntaxError`. An inner `{ const level = "inner"; }` hides an outer `level` only inside those braces.
</How>
</Explain>

```javascript
var x = 1;
var x = 2;                   // var: silently allowed
console.log("x is", x);

const level = "outer";
{
  const level = "inner";     // shadowing: a different variable with the same name
  console.log("inside:", level);
}
console.log("outside:", level);
```

```text output
x is 2
inside: inner
outside: outer
```

Writing `let y = 1;` and then `let y = 2;` in the same block stops the program before it even starts: `SyntaxError: Identifier 'y' has already been declared`.

### 13. Forgetting the keyword (undeclared variables)

<Explain>
<What>
Writing `name = value` without `const`, `let` or `var` first.
</What>
<Why>
In old JavaScript this silently created a **global** variable (available everywhere) — usually from a typo. Modern JavaScript (strict mode) throws an error instead, which catches the typo.
</Why>
<When>
Typos like `totl` instead of `total`, or simply forgetting `const`.
</When>
<Where>
Modern code — ES modules, React, Next.js, Node.js modules, TypeScript — runs in strict mode, so you get the error.
</Where>
<How>
Always declare with `const` or `let`. If you see `ReferenceError: X is not defined`, check the spelling and whether it was declared.
</How>
</Explain>

```javascript
"use strict";
let total = 100;
try {
  totl = 500;               // typo, never declared
} catch (error) {
  console.log(error.name + ":", error.message);
}
console.log("total is still", total);
```

```text output
ReferenceError: totl is not defined
total is still 100
```

### 14. Naming variables well

<Explain>
<What>
The rules the language forces on names, plus the conventions professional developers follow.
</What>
<Why>
Code is read far more often than it is written. A good name explains the code without comments; a bad name (`x`, `data2`, `temp`) hides bugs.
</Why>
<When>
Every time you create a variable.
</When>
<Where>
Everywhere — and code reviews at every company will comment on bad names.
</Where>
<How>
Follow the rules and conventions in the tables below. Name a value by **what it means**: `daysUntilExpiry`, not `d`.
</How>
</Explain>

**Rules** (break them and the code will not run):

| Rule | Good | Bad |
| --- | --- | --- |
| Only letters, digits, `_` and `$` | `user_1`, `$price` | `user-name`, `total amount` |
| Cannot start with a digit | `user1` | `1user` |
| Not a reserved word | `className` | `class`, `let`, `return` |
| Case-sensitive | `total` and `Total` are **two different** variables | — |

**Conventions** (what professional code looks like):

| Style | Used for | Example |
| --- | --- | --- |
| `camelCase` | Normal variables and functions | `cartTotal`, `getUser` |
| `PascalCase` | Classes, React components | `UserCard`, `OrderService` |
| `UPPER_SNAKE_CASE` | Fixed settings | `MAX_RETRIES`, `API_URL` |
| `is` / `has` / `can` + word | true/false values | `isLoggedIn`, `hasAccess` |
| Plural nouns | Lists | `users`, `orderIds` |

### 15. Variables and memory

<Explain>
<What>
While a value is reachable through some variable, it stays in memory (RAM). When nothing points to it any more, JavaScript's **garbage collector** frees that memory automatically.
</What>
<Why>
This is how **memory leaks** happen in JavaScript: a long-living variable (a global, a module-level array, a cache) keeps pointing to data that should have been thrown away, and memory use grows until the app slows down or crashes.
</Why>
<When>
Mostly in long-running programs: Node.js servers, single-page apps open all day.
</When>
<Where>
Arrays that only ever grow, caches without limits, event listeners that are never removed.
</Where>
<How>
Keep variables in the smallest scope that works (inside the function, not at the top of the file), and give caches a size limit.
</How>
</Explain>

## Real-world example

A Next.js API route keeps a list of "recent searches". The first version looks harmless:

```javascript
// app/api/search/route.js — BUG: module-level state
let recentSearches = [];                  // lives as long as the server process

export async function GET(request) {
  const q = new URL(request.url).searchParams.get("q");
  recentSearches.push(q);                 // every user's searches go into ONE array
  return Response.json({ recent: recentSearches.slice(-5) });
}
```

On the developer's laptop it "works". In production:

1. **Privacy leak:** user A sees user B's searches, because the variable is shared by every request the process handles.
2. **Memory leak:** the array grows forever until the process is killed.
3. **Inconsistency:** with three server instances (or serverless functions), each has its own copy, so results jump around.

The fix is about **scope and lifetime**: per-request data lives in variables **inside** the handler; per-user data lives in a database or cache keyed by user ID; only truly shared, read-only things (a database client, configuration) belong at module level, usually as `const`.

```javascript
// Fixed
import { db } from "@/lib/db";            // shared client: module-level const is correct

export async function GET(request) {
  const userId = await getUserId(request);           // per request
  const q = new URL(request.url).searchParams.get("q");
  await db.search.create({ data: { userId, q } });
  const recent = await db.search.findMany({ where: { userId }, take: 5, orderBy: { id: "desc" } });
  return Response.json({ recent: recent.map((r) => r.q) });
}
```

## Common mistakes

- **Using `var` in new code.** Its function scope and silent re-declaration cause bugs that `let`/`const` prevent.
- **Using `let` for everything.** If it is never reassigned, make it `const` — the next reader (including you) instantly knows it will not change.
- **Thinking `const` makes objects immutable.** It only stops reassignment. Use `Object.freeze` or copies when you need immutable data.
- **Mutating shared objects by accident** (`const a = b; a.x = 1;` changes `b`). Copy with spread or `structuredClone`.
- **Reading a variable before setting it** and continuing with `undefined`. Initialize at declaration where possible.
- **Module-level mutable state in servers**, shared across users and requests.
- **Meaningless names** — `data`, `temp`, `x2` — in anything longer than three lines.
- **Shadowing** a variable with the same name in an inner scope and then using the wrong one.

## Security lens

<Callout type="security">
Variables decide **where** data lives and **who** can reach it. Wrong scope is a confidentiality bug; wrong placement of secrets is a breach.
</Callout>

- **Shared state across requests** (module-level `let` in Node.js/Next.js) can leak one user's data to another. Keep per-request and per-user data inside handlers or in proper storage.
- **Secrets in front-end variables are public.** Anything in browser JavaScript — including `NEXT_PUBLIC_*` and `VITE_*` environment variables — is shipped to every visitor and readable in DevTools. API keys with real power must stay in server-only variables.
- **Accidental globals** (sloppy mode) can be read or overwritten by any other script on the page, including third-party scripts and injected XSS payloads. Strict mode and modules prevent this.
- **Logging whole objects** (`console.log(user)`, `logger.info(req.body)`) can write passwords, tokens and personal data into logs. Log specific, safe fields.
- **Prototype pollution:** merging untrusted JSON into objects (`Object.assign(config, req.body)`) can set `__proto__` properties that change the behaviour of every object in the app. Validate input against a schema and copy only known fields.
- **Freezing configuration** (`Object.freeze`) prevents other code from tampering with security-relevant settings at runtime.

## Interview questions

<QA q="What are the differences between var, let and const?">
var is function-scoped, can be re-declared, and is hoisted with the value undefined; at the top level of a classic script it also becomes a property of the global object. let and const are block-scoped, cannot be re-declared in the same scope, and are in the temporal dead zone until their declaration runs, so early access throws a ReferenceError. const must be initialized and cannot be reassigned, though objects it refers to can still be mutated.
</QA>

<QA q="What is hoisting?">
Before executing a scope, JavaScript registers all declarations in it. var declarations are initialized to undefined, so they can be read early without an error. Function declarations are hoisted with their full body and can be called before their line. let, const and class declarations are registered but left uninitialized until their line executes; accessing them before that throws a ReferenceError (the temporal dead zone).
</QA>

<QA q="What is the temporal dead zone?">
It is the period from the start of a scope until the line where a let, const or class declaration is evaluated. During that period the variable exists but cannot be accessed; doing so throws a ReferenceError. It turns "used before assignment" bugs into immediate errors instead of silent undefined values.
</QA>

<QA q="If const means constant, why can I change a const array?">
const prevents rebinding the variable name to a different value; it does not make the value itself immutable. A const array or object still refers to the same object, whose contents can be changed with push, property assignment and so on. To prevent changes to the value, use Object.freeze (shallowly) or immutable update patterns.
</QA>

<QA q="Why does a for loop with var and setTimeout print 3, 3, 3, while let prints 0, 1, 2?">
var creates one function-scoped variable shared by every iteration; the callbacks run after the loop finishes, when i is already 3, and all of them read that same variable. let creates a new block-scoped binding for each iteration, so each callback closes over its own value of the counter.
</QA>

<QA q="What is the difference between primitive and reference values?">
Primitives (string, number, boolean, null, undefined, bigint, symbol) are immutable and copied by value: assigning one variable to another creates an independent copy. Objects, arrays and functions are reference values: assignment copies the reference, so both variables point to the same object and changes through one are visible through the other. Copying requires spread, Object.assign or structuredClone.
</QA>

## Key terms

<Terms>
  <Term name="Variable">A named binding that refers to a value.</Term>
  <Term name="Declaration">Creating a variable name with var, let or const.</Term>
  <Term name="Initialization">Giving a variable its first value.</Term>
  <Term name="Assignment">Giving an existing variable a new value with =.</Term>
  <Term name="Scope">The region of code where a name is accessible.</Term>
  <Term name="Lexical scope">Scope decided by where code is written, not where it runs.</Term>
  <Term name="Block scope">Scope limited to the nearest curly braces; used by let and const.</Term>
  <Term name="Hoisting">Registering declarations before a scope's code runs.</Term>
  <Term name="Temporal dead zone">The period before a let/const declaration runs, during which access throws.</Term>
  <Term name="Shadowing">Declaring a variable with the same name as one in an outer scope.</Term>
  <Term name="Primitive">A simple immutable value copied by value.</Term>
  <Term name="Reference">A pointer to an object; copying it shares the same object.</Term>
  <Term name="Strict mode">A stricter JavaScript mode that turns silent mistakes into errors.</Term>
</Terms>
