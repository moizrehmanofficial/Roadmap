<BigIdea>
<Tr>
<En>
When you write `for (const x of list)`, `[...set]` or `const [a, b] = text`, JavaScript asks the value for an **iterator**: a small object with a `next()` method that hands out values **one at a time**, as `{ value, done }`, until `done` is `true`. Anything that can produce an iterator is **iterable**: arrays, strings, `Map`, `Set`, and your own objects too, if you add a `[Symbol.iterator]` method. Writing iterators by hand is fiddly, so JavaScript has **generators**: functions written with `function*` that `yield` values. A generator **pauses** at every `yield` and continues only when the next value is requested. That makes them **lazy**: they can describe endless sequences, stop as soon as you have what you need, and, as **async generators**, stream pages of data from an API.
</En>
<Ur>
Jab aap `for (const x of list)`, `[...set]` ya `const [a, b] = text` likhte hain, JavaScript value se ek **iterator** maangti hai: chhota sa object jis ke paas `next()` method hai jo values **ek ek kar ke**, `{ value, done }` ki shakal me, deta hai jab tak `done` `true` na ho. Jo bhi iterator bana sake wo **iterable** hai: arrays, strings, `Map`, `Set`, aur aap ke apne objects bhi, agar aap `[Symbol.iterator]` method jor dein. Haath se iterators likhna mushkil hai, isliye JavaScript ke paas **generators** hain: `function*` se likhe functions jo values `yield` karte hain. Generator har `yield` par **ruk** jata hai aur sirf tab aage barhta hai jab agli value maangi jaye. Is se ye **lazy** hote hain: be-intiha silsile bayan kar sakte hain, zaroorat ki cheez milte hi ruk sakte hain, aur **async generators** ki shakal me API se data ke pages stream kar sakte hain.
</Ur>
</Tr>
</BigIdea>

## Picture it

<Tr>
<En>

Think of a **ticket dispenser at a deli counter**.

- An **array** is a **printed stack of all the tickets**: someone printed every number in advance, whether or not anyone needs them.
- An **iterator** is the **dispenser**: each pull (`next()`) gives you the next ticket (`value`). When the roll runs out, it says "empty" (`done: true`).
- A **generator** is a dispenser that **prints each ticket only when you pull**. It remembers where it was between pulls (it pauses at `yield`). It can even have an **endless roll** because it never prints ahead.
- `for…of` is a customer who keeps pulling tickets until the dispenser says empty, or until they decide to leave (`break`).
- An **async generator** is a dispenser connected to a printer in another building: each pull might take a moment (`await`), but you still take tickets one at a time.

</En>
<Ur>

**Deli counter par ticket dispenser** ka sochein.

- **Array** **tamam tickets ka chhapa hua dher** hai: kisi ne har number pehle se chhap diya, kisi ko zaroorat ho ya na ho.
- **Iterator** **dispenser** hai: har khinchaav (`next()`) agla ticket (`value`) deta hai. Jab roll khatam ho to ye kehta hai "khaali" (`done: true`).
- **Generator** aisa dispenser hai jo **har ticket sirf khinchne par chhapta** hai. Khinchaavon ke darmiyan yaad rakhta hai ke kahan tha (`yield` par rukta hai). Is ka **be-intiha roll** bhi ho sakta hai kyun ke ye kabhi pehle se nahi chhapta.
- `for…of` wo customer hai jo tab tak tickets khenchta rehta hai jab tak dispenser khaali na kahe, ya jab tak wo khud jane ka faisla na kare (`break`).
- **Async generator** aisa dispenser hai jo doosri building ke printer se jura hai: har khinchaav me thora waqt lag sakta hai (`await`), magar aap phir bhi ek ek ticket lete hain.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="The iterator protocol">

<Tr>
<En>
Every iterable has a `[Symbol.iterator]()` method that returns an iterator. Calling `next()` on the iterator gives `{ value, done }`. `for…of`, spread and destructuring all use this behind the scenes.
</En>
<Ur>
Har iterable ka `[Symbol.iterator]()` method hota hai jo iterator deta hai. Iterator par `next()` call karna `{ value, done }` deta hai. `for…of`, spread aur destructuring sab parde ke peechhe yahi istemal karte hain.
</Ur>
</Tr>

```javascript
const colors = ["red", "green"];
const it = colors[Symbol.iterator]();
console.log(it.next());
console.log(it.next());
console.log(it.next());

for (const c of "hi") console.log(c);
console.log([...new Set([1, 2, 2])], [...new Map([["a", 1]])], Array.from("abc"));

const [first, ...rest] = "hello";
console.log(first, rest);
```

```text output
{ value: 'red', done: false }
{ value: 'green', done: false }
{ value: undefined, done: true }
h
i
[ 1, 2 ] [ [ 'a', 1 ] ] [ 'a', 'b', 'c' ]
h [ 'e', 'l', 'l', 'o' ]
```

<Happened>
<Tr>
<En>

- Calling `next()` by hand stepped through the array, then reported `done: true`.
- Strings, Sets and Maps are iterable too (a Map gives `[key, value]` pairs).
- Destructuring `const [first, ...rest] = "hello"` pulled one value, then gathered the rest from the same iterator.

</En>
<Ur>

- Haath se `next()` call karne se array qadam ba qadam chali, phir `done: true` bataya.
- Strings, Sets aur Maps bhi iterable hain (Map `[key, value]` jore deta hai).
- Destructuring `const [first, ...rest] = "hello"` ne ek value khenchi, phir usi iterator se baqi jama kin.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Making your own object iterable">

<Tr>
<En>
Give an object a `[Symbol.iterator]()` method that returns an object with `next()`. Now `for…of` and spread work on it. Plain objects aren't iterable by default.
</En>
<Ur>
Object ko `[Symbol.iterator]()` method dein jo `next()` wala object wapas kare. Ab `for…of` aur spread us par chalte hain. Saade objects default me iterable nahi hote.
</Ur>
</Tr>

```javascript
const countdown = {
  from: 3,
  [Symbol.iterator]() {
    let current = this.from;
    return {
      next() {
        if (current > 0) return { value: current--, done: false };
        return { value: undefined, done: true };
      },
    };
  },
};

for (const n of countdown) console.log(n);
console.log([...countdown], Math.max(...countdown));

const plain = { a: 1 };
try {
  for (const x of plain) console.log(x);
} catch (error) {
  console.log(error.name + ": " + error.message);
}
```

```text output
3
2
1
[ 3, 2, 1 ] 3
TypeError: plain is not iterable
```

<Happened>
<Tr>
<En>

- `countdown` now works anywhere an iterable is expected: `for…of`, spread, `Math.max(...)`.
- Each loop calls `[Symbol.iterator]()` again, so you get a **fresh** countdown every time.
- Plain objects throw "is not iterable". Loop over `Object.keys(obj)`, `Object.values(obj)` or `Object.entries(obj)` instead.
- Writing `next()` by hand works but is fiddly. Generators (next step) do the same in a few lines.

</En>
<Ur>

- `countdown` ab har us jagah chalta hai jahan iterable chahiye: `for…of`, spread, `Math.max(...)`.
- Har loop `[Symbol.iterator]()` dobara call karta hai, isliye har dafa **naya** countdown milta hai.
- Saade objects "is not iterable" phenkte hain. Is ke bajaye `Object.keys(obj)`, `Object.values(obj)` ya `Object.entries(obj)` par loop chalayen.
- Haath se `next()` likhna chalta hai magar mushkil hai. Generators (agla qadam) yahi kaam chand lines me karte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Generator functions pause at yield">

<Tr>
<En>
A `function*` doesn't run when you call it; it returns a **generator** (which is an iterator). Each `next()` runs the function until the next `yield`, hands out that value, and **pauses**. A `return` ends it with `done: true`.
</En>
<Ur>
`function*` call karne par chalta nahi; ye **generator** wapas karta hai (jo iterator hai). Har `next()` function ko agle `yield` tak chalata hai, wo value deta hai, aur **ruk** jata hai. `return` ise `done: true` ke saath khatam karta hai.
</Ur>
</Tr>

```javascript
function* steps() {
  console.log("  start");
  yield "one";
  console.log("  after one");
  yield "two";
  console.log("  after two");
  return "done";
}

const gen = steps();
console.log("created, nothing ran yet");
console.log(gen.next());
console.log(gen.next());
console.log(gen.next());
console.log(gen.next());
console.log([...steps()]);
```

```text output
created, nothing ran yet
  start
{ value: 'one', done: false }
  after one
{ value: 'two', done: false }
  after two
{ value: 'done', done: true }
{ value: undefined, done: true }
  start
  after one
  after two
[ 'one', 'two' ]
```

<Happened>
<Tr>
<En>

- Calling `steps()` printed nothing: the body only runs when a value is requested.
- Each `next()` resumed exactly where the function had paused, ran to the next `yield`, and stopped again. Local variables survive between pauses.
- The `return` value appears once with `done: true`; after that, the generator is finished.
- Spread and `for…of` **ignore** the `return` value, which is why `[...steps()]` is `['one', 'two']`.

</En>
<Ur>

- `steps()` call karne se kuch print nahi hua: body sirf value maangne par chalti hai.
- Har `next()` bilkul wahin se dobara shuru hua jahan function ruka tha, agle `yield` tak chala, aur phir ruk gaya. Local variables rukne ke darmiyan bache rehte hain.
- `return` ki value ek dafa `done: true` ke saath aati hai; us ke baad generator khatam.
- Spread aur `for…of` `return` ki value **nazarandaz** karte hain, isi liye `[...steps()]` `['one', 'two']` hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Generators make iterables easy">

<Tr>
<En>
A generator is the simplest way to write a sequence or to make a collection iterable: put `*` in front of the `[Symbol.iterator]` method and `yield` the values.
</En>
<Ur>
Generator silsila likhne ya collection ko iterable banane ka sab se aasaan tareeqa hai: `[Symbol.iterator]` method se pehle `*` lagayen aur values `yield` karein.
</Ur>
</Tr>

```javascript
function* range(start, end, step = 1) {
  for (let i = start; i < end; i += step) yield i;
}
console.log([...range(0, 5)], [...range(10, 20, 5)]);

const countdown = {
  from: 3,
  *[Symbol.iterator]() {
    for (let n = this.from; n > 0; n--) yield n;
  },
};
console.log([...countdown]);
```

```text output
[ 0, 1, 2, 3, 4 ] [ 10, 15 ]
[ 3, 2, 1 ]
```

<Happened>
<Tr>
<En>

- `range` is a reusable sequence in one line, like Python's `range`.
- The countdown from the previous step shrank from 10 lines to 3: the generator handles `next()`, `value` and `done` for you.
- A class can do the same: `*[Symbol.iterator]() { yield* this.#items; }` makes your collection work with `for…of`.

</En>
<Ur>

- `range` ek line me dobara istemal hone wala silsila hai, Python ke `range` ki tarah.
- Pichhle qadam ka countdown 10 lines se 3 reh gaya: generator `next()`, `value` aur `done` aap ke liye sambhalta hai.
- Class bhi yahi kar sakti hai: `*[Symbol.iterator]() { yield* this.#items; }` aap ki collection ko `for…of` ke saath chalata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Infinite and lazy sequences">

<Tr>
<En>
Because generators only compute the next value when asked, they can be **infinite**. Combine small generators (`filter`, `map`, `take`) into a pipeline; values flow through **one at a time**, and nothing extra is computed.
</En>
<Ur>
Chunke generators agli value sirf maangne par nikalte hain, ye **be-intiha** ho sakte hain. Chhote generators (`filter`, `map`, `take`) ko pipeline me jorein; values **ek ek kar ke** guzarti hain, aur kuch izafi nahi nikalta.
</Ur>
</Tr>

```javascript
function* ids() {
  let id = 1;
  while (true) yield `order-${String(id++).padStart(4, "0")}`;
}
const nextId = ids();
console.log(nextId.next().value, nextId.next().value, nextId.next().value);

function* naturals() {
  let n = 1;
  while (true) yield n++;
}
function* filter(iterable, test) {
  for (const x of iterable) if (test(x)) yield x;
}
function* map(iterable, fn) {
  for (const x of iterable) yield fn(x);
}
function* take(iterable, n) {
  if (n <= 0) return;
  for (const x of iterable) {
    yield x;
    if (--n === 0) return;
  }
}

const firstSquaresOfEvens = take(map(filter(naturals(), (n) => n % 2 === 0), (n) => n * n), 4);
console.log([...firstSquaresOfEvens]);
```

```text output
order-0001 order-0002 order-0003
[ 4, 16, 36, 64 ]
```

<Happened>
<Tr>
<En>

- `while (true)` is fine inside a generator: it pauses at each `yield`, so it never runs away.
- `naturals()` is endless, yet the pipeline finished: `take(…, 4)` stopped after 4 values, and the earlier stages only produced what was needed.
- With arrays you'd have to pick a size first ("the first 1,000 numbers") and compute everything up front.

</En>
<Ur>

- Generator ke andar `while (true)` theek hai: ye har `yield` par rukta hai, isliye kabhi be-qaboo nahi hota.
- `naturals()` be-intiha hai, phir bhi pipeline khatam hui: `take(…, 4)` 4 values ke baad ruk gaya, aur pehle ke marahil ne sirf utna banaya jitna chahiye tha.
- Arrays ke saath pehle size chunna parta ("pehle 1,000 numbers") aur sab kuch pehle hi nikalna parta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Stopping early saves work">

<Tr>
<En>
With a generator, `break` stops the producer too: the remaining items are never examined. Array methods like `filter` process **every** item before you see the first result.
</En>
<Ur>
Generator ke saath `break` paida karne wale ko bhi rok deta hai: baqi items kabhi dekhe nahi jate. `filter` jaise array methods pehla nateeja dikhane se pehle **har** item process karte hain.
</Ur>
</Tr>

```javascript
const prices = [5, 30, 45, 120, 8, 300];

let checked = 0;
function* expensive(list) {
  for (const p of list) {
    checked++;
    if (p > 100) yield p;
  }
}
for (const p of expensive(prices)) {
  console.log("first expensive:", p);
  break;
}
console.log("items checked:", checked);

checked = 0;
const all = prices.filter((p) => {
  checked++;
  return p > 100;
});
console.log("with filter:", all[0], "items checked:", checked);
```

```text output
first expensive: 120
items checked: 4
with filter: 120 items checked: 6
```

<Happened>
<Tr>
<En>

- The generator checked only 4 prices: it stopped at 120 because the loop broke.
- `filter` checked all 6, then we took the first. For 6 items it doesn't matter; for a million rows, or rows that each need a network call, it does.
- For "first match in an array", `find` also stops early. Generators shine when the steps are many or the source is huge or endless.

</En>
<Ur>

- Generator ne sirf 4 qeematen check kin: loop toot-ne ki wajah se 120 par ruk gaya.
- `filter` ne teeno ke teeno 6 check kiye, phir humne pehla liya. 6 items ke liye farq nahi; das lakh rows ke liye, ya aisi rows jin me har ek ko network call chahiye, farq hai.
- "Array me pehla mail" ke liye `find` bhi jaldi rukta hai. Generators tab chamakte hain jab qadam bohot hon ya zariya bohot bara ya be-intiha ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="yield*, sending values in, and cleanup">

<Tr>
<En>
`yield*` hands over to another iterable until it's done. `next(value)` can **send** a value back into the generator: it becomes the result of the paused `yield`. A `finally` block runs when the generator finishes **or** is stopped early by `break`.
</En>
<Ur>
`yield*` doosre iterable ko us ke khatam hone tak baari deta hai. `next(value)` generator me value **wapas bhej** sakta hai: ye ruke hue `yield` ka nateeja ban jati hai. `finally` block tab chalta hai jab generator khatam ho **ya** `break` se jaldi rok diya jaye.
</Ur>
</Tr>

```javascript
function* inner() {
  yield "a";
  yield "b";
}
function* outer() {
  yield "start";
  yield* inner();
  yield* [1, 2];
  yield "end";
}
console.log([...outer()]);

function* conversation() {
  const name = yield "What's your name?";
  const color = yield `Hi ${name}! Favourite color?`;
  return `${name} likes ${color}`;
}
const chat = conversation();
console.log(chat.next().value);
console.log(chat.next("Sam").value);
console.log(chat.next("green"));

function* withCleanup() {
  try {
    yield 1;
    yield 2;
    yield 3;
  } finally {
    console.log("cleanup ran");
  }
}
for (const v of withCleanup()) {
  console.log(v);
  if (v === 2) break;
}
```

```text output
[ 'start', 'a', 'b', 1, 2, 'end' ]
What's your name?
Hi Sam! Favourite color?
{ value: 'Sam likes green', done: true }
1
2
cleanup ran
```

<Happened>
<Tr>
<En>

- `yield* inner()` and `yield* [1, 2]` spliced other sequences into the output.
- In `conversation`, the first `next()` started it and got the question. `next("Sam")` resumed it, and `"Sam"` became the value of the first `yield`. Two-way communication like this powers libraries such as Redux-Saga (and is how `async`/`await` was first built).
- `break` called the generator's `return()` behind the scenes, so `finally` ran. Use this to close files or database cursors.

</En>
<Ur>

- `yield* inner()` aur `yield* [1, 2]` ne doosre silsile output me jor diye.
- `conversation` me pehle `next()` ne ise shuru kiya aur sawal mila. `next("Sam")` ne ise dobara chalaya, aur `"Sam"` pehle `yield` ki value ban gaya. Is tarah ki do tarfa baat chit Redux-Saga jaisi libraries chalati hai (aur `async`/`await` pehle isi tarah bana tha).
- `break` ne parde ke peechhe generator ka `return()` call kiya, isliye `finally` chala. Files ya database cursors band karne ke liye ise lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Async generators and for await…of">

<Tr>
<En>
An `async function*` can `await` inside and `yield` values as they arrive. Loop over it with **`for await…of`**. It's ideal for **paginated APIs**: fetch a page, yield its items, fetch the next page only if the loop still wants more.
</En>
<Ur>
`async function*` andar `await` kar sakta hai aur values aate hi `yield` kar sakta hai. Is par **`for await…of`** se loop chalayen. Ye **paginated APIs** ke liye behtareen hai: page lao, us ke items yield karo, agla page sirf tab lao jab loop ko mazeed chahiye.
</Ur>
</Tr>

```javascript
const PAGES = { 1: ["Mug", "Lamp"], 2: ["Notebook", "Pen"], 3: ["Desk"] };

async function fetchPage(n) {
  await new Promise((r) => setTimeout(r, 10));
  return { items: PAGES[n] ?? [], next: PAGES[n + 1] ? n + 1 : null };
}

async function* allProducts() {
  let page = 1;
  while (page) {
    console.log("  fetching page", page);
    const { items, next } = await fetchPage(page);
    yield* items;
    page = next;
  }
}

for await (const product of allProducts()) {
  console.log(product);
  if (product === "Notebook") break;
}
```

```text output
  fetching page 1
Mug
Lamp
  fetching page 2
Notebook
```

<Happened>
<Tr>
<En>

- The loop sees a simple stream of products; the generator hides the paging.
- Page 2 was fetched only when the loop asked for the item after "Lamp".
- After "Notebook" the loop broke, so **page 3 was never requested**. The same pattern reads large files line by line, consumes database cursors, or processes streaming AI responses.
- Node streams and `fetch` response bodies are async iterables too: `for await (const chunk of response.body)`.

</En>
<Ur>

- Loop ko products ki saadi stream nazar aati hai; generator paging chhupa leta hai.
- Page 2 sirf tab laya gaya jab loop ne "Lamp" ke baad wala item maanga.
- "Notebook" ke baad loop toot gaya, isliye **page 3 kabhi request nahi hua**. Yahi pattern bari files line ba line parhta hai, database cursors istemal karta hai, ya streaming AI responses process karta hai.
- Node streams aur `fetch` response bodies bhi async iterables hain: `for await (const chunk of response.body)`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Iterator helpers">

<Tr>
<En>
Modern JavaScript (Chrome 122+, Node 22+) adds array-like methods directly on iterators: `map`, `filter`, `take`, `drop`, `flatMap`, `toArray` and more. They're **lazy**, like the pipeline you built by hand.
</En>
<Ur>
Jadeed JavaScript (Chrome 122+, Node 22+) iterators par seedha array jaise methods jorti hai: `map`, `filter`, `take`, `drop`, `flatMap`, `toArray` waghaira. Ye **lazy** hain, bilkul us pipeline ki tarah jo aap ne haath se banayi.
</Ur>
</Tr>

```javascript
function* naturals() {
  let n = 1;
  while (true) yield n++;
}

const result = naturals()
  .filter((n) => n % 3 === 0)
  .map((n) => n * 10)
  .take(3)
  .toArray();
console.log(result);

console.log(Iterator.from([1, 2, 3]).drop(1).toArray());
```

```text output
[ 30, 60, 90 ]
[ 2, 3 ]
```

<Happened>
<Tr>
<En>

- The infinite `naturals()` was filtered, mapped and cut to 3 values, computing only what was needed.
- `Iterator.from(…)` wraps any iterable so you can use the helpers.
- In older environments these methods don't exist; your own small `map`/`filter`/`take` generators (or a library) do the same job.

</En>
<Ur>

- Be-intiha `naturals()` ko filter, map aur 3 values tak kaata gaya, sirf zaroori hissa nikala gaya.
- `Iterator.from(…)` kisi bhi iterable ko lapetta hai taa ke aap helpers istemal kar sakein.
- Purane mahaul me ye methods maujood nahi; aap ke apne chhote `map`/`filter`/`take` generators (ya library) yahi kaam karte hain.

</Ur>

## Common mistakes

<Compare>
<Bad title="Reusing a used-up generator">

```javascript
function* letters() {
  yield "a";
  yield "b";
}
const gen = letters();
console.log([...gen], [...gen]);
```

```text output
[ 'a', 'b' ] []
```

</Bad>
<Good title="Call the generator function again">

```javascript
function* letters() {
  yield "a";
  yield "b";
}
console.log([...letters()], [...letters()]);
```

```text output
[ 'a', 'b' ] [ 'a', 'b' ]
```

</Good>
</Compare>

<Compare>
<Bad title="Spreading an infinite generator">

```text
function* naturals() { let n = 1; while (true) yield n++; }
const all = [...naturals()];   // never finishes: the page freezes
```

</Bad>
<Good title="Take only what you need">

```javascript
function* naturals() {
  let n = 1;
  while (true) yield n++;
}
const firstFive = [];
for (const n of naturals()) {
  firstFive.push(n);
  if (firstFive.length === 5) break;
}
console.log(firstFive);
```

```text output
[ 1, 2, 3, 4, 5 ]
```

</Good>
</Compare>

<Compare>
<Bad title="Looping a plain object with for…of">

```javascript
const stock = { mug: 3, lamp: 0 };
try {
  for (const item of stock) console.log(item);
} catch (error) {
  console.log(error.message);
}
```

```text output
stock is not iterable
```

</Bad>
<Good title="Use Object.entries">

```javascript
const stock = { mug: 3, lamp: 0 };
for (const [name, qty] of Object.entries(stock)) console.log(name, qty);
```

```text output
mug 3
lamp 0
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting the `*`**: `function range()` with `yield` inside is a SyntaxError.
- **Using `yield` inside a normal callback** (`arr.forEach(x => yield x)`) doesn't work; use `for…of` inside the generator.
- **Expecting `return` values in `for…of`**: the loop ignores them.
- **`for…of` over an async generator**: you need `for await…of`.
- **Using generators where an array is clearer**: for small, finite data, arrays and array methods are simpler.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`*` bhoolna**: andar `yield` wala `function range()` SyntaxError hai.
- **Aam callback ke andar `yield` lagana** (`arr.forEach(x => yield x)`) nahi chalta; generator ke andar `for…of` lein.
- **`for…of` me `return` values ki umeed**: loop inhe nazarandaz karta hai.
- **Async generator par `for…of`**: `for await…of` chahiye.
- **Jahan array zyada wazeh ho wahan generators lagana**: chhote, mehdood data ke liye arrays aur array methods aasaan hain.

</Ur>
</Tr>

## Try it yourself

<Challenge title="An iterable playlist">

<Tr>
<En>
Write a `Playlist` class with a private `#songs` array, an `add(title)` method, and a generator `[Symbol.iterator]` so `for…of` lists the songs. Add a `*shuffled()` generator that yields the songs in a **deterministic** "every other one, then the rest" order (indexes 0, 2, 4…, then 1, 3, 5…).
</En>
<Ur>
`Playlist` class likhein jis me private `#songs` array, `add(title)` method, aur generator `[Symbol.iterator]` ho taa ke `for…of` gaane dikhaye. `*shuffled()` generator jorein jo gaane **pehle se tay** "ek chhor kar ek, phir baqi" tarteeb me yield kare (indexes 0, 2, 4…, phir 1, 3, 5…).
</Ur>
</Tr>

<Solution>

```javascript
class Playlist {
  #songs = [];
  add(title) {
    this.#songs.push(title);
    return this;
  }
  *[Symbol.iterator]() {
    yield* this.#songs;
  }
  *shuffled() {
    for (let i = 0; i < this.#songs.length; i += 2) yield this.#songs[i];
    for (let i = 1; i < this.#songs.length; i += 2) yield this.#songs[i];
  }
}

const list = new Playlist().add("Intro").add("Rain").add("Drive").add("Home").add("Outro");
console.log([...list]);
console.log([...list.shuffled()]);
```

```text output
[ 'Intro', 'Rain', 'Drive', 'Home', 'Outro' ]
[ 'Intro', 'Drive', 'Outro', 'Rain', 'Home' ]
```

</Solution>

<Challenge title="Chunk a big list">

<Tr>
<En>
Write a generator `chunk(iterable, size)` that yields arrays of up to `size` items. Test it with `range(1, 8)` and size 3, and use it to "send" products to an API in batches.
</En>
<Ur>
Generator `chunk(iterable, size)` likhein jo zyada se zyada `size` items ki arrays yield kare. Ise `range(1, 8)` aur size 3 se test karein, aur products ko API ko batches me "bhejne" ke liye istemal karein.
</Ur>
</Tr>

<Solution>

```javascript
function* range(start, end) {
  for (let i = start; i < end; i++) yield i;
}

function* chunk(iterable, size) {
  let batch = [];
  for (const item of iterable) {
    batch.push(item);
    if (batch.length === size) {
      yield batch;
      batch = [];
    }
  }
  if (batch.length > 0) yield batch;
}

console.log([...chunk(range(1, 8), 3)]);
for (const batch of chunk(["Mug", "Lamp", "Pen", "Desk", "Chair"], 2)) {
  console.log("POST /api/products/bulk", batch);
}
```

```text output
[ [ 1, 2, 3 ], [ 4, 5, 6 ], [ 7 ] ]
POST /api/products/bulk [ 'Mug', 'Lamp' ]
POST /api/products/bulk [ 'Pen', 'Desk' ]
POST /api/products/bulk [ 'Chair' ]
```

<Tr>
<En>
The last, shorter batch is yielded after the loop. Because `chunk` accepts any iterable, it works with arrays, Sets and other generators alike.
</En>
<Ur>
Aakhri, chhota batch loop ke baad yield hota hai. Chunke `chunk` koi bhi iterable qabool karta hai, ye arrays, Sets aur doosre generators sab ke saath chalta hai.
</Ur>

<Takeaways>
<Tr>
<En>

- **Iterable** = has `[Symbol.iterator]()`; **iterator** = has `next()` returning `{ value, done }`. `for…of`, spread and destructuring use them.
- Arrays, strings, Maps and Sets are iterable; plain objects aren't (use `Object.entries`).
- **Generators** (`function*` + `yield`) pause at each `yield` and are the easy way to write iterators.
- Generators are **lazy**: infinite sequences are fine; take only what you need; `break` stops the producer too.
- `yield*` delegates; `next(value)` sends values in; `finally` runs on early exit.
- `async function*` + `for await…of` for data that arrives over time (pagination, streams).
- Iterator helpers (`map`, `filter`, `take`, `toArray`) work lazily on any iterator in modern runtimes.

</En>

<DeepDive title="More about iteration">

**Generator objects have three methods.** `next(value)`, `return(value)` (finish early, running `finally`), and `throw(error)` (throw an error **at** the paused `yield`, which the generator can catch).

**Iterator closing.** `for…of`, destructuring and spread call the iterator's `return()` when they stop early (via `break`, `return`, an exception, or destructuring fewer items than exist). Hand-written iterators can implement `return()` to release resources.

**Async iteration protocol.** An async iterable has `[Symbol.asyncIterator]()`, and its `next()` returns a promise of `{ value, done }`. `for await…of` also works on sync iterables of promises.

**`Array.fromAsync(asyncIterable)`** collects an async iterable into an array (newer runtimes).

**Generators vs async/await.** Before `async`/`await`, libraries like co ran generators that yielded promises and resumed them with results: async functions are essentially that pattern built into the language.

**Performance.** Generators have some overhead per value; in very hot loops over plain arrays, a classic `for` loop is faster. Use generators for clarity and laziness, not micro-speed.

</DeepDive>

<DeepDive title="Real world: the export that ran out of memory">

A reporting feature let admins download every order as CSV. The first version loaded all orders into an array, mapped them to CSV lines, joined them into one string, and sent it. With 2 million orders, the Node process needed several gigabytes of memory and crashed, taking the API down for all users.

The rewrite used an **async generator**:

```text
async function* csvLines(db) {
  yield "id,date,total\n";
  for await (const order of db.streamOrders({ batchSize: 1000 })) {
    yield `${order.id},${order.date.toISOString()},${order.total}\n`;
  }
}
// Readable.from(csvLines(db)).pipe(response)
```

The database driver returned a cursor (itself an async iterable) that fetched 1,000 rows at a time. Each row became one CSV line and was written to the response immediately. Memory stayed flat at a few megabytes no matter how many orders existed, and the download started in milliseconds instead of minutes. If the admin cancelled the download, the loop stopped and the cursor was closed through the generator's `finally`.

Lesson: when data is big, **don't build it all, stream it**: generators and async iterables are the tool.

</DeepDive>

<DeepDive title="Security lens">

- **Unbounded iteration over user-controlled data** can exhaust memory or CPU. Put limits (`take(n)`, max pages, max batch size) on generators fed by user input or external APIs.
- **Paginated fetching**: cap the number of pages and handle malicious "next page" links (only follow URLs on the expected host).
- **Spreading untrusted iterables** (`[...value]`) can run arbitrary `[Symbol.iterator]` code if the value comes from untrusted JavaScript (plugins); with JSON data this isn't possible, since JSON can't contain functions.
- **Always release resources** (`finally` in generators) so cancelled streams don't leave database cursors or file handles open, which attackers can exploit by starting and abandoning many downloads.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between an iterable and an iterator?">
An iterable is an object with a Symbol.iterator method that returns an iterator. An iterator is an object with a next method that returns objects with value and done properties. for…of asks the iterable for a fresh iterator each time.
</QA>

<QA q="What is a generator and how does yield work?">
A generator function, declared with function*, returns a generator object when called without running its body. Each next call runs the body until the next yield, which produces a value and pauses execution, preserving local state until the next call.
</QA>

<QA q="What does lazy evaluation mean and why is it useful?">
Values are computed only when requested. It allows infinite sequences, avoids computing values that are never used, and lets pipelines process one item at a time with constant memory instead of building intermediate arrays.
</QA>

<QA q="How would you paginate through an API using async generators?">
Write an async generator that fetches a page, yields each item, and loops while there is a next page. Consumers iterate with for await…of and can break early, in which case no further pages are fetched.
</QA>

<QA q="What does yield* do?">
It delegates to another iterable or generator, yielding each of its values in turn until it is exhausted, and evaluates to the delegated generator's return value.
</QA>

</DeepDive>
