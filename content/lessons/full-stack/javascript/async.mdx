<BigIdea>
<Tr>
<En>
Most code runs **top to bottom, one line at a time**, and each line finishes before the next starts. That's **synchronous** code. But some jobs **take time**: getting data from a server, waiting for a timer, reading a file. If JavaScript stood still and waited, the whole page would freeze. So it does something smarter: it **starts** the slow job, **carries on** with other code, and comes back when the job is done. That's **asynchronous** ("async") code. A slow job gives you a **promise**: a placeholder that says "the result isn't here yet, but it will be". You get the result by writing **`await`** in front of the promise, inside a function marked **`async`**. Errors are caught with **`try`/`catch`**, and several jobs can run at the same time with **`Promise.all`**.
</En>
<Ur>
Zyada tar code **upar se neeche, ek waqt me ek line** chalta hai, aur har line agli shuru hone se pehle khatam hoti hai. Ye **synchronous** code hai. Magar kuch kaamon me **waqt lagta hai**: server se data lana, timer ka intezar, file parhna. Agar JavaScript ruk kar intezar karta to poora page jam jata. Isliye wo zyada samajhdari ka kaam karta hai: sust kaam **shuru** karta hai, baqi code ke saath **aage barhta** hai, aur kaam khatam hone par wapas aata hai. Ye **asynchronous** ("async") code hai. Sust kaam aap ko ek **promise** deta hai: ek placeholder jo kehta hai "nateeja abhi nahi aaya, magar aayega". Nateeja lene ke liye promise se pehle **`await`** likha jata hai, aise function ke andar jis par **`async`** laga ho. Errors **`try`/`catch`** se pakre jate hain, aur kai kaam ek saath **`Promise.all`** se chalaye ja sakte hain.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **The web is slow compared to code.** A line of JavaScript takes a millionth of a second. A network request takes a tenth of a second or more: a hundred thousand times longer.
- **JavaScript does one thing at a time.** If it waited for the network, nothing else could happen: no clicks, no scrolling, no animation.
- **Everything interesting is async:** loading data from an API, saving a form, reading a file, talking to a database, waiting for a payment.
- **In React and Next.js** every data fetch and every form submit uses `async`/`await`.

</En>
<Ur>

- **Code ke muqable me web sust hai.** JavaScript ki ek line second ka das lakhwan hissa leti hai. Network request second ka daswan hissa ya zyada: ek lakh guna zyada.
- **JavaScript ek waqt me ek kaam karta hai.** Agar wo network ka intezar karta to kuch aur ho hi nahi sakta: na clicks, na scrolling, na animation.
- **Har dilchasp kaam async hai:** API se data lana, form mehfooz karna, file parhna, database se baat karna, payment ka intezar.
- **React aur Next.js me** har data fetch aur har form submit `async`/`await` istemal karta hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

You need async whenever your code depends on something **outside** the program that answers **later**:

- a server or API (`fetch`),
- a database or a file,
- a timer (`setTimeout`),
- the user (waiting for a click or a permission prompt).

Ordinary maths and working with arrays and objects are instant; they don't need it.

</En>
<Ur>

Async ki zaroorat tab parti hai jab aap ka code program se **bahar** ki kisi aisi cheez par munhasir ho jo **baad me** jawab deti hai:

- server ya API (`fetch`),
- database ya file,
- timer (`setTimeout`),
- user (click ya ijazat ke sawal ka intezar).

Aam hisaab aur arrays aur objects ka kaam foran hota hai; unhe is ki zaroorat nahi.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```js
async function showUser() {
  try {
    const response = await fetch("/api/user");   // wait for the server
    const user = await response.json();          // wait for the data
    console.log(user.name);
  } catch (error) {
    console.log("Could not load the user");
  }
}
```

Read it like normal top-to-bottom code. Each `await` means "wait here until this is ready".

</En>
<Ur>

```js
async function showUser() {
  try {
    const response = await fetch("/api/user");   // server ka intezar
    const user = await response.json();          // data ka intezar
    console.log(user.name);
  } catch (error) {
    console.log("Could not load the user");
  }
}
```

Ise aam upar-se-neeche code ki tarah parhein. Har `await` ka matlab hai "yahan tab tak ruko jab tak ye tayyar na ho".

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

You walk into a **burger shop** with one person at the counter.

**The synchronous way:** you order. The cashier walks to the kitchen, cooks your burger, and stands there for five minutes while the whole queue behind you waits. Nobody else can even order.

**The asynchronous way:** you order. The cashier hands you a **receipt with a number** and immediately serves the next customer. The kitchen works in the background. When your burger is ready, your number is called.

- The **receipt** is a **promise**: it isn't food, but it guarantees you'll get either a burger (**fulfilled**) or an apology that they've run out (**rejected**).
- While you hold it and wait, it's **pending**.
- **`await`** is you deciding "I'll stand here until my number is called before I do my next thing". Notice that **you** wait; the **shop** keeps serving everyone else.
- **`Promise.all`** is ordering a burger, fries and a drink together and waiting until all three are on your tray, rather than ordering each one only after the last has arrived.

</En>
<Ur>

Aap ek **burger ki dukaan** me jate hain jahan counter par ek hi shakhs hai.

**Synchronous tareeqa:** aap order dete hain. Cashier kitchen me jata hai, aap ka burger banata hai, aur paanch minute wahin khara rehta hai jabke peechhe poori qataar intezar karti hai. Koi aur order tak nahi de sakta.

**Asynchronous tareeqa:** aap order dete hain. Cashier aap ko **number wali raseed** deta hai aur foran agle customer ko dekhta hai. Kitchen peechhe kaam karta rehta hai. Burger tayyar hote hi aap ka number pukara jata hai.

- **Raseed** **promise** hai: ye khana nahi, magar zamanat hai ke aap ko ya to burger milega (**fulfilled**) ya maazrat ke khatam ho gaya (**rejected**).
- Jab tak aap use liye intezar kar rahe hain, wo **pending** hai.
- **`await`** aap ka ye faisla hai ke "agla kaam karne se pehle main yahin khara rahunga jab tak mera number na pukara jaye". Dhyan dein ke intezar **aap** karte hain; **dukaan** baqi sab ko dekhti rehti hai.
- **`Promise.all`** burger, fries aur drink ek saath order kar ke tab tak intezar karna hai jab tak teeno tray me na aa jayen, bajaye is ke ke har cheez pichhli ke aane ke baad order ki jaye.

</Ur>
</Tr>

<Step title="Normal code runs in order">

<Tr>
<En>
First, the ordinary case. Each line finishes before the next begins. This is **synchronous** code.
</En>
<Ur>
Pehle aam surat. Har line agli shuru hone se pehle khatam hoti hai. Ye **synchronous** code hai.
</Ur>
</Tr>

```javascript
console.log("1. Take the order");
console.log("2. Cook the burger");
console.log("3. Serve the burger");
```

```text output
1. Take the order
2. Cook the burger
3. Serve the burger
```

<Happened>
<Tr>
<En>

- Three lines, three outputs, in exactly the order written. Nothing surprising.
- This is fine when every step is instant. The trouble starts when step 2 takes a long time.

</En>
<Ur>

- Teen lines, teen outputs, bilkul usi tarteeb me jaise likhi hain. Koi hairani nahi.
- Jab har qadam foran ho jaye to ye theek hai. Masla tab shuru hota hai jab qadam 2 me bohot waqt lage.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="setTimeout: run this later">

<Tr>
<En>
`setTimeout(function, milliseconds)` says "run this function after this much time". 1000 milliseconds is one second. Watch the **order** of the output carefully.
</En>
<Ur>
`setTimeout(function, milliseconds)` kehta hai "ye function itne waqt ke baad chalao". 1000 milliseconds ek second hai. Output ki **tarteeb** ghaur se dekhein.
</Ur>
</Tr>

```javascript
console.log("1. Order taken");

setTimeout(() => {
  console.log("2. Burger is ready!");
}, 300);

console.log("3. Next customer, please");
```

```text output
1. Order taken
3. Next customer, please
2. Burger is ready!
```

<Happened>
<Tr>
<En>

- Line 3 printed **before** line 2, even though it's written after it.
- `setTimeout` did not pause the program. It **scheduled** the function for later and returned immediately, so JavaScript went straight on to the last line.
- 300 milliseconds later, with nothing else to do, JavaScript ran the scheduled function.
- This is the cashier handing over a receipt and serving the next customer. It's the heart of async: **the order code is written in is not always the order it runs in.**

</En>
<Ur>

- Line 3 line 2 se **pehle** print hui, halanke wo us ke baad likhi hai.
- `setTimeout` ne program ko roka nahi. Us ne function ko baad ke liye **muqarrar** kiya aur foran wapas aa gaya, isliye JavaScript seedha aakhri line par chala gaya.
- 300 milliseconds baad, jab karne ko kuch aur na tha, JavaScript ne muqarrar kiya hua function chalaya.
- Ye wahi cashier hai jo raseed de kar agle customer ko dekhta hai. Async ki asal baat yahi hai: **code jis tarteeb me likha ho, zaroori nahi usi tarteeb me chale.**

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Even zero milliseconds means later">

<Tr>
<En>
What if the delay is `0`? The function still waits until **all** the current code has finished.
</En>
<Ur>
Agar delay `0` ho to? Function phir bhi tab tak intezar karta hai jab tak **saara** maujooda code khatam na ho jaye.
</Ur>
</Tr>

```javascript
console.log("first");

setTimeout(() => console.log("from the timer"), 0);

for (let i = 1; i <= 3; i++) {
  console.log("still busy", i);
}

console.log("last");
```

```text output
first
still busy 1
still busy 2
still busy 3
last
from the timer
```

<Happened>
<Tr>
<En>

- A delay of 0 doesn't mean "now". It means "as soon as you're free".
- JavaScript has one worker. Scheduled functions wait in a **queue**, and the worker only takes the next one when the current code has completely finished.
- This waiting-and-taking-turns system is called the **event loop**.

</En>
<Ur>

- 0 ke delay ka matlab "abhi" nahi. Is ka matlab hai "jaise hi farigh ho".
- JavaScript ka ek hi karkun hai. Muqarrar kiye gaye functions **qataar** me intezar karte hain, aur karkun agla tabhi uthata hai jab maujooda code poori tarah khatam ho jaye.
- Intezar aur baari wale is nizaam ko **event loop** kehte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A promise: a receipt for a future result">

<Tr>
<En>
A **promise** is an object that stands for a result that isn't ready yet. Here we build a tiny helper, `wait`, that gives back a promise which finishes after some milliseconds. `.then(…)` says what to do when it's done.
</En>
<Ur>
**Promise** aisa object hai jo us nateeje ki jagah khara hota hai jo abhi tayyar nahi. Yahan hum ek chhota helper `wait` banate hain jo aisa promise deta hai jo kuch milliseconds baad mukammal hota hai. `.then(…)` batata hai ke mukammal hone par kya karna hai.
</Ur>
</Tr>

```javascript
function wait(ms) {
  return new Promise((resolve) => {
    setTimeout(resolve, ms);
  });
}

const receipt = wait(300);
console.log(receipt);

receipt.then(() => {
  console.log("300ms have passed");
});

console.log("waiting...");
```

```text output
Promise { <pending> }
waiting...
300ms have passed
```

<Happened>
<Tr>
<En>

- `new Promise(…)` creates the receipt. Inside, you start the slow job and call **`resolve`** when it's finished.
- Printing the promise right away shows `Promise { <pending> }`: the kitchen is still working.
- `.then(…)` attached a function to run when the promise is fulfilled.
- `waiting...` printed before the `.then` message, for the same reason as before: the program doesn't stop.
- You will rarely write `new Promise` yourself. Most of the time a built-in function such as `fetch` **gives** you a promise and you just use it.

</En>
<Ur>

- `new Promise(…)` raseed banata hai. Andar aap sust kaam shuru karte hain aur khatam hone par **`resolve`** call karte hain.
- Promise ko foran print karne par `Promise { <pending> }` dikhta hai: kitchen abhi kaam kar raha hai.
- `.then(…)` ne aisa function jora jo promise ke fulfilled hone par chale.
- `waiting...` `.then` wale paighaam se pehle print hua, usi wajah se jo pehle thi: program rukta nahi.
- `new Promise` aap khud kam hi likhenge. Zyada tar `fetch` jaisa koi built-in function aap ko promise **deta** hai aur aap bas use istemal karte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="async and await: wait in a readable way">

<Tr>
<En>
`.then` works, but with several steps the code turns into a staircase. **`await`** is the modern way: it pauses the function until the promise is done, so the code reads top to bottom again. `await` only works inside a function marked **`async`**.
</En>
<Ur>
`.then` chalta hai, magar kai qadam hon to code seerhi ban jata hai. **`await`** jadeed tareeqa hai: ye function ko promise ke mukammal hone tak rokta hai, isliye code phir upar se neeche parha jata hai. `await` sirf us function ke andar chalta hai jis par **`async`** laga ho.
</Ur>
</Tr>

```javascript
function wait(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function makeBurger() {
  console.log("1. Order taken");
  await wait(300);
  console.log("2. Burger cooked");
  await wait(200);
  console.log("3. Burger served");
}

makeBurger();
console.log("Meanwhile, the shop serves other customers");
```

```text output
1. Order taken
Meanwhile, the shop serves other customers
2. Burger cooked
3. Burger served
```

<Happened>
<Tr>
<En>

- Inside `makeBurger`, the steps ran in the order they are written: 1, wait, 2, wait, 3. That's what `await` buys you.
- But look at the second line of output. When `makeBurger` reached its first `await`, **it** paused, and control went back to the code that called it, which printed "Meanwhile…".
- So `await` pauses **only the async function it's in**. The rest of the program keeps running. The customer waits; the shop doesn't.

</En>
<Ur>

- `makeBurger` ke andar qadam usi tarteeb me chale jis me likhe hain: 1, intezar, 2, intezar, 3. `await` ka faida yahi hai.
- Magar output ki doosri line dekhein. Jab `makeBurger` apne pehle `await` par pohancha to **wo** ruk gaya, aur control us code ke paas wapas gaya jis ne use call kiya tha, jis ne "Meanwhile…" print kiya.
- Yaani `await` **sirf us async function** ko rokta hai jis me wo hai. Baqi program chalta rehta hai. Customer intezar karta hai; dukaan nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="await gives you the value">

<Tr>
<En>
A promise usually carries a **result**. `await` unwraps it: the whole `await …` expression becomes the value, and you can store it in a variable. Below, `getUser` pretends to be a server that answers after 200ms.
</En>
<Ur>
Promise aam taur par ek **nateeja** saath lata hai. `await` use khol deta hai: poora `await …` wala hissa value ban jata hai, aur aap use variable me rakh sakte hain. Neeche `getUser` aise server ki naqal karta hai jo 200ms baad jawab deta hai.
</Ur>
</Tr>

```javascript
function getUser(id) {
  return new Promise((resolve) => {
    setTimeout(() => resolve({ id: id, name: "Sara", plan: "pro" }), 200);
  });
}

async function showUser() {
  const user = await getUser(7);
  console.log(user);
  console.log("Hello, " + user.name);
}

showUser();
```

```text output
{ id: 7, name: 'Sara', plan: 'pro' }
Hello, Sara
```

<Happened>
<Tr>
<En>

- `resolve(value)` is how a promise delivers its result: here, a user object.
- `getUser(7)` returns a **promise**. `await getUser(7)` waits and then becomes the **object** inside it.
- After that line, `user` is an ordinary object and the rest of the code is ordinary too.
- This is exactly the shape of real code: `const data = await somethingSlow();`.

</En>
<Ur>

- `resolve(value)` se promise apna nateeja deta hai: yahan ek user object.
- `getUser(7)` ek **promise** wapas karta hai. `await getUser(7)` intezar karta hai aur phir us ke andar ka **object** ban jata hai.
- Us line ke baad `user` aam object hai aur baqi code bhi aam hai.
- Asli code ki bilkul yahi shakal hoti hai: `const data = await somethingSlow();`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Forgetting await gives you the receipt, not the food">

<Tr>
<En>
The most common async mistake is leaving out `await`. You then hold the **promise**, not the result.
</En>
<Ur>
Async ki sab se aam ghalti `await` chhor dena hai. Phir aap ke haath me **promise** hota hai, nateeja nahi.
</Ur>
</Tr>

```javascript
function getPrice() {
  return new Promise((resolve) => setTimeout(() => resolve(40), 100));
}

async function checkout() {
  const wrong = getPrice();
  console.log(wrong);
  console.log(wrong + 5);

  const right = await getPrice();
  console.log(right);
  console.log(right + 5);
}

checkout();
```

```text output
Promise { <pending> }
[object Promise]5
40
45
```

<Happened>
<Tr>
<En>

- Without `await`, `wrong` is the receipt itself: `Promise { <pending> }`.
- Doing maths with a receipt gives nonsense: `[object Promise]5`. On a web page this bug shows up as the text `[object Promise]`.
- With `await`, `right` is `40` and the maths works.
- If you ever see `Promise { <pending> }` or `[object Promise]`, you forgot an `await`.

</En>
<Ur>

- `await` ke baghair `wrong` khud raseed hai: `Promise { <pending> }`.
- Raseed ke saath hisaab karne par bematlab cheez milti hai: `[object Promise]5`. Web page par ye bug `[object Promise]` ke text ki shakal me nazar aata hai.
- `await` ke saath `right` `40` hai aur hisaab sahi chalta hai.
- Jab bhi `Promise { <pending> }` ya `[object Promise]` nazar aaye, samajh lein ke koi `await` reh gaya hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="When things go wrong: reject and try/catch">

<Tr>
<En>
Slow jobs fail: the network drops, the server says no. A failed promise is **rejected**. With `await`, a rejected promise **throws an error** at that line, and you catch it with `try`/`catch`. `finally` runs either way.
</En>
<Ur>
Sust kaam nakaam bhi hote hain: network toot jata hai, server inkar kar deta hai. Nakaam promise **rejected** hota hai. `await` ke saath rejected promise us line par **error phenkta** hai, aur aap use `try`/`catch` se pakarte hain. `finally` dono suraton me chalta hai.
</Ur>
</Tr>

```javascript
function getOrder(id) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (id > 100) {
        reject(new Error("Order " + id + " not found"));
      } else {
        resolve({ id: id, total: 42 });
      }
    }, 100);
  });
}

async function showOrder(id) {
  try {
    console.log("Loading order", id);
    const order = await getOrder(id);
    console.log("Total: $" + order.total);
  } catch (error) {
    console.log("Sorry:", error.message);
  } finally {
    console.log("Done with", id);
  }
}

await showOrder(5);
await showOrder(999);
```

```text output
Loading order 5
Total: $42
Done with 5
Loading order 999
Sorry: Order 999 not found
Done with 999
```

<Happened>
<Tr>
<En>

- A promise's function gets two tools: `resolve` for success and **`reject`** for failure.
- For order 5 everything in `try` ran, and `catch` was skipped.
- For order 999 the promise was rejected. The `await` line threw, the rest of `try` was **skipped**, and `catch` ran with the error.
- `finally` ran both times. It's the place to hide a loading spinner, whatever happened.
- Without `try`/`catch`, the error would be an "unhandled rejection": in a browser the user sees nothing and the page is stuck on "Loading…".

</En>
<Ur>

- Promise ke function ko do auzaar milte hain: kamyabi ke liye `resolve` aur nakaami ke liye **`reject`**.
- Order 5 ke liye `try` ka sab kuch chala, aur `catch` chhor diya gaya.
- Order 999 ke liye promise rejected hua. `await` wali line ne error phenka, `try` ka baqi hissa **chhor** diya gaya, aur `catch` error ke saath chala.
- `finally` dono dafa chala. Loading spinner chhupane ki jagah yahi hai, kuch bhi hua ho.
- `try`/`catch` ke baghair error "unhandled rejection" ban jata: browser me user ko kuch nazar nahi aata aur page "Loading…" par atka rehta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="One after another, or all at once?">

<Tr>
<En>
If three jobs don't depend on each other, don't wait for them one by one. Start them all, then wait for all with **`Promise.all`**. Each fake request below takes 300ms.
</En>
<Ur>
Agar teen kaam ek doosre par munhasir nahi to un ka ek ek kar ke intezar na karein. Sab shuru karein, phir **`Promise.all`** se sab ka intezar karein. Neeche har naqli request 300ms leti hai.
</Ur>
</Tr>

```javascript
function load(name) {
  return new Promise((resolve) => setTimeout(() => resolve(name + " data"), 300));
}

function secondsSince(start) {
  return Math.round((Date.now() - start) / 100) / 10;
}

let start = Date.now();
const user = await load("user");
const orders = await load("orders");
const messages = await load("messages");
console.log("One by one:", secondsSince(start), "seconds");

start = Date.now();
const results = await Promise.all([load("user"), load("orders"), load("messages")]);
console.log("All at once:", secondsSince(start), "seconds");
console.log(results);
```

```text output
One by one: 0.9 seconds
All at once: 0.3 seconds
[ 'user data', 'orders data', 'messages data' ]
```

<Happened>
<Tr>
<En>

- **One by one:** each `await` finished before the next request even **started**: 0.3 + 0.3 + 0.3 = 0.9 seconds.
- **All at once:** calling `load(…)` three times started all three immediately. `Promise.all` waited for the slowest: 0.3 seconds in total. Three times faster.
- `Promise.all` gives back an array of results **in the same order** as the promises you passed, so you can write `const [user, orders, messages] = await Promise.all([…])`.
- Use one-by-one only when a step **needs** the previous result (first get the user, then get that user's orders).

</En>
<Ur>

- **Ek ek kar ke:** har `await` agli request ke **shuru** hone se bhi pehle khatam hua: 0.3 + 0.3 + 0.3 = 0.9 seconds.
- **Sab ek saath:** `load(…)` ko teen dafa call karne se teeno foran shuru ho gaye. `Promise.all` ne sab se sust ka intezar kiya: kul 0.3 seconds. Teen guna tez.
- `Promise.all` nateejon ki array **usi tarteeb me** wapas karta hai jis me promises diye gaye, isliye `const [user, orders, messages] = await Promise.all([…])` likha ja sakta hai.
- Ek ek kar ke sirf tab karein jab kisi qadam ko pichhle nateeje ki **zaroorat** ho (pehle user lao, phir us user ke orders).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="When one of many fails: all vs allSettled">

<Tr>
<En>
`Promise.all` is all-or-nothing: if **any** promise is rejected, the whole thing is rejected. **`Promise.allSettled`** waits for every promise and reports each one's outcome.
</En>
<Ur>
`Promise.all` sab ya kuch nahi wala hai: agar **koi ek** promise rejected ho to poora rejected ho jata hai. **`Promise.allSettled`** har promise ka intezar karta hai aur har ek ka nateeja batata hai.
</Ur>
</Tr>

```javascript
function load(name, shouldFail) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (shouldFail) reject(new Error(name + " failed"));
      else resolve(name + " ok");
    }, 100);
  });
}

try {
  await Promise.all([load("profile", false), load("ads", true)]);
} catch (error) {
  console.log("Promise.all:", error.message);
}

const results = await Promise.allSettled([load("profile", false), load("ads", true)]);
for (const result of results) {
  if (result.status === "fulfilled") {
    console.log("worked:", result.value);
  } else {
    console.log("failed:", result.reason.message);
  }
}
```

```text output
Promise.all: ads failed
worked: profile ok
failed: ads failed
```

<Happened>
<Tr>
<En>

- With `Promise.all`, the failing "ads" request made the whole call fail, and the good "profile" result was lost.
- `Promise.allSettled` never rejects. Each result is an object: `{ status: "fulfilled", value }` or `{ status: "rejected", reason }`.
- Use `all` when you need **everything** (a checkout needs the cart **and** the address). Use `allSettled` when parts are optional (the page should still show even if the ads fail).

</En>
<Ur>

- `Promise.all` ke saath nakaam "ads" request ne poori call nakaam kar di, aur achha "profile" nateeja zaya ho gaya.
- `Promise.allSettled` kabhi reject nahi hota. Har nateeja ek object hai: `{ status: "fulfilled", value }` ya `{ status: "rejected", reason }`.
- `all` tab lein jab **sab kuch** chahiye ho (checkout ko cart **aur** address dono chahiyen). `allSettled` tab lein jab kuch hisse ikhtiyari hon (ads nakaam bhi hon to page dikhna chahiye).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="An async function always returns a promise">

<Tr>
<En>
Whatever you `return` from an `async` function is automatically wrapped in a promise. So the **caller** must `await` it too. Async spreads upward through your code.
</En>
<Ur>
`async` function se aap jo bhi `return` karein wo khud ba khud promise me lapet diya jata hai. Isliye **call karne wale** ko bhi `await` likhna parta hai. Async aap ke code me upar ki taraf phailta hai.
</Ur>
</Tr>

```javascript
async function getTotal() {
  return 42;
}

const withoutAwait = getTotal();
console.log(withoutAwait instanceof Promise);

const withAwait = await getTotal();
console.log(withAwait);

async function getPrices(ids) {
  const promises = ids.map(async (id) => {
    return id * 10;
  });
  console.log(promises.length, "promises");
  return Promise.all(promises);
}
console.log(await getPrices([1, 2, 3]));
```

```text output
true
42
3 promises
[ 10, 20, 30 ]
```

<Happened>
<Tr>
<En>

- `getTotal` returns the number 42, but because it's `async`, the caller receives a **promise** of 42. `withoutAwait instanceof Promise` is `true`: it really is a promise, not a number.
- `await getTotal()` unwraps it to `42`.
- **Arrays and async:** `map` with an async callback gives an **array of promises**, not values. Wrap it in `Promise.all` to wait for all of them. This pattern, `await Promise.all(list.map(async …))`, is how you load many items at once.
- On this page and in modern JavaScript modules you can use `await` at the top level, outside any function. In older setups it must be inside an `async` function.

</En>
<Ur>

- `getTotal` number 42 return karta hai, magar chunke wo `async` hai, call karne wale ko 42 ka **promise** milta hai. `withoutAwait instanceof Promise` `true` hai: ye waqai promise hai, number nahi.
- `await getTotal()` use khol kar `42` bana deta hai.
- **Arrays aur async:** async callback ke saath `map` **promises ki array** deta hai, values nahi. Sab ka intezar karne ke liye use `Promise.all` me lapetein. Ye namoona, `await Promise.all(list.map(async …))`, kai items ek saath load karne ka tareeqa hai.
- Is page par aur jadeed JavaScript modules me `await` sab se upar ki satah par, kisi function ke bahar bhi chalta hai. Purane setups me ise `async` function ke andar hona zaroori hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The real thing: fetch">

<Tr>
<En>
Everything so far used fake delays. In real projects the slow job is usually **`fetch`**, which asks a server for data. It needs **two** awaits: one for the response to arrive, and one to read its body as JSON. And one important catch: `fetch` only rejects when the network itself fails. A "404 Not Found" still counts as a response, so you must check **`response.ok`** yourself.
</En>
<Ur>
Ab tak sab kuch naqli delays se tha. Asli projects me sust kaam aam taur par **`fetch`** hota hai, jo server se data maangta hai. Is me **do** awaits lagte hain: ek response ke aane ke liye, aur ek us ki body ko JSON ki tarah parhne ke liye. Aur ek ahem baat: `fetch` sirf tab reject hota hai jab khud network nakaam ho. "404 Not Found" bhi response hi gina jata hai, isliye **`response.ok`** aap ko khud check karna hota hai.
</Ur>
</Tr>

```text
async function loadUser(id) {
  try {
    const response = await fetch("https://api.example.com/users/" + id);

    if (!response.ok) {
      throw new Error("Server answered " + response.status);
    }

    const user = await response.json();
    return user;
  } catch (error) {
    console.log("Could not load user:", error.message);
    return null;
  }
}

const user = await loadUser(7);
```

<Happened>
<Tr>
<En>

- `await fetch(url)` waits until the server has **started** answering and gives a `response` object.
- `response.ok` is `true` for status codes 200–299. For anything else we `throw` our own error so that `catch` handles it.
- `await response.json()` waits for the body to download and turns the JSON text into an object.
- The function returns the user, or `null` if anything failed, so the caller always knows what to expect.
- You already understand every word in this function. That's the whole pattern for loading data.

</En>
<Ur>

- `await fetch(url)` tab tak intezar karta hai jab tak server jawab dena **shuru** na kar de, aur `response` object deta hai.
- `response.ok` status codes 200–299 ke liye `true` hota hai. Kisi aur surat me hum apna error `throw` karte hain taa ke `catch` use sambhale.
- `await response.json()` body ke download hone ka intezar karta hai aur JSON text ko object me badal deta hai.
- Function user wapas karta hai, ya kuch nakaam ho to `null`, isliye call karne wale ko hamesha maloom hota hai ke kya milega.
- Is function ka har lafz ab aap samajhte hain. Data load karne ka poora namoona yahi hai.

</Ur>
</Tr>
</Happened>

</Step>

<Compare>
<Bad title="Forgetting await">

```text

}
```

</Bad>
<Good title="Await the promise">

```text

}
```

</Good>
</Compare>

<Compare>
<Bad title="await outside an async function">

```text

}
```

</Bad>
<Good title="Mark the function async">

```text

  const user = await getUser(7);
}
```

</Good>
</Compare>

<Compare>
<Bad title="No error handling">

```text
async function load() {
  const response = await fetch(url);   // if this fails, nothing catches it
  return response.json();
}
```

<Tr>
<En>A failed request becomes an unhandled rejection, and a 404 is treated as success.</En>
<Ur>Nakaam request unhandled rejection ban jati hai, aur 404 ko kamyabi samjha jata hai.</Ur>
</Tr>

</Bad>
<Good title="try/catch and check response.ok">

```text
async function load() {
  try {
    const response = await fetch(url);
    if (!response.ok) throw new Error("HTTP " + response.status);
    return await response.json();
  } catch (error) {
    return null;
  }
}
```

</Good>
</Compare>

<Compare>
<Bad title="Waiting one by one for independent jobs">

```text
const user = await getUser();
const posts = await getPosts();      // starts only after getUser finishes
const ads = await getAds();
```

</Bad>
<Good title="Start together, wait together">

```text
const [user, posts, ads] = await Promise.all([getUser(), getPosts(), getAds()]);
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Using `forEach` with an async callback.** `forEach` doesn't wait; the code after it runs before the callbacks finish. Use `for...of` with `await`, or `await Promise.all(list.map(…))`.
- **Returning a value from inside `setTimeout` or `.then` and expecting the outer function to return it.** The outer function has already finished.
- **Assuming the order of results.** Two requests started together can finish in either order.
- **Swallowing errors** with an empty `catch {}`. At least log them.
- **Forgetting to turn off the loading state** when a request fails. Put it in `finally`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Async callback ke saath `forEach`.** `forEach` intezar nahi karta; us ke baad ka code callbacks ke khatam hone se pehle chal jata hai. `await` ke saath `for...of` lein, ya `await Promise.all(list.map(…))`.
- **`setTimeout` ya `.then` ke andar se value return karna aur umeed ke bahar wala function wahi return karega.** Bahar wala function pehle hi khatam ho chuka hota hai.
- **Nateejon ki tarteeb farz kar lena.** Ek saath shuru hui do requests kisi bhi tarteeb me khatam ho sakti hain.
- **Khaali `catch {}` se errors nigal jana.** Kam az kam unhe log karein.
- **Request nakaam hone par loading ki halat band karna bhoolna.** Use `finally` me rakhein.

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- Synchronous code runs line by line. Asynchronous code starts a slow job and carries on.
- `setTimeout` and other callbacks run **later**, after the current code has finished, even with a delay of 0.
- A **promise** is a receipt for a future result: pending, then fulfilled or rejected.

- `Promise { <pending> }` ya `[object Promise]` ka matlab hai ke `await` reh gaya.

<DeepDive title="The event loop, microtasks and more promise tools">

**One thread.** JavaScript runs your code on a single thread with a single **call stack**. Timers, network requests and file access are handled by the browser or Node.js outside that thread. When one finishes, its callback is put in a queue.

**The event loop** repeats forever: run the current code until the stack is empty, then take the next waiting task and run it.

**Two queues.** Promise reactions (`.then`, and the code after an `await`) go into the **microtask queue**. Timers, clicks and network events go into the **task queue** (macrotasks). After each task, the loop empties **all** microtasks before taking the next task. So:

```text
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
console.log("D");
// A, D, C, B
```

**`await` is `.then` in disguise.** `const x = await p; rest();` is roughly `p.then((x) => rest())`. The function is split at each `await`, and the remainder is scheduled as a microtask.

**Other combinators.** `Promise.race([a, b])` settles as soon as the first one settles (useful for timeouts). `Promise.any([a, b])` fulfils with the first **success** and rejects only if all fail.

**Callback style.** Before promises, async functions took a callback: `readFile(path, (error, data) => { … })`. Nesting several of these produced "callback hell". Promises and then `async`/`await` (2017) replaced that style.

**Cancelling.** A promise can't be cancelled, but the work behind it often can. `fetch(url, { signal })` with an `AbortController` stops the request; `AbortSignal.timeout(5000)` gives a simple time limit.

**Blocking is still possible.** A long synchronous loop freezes everything, async or not, because nothing else can run until the stack is empty. Heavy calculation belongs in a Web Worker or on the server.

**Loops.** `for (const x of list) { await work(x); }` runs strictly one at a time. `await Promise.all(list.map(work))` runs all at once. For thousands of items, process in batches so you don't open thousands of connections together.

</DeepDive>

<DeepDive title="Real world: the search box that showed old results">

A search page loads results as the user types:

```javascript
async function onInput(text) {
  const results = await search(text);
  render(results);
}
```

A user types "ca" and then "cat". Two requests are now in flight. Usually "ca" returns first and "cat" second, and all is well. But "ca" matches far more rows and sometimes takes longer, so its response arrives **after** the one for "cat". The page then shows results for "ca" while the box says "cat".

This is a **race condition**: two async jobs finishing in an order the code didn't expect. Nothing throws, and it only happens on slow networks, so it survives testing.

The usual fix is to ignore or cancel outdated requests:

```javascript
let controller;

async function onInput(text) {
  controller?.abort();                       // cancel the previous request
  controller = new AbortController();
  try {
    const results = await search(text, { signal: controller.signal });
    render(results);
  } catch (error) {
    if (error.name !== "AbortError") throw error;
  }
}
```

The same bug appears in React when an effect fetches data and the component's input changes before the response arrives; the effect's cleanup function is where the request is aborted.

</DeepDive>

<DeepDive title="Security lens">

Async code creates gaps in time, and attackers work in gaps.

- **Check-then-act races.** `if (await getBalance(user) >= amount) { await withdraw(user, amount); }` looks safe. Two requests sent at the same moment can both pass the check before either withdrawal is saved, spending the balance twice. Do the check and the change in **one** database transaction or atomic update.
- **Unhandled rejections.** A promise that rejects with nobody listening can crash a Node.js process or leave it in a half-finished state. Every `await` chain needs a `catch` somewhere, and servers should log unhandled rejections.
- **Timeouts.** A `fetch` to a slow or malicious server can hang forever and tie up resources. Always set a limit with `AbortSignal.timeout`.
- **Unbounded concurrency.** `Promise.all(hugeList.map(fetchItem))` on user-supplied input can open thousands of connections and take your own server down, or be used to attack someone else's. Limit the batch size.
- **Error messages.** `catch (error) { res.json({ error: error.message }) }` can leak file paths, SQL and internal hostnames. Log the detail, send the user a generic message.
- **Trusting the response.** Data from `await response.json()` is outside input. Validate its shape and types before using it, even when it comes from your own API.
- **Stale permission checks.** If you check that a user may edit a document, then `await` something slow, the permission may have been revoked by the time you save. Re-check as close to the action as possible.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between synchronous and asynchronous code?">
Synchronous code runs line by line, and each operation must finish before the next begins. Asynchronous code starts an operation that completes later and continues executing other code in the meantime; the result is handled through a callback, a promise or await.
</QA>

<QA q="What is a promise and what are its states?">
A promise is an object representing the eventual result of an asynchronous operation. It starts pending and settles exactly once, becoming either fulfilled with a value or rejected with a reason. Once settled it never changes.
</QA>

<QA q="What do async and await do?">
The async keyword makes a function return a promise and allows await inside it. await pauses that function until the given promise settles, then returns its fulfilled value or throws its rejection reason. Only the async function is paused; the rest of the program keeps running.
</QA>

<QA q="What is the event loop?">
It is the mechanism that lets single-threaded JavaScript handle asynchronous work. The engine runs the current code until the call stack is empty, then runs all queued microtasks such as promise callbacks, then takes the next task such as a timer or event callback, and repeats.
</QA>

<QA q="What is the difference between Promise.all, allSettled, race and any?">
all waits for every promise and rejects as soon as one rejects. allSettled waits for all and never rejects, reporting each outcome. race settles with the first promise to settle, whether it fulfils or rejects. any fulfils with the first promise to fulfil and rejects only if all reject.
</QA>

<QA q="How do you handle errors with async and await?">
Wrap awaited calls in try and catch; a rejected promise throws at the await. Use finally for cleanup. With fetch, also check response.ok, because HTTP error statuses do not reject the promise.
</QA>

<QA q="Why does setTimeout with a delay of zero not run immediately?">
The callback is placed in the task queue and can only run after the current synchronous code has finished and the microtask queue is empty. The delay is a minimum, not a guarantee.
</QA>

<QA q="What happens if you use await inside forEach?">
forEach ignores the promises returned by an async callback, so it does not wait; the code after the loop runs before the callbacks complete. Use a for...of loop for sequential work or Promise.all with map for parallel work.
</QA>

</DeepDive>
