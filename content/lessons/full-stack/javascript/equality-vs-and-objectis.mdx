<BigIdea>
<Tr>
<En>
JavaScript has **three ways to ask "are these the same?"**. **`===` (strict equality)** says yes only if both values have the **same type and the same value**; it never converts anything. **`==` (loose equality)** first **converts** the values to a common type using a set of rules, then compares, which produces surprises like `"" == 0` being `true`. **`Object.is(a, b)`** is like `===` but fixes two edge cases: it treats `NaN` as equal to `NaN`, and `0` as different from `-0`. For objects and arrays, all three compare **identity**, not contents: two separate objects with the same data are **not equal**, just like two identical houses at different addresses. The rule for everyday code is simple: **use `===` and `!==`**, and compare objects by the fields you care about.
</En>
<Ur>
JavaScript me **"kya ye ek jaise hain?" poochne ke teen tareeqe** hain. **`===` (strict equality)** sirf tab haan kehta hai jab dono values ki **type bhi ek ho aur value bhi**; ye kabhi kuch nahi badalta. **`==` (loose equality)** pehle qawaid ke ek set se values ko ek mushtarik type me **badalta** hai, phir compare karta hai, jis se `"" == 0` ka `true` hona jaisi hairaniyan aati hain. **`Object.is(a, b)`** `===` jaisa hai magar do kinare ke masail theek karta hai: `NaN` ko `NaN` ke barabar maanta hai, aur `0` ko `-0` se mukhtalif. Objects aur arrays ke liye teeno **pehchaan** compare karte hain, andar ka maal nahi: ek jaise data wale do alag objects **barabar nahi**, bilkul mukhtalif pate par do ek jaise gharon ki tarah. Roz ke code ka qaida saada hai: **`===` aur `!==` istemal karein**, aur objects ko un fields se compare karein jin ki aap ko parwah hai.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **Every `if` that checks a value uses equality.** A wrong kind of equality means a login check, a filter or a "has this changed?" test quietly gives the wrong answer.
- **`==` hides bugs**: an empty form field equals `0`, `"0"` equals `false`. With `===` those stay different, as they should.
- **Object equality explains React re-renders**, why `includes` can't find "the same" object, and why two dates "at the same time" aren't `===`.

</En>
<Ur>

- **Value check karne wala har `if` barabari istemal karta hai.** Ghalat qisam ki barabari ka matlab login check, filter ya "kya ye badla?" test khamoshi se ghalat jawab deta hai.
- **`==` bugs chhupata hai**: khaali form field `0` ke barabar, `"0"` `false` ke barabar. `===` ke saath ye mukhtalif rehte hain, jaisa hona chahiye.
- **Object ki barabari React ke re-renders samjhati hai**, ye bhi ke `includes` "wahi" object kyun nahi dhoond pata, aur "ek hi waqt" ki do dates `===` kyun nahi.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| You want to check… | Use |
| --- | --- |
| Almost anything | `===` / `!==` |
| "Is it `null` or `undefined`?" in one go | `x == null` (the one accepted use of `==`) |
| "Is it `NaN`?" | `Number.isNaN(x)` (or `Object.is(x, NaN)`) |
| Two objects have the same content | Compare the fields, or a deep-equal helper |
| Two dates are the same moment | `a.getTime() === b.getTime()` |
| Two pieces of user text match | `a.normalize() === b.normalize()` (and maybe lowercase) |

</En>

| Do objects ka maal ek jaisa hai | Fields compare karein, ya deep-equal helper |
| Do dates ek hi lamha hain | `a.getTime() === b.getTime()` |

</Ur>

<Tr>
<En>

1. Default to `===` and `!==`; turn on the ESLint rule `eqeqeq` to enforce it.
2. Convert inputs to the right type **before** comparing (`Number(input) === 5`).
3. For objects, decide what "same" means (same id? same fields?) and compare that.

</En>

1. Default me `===` aur `!==` lein; ise lazmi karne ke liye ESLint ka rule `eqeqeq` on karein.
2. Compare karne se **pehle** inputs ko sahi type me badlein (`Number(input) === 5`).
3. Objects ke liye tay karein ke "ek jaisa" ka matlab kya hai (wahi id? wahi fields?) aur wahi compare karein.

</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think about checking a **ticket at a concert gate**.

- **`===` is a strict guard**: the ticket must be the right **kind** (a real ticket, not a receipt) **and** have the right number. A receipt with the same number is rejected.
- **`==` is a relaxed guard** who tries to be helpful: "a receipt with the number 42? Close enough, I'll treat it as ticket 42". Helpful sometimes, but it lets in things it shouldn't.
- **Objects** are like **houses**. Two houses can look identical inside, same furniture, same paint, but they're at **different addresses**. Asking "is this the same house?" checks the address, not the furniture. Only if you're holding two keys to the **same** house are they equal.

</En>
<Ur>

**Concert ke gate par ticket check** karne ka sochein.

- **`===` sakht guard hai**: ticket sahi **qisam** ka ho (asli ticket, raseed nahi) **aur** number bhi sahi ho. Usi number wali raseed mustarad.
- **`==` narm guard hai** jo madad karne ki koshish karta hai: "42 number wali raseed? Kaafi qareeb hai, main ise ticket 42 maan leta hoon". Kabhi madadgar, magar wo cheezen andar aane deta hai jo nahi aani chahiyen.
- **Objects** **gharon** jaise hain. Do ghar andar se bilkul ek jaise lag sakte hain, wahi furniture, wahi rang, magar wo **mukhtalif pate** par hain. "Kya ye wahi ghar hai?" poochna pata check karta hai, furniture nahi. Sirf tab barabar hain jab aap ke paas **ek hi** ghar ki do chabiyan hon.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Strict equality** | Same type and value, no conversion | `===` |
| **Loose equality** | Converts types, then compares | `==` |
| **`Object.is`** | Like `===`, but `NaN` equals `NaN` and `0` ≠ `-0` | `Object.is(NaN, NaN)` |
| **SameValueZero** | Like `Object.is` but `0` equals `-0` | `includes`, `Set`, `Map` |
| **Primitive** | A simple value compared by value | `5`, `"hi"`, `true` |
| **Reference** | The "address" of an object | two variables, one object |
| **Identity** | Being the very same object | `a === b` for objects |
| **Deep equality** | Same contents, checked recursively | a helper function |
| **`-0`** | Negative zero, a real separate value | `-1 * 0` |
| **Normalization** | Making text use one standard form | `"é".normalize()` |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Strict equality** | Wahi type aur value, koi tabdeeli nahi | `===` |
| **Loose equality** | Types badalta hai, phir compare | `==` |
| **`Object.is`** | `===` jaisa, magar `NaN` barabar `NaN` aur `0` ≠ `-0` | `Object.is(NaN, NaN)` |
| **SameValueZero** | `Object.is` jaisa magar `0` barabar `-0` | `includes`, `Set`, `Map` |
| **Primitive** | Saadi value jo value se compare ho | `5`, `"hi"`, `true` |
| **Reference** | Object ka "pata" | do variables, ek object |

## Learn it step by step

<Walkthrough>

<Step title="=== checks type and value">

<Tr>
<En>
`===` returns `true` only when both sides are the **same type** and have the **same value**. If the types differ, the answer is `false` immediately, with no conversion. `!==` is its opposite.
</En>
<Ur>
`===` sirf tab `true` deta hai jab dono taraf **ek hi type** aur **ek hi value** ho. Agar types mukhtalif hon to jawab foran `false`, koi tabdeeli nahi. `!==` is ka ulat hai.
</Ur>
</Tr>

```javascript
console.log(42 === 42, "hi" === "hi", true === true);
console.log(42 === "42", 1 === true, 0 === "");
console.log(null === null, undefined === undefined, null === undefined);
console.log("Hi" === "hi", "hi " === "hi");
console.log(42 !== "42");
```

```text output
true true true
false false false
true true false
false false
true
```

<Happened>
<Tr>
<En>

- Same type and value → `true`. Number vs string, number vs boolean → `false`, no questions asked.
- `null` and `undefined` are two different types, so `null === undefined` is false.
- Strings must match **exactly**: capital letters and a trailing space make them different. Clean up user input first (`trim()`, `toLowerCase()`).
- This predictability is why `===` is the default in professional code.

</En>
<Ur>

- Wahi type aur value → `true`. Number vs string, number vs boolean → `false`, koi sawal nahi.
- `null` aur `undefined` do mukhtalif types hain, isliye `null === undefined` false hai.
- Strings ko **bilkul** milna chahiye: bare huroof aur aakhir ki space unhe mukhtalif bana deti hai. Pehle user input saaf karein (`trim()`, `toLowerCase()`).
- Yahi pehle se maloom rawaiya wajah hai ke professional code me `===` default hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="== converts first, then compares">

<Tr>
<En>
`==` follows rules to make both sides the same type. The main ones: **`null` and `undefined` equal each other and nothing else**; a **boolean** becomes a number (true → 1, false → 0); a **string** compared with a number becomes a number; an **object** compared with a primitive is turned into a primitive.
</En>
<Ur>
`==` dono taraf ko ek type banane ke liye qawaid par chalta hai. Ahem qawaid: **`null` aur `undefined` ek doosre ke barabar hain aur kisi aur ke nahi**; **boolean** number ban jata hai (true → 1, false → 0); number se compare hone wali **string** number ban jati hai; primitive se compare hone wala **object** primitive me badla jata hai.
</Ur>
</Tr>

```javascript
console.log("5" == 5);
console.log(true == 1, false == 0, true == "1");
console.log(null == undefined, null == 0, undefined == 0);
console.log([5] == 5, ["a"] == "a");
console.log("abc" == NaN);
```

```text output
true
true true true
true false false
true true
false
```

<Happened>
<Tr>
<En>

- `"5" == 5`: the string became 5, so true.
- `true == "1"`: the boolean became 1, then `"1"` became 1, so true.
- `null == undefined` is true, but `null == 0` and `undefined == 0` are **false**: `null` and `undefined` are only loosely equal to each other.
- `[5] == 5`: the array became `"5"`, then 5. `["a"] == "a"`: the array became `"a"`.
- `NaN` is never equal to anything with `==` either.

</En>
<Ur>

- `"5" == 5`: string 5 ban gayi, isliye true.
- `true == "1"`: boolean 1 bana, phir `"1"` 1 bana, isliye true.
- `null == undefined` true hai, magar `null == 0` aur `undefined == 0` **false**: `null` aur `undefined` sirf ek doosre ke loosely barabar hain.
- `[5] == 5`: array `"5"` bani, phir 5. `["a"] == "a"`: array `"a"` bani.
- `==` ke saath bhi `NaN` kabhi kisi ke barabar nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The surprising side of ==">

<Tr>
<En>
Those rules, applied mechanically, give results that look wrong to humans. Here are the classics.
</En>
<Ur>
Ye qawaid mashini andaaz se lagayen to aise nataij aate hain jo insaanon ko ghalat lagte hain. Ye rahe mashhoor namoone.
</Ur>
</Tr>

```javascript
console.log("" == 0, "0" == 0, "" == "0");
console.log(false == "0", false == "", false == []);
console.log("\n" == 0, " " == 0);
console.log([] == ![]);
console.log("false" == false);
```

```text output
true true false
true true true
true true
true
false
```

<Happened>
<Tr>
<En>

- `"" == 0` and `"0" == 0` are both true, yet `"" == "0"` is **false** (two strings: no conversion). So `==` isn't even consistent: A equals C and B equals C, but A doesn't equal B.
- `false == "0"`: false → 0, `"0"` → 0, so true. But `"0"` is **truthy** in an `if`. Equal to false, yet true in a condition.
- Whitespace-only strings become 0: `"\n" == 0` is true.
- `[] == ![]`: `![]` is `false` (arrays are truthy), then `[] == false` → `"" == 0` → `0 == 0` → **true**. An array equals its own opposite.
- `"false" == false` is false: false → 0, `"false"` → `NaN`.
- You don't need to memorise these. You just need to **not use `==`**.

</En>
<Ur>

- `"" == 0` aur `"0" == 0` dono true hain, phir bhi `"" == "0"` **false** hai (do strings: koi tabdeeli nahi). Yani `==` yaksaan bhi nahi: A barabar C aur B barabar C, magar A barabar B nahi.
- `false == "0"`: false → 0, `"0"` → 0, isliye true. Magar `if` me `"0"` **truthy** hai. False ke barabar, phir bhi shart me true.
- Sirf whitespace wali strings 0 ban jati hain: `"\n" == 0` true hai.
- `[] == ![]`: `![]` `false` hai (arrays truthy hain), phir `[] == false` → `"" == 0` → `0 == 0` → **true**. Array apne hi ulat ke barabar.
- `"false" == false` false hai: false → 0, `"false"` → `NaN`.
- Inhe yaad karne ki zaroorat nahi. Bas **`==` istemal nahi karna**.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The one handy use of ==">

<Tr>
<En>
Because `null == undefined` is true and neither is loosely equal to anything else, `x == null` is a short way to say "**x is missing**" (null or undefined) while still treating `0`, `""` and `false` as real values. Many style guides allow exactly this one use.
</En>
<Ur>
Chunke `null == undefined` true hai aur in me se koi kisi aur ke loosely barabar nahi, `x == null` "**x ghayab hai**" (null ya undefined) kehne ka mukhtasar tareeqa hai, jabke `0`, `""` aur `false` ko asli values maanta hai. Bohot se style guides bilkul isi ek istemal ki ijazat dete hain.
</Ur>
</Tr>

```javascript
for (const x of [null, undefined, 0, "", false, "Alex"]) {
  console.log(JSON.stringify(x) ?? "undefined", "missing?", x == null, "| same as:", x === null || x === undefined);
}
```

```text output
null missing? true | same as: true
undefined missing? true | same as: true
0 missing? false | same as: false
"" missing? false | same as: false
false missing? false | same as: false
"Alex" missing? false | same as: false
```

<Happened>
<Tr>
<En>

- `x == null` gave exactly the same answers as the long form `x === null || x === undefined`.
- Today you can often use `??` or `?.` instead (`x ?? "default"`, `user?.name`), which have the same "null or undefined" meaning built in.
- If your team's linter uses `eqeqeq` with the `"smart"` or `{ null: "ignore" }` option, this is the one `==` it allows.

</En>
<Ur>

- `x == null` ne bilkul wahi jawab diye jo lambi shakal `x === null || x === undefined` ne.
- Aaj aksar is ke bajaye `??` ya `?.` istemal kar sakte hain (`x ?? "default"`, `user?.name`), jin me "null ya undefined" wala matlab pehle se bana hai.
- Agar aap ki team ka linter `eqeqeq` ko `"smart"` ya `{ null: "ignore" }` option ke saath chalata hai, to yahi ek `==` hai jis ki wo ijazat deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="NaN: not equal to itself">

<Tr>
<En>
`NaN` is the only value that is **not equal to itself** with both `===` and `==`. So you can't find it with a normal comparison. Use `Number.isNaN(x)` or `Object.is(x, NaN)`.
</En>
<Ur>
`NaN` wahid value hai jo `===` aur `==` dono ke saath **apne aap ke barabar nahi**. Isliye aam muqable se ise dhoonda nahi ja sakta. `Number.isNaN(x)` ya `Object.is(x, NaN)` lein.
</Ur>
</Tr>

```javascript
const price = Number("free");

console.log(price === NaN, price == NaN, price !== price);
console.log(Number.isNaN(price), Object.is(price, NaN));

const prices = [10, NaN, 30];
console.log(prices.indexOf(NaN), prices.includes(NaN));
console.log(prices.findIndex(Number.isNaN));
```

```text output
false false true
true true
-1 true
1
```

<Happened>
<Tr>
<En>

- `price === NaN` is false even though `price` **is** NaN. `price !== price` is true, an old trick for detecting NaN (it's the only value for which that's true).
- `indexOf` uses `===`, so it can't find `NaN` and returns -1. `includes` uses **SameValueZero**, which treats NaN as equal to NaN, so it returns true.
- `findIndex(Number.isNaN)` finds the position: 1.

</En>
<Ur>

- `price === NaN` false hai halanke `price` NaN **hi** hai. `price !== price` true hai, NaN pakarne ki purani chaal (ye wahid value hai jis ke liye ye true hai).
- `indexOf` `===` istemal karta hai, isliye `NaN` nahi dhoond pata aur -1 deta hai. `includes` **SameValueZero** istemal karta hai, jo NaN ko NaN ke barabar maanta hai, isliye true deta hai.
- `findIndex(Number.isNaN)` jagah dhoondta hai: 1.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Object.is and negative zero">

<Tr>
<En>
JavaScript has a **negative zero** (`-0`), produced by things like `-1 * 0` or rounding a tiny negative number. `===` says `0 === -0` is true. `Object.is` tells them apart, and also says `NaN` is equal to `NaN`. Otherwise it behaves exactly like `===`.
</En>
<Ur>
JavaScript me **manfi zero** (`-0`) hota hai, jo `-1 * 0` ya chhote manfi number ko round karne jaisi cheezon se banta hai. `===` kehta hai `0 === -0` true hai. `Object.is` dono ko alag pehchanta hai, aur ye bhi kehta hai ke `NaN` `NaN` ke barabar hai. Baqi har jagah ye bilkul `===` jaisa hai.
</Ur>
</Tr>

```javascript
const tiny = Math.round(-0.2);
console.log(tiny, tiny === 0, Object.is(tiny, 0), Object.is(tiny, -0));
console.log(1 / 0, 1 / -0);

console.log(Object.is(5, 5), Object.is("a", "a"), Object.is(5, "5"));
console.log(Object.is({}, {}));
console.log((-0).toString(), JSON.stringify(-0), String(-0));
```

```text output
-0 true false true
Infinity -Infinity
true true false
false
0 0 0
```

<Happened>
<Tr>
<En>

- `Math.round(-0.2)` gave `-0`. `console.log` shows the minus sign, `===` says it equals 0, and `Object.is` says it doesn't.
- It matters rarely, but it does: `1 / -0` is `-Infinity`, and a temperature or a velocity of "-0" can mean "approaching from below".
- Converting `-0` to text (`toString`, `JSON.stringify`, `String`) drops the sign, so it usually doesn't reach users.
- React uses `Object.is` to decide whether state changed, so setting state to the same `NaN` won't cause a re-render.

</En>
<Ur>

- `Math.round(-0.2)` ne `-0` diya. `console.log` minus ka nishaan dikhata hai, `===` kehta hai ye 0 ke barabar hai, aur `Object.is` kehta hai nahi.
- Ye kam hi ahem hota hai, magar hota hai: `1 / -0` `-Infinity` hai, aur "-0" ka darja hararat ya raftaar "neeche se qareeb aana" ho sakta hai.
- `-0` ko text me badalne (`toString`, `JSON.stringify`, `String`) se nishaan gir jata hai, isliye ye aam taur par users tak nahi pohanchta.
- React ye tay karne ke liye `Object.is` istemal karta hai ke state badli ya nahi, isliye state ko wahi `NaN` dene se re-render nahi hota.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Objects are compared by reference">

<Tr>
<En>
A variable holding an object doesn't hold the object itself; it holds a **reference** (an address) to it. `===` compares those references. Two objects created separately are **different**, even with identical contents. Two variables pointing at the **same** object are equal.
</En>
<Ur>
Object rakhne wala variable khud object nahi rakhta; wo us ka **reference** (pata) rakhta hai. `===` un references ka muqabla karta hai. Alag alag bane do objects **mukhtalif** hain, chahe andar ka maal bilkul ek jaisa ho. **Ek hi** object ki taraf ishara karne wale do variables barabar hain.
</Ur>
</Tr>

```javascript
const a = { id: 1, name: "Mug" };
const b = { id: 1, name: "Mug" };
const c = a;

console.log(a === b, a == b);
console.log(a === c);

c.name = "Big mug";
console.log(a.name);

console.log([1, 2] === [1, 2], [] === []);

const cart = [a, b];
console.log(cart.includes({ id: 1, name: "Mug" }), cart.includes(a));
console.log(cart.some((item) => item.id === 1));
```

```text output
false false
true
Big mug
false false
false true
true
```

<Happened>
<Tr>
<En>

- `a` and `b` look the same but are two separate objects: `===` and `==` are both **false**.
- `c = a` copied the **reference**, not the object. `a === c` is true, and changing `c.name` changed `a.name`, because it's the same object.
- Arrays are objects too: `[1, 2] === [1, 2]` is false, even `[] === []`.
- `includes` with a new object literal never finds anything. Search by a field instead: `some(item => item.id === 1)` or `find`.

</En>
<Ur>

- `a` aur `b` ek jaise lagte hain magar do alag objects hain: `===` aur `==` dono **false**.
- `c = a` ne **reference** copy kiya, object nahi. `a === c` true hai, aur `c.name` badalne se `a.name` badal gaya, kyun ke ye ek hi object hai.
- Arrays bhi objects hain: `[1, 2] === [1, 2]` false hai, `[] === []` bhi.
- Naye object literal ke saath `includes` kabhi kuch nahi dhoondta. Field se dhoondein: `some(item => item.id === 1)` ya `find`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Comparing objects by content">

<Tr>
<En>
To ask "do these two objects hold the same data?", you have to compare their **contents**. Usually the best answer is to compare **the field that identifies them** (like `id`). For a full comparison, use a small deep-equal function or a library. `JSON.stringify` is tempting but fragile.
</En>
<Ur>
"Kya in do objects me ek jaisa data hai?" poochne ke liye un ka **andar ka maal** compare karna parta hai. Aksar behtareen jawab hai **wo field compare karna jo unhe pehchanti hai** (jaise `id`). Poore muqable ke liye chhota deep-equal function ya library lein. `JSON.stringify` lalchata hai magar kamzor hai.
</Ur>
</Tr>

```javascript
const saved = { id: 7, name: "Lamp", price: 30 };
const edited = { name: "Lamp", id: 7, price: 30 };

console.log(saved.id === edited.id);
console.log(JSON.stringify(saved) === JSON.stringify(edited));

function shallowEqual(x, y) {
  const keysX = Object.keys(x);
  const keysY = Object.keys(y);
  if (keysX.length !== keysY.length) return false;
  return keysX.every((key) => Object.is(x[key], y[key]));
}

console.log(shallowEqual(saved, edited));
console.log(shallowEqual(saved, { ...saved, price: 35 }));
console.log(shallowEqual({ tags: ["a"] }, { tags: ["a"] }));
```

```text output
true
false
true
false
false
```

<Happened>
<Tr>
<En>

- Same `id` → same product. For records from a database, that's usually what "equal" means.
- `JSON.stringify` gave **false** because the keys are in a different order (`id, name` vs `name, id`). It also drops `undefined` values and can't handle dates, `Map`s or BigInt properly.
- `shallowEqual` checks that both objects have the same keys with `Object.is`-equal values. It works one level deep: `{ tags: ["a"] }` vs `{ tags: ["a"] }` is false because the two arrays are different objects.
- For nested data use a deep-equal helper: `isDeepStrictEqual` from `node:util` in Node, or `isEqual` from lodash, or `dequal`.

</En>
<Ur>

- Wahi `id` → wahi product. Database ke records ke liye "barabar" ka aksar yahi matlab hai.
- `JSON.stringify` ne **false** diya kyun ke keys ki tarteeb mukhtalif hai (`id, name` vs `name, id`). Ye `undefined` values bhi gira deta hai aur dates, `Map`s ya BigInt theek se nahi sambhalta.
- `shallowEqual` check karta hai ke dono objects ki wahi keys hon aur values `Object.is` ke hisaab se barabar hon. Ye ek level gehra kaam karta hai: `{ tags: ["a"] }` vs `{ tags: ["a"] }` false hai kyun ke do arrays alag objects hain.
- Nested data ke liye deep-equal helper lein: Node me `node:util` ka `isDeepStrictEqual`, ya lodash ka `isEqual`, ya `dequal`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Dates and text: compare the right thing">

<Tr>
<En>
Two `Date` objects are two objects, so `===` is false even for the same moment. Compare their **timestamps**. Text has its own trap: an accented letter like "é" can be stored as **one** character or as "e" plus an accent mark. They look identical but aren't `===` until you **normalize** them.
</En>
<Ur>
Do `Date` objects do objects hain, isliye ek hi lamhe ke liye bhi `===` false hai. Un ke **timestamps** compare karein. Text ka apna jaal hai: "é" jaisa accent wala harf **ek** character ki shakal me ya "e" plus accent ke nishaan ki shakal me mehfooz ho sakta hai. Dekhne me bilkul ek jaise magar **normalize** kiye baghair `===` nahi.
</Ur>
</Tr>

```javascript
const d1 = new Date("2026-11-12T10:00:00Z");
const d2 = new Date("2026-11-12T10:00:00Z");
console.log(d1 === d2, d1.getTime() === d2.getTime(), +d1 === +d2);
console.log(d1 < new Date("2026-12-01T00:00:00Z"));

const typed = "café";
const pasted = "café";
console.log(typed, pasted, typed === pasted, typed.length, pasted.length);
console.log(typed.normalize() === pasted.normalize());

const email1 = "  Alex@Example.com ";
const email2 = "alex@example.com";
console.log(email1.trim().toLowerCase() === email2);
```

```text output
false true true
true
café café false 4 5
true
true
```

<Happened>
<Tr>
<En>

- `getTime()` (or unary `+`) turns a date into milliseconds since 1970, a number you can compare with `===`. `<` and `>` already convert dates to numbers, so they work directly.
- `"café"` typed on a keyboard has 4 characters; the pasted version is `e` + a combining accent: 5 characters. Same on screen, different underneath. `normalize()` converts both to one standard form.
- For things like emails, usernames and search, clean both sides the same way (trim, lowercase, normalize) **before** comparing.

</En>
<Ur>

- `getTime()` (ya unary `+`) date ko 1970 se milliseconds me badalta hai, ek number jise `===` se compare kar sakte hain. `<` aur `>` pehle hi dates ko numbers me badalte hain, isliye seedha chalte hain.
- Keyboard se likha `"café"` 4 characters ka hai; paste kiya version `e` + jurne wala accent hai: 5 characters. Screen par ek jaise, andar mukhtalif. `normalize()` dono ko ek mayari shakal me badalta hai.
- Emails, usernames aur search jaisi cheezon ke liye compare karne se **pehle** dono taraf ko ek hi tarah saaf karein (trim, lowercase, normalize).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Which equality do built-ins use?">

<Tr>
<En>
Built-in features pick one of the equality kinds, and knowing which explains their behaviour. `indexOf` and `switch` use `===`. `includes`, `Set` and `Map` keys use **SameValueZero** (like `===`, but NaN equals NaN). React's state check uses `Object.is`.
</En>
<Ur>
Bani banai features barabari ki qismon me se ek chunti hain, aur kaun si ye jaanna un ka rawaiya samjhata hai. `indexOf` aur `switch` `===` istemal karte hain. `includes`, `Set` aur `Map` ki keys **SameValueZero** istemal karti hain (`===` jaisa, magar NaN barabar NaN). React ka state check `Object.is` istemal karta hai.
</Ur>
</Tr>

```javascript
const ids = new Set([1, 2, 2, "2", NaN, NaN, 0, -0]);
console.log(ids.size, [...ids]);

const seen = new Set();
seen.add({ id: 1 });
seen.add({ id: 1 });
console.log("objects in set:", seen.size);

const status = "1";
switch (status) {
  case 1:
    console.log("matched number 1");
    break;
  case "1":
    console.log("matched string '1'");
    break;
}
```

```text output
5 [ 1, 2, '2', NaN, 0 ]
objects in set: 2
matched string '1'
```

<Happened>
<Tr>
<En>

- The `Set` removed duplicate `2`s, kept `"2"` separately (different type), kept **one** `NaN` (SameValueZero says NaN equals NaN) and one zero (`0` and `-0` count as equal).
- Two separate `{ id: 1 }` objects are two entries: Sets compare objects by reference too. To dedupe objects, use their ids: `new Map(items.map(i => [i.id, i]))`.
- `switch` uses `===`, so the string `"1"` skipped `case 1` and matched `case "1"`. Convert input before a `switch`.

</En>
<Ur>

- `Set` ne dohre `2` hata diye, `"2"` alag rakha (mukhtalif type), **ek** `NaN` rakha (SameValueZero kehta hai NaN barabar NaN) aur ek zero (`0` aur `-0` barabar gine jate hain).
- Do alag `{ id: 1 }` objects do entries hain: Sets bhi objects ko reference se compare karte hain. Objects ke dohre hatane ke liye un ki ids lein: `new Map(items.map(i => [i.id, i]))`.
- `switch` `===` istemal karta hai, isliye string `"1"` ne `case 1` chhora aur `case "1"` se mili. `switch` se pehle input badlein.

</Ur>
</Tr>
</Happened>

</Step>

## Remember

<Takeaways>
<Tr>
<En>

- **Use `===` and `!==`.** They never convert types, so results are predictable.
- `==` converts first and gives surprises (`"" == 0`, `"0" == false`, `[] == ![]`). The only common exception is `x == null`.
- `NaN` isn't equal to itself: use `Number.isNaN`. `Object.is` treats NaN as equal and `0`/`-0` as different.
- Objects and arrays compare by **reference**: separate objects are never equal; copies of a reference are.
- Compare objects by id or fields (or a deep-equal helper), dates with `getTime()`, text after `trim/lowercase/normalize`.
- `indexOf` and `switch` use `===`; `includes`, `Set` and `Map` use SameValueZero; React uses `Object.is`.

</En>
<Ur>

- **`===` aur `!==` lein.** Ye kabhi types nahi badalte, isliye nataij pehle se maloom hote hain.

- `NaN` apne barabar nahi: `Number.isNaN` lein. `Object.is` NaN ko barabar aur `0`/`-0` ko mukhtalif maanta hai.
- Objects aur arrays **reference** se compare hote hain: alag objects kabhi barabar nahi; ek reference ki copies barabar hain.
- Objects ko id ya fields se (ya deep-equal helper se), dates ko `getTime()` se, text ko `trim/lowercase/normalize` ke baad compare karein.
- `indexOf` aur `switch` `===` istemal karte hain; `includes`, `Set` aur `Map` SameValueZero; React `Object.is`.

<DeepDive title="The full == algorithm">

The specification's **IsLooselyEqual(x, y)**, simplified:

1. If `x` and `y` have the same type, return `x === y`.
2. If one is `null` and the other `undefined`, return true.
3. Number and string: convert the string to a number, compare.
4. BigInt and string: convert the string to BigInt, compare.
5. If either is a boolean, convert it to a number and start again.
6. If one is an object and the other a string, number, BigInt or symbol, convert the object with ToPrimitive and start again.
7. BigInt and number: equal if they have the same mathematical value.
8. Otherwise, false.

**Four equality algorithms** exist in the spec: IsStrictlyEqual (`===`), IsLooselyEqual (`==`), SameValue (`Object.is`) and SameValueZero (`includes`, `Set`, `Map`, `TypedArray` searches).

**Structural equality proposals.** Records and tuples (`#{ a: 1 } === #{ a: 1 }`) were proposed to give value equality for immutable structures; until something like that ships, use ids or helpers.

</DeepDive>

<DeepDive title="Real world: the coupon that accepted everything">

A shop validated coupon codes on the server with `if (req.body.code == coupon.code)`. One coupon in the database had been created by mistake with an empty code, `""`.

A tester discovered that sending `{ "code": 0 }`, or `{ "code": [] }`, or `{ "code": false }` in the JSON body matched that coupon: `0 == ""`, `[] == ""` and `false == ""` are all true. Combined with a loop that checked every active coupon, any request with one of those values got a discount. A Discord server shared the trick before the team noticed the revenue dip.

The fixes:

1. Validate the request body with a schema: `code` must be a non-empty string of 4–20 letters and digits.
2. Replace `==` with `===` everywhere and enable ESLint's `eqeqeq` rule.
3. Add a database constraint so a coupon code can't be empty.
4. Look up the coupon by code in the database (`WHERE code = $1`) instead of comparing in a loop.

Lesson: with JSON, **the client chooses the type**. Loose equality lets an attacker pick a type that converts to whatever matches.

</DeepDive>

<DeepDive title="Security lens">

- **Use `===` in every security check**: roles, ids, tokens, coupon codes, feature flags. Loose equality lets attackers send `0`, `[]`, `true` or `null` to match unexpected values.
- **Validate types at the boundary** (zod, TypeScript, JSON Schema) so a "string" field can't arrive as an array or a number.
- **Compare secrets in constant time.** `token === expected` can leak how many leading characters matched through timing; use `crypto.timingSafeEqual` on equal-length buffers.
- **Normalize before comparing identifiers.** Usernames like `admin` spelled with a look-alike Cyrillic letter, or `file` written with the single "fi" ligature character, look the same as the real thing; normalize with `NFKC`, restrict allowed characters, and compare lowercased forms to prevent impersonation.
- **Don't decide access with `JSON.stringify` comparisons** of permission objects; compare explicit fields.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between == and === ?">
Triple equals compares type and value without conversion, while double equals converts operands to a common type using the loose equality rules before comparing, which can produce unintuitive results.
</QA>

<QA q="Why is NaN not equal to NaN and how do you test for it?">
IEEE 754 defines NaN as unordered and unequal to every value including itself. Use Number.isNaN, Object.is with NaN, or the fact that x !== x is true only for NaN.
</QA>

<QA q="What does Object.is do?">
It implements the SameValue algorithm, which behaves like strict equality except that NaN is considered equal to NaN and positive zero is considered different from negative zero.
</QA>

<QA q="How are objects compared in JavaScript?">
By reference. Two variables are equal only if they point to the same object in memory. Objects with identical properties created separately are not equal, so content comparison requires a shallow or deep equality function.
</QA>

<QA q="Why can includes find NaN but indexOf cannot?">
indexOf uses strict equality, under which NaN is never equal to anything, while includes uses SameValueZero, which treats NaN as equal to NaN.
</QA>

</DeepDive>
