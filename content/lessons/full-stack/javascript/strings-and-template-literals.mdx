<BigIdea>
<Tr>
<En>
A **string** is a piece of text: a name, an email, a message, a whole web page. You write it in quotes (`"…"`, `'…'`) or in **backticks** (`` `…` ``). Backtick strings are called **template literals**: they can span several lines and fill in values with `${…}`, which makes building messages easy. Every string has a **length** and numbered characters starting at 0. Strings are **immutable**: methods like `toUpperCase`, `trim`, `slice` and `replace` never change the original; they **return a new string**. With about fifteen methods you can clean user input, search, cut and join text, and format output. The tricky parts are emoji (some "characters" are really two or more) and safety: text from users must be **escaped** before it goes into HTML.
</En>
<Ur>
**String** text ka tukra hai: naam, email, paighaam, poora web page. Ise quotes (`"…"`, `'…'`) ya **backticks** (`` `…` ``) me likhte hain. Backtick wali strings ko **template literals** kehte hain: ye kai lines par phail sakti hain aur `${…}` se values bhar sakti hain, jis se paighaam banana aasaan hota hai. Har string ki **length** aur 0 se shuru hone wale number wale characters hote hain. Strings **badli nahi ja saktin**: `toUpperCase`, `trim`, `slice` aur `replace` jaise methods asal ko kabhi nahi badalte; ye **nayi string wapas karte** hain. Taqreeban pandrah methods se aap user input saaf kar sakte hain, dhoond sakte hain, text kaat aur jor sakte hain, aur output format kar sakte hain. Mushkil hisse emoji hain (kuch "characters" asal me do ya zyada hote hain) aur hifazat: users ka text HTML me jane se pehle **escape** hona chahiye.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

A string is like a **row of letter beads on a string**, glued shut at both ends.

- Each bead has a position number starting at **0**. You can look at any bead (`text[3]`) and count them (`length`).
- The glue means you **can't swap a bead** in place. To "change" the text, you make a **new string of beads**: copy part of it (`slice`), copy it in capitals (`toUpperCase`), copy it with some beads replaced (`replace`). The original is untouched.
- A **template literal** is a bead string with **empty slots** (`${…}`) where you clip in whatever values you have right now.
- Some fancy beads, like many emoji, are actually **two or more beads stuck together**. They look like one, but the count says two.

</En>
<Ur>

String **dhaage me pirote huroof ke daanon ki qatar** jaisi hai, dono kinaron se gond se band.

- Har daane ka jagah ka number hai jo **0** se shuru hota hai. Aap kisi bhi daane ko dekh sakte hain (`text[3]`) aur gin sakte hain (`length`).
- Gond ka matlab aap kisi daane ko apni jagah **badal nahi sakte**. Text "badalne" ke liye aap **daanon ki nayi qatar** banate hain: us ka hissa copy karein (`slice`), bare huroof me copy karein (`toUpperCase`), kuch daane badal kar copy karein (`replace`). Asal ko haath nahi lagta.
- **Template literal** aisi qatar hai jis me **khaali jaghen** (`${…}`) hain jahan aap abhi jo values hain wo laga dete hain.
- Kuch sajawati daane, jaise bohot se emoji, asal me **do ya zyada daane chipke hue** hain. Ek lagte hain, magar ginti do batati hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Quotes, escapes and template literals">

<Tr>
<En>
Double and single quotes work the same. A **backslash** escapes special characters: `\n` is a new line, `\"` a quote inside double quotes, `\\` a real backslash. **Template literals** (backticks) allow `${expression}` and real line breaks.
</En>
<Ur>
Double aur single quotes ek jaise chalte hain. **Backslash** khaas characters ko escape karta hai: `\n` nayi line, `\"` double quotes ke andar quote, `\\` asli backslash. **Template literals** (backticks) `${expression}` aur asli line breaks ki ijazat dete hain.
</Ur>
</Tr>

```javascript
const name = "Alex";
const quote = 'She said "hi"';
const path = "C:\\Users\\alex";
const twoLines = "Line one\nLine two";
console.log(name, "|", quote, "|", path);
console.log(twoLines);

const qty = 3;
const price = 4.5;
const message = `Hi ${name}, your ${qty} items cost $${(qty * price).toFixed(2)}.`;
console.log(message);

const card = `
  Order #1042
  Status: ${qty > 0 ? "paid" : "empty"}
`;
console.log(JSON.stringify(card));
```

```text output
Alex | She said "hi" | C:\Users\alex
Line one
Line two
Hi Alex, your 3 items cost $13.50.
"\n  Order #1042\n  Status: paid\n"
```

<Happened>
<Tr>
<En>

- Using single quotes outside let the double quotes inside print without escapes.
- `"C:\\Users"` printed `C:\Users`: two backslashes in code = one in the text.
- Inside `${…}` you can put **any expression**: math, method calls, even a ternary. `$${…}` is a literal `$` followed by an interpolation.
- The multi-line template kept its line breaks **and** its leading spaces; `JSON.stringify` makes them visible as `\n` and spaces. Watch out for unwanted indentation in multi-line templates.

</En>
<Ur>

- Bahar single quotes istemal karne se andar ke double quotes baghair escape ke print hue.
- `"C:\\Users"` ne `C:\Users` print kiya: code me do backslash = text me ek.
- `${…}` ke andar **koi bhi expression** rakh sakte hain: hisaab, method calls, ternary bhi. `$${…}` matlab ek asli `$` aur us ke baad interpolation.
- Kai lines wale template ne apne line breaks **aur** shuru ki spaces bhi rakhin; `JSON.stringify` inhe `\n` aur spaces ki shakal me dikhata hai. Kai lines wale templates me ghair zaroori indentation se ehtiyat karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Length, characters and immutability">

<Tr>
<En>
`length` counts characters. `text[i]` reads one character (from 0); `at(-1)` reads from the end. You **cannot** change a character in place: strings are immutable. Methods give you a new string instead.
</En>
<Ur>
`length` characters ginta hai. `text[i]` ek character parhta hai (0 se); `at(-1)` aakhir se parhta hai. Aap kisi character ko apni jagah **nahi** badal sakte: strings immutable hain. Is ke bajaye methods nayi string dete hain.
</Ur>
</Tr>

```javascript
const word = "JavaScript";
console.log(word.length, word[0], word[4], word.at(-1), word[99]);

try {
  word[0] = "j";
} catch (error) {
  console.log(error.name + ": " + error.message);
}

const lower = word.toLowerCase();
console.log(lower, word);
```

```text output
10 J S t undefined
TypeError: Cannot assign to read only property '0' of string 'JavaScript'
javascript JavaScript
```

<Happened>
<Tr>
<En>

- The last character is at index `length - 1` (9). `at(-1)` is the easy way to get it; a missing index gives `undefined`.
- Assigning to `word[0]` threw a `TypeError` (in strict mode; in old sloppy scripts it silently did nothing).
- `toLowerCase()` returned a **new** string. `word` is still "JavaScript". So always **save the result**: `name = name.trim()`. Calling `name.trim();` on its own line does nothing useful.

</En>
<Ur>

- Aakhri character index `length - 1` (9) par hai. `at(-1)` use lene ka aasaan tareeqa hai; ghayab index `undefined` deta hai.
- `word[0]` ko value dena `TypeError` phenk gaya (strict mode me; purane sloppy scripts me ye khamoshi se kuch nahi karta tha).
- `toLowerCase()` ne **nayi** string wapas ki. `word` ab bhi "JavaScript" hai. Isliye hamesha **nateeja mehfooz karein**: `name = name.trim()`. Akeli line par `name.trim();` kuch kaam ka nahi karti.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Cleaning: trim, case, padding">

<Tr>
<En>
`trim()` removes whitespace from both ends (`trimStart`/`trimEnd` for one side). `toLowerCase`/`toUpperCase` change case. `padStart`/`padEnd` add characters until a length is reached. `repeat` repeats text.
</En>
<Ur>
`trim()` dono kinaron se whitespace hatata hai (ek taraf ke liye `trimStart`/`trimEnd`). `toLowerCase`/`toUpperCase` case badalte hain. `padStart`/`padEnd` mukarrar length tak characters jorte hain. `repeat` text dohrata hai.
</Ur>
</Tr>

```javascript
const input = "   alex@Example.COM  ";
const email = input.trim().toLowerCase();
console.log(JSON.stringify(email));

console.log("Title".toUpperCase(), "ÉCOLE".toLowerCase());
console.log(String(42).padStart(6, "0"), "7".padStart(3), "|" + "Mug".padEnd(8, ".") + "$8");
console.log("-".repeat(20));

const raw = "  hello world  ";
console.log(JSON.stringify(raw.trimStart()), JSON.stringify(raw.trimEnd()));
```

```text output
"alex@example.com"
TITLE école
000042   7 |Mug.....$8
--------------------
"hello world  " "  hello world"
```

<Happened>
<Tr>
<En>

- Chaining `.trim().toLowerCase()` cleaned the email in one line: each method returns a string, so the next method runs on that.
- Case changes understand accents: "ÉCOLE" → "école".
- `padStart(6, "0")` turned 42 into "000042", perfect for order numbers and times ("7".padStart(2, "0") → "07"). Without a second argument it pads with spaces, which helps align columns.
- `trim` doesn't remove spaces **inside** the text; "hello world" keeps its middle space.

</En>
<Ur>

- `.trim().toLowerCase()` ki zanjeer ne email ek line me saaf kar di: har method string wapas karta hai, isliye agla method us par chalta hai.
- Case ki tabdeeli accents samajhti hai: "ÉCOLE" → "école".
- `padStart(6, "0")` ne 42 ko "000042" bana diya, order numbers aur waqt ke liye behtareen ("7".padStart(2, "0") → "07"). Doosre argument ke baghair ye spaces se bharta hai, jo columns seedhe karne me madad karta hai.
- `trim` text ke **andar** ki spaces nahi hatata; "hello world" ki beech wali space bachi rehti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Searching inside text">

<Tr>
<En>
`includes`, `startsWith` and `endsWith` answer yes/no. `indexOf` tells you **where** something is (or `-1` if it isn't there), and `lastIndexOf` searches from the end. All of them are **case-sensitive**.
</En>
<Ur>
`includes`, `startsWith` aur `endsWith` haan/nahi me jawab dete hain. `indexOf` batata hai koi cheez **kahan** hai (ya na ho to `-1`), aur `lastIndexOf` aakhir se dhoondta hai. Ye sab **case-sensitive** hain.
</Ur>
</Tr>

```javascript
const url = "https://shop.example.com/products/mug?color=red";
console.log(url.includes("products"), url.startsWith("https://"), url.endsWith(".pdf"));
console.log(url.indexOf("/"), url.lastIndexOf("/"), url.indexOf("cart"));
console.log("Banana".includes("ban"), "Banana".toLowerCase().includes("ban"));
```

```text output
true true false
6 33 -1
false true
```

<Happened>
<Tr>
<En>

- The first `/` is at index 6 (inside `https://`); the last is at 33, just before `mug`.
- `indexOf("cart")` is `-1`: not found. Always compare with `-1` (or use `includes`), because `0` is a valid position and is falsy.
- `"Banana".includes("ban")` is false because of the capital B. For a case-insensitive search, lowercase both sides first.
- For real URLs, the `URL` class is safer than manual searching: `new URL(url).searchParams.get("color")` gives `"red"`.

</En>
<Ur>

- Pehla `/` index 6 par hai (`https://` ke andar); aakhri 33 par, `mug` se bilkul pehle.
- `indexOf("cart")` `-1` hai: nahi mila. Hamesha `-1` se compare karein (ya `includes` lein), kyun ke `0` sahi jagah hai aur falsy hai.
- `"Banana".includes("ban")` bare B ki wajah se false hai. Case ka lihaz kiye baghair dhoondne ke liye pehle dono taraf lowercase karein.
- Asli URLs ke liye `URL` class haath se dhoondne se zyada mehfooz hai: `new URL(url).searchParams.get("color")` `"red"` deta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Cutting: slice, split and join">

<Tr>
<En>
`slice(start, end)` copies the characters from `start` up to (but **not** including) `end`. Negative numbers count from the end. `split(separator)` breaks a string into an array; `join(separator)` glues an array back into a string.
</En>
<Ur>
`slice(start, end)` `start` se `end` tak (`end` **shamil nahi**) characters copy karta hai. Manfi numbers aakhir se ginte hain. `split(separator)` string ko array me torta hai; `join(separator)` array ko wapas string me jorta hai.
</Ur>
</Tr>

```javascript
const file = "invoice-2026-11.pdf";
console.log(file.slice(0, 7), file.slice(8, 12), file.slice(-3), file.slice(-7, -4));

const dot = file.lastIndexOf(".");
console.log(file.slice(0, dot), "|", file.slice(dot + 1));
console.log(file.substring(4, 0), file.slice(4, 0) === "");

const csv = "Mug,8,true";
const parts = csv.split(",");
console.log(parts, parts.length);
console.log("a b  c".split(" "), "abc".split(""), "2026-11-12".split("-").map(Number));
console.log(["red", "green", "blue"].join(" / "));
```

```text output
invoice 2026 pdf -11
invoice-2026-11 | pdf
invo true
[ 'Mug', '8', 'true' ] 3
[ 'a', 'b', '', 'c' ] [ 'a', 'b', 'c' ] [ 2026, 11, 12 ]
red / green / blue
```

<Happened>
<Tr>
<En>

- `slice(0, 7)` took indexes 0–6: "invoice". `slice(-3)` took the last three: "pdf".
- Combining `lastIndexOf(".")` with `slice` split the file name from its extension, even with dashes in the name.
- `substring` is an older cousin of `slice`; it swaps its arguments if they're backwards and doesn't support negatives. Prefer `slice`.
- `split(",")` turned CSV text into an array, but every piece is still **text** (`'8'`, `'true'`). Convert as needed (`map(Number)`).
- Two spaces in `"a b  c"` produced an empty string between them. `split("")` splits into characters (but see the emoji step).

</En>
<Ur>

- `slice(0, 7)` ne indexes 0–6 liye: "invoice". `slice(-3)` ne aakhri teen liye: "pdf".
- `lastIndexOf(".")` ko `slice` ke saath milane se file ka naam us ki extension se alag hua, naam me dashes ke bawajood.
- `substring` `slice` ka purana rishtedaar hai; arguments ulte hon to unhe palat deta hai aur manfi support nahi karta. `slice` ko tarjeeh dein.
- `split(",")` ne CSV text ko array me badla, magar har tukra ab bhi **text** hai (`'8'`, `'true'`). Zaroorat ke mutabiq badlein (`map(Number)`).
- `"a b  c"` ki do spaces ne darmiyan khaali string banayi. `split("")` characters me torta hai (magar emoji wala qadam dekhein).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="replace and replaceAll">

<Tr>
<En>
`replace(find, with)` changes **only the first** match when `find` is a string. `replaceAll` changes every match. Both return a new string.
</En>
<Ur>
`replace(find, with)` string ki surat me **sirf pehla** mail badalta hai. `replaceAll` har mail badalta hai. Dono nayi string wapas karte hain.
</Ur>
</Tr>

```javascript
const text = "Free shipping on orders over $50. Free returns.";
console.log(text.replace("Free", "Fast"));
console.log(text.replaceAll("Free", "Fast"));

const template = "Hello {name}, your code is {code}.";
const filled = template.replace("{name}", "Sam").replace("{code}", "X7K2");
console.log(filled);

const slug = "  Summer Sale: 50% Off!  ".trim().toLowerCase().replaceAll(" ", "-");
console.log(slug);
```

```text output
Fast shipping on orders over $50. Free returns.
Fast shipping on orders over $50. Fast returns.
Hello Sam, your code is X7K2.
summer-sale:-50%-off!
```

<Happened>
<Tr>
<En>

- `replace` stopped after the first "Free"; `replaceAll` changed both. Forgetting this is a classic bug.
- Chained `replace` calls filled a simple template. (Template literals are usually better, but this pattern is common for messages stored as text in a database.)
- The slug still has `:`, `%` and `!`, which don't belong in URLs. Removing "everything that isn't a letter, digit or dash" needs a **regular expression**, coming up in a later lesson.

</En>
<Ur>

- `replace` pehle "Free" ke baad ruk gaya; `replaceAll` ne dono badle. Ise bhoolna mashhoor bug hai.
- Zanjeer wale `replace` calls ne saada template bhara. (Template literals aam taur par behtar hain, magar database me text ki shakal me rakhe paighaamon ke liye ye pattern aam hai.)
- Slug me ab bhi `:`, `%` aur `!` hain, jo URLs me nahi hone chahiyen. "Har wo cheez jo harf, hindsa ya dash nahi" hatane ke liye **regular expression** chahiye, jo baad ke lesson me aa raha hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Comparing and sorting text">

<Tr>
<En>
`sort()` without a function orders strings by **character code**: all capitals before lowercase, accented letters last, and "10" before "2". **`localeCompare`** orders text the way people expect, and options handle case and numbers.
</En>
<Ur>
Baghair function ke `sort()` strings ko **character code** se tarteeb deta hai: tamam bare huroof chhote se pehle, accent wale huroof aakhir me, aur "10" "2" se pehle. **`localeCompare`** text ko waise tarteeb deta hai jaise log umeed karte hain, aur options case aur numbers sambhalte hain.
</Ur>
</Tr>

```javascript
const names = ["zoe", "Émile", "adam", "Zoe", "Ben"];
console.log([...names].sort());
console.log([...names].sort((a, b) => a.localeCompare(b)));

console.log("a".localeCompare("b"), "b".localeCompare("a"), "a".localeCompare("a"));
console.log("Zoe".localeCompare("zoe", undefined, { sensitivity: "base" }) === 0);

const files = ["file10.txt", "file2.txt", "file1.txt"];
console.log([...files].sort(), [...files].sort((a, b) => a.localeCompare(b, undefined, { numeric: true })));
```

```text output
[ 'Ben', 'Zoe', 'adam', 'zoe', 'Émile' ]
[ 'adam', 'Ben', 'Émile', 'zoe', 'Zoe' ]
-1 1 0
true
[ 'file1.txt', 'file10.txt', 'file2.txt' ] [ 'file1.txt', 'file2.txt', 'file10.txt' ]
```

<Happened>
<Tr>
<En>

- The plain sort put "Ben" and "Zoe" before "adam", and "Émile" at the very end. Not what a person would expect.
- `localeCompare` returns a negative number (a comes first), positive (b first) or 0 (equal), exactly what `sort` needs.
- `{ sensitivity: "base" }` ignores case and accents when checking equality: "Zoe" equals "zoe".
- `{ numeric: true }` sorts "file2" before "file10", like a file manager does.
- We sorted copies (`[...names]`) because `sort` changes the array it's called on.

</En>
<Ur>

- Saade sort ne "Ben" aur "Zoe" ko "adam" se pehle, aur "Émile" ko bilkul aakhir me rakha. Insaan aisi umeed nahi karta.
- `localeCompare` manfi number (a pehle), musbat (b pehle) ya 0 (barabar) deta hai, bilkul wahi jo `sort` ko chahiye.
- `{ sensitivity: "base" }` barabari check karte waqt case aur accents nazarandaz karta hai: "Zoe" barabar "zoe".
- `{ numeric: true }` "file2" ko "file10" se pehle rakhta hai, jaise file manager karta hai.
- Humne copies (`[...names]`) sort kin kyun ke `sort` us array ko badal deta hai jis par call ho.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Emoji and the length surprise">

<Tr>
<En>
`length` counts **code units** (16-bit pieces), not the characters you see. Most emoji take **two** code units, and some "single" symbols are built from several emoji joined together. Spreading (`[...text]`) counts real code points; **`Intl.Segmenter`** counts what a person sees.
</En>
<Ur>
`length` **code units** (16-bit tukre) ginta hai, wo characters nahi jo aap dekhte hain. Zyada tar emoji **do** code units lete hain, aur kuch "akele" nishaan kai emoji jor kar bante hain. Spread (`[...text]`) asli code points ginta hai; **`Intl.Segmenter`** wo ginta hai jo insaan dekhta hai.
</Ur>
</Tr>

```javascript
const smile = "😀";
console.log(smile.length, [...smile].length);
console.log("😀😀".slice(0, 1) === "😀", [..."😀😀"][0] === "😀");

const thumbs = "👍🏽";
console.log(thumbs.length, [...thumbs].length);

const heart = "I ❤️ JS";
const seg = new Intl.Segmenter("en", { granularity: "grapheme" });
console.log([...seg.segment(thumbs)].length, [...seg.segment(heart)].length, heart.length);
```

```text output
2 1
false true
4 2
1 6 7
```

<Happened>
<Tr>
<En>

- One smiley has `length` 2. `slice(0, 1)` cut it **in half**, producing a broken character. Spreading into an array kept it whole.
- A thumbs-up with a skin tone is **two** emoji joined (thumb + tone): length 4, 2 code points, but **1** visible character.
- `Intl.Segmenter` counted what you see: 1 for the thumb, 6 for "I ❤️ JS", while `length` said 7.
- This matters for "max 280 characters" counters, truncating names with "…", and reversing text. Use `Intl.Segmenter` (or `[...text]` as an approximation) instead of `length` and `slice` when emoji are possible.

</En>
<Ur>

- Ek smiley ki `length` 2 hai. `slice(0, 1)` ne use **aadha kaat** diya, toota hua character bana. Array me spread karne se ye poora raha.
- Skin tone wala thumbs-up **do** emoji jure hue hain (angootha + rang): length 4, 2 code points, magar **1** nazar aane wala character.
- `Intl.Segmenter` ne wahi gina jo nazar aata hai: angoothe ke liye 1, "I ❤️ JS" ke liye 6, jabke `length` ne 7 kaha.
- Ye "zyada se zyada 280 characters" counters, naamon ko "…" se chhota karne, aur text ulatne ke liye ahem hai. Jab emoji mumkin hon to `length` aur `slice` ke bajaye `Intl.Segmenter` (ya andaze ke liye `[...text]`) lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Tagged templates and safe HTML">

<Tr>
<En>
Putting user text straight into HTML lets an attacker inject tags and scripts (**XSS**). A **tagged template** is a function placed before a template literal: it receives the fixed text parts and the values separately, so it can **escape the values** before joining them.
</En>
<Ur>
User ka text seedha HTML me daalna hamla awar ko tags aur scripts daalne deta hai (**XSS**). **Tagged template** template literal se pehle rakha function hai: ise tay shuda text ke hisse aur values alag alag milte hain, isliye ye jorne se pehle **values escape** kar sakta hai.
</Ur>
</Tr>

```javascript
function escapeHtml(value) {
  return String(value)
    .replaceAll("&", "&amp;")
    .replaceAll("<", "&lt;")
    .replaceAll(">", "&gt;")
    .replaceAll('"', "&quot;")
    .replaceAll("'", "&#39;");
}

function html(strings, ...values) {
  return strings.reduce((out, str, i) => out + str + (i < values.length ? escapeHtml(values[i]) : ""), "");
}

const userName = '<img src=x onerror="alert(1)">';
console.log(`<p>Hello ${userName}</p>`);
console.log(html`<p>Hello ${userName}</p>`);

function show(strings, ...values) {
  return { strings, values };
}
console.log(show`a${1}b${2}c`);
console.log(String.raw`C:\new\folder`);
```

```text output
<p>Hello <img src=x onerror="alert(1)"></p>
<p>Hello &lt;img src=x onerror=&quot;alert(1)&quot;&gt;</p>
{ strings: [ 'a', 'b', 'c' ], values: [ 1, 2 ] }
C:\new\folder
```

<Happened>
<Tr>
<En>

- The plain template put a real `<img onerror=…>` tag into the HTML. In a browser, that runs the attacker's script.
- The `html` tag escaped `<`, `>` and quotes in the **value only**, so the browser shows the text instead of running it. The fixed parts (`<p>`, `</p>`) stayed as real HTML.
- `show` reveals how tags work: the text pieces `['a', 'b', 'c']` and the values `[1, 2]` arrive separately.
- `String.raw` is a built-in tag that keeps backslashes as-is (`\n` stays as backslash + n).
- In practice, frameworks like React escape text for you (`{userName}` in JSX is safe). Be careful with `innerHTML` and `dangerouslySetInnerHTML`.

</En>
<Ur>

- Saade template ne HTML me asli `<img onerror=…>` tag daal diya. Browser me ye hamla awar ka script chala deta hai.
- `html` tag ne **sirf value** me `<`, `>` aur quotes escape kiye, isliye browser use chalane ke bajaye text dikhata hai. Tay shuda hisse (`<p>`, `</p>`) asli HTML rahe.
- `show` dikhata hai ke tags kaise kaam karte hain: text ke tukre `['a', 'b', 'c']` aur values `[1, 2]` alag alag pohanchte hain.
- `String.raw` bana banaya tag hai jo backslashes ko waise hi rakhta hai (`\n` backslash + n hi rehta hai).
- Amal me React jaise frameworks aap ke liye text escape karte hain (JSX me `{userName}` mehfooz hai). `innerHTML` aur `dangerouslySetInnerHTML` ke saath ehtiyat karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Building longer text and converting">

<Tr>
<En>
To build text from a list, `map` each item to a line and `join` them; it's cleaner than adding with `+=` in a loop. To turn other values into strings, use `String(value)` or a template literal.
</En>
<Ur>
List se text banane ke liye har item ko `map` se line banayen aur `join` karein; ye loop me `+=` se jorne se zyada saaf hai. Doosri values ko strings me badalne ke liye `String(value)` ya template literal lein.
</Ur>
</Tr>

```javascript
const items = ["Mug", "Lamp", "Notebook"];

let receipt = "";
for (const item of items) receipt += "- " + item + "\n";
console.log(receipt.trimEnd());

const lines = items.map((item, i) => `${i + 1}. ${item}`);
console.log(lines.join("\n"));

console.log(String(42), (42).toString(), 42 + "", `${42}`, String(null), String([1, 2]));
console.log((255).toString(16), (5).toString(2), Number("0x1f"));
```

```text output
- Lamp
- Notebook

2. Lamp

```

<Happened>
<Tr>
<En>

- Both approaches work. The `+=` loop needed `trimEnd()` to remove the last line break; `map` + `join("\n")` puts separators only **between** items.
- `String(x)` works for every value, including `null` and `undefined`; `x.toString()` crashes on those.
- `toString(16)` and `toString(2)` write numbers in hex and binary, handy for colors (`ff`) and bit flags.

</En>
<Ur>

- Dono tareeqe chalte hain. `+=` wale loop ko aakhri line break hatane ke liye `trimEnd()` chahiye tha; `map` + `join("\n")` separators sirf items ke **darmiyan** rakhta hai.
- `String(x)` har value ke liye chalta hai, `null` aur `undefined` samet; `x.toString()` in par crash karta hai.
- `toString(16)` aur `toString(2)` numbers ko hex aur binary me likhte hain, rangon (`ff`) aur bit flags ke liye kaam ke.

</Ur>
</Tr>
</Happened>

<DeepDive title="How strings are stored">

**UTF-16.** JavaScript strings are sequences of 16-bit code units. Characters outside the Basic Multilingual Plane (most emoji, some rare scripts) use a **surrogate pair** of two units. `charCodeAt(i)` reads one unit; `codePointAt(i)` reads a whole code point; `String.fromCodePoint(0x1f600)` builds one.

**Normalization.** The same visible text can have different code points (`"é"` as one code point or `"e"` + combining accent). `normalize("NFC")` composes, `normalize("NFD")` decomposes, and `NFKC` also folds look-alike compatibility characters. Normalize before storing or comparing identifiers.

**Other useful methods.** `split(sep, limit)`, `localeCompare` with locales (`"de"`, `"sv"`), `toLocaleUpperCase("tr")` for Turkish dotted/dotless i, `isWellFormed()` / `toWellFormed()` for broken surrogates, `matchAll` with regular expressions.

**Performance.** Engines optimise `+=` string building well, so for most code readability matters more than micro-optimisation. For very large outputs (megabytes), push parts into an array and `join` once, or stream the output.

**Intl.** `Intl.ListFormat` builds "Mug, Lamp, and Notebook"; `Intl.PluralRules` picks "1 item" vs "2 items" correctly in any language; `Intl.RelativeTimeFormat` writes "3 days ago".

</DeepDive>

<DeepDive title="Real world: the duplicate accounts">

A sign-up form stored emails exactly as typed. Over a year, a store collected accounts like `Alex@Example.com`, `alex@example.com` and `alex@example.com ` (with a trailing space from copy-paste). Password resets went to whichever account the user found first; order history was split across "three customers"; and marketing emails were sent three times to the same person, which got the store's domain flagged as spam.

The fix:

1. Clean emails **on the way in**: `email.trim().toLowerCase().normalize("NFC")`, in both the sign-up and login code.
2. Add a unique index on the **cleaned** email in the database, so duplicates are impossible.
3. A one-off script merged the existing duplicate accounts, keeping the oldest one and moving orders over.
4. Display names kept the user's own capitalisation; only the **identifier** was normalised.

Lesson: decide on **one canonical form** for text you compare (emails, usernames, coupon codes, tags) and convert to it at every entry point.

</DeepDive>

<DeepDive title="Security lens">

- **XSS**: never build HTML from user text without escaping. Prefer `textContent`, framework templating (React, Vue) or a sanitizer like DOMPurify for rich text.
- **SQL injection**: never build SQL with string concatenation or template literals. Use parameterised queries (`$1`, `?`).
- **Command injection**: don't build shell commands from user text; pass arguments as arrays (`execFile`, `spawn`).
- **Log injection**: user text with `\n` can fake extra log lines. Escape or structure logs as JSON.
- **Unicode look-alikes** in usernames and domains can impersonate others. Normalize (NFKC), restrict character sets and lowercase identifiers.
- **Length limits**: limit input size on the server, and remember `length` isn't the visual length; limit bytes too when storing.
- **Timing-safe comparison** for secrets (tokens, signatures): use `crypto.timingSafeEqual` rather than `===`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are template literals and what advantages do they have?">
Strings delimited by backticks that support interpolation with dollar-brace expressions, multi-line text without escapes, and tagged templates where a function processes the literal parts and values separately.
</QA>

<QA q="Why are strings immutable and what does that mean for string methods?">
String values cannot be modified in place, so every method such as trim, toUpperCase, slice or replace returns a new string and leaves the original unchanged. The result must be assigned to use it.
</QA>

<QA q="What is the difference between slice and substring?">
Both extract part of a string with an exclusive end index. slice accepts negative indexes counted from the end, while substring treats negatives as zero and swaps the arguments when start is greater than end.
</QA>

<QA q="Why can the length of a string differ from the number of visible characters?">
length counts UTF-16 code units. Characters outside the Basic Multilingual Plane use two units, and visible characters can combine several code points, such as emoji with skin tones or combining accents. Intl.Segmenter counts grapheme clusters.
</QA>

<QA q="How would you safely insert user input into an HTML string?">
Escape the HTML special characters in the input, for example with a tagged template that escapes interpolated values, or avoid string-built HTML entirely by setting textContent or using a framework that escapes by default.
</QA>

</DeepDive>
