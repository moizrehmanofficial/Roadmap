<BigIdea>
<Tr>
<En>
Normally a program runs **top to bottom, one line after another**. **Control flow** is how you change that order. **Conditions** (`if`, `else`, `switch`) let the program **choose** which lines to run: "if the cart is empty, show a message; otherwise, show the total". **Loops** (`for`, `while`, `for…of`) let it **repeat** lines: "for each item in the cart, add its price". Inside loops, `break` stops early and `continue` skips to the next round. With just these few tools you can express almost any logic: checking passwords, calculating totals, searching lists, retrying requests. The skill is writing them so they're **easy to read** and **always finish**.
</En>
<Ur>
Aam taur par program **upar se neeche, ek line ke baad doosri** chalta hai. **Control flow** wo tareeqa hai jis se aap ye tarteeb badalte hain. **Sharten** (`if`, `else`, `switch`) program ko **chunne** deti hain ke kaun si lines chalen: "agar cart khaali hai to paighaam dikhao; warna total dikhao". **Loops** (`for`, `while`, `for…of`) lines ko **dohrane** dete hain: "cart ke har item ke liye us ki qeemat joro". Loops ke andar `break` jaldi rok deta hai aur `continue` agle chakkar par chala jata hai. Sirf in chand auzaron se aap taqreeban har mantiq likh sakte hain: passwords check karna, totals nikalna, lists me dhoondna, requests dobara bhejna. Hunar ye hai ke inhe aise likhein ke **parhne me aasaan** hon aur **hamesha khatam** hon.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

```javascript
const total = 72;
if (total >= 50) {
  console.log("Free shipping");
} else {
  console.log("Add $" + (50 - total) + " for free shipping");
}

for (const item of ["Mug", "Lamp"]) {
  console.log("Packing", item);
}
```

```text output
Packing Mug
Packing Lamp
```

</What>
<Why>
<Tr>
<En>

- **Programs are mostly decisions and repetition.** Every feature you'll build, from login to checkout, is made of `if`s and loops.
- **Clear control flow is readable code.** Deeply nested `if`s are where bugs hide; guard clauses and good loop choices keep code flat and obvious.
- **Loops that never end freeze apps.** Knowing how loops stop protects your users and your servers.

</En>
<Ur>

- **Programs zyada tar faisle aur takraar hain.** Login se checkout tak har feature `if`s aur loops se banta hai.
- **Saaf control flow parhne layaq code hai.** Gehre nested `if`s me bugs chhupte hain; guard clauses aur sahi loops code ko seedha aur wazeh rakhte hain.
- **Kabhi khatam na hone wale loops apps ko jama dete hain.** Loops kaise rukte hain ye jaanna aap ke users aur servers ko bachata hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Use |
| --- | --- |
| Two or three different cases | `if / else if / else` |
| Many exact values of one variable (status codes, commands) | `switch` or a lookup object |
| Every item in an array | `for…of` (or array methods like `map`, `filter`) |
| A number of times, or you need the index | classic `for` |
| Repeat until something happens (retry, read until empty) | `while` |
| Run at least once, then check | `do…while` |
| Keys of a plain object | `for…in` or `Object.keys/entries` |

</En>
<Ur>

| Soorat-e-haal | Istemal |
| --- | --- |
| Do ya teen mukhtalif soorten | `if / else if / else` |
| Ek variable ki bohot si khaas values (status codes, commands) | `switch` ya lookup object |
| Array ka har item | `for…of` (ya `map`, `filter` jaise array methods) |
| Mukarrar dafa, ya index chahiye | classic `for` |
| Kuch hone tak dohrana (retry, khaali hone tak parhna) | `while` |
| Kam az kam ek dafa chalana, phir check | `do…while` |
| Saade object ki keys | `for…in` ya `Object.keys/entries` |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Write the condition as a question with a yes/no answer: `qty > stock`.
2. Put each branch in `{ }`, even when it's one line.
3. Handle the special cases first and `return` early (guard clauses).
4. For loops, make sure **something changes** each round so the condition eventually becomes false.

</En>
<Ur>

1. Shart ko haan/nahi wale sawal ki tarah likhein: `qty > stock`.
2. Har shaakh `{ }` me rakhein, chahe ek line ki ho.
3. Khaas soorten pehle sambhalein aur jaldi `return` karein (guard clauses).
4. Loops me yaqeeni banayen ke har chakkar me **kuch badle** taa ke shart aakhir kaar false ho.

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of driving with a **GPS**.

- **Conditions** are **junctions**: "If the highway is jammed, take the side road; else if it's raining, take the tunnel; otherwise, stay on the highway." You take exactly one road.
- A **`switch`** is a **roundabout with numbered exits**: you look at one value (your exit number) and leave at the matching exit.
- **Loops** are **laps around a race track**: "Drive laps **while** you have fuel" (`while`), "drive exactly 10 laps" (`for`), "visit every pit stop on the list" (`for…of`).
- **`break`** is pulling off the track early. **`continue`** is skipping the rest of this lap and starting the next one.
- An **infinite loop** is a track with no exit and a fuel tank that never empties: the car never stops.

</En>
<Ur>

**GPS** ke saath gaari chalane ka sochein.

- **Sharten** **chauraahe** hain: "Agar highway band hai to side road lo; warna agar barish hai to tunnel lo; warna highway par raho." Aap bilkul ek raasta lete hain.
- **`switch`** **number wale exits ka gol chakkar** hai: aap ek value (apna exit number) dekhte hain aur milte jhulte exit se nikal jate hain.
- **Loops** **race track ke chakkar** hain: "**Jab tak** fuel hai chakkar lagao" (`while`), "bilkul 10 chakkar lagao" (`for`), "list ke har pit stop par jao" (`for…of`).
- **`break`** track se jaldi utar jana hai. **`continue`** is chakkar ka baqi hissa chhor kar agla shuru karna hai.
- **Infinite loop** aisa track hai jis ka koi exit nahi aur fuel tank kabhi khaali nahi hota: gaari kabhi nahi rukti.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="if and else">

<Tr>
<En>
`if (condition) { … }` runs the block only when the condition is truthy. Add `else { … }` for what to do otherwise. Exactly one of the two blocks runs.
</En>
<Ur>
`if (condition) { … }` block sirf tab chalata hai jab shart truthy ho. Warna kya karna hai us ke liye `else { … }` jorein. Do me se bilkul ek block chalta hai.
</Ur>
</Tr>

```javascript
const stock = 3;
const wanted = 5;

if (wanted <= stock) {
  console.log("Added to cart");
} else {
  console.log("Only " + stock + " left");
}

const isMember = true;
if (isMember) {
  console.log("Member price applied");
}
console.log("Done");
```

```text output
Only 3 left
Member price applied
Done
```

<Happened>
<Tr>
<En>

- `wanted <= stock` was `5 <= 3` → false, so the `else` block ran.
- The second `if` has no `else`: when the condition is true the block runs, and when it's false nothing happens. Either way the program continues with "Done".
- Always use braces `{ }`. Without them only the **next single line** belongs to the `if`, and adding a second line later causes bugs.

</En>
<Ur>

- `wanted <= stock` `5 <= 3` tha → false, isliye `else` block chala.
- Doosre `if` ka `else` nahi: shart sahi ho to block chalta hai, ghalat ho to kuch nahi hota. Dono soorton me program "Done" ke saath aage chalta hai.
- Hamesha braces `{ }` lagayen. In ke baghair sirf **agli ek line** `if` ki hoti hai, aur baad me doosri line jorne se bugs bante hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="else if: more than two cases">

<Tr>
<En>
Chain conditions with `else if`. JavaScript checks them **in order** and runs the **first** one that's true, then skips the rest. Put the most specific conditions first.
</En>
<Ur>
`else if` se sharten zanjeer ki tarah jorein. JavaScript inhe **tarteeb se** check karti hai aur **pehli** sahi wali chalati hai, phir baqi chhor deti hai. Sab se khaas sharten pehle rakhein.
</Ur>
</Tr>

```javascript
function shippingFor(totalCents) {
  if (totalCents >= 10000) {
    return "Free express";
  } else if (totalCents >= 5000) {
    return "Free standard";
  } else if (totalCents > 0) {
    return "$4.99 standard";
  } else {
    return "Cart is empty";
  }
}

for (const total of [12000, 5000, 1999, 0]) {
  console.log(total, "→", shippingFor(total));
}
```

```text output
12000 → Free express
5000 → Free standard
1999 → $4.99 standard
0 → Cart is empty
```

<Happened>
<Tr>
<En>

- 12000 matched the first condition; the others were never checked.
- 5000 failed `>= 10000` but matched `>= 5000`.
- **Order matters.** If `>= 5000` came first, 12000 would match it and never reach "Free express".
- The final `else` catches everything else, so the function always returns something.

</En>
<Ur>

- 12000 pehli shart se mila; baqi kabhi check hi nahi huin.
- 5000 `>= 10000` me fail hua magar `>= 5000` se mila.
- **Tarteeb ahem hai.** Agar `>= 5000` pehle hota to 12000 usi se mil jata aur kabhi "Free express" tak na pohanchta.
- Aakhri `else` baqi sab pakar leta hai, isliye function hamesha kuch na kuch wapas karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Combining conditions">

<Tr>
<En>
Use `&&` (and), `||` (or) and `!` (not) to build bigger conditions. Give complex conditions a **name** by storing them in a variable; the `if` then reads like a sentence.
</En>
<Ur>
Bari sharten banane ke liye `&&` (aur), `||` (ya) aur `!` (nahi) lein. Pecheeda sharton ko variable me rakh kar **naam** dein; phir `if` jumle ki tarah parha jata hai.
</Ur>
</Tr>

```javascript
const user = { loggedIn: true, role: "editor", banned: false };
const post = { authorId: 7, published: false };
const userId = 7;

const isOwner = post.authorId === userId;
const isStaff = user.role === "admin" || user.role === "editor";
const canEdit = user.loggedIn && !user.banned && (isOwner || isStaff);

if (canEdit) {
  console.log("Show the Edit button");
}

if (!post.published && isOwner) {
  console.log("Show 'Publish' to the author");
}
```

```text output
Show the Edit button
Show 'Publish' to the author
```

<Happened>
<Tr>
<En>

- `canEdit` reads like the business rule: "logged in, not banned, and either the owner or staff".
- The brackets in `(isOwner || isStaff)` matter: without them, `&&` would bind first and the rule would change.
- Named conditions are easy to test, reuse and log (`console.log({ isOwner, isStaff })`) when something goes wrong.

</En>
<Ur>

- `canEdit` business ke qaide ki tarah parha jata hai: "login hai, banned nahi, aur ya to maalik ya staff".
- `(isOwner || isStaff)` ke brackets ahem hain: in ke baghair `&&` pehle jurta aur qaida badal jata.
- Naam wali sharten test karna, dobara istemal karna aur masla hone par log karna (`console.log({ isOwner, isStaff })`) aasaan hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Guard clauses: return early">

<Tr>
<En>
Instead of nesting `if` inside `if`, handle the "no" cases first and **leave the function early** with `return`. What's left at the bottom is the normal, happy path, with no extra indentation.
</En>
<Ur>
`if` ke andar `if` daalne ke bajaye pehle "nahi" wali soorten sambhalein aur `return` se **function se jaldi nikal jayen**. Neeche jo bachta hai wo aam, khush raasta hai, baghair izafi indentation ke.
</Ur>
</Tr>

```javascript
// Nested: hard to follow
function checkoutNested(cart, user) {
  if (user) {
    if (cart.length > 0) {
      if (user.address) {
        return "Order placed";
      } else {
        return "Add an address";
      }
    } else {
      return "Cart is empty";
    }
  } else {
    return "Please log in";
  }
}

// Guard clauses: flat and clear
function checkout(cart, user) {
  if (!user) return "Please log in";
  if (cart.length === 0) return "Cart is empty";
  if (!user.address) return "Add an address";
  return "Order placed";
}

const alex = { address: "1 Main St" };
console.log(checkout(["Mug"], alex), "|", checkoutNested(["Mug"], alex));
console.log(checkout([], alex), "|", checkout(["Mug"], null), "|", checkout(["Mug"], {}));
```

```text output
Order placed | Order placed
Cart is empty | Please log in | Add an address
```

<Happened>
<Tr>
<En>

- Both functions give the same answers, but `checkout` is 4 lines you can read top to bottom: each problem is checked and dealt with, then the real work happens.
- In the nested version, each `else` is far from its `if`, so it's easy to match the wrong message to the wrong check.
- Guard clauses are also how you validate input at the top of API handlers.

</En>
<Ur>

- Dono functions ek jaise jawab dete hain, magar `checkout` 4 lines hai jo upar se neeche parhi ja sakti hain: har masla check ho kar nipat jata hai, phir asal kaam hota hai.
- Nested version me har `else` apne `if` se door hai, isliye ghalat paighaam ghalat check se jor dena aasaan hai.
- API handlers ke upar input validate karne ka tareeqa bhi guard clauses hi hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="switch, and the missing break">

<Tr>
<En>
`switch` compares one value against several `case`s using `===`. When a case matches, the code runs **until a `break`**. If you forget `break`, it keeps going into the next case ("fall-through"). `default` handles anything unmatched.
</En>
<Ur>
`switch` ek value ko `===` se kai `case`s se milata hai. Jab case mile, code **`break` tak** chalta hai. `break` bhool jayen to agle case me chalta rehta hai ("fall-through"). `default` har na-mili cheez sambhalta hai.
</Ur>
</Tr>

```javascript
function statusMessage(status) {
  switch (status) {
    case "pending":
      return "We received your order";
    case "shipped":
    case "in_transit":
      return "On its way";
    case "delivered":
      return "Delivered";
    default:
      return "Unknown status: " + status;
  }
}
console.log(statusMessage("shipped"), "|", statusMessage("in_transit"), "|", statusMessage("lost"));

// The classic bug: no break
const plan = "pro";
switch (plan) {
  case "pro":
    console.log("Unlock reports");
  case "basic":
    console.log("Unlock dashboard");
    break;
  case "free":
    console.log("Show upgrade banner");
}
```

```text output
On its way | On its way | Unknown status: lost
Unlock reports
Unlock dashboard
```

<Happened>
<Tr>
<En>

- In `statusMessage`, each case uses `return`, which leaves the function, so no `break` is needed.
- `"shipped"` and `"in_transit"` share one result by stacking the cases: this is **deliberate** fall-through.
- In the second `switch`, `"pro"` printed "Unlock reports" and then **fell through** into the `"basic"` case. Here that might be intended (pro includes basic), but more often a missing `break` is a bug. Add a comment like `// falls through` when you mean it.
- `switch` uses `===`, so `case 1` won't match the string `"1"`.

</En>
<Ur>

- `statusMessage` me har case `return` istemal karta hai, jo function se nikal jata hai, isliye `break` ki zaroorat nahi.
- `"shipped"` aur `"in_transit"` cases ko upar neeche rakh kar ek nateeja share karte hain: ye **jaan boojh kar** fall-through hai.
- Doosre `switch` me `"pro"` ne "Unlock reports" print kiya aur phir `"basic"` case me **gir gaya**. Yahan shayad yahi chahiye tha (pro me basic shamil hai), magar aksar ghayab `break` bug hota hai. Jab irada ho to `// falls through` jaisa comment likhein.
- `switch` `===` istemal karta hai, isliye `case 1` string `"1"` se nahi milega.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A lookup object instead of a long switch">

<Tr>
<En>
When each case just maps a value to a result, an **object** is often shorter and easier to extend than a `switch`. Use `??` for the default.
</En>
<Ur>
Jab har case bas ek value ko nateeje se milata ho, to **object** aksar `switch` se chhota aur barhane me aasaan hota hai. Default ke liye `??` lein.
</Ur>
</Tr>

```javascript
const SHIPPING_DAYS = {
  standard: 5,
  express: 2,
  overnight: 1,
};

function deliveryDays(method) {
  return SHIPPING_DAYS[method] ?? "Unknown method";
}

console.log(deliveryDays("express"), deliveryDays("overnight"), deliveryDays("drone"));
console.log(Object.keys(SHIPPING_DAYS));
```

```text output
2 1 Unknown method
[ 'standard', 'express', 'overnight' ]
```

<Happened>
<Tr>
<En>

- Adding a new method is one line of data, not a new `case`.
- The same object can also feed a dropdown (`Object.keys`), so the options and the logic never get out of sync.
- Careful with user input: `SHIPPING_DAYS["toString"]` finds a built-in function. Use `Object.hasOwn(SHIPPING_DAYS, method)` or a `Map` when keys come from users.

</En>
<Ur>

- Naya method jorna data ki ek line hai, naya `case` nahi.
- Wahi object dropdown ko bhi data de sakta hai (`Object.keys`), isliye options aur mantiq kabhi bemail nahi hote.
- User input ke saath ehtiyat: `SHIPPING_DAYS["toString"]` ek built-in function dhoond leta hai. Jab keys users se aayen to `Object.hasOwn(SHIPPING_DAYS, method)` ya `Map` lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The classic for loop">

<Tr>
<En>
A `for` loop has three parts in its brackets: **start** (`let i = 0`), **keep going while** (`i < 5`) and **after each round** (`i++`). Use it when you need a counter or the index.
</En>
<Ur>
`for` loop ke brackets me teen hisse hote hain: **shuru** (`let i = 0`), **jab tak chalte raho** (`i < 5`) aur **har chakkar ke baad** (`i++`). Jab counter ya index chahiye ho to ise lein.
</Ur>
</Tr>

```javascript
for (let i = 1; i <= 3; i++) {
  console.log("Round", i);
}

const products = ["Mug", "Lamp", "Notebook"];
for (let i = 0; i < products.length; i++) {
  console.log(i + 1 + ".", products[i]);
}

// Count down by 2
for (let n = 10; n > 0; n -= 2) {
  console.log("n =", n);
}
```

```text output
Round 1
Round 2
Round 3
1. Mug
2. Lamp
3. Notebook
n = 10
n = 8
n = 6
n = 4
n = 2
```

<Happened>
<Tr>
<En>

- Round by round: set `i = 1` → check `1 <= 3` → run the body → `i++` → check again… When `i` becomes 4, `4 <= 3` is false and the loop ends.
- Array indexes start at **0**, so the loop goes from `0` to `products.length - 1`. Using `<=` there would read `products[3]`, which is `undefined` (an "off-by-one" bug).
- The third part can be anything that moves toward the end: `n -= 2` counts down by two.

</En>
<Ur>

- Chakkar ba chakkar: `i = 1` rakho → `1 <= 3` check → body chalao → `i++` → dobara check… Jab `i` 4 hota hai to `4 <= 3` false hai aur loop khatam.
- Array ke indexes **0** se shuru hote hain, isliye loop `0` se `products.length - 1` tak jata hai. Wahan `<=` lagana `products[3]` parhta, jo `undefined` hai (ek "off-by-one" bug).
- Teesra hissa kuch bhi ho sakta hai jo aakhir ki taraf le jaye: `n -= 2` do do kar ke neeche ginta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="for…of for lists, for…in for keys">

<Tr>
<En>
`for…of` gives you each **value** of an array, string, `Map` or `Set`. It's the clearest way to visit every item. `for…in` gives you each **key** of an object. Don't use `for…in` on arrays.
</En>
<Ur>
`for…of` array, string, `Map` ya `Set` ki har **value** deta hai. Har item tak jane ka sab se wazeh tareeqa hai. `for…in` object ki har **key** deta hai. Arrays par `for…in` istemal na karein.
</Ur>
</Tr>

```javascript
const cart = [
  { name: "Mug", price: 8 },
  { name: "Lamp", price: 30 },
];

let total = 0;
for (const item of cart) {
  total += item.price;
}
console.log("total:", total);

for (const letter of "Hey") {
  console.log(letter);
}

for (const [index, item] of cart.entries()) {
  console.log(index, item.name);
}

const prices = { mug: 8, lamp: 30 };
for (const key in prices) {
  console.log(key, "costs", prices[key]);
}
for (const [key, value] of Object.entries(prices)) {
  console.log(key, "=", value);
}
```

```text output
total: 38
H
e
y
0 Mug
1 Lamp
mug costs 8
lamp costs 30
mug = 8
lamp = 30
```

<Happened>
<Tr>
<En>

- `for (const item of cart)` hands you each object directly; no index juggling, no off-by-one.
- Strings are lists of characters, so `for…of` walks through `"Hey"` letter by letter.
- `cart.entries()` gives `[index, item]` pairs when you need both.
- `for…in` gave the keys of `prices`. `Object.entries` + `for…of` gives keys **and** values together and is the more modern style.
- `for…in` on an array gives the indexes as **strings** (`"0"`, `"1"`) and also visits extra properties, so stick to `for…of` for arrays.

</En>
<Ur>

- `for (const item of cart)` har object seedha deta hai; index ka jhanjhat nahi, off-by-one nahi.
- Strings characters ki list hain, isliye `for…of` `"Hey"` ko harf ba harf chalta hai.
- Jab dono chahiyen to `cart.entries()` `[index, item]` ke jore deta hai.
- `for…in` ne `prices` ki keys din. `Object.entries` + `for…of` keys **aur** values ek saath deta hai aur zyada jadeed andaaz hai.
- Array par `for…in` indexes **strings** ki shakal me deta hai (`"0"`, `"1"`) aur izafi properties bhi chhoota hai, isliye arrays ke liye `for…of` par rahein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="while and do…while">

<Tr>
<En>
`while (condition)` repeats as long as the condition is true. Use it when you don't know in advance how many rounds you'll need. `do { … } while (condition)` runs the body **once first**, then checks.
</En>
<Ur>
`while (condition)` tab tak dohrata hai jab tak shart sahi ho. Jab pehle se pata na ho ke kitne chakkar lagenge to ise lein. `do { … } while (condition)` body **pehle ek dafa** chalata hai, phir check karta hai.
</Ur>
</Tr>

```javascript
// How many years until savings double at 7% a year?
let balance = 1000;
let years = 0;
while (balance < 2000) {
  balance *= 1.07;
  years++;
}
console.log("years:", years, "balance:", balance.toFixed(2));

// Keep taking items until the box is full
const queue = [4, 3, 5, 2, 6];
const box = [];
let weight = 0;
while (queue.length > 0 && weight + queue[0] <= 10) {
  const item = queue.shift();
  box.push(item);
  weight += item;
}
console.log("box:", box, "left:", queue);

let attempts = 0;
do {
  attempts++;
  console.log("attempt", attempts);
} while (attempts < 0);
```

```text output
years: 11 balance: 2104.85
box: [ 4, 3 ] left: [ 5, 2, 6 ]
attempt 1
```

<Happened>
<Tr>
<En>

- The savings loop didn't know it needed 11 rounds; it just kept going while the balance was under 2000. Each round **changes** `balance`, so the condition eventually becomes false.
- The box loop stops for **either** reason: the queue is empty, or the next item won't fit (4 + 3 = 7, and 7 + 5 = 12 > 10).
- The `do…while` body ran once even though `attempts < 0` was false from the start. That's its only difference from `while`. It's useful for "ask, then check if the answer is valid".

</En>
<Ur>

- Savings wale loop ko pata nahi tha ke 11 chakkar chahiyen; wo bas tab tak chalta raha jab tak balance 2000 se kam tha. Har chakkar `balance` **badalta** hai, isliye shart aakhir kaar false hoti hai.
- Box wala loop **kisi bhi** wajah se rukta hai: queue khaali ho, ya agla item fit na ho (4 + 3 = 7, aur 7 + 5 = 12 > 10).
- `do…while` ki body ek dafa chali halanke `attempts < 0` shuru se false tha. `while` se iska yahi wahid farq hai. "Poochho, phir check karo ke jawab sahi hai" ke liye kaam ka hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="break and continue">

<Tr>
<En>
`break` leaves the loop immediately: use it when you've found what you were looking for. `continue` skips the rest of the current round and goes to the next one: use it to ignore items you don't care about.
</En>
<Ur>
`break` foran loop se nikal jata hai: jab jo dhoond rahe the wo mil jaye to ise lein. `continue` maujooda chakkar ka baqi hissa chhor kar agle par jata hai: jin items ki parwah nahi unhe nazarandaz karne ke liye ise lein.
</Ur>
</Tr>

```javascript
const orders = [
  { id: 101, status: "paid", total: 40 },
  { id: 102, status: "cancelled", total: 99 },
  { id: 103, status: "paid", total: 15 },
  { id: 104, status: "paid", total: 250 },
  { id: 105, status: "paid", total: 60 },
];

let revenue = 0;
for (const order of orders) {
  if (order.status === "cancelled") continue;
  revenue += order.total;
}
console.log("revenue:", revenue);

let firstBig = null;
for (const order of orders) {
  console.log("checking", order.id);
  if (order.total > 100) {
    firstBig = order;
    break;
  }
}
console.log("first big order:", firstBig.id);
```

```text output
revenue: 365
checking 101
checking 102
checking 103
checking 104
first big order: 104
```

<Happened>
<Tr>
<En>

- `continue` skipped the cancelled order, so its 99 wasn't added: 40 + 15 + 250 + 60 = 365.
- `break` stopped the search at order 104. Order 105 was never checked, which saves work on long lists.
- Array methods do the same jobs with less code: `orders.filter(o => o.status !== "cancelled")` and `orders.find(o => o.total > 100)`. Loops are still useful when you need `break` with complex logic, or `await` inside.

</En>
<Ur>

- `continue` ne cancelled order chhor diya, isliye us ke 99 nahi jure: 40 + 15 + 250 + 60 = 365.
- `break` ne talaash order 104 par rok di. Order 105 kabhi check nahi hua, jo lambi lists par mehnat bachata hai.
- Array methods yahi kaam kam code me karte hain: `orders.filter(o => o.status !== "cancelled")` aur `orders.find(o => o.total > 100)`. Loops tab bhi kaam ke hain jab pecheeda mantiq ke saath `break` chahiye, ya andar `await`.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Nested loops and labels">

<Tr>
<En>
A loop can contain another loop: for every round of the outer loop, the inner loop runs completely. `break` only leaves the **innermost** loop; to leave both, put the code in a function and `return`, or use a **label**.
</En>
<Ur>
Loop ke andar doosra loop ho sakta hai: bahar wale loop ke har chakkar me andar wala poora chalta hai. `break` sirf **sab se andar wale** loop se nikalta hai; dono se nikalne ke liye code function me rakh kar `return` karein, ya **label** lein.
</Ur>
</Tr>

```javascript
const sizes = ["S", "M"];
const colors = ["red", "blue", "green"];
for (const size of sizes) {
  for (const color of colors) {
    console.log(size + "-" + color);
  }
}

const seats = [
  ["taken", "taken", "free"],
  ["taken", "free", "free"],
];

function firstFreeSeat(rows) {
  for (let r = 0; r < rows.length; r++) {
    for (let s = 0; s < rows[r].length; s++) {
      if (rows[r][s] === "free") return { row: r + 1, seat: s + 1 };
    }
  }
  return null;
}
console.log(firstFreeSeat(seats));

outer: for (const row of seats) {
  for (const seat of row) {
    if (seat === "free") {
      console.log("found one, stopping both loops");
      break outer;
    }
  }
}
```

```text output
S-red
S-blue
S-green
M-red
M-blue
M-green
{ row: 1, seat: 3 }
found one, stopping both loops
```

<Happened>
<Tr>
<En>

- 2 sizes × 3 colors = 6 combinations: the inner loop ran fully for each size.
- `firstFreeSeat` used `return` to leave **both** loops at once as soon as it found a free seat. This is the cleanest approach.
- `break outer` jumps out of the loop labelled `outer:`. Labels work, but they're rare; a function with `return` is usually clearer.
- Watch the cost: nested loops multiply. 1,000 × 1,000 = a million rounds. For lookups, a `Map` or `Set` is often much faster.

</En>
<Ur>

- 2 sizes × 3 rang = 6 jore: andar wala loop har size ke liye poora chala.
- `firstFreeSeat` ne khaali seat milte hi `return` se **dono** loops se ek saath nikal gaya. Ye sab se saaf tareeqa hai.
- `break outer` `outer:` label wale loop se bahar kood jata hai. Labels chalte hain, magar kam milte hain; `return` wala function aam taur par zyada wazeh hai.
- Qeemat par nazar rakhein: nested loops zarb hote hain. 1,000 × 1,000 = das lakh chakkar. Dhoondne ke liye `Map` ya `Set` aksar kaheen tez hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Avoiding infinite loops">

<Tr>
<En>
A loop runs forever if its condition **never becomes false** and nothing calls `break`. In a browser tab that freezes the page; on a server it burns CPU. Always check: **what changes each round, and does it move toward the end?** A safety limit helps for loops that wait on outside conditions.
</En>
<Ur>
Loop hamesha chalta hai agar us ki shart **kabhi false na ho** aur koi `break` call na kare. Browser tab me ye page jama deta hai; server par CPU jalata hai. Hamesha check karein: **har chakkar me kya badalta hai, aur kya wo aakhir ki taraf jata hai?** Bahar ki sharton ka intezar karne wale loops ke liye hifazati hadd madad karti hai.
</Ur>
</Tr>

```javascript
// Bug: i never changes → would loop forever (don't run this)
// let i = 0;
// while (i < 3) { console.log(i); }

// Bug: counting the wrong way → also forever
// for (let n = 10; n > 0; n++) { … }

// Safe pattern for "retry until it works"
function tryToConnect(attempt) {
  return attempt === 3; // pretend it succeeds on the 3rd try
}

const MAX_ATTEMPTS = 5;
let attempt = 0;
let connected = false;
while (!connected && attempt < MAX_ATTEMPTS) {
  attempt++;
  connected = tryToConnect(attempt);
  console.log("attempt", attempt, connected ? "ok" : "failed");
}
console.log(connected ? "Connected" : "Gave up after " + MAX_ATTEMPTS + " attempts");
```

```text output
attempt 1 failed
attempt 2 failed
attempt 3 ok
Connected
```

<Happened>
<Tr>
<En>

- The two commented-out loops show the usual causes: forgetting to update the counter, and updating it in the wrong direction.
- The retry loop has **two** ways out: success (`connected`) or the limit (`MAX_ATTEMPTS`). Even if the connection never works, it stops after 5 tries.
- If you do freeze a loop on this page, the Run button stops it after 5 seconds. In a browser tab, close the tab; in Node, press **Ctrl+C**.

</En>
<Ur>

- Comment kiye gaye do loops aam wajahen dikhate hain: counter update karna bhool jana, aur ghalat simt me update karna.
- Retry loop ke nikalne ke **do** raaste hain: kamyabi (`connected`) ya hadd (`MAX_ATTEMPTS`). Agar connection kabhi na bane tab bhi 5 koshishon ke baad ruk jata hai.
- Agar is page par koi loop atak jaye to Run button 5 second baad use rok deta hai. Browser tab me tab band karein; Node me **Ctrl+C** dabayen.

</Ur>
</Tr>
</Happened>

<Tr>
<En>

More mistakes to avoid:

- **Changing an array while looping over it** (`splice` inside `for`), which skips items. Build a new array or loop backwards.
- **Using `for…in` on arrays.** Use `for…of`.
- **Deep nesting** of `if`s. Use guard clauses and named conditions.
- **Using `var` for loop counters**: closures inside the loop all see the last value. Use `let` (Scope & Closures lesson).
- **No exit condition** in `while (true)` loops. Always have a `break` and a safety limit.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Arrays par `for…in` lagana.** `for…of` lein.
- **`if`s ki gehri nesting.** Guard clauses aur naam wali sharten lein.
- **Loop counters ke liye `var`**: loop ke andar ke closures sab aakhri value dekhte hain. `let` lein (Scope & Closures lesson).
- **`while (true)` loops me nikalne ki shart na hona.** Hamesha `break` aur hifazati hadd rakhein.

</Ur>

```javascript
function passwordProblems(pw) {
  let hasDigit = false;
  let hasUpper = false;
  for (const ch of pw) {
    if (ch >= "0" && ch <= "9") hasDigit = true;
    else if (ch >= "A" && ch <= "Z") hasUpper = true;

  if (pw.length < 10) problems.push("at least 10 characters");
  if (!hasDigit) problems.push("a digit");
  if (!hasUpper) problems.push("an uppercase letter");
```

## Remember

<Takeaways>
<Tr>
<En>

- `if / else if / else` runs the **first** matching branch; put specific conditions first; always use `{ }`.
- Name complex conditions (`const canEdit = …`) and use **guard clauses** to keep code flat.
- `switch` matches with `===` and falls through without `break`; a lookup object is often simpler.
- `for` for counters, `for…of` for values, `for…in` / `Object.entries` for object keys, `while` for "until", `do…while` for "at least once".
- `break` leaves a loop; `continue` skips one round; `return` leaves nested loops inside a function.
- Every loop needs something that changes toward the end; add a max-attempts limit for retries.

</En>

- `if / else if / else` **pehli** milne wali shaakh chalata hai; khaas sharten pehle; hamesha `{ }` lagayen.
- Pecheeda sharton ko naam dein (`const canEdit = …`) aur code seedha rakhne ke liye **guard clauses** lein.
- `switch` `===` se milata hai aur `break` ke baghair gir jata hai; lookup object aksar aasaan hai.
- Counters ke liye `for`, values ke liye `for…of`, object keys ke liye `for…in` / `Object.entries`, "jab tak" ke liye `while`, "kam az kam ek dafa" ke liye `do…while`.
- `break` loop se nikalta hai; `continue` ek chakkar chhorta hai; function ke andar `return` nested loops se nikalta hai.

<DeepDive title="More about control flow">

**Block scope.** `let` and `const` declared inside `{ }` (an `if` body or a loop) only exist inside that block. A `let` in a `for` header gets a **fresh copy each iteration**, which is why closures in `for (let i…)` loops work as expected.

**`switch (true)`.** A pattern for ranges: `switch (true) { case score >= 90: … }`. It works, but an `if…else if` chain is usually clearer.

**Loops vs array methods.**

| Need | Loop | Method |
| --- | --- | --- |
| Transform each item | `for…of` + `push` | `map` |
| Keep some items | `for…of` + `if` + `push` | `filter` |
| Find the first match | `for…of` + `break` | `find` |
| Total | `for…of` + `+=` | `reduce` |
| Any / all | loop + flag | `some` / `every` |

Methods are shorter and say **what** you want; loops are better for early exits with side effects, very hot code, and `await` in sequence.

**`for await…of`** loops over async iterables (streams, paginated APIs). Covered with iterators and generators.

**Exceptions as control flow.** `throw` jumps out of any number of loops and functions to the nearest `try…catch`. Use it for errors, not for normal decisions (Error Handling lesson).

</DeepDive>

<DeepDive title="Real world: the retry loop that took down an API">

A mobile app's sync feature called an API in a loop until it succeeded:

```text
while (true) {
  const ok = await sync();
  if (ok) break;
}
```

One day the API had a 10-minute outage. Every open app, about 200,000 of them, started retrying **as fast as the network allowed**, with no delay and no limit. When the API came back, it was immediately hit by millions of requests per second and fell over again. Engineers called it a "retry storm"; the outage lasted three hours instead of ten minutes.

The fix:

1. A **maximum number of attempts** (5), after which the app showed "Sync paused, will retry later".
2. **Exponential backoff**: wait 1s, 2s, 4s, 8s… between attempts.
3. **Jitter**: add a random delay so 200,000 phones don't all retry at the same second.
4. Respect the server's `Retry-After` header when it sends one.

Lesson: every loop that depends on the outside world needs **two exits** (success and a limit) and must **slow down** between attempts.

</DeepDive>

<DeepDive title="Security lens">

- **Fail closed in conditions.** Write `if (!isAuthorised) return deny();` at the top (a guard clause), so any unexpected value means "no".
- **Don't loop over user-controlled sizes without limits.** A request asking for `count=100000000` can make a loop run for minutes. Cap sizes and validate input.
- **Regular-expression and nested-loop complexity** can be abused (ReDoS, quadratic algorithms). Watch for loops inside loops over user data.
- **Lookup objects with user keys** can hit built-in properties like `__proto__` or `constructor`. Use `Map`, `Object.hasOwn`, or `Object.create(null)`.
- **Rate-limit retries and logins.** A loop that retries a password check or an API call without delay is a brute-force tool.
- **Always have a `default` branch** in switches over security-relevant values (roles, actions) that denies by default.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between for…of and for…in?">
for…of iterates over the values of an iterable such as an array, string, Map or Set. for…in iterates over the enumerable string keys of an object, including inherited ones, and gives array indexes as strings, so it is meant for plain objects rather than arrays.
</QA>

<QA q="What is a guard clause and why use it?">
A guard clause is an early return or throw that handles an invalid or special case at the start of a function. It removes nesting, keeps the main logic at the top level and makes preconditions explicit.
</QA>

<QA q="What is switch fall-through?">
When a matching case has no break or return, execution continues into the following cases. It can be used deliberately to share code between cases but is a common source of bugs when the break is forgotten.
</QA>

<QA q="How do you exit nested loops early?">
Put the loops in a function and return when done, use a labeled break that names the outer loop, or restructure with array methods such as some or find.
</QA>

<QA q="How do you prevent infinite loops when retrying an operation?">
Ensure the loop has a success exit and a maximum attempt limit, update the state each iteration, and add delays such as exponential backoff with jitter between attempts.
</QA>

</DeepDive>
