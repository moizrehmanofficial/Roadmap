<BigIdea>
<Tr>
<En>
A **regular expression** (regex) is a small pattern language for text. Instead of searching for one exact word, you describe a **shape**: `/\d+/` means "one or more digits", `/^\d{5}$/` means "exactly five digits and nothing else", `/[^a-z0-9]+/g` means "every run of characters that isn't a lowercase letter or digit". In JavaScript you write a pattern between slashes and use it with **`test`** (yes/no), **`match`** / **`matchAll`** (find), **`replace`** (change) and **`split`** (cut). Regex is powerful for cleaning and checking text: slugs, dates, log lines, postal codes. It's also easy to make unreadable or **dangerously slow**, so the skill is keeping patterns small, testing them with real examples, and using a proper parser for complex formats.
</En>
<Ur>
**Regular expression** (regex) text ke liye patterns ki chhoti si zaban hai. Ek bilkul theek lafz dhoondne ke bajaye aap **shakal** bayan karte hain: `/\d+/` matlab "ek ya zyada hindse", `/^\d{5}$/` matlab "bilkul paanch hindse aur kuch nahi", `/[^a-z0-9]+/g` matlab "characters ka har silsila jo chhota harf ya hindsa nahi". JavaScript me aap pattern slashes ke darmiyan likhte hain aur use **`test`** (haan/nahi), **`match`** / **`matchAll`** (dhoondna), **`replace`** (badalna) aur **`split`** (kaatna) ke saath istemal karte hain. Regex text saaf aur check karne ke liye taqatwar hai: slugs, dates, log lines, postal codes. Ise na-qabil-e-parh ya **khatarnak had tak sust** banana bhi aasaan hai, isliye hunar ye hai ke patterns chhote rakhein, asli misaalon se test karein, aur pecheeda formats ke liye durust parser lein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

A regex is like a **stencil** you slide along a line of text.

- A plain word stencil (`/cat/`) only lights up where those exact letters appear.
- **Character classes** are holes shaped like "any digit" (`\d`) or "any vowel" (`[aeiou]`): many different letters fit through.
- **Quantifiers** are stretchy holes: `\d+` stretches to fit "7" or "1042".
- **Anchors** (`^`, `$`) pin the stencil to the start or end of the line, so "must be **exactly** five digits" really means exactly.
- **Groups** are labelled windows in the stencil: after a match, you can read what showed through each window (year, month, day).
- The **`g` flag** means "slide the stencil all the way along and mark **every** match", not just the first.

</En>
<Ur>

Regex text ki line par sarkaya jane wala **stencil** jaisa hai.

- Saade lafz ka stencil (`/cat/`) sirf wahan roshan hota hai jahan bilkul wahi huroof hon.
- **Character classes** "koi bhi hindsa" (`\d`) ya "koi bhi vowel" (`[aeiou]`) ki shakal ke surakh hain: bohot se mukhtalif huroof un se guzar jate hain.
- **Quantifiers** khinchne wale surakh hain: `\d+` "7" ya "1042" me fit hone ke liye khinch jata hai.
- **Anchors** (`^`, `$`) stencil ko line ke shuru ya aakhir se baandh dete hain, taa ke "**bilkul** paanch hindse" ka matlab waqai bilkul ho.
- **Groups** stencil me label lagi khirkiyan hain: mail ke baad aap parh sakte hain ke har khirki se kya nazar aaya (saal, mahina, din).
- **`g` flag** ka matlab "stencil ko poori line par sarkao aur **har** mail par nishaan lagao", sirf pehle par nahi.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Your first patterns: test, match, replace">

<Tr>
<En>
Write a pattern between slashes. `pattern.test(text)` answers yes/no. `text.match(pattern)` returns the first match (or, with the **`g`** flag, all matches). `text.replace(pattern, with)` changes matches. The **`i`** flag ignores case.
</En>
<Ur>
Pattern slashes ke darmiyan likhein. `pattern.test(text)` haan/nahi me jawab deta hai. `text.match(pattern)` pehla mail deta hai (ya **`g`** flag ke saath tamam mail). `text.replace(pattern, with)` mail badalta hai. **`i`** flag case nazarandaz karta hai.
</Ur>
</Tr>

```javascript
const text = "Order 1042 shipped. Order 77 pending.";

console.log(/Order/.test(text), /order/.test(text), /order/i.test(text));

const first = text.match(/\d+/);
console.log(first[0], "at index", first.index);

console.log(text.match(/\d+/g));
console.log(text.replace(/\d+/g, "#"));
console.log(text.replace(/\d+/, "#"));
```

```text output
true false true
1042 at index 6
[ '1042', '77' ]
Order # shipped. Order # pending.
Order # shipped. Order 77 pending.
```

<Happened>
<Tr>
<En>

- `/order/` failed because of the capital O; `/order/i` matched.
- `\d+` means "one or more digits". Without `g`, `match` gives the first match plus its position (`index`).
- With `g`, `match` returns **every** match as a plain array of strings.
- `replace` with `g` changed every number; without `g` only the first.

</En>
<Ur>

- `/order/` bare O ki wajah se fail hua; `/order/i` mil gaya.
- `\d+` matlab "ek ya zyada hindse". `g` ke baghair `match` pehla mail aur us ki jagah (`index`) deta hai.
- `g` ke saath `match` **har** mail strings ki saadi array ki shakal me deta hai.
- `g` ke saath `replace` ne har number badla; `g` ke baghair sirf pehla.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Character classes: which characters fit">

<Tr>
<En>
`.` matches any one character. `[aeiou]` matches one of the listed characters; `[a-z]` a range; `[^…]` anything **except** those. Shortcuts: `\d` digit, `\w` word character (letter, digit, underscore), `\s` whitespace; capital versions (`\D`, `\W`, `\S`) mean the opposite.
</En>
<Ur>
`.` koi bhi ek character milata hai. `[aeiou]` list ke characters me se ek milata hai; `[a-z]` ek range; `[^…]` un ke **siwa** kuch bhi. Shortcuts: `\d` hindsa, `\w` lafz ka character (harf, hindsa, underscore), `\s` whitespace; bare versions (`\D`, `\W`, `\S`) ulta matlab dete hain.
</Ur>
</Tr>

```javascript
const words = ["cat", "cut", "c4t", "ct", "coat"];

for (const w of words) {
  console.log(w.padEnd(5), /^c.t$/.test(w), /^c[aeiou]t$/.test(w), /^c\wt$/.test(w), /^co?a?t$/.test(w));
}

console.log("Call 555-0142 or 555-0199".match(/\d{3}-\d{4}/g));
console.log("a1 b2 c3".replace(/\D/g, ""), "a1 b2 c3".replace(/\s/g, "_"));
```

```text output
cat   true true true true
cut   true true true false
c4t   true false true false
ct    false false false true
coat  false false false true
[ '555-0142', '555-0199' ]
123 a1_b2_c3
```

<Happened>
<Tr>
<En>

- `^c.t$`: c, **any one** character, t. "c4t" fits; "ct" doesn't (nothing in the middle); "coat" doesn't (two in the middle).
- `^c[aeiou]t$`: only a vowel in the middle, so "c4t" fails.
- `\w` accepts letters **and digits**, so "c4t" passes.
- `^co?a?t$`: `?` makes the character before it optional, so "ct" and "coat" match, but "cat" too (o skipped).
- `\D` (not a digit) with `g` removed everything except digits. Inside `[ ]`, most special characters lose their meaning: `[.]` is a literal dot.

</En>
<Ur>

- `^c.t$`: c, **koi bhi ek** character, t. "c4t" fit hai; "ct" nahi (beech me kuch nahi); "coat" nahi (beech me do).
- `^c[aeiou]t$`: beech me sirf vowel, isliye "c4t" fail.
- `\w` huroof **aur hindse** dono qabool karta hai, isliye "c4t" paas.
- `^co?a?t$`: `?` apne se pehle wale character ko ikhtiyari banata hai, isliye "ct" aur "coat" milte hain, aur "cat" bhi (o chhoot gaya).
- `g` ke saath `\D` (hindsa nahi) ne hindson ke siwa sab hata diya. `[ ]` ke andar zyada tar khaas characters apna matlab kho dete hain: `[.]` asli dot hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Quantifiers and anchors">

<Tr>
<En>
Quantifiers say **how many**: `*` (0 or more), `+` (1 or more), `?` (0 or 1), `{5}` (exactly 5), `{2,4}` (2 to 4). Anchors say **where**: `^` start, `$` end. For validation, always anchor both ends, or "contains five digits" will pass for "abc12345xyz".
</En>
<Ur>
Quantifiers batate hain **kitne**: `*` (0 ya zyada), `+` (1 ya zyada), `?` (0 ya 1), `{5}` (bilkul 5), `{2,4}` (2 se 4). Anchors batate hain **kahan**: `^` shuru, `$` aakhir. Validation ke liye hamesha dono kinare band karein, warna "paanch hindse shamil hain" "abc12345xyz" ke liye paas ho jayega.
</Ur>
</Tr>

```javascript
const zips = ["80202", "8020", "802021", "80202-1234", "ABCDE"];
for (const z of zips) {
  console.log(z.padEnd(11), /^\d{5}$/.test(z), /^\d{5}(-\d{4})?$/.test(z), /\d{5}/.test(z));
}

const html = "<b>x</b><b>y</b>";
console.log(html.match(/<b>.*<\/b>/)[0]);
console.log(html.match(/<b>.*?<\/b>/)[0]);
```

```text output
80202       true true true
8020        false false false
802021      false false true
80202-1234  false true true
ABCDE       false false false
<b>x</b><b>y</b>
<b>x</b>
```

<Happened>
<Tr>
<En>

- `^\d{5}$` accepted only exactly five digits.
- `^\d{5}(-\d{4})?$` also accepted the ZIP+4 form: the group `(-\d{4})` is made optional by `?`.
- The **unanchored** `/\d{5}/` accepted "802021": it only checks that five digits appear **somewhere**. That's the most common validation bug.
- `.*` is **greedy**: it grabbed as much as possible, from the first `<b>` to the **last** `</b>`. `.*?` is **lazy**: it stopped at the first `</b>`. (`\/` escapes the slash inside a pattern.)

</En>
<Ur>

- `^\d{5}$` ne sirf bilkul paanch hindse qabool kiye.
- `^\d{5}(-\d{4})?$` ne ZIP+4 shakal bhi qabool ki: group `(-\d{4})` `?` se ikhtiyari bana.
- **Baghair anchor** wale `/\d{5}/` ne "802021" qabool kiya: ye sirf check karta hai ke paanch hindse **kahin** hain. Ye sab se aam validation bug hai.
- `.*` **greedy** hai: is ne jitna ho saka liya, pehle `<b>` se **aakhri** `</b>` tak. `.*?` **lazy** hai: pehle `</b>` par ruk gaya. (`\/` pattern ke andar slash ko escape karta hai.)

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Groups: capturing parts of a match">

<Tr>
<En>
Brackets `( )` group part of a pattern and **capture** what it matched: `match[1]`, `match[2]`… **Named groups** `(?<year>…)` are clearer: read them from `match.groups`. In `replace`, use `$1` or `$<name>` to put captured text into the result.
</En>
<Ur>
Brackets `( )` pattern ke hisse ko group karte hain aur jo milaya use **capture** karte hain: `match[1]`, `match[2]`… **Naam wale groups** `(?<year>…)` zyada wazeh hain: inhe `match.groups` se parhein. `replace` me pakra hua text nateeje me daalne ke liye `$1` ya `$<name>` lein.
</Ur>
</Tr>

```javascript
const date = "2026-11-12";

const m = date.match(/^(\d{4})-(\d{2})-(\d{2})$/);
console.log(m[0], m[1], m[2], m[3]);

const named = date.match(/^(?<year>\d{4})-(?<month>\d{2})-(?<day>\d{2})$/);
const { year, month, day } = named.groups;
console.log(year, month, day);

console.log(date.replace(/(\d{4})-(\d{2})-(\d{2})/, "$2/$3/$1"));
console.log("Alex Kim".replace(/(?<first>\w+) (?<last>\w+)/, "$<last>, $<first>"));
console.log("cat or dog?".match(/cat|dog/g), "gray grey".match(/gr(?:a|e)y/g));
```

```text output
2026-11-12 2026 11 12
2026 11 12
11/12/2026
Kim, Alex
[ 'cat', 'dog' ] [ 'gray', 'grey' ]
```

<Happened>
<Tr>
<En>

- `m[0]` is the whole match; `m[1]`–`m[3]` are the three groups, in order of their opening brackets.
- Named groups let you destructure `{ year, month, day }` instead of remembering positions.
- `"$2/$3/$1"` rearranged the parts into US date order. `$<last>, $<first>` did the same with names.
- `|` means "or". `(?:…)` groups **without capturing**, useful when you only need the grouping for `|` or a quantifier.

</En>
<Ur>

- `m[0]` poora mail hai; `m[1]`–`m[3]` teen groups hain, khulne wale brackets ki tarteeb se.
- Naam wale groups jaghen yaad rakhne ke bajaye `{ year, month, day }` destructure karne dete hain.
- `"$2/$3/$1"` ne hisson ko US date ki tarteeb me rakh diya. `$<last>, $<first>` ne naamon ke saath yahi kiya.
- `|` matlab "ya". `(?:…)` **baghair capture** ke group karta hai, kaam ka jab grouping sirf `|` ya quantifier ke liye chahiye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="All matches with groups: matchAll and the m flag">

<Tr>
<En>
`match` with `g` gives only the matched strings, not their groups. **`matchAll`** gives every match **with** its groups, ready for a `for…of` loop. The **`m`** (multi-line) flag makes `^` and `$` match at the start and end of **each line**.
</En>
<Ur>
`g` ke saath `match` sirf mili hui strings deta hai, un ke groups nahi. **`matchAll`** har mail us ke groups **ke saath** deta hai, `for…of` loop ke liye tayyar. **`m`** (multi-line) flag `^` aur `$` ko **har line** ke shuru aur aakhir par milata hai.
</Ur>
</Tr>

```javascript
const log = "ERROR 12:01 disk full\nINFO 12:02 retry\nERROR 12:05 disk full again";

for (const match of log.matchAll(/^ERROR (\d{2}:\d{2}) (.+)$/gm)) {
  console.log(match[1], "→", match[2]);
}

console.log(log.match(/^ERROR/g), log.match(/^ERROR/gm));
```

```text output
12:01 → disk full
12:05 → disk full again
[ 'ERROR' ] [ 'ERROR', 'ERROR' ]
```

<Happened>
<Tr>
<En>

- `matchAll` returned both ERROR lines with their time and message groups. (It requires the `g` flag.)
- Without `m`, `^` only means "start of the whole text", so only the first ERROR matched. With `m`, every line start counts.
- `.+` stopped at the end of each line because `.` doesn't match line breaks (add the `s` flag if you need it to).

</En>
<Ur>

- `matchAll` ne dono ERROR lines un ke waqt aur paighaam ke groups ke saath din. (Ise `g` flag chahiye.)
- `m` ke baghair `^` ka matlab sirf "poore text ka shuru" hai, isliye sirf pehla ERROR mila. `m` ke saath har line ka shuru ginta hai.
- `.+` har line ke aakhir par ruka kyun ke `.` line breaks nahi milata (agar chahiye to `s` flag jorein).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Cleaning text with replace and split">

<Tr>
<En>
Regex shines at cleaning. With the `g` flag, `replace` can remove or collapse **every** unwanted character at once. `split` also accepts a regex, so you can split on several different separators.
</En>
<Ur>
Regex saaf karne me chamakta hai. `g` flag ke saath `replace` **har** na-pasandeeda character ek saath hata ya sikor sakta hai. `split` bhi regex qabool karta hai, isliye aap kai mukhtalif separators par split kar sakte hain.
</Ur>
</Tr>

```javascript
function slugify(title) {
  return title
    .toLowerCase()
    .normalize("NFD")
    .replace(/[̀-ͯ]/g, "")
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "");
}

console.log(slugify("  Summer Sale: 50% Off!  "), slugify("Café & Crème brûlée"), slugify("---Hello---World---"));
console.log("a, b ,c;d  e".split(/\s*[,;]\s*|\s+/));
console.log("  too   many    spaces ".trim().replace(/\s+/g, " "));
console.log("Price: $1,234.50".replace(/[^\d.]/g, ""));
```

```text output

[ 'a', 'b', 'c', 'd', 'e' ]
too many spaces
1234.50
```

<Happened>
<Tr>
<En>

- `slugify` finished the job from the Strings lesson:
  1. `normalize("NFD")` splits accented letters into letter + accent mark, and `/[̀-ͯ]/g` removes the accent marks ("é" → "e").
  2. `/[^a-z0-9]+/g` turns every run of other characters (spaces, `:`, `%`, `!`, `&`) into **one** dash.
  3. `/^-+|-+$/g` trims dashes from both ends.
- `split` used one pattern for "comma or semicolon with optional spaces, or just spaces".
- `/\s+/g` → `" "` collapsed repeated spaces.
- `[^\d.]` kept only digits and the dot. (For real money input, parse more carefully: commas mean decimals in many countries.)

</En>
<Ur>

- `slugify` ne Strings lesson ka kaam mukammal kiya:
  1. `normalize("NFD")` accent wale huroof ko harf + accent ke nishaan me torta hai, aur `/[̀-ͯ]/g` accent ke nishaan hata deta hai ("é" → "e").
  2. `/[^a-z0-9]+/g` doosre characters ke har silsile (spaces, `:`, `%`, `!`, `&`) ko **ek** dash me badalta hai.
  3. `/^-+|-+$/g` dono kinaron se dashes kaat-ta hai.
- `split` ne "comma ya semicolon ikhtiyari spaces ke saath, ya sirf spaces" ke liye ek pattern istemal kiya.
- `/\s+/g` → `" "` ne dohri spaces sikor din.
- `[^\d.]` ne sirf hindse aur dot rakhe. (Asli paison ke input ke liye zyada ehtiyat se parse karein: bohot se mulkon me comma ka matlab decimal hai.)

</Ur>

<Step title="Simple validation and lookaheads">

<Tr>
<En>
For forms, a **simple, anchored** pattern catches typos; the real check (does this email exist? is the code valid?) happens on the server. **Lookaheads** `(?=…)` check that something appears **somewhere ahead** without consuming characters, which is handy for "must contain a digit" rules.
</En>
<Ur>
Forms ke liye **saada, anchored** pattern typos pakar leta hai; asli check (kya ye email maujood hai? kya code sahi hai?) server par hota hai. **Lookaheads** `(?=…)` check karte hain ke koi cheez **aage kahin** hai, characters istemal kiye baghair, jo "hindsa zaroor ho" jaise qawaid ke liye kaam ka hai.
</Ur>
</Tr>

```javascript
const emailLike = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
for (const e of ["alex@example.com", "alex@example", "a b@example.com", "@example.com", "alex@mail.example.co"]) {
  console.log(e.padEnd(22), emailLike.test(e));
}

const strong = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).{10,}$/;
for (const p of ["short1A", "longenough1", "LongEnough42"]) {
  console.log(p, strong.test(p));
}
```

```text output

alex@example           false
a b@example.com        false
@example.com           false
alex@mail.example.co   true
short1A false
longenough1 false
LongEnough42 true
```

<Happened>
<Tr>
<En>

- `emailLike` reads: some non-space, non-@ characters, then `@`, then more, then a dot, then more. It catches common typos without trying to implement the full email standard (which is enormous). To be sure an email works, send a confirmation link.
- The password pattern has three lookaheads, each checking "somewhere ahead there's a lowercase letter / an uppercase letter / a digit", then `.{10,}` requires at least 10 characters.
- For user-facing rules, separate checks (like the Control Flow challenge) give **better error messages** than one big regex that just says "invalid".

</En>
<Ur>

- `emailLike` aise parha jata hai: kuch characters jo space ya @ nahi, phir `@`, phir aur, phir dot, phir aur. Ye poora email standard (jo bohot bara hai) banaye baghair aam typos pakar leta hai. Email chalti hai ye yaqeeni banane ke liye confirmation link bhejein.
- Password pattern me teen lookaheads hain, har ek check karta hai "aage kahin chhota harf / bara harf / hindsa hai", phir `.{10,}` kam az kam 10 characters maangta hai.
- User ke saamne ke qawaid ke liye alag checks (jaise Control Flow challenge) ek bare regex se, jo bas "invalid" kehta hai, **behtar error paighaam** dete hain.

</Ur>
</Tr>
</Happened>

<Step title="Building patterns from variables (safely)">

<Tr>
<En>
`new RegExp(text, flags)` builds a pattern from a string, for example a search word typed by a user. But characters like `.`, `?`, `(` and `+` are **special**; you must **escape** them first, or the user's text changes the meaning of your pattern (or crashes it). Also beware: the `g` flag makes `test` remember its position between calls.
</En>
<Ur>
`new RegExp(text, flags)` string se pattern banata hai, maslan user ka likha search lafz. Magar `.`, `?`, `(` aur `+` jaise characters **khaas** hain; inhe pehle **escape** karna zaroori hai, warna user ka text aap ke pattern ka matlab badal deta hai (ya crash kar deta hai). Ye bhi dhyan rahe: `g` flag `test` ko calls ke darmiyan apni jagah yaad rakhne deta hai.
</Ur>
</Tr>

```javascript
const escapeRegExp = (s) => s.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");

const search = "1+1=2 (really?)";
console.log(escapeRegExp(search));
console.log(new RegExp(escapeRegExp("(really?)")).test(search));

try {
  new RegExp("(really?");
} catch (error) {
  console.log(error.name + ":", error.message);
}

const word = "sale";
const wholeWord = new RegExp(`\\b${escapeRegExp(word)}\\b`, "i");
console.log(wholeWord.test("Big SALE today"), wholeWord.test("wholesale"));

const re = /cat/g;
console.log(re.test("cat cat"), re.lastIndex, re.test("cat cat"), re.lastIndex, re.test("cat cat"), re.lastIndex);
```

```text output
1\+1=2 \(really\?\)
true
SyntaxError: Invalid regular expression: /(really?/: Unterminated group
true false
true 3 true 7 false 0
```

<Happened>
<Tr>
<En>

- `escapeRegExp` puts a backslash before every special character (`$&` in the replacement means "the matched character").
- Unescaped user input like `"(really?"` is an **invalid pattern** and throws; worse inputs can make your regex match everything or run very slowly.
- In a template string, `\\b` is needed to produce `\b` (word boundary). `\bsale\b` matched "SALE" but not "whole**sale**".
- With `g`, `test` started each search at `lastIndex`: true, true, then **false** (no third "cat"), then reset to 0. Reusing a global regex in `test` or `exec` across different strings gives alternating results. Don't use `g` with `test`.

</En>
<Ur>

- `escapeRegExp` har khaas character se pehle backslash laga deta hai (replacement me `$&` matlab "mila hua character").
- Baghair escape ka user input jaise `"(really?"` **ghalat pattern** hai aur error phenkta hai; is se bura input aap ke regex ko sab kuch milane wala ya bohot sust bana sakta hai.
- Template string me `\b` (lafz ki hadd) banane ke liye `\\b` chahiye. `\bsale\b` ne "SALE" milaya magar "whole**sale**" nahi.
- `g` ke saath `test` ne har talaash `lastIndex` se shuru ki: true, true, phir **false** (teesra "cat" nahi), phir 0 par reset. Global regex ko `test` ya `exec` me mukhtalif strings par dobara istemal karna badalte nataij deta hai. `test` ke saath `g` na lagayen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The slow-regex trap (ReDoS)">

<Tr>
<En>
Some patterns, especially **nested quantifiers** like `(a+)+`, can try an astronomical number of ways to match when the input **almost** matches. A short string can freeze a browser tab or a server thread. This is called **ReDoS** (regular expression denial of service).
</En>
<Ur>
Kuch patterns, khaas taur par **nested quantifiers** jaise `(a+)+`, jab input **taqreeban** mil raha ho to milane ke behad zyada tareeqe aazmate hain. Chhoti si string browser tab ya server thread jama sakti hai. Ise **ReDoS** (regular expression denial of service) kehte hain.
</Ur>
</Tr>

```javascript
const input = "a".repeat(25) + "!";

let start = performance.now();
/^(a+)+$/.test(input);
const slow = performance.now() - start;

start = performance.now();
/^a+$/.test(input);
const fast = performance.now() - start;

console.log("nested quantifier slower by more than 100x:", slow > fast * 100, "| took over 50ms:", slow > 50);
```

```text output
nested quantifier slower by more than 100x: true | took over 50ms: true
```

<Happened>
<Tr>
<En>

- Both patterns mean the same thing ("only a's"), and both fail on the final "!". But `(a+)+` tried every way of splitting 25 a's into groups before giving up, while `a+` failed almost instantly.
- Each extra "a" roughly **doubles** the time. A few more characters turns milliseconds into minutes.
- Avoid nested quantifiers (`(x+)+`, `(x*)*`, `(\w+\s?)*`), limit input length before matching, and for user-supplied patterns use a safe engine (like RE2) or don't allow them at all.

</En>
<Ur>

- Dono patterns ka ek hi matlab hai ("sirf a"), aur dono aakhri "!" par fail hote hain. Magar `(a+)+` ne haar maanne se pehle 25 a ko groups me baantne ka har tareeqa aazmaya, jabke `a+` taqreeban foran fail hua.
- Har izafi "a" waqt ko taqreeban **dugna** karta hai. Chand aur characters milliseconds ko minton me badal dete hain.
- Nested quantifiers (`(x+)+`, `(x*)*`, `(\w+\s?)*`) se bachein, milane se pehle input ki length mehdood karein, aur users ke diye patterns ke liye mehfooz engine (jaise RE2) lein ya unhe ijazat hi na dein.

</Ur>
</Tr>
</Happened>

</Step>

<Takeaways>
<Tr>
<En>

- Patterns go between slashes: `/…/flags`. Use them with `test`, `match`, `matchAll`, `replace`, `split`.

<DeepDive title="More regex features">

**More flags.** `s` (dotAll) lets `.` match newlines; `u` enables full Unicode (needed for `\p{…}` and emoji); `v` is a newer, stricter Unicode mode with set operations; `y` (sticky) matches only at `lastIndex`; `d` adds start/end indices for groups.

**Unicode property escapes.** With `u`: `\p{L}` any letter in any language, `\p{Lu}` uppercase letters, `\p{N}` numbers, `\p{Emoji}`. A Unicode-aware slug might use `/[^\p{L}\p{N}]+/gu`.

**Lookarounds.** `(?=…)` followed by, `(?!…)` not followed by, `(?<=…)` preceded by, `(?<!…)` not preceded by. Example: `/(?<=\$)\d+/` finds numbers after a dollar sign without including the `$`.

**Backreferences.** `\1` or `\k<name>` match the **same text** a group matched earlier: `/(\w)\1/` finds doubled letters.

**Replacement functions.** `text.replace(/\d+/g, (n) => n * 2)` computes each replacement; it receives the match and its groups.

**Other methods.** `regex.exec(text)` (like `match`, used in loops with `g`), `String.prototype.search` (index of first match), `RegExp.prototype.source` and `.flags`.

**Readability.** Build complex patterns from named pieces with template strings, keep a test list next to them, and prefer several simple steps over one clever pattern.

</DeepDive>

<DeepDive title="Real world: the regex that took a site down">

A large content-delivery company pushed a new firewall rule containing a regular expression meant to detect attacks in HTTP requests. Part of it had the shape `.*(?:.*=.*)`: several greedy `.*`s that could each match the same characters in many different ways.

For most requests it was fine. But for certain inputs, the regex engine had to try a huge number of combinations before deciding there was no match. CPU usage on every server running the rule shot to 100%, and websites behind the service started returning errors worldwide for about half an hour until the rule was rolled back.

What the post-incident fixes looked like:

1. **Switch to a regex engine with guaranteed linear time** (like RE2, which doesn't allow backtracking features).
2. **Performance-test** new patterns against worst-case inputs, not just normal traffic.
3. **Roll out rule changes gradually** instead of everywhere at once, with automatic rollback when CPU spikes.

Lesson: a regex is code. A pattern with ambiguous nested repetition can be a **denial-of-service bug**, and the input that triggers it can be very short.

</DeepDive>

<DeepDive title="Security lens">

- **ReDoS**: avoid nested quantifiers and overlapping alternatives; limit input length; time out or use RE2 for patterns on untrusted input. Lint tools (eslint-plugin-regexp, safe-regex) flag risky patterns.
- **Escape user input** before `new RegExp`, or use `includes` for plain-text search.
- **Anchor allow-list checks.** `/https:\/\/example\.com/.test(url)` passes for `https://evil.com/?https://example.com`. Parse URLs with `new URL()` and compare `url.hostname` exactly.
- **Don't sanitize HTML with regex.** Attackers have endless ways around patterns like `/<script.*?>/`. Use a real sanitizer (DOMPurify) or escape text.
- **Regex validation is a convenience, not security**: always validate on the server and use parameterised queries, escaping and proper authorisation.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between greedy and lazy quantifiers?">
Greedy quantifiers such as asterisk and plus match as many characters as possible and then backtrack if needed. Lazy versions, written with a trailing question mark, match as few characters as possible, so they stop at the first point where the rest of the pattern can match.
</QA>

<QA q="What do the g, i and m flags do?">
g finds all matches instead of only the first, i makes matching case-insensitive, and m makes the caret and dollar anchors match at the start and end of each line instead of the whole string.
</QA>

<QA q="How do capturing groups and named groups work in JavaScript?">
Parentheses capture the text they match, available as indexed entries in the match array and as $1, $2 in replacement strings. Named groups put a question mark and a name in angle brackets right after the opening parenthesis; their values appear in match.groups and can be referenced by name in replacement strings.
</QA>

<QA q="Why can a global regex give different results when test is called repeatedly?">
Regexes with the g or y flag keep state in lastIndex. Each test or exec call starts searching from lastIndex and updates it, so repeated calls on the same or different strings can alternate between true and false until lastIndex resets.
</QA>

<QA q="What is ReDoS and how do you prevent it?">
Regular expression denial of service occurs when a backtracking engine takes exponential time on crafted input, typically due to nested or overlapping quantifiers. Prevent it by avoiding such patterns, limiting input size, testing worst cases, and using linear-time engines like RE2 for untrusted input.
</QA>

</DeepDive>
