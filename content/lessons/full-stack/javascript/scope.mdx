<BigIdea>
<Tr>
<En>
**Scope** is the answer to one question: **"from this line of code, which variables can I see?"** A variable made inside `{ }` or inside a function can only be seen **there and deeper inside**; code outside can't see it. Code **inside** can always look **outward**, never the other way. When you use a name, JavaScript searches the current scope, then the one around it, then the next, up to the **global** scope: this is the **scope chain**. A **closure** is what you get when a function **remembers** the variables that were around it when it was created, and keeps using them **even after** the outer function has finished. Closures are how JavaScript does private data, counters, event handlers and React hooks.
</En>
<Ur>
**Scope** ek sawal ka jawab hai: **"code ki is line se main kaun se variables dekh sakta hoon?"** `{ }` ke andar ya function ke andar bana variable sirf **wahan aur us ke andar** dekha ja sakta hai; bahar ka code use nahi dekh sakta. **Andar** ka code hamesha **bahar** dekh sakta hai, ulta kabhi nahi. Jab aap koi naam istemal karte hain to JavaScript maujooda scope me dhoondta hai, phir us ke gird wale me, phir agle me, **global** scope tak: ise **scope chain** kehte hain. **Closure** tab banta hai jab function un variables ko **yaad rakhta** hai jo us ke banne ke waqt us ke gird the, aur bahar wala function khatam hone ke **baad bhi** unhe istemal karta rehta hai. JavaScript me private data, counters, event handlers aur React hooks sab closures se bante hain.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

Three kinds of scope, from widest to narrowest:

| Scope | Where it is | Who can see its variables |
| --- | --- | --- |
| **Global** | Outside every function and block | All code in the file |
| **Function** | Inside a function's `{ }` | Only code inside that function |
| **Block** | Inside any `{ }`: `if`, `for`, or bare braces | Only code inside that block (`let` and `const`) |

A **closure** = a function + the variables it remembers from where it was written.

</En>
<Ur>

Scope ki teen qismen, sab se chauri se sab se tang tak:

| Scope | Kahan hai | Is ke variables kaun dekh sakta hai |
| --- | --- | --- |
| **Global** | Har function aur block ke bahar | File ka saara code |
| **Function** | Function ke `{ }` ke andar | Sirf us function ke andar ka code |
| **Block** | Kisi bhi `{ }` ke andar: `if`, `for`, ya khaali braces | Sirf us block ke andar ka code (`let` aur `const`) |

**Closure** = function + wo variables jo use apne likhe jane ki jagah se yaad hain.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **No name clashes.** Two functions can both have a variable called `total` without disturbing each other.
- **Safety.** Code can't accidentally change a variable it can't see.
- **Memory.** Closures let a function keep private information between calls, without global variables.
- **Understanding errors.** `ReferenceError: x is not defined` is almost always a scope problem.
- **React.** `useState`, `useEffect` and every event handler rely on closures. "Stale state" bugs are closure bugs.

</En>
<Ur>

- **Naamon ka takrao nahi.** Do functions dono `total` naam ka variable rakh sakte hain, ek doosre ko chhere baghair.
- **Hifazat.** Code ghalti se wo variable nahi badal sakta jo use nazar hi nahi aata.
- **Yaad dasht.** Closures function ko calls ke darmiyan apni private maloomat rakhne dete hain, global variables ke baghair.
- **Errors samajhna.** `ReferenceError: x is not defined` taqreeban hamesha scope ka masla hota hai.
- **React.** `useState`, `useEffect` aur har event handler closures par chalte hain. "Purani state" wale bugs closure ke bugs hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Scope applies to **every line you write**. You use closures, often without noticing, whenever:

- a function is used **later** than it was created (click handlers, timers, callbacks),
- a function **returns** another function,
- you want data that only certain functions can touch.

</En>
<Ur>

Scope **har us line** par lagta hai jo aap likhte hain. Closures aap, aksar ghaur kiye baghair, tab istemal karte hain jab:

- function apne banne ke **baad me** istemal ho (click handlers, timers, callbacks),
- function doosra function **return** kare,
- aap aisa data chahein jise sirf khaas functions chhu saken.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```js
function createCounter() {
  let count = 0;            // private: lives in this function's scope
  return () => {            // this inner function remembers count
    count = count + 1;
    return count;
  };
}

const next = createCounter();
next();   // 1
next();   // 2   - count was remembered
```

</En>
<Ur>

```js
function createCounter() {
  let count = 0;            // private: is function ke scope me rehta hai
  return () => {            // andar wala function count ko yaad rakhta hai
    count = count + 1;
    return count;
  };
}

const next = createCounter();
next();   // 1
next();   // 2   - count yaad raha
```

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

**Scope** is a **house with rooms**. Things in the **living room** (global scope) can be seen by everyone in the house. Each **bedroom** (a function) has its own things. Someone standing in a bedroom can see what's in that bedroom, and can also look out through the door into the living room. But someone in the living room **can't see into a closed bedroom**. A **cupboard inside the bedroom** (a block) works the same way, one level deeper.

When you look for something, you search **your own room first**, then the room outside, then the next one out. You never search inward, and you never search a neighbour's room.

A **closure** is a **backpack**. When a function is created, it packs a backpack with links to the variables around it. Wherever the function travels, even long after the room it was born in has been locked up, it still carries the backpack and can use what's inside.

</En>
<Ur>

**Scope** **kamron wala ghar** hai. **Living room** (global scope) ki cheezen ghar ka har fard dekh sakta hai. Har **bedroom** (function) ki apni cheezen hain. Bedroom me khara shakhs us bedroom ki cheezen dekh sakta hai, aur darwaze se bahar living room me bhi jhaank sakta hai. Magar living room me khara shakhs **band bedroom ke andar nahi dekh sakta**. **Bedroom ke andar ki almaari** (block) bhi isi tarah hai, ek darja aur andar.

Koi cheez dhoondte waqt aap **pehle apna kamra** dekhte hain, phir bahar wala kamra, phir us se bahar wala. Aap kabhi andar ki taraf nahi dhoondte, aur parosi ke kamre me bhi nahi.

**Closure** ek **backpack** hai. Function bante waqt apne gird ke variables ke links backpack me rakh leta hai. Function jahan bhi jaye, chahe us ke paidaish wala kamra kab ka band ho chuka ho, backpack us ke saath rehta hai aur wo andar ki cheezen istemal kar sakta hai.

</Ur>
</Tr>

<Walkthrough>

<Step title="A variable lives inside its { }">

<Tr>
<En>
A variable made with `let` or `const` exists only inside the nearest pair of curly braces. Outside them, it's as if it was never made. (We use `try`/`catch` so the error is shown instead of stopping the program.)
</En>
<Ur>
`let` ya `const` se bana variable sirf sab se qareebi curly braces ke andar maujood hota hai. Un ke bahar aisa hai jaise wo kabhi bana hi nahi. (`try`/`catch` isliye hai ke error dikh jaye aur program na ruke.)
</Ur>
</Tr>

```javascript
const isMember = true;

if (isMember) {
  const discount = 20;
  console.log("inside the block:", discount);
}

try {
  console.log(discount);
} catch (error) {
  console.log(error.name + ": " + error.message);
}
```

```text output
inside the block: 20
ReferenceError: discount is not defined
```

<Happened>
<Tr>
<En>

- `discount` was created inside the `if` block's `{ }`. Inside, it works.
- After the closing `}`, the block's scope is gone, and `discount` with it.
- Reading a name that isn't in any scope you can see gives a **ReferenceError**.
- If you need a value after the block, create the variable **before** the block and assign it inside.

</En>
<Ur>

- `discount` `if` block ke `{ }` ke andar bana. Andar ye chalta hai.
- Band hone wale `}` ke baad block ka scope khatam, aur us ke saath `discount` bhi.
- Aisa naam parhna jo aap ko nazar aane wale kisi scope me na ho, **ReferenceError** deta hai.
- Agar value block ke baad chahiye to variable block se **pehle** banayen aur andar us me value rakhein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Each function has its own private room">

<Tr>
<En>
Variables made inside a function, including its parameters, belong to that function. Two functions can use the same names and never interfere.
</En>
<Ur>
Function ke andar bane variables, us ke parameters samet, usi function ke hain. Do functions wahi naam istemal kar sakte hain aur kabhi ek doosre me dakhal nahi dete.
</Ur>
</Tr>

```javascript
function priceWithTax(price) {
  const total = price * 1.1;
  return total;
}

function priceWithDiscount(price) {
  const total = price - 5;
  return total;
}

console.log(priceWithTax(100));
console.log(priceWithDiscount(100));
console.log(typeof total);
```

```text output
110.00000000000001
95
undefined
```

<Happened>
<Tr>
<En>

- Each function has its own `price` and its own `total`. They are different boxes that happen to share a label, like two people in different houses both owning "the red cup".
- Outside the functions, `total` doesn't exist. (`typeof` on a missing name says `"undefined"` instead of throwing an error.)
- `110.00000000000001` is the decimal rounding you met in the Data Types lesson, not a scope problem.
- Every **call** also gets a fresh room: the `total` from one call is gone before the next call begins.

</En>
<Ur>

- Har function ka apna `price` aur apna `total` hai. Ye alag dabbe hain jin ka label bas ittefaq se ek hai, jaise do alag gharon ke do logon ke paas "laal cup" ho.
- Functions ke bahar `total` maujood hi nahi. (Ghayab naam par `typeof` error ke bajaye `"undefined"` kehta hai.)
- `110.00000000000001` decimals ki wahi rounding hai jo Data Types lesson me dekhi thi, scope ka masla nahi.
- Har **call** ko bhi naya kamra milta hai: ek call ka `total` agli call shuru hone se pehle khatam ho chuka hota hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Global scope: visible everywhere">

<Tr>
<En>
A variable made outside every function and block is **global**. Every function can read it, and, if it's a `let`, change it.
</En>
<Ur>
Har function aur block ke bahar bana variable **global** hai. Har function use parh sakta hai, aur agar wo `let` ho to badal bhi sakta hai.
</Ur>
</Tr>

```javascript
const storeName = "Fresh Mart";
let visitors = 0;

function welcome() {
  visitors = visitors + 1;
  return "Welcome to " + storeName + ", visitor " + visitors;
}

console.log(welcome());
console.log(welcome());
console.log(visitors);
```

```text output
Welcome to Fresh Mart, visitor 1
Welcome to Fresh Mart, visitor 2
2
```

<Happened>
<Tr>
<En>

- `welcome` has no variable called `storeName` or `visitors` of its own, so it used the global ones.
- It **changed** the global `visitors`. Any other function could change it too, which is why global `let` variables are risky: when the value is wrong, every function is a suspect.
- Use globals for a few true constants (`const storeName`). Keep changing data inside functions.

</En>
<Ur>

- `welcome` ke paas apna `storeName` ya `visitors` nahi, isliye us ne global wale istemal kiye.
- Us ne global `visitors` ko **badal** diya. Koi bhi doosra function use badal sakta hai, isi liye global `let` variables khatarnak hain: value ghalat ho to har function par shak jata hai.
- Globals sirf chand asli constants ke liye rakhein (`const storeName`). Badalne wala data functions ke andar rakhein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Inside can see outside, never the reverse">

<Tr>
<En>
When JavaScript meets a name, it looks in the current scope. If it's not there, it looks one level out, and keeps going outward until it finds the name or runs out of scopes. This outward path is the **scope chain**.
</En>
<Ur>
JavaScript ko jab koi naam milta hai to wo maujooda scope me dekhta hai. Wahan na ho to ek darja bahar dekhta hai, aur bahar ki taraf jata rehta hai jab tak naam mil na jaye ya scopes khatam na ho jayen. Bahar ki taraf ka ye raasta **scope chain** hai.
</Ur>
</Tr>

```javascript
const level = "global";

function outer() {
  const outerOnly = "outer";

  function inner() {
    const innerOnly = "inner";
    console.log(innerOnly, "+", outerOnly, "+", level);
  }

  inner();

  try {
    console.log(innerOnly);
  } catch (error) {
    console.log("outer cannot see it:", error.message);
  }
}

outer();
```

```text output
inner + outer + global
outer cannot see it: innerOnly is not defined
```

<Happened>
<Tr>
<En>

- Inside `inner`, all three names work: `innerOnly` is found right there, `outerOnly` one level out, `level` two levels out.
- `outer` tried to read `innerOnly` and failed. Looking **inward** is never allowed.
- The search stops at the **first** match, starting from the inside.

</En>
<Ur>

- `inner` ke andar teeno naam chalte hain: `innerOnly` wahin mil gaya, `outerOnly` ek darja bahar, `level` do darje bahar.
- `outer` ne `innerOnly` parhne ki koshish ki aur nakaam raha. **Andar** ki taraf dekhna kabhi mumkin nahi.
- Talaash andar se shuru ho kar **pehle** milne wale naam par ruk jati hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Shadowing: the nearest name wins">

<Tr>
<En>
If an inner scope makes a variable with the **same name** as an outer one, the inner one hides ("shadows") the outer one while you're inside. The outer variable is not changed.
</En>
<Ur>
Agar andar ka scope bahar wale ke **hum-naam** variable banaye to andar rehte hue andar wala bahar wale ko chhupa deta hai (ise "shadowing" kehte hain). Bahar wala variable badalta nahi.
</Ur>
</Tr>

```javascript
const price = 100;

function showSalePrice() {
  const price = 80;
  console.log("inside:", price);
}

showSalePrice();
console.log("outside:", price);
```

```text output
inside: 80
outside: 100
```

<Happened>
<Tr>
<En>

- Inside the function, the search for `price` stops at the first match: the inner one, `80`.
- The global `price` is still `100`. They are two separate boxes.
- Shadowing is legal but confusing. Prefer different names (`salePrice`).

</En>
<Ur>

- Function ke andar `price` ki talaash pehle milne wale par rukti hai: andar wala, `80`.
- Global `price` ab bhi `100` hai. Ye do alag dabbe hain.
- Shadowing jaiz hai magar uljhan paida karti hai. Alag naam behtar hain (`salePrice`).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Scope depends on where code is written">

<Tr>
<En>
A function looks for variables starting from the place where it was **written**, not the place where it is **called**. This rule is called **lexical scope**.
</En>
<Ur>
Function variables ki talaash wahan se shuru karta hai jahan wo **likha** gaya, wahan se nahi jahan wo **call** hua. Is qaide ko **lexical scope** kehte hain.
</Ur>
</Tr>

```javascript
const language = "English";

function showLanguage() {
  console.log(language);
}

function runElsewhere() {
  const language = "Spanish";
  showLanguage();
}

runElsewhere();
```

```text output
English
```

<Happened>
<Tr>
<En>

- `showLanguage` was **written** at the top level, so its outer scope is the global one, where `language` is `"English"`.
- It was **called** from inside `runElsewhere`, which has its own `language`. That doesn't matter. A function never looks into the room it was called from.
- This is why you can read code and know which variable a name refers to, just by looking at where things are written.

</En>
<Ur>

- `showLanguage` sab se upar ki satah par **likha** gaya, isliye us ka bahar wala scope global hai, jahan `language` `"English"` hai.
- Ye `runElsewhere` ke andar se **call** hua, jis ka apna `language` hai. Is se farq nahi parta. Function kabhi us kamre me nahi jhaankta jahan se use call kiya gaya.
- Isi liye aap code parh kar, sirf ye dekh kar ke cheezen kahan likhi hain, bata sakte hain ke naam kis variable ki taraf ishara karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Closure: a function that remembers">

<Tr>
<En>
Normally a function's variables disappear when the function finishes. But if an **inner function** still uses them and is still reachable, JavaScript keeps them alive. The inner function plus its remembered variables is a **closure**.
</En>
<Ur>
Aam taur par function ke variables function khatam hote hi ghayab ho jate hain. Magar agar koi **andar wala function** unhe ab bhi istemal karta ho aur us tak pohancha ja sakta ho, to JavaScript unhe zinda rakhta hai. Andar wala function aur us ke yaad rakhe hue variables mil kar **closure** hain.
</Ur>
</Tr>

```javascript
function createCounter() {
  let count = 0;

  return function () {
    count = count + 1;
    return count;
  };
}

const counter = createCounter();

console.log(counter());
console.log(counter());
console.log(counter());
console.log(typeof count);
```

```text output
1
2
3
undefined
```

<Happened>
<Tr>
<En>

- `createCounter()` ran once and **finished**. Normally `count` would be gone.
- But it returned an inner function that uses `count`. That function carries `count` in its backpack.
- Each call to `counter()` adds one to the **same** remembered `count`: 1, 2, 3.
- From outside, `count` doesn't exist (`typeof count` is `"undefined"`). The **only** way to reach it is through `counter()`. It's private.

</En>
<Ur>

- `createCounter()` ek dafa chala aur **khatam** ho gaya. Aam taur par `count` ghayab ho jata.
- Magar us ne andar wala function wapas kiya jo `count` istemal karta hai. Wo function `count` ko apne backpack me liye phirta hai.
- `counter()` ki har call **usi** yaad rakhe hue `count` me ek jorti hai: 1, 2, 3.
- Bahar se `count` maujood hi nahi (`typeof count` `"undefined"` hai). Us tak pohanchne ka **wahid** raasta `counter()` hai. Ye private hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Every call makes a fresh backpack">

<Tr>
<En>
Each time the outer function runs, it creates brand-new variables, and the inner function it returns remembers **those**. So two counters never share a count.
</En>
<Ur>
Bahar wala function jitni dafa chalta hai, bilkul naye variables banata hai, aur jo andar wala function wo wapas karta hai use **wahi** yaad rehte hain. Isliye do counters ka count kabhi mushtarak nahi hota.
</Ur>
</Tr>

```javascript
function createCounter() {
  let count = 0;
  return () => {
    count = count + 1;
    return count;
  };
}

const likes = createCounter();
const shares = createCounter();

console.log("likes:", likes(), likes(), likes());
console.log("shares:", shares());
console.log("likes again:", likes());
```

```text output
likes: 1 2 3
shares: 1
likes again: 4
```

<Happened>
<Tr>
<En>

- `likes` and `shares` came from two separate calls to `createCounter`, so each has its own `count`.
- Calling `shares()` didn't disturb `likes`: it continued from 3 to 4.
- This is a **factory**: one function that produces many independent things.

</En>
<Ur>

- `likes` aur `shares` `createCounter` ki do alag calls se bane, isliye har ek ka apna `count` hai.
- `shares()` call karne se `likes` par asar nahi hua: wo 3 se 4 par gaya.
- Ye **factory** hai: ek function jo kai azad cheezen banata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Closures keep data private">

<Tr>
<En>
Because outside code can't see into a function, a closure is a natural way to protect data. Here, the balance can only be changed through functions that check the rules.
</En>
<Ur>
Chunke bahar ka code function ke andar nahi dekh sakta, closure data ki hifazat ka qudrati tareeqa hai. Yahan balance sirf un functions ke zariye badal sakta hai jo qawaid check karte hain.
</Ur>
</Tr>

```javascript
function createWallet(startingBalance) {
  let balance = startingBalance;

  function deposit(amount) {
    if (amount <= 0) {
      return "Amount must be positive";
    }
    balance = balance + amount;
    return balance;
  }

  function spend(amount) {
    if (amount > balance) {
      return "Not enough money";
    }
    balance = balance - amount;
    return balance;
  }

  function getBalance() {
    return balance;
  }

  return { deposit, spend, getBalance };
}

const wallet = createWallet(50);
console.log(wallet.deposit(25));
console.log(wallet.spend(100));
console.log(wallet.spend(30));
console.log(wallet.balance);
console.log(wallet.getBalance());
```

```text output
75
Not enough money
45
undefined
45
```

<Happened>
<Tr>
<En>

- `createWallet` returns an object holding three functions. All three share the same remembered `balance`.
- `wallet.balance` is `undefined`: there is no such property. Nobody can write `wallet.balance = 1000000`.
- The only way to change the balance is through `deposit` and `spend`, which enforce the rules (no negative deposits, no overspending).
- This pattern, private data plus a few public functions, is called the **module pattern**.

</En>
<Ur>

- `createWallet` aisa object wapas karta hai jis me teen functions hain. Teeno ko wahi yaad rakha hua `balance` mushtarak hai.
- `wallet.balance` `undefined` hai: aisi koi property hai hi nahi. Koi `wallet.balance = 1000000` nahi likh sakta.
- Balance badalne ka wahid raasta `deposit` aur `spend` hain, jo qawaid lagu karte hain (manfi deposit nahi, had se zyada kharch nahi).
- Is namoone ko, yaani private data aur chand public functions, **module pattern** kehte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A closure holds a live link, not a copy">

<Tr>
<En>
A closure doesn't take a snapshot of the value. It keeps a link to the **variable itself**, so it always sees the latest value.
</En>
<Ur>
Closure value ki tasveer nahi kheenchta. Wo **khud variable** ka link rakhta hai, isliye use hamesha taza tareen value nazar aati hai.
</Ur>
</Tr>

```javascript
let userName = "Sara";

const greet = () => "Hello, " + userName;

console.log(greet());
userName = "Alex";
console.log(greet());
```

```text output
Hello, Sara
Hello, Alex
```

<Happened>
<Tr>
<En>

- `greet` was created while `userName` was `"Sara"`, but it didn't store `"Sara"`. It stored a link to the box `userName`.
- After the box was refilled with `"Alex"`, the next call read the new value.
- Remember this for the next step: a closure reads the variable **when it runs**, not when it was created.

</En>
<Ur>

- `greet` tab bana jab `userName` `"Sara"` tha, magar us ne `"Sara"` mehfooz nahi kiya. Us ne `userName` wale dabbe ka link rakha.
- Dabbe me `"Alex"` rakhne ke baad agli call ne nayi value parhi.
- Agle qadam ke liye yaad rakhein: closure variable ko **chalte waqt** parhta hai, bante waqt nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The classic loop trap: var vs let">

<Tr>
<En>
This is the most famous closure puzzle. Three timers are created in a loop. Each should print its own number. With the old `var`, they all print the same thing.
</En>
<Ur>
Ye closure ki sab se mashhoor paheli hai. Loop me teen timers bante hain. Har ek ko apna number print karna chahiye. Purane `var` ke saath sab ek hi cheez print karte hain.
</Ur>
</Tr>

```javascript
for (var i = 1; i <= 3; i++) {
  setTimeout(() => console.log("var loop:", i), 0);
}

for (let j = 1; j <= 3; j++) {
  setTimeout(() => console.log("let loop:", j), 0);
}
```

```text output
var loop: 4
var loop: 4
var loop: 4
let loop: 1
let loop: 2
let loop: 3
```

<Happened>
<Tr>
<En>

- `setTimeout` runs its function **later**, after both loops have completely finished.
- `var` ignores block scope, so there is only **one** `i` for the whole loop. All three functions link to that single box. By the time they run, the loop has ended and the box holds `4`.
- `let` creates a **new** `j` for every round of the loop. Each function links to its own box: 1, 2, 3.
- This is one of the main reasons `let` replaced `var`.

</En>
<Ur>

- `setTimeout` apna function **baad me** chalata hai, jab dono loops poori tarah khatam ho chuke hote hain.
- `var` block scope ko nahi maanta, isliye poore loop ke liye sirf **ek** `i` hai. Teeno functions usi ek dabbe se jure hain. Jab tak wo chalte hain loop khatam ho chuka hota hai aur dabbe me `4` hota hai.
- `let` loop ke har chakkar ke liye **naya** `j` banata hai. Har function apne dabbe se jura hai: 1, 2, 3.
- `var` ki jagah `let` aane ki bari wajahon me se ek yahi hai.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Creating the variable inside the block, using it outside">

```javascript
const cartTotal = 120;
if (cartTotal > 100) {
  const shipping = 0;
}
console.log(shipping);   // ReferenceError
```

</Bad>
<Good title="Create it outside, assign inside">

```javascript
const cartTotal = 120;
let shipping = 10;
if (cartTotal > 100) {
  shipping = 0;
}
console.log(shipping);
```

</Good>
</Compare>

<Compare>
<Bad title="Global variables that anything can change">

```javascript
let count = 0;
function increment() { count++; }
// any other code can also do: count = -999
```

<Tr>
<En>Every function in the program can read and overwrite it.</En>
<Ur>Program ka har function ise parh aur badal sakta hai.</Ur>
</Tr>

</Bad>
<Good title="Hide it in a closure">

```javascript
function createCounter() {
  let count = 0;
  return () => ++count;
}
const increment = createCounter();
```

</Good>
</Compare>

<Compare>
<Bad title="var in a loop with callbacks">

```javascript
for (var i = 0; i < 3; i++) {
  buttons[i].onclick = () => alert(i);   // always 3
}
```

</Bad>
<Good title="let gives each round its own variable">

```javascript
for (let i = 0; i < 3; i++) {
  buttons[i].onclick = () => alert(i);   // 0, 1, 2
}
```

</Good>
</Compare>

<Compare>
<Bad title="Accidental shadowing">

```javascript
let total = 0;
function addItem(price) {
  let total = price;   // a NEW total; the outer one never changes
}
```

</Bad>
<Good title="Assign to the outer one, or better, return a value">

```javascript
function addItem(total, price) {
  return total + price;
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Expecting a function to see variables from where it's called.** It only sees variables from where it's written.
- **Thinking a closure stores a copy.** It stores a link; it sees later changes.
- **Forgetting that every call to the outer function creates a new, separate closure.**
- **Leaving a `let`/`const` off** (`total = 5` with no keyword). In strict mode and modules this is an error; in old scripts it silently creates a global.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Umeed ke function wahan ke variables dekhega jahan se call hua.** Wo sirf wahan ke variables dekhta hai jahan likha gaya.
- **Sochna ke closure copy rakhta hai.** Wo link rakhta hai; baad ki tabdeeliyan use nazar aati hain.
- **Bhoolna ke bahar wale function ki har call naya, alag closure banati hai.**
- **`let`/`const` chhor dena** (`total = 5` kisi keyword ke baghair). Strict mode aur modules me ye error hai; purane scripts me ye chupke se global bana deta hai.

</Ur>
</Tr>

<DeepDive title="How scope and closures work under the hood">

**Environments.** Each time a function is called or a block is entered, the engine creates an **environment record**: a table of that scope's variables, plus a link to the **outer** environment. Name lookup walks these links: that's the scope chain.

**Functions carry their birthplace.** When a function is created, it stores a hidden link to the environment it was created in. When it's called later, its new environment's "outer" link points there, not to the caller. That single rule is both lexical scope and closures.

**Garbage collection.** An environment stays in memory as long as something can still reach it. A returned inner function reaches its outer environment, so the variables survive. When the last reference to the function is dropped, the environment can be freed. Long-lived closures that hold big objects (a listener that's never removed) are a common source of **memory leaks**.

**`var` and function scope.** `var` is scoped to the nearest **function**, not block, and is hoisted with the value `undefined`. Before `let`, the loop trap was fixed with an **IIFE** that created a new function scope per iteration: `(function (n) { setTimeout(() => console.log(n)); })(i);`.

**Temporal dead zone.** A `let`/`const` variable exists from the start of its block but can't be touched until its declaration line runs. Reading it earlier throws `ReferenceError: Cannot access 'x' before initialization`.

**Module scope.** In an ES module (any file using `import`/`export`), top-level variables are scoped to the **file**, not truly global. Only what you `export` is visible elsewhere. In a classic `<script>`, top-level `var` and function declarations become properties of `window`.

**Stale closures in React.** Each render of a component is a new function call with new variables. A callback created in an old render remembers the **old** render's state. An effect or timer that keeps using that old callback sees outdated values; that is what the dependency array of `useEffect` is for.

</DeepDive>

<DeepDive title="Real world: the counter that never moved">

A React developer writes a timer:

```javascript
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(seconds + 1);   // always 0 + 1
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return seconds;
}
```

The screen shows `1` and stays there forever. The interval callback was created during the **first** render, so its closure remembers that render's `seconds`, which is `0`. Every tick computes `0 + 1`.

Nothing is broken in React or JavaScript; the closure is doing exactly what closures do. The fix is to stop depending on the remembered value and ask React for the current one:

```javascript
setSeconds((current) => current + 1);
```

Once you can see the closure, a whole family of "my state is one step behind" bugs becomes easy to explain.

</DeepDive>

<DeepDive title="Security lens">

Scope is JavaScript's main tool for **limiting who can touch what**.

- **Globals are shared with every script on the page.** Analytics, ads, browser extensions and any injected script can read and overwrite `window` variables. Never keep tokens, user data or security flags in globals.
- **Closures give real privacy.** A variable inside a closure cannot be reached from outside, so sensitive values (a CSRF token, an API client with credentials) can be exposed only through functions that enforce rules.
- **But front-end privacy is not secrecy.** Anything in the browser can be inspected with DevTools by the user. Closures protect against other scripts' accidents, not against a determined user. Real secrets stay on the server.
- **Module-level state on servers is shared between users.** A `let` at the top of a server file lives as long as the process and is seen by every request. Storing "the current user" there leaks one user's data to another. Keep per-request data inside the request handler's scope.
- **Leaked closures leak data.** A long-lived listener or cache that closes over a request or user object keeps it in memory. Remove listeners and clear timers.
- **Accidental globals.** Assigning to an undeclared name creates a global in non-strict scripts. Use modules or `"use strict"` so it becomes an error.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is scope in JavaScript?">
Scope is the region of code in which a variable is accessible. JavaScript has global scope, function scope and block scope. let and const are block-scoped; var is function-scoped. In ES modules, top-level declarations are scoped to the module file.
</QA>

<QA q="What is lexical scope?">
It means a function's accessible variables are determined by where the function is written in the source code, not by where it is called. Each function keeps a reference to the environment in which it was defined, and name lookup proceeds outward through those environments.
</QA>

<QA q="What is a closure?">
A closure is a function bundled with references to the variables of its surrounding scope. It lets the function keep using those variables even after the outer function has returned. Closures are used for private state, function factories, callbacks, event handlers and memoisation.
</QA>

<QA q="Why does a var loop with setTimeout log the same value, and how do you fix it?">
var declares one variable for the whole function, so every callback closes over the same binding. The callbacks run after the loop has finished, when the variable holds its final value. Using let creates a new binding per iteration; older fixes wrap the body in an immediately invoked function or pass the value as an argument.
</QA>

<QA q="What is variable shadowing?">
Shadowing happens when a variable declared in an inner scope has the same name as one in an outer scope. Inside the inner scope the name refers to the inner variable, and the outer one is temporarily inaccessible but unchanged.
</QA>

<QA q="Can closures cause memory leaks?">
Yes. Variables captured by a closure cannot be garbage-collected while the closure is reachable. Long-lived closures such as event listeners, timers or cache entries that capture large objects keep them in memory. Removing listeners, clearing timers and not capturing more than necessary prevents this.
</QA>

</DeepDive>
