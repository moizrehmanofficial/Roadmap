<BigIdea>
<Tr>
<En>
**Mutating** means changing a value in place: pushing into an array, setting a property. **Immutability** means you **don't** change existing data; you make a **new** version with the change. Why care? Because in JavaScript, objects and arrays are shared by **reference**: two variables, a function argument, React state and a cache can all point to the **same** object. Change it through one, and every other place sees the change, often by surprise. To work safely you need to know which operations mutate (`sort`, `push`, `splice`, assigning properties) and which return new values (`toSorted`, `map`, `filter`, spread), and how deep a copy goes: **shallow** copies (spread, `Object.assign`, `slice`) copy only the top level; **deep** copies (`structuredClone`) copy everything. `Object.freeze` can lock an object, but only one level deep.
</En>
<Ur>
**Mutate** karne ka matlab hai value ko apni jagah badalna: array me push karna, property set karna. **Immutability** ka matlab hai ke aap maujooda data ko **nahi** badalte; tabdeeli ke saath **naya** version banate hain. Parwah kyun? Kyun ke JavaScript me objects aur arrays **reference** se share hote hain: do variables, function ka argument, React state aur cache sab **ek hi** object ki taraf ishara kar sakte hain. Ek ke zariye badlein, aur har doosri jagah tabdeeli dekhti hai, aksar hairani ke saath. Mehfooz kaam ke liye jaanna zaroori hai ke kaun se amal mutate karte hain (`sort`, `push`, `splice`, properties dena) aur kaun nayi values dete hain (`toSorted`, `map`, `filter`, spread), aur copy kitni gehri jati hai: **shallow** copies (spread, `Object.assign`, `slice`) sirf upar ka level copy karti hain; **deep** copies (`structuredClone`) sab kuch. `Object.freeze` object ko band kar sakta hai, magar sirf ek level gehra.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

```javascript
const scores = [72, 95, 61];
const sorted = scores.toSorted((a, b) => b - a);
const user = { name: "Alex", address: { city: "Denver" } };
const shallow = { ...user };
const deep = structuredClone(user);
console.log(scores, sorted);
console.log(shallow.address === user.address, deep.address === user.address);
```

```text output
true false
```

| --- | --- |
| `push`, `pop`, `shift`, `unshift` | `[...arr, x]`, `slice`, `concat` |
| `sort`, `reverse` | `toSorted`, `toReversed` |
| `splice` | `toSpliced`, `filter` |
| `arr[i] = x`, `fill` | `with(i, x)`, `map` |
| `obj.key = x`, `delete obj.key` | `{ ...obj, key: x }`, rest destructuring |

</En>

```javascript
const scores = [72, 95, 61];
```

| --- | --- |

| `splice` | `toSpliced`, `filter` |
| `arr[i] = x`, `fill` | `with(i, x)`, `map` |
| `obj.key = x`, `delete obj.key` | `{ ...obj, key: x }`, rest destructuring |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Shared-data bugs are hard to find**: the code that breaks is far away from the code that made the change.
- **React, Redux and many libraries depend on it**: they detect changes with `===`; mutated objects look "unchanged" and the screen doesn't update.
- **Undo, history and caching become easy** when old versions are never changed.
- **Functions that don't change their inputs** are easier to test, reuse and reason about.

</En>
<Ur>

- **Share kiye data ke bugs dhoondna mushkil hai**: tootne wala code tabdeeli karne wale code se bohot door hota hai.
- **React, Redux aur bohot si libraries is par chalti hain**: ye `===` se tabdeeli pehchanti hain; mutate kiye objects "be-badle" lagte hain aur screen update nahi hoti.
- **Undo, history aur caching aasaan ho jate hain** jab purane versions kabhi nahi badalte.
- **Inputs na badalne wale functions** test karna, dobara istemal karna aur samajhna aasaan hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Approach |
| --- | --- |
| React/Redux state, props, data from a cache | Never mutate; make new objects |
| Function arguments | Don't change them; return a new value |
| A local array you just created inside a function | Mutating it is fine (nobody else sees it) |
| Copy plain data completely | `structuredClone` |
| Copy one level to change top-level fields | spread / `slice` |
| Config or constants that must never change | `Object.freeze` (deep-freeze for nested) |

</En>
<Ur>

| Soorat-e-haal | Tareeqa |
| --- | --- |
| React/Redux state, props, cache se aaya data | Kabhi mutate nahi; naye objects banayen |
| Function arguments | Inhe na badlein; nayi value wapas karein |
| Function ke andar abhi banayi local array | Use mutate karna theek hai (koi aur nahi dekhta) |
| Saada data poori tarah copy karna | `structuredClone` |
| Upar ki fields badalne ke liye ek level copy | spread / `slice` |
| Config ya constants jo kabhi na badlein | `Object.freeze` (nested ke liye deep-freeze) |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Ask "who else holds a reference to this?" before changing an object.
2. Prefer non-mutating methods: `map`, `filter`, `toSorted`, spread.
3. When updating nested data, copy **every level on the path** to the change.
4. Use `structuredClone` when you truly need an independent copy.

</En>
<Ur>

1. Object badalne se pehle poochein "is ka reference aur kis ke paas hai?"
2. Mutate na karne wale methods ko tarjeeh dein: `map`, `filter`, `toSorted`, spread.
3. Nested data update karte waqt tabdeeli tak ke **raaste ka har level** copy karein.
4. Jab waqai alag copy chahiye to `structuredClone` lein.

</Ur>
</Tr>
</How>
</Glance>

## Picture it

<Tr>
<En>

Think of a **shared Google Doc** versus a **printed copy**.

- A variable holding an object is like holding a **link** to a shared document. Give the link to a teammate (`const b = a`, or pass it to a function) and you're both editing **the same** document. If they delete a paragraph, it's gone for you too.
- A **shallow copy** is printing the document's front page. The front page is yours, but it says "see attached spreadsheet" with **a link to the same spreadsheet**. Edit that, and everyone's spreadsheet changes.
- A **deep copy** is downloading the doc **and every attachment** into your own folder. Nothing you change affects anyone else.
- **Immutability** is a team rule: "never edit a shared doc; make a new version and share the new link". Everyone can see exactly what changed, and old versions stay intact for undo.

</En>
<Ur>

**Shared Google Doc** aur **printed copy** ka sochein.

- Object rakhne wala variable shared document ka **link** rakhne jaisa hai. Link teammate ko dein (`const b = a`, ya function ko bhej dein) aur aap dono **ek hi** document edit kar rahe hain. Agar wo paragraph mitaye to aap ke liye bhi chala gaya.
- **Shallow copy** document ka pehla safha print karna hai. Pehla safha aap ka hai, magar us par likha hai "saath laga spreadsheet dekhein" aur **usi spreadsheet ka link** hai. Use edit karein to sab ka spreadsheet badal jata hai.
- **Deep copy** doc **aur har attachment** ko apne folder me download karna hai. Aap jo bhi badlein kisi aur par asar nahi.
- **Immutability** team ka qaida hai: "shared doc kabhi edit na karo; naya version bana kar naya link share karo". Har koi bilkul dekh sakta hai kya badla, aur purane versions undo ke liye bache rehte hain.

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Mutate** | Change a value in place | `arr.push(4)` |
| **Immutable** | Never changed after creation | strings, frozen objects |
| **Reference** | A pointer to an object, copied on assignment | `const b = a` |
| **Value (primitive)** | Copied completely on assignment | numbers, strings |
| **Side effect** | A function changing something outside itself | sorting its argument |
| **Pure function** | Same input → same output, no side effects | `(a, b) => a + b` |
| **Shallow copy** | New top level, shared nested objects | `{ ...obj }` |
| **Deep copy** | Everything copied, nothing shared | `structuredClone(obj)` |
| **Freeze** | Lock an object's properties | `Object.freeze(obj)` |
| **Structural sharing** | New version reuses unchanged parts | immutable updates |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Mutate** | Value ko apni jagah badalna | `arr.push(4)` |
| **Immutable** | Banne ke baad kabhi na badle | strings, frozen objects |
| **Reference** | Object ki taraf ishara, assignment par copy hota hai | `const b = a` |
| **Value (primitive)** | Assignment par poori copy hoti hai | numbers, strings |
| **Side effect** | Function ka apne bahar kuch badalna | apna argument sort karna |
| **Pure function** | Wahi input → wahi output, koi side effect nahi | `(a, b) => a + b` |
| **Shallow copy** | Naya upar ka level, nested objects share | `{ ...obj }` |
| **Deep copy** | Sab copy, kuch share nahi | `structuredClone(obj)` |
| **Freeze** | Object ki properties band karna | `Object.freeze(obj)` |
| **Structural sharing** | Naya version be-badle hisse dobara istemal kare | immutable updates |

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Values are copied, objects are shared">

<Tr>
<En>
Assigning a **primitive** (number, string, boolean) copies the value. Assigning an **object or array** copies only the **reference**: both variables point to the same object.
</En>
<Ur>
**Primitive** (number, string, boolean) dena value copy karta hai. **Object ya array** dena sirf **reference** copy karta hai: dono variables ek hi object ki taraf ishara karte hain.
</Ur>
</Tr>

```javascript
let a = 5;
let b = a;
b = 10;
console.log(a, b);

const cart1 = { items: ["Mug"] };
const cart2 = cart1;
cart2.items.push("Lamp");
console.log(cart1.items, cart1 === cart2);
```

```text output
5 10
[ 'Mug', 'Lamp' ] true
```

<Happened>
<Tr>
<En>

- Changing `b` didn't affect `a`: numbers are copied.
- `cart2 = cart1` didn't create a second cart. There's **one** cart object with two names, so pushing through `cart2` changed what `cart1` sees.
- Passing an object to a function works the same way: the function receives a reference to **your** object.

</En>
<Ur>

- `b` badalne se `a` par asar nahi hua: numbers copy hote hain.
- `cart2 = cart1` ne doosra cart nahi banaya. **Ek** cart object hai jis ke do naam hain, isliye `cart2` ke zariye push karne se wo badla jo `cart1` dekhta hai.
- Function ko object bhejna bhi aise hi kaam karta hai: function ko **aap ke** object ka reference milta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Functions that secretly change their input">

<Tr>
<En>
Some built-in methods mutate the array they're called on. The famous one is **`sort`**. A function that sorts its argument changes the caller's data as a **side effect**. The newer **`toSorted`** returns a sorted copy instead.
</En>
<Ur>
Kuch bane banaye methods us array ko mutate karte hain jis par call hon. Mashhoor wala **`sort`** hai. Apna argument sort karne wala function **side effect** ke taur par call karne wale ka data badal deta hai. Naya **`toSorted`** is ke bajaye sorted copy deta hai.
</Ur>
</Tr>

```javascript
function topThree(scores) {
  return scores.sort((x, y) => y - x).slice(0, 3);
}
const scores = [72, 95, 61, 88, 79];
console.log(topThree(scores));
console.log(scores);

function topThreeSafe(list) {
  return list.toSorted((x, y) => y - x).slice(0, 3);
}
const fresh = [72, 95, 61, 88, 79];
console.log(topThreeSafe(fresh), fresh);
```

```text output
[ 95, 88, 79 ]
[ 95, 88, 79, 72, 61 ]
[ 95, 88, 79 ] [ 72, 95, 61, 88, 79 ]
```

<Happened>
<Tr>
<En>

- `topThree` gave the right answer **and** quietly reordered the caller's `scores`. If another part of the app relied on the original order (say, scores by date), it's now broken.
- `topThreeSafe` used `toSorted`, so `fresh` kept its original order.
- `toSorted`, `toReversed`, `toSpliced` and `with` are available in all modern browsers and Node 20+. In older code you'll see `[...list].sort(…)`, which does the same: copy first, then sort the copy.

</En>
<Ur>

- `topThree` ne sahi jawab diya **aur** khamoshi se call karne wale ke `scores` ki tarteeb badal di. Agar app ka koi aur hissa asal tarteeb par chalta tha (maslan date ke hisaab se scores), wo ab toot gaya.
- `topThreeSafe` ne `toSorted` istemal kiya, isliye `fresh` ki asal tarteeb bachi rahi.
- `toSorted`, `toReversed`, `toSpliced` aur `with` tamam jadeed browsers aur Node 20+ me hain. Purane code me `[...list].sort(…)` milega, jo yahi karta hai: pehle copy, phir copy ko sort.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Mutating vs non-mutating array methods">

<Tr>
<En>
Learn which array methods change the array and which return a new one. Each mutating method has a safe twin.
</En>
<Ur>
Seekhein ke kaun se array methods array badalte hain aur kaun naya dete hain. Har mutate karne wale method ka mehfooz jurwan hai.
</Ur>
</Tr>

```javascript
const nums = [3, 1, 2];
console.log(nums.toSorted(), nums.toReversed(), nums.with(0, 99), nums.toSpliced(1, 1), nums);
console.log(nums.concat([4]), nums.slice(1), nums);

const m = [3, 1, 2];
m.reverse();
console.log(m);
m.splice(0, 1);
console.log(m);
m.fill(0);
console.log(m);
```

```text output
[ 1, 2, 3 ] [ 2, 1, 3 ] [ 99, 1, 2 ] [ 3, 2 ] [ 3, 1, 2 ]
[ 3, 1, 2, 4 ] [ 1, 2 ] [ 3, 1, 2 ]
[ 2, 1, 3 ]
[ 1, 3 ]
[ 0, 0 ]
```

<Happened>
<Tr>
<En>

- After all those safe methods, `nums` is still `[3, 1, 2]`.
- `with(0, 99)` is the non-mutating version of `nums[0] = 99`; `toSpliced(1, 1)` removes one item at index 1 into a copy.
- On `m`, `reverse`, `splice` and `fill` each changed the array itself.
- Watch for **`sort`** and **`reverse`** especially: their names don't sound like they change anything, but they do.

</En>
<Ur>

- Un tamam mehfooz methods ke baad bhi `nums` `[3, 1, 2]` hai.
- `with(0, 99)` `nums[0] = 99` ka mutate na karne wala version hai; `toSpliced(1, 1)` index 1 ka ek item hata kar copy deta hai.
- `m` par `reverse`, `splice` aur `fill` har ek ne khud array badal di.
- Khaas taur par **`sort`** aur **`reverse`** par nazar rakhein: in ke naam aise nahi lagte ke kuch badlenge, magar badalte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="const doesn't make things immutable">

<Tr>
<En>
`const` means the **variable** can't be reassigned to a different value. It says nothing about the object inside: you can still change its properties.
</En>
<Ur>
`const` ka matlab hai ke **variable** ko doosri value nahi di ja sakti. Andar ke object ke baare me ye kuch nahi kehta: aap ab bhi us ki properties badal sakte hain.
</Ur>
</Tr>

```javascript
const settings = { theme: "light" };
settings.theme = "dark";
console.log(settings);

try {
  settings = {};
} catch (error) {
  console.log(error.name + ": " + error.message);
}
```

```text output
{ theme: 'dark' }
TypeError: Assignment to constant variable.
```

<Happened>
<Tr>
<En>

- Changing `settings.theme` worked fine.
- Only **pointing `settings` at a new object** was blocked.
- Think of `const` as "this label is glued to this box". You can't move the label, but you can rearrange what's inside the box. To lock the contents, use `Object.freeze` (coming up).

</En>
<Ur>

- `settings.theme` badalna theek chala.
- Sirf **`settings` ko naye object ki taraf karna** roka gaya.
- `const` ko "ye label is dabbe par chipka hai" samjhein. Label hata nahi sakte, magar dabbe ke andar ki cheezen ulat palat kar sakte hain. Andar ka maal band karne ke liye `Object.freeze` lein (aage aa raha hai).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Shallow vs deep copies compared">

<Tr>
<En>
Every common copying tool makes a new top-level object, but only some copy what's **inside**. The last two columns below answer "is the nested array/object still shared with the original?".
</En>
<Ur>
Har aam copy auzaar naya upar ka object banata hai, magar sirf kuch hi **andar** ka maal copy karte hain. Neeche ke aakhri do columns jawab dete hain "kya nested array/object ab bhi asal ke saath share hai?".
</Ur>
</Tr>

```javascript
const original = { name: "Alex", tags: ["vip"], address: { city: "Denver" } };

const copies = {
  spread: { ...original },
  assign: Object.assign({}, original),
  structured: structuredClone(original),
  json: JSON.parse(JSON.stringify(original)),
};

for (const [how, c] of Object.entries(copies)) {
  console.log(how.padEnd(10), c !== original, c.tags === original.tags, c.address === original.address);
}

const arr = [{ id: 1 }, { id: 2 }];
const arrCopies = [[...arr], arr.slice(), Array.from(arr), structuredClone(arr)];
console.log(arrCopies.map((c) => c[0] === arr[0]));
```

```text output
spread     true true true
assign     true true true
structured true false false
json       true false false
[ true, true, true, false ]
```

<Happened>
<Tr>
<En>

| Tool | Top level new? | Nested shared? |
| --- | --- | --- |
| `{ ...obj }`, `Object.assign({}, obj)` | yes | **yes** (shallow) |
| `[...arr]`, `arr.slice()`, `Array.from(arr)` | yes | **yes** (shallow) |
| `structuredClone(x)` | yes | no (deep) |
| `JSON.parse(JSON.stringify(x))` | yes | no, but loses types (next step) |

- An "array of objects" copied with spread is a new array holding **the same objects**: change `copy[0].qty` and the original's first item changes too.

</En>
<Ur>

| Auzaar | Upar ka level naya? | Nested share? |
| --- | --- | --- |
| `{ ...obj }`, `Object.assign({}, obj)` | haan | **haan** (shallow) |
| `[...arr]`, `arr.slice()`, `Array.from(arr)` | haan | **haan** (shallow) |
| `structuredClone(x)` | haan | nahi (deep) |
| `JSON.parse(JSON.stringify(x))` | haan | nahi, magar types kho deta hai (agla qadam) |

- Spread se copy hui "objects ki array" nayi array hai jis me **wahi objects** hain: `copy[0].qty` badlein aur asal ka pehla item bhi badal jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="What structuredClone can and can't copy">

<Tr>
<En>
`structuredClone` deep-copies most built-in data types correctly, including dates, `Map`, `Set` and even objects that refer to themselves. It **can't** copy functions, and class instances come back as plain objects without their methods.
</En>
<Ur>
`structuredClone` zyada tar bani banai data types ki sahi deep copy karta hai, dates, `Map`, `Set` aur khud ki taraf ishara karne wale objects samet. Ye functions copy **nahi** kar sakta, aur class instances apne methods ke baghair saade objects ban kar wapas aate hain.
</Ur>
</Tr>

```javascript
const order = {
  placed: new Date("2026-11-12T10:00:00Z"),
  tags: new Set(["gift"]),
  prices: new Map([["mug", 8]]),
  note: undefined,
};

const s = structuredClone(order);
const j = JSON.parse(JSON.stringify(order));
console.log(s.placed instanceof Date, s.tags.has("gift"), s.prices.get("mug"), "note" in s);
console.log(typeof j.placed, j.tags, j.prices, "note" in j);

const loop = { name: "loop" };
loop.self = loop;
const loopCopy = structuredClone(loop);
console.log(loopCopy.self === loopCopy, loopCopy !== loop);

try {
  structuredClone({ fn() {} });
} catch (error) {
  console.log(error.name);
}

class Money {
  constructor(cents) {
    this.cents = cents;
  }
  format() {
    return "$" + (this.cents / 100).toFixed(2);
  }
}
const cloned = structuredClone(new Money(1999));
console.log(cloned, cloned instanceof Money, typeof cloned.format);
```

```text output
true true 8 true
string {} {} false
true true
DataCloneError
{ cents: 1999 } false undefined
```

<Happened>
<Tr>
<En>

- `structuredClone` kept the `Date`, the `Set`, the `Map` and the `undefined` field. The JSON trick turned the date into a string, emptied the `Set` and `Map`, and dropped `note`.
- A self-referencing object was copied correctly, and the copy points to **itself**, not to the original.
- Functions throw a `DataCloneError`.
- The `Money` instance came back as `{ cents: 1999 }`: the data survived, but it's no longer a `Money`, so `format` is gone. For class instances, write your own `clone()` method (`new Money(this.cents)`).

</En>
<Ur>

- `structuredClone` ne `Date`, `Set`, `Map` aur `undefined` field rakhi. JSON wali chaal ne date ko string banaya, `Set` aur `Map` khaali kiye, aur `note` gira diya.
- Khud ki taraf ishara karne wala object sahi copy hua, aur copy **apni** taraf ishara karti hai, asal ki taraf nahi.
- Functions `DataCloneError` phenkte hain.
- `Money` instance `{ cents: 1999 }` ban kar wapas aaya: data bacha, magar ab ye `Money` nahi, isliye `format` chala gaya. Class instances ke liye apna `clone()` method likhein (`new Money(this.cents)`).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Object.freeze, and why it's shallow">

<Tr>
<En>
`Object.freeze(obj)` stops properties from being added, removed or changed. In strict mode (modules, classes), trying throws a `TypeError`. But freezing is **shallow**: nested objects are still changeable unless you freeze them too.
</En>
<Ur>
`Object.freeze(obj)` properties ko jorne, hatane ya badalne se rokta hai. Strict mode (modules, classes) me koshish `TypeError` phenkti hai. Magar freeze **shallow** hai: nested objects tab tak badal sakte hain jab tak aap unhe bhi freeze na karein.
</Ur>
</Tr>

```javascript
const config = Object.freeze({ apiUrl: "https://api.example.com", retry: { times: 3 } });

try {
  config.apiUrl = "http://evil.example";
} catch (error) {
  console.log(error.name + ": " + error.message);
}
config.retry.times = 99;
console.log(config.apiUrl, config.retry.times, Object.isFrozen(config), Object.isFrozen(config.retry));

function deepFreeze(obj) {
  for (const value of Object.values(obj)) {
    if (value && typeof value === "object" && !Object.isFrozen(value)) deepFreeze(value);
  }
  return Object.freeze(obj);
}

const safe = deepFreeze({ retry: { times: 3 }, hosts: ["a", "b"] });
try {
  safe.retry.times = 99;
} catch (error) {
  console.log(error.name + ": " + error.message);
}
try {
  safe.hosts.push("c");
} catch (error) {
  console.log(error.name + ": " + error.message);
}
console.log(safe.retry.times, safe.hosts);
```

```text output
TypeError: Cannot assign to read only property 'apiUrl' of object '#<Object>'
https://api.example.com 99 true false
TypeError: Cannot assign to read only property 'times' of object '#<Object>'
TypeError: Cannot add property 2, object is not extensible
3 [ 'a', 'b' ]
```

<Happened>
<Tr>
<En>

- Changing `config.apiUrl` threw, but `config.retry.times = 99` **worked**: `retry` itself wasn't frozen.
- `deepFreeze` walks every nested object and array and freezes them all, so both changes were blocked.
- In old sloppy-mode scripts, writes to frozen objects fail **silently** (no error), which is confusing. Another reason to use modules.
- Freezing is great for config and constants. For app state, most teams rely on **not mutating** (and tools like TypeScript's `readonly` or Immer) rather than freezing everything.

</En>
<Ur>

- `config.apiUrl` badalna error phenk gaya, magar `config.retry.times = 99` **chal gaya**: khud `retry` freeze nahi tha.
- `deepFreeze` har nested object aur array tak jata hai aur sab freeze karta hai, isliye dono tabdeeliyan rok di gayin.
- Purane sloppy-mode scripts me frozen objects par likhna **khamoshi se** fail hota hai (koi error nahi), jo uljhan wala hai. Modules istemal karne ki ek aur wajah.
- Freeze karna config aur constants ke liye behtareen hai. App state ke liye zyada tar teams sab freeze karne ke bajaye **mutate na karne** (aur TypeScript ke `readonly` ya Immer jaise auzaron) par chalti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Updating nested data immutably">

<Tr>
<En>
To change something deep inside, copy **each object on the path** to it and reuse everything else. Unchanged parts stay the same objects (**structural sharing**), which is fast and lets `===` show exactly what changed.
</En>
<Ur>
Andar gehri koi cheez badalne ke liye us tak ke **raaste ka har object** copy karein aur baqi sab dobara istemal karein. Be-badle hisse wahi objects rehte hain (**structural sharing**), jo tez hai aur `===` ko bilkul dikhane deta hai ke kya badla.
</Ur>
</Tr>

```javascript
const state = {
  user: { name: "Alex" },
  cart: { items: [{ id: 1, qty: 1 }, { id: 2, qty: 2 }], coupon: null },
};

const next = {
  ...state,
  cart: {
    ...state.cart,
    items: state.cart.items.map((item) => (item.id === 2 ? { ...item, qty: 3 } : item)),
  },
};

console.log(state.cart.items[1].qty, next.cart.items[1].qty);
console.log(next.user === state.user, next.cart === state.cart, next.cart.items[0] === state.cart.items[0]);
```

```text output
2 3
true false true
```

<Happened>
<Tr>
<En>

- The path to the change was `state → cart → items → item 2`. Each of those got a new object; `state` itself still says qty 2.
- `user` and item 1 weren't on the path, so they're **reused** (`===` is true). A UI that shows the user's name can skip re-rendering.
- This gets verbose for deep data. Libraries like **Immer** let you write `draft.cart.items[1].qty = 3` and produce exactly this result for you.

</En>
<Ur>

- Tabdeeli ka raasta `state → cart → items → item 2` tha. In me se har ek ko naya object mila; khud `state` ab bhi qty 2 kehta hai.
- `user` aur item 1 raaste par nahi the, isliye wo **dobara istemal** hue (`===` true hai). User ka naam dikhane wali UI re-render chhor sakti hai.
- Gehre data ke liye ye lamba ho jata hai. **Immer** jaisi libraries aap ko `draft.cart.items[1].qty = 3` likhne deti hain aur bilkul yahi nateeja bana deti hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Undo history for free">

<Tr>
<En>
When every change creates a new version and old versions are never mutated, keeping a **history** is just keeping the old objects in a list. Undo means going back to the previous one.
</En>
<Ur>
Jab har tabdeeli naya version banaye aur purane versions kabhi mutate na hon, to **history** rakhna bas purane objects ko list me rakhna hai. Undo ka matlab pichhle par wapas jana.
</Ur>
</Tr>

```javascript
const history = [];
let doc = { title: "Draft", words: 0 };

function edit(changes) {
  history.push(doc);
  doc = { ...doc, ...changes };
}

edit({ words: 120 });
edit({ title: "Final" });
console.log(doc);
console.log(history);

doc = history.pop();
console.log("after undo:", doc);
```

```text output
{ title: 'Final', words: 120 }
[ { title: 'Draft', words: 0 }, { title: 'Draft', words: 120 } ]
after undo: { title: 'Draft', words: 120 }
```

<Happened>
<Tr>
<En>

- Each `edit` saved the current version, then replaced `doc` with a new object.
- The history shows both earlier versions exactly as they were. If `edit` had mutated `doc` (`doc.words = 120`), every history entry would be **the same object** showing the latest values, and undo would be impossible.
- Redux DevTools' "time travel" and many editors' undo features work this way.

</En>
<Ur>

- Har `edit` ne maujooda version mehfooz kiya, phir `doc` ko naye object se badal diya.
- History dono pichhle versions bilkul waise dikhati hai jaise wo the. Agar `edit` `doc` ko mutate karta (`doc.words = 120`), to history ki har entry **ek hi object** hoti jo taaza values dikhati, aur undo na-mumkin hota.
- Redux DevTools ka "time travel" aur bohot se editors ke undo features aise hi kaam karte hain.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Changing a function's argument">

```javascript
function addTax(order) {
  order.total = Math.round(order.total * 1.08);
  return order;
}
const order = { id: 1, total: 1000 };
const withTax = addTax(order);
console.log(order.total, withTax === order);
```

```text output
1080 true
```

</Bad>
<Good title="Return a new object">

```javascript
function addTax(order) {
  return { ...order, total: Math.round(order.total * 1.08) };
}
const order = { id: 1, total: 1000 };
const withTax = addTax(order);
console.log(order.total, withTax.total, withTax === order);
```

```text output
1000 1080 false
```

</Good>
</Compare>

<Compare>
<Bad title="Shallow copy of an array of objects, then editing items">

```javascript
const items = [{ name: "Mug", qty: 1 }];
const copy = [...items];
copy[0].qty = 5;
console.log(items[0].qty);
```

```text output
5
```

</Bad>
<Good title="Copy the item you change">

```javascript
const items = [{ name: "Mug", qty: 1 }];
const copy = items.map((item, i) => (i === 0 ? { ...item, qty: 5 } : item));
console.log(items[0].qty, copy[0].qty);
```

```text output
1 5
```

</Good>
</Compare>

<Compare>
<Bad title="Default values shared between calls">

```javascript
const DEFAULT_FILTERS = { tags: [] };
function makeFilters() {
  return DEFAULT_FILTERS;
}
const a = makeFilters();
a.tags.push("sale");
console.log(makeFilters().tags);
```

```text output
[ 'sale' ]
```

</Bad>
<Good title="Create a fresh object each time">

```javascript
function makeFilters() {
  return { tags: [] };
}
const a = makeFilters();
a.tags.push("sale");
console.log(makeFilters().tags);
```

```text output
[]
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Assuming `const` freezes objects.** It only prevents reassignment.
- **Using `JSON.parse(JSON.stringify(x))` as a deep copy** of data with dates, `Map`s, `Set`s or `undefined`.
- **Calling `sort`/`reverse` on props or state.** Use `toSorted`/`toReversed`.
- **Freezing and forgetting it's shallow.**
- **Deep-cloning huge objects on every change** "to be safe". Copy only the path you change.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Ye samajhna ke `const` objects freeze karta hai.** Ye sirf dobara value dene se rokta hai.
- **Dates, `Map`s, `Set`s ya `undefined` wale data ki deep copy ke liye `JSON.parse(JSON.stringify(x))` lagana.**
- **Props ya state par `sort`/`reverse` call karna.** `toSorted`/`toReversed` lein.
- **Freeze kar ke bhool jana ke ye shallow hai.**
- **"Mehfooz rehne ke liye" har tabdeeli par bohot bare objects ki deep clone karna.** Sirf wo raasta copy karein jo badal rahe hain.

</Ur>
</Tr>

<Challenge title="Pure cart functions">

<Tr>
<En>
Write three functions that never change their input: `addItem(cart, item)`, `setQty(cart, id, qty)` and `removeItem(cart, id)`, where `cart` is `{ items: [...] }`. Show that the original cart is unchanged after calling all three.
</En>
<Ur>
Teen functions likhein jo kabhi apna input na badlein: `addItem(cart, item)`, `setQty(cart, id, qty)` aur `removeItem(cart, id)`, jahan `cart` `{ items: [...] }` hai. Dikhayen ke teeno call karne ke baad asal cart nahi badla.
</Ur>
</Tr>

<Solution>

```javascript
const addItem = (cart, item) => ({ ...cart, items: [...cart.items, item] });

  ...cart,
  items: cart.items.map((i) => (i.id === id ? { ...i, qty } : i)),
});
const removeItem = (cart, id) => ({ ...cart, items: cart.items.filter((i) => i.id !== id) });

const cart = { items: [{ id: 1, qty: 1 }] };
const c1 = addItem(cart, { id: 2, qty: 1 });
const c2 = setQty(c1, 2, 4);
const c3 = removeItem(c2, 1);

console.log(JSON.stringify(cart));
console.log(JSON.stringify(c3));
```

```text output
{"items":[{"id":1,"qty":1}]}
{"items":[{"id":2,"qty":4}]}
```

</Solution>

## Remember

<Takeaways>
<Tr>
<En>

- Primitives are copied; **objects and arrays are shared by reference** (assignment, function arguments).
- **Mutating** methods: `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`, `fill`, property assignment. **Safe** twins: spread, `slice`, `concat`, `map`, `filter`, `toSorted`, `toReversed`, `toSpliced`, `with`.
- `const` stops reassignment, not mutation.
- **Shallow** copies (spread, `Object.assign`, `slice`, `Array.from`) share nested objects; **`structuredClone`** copies deeply (not functions; class instances lose methods).
- `Object.freeze` is shallow; deep-freeze for nested config.
- Update nested data by copying **each level on the path**; unchanged parts are reused.
- Immutability makes change detection (`===`), undo and debugging easy. Mutating local data you just created is fine.

</En>
<Ur>

- Primitives copy hote hain; **objects aur arrays reference se share hote hain** (assignment, function arguments).
- **Mutate karne wale** methods: `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`, `fill`, property dena. **Mehfooz** jurwan: spread, `slice`, `concat`, `map`, `filter`, `toSorted`, `toReversed`, `toSpliced`, `with`.
- `const` dobara value dene ko rokta hai, mutation ko nahi.
- **Shallow** copies (spread, `Object.assign`, `slice`, `Array.from`) nested objects share karti hain; **`structuredClone`** gehri copy karta hai (functions nahi; class instances methods kho dete hain).
- `Object.freeze` shallow hai; nested config ke liye deep-freeze.
- Nested data **raaste ka har level** copy kar ke update karein; be-badle hisse dobara istemal hote hain.
- Immutability tabdeeli pehchanna (`===`), undo aur debugging aasaan banati hai. Abhi banaya local data mutate karna theek hai.

<DeepDive title="More about immutability">

**Levels of locking.**

| Method | Add props | Delete props | Change values |
| --- | --- | --- | --- |
| `Object.preventExtensions` | no | yes | yes |
| `Object.seal` | no | no | yes |
| `Object.freeze` | no | no | no |

**TypeScript helps at compile time.** `readonly` properties, `ReadonlyArray<T>` / `readonly T[]` and `as const` make the compiler reject mutations, at zero runtime cost.

**Immer.** `produce(state, draft => { draft.cart.items[1].qty = 3 })` lets you write mutating code against a proxy "draft" and returns a new immutable state with structural sharing. Redux Toolkit uses it internally.

**Persistent data structures** (Immutable.js and similar) make large immutable collections efficient by sharing internal tree nodes, at the cost of a different API.

**Performance.** Copying is O(n) in the size of what you copy. Copying only the changed path keeps updates cheap. Inside a function, building a result with `push` on a **local** array and returning it is perfectly fine: nothing outside sees the mutation.

**Strings are already immutable**, which is why string methods always return new strings.

</DeepDive>

<DeepDive title="Real world: the shared default filters">

A dashboard had a filter panel. Its initial state came from a module-level constant:

```text
export const DEFAULT_FILTERS = { status: "all", tags: [] };
const [filters, setFilters] = useState(DEFAULT_FILTERS);
```

When a user added a tag, the handler did `filters.tags.push(tag); setFilters({ ...filters })`. The spread made a new top-level object, so React re-rendered, and everything looked fine.

But `filters.tags` **was** `DEFAULT_FILTERS.tags`. Every tag anyone added was pushed into the shared constant. "Reset filters" set the state back to `DEFAULT_FILTERS`, which now contained all the old tags, so reset appeared broken. In server-side rendering, the constant lived in the server process and tags from **one user's request leaked into other users' pages** until the server restarted.

The fix:

1. Never mutate: `setFilters((f) => ({ ...f, tags: [...f.tags, tag] }))`.
2. Make the default a function: `const makeDefaultFilters = () => ({ status: "all", tags: [] })`.
3. Deep-freeze shared constants in development so any accidental mutation throws immediately.

Lesson: a shallow copy at the top doesn't protect what's nested inside, and module-level objects are shared by everyone, sometimes across users.

</DeepDive>

<DeepDive title="Security lens">

- **Shared mutable state on servers can leak data between users.** Module-level objects live for the whole process; never store per-request data in them, and never mutate shared defaults.
- **Freeze security-sensitive config** (allowed origins, role lists, feature flags) so a bug or a malicious dependency can't change it at runtime.
- **Clone before passing data to untrusted code** (plugins, third-party scripts) so they can't modify your internal objects.
- **Prototype pollution** mutates shared prototypes (`Object.prototype`) through unsafe merges; immutable updates with spread and validated input reduce the risk, and `Object.freeze(Object.prototype)` is a hardening option in some apps.
- **Audit logs and history should be append-only**: store new records instead of editing old ones.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between a shallow copy and a deep copy?">
A shallow copy creates a new top-level object or array but keeps references to the same nested objects. A deep copy recursively copies every nested value so the copy shares nothing with the original.
</QA>

<QA q="Does const make an object immutable?">
No. const prevents the variable from being reassigned, but the object it refers to can still be mutated. Object.freeze prevents changes to the object's own properties, but only shallowly.
</QA>

<QA q="Which array methods mutate the array?">
push, pop, shift, unshift, splice, sort, reverse, fill and copyWithin, plus direct index assignment. Non-mutating alternatives include slice, concat, map, filter, toSorted, toReversed, toSpliced and with.
</QA>

<QA q="What are the limitations of structuredClone?">
It cannot clone functions or DOM nodes, it does not preserve class prototypes so instances become plain objects, and it drops property descriptors such as getters. It does support dates, maps, sets, typed arrays, errors and circular references.
</QA>

<QA q="Why does React prefer immutable updates?">
React compares previous and next state or props by reference. Creating new objects for changed data lets it detect changes cheaply and skip unchanged subtrees, while mutation keeps the same reference and can cause missed updates.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Mutation">Changing an existing value in place.</Term>
  <Term name="Immutability">Treating data as unchangeable and creating new versions instead.</Term>
  <Term name="Reference">A pointer to an object that is shared when assigned.</Term>
  <Term name="Side effect">A change a function makes outside its own scope.</Term>
  <Term name="Pure function">A function with no side effects whose output depends only on its inputs.</Term>
  <Term name="Shallow copy">A copy of the top level that shares nested references.</Term>
  <Term name="Deep copy">A fully independent recursive copy.</Term>
  <Term name="structuredClone">A built-in deep-copy function for structured data.</Term>
  <Term name="Object.freeze">Prevents adding, removing or changing an object's own properties.</Term>
  <Term name="Deep freeze">Recursively freezing an object and everything inside it.</Term>
  <Term name="Structural sharing">Reusing unchanged parts between old and new versions.</Term>
  <Term name="Change detection">Determining whether data changed, often by reference comparison.</Term>
</Terms>
