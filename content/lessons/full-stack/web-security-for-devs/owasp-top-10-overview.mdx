<BigIdea>
<Tr>
<En>
**OWASP** (the Open Worldwide Application Security Project) is a non-profit that publishes free security guidance. Its **Top 10** is an awareness list of the ten most critical risk **categories** for web applications, built from vulnerability data on millions of apps plus a community survey, and updated every few years. The **2025** edition is: **A01 Broken Access Control**, **A02 Security Misconfiguration**, **A03 Software Supply Chain Failures**, **A04 Cryptographic Failures**, **A05 Injection**, **A06 Insecure Design**, **A07 Authentication Failures**, **A08 Software or Data Integrity Failures**, **A09 Security Logging & Alerting Failures**, and **A10 Mishandling of Exceptional Conditions**. It's not a checklist or a standard to "comply" with; it's a map of where real breaches come from, so you know what to look for in your own code and reviews. Most items come down to a few habits: check permissions on the server for every request, never build queries from strings, keep secure defaults and dependencies up to date, handle errors by **failing safely**, and log what matters.
</En>

**OWASP** (Open Worldwide Application Security Project) ek non-profit hai jo muft security rehnumai shaya karta hai. ## Picture it

<Tr>
<En>

Think of the Top 10 as a **fire safety inspector's list** for a building.

- Inspectors don't list every possible accident; they list the causes of most real fires: blocked exits, overloaded sockets, missing alarms, flammable storage.
- Each item maps to a habit: keep exits clear (access control), don't leave the gas on (misconfiguration), check what suppliers deliver (supply chain), install alarms that actually ring somewhere (logging and alerting).
- A building can pass the inspection and still burn, and a building with one blocked exit isn't doomed; the list tells you where to look first, not that you're done.

</En>
<Ur>

Top 10 ko imarat ke **aag ki hifazat ke inspector ki list** samjhein.

- Inspectors har mumkin haadse ki list nahi banate; woh zyadatar asli aag ki wajahen likhte hain: band raste, zyada bojh wale sockets, ghayab alarms, aag pakarne wala saaman.
- Har item ek aadat se milta hai: raste khule rakho (access control), gas khuli na chhoro (misconfiguration), suppliers kya dete hain check karo (supply chain), aise alarms lagao jo waqai kahin bajen (logging aur alerting).
- Imarat inspection pass kar ke bhi jal sakti hai, aur ek band raste wali imarat barbaad nahi; list batati hai pehle kahan dekhna hai, ye nahi ke aap ka kaam khatam.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Attack an insecure app">

<Tr>
<En>
`vulnerable.js` is a small invoice API with one realistic flaw from four categories: a login query built with a template string (**A05**), an invoice route that only checks you're logged in (**A01**), a transfer that continues when the fraud check throws (**A10**), and error handling that returns the database error and stack (**A02**, plus Express's default `X-Powered-By` header). `attack.js` runs five attacks and reports each one. Only run attacks like these against your own apps.
</En>
<Ur>
`vulnerable.js` chhoti invoice API hai jis me chaar qismon se ek ek haqeeqi khami hai: template string se bani login query (**A05**), invoice route jo sirf ye check karta hai ke aap logged in hain (**A01**), transfer jo fraud check ke error dene par jaari rehta hai (**A10**), aur error handling jo database error aur stack lautati hai (**A02**, plus Express ka default `X-Powered-By` header). `attack.js` paanch hamle chalata aur har ek ki report deta hai. Aise hamle sirf apni apps par chalayen.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 pg@8.23.1 --silent
export PGPASSWORD=postgres
psql -q -h localhost -U postgres -c 'DROP DATABASE IF EXISTS owasp_demo' -c 'CREATE DATABASE owasp_demo' 2> /dev/null
psql -q -h localhost -U postgres -d owasp_demo -c "CREATE TABLE users (id int PRIMARY KEY, email text, password text)" \
  -c "INSERT INTO users VALUES (1, 'jane@example.com', 'correct horse'), (2, 'john@example.com', 'tr0ub4dor')" \
  -c "CREATE TABLE invoices (id int PRIMARY KEY, owner_id int, amount_cents int)" -c "INSERT INTO invoices VALUES (10, 1, 4200), (20, 2, 990000)"
# A deliberately INSECURE app: one flaw from four different Top 10 categories
cat > vulnerable.js <<'EOF'
import express from 'express';
import pg from 'pg';
const db = new pg.Pool({ connectionString: 'postgres://postgres:postgres@localhost:5432/owasp_demo' });
const app = express();
app.use(express.json());
const checkFraud = async (req) => { if (req.get('x-region') === 'test-outage') throw new Error('fraud service timeout'); return { blocked: req.get('x-region') === 'blocked' }; };

app.post('/login', async (req, res) => {                                    // A05 Injection: SQL built from strings
  const { rows } = await db.query(`SELECT id FROM users WHERE email = '${req.body.email}' AND password = '${req.body.password}'`);
  rows.length ? res.json({ token: `user-${rows[0].id}` }) : res.status(401).json({ error: 'bad login' });
});
const auth = (req, res, next) => { req.userId = Number(req.get('authorization')?.replace('Bearer user-', '')); req.userId ? next() : res.sendStatus(401); };
app.get('/invoices/:id', auth, async (req, res) => {                        // A01 Broken Access Control: no ownership check
  const { rows: [inv] } = await db.query('SELECT * FROM invoices WHERE id = $1', [req.params.id]);
  inv ? res.json(inv) : res.sendStatus(404);
});
app.post('/transfer', auth, async (req, res) => {                           // A10 Exceptional conditions: fails OPEN
  let verdict = { blocked: false };
  try { verdict = await checkFraud(req); } catch { /* fraud service down: carry on */ }
  verdict.blocked ? res.status(403).json({ error: 'blocked' }) : res.json({ sent: req.body.amount });
});
app.get('/invoices-search', auth, async (req, res) => {                     // A02 Misconfiguration: errors leak internals
  try { res.json((await db.query(`SELECT * FROM invoices WHERE amount_cents > ${req.query.min}`)).rows); }
  catch (e) { res.status(500).json({ error: e.message, stack: e.stack.split('\n')[1].trim() }); }
});
app.listen(3000);
EOF
cat > attack.js <<'EOF'
// The same attacks are run against whichever app is listening on :3000
const call = async (method, path, { body, headers = {} } = {}) => {
  const res = await fetch(`http://localhost:3000${path}`, { method, headers: { 'content-type': 'application/json', ...headers }, body: body && JSON.stringify(body) });
  return { status: res.status, body: await res.text(), headers: res.headers };
};
const jane = { authorization: 'Bearer user-1' };
const report = (cat, name, vulnerable, detail) => console.log(`${cat.padEnd(4)} ${name.padEnd(42)} ${vulnerable ? 'VULNERABLE' : 'blocked   '} ${detail}`);

const sqli = await call('POST', '/login', { body: { email: "john@example.com' --", password: 'anything' } });
report('A05', "email john@example.com' -- logs in as John", sqli.status === 200, `${sqli.status} ${sqli.body}`);
const idor = await call('GET', '/invoices/20', { headers: jane });
report('A01', "Jane reads John's invoice 20", idor.status === 200, `${idor.status} ${idor.body}`);
const fail = await call('POST', '/transfer', { body: { amount: 5000 }, headers: { ...jane, 'x-region': 'test-outage' } });
report('A10', 'transfer while the fraud check is down', fail.status === 200, `${fail.status} ${fail.body}`);
const leak = await call('GET', '/invoices-search?min=abc', { headers: jane });
const leaked = JSON.parse(leak.body);
report('A02', 'bad input reveals internals', Boolean(leaked.stack || /column|relation/.test(leaked.error)), `${leak.status} error=${JSON.stringify(leaked.error)} stack=${leaked.stack ? 'yes' : 'no'}`);
report('A02', 'X-Powered-By header names the framework', leak.headers.has('x-powered-by'), `${leak.headers.get('x-powered-by') ?? '(none)'}`);
EOF
node vulnerable.js & APP=$!; sleep 1
node attack.js
kill $APP
```

<Happened>
<Tr>
<En>

- **A05 Injection**: the email `john@example.com' --` closed the string and turned the password check into a comment, so the query became "find John" and returned his token. No password needed.
- **A01 Broken Access Control**: Jane, logged in, changed the URL to invoice 20 and read John's $9,900 invoice. Being authenticated isn't the same as being allowed.
- **A10 Mishandling of Exceptional Conditions**: when the fraud service timed out, the empty `catch` let the transfer go through. An attacker who can make the check fail (overload it, send weird input) bypasses it completely.
- **A02 Security Misconfiguration**: invalid input produced a 500 containing the raw database error (`column "abc" does not exist`, which also reveals the input reached SQL unescaped) and a stack line with file paths. The `X-Powered-By: Express` header tells attackers which exploits to try.

</En>
<Ur>

- **A05 Injection**: email `john@example.com' --` ne string band kar ke password check ko comment bana diya, isliye query "John dhoondo" ban gayi aur us ka token lautaya. Password ki zaroorat nahi.
- **A01 Broken Access Control**: logged in Jane ne URL ko invoice 20 kiya aur John ki $9,900 ki invoice parh li. Authenticated hona ijazat hone jaisa nahi.
- **A10 Mishandling of Exceptional Conditions**: fraud service ke timeout par khaali `catch` ne transfer guzarne diya. Jo hamla awar check ko nakam kara sake (bojh daal kar, ajeeb input bhej kar) woh use poori tarah bypass kar leta hai.
- **A02 Security Misconfiguration**: ghalat input ne 500 diya jis me database ka kaccha error tha (`column "abc" does not exist`, jo ye bhi batata hai ke input bina escape ke SQL tak pohncha) aur file paths wali stack line. `X-Powered-By: Express` header hamla awaron ko batata hai kaunse exploits aazmayen.

</Ur>

<Step title="Fix all five, and run the same attacks again">

<Tr>
<En>
`secure.js` keeps the same routes and makes small, standard changes: **parameterized queries**, an invoice query scoped to the **owner**, a fraud check that **fails closed** with 503, **input validation** plus a generic error handler that logs details server-side, and `x-powered-by` disabled. The same `attack.js` runs unchanged, then `normal.js` checks that ordinary use still works.
</En>
<Ur>
`secure.js` wahi routes rakhta aur chhoti, standard tabdeeliyan karta hai: **parameterized queries**, **malik** tak mehdood invoice query, **band ho kar nakam** hone wala fraud check (503), **input validation** plus aam error handler jo tafseelat server par log kare, aur `x-powered-by` band. Wahi `attack.js` bina tabdeeli chalta hai, phir `normal.js` check karta hai ke aam istemal ab bhi chalta hai.
</Ur>
</Tr>

```bash
cat > secure.js <<'EOF'
import express from 'express';
import pg from 'pg';
const db = new pg.Pool({ connectionString: 'postgres://postgres:postgres@localhost:5432/owasp_demo' });
const app = express();
app.disable('x-powered-by');                                               // A02: don't advertise the stack
app.use(express.json());
const checkFraud = async (req) => { if (req.get('x-region') === 'test-outage') throw new Error('fraud service timeout'); return { blocked: req.get('x-region') === 'blocked' }; };

app.post('/login', async (req, res) => {                                    // A05: parameters, never string-built SQL
  const { rows } = await db.query('SELECT id FROM users WHERE email = $1 AND password = $2', [req.body.email, req.body.password]);
  // (A04: real apps store slow, salted password hashes, never plain passwords -- see Sessions and Cookies)
  rows.length ? res.json({ token: `user-${rows[0].id}` }) : res.status(401).json({ error: 'bad login' });
});
const auth = (req, res, next) => { req.userId = Number(req.get('authorization')?.replace('Bearer user-', '')); req.userId ? next() : res.sendStatus(401); };
app.get('/invoices/:id', auth, async (req, res) => {                        // A01: scope the query to the owner
  const { rows: [inv] } = await db.query('SELECT * FROM invoices WHERE id = $1 AND owner_id = $2', [req.params.id, req.userId]);
  inv ? res.json(inv) : res.sendStatus(404);
});
app.post('/transfer', auth, async (req, res) => {                           // A10: fail CLOSED
  let verdict;
  try { verdict = await checkFraud(req); }
  catch (e) { console.error('fraud check failed:', e.message); return res.status(503).json({ error: 'try again later' }); }
  verdict.blocked ? res.status(403).json({ error: 'blocked' }) : res.json({ sent: req.body.amount });
});
app.get('/invoices-search', auth, async (req, res, next) => {
  const min = Number(req.query.min);
  if (!Number.isInteger(min)) return res.status(400).json({ error: 'min must be an integer' });   // validate input
  res.json((await db.query('SELECT * FROM invoices WHERE owner_id = $1 AND amount_cents > $2', [req.userId, min])).rows);
});
app.use((err, req, res, next) => { console.error(err); res.status(500).json({ error: 'internal error' }); });   // A02: details go to logs only
app.listen(3000);
EOF
cat > normal.js <<'EOF'
const post = await fetch('http://localhost:3000/login', { method: 'POST', headers: { 'content-type': 'application/json' }, body: JSON.stringify({ email: 'jane@example.com', password: 'correct horse' }) });
console.log('Jane logs in            ', post.status, await post.text());
const own = await fetch('http://localhost:3000/invoices/10', { headers: { authorization: 'Bearer user-1' } });
console.log('Jane reads her invoice 10', own.status, await own.text());
EOF
node secure.js 2> app-errors.log & APP=$!; sleep 1
node attack.js
echo "--- normal use still works"
node normal.js
```

<Happened>
<Tr>
<En>

- With `$1`/`$2` parameters, the email `john@example.com' --` is just a string that matches no user: **401**. The SQL structure can't be changed by input.
- Adding `AND owner_id = $2` made John's invoice invisible to Jane: **404**, the same answer as a missing invoice, so ids can't be probed.
- The fraud check outage now returns **503 "try again later"** and logs the error: **fail closed**. A temporary outage costs a retry instead of letting fraud through.
- Bad input gets a clear **400** before reaching SQL; unexpected errors would get a generic 500 while details go to the server log. No framework header is sent.
- Jane can still log in and read **her own** invoice. Good security fixes are usually small and keep normal behavior intact; keep this attack script as a test so the fixes stay fixed.
- The `users` table still stores plain passwords to keep the demo short. That's **A04 Cryptographic Failures** in a real app: store slow, salted hashes (see Sessions and Cookies).

</En>
<Ur>

- `$1`/`$2` parameters ke saath email `john@example.com' --` bas ek string hai jo kisi user se mel nahi khati: **401**. Input SQL ka dhancha nahi badal sakta.
- `AND owner_id = $2` jorne se John ki invoice Jane ke liye ghayab ho gayi: **404**, ghayab invoice jaisa jawab, isliye ids tatole nahi ja sakte.
- Fraud check ka outage ab **503 "try again later"** deta aur error log karta hai: **band ho kar nakam**. Aarzi outage fraud guzarne dene ke bajaye ek retry ki qeemat leta hai.
- Ghalat input SQL tak pohanchne se pehle wazeh **400** pata hai; ghair mutawaqqa errors aam 500 pate jabke tafseelat server log me jati hain. Koi framework header nahi bheja jata.
- Jane ab bhi login aur **apni** invoice parh sakti hai. Achhe security fixes aam taur par chhote hote aur aam rawaiya qaim rakhte hain; is attack script ko test ki tarah rakhein taa ke fixes qaim rahein.
- Demo chhota rakhne ke liye `users` table ab bhi saade passwords rakhta hai. Asal app me ye **A04 Cryptographic Failures** hai: sust, salted hashes rakhein (Sessions and Cookies dekhein).

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Treating the Top 10 as a compliance checkbox">

```text
"We ran a scanner, it found no Top 10 issues, so we're secure."
// scanners miss most access-control and design flaws
```

</Bad>
<Good title="Using it to guide design, review and tests">

```text
design review:  who can call this? what if the payment check errors?

tests:          403/404 for other users, 400 for bad input, 503 when a check is down
```

<Compare>
<Bad title="Swallowing errors in security checks">

```text

try { allowed = await policy.check(user, action); } catch { /* ignore */ }
if (allowed) doIt();
```

</Bad>
<Good title="Fail closed and record it">

```text
let allowed = false;
try { allowed = await policy.check(user, action); }
catch (e) { logger.error({ err: e, user: user.id, action }, 'policy check failed'); }
if (!allowed) return res.status(503).json({ error: 'try again later' });
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Fixing only the reported endpoint**: an IDOR in one route usually exists in its siblings; search the codebase for the pattern.
- **Relying on the frontend** to hide buttons or validate input (A01, A05).
- **Debug mode, default credentials and verbose errors in production** (A02).
- **Adding packages without checking them** (A03): unmaintained, typo-squatted or with install scripts.
- **No alerts**: logs nobody reads don't stop attacks (A09).
- **Thinking frameworks make you safe automatically**: they help, but string-built queries and missing checks are still possible.

</En>

<DeepDive title="More about the OWASP Top 10">

**What changed from 2021.** Security Misconfiguration rose from #5 to #2; Vulnerable and Outdated Components grew into Software Supply Chain Failures (#3); Cryptographic Failures, Injection and Insecure Design each moved down two places; SSRF was folded into Broken Access Control; "Identification and Authentication Failures" became Authentication Failures; logging was renamed to emphasize alerting; and Mishandling of Exceptional Conditions is new.

**How it's built.** Most categories come from contributed testing data mapped to CWEs; a couple are chosen through a practitioner survey, to capture risks testing data doesn't show well yet.

**Other OWASP resources.** The Cheat Sheet Series (practical how-tos), ASVS (a detailed verification standard), the API Security Top 10, the Top 10 for LLM Applications, and Juice Shop (a deliberately vulnerable app for practice).

**The rest of this module.** Injection, XSS, CSRF, access control, security headers, file uploads, secrets and dependency vulnerabilities each get their own lesson.

Source: owasp.org/Top10/2025.

</DeepDive>

<DeepDive title="Real world: the error message that gave away the database">

A job board returned detailed database errors to the browser "to help support debug". A researcher noticed that a malformed filter produced a PostgreSQL syntax error showing part of the SQL query. That confirmed the filter was concatenated into SQL; within an hour they had extracted the users table, including password hashes. Several categories lined up: verbose errors (A02, A10) revealed an injection (A05), and weak, fast password hashes (A04) made cracking easy. Nobody noticed the unusual queries (A09).

What changed:

1. All queries were moved to parameters, with a lint rule against template strings in `query()` calls.
2. Errors return a generic message and a request id; details go only to logs.
3. Passwords were rehashed with argon2id on next login, and all sessions were reset.
4. Alerts on database errors per endpoint and on unusual data volumes per request.

</DeepDive>

<DeepDive title="Security lens">

- **Shift left**: think about access control and failure modes during design, not after a pentest.
- **Automate the boring parts**: dependency audits, secret scanning, static analysis and security headers checks in CI.
- **Test the negative paths**: other users, other tenants, bad input, failing dependencies.
- **Assume breach**: logging, alerting and incident playbooks decide how bad an attack gets.
- **Practice legally**: use your own apps, OWASP Juice Shop or bug bounty programs with clear rules; never test systems you don't have permission to test.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the OWASP Top 10?">
An awareness document from OWASP listing the ten most critical security risk categories for web applications, based on vulnerability data and a community survey, updated every few years. The latest edition is 2025, with Broken Access Control at number one.
</QA>

<QA q="What is broken access control and how do you prevent it?">
Users acting outside their permissions, such as reading other users' records by changing an id or calling admin functions. Prevent it with server-side checks on every request, queries scoped to the user or tenant, deny by default, and tests for cross-user access.
</QA>

<QA q="How do you prevent injection?">
Keep data separate from code: parameterized queries or safe ORM APIs for SQL, argument arrays instead of shell strings, context-aware output encoding for HTML, plus input validation as an extra layer.
</QA>

<QA q="What does fail closed mean?">
When a security control can't make a decision because of an error, the system denies the action instead of allowing it, and records the failure.
</QA>

<QA q="What are software supply chain failures?">
Risks from everything your software is built from: vulnerable or malicious dependencies, compromised build systems or CI, and untrusted update channels. Defenses include lockfiles, audits, minimal dependencies, provenance and signature checks, and protecting the pipeline.
</QA>

</DeepDive>
