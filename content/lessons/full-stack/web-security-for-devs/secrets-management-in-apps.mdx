<BigIdea>
<Tr>
<En>
A **secret** is any value that grants access: API keys, database URLs with passwords, JWT and webhook signing keys, OAuth client secrets, cloud credentials. Secrets must never be in **source code**, because code is copied everywhere (laptops, CI, forks, backups) and **git remembers every version forever**: deleting a key in a later commit doesn't remove it from history, and bots scan public repositories for keys within minutes. Keep secrets **outside the code**: in a git-ignored `.env` file locally, in your CI's encrypted secrets for pipelines, and in a **secret manager** (AWS Secrets Manager, GCP Secret Manager, Vault, Doppler, your platform's environment settings) in production, injected as environment variables or files at runtime. Then handle them carefully in the app: **validate** them at startup so misconfiguration fails fast, never **log** them, give each service its own **least-privilege** credentials, and **rotate** them regularly and immediately after any suspected leak. When a secret leaks, the fix is **rotation**, not just deleting it.
</En>
<Ur>
**Secret** koi bhi qeemat hai jo rasai deti hai: API keys, passwords wale database URLs, JWT aur webhook signing keys, OAuth client secrets, cloud credentials. Secrets kabhi **source code** me nahi hone chahiye, kyunke code har jagah copy hota hai (laptops, CI, forks, backups) aur **git har version hamesha yaad rakhta hai**: baad ke commit me key mitana use history se nahi hatata, aur bots minton me public repositories me keys dhoondte hain. Secrets **code ke bahar** rakhein: local me git-ignored `.env` file me, pipelines ke liye CI ke encrypted secrets me, aur production me **secret manager** (AWS Secrets Manager, GCP Secret Manager, Vault, Doppler, aap ke platform ki environment settings) me, jo runtime par environment variables ya files ki tarah daale jate hain. Phir app me ehtiyat se sambhalein: startup par **validate** karein taa ke ghalat config jaldi fail ho, kabhi **log** na karein, har service ko apne **kam ikhtiyar wale** credentials dein, aur baqaidagi se aur leak ke shak par foran **rotate** karein. Jab secret leak ho to hal **rotation** hai, sirf mitana nahi.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- Leaked keys are used within minutes: crypto mining on cloud accounts, data theft, sending spam through your email provider.
- Git history, forks and CI logs keep secrets long after you "removed" them.
- One shared all-powerful key turns any small leak into a full compromise.
- Rotation is only easy if the app was built to support it.

</En>
<Ur>

- Leak hui keys minton me istemal hoti hain: cloud accounts par crypto mining, data chori, aap ke email provider se spam.
- Git history, forks aur CI logs secrets ko "hatane" ke kaafi baad tak rakhte hain.
- Ek shared, har kaam wali key har chhote leak ko poore hamle me badal deti hai.

</Ur>

## Picture it

<Tr>
<En>

Think of the **keys to your shop**.

- Writing the alarm code on the shop's sign "temporarily" and painting over it later doesn't help: everyone who walked past has already seen it, and photos of the old sign exist (git history, forks, caches). The only fix is **changing the code** (rotation).
- Keys belong in a **key safe** (secret manager); staff get only the keys they need (least privilege), and the safe logs who took which key.
- When a cleaner leaves, you **change the locks** they had keys for.
- A good shop can change locks without closing for a day: for a short time, both the old and the new key open the door (rotation with an overlap).

</En>
<Ur>

Apni **dukan ki chabiyan** socheyn.

- Alarm ka code dukan ke board par "aarzi tor par" likh kar baad me us par rang phir dena madad nahi karta: paas se guzarne wala har shakhs dekh chuka, aur purane board ki tasveeren mojood hain (git history, forks, caches). Wahid hal **code badalna** hai (rotation).
- Chabiyan **key safe** (secret manager) me rehni chahiye; staff ko sirf zaroori chabiyan milti hain (kam ikhtiyar), aur safe log rakhta hai kis ne kaunsi chabi li.
- Jab safai wala chhore to un **taalon ko badlein** jin ki chabiyan us ke paas thin.
- Achhi dukan ek din band kiye baghair taale badal sakti hai: thori der ke liye purani aur nayi dono chabiyan darwaza kholti hain (overlap ke saath rotation).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="A removed secret is still in git, and where secrets belong instead">

<Tr>
<En>
A developer commits a payment key in `payments.js` "just to test", then the next day replaces it with `process.env.PAYMENTS_KEY`. We search the current code, then the history, then run a tiny regex scanner over every commit, the way real secret scanners do. Finally we put local secrets in a git-ignored `.env` and load it with Node's built-in `--env-file`. (The key format is invented for this demo.)
</En>
<Ur>
Ek developer "bas test ke liye" `payments.js` me payment key commit karta hai, phir agle din use `process.env.PAYMENTS_KEY` se badal deta hai. Hum mojooda code, phir history dhoondte hain, phir har commit par chhota regex scanner chalate hain, jaise asli secret scanners karte hain. Aakhir me local secrets git-ignored `.env` me rakh kar Node ke built-in `--env-file` se load karte hain. (Key ka format is demo ke liye ghara gaya hai.)
</Ur>
</Tr>

```bash
mkdir -p shop && cd shop && git init -q -b main && git config user.email dev@example.com && git config user.name "Dev"
# Day 1: a developer hard-codes the payment key "just to test"
cat > payments.js <<'EOF'
export const paymentsKey = 'acme_live_FAKEexampleKEY9xQ2';
EOF
git add . && git commit -qm "Add payments"
# Day 2: they notice and "fix" it by reading the key from the environment
cat > payments.js <<'EOF'
export const paymentsKey = process.env.PAYMENTS_KEY;
EOF
git add . && git commit -qm "Move key to env"

echo "--- the current code looks clean"
grep -rn 'acme_live' --include=*.js . || echo "(no match in the working tree)"
echo "--- but git keeps every version"
git log --format='%s' -S 'acme_live_' 
git show HEAD~1:payments.js
echo "--- a scanner that reads all of history finds it in seconds"
git log -p --all | grep -oE '(acme_live_|AKIA|ghp_)[A-Za-z0-9]{12,}' | sort -u

echo "--- the right place for local secrets: a .env file that git ignores"
printf 'PAYMENTS_KEY=acme_test_localDevKeyOnly\nDATABASE_URL=postgres://app:app-pass@localhost:5432/shop\n' > .env
echo '.env' > .gitignore
git check-ignore -v .env
node --env-file=.env -e "console.log('loaded PAYMENTS_KEY starts with', process.env.PAYMENTS_KEY.slice(0, 10))"
git status --short
```

```text output
--- the current code looks clean
(no match in the working tree)
--- but git keeps every version
Move key to env
Add payments
export const paymentsKey = 'acme_live_FAKEexampleKEY9xQ2';
--- a scanner that reads all of history finds it in seconds
acme_live_FAKEexampleKEY9xQ2
--- the right place for local secrets: a .env file that git ignores
.gitignore:1:.env	.env
loaded PAYMENTS_KEY starts with acme_test_
?? .gitignore
```

<Happened>
<Tr>
<En>

- The working tree is clean, so a quick code review wouldn't notice anything.
- `git log -S` found the two commits that added and removed the string, and `git show HEAD~1:payments.js` printed the **full key**. Anyone with the repository (every clone, fork, CI cache and backup) has it.
- The scanner found it with one regex over all history. Attackers run the same kind of scan on every public push within minutes; tools like **gitleaks** or **trufflehog** and GitHub's **push protection** do it for you before damage is done.
- The only real fix is to **revoke and rotate** the key at the provider. Rewriting history (`git filter-repo`) helps keep the repo clean afterwards, but can't recall copies that already exist.
- `.env` is listed in `.gitignore` (`git check-ignore` confirms which rule matches), `git status` shows only `.gitignore` as new, and `node --env-file=.env` loaded the **test** key without any extra package.

</En>
<Ur>

- Working tree saaf hai, isliye jaldi ka code review kuch nahi pakarta.
- `git log -S` ne woh do commits dhoondhe jinhon ne string joda aur hataya, aur `git show HEAD~1:payments.js` ne **poori key** chhap di. Repository rakhne wale har shakhs (har clone, fork, CI cache aur backup) ke paas ye hai.
- Scanner ne poori history par ek regex se use dhoond liya. Hamla awar har public push par minton me yahi scan chalate hain; **gitleaks** ya **trufflehog** jaise tools aur GitHub ki **push protection** nuqsaan se pehle aap ke liye ye karte hain.
- Wahid asal hal provider par key **revoke aur rotate** karna hai. History dobara likhna (`git filter-repo`) baad me repo saaf rakhne me madad karta hai, magar pehle se mojood copies wapas nahi la sakta.
- `.env` `.gitignore` me darj hai (`git check-ignore` tasdeeq karta hai kaunsa rule mel khata hai), `git status` sirf `.gitignore` ko naya dikhata hai, aur `node --env-file=.env` ne bina extra package ke **test** key load ki.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Validate at startup, redact logs, rotate without downtime">

<Tr>
<En>
`config.js` validates `process.env` with **zod** once at startup: a database URL, a payment key with the expected shape, and a comma-separated list of webhook signing secrets (current first, previous second). `app.js` logs its config and a request with **pino redaction**, then verifies webhook signatures against **both** secrets, the way you'd rotate a signing key while partners switch over. Last, we start it with a broken setting.
</En>
<Ur>
`config.js` startup par ek dafa **zod** se `process.env` validate karta hai: database URL, mutawaqqa shakal wali payment key, aur webhook signing secrets ki comma se juda list (pehle mojooda, doosra pichla). `app.js` apni config aur ek request ko **pino redaction** ke saath log karta hai, phir webhook signatures ko **dono** secrets se tasdeeq karta hai, jaise partners ke badalne ke dauran signing key rotate karte hain. Aakhir me ise ghalat setting ke saath shuru karte hain.
</Ur>
</Tr>

```bash
cd shop && npm init -y > /dev/null && npm pkg set type=module && npm install zod@4.6.7 pino@10.4.0 --silent
# 1. Validate configuration once, at startup, and fail fast with a clear message
cat > config.js <<'EOF'
import { z } from 'zod';
const schema = z.object({
  DATABASE_URL: z.string().url(),
  PAYMENTS_KEY: z.string().regex(/^acme_(live|test)_\w{10,}$/, 'must look like acme_live_… or acme_test_…'),
  WEBHOOK_SECRETS: z.string().transform((s) => s.split(',')).pipe(z.array(z.string().min(32)).min(1)),   // current,previous
});
const parsed = schema.safeParse(process.env);
if (!parsed.success) {
  console.error('Invalid configuration:', parsed.error.issues.map((i) => `${i.path.join('.')}: ${i.message}`).join('; '));
  process.exit(1);
}
export const config = Object.freeze(parsed.data);
EOF
echo 'WEBHOOK_SECRETS=new-secret-0123456789abcdef0123456789,old-secret-0123456789abcdef0123456789' >> .env
cat > app.js <<'EOF'
import { createHmac, timingSafeEqual } from 'node:crypto';
import pino from 'pino';
import { config } from './config.js';

// 2. Logs: redact secret-looking fields so they never reach log storage
const log = pino({ base: null, timestamp: false, redact: { paths: ['config.PAYMENTS_KEY', 'config.DATABASE_URL', 'config.WEBHOOK_SECRETS', 'req.headers.authorization'], censor: '[REDACTED]' } });
log.info({ config, req: { headers: { authorization: 'Bearer user-token-123', 'user-agent': 'curl' } } }, 'starting');

// 3. Rotation: sign with the newest secret, accept current AND previous while partners switch over
const sign = (body, secret) => createHmac('sha256', secret).update(body).digest('hex');
const verify = (body, sig) => config.WEBHOOK_SECRETS.some((s) => timingSafeEqual(Buffer.from(sign(body, s)), Buffer.from(sig)));
const body = '{"event":"order.paid","id":42}';
console.log('signed with the new secret  ->', verify(body, sign(body, 'new-secret-0123456789abcdef0123456789')));
console.log('signed with the old secret  ->', verify(body, sign(body, 'old-secret-0123456789abcdef0123456789')), '(still accepted during rotation)');
console.log('signed with a leaked/unknown ->', verify(body, sign(body, 'leaked-secret-0123456789abcdef01234567')));
EOF
echo "--- with a valid .env"
node --env-file=.env app.js
echo "--- with a broken setting, the app refuses to start"
PAYMENTS_KEY=oops node --env-file=.env app.js; echo "exit code: $?"
```

```text output
--- with a valid .env
signed with the new secret  -> true
signed with the old secret  -> true (still accepted during rotation)
signed with a leaked/unknown -> false
{"level":30,"config":{"DATABASE_URL":"[REDACTED]","PAYMENTS_KEY":"[REDACTED]","WEBHOOK_SECRETS":"[REDACTED]"},"req":{"headers":{"authorization":"[REDACTED]","user-agent":"curl"}},"msg":"starting"}
--- with a broken setting, the app refuses to start
Invalid configuration: PAYMENTS_KEY: must look like acme_live_… or acme_test_…
exit code: 1
```

<Happened>
<Tr>
<En>

- The startup log contains the structure you need to debug (which keys exist, the user agent) but every secret, and the request's `Authorization` header, became **`[REDACTED]`**. Logs are copied to log services, dashboards and support tickets; treat them as semi-public.
- A webhook signed with the **new** secret verified, and so did one signed with the **old** secret: during rotation the app accepts both, so senders can switch at their own pace. After the switch, remove the old one from `WEBHOOK_SECRETS`. A signature made with an unknown (or leaked and already removed) secret failed.
- With `PAYMENTS_KEY=oops`, the app **refused to start** with a precise message and exit code 1. Failing at startup beats failing on the first real payment at 3 a.m. Note the message names the setting but never prints its value.
- The validated config is **frozen** and imported where needed, instead of reading `process.env` all over the codebase, which makes it easy to see and audit every secret the app uses.

</En>
<Ur>

- Startup log me debug ke liye zaroori dhancha hai (kaunsi keys mojood hain, user agent) magar har secret, aur request ka `Authorization` header, **`[REDACTED]`** ban gaya. Logs log services, dashboards aur support tickets me copy hote hain; unhe nim-public samjhein.
- **Naye** secret se signed webhook tasdeeq hua, aur **purane** secret wala bhi: rotation ke dauran app dono qubool karti hai, taa ke bhejne wale apni raftaar se badal sakein. Badalne ke baad purana `WEBHOOK_SECRETS` se hata dein. Na maloom (ya leak ho kar pehle hi hataye gaye) secret wala signature nakam hua.
- `PAYMENTS_KEY=oops` ke saath app ne wazeh paigham aur exit code 1 ke saath **shuru hone se inkaar** kiya. Startup par nakam hona raat 3 baje pehli asli payment par nakam hone se behtar hai. Dhyan dein ke paigham setting ka naam leta hai magar qeemat kabhi nahi chhapta.
- Validate shuda config **frozen** hai aur zaroorat ki jagah import hoti hai, poore codebase me `process.env` parhne ke bajaye, jis se app ke har secret ko dekhna aur audit karna aasan hai.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Secrets in the frontend bundle">

```text
// .env
NEXT_PUBLIC_STRIPE_SECRET_KEY=…     // NEXT_PUBLIC_ means "ship to every browser"
VITE_OPENAI_API_KEY=…               // anyone can read it in DevTools
```

</Bad>
<Good title="Secrets stay on the server">

```text
// server-only env: STRIPE_SECRET_KEY, OPENAI_API_KEY
// the browser calls YOUR API route, which calls the provider with the secret
// only publishable keys (designed to be public) go to the frontend
```

</Good>
</Compare>

<Compare>
<Bad title="Baking secrets into images and logs">

```text
# Dockerfile
ENV DATABASE_URL=postgres://admin:admin-pass@db/shop      # stored in every image layer
console.log('starting with config', process.env);         # every secret in the logs
```

</Bad>
<Good title="Inject at runtime, log safely">

```text
# docker run -e DATABASE_URL (from the secret manager) or mounted secret files
log.info({ config }, 'starting')   // with redact paths for secret fields
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Deleting a leaked key from code without rotating it**: the old key still works.
- **One admin key for everything**: give each service its own key with minimal permissions, so a leak is contained.
- **Secrets in URLs** (`?api_key=`): they end up in logs, browser history and Referer headers.
- **Printing env in CI** (`env`, `set -x`): build logs are widely readable; CI masking isn't perfect.
- **Never rotating**: long-lived secrets accumulate in old laptops, backups and ex-employees' notes.
- **Sharing `.env` files in chat or email**: use a secret manager or password manager.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Leak hui key ko rotate kiye baghair code se mitana**: purani key ab bhi chalti hai.
- **Har cheez ke liye ek admin key**: har service ko kam se kam ijazaton wali apni key dein, taa ke leak mehdood rahe.
- **URLs me secrets** (`?api_key=`): ye logs, browser history aur Referer headers me pohanchte hain.
- **CI me env chhapna** (`env`, `set -x`): build logs bohot logon ko dikhte hain; CI masking mukammal nahi.
- **Kabhi rotate na karna**: lambi umar ke secrets purane laptops, backups aur sabiq mulazimon ke notes me jama hote hain.
- **`.env` files chat ya email me share karna**: secret manager ya password manager lein.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Respond to a leaked key">

<Tr>
<En>
At 10:05 you notice the production database URL (with password) was pushed to a public GitHub repo at 09:40. Write your response, in order.
</En>
<Ur>
10:05 par aap dekhte hain ke production database URL (password samet) 09:40 par public GitHub repo me push hua tha. Tarteeb se apna jawab likhein.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

1. **Rotate first**: create a new database password (or a new user), update it in the secret manager, redeploy so the app uses it, then **revoke** the old password. Assume it's already been used.
2. **Check for misuse**: database logs for connections from unknown IPs since 09:40, unusual queries or exports; restrict network access to the database if it was reachable from the internet.
3. **Contain**: if there are signs of access, follow your incident process (preserve logs, assess what data was exposed, legal and notification duties).
4. **Clean up**: remove the secret from the repo history (`git filter-repo`), make the repo private if it shouldn't be public, ask GitHub support to purge cached views if needed.
5. **Prevent**: enable push protection and secret scanning, add a pre-commit hook (gitleaks), and find out why a production URL was on a laptop in the first place.

</En>
<Ur>

1. **Pehle rotate**: naya database password (ya naya user) banayen, secret manager me update karein, redeploy karein taa ke app use istemal kare, phir purana password **revoke** karein. Farz karein ke ye pehle hi istemal ho chuka.
2. **Ghalat istemal check karein**: 09:40 se na maloom IPs ke connections, ghair mamooli queries ya exports ke liye database logs; agar database internet se pohanch me tha to network rasai mehdood karein.
3. **Qaboo karein**: rasai ke nishan hon to apna incident process follow karein (logs mehfooz, kaunsa data khula andaza, qanooni aur ittila ki zimmedariyan).

<Challenge title="Design secrets for a three-environment app">

<Tr>
<En>
An app has development, staging and production, uses PostgreSQL, a payment provider and an email provider, and deploys with GitHub Actions to a cloud platform. Describe where each environment's secrets live, how CI gets access, and how you'd rotate the database password quarterly.
</En>
<Ur>
Ek app ke development, staging aur production hain, PostgreSQL, payment provider aur email provider istemal karti hai, aur GitHub Actions se cloud platform par deploy hoti hai. Batayen har mahol ke secrets kahan rehte hain, CI ko rasai kaise milti hai, aur aap har teen mahine database password kaise rotate karenge.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

- **Development**: each developer's `.env` with **test-mode** provider keys and a local database; `.env.example` committed. No production secrets on laptops.
- **Staging and production**: separate secret entries in the cloud secret manager (`shop/staging`, `shop/prod`), separate provider accounts or keys, separate database users with least privilege.
- **CI**: GitHub Actions authenticates to the cloud with **OIDC** (no stored cloud keys) using a role allowed to deploy and read only that environment's secrets; GitHub "environments" require approval for production.
- **Runtime**: the platform injects secrets as env vars or mounted files; the app validates them at startup.
- **Quarterly DB rotation**: create a new password (or a second user), store it as the new version in the secret manager, roll the app instances so they pick it up, confirm no connections use the old credential, then disable it. Many secret managers automate this with rotation functions.

</En>

<DeepDive title="More about secrets management">

**Dynamic secrets.** Vault and cloud IAM can issue credentials that exist only for minutes (database users, cloud roles), so there's nothing long-lived to leak.

**Workload identity.** Instead of API keys, services on AWS, GCP and Azure get credentials from their environment (IAM roles, service accounts); CI uses OIDC to assume roles.

**Encrypted files in git.** SOPS or git-crypt encrypt secret files with keys held in KMS, useful for GitOps; access to decrypt is still managed centrally.

**Kubernetes Secrets.** Base64 is not encryption; enable encryption at rest and prefer external secret operators that sync from a secret manager.

**Detection.** gitleaks, trufflehog, GitHub secret scanning with push protection, and pre-commit hooks catch most leaks before or right after they happen.

**Memory and dumps.** Secrets in process memory can appear in crash dumps and heap snapshots; restrict who can collect those in production.

</DeepDive>

<DeepDive title="Real world: the key in a mobile app">

A startup shipped a mobile app that called a third-party SMS API directly, with the API key embedded in the app bundle. Within weeks, someone extracted the key from the app package and used it to send hundreds of thousands of spam messages, leaving the startup with a five-figure bill and a suspended SMS account.

The fixes:

1. The key was rotated and moved to the backend; the app now calls the startup's own API, which sends SMS after checking the user and applying rate limits.
2. A spending cap and usage alerts were set on the SMS provider account.
3. A rule: anything shipped to clients (mobile apps, browser JavaScript) is public, and only keys designed to be public may go there.
4. Secret scanning on all repositories, including the mobile app's.

</DeepDive>

<DeepDive title="Security lens">

- **Assume leaks will happen**: design for quick rotation and limited blast radius.
- **Audit access**: secret managers log who read which secret; review unusual reads.
- **Separate environments completely**: a staging leak must never unlock production.
- **Protect the pipeline**: CI systems hold powerful credentials; restrict who can change workflows and which branches can deploy.
- **Spending limits and alerts** on paid APIs turn a leaked key into a notification instead of a huge bill.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How should an application manage secrets?">
Keep them out of source code, load them from the environment or a secret manager at runtime, validate them at startup, give each service least-privilege credentials, never log them, and support rotation.
</QA>

<QA q="A secret was committed to git. What do you do?">
Rotate and revoke it immediately, check for misuse, then clean the history if needed and add scanning and push protection. Removing it from the latest commit alone does nothing, because history and clones keep it.
</QA>

<QA q="Are environment variables secure?">
They're a reasonable delivery mechanism, better than code, but they can leak through logs, crash reports, child processes and debugging endpoints. Combine them with a secret manager, redaction and least privilege, or use mounted files and workload identity.
</QA>

<QA q="How do you rotate a secret without downtime?">
Support two valid values for a period: add the new secret, switch producers to it, keep accepting the old one until everyone has switched, then revoke the old one.
</QA>

<QA q="Why can't frontend code hold secrets?">
Everything shipped to the browser or a mobile app can be read by users. Only publishable keys meant to be public may be used there; secret operations must go through your backend.
</QA>

</DeepDive>
