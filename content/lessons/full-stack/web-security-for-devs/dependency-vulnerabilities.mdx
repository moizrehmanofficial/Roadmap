<BigIdea>
<Tr>
<En>
A typical Node.js app has a few dozen direct dependencies and **hundreds or thousands of transitive ones**. That makes dependencies the biggest part of your attack surface, and **Software Supply Chain Failures** is #3 in the OWASP Top 10 2025. There are two kinds of risk. **Known vulnerabilities**: an honest package has a bug with a published advisory (prototype pollution, ReDoS, path traversal…); tools like **`npm audit`**, Dependabot or Renovate compare your installed versions with advisory databases, and the fix is usually **upgrading**. **Malicious or compromised packages**: typosquats (`expresss`), hijacked maintainer accounts, or packages whose **install scripts** steal tokens the moment you run `npm install`. Defenses: commit the **lockfile** and install with **`npm ci`** (exact versions, verified **integrity hashes**), keep dependencies few and maintained, update regularly with automated pull requests, run **`npm audit`** in CI, be careful with install scripts (`--ignore-scripts` where possible), protect publishing accounts with 2FA, and check new packages before adding them.
</En>
<Ur>
Aam Node.js app ki chand darjan seedhi dependencies aur **saikron ya hazaron transitive** hoti hain. Is se dependencies aap ke hamle ki satah ka sab se bara hissa ban jati hain, aur **Software Supply Chain Failures** OWASP Top 10 2025 me #3 hai. Khatre do qism ke hain. **Maloom kamzoriyan**: kisi imandar package me bug hai jis ki advisory shaya ho chuki (prototype pollution, ReDoS, path traversal…); **`npm audit`**, Dependabot ya Renovate jaise tools aap ke installed versions ko advisory databases se milate hain, aur hal aam taur par **upgrade** hai. **Bad-niyat ya hack shuda packages**: typosquats (`expresss`), chhine gaye maintainer accounts, ya aise packages jin ke **install scripts** `npm install` chalate hi tokens chura lete hain. Bachao: **lockfile** commit karein aur **`npm ci`** se install karein (theek versions, tasdeeq shuda **integrity hashes**), dependencies kam aur maintained rakhein, khud-kaar pull requests se baqaidagi se update karein, CI me **`npm audit`** chalayen, install scripts ke saath ehtiyat (jahan mumkin `--ignore-scripts`), publish accounts ko 2FA se bachayen, aur naye packages jorne se pehle jaanch karein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **restaurant kitchen and its suppliers**.

- You cook carefully, but your ingredients come from dozens of suppliers, and their suppliers. A **recall notice** for a batch of flour (an advisory) means you check your shelves and replace that batch (npm audit, upgrade).
- Some risks aren't mistakes: a fake supplier with a name one letter off (typosquatting), or a real supplier whose van was hijacked (compromised maintainer account).
- The **delivery note** lists each item with a tamper-proof seal number (lockfile integrity hashes); if the seal on a box doesn't match the note, you refuse the box (`npm ci` fails).
- And you don't let a new supplier's delivery driver wander into your office with access to the safe (install scripts running with your user's permissions).

</En>
<Ur>

**Restaurant ki kitchen aur us ke suppliers** socheyn.

- Aap ehtiyat se pakate hain, magar aap ke ajza darjanon suppliers, aur un ke suppliers, se aate hain. Aate ki ek batch ka **recall notice** (advisory) ka matlab aap apni shelves check kar ke woh batch badalte hain (npm audit, upgrade).
- Kuch khatre ghaltiyan nahi: ek harf ke farq wale naam ka nakli supplier (typosquatting), ya asli supplier jis ki gaari chheen li gayi (hack shuda maintainer account).
- **Delivery note** har cheez ko tamper-proof seal number ke saath darj karta hai (lockfile integrity hashes); agar dabbe ki seal note se mel na khaye to aap dabba wapas karte hain (`npm ci` nakam).
- Aur aap naye supplier ke driver ko tijori ki rasai ke saath apne daftar me ghoomne nahi dete (install scripts aap ke user ki ijazaton ke saath chalte hue).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="A known vulnerability: exploit, audit, upgrade">

<Tr>
<En>
An app installs **lodash 4.17.4** (an old version) and uses `_.merge` to combine default settings with user JSON, a very common pattern. The user JSON contains a `__proto__` key. We run the app, ask `npm audit` what it knows, run `npm audit fix`, and run the app again.
</En>
<Ur>
Ek app **lodash 4.17.4** (purana version) install karti hai aur default settings ko user JSON se milane ke liye `_.merge` istemal karti hai, jo bohot aam pattern hai. User JSON me `__proto__` key hai. Hum app chalate hain, `npm audit` se poochhte hain ke woh kya janta hai, `npm audit fix` chalate hain, aur app dobara chalate hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install lodash@4.17.4 --silent
cat > app.js <<'EOF'
import _ from 'lodash';
// A settings endpoint merges user JSON into defaults (a very common pattern)
const defaults = { theme: 'light', notifications: true };
const userInput = JSON.parse('{ "theme": "dark", "__proto__": { "isAdmin": true } }');
const settings = _.merge({}, defaults, userInput);
const someOtherUser = {};                       // a brand-new, unrelated object
console.log(`lodash ${_.VERSION}: settings.theme = ${settings.theme}, {}.isAdmin = ${someOtherUser.isAdmin}`);
EOF
echo "--- 1. the app with an old lodash"
node app.js
echo "--- 2. npm audit compares installed versions with the advisory database"
npm audit --json > audit.json
node -e "
const a = JSON.parse(require('fs').readFileSync('audit.json'));
const l = a.vulnerabilities.lodash;
console.log('lodash severity:', l.severity, '| prototype pollution advisory:', l.via.some((v) => /Prototype Pollution/.test(v.title)), '| fix available:', Boolean(l.fixAvailable));
"
echo "--- 3. npm audit fix upgrades within the allowed semver range"
npm audit fix --silent > /dev/null 2>&1
echo "installed now: lodash $(node -p "require('lodash/package.json').version")"
npm audit --audit-level=low > /dev/null && echo "npm audit: no known vulnerabilities"
node app.js
```

```text output
--- 1. the app with an old lodash
lodash 4.17.4: settings.theme = dark, {}.isAdmin = true
--- 2. npm audit compares installed versions with the advisory database
lodash severity: critical | prototype pollution advisory: true | fix available: true
--- 3. npm audit fix upgrades within the allowed semver range
installed now: lodash 4.18.1
npm audit: no known vulnerabilities
lodash 4.18.1: settings.theme = dark, {}.isAdmin = undefined
```

<Happened>
<Tr>
<En>

- With the old lodash, merging the user's JSON wrote `isAdmin: true` onto **`Object.prototype`**, so a brand-new, unrelated object `{}` suddenly had `isAdmin === true`. Any code like `if (user.isAdmin)` on an object without its own `isAdmin` would now pass: **prototype pollution**, a real advisory for this version.
- `npm audit` matched the installed version against the advisory database and reported lodash as **critical**, including a prototype pollution advisory, with a fix available. It doesn't scan your code; it checks versions, so it also flags issues in functions you might not use.
- `npm audit fix` upgraded lodash within the allowed range (`^4.17.4` permits newer 4.x versions), and a new audit reported nothing. The same app no longer pollutes the prototype.
- When the fix needs a **major** version, `npm audit fix` won't apply it automatically (`npm audit fix --force` would, at the risk of breaking changes); then upgrade deliberately with tests. For a vulnerable **transitive** package, update its parent or use `overrides`.

</En>
<Ur>

- Purane lodash ke saath user ka JSON milane ne **`Object.prototype`** par `isAdmin: true` likh diya, isliye bilkul naya, be-taalluq object `{}` achanak `isAdmin === true` rakhne laga. Jis object ka apna `isAdmin` na ho us par `if (user.isAdmin)` jaisa koi bhi code ab guzar jata: **prototype pollution**, is version ki asli advisory.
- `npm audit` ne installed version ko advisory database se milaya aur lodash ko **critical** bataya, prototype pollution advisory samet, fix mojood hone ke saath. Ye aap ka code scan nahi karta; versions check karta hai, isliye un functions ke masle bhi batata hai jo shayad aap istemal na karte hon.
- `npm audit fix` ne ijazat shuda range ke andar lodash upgrade kiya (`^4.17.4` naye 4.x versions ki ijazat deta hai), aur naye audit ne kuch nahi bataya. Wahi app ab prototype pollute nahi karti.
- Jab fix ko **major** version chahiye ho, `npm audit fix` use khud nahi lagata (`npm audit fix --force` lagata, breaking changes ke khatre ke saath); phir tests ke saath soch samajh kar upgrade karein. Kamzor **transitive** package ke liye us ka parent update karein ya `overrides` lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Supply chain: install scripts and lockfile integrity">

<Tr>
<En>
We build a local package, `color-helper-pro`, whose `postinstall` script looks for environment variables with names like KEY or TOKEN and writes their names to a file (real malware would send names **and values** to a server). We install it in a shell that has two secrets, then again with `--ignore-scripts`. Finally we simulate a swapped package by changing lodash's integrity hash in the lockfile and run `npm ci`.
</En>
<Ur>
Hum ek local package `color-helper-pro` banate hain jis ka `postinstall` script KEY ya TOKEN jaise naamon wale environment variables dhoondta aur un ke naam file me likhta hai (asli malware naam **aur qeematen** server ko bhejta). Hum ise do secrets wale shell me install karte hain, phir `--ignore-scripts` ke saath. Aakhir me lockfile me lodash ka integrity hash badal kar badle hue package ki naqal karte aur `npm ci` chalate hain.
</Ur>
</Tr>

```bash
# A package from "a stranger" with an install script (malicious packages often work exactly like this)
mkdir -p evil-pkg && cat > evil-pkg/package.json <<'EOF'
{ "name": "color-helper-pro", "version": "1.0.0", "scripts": { "postinstall": "node collect.js" } }
EOF
cat > evil-pkg/collect.js <<'EOF'
// Runs automatically on npm install, with YOUR user's permissions
const found = Object.keys(process.env).filter((k) => /KEY|TOKEN|SECRET|PASSWORD/.test(k)).sort();
require('fs').writeFileSync(require('path').join(process.env.INIT_CWD, 'stolen.txt'), `would send: ${found.join(', ')}\n`);
EOF
(cd evil-pkg && npm pack --silent > /dev/null)
demo_env() { env -i PATH="$PATH" HOME="$HOME" PAYMENTS_KEY=acme_test_123 GITHUB_TOKEN=ghp_fake_for_demo "$@"; }   # a developer shell with two secrets
echo "--- 1. a normal install runs the package's postinstall script"
rm -f stolen.txt; demo_env npm install ./evil-pkg/color-helper-pro-1.0.0.tgz --silent
cat stolen.txt 2> /dev/null || echo "(nothing written)"
echo "--- 2. with --ignore-scripts it doesn't run"
npm uninstall color-helper-pro --silent; rm -f stolen.txt
demo_env npm install ./evil-pkg/color-helper-pro-1.0.0.tgz --ignore-scripts --silent
cat stolen.txt 2> /dev/null || echo "(nothing written)"
npm uninstall color-helper-pro --silent

echo "--- 3. the lockfile pins exact versions AND content hashes; npm ci refuses tampered packages"
node -e "
const fs = require('fs'); const lock = JSON.parse(fs.readFileSync('package-lock.json'));
console.log('lockfile pins lodash', lock.packages['node_modules/lodash'].version, 'with integrity', lock.packages['node_modules/lodash'].integrity.slice(0, 15) + '…');
lock.packages['node_modules/lodash'].integrity = 'sha512-' + Buffer.alloc(64).toString('base64');   // simulate a swapped package
fs.writeFileSync('package-lock.json', JSON.stringify(lock, null, 2));
"
npm ci > ci.log 2>&1; echo "npm ci exit code: $?"
grep -oE 'code EINTEGRITY|integrity checksum failed' ci.log | sort -u
```

```text output
--- 1. a normal install runs the package's postinstall script
would send: GITHUB_TOKEN, PAYMENTS_KEY
--- 2. with --ignore-scripts it doesn't run
(nothing written)
--- 3. the lockfile pins exact versions AND content hashes; npm ci refuses tampered packages
lockfile pins lodash 4.18.1 with integrity sha512-dMInicTP…
npm ci exit code: 1
code EINTEGRITY
integrity checksum failed
```

<Happened>
<Tr>
<En>

- A plain `npm install` ran the **postinstall** script immediately, with your user's permissions, and it found **GITHUB_TOKEN** and **PAYMENTS_KEY**. Real attacks have used exactly this to steal npm, GitHub and cloud tokens from developer machines and CI, then publish more infected packages.
- With `--ignore-scripts`, nothing ran. Setting `ignore-scripts=true` in `.npmrc` (especially in CI) blocks this whole class; for the few packages that need a build step (native modules), run their scripts explicitly or use prebuilt binaries.
- The lockfile records each package's **exact version and SHA-512 hash**. When the hash no longer matched the downloaded tarball, `npm ci` stopped with **EINTEGRITY** and a non-zero exit code: a package changed on the way (or in a compromised mirror) can't sneak in. That's why you commit the lockfile and use `npm ci` in CI and deployments.
- Integrity protects against **tampering after** the version was locked; it can't tell you a version was malicious from the start. That's what careful updates, audits, provenance and limited scripts are for.

</En>
<Ur>

- Saade `npm install` ne aap ke user ki ijazaton ke saath foran **postinstall** script chalaya, aur us ne **GITHUB_TOKEN** aur **PAYMENTS_KEY** dhoond liye. Asli hamle bilkul isi se developer machines aur CI se npm, GitHub aur cloud tokens chura kar mazeed infected packages publish kar chuke hain.
- `--ignore-scripts` ke saath kuch nahi chala. `.npmrc` me `ignore-scripts=true` (khaas kar CI me) ye poori qism rokta hai; build qadam wale chand packages (native modules) ke scripts wazeh tor par chalayen ya prebuilt binaries lein.
- Lockfile har package ka **theek version aur SHA-512 hash** darj karti hai. Jab hash download kiye tarball se mel nahi khaya, `npm ci` **EINTEGRITY** aur non-zero exit code ke saath ruk gaya: raste me (ya hack shuda mirror me) badla package andar nahi ghus sakta. Isi liye lockfile commit karte aur CI aur deployments me `npm ci` istemal karte hain.
- Integrity version lock hone ke **baad ki chhed-chhaar** se bachati hai; ye nahi bata sakti ke version shuru se bad-niyat tha. Us ke liye ehtiyat wale updates, audits, provenance aur mehdood scripts hain.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Ignoring audit output forever">

```text
npm install … found 37 vulnerabilities (4 critical)
# "it's always like that", nobody reads it, CI doesn't check
```

</Bad>
<Good title="Fail CI on serious issues, fix or document the rest">

```text
- run: npm ci
- run: npm audit --audit-level=high       # fails the build on high/critical
# Dependabot/Renovate opens weekly update PRs; exceptions are documented with a reason and a review date
```

</Good>
</Compare>

<Compare>
<Bad title="Installing whatever looks right">

```text
npm install expresss          # typo: a squatted package
npm install left-pad-plus     # 3 downloads, no repo, postinstall script, published yesterday
```

</Bad>
<Good title="Check before you add">

```text
npm view left-pad-plus repository maintainers time scripts   # repo? maintainers? age? install scripts?
# prefer well-maintained packages, or write 10 lines yourself
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Not committing the lockfile**, or using `npm install` in CI: builds get different versions each time.
- **`npm audit fix --force` blindly**: major upgrades can break things; run tests and read changelogs.
- **Pinning forever**: never updating means a huge, risky upgrade when a critical fix arrives.
- **Powerful tokens in CI** available to every step, including dependency install scripts.
- **Publishing without 2FA**: hijacked maintainer accounts are a main source of malicious versions.
- **Forgetting other ecosystems**: Docker base images, GitHub Actions and system packages need updates too.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Lockfile commit na karna**, ya CI me `npm install`: har build ko mukhtalif versions milte hain.
- **Andha dhund `npm audit fix --force`**: major upgrades cheezen tor sakte hain; tests chalayen aur changelogs parhein.
- **Hamesha pin rakhna**: kabhi update na karna matlab critical fix aane par bara, khatarnak upgrade.
- **CI me taqatwar tokens** har qadam ke liye, dependency install scripts samet.
- **Bina 2FA publish karna**: chhine gaye maintainer accounts bad-niyat versions ka bara zariya hain.
- **Doosre ecosystems bhoolna**: Docker base images, GitHub Actions aur system packages ko bhi updates chahiye.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Fix a transitive vulnerability">

<Tr>
<En>
`npm audit` reports a high-severity advisory in `semver` 7.5.1, used by a build tool you depend on; the tool's latest version still depends on `semver@~7.5.1`. Describe how you find why it's installed, fix it today, and make sure it stays fixed.
</En>
<Ur>
`npm audit` `semver` 7.5.1 me high-severity advisory batata hai, jo aap ki dependency wala build tool istemal karta hai; tool ka taaza version ab bhi `semver@~7.5.1` par munhasir hai. Batayen kaise pata karenge ye kyun installed hai, aaj kaise theek karenge, aur kaise yaqeeni banayenge ke theek rahe.
</Ur>
</Tr>

<Solution>

<Tr>
<En>

1. `npm explain semver` (or `npm ls semver`) shows the chain: `your-app → build-tool → semver@7.5.1`.
2. Check the advisory: which versions are fixed (for example 7.5.2+) and whether the fix is a patch, so it's compatible.
3. Add to package.json: `"overrides": { "semver": "^7.5.4" }`, run `npm install`, and confirm with `npm ls semver` and `npm audit`.
4. Run the full test suite and build, because you're overriding what the tool asked for.
5. Open an issue or PR on the build tool to update its range, and add a comment next to the override with the advisory id so you can remove it later.
6. Keep `npm audit --audit-level=high` in CI so a regression fails the build.

</En>
<Ur>

1. `npm explain semver` (ya `npm ls semver`) silsila dikhata hai: `your-app → build-tool → semver@7.5.1`.
2. Advisory check karein: kaunse versions theek hain (maslan 7.5.2+) aur kya fix patch hai, taa ke mutabiqat rahe.
3. package.json me jorein: `"overrides": { "semver": "^7.5.4" }`, `npm install` chalayen, aur `npm ls semver` aur `npm audit` se tasdeeq karein.

<DeepDive title="More about dependency security">

**Reachability.** Tools like Snyk, Socket, or GitHub's code scanning can tell whether your code actually calls the vulnerable function, helping prioritize.

**Behavioral analysis.** Socket and similar services flag packages that add install scripts, network access or obfuscated code in a new version, which catches malicious releases that advisories don't cover yet.

**Provenance and signatures.** npm supports provenance attestations linking a package to its source repo and CI build; `npm audit signatures` verifies them.

**Prototype pollution defense.** Use `Object.create(null)` or `Map` for user-keyed data, reject `__proto__`, `constructor` and `prototype` keys in parsers, and freeze prototypes in sensitive services (`node --frozen-intrinsics` is experimental).

**SBOMs.** `npm sbom --sbom-format cyclonedx` generates a bill of materials you can scan and share.

**Other package managers.** pnpm doesn't run dependency install scripts by default in recent versions (they must be allowed), and Yarn has similar controls.

</DeepDive>

<DeepDive title="Real world: the package that stole tokens on install">

In 2025, attackers phished the maintainers of several widely used npm packages and published new versions containing code that, on install, searched developer machines and CI runners for npm, GitHub and cloud tokens, then used stolen npm tokens to publish infected versions of the victims' own packages, spreading further. Projects that pulled the new versions within hours, through ranges like `^1.2.0` and fresh installs, ran the code.

What teams that weren't affected had in common:

1. Lockfiles committed and `npm ci` in CI, so new versions only arrived through reviewed update PRs.
2. A short delay before adopting new releases (Renovate's "minimum release age"), giving the ecosystem time to spot malicious versions.
3. Install scripts disabled in CI, and no long-lived tokens available to the install step.
4. 2FA (and trusted publishing from CI) on their own npm accounts, so stolen tokens couldn't publish.

</DeepDive>

<DeepDive title="Security lens">

- **Least privilege for builds**: separate test and deploy jobs; short-lived credentials via OIDC.
- **Pin and verify**: lockfiles, integrity hashes, and GitHub Actions pinned to commit SHAs.
- **Respond quickly**: know how to find every project using a package (`npm ls` across repos, SBOMs) when an advisory drops.
- **Minimize**: fewer dependencies mean fewer advisories, faster installs and smaller attack surface.
- **Watch your own packages**: if you publish, use 2FA, trusted publishing and provenance.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you manage vulnerabilities in dependencies?">
Commit lockfiles, run npm audit or a scanner in CI with a severity threshold, keep dependencies updated with Dependabot or Renovate, fix transitive issues by updating parents or using overrides, and prioritize by severity and reachability.
</QA>

<QA q="What is a software supply chain attack?">
Compromising software through its dependencies or build process, such as publishing a malicious package version, typosquatting, hijacking maintainer accounts or tampering with CI, so victims run the attacker's code when they install or build.
</QA>

<QA q="Why use npm ci instead of npm install in CI?">
npm ci installs exactly what the lockfile specifies, verifies integrity hashes, fails if package.json and the lockfile disagree, and starts from a clean node_modules, giving reproducible and tamper-resistant builds.
</QA>

<QA q="What is prototype pollution?">
A JavaScript vulnerability where attacker-controlled keys like __proto__ modify Object.prototype, adding properties to every object and potentially bypassing checks or causing crashes or code execution.
</QA>

<QA q="Why are install scripts risky?">
They run automatically during installation with the user's permissions, so a malicious or compromised package can read files and environment variables, steal tokens and change the system before any code is reviewed.
</QA>

</DeepDive>
