<BigIdea>
<Tr>
<En>
An upload form is an invitation for **anyone to store content on your server and get it served back to other users**. Everything the client sends can be a lie: the **file name** (it can contain `../`, collide with another user's file, or end in `.html`), the **Content-Type** header ("image/png" for a script), and even the extension. Real risks: an uploaded **HTML or SVG** file served from your domain is **stored XSS**; a predictable name lets one user **overwrite** another's file; files with no size limit **fill your disk** or memory; files saved inside the web root or a code folder can be **executed**; and image or document parsers have had exploitable bugs. The secure recipe: **limit size and count**, detect the type from the **file's bytes** and accept only an **allowlist** (PNG, JPEG, WebP, PDF…), **generate your own random names**, store files **outside the web root** (or in object storage like S3), serve them with the right `Content-Type`, `X-Content-Type-Options: nosniff` and, for anything not an image, `Content-Disposition: attachment` or a separate domain. For extra safety, **re-encode images** and **scan** files.
</En>
<Ur>
Upload form **har kisi ko aap ke server par content rakhne aur use doosre users ko wapas dilwane** ki dawat hai. Client jo kuch bhejta hai woh jhoot ho sakta hai: **file ka naam** (is me `../` ho sakta hai, kisi aur user ki file se takra sakta hai, ya `.html` par khatam ho sakta hai), **Content-Type** header (script ke liye "image/png"), aur extension bhi. Asli khatre: aap ke domain se serve hone wali upload ki gayi **HTML ya SVG** file **stored XSS** hai; andaza lagane layak naam ek user ko doosre ki file **overwrite** karne deta hai; bina size had wali files **disk** ya memory **bhar deti hain**; web root ya code folder me save files **chal** sakti hain; aur image ya document parsers me istemal hone wale bugs rahe hain. Mehfooz nuskha: **size aur ginti mehdood** karein, qism **file ke bytes** se pehchanein aur sirf **allowlist** (PNG, JPEG, WebP, PDF…) qubool karein, **apne random naam banayen**, files **web root ke bahar** (ya S3 jaisi object storage me) rakhein, unhe sahi `Content-Type`, `X-Content-Type-Options: nosniff` aur, jo image na ho us ke liye, `Content-Disposition: attachment` ya alag domain ke saath serve karein. Extra hifazat ke liye **images re-encode** karein aur files **scan** karein.
</Ur>
</Tr>

| Parser exploits | malicious image or PDF | re-encode images (sharp), keep libraries updated, scan |

## Picture it

<Tr>
<En>

Think of a **coat check that also accepts parcels**.

- A careless attendant takes any parcel, writes the **customer's own label** on the shelf, and hands parcels to anyone who reads a label aloud. Someone labels their parcel "Jane's coat" and Jane walks away with it (overwrite); someone drops a ticking box in the public display case (HTML served from your site); someone hands in a wardrobe (no size limit).
- A careful attendant **weighs** parcels first (size limit), **opens and checks** what's inside, ignoring the label (magic bytes), accepts only coats, bags and umbrellas (allowlist), puts the house's own **numbered tag** on each (random names), keeps them in the **back room**, not the display case (outside the web root), and hands them back in a sealed bag (safe headers).

</En>
<Ur>

**Coat check** socheyn jo parcels bhi leta hai.

- Lapparwah attendant har parcel le leta hai, shelf par **customer ka apna label** likh deta hai, aur jo bhi label parh kar sunaye use parcel de deta hai. Koi apne parcel par "Jane's coat" likhta hai aur Jane woh le kar chali jati hai (overwrite); koi tick tick karta dabba public display case me rakh deta hai (aap ki site se serve hone wala HTML); koi poori almari jama karata hai (size had nahi).
- Ehtiyat wala attendant pehle parcel **tolta** hai (size had), label nazar andaz kar ke **khol kar dekhta** hai andar kya hai (magic bytes), sirf coats, bags aur chhatriyan leta hai (allowlist), har ek par ghar ka apna **number wala tag** lagata hai (random naam), unhe display case ke bajaye **pichle kamre** me rakhta hai (web root ke bahar), aur band thaile me wapas deta hai (mehfooz headers).

## Learn it step by step

<Walkthrough>

<Step title="Attack a quick-and-dirty upload">

<Tr>
<En>
`unsafe.js` is an avatar upload written the quick way: multer saves files to `public/uploads` under the **client's file name**, and `express.static` serves that folder. `attack.sh` uploads a real 1×1 PNG as Jane, then an HTML file with a script, an SVG with a script, a different file also named `cat.png`, and a 30 MB file, and checks how each is served.
</En>
<Ur>
`unsafe.js` jaldi me likha avatar upload hai: multer files ko **client ke file naam** se `public/uploads` me save karta hai, aur `express.static` woh folder serve karta hai. `attack.sh` Jane ki tarah asli 1×1 PNG upload karta hai, phir script wali HTML file, script wali SVG, `cat.png` naam ki ek doosri file, aur 30 MB ki file, aur check karta hai ke har ek kaise serve hoti hai.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 multer@2.5.0 file-type@22.3.0 --silent
cat > unsafe.js <<'EOF'
// An avatar upload done the quick way
import express from 'express';
import multer from 'multer';
const upload = multer({ storage: multer.diskStorage({
  destination: 'public/uploads',
  filename: (req, file, cb) => cb(null, file.originalname),        // trusts the client's file name
}) });
const app = express();
app.use(express.static('public'));                                  // uploads are served from the site itself
app.post('/avatar', upload.single('avatar'), (req, res) => res.json({ url: `/uploads/${req.file.filename}`, size: req.file.size }));
app.listen(3000);
EOF

printf '<script>fetch("/steal?c="+document.cookie)</script>' > evil.html                                # HTML with a script
printf '<svg xmlns="http://www.w3.org/2000/svg"><script>alert(document.domain)</script></svg>' > logo.svg
```

<Happened>
<Tr>
<En>

- The HTML "avatar" was accepted and served back as **`text/html`** from your own origin. Anyone who opens that link runs the attacker's script with their session on your site: stored XSS through the upload form.
- The SVG was served as **`image/svg+xml`**. SVG is XML that can contain `<script>`; opened directly, it runs too. That's why SVG shouldn't be in an upload allowlist unless you sanitize it or serve it from another domain.

- The **30 MB** file was accepted with no limit. A loop of such uploads fills the disk; `memoryStorage` without limits would fill RAM instead.

</En>
<Ur>

- HTML "avatar" qubool hua aur aap ke apne origin se **`text/html`** ki tarah wapas serve hua. Jo bhi woh link khole, aap ki site par apne session ke saath hamla awar ka script chalata hai: upload form ke zariye stored XSS.
- SVG **`image/svg+xml`** ki tarah serve hui. SVG XML hai jis me `<script>` ho sakta hai; seedha kholne par ye bhi chalta hai. Isi liye SVG upload allowlist me nahi honi chahiye jab tak aap use sanitize na karein ya doosre domain se serve na karein.
- `cat.png` naam ki doosri file ne **Jane ka avatar** hamla awar ke content se **badal diya**, kyunke server ne client ka naam istemal kiya. (multer ke neeche busboy default me naamon se `../` jaise directory hisse hata deta hai, magar is par bharosa na karein: client ke naam paths me kabhi na lein.)
- **30 MB** file bina had ke qubool hui. Aisi uploads ka loop disk bhar deta hai; bina had ke `memoryStorage` is ke bajaye RAM bhar deta.

</Ur>

<Step title="A secure upload: limits, real types, own names, safe serving">

<Tr>
<En>
`safe.js` keeps the file in memory with a **2 MB limit**, checks its **magic bytes** with `file-type` against an allowlist of PNG, JPEG and WebP, saves it under a **random UUID** in `storage/avatars` (outside `public/`), and serves it through a route that validates the id and sends `nosniff` plus a sandboxing CSP. Multer's size error becomes a clear **413**. The same attack script runs; UUIDs are replaced with `<uuid>` in the output.
</En>
<Ur>
`safe.js` file ko **2 MB had** ke saath memory me rakhta hai, `file-type` se us ke **magic bytes** ko PNG, JPEG aur WebP ki allowlist se check karta hai, use `storage/avatars` (`public/` ke bahar) me **random UUID** ke naam se save karta hai, aur aise route se serve karta hai jo id validate kar ke `nosniff` plus sandboxing CSP bhejta hai. Multer ka size error wazeh **413** ban jata hai. Wahi attack script chalta hai; output me UUIDs ko `<uuid>` se badla gaya hai.
</Ur>
</Tr>

```bash
cat > safe.js <<'EOF'
import express from 'express';
import multer from 'multer';
import { fileTypeFromBuffer } from 'file-type';
import { randomUUID } from 'node:crypto';
import { mkdirSync, writeFileSync, readFileSync, existsSync } from 'node:fs';
import path from 'node:path';

const DIR = path.resolve('storage/avatars');                     // NOT inside public/
mkdirSync(DIR, { recursive: true });
const ALLOWED = new Map([['image/png', 'png'], ['image/jpeg', 'jpg'], ['image/webp', 'webp']]);   // no SVG, no HTML
const upload = multer({ storage: multer.memoryStorage(), limits: { fileSize: 2 * 1024 * 1024, files: 1 } });

const app = express();
app.post('/avatar', upload.single('avatar'), async (req, res) => {
  if (!req.file) return res.status(400).json({ error: 'no file' });
  const type = await fileTypeFromBuffer(req.file.buffer);         // look at the BYTES, not the name or header
  if (!type || !ALLOWED.has(type.mime)) return res.status(415).json({ error: `not an allowed image (detected: ${type?.mime ?? 'unknown'})` });
  const id = `${randomUUID()}.${ALLOWED.get(type.mime)}`;        // our name, never the client's
  writeFileSync(path.join(DIR, id), req.file.buffer);
  res.status(201).json({ url: `/avatars/${id}`, size: req.file.size });
});
app.get('/avatars/:id', (req, res) => {
  if (!/^[0-9a-f-]{36}\.(png|jpg|webp)$/.test(req.params.id)) return res.sendStatus(404);
  const file = path.join(DIR, req.params.id);
  if (!existsSync(file)) return res.sendStatus(404);
  res.set({ 'X-Content-Type-Options': 'nosniff', 'Content-Security-Policy': "default-src 'none'; sandbox" })
     .type(path.extname(file)).send(readFileSync(file));
});
app.use((err, req, res, next) => (err instanceof multer.MulterError
  ? res.status(413).json({ error: err.code })                    // e.g. LIMIT_FILE_SIZE
  : res.status(500).json({ error: 'upload failed' })));
app.listen(3000);
EOF
node safe.js & APP=$!; sleep 1
bash attack.sh | sed -E 's/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}/<uuid>/'
kill $APP; wait $APP 2> /dev/null || true
echo "files in public/ from this server: $(find public -newer safe.js -type f | wc -l)"
```

```text output
1. Jane's normal avatar:      {"url":"/avatars/<uuid>.png","size":70}
2. HTML as an 'avatar':       {"error":"not an allowed image (detected: unknown)"}
   served back as:            (nothing stored)
3. SVG with a script:         {"error":"not an allowed image (detected: unknown)"}
   served back as:            (nothing stored)
4. attacker uploads 'cat.png': {"error":"not an allowed image (detected: unknown)"}
   Jane's avatar:             unchanged
5. a 30 MB file:              {"error":"LIMIT_FILE_SIZE"}
files in public/ from this server: 0
```

<Happened>
<Tr>
<En>

- Jane's real PNG was accepted and stored as `/avatars/<uuid>.png`: the extension comes from the **detected** type, the name from the server.
- The HTML, the SVG and the attacker's fake `cat.png` were all rejected with **"detected: unknown"**: their bytes aren't PNG, JPEG or WebP, whatever the name or header said. Nothing was stored, so nothing could be served.
- Jane's avatar stayed **unchanged**: random names mean uploads can't collide with or target existing files.
- The 30 MB upload stopped at **LIMIT_FILE_SIZE** (413) as soon as it crossed 2 MB, before it filled memory.
- Nothing was written into `public/`. Even if a dangerous file got through, the serving route sends `nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`, so the browser won't run scripts in it. In production, go further: re-encode images with `sharp` (which also strips EXIF location data), store in a private bucket, and serve user content from a separate domain.

</En>
<Ur>

- Jane ki asli PNG qubool ho kar `/avatars/<uuid>.png` ki tarah save hui: extension **pehchani gayi** qism se, naam server se.
- HTML, SVG aur hamla awar ki nakli `cat.png` sab **"detected: unknown"** ke saath rad hueen: un ke bytes PNG, JPEG ya WebP nahi, naam ya header jo bhi kahe. Kuch save nahi hua, isliye kuch serve nahi ho saka.
- Jane ka avatar **wahi raha**: random naamon ka matlab uploads mojooda files se takra ya unhe nishana nahi bana saktin.
- 30 MB upload 2 MB paar karte hi **LIMIT_FILE_SIZE** (413) par ruk gaya, memory bharne se pehle.
- `public/` me kuch nahi likha gaya. Agar koi khatarnak file guzar bhi jaye, serve karne wala route `nosniff` aur `Content-Security-Policy: default-src 'none'; sandbox` bhejta hai, isliye browser us me scripts nahi chalata. Production me aur aage jayen: `sharp` se images re-encode karein (jo EXIF location data bhi hatata hai), private bucket me rakhein, aur user content alag domain se serve karein.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Trusting the name, extension and Content-Type">

```text
if (!file.originalname.endsWith('.png') || file.mimetype !== 'image/png') reject();
// both are chosen by the client: evil.html renamed to evil.png passes
fs.writeFileSync(`uploads/${file.originalname}`, file.buffer);
```

</Bad>
<Good title="Check bytes, choose the name yourself">

```text
const type = await fileTypeFromBuffer(file.buffer);
if (!ALLOWED.has(type?.mime)) return res.status(415).end();
const key = `${randomUUID()}.${ALLOWED.get(type.mime)}`;
```

</Good>
</Compare>

<Compare>
<Bad title="Uploads in the web root, served as-is">

```text
multer({ dest: 'public/uploads' });          // no limits
app.use(express.static('public'));           // uploads served with guessed types from your origin
```

</Bad>
<Good title="Private storage, served deliberately">

```text
multer({ storage: multer.memoryStorage(), limits: { fileSize: 5 * 1024 * 1024, files: 1 } });
// store in a private bucket; serve via a route or signed URL on a separate domain,
// with Content-Type from detection, nosniff, and Content-Disposition: attachment for documents
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Allowing SVG, HTML, XML or JS** as "images" or attachments without sanitizing or a separate domain.
- **No access control on downloads**: private documents behind guessable URLs (see IDOR).
- **Processing untrusted archives** without limits: zip bombs and "zip slip" (archive entries named `../../`).
- **Keeping EXIF metadata**: photos can reveal a user's home location.
- **Running ImageMagick or PDF tools on raw uploads** with outdated versions or dangerous coders enabled.
- **Ignoring disk and storage quotas** per user.

</En>

- **SVG, HTML, XML ya JS** ko bina sanitize ya alag domain ke "images" ya attachments ke tor par ijazat dena.

<DeepDive title="More about uploads">

**Polyglot files.** A file can be a valid image and valid HTML or JavaScript at the same time; type detection alone isn't enough if you serve it with a dangerous type or from your main domain. Re-encoding destroys most polyglots.

**Image libraries.** `sharp` (libvips) is fast and safer than shelling out to ImageMagick; set `limitInputPixels` to stop decompression bombs (tiny files with huge dimensions).

**Archives.** When extracting zips, check each entry's resolved path stays inside the target folder (zip slip), and cap total uncompressed size and entry count.

**Streaming.** For large files, stream to storage instead of buffering, counting bytes as they arrive.

**Antivirus.** ClamAV, cloud malware scanning (for example for S3), or commercial APIs; scan asynchronously and quarantine until clean.

**Separate domains.** Google uses `googleusercontent.com` for user content; a different site means scripts there can't touch your cookies or DOM.

</DeepDive>

<DeepDive title="Real world: the resume that phished the HR team">

A recruiting platform let candidates upload a "resume" in any format and served the files from `careers.company.com/uploads/`. An attacker uploaded an HTML file named `resume.html` that looked like the company's internal login page. Recruiters clicking the link in the applicant tracking system saw a real company URL, entered their single sign-on passwords, and the page sent them to the attacker.

The fixes:

1. Uploads limited to PDF and DOCX, verified by magic bytes.
2. Files moved to a private bucket and served from a separate domain via signed URLs with `Content-Disposition: attachment`.
3. PDFs rendered to images for in-browser preview, so recruiters never open the raw file in the app.
4. MFA for all staff accounts, which would have limited the damage.

</DeepDive>

<DeepDive title="Security lens">

- **Authenticate and rate-limit upload endpoints**; anonymous uploads are a magnet for abuse and illegal content.
- **Authorize downloads** like any other resource: owner, tenant, role.
- **Keep parsers updated**: image, PDF, Office and archive libraries regularly get security fixes.
- **Least privilege for storage credentials**: the upload service can write to one bucket prefix, not read everything.
- **Moderation and legal obligations**: public uploads may need content scanning and takedown processes.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you secure a file upload feature?">
Authenticate and rate-limit, enforce size and count limits, verify the type from file content against an allowlist, generate random names, store outside the web root or in private object storage, serve with the correct type, nosniff and safe disposition from a separate domain, re-encode images, scan files and check access on download.
</QA>

<QA q="Why not trust the Content-Type or extension?">
Both are supplied by the client and can be set to anything. The file's bytes, checked with magic-number detection, are a better signal, and even then the file should be served safely.
</QA>

<QA q="What is the risk of serving uploads from your main domain?">
If an uploaded file is interpreted as HTML or script, it runs with your origin's privileges, enabling XSS, cookie theft and phishing on a trusted URL. A separate domain isolates it.
</QA>

<QA q="What is zip slip?">
A path traversal attack where archive entries have names like ../../app.js, so extracting them writes files outside the target directory. Prevent it by resolving each path and checking it stays inside the destination.
</QA>

<QA q="How do presigned URLs help with uploads?">
They let clients upload directly to object storage with a temporary, scoped permission, so large files skip your servers, while conditions on the URL enforce key, size and content type.
</QA>

</DeepDive>
