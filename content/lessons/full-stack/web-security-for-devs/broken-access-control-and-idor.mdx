<BigIdea>
<Tr>
<En>
**Access control** decides what an authenticated user may do; when it's **broken**, a normal user can read or change other people's data, or perform admin actions, just by editing a request. It has been #1 in the OWASP Top 10 since 2021, and in 2025 it also absorbed **SSRF**. The classic form is **IDOR** (insecure direct object reference, also called **BOLA**): `/invoices/102` returns invoice 102 to whoever asks, so counting ids leaks everyone's invoices. Others are just as common: the check exists on `GET` but not on `DELETE`; **mass assignment** copies a request body (including `"role": "admin"`) onto a record; an admin API is "protected" only because the button is hidden; and **server-side request forgery** makes your server fetch internal URLs for the attacker. The cure is boring and reliable: **check permissions on the server for every request, every method, every object**, scope queries by owner or tenant, **allowlist** which fields users can change, put role checks on whole routers, validate outbound URLs, **deny by default**, and write tests that act as the wrong user.
</En>
<Ur>
**Access control** tay karta hai ke authenticated user kya kar sakta hai; jab ye **toota** ho, to aam user sirf request badal kar doosron ka data parh ya badal sakta hai, ya admin ke kaam kar sakta hai. Ye 2021 se OWASP Top 10 me #1 hai, aur 2025 me is ne **SSRF** ko bhi apne andar le liya. Classic shakal **IDOR** (insecure direct object reference, jise **BOLA** bhi kehte hain) hai: `/invoices/102` jo bhi maange use invoice 102 de deta hai, isliye ids ginna har kisi ki invoices leak kar deta hai. Baqi bhi utni hi aam hain: check `GET` par hai magar `DELETE` par nahi; **mass assignment** request body (`"role": "admin"` samet) record par copy kar deta hai; admin API sirf is liye "mehfooz" hai ke button chhupa hai; aur **server-side request forgery** aap ke server se hamla awar ke liye andaruni URLs mangwata hai. Ilaj boring aur qabil-e-bharosa hai: **har request, har method, har object ke liye server par ijazat check karein**, queries ko malik ya tenant se scope karein, users kaunse fields badal sakte hain ki **allowlist** rakhein, poore routers par role checks lagayen, bahar jane wale URLs validate karein, **default inkaar** rakhein, aur aise tests likhein jo ghalat user ban kar chalein.
</Ur>
</Tr>
</BigIdea>

<En>

- It's the most common serious web vulnerability, and easy to exploit: no special tools, just edited requests.
- One missing check can expose every customer's data.
- Automated scanners rarely find it: they don't know which data belongs to whom.
- Leaks across users or tenants are reportable breaches with legal consequences.

<Tr>
<En>

| --- | --- | --- |
| **Access control** | Enforcing what users may do | ownership, roles |

## Learn it step by step

<Walkthrough>

<Step title="Five ways a customer gets too much power">

<Tr>
<En>
`api.js` is a small invoice API with five classic flaws. `internal.js` plays an **internal service** that holds secrets and listens only on `127.0.0.1:3001` (like a cloud metadata endpoint or an internal admin tool). `attack.js` is Jane, a normal customer (user 1), trying: counting invoice ids, deleting John's invoice, calling the admin API directly, adding `"role": "admin"` to a profile update, and asking the preview feature to fetch the internal URL.
</En>
<Ur>
`api.js` paanch classic khamiyon wali chhoti invoice API hai. `internal.js` ek **andaruni service** ka kirdar ada karta hai jo raaz rakhti hai aur sirf `127.0.0.1:3001` par sunti hai (cloud metadata endpoint ya andaruni admin tool ki tarah). `attack.js` Jane hai, ek aam customer (user 1), jo aazmati hai: invoice ids ginna, John ki invoice mitana, admin API seedha bulana, profile update me `"role": "admin"` jorna, aur preview feature se andaruni URL mangwana.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install express@5.1.0 --silent
cat > internal.js <<'EOF'
// An INTERNAL service only reachable from inside the network (like a cloud metadata endpoint)
import express from 'express';
express().get('/secrets', (req, res) => res.json({ dbPassword: 'prod-db-password', awsKey: 'AKIA-EXAMPLE' })).listen(3001, '127.0.0.1');
EOF
cat > api.js <<'EOF'
// SAFE=1 turns on the fixes (next step)
import express from 'express';
const SAFE = process.env.SAFE === '1';
const users = { 1: { id: 1, name: 'Jane Doe', role: 'customer' }, 2: { id: 2, name: 'John Smith', role: 'customer' }, 3: { id: 3, name: 'Ana Lee', role: 'admin' } };
const invoices = Array.from({ length: 6 }, (_, i) => ({ id: 101 + i, ownerId: (i % 2) + 1, cents: 1000 * (i + 1) }));
const app = express();
app.use(express.json());
app.use((req, res, next) => { req.user = users[Number(req.get('x-user-id'))]; req.user ? next() : res.sendStatus(401); });   // stand-in for real auth
const requireAdmin = (req, res, next) => (req.user.role === 'admin' ? next() : res.sendStatus(403));

// 1. Object level: can this user see THIS invoice?
app.get('/invoices/:id', (req, res) => {
  const inv = invoices.find((i) => i.id === Number(req.params.id) && (!SAFE || i.ownerId === req.user.id));
  inv ? res.json(inv) : res.sendStatus(404);
});
// 2. Same resource, different method: the delete route was written later
app.delete('/invoices/:id', (req, res) => {
  const idx = invoices.findIndex((i) => i.id === Number(req.params.id) && (!SAFE || i.ownerId === req.user.id));
  if (idx < 0) return res.sendStatus(404);
  invoices.splice(idx, 1); res.sendStatus(204);
});
// 3. Mass assignment: the body is copied onto the user
app.patch('/me', (req, res) => {
  const changes = SAFE ? { name: String(req.body.name ?? req.user.name) } : req.body;       // allowlist fields
  Object.assign(req.user, changes); res.json(req.user);
});
// 4. Function level: the admin page is hidden in the UI, but is the API protected?
app.get('/admin/users', ...(SAFE ? [requireAdmin] : []), (req, res) => res.json(Object.values(users)));
// 5. SSRF (part of A01 in 2025): the server fetches any URL the user gives
app.get('/preview', async (req, res) => {
  const url = new URL(String(req.query.url));
  if (SAFE && (url.protocol !== 'https:' || ['localhost', '127.0.0.1', '0.0.0.0', '169.254.169.254'].includes(url.hostname) || /^(10|192\.168|172\.(1[6-9]|2\d|3[01]))\./.test(url.hostname)))
    return res.status(400).json({ error: 'URL not allowed' });
  try { res.type('text').send((await (await fetch(url)).text()).slice(0, 80)); } catch { res.status(502).send('fetch failed'); }
});
app.listen(3000);
EOF
cat > attack.js <<'EOF'
// Jane (user 1, a customer) probes the API
const call = async (method, path, body) => {
  const r = await fetch(`http://localhost:3000${path}`, { method, headers: { 'x-user-id': '1', 'content-type': 'application/json' }, body: body && JSON.stringify(body) });
  return { status: r.status, text: await r.text() };
};
const line = (name, bad, detail) => console.log(`${name.padEnd(36)} ${bad ? 'VULNERABLE' : 'blocked   '} ${detail}`);

let seen = [];
for (let id = 101; id <= 106; id++) if ((await call('GET', `/invoices/${id}`)).status === 200) seen.push(id);
line('read invoices by counting ids', seen.some((id) => id % 2 === 0), `readable: ${seen.join(', ')} (hers: 101, 103, 105)`);
const del = await call('DELETE', '/invoices/102');
line("delete John's invoice 102", del.status === 204, `${del.status}`);
const adm = await call('GET', '/admin/users');
line('call the admin API directly', adm.status === 200, `${adm.status}`);
const me = JSON.parse((await call('PATCH', '/me', { name: 'Jane D.', role: 'admin' })).text);
line('PATCH /me with "role": "admin"', me.role === 'admin', `role is now ${me.role}`);
const ssrf = await call('GET', '/preview?url=' + encodeURIComponent('http://127.0.0.1:3001/secrets'));
line('SSRF to an internal service', ssrf.text.includes('dbPassword'), `${ssrf.status} ${ssrf.text}`);
EOF
node internal.js & INT=$!; node api.js & API=$!; sleep 1
node attack.js
kill $API $INT; wait $API $INT 2> /dev/null || true
```

```text output
read invoices by counting ids        VULNERABLE readable: 101, 102, 103, 104, 105, 106 (hers: 101, 103, 105)
delete John's invoice 102            VULNERABLE 204
call the admin API directly          VULNERABLE 200
PATCH /me with "role": "admin"       VULNERABLE role is now admin
SSRF to an internal service          VULNERABLE 200 {"dbPassword":"prod-db-password","awsKey":"AKIA-EXAMPLE"}
```

<Happened>
<Tr>
<En>

- **IDOR**: by counting 101 to 106, Jane read **all six** invoices, including John's (102, 104, 106). Sequential ids make this trivial, but random ids only slow attackers down; the missing check is the bug.
- **Another method**: `DELETE /invoices/102` returned **204**, John's invoice is gone. The developer who wrote the delete route later didn't reuse any check.
- **Function level**: `/admin/users` returned **200** to a customer. The admin link was hidden in the UI, but the API never asked who was calling.
- **Mass assignment**: `PATCH /me` copied the whole body, so Jane made herself **admin**. Every later request she makes now passes any role check.
- **SSRF**: the preview feature fetched `http://127.0.0.1:3001/secrets` from **inside** the network and returned database and cloud credentials. On cloud servers, the same trick against `169.254.169.254` has leaked real credentials in major breaches.

</En>
<Ur>

- **IDOR**: 101 se 106 tak gin kar Jane ne **chhe ki chhe** invoices parh lin, John ki (102, 104, 106) samet. Musalsal ids ise aasan banati hain, magar random ids sirf hamla awaron ko sust karti hain; ghayab check hi bug hai.
- **Doosra method**: `DELETE /invoices/102` ne **204** diya, John ki invoice gayi. Baad me delete route likhne wale developer ne koi check dobara istemal nahi kiya.
- **Function level**: `/admin/users` ne customer ko **200** diya. Admin link UI me chhupa tha, magar API ne kabhi nahi poochha ke kaun bula raha hai.
- **Mass assignment**: `PATCH /me` ne poori body copy kar di, isliye Jane ne khud ko **admin** bana liya. Ab us ki har agli request kisi bhi role check se guzar jati hai.
- **SSRF**: preview feature ne network ke **andar** se `http://127.0.0.1:3001/secrets` mangwaya aur database aur cloud credentials lauta diye. Cloud servers par `169.254.169.254` ke khilaf yahi chaal bari breaches me asli credentials leak kar chuki hai.

</Ur>
</Tr>

<Step title="The fixes, and the same attacks again">

<Tr>
<En>
`SAFE=1` turns on five small changes: both invoice queries also require `ownerId === req.user.id`; `PATCH /me` accepts only `name`; the admin route has `requireAdmin`; and the preview rejects anything but `https:` and refuses local and private addresses. The same attack script runs, then two normal requests check that Jane can still use her account.
</En>
<Ur>
`SAFE=1` paanch chhoti tabdeeliyan on karta hai: dono invoice queries `ownerId === req.user.id` bhi maangti hain; `PATCH /me` sirf `name` qubool karta hai; admin route par `requireAdmin` hai; aur preview `https:` ke ilawa sab rad karta aur local aur private addresses se inkaar karta hai. Wahi attack script chalta hai, phir do aam requests check karti hain ke Jane ab bhi apna account istemal kar sakti hai.
</Ur>
</Tr>

```bash
node internal.js & INT=$!; SAFE=1 node api.js & API=$!; sleep 1
node attack.js
echo "--- Jane's normal use still works"
curl -s -H 'x-user-id: 1' localhost:3000/invoices/101; echo
curl -s -X PATCH -H 'x-user-id: 1' -H 'content-type: application/json' -d '{"name":"Jane D."}' localhost:3000/me; echo
kill $API $INT; wait $API $INT 2> /dev/null || true
```

delete John's invoice 102            blocked    404
call the admin API directly          blocked    403
PATCH /me with "role": "admin"       blocked    role is now customer
SSRF to an internal service          blocked    400 {"error":"URL not allowed"}

<Happened>
<Tr>
<En>

- Counting ids now returns only **101, 103, 105**, Jane's own; John's invoices answer **404**, the same as a missing one, so ids can't even be confirmed to exist.
- The delete route uses the same ownership condition: **404**. In a real codebase, put the rule in one place (a policy function or a scoped repository like `invoicesFor(user)`) so every method inherits it.
- The admin API answers **403**; protect the whole `/admin` router with one middleware so new admin routes are covered automatically.
- `"role": "admin"` was ignored: only `name` is copied, and Jane stays a **customer**. Use explicit schemas (`zod.strict()`, NestJS DTOs with `whitelist: true`) rather than copying bodies.
- The SSRF attempt got **400**. Hostname checks are only a start: attackers use redirects, DNS names that resolve to private IPs, and odd IP formats (`2130706433`). Robust SSRF defense allowlists the exact hosts you need, resolves the name and checks the IP, disables redirects, and blocks metadata endpoints at the network level (for example IMDSv2 on AWS).
- Jane's own invoice and her name change still work: good access control is invisible to legitimate users.

</En>
<Ur>

- Ids ginna ab sirf **101, 103, 105** lautata hai, Jane ki apni; John ki invoices **404** deti hain, ghayab invoice jaisa, isliye ids ka mojood hona bhi tasdeeq nahi hota.
- Delete route wahi malikana shart istemal karta hai: **404**. Asal codebase me rule ek jagah rakhein (policy function ya `invoicesFor(user)` jaisi scoped repository) taa ke har method use virsa me paye.
- Admin API **403** deti hai; poore `/admin` router ko ek middleware se mehfooz karein taa ke naye admin routes khud cover hon.
- `"role": "admin"` nazar andaz hua: sirf `name` copy hota hai, aur Jane **customer** rehti hai. Bodies copy karne ke bajaye wazeh schemas lein (`zod.strict()`, `whitelist: true` ke saath NestJS DTOs).
- SSRF koshish ko **400** mila. Hostname checks sirf shuruat hain: hamla awar redirects, private IPs par resolve hone wale DNS naam, aur ajeeb IP formats (`2130706433`) istemal karte hain. Mazboot SSRF bachao sirf zaroori hosts allowlist karta hai, naam resolve kar ke IP check karta hai, redirects band karta hai, aur network level par metadata endpoints rokta hai (maslan AWS par IMDSv2).
- Jane ki apni invoice aur naam ki tabdeeli ab bhi chalti hain: achha access control jaiz users ko nazar nahi aata.

</Ur>

## Common mistakes

<Compare>
<Bad title="Checking ownership after loading, in each route separately">

```text
app.get('/orders/:id', async (req, res) => { const o = await Orders.find(req.params.id); if (o.userId !== req.user.id) return res.sendStatus(403); res.json(o); });
app.put('/orders/:id', async (req, res) => { const o = await Orders.find(req.params.id); /* forgot the check */ await o.update(req.body); });
```

</Bad>
<Good title="Scoped data access everyone uses">

```text
const ordersFor = (user) => ({
  find: (id) => db.one('SELECT * FROM orders WHERE id = $1 AND user_id = $2', [id, user.id]),
  update: (id, changes) => db.query('UPDATE orders SET note = $1 WHERE id = $2 AND user_id = $3', [changes.note, id, user.id]),
});
// routes only ever call ordersFor(req.user)
```

</Good>
</Compare>

<Compare>
<Bad title="Trusting ids and roles from the client">

```text
POST /orders   { "userId": 2, "items": [...] }          // order created for someone else
PATCH /users/1 { "isAdmin": true }                      // copied straight into the row
```

</Bad>
<Good title="Identity from the session, fields from a schema">

```text
createOrder({ userId: req.user.id, items: OrderItems.parse(req.body.items) });
updateUser(req.user.id, z.object({ name: z.string(), avatarUrl: z.string().url() }).partial().strict().parse(req.body));
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **List endpoints without filters**: the detail page checks ownership but `/orders?status=paid` returns everyone's.
- **Returning 403 vs 404 inconsistently**: different answers for "not yours" and "doesn't exist" reveal which ids exist.
- **GraphQL resolvers** that check access on the top query but not on nested fields.
- **File URLs** (S3, uploads) that are public or guessable instead of short-lived signed URLs.
- **Caching authorized responses** under keys that don't include the user.
- **No tests as the wrong user**: almost every IDOR would be caught by one test per route.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bina filter list endpoints**: detail page malikana haq check karta hai magar `/orders?status=paid` sab ke lautata hai.
- **403 aur 404 be-tarteeb lautana**: "aap ka nahi" aur "mojood nahi" ke mukhtalif jawab batate hain kaunsi ids mojood hain.
- **GraphQL resolvers** jo upar ki query par rasai check karte hain magar nested fields par nahi.
- **File URLs** (S3, uploads) jo chhoti umar ke signed URLs ke bajaye public ya andaza hone wale hain.
- **Authorized jawabon ki caching** aisi keys par jin me user shamil nahi.
- **Ghalat user ke tests nahi**: taqreeban har IDOR har route ke ek test se pakra jata.

</Ur>
</Tr>

</Ur>

<Solution>

<Tr>
<En>

1. Accept only `https:` (maybe `http:`) and default ports; reject credentials in URLs.
2. Resolve the hostname yourself (`dns.lookup` with `all: true`) and reject if **any** address is loopback, private, link-local (`169.254.0.0/16`), multicast or IPv6 equivalents (use a tested library such as `ipaddr.js`).

4. Disable automatic redirects; if you follow one, repeat steps 1–3 for the new URL, with a small redirect limit.
5. Limit time, response size and content types; never return raw responses for errors.
6. Run the fetcher in an isolated service or network segment with no access to internal systems, and enable IMDSv2 / block the metadata IP at the firewall.

<DeepDive title="More about access control">

**OWASP API Security Top 10.** BOLA (object level) is API1, broken function level authorization and broken object property level authorization (mass assignment and excessive data exposure) are also on the list.

**Excessive data exposure.** Returning whole database rows and letting the frontend hide fields leaks data like password hashes or internal notes; select only what the client should see.

**Centralized policies.** Policy functions, CASL, OPA or Cedar keep rules in one place; row-level security in PostgreSQL adds a database safety net (see Multi-Tenant Authorization).

**Indirect references.** Using per-user references (or UUIDs) reduces enumeration but never replaces checks.

**SSRF beyond URLs.** PDF generators, image processors (ImageMagick), webhooks, XML parsers (XXE) and OAuth `redirect_uri` handling can all make servers fetch attacker-chosen URLs.

**Testing tools.** Burp Suite's Autorize extension replays requests with another user's session to find IDORs quickly (only on systems you're allowed to test).

</DeepDive>

<DeepDive title="Real world: the API that returned everyone's orders">

A food delivery startup's mobile app called `GET /api/orders/{id}`. The endpoint checked that the request had a valid token but not that the order belonged to the caller. Order ids were sequential. A researcher wrote a short script, and within an afternoon had downloaded names, addresses, phone numbers and order histories for hundreds of thousands of customers. The mobile app never showed other users' orders, so nobody had noticed.

The fixes:

1. All order queries go through a repository that always filters by the authenticated user (and by restaurant for restaurant staff).
2. An automated test suite replays every API call with a second user's token and expects 404.
3. Public ids became random, and rate limits and alerts were added for unusual numbers of 404s per user.
4. The breach was reported to the regulator and affected customers, as required by data protection law.

</DeepDive>

<DeepDive title="Security lens">

- **Authorization is a feature**: design it, review it, and test it like any other feature.
- **Watch for patterns**: one IDOR usually means the same mistake exists elsewhere; search for it.
- **Monitor**: spikes of 403/404 from one account often mean someone is probing ids.
- **Least privilege for services too**: the app's database user, cloud role and network access should limit what a successful SSRF or IDOR can reach.
- **Log access to sensitive records** so you can answer "who saw this?" after an incident.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is broken access control?">
Failures to enforce what authenticated users may do, letting them access other users' data, change fields they shouldn't, or use admin functions. It's the top OWASP risk and includes IDOR, missing function-level checks, mass assignment and, since 2025, SSRF.
</QA>

<QA q="How do you prevent IDOR?">
Check ownership or permission for every object on the server, ideally by scoping queries to the current user or tenant, use the same policy for every method, return 404 for objects the user can't access, and test with a second user.
</QA>

<QA q="What is mass assignment?">
Binding request fields directly onto a model, so attackers can set fields like role, isAdmin or ownerId. Prevent it with explicit allowlists or DTOs that only accept permitted fields.
</QA>

<QA q="What is SSRF and how do you mitigate it?">
Server-side request forgery makes your server fetch attacker-controlled URLs, reaching internal services or cloud metadata. Mitigate with host allowlists, resolving and checking IPs against private ranges, disabling redirects, network isolation and protecting metadata endpoints.
</QA>

<QA q="Are random UUIDs enough to stop IDOR?">
No. They make guessing harder, but ids leak through URLs, logs and shared links. Authorization checks are still required for every access.
</QA>

</DeepDive>
