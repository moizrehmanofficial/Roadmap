<BigIdea>
<Tr>
<En>
**Deploying** means copying your app to computers that are always on and reachable from the internet, so anyone can open it with a URL. **Vercel** is a hosting platform made by the team behind Next.js. You connect a **GitHub repository**, and from then on every `git push` makes Vercel **install, build and publish** your app automatically. Pushes to `main` update the **production** site; pushes to other branches get their own **preview** URL. Settings that differ between your laptop and the live site, such as database URLs and API keys, are **environment variables**: you keep them in `.env.local` locally (never committed to Git) and enter them in the Vercel dashboard. Variables starting with **`NEXT_PUBLIC_`** are copied into the JavaScript sent to browsers, so they must never hold secrets.
</En>
<Ur>
**Deploy** karne ka matlab hai apni app ko aise computers par copy karna jo hamesha on rehte hain aur internet se pohanch me hain, taa ke koi bhi URL se use khol sake. **Vercel** ek hosting platform hai jo Next.js banane wali team ne banaya. Aap ek **GitHub repository** jorte hain, aur us ke baad har `git push` par Vercel khud aap ki app **install, build aur publish** karta hai. `main` par push **production** site update karta hai; doosri branches par push ko apna **preview** URL milta hai. Jo settings aap ke laptop aur live site me mukhtalif hoti hain, jaise database URLs aur API keys, wo **environment variables** hain: inhe local par `.env.local` me rakhein (kabhi Git me commit nahi) aur Vercel dashboard me darj karein. **`NEXT_PUBLIC_`** se shuru hone wale variables browsers ko bheji jane wali JavaScript me copy ho jate hain, isliye un me kabhi secrets nahi hone chahiyen.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **An app nobody can open isn't finished.** Clients, employers and users need a URL.
- **Automatic deploys** remove manual steps: push code, and a minute later it's live. Fewer steps means fewer mistakes.
- **Preview URLs** let teammates and clients test a change before it reaches real users.
- **Zero server management**: no operating system updates, no web server config, HTTPS certificates added automatically, and a global CDN for speed.

</En>
<Ur>

- **Jo app koi khol na sake wo mukammal nahi.** Clients, employers aur users ko URL chahiye.
- **Khudkar deploys** haath ke qadam khatam karte hain: code push karein, ek minute baad live. Kam qadam ka matlab kam ghaltiyan.
- **Preview URLs** teammates aur clients ko asli users tak pohanchne se pehle tabdeeli test karne dete hain.
- **Server sambhalne ki zaroorat nahi**: operating system updates nahi, web server config nahi, HTTPS certificates khud lag jate hain, aur raftaar ke liye global CDN.

</Ur>

## Picture it

<Tr>
<En>

Deploying is like a **restaurant chain opening a new branch from a recipe book**.

- Your **GitHub repo** is the recipe book. It holds the recipes (code), but **not** the safe's combination (secrets).
- **Vercel** is the head office's kitchen team. Every time the recipe book changes, they cook everything fresh (**build**) and send the dishes to branches worldwide (the **CDN**).
- The safe's combination is given to the head office **separately**, through a locked form (**environment variables** in the dashboard).
- Anything printed on the **menu** (`NEXT_PUBLIC_` variables) is visible to every customer. You'd never print the safe combination on the menu.
- Before changing the real menu, the kitchen cooks a **tasting version** for staff only (a **preview deployment**).

</En>
<Ur>

Deploy karna aisa hai jaise **restaurant chain recipe book se nayi branch kholti hai**.

- Aap ki **GitHub repo** recipe book hai. Is me recipes (code) hain, magar tijori ka code (secrets) **nahi**.
- **Vercel** head office ki kitchen team hai. Har dafa recipe book badalti hai, wo sab kuch taaza pakate hain (**build**) aur dunya bhar ki branches ko bhejte hain (**CDN**).
- Tijori ka code head office ko **alag se**, band form ke zariye diya jata hai (dashboard me **environment variables**).
- **Menu** par jo chhapa ho (`NEXT_PUBLIC_` variables) wo har customer dekhta hai. Aap tijori ka code kabhi menu par nahi chhapenge.
- Asli menu badalne se pehle kitchen sirf staff ke liye **chakhne wala version** banati hai (**preview deployment**).

</Ur>
</Tr>

<Step title="Keep secrets and junk out of Git">

<Tr>
<En>
Before your first push, check what Git would upload. `node_modules/` and `.next/` are huge and rebuilt by Vercel; `.env.local` contains secrets. A `.gitignore` file tells Git to skip them. Commit a **`.env.example`** with the variable names but no values, so teammates know what to set.
</En>
<Ur>
Pehle push se pehle dekhein ke Git kya upload karega. `node_modules/` aur `.next/` bohot bare hain aur Vercel unhe dobara banata hai; `.env.local` me secrets hain. `.gitignore` file Git ko inhe chhorne ka kehti hai. Variable ke naam (values ke baghair) wali **`.env.example`** commit karein, taa ke teammates jaanein kya set karna hai.
</Ur>
</Tr>

```bash
git status --short -uall
```

```text
?? .env.example
?? .env.local
?? .next/b
?? app/page.tsx
?? node_modules/x/i.js
?? package.json
```

```bash
printf 'node_modules/\n.next/\n.env*.local\n' > .gitignore
git status --short -uall
```

```text
?? .env.example
?? .gitignore
?? app/page.tsx
?? package.json
```

<Happened>
<Tr>
<En>

- Before `.gitignore`, Git would have uploaded `.env.local` (secrets), plus `node_modules/` and `.next/`.
- After it, only source files, `.env.example` and `.gitignore` itself remain. `create-next-app` adds a `.gitignore` like this for you; check it's still there.
- If a secret was **ever** pushed, adding it to `.gitignore` later doesn't remove it from history. **Rotate the key** (create a new one, delete the old one) at the provider.

</En>
<Ur>

- `.gitignore` se pehle Git `.env.local` (secrets), `node_modules/` aur `.next/` upload kar deta.
- Us ke baad sirf source files, `.env.example` aur khud `.gitignore` bachi. `create-next-app` aap ke liye aisi `.gitignore` bana deta hai; check karein ke wo ab bhi maujood hai.
- Agar koi secret **kabhi bhi** push hua ho, to baad me `.gitignore` me daalne se wo history se nahi hat-ta. Provider par **key badal dein** (nayi banayen, purani mita dein).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Import the project on Vercel">

<Tr>
<En>

Push your code to a GitHub repository, then:

1. Sign up at **vercel.com** with your GitHub account.
2. Click **Add New… → Project**, find your repository and click **Import**. (Allow Vercel's GitHub app to access it if asked.)
3. Vercel detects **Next.js** and fills in the build settings: install with `npm install`, build with `npm run build`. Leave them as they are.
4. Open **Environment Variables** and add every variable from your `.env.example` with its **production** value (next step).
5. Click **Deploy**. You'll see the build log stream live; when it finishes, you get a URL like `acme-store.vercel.app`.

</En>
<Ur>

Apna code GitHub repository par push karein, phir:

1. Apne GitHub account se **vercel.com** par sign up karein.
2. **Add New… → Project** dabayen, apni repository dhoondein aur **Import** dabayen. (Pucha jaye to Vercel ki GitHub app ko ijazat dein.)
3. Vercel **Next.js** pehchaan kar build settings bhar deta hai: `npm install` se install, `npm run build` se build. Inhe waise hi rehne dein.
4. **Environment Variables** kholein aur apni `.env.example` ka har variable us ki **production** value ke saath daalein (agla qadam).
5. **Deploy** dabayen. Build log live chalta nazar aayega; khatam hone par `acme-store.vercel.app` jaisa URL milega.

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- Vercel connected a **webhook** to your repo: from now on, every push triggers a new deployment. You don't click Deploy again.
- Each deployment is **immutable**: a frozen copy of one commit with its own unique URL. The production domain just points to the latest successful one.
- If the build fails, the old version keeps serving. Users never see a broken build.

</En>
<Ur>

- Vercel ne aap ki repo se **webhook** jor diya: ab har push naya deployment shuru karega. Dobara Deploy dabane ki zaroorat nahi.
- Har deployment **na-qabil-e-tabdeel** hai: ek commit ki jami hui copy apne alag URL ke saath. Production domain bas sab se taaza kamyab wale ki taraf ishara karta hai.
- Agar build fail ho to purana version chalta rehta hai. Users ko kabhi toota build nazar nahi aata.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Environment variables, locally and on Vercel">

<Tr>
<En>
Code reads settings from `process.env`. Locally they come from `.env.local`; on Vercel, from the dashboard. Our test app had this `.env.local` and a page that reads both variables on the server and in a Client Component.
</En>
<Ur>
Code settings `process.env` se parhta hai. Local par ye `.env.local` se aati hain; Vercel par dashboard se. Hamari test app me ye `.env.local` thi aur ek page jo dono variables server par aur Client Component me parhta hai.
</Ur>
</Tr>

```text
# .env.local  (never committed)
NEXT_PUBLIC_SITE_NAME=Acme Store
STRIPE_SECRET_KEY=sk_test_51abcDEMOonly
```

```tsx
// app/env/page.tsx  (Server Component)
import EnvShow from "./EnvShow";

export const dynamic = "force-dynamic";

export default function EnvPage() {
  const hasKey = Boolean(process.env.STRIPE_SECRET_KEY);
  return (
    <main>
      <p>Server sees the secret: {hasKey ? "yes" : "no"}</p>
      <EnvShow />
    </main>
  );
}
```

```tsx
// app/env/EnvShow.tsx  (Client Component)
"use client";

export default function EnvShow() {
  return (
    <ul>
      <li>NEXT_PUBLIC_SITE_NAME: {process.env.NEXT_PUBLIC_SITE_NAME ?? "undefined"}</li>
      <li>STRIPE_SECRET_KEY: {process.env.STRIPE_SECRET_KEY ?? "undefined"}</li>
    </ul>
  );
}
```

```text
What the browser showed after the page loaded:

Server sees the secret: yes
NEXT_PUBLIC_SITE_NAME: Acme Store
STRIPE_SECRET_KEY: undefined
```

<Happened>
<Tr>
<En>

- **Server code sees every variable.** The Server Component could read `STRIPE_SECRET_KEY` and only sent the word "yes".
- **Browser code only sees `NEXT_PUBLIC_` variables.** In the browser, `STRIPE_SECRET_KEY` was `undefined`.
- At build time, Next.js **replaces** `process.env.NEXT_PUBLIC_SITE_NAME` in browser code with the literal text. We searched the built files in `.next/static` and found `"Acme Store"` written inside a JavaScript chunk. That's why `NEXT_PUBLIC_` values are public and why changing one needs a **new build**.
- On Vercel, a variable can apply to **Production**, **Preview** and/or **Development**. Use a test database and test keys for Preview. After changing a variable, **redeploy**: running deployments keep the values they were built with.

</En>
<Ur>

- **Server code har variable dekhta hai.** Server Component `STRIPE_SECRET_KEY` parh saka aur sirf lafz "yes" bheja.
- **Browser code sirf `NEXT_PUBLIC_` variables dekhta hai.** Browser me `STRIPE_SECRET_KEY` `undefined` tha.
- Build ke waqt Next.js browser code me `process.env.NEXT_PUBLIC_SITE_NAME` ko asal text se **badal deta** hai. Humne `.next/static` ki bani files me dhoonda to JavaScript chunk ke andar `"Acme Store"` likha mila. Isi liye `NEXT_PUBLIC_` values public hain aur ek badalne ke liye **naya build** chahiye.
- Vercel par variable **Production**, **Preview** aur/ya **Development** par lagu ho sakta hai. Preview ke liye test database aur test keys lein. Variable badalne ke baad **redeploy** karein: chalte deployments wahi values rakhte hain jin ke saath bane the.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The leak you can't see in the browser">

<Tr>
<En>
The browser showed `undefined` for the secret, so it looks safe. It isn't. A Client Component **also runs on the server** to produce the first HTML, and on the server the secret exists. We downloaded the raw HTML with curl:
</En>
<Ur>
Browser ne secret ke liye `undefined` dikhaya, isliye mehfooz lagta hai. Aisa nahi. Client Component pehla HTML banane ke liye **server par bhi chalta** hai, aur server par secret maujood hai. Humne curl se kaccha HTML download kiya:
</Ur>
</Tr>

```bash
curl -s http://localhost:3000/env | grep -o '<li>[^/]*</li>'
```

```text
<li>NEXT_PUBLIC_SITE_NAME: <!-- -->Acme Store</li>
<li>STRIPE_SECRET_KEY: <!-- -->sk_test_51abcDEMOonly</li>
```

<Happened>
<Tr>
<En>

- The **secret key is in the HTML** sent to every visitor. Anyone using "View Page Source" or curl can copy it. React then replaced it with `undefined` in the browser, hiding the problem from you.
- The rule: **never mention a secret variable inside a Client Component** or any file it imports. Read secrets only in Server Components, route handlers and Server Actions, and send the browser only the result.
- Add `import "server-only";` to files that use secrets (Server vs Client lesson). If a Client Component imports them, the **build fails** instead of leaking.

</En>
<Ur>

- **Secret key HTML me hai** jo har visitor ko bheja gaya. "View Page Source" ya curl istemal karne wala koi bhi ise copy kar sakta hai. Phir React ne browser me ise `undefined` se badal diya, aur masla aap se chhup gaya.
- Qaida: **Client Component ya us ki import ki hui kisi file me kabhi secret variable ka zikr na karein.** Secrets sirf Server Components, route handlers aur Server Actions me parhein, aur browser ko sirf nateeja bhejein.
- Secrets istemal karne wali files me `import "server-only";` daalein (Server vs Client lesson). Agar Client Component unhe import kare to leak hone ke bajaye **build fail** ho jata hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Preview deployments for every branch">

<Tr>
<En>

Work on a branch, push it, and Vercel builds a **separate live copy**:

```bash
git switch -c new-checkout
# … make changes, commit …
git push -u origin new-checkout
```

- Vercel gives the branch its own URL and, if you open a **pull request** on GitHub, posts the preview link as a comment on it.
- Preview deployments use the variables marked **Preview**, so point them at a test database and test payment keys.
- Share the link with a client or teammate. When the pull request is merged into `main`, Vercel builds again and that version goes to **production**.

</En>
<Ur>

Branch par kaam karein, push karein, aur Vercel ek **alag live copy** banata hai:

```bash
git switch -c new-checkout
# … tabdeeliyan karein, commit karein …
git push -u origin new-checkout
```

- Vercel branch ko apna URL deta hai aur, agar aap GitHub par **pull request** kholein, to us par preview link comment me daal deta hai.
- Preview deployments **Preview** wale variables istemal karti hain, isliye unhe test database aur test payment keys ki taraf rakhein.
- Link client ya teammate ke saath share karein. Jab pull request `main` me merge ho, Vercel dobara build karta hai aur wo version **production** par chala jata hai.

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- Previews make reviews real: people click the actual app instead of reading code.
- Preview URLs are hard to guess but not secret. Turn on **Deployment Protection** in project settings if previews show unreleased or private data.

</En>
<Ur>

- Previews review ko asli banate hain: log code parhne ke bajaye asal app par click karte hain.
- Preview URLs ka andaza lagana mushkil hai magar ye raaz nahi. Agar previews me ghair shaya ya zaati data ho to project settings me **Deployment Protection** on karein.

</Ur>
</Tr>
</Happened>

<Step title="Add your own domain">

<Tr>
<En>

1. Buy a domain from any registrar (Namecheap, Cloudflare, Porkbun, Vercel itself…).
2. In Vercel: **Project → Settings → Domains → Add**, and type `acme-store.com`. Vercel suggests also adding `www.acme-store.com` and redirecting one to the other.
3. Vercel shows the **DNS records** to create: typically an **A record** for the root domain and a **CNAME** for `www`. Copy the exact values from the dashboard into your registrar's DNS settings.
4. Wait for the domain to show **Valid Configuration**. DNS changes can take from minutes to a few hours.
5. Vercel issues the **HTTPS certificate** automatically.

</En>
<Ur>

1. Kisi bhi registrar se domain khareedein (Namecheap, Cloudflare, Porkbun, khud Vercel…).
2. Vercel me: **Project → Settings → Domains → Add**, aur `acme-store.com` likhein. Vercel `www.acme-store.com` bhi jorne aur ek ko doosre par redirect karne ka mashwara deta hai.

<Step title="Logs, rollbacks and serverless limits">

<Tr>
<En>

When something breaks in production:

- **Deployments tab → a deployment → Build Logs** shows why a build failed (the same errors `npm run build` would show you).
- **Logs** (runtime logs) show `console.log` and errors from your API routes, Server Actions and server rendering. Log useful context, never secrets or passwords.
- **Instant Rollback**: pick an earlier working deployment and promote it to production in seconds while you fix the bug.

Serverless means your server code starts **per request** on many machines:

- **No shared memory.** The in-memory `products` array from the API Routes lesson would differ between instances and reset often. Use a database.
- **No permanent disk.** Files written to disk disappear. Use object storage for uploads.
- **Time limits.** Each function has a maximum duration (configurable per plan); long jobs belong in a background worker or queue.

</En>
<Ur>

Jab production me kuch toote:

- **Deployments tab → ek deployment → Build Logs** batata hai build kyun fail hua (wahi errors jo `npm run build` aap ko dikhata).
- **Logs** (runtime logs) aap ke API routes, Server Actions aur server rendering ke `console.log` aur errors dikhate hain. Kaam ka context log karein, kabhi secrets ya passwords nahi.
- **Instant Rollback**: pichhla chalne wala deployment chun kar seconds me production par le aayen, jab tak aap bug theek karein.

Serverless ka matlab aap ka server code bohot si machines par **har request par** shuru hota hai:

- **Share memory nahi.** API Routes lesson ki memory wali `products` array har instance me mukhtalif hogi aur aksar reset hogi. Database istemal karein.
- **Mustaqil disk nahi.** Disk par likhi files ghayab ho jati hain. Uploads ke liye object storage lein.
- **Waqt ki hadd.** Har function ki zyada se zyada muddat hoti hai (plan ke mutabiq set ho sakti hai); lambe kaam background worker ya queue me jate hain.

</Ur>
</Tr>

<Tr>

</En>

## Common mistakes

<Compare>
<Bad title="A secret with the public prefix">

```text
NEXT_PUBLIC_STRIPE_SECRET_KEY=sk_live_…
```

</Bad>
<Good title="Public prefix only for public values">

```text
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_live_…
STRIPE_SECRET_KEY=sk_live_…
```

</Good>
</Compare>

<Compare>
<Bad title="Reading a secret in a Client Component">

```tsx
"use client";
const key = process.env.STRIPE_SECRET_KEY;   // ends up in the HTML
```

</Bad>
<Good title="Read it on the server, send the result">

```ts
// app/api/checkout/route.ts
const key = process.env.STRIPE_SECRET_KEY;   // stays on the server
```

</Good>
</Compare>

<Compare>
<Bad title="Committing .env.local">

```bash
git add .
git commit -m "add everything"   # .env.local included
```

</Bad>
<Good title="Ignore it, commit an example">

```text
# .gitignore
.env*.local

# .env.example (committed)
STRIPE_SECRET_KEY=
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Changing a variable and not redeploying**, then wondering why nothing changed.
- **Using production keys and the production database in Preview.** A test checkout on a preview can charge real cards.
- **Pushing without building locally**, then debugging through failed deploys.
- **Hard-coding `http://localhost:3000`** in code that runs on Vercel. Use relative URLs or a `NEXT_PUBLIC_SITE_URL` variable.
- **Forgetting auth and webhook URLs** after adding a custom domain.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Variable badal kar redeploy na karna**, phir sochna ke kuch badla kyun nahi.
- **Preview me production keys aur production database istemal karna.** Preview par test checkout asli cards se paise kaat sakta hai.
- **Local build ke baghair push karna**, phir fail deploys ke zariye debug karna.
- Vercel par chalne wale code me **`http://localhost:3000` likh dena**. Relative URLs ya `NEXT_PUBLIC_SITE_URL` variable istemal karein.
- Custom domain jorne ke baad **auth aur webhook URLs bhool jana**.

</Ur>
</Tr>

<DeepDive title="More about Vercel">

**`vercel.json` / `vercel.ts`.** Next.js projects rarely need one, because redirects, rewrites and headers usually go in `next.config.ts`. Use Vercel's config for platform settings such as cron jobs or function regions.

```text
// next.config.ts
const nextConfig = {
  async redirects() {
    return [{ source: "/old-blog/:slug", destination: "/blog/:slug", permanent: true }];
  },
};
export default nextConfig;
```

**Cron jobs.** Vercel can call one of your route handlers on a schedule (for example, a nightly cleanup). Protect that route with a secret so strangers can't trigger it.

**Function region.** Put your functions in the region closest to your **database**, not your users: a page that makes five database queries is faster when each query is short.

**Monorepos.** Set the project's **Root Directory** to the app folder (for example `apps/web`).

**Build cache.** Vercel caches dependencies and Next.js build output between deploys. If a build behaves strangely, redeploy without the cache.

**Other hosts.** Next.js also runs on Netlify, Cloudflare, AWS Amplify, or any Node server with `next build && next start` (or `output: "standalone"` in Docker). The ideas in this lesson (build, env vars, public prefix, previews) carry over.

</DeepDive>

<DeepDive title="Real world: the key that was in every page">

A small team built an online store. A developer wanted the admin product editor to talk to the payment provider, and wrote the call inside a component that already had `"use client"` at the top:

```text
"use client";
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);
```

In the browser, the key was `undefined`, so the payment code failed and the developer moved the API call into a route handler. The bug seemed fixed. But the component still printed `process.env.STRIPE_SECRET_KEY` in a debug line they'd forgotten, and server rendering had been putting the live secret key into the HTML of the admin page for two weeks.

A security researcher found it with "View Page Source" and reported it. The team:

1. **Rolled the key** at the payment provider immediately, which made the leaked key useless.
2. Checked the provider's logs for any calls made with the old key.
3. Moved every use of secrets into files with `import "server-only";`, so a Client Component importing them now fails the build.
4. Added a CI step that builds the app and searches `.next/` and the rendered HTML for anything that looks like a secret key (for example, `grep -r "sk_live_"`).

Lesson: "the browser shows `undefined`" doesn't prove a secret is safe. Check the HTML, and keep secrets in server-only files.

</DeepDive>

<DeepDive title="Security lens">

- **Secrets never in Git.** Use `.gitignore`, a pre-commit secret scanner (gitleaks), and GitHub secret scanning. If a secret is ever pushed, **rotate it**; deleting the commit isn't enough.
- **`NEXT_PUBLIC_` is public.** Only publishable keys, public URLs and ids.
- **No secrets in Client Components** or files they import; use `server-only`.
- **Separate environments**: test keys and a test database for Preview and Development; production keys only in Production.
- **Least privilege**: give each key only the permissions the app needs, and different keys per environment.
- **Deployment Protection** for previews that show private data; restrict who can change environment variables in your Vercel team.
- **Security headers** (Content-Security-Policy, Strict-Transport-Security, X-Frame-Options) via `next.config.ts` headers or middleware.
- **Logs**: never log tokens, passwords or full card data; Vercel logs are visible to everyone on the team.
- **Dependencies**: Vercel installs exactly what your lockfile says; keep the lockfile committed and run `npm audit` regularly.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does a Git-connected Vercel deployment work?">
Vercel installs a webhook on the repository. Each push triggers a build that runs the install and build commands and produces an immutable deployment with its own URL. Pushes to the production branch are promoted to the production domains, and other branches or pull requests get preview deployments.
</QA>

<QA q="What is the difference between NEXT_PUBLIC_ variables and other environment variables in Next.js?">
Variables with the NEXT_PUBLIC_ prefix are inlined into the client JavaScript at build time, so they are visible to anyone and require a rebuild to change. Other variables are only available in server code at runtime, such as Server Components, route handlers and Server Actions.
</QA>

<QA q="Why might a secret leak even if the browser shows it as undefined?">
Client Components are also rendered on the server for the initial HTML. If a Client Component reads a server-only variable, the server-rendered HTML contains the real value, even though the client bundle does not, so the secret is visible in the page source.
</QA>

<QA q="What constraints does serverless hosting place on your application?">
Instances are short-lived and not shared, so in-memory state and local disk writes do not persist. Functions have execution time limits, cold starts can add latency, and long-running processes such as WebSocket servers or background workers need a different host or a managed service.
</QA>

<QA q="How would you roll back a bad production deployment on Vercel?">
Use Instant Rollback, or promote a previous successful deployment to production from the dashboard. Because deployments are immutable, this takes effect quickly without rebuilding, and then you fix the issue and push a new commit.
</QA>

</DeepDive>
