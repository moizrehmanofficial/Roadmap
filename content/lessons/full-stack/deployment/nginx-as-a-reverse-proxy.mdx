<BigIdea>
<Tr>
<En>
A **reverse proxy** is a server that sits in front of your apps and receives every request first. Clients only ever talk to it; it decides where each request goes and passes the response back. **Nginx** is the most widely used one. It's tiny, extremely fast at serving static files and holding thousands of connections, and battle-tested. Putting it in front of a Node API lets it do the jobs Node shouldn't spend effort on: **terminating TLS** (HTTPS) with your certificate, **redirecting** HTTP to HTTPS, serving the **frontend's static files**, **routing** `/api/` to the app, **load balancing** across several app instances, adding the **forwarded headers** so the app knows the real client IP and protocol, **gzip** compression, **request size limits**, **rate limiting**, timeouts and **security headers**. Your apps then listen only on a private network, and Nginx is the single public entry point.
</En>
<Ur>
**Reverse proxy** aisa server hai jo aap ki apps ke aage baith kar har request pehle leta hai. Clients sirf us se baat karte hain; woh tay karta hai ke har request kahan jaye aur jawab wapas pohanchata hai. **Nginx** sab se zyada istemal hone wala hai. Ye chhota, static files dene aur hazaron connections sambhalne me bohot tez, aur aazmaya hua hai. Ise Node API ke aage lagane se woh kaam ye karta hai jin par Node ko mehnat nahi karni chahiye: aap ke certificate se **TLS terminate** karna (HTTPS), HTTP ko HTTPS par **redirect**, **frontend ki static files** dena, `/api/` ko app tak **route** karna, kayi app instances par **load balancing**, **forwarded headers** jorna taa ke app ko asal client IP aur protocol pata ho, **gzip** compression, **request size limits**, **rate limiting**, timeouts aur **security headers**. Phir aap ki apps sirf private network par sunti hain, aur Nginx akela public darwaza hota hai.
</Ur>
</Tr>
</BigIdea>

## Picture it

<Tr>
<En>

Think of the **reception desk of an office building**.

- Visitors never wander the corridors; they go to reception (one public entry point). Reception checks their badge (TLS), sends a courier who came to the wrong door round to the main entrance (HTTP to HTTPS redirect), and turns away anyone carrying something too big (413).
- Brochures are handed out at the desk without bothering anyone upstairs (static files).
- Visitors for "accounts" are sent to the third floor, where whichever clerk is free takes them (routing and load balancing). Reception writes the visitor's name on a slip so the clerk knows who really came, not just "reception sent them" (X-Forwarded-For, X-Real-IP).
- Someone who keeps coming back every few seconds is asked to wait (rate limiting).

</En>

## Learn it step by step

<Walkthrough>

<Step title="Static files, /api routing and load balancing">

<Tr>
<En>
Two copies of a small Node API (`api1`, `api2`) run on a private Docker network and report what they received: the path, the `Host` header, the client IP and protocol. Nginx is the only container with a published port. It serves `site/` as the frontend with an SPA fallback, and forwards `/api/` to an `upstream` of both APIs, stripping the `/api` prefix and adding forwarded headers. `nginx -t` checks the config first.
</En>
<Ur>
Chhoti Node API ki do copies (`api1`, `api2`) private Docker network par chalti hain aur batati hain ke unhe kya mila: path, `Host` header, client IP aur protocol. Sirf Nginx container ka port bahar khula hai. Woh `site/` ko SPA fallback ke saath frontend ki tarah deta hai, aur `/api/` ko dono APIs ke `upstream` tak bhejta hai, `/api` prefix hata kar aur forwarded headers jor kar. `nginx -t` pehle config check karta hai.
</Ur>
</Tr>

```bash
mkdir -p site && echo '<h1>Shop</h1>' > site/index.html
cat > app.js <<'EOF'
import http from 'node:http';
http.createServer((req, res) => {
  res.setHeader('content-type', 'application/json');
  res.end(JSON.stringify({ server: process.env.NAME, path: req.url, host: req.headers.host,
    clientIp: req.headers['x-real-ip'], proto: req.headers['x-forwarded-proto'] }));
}).listen(3000);
EOF
cat > nginx.conf <<'EOF'
upstream api_servers {            # several app instances; round robin by default
    server api1:3000;
    server api2:3000;
}
server {
    listen 80;
    server_name example.test;

    root /usr/share/nginx/html;   # static files: nginx serves them itself, very fast
    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {              # everything under /api goes to Node
        proxy_pass http://api_servers/;     # trailing slash: /api/orders -> /orders
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF
docker rm -f api1 api2 proxy > /dev/null 2>&1; docker network rm shopnet > /dev/null 2>&1
docker network create --subnet 172.30.0.0/24 shopnet > /dev/null
for n in api1 api2; do
  docker run -d --name $n --network shopnet -e NAME=$n -v "$PWD/app.js:/app/app.mjs:ro" node:24-alpine node /app/app.mjs > /dev/null
done
docker run -d --name proxy --network shopnet -p 8080:80 -v "$PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  -v "$PWD/site:/usr/share/nginx/html:ro" nginx:1.29-alpine > /dev/null
sleep 1.5
docker exec proxy nginx -t 2>&1 | tail -1
curl -s localhost:8080/
curl -s localhost:8080/products/42 | tr -d "\n"; echo "   <- unknown path falls back to index.html (SPA routing)"
curl -s localhost:8080/api/orders?page=2 | sed 's/"server":"api[12]",//'; echo
echo "servers that answered 6 requests: $(for i in 1 2 3 4 5 6; do curl -s localhost:8080/api/health | grep -o 'api[12]'; done | sort -u | tr '\n' ' ')"
echo "port 3000 reachable from the host? $(curl -s -m 1 localhost:3000 > /dev/null && echo yes || echo no, only nginx is exposed)"
```

```text output
nginx: configuration file /etc/nginx/nginx.conf test is successful
<h1>Shop</h1>
<h1>Shop</h1>   <- unknown path falls back to index.html (SPA routing)
{"path":"/orders?page=2","host":"localhost","clientIp":"172.30.0.1","proto":"http"}
servers that answered 6 requests: api1 api2 
port 3000 reachable from the host? no, only nginx is exposed
```

<Happened>
<Tr>
<En>

- `nginx -t` reported the configuration **successful**. Always run it before reloading on a server: a typo in a reload is caught here, while a typo in a restart takes the site down.
- `/` returned the HTML from disk without touching Node, and `/products/42`, which isn't a file, **fell back to index.html** so the frontend's router can handle it. Without `try_files`, refreshing any client-side route would give a 404.
- `/api/orders?page=2` arrived at Node as **`/orders?page=2`**: the trailing slash in `proxy_pass http://api_servers/;` replaces the matched `/api/` prefix. Without it, Node would receive `/api/orders`. This one slash is the most common Nginx confusion.
- The app saw the original **Host** and the **client IP** from `X-Real-IP`; without these headers it would see Nginx's own address for every request, breaking logs, rate limits and redirects. In Express, `app.set('trust proxy', 1)` makes `req.ip` and `req.protocol` use them.
- Requests were spread over **both api1 and api2**. If one stops, Nginx retries the request on the other (for safe methods) and marks the failed one unavailable for a while.
- Port 3000 was **not reachable** from outside: only Nginx is public.

</En>
<Ur>

- `nginx -t` ne configuration **successful** batayi. Server par reload se pehle hamesha chalayen: reload me typo yahin pakra jata, jabke restart me typo site band kar deta hai.
- `/` ne Node ko chhue baghair disk se HTML lautaya, aur `/products/42`, jo file nahi, **index.html par fallback** hua taa ke frontend ka router use sambhale. `try_files` ke baghair kisi bhi client-side route ko refresh karne par 404 milta.
- `/api/orders?page=2` Node tak **`/orders?page=2`** ban kar pohncha: `proxy_pass http://api_servers/;` me aakhri slash milte hue `/api/` prefix ko badal deta hai. Is ke baghair Node ko `/api/orders` milta. Ye ek slash Nginx ki sab se aam uljhan hai.
- App ne asal **Host** aur `X-Real-IP` se **client IP** dekha; in headers ke baghair use har request par Nginx ka apna address dikhta, jo logs, rate limits aur redirects torta. Express me `app.set('trust proxy', 1)` `req.ip` aur `req.protocol` ko inhe istemal karwata hai.
- Requests **api1 aur api2 dono** par bantin. Ek ruk jaye to Nginx request doosre par dobara bhejta hai (mehfooz methods ke liye) aur nakam wale ko kuch der na-mojood mark karta hai.
- Port 3000 bahar se **pohanch me nahi** tha: sirf Nginx public hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="HTTPS, redirects, headers, gzip and limits">

<Tr>
<En>
Now the production version. Port 80 only redirects to HTTPS. Port 443 terminates TLS with a certificate (self-signed here; Let's Encrypt via certbot on a real server), enables HTTP/2, adds **HSTS** and `nosniff`, hides the version, gzips JSON, limits bodies to 1 KB (tiny for the demo) and rate-limits `/api/` to 1 request per second per IP with a burst of 2. We test each feature with curl.
</En>
<Ur>
Ab production wala version. Port 80 sirf HTTPS par redirect karta hai. Port 443 certificate se TLS terminate karta (yahan self-signed; asal server par certbot ke zariye Let's Encrypt), HTTP/2 on karta, **HSTS** aur `nosniff` jorta, version chhupata, JSON gzip karta, bodies 1 KB tak mehdood karta (demo ke liye chhota) aur `/api/` ko fi IP 1 request per second, 2 ke burst ke saath, rate-limit karta hai. Har feature curl se test karte hain.
</Ur>
</Tr>

```bash
mkdir -p certs
openssl req -x509 -newkey rsa:2048 -nodes -days 30 -keyout certs/key.pem -out certs/cert.pem -subj "/CN=example.test" \
  -addext "subjectAltName=DNS:example.test" 2> /dev/null
cat > nginx.conf <<'EOF'
upstream api_servers { server api1:3000; server api2:3000; }
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=1r/s;   # per client IP

server {                                  # plain HTTP: only redirect
    listen 80;
    server_name example.test;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    http2 on;
    server_name example.test;
    ssl_certificate     /etc/nginx/certs/cert.pem;   # in production: from Let's Encrypt (certbot)
    ssl_certificate_key /etc/nginx/certs/key.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options nosniff always;
    server_tokens off;                    # don't advertise the nginx version

    gzip on;
    gzip_types application/json text/css application/javascript;
    client_max_body_size 1k;              # tiny on purpose for the demo; 10m is common

    root /usr/share/nginx/html;
    location / { try_files $uri $uri/ /index.html; }

    location /api/ {
        limit_req zone=api_limit burst=2 nodelay;
        limit_req_status 429;
        proxy_pass http://api_servers/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;
    }
}
EOF
docker rm -f proxy > /dev/null
docker run -d --name proxy --network shopnet -p 8080:80 -p 8443:443 -v "$PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  -v "$PWD/certs:/etc/nginx/certs:ro" -v "$PWD/site:/usr/share/nginx/html:ro" nginx:1.29-alpine > /dev/null
sleep 1.5
c() { curl -s --noproxy '*' --cacert certs/cert.pem --resolve example.test:8443:127.0.0.1 --resolve example.test:8080:127.0.0.1 "$@"; }
c -o /dev/null -w 'http://  -> %{http_code} %{redirect_url}\n' http://example.test:8080/cart
c -sI https://example.test:8443/ | grep -iE '^(HTTP|server|strict-transport|x-content-type)' | tr -d '\r'
c https://example.test:8443/api/orders | sed 's/"server":"api[12]",//'; echo
sleep 1.1
c -H 'Accept-Encoding: gzip' -o /dev/null -D - https://example.test:8443/api/orders | grep -i '^content-encoding' | tr -d '\r'
sleep 3
printf 'six quick API calls: '; for i in 1 2 3 4 5 6; do c -o /dev/null -w '%{http_code} ' https://example.test:8443/api/orders; done; echo
sleep 3
c -o /dev/null -w 'upload of 2 KB -> %{http_code}\n' -X POST --data "$(head -c 2048 /dev/zero | tr '\0' a)" https://example.test:8443/api/upload
docker rm -f api1 api2 proxy > /dev/null; docker network rm shopnet > /dev/null
```

```text output
http://  -> 301 https://example.test/cart
HTTP/2 200 
server: nginx
strict-transport-security: max-age=31536000
x-content-type-options: nosniff
{"path":"/orders","host":"example.test","clientIp":"172.30.0.1","proto":"https"}
content-encoding: gzip
six quick API calls: 200 200 200 429 429 429 
upload of 2 KB -> 413
```

<Happened>
<Tr>
<En>

- **HTTP got a 301** to the same path on `https://`, so old links and people typing the bare domain still land on the secure site. (The redirect drops our demo port 8080; on a real server both are on standard ports.)
- The HTTPS response came over **HTTP/2**, with **HSTS** (browsers will refuse plain HTTP for this domain for a year) and `nosniff`. The `server` header says only `nginx`, without a version an attacker could match to known vulnerabilities.
- The app saw **`proto: https`** even though Nginx talked to it over plain HTTP on the private network. That's TLS termination: the app must trust `X-Forwarded-Proto` (via `trust proxy`) to build correct URLs and set `Secure` cookies.
- The JSON response was **gzip**-compressed because the client accepted it; text compresses to a fraction of its size.
- Six quick API calls gave **200 200 200 429 429 429**: one allowed by the rate plus a burst of two, then rejected. Rate limits by IP protect login and expensive endpoints from brute force and floods; tune the rate per route.
- A 2 KB upload got **413** before it ever reached Node. Set this to your real maximum (and match it in the app), so huge bodies can't tie up memory.

</En>
<Ur>

- **HTTP ko 301** mila, `https://` par usi path ki taraf, isliye purane links aur khaali domain likhne wale bhi mehfooz site par pohanchte hain. (Redirect hamara demo port 8080 chhor deta hai; asal server par dono standard ports par hote hain.)
- HTTPS jawab **HTTP/2** par aaya, **HSTS** (browsers ek saal tak is domain ke liye saada HTTP se inkar karenge) aur `nosniff` ke saath. `server` header sirf `nginx` kehta hai, aise version ke baghair jise hamla awar maloom kamzoriyon se mila sake.
- App ne **`proto: https`** dekha halanke Nginx ne us se private network par saade HTTP se baat ki. Yahi TLS termination hai: sahi URLs banane aur `Secure` cookies set karne ke liye app ko `X-Forwarded-Proto` par (`trust proxy` se) bharosa karna hoga.
- JSON jawab **gzip** compress hua kyunke client ne qabool kiya; text apne size ke chhote hisse tak simat jata hai.
- Chhe tez API calls ne **200 200 200 429 429 429** diya: ek rate se aur do burst se ijazat, phir radd. IP se rate limits login aur mehngay endpoints ko brute force aur sailaab se bachate hain; har route ke liye rate set karein.
- 2 KB upload ko Node tak pohanchne se pehle hi **413** mila. Ise apni asal had par rakhein (aur app me bhi wahi), taa ke bari bodies memory na roke rakhein.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="The app doesn't know it's behind a proxy">

```text
location /api/ {
    proxy_pass http://127.0.0.1:3000;        # no forwarded headers
}
// Express: req.ip is always 127.0.0.1, req.protocol is 'http'
// -> rate limiter blocks everyone at once, redirects go to http://, Secure cookies not set
```

</Bad>
<Good title="Forward the headers and trust exactly one proxy">

```text
location /api/ {
    proxy_pass http://127.0.0.1:3000/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
// Express: app.set('trust proxy', 1)   // trust only the nearest proxy
```

</Good>
</Compare>

<Compare>
<Bad title="Restart without testing">

```text
sudo nano /etc/nginx/sites-available/shop
sudo systemctl restart nginx
# a missing semicolon -> nginx fails to start -> every site on the server is down
```

</Bad>
<Good title="Test, then reload">

```text
sudo nginx -t && sudo systemctl reload nginx
# a bad config is rejected and the old one keeps serving;
# reload swaps workers gracefully without dropping connections
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **App listening on 0.0.0.0 with the port open**: attackers bypass Nginx's limits; bind to 127.0.0.1 or a private network and firewall the port.
- **Trusting X-Forwarded-For from anyone**: clients can send fake values; trust only your own proxy (`trust proxy` set to the number of proxies).
- **Forgetting WebSocket headers**: WebSockets need `proxy_http_version 1.1` plus `Upgrade` and `Connection` headers.
- **Timeouts too short for slow endpoints** (504s) or too long for everything (slow clients tie up workers).
- **`add_header` inside a location silently dropping the server-level headers**: headers are inherited only if the location defines none.
- **Certificates not renewing**: check `certbot renew --dry-run` and that the renewal timer exists.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **App 0.0.0.0 par khule port ke saath**: hamla awar Nginx ki hadein phalang jate hain; 127.0.0.1 ya private network par bind karein aur port firewall karein.

</Ur>

<Tr>
<En>
Users report three problems after a deploy: some pages show "502 Bad Gateway", a report export shows "504 Gateway Time-out" after exactly 60 seconds, and the chat feature, which uses WebSockets, never connects. Explain the likely cause of each and the fix.
</En>

Deploy ke baad users teen maslay batate hain: kuch pages par "502 Bad Gateway", report export theek 60 second baad "504 Gateway Time-out" dikhata hai, aur WebSockets istemal karne wala chat feature kabhi nahi jurta. Har ek ki mumkina wajah aur hal batayen.

<Solution>

<Tr>
<En>

- **502**: Nginx couldn't connect to the app, which crashed, is restarting or listens on a different port or address than `proxy_pass` expects. Check `docker ps` or `systemctl status`, the app logs and Nginx's `error.log` (it says "connect() failed").

</En>

<DeepDive title="More about Nginx">

**How Nginx handles connections.** A master process and a few worker processes, each with an event loop handling thousands of connections, which is why it copes with slow clients so well: it buffers the slow client and talks to your app quickly.

**Location matching.** Exact `=` matches first, then the longest prefix, with `^~` stopping regex checks, then regex locations in order. Keep configs simple to avoid surprises.

**Caching.** `proxy_cache` stores app responses on disk; with `proxy_cache_use_stale` Nginx can serve a cached page while the app is down. Long `Cache-Control` headers with hashed file names suit static assets.

**Load balancing options.** Round robin (default), `least_conn`, `ip_hash` (sticky by client IP), weights, `max_fails` and `fail_timeout` for passive health checks, and `keepalive` connections to upstreams for speed.

**Alternatives.** Caddy gets and renews certificates automatically with a few-line config. Traefik discovers Docker containers through labels. HAProxy is a specialist load balancer. Envoy powers service meshes.

</DeepDive>

<DeepDive title="Real world: the IP that rate-limited everyone">

A team added an Express rate limiter to their login route: 10 attempts per IP per 15 minutes. It worked in testing. In production, behind Nginx, every user started getting "Too many attempts" at once on busy mornings. The app saw every request coming from `127.0.0.1`, Nginx's address, so all users shared one counter.

The fixes:

1. Nginx forwards `X-Real-IP` and `X-Forwarded-For`; Express uses `app.set('trust proxy', 1)` so `req.ip` is the client's address.
2. They checked that the app port was not reachable from outside, otherwise attackers could send a fake `X-Forwarded-For` directly.
3. A second, coarser rate limit in Nginx itself protects the login route even if the app is slow.
4. Logs now record the client IP, which also made support investigations possible.

</DeepDive>

<DeepDive title="Security lens">

- **Modern TLS only** (1.2 and 1.3), automatic renewal, and HSTS once every subdomain works over HTTPS.
- **Hide version numbers** with `server_tokens off`, and keep Nginx updated through the OS package manager.
- **Limit what reaches the app**: body size, rate limits, timeouts, and blocking paths like `/.git` and `/.env` that should never be served.
- **Don't let the proxy become an open door**: never `proxy_pass` to a URL built from user input (SSRF), and restrict admin locations by IP or authentication.
- **Security headers** can be set centrally here: HSTS, `X-Content-Type-Options`, `Referrer-Policy`, and a CSP if the app doesn't set one.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is a reverse proxy and why use one?">
A server in front of application servers that receives client requests and forwards them. It provides a single entry point, TLS termination, static file serving, routing, load balancing, compression, caching, rate limiting and protection from slow or abusive clients.
</QA>

<QA q="What is TLS termination?">
Decrypting HTTPS at the proxy or load balancer and forwarding plain HTTP (or re-encrypted traffic) to the backends on a private network. The app learns the original protocol through X-Forwarded-Proto.
</QA>

<QA q="What do X-Forwarded-For and trust proxy do?">
X-Forwarded-For carries the client IP through proxies. Setting trust proxy in Express tells it how many proxies to trust, so req.ip and req.protocol come from those headers. Trusting too many lets clients spoof their IP.
</QA>

<QA q="502 vs 504 from Nginx?">
502 Bad Gateway means Nginx couldn't get a valid response from the upstream, for example it was down or refused the connection. 504 Gateway Timeout means the upstream accepted the request but didn't answer within the configured timeout.
</QA>

<QA q="How do you change Nginx config without downtime?">
Validate with nginx -t, then reload, which starts new workers with the new configuration and lets old workers finish their current connections before exiting.
</QA>

</DeepDive>
