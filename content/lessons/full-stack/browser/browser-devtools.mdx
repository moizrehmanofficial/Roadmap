<BigIdea>
<Tr>
<En>
**DevTools** is a set of panels built into every modern browser that shows you what the page is **really** doing, not what you think it's doing. Press **F12** (or **Ctrl+Shift+I** / **⌘+⌥+I**) and you can: **inspect** any element and change its HTML and CSS live (**Elements**); run JavaScript and read errors (**Console**); pause code with breakpoints (**Sources**); see every request, its status, headers, body and timing (**Network**); look at cookies, localStorage and caches (**Application**); and record exactly where time goes and why the page is slow (**Performance**, **Lighthouse**). You can also pretend to be a phone (**device mode**) or a slow 3G connection. Professional developers have DevTools open almost all day. Learning a dozen of its features (the element picker, the Styles pane, console filters, the Network tab's status column, "Copy as fetch", throttling, breakpoints) will make you faster at building **and** fixing everything else in this course.
</En>
<Ur>
**DevTools** har jadeed browser me bane panels ka majmua hai jo dikhata hai ke page **asal me** kya kar raha hai, wo nahi jo aap samajhte hain. **F12** dabayen (ya **Ctrl+Shift+I** / **⌘+⌥+I**) aur aap kar sakte hain: kisi bhi element ka **jaiza** le kar us ka HTML aur CSS zinda badalna (**Elements**); JavaScript chalana aur errors parhna (**Console**); breakpoints se code rokna (**Sources**); har request, us ka status, headers, body aur waqt dekhna (**Network**); cookies, localStorage aur caches dekhna (**Application**); aur bilkul record karna ke waqt kahan jata hai aur page sust kyun hai (**Performance**, **Lighthouse**). Aap phone (**device mode**) ya sust 3G connection ka roop bhi dhaar sakte hain. Professional developers taqreeban saara din DevTools khula rakhte hain. Is ki darjan bhar features (element picker, Styles pane, console filters, Network tab ka status column, "Copy as fetch", throttling, breakpoints) seekhna aap ko is course ki har doosri cheez banane **aur** theek karne me tez bana dega.

## Picture it

<Tr>
<En>

Think of a **mechanic's garage** with a car on a lift.

- From the outside, you only see the car (the page). On the lift, the mechanic can see **every part** (Elements), plug in a **diagnostic computer** that reads error codes (Console), watch the **fuel lines** while the engine runs (Network), open the **glovebox** with the owner's papers (Application), and run the car on a **dynamometer** to measure exactly where power is lost (Performance).
- The mechanic can **swap a part temporarily** to see if it fixes the noise (live editing). Nothing is permanent until they order the real part (your source code).
- A **pre-made checklist** inspection (Lighthouse) catches common problems in minutes.

</En>

Lift par khari gaari wale **mechanic ke garage** ka sochein.

- Bahar se aap sirf gaari (page) dekhte hain. Lift par mechanic **har purza** dekh sakta hai (Elements), error codes parhne wala **diagnostic computer** laga sakta hai (Console), engine chalte waqt **fuel ki nalkiyan** dekh sakta hai (Network), malik ke kaghzaat wala **glovebox** khol sakta hai (Application), aur gaari ko **dynamometer** par chala kar bilkul naap sakta hai ke taqat kahan zaya hoti hai (Performance).
- Mechanic awaaz theek hoti hai ya nahi dekhne ke liye **purza aarzi taur par badal** sakta hai (zinda editing). Asli purza mangwane (aap ka source code) tak kuch pakka nahi.

<Step title="Sources: breakpoints, snippets and overrides">

<Tr>
<En>

The Debugging JavaScript lesson covered breakpoints and stepping. A few more Sources features are worth knowing:

- **Pretty print** (`{}` button at the bottom of a file) formats minified code so you can read and set breakpoints in it.
- **Conditional breakpoints and logpoints**: right-click a line number. Logpoints add `console.log` without editing the code.
- **Event listener breakpoints** (right sidebar): pause on any `click`, `keydown`, `submit`, timer or XHR/fetch, which is great when you don't know which code handles an action.
- **Pause on exceptions** (⏸ with a stop sign): stop exactly where an error is thrown, even if it's caught.
- **Snippets** (Sources → Snippets): save small scripts and run them on any page with Ctrl+Enter, such as "list all images without alt text".
- **Local overrides**: save edited copies of a site's files or **response headers** locally, and DevTools serves them instead of the real ones, even after reload. Useful for testing a fix on production, or faking an API response.
- **Ignore list**: mark `node_modules` / framework code as ignored so stepping skips it.

</En>
<Ur>

Debugging JavaScript lesson ne breakpoints aur stepping samjhaye. Sources ki chand aur features jaanne layaq hain:

- **Pretty print** (file ke neeche `{}` button) minified code ko format karta hai taa ke aap use parh sakein aur us me breakpoints laga sakein.
- **Conditional breakpoints aur logpoints**: line number par right-click. Logpoints code badle baghair `console.log` jorte hain.
- **Event listener breakpoints** (daayen sidebar): kisi bhi `click`, `keydown`, `submit`, timer ya XHR/fetch par rukna, jab aap ko maloom na ho ke kaun sa code amal sambhalta hai tab behtareen.
- **Pause on exceptions** (stop nishaan wala ⏸): bilkul wahan rukna jahan error phenka jaye, chahe pakra jaye.
- **Snippets** (Sources → Snippets): chhote scripts mehfooz kar ke kisi bhi page par Ctrl+Enter se chalayen, jaise "bina alt text ki tamam images ki list".
- **Local overrides**: site ki files ya **response headers** ki badli hui copies apne computer par mehfooz karein, aur DevTools asli ke bajaye unhen deta hai, reload ke baad bhi. Production par hal aazmane, ya naqli API response ke liye kaam ka.
- **Ignore list**: `node_modules` / framework code ko ignored nishaan zad karein taa ke stepping use chhor de.

</Ur>
</Tr>

<Step title="Performance and Lighthouse: why is it slow?">

<Tr>
<En>

<DeepDive title="More DevTools features">

**React DevTools and other framework extensions.** The React extension adds **Components** (props, state, hooks, which component rendered an element) and **Profiler** (why and how long components rendered). Vue, Angular and Redux have similar extensions.

**Workspaces.** Map DevTools' Sources to your local project folder so edits in DevTools are saved to your real files.

**Accessibility pane.** Shows the accessibility tree, computed role and name, and ARIA attributes for the selected element, plus a full-page accessibility tree view.

**CSS Overview.** (Command menu → "Show CSS Overview") lists every colour, font, unused declaration and contrast issue on a page.

**Animations drawer.** Slow down, replay and scrub CSS animations and transitions.

**Network request blocking and conditions.** Block patterns (`*analytics*`), and override the user agent.

**Firefox extras.** Excellent grid and flexbox inspectors, the "inactive CSS" hints that explain why a property has no effect, and a font editor.

**Remote debugging Node.** `chrome://inspect` connects Chrome DevTools to `node --inspect` processes (Debugging lesson).

**AI assistance.** Recent Chrome versions can explain console errors and styling problems with an AI assistant; treat its answers like any suggestion and verify them in the panels.

</DeepDive>

<DeepDive title="Real world: the checkout button that only failed in production">

A store's "Place order" button did nothing for some customers, but worked for every developer. No errors appeared in the error-tracking service, and nobody could reproduce it locally.

A developer opened the production site in an Incognito window with DevTools:

1. **Console** (with Preserve log): a `TypeError` appeared, but only in Incognito: `Cannot read properties of null (reading 'getItem')`. A third-party script wrapped `localStorage` and failed when storage was partitioned.
2. **Sources → Pause on caught exceptions** showed the error was being swallowed by a `try/catch` in the checkout code, which then silently returned, so nothing was reported.
3. **Network** confirmed the order request was never sent: no `POST /api/orders` row.
4. **Local overrides** let them patch the minified checkout file in production, in their own browser only, to confirm the fix (handle missing storage, report the error) before deploying.

The real fix shipped the same afternoon. Developers had never seen the bug because their normal browser profiles had storage, extensions and cached data that real first-time visitors in privacy modes didn't. The team added "test in Incognito with Slow 4G and cache disabled" to their release checklist.

</DeepDive>

<DeepDive title="Security lens">

- **Self-XSS**: scammers ask users to paste code into the Console ("to unlock a feature"). That code runs with the user's session. Browsers show a warning for this; never paste code you don't understand, and teach users the same.
- **HAR files and screenshots** often contain cookies, `Authorization` headers and personal data. Sanitise them before sharing in tickets or chats.
- **Everything in DevTools is visible to any user** of your site: API responses, JavaScript source, source maps, storage. Never rely on hiding something in the frontend; enforce rules on the server.
- **Users can edit anything** (disabled buttons, hidden fields, prices in the DOM, requests via "Copy as fetch"). Validate every request server-side.
- **Local overrides and extensions** change what you see; when debugging security issues, also test in a clean profile.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How would you debug a CSS layout problem?">
Inspect the element in DevTools, check the box model for unexpected margin, padding or sizes, look in Styles for overridden or invalid declarations and in Computed for final values, use the flexbox or grid overlays, toggle rules on and off to isolate the cause, then copy the fix into the source.
</QA>

<QA q="How do you investigate why an API-driven list is empty?">
Open the Network tab, filter to Fetch/XHR, find the request, and check its status, request payload and response body. If the response is wrong, the issue is on the server or in the request parameters; if it's correct, debug the frontend code that renders it, using breakpoints.
</QA>

<QA q="How would you find what makes a page slow?">
Run Lighthouse for an overview, then record a Performance profile with CPU and network throttling, look for long tasks, heavy scripting, layout and paint on the main thread, and use Bottom-Up to find expensive functions. Check the Network waterfall for large or late-loading resources and request chains.
</QA>

<QA q="What is the difference between the Styles and Computed panes?">
Styles lists every CSS rule matching the element in cascade order, including overridden ones that are crossed out. Computed shows the final resolved value of each property after the cascade, inheritance and defaults, with a link to the rule that produced it.
</QA>

<QA q="How can you test a fix on a production site before deploying?">
Use DevTools local overrides to replace a production file or response header with an edited copy that is served only to your browser, or edit CSS and DOM live in Elements, then apply the confirmed change in the source code and deploy normally.
</QA>

</DeepDive>
