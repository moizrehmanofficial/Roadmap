<BigIdea>
<Tr>
<En>
A web page doesn't arrive as a picture. It arrives as **text**: HTML, CSS and JavaScript files. The browser turns that text into pixels in a fixed series of steps, often called the **critical rendering path**. First it **finds and asks** the server: DNS lookup, connection, HTTP request. As the HTML streams in, it **parses** it into the **DOM** (a tree of elements) and spots more files to download: stylesheets, scripts, images. CSS is parsed into the **CSSOM**. DOM + CSSOM become the **render tree** (only what's visible, with final styles). Then **layout** works out the size and position of every box, **paint** fills in the pixels (text, colours, borders, shadows), and **compositing** stacks layers onto the screen. JavaScript can pause parsing and can force these steps to run again. Knowing the order explains a lot: why scripts go at the end or get `defer`, why CSS blocks the first paint, why animating `transform` is smooth while animating `width` stutters, and what tools like Lighthouse are measuring.
</En>
<Ur>
Web page tasveer ki shakal me nahi aata. Ye **text** ki shakal me aata hai: HTML, CSS aur JavaScript files. Browser us text ko ek muqarrar silsile me pixels me badalta hai, jise aksar **critical rendering path** kehte hain. Pehle ye server ko **dhoondhta aur poochta** hai: DNS lookup, connection, HTTP request. Jaise jaise HTML aata hai, ye use **parse** kar ke **DOM** (elements ka darakht) banata hai aur mazeed download hone wali files pehchanta hai: stylesheets, scripts, images. CSS parse ho kar **CSSOM** banti hai. DOM + CSSOM mil kar **render tree** bante hain (sirf jo nazar aata hai, aakhri styles ke saath). Phir **layout** har dabbe ka size aur jagah nikalta hai, **paint** pixels bharta hai (text, rang, borders, shadows), aur **compositing** layers ko screen par tah dar tah rakhta hai. JavaScript parsing rok sakta hai aur in qadmon ko dobara chalne par majboor kar sakta hai. Tarteeb jaanna bohot kuch samjhata hai: scripts aakhir me kyun jate hain ya `defer` kyun lagta hai, CSS pehla paint kyun rokti hai, `transform` ki animation hamwar kyun hai jabke `width` ki atakti hai, aur Lighthouse jaise tools kya naapte hain.
</Ur>

## Picture it

<Tr>
<En>

Think of **building a house from a mailed plan**.

- First you need the architect's **address** (DNS), then you call and ask for the plan (HTTP request).
- The plan arrives **page by page**. You don't wait for the last page: as each page arrives you start listing rooms and how they connect. That list is the **DOM**.
- The plan mentions extra documents: "see the colour scheme" (CSS), "see the electrician's notes" (JavaScript), "see these photos" (images). You **order them all** as soon as you read the references.
- You can't decorate until you have the colour scheme, so the **painters wait for the CSS**. When the electrician's notes arrive without `defer`, **all work stops** until they're read, because they might say "knock down this wall".
- Then the builders measure every room (**layout**), the decorators paint them (**paint**), and finally the rooms are assembled into the finished house you can see (**compositing**).
- Moving a painting on the wall is quick (**composite only**). Moving a wall means re-measuring every room around it (**layout**).

</En>
<Ur>

**Daak se aaye naqshe se ghar banane** ka sochein.

- Pehle aap ko architect ka **pata** chahiye (DNS), phir aap call kar ke naqsha maangte hain (HTTP request).
- Naqsha **safha ba safha** aata hai. Aap aakhri safhe ka intezar nahi karte: har safha aate hi kamron aur un ke rabton ki list banana shuru kar dete hain. Wo list **DOM** hai.
- Naqsha mazeed kaghzaat ka zikr karta hai: "rangon ki scheme dekhein" (CSS), "electrician ke notes dekhein" (JavaScript), "ye tasveerein dekhein" (images). Hawale parhte hi aap **sab mangwa lete hain**.
- Rangon ki scheme ke baghair sajawat nahi ho sakti, isliye **painters CSS ka intezar karte hain**. Jab electrician ke notes `defer` ke baghair aate hain, **saara kaam ruk jata hai** jab tak parhe na jayen, kyun ke shayad wo kahen "ye deewar gira do".
- Phir mistri har kamra naapte hain (**layout**), sajane wale rang karte hain (**paint**), aur aakhir me kamre jor kar mukammal ghar banta hai jo aap dekhte hain (**compositing**).
- Deewar par tasveer khiskana tez hai (**sirf composite**). Deewar khiskane ka matlab us ke aas paas ke har kamre ko dobara naapna (**layout**).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="From URL to the first byte">

<Tr>
<En>

When you type `https://shop.example.com/products` and press Enter:

1. **URL parsing**: the browser splits it into scheme (`https`), host (`shop.example.com`) and path (`/products`). If it doesn't look like a URL, it becomes a search.
2. **Cache check**: a fresh copy in the HTTP cache (or a service worker) can skip the network entirely.
3. **DNS lookup**: the host becomes an IP address, checking the browser cache, the OS, then DNS servers.
4. **Connection**: a TCP connection (or QUIC for HTTP/3), then a **TLS handshake** to agree on encryption and verify the server's certificate.
5. **Request**: `GET /products` with headers (cookies, accepted languages, the browser's user agent).
6. **Response**: status `200`, headers (`content-type: text/html`, caching rules), then the body, which **streams** in chunks.

Steps 3 and 4 can take hundreds of milliseconds on mobile networks, which is why `<link rel="preconnect" href="https://cdn.example.com">` (warm up a connection early) and CDNs (servers close to users) help.

</En>
<Ur>

Jab aap `https://shop.example.com/products` likh kar Enter dabate hain:

1. **URL parsing**: browser ise scheme (`https`), host (`shop.example.com`) aur path (`/products`) me torta hai. Agar ye URL jaisa na lage to search ban jata hai.
2. **Cache check**: HTTP cache (ya service worker) me taaza copy network ko bilkul chhor sakti hai.
3. **DNS lookup**: host IP address ban jata hai, pehle browser cache, phir OS, phir DNS servers check kar ke.
4. **Connection**: TCP connection (ya HTTP/3 ke liye QUIC), phir encryption par ittefaq aur server ka certificate verify karne ke liye **TLS handshake**.
5. **Request**: headers (cookies, qubool zabanen, browser ka user agent) ke saath `GET /products`.
6. **Response**: status `200`, headers (`content-type: text/html`, caching ke qawaid), phir body, jo tukron me **behti** aati hai.

Qadam 3 aur 4 mobile networks par saikron milliseconds le sakte hain, isi liye `<link rel="preconnect" href="https://cdn.example.com">` (connection jaldi garam karna) aur CDNs (users ke qareeb servers) madad karte hain.

</Ur>
</Tr>

<Step title="A mini browser: HTML first, then everything it mentions">

<Tr>
<En>
Let's act out the next part in Node. A tiny server serves an HTML page plus a stylesheet, a script and an image. Our "browser" fetches the HTML, **scans it for references** like a real parser does, and fetches those in parallel.
</En>
<Ur>
Agla hissa Node me kar ke dekhte hain. Ek chhota server HTML page ke saath stylesheet, script aur image deta hai. Hamara "browser" HTML lata hai, asli parser ki tarah us me **hawale dhoondhta** hai, aur unhen ek saath lata hai.
</Ur>
</Tr>

```bash
cat > mini-browser.mjs <<'EOF'
import http from "node:http";

const files = {
  "/": ["text/html", `<!doctype html>
<html>
<head>
  <title>Mini Shop</title>
  <link rel="stylesheet" href="/style.css">
  <script src="/app.js" defer></script>
</head>
<body>
  <h1>Mini Shop</h1>
  <img src="/logo.png" alt="Logo">
</body>
</html>`],
  "/style.css": ["text/css", "h1 { color: teal; }"],
  "/app.js": ["text/javascript", "console.log('hi');"],
  "/logo.png": ["image/png", "PNG..."],
};

const server = http.createServer((req, res) => {
  const file = files[req.url];
  console.log("server got:", req.method, req.url);
  if (!file) { res.writeHead(404); return res.end(); }
  res.writeHead(200, { "content-type": file[0] });
  res.end(file[1]);
});

server.listen(0, async () => {
  const base = "http://localhost:" + server.address().port;

  const page = await fetch(base + "/");
  console.log("browser: got HTML", page.status, page.headers.get("content-type"));
  const html = await page.text();

  const found = [...html.matchAll(/(?:href|src)="([^"]+)"/g)].map((m) => m[1]);
  console.log("browser: found sub-resources", found);

  const results = await Promise.all(found.map((url) => fetch(base + url)));
  results.forEach((r, i) => console.log("browser: loaded", found[i], r.status, r.headers.get("content-type")));
  server.close();
});
EOF
node mini-browser.mjs
```

```text output
server got: GET /
browser: got HTML 200 text/html
browser: found sub-resources [ '/style.css', '/app.js', '/logo.png' ]
server got: GET /style.css
server got: GET /app.js
server got: GET /logo.png
browser: loaded /style.css 200 text/css
browser: loaded /app.js 200 text/javascript
browser: loaded /logo.png 200 image/png
```

<Happened>
<Tr>
<En>

- One request became **four**. The HTML is the map; everything else is discovered by reading it. A typical real page makes 50 to 100 requests.
- The `content-type` header tells the browser how to treat each file: parse as HTML, CSS, run as JavaScript, decode as an image.
- Real browsers have a **preload scanner** that looks ahead in the HTML for these references even while the main parser is paused by a script, so downloads start as early as possible.
- Resources the parser can't see (an image set only by JavaScript, a font referenced deep in CSS) are discovered **late**. `<link rel="preload">` is a way to announce them early.

</En>
<Ur>

- Ek request **chaar** ban gayin. HTML naqsha hai; baqi sab use parh kar pehchana jata hai. Aam asli page 50 se 100 requests karta hai.
- `content-type` header browser ko batata hai ke har file ke saath kya kare: HTML ki tarah parse, CSS, JavaScript ki tarah chalana, image ki tarah decode.
- Asli browsers ke paas **preload scanner** hota hai jo main parser ke script ki wajah se ruke hone ke dauran bhi HTML me aage in hawalon ko dekhta hai, taa ke downloads jitna jaldi ho sake shuru hon.
- Jo resources parser nahi dekh sakta (sirf JavaScript se set hone wali image, CSS me gehrai me likha font) wo **der se** pehchane jate hain. `<link rel="preload">` unhen jaldi batane ka tareeqa hai.

</Ur>

<Step title="Parsing HTML into the DOM tree">

<Tr>
<En>
The parser reads tags and text and builds a **tree of nodes**: elements contain other elements and text nodes. This tree, the **DOM**, is what JavaScript reads and changes. This live preview walks its own DOM and prints it.
</En>
<Ur>
Parser tags aur text parh kar **nodes ka darakht** banata hai: elements ke andar doosre elements aur text nodes hote hain. Ye darakht, **DOM**, wahi hai jise JavaScript parhta aur badalta hai. Ye live preview apna DOM ghoom kar print karta hai.
</Ur>
</Tr>

```html preview-js h=330
<main id="shop">
  <h1>Mini Shop</h1>
  <p class="intro">Fresh <strong>coffee</strong> mugs.</p>
  <ul><li>Mug</li><li>Lamp</li></ul>
</main>
<pre id="tree" style="background:#f1f5f9;padding:8px"></pre>
<script>
  function draw(node, depth) {
    const pad = "  ".repeat(depth);
    if (node.nodeType === Node.TEXT_NODE) {
      const text = node.textContent.trim();
      return text ? pad + '"' + text + '"\n' : "";
    }
    let out = pad + node.nodeName.toLowerCase() + "\n";
    for (const child of node.childNodes) out += draw(child, depth + 1);
    return out;
  }
  document.querySelector("#tree").textContent = draw(document.querySelector("#shop"), 0);
</script>
```

<Step title="Scripts pause the parser: order of events">

<Tr>
<En>

A plain `<script>` **stops HTML parsing** until it has downloaded and run, because it might change the document. A script in `<head>` therefore runs when the body doesn't exist yet. This preview records the exact order: a head script, an end-of-body script, a `defer` script, `DOMContentLoaded` and `load`.

</En>
<Ur>

Saada `<script>` download ho kar chalne tak **HTML parsing rok deta hai**, kyun ke ye document badal sakta hai. Isliye `<head>` ka script tab chalta hai jab body abhi maujood hi nahi hoti. Ye preview bilkul tarteeb record karta hai: head script, body ke aakhir ka script, `defer` script, `DOMContentLoaded` aur `load`.

</Ur>
</Tr>

```html preview-js h=230

<head>

    window.log = [];
    log.push("1. head script runs, readyState = " + document.readyState +
             ", #price exists? " + (document.querySelector("#price") !== null));
    document.addEventListener("DOMContentLoaded", () => log.push("4. DOMContentLoaded: HTML fully parsed"));
    window.addEventListener("load", () => {
      log.push("5. load: images and other files finished too");
      document.querySelector("#out").textContent = log.join("\n");
    });
  </script>
  <script defer src="data:text/javascript,log.push('3. defer script runs after parsing, %23price says: ' + document.querySelector('%23price').textContent)"></script>

<body>
```

<Step title="defer, async and type=module">

<Tr>
<En>

| Tag | Downloads | Runs | Order between scripts | Use for |
| --- | --- | --- | --- | --- |
| `<script src>` | blocks parsing | immediately | in order | almost never in `<head>` |

| `<script async src>` | in parallel | as soon as downloaded (pauses parsing then) | **any order** | independent scripts: analytics, ads |
| `<script type="module" src>` | in parallel | like `defer` | in order | modern code with `import` |
| inline `<script>` | none | immediately | in order | tiny snippets; put at end of body |

```text
         ↳ download ──┘
```

<Step title="CSS, the CSSOM and the render tree">

<Tr>
<En>

CSS is parsed into the **CSSOM**. The browser then walks the DOM and, for each node, works out its **computed style** from all matching rules (the cascade). Visible nodes plus their styles form the **render tree**.

- CSS is **render-blocking**: the browser won't paint until the stylesheets in `<head>` have loaded, otherwise you'd see a flash of unstyled content and then a jump.
- `display: none` elements are **not** in the render tree (no box, no space). `visibility: hidden` elements **are**: they take space but aren't painted.
- `<head>`, `<script>` and `<meta>` are in the DOM but never in the render tree.
- Big CSS files delay the first paint. Common fixes: remove unused CSS (Tailwind does this at build), inline the small amount of "critical" CSS needed for the top of the page, and load the rest later.

</En>
<Ur>

CSS parse ho kar **CSSOM** banti hai. Phir browser DOM me chalta hai aur har node ke liye tamam milne wale qawaid (cascade) se us ka **computed style** nikalta hai. Nazar aane wale nodes aur un ke styles mil kar **render tree** banate hain.

- CSS **render-blocking** hai: `<head>` ki stylesheets load hone tak browser paint nahi karta, warna aap ko bina style ke content ki jhalak aur phir uchhal nazar aata.
- `display: none` elements render tree me **nahi** hote (na dabba, na jagah). `visibility: hidden` elements **hote** hain: jagah lete hain magar paint nahi hote.
- `<head>`, `<script>` aur `<meta>` DOM me hain magar render tree me kabhi nahi.
- Bari CSS files pehla paint der se karti hain. Aam hal: ghair istemal CSS hatayen (Tailwind build par ye karta hai), page ke upar wale hisse ke liye zaroori thori si "critical" CSS inline karein, aur baqi baad me load karein.

</Ur>
</Tr>

```html preview-js h=200
  .ghost { visibility: hidden; }
</style>
<div class="box">A: normal</div>
<div class="box gone">B: display none</div>
<div class="box ghost">C: visibility hidden</div>
<div class="box">D: normal</div>
<pre id="out"></pre>
<script>
  const lines = [...document.querySelectorAll(".box")].map((el) => {
    const r = el.getBoundingClientRect();
```

- `getBoundingClientRect()` reads layout information. Reading it forces the browser to make sure layout is up to date, which matters in a moment.

</En>
<Ur>

- A aur D bane. B **koi khaali jagah nahi** chhorta: us ka koi dabba hi nahi, isliye us ki height `0` hai. C A jitni **khaali jagah** chhorta hai: us ka dabba hai (layout hua) magar paint nahi hua.
- `getBoundingClientRect()` layout ki maloomat parhta hai. Ise parhna browser ko majboor karta hai ke layout taaza ho, jo zara der me ahem hoga.

<Step title="Layout, paint and composite: cheap and expensive changes">

<Tr>
<En>

After the first frame, every change you make goes back through some of the pipeline. Which steps depends on **what** you change:

| You change | Layout | Paint | Composite | Cost |
| --- | --- | --- | --- | --- |
| `width`, `height`, `margin`, `padding`, `top`/`left`, font size, adding elements | ✔ | ✔ | ✔ | expensive |
| `color`, `background`, `box-shadow`, `border-color` | | ✔ | ✔ | medium |
| `transform` (move, scale, rotate), `opacity` | | | ✔ | cheap |

A screen refreshes about **60 times per second**, so each frame has roughly **16 ms** for JavaScript, style, layout, paint and composite together. If a frame takes longer, it's dropped, and you see stutter ("jank").

</En>
<Ur>

Pehle frame ke baad aap ki har tabdeeli pipeline ke kuch hisse se dobara guzarti hai. Kaun se qadam, ye is par munhasir hai ke aap **kya** badalte hain:

| Aap badalte hain | Layout | Paint | Composite | Qeemat |
| --- | --- | --- | --- | --- |
| `width`, `height`, `margin`, `padding`, `top`/`left`, font size, elements jorna | ✔ | ✔ | ✔ | mehnga |
| `color`, `background`, `box-shadow`, `border-color` | | ✔ | ✔ | darmiyana |
| `transform` (khiskana, bara karna, ghumana), `opacity` | | | ✔ | sasta |

Screen taqreeban **60 dafa fi second** refresh hoti hai, isliye har frame ke paas JavaScript, style, layout, paint aur composite sab ke liye mil kar taqreeban **16 ms** hote hain. Agar frame zyada le to wo gir jata hai, aur aap atkan ("jank") dekhte hain.

</Ur>
</Tr>

<Step title="Layout thrashing: reading and writing in a loop">

<Tr>
<En>
Writing a style marks layout as "dirty". Reading a layout value (`offsetWidth`, `getBoundingClientRect()`, `scrollTop`) then **forces** the browser to recalculate layout immediately. Doing write, read, write, read in a loop forces layout hundreds of times. Click both buttons.
</En>
<Ur>
Style likhna layout ko "ganda" nishaan zad kar deta hai. Phir layout ki value parhna (`offsetWidth`, `getBoundingClientRect()`, `scrollTop`) browser ko foran layout dobara nikalne par **majboor** karta hai. Loop me likho, parho, likho, parho karna layout ko saikron dafa majboor karta hai. Dono buttons dabayen.
</Ur>
</Tr>

```html preview-js h=200
<button id="slow">Read inside the loop</button>
<button id="fast">Read first, then write</button>
<p id="result">Click a button.</p>
<div id="boxes"></div>
<script>
  const boxes = document.querySelector("#boxes");
  for (let i = 0; i < 400; i++) {
    const d = document.createElement("div");
    d.style.cssText = "height:4px;background:teal;margin:1px 0;width:50px";
    boxes.appendChild(d);
  }
  const all = [...boxes.children];
  function run(label, fn) {
    const t0 = performance.now();
    fn();
    document.querySelector("#result").textContent = label + ": " + (performance.now() - t0).toFixed(1) + " ms";
  }
  document.querySelector("#slow").onclick = () => run("Interleaved read/write", () => {
    for (const d of all) d.style.width = (d.offsetWidth + 1) + "px";
  });
  document.querySelector("#fast").onclick = () => run("Batched", () => {
    const widths = all.map((d) => d.offsetWidth);
    all.forEach((d, i) => (d.style.width = widths[i] + 1 + "px"));
  });
</script>
```

<Happened>
<Tr>
<En>

- When we tested in Chromium, the interleaved version took about **69 ms** and the batched version about **0.6 ms**: over 100 times slower for the same result. Your numbers will differ, but the gap will be huge.
- The slow loop reads `offsetWidth` right after the previous write, forcing **400 layouts**. The fast version does all reads first (one layout), then all writes (layout once, later, before the next frame).
- 69 ms is four dropped frames: enough to make a list or a drag feel sticky. In DevTools Performance recordings this shows up as purple "Layout" blocks with a warning "Forced reflow".

</En>
<Ur>

- Jab humne Chromium me test kiya, mila jula version taqreeban **69 ms** aur ikattha version taqreeban **0.6 ms** laga: ek hi nateeje ke liye 100 guna se zyada sust. Aap ke numbers mukhtalif honge, magar farq bohot bara hoga.
- Sust loop pichhli likhai ke foran baad `offsetWidth` parhta hai, **400 layouts** par majboor karte hue. Tez version pehle saari parhai karta hai (ek layout), phir saari likhai (layout ek dafa, baad me, agle frame se pehle).
- 69 ms chaar gire hue frames hain: list ya drag ko chipchipa mehsoos karane ke liye kafi. DevTools Performance recordings me ye "Forced reflow" warning wale jamni "Layout" blocks ki shakal me dikhta hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Blocking script in the head">

```text
<head>
  <script src="/app.js"></script>   <!-- parsing stops; DOM not ready -->
</head>
// app.js: document.querySelector("#cart").addEventListener(...)
// TypeError: Cannot read properties of null (reading 'addEventListener')
```

</Bad>
<Good title="defer it">

```text
<head>
  <script src="/app.js" defer></script>   <!-- downloads in parallel -->
</head>
// runs after the HTML is parsed: #cart exists
```

</Good>
</Compare>

<Compare>
<Bad title="Images without dimensions">

```text
<img src="/hero.jpg" alt="Spring sale">
<!-- takes 0px until it loads, then pushes everything down: high CLS -->
```

</Bad>
<Good title="Reserve the space">

```text
<img src="/hero.jpg" alt="Spring sale" width="1200" height="600">
<!-- with CSS img { max-width: 100%; height: auto; } the box keeps
     its aspect ratio from the start, so nothing jumps -->
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Animating `width`, `top` or `left`** instead of `transform`.
- **Reading layout values inside loops that also write styles** (layout thrashing).
- **Huge CSS bundles in `<head>`** that delay the first paint; remove unused CSS.
- **Loading important images lazily** (`loading="lazy"` on the hero hurts LCP; use it for images further down).
- **Waiting for `load`** to run app code when `DOMContentLoaded` (or `defer`) is enough.
- **Long JavaScript tasks** on click; split work up or move it to a Web Worker (later lesson).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- `transform` ke bajaye **`width`, `top` ya `left` animate karna**.
- **Aise loops me layout values parhna jo styles bhi likhte hain** (layout thrashing).
- **`<head>` me bohot bare CSS bundles** jo pehla paint der se karayen; ghair istemal CSS hatayen.
- **Ahem images lazy load karna** (hero par `loading="lazy"` LCP ko nuqsaan deta hai; neeche ki images ke liye lagayen).
- Jab `DOMContentLoaded` (ya `defer`) kafi ho tab app code ke liye **`load` ka intezar karna**.
- Click par **lambe JavaScript kaam**; kaam baantein ya Web Worker me le jayen (aage ka lesson).

</Ur>
</Tr>

<DeepDive title="More about the rendering pipeline">

**Browser processes.** Modern browsers split work: a browser process (tabs, address bar), a network process, a GPU process and one **renderer process** per site (for security and stability). Inside the renderer, the **main thread** runs HTML parsing, JavaScript, style, layout and paint; the **compositor thread** can scroll and animate composited layers even while the main thread is busy.

**Layers.** Elements with `transform` animations, `will-change: transform`, `position: fixed`, videos and canvases may get their own compositor layers. Too many layers use a lot of memory, so use `will-change` sparingly.

**Resource hints.** `<link rel="preconnect">` (open a connection early), `rel="dns-prefetch"`, `rel="preload"` (fetch a critical font or image now), `rel="prefetch"` (fetch something the next page will need), and `fetchpriority="high"` on the LCP image.

**HTTP/2 and HTTP/3.** Many requests share one connection (multiplexing), so "combine all files into one" matters less than it used to; caching and smaller total bytes matter more.

**Fonts.** Web fonts can cause invisible text (FOIT) or a style swap (FOUT). `font-display: swap` shows fallback text immediately; `next/font` self-hosts fonts and sets sizes to avoid layout shift.

**`requestAnimationFrame`.** Runs your callback right before the next frame's style/layout/paint, the right place for JavaScript-driven animations and batched DOM writes.

**`content-visibility: auto`.** Lets the browser skip layout and paint for off-screen sections of long pages.

**Server rendering.** Sending ready-made HTML (SSR/SSG in Next.js) lets the browser parse and paint content before any JavaScript runs, which usually improves LCP compared with an empty page filled in by client JavaScript.

</DeepDive>

<DeepDive title="Real world: the 4-second blank homepage">

A small online store's homepage showed a white screen for about four seconds on phones, and the bounce rate was high. Lighthouse gave an LCP of 5.8 s.

The Network waterfall told the story:

1. In `<head>`: a chat widget script **without** `defer` (blocking parsing for about 900 ms on 4G), and three CSS files including a whole icon library (180 KB) for 12 icons.
2. The hero image was a 2.4 MB JPEG set as a CSS background, so the preload scanner couldn't see it until the CSS had loaded and been applied.
3. Product cards had images without `width`/`height`; CLS was 0.31 as they loaded.

The fixes, in order of impact:

- Chat widget → `async`, and loaded only after the user scrolled or after 5 seconds.
- Icon library replaced with 12 inline SVGs; unused CSS removed; CSS dropped to 22 KB.
- Hero became an `<img>` in the HTML with `fetchpriority="high"`, served as a 140 KB AVIF via `next/image`.
- Every product image got dimensions.

LCP fell to 1.9 s, CLS to 0.02, and mobile conversion rose noticeably the following month. None of it needed new features, just respect for the rendering pipeline.

</DeepDive>

<DeepDive title="Security lens">

- **Third-party scripts run with full access to your page** (DOM, cookies not marked `HttpOnly`, form inputs). Every `<script src="https://other-site…">` is a trust decision; use Subresource Integrity (`integrity="sha384-…"`) for fixed files from CDNs.
- **Content Security Policy (CSP)** headers tell the browser which script sources may run, limiting the damage of XSS.
- **HTTPS everywhere**: the TLS step protects the HTML and every sub-resource from being read or modified in transit; mixed (HTTP) content is blocked.
- **Renderer process isolation** (site isolation) is why a malicious site in one tab can't read another tab's memory, even with CPU bugs like Spectre.
- **Don't leak secrets into HTML**: anything in the page source, including inline JSON for hydration, is visible to everyone.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What happens when you type a URL and press Enter?">
The browser parses the URL, checks caches, resolves the domain with DNS, opens a TCP or QUIC connection with a TLS handshake, sends an HTTP request, and receives the HTML. It parses the HTML into the DOM while fetching discovered CSS, JavaScript and images, builds the CSSOM, runs scripts, creates the render tree, then performs layout, paint and compositing to show the page.
</QA>

<QA q="What is the difference between defer and async?">
Both download scripts in parallel without blocking parsing. defer scripts execute in document order after parsing finishes and before DOMContentLoaded. async scripts execute as soon as each one finishes downloading, in any order, pausing parsing at that moment.
</QA>

<QA q="What is the critical rendering path?">
The sequence of steps needed to render the first view of a page: fetching and parsing HTML into the DOM, CSS into the CSSOM, combining them into the render tree, layout and paint. Optimizing it means reducing render-blocking resources and the bytes and round trips needed before first paint.
</QA>

<QA q="What is reflow and how do you avoid unnecessary reflows?">
Reflow, or layout, is recalculating the geometry of elements. Avoid it by animating transform and opacity instead of layout properties, batching DOM reads before writes, avoiding layout reads in loops, and changing classes once instead of many inline styles.
</QA>

<QA q="What do LCP, INP and CLS measure?">
LCP measures when the largest content element is rendered, INP measures the responsiveness of interactions until the next paint, and CLS measures unexpected layout shifts during the page's life.
</QA>

</DeepDive>

  <Term name="DOMContentLoaded">Event fired when the HTML is fully parsed.</Term>
