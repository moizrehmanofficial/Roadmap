<BigIdea>
<Tr>
<En>
In the early web, every change meant loading a whole new page. Today a page can talk to a server **in the background**: send a search term, get back JSON, and update only the list. The built-in tool for this is **`fetch(url, options)`**. It returns a **promise** of a **`Response`**: you `await` it, check `response.ok` / `response.status`, then read the body with `await response.json()` (or `.text()`, `.blob()`). To send data, you pass `method: "POST"`, a `body` (usually `JSON.stringify(data)` or a `FormData`) and the right `content-type` header. A few surprises trip up everyone. `fetch` only rejects when the **network** fails, **not** on 404 or 500, so you must check `ok` yourself. Requests can hang, so you need **timeouts**. A slow old response can overwrite a newer one, so you **cancel** stale requests with `AbortController`. And in browsers, rules like **CORS** and **cookies** decide what you're allowed to request. Get these right, show clear loading and error states, and your app feels fast and reliable.
</En>
<Ur>
Shuru ke web me har tabdeeli ka matlab poora naya page load karna tha. Aaj page server se **pas-e-parda** baat kar sakta hai: search term bheje, JSON wapas le, aur sirf list update kare. Is ka bana banaya auzaar **`fetch(url, options)`** hai. Ye **`Response`** ka **promise** wapas karta hai: aap use `await` karte hain, `response.ok` / `response.status` check karte hain, phir `await response.json()` (ya `.text()`, `.blob()`) se body parhte hain. Data bhejne ke liye aap `method: "POST"`, `body` (aam taur par `JSON.stringify(data)` ya `FormData`) aur sahi `content-type` header dete hain. Chand hairat angez baatein sab ko girati hain. `fetch` sirf **network** fail hone par reject karta hai, 404 ya 500 par **nahi**, isliye `ok` khud check karna parta hai. Requests atak sakti hain, isliye **timeouts** chahiyen. Sust purana jawab naye ko mita sakta hai, isliye `AbortController` se purani requests **mansookh** karte hain. Aur browsers me **CORS** aur **cookies** jaise qawaid tay karte hain ke aap kya request kar sakte hain. Ye sahi kar lein, loading aur error ki saaf halaten dikhayen, aur aap ki app tez aur qabil-e-bharosa mehsoos hogi.
</Ur>

## Picture it

<Tr>
<En>

Think of **ordering at a restaurant counter with a pager**.

- You place an order (**request**: what you want, plus details like "no onions" = **headers** and **body**).
- You immediately get a **pager** (a **promise**). You can sit down and do other things; the page stays usable.
- When the pager buzzes, you get a **tray** (the `Response`) with a **receipt** on top: "200 OK" or "404 sold out" (**status**). Getting a tray doesn't mean you got food: you must **read the receipt** (`res.ok`). This is why `fetch` doesn't "fail" on 404: the counter did answer you.
- Only if the counter is **closed** or the line is cut (no network) does the pager say "failed" (**rejection**).
- If you change your mind ("actually, a large instead"), you **cancel** the first order so you don't end up with two (**AbortController**).
- If nobody answers for ten minutes, you give up (**timeout**).

</En>
<Ur>

**Pager wale restaurant counter par order** ka sochein.

- Aap order dete hain (**request**: kya chahiye, aur "piyaz nahi" jaisi tafseelat = **headers** aur **body**).
- Aap ko foran **pager** milta hai (**promise**). Aap baith kar doosre kaam kar sakte hain; page istemal ke qabil rehta hai.
- Jab pager bajta hai, aap ko **tray** milti hai (`Response`) jis par **raseed** hoti hai: "200 OK" ya "404 khatam" (**status**). Tray milne ka matlab ye nahi ke khana mila: **raseed parhni** parti hai (`res.ok`). Isi liye `fetch` 404 par "fail" nahi hota: counter ne jawab to diya.
- Sirf agar counter **band** ho ya line kat jaye (network nahi) to pager kehta hai "nakam" (**rejection**).
- Agar aap ka iraada badle ("asal me bara chahiye"), aap pehla order **mansookh** karte hain taa ke do na mil jayen (**AbortController**).
- Agar das minute koi jawab na de to aap chhor dete hain (**timeout**).

</Ur>
</Tr>

<Step title="Your first GET request">

<Tr>
<En>
`await fetch(url)` gives you a `Response`. Its **status and headers arrive first**; the body is read separately with `await res.json()`.
</En>
<Ur>
`await fetch(url)` aap ko `Response` deta hai. Is ka **status aur headers pehle aate hain**; body alag se `await res.json()` se parhi jati hai.
</Ur>
</Tr>

```bash
cat > server.mjs <<'EOF'
import http from "node:http";

const products = [
  { id: 1, name: "Mug", price: 12 },
  { id: 2, name: "Desk Lamp", price: 30 },
  { id: 3, name: "Floor Lamp", price: 85 },
];
let flakyCalls = 0;

function send(res, status, data, headers = {}) {
  res.writeHead(status, { "content-type": "application/json", ...headers });
  res.end(JSON.stringify(data));
}

async function readBody(req) {
  let body = "";
  for await (const chunk of req) body += chunk;
  return body;
}

const server = http.createServer(async (req, res) => {
  const url = new URL(req.url, "http://localhost");
  const path = url.pathname;

  if (req.method === "GET" && path === "/api/products") {
    const q = (url.searchParams.get("q") ?? "").toLowerCase();
    const max = Number(url.searchParams.get("maxPrice") ?? Infinity);
    return send(res, 200, products.filter((p) => p.name.toLowerCase().includes(q) && p.price <= max));
  }
  const match = path.match(/^\/api\/products\/(\d+)$/);
  if (req.method === "GET" && match) {
    const p = products.find((x) => x.id === Number(match[1]));
    return p ? send(res, 200, p) : send(res, 404, { error: "Product not found" });
  }
  if (path === "/api/boom") return send(res, 500, { error: "Database unavailable" });
  if (req.method === "POST" && path === "/api/orders") {
    const type = req.headers["content-type"] ?? "";
    const raw = await readBody(req);
    let data = null;
    try { data = JSON.parse(raw); } catch {}
    if (!type.startsWith("application/json") || !data || !Number.isInteger(data.productId) || !(data.qty > 0)) {
      return send(res, 400, { error: "Send JSON with productId and qty", got: { contentType: type, body: raw } });
    }
    return send(res, 201, { id: "A-1001", ...data, status: "pending" }, { location: "/api/orders/A-1001" });
  }
  if (req.method === "POST" && path === "/api/contact") {
    const type = req.headers["content-type"];
    const form = await new Response(await readBody(req), { headers: { "content-type": type } }).formData();
    const fields = [...form].map(([k, v]) => k + "=" + (typeof v === "string" ? v : v.name + " (" + v.size + " bytes)"));
    return send(res, 200, { contentType: type.split(";")[0], fields });
  }
  if (path === "/api/slow") {
    const ms = Number(url.searchParams.get("ms") ?? 1000);
    const timer = setTimeout(() => send(res, 200, { done: true, waited: ms }), ms);
    req.on("close", () => clearTimeout(timer));
    return;
  }
  if (path === "/api/flaky") {
    flakyCalls++;
    return flakyCalls < 3 ? send(res, 503, { error: "Try again" }) : send(res, 200, { ok: true, attempts: flakyCalls });
  }
  send(res, 404, { error: "No route" });
});

export function start() {
  return new Promise((resolve) => {
    server.listen(0, () => resolve({ base: "http://localhost:" + server.address().port, stop: () => server.close() }));
  });
}
EOF
cat > get.mjs <<'EOF'
import { start } from "./server.mjs";
const { base, stop } = await start();

const res = await fetch(base + "/api/products");
console.log("status:", res.status, res.statusText, "| ok:", res.ok);
console.log("content-type:", res.headers.get("content-type"));
const products = await res.json();
console.log("products:", products);
console.log("first name:", products[0].name);

stop();
EOF
node get.mjs
```

```text output
products: [
```

<Happened>
<Tr>
<En>

- There are **two awaits**: one for the response to start arriving (status + headers), one for the full body to download and parse.
- `res.json()` parses the body as JSON. Use `res.text()` for plain text/HTML, `res.blob()` for images and files, `res.arrayBuffer()` for raw bytes. The body can be read **only once**.
- `res.headers.get(...)` is case-insensitive. The server said `application/json`, so `.json()` is safe.
- In the browser, the same code runs in your page script or a React effect, and the request appears in DevTools → **Network**.

</En>
<Ur>

- **Do awaits** hain: ek response ke aana shuru hone (status + headers) ka, ek poori body ke download aur parse hone ka.
- `res.json()` body ko JSON ki tarah parse karta hai. Saade text/HTML ke liye `res.text()`, images aur files ke liye `res.blob()`, kache bytes ke liye `res.arrayBuffer()` lein. Body **sirf ek dafa** parhi ja sakti hai.
- `res.headers.get(...)` bare chhote huroof ki parwah nahi karta. Server ne `application/json` kaha, isliye `.json()` mehfooz hai.
- Browser me yahi code aap ke page script ya React effect me chalta hai, aur request DevTools → **Network** me nazar aati hai.

</Ur>
</Tr>
</Happened>

<Step title="fetch does not throw on 404 or 500">

<Tr>
<En>
This surprises almost everyone. A 404 or 500 is still a **valid HTTP response**, so the promise **resolves**. Only a **network failure** (no connection, DNS failure, CORS block, abort) makes it reject.
</En>
<Ur>
Ye taqreeban har kisi ko hairan karta hai. 404 ya 500 phir bhi **jaiz HTTP response** hai, isliye promise **resolve** hota hai. Sirf **network ki nakami** (connection nahi, DNS fail, CORS rok, abort) use reject karati hai.
</Ur>
</Tr>

```bash
cat > errors.mjs <<'EOF'
import { start } from "./server.mjs";
const { base, stop } = await start();

for (const path of ["/api/products/2", "/api/products/99", "/api/boom"]) {
  const res = await fetch(base + path);
  const body = await res.json();
  console.log(path, "→", res.status, res.ok, JSON.stringify(body));
}

try {
  await fetch("http://localhost:1/api/products");
} catch (error) {
  console.log("network failure:", error.name + ":", error.message);
}
stop();
EOF
node errors.mjs
```

```text output
/api/products/2 → 200 true {"id":2,"name":"Desk Lamp","price":30}
/api/products/99 → 404 false {"error":"Product not found"}
/api/boom → 500 false {"error":"Database unavailable"}
```

<Happened>
<Tr>
<En>

- The 404 and 500 responses came back normally with `ok: false`, and their bodies contain useful error messages from the server.
- Port 1 has nothing listening, so the request couldn't even be sent: that's the only case that threw. (In browsers the message is "Failed to fetch" or "NetworkError when attempting to fetch resource".)
- Code that does `const data = await (await fetch(url)).json()` without checking `ok` will happily treat `{ "error": "Product not found" }` as product data.

</En>
<Ur>

- 404 aur 500 responses aam tarah `ok: false` ke saath wapas aaye, aur un ki bodies me server ke kaam ke error paighaam hain.
- Port 1 par koi nahi sun raha, isliye request bheji hi na ja saki: sirf yahi surat throw hui. (Browsers me paighaam "Failed to fetch" ya "NetworkError when attempting to fetch resource" hota hai.)
- Jo code `ok` check kiye baghair `const data = await (await fetch(url)).json()` karta hai wo khushi se `{ "error": "Product not found" }` ko product ka data samjhega.

</Ur>
</Tr>

<Step title="A small getJson helper that does throw">

<Tr>
<En>
Wrap `fetch` once so every call checks `ok`, parses JSON only when the server sent JSON, and throws a useful error with the status. Then callers can handle 404 differently from 500.
</En>
<Ur>
`fetch` ko ek dafa lapetein taa ke har call `ok` check kare, JSON sirf tab parse kare jab server ne JSON bheja ho, aur status ke saath kaam ka error throw kare. Phir call karne wale 404 ko 500 se alag sambhal sakte hain.
</Ur>
</Tr>

```bash
cat > helper.mjs <<'EOF'
import { start } from "./server.mjs";
const { base, stop } = await start();

class HttpError extends Error {
  constructor(status, body) {
    super("HTTP " + status + ": " + (body?.error ?? "Request failed"));
    this.status = status;
    this.body = body;
  }
}

async function getJson(url, options = {}) {
  const res = await fetch(url, { headers: { accept: "application/json" }, ...options });
  const isJson = res.headers.get("content-type")?.includes("application/json");
  const body = isJson ? await res.json() : await res.text();
  if (!res.ok) throw new HttpError(res.status, body);
  return body;
}

console.log(await getJson(base + "/api/products/1"));
for (const path of ["/api/products/99", "/api/boom"]) {
  try {
    await getJson(base + path);
  } catch (error) {
    if (error instanceof HttpError && error.status === 404) console.log("show 'not found' page:", error.message);
    else console.log("show error banner:", error.message);
  }
}
stop();
EOF
node helper.mjs
```

```text output
{ id: 1, name: 'Mug', price: 12 }
show 'not found' page: HTTP 404: Product not found
show error banner: HTTP 500: Database unavailable
```

<Happened>
<Tr>
<En>

- One place handles headers, parsing and status checks; every feature uses `getJson`.
- `HttpError` carries `status` and the server's `body`, so the UI can show "not found" for 404, "please log in" for 401, and a generic banner for 5xx.
- Checking `content-type` before `.json()` avoids a confusing `SyntaxError` when a proxy or server returns an HTML error page.
- In TypeScript, pass a zod schema to this helper (previous module) so the returned data is validated and typed.

</En>
<Ur>

- Ek jagah headers, parsing aur status checks sambhalti hai; har feature `getJson` istemal karta hai.
- `HttpError` `status` aur server ki `body` saath rakhta hai, isliye UI 404 ke liye "nahi mila", 401 ke liye "login karein", aur 5xx ke liye aam banner dikha sakta hai.
- `.json()` se pehle `content-type` check karna tab ulajhane wale `SyntaxError` se bachata hai jab proxy ya server HTML error page wapas kare.
- TypeScript me is helper ko zod schema dein (pichhla module) taa ke wapas aane wala data validated aur typed ho.

</Ur>
</Tr>
</Happened>

<Step title="POSTing JSON">

<Tr>
<En>
To send data: `method: "POST"`, a `content-type: application/json` header, and the body **as a string** with `JSON.stringify`. The second request makes the classic mistake of passing an object directly.
</En>
<Ur>
Data bhejne ke liye: `method: "POST"`, `content-type: application/json` header, aur body `JSON.stringify` se **string ki shakal me**. Doosri request mashhoor ghalti karti hai: object seedha de deti hai.

```bash
});
console.log(res.status, res.headers.get("location"));
console.log(await res.json());

const wrong = await fetch(base + "/api/orders", {
  method: "POST",
  body: { productId: 2, qty: 3 },
});
console.log(wrong.status, await wrong.json());
stop();
EOF
```

```text output
  got: { contentType: 'text/plain;charset=UTF-8', body: '[object Object]' }
}
```

<Happened>
<Tr>
<En>

- The server answered **201 Created** with a `location` header pointing at the new order, and echoed the saved data.

</En>
<Ur>

</Ur>

<Step title="Query strings with URL and URLSearchParams">

<Tr>
<En>

<Step title="Timeouts and cancelling stale requests">

<Tr>
<En>
By default a fetch can wait for a very long time. `AbortSignal.timeout(ms)` gives up after a limit. An `AbortController` lets you cancel on demand, for example the previous search when the user types another letter. Here three searches start almost together, and the **older ones are slower**, exactly the situation that shows wrong results.
</En>
<Ur>
Default me fetch bohot lamba intezar kar sakta hai. `AbortSignal.timeout(ms)` hadd ke baad chhor deta hai. `AbortController` jab chaho mansookh karne deta hai, maslan jab user aur harf likhe to pichhli search. Yahan teen searches taqreeban saath shuru hoti hain, aur **purani zyada sust** hain, bilkul wo soorat jo ghalat nataij dikhati hai.
</Ur>
</Tr>

```bash
cat > abort.mjs <<'EOF'
import { start } from "./server.mjs";
const { base, stop } = await start();

try {
  await fetch(base + "/api/slow?ms=2000", { signal: AbortSignal.timeout(200) });
} catch (error) {
  console.log("timeout:", error.name, "-", error.message);
}

let current;
async function search(term, delay) {
  current?.abort();
  current = new AbortController();
  try {
    const res = await fetch(base + "/api/slow?ms=" + delay, { signal: current.signal });
    console.log("showing results for", JSON.stringify(term), await res.json());
  } catch (error) {
    if (error.name === "AbortError") console.log("cancelled stale request for", JSON.stringify(term));
    else throw error;
  }
}
await Promise.all([search("la", 300), search("lam", 200), search("lamp", 100)]);
stop();
EOF
node abort.mjs
```

```text output
timeout: TimeoutError - The operation was aborted due to timeout
cancelled stale request for "la"
cancelled stale request for "lam"
showing results for "lamp" { done: true, waited: 100 }
```

<Happened>
<Tr>
<En>

- The 2-second request was abandoned after 200 ms with a `TimeoutError`, so the UI can show "This is taking too long, retry?".
- Each new `search` aborted the previous controller. Without that, `"la"` (the slowest) would have finished **last** and replaced the `"lamp"` results with results for `"la"`, a real bug in many search boxes.
- Aborted fetches reject with `AbortError`; treat that as "nothing to show", not as an error banner.
- One signal can cancel many requests, and you can combine signals with `AbortSignal.any([userCancel, AbortSignal.timeout(5000)])`.

</En>
<Ur>

- 2 second wali request `TimeoutError` ke saath 200 ms baad chhor di gayi, taa ke UI "Ye bohot der le raha hai, dobara koshish?" dikha sake.
- Har nayi `search` ne pichhla controller abort kiya. Is ke baghair `"la"` (sab se sust) **aakhir me** khatam hoti aur `"lamp"` ke nataij ko `"la"` ke nataij se badal deti, bohot se search boxes ka asli bug.
- Abort hui fetches `AbortError` ke saath reject hoti hain; ise "dikhane ko kuch nahi" samjhein, error banner nahi.
- Ek signal kai requests mansookh kar sakta hai, aur aap signals ko `AbortSignal.any([userCancel, AbortSignal.timeout(5000)])` se mila sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Parallel requests: Promise.all and allSettled">

<Tr>
<En>
Independent requests should run **at the same time**. `await` in a loop runs them one after another. `Promise.all` waits for all (and fails if any fails); `Promise.allSettled` gives you every result, success or failure.
</En>
<Ur>
Aazad requests **ek saath** chalni chahiyen. Loop me `await` unhen ek ke baad ek chalata hai. `Promise.all` sab ka intezar karta hai (aur koi bhi fail ho to fail hota hai); `Promise.allSettled` har nateeja deta hai, kamyabi ho ya nakami.
</Ur>
</Tr>

```bash
cat > parallel.mjs <<'EOF'
import { start } from "./server.mjs";
const { base, stop } = await start();

const t0 = performance.now();
for (const ms of [300, 300, 300]) await fetch(base + "/api/slow?ms=" + ms);
console.log("one after another: ~" + Math.round((performance.now() - t0) / 100) * 100 + " ms");

const t1 = performance.now();
await Promise.all([300, 300, 300].map((ms) => fetch(base + "/api/slow?ms=" + ms)));
console.log("in parallel:       ~" + Math.round((performance.now() - t1) / 100) * 100 + " ms");

const results = await Promise.allSettled(
  ["/api/products/1", "/api/products/99", "/api/products/3"].map(async (path) => {
    const res = await fetch(base + path);
    if (!res.ok) throw new Error(path + " → " + res.status);
    return (await res.json()).name;
  })
);
for (const r of results) console.log(r.status, r.status === "fulfilled" ? r.value : r.reason.message);
stop();
EOF
node parallel.mjs
```

```text output
one after another: ~900 ms
in parallel:       ~300 ms
fulfilled Mug
rejected /api/products/99 → 404
fulfilled Floor Lamp
```

<Happened>
<Tr>
<En>

- Three 300 ms requests took ~900 ms in a `for…await` loop, and ~300 ms together. A dashboard loading user, orders and notifications should start all three at once.
- With `allSettled`, one missing product didn't stop us showing the other two. Use `Promise.all` when you need **everything** (and want to stop at the first failure).
- Only parallelise **independent** requests. If request B needs the id from A, it has to wait.
- Browsers limit simultaneous connections per server on HTTP/1.1 (about 6). HTTP/2 multiplexes, but hundreds of requests at once is still a bad idea: batch or paginate.

</En>
<Ur>

- Teen 300 ms requests ne `for…await` loop me ~900 ms aur ek saath ~300 ms liye. User, orders aur notifications load karne wala dashboard teeno ek saath shuru kare.
- `allSettled` ke saath ek ghayab product ne baqi do dikhane se nahi roka. Jab **sab kuch** chahiye ho (aur pehli nakami par rukna ho) to `Promise.all` lein.
- Sirf **aazad** requests saath chalayen. Agar request B ko A ki id chahiye to use intezar karna hoga.
- Browsers HTTP/1.1 par har server ke liye ek waqt ke connections mehdood rakhte hain (taqreeban 6). HTTP/2 multiplex karta hai, magar ek saath saikron requests phir bhi buri baat hai: batch ya paginate karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Retries with exponential backoff">

<Tr>
<En>
Some failures are temporary: `503 Service Unavailable`, `429 Too Many Requests`, a dropped connection. Retrying **a few times, waiting longer each time**, often succeeds. Our `/api/flaky` endpoint fails twice, then works.
</En>
<Ur>
Kuch nakamiyan aarzi hoti hain: `503 Service Unavailable`, `429 Too Many Requests`, toota connection. **Chand dafa, har dafa zyada intezar ke saath** dobara koshish aksar kamyab hoti hai. Hamara `/api/flaky` endpoint do dafa fail hota hai, phir chalta hai.
</Ur>
</Tr>

```bash
cat > retry.mjs <<'EOF'
import { start } from "./server.mjs";
const { base, stop } = await start();

async function fetchWithRetry(url, { retries = 3, baseDelay = 100 } = {}) {
  for (let attempt = 1; ; attempt++) {
    const res = await fetch(url);
    if (res.ok || res.status < 500 || attempt > retries) return res;
    const delay = baseDelay * 2 ** (attempt - 1);
    console.log("attempt " + attempt + ": " + res.status + ", retrying in " + delay + " ms");
    await new Promise((r) => setTimeout(r, delay));
  }
}

const res = await fetchWithRetry(base + "/api/flaky");
console.log("final:", res.status, await res.json());
stop();
EOF
node retry.mjs
```

```text output
attempt 1: 503, retrying in 100 ms
attempt 2: 503, retrying in 200 ms
final: 200 { ok: true, attempts: 3 }
```

<Happened>
<Tr>
<En>

- The wait doubled (100 → 200 ms): **exponential backoff**. Real code adds a little random **jitter** so thousands of clients don't retry at the same instant, and respects a `Retry-After` header if the server sends one.
- We **don't** retry 4xx errors (`res.status < 500`): a 404 or 400 will fail the same way every time.
- Only automatically retry **safe/idempotent** requests (GET, PUT, DELETE). Retrying a POST can create **duplicate orders** unless the server supports an idempotency key header.

</En>
<Ur>

- Intezar dugna hua (100 → 200 ms): **exponential backoff**. Asli code thora sa ittefaqi **jitter** jorta hai taa ke hazaron clients ek hi lamhe dobara koshish na karein, aur agar server `Retry-After` header bheje to us ki pabandi karta hai.
- Hum 4xx errors par dobara koshish **nahi** karte (`res.status < 500`): 404 ya 400 har dafa isi tarah fail hoga.
- Sirf **mehfooz/idempotent** requests (GET, PUT, DELETE) khud dobara karein. POST dohrana **dohre orders** bana sakta hai jab tak server idempotency key header support na kare.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Loading, error, empty and success states in the UI">

<Tr>
<En>
Users need to see what's happening. Every request in the UI has (at least) four states: **loading**, **error** (with a retry), **empty**, and **success**. This preview uses a pretend `fetch` (so it works offline) that you can make slow, fail or return nothing.
</En>
<Ur>
Users ko dikhna chahiye ke kya ho raha hai. UI me har request ki (kam az kam) chaar halaten hain: **loading**, **error** (retry ke saath), **khaali**, aur **kamyabi**. Ye preview naqli `fetch` istemal karta hai (taa ke offline chale) jise aap sust, fail ya khaali kar sakte hain.
</Ur>
</Tr>

```html preview-js h=270
<button data-mode="ok">Load products</button>
<button data-mode="empty">Load (no results)</button>
<button data-mode="fail">Load (server error)</button>
<div id="view" aria-live="polite" style="margin-top:8px"></div>
<script>
  // A pretend server so the demo works offline
  function fakeFetch(mode) {
    return new Promise((resolve) => setTimeout(() => {
      if (mode === "fail") resolve(new Response(JSON.stringify({ error: "Database unavailable" }), { status: 500 }));
      else resolve(new Response(JSON.stringify(mode === "empty" ? [] : [
        { name: "Mug", price: 12 }, { name: "Desk Lamp", price: 30 },
      ]), { headers: { "content-type": "application/json" } }));
    }, 800));
  }

  const view = document.querySelector("#view");
  const buttons = document.querySelectorAll("button");

  async function load(mode) {
    buttons.forEach((b) => (b.disabled = true));
    view.textContent = "Loading…";
    try {
      const res = await fakeFetch(mode);
      if (!res.ok) throw new Error((await res.json()).error);
      const products = await res.json();
      if (products.length === 0) {
        view.textContent = "No products found.";
        return;
      }
      const ul = document.createElement("ul");
      for (const p of products) {
        const li = document.createElement("li");
        li.textContent = p.name + " $" + p.price;
        ul.append(li);
      }
      view.replaceChildren(ul);
    } catch (error) {
      const retry = document.createElement("button");
      retry.textContent = "Try again";
      retry.addEventListener("click", () => load("ok"));
      view.replaceChildren("Couldn't load products: " + error.message + " ", retry);
    } finally {
      buttons.forEach((b) => (b.disabled = false));
    }
  }

  document.addEventListener("click", (e) => {
    const b = e.target.closest("button[data-mode]");
    if (b) load(b.dataset.mode);
  });
</script>
```

<Happened>
<Tr>
<En>

- Product names go in with `textContent` (DOM lesson): API data is untrusted.
- `aria-live="polite"` announces changes to screen-reader users. For long lists, skeleton placeholders feel faster than a spinner.

</En>
<Ur>

- **Load products** 0.8 s tak "Loading…" dikhata hai, phir list. **No results** khaali jagah ke bajaye dostana khaali paighaam dikhata hai. **Server error** wajah aur kaam karne wala **Try again** button dikhata hai.

- Product naam `textContent` se jate hain (DOM lesson): API ka data na-qabil-e-bharosa hai.

<Step title="Browser rules: CORS, cookies and caching">

<Tr>
<En>

Everything above works the same in Node and the browser. In the browser, a few **extra rules** apply because the request runs **on behalf of the user**:

| Rule | What it means for `fetch` |
| --- | --- |
| **Same-origin policy / CORS** | Your page at `https://shop.example.com` can call `https://api.other.com` only if that server replies with `Access-Control-Allow-Origin` allowing your origin. Otherwise the browser **hides the response** and `fetch` rejects ("CORS error"). Fix it on the **server**, not in the frontend. (Full lesson soon.) |
| **Cookies** | Same-origin requests send cookies automatically. Cross-origin requests send them only with `credentials: "include"`, **and** the server must allow it. |
| **Preflight** | "Non-simple" requests (JSON `content-type`, `PUT`/`DELETE`, custom headers) trigger an automatic `OPTIONS` request first, visible in DevTools. |
| **Caching** | The browser's HTTP cache follows the server's `Cache-Control` headers. `fetch(url, { cache: "no-store" })` bypasses it. Next.js extends `fetch` with its own caching options on the server. |
| **Mixed content** | An HTTPS page can't fetch `http://` URLs. |
| **Secrets** | Code in the browser is public: never put private API keys in frontend `fetch` calls; call your own backend, which holds the key. |

</En>
<Ur>

Upar ki har cheez Node aur browser me ek jaisi chalti hai. Browser me chand **izafi qawaid** lagte hain kyun ke request **user ki taraf se** chalti hai:

| Qaida | `fetch` ke liye matlab |
| --- | --- |
| **Same-origin policy / CORS** | `https://shop.example.com` par aap ka page `https://api.other.com` ko tabhi call kar sakta hai jab wo server aap ke origin ki ijazat dene wale `Access-Control-Allow-Origin` ke saath jawab de. Warna browser **response chhupa deta hai** aur `fetch` reject hota hai ("CORS error"). Ise **server** par theek karein, frontend me nahi. (Poora lesson jald.) |
| **Cookies** | Same-origin requests cookies khud bhejti hain. Cross-origin requests sirf `credentials: "include"` ke saath bhejti hain, **aur** server ko ijazat deni hoti hai. |
| **Preflight** | "Ghair saadi" requests (JSON `content-type`, `PUT`/`DELETE`, custom headers) pehle khud `OPTIONS` request bhejti hain, jo DevTools me nazar aati hai. |
| **Caching** | Browser ka HTTP cache server ke `Cache-Control` headers ki pairwi karta hai. `fetch(url, { cache: "no-store" })` use chhor deta hai. Next.js server par `fetch` ko apne caching options se barhata hai. |
| **Mixed content** | HTTPS page `http://` URLs fetch nahi kar sakta. |
| **Raaz** | Browser ka code public hai: frontend `fetch` calls me kabhi private API keys na rakhein; apne backend ko call karein, jis ke paas key ho. |

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- When a request fails in the browser, open DevTools → **Network** first: status, response body, and the **Console** for CORS messages tell you which side to fix.
- "It works in Postman/curl but not in the browser" almost always means CORS or cookies, because those tools don't enforce browser rules.

</En>
<Ur>

- Jab browser me request fail ho, pehle DevTools → **Network** kholein: status, response body, aur CORS paighaamon ke liye **Console** batate hain ke kis taraf theek karna hai.
- "Postman/curl me chalta hai magar browser me nahi" ka matlab taqreeban hamesha CORS ya cookies hai, kyun ke wo tools browser ke qawaid lagu nahi karte.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Not checking res.ok">

```text
const res = await fetch("/api/products/99");
const product = await res.json();     // { error: "Product not found" }
title.textContent = product.name;     // shows "undefined"
```

</Bad>
<Good title="Check, then use">

```text
const res = await fetch("/api/products/99");
if (!res.ok) {
  showError(res.status === 404 ? "Product not found" : "Please try again");
  return;
}
const product = await res.json();
title.textContent = product.name;
```

</Good>
</Compare>

<Compare>
<Bad title="Forgetting to await the body">

```text
const res = await fetch("/api/products");
const products = res.json();          // a Promise, not the array
console.log(products.length);         // undefined
```

</Bad>
<Good title="Await both steps">

```text
const res = await fetch("/api/products");
const products = await res.json();
console.log(products.length);         // 3
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Sending an object as `body`** without `JSON.stringify` (sends `[object Object]`).
- **Setting `content-type` by hand with `FormData`** (breaks the multipart boundary).
- **Building URLs with string concatenation** instead of `URL` / `URLSearchParams`.
- **No timeout and no cancellation**: hung spinners and stale results overwriting new ones.
- **`await` in a loop for independent requests**: use `Promise.all`.
- **Retrying POSTs blindly**: duplicate orders and payments.
- **Putting secret API keys in frontend code**: anyone can read them in DevTools.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- `JSON.stringify` ke baghair **object ko `body` dena** (`[object Object]` jata hai).
- **`FormData` ke saath haath se `content-type` set karna** (multipart boundary tor deta hai).
- `URL` / `URLSearchParams` ke bajaye **strings jor kar URLs banana**.
- **Na timeout, na mansookhi**: atke spinners aur purane nataij ka naye ko mitana.
- **Aazad requests ke liye loop me `await`**: `Promise.all` lein.
- **Andha dhund POSTs dohrana**: dohre orders aur payments.
- **Frontend code me raazdaraana API keys rakhna**: koi bhi DevTools me parh sakta hai.

</Ur>
</Tr>

<Tr>
<En>
Write `loadProductPage(ids)` that fetches several products with `Promise.allSettled` and returns `{ found: [...names], missing: [...ids] }`. Call it with `[1, 3, 42]`.

<Ur>

</Ur>

<Solution>

```bash
cat > page.mjs <<'EOF'
import { start } from "./server.mjs";
const { base, stop } = await start();

async function loadProductPage(ids) {
  const results = await Promise.allSettled(
    ids.map(async (id) => {
      const res = await fetch(base + "/api/products/" + id);
      if (!res.ok) throw new Error(String(id));
      return (await res.json()).name;
    })
  );
  return {
    found: results.filter((r) => r.status === "fulfilled").map((r) => r.value),
    missing: results.filter((r) => r.status === "rejected").map((r) => Number(r.reason.message)),
  };
}

console.log(await loadProductPage([1, 3, 42]));
stop();
EOF
node page.mjs
```

<DeepDive title="More about fetch">

**`Request` and `Response` objects.** You can build `new Request(url, options)` and `new Response(body, { status, headers })` yourself: handy for tests, service workers and Next.js route handlers (which return `Response`).

**Streaming bodies.** `res.body` is a `ReadableStream`: read large downloads or AI chat responses chunk by chunk with `res.body.getReader()` or `for await (const chunk of res.body)` in Node.

**Download progress.** Read the stream and compare received bytes with the `content-length` header.

**`keepalive: true`.** Lets a small request (analytics) finish even if the page is closing; `navigator.sendBeacon` is the classic alternative.

**`fetch` vs `XMLHttpRequest` vs axios.** XHR is the older callback API (still useful for upload progress). axios is a library that throws on non-2xx, has interceptors and upload progress, and works in old environments. Modern code usually uses `fetch` plus a small helper like the one in this lesson.

**Data-fetching libraries.** TanStack Query and SWR add caching, deduplication, background refetching, retries and loading states in React. Next.js server components can `await fetch()` directly on the server, avoiding client waterfalls.

**Real-time alternatives.** Polling (fetch every N seconds), Server-Sent Events (`EventSource`, one-way streaming from the server), and WebSockets (two-way) for chats and live dashboards.

**Idempotency keys.** Payment APIs accept an `Idempotency-Key` header so a retried POST is recognised and not charged twice.

</DeepDive>

<DeepDive title="Real world: the search that showed the wrong results">

A marketplace's search box fetched results on every keystroke. Users on mobile networks reported that typing "iphone case" sometimes showed results for "ip" or "iph", and the cursor stuttered while typing.

The DevTools Network panel showed 11 requests for one search (one per letter). Responses arrived out of order because short queries matched more products and took longer, so whichever arrived **last** won, often an early, short query.

The fix combined three things from this lesson and the previous one:

1. **Debounce** the input by 250 ms: one request per pause instead of per letter.
2. **Abort** the previous request whenever a new one starts, so stale responses never render.
3. **Timeout** of 8 seconds with a "Search is slow, try again" message instead of an endless spinner.

They also cached results by query for 60 seconds, so going back to a previous search was instant. Server load from search dropped by about 80 percent, and the "wrong results" reports stopped completely.

</DeepDive>

<DeepDive title="Security lens">

- **Never expose secret keys** (payment, database, AI provider) in browser code. The browser calls your backend; your backend calls the third party with the key.
- **CSRF**: if your API uses cookie authentication, a malicious site can make the browser send requests with those cookies. Use `SameSite` cookies, CSRF tokens, and check the `Origin` header for state-changing requests.
- **Don't loosen CORS with `*` and credentials**; allow only your known origins.
- **Validate responses** before using them (zod), and insert text with `textContent`.
- **Rate-limit and validate on the server**: client-side debouncing is a courtesy, not a protection.
- **Don't log tokens or personal data** from requests and responses in the browser console or error trackers.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Does fetch reject on a 404 or 500 response?">
No. fetch resolves with a Response for any HTTP response, including 404 and 500, setting ok to false. It rejects only on network errors, aborted requests, CORS blocks and similar failures, so code must check response.ok or status.
</QA>

<QA q="How do you send JSON with fetch?">
Set method to POST, PUT or PATCH, add a content-type header of application/json, and pass the data as a string with JSON.stringify in the body. Then check the response status and parse the response body.
</QA>

<QA q="How do you cancel a fetch request?">
Create an AbortController, pass its signal in the fetch options, and call abort on the controller. The fetch promise rejects with an AbortError. AbortSignal.timeout creates a signal that aborts automatically after a delay.
</QA>

<QA q="What is the difference between Promise.all and Promise.allSettled for requests?">
Promise.all resolves with all results when every promise fulfils, but rejects as soon as one rejects. Promise.allSettled waits for all promises and returns each outcome with its status, so partial failures can be handled.
</QA>

<QA q="When is it safe to retry a request automatically?">
For idempotent requests such as GET, PUT and DELETE, on transient failures such as network errors, 503 or 429, with a limited number of attempts and exponential backoff with jitter. Non-idempotent requests like POST should only be retried with an idempotency key.
</QA>

</DeepDive>
