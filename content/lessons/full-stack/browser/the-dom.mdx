<BigIdea>
<Tr>
<En>
When the browser parses your HTML, it builds the **DOM** (Document Object Model): a tree of JavaScript **objects**, one for every element and every piece of text. The page you see is drawn from this tree, and the tree is **live**: change an object and the screen updates. That's how every interactive website works, and it's what React and every other UI library do for you under the hood. The DOM gives you a handful of jobs. **Find** elements (`document.querySelector(".price")`). **Read** them (text, attributes, form values, computed styles). **Change** them (`textContent`, `classList`, `style`, `dataset`). **Create, insert, move and remove** them (`createElement`, `append`, `remove`). **Walk** the tree (`closest`, `children`). A few rules matter a lot: put user data in with `textContent`, never `innerHTML` (that's how XSS attacks happen); prefer toggling classes over writing inline styles; and build many elements off-screen, then insert them in one go.
</En>
<Ur>
Jab browser aap ka HTML parse karta hai, ye **DOM** (Document Object Model) banata hai: JavaScript **objects** ka darakht, har element aur text ke har tukre ke liye ek. Jo page aap dekhte hain wo isi darakht se banta hai, aur darakht **zinda** hai: object badlein aur screen update ho jati hai. Har interactive website isi tarah kaam karti hai, aur React aur har doosri UI library andar se aap ke liye yahi karti hai. DOM aap ko chand kaam deta hai. Elements **dhoondhna** (`document.querySelector(".price")`). Unhen **parhna** (text, attributes, form values, computed styles). Unhen **badalna** (`textContent`, `classList`, `style`, `dataset`). Unhen **banana, daalna, khiskana aur hatana** (`createElement`, `append`, `remove`). Darakht me **chalna** (`closest`, `children`). Chand qawaid bohot ahem hain: user ka data `textContent` se daalein, kabhi `innerHTML` se nahi (XSS hamle isi tarah hote hain); inline styles likhne ke bajaye classes toggle karna pasand karein; aur bohot se elements screen se bahar bana kar ek hi dafa me daalein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of the DOM as a **family tree** for the page, drawn on a **whiteboard that's connected to the screen**.

- `<html>` is the great-grandparent, `<body>` a grandparent, a `<ul>` a parent, each `<li>` a child, and the words inside are the youngest members (text nodes).
- **Finding** an element is like asking "who in this family wears a red hat?" (a CSS selector).
- Every person has a **name tag** (attributes like `id`, `class`, `data-*`) and a **current state** (properties like an input's current `value`).
- When you **rub out** a name or **draw** a new child on the whiteboard, the screen changes instantly.
- **`closest`** is asking "which of my ancestors is a table row?"; **`children`** is "who are my kids?".
- **`innerHTML`** is letting a stranger write **anything** on the whiteboard, including instructions that get executed. **`textContent`** only lets them write plain words.

</En>
<Ur>

DOM ko page ka **khandani shajra** samjhein, jo aisi **whiteboard par bana hai jo screen se jura hai**.

- `<html>` par-dada hai, `<body>` dada, `<ul>` walid, har `<li>` bachcha, aur andar ke alfaaz sab se chhote afraad (text nodes).
- Element **dhoondhna** aisa hai jaise poochna "is khandan me laal topi kis ne pehni hai?" (CSS selector).
- Har shakhs ke paas **naam ka tag** (attributes jaise `id`, `class`, `data-*`) aur **maujooda halat** (properties jaise input ki maujooda `value`) hai.
- Jab aap whiteboard par naam **mitate** ya naya bachcha **banate** hain, screen foran badal jati hai.
- **`closest`** poochna hai "mere buzurgon me se table row kaun hai?"; **`children`** hai "mere bachche kaun hain?".
- **`innerHTML`** kisi ajnabi ko whiteboard par **kuch bhi** likhne dena hai, un hidayat samet jo chal jati hain. **`textContent`** sirf saade alfaaz likhne deta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Finding elements: querySelector and friends">

<Tr>
<En>
`querySelector` takes **any CSS selector** and returns the first match (or `null`). `querySelectorAll` returns all matches as a **static** list: a snapshot. The older `getElementsByClassName` returns a **live** list that changes when the page changes.
</En>
<Ur>
`querySelector` **koi bhi CSS selector** leta hai aur pehla milne wala (ya `null`) wapas karta hai. `querySelectorAll` tamam milne wale **jamid** list ki shakal me deta hai: ek tasveer. Purana `getElementsByClassName` **zinda** list deta hai jo page badalne par badalti hai.
</Ur>
</Tr>

```html preview-js h=220
<ul id="list">
  <li class="item">Mug</li>
  <li class="item">Lamp</li>
</ul>
<pre id="out"></pre>
<script>
  const out = [];
  const staticList = document.querySelectorAll(".item");
  const liveList = document.getElementsByClassName("item");
  out.push("before: querySelectorAll " + staticList.length + ", getElementsByClassName " + liveList.length);

  const li = document.createElement("li");
  li.className = "item";
  li.textContent = "Pen";
  document.querySelector("#list").append(li);

  out.push("after:  querySelectorAll " + staticList.length + ", getElementsByClassName " + liveList.length);
  out.push("fresh querySelectorAll: " + document.querySelectorAll(".item").length);
  document.querySelector("#out").textContent = out.join("\n");
</script>
```

<Happened>
<Tr>
<En>

The preview shows:

```text
before: querySelectorAll 2, getElementsByClassName 2
after:  querySelectorAll 2, getElementsByClassName 3
fresh querySelectorAll: 3
```

- After adding "Pen", the static `NodeList` still says 2 (it was a snapshot); the live `HTMLCollection` says 3.
- Static lists are easier to reason about, which is why `querySelector`/`querySelectorAll` are the modern default. Call them again when you need fresh results.
- `NodeList` has `forEach`; for `map`/`filter`, convert with `[...list]` or `Array.from(list)`.
- You can search **inside** an element: `card.querySelector(".price")` only looks within `card`.
- `querySelector` returns `null` when nothing matches. In TypeScript its type is `Element | null`, so you must check (Narrowing lesson).

</En>
<Ur>

Preview ye dikhata hai:

```text
before: querySelectorAll 2, getElementsByClassName 2
after:  querySelectorAll 2, getElementsByClassName 3
fresh querySelectorAll: 3
```

- "Pen" jorne ke baad jamid `NodeList` ab bhi 2 kehti hai (wo tasveer thi); zinda `HTMLCollection` 3 kehti hai.
- Jamid lists ko samajhna aasan hai, isi liye `querySelector`/`querySelectorAll` jadeed default hain. Taaza nataij chahiyen to dobara call karein.
- `NodeList` ke paas `forEach` hai; `map`/`filter` ke liye `[...list]` ya `Array.from(list)` se badlein.
- Aap kisi element ke **andar** dhoondh sakte hain: `card.querySelector(".price")` sirf `card` ke andar dekhta hai.
- Kuch na mile to `querySelector` `null` deta hai. TypeScript me us ki type `Element | null` hai, isliye check zaroori hai (Narrowing lesson).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Text: textContent, innerText and innerHTML">

<Tr>
<En>
Three ways to read or write an element's content. They differ in what they include and, crucially, in whether they **parse HTML**.
</En>
<Ur>
Element ka maal parhne ya likhne ke teen tareeqe. Ye is me mukhtalif hain ke kya shamil karte hain, aur sab se ahem, ke kya ye **HTML parse karte** hain.
</Ur>
</Tr>

```html preview-js h=120
<p id="total">Total <span style="display:none">(debug: 3 items)</span>$12</p>
<pre id="out"></pre>
<script>
  const p = document.querySelector("#total");
  document.querySelector("#out").textContent =
    "textContent: " + JSON.stringify(p.textContent) + "\ninnerText:   " + JSON.stringify(p.innerText);
</script>
```

<Happened>
<Tr>
<En>

The preview shows:

```text
textContent: "Total (debug: 3 items)$12"
innerText:   "Total $12"
```

- `textContent` returns **all** text in the DOM, including hidden parts. It's fast and doesn't need layout.
- `innerText` returns the text **as rendered**: hidden elements are skipped and line breaks follow the layout. Reading it forces a layout (previous lesson), so it's slower.
- For **writing** plain text, both are safe; `textContent` is the usual choice.
- `innerHTML` reads or writes **HTML markup**. That's the next step, and it needs care.

</En>
<Ur>

Preview ye dikhata hai:

```text
textContent: "Total (debug: 3 items)$12"
innerText:   "Total $12"
```

- `textContent` DOM ka **saara** text deta hai, chhupe hisson samet. Ye tez hai aur layout nahi chahiye.
- `innerText` text **jaisa dikhta hai** waisa deta hai: chhupe elements chhoot jate hain aur nayi lines layout ke mutabiq hoti hain. Ise parhna layout par majboor karta hai (pichhla lesson), isliye ye sust hai.
- Saada text **likhne** ke liye dono mehfooz hain; `textContent` aam intikhab hai.
- `innerHTML` **HTML markup** parhta ya likhta hai. Ye agla qadam hai, aur ise ehtiyat chahiye.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Why innerHTML with user input is dangerous">

<Tr>
<En>
Imagine a product review a user typed. We put it on the page twice: once with `textContent`, once with `innerHTML`. The review contains an `<img>` tag whose `onerror` runs JavaScript.
</En>
<Ur>
Sochein ek user ne product review likha. Hum use page par do dafa daalte hain: ek dafa `textContent` se, ek dafa `innerHTML` se. Review me `<img>` tag hai jis ka `onerror` JavaScript chalata hai.
</Ur>
</Tr>

```html preview-js h=200
<p id="a"></p>
<p id="b"></p>
<pre id="out"></pre>
<script>
  const userInput = 'Nice mug! <img src="x" onerror="document.title=\'hacked\'">';
  document.querySelector("#a").textContent = userInput;
  document.querySelector("#b").innerHTML = userInput;
  setTimeout(() => {
    document.querySelector("#out").textContent = [
      "#a children: " + document.querySelector("#a").children.length,
      "#b children: " + document.querySelector("#b").children.length,
      "document.title: " + document.title,
    ].join("\n");
  }, 200);
</script>
```

<Happened>
<Tr>
<En>

The preview shows the first paragraph with the tag as **visible text**, the second as just "Nice mug!", and:

```text
#a children: 0
#b children: 1
document.title: hacked
```

- With `textContent`, the review is shown as **text**. No elements are created, nothing runs.
- With `innerHTML`, the browser **parsed** it, created a real `<img>`, the image failed to load, and `onerror` **ran the attacker's code**. Here it only changed the title; a real attack would steal session data, make requests as the user, or rewrite the page.
- This is **XSS (cross-site scripting)**. The rule: **never** put untrusted data into `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `document.write`. React escapes text by default for the same reason (`dangerouslySetInnerHTML` is named to scare you).
- If you truly must render user HTML (a rich-text editor), sanitise it with a library like DOMPurify first.

</En>
<Ur>

Preview pehle paragraph me tag ko **nazar aane wale text** ki tarah, doosre me sirf "Nice mug!" dikhata hai, aur:

```text
#a children: 0
#b children: 1
document.title: hacked
```

- `textContent` ke saath review **text** ki tarah dikha. Koi element nahi bana, kuch nahi chala.
- `innerHTML` ke saath browser ne use **parse** kiya, asli `<img>` banaya, image load nahi hui, aur `onerror` ne **hamla awar ka code chala diya**. Yahan is ne sirf title badla; asli hamla session data churata, user ki taraf se requests karta, ya page dobara likh deta.
- Ye **XSS (cross-site scripting)** hai. Qaida: na-qabil-e-bharosa data **kabhi** `innerHTML`, `outerHTML`, `insertAdjacentHTML` ya `document.write` me na daalein. React isi wajah se text default me escape karta hai (`dangerouslySetInnerHTML` ka naam aap ko darane ke liye rakha gaya).
- Agar sach me user ka HTML dikhana hi ho (rich-text editor), pehle DOMPurify jaisi library se use saaf karein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Attributes vs properties">

<Tr>
<En>
An **attribute** is what's written in the HTML. A **property** is the element object's **current** state. They often match, but for form fields they don't: typing changes the `value` property, not the `value` attribute.
</En>
<Ur>
**Attribute** wo hai jo HTML me likha hai. **Property** element object ki **maujooda** halat hai. Aksar ye milte hain, magar form fields ke liye nahi: type karna `value` property badalta hai, `value` attribute nahi.
</Ur>
</Tr>

```html preview-js h=130
<input id="name" value="Sara">
<pre id="out"></pre>
<script>
  const input = document.querySelector("#name");
  input.value = "Alex";
  const lines = [
    'getAttribute("value"): ' + input.getAttribute("value"),
    "input.value:           " + input.value,
    "defaultValue:          " + input.defaultValue,
  ];
  document.querySelector("#out").textContent = lines.join("\n");
</script>
```

<Happened>
<Tr>
<En>

The preview shows:

```text
getAttribute("value"): Sara
input.value:           Alex
defaultValue:          Sara
```

- The attribute keeps the **initial** value from the HTML (`Sara`, also available as `defaultValue`). The property holds what's in the box **now** (`Alex`).
- Always read user input with `.value` (and `.checked` for checkboxes). Reading the attribute is a common bug: you'd always get the original text.
- For most other things, use properties (`el.id`, `link.href`, `img.src`, `button.disabled = true`). Use `getAttribute`/`setAttribute` for custom or ARIA attributes (`aria-expanded`).

</En>
<Ur>

Preview ye dikhata hai:

```text
getAttribute("value"): Sara
input.value:           Alex
defaultValue:          Sara
```

- Attribute HTML ki **shuruati** value rakhta hai (`Sara`, `defaultValue` ki shakal me bhi dastiyab). Property wo rakhti hai jo **abhi** dabbe me hai (`Alex`).
- User ka input hamesha `.value` se parhein (aur checkboxes ke liye `.checked`). Attribute parhna aam bug hai: aap ko hamesha asal text milta.
- Zyada tar doosri cheezon ke liye properties lein (`el.id`, `link.href`, `img.src`, `button.disabled = true`). Custom ya ARIA attributes (`aria-expanded`) ke liye `getAttribute`/`setAttribute` lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="data-* attributes and classList">

<Tr>
<En>
`data-*` attributes let you store small bits of data on an element, available as `el.dataset` (with dashes turned into camelCase). `classList` adds, removes and toggles classes without touching the others.
</En>
<Ur>
`data-*` attributes aap ko element par data ke chhote tukre rakhne dete hain, jo `el.dataset` ki shakal me milte hain (dashes camelCase ban jate hain). `classList` doosri classes chhue baghair classes jorta, hatata aur toggle karta hai.
</Ur>
</Tr>

```html preview-js h=170
<div id="card" data-product-id="42" data-in-stock="true" class="card">Mug</div>
<pre id="out"></pre>
<script>
  const card = document.querySelector("#card");
  const lines = [];
  lines.push("dataset: " + JSON.stringify(card.dataset));
  lines.push("productId type: " + typeof card.dataset.productId);
  card.classList.add("sale");
  card.classList.toggle("card");
  lines.push("classes: " + card.className + " | has sale? " + card.classList.contains("sale"));
  card.dataset.discount = "10";
  lines.push("html: " + card.outerHTML);
  document.querySelector("#out").textContent = lines.join("\n");
</script>
```

<Happened>
<Tr>
<En>

The preview shows:

```text
dataset: {"productId":"42","inStock":"true"}
productId type: string
classes: sale | has sale? true
html: <div id="card" data-product-id="42" data-in-stock="true" class="sale" data-discount="10">Mug</div>
```

- `data-product-id` became `dataset.productId`. Values are **always strings**: convert with `Number(...)` or compare with `"true"`.
- Setting `dataset.discount` wrote a new `data-discount` attribute.
- `toggle("card")` removed `card` because it was present; calling it again would add it back. `toggle("open", isOpen)` forces a state.
- Don't store secrets or large data in `data-*`: everyone can see it in the page.

</En>
<Ur>

Preview ye dikhata hai:

```text
dataset: {"productId":"42","inStock":"true"}
productId type: string
classes: sale | has sale? true
html: <div id="card" data-product-id="42" data-in-stock="true" class="sale" data-discount="10">Mug</div>
```

- `data-product-id` `dataset.productId` ban gaya. Values **hamesha strings** hoti hain: `Number(...)` se badlein ya `"true"` se muqabla karein.
- `dataset.discount` set karne ne naya `data-discount` attribute likha.

- `data-*` me raaz ya bara data na rakhein: page me har koi use dekh sakta hai.

</Ur>
</Tr>

<Step title="Inline styles vs computed styles">

<Tr>
<En>
`el.style` reads and writes **inline** styles only (the `style="…"` attribute). To know the **final** value after all your CSS, use `getComputedStyle(el)`. For changing looks, toggling a class is usually better than writing inline styles.
</En>
<Ur>
`el.style` sirf **inline** styles parhta aur likhta hai (`style="…"` attribute). Aap ki tamam CSS ke baad **aakhri** value jaanne ke liye `getComputedStyle(el)` lein. Shakal badalne ke liye class toggle karna aam taur par inline styles likhne se behtar hai.
</Ur>
</Tr>

```html preview-js h=170
<style>
  .badge { padding: 4px 8px; border-radius: 6px; font-size: 14px; }
  .badge.sale { background: #fee2e2; color: #b91c1c; }
</style>
<span id="b" class="badge">New</span>

<script>
  const b = document.querySelector("#b");

  const cs = getComputedStyle(b);
  document.querySelector("#out").textContent = [
    "inline style attr: " + b.getAttribute("style"),
    "b.style.color (inline only): " + JSON.stringify(b.style.color),

    "computed font-size: " + cs.fontSize,
    "computed font-weight: " + cs.fontWeight,

```

<Happened>
<Tr>
<En>

The preview shows:

```text
computed font-size: 14px
```

<Step title="Creating elements and rendering a list from data">

<Tr>
<En>
`document.createElement` makes a new, detached element. You fill it in, then attach it with `append`. To add many at once, build them in a **DocumentFragment** (an invisible container) and append the fragment once.
</En>
<Ur>
`document.createElement` naya, alag element banata hai. Aap use bharte hain, phir `append` se jorte hain. Bohot se ek saath jorne ke liye unhen **DocumentFragment** (nazar na aane wala dabba) me banayen aur fragment ek dafa append karein.
</Ur>
</Tr>

```html preview-js h=170
<ul id="products"></ul>
<p id="count"></p>
<script>
  const products = [
    { name: "Mug", price: 12 },
    { name: "Lamp", price: 30 },
    { name: "Pen", price: 2.5 },
  ];
  const list = document.querySelector("#products");
  const fragment = document.createDocumentFragment();
  for (const p of products) {
    const li = document.createElement("li");
    const name = document.createElement("strong");
    name.textContent = p.name;
    li.append(name, " $" + p.price.toFixed(2));
    fragment.append(li);
  }
  list.append(fragment);
  document.querySelector("#count").textContent = list.children.length + " products rendered";
</script>
```

<Happened>
<Tr>
<En>

- Three `<li>` elements appeared with bold names and prices, and the count says "3 products rendered".
- `append` accepts elements **and strings** (strings become safe text nodes), and several at once.
- Building in a fragment means the live page is changed **once**, not three times. (Modern browsers batch well, but it's a good habit for big lists.) `list.replaceChildren(...items)` is another one-shot option that also clears old items.
- Notice we used `textContent` for the product names: data from an API is untrusted.
- This "data → elements" loop is exactly what React does when you write `products.map(p => <li>…</li>)`.

</En>
<Ur>

- Teen `<li>` elements bold naamon aur qeemton ke saath nazar aaye, aur ginti kehti hai "3 products rendered".
- `append` elements **aur strings** dono qubool karta hai (strings mehfooz text nodes ban jati hain), aur kai ek saath.
- Fragment me banane ka matlab zinda page **ek dafa** badalta hai, teen dafa nahi. (Jadeed browsers achha batch karte hain, magar bari lists ke liye achhi aadat hai.) `list.replaceChildren(...items)` ek aur ek-dafa wala option hai jo purane items bhi saaf karta hai.
- Dhyan dein humne product naamon ke liye `textContent` istemal kiya: API ka data na-qabil-e-bharosa hai.
- Ye "data → elements" loop bilkul wahi hai jo React karta hai jab aap `products.map(p => <li>…</li>)` likhte hain.

</Ur>
</Tr>
</Happened>

<Step title="Templates for bigger markup">

<Tr>
<En>
For markup with several nested parts, a `<template>` element is cleaner than many `createElement` calls. Its content isn't rendered; you **clone** it, fill in the blanks with `textContent`, and append.
</En>
<Ur>
Kai nested hisson wale markup ke liye `<template>` element bohot se `createElement` calls se zyada saaf hai. Is ka maal render nahi hota; aap use **clone** karte hain, khaali jagahen `textContent` se bharte hain, aur append karte hain.
</Ur>
</Tr>

```html preview-js h=110
<template id="row">
  <li class="product"><span class="name"></span> <em class="price"></em></li>
</template>
<ul id="list"></ul>
<script>
  const tpl = document.querySelector("#row");
  for (const p of [{ name: "Mug", price: 12 }, { name: "Lamp", price: 30 }]) {
    const node = tpl.content.cloneNode(true);
    node.querySelector(".name").textContent = p.name;
    node.querySelector(".price").textContent = "$" + p.price;
    document.querySelector("#list").append(node);
  }
</script>
```

<Happened>
<Tr>
<En>

- The page shows "Mug $12" and "Lamp $30" with italic prices. The `<template>` itself is invisible.
- `cloneNode(true)` copies the template's content **deeply** (with all children). Without `true`, you'd get an empty shell.
- The HTML structure stays readable in one place, and data is still inserted safely as text.

</En>
<Ur>

- Page "Mug $12" aur "Lamp $30" italic qeemton ke saath dikhata hai. Khud `<template>` nazar nahi aata.
- `cloneNode(true)` template ka maal **gehrai tak** (tamam bachchon samet) copy karta hai. `true` ke baghair aap ko khaali khol milta.

<Step title="Walking the tree: closest, parent, siblings">

<Tr>
<En>
From any element you can move around the tree. The most useful move is `closest(selector)`: it walks **up** from the element (including itself) and returns the first ancestor that matches. It's how you find "the row this button belongs to".
</En>
<Ur>
Kisi bhi element se aap darakht me ghoom sakte hain. Sab se kaam ki chaal `closest(selector)` hai: ye element se (khud samet) **upar** chalta hai aur pehla milne wala buzurg wapas karta hai. "Ye button kis row ka hai" isi tarah dhoondhte hain.
</Ur>
</Tr>

```html preview-js h=170
<table id="cart">
  <tr data-id="mug"><td>Mug</td><td><button class="remove">Remove</button></td></tr>
  <tr data-id="lamp"><td>Lamp</td><td><button class="remove">Remove</button></td></tr>
</table>
<pre id="out"></pre>
<script>
  const button = document.querySelector('tr[data-id="lamp"] .remove');
  const row = button.closest("tr");
  const lines = [
    "button.parentElement: " + button.parentElement.nodeName,
    "closest('tr') id: " + row.dataset.id,
    "row.previousElementSibling id: " + row.previousElementSibling.dataset.id,
    "table rows: " + document.querySelectorAll("#cart tr").length,
  ];
  row.remove();
  lines.push("after row.remove(): " + document.querySelectorAll("#cart tr").length);
  document.querySelector("#out").textContent = lines.join("\n");
</script>
```

<Happened>
<Tr>
<En>

```text
row.previousElementSibling id: mug
```

<Step title="Putting it together: a live product filter">

```html preview-js h=260
<style>
  .hidden { display: none; }
  li { padding: 2px 0; }
</style>

  const products = ["Desk Lamp", "Mug", "Floor Lamp", "Notebook", "Pen", "Lamp Shade"];
  const list = document.querySelector("#list");
  list.replaceChildren(...products.map((name) => {
    const li = document.createElement("li");
    li.textContent = name;
```

## Common mistakes

<Compare>
<Bad title="User data into innerHTML">

```text
const comment = await getComment();
list.innerHTML += "<li>" + comment.text + "</li>";
// XSS if comment.text contains HTML; also re-parses and recreates
// every existing <li>, losing their event listeners and state
```

</Bad>
<Good title="Create elements, set textContent">

```text
const comment = await getComment();
const li = document.createElement("li");
li.textContent = comment.text;
list.append(li);
```

</Good>
</Compare>

<Compare>
<Bad title="Assuming the element exists">

```text
document.querySelector("#promo").textContent = "Sale!";
// TypeError on pages without #promo, and the rest of the script stops
```

</Bad>
<Good title="Check first (or use optional chaining)">

```text
const promo = document.querySelector("#promo");
if (promo) promo.textContent = "Sale!";
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Reading `getAttribute("value")`** to get what the user typed. Use `.value`.
- **Forgetting `dataset` values are strings**: `"10" + 5` is `"105"`.
- **Writing many inline styles** instead of toggling a class.
- **Calling `map` on a `NodeList`** (it doesn't have one); spread it first.
- **Running DOM code before the HTML is parsed** (use `defer`, previous lesson).
- **Directly editing DOM that React controls**: React will overwrite it or get confused; change state instead.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- User ka likha lene ke liye **`getAttribute("value")` parhna**. `.value` lein.
- **Bhoolna ke `dataset` values strings hain**: `"10" + 5` `"105"` hai.
- Class toggle karne ke bajaye **bohot si inline styles likhna**.
- **`NodeList` par `map` call karna** (us ke paas nahi); pehle spread karein.
- **HTML parse hone se pehle DOM code chalana** (`defer` lein, pichhla lesson).
- **React ke control wale DOM ko seedha badalna**: React use dobara likh dega ya ulajh jayega; state badlein.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- The DOM is a **live tree of objects**; changing it changes the page.
- Find with `querySelector` / `querySelectorAll` (static); `getElementsBy…` lists are live. Handle `null`.
- `textContent` for text (safe); `innerText` = visible text (forces layout); **never** `innerHTML` with untrusted data.
- Attributes = initial HTML; properties = current state (`input.value`, `.checked`).
- `dataset` for `data-*` (strings); `classList` for classes; `getComputedStyle` for final styles.
- Create with `createElement` / `<template>` + `cloneNode(true)`; insert with `append` / `replaceChildren`; remove with `remove()`.
- `closest()` finds the containing item; `FormData` reads whole forms.

</En>
<Ur>

- DOM **objects ka zinda darakht** hai; ise badalna page badalta hai.
- `querySelector` / `querySelectorAll` (jamid) se dhoondhein; `getElementsBy…` lists zinda hain. `null` sambhalein.
- Text ke liye `textContent` (mehfooz); `innerText` = nazar aane wala text (layout par majboor karta hai); na-qabil-e-bharosa data ke saath **kabhi** `innerHTML` nahi.
- Attributes = shuruati HTML; properties = maujooda halat (`input.value`, `.checked`).
- `data-*` ke liye `dataset` (strings); classes ke liye `classList`; aakhri styles ke liye `getComputedStyle`.
- `createElement` / `<template>` + `cloneNode(true)` se banayen; `append` / `replaceChildren` se daalein; `remove()` se hatayen.
- `closest()` ghere hue item ko dhoondhta hai; `FormData` poore forms parhta hai.

</Ur>

<DeepDive title="More DOM APIs">

**`insertAdjacentElement` / `insertAdjacentText`.** Insert at `"beforebegin"`, `"afterbegin"`, `"beforeend"`, `"afterend"` relative to an element. (`insertAdjacentHTML` has the same XSS risk as `innerHTML`.)

**`matches(selector)`.** Tests whether an element matches a selector: handy in event handlers.

**`MutationObserver`.** Runs a callback when the DOM changes (children added, attributes changed). Useful for reacting to third-party widgets.

**`IntersectionObserver` and `ResizeObserver`.** Tell you when an element enters the viewport (lazy loading, infinite scroll, analytics) or changes size, without polling or scroll listeners.

**`element.scrollIntoView({ behavior: "smooth" })`** and **`focus()`** move the user's attention; manage focus carefully in dialogs for accessibility.

**The `<dialog>` element.** `dialog.showModal()` gives you a real modal with focus trapping and Escape-to-close for free.

**Shadow DOM.** Web Components can attach a private DOM tree (`attachShadow`) whose styles don't leak in or out.

**Virtual DOM.** React keeps a lightweight description of the UI, compares it with the previous one, and applies only the needed DOM changes. Keys help it match list items correctly between renders.

**TypeScript and the DOM.** `document.querySelector<HTMLInputElement>("#email")` gives a typed result (still possibly `null`); `instanceof HTMLInputElement` narrows safely.

</DeepDive>

<DeepDive title="Real world: the review widget that leaked sessions">

A shop added product reviews. To show bold text and line breaks, the review list was built with `container.innerHTML += "<div class='review'>" + review.text + "</div>"`.

A security researcher posted a review containing an image tag with an `onerror` handler that sent `document.cookie` and `localStorage` to their server. Every visitor who opened that product page sent their data. The site stored its auth token in `localStorage`, so the researcher could have logged in as any of them.

The fix had several layers:

1. Reviews rendered with `createElement` + `textContent`; simple formatting (line breaks) handled with CSS `white-space: pre-line` instead of HTML.
2. Moved the session to an `HttpOnly` cookie that JavaScript can't read.
3. Added a Content Security Policy that blocks inline event handlers like `onerror`.
4. Validation on the server rejected reviews over 2,000 characters and stored them as plain text.

As a bonus, the `innerHTML +=` pattern had also been re-creating every review on each addition, so the "Helpful" buttons kept losing their click handlers. The new code fixed that too.

</DeepDive>

<DeepDive title="Security lens">

- **`textContent` for untrusted data**, always. Treat API responses, URL parameters, `localStorage` and form input as untrusted.
- **Dangerous sinks**: `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`, `setTimeout("string")`, and URLs like `href = userInput` (a `javascript:` URL runs code). Validate URLs start with `https://`.
- **Sanitise if you must render HTML** (DOMPurify), and consider Trusted Types, a browser feature that blocks raw strings from reaching dangerous sinks.
- **Don't put secrets in the DOM** (hidden inputs, `data-*`, comments): view-source shows everything.
- **Content Security Policy** is a second line of defence that blocks inline scripts and handlers even if an injection slips through.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the DOM?">
The Document Object Model is the browser's in-memory tree representation of an HTML document, where each element, text and comment is a node object. JavaScript reads and modifies the page through this API, and changes are reflected on screen.
</QA>

<QA q="What is the difference between textContent, innerText and innerHTML?">
textContent gets or sets all text of a node without parsing HTML and ignores styling. innerText returns only rendered, visible text and triggers layout. innerHTML gets or sets HTML markup and parses it, which is an XSS risk with untrusted input.
</QA>

<QA q="What is the difference between an attribute and a property?">
Attributes are defined in HTML and reflect initial values, accessible with getAttribute. Properties belong to the DOM object and reflect current state. For example, an input's value property changes as the user types, while its value attribute keeps the original value.
</QA>

<QA q="What is the difference between a NodeList from querySelectorAll and an HTMLCollection?">
querySelectorAll returns a static NodeList that does not change when the document changes. HTMLCollections returned by getElementsByClassName, getElementsByTagName or children are live and update automatically.
</QA>

<QA q="How would you efficiently add many elements to the page?">
Create the elements off-document, in a DocumentFragment or an array, then insert them in a single operation such as append with a fragment or replaceChildren, avoiding repeated innerHTML concatenation and interleaved layout reads.
</QA>

</DeepDive>
