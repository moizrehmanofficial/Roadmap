<BigIdea>
<Tr>
<En>
A web page sits and waits. When something happens (the user clicks, types, submits a form, scrolls, or a file finishes loading) the browser creates an **event** object describing it and delivers it to any functions you've registered with **`addEventListener`**. Those functions are **event listeners** (or handlers). The interesting part is the **journey** an event takes: a click on a button inside a card inside a list doesn't just happen "on the button". It travels **down** from the window to the button (**capturing**), reaches the button (**target**), then travels back **up** through every ancestor (**bubbling**). Bubbling enables **event delegation**: instead of attaching a listener to each of 500 list items (and remembering to add one to every new item), you attach **one** listener to the list and ask "which item was clicked?" with `event.target.closest(...)`. Add `preventDefault()` to stop the browser's built-in behaviour (following a link, submitting a form), and a few patterns (removing listeners, debouncing, keyboard shortcuts, custom events) and you can build any interaction.
</En>
<Ur>
Web page baitha intezar karta hai. Jab kuch hota hai (user click kare, type kare, form submit kare, scroll kare, ya koi file load ho jaye) browser use bayan karne wala **event** object banata hai aur un functions tak pohanchata hai jo aap ne **`addEventListener`** se register kiye hon. Ye functions **event listeners** (ya handlers) hain. Dilchasp hissa event ka **safar** hai: list ke andar card ke andar button par click sirf "button par" nahi hota. Ye window se button tak **neeche** safar karta hai (**capturing**), button tak pohanchta hai (**target**), phir har buzurg se guzarte hue wapas **upar** jata hai (**bubbling**). Bubbling **event delegation** mumkin banati hai: 500 list items me se har ek par listener lagane (aur har naye item par lagana yaad rakhne) ke bajaye aap list par **ek** listener lagate hain aur `event.target.closest(...)` se poochte hain "kaun sa item click hua?". Browser ka bana banaya bartao (link par jana, form submit karna) rokne ke liye `preventDefault()` jorein, aur chand patterns (listeners hatana, debouncing, keyboard shortcuts, custom events) ke saath aap koi bhi interaction bana sakte hain.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of an **office building** where a letter is delivered to someone at a desk.

- The letter enters at the **front door** (window), goes up through the **floor reception** (body), the **department office** (list), the **team room** (card) and finally reaches the **desk** (button). That trip down is **capturing**.
- At the desk, the person **opens it** (target phase).
- Then a copy of the news travels **back up**: the team room, the department, the floor, the front desk all hear about it. That's **bubbling**.
- **Event delegation** is putting **one receptionist** at the department office who handles letters for every desk in it, including desks added next week, instead of hiring one assistant per desk.
- `stopPropagation()` is saying "don't tell anyone upstairs". `preventDefault()` is saying "don't do the usual thing with this letter" (don't forward it, don't file it).

</En>
<Ur>

Ek **daftar ki imarat** ka sochein jahan kisi desk par baithe shakhs ko khat pohanchaya jata hai.

- Khat **saamne ke darwaze** (window) se dakhil hota hai, **manzil ke reception** (body), **department ke daftar** (list), **team ke kamre** (card) se guzar kar aakhir **desk** (button) tak pohanchta hai. Neeche ka ye safar **capturing** hai.
- Desk par shakhs use **kholta** hai (target phase).
- Phir khabar ki copy **wapas upar** jati hai: team ka kamra, department, manzil, saamne ka desk, sab ko pata chalta hai. Ye **bubbling** hai.
- **Event delegation** department ke daftar par **ek receptionist** bithana hai jo us ki har desk ke khat sambhale, agle hafte jurne wali desks samet, har desk ke liye ek assistant rakhne ke bajaye.
- `stopPropagation()` kehna hai "upar kisi ko mat batao". `preventDefault()` kehna hai "is khat ke saath aam wala kaam mat karo" (aage mat bhejo, file mat karo).

</Ur>
</Tr>

<Step title="Your first listener and the event object">

<Tr>
<En>
`addEventListener(type, handler)` registers a function. When the event happens, the function receives an **event object** full of details. Click the button, then click again while holding Shift.
</En>
<Ur>
`addEventListener(type, handler)` ek function register karta hai. Event hone par function ko tafseelat se bhara **event object** milta hai. Button dabayen, phir Shift daba kar dobara dabayen.
</Ur>
</Tr>

```html preview-js h=200
<button id="buy">Buy now</button>
<pre id="log"></pre>
<script>
  const log = document.querySelector("#log");
  let clicks = 0;
  document.querySelector("#buy").addEventListener("click", (event) => {
    clicks++;
    log.textContent = [
      "click #" + clicks,
      "type: " + event.type,
      "target: <" + event.target.tagName.toLowerCase() + " id=" + event.target.id + ">",
      "shiftKey: " + event.shiftKey,
      "isTrusted: " + event.isTrusted,
    ].join("\n");
  });
</script>
```

<Happened>
<Tr>
<En>

After a normal click:

```text
click #1
type: click
target: <button id=buy>
shiftKey: false
isTrusted: true
```

- The handler runs **every time**; the browser passes a fresh event object each time. A Shift-click shows `shiftKey: true`.
- Mouse events also have `clientX`/`clientY` (position) and `button` (which mouse button). Keyboard events have `key` and `code`. Every event has `type`, `target` and `timeStamp`.
- `isTrusted` is `true` for real user actions and `false` for events created by scripts.
- Prefer `addEventListener` over `onclick = …` properties or `onclick="…"` attributes: it allows several listeners and supports options.

</En>
<Ur>

Aam click ke baad:

```text
click #1
type: click
target: <button id=buy>
shiftKey: false
isTrusted: true
```

- Handler **har dafa** chalta hai; browser har dafa naya event object deta hai. Shift-click `shiftKey: true` dikhata hai.
- Mouse events me `clientX`/`clientY` (jagah) aur `button` (kaun sa mouse button) bhi hote hain. Keyboard events me `key` aur `code` hote hain. Har event me `type`, `target` aur `timeStamp` hota hai.
- `isTrusted` asli user amal ke liye `true` aur scripts ke banaye events ke liye `false` hai.
- `onclick = …` properties ya `onclick="…"` attributes ke bajaye `addEventListener` pasand karein: ye kai listeners ki ijazat deta hai aur options support karta hai.

</Ur>

<Step title="The journey: capturing, target, bubbling">

<Tr>
<En>
Here the same click is listened to on the outer section, the card and the button, both in the capture phase and the bubble phase. Click the **button**.
</En>
<Ur>
Yahan ek hi click ko bahar ke section, card aur button par suna ja raha hai, capture phase aur bubble phase dono me. **Button** dabayen.
</Ur>
</Tr>

```html preview-js h=260
<style>
  section, .card { padding: 10px; border: 2px dashed #94a3b8; }
  .card { border-color: #0d9488; }
</style>
<section id="list">
  list
  <div class="card" id="card">
    card <button id="btn">Add to cart</button>
  </div>
</section>
<pre id="log"></pre>
<script>
  const log = document.querySelector("#log");
  const lines = [];
  function listen(id) {
    const el = document.getElementById(id);
    el.addEventListener("click", () => lines.push("capture  " + id), { capture: true });
    el.addEventListener("click", (e) => {
      lines.push("bubble   " + id + "   (target: " + e.target.id + ", currentTarget: " + e.currentTarget.id + ")");
      log.textContent = lines.join("\n");
    });
  }
  window.addEventListener("click", () => (lines.length = 0), { capture: true });
  ["list", "card", "btn"].forEach(listen);
</script>
```

<Happened>
<Tr>
<En>

Clicking the button logs:

```text
capture  list
capture  card
capture  btn
bubble   btn   (target: btn, currentTarget: btn)
bubble   card   (target: btn, currentTarget: card)
bubble   list   (target: btn, currentTarget: list)
```

- The event went **down** (list → card → btn) in the capture phase, then **up** (btn → card → list) in the bubble phase.
- `event.target` is **always** the button, where the click actually happened. `event.currentTarget` is the element **whose listener** is running right now.
- Click the card's border instead: now `target` is `card`, and the button's listeners don't run at all.
- Most code only uses the bubble phase (the default). Capture is useful when a parent must see the event **first**.
- (The `window` capture listener just clears the log at the start of each click: `window` is the very first stop.)

</En>
<Ur>

Button dabane par ye log hota hai:

```text
capture  list
capture  card
capture  btn
bubble   btn   (target: btn, currentTarget: btn)
bubble   card   (target: btn, currentTarget: card)
bubble   list   (target: btn, currentTarget: list)
```

- Event capture phase me **neeche** (list → card → btn) gaya, phir bubble phase me **upar** (btn → card → list).
- `event.target` **hamesha** button hai, jahan click asal me hua. `event.currentTarget` wo element hai **jis ka listener** abhi chal raha hai.
- Is ke bajaye card ke border par click karein: ab `target` `card` hai, aur button ke listeners bilkul nahi chalte.
- Zyada tar code sirf bubble phase (default) istemal karta hai. Capture tab kaam aata hai jab parent ko event **pehle** dekhna ho.
- (`window` ka capture listener har click ke shuru me log saaf karta hai: `window` sab se pehla parao hai.)

</Ur>
</Tr>
</Happened>

<Step title="preventDefault: cancel the browser's own action">

<Tr>
<En>
Many events have a **default action**: a link navigates, a form submits and reloads the page, a checkbox toggles, a right-click opens a menu. `event.preventDefault()` cancels it so your code can do something else. Click the link and press **Save**.
</En>
<Ur>
Bohot se events ka **default amal** hota hai: link naye page par le jata hai, form submit ho kar page reload karta hai, checkbox toggle hota hai, right-click menu kholta hai. `event.preventDefault()` use mansookh karta hai taa ke aap ka code kuch aur kare. Link dabayen aur **Save** dabayen.
</Ur>
</Tr>

```html preview-js h=200
<a id="docs" href="https://example.com/docs">Open the docs</a>
<form id="profile">
  <input name="name" value="Sara" required>
  <button>Save</button>
</form>
<pre id="log"></pre>
<script>
  const log = (msg) => (document.querySelector("#log").textContent += msg + "\n");

  document.querySelector("#docs").addEventListener("click", (event) => {
    event.preventDefault();
    log("link: stayed on the page instead of opening " + event.currentTarget.href);
  });

  document.querySelector("#profile").addEventListener("submit", (event) => {
    event.preventDefault();
    const name = new FormData(event.currentTarget).get("name");
    log("form: no reload; would save name = " + name + " with fetch");
  });
</script>
```

<Happened>
<Tr>
<En>

```text
link: stayed on the page instead of opening https://example.com/docs
form: no reload; would save name = Sara with fetch
```

- Listen to **`submit` on the form**, not `click` on the button: `submit` also fires when the user presses Enter in a field, and only after built-in validation (`required`) passes.
- `preventDefault()` doesn't stop the event travelling; it only cancels the default action. `stopPropagation()` is the opposite.
- Some events can't be cancelled (`event.cancelable` is `false`), and listeners registered as `passive` aren't allowed to cancel (later step).
- Don't break normal behaviour without a reason: links should usually stay real links so middle-click and "open in new tab" work.

</En>
<Ur>

```text
link: stayed on the page instead of opening https://example.com/docs
form: no reload; would save name = Sara with fetch
```

- Button par `click` ke bajaye **form par `submit`** sunein: `submit` tab bhi chalta hai jab user kisi field me Enter dabaye, aur sirf bane banaye validation (`required`) paas hone ke baad.
- `preventDefault()` event ka safar nahi rokta; ye sirf default amal mansookh karta hai. `stopPropagation()` is ka ulat hai.
- Kuch events mansookh nahi ho sakte (`event.cancelable` `false` hai), aur `passive` ke taur par register hue listeners ko mansookh karne ki ijazat nahi (aage ka qadam).
- Baghair wajah aam bartao na torein: links aam taur par asli links rehne chahiyen taa ke middle-click aur "naye tab me kholo" chalein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Event delegation: one listener for many items">

<Tr>
<En>
Instead of a listener on every "Remove" button, put **one** on the list. When anything inside is clicked, the event bubbles up to it; `event.target.closest("button.remove")` tells us whether a remove button (or something inside it) was clicked. Add items, then remove them, including the new ones.
</En>
<Ur>
Har "Remove" button par listener ke bajaye list par **ek** lagayen. Jab andar kuch bhi click ho, event bubble ho kar us tak aata hai; `event.target.closest("button.remove")` batata hai ke kya remove button (ya us ke andar ki koi cheez) click hua. Items jorein, phir unhen hatayen, naye samet.
</Ur>
</Tr>

```html preview-js h=280
<button id="add">Add item</button>
<ul id="cart">
  <li data-id="mug">Mug <button class="remove"><span aria-hidden="true">✕</span> Remove</button></li>
  <li data-id="lamp">Lamp <button class="remove"><span aria-hidden="true">✕</span> Remove</button></li>
</ul>
<pre id="log"></pre>
<script>
  const cart = document.querySelector("#cart");
  const log = (msg) => (document.querySelector("#log").textContent = msg);
  let n = 0;

  cart.addEventListener("click", (event) => {
    const button = event.target.closest("button.remove");
    if (!button || !cart.contains(button)) return;
    const item = button.closest("li");
    item.remove();
    log("removed " + item.dataset.id + " (clicked on <" + event.target.tagName.toLowerCase() + ">), " +
        cart.children.length + " left");
  });

  document.querySelector("#add").addEventListener("click", () => {
    n++;
    const li = document.createElement("li");
    li.dataset.id = "item-" + n;
    li.append("New item " + n + " ");
    const btn = document.createElement("button");
    btn.className = "remove";
    btn.textContent = "Remove";
    li.append(btn);
    cart.append(li);
    log("added item-" + n + " (no new listener needed)");
  });
</script>
```

<Happened>
<Tr>
<En>

- Clicking **Add item** then that item's **Remove** shows "removed item-1 … 2 left". The new button works even though we never attached a listener to it.
- Clicking exactly on the **✕** shows "clicked on `<span>`": `event.target` was the span inside the button. That's why we use `closest("button.remove")` instead of checking `event.target.matches(...)`.
- `cart.contains(button)` guards against matching a button **outside** the list (relevant when lists are nested).
- Benefits: one listener instead of hundreds (less memory, faster setup), and items added or re-rendered later just work. This is how tables, menus, chat lists and React itself handle clicks.

</En>
<Ur>

- **Add item** aur phir us item ka **Remove** dabane par "removed item-1 … 2 left" aata hai. Naya button kaam karta hai halanke humne us par kabhi listener nahi lagaya.
- Bilkul **✕** par click karne par "clicked on `<span>`" aata hai: `event.target` button ke andar ka span tha. Isi liye hum `event.target.matches(...)` check karne ke bajaye `closest("button.remove")` istemal karte hain.
- `cart.contains(button)` list se **bahar** ke button se milne se bachata hai (nested lists me ahem).
- Faide: saikron ke bajaye ek listener (kam memory, tez setup), aur baad me jore ya dobara bane items khud kaam karte hain. Tables, menus, chat lists aur khud React clicks isi tarah sambhalte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="stopPropagation and clicking outside">

<Tr>
<En>
A common pattern: close a dropdown when the user clicks **outside** it. Listen on `document` and check whether the click target is inside the menu with `contains`. This is better than `stopPropagation()`, which can silently break other listeners (like analytics or other menus).
</En>
<Ur>
Aam pattern: jab user dropdown ke **bahar** click kare to use band karein. `document` par sunein aur `contains` se check karein ke click ka target menu ke andar hai ya nahi. Ye `stopPropagation()` se behtar hai, jo khamoshi se doosre listeners (jaise analytics ya doosre menus) tor sakta hai.
</Ur>
</Tr>

```html preview-js h=230
<style>
  #menu { display: none; border: 1px solid #cbd5e1; padding: 6px; width: 140px; }
  #menu.open { display: block; }
</style>
<div id="dropdown">
  <button id="toggle" aria-expanded="false">Account ▾</button>
  <div id="menu"><a href="#">Profile</a><br><a href="#">Settings</a></div>
</div>
<p>Click anywhere here to close the menu.</p>
<pre id="log"></pre>
<script>
  const dropdown = document.querySelector("#dropdown");
  const menu = document.querySelector("#menu");
  const toggle = document.querySelector("#toggle");
  const log = (m) => (document.querySelector("#log").textContent = m);

  toggle.addEventListener("click", () => {
    const open = menu.classList.toggle("open");
    toggle.setAttribute("aria-expanded", String(open));
    log("toggled: " + (open ? "open" : "closed"));
  });

  document.addEventListener("click", (event) => {
    if (menu.classList.contains("open") && !dropdown.contains(event.target)) {
      menu.classList.remove("open");
      toggle.setAttribute("aria-expanded", "false");
      log("clicked outside: closed");
    }
  });
```

<Step title="input vs change, and debouncing">

<Tr>
<En>
`input` fires on **every** change to a field's value. `change` fires when the change is **committed**: when a text field loses focus, or immediately for checkboxes and selects. For live search, `input` + **debounce** (wait until typing pauses) avoids sending a request for every letter. Type "lamp" quickly.
</En>
<Ur>
`input` field ki value ki **har** tabdeeli par chalta hai. `change` tab chalta hai jab tabdeeli **pakki** ho: jab text field se focus hate, ya checkboxes aur selects ke liye foran. Live search ke liye `input` + **debounce** (type rukne tak intezar) har harf par request bhejne se bachata hai. Jaldi se "lamp" likhein.
</Ur>
</Tr>

```html preview-js h=230
<input id="q" placeholder="Search products">
<pre id="log"></pre>
<script>
  const log = document.querySelector("#log");
  const lines = [];
  const show = (m) => { lines.push(m); log.textContent = lines.slice(-8).join("\n"); };

  function debounce(fn, ms) {
    let timer;
    return (...args) => {
      clearTimeout(timer);
      timer = setTimeout(() => fn(...args), ms);
    };
  }

  const search = debounce((value) => show("→ SEARCH request for " + JSON.stringify(value)), 300);

  const q = document.querySelector("#q");
  q.addEventListener("input", (e) => {
    show("input: " + e.target.value);
    search(e.target.value);
  });
  q.addEventListener("change", (e) => show("change: " + e.target.value + " (committed)"));
</script>
```

<Step title="Removing listeners: once and AbortController">

<Tr>
<En>
Listeners stay until removed. `removeEventListener` needs the **same function reference**, so anonymous arrow functions can't be removed that way. Two simpler tools: `{ once: true }` removes the listener after its first run, and an **`AbortController`** signal removes many listeners at once.
</En>
<Ur>
Listeners hataye jane tak rehte hain. `removeEventListener` ko **wahi function reference** chahiye, isliye be-naam arrow functions us tarah hataye nahi ja sakte. Do aasan auzaar: `{ once: true }` pehli dafa chalne ke baad listener hata deta hai, aur **`AbortController`** signal kai listeners ek saath hata deta hai.
</Ur>
</Tr>

```html preview-js h=230
<button id="welcome">Claim welcome coupon</button>
<button id="tracked">Tracked button</button>
<button id="stop">Stop tracking</button>
<pre id="log"></pre>
<script>
  const log = (m) => (document.querySelector("#log").textContent += m + "\n");

  document.querySelector("#welcome").addEventListener(
    "click",
    () => log("coupon WELCOME10 claimed (only once)"),
    { once: true }
  );

  const controller = new AbortController();
  const { signal } = controller;
  document.querySelector("#tracked").addEventListener("click", () => log("tracked click"), { signal });
  window.addEventListener("resize", () => log("tracked resize"), { signal });

  document.querySelector("#stop").addEventListener("click", () => {
    controller.abort();
    log("all tracking listeners removed");
  });
</script>
```

```text
tracked click
```

```html preview-js h=200
  document.querySelectorAll(".product button").forEach((button) => {
```

<Step title="Scroll, passive listeners and performance">

<Tr>
<En>

Some events fire **very often**: `scroll`, `mousemove`, `pointermove`, `resize`, `touchmove` (dozens of times per second). Heavy work in those handlers makes the page stutter.

- Mark scroll/touch listeners **passive**: `addEventListener("touchmove", fn, { passive: true })` promises you won't call `preventDefault()`, so the browser can scroll immediately without waiting for your code. (Chrome makes `touchstart`/`touchmove`/`wheel` on `window`/`document` passive by default.)
- **Throttle** or use `requestAnimationFrame` to do work at most once per frame.
- Often you don't need scroll events at all: `IntersectionObserver` tells you when elements become visible (lazy loading, "back to top" buttons, analytics), and CSS `position: sticky` handles sticky headers.

```text
let ticking = false;
window.addEventListener("scroll", () => {
  if (ticking) return;
  ticking = true;
  requestAnimationFrame(() => {
    header.classList.toggle("shadow", window.scrollY > 10);
    ticking = false;
  });
}, { passive: true });
```

</En>
<Ur>

Kuch events **bohot aksar** chalte hain: `scroll`, `mousemove`, `pointermove`, `resize`, `touchmove` (fi second darjanon dafa). In handlers me bhaari kaam page ko atka deta hai.

- Scroll/touch listeners ko **passive** nishaan zad karein: `addEventListener("touchmove", fn, { passive: true })` waada karta hai ke aap `preventDefault()` call nahi karenge, isliye browser aap ke code ka intezar kiye baghair foran scroll kar sakta hai. (Chrome `window`/`document` par `touchstart`/`touchmove`/`wheel` ko default me passive banata hai.)
- Har frame me zyada se zyada ek dafa kaam ke liye **throttle** karein ya `requestAnimationFrame` lein.
- Aksar aap ko scroll events ki zaroorat hi nahi: `IntersectionObserver` batata hai ke elements kab nazar aate hain (lazy loading, "back to top" buttons, analytics), aur CSS `position: sticky` chipakne wale headers sambhalta hai.

```text
let ticking = false;
window.addEventListener("scroll", () => {
  if (ticking) return;
  ticking = true;
  requestAnimationFrame(() => {
    header.classList.toggle("shadow", window.scrollY > 10);
    ticking = false;
  });
}, { passive: true });
```

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- The `ticking` flag + `requestAnimationFrame` means that even if `scroll` fires 10 times within one frame, the header is updated once per frame.
- Reading `scrollY` is cheap; reading layout values like `offsetTop` inside scroll handlers can force layout (previous lessons), so read them once and cache.
- Prefer **pointer events** (`pointerdown`, `pointermove`, `pointerup`) for drag interactions: one set of events covers mouse, touch and pen.

</En>
<Ur>

- `ticking` flag + `requestAnimationFrame` ka matlab ek frame me `scroll` 10 dafa chale tab bhi header har frame me ek dafa update hota hai.
- `scrollY` parhna sasta hai; scroll handlers ke andar `offsetTop` jaisi layout values parhna layout par majboor kar sakta hai (pichhle lessons), isliye ek dafa parh kar mehfooz rakhein.
- Drag interactions ke liye **pointer events** (`pointerdown`, `pointermove`, `pointerup`) pasand karein: events ka ek majmua mouse, touch aur pen sab sambhalta hai.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="A listener per item (and none for new items)">

```text
document.querySelectorAll(".remove").forEach((btn) =>
  btn.addEventListener("click", removeItem)
);
// items added later have no listener; 1,000 rows = 1,000 listeners
```

</Bad>
<Good title="Delegate to the container">

```text
list.addEventListener("click", (event) => {
  const btn = event.target.closest(".remove");
  if (btn && list.contains(btn)) removeItem(btn.closest("li"));
});
```

</Good>
</Compare>

<Compare>
<Bad title="Calling the function instead of passing it">

```text
button.addEventListener("click", save());
// save() runs immediately, once, and its return value (undefined)
// is registered as the listener
```

</Bad>
<Good title="Pass the function">

```text
button.addEventListener("click", save);
button.addEventListener("click", () => save(productId));
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Using `event.target` when you meant `currentTarget`** (or the element from `closest`): the target may be an inner icon or span.
- **Listening to `click` on a submit button** instead of `submit` on the form.
- **Using `stopPropagation()` as a quick fix**: it breaks delegation and outside-click logic elsewhere.
- **Adding listeners inside other listeners** (or inside a render loop) so they pile up and fire many times.
- **Never removing global listeners** in single-page apps (memory leaks, duplicated actions).
- **Clickable `<div>`s**: use `<button>` so keyboard users can reach and activate it (Enter/Space fire `click` on buttons).

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Jab `currentTarget` (ya `closest` ka element) chahiye tha tab `event.target` istemal karna**: target andar ka icon ya span ho sakta hai.
- Form par `submit` ke bajaye **submit button par `click` sunna**.
- **Fori hal ke taur par `stopPropagation()` lagana**: ye doosri jagah delegation aur bahar click ki logic torta hai.
- **Listeners ke andar listeners jorna** (ya render loop ke andar) taa ke wo jama ho kar kai dafa chalein.
- Single-page apps me **global listeners kabhi na hatana** (memory leaks, dohre amal).
- **Click hone wale `<div>`**: `<button>` lein taa ke keyboard users us tak pohanch kar use chala sakein (Enter/Space buttons par `click` chalate hain).

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- `addEventListener(type, fn, options)`; the handler gets an **event object** (`type`, `target`, `key`, modifiers…).
- Events travel **capture → target → bubble**. `target` = where it happened; `currentTarget` = whose listener runs.
- `preventDefault()` cancels default actions (link navigation, form submit); `stopPropagation()` stops the journey (rarely needed).
- **Delegation**: one listener on a container + `event.target.closest(selector)`; works for items added later.
- Outside clicks: listen on `document`, check `container.contains(event.target)`.
- `keydown` + `event.key` for shortcuts; `input` for every change, `change` when committed; debounce search.
- Remove listeners with `{ once: true }` or `AbortController` signals; clean up global listeners.
- `CustomEvent` with `detail` lets parts of the page communicate; mark scroll/touch listeners `passive`.

</En>
<Ur>

- `addEventListener(type, fn, options)`; handler ko **event object** milta hai (`type`, `target`, `key`, modifiers…).
- Events **capture → target → bubble** safar karte hain. `target` = jahan hua; `currentTarget` = jis ka listener chal raha hai.
- `preventDefault()` default amal mansookh karta hai (link navigation, form submit); `stopPropagation()` safar rokta hai (kam zaroorat).
- **Delegation**: container par ek listener + `event.target.closest(selector)`; baad me jure items ke liye bhi chalta hai.
- Bahar ke clicks: `document` par sunein, `container.contains(event.target)` check karein.
- Shortcuts ke liye `keydown` + `event.key`; har tabdeeli ke liye `input`, pakki hone par `change`; search ko debounce karein.
- `{ once: true }` ya `AbortController` signals se listeners hatayen; global listeners saaf karein.
- `detail` ke saath `CustomEvent` page ke hisson ko baat karne deta hai; scroll/touch listeners `passive` nishaan zad karein.

</Ur>
</Tr>
</Takeaways>

<DeepDive title="More about events">

**Events that don't bubble.** `focus`, `blur`, `mouseenter`, `mouseleave`, `load` and `scroll` on elements don't bubble. For delegation use the bubbling versions: `focusin` / `focusout`, `mouseover` / `mouseout`, `pointerover` / `pointerout`.

**`stopImmediatePropagation()`.** Also stops other listeners on the **same** element. Rarely appropriate.

**`this` in handlers.** In a regular `function` handler, `this` is `event.currentTarget`; arrow functions keep the outer `this`, so use `event.currentTarget` explicitly.

**Event loop.** User events are **tasks** in the event loop (JavaScript module). A long-running handler blocks the next events, which is what INP measures.

**`composedPath()`.** Returns the full propagation path, including through Shadow DOM boundaries.

**React's synthetic events.** React attaches listeners at the root and wraps native events in its own objects with the same API (`e.target`, `e.preventDefault()`). `onChange` in React fires on every input, like the native `input` event.

**Touch and pointer.** `pointer` events unify mouse, touch and pen, and support `setPointerCapture` for reliable dragging. `touch-action: none` in CSS tells the browser not to scroll while you handle gestures.

**Focus management.** `focus`, `blur`, `:focus-visible` and keyboard navigation are part of accessible event handling; every mouse action should have a keyboard equivalent.

</DeepDive>

<DeepDive title="Real world: the table that got slower every day">

An admin dashboard showed an orders table that refreshed every 30 seconds. On each refresh, the code rebuilt the rows with `innerHTML`, then looped through all `.approve`, `.refund` and `.details` buttons to attach listeners, and also added a `document` click listener to close row menus.

Staff left the dashboard open all day. By afternoon it was sluggish; clicking "Refund" sometimes opened **dozens** of confirmation dialogs. Memory grew to 1.5 GB.

The cause: the `document` listener was added on **every refresh** and never removed, about 1,000 of them after eight hours. Each fired on every click, and each closure kept old rows alive in memory.

The fix:

1. **One delegated listener** on the `<tbody>`, added once at startup, handling all three buttons with `event.target.closest("[data-action]")` and reading `data-action` / `data-order-id`.
2. The outside-click listener added **once**, with an `AbortController` tied to the page's lifetime.
3. Rows updated with `replaceChildren` from data, so there were no listeners to re-attach at all.

Memory stayed flat at around 90 MB over a full day, and duplicate dialogs disappeared.

</DeepDive>

<DeepDive title="Security lens">

- **Never use inline handler attributes with dynamic values** (`onclick="buy('` + name + `')"`): they're a form of `innerHTML`/`eval` and invite XSS. Attach listeners in JavaScript and read data from `dataset`.
- **`event.isTrusted`** distinguishes real user actions from script-generated events, useful for sensitive actions, though it isn't a substitute for server-side checks.
- **Clickjacking**: a malicious site can frame yours invisibly and trick users into clicking. Send `X-Frame-Options: DENY` or CSP `frame-ancestors` to prevent framing.
- **Validate on the server**: disabling a button or preventing a click in JavaScript doesn't stop someone sending the request directly.
- **`postMessage` events** from other windows must check `event.origin` before trusting `event.data`.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="Explain event bubbling and capturing.">
When an event occurs on an element, it first travels from the window down through the ancestors to the target in the capturing phase, triggers listeners on the target, then travels back up through the ancestors in the bubbling phase. Listeners run in the bubbling phase by default unless registered with capture set to true.
</QA>

<QA q="What is event delegation and why use it?">
Attaching a single listener to a common ancestor instead of each child, and determining which child was involved via event.target, often with closest. It reduces the number of listeners and automatically handles elements added later.
</QA>

<QA q="What is the difference between event.target and event.currentTarget?">
target is the element where the event originated, which may be a deeply nested child. currentTarget is the element the currently running listener is attached to.
</QA>

<QA q="What is the difference between preventDefault and stopPropagation?">
preventDefault cancels the browser's default action for the event, such as following a link or submitting a form, but the event still propagates. stopPropagation stops the event from reaching further elements in the propagation path but does not cancel the default action.
</QA>

<QA q="How do you implement debounce?">
Return a wrapper function that clears any pending timer and starts a new timer each time it is called, invoking the original function only when the timer completes without another call, so it runs once after activity stops for the given delay.
</QA>

</DeepDive>
