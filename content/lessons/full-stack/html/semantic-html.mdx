<BigIdea>
<Tr>
<En>
**Semantic HTML** means choosing elements for their **meaning**, not their looks. `<nav>` says "this is navigation", `<main>` "this is the main content", `<button>` "this does something", `<article>` "this is a self-contained piece". Browsers, **screen readers**, **search engines**, translators and reader modes all use that meaning: a screen-reader user can jump straight to the main content only if you used `<main>`. A page built only from `<div>` and `<span>` ("**div soup**") looks the same to sighted users but is an unlabelled jumble to everyone and everything else. Rule: **use the most specific element that fits**, and fall back to `<div>`/`<span>` only for styling or layout wrappers.
</En>
<Ur>
**Semantic HTML** ka matlab elements ko un ke **matlab** ke liye chunna hai, shakal ke liye nahi. `<nav>` kehta hai "ye navigation hai", `<main>` "ye asal mawad hai", `<button>` "ye kuch karta hai", `<article>` "ye apne aap me mukammal tukra hai". Browsers, **screen readers**, **search engines**, tarjuma tools aur reader modes sab ye matlab istemal karte hain: screen-reader user seedha asal mawad par tab hi ja sakta hai jab aap ne `<main>` istemal kiya ho. Sirf `<div>` aur `<span>` se bana page ("**div soup**") dekhne walon ko waisa hi lagta hai lekin baqi har shakhs aur cheez ke liye be-label gadbad hai. Qaida: **jo sab se khaas element fit ho wo lein**, aur `<div>`/`<span>` sirf styling ya layout wrappers ke liye.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

The same page header, written two ways:

```text
<!-- Div soup: only class names describe it, and only to humans reading the code -->
<div class="header">
  <div class="logo">Mango Shop</div>
  <div class="menu"><span onclick="go('/')">Home</span> <span onclick="go('/shop')">Shop</span></div>
</div>

<!-- Semantic: the elements describe it to browsers, tools and people -->
<header>
  <p class="logo">Mango Shop</p>
  <nav aria-label="Main">
    <a href="/">Home</a> <a href="/shop">Shop</a>
  </nav>
</header>
```

Both can look identical. In the second, the browser knows there's a site header, a navigation region and two real links: keyboard users can Tab to them, screen readers say "navigation, Main, link Home", search engines follow them, and they work without JavaScript.

</En>
<Ur>

Ek hi page header, do tareeqon se:

```text
<!-- Div soup: only class names describe it, and only to humans reading the code -->
<div class="header">
  <div class="logo">Mango Shop</div>
  <div class="menu"><span onclick="go('/')">Home</span> <span onclick="go('/shop')">Shop</span></div>
</div>

<!-- Semantic: the elements describe it to browsers, tools and people -->
<header>
  <p class="logo">Mango Shop</p>
  <nav aria-label="Main">
    <a href="/">Home</a> <a href="/shop">Shop</a>

</header>
```

Dono bilkul ek jaise dikh sakte hain. Doosre me browser jaanta hai ke site header, navigation hissa aur do asli links hain: keyboard users Tab se un tak pohnchte hain, screen readers "navigation, Main, link Home" bolte hain, search engines un par chalte hain, aur ye JavaScript ke baghair chalte hain.

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Accessibility:** about 1 in 6 people has a significant disability. Screen-reader users navigate by headings, landmarks, links and buttons. Many countries require accessible sites, and lawsuits over inaccessible sites are common.
- **SEO:** search engines understand structure from headings, `<main>`, `<article>`, links and lists.
- **Free behaviour:** `<button>` is focusable and works with Enter/Space; links open in new tabs; `<details>` expands without JavaScript; forms submit on Enter. Divs give none of that.
- **Maintainability:** `<nav>`, `<article>`, `<footer>` explain themselves to the next developer.
- **Interviews:** "Why `<button>` and not a clickable `<div>`?" is a classic question.

</En>
<Ur>

- **Rasai (accessibility):** taqreeban har 6 me se 1 shakhs ko numaya maazoori hai. Screen-reader users headings, landmarks, links aur buttons se chalte hain. Kai mulk qabil-e-rasai sites lazmi karte hain, aur na-qabil-e-rasai sites par muqadme aam hain.
- **SEO:** search engines headings, `<main>`, `<article>`, links aur lists se banawat samajhte hain.
- **Muft rawaiya:** `<button>` focus hota hai aur Enter/Space se chalta hai; links naye tab me khulte hain; `<details>` JavaScript ke baghair khulta hai; forms Enter par submit hote hain. Divs me ye kuch nahi.
- **Sambhalna aasaan:** `<nav>`, `<article>`, `<footer>` agle developer ko apna aap khud samjhate hain.
- **Interviews:** "Clickable `<div>` ke bajaye `<button>` kyun?" purana sawal hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Always: in plain HTML, server templates and React/Next.js JSX (where div soup is very common and just as harmful). Quick decision guide:

| Content | Element |
| --- | --- |
| Site banner, main menu, footer | `<header>`, `<nav>`, `<footer>` |
| This page's unique content | `<main>` (one per page) |
| Self-contained item (post, product card, comment) | `<article>` |
| Themed part with its own heading | `<section>` |
| Goes somewhere / does something | `<a href>` / `<button>` |
| Pure layout or styling wrapper | `<div>` / `<span>` |

## Picture it

<Tr>
<En>

Imagine a **shopping mall with no signs**: every shop, toilet, exit and food court is an identical grey door. Sighted visitors can peek inside, but a blind visitor, a delivery driver or a fire inspector can't find anything. Semantic HTML puts **signs on the doors**: "Main entrance" (`<header>`), "Directory" (`<nav>`), "Shops" (`<main>`), "Food court" (`<aside>`), "Exit" (`<footer>`). The building is the same; now everyone can find their way.

</En>
<Ur>

Ek **bina board wala shopping mall** sochein: har dukaan, bathroom, nikalne ka raasta aur food court ek jaisa saleti darwaza hai. Dekhne wale andar jhaank sakte hain, lekin nabeena visitor, delivery driver ya fire inspector ko kuch nahi milta. Semantic HTML **darwazon par board** lagata hai: "Main entrance" (`<header>`), "Directory" (`<nav>`), "Shops" (`<main>`), "Food court" (`<aside>`), "Exit" (`<footer>`). Imarat wahi hai; ab har koi raasta dhoondh leta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Landmarks: the page's main regions">

<Tr>
<En>Landmarks mark the big regions: `<header>` (site banner), `<nav>` (major navigation), `<main>` (this page's unique content, **one per page**), `<aside>` (related, secondary content) and `<footer>`. Screen readers list them so users can jump to "main" or "navigation" and skip menus repeated on every page. `<header>`/`<footer>` directly in `<body>` become the **banner** and **contentinfo** landmarks; inside an `<article>` they're just that article's header/footer. Use `aria-label` to tell several navs apart ("Main", "Footer"), and keep site-wide content out of `<main>`.</En>
<Ur>Landmarks bare hisse batate hain: `<header>` (site banner), `<nav>` (bari navigation), `<main>` (is page ka munfarid mawad, **har page par ek**), `<aside>` (mutalliq, doosre darje ka mawad) aur `<footer>`. Screen readers inhen list karte hain taa ke users "main" ya "navigation" par kood saken aur har page par dohraye menus chhor saken. `<body>` me seedhe `<header>`/`<footer>` **banner** aur **contentinfo** landmarks bante hain; `<article>` ke andar wo sirf us article ke header/footer hain. Kai navs alag karne ko `aria-label` ("Main", "Footer") lagayen, aur site bhar ka mawad `<main>` se bahar rakhein.</Ur>
</Tr>

```html preview h=330
<header>
  <p><strong>Mango Shop</strong></p>
  <nav aria-label="Main">
    <a href="#">Home</a> · <a href="#">Shop</a> · <a href="#">Contact</a>
  </nav>
</header>

<main>
  <h1>Fresh mangoes</h1>
  <p>Kent, Keitt and Ataulfo, delivered the same day.</p>
</main>

<aside>
  <h2>Delivery areas</h2>
  <p>Austin and Seattle.</p>
</aside>

<footer>
  <p>&copy; 2026 Mango Shop · <a href="#">Privacy</a></p>
</footer>
```

<Happened>
<Tr>
<En>

`<header>` holds the site name and the main `<nav>` (`aria-label="Main"` is the name a screen reader announces). `<main>` holds this page's content starting with its `<h1>`, `<aside>` the secondary info and `<footer>` the legal links. Without CSS the regions simply stack; a side-by-side layout is CSS's later job (Flexbox or Grid). Semantics and layout are separate:

```text
┌──────────── header (banner) ────────────┐
│ Mango Shop      nav: Home · Shop · ...   │
├──────────────── main ───────────────┬────┤
│ h1 Fresh mangoes                    │aside│
│ p ...                               │     │
├──────────── footer (contentinfo) ───┴────┤
│ © 2026 Mango Shop · Privacy              │
└──────────────────────────────────────────┘
```

</En>
<Ur>

`<header>` me site ka naam aur main `<nav>` hai (`aria-label="Main"` wo naam hai jo screen reader bolta hai). `<main>` me is page ka mawad `<h1>` se shuru, `<aside>` me doosre darje ki maloomat aur `<footer>` me qanooni links. CSS ke baghair hisse bas upar neeche lagte hain; saath saath layout baad me CSS ka kaam hai (Flexbox ya Grid). Semantics aur layout alag kaam hain:


<Step title="What a screen reader sees">

<Tr>
<En>Browsers turn the DOM into an **accessibility tree**: each element's **role** (what it is), **name** (its label) and **state** (checked, expanded…). Screen readers read this tree, not your CSS, so meaningless elements become a flat list of text. Inspect it in Chrome DevTools → Elements → **Accessibility**, Firefox's Accessibility Inspector, or a real screen reader (NVDA on Windows is free; VoiceOver is built into macOS/iOS, TalkBack into Android). Below, a real browser (driven by Playwright) prints the tree of the same content written semantically and as div soup.</En>
<Ur>Browsers DOM ko **accessibility tree** me badalte hain: har element ka **role** (kya hai), **name** (label) aur **state** (checked, expanded…). Screen readers ye darakht parhte hain, aap ka CSS nahi, isliye be-matlab elements text ki sapaat list ban jate hain. Ise Chrome DevTools → Elements → **Accessibility**, Firefox ke Accessibility Inspector, ya asli screen reader me dekhein (Windows par NVDA muft; macOS/iOS me VoiceOver, Android me TalkBack shamil). Neeche asli browser (Playwright se chalaya) ek hi mawad ko semantic aur div soup dono tarah likh kar darakht chhaapta hai.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
semantic = """<header><nav><a href="/">Home</a></nav></header>
<main><h1>Shop</h1><article><h2>Mango</h2><p>Sweet and fresh.</p></article><aside>Free delivery</aside></main>
<footer>Contact us</footer>"""
div_soup = """<div class="header"><div class="nav"><a href="/">Home</a></div></div>
<div class="main"><div class="title">Shop</div><div class="card"><div class="card-title">Mango</div><p>Sweet and fresh.</p></div><div class="side">Free delivery</div></div>
<div class="footer">Contact us</div>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    for label, html in [("SEMANTIC", semantic), ("DIV SOUP", div_soup)]:
        page.set_content("<!DOCTYPE html><title>Demo</title><body>" + html)
        print(f"--- {label}:")
        print(page.locator("body").aria_snapshot())
    browser.close()
PY
```

```text output

- banner:
  - navigation:
    - link "Home":
      - /url: /
- main:
  - heading "Shop" [level=1]
  - article:
    - heading "Mango" [level=2]
    - paragraph: Sweet and fresh.
  - complementary: Free delivery
- contentinfo: Contact us
--- DIV SOUP:
- link "Home":
  - /url: /
- text: Shop Mango
- paragraph: Sweet and fresh.
- text: Free delivery Contact us
```

<Happened>
<Tr>
<En>The script loaded each version into Chromium and printed its **ARIA snapshot**, a text form of the accessibility tree. **Semantic:** `header` became **banner**, `nav` **navigation**, `main` **main**, `h1`/`h2` real **headings** with levels, `article` **article**, `aside` **complementary** and `footer` **contentinfo**; a screen-reader user can jump to any of them with one key. **Div soup:** only the link and paragraph kept meaning. "Shop" and "Mango" merged into one line of plain text, the side note and footer ran together, and there were no landmarks at all.</En>
<Ur>Script ne har version Chromium me load kar ke us ka **ARIA snapshot** chhaapa, accessibility tree ki text shakal. **Semantic:** `header` **banner**, `nav` **navigation**, `main` **main**, `h1`/`h2` levels wali asli **headings**, `article` **article**, `aside` **complementary** aur `footer` **contentinfo** bane; screen-reader user ek key se kisi par bhi kood sakta hai. **Div soup:** sirf link aur paragraph ka matlab bacha. "Shop" aur "Mango" saade text ki ek line ban gaye, side note aur footer jur gaye, aur koi landmark nahi tha.</Ur>

<Step title="article and section">

<Tr>
<En>`<article>` is a **self-contained** piece that makes sense alone (a blog post, a product card, a comment, a news item). `<section>` is a **thematic group** within a page, normally with its own heading. Ask: "Could this be shared on its own?" → `<article>`. "Is it a part of something bigger, with a heading?" → `<section>`. "Just styling or layout?" → `<div>`. Articles can contain sections (chapters) and sections can contain articles (a "Latest posts" list). A section with no heading is usually a `<div>`.</En>
<Ur>`<article>` **apne aap me mukammal** tukra hai jo akela bhi samajh aaye (blog post, product card, comment, khabar). `<section>` page ke andar **mauzooati group** hai, aam taur par apni heading ke saath. Poochhein: "Kya ye akela share ho sakta hai?" → `<article>`. "Kya ye kisi bari cheez ka heading wala hissa hai?" → `<section>`. "Sirf styling ya layout?" → `<div>`. Articles me sections (baab) aur sections me articles (ek "Latest posts" list) ho sakte hain. Bina heading section aksar `<div>` hota hai.</Ur>
</Tr>

```html preview h=360
<main>
  <h1>DevGuide Blog</h1>

  <section>
    <h2>Latest posts</h2>

    <article>
      <h3>JSON vs YAML</h3>
      <p>When to use each format, with real examples.</p>
      <footer>By <a href="#">Emma</a>, <time datetime="2026-11-09">9 November 2026</time></footer>
    </article>

    <article>
      <h3>Signing your Git commits</h3>
      <p>Prove that your commits really come from you.</p>
      <footer>By <a href="#">Jack</a>, <time datetime="2026-11-06">6 November 2026</time></footer>
    </article>
  </section>
</main>
```

<Happened>
<Tr>
<En>One `<section>` groups the posts under "Latest posts". Each teaser is an `<article>` with its own heading that would make sense shown alone elsewhere. Each has its own `<footer>` (inside an article, a footer belongs to that article, not the page). `<time datetime="2026-11-09">` gives machines an exact date while people read "9 November 2026".</En>
<Ur>Ek `<section>` posts ko "Latest posts" ke neeche ikattha karta hai. Har teaser apni heading wala `<article>` hai jo kahin aur akela dikhaya jaye to bhi samajh aaye. Har ek ka apna `<footer>` hai (article ke andar footer us article ka hota hai, page ka nahi). `<time datetime="2026-11-09">` machines ko bilkul durust tareekh deta hai jabke log "9 November 2026" parhte hain.</Ur>
</Tr>
</Happened>

<Step title="Buttons vs links">

<Tr>
<En>**Links** (`<a href>`) **go somewhere**: another page, a section, a file. **Buttons** (`<button>`) **do something**: submit, open a menu, add to cart, toggle dark mode. Each has built-in behaviour that clickable `<div>`s lack: reachable with Tab, activated by keyboard (Enter for links, Enter/Space for buttons), announced with the right role, and links can be opened in new tabs, copied and bookmarked. `<a href="#" onclick>` and `<div onclick>` are classic anti-patterns. In the result below, try reaching the fake button with Tab: you can't.</En>
<Ur>**Links** (`<a href>`) **kahin le jate hain**: doosra page, koi hissa, file. **Buttons** (`<button>`) **kuch karte hain**: submit, menu kholna, cart me daalna, dark mode badalna. Har ek me aisa andaruni rawaiya hai jo clickable `<div>`s me nahi: Tab se pohnch, keyboard se chalna (links ke liye Enter, buttons ke liye Enter/Space), sahi role ke saath elaan, aur links naye tab me khulte, copy aur bookmark hote hain. `<a href="#" onclick>` aur `<div onclick>` purane ghalat namoone hain. Neeche ke result me Tab se naqli button tak pohnchne ki koshish karein: nahi pohnch sakte.</Ur>
</Tr>

```html preview-js h=170 invalid
<p>
  <a href="#reviews">Read reviews</a>
  <button type="button" onclick="this.textContent = 'Added ✓'">Add to cart</button>
  <span style="padding:4px 8px;border:1px solid #888;cursor:pointer" onclick="this.textContent = 'Added ✓'">Fake button (div/span)</span>
</p>
<p>Click into this box, then press <kbd>Tab</kbd> repeatedly: focus visits the link and the real button, but skips the fake one.</p>
```

<Happened>
<Tr>
<En>The link goes to `#reviews`, a part of the page. `<button type="button">` runs an action with mouse, keyboard and touch, and screen readers say "Add to cart, button". The `<span onclick>` works with a mouse only: not focusable, no keyboard, announced as plain text. Fixing it would need `role`, `tabindex` and key handlers that `<button>` gives free. In forms, a `<button>` with no `type` is `submit`, so write `type="button"` for buttons that shouldn't submit.</En>
<Ur>Link `#reviews` par jata hai, page ka ek hissa. `<button type="button">` mouse, keyboard aur touch se kaam karta hai, aur screen readers "Add to cart, button" bolte hain. `<span onclick>` sirf mouse se chalta hai: focus nahi hota, keyboard nahi, saade text ki tarah elaan. Ise theek karne ko `role`, `tabindex` aur key handlers chahiyen jo `<button>` muft deta hai. Forms me bina `type` `<button>` `submit` hota hai, isliye submit na karne wale buttons par `type="button"` likhein.</Ur>
</Tr>
</Happened>

<Step title="Text-level semantics">

<Tr>
<En>Inline elements give meaning to words: `<strong>` (importance), `<em>` (stress), `<mark>` (highlighted), `<time>`, `<abbr>`, `<code>`, `<kbd>`, `<cite>`, `<q>`, `<small>` (fine print), `<sub>`/`<sup>`, `<del>`/`<ins>` (edits). They say **why** text is special, not just that it's bold. Use `<strong>` for warnings and key facts, `<em>` where spoken stress changes meaning, and `<b>`/`<i>` only for stylistic offsets (product names, foreign words). If you only want bold, use CSS.</En>
<Ur>Inline elements alfaaz ko matlab dete hain: `<strong>` (ahmiyat), `<em>` (zor), `<mark>` (numaya), `<time>`, `<abbr>`, `<code>`, `<kbd>`, `<cite>`, `<q>`, `<small>` (bareek likhai), `<sub>`/`<sup>`, `<del>`/`<ins>` (tabdeeliyan). Ye batate hain text **kyun** khaas hai, sirf ye nahi ke bold hai. Warnings aur aham baaton ke liye `<strong>`, jahan bolne ka zor matlab badle wahan `<em>`, aur `<b>`/`<i>` sirf andaz ke farq ke liye (product names, ghair mulki alfaaz). Sirf bold chahiye to CSS.</Ur>
</Tr>

```html preview h=260
<p>Search results for "mango": Fresh <mark>mango</mark> juice.</p>

<p>Press <kbd>Ctrl</kbd> + <kbd>S</kbd> to save, then run <code>git commit</code>.</p>
<p>Price: <del>$12.00</del> <ins>$9.50</ins> <small>(incl. tax)</small></p>
<p>Water is H<sub>2</sub>O; 10<sup>3</sup> = 1000.</p>
```

<Tr>

## Common mistakes

<Compare>
<Bad title="Clickable divs and fake headings">

```text
<div class="title"><b>Keitt Mangoes</b></div>
<div class="btn" onclick="addToCart()">Add to cart</div>
<a href="#" onclick="openMenu()">Menu</a>
```

</Bad>
<Good title="Real headings, buttons and links">

```text
<h1>Keitt Mangoes</h1>
<button type="button" onclick="addToCart()">Add to cart</button>
<button type="button" aria-expanded="false">Menu</button>
<a href="/cart">View cart</a>
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Headings chosen for size**, or bold paragraphs used as headings.
- **Multiple `<main>` elements**, or site-wide nav and footers inside `<main>`.
- **`<section>` everywhere** as a generic wrapper, without headings.
- **`<b>`/`<i>` for importance**, or `<strong>`/`<em>` purely for looks.
- **Fake lists** made with line breaks and bullet characters.
- **Utility classes on divs** (CSS frameworks) don't add meaning: you still need the right elements underneath.
- **Missing `type="button"`** on buttons inside forms, accidentally submitting the form.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Size dekh kar headings**, ya bold paragraphs bator headings.
- **Kai `<main>`**, ya site bhar ki nav aur footers `<main>` ke andar.
- Bina headings aam wrapper bator **har jagah `<section>`**.
- **Ahmiyat ke liye `<b>`/`<i>`**, ya sirf shakal ke liye `<strong>`/`<em>`.
- Line breaks aur bullet characters se bani **naqli lists**.
- Divs par **utility classes** (CSS frameworks) matlab nahi jortin: neeche sahi elements phir bhi chahiyen.
- Forms ke andar buttons par **`type="button"` gum**, jis se form ghalti se submit hota hai.

</Ur>
</Tr>

<DeepDive title="Real world: the admission portal nobody could submit">

A university's admission portal received complaints from visually impaired applicants who couldn't submit forms: the "Next" and "Submit" controls were `<div>`s with click handlers, headings were bold `<span>`s, and the whole page was one unlabelled region. A screen reader announced only a stream of text, and the controls couldn't be reached by keyboard. The fix took two days and no redesign: `<div>`s became `<button>`s and `<a>`s, visual titles became real `<h1>`–`<h3>` headings, the layout got `<header>`, `<nav>`, `<main>` and `<footer>` landmarks, and step lists became `<ol>`. Automated checks (axe DevTools, Lighthouse) went from dozens of errors to none, keyboard-only navigation worked end to end, and the portal's Google snippets improved because headings and links now described the content.

</DeepDive>

<DeepDive title="Security lens">

Semantic elements behave predictably, which matters for security too: real links, buttons, forms and clear structure are easier to protect and audit than click handlers on divs.

- **Clickjacking and fake UI:** attackers imitate buttons and dialogs with styled divs. Real links show their destination on hover, which helps users spot fakes.
- **`javascript:` URLs in links** are an XSS risk: never build `href` from user input without allowing only safe schemes (`https:`, `mailto:`).
- **Hidden content is still content:** text hidden with CSS is in the DOM and accessibility tree unless removed or `aria-hidden`. Never rely on hiding for confidentiality.
- **Accessible security features:** CAPTCHAs, OTP inputs and security warnings must work with screen readers and keyboards, or users get locked out or pushed to unsafe workarounds.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is semantic HTML and why does it matter?">
Semantic HTML uses elements according to their meaning, such as header, nav, main, article, button and h1, rather than generic divs and spans. It matters because browsers expose that meaning in the accessibility tree for screen readers, search engines use it to understand content, elements get built-in keyboard and browser behaviour, and the code is easier to maintain.
</QA>

<QA q="What is the difference between article and section?">
An article is self-contained content that would make sense on its own or when syndicated, such as a blog post, product card or comment. A section is a thematic grouping within a page or article, typically with its own heading. If neither applies and the wrapper is only for styling, a div is appropriate.
</QA>

<QA q="When should you use a button versus a link?">
Use a link with an href when activating it navigates to a URL or a location in the page. Use a button when it performs an action such as submitting a form, opening a dialog or adding to a cart. Each has the correct role and built-in keyboard behaviour, which clickable divs or links with href="#" lack.
</QA>

<QA q="What are landmarks?">
Landmarks are major page regions exposed to assistive technologies so users can jump between them: banner from a top-level header, navigation from nav, main from main, complementary from aside, contentinfo from a top-level footer, plus form and search regions. Multiple landmarks of the same type should be distinguished with aria-label.
</QA>

<QA q="What is the difference between strong and b, or em and i?">
strong indicates strong importance and em indicates stress emphasis that changes the meaning of a sentence; both carry semantic meaning. b and i are for stylistic offsets without extra importance, such as keywords, product names or foreign phrases. Purely visual bolding or italics should be done with CSS.
</QA>

</DeepDive>

<DeepDive title="More practice">

3. Turn on a screen reader (NVDA, VoiceOver or TalkBack) for five minutes and navigate a site using only headings and landmarks.
