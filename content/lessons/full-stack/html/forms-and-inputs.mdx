<BigIdea>
<Tr>
<En>
A **form** collects input and sends it to a server. `<form>` says **where** (`action`) and **how** (`method="get"` or `"post"`); each control (`<input>`, `<select>`, `<textarea>`) needs a **`name`**, because the browser sends `name=value` pairs. Every control needs a visible **`<label>`**: a placeholder is **not** a label. Choose the right **`type`** (`email`, `tel`, `number`, `date`, `password`, `checkbox`, `radio`, `file`…) for the right mobile keyboard and free **validation** (`required`, `pattern`, `min`/`max`, `minlength`). Use **GET** for searches and filters, **POST** for anything that changes data or is private. Client-side validation only helps users: attackers skip it, so the **server must validate everything** again.
</En>
<Ur>
**Form** input jama kar ke server ko bhejta hai. `<form>` batata hai **kahan** (`action`) aur **kaise** (`method="get"` ya `"post"`); har control (`<input>`, `<select>`, `<textarea>`) ko **`name`** chahiye, kyun ke browser `name=value` jore bhejta hai. Har control ko nazar aane wala **`<label>`** chahiye: placeholder label **nahi**. Sahi mobile keyboard aur muft **validation** (`required`, `pattern`, `min`/`max`, `minlength`) ke liye sahi **`type`** chunein (`email`, `tel`, `number`, `date`, `password`, `checkbox`, `radio`, `file`…). Searches aur filters ke liye **GET**, data badalne wali ya private cheezon ke liye **POST**. Client-side validation sirf users ki madad hai: hamla awar ise chhor dete hain, isliye **server ko sab kuch dobara validate** karna lazmi hai.
</Ur>

<Why>
<Tr>
<En>

## Picture it

<Tr>
<En>

A web form is like a **paper application form at a bank counter**. Each box has a **printed label** ("Full name", "Social Security number") so you know what to write; the boxes have **rules** ("9 digits", "date of birth"); you hand it in at a specific **counter** (the server address, `action`); and the clerk **checks everything again** before accepting it, even if you were careful. HTML gives you the boxes, labels and rules; the browser checks the rules before handing it over; the server is the clerk who must double-check, because some people forge forms.

</En>

Web form **bank counter par kaghazi darkhwast form** jaisa hai. HTML khane, labels aur qawaid deta hai; browser dene se pehle qawaid check karta hai; server wo clerk hai jise dobara check karna hi hai, kyun ke kuch log jaali form bharte hain.

<Step title="A minimal form">

<Tr>
<En>`<form>` wraps the controls: `action` is where the data goes, `method` how. Each control has a `name`, and a submit `<button>` sends it. Without `name`, a value isn't sent at all, a very common beginner bug. No `action` means the current URL; no `method` means `get`. Pressing **Enter** in a text field submits too, for free.</En>
<Ur>`<form>` controls ko lapetta hai: `action` data ki manzil, `method` tareeqa. Har control ka `name` hota hai, aur submit `<button>` bhejta hai. `name` ke baghair value bilkul nahi jati, beginners ka bohot aam bug. `action` na ho to maujooda URL; `method` na ho to `get`. Text field me **Enter** dabana bhi muft me submit karta hai.</Ur>
</Tr>

```html preview h=150
<form action="/search" method="get" role="search">
  <label for="q">Search products</label>
  <input id="q" name="q" type="search" placeholder="e.g. keitt">
  <button type="submit">Search</button>
</form>

<Happened>
<Tr>

(In this preview, submitting tries to load `/search` in the small frame: there's no server behind it.)</En>

<Step title="GET vs POST: what the server actually receives">

<Tr>
<En>**GET** puts data in the URL **query string** (`/search?q=keitt+mango`): visible, bookmarkable and shareable, but also saved in history, server logs and analytics. **POST** puts it in the request **body** as `name=value&name=value` (`application/x-www-form-urlencoded`) and is meant for actions that **change** things. GET for search, filters and pagination; POST for login, signup, checkout and anything private. Never put passwords, SSNs or tokens in GET forms. Below, a tiny Python server records exactly what a real browser sends.</En>
<Ur>**GET** data URL ki **query string** me rakhta hai (`/search?q=keitt+mango`): nazar aane wala, bookmark aur share hone wala, lekin history, server logs aur analytics me bhi mehfooz. **POST** ise request **body** me `name=value&name=value` (`application/x-www-form-urlencoded`) ki shakal me rakhta hai aur cheezen **badalne** wale kaamon ke liye hai. Search, filters aur pagination ke liye GET; login, signup, checkout aur har private cheez ke liye POST. Passwords, SSNs ya tokens GET forms me kabhi nahi. Neeche ek chhota Python server bilkul wahi darj karta hai jo asli browser bhejta hai.</Ur>
</Tr>

```bash
python3 - <<'PY'
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from playwright.sync_api import sync_playwright

received = {}
class Recorder(BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers["Content-Length"])).decode()
        received.update(path=self.path, content_type=self.headers["Content-Type"], body=body)
        self.send_response(200); self.end_headers(); self.wfile.write(b"thanks")
    def do_GET(self):
        received.update(path=self.path)
        self.send_response(200); self.end_headers(); self.wfile.write(b"results")
    def log_message(self, *args):
        pass

server = HTTPServer(("127.0.0.1", 0), Recorder)
port = server.server_address[1]
threading.Thread(target=server.serve_forever, daemon=True).start()

page_html = f"""<!DOCTYPE html><title>Shop</title>
<form action="http://127.0.0.1:{port}/orders" method="post">
  <label for="n">Name</label> <input id="n" name="name" required>
  <label for="c">City</label>
  <select id="c" name="city"><option>Chicago</option><option>Houston</option></select>
  <button>Place order</button>
</form>
<form action="http://127.0.0.1:{port}/search" method="get">
  <input name="q" aria-label="Search"> <button>Search</button>
</form>"""

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(page_html)
    page.get_by_role("button", name="Place order").click()
    page.wait_for_timeout(300)
    print("1. empty required field -> request sent?", bool(received))
    page.fill("#n", "Sam Lee & Sons")
    page.select_option("#c", "Houston")
    page.get_by_role("button", name="Place order").click()
    page.wait_for_timeout(300)
    print("2. POST:", received)
    page.set_content(page_html)
    received.clear()
    page.get_by_label("Search").fill("keitt mango")
    page.get_by_role("button", name="Search").click()
    page.wait_for_timeout(300)
    print("3. GET :", received)
    browser.close()
server.shutdown()
PY
```

```text output
1. empty required field -> request sent? False
2. POST: {'path': '/orders', 'content_type': 'application/x-www-form-urlencoded', 'body': 'name=Sam+Lee+%26+Sons&city=Houston'}
3. GET : {'path': '/search?q=keitt+mango'}
```

<Happened>
<Tr>
<En>

- `Recorder` saves the path, `Content-Type` and body of each request, on a free port (`0` lets the OS choose). Playwright drives a real Chromium like a user.
- **1:** "Place order" with the required name empty sent **nothing**: the browser blocked it ("Please fill out this field.").
- **2:** The server got a POST to `/orders` with body `name=Sam+Lee+%26+Sons&city=Houston`: spaces became `+` and `&` became `%26` (URL encoding), so the `&` in the name can't be confused with the separator.
- **3:** GET put the data in the **URL**: `/search?q=keitt+mango`, which also lands in history and logs.
- The button had no `type`: inside a form, a `<button>` defaults to `submit`.

</En>
<Ur>

- `Recorder` har request ka path, `Content-Type` aur body ek khaali port par mehfooz karta hai (`0` OS ko chunne deta hai). Playwright asli Chromium ko user ki tarah chalata hai.
- **1:** Required name khaali chhor kar "Place order" ne **kuch nahi** bheja: browser ne rok diya ("Please fill out this field.").
- **2:** Server ko `/orders` par POST mila jis ki body `name=Sam+Lee+%26+Sons&city=Houston` thi: spaces `+` aur `&` `%26` ban gaye (URL encoding), taa ke naam ka `&` alag karne wale nishan se na ulajhe.
- **3:** GET ne data **URL** me rakha: `/search?q=keitt+mango`, jo history aur logs me bhi jata hai.
- Button ka `type` nahi tha: form ke andar `<button>` default me `submit` hota hai.

</Ur>
</Tr>
</Happened>

<Step title="Labels: placeholders are not labels">

<Tr>
<En>`<label for="id">` connects visible text to the control with that `id` (or wrap it: `<label>Email <input name="email"></label>`), and becomes its **accessible name**. Screen readers announce it on focus, clicking it focuses the field (a bigger touch target for checkboxes), and voice users can say "click Email". Placeholders vanish when you type, have low contrast and aren't reliably read as labels. Label every control; if a design has no visible label, use `aria-label` as a fallback, and keep every `id` unique. Below, a real browser shows the names it computes.</En>
<Ur>`<label for="id">` nazar aane wale text ko us `id` wale control se jorta hai (ya use lapeto: `<label>Email <input name="email"></label>`), aur us ka **accessible name** banta hai. Screen readers focus par ise bolte hain, is par click field par focus deta hai (checkboxes ke liye bara touch target), aur awaz se chalane wale "click Email" keh sakte hain. Placeholders type karte hi ghayab, kam contrast wale, aur label ki tarah bharose se nahi parhe jate. Har control par label lagayen; design me nazar aane wala label na ho to bator fallback `aria-label`, aur har `id` munfarid rakhein. Neeche asli browser apne nikale naam dikhata hai.</Ur>
</Tr>

```bash

  <input name="coupon" placeholder="Coupon code">
  <select name="city"><option>Chicago</option><option>Houston</option></select>

- textbox "Email"
- checkbox "I accept the terms"

Always label selects.</En>
<Ur>`textbox "Email"`: `for`/`id` label naam ban gaya. `checkbox "I accept the terms"`: lapetna bhi chalta hai aur poora jumla clickable banata hai. `textbox "Coupon code"`: label na hone par browser ne placeholder liya, jo user ke type karte hi ghayab ho jata hai. **Bina naam** `combobox`: screen-reader user sirf "combo box, Chicago" sunta hai, pata nahi kya chun raha hai. Selects par hamesha label.</Ur>

<Step title="Input types">

<Tr>
<En>`type` changes an `<input>`'s behaviour, built-in validation and mobile keyboard: `email` gives an @-keyboard and a format check, `tel` a phone keypad, `number` spinners and numeric checks, `date` a native picker, `password` hidden characters plus password-manager help. Use `type="number"` only for real quantities (age, boxes). For phone numbers, SSNs, card numbers and OTPs use `type="text"` (or `tel`) with `inputmode="numeric"`: they aren't numbers you do maths with, and `number` drops leading zeros. Unknown types fall back to `text`, so they're safe.</En>
<Ur>`type` `<input>` ka rawaiya, andaruni validation aur mobile keyboard badalta hai: `email` @-keyboard aur format check, `tel` phone keypad, `number` spinners aur numeric checks, `date` asli picker, `password` chhupe characters aur password-manager ki madad. `type="number"` sirf asli miqdaar (umar, dabbe) ke liye. Phone numbers, SSNs, card numbers aur OTPs ke liye `inputmode="numeric"` ke saath `type="text"` (ya `tel`): ye aise numbers nahi jin ka hisaab karein, aur `number` shuru ke zero gira deta hai. Na-maloom types `text` ban jati hain, isliye mehfooz hain.</Ur>
</Tr>

<Step title="Checkboxes, radio buttons, select and textarea">

<Tr>
<En>**Checkboxes**: independent yes/no choices. **Radio buttons**: exactly one from a group (same `name`). **`<select>`**: a dropdown. **`<textarea>`**: multi-line text. The right control prevents invalid combinations: radios can't produce two delivery speeds. Radios for 2–5 visible options, select for longer lists. Group related ones in a `<fieldset>` with a `<legend>`. Unchecked checkboxes send **nothing**, not "false". Each option's `value` is what gets sent; `checked` and `selected` set defaults.</En>
<Ur>**Checkboxes**: azad haan/nahi intikhab. **Radio buttons**: group me se bilkul ek (wahi `name`). **`<select>`**: dropdown. **`<textarea>`**: kai lines ka text. Sahi control ghalat jore rokta hai: radios do delivery speeds nahi bana sakte. 2–5 nazar aane wale options ke liye radios, lambi lists ke liye select. Mutalliq controls ko `<legend>` wale `<fieldset>` me rakhein. Bina tick checkboxes **kuch nahi** bhejte, "false" bhi nahi. Har option ki `value` hi jati hai; `checked` aur `selected` default set karte hain.</Ur>
</Tr>

<Tr>

</En>

<Step title="Built-in validation">

<Tr>
<En>Attributes set rules the browser checks before submitting: `required`, `type`, `pattern` (a regular expression), `min`/`max`/`step`, `minlength`/`maxlength`. You get instant feedback with no JavaScript, in the user's language, with correct accessibility. The browser shows a bubble and focuses the first invalid field; CSS can style `:invalid`/`:user-invalid`; JavaScript can read `input.validity` and `validationMessage`; `novalidate` turns the checks off when JS shows its own. `pattern` must match the **whole** value, so explain the format with visible help text.</En>
<Ur>Attributes wo qawaid set karte hain jo browser submit se pehle check karta hai: `required`, `type`, `pattern` (regular expression), `min`/`max`/`step`, `minlength`/`maxlength`. Bina JavaScript fauran feedback, user ki zaban me, sahi rasai ke saath. Browser bubble dikhata hai aur pehle ghalat field par focus deta hai; CSS `:invalid`/`:user-invalid` style kar sakta hai; JavaScript `input.validity` aur `validationMessage` parh sakti hai; jab JS apne paigham dikhaye to `novalidate` checks band karta hai. `pattern` **poori** value se milna chahiye, isliye format nazar aane wale help text se samjhayen.</Ur>
</Tr>

<Step title="Buttons in forms">

<Tr>
<En>`<button type="submit">` submits (the default in a form), `type="reset"` clears the form (rarely a good idea), and `type="button"` does nothing by default (for JavaScript). Prefer `<button>` over `<input type="submit">`: it can contain icons and formatted text.</En>
<Ur>`<button type="submit">` submit karta hai (form me default), `type="reset"` form saaf karta hai (kam hi achha khayal), aur `type="button"` default me kuch nahi karta (JavaScript ke liye). <Step title="File uploads">

<Tr>
<En>`<input type="file">` lets users choose files. The form needs `method="post"` and `enctype="multipart/form-data"`, which sends each field and file as a separate body part; without it, only the file **name** is sent. `accept` filters the picker (`image/*`, `.pdf`), `multiple` allows several files and `capture` opens the phone camera. `accept` is only a **hint**: users and attackers can send any file, so the server must check type, size and content.</En>
<Ur>`<input type="file">` users ko files chunne deta hai. Form ko `method="post"` aur `enctype="multipart/form-data"` chahiye, jo har field aur file body ke alag hisse me bhejta hai; is ke baghair sirf file ka **naam** jata hai. `accept` picker filter karta hai (`image/*`, `.pdf`), `multiple` kai files deta hai aur `capture` phone camera kholta hai. `accept` sirf **ishara** hai: users aur hamla awar koi bhi file bhej sakte hain, isliye server ko type, size aur mawad check karna lazmi hai.</Ur>
</Tr>

<Ur>Files ke liye `enctype="multipart/form-data"` aur `method="post"` lazmi hain. `accept=".pdf,application/pdf"` picker me PDFs dikhata hai; label me "max 2 MB" users ko wo hadd batata hai jo server ko lagani hai. `multiple` kai tasveeren chunne deta hai, jo dohraye `photos` hisson me jati hain.</Ur>

<Step title="Accessible, user-friendly forms">

<Tr>
<En>

Good forms are short, clearly labelled, explain formats **before** errors happen, keep the user's input after errors, and announce problems to everyone:

- Help text linked with `aria-describedby`, read together with the label.
- Required fields marked visibly and with `required`.
- Errors next to the field, in text, linked with `aria-describedby`, field marked `aria-invalid="true"`; never colour alone.
- Logical tab order (avoid positive `tabindex`); don't disable paste.

Below: help text and an error connected to the input, as a server-rendered form shows errors after submission.

</En>
<Ur>

Achhe forms chhote, saaf label wale hote hain, errors se **pehle** format samjhate hain, errors ke baad user ka input rakhte hain, aur masle sab ko batate hain:

- `aria-describedby` se jura help text, label ke saath parha jata hai.
- Required fields nazar aane wale nishan aur `required` dono se.
- Errors field ke saath, text me, `aria-describedby` se jure, field par `aria-invalid="true"`; sirf rang kabhi nahi.
- Mantiqi tab tarteeb (positive `tabindex` se bachen); paste band na karein.

Neeche: input se jura help text aur error, jaise server-rendered form submit ke baad errors dikhata hai.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Looks fine, fails everyone">

```text
<form action="/login">                         <!-- GET: password ends up in the URL -->
  <input placeholder="Email">                  <!-- no label, no name -->
  <input type="number" placeholder="Phone">    <!-- drops leading zeros -->
  <input type="password" name="password">
  <button onclick="togglePw()">Show</button>   <!-- submits the form -->
  <button>Log in</button>
</form>
```

</Bad>
<Good title="Labelled, typed, POSTed">

```text
<form action="/login" method="post">
  <label for="email">Email</label>
  <input id="email" name="email" type="email" autocomplete="email" required>
  <label for="pw">Password</label>
  <input id="pw" name="password" type="password" autocomplete="current-password" required>
  <button type="button" onclick="togglePw()">Show</button>
  <button type="submit">Log in</button>
</form>
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Labels not connected** (`for` doesn't match the `id`).
- **File uploads without `enctype="multipart/form-data"`.**
- **Errors shown only by colour**, at the top of the page, or clearing the user's input.
- **Disabling paste**, or making users retype emails and passwords.
- **Relying only on client-side validation.**
- **`<input type="hidden">` for secrets or prices**: hidden fields are in the source and editable.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Na jure labels** (`for` `id` se nahi milta).
- **`enctype="multipart/form-data"` ke baghair file uploads.**
- **Sirf rang se errors**, page ke upar, ya user ka input mita dena.
- **Paste band karna**, ya users se emails aur passwords dobara likhwana.
- **Sirf client-side validation par bharosa.**
- **Raazon ya qeematon ke liye `<input type="hidden">`**: hidden fields source me hain aur badle ja sakte hain.

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- GET for searches and filters; POST for changes and private data.
- Every control gets a connected `<label>`; placeholders are hints.
- Choose specific `type`s and `autocomplete` values; `tel`/`text` + `inputmode` for codes.
- Radios share a `name`; group with `fieldset`/`legend`; empty first select option + `required`.

- `type="button"` for non-submit buttons; `multipart/form-data` for files.
- Errors in text, next to the field, linked with `aria-describedby`; keep input.
- The server validates everything again.

</En>

<DeepDive title="Real world: the checkout half of mobile users abandoned">

An online store in Houston found that 40% of mobile users abandoned checkout. Session recordings showed why: the phone field was `type="number"` (it dropped leading zeros, so numbers failed server checks), labels were placeholders that vanished while typing, the city was free text (typos broke delivery-zone lookups), errors appeared only as a red border at the top, and every server error **cleared the whole form**. The fixes were plain HTML: real labels, `type="tel"` with a `pattern` and help text, a `<select>` of supported cities, `autocomplete` attributes (phones filled name, email and address in one tap), errors next to fields linked with `aria-describedby`, and keeping submitted values on error. Mobile completion rose noticeably. The server kept its own validation for every field, because bots had also been posting orders directly to the endpoint, skipping the form entirely.

</DeepDive>

<DeepDive title="Security lens">

Everything the browser enforces, an attacker can bypass: edit the HTML in DevTools, or skip the browser and send any request with curl or Burp Suite. HTML validation is for user experience; the server is the security boundary.

- **Validate on the server:** types, lengths, formats, allowed values (is `variety` really one of your products?) and business rules (is the price from your database?).
- **Never trust hidden or disabled fields:** a hidden `price` or `role` can be changed. Look up prices and permissions on the server (avoid **mass assignment**).
- **CSRF:** a malicious site can make a victim's browser POST to your site with their cookies. Use CSRF tokens and `SameSite` cookies.
- **Injection and XSS:** treat every value as untrusted; use parameterised SQL and escape on output.
- **File uploads:** size limits, real content-type checks (not just the extension), rename files, store outside the web root or in object storage, scan if possible, never execute.
- **Sensitive fields:** POST over HTTPS only; never log passwords or card data.
- **Bots:** rate-limit form endpoints; use honeypots or accessible CAPTCHAs for public forms.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between GET and POST for forms?">
GET sends the form data in the URL query string, which is visible, bookmarkable and cached but also stored in history and logs, so it suits searches and filters that do not change data. POST sends data in the request body and is used for actions that create or change data or carry sensitive information. Neither is secure without HTTPS.
</QA>

<QA q="Why is a placeholder not a substitute for a label?">
A placeholder disappears when the user types, often has low contrast, is not reliably exposed as the accessible name, and cannot be clicked to focus the field. A visible label connected with for and id, or by wrapping the input, gives the control a persistent, accessible name and a larger click target.
</QA>

<QA q="What does the name attribute do on form controls?">
It is the key under which the control's value is submitted. Controls without a name are not included in the submitted data, radio buttons with the same name form a group where only one can be selected, and checkboxes with the same name submit multiple values.
</QA>

<QA q="Is HTML5 form validation enough to secure an application?">
No. It improves usability by giving instant feedback, but users can disable it, edit the HTML, or send requests directly without a browser. All input must be validated and authorised on the server, including hidden fields, select values and uploaded files.
</QA>

<QA q="What is needed to upload a file with an HTML form?">
An input of type file with a name, a form with method post and enctype multipart/form-data. The accept attribute can filter the file picker and multiple allows several files, but the server must validate file size, type and content and store uploads safely.
</QA>

<DeepDive title="More practice">

1. Build a contact form (name, email, subject select, message) that POSTs, and check the request in DevTools → Network → Payload.
2. Create a search form with GET and confirm the query appears in the URL.
3. Add `pattern` validation for a US ZIP code (`[0-9]{5}`) and a license plate, with visible format help.
4. Test your form using only the keyboard (Tab, Shift+Tab, Space, Enter, arrow keys for radios).
5. Edit a form in DevTools (remove `required`, change a select's option value), submit it, and explain what the server must check.
6. Run axe DevTools or Lighthouse on your form and fix every labelling problem.
