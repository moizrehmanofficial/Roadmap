<Callout type="tip" title="In one minute">
A **form** collects input and sends it to a server. The `<form>` element says **where** (`action`) and **how** (`method="get"` or `"post"`); each control (`<input>`, `<select>`, `<textarea>`) needs a **`name`**, because the browser sends `name=value` pairs. Every control needs a visible **`<label>`** connected with `for`/`id`: a placeholder is **not** a label. Choose the right **`type`** (`email`, `tel`, `number`, `date`, `password`, `checkbox`, `radio`, `file`…) to get the right mobile keyboard and free **validation** (`required`, `pattern`, `min`/`max`, `minlength`/`maxlength`). The browser blocks submission until the fields are valid. Use **GET** for searches and filters (data in the URL) and **POST** for anything that changes data or contains private information. Client-side validation only helps users: an attacker can skip it entirely, so the **server must validate everything** again.
</Callout>

## Start from zero

<Callout type="analogy">
A web form is like a **paper application form at a bank counter**. Each box has a **printed label** ("Full name", "CNIC number") so you know what to write; the boxes have **rules** ("13 digits", "date of birth"); you hand it over at a specific **counter** (the server's address, `action`); and the clerk **checks everything again** before accepting it, even if you were careful. HTML gives you the boxes, labels and rules; the browser checks the rules before handing it over; the server is the clerk who must double-check, because some people forge forms.
</Callout>

### Words you need first

| Word | Simple meaning | Example |
| --- | --- | --- |
| **Form** | A group of controls submitted together | `<form action="/orders" method="post">` |
| **Control** | An input element the user fills or chooses | `<input>`, `<select>`, `<textarea>` |
| **`name`** | The key the value is sent under | `name="email"` |
| **`action`** | The URL that receives the data | `/orders` |
| **`method`** | How data is sent: GET (in the URL) or POST (in the body) | `method="post"` |
| **Label** | The visible text describing a control | `<label for="email">Email</label>` |
| **Validation** | Checking values follow rules | `required`, `type="email"` |
| **Constraint Validation API** | The browser's built-in validation system | `input.validity.valid` |
| **Enctype** | How POST data is encoded | `multipart/form-data` for files |
| **Autocomplete** | Browser autofill hints | `autocomplete="email"` |

## What is it?

```text
 user fills the form ──► browser checks rules (required, type, pattern...) ──► sends name=value pairs
                              │ invalid: shows a message, nothing is sent        │
                                                                                 ▼
 server (action URL) ◄──────────── GET: /search?q=mango        POST: body name=Ali&city=Lahore
    │
    └──► server validates AGAIN, saves, responds (new page, redirect, or JSON for JS forms)
```

Forms work **without any JavaScript**: the browser itself validates, encodes and sends the data. JavaScript (React, fetch) can take over later, but the HTML foundation stays the same.

## Why does it matter?

- **Forms are how users do things:** sign up, log in, search, check out, contact, upload, apply. They're the point where users turn into customers.
- **Bad forms cost money:** confusing labels, wrong keyboards on phones, unclear errors and lost input are top reasons people abandon checkouts.
- **Accessibility:** unlabelled fields are one of the most common accessibility failures; screen-reader users can't know what to type.
- **Security:** forms are the main entry point for attacks (SQL injection, XSS, CSRF, mass assignment). Knowing what browsers send, and what attackers can send instead, is essential for full-stack and security work.

## When and where do you use it?

- **Plain HTML forms:** contact forms, search boxes, login pages, server-rendered apps (Django, Laravel, Rails, Express + templates).
- **In React/Next.js:** you still render `<form>`, `<label>` and `<input>` elements; Next.js Server Actions even use the native `<form action>` again.
- **Everywhere:** the same HTML controls power admin panels, checkout pages and internal tools.

## Concepts one by one

### 1. A minimal form

<Explain>
<What>
`<form>` wraps the controls. `action` is where the data goes, `method` is how. Each control has a `name`; a submit `<button>` sends it.
</What>
<Why>
Without `name`, a control's value isn't sent at all, which is a very common beginner bug.
</Why>
<When>
Every form.
</When>
<Where>
If `action` is missing, the form submits to the current page's URL; if `method` is missing, it's `get`.
</Where>
<How>
Pressing **Enter** in a text field submits the form too, for free.
</How>
</Explain>

```html preview h=150
<form action="/search" method="get" role="search">
  <label for="q">Search products</label>
  <input id="q" name="q" type="search" placeholder="e.g. chaunsa">
  <button type="submit">Search</button>
</form>
```

Line by line:

- `action="/search" method="get"`: submitting sends the browser to `/search?q=whatever-was-typed`.
- `role="search"` marks this form as the site's search landmark for assistive technology.
- `<label for="q">` is connected to the input with `id="q"`: clicking the label focuses the field, and screen readers announce "Search products, search field".
- `name="q"` is the key in the URL. `type="search"` gives a search keyboard on phones and a clear (×) button in some browsers.
- `placeholder` shows an example. It's a hint, not a label (concept 3).
- (In this preview, submitting tries to load `/search` inside the small frame. That's expected; there's no server behind it.)

### 2. GET vs POST: what the server actually receives

<Explain>
<What>
**GET** puts the data in the URL's **query string** (`/search?q=chaunsa+mango`). **POST** puts it in the request **body**, encoded as `name=value&name=value` (`application/x-www-form-urlencoded`) by default.
</What>
<Why>
GET URLs are visible, bookmarkable and shareable, but they're also saved in browser history, server logs and analytics. POST data isn't in the URL, and POST is meant for actions that **change** things (create an order, change a password).
</Why>
<When>
GET: search, filters, sorting, pagination. POST: login, signup, checkout, contact forms, anything private or state-changing.
</When>
<Where>
Never put passwords, CNICs or tokens in GET forms; they leak into logs and Referer headers.
</Where>
<How>
Below, a tiny Python server records exactly what a real browser sends when the forms are submitted.
</How>
</Explain>

```bash
python3 - <<'PY'
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from playwright.sync_api import sync_playwright

received = {}
class Recorder(BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers["Content-Length"])).decode()
        received.update(path=self.path, content_type=self.headers["Content-Type"], body=body)
        self.send_response(200); self.end_headers(); self.wfile.write(b"thanks")
    def do_GET(self):
        received.update(path=self.path)
        self.send_response(200); self.end_headers(); self.wfile.write(b"results")
    def log_message(self, *args):
        pass

server = HTTPServer(("127.0.0.1", 0), Recorder)
port = server.server_address[1]
threading.Thread(target=server.serve_forever, daemon=True).start()

page_html = f"""<!DOCTYPE html><title>Shop</title>
<form action="http://127.0.0.1:{port}/orders" method="post">
  <label for="n">Name</label> <input id="n" name="name" required>
  <label for="c">City</label>
  <select id="c" name="city"><option>Lahore</option><option>Karachi</option></select>
  <button>Place order</button>
</form>
<form action="http://127.0.0.1:{port}/search" method="get">
  <input name="q" aria-label="Search"> <button>Search</button>
</form>"""

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content(page_html)
    page.get_by_role("button", name="Place order").click()
    page.wait_for_timeout(300)
    print("1. empty required field -> request sent?", bool(received))
    page.fill("#n", "Ali Raza & Sons")
    page.select_option("#c", "Karachi")
    page.get_by_role("button", name="Place order").click()
    page.wait_for_timeout(300)
    print("2. POST:", received)
    page.set_content(page_html)
    received.clear()
    page.get_by_label("Search").fill("chaunsa mango")
    page.get_by_role("button", name="Search").click()
    page.wait_for_timeout(300)
    print("3. GET :", received)
    browser.close()
server.shutdown()
PY
```

```text output
1. empty required field -> request sent? False
2. POST: {'path': '/orders', 'content_type': 'application/x-www-form-urlencoded', 'body': 'name=Ali+Raza+%26+Sons&city=Karachi'}
3. GET : {'path': '/search?q=chaunsa+mango'}
```

Line by line:

- `Recorder` is a mini web server that saves the path, the `Content-Type` header and the body of each request it receives. It listens on a free port (`0` lets the OS choose).
- The page has an order form (POST) and a search form (GET), both pointing at the recorder. Playwright drives a real Chromium browser, like a user.
- **1:** Clicking "Place order" with the required name empty sends **nothing**: the browser blocks it and shows "Please fill out this field." (concept 6).
- **2:** After filling the form, the server receives a POST to `/orders` with `Content-Type: application/x-www-form-urlencoded` and the body `name=Ali+Raza+%26+Sons&city=Karachi`. Spaces became `+` and `&` became `%26`: URL encoding, so the `&` inside the name can't be confused with the separator (see **Base64, Hex and Encoding vs Encryption**).
- **3:** The GET form puts the data in the **URL**: `/search?q=chaunsa+mango`. That URL can be bookmarked or shared, and it will also appear in history and server logs.
- Note the button has no `type`: inside a form, a `<button>` defaults to `type="submit"`.

### 3. Labels: placeholders are not labels

<Explain>
<What>
`<label for="id">` connects visible text to a control with that `id` (or wrap the control: `<label>Email <input name="email"></label>`). The label becomes the control's **accessible name**.
</What>
<Why>
Screen readers announce the label when the field is focused; clicking the label focuses the field (a bigger touch target, especially for checkboxes); voice-control users say "click Email". Placeholders vanish when you start typing, have low contrast, and aren't reliably read as labels.
</Why>
<When>
Every control, always. If a design has no visible label (a search box with an icon), use `aria-label` as a fallback.
</When>
<Where>
Each `id` must be unique on the page, or the label connects to the wrong control.
</Where>
<How>
Below, a real browser shows the accessible names it computes. A field with only a placeholder ends up named by the placeholder, and a select with no label gets **no name at all**.
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
form = """<form>
  <label for="email">Email</label> <input id="email" name="email" type="email">
  <label><input type="checkbox" name="terms"> I accept the terms</label>
  <input name="coupon" placeholder="Coupon code">
  <select name="city"><option>Lahore</option><option>Karachi</option></select>
</form>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title>" + form)
    print(page.locator("form").aria_snapshot())
    browser.close()
PY
```

```text output
- text: Email
- textbox "Email"
- checkbox "I accept the terms"
- text: I accept the terms
- textbox "Coupon code"
- combobox:
  - option "Lahore" [selected]
  - option "Karachi"
```

Line by line:

- `textbox "Email"`: the `for`/`id` label became the field's name.
- `checkbox "I accept the terms"`: wrapping the checkbox in the `<label>` works too, and makes the whole sentence clickable.
- `textbox "Coupon code"`: with no label, the browser falls back to the placeholder. It "works" until the user starts typing and the hint disappears, and many tools don't treat it as a proper label.
- `combobox` with **no name**: a screen-reader user hears only "combo box, Lahore" without knowing what they're choosing. Always label selects.

### 4. Input types

<Explain>
<What>
The `type` attribute changes an `<input>`'s behaviour, built-in validation and mobile keyboard.
</What>
<Why>
`type="email"` gives an @-keyboard and checks the format; `type="tel"` a phone keypad; `type="number"` spinner controls and numeric checks; `type="date"` a native date picker; `type="password"` hides characters and lets password managers help.
</Why>
<When>
Pick the most specific type for the data.
</When>
<Where>
Use `type="number"` only for real quantities (age, boxes). For phone numbers, CNICs, card numbers and OTPs, use `type="text"` (or `tel`) with `inputmode="numeric"`, because those aren't numbers you do maths with, and `number` drops leading zeros and adds scroll-to-change behaviour.
</Where>
<How>
Unknown or unsupported types fall back to `text`, so they're safe to use.
</How>
</Explain>

```html preview h=560
<form>
  <p><label for="t-name">Full name</label><br>
     <input id="t-name" name="name" type="text" autocomplete="name"></p>
  <p><label for="t-email">Email</label><br>
     <input id="t-email" name="email" type="email" autocomplete="email"></p>
  <p><label for="t-phone">Mobile</label><br>
     <input id="t-phone" name="phone" type="tel" autocomplete="tel" placeholder="0300-1234567"></p>
  <p><label for="t-pass">Password</label><br>
     <input id="t-pass" name="password" type="password" autocomplete="new-password"></p>
  <p><label for="t-qty">Boxes (1–10)</label><br>
     <input id="t-qty" name="qty" type="number" min="1" max="10" value="1"></p>
  <p><label for="t-date">Delivery date</label><br>
     <input id="t-date" name="date" type="date" min="2026-11-11"></p>
  <p><label for="t-otp">OTP code</label><br>
     <input id="t-otp" name="otp" type="text" inputmode="numeric" autocomplete="one-time-code" maxlength="6"></p>
  <p><label for="t-color">Wrapping colour</label>
     <input id="t-color" name="color" type="color" value="#f4b400"></p>
  <p><label for="t-range">Ripeness</label>
     <input id="t-range" name="ripeness" type="range" min="1" max="5" value="3"></p>
  <button type="submit">Save</button>
</form>
```

| Type | Gives you | Use for |
| --- | --- | --- |
| `text` | Plain text | Names, addresses |
| `email` | @ keyboard, email format check | Email addresses |
| `tel` | Phone keypad (no format check) | Phone numbers |
| `password` | Hidden characters, password managers | Passwords |
| `number` | Number keyboard, min/max/step checks | Quantities, ages |
| `date` / `time` / `datetime-local` | Native pickers | Bookings, deliveries |
| `search` | Search keyboard, clear button | Search boxes |
| `url` | URL keyboard, format check | Websites |
| `checkbox` / `radio` | Choices (concept 5) | Options |
| `file` | File chooser (concept 8) | Uploads |
| `color` / `range` | Colour picker / slider | Settings |
| `hidden` | Not shown, still submitted | IDs, CSRF tokens (not secrets!) |

Line by line:

- Each field has a label and the most fitting type; `autocomplete` values (`name`, `email`, `tel`, `new-password`, `one-time-code`) let browsers and password managers fill them correctly, and let phones offer the SMS code automatically.
- `min="2026-11-11"` on the date picker prevents choosing earlier dates in the picker.
- The OTP uses `type="text"` with `inputmode="numeric"`: numeric keypad, but leading zeros are kept.
- Open the result on your phone (or DevTools' device mode) to see the different keyboards.

### 5. Checkboxes, radio buttons, select and textarea

<Explain>
<What>
**Checkboxes**: independent yes/no choices (zero or more). **Radio buttons**: exactly one choice from a group (same `name`). **`<select>`**: a dropdown of options. **`<textarea>`**: multi-line text.
</What>
<Why>
The right control prevents invalid combinations: radio buttons can't produce two delivery speeds; a select can't produce a city you don't deliver to.
</Why>
<When>
Radio for 2–5 visible options; select for longer lists; checkbox for independent options or a single agreement; textarea for messages and addresses.
</When>
<Where>
Group related radios and checkboxes in a `<fieldset>` with a `<legend>` (the group's label). Unchecked checkboxes send **nothing**, not "false".
</Where>
<How>
Each radio/checkbox has its own `value`, which is what gets sent. `checked` and `selected` set defaults.
</How>
</Explain>

```html preview h=440 noqa
<form>
  <fieldset>
    <legend>Delivery speed</legend>
    <label><input type="radio" name="speed" value="standard" checked> Standard (free)</label><br>
    <label><input type="radio" name="speed" value="express"> Express (Rs 250)</label>
  </fieldset>

  <fieldset>
    <legend>Extras</legend>
    <label><input type="checkbox" name="extras" value="gift"> Gift wrap</label><br>
    <label><input type="checkbox" name="extras" value="card"> Greeting card</label>
  </fieldset>

  <p>
    <label for="city">City</label>
    <select id="city" name="city" required>
      <option value="">Choose a city…</option>
      <optgroup label="Punjab">
        <option value="lhr">Lahore</option>
        <option value="rwp">Rawalpindi</option>
      </optgroup>
      <optgroup label="Islamabad Capital Territory">
        <option value="isb">Islamabad</option>
      </optgroup>
    </select>
  </p>

  <p>
    <label for="notes">Delivery notes</label><br>
    <textarea id="notes" name="notes" rows="3" cols="40" maxlength="300"></textarea>
  </p>
  <button type="submit">Continue</button>
</form>
```

Line by line:

- Both radios share `name="speed"`, so selecting one deselects the other; `checked` makes Standard the default. Only the chosen `value` is sent: `speed=standard`.
- Checkboxes with the same `name="extras"` can both be ticked, sending `extras=gift&extras=card`, or nothing if neither is ticked.
- `<fieldset>`/`<legend>` group each set; screen readers announce "Delivery speed, group" before the options.
- The select's first option has an **empty value**, so combined with `required` the user must actively choose a city. `<optgroup>` groups options under provinces. The `value` (`lhr`) is sent, while the text (`Lahore`) is shown.
- `<textarea>` has `rows`/`cols` for its initial size and `maxlength="300"` to cap the length. Its default text goes **between** the tags, not in a `value` attribute.

### 6. Built-in validation

<Explain>
<What>
Attributes that set rules the browser checks before submitting: `required`, `type` (email/url/number…), `pattern` (a regular expression), `min`/`max`/`step`, `minlength`/`maxlength`.
</What>
<Why>
Instant feedback with no JavaScript, in the user's own language, with correct accessibility.
</Why>
<When>
Every form, as the first layer.
</When>
<Where>
The browser shows a message bubble and focuses the first invalid field. CSS can style `:invalid`, `:user-invalid` and `:valid` states, and JavaScript can read `input.validity` and `input.validationMessage` (the Constraint Validation API). `novalidate` on the form turns the browser checks off (for example, when JavaScript shows its own messages).
</Where>
<How>
`pattern` must match the **whole** value (it's anchored automatically). Use `title` or visible help text to explain the expected format.
</How>
</Explain>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
form = """<form id="order">
  <label for="name">Full name</label>  <input id="name" name="name" required minlength="3">
  <label for="email">Email</label>     <input id="email" name="email" type="email" required>
  <label for="phone">Mobile</label>    <input id="phone" name="phone" type="tel" pattern="03[0-9]{2}-[0-9]{7}">
  <label for="qty">Boxes</label>       <input id="qty" name="qty" type="number" min="1" max="10">
</form>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title>" + form)
    for field, value in [("name", ""), ("name", "Al"), ("email", "ali@"), ("phone", "0300 1234567"), ("qty", "15")]:
        page.fill(f"#{field}", value)
        valid = page.evaluate(f"document.getElementById('{field}').validity.valid")
        message = page.evaluate(f"document.getElementById('{field}').validationMessage")
        print(f"{field:5} {value!r:16} valid={valid!s:5} {message}")
    for field, value in [("name", "Ayesha Khan"), ("email", "ayesha@example.com"), ("phone", "0300-1234567"), ("qty", "2")]:
        page.fill(f"#{field}", value)
    print("whole form valid:", page.evaluate("document.getElementById('order').checkValidity()"))
    browser.close()
PY
```

```text output
name  ''               valid=False Please fill out this field.
name  'Al'             valid=False Please lengthen this text to 3 characters or more (you are currently using 2 characters).
email 'ali@'           valid=False Please enter a part following '@'. 'ali@' is incomplete.
phone '0300 1234567'   valid=False Please match the requested format.
qty   '15'             valid=False Value must be less than or equal to 10.
whole form valid: True
```

Line by line:

- Each test fills one field and asks the browser for `validity.valid` and the `validationMessage` it would show (Chrome's English messages; other browsers and languages word them differently).
- `required` rejects an empty name; `minlength="3"` rejects "Al" with a message that even counts the characters.
- `type="email"` rejects `ali@`, explaining what's missing.
- The `pattern` `03[0-9]{2}-[0-9]{7}` requires the format `0300-1234567`; a space instead of a dash fails. (See **Regular Expressions** for writing patterns.)
- `max="10"` rejects 15 boxes.
- After entering valid values, `form.checkValidity()` returns `true`, so the form may submit.

### 7. Buttons in forms

<Explain>
<What>
`<button type="submit">` submits (the default inside a form), `<button type="reset">` clears the form (rarely a good idea), `<button type="button">` does nothing by default (for JavaScript actions).
</What>
<Why>
Forgetting `type="button"` on, say, a "Show password" button makes it **submit the form** when clicked.
</Why>
<When>
Every button inside a form.
</When>
<Where>
Buttons can override the form's settings: `formaction`, `formmethod` and `formnovalidate` (useful for "Save draft" next to "Publish").
</Where>
<How>
Prefer `<button>` over `<input type="submit">`, because a button can contain icons and formatted text.
</How>
</Explain>

```html preview-js h=170
<form onsubmit="event.preventDefault(); document.getElementById('log').textContent = 'Form submitted!'">
  <label for="pw">Password</label>
  <input id="pw" name="password" type="password" value="mango123" required>
  <button type="button" onclick="pw.type = pw.type === 'password' ? 'text' : 'password'">Show/hide</button>
  <button type="submit">Log in</button>
  <p id="log" role="status"></p>
</form>
```

Line by line:

- `onsubmit="event.preventDefault(); ..."` stops the real submission for this demo and writes a message instead.
- "Show/hide" has `type="button"`, so it only toggles the input between `password` and `text` types, and the form isn't submitted. Remove `type="button"` and it would submit.
- "Log in" is the submit button. Pressing Enter in the password field also triggers it.
- `role="status"` makes screen readers announce the message when it appears.

### 8. File uploads

<Explain>
<What>
`<input type="file">` lets users choose files. The form must use `method="post"` and `enctype="multipart/form-data"`, which sends each field and file as a separate part of the body.
</What>
<Why>
The default URL-encoded format can't carry binary files; without the right `enctype`, only the file **name** is sent.
</Why>
<When>
Profile photos, CVs, documents, CSV imports.
</When>
<Where>
`accept` filters the file chooser (`accept="image/*"`, `accept=".pdf"`), `multiple` allows several files, and `capture` opens the camera on phones.
</Where>
<How>
`accept` is only a **hint** for the file picker; users (and attackers) can still send any file. The server must check type, size and content (Security lens).
</How>
</Explain>

```html preview h=170
<form action="/applications" method="post" enctype="multipart/form-data">
  <p><label for="cv">Upload your CV (PDF, max 2 MB)</label><br>
     <input id="cv" name="cv" type="file" accept=".pdf,application/pdf" required></p>
  <p><label for="photos">Photos of the damaged mangoes</label><br>
     <input id="photos" name="photos" type="file" accept="image/*" multiple></p>
  <button type="submit">Send</button>
</form>
```

Line by line:

- `enctype="multipart/form-data"` is required for files; `method="post"` too.
- `accept=".pdf,application/pdf"` makes the file picker show PDFs by default; "max 2 MB" in the label tells users the limit, which the server must enforce.
- `multiple` lets users pick several photos at once; they're sent as repeated `photos` parts.

### 9. Accessible, user-friendly forms

<Explain>
<What>
Good forms are short, clearly labelled, explain formats **before** errors happen, keep the user's input after errors, and announce problems to everyone.
</What>
<Why>
Every extra or confusing field reduces completion; inaccessible forms exclude users entirely.
</Why>
<When>
Every form you design.
</When>
<Where>
- Help text connected with `aria-describedby`, so screen readers read it with the label.
- Mark required fields visibly (and with `required`).
- Error messages next to the field, in text, connected with `aria-describedby`, and the field marked `aria-invalid="true"`; never colour alone.
- Logical tab order (follow the visual order; avoid positive `tabindex`).
- Don't disable paste in password or email-confirmation fields.
</Where>
<How>
Below: help text and an error message connected to the input, the way a server-rendered form shows errors after submission.
</How>
</Explain>

```html preview h=170
<form>
  <label for="cnic">CNIC number <span aria-hidden="true">*</span></label><br>
  <input id="cnic" name="cnic" type="text" required inputmode="numeric" autocomplete="off"
         pattern="[0-9]{5}-[0-9]{7}-[0-9]" aria-describedby="cnic-help cnic-error" aria-invalid="true"
         value="35202-123456">
  <p id="cnic-help"><small>Format: 12345-1234567-1</small></p>
  <p id="cnic-error" role="alert"><strong>Error:</strong> the CNIC must have 13 digits in the format shown.</p>
  <button type="submit">Verify</button>
</form>
```

Line by line:

- The visible asterisk is hidden from screen readers (`aria-hidden="true"`), because `required` already makes them say "required".
- `aria-describedby="cnic-help cnic-error"` links two descriptions, which screen readers read after the label: the format help and the error.
- `aria-invalid="true"` marks the field as having an error; the error text (not just a red border) explains what's wrong; `role="alert"` announces it immediately.
- The user's value is kept in the field (`value="..."`), so they correct it instead of retyping.

- Two `<fieldset>`s with legends group "Your details" and "Order".

## Real-world example

An online store in Karachi found that 40% of mobile users abandoned checkout. Session recordings showed why: the phone field was `type="number"` (it dropped the leading 0, so numbers failed server checks), labels were placeholders that vanished while typing, the city was free text (typos broke delivery-zone lookups), errors appeared only as a red border at the top of the page, and every server-side error **cleared the whole form**. The fixes were all plain HTML: real labels, `type="tel"` with a `pattern` and help text, a `<select>` of supported cities, `autocomplete` attributes (so phones filled name, email and address in one tap), errors next to the fields with text and `aria-describedby`, and keeping submitted values on error. Mobile checkout completion rose noticeably, and support calls about "wrong number" deliveries dropped. The server kept its own validation for every field, because the store had also seen bots posting orders directly to the endpoint, skipping the form completely.

## Common mistakes

- **Missing `name`** attributes, so values silently aren't sent.
- **Placeholders instead of labels,** or labels not connected (`for` doesn't match the `id`).
- **`type="number"` for phone numbers, CNICs, card numbers and OTPs.**
- **GET for logins or private data,** putting passwords in URLs, logs and history.
- **Buttons without `type="button"`** inside forms, submitting by accident.
- **File uploads without `enctype="multipart/form-data"`.**
- **Errors shown only with colour,** at the top of the page, or clearing the user's input.
- **Disabling paste,** or making users re-type emails and passwords unnecessarily.
- **Relying only on client-side validation.**
- **`<input type="hidden">` for secrets or prices:** hidden fields are visible in the source and editable.

## Security lens

<Callout type="security">
Everything the browser enforces, an attacker can bypass. They can edit the HTML in DevTools, or skip the browser and send any request with curl or Burp Suite. HTML validation is for user experience; the server is the security boundary.
</Callout>

- **Validate on the server:** types, lengths, formats, allowed values (is `variety` really one of your products?), and business rules (is the price from your database, not the form?).
- **Never trust hidden fields or disabled inputs:** a hidden `price` or `role` field can be changed. Look up prices and permissions on the server (avoid **mass assignment**).
- **CSRF:** a malicious site can make a victim's browser submit a POST form to your site with their cookies. Protect state-changing forms with CSRF tokens and `SameSite` cookies (see **Web Security for Developers**).
- **Injection and XSS:** treat every submitted value as untrusted. Use parameterised SQL queries and escape values when displaying them.
- **File uploads:** check size limits and real content type (not just the extension), rename files, store them outside the web root or in object storage, scan them if possible, and never execute them.
- **Sensitive fields:** POST over HTTPS only, `autocomplete="off"` only where truly needed (password managers improve security), and never log submitted passwords or card data.
- **Bots and abuse:** rate-limit form endpoints; use honeypot fields or CAPTCHAs carefully (accessible ones) for public forms.

## Interview questions

<QA q="What is the difference between GET and POST for forms?">
GET sends the form data in the URL query string, which is visible, bookmarkable and cached but also stored in history and logs, so it suits searches and filters that do not change data. POST sends data in the request body and is used for actions that create or change data or carry sensitive information. Neither is secure without HTTPS.
</QA>

<QA q="Why is a placeholder not a substitute for a label?">
A placeholder disappears when the user types, often has low contrast, is not reliably exposed as the accessible name, and cannot be clicked to focus the field. A visible label connected with for and id, or by wrapping the input, gives the control a persistent, accessible name and a larger click target.
</QA>

<QA q="What does the name attribute do on form controls?">
It is the key under which the control's value is submitted. Controls without a name are not included in the submitted data, radio buttons with the same name form a group where only one can be selected, and checkboxes with the same name submit multiple values.
</QA>

<QA q="Is HTML5 form validation enough to secure an application?">
No. It improves usability by giving instant feedback, but users can disable it, edit the HTML, or send requests directly without a browser. All input must be validated and authorised on the server, including hidden fields, select values and uploaded files.
</QA>

<QA q="What is needed to upload a file with an HTML form?">
An input of type file with a name, a form with method post and enctype multipart/form-data. The accept attribute can filter the file picker and multiple allows several files, but the server must validate file size, type and content and store uploads safely.
</QA>
