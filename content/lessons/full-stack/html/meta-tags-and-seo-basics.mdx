<Callout type="tip" title="In one minute">
The `<head>` of a page holds **information about the page** (metadata) that browsers, search engines and social apps read. The essentials are `<meta charset="utf-8">`, the **viewport** tag (for mobile), a unique **`<title>`** (shown as the blue link in search results and the tab name) and a **meta description** (often shown as the snippet below it). **SEO** (search engine optimisation) means helping search engines **crawl** (find), **index** (store and understand) and **rank** (order) your pages. The technical basics are: one **canonical URL** per page, a **robots.txt** and **sitemap.xml**, `noindex` for pages that shouldn't appear, **Open Graph** tags for social previews, **structured data** (JSON-LD) for rich results, good **semantic HTML** and **fast, mobile-friendly** pages. The biggest factor is still content that answers what people search for.
</Callout>

## Start from zero

<Callout type="analogy">
Think of a huge library with a robot librarian. The robot walks the shelves following references from book to book (**crawling**), reads each book's cover, title page and table of contents and files a card for it (**indexing**), and when someone asks a question, picks which books to recommend first (**ranking**). Your **title** and **description** are what's printed on the card. **robots.txt** is a sign on some rooms saying "robot, don't go in here". The **sitemap** is a list you hand the robot: "here are all my books". The **canonical** tag says "these three copies are the same book; file the card under this one". **Open Graph** tags decide what the poster looks like when someone shares your book on a noticeboard (WhatsApp, LinkedIn, X).
</Callout>

## What is it?

A complete, realistic `<head>` for a product page. Every line is explained in the concepts below.

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Kent Mangoes, 5 kg Box | Mango Shop</title>
  <meta name="description" content="Fresh Kent mangoes from Florida, delivered in 2 days across the US. Rs 900 per 5 kg box.">
  <link rel="canonical" href="https://mangoshop.example/products/kent">

  <!-- Social previews -->
  <meta property="og:type" content="product">
  <meta property="og:title" content="Kent Mangoes, 5 kg Box">
  <meta property="og:description" content="Fresh from Florida, delivered in 2 days.">
  <meta property="og:image" content="https://mangoshop.example/img/kent-1200x630.jpg">
  <meta property="og:url" content="https://mangoshop.example/products/kent">
  <meta name="twitter:card" content="summary_large_image">

  <!-- Icons and app -->
  <link rel="icon" href="/favicon.ico" sizes="32x32">
  <link rel="icon" href="/icon.svg" type="image/svg+xml">
  <link rel="apple-touch-icon" href="/apple-touch-icon.png">
  <link rel="manifest" href="/manifest.webmanifest">
  <meta name="theme-color" content="#f4b400">
</head>
<body>
  <h1>Kent Mangoes, 5 kg Box</h1>
</body>
</html>
```

## Why does it matter?

- **Traffic:** for most websites, search is the largest source of free visitors. A page that isn't indexed, or shows a bad title, loses that traffic.
- **Click-through:** a clear title and description decide whether people click your result instead of the one above it.
- **Sharing:** links shared on WhatsApp, Slack, LinkedIn and X show a card built from Open Graph tags. Without them you get a bare URL or a random image.
- **Correctness:** a missing viewport tag makes mobile pages tiny; a wrong `charset` garbles Urdu or emoji; a stray `noindex` can remove a whole site from Google.
- **Careers:** frontend and full-stack developers are expected to know technical SEO; Next.js and other frameworks have dedicated metadata APIs because of it.

## When and where do you use it?

On every public page. Pages behind login (dashboards, account pages) still need `charset`, `viewport` and `title`, but should usually be `noindex` and blocked from crawling.

## Concepts one by one

### 1. How search engines work

<Explain>
<What>
Three stages:
1. **Crawling:** bots fetch URLs found through links, sitemaps and previous crawls, respecting `robots.txt`.
2. **Indexing:** the engine renders the page (Google runs JavaScript, but later and with limits), extracts text, links, headings, metadata and structured data, picks a canonical URL, and stores it.
3. **Ranking:** for each search, hundreds of signals decide the order: relevance of the content to the query, quality and trust, links from other sites, page experience (mobile-friendliness, speed, HTTPS), freshness, location and language.
</What>
<Why>
Problems at each stage have different fixes: a page that's never crawled needs links or a sitemap; a page crawled but not indexed may be a duplicate, thin, or `noindex`; a page indexed but ranking low needs better content.
</Why>
<When>
Debugging "why isn't my page on Google?" always starts by asking which stage failed.
</When>
<Where>
**Google Search Console** and **Bing Webmaster Tools** show crawling and indexing status per URL, search queries, clicks and errors. Both are free.
</Where>
<How>
Search `site:yourdomain.com` to see roughly what's indexed.
</How>
</Explain>

### 2. The essential meta tags

<Explain>
<What>
- **`<meta charset="utf-8">`:** the character encoding. Must be within the first 1024 bytes, so put it first.
- **`<meta name="viewport" content="width=device-width, initial-scale=1">`:** tells mobile browsers to use the device width instead of pretending to be a 980 px desktop. Never add `user-scalable=no` or `maximum-scale=1` (it blocks zoom, an accessibility failure).
- **`<title>`:** required on every page. Shown in tabs, bookmarks, history and as the search result headline.
- **`<meta name="description">`:** a summary of the page; search engines often (not always) use it as the snippet.
- **`<html lang="en">`:** the page language (used by screen readers, translation and search).
</What>
<Why>
These are the tags every page needs; the rest depend on the page.
</Why>
<When>
Every HTML document.
</When>
<Where>
Frameworks generate them from config: Next.js's `metadata` export, Astro/Nuxt head helpers, WordPress SEO plugins.
</Where>
<How>
Below, a Python script parses the head of the example page and prints each tag with its length.
</How>
</Explain>

```bash
python3 - <<'PY'
from html.parser import HTMLParser
page = """<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Kent Mangoes, 5 kg Box | Mango Shop</title>
  <meta name="description" content="Fresh Kent mangoes from Florida, delivered in 2 days across the US. Rs 900 per 5 kg box.">
  <link rel="canonical" href="https://mangoshop.example/products/kent">
  <meta property="og:title" content="Kent Mangoes, 5 kg Box">
  <meta property="og:image" content="https://mangoshop.example/img/kent-1200x630.jpg">
  <meta name="robots" content="index, follow">
</head><body></body></html>"""

class HeadReader(HTMLParser):
    def __init__(self):
        super().__init__()
        self.in_title = False
        self.found = []
    def handle_starttag(self, tag, attrs):
        a = dict(attrs)
        if tag == "title":
            self.in_title = True
        elif tag == "meta":
            key = a.get("name") or a.get("property") or ("charset" if "charset" in a else "?")
            self.found.append((key, a.get("content", a.get("charset"))))
        elif tag == "link" and a.get("rel") == "canonical":
            self.found.append(("canonical", a["href"]))
    def handle_data(self, data):
        if self.in_title:
            self.found.append(("title", data))
            self.in_title = False

reader = HeadReader()
reader.feed(page)
for key, value in reader.found:
    print(f"{key:14} {len(value):3}  {value}")
PY
```

```text output
charset          5  utf-8
viewport        35  width=device-width, initial-scale=1
title           35  Kent Mangoes, 5 kg Box | Mango Shop
description     88  Fresh Kent mangoes from Florida, delivered in 2 days across the US. Rs 900 per 5 kg box.
canonical       39  https://mangoshop.example/products/kent
og:title        22  Kent Mangoes, 5 kg Box
og:image        47  https://mangoshop.example/img/kent-1200x630.jpg
robots          13  index, follow
```

Line by line:

- `HTMLParser` (Python's standard library) calls `handle_starttag` for every opening tag and `handle_data` for text, which is roughly what an SEO crawler does first.
- For `<meta>`, the key is `name` (standard tags), `property` (Open Graph), or `charset`.
- The second column is the length in characters. The title is 35 characters and the description 88: both comfortably inside what Google typically displays (titles are cut at about 600 pixels, roughly 50–60 characters; descriptions at about 150–160 characters on desktop).
- SEO audit tools (Lighthouse, Screaming Frog, Ahrefs) run exactly these checks across thousands of pages: missing, duplicate, too long, too short.

### 3. Writing good titles and descriptions

<Explain>
<What>
- **Title:** unique per page, describes the page's main topic first, brand last: `Primary topic | Brand`. About 50–60 characters.
- **Description:** a one or two sentence pitch with the key facts the searcher cares about (price, delivery, what they'll learn). About 120–160 characters. Not a ranking factor directly, but affects clicks.
</What>
<Why>
Search engines rewrite titles and descriptions that are missing, stuffed with keywords, duplicated or misleading. Good ones get used as written.
</Why>
<When>
Every indexable page; templates for product, category and article pages generate them from data.
</When>
<Where>
The `<h1>` and `<title>` should agree in meaning (they needn't be identical).
</Where>
<How>
Compare:
</How>
</Explain>

| Bad | Why | Better |
| --- | --- | --- |
| `Home` | Says nothing; duplicated on many sites | `Fresh Mangoes Delivered Across the US \| Mango Shop` |
| `Mango Shop \| Mango Shop \| Buy Mangoes` | Repetition, brand first | `Kent Mangoes, 5 kg Box \| Mango Shop` |
| `mangoes, buy mangoes, cheap mangoes, mango Houston` | Keyword stuffing | Write for humans |
| The same description on all 200 product pages | Duplicate, useless as a snippet | Generated from each product's name, origin and price |

The old **`<meta name="keywords">`** tag is **ignored** by Google and Bing (it was abused in the 1990s). Don't spend time on it.

### 4. Controlling indexing: robots meta and robots.txt

<Explain>
<What>
Two different tools:
- **`robots.txt`** (a file at `/robots.txt`) tells bots which URLs they may **crawl**.
- **`<meta name="robots" content="noindex">`** (or the `X-Robots-Tag: noindex` HTTP header) tells engines not to **index** a page they crawled. Other values: `nofollow` (don't follow links), `noarchive`, `max-snippet`, `max-image-preview`.
</What>
<Why>
Keep search results clean: no login pages, carts, internal search results, staging sites or thank-you pages.
</Why>
<When>
- To keep a page **out of the results**, use `noindex`, and **allow** crawling so the bot can see the `noindex`. A page blocked in robots.txt can still appear in results (with no description) if other sites link to it.
- Use robots.txt to save crawl effort on huge sets of useless URLs (filters, sort orders) and to point to sitemaps.
</When>
<Where>
robots.txt is **public and advisory**: anyone can read it and malicious bots ignore it. Never use it to "hide" secret paths.
</Where>
<How>
Python's standard library contains a robots.txt parser, so we can test rules exactly as a polite bot would.
</How>
</Explain>

```bash
python3 - <<'PY'
from urllib.robotparser import RobotFileParser
rules = """User-agent: *
Disallow: /cart
Disallow: /account/
Allow: /

User-agent: GPTBot
Disallow: /

Sitemap: https://mangoshop.example/sitemap.xml"""
rp = RobotFileParser()
rp.parse(rules.splitlines())
checks = [("Googlebot", "/products/kent"), ("Googlebot", "/cart"),
          ("Googlebot", "/account/orders"), ("GPTBot", "/products/kent")]
for agent, path in checks:
    ok = rp.can_fetch(agent, "https://mangoshop.example" + path)
    print(f"{agent:10} {path:20} {'allowed' if ok else 'blocked'}")
print(rp.site_maps())
PY
```

```text output
Googlebot  /products/kent       allowed
Googlebot  /cart                blocked
Googlebot  /account/orders      blocked
GPTBot     /products/kent       blocked
['https://mangoshop.example/sitemap.xml']
```

Line by line:

- `User-agent: *` is a group for all bots without a more specific group. It blocks `/cart` (and anything starting with it, like `/cart/checkout`) and everything under `/account/`, and allows the rest.
- `User-agent: GPTBot` is a separate group for OpenAI's crawler, blocking the whole site. A bot uses the **most specific** group that matches its name, so GPTBot ignores the `*` rules.
- Googlebot can fetch product pages but not the cart or account pages.
- `Sitemap:` lines tell every bot where the sitemap is; `site_maps()` reads them.
- Many sites now add groups like this for AI training crawlers; reputable ones respect them, but robots.txt is not access control.

### 5. Canonical URLs and duplicate content

<Explain>
<What>
The same content is often reachable at many URLs: `http://` and `https://`, with and without `www`, trailing slashes, tracking parameters (`?utm_source=whatsapp`), sort orders, print versions. `<link rel="canonical" href="...">` tells search engines which URL is the **main** one.
</What>
<Why>
Without it, engines guess, ranking signals (links) are split across copies, and the wrong URL may appear in results.
</Why>
<When>
Every indexable page should have a **self-referencing** canonical (pointing to its own clean URL). Duplicates point to the original.
</When>
<Where>
Use **absolute** URLs. Combine with **301 redirects** for duplicates you control (http → https, non-www → www); the canonical is a strong hint, a redirect is a rule.
</Where>
<How>
`https://mangoshop.example/products/kent?utm_source=whatsapp&sort=price` still declares `https://mangoshop.example/products/kent` as canonical.
</How>
</Explain>

### 6. Social previews: Open Graph and Twitter cards

<Explain>
<What>
**Open Graph** (created by Facebook, now used by WhatsApp, LinkedIn, Slack, Discord, Telegram and others) defines `og:title`, `og:description`, `og:image`, `og:url`, `og:type` and `og:site_name`. X (Twitter) reads them too, plus `twitter:card` (`summary` or `summary_large_image`).
</What>
<Why>
A shared link with a large image, clear title and description gets far more clicks than a bare URL.
</Why>
<When>
Every page likely to be shared: home, products, articles, events.
</When>
<Where>
- `og:image` must be an **absolute** https URL. Recommended size: **1200×630** pixels (1.91:1), under about 5 MB, JPG or PNG.
- Apps cache previews; after changing tags, refresh them with each platform's debugger (Facebook Sharing Debugger, LinkedIn Post Inspector).
- These tags use `property=` (Open Graph) or `name=` (Twitter), not interchangeable in older parsers.
</Where>
<How>
See the full head example above.
</How>
</Explain>

### 7. Structured data (JSON-LD)

<Explain>
<What>
**Structured data** describes the page's facts in a vocabulary search engines understand (**schema.org**): a Product with price and availability, an Article with author and date, a Recipe, an Event, FAQ, Breadcrumbs, an Organization with logo. The recommended format is **JSON-LD**, a `<script type="application/ld+json">` block.
</What>
<Why>
It makes pages eligible for **rich results** (prices, ratings, breadcrumbs, event dates in search results), and helps engines understand entities.
</Why>
<When>
Products, articles, recipes, events, job postings, local businesses, breadcrumbs.
</When>
<Where>
The data must match what's **visible** on the page. Fake reviews or prices in structured data violate Google's guidelines and can bring a manual penalty. Test with Google's **Rich Results Test** and the **Schema Markup Validator**.
</Where>
<How>
A product example, then a check that it's valid JSON and contains what Google requires for product snippets.
</How>
</Explain>

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Kent Mangoes, 5 kg Box",
  "image": "https://mangoshop.example/img/kent-1200x630.jpg",
  "description": "Fresh Kent mangoes from Florida.",
  "brand": { "@type": "Brand", "name": "Mango Shop" },
  "offers": {
    "@type": "Offer",
    "price": "900",
    "priceCurrency": "PKR",
    "availability": "https://schema.org/InStock",
    "url": "https://mangoshop.example/products/kent"
  }
}
</script>
```

```bash
mkdir -p site && cat > site/product.html <<'HTML'
<!DOCTYPE html>
<html lang="en"><head><meta charset="utf-8"><title>Kent Mangoes, 5 kg Box | Mango Shop</title>
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Kent Mangoes, 5 kg Box",
  "image": "https://mangoshop.example/img/kent-1200x630.jpg",
  "offers": { "@type": "Offer", "price": "900", "priceCurrency": "PKR",
              "availability": "https://schema.org/InStock" }
}
</script></head><body><h1>Kent Mangoes, 5 kg Box</h1><p>Rs 900</p></body></html>
HTML
python3 - <<'PY'
import json, re
html = open("site/product.html").read()
blocks = re.findall(r'<script type="application/ld\+json">(.*?)</script>', html, re.S)
for raw in blocks:
    data = json.loads(raw)
    print("type:", data["@type"])
    offer = data.get("offers", {})
    print("price:", offer.get("price"), offer.get("priceCurrency"))
    missing = [k for k in ("name", "image", "offers") if k not in data]
    print("missing required:", missing or "none")
PY
```

```text output
type: Product
price: 900 PKR
missing required: none
```

Line by line:

- The page embeds JSON-LD in a script tag; browsers don't run it (it's not JavaScript), they ignore it.
- The Python script extracts each JSON-LD block with a regular expression and parses it with `json.loads`. A trailing comma or a missing quote would raise an error here, and Google would also ignore the block.
- It prints the type and price and checks the fields needed for a product snippet. Real validators check many more rules.

### 8. Sitemaps

<Explain>
<What>
An XML file (usually `/sitemap.xml`) listing the URLs you want indexed, with optional `lastmod` dates. Large sites use a **sitemap index** pointing to several sitemaps (each up to 50,000 URLs or 50 MB).
</What>
<Why>
Helps engines discover new and updated pages, especially on large sites or pages with few internal links.
</Why>
<When>
Every site with more than a handful of pages; generated automatically by your framework or CMS.
</When>
<Where>
List only **canonical, indexable** URLs (no redirects, no `noindex`). Reference it from robots.txt and submit it in Search Console. `lastmod` should be real (Google ignores it if it's always "today"); `priority` and `changefreq` are ignored by Google.
</Where>
<How>
A small sitemap, checked for well-formedness and read back:
</How>
</Explain>

```bash
cat > sitemap.xml <<'XML'
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://mangoshop.example/</loc>
    <lastmod>2026-06-01</lastmod>
  </url>
  <url>
    <loc>https://mangoshop.example/products/kent</loc>
    <lastmod>2026-06-10</lastmod>
  </url>
</urlset>
XML
xmllint --noout sitemap.xml && echo "well-formed"
python3 - <<'PY'
import xml.etree.ElementTree as ET
ns = {"s": "http://www.sitemaps.org/schemas/sitemap/0.9"}
for url in ET.parse("sitemap.xml").getroot().findall("s:url", ns):
    print(url.find("s:lastmod", ns).text, url.find("s:loc", ns).text)
PY
```

```text output
well-formed
2026-06-01 https://mangoshop.example/
2026-06-10 https://mangoshop.example/products/kent
```

Line by line:

- The `urlset` element uses the sitemaps.org namespace; each `url` has a required `loc` (absolute URL) and an optional `lastmod` (date the content last changed meaningfully).
- `xmllint --noout` prints nothing if the XML is well-formed (and errors otherwise), so `echo` runs only on success.
- The Python script reads the URLs back; namespaced XML needs the namespace map (see the XML lesson).

### 9. Icons, manifest and theme colour

<Explain>
<What>
- **Favicons:** `favicon.ico` (32×32, also requested automatically at `/favicon.ico`), an SVG icon for modern browsers, and `apple-touch-icon` (180×180 PNG) for iOS home screens.
- **Web app manifest** (`manifest.webmanifest`): JSON with the app name, icons (192 and 512 px), colours and display mode, used when installing the site as an app (PWA).
- **`theme-color`:** colours the browser UI on mobile.
</What>
<Why>
Icons appear in tabs, bookmarks, search results on mobile, and home screens. A missing favicon also creates a 404 on every visit.
</Why>
<When>
Every site.
</When>
<Where>
Keep the set small; the five lines in the head example cover modern browsers.
</Where>
<How>
Google shows your favicon next to mobile results, so it should be at least 48×48 and recognisable.
</How>
</Explain>

### 10. Multiple languages: hreflang

<Explain>
<What>
If a page exists in several languages or regions, `<link rel="alternate" hreflang="...">` tags list every version, so searchers see the right one.
</What>
<Why>
Without them, an Urdu reader might land on the English page or engines might treat translations as duplicates.
</Why>
<When>
Multilingual or multi-region sites.
</When>
<Where>
Each version lists **all** versions including itself, and links must be reciprocal. `x-default` is the fallback (often a language chooser). Also set `<html lang>` on each version.
</Where>
<How>
Example:
</How>
</Explain>

```html noqa
<link rel="alternate" hreflang="en" href="https://mangoshop.example/en/products/kent">
<link rel="alternate" hreflang="ur" href="https://mangoshop.example/ur/products/kent">
<link rel="alternate" hreflang="x-default" href="https://mangoshop.example/products/kent">
```

### 11. On-page SEO and page experience

<Explain>
<What>
What's in the body matters more than the head:
- **Content** that fully answers the searcher's question, written for people.
- **Semantic HTML:** one clear `<h1>`, a logical heading outline, descriptive link text ("Kent mango guide", not "click here"), alt text on images, lists and tables for structured content.
- **Clean URLs:** `/products/kent`, not `/p?id=8172&cat=3`.
- **Internal links** between related pages, so bots find them and understand the structure.
- **Page experience:** HTTPS, mobile-friendly layout, no intrusive pop-ups, and good **Core Web Vitals**: **LCP** (Largest Contentful Paint, main content loads in under 2.5 s), **INP** (Interaction to Next Paint, responds to taps in under 200 ms), **CLS** (Cumulative Layout Shift, under 0.1, nothing jumps around).
</What>
<Why>
Search engines rank pages that satisfy users. Accessibility and SEO overlap heavily: both read structure, text alternatives and link text.
</Why>
<When>
All the time; check during reviews.
</When>
<Where>
**JavaScript-rendered content:** Google can render client-side JavaScript, but rendering is delayed and other crawlers and social apps often don't run JavaScript at all. Put important content and **all meta tags** in the server-rendered HTML (Next.js server components, static generation).
</Where>
<How>
Lighthouse (Chrome DevTools) has an SEO audit and measures Core Web Vitals in the lab; PageSpeed Insights and Search Console show data from real users.
</How>
</Explain>

## Hands-on

Write the head for an article page on your site, then check it.

1. Create `article.html` with `lang`, charset, viewport, a unique title (50–60 characters), a description (120–160 characters), a self-referencing canonical, Open Graph tags with a 1200×630 image, and an `Article` JSON-LD block with `headline`, `author`, `datePublished` and `image`.
2. Run the head reader script above on it and fix lengths.
3. Write a `robots.txt` that blocks `/admin/` and `/search`, allows everything else and lists your sitemap; test it with `RobotFileParser`.
4. Create `sitemap.xml` with three URLs and check it with `xmllint --noout`.
5. Deploy it (or use an existing page) and open Lighthouse → SEO, the Rich Results Test, and a social preview debugger.

A Next.js equivalent of the essential tags, since this site uses Next.js:

```tsx
// app/products/kent/page.tsx
import type { Metadata } from "next";

export const metadata: Metadata = {
  title: "Kent Mangoes, 5 kg Box | Mango Shop",
  description: "Fresh Kent mangoes from Florida, delivered in 2 days across the US.",
  alternates: { canonical: "https://mangoshop.example/products/kent" },
  openGraph: {
    title: "Kent Mangoes, 5 kg Box",
    images: [{ url: "https://mangoshop.example/img/kent-1200x630.jpg", width: 1200, height: 630 }],
  },
};
```

Next.js renders these as the same `<title>`, `<meta>` and `<link>` tags in the server HTML.

## Real-world example

A common and expensive mistake happens during a site launch: developers add `<meta name="robots" content="noindex">` (or `Disallow: /` in robots.txt) to the staging site so it doesn't appear in Google, then deploy that same configuration to production. Within days, pages start dropping out of the index and organic traffic falls sharply; it can take weeks to recover after the fix. Teams that avoid this generate robots rules from the environment (production allows, staging blocks **and** uses password protection), add an automated check in CI or monitoring that fails if the production home page contains `noindex`, and watch Search Console's indexing report after every launch.

## Common mistakes

- **Missing or duplicate titles and descriptions** across many pages.
- **Forgetting the viewport tag,** or disabling zoom in it.
- **`noindex` left over from staging,** or `Disallow: /` in production robots.txt.
- **Blocking a page in robots.txt to remove it from results** (use `noindex` and allow crawling).
- **No canonical, or canonicals pointing to redirects, 404s or the wrong page.**
- **Relative URLs in `og:image` and canonical.**
- **Meta tags added only by client-side JavaScript,** invisible to social apps.
- **Structured data that doesn't match visible content** (fake ratings, wrong prices).
- **Keyword stuffing** and spending effort on the keywords meta tag.
- **Slow, heavy pages** with layout shifts.

## Security lens

<Callout type="security">
Metadata is public and parsed by many systems. Treat it as both an information leak and an injection surface.
</Callout>

- **robots.txt reveals paths:** `Disallow: /admin-backup-2024/` advertises exactly what you want hidden. Protect private areas with authentication, not robots rules.
- **Staging and preview sites** should require a password, not just `noindex`; otherwise they leak unreleased features and can be indexed through links.
- **Escape user content in meta tags:** a product name or user bio placed into `<title>`, `og:title` or JSON-LD without escaping can enable XSS. In JSON-LD, a value containing `</script>` breaks out of the script block; serialise with a function that escapes `<` (most frameworks do).
- **Open Graph and link previews** are fetched by other companies' servers (link-preview bots). If your app generates previews of user-supplied URLs, that's a **server-side request forgery (SSRF)** risk: block internal addresses (see the Web Security module).
- **Don't put secrets** (internal IDs, API keys, staff emails) in meta tags, comments or JSON-LD; anyone can read the source.

## Interview questions

<QA q="What is the difference between crawling, indexing and ranking?">
Crawling is when a search engine's bot discovers and downloads pages by following links and sitemaps, within the rules of robots.txt. Indexing is processing a crawled page, rendering it, understanding its content and choosing a canonical URL, then storing it. Ranking is ordering indexed pages for a specific query using relevance, quality, links and page-experience signals.
</QA>

<QA q="How do you keep a page out of search results?">
Add a robots meta tag with noindex, or an X-Robots-Tag noindex HTTP header, and make sure the page is not blocked in robots.txt so the crawler can actually see that instruction. Blocking with robots.txt alone only stops crawling, and the URL can still be indexed from external links. For private content, require authentication.
</QA>

<QA q="What is a canonical URL and why does it matter?">
It is the preferred URL for content reachable at several addresses, declared with a link element with rel canonical. It tells search engines which version to index and show, and consolidates ranking signals onto it instead of splitting them across duplicates created by tracking parameters, protocols, trailing slashes or sorting options.
</QA>

<QA q="What are Open Graph tags?">
Meta tags with properties such as og:title, og:description, og:image and og:url that social networks and messaging apps read to build link previews. The image should be an absolute URL, typically 1200 by 630 pixels, and the tags must be in the server-rendered HTML because preview bots usually don't run JavaScript.
</QA>

<QA q="What is structured data and how is it added?">
Machine-readable information about a page's content using the schema.org vocabulary, such as a product's price and availability or an article's author and publish date. The recommended format is JSON-LD in a script element of type application/ld+json. It can make pages eligible for rich results, must match visible content, and is tested with the Rich Results Test.
</QA>
