<BigIdea>
<Tr>
<En>
**Accessibility (a11y)** means people with disabilities can perceive, understand, navigate and use your site: blind users with **screen readers**, people who can't use a mouse (**keyboard** or switch users), low-vision users (**zoom**, contrast), deaf users (captions), and people with cognitive or motor disabilities. The standard is **WCAG** (aim for **AA**). Most of it comes from **good HTML**: semantic elements, labels, alt text, headings, landmarks, real buttons and links. **ARIA** (`aria-label`, `aria-expanded`, `role`…) fills gaps, but its **first rule** is: don't use ARIA when a native element does the job. Make everything work by **keyboard** with **visible focus**, meet **contrast** (4.5:1 for text), announce changes with **live regions**, and test with tools (axe, Lighthouse) **and** by hand.
</En>
<Ur>
**Accessibility (a11y)** ka matlab hai maazoor log aap ki site dekh, samajh, chal aur istemal kar saken: **screen readers** wale nabeena users, jo mouse istemal nahi kar sakte (**keyboard** ya switch users), kam nazar wale (**zoom**, contrast), behre (captions), aur zehni ya harkat ki maazoori wale. Standard **WCAG** hai (**AA** ka hadaf). Is ka zyada hissa **achhe HTML** se aata hai: semantic elements, labels, alt text, headings, landmarks, asli buttons aur links. **ARIA** (`aria-label`, `aria-expanded`, `role`…) khala bharta hai, lekin us ka **pehla qaida** hai: jab native element kaam kare to ARIA na lagao. Sab kuch **keyboard** se **nazar aane wale focus** ke saath chalayen, **contrast** poora karein (text ke liye 4.5:1), tabdeeliyan **live regions** se batayen, aur tools (axe, Lighthouse) **aur** haath se test karein.
</Ur>

## At a glance

<Glance>
<What>
<Tr>
<En>

How different people use the same page:

| Person | Uses | Needs from your HTML |
| --- | --- | --- |
| Blind user | Screen reader + keyboard | Headings, landmarks, labels, alt text, names, announced changes |
| Low-vision user | Zoom (200–400%), magnifier, high contrast | Reflowing text, enough contrast, no text in images |
| Keyboard-only user | Tab, Shift+Tab, Enter, Space, arrows | Everything reachable and operable, visible focus, logical order |
| Voice-control user | "Click Add to cart" | Visible labels that match accessible names |
| Deaf / hard-of-hearing user | Captions, transcripts | Captions for video, text for audio |
| Cognitive disabilities | Clear language, consistent layout | Simple wording, clear errors, no time pressure |

WCAG groups its requirements under **POUR**: **Perceivable** (alternatives, captions, contrast, zoom), **Operable** (keyboard, enough time, no flashing), **Understandable** (clear language, predictable behaviour, error help) and **Robust** (valid, semantic code).

## Learn it step by step

<Walkthrough>

<Step title="Accessible names: what assistive tech calls things">

<Tr>
<En>Every interactive element has an **accessible name**: the words a screen reader announces and voice control uses. Browsers compute it from, in order, `aria-labelledby`, `aria-label`, native labelling (`<label>`, `alt`, `<caption>`), the element's text, and finally `title`/`placeholder`. An icon-only button or image link without `alt` has **no name**: users hear just "button" or "link". Prefer **visible** text as the name (voice users say what they see) and use `aria-label` when there's none. Check names in DevTools → Accessibility → "Name".</En>
<Ur>Har interactive element ka **accessible name** hota hai: wo alfaaz jo screen reader bolta aur voice control istemal karta hai. Browser ise is tarteeb se nikalta hai: `aria-labelledby`, `aria-label`, native label (`<label>`, `alt`, `<caption>`), element ka text, aur aakhir me `title`/`placeholder`. Sirf icon wala button ya bina `alt` image link **be-naam** hai: users sirf "button" ya "link" sunte hain. Naam ke liye **nazar aane wala** text behtar (voice users wahi bolte hain jo dekhte hain) aur jab na ho to `aria-label`. Naam DevTools → Accessibility → "Name" me dekhein.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<button type="button">✕</button>
<button type="button" aria-label="Close dialog">✕</button>
<h2 id="cart-title">Your cart</h2>
<section aria-labelledby="cart-title"><p>2 items</p></section>
<label for="q">Search products</label><input id="q" type="search">
<input type="search" aria-label="Search the help centre">"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title><body>" + html)
    print(page.locator("body").aria_snapshot())
    browser.close()
PY
```

```text output
- button "✕"
- button "Close dialog": ✕
- heading "Your cart" [level=2]
- region "Your cart":
  - paragraph: 2 items
- text: Search products
- searchbox "Search products"
- searchbox "Search the help centre"
```

<Happened>
<Tr>
<En>The first close button's name is just "✕" (a screen reader might say "multiplication x"). With `aria-label="Close dialog"` the name is clear while ✕ stays visible. `aria-labelledby="cart-title"` named the section with the heading's text, and a named `<section>` becomes a **region** landmark. The first search box is named by its `<label>`; the second has no visible label, so `aria-label` provides one.</En>
<Ur>Pehle close button ka naam sirf "✕" hai (screen reader "multiplication x" bol sakta hai). `aria-label="Close dialog"` se naam saaf hai jabke ✕ nazar aata rehta hai. `aria-labelledby="cart-title"` ne section ko heading ke text se naam diya, aur naam wala `<section>` **region** landmark ban jata hai. Pehle search box ka naam `<label>` se hai; doosre ka nazar aane wala label nahi, isliye `aria-label` naam deta hai.</Ur>
</Tr>
</Happened>

<Step title="The first rule of ARIA">

<Tr>
<En>

ARIA **only changes what assistive technology is told**; it adds no behaviour. `role="button"` on a `<div>` doesn't make it focusable or respond to Enter/Space. Wrong ARIA misleads (a button you can't activate, an `aria-expanded` that never updates), and surveys find pages using ARIA have **more** errors on average. **Rule 1:** if native HTML has the meaning and behaviour, use it. Use ARIA for patterns HTML lacks (tabs, comboboxes, tree views) or to add names and states; the W3C **ARIA Authoring Practices Guide** shows tested patterns. "No ARIA is better than bad ARIA."

| Instead of | Use |
| --- | --- |
| `<div role="button" tabindex="0" onclick onkeydown>` | `<button type="button">` |
| `<span role="link" onclick="...">` | `<a href="...">` |
| `<div role="checkbox" aria-checked>` | `<input type="checkbox">` |
| `<div role="heading" aria-level="2">` | `<h2>` |
| `<div role="navigation">` | `<nav>` |
| Custom ARIA accordion | `<details>` / `<summary>` |
| Custom ARIA modal | `<dialog>` with `showModal()` |

</En>
<Ur>

ARIA **sirf ye badalta hai ke assistive technology ko kya bataya jaye**; koi rawaiya nahi jorta. `<div>` par `role="button"` use focus hone wala ya Enter/Space par chalne wala nahi banata. Ghalat ARIA gumrah karta hai (aisa button jo chal na sake, aisa `aria-expanded` jo kabhi update na ho), aur survey batate hain ke ARIA wale pages me ausatan **zyada** ghaltiyan hoti hain. **Qaida 1:** agar native HTML me matlab aur rawaiya hai to wahi lein. ARIA un namoonon ke liye jo HTML me nahi (tabs, comboboxes, tree views) ya naam aur states jorne ke liye; W3C ki **ARIA Authoring Practices Guide** aazmaye namoone dikhati hai. "Bura ARIA se koi ARIA nahi behtar."

| Is ke bajaye | Ye lein |
| --- | --- |
| `<div role="button" tabindex="0" onclick onkeydown>` | `<button type="button">` |
| `<span role="link" onclick="...">` | `<a href="...">` |
| `<div role="checkbox" aria-checked>` | `<input type="checkbox">` |
| `<div role="heading" aria-level="2">` | `<h2>` |
| `<div role="navigation">` | `<nav>` |
| Apna ARIA accordion | `<details>` / `<summary>` |
| Apna ARIA modal | `showModal()` ke saath `<dialog>` |

</Ur>
</Tr>

</Step>

<Step title="Names, descriptions and states">

<Tr>
<En>The ARIA you'll use most: **labelling** (`aria-label`, `aria-labelledby`, `aria-describedby` for help text and errors), **states** (`aria-expanded`, `aria-pressed`, `aria-current="page"`, `aria-invalid`, `aria-disabled`, `aria-busy`) and **relationships** (`aria-controls`). Sighted users see that a menu is open; states let screen readers say the same. States must be **kept in sync** by your JavaScript: `aria-expanded="false"` on an open menu is a bug. Below, a real browser shows a menu button before and after opening.</En>
<Ur>Sab se zyada istemal hone wala ARIA: **label** (`aria-label`, `aria-labelledby`, help text aur errors ke liye `aria-describedby`), **states** (`aria-expanded`, `aria-pressed`, `aria-current="page"`, `aria-invalid`, `aria-disabled`, `aria-busy`) aur **rishte** (`aria-controls`). Dekhne wale dekhte hain ke menu khula hai; states screen readers se yahi bulwati hain. States aap ki JavaScript ko **barabar rakhni** hain: khule menu par `aria-expanded="false"` bug hai. Neeche asli browser menu button kholne se pehle aur baad dikhata hai.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<nav aria-label="Main">
  <button type="button" aria-expanded="false" aria-controls="menu">Menu</button>
  <ul id="menu" hidden>
    <li><a href="/" aria-current="page">Home</a></li>
    <li><a href="/shop">Shop</a></li>
  </ul>
</nav>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title><body>" + html)
    print("--- closed:")
    print(page.locator("nav").aria_snapshot())
    page.get_by_role("button", name="Menu").evaluate(
        "btn => { btn.setAttribute('aria-expanded', 'true'); document.getElementById('menu').hidden = false; }")
    print("--- open:")
    print(page.locator("nav").aria_snapshot())
    browser.close()
PY
```

```text output
--- closed:
- navigation "Main":
  - button "Menu"
--- open:
- navigation "Main":
  - button "Menu" [expanded]
  - list:
    - listitem:
      - link "Home":
        - /url: /
    - listitem:
      - link "Shop":
        - /url: /shop
```

<Happened>
<Tr>
<En>Closed: the list has `hidden`, so it's not in the tree, and the button is collapsed (no `[expanded]` flag). The script simulated a click by setting `aria-expanded="true"` **and** showing the list; both must change together. Open: the button is "Menu, button, expanded", the links appear, and `aria-current="page"` makes screen readers say "Home, current page".</En>
<Ur>Band: list par `hidden` hai, isliye darakht me nahi, aur button simta hua hai (`[expanded]` nishan nahi). Script ne `aria-expanded="true"` set kar ke **aur** list dikha kar click jaisa kiya; dono ikatthe badalne chahiyen. Khula: button "Menu, button, expanded" hai, links nazar aate hain, aur `aria-current="page"` se screen readers "Home, current page" bolte hain.</Ur>
</Tr>
</Happened>

<Step title="Hiding content correctly">

<Tr>
<En>

Three kinds of "hidden":

1. **From everyone:** `hidden` or `display: none` (closed menus, inactive tabs).
2. **Visually only:** a visually-hidden class (`sr-only`) for extra screen-reader context like "(opens in a new tab)".
3. **From screen readers only:** `aria-hidden="true"` for decorative or duplicate content (icons, star graphics next to text that already says the rating).

The wrong one hides information or makes screen readers read noise twice. **Never put `aria-hidden="true"` on focusable elements** or their parents: keyboard users still reach them but hear nothing.

</En>
<Ur>

"Chhupe" ki teen qismen:

1. **Sab se:** `hidden` ya `display: none` (band menus, ghair fa'al tabs).
2. **Sirf nazar se:** visually-hidden class (`sr-only`) screen reader ke izafi siyaq ke liye, jaise "(opens in a new tab)".
3. **Sirf screen readers se:** sajawati ya dohre mawad ke liye `aria-hidden="true"` (icons, rating likhe text ke saath sitaron ki tasveer).

Ghalat qisam maloomat chhupati hai ya screen readers se shor do dafa parhwati hai. **Focus hone wale elements** ya un ke parents par **`aria-hidden="true"` kabhi nahi**: keyboard users un tak pohnchte hain magar kuch nahi sunte.

</Ur>
</Tr>

```html preview h=120 noqa
<style>
  .visually-hidden {
    position: absolute !important; width: 1px; height: 1px; padding: 0; margin: -1px;
    overflow: hidden; clip: rect(0 0 0 0); white-space: nowrap; border: 0;
  }
</style>
<p>
  <span aria-hidden="true">★★★★☆</span>
  <span class="visually-hidden">Rated 4 out of 5</span>
  (128 reviews)
</p>
<p><a href="/terms" target="_blank" rel="noopener">Delivery terms<span class="visually-hidden"> (opens in a new tab)</span></a></p>
```

<Happened>
<Tr>
<En>The stars are hidden from screen readers, which would otherwise say "black star, black star…". "Rated 4 out of 5" is visually hidden but read aloud, so both groups get the information in the form that suits them. The link's visible text stays short while screen readers also hear "(opens in a new tab)". The class hides text without `display: none`, which would hide it from screen readers too.</En>
<Ur>Sitare screen readers se chhupe hain, warna wo "black star, black star…" bolte. "Rated 4 out of 5" nazar se chhupa magar bola jata hai, isliye dono groups ko apne liye munasib shakal me maloomat milti hai. Link ka nazar aane wala text chhota rehta hai jabke screen readers "(opens in a new tab)" bhi sunte hain. Class `display: none` ke baghair text chhupati hai, jo screen readers se bhi chhupa deta.</Ur>
</Tr>
</Happened>

<Step title="Keyboard access and visible focus">

<Tr>
<En>

Everything a mouse can do must work by **keyboard**: Tab/Shift+Tab move between controls, Enter activates links and buttons, Space buttons and checkboxes, arrows move within radios, menus and tabs, Escape closes dialogs. Sighted keyboard users must also **see** the focus.

- Never remove outlines without a replacement: use `:focus-visible` for a clear ring.
- Keep **DOM order** the same as visual order.
- `tabindex="0"` adds a custom element to the tab order, `-1` makes it script-focusable only; avoid positive values.
- No **keyboard traps**, except focus staying inside an open modal.

Click into the result and press Tab.

</En>
<Ur>

Mouse jo kar sake wo **keyboard** se bhi ho: Tab/Shift+Tab controls ke beech chalate hain, Enter links aur buttons chalata hai, Space buttons aur checkboxes, arrows radios, menus aur tabs ke andar, Escape dialogs band karta hai. Dekhne wale keyboard users ko focus **dikhna** bhi chahiye.

- Outlines bina mutabadil kabhi na hatayen: saaf ring ke liye `:focus-visible`.
- **DOM tarteeb** nazar aane wali tarteeb jaisi rakhein.
- `tabindex="0"` apne element ko tab tarteeb me jorta hai, `-1` sirf script se focus hone wala banata hai; positive values se bachen.
- **Keyboard ke jaal** nahi, siwaye khule modal ke andar focus rehne ke.

Result me click kar ke Tab dabayen.

</Ur>
</Tr>

```html preview h=150 noqa
<style>
  a, button, input { font-size: 16px; }
  :focus { outline: none; }                                   /* removes the default ring... */
  :focus-visible { outline: 3px solid #1a73e8; outline-offset: 2px; border-radius: 4px; }  /* ...and replaces it */
  .no-ring:focus-visible { outline: none; }                   /* the bad example */
</style>
<p>
  <a href="#">Good link</a>
  <button type="button">Good button</button>
  <button type="button" class="no-ring">Button without focus ring (bad)</button>
  <input type="text" aria-label="Your name" placeholder="Your name">
</p>
<p>Tab through: you can see where you are, except on the bad button.</p>
```

<Happened>
<Tr>
<En>`:focus-visible` shows a thick blue outline when focus comes from the keyboard (browsers skip it for mouse clicks on buttons), so it's clear for keyboard users and unobtrusive for mouse users. The third button removes the ring entirely: on Tab, nothing shows where you are, which is what thousands of sites do by accident.</En>
<Ur>Jab focus keyboard se aaye to `:focus-visible` mota neela outline dikhata hai (buttons par mouse click ke liye browsers chhor dete hain), isliye keyboard users ke liye saaf aur mouse users ke liye khamosh. Teesra button ring bilkul hata deta hai: Tab par kuch nahi dikhta ke aap kahan hain, jo hazaron sites ghalti se karti hain.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Skip links">

<Tr>
<En>A **skip link** is the first link on the page, "Skip to main content", hidden until focused. Without it, keyboard users Tab through the whole header and menu (sometimes 30+ links) on every page before reaching the content. It links to `#main`, the `id` of `<main>`. <Step title="Colour contrast">

<Tr>
<En>WCAG AA needs a **contrast ratio** of at least **4.5:1** for normal text and **3:1** for large text (about 24 px, or 19 px bold) and important UI parts (input borders, icons, focus rings). The ratio compares the luminance of foreground and background, from 1:1 to 21:1. Low contrast is the **most common** failure on the web and hurts low-vision users and anyone in sunlight. Check with DevTools' colour picker or WebAIM's checker, and never use colour **alone** for meaning (add text or icons). Below, the WCAG formula in Python.</En>
<Ur>WCAG AA aam text ke liye kam se kam **4.5:1** aur bare text (taqreeban 24 px, ya 19 px bold) aur aham UI hisson (input borders, icons, focus rings) ke liye **3:1** **contrast ratio** maangta hai. Ratio foreground aur background ki roshni milata hai, 1:1 se 21:1 tak. Kam contrast web ki **sab se aam** nakaami hai aur kam nazar walon aur dhoop me har kisi ko nuqsan deta hai. DevTools colour picker ya WebAIM checker se check karein, aur matlab ke liye **sirf** rang kabhi nahi (text ya icons joren). Neeche Python me WCAG ka formula.</Ur>
</Tr>

```bash
python3 - <<'PY'
def luminance(hex_colour):
    hex_colour = hex_colour.lstrip("#")
    def channel(c):
        c = int(c, 16) / 255
        return c / 12.92 if c <= 0.04045 else ((c + 0.055) / 1.055) ** 2.4
    r, g, b = (channel(hex_colour[i:i + 2]) for i in (0, 2, 4))
    return 0.2126 * r + 0.7152 * g + 0.0722 * b

def contrast(fg, bg):
    light, dark = sorted((luminance(fg), luminance(bg)), reverse=True)
    return (light + 0.05) / (dark + 0.05)

pairs = [("#aaaaaa", "#ffffff", "light grey text on white"),
         ("#767676", "#ffffff", "mid grey text on white"),
         ("#595959", "#ffffff", "dark grey text on white"),
         ("#ffffff", "#f4b400", "white text on mango yellow"),
         ("#1a1a1a", "#f4b400", "near-black text on mango yellow")]
for fg, bg, label in pairs:
    r = contrast(fg, bg)
    verdict = "passes AA" if r >= 4.5 else ("large text only" if r >= 3 else "FAILS")
    print(f"{label:32} {r:5.2f}:1  {verdict}")
PY
```

```text output
light grey text on white          2.32:1  FAILS
mid grey text on white            4.54:1  passes AA
dark grey text on white           7.00:1  passes AA
white text on mango yellow        1.85:1  FAILS
near-black text on mango yellow   9.43:1  passes AA
```

<Happened>
<Tr>
<En>`luminance` converts each channel from 0–255 to linear brightness (undoing the screen's gamma curve) and weights them, green most (0.7152) because eyes are most sensitive to it. `contrast` divides the lighter luminance by the darker, each plus 0.05. Light grey `#aaaaaa` on white, a very common "subtle" design, fails at 2.32:1; `#767676` is the lightest grey that passes. White on bright yellow fails (1.85:1) while near-black on the same yellow passes easily: brand colours often need dark text.</En>
<Ur>`luminance` har channel ko 0–255 se seedhi roshni me badalta hai (screen ka gamma curve ulta kar ke) aur wazan deta hai, sabz ko sab se zyada (0.7152) kyun ke aankhen us par sab se hassas hain. `contrast` roshan luminance ko tareek se taqseem karta hai, dono me 0.05 jor kar. Safed par halka saleti `#aaaaaa`, bohot aam "naram" design, 2.32:1 par fail hai; `#767676` sab se halka saleti hai jo pass hota hai. Tez peele par safed fail (1.85:1) jabke usi peele par taqreeban kaala aasani se pass: brand ke rangon ko aksar gehra text chahiye.</Ur>
</Tr>
</Happened>

<Step title="Live regions: announcing changes">

<Tr>
<En>When content changes without a page load ("Added to cart", form errors, result counts, chat), screen readers don't notice unless it happens in a **live region**: `role="status"`/`aria-live="polite"` (announce when idle) or `role="alert"`/`aria-live="assertive"` (announce at once, for urgent errors). Otherwise blind users press "Add to cart" and hear nothing. The region should **exist first** (empty) and then get its text. Use `alert` sparingly: it interrupts.</En>
<Ur>Jab mawad page load ke baghair badle ("Added to cart", form errors, natijon ki ginti, chat), screen readers ko pata nahi chalta jab tak ye **live region** me na ho: `role="status"`/`aria-live="polite"` (fursat me batao) ya `role="alert"`/`aria-live="assertive"` (fauran batao, fori errors ke liye). Warna nabeena users "Add to cart" dabate hain aur kuch nahi sunte. Region **pehle maujood** ho (khaali), phir text mile. `alert` kam istemal karein: ye beech me tokta hai.</Ur>

<Step title="Testing accessibility">

<Tr>
<En>Two kinds of testing: **automated** (axe, Lighthouse, WAVE, html-validate) and **manual** (keyboard, screen reader, zoom, contrast). ## Common mistakes

<Compare>
<Bad title="Inaccessible product card">

```text
<div class="card" onclick="openProduct()">
  <img src="kent.jpg">
  <div class="title">Kent</div>
  <div style="color:#bbb">$9 / box</div>
  <div class="icon-btn" onclick="addToCart()"><svg>...</svg></div>
```

<Good title="Named, keyboard-ready, readable">

```text

  <img src="kent.jpg" alt="A ripe yellow Kent mango" width="256" height="120">
  <h2 id="p-title"><a href="/kent">Kent mangoes, 5 kg box</a></h2>
  <p style="color:#595959">$9 per box</p>
  <button type="button"><svg aria-hidden="true">...</svg> Add to cart</button>

</article>
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Removing focus outlines** without a visible replacement.
- **Colour alone** for errors, required fields or status.
- **ARIA instead of native HTML**, or ARIA states that are never updated.
- **`aria-hidden="true"` on focusable elements.**
- **Placeholders as labels**, errors not connected to fields.
- **Disabling zoom** in the viewport meta tag.
- **Unannounced dynamic updates** (toasts, cart counts, validation).
- **Only automated tools**, or only testing with a mouse.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- Nazar aane wale mutabadil ke baghair **focus outlines hatana**.
- Errors, required fields ya status ke liye **sirf rang**.
- **Native HTML ke bajaye ARIA**, ya ARIA states jo kabhi update na hon.
- **Focus hone wale elements par `aria-hidden="true"`.**
- **Placeholders bator labels**, fields se na jure errors.
- Viewport meta tag me **zoom band karna**.
- **Na bataye jane wale badlao** (toasts, cart ginti, validation).
- **Sirf khud kaar tools**, ya sirf mouse se testing.

</Ur>
</Tr>

<DeepDive title="Real world: the pizza order a screen reader couldn't place">

In 2019 the US Supreme Court declined to hear Domino's Pizza's appeal in a case brought by a blind customer who couldn't order on its website and app with a screen reader, so the ruling that the ADA applies to its website and app stood. The issues were ordinary: unlabelled buttons, images without alt text, and controls that didn't work by keyboard. Thousands of similar lawsuits are now filed every year, and the European Accessibility Act requires many digital services sold in the EU to be accessible. Companies that do well treat accessibility like security: accessible components in the design system, axe in CI so regressions fail the build, screen-reader tests of critical flows (signup, checkout) before each release, and developer training in the basics of this lesson.

</DeepDive>

<DeepDive title="Security lens">

Security features must be accessible, or users are pushed to insecure workarounds or locked out.

- **CAPTCHAs:** image-only CAPTCHAs block blind users; prefer risk-based checks and rate limiting, and always offer an alternative.
- **MFA and OTP fields:** label them, use `autocomplete="one-time-code"`, allow enough time and announce errors. Passkeys are both more secure and more accessible than SMS codes.
- **Session timeouts:** warn before expiry and let users extend (WCAG 2.2.1), especially for slow typists.
- **Security warnings** (phishing alerts, "this link leaves our site") must reach screen-reader and keyboard users, not just appear as coloured banners.
- **ARIA and injection:** don't build `aria-label` values from unescaped user input; it's still HTML.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the first rule of ARIA?">
If a native HTML element or attribute already provides the semantics and behaviour you need, use it instead of adding ARIA to a generic element. ARIA only changes what is exposed to assistive technology and adds no behaviour, so incorrect ARIA can make an interface less accessible than no ARIA.
</QA>

<QA q="What is an accessible name and how is it calculated?">
It is the text assistive technologies use to identify an element, such as a button's label. Browsers compute it from aria-labelledby first, then aria-label, then native labelling such as label elements, alt text or captions, then the element's text content, and finally fallbacks like title or placeholder.
</QA>

<QA q="What are the WCAG contrast requirements?">
At level AA, normal text needs a contrast ratio of at least 4.5 to 1 with its background, large text at least 3 to 1, and essential non-text elements like input borders, icons and focus indicators at least 3 to 1. Level AAA raises text requirements to 7 to 1 and 4.5 to 1.
</QA>

<QA q="How do you make dynamic updates accessible to screen readers?">
Place the changing content in a live region, such as an element with role status or aria-live polite for non-urgent messages, or role alert for urgent ones, that exists in the page before its content changes. Screen readers then announce the new text without moving focus. Focus should be moved deliberately only when appropriate, such as into a newly opened dialog.
</QA>

<QA q="How do you test a website for accessibility?">
Combine automated tools such as axe, Lighthouse or WAVE, ideally in CI, with manual testing: keyboard-only navigation with visible focus, a screen reader such as NVDA or VoiceOver to check names, headings, landmarks and announcements, 200 percent zoom and reflow, and contrast checks. Automated tools find only part of the issues, so manual checks and ideally testing with disabled users are essential.
</QA>

1. Navigate one of your pages with only the keyboard and fix every element you can't reach or can't see focused.
