<BigIdea>
<Tr>
<En>
**Links** (`<a href>`) connect pages: absolute (`https://...`), relative (`about.html`), root-relative (`/about`), fragment (`#reviews`), `mailto:` and `tel:`. Link text must make sense on its own ("Download the 2026 sales report", not "click here"). **Images** (`<img>`) always need **`alt`**: a description for informative images, `alt=""` for decorative ones, the **action** for images inside links. Always set **`width` and `height`** so the page doesn't jump, and `loading="lazy"` below the fold. Serve the right size with **`srcset` + `sizes`** and modern formats with **`<picture>`**. **`<video>`/`<audio>`** need `controls` and captions; **`<iframe>`** needs a `title` and `sandbox`/`allow` limits when you don't fully trust the content.
</En>

<Why>
<Tr>
<En>

- **The web is links:** navigation, sharing, and search engines (which discover pages through links and use link text to understand them).
- **Images are usually the heaviest part of a page:** wrong sizes are the top cause of slow pages and poor **Core Web Vitals** (LCP, CLS), which affect ranking and sales.

</En>

## Learn it step by step

<Walkthrough>

<Step title="Kinds of links">

<Tr>
<En>`<a href>` creates a link; `href` can be absolute, relative, root-relative, a fragment, or a scheme like `mailto:`/`tel:`. Use absolute URLs for other sites, root-relative (`/about`) for your own pages (they work from any folder), and fragments for "jump to section". A fragment scrolls to the element with that `id`. `tel:` links dial on phones. `download` suggests saving the file (same-origin files only).</En>
<Ur>`<a href>` link banata hai; `href` absolute, relative, root-relative, fragment, ya `mailto:`/`tel:` jaisi scheme ho sakti hai. Doosri sites ke liye absolute URLs, apne pages ke liye root-relative (`/about`, har folder se chalta hai), aur "hisse par jao" ke liye fragments. Fragment us `id` wale element tak scroll karta hai. `tel:` links phones par number milate hain. `download` file save karne ka mashwara deta hai (sirf usi origin ki files).</Ur>
</Tr>

```html preview h=300 noqa
<nav aria-label="Examples">
  <ul>
    <li><a href="https://developer.mozilla.org/">MDN Web Docs</a> (absolute: another site)</li>
    <li><a href="/about">About us</a> (root-relative: from the site root)</li>
    <li><a href="products/mangoes.html">Our mangoes</a> (relative: from this page's folder)</li>
    <li><a href="#faq">Jump to the FAQ</a> (fragment: a section on this page)</li>
    <li><a href="mailto:orders@example.com?subject=Bulk%20order">Email us about bulk orders</a></li>
    <li><a href="tel:+15125550147">Call (512) 555-0147</a></li>
    <li><a href="/files/price-list.pdf" download>Download the price list (PDF, 120 KB)</a></li>
  </ul>
</nav>
<h2 id="faq">FAQ</h2>
<p>This heading has <code>id="faq"</code>, so the fragment link scrolls here.</p>
```

<Happened>
<Tr>
<En>An **absolute** URL includes `https://` and the domain, so it works from anywhere. `/about` starts at **your** site's root; `products/mangoes.html` starts at the current folder. `#faq` scrolled to `id="faq"` and changed the URL to `...#faq`, so it can be shared. `mailto:` filled in address and subject (`%20` = space). `tel:` used the international format `+1...` so it dials from anywhere. The download link states format and size.</En>
<Ur>**Absolute** URL me `https://` aur domain hai, isliye har jagah se chalta hai. `/about` **aap ki** site ke root se, `products/mangoes.html` maujooda folder se shuru hota hai. `#faq` ne `id="faq"` tak scroll kiya aur URL `...#faq` kiya, isliye share ho sakta hai. `mailto:` ne pata aur subject bhara (`%20` = space). `tel:` ne international format `+1...` istemal kiya taa ke har jagah se mile. Download link format aur size batata hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Link text that makes sense">

<Tr>
<En>The text inside `<a>` is the link's **accessible name**: what screen readers announce and search engines read. Screen-reader users often pull up a **list of all links**, where "click here, click here, read more" is useless. Make link text describe the destination or action; if the design needs short visible text, make it unique ("Read more about Kent mangoes"). Below, a real browser shows how two links to the same file are announced.</En>
<Ur>`<a>` ke andar ka text link ka **accessible name** hai: jo screen readers bolte aur search engines parhte hain. Screen-reader users aksar **saare links ki list** kholte hain, jahan "click here, click here, read more" bekaar hai. Link text manzil ya amal bayan kare; design ko chhota text chahiye to use munfarid banayen ("Read more about Kent mangoes"). Neeche asli browser dikhata hai ek hi file ke do links kaise bole jate hain.</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<p><a href="/report.pdf">Click here</a> for the report.
<a href="/report.pdf">Download the 2026 sales report (PDF, 2 MB)</a></p>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title><body>" + html)
    print(page.locator("body").aria_snapshot())
    browser.close()
PY
```

```text output
    - /url: /report.pdf
  - text: for the report.
  - link "Download the 2026 sales report (PDF, 2 MB)":

```

<Happened>
<Tr>
<En>The first link's name is just "Click here", which tells the user nothing in a list of links. The second says exactly what happens and what to expect (format and size).</En>
<Ur>Pehle link ka naam sirf "Click here" hai, jo links ki list me kuch nahi batata. Doosra bilkul batata hai kya hoga aur kya umeed rakhein (format aur size).</Ur>

<Step title="Opening links in a new tab">

<Tr>
<En>`target="_blank"` opens a new tab. It's sometimes useful (help while filling a form) but often annoying: it breaks Back and surprises users. Use it sparingly and say "opens in a new tab". Historically the new page could reach `window.opener` and redirect **your** tab to a phishing page ("reverse tabnabbing"); modern browsers now imply `rel="noopener"`, but `rel="noopener noreferrer"` is still common, and `noreferrer` also hides your URL. Users can always Ctrl/Cmd-click themselves.</En>
<Ur>`target="_blank"` naya tab kholta hai. Kabhi mufeed (form bharte waqt madad), lekin aksar tang karne wala: Back tor deta hai aur users ko hairan karta hai. Kam istemal karein aur "opens in a new tab" batayen. Pehle naya page `window.opener` tak pohnch kar **aap ka** tab phishing page par bhej sakta tha ("reverse tabnabbing"); jadeed browsers ab khud `rel="noopener"` maante hain, lekin `rel="noopener noreferrer"` ab bhi aam hai, aur `noreferrer` aap ka URL bhi chhupata hai. Users khud hamesha Ctrl/Cmd-click kar sakte hain.</Ur>
</Tr>

```html preview h=90
<p>
  Read the <a href="https://example.com/delivery-terms" target="_blank" rel="noopener noreferrer">delivery terms (opens in a new tab)</a>
  before placing your order.
</p>
```

<Happened>
<Tr>
<En>`target="_blank"` opens a new tab so the user doesn't lose their half-filled order. `rel="noopener"` stops the new page controlling this tab; `noreferrer` also doesn't send this page's address. The link text warns about the new tab.</En>
<Ur>`target="_blank"` naya tab kholta hai taa ke user ka adhoora order na khoye. `rel="noopener"` naye page ko is tab par qaboo se rokta hai; `noreferrer` is page ka pata bhi nahi bhejta. Link text naye tab ki khabar deta hai.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Images and alt text">

<Tr>
<En>

`<img src alt>` shows an image; `alt` is the **text alternative**, read by screen readers, shown if loading fails and used by search engines. Without it, screen readers may read the file name ("IMG underscore 4521 dot jpg").

- **Informative:** describe the information (`alt="Box of ripe Kent mangoes"`).
- **Decorative:** `alt=""`, so assistive tech skips it. Don't omit the attribute.
- **Functional** (in links/buttons): the **action or destination** (`alt="Cart"`).
- **Complex** (charts): a short alt plus the full data nearby.

Don't start with "Image of…", don't repeat surrounding text, and keep it short. Below, a real browser shows how images are exposed.

</En>
<Ur>

`<img src alt>` tasveer dikhata hai; `alt` **text mutabadil** hai, jo screen readers parhte hain, load fail ho to dikhta hai aur search engines istemal karte hain. Is ke baghair screen readers file ka naam parh sakte hain ("IMG underscore 4521 dot jpg").

- **Maloomati:** maloomat bayan karein (`alt="Box of ripe Kent mangoes"`).
- **Sajawati:** `alt=""`, taa ke assistive tech chhor de. Attribute gum na karein.
- **Amali** (links/buttons me): **amal ya manzil** (`alt="Cart"`).
- **Pecheeda** (charts): chhota alt aur qareeb poora data.

"Image of…" se shuru na karein, aas paas ka text na dohrayen, aur chhota rakhein. Neeche asli browser dikhata hai tasveeren kaise pesh hoti hain.

</Ur>
</Tr>

```bash
python3 - <<'PY'
from playwright.sync_api import sync_playwright
html = """<img src="IMG_4521.jpg">
<img src="divider.png" alt="">
<img src="kent.jpg" alt="Box of ripe Kent mangoes">
<a href="/cart"><img src="cart.svg"></a>
<a href="/cart"><img src="cart.svg" alt="Cart"></a>"""
with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.set_content("<!DOCTYPE html><title>t</title><body>" + html)
    print(page.locator("body").aria_snapshot())
    browser.close()
PY
```

```text output
- img
- img "Box of ripe Kent mangoes"
- link:
  - /url: /cart
  - img
- link "Cart":
  - /url: /cart
  - img "Cart"
```

<Happened>
<Tr>
<En>The image without `alt` is an unnamed `img` (screen readers often fall back to the file name). The divider with `alt=""` doesn't appear at all, correctly ignored. The photo is announced with its description. The cart link with an image and no `alt` is a **link with no name**: a blind user hears just "link". With `alt="Cart"`, the link is named "Cart".</En>
<Ur>Bina `alt` tasveer be-naam `img` hai (screen readers aksar file ka naam parhte hain). `alt=""` wala divider bilkul nazar nahi aata, sahi taur par chhora gaya. Photo apne bayan ke saath boli gayi. Bina `alt` tasveer wala cart link **be-naam link** hai: nabeena user sirf "link" sunta hai. `alt="Cart"` ke saath link ka naam "Cart" hai.</Ur>
</Tr>
</Happened>

<Step title="Width, height and layout shift">

<Tr>
<En>`width` and `height` (pixels, no units) give the browser an image's **aspect ratio** before it downloads. Without them no space is reserved, and when the image arrives everything below jumps: **Cumulative Layout Shift**, a Core Web Vital that causes mis-taps and hurts rankings. Set them on every `<img>` and `<video>`; CSS `img { max-width: 100%; height: auto; }` keeps images responsive while the attributes still reserve space.</En>
<Ur>`width` aur `height` (pixels, bina units) download se pehle browser ko tasveer ka **tanasub (aspect ratio)** dete hain. In ke baghair koi jagah nahi rakhi jati, aur tasveer aate hi neeche sab uchhal jata hai: **Cumulative Layout Shift**, ek Core Web Vital jo ghalat taps karata aur ranking girata hai. Har `<img>` aur `<video>` par dein; CSS `img { max-width: 100%; height: auto; }` tasveeron ko responsive rakhta hai jabke attributes jagah phir bhi rakhte hain.</Ur>
</Tr>

```html preview h=230 noqa
<style>img { max-width: 100%; height: auto; background: #eee; }</style>
<p>Without width/height:</p>
<img src="missing-banner.jpg" alt="Summer sale banner">
<p>With width="800" height="200" (space reserved at 4:1):</p>
<img src="missing-banner.jpg" alt="Summer sale banner" width="800" height="200">
<p>Text below the images.</p>
```

<Happened>
<Tr>
<En>The `<style>` made images responsive with a grey background so the reserved box is visible. The first image has no dimensions, so it takes almost no space and content below would jump when it loads. The second keeps a 4:1 box from the start, even though its file doesn't exist, and the text below never moves.</En>
<Ur>`<style>` ne tasveeron ko responsive aur saleti background wala banaya taa ke rakhi gayi jagah dikhe. Pehli tasveer ke dimensions nahi, isliye wo taqreeban koi jagah nahi leti aur load par neeche ka mawad uchhalta. Doosri shuru se 4:1 ka dabba rakhti hai, chahe file maujood nahi, aur neeche ka text kabhi nahi hilta.</Ur>
</Tr>
</Happened>

</Step>

<Step title="Lazy loading and loading priority">

<Tr>
<En>

`loading="lazy"` delays images and iframes until the user scrolls near them, saving data and speeding up the first view. Use it **below the fold**, **never** on the main above-the-fold image (often the page's **LCP**, Largest Contentful Paint), which should get `fetchpriority="high"`. `decoding="async"` lets the browser decode without blocking. All native, no library.

```text
<!-- hero image: visible immediately, load it first -->
<img src="/img/hero-mangoes.jpg" alt="Crates of fresh mangoes at the farm"
     width="1200" height="600" fetchpriority="high">

<!-- product grid further down: load when the user scrolls near -->
<img src="/img/kent.jpg" alt="Kent mangoes" width="400" height="400" loading="lazy" decoding="async">
<img src="/img/keitt.jpg" alt="Keitt mangoes" width="400" height="400" loading="lazy" decoding="async">
```

</En>
<Ur>

`loading="lazy"` tasveeron aur iframes ko tab tak rokta hai jab tak user un ke qareeb scroll na kare, data bachata aur pehla nazara tez karta hai. Ise **fold ke neeche** lagayen, upar wali bari tasveer par **kabhi nahi** (aksar page ka **LCP**, Largest Contentful Paint), jise `fetchpriority="high"` milna chahiye. `decoding="async"` browser ko bina rukawat decode karne deta hai. Sab asli, koi library nahi.

```text
<!-- hero image: visible immediately, load it first -->
<img src="/img/hero-mangoes.jpg" alt="Crates of fresh mangoes at the farm"
     width="1200" height="600" fetchpriority="high">

<!-- product grid further down: load when the user scrolls near -->
<img src="/img/kent.jpg" alt="Kent mangoes" width="400" height="400" loading="lazy" decoding="async">
<img src="/img/keitt.jpg" alt="Keitt mangoes" width="400" height="400" loading="lazy" decoding="async">
```

</Ur>
</Tr>

</Step>

<Step title="Responsive images: srcset and sizes">

<Tr>
<En>`srcset` lists versions of one image with their widths (`mango-400.jpg 400w, ...`); `sizes` says how wide it will be **displayed** (`100vw`, or rules like `(min-width: 900px) 50vw, 100vw`). The browser picks the smallest file that looks sharp, so a phone on 4G doesn't download a 1600-pixel image to show it at 375. `src` stays as the fallback, and image CDNs (Cloudinary, imgix, Next.js Image) generate the sizes. Below, a real browser loads one page at different widths and pixel densities, and we ask which file it chose (`currentSrc`).</En>
<Ur>`srcset` ek tasveer ke versions un ki chaurai ke saath list karta hai (`mango-400.jpg 400w, ...`); `sizes` batata hai wo kitni chauri **dikhayi** jayegi (`100vw`, ya `(min-width: 900px) 50vw, 100vw` jaise qawaid). Browser sab se chhoti file chunta hai jo saaf dikhe, isliye 4G par phone 375 par dikhane ke liye 1600-pixel tasveer download nahi karta. `src` fallback rehta hai, aur image CDNs (Cloudinary, imgix, Next.js Image) sizes khud banate hain. Neeche asli browser ek page alag chaurai aur pixel density par kholta hai, aur hum poochhte hain us ne kaun si file chuni (`currentSrc`).</Ur>
</Tr>

```bash
python3 - <<'PY'
import pathlib
from playwright.sync_api import sync_playwright
for w in (400, 800, 1600):                        # three versions of the "same" image
    pathlib.Path(f"mango-{w}.svg").write_text(
```

<Step title="picture: modern formats and art direction">

<Tr>
<En>

`<picture>` holds `<source>`s the browser checks in order, then an `<img>` fallback. Sources can choose by **format** (`type="image/avif"`) or **media query** (a different crop on phones). AVIF and WebP are often 30–50% smaller than JPEG at the same quality, and unsupported browsers fall back automatically. The inner `<img>` is what's displayed and carries `alt`, `width`, `height` and `loading`. List the most efficient format first.

```text
<picture>
  <source type="image/avif" srcset="/img/hero-800.avif 800w, /img/hero-1600.avif 1600w" sizes="100vw">
  <source type="image/webp" srcset="/img/hero-800.webp 800w, /img/hero-1600.webp 1600w" sizes="100vw">
  <source media="(max-width: 600px)" srcset="/img/hero-mobile-crop.jpg">
  <img src="/img/hero-1600.jpg" alt="Crates of fresh mangoes at the farm"
       width="1600" height="800" fetchpriority="high">
</picture>
```

| Format | Best for | Notes |
| --- | --- | --- |
| **AVIF** | Photos | Smallest; all modern browsers |
| **WebP** | Photos, transparent graphics | Small; universal modern support |
| **JPEG** | Photos (fallback) | Universal |
| **PNG** | Screenshots, exact pixels | Large for photos |
| **SVG** | Logos, icons, illustrations | Vector: sharp at any size, tiny |
| **GIF** | Avoid | Use `<video>` (MP4/WebM) for animations |

</En>

<Step title="Video and audio">

<Tr>
<En>

`<video>` and `<audio>` play media natively and accessibly. `controls` shows the player, `<source>` offers formats, and `<track>` adds captions or subtitles in **WebVTT**. Browsers block autoplay unless `muted`; background videos need `playsinline` and should respect reduced-motion users. `poster` shows an image before playing; `preload="metadata"` saves data. </video>

<Step title="Embedding other pages: iframe">

<Tr>
<En>

`<iframe>` shows another page inside yours: videos, maps, payment widgets, booking calendars. You get a feature for free, but you're running someone else's code, so restrict it:

- `title` describes it for screen readers (required).
- `loading="lazy"` defers heavy off-screen embeds.
- `sandbox` removes **all** powers (scripts, forms, popups, same-origin) unless you add them back.
- `allow` controls camera, geolocation, fullscreen, payment; `referrerpolicy` limits shared URL data.

```text
<iframe
  src="https://www.youtube-nocookie.com/embed/VIDEO_ID"
  title="How to choose a ripe mango (video)"
  width="560" height="315"
  loading="lazy"
  allow="accelerometer; encrypted-media; gyroscope; picture-in-picture; fullscreen"
  referrerpolicy="strict-origin-when-cross-origin">
</iframe>

<iframe
  src="https://widgets.example.com/user-content/123"
  title="Customer-submitted recipe preview"
  sandbox="allow-scripts"
  loading="lazy" width="600" height="400">
</iframe>
```

The YouTube embed uses the privacy-enhanced domain and only the features the player needs. The untrusted one may run scripts but has no same-origin access: it can't read your cookies, submit forms, open popups or navigate your page. Protect **your** pages from being framed (clickjacking) with CSP `frame-ancestors` or `X-Frame-Options`.

</En>
<Ur>

`<iframe>` aap ke page me doosra page dikhata hai: videos, maps, payment widgets, booking calendars. Khoobi muft milti hai, lekin aap kisi aur ka code chala rahe hain, isliye hadd lagayen:

- `title` screen readers ke liye bayan (lazmi).
- `loading="lazy"` screen se bahar bhari embeds rokta hai.
- `sandbox` **saari** taqatein hata deta hai (scripts, forms, popups, same-origin) jab tak aap wapas na den.
- `allow` camera, location, fullscreen, payment par qaboo; `referrerpolicy` URL ki maloomat mehdood karta hai.


<Compare>

More mistakes to avoid:

- **Alt text like "image" or the file name**, or describing decorative images.

## Remember

<Takeaways>
<Tr>
<En>

- Root-relative links for your site, absolute for others, fragments for sections.
- Link text describes the destination; never "click here".
- New tabs sparingly, with a warning and `rel="noopener"`.

<DeepDive title="Real world: a homepage that scored 31">

A fashion e-commerce site had a beautiful homepage but a Lighthouse performance score of 31 on mobile. The audit showed a 4.2 MB PNG hero served to every phone, 60 product images loading at once, no `width`/`height` (CLS 0.4, with buttons jumping as images loaded), and a 6 MB GIF "sale" banner. Fixes, all in HTML: the hero became a `<picture>` with AVIF/WebP, four `srcset` widths and `fetchpriority="high"`; product images got dimensions, `loading="lazy"` and `srcset`; the GIF became a 400 KB muted looping MP4; and image-only links got proper `alt`. Mobile LCP dropped from 7 seconds to under 2.5, CLS to almost zero, and mobile conversion rose. The screen-reader link list changed from 30 unnamed links to clear product names.

</DeepDive>

<DeepDive title="Security lens">

Links and embeds connect your page to other origins. Validate URLs you didn't write, restrict what embedded content can do, and treat user-uploaded media as untrusted.

- **Untrusted URLs:** if users can submit links, allow only `http:`/`https:` (maybe `mailto:`). `javascript:alert(document.cookie)` is XSS. Add `rel="nofollow ugc"` to user links.
- **Open redirects:** `/redirect?to=https://evil.example` on your trusted domain is a phishing tool; redirect only to allow-listed destinations.
- **Reverse tabnabbing:** `rel="noopener"` for new-tab links.
- **Clickjacking:** `Content-Security-Policy: frame-ancestors 'self'` (or `X-Frame-Options: DENY`).
- **Sandbox embeds:** never combine `allow-scripts` with `allow-same-origin` for content from your own origin; that lets the frame remove its sandbox.
- **User uploads:** SVG can contain JavaScript. Serve uploads from a separate domain with content-type checks, or convert SVG to PNG; strip EXIF metadata (it can contain GPS location).
- **Privacy:** third-party images and embeds let those sites track visitors; self-host or use privacy-enhanced embeds.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How do you write good alt text?">
Describe the information or function the image provides in context, concisely and without starting with phrases like image of. Use an empty alt attribute for purely decorative images so assistive technologies skip them, describe the destination or action for images used as links or buttons, and provide longer text alternatives nearby for complex images like charts.
</QA>

<QA q="Why should images have width and height attributes?">
They let the browser compute the aspect ratio and reserve space before the image downloads, preventing content from jumping as images load. This reduces Cumulative Layout Shift, a Core Web Vital. With CSS such as max-width 100 percent and height auto, images remain responsive.
</QA>

<QA q="What do srcset and sizes do?">
srcset lists alternative image files with their intrinsic widths or pixel densities, and sizes tells the browser how wide the image will be displayed under different conditions. The browser combines this with the viewport and device pixel ratio to download the smallest file that will look sharp, saving bandwidth on small screens.
</QA>

<QA q="When should you use loading lazy?">
For images and iframes below the fold that the user may not scroll to immediately, to save bandwidth and speed up the initial load. It should not be used on the main above-the-fold image, which is often the Largest Contentful Paint element and should be loaded early, optionally with fetchpriority high.
</QA>

<QA q="What security considerations apply to iframes?">
Embedding third-party content runs someone else's code in your page, so use the sandbox attribute to remove capabilities and the allow attribute to limit features like camera or geolocation, set a referrer policy, and lazy-load heavy embeds. To protect your own pages from being framed for clickjacking, send a frame-ancestors Content Security Policy or X-Frame-Options header.
</QA>

</DeepDive>

<DeepDive title="More practice">

1. Audit a page you've built: list every link and image, and fix link and alt text that don't make sense on their own.
2. Export one photo at 400/800/1600 px as WebP and JPEG, build a `<picture>` with `srcset` and `sizes`, and check which file loads in DevTools → Network at different device sizes.
3. Run Lighthouse before and after adding `width`/`height` and `loading="lazy"`, and compare CLS and LCP.
4. Convert a GIF to MP4 (`ffmpeg -i anim.gif -movflags faststart -pix_fmt yuv420p anim.mp4`) and replace it with a muted looping `<video>`.
5. Write a WebVTT caption file for a short video and add it with `<track>`.
6. Embed a YouTube video and a map with `title`, `loading="lazy"` and minimal `allow` permissions.

</DeepDive>
