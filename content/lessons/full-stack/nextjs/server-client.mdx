<BigIdea>
<Tr>
<En>
A Next.js app runs in **two places**: on the **server** (a computer you control) and in the user's **browser**. In the App Router, every component is a **Server Component** unless you say otherwise. Server Components run **only on the server**: they can be `async`, read a database or a secret API key directly, and their code is **never sent** to the browser, only the HTML they produce. When a component needs **interactivity** (state with `useState`, effects, click handlers, or browser things like `window` and `localStorage`), you put **`"use client"`** at the top of its file. That makes it a **Client Component**: it's still rendered to HTML on the server first, but its JavaScript is also sent to the browser so it can respond to the user. The usual pattern: **pages and data loading on the server, small interactive pieces on the client**, with data passed down as props.
</En>
<Ur>
Next.js app **do jagah** chalti hai: **server** par (aap ke qaboo wala computer) aur user ke **browser** me. App Router me har component **Server Component** hota hai jab tak aap kuch aur na kahein. Server Components **sirf server par** chalte hain: ye `async` ho sakte hain, database ya secret API key seedha parh sakte hain, aur in ka code browser ko **kabhi nahi bheja** jata, sirf in ka banaya hua HTML. Jab kisi component ko **interactivity** chahiye (`useState` wali state, effects, click handlers, ya `window` aur `localStorage` jaisi browser ki cheezen), aap us ki file ke upar **`"use client"`** likhte hain. Ye use **Client Component** bana deta hai: ye ab bhi pehle server par HTML banta hai, magar is ki JavaScript browser ko bhi bheji jati hai taa ke ye user ko jawab de sake. Aam namoona: **pages aur data loading server par, chhote interactive tukre client par**, aur data props ki shakal me neeche bheja jata hai.
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>
<Tr>
<En>

| | Server Component (default) | Client Component (`"use client"`) |
| --- | --- | --- |
| Runs on | Server only | Server (first HTML) **and** browser |
| Code sent to browser | **No** | Yes |
| `async` / `await` data in the component | **Yes** | No (use a server parent, or a library) |
| Database, secrets, files | **Yes** | **Never** |
| `useState`, `useEffect`, `useRef` | No | **Yes** |
| `onClick`, `onChange`, forms with live feedback | No | **Yes** |
| `window`, `localStorage`, `usePathname` | No | **Yes** |

</En>
<Ur>

| | Server Component (default) | Client Component (`"use client"`) |
| --- | --- | --- |
| Kahan chalta hai | Sirf server | Server (pehla HTML) **aur** browser |
| Code browser ko jata hai | **Nahi** | Haan |
| Component me `async` / `await` data | **Haan** | Nahi (server parent lein, ya library) |
| Database, secrets, files | **Haan** | **Kabhi nahi** |
| `useState`, `useEffect`, `useRef` | Nahi | **Haan** |
| `onClick`, `onChange`, zinda jawab dene wale forms | Nahi | **Haan** |
| `window`, `localStorage`, `usePathname` | Nahi | **Haan** |

</Ur>
</Tr>
</What>
<Why>
<Tr>
<En>

- **Less JavaScript for users.** Server Component code stays on the server, so pages load faster, especially on phones and slow networks.
- **Simpler data loading.** `const products = await getProducts()` right in the component: no `useEffect`, no loading flags, no API in between.
- **Safety.** Database queries and secret keys live in code the browser never receives.
- **Interactivity where it's needed.** Buttons, forms and menus still work, because those few components are Client Components.

</En>
<Ur>

- **Users ke liye kam JavaScript.** Server Component ka code server par rehta hai, isliye pages tez load hote hain, khaas taur par phones aur sust networks par.
- **Data load karna aasan.** Component me hi `const products = await getProducts()`: na `useEffect`, na loading ke nishaan, na beech me API.
- **Hifazat.** Database queries aur secret keys aise code me rehti hain jo browser ko kabhi nahi milta.
- **Jahan zaroorat ho wahan interactivity.** Buttons, forms aur menus phir bhi chalte hain, kyun ke wo chand components Client Components hain.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

Ask one question about each component: **"Does it need to respond to the user in the browser?"**

- **No** (shows data, layout, text, lists, product details) → keep it a **Server Component**.
- **Yes** (clicks, typing, toggles, timers, reading the current URL in the browser, `localStorage`) → make **that piece** a **Client Component**, as small as possible.

</En>
<Ur>

Har component ke baare me ek sawal poochein: **"Kya ise browser me user ko jawab dena hai?"**

- **Nahi** (data, layout, text, lists, product ki tafseel dikhata hai) → ise **Server Component** rehne dein.
- **Haan** (clicks, typing, toggles, timers, browser me maujooda URL parhna, `localStorage`) → **sirf wo tukra** **Client Component** banayen, jitna chhota ho sake.

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

```tsx
// app/products/page.tsx: a Server Component (no directive)
import { getProducts } from "@/lib/db";
import AddToCart from "@/app/components/AddToCart";

export default async function ProductsPage() {
  const products = await getProducts();          // runs on the server
  return products.map((p) => <AddToCart key={p.id} name={p.name} />);
}

// app/components/AddToCart.tsx: a Client Component
"use client";
import { useState } from "react";
export default function AddToCart({ name }: { name: string }) { /* useState, onClick */ }
```

</En>
<Ur>

```tsx
// app/products/page.tsx: Server Component (koi directive nahi)
import { getProducts } from "@/lib/db";
import AddToCart from "@/app/components/AddToCart";

export default async function ProductsPage() {
  const products = await getProducts();          // server par chalta hai
  return products.map((p) => <AddToCart key={p.id} name={p.name} />);
}

// app/components/AddToCart.tsx: Client Component
"use client";
import { useState } from "react";
export default function AddToCart({ name }: { name: string }) { /* useState, onClick */ }
```

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of a **restaurant**.

- The **kitchen** is the **server**. The chef has the recipes, the pantry and the supplier's account numbers. Guests never go into the kitchen; they only receive the finished plates. **Server Components** are dishes made entirely in the kitchen: the guest gets the food (the HTML), never the recipe (the code) or the pantry key (the secrets).
- Some dishes need a final touch **at the table**: a waiter flambés a dessert, or the guest adds their own sauce. Those are **Client Components**. The plate is prepared in the kitchen first (server-rendered HTML), then **finished at the table** (JavaScript running in the browser).
- `"use client"` is the label on the order slip that says "**this part is finished at the table**". Anything on that plate goes out to the dining room, so you'd never put the supplier's account book on it.

</En>
<Ur>

Ek **restaurant** ka sochein.

- **Kitchen** **server** hai. Chef ke paas recipes, godaam aur supplier ke account numbers hain. Mehmaan kabhi kitchen me nahi jate; unhe sirf tayyar plates milti hain. **Server Components** poori tarah kitchen me bani dishes hain: mehmaan ko khana (HTML) milta hai, recipe (code) ya godaam ki chabi (secrets) kabhi nahi.
- Kuch dishes ko **mez par** aakhri touch chahiye: waiter dessert par aag lagata hai, ya mehmaan apni chatni dalta hai. Ye **Client Components** hain. Plate pehle kitchen me tayyar hoti hai (server par bana HTML), phir **mez par mukammal** hoti hai (browser me chalti JavaScript).
- `"use client"` order ki parchi par laga label hai jo kehta hai "**ye hissa mez par mukammal hota hai**". Us plate par jo kuch ho wo dining hall me jata hai, isliye aap supplier ki account book kabhi us par na rakhen.

</Ur>
</Tr>

<Step title="A Server Component loads its own data">

<Tr>
<En>
Pages are Server Components by default, so they can be **`async`** and `await` data directly. Here the data comes from `lib/db.ts`, which stands in for a real database.
</En>
<Ur>
Pages default me Server Components hote hain, isliye ye **`async`** ho sakte hain aur seedha data ka `await` kar sakte hain. Yahan data `lib/db.ts` se aata hai, jo asli database ki jagah hai.
</Ur>
</Tr>

```tsx
// lib/db.ts
import "server-only";

const products = [
  { id: 1, name: "Notebook", price: 5 },
  { id: 2, name: "Desk lamp", price: 30 },
  { id: 3, name: "Mug", price: 8.5 },
];

export async function getProducts() {
  console.log("getProducts ran on the server, key starts with", process.env.STRIPE_SECRET_KEY?.slice(0, 7));
  return products;
}
```

```text
Server terminal (where `next start` runs), when /products is requested:
getProducts ran on the server, key starts with sk_live
```

<Happened>
<Tr>
<En>

- The `console.log` appeared in the **server's terminal**, not in the browser's console. That's how you can tell where code runs.
- The function read `process.env.STRIPE_SECRET_KEY`, a secret that must never reach users. In a Server Component that's safe.
- `import "server-only"` at the top is a guard: if any client code ever imports this file, the build fails (step 7 shows it).
- In a real app, `getProducts` would query PostgreSQL or Supabase with a server-side key.

</En>
<Ur>

- `console.log` **server ke terminal** me nazar aaya, browser ke console me nahi. Isi se pata chalta hai ke code kahan chalta hai.
- Function ne `process.env.STRIPE_SECRET_KEY` parhi, aisa raaz jo users tak kabhi nahi pohanchna chahiye. Server Component me ye mehfooz hai.
- Upar `import "server-only"` ek pehredaar hai: agar koi client code is file ko import kare to build nakaam hota hai (qadam 7 dikhata hai).
- Asli app me `getProducts` server ki key ke saath PostgreSQL ya Supabase se query karta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The page uses the data, no useEffect needed">

<Tr>
<En>
The products page just awaits the data and renders it. Compare this with the useEffect lesson: no loading state, no `fetch` in the browser, no race conditions.
</En>
<Ur>
Products page bas data ka `await` karta hai aur use dikhata hai. Is ka useEffect lesson se muqabla karein: na loading ki state, na browser me `fetch`, na race conditions.
</Ur>
</Tr>

```tsx
// app/products/page.tsx  (Server Component: no directive)
import { getProducts } from "@/lib/db";
import AddToCart from "@/app/components/AddToCart";
import Collapsible from "@/app/components/Collapsible";

export const dynamic = "force-dynamic";

export default async function ProductsPage() {
  const products = await getProducts();
  return (
    <>
      <h1>Products</h1>
      <ul>
        {products.map((p) => (
          <li key={p.id}>
            {p.name} — ${p.price.toFixed(2)} <AddToCart name={p.name} />
          </li>
        ))}
      </ul>
      <Collapsible title="delivery info">
        <p>Rendered on the server at request time: {products.length} products in stock.</p>
      </Collapsible>
      <p>Public setting: {process.env.NEXT_PUBLIC_STORE_NAME}</p>
    </>
  );
}
```

```text
The page in the browser (after clicking "Add Mug" twice and "Show delivery info"):
Products
Notebook — $5.00 Add Notebook (0 in cart)
Desk lamp — $30.00 Add Desk lamp (0 in cart)
Mug — $8.50 Add Mug (2 in cart)
Hide delivery info
Rendered on the server at request time: 3 products in stock.
Public setting: Fresh Mart Austin
```

<Happened>
<Tr>
<En>

- The product list arrived as **finished HTML**: it's visible even before any JavaScript runs, which is great for speed and for search engines.
- `export const dynamic = "force-dynamic"` makes Next.js run this page on every request (useful when data changes often). Without it, this page would be built once at build time.
- `AddToCart` and `Collapsible` are Client Components (next steps), placed **inside** a Server Component page. That mix is normal and encouraged.

</En>
<Ur>

- Products ki list **tayyar HTML** ki shakal me aayi: ye koi bhi JavaScript chalne se pehle nazar aati hai, jo raftaar aur search engines ke liye behtareen hai.
- `export const dynamic = "force-dynamic"` Next.js se ye page har request par chalwata hai (jab data aksar badle to mufeed). Is ke baghair ye page build ke waqt ek dafa banta.
- `AddToCart` aur `Collapsible` Client Components hain (agle qadam), Server Component page ke **andar** rakhe gaye. Ye milawat aam hai aur is ki hosla afzai ki jati hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Secrets and server code never reach the browser">

<Tr>
<En>
After building, we searched the JavaScript files that are sent to the browser (`.next/static`) and the page's HTML for the secret key and for the server-only code.
</En>
<Ur>
Build ke baad humne browser ko bheji jane wali JavaScript files (`.next/static`) aur page ke HTML me secret key aur sirf server wala code dhoonda.
</Ur>
</Tr>

```text
$ grep -rl "TOPSECRET" .next/static | wc -l           # the secret key's value
0
$ grep -rl "getProducts ran" .next/static | wc -l     # code from lib/db.ts
0
$ curl -s localhost:3000/products | grep -c TOPSECRET  # the page's HTML
0
$ grep -rl "in cart" .next/static | wc -l             # code from the AddToCart client component
1
```

<Happened>
<Tr>
<En>

- The secret key (we set it to a value containing `TOPSECRET`) appears in **no** browser file and not in the HTML.
- The server function's code isn't in the browser files either: the browser only got the **result** (the product list).
- `AddToCart`'s code **is** in a browser file, because it's a Client Component and must run there.
- This is the core safety rule: **anything in a Client Component, or imported by one, is public.**

</En>
<Ur>

- Secret key (jis ki value me humne `TOPSECRET` rakha) **kisi** browser file me nahi, aur HTML me bhi nahi.
- Server function ka code bhi browser files me nahi: browser ko sirf **nateeja** (products ki list) mila.
- `AddToCart` ka code browser file me **hai**, kyun ke ye Client Component hai aur use wahan chalna hai.
- Hifazat ka asal qaida yahi hai: **Client Component me, ya us ki import ki hui har cheez public hai.**

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Hooks and events need a Client Component">

<Tr>
<En>
What happens if a Server Component tries to use state? We made a page with `useState` and no directive, and ran the build.
</En>
<Ur>
Kya hota hai agar Server Component state istemal karne ki koshish kare? Humne `useState` wala page baghair directive ke banaya aur build chalaya.
</Ur>
</Tr>

```tsx
// app/broken/page.tsx  (no "use client")
import { useState } from "react";

export default function CounterPage() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
```

```text
> Build error occurred
./app/broken/page.tsx:1:10
Error: You're importing a module that depends on `useState` into a React Server Component
module. This API is only available in Client Components. To fix, mark the file (or its
parent) with the `"use client"` directive.
> 1 | import { useState } from "react";
    |          ^^^^^^^^
```

<Happened>
<Tr>
<En>

- The build stopped and pointed at the exact import. A Server Component runs once on the server to produce HTML; there's no "later" for state to change in, so state, effects and refs aren't available.
- The same applies to `useEffect`, `useRef`, `useContext` and to browser globals like `window` and `localStorage`.
- The message tells you the fix: add `"use client"`. But put it on the **smallest** component that needs it, not on the whole page (next step).

</En>
<Ur>

- Build ruk gaya aur bilkul us import ki taraf ishara kiya. Server Component HTML banane ke liye server par ek dafa chalta hai; state ke badalne ke liye koi "baad me" nahi, isliye state, effects aur refs dastyab nahi.
- `useEffect`, `useRef`, `useContext` aur `window` aur `localStorage` jaise browser globals par bhi yahi lagu hai.
- Paighaam hal batata hai: `"use client"` jorein. Magar ise **sab se chhote** zaroori component par lagayen, poore page par nahi (agla qadam).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The use client directive: an interactive piece">

<Tr>
<En>
Put `"use client"` as the **very first line** of the file. Everything in that file now works like the React you learned: state, events, effects.
</En>
<Ur>
`"use client"` file ki **bilkul pehli line** par likhein. Ab us file ki har cheez us React ki tarah chalti hai jo aap ne seekha: state, events, effects.
</Ur>
</Tr>

```tsx
// app/components/AddToCart.tsx
"use client";

import { useState } from "react";

export default function AddToCart({ name }: { name: string }) {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      Add {name} ({count} in cart)
    </button>
  );
}
```

<Happened>
<Tr>
<En>

- On the first request, the server rendered each button as HTML showing "(0 in cart)". Then the browser downloaded `AddToCart`'s JavaScript and **hydrated** the buttons: React attached the click handlers to the HTML that was already on screen.
- Clicking "Add Mug" twice changed only that button to "(2 in cart)", as you saw in step 2. Each button has its own state.
- The page around it stayed a Server Component, so the product data and the database code never went to the browser.

</En>
<Ur>

- Pehli request par server ne har button ko "(0 in cart)" dikhane wale HTML ki shakal me banaya. Phir browser ne `AddToCart` ki JavaScript download ki aur buttons ko **hydrate** kiya: React ne pehle se screen par maujood HTML se click handlers jor diye.
- "Add Mug" do dafa click karne se sirf wahi button "(2 in cart)" bana, jaisa aap ne qadam 2 me dekha. Har button ki apni state hai.
- Gird ka page Server Component raha, isliye products ka data aur database ka code kabhi browser tak nahi gaya.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Passing data across the boundary">

<Tr>
<En>
A Server Component can render a Client Component and pass it **props**. Those props travel from server to browser over the network, so they must be **serializable**: strings, numbers, booleans, plain objects and arrays, dates, promises. **Functions can't be sent.**
</En>
<Ur>
Server Component Client Component bana kar use **props** de sakta hai. Ye props network par server se browser tak safar karte hain, isliye inhe **serializable** hona chahiye: strings, numbers, booleans, saade objects aur arrays, dates, promises. **Functions nahi bheje ja sakte.**
</Ur>
</Tr>

```tsx
// app/broken/page.tsx  (Server Component)
export default function Page() {
  return <button onClick={() => console.log("clicked")}>Click me</button>;
}
```

```text
Error occurred prerendering page "/broken".
Error: Event handlers cannot be passed to Client Component props.
  {onClick: function onClick, children: ...}
Export encountered an error on /broken/page: /broken, exiting the build.
```

<Happened>
<Tr>
<En>

- A `<button>` with `onClick` needs JavaScript in the browser, but this function only exists on the server; there's no way to ship it. The build refused.
- The fix is to move the button into a Client Component, like `AddToCart`, and pass only **data** to it (`name={p.name}`).
- Pass **only what the client needs**. Passing a whole database row (`user={user}`) sends every field, including private ones, to the browser.

</En>
<Ur>

- `onClick` wale `<button>` ko browser me JavaScript chahiye, magar ye function sirf server par maujood hai; use bhejne ka koi tareeqa nahi. Build ne inkar kar diya.
- Hal ye hai ke button ko `AddToCart` jaise Client Component me le jayen, aur use sirf **data** dein (`name={p.name}`).
- **Sirf wahi dein jo client ko chahiye.** Poori database row (`user={user}`) dena har field browser ko bhej deta hai, private wali samet.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Client imports become client code (and server-only stops mistakes)">

<Tr>
<En>
`"use client"` marks a **boundary**: the file and **everything it imports** becomes part of the browser bundle. So if a client component imports your database module, that code would be shipped to every visitor. The `server-only` import turns that mistake into a build error.
</En>
<Ur>
`"use client"` ek **boundary** banata hai: file aur **us ki har import ki hui cheez** browser bundle ka hissa ban jati hai. Isliye agar client component aap ka database module import kare to wo code har visitor tak pohanch jata. `server-only` import is ghalti ko build error bana deta hai.
</Ur>
</Tr>

```tsx
// app/broken/PriceList.tsx
"use client";

import { getProducts } from "@/lib/db";

export default function PriceList() {
  return <button onClick={() => getProducts()}>Load prices</button>;
}
```

```text
> Build error occurred
./lib/db.ts:1:1
Error: You're importing a module that depends on "server-only". This API is only
available in Server Components in the App Router, ...
> 1 | import "server-only";
    | ^^^^^^^^^^^^^^^^^^^^^
Import traces:
  Client Component Browser:
    ./lib/db.ts [Client Component Browser]
    ./app/broken/PriceList.tsx [Client Component Browser]
```

<Happened>
<Tr>
<En>

- The import trace shows the path: `PriceList.tsx` (client) → `lib/db.ts`. Without the guard, the build would have succeeded and shipped your query code (and any secret read at module level) to the browser.
- Add `import "server-only"` (from the `server-only` package) to every file that touches the database, secrets or the file system.
- Keep `"use client"` files **small and at the leaves** of the tree: a button, a form, a menu. A `"use client"` at the top of a page turns everything it imports into browser code.
- To load data from a click, use a **Server Action** or an API route (the next lessons), not a direct import.

</En>
<Ur>

<Tr>

<Step title="Browser-only hooks: usePathname and friends">

<Tr>
<En>
Some Next.js hooks give you information about the browser's current state: **`usePathname`**, **`useSearchParams`**, **`useRouter`**. They're hooks, so they only work in Client Components. A classic use: highlight the current page in the nav.
</En>
<Ur>
Next.js ke kuch hooks browser ki maujooda halat ki maloomat dete hain: **`usePathname`**, **`useSearchParams`**, **`useRouter`**. Ye hooks hain, isliye sirf Client Components me chalte hain. Mashhoor istemal: nav me maujooda page ko numayan karna.
</Ur>

```tsx
// app/components/NavLink.tsx
"use client";

import Link from "next/link";
import { usePathname } from "next/navigation";

export default function NavLink({ href, children }: { href: string; children: React.ReactNode }) {
  const pathname = usePathname();
  const active = pathname === href;
  return (
    <Link href={href} style={{ fontWeight: active ? 700 : 400 }} aria-current={active ? "page" : undefined}>
      {children}
    </Link>
  );
}
```

<Tr>
<En>

- The root layout (a Server Component) can use `<NavLink href="/about">About</NavLink>` in place of `<Link>`; only `NavLink` becomes client code.

- In Server Components, use the page's `params` and `searchParams` props instead of these hooks.

</En>
<Ur>

- Root layout (Server Component) `<Link>` ki jagah `<NavLink href="/about">About</NavLink>` istemal kar sakta hai; sirf `NavLink` client code banta hai.
- Navigate karne par `usePathname()` update hota hai aur milta hua link bold ho jata hai. `aria-current="page"` screen readers ko batata hai ke kaun sa page active hai.
- Server Components me in hooks ke bajaye page ke `params` aur `searchParams` props lein.

<En>

## Common mistakes

<Compare>
<Bad title="use client on the whole page">

```tsx
"use client";
export default function ProductsPage() {
  // now the page can't await data, and everything it imports ships to the browser
}
```

</Bad>
<Good title="Server page, small client leaf">

```tsx
export default async function ProductsPage() {
  const products = await getProducts();
  return products.map((p) => <AddToCart key={p.id} name={p.name} />);
}
```

</Good>
</Compare>

<Compare>
<Bad title="A secret with the NEXT_PUBLIC_ prefix">

```text
NEXT_PUBLIC_OPENAI_API_KEY=sk-...
```

</Bad>
<Good title="Server-only variable, used on the server">

```text
OPENAI_API_KEY=sk-...    # read in a Server Component, route handler or server action
```

</Good>
</Compare>

<Compare>
<Bad title="Passing a whole record to a client component">

```tsx
<ProfileCard user={user} />   // sends email, passwordHash, role… to the browser
```

</Bad>
<Good title="Pass only what it shows">

```tsx
<ProfileCard name={user.name} avatarUrl={user.avatarUrl} />
```

</Good>
</Compare>

<Compare>
<Bad title="Fetching in useEffect what the server could load">

```tsx
"use client";
useEffect(() => { fetch("/api/products").then(…) }, []);
```

</Bad>
<Good title="Await it in a Server Component">

```tsx
const products = await getProducts();
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Putting `"use client"` below the imports.** It must be the first line (comments are allowed above it).
- **Using `window` or `localStorage` while rendering a Client Component.** It also renders on the server, where they don't exist; use them in `useEffect` or event handlers.
- **Importing database or secret modules into client files.** Add `import "server-only"` so the build catches it.
- **Assuming a Client Component never renders on the server.** It does, for the first HTML.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Imports ke neeche `"use client"` likhna.** Ye pehli line honi chahiye (us ke upar comments ki ijazat hai).
- **Client Component render karte waqt `window` ya `localStorage` istemal karna.** Ye server par bhi banta hai, jahan ye maujood nahi; inhe `useEffect` ya event handlers me istemal karein.
- **Database ya secret modules client files me import karna.** `import "server-only"` jorein taa ke build pakar le.
- **Ye samajhna ke Client Component kabhi server par nahi banta.** Banta hai, pehle HTML ke liye.

</Ur>
</Tr>

<DeepDive title="How it works under the hood">

**The RSC payload.** When a page renders, the server produces two things: HTML for the first paint, and the **React Server Components payload**, a compact description of the rendered tree with "holes" where Client Components go, plus their props. The browser uses the payload to hydrate Client Components and, on later navigations, to update the page without new HTML.

**Hydration mismatches.** A Client Component's server HTML must match its first browser render. Using `Date.now()`, `Math.random()`, `window.innerWidth` or locale-dependent formatting during render produces different output and a "hydration failed" warning. Move such values into `useEffect`, or render them only on the client.

**Server Actions.** A function marked `"use server"` can be passed to Client Components or used as a form `action`; React sends a reference, not the code, and calling it makes a request to the server. That's how a client button "calls" server code safely (its own lesson).

**Third-party components.** A library component that uses hooks but lacks `"use client"` fails when used in a Server Component. Re-export it from your own file that starts with `"use client"`.

**Context providers** use state, so they're Client Components. Wrap them in a small `Providers` client component and render it in the root layout around `{children}`: the children can still be Server Components.

**Streaming and Suspense.** Async Server Components can be wrapped in `<Suspense fallback={…}>` so slow parts stream in later while the rest of the page shows immediately; `loading.tsx` does this for whole routes.

**Caching.** Server Component output and `fetch` results can be cached and reused; the "Data Fetching and Caching" lesson explains when Next.js renders statically, dynamically, or revalidates.

</DeepDive>

<DeepDive title="Real world: the dashboard that shipped its database credentials">

A small team moved a dashboard to the App Router. To get a chart's hover effects working quickly, a developer added `"use client"` to the top of the **page** file. Everything kept working, so it went to production.

The page imported a `db.ts` helper that created a database client at module level using a connection string from `process.env.DATABASE_URL`. In client code, that variable was `undefined`, so the chart's data failed to load in the browser; to "fix" it, someone renamed the variable to `NEXT_PUBLIC_DATABASE_URL`. Now the connection string, with the database password, was in the JavaScript downloaded by every visitor. A security scanner that crawls public sites for credentials found it within days.

The fix and the rules that came out of it:

1. Rotate the database password immediately.
2. Make the page a Server Component again; move the chart into a small `"use client"` component that receives the data as props.
3. Add `import "server-only"` to every module that touches the database or secrets, so a client import becomes a build error.
4. A lint rule and code review checklist: **no secret ever gets a `NEXT_PUBLIC_` name**, and every `"use client"` is questioned: "Can this be smaller?"

</DeepDive>

<DeepDive title="Security lens">

The server/client split is a security boundary, so draw it deliberately.

- **Everything sent to a Client Component is public**: its code, its props and anything it imports. Treat props like an API response: send only safe fields.
- **Secrets stay in server-only modules**, never in `NEXT_PUBLIC_` variables. Guard those modules with `import "server-only"`.
- **Server Components still need authorization.** Check the session and the user's permissions before querying data; rendering on the server doesn't make data private if the page itself is reachable.
- **Server Actions are public endpoints.** Anyone can call them with any arguments, even if the button that uses them is hidden. Validate input and check permissions inside every action.
- **Taint APIs.** React offers `experimental_taintObjectReference` and `experimental_taintUniqueValue` to prevent specific objects or values (like a user record or a token) from ever being passed to the client; frameworks may enable them.
- **Hydration and user content.** Rendering user content is escaped by React on both server and client; avoid `dangerouslySetInnerHTML` with unsanitised data in either.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are React Server Components?">
Components that render only on the server. They can be async, access databases, file systems and secrets directly, and their code is not included in the client JavaScript bundle; only their rendered output is sent. In the Next.js App Router they are the default.
</QA>

<QA q="What does the use client directive do?">
It marks a file as the entry point to client code. The component and everything it imports are included in the browser bundle, rendered to HTML on the server for the initial load and then hydrated so they can use state, effects, event handlers and browser APIs.
</QA>

<QA q="When should a component be a Client Component?">
When it needs interactivity or browser-only features: useState, useEffect, useRef or context, event handlers, browser APIs such as localStorage or window, client navigation hooks, or third-party libraries that rely on them. Otherwise keep it a Server Component.
</QA>

<QA q="Can a Client Component render a Server Component?">
It cannot import one, because everything imported by a client file becomes client code. It can receive Server Components as children or other props from a Server Component parent, which renders them on the server and passes the result through.
</QA>

<QA q="What can be passed as props from a Server Component to a Client Component?">
Only serializable values, such as strings, numbers, booleans, null, plain objects and arrays, dates, Maps, Sets, promises and JSX. Functions cannot be passed, except Server Actions, which are sent as references.
</QA>

<QA q="How do environment variables behave in Next.js?">
All variables are available to server code through process.env. Only variables prefixed with NEXT_PUBLIC_ are inlined into client bundles at build time, so secrets must never use that prefix.
</QA>

</DeepDive>
