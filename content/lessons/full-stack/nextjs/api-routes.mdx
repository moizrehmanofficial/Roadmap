<BigIdea>
<Tr>
<En>
An **API** is a set of URLs that programs (not people) call to get or change data, usually exchanging **JSON**. In the Next.js App Router you build one with **route handlers**: a file named **`route.ts`** inside `app/`, usually under `app/api/`. Instead of a component, the file exports functions named after **HTTP methods**: `GET` to read, `POST` to create, `PATCH` or `PUT` to update, `DELETE` to remove. Each function receives the **request** and returns a **`Response`**, for example `Response.json(data, { status: 201 })`. Dynamic folders work just like pages: `app/api/products/[id]/route.ts` handles `/api/products/7`. Route handlers run **only on the server**, so they can use databases and secret keys. Because anyone can call them, every handler must **validate input**, **check permissions** and reply with an honest **status code**.
</En>
<Ur>
**API** URLs ka aisa set hai jise programs (log nahi) data lene ya badalne ke liye call karte hain, aam taur par **JSON** ka len den karte hue. Next.js App Router me ise **route handlers** se banaya jata hai: `app/` ke andar, aam taur par `app/api/` ke neeche, **`route.ts`** naam ki file. Component ke bajaye ye file **HTTP methods** ke naam wale functions export karti hai: parhne ke liye `GET`, banane ke liye `POST`, badalne ke liye `PATCH` ya `PUT`, hatane ke liye `DELETE`. Har function **request** leta hai aur **`Response`** wapas karta hai, maslan `Response.json(data, { status: 201 })`. Dynamic folders bilkul pages ki tarah chalte hain: `app/api/products/[id]/route.ts` `/api/products/7` sambhalta hai. Route handlers **sirf server par** chalte hain, isliye databases aur secret keys istemal kar sakte hain. Chunke inhe koi bhi call kar sakta hai, har handler ko **input validate** karna, **permissions check** karna aur imaandar **status code** ke saath jawab dena chahiye.
</Ur>
</Tr>

<En>

## Picture it

<Tr>
<En>

An API is a **restaurant's takeaway window**.

- The **menu board** lists what you can order: those are the **URLs** (`/api/products`, `/api/products/7`).
- **How** you order matters: "I'd like to **see** the menu" (`GET`), "I'd like to **place** an order" (`POST`), "Please **change** my order" (`PATCH`), "**Cancel** my order" (`DELETE`). Those are the **HTTP methods**.
- You hand over an order slip (the **request body**, in JSON) and sometimes show a membership card (a **header** like `Authorization`).
- The window always answers with a **numbered reply** (the **status code**) plus the food or a note: 200 "here you go", 201 "order created", 400 "we can't read your slip", 401 "members only", 404 "we don't have that", 500 "something broke in the kitchen".
- The staff behind the window (the **route handler**) checks every slip, because anyone can walk up to the window.

</En>
<Ur>

API ek **restaurant ki takeaway khirki** hai.

- **Menu board** batata hai ke kya order kiya ja sakta hai: ye **URLs** hain (`/api/products`, `/api/products/7`).
- Order **kaise** dete hain ye ahem hai: "Mujhe menu **dekhna** hai" (`GET`), "Mujhe order **dena** hai" (`POST`), "Mera order **badal** dein" (`PATCH`), "Mera order **cancel** kar dein" (`DELETE`). Ye **HTTP methods** hain.
- Aap order ki parchi dete hain (**request body**, JSON me) aur kabhi membership card dikhate hain (`Authorization` jaisa **header**).
- Khirki hamesha **number wale jawab** (**status code**) aur khane ya note ke saath jawab deti hai: 200 "ye lijiye", 201 "order ban gaya", 400 "aap ki parchi parhi nahi ja rahi", 401 "sirf members ke liye", 404 "ye hamare paas nahi", 500 "kitchen me kuch toot gaya".
- Khirki ke peechhe ka staff (**route handler**) har parchi check karta hai, kyun ke koi bhi khirki tak aa sakta hai.

</Ur>
</Tr>

<Step title="GET a list, with a query string">

<Tr>
<En>
`GET /api/products` returns the list. Options such as filters and page size come in the **query string**, which you read from `request.url`. Query values are always **text**, so convert and validate them.
</En>
<Ur>
`GET /api/products` list wapas karta hai. Filters aur page size jaise options **query string** me aate hain, jise aap `request.url` se parhte hain. Query ki values hamesha **text** hoti hain, isliye unhe badlein aur jaanchein.
</Ur>
</Tr>

```ts
// app/api/products/route.ts
import { products, newId } from "@/lib/store";

export function GET(request: Request) {
  const { searchParams } = new URL(request.url);
  const inStock = searchParams.get("inStock");
  const limit = Number(searchParams.get("limit") ?? 10);

  if (!Number.isInteger(limit) || limit < 1 || limit > 50) {
    return Response.json({ error: "limit must be a whole number from 1 to 50" }, { status: 400 });
  }

  let result = products;
  if (inStock === "true") result = result.filter((p) => p.inStock);

  return Response.json({ items: result.slice(0, limit), total: result.length });
}
```

```text
$ curl -s 'http://localhost:3000/api/products' -w '  [%{http_code}]'
{"items":[{"id":1,"name":"Notebook","price":5,"inStock":true},{"id":2,"name":"Desk lamp","price":30,"inStock":true},{"id":3,"name":"Backpack","price":45,"inStock":false}],"total":3}  [200]

$ curl -s 'http://localhost:3000/api/products?inStock=true&limit=1' -w '  [%{http_code}]'
{"items":[{"id":1,"name":"Notebook","price":5,"inStock":true}],"total":2}  [200]

$ curl -s 'http://localhost:3000/api/products?limit=500' -w '  [%{http_code}]'
{"error":"limit must be a whole number from 1 to 50"}  [400]
```

<Happened>
<Tr>
<En>

- With no options, all 3 products came back, plus a `total`.
- `?inStock=true&limit=1` filtered to the 2 in-stock products and returned only the first, while `total` still says 2 (so a client can build "page 1 of 2").
- `?limit=500` was rejected with **400 Bad Request** and a clear message. Without the check, a caller could ask for a million rows and slow down your server.
- `searchParams.get("inStock")` returns the **string** `"true"`, not a boolean, which is why we compare with `=== "true"`.

</En>
<Ur>

- Baghair options ke teeno products wapas aaye, saath `total`.
- `?inStock=true&limit=1` ne stock wale 2 products tak filter kiya aur sirf pehla wapas kiya, jabke `total` ab bhi 2 kehta hai (taa ke client "page 1 of 2" bana sake).
- `?limit=500` **400 Bad Request** aur saaf paighaam ke saath mustarad hua. Check ke baghair call karne wala das lakh rows maang kar aap ka server sust kar sakta tha.
- `searchParams.get("inStock")` **string** `"true"` wapas karta hai, boolean nahi, isi liye hum `=== "true"` se muqabla karte hain.

</Ur>

<Step title="GET one item with a dynamic segment">

<Tr>
<En>
For `/api/products/2`, put the handler in `app/api/products/[id]/route.ts`. The second argument to the handler contains **`params`**, a promise, just like in pages.
</En>
<Ur>
`/api/products/2` ke liye handler `app/api/products/[id]/route.ts` me rakhein. Handler ke doosre argument me **`params`** hota hai, ek promise, bilkul pages ki tarah.
</Ur>
</Tr>

```ts
// app/api/products/[id]/route.ts
import { products } from "@/lib/store";

type Context = { params: Promise<{ id: string }> };

function findIndex(id: string) {
  return products.findIndex((p) => p.id === Number(id));
}

export async function GET(_request: Request, { params }: Context) {
  const { id } = await params;
  const product = products[findIndex(id)];
  if (!product) return Response.json({ error: "Product not found" }, { status: 404 });
  return Response.json(product);
}
```

```text
$ curl -s http://localhost:3000/api/products/2 -w '  [%{http_code}]'
{"id":2,"name":"Desk lamp","price":30,"inStock":true}  [200]

$ curl -s http://localhost:3000/api/products/99 -w '  [%{http_code}]'
{"error":"Product not found"}  [404]
```

<Happened>
<Tr>
<En>

- `params.id` is the **string** `"2"`; `Number(id)` converts it before comparing with the numeric ids.
- A missing product returns **404 Not Found** with an error object, not a 200 with `null`. Clients can then react properly ("this product no longer exists").
- The first parameter is named `_request` because this handler doesn't use it; the underscore is a common signal for "unused".

</En>
<Ur>

- `params.id` **string** `"2"` hai; number wali ids se muqable se pehle `Number(id)` use badalta hai.
- Ghayab product **404 Not Found** aur error object ke saath wapas aata hai, `null` ke saath 200 nahi. Phir clients sahi jawab de sakte hain ("ye product ab maujood nahi").
- Pehle parameter ka naam `_request` hai kyun ke ye handler use istemal nahi karta; underscore "istemal nahi hua" ka aam ishara hai.

</Ur>
</Tr>
</Happened>

<Step title="POST: create, with authorisation and validation">

<Tr>
<En>
`POST /api/products` creates a product. It does three checks **in order**: is the caller allowed? Is the body valid JSON? Are the fields the right types? Only then does it save and reply **201 Created**.
</En>
<Ur>
`POST /api/products` product banata hai. Ye teen checks **tarteeb se** karta hai: kya call karne wale ko ijazat hai? Kya body sahi JSON hai? Kya fields ki types sahi hain? Tab hi ye mehfooz karta aur **201 Created** ke saath jawab deta hai.
</Ur>
</Tr>

```ts
// app/api/products/route.ts  (continued)
export async function POST(request: Request) {
  if (request.headers.get("authorization") !== `Bearer ${process.env.ADMIN_TOKEN}`) {
    return Response.json({ error: "Not authorised" }, { status: 401 });
  }

  let body: unknown;
  try {
    body = await request.json();
  } catch {
    return Response.json({ error: "Body must be valid JSON" }, { status: 400 });
  }

  const { name, price } = (body ?? {}) as { name?: unknown; price?: unknown };
  if (typeof name !== "string" || name.trim() === "" || typeof price !== "number" || price < 0) {
    return Response.json({ error: "name (text) and price (a number ≥ 0) are required" }, { status: 400 });
  }

  const product = { id: newId(), name: name.trim(), price, inStock: true };
  products.push(product);
  return Response.json(product, { status: 201 });
}
```

```text
$ curl -s -X POST http://localhost:3000/api/products \
    -H 'Content-Type: application/json' -d '{"name":"Mug","price":8.5}' -w '  [%{http_code}]'
{"error":"Not authorised"}  [401]

$ curl -s -X POST http://localhost:3000/api/products -H 'Authorization: Bearer let-me-in' \
    -H 'Content-Type: application/json' -d '{"name":"Mug","price":8.5}' -w '  [%{http_code}]'
{"id":4,"name":"Mug","price":8.5,"inStock":true}  [201]

$ curl -s -X POST http://localhost:3000/api/products -H 'Authorization: Bearer let-me-in' \
    -H 'Content-Type: application/json' -d '{"name":"","price":"free"}' -w '  [%{http_code}]'
{"error":"name (text) and price (a number ≥ 0) are required"}  [400]

$ curl -s -X POST http://localhost:3000/api/products -H 'Authorization: Bearer let-me-in' \
    -H 'Content-Type: application/json' -d '{name: Mug}' -w '  [%{http_code}]'
{"error":"Body must be valid JSON"}  [400]
```

<Happened>
<Tr>
<En>

- **No token → 401 Unauthorized.** The server was started with `ADMIN_TOKEN=let-me-in`, and the header must be `Authorization: Bearer let-me-in`. (Real apps check a logged-in user's session or a proper API key; this is the simplest version.)
- **Valid request → 201 Created**, and the reply contains the new product with the id the server assigned (4). Clients should use that, not invent ids.
- **Wrong types → 400**: an empty name and the text `"free"` as a price were both refused.
- **Broken JSON → 400**: `{name: Mug}` isn't valid JSON (keys and text need double quotes), so `request.json()` threw, and we caught it instead of crashing with a 500.
- `body` is typed as `unknown` (TypeScript lesson): we prove the shape before using it. A library such as **zod** does these checks in one line.

</En>
<Ur>

- **Token nahi → 401 Unauthorized.** Server `ADMIN_TOKEN=let-me-in` ke saath chalaya gaya tha, aur header `Authorization: Bearer let-me-in` hona chahiye. (Asli apps login user ka session ya durust API key check karti hain; ye sab se saada version hai.)
- **Sahi request → 201 Created**, aur jawab me naya product us id ke saath hai jo server ne di (4). Clients ko yahi istemal karni chahiye, apni ids nahi gharni chahiyen.
- **Ghalat types → 400**: khaali naam aur price ke taur par text `"free"` dono mustarad hue.
- **Toota JSON → 400**: `{name: Mug}` sahi JSON nahi (keys aur text ko double quotes chahiyen), isliye `request.json()` ne error phenka, aur humne 500 ke saath crash hone ke bajaye use pakar liya.
- `body` ki type `unknown` hai (TypeScript lesson): istemal se pehle hum shakal sabit karte hain. **zod** jaisi library ye checks ek line me karti hai.

</Ur>
</Tr>
</Happened>

<Step title="PATCH: change some fields">

<Tr>
<En>
`PATCH` updates **only the fields sent**. Validate each field that's present, keep the rest, and return the updated item.
</En>
<Ur>
`PATCH` **sirf bheji gayi fields** update karta hai. Har maujood field ko jaanchein, baqi waisi rakhein, aur update hua item wapas karein.
</Ur>
</Tr>

```ts
// app/api/products/[id]/route.ts  (continued)
export async function PATCH(request: Request, { params }: Context) {
  const { id } = await params;
  const index = findIndex(id);
  if (index === -1) return Response.json({ error: "Product not found" }, { status: 404 });

  const changes = (await request.json()) as { price?: unknown; inStock?: unknown };
  if (changes.price !== undefined && (typeof changes.price !== "number" || changes.price < 0)) {
    return Response.json({ error: "price must be a number ≥ 0" }, { status: 400 });
  }
  if (changes.inStock !== undefined && typeof changes.inStock !== "boolean") {
    return Response.json({ error: "inStock must be true or false" }, { status: 400 });
  }

  const updated = {
    ...products[index],
    ...(changes.price !== undefined && { price: changes.price }),
    ...(changes.inStock !== undefined && { inStock: changes.inStock }),
  };
  products[index] = updated;
  return Response.json(updated);
}
```

```text
$ curl -s -X PATCH http://localhost:3000/api/products/3 \
    -H 'Content-Type: application/json' -d '{"inStock":true,"price":40}' -w '  [%{http_code}]'
{"id":3,"name":"Backpack","price":40,"inStock":true}  [200]

$ curl -s -X PATCH http://localhost:3000/api/products/3 \
    -H 'Content-Type: application/json' -d '{"inStock":"yes"}' -w '  [%{http_code}]'
{"error":"inStock must be true or false"}  [400]
```

<Happened>
<Tr>
<En>

- The backpack's price and stock changed; its `name` and `id` were kept.
- We copy **only known fields** from the body. Writing `{ ...products[index], ...changes }` would let a caller overwrite anything they send, including `id` (a **mass assignment** bug).
- `"yes"` isn't a boolean, so it was rejected.
- For brevity, `PATCH` and `DELETE` here skip the authorisation check from `POST`. A real API must check it on **every** write (see the first challenge).

</En>
<Ur>

- Backpack ki price aur stock badle; us ka `name` aur `id` waisa raha.
- Hum body se **sirf jaani pehchani fields** copy karte hain. `{ ...products[index], ...changes }` likhna call karne wale ko jo bhi wo bheje us par likhne deta, `id` samet (**mass assignment** bug).
- `"yes"` boolean nahi, isliye mustarad hua.
- Ikhtisar ke liye yahan `PATCH` aur `DELETE` `POST` wala authorisation check chhor dete hain. Asli API ko ye **har** likhne wale kaam par check karna chahiye (pehla challenge dekhein).

</Ur>
</Tr>
</Happened>

<Step title="DELETE, and methods that don't exist">

<Tr>
<En>
`DELETE` removes the item and usually replies **204 No Content**: success, with an empty body. If a file doesn't export a method, Next.js answers **405 Method Not Allowed** for you.
</En>
<Ur>
`DELETE` item hata deta hai aur aam taur par **204 No Content** ke saath jawab deta hai: kamyabi, khaali body ke saath. Agar file koi method export na kare to Next.js aap ki taraf se **405 Method Not Allowed** jawab deta hai.
</Ur>
</Tr>

```ts
// app/api/products/[id]/route.ts  (continued)
export async function DELETE(_request: Request, { params }: Context) {
  const { id } = await params;
  const index = findIndex(id);
  if (index === -1) return Response.json({ error: "Product not found" }, { status: 404 });
  products.splice(index, 1);
  return new Response(null, { status: 204 });
}
```

</En>

<Step title="Status codes that tell the truth">

<Tr>
<En>

The status code is the first thing a client checks. Use the right family, and always send a JSON error message the client can show.

| Code | Name | Use it when |
| --- | --- | --- |
| **200** | OK | A read or update succeeded |
| **201** | Created | `POST` created something (return it) |
| **204** | No Content | Success with nothing to return (`DELETE`) |
| **400** | Bad Request | Invalid JSON, wrong types, missing fields, bad query values |
| **401** | Unauthorized | Not logged in / no valid credentials |
| **403** | Forbidden | Logged in, but not allowed to do this |
| **404** | Not Found | The thing doesn't exist (or the user mustn't know it exists) |
| **405** | Method Not Allowed | That method isn't supported on this URL |
| **409** | Conflict | Duplicate (email already registered), version clash |
| **422** | Unprocessable Content | Valid JSON, but breaks a business rule |
| **429** | Too Many Requests | Rate limit reached |
| **500** | Internal Server Error | A bug or an outage on your side |

</En>
<Ur>

Status code wo pehli cheez hai jo client check karta hai. Sahi khandan istemal karein, aur hamesha aisa JSON error message bhejein jo client dikha sake.

| Code | Naam | Kab istemal karein |
| --- | --- | --- |
| **200** | OK | Parhna ya update kamyab hua |
| **201** | Created | `POST` ne kuch banaya (use wapas karein) |
| **204** | No Content | Kamyabi magar wapas karne ko kuch nahi (`DELETE`) |
| **400** | Bad Request | Ghalat JSON, ghalat types, ghayab fields, ghalat query values |
| **401** | Unauthorized | Login nahi / durust credentials nahi |
| **403** | Forbidden | Login hai, magar ye karne ki ijazat nahi |
| **404** | Not Found | Cheez maujood nahi (ya user ko pata nahi chalna chahiye ke hai) |
| **405** | Method Not Allowed | Is URL par wo method nahi chalta |
| **409** | Conflict | Dohra (email pehle se registered), version ka takrao |
| **422** | Unprocessable Content | JSON sahi, magar business ka qaida torta hai |
| **429** | Too Many Requests | Rate limit tak pohanch gaye |
| **500** | Internal Server Error | Aap ki taraf bug ya bandish |

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- **2xx** = it worked, **4xx** = the caller did something wrong (they can fix it), **5xx** = the server did something wrong.
- Never reply **200** with `{ "error": … }` in the body: tools, monitoring and `response.ok` in `fetch` all rely on the status code.

</En>
<Ur>

- **2xx** = kaam ho gaya, **4xx** = call karne wale ne kuch ghalat kiya (wo theek kar sakta hai), **5xx** = server ne kuch ghalat kiya.
- Body me `{ "error": … }` ke saath kabhi **200** jawab na dein: tools, monitoring aur `fetch` me `response.ok` sab status code par chalte hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Calling your API from a page">

<Tr>
<En>
A Client Component calls the API with `fetch`, using a **relative URL** (same site, so no domain needed). Check `response.ok`, then read the JSON.
</En>
<Ur>
Client Component `fetch` se API call karta hai, **relative URL** ke saath (wahi site, isliye domain ki zaroorat nahi). `response.ok` check karein, phir JSON parhein.
</Ur>
</Tr>

```tsx
// app/components/StockToggle.tsx
"use client";

import { useState } from "react";

export default function StockToggle({ id, initial }: { id: number; initial: boolean }) {
  const [inStock, setInStock] = useState(initial);
  const [error, setError] = useState("");

  async function toggle() {
    setError("");
    const response = await fetch(`/api/products/${id}`, {
      method: "PATCH",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ inStock: !inStock }),
    });
    const data = await response.json();
    if (!response.ok) {
      setError(data.error ?? "Something went wrong");
      return;
    }
    setInStock(data.inStock);
  }

  return (
    <span>
      <button onClick={toggle}>{inStock ? "Mark sold out" : "Mark in stock"}</button>
      {error && <small role="alert"> {error}</small>}
    </span>
  );
}
```

<Happened>
<Tr>
<En>

- `method`, `headers` and `body` match what we sent with curl: `-X PATCH`, `-H 'Content-Type: …'`, `-d '…'`. `JSON.stringify` turns the object into JSON text.
- `response.ok` is `true` for 200–299. For 400 and 404, we show the server's error message.
- The new state comes from the **server's reply** (`data.inStock`), so the screen shows what was actually saved.
- **Don't call your own API from a Server Component.** A Server Component can import `lib/store` (or your database code) directly; going through HTTP to the same server adds a slow, pointless round trip.

</En>
<Ur>

- `method`, `headers` aur `body` wahi hain jo humne curl se bheje: `-X PATCH`, `-H 'Content-Type: …'`, `-d '…'`. `JSON.stringify` object ko JSON text me badalta hai.
- `response.ok` 200–299 ke liye `true` hai. 400 aur 404 par hum server ka error message dikhate hain.
- Nayi state **server ke jawab** (`data.inStock`) se aati hai, isliye screen wahi dikhati hai jo asal me mehfooz hua.
- **Server Component se apni hi API call na karein.** Server Component `lib/store` (ya aap ka database code) seedha import kar sakta hai; usi server tak HTTP ke zariye jana ek sust, bekaar chakkar jorta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Headers, cookies and caching">

<Tr>
<En>
Route handlers can read request headers and cookies, and set response headers. GET handlers run on **every request** by default (they show as `ƒ` in the build output), so the data is always fresh.
</En>
<Ur>
Route handlers request ke headers aur cookies parh sakte hain, aur response ke headers set kar sakte hain. GET handlers default me **har request par** chalte hain (build output me `ƒ` ki shakal me), isliye data hamesha taaza hota hai.
</Ur>
</Tr>

```ts
// app/api/me/route.ts
import { cookies, headers } from "next/headers";

export async function GET() {
  const cookieStore = await cookies();
  const session = cookieStore.get("session")?.value;
  const agent = (await headers()).get("user-agent");

  if (!session) {
    return Response.json({ error: "Not logged in" }, { status: 401 });
  }

  return Response.json(
    { session, agent },
    { headers: { "Cache-Control": "private, no-store" } }
  );
}
```

<Happened>
<Tr>
<En>

- `cookies()` and `headers()` from `next/headers` are async in Next.js 15+; you can also read `request.headers` directly from the handler's `request`.
- `Cache-Control: private, no-store` tells browsers and CDNs never to store this personal response.
- In our build, `/api/hello` and the product routes were all marked `ƒ` (dynamic). To cache a GET handler's result at build time, you'd opt in, for example with `export const dynamic = "force-static"` or `export const revalidate = 60`.

</En>
<Ur>

- `next/headers` ke `cookies()` aur `headers()` Next.js 15+ me async hain; aap handler ke `request` se seedha `request.headers` bhi parh sakte hain.
- `Cache-Control: private, no-store` browsers aur CDNs se kehta hai ke is zaati response ko kabhi mehfooz na karein.
- Hamare build me `/api/hello` aur product routes sab `ƒ` (dynamic) nishaan wale the. GET handler ka nateeja build ke waqt cache karna ho to aap ko khud chunna parta, maslan `export const dynamic = "force-static"` ya `export const revalidate = 60` se.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Trusting the body">

```ts
const body = await request.json();
products.push(body);          // any fields, any types, any size
```

</Bad>
<Good title="Validate, then copy known fields">

```ts
const { name, price } = await request.json();
if (typeof name !== "string" || typeof price !== "number") {
  return Response.json({ error: "Invalid product" }, { status: 400 });
}
products.push({ id: newId(), name, price, inStock: true });
```

</Good>
</Compare>

<Compare>
<Bad title="Errors with status 200">

```ts
return Response.json({ error: "Not found" });   // status 200
```

</Bad>
<Good title="Honest status codes">

```ts
return Response.json({ error: "Not found" }, { status: 404 });
```

</Good>
</Compare>

<Compare>
<Bad title="Letting JSON errors crash the handler">

```ts
const body = await request.json();   // throws on invalid JSON → 500
```

</Bad>
<Good title="Catch and reply 400">

```ts
let body: unknown;
try { body = await request.json(); }
catch { return Response.json({ error: "Body must be valid JSON" }, { status: 400 }); }
```

</Good>
</Compare>

<Compare>
<Bad title="A Server Component fetching its own API">

```tsx
const res = await fetch("http://localhost:3000/api/products");
```

</Bad>
<Good title="Call the data function directly">

```tsx
import { products } from "@/lib/store";   // or your database helper
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Checking permissions only on some methods.** Every write (`POST`, `PATCH`, `PUT`, `DELETE`) needs it.
- **Returning internal error details** (`error.stack`, SQL) to the client. Log them; send a generic message.
- **Storing data in module variables in production.** It's lost on restart and not shared between server instances.
- **No limits** on list sizes, body sizes or request rates.
- **Naming the file `route.tsx`** or putting it next to a `page.tsx` in the same folder.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Permissions sirf kuch methods par check karna.** Har likhne wale kaam (`POST`, `PATCH`, `PUT`, `DELETE`) ko ye chahiye.
- **Andaruni error ki tafseel client ko bhejna** (`error.stack`, SQL). Inhe log karein; aam paighaam bhejein.
- **Production me module variables me data rakhna.** Restart par kho jata hai aur server instances ke darmiyan share nahi hota.
- **Hadood ka na hona**: list ke size, body ke size ya requests ki raftaar par.
- **File ka naam `route.tsx` rakhna** ya use usi folder me `page.tsx` ke saath rakhna.

</Ur>
</Tr>

// lib/auth.ts
import "server-only";
import { timingSafeEqual } from "node:crypto";

export function isAdmin(request: Request): boolean {
  const expected = `Bearer ${process.env.ADMIN_TOKEN ?? ""}`;
  const given = request.headers.get("authorization") ?? "";
  if (!process.env.ADMIN_TOKEN || given.length !== expected.length) return false;
  return timingSafeEqual(Buffer.from(given), Buffer.from(expected));
}

// app/api/products/[id]/route.ts
import { isAdmin } from "@/lib/auth";

export async function DELETE(request: Request, { params }: Context) {
  if (!isAdmin(request)) return Response.json({ error: "Not authorised" }, { status: 401 });
  // … same as before
}
// do the same at the top of PATCH and POST

<DeepDive title="More about route handlers">

**Validation with zod.**

```text
import { z } from "zod";
const NewProduct = z.object({ name: z.string().trim().min(1).max(100), price: z.number().min(0) });

const parsed = NewProduct.safeParse(await request.json());
if (!parsed.success) return Response.json({ errors: parsed.error.flatten() }, { status: 400 });
const { name, price } = parsed.data;   // fully typed and checked
```

**`NextRequest` and `NextResponse`** (from `next/server`) extend the standard objects: `request.nextUrl.searchParams`, `request.cookies`, and `NextResponse.redirect()` or `response.cookies.set()`.

**Other response types.** Return files (`new Response(buffer, { headers: { "Content-Type": "application/pdf" } })`), redirects (`Response.redirect(url, 307)`), streams (a `ReadableStream`, useful for AI text streaming), or RSS/XML.

**Webhooks.** Payment providers call your route handler when something happens. Read the **raw** body (`await request.text()`), verify the provider's signature header with your webhook secret, and make the handler idempotent (the same event may arrive twice).

**CORS.** Browsers block pages on **other** sites from reading your API's responses unless you send `Access-Control-Allow-Origin`. Same-site calls don't need it. Only allow specific origins, and handle the `OPTIONS` preflight if needed.

**Runtimes.** Handlers run on Node.js by default; `export const runtime = "edge"` runs them on the lighter edge runtime (no Node APIs like `fs`).

**Server Actions vs route handlers.** For mutations triggered by your own forms and buttons, Server Actions remove the boilerplate (no URL, no `fetch`, no JSON parsing). Route handlers are for public or external interfaces.

**REST conventions.** Plural nouns for collections (`/api/products`), ids for items (`/api/products/7`), methods for actions, query strings for filtering and paging, consistent error shapes (`{ "error": "…" }`), and versioning (`/api/v1/…`) once outside clients depend on you.

</DeepDive>

<DeepDive title="Real world: the coupon endpoint that trusted the client">

An online shop added a coupon feature. The checkout page calculated the discounted total in the browser and sent it to the API:

```text
POST /api/orders
{ "items": [{ "id": 17, "qty": 2 }], "coupon": "SPRING20", "total": 64.00 }
```

The handler validated that `total` was a positive number and charged that amount. Within a week, a forum post explained how to open DevTools, copy the request and change `"total"` to `1.00`. Dozens of orders went through for a dollar.

The handler had validated the **type** of the input, but trusted its **meaning**. The fix was to stop accepting prices and totals from the client at all:

1. The client sends only **what** it wants: item ids, quantities and a coupon code.
2. The server looks up current prices in the database, checks stock, validates the coupon (exists, not expired, not already used by this customer) and **calculates the total itself**.
3. The payment amount comes from the server's calculation, never from the request.

The rule they wrote down: **the client can ask; the server decides.** Anything with money, permissions or limits is computed on the server.

</DeepDive>

<DeepDive title="Security lens">

Every route handler is a public door. Assume attackers will call it directly, with anything.

- **Authenticate and authorise on every request**, per method and per resource. "Is this user logged in?" isn't enough; also check "does this order belong to them?" (insecure direct object reference is one of the most common API bugs).
- **Validate everything**: types, ranges, lengths, allowed values. Use a schema library and copy only known fields (prevents **mass assignment**).
- **Never trust client-computed values** for prices, totals, roles or discounts. Recalculate on the server.
- **Parameterised database queries** only; never build SQL from request values.
- **Rate limiting** on login, sign-up, password reset and expensive endpoints (Vercel firewall rules, Upstash ratelimit, or a gateway).
- **Limit what you return**: no password hashes, internal ids or stack traces. Use `Cache-Control: private, no-store` for personal data.
- **CSRF.** Endpoints that rely on cookies can be triggered by other sites' forms. Use `SameSite=Lax` or `Strict` cookies, require JSON with a `Content-Type` check, or verify a CSRF token; Server Actions include protection automatically.
- **Webhooks**: verify signatures with the provider's secret before acting.
- **Log** failed authorisation attempts and unusual patterns so abuse is noticed.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are route handlers in the Next.js App Router?">
Files named route.ts inside the app directory that export functions named after HTTP methods. Each receives a Web Request and an object containing params, and returns a Web Response. They run on the server and are used to build API endpoints, webhooks and non-HTML responses.
</QA>

<QA q="How do you read the different parts of a request in a route handler?">
Query string values come from new URL(request.url).searchParams or request.nextUrl.searchParams, dynamic segments from the awaited params argument, the JSON body from await request.json(), headers from request.headers, and cookies from request.cookies or the cookies function from next/headers.
</QA>

<QA q="What is the difference between 401 and 403?">
401 Unauthorized means the request lacks valid authentication, so the client should log in or supply credentials. 403 Forbidden means the server knows who the client is, but that identity is not allowed to perform the action.
</QA>

<QA q="What is the difference between PUT and PATCH?">
PUT replaces the entire resource with the representation sent, and repeating it has the same effect. PATCH applies a partial update to only the fields provided.
</QA>

<QA q="When would you use a route handler instead of a Server Action or Server Component?">
Use Server Components to read data for your own pages and Server Actions for mutations triggered from your own UI. Use route handlers when external clients need an HTTP interface, such as mobile apps, webhooks or third parties, or when returning non-HTML responses like files and feeds.
</QA>

<QA q="What is mass assignment and how do you prevent it?">
It occurs when an endpoint copies all fields from the request body into a stored object, allowing attackers to set fields they should not control, such as roles or ids. Prevent it by validating against a schema and copying only explicitly allowed fields.
</QA>

</DeepDive>
