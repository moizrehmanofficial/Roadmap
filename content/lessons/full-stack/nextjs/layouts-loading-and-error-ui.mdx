<BigIdea>
<Tr>
<En>
In the App Router, each folder can contain a few **special files**, and Next.js wires them together for you. **`layout.tsx`** wraps a section of the site (a sidebar, a header) and **stays mounted** when you move between its pages, so its state survives. **`template.tsx`** looks like a layout but is **re-created** on every navigation. **`loading.tsx`** is shown **instantly** while the page's data is still loading, and the real content **streams** in when ready; with **`<Suspense>`** you can stream individual parts of a page separately. **`error.tsx`** catches crashes in that section and shows a friendly message with a **Try again** button instead of breaking the whole app. **`not-found.tsx`** is what users see when you call **`notFound()`** for a record that doesn't exist. Together they give every route a polished loading, error and empty state without any `useState` or `useEffect`.
</En>
<Ur>
App Router me har folder me kuch **khaas files** ho sakti hain, aur Next.js unhen aap ke liye aapas me jor deta hai. **`layout.tsx`** site ke ek hisse ko gherta hai (sidebar, header) aur us ke pages ke darmiyan jane par **mounted rehta** hai, isliye us ki state bachi rehti hai. **`template.tsx`** layout jaisa dikhta hai magar har navigation par **naye sire se banta** hai. **`loading.tsx`** page ka data load hote waqt **foran** dikhaya jata hai, aur asli content tayyar hone par **stream** hota hai; **`<Suspense>`** se aap page ke alag alag hisse alag stream kar sakte hain. **`error.tsx`** us hisse ke crash pakarta hai aur poori app torne ke bajaye **Try again** button ke saath achha paighaam dikhata hai. **`not-found.tsx`** wo hai jo users ko tab nazar aata hai jab aap na maujood record ke liye **`notFound()`** call karte hain. Mil kar ye har route ko bina kisi `useState` ya `useEffect` ke saaf loading, error aur khaali halat dete hain.
</Ur>
</Tr>
</BigIdea>

</What>
<Why>
<Tr>
<En>

- **Speed you can feel**: users see the page frame and a loading message immediately instead of a blank screen while the server waits for the database.
- **Resilience**: one broken widget or failing API shows a local error box, not a white screen for the whole app.
- **Less code**: no `isLoading` / `error` state in every page; the file system handles it.
- **Better UX**: sidebars, inputs and scroll positions in layouts survive navigation.

</En>
<Ur>

- **Mehsoos hone wali raftaar**: server ke database ka intezar karte waqt users khaali screen ke bajaye foran page ka dhancha aur loading paighaam dekhte hain.
- **Mazbooti**: ek toota widget ya fail hoti API poori app ke liye safed screen nahi, balke maqami error box dikhati hai.
- **Kam code**: har page me `isLoading` / `error` state nahi; file system ye sambhalta hai.
- **Behtar UX**: layouts ke sidebars, inputs aur scroll ki jagah navigation ke baad bhi bachi rehti hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Use |
| --- | --- |
| Header, sidebar or tabs shared by several pages | `layout.tsx` in their parent folder |
| Something must reset on every page (enter animation, page timer, per-page form) | `template.tsx` |
| A page waits for slow data | `loading.tsx` next to its `page.tsx` |
| Only part of a page is slow | wrap that part in `<Suspense fallback>` |
| A section talks to an unreliable service | `error.tsx` in that section |
| A URL points to a record that doesn't exist | `notFound()` + `not-found.tsx` |

</En>

| Page ka sirf ek hissa sust hai | us hisse ko `<Suspense fallback>` me lapetein |

## Picture it

<Tr>
<En>

Think of a **restaurant**.

- The **building, the tables and the menu board** stay the same while different dishes arrive (the **layout**). If you've written a note on the paper tablecloth, it's still there when the next course comes.
- The **place mat** is replaced with a fresh one for every course (the **template**).
- When you order something that takes 20 minutes, the waiter immediately brings **bread** and says "your dish is coming" (**loading.tsx**). You're not left staring at an empty table.
- If the starter is quick and the main is slow, the starter comes first (**Suspense** streaming parts separately).
- If the kitchen burns your dish, the waiter apologises and offers to **cook it again** (**error.tsx** with Try again), while the rest of your table carries on as normal.
- If you order something that isn't on the menu, you're told politely "we don't have that" (**not-found**).

</En>
<Ur>

Ek **restaurant** ka sochein.

- **Imarat, mezein aur menu board** wahi rehte hain jab ke mukhtalif khane aate hain (**layout**). Agar aap ne kaghazi mezposh par note likha ho, to agla khana aane par bhi wo wahin hota hai.
- **Place mat** har khane ke liye naye se badla jata hai (**template**).
- Jab aap 20 minute lene wali cheez order karte hain, waiter foran **roti** la kar kehta hai "aap ka khana aa raha hai" (**loading.tsx**). Aap khaali mez ko ghoorte nahi reh jate.
- Agar starter jaldi aur main course der se bane, starter pehle aata hai (**Suspense** hisson ko alag stream karna).
- Agar kitchen aap ka khana jala de, waiter maafi maang kar **dobara pakane** ki peshkash karta hai (**error.tsx** with Try again), jab ke aap ki baqi mez aam tareeqe se chalti rehti hai.
- Agar aap menu se bahar ki cheez maangein, to narmi se bataya jata hai "ye hamare paas nahi" (**not-found**).

</Ur>
</Tr>

## Words you'll see

<Tr>
<En>

| Word | What it means | Example |
| --- | --- | --- |
| **Segment** | One folder in the URL path | `dashboard`, `orders` |
| **Layout** | UI that wraps child segments and persists | `app/dashboard/layout.tsx` |
| **Template** | A layout that remounts on navigation | `template.tsx` |
| **Streaming** | Sending the HTML in pieces as each part is ready | loading first, data later |
| **Suspense boundary** | A place that shows a fallback while children wait | `<Suspense fallback>` |
| **Fallback** | The placeholder UI shown while waiting | "Loading orders…" |
| **Error boundary** | A component that catches render errors below it | `error.tsx` |
| **`retry()`** | Re-fetches and re-renders the failed segment | Try again button |
| **Digest** | A short ID for a server error, matching the server log | `3422030179` |
| **`notFound()`** | Stops rendering and shows the nearest `not-found.tsx` | missing order |
| **`connection()`** | Marks a page as dynamic (render per request) | `await connection()` |

</En>
<Ur>

| Lafz | Matlab | Misaal |
| --- | --- | --- |
| **Segment** | URL path ka ek folder | `dashboard`, `orders` |
| **Layout** | Child segments ko gherne wali aur qaim rehne wali UI | `app/dashboard/layout.tsx` |
| **Template** | Navigation par dobara mount hone wala layout | `template.tsx` |
| **Streaming** | Har hissa tayyar hote hi HTML tukron me bhejna | pehle loading, baad me data |
| **Suspense boundary** | Jagah jo children ke intezar me fallback dikhaye | `<Suspense fallback>` |
| **Fallback** | Intezar ke dauran dikhai jane wali placeholder UI | "Loading orders…" |
| **Error boundary** | Component jo neeche ke render errors pakre | `error.tsx` |
| **`retry()`** | Fail hue segment ko dobara fetch aur render karta hai | Try again button |
| **Digest** | Server error ki chhoti ID, server log se milti hai | `3422030179` |
| **`notFound()`** | Rendering rok kar qareebi `not-found.tsx` dikhata hai | ghayab order |
| **`connection()`** | Page ko dynamic nishaan zad karta hai (har request par render) | `await connection()` |

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="A layout wraps pages and keeps its state">

<Tr>
<En>
The root `app/layout.tsx` wraps the whole site. Any folder can add its own `layout.tsx` that wraps only its pages. Here the dashboard gets a sidebar with a "Quick note" input (a small client component).
</En>
<Ur>
Root `app/layout.tsx` poori site ko gherta hai. Koi bhi folder apna `layout.tsx` jor sakta hai jo sirf us ke pages ko ghere. Yahan dashboard ko "Quick note" input (chhota client component) wala sidebar milta hai.
</Ur>
</Tr>

```tsx
// app/dashboard/layout.tsx
import Link from "next/link";
import QuickNote from "./QuickNote";

export default function DashboardLayout({ children }: { children: React.ReactNode }) {
  return (
    <div style={{ display: "flex", gap: 24 }}>
      <aside>
        <p>Dashboard menu</p>
        <ul>
          <li><Link href="/dashboard">Overview</Link></li>
          <li><Link href="/dashboard/orders">Orders</Link></li>
          <li><Link href="/dashboard/reports">Reports</Link></li>
        </ul>
        <QuickNote />
      </aside>
      <section>{children}</section>
    </div>
  );
}

// app/dashboard/QuickNote.tsx
"use client";
import { useState } from "react";

export default function QuickNote() {
  const [note, setNote] = useState("");
  return (
    <label>
      Quick note <input value={note} onChange={(e) => setNote(e.target.value)} />
    </label>
  );
}
```

```text
1. Open /dashboard and type "Call Liam" in Quick note.
2. Click "Reports" in the sidebar.

Result (after the page loads):
Acme Admin · Home · Dashboard
Dashboard menu
Overview / Orders / Reports
Quick note [Call Liam]          ← still there
Reports
Sales today: $1,240
Top products: Mug, Desk Lamp, Notebook
```

<Happened>
<Tr>
<En>

- `children` is the current page (`/dashboard`, `/dashboard/reports`…). When you click a `<Link>`, Next.js only swaps `children`; the layout **isn't re-rendered from scratch**, so the input keeps "Call Liam".
- Layouts **nest**: the root layout's header wraps the dashboard layout, which wraps the page.
- A layout can't read the current page's `params` for child segments or `searchParams`; if the sidebar must highlight the active link, use a client component with `usePathname()`.

</En>
<Ur>

- `children` maujooda page hai (`/dashboard`, `/dashboard/reports`…). `<Link>` dabane par Next.js sirf `children` badalta hai; layout **naye sire se render nahi hota**, isliye input "Call Liam" rakhta hai.
- Layouts **ek doosre ke andar** hote hain: root layout ka header dashboard layout ko gherta hai, jo page ko gherta hai.
- Layout child segments ke `params` ya `searchParams` nahi parh sakta; agar sidebar ko active link roshan karna ho to `usePathname()` wala client component lein.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="A template remounts on every navigation">

<Tr>
<En>
Sometimes you **want** a reset on each page: an entrance animation, a "time on this page" counter, analytics per page view. `template.tsx` sits between the layout and the page, but React creates a **new instance** each time you navigate.
</En>
<Ur>
Kabhi aap har page par reset **chahte** hain: andar aane ki animation, "is page par waqt" counter, har page view ki analytics. `template.tsx` layout aur page ke darmiyan baithta hai, magar har navigation par React **naya instance** banata hai.
</Ur>
</Tr>

```tsx
// app/dashboard/template.tsx
import PageTimer from "./PageTimer";

// Like a layout, but React creates a NEW instance on every navigation
export default function DashboardTemplate({ children }: { children: React.ReactNode }) {
  return (
    <div>
      <PageTimer />
      {children}
    </div>
  );
}

// app/dashboard/PageTimer.tsx
"use client";
import { useEffect, useState } from "react";

export default function PageTimer() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setSeconds((s) => s + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <small>On this page for {seconds}s</small>;
}
```

```text
/dashboard after 3 seconds:          On this page for 3s · Overview
click Reports, wait 2 seconds:       On this page for 2s · Reports     ← counter restarted
Quick note in the layout:            [Call Liam]                        ← kept
```

<Happened>
<Tr>
<En>

- The timer restarted from 0 on the Reports page (template remounted), while the note in the layout survived (layout persisted).
- Use templates sparingly: most shared UI should be a layout, because keeping state is usually what users want.
- If one component needs to reset when the URL changes, `key={pathname}` on that component is a lighter alternative to a whole template.

</En>
<Ur>

- Reports page par timer 0 se dobara shuru hua (template dobara mount hua), jab ke layout ka note bacha raha (layout qaim raha).
- Templates kam istemal karein: zyada tar mushtarka UI layout honi chahiye, kyun ke state bachana aam taur par wahi hai jo users chahte hain.
- Agar sirf ek component ko URL badalne par reset hona ho to us par `key={pathname}` poore template se halka mutabadil hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="loading.tsx: show something instantly while data loads">

<Tr>
<En>
The orders page waits **2 seconds** for a slow database. Without help, the user would stare at the old page (or a blank tab) until everything is ready. Adding `loading.tsx` next to `page.tsx` gives an instant fallback, and the real page **streams in** when ready.
</En>
<Ur>
Orders page sust database ke liye **2 second** intezar karta hai. Madad ke baghair user sab tayyar hone tak purana page (ya khaali tab) dekhta rehta. `page.tsx` ke saath `loading.tsx` jorna fori fallback deta hai, aur asli page tayyar hone par **stream** ho kar aata hai.
</Ur>
</Tr>

```tsx
// lib/data.ts
export const wait = (ms: number) => new Promise((r) => setTimeout(r, ms));

export const orders = [
  { id: "1001", customer: "Emma Johnson", total: 42.5, status: "Shipped" },
  { id: "1002", customer: "Liam Carter", total: 18.0, status: "Processing" },
  { id: "1003", customer: "Olivia Brown", total: 99.99, status: "Delivered" },
];

export async function getOrders() {
  await wait(2000); // pretend the database is slow
  return orders;
}

// app/dashboard/orders/page.tsx
import Link from "next/link";
import { connection } from "next/server";
import { getOrders } from "@/lib/data";

export default async function OrdersPage() {
  await connection(); // render on every request, not at build time
  const orders = await getOrders(); // takes 2 seconds
  return (
    <>
      <h1>Orders</h1>
      <ul>
        {orders.map((o) => (
          <li key={o.id}>
            <Link href={`/dashboard/orders/${o.id}`}>#{o.id}</Link> {o.customer}: ${o.total.toFixed(2)} ({o.status})
          </li>
        ))}
      </ul>
    </>
  );
}

// app/dashboard/orders/loading.tsx
export default function Loading() {
  return <p>Loading orders…</p>;
}
```

```text
Opening /dashboard/orders in the browser:

after 0.3 s   Acme Admin · Home · Dashboard
              Dashboard menu · Overview / Orders / Reports · Quick note
              Loading orders…

after 2.7 s   … same header and sidebar …
              Orders
              #1001 Emma Johnson: $42.50 (Shipped)
              #1002 Liam Carter: $18.00 (Processing)
              #1003 Olivia Brown: $99.99 (Delivered)

The raw HTTP response, read chunk by chunk:
status 200 after 0.01s
0.01s  chunk 1888 bytes   contains "Loading orders": True
0.01s  chunk 5898 bytes   contains "Loading orders": True
2.01s  chunk  724 bytes   contains "Emma Johnson":   True
2.01s  chunk 1557 bytes   contains "Emma Johnson":   True
```

<Happened>
<Tr>
<En>

- The server sent the header, sidebar and "Loading orders…" **immediately** (status 200 at 0.01 s), then kept the connection open and sent the orders **two seconds later** in the same response. That's **streaming**.
- Behind the scenes, Next.js wraps the page in `<Suspense fallback={<Loading />}>`. The layout above it isn't blocked, so the sidebar is usable straight away.
- When navigating with a `<Link>`, the loading UI is **prefetched**, so it appears the instant you click.
- `await connection()` tells Next.js this page must run for every request. Without it, a page with no request data would be rendered **once at build time** (the build would simply wait two seconds).

</En>
<Ur>

- Server ne header, sidebar aur "Loading orders…" **foran** bheje (0.01 s par status 200), phir connection khula rakh kar orders **do second baad** usi response me bheje. Yahi **streaming** hai.
- Parde ke peeche Next.js page ko `<Suspense fallback={<Loading />}>` me lapet'ta hai. Upar ka layout ruka nahi, isliye sidebar foran istemal ke qabil hai.
- `<Link>` se jane par loading UI **pehle se prefetch** hoti hai, isliye click karte hi nazar aati hai.
- `await connection()` Next.js ko batata hai ke ye page har request par chalna chahiye. Is ke baghair, bina request data wala page **build ke waqt ek dafa** render hota (build bas do second intezar karti).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Suspense: stream parts of a page separately">

<Tr>
<En>
`loading.tsx` covers the **whole** page. When one widget is slow and the rest is fast, wrap each slow part in its own `<Suspense>` so the fast parts don't wait for the slowest one.
</En>
<Ur>
`loading.tsx` **poore** page ko dhakta hai. Jab ek widget sust aur baqi tez ho, har sust hisse ko apne `<Suspense>` me lapetein taa ke tez hisse sab se sust ka intezar na karein.
</Ur>
</Tr>

```tsx
// app/dashboard/reports/page.tsx
import { Suspense } from "react";
import { connection } from "next/server";
import { wait } from "@/lib/data";

async function SalesToday() {
  await wait(500);
  return <p>Sales today: $1,240</p>;
}

async function TopProducts() {
  await wait(2500); // the slow part
  return <p>Top products: Mug, Desk Lamp, Notebook</p>;
}

export default async function ReportsPage() {
  await connection();
  return (
    <>
      <h1>Reports</h1>
      <Suspense fallback={<p>Loading sales…</p>}>
        <SalesToday />
      </Suspense>
      <Suspense fallback={<p>Loading top products…</p>}>
        <TopProducts />
      </Suspense>
    </>
  );
}
```

```text
right after clicking Reports:   Reports
                                Loading sales…
                                Loading top products…

about 0.7 s later:              Reports
                                Sales today: $1,240
                                Loading top products…

about 3 s after the click:      Reports
                                Sales today: $1,240
                                Top products: Mug, Desk Lamp, Notebook
```

<Happened>
<Tr>
<En>

- The heading appeared at once, sales after half a second, and top products last. Each `<Suspense>` boundary is filled as soon as **its** data is ready.
- Both async components **start at the same time**, so the page is done in 2.5 s, not 0.5 + 2.5 = 3 s.
- Rule of thumb: `loading.tsx` for "the whole page is waiting", `<Suspense>` for "this card is slow". Fallbacks shaped like the real content (skeletons) avoid layout jumps (CLS).

</En>
<Ur>

- Heading foran aaya, sales aadhe second baad, aur top products aakhir me. Har `<Suspense>` hadd **apna** data tayyar hote hi bhar jati hai.
- Dono async components **ek saath shuru** hote hain, isliye page 0.5 + 2.5 = 3 s nahi, 2.5 s me mukammal hota hai.
- Aam qaida: "poora page intezar me hai" ke liye `loading.tsx`, "ye card sust hai" ke liye `<Suspense>`. Asli content jaisi shakal ke fallbacks (skeletons) layout ke jhatkon (CLS) se bachate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="error.tsx: catch a crash and offer Try again">

<Tr>
<En>
The inventory service is unreliable: our pretend version fails on every other call. Without an error boundary, the error would replace the whole app with an error page. `error.tsx` catches it **inside this segment**, so the header and sidebar keep working. It must be a **Client Component**.
</En>
<Ur>
Inventory service ghair bharosemand hai: hamara naqli version har doosri call par fail hota hai. Error boundary ke baghair error poori app ko error page se badal deta. `error.tsx` use **isi segment ke andar** pakarti hai, isliye header aur sidebar chalte rehte hain. Ise **Client Component** hona chahiye.
</Ur>
</Tr>

```tsx
// lib/flaky.ts
const state = globalThis as unknown as { inventoryCalls?: number };
```

<Step title="notFound() and not-found.tsx for missing records">

<Tr>
<En>
A URL like `/dashboard/orders/9999` is a valid route, but order 9999 doesn't exist. Calling `notFound()` stops rendering and shows the nearest `not-found.tsx`. This is an **expected** situation, so it's not an error.
</En>
<Ur>
`/dashboard/orders/9999` jaisa URL durust route hai, magar order 9999 maujood nahi. `notFound()` call karna rendering rok kar qareebi `not-found.tsx` dikhata hai. Ye **mutawaqqa** soorat hai, isliye error nahi.
</Ur>

```tsx
import { getOrder } from "@/lib/data";

export default async function OrderPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const order = await getOrder(id);
  if (!order) notFound();
  return (
    <>
      <h1>Order #{order.id}</h1>
      <p>{order.customer} · ${order.total.toFixed(2)} · {order.status}</p>
    </>
  );
}

// app/dashboard/orders/[id]/not-found.tsx
import Link from "next/link";

export default function OrderNotFound() {
  return (
    <>
      <h1>Order not found</h1>
      <p>Check the order number, or go back to <Link href="/dashboard/orders">all orders</Link>.</p>
    </>
  );
}
```

- After `notFound()`, TypeScript knows `order` isn't `null`: the function never returns (its type is `never`).

<Step title="How the files nest">

<Tr>
<En>

For one segment, Next.js builds this tree (outermost first):

```text
<Layout>
  <Template>
    <ErrorBoundary fallback={<Error />}>
      <Suspense fallback={<Loading />}>
        <NotFoundBoundary fallback={<NotFound />}>
          <Page />
        </NotFoundBoundary>
      </Suspense>
    </ErrorBoundary>
  </Template>
</Layout>
```

Consequences:

- `error.tsx` doesn't catch errors from the **layout** in the same folder (the layout is outside it); put the boundary in the parent folder.
- A `loading.tsx` also covers nested child routes until they define their own.
- The nearest file wins: `orders/[id]/not-found.tsx` beats `app/not-found.tsx` for missing orders.

</En>
<Ur>

Ek segment ke liye Next.js ye darakht banata hai (sab se bahar wala pehle):

```text
<Layout>
  <Template>
    <ErrorBoundary fallback={<Error />}>
      <Suspense fallback={<Loading />}>
        <NotFoundBoundary fallback={<NotFound />}>
          <Page />
        </NotFoundBoundary>
      </Suspense>
    </ErrorBoundary>
  </Template>
</Layout>
```

Nataij:

- `error.tsx` usi folder ke **layout** ke errors nahi pakarti (layout us se bahar hai); boundary parent folder me rakhein.
- `loading.tsx` andar ke child routes ko bhi dhakta hai jab tak wo apna na banayen.
- Qareebi file jeet'ti hai: ghayab orders ke liye `orders/[id]/not-found.tsx` `app/not-found.tsx` par bhaari hai.

</Ur>
</Tr>

<Happened>
<Tr>
<En>

- Think of it as layers of safety nets: each folder can add its own, and the closest one catches the fall.
- Since `retry()` re-renders only that boundary's subtree, smaller boundaries mean smaller retries.

</En>
<Ur>

- Ise hifazati jaalon ki tahon ki tarah samjhein: har folder apna jor sakta hai, aur sab se qareeb wala girne ko pakarta hai.
- Kyun ke `retry()` sirf us boundary ka hissa dobara render karta hai, chhoti boundaries ka matlab chhote retries hain.

## Common mistakes

<Compare>
<Bad title="Fetching in useEffect with manual loading state">

```text
"use client";
export default function OrdersPage() {
  const [orders, setOrders] = useState(null);
  useEffect(() => { fetch("/api/orders").then((r) => r.json()).then(setOrders); }, []);
  if (!orders) return <p>Loading…</p>;
  return <OrderList orders={orders} />;
}
// extra round trip, blank HTML for search engines, no error handling
```

</Bad>
<Good title="Async Server Component + loading.tsx + error.tsx">

```text
// page.tsx
export default async function OrdersPage() {
  const orders = await getOrders();
  return <OrderList orders={orders} />;
}
// loading.tsx → <p>Loading orders…</p>
// error.tsx   → "use client" + retry()
```

</Good>
</Compare>

<Compare>
<Bad title="Showing the raw error message to users">

```text
"use client";
export default function Error({ error }) {
  return <pre>{String(error)}</pre>;   // in development this may show internals; it's noise to users
}
```

</Bad>
<Good title="Friendly message + digest + logging">

```text
"use client";
export default function Error({ error, retry }) {
  useEffect(() => { reportError(error); }, [error]);
  return (
    <div role="alert">
      <h2>Something went wrong</h2>
      <p>Reference: {error?.digest}</p>
      <button onClick={() => retry()}>Try again</button>
    </div>
  );
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting `"use client"` in `error.tsx`**: the build fails, because error boundaries need client-side React.
- **Expecting `error.tsx` to catch errors in the layout next to it**: put it one level up, or use `global-error.tsx` for the root.
- **Using `try/catch` + `throw` for expected cases** (missing records, invalid input): use `notFound()`, return a message, or `redirect()` instead.
- **One giant loading spinner** for a page whose slow part is a single card: use a `<Suspense>` around that card.
- **Putting a `template.tsx` where a layout should be**: state like open menus or typed text is lost on every click.
- **Fallbacks with a different size** from the real content: the page jumps when data arrives.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`error.tsx` me `"use client"` bhoolna**: build fail hoti hai, kyun ke error boundaries ko client side React chahiye.
- **`error.tsx` se saath wale layout ke errors pakarne ki umeed**: ise ek level upar rakhein, ya root ke liye `global-error.tsx` lein.
- **Mutawaqqa suraton ke liye `try/catch` + `throw`** (ghayab records, ghalat input): is ke bajaye `notFound()`, paighaam wapas karna, ya `redirect()` lein.
- **Aise page ke liye ek bara loading spinner** jis ka sust hissa sirf ek card ho: us card ke gird `<Suspense>` lein.
- **Jahan layout hona chahiye wahan `template.tsx`**: khule menus ya likha text jaisi state har click par kho jati hai.
- **Asli content se mukhtalif size ke fallbacks**: data aane par page jhatka khata hai.

</Ur>
</Tr>

<Takeaways>
<Tr>
<En>

- `layout.tsx` wraps child routes and **keeps its state** across navigation; `template.tsx` **remounts**.
- `loading.tsx` shows instantly while a page loads; the real content **streams** in the same response.
- `<Suspense fallback>` streams individual slow parts so fast parts don't wait.
- `error.tsx` (`"use client"`) catches errors in its segment; `retry()` re-fetches; `global-error.tsx` covers the root layout.
- Production hides server error messages; use the **digest** to find them in logs.
- `notFound()` + `not-found.tsx` for missing records; unknown URLs get a 404.
- Mark per-request pages as dynamic, for example with `await connection()`.

</En>

<DeepDive title="More about special files">

**Parallel routes.** Folders named `@analytics` and `@team` inside a segment become named slots passed to the layout as props (`{ analytics, team }`). Each slot gets its own loading and error files, so two dashboard panels can load and fail independently. A `default.tsx` provides a fallback when a slot doesn't match the URL.

**Intercepting routes.** Folders like `(.)photo/[id]` show a route inside the current page (for example as a modal) on client navigation, while a direct visit renders the full page.

**`forbidden()` and `unauthorized()`.** Like `notFound()`, they render `forbidden.tsx` (403) and `unauthorized.tsx` (401); they are experimental and need `experimental: { authInterrupts: true }` in `next.config.ts`.

**Route segment config.** Pages and layouts can export settings such as `export const maxDuration = 30` or `export const revalidate = 60` (covered in Data Fetching and Caching).

**Root layout rules.** The root layout must render `<html>` and `<body>`, and it's required. Several root layouts are possible with route groups (`app/(shop)/layout.tsx`, `app/(admin)/layout.tsx`), but navigating between them does a full page load.

**`useSelectedLayoutSegment()`.** A client hook for layouts that need to know which child is active, for example to highlight a tab.

**Instant navigation.** Because loading UI is prefetched with links, navigation feels instant even when the next page has slow data. Prefetching happens for links in the viewport in production.

</DeepDive>

<DeepDive title="Real world: the dashboard that went white">

A logistics company's admin dashboard showed shipments, invoices and a weather widget for each warehouse. The weather widget called a free third-party API. One morning that API started returning HTML error pages instead of JSON, `JSON.parse` threw, and because the app had no error boundaries below the root, every user saw a blank white page with "Application error: a client-side exception has occurred". Warehouse staff couldn't print shipping labels for two hours.

The fix took an afternoon:

1. Each dashboard panel became its own async Server Component wrapped in `<Suspense>` with a skeleton the same size as the panel.
2. Each panel got an error boundary (`error.tsx` for route-level sections, and a small client error boundary component around individual widgets) with a "Try again" button and the error digest.
3. `global-error.tsx` was added as a last resort with a link to the status page.
4. The weather call got a 2-second timeout and returned `null` on failure, so the widget simply said "Weather unavailable" (an expected case, not an exception).

A month later the same API failed again. This time the weather card said "Weather unavailable", the error rate alert pointed to the digest in the logs, and nobody else noticed.

</DeepDive>

<DeepDive title="Security lens">

- **Don't leak internals in error UI**: production already hides Server Component error messages, but errors thrown in Client Components are passed as they are. Show friendly text and a digest, not `error.message` or stack traces.
- **Log server-side with context** (user ID, route, digest) so you can investigate without exposing details to users.
- **`notFound()` vs `forbidden()`**: for records a user isn't allowed to see, returning not-found avoids confirming that the record exists (no ID enumeration).
- **Loading UI must not include private data**: it's shown before any checks finish. Do authorisation in the page or data layer, not by hiding UI.
- **Streaming and status codes**: once streaming starts, the status is already 200. Don't rely on status codes from streamed pages for security decisions; protect data at the source.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between layout.tsx and template.tsx?">
Both wrap child routes. A layout is preserved across navigation between its children, so its state and DOM persist and it doesn't re-render from scratch. A template is given a unique key per route, so it remounts on every navigation, resetting state and re-running effects.
</QA>

<QA q="How does loading.tsx work under the hood?">
Next.js wraps the segment's page in a React Suspense boundary with the loading component as the fallback. The server sends the layout and fallback HTML immediately and streams the page's HTML in the same response when its async work finishes. On client navigation the loading UI is prefetched so it shows instantly.
</QA>

<QA q="How do you handle errors in the App Router?">
Expected errors are handled as return values, notFound or redirect. Unexpected exceptions are caught by error.tsx files, which are client-side error boundaries for their segment, receiving the error and a retry function. global-error.tsx catches errors in the root layout. In production, server error messages are replaced by a generic message and a digest for log correlation.
</QA>

<QA q="Why doesn't error.tsx catch errors from the layout in the same folder?">
Because the error boundary is rendered inside that layout in the component tree. To catch layout errors, place an error.tsx in the parent segment, or use global-error.tsx for the root layout.
</QA>

<QA q="What is streaming and why is it useful?">
Streaming sends HTML to the browser in chunks as each part of the page is ready instead of waiting for all data. Users see the shell and fallbacks immediately, fast sections don't wait for slow ones, and time to first byte stays low.
</QA>

</DeepDive>
