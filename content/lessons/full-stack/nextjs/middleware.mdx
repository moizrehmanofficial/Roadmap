<BigIdea>
<Tr>
<En>
**Middleware** is a single function that Next.js runs **before** it handles a request: before the page renders, before the API route runs, before the static file is served. It sees the incoming **request** (URL, cookies, headers) and decides what happens next: let it **continue** (optionally adding headers), **redirect** the browser somewhere else, **rewrite** it to a different page while keeping the URL, or **answer directly** (a 403, a JSON response). Since **Next.js 16**, the file is called **`proxy.ts`** and exports a function named **`proxy`**; the old `middleware.ts` still works but prints a deprecation warning, and most articles and job descriptions still say "middleware". It's ideal for **quick decisions** that apply to many routes: send logged-out users to `/login`, A/B tests, locale redirects, request IDs, security headers. A **`matcher`** limits which paths it runs on. It's **not** for slow work (database queries on every request) and it's **not** a complete security layer: pages, API routes and Server Actions must still check permissions themselves.
</En>
<Ur>
**Middleware** ek akela function hai jo Next.js request sambhalne se **pehle** chalata hai: page render hone se pehle, API route chalne se pehle, static file dene se pehle. Ye aane wali **request** (URL, cookies, headers) dekhta hai aur faisla karta hai ke aage kya ho: use **jari** rehne de (chahe headers jor kar), browser ko kahin aur **redirect** kare, URL wahi rakh kar use doosre page par **rewrite** kare, ya **seedha jawab** de (403, JSON response). **Next.js 16** se file ka naam **`proxy.ts`** hai aur ye **`proxy`** naam ka function export karti hai; purani `middleware.ts` ab bhi chalti hai magar deprecation warning deti hai, aur zyada tar articles aur naukriyon ki tafseelat ab bhi "middleware" kehti hain. Ye bohot se routes par lagne wale **jaldi faislon** ke liye behtareen hai: logged-out users ko `/login` bhejna, A/B tests, zabaan ke hisaab se redirects, request IDs, security headers. **`matcher`** hadd lagata hai ke ye kin paths par chale. Ye sust kaam (har request par database queries) ke liye **nahi**, aur mukammal security layer **nahi**: pages, API routes aur Server Actions ko phir bhi khud permissions check karni hain.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **One place** for rules that apply across many routes, instead of repeating checks in every page.
- **Runs early**: redirects happen before any page code or data fetching, so they're fast and cheap.
- **Invisible routing**: rewrites let you change what's served without changing URLs (experiments, tenants, migrations).
- **Common interview topic**, and a real security incident (2025) shows why understanding its limits matters.

</En>
<Ur>

- Bohot se routes par lagne wale qawaid ke liye **ek jagah**, har page me checks dohrane ke bajaye.
- **Jaldi chalta hai**: redirects kisi page code ya data fetching se pehle hote hain, isliye tez aur saste hain.
- **Nazar na aane wali routing**: rewrites URLs badle baghair jo diya ja raha hai wo badalne dete hain (experiments, tenants, migrations).
- **Interview ka aam mauzoo**, aur ek asli security waqiya (2025) dikhata hai ke is ki hadein samajhna kyun ahem hai.

</Ur>
</Tr>
</Why>

<En>

| Check the user's role in the database on every request | ❌ do it in the page / data layer |
| Heavy work: calling slow APIs, rendering | ❌ |
| The only protection for admin pages or actions | ❌ never |

| Kaam | Middleware? |

<How>
<Tr>
<En>

1. Create `proxy.ts` in the project root (next to `app/`, or inside `src/`).
2. Export `function proxy(request: NextRequest)` (or a default export).
3. Return `NextResponse.next()`, `redirect`, `rewrite`, or a `Response`.

## Picture it

<Tr>
<En>

Think of the **reception desk** at an office building.

- Every visitor passes the desk **before** reaching any office (runs before every matched request).
- No visitor badge? "Please sign in at the front first" (**redirect** to `/login`).

## Learn it step by step

<Walkthrough>

<Step title="The whole proxy.ts we'll explore">

<Tr>
<En>
Here is the complete file used in this lesson. It lives in the project root next to the `app/` folder. The next steps test each part against a real production build.
</En>
<Ur>
Ye is lesson me istemal hone wali poori file hai. Ye `app/` folder ke saath project ki jarr me hai. Agle steps har hisse ko asli production build par test karte hain.
</Ur>
</Tr>

```ts
// proxy.ts
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  console.log(`proxy: ${request.method} ${pathname}`);

  // 1. Block a misbehaving scraper before any page code runs
  if (request.headers.get("user-agent")?.includes("BadBot")) {
    return Response.json({ error: "Forbidden" }, { status: 403 });
  }

  // 2. Optimistic auth check: no session cookie → go to the login page
  if (pathname.startsWith("/dashboard") && !request.cookies.has("session")) {
    const login = new URL("/login", request.url);
    login.searchParams.set("from", pathname);
    return NextResponse.redirect(login);
  }

  // 3. A/B test: same URL, different page, sticky per visitor
  if (pathname === "/pricing") {
    let bucket = request.cookies.get("ab-pricing")?.value;
    if (bucket !== "a" && bucket !== "b") bucket = Math.random() < 0.5 ? "a" : "b";
    const response =
      bucket === "b"
        ? NextResponse.rewrite(new URL("/experiments/pricing-b", request.url))
        : NextResponse.next();
    response.cookies.set("ab-pricing", bucket, { maxAge: 60 * 60 * 24 * 30 });
    return response;
  }

  // 4. Add a request ID: forwarded to the page AND returned to the browser
  const requestId = crypto.randomUUID().slice(0, 8);
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set("x-request-id", requestId);
  const response = NextResponse.next({ request: { headers: requestHeaders } });
  response.headers.set("x-request-id", requestId);
  return response;
}

export const config = {
  // Skip Next.js internals and static files
  matcher: ["/((?!_next/static|_next/image|favicon.ico|robots.txt).*)"],
};
```

```text
$ npx next build
...
├ ƒ /login
└ ƒ /whoami
ƒ Proxy (Middleware)
```

<Happened>
<Tr>
<En>

- The build lists **`ƒ Proxy (Middleware)`**: Next.js found the file and will run it on matching requests.
- The function runs top to bottom and **returns early** for the first rule that applies. Order matters: the bot block comes first so blocked requests do no other work.
- It runs in the **Node.js runtime** (the `runtime` option isn't allowed in proxy files), so most Node APIs work, but keep it fast: it's on the path of every matching request.

</En>
<Ur>

- Build **`ƒ Proxy (Middleware)`** dikhati hai: Next.js ne file dhoond li aur ise milti requests par chalayega.
- Function upar se neeche chalta hai aur lagne wale pehle qaide par **jaldi wapas** aata hai. Tarteeb ahem hai: bot block pehle hai taa ke rokki gayi requests aur koi kaam na karein.
- Ye default me **Node.js runtime** me chalta hai, isliye zyada tar Node APIs kaam karti hain, magar ise tez rakhein: ye har milti request ke raaste me hai.

</Ur>
</Tr>
</Happened>

<Step title="Redirect visitors without a session">

<Tr>
<En>
Rule 2 sends anyone without a `session` cookie away from `/dashboard…` to `/login`, remembering where they wanted to go in `?from=`.
</En>
<Ur>
Qaida 2 `session` cookie ke baghair har kisi ko `/dashboard…` se `/login` bhejta hai, `?from=` me yaad rakh kar ke wo kahan jana chahte the.
</Ur>
</Tr>

```text
$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" localhost:3200/dashboard/orders
307 http://localhost:3200/login?from=%2Fdashboard%2Forders

$ curl -s -o /dev/null -w "%{http_code}\n" -H "Cookie: session=abc" localhost:3200/dashboard
200

The login page (app/login/page.tsx) reads searchParams:
Log in
You'll be sent back to: /dashboard/orders
```

<Happened>
<Tr>
<En>

- `NextResponse.redirect` returns **307 Temporary Redirect** by default (the browser keeps the method). Pass a second argument for others: `NextResponse.redirect(url, 308)`.
- The check only asks "is there a cookie called `session`?" It doesn't verify the cookie or the user's role; a fake `session=abc` got through. That's fine for an **optimistic** redirect that improves UX, but the dashboard pages must still verify the session (Authentication lesson).
- After logging in, the login action can `redirect(from)`, but validate that `from` is a path on your own site (starts with a single `/`) to avoid open redirects.

</En>
<Ur>

- `NextResponse.redirect` default me **307 Temporary Redirect** deta hai (browser method wahi rakhta hai). Doosre ke liye doosra argument dein: `NextResponse.redirect(url, 308)`.
- Check sirf poochta hai "kya `session` naam ki cookie hai?" Ye cookie ya user ka role tasdeeq nahi karta; jaali `session=abc` guzar gayi. **Optimistic** redirect ke liye jo UX behtar kare ye theek hai, magar dashboard pages ko phir bhi session tasdeeq karna hai (Authentication lesson).
- Login ke baad login action `redirect(from)` kar sakta hai, magar open redirects se bachne ke liye check karein ke `from` aap ki apni site ka path ho (ek akele `/` se shuru ho).

</Ur>
</Tr>
</Happened>

<Step title="Rewrite: an A/B test on the same URL">

<Tr>
<En>
Rule 3 puts each new visitor in bucket A or B at random, stores it in a cookie for 30 days, and for bucket B **rewrites** `/pricing` to a different page. The browser still shows `/pricing`.
</En>
<Ur>
Qaida 3 har naye visitor ko ittefaqan bucket A ya B me rakhta hai, use 30 din ke liye cookie me mehfooz karta hai, aur bucket B ke liye `/pricing` ko doosre page par **rewrite** karta hai. Browser ab bhi `/pricing` dikhata hai.
</Ur>

Six new visitors (no cookie) requesting /pricing:

version A   set-cookie: ab-pricing=a; Path=/; Expires=Mon, 14 Dec 2026 …

version A   set-cookie: ab-pricing=a; Path=/; Expires=Mon, 14 Dec 2026 …

<Happened>
<Tr>
<En>

- New visitors were split between the two versions (random, so your run will differ), and each got a cookie.
- A returning visitor with `ab-pricing=b` **always** saw version B: the bucket is sticky, so people don't see prices jump between visits.
- The B page lives at `app/experiments/pricing-b/page.tsx`. Users never see that path; the URL stays `/pricing`. (It can still be opened directly, so don't put secrets there.)
- Rewrites power multi-tenant apps too: `acme.example.com/` can be rewritten to `/tenants/acme`.

</En>
<Ur>

- Naye visitors do versions me bat gaye (ittefaqi, isliye aap ka nateeja mukhtalif hoga), aur har ek ko cookie mili.
- `ab-pricing=b` wala lautne wala visitor **hamesha** version B dekhta raha: bucket chipka rehta hai, isliye log visits ke darmiyan qeematein uchhalti nahi dekhte.
- B page `app/experiments/pricing-b/page.tsx` par hai. Users ye path kabhi nahi dekhte; URL `/pricing` rehta hai. (Ise phir bhi seedha khola ja sakta hai, isliye wahan raaz na rakhein.)
- Rewrites multi-tenant apps ko bhi chalate hain: `acme.example.com/` ko `/tenants/acme` par rewrite kiya ja sakta hai.

</Ur>

<Step title="Pass data to the page with request headers">

<Tr>
<En>
Rule 4 creates a short request ID and sets it **twice**: on the **request** headers (so the page can read it with `headers()`) and on the **response** headers (so the browser and support staff can see it).
</En>
<Ur>
Qaida 4 chhoti request ID banata hai aur use **do dafa** set karta hai: **request** headers par (taa ke page use `headers()` se parh sake) aur **response** headers par (taa ke browser aur support staff use dekh sakein).
</Ur>
</Tr>

```tsx
// app/whoami/page.tsx
import { headers } from "next/headers";

export default async function WhoAmI() {
  const h = await headers();
  return <p>Request ID from the proxy: {h.get("x-request-id")}</p>;
}
```

```text
$ curl -s -D headers.txt localhost:3200/whoami
Request ID from the proxy: 5dc3e1cd

headers.txt:
x-request-id: 5dc3e1cd
```

<Happened>
<Tr>
<En>

- The page and the response show the **same** ID. Log it in your server code too, and you can trace one user's request across logs ("it failed for request 5dc3e1cd").
- `NextResponse.next({ request: { headers } })` is the only way to pass data from middleware to pages and route handlers; there's no shared object between them.
- Don't forward everything: only set headers you control. A client can send its own `x-request-id` too, which is why we overwrite it.

</En>
<Ur>

- Page aur response **wahi** ID dikhate hain. Ise apne server code me bhi log karein, aur aap ek user ki request logs me trace kar sakte hain ("request 5dc3e1cd ke liye fail hua").
- `NextResponse.next({ request: { headers } })` middleware se pages aur route handlers ko data dene ka wahid tareeqa hai; un ke darmiyan koi mushtarka object nahi.
- Sab aage na bhejein: sirf apne control wale headers set karein. Client apna `x-request-id` bhi bhej sakta hai, isi liye hum use overwrite karte hain.

</Ur>
</Tr>
</Happened>

<En>

<Happened>
<Tr>
<En>

- Without the matcher, six extra invocations ran for JavaScript files: wasted work on every page view, and a risk if your middleware adds cookies or redirects to static files.
- Notice the other lines: `/`, `/dashboard` and `/login` were **prefetch** requests for the links in the root layout. Middleware runs on those too, which is why the dashboard prefetch was redirected to `/login`.
- Matcher patterns: `"/dashboard/:path*"` (a section), an array of patterns, or a regex with a negative lookahead like ours to exclude paths. Values must be constants (they're read at build time).
- Server Actions are POST requests to the page that uses them; if a matcher excludes that page, the actions there skip middleware too. Another reason to check permissions inside actions.

</En>
<Ur>

- Matcher ke baghair JavaScript files ke liye chhe izafi dafa chala: har page view par zaya kaam, aur khatra agar aap ka middleware static files par cookies ya redirects lagaye.
- Doosri lines dekhein: `/`, `/dashboard` aur `/login` root layout ke links ki **prefetch** requests thin. Middleware un par bhi chalta hai, isi liye dashboard ka prefetch `/login` par redirect hua.

</Ur>

## Common mistakes

<Compare>
<Bad title="Middleware as the only gate to admin data">

```text
// proxy.ts
if (pathname.startsWith("/admin") && request.cookies.get("role")?.value !== "admin") {
  return NextResponse.redirect(new URL("/", request.url));
}
// app/admin/users/page.tsx, app/api/admin/*, admin Server Actions: no checks
```

</Bad>
<Good title="Middleware for UX, real checks next to the data">

```text
// proxy.ts: quick redirect if there's no session cookie at all
// app/admin/users/page.tsx
const user = await verifySession();          // verified, from the database or a signed token
if (user.role !== "admin") forbidden();      // or notFound()
// every admin API route and Server Action calls requireAdmin() too
```

</Good>
</Compare>

<Compare>
<Bad title="No matcher and slow work on every request">

```text
export async function proxy(request: NextRequest) {
  const settings = await fetch("https://config-service.internal/settings").then((r) => r.json());
  // runs for every page, prefetch, JS chunk and image: slow and expensive
}
```

</Bad>
<Good title="Narrow matcher, fast checks only">

```text
export function proxy(request: NextRequest) {
  // cookie and header checks only; fetch settings where they're used, with "use cache"
}
export const config = { matcher: ["/dashboard/:path*", "/account/:path*"] };
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Redirect loops**: redirecting `/login` to `/login` (forgetting to exclude the login page from the rule).
- **Open redirects**: `redirect(searchParams.get("next"))` to any URL lets attackers use your domain in phishing links; allow only internal paths.
- **Using middleware for fixed redirects** that belong in `next.config.ts` `redirects` (faster, simpler, cached by CDNs).
- **Forgetting that prefetches pass through middleware**: expensive logic or analytics in middleware counts prefetches as visits.
- **Trusting headers or cookies the client controls** (`x-user-role`, `role=admin`) as proof of identity.
- **Expecting `"use cache"` or `fetch` caching to work in middleware**: directives have no effect there.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Redirect loops**: `/login` ko `/login` par redirect karna (login page ko qaide se chhorna bhool jana).
- **Open redirects**: kisi bhi URL par `redirect(searchParams.get("next"))` hamla awaron ko phishing links me aap ka domain istemal karne deta hai; sirf andaruni paths ki ijazat dein.
- **Muqarrar redirects ke liye middleware** jo `next.config.ts` ke `redirects` me hone chahiyen (tez, saade, CDNs par cache).
- **Bhool jana ke prefetches middleware se guzarte hain**: middleware me mehnga logic ya analytics prefetches ko visits gin leti hai.
- **Client ke control wale headers ya cookies** (`x-user-role`, `role=admin`) ko pehchan ka saboot samajhna.
- **Middleware me `"use cache"` ya `fetch` caching chalne ki umeed**: directives ka wahan koi asar nahi.

</Ur>
</Tr>

## Try it yourself

<Challenge title="Locale redirect">

<Tr>
<En>
Write a `proxy.ts` that redirects `/` to `/de` when the browser's `Accept-Language` starts with `de`, and to `/en` otherwise, but leaves every other path alone. A visitor who already chose a language has a `locale` cookie; respect it.
</En>
<Ur>
`proxy.ts` likhein jo `/` ko `/de` par redirect kare jab browser ki `Accept-Language` `de` se shuru ho, warna `/en` par, magar har doosre path ko na chhede. Jis visitor ne pehle zabaan chuni ho us ke paas `locale` cookie hai; us ka ehtiraam karein.
</Ur>
</Tr>

<Solution>

```text
import { NextResponse, type NextRequest } from "next/server";

const SUPPORTED = ["en", "de"];

export function proxy(request: NextRequest) {
  const cookie = request.cookies.get("locale")?.value;
  const header = request.headers.get("accept-language") ?? "";
  const preferred = cookie && SUPPORTED.includes(cookie)
    ? cookie
    : header.toLowerCase().startsWith("de") ? "de" : "en";
  return NextResponse.redirect(new URL(`/${preferred}`, request.url));
}

export const config = { matcher: ["/"] };    // only the home page
```

<Tr>
<En>
The matcher `["/"]` means the function runs only for the home page, so there's no risk of redirect loops on `/en` or `/de`. Real apps often use a library like `negotiator` to parse quality values (`de;q=0.9, en;q=0.8`).
</En>
<Ur>
Matcher `["/"]` ka matlab hai function sirf home page ke liye chalta hai, isliye `/en` ya `/de` par redirect loops ka khatra nahi. Asli apps quality values (`de;q=0.9, en;q=0.8`) parse karne ke liye aksar `negotiator` jaisi library istemal karti hain.
</Ur>
</Tr>

</Solution>

## Remember

<Takeaways>
<Tr>
<En>

- Middleware runs **before** routes. In Next.js 16 it's **`proxy.ts`** exporting `proxy`; `middleware.ts` is deprecated but works.
- Return `next()` (optionally with request/response headers or cookies), `redirect()` (URL changes, 307), `rewrite()` (URL stays), or a `Response`.
- Pass data to pages with **request headers**; show data to browsers with **response headers**.
- Use a **matcher** to skip static files and limit it to relevant paths; prefetches pass through it too.
- Keep it **fast**: cookie and header checks, no slow fetches; directives like `"use cache"` don't work there.
- It's an **optimistic** layer: always verify sessions and permissions in pages, route handlers and Server Actions.
- Static redirects and headers belong in `next.config.ts`.

</En>
<Ur>

- Middleware routes se **pehle** chalta hai. Next.js 16 me ye `proxy` export karne wali **`proxy.ts`** hai; `middleware.ts` deprecated hai magar chalti hai.
- `next()` (chahe request/response headers ya cookies ke saath), `redirect()` (URL badalta hai, 307), `rewrite()` (URL wahi), ya `Response` wapas karein.
- Pages ko data **request headers** se dein; browsers ko data **response headers** se dikhayen.
- Static files chhorne aur mutaliqa paths tak mehdood karne ke liye **matcher** lein; prefetches bhi is se guzarte hain.
- Ise **tez** rakhein: cookie aur header checks, sust fetches nahi; `"use cache"` jaise directives wahan nahi chalte.
- Ye **optimistic** layer hai: sessions aur permissions hamesha pages, route handlers aur Server Actions me tasdeeq karein.

<DeepDive title="More about middleware">

**Execution order.** For each request: `headers` from `next.config`, then `redirects` from `next.config`, then middleware, then `beforeFiles` rewrites, filesystem routes (`public/`, `app/`), `afterFiles` rewrites, dynamic routes, and finally `fallback` rewrites.

**Advanced matchers.** Matcher objects support `has` and `missing` conditions on headers, cookies and query parameters, for example running only when a `session` cookie is missing.

**`event.waitUntil`.** The second argument (`NextFetchEvent`) can keep work like logging running after the response is sent.

**Content Security Policy with nonces.** Middleware is the standard place to generate a random nonce per request, put it in the `Content-Security-Policy` response header, and pass it to the layout through a request header so scripts can use it.

**Response cookies vs request cookies.** `response.cookies.set` sends `Set-Cookie` to the browser; to make a new cookie visible to the page in the same request, also set it on the request headers.

**Platforms.** On Vercel and other edge networks, middleware may run close to the user. Self-hosted, it runs inside your Node.js server process.

**Config flags.** `skipTrailingSlashRedirect` and `skipProxyUrlNormalize` cover rare cases like incremental migrations from other frameworks.

</DeepDive>

<DeepDive title="Real world: the header that skipped middleware">

In March 2025, a vulnerability in Next.js (CVE-2025-29927) showed why middleware must never be the only security check. Next.js used an internal header, `x-middleware-subrequest`, to stop middleware from running in a loop when it made requests to itself. Researchers found that an attacker could simply **send that header** with a request, and self-hosted Next.js would **skip middleware entirely**.

Apps that protected `/admin` only with a cookie check in middleware were exposed: adding one header to a request opened the admin pages. Apps that also checked the session inside their pages, API routes and data layer were not affected in practice, because the second check still ran.

The fix was released quickly (15.2.3, 14.2.25 and backports), and the common advice became:

1. Upgrade Next.js promptly and watch its security advisories.
2. Treat middleware as an **optimisation and UX layer**: fast redirects, headers, experiments.
3. Put **authorisation next to the data**: a `verifySession()` / `requireAdmin()` call in every protected page, route handler and Server Action.
4. Strip or block unexpected internal headers at the load balancer or CDN as defence in depth.

Teams that followed "defence in depth" before the incident had a quiet week.

</DeepDive>

<DeepDive title="Security lens">

- **Defence in depth**: middleware checks are optimistic; repeat real checks where data is read or changed.
- **Validate redirect targets** to prevent open redirects; allow only relative paths or a list of known hosts.
- **Don't trust client-controlled headers or cookies** for identity; verify signed tokens or sessions.
- **Security headers** (CSP with nonces, `X-Content-Type-Options`, `Referrer-Policy`, HSTS) are a good fit for middleware or `next.config.ts` headers.
- **Rate limiting** in middleware needs a shared store (Redis, an edge KV); in-memory counters don't work across instances.
- **Keep Next.js updated**: framework-level bypasses do happen.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is middleware in Next.js and when does it run?">
It's a single function, in proxy.ts since Next.js 16 and middleware.ts before, that runs before a request reaches routes, after next.config headers and redirects. It can continue the request, modify request or response headers and cookies, redirect, rewrite, or return a response directly. A matcher limits which paths it runs on.
</QA>

<QA q="What is the difference between redirect and rewrite?">
A redirect sends a 3xx response telling the browser to request a different URL, so the address bar changes. A rewrite is internal: the server renders a different route for the same request and the browser's URL stays the same.
</QA>

<QA q="Should you do authentication in middleware?">
Only optimistic checks, such as redirecting users without a session cookie, to improve UX and reduce wasted work. Full verification and authorisation must happen in pages, route handlers, Server Actions and the data layer, because middleware can be misconfigured, skipped by matchers, or bypassed, as CVE-2025-29927 showed.
</QA>

<QA q="How do you share data from middleware with a page?">
Set request headers with NextResponse.next and a request.headers option, then read them in the page or route handler with headers(). Response headers are only visible to the client.
</QA>

<QA q="Why use a matcher, and what does it run on by default?">
By default middleware runs on every request, including static assets, images and prefetches. A matcher restricts it to relevant paths, reducing latency and cost and avoiding side effects on assets.
</QA>

</DeepDive>
