<BigIdea>
<Tr>
<En>
**Authentication** answers "who are you?" and **authorisation** answers "what are you allowed to do?". In a Next.js app, the flow has four parts. **1. Sign up / log in**: a form sends credentials to a **Server Action**, which validates them (zod) and checks or stores a **slow, salted password hash** (never the password). **2. Session**: on success the server creates a **session token**, here a **signed JWT** made with `jose`, and stores it in a cookie that is **httpOnly** (JavaScript can't read it), **Secure** and **SameSite=Lax**. **3. Verifying**: a small **Data Access Layer** (`lib/dal.ts`, marked `server-only`) exposes `verifySession()` and `getCurrentUser()`; every page, Server Action and route handler that touches private data calls them. Because the token is signed, a user who edits it is rejected. **4. Optimistic redirects**: `proxy.ts` sends visitors without a valid cookie to `/login` early, for a smoother experience, but it's never the only check. For production apps, a library (Auth.js, Better Auth, Clerk, Supabase Auth) usually handles OAuth, password resets, MFA and session rotation; understanding this flow lets you use any of them safely.
</En>
<Ur>
**Authentication** jawab deta hai "aap kaun hain?" aur **authorisation** jawab deta hai "aap ko kya karne ki ijazat hai?". Next.js app me is ke chaar hisse hain. **1. Sign up / log in**: form credentials **Server Action** ko bhejta hai, jo unhen validate karta hai (zod) aur **sust, salted password hash** check ya mehfooz karta hai (password kabhi nahi). **2. Session**: kamyabi par server **session token** banata hai, yahan `jose` se bana **signed JWT**, aur use aisi cookie me rakhta hai jo **httpOnly** (JavaScript ise nahi parh sakti), **Secure** aur **SameSite=Lax** ho. **3. Tasdeeq**: chhoti si **Data Access Layer** (`lib/dal.ts`, `server-only` nishaan zad) `verifySession()` aur `getCurrentUser()` deti hai; private data chhune wala har page, Server Action aur route handler inhen call karta hai. Kyun ke token signed hai, ise badalne wala user radd ho jata hai. **4. Optimistic redirects**: `proxy.ts` bina durust cookie wale visitors ko jaldi `/login` bhejta hai, behtar tajurbe ke liye, magar ye kabhi wahid check nahi. Production apps me aam taur par library (Auth.js, Better Auth, Clerk, Supabase Auth) OAuth, password reset, MFA aur session rotation sambhalti hai; ye flow samajhna aap ko in me se koi bhi mehfooz tareeqe se istemal karne deta hai.

## Picture it

<Tr>
<En>

Think of a **concert with wristbands**.

- At the **ticket desk**, staff check your ID and ticket (log-in with password check). They never keep a copy of your house key, only a way to recognise it (the password **hash**).
- You get a **wristband** with a tamper-proof seal (the **signed session cookie**). You can see what's printed on it, but if you cut and re-glue it to say "VIP", the seal breaks (forged token rejected).
- The wristband is **sewn on** so pickpockets can't slip it off (httpOnly: page scripts can't read it).
- A steward at the **entrance to each area** glances at wristbands and sends people without one back to the desk (proxy's optimistic redirect).
- The **VIP lounge door** has its own guard who scans the band and checks the guest list (the DAL + role check in the page). Even if someone sneaks past the first steward, they don't get into the lounge.
- Leaving early? The band is cut off (log-out deletes the cookie).

</En>
<Ur>

**Wristbands wale concert** ka sochein.

- **Ticket desk** par staff aap ki ID aur ticket check karta hai (password check ke saath log-in). Wo aap ke ghar ki chaabi ki copy kabhi nahi rakhte, sirf use pehchanne ka tareeqa (password **hash**).

## Learn it step by step

<Walkthrough>

<Step title="Store users with slow, salted password hashes">

<Tr>
<En>
Never store passwords. Store the output of a **slow** hash with a **random salt** (Password Storage lesson). Node's built-in `scrypt` is a good choice; `bcrypt` and `argon2` are common too. Our "database" is an array in server memory, seeded with one admin.
</En>
<Ur>
Passwords kabhi mehfooz na karein. **Random salt** ke saath **sust** hash ka output mehfooz karein (Password Storage lesson). Node ka bana banaya `scrypt` achha intikhab hai; `bcrypt` aur `argon2` bhi aam hain. Hamara "database" server memory me ek array hai, ek admin ke saath.
</Ur>
</Tr>

```ts
// lib/users.ts
import "server-only";
import { randomBytes, scrypt, timingSafeEqual } from "node:crypto";
import { promisify } from "node:util";

const scryptAsync = promisify(scrypt) as (pw: string, salt: string, len: number) => Promise<Buffer>;

export type User = { id: string; name: string; email: string; role: "user" | "admin"; passwordHash: string };

// Pretend database table, kept in server memory
const db = globalThis as unknown as { users?: User[] };
db.users ??= [];

export async function hashPassword(password: string) {
  const salt = randomBytes(16).toString("hex");
  const key = await scryptAsync(password, salt, 64);
  return `${salt}:${key.toString("hex")}`;
}

export async function checkPassword(password: string, stored: string) {
  const [salt, keyHex] = stored.split(":");
  const key = await scryptAsync(password, salt, 64);
  return timingSafeEqual(key, Buffer.from(keyHex, "hex"));
}

export async function createUser(name: string, email: string, password: string, role: User["role"] = "user") {
  const user: User = { id: crypto.randomUUID(), name, email, role, passwordHash: await hashPassword(password) };
  db.users!.push(user);
  return user;
}

export async function findUserByEmail(email: string) {
  return db.users!.find((u) => u.email === email) ?? null;
}

export async function findUserById(id: string) {
  return db.users!.find((u) => u.id === id) ?? null;
}

export function allUsers() {
  return db.users!;
}

// Seed one admin the first time the module loads
if (!db.users.some((u) => u.role === "admin")) {
  createUser("Ava Admin", "admin@example.com", "correct-horse-battery", "admin");
}
```

```text
What a stored hash looks like (salt : key), for the password "blue-teapot-2026":
ed94f821636050565043b336cd9b5f90:54dd645…   (length 161)
```

<Happened>
<Tr>
<En>

- The stored value is `salt:key`: 32 hex characters of salt, a colon, and 128 hex characters of derived key. The original password can't be recovered from it; to check a login we hash the attempt with the **same salt** and compare.
- `timingSafeEqual` compares in constant time, so an attacker can't learn how many bytes matched from response times.
- `import "server-only"` makes the **build fail** if this file is ever imported into a Client Component (shown in step 5).

</En>
<Ur>

- Mehfooz value `salt:key` hai: salt ke 32 hex huroof, colon, aur nikali gayi key ke 128 hex huroof. Is se asal password wapas nahi mil sakta; login check karne ke liye hum koshish ko **usi salt** se hash kar ke milate hain.
- `timingSafeEqual` mustaqil waqt me muqabla karta hai, isliye hamla awar response ke waqt se nahi seekh sakta ke kitne bytes mile.
- `import "server-only"` ye file kabhi Client Component me import ho to **build fail** kar deta hai (step 5 me dikhaya).

</Ur>
</Tr>
</Happened>

<Step title="Sessions: a signed token in an httpOnly cookie">

<Tr>
<En>
After a successful log-in, the server must remember the user on the next request. We put `{ userId, role, expiresAt }` in a **JWT signed** with a secret only the server knows, and store it in a cookie with safe flags.
</En>
<Ur>
Kamyab log-in ke baad server ko agli request par user yaad rakhna hai. Hum `{ userId, role, expiresAt }` ko aise secret se **signed JWT** me rakhte hain jo sirf server janta hai, aur use mehfooz flags wali cookie me mehfooz karte hain.
</Ur>
</Tr>

```ts
// lib/session.ts
import "server-only";
import { SignJWT, jwtVerify } from "jose";
import { cookies } from "next/headers";

export type SessionPayload = { userId: string; role: "user" | "admin"; expiresAt: string };

const key = new TextEncoder().encode(process.env.SESSION_SECRET);

export async function encrypt(payload: SessionPayload) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: "HS256" })
    .setIssuedAt()
    .setExpirationTime("7d")
    .sign(key);
}

export async function decrypt(token: string | undefined) {
  if (!token) return null;
  try {
    const { payload } = await jwtVerify<SessionPayload>(token, key, { algorithms: ["HS256"] });
    return payload;
  } catch {
    return null; // bad signature, expired, or malformed
  }
}

export async function createSession(userId: string, role: SessionPayload["role"]) {
  const expires = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000);
  const token = await encrypt({ userId, role, expiresAt: expires.toISOString() });
  (await cookies()).set("session", token, {
    httpOnly: true,                                  // JavaScript in the page can't read it
    secure: process.env.NODE_ENV === "production",   // HTTPS only in production
    sameSite: "lax",                                 // not sent on cross-site POSTs
    expires,
    path: "/",
  });
}

export async function deleteSession() {
  (await cookies()).delete("session");
}
```

<Happened>
<Tr>
<En>

- `SESSION_SECRET` comes from `.env.local` (generated with `openssl rand -base64 32`, 44 characters). Never commit it; if it leaks, anyone can mint valid sessions, so rotate it.
- The cookie flags matter: **httpOnly** blocks `document.cookie` (so an XSS bug can't steal the session), **Secure** keeps it off plain HTTP, **SameSite=Lax** stops other sites from sending it with cross-site POST requests.
- Despite the function name `encrypt` (taken from the Next.js docs), a JWT is **signed, not encrypted**: anyone holding it can read the payload. Step 6 proves that. Keep only IDs and roles in it, never emails, addresses or secrets.

</En>
<Ur>

- `SESSION_SECRET` `.env.local` se aata hai (`openssl rand -base64 32` se bana, 44 huroof). Ise kabhi commit na karein; leak ho to koi bhi durust sessions bana sakta hai, isliye use badal dein.
- Cookie flags ahem hain: **httpOnly** `document.cookie` rokta hai (taa ke XSS bug session chura na sake), **Secure** ise saade HTTP se door rakhta hai, **SameSite=Lax** doosri sites ko cross-site POST requests ke saath ise bhejne se rokta hai.
- Function ke naam `encrypt` ke bawajood (Next.js docs se liya gaya), JWT **signed hai, encrypted nahi**: jis ke paas ho wo payload parh sakta hai. Step 6 ye sabit karta hai. Is me sirf IDs aur roles rakhein, emails, pate ya raaz kabhi nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Sign-up, log-in and log-out as Server Actions">

<Tr>
<En>
The actions validate input, create or check the user, create the session, and redirect. Log-in returns **the same message** whether the email or the password was wrong, so attackers can't use the form to find out which emails have accounts.
</En>
<Ur>
Actions input validate karte hain, user banate ya check karte hain, session banate hain, aur redirect karte hain. Log-in **ek hi paighaam** deta hai chahe email ghalat ho ya password, taa ke hamla awar form se ye pata na laga sakein ke kin emails ke accounts hain.
</Ur>
</Tr>

```ts
// app/actions/auth.ts
"use server";

import { redirect } from "next/navigation";
import { z } from "zod";
import { createSession, deleteSession } from "@/lib/session";
import { checkPassword, createUser, findUserByEmail } from "@/lib/users";

export type AuthState = { message?: string; errors?: Record<string, string[] | undefined>; email?: string };

const SignupSchema = z.object({
  name: z.string().trim().min(2, "Name must be at least 2 characters"),
  email: z.email("Enter a valid email").trim().toLowerCase(),
  password: z
    .string()
    .min(12, "Use at least 12 characters")
    .regex(/[A-Za-z]/, "Include at least one letter")
    .regex(/[0-9]/, "Include at least one number"),
});

export async function signup(prev: AuthState, formData: FormData): Promise<AuthState> {
  const parsed = SignupSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) {
    return { errors: z.flattenError(parsed.error).fieldErrors, email: String(formData.get("email") ?? "") };
  }
  const { name, email, password } = parsed.data;
  if (await findUserByEmail(email)) {
    return { message: "An account with this email already exists.", email };
  }
  const user = await createUser(name, email, password);
  await createSession(user.id, user.role);
  redirect("/dashboard");
}

export async function login(prev: AuthState, formData: FormData): Promise<AuthState> {
  const email = String(formData.get("email") ?? "").trim().toLowerCase();
  const password = String(formData.get("password") ?? "");
  const user = await findUserByEmail(email);
  // Same message whether the email or the password is wrong
  if (!user || !(await checkPassword(password, user.passwordHash))) {
    return { message: "Invalid email or password.", email };
  }
  await createSession(user.id, user.role);
  redirect("/dashboard");
}

export async function logout() {
  await deleteSession();
  redirect("/login");
}
```

```tsx
  submitLabel: string;
};

  return (
    <form action={formAction}>
      {withName && <p><label>Name <input name="name" /></label></p>}

}
```

<Happened>
<Tr>
<En>

- The email was **normalised** to lowercase, so "Emma@Example.com" and "emma@example.com" are the same account.
- The browser's own `type="email"` check blocks obviously broken addresses like `emma@`; the server check (zod) is what really counts.

- Sign-up says "already exists" for duplicates. That reveals which emails have accounts; stricter apps always say "check your email" and send a message instead.

</En>
<Ur>

- Email ko lowercase me **yaksan** kiya gaya, isliye "Emma@Example.com" aur "emma@example.com" ek hi account hain.
- Browser ka apna `type="email"` check `emma@` jaise saaf toote pate rokta hai; asal check server wala (zod) hai.
- Dono nakam log-ins bilkul ek jaisa text dikhate hain. Production me log-in koshishon ko har IP aur har account ke liye **rate-limit** bhi karein, warna hamla awar hazaron passwords aazma sakte hain.
- Sign-up dohre accounts ke liye "already exists" kehta hai. Ye batata hai ke kin emails ke accounts hain; zyada sakht apps hamesha "apna email check karein" keh kar paighaam bhejti hain.

<Step title="The Data Access Layer: one place that decides who you are">

<Tr>
<En>
Instead of reading cookies all over the app, every check goes through two functions in `lib/dal.ts`. `cache()` makes them run once per request even if the layout, the page and three components all call them.
</En>
<Ur>

```ts
// lib/dal.ts
import "server-only";
import { cache } from "react";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import { decrypt } from "./session";
import { findUserById } from "./users";

// Data Access Layer: the ONE place that decides who the current user is
export const verifySession = cache(async () => {
  const token = (await cookies()).get("session")?.value;
  const session = await decrypt(token);
  if (!session) redirect("/login");
  return { userId: session.userId, role: session.role };
});

// Returns only the fields the UI needs (a DTO), never the password hash
export const getCurrentUser = cache(async () => {
  const { userId } = await verifySession();
  const user = await findUserById(userId);
  if (!user) redirect("/login");
  return { id: user.id, name: user.name, email: user.email, role: user.role };
});
```

<Step title="Optimistic redirects in proxy.ts, and keeping auth code server-only">

<Tr>
<En>
Finally, `proxy.ts` gives a smooth experience: logged-out visitors are sent to `/login` before any page code runs, and logged-in users skip the login page. It verifies the signature (cheap, no database) but the pages still do their own checks.
</En>
<Ur>
Aakhir me `proxy.ts` hamwar tajurba deta hai: logged-out visitors kisi page code se pehle `/login` bheje jate hain, aur logged-in users login page chhor dete hain. Ye signature tasdeeq karta hai (sasta, database nahi) magar pages phir bhi apne checks khud karte hain.
</Ur>
</Tr>

```ts
// proxy.ts
import { NextResponse, type NextRequest } from "next/server";
import { decrypt } from "@/lib/session";

const protectedPrefixes = ["/dashboard", "/admin"];
const authPages = ["/login", "/signup"];

export async function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const session = await decrypt(request.cookies.get("session")?.value);

  // Optimistic checks only: the pages verify again through the DAL
  if (protectedPrefixes.some((p) => pathname.startsWith(p)) && !session) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  if (authPages.includes(pathname) && session) {
    return NextResponse.redirect(new URL("/dashboard", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|favicon.ico).*)"],
};
```

## Common mistakes

<Compare>
<Bad title="Checking auth only in the layout or proxy">

```text
// app/dashboard/layout.tsx
const user = await getCurrentUser();   // ✓ runs on first load…
// app/dashboard/invoices/page.tsx
const invoices = await db.invoice.findMany();   // ✗ no check here
// layouts don't re-run on client navigation, and Server Actions / route handlers skip layouts entirely
```

</Bad>
<Good title="Check next to the data">

```text
// lib/invoices.ts (server-only, part of the DAL)

  const me = await getCurrentUser();
  return db.invoice.findMany({ where: { ownerId: me.id }, select: { id: true, total: true, status: true } });
}
```

</Good>
</Compare>

<Compare>
<Bad title="Session in localStorage">

```text
"use client";
localStorage.setItem("token", token);          // any XSS bug can read and send it anywhere
fetch("/api/orders", { headers: { Authorization: `Bearer ${localStorage.getItem("token")}` } });
```

</Bad>
<Good title="httpOnly cookie set by the server">

```text
(await cookies()).set("session", token, { httpOnly: true, secure: true, sameSite: "lax", path: "/" });
// sent automatically with same-site requests; page scripts can't read it
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Storing plain or fast-hashed passwords** (MD5, SHA-256 without a slow KDF).
- **Different messages** for "no such user" and "wrong password", or no rate limiting on log-in.
- **Putting personal data in the JWT payload**: it's readable by anyone with the token.
- **Weak or committed `SESSION_SECRET`**, or one shared between environments.
- **Trusting the role in the token** for sensitive actions after a user's role was changed; read it from the database.
- **Returning full user rows** to Client Components (password hashes, tokens).
- **Redirecting after login to any `?next=` URL** (open redirect); allow only internal paths.
- **Forgetting Server Actions and route handlers**: they are entry points too.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Saade ya tez hash wale passwords mehfooz karna** (MD5, sust KDF ke baghair SHA-256).
- "Aisa user nahi" aur "ghalat password" ke liye **mukhtalif paighaam**, ya log-in par rate limiting nahi.
- **JWT payload me zaati data rakhna**: token wala koi bhi ise parh sakta hai.
- **Kamzor ya commit kiya `SESSION_SECRET`**, ya environments ke darmiyan mushtarka.
- User ka role badalne ke baad hassas actions ke liye **token ke role par bharosa**; ise database se parhein.
- Client Components ko **poori user rows** dena (password hashes, tokens).
- **Login ke baad kisi bhi `?next=` URL par redirect** (open redirect); sirf andaruni paths ki ijazat dein.
- **Server Actions aur route handlers bhoolna**: ye bhi andar aane ke raaste hain.

</Ur>
</Tr>

```text
"use server";
import { updateTag } from "next/cache";
import { z } from "zod";
import { getCurrentUser } from "@/lib/dal";

export async function updateNote(noteId: string, formData: FormData) {
  const me = await getCurrentUser();                               // 1. authenticated (redirects if not)
  const note = await db.note.findUnique({ where: { id: noteId } });
  if (!note || note.ownerId !== me.id) {                           // 2. authorised for THIS note
    return { error: "Note not found." };                           //    same answer for "missing" and "not yours"
  }
  const parsed = z.string().trim().min(1).max(2000).safeParse(formData.get("text"));
  if (!parsed.success) return { error: "Notes must be 1 to 2,000 characters." };   // 3. validated
  await db.note.update({ where: { id: noteId }, data: { text: parsed.data } });
  updateTag(`notes-${me.id}`);                                     // 4. refresh
  return { ok: true };
}
```

## Remember

<Takeaways>
<Tr>
<En>

- **Authentication** = who you are; **authorisation** = what you may do. Do both on the server.
- Hash passwords with a **slow, salted** algorithm (scrypt, bcrypt, argon2); compare in constant time.
- Sessions: a **signed** (or encrypted) token or a database session ID in an **httpOnly, Secure, SameSite=Lax** cookie, with an expiry.
- A JWT payload is **readable**; keep only IDs and roles in it, and keep the secret long, random and private.
- A **server-only DAL** (`verifySession`, `getCurrentUser` with `cache()`) is the single source of truth; return DTOs, not raw rows.
- Check permissions in **every** page, Server Action and route handler that touches private data; proxy redirects are optimistic.
- Same error for wrong email/password, rate limits, no open redirects.
- Prefer a maintained library for OAuth, password resets, MFA and session rotation.

</En>
<Ur>

- **Authentication** = aap kaun hain; **authorisation** = aap kya kar sakte hain. Dono server par karein.
- Passwords ko **sust, salted** algorithm (scrypt, bcrypt, argon2) se hash karein; mustaqil waqt me muqabla karein.
- Sessions: **httpOnly, Secure, SameSite=Lax** cookie me **signed** (ya encrypted) token ya database session ID, muddat ke saath.
- JWT payload **parha ja sakta** hai; is me sirf IDs aur roles rakhein, aur secret lamba, random aur private rakhein.
- **Server-only DAL** (`cache()` ke saath `verifySession`, `getCurrentUser`) sachai ka wahid zariya hai; kachi rows nahi, DTOs wapas karein.
- Private data chhune wale **har** page, Server Action aur route handler me permissions check karein; proxy redirects optimistic hain.
- Ghalat email/password ke liye ek jaisa error, rate limits, open redirects nahi.
- OAuth, password reset, MFA aur session rotation ke liye maintained library behtar hai.

</Ur>
</Tr>

<DeepDive title="More about authentication">

**Database sessions.** The cookie holds a long random ID; a `sessions` table maps it to the user and expiry. Log-out, "log out of all devices" and banning are instant (delete rows), at the cost of a database read per request (cache it per request with `cache()`). Store a **hash** of the session ID in the table so a database leak doesn't expose live sessions.

**Refreshing sessions.** Extend the expiry on activity (sliding sessions) and rotate the token after log-in and privilege changes to prevent session fixation.

**OAuth / OpenID Connect.** "Sign in with Google" redirects to the provider, which sends back a code your server exchanges for the user's identity. Libraries handle state and PKCE parameters that prevent CSRF and code interception; don't hand-roll them.

**Passkeys (WebAuthn).** Phishing-resistant log-in with device biometrics; supported by Better Auth, Clerk and others.

**MFA and password reset.** Reset links must be single-use, short-lived random tokens stored hashed; MFA codes need rate limiting.

**Auth.js (NextAuth v5).** Exports `auth()` you call in Server Components, actions and route handlers, with providers for OAuth, email and credentials, and adapters for databases.

**`unauthorized()`.** The 401 counterpart to `forbidden()`, rendering `unauthorized.tsx`, useful when you'd rather show a login prompt than redirect.

</DeepDive>

<DeepDive title="Real world: the admin flag in the cookie">

A small SaaS company stored the whole session in an unsigned cookie: a base64-encoded JSON object like `{"userId":"…","isAdmin":false}`. It looked unreadable to non-developers, and the team assumed nobody would touch it. Admin pages checked `session.isAdmin` from that cookie.

A user who was curious about the strange cookie decoded it in a browser extension, changed `false` to `true`, encoded it again and reloaded. The admin panel appeared, with every customer's billing details. Fortunately they reported it through the company's security contact.

The fixes:

1. Sessions moved to **signed** tokens (and later to database sessions so they could be revoked).
2. Admin status was read from the **database** on every admin request, not from the cookie.
3. A DAL with `requireAdmin()` was added and used by every admin page, route handler and Server Action.
4. All existing sessions were invalidated, forcing everyone to log in again.
5. The company started a small bug bounty, and thanked the reporter publicly.

Base64 is an **encoding**, not security. Anything the client can read, it can change, unless a signature proves it hasn't been.

</DeepDive>

<DeepDive title="Security lens">

- **Credential stuffing** (leaked password lists): rate limiting, breached-password checks, MFA.
- **Session theft**: httpOnly + Secure cookies, short lifetimes, rotation, HTTPS everywhere.
- **CSRF**: SameSite=Lax cookies plus Next.js's Origin check for Server Actions; protect custom POST route handlers too.
- **IDOR**: always filter by owner (`where: { ownerId: me.id }`), never trust IDs from the client.
- **User enumeration**: identical responses and timing for unknown users and wrong passwords.
- **Secrets**: `SESSION_SECRET` in environment variables, different per environment, rotated if leaked.
- **Logging**: never log passwords, tokens or full cookies.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is the difference between authentication and authorisation?">
Authentication verifies identity, for example by checking a password or an OAuth login, and results in a session. Authorisation decides whether that identity may perform a specific action on a specific resource, for example whether a user can view an invoice or is an admin.
</QA>

<QA q="Stateless JWT sessions vs database sessions?">
Stateless sessions store signed or encrypted data in the cookie, so verification needs no database lookup and scales easily, but tokens can't be revoked before expiry and the payload size is limited. Database sessions store a random ID in the cookie and data on the server, enabling instant revocation and richer data at the cost of a lookup per request.
</QA>

<QA q="Where do you check authorisation in a Next.js App Router app?">
In a server-only Data Access Layer called from every Server Component, Server Action and Route Handler that reads or changes protected data. Proxy and layouts can do optimistic checks for UX, but they don't cover every entry point, and layouts don't re-render on client navigation.
</QA>

<QA q="How should passwords be stored?">
As salted hashes produced by a deliberately slow, memory-hard function such as argon2id, scrypt or bcrypt, never in plain text or with fast hashes. Verification recomputes the hash with the stored salt and compares in constant time.
</QA>

<QA q="Which cookie attributes should a session cookie have?">
HttpOnly so scripts can't read it, Secure so it's only sent over HTTPS, SameSite Lax or Strict to limit cross-site sending, a reasonable expiry, and a path scope. The value should be signed, encrypted or an opaque random ID.
</QA>

</DeepDive>

<DeepDive title="All key terms">

<Terms>
  <Term name="Authentication">Verifying who a user is.</Term>
  <Term name="Authorisation">Deciding what an authenticated user may do.</Term>
  <Term name="Password hash">The stored output of a slow, salted one-way function.</Term>
  <Term name="Salt">A random value combined with a password before hashing.</Term>
  <Term name="Session">State that identifies a logged-in user across requests.</Term>
  <Term name="JWT">A signed token made of a header, payload and signature.</Term>
  <Term name="Signature">Proof that a token was created by the holder of the secret and not changed.</Term>
  <Term name="httpOnly cookie">A cookie that page JavaScript cannot read.</Term>
  <Term name="SameSite">A cookie attribute limiting when it is sent with cross-site requests.</Term>
  <Term name="Data Access Layer">Server-only functions that centralise auth checks and data access.</Term>
  <Term name="DTO">An object exposing only the fields a consumer may see.</Term>
  <Term name="server-only">A package that fails the build if a module is imported on the client.</Term>
  <Term name="forbidden">A Next.js function rendering the 403 UI.</Term>
  <Term name="User enumeration">Discovering which accounts exist from differing responses.</Term>
  <Term name="Rate limiting">Restricting how many attempts are allowed in a time window.</Term>
</Terms>
