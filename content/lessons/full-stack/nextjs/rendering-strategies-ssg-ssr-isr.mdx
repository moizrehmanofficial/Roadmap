<BigIdea>
<Tr>
<En>
A web page is HTML, and someone has to produce that HTML. The question is **when**. With **Static Site Generation (SSG)** it's produced **once at build time** and served as a file: fastest, cheapest, same for everyone, but only as fresh as the last build. With **Server-Side Rendering (SSR)** it's produced **on every request**: always fresh and can be personal (cookies, user data), but every visitor waits for the server and your database works for each one. **Incremental Static Regeneration (ISR)** is the middle way: a static page that Next.js **rebuilds in the background** after a time limit (`revalidate = 60`) or when you ask (`revalidatePath`, `revalidateTag`), so visitors keep getting fast cached HTML. **Client-Side Rendering (CSR)** sends a mostly empty page and lets JavaScript in the browser fetch and draw the data, useful for highly interactive, private, live parts. Next.js picks the strategy **per route** automatically: no request data → static; `cookies()`, `headers()`, `connection()`, `searchParams` → dynamic; `revalidate` → ISR. With **Cache Components** in Next.js 16, the choice becomes per **component**: a page's static and cached parts are prerendered into a shell and only the request-specific parts are rendered per request (**Partial Prerendering**).
</En>
<Ur>
Web page HTML hai, aur kisi ko wo HTML banana hota hai. Sawal ye hai ke **kab**. **Static Site Generation (SSG)** me ye **build ke waqt ek dafa** banta aur file ki tarah diya jata hai: sab se tez, sab se sasta, sab ke liye ek jaisa, magar sirf aakhri build jitna taaza. **Server-Side Rendering (SSR)** me ye **har request par** banta hai: hamesha taaza aur zaati ho sakta hai (cookies, user data), magar har visitor server ka intezar karta hai aur aap ka database har ek ke liye kaam karta hai. **Incremental Static Regeneration (ISR)** darmiyani raasta hai: static page jise Next.js waqt ki hadd (`revalidate = 60`) ke baad ya aap ke kehne par (`revalidatePath`, `revalidateTag`) **peeche se dobara banata** hai, taa ke visitors ko tez cache shuda HTML milta rahe. **Client-Side Rendering (CSR)** taqreeban khaali page bhejta hai aur browser ke JavaScript ko data la kar banane deta hai, jo bohot interactive, private, live hisson ke liye kaam ka hai. Next.js **har route** ke liye strategy khud chunta hai: request data nahi → static; `cookies()`, `headers()`, `connection()`, `searchParams` → dynamic; `revalidate` → ISR. Next.js 16 ke **Cache Components** ke saath intikhab har **component** ka ho jata hai: page ke static aur cache shuda hisse shell me pehle se render hote hain aur sirf request wale hisse har request par render hote hain (**Partial Prerendering**).
</Ur>
</Tr>
</BigIdea>

## At a glance

<Glance>
<What>

<En>

| --- | --- | --- | --- | --- | --- |
| **SSG** | at build | as of the last build | fastest (CDN file) | no | ○ (or ● with `generateStaticParams`) |

| **CSR** | in the browser | live | fast shell, then loading | yes | (a client component) |
| **PPR** (Cache Components) | static shell at build + request parts streamed | mixed | fast shell, streamed holes | partly | ◐ |

</What>
<Why>
<Tr>
<En>

- The choice decides **speed** (time to first byte), **cost** (server and database load per visitor), **freshness** and **SEO** (search engines get full HTML with SSG/SSR/ISR, not with CSR).
- Most performance problems in Next.js apps are pages that are **dynamic by accident** (one `cookies()` call made the whole page SSR) or **static by accident** (a page that should update never does).
- It's one of the most common interview topics for React and Next.js roles.

</En>
<Ur>

- Intikhab **raftaar** (pehle byte ka waqt), **kharcha** (har visitor par server aur database ka bojh), **taazgi** aur **SEO** (search engines ko SSG/SSR/ISR ke saath poora HTML milta hai, CSR ke saath nahi) tay karta hai.
- Next.js apps ke zyada tar performance masle aise pages hain jo **ghalti se dynamic** hain (ek `cookies()` call ne poora page SSR bana diya) ya **ghalti se static** (jo page update hona chahiye wo kabhi nahi hota).
- Ye React aur Next.js naukriyon ke sab se aam interview mauzooat me se hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Page | Strategy |
| --- | --- |
| Marketing pages, docs, about, pricing | SSG |
| Blog posts, product pages from a CMS | SSG/ISR with on-demand revalidation (webhook) |
| Category pages with prices that change hourly | ISR (`revalidate = 3600`) |
| Search results with `?q=` | SSR (or PPR: static layout + streamed results) |
| Dashboard, account, cart | SSR / PPR, with private data per request |
| Live chat, stock tickers, collaborative editing | CSR (+ WebSockets) inside a server-rendered page |

</En>
<Ur>

| Page | Strategy |
| --- | --- |
| Marketing pages, docs, about, pricing | SSG |
| CMS se blog posts, product pages | on-demand revalidation (webhook) ke saath SSG/ISR |
| Har ghante badalti qeematon wale category pages | ISR (`revalidate = 3600`) |
| `?q=` wale search nataij | SSR (ya PPR: static layout + stream hote nataij) |
| Dashboard, account, cart | SSR / PPR, har request ke private data ke saath |
| Live chat, stock tickers, mil kar editing | server rendered page ke andar CSR (+ WebSockets) |

</Ur>
</Tr>
</When>
<How>
<Tr>
<En>

1. Run `next build` and read the route table: ○ static, ● SSG with params, ƒ dynamic, ◐ partial prerender, plus the Revalidate column.
2. If a page is ƒ but shouldn't be, find what reads request data (cookies, headers, searchParams, `connection()`) and move it into a smaller component or a client component.
3. If a page is static but should update, add `revalidate` (classic) or `cacheLife` (Cache Components), and on-demand revalidation for edits.
4. Measure: TTFB in the Network panel, `x-nextjs-cache` response header (HIT, STALE, MISS).

</En>
<Ur>

1. `next build` chala kar route table parhein: ○ static, ● params ke saath SSG, ƒ dynamic, ◐ partial prerender, plus Revalidate column.
2. Agar page ƒ hai magar nahi hona chahiye, dhoondhein ke kya request data parhta hai (cookies, headers, searchParams, `connection()`) aur use chhote component ya client component me le jayen.
3. Agar page static hai magar update hona chahiye, `revalidate` (classic) ya `cacheLife` (Cache Components) jorein, aur edits ke liye on-demand revalidation.
4. Naapein: Network panel me TTFB, `x-nextjs-cache` response header (HIT, STALE, MISS).

</Ur>
</Tr>
</How>

## Picture it

<Tr>
<En>

Think of how a **newspaper** reaches people.

- **SSG** is the **printed morning edition**: printed once at night, stacked at every newsstand, grabbed instantly. Nothing changes until tomorrow's edition (the next build).
- **ISR** is a newsstand that **reprints the front page every hour**: you always get a paper immediately; if the hour has passed, the first buyer still gets the current copy while a fresh batch is printed for the next people. A big breaking story can trigger an **immediate reprint** (on-demand revalidation).
- **SSR** is a **personal news briefing** read to you over the phone: always up to date and about your interests, but you wait while it's prepared, and it costs the newsroom work for every caller.
- **CSR** is handing someone a **blank paper and a radio**: they see the page straight away but have to listen and fill it in themselves.
- **PPR** is a printed paper with a **blank box** where your personal horoscope is added at the stand: most of it is ready instantly, only the box is made for you.

</En>
<Ur>

Sochein **akhbaar** logon tak kaise pohanchta hai.

- **SSG** **chhapa hua subah ka edition** hai: raat ko ek dafa chhapa, har stall par dher, foran utha liya. Kal ke edition (agli build) tak kuch nahi badalta.
- **ISR** aisa stall hai jo **har ghante pehla safha dobara chhapta** hai: aap ko hamesha foran akhbaar milta hai; agar ghanta guzar gaya ho to pehle khareedar ko ab bhi maujooda copy milti hai jab ke agle logon ke liye taaza batch chhapta hai. Bari fori khabar **foran dobara chhapai** karwa sakti hai (on-demand revalidation).
- **SSR** phone par parhi gayi **zaati khabron ki briefing** hai: hamesha taaza aur aap ki dilchaspi ki, magar tayyari ke dauran aap intezar karte hain, aur har call karne wale ke liye newsroom ko kaam karna parta hai.
- **CSR** kisi ko **khaali kaghaz aur radio** dena hai: wo safha foran dekhte hain magar sun kar khud bharna parta hai.
- **PPR** chhapa akhbaar hai jis me ek **khaali dabba** hai jahan stall par aap ka zaati horoscope joda jata hai: zyada tar foran tayyar, sirf dabba aap ke liye banta hai.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="SSG: rendered once, at build time">

<Tr>
<En>
A page with no request data and no time limit is rendered **once during `next build`**. Every visitor gets the same stored HTML. We print the render time to see when it happened.
</En>
<Ur>
Bina request data aur bina waqt ki hadd wala page **`next build` ke dauran ek dafa** render hota hai. Har visitor ko wahi mehfooz HTML milta hai. Hum render ka waqt print karte hain taa ke dekhein ke ye kab hua.
</Ur>
</Tr>

```tsx
// lib/clock.ts
export const now = () => new Date().toISOString().slice(11, 19); // HH:MM:SS (UTC)
export const wait = (ms: number) => new Promise((r) => setTimeout(r, ms));

// app/about/page.tsx
import { now } from "@/lib/clock";

// No dynamic data → rendered once at build time (SSG)
export default function AboutPage() {
  return <p>About Acme. Rendered at {now()}</p>;
}
```

```text
$ npx next build
├ ○ /about

Server started at 21:28:56, two requests:
about ttfb=0.035508s   Rendered at 21:28:47
about ttfb=0.003103s   Rendered at 21:28:47
```

<Happened>
<Tr>
<En>

- The page says **21:28:47**, the build time, even though we requested it after the server started at 21:28:56. No code ran per request: the server just sent a stored file.
- The second request took **3 milliseconds** to the first byte. On a CDN this HTML is served from a location near the user.
- To change this page you **rebuild and redeploy**, or switch it to ISR.

</En>
<Ur>

- Page **21:28:47** batata hai, build ka waqt, halanke humne ise 21:28:56 par server shuru hone ke baad maanga. Har request par koi code nahi chala: server ne bas mehfooz file bheji.
- Doosri request ko pehle byte tak **3 millisecond** lage. CDN par ye HTML user ke qareeb ki jagah se diya jata hai.
- Ye page badalne ke liye aap **dobara build aur deploy** karte hain, ya ise ISR par le jate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="SSR: rendered on every request">

<Tr>
<En>
As soon as a page needs something only the request knows (cookies, headers, the query string) or calls `connection()`, Next.js renders it **for each request**. Our page also pretends to query a database for 300 ms.
</En>
<Ur>
Jaise hi page ko kuch aisa chahiye jo sirf request janti ho (cookies, headers, query string) ya wo `connection()` call kare, Next.js use **har request ke liye** render karta hai. Hamara page 300 ms ki database query ki naqal bhi karta hai.
</Ur>
</Tr>

```tsx
// app/live/page.tsx
import { connection } from "next/server";
import { now, wait } from "@/lib/clock";

// Reads request-time data → rendered on every request (SSR)
export default async function LivePage() {
  await connection();
  await wait(300); // pretend database query
  return <p>Live stock levels. Rendered at {now()}</p>;
}
```

```text
$ npx next build
├ ƒ /live

live ttfb=0.334024s   Rendered at 21:28:56
live ttfb=0.308536s   Rendered at 21:28:57
```

<Happened>
<Tr>
<En>

- Each request shows a **new time**: the page was rendered fresh both times.
- Each visitor waited about **300 ms** before receiving anything, about 100 times longer than the static page. With 1,000 visitors a minute, the database is queried 1,000 times a minute.
- That's the right trade-off for **personal or truly live** content. For everything else, it's wasted work. Streaming (`loading.tsx`, `<Suspense>`) hides some of the wait by sending the page shell first.

</En>
<Ur>

- Har request **naya waqt** dikhati hai: page dono dafa naye sire se render hua.
- Har visitor ne kuch bhi milne se pehle taqreeban **300 ms** intezar kiya, static page se taqreeban 100 guna zyada. Har minute 1,000 visitors ke saath database har minute 1,000 dafa query hota hai.
- **Zaati ya sach me live** content ke liye ye sahi sauda hai. Baqi sab ke liye ye zaya kaam hai. Streaming (`loading.tsx`, `<Suspense>`) page ka shell pehle bhej kar kuch intezar chhupa deti hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="ISR: static, but refreshed in the background">

<Tr>
<En>
`export const revalidate = 10` keeps the page static but allows Next.js to rebuild it **at most every 10 seconds** when someone visits. We used the counting Catalog API from the Data Fetching lesson and changed the Mug's price from $12 to $15 halfway through.
</En>
<Ur>
`export const revalidate = 10` page ko static rakhta hai magar Next.js ko kisi ke aane par use **zyada se zyada har 10 second** me dobara banane deta hai. Humne Data Fetching lesson ki ginne wali Catalog API istemal ki aur beech me Mug ki qeemat $12 se $15 ki.
</Ur>
</Tr>

```tsx
// app/deals/page.tsx
import { now } from "@/lib/clock";

// ISR: static, but rebuilt in the background at most every 10 seconds
export const revalidate = 10;

export default async function DealsPage() {
  const res = await fetch("http://localhost:4000/products");
  const products: { name: string; price: number }[] = await res.json();
  return <p>Today's deal: {products[0].name} for ${products[0].price}. Rendered at {now()}</p>;
}
```

```text
$ npx next build
Route (app)                           Revalidate  Expire
├ ○ /deals                                   10s      1y

time      what the visitor got                          header                API hits
21:29:02  Mug for $12. Rendered at 21:28:47             x-nextjs-cache: STALE  2
21:29:06  Mug for $12. Rendered at 21:29:02             x-nextjs-cache: HIT    2
-- price changed to $15 in the API
21:29:06  Mug for $12. Rendered at 21:29:02             x-nextjs-cache: HIT    2
21:29:14  Mug for $12. Rendered at 21:29:02             x-nextjs-cache: STALE  3
21:29:15  Mug for $15. Rendered at 21:29:15             x-nextjs-cache: HIT    3
21:29:15  Mug for $15. Rendered at 21:29:15             x-nextjs-cache: HIT    3
```

<Happened>
<Tr>
<En>

- At 21:29:02 the build-time page (21:28:47) was older than 10 s, so the visitor got it **immediately** but marked **STALE**, and Next.js regenerated it in the background (API hit #2).
- Within the next 10 seconds, visitors got the cached copy (**HIT**) and the API wasn't called, even after the price changed.
- At 21:29:14 the copy was stale again: that visitor still saw $12 (STALE) while a new version was made, and the very next visitor saw **$15**. Nobody ever waited for the API.
- Freshness guarantee: data can be **up to `revalidate` seconds old, plus one visit**. That's fine for prices on a category page, not for a bank balance.

</En>
<Ur>

- 21:29:02 par build wala page (21:28:47) 10 s se purana tha, isliye visitor ko wo **foran** mila magar **STALE** nishaan ke saath, aur Next.js ne use peeche se dobara banaya (API hit #2).
- Agle 10 second me visitors ko cache copy (**HIT**) mili aur API call nahi hui, qeemat badalne ke baad bhi.
- 21:29:14 par copy phir purani thi: us visitor ne ab bhi $12 dekha (STALE) jab ke naya version bana, aur bilkul agle visitor ne **$15** dekha. Kisi ne kabhi API ka intezar nahi kiya.
- Taazgi ki zamanat: data **`revalidate` seconds tak purana, plus ek visit** ho sakta hai. Category page ki qeematon ke liye theek, bank balance ke liye nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="On-demand revalidation: refresh when data changes">

<Tr>
<En>
Waiting for the timer isn't ideal when you **know** the data just changed (an editor clicked Publish, a webhook arrived). `revalidatePath` (or `revalidateTag`) refreshes it right away.
</En>
<Ur>
Jab aap **jante** hain ke data abhi badla (editor ne Publish dabaya, webhook aaya) to timer ka intezar behtar nahi. `revalidatePath` (ya `revalidateTag`) ise foran taaza karta hai.
</Ur>
</Tr>

```tsx
// app/api/revalidate/route.ts
import { revalidatePath } from "next/cache";

export async function POST(request: Request) {
  if (request.headers.get("x-secret") !== process.env.REVALIDATE_SECRET) {
    return Response.json({ error: "Unauthorized" }, { status: 401 });
  }
  revalidatePath("/deals");
  return Response.json({ revalidated: "/deals" });
}
```

```text
$ curl -X POST -H "x-secret: s3cret" localhost:3500/api/revalidate
{"revalidated":"/deals"}

21:29:16  Mug for $15. Rendered at 21:29:16   x-nextjs-cache: MISS   API hits 4
21:29:17  Mug for $15. Rendered at 21:29:16   x-nextjs-cache: HIT    API hits 4
```

<Happened>
<Tr>
<En>

- After `revalidatePath`, the next request was a **MISS**: the old copy was thrown away and the page was rendered for that visitor, then cached again (HIT).
- A common setup is a long `revalidate` (an hour or a day) as a safety net **plus** on-demand revalidation from your CMS or admin actions, so pages are both fast and up to date.
- With tags (`revalidateTag("products", "max")`) you refresh every page that uses the data without listing paths (Data Fetching and Caching lesson).

</En>
<Ur>

- `revalidatePath` ke baad agli request **MISS** thi: purani copy phenk di gayi aur page us visitor ke liye render hua, phir dobara cache hua (HIT).
- Aam setup lamba `revalidate` (ek ghanta ya din) hifazati jaal ki tarah, **plus** CMS ya admin actions se on-demand revalidation hai, taa ke pages tez bhi hon aur taaza bhi.
- Tags (`revalidateTag("products", "max")`) ke saath aap paths ki list ke baghair data istemal karne wala har page taaza karte hain (Data Fetching and Caching lesson).

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Dynamic routes: generateStaticParams and dynamicParams">

<Tr>
<En>
For `/products/[slug]`, `generateStaticParams` decides which slugs are built ahead of time (●). Here we prebuild only the best seller. What happens to the others depends on `dynamicParams`.
</En>
<Ur>
`/products/[slug]` ke liye `generateStaticParams` tay karta hai ke kaun se slugs pehle se bante hain (●). Yahan hum sirf sab se zyada bikne wala pehle se banate hain. Baqi ka kya hota hai ye `dynamicParams` par munhasir hai.
</Ur>
</Tr>

```tsx
// app/products/[slug]/page.tsx (part)
export function generateStaticParams() {
  return products.slice(0, 1).map((p) => ({ slug: p.slug })); // only the best seller at build time
}
```

```text
$ npx next build
├   /products/[slug]
│ └ ● /products/travel-mug

dynamicParams = true (the default):
travel-mug      200   0.042s   x-nextjs-cache: HIT     ← built at build time
desk-lamp       200   0.085s   x-nextjs-cache: MISS    ← rendered on first request…
desk-lamp       200   0.007s   x-nextjs-cache: HIT     ← …then cached like a static page
no-such-thing   404   0.024s                           ← the page called notFound()

export const dynamicParams = false; // unknown slugs → 404 without rendering
travel-mug      200
desk-lamp       404                                    ← not in the list, never rendered
```

<Happened>
<Tr>
<En>

- With the default (`true`), pages not built in advance are rendered on the **first visit** and then cached. You can prebuild your top 1,000 products and let the long tail fill in on demand, which keeps builds fast.
- With `dynamicParams = false`, only the listed slugs exist; everything else is a 404 without running your code. Good for a small, fixed set (docs versions, country pages).
- Returning an empty array from `generateStaticParams` (with `dynamicParams` true) means "build nothing now, cache each page after its first visit".

</En>
<Ur>

- Default (`true`) ke saath jo pages pehle se nahi bane wo **pehle visit** par render hote hain aur phir cache. Aap apne top 1,000 products pehle se bana kar baqi ko zaroorat par bharne de sakte hain, jo builds tez rakhta hai.
- `dynamicParams = false` ke saath sirf fehrist wale slugs maujood hain; baqi sab aap ka code chalaye baghair 404 hai. Chhote, muqarrar set ke liye achha (docs versions, mulk ke pages).
- `generateStaticParams` se khaali array wapas karna (`dynamicParams` true ke saath) ka matlab hai "abhi kuch na banao, har page ko us ke pehle visit ke baad cache karo".

</Ur>

## Common mistakes

<Compare>
<Bad title="One small personal detail makes the whole page dynamic">

```text
// app/products/page.tsx (classic model)
export default async function Products() {
  const name = (await cookies()).get("name")?.value;   // only for "Hi, Emma"
  const products = await getAllProducts();              // 2,000 products, same for everyone
  return <>{name && <p>Hi, {name}</p>}<ProductGrid products={products} /></>;
}
// ƒ: the product grid is rebuilt for every visitor
```

</Bad>
<Good title="Keep the big part static; isolate the personal part">

```text
// ISR page + a small client component for the greeting (reads a non-httpOnly cookie or /api/me),
// or with Cache Components:
export default function Products() {
  return (
    <>
      <Suspense fallback={null}><Greeting /></Suspense>   {/* reads cookies */}
      <ProductGrid />                                      {/* "use cache" + cacheLife("hours") */}
    </>
  );
}
```

</Good>
</Compare>

<Compare>
<Bad title="SSR for content that rarely changes">

```text
export const dynamic = "force-dynamic";      // "to always be fresh"
export default async function BlogPost({ params }) { … }
// every view queries the CMS; slow pages, rate-limit errors during traffic spikes
```

</Bad>
<Good title="Static + on-demand revalidation">

```text
export const revalidate = 86400;              // safety net: once a day
// the CMS webhook calls revalidatePath(`/blog/${slug}`) when a post is published or edited
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Not reading the build output**: a page you think is static shows ƒ.
- **Very short `revalidate` values** (1 second) on high-traffic pages: almost SSR cost, with stale data anyway.
- **Personal data in ISR/SSG pages**: the first visitor's data would be cached for everyone.
- **Building 100,000 pages at build time** when most are rarely visited: prebuild the popular ones, render the rest on demand.
- **CSR for SEO-critical content** (product descriptions, articles).
- **Testing caching in `next dev`**: development renders on every request; use `next build && next start`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Build output na parhna**: jo page aap static samajhte hain wo ƒ dikhata hai.
- Zyada traffic wale pages par **bohot chhote `revalidate`** (1 second): taqreeban SSR ka kharcha, phir bhi purana data.
- **ISR/SSG pages me zaati data**: pehle visitor ka data sab ke liye cache ho jata.
- **Build ke waqt 100,000 pages banana** jab zyada tar kam dekhe jate hon: maqbool wale pehle se banayen, baqi zaroorat par.
- **SEO ke liye ahem content ke liye CSR** (product descriptions, articles).
- **`next dev` me caching test karna**: development har request par render karta hai; `next build && next start` lein.

</Ur>
</Tr>

<DeepDive title="More about rendering">

**Static export.** `output: "export"` in `next.config.ts` produces plain HTML/CSS/JS files you can host anywhere (S3, GitHub Pages), with no Node server: only SSG and CSR are possible (no ISR, SSR, Server Actions or image optimisation without a custom loader).

**Where ISR state lives.** Self-hosted, regenerated pages are stored in `.next` on that server's disk; with several servers, configure a shared cache handler so instances don't serve different versions. Platforms like Vercel handle this for you.

**`expire`.** The second column in the build table: after this long without a visit, a stale page isn't served as STALE anymore; it's rebuilt before responding.

**Edge vs Node.js.** SSR can run close to users on edge runtimes for lower latency, with fewer APIs available; most apps use Node.js.

**Streaming SSR.** SSR doesn't have to wait for everything: `loading.tsx` and `<Suspense>` send the shell first, which improves perceived speed and TTFB.

**Hydration cost.** Server-rendered HTML still needs JavaScript to become interactive; keeping most components as Server Components reduces that cost regardless of strategy.

**Other frameworks.** The same ideas exist elsewhere: Astro (static by default with islands), Nuxt (`routeRules` with `swr`), Remix/React Router (SSR with HTTP caching), Gatsby (SSG).

</DeepDive>

<DeepDive title="Real world: Black Friday on SSR">

A fashion retailer rendered every product page with SSR because "prices must always be correct". On a normal day this worked: about 50 requests per second, each querying the product database and a pricing service for around 200 ms.

On Black Friday traffic reached 2,000 requests per second. The pricing service, called on every page view, hit its rate limit; pages started taking 8 seconds, then returned errors. The database connection pool was exhausted, which also broke checkout, the one part that truly had to work.

After the incident, the team split the page by how fresh each part needed to be:

1. Product details, images and descriptions became ISR with on-demand revalidation from the product system (changes are rare and known).
2. Prices were cached with a 60-second lifetime and revalidated by tag when the pricing team changed them.
3. Stock levels ("only 3 left") became a small client component polling a cached API every 30 seconds.
4. Checkout stayed fully dynamic, with prices re-validated on the server before payment.

The following year's sale peaked at 3,500 requests per second. Product pages were served from the CDN in under 50 ms, the pricing service received a few hundred calls per minute instead of thousands per second, and checkout never slowed down.

</DeepDive>

<DeepDive title="Security lens">

- **Never cache personal data in shared pages** (SSG/ISR/`"use cache"` without the user in the key); the first visitor's data would be shown to everyone. Watch out for user-specific headers or cookies read in "static" code paths.
- **Revalidation endpoints** must check a secret or signature and be rate-limited; otherwise attackers can force constant regeneration (a cheap denial-of-service).
- **Prices and permissions** shown from cache are for display only: re-check on the server at checkout or when performing actions.
- **Static pages can't check auth**: anything in a static page is public. Protect private content with dynamic rendering and the DAL.
- **CDN caching headers**: make sure dynamic, personal responses aren't cached by a CDN (`Cache-Control: private, no-store`); Next.js sets this for dynamic routes, but custom headers can override it.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What's the difference between SSG, SSR, ISR and CSR?">
SSG renders HTML at build time and serves the same file to everyone. SSR renders HTML on the server for each request, allowing fresh and personalised content at a performance and cost price. ISR serves static HTML but regenerates it after a revalidation interval or on demand, using stale-while-revalidate. CSR renders in the browser using JavaScript and client-side data fetching.
</QA>

<QA q="How does Next.js decide whether a route is static or dynamic?">
In the classic model, a route is static unless it uses dynamic APIs such as cookies, headers, searchParams, connection, uncached fetches, or segment config like dynamic force-dynamic; revalidate makes it ISR. With Cache Components, everything is prerendered into a static shell except components that access runtime data or uncached I/O, which must be inside Suspense or cached with use cache.
</QA>

<QA q="How does ISR serve fresh content without making users wait?">
After the revalidation period, the next request still receives the cached page immediately while Next.js regenerates it in the background. Once regeneration succeeds, subsequent requests receive the new version. On-demand revalidation with revalidatePath or revalidateTag invalidates the cache when data changes.
</QA>

<QA q="What is Partial Prerendering?">
A rendering model where each route has a static shell prerendered at build time, including cached data and Suspense fallbacks, and dynamic parts that depend on the request are rendered at request time and streamed into the shell, combining static speed with dynamic content in one response.
</QA>

<QA q="What do generateStaticParams and dynamicParams do?">
generateStaticParams returns the dynamic segment values to prerender at build time. dynamicParams controls what happens for other values: true renders them on demand and caches the result, false returns 404.
</QA>

</DeepDive>
