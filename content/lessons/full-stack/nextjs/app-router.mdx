<BigIdea>
<Tr>
<En>
**Next.js** is a framework built on React that adds what a real website needs: pages with URLs, server rendering, data loading, APIs and optimised builds. Its **App Router** uses **file-based routing**: the **folders inside `app/` are the URLs**. A file called **`page.tsx`** makes a folder visible as a page, so `app/about/page.tsx` is `/about` and `app/page.tsx` is the home page `/`. A **`layout.tsx`** wraps all the pages below it (a shared header and footer), and layouts **nest**. Folder names in square brackets are **dynamic**: `app/blog/[slug]/page.tsx` handles `/blog/hello-world`, `/blog/spring-sale` and any other slug, and the page receives the slug in `params`. You move between pages with the **`<Link>`** component, which loads the next page without a full browser reload. No routing configuration file is needed: create a folder, add `page.tsx`, and the URL exists.
</En>
<Ur>
**Next.js** React par bana framework hai jo wo cheezen jorta hai jo asli website ko chahiyen: URLs wale pages, server rendering, data loading, APIs aur behtar banaye gaye builds. Is ka **App Router** **file-based routing** istemal karta hai: **`app/` ke andar ke folders hi URLs hain**. **`page.tsx`** naam ki file folder ko page ki shakal me nazar aane wala banati hai, isliye `app/about/page.tsx` `/about` hai aur `app/page.tsx` home page `/` hai. **`layout.tsx`** apne neeche ke tamam pages ko lapetta hai (mushtarak header aur footer), aur layouts ek doosre ke andar **aate** hain. Square brackets wale folder ke naam **dynamic** hote hain: `app/blog/[slug]/page.tsx` `/blog/hello-world`, `/blog/spring-sale` aur har doosra slug sambhalta hai, aur page ko slug `params` me milta hai. Pages ke darmiyan **`<Link>`** component se jaya jata hai, jo browser ko poora reload kiye baghair agla page lata hai. Routing ki koi configuration file nahi chahiye: folder banayen, `page.tsx` jorein, aur URL ban gaya.
</Ur>
</Tr>
</BigIdea>

<Why>
<Tr>
<En>

- **No routing setup.** The folder tree **is** the site map; anyone can find the code for `/dashboard/settings` by opening that folder.
- **Shared layouts** stay on screen while you navigate, so headers and sidebars don't flicker or lose state.
- **Fast navigation.** `<Link>` fetches only what changed and prefetches pages that are visible in links.
- **Server rendering by default.** Pages are HTML from the start, which is good for speed and search engines (more in the next lesson).

</En>

## Picture it

<Tr>
<En>

Think of a **shopping centre**.

- Each **folder** is a **corridor**, and corridors lead off other corridors: the "Blog" corridor, and off it, one door per post.
- A **`page.tsx`** is a **shop door** with a sign. A corridor without a door is just a passage: you can't visit it, but it can lead somewhere.
- A **`layout.tsx`** is the **corridor itself**: the walls, signs and lighting that stay the same while you walk from shop to shop. The main entrance hall (the root layout) wraps everything; the "Dashboard" wing has its own extra signage.
- A **`[slug]`** folder is a door marked **"Any number"**: one door design that opens onto unit 1, unit 2 or unit 300, and the unit number is written on your ticket (`params`).
- **`not-found.tsx`** is the information desk that says "Sorry, there's no shop with that name."

</En>
<Ur>

Ek **shopping centre** ka sochein.

- Har **folder** ek **rahdari** hai, aur rahdariyan doosri rahdariyon se nikalti hain: "Blog" ki rahdari, aur us se har post ka ek darwaza.
- **`page.tsx`** board wala **dukaan ka darwaza** hai. Baghair darwaze ki rahdari bas guzargah hai: aap us me "ja" nahi sakte, magar wo kahin le ja sakti hai.
- **`layout.tsx`** **khud rahdari** hai: deewaren, board aur roshni jo ek dukaan se doosri tak chalte waqt wahi rehti hain. Bara darwaze wala hall (root layout) har cheez ko lapetta hai; "Dashboard" wing ke apne izafi board hain.
- **`[slug]`** folder **"Koi bhi number"** wala darwaza hai: ek hi design ka darwaza jo unit 1, unit 2 ya unit 300 par khulta hai, aur unit ka number aap ke ticket (`params`) par likha hota hai.
- **`not-found.tsx`** wo information desk hai jo kehta hai "Maazrat, is naam ki koi dukaan nahi."

</Ur>
</Tr>

<Step title="The home page and the root layout">

<Tr>
<En>
Every App Router app needs two files to start: `app/layout.tsx` (the shell around every page) and `app/page.tsx` (the home page, `/`).
</En>
<Ur>
Har App Router app ko shuru karne ke liye do files chahiyen: `app/layout.tsx` (har page ke gird ka khol) aur `app/page.tsx` (home page, `/`).
</Ur>
</Tr>

```tsx
// app/layout.tsx
import Link from "next/link";
import "./globals.css";

export const metadata = { title: "Fresh Mart" };

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <nav>
          <Link href="/">Home</Link> | <Link href="/about">About</Link> |{" "}
          <Link href="/blog">Blog</Link> | <Link href="/dashboard">Dashboard</Link>
        </nav>
        <main>{children}</main>
        <footer>© Fresh Mart</footer>
      </body>
    </html>
  );
}

// app/page.tsx
export default function HomePage() {
  return <h1>Welcome to Fresh Mart</h1>;
}
```

```text
Visiting the pages
/            → 200 | title: Fresh Mart | Welcome to Fresh Mart
```

<Happened>
<Tr>
<En>

- The **root layout** is the only place with `<html>` and `<body>`. It's required, and it wraps **every** page in the app.
- `{children}` is where the current page goes. For `/`, that's `HomePage`.
- `export const metadata = { title: … }` sets the browser tab's `<title>`. Next.js reads it on the server; no `useEffect` needed.
- Both files **default-export** a component. The name of the function doesn't matter to Next.js; the file name and folder do.

</En>
<Ur>

- **Root layout** wahid jagah hai jahan `<html>` aur `<body>` hain. Ye lazmi hai, aur app ke **har** page ko lapetta hai.
- `{children}` wo jagah hai jahan maujooda page aata hai. `/` ke liye ye `HomePage` hai.
- `export const metadata = { title: … }` browser tab ka `<title>` set karta hai. Next.js ise server par parhta hai; `useEffect` ki zaroorat nahi.
- Dono files component ko **default-export** karti hain. Function ka naam Next.js ke liye ahem nahi; file ka naam aur folder ahem hain.

</Ur>
</Tr>
</Happened>

</Step>

<En>
To add `/about`, create the folder `app/about` and put a `page.tsx` in it. That's the whole routing step. A page can also set its own `metadata`.

`/about` jorne ke liye `app/about` folder banayen aur us me `page.tsx` rakhein. Routing ka poora qadam yahi hai. Page apna `metadata` bhi set kar sakta hai.

<Step title="Only page.tsx makes a route">

<Tr>
<En>
You can keep other files inside `app/` (components, helpers, styles). They're **not** pages: only a file named `page.tsx` (or `route.ts`, for APIs) becomes visitable.
</En>
<Ur>
Aap `app/` ke andar doosri files bhi rakh sakte hain (components, helpers, styles). Ye pages **nahi**: sirf `page.tsx` naam ki file (ya APIs ke liye `route.ts`) jane ke qabil banti hai.
</Ur>
</Tr>

```tsx

}
```

```text
Visiting the pages
/components/Price → 404 | title: Fresh Mart | Page not found Back to the home page
/missing          → 404 | title: Fresh Mart | Page not found Back to the home page
```

<Happened>
<Tr>
<En>

- `app/components/Price.tsx` is just a component to import; it isn't a page, so its URL is a 404.
- `/missing` doesn't match any folder: also 404. Both show our custom `app/not-found.tsx` (step 9).
- Many projects keep shared components **outside** `app/` (for example `components/` at the project root) or in a folder starting with `_`, like `app/_components`, which Next.js always ignores for routing.

</En>
<Ur>

- `app/components/Price.tsx` sirf import karne wala component hai; ye page nahi, isliye is ka URL 404 hai.
- `/missing` kisi folder se nahi milta: ye bhi 404. Dono hamara apna `app/not-found.tsx` dikhate hain (qadam 9).
- Kai projects mushtarak components `app/` ke **bahar** rakhte hain (maslan project ke root par `components/`) ya `_` se shuru hone wale folder me, jaise `app/_components`, jise Next.js routing me hamesha nazar andaz karta hai.

</Ur>
</Tr>
</Happened>

<Step title="Moving between pages with Link">

<Tr>
<En>
Use `<Link href="…">` from `next/link` for links inside your app. It renders a normal `<a>`, but clicking it **swaps only the page part** instead of reloading the whole site.
</En>
<Ur>
App ke andar ke links ke liye `next/link` ka `<Link href="…">` lein. Ye aam `<a>` banata hai, magar click karne par poori site reload karne ke bajaye **sirf page wala hissa badalta** hai.
</Ur>
</Tr>

```tsx
// app/blog/page.tsx
import Link from "next/link";
import { posts } from "@/lib/posts";

export default function BlogPage() {
  return (
    <>
      <h1>Blog</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.slug}>
            <Link href={`/blog/${post.slug}`}>{post.title}</Link>
          </li>
        ))}
      </ul>
    </>
  );
}

// lib/posts.ts
export const posts = [
  { slug: "hello-world", title: "Hello, world", body: "Our very first post." },
  { slug: "spring-sale", title: "Spring sale", body: "Everything is 20% off this week." },
];

export function getPost(slug: string) {
  return posts.find((post) => post.slug === slug);
}
```

```text
Visiting the pages
/blog        → 200 | title: Fresh Mart | Blog Hello, world Spring sale
```

<Happened>
<Tr>
<En>

- The blog page lists both posts as links to `/blog/hello-world` and `/blog/spring-sale`.
- When a user clicks one, Next.js fetches just the new page's content, keeps the layout (nav, footer) in place, and updates the URL. Links visible on screen are **prefetched** in production, so the click feels instant.
- Use a plain `<a>` only for links **outside** your app.
- `@/lib/posts` is a path alias for the project root, set up by `create-next-app`.

</En>
<Ur>

- Blog page dono posts ko `/blog/hello-world` aur `/blog/spring-sale` ke links ki shakal me dikhata hai.
- User kisi par click kare to Next.js sirf naye page ka mawad lata hai, layout (nav, footer) apni jagah rakhta hai, aur URL update karta hai. Production me screen par nazar aane wale links **pehle se mangwa** liye jate hain, isliye click foran mehsoos hota hai.
- Saada `<a>` sirf app ke **bahar** ke links ke liye lein.
- `@/lib/posts` project root ka path alias hai, jo `create-next-app` set karta hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Dynamic routes: one page for many URLs">

<Tr>
<En>
A folder named in **square brackets**, like `[slug]`, matches **any value** in that position. The page receives it in **`params`**. In Next.js 15 and later, `params` is a **promise**, so the page is `async` and `await`s it.
</En>
<Ur>
**Square brackets** wala folder, jaise `[slug]`, us jagah **koi bhi value** se milta hai. Page use **`params`** me leta hai. Next.js 15 aur baad me `params` ek **promise** hai, isliye page `async` hota hai aur us ka `await` karta hai.
</Ur>
</Tr>

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from "next/navigation";
import { getPost, posts } from "@/lib/posts";

export function generateStaticParams() {
  return posts.map((post) => ({ slug: post.slug }));
}

export default async function PostPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = getPost(slug);
  if (!post) notFound();

  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.body}</p>
    </article>
  );
}
```

```text
Visiting the pages
/blog/hello-world → 200 | title: Fresh Mart | Hello, world Our very first post.
/blog/nope        → 404 | (shows "Page not found")
```

<Happened>
<Tr>
<En>

- One file served every post. For `/blog/hello-world`, `params` resolved to `{ slug: "hello-world" }`.
- For `/blog/nope`, `getPost` found nothing, so `notFound()` stopped the page and Next.js sent a real **404** with the not-found page.
- `generateStaticParams` tells Next.js which slugs exist **at build time**, so those pages are generated once as static HTML. In the build output they're marked `●` (SSG). Slugs added later still work; they're rendered when first requested.
- The folder name decides the key: `[slug]` gives `params.slug`; `[id]` would give `params.id`.

</En>
<Ur>

- Ek file ne har post dikhayi. `/blog/hello-world` ke liye `params` `{ slug: "hello-world" }` bana.
- `/blog/nope` ke liye `getPost` ko kuch nahi mila, isliye `notFound()` ne page rok diya aur Next.js ne not-found page ke saath asli **404** bheja.
- `generateStaticParams` Next.js ko **build ke waqt** batata hai ke kaun se slugs maujood hain, isliye wo pages ek dafa static HTML ki shakal me bante hain. Build output me unhe `●` (SSG) se nishaan diya jata hai. Baad me jure slugs bhi chalte hain; wo pehli dafa maange jane par bante hain.
- Folder ka naam key tay karta hai: `[slug]` `params.slug` deta hai; `[id]` `params.id` deta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Catch-all routes">

<Tr>
<En>
`[...name]` matches **one or more** segments and gives them to you as an **array**. Useful for category trees and docs paths of any depth.
</En>
<Ur>
`[...name]` **ek ya zyada** segments se milta hai aur unhe **array** ki shakal me deta hai. Kisi bhi gehrai ke category trees aur docs paths ke liye mufeed.
</Ur>
</Tr>

```tsx
// app/shop/[...categories]/page.tsx
export default async function ShopPage({ params }: { params: Promise<{ categories: string[] }> }) {
  const { categories } = await params;
  return <h1>Shop: {categories.join(" > ")}</h1>;
}
```

```text
Visiting the pages
/shop/clothes/men/shirts → 200 | title: Fresh Mart | Shop: clothes > men > shirts
```

<Happened>
<Tr>
<En>

- `/shop/clothes/men/shirts` gave `categories = ["clothes", "men", "shirts"]`.
- `/shop` on its own would **not** match `[...categories]` (it needs at least one segment). Use double brackets, `[[...categories]]`, for an **optional** catch-all that also matches `/shop`.
- More specific routes win: if `app/shop/sale/page.tsx` existed, `/shop/sale` would use it, not the catch-all.

</En>
<Ur>

- `/shop/clothes/men/shirts` ne `categories = ["clothes", "men", "shirts"]` diya.
- Akela `/shop` `[...categories]` se **nahi** milta (kam az kam ek segment chahiye). **Ikhtiyari** catch-all ke liye jo `/shop` se bhi mile, dohre brackets lein: `[[...categories]]`.
- Zyada khaas routes jeette hain: agar `app/shop/sale/page.tsx` hoti to `/shop/sale` usi ko istemal karta, catch-all ko nahi.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Nested layouts">

<Tr>
<En>
A `layout.tsx` in a subfolder wraps every page in that folder, **inside** the root layout. When you move between those pages, the layout **stays mounted**: it doesn't re-render from scratch or lose its state.
</En>
<Ur>
Subfolder me `layout.tsx` us folder ke har page ko root layout ke **andar** lapetta hai. Jab aap un pages ke darmiyan jate hain to layout **qaim** rehta hai: shuru se dobara nahi banta aur apni state nahi khota.
</Ur>
</Tr>

```tsx
// app/dashboard/layout.tsx
import Link from "next/link";
```

<Step title="Reading the query string with searchParams">

<Tr>
<En>
The part of a URL after `?` (like `?q=mango&page=2`) isn't part of the route. Pages receive it as **`searchParams`**, also a promise. Values are always **strings** (or missing).
</En>
<Ur>
URL ka `?` ke baad wala hissa (jaise `?q=mango&page=2`) route ka hissa nahi. Pages ise **`searchParams`** ki shakal me lete hain, jo bhi promise hai. Values hamesha **strings** hoti hain (ya ghayab).
</Ur>
</Tr>

```tsx
// app/search/page.tsx
export default async function SearchPage({
  searchParams,
}: {
  searchParams: Promise<{ q?: string; page?: string }>;
}) {
  const { q = "", page = "1" } = await searchParams;
  return (
    <h1>
      Results for “{q}”, page {page}
    </h1>
  );
}
```

```text
Visiting the pages
/search?q=mango&page=2 → 200 | title: Fresh Mart | Results for “mango”, page 2
/search                → 200 | title: Fresh Mart | Results for “”, page 1
```

<Happened>
<Tr>
<En>

- `?q=mango&page=2` gave `q = "mango"` and `page = "2"`, a **string**. Convert with `Number(page)` before doing maths, and check the result (Data Types lesson).
- Without a query string, the defaults in the destructuring (`""` and `"1"`) were used.
- Reading `searchParams` makes the page **dynamic**: it's rendered on each request (marked `ƒ` in the build output), because the HTML depends on the URL.
- Build search links with `<Link href={{ pathname: "/search", query: { q: "mango" } }}>` or `URLSearchParams`, so special characters are encoded correctly.

</En>
<Ur>

- `?q=mango&page=2` ne `q = "mango"` aur `page = "2"` diya, jo **string** hai. Hisaab se pehle `Number(page)` se badlein, aur nateeja check karein (Data Types lesson).
- Query string ke baghair destructuring ke defaults (`""` aur `"1"`) istemal hue.
- `searchParams` parhna page ko **dynamic** banata hai: ye har request par banta hai (build output me `ƒ` ka nishaan), kyun ke HTML URL par munhasir hai.
- Search links `<Link href={{ pathname: "/search", query: { q: "mango" } }}>` ya `URLSearchParams` se banayen, taa ke khaas characters sahi encode hon.

</Ur>
</Tr>

<DeepDive title="All the special files, and more routing features">

**Special files in a route folder** (all optional except the root layout and a page):

| File | Purpose |
| --- | --- |
| `page.tsx` | The UI for the route |
| `layout.tsx` | Shared, persistent wrapper |
| `template.tsx` | Like a layout, but re-mounted on every navigation |
| `loading.tsx` | Instant loading UI (wraps the page in Suspense) |
| `error.tsx` | Error boundary for the segment (must be a client component) |
| `not-found.tsx` | UI for `notFound()` and unmatched URLs |
| `route.ts` | An API endpoint instead of a page |
| `default.tsx` | Fallback for parallel routes |

**Programmatic navigation.** In client components, `useRouter()` from `next/navigation` gives `router.push("/path")`, `router.back()` and `router.refresh()`. On the server, `redirect("/login")` stops rendering and redirects.

**Reading the current URL** in client components: `usePathname()`, `useSearchParams()` and `useParams()`. A common use is highlighting the active link in a nav bar.

**Parallel routes** (`@slot` folders) render several pages in one layout at once, such as a dashboard with independent panels. **Intercepting routes** (`(.)photo/[id]`) show a route in a modal while keeping the URL shareable, like photo feeds.

**Metadata** can be dynamic: export `async function generateMetadata({ params })` to set the title and description from data, for example each blog post's title.

**Static vs dynamic** is decided automatically: using `searchParams`, `cookies()`, `headers()` or uncached data makes a route dynamic. The "Rendering Strategies" and "Data Fetching and Caching" lessons go deeper.

**The `pages/` router.** Older Next.js projects use `pages/about.tsx` and `getServerSideProps`. It still works, but new projects use `app/`.

</DeepDive>

<DeepDive title="Real world: the migration that broke every old link">

A content site moved from the old `pages/` router to the App Router and reorganised its folders at the same time. Articles moved from `/posts/[id]` to `/blog/[slug]`, and the team was pleased with the cleaner URLs.

Within a week, search traffic fell by about a third. Thousands of links on other websites, in newsletters and in search results pointed at `/posts/123`, and now every one of them showed the not-found page. Search engines saw a wave of 404s and dropped the pages.

The fix was **redirects**, which Next.js supports in `next.config` or in a route:

```text
// next.config.ts
export default {
  async redirects() {
    return [{ source: "/posts/:id", destination: "/api/legacy-post/:id", permanent: true }];
  },
};
```

The legacy route looked up the old id, found the new slug and issued a **308 permanent redirect** to `/blog/<slug>`. Traffic recovered over the following weeks.

Lesson: **URLs are a public interface.** Once a page is published and linked, changing its URL needs a permanent redirect. File-based routing makes URLs easy to change, which makes it easy to break them.

</DeepDive>

<DeepDive title="Security lens">

Routes are your app's public surface, so treat every one as reachable by anyone.

- **A route without a link is still public.** Hiding `/admin` from the nav doesn't protect it. Check authentication and permissions on the server, in the page or layout (and in middleware for coarse checks), before rendering private data.
- **Layouts don't re-run on navigation.** An auth check placed only in a layout may not run again when the user navigates between pages inside it. Check access in each page or in the data functions they call, as close to the data as possible.
- **Validate `params` and `searchParams`.** They come straight from the URL. Check that an id is a valid number or UUID before querying, and never put them into SQL, HTML or file paths unescaped.
- **Authorization per resource.** `/orders/[id]` must confirm the order belongs to the logged-in user; otherwise changing the number in the URL shows other people's orders (an insecure direct object reference).
- **Use `notFound()` for things the user may not see,** not "403 forbidden", when revealing that the resource exists would leak information.
- **Open redirects.** If a page redirects to `searchParams.next` after login, allow only relative paths on your own site, or attackers can send users to look-alike phishing pages.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does routing work in the Next.js App Router?">
It is file-system based: folders inside the app directory define URL segments, and a page file inside a folder makes that segment publicly routable. Special files such as layout, loading, error and not-found add shared UI and states for each segment, and route handlers define API endpoints.
</QA>

<QA q="What is the difference between a layout and a page?">
A page renders the unique content of one route. A layout wraps a segment and all its children, receives them as the children prop, and stays mounted while navigating between those child routes, preserving its state. The root layout is required and defines the html and body tags.
</QA>

<QA q="How do dynamic routes work?">
A folder name in square brackets creates a dynamic segment that matches any value; the value is passed to the page in params, which is a promise in Next.js 15 and later. Spread brackets create catch-all segments that receive an array, and double brackets make the catch-all optional. generateStaticParams can pre-render known values at build time.
</QA>

<QA q="What are route groups for?">
A folder name in parentheses groups routes for organisation or to share a layout without adding a segment to the URL, for example separating marketing pages and application pages with different layouts.
</QA>

<QA q="Why use the Link component?">
It performs client-side navigation, updating only the parts of the page that change while keeping shared layouts mounted, and in production it prefetches routes linked from the visible viewport, making navigation fast.
</QA>

<QA q="How do you return a 404 for a missing resource?">
Call notFound from next/navigation in the page or data function. It stops rendering and shows the nearest not-found file with an HTTP 404 status, which is important for search engines.
</QA>
