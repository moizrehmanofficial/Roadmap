<BigIdea>
<Tr>
<En>
Reading data in Next.js is easy: await it in a Server Component. **Changing** data (posting a review, saving settings, deleting a row) used to need three pieces: an API route, a `fetch` call from the browser, and code to refresh the page. **Server Actions** collapse that into one: an `async` function in a file marked **`"use server"`**. Pass it to a form's **`action`** prop, or call it from a click handler, and Next.js handles the network request for you. The function receives the **`FormData`**, **validates** it (zod), writes to the database, calls **`updateTag`** (or `revalidatePath`) so cached data refreshes, and can **return** a result (errors, a message) or **`redirect()`**. In the browser, **`useActionState`** shows that result and **`useFormStatus`** shows a pending button. Forms built this way even work **before JavaScript loads**. One rule overrides everything else: a Server Action is a **public HTTP endpoint**. Anyone can call it with any arguments, so **every action must validate input and check permissions itself**.
</En>
<Ur>
Next.js me data parhna aasan hai: Server Component me us ka await karein. Data **badalna** (review post karna, settings save karna, row delete karna) pehle teen hisse maangta tha: API route, browser se `fetch` call, aur page refresh karne ka code. **Server Actions** ye sab ek me samet dete hain: **`"use server"`** wali file me ek `async` function. Ise form ke **`action`** prop ko dein, ya click handler se call karein, aur Next.js aap ke liye network request sambhalta hai. Function ko **`FormData`** milta hai, wo use **validate** karta hai (zod), database me likhta hai, **`updateTag`** (ya `revalidatePath`) call karta hai taa ke cache shuda data taaza ho, aur nateeja (errors, paighaam) **wapas** kar sakta ya **`redirect()`** kar sakta hai. Browser me **`useActionState`** wo nateeja dikhata aur **`useFormStatus`** pending button dikhata hai. Is tarah bane forms **JavaScript load hone se pehle** bhi chalte hain. Ek qaida sab par bhaari hai: Server Action **public HTTP endpoint** hai. Koi bhi ise kisi bhi arguments ke saath call kar sakta hai, isliye **har action ko input khud validate aur permissions khud check karni chahiye**.
</Ur>
</Tr>

## At a glance

<Glance>
<What>
<Tr>
<En>

| Piece | Where | What it does |
| --- | --- | --- |
| `"use server"` at the top of a file | `app/…/actions.ts` | every exported async function becomes a Server Action |
| `<form action={myAction}>` | Server or Client Component | submits `FormData` to the action |
| `useActionState(action, initial)` | Client Component | gives `[state, formAction, isPending]`; the action receives `(prevState, formData)` |
| `useFormStatus()` (`react-dom`) | a child of the form | `pending` while the form submits |
| `action.bind(null, id)` | anywhere | pre-fills arguments (e.g. which row to delete) |
| `await myAction(args)` | event handler + `startTransition` | calls it like a function; gets the return value |
| `updateTag` / `revalidatePath` | inside the action | refresh cached data the user just changed |
| `redirect("/somewhere")` | inside the action | navigate after success |
| `cookies()` | inside the action | read or set cookies (session, role) |

</En>

<Why>
<Tr>
<En>

- **Less code**: no API route, no `fetch`, no JSON parsing, no manual page refresh.
- **Type safety end to end**: the client imports the action, so TypeScript checks its arguments and return type.
- **Progressive enhancement**: forms work with JavaScript disabled or still loading (slow phones, flaky networks).
- **Integrated with caching**: one `updateTag` call refreshes every page showing that data, and the response includes the updated UI.

</En>
<Ur>

- **Kam code**: na API route, na `fetch`, na JSON parsing, na haath se page refresh.
- **Shuru se aakhir tak type safety**: client action import karta hai, isliye TypeScript us ke arguments aur return type check karta hai.
- **Progressive enhancement**: forms JavaScript band ya abhi load hote hue bhi chalte hain (sust phones, kamzor network).
- **Caching ke saath jure**: ek `updateTag` call wo data dikhane wale har page ko taaza karta hai, aur response me updated UI shamil hoti hai.

</Ur>
</Tr>
</Why>
<When>
<Tr>
<En>

| Situation | Server Action? |
| --- | --- |
| Forms and buttons in your own Next.js app that change data | ✅ yes |
| Likes, toggles, "mark as read" | ✅ yes (with `useOptimistic` for instant feedback) |

<How>
<Tr>
<En>

1. Create `actions.ts` with `"use server"` at the top and export async functions.

## Picture it

<Tr>
<En>

Think of a **bank's deposit slip and counter**.

- You fill in a **slip** (the form) and hand it over the counter. You don't need to know how the bank's back office works (no API design, no fetch).
- The clerk **checks your ID** (authentication), checks you're **allowed** to use this account (authorisation), and checks the slip is **filled in correctly** (validation). If not, the slip comes back with the wrong boxes circled (field errors).
- While the clerk works, a sign says **"processing"** (pending state).
- After the deposit, your **passbook is updated** straight away (updateTag), so you see your own change.
- Anyone can walk up to the counter with a slip, even a stranger with a forged one. That's why the clerk checks every slip, **no matter which door it came through** (actions are public endpoints).

</En>
<Ur>

**Bank ki deposit slip aur counter** ka sochein.

- Aap **slip** (form) bhar kar counter par dete hain. Aap ko bank ke andaruni daftar ka kaam janne ki zaroorat nahi (na API design, na fetch).
- Clerk **aap ki ID check** karta hai (authentication), check karta hai ke aap ko ye account istemal karne ki **ijazat** hai (authorisation), aur ke slip **sahi bhari** hai (validation). Agar nahi, to slip ghalat khanon par gol daire laga kar wapas aati hai (field errors).
- Clerk ke kaam ke dauran board par **"processing"** likha hota hai (pending halat).
- Deposit ke baad aap ki **passbook foran update** hoti hai (updateTag), taa ke aap apni tabdeeli dekhein.
- Koi bhi slip le kar counter par aa sakta hai, jaali slip wala ajnabi bhi. Isi liye clerk har slip check karta hai, **chahe wo kisi bhi darwaze se aayi ho** (actions public endpoints hain).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="The data: cached reviews with a tag">

<Tr>
<En>
Our page shows reviews for a mug. A pretend database lives in server memory. Reading is cached and tagged `"reviews"` (Data Fetching and Caching lesson), so the page is static until something changes.
</En>
<Ur>
Hamara page ek mug ke reviews dikhata hai. Naqli database server ki memory me hai. Parhna cache aur `"reviews"` tag shuda hai (Data Fetching and Caching lesson), isliye page kuch badalne tak static hai.
</Ur>
</Tr>

```tsx
// lib/reviews.ts
import { cacheLife, cacheTag } from "next/cache";

export type Review = { id: number; author: string; rating: number; text: string };

// A pretend database table kept in server memory
const db = globalThis as unknown as { reviews?: Review[]; nextId?: number };
db.reviews ??= [{ id: 1, author: "Liam", rating: 5, text: "Keeps coffee hot for ages." }];
db.nextId ??= 2;

export async function getReviews() {
  "use cache";
  cacheLife("hours");
  cacheTag("reviews");
  return [...db.reviews!];
}

export async function insertReview(r: Omit<Review, "id">) {
  db.reviews!.push({ ...r, id: db.nextId!++ });
}

export async function removeReview(id: number) {
  db.reviews = db.reviews!.filter((r) => r.id !== id);
}
```

```text
$ npx next build
├ ○ /reviews                 1h      1d
```

<Happened>
<Tr>
<En>

- `/reviews` is prerendered (○). Without a refresh after writes, new reviews wouldn't appear for up to an hour. Actions fix that with `updateTag("reviews")`.
- In a real app, `insertReview` would be a Prisma or SQL query; nothing else in this lesson would change.

</En>
<Ur>

- `/reviews` pehle se render hai (○). Likhne ke baad refresh ke baghair naye reviews ek ghante tak nazar na aate. Actions ise `updateTag("reviews")` se theek karte hain.
- Asli app me `insertReview` Prisma ya SQL query hoti; is lesson me aur kuch na badalta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Write the actions: validate, write, refresh">

<Tr>
<En>
`"use server"` at the top of `actions.ts` turns each exported async function into an action. `addReview` is designed for `useActionState`, so it receives the previous state first, then the `FormData`. It returns errors instead of throwing, because invalid input is **expected**.
</En>
<Ur>
`actions.ts` ke shuru me `"use server"` har exported async function ko action bana deta hai. `addReview` `useActionState` ke liye bana hai, isliye use pehle pichhli state, phir `FormData` milta hai. Ye throw karne ke bajaye errors wapas karta hai, kyun ke ghalat input **mutawaqqa** hai.
</Ur>
</Tr>

```tsx
// app/reviews/actions.ts
"use server";

import { updateTag } from "next/cache";
import { cookies } from "next/headers";
import { z } from "zod";
import { insertReview, removeReview } from "@/lib/reviews";

const ReviewSchema = z.object({
  author: z.string().trim().min(2, "Name must be at least 2 characters"),
  rating: z.coerce.number().int().min(1).max(5, "Rating must be 1 to 5"),
  text: z.string().trim().min(10, "Review must be at least 10 characters").max(500),
});

export type ReviewState = {
  message?: string;
  errors?: Partial<Record<"author" | "rating" | "text", string[]>>;
  values?: { author: string; rating: string; text: string };
};

export async function addReview(prev: ReviewState, formData: FormData): Promise<ReviewState> {
  const raw = {
    author: String(formData.get("author") ?? ""),
    rating: String(formData.get("rating") ?? ""),
    text: String(formData.get("text") ?? ""),
  };
  const parsed = ReviewSchema.safeParse(raw);
  if (!parsed.success) {
    return { errors: z.flattenError(parsed.error).fieldErrors, values: raw };
  }
  await new Promise((r) => setTimeout(r, 800)); // pretend the database is slow
  await insertReview(parsed.data);
  updateTag("reviews"); // the author sees their review on the next render
  return { message: `Thanks, ${parsed.data.author}! Your review is live.` };
}

export async function deleteReview(id: number) {
  const role = (await cookies()).get("role")?.value;
  if (role !== "admin") {
    throw new Error("Only admins can delete reviews");
  }
  await removeReview(id);
  updateTag("reviews");
}
```

<Happened>
<Tr>
<En>

- Everything from `FormData` is a **string** (or a `File`), so `z.coerce.number()` turns `"4"` into `4`. Never trust types from the client.
- Returning `values` lets the form refill what the user typed after an error (React resets forms after an action).
- `deleteReview` checks the role **inside the action**. Hiding the Delete button from normal users is good UX, but it's not security (Step 7 proves why).
- A `"use server"` file can only export **async functions** (and types). Constants or schemas you want to share must live in another file.

</En>
<Ur>

- `FormData` se aane wali har cheez **string** (ya `File`) hai, isliye `z.coerce.number()` `"4"` ko `4` banata hai. Client ki types par kabhi bharosa na karein.
- `values` wapas karna form ko error ke baad user ka likha dobara bharne deta hai (React action ke baad forms reset karta hai).
- `deleteReview` role **action ke andar** check karta hai. Aam users se Delete button chhupana achha UX hai, magar security nahi (Step 7 sabit karta hai kyun).
- `"use server"` file sirf **async functions** (aur types) export kar sakti hai. Baantne wale constants ya schemas doosri file me hone chahiyen.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="The form: useActionState and useFormStatus">

<Tr>
<En>
A small Client Component connects the action to the UI. `useActionState` gives the latest returned state and a `formAction` to put on the form. The submit button reads the form's pending state with `useFormStatus`.
</En>
<Ur>
Ek chhota Client Component action ko UI se jorta hai. `useActionState` aakhri wapas ki gayi state aur form par lagane ke liye `formAction` deta hai. Submit button `useFormStatus` se form ki pending halat parhta hai.
</Ur>
</Tr>

```tsx
// app/reviews/ReviewForm.tsx
"use client";

import { useActionState } from "react";
import { useFormStatus } from "react-dom";
import { addReview, type ReviewState } from "./actions";

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "Posting…" : "Post review"}</button>;
}

export default function ReviewForm() {
  const [state, formAction] = useActionState(addReview, {} as ReviewState);
  return (
    <form action={formAction}>
      <p><label>Name <input name="author" defaultValue={state.values?.author} /></label></p>
      {state.errors?.author && <p role="alert">{state.errors.author[0]}</p>}
      <p><label>Rating (1-5) <input name="rating" defaultValue={state.values?.rating ?? "5"} /></label></p>
      {state.errors?.rating && <p role="alert">{state.errors.rating[0]}</p>}
      <p><label>Review <textarea name="text" defaultValue={state.values?.text} /></label></p>
      {state.errors?.text && <p role="alert">{state.errors.text[0]}</p>}
      <SubmitButton />
      {state.message && <p role="status">{state.message}</p>}
    </form>
  );
}

// app/reviews/page.tsx (the list part)
import { getReviews } from "@/lib/reviews";
import { deleteReview } from "./actions";
import ReviewForm from "./ReviewForm";
import HelpfulButton from "./HelpfulButton";

async function ReviewList() {
  const reviews = await getReviews();
  return (
    <ul>
      {reviews.map((r) => (
        <li key={r.id}>
          {"★".repeat(r.rating)} {r.author}: {r.text} <HelpfulButton id={r.id} />{" "}
          <form action={deleteReview.bind(null, r.id)} style={{ display: "inline" }}>
            <button>Delete</button>
          </form>
        </li>
      ))}
    </ul>
  );
}

export default function ReviewsPage() {
  return (
    <>
      <h1>Mug reviews</h1>
      <ReviewList />
      <h2>Write a review</h2>
      <ReviewForm />
    </>
  );
}
```

```text
1. Submit Name "E", Rating "9", Review "Nice":
   Name must be at least 2 characters
   Rating must be 1 to 5
   Review must be at least 10 characters
   (fields still show "E" and "Nice")

2. Submit Name "Emma", Rating "4", Review "Great mug, but the handle gets warm.":
   0.2 s later:  button shows "Posting…"
   1.7 s later:  ★★★★★ Liam: Keeps coffee hot for ages.
                 ★★★★ Emma: Great mug, but the handle gets warm.
                 Thanks, Emma! Your review is live.
                 (fields are empty again)
```

<Happened>
<Tr>
<En>

- Validation ran **on the server**; the errors came back as the action's return value and rendered next to each field.
- During the 0.8 s "database" wait, the button said "Posting…" and was disabled, so no double submits.
- The new review appeared **in the same response**: `updateTag("reviews")` expired the cached list, and Next.js sent the re-rendered page along with the action result. No `router.refresh()` needed.
- After success, React reset the form fields. Add browser-side checks (`required`, `minLength`) too for instant hints, but the server check is the one that counts.

</En>
<Ur>

- Validation **server par** chali; errors action ki return value ban kar aaye aur har field ke saath dikhe.
- 0.8 s ke "database" intezar me button "Posting…" kehta raha aur band tha, isliye dohra submit nahi.
- Naya review **usi response me** aaya: `updateTag("reviews")` ne cache shuda list expire ki, aur Next.js ne action ke nateeje ke saath dobara render hua page bheja. `router.refresh()` ki zaroorat nahi.
- Kamyabi ke baad React ne form ke fields reset kiye. Fori ishare ke liye browser side checks (`required`, `minLength`) bhi lagayen, magar asal check server wala hai.

</Ur>
</Tr>
</Happened>

<Happened>
<Tr>
<En>

- Posting, validation errors and the success message all worked with a plain page reload. `useActionState` with a Server Action supports this **progressive enhancement** automatically.
- With JavaScript on, the same form submits in the background and updates without a reload.

- Post karna, validation errors aur kamyabi ka paighaam sab saade page reload ke saath chale. Server Action ke saath `useActionState` ye **progressive enhancement** khud support karta hai.

- Chhupe fields batate hain ke ye kaise chalta hai: **action ID** batati hai ke kaun sa server function chalana hai, aur **bound argument** (`[1]`, review ki ID) **browser se** bheja jata hai. Matlab user use badal sakta hai. Ye agle step ke liye yaad rakhein.

</Ur>
</Tr>

<Step title="Call an action from a click handler">

<Tr>
<En>
Actions don't need a form. Import one into a Client Component and call it like an async function inside `startTransition`. Whatever it returns comes back to you.
</En>
<Ur>
Actions ko form ki zaroorat nahi. Ise Client Component me import kar ke `startTransition` ke andar async function ki tarah call karein. Jo kuch ye wapas kare wo aap ko mil jata hai.
</Ur>
</Tr>

```tsx
// app/reviews/actions.ts (added)
const likes = globalThis as unknown as { likes?: Record<number, number> };

export async function likeReview(id: number) {
  likes.likes ??= {};
  likes.likes[id] = (likes.likes[id] ?? 0) + 1;
  return likes.likes[id]; // return values come back to the caller
}

// app/reviews/HelpfulButton.tsx
"use client";

import { useState, useTransition } from "react";
import { likeReview } from "./actions";

export default function HelpfulButton({ id }: { id: number }) {
  const [count, setCount] = useState(0);
  const [isPending, startTransition] = useTransition();

  return (
    <button
      disabled={isPending}
      onClick={() =>
        startTransition(async () => {
          const newCount = await likeReview(id); // looks like a normal function call
          setCount(newCount);
```

## Common mistakes

<Compare>
<Bad title="Trusting the client">

```text
"use server";
export async function updateOrder(orderId: string, total: number, userId: string) {
  await db.order.update({ where: { id: orderId }, data: { total } });
}
// anyone can call it with any orderId, any total, any userId
```

</Bad>
<Good title="Authenticate, authorise, validate on the server">

```text
"use server";
export async function updateOrderNote(orderId: string, formData: FormData) {
  const user = await requireUser();                              // from the session, not an argument
  const order = await db.order.findUnique({ where: { id: orderId } });
  if (!order || order.userId !== user.id) throw new Error("Not allowed");
  const note = z.string().max(200).parse(formData.get("note"));
  await db.order.update({ where: { id: orderId }, data: { note } });  // total is computed server-side, never sent
  updateTag(`order-${orderId}`);
}
```

</Good>
</Compare>

<Compare>
<Bad title="Forgetting to refresh after a write">

```text
export async function addReview(prev, formData) {
  await insertReview(parse(formData));
  return { message: "Saved!" };            // the cached list still shows the old reviews
}
```

</Bad>
<Good title="Refresh what changed">

```text
export async function addReview(prev, formData) {
  await insertReview(parse(formData));
  updateTag("reviews");                    // the list updates in the same response
  return { message: "Saved!" };
}
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Exporting non-async things from a `"use server"` file** (a zod schema, a constant): the build fails; move them to another module.
- **Using `useFormStatus` in the component that renders the `<form>`**: it reads the **parent** form, so put it in a child button component.
- **Throwing for validation errors**: users get an error page instead of field messages; return them.
- **Catching `redirect()` in try/catch** and swallowing it.
- **Putting secrets in bound arguments** or trusting them: `.bind` values travel through the browser.
- **Using actions for reading data**: they're POST requests, run one at a time per client, and aren't cached; read in Server Components.
- **Large uploads through actions**: the default body limit is 1 MB (`serverActions.bodySizeLimit` raises it); prefer direct uploads to storage.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **`"use server"` file se ghair async cheezein export karna** (zod schema, constant): build fail hoti hai; unhen doosre module me le jayen.
- **`<form>` render karne wale component me `useFormStatus` istemal karna**: ye **parent** form parhta hai, isliye ise child button component me rakhein.
- **Validation errors ke liye throw karna**: users ko field ke paighaamon ke bajaye error page milta hai; unhen wapas karein.
- **`redirect()` ko try/catch me pakar kar nigal jana**.
- **Bound arguments me secrets rakhna** ya un par bharosa karna: `.bind` values browser se guzarti hain.
- **Data parhne ke liye actions**: ye POST requests hain, har client ke liye ek waqt me ek chalti hain, aur cache nahi hoti; Server Components me parhein.
- **Actions ke zariye bari uploads**: default body hadd 1 MB hai (`serverActions.bodySizeLimit` barhata hai); seedha storage me upload behtar hai.

</Ur>
</Tr>

```text
// app/newsletter/actions.ts
"use server";
import { z } from "zod";

const subscribers = new Set<string>();

export async function subscribe(prev: { error?: string; message?: string }, formData: FormData) {
  const parsed = z.email("Enter a valid email").safeParse(String(formData.get("email") ?? "").trim().toLowerCase());
  if (!parsed.success) return { error: parsed.error.issues[0].message };
  if (subscribers.has(parsed.data)) return { error: "You're already subscribed." };
  subscribers.add(parsed.data);
  return { message: "Check your inbox to confirm." };
}

// app/newsletter/SignupForm.tsx
"use client";
import { useActionState } from "react";
import { useFormStatus } from "react-dom";
import { subscribe } from "./actions";

function Submit() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? "Subscribing…" : "Subscribe"}</button>;
}

export default function SignupForm() {
  const [state, action] = useActionState(subscribe, {});
  return (
    <form action={action}>
      <input name="email" type="email" required placeholder="you@example.com" />
      <Submit />
      {state.error && <p role="alert">{state.error}</p>}
      {state.message && <p role="status">{state.message}</p>}
    </form>
  );
}
```

<En>

- A **Server Action** is an async function in a `"use server"` file, used as a form `action` or called from a handler inside `startTransition`.

<DeepDive title="More about Server Actions">

**Inline actions.** A Server Component can define an action inline with `"use server"` as the first line of the function body. Variables it closes over are encrypted before being sent to the browser; bound arguments (`.bind`) are not.

**Action IDs and dead code.** Next.js generates an unguessable ID per action and removes unused actions from the client bundle. IDs are recalculated between builds, so a tab left open from an old deployment can fail to call actions after you deploy. When self-hosting on several servers, set `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` so every instance uses the same encryption key.

**CSRF protection.** Actions only accept POST, and Next.js compares the `Origin` header with the host, so other websites can't trigger them from a user's browser. If you use a proxy with different hostnames, configure `serverActions.allowedOrigins`.

**Sequential execution.** Calls from one client are queued and run one after another, which keeps state consistent but means actions aren't suited to parallel data fetching.

**Optimistic updates.** Combine `useOptimistic` with an action for instant UI; when the action finishes, React shows the real (refreshed) data or rolls back.

**`after()` in actions.** Send emails, write analytics or call webhooks after the response, so the user doesn't wait.

**Testing.** Actions are plain async functions: unit-test the logic by calling them with a `FormData` object, and test the full flow with Playwright (as this lesson did), including JavaScript disabled.

</DeepDive>

<DeepDive title="Real world: the coupon that anyone could create">

An online shop's admin area had a "Create coupon" form, visible only on pages under `/admin`, which were protected by a check in the admin layout. The form called a Server Action, `createCoupon(formData)`, which inserted the code and discount straight into the database. The developer assumed that because only admins could reach the page, only admins could call the action.

A customer looking at the site's JavaScript noticed the action ID, replayed the request with `curl`, and created a 90 percent coupon for themselves. It was spotted three days later when finance asked why dozens of orders had huge discounts.

The fixes:

1. A shared `requireAdmin()` helper (verifying the signed session cookie and the user's role in the database) was called at the top of **every** admin action, not just in the layout.
2. Inputs were validated with zod: discounts were limited to 1-50 percent and codes to letters and numbers.
3. Each action wrote an audit log row with the admin's ID.
4. An ESLint rule and a code review checklist flagged any exported action without an auth helper call in its first lines.
5. Coupons created in the incident were disabled and the affected orders reviewed.

The lesson the team wrote in their wiki: "Layouts protect pages, not actions. Every action checks for itself."

</DeepDive>

<DeepDive title="Security lens">

- **Authenticate and authorise in every action**, using the verified session, never a user ID passed from the client.
- **Validate every argument** with a schema; `FormData` and bound values are attacker-controlled.
- **Check ownership** of the specific record (IDOR protection): "is order 123 this user's?"
- **Don't return sensitive data** in action results; they go to the browser.
- **Rate-limit** actions that send emails, create accounts or cost money.
- **Use `server-only`** in data modules so database code can't accidentally be imported into client bundles.
- **Mind the body size** to prevent abuse, and validate file types and sizes for uploads.
- Next.js protects against CSRF by checking the Origin; keep `allowedOrigins` tight if you configure it.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are Server Actions and how do they work?">
They are async server functions marked with use server that client code can call, typically as a form action or from an event handler. Next.js gives each one an ID, and calling it sends a POST request with that ID and the serialised arguments; the server runs the function and responds with its return value and, if data was revalidated, the updated UI.
</QA>

<QA q="How do you handle validation errors and pending state with Server Actions?">
The action validates input, for example with zod, and returns errors as part of its result. On the client, useActionState provides the latest state to render field errors and a pending flag, and useFormStatus in a child of the form gives a pending state for submit buttons.
</QA>

<QA q="How do you keep the UI fresh after a Server Action mutates data?">
Call updateTag for tags the user should see updated immediately, revalidateTag for background refresh, or revalidatePath for a route, then return or redirect. Next.js sends the re-rendered UI with the action response.
</QA>

<QA q="What are the security considerations of Server Actions?">
Each action is a publicly reachable endpoint. You must authenticate the caller, authorise access to the specific resource, validate all arguments including bound values, avoid returning sensitive data, and rate-limit sensitive operations. Next.js adds CSRF protection by only allowing POST and checking the Origin header.
</QA>

<QA q="When would you use a Route Handler instead of a Server Action?">
For endpoints called by external systems such as webhooks or mobile apps, when you need a stable URL, custom HTTP methods, raw request bodies or signature verification, for streaming responses, and for large file uploads.
</QA>

</DeepDive>
