<BigIdea>
<Tr>
<En>
Many operations are really **several changes that only make sense together**: a transfer debits one account **and** credits another; placing an order creates the order, its items **and** reduces stock. If the app crashes, times out or hits an error halfway, you're left with half a change: money gone from one account and never arriving in the other. A **transaction** groups statements between `BEGIN` and `COMMIT` so they apply **all together or not at all**; on any error you `ROLLBACK` (or the connection drops) and nothing happened. Databases promise **ACID**: **Atomicity** (all or nothing), **Consistency** (constraints hold after every transaction), **Isolation** (concurrent transactions don't see each other's half-done work), and **Durability** (once committed, it survives a crash). Isolation is where real bugs hide: when two requests **read a value, compute in the app, and write it back** at the same time, one update silently overwrites the other (a **lost update**). Fix it by letting the database do the arithmetic in one `UPDATE`, by **locking** the row with `SELECT … FOR UPDATE`, or by using **SERIALIZABLE** isolation and **retrying** when the database reports a conflict.
</En>
<Ur>
Bohot se amal asal me **kai tabdeeliyan hain jo sirf ikatthe matlab rakhti hain**: transfer ek account se nikalta **aur** doosre me dalta hai; order dena order, us ke items banata **aur** stock kam karta hai. Agar app beech me crash, timeout ya error kha jaye to aadhi tabdeeli reh jati hai: ek account se paise gaye aur doosre me kabhi nahi pahunche. **Transaction** `BEGIN` aur `COMMIT` ke darmiyan statements ko ikattha karti hai taa ke wo **sab ek saath ya bilkul nahi** lagen; kisi bhi error par aap `ROLLBACK` karte hain (ya connection toot jata hai) aur kuch nahi hua. Databases **ACID** ka wada karte hain: **Atomicity** (sab ya kuch nahi), **Consistency** (har transaction ke baad constraints qaim), **Isolation** (ek saath chalti transactions ek doosre ka adhoora kaam nahi dekhtin), aur **Durability** (commit ho gaya to crash ke baad bhi qaim). Asli bugs isolation me chhupte hain: jab do requests ek saath **value parhti hain, app me hisaab karti hain, aur wapas likhti hain**, to ek update khamoshi se doosre ko mita deta hai (**lost update**). Ise database ko ek `UPDATE` me hisaab karne de kar, `SELECT … FOR UPDATE` se row **lock** kar ke, ya **SERIALIZABLE** isolation istemal kar ke aur database ke takrao batane par **retry** kar ke theek karein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of **moving furniture between two flats**.

- Without a transaction, you carry the sofa out of flat A and then trip on the stairs: the sofa is in neither flat.
- A **transaction** is a magic moving van: either the sofa ends up in flat B, or, if anything goes wrong, it's back in flat A as if nothing happened (**atomicity**).
- The building rule "no furniture on the stairs" is checked before the van finishes (**consistency**).
- Neighbors looking in see the sofa in A or in B, never halfway (**isolation**).
- Once the van says "delivered", it stays delivered even if the power goes out (**durability**).
- **Lost update**: two movers each read the shopping list "3 chairs left to move", each moves one, and each writes "2 left". One chair is forgotten. The fix: one mover holds the list while updating it (**lock**), or the list says "subtract one" instead of "write 2" (**atomic update**).

</En>
<Ur>

**Do flats ke darmiyan furniture muntaqil karne** ka sochein.

- Transaction ke baghair aap sofa flat A se nikalte hain aur seedhiyon par phisal jate hain: sofa kisi flat me nahi.
- **Transaction** jadui moving van hai: ya to sofa flat B me pahunchta hai, ya kuch ghalat ho to wapas flat A me jaise kuch hua hi nahi (**atomicity**).
- Imarat ka qaida "seedhiyon par furniture nahi" van ke khatam hone se pehle check hota hai (**consistency**).
- Jhankne wale parosi sofa A me ya B me dekhte hain, kabhi beech me nahi (**isolation**).
- Van ne "pahunch gaya" keh diya to bijli jane par bhi pahuncha hua rehta hai (**durability**).
- **Lost update**: do mazdoor list parhte hain "3 kursiyan baqi", har ek ek uthata hai, aur har ek "2 baqi" likhta hai. Ek kursi bhool jati hai. Hal: ek mazdoor update karte waqt list pakre rakhe (**lock**), ya list "2 likho" ke bajaye "ek ghatao" kahe (**atomic update**).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Atomicity and consistency: the half-finished transfer">

<Tr>
<En>
Two accounts, Jane with $100 and John with $50, and a `CHECK` that balances can't go negative. `run` feeds statements to psql with `ON_ERROR_STOP=1`: at the first error psql stops and disconnects, just like an app that crashes mid-way. We transfer money without a transaction, inside one, with too little money, and finally correctly, printing the balances and total each time.
</En>
<Ur>
Do accounts, Jane ke $100 aur John ke $50, aur ek `CHECK` ke balance manfi nahi ho sakta. `run` statements `ON_ERROR_STOP=1` ke saath psql ko deta hai: pehle error par psql ruk kar disconnect hota hai, bilkul us app ki tarah jo beech me crash ho jaye. Hum transaction ke baghair, us ke andar, kam paison ke saath, aur aakhir me sahi tarah paise bhejte hain, har dafa balances aur total chhapte hue.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
psql -q -h localhost -U postgres -c 'DROP DATABASE IF EXISTS bank' -c 'CREATE DATABASE bank' 2> /dev/null
psql -q -h localhost -U postgres -d bank <<'EOF'
CREATE TABLE accounts (
  id int PRIMARY KEY, owner text NOT NULL,
  balance_cents int NOT NULL CHECK (balance_cents >= 0)     -- the bank's rule: no negative balances
);
INSERT INTO accounts VALUES (1, 'Jane', 10000), (2, 'John', 5000);
EOF
# ON_ERROR_STOP=1: psql stops at the first error and disconnects, like an app that crashes mid-way
run()  { psql -q -h localhost -U postgres -d bank -v ON_ERROR_STOP=1 2>&1 | grep -E 'ERROR' | sed 's/^psql:<stdin>:[0-9]*: //'; }
show() { echo "   balances: $(psql -h localhost -U postgres -d bank -tA -c "SELECT string_agg(owner || '=' || balance_cents, ', ' ORDER BY id) || ', total=' || sum(balance_cents) FROM accounts")"; }
echo "start:"; show

echo "1) transfer \$30 from Jane to John WITHOUT a transaction; the app fails between the two updates"
run <<'EOF'
UPDATE accounts SET balance_cents = balance_cents - 3000 WHERE id = 1;
INSERT INTO accounts_log_that_does_not_exist VALUES (1);           -- fails here (in real life: a crash, a bug, a timeout)
UPDATE accounts SET balance_cents = balance_cents + 3000 WHERE id = 2;
EOF
show

psql -q -h localhost -U postgres -d bank -c "UPDATE accounts SET balance_cents = 10000 WHERE id = 1"   # reset
echo "2) the same steps INSIDE a transaction"
run <<'EOF'
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 3000 WHERE id = 1;
INSERT INTO accounts_log_that_does_not_exist VALUES (1);
UPDATE accounts SET balance_cents = balance_cents + 3000 WHERE id = 2;
COMMIT;
EOF
show

echo "3) Jane sends \$150 but has \$100: the CHECK fails, so the credit to John is undone too"
run <<'EOF'
BEGIN;
UPDATE accounts SET balance_cents = balance_cents + 15000 WHERE id = 2;
UPDATE accounts SET balance_cents = balance_cents - 15000 WHERE id = 1;
COMMIT;
EOF
show

echo "4) a valid \$40 transfer commits both changes"
run <<'EOF'
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 4000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 4000 WHERE id = 2;
COMMIT;
EOF
show
```

```text output
start:
   balances: Jane=10000, John=5000, total=15000
1) transfer $30 from Jane to John WITHOUT a transaction; the app fails between the two updates
ERROR:  relation "accounts_log_that_does_not_exist" does not exist
   balances: Jane=7000, John=5000, total=12000
2) the same steps INSIDE a transaction
ERROR:  relation "accounts_log_that_does_not_exist" does not exist
   balances: Jane=10000, John=5000, total=15000
3) Jane sends $150 but has $100: the CHECK fails, so the credit to John is undone too
ERROR:  new row for relation "accounts" violates check constraint "accounts_balance_cents_check"
   balances: Jane=10000, John=5000, total=15000
4) a valid $40 transfer commits both changes
   balances: Jane=6000, John=9000, total=15000
```

<Happened>
<Tr>
<En>

- **Without a transaction**, the debit was saved immediately; the failure stopped the credit. Jane lost $30, John got nothing, and the bank's **total dropped from 15000 to 12000**: money vanished. Each statement on its own was correct; the problem is that they weren't one unit.
- **Inside a transaction**, the same failure left everything as it was: the open transaction was rolled back when the session ended, so the debit never became visible to anyone. That's **atomicity**.
- In case 3, crediting John succeeded first, then debiting Jane broke the `CHECK`. The whole transaction aborted, so **John's credit was undone too**. That's **consistency**: constraints are checked, and a transaction that would break them doesn't commit.
- The valid transfer committed both changes, and the total stayed 15000. Notice the invariant: inside correct transactions, money moves but the total never changes.

</En>
<Ur>

- **Transaction ke baghair** debit foran save ho gaya; nakami ne credit rok diya. Jane ke $30 gaye, John ko kuch nahi mila, aur bank ka **total 15000 se 12000** ho gaya: paise ghaib. Har statement apni jagah durust tha; masla ye hai ke wo ek ikai nahi the.
- **Transaction ke andar** wahi nakami sab kuch waise ka waisa chhor gayi: session khatam hone par khuli transaction rollback hui, isliye debit kabhi kisi ko nazar nahi aaya. Ye **atomicity** hai.
- Case 3 me pehle John ka credit kamyab hua, phir Jane ka debit `CHECK` tor gaya. Poori transaction ruk gayi, isliye **John ka credit bhi wapas** hua. Ye **consistency** hai: constraints check hote hain, aur unhen torne wali transaction commit nahi hoti.
- Sahi transfer ne dono tabdeeliyan commit kin, aur total 15000 raha. Ye qaida dekhein: durust transactions me paise chalte hain magar total kabhi nahi badalta.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Isolation: 20 withdrawals at once">

<Tr>
<En>
Now concurrency. Twenty requests each withdraw $1 (100 cents) from Jane's $100 at the same moment, so the correct final balance is **8000**. We try four implementations with Node's `pg` pool (20 connections): read-modify-write in JavaScript, a single atomic `UPDATE`, `SELECT … FOR UPDATE`, and `SERIALIZABLE` isolation with a retry loop. A 20 ms pause between read and write stands in for real app work.
</En>
<Ur>
Ab concurrency. Bees requests ek hi lamhe Jane ke $100 se $1 (100 cents) nikalti hain, isliye sahi aakhri balance **8000** hai. Hum Node ke `pg` pool (20 connections) ke saath chaar tareeqe azmate hain: JavaScript me read-modify-write, ek atomic `UPDATE`, `SELECT … FOR UPDATE`, aur retry loop ke saath `SERIALIZABLE` isolation. Parhne aur likhne ke beech 20 ms ka waqfa asli app ke kaam ki jagah hai.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
npm init -y > /dev/null && npm pkg set type=module && npm install pg@8.23.1 --silent
cat > race.js <<'EOF'
import pg from "pg";
const pool = new pg.Pool({ connectionString: "postgres://postgres:postgres@localhost:5432/bank", max: 20 });
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const reset = () => pool.query("UPDATE accounts SET balance_cents = 10000 WHERE id = 1");
const balance = async () => (await pool.query("SELECT balance_cents FROM accounts WHERE id = 1")).rows[0].balance_cents;

// 20 requests each withdraw $1 (100 cents) at the same moment. Correct result: 10000 - 2000 = 8000
async function race(name, withdraw) {
  await reset();
  const results = await Promise.allSettled(Array.from({ length: 20 }, () => withdraw()));
  const failed = results.filter((r) => r.status === "rejected").length;
  const b = await balance();
  // the wrong result varies from run to run (9900, 9800, …), so print it as a check
  console.log(`${name.padEnd(37)} ${b === 8000 ? "8000, correct" : "WRONG: above 8000, withdrawals were lost"}${failed ? `  (${failed} failed)` : ""}`);
}

// A) read, compute in JavaScript, write back: the classic lost update
await race("read-modify-write (no lock)", async () => {
  const c = await pool.connect();
  try {
    const { rows } = await c.query("SELECT balance_cents FROM accounts WHERE id = 1");
    await sleep(20);                                              // the app does some work in between
    await c.query("UPDATE accounts SET balance_cents = $1 WHERE id = 1", [rows[0].balance_cents - 100]);
  } finally { c.release(); }
});

// B) let the database do the arithmetic in one statement
await race("atomic UPDATE … balance - 100", () =>
  pool.query("UPDATE accounts SET balance_cents = balance_cents - 100 WHERE id = 1"));

// C) lock the row while deciding
await race("SELECT … FOR UPDATE in a transaction", async () => {
  const c = await pool.connect();
  try {
    await c.query("BEGIN");
    const { rows } = await c.query("SELECT balance_cents FROM accounts WHERE id = 1 FOR UPDATE");   // others wait here
    await sleep(20);
    await c.query("UPDATE accounts SET balance_cents = $1 WHERE id = 1", [rows[0].balance_cents - 100]);
    await c.query("COMMIT");
  } catch (e) { await c.query("ROLLBACK"); throw e; } finally { c.release(); }
});

// D) SERIALIZABLE: PostgreSQL detects the conflict and aborts one side (error 40001); we retry
let retries = 0;
await race("SERIALIZABLE + retry", async () => {
  for (;;) {
    const c = await pool.connect();
    try {
      await c.query("BEGIN ISOLATION LEVEL SERIALIZABLE");
      const { rows } = await c.query("SELECT balance_cents FROM accounts WHERE id = 1");
      await sleep(20);
      await c.query("UPDATE accounts SET balance_cents = $1 WHERE id = 1", [rows[0].balance_cents - 100]);
      await c.query("COMMIT");
      return;
    } catch (e) {
      await c.query("ROLLBACK");
      if (e.code !== "40001") throw e;
      retries++;
    } finally { c.release(); }
  }
});
console.log(`   serialization failures that were retried: ${retries > 0 ? "yes, several" : "none"}`);
await pool.end();
EOF
node race.js
```

```text output
read-modify-write (no lock)           WRONG: above 8000, withdrawals were lost
atomic UPDATE … balance - 100         8000, correct
SELECT … FOR UPDATE in a transaction  8000, correct
SERIALIZABLE + retry                  8000, correct
   serialization failures that were retried: yes, several
```

<Happened>
<Tr>
<En>

- **Read-modify-write** lost withdrawals: many requests read the same balance (say 10000), each wrote "balance − 100", and later writes overwrote earlier ones. The final value varies from run to run (9900, 9800…), but it's always far above 8000: the bank paid out $20 and recorded only a dollar or two. No error appeared anywhere. Under PostgreSQL's default **Read Committed** level this is allowed.
- **Atomic UPDATE** (`SET balance_cents = balance_cents - 100`): the database reads and writes the row in one step while holding its lock, so 20 updates apply one after another. Exactly 8000. This is the simplest fix whenever the change can be written as arithmetic; add `WHERE balance_cents >= 100` to refuse overdrafts.
- **SELECT … FOR UPDATE** locked Jane's row inside each transaction: the other 19 waited at that line until the lock was released at `COMMIT`, then read the fresh value. Exactly 8000. Use it when the app must read, decide with code, then write.
- **SERIALIZABLE** let transactions run in parallel but **aborted** the ones whose result couldn't match any one-at-a-time order (SQLSTATE `40001`); the loop retried them. Exactly 8000, with several retries. Serializable is the strongest guarantee, but you **must** retry, and keep transactions short.

</En>
<Ur>

- **Read-modify-write** ne withdrawals kho din: bohot si requests ne wahi balance (maslan 10000) parha, har ek ne "balance − 100" likha, aur baad ke writes ne pehle walon ko mita diya. Aakhri value har run me badalti hai (9900, 9800…), magar hamesha 8000 se kahin upar: bank ne $20 diye aur sirf ek do dollar record kiye. Kahin koi error nahi aaya. PostgreSQL ke default **Read Committed** level par ye jaiz hai.
- **Atomic UPDATE** (`SET balance_cents = balance_cents - 100`): database row ka lock pakre ek qadam me parhta aur likhta hai, isliye 20 updates ek ke baad ek lagte hain. Bilkul 8000. Jab tabdeeli hisaab ki shakal me likhi ja sake to ye sab se saada hal hai; overdraft rad karne ke liye `WHERE balance_cents >= 100` jorein.
- **SELECT … FOR UPDATE** ne har transaction ke andar Jane ki row lock ki: baqi 19 us line par `COMMIT` par lock chhootne tak ruki rahin, phir taaza value parhi. Bilkul 8000. Ise tab lein jab app ko parhna, code se faisla karna, phir likhna ho.
- **SERIALIZABLE** ne transactions ko mutawazi chalne diya magar un ko **rok diya** jin ka nateeja kisi ek-ek kar ke tarteeb se mel na khata (SQLSTATE `40001`); loop ne unhen dobara chalaya. Bilkul 8000, kai retries ke saath. Serializable sab se mazboot zamanat hai, magar retry **lazmi** hai, aur transactions chhoti rakhein.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Transaction statements on different pool connections">

```text
await pool.query('BEGIN');                      // connection #1
await pool.query('UPDATE accounts …');          // maybe connection #2: NOT in the transaction
await pool.query('COMMIT');                     // maybe connection #3
```

</Bad>
<Good title="One client for the whole transaction">

```text
const c = await pool.connect();
try {
  await c.query('BEGIN');
  await c.query('UPDATE accounts …');
  await c.query('COMMIT');
} catch (e) { await c.query('ROLLBACK'); throw e; } finally { c.release(); }
```

</Good>
</Compare>

<Compare>
<Bad title="Slow external calls inside a transaction">

```text
BEGIN;
SELECT … FOR UPDATE;                 -- row locked
await paymentProvider.charge(…);     -- 3 seconds: every other request for this row waits
COMMIT;
```

</Bad>
<Good title="Keep transactions short; do external work outside">

```text
-- reserve in a short transaction (status = 'pending'), commit
-- call the payment provider (with an idempotency key)
-- record the result in a second short transaction
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Forgetting ROLLBACK on errors**: the connection goes back to the pool stuck in an aborted transaction, and every later query on it fails.
- **Assuming the default isolation prevents races**: Read Committed allows lost updates in read-modify-write code.
- **Using SERIALIZABLE without retries**: some transactions will fail by design; without a retry loop users see random errors.
- **Locking rows in different orders**: transaction A locks row 1 then 2, B locks 2 then 1, and they deadlock. Lock in a consistent order (e.g. by id).
- **Expecting a DB transaction to cover external systems**: emails sent or APIs called inside a rolled-back transaction are not undone.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Errors par ROLLBACK bhoolna**: connection ruki hui transaction ke saath pool me wapas jata hai, aur is par baad ki har query nakam hoti hai.
- **Ye samajhna ke default isolation races rokti hai**: Read Committed read-modify-write code me lost updates ki ijazat deta hai.
- **Retries ke baghair SERIALIZABLE**: kuch transactions design ke mutabiq nakam hongi; retry loop ke baghair users be-tarteeb errors dekhte hain.
- **Rows mukhtalif tarteeb me lock karna**: transaction A pehle row 1 phir 2 lock karti hai, B pehle 2 phir 1, aur deadlock ho jata hai. Ek jaisi tarteeb me lock karein (maslan id se).

<Challenge title="Make checkout safe">

<Tr>
<En>
Checkout must: create an order, insert its items, reduce stock for each product (never below zero) and fail entirely if any product is out of stock. Two customers often buy the last unit at the same time. Write the SQL steps.
</En>
<Ur>

</Ur>

<Solution>

<Tr>
<En>

```text
BEGIN;
INSERT INTO orders (customer_id) VALUES ($1) RETURNING id;               -- :order_id
-- for each item, in product_id order (consistent locking order avoids deadlocks):
UPDATE products SET stock = stock - $qty WHERE id = $product AND stock >= $qty;
-- if this affected 0 rows → ROLLBACK and tell the customer it's out of stock
INSERT INTO order_items (order_id, product_id, qty, unit_price_cents)
  SELECT :order_id, id, $qty, price_cents FROM products WHERE id = $product;
COMMIT;
```

The conditional `UPDATE … WHERE stock >= $qty` is atomic: of two buyers of the last unit, one updates 1 row and the other 0 rows. A `CHECK (stock >= 0)` on the table is a second safety net. Payment happens after this transaction (with an idempotency key), and a failed payment releases the stock in a new transaction.

</En>

<DeepDive title="More about transactions">

**MVCC.** PostgreSQL keeps multiple versions of rows: readers never block writers and writers never block readers; each transaction sees a consistent snapshot. Old versions are cleaned up by VACUUM.

**Savepoints.** `SAVEPOINT s1; … ROLLBACK TO s1;` undoes part of a transaction without aborting all of it.

**Optimistic locking.** Store a `version` column; `UPDATE … SET version = version + 1 WHERE id = $1 AND version = $2` fails (0 rows) if someone else changed the row; the app retries or reports a conflict (like ETags in APIs).

**Advisory locks.** `pg_advisory_xact_lock(key)` locks an application-defined key, useful for "only one job processes customer X at a time".

**Durability settings.** `synchronous_commit` and replication settings trade a little durability for speed; the defaults are safe.

**ORMs.** Prisma `$transaction`, TypeORM `dataSource.transaction()` and NestJS interceptors wrap the same `BEGIN`/`COMMIT`; the isolation and locking rules don't change.

</DeepDive>

<DeepDive title="Real world: the gift card that paid twice">

A retailer's gift cards were redeemed with this code: read the card's balance, check it covers the order, create the order, then write `balance - amount`. It worked for years.

A user discovered that submitting the checkout form from two browser tabs at the same instant let them spend a $100 card on two $100 orders: both requests read $100, both passed the check, both wrote $0. Shared on a forum, the trick cost the retailer thousands of dollars in a weekend.

The fixes:

1. Redemption became one conditional statement: `UPDATE gift_cards SET balance_cents = balance_cents - $1 WHERE code = $2 AND balance_cents >= $1 RETURNING balance_cents`, inside the same transaction as the order; zero rows means insufficient balance.
2. A `CHECK (balance_cents >= 0)` constraint as a backstop.
3. A redemption log table with a unique `(order_id, card_id)` to prevent double application on retries.
4. A concurrency test that fires 50 parallel redemptions and asserts the balance arithmetic.

</DeepDive>

<DeepDive title="Security lens">

- **Race conditions are exploitable**: attackers deliberately send parallel requests to double-spend coupons, gift cards, votes and limits ("race condition attacks"). Treat check-then-act code on money or quotas as a security issue.
- **Enforce invariants in the database** (constraints, conditional updates), not only in application checks.
- **Statement and lock timeouts** (`lock_timeout`, `statement_timeout`) stop one request from holding locks forever.
- **Audit trails**: record who changed what inside the same transaction as the change, so logs and data never disagree.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What does ACID stand for?">
Atomicity: a transaction's changes apply entirely or not at all. Consistency: every committed transaction leaves the data satisfying all constraints. Isolation: concurrent transactions behave as if they didn't interfere, to the degree set by the isolation level. Durability: committed changes survive crashes.
</QA>

<QA q="What is a lost update and how do you prevent it?">
Two transactions read the same value, compute new values in the application and write them back, so one write overwrites the other. Prevent it with atomic updates that compute in SQL, row locks via SELECT FOR UPDATE, optimistic locking with a version column, or serializable isolation with retries.
</QA>

<QA q="What are the SQL isolation levels?">
Read Uncommitted, Read Committed, Repeatable Read and Serializable, each preventing more anomalies such as dirty reads, non-repeatable reads, phantoms and write skew. PostgreSQL's default is Read Committed, and it treats Read Uncommitted as Read Committed.
</QA>

<QA q="What is a deadlock and how do you avoid it?">
Two transactions each hold a lock the other needs, so both wait forever; the database detects it and aborts one. Avoid it by locking rows in a consistent order, keeping transactions short and retrying aborted ones.
</QA>

<QA q="Why shouldn't you call external APIs inside a database transaction?">
They're slow, so locks and connections are held for a long time, and they can't be rolled back: if the transaction later aborts, the external side effect remains. Do external work outside the transaction, using patterns like outbox, idempotency keys and compensating actions.
</QA>

</DeepDive>
