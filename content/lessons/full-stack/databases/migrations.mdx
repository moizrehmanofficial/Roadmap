<BigIdea>
<Tr>
<En>
A **migration** is a small, versioned script that moves the database schema from one version to the next: create a table, add a column, rename a field, add an index. Migrations live in your repository next to the code, run in order, and the database records which ones it has already applied (Prisma keeps a `_prisma_migrations` table). That gives you the same schema on every laptop, in CI, staging and production, with every change reviewed in a pull request. The rules that keep you out of trouble: **generate in development, review the SQL, apply in production with a deploy command**; **never edit a migration that already ran**, add a new one instead; **read what the tool generated**, because a rename can come out as "drop column, add column" and silently destroy data; and remember that on a busy table a schema change is about **locks**: an `ALTER TABLE` waiting for a lock blocks every query behind it, so set a `lock_timeout`, prefer changes that don't rewrite the table, build indexes `CONCURRENTLY`, and split risky changes into **expand → migrate data → contract** steps.
</En>
<Ur>
**Migration** ek chhota, versioned script hai jo database schema ko ek version se agle par le jata hai: table banana, column jorna, field ka naam badalna, index jorna. Migrations aap ki repository me code ke saath rehti hain, tarteeb se chalti hain, aur database yaad rakhta hai ke kaunsi pehle chal chuki hain (Prisma `_prisma_migrations` table rakhta hai). Is se har laptop, CI, staging aur production me ek jaisa schema milta hai, aur har tabdeeli pull request me review hoti hai. Musibat se bachane wale usool: **development me generate karein, SQL review karein, production me deploy command se chalayen**; **chal chuki migration kabhi edit na karein**, nayi jorein; **tool ka banaya hua parhein**, kyunke naam badalna "column hatao, column jorho" ban kar khamoshi se data mita sakta hai; aur yaad rakhein ke masroof table par schema tabdeeli asal me **locks** ka maamla hai: lock ka intezar karta `ALTER TABLE` apne peeche har query rok deta hai, isliye `lock_timeout` lagayen, table dobara na likhne wali tabdeeliyan chunein, indexes `CONCURRENTLY` banayen, aur khatarnak tabdeeliyon ko **expand → data migrate → contract** qadmon me torein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of migrations as the **renovation log of a building that stays open**.

- Each renovation is a numbered work order (a migration file). The building manager keeps a signed list of finished work orders (the migrations table), so a new crew never redoes or skips one.
- You plan and test each work order in a model building first (the dev database), then the same order is carried out in the real one (deploy).
- You never rewrite a finished work order. If it was wrong, you issue a new one.
- Some jobs need a hallway closed (a lock). If the crew stands in the hallway waiting for a slow visitor to leave, everyone behind them is stuck too. A smart crew waits only a few seconds, steps aside and tries again later (`lock_timeout` and retry).
- Big changes happen in stages: open the new hallway, move people over, then close the old one (expand and contract).

</En>
<Ur>

Migrations ko **khuli rehne wali imarat ki marammat ka register** samjhein.

- Har marammat ek numbered work order hai (migration file). Building manager mukammal work orders ki dastakhat shuda list rakhta hai (migrations table), taa ke nayi team kabhi koi dobara na kare ya chhore.
- Har work order pehle model imarat me plan aur test hota hai (dev database), phir wahi order asal imarat me hota hai (deploy).
- Mukammal work order kabhi dobara nahi likhte. Ghalat tha to naya jaari karte hain.
- Kuch kaamon ke liye hallway band karna parta hai (lock). Agar team hallway me khari ho kar ek sust visitor ke nikalne ka intezar kare, to un ke peeche sab phans jate hain. Samajhdar team sirf chand second rukti hai, hat jati hai aur baad me dobara koshish karti hai (`lock_timeout` aur retry).
- Bari tabdeeliyan marhalon me hoti hain: naya hallway kholo, logon ko muntaqil karo, phir purana band karo (expand aur contract).

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="The Prisma Migrate workflow: dev, status, deploy">

<Tr>
<En>
Two databases stand in for your laptop (`shop_dev`) and production (`shop_prod`). We create the first migration in development, deploy it to production and add real customers. Then we rename a column in the schema, let Prisma draft the migration without applying it, inspect what it wrote, fix it, and deploy. Finally someone edits a migration that already ran. Timestamps in migration names are replaced with a placeholder so the output is stable.
</En>
<Ur>
Do databases aap ke laptop (`shop_dev`) aur production (`shop_prod`) ki jagah hain. Hum development me pehli migration banate hain, production par deploy kar ke asal customers jorte hain. Phir schema me ek column ka naam badalte hain, Prisma se migration chalaye baghair likhwate hain, dekhte hain kya likha, theek karte hain, aur deploy karte hain. Aakhir me koi chal chuki migration edit karta hai. Output mustaqil rakhne ke liye migration naamon ke timestamps ek placeholder se badle gaye hain.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
for db in shop_dev shop_prod; do psql -q -h localhost -U postgres -c "DROP DATABASE IF EXISTS $db" -c "CREATE DATABASE $db" 2> /dev/null; done
npm init -y > /dev/null && npm install -D prisma@7.10.1 --silent
DEV=postgres://postgres:postgres@localhost:5432/shop_dev
PROD=postgres://postgres:postgres@localhost:5432/shop_prod
mkdir -p prisma
cat > prisma.config.ts <<'EOF'
import { defineConfig } from 'prisma/config';
export default defineConfig({ schema: 'prisma/schema.prisma', datasource: { url: process.env.DATABASE_URL! } });
EOF
cat > prisma/schema.prisma <<'EOF'
datasource db {
  provider = "postgresql"
}
model Customer {
  id       Int    @id @default(autoincrement())
  email    String @unique
  fullName String
}
EOF
echo "--- 1. create the first migration on the dev database"
DATABASE_URL=$DEV npx prisma migrate dev --name init > /dev/null 2>&1
find prisma/migrations -type f | sort | sed -E 's/[0-9]{14}/<timestamp>/'
cat prisma/migrations/*_init/migration.sql | grep -v '^--' | grep -v '^$'

echo "--- 2. production: see what's pending, deploy, add real data"
DATABASE_URL=$PROD npx prisma migrate status 2>&1 | grep -E 'not yet been applied|_init$' | sed -E 's/[0-9]{14}/<timestamp>/'
DATABASE_URL=$PROD npx prisma migrate deploy 2>&1 | grep -E 'Applying|successfully' | sed -E 's/[0-9]{14}/<timestamp>/'
psql -q -h localhost -U postgres -d shop_prod -c "INSERT INTO \"Customer\" (email, \"fullName\") VALUES ('jane@example.com','Jane Doe'), ('john@example.com','John Smith')"

echo "--- 3. rename fullName to name in the schema; let Prisma draft the migration"
sed -i 's/fullName String/name     String/' prisma/schema.prisma
DATABASE_URL=$DEV npx prisma migrate dev --name rename_full_name --create-only > /dev/null 2>&1
M=$(ls -d prisma/migrations/*_rename_full_name)
grep -v '^$' $M/migration.sql

echo "--- 4. that SQL would delete every name; replace it with a rename, then apply on dev"
echo 'ALTER TABLE "Customer" RENAME COLUMN "fullName" TO "name";' > $M/migration.sql
DATABASE_URL=$DEV npx prisma migrate dev > /dev/null 2>&1 && echo "dev: applied"

echo "--- 5. deploy to production: the data survives"
DATABASE_URL=$PROD npx prisma migrate deploy 2>&1 | grep -E 'Applying|successfully' | sed -E 's/[0-9]{14}/<timestamp>/'
psql -h localhost -U postgres -d shop_prod -c 'SELECT id, email, name FROM "Customer" ORDER BY id'
psql -h localhost -U postgres -d shop_prod -c "SELECT regexp_replace(migration_name, '^[0-9]+', '<timestamp>') AS migration_name, finished_at IS NOT NULL AS done FROM _prisma_migrations ORDER BY started_at"

echo "--- 6. someone edits a migration that already ran; Prisma notices the checksum change"
echo '-- small tweak' >> prisma/migrations/*_init/migration.sql
DATABASE_URL=$DEV npx prisma migrate dev 2>&1 | grep -E 'modified after|reset' | sed -E 's/[0-9]{14}/<timestamp>/'
```

<Happened>
<Tr>
<En>

- `migrate dev` compared the schema with the dev database and wrote a **plain SQL file** in a timestamped folder. That file is what you review and commit; `migration_lock.toml` records the database provider.
- On production, `migrate status` listed the pending migration and **`migrate deploy`** applied it. Deploy never generates or resets anything: it only runs committed files that haven't run yet.
- After renaming `fullName` to `name`, Prisma couldn't know it was a rename. It drafted **drop the column, add a new one**, and its own warnings say so: all names would be lost, and the new `NOT NULL` column can't even be added to a table with rows. Applied blindly in production it would either fail or, with a default, quietly wipe the data.
- With `--create-only` we got the file without running it, replaced the SQL with `RENAME COLUMN`, and applied it. Production kept Jane and John's names, and `_prisma_migrations` shows both migrations as finished.
- Editing a migration that already ran changed its **checksum**, so `migrate dev` refused to continue and asked to reset the dev database. Shared history must not change: fix mistakes with a **new** migration.

</En>
<Ur>

- `migrate dev` ne schema ko dev database se milaya aur timestamp wale folder me **saada SQL file** likhi. Yahi file aap review aur commit karte hain; `migration_lock.toml` database provider darj karti hai.
- Production par `migrate status` ne baqi migration dikhayi aur **`migrate deploy`** ne use chalaya. Deploy kabhi kuch generate ya reset nahi karta: sirf woh committed files chalata hai jo abhi nahi chalin.
- `fullName` ko `name` karne ke baad Prisma ko pata nahi chal sakta tha ke ye rename hai. Us ne **column hatao, naya jorho** likha, aur us ki apni warnings yahi kehti hain: saare naam khatam ho jayenge, aur naya `NOT NULL` column rows wale table me jor bhi nahi sakte. Production me bina dekhe chalta to ya fail hota ya, default ke saath, khamoshi se data mita deta.
- `--create-only` se humein file chalaye baghair mili, SQL ko `RENAME COLUMN` se badla, aur chalaya. Production ne Jane aur John ke naam rakhe, aur `_prisma_migrations` dono migrations mukammal dikhata hai.
- Chal chuki migration edit karne se us ka **checksum** badla, isliye `migrate dev` ne aage barhne se inkar kiya aur dev database reset karne ko kaha. Shared tareekh nahi badalni chahiye: ghaltiyan **nayi** migration se theek karein.

</Ur>

<Step title="Under the hood: locks, rewrites and safe indexes in PostgreSQL">

<Tr>
<En>
A 200,000-row `orders` table. First a slow report holds a read lock for 4 seconds while an `ALTER TABLE` arrives, and we try a normal app query with a 1-second timeout. Then the same with `lock_timeout` on the migration. Next we check which kinds of `ALTER TABLE` rewrite the whole table, by comparing the table's file on disk before and after. Last, `CREATE INDEX CONCURRENTLY` inside and outside a transaction.
</En>
<Ur>
200,000 rows wala `orders` table. Pehle ek sust report 4 second read lock rakhti hai jab ek `ALTER TABLE` aata hai, aur hum 1 second timeout wali aam app query chalate hain. Phir yahi, migration par `lock_timeout` ke saath. Us ke baad dekhte hain ke `ALTER TABLE` ki kaunsi qismen poora table dobara likhti hain, table ki disk file pehle aur baad me mila kar. Aakhir me `CREATE INDEX CONCURRENTLY` transaction ke andar aur bahar.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
psql -q -h localhost -U postgres -c 'DROP DATABASE IF EXISTS shop_locks' -c 'CREATE DATABASE shop_locks' 2> /dev/null
P="psql -h localhost -U postgres -d shop_locks -qAt"
$P -c "CREATE TABLE orders AS SELECT g AS id, g % 100 AS customer_id, 'open'::text AS status FROM generate_series(1, 200000) g" -c "ALTER TABLE orders ADD PRIMARY KEY (id)"

echo "--- 1. a slow report reads orders for 4 seconds; a migration arrives with no lock_timeout"
$P -c "BEGIN" -c "SELECT count(*) FROM orders" -c "SELECT pg_sleep(4)" -c "COMMIT" > /dev/null &
sleep 1
( $P -c "ALTER TABLE orders ADD COLUMN note text" && echo "migration: finished after waiting for the report" ) &
sleep 0.5
echo "a normal app query (1s timeout) while the migration waits in the lock queue:"
$P -c "SET statement_timeout = '1s'" -c "SELECT status FROM orders WHERE id = 1" 2>&1
wait

echo "--- 2. same situation, but the migration sets lock_timeout"
$P -c "BEGIN" -c "SELECT count(*) FROM orders" -c "SELECT pg_sleep(4)" -c "COMMIT" > /dev/null &
sleep 1
$P -c "SET lock_timeout = '1s'" -c "ALTER TABLE orders ADD COLUMN priority int" 2>&1
echo "a normal app query right after:"
$P -c "SET statement_timeout = '1s'" -c "SELECT status FROM orders WHERE id = 1" 2>&1
wait
$P -c "SET lock_timeout = '1s'" -c "ALTER TABLE orders ADD COLUMN priority int" && echo "retry after the report finished: added"

echo "--- 3. which changes rewrite the whole table? (the file on disk changes when it is rewritten)"
check() { before=$($P -c "SELECT pg_relation_filenode('orders')"); $P -c "$2"; after=$($P -c "SELECT pg_relation_filenode('orders')"); [ "$before" = "$after" ] && r="no rewrite (instant)" || r="REWROTE the table"; printf '%-52s %s\n' "$1" "$r"; }
check "ADD COLUMN with a constant default"      "ALTER TABLE orders ADD COLUMN currency text NOT NULL DEFAULT 'USD'"
check "ADD COLUMN with a volatile default"      "ALTER TABLE orders ADD COLUMN token uuid DEFAULT gen_random_uuid()"
check "change customer_id type int -> bigint"   "ALTER TABLE orders ALTER COLUMN customer_id TYPE bigint"
check "RENAME COLUMN"                           "ALTER TABLE orders RENAME COLUMN note TO notes"

echo "--- 4. indexes: plain CREATE INDEX blocks writes; CONCURRENTLY doesn't, but has rules"
$P -c "BEGIN" -c "CREATE INDEX CONCURRENTLY orders_customer_idx ON orders (customer_id)" -c "COMMIT" 2>&1 | grep ERROR
$P -c "CREATE INDEX CONCURRENTLY orders_customer_idx ON orders (customer_id)" && echo "outside a transaction: index created"
$P -c "SELECT indexname FROM pg_indexes WHERE tablename = 'orders' ORDER BY 1"
```

<Happened>
<Tr>
<En>

- **The lock queue.** `ADD COLUMN` needs an exclusive lock, so it waited for the report. A simple `SELECT` by primary key then **timed out**: it queued **behind** the waiting `ALTER`. A quick migration on a busy table can take the whole app down this way, without doing any work.
- With **`lock_timeout = '1s'`** the migration gave up after a second, the app query answered immediately (`open`), and a retry after the report finished succeeded. Migration tools and scripts should set a lock timeout and retry.
- **Rewrites.** Adding a column with a constant default and renaming are **metadata-only** in modern PostgreSQL: instant on any size. A volatile default (`gen_random_uuid()`) and changing a column type **rewrote all 200,000 rows** while holding the exclusive lock. On a big table that's minutes of downtime; do it with a new column, a batched backfill and a switch-over instead.
- **`CREATE INDEX CONCURRENTLY`** builds an index without blocking writes, but can't run inside a transaction. Tools that wrap each migration in a transaction need it in its own migration, outside a transaction. If a concurrent build fails, it leaves an invalid index you must drop and recreate.

</En>
<Ur>

- **Lock queue.** `ADD COLUMN` ko exclusive lock chahiye, isliye us ne report ka intezar kiya. Phir primary key se ek saada `SELECT` **time out** ho gaya: woh intezar karte `ALTER` ke **peeche** line me laga. Is tarah masroof table par ek chhoti migration bhi koi kaam kiye baghair poori app gira sakti hai.
- **`lock_timeout = '1s'`** ke saath migration ne ek second baad haar maani, app query ne foran jawab diya (`open`), aur report khatam hone ke baad retry kamyab hua. Migration tools aur scripts ko lock timeout aur retry lagana chahiye.
- **Rewrites.** Constant default ke saath column jorna aur naam badalna jadeed PostgreSQL me **sirf metadata** hai: kisi bhi size par foran. Volatile default (`gen_random_uuid()`) aur column type badalne ne exclusive lock rakhte hue **saari 200,000 rows dobara likhin**. Bare table par ye minton ka downtime hai; is ke bajaye naya column, batches me backfill aur switch-over karein.
- **`CREATE INDEX CONCURRENTLY`** writes roke baghair index banata hai, magar transaction ke andar nahi chal sakta. Jo tools har migration ko transaction me lapette hain, un me ise transaction ke bahar alag migration chahiye. Concurrent build fail ho to ek invalid index chhorta hai jise drop kar ke dobara banana hota hai.

</Ur>
</Tr>
</Happened>

</Step>

</Walkthrough>

## Common mistakes

<Compare>
<Bad title="Fixing a migration that already ran">

```text
# 2026..._add_status/migration.sql already ran in staging and production
# "small fix": edit the file and push
ALTER TABLE "Order" ADD COLUMN "status" TEXT NOT NULL DEFAULT 'new';   -- was 'pending'
```

</Bad>
<Good title="Add a new migration">

```text
npx prisma migrate dev --name change_status_default --create-only
-- new file:
ALTER TABLE "Order" ALTER COLUMN "status" SET DEFAULT 'new';
```

</Good>
</Compare>

<Compare>
<Bad title="Renaming a busy column in one deploy">

```text
ALTER TABLE users RENAME COLUMN fullname TO name;
-- old app servers still running during the rollout query "fullname" and crash
```

</Bad>
<Good title="Expand, migrate, contract">

```text
1. ADD COLUMN name; app writes both columns, reads the old one
2. backfill name from fullname in batches; app reads name
3. after every server runs the new code: DROP COLUMN fullname
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Not reading generated SQL**: renames become drop + add, and type changes can rewrite tables. Review every migration in the pull request.
- **Running `migrate dev` or `db push` against production**: they can reset or diff destructively. Production uses `migrate deploy` only.
- **Running migrations on every app replica at startup**: ten pods race to migrate. Use one job or pipeline step before rollout.
- **No `lock_timeout`** on busy tables: a waiting ALTER blocks all traffic behind it.
- **One huge `UPDATE` backfill**: long locks, bloat and replication lag. Update in batches of a few thousand rows.
- **Planning on down migrations**: in production, data has moved on; roll forward with a fix and have backups.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bana SQL na parhna**: rename drop + add ban jata hai, aur type tabdeeliyan table dobara likh sakti hain. Har migration pull request me review karein.
- **Production par `migrate dev` ya `db push` chalana**: ye reset ya tabahkun diff kar sakte hain. Production sirf `migrate deploy` istemal karta hai.
- **App ki har replica ke shuru hone par migrations chalana**: das pods migrate karne ki dor lagate hain. Rollout se pehle ek job ya pipeline qadam lein.
- **Masroof tables par `lock_timeout` nahi**: intezar karta ALTER apne peeche saara traffic rokta hai.
- **Ek bohot bara `UPDATE` backfill**: lambe locks, bloat aur replication lag. Chand hazar rows ke batches me update karein.
- **Down migrations par bharosa**: production me data aage barh chuka hota hai; fix ke saath aage barhein aur backups rakhein.

</Ur>
</Tr>

<Solution>

<Tr>
<En>

```text

  SET lock_timeout = '5s';
  ALTER TABLE orders ADD COLUMN amount_cents bigint;

  UPDATE orders SET amount_cents = round(amount * 100)
  WHERE id BETWEEN $1 AND $2 AND amount_cents IS NULL;

  ALTER TABLE orders ADD CONSTRAINT amount_cents_not_null CHECK (amount_cents IS NOT NULL) NOT VALID;
  ALTER TABLE orders VALIDATE CONSTRAINT amount_cents_not_null;   -- scans, but allows reads and writes

Migration 3 (contract), after every server runs release B:
  ALTER TABLE orders DROP COLUMN amount;
```

<Tr>
<En>
Your app runs as 4 containers behind a load balancer and deploys with a rolling update. Describe where `prisma migrate deploy` runs, what happens if it fails, and which kinds of migrations are safe to ship in the same release as the code that uses them.

<Solution>

<Tr>
<En>

- Run it **once**, as a pipeline step or a one-off job (a Kubernetes Job, a release command), **before** the rolling update starts, using a database user allowed to change the schema.
- If it fails, **stop the deployment**: the old version keeps running against a schema it understands. Fix forward with a new migration.

<DeepDive title="More about migrations">

**Tools.** Prisma Migrate, TypeORM migrations, Knex, node-pg-migrate, Drizzle Kit in Node.js; Flyway and Liquibase in Java shops; Atlas for declarative schemas; Rails, Django and Laravel have their own. They all share the same idea: ordered files plus a table of applied versions.

**Declarative vs imperative.** Prisma and Atlas diff a desired schema and generate SQL (declarative); node-pg-migrate and Flyway run the steps you write (imperative). Declarative tools still need human review for renames and data changes.

**Transactions.** PostgreSQL can run most DDL inside a transaction, so a failed migration rolls back cleanly. A few statements, such as `CREATE INDEX CONCURRENTLY`, can't, and need their own migration.

**Data migrations.** Changing data (backfills, splitting a column) is different from changing structure. Long-running data changes belong in batched jobs, not a single migration that blocks a deploy.

**Squashing.** Hundreds of old migrations slow down fresh setups. Teams sometimes replace them with a single baseline once every environment is up to date.

**Testing.** Run migrations from scratch in CI, and test against a recent copy of production data (anonymized) to catch slow or failing migrations before release.

</DeepDive>

<DeepDive title="Real world: the five-second migration that caused a 20-minute outage">

A team added a nullable column to their `events` table, a change that takes milliseconds. They deployed at noon. At the same moment, an analytics export was running a 20-minute query against `events`. The `ALTER TABLE` waited for the export's lock, and every API request touching `events` queued behind the `ALTER`. Connection pools filled up, health checks failed, and the load balancer marked every server unhealthy. The app was down until someone killed the export.

The fixes:

1. Every migration starts with `SET lock_timeout = '5s'`, and the deploy pipeline retries a timed-out migration a few times before failing.
2. Analytics queries moved to a read replica.
3. A `statement_timeout` for the app role, so no API query can run for minutes.
4. A pre-deploy check listing long-running transactions on the primary.

</DeepDive>

<DeepDive title="Security lens">

- **Separate roles**: the app's database user can read and write data but not change the schema; only the migration job uses a role with DDL rights.
- **Review migrations like code**: a migration can drop tables, grant permissions or disable row-level security. Require approval for the migrations folder.
- **Protect secrets**: production connection strings for migrations live in the CI secret store, not in developer laptops or the repository.
- **Backups before risky migrations**: take or confirm a recent backup and know how to restore it (the next lessons).
- **Sensitive data in migrations**: don't seed real user data or credentials in migration files; they live forever in git history.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are database migrations and why use them?">
Versioned, ordered scripts that change the schema, stored with the code and tracked in a table in the database. They keep every environment consistent, make changes reviewable and repeatable, and let deployments apply schema changes automatically.
</QA>

<QA q="How do you rename a column without downtime?">
Expand and contract: add the new column, deploy code that writes both and reads the old, backfill in batches, switch reads to the new column, and after every server runs the new code, drop the old column in a later migration.
</QA>

<QA q="Why can a fast ALTER TABLE still cause an outage?">
It needs an exclusive lock. If a long transaction holds a conflicting lock, the ALTER waits, and every new query on that table queues behind it. Setting lock_timeout and retrying avoids blocking the queue.
</QA>

<QA q="Should migrations run when the application starts?">
Usually not in multi-instance deployments: replicas race and a failure crashes every instance. Run them once as a separate deployment step before the new version rolls out, with the app compatible with both schemas.
</QA>

<QA q="Do you rely on down migrations for rollback?">
Rarely in production. Once new data has been written, reversing a schema change can lose it. Teams prefer backward-compatible migrations, rolling forward with a fix, and backups for disasters.
</QA>

</DeepDive>
