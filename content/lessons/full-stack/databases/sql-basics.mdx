<BigIdea>
<Tr>
<En>
A **relational database** keeps data in **tables**, like spreadsheets with strict rules. Each **table** is about one kind of thing (products, customers, orders), each **row** is one thing, and each **column** is one detail with a fixed type (text, number, date). **SQL** (Structured Query Language) is how you talk to it. Almost everything you do is one of four actions, called **CRUD**: **Create** rows with `INSERT`, **Read** them with `SELECT`, **Update** them with `UPDATE`, and **Delete** them with `DELETE`. You describe **what** you want ("products under $10, cheapest first"), and the database works out **how** to get it. Rules called **constraints** (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys) stop bad data getting in, and a **JOIN** combines rows from related tables. SQL is over 50 years old and still the most widely used data language in the world.
</En>
<Ur>
**Relational database** data ko **tables** me rakhta hai, sakht qawaid wali spreadsheets ki tarah. Har **table** ek qisam ki cheez ke baare me hoti hai (products, customers, orders), har **row** ek cheez hai, aur har **column** ek muqarrar type (text, number, tareekh) wali ek tafseel. **SQL** (Structured Query Language) is se baat karne ka tareeqa hai. Aap jo kuch karte hain wo taqreeban chaar kaamon me se ek hota hai, jinhe **CRUD** kehte hain: `INSERT` se rows **banana** (Create), `SELECT` se **parhna** (Read), `UPDATE` se **badalna** (Update), aur `DELETE` se **mitana** (Delete). Aap batate hain ke **kya** chahiye ("$10 se saste products, sab se sasta pehle"), aur database khud tay karta hai ke **kaise** laye. **Constraints** naam ke qawaid (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys) ghalat data ko andar aane se rokte hain, aur **JOIN** mutaliqa tables ki rows ko milata hai. SQL 50 saal se zyada purana hai aur ab bhi duniya me sab se zyada istemal hone wali data ki zabaan hai.
</Ur>

## Picture it

<Tr>
<En>

A database is a **library's card catalogue**, run by a very strict librarian.

- Each **drawer** is a **table**: one for books, one for members, one for loans.
- Each **card** in a drawer is a **row**, and every card in that drawer has the **same printed boxes** (columns): Title, Author, Year.
- You never open the drawers yourself. You hand the librarian a **request slip** written in a precise language (SQL): "Bring me the titles of all books by this author published after 2010, newest first."
- The librarian refuses slips that break the rules: a card with no title when the title box is marked *required* (`NOT NULL`), a second member with the same card number (`UNIQUE`), a loan for a book that doesn't exist (foreign key).
- A **JOIN** is asking for information from two drawers at once: "for every loan, show the member's name and the book's title".

</En>
<Ur>

Database ek **library ka card catalogue** hai, jise bohot sakht librarian chalata hai.

- Har **daraaz** ek **table** hai: ek kitabon ki, ek members ki, ek udhaar ki.
- Daraaz ka har **card** ek **row** hai, aur us daraaz ke har card par **wahi chhape hue khaane** (columns) hain: Title, Author, Year.
- Aap daraazen khud kabhi nahi kholte. Aap librarian ko ek bilkul durust zabaan (SQL) me likhi **darkhwast ki parchi** dete hain: "Is author ki 2010 ke baad chhapi saari kitabon ke titles lao, sab se nayi pehle."
- Librarian qawaid torne wali parchiyan mustarad kar deta hai: baghair title ka card jab title ka khaana *zaroori* ho (`NOT NULL`), wahi card number wala doosra member (`UNIQUE`), aisi kitab ka udhaar jo maujood hi nahi (foreign key).
- **JOIN** ek saath do daraazon se maloomat maangna hai: "har udhaar ke liye member ka naam aur kitab ka title dikhao".

</Ur>
</Tr>

## Learn it step by step

<Tr>

Pehle chand baaten: SQL ke keywords case-sensitive nahi (`select` bhi chalta hai), magar unhe BARE HUROOF me likhna riwayat hai. **Text single quotes me jata hai**: `'Pen'`. Har statement `;` par khatam hota hai. `--` comment shuru karta hai.

<Step title="Create a table">

<Tr>
<En>
A table is defined once: its name, and for each column a **name**, a **type** and optional **rules**. This is the "drawer with printed boxes".
</En>
<Ur>
Table ek dafa bayan ki jati hai: us ka naam, aur har column ka **naam**, **type** aur ikhtiyari **qawaid**. Ye "chhape khaanon wali daraaz" hai.
</Ur>
</Tr>

```sql
CREATE TABLE products (
  id        serial PRIMARY KEY,
  name      text NOT NULL,
  category  text NOT NULL DEFAULT 'other',
  price     numeric(8, 2) NOT NULL CHECK (price >= 0),
  stock     integer NOT NULL DEFAULT 0
);
```

```text output
CREATE TABLE
```

<Happened>
<Tr>
<En>

- `products` now exists, with five columns and no rows.
- `serial PRIMARY KEY`: the database gives each new row the next number (1, 2, 3…) automatically, and no two rows can share it.
- `text` holds any length of text; `integer` whole numbers; `numeric(8, 2)` exact decimals with 2 places, which is right for **money** (no `0.1 + 0.2` rounding problems).
- `NOT NULL` means the column must have a value. `DEFAULT 'other'` fills it in if you don't. `CHECK (price >= 0)` rejects negative prices.
- `psql` replied `CREATE TABLE`: the command's **tag**, telling you what happened.

</En>
<Ur>

- `products` ab maujood hai, paanch columns ke saath aur koi row nahi.
- `serial PRIMARY KEY`: database har nayi row ko khud agla number deta hai (1, 2, 3…), aur do rows ka ek number nahi ho sakta.
- `text` kisi bhi lambai ka text rakhta hai; `integer` poore numbers; `numeric(8, 2)` 2 decimal jagahon wale durust decimals, jo **paison** ke liye sahi hai (koi `0.1 + 0.2` wali rounding ke masle nahi).
- `NOT NULL` ka matlab column me value honi chahiye. `DEFAULT 'other'` aap na dein to bhar deta hai. `CHECK (price >= 0)` manfi prices mustarad karta hai.
- `psql` ne `CREATE TABLE` jawab diya: command ka **tag**, jo batata hai kya hua.

</Ur>
</Tr>
</Happened>

<En>

- We never gave an `id`: `serial` numbered them 1 to 6.
- The gift card left out `category` and `stock`, so it got the defaults: `'other'` and `0`.

</En>
<Ur>

- `INSERT 0 5` ka matlab "**5** rows daali gayin" (`0` purane PostgreSQL versions ki baqiyat hai; nazar andaz karein). Phir gift card ke liye `INSERT 0 1`.
- Humne kabhi `id` nahi di: `serial` ne unhe 1 se 6 tak number diye.
- Gift card ne `category` aur `stock` chhor diye, isliye use defaults mile: `'other'` aur `0`.

<Step title="Filter rows with WHERE">

<Tr>
<En>
`WHERE` keeps only rows for which a condition is true. Combine conditions with `AND` and `OR`; use `IN` for "one of these", `BETWEEN` for ranges and `ILIKE` for case-insensitive text matching with `%` as "anything".
</En>
<Ur>
`WHERE` sirf wo rows rakhta hai jin ke liye shart sach ho. Shartein `AND` aur `OR` se jorein; "in me se ek" ke liye `IN`, had ke liye `BETWEEN`, aur case ki parwah kiye baghair text milane ke liye `ILIKE` lein, jahan `%` ka matlab "kuch bhi".
</Ur>
</Tr>

```sql
SELECT name, price FROM products WHERE price < 10;

SELECT name, category, stock FROM products
WHERE category = 'home' AND stock > 20;

SELECT name FROM products WHERE category IN ('bags', 'other');

SELECT name, price FROM products WHERE name ILIKE '%pen%' OR price BETWEEN 25 AND 30;
```

```text output
   name   | price
----------+-------
 Notebook |  5.00
 Pen      |  2.00
 Mug      |  8.50
(3 rows)

 name | category | stock
------+----------+-------
 Mug  | home     |    60
(1 row)

   name
-----------
 Backpack
 Gift card
(2 rows)

   name    | price
-----------+-------
 Pen       |  2.00
 Desk lamp | 30.00
 Gift card | 25.00
(3 rows)
```

<Happened>
<Tr>
<En>

- `price < 10`: Notebook, Pen and Mug.
- `category = 'home' AND stock > 20`: only the mug; the desk lamp is in `home` but has 15 in stock. Note: comparing uses a **single** `=` in SQL.
- `IN ('bags', 'other')`: the backpack and the gift card.
- `ILIKE '%pen%'` matches "Pen" whatever the capitals, and `BETWEEN 25 AND 30` includes both ends, so it adds the desk lamp (30) and the gift card (25).

</En>
<Ur>

- `price < 10`: Notebook, Pen aur Mug.
- `category = 'home' AND stock > 20`: sirf mug; desk lamp `home` me hai magar stock 15 hai. Dhyan: SQL me muqabla **ek** `=` se hota hai.
- `IN ('bags', 'other')`: backpack aur gift card.
- `ILIKE '%pen%'` "Pen" se milta hai bare chhote huroof kuch bhi hon, aur `BETWEEN 25 AND 30` dono kinare shamil karta hai, isliye desk lamp (30) aur gift card (25) jur jate hain.

</Ur>
</Tr>

<Step title="Sort and page with ORDER BY and LIMIT">

<Tr>
<En>
`ORDER BY` sorts (`ASC` ascending is the default, `DESC` descending). `LIMIT` returns only the first N rows, and `OFFSET` skips some first: together they make pages.
</En>
<Ur>
`ORDER BY` tarteeb deta hai (`ASC` barhti hui default hai, `DESC` ghatti hui). `LIMIT` sirf pehli N rows wapas karta hai, aur `OFFSET` pehle kuch chhor deta hai: dono mil kar pages banate hain.
</Ur>
</Tr>

```sql
SELECT name, price FROM products ORDER BY price DESC LIMIT 3;

SELECT name, category, price FROM products ORDER BY category, price;

SELECT id, name FROM products ORDER BY id LIMIT 2 OFFSET 2;
```

```text output
   name    | price
-----------+-------
 Backpack  | 45.00
 Desk lamp | 30.00
 Gift card | 25.00
(3 rows)

   name    |  category  | price
-----------+------------+-------
 Backpack  | bags       | 45.00
 Mug       | home       |  8.50
 Desk lamp | home       | 30.00
 Gift card | other      | 25.00
 Pen       | stationery |  2.00
 Notebook  | stationery |  5.00
(6 rows)

 id |   name
----+-----------
  3 | Desk lamp
  4 | Backpack
(2 rows)
```

<Happened>
<Tr>
<En>

- Most expensive first, top 3: backpack, desk lamp, gift card.
- `ORDER BY category, price`: sorted by category alphabetically, then by price **within** each category.
- `LIMIT 2 OFFSET 2` skipped rows 1–2 and returned rows 3–4: "page 2" with 2 per page.
- Always use `ORDER BY` with `LIMIT`; otherwise "the first 3" can be any 3.

</En>
<Ur>

- Sab se mehanga pehle, top 3: backpack, desk lamp, gift card.
- `ORDER BY category, price`: pehle category alphabet ke hisaab se, phir har category ke **andar** price se.
- `LIMIT 2 OFFSET 2` ne rows 1–2 chhor kar rows 3–4 wapas kin: har page par 2 ke hisaab se "page 2".
- `LIMIT` ke saath hamesha `ORDER BY` lein; warna "pehle 3" koi bhi 3 ho sakte hain.

</Ur>
</Tr>
</Happened>

<Step title="Calculations and column names">

<Tr>
<En>
A `SELECT` can calculate new values from columns, call functions, and give the result a readable name with `AS`.
</En>
<Ur>
`SELECT` columns se nayi values nikal sakta hai, functions call kar sakta hai, aur `AS` se nateeje ko parhne ke qabil naam de sakta hai.
</Ur>
</Tr>

```sql
SELECT
  upper(name)        AS product,
  price,
  stock,
  price * stock      AS stock_value,
  round(price * 1.08, 2) AS price_with_tax
FROM products
WHERE stock > 0
ORDER BY stock_value DESC;
```

```text output
  product  | price | stock | stock_value | price_with_tax
-----------+-------+-------+-------------+----------------
 NOTEBOOK  |  5.00 |   120 |      600.00 |           5.40
 PEN       |  2.00 |   300 |      600.00 |           2.16
 MUG       |  8.50 |    60 |      510.00 |           9.18
 DESK LAMP | 30.00 |    15 |      450.00 |          32.40
(4 rows)
```

<Happened>
<Tr>
<En>

- `price * stock` was worked out for every row; `AS stock_value` named the column, and we could even sort by that name.
- `upper(name)` capitalised the text; `round(…, 2)` kept two decimal places after adding 8% tax.
- `WHERE stock > 0` left out the backpack and the gift card.
- Nothing in the table changed: `SELECT` only reads.

</En>
<Ur>

- `price * stock` har row ke liye nikala gaya; `AS stock_value` ne column ko naam diya, aur hum us naam se tarteeb bhi de sake.
- `upper(name)` ne text bare huroof me kiya; `round(…, 2)` ne 8% tax jorne ke baad do decimal jagahen rakhin.
- `WHERE stock > 0` ne backpack aur gift card ko chhor diya.
- Table me kuch nahi badla: `SELECT` sirf parhta hai.

</Ur>
</Tr>
</Happened>

<Step title="Totals with COUNT, SUM, AVG and GROUP BY">

<Tr>
<En>
**Aggregate functions** turn many rows into one value. With **`GROUP BY`**, you get one result row per group. **`HAVING`** filters those groups (while `WHERE` filters rows before grouping).
</En>
<Ur>
**Aggregate functions** kai rows ko ek value me badalte hain. **`GROUP BY`** ke saath har group ki ek nateeja row milti hai. **`HAVING`** un groups ko filter karta hai (jabke `WHERE` grouping se pehle rows filter karta hai).
</Ur>
</Tr>

```sql
SELECT count(*) AS products, sum(stock) AS units, round(avg(price), 2) AS avg_price
FROM products;

SELECT category, count(*) AS products, sum(price * stock) AS stock_value
FROM products
GROUP BY category
ORDER BY stock_value DESC;

SELECT category, count(*) AS products
FROM products
GROUP BY category
HAVING count(*) >= 2;
```

```text output
 products | units | avg_price
----------+-------+-----------
        6 |   495 |     19.25
(1 row)

  category  | products | stock_value
------------+----------+-------------
 stationery |        2 |     1200.00
 home       |        2 |      960.00
 bags       |        1 |        0.00
 other      |        1 |        0.00
(4 rows)

  category  | products
------------+----------
 stationery |        2
 home       |        2
(2 rows)
```

<Happened>
<Tr>
<En>

- The first query summarised the whole table in one row: 6 products, 495 units, average price 19.25.
- `GROUP BY category` produced one row per category, each with its own count and total value. Stationery leads because of the many pens and notebooks.
- `HAVING count(*) >= 2` kept only categories with at least two products: home and stationery.
- Every column in a grouped `SELECT` must either be in `GROUP BY` or inside an aggregate; otherwise PostgreSQL refuses, because it wouldn't know which row's value to show.

</En>
<Ur>

- Pehli query ne poori table ek row me samet di: 6 products, 495 units, ausat price 19.25.

- `HAVING count(*) >= 2` ne sirf kam az kam do products wali categories rakhin: home aur stationery.
- Grouped `SELECT` ka har column ya to `GROUP BY` me ho ya kisi aggregate ke andar; warna PostgreSQL inkar karta hai, kyun ke use pata nahi hota ke kis row ki value dikhaye.

<Step title="Update: change existing rows">

<Tr>
<En>
`UPDATE` changes values in rows that match a `WHERE`. In PostgreSQL, **`RETURNING`** shows the changed rows, which saves a second query.
</En>

```sql
UPDATE products SET price = price * 0.9 WHERE category = 'home' RETURNING name, price;
```

<Step title="The forgotten WHERE">

<Tr>
<En>
An `UPDATE` or `DELETE` **without** `WHERE` affects **every row**. To try something risky safely, wrap it in a **transaction**: `BEGIN`, run it, look, then `ROLLBACK` to undo or `COMMIT` to keep.
</En>
<Ur>
`WHERE` **ke baghair** `UPDATE` ya `DELETE` **har row** par asar karta hai. Koi khatarnak cheez mehfooz tareeqe se aazmani ho to use **transaction** me lapetein: `BEGIN`, chalayen, dekhein, phir wapas karne ke liye `ROLLBACK` ya rakhne ke liye `COMMIT`.
</Ur>
</Tr>

```sql
BEGIN;
UPDATE products SET price = 0;
SELECT name, price FROM products ORDER BY id LIMIT 3;
ROLLBACK;

SELECT name, price FROM products ORDER BY id LIMIT 3;
```

```text output
BEGIN
UPDATE 6
   name    | price
-----------+-------
 Notebook  |  0.00
 Pen       |  0.00
 Desk lamp |  0.00
(3 rows)

ROLLBACK
   name    | price
-----------+-------
 Notebook  |  4.50
 Pen       |  2.00
 Desk lamp | 27.00
(3 rows)
```

<Happened>
<Tr>
<En>

- `UPDATE 6`: the missing `WHERE` set **all six** prices to 0. In a real shop, that's every product free.
- Inside the transaction we could see the damage. `ROLLBACK` threw it all away.
- The last query, outside the transaction, shows the real prices are untouched.
- Habits that prevent disasters: write the `WHERE` **first**; run the same `WHERE` as a `SELECT` to see which rows match; use a transaction for manual fixes; and keep backups.

</En>
<Ur>

- `UPDATE 6`: ghayab `WHERE` ne **chhe ki chhe** prices 0 kar din. Asli dukaan me iska matlab har product muft.
- Transaction ke andar hum nuqsan dekh sake. `ROLLBACK` ne sab phenk diya.
- Aakhri query, transaction ke bahar, dikhati hai ke asli prices waisi hi hain.
- Tabahi se bachane wali aadaten: `WHERE` **pehle** likhein; wahi `WHERE` `SELECT` ki shakal me chala kar dekhein kaun si rows milti hain; haath se theek karne ke liye transaction lein; aur backups rakhein.

</Ur>
</Tr>
</Happened>

<Tr>
<En>
The rules in `CREATE TABLE` are enforced on **every** insert and update, from any program. Let's break each one on purpose.

```sql
INSERT INTO products (name, price) VALUES (NULL, 3.00);
```

<Step title="Two related tables and a first JOIN">

<Tr>
<En>
Real data is split across tables that **refer to each other**. An order belongs to a customer, so `orders` stores the customer's `id` in a **foreign key** column. A **`JOIN`** puts the matching rows back together when you read.
</En>
<Ur>
Asli data aisi tables me banta hota hai jo **ek doosre ka hawala** deti hain. Order kisi customer ka hota hai, isliye `orders` **foreign key** column me customer ki `id` rakhti hai. Parhte waqt **`JOIN`** milti hui rows ko dobara jor deta hai.
</Ur>
</Tr>

```sql
CREATE TABLE customers (
  id    serial PRIMARY KEY,
  name  text NOT NULL,
  email text NOT NULL UNIQUE
);

CREATE TABLE orders (
  id          serial PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES customers (id),
  total       numeric(8, 2) NOT NULL,
  placed_on   date NOT NULL DEFAULT '2026-11-01'
);

INSERT INTO customers (name, email) VALUES
  ('Sara Lee', 'sara@example.com'),
  ('Alex Kim', 'alex@example.com'),
  ('Emma Stone', 'emma@example.com');

INSERT INTO orders (customer_id, total, placed_on) VALUES
  (1, 42.00, '2026-11-02'),
  (1, 9.50,  '2026-11-05'),
  (2, 120.00, '2026-11-06');
```

```text output

CREATE TABLE
INSERT 0 3
INSERT 0 3
```

<Happened>
<Tr>
<En>

- `customer_id integer NOT NULL REFERENCES customers (id)` is the **foreign key**: every order must point at a customer that exists.
- `email … UNIQUE` means no two customers can share an email.
- Sara (id 1) has two orders, Alex (id 2) has one, Emma (id 3) has none.

</En>
<Ur>

- `customer_id integer NOT NULL REFERENCES customers (id)` **foreign key** hai: har order ko kisi maujood customer ki taraf ishara karna chahiye.
- `email … UNIQUE` ka matlab do customers ka ek email nahi ho sakta.
- Sara (id 1) ke do orders hain, Alex (id 2) ka ek, Emma (id 3) ka koi nahi.

</Ur>
</Tr>
</Happened>

<Step title="JOIN: read across tables">

<Tr>
<En>
`JOIN … ON …` matches rows where the condition is true. An **inner join** (plain `JOIN`) keeps only matches; a **`LEFT JOIN`** keeps every row from the left table, filling in `NULL` where there's no match.
</En>
<Ur>
`JOIN … ON …` un rows ko milata hai jahan shart sach ho. **Inner join** (saada `JOIN`) sirf mile hue rakhta hai; **`LEFT JOIN`** baayen table ki har row rakhta hai, aur jahan mel na ho wahan `NULL` bharta hai.
</Ur>
</Tr>

```sql
SELECT o.id AS order_id, c.name, o.total, o.placed_on
FROM orders o
JOIN customers c ON c.id = o.customer_id
ORDER BY o.id;

SELECT c.name, count(o.id) AS orders, coalesce(sum(o.total), 0) AS spent
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.name
ORDER BY spent DESC;

INSERT INTO orders (customer_id, total) VALUES (99, 10.00);
```

```text output
 order_id |   name   | total  | placed_on
----------+----------+--------+------------
        1 | Sara Lee |  42.00 | 2026-11-02
        2 | Sara Lee |   9.50 | 2026-11-05
        3 | Alex Kim | 120.00 | 2026-11-06
(3 rows)

    name    | orders | spent
------------+--------+--------
 Alex Kim   |      1 | 120.00
 Sara Lee   |      2 |  51.50
 Emma Stone |      0 |      0
(3 rows)

ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(99) is not present in table "customers".
```

<Happened>
<Tr>
<En>

- The first query shows each order **with the customer's name**, which lives in another table. `o` and `c` are short **aliases** for the table names.
- The second uses `LEFT JOIN`, so Emma appears even with no orders. `count(o.id)` counts only real orders (0 for her), and `coalesce(sum(o.total), 0)` turns her `NULL` total into 0.
- The last insert points at customer 99, who doesn't exist, so the **foreign key** rejects it. No "orphan" orders.
- Joins have a full lesson of their own; this is the core idea.

</En>
<Ur>

- Pehli query har order **customer ke naam ke saath** dikhati hai, jo doosri table me hai. `o` aur `c` tables ke naamon ke chhote **aliases** hain.
- Doosri `LEFT JOIN` istemal karti hai, isliye Emma koi order na hone ke bawajood nazar aati hai. `count(o.id)` sirf asli orders ginta hai (us ke liye 0), aur `coalesce(sum(o.total), 0)` us ke `NULL` total ko 0 bana deta hai.
- Aakhri insert customer 99 ki taraf ishara karta hai, jo maujood hi nahi, isliye **foreign key** use mustarad karti hai. Koi "yateem" orders nahi.
- Joins ka apna poora lesson hai; ye asal khayal hai.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="NULL is not a value">

<Tr>
<En>
`NULL` means "unknown". It isn't zero or empty text, and **any comparison with `NULL` is unknown**, so `= NULL` never matches. Use `IS NULL` and `IS NOT NULL`.
</En>
<Ur>
`NULL` ka matlab "maloom nahi". Ye zero ya khaali text nahi, aur **`NULL` ke saath har muqabla bhi maloom nahi** hota, isliye `= NULL` kabhi nahi milta. `IS NULL` aur `IS NOT NULL` lein.
</Ur>
</Tr>

```sql
ALTER TABLE products ADD COLUMN discount numeric(4, 2);
UPDATE products SET discount = 0.10 WHERE id = 2;

SELECT count(*) AS with_equals FROM products WHERE discount = NULL;
SELECT count(*) AS with_is FROM products WHERE discount IS NULL;
SELECT name, price, round(price * (1 - coalesce(discount, 0)), 2) AS final_price
FROM products ORDER BY id;
```

```text output
ALTER TABLE
UPDATE 1
 with_equals
-------------
           0
(1 row)

 with_is
---------
       4
(1 row)

   name    | price | final_price
-----------+-------+-------------
 Notebook  |  4.50 |        4.50
 Pen       |  2.00 |        1.80
 Desk lamp | 27.00 |       27.00
 Backpack  | 45.00 |       45.00
 Mug       |  7.65 |        7.65
(5 rows)
```

<Happened>
<Tr>
<En>

- `ALTER TABLE … ADD COLUMN` added a column to the existing table; every existing row got `NULL` in it. Then only the pen got a 10% discount.
- `WHERE discount = NULL` matched **0** rows, even though four rows have no discount.
- `WHERE discount IS NULL` correctly found all **4**.
- Arithmetic with `NULL` gives `NULL`, so `coalesce(discount, 0)` treats "no discount" as 0. The pen's final price is 1.80; the others keep their price.

</En>
<Ur>

- `ALTER TABLE … ADD COLUMN` ne maujooda table me column jora; har maujood row me `NULL` aaya. Phir sirf pen ko 10% discount mila.
- `WHERE discount = NULL` ne **0** rows milayin, halanke chaar rows ka koi discount nahi.
- `WHERE discount IS NULL` ne durust tareeqe se saari **4** dhoond lin.
- `NULL` ke saath hisaab `NULL` deta hai, isliye `coalesce(discount, 0)` "koi discount nahi" ko 0 samajhta hai. Pen ki aakhri price 1.80 hai; baqi apni price par rehte hain.

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="UPDATE or DELETE with no WHERE">

```sql
DELETE FROM orders;   -- every order is gone
```

</Bad>
<Good title="Check first, then change">

```sql
SELECT id FROM orders WHERE placed_on < '2025-01-01';
DELETE FROM orders WHERE placed_on < '2025-01-01';
```

</Good>
</Compare>

<Compare>
<Bad title="Double quotes for text">

```sql
SELECT * FROM products WHERE name = "Pen";
-- ERROR: column "Pen" does not exist
```

<Tr>
<En>In PostgreSQL, double quotes mean a **column or table name**.</En>
<Ur>PostgreSQL me double quotes ka matlab **column ya table ka naam** hai.</Ur>
</Tr>

</Bad>
<Good title="Single quotes for text">

```sql
SELECT * FROM products WHERE name = 'Pen';
```

</Good>
</Compare>

<Compare>
<Bad title="Comparing with NULL using =">

```sql
SELECT * FROM products WHERE discount = NULL;   -- always 0 rows
```

</Bad>
<Good title="IS NULL">

```sql
SELECT * FROM products WHERE discount IS NULL;
```

</Good>
</Compare>

<Compare>
<Bad title="Building SQL by joining strings in code">

```text
db.query("SELECT * FROM users WHERE email = '" + email + "'");
```

<Tr>
<En>If `email` is `' OR '1'='1`, the query returns every user. This is **SQL injection**.</En>
<Ur>Agar `email` `' OR '1'='1` ho to query har user wapas karti hai. Ye **SQL injection** hai.</Ur>
</Tr>

</Bad>
<Good title="Parameters">

```text
db.query("SELECT * FROM users WHERE email = $1", [email]);
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Floating-point types for money** (`real`, `double precision`). Use `numeric(10, 2)` or store cents as `integer`.
- **`LIMIT` without `ORDER BY`**, which gives an unpredictable "top N".
- **`SELECT *` in application code**, which sends unneeded (sometimes sensitive) columns.
- **No primary key** on a table, which makes updating one specific row hard.
- **Storing lists in one text column** (`"red,blue,green"`). Use a separate table with one row per item.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Paison ke liye floating-point types** (`real`, `double precision`). `numeric(10, 2)` lein ya cents `integer` me rakhein.
- **`ORDER BY` ke baghair `LIMIT`**, jo ghair yaqeeni "top N" deta hai.
- **Application code me `SELECT *`**, jo ghair zaroori (kabhi hassas) columns bhejta hai.
- **Table par primary key na hona**, jis se kisi khaas row ko badalna mushkil hota hai.
- **Ek text column me lists rakhna** (`"red,blue,green"`). Har item ki ek row wali alag table lein.

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Data lives in **tables** of **rows** and typed **columns**; each row has a **primary key**.
- CRUD = `INSERT` (create), `SELECT` (read), `UPDATE` (update), `DELETE` (delete).
- `WHERE` filters, `ORDER BY` sorts, `LIMIT`/`OFFSET` page; text uses **single quotes**.
- Calculate in `SELECT`, name results with `AS`; summarise with `COUNT`, `SUM`, `AVG` and `GROUP BY`, filter groups with `HAVING`.
- Always write the `WHERE` for `UPDATE`/`DELETE`; test it as a `SELECT` and use `BEGIN … ROLLBACK` for risky changes.
- Constraints (`NOT NULL`, `CHECK`, `UNIQUE`, primary and foreign keys) reject bad data from any source.
- `JOIN` combines related tables; `LEFT JOIN` keeps rows without matches.
- `NULL` means unknown: use `IS NULL` and `coalesce`.
- In code, always pass values as **parameters**, never by joining strings.

</En>

<DeepDive title="How a query is evaluated, and other details">

**Logical order.** You write `SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT`, but the database evaluates it as: `FROM`/`JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. That's why `WHERE` can't use an alias defined in `SELECT`, but `ORDER BY` can.

**Identity columns.** Modern PostgreSQL prefers `id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY` over `serial`. Many apps use UUIDs (`uuid DEFAULT gen_random_uuid()`) so ids can't be guessed.

**Types worth knowing:** `text`, `varchar(n)`, `integer`, `bigint`, `numeric(p, s)`, `boolean`, `date`, `timestamptz` (always store times with time zones), `jsonb` (indexed JSON), `uuid`, arrays.

**Upsert.** `INSERT … ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name` inserts or updates in one atomic statement.

**Indexes.** Without an index, `WHERE email = '…'` reads every row. `CREATE INDEX ON customers (email);` makes it fast; `UNIQUE` and primary keys create indexes automatically. `EXPLAIN ANALYZE` shows how a query runs.

**Transactions and ACID.** Statements inside `BEGIN … COMMIT` are **atomic** (all or nothing), keep the data **consistent** with constraints, run **isolated** from other transactions, and are **durable** once committed.

**Pagination at scale.** `OFFSET 100000` still reads and discards 100,000 rows. "Keyset" pagination (`WHERE id > last_seen_id ORDER BY id LIMIT 20`) stays fast.

**Dialects.** Core SQL is shared, but details differ: MySQL uses `AUTO_INCREMENT` and backticks for names; SQLite is very loose about types; `ILIKE` and `RETURNING` are PostgreSQL features (SQLite now has `RETURNING` too).

</DeepDive>

<DeepDive title="Real world: the support script without a WHERE">

A support engineer at an online shop needed to cancel one customer's pending order. They opened a database console on production and typed:

```text
UPDATE orders SET status = 'cancelled'
```

They meant to add `WHERE id = 48213` on the next line, but pressed Enter. The console ran the statement immediately: `UPDATE 1384022`. Every order in the system, including delivered and refunded ones, was now "cancelled". Customers started receiving cancellation emails within minutes, because an automation listened for status changes.

Recovery took most of a day: restoring from the nightly backup into a separate database, then copying back the correct statuses, then reconciling orders placed since the backup.

The changes the team made afterwards are standard practice:

1. **Production consoles start a transaction automatically** (many tools have a "manual commit" mode), so nothing is permanent until `COMMIT`.
2. **Read-only access by default**; write access only through reviewed scripts.
3. **The `pg-safeupdate` extension** (or MySQL's `sql_safe_updates`) rejects `UPDATE` and `DELETE` without a `WHERE`.
4. **Point-in-time recovery** so restores don't lose a whole day.

</DeepDive>

<DeepDive title="Security lens">

The database holds the most valuable data in the system, so it's the main target.

- **SQL injection** is the classic attack: user input concatenated into SQL becomes part of the command. `' OR '1'='1` can log in as anyone; `'; DROP TABLE users; --` can destroy data. **Always use parameters** (`$1`, `?`) or a query builder/ORM; never build SQL with string joining or template literals.
- **Least privilege.** The app's database user should only have the permissions it needs (often `SELECT`, `INSERT`, `UPDATE` on specific tables, no `DROP`). Admin credentials never belong in the app.
- **Row-level security.** One SQL bug shouldn't show one customer another customer's orders. Filter by the logged-in user's id in every query, or enforce it in the database with row-level security (used heavily by Supabase).
- **Never store plain passwords.** Store a slow hash (bcrypt, Argon2) instead.
- **Don't select more than you need.** `SELECT *` on a users table can leak password hashes and reset tokens into logs and API responses.
- **Error messages.** Database errors contain table and column names. Log them on the server; show users a generic message.
- **Backups are part of security.** Test that you can restore them; ransomware and mistakes both make them essential.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What do CRUD operations map to in SQL?">
Create is INSERT, Read is SELECT, Update is UPDATE and Delete is DELETE. CREATE TABLE, ALTER TABLE and DROP TABLE change the structure rather than the data.
</QA>

<QA q="What is the difference between WHERE and HAVING?">
WHERE filters individual rows before grouping and cannot use aggregate functions. HAVING filters groups after GROUP BY and can use aggregates such as count or sum.
</QA>

<QA q="What is a primary key and what is a foreign key?">
A primary key uniquely identifies each row of a table and cannot be null. A foreign key is a column that references the primary key of another table, ensuring every value points at an existing row and defining the relationship between the tables.
</QA>

<QA q="What is the difference between an inner join and a left join?">
An inner join returns only rows that have a match in both tables. A left join returns every row from the left table and the matching rows from the right table, with nulls where there is no match.
</QA>

<QA q="Why can you not compare with NULL using equals?">
NULL represents an unknown value, so any comparison with it yields unknown rather than true, and WHERE only keeps rows where the condition is true. Use IS NULL or IS NOT NULL, and coalesce to substitute a default.
</QA>

<QA q="What is SQL injection and how do you prevent it?">
It is an attack where user input is interpreted as part of a SQL statement because the query was built by concatenating strings. It is prevented by using parameterised queries or prepared statements, which send the values separately from the SQL text, plus least-privilege database accounts.
</QA>

<QA q="What is a transaction?">
A group of statements that execute as a single unit: either all take effect on COMMIT or none do on ROLLBACK. Transactions provide atomicity, consistency, isolation and durability.
</QA>

</DeepDive>
