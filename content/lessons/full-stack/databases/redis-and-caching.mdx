<BigIdea>
<Tr>
<En>
**Redis** is a database that keeps everything **in memory**, so reads and writes take well under a millisecond. Instead of tables it has **keys**, and each key holds a **data type** with its own commands: **strings** (text, numbers, JSON) with optional **expiry** and atomic counters (`INCR`), **hashes** (an object's fields), **lists** (ordered, like a queue or "latest 10 activities"), **sets** (unique members) and **sorted sets** (members ordered by a score, perfect for leaderboards). That makes Redis the standard tool for **caching** expensive results, **sessions**, **rate limiting**, **locks**, **queues** (BullMQ is built on it) and **real-time counters**. The most common pattern is **cache-aside**: look in Redis first; on a miss, read the database and store the result with a **TTL**; when the data changes, **delete** the cached copy. Memory is limited, so you also decide what Redis does when it's full: refuse writes (`noeviction`) or evict the least recently used keys (`allkeys-lru`). Redis is usually a fast layer **next to** your main database, not a replacement for it.
</En>
<Ur>
**Redis** aisa database hai jo sab kuch **memory me** rakhta hai, isliye parhna aur likhna ek millisecond se bhi kam leta hai. Tables ke bajaye is me **keys** hain, aur har key ek **data type** rakhti hai jis ke apne commands hain: **strings** (text, numbers, JSON) ikhtiyari **expiry** aur atomic counters (`INCR`) ke saath, **hashes** (object ke fields), **lists** (tarteeb wali, queue ya "aakhri 10 activities" jaisi), **sets** (unique members) aur **sorted sets** (score se tarteeb diye members, leaderboards ke liye behtareen). Isi liye Redis mehnge nataij ki **caching**, **sessions**, **rate limiting**, **locks**, **queues** (BullMQ isi par bana hai) aur **real-time counters** ka mayari auzaar hai. Sab se aam pattern **cache-aside** hai: pehle Redis me dekho; na mile to database parho aur nateeja **TTL** ke saath rakho; data badle to cached copy **mita do**. Memory mehdood hai, isliye aap ye bhi tay karte hain ke bharne par Redis kya kare: writes rad kare (`noeviction`) ya sab se kam haal me istemal hui keys nikal de (`allkeys-lru`). Redis aam taur par aap ke asal database ke **saath** ek tez parat hai, us ki jagah nahi.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **chef's countertop next to the walk-in freezer**.

- The **freezer** is your main database: everything is there and safe, but walking in and searching takes time.
- The **countertop** is Redis: small, right at hand, with the things used most often. Grabbing from it is instant.
- Each item on the counter has a **"use by" sticker** (TTL), so nothing sits there forever.
- When the recipe changes, the chef **throws away the old prepared sauce** on the counter (invalidation); otherwise the next dish uses the old one.
- When the counter is full, either the chef refuses to put anything else down (noeviction), or clears the thing that hasn't been touched longest (LRU eviction).

</En>
<Ur>

**Walk-in freezer ke saath chef ka countertop** sochein.

- **Freezer** aap ka asal database hai: sab kuch wahan mehfooz hai, magar andar ja kar dhoondhne me waqt lagta hai.
- **Countertop** Redis hai: chhota, haath ke paas, sab se zyada istemal hone wali cheezon ke saath. Is se uthana foran hai.
- Counter par har cheez par **"is tareekh tak istemal"** sticker hai (TTL), isliye kuch hamesha nahi para rehta.
- Jab recipe badle, chef counter par rakhi **purani tayyar sauce phenk deta** hai (invalidation); warna agli dish purani wali istemal karti hai.
- Counter bhar jaye to ya chef kuch aur rakhne se inkar karta hai (noeviction), ya sab se der se na chhui cheez hata deta hai (LRU eviction).

</Ur>
</Tr>

<Step title="The data types, from redis-cli">

<Tr>
<En>
Each command is printed like the `redis-cli` prompt, followed by Redis's reply. Everything goes into database number 5 (`-n 5`) so it doesn't touch other data, and the database is emptied first.
</En>
<Ur>
Har command `redis-cli` prompt ki tarah chhapi jati hai, us ke baad Redis ka jawab. Sab kuch database number 5 (`-n 5`) me jata hai taa ke doosre data ko na chhooye, aur pehle database khaali kiya jata hai.
</Ur>

```bash
# show each command like redis-cli's prompt, then its reply (database 5, so we don't touch other data)
r() {
  printf '>'; for a in "$@"; do case "$a" in *" "*) printf ' "%s"' "$a" ;; *) printf ' %s' "$a" ;; esac; done; echo
  redis-cli --no-raw -n 5 "$@" | sed 's/^/  /'
}
redis-cli -n 5 FLUSHDB > /dev/null

echo "--- strings: values, counters, expiry"
r SET greeting "hello" EX 60
r GET greeting
r TTL greeting
r INCR page:views
r INCRBY page:views 10
r SET once "locked" NX EX 30
r SET once "again" NX EX 30

echo "--- hashes: an object with fields (a session)"
r HSET session:abc123 userId 42 name "Jane Doe" role admin
r HGET session:abc123 role
r EXPIRE session:abc123 1800
r HGETALL session:abc123

echo "--- lists: recent activity, newest first, keep 3"
for e in login viewed-lamp added-to-cart checkout; do redis-cli -n 5 LPUSH user:42:activity "$e" > /dev/null; done
r LTRIM user:42:activity 0 2
r LRANGE user:42:activity 0 -1
```

<Happened>
<Tr>
<En>

- **Strings**: `SET … EX 60` stored a value that **expires** in 60 seconds (`TTL` shows the time left). `INCR`/`INCRBY` turned a missing key into a counter **atomically**: a thousand requests incrementing at once never lose a count. `SET … NX` sets only if the key doesn't exist: the second attempt returned `(nil)`, which is the basis of simple locks and "do this once" flags.
- **Hashes** store an object's fields under one key, like a session; `EXPIRE` gives the whole session a lifetime, and `HGET` reads one field without loading the rest.
- **Lists** kept the newest activity first (`LPUSH`), and `LTRIM 0 2` capped it at the latest 3, a common "recent items" pattern that never grows without limit.
- **Sets** hold unique members; `SINTER` found users who viewed **both** products (2 and 42) in one command.
- **Sorted sets** keep members ordered by score: `ZINCRBY` added 300 to John's score, `ZREVRANGE … WITHSCORES` returned the top 3, and `ZREVRANK` said John is now 2nd (rank 1, counting from 0). Ranking stays fast even with millions of players.
- Keys use a **`type:id:field` naming convention** (`session:abc123`, `user:42:activity`), which keeps a shared Redis organized.

</En>
<Ur>

- **Strings**: `SET … EX 60` ne aisi value rakhi jo 60 second me **expire** hoti hai (`TTL` baqi waqt dikhata hai). `INCR`/`INCRBY` ne na mojood key ko **atomic tor par** counter bana diya: hazar requests ek saath barhayen to bhi koi ginti nahi khoti. `SET … NX` sirf tab set karta hai jab key na ho: doosri koshish ne `(nil)` lautaya, jo saade locks aur "ye ek dafa karo" nishanon ki bunyad hai.
- **Hashes** object ke fields ek key ke neeche rakhte hain, session ki tarah; `EXPIRE` poore session ko umar deta hai, aur `HGET` baqi load kiye baghair ek field parhta hai.
- **Lists** ne naya activity pehle rakha (`LPUSH`), aur `LTRIM 0 2` ne use aakhri 3 tak mehdood kiya, aam "haal ke items" pattern jo kabhi be-hadd nahi barhta.
- **Sets** unique members rakhte hain; `SINTER` ne ek command me un users ko dhoondha jinhon ne **dono** products dekhe (2 aur 42).
- **Sorted sets** members ko score se tarteeb me rakhte hain: `ZINCRBY` ne John ke score me 300 jore, `ZREVRANGE … WITHSCORES` ne top 3 lautaye, aur `ZREVRANK` ne bataya ke John ab doosre number par hai (rank 1, 0 se ginti). Lakhon khilariyon ke saath bhi ranking tez rehti hai.
- Keys **`type:id:field` naam ki riwayat** istemal karti hain (`session:abc123`, `user:42:activity`), jo mushtarka Redis ko munazzam rakhti hai.

</Ur>

<Step title="Cache-aside in Node.js, and memory limits">

<Tr>
<En>
A pretend database takes 300 ms per read and counts its calls. `getProduct` implements **cache-aside** with a 60-second TTL, and `updatePrice` writes to the database and, optionally, deletes the cached copy. Then we limit Redis to 3 MB and write 5,000 values of 1 KB, first with the `noeviction` policy and then with `allkeys-lru`, and restore the settings at the end.
</En>
<Ur>
Naqli database har read me 300 ms leta aur apni calls ginta hai. `getProduct` 60 second TTL ke saath **cache-aside** banata hai, aur `updatePrice` database me likhta aur, ikhtiyari tor par, cached copy mitata hai. Phir hum Redis ko 3 MB tak mehdood kar ke 1 KB ki 5,000 values likhte hain, pehle `noeviction` policy ke saath phir `allkeys-lru` ke saath, aur aakhir me settings wapas karte hain.
</Ur>
</Tr>

```bash
npm init -y > /dev/null && npm pkg set type=module && npm install ioredis@6.0.0 --silent
cat > cache.js <<'EOF'
import { Redis } from "ioredis";
const redis = new Redis({ db: 5 });

// A pretend slow database
const db = { calls: 0, products: { 1: { id: 1, name: "Desk Lamp", priceCents: 2999 } } };
const loadProduct = async (id) => { db.calls++; await new Promise((r) => setTimeout(r, 300)); return { ...db.products[id] }; };

// Cache-aside: look in Redis first; on a miss, load from the database and store with a TTL
async function getProduct(id) {
  const cached = await redis.get(`product:${id}`);
  if (cached) return JSON.parse(cached);
  const product = await loadProduct(id);
  await redis.set(`product:${id}`, JSON.stringify(product), "EX", 60);
  return product;
}
async function updatePrice(id, priceCents, { invalidate }) {
  db.products[id].priceCents = priceCents;                         // write to the database first
  if (invalidate) await redis.del(`product:${id}`);                // then drop the cached copy
}
const timed = async (label) => {
  const t = Date.now(); const p = await getProduct(1);
  console.log(`${label.padEnd(30)} price ${p.priceCents}  ${Date.now() - t > 200 ? "slow (database)" : "fast (cache)"}  db calls: ${db.calls}`);
};

await redis.del("product:1");
await timed("1st read");
await timed("2nd read");
await updatePrice(1, 3499, { invalidate: false });
await timed("after update, no invalidation");
await updatePrice(1, 3999, { invalidate: true });
await timed("after update + DEL");
console.log(`TTL left on the cached copy: ${(await redis.ttl("product:1")) > 55 ? "about 60 s" : "?"}`);

// When memory is full, Redis either refuses writes or evicts keys, depending on maxmemory-policy
async function fill(policy) {
  await redis.flushdb();
  await redis.config("SET", "maxmemory-policy", policy);
  await redis.config("SET", "maxmemory", "3mb");
  const before = Number((await redis.info("stats")).match(/evicted_keys:(\d+)/)[1]);
  let error = null;
  for (let i = 0; i < 5000 && !error; i++)
    await redis.set(`cache:${i}`, "x".repeat(1000)).catch((e) => (error = e.message.split(" ").slice(0, 4).join(" ")));
  const evicted = Number((await redis.info("stats")).match(/evicted_keys:(\d+)/)[1]) - before;
  console.log(`${policy.padEnd(12)} keys kept: ${(await redis.dbsize()) < 5000 ? "fewer than 5000" : 5000}, ` +
              `evicted: ${evicted > 0 ? "yes" : "no"}, error: ${error ?? "none"}`);
}
console.log("--- 5000 values of 1 KB into a Redis limited to 3 MB");
await fill("noeviction");
await fill("allkeys-lru");
await redis.config("SET", "maxmemory", "0");                     // back to unlimited for the rest of the course
await redis.config("SET", "maxmemory-policy", "noeviction");
await redis.flushdb();
redis.disconnect();
EOF
node cache.js
```

```text output

2nd read                       price 2999  fast (cache)  db calls: 1
after update, no invalidation  price 2999  fast (cache)  db calls: 1
after update + DEL             price 3999  slow (database)  db calls: 2

```

<Happened>
<Tr>
<En>

- The first read was a **miss**: slow (300 ms) and one database call. The second was a **hit**: fast, and the database call count stayed at 1.
- After changing the price to 3499 **without invalidating**, readers still got **2999** from the cache, and would for up to 60 seconds. That's **stale data**: customers see one price and are charged another.
- Updating and then **`DEL`-ing** the key made the next read miss, reload from the database and show **3999**. The rule: write to the database first, then delete the cache (not "update the cache"), so a failure in between leaves at worst a cache miss.
- The TTL is the **safety net**: even if an invalidation is forgotten, stale data disappears within 60 seconds. Choose TTLs by how stale each kind of data may be.
- With `maxmemory` 3 MB and **`noeviction`**, Redis started **refusing writes** with an OOM error once full. That's right for Redis holding data you can't lose (queues, sessions), but your app must handle the error.
- With **`allkeys-lru`**, Redis kept accepting writes by **evicting** the least recently used keys, so fewer than 5,000 remained. That's what you want for a pure cache: losing a cached value only costs a reload.

</En>
<Ur>

- Pehla read **miss** tha: sust (300 ms) aur ek database call. Doosra **hit** tha: tez, aur database calls ki ginti 1 rahi.
- **Invalidate kiye baghair** qeemat 3499 karne ke baad parhne walon ko cache se ab bhi **2999** mila, aur 60 second tak milta. Ye **stale data** hai: customers ek qeemat dekhte aur doosri ada karte hain.
- Update kar ke key **`DEL`** karne se agla read miss hua, database se dobara laya aur **3999** dikhaya. Qaida: pehle database me likho, phir cache mitao ("cache update karo" nahi), taa ke beech me nakami ho to zyada se zyada cache miss ho.
- TTL **hifazati jaal** hai: invalidation bhool bhi jaye to stale data 60 second me ghaib ho jata hai. Har qism ke data ke liye TTL is hisaab se chunein ke wo kitna purana ho sakta hai.
- `maxmemory` 3 MB aur **`noeviction`** ke saath, bharne par Redis ne OOM error se **writes rad karna** shuru kiya. Ye un cheezon ke liye sahi hai jo khoni nahi chahiyen (queues, sessions), magar app ko error sambhalna chahiye.
- **`allkeys-lru`** ke saath Redis ne sab se kam haal me istemal hui keys **nikal kar** writes qubool karna jari rakha, isliye 5,000 se kam bachin. Khalis cache ke liye yahi chahiye: cached value khone ki qeemat sirf dobara load hai.

</Ur>
</Tr>

## Common mistakes

<Compare>
<Bad title="Updating the cache instead of deleting it">

```text
await db.update(id, data);
await redis.set(`product:${id}`, JSON.stringify(merged));   // two concurrent updates can leave the older value in the cache
```

</Bad>
<Good title="Write the database, delete the cache, keep a TTL">

```text
await db.update(id, data);
await redis.del(`product:${id}`);          // next read reloads the truth
// every SET has EX so mistakes heal themselves
```

</Good>
</Compare>

<Compare>
<Bad title="KEYS in production">

```text
const keys = await redis.keys('product:*');   // scans every key and blocks Redis for everyone
await redis.del(...keys);
```

</Bad>
<Good title="SCAN in batches, or version the keys">

```text
for await (const batch of redis.scanStream({ match: 'product:*', count: 500 })) if (batch.length) await redis.del(...batch);
// or include a version in keys (product:v7:1) and bump the version to invalidate all at once
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Caching without TTLs**: one missed invalidation becomes permanent wrong data, and memory fills up.
- **Using Redis as the only copy of important data** with eviction enabled: evicted keys are gone.
- **Huge values and hot keys**: storing megabytes per key or sending all traffic to one key slows everyone; split data and spread load.
- **Caching per-user data under shared keys**: user A sees user B's data; include the user ID in the key.
- **No timeouts or fallbacks**: if Redis is down, a cache should degrade to the database, not take the site down.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **TTLs ke baghair caching**: ek chhooti invalidation mustaqil ghalat data ban jati hai, aur memory bhar jati hai.
- **Eviction on hote hue Redis ko ahem data ki wahid copy banana**: nikali gayi keys chali gayin.
- **Bari values aur garam keys**: har key me megabytes rakhna ya saara traffic ek key par bhejna sab ko sust karta hai; data baantein aur bojh phailayen.
- **Har user ka data mushtarka keys me cache karna**: user A user B ka data dekhta hai; key me user ID shamil karein.
- **Timeouts ya fallbacks nahi**: Redis band ho to cache ko database par aa jana chahiye, site gira deni nahi chahiye.

</Ur>
</Tr>

<DeepDive title="More about Redis">

**Persistence.** RDB snapshots and the AOF (append-only file) can save data to disk, so Redis can survive restarts; even so, treat it as a fast layer, not the system of record.

**Replication and failover.** Replicas copy the primary; Redis Sentinel or managed services handle failover; Redis Cluster shards keys across nodes.

**Pipelining and transactions.** Send many commands in one round trip (`pipeline()`); `MULTI/EXEC` runs a batch atomically; Lua scripts (`EVAL`) do read-modify-write atomically.

**Pub/Sub and Streams.** Publish/subscribe for broadcasting messages between servers; Streams (`XADD`, consumer groups) for durable event logs.

**Other structures.** Bitmaps and HyperLogLog (approximate unique counts with tiny memory), geospatial indexes (`GEOSEARCH`).

**Caching strategies.** Read-through, write-through and write-behind caches; stampede protection with locks or early refresh (see Caching in NestJS).

</DeepDive>

<DeepDive title="Real world: the cache that showed the wrong account">

A banking app cached the "account overview" API response in Redis to cope with morning traffic. The key was built from the URL: `cache:/api/account/overview`. The URL was the same for every user, because the user came from the session cookie.

For eleven minutes after a deploy, users opening the app saw **another customer's** balance and recent transactions: whoever loaded the page first after the cache expired filled the key for everyone. The bank had to disclose the incident to regulators.

The fixes:

1. Cache keys for personal data always include the user ID (`overview:user:<id>`), enforced by a helper that refuses to cache authenticated responses without one.
2. The shared HTTP-level cache was limited to public endpoints.
3. A test logs in as two users and checks each sees only their own data, with caching enabled.
4. Sensitive responses use short TTLs, and the cache is flushed on deploys.

</DeepDive>

<DeepDive title="Security lens">

- **Never expose Redis to the internet**: it's built for trusted networks; open Redis servers are hijacked to run malware within minutes. Bind to private interfaces and require a password or ACL user.
- **Use TLS** across untrusted networks (managed Redis provides it).
- **Separate data by key prefix and user**: never cache private data under shared keys.
- **Disable or rename dangerous commands** (`FLUSHALL`, `CONFIG`, `KEYS`) for application users with ACLs.
- **Treat cached data as sensitive** as the source: tokens, sessions and personal data in Redis need the same care as in the database.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is Redis and what is it used for?">
An in-memory key-value data store with data types such as strings, hashes, lists, sets and sorted sets. It's used for caching, sessions, rate limiting, distributed locks, queues, pub/sub, leaderboards and real-time counters, usually alongside a primary database.
</QA>

<QA q="Explain the cache-aside pattern.">
The application reads from the cache first; on a miss it loads from the database, stores the result in the cache with a TTL and returns it. On writes it updates the database and then deletes the cached entry so the next read reloads fresh data.
</QA>

<QA q="Why delete the cache entry on update instead of updating it?">
Updating the cache can race with other writes and leave older data in the cache, and it duplicates logic. Deleting is simpler and safe: the next read rebuilds the entry from the database, and the TTL covers any missed deletes.
</QA>

<QA q="What happens when Redis runs out of memory?">
It depends on maxmemory-policy: noeviction rejects writes with an error, while policies like allkeys-lru or volatile-ttl evict keys to make room. Caches typically use an LRU or LFU policy; data that must not be lost needs noeviction and enough memory.
</QA>

<QA q="How would you implement a leaderboard with Redis?">
With a sorted set: ZADD or ZINCRBY to set or increase a player's score, ZREVRANGE with WITHSCORES to get the top N, and ZREVRANK to get a player's position, all efficient even with millions of members.
</QA>

</DeepDive>
