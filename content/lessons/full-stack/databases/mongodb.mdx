<BigIdea>
<Tr>
<En>
**MongoDB** stores **documents**: JSON-like objects (stored as BSON) that can contain nested objects and arrays, grouped into **collections**. There are no tables to declare up front; an order document can carry its items inside it. You query with **filter documents** that mirror the data: `{ priceCents: { $lt: 5000 } }`, `{ "specs.watts": { $gt: 10 } }`, `{ tags: "desk" }` (matches if the array contains "desk"). You change documents with **update operators** that edit parts of them in place: `$set`, `$inc`, `$push`, and `$` to target the matching array element. Like any database, MongoDB needs **indexes**: without one, a query scans the whole collection (`COLLSCAN`); with one it walks the index (`IXSCAN`), and **unique indexes** enforce rules like "one product per SKU". For reports, the **aggregation pipeline** passes documents through stages, `$match` (filter), `$unwind` (one document per array element), `$group` (totals), `$lookup` (join another collection), `$project` (reshape), `$sort`, much like SQL's WHERE, JOIN, GROUP BY and ORDER BY. The key design question is **embed or reference**: embed what's read together and bounded in size; reference what's shared, large or changes on its own.
</En>
<Ur>
**MongoDB** **documents** rakhta hai: JSON jaise objects (BSON ki shakal me) jin me nested objects aur arrays ho sakte hain, **collections** me jama. Pehle se tables bayan nahi karne parte; order document apne items andar rakh sakta hai. Aap **filter documents** se poochhte hain jo data jaise dikhte hain: `{ priceCents: { $lt: 5000 } }`, `{ "specs.watts": { $gt: 10 } }`, `{ tags: "desk" }` (array me "desk" ho to mel). Documents **update operators** se badalte hain jo un ke hisse wahin badalte hain: `$set`, `$inc`, `$push`, aur mel khane wale array element ko nishana banane ke liye `$`. Har database ki tarah MongoDB ko **indexes** chahiye: index ke baghair query poori collection scan karti hai (`COLLSCAN`); index ke saath index par chalti hai (`IXSCAN`), aur **unique indexes** "har SKU ka ek product" jaise qawaid nafiz karte hain. Reports ke liye **aggregation pipeline** documents ko stages se guzarti hai, `$match` (filter), `$unwind` (har array element ka ek document), `$group` (totals), `$lookup` (doosri collection join), `$project` (nayi shakal), `$sort`, bilkul SQL ke WHERE, JOIN, GROUP BY aur ORDER BY ki tarah. Design ka bunyadi sawal hai **embed ya reference**: jo saath parha jaye aur size me mehdood ho use embed karein; jo mushtarka, bara ho ya khud badle use reference karein.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **filing cabinet of folders**.

- A **collection** is a drawer; a **document** is a folder, and each folder can hold sheets and smaller envelopes (nested objects and arrays). Folders in the same drawer don't need identical contents.
- A **query filter** is a description you hand the clerk: "folders where price is under $50 and the tag list includes desk".
- **Update operators** are instructions like "cross out the stock number and write two less" (`$inc`) or "add a 'sale' sticker" (`$push`), without rewriting the whole folder.
- An **index** is the alphabetical tab strip on the drawer; without it the clerk opens every folder.
- An **aggregation pipeline** is an assembly line: first keep only paid orders, then take every item out of its folder, then sort items into piles by product, then count each pile.

</En>
<Ur>

**Folders wali filing cabinet** ka sochein.

- **Collection** ek daraaz hai; **document** ek folder, aur har folder me kaghaz aur chhote lifafe ho sakte hain (nested objects aur arrays). Ek daraaz ke folders ke mawad ka ek jaisa hona zaroori nahi.
- **Query filter** clerk ko di gayi tafseel hai: "wo folders jin ki qeemat $50 se kam aur tags ki list me desk ho".
- **Update operators** hidayat hain jaise "stock number kaat kar do kam likho" (`$inc`) ya "'sale' sticker lagao" (`$push`), poora folder dobara likhe baghair.
- **Index** daraaz par alphabet ke tabs ki patti hai; is ke baghair clerk har folder kholta hai.
- **Aggregation pipeline** assembly line hai: pehle sirf paid orders rakho, phir har item folder se nikalo, phir items ko product ke hisaab se dheron me rakho, phir har dher gino.

</Ur>
</Tr>

<Step title="CRUD, query operators and indexes">

<Tr>
<En>
MongoDB 8 runs in a Docker container. Four products are inserted with nested `specs` objects and `tags` arrays (not every product has the same fields). We run several queries, change documents with update operators, upsert a new SKU, delete out-of-stock products, then add a unique index and compare `explain()` output for a query on 20,000 orders without and with an index.
</En>
<Ur>
MongoDB 8 Docker container me chalta hai. Chaar products nested `specs` objects aur `tags` arrays ke saath daale jate hain (har product ke fields ek jaise nahi). Hum kai queries chalate, update operators se documents badalte, naya SKU upsert karte, khatam stock wale products mitate hain, phir unique index jor kar 20,000 orders par ek query ka `explain()` index ke baghair aur saath milate hain.
</Ur>
</Tr>

```bash
docker rm -f mongo-demo > /dev/null 2>&1
docker run -d --name mongo-demo -p 27017:27017 mongo:8 > /dev/null
npm init -y > /dev/null && npm pkg set type=module && npm install mongodb@7.9.1 --silent
cat > crud.js <<'EOF'
import { MongoClient } from "mongodb";
const client = await new MongoClient("mongodb://localhost:27017").connect();
const db = client.db("shop");
await db.dropDatabase();
const products = db.collection("products");
const show = (label, x) => console.log(label.padEnd(34), JSON.stringify(x));

// CREATE: documents can nest objects and arrays
await products.insertMany([
  { sku: "LAMP-1", name: "Desk Lamp",   priceCents: 2999, stock: 10, tags: ["lighting", "desk"], specs: { watts: 9,  color: "black" } },
  { sku: "LAMP-2", name: "Floor Lamp",  priceCents: 8900, stock: 0,  tags: ["lighting"],         specs: { watts: 15, color: "white" } },
  { sku: "ARM-1",  name: "Monitor Arm", priceCents: 5400, stock: 4,  tags: ["desk"],             specs: { maxKg: 8 } },
  { sku: "TRAY-1", name: "Cable Tray",  priceCents: 1500, stock: 25, tags: ["desk", "cables"] },
]);

// READ: filters are documents too
const p = { _id: 0, sku: 1 };
show("price < $50:",               await products.find({ priceCents: { $lt: 5000 } }, { projection: p }).toArray());
show("in stock AND tagged desk:",  await products.find({ stock: { $gt: 0 }, tags: "desk" }, { projection: p }).toArray());
show("nested field specs.watts>10:", await products.find({ "specs.watts": { $gt: 10 } }, { projection: p }).toArray());
show("has field specs.maxKg:",     await products.find({ "specs.maxKg": { $exists: true } }, { projection: p }).toArray());
show("two cheapest:",              await products.find({}, { projection: { _id: 0, sku: 1, priceCents: 1 } }).sort({ priceCents: 1 }).limit(2).toArray());

// UPDATE: operators change parts of a document
await products.updateOne({ sku: "LAMP-1" }, { $inc: { stock: -2 }, $push: { tags: "sale" }, $set: { "specs.color": "brass" } });
show("after $inc/$push/$set:",     await products.findOne({ sku: "LAMP-1" }, { projection: { _id: 0, stock: 1, tags: 1, specs: 1 } }));
const r = await products.updateOne({ sku: "HOOK-1" }, { $set: { name: "Headphone Hook", priceCents: 999 }, $setOnInsert: { stock: 0 } }, { upsert: true });
show("upsert of a new SKU:",       { matched: r.matchedCount, inserted: r.upsertedCount });

// DELETE
show("deleteMany out of stock:",   { deleted: (await products.deleteMany({ stock: 0 })).deletedCount });

// INDEXES: unique SKU, and what a query does with and without an index
await products.createIndex({ sku: 1 }, { unique: true });
try { await products.insertOne({ sku: "ARM-1", name: "Duplicate" }); } catch (e) { show("duplicate sku:", e.code === 11000 ? "rejected (E11000 duplicate key)" : e.message); }

const many = db.collection("orders");
await many.insertMany(Array.from({ length: 20000 }, (_, i) => ({ customerId: i % 2000, totalCents: (i * 37) % 9000 + 100 })));
const plan = async () => {
  const e = await many.find({ customerId: 42 }).explain("executionStats");
  const stage = (s) => s.inputStage ? `${s.stage} <- ${stage(s.inputStage)}` : s.stage;
  return `${stage(e.queryPlanner.winningPlan)}, examined ${e.executionStats.totalDocsExamined} docs for ${e.executionStats.nReturned} results`;
};
show("customerId 42, no index:", await plan());
await many.createIndex({ customerId: 1 });
show("customerId 42, with index:", await plan());
await client.close();
EOF
until docker exec mongo-demo mongosh --quiet --eval 'db.runCommand({ ping: 1 }).ok' > /dev/null 2>&1; do sleep 0.5; done
node crud.js
```

<Happened>
<Tr>
<En>

- Filters are documents: `{ priceCents: { $lt: 5000 } }` is "price below 5000". Several fields in one filter are combined with AND. `tags: "desk"` matched documents whose **array contains** "desk", with no special operator needed.
- Dotted paths reach **into nested objects** (`"specs.watts"`), and `$exists` found the only product that has a `maxKg` spec: documents in one collection can have different shapes.
- One `updateOne` did three things atomically: `$inc` lowered the stock by 2, `$push` added a tag and `$set` changed a nested field, without sending the whole document.
- The upsert found no `HOOK-1`, so it **inserted** one (`$setOnInsert` sets fields only when inserting). `deleteMany({ stock: 0 })` then removed both zero-stock products: the floor lamp and the new hook.
- The **unique index** on `sku` rejected a duplicate with error code **11000**. Without it, nothing stops two products from sharing a SKU.
- Without an index, finding customer 42's orders **examined all 20,000 documents** (`COLLSCAN`) to return 10. After `createIndex({ customerId: 1 })` it examined exactly **10** (`IXSCAN`, then `FETCH` to load the documents). Index every field you filter or sort on frequently.

</En>
<Ur>

- Filters documents hain: `{ priceCents: { $lt: 5000 } }` ka matlab "qeemat 5000 se kam". Ek filter ke kai fields AND se jurte hain. `tags: "desk"` ne un documents se mel khaya jin ki **array me** "desk" hai, kisi khaas operator ke baghair.
- Dot wale raaste **nested objects ke andar** pahunchte hain (`"specs.watts"`), aur `$exists` ne wahid product dhoondha jis ka `maxKg` spec hai: ek collection ke documents ki shaklen mukhtalif ho sakti hain.
- Ek `updateOne` ne atomic tor par teen kaam kiye: `$inc` ne stock 2 kam kiya, `$push` ne tag joda aur `$set` ne nested field badla, poora document bheje baghair.
- Upsert ko `HOOK-1` nahi mila, isliye us ne naya **daala** (`$setOnInsert` sirf daalte waqt fields set karta hai). Phir `deleteMany({ stock: 0 })` ne sifar stock wale dono products hataye: floor lamp aur naya hook.
- `sku` par **unique index** ne dohraav ko error code **11000** ke saath rad kiya. Is ke baghair do products ka ek SKU hone se koi nahi rokta.
- Index ke baghair customer 42 ke orders dhoondhne ne 10 lautane ke liye **saare 20,000 documents jaanche** (`COLLSCAN`). `createIndex({ customerId: 1 })` ke baad bilkul **10** jaanche (`IXSCAN`, phir documents laane ke liye `FETCH`). Jin fields par aksar filter ya sort karte hain unhen index karein.

</Ur>

<Step title="Aggregation pipelines and embedded arrays">

<Tr>
<En>
Three customers and four orders. Each order **embeds** its items and **references** its customer by `_id`. We compute units and revenue per product from paid orders, then revenue per country by joining customers with `$lookup`, and finally increase one item's quantity inside an order's array.
</En>
<Ur>
Teen customers aur chaar orders. Har order apne items **embed** karta hai aur apne customer ko `_id` se **reference** karta hai. Hum paid orders se har product ki units aur revenue nikalte hain, phir `$lookup` se customers join kar ke har mulk ki revenue, aur aakhir me order ki array ke andar ek item ki miqdar barhate hain.
</Ur>
</Tr>

```bash
cat > agg.js <<'EOF'
import { MongoClient } from "mongodb";
const client = await new MongoClient("mongodb://localhost:27017").connect();
const db = client.db("shop");
await db.collection("customers").deleteMany({});
await db.collection("sales").deleteMany({});
await db.collection("customers").insertMany([
  { _id: "c1", name: "Jane Doe", country: "US" }, { _id: "c2", name: "John Smith", country: "UK" },
  { _id: "c3", name: "Ana Lee",  country: "US" },
]);
// Each order EMBEDS its items, and REFERENCES the customer by id
await db.collection("sales").insertMany([
  { customerId: "c1", status: "paid",     items: [{ sku: "LAMP-1", qty: 2, priceCents: 2999 }, { sku: "ARM-1", qty: 1, priceCents: 5400 }] },
  { customerId: "c2", status: "paid",     items: [{ sku: "LAMP-1", qty: 1, priceCents: 2999 }] },
  { customerId: "c1", status: "refunded", items: [{ sku: "TRAY-1", qty: 3, priceCents: 1500 }] },
  { customerId: "c3", status: "paid",     items: [{ sku: "TRAY-1", qty: 4, priceCents: 1500 }, { sku: "LAMP-1", qty: 1, priceCents: 2999 }] },
]);
const sales = db.collection("sales");

// A pipeline = stages applied in order, like SQL's WHERE → JOIN → GROUP BY → ORDER BY
console.log("--- units and revenue per product (paid orders only)");
for (const row of await sales.aggregate([
  { $match: { status: "paid" } },                                  // WHERE
  { $unwind: "$items" },                                           // one document per item
  { $group: { _id: "$items.sku",                                   // GROUP BY sku
              units: { $sum: "$items.qty" },
              revenueCents: { $sum: { $multiply: ["$items.qty", "$items.priceCents"] } } } },
  { $sort: { revenueCents: -1 } },                                 // ORDER BY
]).toArray()) console.log(JSON.stringify(row));

console.log("--- revenue per country, joining customers with $lookup");
for (const row of await sales.aggregate([
  { $match: { status: "paid" } },
  { $lookup: { from: "customers", localField: "customerId", foreignField: "_id", as: "customer" } },   // LEFT JOIN
  { $unwind: "$customer" },
  { $unwind: "$items" },
  { $group: { _id: "$customer.country", orders: { $addToSet: "$_id" },
              revenueCents: { $sum: { $multiply: ["$items.qty", "$items.priceCents"] } } } },
  { $project: { _id: 0, country: "$_id", orders: { $size: "$orders" }, revenueCents: 1 } },
  { $sort: { country: 1 } },
]).toArray()) console.log(JSON.stringify(row));

console.log("--- update one item inside an array with the positional $ operator");
await sales.updateOne({ customerId: "c2", "items.sku": "LAMP-1" }, { $inc: { "items.$.qty": 1 } });
console.log(JSON.stringify((await sales.findOne({ customerId: "c2" }, { projection: { _id: 0, items: 1 } })).items));
await client.close();
EOF
node agg.js
```

<Happened>
<Tr>
<En>

- The first pipeline read like SQL in stages: `$match` kept paid orders (WHERE), `$unwind` turned each order into **one document per item**, `$group` summed units and `qty × price` per SKU (GROUP BY), and `$sort` ordered by revenue. The refunded tray order was excluded, so TRAY-1 shows 4 units, not 7.
- `$lookup` joined each order to its customer document (a left join; the result is an array, so we `$unwind` it). Grouping by `customer.country` gave US revenue from Jane's and Ana's orders. `$addToSet` collected distinct order ids so `$size` could count **orders** even after unwinding items.
- `$project` reshaped the output (renamed `_id` to `country`, computed the order count). Put `$match` as early as possible so later stages process fewer documents, and index the fields `$match` and `$lookup` use.
- The positional **`$`** in `"items.$.qty"` updated **only the array element that matched** `"items.sku": "LAMP-1"`, without rewriting the rest of the order.
- Embedding items made "show an order" one read; referencing customers means a name change happens in one place. Use `$lookup` for reports, not for every page view: if you join on every request, the data probably belongs together or in a relational database.

</En>
<Ur>

- Pehli pipeline SQL ki tarah stages me parhi gayi: `$match` ne paid orders rakhe (WHERE), `$unwind` ne har order ko **har item ka ek document** banaya, `$group` ne har SKU ki units aur `qty × price` joda (GROUP BY), aur `$sort` ne revenue se tarteeb di. Refunded tray order nikal gaya, isliye TRAY-1 7 nahi 4 units dikhata hai.
- `$lookup` ne har order ko us ke customer document se joda (left join; nateeja array hai, isliye hum `$unwind` karte hain). `customer.country` se group karne par US ki revenue Jane aur Ana ke orders se aayi. `$addToSet` ne alag order ids jama kin taa ke items unwind hone ke baad bhi `$size` **orders** gin sake.
- `$project` ne output ki shakal badli (`_id` ka naam `country` kiya, orders ki ginti nikali). `$match` jitna pehle ho sake rakhein taa ke baad ke stages kam documents sambhalen, aur jin fields ko `$match` aur `$lookup` istemal karte hain unhen index karein.
- `"items.$.qty"` me positional **`$`** ne **sirf wo array element** update kiya jo `"items.sku": "LAMP-1"` se mila, baqi order dobara likhe baghair.
- Items embed karne se "order dikhao" ek read bana; customers ko reference karne ka matlab naam ki tabdeeli ek jagah hoti hai. `$lookup` reports ke liye lein, har page view ke liye nahi: agar har request par join karte hain to data shayad saath hona chahiye ya relational database me.

</Ur>
</Tr>
</Happened>

</Step>

## Common mistakes

<Compare>
<Bad title="Read, change in JavaScript, write the whole document back">

```text
const p = await products.findOne({ sku });
p.stock -= 1;
await products.replaceOne({ sku }, p);      // two requests at once → one decrement lost
```

</Bad>
<Good title="Atomic update operator with a condition">

```text
const r = await products.updateOne({ sku, stock: { $gte: 1 } }, { $inc: { stock: -1 } });
if (r.modifiedCount === 0) throw new Error('Out of stock');
```

</Good>
</Compare>

<Compare>
<Bad title="Passing request input straight into a filter">

```text
// POST /login { "email": "jane@example.com", "password": { "$ne": "" } }
users.findOne({ email: req.body.email, password: req.body.password });   // operator injection: matches any password
```

</Bad>
<Good title="Validate types before querying">

```text
const { email, password } = LoginSchema.parse(req.body);   // both must be strings
const user = await users.findOne({ email });
if (!user || !(await bcrypt.compare(password, user.passwordHash))) throw unauthorized();
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Unbounded arrays** (all comments inside a post): documents are capped at 16 MB and big arrays make every update slower; use a separate collection.
- **No indexes**: MongoDB scans the whole collection just like SQL without indexes; check `explain()` for `COLLSCAN`.
- **Assuming a schema exists**: typos create new fields silently; use `$jsonSchema` validation and typed models (TypeScript, Zod, or Mongoose schemas).
- **Joining with `$lookup` on every request**: a sign your data model fights your access pattern.
- **Forgetting `_id` in projections**: it's returned unless you exclude it with `_id: 0`.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Be-hadd arrays** (post ke andar saare comments): documents ki hadd 16 MB hai aur bari arrays har update sust karti hain; alag collection lein.
- **Indexes nahi**: MongoDB bina indexes ke SQL ki tarah poori collection scan karta hai; `explain()` me `COLLSCAN` dekhein.
- **Schema farz karna**: typos khamoshi se naye fields banate hain; `$jsonSchema` validation aur typed models (TypeScript, Zod, ya Mongoose schemas) lein.
- **Har request par `$lookup` se join**: is ka ishara ke aap ka data model aap ke access pattern se lar raha hai.
- **Projections me `_id` bhoolna**: ye lautaya jata hai jab tak `_id: 0` se nikala na jaye.

</Ur>
</Tr>

Write an aggregation over `sales` that returns, for paid orders, the top 2 customers by total spent, with their name and number of orders.

<Tr>
<En>

```text
sales.aggregate([
  { $match: { status: 'paid' } },
  { $unwind: '$items' },
  { $group: { _id: '$customerId', orders: { $addToSet: '$_id' },
              spentCents: { $sum: { $multiply: ['$items.qty', '$items.priceCents'] } } } },

  { $project: { _id: 0, name: { $first: '$customer.name' }, orders: { $size: '$orders' }, spentCents: 1 } },
])
```

## Remember

<Takeaways>
<Tr>
<En>

- Documents in collections; filters, projections and updates are written as documents.
- Use update operators (`$set`, `$inc`, `$push`, positional `$`) for atomic partial updates; upsert with `{ upsert: true }`.

<DeepDive title="More about MongoDB">

**Transactions.** Single-document operations are always atomic; multi-document ACID transactions (`session.withTransaction`) need a replica set (Atlas and production deployments are replica sets; a lone Docker container isn't).

**Replica sets and read/write concerns.** A primary takes writes, secondaries copy them; `writeConcern: majority` waits until most members have the write.

**Sharding.** Collections are split across servers by a shard key; a good key spreads writes evenly and matches common queries.

**Compound indexes and ESR.** Order index fields as Equality, Sort, Range for best results, similar to composite indexes in SQL.

**Mongoose.** A popular ODM adding schemas, validation, middleware and `populate()` on top of the driver.

**Change streams.** Subscribe to inserts and updates in real time, useful for syncing to search engines or caches.

</DeepDive>

<DeepDive title="Real world: the post that hit 16 MB">

A community app stored each discussion as one document with an embedded `comments` array. It made the discussion page a single query and worked well for a year.

Then a viral thread passed 40,000 comments. Each new comment rewrote a document several megabytes in size; writes slowed to seconds, memory use spiked, and finally inserts failed with "document too large" at the 16 MB limit. The page also loaded every comment at once.

The fixes:

1. Comments moved to their own collection `{ threadId, authorId, body, createdAt }` with an index on `{ threadId: 1, createdAt: 1 }`.
2. The thread document kept only `commentCount` and the latest 3 comments as a preview, updated with `$inc` and `$push` with `$slice: -3`.
3. The page paginated comments with a cursor on `createdAt`.
4. A schema review rule: "arrays that can grow without limit don't get embedded".

</DeepDive>

<DeepDive title="Security lens">

- **Operator injection**: never pass `req.body` fields into filters without checking they're plain strings or numbers; `{ "$ne": "" }` can bypass checks.
- **Authentication and network**: enable auth, create users with least privilege, and never expose port 27017 to the internet (thousands of open MongoDB servers have been wiped and ransomed).
- **`$where` and server-side JavaScript**: avoid; they can run attacker-controlled code.
- **Validate documents** with `$jsonSchema` so bad writes are rejected even if app code has a bug.
- **Encrypt sensitive fields** (MongoDB supports client-side field-level encryption) and keep backups protected.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="How does MongoDB differ from a relational database?">
It stores flexible JSON-like documents in collections instead of rows in fixed tables, encourages embedding related data, queries with filter documents and aggregation pipelines instead of SQL, and scales horizontally with sharding; schema rules and joins exist but are optional or limited compared with relational databases.
</QA>

<QA q="When do you embed and when do you reference?">
Embed data that's read with its parent, owned by it and bounded in size, such as order items or addresses. Reference data that's shared, large, unbounded or updated independently, such as customers, products or comments.
</QA>

<QA q="What is the aggregation pipeline?">
A sequence of stages that transform documents, such as $match to filter, $unwind to flatten arrays, $group to aggregate, $lookup to join, $project to reshape and $sort and $limit, used for reports and complex queries.
</QA>

<QA q="How do you make MongoDB queries fast?">
Create indexes matching filters and sorts, including compound indexes ordered by equality, sort and range fields, check explain() for COLLSCAN versus IXSCAN, project only needed fields, and put $match early in pipelines.
</QA>

<QA q="Does MongoDB support transactions?">
Single-document operations are atomic. Multi-document ACID transactions are supported on replica sets and sharded clusters, but well-designed document models need them less often.
</QA>
