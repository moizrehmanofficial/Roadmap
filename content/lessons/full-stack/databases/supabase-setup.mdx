<BigIdea>
<Tr>
<En>
**Supabase** is a service that gives every project a real **PostgreSQL database** plus the pieces around it that apps need: an **automatic API** for your tables, **user sign-up and login** (Auth), **file storage** and **realtime** updates. You create tables with the SQL you already know, and then your JavaScript talks to them with the **`supabase-js`** client: `supabase.from("todos").select()` is the same as `SELECT * FROM todos`. Because the browser talks to the database through that API, security can't live in your front-end code. Instead, Supabase uses PostgreSQL's **Row Level Security (RLS)**: rules written in SQL, checked by the database on **every row of every request**, such as "a user can only see their own todos". Get RLS right and Supabase is a fast, safe way to build a full app; forget it and anyone with your public key can read your whole table.
</En>
<Ur>
**Supabase** aisi service hai jo har project ko asli **PostgreSQL database** deti hai, aur saath wo hisse jo apps ko chahiyen: aap ki tables ke liye **khud ba khud bani API**, **user sign-up aur login** (Auth), **files ka zakheera** aur **realtime** updates. Aap tables usi SQL se banate hain jo pehle se jaante hain, aur phir aap ki JavaScript **`supabase-js`** client se un se baat karti hai: `supabase.from("todos").select()` wahi hai jo `SELECT * FROM todos`. Chunke browser database se us API ke zariye baat karta hai, hifazat aap ke front-end code me nahi reh sakti. Is ke bajaye Supabase PostgreSQL ki **Row Level Security (RLS)** istemal karta hai: SQL me likhe qawaid, jinhe database **har request ki har row** par check karta hai, jaise "user sirf apne todos dekh sakta hai". RLS sahi ho to Supabase poori app banane ka tez aur mehfooz tareeqa hai; bhool jayen to aap ki public key rakhne wala koi bhi aap ki poori table parh sakta hai.
</Ur>
</Tr>

## Picture it

<Tr>
<En>

Think of a **bank with a public counter**.

- The **vault** is the PostgreSQL database.
- The **counter window** is the automatic API: anyone can walk up to it. Your **publishable key** is like the bank's address: it's printed on every leaflet (your website), so it's not a secret.
- **Row Level Security** is the **clerk behind the window** who checks your ID on every single request: "You're Sara, so here are **Sara's** statements, and nobody else's." The clerk doesn't care what you ask for; they only hand over what the rules allow.
- The **secret (service role) key** is the **manager's master key**: it skips the clerk entirely. It must never leave the back office (your server).

Without RLS, the counter has **no clerk**, and anyone who knows the address can ask for every customer's statements.

</En>
<Ur>

Ek **bank ka public counter** sochein.

- **Tijori** PostgreSQL database hai.
- **Counter ki khirki** khud ba khud bani API hai: koi bhi us tak ja sakta hai. Aap ki **publishable key** bank ke pate jaisi hai: ye har parche (aap ki website) par chhapi hoti hai, isliye raaz nahi.
- **Row Level Security** khirki ke **peechhe baitha clerk** hai jo har ek request par aap ki pehchaan check karta hai: "Aap Sara hain, isliye ye rahe **Sara** ke statements, kisi aur ke nahi." Clerk ko is se gharz nahi ke aap kya maangte hain; wo sirf wahi deta hai jis ki qawaid ijazat dein.
- **Secret (service role) key** **manager ki master chabi** hai: ye clerk ko bilkul chhor deti hai. Ise kabhi back office (aap ke server) se bahar nahi jana chahiye.

RLS ke baghair counter par **koi clerk nahi**, aur pata jaanne wala koi bhi har customer ke statements maang sakta hai.

</Ur>
</Tr>

<Step title="Create a project and find your keys">

<Tr>
<En>

1. Sign in at **supabase.com** and click **New project**. Choose a name, a strong database password (save it in a password manager) and the region closest to your users.
2. Wait a minute while the database is created.
3. Open **Project Settings → API** (in newer dashboards, **API Keys**). Copy two things:
   - the **Project URL**, like `https://abcdefgh.supabase.co`,
   - the **publishable key** (called the **anon** key in older projects).
4. You'll also see a **secret** key (older name: **service_role**). Don't copy it into front-end code, ever.

</En>
<Ur>

1. **supabase.com** par sign in karein aur **New project** click karein. Naam, mazboot database password (password manager me mehfooz karein) aur apne users ke sab se qareeb region chunein.
2. Database bante waqt ek minute intezar karein.
3. **Project Settings → API** kholein (naye dashboards me **API Keys**). Do cheezen copy karein:
   - **Project URL**, jaise `https://abcdefgh.supabase.co`,
   - **publishable key** (purane projects me **anon** key kehlati hai).
4. Aap ko **secret** key bhi nazar aayegi (purana naam: **service_role**). Ise front-end code me kabhi copy na karein.

</Ur>
</Tr>

```text
# .env.local  (in your Next.js project; never commit this file)
NEXT_PUBLIC_SUPABASE_URL=https://abcdefgh.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxxxxxxxxxxxxxxx

# Server-only. No NEXT_PUBLIC_ prefix, so it never reaches the browser.
SUPABASE_SECRET_KEY=sb_secret_xxxxxxxxxxxxxxxx
```

<Happened>
<Tr>
<En>

- In Next.js, variables starting with **`NEXT_PUBLIC_`** are copied into the browser's JavaScript. That's fine for the URL and the publishable key: they're meant to be public, and RLS protects the data.
- The secret key has no prefix, so only server code can read it.
- `.env.local` is listed in `.gitignore` by Next.js, so it isn't pushed to GitHub. On Vercel you add the same variables in the project settings.

</En>
<Ur>

- Next.js me **`NEXT_PUBLIC_`** se shuru hone wale variables browser ki JavaScript me copy ho jate hain. URL aur publishable key ke liye ye theek hai: ye public hone ke liye hi hain, aur data ki hifazat RLS karta hai.
- Secret key par koi prefix nahi, isliye sirf server code use parh sakta hai.
- Next.js `.env.local` ko `.gitignore` me rakhta hai, isliye ye GitHub par push nahi hoti. Vercel par aap yahi variables project settings me jorte hain.

</Ur>
</Tr>
</Happened>

<Step title="What Supabase sets up for you">

<Tr>
<En>
Every Supabase project already has an `auth.users` table, two roles (`anon` for logged-out requests, `authenticated` for logged-in ones) and a function `auth.uid()` that returns the current user's id. To follow along in plain PostgreSQL, we created the same pieces first. **In Supabase you skip this block.**
</En>
<Ur>
Har Supabase project me pehle se `auth.users` table, do roles (logout requests ke liye `anon`, login wali ke liye `authenticated`) aur `auth.uid()` function hota hai jo maujooda user ki id wapas karta hai. Saade PostgreSQL me saath chalne ke liye humne pehle yahi hisse banaye. **Supabase me ye block chhor dein.**
</Ur>
</Tr>

```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'anon') THEN CREATE ROLE anon NOLOGIN; END IF;
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'authenticated') THEN CREATE ROLE authenticated NOLOGIN; END IF;
END $$;

CREATE SCHEMA auth;
CREATE TABLE auth.users (id uuid PRIMARY KEY, email text NOT NULL);
CREATE FUNCTION auth.uid() RETURNS uuid LANGUAGE sql STABLE AS $$
  SELECT nullif(current_setting('request.jwt.claim.sub', true), '')::uuid
$$;
GRANT USAGE ON SCHEMA auth TO anon, authenticated;

INSERT INTO auth.users VALUES
  ('11111111-1111-1111-1111-111111111111', 'sara@example.com'),
  ('22222222-2222-2222-2222-222222222222', 'alex@example.com');
```

```text output
DO
CREATE SCHEMA
CREATE TABLE
CREATE FUNCTION
GRANT
INSERT 0 2
```

<Happened>
<Tr>
<En>

- Two users now exist: Sara and Alex, each with a **UUID** as their id. In Supabase, rows appear in `auth.users` when people sign up.
- `auth.uid()` reads the user id from the request. In Supabase, it comes from the logged-in user's **JWT** (the signed login token the client sends). Here we'll set it by hand to pretend to be Sara or Alex.

</En>
<Ur>

- Ab do users maujood hain: Sara aur Alex, har ek ki id ek **UUID** hai. Supabase me log sign up karte hain to `auth.users` me rows aati hain.
- `auth.uid()` request se user ki id parhta hai. Supabase me ye login user ke **JWT** (client ka bheja hua signed login token) se aati hai. Yahan hum Sara ya Alex hone ka bahana karne ke liye ise haath se set karenge.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Create a table in the SQL editor">

<Tr>
<En>
A to-do table where every row belongs to a user. `user_id` defaults to `auth.uid()`, so when a logged-in user inserts a todo, it's automatically theirs.
</En>
<Ur>
Aisi to-do table jis ki har row kisi user ki ho. `user_id` ka default `auth.uid()` hai, isliye jab login user todo daale to wo khud ba khud usi ka ho jata hai.
</Ur>
</Tr>

```sql
CREATE TABLE public.todos (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     uuid NOT NULL DEFAULT auth.uid() REFERENCES auth.users (id) ON DELETE CASCADE,
  task        text NOT NULL CHECK (char_length(task) BETWEEN 1 AND 200),
  is_done     boolean NOT NULL DEFAULT false,
  inserted_at timestamptz NOT NULL DEFAULT now()
);

GRANT SELECT, INSERT, UPDATE, DELETE ON public.todos TO anon, authenticated;

INSERT INTO public.todos (user_id, task) VALUES
  ('11111111-1111-1111-1111-111111111111', 'Buy milk'),
  ('11111111-1111-1111-1111-111111111111', 'Book dentist'),
  ('22222222-2222-2222-2222-222222222222', 'Renew passport');
```

```text output
CREATE TABLE
GRANT
INSERT 0 3
```

<Happened>
<Tr>
<En>

- `GENERATED ALWAYS AS IDENTITY` is the modern way to make an auto-numbered id.
- `REFERENCES auth.users (id) ON DELETE CASCADE`: every todo must belong to a real user, and if a user deletes their account, their todos go too.
- The `CHECK` keeps tasks between 1 and 200 characters, whatever the front end does.
- The `GRANT` gives the API roles permission to use the table. **Supabase grants this automatically** for tables in `public`, which is exactly why RLS matters: the API can reach the table as soon as it exists.
- Sara has two todos; Alex has one.

</En>
<Ur>

- `GENERATED ALWAYS AS IDENTITY` khud number lagne wali id banane ka jadeed tareeqa hai.
- `REFERENCES auth.users (id) ON DELETE CASCADE`: har todo kisi asli user ka hona chahiye, aur agar user apna account mita de to us ke todos bhi chale jate hain.
- `CHECK` tasks ko 1 se 200 characters ke darmiyan rakhta hai, front end kuch bhi kare.
- `GRANT` API roles ko table istemal karne ki ijazat deta hai. `public` ki tables ke liye **Supabase ye khud deta hai**, isi liye RLS ahem hai: table bante hi API us tak pohanch sakti hai.
- Sara ke do todos hain; Alex ka ek.

</Ur>
</Tr>
</Happened>

<Step title="The danger: no RLS means everyone can see everything">

<Tr>
<En>
Let's act as a **logged-out visitor**, the `anon` role, which is what anyone using your publishable key from a browser is. RLS isn't enabled yet.
</En>
<Ur>
Aaiye **logout visitor** ban kar dekhein, yaani `anon` role, jo browser se aap ki publishable key istemal karne wala har shakhs hota hai. RLS abhi chalu nahi.
</Ur>
</Tr>

```sql
SET ROLE anon;
SELECT task, user_id FROM public.todos;
DELETE FROM public.todos WHERE task = 'Renew passport';
RESET ROLE;
INSERT INTO public.todos (user_id, task) VALUES ('22222222-2222-2222-2222-222222222222', 'Renew passport');
```

```text output

----------------+--------------------------------------
 Buy milk       | 11111111-1111-1111-1111-111111111111
 Book dentist   | 11111111-1111-1111-1111-111111111111
 Renew passport | 22222222-2222-2222-2222-222222222222
(3 rows)

DELETE 1
RESET
INSERT 0 1
```

<Happened>
<Tr>
<En>

- An anonymous visitor read **every user's** todos, including Alex's.
- Worse, they **deleted** Alex's todo (`DELETE 1`). (We put it back afterwards as the admin, so the rest of the lesson has the same data.)
- In a real app the same thing happens through the API: anyone can open DevTools, copy your project URL and publishable key from your site, and run `supabase.from("todos").select()` or `.delete()`.
- That's why Supabase shows a warning on every table without RLS. **Never ship a table without it.**

</En>
<Ur>

- Gumnaam visitor ne **har user** ke todos parh liye, Alex ke samet.
- Is se bura, us ne Alex ka todo **mita** diya (`DELETE 1`). (Humne baad me admin ki hesiyat se use wapas daal diya, taa ke baqi lesson me wahi data rahe.)
- Asli app me API ke zariye bilkul yahi hota hai: koi bhi DevTools khol kar aap ki site se project URL aur publishable key copy kar ke `supabase.from("todos").select()` ya `.delete()` chala sakta hai.
- Isi liye Supabase RLS ke baghair har table par warning dikhata hai. **Kabhi baghair RLS ke table ship na karein.**

</Ur>
</Tr>
</Happened>

<Step title="Turn on Row Level Security">

<Tr>
<En>
Enabling RLS flips the default from "allow everything" to **"allow nothing"**. Until you add policies, the API can't see or change any rows.
</En>
<Ur>
RLS chalu karna default ko "sab ki ijazat" se **"kisi cheez ki ijazat nahi"** par palat deta hai. Jab tak aap policies na jorein, API koi row na dekh sakti hai na badal sakti hai.
</Ur>
</Tr>

```sql
ALTER TABLE public.todos ENABLE ROW LEVEL SECURITY;

SET ROLE anon;
SELECT count(*) AS visible_to_anon FROM public.todos;
DELETE FROM public.todos;
RESET ROLE;

SELECT count(*) AS really_in_table FROM public.todos;
```

```text output
ALTER TABLE
SET
 visible_to_anon
-----------------
               0
(1 row)

DELETE 0
RESET
 really_in_table
-----------------
               3
(1 row)
```

<Happened>
<Tr>
<En>

- The anonymous visitor now sees **0** rows, and their `DELETE` affected **0** rows. No error, just nothing allowed.
- The table still has all 3 rows: the admin (the table owner, or Supabase's secret key) isn't limited by RLS.
- Next we add **policies** that open up exactly what each user should get.

</En>
<Ur>

- Gumnaam visitor ko ab **0** rows nazar aati hain, aur us ke `DELETE` ne **0** rows par asar kiya. Koi error nahi, bas kisi cheez ki ijazat nahi.
- Table me ab bhi teeno rows hain: admin (table ka maalik, ya Supabase ki secret key) RLS se mehdood nahi.
- Ab hum **policies** jorte hain jo har user ke liye bilkul wahi kholti hain jo use milna chahiye.

</Ur>
</Tr>
</Happened>

<Step title="Policies: each user owns their rows">

<Tr>
<En>
A policy says **who** (`TO authenticated`), **what** (`FOR SELECT`, `INSERT`, `UPDATE`, `DELETE`) and **which rows** (`USING` for existing rows, `WITH CHECK` for new or changed rows).
</En>
<Ur>
Policy batati hai **kaun** (`TO authenticated`), **kya** (`FOR SELECT`, `INSERT`, `UPDATE`, `DELETE`) aur **kaun si rows** (maujood rows ke liye `USING`, nayi ya badli rows ke liye `WITH CHECK`).
</Ur>
</Tr>

```sql
CREATE POLICY "Users read their own todos" ON public.todos
  FOR SELECT TO authenticated USING (user_id = auth.uid());

CREATE POLICY "Users add their own todos" ON public.todos
  FOR INSERT TO authenticated WITH CHECK (user_id = auth.uid());

CREATE POLICY "Users update their own todos" ON public.todos
  FOR UPDATE TO authenticated USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid());

CREATE POLICY "Users delete their own todos" ON public.todos
  FOR DELETE TO authenticated USING (user_id = auth.uid());
```

```text output
CREATE POLICY
CREATE POLICY
CREATE POLICY
CREATE POLICY
```

<Happened>
<Tr>
<En>

- Four policies, one per action, all with the same idea: **the row's `user_id` must be the logged-in user's id**.
- `USING` filters which existing rows the user can see, update or delete. `WITH CHECK` validates the row being written, so a user can't insert a todo for someone else, or change a todo's owner.
- There's no policy for `anon`, so logged-out visitors still get nothing.
- In the dashboard you can also create these from **Authentication → Policies** using templates; they produce the same SQL.

</En>
<Ur>

- Chaar policies, har kaam ki ek, sab me ek hi khayal: **row ka `user_id` login user ki id hona chahiye**.
- `USING` filter karta hai ke user kaun si maujood rows dekh, update ya delete kar sakta hai. `WITH CHECK` likhi ja rahi row ko jaanchta hai, isliye user kisi aur ke liye todo nahi daal sakta, ya todo ka maalik nahi badal sakta.
- `anon` ki koi policy nahi, isliye logout visitors ko ab bhi kuch nahi milta.
- Dashboard me aap inhe **Authentication → Policies** se templates ke zariye bhi bana sakte hain; wo wahi SQL banate hain.

</Ur>
</Tr>
</Happened>

</Step>

<Step title="Test the policies as Sara and as Alex">

<Tr>
<En>
Now we pretend to be each user by setting the role and the user id, exactly what Supabase does for every API request from a logged-in user. (In the Supabase SQL editor, the **role** dropdown lets you impersonate a user the same way.)
</En>

```text

    .from("todos")
    .insert({ task })
    .select()
    .single();

    // error.message, error.code (a PostgreSQL error code such as 23514), error.details
```

- Show users a friendly message; log the details for yourself.

</En>

## Common mistakes

<Compare>
<Bad title="A table without RLS">

```text
create table public.messages (...);
-- the publishable key can now read and delete every message
```

</Bad>
<Good title="Enable RLS and add policies immediately">

```text
create table public.messages (...);
alter table public.messages enable row level security;
create policy "Read own" on public.messages
  for select to authenticated using (user_id = auth.uid());
```

</Good>
</Compare>

<Compare>
<Bad title="Secret key in the browser">

```text
NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY=...
```

<Tr>
<En>`NEXT_PUBLIC_` ships it to every visitor, and this key bypasses RLS completely.</En>
<Ur>`NEXT_PUBLIC_` ise har visitor tak bhej deta hai, aur ye key RLS ko poori tarah chhor deti hai.</Ur>
</Tr>

</Bad>
<Good title="Server-only variable">

```text
SUPABASE_SECRET_KEY=...   # read only in server code
```

</Good>
</Compare>

<Compare>
<Bad title="Ignoring the error">

```text
const { data } = await supabase.from("todos").select();
setTodos(data);   // null on failure, the page shows "no todos"
```

</Bad>
<Good title="Handle it">

```text
const { data, error } = await supabase.from("todos").select();
if (error) return showError(error.message);
setTodos(data);
```

</Good>
</Compare>

<Compare>
<Bad title="Security checks only in the front end">

```text
if (todo.user_id === user.id) {
  await supabase.from("todos").delete().eq("id", todo.id);
}
```

<Tr>
<En>An attacker skips your `if` and calls the API directly.</En>
<Ur>Hamla aawar aap ka `if` chhor kar seedha API call karta hai.</Ur>
</Tr>

</Bad>
<Good title="The database enforces it">

```text
create policy "Delete own" on public.todos
  for delete to authenticated using (user_id = auth.uid());
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **Policies that are too broad**, such as `using (true)` for `authenticated`, which lets every logged-in user read everyone's data.
- **Forgetting `WITH CHECK`** on insert and update policies, so users can write rows owned by others.
- **Changing the schema only by clicking in the dashboard.** Save changes as migration files so they can be reviewed and reproduced.
- **Trusting `getSession()` on the server** instead of `getUser()`.
- **Leaving Storage buckets public** when they hold private files.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **Bohot chauri policies**, jaise `authenticated` ke liye `using (true)`, jo har login user ko sab ka data parhne deti hai.
- **Insert aur update policies par `WITH CHECK` bhoolna**, jis se users doosron ki milkiyat wali rows likh sakte hain.
- **Schema sirf dashboard me click kar ke badalna.** Tabdeeliyan migration files ki shakal me mehfooz karein taa ke jaanchi aur dobara banayi ja saken.
- **Server par `getUser()` ke bajaye `getSession()` par bharosa.**
- **Private files wali Storage buckets ko public chhorna.**

</Ur>
</Tr>

## Remember

<Takeaways>
<Tr>
<En>

- Supabase = hosted PostgreSQL + automatic API + Auth + Storage + Realtime.
- The **URL and publishable key** are public; the **secret key** bypasses RLS and must stay on the server.
- Create tables with SQL; Supabase exposes them through the API immediately.
- **Enable RLS on every table.** Without it, anyone with your public key can read and change everything.
- Policies: `TO` who, `FOR` which action, `USING` which rows, `WITH CHECK` which new rows; usually `user_id = auth.uid()`.
- supabase-js mirrors SQL: `from().select().eq().order()`, `insert`, `update`, `delete`, `.select()` to return rows.
- Every call returns `{ data, error }`: check `error`.
- Auth users become `auth.uid()`; use `getUser()` on the server; generate types from your schema.

</En>
<Ur>

- Supabase = hosted PostgreSQL + khud ba khud bani API + Auth + Storage + Realtime.
- **URL aur publishable key** public hain; **secret key** RLS ko chhor deti hai aur server par hi rehni chahiye.
- Tables SQL se banayen; Supabase unhe foran API se pohanch me la deta hai.
- **Har table par RLS chalu karein.** Is ke baghair aap ki public key wala koi bhi sab kuch parh aur badal sakta hai.
- Policies: `TO` kaun, `FOR` kaun sa kaam, `USING` kaun si rows, `WITH CHECK` kaun si nayi rows; aam taur par `user_id = auth.uid()`.
- supabase-js SQL ka aks hai: `from().select().eq().order()`, `insert`, `update`, `delete`, rows wapas lene ke liye `.select()`.
- Har call `{ data, error }` wapas karti hai: `error` check karein.
- Auth users `auth.uid()` bante hain; server par `getUser()` lein; apne schema se types banayen.

</Ur>
</Tr>

<DeepDive title="How Supabase works under the hood">

**PostgREST.** The API is a server called PostgREST that turns HTTP requests into SQL. `GET /rest/v1/todos?select=task&is_done=eq.false` becomes `SELECT task FROM todos WHERE is_done = false`. supabase-js builds those URLs for you.

**JWTs and roles.** Each request carries a key and, when logged in, the user's JWT. PostgREST switches to the matching database role (`anon` or `authenticated`) and makes the token's claims available to SQL, which is how `auth.uid()` and `auth.jwt()` work. The secret key maps to `service_role`, which has `BYPASSRLS`.

**Policy performance.** Policies run for every row, so index the columns they use (`create index on todos (user_id);`) and wrap function calls as `(select auth.uid())` so PostgreSQL evaluates them once per query instead of once per row.

**Server-side logic.** For things that shouldn't be done from the browser (charging a card, sending emails, calling paid APIs with secret keys), use **Edge Functions**, Next.js route handlers or server actions, with the secret key kept on the server.

**Database functions.** `create function … security definer` runs with the creator's rights; useful but dangerous, so always set `search_path` and check permissions inside. Call them with `supabase.rpc("name", args)`.

**Migrations and local development.** The Supabase CLI runs the whole stack locally in Docker (`supabase start`), records schema changes as SQL migrations (`supabase migration new`, `supabase db diff`) and applies them to production (`supabase db push`).

**Realtime.** `supabase.channel("todos").on("postgres_changes", { event: "*", schema: "public", table: "todos" }, handler).subscribe()` delivers changes, and RLS decides which ones each user receives.

**Storage** buckets have their own policies on the `storage.objects` table, written the same way.

</DeepDive>

<DeepDive title="Real world: apps that forgot RLS">

Security researchers have repeatedly scanned public websites built on Supabase and similar platforms, looking for the project URL and public key in the JavaScript (which is normal) and then simply calling the API. A worrying number of apps, many of them generated quickly by AI coding tools, had tables with **RLS disabled** or with policies like `using (true)`. With nothing but the public key, the researchers could list users' emails, private messages, API tokens stored in tables, and in some cases update or delete data.

None of these were bugs in Supabase. The platform warns about tables without RLS, and the dashboard's **Security Advisor** lists them. The apps had simply been shipped without anyone writing policies.

The checklist teams now use before launch:

1. Every table in `public` has RLS enabled (the Security Advisor shows none missing).
2. Every policy has been read by a second person, with special attention to `using (true)` and missing `WITH CHECK`.
3. Tests that log in as two different users and confirm each can't see the other's data.
4. No secret key, admin password or third-party API key appears in front-end code or in a table readable by `anon`.

</DeepDive>

<DeepDive title="Security lens">

With Supabase, **the database is your backend's security layer**, so treat policies like code.

- **RLS on every exposed table**, deny by default, and grant exactly what's needed per role and action.
- **Never expose the secret key.** Not in `NEXT_PUBLIC_` variables, not in mobile apps, not in client-side logs. Rotate it immediately if it leaks.
- **Validate in the database:** `CHECK` constraints, `NOT NULL`, foreign keys and length limits stop bad data from any client.
- **Columns users mustn't change** (`role`, `is_admin`, `balance`) need protection beyond row ownership: keep them in a separate table only the server can write, or use column privileges or triggers. A policy that lets users update "their own profile row" lets them update **every** column of it.
- **Verify identity on the server** with `getUser()`, not by trusting a user id sent from the client.
- **Rate limits and abuse.** The API is public; enable CAPTCHA on sign-up, set password rules and email confirmation, and watch the logs.
- **Storage policies** for private buckets, and signed URLs with short expiry for sharing files.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What is Supabase?">
An open-source backend platform built on PostgreSQL. Each project provides a Postgres database with an automatically generated REST and GraphQL API through PostgREST, authentication, file storage, realtime subscriptions and serverless edge functions, accessed through client libraries such as supabase-js.
</QA>

<QA q="What is Row Level Security?">
A PostgreSQL feature that attaches policies to a table so the database filters and validates every row a query reads or writes based on the current role and context. In Supabase it is how access control is enforced for requests made directly from browsers, typically by comparing a user_id column with auth.uid().
</QA>

<QA q="What is the difference between the anon or publishable key and the service role or secret key?">
The publishable key is meant for clients and maps to the anon or authenticated role, so all access goes through RLS policies. The secret key maps to the service role, which bypasses RLS and has full access; it must only be used in trusted server environments.
</QA>

<QA q="What is the difference between USING and WITH CHECK in a policy?">
USING determines which existing rows are visible or can be updated or deleted. WITH CHECK validates the values of rows being inserted or the new values of updated rows, preventing users from writing rows they would not be allowed to own.
</QA>

<QA q="How does supabase-js report errors?">
Queries resolve to an object containing data and error rather than throwing. Code must check error, which includes a message and, for database errors, the PostgreSQL error code.
</QA>

<QA q="Why can a query return no rows instead of a permission error under RLS?">
For SELECT, UPDATE and DELETE, RLS policies act as an extra filter on the rows, so rows the user may not access are simply invisible, resulting in empty results or zero affected rows. Inserts or updates that fail WITH CHECK raise a row-level security violation error.
</QA>

</DeepDive>
