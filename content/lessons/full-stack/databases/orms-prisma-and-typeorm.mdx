<BigIdea>
<Tr>
<En>
An **ORM** (object-relational mapper) lets you work with database rows as **objects in your language**: `prisma.user.findMany({ include: { posts: true } })` instead of writing the SQL and mapping columns to fields yourself. It generates SQL, maps results to typed objects, handles relations, migrations and transactions, and protects against SQL injection by always using parameters. In Node.js the two most popular are **Prisma** (you write a `schema.prisma` file; it **generates a fully typed client**, so a misspelled field is a compile error) and **TypeORM** (you define **entities** as classes or schemas; you get **repositories**, relations and a **QueryBuilder** for complex queries). ORMs don't remove the need to understand SQL: a loop that loads related data one row at a time silently sends **N+1 queries**; aggregate results may come back as strings; and for reports or tricky queries you'll drop to **raw SQL**, which must still be parameterized. Use the ORM for everyday CRUD, check the SQL it generates, and reach for SQL when it's clearer or faster.
</En>
<Ur>
**ORM** (object-relational mapper) aap ko database rows ke saath **apni zaban ke objects** ki tarah kaam karne deta hai: SQL likh kar columns ko fields se khud milane ke bajaye `prisma.user.findMany({ include: { posts: true } })`. Ye SQL banata hai, nataij ko typed objects me badalta hai, relations, migrations aur transactions sambhalta hai, aur hamesha parameters istemal kar ke SQL injection se bachata hai. Node.js me do sab se mashhoor hain **Prisma** (aap `schema.prisma` file likhte hain; ye **mukammal typed client banata** hai, isliye ghalat likha field compile error hai) aur **TypeORM** (aap **entities** classes ya schemas ki shakal me bayan karte hain; aap ko **repositories**, relations aur pechida queries ke liye **QueryBuilder** milta hai). ORMs SQL samajhne ki zaroorat khatam nahi karte: mutaliqa data ek ek row load karne wala loop khamoshi se **N+1 queries** bhejta hai; aggregate nataij strings ban kar aa sakte hain; aur reports ya mushkil queries ke liye aap **raw SQL** par utrenge, jo phir bhi parameterized hona chahiye. Rozmarra CRUD ke liye ORM lein, jo SQL ye banata hai use check karein, aur jab SQL zyada wazeh ya tez ho to SQL lein.
</Ur>
</Tr>
</BigIdea>

## Picture it

<Tr>
<En>

Think of an ORM as an **interpreter** between you and a librarian who only speaks SQL.

- You say "give me every author with their books"; the interpreter translates, and hands back neat folders (objects) instead of raw index cards (rows).
- A good interpreter asks once: "all authors, and all books by those authors" (a join or a batched query).
- A careless request ("get the authors… now get author 1's books… now author 2's…") makes the interpreter walk to the librarian once per author: the **N+1 problem**. The words were simple; the trips were many.
- For unusual requests, you can still **speak SQL directly** (raw queries), but you must hand over your values on a separate slip (parameters), never written into the sentence.

</En>
<Ur>

ORM ko aap aur sirf SQL bolne wale librarian ke beech **tarjuman** samjhein.

- Aap kehte hain "har author apni kitabon ke saath do"; tarjuman tarjuma karta hai, aur kacche index cards (rows) ke bajaye saaf folders (objects) deta hai.
- Achha tarjuman ek dafa poochhta hai: "saare authors, aur un authors ki saari kitaben" (join ya batched query).
- Lapparwah darkhwast ("authors do… ab author 1 ki kitaben… ab author 2 ki…") tarjuman ko har author ke liye ek dafa librarian ke paas bhejti hai: **N+1 masla**. Alfaaz saade the; chakkar bohot.
- Ghair mamooli darkhwaston ke liye aap ab bhi **seedha SQL bol** sakte hain (raw queries), magar apni values alag parchi par deni hain (parameters), jumle me likh kar kabhi nahi.

</Ur>
</Tr>

## Learn it step by step

<Walkthrough>

<Step title="Prisma: typed client, include, aggregates, raw SQL">

<Tr>
<En>
A `User`/`Post` schema in `schema.prisma`, migrated and generated into a typed client. `demo.ts` runs directly with Node 22's TypeScript support and counts every SQL query Prisma sends. It creates four users with two posts each, loads posts the N+1 way and with `include`, runs an aggregate, compares safe and unsafe raw SQL, and finally `tsc` type-checks a file with two mistakes.
</En>
<Ur>
`schema.prisma` me `User`/`Post` schema, migrate kar ke typed client me generate kiya gaya. `demo.ts` Node 22 ki TypeScript sahulat se seedha chalta hai aur Prisma ki bheji har SQL query ginta hai. Ye do do posts wale chaar users banata hai, posts N+1 tareeqe se aur `include` se load karta hai, aggregate chalata hai, mehfooz aur ghair-mehfooz raw SQL milata hai, aur aakhir me `tsc` do ghaltiyon wali file type-check karta hai.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
psql -q -h localhost -U postgres -c 'DROP DATABASE IF EXISTS blog_prisma' -c 'CREATE DATABASE blog_prisma' 2> /dev/null
npm init -y > /dev/null && npm pkg set type=module
npm install -D prisma@7.10.1 typescript@5.9.3 --silent && npm install @prisma/client@7.10.1 @prisma/adapter-pg@7.10.1 pg@8.23.1 --silent
export DATABASE_URL=postgres://postgres:postgres@localhost:5432/blog_prisma
mkdir -p prisma
cat > prisma/schema.prisma <<'EOF'
generator client {
  provider            = "prisma-client"
  output              = "../generated/prisma"
  moduleFormat        = "esm"
  importFileExtension = "ts"
}
datasource db {
  provider = "postgresql"
}
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  name  String
  posts Post[]
}
model Post {
  id       Int     @id @default(autoincrement())
  title    String
  views    Int     @default(0)
  author   User    @relation(fields: [authorId], references: [id])
  authorId Int

  @@index([authorId])
}
EOF
cat > prisma.config.ts <<'EOF'
import { defineConfig } from 'prisma/config';
export default defineConfig({ schema: 'prisma/schema.prisma', datasource: { url: process.env.DATABASE_URL! } });
EOF
npx prisma migrate dev --name init > /dev/null 2>&1 && npx prisma generate > /dev/null 2>&1
cat > demo.ts <<'EOF'
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from './generated/prisma/client.ts';

const prisma = new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL! }), log: [{ emit: 'event', level: 'query' }] });
let queries = 0;
prisma.$on('query', () => queries++);
const count = async <T>(label: string, fn: () => Promise<T>): Promise<T> => { queries = 0; const r = await fn(); console.log(`${label.padEnd(44)} SQL queries: ${queries}`); return r; };

// Typed writes, including nested creates
for (const [i, name] of ['Jane Doe', 'John Smith', 'Ana Lee', 'Omar Ali'].entries())
  await prisma.user.create({ data: { name, email: `user${i}@example.com`,
    posts: { create: [{ title: `${name}'s first post`, views: 10 * (i + 1) }, { title: `${name}'s second post` }] } } });

// N+1: one query for users, then one per user
await count('N+1: users, then posts for each user', async () => {
  const users = await prisma.user.findMany();
  for (const u of users) await prisma.post.findMany({ where: { authorId: u.id } });
});
// include: Prisma loads the relation in a single round trip
const users = await count('include: users with their posts', () => prisma.user.findMany({ include: { posts: true }, orderBy: { id: 'asc' } }));
console.log(`   ${users[0].name} has ${users[0].posts.length} posts`);   // users is typed as (User & { posts: Post[] })[]

// Aggregates and typed filters
const stats = await prisma.post.aggregate({ _sum: { views: true }, _count: true, where: { views: { gt: 0 } } });
console.log('aggregate:', JSON.stringify(stats));

// The escape hatch: raw SQL. Tagged templates are parameterized...
const evil = "x' OR '1'='1";
const safe = await prisma.$queryRaw`SELECT count(*)::int AS n FROM "User" WHERE name = ${evil}`;
console.log('$queryRaw with ${…}:', JSON.stringify(safe));
// ...string-built SQL is not
const unsafe = await prisma.$queryRawUnsafe(`SELECT count(*)::int AS n FROM "User" WHERE name = '${evil}'`);
console.log('$queryRawUnsafe with a string:', JSON.stringify(unsafe), '<- SQL injection returned every user');
await prisma.$disconnect();
EOF
node demo.ts
# Node runs .ts by stripping types; tsc actually checks them
cat > typo.ts <<'EOF'
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from './generated/prisma/client.ts';
const prisma = new PrismaClient({ adapter: new PrismaPg({ connectionString: '' }) });
await prisma.user.findMany({ where: { emial: 'jane@example.com' } });     // typo in a field name
await prisma.post.create({ data: { title: 'Hi', views: 'many' } });       // wrong type for views
EOF
echo "--- tsc on code with mistakes:"
npx tsc --noEmit --strict --module nodenext --target es2022 --allowImportingTsExtensions --skipLibCheck typo.ts \
  | sed -E 's/^typo.ts\(([0-9]+),[0-9]+\): error TS[0-9]+: /line \1: /' | cut -c1-110
```

```text output
N+1: users, then posts for each user         SQL queries: 5
include: users with their posts              SQL queries: 2
   Jane Doe has 2 posts
aggregate: {"_sum":{"views":100},"_count":4}
$queryRaw with ${…}: [{"n":0}]
$queryRawUnsafe with a string: [{"n":4}] <- SQL injection returned every user
--- tsc on code with mistakes:
line 4: Object literal may only specify known properties, but 'emial' does not exist in type 'UserWhereInput'.
line 5: Type 'string' is not assignable to type 'number'.
```

<Happened>
<Tr>
<En>

- The **N+1** version sent **5** queries for 4 users (1 for users + 1 per user). With 1,000 users it would send 1,001. The code looked innocent; only counting queries reveals it.
- `include: { posts: true }` loaded everything in **2** queries (Prisma fetches users, then all their posts with one `IN (…)` query), no matter how many users. The result type is `(User & { posts: Post[] })[]`, so the editor autocompletes `users[0].posts`.
- `aggregate` computed sum and count in the database.
- The tagged template **`$queryRaw`** sent the dangerous string as a **parameter**: it matched no user (0). **`$queryRawUnsafe`** with a string-built query let `x' OR '1'='1` rewrite the SQL and return **every user** (4): classic SQL injection. Raw SQL inside an ORM is exactly as dangerous as raw SQL anywhere.
- Node ran `demo.ts` by **stripping** the types without checking them. `tsc` actually **checks**: it rejected the misspelled `emial` filter and a string for the numeric `views`, before any of it could run. Run `tsc --noEmit` in CI.

</En>
<Ur>

- **N+1** wale version ne 4 users ke liye **5** queries bhejin (users ki 1 + har user ki 1). 1,000 users ke saath 1,001 bhejta. Code masoom lagta tha; sirf queries ginna ise zahir karta hai.
- `include: { posts: true }` ne sab kuch **2** queries me load kiya (Prisma users laata hai, phir un ki saari posts ek `IN (…)` query se), chahe users kitne hon. Nateeje ki type `(User & { posts: Post[] })[]` hai, isliye editor `users[0].posts` khud mukammal karta hai.
- `aggregate` ne database me sum aur count nikala.
- Tagged template **`$queryRaw`** ne khatarnak string ko **parameter** ke tor par bheja: kisi user se mel nahi khaya (0). String se bani query ke saath **`$queryRawUnsafe`** ne `x' OR '1'='1` ko SQL dobara likhne diya aur **har user** (4) lautaya: mashhoor SQL injection. ORM ke andar raw SQL bilkul utna hi khatarnak hai jitna kahin bhi.
- Node ne `demo.ts` types ko check kiye baghair **hata kar** chalaya. `tsc` asal me **check** karta hai: us ne ghalat likha `emial` filter aur numeric `views` ke liye string kuch bhi chalne se pehle rad kiye. CI me `tsc --noEmit` chalayen.

</Ur>
</Tr>
</Happened>

<Step title="TypeORM: repositories, relations, QueryBuilder, transactions">

<Tr>
<En>
The same blog in TypeORM, written in plain JavaScript with `EntitySchema` (in TypeScript you'd usually use decorated classes). A custom logger counts queries. `synchronize: true` creates the tables from the entities for this demo. We repeat the N+1 comparison, build a grouped query with the QueryBuilder, and run a transaction that fails halfway.
</En>
<Ur>
Wahi blog TypeORM me, `EntitySchema` ke saath saade JavaScript me likha (TypeScript me aam taur par decorated classes lagti hain). Ek custom logger queries ginta hai. Is demo ke liye `synchronize: true` entities se tables banata hai. Hum N+1 ka muqabla dohrate hain, QueryBuilder se grouped query banate hain, aur aisi transaction chalate hain jo beech me nakam ho.
</Ur>
</Tr>

```bash
export PGPASSWORD=postgres
psql -q -h localhost -U postgres -c 'DROP DATABASE IF EXISTS blog_typeorm' -c 'CREATE DATABASE blog_typeorm' 2> /dev/null
npm install typeorm@1.1.3 --silent
cat > typeorm-demo.js <<'EOF'
import { DataSource, EntitySchema } from 'typeorm';

// Entities can be classes with decorators (TypeScript) or schemas like these (plain JavaScript)
const User = new EntitySchema({
  name: 'User', tableName: 'users',
  columns: { id: { type: Number, primary: true, generated: true }, email: { type: String, unique: true }, name: { type: String } },
  relations: { posts: { type: 'one-to-many', target: 'Post', inverseSide: 'author' } },
});
const Post = new EntitySchema({
  name: 'Post', tableName: 'posts',
  columns: { id: { type: Number, primary: true, generated: true }, title: { type: String }, views: { type: Number, default: 0 } },
  relations: { author: { type: 'many-to-one', target: 'User', joinColumn: { name: 'author_id' }, inverseSide: 'posts' } },
});

let queries = 0;
const ds = new DataSource({
  type: 'postgres', url: 'postgres://postgres:postgres@localhost:5432/blog_typeorm', entities: [User, Post],
  synchronize: true,                       // creates tables from the entities: fine for a demo, never in production
  logger: { logQuery: () => queries++, logQueryError() {}, logQuerySlow() {}, logSchemaBuild() {}, logMigration() {}, log() {} },
  logging: ['query'],
});
await ds.initialize();
const users = ds.getRepository('User'), posts = ds.getRepository('Post');
const count = async (label, fn) => { queries = 0; const r = await fn(); console.log(`${label.padEnd(44)} SQL queries: ${queries}`); return r; };

for (const [i, name] of ['Jane Doe', 'John Smith', 'Ana Lee', 'Omar Ali'].entries()) {
  const u = await users.save({ name, email: `user${i}@example.com` });
  await posts.save([{ title: `${name}'s first post`, views: 10 * (i + 1), author: u }, { title: `${name}'s second post`, author: u }]);
}

await count('N+1: users, then posts for each user', async () => {
  for (const u of await users.find()) await posts.find({ where: { author: { id: u.id } } });
});
const withPosts = await count('relations: users with their posts (a JOIN)', () => users.find({ relations: { posts: true }, order: { id: 'ASC' } }));
console.log(`   ${withPosts[0].name} has ${withPosts[0].posts.length} posts`);

// QueryBuilder for anything the simple API can't express
const top = await ds.getRepository('User').createQueryBuilder('u')
  .leftJoin('u.posts', 'p').select('u.name', 'name').addSelect('COALESCE(SUM(p.views), 0)', 'views')
  .groupBy('u.id').orderBy('views', 'DESC').limit(2).getRawMany();
console.log('top authors by views:', JSON.stringify(top));

// Transactions: both saves or neither
try {
  await ds.transaction(async (tx) => {
    const u = await tx.getRepository('User').save({ name: 'Tom', email: 'tom@example.com' });
    await tx.getRepository('Post').save({ title: 'Hello', author: u });
    await tx.getRepository('User').save({ name: 'Copy', email: 'tom@example.com' });   // duplicate email → error
  });
} catch (e) { console.log('transaction failed:', e.code === '23505' ? 'duplicate email, rolled back' : e.message); }
console.log('users named Tom after the failed transaction:', await users.countBy({ name: 'Tom' }));
await ds.destroy();
EOF
node typeorm-demo.js
```

```text output
N+1: users, then posts for each user         SQL queries: 5
relations: users with their posts (a JOIN)   SQL queries: 1
   Jane Doe has 2 posts
top authors by views: [{"name":"Omar Ali","views":"40"},{"name":"Ana Lee","views":"30"}]
transaction failed: duplicate email, rolled back
users named Tom after the failed transaction: 0
```

<Happened>
<Tr>
<En>

- The N+1 loop sent **5** queries again; `relations: { posts: true }` sent **1**, a single SQL `LEFT JOIN`. Different ORMs load relations differently (one join, or one query per relation), but both beat N+1.
- The **QueryBuilder** expressed a `LEFT JOIN … GROUP BY … ORDER BY … LIMIT` with column aliases. Note that **`views` came back as a string** (`"40"`): PostgreSQL returns `SUM` as `bigint`/`numeric`, which the `pg` driver turns into strings to avoid losing precision in JavaScript. Convert deliberately (`Number(…)`, or cast to `int` in SQL) when you know the values are small.
- In `ds.transaction`, the third save hit the unique email constraint (`23505`), so the **whole transaction rolled back**: Tom and his post never existed. Use the `tx` manager passed to the callback for every query inside, or the queries run outside the transaction.
- `synchronize: true` is convenient for demos but can drop columns or data when entities change. Production uses **migrations** (the next lesson).

</En>
<Ur>

- N+1 loop ne phir **5** queries bhejin; `relations: { posts: true }` ne **1**, ek SQL `LEFT JOIN`. Mukhtalif ORMs relations alag tarah load karte hain (ek join, ya har relation ki ek query), magar dono N+1 se behtar hain.
- **QueryBuilder** ne column aliases ke saath `LEFT JOIN … GROUP BY … ORDER BY … LIMIT` bayan kiya. Dhyan dein ke **`views` string ban kar aaya** (`"40"`): PostgreSQL `SUM` ko `bigint`/`numeric` lautata hai, jise `pg` driver JavaScript me darusti khone se bachane ke liye strings banata hai. Jab maloom ho ke values chhoti hain to jaan boojh kar badlein (`Number(…)`, ya SQL me `int` cast).
- `ds.transaction` me teesra save unique email constraint (`23505`) se takraya, isliye **poori transaction rollback** hui: Tom aur us ki post kabhi mojood nahi the. Andar har query ke liye callback me diya gaya `tx` manager istemal karein, warna queries transaction ke bahar chalti hain.
- `synchronize: true` demos ke liye aasan hai magar entities badalne par columns ya data mita sakta hai. Production **migrations** istemal karta hai (agla lesson).

</Ur>
</Tr>
</Happened>

## Common mistakes

<Compare>
<Bad title="Loading relations in a loop">

```text
const orders = await prisma.order.findMany();
for (const o of orders) o.customer = await prisma.customer.findUnique({ where: { id: o.customerId } });   // N+1
```

</Bad>
<Good title="Ask for the relation once">

```text
const orders = await prisma.order.findMany({ include: { customer: true } });
// TypeORM: repo.find({ relations: { customer: true } })
```

</Good>
</Compare>

<Compare>
<Bad title="Fetching whole rows and filtering in JavaScript">

```text
const all = await prisma.post.findMany();                          // 2 million rows
const popular = all.filter((p) => p.views > 1000).slice(0, 10);
```

</Bad>
<Good title="Let the database filter, sort and limit">

```text

  where: { views: { gt: 1000 } }, orderBy: { views: 'desc' }, take: 10, select: { id: true, title: true },
});
```

</Good>
</Compare>

<Tr>
<En>

More mistakes to avoid:

- **`$queryRawUnsafe` / string-built `query()`** with user input: SQL injection. Use tagged templates or parameter arrays.
- **`synchronize: true` in production** (TypeORM): schema changes can drop data; use migrations.
- **Forgetting the transaction manager**: inside `ds.transaction(async (tx) => …)`, queries through the global repository aren't in the transaction.
- **Selecting everything**: use `select` to avoid sending large or sensitive columns (like `passwordHash`) to the app.
- **Trusting the ORM blindly**: turn on query logging in development and check `EXPLAIN` for slow ones.

</En>
<Ur>

Bachne wali mazeed ghaltiyan:

- **User input ke saath `$queryRawUnsafe` / string se bana `query()`**: SQL injection. Tagged templates ya parameter arrays lein.
- **Production me `synchronize: true`** (TypeORM): schema tabdeeliyan data mita sakti hain; migrations lein.

- **ORM par andha bharosa**: development me query logging on karein aur sust queries ke liye `EXPLAIN` dekhein.

</Ur>

<Challenge title="Find the N+1">

<Tr>
<En>
A GraphQL or REST endpoint lists 50 orders, and for each shows the customer name and the number of items. Query logs show 101 queries per request. Explain where they come from and rewrite the data loading so it uses at most 2–3 queries.
</En>
<Ur>
Ek GraphQL ya REST endpoint 50 orders list karta hai, aur har ek ke saath customer ka naam aur items ki ginti dikhata hai. Query logs har request par 101 queries dikhate hain. Batayen ke ye kahan se aati hain aur data loading dobara likhein taa ke zyada se zyada 2–3 queries hon.
</Ur>
</Tr>

<Solution>

<Tr>
<En>
1 query loads the orders, then **for each of the 50 orders** one query loads the customer and one counts the items: 1 + 50 + 50 = 101. Load everything at once:

```text
prisma.order.findMany({
  take: 50, orderBy: { createdAt: 'desc' },
  select: { id: true, createdAt: true, customer: { select: { name: true } }, _count: { select: { items: true } } },
})
```

Prisma runs a few batched queries regardless of the number of orders. In TypeORM, a QueryBuilder with `leftJoin` on customer and a `COUNT` subquery, or two `IN (…)` queries, does the same. In GraphQL, use DataLoader for the per-field resolvers.

</En>
<Ur>
1 query orders load karti hai, phir **50 orders me se har ek** ke liye ek query customer load karti aur ek items ginti hai: 1 + 50 + 50 = 101. Sab kuch ek saath load karein:

```text
prisma.order.findMany({
  take: 50, orderBy: { createdAt: 'desc' },
  select: { id: true, createdAt: true, customer: { select: { name: true } }, _count: { select: { items: true } } },
})
```

Prisma orders ki ginti se qata-e-nazar chand batched queries chalata hai. TypeORM me customer par `leftJoin` aur `COUNT` subquery wala QueryBuilder, ya do `IN (…)` queries, yahi karti hain. GraphQL me har field ke resolvers ke liye DataLoader lein.

</Ur>

<DeepDive title="More about ORMs">

**Active Record vs Data Mapper.** TypeORM supports both: entities with `save()` on themselves (Active Record) or repositories that save entities (Data Mapper). Prisma is closer to a query builder with generated types.

**Lightweight alternatives.** Drizzle and Kysely are typed SQL builders: closer to SQL, fewer abstractions, still type-safe. Some teams use plain `pg` with typed helpers.

**Loading strategies.** Eager vs lazy loading; TypeORM lazy relations return promises and can cause N+1 quietly. Prefer explicit loading per query.

**Big numbers.** `bigint` IDs may come back as strings or `BigInt`; decide how your API serializes them.

**Connection pools.** ORMs pool connections; serverless functions may need an external pooler or Prisma's adapters to avoid exhausting the database.

**NestJS.** See Database with Prisma and Database with TypeORM for the framework integrations.

</DeepDive>

<DeepDive title="Real world: the ORM that sent 30,000 queries">

A logistics dashboard showed shipments with their carrier, destination and the last tracking event. In development, with 20 shipments, it loaded instantly. In production, with a page size of 500 and three lazily loaded relations per shipment, a single page view sent over 1,500 queries, and the "export all" button sent 30,000. The database CPU hit 100% every morning when operators opened the dashboard.

The fixes:

1. Query logging in staging with a per-request query counter, and an alert when a request exceeds 50 queries.
2. Explicit `relations` / `include` for everything the page displays, and `select` to limit columns.
3. The "last tracking event" moved to a single SQL query with `DISTINCT ON (shipment_id)`, run through the ORM's raw query API with parameters.
4. The export became a background job streaming results in batches.

</DeepDive>

<DeepDive title="Security lens">

- **Parameterize raw SQL**: `$queryRaw` tagged templates, `query(sql, [params])`; never `$queryRawUnsafe` or string concatenation with input.
- **Mass assignment**: don't pass `req.body` straight to `create`/`save`; pick allowed fields with DTOs, or users can set `role: 'admin'`.
- **Select carefully**: exclude password hashes, tokens and internal fields from queries feeding API responses.
- **Least-privilege database user** for the app; migrations run with a separate role.
- **Keep ORMs updated**: query builders have had injection bugs in edge cases.

</DeepDive>

<DeepDive title="Interview questions">

<QA q="What are the pros and cons of using an ORM?">
Pros: less boilerplate, typed models, relations and migrations handled, parameterized queries by default, database portability. Cons: hidden or inefficient SQL such as N+1, learning curve, limits for complex queries, and a temptation to ignore how the database works.
</QA>

<QA q="What is the N+1 problem and how do ORMs solve it?">
Loading a list with one query and then related data with one query per item. ORMs provide eager loading such as include or relations, which use joins or batched IN queries, and tools like DataLoader batch loads in GraphQL.
</QA>

<QA q="How do Prisma and TypeORM differ?">
Prisma is schema-first: a Prisma schema generates a typed client and migrations, and results are typed by the exact selection. TypeORM is entity-first: decorated classes or schemas define tables, with repositories, a QueryBuilder and both Active Record and Data Mapper patterns.
</QA>

<QA q="How do you run raw SQL safely through an ORM?">
Use the ORM's parameterized raw query API, such as Prisma's tagged $queryRaw or TypeORM's query with a parameter array, so values are sent separately from the SQL text; never build SQL strings from user input.
</QA>

<QA q="When would you not use an ORM?">
For complex reporting and analytics, performance-critical queries, bulk operations or database-specific features, where raw SQL or a lightweight query builder is clearer and gives more control, often used alongside the ORM.
</QA>

</DeepDive>
